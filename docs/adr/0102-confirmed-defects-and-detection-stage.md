## コンテキスト

[#413](https://github.com/Takenori-Kusaka/process-compass/issues/413) は、#408 の会議体の品質監査の委員が残した論点です。運用メトリクスの「欠陥の検出工程」は、AI の指摘から起票された報告と人が確定した欠陥を区別しない。AI が大量に起票すると上流での検出が増えたように見える、というものです。調査(`research/413-deliberation/survey-413-*.md`)と、起案・現場・品質監査・規格・弁護の 5 委員の会議体(`research/413-deliberation/`)を経ました。

### 見つかったこと

- 問いの手前に、より重い欠陥があった。指標の算出元として「起票テンプレートで必須化」された「検出ゲート」欄を挙げていたが、準拠テンプレートの不具合の様式にその欄は無かった。集計の実装と実装マークも無かった。それでも附属書H は、この指標を C4・C9・H.7・H.9 問5・EV-0062 の観測として引いていた
- 警戒サインが比率(G-7 以降の検出比率)だったため、上流の起票が分母を膨らませ、水増しの経路の大部分を作っていた
- 「欠陥」の確定の規定が無かった。重大度の判定に AI の参加を許していた
- 重大度の定義が 2 つあり、交差していた。障害対応の Sev1〜Sev4 は初動の緊急度で、Sev2 は「回避策なし」。欠陥トリアージ基準の Sev1〜Sev3 は 1.4 の用語で、Sev2 は「回避策あり」。主要機能の障害で回避策のある運用の事象は障害対応で Sev3 になり、ポストモーテムが書かれず、欠陥の台帳に行が足されず、委任が止まらなかった
- 外部: 用語体系は報告(anomaly)と確定した欠陥(defect)を分ける。ODC は検出の属性と確定の属性を別の時点で付ける。AI のレビューの製品は投稿と受理を分けて数え、公表される誤検出率・有用率は人の判断を真値にする。受理を確定と同一視すると、正しいが価値の低い指摘も数える。DORA の不安定性の指標は、本番で介入を要した事後の事象で数える

## 決定

### 1. 算出元と指標(運用メトリクス)

- 算出元の正本を欠陥の台帳 1 つにする。Issue の様式は報告の入口に留める。「起票テンプレートで必須化」の記述を削る
- 指標を、マージの後に見つかった確定した欠陥の、工程ごとの件数に改める。同じ範囲で取り込んだ変更の件数と並べる。警戒サインを比率でなく、運用で確定した欠陥の件数の推移とする(EV-0207、E1)
- PR の中で直った指摘は数えない。独立レビュー(G-6)の検出能力は第5章 5.6.2 の欠陥注入で測る
- 附属書H の観測から外さない。集計の手段が無い構成では「未測定」と開示する。EV-0062 の差し替え条件を、運用で確定した欠陥の件数へ改める
- 準拠テンプレートでは、出荷の証跡の集約が品質レポートに出す(IMPL-0392)。確定日で出荷の範囲に絞って数え、未処分の件数は現時点の行数を出す。期をまたぐ推移の判定は、前回の出力との並記までで、増加の判定は採用者が行う(IMPL-0394。降りていない。採用者に委ねる理由は、期の区切りと比べ方が組織の運用で決まるため)

### 2. 数える母集団

- 第1章 1.4 に「不具合の報告」と「確定した欠陥」を置く
- 数えるのは、欠陥の台帳の処分が「欠陥」で、確定した者(人)と確定日のある行だけとする。AI のレビューの指摘の採用・適用は確定に当たらない
- 確定した者に、作成を指示した者を含めてよい。「欠陥でない」「取り下げ」には理由を書く。運用の報告を原因の変更の作成を指示した者が「欠陥でない」「取り下げ」とした行は、集約が示す(EV-0208、E0)
- 処分は統制を緩めない。G-7 基準2 と委任の停止は、処分によらず台帳の行を読む
- 起票の経路(人 / AI の層 / 機械の検査 / 利用者 / 運用の事象)を列として記録する。経路ごとの件数は指標にせず、対外にも出さない(運用メトリクス「採用しない指標」に足す)
- 確定した者の欄を、個人の評価に用いない
- 「人確定」の語を、欠陥の確定に使わない

### 3. 工程の帰属

- 欠陥は、その欠陥についての報告が最初に記録された時点で進んでいた工程に数える。確定した時点・確定した者のゲートでは決めない。AI の層は工程に数えない。「欠陥でない」とした報告の後に下流で顕在化した欠陥は、顕在化した工程の新しい報告として数える(EV-0209、E1)
- 欠陥の台帳に列「検出した工程」を足す。既存の列「検出の時点」は変えず、食い違う行を集約が示す

### 4. 重大度

- 欠陥の重大度の正本を、欠陥トリアージ基準(第4章)の 3 段階とする。AI は判定の材料と案を示してよく、台帳の重大度は人が確定する
- 障害対応の 4 段階を、初動の緊急度 U1〜U4 へ改める(「等級」は保証の水準に使わないとした語、「E」は根拠の水準の記号と衝突するため避けた)。緊急度を重大度へ写さない
- ポストモーテムを、緊急度 U1・U2 の事象と、原因の欠陥の重大度が Sev1・Sev2 の事象に必須とする。原因の欠陥の重大度は、復旧の後、緊急度によらずすべての事象について、トリアージ基準により人が判定する。ポストモーテムの要否はこの判定で決まる(判定をポストモーテムの中に置くと、要否の判定が循環するため。IMPL-0396)
- 不具合の報告の様式の重大度の文言を、トリアージ基準に揃える(IMPL-0395)

### 課さないと決めたこと

次は、検討したうえで課さないと決めたことです。書かれていないのではありません。

- 不具合の報告の様式に、検出ゲートの欄を必須で置くこと
- PR の中で直った指摘を全件記録させること
- 起票の経路ごとの件数を指標にすること、対外に出すこと
- 確定した者を、作成を指示した者以外に限ること
- AI の報告を、全件人が再現してから確定すること
- 未処分の件数に警戒サインを付けて指標にすること
- 処分で統制(G-7 基準2・委任の停止)を解くこと
- 欠陥の台帳に「原因のゲート」(本来捕まえるべきだったゲート)の列を置くこと。事後検証の判断であり、台帳には既に「原因の変更」の列があり、ポストモーテムが原因と再発防止を記録する
- 障害対応の尺度へ欠陥の重大度を統合すること
- 新しい内部監査の観点を足すこと

## 検討した選択肢

| 選択肢 | 出した者 | 採否と理由 |
| --- | --- | --- |
| 不具合の様式に検出ゲートを必須で足す | 現行の記述 | 採らない(5 委員一致)。API からの起票に効かず、PR の中の検出が漏れる |
| 指標を附属書H の観測から外す | 検討 | 採らない(5 委員一致)。外すと EV-0062 が反証の経路を失う |
| 列「検出の時点」を「検出の工程」に置き換える | 起案 | 採らない。委任の停止の入力(ADR-0081)を変える。列を足して食い違いを示す |
| 比率の警戒サインを残す | 現行 | 採らない。上流の起票が分母を膨らませる |
| AI が出所の報告を一律に除く | 検討 | 採らない(5 委員一致)。AI が見つけ人が確定した実際の欠陥を落とす |
| 起票の経路を記録し、経路ごとの値を出す | 現場・品質監査・規格・起案(記録) | 記録は採る。値は採らない(弁護)。ADR-0092 決定4 の裏口になる |
| 起票の経路を記録しない | 弁護 | 採らない。監査と原因の分析(AI の報告の滞留、誤検出の傾向)の材料が無くなる |
| 確定した者を作成を指示した者以外に限る | 品質監査(運用の報告の処分) | 採らない。1〜2 名の体制で確定できない。統制を処分で解かないことで、隠す向きの誤りを測定に留める |
| 未処分の件数に警戒サインを付ける | 起案 | 採らない(現場)。報告の起票量に左右される |
| 確定した時点・確定した者のゲートに帰属させる | 検討 | 採らない(5 委員一致)。確定の遅れで工程の分布が動く |
| 指摘が出たゲートに帰属させ、不採用の後の顕在化は顕在化したゲートとする | 弁護 | 採る規則の帰結と同じ。「報告が最初に記録された工程」の規則として書く |
| 原因のゲートの列を台帳に置く | 現場・品質監査 | 採らない。事後検証の判断で、ポストモーテムが受け持つ |
| 障害対応の 4 段階へ統合する | 検討 | 採らない(5 委員一致)。初動では回避策の有無が確かめられないことがある |
| 重大度の食い違いを別の Issue へ送る | 検討 | 採らない(5 委員一致)。委任の停止の穴に直結する |

## 影響

- 運用メトリクス(品質の指標の表、数え方の所在、採用しない指標)
- 第4章 欠陥トリアージ基準の節「確定した欠陥と検出した工程」(数え方、IMPL-0392〜0394、EV-0207〜0209)
- 第1章 1.4(不具合の報告、確定した欠陥)
- 第4章 欠陥トリアージ基準(AI の参加の範囲、正本の宣言、原因の欠陥の重大度を復旧の後にすべての事象で判定すること、IMPL-0395・0396)
- 附属書H(C4 の兆候、H.7 の表、EV-0062 の差し替え条件)
- インシデント対応(初動の緊急度 U1〜U4、ポストモーテムの条件)と、緊急度の語に揃えた頁(こんなときどうする、開発避難訓練、運用フェーズの概要、リスクカタログ、導入の手引き、第3章、D-0 の見直しの契機)
- 準拠テンプレート: 欠陥の台帳の様式、不具合の報告の様式、障害時の補助ファイル、出荷の証跡の集約(`readDefectStages`)と試験
- 残るリスク: 処分の記名だけで確定とすると、定型の記名に収束しうる(内部監査の既存の観点と 7.7.8 で見る)。件数の少ない体制では件数の推移から傾向を読めない
