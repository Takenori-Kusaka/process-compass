## コンテキスト

[#360](https://github.com/Takenori-Kusaka/process-compass/issues/360) は、PR 単位の検査・ルールセット・AI レビュー・カバレッジのアダプタに欠けがある 10 件の実装マークを扱いました。Issue 本文のマークの番号は、付け直しの後の番号とずれていました(`research/360-deliberation/intake.md`)。軽の2委員の結論が割れ、go の扱いで ADR どうしの食い違いが重大度「高」と出たため、重へ上げました。

内部の調査(`research/360-deliberation/survey.md`)で、次のことが分かりました。

- go のアダプタは `coverageSummary` が null で、カバレッジの検査は基準3 を測らずに通過(終了コード 0)を返す。G-5 は緑のまま通る。範囲を「変更」にした構成だけを契約検査が止める
- python の coverage.py の出力は文の開始行の集合で、node と同じ近似で変更の範囲を測れる。go の coverprofile はブロック単位で、ソースを構文木で読めば文の開始行へ戻せる
- 準拠テンプレートの検証の弱体化の一覧は削除行だけを見る。行の追加だけで書ける skip・xfail の付与を一覧に出さない
- GitHub のルールセットの規則は ref の更新に掛かり、マージと直接の push を区別しない。AI の担い手による `gh pr merge` はフックが拒否する

外部の調査(`research/360-deliberation/survey-external.md`)では、次のことが分かりました。

- diff-cover・Codecov の既定は、測れない・報告の無い場合に通す向き。報告の無い行を 0% と数える SonarQube の型が、本標準の「未実施は失敗」に近い
- GitHub・GitLab のいずれも、push を許して中間へのマージだけを拒む設定を持たない。スタック型 PR の道具は、下から既定ブランチへ着地させる手順で避けている
- pytest の xfail は、既定では予期せず通っても失敗しない。Jest の `test.failing`・Vitest の `test.fails` は、予期せず通ると失敗にする。go の testing と JUnit 5 は、落ちることを期待する印を持たない

5 委員(起案・現場・品質監査・規格・弁護)の会議体は、go の扱いについて一致しました。誤りは ADR-0085 決定2 の go の句であり、ADR-0121 の限定もその誤りを引き継いでいる、という結論です。議長の裁定は `research/360-deliberation/decision.md` の「重の裁定」にあります。

## 決定

### 1. go の基準3 を測らずに通す扱いを誤りと認め、測れない構成を未実施の失敗にする

- ADR-0085 決定2 の go の句は誤りである。実装が存在する段階で「実施しない」を記録して通すことは、第4章 G-5「検査対象が存在しない場合の扱い」が禁じる「対象なし」の通過と同じ働きをする。未実施を失敗として数える規定に反する
- go の基準3 は `coverage.out`(coverprofile)から測る。全体の割合は文の数の割合とする(`go tool cover -func` の合計と同じ値)。変更の範囲は、ソースの構文木から各文の開始行を得て、その文を含むブロックの回数を行の被覆とする。node・python と同じ「文の開始行」の近似である
- python の基準3 は coverage.py の `coverage json` の文の開始行から、変更の範囲まで測る。全体の割合は、テストのファイルを除いて数える
- 言語のアダプタ(node・python・go)で集計の記録が出ない構成は、未実施として失敗にする
- 移行の猶予は置かない。猶予の期間の間、測らない通過が続くためである。既存の採用者には、準拠テンプレートの更新を取り込む時点で効く。落ちうる検査と直し方は「影響」に列挙する(ADR-0085 決定6)

### 2. 検証の弱体化の検出の範囲を広げ、表示だけにする

- 基底に無い新しいテストのファイル、追加行の skip・xfail・only、削除行のアサーション、同じ塊の中の削除と追加のアサーションの対(旧・新)を検出する
- 製品のコードを変えずに既存のテストを変えた変更を、名前どおりの近似として表示する。「テストだけの変更で失敗が解消した」ことは、この近似では確かめない(push ごとの履歴か、旧版の試験の再実行が要る)
- 期待値の改めの根拠は、PR 本文の表に識別子(判断記録・受入基準・条項)で書く。表の無い改めと、解決できない識別子を表示する
- 正本は、既定ブランチのコードで計算するジョブの要約とする。PR の側のコメントは閲覧の便宜とする。ラベルは使わない。ラベルは誰でも外せるためである
- いずれも G-5 の合否に使わない(第5章 5.8.5 の後の段落)。0 件のときも、検出しない形を定型の文で出す

### 3. 落ちることを期待する印の書式を定め、予期せず通った場合の失敗を枠組みごとに降ろす

- 準拠テンプレートは、枠組みに依らない注釈の書式を定める。`pit-in: known-failure issue=#NNN match="<照合する失敗の理由>" review=YYYY-MM`。欄の欠けと見直しの時期の超過は表示だけにする
- pytest は、`strict` の無い xfail の付与を G-5 の失敗にする。試験の中で `pytest.xfail()` を呼ぶ形も失敗にする。呼んだ時点で試験を終えるため、予期せず通った場合を検出できないからである。予期せず通った場合を試験の失敗とする規定の強制である。検出を合否に使う扱いには当たらない
- 失敗の理由の照合と、印を持たない枠組みは採用者が実装する(`plan=adopter`)。採用者に委ねる理由と求めることは次の表による

| 枠組み | 予期せず通った場合 | 失敗の理由の照合 | 採用者に求めること |
| --- | --- | --- | --- |
| pytest | `strict` で失敗(準拠テンプレートが付与を検査する) | `raises=` で例外の型を照合できる | 照合する理由を `raises=` か注釈の `match` で書き、`raises=` を使えない場合は補助の関数で照合する |
| Jest(`test.failing`)・Vitest(`test.fails`) | 枠組みが失敗にする | 落ちることだけを見る | 理由の照合が要る場合は、試験の中で失敗の内容を確かめる補助を書く |
| go の testing・JUnit 5 ほか | 印が無い | 印が無い | 印を自前の補助で実装するか、印を使わずに試験を直す。`t.Skip` は skip 相当として検出される |

### 4. 中間の層へのマージを拒否する設定を課さない

- ホスティングに、作業ブランチへの push を許して中間へのマージだけを拒む手段が無い。採用者も実装できない。降ろす見込みとして `scheduled`、採用者の実装として `adopter` と表示することは、どちらも事実に反する
- 本文の禁止(既定ブランチ以外へ取り込むマージをしてはならない)は維持する。準拠テンプレートは、人の手順の案内と、マージの後の検出で降ろす。検出は出荷の集約に「検出あり・0 件・未確認」で出し、合否に使わない
- AI の担い手の拒否は、フックが拒否する経路(`gh pr merge`、API による PR のマージ)に限って降りた扱いにする。`git merge` と `git push` の組は降りていない。マージの後の検出は、PR を経ない取り込みを拾わない

### 5. AI の確認の入力の記録と指摘の欠落の表示を、列挙できる範囲で降ろす

- ワークフローが列挙できる入力をパスと sha256 で書き出す。候補は読み込まれうるものの上限であり、実際に読み込まれたものではない
- 道具にしか分からない入力は、差し込み口の契約のファイルで受ける。ファイルが無い確認は「列挙できない確認」と表示する。契約の実装は採用者による(`plan=adopter`)。差し込む道具ごとに、渡す入力の取り出し方が異なるためである
- 構造化された指摘の所在・根拠の欠落を表示する。指摘は消さず、合否に使わない。構造を満たしたことを、内容が成り立つ根拠にしない(附属書H H.4)
- 記録を四半期の抜き取りまで残すことは、まだ降りていない。実行の記録の保持の既定に頼らない

### 6. L2 の採点の稼働の機械の検証を課さない

- 自己申告を超えて検査できる条件が定まらない。条件を条項に定めることは採用者への新しい義務であり、条件の候補(採点の出力の記録)は照合する相手を持たない
- L2 の宣言の根拠が記録で示されているかは、変化点の決定者が根拠の中身を L2 の条件に照らして読んで確かめる
- 規模の基準なしが効いた PR の結果には、根拠の中身を機械で確かめていない旨を毎回出す

## 採らなかった案

| 案 | 採らない理由 |
| --- | --- |
| ADR-0085 決定2 の go の扱いを維持し、開示だけを足す | 開示つきの通過は G-5 の語彙の外の第3の状態になる(ADR-0121 の (c3) と同じ) |
| go の変更の範囲を、変更行に重なるブロックを文の数で重みづけて測る | 分母の定義が本文の「文の開始行」と食い違う |
| go のブロックの範囲の全行を被覆とする | 割合を上へ寄せる |
| go・python の採用者に猶予の期間か警告の段を置く | 猶予の間、測らない通過が続く |
| 静的な近似を「テストだけの変更で失敗が解消した変更」の検出と表示する | 同じ PR で製品とテストを変えた自己修正のほとんどを拾わず、拾ったと誤読される |
| 検証の弱体化の検出・期待値の差分・パスの差・マージの後の検出を、G-5 または出荷の失敗にする | 第5章 5.8.5 の後の段落と衝突する。正当な変更と区別できない |
| 期待値の改めの根拠を、試験のコードの注釈に書く | 根拠を消す変更と同じ差分で消える |
| 落ちることを期待する印を、一覧のファイルに書く | 印と試験のコードが離れ、試験の移動で照合が切れる |
| 「テストだけの変更で失敗が解消した」ことの観測の単位を、条項で「push された記録」に限る | 条項に新しい限定を課す。確かめる部分(履歴・再実行)を降ろす時点で扱う |
| 落ちることを期待する印の、照合できない枠組みを `scheduled` と表示する | 枠組みごとの照合の部品を準拠テンプレートが持つ計画が立たず、降りる見込みを誤って示す |
| L2 の採点の稼働の機械の検証を、`adopter` として採用者に委ねる | 課さないと決めた規定は `plan` の値にせず、条項を改める(`implementation-marking.md`) |
| L2 の採点の稼働の機械の検証を、課さないと書くだけで済ませる | L2 の条件の「記録で示す」は課したままで、人の確認の手順が要る |
| ルールセットの対象を、既定ブランチを除く全ブランチへ広げる | 作業ブランチへの直接の push も止まる(ADR-0078 決定3) |
| 他の層を引数にした `git merge` をフックで拒否する | 既定ブランチからの同期と区別できない |
| 中間の層へのマージの拒否を `scheduled` か `adopter` で表示し続ける | 降ろす手段が無く、どちらの表示も事実に反する |
| L2 の採点の稼働の検査できる条件を条項で定める | 新しい義務であり、照合する相手が無い |
| IMPL-0479(複数のアダプタ)を本件で降ろす | 動的な matrix が空のときの扱いなど、実機でしか確かめられない点がある。#361 へ寄せる |

## 見直しの契機

- ホスティングが、中間へのマージだけを拒む手段を出したとき。公式のスタック型 PR が一般提供になったとき(決定4)
- go の構文木の文の開始行とブロックの対応が、手元の例の外で食い違う事例が見つかったとき(EV-0246)
- 検証の弱体化の検出の拾い漏れを、独立レビューか是正の記録で見つけたとき(EV-0247)
- EV-0246・EV-0247 の見直しの期限(2027-05)

## 影響

- 第4章 G-5: 基準3 の測る範囲に、python・go の変更の範囲と、測れない構成の失敗を足した。「積み重ねた変更とゲート」に、拒否の設定を課さない旨とマージの後の検出を足した。担保水準 L2 に、採点の稼働の機械の検証を課さない旨を足した
- 第5章 5.8.5・5.8.6: 「機械の検出が付けたラベル」を「機械の検出の一覧」に改めた。検出の範囲と、落ちることを期待する印の書式を足した
- 附属書H H.4: 入力の記録と欠落の表示の降ろし方を足した
- 実装マーク: IMPL-0102・0155・0204・0205・0248・0253・0254・0255・0259 の主題と状態を改めた。IMPL-0486〜0496 を足した。IMPL-0479 は #361 へ寄せた
- 既存の採用者を落としうる検査(ADR-0085 決定6)。いずれも、準拠テンプレートの更新を取り込む時点から効く

| 対象 | 落ちる検査 | 直し方 |
| --- | --- | --- |
| go | 基準3 が初めて判定され、基準値を下回れば G-5 の coverage が落ちる | テストを足す。基準値を改める場合は、製品のコードと別の変更で記名を経る(第4章 G-5「基準値と除外設定の変更」) |
| go | `coverage.out` が出ない構成(coverage のコマンドを書き換えた構成)は未実施として落ちる | `go test ./... -coverprofile=coverage.out` を戻す |
| go(範囲が変更) | 変更したファイルが被覆の記録に無い場合(`-coverpkg` の外、go.work の複数の module、replace の先)に落ちる | 対象のパッケージを `./...` に揃える |
| go(範囲が変更) | go の無い環境で検査を流すと落ちる(文の開始行を構文木から得るため) | go の準備の後に検査を流す |
| python | 全体の割合からテストのファイルを除くため値が下がり、基準値を下回れば落ちる | 製品のコードのテストを足す |
| python(範囲が変更) | `[tool.coverage.run] source` が無いと、テストから読み込まれない製品のファイルの変更が未計測として落ちる | `source` を製品の置き場に合わせる |
| python | `files` を持たない `coverage.json` は読めないとして落ちる | pytest-cov の `--cov-report=json` で出し直す |
| 言語のアダプタ | 集計の記録(`coverageSummary`)を null にした構成は、G-5 と契約検査で落ちる | 集計の記録と形式(`coverageFormat`)を書く |
| pytest | `strict` の無い xfail の付与と `pytest.xfail()` の呼び出しを足す PR は、G-5(pr-rules)で落ちる | 印に `strict=True` を書くか、構成に `xfail_strict = true` を置く。`pytest.xfail()` は印に改める |

- 新しく生成する python・go の構成は、測る範囲の既定が変更の範囲になる。既存の構成の範囲は変えない
- 準拠テンプレートの事前点検(`preflight.mjs`)と構成の生成の案内から、go を「実施しない」と記録する旨の文を除いた
