## コンテキスト

[#363](https://github.com/Takenori-Kusaka/process-compass/issues/363) は、python のアダプタの前提と、複数のスタックを持つリポジトリの扱いを問いました。Issue 本文の「ADR-0084」は ADR-0085 の誤記です(決定2 は ADR-0085 にあります)。#360 本文の「IMPL-0253」は IMPL-0259 の誤記です。

調査の記録は `research/363-deliberation/survey-363.md`・`survey-363-2-external.md` にあります。node と python が混在するリポジトリで node のアダプタを選ぶと、わざと落とした python のテストが走らないまま G-5 を通りました(欠陥③。実行で確認)。G-5 基準1 の値は「例外なし」で、集約から検査を外して判定基準を外すことは禁じられています。現状の通過は条項の空白ではなく、既存の規定への黙った違反でした。

外部の調査では、次のことが分かりました。

- GitHub は `if:` で飛ばしたジョブを Success と報告し、必須チェックでも合流を止めない。OpenSSF Scorecard と SLSA は言語の網羅を見ない。プラットフォームや外部の評価では塞げず、塞げるのは利用者側のプロセスだけである
- Nx・Pants・Bazel は1つの変更で複数のスタックの検査を走らせる。選択型の仕組みは、宣言から漏れたものを走らせない限界を公開している。Bazel・alls-green の型は「既定は全部、除外は宣言」である
- 規格は「すべてを試験せよ」とは求めない。ただし無言で省くことも認めず、範囲の識別と宣言を求める(ISO/IEC/IEEE 29119-2 の 4.1.1。IEC 62304・DO-178C・ISO 9001 8.6 は二次資料による読み)

審議は重で行いました(軽の2委員が、新しい義務と ADR-0085 決定2 の理由の変更に当たるとしたため)。起案・現場・品質監査・規格・弁護の5委員の意見(`council-11`〜`15`)と、議長の裁定(`decision.md` の R-1〜R-4)が記録です。5委員とも欠陥③を認めました(弁護を含む)。

## 決定

### 1. 標準には、道具に依らない2つの要求を置く

第4章 G-5 に「製品のすべてのスタック」の節を置きます。

1. G-5 の基準1・2・3・5 の対象は、製品のコードを構成するすべてのスタックである。各スタックの検査が、それぞれ集約の合否に入らなければならない
2. 製品のコードに、宣言していないスタックがある変更は、G-5 を通過させてはならない(除外の一覧に載せたパスを除く)

標準に「アダプタ」「複数のアダプタ」の語を書きません。アダプタは準拠テンプレートの部品です。準拠テンプレートを使わずに G-5 を組む採用者にも、要求を届けるためです。

### 2. 宣言は人が「スタック × 作業の場所」で行う

- スタックの宣言は人が行う。単位はスタックと作業の場所(ディレクトリ)の組。作業の場所の下にある同じスタックの目印は、宣言済みとして数える
- 機械の検出の結果で宣言を埋めない。検出は宣言との突き合わせにだけ使う(ADR-0085 決定2「設問の回答を検出の結果で埋めない」と同じ)
- 検出には、目印のファイルと拡張子の集計を併せて用いる。目印を持たない `.py` の群などを見落とさないため

### 3. 除外は「製品でない」パスだけを、理由と人の記名で外す

- 区分は「製品でない」だけの閉じた区分。製品のスタックは除外できない
- 単位はパス。スタックの単位では除外しない(製品の python と道具の python を区別できないため)
- 各行に理由と人の記名を要する。AI の名義の記名を受け付けない。準拠テンプレートは、ほかの記名と同じ関数で、担い手の識別と同じ文字列と名簿にない名前も拒む(独立の突合 X3-2)
- 除外の一覧は統制の設定に入れ、AI維持管理者の承認を要する(第4章 G-5「統制の設定の変更の承認」。ADR-0115)。新しい承認者の役は置かない
- 除外の変更と製品のコードの変更が同じ変更にあれば、失敗にする
- 除外は基準7(秘匿情報の混入検査)に効かない

### 4. 準拠テンプレートは2段で降ろし、第1段の間も宣言の外を失敗にする

- 第1段(本件で降ろす): PR ごとの契約検査で、製品のコードのスタックを「宣言したスタック + 登録した除外」と突き合わせ、外れたら G-5 を失敗にする。構成のアダプタ(1つ)のスタックと `projectDir` を宣言として読む。アダプタの外の言語と複数のスタックは、手書きの要素(`adapters/none.json` のコマンドと `stacks`)で受ける。手書きの要素が無ければ失敗になる。手書きの要素で受けたスタックも、基準3 を未実施のまま通さない。要素ごとにカバレッジの集計を報告し、要素ごとに同じ基準値と比べる。報告の無い要素は未実施として失敗に数え、合算しない(独立の突合 X3-1)
- 第2段(本件では降ろさない): 1つの構成で複数のアダプタを回す。単一値の欄は有効のまま残し、追加の欄にする。スタックごとの段を並列に回し、段を `if:` で飛ばさない。宣言したアダプタが対象を見つけなければ失敗にする。カバレッジはスタックごとに同じ基準値と比べ、合算しない。IMPL-0479 を `undelivered` で表示し続け、#360 で扱う。node 以外のスタックで変更の範囲のカバレッジを測る部品は IMPL-0259(#360)に依る
- 第2段が降りるまでの間も、宣言の外のスタックは失敗にする。第4章 G-5 の「未実施は失敗に数える」をそのまま当てる
- 表示の語は、ゲートの単位では「基準1 未充足」、検査の単位では「未実施(構成のアダプタの外)」。「検査していない」「未達」は用いない
- 旧い構成(アダプタ1つ)は、値を変えずに移す。構成の形式を変えないため、そのまま宣言として読む。猶予の期間は置かない

### 5. 根拠水準を開示する

- 拡張子の集計の誤検出の率は測っていない(第4章 G-5 の EV-0237)
- 複数のアダプタの CI の時間と、スタックごとのカバレッジの判定の十分さは、実行が無い(EV-0238)
- 62304・DO-178C・9001 8.6 の読みは二次資料だけに依る(EV-0239)
- 検出の見逃し(ノートブック、拡張子の無いスクリプト、置き場と同じ名のディレクトリの下、9言語の外)は開示に留める(EV-0240)

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| (c2) 事前点検で混在を止める | 持ち込みの時点しか見ず、開始の後に足したスタックを塞がない。目印のファイル名だけでは誤検出が多い。止めた後の受け皿が無く、ADR-0085 決定2 が古い併合を止めなかった理由と同じ害を生む |
| (c3) 告げて開示するだけで通す(単独・正本) | 基準1「例外なし」と両立しない。開示つきで外すことも、集約から外すことの禁止に当たる。対象なしにも未実施にも当たらない第3の通過の状態を作る |
| 第2段が降りるまで、止めずに「未充足」を表示して判定者が受け入れる | 判定者が開示を読まない傾向(未実証)が残り、基準1 と両立しない |
| (d) 差分の網羅率を受け皿にする | 基準3 しか受けず、基準1・2 を受けない。python が走らない構成では測る材料が無い。部品は #360 の IMPL-0259 |
| 変更の範囲で走らせるスタックを選ぶ(affected 型) | 宣言から漏れたものを走らせない限界がある。CI の時間の節約は採否の理由にしない |
| 目印から製品かどうかを機械で推定する | 誤検出を機械の判断で消し、人の宣言の代わりになる。ADR-0085 決定2 と食い違う |
| 宣言の初期値を機械で埋める | 同上。漏れの責任の所在が消える |
| スタックの単位の除外 | 後から足した製品の同じスタックまで外れる。製品のスタックを丸ごと外せる |
| 除外の新しい承認者の役 | 1〜2名の体制で立てられず、除外を書かない方向へ逃げる。既存の AI維持管理者の承認で足りる |
| 混在に限った「受容の記録」の新設(9001 8.6 型の権限者の承認による例外) | 除外の記名と承認で目的を果たす。受容の経路を別に置くと、基準1 の例外の入口になる。置くなら第8章の改め(別の重の審議)を要する |
| カバレッジの全スタックの合算 | 厚い側が薄い側を薄め、スタックごとの不足を隠す(ADR-0079 の薄まり) |
| 構成の `adapters.stack` を配列へ置き換える | 単一のスタックの採用者すべてに形式の版の繰り上げと移行を強いる。追加の欄で足りる(第2段) |
| 猶予の期間を置く | ADR-0085 決定5 と同じ理由。猶予の間は黙った通過が続く |
| 除外にワイルドカードを認める | `**/*.py` のような拡張子の単位の除外は、スタックの単位の除外と同じになる。ファイルとディレクトリに限る |
| Scorecard・SLSA への依拠 | 言語の網羅を見ない |

## 見直しの契機

- 契約検査が宣言の外のスタックとして止めたうちの多くが、除外の登録で解かれていると分かったとき。目印と拡張子の規則、除外の区分を見直す(EV-0237)
- 除外したパスの下に製品のコードがあったと分かった事象が、1件でも見つかったとき。除外の検査を見直す
- 第2段を降ろしたとき。CI の時間とスタックごとのカバレッジの判定の記録で EV-0238 を見直す
- 62304・DO-178C・9001 8.6 の原文を確かめたとき(EV-0239)
- 検出が見逃した製品のコードが後に見つかったとき(EV-0240)
- EV-0237〜0240 の見直しの期限(2027-05)

## 影響

- 第4章 G-5: 「製品のすべてのスタック」の節を足した。IMPL-0476〜0479 と EV-0237〜0240 を付けた
- 準拠テンプレートの `scripts/gate/stack-coverage.mjs`(新): 検出・宣言・除外の読み取り・突き合わせ。契約検査 `verify-gate-contract.mjs` が呼ぶ
- 準拠テンプレートの `check-pr.mjs`: 除外の一覧 `.github/stack-exclusions.json` を閾値・除外設定のファイルに入れた。基底の構成が設定済みなら、一覧を新しく置く変更も初回の設定として外さない
- 準拠テンプレートの `adapters/none.json`: 手書きの要素の宣言 `stacks` を足した。`coverage-check.mjs` は要素ごとの `coverageSummary` を読み、無い要素を失敗させる
- 試験: `test-stack-coverage.mjs`(新)、`test-check-pr.mjs`・`test-init-g5.mjs` に場面を足した
- 既存の採用者を落としうる検査(ADR-0085 決定6): 契約検査(`gate-contract`)は、製品のコードに構成のアダプタの外のスタックがあれば落ちる。直し方は、製品のコードならスタックを宣言する(複数のスタックは `adapters/none.json` に全スタックのコマンドと `stacks` を書く)、製品でないなら除外の一覧へ理由と人の記名で登録する(AI維持管理者の承認を要し、製品のコードと同じ PR にしない)。`adapters/none.json` に手でコマンドを書いていた採用者も、`stacks` を書くまで落ちる。`stacks` を書いた後も、要素ごとの `coverageSummary` を書くまで coverage が落ちる。スタックが未確定(`undetermined`)のまま製品のコードがある採用者も落ちる
