## 1. 点ごとの裁定

### 1.1 点1 IMPL-0268 の分母(先に決める)

**裁定: 案 A。分母は「窓の中で既定ブランチへ取り込んだ変更のうち、承認された変更」。**

- ADR-0172 決定2 の文は「分母は窓の中で既定ブランチへ取り込んだ変更のうち承認されたもの」。起案の実装(`own` をそのまま母数にする)は、承認を経ずに取り込んだ変更(G-6 を事後へ移した L3 の変更、PR を経ない直接の取り込み)を「差し戻しを受けずに承認された」と数える。反対の委員の指摘は実物で確かめた。`autonomyState` の入力は `history.changes` と `rejections` だけで、承認の有無を持たない
- 案 A は入力を新しく取りに行くものではない。`readRejectionRecords` は既に承認レビューの写し(記録用ブランチの `records/reviews/pr-N.json` と基底ブランチの `docs/records/reviews/`)を `copies` として読んでいる(`autonomy.mjs:780-800`)。写しの `reviews[]` に承認の状態がある。同じ写しから承認された PR の集合を返せば足りる
- 「承認された」の判定は、template に既にある1つの定義を使う。`aggregate-evidence.mjs:514` の `approvalCountOfCopy`(承認者ごとの最後の状態が APPROVED の人の数)が1以上の写しの PR を、承認された変更とする。新しい定義は作らない。承認者の資格(人の名簿・書き込みの権限・名義の共有)は、取り込みの時点に G-6 の検査(`check-pr.mjs`)が確かめる。一発承認率は合否に使わないため、ここで確かめ直さない(note で開示する)
- 承認された変更と既定ブランチの変更の対応は、`readHistory` の `pr`(件名の `(#n)`)で取る。PR 番号を持たない変更は、承認の写しへ対応づかず、分母に入らない
- 分子: 分母の変更のうち、宣言行を持つ G-6 の差し戻しの判定記録(帰属を確かめたもの。**判定基準の番号の有無は問わない**。`441-443-444-deliberation/decision.md` §1.1)が1件も対応づかない変更。差し戻し率の分子(`cited` だけ)とは絞り方が違う。差し戻しの日付は窓で切らず、判定の日以前のものを数える(変更ごとの「差し戻しを受けたか」を問うため)
- 記録用ブランチを読めないときは、承認の有無を読めないものとして「読めない」と出し、0% とも 100% とも出さない(`undeclared` と同じ扱い)
- 母数(承認された変更)が 30 件未満なら値を出さず「判断に用いない」と出す。表示には「取り込んだ変更 n 件のうち承認された変更 a 件」を併記し、分母が絞られていることを読み手に見せる

**採らない案**

| 起案: 窓の中の変更すべてを分母にする | ADR-0172 決定2 の字義に反する。承認を経ない変更が一発承認に数えられ、値が承認の質と無関係に高くなる。ADR-0172 が避けた「機械が出した値として権威を帯びる害」をそのまま作る |

### 1.3 点3 IMPL-0645 の機械の検査の範囲

**裁定: 機械は次の決定可能な条件まで。** 保持者が1名以下のコア機能ごとに、技術負債台帳に次をすべて満たす行が1つ以上あるか。

1. 区分が「負債」
2. 対象が、NFKC で `コア理解:` から始まり、コロンの後を前後の空白を除いて NFKC で比べた名前が、運用引き継ぎ文書の節2 のコア機能の名前と一致する(ADR-0200 決定2 の印)
3. 状態が「未返却」
4. 返却の目安が空でなく、「—」でない(期限の欄の存在。様式 03 の「期限のない記録を認めない」をそのまま当てる)

- 日付の形(`YYYY-MM-DD`)は求めない。区分「負債」の返却の目安は様式 03 で「時期またはステージ」であり、日付を求めるのは区分「類似検知」だけである。日付を求めると、正しく「S2 移行時」と書いた採用者の行を拒む。反対の委員の「日付の実在まで機械」は、この点で採らない
- 責任者の記載と、期限の中身の妥当性は機械で閉じない(自由な文)。manual にして note で開示する。確かめる者は、D-0 節15 で受容する層1 の権限者(受容の時点)と、出荷判定者(G-7 で保証の開示を読むとき)
- 起案の「返却の目安に日付と責任者」を機械で求める案は採らない。ADR-0200 に無い条件を機械化することになり、細かい定義を増やす(所有者の方針)
- 様式 03 には、是正の行の書き方を手引きとして1段落足す(返却の目安に期限と責任者を書く。区分「未解決」の担当者と同じ欄)。欄・区分は足さない(ADR-0200 の採らなかった案)
- 印の無い行は見分けない(ADR-0200 決定5)。出力に必ず「印(対象の先頭 `コア理解:`)の無い行は是正の行として見分けない」と書く
- 結果は表示だけにする。記載の欠落・G-7 の停止・委任の停止に数えない(要求事項7)。1名の体制では常に出る。一覧の1行にとどめる(反対の委員の 6.2 の3)
- 台帳が無いときは「技術負債台帳が無く、是正の登録を確かめられない」と出す(0 件と出さない)

### 1.4 点4 IMPL-1006 で決め方だけを記録し直す道

**裁定: 反対の委員の案を採る。** 実物で確かめた。`generate-profile.mjs:5851` は percent が変わるときだけ履歴を積む。これでは、実測前の値を2四半期の実測の後に同じ値のまま「実測から」へ記録し直せず、要求事項2 の置き換えが実在の経路を欠く。表示が「実測前」のまま事実と食い違う。

- 種別 settings の `reworkBaseline` は `{ percent, method }` を受ける。`method` は `"pre-measurement"`(実測前の組織の値)か `"measured"`(実測から)
- percent を null でない値に置く記録(新しく置く・上げる・下げる)では `method` を必須にする。percent を null にする記録(外す)では求めない(求めても意味が無い)
- 履歴を積む条件を「percent が変わる、または method が変わる」に広げる。method だけの変化も、決定した者の記名(AI の名義でない)と理由を要する
- method だけの変化は L3 の導出を変えない(`reworkBaselineInfo` の percent は同じ)。変化点の向きは「記録の更新(向きなし)」とし、緩める向きにも強める向きにも数えない
- `config.mjs` の `reworkBaselineProblems`: 履歴の各記録の `method` は、在るなら列挙の値に限る。無いのは問題にしない(旧い記録。「決め方の記録なし」と表示)。どの記録が新しいかを構成の検査は知らないため、必須は入口(settings)で課す
- 採らない: 根拠水準マークで「できない」を開示する案(反対の委員の次善)。直せるものを開示で済ませない

### 1.5 点5 「この構成の窓に先立つ判定可能な窓が無い」の定義

**裁定: 次のとおり固定する。** `measured` の記録(記録した日 R)について、次を満たす評価の日 m が1つも無いとき、「この構成の窓に先立つ判定可能な窓が無い」と併記する。

- m は月初の日で、m ≤ R
- m の窓の長さは、m に効いていた値 `observationWindowAt(config, m)`(観測の窓の履歴で決まる。現在の値で数え直さない)
- 数える記録は、m の前日以前のもの(`reworkCount` の既存の作り)
- 登録した変更種別のいずれか1つで、その窓の手戻り率の母数(タスク)が最小標本数(30件)以上
- 探す範囲は、手戻り率の記録の最も古い日の月から R の月まで(有限で決定可能)

- 反対の委員の懸念(現在の構成で再計算すると表示が揺れる)は、窓の長さについては `observationWindowAt` が履歴で決まるため生じない。残る揺れは、種別の規則(`changeInType` が現在の規則を読む)を後から変えた場合だけである。これは note と表示で開示し、規則の履歴を読む実装は採らない(表示だけの値のために、規則の版を遡る読み出しを足すと、浅い取得で読めない場合の扱いをさらに要する。信頼性が上がらない)
- 機械が閉じるのは、method の列挙の一致と、上の窓の有無まで。「実測から」と書いた値が本当に実測から導かれたかは閉じない。表示は「実測から(申告)」と書き、「確認済み」「検証済み」の語を使わない(反対の委員の 2.2 の1を採る)。保証の開示の項目3 の行にも「決め方は記名者の申告で、実測との照合は機械では確かめていない」を残す
- 決め方は L3 の導出に効かせない(ADR-0158 は基準値の効き方を決め、決め方で止め方を変える案を置いていない)

### 1.6 点6 欠陥の台帳の登録外の ID

**裁定: 向きは K-4 と同じ。害を開示する。** 欠陥の台帳の「登録した変更種別」の列に登録の一覧に無い ID を含む行は、空欄と同じ扱い(すべての種別に当てる)にする。登録の ID と混ざる行も同じ。

- 理由: 書き誤り1つで AI 起因の Sev1 が委任を1つも止めない(起案 §1.3 の G)。同じ層の既定(列の欠け・空欄)は止める側であり、ここだけが逆へ倒れている。所有者の回答40(K-4)の向きをそのまま当てる。安全に触れるが、止める側へ倒すだけで新しい義務は無い
- 移行の害(反対の委員の 3.2): 種別を取り下げると、その ID を書いた過去の行は「登録外の ID」になり、残りの種別をすべて止める。機械は書き誤りと取り下げを見分けられない(取り下げた種別は構成から消え、記録が残らない)。害は止める側で、戻し方は標準の既存の経路(事象の日より後の 5.5.4 の登録の判定)で足りる。停止の理由の文に、行の ID・登録外の ID・「書き誤りなら直す。取り下げた種別の行なら、残りの種別は事象の日より後の登録の判定で戻る。行の記録は書き換えない」を書く。原因を特定できない行は、原因を特定するまで止まる(既存の規則のまま)
- 採らない案
  - 表示だけにとどめる: K-4 の採らなかった案と同じ。同じ層の既定と向きが逆になる
  - 構成の履歴(git の過去の版)で取り下げた ID を見分け、止めない: 履歴を読めない場合(浅い取得)にまた止める側の扱いを要し、表示だけの区別のために読み出しの失敗の経路を足す。頻度は低く(取り下げた種別の、AI 起因の運用の Sev1・Sev2 の行で、他の種別の登録日より後のもの)、戻し方は既存の経路で足りる。見直しの契機: 取り下げによる停止が採用者から報告されたとき

### 1.7 点7 トレーラの読み方の統一と集約の移行

**裁定: 条件を足して採る。** 議長が実物で確かめた追加の事実: `aggregate-evidence.mjs` のトレーラ Spec は、手戻り率の表示ではなく、**G-4 の判定記録の要否**(`specsWithoutG4`、`:3504`)に使う。止める側の用途である。ここで読む行を減らすと、G-4 の欠落が出なくなる(緩む)。

- 集約と次の一手は、末尾の段落の外にある `Spec:` 行を持つコミットの件数を注記に出す(数えていないことを黙らない。表示だけ。欠落に数えない)

### 1.9 追加の点 A 基準値の変化点の向き

- 0291 の後、基準値が未設定の状態は停止になる。`generate-profile.mjs:2541` の `rank`(null = -Infinity、最も緩い)を、null = +Infinity(最も強い。止める)へ改める。結果: 未設定 → x% は緩める向き(停止を解く)、x% → 未設定は強める向き、上げるのは緩める向き(ADR-0129 `:55` のまま)、下げるのは強める向き
