## 1. IMPL-1011(cause を足す機械の検査)— 条件つき

### 1.1 降ろし方の当否

- **同意する点**: 現状の `restrictionInputProblems`(config.mjs:1752 付近)は person を全発動で必須にし、`cause` 欄を拒否する。7.9.1 の1 の正しい記録が書けない(起案の探針と同じ。条文 7.9.6 / ADR-0161 決定5 と逆)。直す必要はある
- **反対する点(閉じたかのような表示)**: `cause` は記録者の**自己申告**である。機械が閉じるのは「cause=1 なら person が無い」「cause=2 なら person が名簿にある」という**整合**だけで、「7.9.1 の2 に当たる事案が cause=2 で記録されたか」は閉じない。意図的な違反の事案を cause=1 で記録すれば、person は書けない(=5.6.3 の措置との照合の材料が欠ける)が、機械は何も出さない。起案が採らない案とした「person の有無から推す」と、**検出できない欠けの種類は同じ**(2 の記録の欠け)になる。ADR-0161 決定5 の採らない案の理由は「2 の記録の欠けを検出できない」だったが、cause を足しても自己申告の誤り・隠蔽には同じ穴が残る。違いは「書き忘れ」と「書き分けの誤り」の差に縮まる
- **対案**: マークは `check=machine` のままでよいが、note に「cause の真偽(5.6.3 の区分の判別)は人の手続。機械は整合だけを検査する」を**必ず書く**。さらに manual の確かめる者(品質保証の機能)を併記する。`state=delivered check=machine` 単独は表示と実態の食い違いに近い(CLAUDE.md の「統制の閉じ方を裁定で決める」: 自由な文の意味や改ざんは manual か adopter で開示する)
- 7.9.1 の1 と2 が**同時に当たる**事案(見逃しの反復の最中に意図的な違反が見つかる)が起案に無い。cause を単一値にすると片方の根拠が記録から落ちる。対案: 発動は事案ごとに別の識別子で2件に分けて記録する(条文は発動の識別子を単位にしている)と手引き(notice.md)に書く。cause を配列にするのは定義を増やすので採らない

### 1.2 移行(既存の正しい記録を拒否しないか)

- 起案は「旧い記録(cause 無し)は止めず legacyCause に数える」と書く。`restrictionState` の既存の `legacy` は「範囲の無い旧い発動」を数える別の概念(config.mjs:1704 以下)で、`legacyCause` と**名前も意味も近い2つの旧い**ができる。対案: 名を `causeless` などにし、`legacy` との差を試験の fixture で固定する
- **対象の人を持つ旧い記録**は changeLog に残る。起案の「active・released に person を持ち回らない」は出力側の除去だけで、`aggregate-evidence.mjs` が changeLog を別の経路で読んでいないかを実装の段で grep する(私は 2232・4248 行のみ確かめた)。条文の目的(個人の記録を集約の出力に出さない)に反する経路が1つでも残れば、機械で閉じたと言えない
- fixture: `test-roster-conditions.mjs` の `R`(person 必須で書いた制限)が110〜127・227〜246・352 行で共用されている。cause を必須にすると**全件が一度に倒れる**ので、旧形式を legacy として読む試験と、新形式を書く試験を分けて直す。過去の決定(ADR-0127 決定5)を固定している fixture なので、書き換えには ADR-0161 決定5 の引用を試験の見出しに付ける

### 1.3 方針の3つの問い

- (1) 条文は結果と証跡まで: 同意
- (2) 例外承認で受けられない: 同意(標準と逆の実装の直し)
- (3) 破られたときの損失: 見逃した個人が記録・表示される。同意。ただし**cause の自己申告で破れる**ことを損失の説明に含める

### 1.4 論点1への答え(cause は定義を増やすか)

- 値 `"7.9.1-1"` / `"7.9.1-2"` は条文の番号そのもので、新しい定義は増えない。同意。ただし person の定義の文を「7.9.1 の2 の区分の対象の人」へ改めるのは**意味を変える**(検査文の改正)ので、ADR-0161 決定5 の範囲だと明記する

## 2. IMPL-0191(PR での拒否)— 条件つき(保護ブランチの判定と直接の push の表示は反対)

### 2.1 PR のコミット本文の走査そのもの — 同意

- 私も実行した: `hasMarker`(seeded-error-scan.mjs:41)は `Seeded-Error:` の行頭(前の空白可、大文字小文字を問わない)に当たり、`> Seeded-Error:`・行の途中の語・`Seeded-Error :` には当たらない。起案の ok/ng の fixture の期待どおり。`MARKER`・`hasMarker` は export 済み
- analyzePr は `mergeBase`・`HEADREF` を持つ(check-pr.mjs:1670-1675)。`git log mergeBase..HEADREF` は実装できる

### 2.2 反対: エラーの文に既存の `FALSE_POSITIVE_HINT` を使ってはならない

- `seeded-error-scan.mjs:32` の `FALSE_POSITIVE_HINT` は「本文から語を外すか、**第7章の例外承認で受ける**」と書く。起案の PR 検査は「例外承認で受けない」と裁定する。定数を import して流用すると**同じ標識の失敗に対し、PR では例外承認を案内し、出荷では案内しない**矛盾が出る。起案は定数 MARKER の import だけ言及している。実装の段で、PR 用の文を別に書く(「本文から標識の行を外す。注入したコミットの標識は外さない」)ことを条件にする

### 2.3 反対: 保護ブランチの判定に ruleset の include を使う

- 実物: 同梱の6つの ruleset のうち、`~DEFAULT_BRANCH` を include するのは checks-only・regulated・safety・team の4つ。records 系は `refs/heads/records` で、**本番のブランチではない**(判定記録の置き場)。include の一般的な glob 解釈を `check-pr.mjs` に足すと、records 宛の PR で誤って走る。決定可能な条件は「PR の基底 == `--policy-base` の既定ブランチ」の1つで足りる
- 演習用のブランチ経由でも、最終的に既定ブランチ宛の PR になれば `mergeBase..HEADREF` の全コミットが走査される。**既定ブランチ宛だけ**を対象にしても取りこぼしは増えない(段階的なスタック型 PR の途中の基底は対象外でも、最後の PR が全コミットを持つ)。リリースブランチを「本番のブランチ」に数えるかは、条文の「本番のブランチ」の定義の問題で、現行の条文は定義を置いていない(新設は定義を増やす向き)
- 対案(私の推す形): 保護ブランチ = 既定ブランチ(`--policy-base`)に限る。`policy-base` を渡さない手元の実行は対象外にして notice を出す。リリースブランチを含めるのは、採用者の要請があったときに別の Issue で足す(採らないと決めたこととして記録)
- 論点2(宣言と実機の食い違い)への答え: 宣言の JSON を読む案は、実機の適用を見ない。実機を API で読む実装が**既にある**(`adoption-trial.mjs` の 1586〜1700 行。ルールセットの `pull_request` の規則を `rsRead.pr` に読み、無ければ「pull_request の規則が無い」で mismatch)。ただし `g6Active` のときだけ。新しい API 読みを足さず、これを再利用するのが信頼性で勝つ

### 2.4 反対: 直接の push の欠けの表示を preflight に置く

- preflight は**初期化の事前点検**(preflight.mjs 冒頭の説明: 構成を設定済みにする前に既存のリポジトリの状態を読む)で、ルールセットはまだ適用されていないのが普通。ここで構成 `ruleset` の JSON を読んで「pull_request が無い」と告げるのは、**宣言の JSON を読むだけ**で、適用の実在を確かめない。表示が「欠けている」と言い切るなら、実機を見る adoption-trial の `items.ruleset` の側に置く
- 対案: (a) 表示は `adoption-trial.mjs` の ruleset 項目に「pull_request の規則が無い」を、g6Active に依らず mismatch でなく**告知**(note)として足す。(b) 保証の開示(aggregate-evidence 6735 行付近)には、その項目の値をそのまま写す。(c) preflight には足さない。置き場を増やすと、定義の置き場所が3か所(preflight・adoption-trial・開示)に分かれ、食い違うたびに突合が要る
- 「checks-only が当たる」のは実物で確認した(checks-only.json に `pull_request` が無く、`required_status_checks` + `non_fast_forward` + `deletion`)。ただし checks-only でも `required_status_checks` が gate-g5 を必須にするため、**検査を通らない直接の push は GitHub が拒む**(PR を経ない先頭のコミットに check run が付かない)。起案の言う「演習のコミットが他の必須の検査に通った状態で直接 push される」経路は、**演習用ブランチのコミットに check run が付く場合に限る**。その経路が実在するかは実機で未確認(私も確かめていない)。したがって「直接の push の欠け」を強く書きすぎない。**暫定 EV のマーク**(実機未確認)を付ける案を勧める

### 2.5 表示(マーク)の閉じ方

- 条文 5.6.2 第2層は3つの要求を持つ: (i) 標識を履歴に残る形で付ける、(ii) 取り込みの前に拒否する、(iii) 演習用ブランチで標識の失われる書き換えをしない。起案の機械の検査は(ii)の**PR の経路だけ**を閉じる。(i)(iii)は機械で閉じない(標識を付け忘れた注入はそもそも走査に当たらず、書き換えで標識を外した履歴は走査が見つけられない)
- `state=delivered check=machine` 1行は、(i)(iii)を閉じたように読める。対案: マークを分ける(IMPL-0191 を(ii)に、新しい IMPL を(i)(iii)の `check=manual plan=adopter` に)か、note に(i)(iii)は採用者の演習の手続(フェーズ5 seeded-error-safety)で manual と書き、確かめる者を付ける。**ここは議長の裁定が要る**(分割は台帳の番号を増やす)

### 2.6 論点3(説明のコミットと文の直し)

- 起案の読み(「標識の失われる履歴の書き換えをしない」は注入したコミットに掛かり、説明のコミットには掛からない)は、条文の主語(第2層の同じ行「注入したコミットに…」「演習用のブランチで…」)から**ほぼ支持される**。ただし機械は、注入したコミットと説明のコミットを**区別できない**。PR のブランチの書き換えで標識を落とせば通る。これは(iii)の manual の話で、起案の「直す手段がある」は(ii)の例外承認が不要の理由にはなるが、書き換えの抜け道の存在を消さない。note に開示する
- 同意: 出荷の走査が例外承認を受ける理由(直す手段が無い)と、PR で受けない理由(直せる)の分け方は筋が通る。ただし 2.2 のとおり文を揃える

### 2.7 テストの追加

- 起案に加える ng/ok: CRLF の本文、行頭が `>` の引用、複数コミットのうち2番目だけに標識、マージコミット(PR のブランチへ main を取り込んだ場合に `mergeBase..HEAD` に main の側のコミットが入らないこと)。マージコミットの試験は、**他者の本番の履歴の標識(過去の演習)で現在の PR が失敗しない**ことの確認で、実行して確かめるべき

## 3. IMPL-1003(開示の行)— 条件つき

- **同意する点**: 構成書の注記は既に降りている(generate-profile.mjs:3703)。保証の開示(6727〜6735 行)に1004 の行はあるが1003 の行は無い。出荷判定者の読む面に開示を足すのは、manual の降ろし方として妥当
- **条件1(文言)**: 起案の文は「適合の主張を述べられない」と書く。条文(overview.md 709・1.10.2)は「述べられる名がこれを**数えない**」で、帰結は適用の表明まで。「適合の主張を述べられない」は帰結を**言い切りすぎる**可能性がある。述べられる名の算出(`evidence.claim.name`)が既にこの列挙に無い離脱を数えない以上、行は「この項目は述べられる名に数えていない。人が確かめる」とだけ書く。IMPL-1004 の行の文型(6735 行)に揃える
- **条件2(常に出す)**: 3名以上の体制では注入する者と見つける者を分けられるので、行を常に出すのは余計な警告になりうる。ただし1004 の行も常に出ている(体制の規模によらない)。**同意**するが、行に「1〜2名の体制で当たる」を入れる
- **論点4(1004 の adopter と並べて不揃いに見えないか)**: 台帳の読み手には不揃いに見える可能性がある。ただし起案の理由(1004 は確かめる証跡がテンプレートの外、1003 は体制の構造で開示と D-0 の体制図で判断できる)は筋が通っている。ただし**1003 の確かめる者「出荷判定者」が、体制図を持つとは限らない**: 秘匿が成り立つかを判断する材料(誰が注入し誰が見つけるか)は、D-0 に欄が無い(起案が欄の新設を採らないと決めた)。材料が無いのに manual で確かめる者を置くのは、**確かめる手段の無い manual**になりうる。対案: 確かめる者は出荷判定者のまま、確かめる材料を「測定の記録の注入者と見つける者(附属書H の項目6 の併記)」と note に名指す。附属書H 項目6 は測定した見つける者を併記する(ADR-0161 の5 の記述)ので、材料は既にある
- 方針の3つの問い: (1)(2)(3)に同意。(3)で、失うのは適合の主張の信頼。同意
