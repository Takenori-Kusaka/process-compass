## 1. IMPL-0291 — 条件つき同意

### 1.1 起案が正しいこと

- 実物で確認した。手戻り率の節(`template/scripts/gate/autonomy.mjs:384-409`)は `判定不能`・`基準値未設定`・`読めない` のいずれでも `stop()` を呼ばない。差し戻し率の側だけが `latest.n < MIN_SAMPLE` で `unmeasurable` の停止を出す(同 377-379)。ADR-0158 決定1 は、手戻り率にも同じ停止を求める
- 「止める側へ倒す」は、新しい義務ではなく ADR-0158 が既に決めた規範の降ろし。例外承認で解く経路は ADR-0158 の採らなかった案(`adr/0158…:89`)。起案の(2)の読みは正しい

### 1.2 突く点と条件

1. **移行は「正しい記録を止める」ではなく「記録が無いことを止める」**。これは ADR-0158 の帰結 (`:101-102`) で、猶予を置かないと決めた。ただし起案の「README に移行の注意」だけでは弱い。取り込み後の最初の評価で、基準値を置いていない採用者の**すべての登録した変更種別**が L1 へ落ちる。実測した fixture(`fixtures/delegation-eligible.json` の `records` は `asOf, f2q1, defects, core, history, rejections` のみ。`rework` も `reworkBaseline` も無い)が示すとおり、既定の構成がそのまま止まる。条件: 次の一手(`autonomyNoteLines`)の停止の理由に、戻し方(基準値を記録する。種別 settings)を文として含める。README だけにしない
2. **「手戻り率の記録だけを読めない」を止めるときの、浅い取得の扱い**。`.github/workflows/delegation.yml:78,118` は `fetch-depth: 0` で、結線は足りている。だが `check-delegation.mjs` をローカルの浅い clone で実行する採用者(`rr.available === false`)は、止まる理由が「履歴を読めない」になる。理由の文に取得の深さを書く(差し戻し率の側の文と揃える)。これは決定可能な条件で足りる
3. **既存 fixture の期待を改める範囲**。`test-check-delegation.mjs` の「発火せず止めない」の3場面(起案が挙げた 539-558 行付近)に加え、`base()` を使う全場面が L1 へ落ちる。fixture に足す手戻りの記録が 30 件以上の母数を満たすこと、基準値の記録日が判定の日より前であること(`reworkBaselineInfo` は `recordedAt < day` で効く)を、起案は書いている。ここは同意。**過去の決定を固定する fixture を書き換えるので、期待を改める理由を ADR-0158 決定1・2 の行で試験の注記に残す**ことを条件にする
4. 機械が閉じるのは件数・値の有無・構文まで。基準値が妥当かは閉じない(ADR-0158 本文が「ゲーミングの跡は止める側にだけ残る」と開示済み)。起案はこの点を新しく主張していないので反対しない

### 1.3 対案と判定

対案なし。降ろす。条件は 1.2 の 1・3。

## 2. IMPL-1006 — 条件つき(一部反対)

### 2.1 実行・読みで確かめたこと

- `config.mjs:3082-3120` の `reworkBaselineInfo`・`reworkBaselineProblems` は `percent / recordedAt / decidedBy / reason` だけを扱う。`method` は無い
- `generate-profile.mjs:5455-5470` の種別 settings の検査は、`percent` 以外の欄を `書けない欄があります` として**拒否**する。起案の「`method` を受け取って積む」は、この拒否を外す変更を含む。起案は変更に書いているが、影響を書いていない
- **決定的な点**: `generate-profile.mjs:5851-5856` は、`S.reworkBaseline.percent !== cur`(値が変わるとき)にだけ履歴を積む。値が同じなら `priorB` を保つ。したがって「暫定の実測前の値を、2四半期の実測の後に、**同じ値のまま**『実測から』へ記録し直す」ことは**できない**。ADR-0158 決定2 は、実測前の値を要求事項2 の置き換え(2四半期の実測)の対象とする。実測で確かめた結果が同じ値だったとき、決め方の記録を更新する道が無い。この道を開けないと、`pre-measurement` の記録が永久に残り、「実測前」の表示が事実と食い違う

### 2.2 反対する点

1. **`method` の機械の検査は列挙の一致だけ**。`measured` は自己申告で、実測から導いたかは機械では閉じない。起案は manual で開示する案を置いており、これは妥当。条件: 表示は「実測から(申告)」と書き、機械が確かめたかのような語(検証済み・確認済み)を使わない。保証の開示の項目3 の文に「決め方は記名者の申告であり、実測との照合は機械では確かめていない」を残す
2. **「この構成の窓に先立つ判定可能な窓が無い」の判定は決定可能だが、基準日の読みが要る**。`reworkAt(m)` は評価の日 m ごとに計算できる(`autonomy.mjs:388-396`)。ただし判定の窓は、記録の日の時点の構成(観測の窓の履歴)と、その時点の記録で決まる。現在の構成の履歴で再計算すると、後から観測の窓を長くした構成で結果が変わる。条件: 「記録した日より前の評価の日で、**その日に効いていた窓の長さ**で判定可能だったか」と定義を固定して試験で押さえる。固定しないと表示が時間で揺れる
3. **旧い記録の扱いは妥当**。`method` の無い旧い履歴を拒否しない(`決め方の記録なし`)は、既存の採用者の正しい記録を壊さない。同意
4. **新しい記録で必須**にすると、既存の settings の呼び出し(`process-change/reference/input.md` の例、`kinds/settings.md`)がすべて拒否される。手引きの更新が必須の同時変更になる

### 2.3 対案

- `method` を記録する入口を、`percent` の変更と**切り離す**。同じ値の再記録(決め方だけの更新)を、決定した者と理由を要する履歴として積めるようにする。採らないなら、ADR-0158 決定2 の「置き換え」が実在の経路を欠くことを、根拠水準マークで開示する(降りていないのでなく「できない」ことの開示)
- 「記録の履歴を積む条件」の変更は、条文を増やさず template の挙動の修正で足りる。細かい定義は増えない

### 2.4 3つの問い

(1) 構成の記録(決め方)と表示まで。同意。(2) 合否に使わない。同意。(3) 実測に依らない値を実測の値と読み違える。同意。ただし破られたとき失うのは、記名者の申告の正しさへの信頼であり、機械は守らない。それを manual で開示する案に同意する

## 3. 欠陥の台帳の「登録した変更種別」の列の登録外の ID — 条件つき同意

### 3.1 確かめたこと

- `autonomy.mjs:296` は `applies(d.changeTypes)` だけを見る。`applies` は `list === null || list.includes(id)`(同 261)。登録外の ID だけの行は、どの種別にも当たらず、`continue` で黙って外れる。起案の表(G・H)と一致する読み
- 同じ層の運用引き継ぎ文書の側は K-4(同 324-326)で、登録外の ID を空欄と同じ扱いにしている(`test-check-delegation.mjs:1010-1022`)。向きの不整合は実在する
- 低-5(区切り)は `typesOf`(同 542 付近)が `、,，/／` で分ける。「・」は分けない。起案の「区切りは変えず README へ1句」は妥当

### 3.2 突く点

1. **取り下げた種別の古い行**。標準は「登録の取り下げ」を種別を L1 へ戻す正しい手段としている(ADR-0158 決定4)。取り下げた種別の ID を書いた過去の Sev1・Sev2 の行は、取り下げの後は『登録外の ID』になる。起案の変更では、その行が、残りの**すべての**種別の停止に効く。AI 起因「あり」なら、その種別が事象の日より後に登録し直されていれば戻る(`registeredAt > d.date`)。しかし、事象の日より前に登録した種別は、登録し直すまで止まる。K-4 の側(運用引き継ぎ文書)でも同じ性質があり、所有者は回答40 で受けている。**同じ向きを当てることには同意する**が、取り下げ・改名で ID が消えた行が全種別を止める害を、README と IMPL-0284 の note に開示する条件を付ける
2. **原因の特定できない行**(`cause-unknown`)は、登録外の ID を持つと、全種別を『原因を特定するまで』止める。登録し直しでは解けない。書き誤りを直せば解ける点は同じ。害の限定は上と同じ
3. 機械が閉じるのは『ID が登録の一覧に在るか』(決定可能)。ID を正しい種別に書いたかは閉じない。起案は新しい主張をしていない

### 3.3 3つの問い

(1) 結果と表示(どの行のどの ID か)まで。同意。(2) 例外承認は不要。同意(書き誤りは直せば戻る)。(3) 破られたとき、AI 起因の Sev1 が委任を止めない。起案の読みに同意

## 4. IMPL-0268 一発承認率 — 反対(分母の定義)

### 4.1 突く点

- ADR-0172 決定2 と `441-443-444-deliberation/decision.md:36-38` は、分母を『窓の中で既定ブランチへ取り込んだ変更のうち、**承認されたもの**』、分子をそのうち差し戻しの判定記録が0件のもの、と定める。「母数と窓は差し戻し率と同じ」は窓の長さと標本数の閾値の意味である
- 起案(§3.4)は、差し戻し率の `count`(`autonomy.mjs:365-368`)の `own`(窓の中の種別の変更すべて)を母数に使い、差し戻しの無い変更を数える。`own` は『承認された』変更に絞っていない。`autonomyState` の入力 `records` は `rejections`(差し戻しの判定記録)と `history.changes`(取り込んだ変更)だけで、**承認を示す記録を持たない**。事後検証に回した委任(G-6 を事後へ移す L3)の変更は、取り込み前の承認が無い。それでも『差し戻しを受けず』に数えられ、一発承認率が実態より高くなる
- 100% 近い値が出るのは、承認の質でなく『承認を経ない変更』が混ざるため、という誤読を機械が作る。ADR-0172 が避けた害(権威を帯びる)

### 4.2 対案

- A: 承認を示す記録を入力に足す(G-6 の判定記録の承認、または承認レビュー)。分母を承認された変更に絞る。入力の追加が要るため、実装の範囲が広がる
- B(次善): 分母を `own` のままにするなら、定義を『差し戻しを受けなかった変更 ÷ 取り込んだ変更』と**改め**、『承認』の語を使わない。ADR-0172 決定2 との食い違いは、編集では直らない(意味が変わる)ため、ADR-0172 に追記する新しい決定が要る
- 議長の裁定の案を、A か B かで割ってよい。起案の「分母は窓の中の変更」とは別の問題なので、先に決めてから実装に渡す

### 4.3 読みの論点(登録した変更種別ごとの範囲)

起案の案(差し戻し率を出す所に限る)に同意する。案件全体で出す読みは、決定2 の『単独で出さない』に反する。

### 4.4 3つの問い

(1) 件数と窓の当てはめまで。同意。(2) 合否に使わない。同意。(3) 少ない標本の値で是正を誤る。ただし分母の定義が違うと、30 件満たしても誤る。ここが反対の核

## 6. IMPL-0645 — 部分的に反対

4. 降ろし先を `debt-ledger-template` から `evidence-aggregation` へ改める案は、前例(IMPL-0644)があるので反対しない。ただし様式 03 側に手引きの1行を足すなら、降ろし先の登録(`impl-targets.yaml`)の意味は変えない
