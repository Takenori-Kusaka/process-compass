# #359 反対の委員の意見

- 時点: 2026-11-12。本体 4c03b68、テンプレート ef539dc
- 読んだもの: intake・survey、ADR-0084 決定4・0094・0069 決定2・0078 決定3・0098・0099・0116 決定4〜6、check-g1.mjs:92-115、next.mjs(--pickup と名簿の team)、04-gate-record.md、tailoring-guide.md:1130-1176、human-ai-boundary.md 5.7.4〜5.7.5。ファイルは変えていない
- 役: 安易に「降ろした」と表示する案と、安易に「採用者へ委ねる」案の欠陥を突く

## 全体への異議

- survey は 17 件を「欄・注記で足りる」群と「判断を要する」群に分けた。しかし前者にも、機械の側が規定と逆の振る舞いをしているもの(IMPL-0250)と、起点の出力が様式へつながらないもの(IMPL-0135)がある。注記を置いた時点で `delivered` と表示すると、台帳の読み手は「テンプレートが運ぶ」と読む。降ろした範囲を超える振る舞いを抱えるマークは、マークを分ける。降ろした部分は `delivered`、残りは `undelivered` として表示し続ける
- `plan=adopter` の理由に「組織による」と書けば、ほぼ何にでも通る。ADR-0084 決定4 の表の先例(IMPL-0277・0279)は「実行の基盤に依存する」という具体の依存だった。同じ水準の依存を名指せない規定は adopter にしない

## マークごと

**IMPL-0135**(是正の記録)
- 台帳に節を足すだけでは、起点(5.6.2 の注入の見逃し、ADR-0038 の弱化の検知)の出力から是正の記録へ誰も導かれない。条件は、注入の見逃しや弱化の検知の記録があって対応する是正の行が無いとき、/pit か adoption-trial が未作成を出すこと。「仕組みで置くか、置かない理由」は判断であり、記録した者に AI の名義を拒む
- adopter の理由は立たない
- `template-fields.yaml` の forms に defect-ledger.md が無い。登録しないと様式の欄を検査できない

**IMPL-0256**(PR の判断の1文)
- 例文を置くと、例文がそのまま残る。例文は `<…>` かコメントにし、「様式の説明のまま」として検出できる形にする
- 委任(R3)の PR で判断の1文を AI が書くと自己の正当化になる。人の欄であるという注記を併記する。内容を機械で見ないこと(pr-workflow.md:139)は `manual` のまま正しい
- adopter の理由は立たない

**IMPL-0250**(合わさった差分への1件の承認)
- **名ばかりになる典型**。G-6.md に注記を置いても、出荷の証跡の集約は既定ブランチへ入った PR ごとに承認を数え、層の合わさりを見ない。機械が規定と逆の数え方をしたまま「降りた」と読まれる
- 条件: マークを「/gate の注記」(delivered)と「集約が合わさった差分の承認を層の確認に数えないこと」(undelivered。IMPL-0248・0254 と同じ #360 へ)に分ける
- ADR-0078 決定3 と矛盾はない。同決定は中間層のマージを拒む設定が無いことを開示済みで、この開示と揃える

**IMPL-0252**(SG-0 の確認した事項・確認していない問いの移し先)
- 注記だけでは、問いが S1 の前提か検証のタスクへ移ったかを追えない。条件は、「確認していない事項」の行に移し先(F-NNN の前提か Task-N)を書く列を置くこと
- ADR-0078 1-D が退けたのは探索の記録の様式の新設で、決断の記録の中の列は当たらない。t4 は欄の文字列で検査する限り壊れない。ただし t4 に「確認した事項」が未登録なので、両方向の検査のために登録する

**IMPL-0220**(要約だけで判定しない)
- /gate の SKILL に1行足すだけでは、判定記録が原資料へ到達できるかを誰も見ない。条件は、「人が判断する項目」に根拠の所在(パス・行・コミット)の列を置くこと。presence はその列の有無に限り、中身は `manual`
- 様式の「挙動要約(G-6 のみ)」は人が書く欄で、ここで言う AI の要約ではない。同じ語なので、注記で混同を断つ
- adopter の理由は立たない

**IMPL-0280**(停止条件の G-1 の記録)
- check-g1 の REQUIRED_ROWS へそのまま足すと、G-1 を通過済みの企画書が遡って失敗する。BRIEF_SCOPE_ROW と同じく「通過済みなら gap の警告」にすることを必須とする
- ADR-0040 により、先に第6章 テンプレ6 に行が要る
- 値の出所が二重になる危険がある。企画書の行と構成の `task.selfHealMaxIterations`・`task.selfHealNoProgressLimit` が食い違えば、どちらが効くかが分からない。行は構成の値を引くか、契約検査で一致を確かめる
- 消費の計測(IMPL-0277、adopter)の値の欄は「採用者の手段」と書けば記入として受け付ける。空欄扱いで落とさない
- adopter の理由は立たない

**IMPL-0465・0466**(試行前チェックリスト)
- survey の誤読: 「品質マネジメント規程か決裁権限規程を持つ組織に限る」のはサンドボックスと既存規程との併存だけ。T-1 は 1〜2名でも「実施する」。様式は全体制へ降ろし、サンドボックスの行だけに適用範囲を書く
- 様式を置くだけでは、「全項目を確認してから始める」の始点をテンプレートが知らない。1〜2名は「対象そのものが試行」なので、始点は /process-init か最初の G-1 になる。未充足を /pit の人の判断待ちに出すことが条件
- 機械で確かめるべき点は2つ。理由の無い「該当なし」を確認済みとしないこと(presence で検出できる)。期限の超過を /pit に出すこと(時計に依存するので、回帰の fixture で時刻を固定する)
- 期限を書き換えることは「自動で延びる」のと同じ。延長は新しい行と決定の記録への所在で残し、旧い期限を消させない
- ADR-0116 決定4 により、承認者名と申請の様式は様式に固定しない
- 10名以上では T-1 は組織の展開で、リポジトリの外にある。adopter の理由になりうるが、決定6 が「この置き場へ降ろす」と決めているので、adopter にするなら新 ADR が要る

**IMPL-0174**(四半期の抽出)
- SKILL に「四半期ごとに抽出する」と書くだけでは、母集団・件数・抽出者・記録の置き場が無く、何も起きない
- ADR-0116 決定5(監査される当事者に抽出の対象を選ばせない)と同じ構造の危険がある。作成を指示した者が /gate で抽出を選べてはならない。条件は、機械が記録の集合から種を記録したうえで抽出し、結果の記録の置き場を持ち、前回から1四半期を過ぎたら /pit に出すこと
- 件数と抽出者を本文が定めていない。テンプレートが値を発明して規範に見せるのは不可。本文の定義の欠けとして先に決めるか、値に EV マークを付ける。所有者の判断の候補
- 母集団はリポジトリの中にあるので、adopter の理由は立たない

**IMPL-0175**(外観の周期的な変更)
- 様式の見出しや欄の文字列を周期で変えると、t4 の固定の検査と、見出しで欄を読む集約が読めなくなる。記録の見出しは固定のままとする
- 変えてよいのは提示の層だけ。/gate が出すレビュー本文の雛形の、確認を求める項目の並びと強調を版ごとに変え、どの版を提示したかを記録に残す
- 版の記録が無ければ、回したことを誰も確かめられず名ばかりになる。根拠は 2015 年の単一の研究なので、EV マークを付ける
- adopter は不可。理由は「様式が静的だから」という自分の都合でしかない

**IMPL-0283**(滞留の観測と通知)
- ADR-0094 決定4 は、velocity を置かない代わりに警告を 2.10.4 で行い、「IMPL-0283 を降ろすことを優先」と決めた。全体を adopter にすると、この前提が崩れる。新 ADR による置き換え無しには不可。いまの note(「採用者が…通知の手段を置く」)は `plan=scheduled` と食い違っており、どちらに決まっても直す
- next.mjs は /pit を呼んだときしか動かない。「継続して」観測するには定期の実行(ワークフローの cron)が要り、強制層の追加なので needs-platform を経る
- 決めておくべき点: 「着手の時刻」の定義(ラベルの付与か Draft PR か。テンプレートの定義として開示する)。85 パーセンタイルを出す履歴が無い間は G-1 の値で代え、その企画書の行には IMPL-0280 と同じ gap の扱い。通知は作業単位へのコメントか見込みの報告の Issue で行い、他の席のラベルを遷移させない(ADR-0094 決定1)
- 分け方: GitHub の上の観測と通知は scheduled に残す。GitHub の外の経路(Slack など)だけを adopter にでき、その理由は IMPL-0279 と同型で立つ

**IMPL-0374**(完了スループット)
- 閉じた Issue(stateReason=completed)を数えて delivered にすると、本文と ADR-0098 が禁じる「閉じた操作そのもの」を完了に数えることになる
- 条件: 数えるのは、取り込んだ PR との結び付きか、完了の判定の記録があるものだけ。それ以外を「閉じたが完了に当たらない」として並べる。「完了の条件を満たしたか」の判断は人に残る(manual)ことを開示する
- 条件そのものは組織が定めるが、数えることは組織に依らない。adopter の理由は立たない

**IMPL-0377**(到達の見込みの算定)
- IMPL-0374 より先に delivered にしない。SC-M の層のラベルが無いまま算定すると、母集団が定まらない
- 件数による帯の算定は scheduled に残す。費用の組だけは会計の基盤に依存するので adopter の理由が立つ。マークを分ける
- 報告は見込みの報告の Issue へ置き、作業単位のラベルを変えない(ADR-0094 決定1)

**IMPL-0381**(途中の判定の到達の見込みの欠落)
- ステージの途中の判定記録を見分ける値がゲート欄に無い。節の有無で見分けると、節を欠いた記録ほど検出から漏れる循環になる
- 条件は、第6章のテンプレ4 にゲート欄の値を定め、テンプレートがそれを写すこと(ADR-0040)。値の無い旧い記録は gap として出す
- #415 の裁定(M2-9)で外した SG の記録への検査は戻さない
- adopter の理由は立たない

**IMPL-0467**(前提の判定記録の無い着手)
- いまの --pickup は、(a)(b)(c) で「判定できない」(終了コード 4)を出す。着手しない方向へ閉じており、安全側である
- ただし満たす手段(差し戻し・価値判断・決裁の記録の様式)が無いまま止め続けると、人は終了コードを無視することを覚える。止め方が形骸化する危険がある
- delivered にする条件は、本文の第6章に記録の様式を置き、テンプレートがそれを読めること
- (c) 機能へ対応づけない作業単位の前提は、本文の定義の欠けである。先に本文で決める。テンプレートで発明しない
- adopter の理由は立たない

**IMPL-0342**(1名の体制の自己の任命)
- 降ろすことは、テンプレートの禁止(新任の自己確定の拒否)を緩める変更である。機械は「上に任命権者がいない」ことを確かめられず、確かめられるのは D-0 の記載の有無まで
- 1名の体制は区別がつかない。個人事業主も、大きな組織の中の1名のチームも、名簿の上では同じ1名に見える。後者は本文が任命権者の経路を求めている。この例外は誰でも使える抜け道になる
- 条件(すべて要る): 名簿がちょうど1名。D-0 に法的な形態(個人事業主か、1名で代表権を持つ法人)を宣言する欄があり、空欄なら拒否する。変化点の記録に「自己の任命」の種別を残す。保証の開示の項目7 へ機械が生成して表示し、抑止できない。緩める向きなので needs-platform を経て AI維持管理者の承認を得る。#432 の自己の決定の例外(IMPL-0483)と条件を揃える
- adopter は最悪の案である。採用者がテンプレートの錠を自分で緩めることになる。scheduled のまま、所有者の判断を待つ
- いま降りていないことは、厳しすぎる側の未達で、危険な側ではない。急ぐ理由はない

**IMPL-0462**(受託の構成での価値責任者の所属)
- 検出には席の所属が要り、ADR-0069 決定2 と正面から衝突する。#359 では降ろさない
- 抜け道への注意: 名簿の people にはすでに `team` の欄がある(next.mjs:1449、generate-profile.mjs:835)。これに発注側・受注側を書かせれば ADR-0069 決定2 の迂回になるので、禁じる
- adopter にすると、#370 の裁定が #357 へ送った設計を永久に閉じることになる。正しい扱いは、scheduled のまま `issue=357` へ付け替えること
- 所有者の判断を要する(ADR-0069 決定2 を改めるか)

## 起案が何を言っても譲れない条件

1. 機械が規定と逆の振る舞いを残しているもの(IMPL-0250 の集約、IMPL-0374 の閉じた件数)を、注記だけで delivered にしない。マークを分け、残りは undelivered として表示し続ける
2. 企画書・判定記録の必須の行や値を足すときは、通過済みの記録を遡って失敗させない(gap の警告)。同時に、本文の第6章へ先に行・値を置く(ADR-0040)
3. 様式の見出しと欄の文字列を周期で変えない。外観を変えるのは提示の層だけとし、提示した版を記録する
4. IMPL-0342 は、1名の体制の宣言の欄・開示の機械による生成・needs-platform の承認・IMPL-0483 との条件の一致が揃うまで降ろさない。adopter にもしない
5. IMPL-0462 は、席・受信箱・名簿の `team` に発注側・受注側を持たせて ADR-0069 決定2 を迂回しない。`issue=357` へ付け替える
6. IMPL-0283 を全体として adopter にしない(ADR-0094 決定4)。adopter にできるのは GitHub の外の通知の経路だけ。食い違う note は直す
7. adopter の理由には、IMPL-0277・0279 と同じ水準で、具体の依存先を名指す。名指せないものは scheduled とする
8. 抽出・検出の対象を、記録の当事者に選ばせない(ADR-0116 決定5 と同型。IMPL-0174)
9. 本文の定義の欠け(IMPL-0174 の件数と抽出者、IMPL-0467(c) の前提、IMPL-0381 のゲート欄の値)を、テンプレートの側で発明して規範に見せない。本文で決めるか、EV マークで開示する
10. 強制層(`scripts/gate/**`・ワークフロー)の変更は needs-platform を経る。テンプレートの CLAUDE.md の定めにより、AI維持管理者の承認待ちをコミットに書く
