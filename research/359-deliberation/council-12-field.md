## 議題1 IMPL-0342 1名の体制の自己の任命

**結論**: 降ろす。条件は IMPL-0483(ADR-0122 決定1)と同じ「当事者以外で記名できる者がいない」に揃え、法的な形態の記載と、開示の機械による生成を加える。降ろさないまま待つ案は、より悪い迂回を残すので採らない。

- 場面(個人事業主の承継): 個人事業主 A が1名で運用していた。A が引退し、子 B が事業を承継して新しい個人事業主になる。A は体制から外れる(発生)。B は自分を決定者に任命したい
  - 【読】いまのテンプレートは、前任が外れた後は組織上の任命権者の記名だけを受け付ける(generate-profile.mjs:2715)。B の上に任命権者はいない
  - 【読】決定者の席が空いている間は、任命権者を名簿へ記名なしで置ける(:2047)。置いた任命権者は次の変化点から記名できる(:2748)
  - 【推】B が取る道は、配偶者か自分の別アカウントを「組織上の任命権者」として置き、次の変化点でその記名で B を任命することである。結果は、実体の無い任命権者の記名として記録され、**自己の任命として開示されない**。ADR-0122 が EV-0243 で開示した「名簿のアカウントが別の人か機械が確かめられない」根と同じ経路である
  - 【推】もう1つの道は、構成を消して /process-init から作り直すことである。変化点の履歴が切れる
- 場面(1名のアカウント移行): 個人事業主が GitHub アカウントを替え、古い行を先に「離脱」させてから新しい行を任命すると、同じ形で詰む。古い行を残して移せば ADR-0122 の経路で通るが、採用者は順序の違いを知らない
- ADR-0122 自身が「例外なしの禁止は1名の体制で行き止まりを作り、迂回を誘うだけで統制を強めない」(採らなかった案 2-F)と書いている。IMPL-0342 だけ禁止を残すのは、同じ判断と食い違う
- 反対の委員の「大きな組織の中の1名のチームと区別できない」は正しい。ただし、同じ穴は IMPL-0483 で既に D-0 の記載の確認で受け付けている。IMPL-0342 だけを止めても穴は塞がらない。塞ぐのは記載の偽りを見つける人(内部監査・3.13.5 の確認者)である
- 運用できる条件(すべて要る):
  1. 変化点の後の体制の内が1名で、名簿に組織上の任命権者がいない。前任の離脱の行が同じ変化点か前の変化点にある
  2. D-0「決裁の権限の出所」に法的な形態を選ぶ形で書く(個人事業主 / 1名で代表権を持つ法人)。法人は登記事項(代表取締役1名)の参照を書かせる(FX-17・FX-18)。空欄・自由記述だけなら受け付けない。大きな組織の1名のチームがここに「個人事業主」と書けば、署名した文書の虚偽になり、灰色の運用ではなくなる
  3. 変化点の記録に種別「自己の任命」を残し、保証の開示の項目7 へ機械が出す。採用者が消せない
  4. 体制の内が2人以上になった後の最初の変化点で、自己の任命を本人以外が追認するかを /pit に出す(ADR-0122 決定の「発生で入った兼務を後で解く」と同じ型)。追認を義務にはしない
  5. テンプレートの錠を緩める向きなので needs-platform を経る(反対の条件10)
- 採らない案
  - 降ろさずに待つ(反対の案): 待つ間、承継の場面の採用者は開示されない迂回へ流れる。「厳しすぎる側の未達で安全」という見立ては、迂回の経路があるので成り立たない
  - adopter にする: 採用者が錠を自分で外す。反対の委員と同じく採らない
  - 外部の確認者の記名を義務にする: 1名の事業者に第三者を探させる詰みを作る(ADR-0122 で退けた R-2 と同じ理由)

## 議題2 IMPL-0462 受託の構成の価値責任者の所属

**結論**: 名簿や席に所属を持たせず、AI-SLA 合意確認書の第9節に「価値責任者(発注側の氏名と席)」の行を置き、名簿の価値責任者の席の責任者がその氏名と一致するかを機械が照らす。#357 へ付け替えて待つ案は採らない。

- 場面(受注側のリポジトリ): 受注側 5名が自社のリポジトリで開発し、発注側の担当者は GitHub アカウントを持たない。G-2 の承認が要るたびに、受注側の PM が「発注側の了承はメールで取った」として価値責任者の席に自分を入れる。最も多い形骸化はこれである(悪意でなく便宜)
  - 自己申告の `organization: vendor` の欄は、この PM が便宜で `orderer` と書けば通る。欄を足しても止まらない
  - 名簿の `team` は、10名以上の規則で既に「別の所属」の判定に使われている(next.mjs:1462)。受託でも `team` に会社名を書く採用者が出る。禁じても書かれる。【推】
- 場面(発注側のリポジトリ): 発注側 1名の情報システム担当が、複数の受注会社を GitHub の組織へ外部の協力者として招く。価値責任者は発注側にいるが、PO の席の作業を受注側のリーダーに「委任」する。規定は委任を禁じていないが、責任者の記名が受注側に移ると規定に反する
- 照らす相手を契約書にする理由: 外部のモデル契約は、PO を発注側が選任することを契約の体制の条項と契約前のチェックリストで確かめる(FX-21・FX-23・FX-24)。AI-SLA 合意確認書は発注側・受注側の双方が第15節で合意する文書で、受注側の一方の申告ではない。ADR-0069 決定2 が課さないとしたのは「席と受信箱に所属を持たせること」で、契約文書の行と名簿の氏名の突合はそれに当たらない
- 運用できる条件:
  1. 第6章テンプレ8 第9節に行「価値責任者(発注側): 氏名・席」を足し、テンプレートの `08-ai-sla.md` へ写す(ADR-0040)。受託(q-dev-form が outsourcer・vendor)のときだけ必須
  2. 機械は、その氏名と名簿の価値責任者の席の責任者の氏名が一致しなければ、G-2 の判定の前に止める(緩める向きでない)。行が空欄なら「確かめられない」と出す
  3. 価値責任者の変更は契約の体制の変更なので、AI-SLA の改版と名簿の変化点を同じ日に要する、と注記する。片方だけ直した状態を /pit に出す
  4. 残る穴(合意確認書そのものを受注側が書き換える)は機械で止めない。G-2 の判定記録に合意確認書の版を書かせ、発注側の確認者が版を見る
- 採らない案
  - 名簿の行に `organization` を足す(起案): 自己申告で、便宜の誤記を止めない。信頼性が上がらないのに「検出している」と表示する
  - `issue=357` へ付け替えて待つ(反対): 受託の採用者はいま契約を結んでいる。待つ間、価値責任者の所属は誰も確かめない。#357 の構成の欄の設計と衝突しない(契約文書と名簿の突合で、構成の欄を足さない)
  - GitHub の outside collaborator の属性で判定する: 発注側が受注側を組織のメンバーにする運用があり、所属と一致しない(FX-28 の示唆)

## 議題4 IMPL-0377 必達基準2 の到達の見込みの算定

**結論**: IMPL-0374(完了スループット)と同じ計画で降ろし、0374 より先に delivered にしない。SC-M の母集団はラベルで示し、ラベルの無い未完了の作業単位を遅い側へ含めて数える。費用の単価は案件ごとの1つの値として企画書へ書かせ、無ければ期間の見込みだけを出す。

- 場面(10名以上・B-2 の会議): 必達基準の判定の時点で算定の機械が無いと、価値責任者が「到達の見込み」の節を手で埋める。IMPL-0381 が節の有無を確かめるようになったので、**空欄でない手書きの数字が通る**。7.7.3 が禁じた「人の見積り」が、検査を通った形で残る。降りていない間の最も大きい危険はこれである
- 閉じた Issue を数えて算定すると、閉じただけの作業単位で速い側に寄る(反対の委員の IMPL-0374 の論点)。0374 の前に 0377 を降ろすと、算定の機械が誤りを正当化する
- SC-M のラベルの付け忘れ: ステージの途中で作業単位を分割した担当者は、ラベルを写し忘れる。ラベルの付いた件数だけで数えると、付け忘れるほど見込みが良く見える。【推】ラベルの無い未完了の作業単位を「層の指定なし N 件」と並べ、遅い側の端はそれを SC-M に含めて算定すれば、付け忘れは見込みを悪くする側に効く(FX-29 の「件数の幅」で母集団の不確かさを表す型と同じ)
- 費用: 1〜2名のスタートアップは会計の基盤を持たない。単位期間あたりの費用(月の人件費と委託費の概算)を企画書に1つ書けば足りる。会計の基盤への接続は adopter(IMPL-0277 と同型)。値が無いときは費用の組を「入力なし」と出し、区分は期間の組だけで出したと明示する(「算定できない」は単位期間が3つ未満の意味なので混ぜない)
- 運用できる条件: 0374・0377・0283 を1つの計画(Issue の読み出しの共通の部品)に載せ、順に delivered にする。それまで IMPL-0381 の出力に「到達の見込みの算定はテンプレートに未実装。節の値は手書き」と併記させる
- 採らない案
  - 0374 の前に 0377 だけ降ろす(起案の順): 誤った入力の上の算定になる
  - 母集団を企画書のスコープ3層の一覧で示す: ステージの途中の分割に追随しない。ラベルより早く腐る

## 議題5 IMPL-0467 前提の判定記録を読めない着手

**結論**: (a)(b) は新しい様式のファイルを作らず、席のアカウントによるレビュー・コメントに宣言行を置く形を第6章テンプレ4 の「判定記録の媒体」として本文に定め、テンプレートが読む。(c) は本文で「機能へ対応づけない作業の類型」を G-1 で決めて記録する形(ITIL の標準変更の型、FX-38)を定める。それまでの間は「判定できない」の件数を数えて表示する。

- 場面(c が最も多い): スタートアップの Issue の多くは、依存の更新・CI の修正・文書の直し・調査で、機能 F-NNN に対応づかない。【読】これらはいま --pickup で毎回「判定できない」(終了コード4)になる(next.mjs:492)。1週間で数十回出ると、担当者と AI の担い手は --pickup を実行しなくなるか、終了コード4 を「進めてよい」と読むことを覚える。止める仕組みが、最も頻度の高い作業で形骸化する
- 場面(a): 出荷判定者が証跡の集約を見て、PR を qm-blocked へ戻す。判定者は GitHub の「変更を要求」のレビューを書くのが自然で、別の記録ファイルは書かない。様式をファイルで新設すると書かれない
- 場面(b): 価値責任者が needs-po の問いに Issue のコメントで答え、ラベルを needs-dev へ替える。ここで別の判定記録のファイルを求めると、コメントの写しを作る転記の作業になる
- 運用できる条件:
  1. 第6章テンプレ4 に、判定記録の簡易な媒体として「席の責任者のアカウントによる PR のレビュー・Issue のコメントで、宣言行(種別・対象・結論・記名)を持つもの」を定める。テンプレートの /gate が既に「承認レビューの本文」を受け皿にしている型の延長である。記名者の追跡は外部の規範が求める点(FX-34(g)・FX-36)を満たす
  2. --pickup は、遷移の直前に、遷移先の前提に当たる席のアカウントの宣言行があるかを読む。ラベルを替えたアカウントだけでは前提にしない(ラベルは判定の成立要件ではない。3.5.5 要求事項4)
  3. (c) の本文: 「機能へ対応づけない作業の類型と、その類型の着手の前提」を G-1 の企画書か D-0 に書き、事業決裁者(または価値責任者)が記名する。作業単位はその類型を示すラベルを持ち、前提は「類型の一覧の承認の記録」と「価値責任者による受信箱への配分(3.5.5 要求事項7)」とする。一覧に無い作業は「判定できない」のまま止める
  4. 本文が定まるまでの間、--pickup の「判定できない」を作業単位ごとに数え、/pit と出荷の集約に件数を出す(FX-37 の「無承認の変更を数える」型)。黙って止め続けない
- 採らない案
  - (c) を needs-po を経た価値責任者の判断とテンプレートがみなす(起案): 本文に無い前提の発明で、needs-po を経ない chore は救わない
  - (a)(b) の専用の記録ファイルを新設する(反対の案の読み方の1つ): 書かれず、ラベルだけが遷移する現状に戻る
  - 「判定できない」を警告に格下げして着手させる: 3.5.5 要求事項5 に反する

## 全体の所見

- 5件に共通するのは「降ろさない・委ねる」の間に、採用者がテンプレートの外の道(実体の無い任命権者・便宜の記名・手書きの見込み・終了コードの無視)を作ることである。未達の表示はその道を止めない。判断軸の信頼性からは、閉じた条件と開示を付けて降ろすほうが、待つより記録が実態に近い
- 議題2・5 の案は第6章テンプレ8・テンプレ4 の欄の追加を伴う(ADR-0040 により本文が先)。議題3・5(c) は本文の値と定義の新設で、EV マークの対象である
