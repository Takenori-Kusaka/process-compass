# #328 残り1点「外殻・内殻」の定義の欠け: 調査(束 B18)

## 受付の理由: 軽

- 語の定義の欠けと、用法どうしの食い違いの解消である。安全・法令・ADR の原則の変更に当たらない
- 案 A・B は採用者に新しい義務を課さない(下の 3)。外部の調査は不要
- 重へ上げる要因は、案の選択で「外殻の合意(G-2)」の意味(G-2 の合意を変える経路)が変わる場合だけ。下の案 C はこれに触れうる
- 会議体は起案と反対の2委員。編集の指摘には当たらない(定義の新設・語の割り当ては意味を変える)

## 2. 1.4 と関係 ADR との突合

- 1.4(phase4-process-design/overview.md:100-111)にあるのは「AI協調ループ」「マクロライフサイクル」「事業ステージ」「ステージ移行ゲート」「工程ゲート」「ゲート」など。「外殻」「内殻」「内側」「マイクロ」は無い。マクロの対の階層は「AI協調ループ」
- 1.4 の定義では、ステージ移行ゲート(SG)はマクロの制御点、工程ゲート(G-1〜G-8)は「1つの開発サイクル内」(= AI協調ループの側)の制御点。したがって (b)「外殻の合意(G-2)」は、1.4 の語では工程ゲートの合意であり、マクロでない。lifecycle.md:735 の食い違いはここ
- ただし実態は単純でない。G-2(要件合意および契約)は契約・SC-M を固定する決裁であり、変更が R1(SC-M・契約・外部インタフェース)に及ぶと既存の稟議・決裁(マクロの「既存制度との関係」欄)の変更管理を起動する(2.10.8)。つまり (b) は「工程ゲートの中で、マクロ側の決裁と結ぶもの」を指している。この意図は ADR-0019 の「外殻(低頻度・既存決裁)」に由来する
- ADR-0019 は外殻 = 低頻度・既存決裁、内側 = 高頻度・AI協調ループ。ADR-0118 は5語が 1.4 に無いと確認したが、採るかは決めていない
- overview.md:263 に「マクロゲート」(1.4 に無い語。SG のこと)が残る。同じ系統の語の揺れとして併せて見る価値がある
- 図の代替文(1)は「外殻 = SG-0 / SG-1 を含む節目」で、(a)。同じ lifecycle.md の中で (a) と (b) が併存している

## 3. 直す案

### 案 A: 1.4 に「外殻」「内殻」を足して定義し、(b) の用法を直す

- 追加: 外殻 = マクロライフサイクルの別名(事業判断の節目。SG と既存の稟議・決裁を指す)。内殻 = AI協調ループの別名(工程ゲート G を含む)
- 直す行: 1.4 の表に2行。lifecycle.md:735・758 と gate-criteria.md:329 の「外殻の合意(G-2…)」を「G-2 の合意(既存の稟議・決裁と結ぶ)」の形へ。ADR-0078 は採用済みなので本文を直さず、新 ADR か注記で扱う。phase1 summary:56 は定義に合わせて自然に一致。ADR-0019 は同様に採用済みのため触らない
- 意味: 語の割り当て上は意味を変えない(G-2 を外殻と呼ばないだけ)。ただし「内殻」を 1.4 に置くと、その名で本文に使われていない語を定義することになる
- 新しい義務: なし
- 問題: 1.4 の語が増える。ADR-0118 の異表記検査への登録が要る(provision-forms)。「内殻」は実用がほぼ無く、定義だけが増える

### 案 B: 「外殻」を定義せず、用法を既存の語へ置き換える(本体の 3〜7・9 を直す)

- 直す行: lifecycle.md:735, 744, 751, 758、gate-criteria.md:329、proposal-template.md:57、tool/requirements.md:73・78、data/tailoring の rules-supplementary.yaml・practices.yaml の 7 箇所前後、複製 JSON(`npm run template:kb`)、図 SVG 2 枚と図の代替文。ADR-0019・0078 は本文を書き換えない(採用済み)。必要なら新 ADR で「外殻」は旧称だった旨を記録
- 意味: 3〜7 を「G-2 の合意」「マクロの決裁(既存の稟議・決裁)」に直す。階層としての外殻・内殻の語は消える。意味を変える箇所は 4・5(「外殻の変更管理」を何と呼ぶか)だけで、選び方に判断が要る
- 新しい義務: なし。ただしタイロリング規則(rules-supplementary)の文言を変えるため、template の記述と suite の fixture(文言を固定している場合)に波及する
- 問題: 変更行が最も多い。公式用語の削除は #438 の前提(外殻・内殻を公式用語とする)と反する。所有者の方針(細かい定義を増やさない)には最も合う

### 案 C: 外殻を (a) に限定して 1.4 で定義し、(b) の「G-2 の合意」を別の語で定義する

- 1.4 に「外殻 = マクロライフサイクルの別名」を置き、(b) は「契約の合意」など既存の G-2 の語で言い直す。内殻は定義しない(「内側」「AI協調ループ」を使う)
- 直す行: A と同じ箇所のほか、(c) の用法(11〜14)が外殻 = ゲート群の総称で、定義と合うかを個別に見る
- 意味: (c) の「外殻ゲート」(企画承認・出荷判定)を (a) に限ると、出荷判定(G-7)は工程ゲートなので外殻ゲートに含まれなくなる。タイロリングの対応づけ規則の意味が変わる。これは採用者の対応づけ(既存の決裁との対応)に影響しうるため、重へ上げる要因になる

### 所見(所有者の方針に照らして)

- 方針は「条文は結果と証跡まで、細かい定義を増やさない」。案 B が最も定義を増やさないが、変更行が多く、図・規則データ・複製に及ぶ
- 案 A のうち「内殻」の定義は実用が無く、増やす理由が弱い。「外殻」だけを足す A' (内殻は定義しない)が最小の定義で、食い違いの原因は (b) の G-2 を外殻と呼んだ点にあるため、A' + (b) の直しで足りる
- (c) の「外殻ゲート」は、定義が (a) になると意味が狭まる。11〜14 の扱いが案の分かれ目で、会議体で決める点
- 推奨の方向(議長の裁定の前の見立て): A' を軸に、(b) を「G-2 の合意」へ直し、(c) は「既存の決裁・承認ゲート」へ言い換えるか、(a)+(b) の総称として 1.4 に書くかを会議体で競わせる

## 4. 外部の調査

しない。新しい義務を課さず、規格の引用も要らない。

## 5. template 側への波及

- template の md・様式に「外殻」「内殻」は無い。複製の知識ベース template/scripts/vendor/tailoring-kb.json の 7 箇所(933・936・955・1000・1011・1289・1290)だけが該当する
- 正本は src/data/tailoring/(practices.yaml:27-28、rules-supplementary.yaml:35,36,46,70,74)。案 B・C で文言を変える場合は、正本を直したあと `npm run template:kb` で複製を再生成する。乖離は `npm run check` が検出する
- 案 A(1.4 に語を足すだけで規則データの文言を変えない)は、template の様式(`src/data/template-fields.yaml` の必須欄)に影響しない。1.4 の用語表は様式の必須欄ではない
- 規則データの文言を変える場合は、tpl2 の suite の fixture が文言を固定していないかを突合する(過去の記録で fixture が決定を固定していた例がある)
- template と本体の push は対で行う(template の変更があれば)。案 A では template の変更なし
