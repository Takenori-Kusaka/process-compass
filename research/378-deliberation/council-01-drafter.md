## 1. 論点1: 連鎖する場面を単独で流せる形にどう分けるか

### 立場

試作の形を採ります。`r3-scen`・`r3-verify`・`r3-succession` の 3 本が、それぞれ `adopter()` と `trialSteps()` で採用者のリポジトリと a〜g を作り直します。ただし次の2つを採用の条件とします。

- 元の連鎖が持っていて、試作の `r3-verify`・`r3-succession` が作らない状態の一覧を、各スクリプトの冒頭の注記と調査の記録に書く。読んだ限りでは次の 4 つ
  - scen の q が類型E の実施日を `2026-10-05` へ直した状態(試作の r3-verify・r3-succession では未来の `2026-10-09` のまま)
  - scen の q が D-0 表7 の「開発者(検証者)」へ実測を転記した状態
  - scen の h〜j が作った記録・集計・PR(記録の件数、`.git/prs/` の番号、G-6 の判定記録)
  - 元の各段の冒頭の「テンプレートの更新を PR で取り込む」コミット(段0)
- 上の状態を持つ連鎖(`r3-scen` の本体 → `r3-verify` の本体 → `r3-succession` の本体を1つの作業用の複製で続けて流す)で、50 場面の合否が単独の場合と同じことを一度だけ実行で確かめ、結果を `research/378-deliberation/` に残す。同じでなければ、その場面は連鎖の状態に依存しているので、単独の形でその状態を前提として作る

### 理由

- 連鎖の順序そのものは、どの場面の「固定する決定」でもありません。scen2 の決定(S24・S25)は記録の要約値と人が書く欄の扱い、scen3 の決定(S23・S25・3.4.3)は記録だけのコミットと代理者の数え方です。読んだ限り、scen2・scen3 の判定の式が読むのは、a〜g の後の記録・演習の記録・退出の予行の記録・D-0 節9 と、各段が自分で作る状態だけです。連鎖は当時の作業の都合でした
- 連鎖では、前の段の失敗が後の段へ流れます。元の scen2・scen3 は、前の段が途中で落ちても、残った状態の上で判定を続けました。どの決定が壊れたのかを、落ちた場面から読み取れません。単独の形なら、落ちた場面がその決定を指します
- 単独の形は、ADR-0089 決定3 の場面の一覧の照合と合います。スクリプトごとに場面の一覧を宣言でき、1本の早期の終了が他の2本の場面を消しません
- それでも「読んだ限り」は実行での確認ではありません。連鎖の状態に黙って依存する場面があれば、単独の形はその場面を別の状態で確かめていることになります。一度だけの連鎖での比較は、この推定を実行で確かめるために要ります

### 採らない案と理由

- 元の連鎖を1本で流す案(scen → scen2 → scen3 を1スクリプトで続ける): 採らない。前の段の失敗が後の段を不明な状態で判定させる形が戻る。1本の早期の終了で 50 場面のうち後ろがまとめて消え、どの決定の固定が失われたかを場面の一覧の差分からしか読めない。連鎖の順序は固定する決定ではないため、この形を常設する理由が無い
- 3本が前の段の場面まで流す案(r3-verify が r3-scen の全段を、r3-succession が r3-scen と r3-verify の全段を流す): 採らない。前の段の場面を判定として流すと、同じ決定の場面が 2〜3 本に重なり、1つの欠陥が 3 本で落ちて原因の場面が分からない。判定せずに段だけを流す形にしても、前の段の失敗が後の段へ流れる問題は残る。必要なのは、連鎖の状態に依存する場面があるかを知ることであり、それは一度の比較で足りる(条件の2つ目)
- 連鎖の比較を常設の実行(`@regress` の `runs` の1つ)にする案: 採らない。比較で依存が無いと確かめた後に常設すると、同じ場面の名前が2つの実行に重なり、場面の一覧の宣言が意味を失う。依存が見つかった場面は、単独の形の前提へ取り込む方が、その依存を名指して固定できる
- 試作のまま、比較を行わずに採る案: 採らない。「a〜g の後の状態で足りる」は、試作の注記が `decision.md` を引いて主張しているが、その根拠は読んだ結果だけである。信頼性を判断軸にする以上、実行で確かめられる推定は確かめる

## 2. 論点2: 採用者の製品のコードの生成を決定的にする方法

### 立場

試作の形を採ります。製品のコード・テスト・受入基準は `scripts/regress/fixtures/adopter-r3/` の固定の本文を写し、欠陥注入が書き換える行(`inspection.js` の 6・11・16 行、`permission.js` の 3・4 行)の中身を、写した後に確かめます。あわせて、7 節の D1・D2 のとおり、確かめを lib-r3 のすべての入力の書き換えへ広げます。

### 理由

- 固定の本文は、場面の入力そのものが PR の差分として人の目に触れます。注入の行・見つける者の記録の行番号(6・11・16・3・4)と、受入基準 AC-1〜AC-3、`tests/README.md` の存在は、場面の期待値と直に結び付いています。入力を読めば、場面が何を確かめているかが分かります
- 行の中身の確かめは、行番号を前提にする場面(trial d の注入の記録、見つける者の記録の `line`)が、本文の変更で黙って別の行を指す形を止めます。外れたら `throw` で止まり、スクリプトの異常終了と場面の一覧の不一致の2つで落ちます
- `copyTree` が CRLF を LF にそろえるため、Windows で取得した作業ツリーでも同じ本文になります

### 採らない案と理由

- 生成スクリプトで本文を組み立てる案(JavaScript の文字列から書き出す): 採らない。固定の本文と情報の量は同じで、差分が文字列の連結として現れ、読み手が本文を読みにくい。決定性が増すわけでもない
- テンプレートの雛形(`--stack node` が置くもの)から作り、注入の行を探して当てる案: 採らない。雛形は試験の対象であり、テンプレートの変更が場面の入力を黙って変える。行番号を前提にする場面が、雛形の1行の増減で別の行を指す。試験の対象と試験の入力を分けておく方が、落ちたときにどちらが変わったかを区別できる
- 当時の `adopter/` の本文を探して取り戻す案: 採れない。退避物に無く、`setup.log` にも docs の段の記録が無い(survey.md 1 章)。取り戻せない以上、逆算した本文を固定し、その出所を記録する(論点4)

## 3. 論点3: 場面の期待値をどこから取るか

### 立場

- 期待値の基準は、元のスクリプトの判定の式(当時の期待)です。当時の出力(`out/`)は退避物に無く、そもそも基準にできません。いまの出力を期待値へ写すことは、ADR-0089 決定3 が禁じる「出力をそのまま期待値へ写すモード」に当たるので採りません
- 判定の式を改めるのは、現在の規定の決定を引ける場合だけです。改めた場面は `changed` に、引いた決定・日付・旧い期待値を残します(ADR-0089 決定3)
- survey.md 3.3 の 5 場面(i1・i3・i8・v4・v6)は、どれも決定の中身(目隠しを確かめられない層を未測定にする、人が書く欄の外の書き換えを検出する)が同じで、語と所在だけが改まっています。`changed` の記録で足ります。ただし、いまの記録の形は直します(7 節の D5)
  - v4・v6 の `by: 'ADR-0066'` は、決定を番号で分けた ADR を番号なしで引いている。ADR-0066 は決定1〜5 を持つので、ADR-0089 決定2 の形に従えば `ADR-0066 決定3`(「開発ライン」の定義)である
  - i1・i8・i3 の `by: 'ADR-0057 決定11'` は、改めの根拠である補足(S26・S32・S35)を名指していない。`from` か注記に補足の番号を書く
  - `from` は、元の判定の式の字面(例: `read('evidence/seeded-errors.json')`、`'人の層: 見つける者が注入した者と同じ'`)と退避物の所在を書く。説明の文だけでは、旧い期待値を読み手が復元できない
- j2・B3 の場面の名前から件数を外したことは、期待値の改めではありません(下限の `>= 8`・`>= 3` は元のまま)。ただし場面の名前は場面の一覧の宣言の単位なので、移した記録に1行残します

### 理由

- 当時の期待が、場面が固定した決定の唯一の手がかりです。いまの規定から期待値を書き起こすと、当時の決定と現在の規定の食い違いが、場面を書いた時点で黙って消えます。食い違いがあれば、それは規定の側の変化として `changed` に現れるべきです
- 5 場面の改めは、どれも語・所在の変更を行った決定を引けます。決定の中身を変えた場面は無いので、`knownFailure` の印や重い審議を要しません

### 採らない案と理由

- 現在の規定を基準に、場面を書き直す案: 採らない。上のとおり、当時の決定との差が記録に残らない。ADR-0089 決定1 の「一致を確かめる前に、既存の試験の形へ書き直さない」の趣旨にも反する
- 食い違う 5 場面に `knownFailure` の印を付け、元の期待のまま落とす案: 採らない。印は「落ちることを期待する」場面の欄であり、規定の変更に従った期待の改めには `changed` が用意されている。印を付けると、決定どおりの挙動を欠陥として表示し続ける
- 5 場面を落とす(移さない)案: 採れない。所有者の決定(すべて覆う)に反し、決定の中身は変わっていないため落とす理由も無い

## 4. 論点4: 退避物に無い「docs の段」を、期待値から逆算して作り直したことの妥当性

### 立場

逆算は妥当です。ただし、循環を防ぐために、作り直した入力を出所で3つに分け、3つ目には対照の場面を付けます。

| 区分 | 例 | 循環の危険 | 防ぎ方 |
| --- | --- | --- | --- |
| (a) 元のスクリプトの字面にある | `inspection.js` の注入の行、D-0 節9 の「品質保証部 課長」、表7 の「開発者(検証者)… 新規の機能の追加」、層1 の育成の担当、`tests/README.md`、AC-1〜AC-3 | 低い。期待値と同じ字面を入力に置くだけ | 入力の注記に、字面の出所(退避物のファイルと場面)を書く |
| (b) 現在の規定が要求する | 合否の基準の行「実環境の統制の確認」(S38)、AI の担い手と条件2〜5 の確認(標準 3.4.2・ADR-0054 決定9)、節12 の列「復旧の目安」、`lib288.mjs` と同じ直し | 中。場面を通すために足した入力に見える | 引いた決定を注記に書く。規定が要求する入力なので、足さなければ場面は規定と別の状態を確かめる |
| (c) 期待値から推定した | 区分の下限の規則(`src/auth/**` は R1) | 高い。A2 の「11 / 11」を通すために置いた入力である | 下記の対照の場面と、推定の根拠の記録 |

(c) の区分の下限の規則には、次を求めます。

- 推定の根拠を記録へ書く。テンプレートの場面集 #6 と、「規則(riskFloor)が無ければ止まらなかった」の分岐は、どちらも #288 の実装 `bcaf3da`(2026-10-08)で入った(`git log -S`)。元の採用者は同じ版で「11 / 11」を得ていたので、何らかの区分の下限の規則を置いていたと読める。規則の中身(`src/auth/**` を R1)は推定であり、元の字面ではない
- 対照の場面を足す。規則を外した複製で場面集 #6 が「止まらなかった」になり、記録が「10 / 11」になることを確かめる。これで、A2 の前提の「11 / 11」がこの入力に依存していることが場面として名指され、入力を外す変更が黙って A2 の前提を変えない
- A2 の固定する決定(S25: 記録を1字変えると不一致)は、「11 / 11」の字面そのものに依りません。前提が崩れたときは、試作どおり `throw` で止めます(空振りで通さない)

### 理由

- 循環の本当の危険は、入力を場面が通るまで調整すると、場面が「決定どおりに動く」ことではなく「調整した入力で通る」ことを確かめる形になる点です。(a) と (b) は、入力の出所が場面の外(元の字面、現在の規定)にあるので、この危険が小さいです。(c) だけが、出所が場面の期待値そのものです
- 対照の場面は、(c) の入力が期待値を作っているという事実を、試験の中に明示します。入力と期待値の関係が隠れていなければ、循環は循環として読めます
- 逆算の代わりに場面を落とすことは、所有者の決定に反します。また、場面が固定する決定(S16・S20・S23〜S25・3.4.3・指摘9・10)は、どれも docs の段の細部に依らない挙動です

### 採らない案と理由

- 逆算をやめ、docs の段を持たない場面だけを移す案: 採れない。50 場面のほぼすべてが docs の段の入力(製品のコード・D-0・層1)を読む。所有者の決定に反する
- 区分の下限の規則を置かず、A2 の置き換えの文字列を「10 / 11」に改める案: 採らない。元の採用者の状態(「11 / 11」)から離れ、`changed` で引ける決定も無い(規定は変わっていない)。期待値を入力に合わせて改める形であり、こちらの方が循環に近い
- 逆算した入力を、注記なしにそのまま固定する案: 採らない。後の読み手が (a)〜(c) を区別できず、(c) を元の事実として扱う

## 5. 論点5: [前提] の場面を場面の一覧に入れることの可否

### 立場

入れます。あわせて次の2つを求めます。

- [前提] の場面に `kind: 'precondition'` を付ける(`ghRun` の [代役] が `kind: 'harness'` を持つのと同じ扱い)。元の 50 場面と前提の場面の数を、記録から機械で分けて数えられるようにする
- [前提] が落ちたら、そのスクリプトを止める。以後の場面を、前提を満たさない状態で判定しない。止まったことは、異常終了と場面の一覧の不一致の2つで現れる

### 理由

- 元の setup・trial は判定を持たず、段が失敗しても黙って続きました。段の失敗を場面として出すことは、移す前より信頼性を上げます
- 場面の一覧の宣言(ADR-0089 決定3)は、場面が黙って消える形を止める仕組みです。[前提] を一覧に入れれば、`trialSteps` の早期の終了や段の削除も一覧の差分として現れます
- 前例があります。`expected/scenes/trial.txt` は「ua2: 初期化が通る」「ua2: 任免が通る」を、`performer-account.txt` は [代役] の場面を一覧に持っています
- 止める理由は、前提の崩れた状態の上の判定が、通っても落ちても意味を持たないためです。止めても場面は消えません。一覧の照合が欠けた場面を名指します

### 採らない案と理由

- [前提] を場面にせず、`throw` だけで止める案: 採らない。どの段が前提を満たさなかったかが、場面の記録(`results.jsonl`)に残らない。lib-r3 の置き換えの空振りの `throw` は入力の作り方の誤りなので `throw` でよいが、段の結果(テンプレートの挙動)は場面として記録する
- [前提] を場面の一覧から外し、元の 50 場面だけを宣言する案: 採らない。前提の段が消えても一覧が変わらず、黙って消える形が残る
- [前提] が落ちても続ける案(試作のいまの挙動): 採らない。上の理由。読んだ範囲では後の場面の多くは空の出力で落ちるように書かれているが、すべてを確かめたわけではない

[前提] の場面にも run.mjs の規則で `fixes` が要ります。試作は節の宣言の `ADR-0057 決定11` を受け継ぎますが、前提の場面は決定を固定していません。`kind` を付けたうえで、固定する決定の対応表(`fixes` から生成するもの)が前提の場面を決定の覆いに数えないかを、実装の際に確かめてください。

## 6. 論点6: DISPOSITION.md の表示をどう改めるか

### 立場

- fix288-r3 の行を「移さなかったもの」から外し、移したものの側へ置く。移した先(`r3-scen` 27・`r3-verify` 11・`r3-succession` 12)と、固定する決定を書く
- 次の「再現しなかった点」を、移した行の中に書く(別の段落へ離さない)
  - docs の段は退避物から再現できず、期待値から逆算して作り直した。入力の出所の区分 (a)〜(c) と、(c) が区分の下限の規則であること
  - 元の連鎖の状態(論点1 の4つ)を作らないこと。連鎖での比較の結果
  - 元の段0(テンプレートの更新を PR で取り込む)を作らないこと(作業用の複製がいまのテンプレートから作られるため)
  - ADR-0089 決定1 の「元の仕組みで流した基準(p302)との場面ごとの一致」は確かめられないこと。元の状態を再現できず、当時の出力も無いため。比較の基準は元の判定の式であり、差は `changed` の 5 場面と j2・B3 の名前だけであること
- 旧い表示「一部だけ。`suite/trial.mjs` が…確かめる」が、実際より多くを主張していたことを記録する。survey.md 2.4 のとおり、50 場面と同じ決定を確かめる場面は無かった(ADR-0089 決定7 が ADR-0066 の「影響」について行ったのと同じ扱い)

### 理由

- 「移さなかったもの」に残すと、50 場面を覆った事実が表から読めません。移したものへ置いたうえで、再現しなかった点を同じ行に書けば、「覆った」と「どこまで元と同じか」を読み手が区別できます(CLAUDE.md「書かれていないと課さないと決めたを区別できる状態」)
- 旧い表示の過大な主張を消すだけでは、表示がいつ誤っていたかが失われます

### 採らない案と理由

- 行を消し、移したものの表に1行足すだけの案: 採らない。逆算と再現しなかった点が表から消え、後の読み手が元の場面と同じものを流していると受け取る
- 再現しなかった点を、表の外の段落へ書く案: 採らない。限定を規範と別の段落に置かない本プロジェクトの書き方(#226)と同じ理由で、行の中に書く

## 8. 反対の委員と割れそうな点の見込み

- 論点1: 反対の委員は、連鎖の状態を作らないことを「元の場面と別の状態を確かめている」として、元の連鎖を1本で流す案か、3本が前の段まで流す案を推すと見込みます。起案は、連鎖の順序が固定する決定ではないことと、一度の連鎖での比較で依存の有無を実行で確かめる条件で応じます。比較を常設するかどうかで割れる可能性が最も高いです
- 論点4: 反対の委員は、区分の下限の規則の推定を循環として退け、A2 を「元の採用者の状態を再現できない場面」として表示し続けることを求めるかもしれません。起案は、テンプレートの履歴(場面集 #6 と規則の無い分岐が同じ版で入った)を根拠に推定を採り、対照の場面で依存を名指すことで応じます
- 論点3: `changed` で足りるかについて、反対の委員は、当時の出力が無い以上「元の期待」自体が確かめられていないと指摘する可能性があります。起案は、元の判定の式は退避物に字面で残っており、それが当時の期待の正本であると考えます
- 論点5: [前提] で止めることに対し、止めると後の場面の情報が失われるという反論があり得ます。起案は、前提の崩れた状態の上の判定は情報にならないことと、場面の一覧の照合が欠けた場面を名指すことで応じます
- D3(h2 の空振り)は、重大度「高」と見込みます。独立の突合でも「高」とされれば、CLAUDE.md の規則により重へ上げる判断が議長に要ります。ただし D3 は試作の欠陥であり、標準の条項の改廃ではないので、直して流し直せば足りると起案は考えます
