## 1. 論点1: 連鎖する場面の分け方

### 立場

単独で流せる3本に分ける方針には賛成します。ただし、**「a〜g の後の状態で足りる」は確かめられていない主張**で、試作のままでは採りません。前の段が状態を変える手順を、判定なしで再生する形へ改めることを求めます。

### 理由

- 元の scen2・scen3 は、scen の q の段を経た状態で流れた。q は類型E の実施日を過去へ直し、D-0 表7 へ転記した。そのため元の scen2・scen3 の記録は、類型E を数え、節6 の類型E の行が「基準を満たす」になっていたはずである
- 試作の r3-verify・r3-succession の記録は、類型E を「記録なし」「**基準を満たさない**」と出す(流した記録の節6・節4 で確認)。verify と代理者の場面は、元とは別の内容の記録の上で確かめている
- 要約値の照合・人が書く欄の範囲・節9 の「同上」の行の位置は、記録の内容に依る。いまの場面が通ることは、元の前提でも通ることを意味しない。逆に、元の前提でしか現れない欠陥(類型E を数えた記録で、節4 の転記の案内の行が人が書く欄の範囲に掛かる、など)は、試作では見えない
- r3-verify・r3-succession の冒頭の注記は `research/378-deliberation/decision.md` を根拠に挙げるが、そのファイルはまだ無い。根拠の所在が空のまま、注記だけが判断を述べている

### 代案

| 案 | 中身 | 評価 |
| --- | --- | --- |
| 甲(試作) | 3 本がそれぞれ a〜g まで作り直す。前の段の状態は作らない | 単独で流せる。元の前提を失う。採らない |

## 2. 論点2: 採用者の製品のコードの生成を決定的にする方法

### 立場

構成管理の下の固定の本文(`fixtures/adopter-r3/`)を写す方針に賛成します。ただし、**注入の前の行を確かめるだけでは、注入が効いたことは確かめていません**。

### 理由

- テンプレートの seal・tally は、注入の記録(manifest)の file・line と見つける者の記録を照らすだけで、`trial/injected` の差分を読まない(`adoption-trial.mjs` の 137〜259 行)。注入の置き換えが黙って空振りしても、場面は一つも落ちない
- 注入の置き換えの文字列は、`INJECT_LINES` と `trialSteps` の `s.replace(...)` の2か所に重複して書かれている。片方だけを直すと、注入しない「注入」が通る
- `fixtures/adopter-r3/tests/inspection.test.mjs` は誰も実行しない。PR の本文は「node --test が通過」と書くが、事実としては確かめていない

### 代案

| 案 | 中身 | 評価 |
| --- | --- | --- |
| 甲(試作) | 固定の本文を写し、注入の前の行の中身を確かめる | 前の状態は確かめる。注入の後は確かめない |
| 乙 | 本文を `lib-r3.mjs` の文字列として持つ | 置き場が1つになるが、差分として読みにくい。甲より良い点は無い。採らない |
| 丙 | 元の `adopter/` を探して復元する | 退避物に無く、復元できない。採れない |
| **丁(推す)** | 甲に加えて、(1) 注入の置き換えを `INJECT_LINES` から導いて1か所にする、(2) `git diff main trial/injected` が manifest の 4 行(3・4・6・16)だけを変えたことを [前提] で確かめる、(3) `main` で `node --test` が通り、`trial/injected` で落ちることを [前提] で確かめる | 注入が実在することを実行で示せる。PR の本文の「node --test が通過」も事実になる |

## 3. 論点3: 場面の期待値をどこから取るか

### 立場

期待値は**元の場面の判定の文(固定していた決定)から取る**ことを原則とし、いまの出力へ合わせることは、後の決定が語や所在を改めたことを特定できた場合に限ります。この原則には試作も概ね従っています。ただし、`changed` の記録だけでは「通るように合わせた」と区別できません。**期待値の変更と入力の変更を分けて記録すること**を求めます。

### 理由

- 調査の 3.3 の5場面(i1・i8・i3・v4・v6)のうち、i1・i8・i3 は期待値の変更で、v4・v6 は**入力(置き換える欄の名)の変更**である。`changed` は「期待値を改めた記録」(lib.mjs の定義)なので、v4・v6 の記録は種類が違う
- 実行での確認 A・B のとおり、元の入力のままでは落ちる場面が少なくとも 7 つある(i6・q3・q4・q5・j6・j7・A2)。試作は入力を足して通し、記録はコードの注記と調査の 3.2 だけにある。生成される `changed.md` にも場面の記録にも出ない。調査の 2.4「いまの規定と食い違う場面は無かった」は、元の入力に対しては成り立たない
- `changed` の `by` が「ADR-0057 決定11」と広すぎる。改めた決定は補足 S26・S35 で、場面の固定する決定と同じ番号を引くと、変更の根拠を後から辿れない
- 調査が「いま」の列を「通る」で埋めたことには賛成できない。通ったのは足した入力の上であり、それを列で区別していない

### 代案

- 期待値の変更は `changed`(いまのまま。`by` は補足の番号 S26・S35 まで書く)
- 入力の変更は、場面の記録へ別の欄で残す。例: `inputChanged: [{ by: 'ADR-0054 決定9', on: '2026-11-11', what: '開発者の席の AI の担い手と条件2〜5 の記録を足した', without: '落ちる(AI の担い手の宣言なし)' }]`。run.mjs はこれを `changed.md` と同じ形の表(`inputs.md`)へ書き出す
- 「通るように合わせた」との区別の規則: 期待値・入力の変更は、元の実行(2026-10-07)より後の決定で、その文が変更の中身に触れるものだけを引ける。引けない変更は、合わせたのではなく回帰として `knownFailure` の印を付け、Issue を起こす
- 元の入力に対するいまの挙動も固定する。AI の担い手を置かない採用者で「AI の層は未測定(AI の担い手の宣言なし)」「表7 の転記の案内は出ない」「基準集合の依存は出ない」となる対照の場面を r3-scen に足す。足さないと、入力を足したことで、元の入力の上の挙動が試験から消える

## 4. 論点4: 退避物に無い docs の段の逆算は循環にならないか

### 立場

**値ごとに分けて判断します**。場面の置き換えの文字列(= 元の入力そのもの)から読んだ値は循環ではありません。場面の期待の文(= 出力)から入力を作った値は循環の恐れがあり、それぞれに対照が要ります。

### 理由

| 足した値 | 何から読んだか | 判断 |
| --- | --- | --- |
| D-0 節9 の出荷判定者の代理者「品質保証部 課長」 | scen3 C の置き換えの元の文字列(入力) | 循環ではない |
| D-0 表7「開発者(検証者) / 未確認 / 新規の機能の追加」 | scen q の置き換えの元の文字列(入力) | 循環ではない。列「復旧の目安」の値「1 週」は新たに選んだ値で、その旨を注記する |
| 層1 の育成の担当「品質保証部 課長(QA の候補)」 | j8 の期待の文(出力) | 欄は外部向けへそのまま写される(`org-assurance.mjs` 336〜346 行)ので、期待の文から入力が一意に決まる。循環の害は小さい。ただし j8 は「役割名を伏せない」ことだけを確かめ、同じ欄に名簿の氏名を入れたら伏せることを確かめない。対照が要る |
| 区分の下限の規則 `src/auth/**` は R1 | A2 の期待「11 / 11」(出力) | 規則があったことは `bcaf3da` の #6 の分岐から裏付けられる(0 章)。**path と下限の値は推定**。あわせて PR #2 の区分を R1 にしたことも推定で、元の `prJson` の既定は R2 だった |
| 開発者の席の AI の担い手と条件2〜5 | i6 の期待(出力) | **場面の意味を変える**。元の `setup.mjs` の席は担い手を置いていない。第3巡の当時の挙動は「担い手なしで AI の層を測る」だった可能性が高く、いまの試作は「担い手と条件をそろえた採用者で測る」を確かめる。しかも j6・j7 まで同じ入力に依る(0 章 A)。これは論点3の入力の変更として記録し、元の入力の上の挙動を対照で固定する |

- 逆算の値で通った場面は、「元の場面を移した」ではなく「元の場面の決定を、作り直した入力で確かめる」と表示する(論点6)

### 代案

- 逆算の値ごとに、何から読んだか(入力・出力・推定)を `lib-r3.mjs` の注記と DISPOSITION.md の表に書く
- 出力から逆算した値には、その値を外したときに場面が落ちることを確かめる対照を置く(0 章の変異 A・B を場面にした形)。対照が落ちることが「この入力が場面の前提である」ことの実行での証拠になる

## 5. 論点5: [前提] の場面を場面の一覧に入れることの可否

### 立場

段の前提を確かめて黙って続けないことには賛成します。元の setup・trial が段の失敗を黙って続けたことは欠陥でした。ただし、**いまの形のまま場面の一覧に入れることには反対します**。

### 理由

- `fixes(['ADR-0057 決定11'])` が [前提] の前に宣言されるため、[前提] 16 件 × 3 本と [代役] 7 件が「ADR-0057 決定11 を固定する場面」に数えられる。流した `fixes.md` では、ADR-0057 決定11 が **87 場面**と出る。元の場面は 50 で、そのうち決定11 を引くのはさらに少ない。覆いの量を過大に見せる
- 拒否を確かめる [前提](a の基準なしの run、b の未コミット・書き換え、d の中の manifest・seal の前の tally)は `!r.ok` だけを見る。テンプレートが例外で落ちても通る。場面として読む人は、`suite/trial.mjs` と同じ拒否を確かめていると受け取るが、実際は理由の文を照らしていない
- `lib.mjs` の `check` は `kind` を記録できるが、`run.mjs` も fixes の書き出しも `kind` を読まない

### 代案

- [前提] は場面の一覧に入れる(消えたら気づけるように)。ただし `kind: 'precondition'` を付け、fixes へは数えない(`run.mjs` の書き出しで `kind` を除く)。fixes は `#378` の作り直しの前提とする
- 拒否の [前提] は拒否の理由の語を照らす(`refused` と同じ照合)。照らさないなら名前を「実行しない(終了コードだけ)」として、確かめた範囲を名前で示す
- 一覧の数は「元の場面 50 / 前提 48 / 代役 7」を分けて出す

## 8. 結論(各論点)

1. 単独で流せる3本に分けることには賛成する。ただし前の段の状態を作り直さないことには反対し、前の段の状態を変える手順を判定なしで再生する形(丙)を推す
2. 固定の本文を写すことには賛成する。注入が効いたこと(差分の行・`node --test` の成否)を [前提] で確かめることを足す
3. 期待値は元の判定の文から取り、後の決定が改めた語・所在だけを改める。期待値の変更と入力の変更を別の欄で記録し、元の入力の上の挙動を対照で固定する
4. 元の置き換えの文字列から読んだ値は循環ではない。期待の文から逆算した値(AI の担い手と条件2〜5、区分の下限、育成の担当)は、外すと落ちる対照を置き、出所を明記する。AI の担い手は場面の意味を変えており、入力の変更として扱う
5. [前提] は一覧に入れるが、`kind` で区別して fixes に数えない。拒否の [前提] は理由の語を照らす
6. DISPOSITION.md は「移したもの」へ移す。作り直した入力、元の入力で落ちる 7 場面、改めた期待値、連鎖の前提の扱い、省いた段0 を行の中に書く
