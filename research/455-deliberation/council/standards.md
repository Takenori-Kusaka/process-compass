# #455 会議体 委員「規格」の意見書

- 日付: 2026-11-27。立場: 規格策定機関の目(結果と証跡を求め手段を指定しない。閾値に根拠があるか。外部規格との整合)
- 読んだもの: `decision-draft.md` 全文、`external.md` 全文、ADR-0151 決定1(項目4 の対象)、7.3(`exception-escalation.md:26-44`)。新しい調査はしていない
- 未確認(external.md §7 のとおり): ISO/IEC 27001 附属書A・OpenChain 18974 の本文(有償)、CRA 第13(5)条・附属書I 本文。この意見書はそれらを根拠にしない。SSDF PW.4.4 は草案(ipd)である
- 総評: 案の骨格(実在を独立の基準にしない・来歴は一覧と人の確認・検証失敗だけ機械)は規格の型に合う。ただし、**印の定義の欠け・基準9 の範囲の読み分け・外部規格の使い分けの不整合**の3点に欠陥がある。争点ごとに述べる

## 争点1 実在: A2 に賛成。ただし2条件を付ける

- 賛成の理由: 独立の基準 A1 は、同じ条件(未登録の名前で解決が失敗する)を二重に検査する。規格は一つの結果に一つの検査を置く。A1 は照会の不達という故障点を足すだけである(§1.2)
- 条件1(ADR の採択順): ADR-0261 は IMPL-E(アダプタごとの実行での確認)の**後**に採択する。決定5 が「実行で確かめずに断言した」ことが今回の欠陥の一因である(F-2)。同じ型の断言を、置き換える側の ADR で繰り返してはならない。案は「実行で確かめた後に delivered」と書くが、ADR の採択の前提とは書いていない
- 条件2(項目4 の扱い): 穴(install を空にした構成・`none`・`undetermined`)は、**ADR-0151 の扱いを変えて項目4 に「依存の導入」を出す**ことで開示する。A1 を足す必要は無い。ADR-0151 は依存の導入を項目4 の対象外と決めた(`0151-…md:26`)が、その理由は集約に項目が無いためである(`:17`)。本件で ADR-0044 決定5 の前提に「依存の導入が走ること」が加わった以上、その前提の不成立は開示の対象になる。採用者に新しい義務は課さず、開示だけが増える。軽い変更である
- 規格としての書き方: ADR だけに前提を置くと、標準の本文(第4章 G-5)には「解決の失敗で落ちる」が現れない。G-5 の原則の文へ、結果として1文(宣言した依存が解決できない場合は G-5 が失敗する)を置くべきである。基準の行を増やさず、既に持つ結果を条文で見えるようにする。これは新しい義務ではない
- 採らない案(A1・A3)の表: 異論なし。切り替えの条件を議長裁定で足りるとする点も同意する

## 争点2 基準9: 新設に条件つきで賛成。「実行で偽陽性が出たら一覧へ下げる」は規定として不安定

- 型としての評価: 結果は「検証の失敗 0 件」で、手段(道具)を指定しない。SSDF PW.4.4 の型(組織が定める要求への適合を検証する)とも矛盾しない。新設自体は適う
- **欠陥A(空虚な通過)**: 基準9 の文案は「検証の手段を持たない依存は対象外とし、件数を記録する」だけである。全依存が対象外でも「0 件」で通る。対象外の件数の**記録**は合否に効かない。規格として、対象が空(または一定割合以下)のときの表示が要る。案は IMPL-C(python 系は undelivered)と項目4 で拾うと書くが、基準の行そのものには無い。最小の直し: 「対象外の件数と全体の件数」を記録とし、対象が 0 件のときは通過でなく未実施として項目4 に出す(ADR-0151 の型)。閾値(何割未満は不可)は課さない。根拠が無いためである
- **欠陥B(名称と実体のずれ)**: 行の名前は「来歴・署名の検証」だが、go の `go mod verify` は go.sum との一致(完全性)で、来歴ではない(案の 5.1 も認める)。npm の `npm audit signatures` はレジストリ署名と attestation で、これも出所の完全性である。標準の行名を「完全性・署名・来歴の検証」とするか、「検証」の語の範囲を第4章で定義しないと、アダプタごとに異なる強さの検査が同じ「通過」で現れる。表示と実態の食い違いに当たる
- **「条件つきの採用」への異論**: 「実行で偽陽性が出たら一覧へ下げる」は、採用者から見て**規定の強さが事後に変わる**ことを意味する。規格の条項は版で変わるものであり、実行結果で自動に変わるものではない。取りうる道は2つに限る。(i) 採択の前に EV-C を実行で確かめる(私設レジストリ・ミラーの挙動を1件でも)。確かめられなければ (ii) 一覧の項目として採り、基準9 は次の版へ回す。案は「採用してから確かめる」順で、規格が採るべき順ではない。本委員は (i) を先にすることを推す。時間が足りなければ (ii) である
- 7.3 の例外: 認めるに賛成。7.3 は基準を持つ事項に限る(F-7)ので、基準9 を置くと例外の受け皿も得る。ただし、**例外承認の記録に記名を求める 7.3 要求事項1**との関係は #459 の領分とする案のとおりでよい
- OSV の MAL- の扱い(案 1.3 末行)に疑義: 「基準2 の範囲(重大指摘)」とするが、基準2 は脆弱性の**重大度**で判定する。悪意ある版の勧告は CVSS の重大度を持たないことが多いと思われる(未確認)。重大度を持たなければ基準2 の機械の判定をすり抜ける。実行で確かめるまで、基準2 に含まれると書いてはならない。未確認なら「基準2 が拾うかは未確認」と書き、手引きに留める

## 争点3 cooldown を課さない: 結論に賛成。ただし論拠に不整合があり、印の定義が欠けている

- 閾値を標準が持たない判断に賛成。根拠は観測だけで規格に無い(external §2.3)。Scorecard の点を合否にする案を採らないのと同じ型である
- **不整合**: 案は C3 を退ける理由に「SSDF PW.4.4・CRA は採用者が定める要求への適合の検証を求める型」を引く(1.4)。一方、cooldown の宣言を求める案を退ける(6節)。外部規格の型は「採用者が自ら要求を定め、検証の証跡を持つ」であり、これは**宣言を求める案のほうに近い**。同じ外部規格を、一方では引き、一方では型に沿わない案の却下の理由にしている。どちらかの記述を直すべきである。直し方の候補は、(1) C3 を退ける理由から外部規格を外す(意味の判定で範囲が無い、だけで足りる)、(2) 宣言を「任意の設定・未設定を開示する」型で採る(下記)
- **欠陥C(印の定義の欠け)**: 案は版の公開日時を一覧へ出すが、印を付ける条件の一覧(1.4 (ii))に**年齢が無い**。印が無ければ G-6 の判定者が読む対象にならない。一覧に出して読まれない統制は、案自身が C1 を退けた理由と同じである。公開直後の版をどうするかが決まらないまま「表示 + G-6」とするのは、実質として何も求めていない
  - 代案(新しい義務にしない): 採用者が閾値を道具の設定で掛けているかを、保証の開示(項目4 または新しい行)で**設定の有無として表示**する。「未設定」は不適合ではなく、開示である。値は標準が決めず、設定された値をそのまま出す。これなら閾値の根拠が不要で、「何も要らない」という読みも避けられる。ADR-0151・ADR-0166 の「採用者が決める」型と整合する
- 「手引きだけで足りるか」: 足りない。手引きは規範でなく、読まれた証跡が残らない。上の開示があれば手引きは補助でよい
- 外部の事実の限定: 手元の install に効くのは道具の設定側のみ(F-6)。この点を条文でなく手引きに書くことに異論なし

## 争点4 G-6 基準5 の確認範囲: 線引きに賛成。ただし「印」の集合を固定し、取得不能を加える

- 直接は全件、推移は初出と印の行、という線引きは、確認の記載が確かめられる範囲に収まる。賛成
- **欠陥D**: 推移的な依存で乗っ取りが入る点は、公開者の変更の印で足りるかが問われている。足りるのは、レジストリが公開者の履歴を返す場合に限る。PyPI・Go は返さないか不完全である(未確認)。取得できない場合の表示は案に「取得できず(理由)」とあるが、**その行を印の対象にする規定が無い**。「取得できず」「照会せず」「対象外(私設・git・URL)」を印の対象に加えるべきである。そうでなければ、検査の盲点が人の目に入らない(争点5と同じ根)
- ロックファイルを持たない requirements.txt は推移の依存が見えない。案は「宣言の行だけ」とするが、確認の範囲が見えないことを一覧に表示しなければならない(省略の件数の表示 F-4 の拡張)
- 「意図した部品か」が形骸化するか: 実証が無い(EV-D)。開示で足りる。ただし規格の側から見ると、**確認の記載の様式**(何を見て意図した部品と判断したか。例: 公式の文書・リポジトリへの導線)を1行だけ求めない限り、「確認した」の一語で通る。氏名・記名の欄は不要だが、判断の拠り所の欄は記名とは別である。#459 の方針を侵さない。軽い要求なので、採るかは議長の裁定に委ねる

## 争点5 照会の不達の非対称: 賛成。ただし G-6 の次の一手を条文に置く

- 非対称の根拠は妥当である。合否に使わない欄は不達で止めず、合否に使う基準9 は止める。規格の型として一貫している(判定に効くか否かで扱いを分ける)
- 統制の弱化に当たるか: 一覧の不達を通すだけなら、弱化に当たる。ただし**「照会せず」を印の対象にして G-6 で読ませる**なら、人の確認へ回すだけで、通したことにならない。上の欠陥Dと同じ処置で閉じる
- G-6 の判定者が「照会せず」の行を見て何をするか: 案は書いていない。最小の定め: (1) 再実行で解けるなら再実行する、(2) 解けないなら「確認できず」と記載して例外とする、の2択を手順に書く。判定者は照会を自分でやり直さない(道具を指定しない)
- 未判定を ADR-0151 の未実施と区別する点(ADR-0077 の範囲)に賛成

## 案に無い欠陥・代案(まとめ)

1. 基準9 の対象が空でも通る(欠陥A)。対象外の件数だけでなく全体件数を記録し、対象 0 件は未実施として開示する
2. 基準9 の行名と実体のずれ(欠陥B)。「完全性」を含める
3. 採択の順序(争点2)。EV-C を実行で確かめる前に基準9 を採らない。確かめられないなら一覧へ
4. 印の定義が年齢・取得不能を含まない(欠陥C・D)。印の集合を条文で固定する
5. 外部規格の使い分けの不整合(争点3)。C3 と宣言案の却下で同じ規格が逆向きに働いている
6. MAL- を基準2 に含めるとする記述は未確認(争点2)。重大度を持たなければ基準2 をすり抜ける
7. 年齢の設定の有無を開示する代案(争点3)。閾値を持たないまま「読まれない表示」を避けられる

## 採らない案の表への異論

- 「宣言を求める案」(cooldown の値)の却下理由は、「宣言の欠落が新しい差し戻しを生み、守るのは宣言の有無であって依存ではない」としている。**開示型(未設定を表示する)で採る案は、この表に無い**。却下したのか、考えていないのかが読み手に区別できない。表へ「設定の有無の開示」を、採るか採らないかを明記して足す(CLAUDE.md「却下は成果である」)
- 「署名者が期待したソースリポジトリ・ワークフローと一致」(external §2.3 の行。期待値の宣言が前提)が表に無い。採らないなら、期待値の維持の運用が要ることを理由に足す
- 「SBOM は本件の範囲の外」「EO 14028 を引かない」「Scorecard の点を使わない」は、異論なし。ADR-0121 の引きも合う
- 「第7章の例外承認だけで受ける」を「成り立たない」としたのは正しい(F-7)

## 判断軸(信頼性)から見た優先順

1. 基準9 の空虚な通過(欠陥A)と採択順(EV-C の先行)。ここが崩れると、標準の表示と実態が再び食い違う
2. 印の定義(年齢・取得不能)。表示が読まれない統制は信頼を足さない
3. 項目4 への依存の導入の表示(争点1)。穴の開示
4. 外部規格の使い分けの整理。文面の編集で足りる
