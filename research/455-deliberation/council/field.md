# #455 会議体 委員「現場」の意見書

- 立場: 標準を採用して日々 PR を出す開発チーム(AI エージェントと人)の実務者。判断軸は信頼性(回るか・形骸化しないか・偽陽性で止まらないか・私設レジストリ/ミラー/オフラインで困らないか)
- 読んだもの: `decision-draft.md` 全文、`template/scripts/gate/dependency-diff.mjs` 全文、`template/.github/workflows/gate-g5.yml` の dependency-diff ジョブ(`:497-519`)、`adapters/node.json`(install は `npm ci`)
- 実行はしていない。npm・go の検証コマンドの挙動は私の知識からの推測で、実行で確かめていない。断定した箇所は無く、「要確認」と付けた

## 総評

案の骨格(実在は新設せず、一覧と G-6 で扱い、機械で落とすのは検証の失敗だけ)は現場から見て妥当。ただし次の3点で、現場では形骸化か偽陽性に転ぶ。

1. 基準9 を今回の版で必須の合否にすること(争点2)。
2. 「印の付いた項目」が、照会不達・オフライン・推移的な依存の大量の差分で、印だらけまたは印ゼロになること(争点4・5)。
3. 守る対象の最大の穴(手元と CI の install)を「開示して閉じない」としか書かず、現場で今日から取れる緩和策(導入時のスクリプト抑止、cooldown の雛形)を標準にも準拠テンプレートにも置かないこと(争点3)。

## 争点1: A1 か A2 か(項目4 の扱い)

賛否: **A2 に賛成。A1 には反対。項目4 の拡大には条件つき反対。**

- A1 に反対する理由。「公開レジストリから解決する依存のうち、レジストリに無い名前 0 件」は、現場では私設スコープ(`@org/…`)・社内ミラー・git/URL 依存・workspace で誤判定の温床になる。除外の構成(`ci.dependencyRegistries`)が要り、それを書き損ねた採用者が最初に踏む偽陽性になる。しかも decision-draft 1.2 のとおり、未登録の名前は install で既に落ちる。二重の検査は信頼を足さず、照会の不達という故障点だけを足す。
- A2 の「実行で確かめる」(IMPL-E、F-2)は必須。ここが決定5 の前提そのものなので、確かめずに ADR-0261 へ書き直すと、同じ種類の「表示と実態の食い違い」を作る。要確認として、`dependency-diff` ジョブは install をしない(`gate-g5.yml:497-519`)。落ちるのは別のジョブの install の段(`adapter.mjs run install`)である。**PR の依存の変更が、その install の段を必ず通ることの確認**(ロックファイル無しのスタック、`npm install` 運用、キャッシュヒットで解決を飛ばす構成)を IMPL-E の試験に含めること。含めないと A2 の前提は「ロックファイルがあり `npm ci` が走る構成」に限られる。
- 項目4 の拡大(依存の導入の未実施を出す)に反対する理由。アダプタ `none`/`undetermined`、install を空にした構成の採用者は、そもそも依存を持たないか、導入の段を持たない。毎回の PR で項目4 に「依存の導入 未実施」が出ると、見慣れた警告になり、本当に出たい行(基準9 の未実施など)が埋もれる。出すなら条件を絞る。**マニフェストが変わった PR で、かつ導入の段が走らなかったときだけ**出す。

## 争点2: 基準9 の新設

賛否: **今回の版では基準9 を合否の基準として新設することに反対。一覧の欄(検証結果の表示)と IMPL を undelivered/暫定で置く形を勧める。** どうしても新設するなら下の条件をすべて付ける。

理由(所在つき):

- 偽陽性が未確認(EV-C、2 節の表)。しかも決定の方向が弱い。案は「実行で偽陽性が出たら一覧へ下げる」としている。採用者から見ると、「ある版で落ちる基準が、後の版で落ちなくなる」規定は安定した規定ではない。止まったときに、採用者は規定の誤りか自分の設定の誤りかを判別できない。
- `npm audit signatures` は(要確認)インストール済みの木全体を対象にする。差分の依存だけではない。導入時に既存の依存が1件でも検証に失敗すると、無関係な全 PR が落ちる。案の 2 節は「導入時に既存の依存を検証して解消する手順を手引きに置く」としているが、それは採用の初日の作業量を増やす。基準9 の対象は**差分(追加・更新した依存)に絞る**べきで、そう書かないなら採らない。
- go の `go mod verify` は、モジュールキャッシュと go.sum の一致を見る。レジストリの署名や来歴ではない。CI の新しいキャッシュでは実質的に常に通る。基準9 の名が「来歴・署名の検証」なので、go が delivered と数えられると「検証した」という表示だけが残り、偽の安心を作る(表示と実態の食い違い)。5.1 の表の注記で「対象の言い方を合わせる」とあるが足りない。go は基準9 の delivered に数えず、完全性の確認として別に書くこと。
- python 系は空(IMPL-C)。結果として基準9 が実効的に働くのは node の一部だけ。1 行増やす割に実効が小さい。偽陽性の未確認と合わせ、現時点では一覧の欄で足りる。
- 7.3 の例外承認で先へ進める案(3.2)は、実際は「記名により承認する」(7.3 要求事項1。F-9)を現場に求める。所有者の方針(記名の欄を求めない)とここで食い違う。基準9 を新設すると、不充足のたびにこの経路を通ることになるので、#459 の結論前に基準9 を足すのは順序が悪い。新設を #459 の後へ遅らせる理由として使える。
- 照会の不達を未判定で落とす(争点5)ので、npm レジストリの障害の日に全 PR が止まる。再実行で解けるとはいえ、止まる側の現場の負担になる。

条件つきの新設なら: (1) 差分の依存だけ、(2) 私設・ミラーは構成で対象外にでき、対象外が既定(allow 方式ではなく、公開レジストリを明示した場合だけ対象)、(3) 7.3 の例外が使える、(4) go は含めない、(5) 初回の実装で偽陽性を実行で確かめるまで state を暫定(EV-C)で出す。

## 争点3: cooldown を課さない判断

賛否: **標準が値も宣言も課さないことには賛成。「手引きで勧めるだけ」では足りないと考える。**

- 標準が日数を課さないのは正しい。閾値の根拠が無く、緊急の修正を止める。
- ただし採用者から見ると、標準にも準拠テンプレートにも何も無ければ「何も要らない」と読む。案の 6 節は「課さないと決めた」と明記しているが、それは採らない案の表(議論の記録)に書かれているだけで、採用者が読む標準の本文に出る形になっていない。**標準の本文(第5章または基準8 の節)に「公開からの日数の閾値は標準では定めない。採用者が道具の設定で掛けてよい」の1文を規範の段落に置く**こと。「書かれていない」と「課さないと決めた」の区別(コアポリシー)は採用者にも見える必要がある。
- 実害の本体は手元の install(F-6)で、案はこれを「本件で閉じない」と書く。それはそのとおりだが、現場にとって唯一効くのは cooldown とスクリプトの抑止である。準拠テンプレートに、**既定は緩く、コメントで理由を添えた雛形**(`.npmrc` の `min-release-age`、Renovate/Dependabot の cooldown、`ignore-scripts` の選択肢)を置くことを勧める。標準の基準にせず、テンプレートの設定例にとどめる。これは本件の統制ではなく 5.8.6(#452)への橋渡しで、「手元は #452」という書き方と両立する。
- CI 側の露出(3.3 の2行目: 同じ名前が CI の install で走る)も同様。標準は「残余として開示」だけ。CI の install を `--ignore-scripts` で走らせる選択肢は現場では実用的だが、ネイティブ依存を壊す。**採らない案の表に載せるべき**(課さない/選択肢として手引きに書く、のどちらかを記録する)。表に無いと、読み手は検討されたか分からない。

## 争点4: G-6 基準5 の確認の範囲

賛否: **直接の依存は全件、推移的は初出と印の行だけ、という線引きには賛成。ただし運用の前提が足りない。**

- 推移的を全件読ませない判断は現場の実情に合う。lockfile の1回の更新で推移的な行が数百になりうる。
- しかし dependency-diff の実物は、名前も版も解析せず、差分の生の行を出し、`slice(0, 200)` で切り、表示は 40 行で切る(`dependency-diff.mjs:44`、`:68-69`)。案の F-4 と 5.1 の `dependency-parse.mjs` で解消する前提だが、**解析が node の lockfile 3種(package-lock・pnpm-lock・yarn.lock)に加え poetry・uv・go.sum まで一度に降りる**範囲は大きい。解析の誤りは、そのまま「初出の名前」の誤印(偽陽性)になる。段階導入(node から始め、他は生の差分のまま「解析なし」と表示)を勧める。解析のできないスタックでは、印の対象が空になることを必ず表示する(空の一覧は「問題なし」と読まれる)。
- 印が出る基準が決まっていない。「初出の名前」は、1回の更新で推移的に数十件出ることがある。印が多すぎると読まれず、印が無いと読むものが無い。推移的な初出の名前の件数に上限を設け、超えた分は件数のみを出し、直接の依存の新規は別の見出しで常に先頭に出す、という整理を勧める(F-4 と同じく、省略した件数は必ず表示)。
- 公開者の変更の印だけで推移的な乗っ取りを拾えるか。拾えるのは、照会が成功し、公開者の情報を提供するレジストリ(npm の `_npmUser` など。要確認)に限る。照会せず・私設レジストリでは印が出ない。つまり**印が付かないことは、乗っ取りが無いことを意味しない**。基準5 の確認の文に既にある「悪意の不在を確かめない」の1文に、「印が無いことも同様」を足すこと。
- 「意図した部品か」の確認の形骸化は、現場では避けにくい。レビュアは差分の名前を見ても、`lodash-es` と `lodash.es` の差を意識しない。確認の記載に氏名を求めないのは同意するが、**確認した内容の最小の形**(例: 追加・更新した直接の依存の名前の一覧を、記載の中に再掲する)を求めれば、記載の有無で「読んだ」ことの代わりを減らせる。機械で検査できるのは「一覧に載った直接の依存の名前が、確認の記載に現れているか」まで(決定可能な条件)。意味の判定は manual のまま EV-D で開示する、という案の閉じ方は崩さない。ただし機械の検査が出ると、偽陽性(名前の書き方の違い)が出るので、同じく決定可能に絞り、Issue で扱う。ここは案に無い代案。
- Dependabot/Renovate の PR は大量の更新を毎週出す。ボットの PR で G-6 の確認が毎回必須だと、確認の記載が定型文になる。「AI追加と人追加で扱いを変えない」(`gate-criteria.md:1270`)は維持してよい(申告で検査範囲を変えない)が、ボットの PR の一括の更新に対する G-6 の確認の運用の指針は手引きに要る。

## 争点5: 照会の不達の扱い

賛否: **非対称には賛成。ただし「照会せず」の行を見た判定者の動作を決めないと、弱化に当たる。**

- 一覧の欄を不達で通すのは正しい(合否に使わない欄が、ネットワークの障害で PR を止めてはならない)。
- 問題は、オフラインや私設ミラーだけの環境では**全行が「照会せず」になる**こと。毎回全部が「照会せず」なら、判定者はそれを標準の状態として見慣れ、確認が定型化する。これは統制の弱化そのもの。対策: 全行が照会せずなら、一覧の先頭に1行で「来歴の照会は全件実施されていません。この PR の来歴の確認は G-6 で人が全件行う」ではなく、**「来歴の情報なしに確認した」と確認の記載に書かせる**(G-6 基準5 の (ii) の印の対象に「照会せず」を含める)。(ii) に含めないと、「印の付いた項目を読んだ」の対象から照会せずが漏れる。
- 照会せずが一部だけのとき(一時的な障害か、レート制限か)は、判定者が G-5 を再実行する選択肢を持つ。再実行の上限を決めないと、通るまで繰り返す運用になる。手引きに「1回再実行して、なお照会せずなら、そのまま記載する」と書く。
- レート制限と所要時間。依存が数百件あるとき、無認証の npm レジストリや PyPI の JSON API への照会は遅い・制限に当たる(要確認)。照会に件数の上限・並列数・全体のタイムアウトを置くこと。上限を超えた分は「照会せず(上限)」と出し、F-4 の省略の件数と同じ扱いにする。この設計がないと、基準9 を未判定で落とす設計(2 節)と組んで、大きな更新の PR だけが恒常的に落ちる。

## 案に無い欠陥・代案

1. **F-3 の裁定(条文を実装に合わせる)に賛成**。PR の記述へ書き込む権限に依存する実装は、`pull-requests: write` が無いフォーク PR などで出ない。ジョブの要約を正とする判断は現場の実情に合う。ただし、ジョブの要約は PR の画面から2クリックで、判定者が見落とす。G-6.md の手順は、PR のコメントへの同内容の出力を「閲覧の便宜」として併せて出す形を維持すること(コメントが出なくても失敗にしない)。
2. **ロックファイルが無い構成**(requirements.txt のみ、`npm install` 運用)が一覧・基準9 から外れることの開示が案に無い。これらの採用者には推移的な依存が見えない。IMPL-C と同じ形で「解析できないスタック」を開示すること。
3. **ミラー・プロキシ経由の採用者**(社内 Artifactory 等)は、`ci.dependencyRegistries` を構成するまで、すべて「対象外(私設)」になり、一覧の来歴の欄が空になる。この状態が既定で出ることを、README の手引きの最初に書くこと。構成の書き方の手引きなしに構成の欄を置くと、書き損ねても何も起きず、静かに働かない(沈黙の穴)。
4. **新規の IMPL が5本・EV が4本**は、1件の審議としては多い。実装する担当は実際に確かめる前提(IMPL-E)から先に進め、基準9(IMPL-B・C)は IMPL-E と EV-C の結果が出てからにする、と順序を決めると、確かめないまま降ろす事故が減る。

## 採らない案の表への異論

- 「基準9 を例外を認めない基準にする」を課さないとしたのには賛成。ただし**例外の経路が 7.3 の記名**(F-9)なので、「例外を認める」と書くだけでは、現場は記名なしで進める道を持たない。この表の行の理由に「記名の扱いは #459 の結論による」と書き足すこと。
- 表に欠けている案: (1) CI の install のスクリプト抑止(上記、争点3)、(2) 基準9 を差分の依存だけに絞る案(争点2)、(3) 確認の記載に直接の依存の名前の再掲を求める案(争点4)、(4) 基準9 の新設を #459 の後に遅らせる案。これらを採る/採らないのどちらでも、表に残すこと。
- 「ダウンロード数を表示する」を課さないとした判断には賛成。現場では「多いから安全」と読まれる。
- 「SBOM は範囲外」「EO 14028 を引かない」には異論なし。
