- 読んだもの: `decision-draft.md` 全文、`internal.md` 全文、`template/scripts/gate/dependency-diff.mjs` 全文。`external.md` と ADR-0151・ADR-0044 の本文は読んでいない(下の「未確認」に明記)。判断軸は信頼性
- 総評: 骨格(基準8 の欄の拡張 + G-6 基準5 の2観点 + ADR-0044 決定5 の置き換え)は支持する。ただし基準9 の文案と、非対称な語(未判定・未実施・照会せず・対象外)は、このままでは採用者が一意に読めない。7.3 の記名との矛盾も1点ある

## 争点ごとの賛否

### 争点1: A1 か A2(実在の確認が消える構成)

- **賛成(A2)。ただし条件を3つ付ける**
  - 理由: 未登録の名前が解決で落ちるなら、独立の基準は同じ条件の二重の検査になる(`decision-draft.md` §1.2)。守る対象は登録済みの悪性の名前で、実在の検査はそれを通す(F-1)
  - 条件1: **順序を条文化する**。F-2 のとおり前提は未確認である。ADR-0261 決定1 は、実行で確かめた後でなければ書けない。案は「実装の段で確かめ、落ちなければ A1 へ切り替え」としているが、ADR を先に採択して後で差し替えるのは、採用済み ADR を書き換えない原則と衝突する。**裁定は IMPL-E の実行結果を受けて確定する**と手順に書く
  - 条件2: ADR-0261 決定1 と条文は、「G-5 で捕まる」を**解決が走る構成に限る**と書く。install を空にした構成・アダプタ `none`・`undetermined` では、この保証が無いと書く。限定は規範の同じ行へ置く(#226)。案は開示の仕組みの存在だけを述べ、採用者が読む条文に落ちていない
  - 条件3: 項目4 へ出すかの争点は、ADR-0151 が依存の導入を項目4 の対象外とした理由を突合してから決める。理由を私は確認していない。理由が「依存の導入は構成で選べない必須の段である」型なら、出すのは原則の変更で、重の扱いになる。理由が「出す手段が無かった」だけなら、出すほうを支持する。**A1 を足す案より、未実施を開示する案のほうが、照会の不達という故障点を増やさない**
- A2 の評価欄にある A3 の却下理由(「A2 で落ちる名前は一覧に届く前に止まる」)は、A2 を前提にした循環である。A3 は A2 が成り立たない構成で意味を持つ。表の理由を直す

### 争点2: 基準9 の新設と 7.3 の例外

- **新設の方向は支持する。文案と条件つき採用の2点に反対する**
  - 反対1(文案が一意でない): 「解決元のレジストリが検証の手段を提供する依存」は、性質の判定を採用者に委ねる。npm で版ごとに来歴の有無が違う場合、「手段を提供する」に当たるかが読み分けられない。案 §5.1 の `ci.dependencyRegistries`(構成の照会先)とも整合しない。**対象は、構成が名指ししたレジストリの一覧だけ**(肯定形の一覧)にする。そうすれば私設レジストリ・ミラーは既定で対象外で、EV-C の偽陽性の主な筋が閉じる
  - 反対2(`go mod verify` との不一致): 案 §5.1 自身が、go は完全性で来歴ではないと認める。文案は「来歴の証明または署名の検証」と書く。node の署名の検証と go の go.sum の一致は、別の統制である。**1つの基準番号の下で別物を検査する**と、「基準9 を通った」の意味が採用者ごとに違う。基準の見出しを「依存の完全性・来歴の検証」とし、検証の種類ごとに結果を記録する書き方へ直すか、種類ごとに行を分ける
  - 反対3(条件つき採用): 「偽陽性が出たら一覧へ下げる」は、採用者にとって**安定した規定ではない**。基準の昇降が条文の外の観測に依るからである。条文に昇降の条件を書かない。代わりに、**実行で確かめた範囲(node・go の公開レジストリ)に限って課す**と、決定の時点で閉じる。EV-C は残る(私設・ミラーは対象外と宣言する形で開示)
  - 反対4(**7.3 の記名との矛盾**): 案 §4 は「基準9 の例外は 7.3 の既存の手続に乗せる。新しい記名の欄を足さない」と書く。しかし 7.3 要求事項1 は「記名により承認する」(F-9)。既存の手続に乗せれば、記名は自動的に付いてくる。所有者の方針(2026-11-27)との関係は、#459 の結論に依る。**「足さない」は欄を足さないことしか言わない**。基準9 の例外の読み方が #459 で変わりうると、ADR-0261 に書く(#459 に依存すると認める)
- 例外を認めること自体は賛成。開発者の責めに帰さない筋(鍵の更新)があり、許可リストの救済と同型である
- 採用者の側から一言: python 系は検証の手段が空のため IMPL-C が undelivered になる。**スラップスクワットの被害の主戦場に近い PyPI で基準9 が実質空**になる。開示はされるが、「新設した基準が最も要る場所に降りない」ことは、案の総括に明記すべきである。PyPI の検証の手段(Integrity API 等)が実用に足るかは、`external.md` の確認が要る(未確認)

### 争点3: cooldown を課さない

- **賛成。ただし置き場を条文の側へ広げる**
  - 「課さない」を ADR と採らない案の表だけに置くと、条文の読み手(採用者)には「何も言っていない」に見える。「書かれていない」と「課さないと決めた」の区別を読み手に保つ原則(CLAUDE.md)に反する。**基準8 の節に1文**、「本標準は公開からの日数の閾値を定めない。道具の設定で掛けることは妨げない」を置く
  - 手引きだけで足りるか: 勧めるだけなら足りる。ただし手引きは規範でないので、**採用者が掛けたかを標準は確かめない**ことも1文で書く。pnpm 11 の既定値の記述は、一次の確認を `external.md` で見る(未確認)
- 「宣言を求めない」(採らない案 3 行目)の理由は、宣言の欠落が差し戻しを生むことと読める。これは理由として弱い。宣言の欠落の差し戻しは、宣言を求める全条項に当てはまるからである。強い理由は、**値の根拠が無い(EV-B)ので、宣言された値の良否を判定できない**ことである。理由を差し替える

### 争点4: G-6 基準5 の範囲

- **直接の依存を全件は支持。推移的は「印の付いた行だけ」に反対する(修正案あり)**
  - 問題1: 印の網羅が照会に依る。公開日時・公開者の欄は、照会が不達なら「照会せず」で印が付かない。**印の付かない行は読まれない**。つまり照会が失敗した推移的依存は、確認の対象から外れる。F-4 の切り捨て(200 行・40 行)と合わせると、見られない依存が二重に生じる
  - 問題2: 「意図した部品か」は直接の依存の綴りの取り違えには効く。推移的依存の乗っ取りには効かない。後者は公開者の変更の印だけが頼りで、これは照会が成功したときだけ働く
  - 修正案: 印の付いた行に加えて、**「照会せず」の行と、省略された行(F-4)も確認の対象**に含める。確認の記載は「印・照会せず・省略の件数と、うち読んだ件数」を持つ。件数は機械の出力と突合できるので、形骸化の一部(数を書かない確認)を機械で閉じられる。ただし、数が合っても中身を読んだことは示さない。この限界を EV-D に含める
  - 「意図した部品か」の形骸化は避けられない。案の EV-D での開示は妥当。判定者が何を見るかを、手引きに**取り違えの類型**(綴りの近い名前・スコープの違い・別エコシステムの同名)として例示する

### 争点5: 照会の不達の非対称

- **方向は支持。語の整理と、判定者の手順の欠落を指摘する**
  - 一覧が不達で通ること自体は、統制の弱化とは言い切れない。欄は合否に使わず、G-6 の人の確認が受けるからである。ただしその受け方が書かれていない。案には「G-6 の判定者が『照会せず』の行を見て何をするか」の答えが無い(争点5 の問い自体が未回答)。**書く内容**: 再実行で解ける不達は再実行する。解けなければ、その行を、手元の道具(レジストリの画面等)で確かめた旨を記載するか、確かめられない旨を判定記録の未解決事項へ置く。経路は既存の3経路(例外承認・前提の受容・未解決事項)に乗せ、新しい経路を作らない
  - 用語: 案は**未判定・未実施・照会せず・対象外**の4語を使う。ADR-0151 の「未実施」と、ADR-0077 の「入力の欠落」の区別は、書き手の私にも1度では追えなかった。採用者は一意に読めない。provision-forms と既存の語彙(`community/provision-forms.md`。私は未読)に照らして、**語を3つ以下に整理**する。提案: 「未実施」(構成で選んだ・手段が無い)/「未判定」(入力の欠落。通過に数えない)/「対象外」(構成で外した)。「照会せず」は欄の表示であって状態の語ではない、と位置づける
  - 基準9 の未判定で落とす点は賛成。落とさないと、不達が通過になる穴になる。再実行で解ける

## 案に無い欠陥・代案

1. **F-6 の残余の開示先が無い**: CI の install で悪性が走る(G-5 の時点)ことを、「残余として開示する」と書くが、EV-A〜D にも IMPL にも載っていない。開示の置き場(保証の開示の項、または ADR-0261 決定6 の本文)を指定する。置き場の無い開示は、ADR-0151 の型に反する
2. **F-3 の「PR から辿れる」は一意でない**: 条文を実装に合わせる案は賛成だが、「辿れる」の到達点(PR の検査の画面のどこか)を書かないと、判定者は一覧を見つけられない。G-6 の確認事項は「G-5 基準8 の出力に対する記載」だから、**出力の所在を指す語**を1つ決める(例: 「G-5 のジョブの要約」)
3. **基準9 の「対象外の件数を記録する」**は、行の中に置く案どおり。ただし**件数の記録先(証跡の名前と欄)**が条文に無い。「証跡まで書く」(3.1)の原則に照らして欠ける
4. **実装の順序**: 5.1 は新規ファイルが多い。量は理由にしないが、**解析(dependency-parse)を先に入れ、試験で固めてから照会を足す**直列でないと、解析の誤りと照会の誤りが混ざる。準拠テンプレートの直列の原則(CLAUDE.md)に沿って段を切る
5. **試験の実レジストリの版**: 「手で一度だけ確かめた記録」は、再現できない記録になる。記録の置き場と日付、確かめた版を残す形式を決める(`research/` ではなく試験の記録として)

## 採らない案の表への異論

- 「重要な依存だけ証明を必須にする」の区分「課さないと決めた(本改訂では)」: 括弧の「本改訂では」は期限を暗示し、「決めた」と「保留」を混ぜる。**区分を「課さないと決めた」か「本件で扱わない」のどちらか1つに倒す**。理由が自己申告の線引きなら前者
- 「EO 14028 を引かない」: 理由を二次情報(撤回の報)に置いている。引かない判断は妥当だが、理由を「一次の確認が無い」と書き、断定を避ける
- 「基準9 を例外を認めない基準にする」: 区分「課さないと決めた」で良い。ただし反対4 の記名の問題は、この表では見えない
- 表に**足すべき行**: (i) 一覧へ「ダウンロード数」を出さない、は既存。(ii) **レジストリの照会を基準8 の必須の欄にする案**(照会の不達で一覧が止まる案)を採らない理由、(iii) **ADR-0044 決定5 を書き換えず放置する案**(採らない。表示と実態の食い違い)
- A3(基準8 の欄として実在を表示)の理由は前記のとおり循環。直す
