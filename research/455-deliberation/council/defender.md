# #455 会議体 意見書(弁護。採用者の側)

- 読んだもの: `decision-draft.md` 全文、`intake.md`、ADR-0044 決定5(63-65行)、ADR-0151 決定1(26行・16-18行)。`internal.md`・`external.md` と条文の原本は読み直していない。下の「確かめていない」は、案の記述に依った箇所
- 立場: 案を擁護する前提を置かない。新しい義務が過剰でないか、根拠の無い合否で採用者が止まらないか、既存の決定と矛盾しないか、課さない判断が利用者を危険に晒さないかを見る

## 総評

案の骨格(実在は新設しない・合否を足すのは基準9 の1行だけ・残りは表示と G-6 の確認)は、採用者の負担と信頼性の釣り合いとして概ね妥当。ただし次の3点で、そのままでは採用者が不安定になるか、表示と実態が食い違う。

1. 基準9 は、偽陽性が未確認(EV-C)のまま合否を課す。条件つきの採用(「偽陽性が出たら一覧へ下げる」)は、採用者から見て規定が変わりうる不安定な義務(争点2)
2. 争点1 の穴(install を空にした構成)に対する案の手当てが、ADR-0151 の読み直しを伴うのに、決定の中身が示されていない
3. 義務の総量。基準9・G-6 の2観点・一覧の印・`ci.dependencyRegistries` の新しい構成欄・python の adopter 残し・ADR の6決定が一度に入る。信頼性の観点では、実行で確かめた順に段階を踏む方が採用者は止まらない

## 争点1(論点 a: A1 と A2)

- **A2 に賛成。A1 の追加には反対**。理由は案 1.2 のとおり。照会の不達という故障点だけが増え、攻撃の本体(登録済みの悪性の名前)を守らない。採用者を止める要因を足して信頼を足さない
- **ただし、ADR-0151 の扱いを変えるかに答える**。ADR-0151 決定1(26行)は「依存の導入は集約の検査の項目を持たず、項目4 の対象外」と決めている。実在の確認を A2 で「解決の失敗」に預けるなら、解決が走らない構成(依存の導入コマンドが空・アダプタ `none`・`undetermined`)では実在の確認が消えるのに、保証の開示に何も出ない。これは案 1.2 が自分で認めた表示と実態の食い違い
  - 採る案: **ADR-0151 の対象外の決定は変えない**(決定の置き換えは採用者全体に波及する。重さが釣り合わない)。代わりに ADR-0261 で、基準8 の一覧(新しい欄・状態の行)に「依存の解決: 実施/未実施(理由)」を1行出す。項目4 の対象を広げずに、一覧の側で開示する。これなら ADR-0151 と矛盾せず、新しい合否も生まない
  - 案が「実在は決定可能」としながら項目4 へ出すか A1 かの二択に絞っているのは、選択肢の絞りすぎ。第3の道(一覧の状態行)を会議体の選択肢に加えたい
- **F-2 の扱いに異議**。決定5 の前提が実行で確かめられていないのに、ADR-0261 で「確かめた」と書く運びは、実装の段が先に終わらないと書けない。裁定の段階では「確かめるまで前提」と書き、確かめ前に採用者へ「G-5 で捕まる」を再び約束しない(約束するなら EV でマークする)

## 争点2(基準9 の新設・7.3 の例外・偽陽性が未確認での採用)

- **新設に条件つきで反対。初版は一覧の欄と開示に留め、基準化は実行の記録の後にする**案を出す
  - 根拠: 3条件の2つ目(偽陽性が実効的に無い)を案自身が「未確認」と書いている(2節の表)。CLAUDE.md の「是正の起動」は、機械で失敗させる形にする条件を3つ課している。**自分で満たしていないと書いた統制に合否を持たせるのは、標準自身の原則と食い違う**。F-8 は3条件を「判定基準として当てる」と書いたのに、結論が基準を満たさないまま
  - 「実行で偽陽性が出たら一覧へ下げる」(1.3 表)は、採用者から見て**安定した規定ではない**。標準が版ごとに合否を出し入れすると、採用者の CI の構成・例外承認の記録・G-5 の読みがその都度変わる。下げる場合も ADR を立てる重さがある。条件つきの採用は、採用前に実行で偽陽性を確かめて終える方が筋が通る
- **新設するなら守る条件**:
  - 7.3 の例外承認を**認める**(案に賛成)。開発者の責めに帰さない失敗(鍵の更新の時期・ミラーの遅れ)で止まり続けると迂回が生まれる。例外を認めない案は不採用でよい
  - 「検証に失敗した」と「検証できなかった」(レジストリが署名を提供しない・鍵が取れない・不達)を条文で分ける。後者を失敗に数えると、私設レジストリの採用者が全員止まる。案は不達を未判定にするが、「署名が提供されない」を対象外(件数を記録)に入れるかは書き切れていない(確かめていない。`npm audit signatures` の私設レジストリでの出力は実行で見ていない)
  - 初版は **node のみ**を対象にして、他のスタックは一覧の表示で足りる。案は go の `go mod verify` を「来歴ではなく完全性」と認めながら同じ基準に混ぜる。意味の違う検査を1行の基準に入れると、基準の読みが割れる
- 利用者を危険に晒す側の指摘: 基準9 を一覧に下げると、改ざんの直接の兆候(署名の検証失敗)を人が見落とす余地が増える。これは、一覧に**検証の失敗は別の目立つ行として出し、G-6 基準5 の(ii)で必ず読む対象に入れる**ことで補える。機械で落とさなくても、読まずに通せない形にはできる

## 争点3(cooldown を課さない判断)

- **賛成**。閾値の根拠が規格に無く(EV-B)、正規の緊急の修正を止める。採用者に宣言を求めると宣言の欠落が新しい差し戻しになる、という案の理由も妥当
- 「何も要らないと読まれないか」への答え: 手引きだけでは読み落とされる。**ADR-0261 の「課さないと決めたこと」を、第4章 G-5 基準8 の説明にも1文で書く**(「版の公開からの日数による合否は課さない。道具の設定で掛けることは妨げない」)。「書かれていない」と「課さないと決めた」を読み手が区別できるようにするという CLAUDE.md の原則に沿う。手引きだけに置くと、第4章だけを読む監査者は「基準が無い=決めていない」と読む
- 道具の設定の勧めは、手元の install にも効く点で信頼性が高い。F-6 の残余(手元の露出は #452 の領分)と同じ文に並べて書くとよい

## 争点4(G-6 基準5 の確認の範囲)

- **線引き(直接は全件、推移は初出の名前と印の行)に条件つきで賛成**。全件読ませる案は、数百行を読まずに確認と書く運用を招くので採らない
- 欠陥1: 印は機械の出力に依る。**照会せず・取得できず・解析できず・省略された行**には印が付かない。印が付かない行は読む対象から外れる。条文に「印の付いた項目」と書くと、照会が全面的に不達の日は読む対象がゼロになる。「照会せず/取得できずの行も、直接の依存なら読む。推移の行は初出の名前だけ」と書く
- 欠陥2: F-4 の省略(`slice(0,200)`・40行表示)の件数を表示するだけでは、省略された行の依存が G-6 の判定者の目に入らない。案は「検査を切らない」と書くが、**人の確認の対象からは切れる**。省略の件数が0でない場合の読み方(全件を別の記録から辿れるか、証跡 JSON を見るか)を手順に書く
- 欠陥3: 乗っ取りは推移の更新で入ることが多い、という懸念は残る。公開者の変更の印で足りるかは、案が自分で EV-D(実証が無い)と書いている。**足りないことを開示済みで、課さないと決めた範囲を明記しているので、義務を増やさない現案で足りる**。推移の全件を読ませる案は採らない
- 「意図した部品か」は形骸化しうる。ただし記載の有無しか機械で確かめられないのは、manual と EV-D で開示済み。弁護の立場では、これ以上義務を増やさない現案を支持する。人が答えられる問いに限った点が良い
- 適用範囲(#226 の書き方): G-6 基準5 の2観点が、R1 の変更だけか、全変更に掛かるか。案は書いていない。ADR-0039(リスク区分は変更ごと・CL は案件ごと)に従い、**どの区分に掛かるかを見出しか行に併記**すること。小規模な採用者(1〜2名)の全変更に印の確認を課すなら、その旨を明示してから決める

## 争点5(照会の不達の非対称)

- **非対称は理にかなう**(一覧は合否を持たないので通す。基準9 は入力の欠落なので未判定にして通過に数えない)。ただし2点
  - 一覧の不達を通すことが統制の弱化になる境界を決める。**全行が「照会せず」になった PR は、一覧が出ているだけの形になる**。G-6 の判定者が「照会せず」を見て何をすべきかが案に無い。採る案: G-6 の手順に「照会せずが一部でなく全体のとき、再実行するか、その旨を記載して意図した部品の確認だけを行う」と書く。保証の開示に照会の状態を出す(案の5.1 のとおり)ので、記録は残る
  - 基準9 の未判定で G-5 を失敗にすると、**外部のレジストリの障害で採用者の出荷が止まる**。案は「再実行で解ける」と言うが、障害が長引く場合の出口は 7.3 の例外承認になる。この出口が実際に使えるか(未判定が不充足として例外承認の対象になるか)を、条文で一言書く必要がある。書かないと、未判定は「満たさない」が成り立たず(F-7 と同型)、止まったまま出口が無い
- 基準9 を一覧に留める案(争点2)を採るなら、この問題はほぼ消える。

## 案に無い欠陥・代案

1. **義務の総量と順序**。新設(基準9)・一覧の拡張・G-6 の観点・新しい構成欄(`ci.dependencyRegistries`)・python の adopter 残し・ADR の6決定が同時に入る。python 系の採用者だけ基準9 が undelivered(adopter)になり、同じ標準の採用者の間で保証の水準が割れる。代案: **第1段(確かめた部分)**として、一覧の欄・省略の件数の表示・G-6 の2観点・ADR-0044 決定5 の範囲の置き換えだけを入れる。**第2段(実行で偽陽性を確かめた後)**に基準9 を足す。EV-C の見直し(2027-02)をその契機にする
2. **`ci.dependencyRegistries` は採用者の新しい構成の負担**。既定が公開レジストリなら、私設レジストリの採用者だけが宣言する。宣言が無いと基準9 が私設を公開と見て落ちうる(案は「対象外にできる」とだけ書く)。既定を「宣言が無い解決元は対象外」にする方が偽陽性を出さない。逆の既定では、私設の採用者が最初に止まる
3. **F-3 の裁定(条文を実装に合わせる)は、意味の変更**。「PR の記述」から「PR から辿れる G-5 の記録」への変更は、レビュアが一覧を見つける場所が変わる。編集の指摘ではない。ただし G-6.md が既に「PR のコメントは閲覧の便宜」と書くので、案に賛成。ADR-0261 の決定に1行入れて、軽い扱いにしないこと
4. **3条件の4つ目(既存の違反を解消してある)**が、基準9 では「初回の実行で確かめる」に先送りされている。実行前に採用者へ義務を課すことになる。争点2 の代案(第2段)で解ける
5. **CL の高い採用者**へ標準が何も強めない点は、利用者を危険に晒しうる。ただし ADR-0039 はリスク区分依存の条項の導出を CL から行わないと決めており、強める案は採れない。標準が強めない代わりに、採用者が自ら掛けることを妨げないと書く(案の「採用者が自ら掛けることは妨げない」と同じ型)に留めるのが整合的

## 採らない案の表への異論

- 「実在を G-5 の独立の基準にする(A1)」を「課さないと決めた」と分類するのは**不正確**。切り替えの条件つき(実行で落ちない構成が見つかれば採る)なので、「課さないと決めた」と読み手が受け取ると、条件の存在が隠れる。区分を「条件つきで採らない」に分ける
- 「基準9 を例外を認めない基準にする」は課さないと決めた、でよい(7.3 の例外を認める案に賛成)。
- 「手元の install の露出を防ぐと書く」を「書かないと決めた」は妥当。ただし、**本件の統制が手元と CI の露出を防がないことを第4章の基準の説明にも書く**(案は ADR と手引きにしか置かない)。第4章の読み手が「G-5 の来歴の検査があるから install は安全」と誤読する余地を残さないため
- 追加すべき行: 「照会結果の合否への利用(基準9 以外の欄)」を課さないと決めた、を明記する(一覧の欄を後から合否に昇格させない約束。採用者の予見可能性のため)。もう1行: 「CL・R 区分で来歴の義務を変える」を課さないと決めた(ADR-0039)
