- 日付: 2026-11-04
- 立場: 旧案(2026-09-23 の旧 ADR-0054「確率的な分類器を、引き上げ方向の助言に限り既定無効で同梱する」)と、オーナーの「条件付きで採用」を弁護する。弁護しきれない点は、変えるべきと認める
- 判断軸: 信頼性。変更量の少なさ・旧案の作業量を、採否の理由にしない
- 入力: `council-00-agenda.md`、`survey-401-1-internal.md`(以下「内部」)、`survey-401-2-external.md`(以下「外部」)、ブランチ `docs/adr-0054-phase-advisor` の旧 ADR と評価メモ、main の本文(`human-ai-boundary.md`・`roles-responsibilities.md`・`deliverable-templates.md`)

## 0. 弁護の要旨

旧案は、2 つの層に分けて評価すべきです。

| 層 | 中身 | 弁護の結論 |
| --- | --- | --- |
| 核(設計の原則) | (a) 出力を人へ戻す側にだけ使い、判定・承認・遮断・完了・ラベルの遷移に使わない。(b) 出力が無いことを問題が無い根拠にしない。(c) 既定無効。人の記録がそろうまで外部へ送らない。(d) 版を固定し、閾値は人が較正し、実績から自動で更新しない。(e) 記録から導けることはコードで決定し、分類器には記録から読めない意図だけを尋ねる。(f) 必須の検査(G-5)と構成の推定に入れない | **維持すべき**。その後に入った規定(ADR-0056・0075・0078・0084)と外部の調査の「課せること」1〜4 は、いずれもこの核と同じ向きです。旧案はそれらに先行していた |
| 実装と当てはめ | 製品の名指しと既定値、端末から API キーで直接つなぐ経路、記録の照合(空でないかだけ)、G-4 記録の置き場、評価の正解ラベル、Haiku の却下理由、「オーナー」の決裁、リポジトリの `settings.json` へのフックの登録 | **変えるべき**。うち 4 点(3.12.2 の経路、記録の照合、5.8.6 の未達の下での同梱、Haiku の却下理由 (1))は、旧案の時点でも欠陥か、その後の規定に正面から当たる |

オーナーの「条件付きで採用」は、核への同意として読むのが最も筋が通ります。ただし条件の記録が無く、内容確認(マージ)も成立していません。弁護の立場から言えるのは、**核への同意を、新しい審議の出発点として尊重する価値がある**ところまでです。オーナーが核に同意した事実を、新案の採用の根拠に数えることはできません(R-5)。

## R-1 位置づけ

### 結論

1. 確率的な分類器の助言は、**どの保証の層にも数えない材料(人へ戻す契機の候補)** として位置づける。検出の層(附属書H H.4)には数えない
2. 次の 2 つを、製品を名指さない一般の規範として書く
   - 助言を、ゲートの判定・承認・遮断・完了・ラベルの遷移とラベルの付与・「該当しない」の結論に数えてはならない
   - **助言が出ないことを、確認の省略・リスク区分の引き下げ・人へ戻さない判断の根拠に数えてはならない**。記録にも書いてはならない
3. 「引き上げ方向」の語は**捨てる**。「人へ戻す側に限る」と書く。助言が人へ戻す契機を示しても、戻すかどうかは 5.5.1 の表で決まる。助言を理由に、表の「戻さない」行の選択まで戻させてはならない

### 理由

- **非対称の効果は旧案の最大の利点で、今も成り立つ**。外部 §1.3 で Jev は注入で答えが動くと自ら認め、偽の「事前承認」メモで遮断の確率が 0.76 から 0.48 へ下がった報告がある。助言が緩める向きに効かない設計なら、注入の被害は最悪でも「助言が無い」状態に留まる(外部 考察A)。緩める向きに使えば、注入はそのまま統制の解除になる。Meta DRS(外部 §2.1)は緩める向きに使っており、本標準はその逆を選ぶ理由を持つ
- **不作為の誤りへの手当ては、旧案が既に書いていた**。旧 ADR 決定1「注意が出ないことを、問題が無いことの根拠にしません」。現行の 5.8.6 要求事項9「拒否が 0 件であることを、想定外の操作が無かったことの根拠として記録してはならない」と同じ型で、旧案が先行していた。ただし旧案の書き方は「問題が無い」の 1 語で、確認の省略・区分の引き下げ・人へ戻さない判断の 3 つを名指していない。Goddard 2012 と FDA 2026(外部 §2.2・§4)の不作為の誤りは、まさに「促されなかったから確認しない」経路なので、3 つを名指す形に強める
- **検出の層に数えない理由**: H.4 の 5 条件は「AI の推定による判定(AI レビュー、受入基準の充足判定)」に掛かる(内部 §2.1)。分類器は成果物を確認しておらず、発話の意図を推定するだけです。検出の層に数えると、次の 2 つが起きる
  - H.4 の条件1(欠陥注入による検出率の測定と開示)を満たさないまま「層」として扱われる
  - 保証の主張に「分類器が見ている」が入り、不作為の誤りを制度として招く
  - 「どの層でもない」と明記するほうが、主張を小さく保てる
- **5.7.4 への類推は撤回し、根拠を置き直す**。旧 ADR は 5.7.4 要求事項2(自動的な判定は人への提示に限る)の「適用」と自己規定した。5.7.4 はゲート承認の記述の質の規定で、発話の分類を扱っていない(内部 §2.1)。類推は方向として正しいが、規範の根拠にはならない。根拠は、G-5 の設計方針(`gate-criteria.md`「注意を向ける材料として提示し、合否には用いません」)、ADR-0084 の却下表(非決定的な結果を合否に使わない)、5.5(確定は席の責任者)に置く。外部の根拠は FDA 基準4、EU AI Act 14 条 4 項 (d)、GitHub Copilot の既定(外部 §4)
- **「引き上げ」の語は弁護できない**。5.4.5 のレベルの引き上げと 5.5.7 の運用形態の引き上げは、統制を緩める向きです(内部 §2.3)。旧案の「引き上げ方向」は厳しくする向きで、逆の意味になる。規格の読み手が逆に読みうる語は、信頼性の欠陥です
- **5.5.1 との緊張は、旧案の設計の中で解ける**。旧案のフックは「注意が出たとき、エージェントは発話が該当するかを自分で確かめる」とし、戻すかどうかを分類器に決めさせていない。したがって 5.5.1 の表(承認済みの受入基準の内側の選択は戻さない)が優先する、と書けば足りる。旧案の delegated_judgment の誤警報(閾値 0.3、適合率 32%)は、この表の「戻さない」行に当たる選択を戻させる力として働く。この誤警報は表で打ち消すもので、規範を変える理由ではない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 検出の層に数え、H.4 の 5 条件を掛ける | 成果物の確認ではないものを層に数えると、保証の主張が実態より大きくなる。不作為の誤りを招く |
| 引き下げ・省略の向きにも使う(Meta DRS 型) | 注入で統制が外れる。外部に開発プロセスでの実証が無い(外部 §2.1・§2.4) |
| 助言の利用を義務にする | 自動化バイアスと警告疲れの副作用がある。使わない判断を確保する EU AI Act 14 条 4 項 (d) と逆になる(外部「課すべきでないこと」3) |
| 「引き上げ方向」の語を定義し直して残す | 5.4.5・5.5.7 の既存の語と同じ文字列で逆の意味を持たせることになる。定義で解消しても、読み違いの余地が残る |

### 反論されうる点

- 「どの層でもない材料」は、規範の外にあるのだから、規範を書く必要は無い、という反論。弁護の答え: 規範が無いと、利用者が判定記録に「分類器の注意なし」と書く経路を止められない。書かないのではなく、**数えないと書く**ことが要る
- 人へ戻す側に限っても、誤警報の量が 5.7.5(摩擦の総量)を壊す、という反論。これは正しい。R-4 の観測で受ける。位置づけの問題ではなく、運用の問題として扱う
- 宛先がエージェントの文脈なら、自動化バイアスはエージェントに起きる(助言が無いから確認しない)。人の研究を引いて足りるのか、という反論。弁護の答え: 結論2 の規範は宛先を問わない。エージェントの不作為も「人へ戻さない判断の根拠に数えない」で塞がる。ただし、エージェントに助言の不在を根拠にさせない手段(指示資産で足りるか)は、実証が無い。根拠水準マークの対象にする

## R-2 外部送信

### 結論

1. 発話ごとの自動送信は、**取り消せない操作の上流の操作**として扱う(5.5.1、ADR-0078 決定2)。有効化(送信の開始)と、送信先・送る範囲の変更が、取り消せない操作に当たる。担い手(AI)が行ってはならず、人へ戻す
2. **常設の事前決裁で足りる**。送信のたびの承認は求めない。ただし、事前決裁には次の欄を持たせる
   - 送信先(宛先の同一性。版を含む)
   - 送る範囲と送らない範囲(データの種別、秘匿情報の扱い)
   - 学習の利用の有無と保持の条件(3.12.8 要求事項3)
   - 期限と見直しの契機(送信先の規約・DPA・版の変更)
   - 取り消しの手順
3. 決める席は「オーナー」ではなく、**取り消せない操作の確定の席**(5.5.5)とする。情報セキュリティの合意を要する組織では、その合意を記録に併記する(フェーズ5 `ai-environment.md:91` の参考)
4. 旧案の経路(利用者の端末から個人の API キーで直接つなぐ)は、**3.12.2 に反するので変える**。接続は AI運用担当者が用意した経路を通す。送出の検査(秘匿情報の検出)は経路の上に置く(3.12.8 要求事項2)。クライアント側の正規表現は、経路の検査に重ねる補助に留める
5. **5.8.6 要求事項1・3(許可していない外部への通信の拒否、ネットワークの既定拒否)が準拠テンプレートへ降りる前に、外部送信をする部品をテンプレートへ入れない**。旧案の順序は誤りだった
6. 有効化した案件では、提供者を 3.12.11 の依存先の一覧(構成の `dependencies`)へ載せる。層1 項目4「AI の利用の拡大」には数えない(括弧の範囲は自律レベルの引き上げと委任の範囲の登録に限られる)。統制は 3.11.6・3.12.3・本節の事前決裁で受ける

### 理由

- **旧案の「既定無効、3 記録がそろうまで送信しない」は、ADR-0078 の後でも正しい形をしている**。ADR-0078 で、後段が人でない経路では上流の操作が取り消せない操作になった。旧案はまさに上流(有効化)を人の記録に縛っていた。ADR-0053 決定4(既定を拒否に置き、許可する発行先の列挙を案件へ渡す)とも一致する。外部「課せること」3・4 も同じ形を勧めている
- **常設の事前決裁を弁護する理由**: 送信のたびに人へ戻す設計は、発話ごとに承認を求めることになる。5.7.5 の摩擦の総量の規定に照らすと、承認は確認済みの印へ縮退する(5.8.6 の前文が述べる形骸化)。類例として、5.5.4 の行「本番環境への反映の承認」が、登録時の記名による事前承認を正規の経路にしている(`human-ai-boundary.md:354`)。取り消せない操作を、範囲を固定した事前承認で覆う形は、本標準に既にある。ただし類例は配備の承認で、第三者への送信ではない。この適用は新しい当てはめになる
- **「オーナー」は弁護できない**。本標準の席の名ではなく、採用者の組織で誰に当たるかが決まらない。旧案の他の 2 記録(AI維持管理者=外部ツールの採否、AI運用担当者=モデルの適合性)は 5.5.6 の表と一致していた(内部 §2.1)。外部送信だけが席に結びついていなかった
- **3.12.2 は旧案の時点から存在し、旧案は引いていなかった**(内部 §2.4)。これは後から変わった規定ではなく、旧案の見落としです。「接続はすべて AI運用担当者が用意した経路を通ります」「個人で契約した経路は正規の経路に当たらない」。端末の環境変数の API キーは、この規定に正面から当たる。経路の上に置かない検査は、利用者の端末の設定で外せる
- **「実装で担保」は、旧案のままでは成り立っていなかった**。コードの `unapproved()` は、3 記録の文字列が空でないか・仮の値でないかだけを見る(内部 §1.2)。任意の文字列で送信が始まる。旧 ADR は「3 つがそろうまで、フックは送信しません。実装で担保します」と書いたが、担保していたのは欄の記入だけで、決裁の実在と記名者ではない。これは旧案の欠陥として認める
- **5.8.6 の前に部品を入れない理由**: 旧案の許可リストはフックのコード内の自己規制です。外部の事例(CVE-2026-47751、postmark-mcp、s1ngularity。外部 §3.5)は、リポジトリ内の設定や拡張の更新で送信先が変わる形でした。ネットワークの既定拒否が強制層に無い現状(IMPL-0200 undelivered)では、許可リストを書き換える PR が、送信先の変更をそのまま実現する。旧評価メモ自身が「強制層にネットワークの既定拒否が無い」を範囲外の不整合 (4) に挙げていた。旧案は欠陥を自覚しつつ、先に部品を入れる順序を選んだ。この順序は弁護しない
- **層1 項目4 に数えない理由**: 項目4 の必須行は、括弧で「自律レベルの引き上げ、委任の範囲の登録」に限っている(`deliverable-templates.md:971` も同じ)。人へ戻す側にだけ働く助言は、AI の自律の範囲を広げない。項目4 へ類推で足すと、必須行の範囲が解釈で広がる。必須行は、受容者が空欄なら層1 を無効にする強い錠です。この錠の範囲を類推で広げるほうが、信頼性を損なう。外部送信の危害は、取り消せない操作として結論1〜3 で受ける

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 送信のたびに人の承認を求める | 承認が形骸化する(5.7.5、5.8.6 前文)。助言の遅延の要件(数百ミリ秒)と両立しない |
| 送信の主体はフックでエージェントではないので、5.5.1 の対象外とする | 内部 §2.4 が挙げる読み。採らない。5.5.1 の定義は「他の者の操作を介さずに効果を生じさせる操作」で、主体を担い手に限っていない。対象外とすると、第8章の「外部へ出た情報」の危害を受ける規定が無くなる |
| ZDR の契約があれば外部送信を許す | ZDR は製品・機能・組織ごとの範囲を持つ(外部 §3.4)。TypeSafe の DPA に ZDR の記述が無い |
| 5.8.6 の降下を待たずに、既定無効なら入れてよいとする | 既定無効は、有効化の後の送信先の改ざんを防がない。有効化した案件で、許可リストの PR による書き換えが強制層の外で効く |
| 分類器の有効化を層1 項目4 の「AI の利用の拡大」に数える | 必須行の範囲を類推で広げる。必要な統制は取り消せない操作の事前決裁で受けられる |

### 反論されうる点

- **常設の事前決裁は、ADR-0078 の「後段の門を理由に止めずに行ってはならない」に反する**、という反論。弁護の答え: 事前決裁は後段の門ではなく、上流の操作(有効化)そのものを人が行う形です。有効化は人へ戻され、人が自ら行う。ただし、有効化の後の各送信が「取り消せない操作を人へ戻さずに行う」ことに当たらないかは、定義の読みが割れる。新 ADR で、上流の操作を人が行ったことで以後の送信を覆う、と明示する必要がある。明示しないと、5.5.4 の「本番環境への反映の承認」と同じ扱いを類推に頼ることになる
- **層1 項目4 に数えないのは、新しい外部の AI を導入する決定を事業側の受容から外すことになる**、という反論。これは強い反論で、弁護は半分しか立たない。代わりに、事前決裁の席を 5.5.5 の確定の席に置き、3.12.11 の依存先の一覧で単一障害点として見える形にする。それでも不足なら、項目4 の括弧を改める別の審議が要る。類推で足すのではなく、改める
- 3.12.2 の経路を通すと、個人や小規模の採用者は事実上使えない、という反論。弁護の答え: それは 3.12.2 の帰結で、本件だけが例外を求める理由にはならない。使えない採用者は、使わないことで適合を失わない(R-1 の結論で利用を義務にしない)

## R-3 同梱と製品の名指し

### 結論

1. **標準の本文では製品を名指さない**。規範は性能と統制で書く(R-1・R-2・R-4 の各規範)。製品は例にも挙げない
2. **準拠テンプレートへの同梱は、現時点では見送る**。次の 3 つが満たされるまで、テンプレートの強制層(`.claude/settings.json` のフックの登録)へ入れない
   - 5.8.6 要求事項1・3 がテンプレートへ降りている(IMPL-0200 が delivered)
   - 接続を AI運用担当者の経路へ通す形が、テンプレートで表せる(3.12.2)
   - 記録の照合が、欄の記入ではなく判定記録の実在と記名者を確かめる
3. 将来同梱するときも、**分類器の接続部分は送信先を差し替えられる形にし、既定値に特定の製品を置かない**。製品の例を手引きに書くなら、時点(YYYY-MM-DD 時点)と「推奨ではない。同等の働きをするものを使ってよい」を併記する
4. 同梱するときは、ADR-0084 決定6(逆向きの追跡)と ADR-0085 決定5・6(契約検査)の扱いを先に決める。既定無効の任意の部品を `TEMPLATE_HOOKS` に入れると、使わない採用者が契約検査で落ちる。任意の部品は強制層の登録の外に置き、採用者が有効化するときに強制層の変更(`state:needs-platform`)として登録する経路を設ける

### 理由

- **同梱の利点は本物で、弁護に値する**。試験(12 件)と評価の道具(`evaluate.mjs`)と既定無効の錠を備えた参照実装を配れば、各組織が場当たりの実装を書くより、統制の抜けが少ない。外部の事故(外部 §3.5)の多くは、出所の確かでない拡張の導入から起きている
- **それでも今は同梱しない**。理由は、利点の前提が今は成り立たないことです
  - 参照実装の錠(許可リスト)は、強制層のネットワークの既定拒否が無いと効かない(R-2)
  - 参照実装は 3.12.2 に反する経路を前提にしている
  - 参照実装の記録の照合は、欄の記入しか見ない
  - 参照実装の G-4 照合は、ADR-0070 の後の記録の置き場と合わず、構造上常に「見つかりません」を出す(内部 §3)。つまり今の参照実装は、旧案の決定4(記録から導けることはコードで判定する)の原則を自ら破っている
  - 欠陥を持つ参照実装をテンプレートの名で配ると、採用者は「標準に適合した部品」と読む。参照実装が無い状態より信頼性が低い
- **製品の名指しは、旧 ADR 自身が決定5 で避けようとしていた**。「送信先を特定製品に固定しない。System One 互換 API として差し替え可能」。一方で、表題・本文・既定値で Jev を名指した。これは不徹底です。1.7(`overview.md:278`)、5.8.6(`human-ai-boundary.md:1061`「製品・拡張機能は指定しません。指定すると、提供条件が変わったときに規定が破綻する」)、ISO/IEC Directives Part 2 第31条・5.4・18.5.4・33.1(外部 §5)のいずれにも当たる。適した製品が 1 つしかない場合にも当たらない(互換の OSS がある。外部 §1.2)
- 「System One 互換 API」も、特定の提供者が定めた API の名です。差し替え可能性を、提供者の API 仕様に依存させない。接続部分の入出力(問いの型と確率)を、標準またはテンプレートの側で定義する
- **テンプレートが既に製品を前提にしている(Claude Code・graft)ことは、名指しを正当化しない**。Claude Code は実行環境そのもので、置き換えるとテンプレートの全体が変わる。graft は外部送信を目的にしない道具です(利用統計の送信の有無は未確認。内部 §2.7)。発話の本文を第三者へ送ることを目的とする部品とは、危害の性質が違う。むしろ graft の「`.mcp.json` に登録せず、使う人が local scope にだけ足す」先例(内部 §2.7)が、任意の部品を強制層の外に置く型として使える
- 製品側の事実(早期アクセス、DPA に ZDR が無い、米国のホストだけ、別名の移動で答えが変わる、廃止方針の記載が無い。外部 §1)は、規格の寿命より短い時間で変わる。旧案の版固定・許可リスト・人の較正は、この事実への正しい対応です。ただしそれは「この製品を使う場合」の運用要件で、テンプレートの既定値に製品を置く理由にはならない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 旧案のとおり、既定無効で同梱し、既定値を Jev にする | 本節の理由のとおり。欠陥のある参照実装を標準の名で配る。製品を名指す |

### 反論されうる点

- 製品を名指さないと、採用者が何を使えばよいか分からない、という反論。弁護の答え: 手引き(参考)で、時点つき・推奨ではない旨つきの例を示す余地は残す。規範の側には書かない

## R-4 評価と適合性

### 結論

1. 旧案の評価(合成発話 240 件、正解ラベルは Claude 3 者の合議)は、**採否の根拠に使わない**。**方法の参考として残す**。新 ADR では、旧評価の値を「旧案の時点の参考値。正解ラベルを人が確認していない」と明記して引くに留める
2. 旧案の Haiku の却下理由 (1)(本体も Claude で、確認する側と共通の原因を持つ)は、**撤回する**。3.5.4 帰結4(`roles-responsibilities.md:664`)に当たる。比較の結果を書くなら、性能の事実(確信度の分離が弱い。Haiku は 0.8 以上が 97.5% を占め、正解と不正解をほとんど分けなかった)だけを書く
3. 分類器のモデルの導入は、**3.12.3 の全要求事項**(1〜6 と 10。7〜9 は出荷に要る席の担い手のモデルに限るため、対象外と明記する)を通す。基準集合の正解ラベルは、案件の人が確認したものとする。基準集合の範囲は AI運用担当者が起案し、技術判断者が記名で承認する
4. 3.4.2(担い手の適合性確認)は掛けない。分類器は席の担い手ではない
5. 助言の有効性を観測し、記録する。観測の項目は次の 4 つ
   - 人へ戻す契機を示した件数
   - そのうち、人が妥当と判断した件数(誤警報の割合が導ける)
   - 人の判断を変えた件数
   - 事後に「示すべきだった」と人が判断した見逃しの件数
6. **閾値の固定値を標準で課さない**。閾値は案件の構成値とし、人が較正し、実績から自動で更新しない(3.12.12 要求事項2 と同じ型)。観測の結果から閾値を見直す契機と、見直しの記録だけを求める。根拠水準マーク(EV-0210 以降)で、観測の項目と見直しの条件が暫定であることを開示する

### 理由

- **旧評価の方法には、弁護すべき誠実さがある**。閾値を奇数番で決めて偶数番で確かめた。方式と質問文の言語を全件で選んだため偶数番も独立でない、と自ら開示した。正解ラベルを人が確認していない、と太字で書いた。根拠水準を E1(間接)にした。帰結に「案件で使い始める前に、人の確認を含めて測り直す必要がある」と書いた。旧案は評価を採否の根拠に過大に使っていない
- それでも採否の根拠にはできない。正解ラベルを AI の合議で作った評価は、分類器が AI の合議と一致する度合いを測っている。人の判断と一致する度合いは測っていない。IMPL-0153(複数の AI の合議を独立した確認に数えない)は評価の正解ラベルに直接は当たらない(内部 §2.2)。しかし、Jev のベンチマークの参照解自体が OpenAI・Anthropic のモデルの出力である(外部 §1.1)。参照解が AI の出力である評価を重ねても、人との一致は測れない
- **Haiku の却下理由 (1) は撤回するが、比較の結論は性能の事実で立ちうる**。旧評価で Haiku は ECE 0.080(Jev 英語 0.051)、確信度 0.8 以上が 97.5% を占めた。確信度で絞って誤警報を抑える設計にとって、確信度が正解と不正解を分けないことは、系統によらない性能の欠点です。提供元の違いを根拠にしなくても、却下の結論は残りうる。ただし 240 件・AI の正解ラベルの上の比較で、結論の強さは E1 に留まる。理由 (2)(prompt 型フックは助言を差し込めない)と (3)(API キーが別に要る)は、実行環境の仕様に依存する事実で、時点を併記すれば使える
- **3.12.3 の全要求事項を通す理由**: 「承認されていないモデルを開発組織で用いてはなりません」(`roles-responsibilities.md:1504`)。分類器も開発組織が用いるモデルです。旧案の `modelAdoption` 1 欄は、要求事項10(範囲の起案と承認の分離。同一人物なら承認に数えない)を表せない(内部 §3)
- **観測の項目の弁護**: 旧 EV-0040 の差し替え条件((a) 注意の件数と妥当件数、(b) 見逃し件数)は、外部の Tricorder の「NOT USEFUL」(外部 §2.3)と同じ発想で、方向は正しかった。足りないのは「人の判断を変えた件数」です。助言が無くても人が同じ判断をしたなら、助言の価値は摩擦だけになる。これが 5.7.6 の主指標(誤りを人が捕捉した割合)へ、助言の寄与を結びつける
- **閾値を課さない理由**: Jev 自身が固定の閾値を示さず、用途しだいとしている(外部 §1.3)。開発プロセスでの適用評価は外部に見つからない(外部 §2.1)。実証の無い値を標準の定数にすると、根拠水準の原則(ADR-0026)に反する

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 旧評価を、案件の 3.12.3 の基準集合として流用する | 正解ラベルを人が確認していない。合成の発話で、案件の発話の分布を代表しない |
| 系統の異なる分類器であることを、助言の価値の根拠に書く | 3.5.4 帰結4 と IMPL-0158 に反する。系統をまたいでも誤りが強く相関する測定がある(ADR-0075 決定12) |
| 閾値の初期値を標準の定数(3.12.12 の登録簿)に載せる | 製品と版と用途に依存する値で、標準の寿命の中で変わる。実証も無い |
| 誤警報率の上限(例: 10%)を課す | 外部の「10% を超えると無視される」は原典を辿れない(外部 §2.3、[未確認]) |
| 観測を求めない | 警告疲れで、有効化しても形骸化するか、既定無効のまま放置される(外部 考察A) |

### 反論されうる点

- 分類器は席の担い手ではないから、3.12.3 も過剰だ、という反論。弁護の答え: 3.12.3 は担い手に限らず、開発組織が用いるモデルに掛かる。発話を第三者のモデルへ送る部品を、モデルの承認の外に置く理由は無い
- 観測の 4 項目の記録は、それ自体が摩擦になる、という反論。妥当な反論です。記録の粒度(助言ごとか、期間ごとの集計か)は案件に委ね、項目だけを課す形にする。これも暫定として根拠水準マークで開示する
- 「人の判断を変えた件数」は観測できない(人は助言が無かった場合の判断を知らない)、という反論。弁護の答え: 厳密には反実仮想で観測できない。代わりに「助言を受けて人へ戻した結果、確定の内容が変わった件数」を数える。測れるものに置き換えたことを、根拠水準マークに書く

## R-5 記録

### 結論

1. **新しい ADR を起こす**。番号は起票の時点の main の最大の次(2026-11-04 時点では ADR-0103)。EV・IMPL も同様(EV-0210・IMPL-0398 以降)。起票の直前に再確認する
2. **標準の本文に、製品を名指さない規範を置く**。置く規範は次のとおり
   - R-1 の結論2(助言を数えない、不在を根拠にしない)
   - R-2 の結論1〜4(外部送信の有効化を上流の操作とする、事前決裁の欄、席、経路)
   - R-4 の結論3・5・6(3.12.3 の適用、観測の項目、閾値を課さない)
   - 置き場の候補は、5.7 の近く(助言と判定の区別)と 5.5.1(上流の操作の例)と 3.12(モデルの適用)。最終の置き場は起草の担当が既存の条項と突合して決める
   - 実行主体の挙動を制約するので、各規範に実装マークを付ける。テンプレートに部品を入れないうちは `state=undelivered` で表示し続ける
3. 部品(旧 PR #50・#51)の同梱は、R-3 の 3 つの前提がそろうまで見送る、と ADR に書く。**却下ではなく、前提つきの見送り**として書く
4. 旧 ADR-0054 は採用されていない(マージされずに閉じた)。新 ADR では、旧案を「置き換え」(supersede)の対象として扱わない。**未成立の提案**として、所在(PR #283、pit-in-template #50・#51)を引く
5. オーナーの 2026-09-23「条件付きで採用」は、次の事実として記録する
   - 2026-09-23 のセッションで、オーナーが「条件付きで採用」を選んだ(一次記録は PR #283 本文だけ)
   - 条件の中身の記録は無い
   - PR は「マージをもって内容の確認とする」としていたが、マージされなかった。内容の確認は成立していない
   - 本 ADR は、この選択を採否の根拠に数えない。旧案の核を、会議体で独立に再審議した
   - 再審議の結果、核の (a)〜(f) は維持し、実装と当てはめの点(R-1〜R-4 の「変えるべき」)は変えた
6. **オーナーにしか決められないこと**を、ADR に分けて書く
   - 本 ADR の採用そのもの(本標準の保守者としての決定)
   - 前提がそろった後に、部品をテンプレートへ同梱するかどうか(テンプレートの強制層の変更。保守者の決定)
   - 旧案の「条件付きで採用」を、本 ADR の決定に置き換えることへの同意。旧案の選択は記録として残し、書き換えない
   - 採用者の案件で分類器を有効化するかどうかは、オーナーではなく**採用者の席**(取り消せない操作の確定の席・AI維持管理者・AI運用担当者・技術判断者)が決める。本標準とテンプレートは、その決定の欄と錠を用意するだけです

### 理由

- **新 ADR が要る理由**: 規範を本文へ置くのは、あとから変えにくい方針の決定です。旧 ADR は番号が衝突し(ADR-0054 は席、EV-0040 はその決定3・4)、本文の拠りどころの表は現行と合わない(5.5 の要約、Label Mailbox 原則3、フェーズ5 の位置づけ。内部 §3)。旧 ADR を番号だけ付け替えて取り込むと、現行と矛盾する拠りどころを公開記録に残す
- **規範を本文に置く理由**: 旧案は「新しい規定は要りません。既存の条項の適用です」と自己規定した。この自己規定は、弁護しきれない。助言の不在を確認の省略の根拠にしないこと、外部送信の有効化を上流の操作とすること、事前決裁の欄は、既存の条項の類推では一意に導けない(R-1・R-2)。類推に頼ると、採用者ごとに読みが割れる。規格として、明文で書くほうが信頼性が高い。また、規範は製品にも部品の同梱にも依らない。採用者が独自に分類器を入れる場合にも掛かる
- **部品の見送りを ADR に書く理由**: 「採らないと決めたこと」を明記する方針(CLAUDE.md のコアポリシー)。前提を列挙しておけば、前提がそろったときに、改めて会議体を開く入口になる
- **オーナーの選択の扱い**: 弁護の立場からは、オーナーが旧案の核に同意した可能性は高いと考える。条件として読めるのは決定1(助言に限る)と決定2(既定無効、記録がそろうまで送らない)で、どちらも本意見書が維持する核に含まれる。ただし、それは推測です。推測を決定の根拠にしない。事実(選択・条件の記録の不在・内容確認の不成立)だけを書き、再審議で独立に同じ核へ至ったことを示す。これが、オーナーの選択を最も損なわない書き方です
- **最後に決めるのはオーナーである**: 本プロジェクトの ADR の採用者は保守者で、会議体は勧告します。会議体の結論を、オーナーの採否の代わりにしない。一方、採用者の案件での有効化は、案件の席の決定です。旧案の「オーナーが外部送信を決裁する」は、本プロジェクトのオーナーと採用者の席を混同させる書き方でした

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 旧 ADR を番号を付け替えて、そのまま取り込む | 拠りどころの表が現行と合わない。「引き上げ」の語、Haiku の却下理由 (1)、3.12.2 の欠落を公開記録に残す |
| テンプレートの部品の ADR だけを起こし、本文には規範を置かない | 部品を見送るので、ADR の対象が無くなる。採用者が独自に入れる分類器に規範が掛からない |
| 旧案の「条件付きで採用」を、新 ADR の採用の根拠として引く | 条件の記録が無く、内容確認が成立していない |

### 反論されうる点

- **本文へ規範を置くと、現時点で使う採用者がいない分類器のために条項を増やすことになる**、という反論。弁護の答え: 採用者がいないことは条項を置かない理由にならない。外部ではすでに、開発の拡張へ確率的な判定や助言を差し込む形が広がっている(Copilot のコードレビュー、DRS-OSS。外部 §2.1)。規範が無いまま広がると、Copilot の例のように、助言が設定 1 つで承認に数えられる状態へ移る。ただし、本文のどこに置くか、何条に分けるかは、既存の 5.7.4・G-5 方針との重複を避けて起草で詰める
- 「未成立の提案」として引くと、オーナーの選択を軽く扱うことになる、という反論。弁護の答え: 選択の事実は残し、書き換えない。軽く扱うのではなく、根拠に使わない。この区別は、採用済み ADR の本文を書き換えない規約と同じ考え方です
- 規範の多くは暫定(根拠水準 E1 以下)で、本文に置くには早い、という反論。弁護の答え: 暫定の規範を本文に置き、根拠水準マークで開示する運用は ADR-0026 が定めた形です。暫定であることは、置かない理由にならない
