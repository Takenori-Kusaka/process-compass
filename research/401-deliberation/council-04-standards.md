## 2. 横断の論点: 規定をどこへ書くか

議題の5論点に共通する問いは、「この話の規範は、確率的な分類器という**製品の種類に固有**か、それとも**AI の推定を作業の流れへ差し込む部品一般**に掛かるか」です。本委員の見立ては後者です。

- 採用者の組織は、本標準の準拠テンプレートが同梱するかどうかに関係なく、発話の意図を推定するフック・プラグイン・常駐の拡張を自ら足しうる(2026-11-04 時点で、Claude Code のフック、MCP サーバー、第三者のプラグインとして普通に流通している。外部 3.5)
- 附属書H の「AI が確認した」の3種(決定論的な検査、AI の推定による判定、人の判定)は、**成果物を確かめる行為**の分類である。作業の段階や発話の意図を推定して注意を差し込む部品は、どの行にも入らない(内部 2.1 の推測を、本委員も本文を読んで同じく読む)。分類の穴は、旧案の採否と独立に存在する
- したがって、**本文に置くのは製品を名指さない一般の規定**、**テンプレート・任意部品に置くのは実装**、という分け方が 1.7(製品名に依存しない)・5.8.6 の末尾(拒否の手段の製品を指定しない)と整合する。旧案は逆で、規範をテンプレートの ADR に置き、本文には何も置かず、製品を既定値として同梱した

## 3. R-1 位置づけ

### 結論

1. 確率的な分類器の助言は、**検出の層ではなく、どの層でもない「AI の推定による注意の提示」**として位置づける。附属書H の3種の表に4つ目の種別として明記し、扱いを「判定にも、検出の層にも、独立した確認にも数えない」とする
2. 「数えない」ものを列挙で書かない。**提示の出力を、判定・承認・遮断・完了・ラベルの付与と遷移・リスク区分の確定・構成の値・保証の開示の、どの入力にもしてはならない**、と入力の側から一文で禁じる。提示先は人またはエージェントの文脈に限る
3. **提示が出ないことを、確認の省略・リスク区分の引き下げ・人へ戻すことの省略・ゲートの通過の根拠として記録してはならない**。5.8.6 要求事項9(拒否が0件であることを想定外の操作が無かった根拠にしない)と同型の禁止として書く。あわせて、**注意が無いときに「問題なし」「該当なし」を表示しない**ことを部品の要求にする(不在を肯定の信号に変える経路を表示の段で塞ぐ)
4. **提示は 5.5.1 の「人へ戻す場合」を増やさない**。人へ戻すかは 5.5.1 の表で決まる。提示は、表のどの行に当たるかを担い手と人が見直す材料にとどまる
5. 「引き上げ」の語は使わない。「人へ戻す側に限る」または「厳しくする向きに限る」と書く

### 理由

- **(1) 検出の層に入れない理由**: 検出の層は「欠陥や規定に反する状態を見つけるために置く確認」で、働きを欠陥注入による検出率で示す(附属書H の定義と条件1)。発話の分類は成果物の欠陥を見つけない。検出率という尺度が定義できないものを検出の層に入れると、条件1 は形式的に「未測定」と開示され続け、「検出の層がある」という表示だけが残る。これは附属書H が「数えてはならない」とする「検出率が未測定の層を、検出能力を確かめた層として示すこと」に近い形骸を生む
- **(1) 「どの層でもない」で放置しない理由**: 分類が書かれていないと、採用者は最も近い既存の行(AI の推定による判定=検出の層)へ類推で入れる。旧案自身が、ゲート承認の記述の質の規定(5.7.4 要求事項2)を類推で引いた(内部 2.1)。類推に頼る規定は、読み手によって位置づけが割れる。適合の判定がばらつく規定は信頼性を欠く
- **(2) 入力の側で禁じる理由**: 「判定・承認・遮断・完了・ラベルの遷移に数えない」という出力の使い道の列挙は、列挙に無い使い道(構成の値の自動更新、保証の開示への記載、リスク区分の推定)を残す。旧案の列挙は G-5 と `/process-init` を個別に除いていたが、それ自体が列挙の漏れやすさを示している。入力の側から「どの判定・記録の入力にもしない」と書けば、検査(機械)も「提示のログを読む検査・集約が無いこと」で確かめられる
- **(3) 不在の禁止を本文に置く理由**: 自動化バイアスには、促されなかったので行動しない不作為の誤りがある(外部 2.2、Goddard ほか 2012)。注入で注意の確率を下げられる(外部 1.3。製品の自己申告と単発の試験)。人へ戻す側に限る非対称の設計は、作為の誤り(誤った助言で緩む)を塞ぐが、不作為の誤りは塞がない(外部 考察A)。本標準はすでに、拒否の0件(5.8.6 要求事項9)について同型の禁止を持つ。並べて置くことで語彙と構造が揃う
- **(4) 人へ戻す場合を増やさない理由**: 5.5.1 は「承認済みの受入基準とスコープの内側にある選択は、選択のたびに人へ戻さない」と明記している(`human-ai-boundary.md:342`)。旧案の注意(とくに丸投げの検出)は、戻さなくてよい選択まで戻させる方向に働く(内部 2.1。誤警報の多くがその型)。提示を人へ戻す契機として認めると、5.5.1 の表と並ぶ第2の基準を AI の推定が作ることになり、5.7.5(摩擦の総量を管理する)にも反する。人へ戻す側に限ることは、それだけでは安全側ではない。過剰な差し戻しは警告疲れを経て提示全体の無視と無効化に至る(外部 2.3)
- **(5) 語の理由**: 本標準で「引き上げ」は 5.4.5(自律レベルの引き上げ)と 5.5.7(運用形態の引き上げ)で**統制を緩める向き**を指し、技術判断者の申請と判定を要する(内部 2.3)。一方で第4章では区分の下限の引き上げ(厳しくする向き)にも使われ、向きが一定でない。向きの一定しない語を、向きそのものが要点の規定に使うと、規定の要点が語で反転して読まれうる
- **既存の枠組みとの整合**: EU AI Act 第14条(人の監督)の趣旨(自動化バイアスの自覚、出力を使わない・無視・上書きできること)と、NIST AI RMF GOVERN 3.2(人と AI の構成における役割の定義と区別)・MAP 3.5(人の監督のプロセスの定義と文書化)に照らして、(2)(3) は外れていない。いずれも開発プロセス内の助言用分類器を直接の対象にしてはいない(第14条は高リスク AI システムが対象。外部 3.2 の考察)。**整合の確認であって、根拠ではない**

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 検出の層に数え、附属書H の5条件を掛ける | 尺度(欠陥注入による検出率)が定義できない。条件1 が常に「未測定」となり、検出の層の表示だけが残る |
| 本文に何も書かず、テンプレート側の ADR だけで「助言に限る」と書く(旧案の形) | 分類の穴は採用者が自ら足す部品にも掛かる。テンプレートの ADR は採用者の組織を拘束しない。規範が届かない |
| 「判定・承認・遮断・完了・ラベルの遷移に数えない」を列挙で書く | 列挙に無い使い道が残る。機械で確かめる手がかりにならない |
| 人へ戻す側の助言を、5.5.1 の人へ戻す場合の追加の契機として認める | 5.5.1 の「選択のたびに人へ戻さない」と衝突し、5.7.5 の摩擦の総量の管理に反する |
| 提示の確信度に応じて表示を変える(高いと強調) | 確信度の較正が独立に測られていない(外部 1.1・1.3)。強調は「主として依存」を誘う。確信度を示すこと自体は禁じないが、規定で求めない |

### 反論されうる点

- 「AI の推定による判定」の行を広く読めば、発話の分類も入る、という反論。→ 行の例(AI レビュー、受入基準の充足判定)はどちらも成果物を対象にする。広く読めば入るかもしれない、という状態そのものが割れの原因で、明記の理由になる
- 4つ目の種別を足すと、附属書H の表が成果物の確認の分類でなくなる、という反論。→ 表の見出しは「AI が確認した」の3種。4つ目を同じ表に入れると見出しと合わない。**同じ表に入れず、表の直後に「AI の推定による注意の提示は、本表のどの種別にも当たらない」と置く書き方**でもよい。起草者に委ねる。要点は、検出の層の外にあると本文が言うこと
- 本文に規定を置くのは、存在しない部品のための規定で、時期尚早だ、という反論。→ 採用者が足す部品は、本標準が同梱するかに関係なく現れる。分類の穴は今ある。ただし実証が無いので、根拠水準のマーク(E0 または E1)で開示する
- 「問題なし」を表示しないことを要求にするのは、部品の UI の設計に踏み込みすぎる、という反論。→ 不作為の誤りを表示の段で塞ぐ手段はこれしか無い。表示の文言は指定せず、「不在を肯定の表示にしない」という性能で書く(Directives Part 2 の性能原則と同じ書き方。外部 5)

## 4. R-2 外部送信

### 結論

1. **送信を始める操作(有効化、送信先の追加・変更、送る範囲の拡大)は、5.5.1 の取り消せない操作(後段が人でない経路の上流の操作)に当たる**と読む。担い手(AI)は行わず、人へ戻す。個々の発話の送信は、5.5.1 の操作として1件ずつ人へ戻すものではない
2. ただし、それで足りるのは、**送信先が 3.12.2 の正規の経路であり、3.12.8 の要求事項1〜3 を満たす場合に限る**。旧案の形(端末の環境変数の API キーで、提供者のホスト API へ直接接続し、秘匿情報の検出を端末側の正規表現で行う)は、決裁の記録がそろっても 3.12.2・3.12.8 を満たさない。**記録をそろえることで、経路の要件を満たしたことにはならない**
3. 「常設の事前決裁」を、本 Issue で新しい承認の型として作らない。送信先の承認は、既存の席の判断の組で表す
   - 接続経路の提供と、学習利用・保持期間の確認と記録: AI運用担当者(3.12.2、3.12.8 要求事項3)
   - モデルの適合性の記名承認: AI運用担当者(3.12.3、5.5.6)
   - 外部ツールの採否と、強制層(フック)の変更の承認: AI維持管理者(3.11.2、3.11.6 要求事項5、5.5.6)
   - 外部との契約(MCA・DPA)に関わる決定: 人(5.4.3 の不変条件3)。席の割り当ては採用者の D-0 による
4. **テンプレートの順序**: 5.8.6 の要求事項1〜3(許可していない外部への通信の実行時の拒否、強制層に置く拒否の範囲、ネットワークの既定の拒否)が準拠テンプレートへ降りる(IMPL-0200 が delivered になる)前に、外部送信を行う部品を準拠テンプレートへ入れない
5. テンプレ11 の項目4「AI の利用の拡大」の必須行へ、解釈で分類器の有効化を含めない。含めるべきだと会議体が決めるなら、行の括弧の中の列挙を改める変更として扱う

### 理由

- **(1) 有効化が上流の操作に当たる理由**: 5.5.1 の定義は「取り消せない効果を、他の者の操作を介さずに生じさせる操作」で、基準は取り消せない時間帯の存在(ADR-0053 決定1、ADR-0078 決定2)。第三者への送信は、送った時点で取り消せない(ADR-0053 決定3、第8章「設計で下げられない危害」の「外部へ出た情報」)。有効化の後は、送信が人の操作を介さずに起きる。「後段が人でない経路では、上流の操作が取り消せない操作に当たる」(`human-ai-boundary.md:353`)の文に、そのまま当たる
- **(1) 個々の送信を1件ずつ戻さない理由**: 個々の発話の送信を取り消せない操作として人へ戻すと読むと、本体のエージェントへの発話の送信(Claude Code が提供者へ送る全発話)も同じく1件ずつ戻すことになり、本標準の全体が成り立たない。本標準は、エージェント本体への送信を 3.12.2 の正規の経路と 3.12.8 の統制の下に置くことで扱っている。分類器への送信も、**同じ構造の下に置かれる限りで**同じに扱うのが、語彙と構造の整合である。逆に言えば、同じ構造の下に置かれない送信を、本体と同じに扱う根拠は無い
- **(2) 旧案が 3.12.2・3.12.8 を満たさない理由**
  - 3.12.2: 「開発組織が AI 実行基盤へ直接接続することを認めません。接続はすべて AI運用担当者が用意した経路を通ります」。分類器はモデルを用いる推論のサービスで、AI 実行基盤に当たると読むのが自然(内部 2.4 の推測に本委員も同意)。当たらないと読む余地を残すなら、本文で明記すべき(下の「反論」)
  - 3.12.8 要求事項2: 「機密情報の送出を検査する仕組みを、接続経路の上に置く」。端末のフックの中の正規表現は、経路の上ではない。フックは版管理下のファイルで、PR で書き換えられる(外部 3.5 の CVE-2026-47751 は、PR のブランチから設定を読む形の実例)
  - 3.12.8 要求事項3: 学習利用と保持期間の確認と記録。提供者の DPA には保持の固定期間も ZDR の記述も無い(外部 1.4。2026-11-04 時点)。記録はできるが、記録した内容が「保持期間の定めなし」になる。受け入れるかは採用者の判断で、本標準は判断の結論を定めない
  - 旧案の3記録の照合は、文字列が空でないかと仮値でないかだけを見る(内部 1.2)。記録の実在も記名者も見ない。**承認の記録を文字列の有無で代替する形は、本標準が承認について一貫して退けてきた形**である(5.7.4 要求事項1 の趣旨、附属書H の条件5「通過の語だけの記録」を数えない扱い)
- **(3) 新しい承認の型を作らない理由**: 本標準で登録時の事前承認が認められているのは、5.5.4 の行「本番環境への反映の承認(登録時の記名による事前承認)」だけである。外部送信のための常設の事前決裁を足すと、事前承認の型が2つになり、それぞれの失効の条件(送信先の変更、版の変更、送る範囲の変更)を別に定める必要が生じる。既存の席の判断(3.12.2・3.12.3・3.12.8・3.11.6)は、それぞれ失効の契機を持っている(3.12.3 は版の変更で回帰評価、3.11.6 は追加と変更で承認)。組み合わせで足りるものを新設しない。これは変更量の理由ではなく、**同じ対象に2つの承認の型があると、どちらの失効で止まるかが読み手で割れる**ためである
- **(4) 順序の理由**: 5.8.6 要求事項2 は「指示ファイルにだけ書いた範囲は、拒否できたものとして扱わない」。IMPL-0200 が未達の準拠テンプレートでは、外部への通信は既定で許されている。そこへ外部送信の部品を入れると、許可リストはフックのコードの中の自己規制だけになる。準拠テンプレートは「本標準に従うとこうなる」の見本であり、見本の中に 5.8.6 を満たさない外部送信の経路が、本標準の部品として入ることになる。既定無効でも、経路のコードは見本の一部として配られる
  - 5.8.6 が降りた後は、外部送信先の追加は「遮断の解除」(3.5.5 の統制の弱化の性質)に当たる(内部 2.5)。降りる前に入れると、弱化の手続を経ないまま宛先が見本に入る。**順序を逆にすると、統制の弱化の手続が掛かるべき変更が、手続の無い時期に入る**
- **(5) 項目4 を解釈で広げない理由**: 項目4 の必須行は「AI の利用の拡大(自律レベルの引き上げ、委任の範囲の登録)」と括弧で範囲を限る(`deliverable-templates.md:1558`)。この行は構成の錠(IMPL-0098)に結びつく。解釈で範囲を広げると、錠の機械の判定と文書の範囲が食い違う。新しいモデルの導入は 3.12.3 が AI運用担当者の記名承認で扱っており、すでに統制の席がある
- **既存の枠組みとの整合**: NIST AI RMF の GOVERN 6.1(第三者の AI リスクの方針)・MAP 4.1/4.2(第三者の構成要素のリスクと内部統制の文書化)・MANAGE 3.1/3.2(第三者資源と事前学習済みモデルの監視)と、本標準の 3.12.2・3.12.3・3.12.8・3.12.11 の組は、同じ方向を向いている。IEEE 3119-2025 が調達の手順を規格として持つこと(要旨のみ確認)は、外部の AI サービスの採用を「道具の追加」ではなく「調達」として扱う作法があることを示す。3.12.11 の依存先の一覧(外部の道具とデータを含む)へ載せることは、この作法と整合する
- **法令を要求事項にしない**: 個人情報保護法の第三者提供・委託の整理(外部 3.1)は、採用者の法務の判断である。Directives Part 2 は文書に法令上の要求を含めない作法を持つ(外部の担当の引用で第4条)。本標準は ADR-0053 決定4 で「何を組織外とするかを定義しない」と決めている。本論点でも、法令の当てはめを要求事項にしない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 有効化を取り消せない操作に数えない(送信の主体がエージェントでなくフックだから、5.5.1 の対象外と読む) | 5.5.1 の定義は操作の効果で決まり、主体で決まらない。主体で除外すると、「フックに送らせる」ことで取り消せない操作の統制を外せる |
| 個々の送信を取り消せない操作として1件ずつ人へ戻す | 本体のエージェントへの送信と扱いが矛盾する。発話のたびに確認を求めると、5.7.5 の摩擦の総量の規定に反し、確認が形骸化する |
| 外部送信のための常設の事前決裁を新しい承認の型として作り、決める席を事業決裁者に置く | 事前承認の型が2つになり、失効の契機が割れる。3.12.2・3.12.8 の経路の要件を、決裁の記名で代替する読みを生む |
| 3記録がそろえば端末から直接接続してよいとする(旧案) | 3.12.2 の直接接続の禁止と、3.12.8 要求事項2 の経路の上での検査に反する。記録の照合が文字列の有無だけで、記名者を見ない |
| ZDR の契約があれば送信してよいとする | ZDR は製品・機能・組織ごとに適用の範囲と例外を持つ(外部 3.4)。二値の条件にすると例外が見えなくなる。当該の提供者の DPA に ZDR の記述も無い |
| 5.8.6 の未達と並行して、既定無効でテンプレートへ入れる | 見本に 5.8.6 を満たさない経路が入る。統制の弱化の手続を経ない宛先の追加になる |

### 反論されうる点

- 分類器は「AI 実行基盤」ではなく、ただの外部 API(外部ツール、3.11.6)だ、という反論。→ 外部ツールと読んでも、3.11.6 の要求事項1・3(一覧と権限を版管理下に置く)は IMPL-0228 が未達、2・4・5 は IMPL-0229 が未達である。どちらと読んでも、テンプレートには受け皿が無い。どちらと読むかは本文で明記すべきで、本委員は「推論を返す外部のサービスは、生成するかどうかに関係なく、3.12 の AI 実行基盤に含める」と書く案を推す。生成しないことを理由に 3.12 から外すと、分類・採点の API を経由する持ち出しの統制が外れるため
- 正規の経路を用意できる組織(ゲートウェイ・プロキシを持つ組織)は限られ、結論 (2) は小規模の採用者に分類器を使わせない、という反論。→ そのとおりである。ただし本標準はすでに、本体のエージェントについて同じ要件を課している。分類器だけ要件を緩めると、本体の経路の統制を迂回する経路が「助言」の名目で開く。小規模の採用者は、正規の経路の上にある既存のモデル(本体と同じ契約)で同じ働きを試せる(R-4 の (2))
- 3.12.8 要求事項2 の「接続経路の上」は、端末側のフックも経路の一部と読める、という反論。→ 経路の上に置く要件の趣旨は、開発組織の手元で外せない位置に置くことである。版管理下のフックは PR で外せる。本文が明記していないのは確かで、会議体で読みを一つに決め、ADR に残すべき点である

## 5. R-3 同梱と製品の名指し

### 結論

1. **準拠テンプレートへ同梱しない**(既定無効の同梱も採らない)
2. 本プロジェクトが分類器を使う部品を保守するなら、**準拠テンプレートの外の任意の部品**(別のリポジトリ、または採用者が各自のローカルの設定へ足す例)として置く。その部品を「準拠テンプレートの部品」「本標準の推奨」として表示しない。保守するかどうかは本プロジェクトのオーナーの判断(R-5)
3. 本文と準拠テンプレートでは製品を名指さない。任意の部品の説明で製品を名指す場合は、(a) 推奨ではないこと、(b) 同等に働くと示せる他の製品・方式を使ってよいこと、(c) 製品の事実の時点(YYYY-MM-DD 時点)、を併記する
4. 本論点の突合で見つかった別件として、**準拠テンプレートがすでに同梱している外部の道具(graft の利用統計の送信)を、R-2 と同じ観点で確かめる Issue を起こす**ことを提案する。本 Issue の結論の先例としては使わない

### 理由

- **準拠テンプレートの性質**: 準拠テンプレートは、本標準に従って開発するための見本で、正本の規則データを複製して持つ(CLAUDE.md の記述)。見本に入った部品は、採用者に「本標準はこれを想定している」と読まれる。既定無効でも、既定値の送信先が特定の提供者のホスト API であれば、事実上の推奨になる
- **製品の名指しの作法**: 本標準 1.7 は「特定の製品名…に依存する表現は用いない」(`overview.md:284`)。5.8.6 の末尾は「拒否の実装の手段(製品・拡張機能)は指定しません。指定すると、提供条件が変わったときに規定が破綻するため」。ISO/IEC Directives Part 2 は、商品名を可能な限り避け、適した製品が現に1つしか無い場合に限って本文に書けるとし、その場合も推奨ではなく同等品を使ってよい旨を付けるとする(外部の担当の引用で第31条。性能で書く原則は 5.4、単一製造者の指定を避けることは 18.5.4、第一者・第二者・第三者のいずれでも適合を評価できる書き方は 33.1)。確率的な分類は汎用の LLM、OSS の分類器、互換 API の OSS でも実現でき(外部 1.2)、「1つしか無い」に当たらない
- **製品の事実の寿命**: 早期アクセス、価格補助の可能性、廃止方針の不記載、別名による無告知の挙動の変化、DPA に ZDR の記述が無い、ホスト地域の選択が無い(外部 1.1〜1.4、2026-11-04 時点)。いずれも本標準の版の寿命より短い時間で変わりうる。見本に入れると、見本の改訂が製品の改訂に追随する義務を負う(ADR-0080 M-4 が開発手法の名指しを避けた理由の型と同じ。M-4 は手法についての決定で、製品に直接は当たらない。類推である)
- **強制層への登録の手続との整合**
  - ADR-0084 決定6(逆向きの追跡): テンプレートのフックは、降ろし先の登録簿か除外の一覧に載らなければ検査が落ちる。登録簿に載せるには、標準の側にそのフックが降ろす規定(IMPL マーク)が要る。R-1 の一般の規定は「提示を入力にしない」「不在を根拠にしない」で、**分類器のフックを置くことを求める規定ではない**。フックを置く規定が無いのに登録簿へ載せると、逆向きの追跡が「規定のない強制層の部品」を通すことになる。除外の一覧(library/infra/variant)のどれにも当たらない
  - ADR-0085 決定5・6(契約検査): テンプレートのフックの登録は契約で、`TEMPLATE_HOOKS` に入れれば取り込まない採用者が契約検査で落ち、入れなければ契約の外の強制層の部品が見本に入る。どちらも、強制層を「全採用者に共通の契約」として扱う ADR-0085 の構造と合わない
  - 任意の部品を各自のローカルの設定に置き、リポジトリの強制層に入れない形には、準拠テンプレート自身に先例がある(graft の MCP サーバーを `.mcp.json` に登録しない方針。内部 2.7)。理由は資源と波及で外部送信ではないが、「任意の部品は強制層の契約に入れない」という構造は同じ
- **攻撃の面**: 既定無効のコードも、有効化の値と記録の文字列を PR で書き換えれば動く(旧案の照合は文字列の有無だけ)。2025〜2026 の事件は、信頼された拡張の設定や版が PR・更新で変わる形だった(外部 3.5)。見本に入れれば、全採用者のリポジトリに同じ面が配られる
- **graft の件を別 Issue にする理由**: graft の SKILL は「匿名の利用統計を止めるなら telemetry disable」と書いており(内部 2.7)、準拠テンプレートは外部送信を伴いうる道具をすでに同梱している。送信先と内容は未確認。これを本 Issue の「先例があるから同梱してよい」の根拠に使うと、確かめていない状態を先例として固定することになる。逆に、本 Issue の結論(5.8.6 の前に外部送信の部品を入れない)と矛盾する状態がすでにある可能性があるので、突合の結果として別に扱う

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 既定無効で準拠テンプレートへ同梱する(旧案) | 見本に 5.8.6・3.12.2 を満たさない経路と、特定の提供者を既定値とする事実上の推奨が入る。逆向きの追跡と契約検査の構造と合わない |
| 製品名を外し、「System One 互換 API」として同梱する | 送信先の要件(R-2)と順序(5.8.6)の問題は残る。互換 API という括りも、特定の提供者の API 仕様への依存である |
| 本文に「確率的な分類器を使ってよい」と許容事項で書く | 許容事項として書く必要が無い。本標準は道具の使用を一般に禁じていない。許容と書くと、推奨と読まれる |
| 名指しの例を本文の注記に置く(Directives Part 2 が脚注の例を認める型) | 「1つしか無い」でも「特性を記述しにくい」でもない。性能(R-1 の要求)で書ける |

### 反論されうる点

- 本プロジェクトは ISO の文書ではなく、Directives Part 2 に従う義務は無い、という反論。→ そのとおりで、根拠の主柱は本標準自身の 1.7 と 5.8.6 の末尾である。Directives Part 2 は、本標準の作法が規格の世界の作法と同じ向きであることの確認に使う
- 準拠テンプレートはすでに Claude Code と GitHub を前提にしており、製品の中立は崩れている、という反論。→ 準拠テンプレートは実装で、本文はそれらを要求していない(本文は「GitHub の Environment など」と例として書く)。テンプレートが実行環境として1つの組み合わせを選ぶことと、任意の機能のために2つ目の提供者への依存を見本に足すことは、性質が違う。前者は見本を動かすのに要り、後者は要らない
- 外に置いた任意の部品は、誰も確かめないまま放置され、かえって危ない、という反論。→ 外に置く部品の保守は本プロジェクトのオーナーの判断に委ね、保守しないなら作らない。外に置くことは、品質を下げてよいことを意味しない。R-2 の要件(正規の経路、経路の上での検査、有効化を人が行う)と R-1 の要求(提示を入力にしない、不在を根拠にしない、不在を肯定で表示しない)は、外の部品にも本文の規定として掛かる

## 6. R-4 評価と適合性

### 結論

1. 旧案の評価(合成発話 240 件、正解ラベルは Claude 3 者の合議、人は未確認)を、**採否の根拠に使わない**。参考の記録として残すことはよい。根拠水準を書くなら E0 に近い E1 とし、「正解ラベルが AI の合議」と明記する
2. 旧 ADR 案の却下理由のうち、「本体のエージェントも Claude であり、確認する側と共通の原因を持つ」は**使えない**(3.5.4、ADR-0075 決定12)。この理由で退けた案(正規の経路の上にある既存のモデルで同じ推定を行う)を、比較の対象へ戻す
3. 分類器は席の担い手ではないので 3.4.2 の適合性確認は掛からない。**3.12.3(新しいモデルの導入)は掛かる**。基準集合の範囲の起案と承認の分離(要求事項10)を含む
4. **基準集合の正解ラベルを、AI の合議・多数決で作ったものだけにしてはならない**。正解の確定は人が行う。この扱いは 3.12.3 に書かれていない(内部 2.2)ので、本文で明記するかを会議体で決める。本委員は明記を推す
5. 助言の有効性を観測する。指標は、提示の件数、提示によって人の判断が変わった件数、提示が無視された件数、**提示が無かったのに後から人へ戻すべきだったと分かった件数(不在の見逃し)**。観測の結果を**検出率として保証の開示に載せない**
6. 閾値の固定値を本文で課さない。閾値は 3.12.12 の能力依存の定数の登録簿にも載せない。部品が持つ値は 1.7.7 の「既定値」または「例」の型で、置き換えの手続と記録を部品の側で持つ

### 理由

- **(1) 合議のラベルを根拠にしない理由**: 附属書H は、複数の AI の合議や多数決の一致を、検出の層にも独立した確認にも数えない(IMPL-0153)。評価の正解ラベルは確認ではないので直接は当たらないが、構造は同じである。AI の合議で作った正解に対する一致率は、「分類器が Claude の合議と一致する割合」で、正しさではない。提供者の自社ベンチマークも参照解が最先端モデルの出力だった(外部 1.1)。系統をまたいでも誤りは強く相関しうる(ADR-0075 決定12 が引く測定)。正解が AI に由来する評価で AI の採否を決めると、評価が採否を支える形に見えて、実際には何も支えていない
- **(2) 却下理由が使えない理由**: 3.5.4 は「系統の違いを、保証の開示・判定記録・対外の表示で、確認の強さの根拠として書いてはならない」(`roles-responsibilities.md:664`、IMPL-0158)。ADR は判定記録ではないが、本標準の決定の記録に「別系統なので共通の原因を持たない」と書けば、確認の強さの根拠に系統の違いを使う読みになる。2026-10-23 に入った規定で、旧案より後である
  - この却下理由が消えると、比較の構図が変わる。**正規の経路(3.12.2)の上にある既存のモデルで同じ推定を行う案は、R-2 の経路と順序の問題をほぼ持たない**(送信先が増えない)。旧案は残る理由(prompt 型のフックは助言を差し込めない、API キーが別に要る)も挙げたが、どちらも 2026-11-04 時点の実行基盤の仕様で、確かめ直しが要る。比較をやり直さずに外部の分類器を採る理由は無い
- **(3) 3.4.2 と 3.12.3 の掛かり方**: 3.4.2 の確認の単位は席の担い手の識別で、分類器は席に就かない。3.12.3 は「新しいモデルを開発組織へ導入する前」に掛かり、「承認されていないモデルを開発組織で用いてはなりません」とある。分類器の出力をエージェントの文脈へ差し込めば、開発組織の作業の流れで用いることになる
- **(4) 正解の確定を人に置く理由**: 3.12.3 の基準集合は、モデルの更新のたびの回帰評価の基準である。正解を AI が作ると、更新後のモデルとの一致を AI の正解で測ることになり、回帰の検出が AI の誤りと相関する。要求事項10 は範囲の承認を人(技術判断者)に置いているが、正解そのものの確定は書いていない。範囲だけ人が承認しても、正解が AI 由来なら承認の対象が空になる
- **(5) 観測の指標の理由**: 警告疲れの先例は、利用者側から見た誤検知(見たくなかった報告)を継続的に測り、高い解析器を人の前に出さない運用である(外部 2.3、Tricorder。要旨のみ)。有用さの観測が無いと、既定無効のまま放置されるか、有効化しても無視される(外部 考察A)。**不在の見逃しの件数を入れるのは、R-1 (3) の不作為の誤りを観測で拾うため**で、人へ戻す側に限る設計で最も見えにくい失敗である。観測の源は、第7章の是正の記録と、人へ戻した事例の記録で、提示のログだけでは数えられない
  - 検出率として保証の開示に載せない理由は R-1 (1) と同じで、検出の層ではないものに検出の層の尺度を付けない
  - 観測の記録に発話の本文を残さない(旧案はハッシュだけを残した。この点は保つ)。観測のために送信の記録を厚くすると、3.12.8 の機密情報の扱いが重くなる
- **(6) 閾値を課さない理由**: 提供者自身が固定の閾値を示さず用途しだいとし、版の更新で答えが変わり、版ごとの再調整を求めている(外部 1.2・1.3)。本文に値を置けば、製品の版に本文が縛られる。3.12.12 の登録簿は本標準の定数の登録簿で、部品の構成値を載せる場所ではない。1.7.7 の型で言えば、提示の閾値は「置き換えずに用いても統制を弱めない」値(提示は判定に数えないので、閾値を上げても下げても統制は変わらない)で、既定値としてよい型に当たる
- **既存の枠組みとの整合**: NIST AI RMF の MANAGE 3.2(開発に使う事前学習済みモデルを監視・保守の一部として監視する)は、(5) の継続観測と向きが合う

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 旧評価の値(工程 84.6%、注意の再現率 67〜100%、誤警報 6.9%)を採否の根拠に使う | 正解が AI の合議で、偶数番も方式の選定に使われ独立でない(評価メモ自身が開示。内部 1.4) |
| 分類器にも附属書H の5条件(欠陥注入の検出率など)を掛ける | 検出の層ではない(R-1)。尺度が合わない |
| 3.4.2 の適合性確認を分類器にも掛ける | 席の担い手ではない。掛けると 3.4.2 の単位(担い手の識別)の定義が崩れる |
| 閾値の参考の値を本文に置く | 製品の版に本文が縛られる。実証も無い |
| 有用さの観測の値に、停止の基準値(無視の割合が X% を超えたら止める等)を本文で課す | 値の実証が無い。止める判断は観測を見た人が行い、値は部品の側の既定値または組織が定める値にとどめる。根拠水準のマークで開示する |

### 反論されうる点

- 正解の確定を人に置くと、240 件規模の基準集合でも人の工数が大きく、評価がされなくなる、という反論。→ 工数は採否の理由にしない。評価がされないなら採らない、が信頼性の判断である。人が確定した少数の基準集合のほうが、AI の合議の多数より採否の根拠として強い
- 「既存のモデルで同じ推定を行う案を比較へ戻す」は、規格の委員の範囲を超えた技術判断だ、という反論。→ 本委員が言うのは、採用済みの規定(3.5.4)によって旧案の比較の前提が崩れたので、比較をやり直さずに結論を引き継げない、という整合の指摘である。どちらを採るかは技術の委員と本プロジェクトのオーナーが決める
- 不在の見逃しの件数は、事後に「戻すべきだった」と判定する者の主観に依る、という反論。→ そのとおりで、指標としての精度は低い。ただし、数えないと不作為の誤りがまったく見えない。精度の低さは根拠水準のマークで開示する

## 7. R-5 記録

### 結論

1. **新しい ADR を起こす**(番号はコミットの直前の main の最大の次。2026-11-04 時点で ADR-0103)。ADR の決定は、旧案の採否ではなく、**本標準がこの種の部品をどう位置づけるか**を主語にする
2. **本文に一般の規定を置く**(R-1 の (1)〜(4)、R-2 の (1)(2) の読みの明記、R-4 の (4))。製品を名指さない。実証が無いので、根拠水準のマーク(新しい EV)を付ける。実行主体の挙動を縛る規定なので実装マーク(新しい IMPL)を付け、準拠テンプレートへ降りていないものは `state=undelivered` で表示し続ける
3. ADR の中で、旧案(確率的な分類器を準拠テンプレートへ既定無効で同梱する案)を**採らないと明記する**。却下の理由を、R-2・R-3・R-4 の理由で書く。「書かれていない」と「採らないと決めた」を区別できるようにする
4. 本プロジェクトのオーナーの 2026-09-23「条件付きで採用」は、**事実として経緯の節に記録し、本 ADR の決定がそれに代わると書く**。置き換え(ステータスの語彙)の対象にはしない。旧 ADR 案は main に入っていないため
5. 決める者の切り分けを ADR に書く

### 理由

- **(1) ADR を起こす理由**: 旧案の論点の多くは、あとから変えにくい位置づけの決定(検出の層に数えるか、外部送信の上流の操作をどう読むか、見本に入れるか)である。ADR の運用規則の「あとから変えにくい決定」に当たる。主語を「本標準の位置づけ」にするのは、旧案の採否だけを記録すると、採用者が自ら足す部品について何も決まっていない状態が残るため(第2節)
- **(2) 本文に置く理由**: テンプレートの部品としての ADR に留めると、規範が採用者の組織に届かない(R-1 の採らない案)。本文に置く規定は「提示を入力にしない」「不在を根拠にしない」のように**禁止と性能**で書ける。1.7.1 の要求・禁止の形で書き、理由の文(「〜ためです」)と分ける(1.7.2。要求を名詞で結ぶ文や注記に書かない)
  - 置き場の候補は附属書H の「AI が確認した」の分類の直後と、5.7.4 の近く。附属書H を推す。5.7.4 はゲート承認の記述の質の節で、発話の分類を扱う節ではないため(内部 2.1)。旧案がここを類推で引いたことが、位置づけの割れの一因だった
  - R-2 の (1)(2) は、新しい規定ではなく既存の規定(5.5.1・3.12.2・3.12.8)の読みの確定である。本文を改めるか、ADR の決定として読みを記録するかは起草者に委ねる。ただし「推論を返す外部のサービスを 3.12 の AI 実行基盤に含めるか」は、本文に書かないと読みが割れ続ける。本文に書くことを推す
  - 準拠テンプレートへの降ろし先: 「提示を入力にしない」「不在を根拠にしない」は CLAUDE.md の判断の確定の節(既存の「AI の確認は検出の層」の行の近く)が候補。常駐の規則の行数(RC-07)に近いことは、置かない理由にしない。既存の行と統合する書き方を起草者が考える
- **(3) 採らないと明記する理由**: 本プロジェクトのコアポリシー(却下は成果である)。旧案の PR は「番号の衝突・main との衝突・会議体を経ていない」という手続の理由で閉じた。中身の理由で採らないと決めた記録は無い。手続の理由だけで閉じたものは、手続を整えれば再提出できると読まれる
- **(4) 2026-09-23 の扱い**: 一次の記録は PR #283 の本文だけで、条件の中身は記録されていない。PR は「マージをもって内容の確認とします」と書き、マージされずに閉じた(内部 1.5)。PR の自身の条件によれば、内容の確認は成立していない。ただし、オーナーが一度「条件付きで採用」を選んだ事実は消えない。**消さずに経緯へ書き、本 ADR の決定がそれに代わることと、代わる理由(その後に入った規定: 3.5.4・5.5.1 の定義・3.12.3 の拡張・ADR-0084/0085、旧案が引いていなかった 3.12.2・3.12.8)を書く**。「取り下げ」と書くか「変更」と書くかは、オーナー本人の判断(下の切り分け)
- **(5) 決める者の切り分け**
  - 本プロジェクトのオーナー(標準の保守者)が決めること: ADR と本文の改訂を採るか(マージ)。準拠テンプレートの外に任意の部品を保守するか。2026-09-23 の選択を「取り下げ」と書くか「変更」と書くか
  - 会議体が決めて、オーナーへ提案すること: 位置づけ(R-1)、読みの確定(R-2)、同梱しないこと(R-3)、評価の要件(R-4)
  - 本標準が採用者の席に割り当てること(本プロジェクトのオーナーは決めない): 採用者の組織で分類器を有効にするかどうか。AI運用担当者(経路、モデルの適合性)、AI維持管理者(外部ツールとフック)、外部との契約に関わる人の判断(5.4.3)。**採用者の組織での採用の可否を最後に決めるのは、採用者の席であって、本プロジェクトのオーナーではない**。旧案はこの二者を「オーナー」の一語で重ねていた

### 反論されうる点

- 本文に規定を置くと、存在しない部品のための条項が増え、採用者の読む量が増える、という反論。→ 読む量は採否の理由にしない。ただし条項は、附属書H の分類に1つの種別を足す規模で書け、新しい節を要しない。読む量が増えないように書くのは起草の技術で、規定を置かない理由にはならない
- 「採用者の組織での採用の可否は採用者の席が決める」なら、本プロジェクトが位置づけを決める必要も無い、という反論。→ 本標準が決めるのは、採用者が使うときの位置づけ(何に数えないか)と経路の要件で、使うかどうかではない。前者は規格の役割、後者は採用者の役割で、旧案の議論はこの二つを混ぜていた
- 根拠水準のマークだらけになる、という反論。→ 実証が無いのは事実で、開示がコアポリシーの要求である。差し替え条件には R-4 (5) の観測の指標を使える

## 9. 論点ごとの結論(1行)

- R-1: 検出の層ではなく、どの層でもない「AI の推定による注意の提示」として附属書H に明記し、出力をどの判定・記録の入力にもしないこと、不在を省略・引き下げの根拠にしないこと、提示が 5.5.1 の人へ戻す場合を増やさないことを本文で定める。「引き上げ」の語は使わない
- R-2: 有効化・送信先の追加は 5.5.1 の上流の取り消せない操作として人が行う。個々の送信は 3.12.2 の正規の経路と 3.12.8 を満たす場合に限って1件ずつ戻さない。旧案の端末からの直接接続は記録がそろっても不適合。常設の事前決裁を新設しない。5.8.6(IMPL-0200)が降りる前にテンプレートへ外部送信の部品を入れない
- R-3: 準拠テンプレートへ同梱しない(既定無効も不可)。保守するなら外の任意部品とし、推奨でない・同等品可・時点を併記。本文とテンプレートは製品を名指さない。graft の利用統計を別 Issue で確かめる
- R-4: 旧評価(AI 合議の正解ラベル)は採否の根拠にしない。系統違いの却下理由は 3.5.4 により使えず、既存の正規の経路のモデルを比較へ戻す。3.12.3 は掛かり、基準集合の正解は人が確定する。有用さ(不在の見逃しを含む)を観測し、検出率として開示しない。閾値は本文で課さない
- R-5: ADR-0103(コミット直前に取り直す)を起こし、本標準の位置づけを主語に決める。本文に製品を名指さない一般の規定を EV・IMPL のマーク付きで置く。旧案を採らないと明記し、2026-09-23 の選択は経緯に事実として残して本 ADR が代わると書く。採用者の組織での採否は採用者の席、本標準と見本の改訂の採否は本プロジェクトのオーナーが決める
