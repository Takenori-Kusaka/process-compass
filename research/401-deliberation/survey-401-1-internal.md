### 2.3 「引き上げ」の語と、自律レベルの引き上げ(5.4.5)・運用形態(5.5.7)

- **語の衝突**: 旧案の「引き上げ方向の助言」は「人へ戻す/`state:needs-*` へ引き渡す」(エスカレーション)の意味。現行の標準で「引き上げ」は、主に**統制を緩める向き**の語である
  - 5.4.5 レベルの引き上げ(`std/human-ai-boundary.md:114-147`): L1→L2→L3。技術判断者が申請し B-2 が判定する。条件6 を欠いた引き上げを認めない
  - 5.5.7 運用形態の引き上げと引き下げ(`:552-591`): 「統制を緩める向きは判定を要し、厳しくする向きは即時に適用」。緩める = 人確定→協働→委任
  - 5.5.6 `:519` 技術判断者の確定事項「AI自律レベルの引き上げの申請(5.4.5)」
  - 一方で `std/gate-criteria.md:1580`「区分の下限を R2 へ引き上げる」と `:717-720` の代償措置の「引き上げた下限」は、厳しくする向き。**標準の中でも「引き上げ」の向きは一定でない**
  - 人へ戻すことを表す語は、5.5.1 の「人へ戻す」(`:343-347`)、tpl/CLAUDE.md:28 の「人へ戻す3つの場合」、第7章の「エスカレーション」。推測: 新案では「引き上げ方向」を使わず、「人へ戻す側に限る」「厳しくする向き」へ寄せないと、5.4.5 の引き上げと読み違えられる
- 向きの非対称との関係: 5.5.7 は「厳しくする向きは即時」。助言が人へ戻す側にだけ働くなら厳しくする向きで、判定を要しない、という論は立つ(推測)。ただし**助言の仕組みを有効にすること自体**は外部送信を始める決定で、5.5.7 の向きの表のどこにも当たらない。有効化をどの手続で決めるかは、別に決める必要がある(2.4・2.5)
- 層1(テンプレ11)項目4 の必須行「AI の利用の拡大(自律レベルの引き上げ、委任の範囲の登録)」(`std/deliverable-templates.md:1504`、2026-10-08 f3b7033、ADR-0057)。括弧で範囲を限っており、**新しい AI の部品(分類器)の追加が「AI の利用の拡大」に当たるかは書かれていない**。5.5.7 `:586` は、この行が「認めない」で始まる組織では委任の登録を構成で受け付けない錠(IMPL-0098)。推測: 分類器の有効化を「AI の利用の拡大」に数えるなら、層1 の受容者の記名が要る

### 2.4 取り消せない操作(外部への発行・第三者への送信)と、外部送信・データの扱い

- 5.5.1 の定義(`std/human-ai-boundary.md:349-359`、2026-10-23 76bd440、ADR-0078 決定2): 「取り消せない操作とは、取り消せない効果を、他の者の操作を介さずに生じさせる操作」。基準は「取り消せない時間帯が存在すること」(ADR-0053 決定1)。`:353`「後段が人でない経路では、上流の操作が取り消せない操作に当たる。…予約した公開、push を契機に動く配備が、これに当たる」
  - tpl/CLAUDE.md:36 の (c) と、`tpl/CLAUDE.md:64`「事前承認のない外部パブリックホストへ決裁資料やログを置く」= 第5章 5.5.1 (c)(組織の管理外への発行は取り消せない操作)。**5.5.1 本文に (c) の記号は無い。(c) はテンプレートの「人へ戻す3つの場合」の記号**。Issue #401 本文の「第5章 5.5.1 (c)」は、テンプレートの表記に由来する
  - 第8章「設計で下げられない危害」(`std/tailoring-guide.md:910-918`)「外部へ出た情報(公開、第三者への送信、漏えい)」
  - ADR-0053 決定3(`adr/0053-...:79-84`)「組織の管理外への発行(公開ホストへの掲載、第三者への送信。発行を削除しても、発行されていた時間帯は消えない)」。決定4(`:86-97`)「何を組織外とするかを標準は定義しない。発行先の既定を拒否に置き、許可する発行先の列挙を案件へ渡す」
  - **突き合わせの論点**: 旧案の発話ごとの送信は、フック(Claude Code の実行基盤)が人の操作を介さずに行う第三者への送信。5.5.1 の定義に照らすと、各送信は取り消せない効果を他の者の操作を介さずに生じさせる操作に当たり、`:353` により有効化(`enabled:true` と 3 記録)という上流の操作が取り消せない操作に当たる、という読みになる(推測)。旧案はオーナーの外部送信の決裁 1 回で以後の送信をすべて覆う形で、**送信ごとに人へ戻さない**。この「常設の事前決裁」で 5.5.1 を満たせるかは、標準に書かれていない。近い類例は 5.5.4 の行「本番環境への反映の承認」(登録時の記名による事前承認、`:354`)だけ
  - 送信の主体がエージェントではなくフックであるため、5.5.1(担い手が人へ戻す場合)の対象外と読む余地もある(推測)。その場合も、第8章の「外部へ出た情報」の危害は残る
- 5.8.6(`std/human-ai-boundary.md:1040-1079`。本文への移設は 2026-10-24 e3b701d。中身は附属書E E.6 とフェーズ5 にあったと EV-0175 が記す)
  - 要求事項1(`:1046`)「許可していない外部への通信」を実行時に拒否する
  - 要求事項3(`:1048`)ネットワークは既定を拒否とし、必要な宛先に限る
  - 要求事項4(`:1049`)秘匿情報は実行環境から参照できない位置へ置く。読み取りの制限だけに頼らない
  - **IMPL-0200(`:1065`)は `state=undelivered`(issue #358、見直し 2026-11)**: 準拠テンプレートの権限設定は、書き込みの範囲とネットワークを限らない。旧評価メモの不整合(4)「強制層にネットワークの既定拒否が無い」は**現行でも未解消**(`tpl/.claude/settings.json` の ask は `wget` と `npm publish` だけ。`curl` や node の fetch は限られない)
  - 推測: Claude Code のフックの command は、エージェントの権限設定(permissions)の外で実行される。旧案の許可リスト(`allowedEndpoint`)はフックのコード内の自己規制で、5.8.6 要求事項2 の「実行環境の設定(強制層)に置く」に当たるかは要検討(フック本体は `.claude/hooks/**` で ask の対象、つまり強制層の一部とは読める)
- 3.12.2(`std/roles-responsibilities.md:1474-1486`、2026-08-05 から存在): 「開発組織が AI 実行基盤へ直接接続することを認めません。接続はすべて AI運用担当者が用意した経路を通ります」。「個人で契約した経路は正規の経路に当たらない」(後段は 2026-10-23 に追加)。**旧案は API キーを環境変数で受け、端末から直接 `api.typesafe.ai` へ接続する。旧 ADR は 3.12.2 を引いていない**。分類器が「AI 実行基盤」に当たるかは書かれていないが、当たると読むのが自然(推測)
- 3.12.8 セキュリティとデータ保護(`:1605-1613`、2026-08-05 から存在): 要求事項1「承認された経路以外からモデルへ接続してはならない」、2「機密情報の送出を検査する仕組みを、接続経路の上に置く」、3「入出力の学習利用の有無と保持期間を確認し記録する」。旧案の秘匿情報の検出(正規表現)はクライアント側で、接続経路の上ではない。保持期間は「定めなし」と評価メモが記録している。**旧 ADR は 3.12.8 も引いていない**
- 3.12.11 依存先の一覧と単一障害点(`:1696-1716`、ADR-0057 で新設、2026-10-08): 要求事項1 は依存先に「外部の道具(3.11.6)」と「データ」を含める。要求事項2 は各行に、代替の有無・通知の期間・渡すデータの種別と保持の条件を持たせる。テンプレ側は構成の `dependencies` 欄(`tpl/scripts/init/generate-profile.mjs:1900-1902, 4216`)。旧案の `phaseAdvisor` は `dependencies` に載らない。**有効化した案件では、TypeSafe が「代替の無い依存先」「退出を試していない依存先」(3.12.3 要求事項7〜9)として単一障害点の一覧に出るはず**(推測。ただし出荷に要る席の担い手ではないため、3.12.3 要求事項7 の対象かは読みが割れる)
- フェーズ5(参考)`phase5-implementation/ai-environment.md:91`「外部送信の範囲を情報セキュリティ部門と事前合意し、対象外データは deny 設定と運用の両方で遮断」。旧案の「オーナーの決裁」は、情報セキュリティ部門との合意を名指していない

### 2.5 強制層(`.claude/settings.json` のフック)の追加の承認

- 3.11.3 指示資産の3層(`std/roles-responsibilities.md:1307-1325`): 強制層 = 権限設定・実行前フック・CI の必須検査。旧案のフックは**遮断しない**ので機能は誘導層(文脈への差し込み)に近いが、置き場(`.claude/hooks/`・`.claude/settings.json`)は強制層。推測: どちらとして扱うかを決める必要がある
- 3.11.2 AI維持管理者の承認権限(`:1296-1303`): 指示資産の変更(強制層の検査の追加・削除・統合を含む)と、外部ツールの採用可否。「検査の追加の要否は技術判断者が決める」
- `tpl/CLAUDE.md:121`「エージェント指示資産(`.claude/**`)と CI の検査の追加・統合・削除は AI維持管理者が承認する(`state:needs-platform`)。検査の追加の要否は技術判断者が決める。AI は候補の提示まで」。この行は採用者のリポジトリでの規則。旧 PR #50 は AI が起草してフックの追加まで実装した。テンプレートへ降ろす場合の承認者は、本プロジェクトのオーナー(保守者)
- 統制の弱化(3.5.5「統制の弱化を検知したときの引き渡し」`:741-760`、ADR-0038 決定1〜5): 性質(遮断の解除・閾値の緩和・強制層の縮小)で定義する。**フックの追加は弱化の 3 性質に当たらない**(増やす向き)。ただし旧案は、`UserPromptSubmit` で外部送信を始める経路を強制層の中に作る。これが「遮断の解除」(禁止していた操作 = 外部への通信を許可する)に当たるかについては、ネットワークを既定拒否にしていない現状(IMPL-0200 未達)では、そもそも禁止していないため当たらない、という読みになる(推測)。5.8.6 が降りた後は当たる
  - ADR-0038 決定3 の見出しは「不可逆4操作に該当する場合は事業決裁者を併記」(`adr/0038-...:56`)。採用済み ADR の本文は書き換えない規約のため旧語が残る。現行の本文(`:747`)は「取り消せない操作に当たる場合」へ改められている
- ADR-0084 決定6(逆向きの追跡、`adr/0084-...:118`): 準拠テンプレートのフック(`.claude/hooks`)と `.claude` 直下の json の各ファイルは、降ろし先の登録簿(`src/data/impl-targets.yaml`。現在のフックは `guard-write-hook` `:300-303` だけ)か除外の一覧(`src/data/impl-untraced.yaml`)に載っていなければ、`check-impl.mjs` が落とす。**新しいフックを入れるなら、標準側に規定(IMPL マーク)を置くか、除外の理由(library/infra/variant)を書く必要がある**。旧案はどちらも無い(当時はこの検査が無かった)
- ADR-0085 決定5・6(`adr/0085-...:81-86, 126-134`): テンプレートのフックの登録の欠けを、契約検査で失敗にする(`tpl/scripts/gate/verify-gate-contract.mjs:260-279`、`tpl/scripts/gate/config.mjs:2167` の `TEMPLATE_HOOKS`)。取り込みは強制層の変更(`state:needs-platform`)。推測: 新しいフックを `TEMPLATE_HOOKS` に加えると、取り込まない採用者が契約検査で落ちる。加えないなら、既定無効の任意の部品として扱う別の経路が要る
- ADR-0050・ADR-0074: 強制層を段階(PoC)で外さない。任意の部品を既定無効で同梱する形は、強制層を外す形ではないので直接は当たらない
- 権限設定の現状: `tpl/.claude/settings.json` は `Edit(./process.config.json)`・`Edit(./.claude/hooks/**)`・`Edit(./.claude/settings.json)` を ask にしている。旧案の `phaseAdvisor`(有効化・閾値・承認欄)は `process.config.json` にあるため、エージェントの Edit には確認が掛かる。Bash 経由の書き込みは限らない(IMPL-0200 未達と同根)

### 2.7 特定の製品の名指しと同梱(ADR-0080 M-4 ほか)

- ADR-0080 M-4(`adr/0080-method-neutrality-and-relation-to-existing-methods.md:65`)は、**開発手法**(SAFe・Shape Up 等)を名指さない決定。製品(分類器のサービス)には直接は当たらない。理由の型「改訂の速いものを名指すと追随を負い、相手の公式見解と取り違えられる」は、製品にも類推できる(推測)

- 3.11.6 外部ツールの統治(`std/roles-responsibilities.md:1418-1433`): 要求事項1・3(一覧と権限を版管理下に置く)は IMPL-0228 が `undelivered`(#358)。要求事項2・4・5(提供元の確認、説明文を信頼できない入力として扱う、追加と変更に AI維持管理者の承認)は IMPL-0229 が `undelivered`(#358)。注記は「準拠テンプレートは外部連携サーバの設定(.mcp.json)を置かず、一覧と権限の置き場が無い」。旧案の `approval.toolAdoption` は、この未達の置き場を部分的に埋める形になる(推測)

### 3.2 会議体へ渡す論点の候補(この調査から出たもの。採否の提案ではない)

1. 助言の仕組みは、検出の層か、どの層でもないか(H.4 の5条件を掛けるか)
2. 「引き上げ方向」の語を使うか(5.4.5・5.5.7 の「引き上げ」との衝突)
3. 発話ごとの自動送信を、5.5.1 の取り消せない操作の「上流の操作」として扱うか。常設の事前決裁で足りるか。決める席は事業決裁者か(旧案の「オーナー」は席の名ではない)
4. 3.12.2・3.12.8(接続経路、送出の検査を経路の上に置く、学習と保持の記録)を、端末から直接つなぐ形でどう満たすか。旧案は引いていない
5. 5.8.6 要求事項1・3 が未達(IMPL-0200)のテンプレートへ、外部送信をするフックを先に入れる順序の是非
6. 準拠テンプレートへの同梱か、graft の MCP と同じく各自のローカル設定に置く任意部品か。同梱なら、逆向きの追跡(ADR-0084)と契約検査(ADR-0085)の扱い
7. 標準の本文へ規定を置くか(置かないなら、テンプレートだけの部品として ADR に記録する)。製品の名指し(1.7 `std/overview.md:278`)との関係
8. 評価の正解ラベルを AI の合議で作ったこと、提供元の違いを却下理由に使ったことの扱い(3.5.4 `:664`、IMPL-0153)
9. 旧案の G-4 の照合が、ADR-0070 の後の記録の置き場と合わないこと
10. オーナーの 2026-09-23「条件付きで採用」は、条件の記録が無く、内容確認(マージ)も成立していない。維持・変更・取り下げを記録する際の事実として扱う
