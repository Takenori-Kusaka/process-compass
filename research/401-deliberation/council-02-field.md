# #401 会議体 委員意見: 現場

- 立場: 現場(1〜2名・3〜9名・10名以上の体制で、実際に回るか、形骸化しないか、手間と情報管理の負担に見合うか、警告疲れが起きないかを見る)
- 日付: 2026-11-04
- 入力: `council-00-agenda.md`、`survey-401-1-internal.md`(以下「内部」)、`survey-401-2-external.md`(以下「外部」)。補足で本文 `std/human-ai-boundary.md` の 5.7.5・5.8.6 と `template/CLAUDE.md:100-112` を読んだ
- 判断軸: 信頼性。変更量の少なさ・実装済みの旧 PR があることを採否の理由にしない
- 推測は「推測」と書く。体制の負担の見積もりは、実測ではなく現場の経験則による推測である

## 0. 現場から見た前提(全論点に共通)

1. **発話ごとに動く仕組みは、ゲートの単位で動く仕組みと桁が違う**。旧案のフックは `UserPromptSubmit` で全発話に起動する。1名でも1日に数十〜百を超える発話になる(推測)。注意の要らない発話の 6.9% で誤警報(内部 1.4)なら、1日に数件〜10件程度の誤警報が恒常的に出る。5.7.5「摩擦の総量を管理する。総量が増えるほど個々の摩擦は無視される」の対象そのもの
2. **助言の宛先が、主にエージェントの文脈である**(`additionalContext`。内部 1.2)。人は助言を見ないまま、エージェントの振る舞いだけが変わる。現場では「人が助言を無視する」より先に「人が助言の存在を知らない」が起きる。観測も是正も、人の目に入らないところで進む
3. **発話には、現場で最も統制しにくい情報が混ざる**。貼り付けたログ、顧客のデータ、エラーの全文、社内の口頭文脈。タグの無い貼り付けは本文に混ざって送られる(内部 1.2、旧 README の「限界」)。秘匿情報の検出は既知の形の正規表現だけで、個人情報・顧客名・未公開の事業情報は検出できない
4. **テンプレートの「既定無効の部品」は、現場では「誰も保守していない部品」になる**。旧案の基点から 129 コミットで差分が当たらなくなった(内部 2.8)。既定無効の部品は誰も通しで動かさないため、壊れても誰も気づかない
5. **本プロジェクトの未達(IMPL-0200: ネットワークの既定拒否)は、現場の採用者にとって「拒否が無い」という事実**である。テンプレートを信頼して採用した組織は、外部送信が強制層で止まっていると思い込む(推測)

## R-1 位置づけ

### 結論

- 確率的な分類器の助言は、**どの層でもない「誘導」**に置く。検出の層に数えない。附属書H H.4 の5条件を満たしたと主張する経路も開けない
- 判定・承認・遮断・完了・ラベルの遷移・リスク区分の決定・「該当しない」の結論に**数えない**ことを規範で書く
- **助言が出なかったことを、確認の省略・区分の引き下げ・運用形態の判断・ゲートの通過の根拠に数えない。記録・PR の本文・判定記録に「分類器は注意を出さなかった」と書かない**
- 「引き上げ方向」の語は使わない。「**人へ戻す側にだけ働く助言**」「厳しくする向きの助言」と書く

### 理由

- 現場で最も起きやすい誤用は、助言を判定に使うことより、**助言が出ないことを安心材料に使うこと**(不作為の誤り。外部 2.2 Goddard、FDA 基準4)。エージェントは文脈にあるものを根拠として引きたがる。「phase-advisor の注意はありませんでした」を PR の本文へ書く挙動は、指示が無ければ高い確率で起きる(推測)。5.8.6 要求事項9「拒否が0件であることを根拠として記録しない」と同型の禁止を、助言にも置く必要がある
- 検出の層に数えると、H.4 の5条件(欠陥注入による検出率の測定と開示、指摘と採否の記録)を案件ごとに満たす作業が生じる。1〜2名・3〜9名の体制で、発話の分類の検出率を案件で測ることは現実に回らない。回らない条件を置くと、条件を満たしたことにする記録が作られる(形骸化)。数えないと決めるほうが信頼できる
- 「引き上げ」の衝突は、机上の話ではない。エージェントが毎回読む `template/CLAUDE.md:103` に「運用形態は上限の宣言。案件の判断で**引き上げない**」(緩める向き)がある。同じファイルに「引き上げ方向の助言」が並ぶと、エージェントも人も向きを取り違える
- 5.5.1(`human-ai-boundary.md:338-345`)は、承認済みの範囲の内側の選択を「選択のたびに人へ戻さない」と定める。旧案の注意(とくに delegated_judgment。誤警報の多くが「決めちゃって」型)は、この戻さなくてよい選択までエージェントに人へ戻させる。人へ戻す側だけに働く助言でも、**無害ではない**。戻しすぎは、人の側の警告疲れと、「戻されたら即承認」の癖を生む

### 体制ごとに回るか

| 体制 | 回るか | 現場の見立て |
| --- | --- | --- |
| 1〜2名 | 回らない恐れが大きい | 戻される先は自分しかいない。助言で戻されるたびに自分の作業が止まり、数日で無効化するか、内容を読まずに続行する癖が付く(推測)。「数えない」の規範は守れるが、助言自体が役に立たない |
| 3〜9名 | 条件つきで回る | 戻す先の席が分かれ始める。戻しすぎの影響は技術判断者へ集中する。頻度の観測(R-4)が無ければ形骸化する |
| 10名以上 | 規範は回る。誤用の監視が要る | 記録・PR の本文を書く人とエージェントが多く、「出なかった」を根拠に書く事例が散発する。禁止を CLAUDE.md の常駐の規則に置き、レビューで拾える形にする必要がある |

### 譲れない点

1. 助言の不在を根拠に数えない・書かない禁止を、**エージェントが読む場所(常駐の規則)**に置くこと。本文に置くだけでは現場に届かない
2. 検出の層に数えないこと。条件つきで数えられる道を残さない
3. 「引き上げ」の語を使わないこと
4. 助言が人へ戻すことを促す場合も、5.5.1 の「戻さなくてよい選択」を戻させないこと。助言は戻す理由の**候補**を示すに留め、戻すかどうかは 5.5.1 の3つの場合の判断による

### 採らない案

- 検出の層に数え、H.4 の5条件を課す案。小規模体制で条件の確認が回らず、確認したことにする記録を生む
- 助言を誘導層の指示資産(CLAUDE.md の規則)と同列に扱う案。指示資産は人が書いた決定論の規則で、確率的な出力とは性質が違う
- 「引き上げ方向」の語を定義し直して使い続ける案。既存の 5.4.5・5.5.7・`template/CLAUDE.md:103` の読みを壊す

### 反論されうる点

- 「誘導にすぎないなら、標準が規定する必要は無い」→ 現場では誘導が記録の根拠に化ける(不作為の誤り)。規定しないと、採用者は Copilot の承認の例(外部 2.1)のように、設定1つで境界を越える
- 「人へ戻す側だけなら害は無い」→ 戻しすぎは 5.5.1 と 5.7.5 に反する。害の形が違うだけ
- 「1〜2名で回らないなら、1〜2名には適用外と書けばよい」→ 適用外にすると、1〜2名の採用者が使ったときの禁止(不在を根拠にしない)まで外れる。禁止は体制によらず掛け、使うかどうかを任意にするほうが安全

## R-2 外部送信

### 結論

- 発話ごとの自動送信は、各送信が第三者への送信(取り消せない効果)であり、後段に人がいない経路である。したがって**有効化(と、送信先・送る範囲・版の変更)を、取り消せない操作の上流の操作として扱う**(5.5.1 `:353`、ADR-0078 決定2)
- 送信ごとの人の承認は現場で回らない(発話ごとになる)。**取れる形は常設の事前決裁だけ**である。ただし常設の決裁を受け付ける条件を絞る
  - 決める席は**事業決裁者**(旧案の「オーナー」は席の名ではない)。情報セキュリティ部門が組織にある場合は、その合意の記録を決裁に添える
  - 決裁の記録は、空でない文字列ではなく**中身を持つ**: 送信先、送るデータの種別と除外するデータ、保持期間と学習利用の確認結果(3.12.8 要求事項3)、接続の経路(3.12.2)、見直しの時期、取り消しの手順
  - 送信先・送る範囲・提供者の規約(DPA)・モデルの版が変わったら、決裁は失効する
- 3.12.2(直接接続を認めない。個人で契約した経路は正規の経路でない)と 3.12.8(送出の検査を接続経路の上に置く)を、そのまま掛ける。**端末から個人の API キーで直接つなぐ形は、決裁があっても正規の経路にならない**
- 3.12.11 の依存先の一覧へ載せる。層1 項目4「AI の利用の拡大」に数える(新しい AI の部品を、新しいデータの流れとともに足すため)
- **5.8.6(外部通信の既定拒否、IMPL-0200)が準拠テンプレートへ降りるまで、外部送信をする部品をテンプレートへ入れない**。この順序は譲れない

### 理由

- 常設の事前決裁は、現場で最も形骸化しやすい承認である。「情報持ち出し申請」型の決裁は、一度通ると以後の送信の中身を誰も見ない(外部の「埋められなかった穴」に実データは無いが、現場では典型。推測)。旧案は3記録を「空でないか、仮の値でないか」だけで判定しており(内部 1.2、`unapproved()`)、任意の文字列で送信が始まる。これは決裁ではなく、決裁の欄である
- 発話は、送る中身を事前に列挙できない。ゲートの判定記録の送信なら中身を決められるが、発話には貼り付けたログ・顧客データ・社内の文脈が混ざる。決裁者は「何が送られるか」を決裁時に知りようがない。だからこそ、**送るデータの種別と除外**を決裁の中身に要求し、除外を実装で担保できるかを決裁の前に確かめる必要がある
- 旧案の許可リスト(`allowedEndpoint`)はフックのコード内の自己規制で、5.8.6 要求事項2「拒否の範囲は実行環境の設定(強制層)に置く」に当たらない。テンプレートの権限設定は Bash 経由の書き込みと `curl`・node の fetch を限っていない(内部 2.5)。エージェントが Bash でフックや構成を書き換えれば、許可リストも有効化の欄も変わる。**外側で止める層が無いまま、内側の自己規制だけを持つ部品を配ることは、採用者に誤った安心を与える**
- 外部 3.5 の事件(postmark-mcp、s1ngularity、CVE-2026-47751)は、いずれも「導入済みの信頼された拡張が、更新や設定ファイル経由で送信先を変える」形。リポジトリ内の設定を PR で差し替えられる現状で、外部送信の部品を足すと攻撃面が増える
- 1〜2名の体制では、事業決裁者・AI運用担当者・AI維持管理者が同一人物になる。3つの記録を同じ人が書く儀式になるが、ADR-0057 補足 S50 と 5.5.7 `:588` は「どの席で判断したかを記録し、同一人物を理由に記録を省かない」とする。現場の結論は、**記録は分けるが、欄の数を増やさず、中身(送るデータの種別・保持・経路)を1つの決裁へ集める**こと。欄を増やすほど、1名の現場では空欄埋めになる

### 体制ごとに回るか

| 体制 | 回るか | 現場の見立て |
| --- | --- | --- |
| 1〜2名 | 決裁は形だけになりやすい | 決裁者=利用者。決裁の中身(送るデータの種別・保持・経路)を書かせる様式が無いと、空でない1行で済ませる。3.12.2 の「正規の経路」を自分で用意することになり、実際には個人の API キーになる(推測)。**この体制では、外部送信を伴う助言を使わない選択が最も信頼できる** |
| 3〜9名 | 回るが、情報管理の担い手が不在のことが多い | 情報セキュリティ部門が無い組織が多い(推測)。保持期間・学習利用・ZDR の有無を誰が確かめたかが曖昧になる。決裁の中身の様式と失効条件が要る |
| 10名以上 | 手続は回る。中身が見られなくなる | 情報セキュリティ部門・法務との合意の手続は既にある。ただし一度通った常設の決裁は見直されない。失効条件(送信先・規約・版の変更)と見直しの時期を決裁の中に持たせ、依存先の一覧(3.12.11)から辿れるようにすることが要る。委託の案件では強制層を所有する組織の同意(ADR-0087)が加わる |

### 譲れない点

1. 5.8.6 の既定拒否が降りる前に、外部送信の部品をテンプレートへ入れない
2. 決裁の記録は中身を持つ(送信先・送るデータの種別と除外・保持と学習利用・経路・見直しの時期・取り消しの手順)。欄が空でないことを決裁の成立に数えない
3. 3.12.2 の正規の経路を通る。個人の API キーで端末から直接つなぐ形を、決裁で正当化しない
4. 送信先・規約・版の変更で決裁が失効する

### 採らない案

- 送信ごとに人が承認する案。発話ごとの承認は数日で「全部許可」になる(警告疲れ)。承認の形骸化を作るだけ
- フックは担い手ではないので 5.5.1 の対象外と読む案(内部 2.4 の余地)。送信の主体が誰でも、第8章「外部へ出た情報」の危害は残る。主体で逃がす読みは、現場では「フックなら何を送ってもよい」に化ける
- ZDR の契約があれば送信を許す案。ZDR は製品・機能ごとの適用範囲を持ち例外がある(外部 3.4)。当該の提供者の DPA には ZDR の記述も無い(外部 1.4)
- 秘匿情報の正規表現による検出を、3.12.8 要求事項2 の「送出の検査」に数える案。端末側の自己検査で、接続経路の上ではない。既知の形しか拾えない

### 反論されうる点

- 「常設の決裁は、結局形骸化するのだから意味が無い」→ 送信ごとの承認より形骸化が遅い。失効条件と見直しの時期を持たせることで、形骸化を時期で区切れる。それでも形骸化しうることは認め、R-4 の観測の結果で無効化できる道を残す
- 「5.8.6 の降下を待つと、いつまでも入らない」→ 入らないことは損失ではない。助言は無くても標準の統制は回る(G-5 も 5.5 も助言に依存しない)。外側で止める層が無いまま送る部品を配るほうが、採用者の信頼を損なう
- 「1〜2名に外部送信を使わない選択を勧めるのは、規格の越権」→ 勧めるのではなく、使わない選択が適合の妨げにならないことを示す。外部 課すべきでないこと3 と同じ

## R-3 同梱と製品の名指し

### 結論

- **準拠テンプレートへ同梱しない。既定無効でも入れない**
- 任意の部品として本プロジェクトが外に置く(別リポジトリ・別パッケージで配る)ことも、現時点では採らない。本プロジェクトは配る者になると、版の追随・提供者の規約の変化・攻撃面の監視の保守を負う
- 標準には、製品名を出さずに、**採用者が自ら確率的な分類器の助言を足すときの条件**(R-1 の位置づけ、R-2 の外部送信、R-4 の観測)を置く。採用者が足すときは、採用者のリポジトリの強制層の変更として扱う(`state:needs-platform`、AI維持管理者の承認、3.11.6 の外部ツールの統治)
- 製品名(Jev・TypeSafe)は標準の本文にもテンプレートにも書かない。ADR の背景と research に、時点(2026-11-04)を付けて事実として残すに留める

### 理由

- 既定無効の部品は、現場では動かされないまま腐る(前提4)。動かされない部品は、契約検査(ADR-0085)と逆向きの追跡(ADR-0084)の対象に入れるか除外するかの判断を毎回生み、`generate-profile.mjs` の改修のたびに引き継ぎの手当てが要る。**採用者が使わない部品の保守の費用を、全採用者の検査の信頼性で払う**ことになる
- 既定無効でも、テンプレートに入っているものは「標準の推奨」と読まれる(推測。日本の組織では、テンプレートに入っている=使ってよいの許可、として稟議を通す経路がある)。外部 5 の Directives Part 2 第31条は、適した製品が1つしかない場合に限って名指しを認める。確率的な分類は汎用の LLM・OSS でも実現でき、互換 OSS もある(外部 1.2)。名指しの例外に当たらない
- CLAUDE.md は 190 行で、RC-07(200 行)に近い(内部 2.8)。助言の節を足すと、エージェントが常に読む規則の中で、使っていない部品の説明が場所を取る。全採用者の常駐の規則の質を、少数の利用者のために下げることになる
- 提供者は早期アクセス段階で、価格補助の可能性・廃止方針の不記載・別名での無告知の挙動変化がある(外部 1.1・1.2)。規格の寿命より短い時間軸で変わる。テンプレートに置くと、その変化に追随する責任を本プロジェクトが負う。追随が遅れた期間、採用者は古い前提の部品を使う
- graft の先例(内部 2.7)は、MCP サーバーを `.mcp.json` に入れず、各自のローカル設定に置く。外部送信を伴いうる部品をリポジトリの強制層に入れない型の先例として整合する

### 体制ごとに回るか

| 体制 | 同梱した場合 | 同梱しない場合 |
| --- | --- | --- |
| 1〜2名 | 使わない部品の説明と構成欄が常駐の規則と構成に残る。読む負担だけが増える | 影響なし。使いたい人は条件(標準の規定)を読んで自分で足す |
| 3〜9名 | 「入っているから有効にしよう」の誘因が働く。決裁の中身が薄いまま有効化されやすい | 足すには強制層の変更の手続を通る。手続そのものが、決裁の中身を考える機会になる |
| 10名以上 | 情報セキュリティの審査の対象に、テンプレートの部品として持ち込まれる。審査は「標準が同梱している」を理由に甘くなる恐れ(推測) | 組織の外部ツールの審査(3.11.6)の通常の経路に乗る |

### 譲れない点

1. 既定無効でも同梱しない
2. 標準の本文・テンプレートで製品を名指さない
3. 採用者が足す場合の条件を、製品によらない性能・統制の形で標準に置く(同梱しないことを、規定しないことと取り違えない)

### 採らない案

- 既定無効で同梱する案(旧案)。保守の費用、推奨と読まれる誤認、常駐の規則の圧迫、5.8.6 未達との組み合わせ
- 任意の部品として本プロジェクトが別に配る案。配る者の保守と追随の責任を負う。現時点で、それを負う理由(開発プロセスでの有効性の実証)が無い(外部 2.1: フェーズの判定に使った一次の実務報告は見つからない)
- 「推奨ではない・同等品可」の脚注を付けて名指す案。例外の条件(適した製品が1つ)に当たらない
- `TEMPLATE_HOOKS` に入れて全採用者に必須にする案。取り込まない採用者が契約検査で落ちる

### 反論されうる点

- 「条件だけ書いて部品を配らないと、採用者がもっと粗い実装をする」→ その恐れはある。だから条件を具体に書く(R-2 の決裁の中身、R-1 の禁止)。粗い実装を防ぐのは条件の具体性で、配布ではない
- 「外に置くことまで止めるのは慎重すぎる」→ 現時点での判断であり、R-4 の観測で有効性が示され、5.8.6 が降りた後に再審議する道を ADR に残す

## R-4 評価と適合性

### 結論

- 旧案の評価(合成発話 240 件、正解ラベルは AI 3者の合議、人は未確認)は、**採用の根拠に使わない**。ADR の背景に「試行の記録」として残すに留める。根拠水準は E1 にも届かない扱い(実案件の観測がゼロで、正解が人の判断でない)
- 旧案の却下理由「本体も Claude で、確認する側と共通の原因を持つ」は使わない(3.5.4 `:664`、`template/CLAUDE.md:109`)。系統の違いを助言の強さの根拠にも、他の案を却下する理由にも書かない
- 採用者が助言を足す場合、3.12.3(回帰評価・記名承認・基準集合を自組織に置く・範囲の起案と承認の分離)を掛ける。**基準集合の正解ラベルは人が確定する**。AI の合議で作った正解を、基準集合の正解に数えない
- 有効化した案件では、次の観測を記録する。**閾値の固定値は課さない**
  - 助言の件数(期間あたり)
  - 助言が人へ戻すことにつながった件数(戻した記録 `state:needs-*` と突き合わせる)
  - そのうち、人が「役に立たなかった」と記録した件数(一操作で付けられる印)
- **有効化の時点で、無効化の条件(どの観測値で止めるか)と見直しの時期を、決裁の中に決めておく**。値は案件が決める。決めていない有効化を受け付けない

### 理由

- 現場では「評価をした」という事実が、評価の中身より強く効く。合成発話で工程 84.6% という数字は、実案件での振る舞いを何も示さない。数字だけが稟議に転記される(推測)。採用の根拠に使わないと明記しないと、旧案の数字が独り歩きする
- 基準集合の正解を AI の合議で作ることは、標準に書かれていない(内部 2.2)。IMPL-0153 は「合議の一致を検出の層・独立した確認に数えない」とする。評価の正解はそれ自体が「正しさの確認」で、合議で作れば同じ問題を持つ
- 観測は、手間の少ない形でなければ現場で続かない。助言ごとに採否を書かせる(H.4 条件5 型)と、1日数十件の記録になる。**機械が自動で取れるもの(件数、戻した記録との突き合わせ)と、人が一操作で付ける印(役に立たなかった)に絞る**。Tricorder の「NOT USEFUL」(外部 2.3)と同じ考え方
- 不作為の誤り(見逃し)は現場では測れない。正解が無いからである。見逃しの件数を差し替え条件に置く(旧 EV-0040)と、誰も数えられない条件になる。測れないものは測れないと書き、測れるもので無効化の判断をする
- 無効化の条件を事前に決めないと、「役に立たないが、止める決定を誰もしない」状態で常設になる。決裁は始めるときより止めるときのほうが通りにくい(推測)。始める決裁の中に止める条件を入れる

### 体制ごとに回るか

| 体制 | 回るか | 現場の見立て |
| --- | --- | --- |
| 1〜2名 | 人による正解ラベルの確定が回らない | 基準集合を人が作る時間が無い。3.12.3 を満たせない以上、使わないことになる。それで良い。観測は件数の自動集計だけなら回る |
| 3〜9名 | 条件つきで回る | 基準集合の範囲の起案(AI運用担当者)と承認(技術判断者)を分けられる。正解ラベルの確定は数十件なら回る(推測)。「役に立たなかった」の印は付け忘れが多い。件数と戻した記録の突き合わせを主にする |
| 10名以上 | 回る | 評価と観測の担い手を置ける。観測の集計を四半期の見直しに載せる |

### 譲れない点

1. 旧案の評価を採用の根拠に使わない
2. 系統・提供元の違いを、助言の強さの根拠にも却下の理由にも書かない
3. 基準集合の正解は人が確定する
4. 無効化の条件と見直しの時期を、有効化の決裁に含める
5. 閾値の固定値を標準で課さない

### 採らない案

- 旧案の評価を E1 として採用の根拠にする案。正解が人の判断でなく、実案件の観測がゼロ
- 助言ごとに採否を記録させる案(H.4 条件5 の全面適用)。発話の単位では記録が続かず、空の記録が並ぶ
- 見逃し件数を差し替え条件・観測項目に置く案。現場では数えられない
- 標準で閾値の値(例: 確信度 0.8)を定める案。提供者自身が固定の閾値を示さない(外部 1.3)

### 反論されうる点

- 「観測の印(役に立たなかった)は付けられないまま終わる」→ そのとおりになりうる。だから主の観測は機械が取る件数と戻した記録の突き合わせにし、印は補助にする。印が付かないことも、助言が読まれていない兆候として扱える
- 「1〜2名に事実上使わせないのは不公平」→ 3.12.3 を満たせないモデルを使ってはならない(`:1504`)は既存の規定。体制によらず同じ条件を掛けた結果である

## R-5 記録

### 結論

- 新しい ADR を起こす。番号は起票時点の main の最大の次(2026-11-04 時点で ADR-0103。EV・IMPL も同じく採番時点の最大の次)
- 決定の中身は「**確率的な分類器の助言の扱い**」(製品によらない)と「**準拠テンプレートへ同梱しない**」の2つ。製品名は背景に時点つきで書く
- 標準の本文に規定を置く。置き場は第5章(5.7 または 5.8 の近く。助言の出力の扱いと外部送信の条件)。実装マークを付け、テンプレートへは**常駐の規則の1〜2行**(助言を判定・記録の根拠にしない、出ないことを根拠にしない)だけを降ろす。部品は降ろさない
- 採らない案を ADR に明記する: 既定無効の同梱、別配布、名指し、検出の層に数える、送信ごとの承認、ZDR での許可、旧評価を根拠にする、系統の違いを理由にした却下
- オーナーの 2026-09-23「条件付きで採用」は、**条件の記録が無く、内容の確認(マージ)が成立していない事実**として ADR の背景に書く。そのうえで、本 ADR が採否の判断を置き換えることを書く。会議体の結論は同梱しない方向だが、**取り下げを決めるのはオーナー**であり、オーナーが本 ADR を承認することで旧判断の取り下げ(または変更)が記録される
- 再審議の契機を ADR に書く: 5.8.6 の既定拒否がテンプレートへ降りたとき、開発プロセスでの有効性の実証(外部の一次報告、または採用者の観測)が現れたとき

### 理由

- 「書かれていない」と「課さないと決めた」を区別するのがコアポリシー。同梱しない決定を記録しないと、半年後に同じ提案が同じ材料で出てくる(実際に #283 → #401 で起きている)
- 標準に規定を置く理由は、同梱の有無にかかわらず、採用者は確率的な助言を自分で足すから(Copilot のレビュー、DRS 型のリスク推定。外部 2.1)。足したときの位置づけと外部送信の条件は、本プロジェクトの部品の有無と独立に要る
- テンプレートへ部品を降ろさず規則だけを降ろすのは、現場でいちばん効くのがエージェントの常駐の規則だから。既存の行(`template/CLAUDE.md:105` の「AI の確認は検出の層」)は「確認」を対象にしており、発話の分類器の助言を覆うかは読みが割れる。既存の行を広げる形で、行数を増やさずに覆えるかを起草で検討する(RC-07 の制約)
- オーナーの判断の扱いを曖昧にすると、現場(本プロジェクトの次のセッション)は「採用済み」と「却下」のどちらで動けばよいか分からない。条件の記録が無いこと、マージされていないことは事実として書ける。採否の最後の決定はオーナーにしかできない

### オーナーにしか決められないこと

1. 旧判断(2026-09-23)を取り下げるか、条件を変えて維持するか
2. 本プロジェクトが、外部送信を伴う部品の保守(版の追随・提供者の規約の監視・攻撃面の監視)を将来負うか
3. 新しい ADR の承認(採用者の立場での採否は、採用者の事業決裁者・AI維持管理者・AI運用担当者が決める。本プロジェクトのオーナーが決めるのは、標準とテンプレートに何を置くか)

### 体制ごとに回るか

- 記録は本プロジェクト側の作業で、採用者の体制には依らない。採用者に効くのは、本文の規定(R-1・R-2・R-4 の条件)と常駐の規則の1〜2行。1〜2名の採用者にとっては、使わなければ追加の手間は常駐の規則を読むことだけで、負担は小さい

### 譲れない点

1. 同梱しないことを、採らない案として ADR に明記する
2. オーナーの旧判断を、条件の記録が無いこと・内容の確認が成立していないことを事実として書いたうえで扱う。会議体が代わりに取り下げを決めたと書かない
3. 標準の本文に、製品によらない規定を置く(ADR だけに留めない)

### 採らない案

- テンプレートの部品としての ADR に留め、標準の本文に規定を置かない案。採用者が自分で足す場合の条件が標準から読めない
- 旧 ADR-0054(案)を番号だけ付け替えて採る案。拠っていた規定のうち多くが変わった(内部 3)
- オーナーの旧判断を「採用済み」として扱い、条件を後から補う案。条件の記録が無く、後から補った条件はオーナーの判断ではない

### 反論されうる点

- 「同梱しないのに本文へ規定を置くのは、課す範囲を広げすぎ」→ 規定は「足すなら」の条件で、足さない採用者には何も課さない(R-1 の禁止は、助言を足した場合に掛かる)。適用範囲を見出しに併記する(#226 の書き方)
- 「常駐の規則に行を足すと RC-07 を超える」→ 既存の行の対象を広げる形を先に検討する。行数の制約は、規則を落とす理由ではなく、書き方を詰める理由

## 論点ごとの結論(1行)

- R-1: 助言はどの層でもない誘導に置き、判定・承認・遮断・完了・遷移と、出なかったことの根拠化を禁止する(常駐の規則にも置く)。「引き上げ」の語は使わない
- R-2: 有効化と範囲の変更を取り消せない操作の上流の操作とし、事業決裁者の中身のある常設決裁(失効条件つき)と 3.12.2・3.12.8・3.12.11・層1 項目4 を掛ける。5.8.6 が降りるまで外部送信の部品をテンプレートへ入れない
- R-3: 既定無効でも同梱せず、別配布もしない。製品を名指さず、採用者が足すときの製品によらない条件を標準に置く
- R-4: 旧評価は採用の根拠にせず、系統の違いを理由に使わない。基準集合の正解は人が確定し、件数と戻した記録の突き合わせで観測し、無効化の条件を有効化の決裁に含める。閾値は課さない
- R-5: 新 ADR(採番時点の最大の次)で「助言の扱い」と「同梱しない」を決め、本文に規定、テンプレートには常駐の規則だけを降ろす。旧判断は条件の記録が無い事実として書き、取り下げの決定はオーナーに委ねる
