## 1. Jev / TypeSafe AI の公開情報(2026-11-04 時点)

結論: 製品は実在し、一次情報(ローンチ記事・技術文書・DPA)が公開されている。ただし早期アクセス段階で、性能・較正の主張は自社評価に依存し、独立検証は乏しい。

### 1.1 製品の正体

- Jev は TypeSafe AI(米サンフランシスコ)の最初の「System One Model」。文章を生成せず、事前に定義した型つきの値を確率と確信度つきで返す、分類・判定用のモデル。早期アクセス段階 — [一次] TypeSafe AI「Introducing System One Models and Jev」 https://typesafe.ai/blog/introducing-system-one-models-and-jev (記事上の日付 2026-09-15。ページのメタデータは 2026-11-03)
- 想定用途は、通常のソフトウェア内の分類・ルーティング・採点・抽出・分岐、大量データ処理、リアルタイム処理、LLM 出力の検証やガードレール — [一次] 同上
- 入力は文字列または構造化された状態(state)と、型つきの質問の集合を 1 回で並列評価する。出力は Choice・Score・Noul の 3 種で、確率分布と確信度を持つ。閾値を超えたら実行し、下回ったらエスカレーションする使い方を想定。文脈長 32,000 トークン — [二次] InfoQ, Daniel Curtis, 2026-10-01 https://infoq.com/news/2026/10/typesafe-ai-jev-released
- 学習法は同社が RLCD(Reinforcement Learning for Calibrated Decisions)と呼ぶもの。「確信度が高いほど正答率が高い」ことを狙うと主張するが、較正の実測値は公開記事に示されていない — [一次] ローンチ記事 / [二次] KDnuggets, Abid Ali Awan, 2026-09-21 https://www.kdnuggets.com/what-everyone-is-getting-wrong-about-typesafe-ais-jev
- 「ハルシネーションなし」はスキーマ外の出力がないという意味で、誤ったラベルを選ばないという意味ではない — [一次] ローンチ記事(スキーマ一致に基づく主張と自認) / [二次] KDnuggets 同上
- ベンチマークは自社実施で、参照解は主に OpenAI・Anthropic のモデルの出力(真の正解ではない)。価格は補助されている可能性があり、長期の持続性は未証明と同社自身が書く — [一次] ローンチ記事
- 構造・学習設定・モデル規模は非公開。独立検証は小規模な第三者試験にとどまる。自社ワークフロー評価での正答率は約 68%(参照解は最先端モデル) — [二次] KDnuggets 同上

### 1.2 提供の形と版

- 提供はホスト型 API のみ(SDK・API・エージェント用 skill・Playground)。いずれも `TYPESAFE_API_KEY` で同社のホスト API を呼ぶ。公開の重み・自己ホスト版・オンプレミス導入手段は文書化されていない。企業向け VPC/オンプレミスは営業への問い合わせで、記事の著者は未確認 — [二次] Hora de Codar, 2026-10-13 https://horadecodar.com.br/?p=47570
- 別名 `jev-latest`・`jev-preview` は新版の出荷で指す先が変わり、**コード変更なしに答えが変わる**。応答の `model` 欄に版つき ID が返る。**確信度の閾値を特定の版で調整したなら版つき ID(例 `jev-1.14.0`)で固定することを推奨**。廃止(提供終了)方針は記載なし — [一次] TypeSafe docs「Models」 https://docs.typesafe.ai/models (2026-11-04 閲覧時点で `jev-latest` → `jev-1.14.0`)
- 第三者の統合(Pipecat の分類器、LiteLLM のパススルー、Vercel AI Gateway、Netlify、LangChain)が存在する — [二次] InfoQ 同上 / [未確認] https://reference-server.pipecat.ai/en/latest/api/pipecat.classifiers.jev.classifier.html 、 https://docs.litellm.ai/docs/pass_through/typesafe.md
- 互換 API を名乗る独立 OSS(MIT、別モデルで動く)も存在する — [二次] Hora de Codar 同上

### 1.3 既知の弱点(同社の自己申告)

- 問いを字義どおりに読む。否定・範囲語・暗黙の条件に弱い。計算・計数・日付の比較は不可で、コード側で行うべき — [一次] TypeSafe docs「Model jaggedness」 https://docs.typesafe.ai/model-jaggedness/jev-1.13 (版別ではなく一般の記述)
- **入力(state)を既定で敵対的とみなさない。注入・誤誘導の内容で答えが動く**。無関係な大きな入力は撹乱要因。選択肢の先頭に偏る — [一次] 同上
- 固定の閾値は示さない(例は `YES = 0.5` で「用途しだい」)。Score の段階間の補間はしないよう求める(数値の較正が弱い) — [一次] 同上
- 統合試験で偽の「事前承認」メモが遮断確率を 0.76 から 0.48 に下げたという報告(単発・コミュニティの試験で監査ではない) — [二次] NeuralTrust, Roger Howroyd, 2026-10-06 https://neuraltrust.ai/blog/jev-typesafe-ai-security

### 1.4 データの扱い

- 「Jev は顧客のリクエスト・レスポンスで学習しない」。顧客データでの微調整・LoRA 適応もしない。全アカウントが同じ重み — [一次] TypeSafe docs「Models」 https://docs.typesafe.ai/models
- DPA(最終更新 2026-04-24)の要点 — [一次] TypeSafe「Data Processing Addendum」 https://typesafe.ai/legal/data-processing
  - 保持期間: 「処理目的に照らして必要な限り」で固定期間なし(Schedule I §8)
  - 学習への利用: 直接の記述なし(文書化された指示に基づく処理に限定、目的外処理の禁止 §2.1–2.2)
  - ゼロデータ保持(ZDR): 記述なし
  - 再委託先: trust.typesafe.ai/subprocessors に掲示。追加は事前通知、15 日以内に異議可(§3)
  - 越境移転: EU SCC(Module 2/3、アイルランド法)と英国 IDTA 補遺(§6)。ホスティング地域の明記なし
- ZDR は企業顧客向けで営業経由との記述(docs は Legal ページへ誘導)。ホスティングは米国のみで EU 地域の選択肢は見当たらない。同社文書から認証(SOC 2・ISO/IEC 27001 等)を確認できない(SOC 2 Type II は第三者索引の情報で未確認)。72 時間の侵害通知、12 か月に 1 回の監査 — [二次] NeuralTrust 同上
- **読めなかったもの**: Trust Center(trust.typesafe.ai)、Master Customer Agreement、Privacy Policy の原文、企業向け ZDR の条件

## 2. 確率的分類器を開発プロセスの「助言」に使う実務と研究(2025〜2026)

### 2.1 実務の先例

- **Meta の Diff Risk Score(DRS)**: 微調整した Llama で、コード変更が重大障害(SEV)を起こす確率を推定し危険箇所を示す。用途はコードフリーズ中の低リスク変更の投入(**緩和方向**)、レビュアー選定、ビルド・テスト選択、リリースのリスク分析。誰が最終判断するか・閾値・較正は公表されていない — [一次] Engineering at Meta, 2025-08-06 https://engineering.fb.com/2025/08/06/developer-tools/diff-risk-score-drs-ai-risk-aware-software-development-meta/
- 同系統の論文: 上位 5%・10%・50% の危険な diff をゲートすると SEV のそれぞれ 18.7%・27.9%・84.6% を捕捉(ベースラインの回帰モデル)。BERT 系はロジスティック回帰に劣った。入力は diff の題名・テスト計画・コード変更 — [一次] 「Moving Faster and Reducing Risk: Using LLMs in Release Deployment」arXiv 2410.06351(ICSE 2025 SEIP) https://arxiv.org/abs/2410.06351
- **DRS-OSS**: Llama 3.1 8B の系列分類器。GitHub App がリスクのラベルと確信度を PR に付け、レビュー能力に応じて閾値を調整できる。エスカレーションの仕組みは確認できず — [一次・要旨] arXiv 2511.21964(2026-01 改訂) https://arxiv.org/abs/2511.21964
- AI 生成 PR のレビュー工数を早期予測し、レビュー予算 20% で高コスト PR の 3 分の 2 超を捕捉 — [一次・要旨] arXiv 2601.00753 https://arxiv.org/abs/2601.00753
- **GitHub Copilot のコードレビュー**: 既定で「Comment」レビューを残し、必須承認数に数えない。各レビューの「承認可否の評価」も単独ではマージ要件に数えない。**ただし 2026-11-04 時点で、設定により Copilot の Approve が必須承認を満たせる機能がある**(既定は無効、企業・組織・リポジトリ単位で設定、パス単位で数えるか制御、新コミットで承認は取り消し) — [一次] GitHub Docs「Using GitHub Copilot code review」 https://docs.github.com/en/copilot/how-tos/use-copilot-agents/use-code-review (2026-11-04 閲覧)
- 開発プロセスの「作業フェーズの判定」に確率的分類器を使った一次の実務報告は見つからなかった

### 2.2 自動化バイアス・過信の研究

- 自動化バイアスは「注意深い情報探索・処理を発見的に置き換えること」。誤った助言に従う**作為の誤り**(commission)と、システムが促さなかったため行動しない**不作為の誤り**(omission)がある。医療の 4 研究の統合で、誤った CDSS 助言は誤判断のリスクを 26% 高めた(RR 1.26、95%CI 1.11–1.44) — [一次] Goddard, Roudsari, Wyatt「Automation bias: a systematic review of frequency, effect mediators, and mitigators」JAMIA 19(1), 2012 https://pmc.ncbi.nlm.nih.gov/articles/PMC3240751
- 同レビューの緩和策: 助言ごとに更新される確信度の提示は、固定の確信度より適切な依存を促した。命令(推奨)ではなく情報として示すことが自動化バイアスを減らしうる。説明責任の付与は効果が混在 — [一次] 同上
- 自動化への慢心(complacency)と自動化バイアスは注意を共通の根に持つ重なった現象。多重課題の負荷下で起き、熟練者にも生じ、単なる練習では克服できない — [一次・要旨] Parasuraman & Manzey「Complacency and Bias in Human Use of Automation」Human Factors 52(3), 2010 https://pubmed.ncbi.nlm.nih.gov/21077562/
- LLM 支援開発では、観察した開発者の行動の 48.8% にバイアスがあり、その 56.4% が LLM とのやり取りに関わった(14 名観察+22 名調査) — [一次・要旨] Zhou ほか「Cognitive Biases in LLM-Assisted Software Development」arXiv 2601.08045(ICSE '26) https://arxiv.org/abs/2601.08045 (自動化バイアスの扱いは要旨から確認できず)
- 自動コードレビューの実務調査で、ボットのレビューがあると人が他の問題の確認を省くとの回答があり、重大欠陥の見逃しにつながると警告 — [一次・要旨] arXiv 2412.18531「Automated Code Review In Practice」 https://arxiv.org/abs/2412.18531
- 「熟練開発者ほど自動化バイアスが強い」「2025 年の 89 研究のレビュー」などの主張は二次資料のみで原典を辿れなかった — [未確認]

### 2.3 警告疲れ

- Google の Tricorder は、利用者側から見た誤検知を「見たくなかった報告すべて」と定義し、「NOT USEFUL」ボタンで継続的に測る。誤検知率を十分低く保つことを解析器の作者との契約とし、高いものはコードレビューに出さず夜間実行へ回す — [一次・要旨] Sadowski ほか「Tricorder: Building a Program Analysis Ecosystem」ICSE 2015 https://research.google/pubs/pub43322/
- 「誤検知率約 10% を超える解析器は無視・無効化される」という数値は二次資料でのみ確認 — [未確認]
- 静的解析の警告の 35〜91% が誤検知という既往推定を引き、実行不能な警告の量で開発者がツールを放棄しうると述べる — [一次・要旨] arXiv 2604.18525(EASE 2026 予定) https://arxiv.org/html/2604.18525

### 2.4 「引き上げのみ」の非対称な設計の先例

- 医療トリアージでは「過剰トリアージは時間を浪費し、過少トリアージは命を失わせる」という非対称から、赤旗の症状はモデルの確信度に関わらず無条件に上位へ回す設計が語られる(ベンダーの主張) — [二次] Fora Soft https://www.forasoft.com/learn/telemedicine/glossary/terms-telemedicine/ai-triage
- LLM は訓練されたトリアージ専門職に全比較で劣り(κ=0.54–0.67)、系統的に過剰トリアージした。著者は AI が人の判断を補う形を支持 — [未確認] JMIR 2026 https://www.jmir.org/2026/1/e88396/PDF (検索要約のみ)
- チケット管理の「優先度の引き下げ防止」: 人が付けた高い優先度を自動で戻し、自ら引き上げはしない、という一方向の規則 — [二次] Thread「Priority downgrade guard」 https://helpdocs.getthread.com/skill-library/triage-and-routing/priority-downgrade-guard
- **ソフトウェア開発のプロセス規格・ガイドで「AI の助言は引き上げ方向にだけ使う」と定めた一次資料は見つからなかった**
- 逆向きの先例として、Meta DRS はリスクスコアを**緩和方向**(フリーズ中の投入許可)に使っている — [一次] 2.1 の Meta 記事
- FDA は「生命に関わる状態を検知して HCP に警報を出す」機能を、時間的切迫と特定の出力・指示を理由に非医療機器 CDS の基準 3・4 を満たさない(=規制対象の機器)と例示する。**警報(引き上げ)であっても判断を方向づける出力として扱われる** — [一次] FDA CDRH ウェビナー資料「Clinical Decision Support Software, Final Guidance」2026-03-11 https://www.fda.gov/media/191561/download (スライド 33–35)

## 3. 開発の文脈を外部 AI サービスへ送ることの統制

### 3.1 個人情報保護法(日本)

- 個人情報保護委員会は 2023-06-02、生成 AI サービスの利用について注意喚起。個人情報取扱事業者がプロンプトに個人情報を入力する場合は利用目的の範囲内かを確認すること、本人同意なく個人データを入力し、それが応答の出力以外の目的で取り扱われる場合は法違反のおそれがあること、を示した — [一次] 個人情報保護委員会「生成AIサービスの利用に関する注意喚起等について」2023-06-02 https://www.ppc.go.jp/news/press/2023/230602kouhou/ (本文 PDF は取得したが文字抽出できず、要旨は報道で補った: [二次] ScanNetSecurity https://scan.netsecurity.ne.jp/article/2023/06/13/49506.html )
- クラウド例外(Q&A 7-53): 第三者提供・委託に当たるかは「保存データに個人データが含まれるか」ではなく「クラウド事業者が当該個人データを**取り扱うこととなっているか**」で判断する。取り扱わない例は、契約条項で取り扱わない旨を定め、適切にアクセス制御している場合。法 28 条(外国にある第三者)との関係は Q&A 12-3 を参照 — [一次] 個人情報保護委員会 Q&A 7-53 https://www.ppc.go.jp/all_faq_index/faq1-q7-53/
- クラウド例外の当てはめを誤って行政指導を受けた事例(2024)が解説されている — [二次] 検索要約(弁護士事務所の解説 PDF) https://miyake.gr.jp/wp-content/uploads/2024/05/ (原文未読) — 日本の実務で「クラウドだから提供に当たらない」という建前が実態と乖離しうる例
- AI 事業者ガイドラインは総務省・経済産業省の自主的取組の参考指針。第 1.1 版(2025-03-28)、第 1.2 版(2026-03-31)— [二次] 検索要約 https://www.soumu.go.jp/main_content/001002576.pdf (入力データの外部送信に関する記述は本調査で確認できず)

### 3.2 EU AI Act

- 第 14 条 4 項: 高リスク AI システムの人の監督の措置は、監督者が (a) 能力と限界を理解し異常を検知でき、(b) **出力に自動的に依存・過依存する傾向(自動化バイアス)を自覚し続けられる**(とくに自然人の判断のための情報・推奨を出すシステム)、(c) 出力を正しく解釈でき、(d) 使わない、または出力を無視・上書き・取り消す判断ができ、(e) 停止できる、ようにする — [二次・条文転載] https://artificialintelligenceact.eu/article/14/ (原典は Regulation (EU) 2024/1689。EUR-Lex 原文は未取得)
- 開発プロセス内の助言用分類器は、通常は附属書 III の高リスク用途に当たらないと考えられるため 14 条は直接は掛からない(考察。当てはめは要確認)
- Digital Omnibus により附属書 III の高リスク義務の適用は 2027-12-02、製品組込みは 2028-08-02 へ延期する暫定合意(2026-05-07)。官報掲載の確認はできていない — [二次] Gibson Dunn ほか https://www.gibsondunn.com/eu-ai-act-omnibus-agreement-postponed-high-risk-deadlines/

### 3.3 ISO/IEC 42001・NIST AI RMF

- NIST AI RMF 1.0 の該当サブカテゴリ — [一次] NIST AIRC「AI RMF Core」 https://airc.nist.gov/airmf-resources/airmf/5-sec-core/
  - GOVERN 3.2: 人と AI の構成(human-AI configurations)における役割と責任を定義し区別する方針・手順
  - GOVERN 6.1: 第三者に関わる AI リスク(知財侵害等を含む)に対処する方針・手順
  - GOVERN 6.2: 高リスクとされる第三者データ・AI システムの障害・インシデントへの緊急時対応
  - MAP 3.5: 人の監督のプロセスを組織方針に従って定義・評価・文書化する
  - MAP 4.1 / 4.2: 第三者のデータ・ソフトウェアを含む構成要素の技術・法的リスクの把握と、内部統制の特定・文書化
  - MANAGE 3.1 / 3.2: 第三者資源のリスクと便益を定期的に監視し、統制を適用・文書化する。開発に使う事前学習済みモデルを監視・保守の一部として監視する
- ISO/IEC 42001:2023 附属書 A は A.2〜A.10 の 9 管理目的・38 管理策。A.7 は AI システムのデータ(品質・来歴)、A.9 は AI システムの利用(責任ある利用のプロセス A.9.2、目的 A.9.3、意図した利用 A.9.4)、A.10 は第三者・顧客との関係(価値連鎖の責任配分 A.10.2、供給者 A.10.3、顧客 A.10.4) — [二次] Modulos ほか https://docs.modulos.ai/frameworks/iso-42001/annexes-a-d.html (規格原文は未読。附属書 A の規範性について二次資料間で記述が食い違う)
- IEEE 3119-2025(AI と自動意思決定システムの調達): 問題定義、募集準備、ベンダー・解決策の評価、契約交渉、契約監視の手順を定める。商用 AI 製品・サービスの購入を対象とし、内製は対象外 — [一次・要旨] IEEE SA https://standards.ieee.org/ieee/P3119/10729/ (2025-05-23 発行)

### 3.4 ゼロデータ保持(ZDR)の実務

- Anthropic の例: ZDR は組織単位で審査・適用され、対象は適格な API、商用組織の API キーで使う製品(API 経由の Claude Code を含む)、Enterprise プランの Claude Code に限られる。ベータ製品等は対象外で、Files API は ZDR に関わらず削除まで保持される — [一次] Anthropic Privacy Center https://privacy.claude.com/en/articles/8956058-i-have-a-zero-data-retention-agreement-with-anthropic-what-are-the-exceptions
- **ZDR は「契約の有無」の二値ではなく、製品・機能・組織ごとの適用範囲を持つ**(上記一次資料からの読み取り)
- 2026 年の最先端モデルで ZDR の適用外・後に例外承認という経緯の報道がある — [二次・未確認] https://www.cxtoday.com/?p=992747

## 4. 規格・ガイドにおける「AI の推奨・助言」と人の判断の分担

- **FDA の非医療機器 CDS 基準 4**(21st Century Cures Act 520(o)(1)(E)(iii)): 医療者が推奨の根拠を独立に吟味でき、推奨に「主として依存」しないことを意図した機能であること。満たすために、意図した利用と利用者、必要な入力、アルゴリズムの開発・検証の平易な説明(手法、データ、検証結果)、既知・未知の事項の提示を推奨する。判断に際し**自動化の水準**と**判断の時間的切迫**を考慮し、自動化バイアス(作為・不作為の誤り)の理解がこの解釈を支える、と明記 — [一次] FDA CDRH ウェビナー資料 2026-03-11 https://www.fda.gov/media/191561/download (最終ガイダンス 2026-01-06、2026-01-29 再発行。ガイダンス本文は未取得)
  - 「助言を判定に数えない」に最も近い規制上の規範。助言が「判断を置き換えない」ことを、表示内容と時間的余裕で担保させる
- **EU AI Act 第 14 条 4 項 (b)(d)**: 自動化バイアスの自覚と、出力を無視・上書き・取り消す能力の確保(3.2 参照)
- **NIST AI RMF GOVERN 3.2 / MAP 3.5**: 人と AI の構成における役割の区別、人の監督プロセスの定義・評価・文書化(3.3 参照)
- **ISO/IEC TS 8200:2024**(自動 AI システムの可制御性): 状態の可観測性と状態遷移、制御移譲の過程とコスト、制御移譲時の不確かさへの対応、検証と妥当性確認を扱う — [一次・要旨] IEC Webstore https://webstore.iec.ch/publication/94106 (本文未読)
- **ISO/IEC 23894:2023**: 目次に附属書 B「B.4 Level of automation」があり、自動化の水準をリスク源として扱う — [二次・目次] Standards Australia https://store.standards.org.au/product/as-iso-iec-23894-2023 (本文未読。自動化バイアスへの言及は確認できず)

## 5. 規格が特定の製品・サービスを同梱・推奨することの作法(規格の中立性)

- **ISO/IEC Directives Part 2(第 9 版、2021-05)第 31 条「商品名及び商標の使用」** — [一次] ISO/IEC DIR 2:2021 RLV https://www.cta.tech/media/1ebl2xah/iso-iec-directives-part-2.pdf
  - 商品名・商標ではなく、製品の正しい名称または記述を示す(shall)。広く使われていても特定製品の商品名は可能な限り避ける(should)
  - 例外的に避けられない場合は ® / ™ で性質を示す
  - **適用に適した製品が現に 1 つしかないと分かっている場合に限り**商品名を本文に書けるが、「利用者の便宜のための情報であり ISO/IEC による当該製品の推奨ではない。同じ結果につながることを示せれば同等の製品を使ってよい」旨の脚注を付ける
  - 特性の詳細な記述が難しい場合は、適した市販製品の「例」を脚注に書ける(推奨ではない旨を付記)
  - 第 9 版で、公共の利益・公共の安全を理由とする場合の記載を追加
- 同 5.4(性能原則): 要求は可能な限り設計・記述でなく性能で表す。性能特性を決められず材料・製品を指定する場合は「…又は同等に適すると証明された他の材料・製品」の文言を含めるべき — [一次] 同上
- 同 18.5.4: 単一の製造者による機器は可能な限り指定しない。入手容易でない場合は、全当事者が比較可能な試験を行えるだけの仕様を書く — [一次] 同上
- 同 10.2: 引用規格(normative reference)は公開され、無償または公正・合理的・非差別的な条件で入手できる文書に限る — [一次] 同上
- 同 33.1(中立性原則): 製品・プロセス・サービス等の要求を含む文書は、第一者・第二者・第三者のいずれでも適合性を評価できるように書く — [一次] 同上
- 同 4: 文書は契約上の要求や法令上の要求を含めない — [一次] 同上
- ETSI も商品名・商標を避け、対応する規格・正しい名称・一般的な記述を使うよう求める(例: ZigBee® ではなく IEEE 802.15.4™) — [一次] ETSI editHelp! https://portal.etsi.org/Services/editHelp!/Tohelpyouinyourwork/Useandreproductionoftext,signsandmateriallegallyprotected/Tradenamesandtrademarks.aspx
- 実際の ISO 規格では「本書で使われる商品名は利用者の便宜のための情報であり推奨ではない」旨の定型文が使われる — [二次・抜粋] ISO 5284:2025 プレビュー https://webstore.ansi.org/preview-pages/ISO/preview_ISO+5284-2025.pdf
- **見つからなかったもの**: IPA が文書中で特定製品を扱う際の作法(「特定の製品を推奨するものではない」旨の定型)の一次資料。JIS Z 8301(規格票の様式)の商品名に関する条項の原文(第 2019 版が Directives Part 2 との差異を踏まえ改正されたことのみ確認 [二次] https://webdesk.jsa.or.jp/preview/pre_jis_z_08301_000_000_2019_j_ed10_ch.pdf )

## 考察(事実ではなく本調査者の解釈)

### A. 「引き上げ方向の助言にだけ使う」設計の評価

- 非対称化の効果は「誤った助言で緩む」作為の誤りを構造的に塞ぐことにある。Jev が注入で遮断確率を下げうる(1.3)ことを考えると、**助言が下げ方向に効かない設計は、注入の被害を「助言なし」と同じ水準に抑える**。この点で条件は理にかなう
- 一方、Goddard(2.2)と FDA(2.4・4)が示すとおり、自動化バイアスには不作為の誤りがある。引き上げのみの設計では、**「引き上げられなかった」ことが暗黙の「安全」の信号として読まれる**危険が残る。注入で引き上げが抑えられた場合はまさにこの経路で見逃しが生じる。したがって「助言の不在を、引き下げ・省略の根拠に数えない」ことまで明文化しないと、非対称の効果は半分しか得られない
- 警告疲れ(2.3)の先例は、引き上げが多すぎると人が助言全体を無視・無効化することを示す。引き上げのみの設計は偽陽性を許容しやすいため、**引き上げの頻度と、引き上げが実際に役立った割合を観測する**仕組みがないと、既定無効のまま放置されるか、有効化しても形骸化する。日本の組織で「導入した」という建前と「誰も見ていない」実態が乖離する典型の経路でもある(実証データは本調査で見つけていない)
- GitHub Copilot の例(2.1)は、「助言は承認に数えない」という境界が、ベンダーの機能追加で設定 1 つにより越えられるようになる実例である。準拠テンプレートが助言の位置づけを定めても、**下層のツール設定で境界が崩れていないかを確認する記録**が要る

### B. Jev を名指しで同梱することの評価

- Directives Part 2 第 31 条の基準に照らすと、「適した製品が現に 1 つしかない」場合に当たらない(確率的分類は汎用 LLM や OSS の分類器でも実現でき、Jev の互換 OSS も存在する)。規格本文での名指しは原則に反し、例示にとどめるなら「推奨ではない」「同等品可」の注記が要る
- 製品側の事実(早期アクセス、価格補助の可能性、廃止方針の不記載、別名による無告知の挙動変化、ZDR が DPA にない、ホスト地域の選択肢なし、認証の未確認)は、いずれも**規格の寿命より短い時間軸で変わりうる**。版固定・許可リスト・閾値の人による較正という条件は、製品固有の事実(1.2・1.3)に正しく対応しているが、それは「この製品を使うなら」の運用要件であり、規格の条項としては製品名を外した性能・統制要件に書き直すべき対象と考えられる
- 送信先が米国のホスト API で処理を行う以上、Q&A 7-53 のクラウド例外(取り扱わない契約+アクセス制御)に当たる余地は小さく、委託または外国にある第三者への提供として整理する必要が生じうる(法的判断は専門家の確認を要する)。「3 記録がそろうまで送信しない」条件は、この整理を組織に強いる点で妥当

### C. 拡張(フック・MCP)に外部送信を含めることの評価

- 2025〜2026 の事件(3.5)はいずれも、「導入済みの信頼された拡張・CLI が、更新や設定ファイル経由で送信先・権限を変える」形である。既定無効・版固定・許可リストは対策として正しい方向だが、**拡張自体の更新(依存パッケージの版)と、リポジトリ内の設定ファイル(`.mcp.json` 等)を PR で変えられること**まで統制しないと、許可リストの外への送信は防げない(CVE-2026-47751 はまさに PR 経由の設定差し替え)

## 規格として課せること / 課すべきでないこと(根拠つきの提案。審議の材料であり決定ではない)

### 課せること(性能・統制として書ける)

1. **助言は判定・承認・遮断・完了に数えない**ことを規範として課す。根拠: FDA 基準 4(推奨に主として依存しない)、EU AI Act 14 条 4 項 (d)(出力を無視・上書きできる)、GitHub Copilot の既定(Comment は承認に数えない)
2. **助言の不在を、確認の省略・リスク区分の引き下げ・ゲートの通過の根拠に数えない**ことを課す。根拠: 不作為の誤り(Goddard 2012、FDA 2026)、注入による引き上げの抑制(Jev の自己申告と NeuralTrust の報告)
3. **外部送信を伴う助言は既定無効とし、有効化には組織の記録(外部送信の決裁・ツール採用・モデル採用)を要する**ことを課す。根拠: PPC 注意喚起(利用目的・目的外利用の確認)、Q&A 7-53(取り扱いの有無で判断)、NIST AI RMF GOVERN 6.1・MAP 4.1/4.2、IEEE 3119 の調達手順、ISO/IEC 42001 A.10(二次資料)
4. **送信先の許可リスト、モデルの版の固定、版の変更時の閾値の再較正を人が行い記録する**ことを課す。根拠: Jev 自身が版固定と用途別の閾値を求めている(一次)、NIST MANAGE 3.2(事前学習済みモデルの監視)
5. **助言の有効性の観測**(引き上げの件数、引き上げが人の判断を変えた割合、無視された割合)を記録として課す。根拠: Tricorder の「NOT USEFUL」と誤検知率の契約、警告疲れの研究。ただし閾値の数値は実証がないため課さず、根拠水準マーク(暫定)での提示にとどめるべき
6. **拡張の設定ファイル・依存の版の変更を、外部送信先の変更として扱う**ことを課す。根拠: CVE-2026-47751、postmark-mcp、s1ngularity、MCP 仕様のローカルサーバー構成時の同意要件(MUST)

### 課すべきでないこと(採らない理由)

1. **特定製品(Jev / TypeSafe)を規格本文で名指し・推奨・必須化しない**。根拠: ISO/IEC Directives Part 2 第 31 条(適した製品が 1 つしかない場合に限る)、5.4(性能原則と「同等品」の文言)、18.5.4(単一製造者の指定を避ける)、33.1(中立性原則)。テンプレートの例示に残す場合も「推奨ではない・同等品可」の注記と、製品事実の時点(2026-11-04 時点)を併記すべき
2. **助言の確信度に固定の閾値を規格で定めない**。根拠: Jev 自身が固定閾値を示さず用途依存とし、Score の数値較正の弱さを認めている(一次)。較正の実測は非公開
3. **助言の利用を義務化しない**(使わない選択を適合の妨げにしない)。根拠: 自動化バイアス・警告疲れの研究が示す副作用、EU AI Act 14 条 4 項 (d)(使わない判断の確保)
4. **ZDR 契約の存在だけで外部送信を許す形にしない**。根拠: ZDR は製品・機能・組織ごとの適用範囲を持ち例外がある(Anthropic の一次資料)。TypeSafe の DPA には ZDR の記述がない
5. **法令の適合(個人情報保護法の整理など)を規格の要求事項として書かない**。根拠: Directives Part 2 第 4 条(法令上の要求を含めない)。法令は外部制約として参照するにとどめる
