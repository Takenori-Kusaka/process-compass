## R-1 位置づけ

### 結論

1. 確率的な分類器の助言は、**検出の層に数えない。どの層にも数えない誘導(注意の喚起)として位置づける**。判定・承認・遮断・完了・ラベルの遷移・「該当しない」の結論のいずれにも数えない
2. **助言が出ないこと(注意の不在)を、確認の省略・リスク区分の引き下げ・ゲートの通過・人へ戻さないことの根拠に数えない**。この不作為の側を、作為の側(誤った助言に従う)と同じ強さで明文化する
3. 助言の有無・件数・内容を、**判定記録・保証の開示・PR の本文に、確認の強さの根拠として書かない**(3.5.4 帰結4 の「系統の違いを根拠として書かない」と同型の禁止)
4. 「引き上げ」の語を使わない。「**人へ戻す側に限る助言**」と書く。5.4.5・5.5.7 の「引き上げ」は統制を緩める向きの語であり、同じ語で逆の向きを表すと監査で読み違える
5. 人へ戻す側に限る、という限定は**出力の種別ごとに確かめる**。旧案の「工程の候補」はエージェントの作業を誘導する出力で、人へ戻す側に限られない。人へ戻す側に限れない出力は、この位置づけの対象から外す(=出さない)

### 理由

- 検出の層に数えるなら H.4 の5条件が掛かる。条件1(欠陥注入による検出率の測定と開示)は、発話の分類では「欠陥」の定義から立たない。条件5(指摘の内容と採否の記録)を満たすには、注意ごとに人の採否を残す必要がある。いずれも旧案に無く、作れる見込みも示されていない。**数えないと書くほうが、監査で確かめられる主張になる**。数える主張は、条件を満たした記録が無い限り監査で「条件未確認」(IMPL-0075、観点22)として崩れる
- 不作為の誤りは実証がある(外部 2.2: Goddard 2012 の omission、FDA 2026 の CDS 基準4 が作為・不作為の両方を明記)。分類器は注入で遮断の確率が下がりうる(外部 1.3: 製品の自己申告と NeuralTrust の単発の報告)。**人へ戻す側に限る設計は作為の害を塞ぐが、注入で注意が抑えられた場合の被害は「注意が出ない=問題なし」と読まれる経路でだけ生じる**。2 を書かなければ、非対称の設計の効果は半分しか得られない(外部 考察A)
- 本標準には同型の規定が既にある。5.8.6 要求事項9「拒否が0件であることを、想定外の操作が無かったことの根拠として記録してはならない」。これと整合する
- 3 は、Copilot のレビューが設定一つで必須承認に数えられるようになった実例(外部 2.1)への備えである。「判定に数えない」と書いても、下流の記録が助言を根拠として引けば境界は崩れる。**記録の側で禁止しないと、監査は境界の崩れを見つけられない**
- 5 について: 工程の候補を受けたエージェントが、仕様の承認(G-4)を経ずに実装のスキルへ進む方向に働く余地がある。これは人へ戻す向きではなく、作業を先へ進める向きである。旧 ADR は決定4 で G-4 の照合をコードで行うとしたが、その照合は ADR-0070 の後の記録の置き場では構造上常に「見つかりません」を出す(内部 §3 の表)。照合が壊れたまま候補だけが出る状態は、監査上いちばん悪い

### 監査で確かめられること

- 判定記録・保証の開示・PR の本文・承認レビューの本文に、助言(分類器の出力・注意の有無・件数)を確認の根拠として引いた記述が無いか(抜き取り。記述の意味の判定なので機械で決めない。5.7.4)
- 「注意なし」「助言なし」の旨を、確認を省いた理由・区分を下げた理由・人へ戻さなかった理由として書いた記述が無いか
- 助言の出力の種別ごとに、人へ戻す側に限られていることの説明が記録にあるか(種別の一覧と、各種別の向き)
- 助言の仕組みのログが、判定記録の材料として引かれていないか

### 採らない案

- **検出の層として数える**: H.4 の条件1・5 を満たす手段が示されていない。数えると保証の開示に「AI の層」が載り、条件未確認のまま検出率を主張する形を招く
- **「助言は人の判断を補う」とだけ書き、数えない対象を列挙しない**: 判定・承認・遮断・完了・ラベルの遷移・「該当しない」の結論、のどれに数えないかを列挙しないと、監査は個々の記録が違反かを決められない
- **「引き上げ方向」の語を定義して使い続ける**: 同じ語を標準の中で逆の向きに使う状態を固定する。「人へ戻す」は 5.5.1 にある語で、新しい定義を要しない
- **工程の推定を「引き上げ方向」に含めて残す**: 向きを確かめられない出力を、向きを限ったという主張の下に置くことになる

### 反論されうる点

- 「どの層でもない誘導なら、そもそも標準が規定する必要は無い」。応答: 規定しないと、助言が判定・承認の代わりに読まれる経路と、不在が安全の信号に読まれる経路を、監査が違反として指摘できない。規定の対象は助言の仕組みの効果ではなく、**記録の側での扱い**である
- 「不在を根拠にしないと書いても、人の頭の中の依存は防げない」。応答: そのとおりで、記録で確かめられるのは書かれた理由だけである。頭の中の依存は R-4 の観測(注意の要らない発話への誤警報率、見逃し)でしか近づけない。**防げない部分があることを根拠水準マーク(E1、外部 2.2 の医療の研究からの類推)で開示する**
- 「人へ戻しすぎる誤警報も害ではないか」(5.5.1 の担い手が決めてよい選択、5.7.5 の摩擦の総量)。応答: 害である。人へ戻す側に限ることは、誤警報の害を消さない。R-4 の観測で扱う

## R-2 外部送信

### 結論

1. 発話ごとの自動送信は、**取り消せない操作に当たる**(第三者への送信。取り消せない時間帯が生じる。ADR-0053 決定3)。送信ごとに人が自ら行う操作が介在しないため、5.5.1 の「後段が人でない経路では、上流の操作が取り消せない操作に当たる」により、**有効化(と、送信先・送るデータの種別・版の変更)が取り消せない操作に当たる**
2. 常設の事前決裁は**認める**。ただし決裁が覆う範囲を記録に固定する: 送信先、送るデータの種別(発話本文・貼り付け・構成値)、モデルの版、フックのコードの要約値、見直しの期限。**このいずれかが変わったら決裁をやり直す**。無期限・範囲の無い決裁は認めない
3. 決める席: 有効化(取り消せない操作)の決裁は**事業決裁者**。外部ツールの採否は **AI維持管理者**(3.11.2、5.5.6)。モデルの導入の承認と接続経路は **AI運用担当者**(3.12.2・3.12.3)。基準集合の範囲は AI運用担当者の起案と技術判断者の承認(3.12.3 要求事項10)。旧案の「オーナー」は席の名でないので使わない。1 人が兼ねる体制では、どの席で判断したかを記録して受け付ける(ADR-0057 補足 S50)
4. **端末から API キーで提供者へ直接つなぐ形は、3.12.2・3.12.8 に適合しない**。接続は AI運用担当者が用意した経路を通す。機密情報の送出の検査は、接続経路の上に置く(3.12.8 要求事項2)。クライアント側の正規表現による秘匿情報の検出は、補助にはなるが要求事項2 を満たしたことにならない。学習利用の有無と保持期間は確認して記録する(3.12.8 要求事項3)。保持期間が「必要な限り」で固定期間の無い提供者は、その事実を記録したうえで決裁の材料にする
5. 有効化した案件では、提供者を**依存先の一覧(3.12.11)へ載せる**。渡すデータの種別と保持の条件の欄を埋める
6. **5.8.6 要求事項1・3(許可していない外部への通信の拒否、ネットワークの既定拒否)が準拠テンプレートへ降りる前(IMPL-0200 が undelivered の間)に、外部送信の部品をテンプレートへ入れない**
7. 層1 項目4「AI の利用の拡大」へは**読み込まない**。テンプレ11 は拡大の判断点を「AI自律レベルの引き上げと委任の範囲の登録」と定めている。分類器の有効化はこのどちらでもない。組織の統制は 3.12.2 の経路(AI運用担当者)と 3.12.3 の導入の承認で届ける。読み込むか否かを解釈に任せず、**ADR に「数えない」とその理由を書く**

### 理由

- 1 は、5.5.1 の定義(2026-10-23、ADR-0078 決定2)の素直な当てはめである。送信の主体がエージェントではなくフックである、という読みで 5.5.1 の外に置く余地は内部 2.4 が指摘する。しかし 5.5.1 の定義は「取り消せない効果を、他の者の操作を介さずに生じさせる操作」で、主体を担い手に限っていない。フックを置いた構成の有効化は、人の操作を介さずに送信を生じさせる上流の操作である。**主体の読みで外に置くと、エージェントにやらせれば人へ戻す送信を、フックにやらせれば戻さなくてよい、という抜け道になる**
- 2 で常設の決裁を認めるのは、送信ごとに人へ戻すと発話のたびに人へ戻ることになり、5.7.5(摩擦の総量)に正面から反し、形骸化した承認の印だけが残るためである。類例は 5.5.4 の「本番環境への反映の承認」(登録時の記名による事前承認)。ただし類例は、登録した範囲の外を受け付けない構造を持つ。**範囲を固定しない常設の決裁は、後から送信先やデータの種別が変わっても誰も決め直さない状態を作る**。拡張の設定を PR で差し替えて送信先を変えた実例(外部 3.5: CVE-2026-47751、postmark-mcp)があるため、フックのコードの要約値まで範囲に含める
- 旧案は 3 記録を「文字列が空でないか、仮の値でないか」だけで照合した(内部 1.2、コード `unapproved()`)。**任意の文字列で送信が始まる**。監査から見ると、記録の欄は存在しても記録の実在と記名者を確かめられない。決裁の記録は、所在(判定記録・承認レビューの URL など)を指し、記名者がその席の責任者であることを照合できる形でなければ、監査の証跡にならない
- 4: 3.12.2 は 2026-08-05 から存在し、旧 ADR は引いていない(内部 2.4)。正規の経路は「統制を規程でなく実行環境として届ける」ための前提で、端末から直接つなぐ形は経路の上の記録(消費の実績、送出の検査)を全て失う。監査は手元のログに頼れない(3.12.2 は手元のログを判定が読む記録としない)
- 6: 旧案の許可リスト(`allowedEndpoint`)はフックのコード内の自己規制で、5.8.6 要求事項2 の「実行環境の設定(強制層)」に置いた拒否ではない。現行のテンプレートは `curl` も node の `fetch` も限らない(内部 2.4)。**外への通信を限らない環境へ、外へ送る部品を先に入れると、許可リストの効き目をフックのコードの正しさだけに頼ることになる**。順序を逆にする理由が、信頼性の側に無い
- 7: 層1 項目4 の括弧書きは範囲を限っている。解釈で広げると、層1 の受容者が空欄の組織で何が止まるかが監査で決められなくなる。数えない理由を書くことで、「書かれていない」と「課さないと決めた」を区別できる

### 監査で確かめられること

- 有効化している案件に、事業決裁者の決裁の記録があり、記録が送信先・データの種別・版・フックの要約値・見直しの期限を持つか。現に動いている構成の値と、決裁の値が一致しているか(構成と記録の突合は機械でできる)
- 見直しの期限を過ぎた決裁のまま送信が続いていないか
- AI維持管理者のツール採用の承認、AI運用担当者のモデル導入の承認(3.12.3 要求事項1〜4・10 の記録)がそろっているか。1 人が兼ねる場合に、どの席で判断したかの記録があるか
- 接続が AI運用担当者の経路を通っているか(経路の側の消費の実績に、その提供者への送信が載っているか)
- 依存先の一覧に提供者が載り、データの種別と保持の条件の欄が埋まっているか
- 学習利用と保持期間の確認の記録があるか(確認日つき)

### 採らない案

- **送信ごとに人へ戻す**: 発話ごとの承認は 5.7.5 に反し、承認の印への縮退を招く。統制として強く見えて、記録の信頼性は下がる
- **送信の主体がフックであることを理由に 5.5.1 の外に置く**: 上記の抜け道を作る
- **ZDR の契約があれば送信してよい**: ZDR は製品・機能・組織ごとの適用範囲と例外を持つ(外部 3.4)。契約の有無の二値で許すと、適用外の機能への送信を見落とす
- **3 記録を空欄でない文字列で照合する(旧案)**: 記録の実在と記名者を確かめられない
- **5.8.6 の降ろしと同時に、または先に部品を入れる**: 拒否が効く前に送信する部品が存在する期間を作る
- **層1 項目4 へ解釈で読み込む**: 範囲の限定を崩す

### 反論されうる点

- 「常設の決裁を範囲で固定しても、決裁者は中身を読まずに記名する」。応答: 範囲の固定は、読まずに記名することを防がない。防ぐのは、記名した範囲の外で送信が続くことである。中身を読んだかは監査で確かめられない(確かめられないことを開示する)
- 「事業決裁者を要するのは重すぎる。外部ツールの採否は AI維持管理者の権限ではないか」。応答: ツールの採否と、そのツールで組織外へ情報を出し続けることの決裁は別の判断である。前者は道具の適否、後者は取り消せない効果の受容で、後者は 5.5.6 の表で事業決裁者以外が確定する事項に無い。重さは判断の性質から来る
- 「5.8.6 の降ろしは #358 で見通しが立っておらず、順序を守ると部品は当面入らない」。応答: そのとおりで、それが結論である。入らない期間の不便は、外への通信を限らない環境で送信する部品を配ることの不信頼を上回らない
- 「個人情報保護法などの整理を要求すべきではないか」。応答: 法令の適合を本標準の要求事項として書かない(外部 5、Directives Part 2 第4条)。決裁の材料として、送るデータの種別と保持の条件を記録させるところまでが本標準の範囲である

## R-3 同梱と製品の名指し

### 結論

1. **準拠テンプレートへ同梱しない**(既定無効でも同梱しない)
2. 本標準の本文・準拠テンプレートの既定値で、特定の製品(Jev / TypeSafe)を名指さない。参照実装として既定値に置くこともしない
3. 任意の部品として外に置くことも、本プロジェクトとしては**しない**。採用者が自組織で採るなら、自組織の強制層の変更(AI維持管理者の承認、`state:needs-platform`)として入れ、R-2 の決裁と記録を自ら整える。本標準が規定するのは、助言の仕組み一般に掛かる扱い(R-1)と、外部送信に掛かる既存の要求(R-2)の当てはめである
4. 再審の条件を ADR に書く: (a) 5.8.6 要求事項1・3 がテンプレートへ降りた(IMPL-0200 が delivered)、(b) 開発プロセスでの適用評価(人が正解を確定した基準集合、R-4)が存在する、(c) 提供者が R-2 の 4(経路・保持・学習利用)を満たせる条件を公開している。3 つがそろうまで再審しない

### 理由

- 既定無効の同梱は、無効の状態でも**外部送信のコードを全採用者の強制層の置き場(`.claude/hooks/`・`.claude/settings.json`)に置く**。有効化は構成の 1 欄と記録の文字列で起きる。PR で構成と記録を書き換える攻撃の型は実在する(外部 3.5)。無効であることの監査は可能だが、「無効のまま置かれたコードが、いつ有効になったか」を採用者ごとに監査させる負担を、利益の実証が無い部品のために全採用者へ負わせる理由が無い
- ADR-0084 決定6 により、テンプレートのフックは降ろし先の登録簿か除外の一覧に載らなければ検査で落ちる。同梱するなら、標準の側に降ろし先の規定(IMPL マーク)を置く必要がある。**特定の製品へ送るフックを、標準の規定の降ろし先として登録することは、標準がその部品を規定の実装として認めることになる**。ADR-0085 の契約検査(`TEMPLATE_HOOKS`)へ入れれば取り込まない採用者が落ち、入れなければ契約検査の外の強制層の部品が生じる。どちらも監査上の筋が悪い
- 製品の名指し: 1.7「特定の製品名…に依存する表現は用いない」、5.8.6「拒否の実装の手段(製品・拡張機能)は指定しません」。外部 5 の ISO/IEC Directives Part 2 第31条は、適した製品が現に 1 つしかない場合に限って名指しを認める。確率的な分類は他の手段でも実現でき、互換を名乗る OSS もある(外部 1.2)。名指しの例外に当たらない
- 製品側の事実(早期アクセス、別名で無告知に答えが変わる、廃止方針の不記載、ZDR が DPA に無い、ホスト地域の選択が無い。外部 1)は、規格の寿命より短い時間軸で変わる。既定値に置くと、その変化に本プロジェクトが追随する負担と、採用者が「標準が推奨した」と読む誤解を同時に生む
- 3 で「外に置く任意部品」も採らないのは、外に置いても本プロジェクトが配る以上、採用者から見れば本標準の提供物であり、名指しと推奨の問題が消えないためである。また、各自のローカル設定(local scope)に置く形は版管理の外で、5.8.6 要求事項2「設定は版管理下に置き、案件ごとに定める」と合わない。graft の MCP を local scope に置く先例(内部 2.7)は、資源と波及の理由によるもので、外部送信の統制の先例にはならない

### 監査で確かめられること

- 準拠テンプレートの強制層の置き場に、外部へ送信するフックが無いこと(ADR-0084 の逆向きの追跡で、フックの全ファイルが登録簿か除外の一覧に載る。新しいフックが入れば検査が拾う)
- 本文・テンプレートに特定の分類器の製品名が無いこと(grep で確かめられる)
- 採用者が自組織で入れた場合: 強制層の変更の承認(`state:needs-platform`)の記録、R-2 の記録一式

### 採らない案

- **既定無効で同梱する(旧案)**: 上記のとおり
- **製品名を外し、「System One 互換 API」として同梱する**: 互換の API 仕様自体が単一の提供者の定めたもので、実質的な名指しである。送信先が差し替え可能であることは、送信の統制を緩める方向にしか働かない(送信先の変更が構成の 1 欄で起きる)
- **例示として本文の注に製品名を書く**: Directives Part 2 は、例示を脚注に置く場合も推奨でない旨の付記を求める。付記を書いても、本標準の利用者が「例示された製品なら決裁が通りやすい」と読む経路は残る。例示の利益が示されていない
- **別リポジトリの任意部品として配る**: 上記のとおり

### 反論されうる点

- 「同梱しなければ、採用者がばらばらに自作し、統制のない形で使われる。配布物で統制を形にするほうが信頼性は高い」。応答: 強い反論で、少数意見として記録すべきである。ただし統制を形にするなら、配るべきは製品へ送る部品ではなく、**外部送信を拒否する強制層(5.8.6 の降ろし)と、助言の扱いの規定(R-1)**である。前者が無いまま送信の部品だけを配ると、統制の形を配ったことにならない
- 「テンプレートは既に graft を版固定で許可しており、外部送信を伴いうる道具を同梱している」(内部 2.7)。応答: 先例があることは、同じ形を増やす理由にならない。graft の利用統計の送信先と内容は未確認であり、こちらを 3.11.6・3.12.8 で点検する別の Issue を立てるべきである(本議題の結論ではなく、品質監査からの付記)
- 「再審の条件 (b)(c) は本プロジェクトが満たせない外部条件で、事実上の永久却下ではないか」。応答: 条件は信頼性の要件から来ており、満たせないなら却下が正しい。永久かどうかは条件の側が決める

## R-4 評価と適合性

### 結論

1. 旧案の評価(合成発話 240 件、`evaluate.mjs`)は、**3.12.3 の適合性評価の証拠に数えない**。参考の記録として残す(PR のブランチに残置されている事実を ADR に書く)
2. 旧案の評価が Haiku を却下した理由(本体も Claude で、確認する側と共通の原因を持つ)は、**新しい ADR で使わない**。3.5.4 の「系統・提供元の違いを、確認の強さの根拠として書かない」(IMPL-0158)に当たる
3. 採用者が分類器を入れる場合の適合性確認には、3.12.3 要求事項1〜5・10 をそのまま当てる。**基準集合の正解ラベルは人が確定し、確定した者を記録する**。AI の合議で作った正解は、基準集合の正解に数えない
4. 助言の有効性の**観測を有効化の条件にする**: 注意の件数、人が注意に従って人へ戻した件数、注意が人の判断を変えた件数、無視された(採らなかった)件数、注意の要らない場面への誤警報、事後に「人へ戻すべきだった」と分かった事例で注意が出ていなかった件数(見逃し)。観測できない構成では有効にしない
5. 閾値の固定値は本標準で課さない。閾値の較正は人が行い、版の変更時に再較正し、実績から自動で更新しない(3.12.12 要求事項2 と同型)
6. 3 の「基準集合の正解を AI の合議で作ったものを数えない」は、3.12.3 一般に掛かる論点で、#401 の範囲を越える。**別の Issue として起票し、同じ手順(調査・会議体・突合)で扱う**。#401 の ADR では、分類器の評価に限ってこの扱いを決める

### 理由

- 旧評価の欠陥は、監査の観点から重い順に次のとおり
  - 正解ラベルが Claude 3 者の合議で、人が確かめていない(内部 1.3)。評価の値は「AI の合議との一致率」で、正しさの率ではない。合議の一致を正しさの証拠にしない、という本標準の立場(H.4 の合議の行、IMPL-0153、ADR-0075 の FND-0077・0078)と同じ理由が、基準集合の正解にも当てはまる
  - 方式と質問文の言語を 240 件全体で選んでおり、評価に使った偶数番も独立でない(評価メモ自身の開示)
  - 合成の発話で、実際の利用の分布ではない
  - 3.12.3 要求事項10(基準集合の範囲の起案と承認の分離)の記録が無い
  - 製品側も参照解を他社モデルの出力に置いた自社評価で、独立の較正の測定が無い(外部 1.1)
- 2: 旧 ADR の却下理由は、Jev が Claude と別系統であることを、助言の強さ(共通の原因を持たないこと)の根拠にしている。現行の規定の後では書けない。**却下理由を差し替えずに旧案を蘇らせると、本標準が禁じる主張を ADR が記録することになる**
- 4: 警告疲れの先例(外部 2.3: Tricorder の「見たくなかった報告」の継続測定、誤警報の多い解析器の無視・無効化)は、観測を伴わない助言が、無視されるか既定無効のまま放置されることを示す。旧案の誤警報 6.9%、3 回送ると 6.8% で出す/出さないが変わる非決定性(内部 1.4)を、実際の利用で測り直す手段が無いと、有効化の判断を見直せない。**見逃しの件数は不作為の誤りを測る唯一の手段**であり、R-1 の 2 の規定の効き目を監査で見る材料になる
- 4 の観測は、5.7.6 の主指標(AI または前工程が誤っていた事例を、人間が捕捉した割合)と別の指標である。助言は捕捉の主体ではないので、主指標に混ぜない。混ぜると、助言が捕捉に寄与したように見える
- 5: 製品自身が固定の閾値を示さず、数値の較正の弱さを認めている(外部 1.3)。標準で値を課す根拠が無い

### 監査で確かめられること

- 基準集合が自組織のリポジトリにあり(3.12.3 要求事項5)、正解ラベルの確定者が記録され、範囲の起案者と承認者が別人として記録されているか(同一人物なら承認に数えない。ADR-0057 補足 S21)
- モデルの版が固定され、応答の版と一致しない場合に助言を出さないことが、構成と記録で確かめられるか。版の変更のたびに回帰評価と再較正の記録があるか
- 4 の観測の記録が、見直しの期限ごとに存在するか。注意ごとの採否が残っているか(本文を残さずに、注意の識別子と、人へ戻した記録への参照で結べる)
- ADR・PR の本文・保証の開示に、提供元の違いを助言の強さの根拠とした記述が無いか

### 採らない案

- **旧評価を「暫定の根拠」として EV マークつきで使う**: 根拠水準マークは実証の弱さの開示であって、正解の作り方の欠陥を補わない。合議の一致率を正答率として載せると、マークがあっても数値が独り歩きする
- **評価の正解ラベルは確認ではないので、合議で作ってよい**(内部 2.2 の読みの一つ): 形式上は IMPL-0153 の対象外でも、合議の一致を正しさの代わりにする構造は同じである
- **閾値を標準の定数(3.12.12 の登録簿)に載せる**: 製品・用途ごとに変わる値で、能力依存の定数として扱う根拠が無い
- **観測を任意にする**: 観測しない助言は見直せない。見直せない統制は形骸化の検知ができない
- **観測の値に目標を置く(誤警報 N% 以下など)**: 実証が無い。値を置くなら根拠水準マークで提示するにとどめる(外部「課せること」5)

### 反論されうる点

- 「人が正解を確定する基準集合は、作る費用が高く、誰も有効化しなくなる」。応答: 費用は採否の理由にしない。正解を人が確定できない用途では、助言の誤りを誰も測れない。測れないものを有効にしないのは結論として正しい
- 「見逃し(注意が出なかったが戻すべきだった)の件数は、事後に気づいた事例しか数えられず、過小評価になる」。応答: そのとおり。数えられた見逃しは下限であり、0 件を見逃しが無いことの根拠に数えない(R-1 の 2 と同じ扱い)。この限界を根拠水準マークで開示する
- 「基準集合の正解を AI の合議で作らない、という規定は分類器以外の 3.12.3 の運用にも波及する」。応答: だから別の Issue にする。#401 で一般の規定を決めると、#401 の調査が覆っていない範囲(コード生成モデルの回帰評価など)に条項を課すことになる

## R-5 記録

### 結論

1. **新しい ADR を起こす**。番号は起票の直前に main の最大の次を取る(2026-11-04 の main では ADR-0103、EV-0210、IMPL-0398 が次)。旧 ADR-0054(PR #283)の番号と本文は使わない
2. ADR の決定は「**準拠テンプレートへ同梱しない。特定の製品を名指さない**」を主文にした却下の記録とし、R-3 の再審の条件、R-2 の当てはめ、R-4 の評価の扱いを決定として書く。採らない案の表に、旧案の各要素(既定無効の同梱、3 記録の文字列照合、Haiku の却下理由、工程の推定、引き上げの語)を理由つきで残す
3. **標準の本文へ、助言の仕組み一般の扱い(R-1 の 1〜3)を規定として置く**。置き場は第5章(人と AI の境界)で、5.7.4 の「自動的な判定は人間への提示に限る」の隣接の節が候補。製品も分類器の方式も名指さない。**AI のレビュー・コードレビューの助言の設定(Copilot の承認の例)にも同じ扱いが掛かる書き方にする**。実装マーク(IMPL)を付け、テンプレートの `CLAUDE.md` の常駐の規則へ降りるまでは `state=undelivered` で表示し続ける。不作為の側の規定は E1(医療・規制からの類推)として根拠水準マークを付ける
4. 内部監査の観点(H.3)へ、助言の扱いと外部送信の決裁の突合を足すかを、本文の起草で検討する(観点22 の「AI の確認の条件」の隣に置く案)。品質監査としては足すことを支持する。足さないなら、観点20〜25 のどれで見るかを書く
5. オーナーの 2026-09-23「条件付きで採用」は、**記録上「採用に至らなかった」として扱う**。事実として次を ADR に書く: 条件の中身を書いた記録が無い、PR は「マージをもって内容の確認」としたがマージされずに閉じた、ADR のステータスが当時「条件付き」を表せなかった。**維持・変更・取り下げの選択は、オーナー本人が新しい ADR の採否として記録する**。AI が要約した「オーナーが選んだ」の一文を、オーナーの決定の記録に数えない
6. 採用の可否を最後に決めるのは、本標準・準拠テンプレートの保守者(オーナー)である。会議体は案を競わせて結論を出すが、確定しない。採用者の組織での有効化を決めるのは R-2 の 3 の席であり、本プロジェクトのオーナーではない。**この 2 つの水準(本標準に何を書くか/採用者の組織で何を有効にするか)を ADR の中で分けて書く**

### 理由

- 1・2: 却下は成果である(コアポリシー)。旧案は PR のブランチに残っており、記録が無いと後の起票者が同じ案を再提出し、同じ調査をやり直す。却下の理由と再審の条件を記録すれば、再提出の際に条件が満たされたかだけを確かめればよい
- 3: R-1 の扱いは分類器に固有ではない。助言が判定・承認の代わりに読まれる経路と、不在が安全の信号に読まれる経路は、AI レビューの指摘、静的解析の警告、プラットフォームの推奨のいずれにもある。テンプレートの部品の ADR に留めると、部品を同梱しない以上、規定がどこにも降りない。**部品を却下し、扱いの規定だけを本文に置くことで、「書かれていない」と「課さないと決めた」が区別できる**。既存の規定(5.7.4 はゲート承認の記述の質、H.4 は AI の推定による判定)は、発話の分類のような助言を直接は扱っていない(内部 2.1)。この穴を類推で埋めた旧案の形を繰り返さない
- 5: 監査の観点からは、決定の記録は決定者本人によるものでなければならない。「本文は AI が起草しました。マージをもって内容の確認とします」という形は、マージという行為を確認の記録に充てる設計で、マージされなければ確認の記録が無い。旧案はまさにその状態にある。条件の無い「条件付き」を維持として記録すると、条件の中身を後から誰でも補えることになる
- 6: 旧案の「オーナーの決裁」は、本プロジェクトのオーナーと、採用者の組織の決裁者を区別していなかった。テンプレートに埋め込まれた「オーナー」の語は、採用者の側で誰を指すかが決まらない

### 監査で確かめられること

- 新しい ADR の番号・EV・IMPL が台帳と衝突していないこと(`npm run lint:refs`、`evidence:write`、`impl:write` の再生成で確かめられる)
- ADR の採否の記録が、オーナー本人の記録(本人のコメント・承認レビュー)を指していること
- 本文の新しい規定に IMPL マークがあり、降りるまで undelivered で台帳に出ていること
- 採らない案の表に、旧案の要素がすべて理由つきで載っていること(旧 PR の差分の要素との突合)

### 採らない案

- **旧 ADR-0054 の番号を振り直して蘇らせる**: 却下理由(Haiku)・照合(G-4)・送信の統制(3.12.2 不参照)が現行と合わず、差し替える範囲が本文の大半に及ぶ。蘇らせる形は「旧案が正しい」前提を置く
- **テンプレートの部品としての ADR に留め、本文へ規定を置かない**: 部品を同梱しないなら規定がどこにも無い状態になる
- **「条件付きで採用」を維持として記録し、条件を本会議体が補って書く**: 条件の作者がオーナーでなくなる
- **ADR を起こさず Issue を閉じるだけにする**: 却下の理由と再審の条件が、標準の利用者から読めない場所に置かれる
- **会議体の結論をもって採否を確定する**: 確定は席(本プロジェクトではオーナー)が行う

### 反論されうる点

- 「本文へ一般の規定を置くのは #401 の範囲を越える」。応答: #401 の論点(助言を判定に数えない、不在を根拠にしない)そのものであり、範囲の内である。越えるのは 3.12.3 の基準集合の正解の一般論で、そちらは R-4 の 6 のとおり別の Issue にする
- 「観点を H.3 へ足すと、監査の負担が増え、観点の数が形骸化を招く」。応答: 負担の増加は採否の理由にしない。形骸化の懸念は正当で、足すなら既存の観点(22: AI の確認の条件)へ統合する案と比べて決める
- 「オーナーの選択を『採用に至らなかった』と書くのは、オーナーの意思を否定する」。応答: 否定ではなく、記録に残っている事実の記述である。オーナーが維持を選ぶなら、新しい ADR でその旨と条件を本人が記録すればよい。その経路を閉じない

## 付記(本議題の結論ではない。品質監査から別に起票を勧めるもの)

- 3.12.3 の基準集合の正解を AI の合議で作ることの扱い(R-4 の 6)
