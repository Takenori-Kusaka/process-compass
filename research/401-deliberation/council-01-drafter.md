## R-1 位置づけ

### 結論

1. 確率的な分類器の出力を、**判定にも検出の層にも数えない**。どの層でもない「**推定による注意の喚起**」として定義する
2. 置き場は第5章 5.8 の新設の節 5.8.7(5.8.1「未検証の入力として扱う」の下)。製品を名指さない一般の規定にする。人へ戻す判別に関わる 1 文だけを 5.5.1 に置く(5.5.1 は採用者に委ねられない節。`src/data/impl-no-adopter.yaml`)
3. 附属書H H.4 の「数えてはならない」の列挙へ 1 行足す(数え方の正本は H.4 のため)
4. 「引き上げ」の語を使わない。5.5.7 の語彙の「**厳しくする向き**」を使う
5. 注意の喚起の出力の**場所**は誘導層(遵守を保証しない)、部品と設定の**置き場**は強制層、と分けて書く

### 理由

- **検出の層に数えない理由**: 検出の層は、成果物の欠陥を見つける確認を、欠陥注入による検出率で働きを示して数える仕組みである(H.4 の条件1)。発話の分類は欠陥を見つける確認ではなく、検出率を測る対象が無い。数えると、保証の開示の AI の層(項目6)に「助言の層」が並び、確認の強さを示すものと読まれる。内部 2.1 の推測(H.4 の「AI の推定による判定」に入らない読み)を、読みに委ねず条文で閉じる
- **一般の節にする理由**: 推定を開発の工程の振り分けに使う実務は、Jev に限らず既にある(外部 2.1: Meta の DRS は**緩める向き**に使い、Copilot は設定で承認に数えられるようになった)。現行の規定は、ゲート承認の記述の質(5.7.4)と成果物の AI レビュー(H.4)を扱い、指示・発話・状態の推定を扱わない。本標準に従う他組織が、この空白を各自の判断で埋めると、緩める向きの利用(区分の引き下げ、委任の該当の判定)が入りうる
- **片向きと不在の明文化**: 片向きは作為の誤り(誤った注意で緩む)を塞ぐ。注入で注意の確率を下げられる(外部 1.3)ため、注意の効果は注入された場合に「注意なし」と同じ水準へ落ちる。その水準が安全であるのは、不在を根拠に数えない場合に限る(不作為の誤り。外部 2.2・考察 A)。5.8.6 の要求事項9(拒否が 0 件であることを根拠にしない)と同型で、既存の規定と整合する
- **5.5.1 と 5.8.7 に分ける理由**: 人へ戻す判別は 5.5.1 が正本で、採用者に委ねられない。注意の不在の扱いをそこへ置くと、テンプレートが部品を同梱しなくても降ろす規定になる。5.8.7 の残りの要求は、部品を置いた採用者にだけ掛かるため `plan=adopter` にできる
- **「人へ戻す場合を増やしも減らしもしない」**: 5.5.1 は「選択のたびに人へ戻さない」「決めてよい範囲と人へ戻す場合を対で示す」を求める(`human-ai-boundary.md:346, 375`)。旧案の注意の 1 つ(判断の丸投げ、閾値 0.3)は、誤警報の多くが戻さなくてよい技術判断だった(内部 2.1)。注意を 4 つ目の戻す理由にすると、協働の席の担い手が小さな選択まで人へ戻し続ける。注意は判別を促し直すだけにする
- **「引き上げ」を使わない理由**: 5.4.5・5.5.7 の「引き上げ」は統制を**緩める**向きである。一方で 3.8.1 の下限の「引き上げ」は厳しくする向きで、語の向きが定まっていない(内部 2.3)。5.5.7 の表の語「厳しくする」は向きが一意である
- **無効化を弱化に数えない理由**: 要求事項3 で何も注意の喚起に依らせないので、外しても失われる統制が無い。数えると、効かない注意を外すたびに `state:needs-platform` と弱化の扱いが要り、形骸化した注意が残り続ける(警告疲れ。外部 2.3)

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 注意の喚起を H.4 の検出の層に数え、5 条件を掛ける | 条件1 の欠陥注入による検出率は、発話の分類には測る対象が無い。測れない条件を掛けると、常に「条件未確認」になるか、合成の発話での正解率を検出率と取り違えて開示する |
| 旧案と同じく「5.5・5.7.4・5.8.3 の適用で、新しい規定ではない」とする | 5.7.4 はゲート承認の記述の質の規定で、発話の分類を扱わない(内部 2.1)。類推で引くと、他組織は類推の範囲を各自で決める。不在の扱い・送信・観測は既存のどの条項にも無い |
| 規定を置かず、テンプレートの ADR にだけ記録する | 推定を緩める向きに使う実務(DRS)と承認に数える設定(Copilot)が現にある。標準が黙っていると、他組織が緩める向きに使うことを止める条項が無い |
| 注意の喚起を禁止する | 片向きにして不在を根拠にしなければ、注意の誤りは統制を緩めない。禁止する根拠となる害の測定が無い。使わない選択は既に妨げない(本標準は置くことを求めない) |
| 「引き上げ方向」の語に定義を付けて使う | 同じ章の 5.4.5・5.5.7 で逆向きの意味を持つ。定義で上書きしても、節をまたいで読む者は取り違える |
| 退けた注意を、変更ごとの記録へ書かせる | 誤警報の率(旧案の評価で 6.9%)のまま記録を求めると、記録の欄が定型文で埋まる(5.7.5)。件数の観測(要求事項9)で足りる |

### 反論されうる点

- 「5.8 は AI が生成した**成果物**の統制で、注意は成果物でない」。→ 5.8.1 は AI の出力一般を未検証の入力として扱う原則で、注意の喚起はその直接の適用である。第5章の別の箇所(5.7 の後に 5.7.7 を足す等)が適切だという対案はありうる
- 「部品を同梱しないのに 5.5.1 の規定を常駐させるのは、CLAUDE.md の行数(RC-07)を使う割に効かない」。→ 既存の箇条への追記で行は増やさない。採用者が独自に分類器を足す経路は止められないため、不在の扱いは部品の有無に依らず要る
- 「厳しくする向きの注意でも、自動化バイアスで人の判断を方向づける(FDA は警報も判断を方向づける出力と扱う)」。→ 本案は注意を判定に使わず、件数で観測するまでで、方向づけの害を測ってはいない。EV-0210 に開示した
- 「要求事項2 の『区分を高く見直す』は、注意で G-5 の下限を上げる経路を開く」。→ 要求事項1 で区分の下限の規則に使うことを禁じた。高く見直すのは確定者(人)である
- 「層1 項目4 に当たらない、と標準が言い切るのは、トップマネジメントの定めを狭める」。→ 項目4 の括弧の範囲(自律レベルの引き上げ、委任の範囲の登録)を変えない確認にとどまる。トップマネジメントが項目4 に含めたい場合は、層1 の行として書ける。言い切らずに「組織が層1 で定める」とする対案がある

## R-2 外部送信

### 結論

1. 発話ごとの自動送信は、組織の管理外への発行(ADR-0053 決定3)であり、後段が人でない経路である。5.5.1 の箇条「後段が人でない経路では、上流の操作が取り消せない操作に当たる」(`human-ai-boundary.md:357`)により、**送信を始める設定の有効化と、送信先・送る項目の変更が、取り消せない操作に当たる**。担い手に行わせない
2. 個々の送信は、送信ごとに人へ戻さない。**常設の決裁で覆ってよい**。ただし決裁は、送信先・送る項目と送らない項目・期限を定めたものに限る(5.8.7 の要求事項7)
3. 決める席は**事業決裁者**。旧案の「オーナー」は席の名でない。決める事項ごとの席は次の表のとおり
4. 推定のサービスは 3.12.2 の AI 実行基盤に当たる。個人のキーで端末から直接つなぐ形は正規の経路でない
5. 5.8.6 の要求事項1・3(許可していない外部への通信の拒否、ネットワークの既定拒否)が準拠テンプレートへ降りるまで(IMPL-0200、#358)、**外部送信の部品を準拠テンプレートへ入れない**

| 決める事項 | 席 | 規定 |
| --- | --- | --- |
| 組織の管理外へ送ることの可否、送信先・送る項目・期限 | 事業決裁者 | 5.5.1(取り消せない操作)、5.8.7 の要求事項7 |
| 接続の経路(正規の経路の用意)、モデルの導入の記名承認、学習利用と保持の確認の記録 | AI運用担当者 | 3.12.2、3.12.3 の要求事項3、3.12.8 |
| 部品(フック)と設定・送信先の許可(強制層)の変更の承認 | AI維持管理者 | 3.11.2、3.5.5 |
| 部品を置くことの要否(検査を足すことの要否と同じ扱い)、閾値 | 技術判断者 | 3.11.2「検査の追加の要否は技術判断者が決める」、5.8.7 の要求事項6 |
| 基準集合の範囲 | AI運用担当者が起案、技術判断者が承認 | 3.12.3 の要求事項10 |
| 委託で強制層を所有する組織が異なる場合の送信先の追加 | 所有する組織の同意の記録 | 3.11.2(ADR-0087)、第8章 軸D |

### 案

- 標準の文面は R-1 の案 1-b の要求事項4・7・8(再掲しない)
- 既存の条項は改めない。3.12.2・3.12.8・3.12.11・5.8.6 の要求は、そのまま推定のサービスにも掛かる。5.8.7 は「掛かること」と「部品の側の自己規制を満たしたものと扱わないこと」だけを足す
- 担い手が有効化しないことは、テンプレートの CLAUDE.md の (c)(外部への発行、IMPL-0251)が既に運ぶ。新しい常駐の規則は足さない
- 準拠テンプレートへの外部送信の部品の投入は、R-3 の再審の条件に「IMPL-0200 が delivered であること」を入れて縛る

### 理由

- **上流の操作に当たる理由**: 送信は削除しても送られていた時間帯が消えない(ADR-0053 決定1・3)。発話ごとの送信の後段に人はいない。5.5.1 の定義をそのまま当てると、上流の有効化が当たる。読みを分ける余地(送信の主体がフックで、担い手でない。内部 2.4)は、5.5.1 が「他の者の操作を介さずに生じさせる操作」と主体ではなく効果で定めていることで閉じる。有効化の設定を書くのが担い手でも人でも、効果を生む経路の起点は有効化である
- **常設の決裁で足りるとする理由**: 発話ごとに人の承認を求めると、承認は記録の操作へ縮退し(5.6・5.7.5)、統制の実質は消えたまま記録だけが残る。5.5.4 の「本番環境への反映の承認」は、登録時の記名で後続の反映を覆う型であり、本標準の中に先例がある。ただし範囲と期限を欠いた決裁は、送信先・項目の後からの変更を覆ってしまうため、範囲と期限を決裁の必須の中身にし、変更を上流の操作として扱い直す
- **事業決裁者である理由**: 送信は取り消せない操作で、テンプレートの写像は `state:needs-owner`(事業決裁)である。提供者との契約(責任の上限、保持、再委託)は 5.4.3 の不変条件3「外部との契約に関わる決定」に当たる(内部 3 の表)。技術判断者・AI維持管理者は、送ることの可否を決める席ではない
- **3.12.2 の経路の理由**: 正規の経路の外の利用は、依存先の一覧に載らず(3.12.11 の末尾)、送出の検査も通らない(3.12.8 の要求事項2)。旧案はキーを環境変数で受けて端末から直接つないだ(内部 2.4)。分類器だけを 3.12.2 の外に置く理由は見当たらない
- **部品の自己規制を数えない理由**: 旧案の許可の一覧と秘匿情報の検出は部品のコードの中にある。3 記録は空でないかだけを見ていた(内部 1.2)。設定と部品は PR で差し替えられる(外部 3.5、CVE-2026-47751)。Bash から node の fetch を呼ぶ経路は限られていない(IMPL-0200)。部品の中の一覧は、部品が改められれば同時に改められ、許可の範囲を示す独立の事実にならない
- **順序の理由**: 5.8.6 は本文の要求で、テンプレートは未達である。未達のまま外部送信の部品を入れると、準拠テンプレート自身が「許可していない外部への通信を拒否できない環境に、外部へ送る部品を置く」形になる。5.8.6 の要求事項3 が降りた後なら、送信先の追加は既定拒否を解く変更になり、3.5.5 の弱化の扱いと ADR-0087 の同意が自然に掛かる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 送信ごとに人へ戻す | 承認の疲れで記録の操作へ縮退する(5.7.5)。発話ごとの摩擦は、注意の喚起の効用を上回る |
| 決裁を 1 回取れば以後を無期限に覆う(旧案の形) | 送信先・送る項目・提供者の条件(保持・再委託)の変化を覆ってしまう。DPA の保持は「必要な限り」で固定期間が無い(外部 1.4)。期限が無いと、条件の変化を確かめる契機が無い |
| 旧案の 3 記録(外部送信の決裁・ツールの採用・モデルの採用)を記録の文字列の有無で確かめて送信を許す | 記録の実在と記名者を照合しない。任意の文字列で送信が始まる(内部 1.2)。記録の文字列の有無は統制の事実でない |
| 「オーナー」を決裁者にする | 席の名でない。採用者の組織で誰に当たるかが定まらない |
| 5.8.6 の降ろしを待たず、既定無効で先に入れる | 上の「順序の理由」。既定無効でも、有効化に要るのは設定の 1 箇所で、外部への通信を拒否する層が無い |
| 「ZDR の契約がある」ことで送信を許す | ZDR は製品・機能・組織ごとに適用範囲を持ち、例外がある(外部 3.4)。提供者の DPA に記述が無い(外部 1.4)。契約の有無の二値で許すと、適用外の機能への送信を覆う |
| 個人情報保護法の整理を要求事項にする | 規格に法令上の要求を書かない(ISO/IEC Directives Part 2 第4条。外部 5)。組織の規程による、と書くにとどめる |

### 反論されうる点

- 「上流の操作として扱うのは過剰。開発者が手で外部の AI へ貼り付けるのと同じで、5.5.1 は担い手の操作の規定だ」。→ 手で貼り付ける場合は人が自ら行う操作で、5.5.5 の項目4 の型である。自動送信は後段に人がいない。5.5.1 の箇条の 3 つ目(予約した公開、push を契機に動く配備)と同じ構造である
- 「事業決裁者に集めると、判断の要らない事項まで決裁へ集まる(ADR-0038 が退けた形)」。→ 決裁するのは送ることの可否と範囲・期限だけで、閾値・部品・経路は他の席に分けた
- 「常設の決裁の期限の長さを定めないと、無期限と同じになる」。→ 長さの根拠となる測定が無いため課さない。期限の欄が空の決裁は決裁として扱わない、までなら課せる(会議で詰める)
- 「AI運用担当者の経路が無い小規模な組織では、事実上使えない」。→ 3.12.2 の既存の帰結で、本件に固有でない。正規の経路の整備は統制の前提条件である(3.12.2 末尾)

## R-3 同梱と製品の名指し

### 結論

1. **準拠テンプレートへ同梱しない**。既定無効の同梱も、任意の部品として別に配る形も、現時点では採らない
2. 標準の本文と準拠テンプレートで製品を名指さない。ADR-0103 は審議の契機として製品名を時点つき(2026-11-04 時点)で書く
3. テンプレートへ入れるのは、注意の不在を根拠にしない規則 1 つ(案 3-b)
4. 差し込み口(製品に依らない、注意を出す部品を採用者が差し込む口。`ai-review-workflow` の型)を置くかは、次の**再審の条件**がそろってから改めて審議する。条件を ADR-0103 に記録する
   - 5.8.6 の要求事項1・3 が準拠テンプレートへ降りている(IMPL-0200 が delivered)
   - 3.11.6 の外部ツールの一覧と権限の置き場がある(IMPL-0228・0229 が delivered)
   - 人が正解を確定した基準集合で、注意の喚起を評価した記録が 1 件以上ある(採用者の案件か本プロジェクトの試行)
   - 差し込み口を求める採用者の要望、または本プロジェクトの試行の記録がある

```markdown
- 外部のサービスを使う場合は、送信先をネットワークの許可(5.8.6)に置き、部品の中の一覧に頼らない。接続は AI運用担当者の経路(第3章 3.12.2)を通す
- モデルの版を固定し、応答の版が異なれば注意を出さない
- 発話の本文を記録に残さない。件数(5.8.7 の要求事項9)の集計に要る値だけを残す
```

### 理由

- **同梱しない理由(製品の事実)**: 早期アクセス、価格補助の可能性、廃止方針の記載なし、別名で無告知に答えが変わる、DPA に ZDR と固定の保持期間が無い、ホスト地域の選択が無い、注入で答えが動く(外部 1)。いずれも標準・テンプレートの寿命より短い時間軸で変わる。既定値として置くと、テンプレートが採用者に代わって提供者を選んだ形になる
- **同梱しない理由(統制の事実)**: R-2 の 3.12.2(直接接続)と IMPL-0200(既定拒否が無い)。テンプレートが自らの準拠する標準の未達の上に外部送信の経路を置くことになる
- **既定無効の同梱も採らない理由**: 有効化は設定 1 箇所で、テンプレートの採用者すべてが外部送信の経路を持つ。リポジトリの設定を PR で差し替える攻撃は実例がある(外部 3.5)。使わない採用者に、保守・追跡(ADR-0084 決定6)・契約検査(ADR-0085)の負担と攻撃面を配る。`TEMPLATE_HOOKS` に入れれば取り込まない採用者が契約検査で落ち、入れなければ同梱したフックが契約の外に残る(内部 2.5)
- **graft との違い**: テンプレートは既に版固定で graft を許可している(内部 2.7)。ただし graft は MCP をリポジトリの `.mcp.json` に登録せず、各自のローカルに置く方針で、外部送信を主機能にしない。推定のサービスは、発話の本文を外部へ送ることが主機能である。graft の先例は、同梱の根拠にはならない(graft の利用統計の送信は未確認で、本件とは別に確かめる価値がある。会議の論点の外)
- **名指さない理由**: 1.7「特定の製品名…は用いない」(`overview.md:284`)、5.8.6 の「手段(製品・拡張機能)は指定しません」。ISO/IEC Directives Part 2 第31条は、適した製品が現に 1 つしかない場合に限り商品名を本文に書けるとする(外部 5)。確率と確信度を返す分類は、汎用のモデルや互換の OSS でも実現できる
- **差し込み口を今は置かない理由**: 差し込み口だけを置いても、5.8.7 の要求事項7・8 を満たす経路(既定拒否、正規の経路)がテンプレートに無い。満たせない口を置くと、採用者が口へ外部のサービスを直接つなぐ経路を、テンプレートが用意したことになる
- **3-b を入れる理由**: 採用者が独自のフックで推定を足すことは止められない。そのとき、不在を根拠にしない規則が CLAUDE.md に無いと、担い手は「注意が出ていないから当たらない」と書きうる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 旧案どおり既定無効で同梱し、Jev を既定の送信先にする | 上の「同梱しない理由」2 つと名指しの理由 |
| 製品を外した互換 API の部品として、既定無効で同梱する | 名指しの問題は解けるが、統制の事実(3.12.2、IMPL-0200)と攻撃面・契約検査の問題は残る |
| 任意の部品として別のリポジトリで配る(pit-crew・別の配布物) | テンプレートの外に置いても、本プロジェクトが配る部品である限り、5.8.7 の要求事項7・8 を満たせない環境へ外部送信の部品を配る点は同じ。再審の条件がそろった後の選択肢として残す |
| 外部送信を伴わない部品(端末内のモデル、キーワード規則)だけを同梱する | 旧案の評価でキーワード規則は工程 55.8%・注意の再現率 0〜43%(旧 ADR の表)。端末内のモデルは本プロジェクトで評価していない。効くかを確かめていない部品を同梱する根拠が無い |
| 標準の本文に「例: Jev」と例示する | 例示でも、規格の読み手は推奨と取る。Directives Part 2 の例外(単一の製品)に当たらない |

### 反論されうる点

- 「同梱しないと、採用者が各自で質の低い実装をする。良い既定を配るほうが信頼性が高い」。→ 有力な反論。ただし、良い既定の前提(既定拒否・正規の経路・人が確定した基準集合)がテンプレートにまだ無い。前提がそろうまでは、配った既定が良い既定である根拠が無い。再審の条件はこの反論に応える形にした
- 「3-b は部品の無いテンプレートの CLAUDE.md に、使われない規則を置くことになる」。→ 5.5.1 を降ろす以上、行は要る。読み手が「分類器」の語で戸惑う可能性は残る
- 「再審の条件の 3 つ目(人が確定した基準集合の評価)を本プロジェクトが満たす手段が無い」。→ 採用者の案件の記録でも足りるとした。満たされなければ同梱しない状態が続く。それを結果として受け入れる

## R-4 評価と適合性

### 結論

1. **旧案の評価(合成発話 240 件、正解は Claude 3 者の合議、人は未確認)を、採否の根拠にも EV の根拠にも使わない**。評価メモは参考の記録として research に残す(取り込むかは R-5)
2. 旧 ADR の却下理由「Claude(Haiku)は本体と共通の原因を持つ」は**撤回**する。3.5.4 の箇条(`roles-responsibilities.md:664`。系統の違いを確認の強さの根拠として書かない)と IMPL-0158 に当たる。ADR-0103 では、Jev が別の提供元であることを、注意の確かさの根拠として書かない
3. 推定に用いるモデルには **3.12.3 を掛け、3.4.2 は掛けない**(席の担い手でない)。3.12.3 の要求事項7〜9(退出の予行)は、出荷に要る席の担い手のモデルに限るため掛からない
4. **基準集合の正解は人が確定する**(5.8.7 の要求事項5)。複数の AI の合議の正解を数えない
5. 働きを **5 つの件数**で観測する(5.8.7 の要求事項9)。人の判断を変えた割合は (c)/(b)、無視された割合は (d)/(a)
6. **閾値の値と、件数の警戒水準を課さない**。閾値は版ごとに技術判断者が記名で決め、実績から自動で変えない(5.8.7 の要求事項6)。3.12.12 の能力依存の定数の登録簿には載せない

### 案

- 標準の文面は R-1 の案 1-b の要求事項4〜6・9 と注記(再掲しない)
- 3.12.3 の要求事項1 の「基準集合」の正解を AI の合議で作ることの扱いは、**分類器に限らず全モデルの問題**である。本件では 5.8.7 の中に閉じ、3.12.3 の改訂は別の Issue として起票を提案する(本件の範囲で 3.12.3 を改めると、ほかの全モデルの導入に効く変更を、分類器の審議だけで決めることになる)
- ADR-0103 の「コンテキスト」に、旧案の評価の値を**参考として**載せる場合は、次の 3 点を同じ表に添える
  - 正解は AI の合議で、人は確認していない
  - 方式と質問文の言語を 240 件全体で選んだため、偶数番も独立でない
  - 提供者の公開の比較は、参照解が他社のモデルの出力で、真の正解でない(外部 1.1)

### 理由

- **評価を根拠に使わない理由**: 正解が AI の合議で作られている。H.4 は複数の AI の合議の一致を検出の層にも独立した確認にも数えない。評価の正解は確認そのものではないが、正解が誤っていれば正解率・再現率・誤警報率のすべてが誤る。人へ戻す場合に当たるかは人が確定する判断の写し(5.5.1)であり、その正解を AI だけで作ると、人の判断の代わりに AI の判断で AI を較正したことになる
- **撤回の理由**: 3.5.4 は系統の違いの効果が測定で向きが分かれること、系統をまたいで誤りが強く相関した測定があることを理由に、強さの根拠に使うことを禁じた(ADR-0075 決定12)。旧 ADR の理由 (1) は Haiku を退ける理由として系統の同一を弱さの根拠にしており、裏返すと Jev の別系統を強さの根拠にしている
- **3.4.2 を掛けない理由**: 3.4.2 は席の担い手(モデルの版・指示資産の版・権限の組)の適合性確認で、確認の結果が運用形態の上限を決める。注意の喚起は判定にも作業にも数えないため、担い手の識別に入らない。掛けると、注意の部品の版を変えるたびに席の適合性確認が失効する読みが生じる
- **3.12.3 を掛ける理由**: 3.12.3 は「新しいモデルを開発組織へ導入する前」に掛かり、「承認されていないモデルを開発組織で用いてはなりません」(`roles-responsibilities.md:1507`)とする。分類器を除く根拠は無い
- **件数の選び方**: 5.7.6 の主指標(人が捕捉した割合)は承認設計の指標で、注意の喚起には当たらない。Tricorder の型(利用者から見た誤検知を継続して測る)に倣い、注意が役立ったか (c)、放置されたか (d)、見逃したか (e) を分けた。(e) は事後に見つかった分しか数えられないため、0 件を見逃しの無さに読まない注記を付けた
- **閾値を課さない理由**: 提供者自身が固定の閾値を示さず用途しだいとし、数値の較正の弱さを認めている(外部 1.3)。3.12.12 の登録簿は標準の定数で、案件の構成値の閾値はその対象でない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 旧案の評価を EV の根拠(E1)として引く | 正解が人の確定を経ていない。根拠の水準 E1 は「隣接する領域の測定」で、正解の誤りの可能性を含む測定を根拠に数えると、水準の表示が実態より強くなる |
| H.4 の条件1 に倣い、注意の喚起に欠陥注入による検出率を求める | 測る対象が無い(R-1) |
| 注意の件数・妥当件数が 30 件たまったら閾値を見直す(旧 EV-0040 の差し替え条件) | 30 件の根拠が無い。件数が少ない案件では見直しが起きない。四半期の棚卸しの契機に結びつけた |
| 誤警報率の上限(例: 10%)を課す | 外部 2.3 の「約 10%」は二次資料でのみ確認(未確認)。案件で適切な値が異なる |
| 3.12.3 を本件で改め、基準集合の正解を人が確定することを全モデルへ課す | 全モデルの導入に効く変更で、分類器の審議の範囲を超える。別の Issue で、生成モデルの基準集合の正解の作り方と合わせて審議する |

### 反論されうる点

- 「人が正解を確定する基準集合を作る負担が大きく、事実上だれも有効にできない」。→ 有効にしない状態が続くことは、本案では害にならない(要求事項3 で何も依らない)。負担の大きさを理由に、正解の確定を AI に移す根拠は無い
- 「5.8.7 にだけ人の確定を課し、3.12.3 一般には課さないのは不整合」。→ 起案者も認める。別の Issue で解く前提で、本件の範囲を限った
- 「件数 (c) の判断(戻しを要したか)を受け取った席の責任者に書かせるのは、新しい記録の負担」。→ 受け取った席は既にラベルの遷移と判定の記録を書く(3.5.5)。その記録に「注意が契機か」を残すかは、採用者の実装に委ねる(`plan=adopter`)

#### 案 5-b: 旧案の材料の扱い

- 評価メモ(`origin/docs/adr-0054-phase-advisor:research/20260923-jev-phase-advisor-evaluation.md`)は、`research/401-deliberation/` へ写して残す。冒頭に「正解は AI の合議で人は未確認。採否の根拠に使わない(ADR-0103)」を添える。旧ブランチは消える可能性があり、審議の材料を残すため

### 反論されうる点

- 「同梱しないなら ADR は『採らない』だけで足り、5.8.7 は将来の需要が出てから書けばよい」。→ 却下は成果であり記録する。ただし 5.8.7 の主眼は同梱ではなく、他組織が推定を緩める向きに使うことを止める点にある。それを将来へ回す理由は無い
- 「オーナーが『維持』を選んだ場合、本案はどうなるか」。→ その場合も、5.8.7(とくに要求事項7・8)と 3.12.2 を満たす形へ旧案を作り直す必要がある。IMPL-0200 が降りるまで入れない順序は、維持でも変わらない、と起案者は考える

## オーナーにしか決められないこと

1. 2026-09-23 の「条件付きで採用」を、維持・変更・取り下げのどれにするか(起案者は変更を推す)
2. 標準の本文へ 5.8.7 と 5.5.1 の段落を置くことの採否(本標準の保守者として)
3. 準拠テンプレートへの同梱の可否と、CR-091 の取り込み(テンプレートの保守者として。強制層の変更)
4. 再審の条件の 3 つ目(人が確定した基準集合での評価)を、本プロジェクトで試すかどうか。試すなら、本プロジェクト自身が外部へ発話を送ることになり、本プロジェクトの事業決裁(オーナー)と経路の判断が要る

採用者の組織で注意の喚起を有効にするかは、オーナーではなく採用者の席(R-2 の表)が決める。
