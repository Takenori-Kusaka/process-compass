## 1. 争点ごとの裁定

### 争点1-1 条文にするか手引きにするか — **課さないと明記する(案B)。軽のまま閉じる**

裁定: 第1章 1.10.2 は変えない。受け取り側の生成元の確認を、採用者の義務にも、適用の表明の必須の併記事項にもしない。確認の手順は手引き(`community/standard-editions.md`)に置き、だれでも行える手順として示す。課さない旨を ADR-0157 に記録する。

理由:

1. 起案の案A(「済の日付と条件、または未実施」の併記)は、行為を課さず開示だけを課すと主張する。しかし 1.10.2 は「併記しない表明を、本標準に基づく適用の表明として扱わない」形の箇条を持つ。必須の併記事項を足すことは、既存の採用者の表明の成立条件を変える。**採用者への新しい義務に当たる**。採るなら重である
2. 案A の「済」は、採用者が自由に書ける自己申告である。`VERSION.md` が自由に書けるという弱点(ADR-0077 L108)と同じ型で、読み手は「済」を信じる以外に確かめようがない。一方、1.10.2 は既にコミットの識別の併記を求めている。標準のリポジトリは公開である。**表明の読み手が、名指されたコミットについて同じ手順を自分で再現できる**。読み手が確かめられることを、書き手の申告に置き換える理由は無い。起案の懸念「読み手が確認済みか未確認かを区別できない」は、読み手が自分で確かめられることで解ける
3. 0章のとおり、確からしい食い違いの発生源は配る側である。配る側を機械の検査で閉じる方が(争点1-3)、全採用者に確認と開示を求めるより信頼性が高い
4. 案A の前提(配布物 `docs/` と生成元の本文の一致)は `dist/standard` を submodule で取り込む形のものである。準拠テンプレートの採用者は知識ベースだけを持ち、その確認は使えない。前提が取り込みの主な形と合わない

採らない案:

- **案A(1.10.2 に確認の結果の併記を求める)**: 上の1〜4。重へ上げずに採らない
- **併記を「してよい」とする任意の条項**(起案が示した落としどころ): 許す条項は何も規律せず、条文を増やすだけである。表明に確認の結果を添えることは、条文が無くても禁じられていない。手引きに「添えてよい」と書けば足りる
- **確認の実施の義務化**: 2委員とも採らない。新しい義務で重。実証は1時点(E1)

重へ上げるか: **上げない**。割れた点(案A)を採らないため。

### 争点1-2 検査の強さ — **手引きに (b) とその保証の範囲を書く。(a)・(c)・(d) は採らない**

裁定: 手引きの手順は、取り込みの形ごとに2つの条件を確かめる。どちらも決定可能(存在・一致)。

| 取り込みの形 | 条件1(来歴) | 条件2(中身) |
| --- | --- | --- |
| `dist/standard` のコミット D を固定する | D の `VERSION.md` のコミット S が、標準の `main` の祖先である。`tailoring-kb.json` の `source.commit` が S と一致する | `S:src/content/docs` と `D:docs` の差が空 |
| 準拠テンプレートの同梱の知識ベース(`source.commit` = S) | S が標準の `main` の祖先である | `dist/standard` のうち `source.commit` が S のコミット D の `tailoring-kb.json` と、同梱の知識ベースがバイト一致する。D が無い(S が配布を起動しなかったコミット)ときは「未確認」であり、「不一致」とも「一致」とも書かない |

保証しないこと(手引きに明記する。反対委員の指摘を採る): (i) 本文が正しいこと。言うのは「main の上の本文・CI が main から生成したものと一致する」までである。(ii) 確かめた後の `main` の書き換え(force push)。確認は1時点の事実である。(iii) 保守者のアカウントが侵害され、main そのものへ書かれた場合。CI はそれも配布する(SRC-0459 と同型)。

採らない案:

- **(a) 祖先の確認だけ**: 実在の SHA を名乗って中身を差し替えた配布物を通す(intake 1.2)
- **(c) 採用者が再生成して知識ベースまで一致を見る**: 採用者の環境に生成の一式が要り、node の版などで結果が揺れる。CI の生成物(`dist/standard`)との比較で同じことを決定可能に確かめられる。同梱の知識ベースの比較の相手は再生成でなく、CI の配布物とする
- **(d) artifact attestation**: GitHub が個別の文書ファイルを対象にすべきでないとする(FND-0100)。git のコミットとして取り込む形と型が合わない。署名は誰のビルドかを言い、中身の良さを言わない(SRC-0459)。**課さないと決めた**(ADR-0157)

### 争点1-3 だれが・いつ — **受け取り側は任意。配る側(標準のリポジトリ)は機械の検査で閉じる**

裁定:

- 受け取り側の確認: 採用者・監査する者・表明の読み手のだれでも、適用の開始と版の切り替えのときに行える手順として手引きに置く。だれにも課さない。継続の検査にしない
- 準拠テンプレートの契約検査には入れない(2委員とも同じ)。ネットワークに依存し、正本の書き換えで後から落ちる。機械の検査にする部分の決定可能な条件は、配る側で閉じられる
- **配る側の機械の検査を足す(議長が0章の事実から足す)**: `scripts/check-gate-criteria.mjs` が既定の対象(テンプレートへ複製した知識ベース)を検査するとき、`source.commit` が標準のリポジトリの `HEAD` の祖先であることを求める(`git merge-base --is-ancestor`)。決定可能な条件(履歴の中の存在)である。#301 がコミットを比較から外した理由(HEAD が進むと一致しない)と矛盾しない。祖先であることは HEAD が進んでも保たれる。rebase で生成元が履歴から外れたときだけ落ちる
  - 履歴を読めない場合(浅い clone、コミットの対象が無い)は、失敗とする。入力が無いことを一致として扱わない(#293 裁定 J-3)。CI の `check` は `fetch-depth: 0`(ci.yml L38)なので読める
  - `--kb` を渡す配布のジョブは、既存の `GITHUB_SHA` との一致の検査を維持する(一致すれば祖先でもある)
  - `editionAt` が到達できないコミットを黙って「発行の時点でない」と読む点は、上の検査が先に落とすので、`editionAt` 自体は変えない。読み手のために `check-gate-criteria` の問題の文に「rebase の後は `npm run template:kb` で再生成する」と書く

採らない案: テンプレートの契約検査で祖先・中身の一致まで自動化する(2委員と同じ理由)。採用者のテンプレートに 40 桁の形式と `VERSION.md` との一致の検査を足す(起案の template の項1)。テンプレートの採用者は `VERSION.md` を持たない(0章)。形式は配る側で既に見ている。

### 争点1-4 配る側の補強(実行の番号の突き合わせ・保護) — **先送り**

裁定: `dist/standard` の各コミットと `main` の CI の実行の突き合わせは、ADR-0090 決定8 の候補のまま残す。本件では決めない。`main`・`dist/standard` へのルールセット(Actions だけが書ける)は本件の範囲外とし、既存の open Issue があればそこへコメントで寄せる(新規の起票はしない。後継は既存へ寄せる)。

理由: 2委員とも、番号を自由に書ける場所へ足しても権限者の偽装を検出しないと見る。議長も同じ。保護は1名の体制で自分を縛る設定であり、ソロ期の運用との関係を本件の材料では決められない。

採らない案: 本束で実行の番号の突き合わせを実装する(検出できるものが 1-2 の条件と重なる)。

### 争点1-5 「課さない」の明記 — **ADR-0157 を立てる**

裁定: 新 ADR-0157 で、ADR-0090 決定8 の次の2項目を候補から決定へ移す(ADR-0090 の本文は書き換えない。ADR-0157 のステータスの表で一部置き換えを宣言する)。

- 「受け手の検証」: 採用者の義務にしない。手引きの手順を置く
- 「来歴の証明(artifact attestation)」: 文書の配布には課さない。再開の条件は、配布を単一の成果物(tarball・パッケージ)にするとき
- 「`dist/standard` の各コミットと `main` の CI の実行との突き合わせ」と「配布の経路の変更(Pages)」は候補のまま残す

ADR-0077 L108 の開示(`VERSION.md` は自由に書けるので実行の番号を Actions の記録と突き合わせる)は置き換えない。起案は手引きへの誘導で置き換えるとしたが、L108 は配る側の弱点の開示として今も正しい。手引きの条件1・2 は弱点を消さず、別の確かめ方を足すだけである。

採らない案: ADR を立てず手引きの冒頭だけに書く(ADR-0090 決定8 と食い違ったまま残る)。ADR-0077 L108 を置き換える(上の理由)。

### 争点2-1 compute-strategy に1名の体制の列を足すか — **列は足さない。参照の1文を足す**

裁定: 2委員とも列を足さない。議長も同じ。git-strategy.md L138 の1名の行を正本とする。compute-strategy.md の L124 の段落の直後に、段の構成の差だけを書く1文を足す(文案は5章)。git-strategy.md L138 は変えない。

採らない案: 1名の体制の列・節の新設(git-strategy と二重になり乖離のもと)。git-strategy の1名の行に「プッシュ前が重くなる」を足す(反対委員が境目と見た点。段の構成の説明は compute-strategy の役目であり、1名の行は体制の条件を書く場所である。足さない)。

### 争点2-2 「PR」の語の中立化 — **編集の指摘として議長が直す**(会議体なし、独立の突合を1回)

L24・L37 の2か所(文案は5章)。L124 の「PR を経る体制では…」は体制を区別して書いており、直さない。

### 争点2-3 落ちた後の扱い(revert・ロック) — **課さないと明記する**

裁定: 条項にしない。2-1 の1文の中で、本標準は revert も既定ブランチのロックも求めないと書く。

理由: 「push そのものは止めない」(git-strategy L138)と緊張する。公開・配布を集約の通過に結線する体制では、落ちた版は外へ出ない。失うのは案件の既定ブランチの健全性に限られる。トランクベース開発の「速やかに revert」の出典は E0〜E1 である。

採らない案: revert の義務、ロックの義務。「望ましい」の推奨(起案の文案)。推奨の語は根拠水準マークを要する実務の主張になり、出典が E0〜E1 で支えられない。事実(本標準は求めない、外へは出ない)だけを書く。

## 2. 所有者の方針の3つの問いの通し方

| 問い | 論点1 | 論点2 |
| --- | --- | --- |
| (1) 条文は結果と証跡まで、手順は手引き | 条文を足さない。手順(2条件のコマンド)と保証の範囲は手引き。配る側の検査は標準のリポジトリの運営であり、ADR-0157 に記録する | 条文を足さない。phase5 は手引き |
| (2) 第7章の例外承認で受けられないか | 義務を課さないので、例外承認は要らない。義務を課す案(案A・義務化)は、例外承認で受けられても新しい義務である判定を変えない(intake 4章) | 該当しない |
| (3) 破られたとき誰が何を失うか | 識別が誤っていると、採用者は辿れないコミットを名指して表明する。表明の読み手は確かめられない。知識ベースが差し替えられると、判定基準が緩みうる(CL の高い案件で重い)。0章の実例では中身は正しく、失われたのは識別の追跡可能性。**塞ぐのは配る側の検査**であり、採用者は何も負わない | 案件の既定ブランチの健全性。外へは出ない |

条項を足すときに削れる既存の条項と小さいチームでの省き方: 本件は条項を足さないので、削る条項は無い。手引きの手順は任意で、小さいチームは行わなくてよい。行う場合も、適用の開始と版の切り替えの2回、2コマンドずつ。配る側の検査は採用者に費用を生まない。

## 3. 統制の閉じ方

| 統制 | 閉じ方 | 理由 |
| --- | --- | --- |
| 同梱の知識ベースの `source.commit` が 40 桁の16進 | 機械(既存の `commitProblems`) | 構文 |

実装マーク: **不要**。1.10.2 を変えず、新しい規定が実行主体(採用者・エージェント)を制約しない。配る側の検査は標準のリポジトリの検査で、`impl-targets.yaml` の降ろし先(テンプレート側)に当たらない。IMPL-NEW1 は使わない。

根拠水準マーク: **EV-NEW1 を1つ**(手引きの手順の節。下の文案)。ADR-0157 の本文にも同じ限界を書き、EV-NEW1 を参照する。

新 ADR: **ADR-0157**「受け取り側の生成元の確認を義務にせず手順を示し、準拠テンプレートへ複製する知識ベースの生成元を既定ブランチの履歴に限る」(題は実装の段で整えてよい)。決定は次の5つ。(1) 受け取り側の確認を課さない。手引きを置く。(2) artifact attestation を文書の配布に課さない。再開の条件。(3) 同梱の知識ベースの生成元を `HEAD` の祖先に限る機械の検査。(4) 実行の番号の突き合わせと配布の経路は候補のまま。(5) 1名の体制の段の列を足さず、revert・ロックを課さない。検討した選択肢の表に、本書の「採らない案」をすべて写す。ADR の索引(`adr/index.md`)へ行を足す。

### 5.1 `community/standard-editions.md` に節を足す(「配布物への版の記録」の直後)

文案:

```markdown
## 受け取り側が生成元を確かめる手順

本標準は、この確認を採用者に課しません([ADR-0157](/process-compass/adr/0157-…/))。適用の表明の読み手・監査する者・採用者のだれでも、適用の開始と版の切り替えのときに行えます。確かめた結果を表明に添えてもかまいません。

確かめるのは2つの条件です。標準のリポジトリを履歴ごと取得した clone の中で実行します。

| 取り込みの形 | 条件1(来歴) | 条件2(中身) |
| --- | --- | --- |
| `dist/standard` のコミット D を固定する | `VERSION.md` のコミット S について `git merge-base --is-ancestor S origin/main` が成功する。`tailoring-kb.json` の `source.commit` が S と一致する | `git diff --quiet S:src/content/docs D:docs` が成功する |
| 準拠テンプレートの同梱の知識ベース(`source.commit` が S) | 同上の祖先の確認 | `source.commit` が S である `dist/standard` のコミット D の `tailoring-kb.json` と、同梱の知識ベースがバイト一致する。D が無いときは未確認とする |

- 確かめられるのは、名指したコミットが確かめた時点で既定ブランチの上にあり、中身が CI の生成物と一致することまで
- 本文が正しいことは確かめない
- 確かめた後の既定ブランチの書き換えは検出しない
- 保守者の権限で既定ブランチへ書かれた変更は、CI が配布するため検出しない

:::caution[暫定 EV-NEW1 / 見直し 2027-05]
(手順が偽装した配布物を落とすことは、使い捨てのリポジトリと 2026-11 の配布物の1時点で確かめただけです。確認は1時点の事実で、既定ブランチの書き換えの後は結果が変わります。)
:::
```

実装の担当は、6章の結果に合わせて caution の本文の事実を直す。コマンドは6章で実際に流したものと一字一句合わせる。

### 5.3 配る側の検査

- `scripts/lib/inputs.mjs`(または `check-gate-criteria.mjs`)に、既定の対象の知識ベースの `source.commit` が `HEAD` の祖先かを確かめる処理を足す。`--kb` のときは既存の `GITHUB_SHA` の検査を使う
- 祖先でない: 問題「テンプレートへ複製した知識ベースの生成元(<12桁>)が、標準の履歴の上にありません。rebase の後は `npm run template:kb` で再生成してください(ADR-0157)」
- 履歴を読めない(`git cat-file -e` の失敗・浅い clone): 問題とする(未確認を通さない)
- 試験: 既存の一時 git リポジトリの試験(`npm run test:edition` の型)に倣い、祖先・非祖先・存在しないコミット・浅い clone の4例を足す
- **テンプレートとの順序(直列)**: 0章のとおり、現在のテンプレートの main の知識ベースは非祖先であり、この検査を入れると `npm run check` が落ちる。本束はテンプレートを触らないので、次のどちらかを束の議長が選ぶ。(i) 本束の最後のテンプレートの参照を進める段(他の Issue の段)で、最後の rebase の後に `npm run template:kb` を流し直し、その段に検査を入れる。(ii) 検査をテンプレートを触る次の束へ回し、ADR-0157 の決定3 に「降ろすまでの間は未達」と書き、Issue にコメントを残す。**(i) を推す**。0章の食い違いは「高」で、束ごとの rebase で再発するため
