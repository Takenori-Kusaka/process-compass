# #332 起案委員の意見書(軽の会議体、2026-11-17)

材料: `intake-ruling.md`、`intake.md`。確かめた条文: `phase4-process-design/overview.md` L650・L657(1.10.2 の適用の表明の併記事項。作業中の版は「名指してよい」)、`phase5-implementation/git-strategy.md`(段階導入の表、1名の行)、`phase5-implementation/compute-strategy.md` L24・L37・L124、`adr/0090` 決定8 の行(L18。「来歴の証明と配布の突合は後継の Issue の候補」)。

## 方針の3つの問いへの総括

| 問い | 論点1 | 論点2 |
| --- | --- | --- |
| (1) 結果と証跡まで、手順は手引き | 条文は「生成元の確認の結果」の併記まで。`is-ancestor`・`diff` の手順は手引き(community) | 条文は増やさない。compute-strategy は手引き |
| (2) 第7章の例外承認で受けられないか | 案A は「実施せよ」でなく「実施の有無を併記せよ」にするので、閉域でも「未実施」と書けば足り、例外承認は要らない。議長が実施の義務へ上げるなら、閉域は第7章の例外承認で受ける(新しい例外の仕組みは作らない) | 該当しない |
| (3) 破られたとき誰が何を失うか | 失うのは採用者。偽装された配布物の上で作業し、適合を主張する。`tailoring-kb.json` が偽装されるとゲートの判定が緩む(安全重要度が高い案件で重い)。保守者は名前が使われる信用を失う | 失うのは案件の main の健全性。公開は `needs: check` で止まり、外へは出ない |

## 争点1-1 条文か手引きか

- **採る案**: 1.10.2 の適用の表明の併記を、1項目だけ足す。作業中の版を名指す場合に限り、「配布物のコミットの生成元の確認: 済(日付・確認した条件)/未実施」を併記する。確認の手順は community の手引きへ置く。**確認を実施する義務は課さない。実施の有無を偽らず開示させる**
- 文案(overview.md L650 の表の「適用の表明」行、「従う本標準の版(作業中の版のときは、配布物のコミットの識別を併記する)」の直後):
  「作業中の版のときは、配布物のコミットの識別に加えて、その生成元の確認の結果(済の日付と、確かめた条件。または未実施)を併記する」
  L657 の箇条書きの末尾にも同じ趣旨を1文足す(「確認の結果を併記する。未実施は未実施と書く」)
- 理由: (1) 結果と証跡のみで手順を書かない。(2) 1.10.2 は既に「配布物のコミットの識別」の併記を求めており、穴は「名指したコミットが正本由来かどうか」の開示だけ。節も欄も新設せず、既存の行へ語句を足す。(3) 「未実施」と書けば足りるので、閉域の採用者を締め出さず、例外承認の仕組みも要らない。採用者に課す新しい**行為**の義務は無い。開示の義務は、作業中の版を名指す選択をした者だけに掛かる
- 重へ上げる点: 議長が、これを「新しい義務」と判定した場合。私の見立ては、既存の併記義務の項目追加で、行為の義務ではないため軽に残る。判定は議長の裁定事項
- **採らない案**
  - 手引きのみ(案B): 開示が条文に無いと、「名指したが確認していない」が表明から読めない。表明を読む第三者は、確認済みか未確認かを区別できない。「書かれていない」と「課さないと決めた」の区別を保つ原則に反する。ただし案B は軽の範囲で最小の変更であり、私は信頼性の面で劣ると判断する(安さは理由にしない)
  - 確認の実施の義務化: 新しい義務(採用者の行為)で重になる。外部の SLSA・attestation の実務水準は、受け取り側の検証が既定だが、レジストリという信頼の根を持つ npm の例であり、submodule には根がない。実証(E1、1時点)が薄い義務は課さない
- 削れる既存条項: ADR-0077 の「`VERSION.md` は自由に書けるため実行の番号を Actions の記録と突き合わせる」の配布側の注記は、受け取り側の確認と重複する。新 ADR(1-5)で「手引きの確認へ誘導」に置き換える。ADR 本文は書き換えない
- 小さいチーム: 併記は1行。確認は適用の開始と版の切り替えの2回、2コマンド。省ける: 署名の鍵、attestation、正本の常時ミラー

## 争点1-2 検査の強さ

- **採る案**: (b) 祖先+本文の一致。条文は強さを指定せず結果で書く(「生成元が正本の既定ブランチの履歴の上にあり、配布物の本文が生成元の本文と一致すること」)。(b) の具体は手引きに置く
- 理由: 実行での確認(intake 1.2)で、(a) は実在の SHA を書いて中身を差し替えた配布物を通す。(b) の2条件はどちらも決定可能(存在・一致)
- **採らない案**: (a) 偽装を通す。(c) 再生成して知識ベースまで一致: 採用者の環境にビルド一式を要し、再現性が環境に左右され、決定可能でも費用が重い。手引きの「より強い確認」として言及はしてよい。(d) attestation: GitHub が個別の文書ファイルを対象にすべきでないと明記しており、git のコミットとして取り込む型と合わない。SRC-0459 のとおり署名は「誰のビルドか」を言うだけで中身の良さを言わない。課さないと決めた旨を1-5で明記する
- 限界の開示: 検査は「ある時点の事実」であり、後の force push や main の書き換えは検出しない。手引きにこの限界を書き、根拠水準マーク(暫定 EV-NNNN、実証は run 146 の1時点)を付す

## 争点1-3 だれが・いつ

- **採る案**: 採用者が、適用の開始時と版の切り替え時に1回行い、結果を適用の表明へ併記する。継続の検査にしない
- 機械の検査にする部分は決定可能な条件に限る。準拠テンプレートの契約検査は、`VERSION.md` の生成元が40桁の形式であること、`tailoring-kb.json` の `source.commit` と `VERSION.md` が一致することだけ。ネットワークを要する祖先の確認と本文の一致は、manual(採用者が行い表明へ記録)とし、実装マーク `state=undelivered` または adopter で開示する(自由な文の意味や改ざんの防止は機械で閉じない)
- 理由: 毎回の CI で正本を取得すると外部ネットワーク依存が CI の信頼性を落とす。リスクは版の取り込みの時点に集中する
- **採らない案**: テンプレートの検査で祖先・本文の一致まで自動化する案。ネットワーク依存と、正本が書き換えられたときに後から落ちる不安定さで、判定の信頼性が下がる
- template に及ぶ分(本束では触らない。Issue のコメント用の一覧):
  1. 契約検査: `VERSION.md` の生成元の形式と、`source.commit` との一致(機械)
  2. 適用の表明の様式に「生成元の確認」欄を足す
  3. 取り込みの手順(submodule での固定、確認の2コマンド)を手引きへ
  4. 未読: `template/` の取り込みの形は未初期化のため未確認。実装の段で確かめる

## 争点1-4 配布側の補強

- **採る案**: 本束では足さない。ADR-0090 決定8 の「配布の突合」は後継の候補として残す(課さないと決めたのではなく、まだ決めない、と区別して書く)
- 理由: 実行の番号を `dist/standard` のコミットに持たせても、`VERSION.md` が自由記述である弱点は残る。(b) の確認が中身の差し替えを直接検出する。両方を足すと二重で、乖離のもとになる
- **採らない案**: 今回の導入。理由は上のとおり、費用に対し検出できるものが(b)と重なる
- 反証が出たら見直す条件: コントリビューターが書き込み権を得たとき(見直し 2027-04 相当)

## 争点1-5 「課さない」の明記

- **採る案**: 新 ADR を1本立てる。ADR-0090 決定8 を一部置き換える(本文は書き換えない)。内容: (1) 受け手の確認の実施は課さず、併記による開示を課す。(2) attestation は課さない(型が合わない、GitHub の指針、署名は中身を保証しない)。(3) 配布の突合は後継の候補のまま。(4) ADR-0077 の注記を手引きへの誘導で置き換える。根拠水準マークで、実証が1時点であることを開示
- 理由: 「書かれていない」と「課さないと決めた」の区別を保つため
- **採らない案**: 本文だけに書き ADR を立てない。ADR-0090 決定8 と食い違ったまま残る

## 争点2-1 compute-strategy に1名の体制を足すか

- **採る案**: 列も節も足さない。git-strategy の1名の行を正本とし、compute-strategy は参照にする。末尾の段落(L124)の直後に1文だけ足す
- 文案: 「PR を経ない体制(git-strategy の1名の行)では、プッシュ前の全量の実行が、PR を経る体制での手元の検査より重い役割を持つ。判定は、既定ブランチへの push の後の集約が担う。集約が落ちたときは、次の作業より先に直すことが望ましい(revert でもよい。[Git 戦略](/process-compass/phase5-implementation/git-strategy/))」
- 理由: 規範でなく手引きの置き場。二重の記述は乖離のもと。構成の差(プッシュ前が重い)だけを書く
- 問い(3): 放置の損失は main の健全性で、配布は止まる
- **採らない案**: 1名の列の新設。git-strategy と重複し、同期の保守が要る
- 注: 「望ましい」とし、「しなければならない」にしない(2-3 参照)

## 争点2-3 落ちた後の扱い(revert)

- **採る案**: 条項にしない。手引きの2-1の1文で足りる
- 理由: 標準は push そのものを止めない原則(git-strategy 1名の行)。revert や main のロックを義務にすると、原則と緊張する。落ちた main は公開・配布を `needs: check` が止め、外へ出ない。破られた損失は案件内に限られる
- **採らない案**: revert の義務、ロックの義務。Trunk Based Development の実務は revert を原則とするが、出典は実務サイト(E0〜E1)。実証の無い義務は課さない
- 削れる条項: なし。足す条項もない

## 議長に残す点

- 1-1 を「新しい義務」と判定するかの判定。私は開示の項目追加で軽に残ると見るが、反対委員が「開示の義務は実質的な圧力」と主張する可能性がある。その場合の落としどころは、併記を「してよい」(任意)にして、未実施の開示を求めない案。ただしそれは案B に近く、表明の読み手が区別できない欠点が残る
- 2-2(「PR」の語の中立化。compute-strategy L24 の「PR を遅くせずに」、L37 の「PR で回し」)は編集の指摘として議長が直す
