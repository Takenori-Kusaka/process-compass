# #332 反対委員の意見書(軽の会議体、2026-11-17、束 B11)

立場: 起票者の提案と調査の見立てを疑う。課さない・変えない・別の形で受ける案を最も強く立てる。判断軸は信頼性。安さ・変更量の少なさは理由にしない。
読んだもの: `intake-ruling.md`、`intake.md`、ADR-0090 決定8 の参照箇所(L18)、git-strategy.md の段階導入の表。`template/` は未初期化のため読めていない(intake.md 8章と同じ限界)。

## 総論

調査の見立ての中心は「(b) 祖先+本文の一致」を採用者に確かめさせる、である。この見立てには3つの弱点がある。

1. **脅威が検出対象と合っていない**。調査自身が認めるとおり、最も確からしい脅威は事故であり、事故への抑止は #293 で既に効いている。(b) が効くのは、書き込み権限者の侵害か悪意の場合に限られる。その場合、攻撃者は `VERSION.md` を偽る前に、`main` 側の本文を書き換える方が安い。(b) は「正本の main の上にある」ことしか言わない。**main の上の本文が正しいことは言わない**。信頼の根は変わらず正本の保守者に残る。
2. **検査は「ある時点の事実」にすぎない**(intake 1.2)。正本の force push で後から no になり得る。main にルールセットが無い現状では、検査の価値は main 側の保護に依存する。保護を足す(配る側の根本策)前に受け取り側へ義務を課すのは順序が逆である。
3. **実証が1時点・1件(run 146)のみ**で E1。「偽装を検出できる」ことは実行で確かめていない。確かめたのは、正常な配布物が検査を通ることだけである。偽装した配布物を作って落ちることの確認(目隠しの反例)が無い。

## 方針の3つの問い(全体)

| 問い | 通した結果 |
| --- | --- |
| (1) 条文は結果と証跡までか | 条文にできるのは「確認した結果を適用の表明に書く」までである。ただしそれは新しい義務になる(争点1-1)。手順(`merge-base`、`diff`)は手引き |
| (2) 第7章の例外承認で受けられないか | 受けられるが、それは義務化の免罪符にならない。例外で受ける前提の義務は、大半の採用者が例外を申請する条項になり、例外の濫用か形骸化を招く。ネットワークが無い採用者より、**確認を省く採用者**が多数派になる |
| (3) 破られたとき誰が何を失うか | 失うのは採用者(誤った規範で適合を主張)。保守者は評判。第三者の被害は間接的。破られる経路は権限の侵害に限られる。事故は配る側が抑止済み |

## 争点ごとの意見

### 争点1-1: 条文にするか手引きにするか

- **採る案**: 案B。条文は課さない。手引き(community)に「受け取り側の確認の手順」を置く。
- **理由**:
  - 義務の発生源が無い。ADR-0090 決定8 は「課さないと決めたのではなく後継の候補」とだけ言う。候補は義務の根拠ではない。
  - 1.10.2 の併記は「識別」を求める条項である。「識別の正しさの確認」を足すと、表明の意味が「名指した」から「検証した」に変わる。**表明の意味の変更**であり、ADR-0083 の原則に触れる。
  - 脅威(権限の侵害)に対して効くのは配る側の統制である。受け取り側の自己申告は、攻撃者が侵害した環境では偽れる。
- **調査の見立ての弱点**: 「最小の増加」と述べる(5章)。増加の少なさは採否の理由にならない。しかも「新しい節は不要」でも義務は新設される。
- **採らない案**: 案A(1.10.2 に確認の結果を足す)。採らない理由は上のとおり。かつ採ると重へ上がる(採用者への新しい義務)。
- **重への上げ方**: 案A が裁定で残るなら重。私は上げずに案B で閉じることを勧める。

### 争点1-2: 検査の強さ

- **採る案**: 手引きに書く検査としては (b)。条文に書く強さとしては、何も書かない。
- 手引きで (a) だけを書いてはならない点は調査に同意する。実在の SHA を名乗って中身を差し替えた配布物を (a) は通す。
- **ただし**、手引きでも (b) に「何を保証し、何を保証しないか」を明記する。(b) は main の上の本文との一致であり、本文の正しさではない。保証しないことを書かないと過信を生む(SRC-0459 と同型)。根拠水準マーク(暫定)で、実証が1時点であることを開示する。
- **採らない案**: (c) 再生成して KB まで一致。再生成は採用者の環境の依存(node の版など)に左右され、決定可能でない。偽陽性で採用者を止める。(d) attestation。型が合わず(個別の文書は非推奨)、取り込みの形の変更を伴う。調査に同意する。

### 争点1-3: だれが・いつ行うか

- **採る案**: 採用者の手引きとして、適用の開始時と版の切り替え時に任意で行う。準拠テンプレートの契約検査には入れない。
- **理由**:
  - テンプレートの検査にすると、ネットワーク依存が CI に入る。調査自身が「CI の信頼性を落とす」と認めている。
  - 機械で閉じる部分(40桁の形式、`VERSION.md` と KB の `source.commit` の一致)は決定可能なので、**配る側の `check` で既に検査できる**。確認はこちらで行う。受け取り側のテンプレートへ重複させない。
  - ネットワークを要する部分は、機械で閉じない統制である。CLAUDE.md の裁定どおり manual か adopter とし、根拠水準マークで開示する。
- **調査の見立ての弱点**: テンプレートへ降ろす案が残るが、`template/` を読めていない。取り込みの形を確かめずに検査の置き場を決められない。この点は次の段で確かめる事項であり、本束で決める根拠が無い。
- **採らない案**: テンプレートの契約検査。上の理由。

### 争点1-4: 配布側の補強(CI の実行番号を各コミットへ)

- **採る案**: 採るなら配る側の仕事として別 Issue に分ける。ただし本件の裁定には含めない。
- **理由**: 調査自身が「VERSION.md の自由記述の弱点は残る」と書く。書き込み権限者が偽れる場所へ番号を足しても、権限者による偽装は検出できない。検出できるのは Actions の記録と突き合わせる第三者(受け取り側)だけで、それは1-2の確認と同じ負担を受け取り側へ課す。
- 配る側の根本策は、`main` と `dist/standard` へ保護(ルールセット、Actions だけが push できる)を掛けることである。これは権限者による偽装を構造として塞ぐ。受け取り側の検査より信頼性が高い。**ただし1名の体制で自分自身を縛る設定は、ソロ期の運用との緊張がある**(要確認、本束の範囲外)。
- **後継の扱い**: 既存の open Issue があればそこへコメントで足す(後継は既存へ寄せる原則)。
- **採らない案**: 本束で決定8 の候補を実装すること。順序と検証が足りない。

### 争点1-5: 「課さない」場合の明記

- **採る案**: 明記する。ただし ADR-0090 を書き換えず、新 ADR か手引きの冒頭で決定8 の候補を「受け取り側の義務としては課さないと決めた」と置き換える。
- **書く内容**: (i) 課さない。(ii) 理由は、脅威が権限の侵害に限られ、配る側の統制が根の対策であること、検査が1時点の事実であること。(iii) 手引きの確認は任意で、保証の範囲は (b) まで。(iv) 再開の条件。コントリビューターが書き込み権を得たとき、または `main` に保護が掛けられないと決めたとき。
- **理由**: 「書かれていない」と「課さないと決めた」を区別する、というコアポリシーの要請。
- **注意**: 「課さない」は ADR の原則の変更に当たらない(決定8 が候補としていたものを、候補から却下へ移すだけ)。新 ADR を要するかは、手引きの冒頭の記述で足りるかの議長の裁定事項とする。私は新 ADR を勧める(あとから変えにくい決定は ADR に残す規約)。

### 争点2-1: compute-strategy に1名の体制の列/節を足すか

- **採る案**: 案B。足さない。git-strategy.md の段階導入の表(1名の行)を正本として参照する。**ただし食い違いの解消は行う**。
- **理由**: 二重の記述は乖離のもと。調査も正本は git-strategy と認める。
- **調査の見立ての弱点**: 「足りないのは段の構成の表の1名の列だけ」と見立てるが、表の列を足すと、体制ごとの「プッシュ前が重くなる」といった**構成の差の説明**がphase5 の側に二重化する。差の説明は git-strategy の1名の行へ寄せ、compute-strategy は「体制によらず、集約の段は同じ。体制ごとの設定は git-strategy を見る」の参照1文にする。
- **足すべきは**: git-strategy 側の1名の行に、「プッシュ前の全量が PR のレビューの代わりに重くなる」を一言足すかの判断である。これは編集の範囲か意味の追加かの境目である。意味の追加(新しい要請)なら軽の審議に掛け直す。私は足さない側。
- **採らない案**: compute-strategy に列を足す案A。二重の記述になる。

### 争点2-3: 落ちた後の扱い(revert)を条項にするか

- **採る案**: 条項にしない。手引き(git-strategy の1名の行の注記、または compute-strategy の末尾)に「落ちたら次の作業より先に直す。revert でもよい」を置く。
- **理由**: 「push そのものは止めない」という ADR の原則と、revert の義務化は緊張する。公開・配布は `needs: check` で止まるため、外へは出ない(intake 4章(3))。失うのは案件の main の健全性だけで、第三者の被害は無い。条文の水準に上げる安全上の理由が無い。
- **明記する**: 「課さないと決めた」と書く。「書かれていない」ままにしない。
- **調査の見立ての弱点**: Trunk Based Development を根拠にするが、出典は実務サイトとブログで E0〜E1。しかも前提は「高速な CI を push 直後に回す」である。標準の CI の所要時間は前提を満たすと確かめていない。「速やかに revert」を標準の語にするなら暫定マークを要する。
- **採らない案**: revert の義務化。上の緊張と実証の欠如。ロック(トランクの一時ロック)も、1名の体制では意味を成さない(自分で自分を止める)。

## 重へ上げるべき点

- 争点1-1 で案A(条文で確認の結果を求める)が裁定に残った場合は**重**(採用者への新しい義務、かつ表明の意味の変更で ADR-0083 の原則に触れる)。5 委員で、起案・現場・品質監査・規格・弁護を揃え、外部の調査(規格の引用)を足す。
- 案B(課さない)で閉じるなら軽のまま。
- 安全: CL が高い案件で KB の改ざんがゲートの判定を緩める点は、安全の論点に近い。ただし防ぐ手段は受け取り側の自己確認でなく、配る側の保護と KB の検査である。これは本束の範囲外であり、別 Issue(既存へ寄せる)で扱う。

## 反対委員としての総括

- 受け取り側の検査は**手引きの任意の手順として置き、保証の範囲を明記する**。条文の義務にしない。
- 却下(課さない)を新 ADR で明記し、再開の条件を書く。
- 本物の対策は配る側の保護である。受け取り側の確認は、その代替でなく補助である。
- 実証は1時点・正常側のみ。**偽装した配布物が (b) で落ちることを、使い捨てリポジトリで確かめてから手引きに書く**。この確認を実装の段の条件にする。
- 論点2 は参照1文と注記1行で足りる。列を足さない。revert は義務にしない。
