作成: 2026-11-17。担当: 受付と調査。次の段は議長の裁定の案(会議体)。条項・src/ は変更していない。

## 1. 受付の見立て

### 1.1 起票者の主張の検証(前提を置かない)

| 主張 | 検証 | 結果 |
| --- | --- | --- |

### 1.2 実行での確認(scratchpad と実リポジトリの読み取り)

- `git merge-base --is-ancestor <生成元> origin/main` は、main 上の SHA で yes、別枝のコミットで no を返す(scratchpad の使い捨てリポジトリで確認)
- 実物の `origin/dist/standard`(62 コミット、先頭の `VERSION.md` の生成元 `154c2086`)に同じ検査を行うと、`origin/main` の上で yes
- `git diff --stat <生成元>:src/content/docs origin/dist/standard:docs` は**差が空**。配布物の `docs/` は、生成元コミットの本文とバイト一致する。`tailoring-kb.json` の `source.commit` も `VERSION.md` と一致
- 発見: **「生成元が main の上にある」だけでは弱く、「配布物の中身が生成元コミットの本文と一致する」まで確かめて初めて、書き込み権限者が `VERSION.md` を偽っていないことを検出できる**。前者だけだと、実在の main の SHA を書いて中身を差し替えた配布物を通す。どちらも決定可能な条件(存在・一致)で、機械の検査にできる
- 限界(実行で確かめた事実): 受け取り側は配布物の submodule だけでは生成元を持たない。正本の履歴の取得(公開リポジトリなので可能。ネットワーク要)が要る。`source.commit` の 40 桁だけでは、正本が force push で書き換えられたとき(main にルールセットが無い)に、後で no になる。**検査は「ある時点の事実」**
- 検査できなかったこと: `template/` はこの作業ツリーで未初期化(空)。テンプレートが標準をどう取り込むかは読めていない。`dist/standard` を取り込む手順は本文に無い(上記)

### 1.3 関係する条文・ADR・IMPL

- ADR-0052 決定2(生成元の版を記録する。「受け取り側が知る手段はこれしかない」)、決定4(配布物は正本から生成)
- ADR-0077(配布の結線、強制 push の廃止、`VERSION.md` は書き込んだ者が自由に書けるため実行の番号を Actions の記録と突き合わせる)
- **ADR-0090 決定8**: 「配布の経路の変更(受け手の検証・各コミットと main の CI の突き合わせ)・来歴の証明(artifact attestation)」は**課さないと決めたのではなく、後継 Issue の候補**。本 Issue はこの候補の受け皿。#332 の論点1 は ADR-0090 決定8 の再開であり、「新しい義務」の側面を持つ
- ADR-0083 / 第1章 1.10.2: 適用の表明に、作業中の版のとき**配布物のコミットの識別**を併記する。標準は既に、受け取り側が配布物のコミットを名指すことを求めている。しかし、名指したコミットが正本由来であることの確認は求めていない(ここが論点1 の穴)
- project-management.md「止まらない経路」L113: 書き込み権限者は `dist/standard` へ早送りの push ができ、`VERSION.md` は自由に書ける、と開示済み。論点1 はこの開示された経路の**受け取り側からの検出**
- ADR-0090 L43: リモートの main と手元の食い違い(#293 以降の変更がリモートに未反映だった時期)。2026-11-17 時点で `origin/main` の `ci.yml` は新しい publish を持ち、`dist/standard` は run 146 で追従している(上の確認)

### 1.4 矛盾・食い違い

1. compute-strategy.md の「ローカルファーストの多段検査」の図は A→B→C→D と 1名でも成り立つが、表の 4 行目「定期」の狙いに「PR を遅くせずに」とあり、PR 前提が残る。「CI コスト最適化」の表の「差分実行 … PR で回し」も同じ。#293 は「必須の検査の集約」の行しか直していない
2. 末尾段落は「PR を経ない体制では既定ブランチへの push の後の版」と書くが、push の後に集約が落ちたときの扱い(revert、ロック)の規定は無い。git-strategy.md の 1名の行も「push そのものは止めない」までで、落ちた後を書かない。Trunk Based Development の実務は「速やかに revert」を原則とする(外部 3 章)。ただし標準の本文は revert の義務までは書いていない
3. ADR-0090 決定8 は受け手の検証を「課さないと決めたのではない」とする。論点1 の裁定が「課さない」なら、その旨の明記が要る(却下は成果)

## 4. 所有者の方針の 3 つの問い

### (1) 条文は結果と証跡までで、手順は手引きへ

- 論点1: 条文に置けるのは「結果」まで。例: 「採用者は、固定した配布物のコミットの生成元が正本の main の上にあり、配布物の本文が生成元の本文と一致することを、適用の開始と版の切り替えのときに確かめ、結果を記録する」。`git merge-base --is-ancestor`・`git diff` の手順、`gh attestation verify` の使い方は**手引き**(附属書または community の手引き)
- 論点2: 条文でなく**手引き**(phase5 の compute-strategy は実装の手引きで、規範の置き場ではない。CLAUDE.md の構成でも phase5 は種別未定で規範を担えないと ADR-0086 系の裁定済み: #293 decision L86「フェーズ5 は種別が未定で規範を担えないので第4章へ置く」)。よって論点2 は規範を増やさず、compute-strategy の表へ 1名の体制の注記を足すだけで足りる見込み

### (2) 第7章の例外承認で受けられないか

- 論点1 の検査を義務化した場合、確かめられない案件(ネットワークの無い閉域、正本の履歴を取得できない)は**第7章の例外承認・逸脱で受けられる**。よって義務化しても「できない者を締め出す」ことにはならない。逆に、義務化しない場合は例外の仕組みは要らない。例外で受けられる程度の義務なら、軽〜重の境界は軽に寄る。ただし「新しい義務」の判定は例外の有無に依らない(議長の裁定事項)
- 論点2 は義務でないため該当しない

### (3) 破られたとき誰が何を失うか

- 論点1: 破られた(中身が差し替えられた、または正本に無い SHA を名乗る)ときに失うのは**採用者**。標準の本文は文書で、ビルドして実行されるコードではないため、被害は「誤った規範に従って作業し、適合を主張する」ことになる。第三者の被害(利用者の安全)は間接的。ただし `tailoring-kb.json` は機械可読で、テーラリングエンジンの入力になる。**判定基準が改ざんされると、ゲートの判定が緩む**。安全に関わる案件(CL が高い)では影響が重い。正本の保守者は、改ざんされた配布物が自分の名前で流通する評判の損失
- 脅威の確からしさ: 書き込み権限者は現在保守者 1 名(project-management.md L113)。最も確からしいのは悪意でなく事故(旧 `dist/standard` の強制 push 事故は #293 で実在。過去 14 回分が到達不能)。事故に対しては、配る側の抑止(#293)が既に効いている。受け取り側の検査は、権限の侵害(保守者のアカウントの侵害)と、将来コントリビューターが書き込み権を得た場合に効く
- 論点2: 破られたとき(直 push の後の CI が落ちたまま放置)に失うのは、その案件の main の健全性。公開・配布は `needs: check` で止まるので、外へは出ない

## 5. 既存の条項を削れないか

- 論点1: 新設でなく、**ADR-0052 決定2 と 第1章 1.10.2 の表明の併記を活かす**案が最小の増加。1.10.2 の併記(配布物のコミットの識別)に「確認の結果」を足す。新しい節は不要
- ADR-0077 の「`VERSION.md` は書き込んだ者が自由に書けるため、実行の番号を Actions の実行の記録と突き合わせて確かめる」は、受け取り側の検査と重複する。**配布側の注記を「受け取り側の確認の手順へ誘導」に置き換えれば、重複を削れる**(ADR 本文は書き換えず、新 ADR か手引きで置換)
- compute-strategy: 末尾段落(手元の検査の定義が古いことを理由に止めない。EV-0138)は、論点2 の追加で膨らませず、**1名の体制の注記を 1 行で足す**に留める案。「定期」の行と差分実行の行の「PR」を中立語にするのは編集の指摘(ed)で、会議体を要さない
- **採らない案の候補**: attestation の義務化(文書の署名は GitHub が非推奨。型が合わない)

## 6. 小さいチームでの省き方

- 1名の案件が受け取り側の検査を行う費用は、適用の開始時と版の切り替え時の 2 コマンド(`is-ancestor` と `diff`)。継続の費用は無い。高頻度で回す検査にしない(毎 CI で正本を取得すると外部ネットワーク依存が CI の信頼性を落とす)
- 省ける: attestation、署名の鍵の運用、正本の履歴の常時ミラー
- 1名の体制の段: 保存時 → プッシュ前(全量。事実上必須。トレーラ `Risk`/`Verification` が証跡)→ push → 集約(CI)→ 落ちたら次の作業より先に直す(revert でもよい)→ 定期。PR を経ない分、**プッシュ前の全量が一段重くなる**という構成の差を明記する案

## 7. 会議体の争点の案(軽: 起案と反対の 2 委員)

起案(案A)と反対(案B)を競わせる。議長が裁定し、採らない案を記録する。

論点1
- 争点1-1: 条文にするか、手引きにするか。案A: 1.10.2 の併記に「生成元の確認の結果」を足す(結果と証跡まで)。案B: 手引き(community)のみで、条文は課さない。重へ上げる条件: 案A が採られた場合
- 争点1-2: 検査の強さ。案: (a) 祖先の確認のみ、(b) 祖先+本文の一致、(c) 再生成して知識ベースまで一致、(d) attestation。調査の含意は (b)。(a) は偽装を通す(1.2)。(d) は型が合わない
- 争点1-3: 検査をだれが・いつ行うか。採用者(適用の開始時、版の切り替え時)か、準拠テンプレートの契約検査か。テンプレートの検査にするなら「ネットワークが要る」ため機械の検査にできるのは決定可能な部分(40 桁の形式・VERSION と KB の一致)に限る。ネットワークを要する部分は manual か adopter として根拠水準マークで開示(CLAUDE.md の「統制の閉じ方」)
- 争点1-4: 配布側の補強。`dist/standard` の各コミットに main の CI 成功の実行の番号を持たせる(ADR-0090 決定8 の「突き合わせ」)。VERSION.md の自由記述の弱点は残る
- 争点1-5: 「課さない」場合の明記。却下を ADR か本文に残す。ADR-0090 決定8 を置き換える

論点2
- 争点2-1: compute-strategy に 1名の体制の列(または節)を足すか。案A: 足す(プッシュ前が重くなる、集約が落ちたら先に直す)。案B: 足さない(git-strategy の 1名の行で足りる。二重の記述は乖離のもと)。調査の含意: git-strategy.md L138 が正本で、compute-strategy は参照にして重複を避けるのが整合的
- 争点2-2: 「PR」の語の残り(定期の行、差分実行の行)の中立化は編集の指摘として議長が直す
- 争点2-3: 落ちた後の扱い(revert)を条項にするか。実務は revert を原則とするが、標準は書き込みを止めない立場で、義務化は ADR の原則(push そのものは止めない)と緊張しうる。手引きに留める案が有力
