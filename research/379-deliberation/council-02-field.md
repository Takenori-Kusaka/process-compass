## 0. 現場から見た前提の補正

### 0.1 現場で実際に起きる書き換えは、悪意より「片付け」である

議題は書き込みの権限を持つ者とジョブのトークンによる偽装を中心に置きます。現場の目で頻度を見積もると、先に起きるのは次の善意の書き換えです。

| 起きること | 主体 | 体制 | 今の実装での結果 |
| --- | --- | --- | --- |
| AI の担い手が様式の誤字・表記を「直す」、JSON を整形する | AI の担い手(多くは本人の `gh` 認証) | 1〜2名で最も多い | 検出されない。帰属は author の一致で弱い裏づけのまま |
| 整形ツール・lint の自動修正が `records/` の JSON を書き直す | 人・CI | 全体制 | 同上 |
| 改行の変換(Windows で `core.autocrlf` の設定が人ごとに違う) | 人 | 3名以上で混在が増える | 同上 |
| 判定者が出荷の前に自分の様式を訂正する | 記名者本人 | 全体制 | 同上。訂正の前の内容は先頭から消える |
| record-copy の再実行で、同じ PR の写しが既にある | ジョブ | 全体制 | 警告で終わる(本物と同じ内容なら害は無い) |

この表から、現場の要求は2つです。

1. 検出は、悪意の書き換えと善意の書き換えを**区別せずに**拾う必要がある。区別を書き手の申告に頼れば、悪意の書き換えも善意を名乗る
2. 検出したものを**解く手続き**が無ければ、善意の書き換え1件で出荷が止まる。履歴は消せないので、検出は永久に残る。解き方の無い検出は、現場では最初の1件で無効化される(検査を外す、閾値を緩める)

### 0.2 体制・所有形態・プランで、使える保護が違う

| 構成 | 記録用ブランチのルールセット | 既定ブランチの保護 | 書ける主体の現実 |
| --- | --- | --- | --- |
| 個人所有 public(Free) | 使える〔推。外部 1.5〕 | 使える | 所有者1人と、その認証で動く AI の担い手。ジョブのトークン |
| 個人所有 private(Free) | **使えない**(README `:117` の開示の対象) | **使えない** | 同上。ここでは force push も止まらない |
| 個人所有 private(Pro) | 使える〔二次〕 | 使える | 同上 |
| 組織所有(Team・Enterprise) | 使える。Restrict updates と App の bypass、push ruleset(private)も使える | 使える | 書き込みの権限を持つ全員、ジョブのトークン、admin |

1〜2名の体制は多くが個人所有です。**脅威の主体は「他人」ではなく「同じアカウントで動く AI の担い手」**になります。ここでは主体を人に結び付ける手段(署名・push の記録)を、AI の担い手も同じように使えます(ADR-0107 の名義の共有)。この体制で検出が役に立つのは「誰が」ではなく「書き換えが起きたこと」を確かめる場面です。

## R-1 要求の形(防止か検出か)

### 結論

- **要求を「記録を残さずに書き換えられない場所」へ改める**。写しと様式の既存のファイルの変更・削除・差し替えと、記録の形に合わない追記を、出荷の証跡の集約が**履歴から機械で検出**し、欠落に数える
- **防止は求めない**。Restrict updates と専用 App の bypass による書き込みの限定は、組織所有の構成での任意の強化として準拠テンプレートに手順を置くにとどめる
- **外部の WORM・透明性ログは求めない**。代わりに、各出荷の集約が取り込んだ記録用ブランチの先頭の識別子を、既定ブランチの強制層の下にある出荷の証跡へ記録する(以下「錨」)。次の出荷の集約は、錨が今の先頭の祖先であることを確かめ、そうでなければ欠落にする
- 検出に**解き方を対で置く**。様式の訂正は既存のファイルを変えず、元を指す訂正の様式を足す形に限る。既に起きた書き換えは、書き換えたコミットを対象とする例外承認(効力を持つ記録。ADR-0106 の照合を経る)でだけ解ける

### 理由

1. 防止は、どの構成でも完全には成立しない。admin(個人所有では所有者)はルールセットを外せる(外部 0.4)。1〜2名の体制では、書ける者と判定される者が同じ人であり、防止の設定を外す者もその人である。**防止を要求すると、要求が満たされたかのように見える構成が増える**。これは EV-0185 が戒めた誤りの再生産になる
2. 検出は、全構成で同じ形で成立する。force push と削除が止まる構成では、先頭から辿れる履歴は追記だけになり、既存のファイルの M・D・R は `git log --name-status` で列挙できる(内部 3.6)。21 CFR 11.10(e) の「変更が以前の記録を覆い隠さない」とも形が合う(外部 3.1)。SLSA Source L2 も履歴の不変までを求め、内容の追記専用を求めない(外部 2.3)
3. 錨を置く理由: ルールセットを一時的に外した間の force push は、今の規則からは見えない(内部 3.6)。錨を既定ブランチの強制層の下に置けば、次の出荷で履歴の巻き戻しを検出できる。外部の WORM と比べて、新しい外部サービスを要さず、全プランで同じ形で動く。既定ブランチ自体を admin が書き換えられることは残るが、それは本標準の他の全ての記録と同じ残余であり、R-5 の開示で扱う
4. 解き方を例外承認に限る理由: 善意の書き換えを「書き換えの理由の欄」で自己申告させると、悪意の書き換えも同じ欄を書く。例外承認は効力を持つ前に記名者本人のアカウントの操作で帰属を確かめる(ADR-0106)。書き換えを受け入れる判断に、既にある最も強い照合を当てる。新しい解除の手続きを作らない理由は、同じ結果を導く手続きを2つ持つと条件の緩いほうだけが使われるため(本文 `:1927` と同じ論理)

### 体制ごとに回るか

| 体制 | 履歴の走査 | 錨 | 解き方 | 手間 |
| --- | --- | --- | --- | --- |
| 1〜2名・個人所有 public | 回る。records は小さく、走査は数秒〔推〕 | 回る | 例外承認は自己申告で受け付ける(帰属の確認者を置けない体制の既定) | 初期設定は無し。書き換えが起きたときだけ例外承認1件 |
| 1〜2名・個人所有 private(Free) | **意味を持たない**。records も既定ブランチも保護できず、force push で履歴ごと差し替えられる | 錨自体も書き換えられる | — | R-5 で「手段が無い未達」として開示する。検出が成立したとは書かない |
| 3〜9名 | 回る。改行・整形の誤検出が最も出やすい層 | 回る | 記名者以外の人の帰属の確認で例外承認 | 下記の誤検出対策を準拠テンプレートが既定で入れることが条件 |
| 10名以上・組織所有 | 回る。出荷の間隔が短くても、走査は錨からの区間だけ | 回る | 同上 | 任意で Restrict updates と専用 App による防止を重ねられる |

誤検出を抑えるために、準拠テンプレートが既定で入れるもの(要求ではなく実装の条件):

- 記録用ブランチの `.gitattributes` で改行の変換を止める(`* -text` か `text eol=lf`)
- 整形ツール・textlint・lint の対象から `records/` を外す
- record-copy が正規化した JSON を書く(キーの順・改行・末尾の改行を固定)
- AI の担い手の常駐の規則と実行時のフックで、`records/` の既存ファイルの編集を拒否する(git の push の拒否は ADR-0107 で既にある。編集そのものを止める層を足す)

### 譲れない点

- 検出したものを**所見ではなく欠落**に数える。所見にとどめると、今の `reconcileCopy` と同じく、偽の承認があっても出荷は通る
- 走査を、**判定される側が同じ変更の中で書き換えられない定義で動かす**。出荷の PR の検査は `pull_request` で PR の側のワークフロー定義を使う〔要外〕。出荷の PR が `docs/records`・`docs/gates`・`docs/evidence` 以外(とくに `.github/` と `scripts/`)を変える場合は、出荷の PR として失敗させる
- 1〜2名・個人所有 private(Free)で「検出できる」と書かない

### 採らない案

- **防止の要求**(Restrict updates・push ruleset の file_path_restriction・Restrict who can push)。理由は上記1。加えて file_path_restriction は public で使えず、Restrict who can push は個人所有で使えない(外部 1.5)。所有形態で要求の成否が割れる規定は、1〜2名の個人所有の多数を恒常的な未達にする
- **外部の WORM・透明性ログ・RFC 3161 の時刻印の要求**。S3 Object Lock は費用と別アカウントの管理を要し、artifact attestation は個人所有の private で使えない(外部 2.4)。錨で巻き戻しの検出は足り、残るのは「既定ブランチごと書き換える admin」だけで、これは外部の記録を足しても admin が外部への記録を止められる限り同じである。規制業(軸C)で監査人が外部の記録を求める場合は、採用者の追加の統制として扱い、本標準は求めない
- **書き換えを「理由の欄」の自己申告で許す案**。理由は上記4

### 反論されうる点

- 「検出は防止より弱く、規制業には足りない」: 防止を名乗れる構成は GitHub の上には無い(admin が外せる)。足りないと判断する採用者に外部の WORM を禁じてはいない。本標準が防止を求めれば、満たせない要求を満たしたと申告させることになり、信頼性が下がる
- 「訂正のたびに様式が増える」: 訂正の様式は元を指すだけの小さなファイルで、集約は最新の訂正を判定の内容として読み、訂正の連鎖を開示する。消して書き直すほうが速いが、それは 11.10(e) が禁じる形そのものである
- 「例外承認で解くのは重い」: 書き換えは本来起きない操作であり、起きたら重く扱うのが正しい。0.1 の誤検出対策を既定で入れれば、例外承認に至るのは本当に既存のファイルが変わった場合だけになる〔推。誤検出の件数を新しい EV の差し替え条件にする(R-5)〕

## R-2 写しと API の突合の向きと、G-6 の数え方

### 結論

- **ホスティングの記録(API)を正とする**。G-6 の承認の数は、API が返すレビューで数える。写しは、API が同じレビューを返せないとき(承認者のアカウントの削除など)の**代わり**としてだけ使う
- 写しを代わりに使えるのは、写しの履歴が清浄なとき(record-copy の形のコミットで、PR の `merged_at` より後に1回だけ追加され、以後 M・D が無い)に限る
- 比べる欄と扱い:

| 欄 | 扱い |
| --- | --- |
| `id`・`user.id`(数値)・`commit_id`・`submitted_at` | 不変の欄〔要外〕。不一致は**欠落**(写しの書き換え) |
| 写しにだけあるレビュー | API の書き手が削除済みアカウント(ghost)でなければ**欠落**。削除済みなら所見(写しを代わりに使う) |
| API にだけある承認 | 所見(写しの取り漏れ)。数は API で数えるので G-6 には影響しない |
| `state` | 写しが APPROVED で API が DISMISSED のとき、dismiss の時刻(タイムラインの記録)が `merged_at` より後なら所見(マージの時点の承認は成立)。前なら**欠落** |
| 本文 | 編集の履歴(`lastEditedAt`・`userContentEdits`)〔要実機〕で、`copied_at` より後のホスティング側の編集があれば所見(EV-0220 の論点)。無ければ**欠落**(写しの側の書き換え) |
| `user.login`・`author_association` | 所見。改名・所属の変更で正当に変わる |

- **API の取得失敗は、一致とも不一致とも数えない**。「未照合」として G-7 の判定を保留させ、再実行で解く。取得失敗を黙って写しで代替する経路は置かない
- **出荷の後は、基底ブランチの複製を正とする**。`mergeRecordSources` と G-7 基準5 の向きを逆にし、出荷済みの範囲で records が基底の複製と食い違えば、records の側の書き換えとして欠落に数える(次の出荷で R-1 の走査と合わせて出る)

### 理由

1. 写しの原本はホスティングにある。原本と照らせるのに、書き換えうる写しを優先する理由は無い。今の `fromCopy ? fromCopy.reviews : apiReviews` は、EV-0185 の「書き換えられない記録として扱わない」と実装が食い違っている(内部 6.1)
2. それでも写しを残す理由は、写しの目的が「ホスティングの記録が失われたとき」にあるから(EV-0112 の差し替え条件の「承認者のアカウントの消失」)。API を正にしたうえで、API が答えられない場面にだけ写しを使い、その写しは履歴で清浄さを確かめる。これで写しの価値を保ったまま、偽の写しの効き目を消せる
3. 不変の欄と可変の欄を分ける理由は、**現場の誤検出の大半が可変の欄から出る**から。承認者の改名、組織への出入り、本文の誤字の直し、マージ後の dismiss は、どの体制でも正当に起きる。これらを欠落にすると、10名以上の体制では出荷のたびに数件の誤検出が出る〔推〕。数値の識別子で対応づけ、可変の欄は所見にする
4. 出荷の後の向きを逆にする理由: 既定ブランチの複製は強制層の下にあり、records より強い置き場である。今の向きでは、出荷の後に records だけを書き換えた者が、正しい基底の複製を「人が書き換えた記録」に見せかけられる(内部 2 の表)。弱い置き場を正にする理由は無い

### 体制ごとに回るか

| 体制 | API の照合 | 手間・負荷 |
| --- | --- | --- |
| 1〜2名 | 回る。PR の数が少なく、API の呼び出しは数十件 | 追加の手作業は無い |
| 3〜9名 | 回る | 同上 |
| 10名以上 | 回るが、**呼び出しの数に注意**。出荷の範囲が数百 PR になると、PR ごとに REST を3本(reviews・timeline・編集の履歴)引けば、ジョブのトークンの上限(リポジトリあたり毎時 1,000 件程度〔要外〕)に届く | GraphQL で複数の PR をまとめて引く実装を条件にする。上限に当たったら「未照合」で保留し、欠落とも一致とも数えない |

個人所有・組織所有、無料・有料で差は出ません(PR のレビューの API はどのプランでも読める〔推〕)。

### 譲れない点

- 写しを API より優先して数えない
- API の取得失敗を「一致」にしない。取得失敗のまま出荷を通すと、API を止めれば偽の写しが通る経路が開く
- 可変の欄(ログイン名・所属・事後の dismiss・ホスティング側の編集)の差を欠落にしない。これを欠落にすると、現場は最初の改名で突合を外す

### 採らない案

- **写しを正とし、API との差を所見のまま残す今の形**。理由は上記1
- **API だけを使い、写しを廃する案**。承認者のアカウントの削除で、成立していた承認の証拠が消える。記録の保持の期間(EV-0112)を満たせない
- **全欄の不一致を欠落にする案**。理由は上記3

### 反論されうる点

- 「ghost のとき写しを使うなら、偽の写しを足してから承認者を削除させれば通る」: 他人のアカウントの削除は、判定される側にはできない。自分のアカウントを削除すれば、記名者の側も消える。残るのは「写しの履歴が清浄でない」場合で、これは R-1 の走査で欠落になる
- 「レビューの `commit_id` と `submitted_at` は本当に不変か」: 〔要外〕。不変でなければ、その欄を所見の側へ移す。実機で確かめるまで、不変の欄の扱いを EV で開示する

## R-3 様式の帰属(署名の無い author の一致)

### 結論

- **署名の無い author の一致を、判定記録の帰属の裏づけに数えない(候補 b を採る)**。裏づかない様式は、記名が自己申告の記録として保証の開示へ出す。欠落にはしない(判定記録の帰属は事後でよいという ADR-0106 の区分を保つ)
- 本文 `:127` の「署名の無い push は、author の一致による弱い裏づけである」を削る。「記名者本人の push」は、push の主体をホスティングの記録から機械が読める場合に限って裏づけに数える。読めない間は数えない〔要実機: リポジトリの活動の API が push の actor を返すか、保持期間〕
- 署名の検証を、手元の `%G?` からホスティングの検証(コミットの `verification.verified`)へ移す。照らす条件は効力を持つ記録(`introducedBacking`)と揃え、committer と author の両方が記名者の数値の識別子であることを求める
- 照らすコミットは、**records で様式を追加したコミット**とする。基底へ運んだ squash のコミットや、最後に触ったコミットではない
- 署名の鍵を持たない人のための経路を、準拠テンプレートが既定で用意する。本人の `gh` 認証での API 経由のコミット(`createCommitOnBranch`)か、Web の画面からのコミットは、ホスティングが署名し、本人のアカウントに結び付く〔要実機〕。鍵の管理を要さない

### 理由

1. git の author は書き手が自由に設定でき、git の文書自身が「認証に影響しない」と書く(外部 4)。NIST AU-10(4) の「レビュー者の識別子と情報の結合の検証」にあたらない。弱い裏づけと書いても、集約は `backed: true` に数えており、読み手は区別できない
2. 同じ標準の中で、効力を持つ記録はホスティングの検証と committer・author を求め、判定記録は手元の `%G?` と author だけを読む。照合の強さが二重になっている(内部 6.6)。CI の runner には鍵束が無いので、手元の `%G?` は CI ではほぼ成立せず、実際に効いているのは author の一致だけである〔推〕
3. 最後に触ったコミットで照らすと、書き換えた者で帰属が上書きされる。R-1 で書き換えを検出しても、帰属がその書き換えで「裏づいた」ことになれば、検出の意味が失われる
4. 署名の鍵の運用を全員に課す必要は無い。ホスティングが署名する経路があれば、鍵を持たない人も本人のアカウントで裏づけられる。ADR-0106 決定7 が退けた a2 の理由(1〜2名で鍵の運用を既定にする根拠が無い)を避けられる

### 体制ごとに回るか

| 体制 | 起きること | 判断 |
| --- | --- | --- |
| 1〜2名(多くは AI の担い手と名義を共有) | ほとんどの様式が自己申告になる。署名しても、AI の担い手が同じ鍵・同じ `gh` 認証で署名できるため、名義の共有の扱い(ADR-0107)で裏づけに数えない | **それが実態であり、開示が正しくなるだけ**。手間は増えない(欠落にしないので出荷は止まらない) |
| 3〜9名 | 鍵を設定した人と設定しない人が混在する。API 経由のコミットを既定の経路にすれば、追加の設定なしに裏づく | 準拠テンプレートの `/gate` の手順が、様式を API 経由で置く形を既定にすることが条件 |
| 10名以上・組織所有 | 署名の要求(records-signed)を既に使う構成がある。組織の SSO と vigilant mode を併用できる | 回る。照らす条件が効力を持つ記録と揃うので、運用の説明が1つで済む |

保証の開示の項目1 の「自己申告」の件数は、ほとんどの採用者で大きく増えます。これは改悪ではなく、今まで裏づいていなかったものが正しく数えられるだけです。ただし読み手が驚くので、R-5 で改めた理由を開示へ添えます。

### 譲れない点

- author の一致を `backed` に数えない
- ホスティングの検証で、committer と author の両方を数値の識別子で照らす(ログイン名・email の文字列で照らさない)
- 名義の共有の扱い(ADR-0107)を、判定記録の様式の帰属(`formAttribution`)にも入れる。今は `signerSharing` を見ていない(内部 5(b))。入れなければ、1〜2名の体制で AI の担い手の署名が本人の裏づけに数えられる

### 採らない案

- **本文の「弱い裏づけ」を残し、開示で「弱い」と区別する案**。弱い裏づけは、偽装に費用が掛からない以上、裏づけではない。区別の欄を足しても、件数を足し合わせる読み手が出る
- **署名を必須にする案(署名の無い様式を欠落にする)**。判定記録の帰属は事後でよいという区分(ADR-0106)を崩し、1〜2名の体制で出荷が恒常的に止まる。止まった後に取られる行動は、自己申告と同じ内容の署名(AI の担い手の鍵での署名)であり、信頼性は上がらない
- **手元の `%G?` を残し、CI に鍵束を配る案**。鍵束の管理という別の統制を生み、鍵とアカウントの結び付きはホスティングの検証のほうが強い

### 反論されうる点

- 「API 経由のコミットは AI の担い手も同じように作れる」: そのとおりで、名義の共有の構成では裏づけに数えない(ADR-0107)。名義を共有しない構成(担い手が専用のアカウント・App で動く)では、担い手のコミットは別のアカウントに結び付き、本人の裏づけにならない。どちらの場合も誤って裏づくことはない
- 「本人の push を外すと、push で様式を置いてきた運用が全部自己申告になる」: 今も実装は push の主体を読んでおらず、author を読んでいるだけである(内部 3.4)。実態として裏づいていなかったものが表示どおりになる

## R-4 写しの先取りと、効力を持つ記録の列挙の漏れ

### 結論

- **先取りは R-2 と R-1 で塞ぐ**。G-6 は API で数えるので、偽の写しは承認の数に効かない。写しにだけあるレビューは欠落になる。マージより前に置かれた写し、record-copy の形でないコミットで置かれた写しは、R-1 の走査で欠落になる
- 加えて record-copy は、既存の写しがあるとき、今取り出した写しと**不変の欄**(R-2 の表)を比べ、食い違えば**失敗**で終える。一致すれば成功で終える(再実行は正当に起きるため)。本文・ログイン名の差は警告にとどめる
- **records の G-6 差し戻しの記録を、効力を持つ記録の列挙へ加える**。ただし帰属を確かめる向きは「足す」ではなく「消す・取り下げる」に置く
  - 差し戻しの記録は、追加の時点では帰属の照合を要しない(足せば委任が厳しくなる向き)
  - 一度足した差し戻しは、取り下げの記録(元を指す)が効力を持つまで数え続ける。取り下げの記録は効力を持つ記録として、効力を持つ前に記名者本人の操作で帰属を確かめる
  - 委任の判定(`autonomy.mjs`)は、records の先頭ではなく**履歴に一度でも現れた差し戻しの記録**を数える。差し戻しの記録の M・D を検出したら、委任のマージを止める(閉じる向きに倒す)
- roster-ids の提案は、写しではなくホスティングの現在の値(`--lookup`)を既定にする。写しは補助にとどめる

### 理由

1. 先取りの害は「偽の写しが本物の代わりに数えられる」ことにある。R-2 で数える源を API に移せば、害の本体が消える。record-copy の失敗は、それを早く知らせる層であって、塞ぐ層ではない。record-copy の失敗だけに頼ると、Actions の記録を誰も見ない体制(1〜2名で多い)では気づかれない
2. 再実行を失敗にしない理由: record-copy はネットワークの失敗などで再実行される。既に正しい写しがあるときに失敗させると、誤検出で通知が鳴り続け、現場は通知を無視するようになる
3. 差し戻しの記録を列挙へ加える理由: 委任の判定は PR の時点で効き、事後の検出ではマージを取り消せない。ADR-0106 の論理(事後の開示では取り消せない)にそのまま当たる。列挙に無いのに効いている今の状態は、本文 `:125`「列挙に無い記録を、効力を持つ記録として扱わない」と矛盾する。矛盾を解く方法は2つで、読み手に効かせないか、列挙に加えるかである。差し戻し率は委任の停止の要であり、効かせない選択は採れない
4. 向きを「消す」に置く理由: 差し戻しの記録を偽って足しても、委任が止まるだけで、統制は緩まない。足す側に帰属の照合を課すと、差し戻しを記録する手間が増え、差し戻しが記録されなくなる(現場で最も起きやすい形骸化)。緩む向きは消す・取り下げる操作だけなので、そこに照合を置く

### 体制ごとに回るか

| 体制 | 先取りの対策 | 差し戻しの記録 |
| --- | --- | --- |
| 1〜2名 | 回る。委任を使うのは主にこの体制(第8章の事後監査への切替) | 履歴の走査は PR の時点で要る。records の履歴をチェックアウトで取得する(records は小さいので負担は小さい〔推〕)。取り下げは自己申告として受け付け、開示へ出す |
| 3〜9名 | 回る | 取り下げは記名者以外の人の帰属の確認 |
| 10名以上 | 回る | 同上。PR の数が多いので、差し戻しの記録の走査は錨からの区間に限る |

### 譲れない点

- 差し戻しの記録の削除・書き換えで委任が緩む経路を残さない。検出したら委任を止める(緩む向きに倒さない)
- 足す向きに照合を課さない

### 採らない案

- **record-copy の失敗だけで先取りを塞ぐ案**。理由は上記1
- **既存の写しがあれば常に失敗させる案**。理由は上記2
- **差し戻しの記録を列挙へ入れず、委任の判定から外す案**。差し戻し率が委任の停止に効かなくなる
- **差し戻しの記録を、足す時点から効力を持つ記録として照合する案**。理由は上記4

### 反論されうる点

- 「他人の差し戻しを偽って足せば、他人の委任を止められる(妨害)」: 止める向きであり、統制は緩まない。妨害は人が止まったことに気づいて解く。取り下げの記録の帰属は確かめるので、妨害を解く操作も本人の操作になる。妨害の件数は新しい EV の観測に入れる
- 「列挙へ足すことは ADR-0106 の改めになる」: 本文は「列挙へ足す変更は、厳しくする向きの変更」と既に書いており、足すこと自体は想定済みである。新しい ADR で足す

## R-5 開示と記録

### 結論

- **候補 (c) を採る**。書き込みの主体を限れないホスティングの制約を、保証の開示に**構成ごとの固定の文**で出す。外部へ渡す保証の開示(`assurance-disclosure.external.md`)にも同じ文を載せる
  - records.json の構成: 書き込みの権限を持つ者とジョブのトークンは、記録用ブランチの写しと様式を新しいコミットで追加・変更・削除できる。止まるのは履歴の書き換えと削除だけで、変更は出荷の集約が検出する
  - records-signed の構成: 人の書き込みは署名で主体を確かめられるが、ジョブのトークンの書き込みは record-copy の書き込みと区別できない
  - ルールセットを使えない構成(個人所有 private の Free): 記録用ブランチの書き換えも履歴の差し替えも検出できない。ADR-0090 決定2 の「手段が無い」未達として出す
  - 全構成: admin はルールセットを外せる。錨で巻き戻しは検出するが、既定ブランチごとの書き換えは検出しない
- (c) を単独では採らない。開示と同じ欄に、R-1 の走査の結果(書き換え・追記・主体が不明の件数)を件数で併記する
- **新しい ADR を起こす**。ADR-0070 決定5(書き換えられない場所)を置き換え、R-1〜R-4 の決定(検出の要求と錨、API を正とする向き、出荷の後の向き、author の一致を数えない、差し戻しの記録を列挙へ加える)を記録する。ADR-0106 の列挙を足すことも、この ADR に書く
- **EV-0185 は差し替える**(会議体の結論が差し替え条件そのもの)。識別子は再利用せず、新しい EV を2つ置く
  - 新 EV(検出の前提): 対象は「force push と削除を止めた記録用ブランチで、既存のファイルの変更が履歴から検出できる」「レビューの不変の欄が本当に不変」「ホスティングの署名の経路が鍵なしで本人に結び付く」こと。根拠の水準は E0。差し替え条件は下記の実機の確認の結果
  - 新 EV(運用の負担): 対象は検出を欠落にする判断。差し替え条件は、採用組織での検出の件数のうち善意の書き換えの件数、それを解くための例外承認の件数、誤検出で出荷が止まった件数、API の未照合で保留した件数。**善意の書き換えが多数を占めて例外承認が形骸になれば、0.1 の誤検出対策を強める**(検出を所見へ戻す方向には倒さない)
- **IMPL-0353 は、要求が変わるので新しい ADR で置き換え、降ろし先の新しい実装マークへ引き継ぐ**。新しいマークは、降りるまで `state=undelivered` で表示し続ける
  - 履歴の走査と錨(evidence-aggregation)
  - API を正とする G-6 の数え方と、出荷の後の向き(evidence-aggregation)
  - record-copy の不変の欄の照合(record-copy-workflow)
  - 様式の帰属のホスティングの検証(evidence-aggregation。IMPL-0128 の note と試験を改める)
  - 差し戻しの記録の履歴での計数と、M・D での委任の停止(委任の判定の降ろし先)
  - 誤検出対策の既定(`.gitattributes`・整形の除外・AI の担い手の編集の拒否)
  - 保証の開示の固定の文(evidence-aggregation)
- README `:117` の開示(ルールセットを使えない構成)を、ルールセットを適用した構成へ広げる

### 実機で確かめること(EV の差し替えの材料。ADR を「採用」にする前に)

1. records.json の下で、書き込みの権限を持つ者が既存の写しを変えるコミットを push でき、その M が `git log --name-status` に残ること
2. 別のブランチのワークフローのジョブのトークンが records へ push できること
3. レビューの `commit_id`・`submitted_at`・`user.id` がホスティングの側で変わらないこと。本文の編集の履歴が取れること
4. 本人の `gh` 認証での `createCommitOnBranch` と、Web の画面からのコミットが、verified で本人の数値の識別子に結び付くこと(個人所有・組織所有の両方)
5. リポジトリの活動の API が records への push の actor を返すかと、その保持期間(本文の「本人の push」を残せるかの判断)
6. 個人所有 private の Free で、ルールセットと既定ブランチの保護が本当に使えないこと(開示の文の根拠)

### 体制ごとに回るか

開示は固定の文と件数で、採用者の手作業を増やしません。構成の判定(どの文を出すか)は env-check が読む今の規則から機械で決めます。1〜2名・個人所有 private の Free は「手段が無い未達」の開示になり、出荷は止めません。未達のゲートと同じ扱いです。

### 譲れない点

- 外部へ渡す開示にも載せる。記録を受け取る側(発注者・監査人)こそ、写しが書き換えうることを知る必要がある
- 1〜2名・個人所有 private の Free を、検出が成立した構成として数えない
- 採らないと決めたこと(防止の要求、外部の WORM の要求、author の一致の裏づけ、写しの優先)を、ADR と本文の両方に「採らない」と明記する。書かれていないのか課さないと決めたのかを、読み手が区別できるようにする

### 採らない案

- **(c) だけを採る案**。開示しても、G-6 は書き換えうる写しで数え続け、G-7 基準5 は弱い置き場を正とし続ける。開示の文と判定の扱いが食い違う(内部 5(c))
- **EV-0185 を見直し期限の延長で残す案**。会議体の結論が出た時点で差し替え条件は満たされる。延長すれば、結論が本文に入らないまま暫定の文が残る
- **IMPL-0353 を delivered にする案**。防止を求めないと決めたので、IMPL-0353 が書く「書き換えられない場所へ置く」は降ろし先を持たない。delivered にすれば、降りていない検出の実装が台帳から見えなくなる

### 反論されうる点

- 「開示の文が採用者を不安にさせる」: 不安の源は文ではなく構成の事実である。事実を書かない開示は、外部の読み手を誤らせる
- 「新しい EV を2つ置くのは多い」: 検出が成立する前提(技術)と、検出を欠落にする判断(運用)は、差し替え条件が別である。1つにまとめると、技術の確認だけで運用の判断まで確定したように読める
