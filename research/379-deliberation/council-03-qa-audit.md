### 内部調査の1点の訂正(P-9)

内部調査 §2 の表は「差し戻しの様式を消すと差し戻し率が下がり、停止を避けられる」と書く。コードの向きは逆である。停止の条件は「判定基準の番号を引いた差し戻しが**0件**の月が2か月続く」(ラバースタンプの検出)で、消すと停止の側へ倒れる(`autonomy.mjs:454` の注記もそう書く)。**危ないのは消すことではなく足すことである**。足された差し戻しが、ラバースタンプの検出を黙らせる。論点 R-4 はこの向きで扱う。

### 経路の型

上の経路は3つの型にまとまる。

1. **書き換えうる記録を、ホスティングの一次記録より優先して数える**(P-1・P-2・P-3・P-5)。写しの本来の役目は「ホスティングが後で失うもの(編集前の本文、退会で ghost になった user)を残す」ことなのに、ホスティングがまだ持っている欄まで写しで上書きしている
2. **置き場の場所で正を決める**(P-4)。どちらの置き場も W が書ける。場所ではなく「いつ、何によって最初に置かれ、その後に変わったか」で決めるしかない
3. **名前の文字列で人を数える**(P-7・P-8・P-9)。author の文字列、様式の判定者の欄、写しの宣言行のログイン名は、どれもホスティングが認証した操作ではない

## R-1 要求の形(防止か検出か)

### 結論

- 写しと様式の置き場の要求を、「記名者と判定される側が書き換えられない場所」から、**「書き換え・削除・成立前の先置きが、判定される側の消せない記録に残り、出荷の集約が欠落として検出する場所」**へ改める
- ただし、検出の要求だけを書き換えても足りない。**同じ条項に、「判定と数え方は、ホスティングの一次記録で照合できない限り、書き換えうる置き場の内容に依らない」を置く**。これが R-2 の向きの根拠になる
- 防止(書き込みの主体を限ること)は、要求にしない。採用者の任意の強化として書き、強化しても遮断に数えない
- 外部の WORM・透明性ログは、要求にしない(課さないと決めた旨を書く)。代わりに、**出荷の証跡(基底ブランチの強制層の下)に、取り込んだ records の先頭の SHA を記録し、次の集約で祖先関係を確かめる**ことを要求に入れる

### 理由

- GitHub の中で、書き込みの主体を限れない。T はどのワークフローでも同じ App の名義で、ワークフロー単位に区別できない(外部調査 §1.4)。A はルールセットを外せる(外部調査 §0-4)。防止を要求すれば、満たせない要求を「満たした」と書かせることになる。いまの EV-0185 が開示している過大な主張を、要求の側に戻すだけである
- 一方、`non_fast_forward` と `deletion` は、先頭から辿れる履歴を追記だけにする。既存のファイルの M・D・R も、先取りの A も、履歴に残る(P-1・P-2・P-4・P-9 の「後から確かめられるか」)。検出なら、いまのルールセットのままで成立する。SLSA Source L2 が求めるのも履歴の不変までで、内容の追記専用は求めない(外部調査 §2.3)。21 CFR 11.10(e) の「変更が以前の記録を覆い隠さない」とも形が合う
- しかし、検出が集約の所見に止まり、判定が書き換えうる写しで数え続けるなら、検出は信頼性に寄与しない(いまの `reconcileCopy` がその状態)。検出の条項と、数え方の条項を同じ所に置く必要がある
- P-11(A による履歴の書き換え)は、git の中では検出できない。ただし、出荷の証跡は既定ブランチの強制層(PR・承認・`non_fast_forward`)の下に入る。そこに records の先頭の SHA を残せば、次の出荷の集約は「前回の SHA が今回の先頭の祖先か」を確かめられる。A が records の履歴を書き換えると、既定ブランチの履歴まで書き換えない限り検出される。既定ブランチまで書き換える A は、本標準のどの統制も外せる。これは保証の開示の残余リスクとして書く(R-5)
- 外部の WORM・透明性ログを一律に求めない理由は、費用ではない。(i) 1〜2名の体制では、外部へ固定する手順を動かすのも A 本人であり、固定を省いた出荷を止める主体がいない。固定は「省かれたこと」が後で分かる形にしかならず、既定ブランチの SHA の連鎖と同じ強さに止まる。(ii) public リポジトリの Rekor への記録には、記名者の識別子が公開ログに載る(外部調査 §2.5 gitsign)。(iii) private の artifact attestation は透明性ログを持たない(外部調査 §2.4)。所有形態によって効き方が変わり、規格として一律の要求にできない。根拠水準は E0 で、見直しの条件を付ける

### 監査で確かめられること

- 記録の置き場の書き換えの有無: `git log --format='%H%x09%cI%x09%an <%ae>%x09%cn <%ce>' --name-status origin/records -- records/` で A 以外の行を数える。0件でなければ、どのコミットがどのファイルを変えたかが出る
- 先取りの有無: `records/reviews/pr-N.json` を追加したコミットの日時と、REST `pulls/N` の `merged_at` を比べる
- 履歴の連続: 前回の出荷の証跡(`docs/evidence/*.md`)に残した records の先頭の SHA が、今回の先頭の祖先であること(`git merge-base --is-ancestor`)
- 確かめられないこと: 書き換えたのが誰か(R-3・R-5)。A が既定ブランチごと書き換えた場合

### 採らない案

- **防止を要求する**(ルールセットの `update` で push を bypass の主体に限る): T は限れず、専用 App の bypass は個人所有での可否が実機で未確認、様式を判定者本人が直接 push する経路と両立しない、A は外せる。要求にはしない。採用者が専用 App と environment で強化する形は任意として書き、遮断に数えない
- **Restrict file paths で records/ の既存のパスを止める**: public で使えず、パスの全面禁止で追記と区別できない
- **GITHUB_TOKEN(GitHub Actions の App)を bypass に入れる**: どのブランチのワークフローも同じ名義で通るため、主体を限らない
- **外部の WORM・透明性ログを要求する**: 上の理由。課さないと決めた旨を書く
- **写しを既定ブランチへ bypass で入れる**: ADR-0070 決定7 で強制層の縮小として却下済み。今回も採らない

### 反論されうる点

- 「検出は事後であり、出荷までに書き換えを直されたら意味がない」: 直す操作も新しいコミットで、履歴に残る。消せないのは「書き換えたこと」である。ただし、書き換えの**中身の正しさ**は履歴からは分からない。写しはホスティングとの照合(R-2)、様式は署名(R-3)で補う
- 「SHA の連鎖は A に対して無力ではないか」: 既定ブランチまで書き換えない限り効く。既定ブランチまで書き換える A に対しては、本標準の他の統制も効かない。ここは隠さずに開示する
- 「規制業・CL2 以上には外部の固定点を求めるべきだ」: 監査の観点では、外部の固定点があれば「出荷の時点の内容」を第三者が確かめられる利点は大きい。ただし、それを求める実証は無い。E0 として見直しの条件(採用者の規制当局の査察で、既定ブランチの SHA の連鎖が受け入れられなかった事例)を置くのが妥当と考える

## R-2 写しと API の突合の向きと、G-6 の数え方

### 結論

- **正はホスティングの一次記録**(REST `pulls/N/reviews` と `pulls/N`)とする。写しは、ホスティングが後で失うもの(写しを取った後に編集された本文、退会で ghost になった user)を補う記録として扱う
- G-6 の承認は API のレビューで数える。写しで数えてよいのは、API のレビューと `id`・`submitted_at`・`commit_id` が一致し、API の側の欄が失われている場合(user が ghost、本文が編集された)だけである
- 次の不一致は**欠落**に数える(所見に止めない)
  - 写しにだけあるレビュー
  - `id` が一致して、`user.id`・`commit_id`・`submitted_at`・`author_association` が違うもの
  - `state` の違いのうち、API の側が DISMISSED でないもの(dismiss はホスティングの側の変化なので所見)
  - 本文の違いのうち、API の編集の記録(`lastEditedAt`・`userContentEdits`)で写しの後の編集と説明できないもの〔外: レビューの編集の履歴を GraphQL で引けるかを確かめる〕
- API を読めない PR は、写しで G-6 を数えない。「ホスティングで照合できない」と出し、その PR の G-6 は確かめられていないものとして扱う
- 写しの `merge_commit_sha` で PR を起こす後退経路(`:1036-1046`)は、ホスティングが「PR n は無い」「PR n のマージコミットは別」と答えた場合に使わない。答えを得られない場合に限り、使った件数を欠落として出す(P-3)
- 基底の複製と records の写しが食い違うとき、**場所で正を決めない**。両方のブランチの履歴で、最初に置かれた版(records で追加したコミット。マージより後で、record-copy の形のもの)を基準にし、その後に変わった側を書き換えとして名指して欠落に数える。欠落の文の「記録用ブランチの写しを複製し直してください」は消す
- 出荷の後の records の書き換えは、R-1 の履歴の走査で、前回の出荷の SHA から今回の先頭までの区間を見て検出する
- 基底の記録の置き場(`docs/records/**`・`docs/gates/**`・`docs/evidence/**`)の追加だけの規則を、出荷の PR に限らずすべての PR で、**必須のステータスチェック**として検査する(P-5・P-6)

### 理由

- 写しの役目は、ADR-0070 のとおり「承認レビューの本文は編集でき、user は ghost になる」ことへの備えである(`record-copy.yml:4-6`)。ホスティングが今も持っていて、ホスティングの側で変えられない欄(`id`・`user.id`・`commit_id`・`submitted_at`)まで写しを優先する理由は無い。優先すると、W・T が書ける置き場が、ホスティングが認証した記録を上書きする(P-1)
- 外部調査 §5-1 も、写しの真正性は「GitHub が認証した一次記録との再照合で確かめる設計にしないと区別できない」とする。NIST AU-10(4)(レビュー者の識別子と情報の結合の検証)とも合う
- 所見は判定を変えない。G-6 の承認の数は G-7 の判定と保証の主張の材料なので、数え方を変える不一致は欠落でなければならない。一方、dismiss や正当な編集はホスティングの側の変化なので、所見のままでよい。これを区別できる欄だけを比べる
- 場所で正を決めると、P-4 のように書き換えた側が勝つ。基底のほうが強いとも言い切れない。`checks-only.json` の構成では、基底の `docs/records` も承認なしの PR で変えられ、gate-g5 はそれを止めない(P-5)。どちらの置き場にも、消せないのは履歴だけである。履歴で最初の版を決めるのが、両方の置き場に同じ強さで効く唯一の基準である
- verify を必須にしない限り、出荷の PR の検査は承認者(転記の確認)の目視に依る。転記の確認者に、判定される側が書き換えた写しを見抜かせる設計は、信頼性を人の注意に預ける

### 監査で確かめられること

- 各 PR の G-6 の承認者が、REST のレビューの `user.id` で名簿の人に対応づくこと(写しの値でなく)
- 写しと REST の不一致が、欠落か所見かのどちらに分類されたか、分類の理由の欄(dismiss・編集の記録)
- 写しで対応づけた PR(`prFromCopy`)について、REST で PR が存在しないことの応答(404)を集約が記録していること
- 基底と records の食い違いについて、どちらの側のどのコミットが初出の版を変えたか

### 採らない案

- **records を正とする(現状)**: P-1・P-4 の経路が残る
- **基底の複製を正とする**: P-5 の経路が残る。基底も W が書ける
- **不一致を所見のままにする**: 判定が変わらない
- **API のレビューだけで数え、写しを読まない**: ghost 化と本文の編集で、正当な承認を失う。写しの役目を捨てることになる
- **verify ジョブを出荷の PR だけの検査のままにする**: P-5 が残る

### 反論されうる点

- 「API の取得が失敗する構成(権限・レート制限)で、G-6 が数えられなくなる」: その通りで、確かめられないものを確かめたと書かない、という判断である。取得の失敗は理由つきで出し、再実行で埋まる。写しで黙って埋めるより信頼できる
- 「ghost になった承認者の `user.id` は、写しの値しか無い」: そのとおりで、`id`・`submitted_at`・`commit_id` が API と一致するレビューに限って写しの `user.id` を使う。写しの `user.id` を書き換えれば、ghost の承認を名簿の人に付け替えられる経路は残る。これは records の履歴の走査(写しの M)で検出する
- 「必須のステータスチェックを足すのは強制層の追加で、採用者の負担になる」: 負担は採否の理由にしない。追加だけの規則を必須にしないなら、その構成は保証の開示に出す

## R-3 様式の帰属(署名の無い author の一致)

### 結論

- **候補 (b) を採る**。署名の無いコミットの author の一致(`author-login`・`author-email`)を、判定記録の帰属の裏づけに数えない。自己申告として開示する
- 署名の検証は、手元の `%G?` ではなく**ホスティングの検証**(REST `commits/{sha}` の `verification.verified`)で行う。committer と author の両方が記名者のアカウント(数値の識別子)であることを求める。効力を持つ記録の `introducedBacking`(`material-attribution.mjs:301-304`)と同じ強さにそろえる
- 照らすのは、様式を**追加した**コミット(`--diff-filter=A`)とする。最後に触ったコミットではない。追加の後の変更は、R-1 の走査で書き換えとして欠落になる
- 本文 `:127` と `ci-gates.md:637` の「署名の無い push は、author の一致による弱い裏づけである」を削る。「記名者本人の push」は、push の主体をホスティングの記録で読める場合に限って裏づけに数える。読めない構成では裏づけの例から外す
- **保証の主張の成立条件4 は、G-7 と G-8 の両方の記名の帰属が裏づいていることを条件に加える**(P-8)。裏づけの経路には、記名者本人の宣言行つきレビュー(ホスティングが認証した操作)を含める

### 理由

- git の文書は author の名前を「認証に効かない」と書く。GitHub も author と committer を任意に設定できると書く(外部調査 §4)。noreply アドレスを書けば誰でも記名者の名義になる(P-7)。これを「裏づけ」と呼ぶと、保証の開示 項目1 の自己申告の件数が、実際より少なく出る。開示が実態より強く見える
- 同じ標準の中で、効力を持つ記録はホスティングの検証と committer・author を求め、判定記録は手元の `%G?` と author だけを見る。照合の強さが二重になっている。記録の重さで要求の強さを変えること(効力の前か事後か)は ADR-0106 の区分で正当化できるが、**同じ「裏づけ」という語で違う強さを数える**ことは正当化できない
- CI の runner は署名者の鍵を持たない。手元の `%G?` は署名の経路をほぼ成立させず、効いているのは author の一致だけである〔推〕。ホスティングの検証へ移さないと、署名を運用している採用者まで自己申告に落ちる
- 成立条件4 は「別の自然人」を求める。名前の文字列は自然人の別を示さない。帰属を見ない条件4 は、1人で2つの名前を書けば成立する(P-8)。これは保証の主張そのものの過大であり、開示の件数に出すだけでは足りない

### 監査で確かめられること

- 各様式の追加のコミットについて、REST の `verification.verified`・`verification.reason`、`committer.id`・`author.id` と名簿の数値の識別子の一致
- 自己申告とした様式の件数と一覧(保証の開示 項目1)
- 成立条件4 の判定に使った G-7・G-8 の様式の、裏づけの経路(署名・本人のレビュー)
- 確かめられないこと: 署名の無いコミットを誰が置いたか(activity view の保存期間の外)

### 採らない案

- **author の一致を「弱い裏づけ」として残す(現状)**: 上の理由
- **署名を必須にする(すべての採用者)**: ADR-0106 決定7 が a2 を退けた理由(鍵と名簿のアカウントの結び付き、1〜2名の体制で鍵の運用を既定にする根拠の無さ)が、判定記録にもそのまま当たる。(b) は裏づけの数え方を正すだけで、出荷を止めない
- **手元の `%G?` に鍵束を配って検証する**: 鍵束そのものを W が書ける。ホスティングの検証のほうが判定される側から遠い

### 反論されうる点

- 「多くの採用者で、様式のほとんどが自己申告になる」: なる。それが実態である。開示の値が大きく変わることは、いまの値が過大だったことを示す
- 「成立条件4 に帰属を加えると、1〜2名の体制で保証の主張が立たなくなる」: 記名者本人の宣言行つきレビューで裏づけられる。手段はある。立たない場合は、主張しないことが正しい
- 「`introducedBacking` と同じ条件にすると、判定記録にも効力を持つ記録と同じ重さを課すことになる」: 課すのは照合の**強さ**であって、**時点**ではない。判定記録は事後(G-7)のままでよい。ADR-0106 の区分は保たれる

## R-4 写しの先取りと、効力を持つ記録の列挙の漏れ

### 結論

- **先取り**: record-copy は、既に同じ PR の写しがあるとき、既存の写しと今取り出した写しを正規化して比べる。一致すれば成功、違えば**失敗**させる(既存のファイルは書き換えない)。あわせて、集約は R-1 の走査で「マージより前に追加された写し」「record-copy の形でない追加」を欠落にし、R-2 の照合で中身の偽を欠落にする。**先取りを止める主たる統制は、置き場の書き込みではなく、ホスティングとの照合である**
- 写しに `run_id`・`run_attempt`・`workflow_ref` を書き、コミットの件名にも `run_id` を入れる。集約と監査は Actions の API で、その実行が record-copy.yml の既定ブランチの定義で、その PR の closed で動いたことを、保存期間の内に確かめる
- **委任の判定に使う G-6 の差し戻しの記録を、効力を持つ記録の列挙に加える**。委任の判定は、差し戻しを、(i) 判定者の席のアカウント(数値の識別子)の宣言行つきレビューを REST で引いたもの、または (ii) 基底ブランチの様式で、効力を持つ記録と同じ帰属(`introducedBacking`)が裏づくもの、からだけ数える。records の先頭は読まない
- `rejectionsFromReviewCopies` は、判定者のログインで絞らずに宣言行を数えている。判定者の席のアカウントの宣言行だけを数える
- `roster-ids` の提案は列挙に加えない。名簿の変更そのものが効力を持つ記録であり、人が入れる。ただし提案の既定を `--lookup`(ホスティングの今の値)にし、写しの値は照合の手がかりとして並べるだけにする

### 理由

- 先取りの写しは「誰が置いたか」を記録から確実には結び付けられない(T の push は record-copy と区別できない)。一方、写しの**中身**はホスティングの原本と比べられる。結び付けられないものに頼らず、比べられるもので塞ぐのが、監査で再現できる統制である
- record-copy の「警告して exit 0」は、失敗を成功として記録する。Actions の実行の結論が success のままでは、env-check(`adoption-trial.mjs:1338`、直近の実行の結論を見る)にも出ない
- `run_id` は写しの中の自己申告だが、ホスティングの Actions の記録と照らせる。ただし、偽の写しが**本物の record-copy の実行の `run_id`** を書くことはできる(先取りの場合、本物の実行は exit 0 で終わっているため)。したがって `run_id` は補助で、主たる統制は R-2 の照合である。この限界は開示する
- P-9 は、ADR-0106 の論理そのものに当たる。効力を持つ記録を閉じた列挙にしたのは、「事後の開示では、済んだ効力を取り消せない」からである。委任のマージは PR の時点で効き、G-7 で見つけても戻らない。差し戻しの記録は委任の可否に効いているので、列挙に無いこと自体が `:125`(列挙に無い記録を効力を持つ記録として扱わない)と食い違う。列挙に加えるか、委任の判定が読まないかの二択で、読まなければラバースタンプの検出が働かない。だから加える
- 宣言行を判定者で絞らないと、ホスティングが認証したレビューであっても、判定者の席でない人の差し戻しで停止を黙らせられる。これは records の書き換えと独立の穴で、同じ機会に塞ぐ

### 監査で確かめられること

- 写しを追加したコミットの日時が `merged_at` より後であること。record-copy の実行が成功で、警告の行(既にある)を含まないこと(実行の記録の保存期間の内)
- 委任のマージごとに、判定に使った差し戻しの記録の一覧と、その帰属の経路(REST のレビュー id・署名を検証したコミット)。delegation の実行の記録にこれを書かせる
- 確かめられないこと: 保存期間を過ぎた Actions の実行と、その実行が押したコミットの対応

### 採らない案

- **record-copy の警告のままにする(現状)**: 上の理由
- **records の `creation`・`update` をルールセットで限って先取りを止める**: R-1 の「防止を要求する」と同じ理由で、要求にしない
- **既存の写しを上書きする**: 追記だけの原則を崩し、書き換えの記録と正当な複製を区別できなくなる
- **委任の判定が records の書き換えの検出結果を読む**(列挙に加えず、走査の結果で補う): 走査は書き換え(M・D)と先取りを見つけるが、**新しく足された偽の差し戻し**は、形が正しければ A として正常に見える。中身の真正性はホスティングの記録でしか確かめられない
- **差し戻しの記録を委任の判定から外す**: 第5章 5.4.6 の差し戻し率の検出をやめることになる

### 反論されうる点

- 「差し戻しを効力を持つ記録にすると、様式で差し戻した記録が数えられなくなる」: 基底へ帰属つきで入れれば数えられる。手間は増えるが、委任の停止を黙らせる経路を塞ぐ対価である
- 「record-copy を失敗させると、正当な再実行で写しが既にある場合に失敗する」: 一致すれば成功させる。違うのは、写しの後に本文が編集された・dismiss された場合で、そのときは失敗が正しい(写しの時点と違う)。失敗の文で理由を区別して出す

## R-5 開示と記録

### 結論

- **候補 (c) を採る。ただし (a)(b) と組で採る**。(c) だけでは判定・数え方が変わらない(内部調査 §5 (c))
- 保証の開示に、構成ごとの固定の文と、走査の件数を出す
  - records.json の構成: 「書き込みの権限を持つ者とジョブのトークンは、記録用ブランチの写しと様式を新しいコミットで追加・変更・削除できる。止まるのは履歴の書き換えと削除だけである。書き換えは履歴の走査で検出し、写しの中身はホスティングの記録と照合する。書き込んだ主体は、署名の検証が通ったコミットを除いて特定できない」
  - records-signed.json の構成: 上に加えて「人の書き込みは署名で主体を確かめられるが、ジョブのトークンの書き込みは record-copy の書き込みと区別できない」
  - 共通: 「リポジトリの管理者はルールセットを外せる。既定ブランチの履歴まで書き換えた場合は検出の外である」
  - 件数: 走査で見つけた書き換え(M・D・R)、先取り(マージより前の追加)、record-copy の形でない追加、写しと API の不一致(欠落・所見の別)、自己申告の様式
- 外部へ渡す保証の開示(`assurance-disclosure.external.md`)にも同じ文を載せる。外の読み手ほど、置き場の性質を知らない
- **新しい ADR を起こす**。ADR-0070 決定5(置き場の要求)を置き換え、次を決定として記録する: 要求を検出へ改めること(R-1)、正をホスティングの一次記録とし場所で正を決めないこと(R-2)、署名の無い author の一致を裏づけに数えないこと(R-3)、委任の判定に使う差し戻しの記録を効力を持つ記録に加えること(R-4)、外部の WORM・透明性ログと防止を要求しないこと。ADR-0070・0106 の本文は書き換えない
- **EV-0185** は差し替える(差し替え条件だった #379 の結論が出る)。後継の EV を新しい識別子で起こし、対象を「履歴の走査とホスティングとの照合で、写しと様式の書き換えを検出できるか」と「既定ブランチの SHA の連鎖で、管理者以外による records の履歴の書き換えを検出できるか」にする。根拠は実機の未確認(内部調査 §6-8 の4点)のため E0、見直しは実機で確かめた後。外部の固定点を課さない判断にも、見直しの条件つきで EV を付ける
- **IMPL-0353** は、降ろし先が「ルールセットで書き換えを止める」前提なので、規定の側を改めた後に後継の実装マークへ引き継ぐ(識別子は再利用しない。扱いの書式は `community/implementation-marking.md` に従う)。後継は少なくとも、(i) 集約の履歴の走査と SHA の連鎖、(ii) 写しとホスティングの照合の欠落化、(iii) record-copy の先取りの失敗化、(iv) 帰属のホスティングの検証、(v) 記録の置き場の追加だけの規則の必須のステータスチェック、(vi) 委任の判定の差し戻しの読み方、(vii) 保証の開示の固定の文、に分ける。降りるまでは `state=undelivered` で表示し続ける
- EV-0111 の差し替え条件(記名者以外の書き換え・追記の件数を git の履歴で数える)は、(i) の走査で初めて観測できる。後継の実装マークから EV-0111 を引く
- EV-0113 の差し替え条件は「置き場の外への書き込み」だけを測る。置き場の中の書き込みは後継の EV で測る。EV-0113 は変えない

### 理由

- 書き込みの主体を限れないのはホスティングの構造で、採用者の設定の弱化ではない。env-check の所見(弱化の検出)ではなく、保証の開示の固定の文で出すのが、ADR-0090 決定2 の未達の区分(手段が無い)と同じ型になる
- いまの README は、ルールセットを使えないプランについてだけ「records 自体の書き換えは検出できない」と書く。適用した構成でも書き換えは止まらない。開示の範囲が実態より狭い
- 却下を明記するのはコアポリシーの要求である。防止・外部の固定点・GITHUB_TOKEN の bypass・場所で正を決める案は、どれも「書かれていない」のではなく「課さないと決めた」ことを読み手が区別できなければならない

### 監査で確かめられること

- 保証の開示に、構成に合った固定の文と、走査の各件数が出ていること。件数の元(コミットの SHA、PR 番号)が一覧で引けること
- 新しい ADR・後継の EV・後継の実装マークが、本文の条項から引かれていること(`npm run lint:refs`・`evidence:write`・`impl:write` の台帳)

### 採らない案

- **(c) だけを採る**: 判定と数え方が変わらない
- **EV-0185 を残したまま注記で済ませる**: 差し替え条件が満たされた EV を残すと、結論が出たのに「結論が出るまで」の扱いが続いて見える
- **主体を限れないことを env-check の所見に出す**: 所見は弱化の検出であり、構造の制約を弱化と混同させる

### 反論されうる点

- 「固定の文は採用者を不安にさせる」: 規格は、採用者が自分の保証を過大に主張しないための道具である。不安を減らす目的で開示を弱めない
- 「ADR を1本にまとめると、R-1〜R-4 のどれかを後で変えるときに全体を置き換えることになる」: 決定を番号で分けて書けば、個別に後継の ADR で置き換えられる。分けて起こすかは起草の判断に委ねるが、ADR-0070 決定5 の後継は1本に定める必要がある

## 申し送り(本議題の範囲の外。別の Issue で扱うかを決める)

- **gate-g5 と ship-evidence の verify は `pull_request` で動き、ワークフローの定義を PR の側から読む**〔外〕。PR の中で `.github/workflows/gate-g5.yml` を書き換えれば、必須のステータスチェック `gate-g5` そのものを通せる。ルールセットの必須のチェックは `context` の名前だけで、送り手(`integration_id`)を縛っていない(`team.json` ほか)〔確〕。`CONTROL_FILES`(`check-pr.mjs:328`)が PR 本文に陰性の確認を求めるが、その検査も書き換えられた側の定義で動く。`delegation.yml` は同じ理由で `pull_request_target` を使っている。ADR-0090 の論理の適用漏れの可能性があり、#379 の結論とは独立に、強制層の設計として会議体に掛けるべきと考える
- 出荷の PR の本文の印(`from`・`to`)を PR の作成者が書き換えて集約の範囲を狭める経路(P-6 (ii))。範囲はタグと照らして機械が確かめるべきである
- 基底へ残る品質レポート(`docs/evidence/*.md`)の内容を、集約の出力と照合していない(P-6 (iii))。成果物の原本は保存期間で消えるため、基底の写しが唯一の記録になる。ダイジェストの照合か、集約の出力を verify が置き直す形が要る

## 実機で確かめていないこと(EV の材料)

内部調査 §6-8 の4点に加えて:

1. `pull_request` のイベントで、PR の中で書き換えたワークフローの定義が使われること(P-6 (i)・申し送り1)
2. 存在しない PR 番号に対する `fetchPr` の失敗が null として返り、写しの対応づけへ進むこと(P-3)。試験 `test-aggregate-records.mjs` に違反の対を置いて確かめる
3. 偽の差し戻しの写しを足した状態で、`autonomyState` の 0% の停止が発火しないこと(P-9)。試験の対で確かめる
4. REST のレビューの `commit_id`・`submitted_at` がホスティングの側で不変であること、GraphQL でレビューの編集の履歴を引けること
