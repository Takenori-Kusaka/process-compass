# #379 会議体: 弁護(現行の構成を弁護する立場)

- 日付: 2026-11-05
- 立場: 現行の構成(記録用ブランチ records は force push と削除だけを止める。集約は写しを API より優先して読む。署名の無い author の一致を弱い裏づけとして数える。不足は EV-0185 で開示する)を弁護する。変える必要が本当にあるか、変えると何が壊れるか(1名の体制・無料のプラン・誤検出・既存の記録)を問う
- 判断軸: 信頼性。変更量の少なさは採否の理由にしない。弁護できない欠陥は欠陥と認める
- 入力: `council-00-agenda.md`、`survey-379-1-internal.md`(以下「内部」)、`survey-379-2-external.md`(以下「外部」)。`template/scripts/gate/aggregate-evidence.mjs:1546-1551`(写しの優先)、`:238-239`(突合の先を records とするコメント)、`template/scripts/gate/records.mjs` の `recordAttribution`(author-login・author-email を backed にする)、`template/.github/workflows/record-copy.yml:167-171`(既にあれば exit 0)は現物で確かめた

## 0. 弁護の総括

現行の構成のうち、弁護できるのは**骨格**である。

- 防止ではなく検出を選ぶこと(force push と削除だけを止め、内容の変更を止めない)
- 写しを残すこと(ホスティングの記録はマージの後に変わるため、マージの時点の断面が要る)
- 不足を EV で開示し、効力を持つ記録を records に依らせないこと(ADR-0106)

弁護できないのは**骨格の上に載った読み方**である。EV-0185 は「書き換えられない記録として扱わない」と開示しているのに、実装は写しを API より優先して G-6 を数え、出荷の後は records を正として基底の複製を「書き換えた記録」とし、author の文字列の一致を backed と数える。開示と実装が逆を向いている。開示で済ませられる段階は、実装が開示どおりに振る舞うことが前提であり、その前提が崩れている。ここは欠陥と認める。

したがって弁護の結論は「骨格は変えない。読み方は変える。変え方は誤検出と既存の記録を壊さない形に限る」である。

## R-1 要求の形(防止か検出か)

### 結論

- 要求は**検出**とする。「書き換えられない場所」ではなく「書き換え・削除・追記が履歴に残り、出荷の時点で機械が列挙する場所」と書く。防止は要求しない
- 外部の WORM・透明性ログは**要求しない**。採用者が足してよい強化として附属書の手引きに置くにとどめ、要求に数えない
- ただし、検出は現行の構成に**無い**(履歴の走査の実装が無い。内部 1.4)。「現行は検出の構成である」とは弁護できない。現行は「検出できる素地がある構成」にすぎず、検出の実装を足すことは変更として認める

### 理由

1. **防止は、この標準の想定する体制で成立しない**。ルールセットの Restrict updates で push を bypass の主体に限れても、admin(個人所有では所有者)はルールセットを外せる(外部 0.4)。1名の体制では、所有者・記名者・ルールセットの管理者が同一人物である。そこで防止を名乗ると、外せる者が外さないことを前提にした「防止」になり、標準が実態より強い主張をする。#321 F-6 で「誤っている側は main の前提の書き方(過大)」とされた誤りを、別の形で繰り返すことになる
2. **防止の部品は、無料のプランと個人所有で揃わない**。Restrict file paths は public で使えない(外部 1.1)。個人所有で App を bypass に入れられるかは未確認(外部 1.2)。environment の秘密は Free の個人では public に限る(外部 1.4)。GITHUB_TOKEN はワークフロー単位で区別できない(ADR-0090、外部 1.4)。要求に掛けると、多くの採用者が「手段が無い未達」(ADR-0090 決定2)になり、未達の表示が常態化して信号の価値を失う
3. **防止は、判定者本人が様式を直接置く経路と両立しない**。records への書き込みを App に限ると、人の様式も App を経由させることになる。App が書いたコミットの名義は App であり、記名者に結び付く手がかりが消える。帰属(R-3)を弱めて改ざんへの耐性を買う取引になり、信頼性は上がらない
4. **検出は、参照した規格の水準と形が合う**。SLSA Source L2 は履歴の継続・不変・保持までを求め、内容の追記専用を求めない(外部 2.3)。21 CFR 11.10(e) は「変更が以前の記録を覆い隠さない」ことを求め、変更そのものを禁じない(外部 3.1)。force push と削除を止めた git の履歴は、この形に合う。NIST AU-9 b も「検知したら通知する」を含む
5. **WORM・透明性ログを要求に上げても、残る問いは解けない**。外部のログが証明するのは「その時点にその内容があった」ことで、「誰が書いたか」ではない。public の Rekor は email を公開する(外部 2.5)。private では GitHub の attestation に透明性ログが無い(外部 2.4)。外部の依存を増やして可用性の故障点を足すわりに、帰属の弱さ(R-3)は残る

### 検出の要求の中身(弁護側が受け入れる線)

- records の `records/` の下で、追加(A)以外の変更(M・D・R)を履歴から列挙し、出荷の時点で欠落に数える
- **様式の訂正は、既存のファイルの変更でなく、訂正の様式の追加で行う**と定める。これで「正当な訂正」と「書き換え」を、履歴の上で区別できる。訂正を M で許すと、誤検出を避けるために M の一部を許す例外が要り、その例外が改ざんの通り道になる
- 走査の起点は、**前回の出荷の証跡に記録した records の先頭の SHA**とする。前回の SHA が今の先頭の祖先でなければ、履歴の書き換え(ルールセットを外していた間の force push)として欠落にする(内部 5(a)-5)。admin がルールセットを外しても、外していた間の書き換えは次の出荷で見える。防止はできないが、検出は届く

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 防止を要求する(Restrict updates + bypass の限定) | 理由 1〜3。外せる者が外さないことを前提にする。無料のプラン・個人所有で部品が揃わない。人の様式の帰属を失う |
| Restrict file paths で `records/**` の変更を禁じる | public で使えない。パス単位の全面禁止で、追加も止まる |
| 外部の WORM・透明性ログを要求する(規制業・CL2 以上に限る形を含む) | 理由 5。帰属を解かないまま外部の故障点を足す。強化の選択肢として手引きに置くことは妨げない |
| 現行のまま(検出の実装も足さない) | 弁護できない。EV-0111 の差し替え条件は「git の履歴で検出」した件数を前提にしているのに、件数を出す実装が無い。観測できない差し替え条件は、見直しの期日が来ても判断の材料にならない |

### 反論されうる点

- 「検出は事後であり、委任の判定のように PR の時点で効く読み手には届かない」。認める。R-4 で、PR の時点の読み手を履歴の追加だけから読む形へ改めることで答える。検出だけで全ての読み手を守れるとは主張しない
- 「訂正を追加で行う規則は、既存の採用者の運用を変える」。変える。ただし既存の記録は起点の SHA より前を走査しないので、過去の M を欠落にしない(既存の記録を壊さない)。起点を置く前の区間は「走査していない区間」として保証の開示に出す
- 「1名の体制で、所有者自身の書き換えを検出して何になるのか」。この標準で判定される側は AI の担い手である。ADR-0107 の guard-bash は `git push records` を止めるが、担い手が書いたプログラムや API の経路は止まらない。1名の体制でも、担い手による records の書き換えは検出の対象として意味を持つ。所有者自身の書き換えは、どの手段でもリポジトリの中では塞げない残余として開示する(R-5)

## R-2 写しと API の突合の向きと、G-6 の数え方

### 結論

- **写しの優先は、欄によって分ける**。ホスティングの側で変わらない欄(`id`・`user.id`・`commit_id`・`submitted_at`)は API を正とし、写しとの不一致と「写しにだけあるレビュー」を**欠落**にする。マージの後に変わりうる欄(本文・`state`・`author_association`)は、写しをマージの時点の断面として使い続ける
- **API を読めないときは、写しで数え、「照合できなかった」として開示する**。欠落にしない
- **出荷の後は、基底の複製を正とする**。records との食い違いは records の側の書き換えとして欠落に数える。`mergeRecordSources` と G-7 基準5 の向きを改める
- 現行の「写しがあれば写しだけで数え、API との差は所見にとどめる」は弁護できない。欠陥と認める

### 理由

1. **写しを残す理由は今も正しい**。承認レビューの本文は後から編集でき、`state` は dismiss で変わり、`author_association` は API が今の値を返す。マージの時点で何が承認されていたかは、写しにしか残らない。写しを捨てて API だけで数える案は、マージの後の編集で G-6 の結果が変わる記録になり、信頼性が下がる
2. **しかし、写しが API より強い理由は、変わらない欄には無い**。`id`・`user.id`・`commit_id`・`submitted_at` はホスティングの側で変わらない(内部 3.6。最終確認は要外)。この欄で写しを優先する根拠は無く、優先すると「書き換えうる場所の値で、書き換えられない場所の値を上書きする」ことになる。現行の G-6 は、偽の承認を足した写しで成立する(内部 2)
3. **所見止まりは、検出していないのと同じ**。所見は欠落に数えられず、G-7 を止めない。EV-0185 が「書き換えられない記録として扱わない」と書いた以上、書き換えの兆候は欠落に数えるのが開示と整合する
4. **基底の複製のほうが強い置き場である**。基底は既定ブランチの強制層の下にある。records は force push と削除しか止まらない。弱い側を正とし、強い側を「人が書き換えた記録」と判定する現行の向きは、置き場の強さと逆である。`aggregate-evidence.mjs:238` のコメント「記名者と判定される側が書き換えられない置き場」は、EV-0185 が否定した前提をそのまま残している

### 誤検出を避ける条件(弁護側が譲らない線)

変わらない欄の不一致を欠落にするなら、次の場合を欠落から除き、「照合できなかった」として開示する。除かないと、改ざんの無い採用者が出荷を止められる。

- **アカウントの削除**: 削除されたアカウントのレビューは、ホスティングの側で別の主体(ghost)に付け替えられる〔推。要実機〕。`user.id` の不一致を書き換えと判定すると誤検出になる
- **API を読めない**: レート制限、権限の不足、手元での集約。API が読めないことを欠落にすると、無料のプランや手元の実行で集約が成立しなくなる
- **dismiss・本文の編集**: マージの後の `state` と本文の変化は、写しの書き換えではない。比べるなら、ホスティングの側の編集の時刻(`lastEditedAt`、dismiss の時刻)と写しの `copied_at` を比べ、写しの後の変化はホスティングの側の変化とする

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 写しを捨て、API だけで数える | 理由 1。マージの後の編集で結果が変わる |
| 写しの優先を続け、API との差を所見にとどめる(現行) | 理由 2・3。欠陥と認める |
| 全ての欄で API を正とする | `author_association` は API が今の値を返すため、退職・権限の変更で過去の承認が UNTRUSTED に変わる。誤検出になる |
| API を読めないときに欠落にする | 誤検出。改ざんと無関係な事情で出荷が止まる |
| 出荷の後も records を正とする(現行) | 理由 4。欠陥と認める |

### 反論されうる点

- 「`author_association` を写しで使い続けるなら、そこは書き換えうるままではないか」。認める。この欄はホスティングとの突合で守れない。R-1 の履歴の走査(写しの追加の後の M を欠落にする)と、R-4 の先取りの検出(追加の時刻と record-copy の実行の照合)の組で守る。突合だけでは守れない欄が残ることを開示する
- 「照合できなかった場合を欠落にしないなら、攻撃者は API を読めない状況を作ればよい」。API を読めない状況を作れるのは、集約を走らせる側である。集約が CI で走る場合に API を読めないことは稀であり、照合できなかった件数を保証の開示に出せば、件数の偏りとして見える。欠落にする誤検出の害のほうが大きいと判断する(根拠は推論。EV で開示する)

## R-3 様式の帰属(署名の無い author の一致)

### 結論

- **署名の無い author の一致を、帰属の裏づけ(backed)に数えない**(候補 b を採る)。現行の弁護は放棄する
- ただし、一致を「不一致」と同じ箱に入れない。三つに分けて開示する: (1) ホスティングが検証した裏づけ、(2) 署名の無い author の一致(**裏づけではない**。自己申告に数える)、(3) 不一致
- 署名の確認は、手元の `%G?` ではなく**ホスティングの検証**(`commit.verification.verified`)で行い、committer と author の両方を照らす。効力を持つ記録の側(`introducedBacking`)と強さを揃える
- 照らすコミットは、様式を最後に触ったコミットではなく、**records で様式を追加したコミット**とする
- 本文 `:127` の「記名者本人の push」は、読む手段が実装に無い。読む手段(ホスティングの push の記録)を降ろすまで、裏づけの経路から外すか、未達(undelivered)として表示する。「弱い裏づけ」の文は削り、「裏づけではない」と書き改める

### 理由

1. **弁護の材料が無い**。git の文書は author の名を「認証に効かない」と書く(外部 4)。GitHub の vigilant mode は既定で無効で、無効の利用者の名義を騙った署名の無いコミットには何の表示も付かない(外部 4)。NIST AU-10(4) が求める「レビュー者の識別子と情報の結合の検証」に、文字列の一致は当たらない。本文自身が「弱い裏づけ」と書いたのは、裏づけでないことを半ば認めた表現であり、それを `backed: true` に数えるのは、開示の値が実態より強く見える誤りである
2. **数えないことで壊れるものは、開示の値だけである**。帰属の結果は保証の開示 項目1 の「自己申告の件数」にだけ効き、欠落に数えない(内部 3.4)。1名の体制や無料のプランで様式のほとんどが自己申告になるが、出荷は止まらない。値が大きく変わるのは、今の値が過大だったからであり、正しい値へ戻るだけである
3. **一致と不一致を分けるのは、情報を捨てないため**。author が記名者と違う名を持つ様式は、記名者以外が置いた兆候である。一致と不一致を同じ「自己申告」へ潰すと、この兆候が消える。数え方(裏づけか否か)と、兆候の表示(一致か否か)は別の問いである
4. **`%G?` は CI の runner でほぼ成立しない**〔推。要実機〕。署名者の公開鍵が runner に無いため、署名の経路は動かず、実際に効いていたのは author の一致だけだった(内部 3.4)。署名を足しても裏づかない構成は、採用者に「署名すれば裏づく」と誤って伝える
5. **照らすコミットの誤り**。最後に触ったコミットを照らすと、書き換えた者が author を記名者にすれば裏づけが上書きされる。また基底へ運んだ squash のコミットを照らすと、出荷の PR を開いた者が照らされる(内部 3.4)。追加のコミットを照らすのが正しい

### 1名の体制・無料のプランへの影響(弁護側の確認)

- 1名の体制は、自分の PR を自分でレビューできないため、「記名者のレビュー」の経路が無い。裏づけの経路は**署名だけ**になる。SSH の署名鍵は無料のプランで使え、GitHub はアカウントに登録した鍵で検証する。要求でなく選択肢として残るので、1名の体制を排除しない
- Web の画面や API(`createCommitOnBranch`)で置いたコミットは GitHub が署名し、committer は GitHub の側の主体になる〔推。要実機〕。committer と author の両方を記名者に求める条件では、この経路が裏づかない。この経路を裏づけに数えるか(author が認証された利用者に固定されるなら数えられる)は、実機で確かめてから決める。確かめる前に数えない
- ADR-0107 の名義の共有の構成では、記名者のアカウントの操作が裏づけにならない。`formAttribution` は `signerSharing` を見ていない(内部 5(b))。同じ機会に揃える。揃えないと、共有の構成で判定記録だけが裏づいて見える

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 署名の無い author の一致を弱い裏づけとして数え続ける(現行) | 理由 1。弁護を放棄する |
| 署名を必須にする(裏づかない様式を欠落にする) | 判定記録の帰属は事後でよく、欠落にしないと ADR-0106 が決めている。1〜2名の体制で鍵の運用を既定にする根拠が無い(ADR-0106 決定7 の a2 の却下理由と同じ)。効力を持つ記録ではないものに、効力を持つ記録より重い条件を課すことになる |
| 一致と不一致を同じ「自己申告」に潰す | 理由 3。兆候を捨てる |
| `%G?` を残し、runner に鍵束を配る | 鍵束を配る者が信頼の起点になり、配った鍵束の改ざんで裏づけを作れる。ホスティングの検証のほうが起点が少ない |

### 反論されうる点

- 「三つに分けた表示の (2) は、結局は読み手に『ほぼ裏づいた』と読まれる」。そう読まれない文言にする責任は開示の側にある。(2) の見出しに「署名の無い一致。git の author は自己申告であり、裏づけではない」と書く
- 「本文の改めは、採用済みの ADR の決定を変えるのではないか」。`:127` の文は ADR の本文ではなく第4章の本文である。新しい ADR で理由を記録して改める

## R-4 写しの先取りと、効力を持つ記録の列挙の漏れ

### 結論

- **先取りの経路は欠陥と認める**。record-copy は、既に写しがあれば、今取り出した写しと変わらない欄を比べ、不一致なら**失敗**する。本文など変わりうる欄だけの差は警告にとどめる
- 集約は、写しを追加したコミットの時刻がその PR のマージより前なら、先取りとして欠落に数える
- **autonomy が読む G-6 の差し戻しの記録は、列挙の漏れと認める**。直し方は、効力を持つ記録の列挙へ入れて効力の前の確認を課すのではなく、**履歴の追加だけから読む**形へ改める。そのうえで、この読み方を第4章の本文に明記する(黙って列挙の外に置かない)
- roster-ids の提案は効力を持たない(名簿へ入れるのは人)。ただし、提案の源を写しから API(`--lookup`)へ既定で移し、写しから引いた提案にはその旨を出す

### 理由

1. **先取り**: マージより前に偽の `pr-N.json` を置けば、record-copy は警告だけで成功し、本物の写しが置かれない(`record-copy.yml:167-171` を確かめた)。警告は Actions の記録に残るだけで、集約は読まない。G-6 は写しで数える(R-2 の現行)。この経路は、R-2 で変わらない欄の突合を欠落に上げれば大半が塞がるが、突合で守れない欄(`author_association`)が残るため、書き込みの側でも塞ぐ
2. **失敗にしても誤検出は増えない**。record-copy の再実行は、自分が置いた写しと同じ内容を取り出すので、変わらない欄は一致する。マージの後の本文の編集は、変わりうる欄の差なので警告にとどまる
3. **autonomy の読み手は、PR の時点で効く**。差し戻しの様式を消すと、差し戻し率が下がり、委任の停止を避けられる(内部 2。推論)。G-7 の検出では、すでに行われた委任のマージを取り消せない。ADR-0106 の論理(事後の開示では取り消せない)に照らすと、事後の検出だけでは守れない
4. **列挙へ入れるより、履歴の追加から読むほうが信頼性が高い**。差し戻しの記録を「追加されたコミットの時点の内容」から数えれば、消しても書き換えても数は減らない。force push は止まるので、追加は消せない。偽の差し戻しを足すことはできるが、差し戻し率が上がる側、つまり委任が止まる側にしか効かない。安全側にしか倒れない読み取りに、効力の前の確認を課しても守るものが無い。ルールセットを外した間の書き換えは、R-1 の起点の SHA の祖先の確認で検出する
5. **ただし、黙って列挙の外に置くことは弁護できない**。`:125` は「列挙に無い記録を効力を持つ記録として扱わない」と書くのに、実装は列挙に無い記録で委任の可否を決めている。本文と実装が食い違ったままである。「履歴の追加だけから読み、書き換えが安全側にしか効かない読み取り」という区分を本文に置き、autonomy をその区分に属すると明記する

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 既にあれば警告して exit 0(現行) | 理由 1。欠陥と認める |
| 既にあれば無条件に失敗 | 再実行で誤検出になる |
| G-6 の差し戻しの記録を効力を持つ記録の列挙へ入れ、効力の前の確認を課す | 理由 4。差し戻しは安全側にしか効かない記録で、追加の履歴から読めば書き換えが効かない。確認を課しても信頼性は上がらず、差し戻しを記録する手間が差し戻しを避ける誘因になる(差し戻しの記録が減る側へ働く) |
| autonomy を records の先頭から読み続け、G-7 で検出する(現行) | 理由 3。事後の検出では取り消せない |
| 差し戻しの記録を records の外(基底の `docs/gates/`)へ移す | 差し戻しの直後に委任の判定へ反映できなくなる(基底へ入るのは PR の後)。追加の履歴から読めば records のままで足りる |

### 反論されうる点

- 「履歴の追加から読む区分を作ると、閉じた列挙の意味が薄まる」。区分の条件を「追加の履歴だけを読み、書き換えも偽の追加も判定を厳しい側にしか動かさない」に限り、条件を満たすことを試験で示す。満たさない読み手は列挙へ入れるか、読むのをやめる。区分は列挙の例外ではなく、列挙が守ろうとしたもの(効力の前に改ざんを止める)を別の形で満たす読み方である
- 「先取りの時刻の判定は、コミットの日時が自己申告なので偽装できる」。認める。コミットの日時ではなく、push の時刻(ホスティングの記録)と record-copy の実行の記録で照らすのが正しい。push の記録が取れない構成では、record-copy の失敗(理由 1 の比較)だけが守りになる。その構成を保証の開示に出す

## R-5 開示と記録

### 結論

- **書き込みの主体を限れないというホスティングの制約を、保証の開示へ固定の文として出す**(候補 c を採る)。ただし (c) だけでは判定と照合の扱いが変わらないため、R-1〜R-4 と組で採る
- 開示の文は構成ごとに分ける。records.json の構成では「書き込みの権限を持つ者とジョブのトークンは、写しと様式を新しいコミットで追加・変更・削除できる。止まるのは履歴の書き換えと削除だけ。変更と削除は出荷の時点で列挙する」。records-signed の構成では「人の書き込みは署名で主体を確かめられるが、ジョブのトークンの書き込みは record-copy の書き込みと区別できない」。併せて、走査していない区間、照合できなかった写しの件数、所有者自身による書き換えはリポジトリの中では防げないこと、を出す
- **新しい ADR** を起こす。ADR-0070 決定5(書き換えられない場所)を置き換え、ADR-0106 の閉じた列挙に「追加の履歴から読む区分」を足す。採用済みの ADR の本文は書き換えない
- **EV-0185 は差し替える**(差し替え条件「#379 の会議体の結論」が満たされる)。識別子は再利用せず、検出の構成の主張に新しい EV を付ける。根拠は実機で確かめていない(内部 6-8 の (i)〜(iv))ので、新しい EV は E0 から始める
- **IMPL-0353**(rulesets で書き換えられない場所を作る)は、要求そのものを採らないと決めたので、未達(undelivered)のまま表示し続けるのではなく、「採らないと決めた」旨と置き換え先の IMPL を明記して閉じる。消さない。新しい要求(履歴の走査、変わらない欄の突合の欠落、record-copy の失敗、ホスティングの署名の検証、autonomy の追加の履歴の読み取り、開示の固定の文)にはそれぞれ IMPL を付ける

### 理由

1. **開示は、実装が開示どおりに振る舞うときにだけ意味を持つ**。EV-0185 は「書き換えられない記録として扱わない」と書いたが、集約は写しを優先し、records を正として数え続けた(R-2)。開示だけを足す (c) 単独は、この食い違いを残す。だから組で採る
2. **制約はホスティングの構造であり、採用者の弱化ではない**。ADR-0038 の弱化の検出(env-check の所見)は、採用者が保護を外した場合に出る。主体を限れないことは誰が設定しても変わらない構造なので、所見ではなく固定の文で出すのが正しい(内部 5(c))
3. **所有者自身の書き換えを開示するのは、標準の主張を実態に揃えるため**。1名の体制では、所有者は記名者でもある。リポジトリの中のどの手段も、所有者がルールセットと基底の保護を外して全てを書き換えることを塞げない(外部 0.4)。塞げないものを塞げると読ませないことが、R-1 で防止を要求しない理由と同じである
4. **IMPL-0353 を undelivered で残し続けない理由**。undelivered は「降ろすべき規定がまだ降りていない」を意味する。防止を要求しないと決めた後に undelivered で残すと、読み手は「いずれ降りる」と読む。却下は成果であり、「課さないと決めた」と「まだ降りていない」を区別できる表示にする

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| (c) だけを採る | 理由 1。判定と照合の扱いが変わらない |
| EV-0185 を見直しの期日(2027-01)まで据え置く | 差し替え条件が満たされる。据え置くと、実装を改めた後も「結論が出るまで扱わない」の文が残り、本文と食い違う |
| EV-0185 の識別子を新しい主張に使い回す | ADR-0026 の規則(識別子を再利用しない)に反する |
| IMPL-0353 を消す | 降りていない規定を消さない規則(#222)に反し、却下の記録も消える |
| 外部へ渡す保証の開示(`assurance-disclosure.external.md`)には載せない | 外部の読み手こそ、記録の置き場の強さを知る必要がある。内部の開示と同じ文を載せる |

### 反論されうる点

- 「新しい EV を E0 から始めると、改めた後の構成も実証が無いままになる」。そのとおりで、隠さない。差し替え条件に、実機の確かめ(内部 6-8 の (i)〜(iv))と、走査が検出した M・D・先取りの件数(EV-0111 の観測値と共有する)を置く
- 「開示の文が長くなり、読まれない」。文の長さより、主張の過大のほうが害が大きい。構成ごとに該当する文だけを出す

## 付記: 弁護として最後まで残す主張

- **防止を要求しない**。所有者がルールセットを外せる構造の上で防止を名乗ることは、信頼性を上げず、主張を過大にする
- **写しを残す**。マージの時点の断面は API に無い。写しを捨てる案は採らない
- **誤検出を欠落にしない**。アカウントの削除・API を読めない・マージの後の編集を、改ざんと区別して開示する。改ざんの無い採用者の出荷を止める仕組みは、やがて検査を外される仕組みになる
- **既存の記録を遡って裁かない**。走査の起点より前の M は欠落にせず、走査していない区間として開示する

## 付記: 欠陥と認めたもの

1. 写しを API より優先して G-6 を数え、変わらない欄の不一致を所見にとどめること(R-2)
2. 出荷の後に records を正とし、基底の複製を「書き換えた記録」と判定する向き(R-2)
3. 署名の無い author の一致を backed と数えること。手元の `%G?` に頼ること。最後に触ったコミットを照らすこと(R-3)
4. record-copy の「既にあれば exit 0」による先取りの経路(R-4)
5. autonomy が、列挙に無い records の記録で委任の可否を決めていること(R-4)
6. EV-0111 の差し替え条件が、実装の無い観測(履歴の検出)を前提にしていること(R-1)
7. 本文 `:127` の「記名者本人の push」を、実装が読めないこと(R-3)
