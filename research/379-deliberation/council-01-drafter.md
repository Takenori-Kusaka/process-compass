## 0. 起案の前に直す事実(内部調査の訂正 1 件と、補足 2 件)

### 0.1 差し戻しの記録を「消す」と停止を避けられる、は向きが逆

内部 §2 の表(`autonomy.mjs readRejectionRecords` の行)は「差し戻しの様式を消すと差し戻し率が下がり、停止を避けられる」と書く。HB:160 の引き下げの条件は「独立レビューの差し戻し率が 0% のまま推移した(2か月継続)」であり、差し戻し率が**下がる**向きは停止の側へ倒れる。`autonomy.mjs:451` のコメントも「数え漏れは差し戻し率を下げ、停止の側へ倒れる」と書く。

脅威になる向きは**偽の差し戻しの記録を足すこと**である。判定される側(委任で先へ進めたい側)が、`records/gates/` に G-6 差し戻しの様式を 1 件足すか、`records/reviews/pr-N.json` に差し戻しの宣言行を持つ偽のレビューを入れると、0% の継続が切れ、HB 5.4.6 の 2 行目の引き下げが発火しない。HB:121(引き上げの条件2「基準の範囲内」)の材料も同じ記録から作れる。R-4 の案はこの向きで組む。

### 0.2 写しの `user.id` が変わる正当な場合がある

アカウントが削除されると、GitHub はそのレビューの書き手を ghost(共通の代替アカウント)へ付け替える〔要外: 一次資料で確かめる〕。EV-0112(GC:1170 付近)は「承認者のアカウントの消失」を写しが守るべき損失に挙げている。ホスティングとの突合で `user.id` の不一致を一律に欠落にすると、写しが本来守る場面で正しい写しを欠落にする。R-2 の欄の区分はこれを分けて書く。

### 0.3 G-7 の様式は、出荷の PR の作成者で裏づけられる

EV-0113(CG:648 付近)は、出荷の PR を出荷判定者が開く形にしたと書く。出荷の PR の作成者はホスティングが認証した操作である。G-7 の様式は、署名の鍵を持たない体制でも「様式の今の中身を基底へ入れた PR の作成者または承認者が記名者」で裏づけられる。これは効力を持つ記録の `introducedBacking`(GC:135)と同じ形であり、R-3 で author の一致を外しても、2名以上の体制で成立条件4 に届く道が残る根拠になる。

## R-1 要求の形(防止か検出か)

### 結論

- 写しと様式の置き場の要求を「記名者と判定される側が書き換えられない場所」から、**「記録を残さずには書き換えられない場所」**へ改める。書き換え・追記・削除は、出荷判定(G-7)の集約が機械で検出し、検出したものを欠落に数える
- **防止は要求しない**(課さないと決めたことを本文に書く)。外部の WORM・透明性ログも要求しない。ただし、出荷ごとに記録用ブランチの先頭を、既定ブランチの強制層の下にある出荷の証跡へ固定する(以下「先頭の固定」)。規制業(軸C)では、その出荷の証跡が既存の「文書管理の規程の下への配置」(GC:87)の対象であることを明記する
- 検出は強制層に数えない。保証の開示で「防いでいない」ことを固定の文で示す(R-5)

### 案

#### (1) GC:137 の直後へ挿入する箇条(新設)

```markdown
- 判定記録と写しを、基底ブランチへ入れる前に置く場所(以下「置き場」)は、**記録を残さずには書き換えられない場所**に限る。置き場は、次の3つを満たす
  - 履歴の書き換えと置き場そのものの削除を、ホスティングの規則で止める
  - 置き場の中の既存の記録の変更・削除と、記録の追加を、出荷判定(G-7)の集約が置き場の履歴から機械で列挙できる
  - 前回の出荷で集約が読んだ置き場の先頭を、出荷の証跡(基底ブランチへ入る記録)に残し、次の集約がその先頭から今の先頭までの履歴が連続していることを確かめる
- 置き場への書き込みを、記名者と機械に限ることは求めない。ホスティングが書き込みの主体を限れない構成でも、上の3つを満たせば置き場にしてよい。限れないことは、保証の開示へ出す(後掲 G-7「保証の開示」)
- 集約は、置き場の履歴のうち、次のものを**成立済みの記録の書き換え**として記載の欠落に数える。既存の記録を変更・削除・改名したコミット。写しの対象の PR がマージされるより前に写しを足したコミット。前回の出荷で残した先頭から、今の先頭へ連続しない履歴
- 置き場の性質は、書き換えを止めることではなく、書き換えが後から必ず見えることである。置き場の規則を強制層に数えない
```

挿入先の理由: GC:137「置き場の形は準拠テンプレートが定める」の直後に置き、標準は性質だけを定めるという ADR-0070 決定7 末尾(ADR-0035 の型)を保つ。

#### (2) 「採らない形」(GC:138 の箇条)へ追記する文

```markdown
- **採らない形**(置き場): 置き場への書き込みの防止(書き込める主体を記名者と機械に限る規則)を、本標準の要求にすること。外部の追記専用の保管(WORM、透明性ログ)を要求にすること。ホスティングの管理者は規則そのものを外せるため、ホスティングの中の防止は管理者に対しては成立しない。外部の保管を課しても、記名の帰属(誰が書いたか)は解けない。本標準は、置き場の書き換えを出荷の前に検出して欠落に数え、防いでいないことを開示する形を採る。組織が防止を足すことは妨げない。足した場合も検出は省かない
```

### 理由

1. **防止は、管理者に対して成立しない**。外部 §0-4・§2.1: ルールセットは admin(個人所有では所有者)が外せる。1〜2名の体制では、所有者は判定される側でもある。「書き換えられない」と書けば、成立しない性質を要求として掲げることになる。EV-0185 自身が「書き換えられない記録として扱わない」と書いており、要求の文と実際の扱いが食い違ったまま標準が出回っている。信頼性の観点では、成り立たない約束を掲げることが最も悪い
2. **検出は成立する**。ルールセットが履歴の書き換えを止める限り、既存ファイルの変更は消せないコミットとして残る(内部 §3.6、外部 §2.5)。止まっていない期間(規則を外した間)は、先頭を既定ブランチの強制層の下へ固定しておけば、祖先関係の破れとして出る。検出の網の外に残るのは、「規則を外し、履歴を書き換え、さらに既定ブランチの出荷の証跡も書き換える」経路であり、これは既定ブランチの強制層(PR と G-6)を破る操作になる
3. **既存の差し替え条件と同じ向き**。EV-0111(GC:150-156)の差し替え条件は「git の履歴で検出」した書き換えと追記の件数であり、観測の手段が本文に既に前提されている。降りていないのは観測の実装だけである(内部 §1.4)
4. **21 CFR 11.10(e) の形と合う**。「Record changes shall not obscure previously recorded information」(外部 §3.1)は、変更を禁じるのではなく、変更が以前の記録を覆わないことを求める。追記専用の履歴+検出はこの形である。ただし「computer-generated」「独立」は満たさない(書き手が自分の名で書けるコミット)。だから規制業では、出荷の証跡を文書管理の規程の下へ置くこと(GC:87 の既存の要求)を、ここで明示的に結び付ける。電子記録の規制の適否は所管部門が決める(GC:88 の既存の要求)ことも変えない
5. **NIST AU-9(2)(別システムへの保存)の方向**を、既定ブランチ(強制層の下)への先頭の固定と、文書管理の置き場で部分的に満たす。完全な別システムは要求しない(採らない案 R-1-ii)

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| R-1-i: ルールセットの `update`(Restrict updates)で、記録用ブランチへの push を迂回者(記名者の User と専用 App)に限る(防止) | (1) 個人所有で App を迂回者に置けるかは実機で確かめていない(外部 §1.2)。(2) `GITHUB_TOKEN` を迂回者に置くと、書き込みの権限を持つ者が別ブランチに置いたワークフローも同じ名義で通る(外部 §1.4)。限ったことにならない。(3) 専用 App の鍵は新しい信頼の根になり、environment と既定ブランチのワークフローの保護まで閉じないと鍵を取り出せる(外部 §1.4「残る穴」)。(4) 管理者は規則を外せる。防止を課しても検出は省けず、検出があれば防止の有無で保証の主張は変わらない。組織が足すことは妨げない |
| R-1-ii: 外部の WORM(S3 Object Lock の compliance mode)や透明性ログ(Rekor)、RFC 3161 のタイムスタンプを要求する | 防止の唯一の成立手段ではある(外部 §2.1)。しかし (1) 帰属(誰が書いたか)は解けない。WORM に入る前の内容を判定される側が作れる。(2) 1〜2名の体制に外部の保管の契約を前提にする根拠が無い。(3) 規制業には既存の文書管理の要求(GC:87)があり、その置き場の性質は組織の規程が決める。本標準が置き場の製品を指定する理由が無い(ADR-0035 の型)。見直しの条件は EV-0224 に書く |
| R-1-iii: `file_path_restriction` で `records/**` の変更を禁じる | public では使えない(外部 §1.1)。パス単位の全面禁止で、追加も止まる |
| R-1-iv: 要求の文をそのまま残し、IMPL-0353 を undelivered で表示し続ける | 管理者に対して成立しない性質を、降ろすべき規定として表示し続けることになる。ADR-0106 決定7 の最後の箇条(降ろすと統制が壊れる規定を表示し続けない)と同じ理由 |
| R-1-v: 置き場を記録用ブランチから CI の成果物へ移す | 成果物は基盤の保持期間で消える(GC:115「CI 基盤の既定の保持を保管とみなしてはならない」)。書き換えの履歴も残らない |

### 反論されうる点

- **R-1-a 検出は事後であり、出荷の前に書き換えた写しで G-6 が成立する時間がある**: 判定記録は ADR-0106 で「G-7 の集約。事後でよい」と区分した記録である。書き換えは G-7 の集約で欠落になり、出荷は止まる。事前に効く読み手(autonomy・roster-ids)は R-4 で別に扱う
- **R-1-b 規定を改めて IMPL-0353 を delivered にするのは、言い換えで未達を消すことではないか**: 消えるのは「防止」の未達表示であり、その代わりに (1) 防止を課さないと本文に書き、(2) 防げていないことを出荷ごとの保証の開示に固定の文で出し(IMPL-0440)、(3) 新しい検出の規定を undelivered から始める(IMPL-0432・0435)。読み手が「防いでいない」を知る経路は、今より増える
- **R-1-c 検出の実装そのものを判定される側が書き換えられる**: 集約のスクリプトとワークフローは既定ブランチにあり、変更は PR と G-6 を経る。`pull_request` の契機の verify は PR 側の定義で走る〔要外: 同一リポジトリの PR での定義の版〕。走査の結論は、既定ブランチの定義で走る集約(`workflow_dispatch`・`push`)の出力に限る

## R-2 写しと API の突合の向きと、G-6 の数え方

### 結論

- **写しの正は、欄によって決める**。ホスティングの側で変わらない欄(レビューの識別子・対象のコミット・提出日時・書き手の数値の識別子)は**ホスティングの記録を正**とし、写しとの不一致を欠落にする。ホスティングの側で変わりうる欄(本文・状態・リポジトリとの関係)は、**写しを取った時点の値を記録**とし、ホスティングの側の変化を所見にする。ホスティングの側に変化の記録が無いのに写しが異なる場合は、写しの書き換えとして欠落にする
- **写しにだけあるレビューは欠落**。ホスティングにあり、マージより前に提出されたのに写しに無いレビューも欠落(写しの取りこぼし)

## R-3 様式の帰属(署名の無い author の一致)

### 結論

- **候補 (b) を採る**。署名の無いコミットの author(名前・email・email から推したログイン名)の一致を、判定記録の帰属の裏づけに数えない。自己申告として保証の開示へ出す
- 本文 GC:127・CG:637 の「署名の無い push は、author の一致による弱い裏づけである」を削る。「記名者本人の push」は、ホスティングが認証した push の記録(押した主体)を機械が読める場合に限って裏づけに残す
- 署名の確認は、手元の `%G?` ではなく**ホスティングの検証**(コミットの verification と committer・author のアカウントの数値の識別子)で行い、committer と author の両方が記名者であることを求める。効力を持つ記録の照合(GC:135、`introducedBacking`)と強さを揃える
- 照らすコミットは「様式を最後に触ったコミット」ではなく、**記録用ブランチで様式を足したコミット**とする(足した後の変更は R-1 の走査で書き換えとして出る)。様式を基底へ運んだ PR の**作成者または承認者**(ホスティングの記録)が記名者である場合も裏づけに数える
- 名義を共有する構成(ADR-0107)では、効力を持つ記録と同じく、記名者のアカウントの操作だけでは裏づけに数えず、名義の共有を理由とする自己申告として区別して出す
- **保証の主張の成立条件4 は、帰属を裏づけた G-7・G-8 の記名者で判定する**。自己申告の記名では成立条件4 を成立させない

### 案

#### (1) GC:127 の改め

```markdown
- 判定記録を基底ブランチへ入れる操作に、**記名者以外の者の判定を課さない**。記名の帰属の裏づけは、次のいずれかを機械がホスティングの記録で確かめられるものに限る。名前・email の一致を裏づけに数えない
  - 記名者のレビュー(対象が PR として存在する判定の、記名者本人のレビュー)
  - 判定記録の今の中身を基底ブランチへ入れた変更(準拠テンプレートでは出荷の PR)の、作成者または承認者のアカウントが記名者のアカウントであること
  - 判定記録を置き場へ足したコミットが、ホスティングが署名を検証したコミットであり、committer と author がいずれも記名者のアカウントであること
  - 判定記録を置き場へ足した push を、ホスティングが認証した主体の記録として読め、その主体が記名者のアカウントであること
- 裏づけの無い記録は、記名が自己申告であることを保証の開示へ出す(後掲 G-7「保証の開示」)。記名者のアカウントを AI の担い手と共有する構成では、記名者のアカウントの操作だけを裏づけに数えず、名義の共有を理由とする自己申告として区別して出す(効力を持つ記録と同じ扱い)
```

- 改めの要点: (i) 「署名の無い push は、author の一致による弱い裏づけである」を削る。(ii) 「記名者本人の push」を「ホスティングが認証した push の主体の記録」に限る。(iii) 「出荷の PR の作成者」を裏づけに加える(0.3)。(iv) 名義の共有の扱いを揃える
- 「出荷の PR の承認者」を裏づけに数えることは、ADR-0106 決定6(出荷の PR の承認者を出荷判定者の本人と書かない)と矛盾しない。決定6 は「承認者=出荷判定者」と書かないことであり、承認者が自分の記名した記録(たとえば G-8 の様式)を運ぶ PR を承認した場合に、その承認をその人の記録の裏づけに数えることを妨げない。承認は転記の確認であり、記録の中身の判定ではない、という性格も変わらない

#### (2) CG:637 の改め

「帰属の裏づけは記名者本人の操作(署名コミット、記名者本人の push、または記名者のレビュー)です」を、「帰属の裏づけは、記名者本人のアカウントの操作として、ホスティングの記録で確かめられるもの(記名者のレビュー、記録を基底へ入れた PR の作成または承認、ホスティングが検証した署名コミット、認証された push の主体)です。名前・email の一致は裏づけに数えません」へ。

#### (4) EV-0226(成立条件4 の箇条の直後)


### 理由

1. **author の一致は認証ではない**(外部 §4)。Git の文書が「This name has no effect on authentication」と書く。判定者の noreply アドレスを author に書けば、誰でも判定者の名義に見せられる。「弱い裏づけ」は、裏づけの語を使った自己申告である。本文自身が弱いと書きながら backed に数え、自己申告の件数から外していた。開示の値が実態より良く見える向きの誤り
2. **照合の強さの二重化を解く**(内部 §3.4、§5 (b))。同じリポジトリで、効力を持つ記録はホスティングの検証と committer・author を求め、判定記録は手元の `%G?` と author だけを読む。CI の runner は署名者の鍵を持たず、`%G?` はほぼ成立しない〔推〕。結果として実際に効いていたのは author の一致だけである
3. **「記名者本人の push」は、実装が読めない裏づけ**だった(git は push した者を記録しない。内部 §3.4)。読めない裏づけを本文に残すと、裏づけがあると読まれる。ホスティングの push の記録(activity。外部 §2.5)を読める場合に限って残す
4. **成立条件4 は対外的な主張**である。「G-7 と G-8 を別の自然人が記名した」を、誰でも書ける名前で成立させると、顧客へ渡す保証の主張が自己申告の上に立つ。2 名以上の体制では 0.3 の経路で届くため、鍵の運用を既定にしない(ADR-0106 の a2 却下の理由)とも両立する

## R-4 写しの先取りと、効力を持つ記録の列挙の漏れ

### 結論

- **先取りは三重に塞ぐ**。(1) record-copy は、同じ PR の写しが既にあるとき、今取り出した写しと比べ、一致すれば再実行として成功、食い違えば失敗し、食い違いの記録を記録用ブランチへ追記する。(2) 集約は、マージより前に足した写しを書き換えとして欠落にする(R-1、IMPL-0432)。(3) 集約は、写しにだけあるレビューを欠落にする(R-2、IMPL-0433)。(3) が主の防御で、(1)(2) は早く気づく手段
- **委任の判定(HB 5.4.6 の差し戻し率)が数える G-6 の差し戻しの記録を、効力を持つ記録の列挙に加える**。効力を持つ前(委任の判定の時点)に帰属を確かめ、確かめられない記録を差し戻し率の分子に数えない。数えないことは差し戻し率を下げ、停止の側へ倒れる(0.1)。列挙へ足す変更は厳しくする向きの変更であり、GC:125 の既存の文に合う
- **名簿の数値の識別子の提案**(roster-ids)は、効力を持つ記録に加えない(提案であり、名簿へ入れる人の変更が効力を持つ記録である。ADR-0108)。ただし提案の源を、ホスティングとの突合(R-2)を通った写しに限る

### 案

### 理由

1. **ADR-0106 の論理をそのまま当てる**。「事後の開示では、既にマージされた変更を取り消せない」(GC:125)。委任の判定は PR の時点に効き、その後の G-7 の検出では委任のマージを取り消せない。列挙に無いが効力を持つ記録が残ると、閉じた列挙(「列挙に無い記録を、効力を持つ記録として扱わない」)が、統制の穴の目隠しになる
2. **向きの非対称**(0.1)。数えないことは停止の側へ倒れる。帰属を確かめられない記録を数えない規則は、失敗したときに閉じる
3. **先取りの防御の主は、ホスティングとの突合**。record-copy の比較は、マージの後に偽の写しを差し替える経路を塞がない。集約の突合は、いつ置いた写しでも同じように捕まえる。record-copy の比較と履歴の走査は、早く・別の観点で気づく手段として足す。どれか 1 つの失敗で先取りが通らないようにする
4. **roster-ids は提案**であり、効力を持つのは人が名簿を変える記録である(ADR-0108 決定2)。提案の源の汚染は、提案を読む人に誤った値を見せる経路なので、源を突合済みの写しに限るだけで足りる。列挙には足さない

| R-4-iii: record-copy の比較だけで先取りを塞いだとする | 理由3。また record-copy が失敗しても、集約は Actions の実行の記録を読まない(内部 §3.2) |
| R-4-iv: record-copy が食い違いのときに既存の写しを上書きする | 追記だけの規則を機械が自ら破る。上書きの経路を作れば、偽の写しを作る者がその経路を使う |
| R-4-v: roster-ids の提案を効力を持つ記録へ足す | 提案は照合・判定に効かない。効くのは名簿の変更で、既に効力を持つ記録である(ADR-0108) |

### 反論されうる点

- **R-4-a 委任の判定の時点で REST を引くと、トークンの無い手元の実行で判定できない**: 手元の実行では記録用ブランチの記録を数えず、停止の側へ倒す(IMPL-0439 の note)。委任のマージの可否を決める実行は CI であり、トークンを持つ
- **R-4-b 「委任の判定」は G-6 の判定記録の働きであって、記録の種類ではない。同じ記録が判定記録と効力を持つ記録の両方になる**: 列挙は記録の働きで分けている(GC:118「働きによって2つに分かれます」)。同じ様式でも、委任の判定が数える場面では効力を持つ記録として帰属を確かめ、G-7 の完備では判定記録として扱う。表の区分の欄にこの旨を書くかは審議に掛けたい
- **R-4-c HB:121(引き上げの条件2)の材料も同じ記録から作れる**: 引き上げは B-2 が判定する(HB:117)。人の判定の材料として、帰属を確かめた件数と確かめられない件数を分けて出せば足りる。効力を持つ記録の列挙には、自動で効く引き下げと委任のマージの判定だけを入れる

2. **「書かれていない」と「課さないと決めた」の区別**(コアポリシー)。防止を課さないことを本文の採らない形に書き、開示の固定の文で出荷ごとに示す
3. **ADR-0038 の扱いとの関係**: 採用者が records の保護を外すのは統制の弱化で、env-check の所見に既に出る。主体を限れないことは弱化ではなくホスティングの構造であり、所見ではなく固定の文で出す(内部 §5 (c))

## 論点ごとの結論(1 行)

- R-1: 置き場の要求を「記録を残さずには書き換えられない場所」へ改め、G-7 の集約による履歴の走査と、出荷ごとの先頭の固定で検出して欠落にする。防止と外部の WORM・透明性ログは要求しない(採らない形に明記。EV-0224)
- R-2: 写しの正は欄で決める(不変の欄はホスティング、本文・状態は写しの時点の値)。写しにだけあるレビューは欠落。G-6 は突合を通った写しで数え、出荷の後は基底の複製を正とする(G-7 基準5・`mergeRecordSources` の向きを改める。EV-0225)
- R-3: 候補 (b) を採る。署名の無い author の一致を裏づけから外し、本文 :127・CG:637 の「弱い裏づけ」を削る。署名はホスティングの検証で committer・author の両方を照らし、出荷の PR の作成者・承認者を裏づけに加え、成立条件4 は裏づけた記名者で判定する(EV-0226)
- R-4: 先取りは record-copy の比較・履歴の走査・ホスティングとの突合の三重で塞ぐ。委任の判定が数える G-6 差し戻しの記録を効力を持つ記録に加え、帰属を確かめられないものは数えない(停止の側へ倒れる。EV-0227)。注意: 内部調査の「消すと停止を避けられる」は向きが逆で、脅威は偽の差し戻しを足すこと
- R-5: 候補 (c) を (a)(b) と組で採る。書き込みの主体を限れないことを保証の開示の項目1(外部用を含む)に固定の文と件数で出す。ADR-0109 を新設して ADR-0070 決定5 を置き換え、EV-0185 を削除、IMPL-0353 は規定を改めて残し、IMPL-0128 は undelivered へ戻す
