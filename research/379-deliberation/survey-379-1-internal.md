### 1.5 「効力を持つ記録」(#380・#428・#429・#430、ADR-0106〜0108)との関係

- ADR-0106 決定7(`0106-...md:75`)は、台帳と解除の記録を記録用ブランチへ移す案(a1)を **EV-0185 を理由に却下**した。#380 の会議体(drafter・field・qa-audit・standards・defender)は全員、a1 を「#379 の結論に依存」「records は判定される側が書ける」として退けた(`research/380-deliberation/decision.md:52` ほか)
- #428 の突合 M-2(`research/428-delivery/crosscheck.md:31-34`, `notes.md:84`)で、前倒しで要る SG の記録も記録用ブランチの経路から外した。今は、判定者本人が作成者か承認者となる PR で `docs/gates/` へ入れる。**判定者本人の records への push は、効力を持つ記録の照合に使われない**
- 結論: **効力を持つ記録はすでに records に依存しない設計になった**。残る依存は、判定記録(様式・写し)と、次節で示す「列挙に無いが判定・照合に効く読み取り」である
- ADR-0108 / EV-0223(`gate-criteria.md:93-99`): 名簿の数値の識別子は、**記録用ブランチの写しの `user.id`・`author.id` から提案する**(`roster-ids.mjs:3-15`)。名簿へ入れるのは人で、名簿の変更は効力を持つ記録になる。ただし、提案の源である写しが書き換えられると、誤った識別子が提案される。roster-ids は「写しどうしの食い違い」と「`--lookup` の現在の値との食い違い」を所見に出す。偽の写しを1件だけ足し、他の写しと矛盾しない形にすれば、`--lookup` を使わない提案では見抜けない〔推〕
- ADR-0107(`0107-...md:58`): 共有の担い手と未申告の担い手には、記録用ブランチへの push を拒否する設定を置く。`guard-bash.mjs:179` は `git push ... records` を拒否する。担い手が書いたプログラムや API(`createCommitOnBranch`、contents API)の経路は止まらないと、ADR 自身が開示している

## 3. 準拠テンプレートの現物

### 3.1 ルールセット

- `records.json`: `non_fast_forward`・`deletion` だけ。bypass actor なし
- `records-signed.json`: 上の2つに `required_signatures`。規制業(軸C)と CL2 以上(軸E)向け(`.github/rulesets/README.md:33-34`)
- どちらにも `update`(更新の制限)・`creation`・`pull_request`・ファイルパスの規則は無い。**新しいコミットによる追加・変更・削除はすべて通る**〔確: 規則の一覧から〕
- README `:117` は、プランによりルールセットを使えない構成について、verify が「`records` ブランチ自体の書き換えは検出できません」と開示済み。**ルールセットを適用した構成でも同じ**であることは書かれていない
- README `:93`: `records/**` の CODEOWNERS は誘導層で、遮断に数えない(pull_request の規則が無いため、そもそも効かない)

### 3.2 record-copy.yml(写しの書き込み)

- 契機: `pull_request: closed` かつ merged。権限は `contents: write`、`pull-requests: read`。定義は既定ブランチのものを使う(`:54-55`)
- 書き込み: git push(既定)、または `RECORDS_SIGNED=true` / `records.signed` のときは GraphQL `createCommitOnBranch`(GitHub が署名する)
- **追記だけ**: `records/reviews/pr-N.json` が既にあれば、警告(`::warning::`)を出して **exit 0** で終える(`:167-171`、`:207-210`)
  - **先取りの経路**〔推〕: 書き込みの権限を持つ者が、マージより前に偽の `pr-N.json` を push しておくと、record-copy は本物の写しを置かずに成功で終わる。警告は Actions の記録に残るだけで、集約は読まない
- 写しの欄: `copied_at`・`copied_by: "record-copy workflow (GITHUB_TOKEN)"` は**写しの中の自己申告**で、誰が書いても同じ値を書ける
- `edited_by` は GraphQL の `editor`(直近の編集者)から引く。編集の履歴の全体(`userContentEdits`)は引いていない

### 3.3 ship-evidence.yml の verify(`:284-400`)

検出するもの:

- 出荷の PR の差分で、`docs/records`・`docs/gates`・`docs/evidence` の**追加以外**(M・D・R)の変更を失敗させる(`:358-363`)
- 複製(PR の中の `docs/records/reviews/*.json`)と records の**今の先頭**の写しの一致。シェルで比べる欄は `pr`・`merge_commit_sha`・`head_sha` と `reviews[]` の `id`・`commit_id`・`submitted_at`・`user.id`・`body`(`:370`)。`state`・`author`・`author_association`・`edited_by`・`user.login`・`user.type` は比べない。ただし、同じジョブで再実行する集約の `mergeRecordSources` は JSON 全体を比べるため、出荷の PR の中の不一致は集約の欠落としても出る
- 様式は内容の一致(`:383-391`)。records に無い様式を出荷の PR で足すと失敗する

見ないもの:

- **records の写し・様式が、ホスティングの記録(承認レビューそのもの)と一致するか**。verify は「複製 = records の先頭」を確かめるだけで、records の中身の正しさは確かめない
- **records の履歴**。先頭より前に既存のファイルが変更・削除・差し替えされたかを見ない
- records へ書き込んだ主体(record-copy のジョブか、人か、別のワークフローか)
- 写しが置かれた時刻(マージより前に置かれた写しは先取りの疑いがある)

### 3.4 records.mjs `recordAttribution`(`:299-313`)と様式の帰属

- `lastCommitOf` は `git log -1 --format=...%G?` で、**手元の git の署名の検証**を読む(`:83-90`)。G・U を署名ありとする
  - CI の runner には署名者の公開鍵(GPG の鍵束、SSH の allowed signers)が無いため、%G? は E(検証できない)などになり、`signed=null` になる〔推。実機未確認〕。つまり **CI の集約では `signed-commit` の経路はほぼ成立せず、実際に効くのは author の一致**である
  - 署名ありの場合も **author だけを照らし、committer を照らさない**。`material-attribution.mjs:301-304` の `introducedBacking` は、「ホスティングの署名の検証が結び付けるのは committer。author は偽装できる」として、committer と author の両方を求める。**同じリポジトリの中で、帰属の照合の強さが食い違っている**
- `author-login`・`author-email`(署名なし)を `backed: true`(弱い裏づけ)にする(`:309-310`)。author の email は書き手が自由に設定できる。GitHub も、コミットの email を、その email を確認済みにしたアカウントへ対応づけて表示する。判定者の noreply アドレスを書けば、判定者の名義に見える〔推: 周知の仕様。〔要外〕で一次資料を確かめる〕
- 本文 `:127` の「記名者本人の push」は、**実装では読まれていない**。git のコミットは push した者を記録しない。実装が読むのは author だけである
- 帰属の結果が効くのは、保証の開示 項目1 の「記名が自己申告の記録」の件数だけで、欠落には数えない(`aggregate-evidence.mjs:2444-2447`、IMPL-0128 は `check=presence`)
- `formAttribution` は、様式を基底へ運んだ PR の承認者のうち、記名者本人の承認を `approval-review` とする(`:552-571`)。出荷の PR の承認者は開いた人以外の人(転記の確認)なので、出荷判定者本人の様式は、この経路では通常裏づかない。その場合は、基底の HEAD でファイルを最後に触ったコミット(出荷の PR を squash したコミット)の author で照らすことになる。squash のコミットの author は PR の作成者なので、**records へ様式を置いた者ではなく、出荷の PR を開いた者が照らされる**〔推〕

### 3.5 aggregate-evidence.mjs が records を読む経路

1. `readRecordsBranch`(`records.mjs:185-243`): `refs/remotes/origin/records` か `refs/heads/records` の**先頭の木**を `ls-tree` と `git show` で読む。履歴は読まない。各様式についてだけ `lastCommitOf`(最後に触ったコミット)を取る
2. `readBaseCopies`: 基底の `docs/records/reviews/`
3. `mergeRecordSources`: 両方を突き合わせ、不一致を欠落にする。正は records(2 の表の行を参照)
4. G-6 の数え方・判定者本人のレビュー・機械が出す欄: 写しを優先する
5. `reconcileCopy`: 写しと API の差は所見にする

### 3.6 書き込みの主体と、検出されるかどうか

前提: records.json を適用した構成。書き込みの権限を持つ者を W、ジョブのトークンを T(どのブランチのワークフローも `permissions: contents: write` を宣言できる。ADR-0090 の分析と同じ。`ship-evidence.yml` も `contents: write` で、`pull_request` で動くときは PR の側の定義が使われる〔要外: pull_request イベントで使われるワークフロー定義の版を一次資料で確かめる〕)とする。

| 操作 | 主体 | verify | 集約 | 履歴から検出できるか |
| --- | --- | --- | --- | --- |
| 既存の写し `pr-N.json` を、新しいコミットで書き換える(出荷の前) | W・T | 検出しない(複製は書き換え後の先頭と一致する) | 承認・状態・`commit_id`・`user.id`・`author_association` の書き換えは検出しない。API が読めれば、本文・状態・ログイン名の差が**所見**として出る | できる。そのファイルを M にしたコミットが履歴に残る(non_fast_forward のため消せない) |
| 写しを新しく足す(偽の承認を含む写しの先取り) | W・T | 検出しない | 写しにだけあるレビューは所見になる。G-6 は写しで数える | できる。追加のコミットの時刻・作成者・付随する record-copy の実行の有無で疑える。ただし、作成者は偽装でき、T の push は record-copy と同じ `github-actions[bot]` になる |
| 写しを消す | W・T | — | `copyCoverage` が欠落として出す(record-copy の失敗と区別しない) | できる(D) |
| 既存の様式を書き換える・消す | W・T | 出荷の前なら検出しない。出荷の後に records だけを書き換えると、基底と食い違って欠落になる(ただし基底の側が「書き換えた記録」とされる) | 帰属は最後に触ったコミットの author で照らすので、書き換えた者が author を記名者にすれば、弱い裏づけのまま | できる(M・D) |
| 記名者の名を書いた様式を足す | W・T | 検出しない | author を記名者の noreply にすれば `author-login`(backed) | 追加のコミットの author は偽装できる。push した者は git に残らない |
| G-6 の差し戻しの様式を消す | W・T | — | autonomy の差し戻し率が下がる。委任の判定は PR の時点で records の先頭を読む | できる(D)。ただし、委任の判定はそれを見ない |
| records-signed の構成で、上のいずれか | W は自分の鍵で署名、T は `createCommitOnBranch` | 同上 | 同上 | 署名を検証したコミットの committer(ホスティングの記録)で、W の書き込みを人に結び付けられる。**T の書き込みは record-copy の書き込みと区別できない**(どちらも GitHub が署名した `github-actions[bot]`) |

履歴からの検出についてのまとめ:

- 履歴の書き換え(force push)とブランチの削除はルールセットで止まる。そのため、**先頭から辿れる履歴は追記だけ**になる。既存のファイルの M・D・R は、`git log --name-status records -- records/` で機械的に列挙できる〔確: ルールの性質から。走査の実装は無い〕
- 消せないのは「書き換えたこと」であって、「誰が書き換えたか」ではない。git の author・committer は自己申告である。主体を人に結び付けられるのは、(i) ホスティングが署名を検証したコミットの committer、(ii) push した者のホスティングの記録(リポジトリの活動の API。push の actor・前後の SHA を返す〔要外: API の存在・保持期間・プランの条件〕)の2つだけである
- ルールセット自体の無効化・削除は管理者ができる。env-check(`adoption-trial.mjs:1278-1350`)が読むのは**今の**規則だけである。無効化していた間の force push は、今の規則からは見えない〔要外: ルールセットの変更の履歴の API の有無〕
- 写しには、ホスティング側に原本がある(承認レビュー)。`id`・`user.id`・`commit_id`・`submitted_at` はホスティングの側で変えられない欄である〔要外: レビューの `commit_id` と `submitted_at` が不変かを確かめる〕。本文はホスティングの側で編集できる。`state` は dismiss で変わる。したがって写しは、**履歴に依らず、ホスティングとの突合で書き換えを検出できる**。様式にはホスティング側の原本が無いため、履歴と署名に頼るしかない

## 5. 候補ごとの整合と実装の手がかり

### (a) 要求を「記録を残さずに書き換えられない場所」へ改め、記名者以外の書き込みと既存ファイルの変更を集約で検出する

整合:

- **EV-0111 の差し替え条件(git の履歴で、記名者以外の書き換え・追記を数える)と同じ観測を要求へ上げる形**で、既存の規定と向きが一致する
- ADR-0106 の区分(判定記録は G-7 の集約で事後に確かめる)と合う。検出は承認を課さないので、決定2(記名者以外の判定を課さない)とも衝突しない
- ADR-0038 との関係: 検出は遮断ではない。「書き換えられない」を「書き換えが記録に残り、出荷の時点で検出される」へ改めることになる。強制層に数えない旨を開示する必要がある
- ADR-0090 との関係: 防止(ADR-0090 (c) と同じ形。records の `update` の規則で書き込みを結び付いた資格情報に限る)は、様式を判定者本人が直接 push する経路と両立しない。ルールセットの bypass actor に個人を指定できない〔要外: bypass actor に指定できる種別(リポジトリの役割・チーム・App・deploy key)〕。また T は App として bypass に入れられない〔要外〕。防止ではなく検出を選ぶ理由はここにある
- **前提として合わない箇所**: `mergeRecordSources` と G-7 基準5(`:1167`)は records を正としている。(a) を採るなら、出荷の後は**基底の複製(既定ブランチの強制層の下にある)を正とし、records との食い違いを records の側の書き換えとして出す**向きへ改める必要がある
- **事後の検出が届かない読み手がある**: autonomy(委任の判定、PR の時点)は records の先頭を読む。G-7 の集約で検出しても、すでに行われた委任のマージは取り消せない。ADR-0106 の論理(事後の開示では取り消せない)に照らせば、G-6 の差し戻しの記録は効力を持つ記録の列挙に入れるべきか、少なくとも委任の判定が records の書き換えの検出を読む必要がある。**閉じた列挙(`:125`)との突合が要る論点**

実装の手がかり:

1. 履歴の走査(新設): `git log --reverse --format=%H%x09%cI%x09%an%x09%ae%x09%cn%x09%ce --name-status records -- records/`
   - `records/` の下で A 以外(M・D・R・C)を **「成立済みの記録の書き換え」として欠落**に数える
   - 写しの追加のコミットは、record-copy の形(1コミット1ファイル、件名 `records: PR #N の承認レビューの写しを置く`)と、その PR の `merged_at` より後であることを確かめる。マージより前に置かれた写しは先取りの疑いとして欠落に数える
   - 判定者本人の様式の追加以外の書き込み(記名者以外の作成者、ホスティングの検証が通らないコミット)を、EV-0111 の追記の件数として出す
2. 写しのホスティングとの突合を所見から欠落へ上げる: `reconcileCopy` を REST(`pulls/N/reviews`。数値の `user.id`・`commit_id` を持つ)で行い、`id` で対応づける。不変の欄(`id`・`user.id`・`commit_id`・`submitted_at`)の不一致と、写しにだけあるレビューを欠落にする。本文の差は、GraphQL の `lastEditedAt` と `userContentEdits`(編集の履歴。EV-0220 の「`editor` は直近だけ」の弱さも同時に埋まる〔要外: PullRequestReview が UserContentEditable で、編集の履歴を返すか〕)で、写しの `copied_at` より後の編集があればホスティングの側の編集、無ければ写しの側の書き換えと区別する
3. record-copy.yml の「既にあれば exit 0」を、既存の写しと今取り出した写しの不一致で失敗させる形に改める(先取りの検出)
4. 主体の記録: リポジトリの活動の API で、records への push の actor を引き、記名者・record-copy の実行と照らす〔要外: API の保持期間・取得できるプラン〕。保持期間を過ぎる前に読むなら、record-copy 自身が直前の push の記録を写しへ入れる形も考えられる
5. 出荷の証跡に、取り込んだ records の先頭の SHA を記録する(`aggregate-evidence.mjs:3742-3748` は `head` の先頭8文字を既に出している)。次の出荷の集約は、前回の SHA から今回の先頭までの区間だけを走査すれば足りる。前回の SHA が先頭の祖先でなければ、履歴の書き換え(ルールセットの無効化の間の force push)として欠落にする
6. 試験: `test-records.mjs`・`test-aggregate-records.mjs` に、M・D のコミットと先取りの写しの違反・適合の対を置く

### (b) 署名の無い author の一致を、帰属の裏づけに数えない

整合:

- **本文 `:127` と `ci-gates.md:637` が「署名の無い push は author の一致による弱い裏づけ」と明記している**。(b) はテンプレートだけでなく、標準の文の改めを要する
- 効力を持つ記録(`introducedBacking`)は、すでにホスティングが検証した署名と、committer・author の両方が記名者であることを求めている。判定記録の側だけが手元の %G? と author を読み、author の一致を backed にする。(b) は**同じ標準の中の照合の強さを揃える**変更になる
- ADR-0106 決定7 が「署名コミットだけで裏づける形(a2)」を退けた理由(鍵と名簿のアカウントの結び付きを確かめていない。1〜2名の体制で鍵の運用を既定にする根拠が無い)は、**効力を持つ記録を通すための唯一の手段として**の話である。(b) は判定記録の裏づけを狭めるだけで、裏づかない記録は自己申告として開示されるため(欠落にしない)、出荷は止まらない。直接は衝突しない。ただし、多くの採用者で様式のほとんどが自己申告になる。保証の開示の値が大きく変わる
- 本文 `:127` の「記名者本人の push」は、実装が読めない(git に push の主体が無い)。(b) を採るなら、push を裏づけに残すには主体の記録(5 (a) の4)が要る。読めないなら、本文から外すかを決める必要がある
- ADR-0107(名義の共有): 共有の構成では記名者のアカウントの操作だけでは裏づけにならない。この扱いは判定記録の様式の帰属(`formAttribution`)にはまだ入っていない〔確: `formAttribution` は `signerSharing` を見ない〕。(b) と同じ機会に揃えるかが論点になる

実装の手がかり:

- `recordAttribution` の `author-login`・`author-email` を `backed: false`(自己申告。理由つき)にする
- 署名の判定を手元の %G? からホスティングの `GET repos/{repo}/commits/{sha}` の `commit.verification.verified` と `committer.login`・`author.login`(数値の識別子)へ移す。`material-attribution.mjs:412-424` の `prOfCommit` の PR を経ない分岐をそのまま使える。records ブランチのコミットも同じリポジトリのコミットなので引ける〔推〕
- 署名を検証したコミットで committer・author とも記名者のものに限る(`introducedBacking:301-304` と同じ条件)
- 様式を基底へ運んだ squash のコミットではなく、**records で様式を追加したコミット**(`git log --diff-filter=A --format=%H records -- <file>`)を照らす。今の実装は最後に触ったコミットを照らすため、書き換えた者で上書きされる
- IMPL-0128 の note と `check=presence` の扱い、試験 `test-records.mjs` の `author-login` の期待値を改める

### (c) 書き込みの主体を限れないというホスティングの制約を、保証の開示へ出す

整合:

- ADR-0090 決定2 の未達の区分(手段が無い / 使わないと決めた)と同じ型になる。records は「配備先が同じリポジトリの参照」と同じ構造なので、ADR-0090 の (c) を満たさない構成として開示するのが一貫する
- README `:117` は、ルールセットを使えないプランについて「records 自体の書き換えは検出できない」とだけ開示している。(c) はルールセットを適用した構成にも広げる

- ADR-0038(統制の弱化の検出の引き渡し): 採用者が records の保護を外した場合は、env-check の所見(`adoption-trial.mjs:1317-1321`)として既に出る。主体を限れないことは、弱化ではなくホスティングの構造なので、所見ではなく保証の開示の固定の文として出す形になる

実装の手がかり:

- 外部へ渡す保証の開示(`assurance-disclosure.external.md`)にも同じ文を載せるかを決める

## 6. 会議体へ渡す論点(内部調査から)

1. **G-6 の承認が、書き換えうる写しを優先して数えられている**(`aggregate-evidence.mjs:1548-1551`)。ホスティングとの差は所見にとどまる。EV-0185 の「書き換えられない記録として扱わない」と、実装の扱いが食い違っている
2. **正の向き**: `mergeRecordSources` と G-7 基準5(`:1167`)は records を正とし、基底の複製を「人が書き換えた記録」とする。既定ブランチの強制層の下にある基底のほうが強い置き場である
3. **records の読み手で、効力を持つのに列挙に入っていないもの**: autonomy の差し戻しの記録(委任の判定、PR の時点)。ADR-0106 の閉じた列挙と突き合わせる
4. **record-copy の「既にあれば exit 0」**による先取りの経路
5. **本文 `:127` の「記名者本人の push」は実装が読めず、「署名の無い push は弱い裏づけ」は本文が認めている**。(b) は標準の文の改めを要する
6. 照合の強さが二重になっている: 判定記録は手元の %G? と author、効力を持つ記録はホスティングの検証と committer・author
7. 付随の不整合(ついでに直す候補): `template/scripts/init/generate-profile.mjs:2841-2842` のコメントが、出荷の PR の承認者を「出荷判定者本人」と書いている。ADR-0106 決定6(出荷の PR の承認者を出荷判定者の本人と書かない)と食い違う
8. 実機で確かめていないこと(EV-0185 の差し替えの材料): (i) records.json の下で、書き込みの権限を持つ者が既存の写しを変えるコミットを push できること。(ii) 別のブランチのワークフローの T が records へ push できること。(iii) CI の runner で、署名つきのコミットの %G? が何を返すか。(iv) リポジトリの活動の API で、records への push の actor が取れるかと、その保持期間
