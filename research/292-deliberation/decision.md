## 1. 母集団・単位・除外(I-1〜I-3)

### I-1 母集団

- 全委員が「節」を棚卸しの単位にし、文末の機械の列挙を合否に使わないことで一致した
- 理由: 1.7.1 は文末の強さに差を置かず、1.7.2 は迷う文を要求として読む。文末で作る母集団は閉じない(標本の適合率 約 0.73、survey-292-1)。適合率 0.70〜0.81 の語の検出を合否にしない理由(`provision-forms.md` L82)と同じ。ETSI EG 201 058 8.2 は全 shall の機械的な探索から要求の一覧を作らないとする。外部の no-silent-gap(FedRAMP・27001 の適用宣言書・Kubernetes conformance)は、識別子が先に振られた閉じた集合に掛かる(survey-292-3)。本標準でそれに当たるのは節の見出し(15 日で 296 中 1 件だけ変化)
- 番号つきの要求事項・禁止事項の表の行も単位にする(品質保証・規格)。3.11.4 要求事項6 は節に IMPL-0130 があるため、節の単位では漏れが見えなかった
- フェーズ5・6 を含める(起草・現場・品質保証・擁護。規格は外す案)。名指しの頁(`pre-review-automation`・`seeded-error-safety`)がフェーズ5 にあり、外すと手続の外に出る。1.8 の「フェーズ5・6 は本文に従属する」はマークの要否と別の問い
- 落とした案: 強い文末だけ(1.7.1 と当たる)、文の単位の no-silent-gap(除外が千件規模になり、理由が書き埋められる印に堕ちる。G-5 の 3 条件の「実効的な偽陽性が無い」を満たさない)

### I-2 区分

- 区分: `marked`(その節が持つマークの識別子を列挙。番号つきの表の行がある節は、行番号ごとに `marked` か `none` を書く)/ `kb`(判定基準の表。`integrated.yaml` へ降りる)/ `none`(閉じた区分: 説明・制度設計・所在は他節・課さない。理由を必須。「所在は他節」は所在を必須)/ `pending`(未棚卸し)
- `marked` の登録は、登録者が「この節の、実行主体の挙動を制約する規定のすべてに、列挙したマークがある」と判断したことを記録する(起草)。1 つのマークで節が済んだと扱わない(擁護)
- 判定者・人の席を縛る規定は対象に入る。1.4 は「担い手」を人または AI の実行主体と定義する(擁護)。既に 13 件以上が判定者の規定にマークを持ち、規約の表が実務と食い違っていた(品質保証)。規約の「対象にする」に「ゲートの判定者・ロールの席が守るべき手続のうち、様式・スキル・通知へ降ろすもの」を足す

### I-3 除外の書き方と陳腐化

- 争点: 本文の印(現場・規格)か、本文の外の登録簿(起草・品質保証・擁護)か
- 裁定: 登録簿 `src/data/impl-inventory.yaml`。理由: (1) 本文の印は、規定を書く者が同時に除外を決める形になり、差分で除外を読む場所が分散する(品質保証)。(2) 登録簿なら、消えた鍵・存在しない識別子を決定論で落とせる(Rust `#[expect]`・ESLint v9 の未使用抑止の型。偽陽性が出ない)。(3) 本文の印は読者向けの頁に除外の印が並ぶ
- 鍵は頁 + 見出しの経路。見出しの「(適用: …)」は外して照合する。第6章の重複見出しは経路で区別する
- 失敗にするもの: 消えた鍵、列挙した識別子が台帳に無い、`none` の節にマークがある(使われない除外)、閉じた区分の外の語、理由の空
- 本文の指紋による無効化は課さないと明記する(擁護・現場。起草は推した)。文言の調整のたびに発火し、確認が機械的な更新に変わる。節の中身の変更で新しい規定が入った場合は、会議体の突合で区分を確かめる。これは機械が見ない限界として「限界」節に書く

## 2. 未分類・0 件・限界(I-4〜I-6)

### I-4 未棚卸しの扱い

- ラチェット(現場・品質保証・擁護)を採る: 2026-10-23 時点の全節を `pending` で一度だけ登録し、基準線にする。登録の無い節(新設・改名)は失敗。基準線に無い `pending` は失敗(変えた節を `pending` で登録し直す経路を塞ぐ: 起草)
- 全件の失敗化(規格・起草の「本 Issue で全節を終える」)は採らない。理由: 400 節超を一度に分類すると、分類の一致率が測られていないまま確定する(擁護)。ただし起草・規格の懸念(ADR-0061 決定3 の「別作業」が 103→101 件で止まった)は正しい。そこで残りの章ごとに Issue を起票し、持ち主と順序を付ける。台帳の冒頭に `pending` の件数を章ごとに出す
- 根拠水準: E1(節の棚卸しが漏れを減らすことは測られていない)。暫定マーク、見直し 2027-10。差し替え条件: 棚卸し済みの節で、後から未マークの規範が見つかった件数

### I-5 0 件の扱い — 課さないと明記する(全委員一致)

- 「降りていない規定の件数を、合否にも警戒の条件にも使わない」と規約に書く
- 理由: 0 件を赤旗とする規格は見つからない(E0)。正当な 0 件と区別できず、降ろさずに残す誘因になる。外部の型は前提条件(期待値との照合・陽性対照・参照一覧との突合)で、本標準では網羅の側を `pending` の件数で示す
- 0 件でも台帳の「降りていない規定」の節と件数の行を出す(`check-impl.mjs` L209 は 0 件で節ごと消える。品質保証の発見)
- 検査スクリプト自身の陽性対照(既知の違反を入れて落ちることの試験)を置く

### I-6 限界の書き直し(全委員一致)

- 「限界」節の L94「網羅性を機械的に確かめる手段は現時点でありません」は、手続を入れると半分偽になる。機械が確かめること(節の登録の有無、鍵の実在、識別子の実在、除外とマークの併存)と確かめないこと(節の中の網羅、`marked` の判断の正しさ、節の中身の変更)を並べて書く
- 「台帳の件数は網羅の証明ではない。降りていない規定 0 件・未棚卸し 0 件のどちらも、規定がすべて降りたことを示さない」を規約・台帳の定型文に置く(ADR-0041 決定1 を本標準自身の台帳にも当てる: 擁護)
- ADR-0076 に記録する
