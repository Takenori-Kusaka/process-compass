## 5. 決定どおりにできなかった箇所、決定に明記が無く帰結として書いたもの

### 5.1 節の単位を「最下位の節」より広く取った

I-1 は「各頁の最下位の節」と書く。実装は「見出しと、次の見出し(どの階層でも)までの本文。本文の無い見出しは数えない」とした。下位の見出しを持つ親の見出しでも、直下に本文があれば節に数える。最初の見出しより前の本文は「(冒頭)」の節にした。親の見出しの直下の導入文にも規範が置かれており(例: 5.6、5.8.4 の直上の文)、最下位の節だけを数えると、これらが母集団から漏れるため。母集団は裁定より広い側にずれる(狭める向きの逸脱は無い)。規約の「母集団と単位」はこの定義で書いた。

### 5.2 基準線のラチェットの機械の範囲(取り下げた)

当初は「基準線の中の入れ替えは機械では止まらない」を限界として開示した。突合 X-1 で、入れ替えの普通の場合が改名で、裁定 I-4 が塞ぐと決めた経路そのものだと指摘され、議長の裁定(decision.md 8 章)で取り下げた。基準線を要約で凍結して直した(7 章)。

### 5.3 E.5 順1 の追跡を登録簿に書いていない

### 7.1 判断が要った箇所

- **I-7 の前提の誤り(X-12)**: 裁定 I-7 は IMPL-0160(目的の限定)を `adoption-trial`・`delivered` とした。準拠テンプレートが持つのは「導入前の検証のコマンドが人ごとの率を出さない」ことだけで、用途の限定を採用者・担い手へ伝える文はコードの注記にしか無かった。裁定の前提(テンプレートが目的の限定を持つ)は誤りだった
- **X-11 の `location` を `marked` にも許した**: 裁定は「列挙した識別子はすべて節の中」と「他の節で追跡される節は `elsewhere`」を定める。節の中にマークがあり、規定の一部だけを他の節で追う節(例: 5.6、5.7.1、3.11.4)は、どちらにも当たらない。識別子を挙げずに節の鍵を `location` に挙げる形にした。所在の節の実在は検査する。所在の節のマークが規定を本当に追っているかは確かめない(規約の限界の表に足した)
- **X-11 で挙げた識別子を落とした**: 節の外の識別子を `ids` から外したため、登録簿の記述は「節の中のマーク + 所在」に変わった。外した識別子は所在の節の登録に挙がっている
- **X-2 の比較の基点の既定**: 現在の `origin/main` には登録簿が無いため、手元と CI の最初の実行では「比べなかった」と出る。基点に登録簿が入った後の PR から比較が効く。凍結した基準線には本 Issue で判断した 86 節が入っていないため、それらを戻すことは基点が無くても基準線の側で落ちる
- **X-7 の CI の push の起動**: 裁定は「`npm run check` を実行する形に改める」とだけ書く。CLAUDE.md の「ソロ期は main へ直接 push」では PR の起動だけだと検査が走らないため、main への push でも起動するようにした。CLAUDE.md の記述は変えていない(「PR では CI が同じチェックを実行」は、改めた CI で事実になった)
