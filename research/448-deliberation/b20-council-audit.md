## 2. IMPL-0498 層の合わさりの承認の数え方(#355)

**結論: 修正して賛成**。式を機械に入れること自体は決定可能だが、「祖先を読めない場合は未確認と表示する」の扱いが監査上の穴になる。

### 監査で指摘する点

1. **未確認の向き**。祖先判定は `git` の履歴が要る。浅い取得・履歴の欠けで読めないときに、Y の承認を**確認ありに数えたまま未確認と表示する**なら、浅い取得にするだけで検査を無効にできる。**未確認のときは「確認ありに数えない」(止まる側)か、少なくとも「確認ありに数えるが欠落ではなく注意」を条文で選ぶ**。受付は後者に見える。cl-judgment は浅い取得を欠落にする先例を持つ(`recordPoint` の `shallow`)ので、**そろえるなら欠落**
2. **現行の検出は合否に使わない**(`aggregate-evidence.mjs` 854 行「検出は合否・出荷の失敗に使いません」)。0498 の式は、この検出の仕様の変更になる。保証の開示の項目の文言(6061 行)も変えるべきで、変えないと「合否に使わない」と書いたまま数え方が変わり、**表示と実態が食い違う**
3. **入力の信頼**。式は承認レビューの写しと PR の写し(`merge_commit_sha`・`head_sha`・`base.ref`)に依る。写しは `record-copy.yml` が作る記録で、書き込み権限者の改ざんは防がない(履歴には残る)。この限界は IMPL-0522 の note と同じ型で開示できる
4. **rebase の見逃し**(355 の F5)。外部の調査(GitHub Docs)は、差分が変わらない rebase の後も承認が維持される仕様を示す。つまり GitHub 側はこれを「承認の維持」と見る。**式が見逃すのは、中間の層を取り込んだ後に Y を rebase した場合**で、承認の対象のコミットが変わっているのに数えてしまう。SLSA の「最終版に承認が有効」の規範とは食い違いうる。開示で閉じるのは妥当だが、開示は根拠水準マーク(暫定)と保証の開示の項目の双方に書くこと。マークだけでは読み手に届かない
5. **GitHub 標準のスタックでは誤検知しない**ことの確認が必要である。外部の調査では各層が基底の規則で評価される。式が標準のスタックで偽陽性を出すと、採用者が検査を外す動機になる。試験は、標準のスタック(下から順に取り込む)・手動のスタック・squash・rebase の4場面の対で固定すること(受付の F5 は使い捨てリポジトリで確かめた【記録】。実装の段で再現すること)

### 必要な証跡

- 4場面 × (数える / 数えない / 未確認) の対の試験。浅い取得の場面を含める
- 保証の開示の項目の文言の改訂
- 暫定マーク(rebase の見逃し・写しの改ざんを防がないこと)

### 採らない案

- `base.ref` だけで数えから外す(標準のスタックと区別できない。note のとおり)
- 祖先を読めないときに黙って数える(浅い取得で無効化できる)
- 層ごとの承認の有無の検査を GitHub 側の設定に任せ、本標準は数えない(外部調査が示す可能性。ただし ship-evidence の verify が必須でない以上、設定の正しさを本標準が確かめる手段が無い。採らない)

## 3. IMPL-0990 G-3 の表と機械で閉じない検査(#355)

**結論: 受付の案(案 C)に賛成**。ただし表の改め方に条件を付ける。

### 監査で指摘する点

1. 【読】現状は表示と実態の食い違いそのものである。`gate-criteria.md` の表は「前の判断記録と記述が一致している: 検査する」と約束するが、`check-decisions.mjs` 24 行は検査しないと自ら書く。**案 A・B いずれも、定義が標準に無いので、失敗にしても所見にしても、何を一致と読むか(語の一致か意味か)を決められない**。全部を置き換える記録は正当に同じ影響を書くので、一致を失敗にすると正しい記録を落とす(偽陽性)
2. 案 C は「検査をやめる」ことなので、**統制が消える**。消えた分を黙って消さず、残る統制を条文に書くこと。残るのは (a) 判定者が判定のときに読む (b) その旨を判定記録のどこに残すか。**判定者が読んだ証跡が無いと、「判定する」は実態のない約束になる**(1010 の読まれない散文と同型)。最低限、判定記録に「前の記録との突合: 実施 / 対象なし」の1行を残す案を勧める。ただしこれを機械で検査する(空欄を欠落にする)のは決定可能な条件なので許容できる。意味の判定は課さない
3. 表の他の行(「検査する」と書かれた4行・置き換えの両側の参照)は実装済みである。**同じ表に「検査する」が残る行が、本当に1行ずつ test と対応しているか**を台帳で確かめること。今回の差分で3行目までは対応を【読】で確かめた(IMPL-0132・0131)

### 必要な証跡

- 表の改訂(機械の列「しない」・人の列「判定する」)と、マーク IMPL-0990 を manual の delivered へ
- 判定記録の1行(突合の実施の記録)を足す場合は、様式と欄の登録(`template-fields.yaml`)

### 採らない案

- 一致の失敗化(定義と閾値の根拠が無い。外部の調査も、閾値は候補の絞り込み用で合否には使わない傾向を示す)

## 5. IMPL-1007・0925・0927・0934・0759 安全の記録の検査(#448)

2. **欠落と未確認の区別**。記録のファイル(`docs/safety-risk-assessment.md`)が無い、節が無い、D-0 が読めないときは、**適用なら欠落**、適用かどうかを判定できないなら **適用とみなす(止まる側)**とする。未確認で通さない
3. **基準7 の `machine: 'not-checked'` を変える表示**。現行の集約は「基準7: 機械では確かめていない」と出す(5433 行)。検査を足した後は「記載の欠落の検査のみ。内容は確かめていない」と書く必要がある。**文言を変えずに結果だけ出すと、「安全適合性の検証記録は機械で確認済み」と読まれる**
4. **重複**。IMPL-0761(#445)は「CL2 以上の安全適合性の検証記録を G-7 の判定基準にする」の降ろしで、1007 と範囲が重なる【読】。どちらが「記録の有無」を、どちらが「欄の検査」を持つかを決め、二重の実装と食い違う文言を避けること。受付は触れていない
5. **標準側との語の整合**。受付の 0925 の語彙「実行前の挿入」は、F.7 の本文(「試験台の実機・模擬環境・専門部門の設備の別と、その識別」)に無い。標準に無い語を機械が受け入れる値に含めると、テンプレートが標準を超える。語を足すなら標準側(F.7)に先に書くこと。F.7 の表は6行、09 の様式は10行(細分)で、受付の「6項目の有無」は F.7 の6行に対応するのか、09 の細分に対応するのかを明記すること
6. **IMPL-0925 は E0**。F.5 の禁止そのものが規格に先例の無い本標準独自の規定で、外部の調査も「本番への挿入を禁じる条文は読めていない」。機械の検査が通ることを「禁止を守った」と読ませないこと。F.5 は第7章の例外承認の対象外でもあるので、**例外で通す抜け道は無い**(ここは強い)

### 5.1 IMPL-1007(項目の欠落・空欄)

- **賛成**。存在・空欄・様式の初期の文のままは決定可能。規格 7.9 の「文書化」と整合する
- 指摘: 空欄の判定に「—」「-」「<…>」「N/A」「なし」が入るか。G-3 の検査(`check-decisions.mjs`)は「不明」「TBD」を通す設計である。**安全の記録で「TBD」が通ると、書いていないのと同じ**。G-3 の先例にそろえず、安全の記録は「TBD」「不明」「後日」「未定」も空欄に数えること。これは新しい義務ではなく、決定可能な語の一致である

### 5.2 IMPL-0925(挿入した環境)

- 受付の案: 列の値が「試験台の実機・模擬環境・専門部門の設備・実行前の挿入」で始まる語に限る
- すり抜け経路: (a) 本番の設備に「試験台の実機」と書く。語頭の一致だけでは嘘を防げない(受付も開示している) (b) 語頭の語の後に識別(設備の名前・番号)が無くても通る。**F.7 は「その識別」を求める。語頭の語の後に空でない識別を要求すること**。これは存在の検査である (c) 全行に「実行前の挿入」と書けば、実行時の挿入を隠せる。「実行前の挿入」は、その試験項目が実行時の挿入を要しない場合に限る旨を様式の注に書くこと(manual)
- 必要な証跡: 環境の識別と、独立した評価者が環境を確かめた記録(F.7 の「独立した評価」の欄で足りる。評価者が本番でないことを確認したかを「評価の結論」に書く旨を様式の注へ)。機械で閉じないこと(実際に本番でないこと)は note と EV-0296 に書く
- 採らない: 環境の実在を機械で確かめる(閉じない)/ 本番でないことを機械が確認したと表示する

### 5.3 IMPL-0927(項目2 の省略)

- 受付の案: 項目2 の結果が空欄、または「省略・該当なし・未実施」で始まれば欠落
- すり抜け経路: 禁止語リスト(黒名簿)方式のため、「対象外」「N/A」「実施せず」「別途」「後日」「-」「なし」で通る。**語の一覧は閉じない**。ただし機械が確かめる範囲はここまでと割り切るなら、**開示を明示**:「項目2 が埋まっているだけで、試験をしたことは示さない」
- 改善案: 黒名簿を広げる(上の語を含める)だけでなく、**実際の結果を示す形を要求する**。結果の欄に「期待との一致(一致 / 不一致)」の選択肢を持たせ、その語頭の一致を要求する形にすれば、白名簿方式で閉じる(語の一致で閉じる決定可能な条件)。様式の列が現状「結果と期待との一致」なので、この列を「一致 / 不一致 / 未実施」の語頭に限る形が素直である。未実施は欠落。**黒名簿より白名簿を勧める**
- 規格の先例は「項目ごとの省略禁止」を名指ししていない(外部の調査)。個別項目の名指しは本標準独自で、E0 のまま開示する

### 5.4 IMPL-0934(HR の不採用に理由が無い記録)

- 受付の案: 手法の表(手法・推奨度・適用・しない理由)を足し、HR で不適用かつ理由が空の行を欠落に数える。推奨度は記入者が書く
- **最大のすり抜け経路**。推奨度を記入者が書くので、**HR の行を「R」と書き換えれば検査をすり抜ける**。HR の行を表から外しても通る(受付は「漏れなく書いたかは manual」と開示)。機械の検査は「記入者が HR と書いた行」の整合しか見ないので、**検査が通っても、規格の HR を守った証拠にならない**
- 証跡として最低限足せるもの(いずれも存在の検査で足りる): (a) 各行に「出典(規格・版・表番号・行)」の欄を置き、空欄を欠落にする。監査人は出典の表と行ごとに突合できる (b) 表の末尾に「規格の HR 行の総数」を記入者に書かせ、表の HR 行の数と比べる(欠けた行を検出する。数え間違いと嘘は防げないが、漏れは減る) (c) 独立した評価の欄に「手法の表を規格の表と突合した」旨を要求する(manual)
- 外部の調査: 規格(61508 の凡例)は「理由の詳述」を求めており、この方向は規格の求める証跡の形に合う。推奨度を記入者に書かせる点は、F.4 が例で規格の表が正だからという理由で妥当
- 採らない: F.4 の HR の一覧を機械の正本にする(受付に同意)

### 5.5 IMPL-0759(構成要素ごとの判定と最大の区分)

- 受付の案: 節16 に構成要素の表(構成要素・区分・最悪の帰結)を足し、最大の区分と「判定した区分」の一致を `cl-judgment.mjs` が確かめる
- **一致の向きが問題**。「一致」を等号にすると、判定した区分が表の最大より**高い**(安全側)記録を落とす。cl-judgment は既に「構成が判定より高い向き」を注意にとどめる設計(コメント 273〜275 行)。**判定 < 表の最大 → 欠落(止める)、判定 > 表の最大 → 注意(引き上げた根拠を書く)** とし、既存の向きにそろえる
- すり抜け経路: 構成要素の列挙を絞る・個々の区分を低く書くことは機械で閉じない(受付が manual と開示)。**構成要素が1行だけの表**でも通る。最低でも行数が0なら欠落、1行なら「単一の構成要素と判断した根拠」を要求する、などは存在の検査として許容できる
- 区分の語の読み方(CL0〜CL3 のどれか1つとして読める)は既存の `classOf` を使うこと。新しい語彙を足さない
- 順序: 検査は G-1 の前に失敗する。`check-d0` の失敗の文面に、判定を下げた記録は「引き下げの根拠」を先に書く既存の手順(cl-judgment 276 行)へ導くこと
