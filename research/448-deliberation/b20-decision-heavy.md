## 2. IMPL-0738 未達のまま出荷が止まらない穴

### 裁定

CL1 以上の案件と規制業の案件は、**未達の種類を問わず**、集約の記載の欠落に数える。解く道は未達の解消だけとする。CL0 で規制業でない案件は、現行のとおり開示と G-8 の受容で出荷できる。

### 理由

1. **条文の表は未達の種類で分けていない**。`tailoring-guide.md` 115〜119 行の表の見出しは「未達のまま出荷する対象」で、行は案件の属性で分かれる
2. **人員由来に限る読みは、他の条文と合わない**。1086 行(判定の確認の未達)と 1135 行(独立した安全性の評価の未達)が同じ表を引く。ADR-0088・0113 も同じである。表が G-6 の人員不足だけの規定なら、これらの引用が成り立たない
3. **永久に止まる恐れは実行で否定された**(P1)。止まるのは G-3 だけで、典型の初期状態では出ない。解消は `/process-change` のスタックの確定 1 回で、人を増やす必要が無い
4. **例外承認では解けない**。7.3 は「構成の条件」を対象にせず(`exception-escalation.md` 60 行)、「例外承認は未達を解かない」と定める(`tailoring-guide.md` 1136 行)

## 3. IMPL-0498 層の合わさりの承認の数え方

### 裁定

機械で**確認ありに数えない**。式は次のとおりとする。

- X: 基底が既定ブランチ以外の写しで、X 自身に有効な承認が無いもの
- Y: 既定ブランチへ入った PR
- X の `merge_commit_sha` が Y の `head_sha` の祖先なら、Y を確認ありに数えない

読めないときの倒し方は**数えない側**とする。

| 状態 | 扱い |
| --- | --- |
| 祖先である | 数えない(理由 `stackedLayer`) |
| Y の head があり、浅い取得でなく、祖先でない(X の版が無い場合を含む) | 数える |
| 浅い取得、または Y の head を取得できない | **数えない**(理由 `stackedUnconfirmed`)。件数を開示に出す |

数えなかった結果は、既存の G-7 基準5 の表(`exceptionNeeded`)がそのまま扱う。新しい停止を足さない。例外承認の行が対応づけば欠落にならない。

### 理由

1. **条文は「数えない」と定める**(IMPL-0250)。候補の提示だけでは、機械が規定と逆に数え続ける(#359 の裁定 1-3)
2. **現場の懸念の場面には当たらない**(P6)。下の層を既定へ入れてから上の層を rebase する通常の運用では、X の基底が既定ブランチなので候補に入らない。X に承認があれば数える
3. **未確認を数える側に倒すと、浅い取得で検査を無効にできる**。判定が要るのは承認の無い X があるときだけなので、数えない側へ倒しても影響は小さい。IMPL-0241 の先例(未確認を欠落にしない)は全変更に掛かる検査の判断で、この場面に当たらない
4. **ブランチを消す運用では、取得の手順を足さないと式が動かない**(P5)。受付の F5 はこの場面を試していない

### 採らない案

- 候補の提示にとどめる(現場): 理由 1
- 未確認を数える側に倒す(起案・規格): 理由 3
- X の承認の有無を条件から外す(弁護): 層ごとに正当に承認した積み重ねを落とす。判定は既存の `independentConfirmation` を X の写しへ当てるだけで、承認の有効性を追う処理を新設しない
- patch-id などの近似で rebase の見逃しを塞ぐ: 決定可能でなく、偽陽性が出る
- `base.ref` だけで数えから外す: 標準のスタックと区別できない

### 変更後

`state=delivered check=machine test=template/scripts/gate/test-aggregate-records.mjs`。note に見逃しと入力の限界を書く。

### 実装の指示

1. `aggregate-evidence.mjs` に `stackedLayerCheck({ copies, prs, git })` を置く。候補の X は出荷の範囲に限らず、読めるすべての写しから、Y のマージより前のものを取る
2. 承認の無い X が 1 件でもあるときだけ、Y ごとに `git fetch --no-tags origin refs/pull/<Y>/head` を実行する
3. `independent.counted` を偽にし、`NOT_COUNTED_CODE` に 2 つの理由を足す
4. `OFF_DEFAULT_MERGE_LIMIT_TEXT`(854 行)と開示の行(6061 行)の「合否に使わない」は、検出の一覧の扱いに限ることが読めるように改める。同じ行に、数えなかった件数、未確認の件数、見逃す場面を出す
5. verify ジョブは同じ集約を再実行するので、同じ取得で同じ結果になることを確かめる

試験項目の 7 行すべてについて、結果の欄は「一致」「不一致」で始める。項目を実施しない場合は `例外承認: <行の ID>` と書く。ID は技術負債台帳の区分「例外」の、失効していない行に限る。

### 理由と対立の決着

- **「該当なし(時間窓なし)」は通さない**。F.5 は「項目2を省いてはなりません」と定め、単純な監視タイマについては「その旨と診断能力の限界を記録します」と定める。単純な監視でも試験をして、早い応答を通すという結果を書くのが条文の形である。よって規格委員の懸念は「不一致(時間窓なし。早い応答を通す)」で満たされ、条文との衝突は無い
- 監査の白名簿を採る。黒名簿は言い換えで抜けられる
- 監視タイマを持たない構成: 新しい免除を作らず、第7章の例外承認で受ける(方針の 2、弁護の案)。基準7 は 7.3 の対象で、7.4 の禁止の対象でない
- 7 行に同じ形を当てる: F.7 は「試験項目ごとの挙動と、期待との一致」を項目を限らず求める。項目2 だけを検査すると、他の項目で「省略」が通る

「不一致」は欠落に数えない。結果の受け入れは人の判定である。

### 採らない案

- 監視タイマが無い旨で項目2 を免除する(現場): 条文に無い免除の新設になる
- 空欄だけを欠落にする(弁護): 「省略」と書けば通り、「省いてはならない」を閉じない
- 黒名簿を広げる: 語の一覧が閉じない

`state=delivered check=machine test=template/scripts/gate/test-safety-record.mjs`。note に「結果の欄の形を検査する。試験を実際に行ったことは機械で閉じない」と書く。

## 11. IMPL-0934 HR の不採用に理由が無い記録

| 条件 | 判定 |
| --- | --- |

| 推奨度・出典・適用のいずれかが空欄 | 欠落 |
| 適用が「適用」「しない」のどちらでもない | 欠落 |
| 推奨度が HR で始まり、適用が「しない」で、理由が空欄 | 欠落 |

出力に「HR の行 n 件・うち不適用 m 件(推奨度は記入者の申告)」を出す。

### 自己記入のすり抜け

推奨度を HR から R へ書き換えること、HR の行を表から外すことは、**機械で閉じない**。次で扱う。

- 出典の欄で、行ごとに規格の表へ突き合わせられる証跡を残す(存在の検査)
- 突き合わせは独立した評価者が行う(manual)。根拠水準マークで開示する

### 規格の表の転載

**標準にもテンプレートにも、規格の表を転載しない**。様式は空の行だけを配り、規格の表の内容を持たない。出典の欄は番号だけを書かせる。F.4 の表は「例」のまま機械の正本にしない。他の記号体系の規格は、記入者が `HR(原記号: X)` と書く。記号の対応を本標準で定めない。

### 採らない案

- F.4 の HR の一覧を機械の正本にする: F.4 は例で、規格の表が正である
- 規格の HR の総数を書かせて行数と比べる(監査): 総数も自己申告で、閉じない
- 推奨度の値域を規格ごとに検査する: 規格の表を持つことになる

## 12. IMPL-0759 構成要素の最大の区分

### 裁定

| 論点 | 裁定 |
| --- | --- |
| 適用の範囲 | **全 CL に求める**。1 行で足りる |
| 判定 < 表の最大 | 記録の不備(G-1 の前は失敗、以後は欠落) |
| 判定 > 表の最大 | 注意(止めない) |
| 表が無い・行が 0 件・区分を読めない | 記録の不備 |
| 区分の列 | **低減の後の区分**を書く |

### 理由

1. 範囲を CL1 以上や Q1「はい」へ限ると、**低く判定した案件ほど検査を受けない**。この規定が塞ぐのは過小な判定である
2. 条文(1049 行)は CL を限定しない。表10 は「CL0 を含むすべての区分で必須」で、最悪の帰結は既に構成要素ごとに書く定めである。増えるのは書き方の形で、1 行で足りるので弁護の負担の懸念も満たす
3. 高い側を注意にするのは、`cl-judgment.mjs` 273〜280 行の既存の向きと同じである
4. 低減の後の区分とするのは、「設計によって区分を下げる」経路で正当に下げた案件を落とさないためである

### 採らない案

- CL1 以上か Q1「はい」に限る(弁護・現場): 理由 1
- 等号の一致: 安全側の判定を落とす
- 1 行の表に根拠を要求する(監査): 文の意味の判定になる
- 最悪の帰結の文から区分を導く: 機械で閉じない
