## 1. IMPL-0738(未達のまま出荷しない)

**結論: 修正。受付の「機。CL1 以上か規制業で `unmet` があれば欠落にする」には反対する。**

### 1.1 整合の確認

- 条文の所在は `tailoring-guide.md` の再実行の節の表(L112〜119)。表の直前の文は「人の離脱で成立しなくなった統制」「体制の縮小を緩める向きの決定として扱わない」を扱う。表の 2 行目は「出荷しない。**軸E「人員が足りない場合」の選択肢による**」と、手段を限定する
- 軸E「人員が足りない場合」(L1246〜)は、運用中に 1〜2名になった構成を「**出荷できない状態**として表示する」と定め、これは `shipBlocked` と IMPL-0769(delivered)が既に実装している。IMPL-0450(安全重要度の判定の確認の未達)も既に出荷を止める
- したがって条文の「出荷しない」は、読みやすい範囲では**体制の縮小に起因する未達**に掛かる。受付の F4 の探針は、CL1・3〜9名・スタック未確定・S1 の構成で `unmet=[g3]` を出した。**この構成の未達は人員由来ではない**。F4 は「人員由来でない未達が止まらない」ことを示したのであって、「条文の出荷しないに穴がある」ことは示していない

### 1.2 矛盾とどちらが誤りか

- 条文を CL1 以上の未達すべてに広げると、同じ表の 3 行目(上記以外は開示して G-8 で受容を記名)と、ADR-0028(未達と省略の区別)の「未達は表示して続ける」の型に食い違いが出る。広げた後の R1 の行(7.3 の例外承認)との重なりも決まらない(CL1 以上の R1 は、例外承認があっても止まるのか)
- どちらが誤りか: **受付の読みが範囲を広げている**。マークの note も「未達の種類を問わず CL1 以上・規制業の未達のまま出荷を止める検査は読めていない」と書くが、これは「検査が無い」ことを述べるだけで、条文がその範囲を求めるとは述べていない。note の文を、条文の求めの範囲と取り違えてはならない
- 外部調査は「止める条件をリスクの水準で変える先例はある。ただし規格の条文として安全の水準が X 以上なら未達の出荷を禁じるものは無い」「CL で一括して止める案は先例の粒度(欠陥ごとのリスク評価)より荒い」と述べる。止める対象を「未達のゲート」か「リスクを評価していない未達」かは外部からは決まらない、とも述べている。これを根拠に広げるのは、確かめられなかった点を根拠に断定することになる

### 1.3 案

- 賛成の部分: 人員由来の未達と IMPL-0450 は既に止まる。条文が求める範囲は、これで届いている。**試験で固定する**(違反と適合の対)ことで、マークは delivered / machine にできる
- 反対の部分: 人員由来でない未達(スタック未確定など)を CL1 以上で一律に止める処理は、本束で入れない。入れるなら、(a) 止める未達の種類を列挙する、(b) 例外承認(7.3)との関係を決める、(c) 外部の先例(欠陥ごとの評価)との粒度の差を開示する、の 3 つを備えた別の審議にする。本束では**採らないと決めた**旨を ADR-0218 に書く(「書かれていない」と「課さない」を区別するため)
- 第7章の例外承認で受けられるか(方針の軸 2): 人員由来でない未達を CL1 以上で出荷する構成は、受容の記名(G-8)で受ける現行の型で足りる。珍しい構成のために新しい禁止を足す理由は示されていない
- 根拠水準マーク: 新しい禁止を足さない案なら不要。広げる案を会議体が採るなら E0(外部の先例なし)で開示する
- 採らない案: (1) 受付の案(未達すべてを欠落) 理由: 条文の範囲を超える。(2) 「CL で一括」でなく「リスク未評価の未達」を止める案 理由: 評価の定義が標準に無く、機械で閉じない

## 2. IMPL-0498(層の合わさりの承認)

**結論: 賛成(条件つき)。**

### 2.1 整合の確認

- IMPL-0250(delivered / manual)は「層ごとの承認が無いまま合わさった差分への 1 件の承認を層ごとの G-6 の確認に数えない」「GitHub 標準のスタックは当たらない」と定め、IMPL-0498 は集約側の機械の実装である。方向は同じで矛盾しない
- 外部調査: SLSA v1.2 は承認を「最終版」「特定の文脈」に結びつけ、別の文脈へ移した内容に改めてレビューを求める。IMPL-0498 の趣旨はこれと同型。GitHub の公式文書は、スタックの各層を基底の規則で評価すると書く。ここまでは一次で確かめられている
- 外部調査が確かめていない点: 強制 push・retarget・中間の層の取り込み後の承認の扱い(H8)。さらに、スタック型 PR の公開状態は、変更履歴(一般提供)と gh-stack の頁(private preview)で食い違う

### 2.2 指摘

1. **「式が `base.ref` だけでは区別できない問題を解く」は、実機の探針 F5 の 4 場面だけが根拠である**。F5 自身が rebase の見逃しを示している。断定せず、「手動のスタックと squash を検出し、中間の層の取り込み後の rebase は見逃す」と書く。これは根拠水準マークで開示する
2. 外部調査の考察は「GitHub 側の必須レビューが正しければ、重ねて数える必要は薄い」と述べる。集約が数える承認は、事後の検出である。予防は IMPL-0248・0254(中間の層へのマージの拒否)が担う。**事後の検出で止める強さを、予防の側の設定が正しい前提で測っていることを ADR-0218 に書く**
3. 「祖先を読めない場合は未確認と表示」は IMPL-0241 の型と揃っていて妥当。未確認を欠落にしないなら、未確認の件数を保証の開示へ必ず出すことを条件にする(出さないと、見逃しと未確認の区別が読み手に届かない)
4. AI のレビューを承認の数に入れるかは、規格の条文では決まらない(外部調査 H10)。本件では範囲外だが、「人間の承認」を前提にした式であることを note に残す

### 2.3 根拠水準マークと採らない案

- マーク: 要。「rebase の見逃し」と「GitHub のスタックの公開状態と挙動(H8)が未確認」を `:::caution[暫定 EV-NNNN / 見直し 2027-05]` で開示
- 採らない案: (1) `base.ref` だけで数えから外す 理由: GitHub 標準のスタックと区別できず、正当な承認を落とす。(2) 取り込みを機械で拒む 理由: IMPL-0248・0254 の担当。(3) 見逃しを塞ぐ全層の再検証 理由: 決定可能でない

## 4. IMPL-0919・0766(安全関連部の自律レベル)

## 5. U2 安全の記録の検査(1007・0925・0927・0934・0759)

2. 0498: 「式が base.ref の問題を解く」は、H8(強制 push・retarget・取り込み後の承認)が未確認のまま。GitHub のスタックの公開状態も食い違う
3. 0990: 案 C が「実務の型と整合」は、ADR と実装の一致の検査を扱う研究を調べていない(H11)
4. 0919・0925・0927・1007: 規格の逐語は未確認(EV-0296・EV-0316)。ADR では「規格が求める」でなく「本標準が足す」と書く
5. 外部調査の独立性の水準(I0〜I3 と ASIL の対応)は、本件に使わない。使うなら出典を確かめてから
