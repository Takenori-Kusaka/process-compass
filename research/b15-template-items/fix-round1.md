## F-4 IMPL-0987 の強制層の変更の承認(impl-02.md 順 6 の続き)

- 所有者の承認(2026-11-18): `record-copy.yml` の権限の追加(`actions: read`)は強制層の変更である。所有者が AI維持管理者として承認した(所有者の回答 2026-11-18、triage §4 の 23・24)
- 承認者の名: AI の名義は書かない。名を書く欄は作っていない。IMPL-0987 の note に「承認者の名は所有者が記す」と残した。所有者が記録に名を書く
- 順序の食い違い: 裁定の表(intake §2 の順 6)は「§4 の実機の確認の後に delivered」、§4 は「集約の検出を先に入れ、`workflow_dispatch` の削除だけ実機の後」と書いていた。実装は §4 に合わせた(集約の検出を先に入れ delivered とし、削除は実機の後に回し、EV-0325 で開示した)。理由は、採用者が契機を足し戻せるため、集約での検出を実機の結果に依らず外せないこと(intake の 68 行目)。表の「delivered は実機の後」は、§4 の読みに揃えて「集約の検出が delivered、削除の判断が実機の後」と読む
- IMPL-0987 の note(`gate-criteria.md`)に、承認を書き足した

## 直さない理由

- F-6(pull_request_target の照会): いまの gate-g5.yml は pull_request だけを使い、実害は無い。通過に数えない側へ倒れ、未確認と表示する。直すには、基底ブランチの先端ではなく PR の head を引く別の経路(PR の頭のコミットの列挙など)を設計する必要があり、意味が変わる。per_page=100 の頁送りも同じ。採用者が契機を変えたときの扱いを、契機の変更の検出(push-trigger の型)とあわせて決めるべきで、裁定の判断が要る
- F-7(集約の通しが Windows で読み飛ばされる): 試験の環境の制約であり、コードの欠陥ではない。WSL(node 26)で通過を確かめてある。push の後の CI の Linux で確かめる。直せない
- F-9(IMPL-0959 の「なし」の分岐): check=manual で表示との食い違いは無い。分岐を無くすか入力を作り込むかは、表示の仕様を変えることになり、裁定の判断が要る
- F-10(gates/G-1.md の語): B16(手引きの文書)の範囲で、intake は templates/09 だけを範囲とした。B16 で拾う
