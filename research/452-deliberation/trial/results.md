# #452 試行の測定と計画外の置き場の既定の一覧の実測の案(束 B34、2026-11-26)

## 0. 試行の条件と限界

- 場所: `pit-in-trial-node-tmp`(private、削除済み。#361 の node と兼ねる)。初期化の後の既定ブランチの第1親 15 コミットを測った(`452-measure.md`、台本は `measure452.mjs`)。
- 機能 3つ(F-001 CLI 引数、F-002 設定の読み込み、F-003 依存の追加)、タスク 9(F-001 3 / F-002 3 / F-003 2 + 計画の修正 1 PR)、計画の PR 3、うち 1 件は「計画と実装を同じ PR」(PR #9)、1 件は「計画の誤りを直す PR」(PR #14)。
- **限界(結論の強さに響く)**: (1) 実行役は測定の分類を知っていた(盲検でない。§3 の「知らされない担当」の要件を満たせなかった)。(2) 担い手が Claude Code のスキル(`/spec-write`・`/implement`)を介さず、実行役が計画・実装を直接書いた。計画の書き方は実運用の担い手より素朴な可能性がある。(3) 計画と実装の書き手が同じで、合成の小さなアプリ(src 数ファイル)。(4) 補助のフック(コミットしなかった書き込み)は置いていない。(5) `git fetch` の前後で U が変わる件(手元の `origin/<既定>` の古さ)は、実行役が毎回 pull したため観測していない。(6) G-2・G-4 の判定記録の records ブランチへの記録は行っていない。単一の試行であり、根拠の水準は E2 を超えない。

## 3. 規定の読みの欠け(新たに分かったこと)

- 計画と実装を同じ PR に入れると、既定ブランチの計画に無いため IMPL-0205 は `notInBase` を出し、範囲の判定は何も行わない(R1 でも R3 でも同じ)。「計画を先に既定ブランチへ入れる」運用でないと、要求事項3 の「既定ブランチへ入った実装計画」の和は空になる。
- 実装 PR が計画の「状態」の升を書き換える運用(テンプレートの様式が「Draft PR を作ったら着手にする」と求める)は、計画の PR でなく実装の PR で `specs/**` を触る。範囲を `specs/**` へ広げなければ、状態の更新が毎回外れる。
