## R-1 算出元

### 結論

1. `metrics.md:182` の「欠陥 Issue の『検出ゲート』欄(起票テンプレートで必須化)」は**事実と違う**〔確〕(`bug.yml` に欄が無い)。現状のまま公開を続けると、規格の読み手は「準拠テンプレートに欄がある」と読む。最初に直す
2. 算出元は**欠陥の台帳**(`docs/defect-ledger.md`)に置く。台帳は G-7 の基準2 の入力として既に必須で、出荷前と運用の Sev1・Sev2 の行がここへ集まる〔確〕。Issue の欄を正本にしない
3. 数える範囲を**「G-6 を通過してマージされた変更に、その後で見つかった欠陥」**に限る。PR の中で見つかって直った指摘は、この指標に数えない
   - 台帳に「検出の位置」を足す。値は「マージ後の検証(出荷前)/ 出荷判定(G-7)/ ステージ移行(SG)/ 運用」。既存の「検出の時点(出荷前 / 運用)」は委任の停止(`autonomy.mjs`)が読むので残し、その内訳として持つ
   - 運用の Sev1・Sev2 は、ポストモーテムで特定した**原因のゲート**(本来どこで止めるべきだったか)も台帳へ書く。C9 の崩れ「重大な欠陥の流出に原因ゲートの特定が無い」(`assurance-case.md:216`)はこの欄で観測できる
4. 指標の中身を「上流で捕まえた比率」から「G-6 を越えて残った欠陥が、どこで見つかったか」へ読み替える。H.7 の「下流での検出が増えれば、上流の確認が働いていない」は、**G-6 を越えた欠陥の件数と、そのうち運用で見つかった件数**で読める
5. 実装されるまでは、C4・C9・H.7・H.9 問5 から外さない。**外すと穴が見えなくなる**。その代わり「算出元の実装なし。未測定」と開示する(検出率の「未測定」と同じ扱い。ADR-0028 の未達の表示の考え方)

### 理由

- **PR の中の検出は記録が落ちる**。G-6 で見つかった欠陥の多くは同じ PR の中で直り、Issue にならない(内部 H7)。アジャイルの現場では、バグを記録せずに即修正するのが普通で、記録の義務化はアジリティを損なうという実務の指摘がある(外部 2. NTT データ)。分母の上流側が系統的に欠ける比率は、何を入れても信頼できない
- 上流の件数を記録させると、**記録の圧力そのものが水増しの経路になる**。修正が容易で本質的でない指摘を積んでレビュー実施の証拠を作る形骸化(外部 3.5 森崎)は、AI が指摘を量産できる今、人の手間なしに起きる
- G-6 の検出能力は、既に**欠陥注入の検出率**(5.6.2、C6)で、所在が注入箇所を指す指摘だけを数える規則つきで測っている(IMPL-0157、delivered)〔確〕。PR の中の検出を数える役目は、ここが持つ。同じことを実欠陥の自己申告で二重に測る必要はない
- マージ後に見つかった欠陥は、台帳の行・Issue・ポストモーテムのいずれかに必ず痕跡が残る。数え漏らしが起きにくい側だけを数える

### 体制ごとに回るか

| 体制 | 回るか |
| --- | --- |
| 1〜2名 | 回る。台帳は G-7 のために既に書く。足すのは「検出の位置」の1列で、行は年に数件〜数十件。PR の中の指摘を台帳へ書かせる案なら、ほぼ確実に書かれなくなる |
| 3〜9名 | 回る。出荷前の台帳の書き出しの段で、トリアージの担当が列を埋める。原因のゲートはポストモーテムの既存の項目から写す |
| 10名以上 | 回る。Issue の追跡道具から台帳を書き出す運用(`defect-ledger.md` 冒頭)で、列を道具の項目に対応させれば機械で埋まる。件数が多いので、比率の推移を読める |

### 譲れない点

- 「必須化」の記述を、事実と違うまま残さない
- 算出元の無い間も、観測から**黙って外さない**。「未測定」と表示し続ける
- PR の中で直った指摘を、この指標の分子にも分母にも入れない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `bug.yml` に「検出ゲート」を必須のドロップダウンで足す | `bug.yml` は利用者・外部の報告者も使う。報告者はゲートを知らず、必須にすると適当な値が入る。G-6 の検出は Issue にならないので、欄を足しても非対称(内部 H7)は解けない |
| G-6 で見つけた欠陥も、すべて Issue または台帳の行にさせる | 記録の手間が PR の件数に比例し、1〜2名では書かれず、10名以上では AI の指摘を写すだけの作業になる。記録の圧力が水増しの経路になる |
| 指標を附属書H の観測から外す | 穴が見えなくなる。H.7 の4つのうち1つを、代わりの手段なしに失う |
| 実装まで「暫定」として手で集計させる | `metrics.md` の手続3「実装前の指標を暫定として運用しない」に反する〔確〕 |

### 反論されうる点

- 「IPA の上流工程での不具合摘出比率から離れる」(#408 の規格の委員、`council-04-standards.md:201`)。答え: 離れる。ただし IPA の比率はレビュー記録票を書く文化を前提にした数え方で、PR の中で直る現場では分母が欠ける。比べられない値を同じ名で出すより、何を数えたかを明示して出すほうが信頼できる。IPA の比率との対応は EV で開示する
- 「G-6 の効き目を実欠陥で見られなくなる」。答え: 欠陥注入の検出率と、**G-6 を越えた欠陥の件数**の組で見る。G-6 が効かなくなれば後者が増える
- 「マージ後の AI の定期走査で大量に起票されると、結局ここが膨らむ」。答え: R-2 の確定の条件で塞ぐ

## R-2 数える母集団

### 結論

1. 集計に数える「欠陥」は、台帳の行のうち、**処分が「欠陥」(修復または置換を要する)で、確定した者の欄に人の氏名がある行**に限る
2. 台帳に次の列を足す
   - 起票の経路: 人(開発側)/ AI / 利用者 / 監視
   - 処分: 欠陥 / 欠陥でない / 重複 / 取り下げ / 未処分
   - 確定した者: 人の氏名。AI と bot の名義を書かない(`defect-ledger.md:34` の型、`assurance-case.md:646`)
3. **確定と起票の経路の両方を記録する**。区別しない案と、確定に限る案のどちらか一方ではない
   - 指標は確定した行だけで数える
   - 未処分の件数を、起票の経路別に**滞留として表示する**(`/pit`・出荷の集約)。目標値や警戒サインを持つ指標にはしない。「AI の指摘の件数」を指標にしない規定(`metrics.md:85`)とは衝突しない
4. 確定した者は、**原因の変更の作成を指示した者でもよい**。自分の変更に欠陥があると認めることは、自分に不利な方向の判断だからである。逆に、**自分が作成を指示した変更への報告を「欠陥でない」「取り下げ」と処分した行**は、台帳と保証の開示に「同一人物」と出す。3名以上の体制では、この処分は作成を指示した者以外が行う
5. **確定の条件を、指標以外の安全の仕組みへ広げない**
   - 委任の停止(`autonomy.mjs`)は、運用の Sev1・Sev2 の行を処分によらず数える(未処分でも止める)
   - G-7 の集約は、未処分の行を未解決と別に件数で出し、出荷判定者が見る。機械が出荷の可否を判定しない現行の原則(`defect-ledger.md`)のとおり
6. 語: 「人確定」(自律レベルの語、`human-ai-boundary.md:385`)を使わない。「欠陥の確定」「確定した者」を使う

### 理由

- 規格の語彙は既に、報告されたもの(anomaly)と、修復または置換を要する欠陥(defect)を分けている(外部 1.1・1.2)。DRE・DDP・フェーズ yield の単位も「欠陥」で、報告ではない(外部 2.)。未確定の報告を数える指標は、規格の言う指標と別物になる
- 業界の公表値は、どれも人の判断を真値にして AI の指摘の真偽を決めている(外部 3.2。Meta の JiT は weak catch と strong catch を人への問い合わせで分ける)。人の記名を条件にするのは、現場の実務と同じ形である
- **受理(適用)を確定と見なさない**。正しいが価値の低い指摘も適用される(外部 3.2 AutoCommenter)。適用を確定に数えると、好みの指摘で件数が増える
- 確定に限るだけだと、**AI の報告の滞留が見えなくなる**。curl の例のとおり、AI の起票が増えるとトリアージの工数を食う(外部 3.3)。滞留を表示すれば、その費用が見える。指標にしないのは、件数を下げる圧力が「起票させない」「まとめて却下する」へ向くため(`metrics.md:88` と同じ理屈)
- 不利な方向と有利な方向で扱いを分ける。**水増しの危険は「欠陥」と数えすぎる方向、隠蔽の危険は「欠陥でない」と処分する方向**にある。前者は確定の条件で、後者は同一人物の表示で塞ぐ。どちらにも同じ独立性を課すと、1〜2名で欠陥を確定できなくなる
- 確定の条件を委任の停止や G-7 へ持ち込むと、「確定しなければ止まらない・出荷を止めない」という逆の誘因が生まれる。集計の母集団を絞る規定は、集計の中だけで効かせる

### 体制ごとに回るか

| 体制 | 回るか |
| --- | --- |
| 1〜2名 | 回る。確定する人は本人しかいないが、欠陥と認める確定は本人でよい。「欠陥でない」の処分は同一人物と表示される(1〜2名の他の兼務の表示と同じ扱い)。AI の報告の滞留が見えるので、処理しきれない量を AI に起票させていることに気づける |
| 3〜9名 | 回る。週次のトリアージで処分を付ける。「欠陥でない」の処分を原因の変更の作成を指示した者以外が行うのは、レビュアの組み合わせで足りる |
| 10名以上 | 回るが、量が問題になる。AI の起票が多いと未処分が溜まる。滞留の表示で、トリアージの担当の増員か、AI の起票の絞り込みかを決める材料になる。処分の列は追跡道具の状態(close の理由)に対応させ、機械で台帳へ書き出す |

### 譲れない点

- 指標の母集団は、人が記名した「欠陥」の処分に限る。AI と bot の名義、承認の機能(2026-10 GA の Copilot の承認など、外部 3.4)を確定に数えない
- 未処分の件数を、起票の経路別に必ず表示する。確定に限ることで滞留を隠さない
- 確定の条件を、委任の停止と G-7 の未解決の件数に持ち込まない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 区別しない(起票数をそのまま数える) | AI の起票量が指標を直接動かす。上流の検出が増えたように見え、人の確認の劣化を隠す(#408 品質監査 `council-03-qa-audit.md:144`) |
| 起票の経路で分けて両方の値を出すだけで、確定を条件にしない | 人の起票にも重複・誤報がある。経路の区別は確定の代わりにならない。経路は自己申告で、AI が人のトークンで起票すれば人に見える |
| PR の採否の「採用」を欠陥の確定とみなす | 採否は PR のレビューの記録で、採った指摘が修復を要する欠陥とは限らない(受理と確定の混同)。R-1 の範囲では PR の中の指摘をそもそも数えない |
| 確定者を作成を指示した者以外に限る | 1〜2名で欠陥を確定できず、台帳が「未処分」で埋まる。欠陥と認める方向の判断に独立性は要らない |
| AI の報告はすべて人が再現してから確定する | 再現の手間が報告の量に比例する(curl では1件に3〜4名・数時間)。再現は確定の材料の1つにとどめ、要求しない。確定の記名で責任を負わせる |
| 未処分の件数を警戒サインつきの指標にする | 件数を下げる圧力が、起票の抑制と一括の却下へ向く。表示にとどめる |

### 反論されうる点

- 「記名だけで確定が成立すると、AI の報告に一括で記名する形骸化が起きる」(#408 起案 `council-01-drafter.md:165`)。答え: 完全には防げない。対策は2つ。確定した行の起票の経路の内訳を表示して、AI 由来の確定の急増を読めるようにすること。もう1つは、マージ後に限る範囲では一括の記名が**下流の件数を増やす向き**に働くこと。上流の見かけを良くする経路にならない。この効き方は実証が無いので EV で開示する
- 「起票の経路は自己申告で当てにならない」。答え: そのとおり。準拠テンプレートでは AI エージェントの起票に目印(ラベル)を付ける手順を降ろし(R-5)、それ以外は申告と記す。経路は指標の母集団を決める列ではなく、滞留と内訳の表示に使う列なので、誤りの影響は限られる

## R-3 工程の帰属

### 結論

- **最初に報告された時点の工程**(R-1 の「検出の位置」)に帰属させる。ODC で検出側の属性(activity・trigger)を起票の時点で付けるのと同じ考え方(外部 1.3)
- 確定した人のゲートには帰属させない。確定が遅れても、工程は動かない
- 「AI の層」は工程に置かない。AI が見つけたか人が見つけたかは、R-2 の起票の経路という**別の軸**で持つ
- 運用で見つかった欠陥は、検出の位置(運用)とは別に、ポストモーテムで特定した**原因のゲート**も持つ(R-1)。前者は「どこで見つかったか」、後者は「どこで止めるべきだったか」

### 理由

- 確定した人のゲートへ帰属させると、トリアージが遅いほど欠陥が下流へ移る。滞留が指標を悪化させ、それを避けるために確定を急がせる圧力、または確定の時点を書き換える誘因が生まれる
- AI の層を工程にすると、同じ変更が AI の層と G-6 の両方に現れ、工程の分布の意味が崩れる。AI の層は G-6 の中で働く検出の層(H.4)であって、ゲートではない〔確〕(`assurance-case.md:314`)
- 経路を別の軸にすれば、「マージ後に AI の定期走査で見つかった欠陥」と「利用者が報告した欠陥」を、同じ工程の中で分けて読める

### 体制ごとに回るか

| 体制 | 回るか |
| --- | --- |
| 1〜2名 | 回る。起票した時点で位置は決まる。後から考える必要がない |
| 3〜9名 | 回る。原因のゲートはポストモーテムの既存の項目 |
| 10名以上 | 回る。追跡道具の起票日時と、そのときの出荷の状態(出荷前か後か)から機械で埋められる |

### 譲れない点

- 帰属は起票の時点で固定し、確定の遅れで動かさない
- AI の層を工程の値にしない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 確定した人のゲートへ帰属 | トリアージの遅れが工程を下流へ動かす。確定を急がせる圧力になる |
| AI の層を独立の工程として数える | 層はゲートではない(H.4)。同じ欠陥が二重に現れる |
| 原因のゲートだけを持ち、検出の位置を持たない | 「どこで見つかったか」が無いと、出荷前の検証と運用のどちらで捕まえたかが読めない |

### 反論されうる点

- 「起票が遅れれば同じ問題が起票の側で起きる」。答え: 起きる。ただし起票の遅れは確定の遅れより短く、運用の事象は監視・報告の時刻で決まる。出荷前か後かの境は出荷の日時で機械が判定できる

## R-4 重大度の2つの定義

### 結論

- **本件で揃える**。「重大欠陥の流出」は Sev1・Sev2 の件数であり、定義が2つあるままでは母集団が決まらない。台帳は出荷前と運用の行を同じ「重大度」の列に入れる〔確〕
- **誤っているのは `incident-response.md` の側**。トリアージ基準(`gate-criteria.md`。規範の章)、台帳、`bug.yml` の3つは「Sev2 = 回避策がある」で一致している〔確〕。障害対応だけが「Sev2 = 回避策なし、Sev3 = 回避策あり」で、同じ記号を別の意味で使う
- ただし、障害対応の段階そのものを消してトリアージ基準へ統合しない。障害対応の段階は**初動の緊急度**を決める尺度で、「当番が単独で即断し、迷ったら高いほうに倒す」設計である。トリアージ基準は「文書化した回避策があるか」を確かめる尺度で、深夜の初動でそれを確かめさせるのは無理がある。**役目が違うので、記号を分ける**(例: 障害対応の段階を別の名前と記号にする。名称は起案に委ねる)
- 運用の事象を台帳へ書くときは、**事後検証の時点で、トリアージ基準の定義により重大度を付け直す**。付けた者は人の氏名で記名する(R-2 の確定した者と同じ人でよい)
- 判定者の食い違い: トリアージ基準の「AI を参加させてよい」は残す。ただし、台帳に記録する重大度は人が記名して確定する。AI の推定を判定に数えない H.4 と同じ型。ポストモーテムを書くかどうか(障害対応の段階)の判定は、現行どおり人が行う

### 理由

- 同じ「Sev2」が、出荷前の行では回避策あり、運用の行では回避策なしを指すと、流出の件数も、G-7 の未解決の件数も、委任の停止の対象も、行によって意味が変わる。数字としての信頼性が無い
- 障害対応と欠陥の重大度を別の尺度で持つのは、実務で普通の形である(インシデントの緊急度と、不具合の重大度を別に付ける)。問題は尺度が2つあることではなく、**記号が同じこと**
- 重大度は委任の停止と出荷の判定を直接動かす値である。AI の参加は材料の提示にとどめ、記録する値は人が負う

### 体制ごとに回るか

| 体制 | 回るか |
| --- | --- |
| 1〜2名 | 回る。当番も事後検証も本人。付け直しは台帳へ行を書く段で1回 |
| 3〜9名 | 回る。当番の即断と、事後検証での付け直しを別の人がしてよい |
| 10名以上 | 回る。障害管理の道具の緊急度と、欠陥追跡の道具の重大度を別の項目として持つ構成が、多くの道具で既にある |

### 譲れない点

- 台帳の重大度の列は、出荷前・運用を問わず、トリアージ基準の1つの定義で付ける
- 障害対応の段階と欠陥の重大度に、同じ記号を使わない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 障害対応の4段階へ統合する | Sev4(影響のない異常)は欠陥の重大度に要らない。トリアージマトリクス(ステージ×Sev1〜3)と G-7 の基準を作り直すことになり、規範の章を参考の頁に合わせる向きが逆 |
| トリアージ基準の3段階へ統合し、障害対応にも「文書化した回避策」の判定を求める | 初動の即断を妨げる。深夜の当番に回避策の文書の所在を確かめさせると、判定が遅れるか、低く倒れる |
| 本件では扱わず別 Issue へ送る | 流出の指標の母集団が決まらないまま R-2 の確定を決めても、値が揃わない(内部 6.2 の推) |
| 記録する重大度も AI の判定でよいとする | 委任の停止と出荷を動かす値を、人が負わない形になる。H.4 の型と合わない |

### 反論されうる点

- 「障害対応の段階の名前を変えると、ポストモーテムの要否(重大度1・2は必須)や初動期限の表を直す範囲が広い」。答え: 範囲の広さは採否の理由にしない。直さなければ、同じ記号の2つの意味が台帳へ流れ続ける

## R-5 記録と降ろし先

### 結論

1. **新しい ADR を起こす**(現行の最新は ADR-0101〔確〕)。決定は R-1〜R-4 の結論。採らない案は各論点の表をそのまま載せる
   - ADR-0092 決定7・選択肢(`adr/0092-...md:78,104`)が送った論点への答えとして、そこから辿れるようにする(採用済み ADR の本文は書き換えない)
2. 本文の改め
   - `metrics.md` の「欠陥の検出工程」「重大欠陥の流出」の行: 算出元を台帳へ。範囲(マージ後)、母集団(処分「欠陥」と記名)、帰属(最初の報告の時点)を書く。「Sev1/Sev2 ラベル」の前提を台帳の重大度の列へ改める
   - `assurance-case.md` の C4・C9・H.7・H.9 問5・EV-0062: 実装まで「未測定」と開示する。EV-0062 の差し替え条件の「G-7 以降で検出された欠陥の比率」を新しい定義へ合わせる
   - `incident-response.md`: 障害対応の段階の記号を改め、台帳へ書くときの付け直しを書く
   - `gate-criteria.md` 欠陥トリアージ基準: 台帳に記録する重大度は人が記名して確定する、と足す。欠陥の定義(修復または置換を要する不備)と処分の値をここへ置く
3. 実装マーク(IMPL)
   - 台帳の列の追加(検出の位置・原因のゲート・起票の経路・処分・確定した者) → `template/templates/defect-ledger.md`
   - 出荷の集約が、処分「欠陥」の行だけで検出の位置の分布を出し、未処分を経路別に出す → `aggregate-evidence.mjs`・`verification-trace.mjs`。委任の停止(`autonomy.mjs`)は処分によらず数えることを検査で確かめる
   - `bug.yml` に「見つけた経路」の**任意**のドロップダウン。必須にしない
   - AI エージェントが起票するときにラベルを付ける手順 → 準拠テンプレートの `CLAUDE.md`
   - 実装までは `state=undelivered` で表示し続ける
4. 根拠水準のマーク(EV)
   - マージ後に限る境界と、上流の比率から離れること(IPA の比率との対応が未検証)
   - 欠陥と認める確定を作成を指示した者に許し、「欠陥でない」の処分だけを同一人物と表示する非対称(効果の実証なし)
   - 件数が少ない体制での比率の扱い: 1〜2名では G-6 を越える欠陥が年に数件しか出ない。比率の上昇を警戒サインにしても雑音である。**一定の件数に満たない間は比率でなく件数と分母を出す**。閾値は実証が無いので EV で開示する

### 理由

- あとから変えにくい定義(何を1件と数えるか)であり、ADR が要る
- 本件の穴の中心は「書いてあるのに降りていない」ことだった(`metrics.md:182`)。同じことを繰り返さないため、降ろし先を IMPL で縛り、未達を表示し続ける
- `bug.yml` を任意にとどめるのは、R-1 のとおり報告者がゲートや経路を正しく選べないため。正本は台帳で、トリアージの担当が埋める

| 3〜9名 | 回る |
| 10名以上 | 回る。追跡道具からの書き出しで列を機械で埋める前提。書き出しの対応表を手引きで示す |

- 少数件数のときに比率で警戒させない
