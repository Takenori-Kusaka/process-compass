# #413 内部調査: 欠陥の検出工程・流出の集計と、AI の指摘から起票した欠陥

調査日: 2026-11-04(コミット a0d0607 時点)。行番号はこの時点のもの。#408 の会議体の記録は `metrics.md:178-179` を引くが、現在は `:181-182` へずれている。

〔確〕は本文で確かめた事実、〔推〕は本調査の読み取り。

## 0. 結論の要約

1. 「欠陥の検出工程」は運用メトリクスの候補の指標であり、算出元を「欠陥 Issue の『検出ゲート』欄(起票テンプレートで必須化)」と書いている(`src/content/docs/phase6-operation/metrics.md:182`)。**しかし準拠テンプレートの起票テンプレート `bug.yml` に「検出ゲート」欄は無い**(`template/.github/ISSUE_TEMPLATE/bug.yml:1-38`)。リポジトリ全体でも「検出ゲート」の語は `metrics.md:182` にしか無い〔確〕。集計の実装も無い〔確〕。指標は、AI の起票を区別する以前に**算出元が存在しない**
2. 欠陥の台帳の列は「検出の時点(出荷前 / 運用)」の2値だけで、ゲート単位を持たない(`template/templates/defect-ledger.md:9,17`)。下流(G-7 以降)での検出比率は、台帳からは出せない〔確〕
3. 本標準に「欠陥」の定義と「誰が欠陥を確定するか」の規定は無い〔確〕。重大度は「技術側」が決め、**AI エージェントの参加を許す**(`gate-criteria.md:1871-1876`)。インシデント対応は重大度を人が判定する(`incident-response.md:15,24,37`)。AI の指摘の採否は人が記録する(H.4 条件5)が、採否と「欠陥としての確定」は結ばれていない〔確〕
4. 「AI の推定を判定に数えない」(H.4)、「人の確認を経ていない AI の生成物を品質の活動の証拠に数えない」(7.7.8 要求事項12)、「AI が生成した顧客の声を観測に数えない」(ADR-0091 決定2)が同型の既存原則。#413 の案は、この型を測定の母集団へ及ぼすものと読める〔推〕
5. この指標は保証の主張 C4・C9 の観測と H.7「形骸化していないことの示し方」の4つのうち1つに使われている(`assurance-case.md:216,233,769,864`)。算出元が無いまま観測に名指しされているのが、#413 より大きい穴である〔推〕

## 1. 指標の定義の所在と、指標を引く規定

### 1.1 定義

| 指標 | 所在 | 中身 |
| --- | --- | --- |
| 重大欠陥の流出 | `src/content/docs/phase6-operation/metrics.md:181` | 「本番で発覚した重大欠陥数」。算出は「`bug` かつ Sev1/Sev2 ラベルの Issue 起票数(GitHub API)」。警戒サインは1件でも発生 |
| 欠陥の検出工程 | `metrics.md:182` | 「どのゲートで捕まえたか」。算出は「欠陥 Issue の『検出ゲート』欄(起票テンプレートで必須化)を集計」。警戒サインは「下流(G-7以降)での検出比率の上昇」 |
| 欠陥注入の検出率 | `metrics.md:236`(三識の胆識) | 第5章 5.6.2 の集計(工程単位)。対の指標は注入難度の較正結果 |
| 歪みの検知 | `metrics.md:261` | 「差し戻し率が0%に近く、欠陥注入の検出率も低下した」→ 検査全体の形骸化 |

- 2つの欠陥の指標は、いずれも**起票数・起票の欄**を算出元にする。起票者(人 / AI / bot)も、欠陥と確定したか(採否・重複・取り下げ)も区別しない〔確〕
- 重大欠陥の流出の算出は「Sev1/Sev2 ラベル」を前提にするが、`bug.yml` の重大度はラベルではなくドロップダウン(`bug.yml:28-38`)で、ラベルは `bug` だけを付ける(`bug.yml:3`)〔確〕。ラベルからは数えられない
- 欠陥注入の検出率は、AI の指摘のうち所在が注入箇所を指すものだけを検出に数える(`assurance-case.md:407`)。**検出率の側には AI の指摘の数え方の規則があり、検出工程の側には無い**〔確〕

### 1.2 指標の採用の手続(運用メトリクス)

- 手続3「自動集計の実装をもって採用にする。実装前の指標を暫定として運用しない」(`metrics.md:52`)。表の指標は「候補の一覧」(`metrics.md:71`)
- 「採用しない指標」に「AI が生成した文書・レビューの指摘の件数」(`metrics.md:85`、ADR-0092 決定4 で追加)と「変更あたりの後続の Issue の件数、バックログの純増」(`metrics.md:88`。理由は「後続の起票は見つけたことの記録でもあり、件数を下げる圧力は起票を控える向きに働く」)
- 〔推〕AI の指摘の**件数**は指標として退けたが、AI の指摘を起票した Issue が**欠陥の検出工程の分母・分子**に入る経路は、`:85` の行では塞がれていない。#413 の穴はここ

## 2. 欠陥の定義・台帳と、誰が欠陥を確定するか

### 2.1 欠陥の定義

- 「欠陥」の語の定義は本標準に無い(「欠陥とは」「**欠陥**」で docs 配下を検索して0件)〔確〕
- 欠陥トリアージ基準(`gate-criteria.md:1863-1910`)は重大度の3段階を定めるが、何を欠陥とするか(受入基準への不適合か、期待との差か)は定めない
- 起票テンプレート `bug.yml:2` は「期待した挙動と異なる。観測できた事象で書く」。受入基準(F-xxx)は任意で添える(`bug.yml:17`)

### 2.2 誰が決めるか

| 対象 | 決める者 | 所在 |
| --- | --- | --- |
| 重大度 | 技術側。観測可能な事実で判定。**AI エージェントを参加させてよい** | `gate-criteria.md:1873,1876` |
| 優先度 | 事業側。人間が決める | `gate-criteria.md:1874,1876` |
| 重大度(運用のインシデント) | 当番の担当者が単独で即断。AI は一次分析、人が重大度判定 | `src/content/docs/phase6-operation/incident-response.md:15,24,37` |
| 台帳の重大度 | 「技術側が観測可能な事実で決める」 | `template/templates/defect-ledger.md:13` |
| 欠陥であることの確定 | **規定なし** | — |

- 欠陥の台帳は G-7 基準2 の入力(`defect-ledger.md:3`、`gate-criteria.md:1069,1155`、集約は IMPL-0041 `gate-criteria.md:1079`)。台帳に起票者・確定者の列は無い(`defect-ledger.md:9`)〔確〕
- 台帳の別表「引き下げの点検の記録」は「記録した者は人の氏名。AI の名義を書かない」(`defect-ledger.md:34`)。**欠陥の行そのものには、この型の記名が無い**〔確〕

### 2.3 AI の指摘の扱い

- H.4: AI の推定による判定は「判定に数えない。検出の層としてのみ数える」(`assurance-case.md:311,314`)
- 条件5: 記録には「AI レビュー通過」ではなく指摘の内容と採否を残す(`assurance-case.md:324,335`)
- 所在か根拠を欠く指摘は、レビュアが「不採用(所在・根拠なし)」と採否に記録してよい。機械は指摘を消さない(`assurance-case.md:405-406`)。提出の時点で不成立にしない(`:411`)
- 欠陥注入で「検出」に数えるのは所在が注入箇所を指す指摘に限る(`assurance-case.md:407`、ADR-0075 決定7 `src/content/docs/adr/0075-acceptance-criteria-coverage-premises-and-ai-findings.md:98`。理由は「『懸念がある』型の指摘で検出率が膨らむ経路を塞ぐため」)
- AI の担い手の出力は第3章 3.10 の「意見」に当たらない(ADR-0075 `:104`)
- 準拠テンプレートの `ai-review.yml`: 指摘は検出の層。合否条件にしない。「指摘を採るかどうかは、人が判断して記録してください」(`template/.github/workflows/ai-review.yml:44,48,51,58,62`)。`template/CLAUDE.md:105-106` も同旨
- 〔推〕「採否」は PR のレビューの中の記録であり、採った指摘が欠陥 Issue として起票されるか、起票された Issue が採否のどれに当たるかを結ぶ規定は無い。採否 = 欠陥の確定、とは定められていない

## 3. 「人が確定」に近い既存の語彙と、AI の出力を数えない原則

### 3.1 語彙

### 3.2 AI の出力を数えない既存の原則(同型)

| 原則 | 所在 |
| --- | --- |
| AI の推定による判定を判定に数えない | `assurance-case.md:69,311`、IMPL-0031 `:346` |

## 4. 準拠テンプレートの実装

- 欠陥の検出工程を集計する実装は無い。`template/scripts/gate/*.mjs` に「検出ゲート」「検出工程」の語は無い〔確〕
- 欠陥の台帳の読み込みは2か所
  - `template/scripts/gate/verification-trace.mjs:353` `readDefectLedger` → 出荷の集約(`aggregate-evidence.mjs:2823,2948-2953,3706-3713`)。G-7 基準2 の未解決の件数を重大度・トリアージの区分ごとに数える。検出の時点・起票者は読まない
  - `template/scripts/gate/autonomy.mjs:350,366-367` が「検出の時点(出荷前 / 運用)」を読み、委任の停止に「運用」だけを数える(`:220-221`、`defect-ledger.md:21`)
- 集約の `detection`(`aggregate-evidence.mjs:3104-3194,4396-4439`)は欠陥注入の検出率(人の層 / AI の層)で、実欠陥の検出工程ではない
- Issue を自動起票するワークフローは `context-drift.yml:57`(棚卸し)と `gate-entry.yml:50`(D-0 見直し)だけ。**AI レビュー(`ai-review.yml`)は Issue を起票しない**〔確〕。〔推〕現時点の準拠テンプレートでは、AI の指摘の大量起票は採用者が独自に足した経路(AI エージェントが `gh issue create` を使う等)でしか起きない。ただし標準の本文は起票経路を限っていない
- `bug.yml` に起票者の区分・検出ゲート・確定者の欄は無い(`template/.github/ISSUE_TEMPLATE/bug.yml:1-38`)
