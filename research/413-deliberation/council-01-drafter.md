## 1. 起案の前提として確かめた事実(議題の要旨への追加分)

1. 1.4 用語の定義は「重大度(Severity) 欠陥がもたらす技術的な影響の大きさ。Sev1〜Sev3 の3段階」と定める(`src/content/docs/phase4-process-design/overview.md:148`)〔確〕。インシデント対応の4段階(`src/content/docs/phase6-operation/incident-response.md:26-31`)は、この定義と記号が衝突している
2. 欠陥の台帳は「運用で発生した Sev1・Sev2(ポストモーテムを書く障害)も、この台帳に行を足す」と書く(`template/templates/defect-ledger.md:16`)〔確〕。ポストモーテムの要否はインシデントの尺度で決まる(`incident-response.md:18`「重大度1・2は必須」)。**インシデントの Sev2 と欠陥の Sev2 を同じものとして台帳へ写す経路**がここにある
3. 是正の起動は「重大度が Sev1 または Sev2(後掲「欠陥トリアージ基準」)」で起動し(`gate-criteria.md:596`)、その記録をポストモーテムとする(`gate-criteria.md:607`)〔確〕。インシデントの Sev3「一部機能の劣化(回避策あり)」は欠陥トリアージ基準の Sev2 に当たりうる。この場合、是正の記録が要るのに、ポストモーテムは必須でない〔推〕
4. 5.4.6 の停止の Sev1・Sev2 は「出荷の後に発生し、事後検証の対象となった事象に限る」と書く(`human-ai-boundary.md:187`)〔確〕。どちらの尺度の Sev かを書いていない
5. GitHub の Issue forms の必須の検証は、Web の画面で起票するときだけに効く。`gh issue create` や API からの起票には効かない〔推。GitHub の仕様の一般的な理解。会議体の規格・現場の委員に確かめてほしい〕。AI エージェントの起票はこの経路を通る。**起票テンプレートの必須欄は、AI の起票を区別する手段にならない**
6. 委任の停止(`template/scripts/gate/autonomy.mjs:220-221,350,366-367`)は列「検出の時点」を正規表現 `/検出の時点/` で読み、「出荷前」の行を停止に数えない〔確〕。列を置き換えるなら、この読み込みを同時に変える必要がある
7. 欠陥の台帳の「記録した者は人の氏名。AI の名義を書かない」(`defect-ledger.md:34`)は、別表(引き下げの点検の記録)だけに掛かる〔確〕

## 2. R-1 算出元

### 2.1 結論

- 「欠陥の検出工程」と「重大欠陥の流出」の算出元の正本を、**欠陥の台帳**(`docs/defect-ledger.md`)にする。起票テンプレート(`bug.yml`)は入口であり、正本にしない
- 台帳の列「検出の時点(出荷前 / 運用)」を、列「**検出の工程**(G-6 / 出荷前の検証 / 運用 / 特定できない)」へ置き換える。2値の「出荷前 / 運用」は、この列から導く(G-6・出荷前の検証 → 出荷前、運用 → 運用、特定できない・空欄 → 運用として数える)
- 指標は附属書H の観測(C4・C9・H.7・H.9 問5、EV-0062 の差し替え条件)から**外さない**。集計の手段が準拠テンプレートへ降りるまで、観測は「未測定」として開示する。その事実を IMPL の undelivered で表示し続ける
- `metrics.md:182` の「起票テンプレートで必須化」は事実に反する記述であり、削る。`metrics.md:181` の「Sev1/Sev2 ラベル」も、ラベルが存在しないため算出元から外す

### 2.3 理由

1. Issue を正本にすると、3つの経路で値が実態からずれる。(i) `gh issue create`・API の起票は様式の必須欄を通らない(1.5)。AI の起票はこの経路を通る。(ii) G-6 で見つかった欠陥は PR の中で直り Issue にならない(調査 H7)。(iii) Issue 追跡を使わない組織がある(台帳は「欠陥管理の道具を使う組織は、出荷の前にこの形へ書き出す」と書く。`defect-ledger.md:3`)。台帳は G-7 基準2 の入力であり、出荷のたびに書き出しが強制される唯一の記録である
2. 台帳の2値の列は委任の停止の入力であり、工程の列と別に持つと2列が食い違いうる。1列から導けば食い違いは生じない
3. 観測から外すと、附属書H が実際の欠陥の結果を見る唯一の観測を失う。ほかの観測(検出率)は注入した欠陥によるもので、EV-0062 自身が「注入した欠陥と実際の欠陥は、見つけやすさが一致しない」と書く(`assurance-case.md:784`)。外すのでなく、未測定と開示するのが H.7 の既存の規定(「件数が足りない体制では未測定と開示」)と同じ扱いである
4. 手続3 との緊張は、観測と正式指標を分けて解ける。附属書H の観測は、組織が正式指標に採るかに依らず「何を見ると主張の崩れが分かるか」を示す。観測できない間は未測定と書けば、主張と事実が一致する

### 2.5 反論されうる点

- 「G-6 の PR の中の検出を数えないと、『どのゲートで捕まえたか』という指標の元の意味から外れる」(現場・規格)。答え: 元の意味は算出元を持たず、一度も値が出ていない。上流の働きは検出率が測る(C6)。結果側は取り込み後の欠陥で測る。2つを対で読む形は EV-0062 の差し替え条件と同じ構造である。IPA の「上流工程での不具合摘出比率」とは量が違うことを、本文へ注記する必要があるかもしれない(規格の委員に問う)

## 3. R-2 数える母集団

### 3.1 結論

- 語を分ける。**不具合の報告**(起票されたもの。IEEE 1044 の anomaly に当たる)と、**欠陥**(作業成果物の不備で、受入基準・仕様・壊してはならない品質条件・期待した挙動に適合せず、修復または置換を要すると人が確定したもの。24765 の defect に当たる)
- 欠陥の検出工程・重大欠陥の流出の集計に数えるのは、**確定した欠陥**に限る
- 確定の操作的な定義: 台帳の行の欄「確定」に、(i) 確定した者(名簿にある人の氏名。AI の名義を書かない)、(ii) 確定日、(iii) 確定の根拠の所在(再現の記録、修正の変更、受入基準・品質条件の識別子のいずれか)の3つが埋まっていること。どれかが空なら未確定
- 確定の結果「欠陥でない」とした報告は、状態を「取り下げ(重複 / 再現しない / 仕様どおり / その他)」とし、行を消さない。取り下げにも確定した者を書く。**重複は原因が同じ欠陥を1件とし、残りを取り下げ(重複)にする**(IPA の原因数の数え方)
- 起票の起点を別の列で持つ: 人の観測 / AI のレビュー・解析の指摘 / AI エージェントの起票 / 機械の検査 / 利用者・顧客の報告 / 特定できない
- **母集団の限定は運用メトリクスの集計だけに掛ける**。出荷判定(G-7 基準2)と委任の停止(5.4.6)は、未確定の行も記載の重大度で数える(停止の側・止める側へ倒す)。確定を遅らせて出荷の判定や停止を逃れる経路を作らない
- 確定者に作成を指示した者(AI に解析を指示した者、原因の変更を指示した者)を**含めてよい**。分離を課さない。代わりに確定の根拠の所在を必須にし、内部監査が AI を起点とする確定の行を抜き取って根拠を確かめる。分離を課さない判断は EV で開示する
- 語「人確定」は使わない。自律レベルの語(`human-ai-boundary.md:86,385`)との衝突を避け、「欠陥の確定」「確定した者」と書く。既存の型「区分の確定者の記名(人が確定した場合)」(`deliverable-templates.md:683`)と同じ語の作りに揃える

> | 5 | AI のレビューの指摘を採ったこと(採否の記録の「採用」)を、欠陥の確定とみなさない。採った指摘から報告を起票した場合も、要求事項1 による |

> 確定した者は、報告を起票させた者・原因の変更を指示した者と同じ人でもかまいません。**本標準は、確定に、作成を指示した者と別の人を課しません**。確定は事実の確認であり、根拠の所在(要求事項1)を後から第三者が確かめられるためです。根拠を欠く確定は、内部監査が抜き取りで拾います([プロセス内部監査](/process-compass/phase6-operation/process-audit/))。

**(d) 内部監査の観点**: `src/content/docs/phase6-operation/process-audit.md` の観点の表(要確認。観点番号の正本は H.3)へ「AI を起票の起点とする確定した欠陥の行を抜き取り、確定の根拠の所在から欠陥と確かめられるか」を観点として足すか、既存の観点(C9 の担当の観点23)の確かめる中身に加える。**H.3 の観点は保証の主張の観測の担当として置く**(ADR-0086)。C9 の観点23 の中身へ加える形を案とする

### 3.3 理由

1. 用語体系では報告(anomaly)と欠陥(defect)は別の概念であり(24765 を引く SWEBOK、IEEE 1044 の認識 → 調査 → 処分)、新しい概念の発明ではない。DRE・DDP・フェーズ yield の単位も欠陥である
2. 未確定の報告を数えると、AI の起票量が指標を直接動かす。調査の curl の例(約20% が AI の slop、確認できた脆弱性は約5%)は、起票の量と欠陥の量が乖離することを示す
3. 確定に限ると未確定の滞留が見えなくなる(議題の指摘)。この欠点は、起点の記録と対の指標(未確定の報告の滞留)で塞ぐ。片方だけでは足りない。「確定に限る」だけなら滞留が隠れ、「起点を記録して両方出す」だけなら未確定の値が主張に使われる
4. 受理を確定と同一視しない理由: AutoCommenter が示すとおり、正しいが価値の低い指摘・好みの指摘も適用される。欠陥の定義を「適合しないもの」に締めるのは、好みの指摘で件数が増える経路を塞ぐためである。H.4 条件5 の採否の記録は残し、欠陥の確定とは別の記録にする
5. G-7 と委任の停止で未確定を数える理由: 確定を集計の条件にすると、確定しないことが値を下げる手段になる。判定と停止の側では確定を条件にしなければ、この手段は判定と停止に効かない。台帳の既存の規定(空欄は止まる側に数える。`defect-ledger.md:17,18,20`)と同じ向きである
6. 分離を課さない理由: 分離を課すと 1〜2 名の体制で確定が成立しない。分離の効果は「水増しの抑止」だが、根拠の所在の欄があれば水増しは事後に検出できる。ODC でも defect type は修正するプログラマ(当事者)が付ける。ただし実証は無いため E0 で開示する

### 3.5 反論されうる点

- 「未確定の行を G-7 で数えると、AI の大量起票が出荷を止める」(現場)。答え: 止めるのは記載の重大度が基準に当たる行だけで、Sev3 の報告は S2 でも「記録し計画返却」である。重大な報告を確定せずに出荷しないことは、利用者から見た信頼性の要求そのものである。大量の起票の費用は、未確定の報告の滞留の指標に現れる。止まることで AI の起票の運用(起票の閾値)を見直す契機になる
- 「確定の根拠の所在を必須にすると記録の負担が増える」。答え: 根拠は再現の手順・修正の PR 番号のどれか1つでよく、多くは起票の時点で既にある
- 「確定した者が名簿の人かを機械で確かめても、AI が人の名を書けば通る」。答え: そのとおりで、機械は名簿との照合までしか確かめない(IMPL-0395 の note に書く)。人の名の詐称は記名の一般の問題で、C1 の観測(内部監査 観点6)が扱う

## 4. R-3 工程の帰属

### 4.1 結論

- 欠陥は、**報告された時点に進んでいた工程**に数える(ODC の opener の属性 activity・trigger に当たる)。値は「G-6 / 出荷前の検証 / 運用 / 特定できない」
  - G-6: 独立レビューの中で、レビューの対象の外にある取り込み済みの欠陥を見つけた(人の指摘・AI の層の指摘を問わない)
  - 出荷前の検証: 取り込まれた後、その変更を含むリリースの出荷判定(G-7)の前に見つかった(結合・受入のテスト、取り込み後の定期の検査、AI エージェントによる走査を含む)
  - 運用: 出荷の後に見つかった(インシデント、利用者の報告、出荷後の走査を含む)
- 確定した人のゲートにも、独立の工程「AI の層」にも数えない。AI か人かは列「起票の起点」が持つ。工程と起点は直交する別の属性として集計する

### 4.2 案(挿入先と文面)

`gate-criteria.md` の新節「欠陥と報告の区別」(3.2 の b)の要求事項の表に行を足す。

> | 6 | 検出の工程は、報告が起票された時点に進んでいた工程で書く(G-6 / 出荷前の検証 / 運用 / 特定できない)。確定した時点・確定した者の工程で書き換えない。AI のレビュー・解析の指摘から起票した報告も、指摘が出された工程で書き、起票の起点の欄で AI であることを示す |

台帳の様式(`template/templates/defect-ledger.md:17`)の説明の行を置き換える(6.2 の IMPL-0392 の文面)。

### 4.3 理由

1. 工程の指標が知りたいのは「どこの確認が欠陥を通したか」である。通した工程は、見つかった時点の工程の直前までの全工程である。確定の時点を使うと、確定を遅らせるほど工程が下流へ動き、確定の速さが値を決める
2. 「AI の層の工程」は存在しない。AI の推定による確認は、置かれた工程の中の検出の層である(H.4、`assurance-case.md:314`)。別の工程として数えると、検出の層をゲートと並べることになり H.4 と衝突する
3. 起点を別の列にすれば、「AI が見つけた欠陥の工程の分布」と「人が見つけた欠陥の工程の分布」を並べられる。AI の層の働きを結果側で見る材料になり、要求事項12 を満たす形で 7.7.8 の評価の入力にできる

### 4.4 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 確定した人のゲートに数える | 4.3 の1。確定の速さが値を決める |
| AI の層を独立の工程として数える | 4.3 の2 |
| 原因の変更が通ったゲート(注入の工程)で数える | 注入の工程は別の量(原因の変更の列・AI 起因の列が持つ)。検出の工程と混ぜると、どちらの量も読めない |

### 4.5 反論されうる点

- 「出荷前の検証と G-6 の境界があいまい(取り込み後に別の PR のレビューで見つけた場合)」。答え: レビューの中で見つけたなら G-6、レビューの外の検証なら出荷前の検証。どちらも出荷前に数えられ、委任の停止と警戒サインの判定は変わらない
- 「運用での AI の走査が見つけた欠陥を運用に数えると、AI の走査を回すほど運用の比率が上がり悪く見える」。答え: 出荷の後に見つかった欠陥は利用者に露出していた欠陥であり、運用に数えるのが正しい。運用の比率の上昇は「上流の確認が通した」を示し、AI の走査が見つけたかどうかで意味は変わらない

## 5. R-4 重大度の2つの定義と判定者

### 5.1 結論

- 本件で揃える。流出の指標の母集団(Sev1・Sev2)、是正の起動、委任の停止、G-7 基準2 がすべて欠陥の重大度を入力にしており、尺度が2つあるままでは母集団が定まらないため
- **誤っているのはインシデント対応の側**である。1.4 は重大度を「Sev1〜Sev3 の3段階」と定義し(`overview.md:148`)、欠陥トリアージ基準と bug.yml と台帳が同じ3段階を使う。インシデント対応だけが同じ記号 Sev を4段階の別の尺度に使う
- ただしインシデントの尺度そのものは誤りではない。事象への対応の急ぎ(初動期限・エスカレーション)を決める尺度であり、欠陥の影響の尺度と目的が違う。**尺度は2つ残し、名と役割を分ける**
  - インシデント対応の4段階を「事象の等級(等級1〜等級4)」へ改名する。初動期限・エスカレーション・ポストモーテムの要否を決める
  - 欠陥の重大度(Sev1〜Sev3)は欠陥トリアージ基準だけを正本にする。台帳・流出・是正の起動・委任の停止・G-7 はこちらを使う
  - 原因が欠陥である事象は、事後検証で欠陥トリアージ基準により重大度を判定し、台帳に行を足す。**事象の等級を重大度へ写さない**
  - ポストモーテムを、事象の等級1・2 に加えて、**原因の欠陥が Sev1・Sev2 と確定した事象**でも必須にする(是正の記録が要るのにポストモーテムが無い穴を塞ぐ。1.3)
- 判定者を揃える。重大度の判定に AI は**案を出してよい**が、台帳に記録する重大度は人が確定する(確定した者の欄。R-2 の要求事項1 と同じ欄)。インシデントの等級は従来どおり当番の人が単独で即断する

### 5.5 反論されうる点

- 「等級1〜4 への改名は、組織が使い慣れた Sev の呼び方を変える」(現場)。答え: 本標準の Sev は 1.4 で定義済みであり、別の尺度に同じ記号を当てていたのは本標準の誤りである。組織が社内で別の呼び名を使うことは 1.7.5 の読み替えで扱える。「等級」の語が既存の語と衝突しないかは突合で確かめる(本委員は docs 配下の「等級」の既存用法を確かめていない)
- 「重大度を人が確定すると、AI の一次分析から台帳への転記が遅れる」。答え: 未確定の行も G-7 と委任の停止に記載の重大度で数える(R-2 要求事項4)ため、確定の遅れは止める側にしか働かない

## 6. R-5 記録と降ろし先

### 6.1 ADR-0102(案)

- 題: 欠陥の検出工程と流出は、取り込まれた後に人が確定した欠陥を、報告された工程で数える。事象の等級と欠陥の重大度を分ける
- 決定
  1. 不具合の報告と欠陥を分け、欠陥の確定を台帳の行で人が行う(確定した者・確定日・根拠の所在)。AI の名義を確定した者に書かない。採否の「採用」を確定とみなさない
  2. 欠陥の検出工程・重大欠陥の流出の算出元の正本を欠陥の台帳とし、確定した欠陥だけを数える。PR の中で直した欠陥は数えない。対の指標に未確定の報告の滞留を置く
  3. 出荷判定(G-7 基準2)と委任の停止は、未確定の行も記載の重大度で数える
  4. 検出の工程は報告された時点の工程で書く(G-6 / 出荷前の検証 / 運用 / 特定できない)。起票の起点を別の列で持つ。台帳の列「検出の時点」は、この列から導く
  5. 確定に、作成を指示した者と別の人を課さない(EV-0208)
  6. インシデント対応の尺度を事象の等級(等級1〜4)へ改名し、欠陥の重大度(Sev1〜Sev3)と分ける。事象の等級を重大度へ写さない。原因の欠陥が Sev1・Sev2 の事象はポストモーテムを要する
  7. 重大度は AI が案を出してよいが、台帳の値は人が確定する(`gate-criteria.md:1876` の改め)
  8. 附属書H の観測から指標を外さず、集計の手段が降りるまで未測定と開示する(IMPL-0394)
- 検討した選択肢: 2.4・3.4・4.4・5.4 の表を統合する
- 突合: ADR-0028(未達の表示)、ADR-0075 決定7(検出に数える指摘の限定。本件は母集団へ同型を及ぼす)、ADR-0081(委任の停止の入力)、ADR-0086(H.3 の観点の置き方)、ADR-0092 決定7(本件へ送った件)・選択肢の行(`adr/0092-...md:104`)、ADR-0073(是正の起動)
- ADR-0092 は採用済みのため書き換えない。ADR-0092 の選択肢の行「本件では決めない。#413 へ送る」に対する答えは ADR-0102 に書く

### 6.4 採らないと明記する事項(ADR-0102 の「本件で課さないこと」へ)
