# #413 会議体: 弁護の委員の意見

- 立場: 現行の規定と既存の決定(ADR)を弁護する。変える必要が本当にあるか、変えると何が壊れるかを問う。弁護できない欠陥は欠陥と認める
- 判断軸: 信頼性。変更量の少なさを採否の理由にしない
- 入力: `council-00-agenda.md`、`survey-413-1-internal.md`、`survey-413-2-external.md`。本文と準拠テンプレートを a0d0607 時点で読み直した
- 凡例: 〔認〕弁護できない欠陥と認める点。〔護〕現行を弁護する点。〔条〕変更を受け入れるが、条件を付ける点

## 0. 要旨

| 論点 | 結論 |
| --- | --- |
| R-1 算出元 | 〔認〕`metrics.md:182` の「起票テンプレートで必須化」は事実に反し、算出元の無い指標を附属書H の観測に使っている。〔護〕指標は附属書H から外さない。算出元は `bug.yml` ではなく欠陥の台帳に置く。流出は台帳の既存の列で今すぐ出せる。検出工程は台帳に列を足し、集計が入るまで「未測定」と開示する |
| R-2 母集団 | 〔条〕数えるのは、修復を要すると人が判断し、その人を記名した欠陥に限る。新しい原則ではなく H.4 の適用として書く。起票者の区分(人 / AI)を記録して両方の値を出す案は採らない(ADR-0092 決定4 が退けた「AI の指摘の件数」を裏口から戻すため)。確定者を作成を指示した者と分けることは求めない。「人確定」の語は使わない |
| R-3 工程の帰属 | 〔護〕検出の層は工程ではない(H.4)。AI が見つけた欠陥は、その指摘が出たゲートに帰属させる。確定した時点のゲートには帰属させない。ただし、指摘を不採用にした後に下流で顕在化した欠陥は、顕在化したゲートに数える |
| R-4 重大度 | 〔認〕同じ「Sev1〜Sev3」の名で 2 つの定義が並び、欠陥の台帳と委任の停止(機械の統制)で交差している。誤っているのはインシデント対応の側である。本件で揃える。判定者は「AI は材料を出す。重大度を確定するのは人」と明記し、両者の食い違いを解く |
| R-5 記録と降ろし先 | 新しい ADR を起こし、既存の ADR(0028・0075・0081・0092)は書き換えない。欠陥の台帳の様式に 2 列を足し、既存の「検出の時点(出荷前 / 運用)」の 2 値は変えない。実装マークは降りていない状態で出し続ける。`bug.yml` は報告の入口に留め、算出元にしない |

## R-1 算出元

### 結論

1. 〔認〕`metrics.md:182` の「欠陥 Issue の『検出ゲート』欄(起票テンプレートで必須化)」は、準拠テンプレートの事実(`bug.yml:1-38` にその欄は無い)と食い違う。標準が自分の様式について誤った事実を書いている状態であり、弁護できない。直す
2. 〔認〕手続3(`metrics.md:52`「自動集計の実装をもって採用にする。実装前の指標を暫定として運用しない」)のもとで、この指標は**候補**である。候補であること自体は正当である。欠陥は、附属書H の C4・C9 の観測(`assurance-case.md:216,233`)、H.7 の 4 つの 1 つ(`:769`)、H.9 問5(`:864`)、EV-0062 の差し替え条件(`:782`)が、この指標を**運用されている観測**として書いている点にある。担当と時点まで割り当てた観測が、実際には算出できない。手続3 との緊張は、#413 の論点(AI の起票)より大きい穴である
3. 〔護〕それでも、指標を附属書H の観測から**外さない**。外したときに壊れるものが大きいためである
   - EV-0062 は、注入した欠陥の検出率を形骸化しないことの証跡にする判断を、「注入欠陥の検出率の推移」と「G-7 以降で検出された欠陥の比率の推移」の対応で差し替えると定めている。注入した欠陥と実際の欠陥は見つけやすさが違う(`assurance-case.md:937`)。**実際の欠陥の側で検出率に対抗する観測は、この指標しか無い**。外すと EV-0062 は反証の経路を失い、注入の検出率だけが自己参照で証跡の地位に残る
   - H.7 の論理(「下流での検出が増えれば、上流の確認が働いていない」)は、IPA の「上流工程での不具合摘出比率」、ISTQB の DDP、PSP のフェーズ yield と同じ型であり、外部の実務とも合う(`survey-413-2-external.md` §2、#408 規格の委員 `council-04-standards.md:201`)
   - 外すなら H.7 の 4 つを 3 つに減らす理由を書かなければならない。理由は「算出元を作っていないから」になり、それは指標の不備ではなく実装の不備である
4. 〔条〕外さない代わりに、附属書H の各所に「集計が入るまでは未測定として扱う」ことを書く。未測定を有効な値として扱う形は、H.7 の既存の規定(「件数が足りない体制では『未測定』と開示する」)と ADR-0028(未達と省略の区別)に既にある。新しい扱いを発明しない
5. 〔護〕算出元は**欠陥の台帳**(`template/templates/defect-ledger.md`)に置く。`bug.yml` には置かない
   - 台帳は G-7 基準2 の入力として機械が読んでいる(IMPL-0041 delivered、`verification-trace.mjs:353`、`autonomy.mjs:350`)。`bug.yml` を読む機械は無い
   - 台帳は道具に依らない(「欠陥管理の道具を使う組織は、出荷の前にこの形へ書き出します」`defect-ledger.md:3`)。他組織が従う規格が、算出元を GitHub の Issue フォームに置くのは誤りである。`metrics.md:181-182` の「GitHub API」「起票テンプレート」は、規格の算出元の書き方として不適切だった
   - 起票(Issue)は報告であって、確定ではない(R-2)。報告の欄を集計しても、確定した欠陥は数えられない
6. 〔認〕「重大欠陥の流出」の算出(「`bug` かつ Sev1/Sev2 ラベル」)も、`bug.yml` が重大度をラベルにしない(`bug.yml:3,28-38`)ため出せない。ただし**台帳には既に必要な列がある**。「検出の時点 = 運用」かつ「重大度 = Sev1 / Sev2」の行を数えれば、流出は今すぐ算出できる。`autonomy.mjs` はこの組み合わせを委任の停止のために既に読んでいる。算出元の記述を台帳へ向け直せば、流出は候補から採用へ進められる
7. 検出工程は、台帳に「検出したゲート」の列を足す(R-5)。既存の「検出の時点(出荷前 / 運用)」の 2 値は**置き換えない**。この 2 値は委任の停止の入力であり、ADR-0081 が「出荷前に検出した欠陥を停止に数えない」と決め、`defect-ledger.md` が理由(「停止に数えると、検出が罰になり、重大度を低く書く誘因になる」)まで書いている。ゲート単位の値へ置き換えると、`autonomy.mjs` の読み取りと ADR-0081 の線引きが壊れる

### 理由(信頼性)

算出できない観測が保証の論証に名指しされていると、読み手は「見ている」と受け取る。見ていない観測を見ていると読ませるのは、未測定と開示するより信頼性を損なう。一方で、観測を外すと、注入欠陥の検出率に対する実欠陥の側の歯止めが消える。どちらも信頼性を損なうため、外すのではなく、算出元を正しく置き、入るまでは未測定と開示する。

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 指標を附属書H の観測(C4・C9・H.7・H.9 問5)から外す | EV-0062 の差し替え条件が観測不能のまま固定され、実欠陥の側の歯止めが消える。外す理由が「実装していない」であり、指標の欠陥ではない |
| `bug.yml` に「検出ゲート」欄を足して必須にし、それを算出元にする | 起票は報告で、確定ではない。G-6 の PR の中で直る欠陥は Issue にならず、AI が Issue を起票する経路だけが上流の件数を足す(内部調査 H7 の非対称)。道具に依存する算出元を規格に置くことにもなる |
| 欠陥の台帳の「検出の時点」をゲート単位の値へ置き換える | 委任の停止の入力(ADR-0081・`autonomy.mjs`)を壊す。2 値と別の列にすれば両立する |
| 算出元を直さず、`metrics.md:182` の「必須化」の語だけを消す | 誤った事実は消えるが、附属書H が算出できない観測を運用中として名指しする状態が残る |

### 反論されうる点

- **G-6 で見つかって PR の中で直った欠陥は、台帳にも行が無い**。台帳を算出元にしても、上流の検出は数え漏れる。これは認める。ただし数え漏れの向きを見る必要がある。上流の数え漏れは「G-7 以降の比率」を**高く**見せ、警戒の側へ倒れる。AI の未確定の起票は比率を**低く**見せ、隠す側へ倒れる。信頼性にとって危険なのは後者であり、R-2 がそれを塞ぐ。前者については、G-6 の全指摘を台帳の行にする記録の義務は、記録を即修正で済ませる実務(NTT データの指摘、`survey-413-2-external.md` §2)と衝突し、新しい負担の割に値の意味が定まらない。どこまでを行にするかは、起案が案を出すべき論点として残す
- 比率が常に高く出て警戒サインが点き続けるなら、「人の指摘を CI の検査へ移した件数」(値が常に 0 で廃止された、`metrics.md` 採用しない指標)と同じ運命をたどる、という反論。これには、上流の分母に何を入れるかを明記し、明記できないうちは比率ではなく「G-7 以降で検出した確定欠陥の件数と推移」に留める、という後退の余地がある。比率の定義は起案と現場の委員の判断に委ねる
- 「未測定と開示する」を書けば、未測定のまま長く放置される、という反論。これは IMPL の未達の表示(降りていない規定を台帳に出し続ける)で見える状態に保つ。消さない

## R-2 数える母集団

### 結論

1. 〔条〕集計に数える欠陥は、**修復を要すると人が判断し、判断した人を記名した欠陥**に限る。AI の指摘・AI が起票した Issue は、人がそう判断して記名するまで数えない
2. 〔護〕これを**新しい原則として足さない**。H.4 の「AI の推定による判定は、判定に数えない」(`assurance-case.md:311`)の適用として書く。「これは修復を要する欠陥である」は判定であり、AI がそう推定しただけの起票を欠陥に数えることは、AI の推定を判定に数えることに当たる。既存の同型の規定(7.7.8 要求事項12、ADR-0075 決定7 の「所在が注入箇所を指す指摘だけを検出に数える」、ADR-0091 決定2、`assurance-case.md:646` の AI と bot の承認を数えない)と並べて新しい原則を立てると、原則が増えるほど適用の境界の争いが増える。H.4 の射程に入ることを示せば足りる
3. 確定の操作的な定義は、次の 3 つを満たす台帳の行とする
   - 台帳に行がある(報告ではなく、台帳へ登録されている)
   - 「欠陥と判断した者」の欄に人の氏名がある。AI と bot の名義を書かない(`defect-ledger.md:34` の「記録した者は人の氏名を書く。AI の名義を書かない」と同じ型)
   - 重大度が人によって確定している(R-4)
4. 〔護〕判断した者を、作成を指示した者と**分けることは求めない**
   - 分離の規定(G-6 の作成を指示した者以外の承認、`PULL_REQUEST_TEMPLATE.md:38,51`)は、AI の出力を**通す**判断に掛かる。通す判断では、作成を指示した者に通したい誘因がある
   - 欠陥と認める判断の誘因は逆向きである。作成を指示した者は、自分の変更の欠陥を**認めたくない**側にいる。分離を課しても、#413 が問題にした水増し(AI の起票で上流の件数が増える)は防げない。水増しを生むのは起票の経路であり、確定者の同一性ではない
   - 1〜2 名の体制では分離を満たせず、指標は常に未測定になる。分離が信頼性を上げない場所で、測定だけを止めることになる
5. 〔護〕「人確定」の語は使わない。`human-ai-boundary.md:86,385` で変更の自律レベル(L1 と対になる水準)の語として定義済みであり、欠陥に当てると、ある欠陥の確定と変更の自律レベルが同じ語で書かれ、照合のたびに読み違える。語は「欠陥と判断した者」とし、近い既存の型(`deliverable-templates.md:683` の「区分の確定者の記名(人が確定した場合)」)と並べる。新しい用語を定義語として立てない
6. 〔護〕起票者の区分(人 / AI)を記録して、確定した欠陥と未確定の起票の両方の値を出す案は**採らない**
   - `metrics.md:85`(ADR-0092 決定4)が「AI が生成した文書・レビューの指摘の件数」を正式指標にも警戒サインにも置かないと決めている。理由は「AI は人の注力と無関係に件数を増やせる」「対になる指標を指定できない」。AI の起票の件数を第 2 の値として出すのは、退けた量を別の名で戻すことである。採用済み ADR の決定を、後続の Issue が迂回してはならない
   - `metrics.md:88` も「変更あたりの後続の Issue の件数、バックログの純増」を、起票を控える圧力を生むとして退けている。未確定の起票の件数も同じ圧力を生む
   - 確定に限ると未確定の AI の指摘の滞留が見えなくなる、という懸念は認める。ただし滞留は品質の指標で見るものではない。PR の中の指摘は、H.4 条件5 が採否の記録を求めており、採否の無い指摘は記録の欠落として既に扱える(IMPL-0155・IMPL-0253 は未達のまま表示される)。PR の外で AI が起票した Issue の滞留は、トリアージの工数の問題であり(curl の事例、`survey-413-2-external.md` §3.3)、7.7.8 の AI の利用の評価が総費用の区分で扱う側にある
7. 〔条〕確定を「AI の指摘を採った」ことと同一視しない。採否の「採用」は、指摘への対処を決めたことであり、修復を要する欠陥であったことを意味しない。好みや軽微な指摘も採用される(AutoCommenter の「正しいが価値の低いコメント」、`survey-413-2-external.md` §3.2・§6)。採用を自動的に欠陥へ数えると、森崎の言う形骸化の AI 版が起きる。採否の記録と台帳の行は、人が台帳へ登録する判断で結ぶ。機械で結ばない

### 理由(信頼性)

用語体系は、報告されたもの(anomaly)と修復を要する欠陥(defect)を別の概念として持つ(24765 を引く SWEBOK)。ODC は確定側の属性を修正する者が付け、Meta の JiT は候補(weak catch)と真陽性(strong catch)を人への問い合わせで分ける。数える単位を確定した欠陥に固定しない限り、AI の起票量が指標を直接動かす。これは外部の実務とも、本標準の H.4 とも整合する。

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 起票者の区分(人 / AI)を記録し、確定と未確定の両方の値を出す | ADR-0092 決定4(`metrics.md:85`)が退けた量を戻す。滞留は採否の記録と 7.7.8 の側で扱う |
| 確定者を作成を指示した者と別の人に限る | 水増しの経路(起票)を塞がない。誘因の向きが承認と逆。1〜2 名の体制で指標が常に未測定になる |
| AI の指摘の「採用」を欠陥の確定とみなす | 採用は欠陥であったことを意味しない。軽微な指摘で上流の件数が増える |
| 確定を「人確定」と呼ぶ | 自律レベルの定義語と衝突する |
| AI の承認(2026-10 GA の Copilot の承認など)が付いた確定を数える | H.4 と `assurance-case.md:646`(AI と bot の承認を数えない)に反する。確定の主体は人に限る |
| 「欠陥」の一般的な定義を本標準の定義語として新設する | 本件の母集団に要るのは「どの行を数えるか」であり、語の定義ではない。定義語を立てると、受入基準への不適合か期待との差かの争いを本件へ持ち込む。台帳に載せる判断の基準(修復を要する)だけを書く |

### 反論されうる点

- 「記名だけで確定とすると、AI が大量に起票し人が記名だけを付ける形骸化が起きる」(#408 起案 `council-01-drafter.md:165` の懸念)。認める。記名は判断の深さを保証しない。ただし、確定の深さを確かめる新しい統制を足すと、欠陥を認める手間が増え、欠陥の登録を控える圧力になる(ADR-0081 が出荷前の欠陥を停止に数えなかったのと同じ理由)。記名の形骸化は、7.7.8 の評価と内部監査の側で見る、という分担に留める。ここは監査の委員と争点になる
- 「H.4 の適用と書くのは拡大解釈である。H.4 は判定(ゲートの合否)を対象にしている」という反論。H.4 の対象を広げる解釈であることは認める。拡大を避けたいなら、新しい ADR の決定として H.4 の射程を明記する(R-5)。いずれにせよ、別の原則として並べるより、H.4 の射程の明記の方が境界の争いが少ない
- 「未確定の滞留が見えないと、AI の起票がトリアージを溢れさせても気づかない」。品質の指標で気づく必要は無い、が弁護の立場である。7.7.8 の総費用で見えない場合は、#413 の範囲の外として別 Issue に送る

## R-3 工程の帰属

### 結論

1. 〔護〕AI の層は工程ではない。H.4 は AI のレビューを「判定に数えない。検出の層としてのみ数える」と定め(`assurance-case.md:311,314`)、検出の層はゲートの中で働く。「AI の層の工程」という帰属先は本標準に存在しない。作れば、AI の確認を独立の工程として扱うことになり、H.4 と ADR-0075 決定11 に反する
2. 〔護〕AI が見つけて人が確定した欠陥は、**その指摘が出たゲート**(検出したゲート)に帰属させる。G-6 の PR で AI が指摘し、人が欠陥と判断して台帳へ登録したなら G-6 である。ODC で検出側の属性(activity・trigger)が検出の時点で付き、確定側の属性(defect type)が修正の時点で付くのと同じ分け方である。工程の帰属は検出側の属性であり、確定の時点の属性ではない
3. 〔護〕確定した人のゲート(確定した時点のゲート)には帰属させない。確定の時点はトリアージの都合で動く。G-6 で出た指摘を出荷の後に確定すれば「運用」に、確定を急げば上流に数わる、という具合に、帰属が人の作業の遅速で動き、工程の働きを測れない
4. 〔条〕ただし、指摘が出ても**不採用にされ、後に下流で顕在化した欠陥**は、顕在化したゲートに数える。工程がその欠陥を止めなかったからである。指摘が出たゲートに数えると、「AI は見つけていた」ことを理由に上流の検出として数え、人が退けた見逃しを隠す。この扱いは H.7 の論理(下流の検出は上流の確認が働いていないことを示す)と合う
5. 帰属の判断も人が行い、台帳の「検出したゲート」に書く。機械は採否の記録から推定しない

### 理由(信頼性)

工程の帰属を確定の時点や AI の層に置くと、指標は工程の働き(どこで止めたか)ではなく、トリアージの速さや AI の稼働量を示すようになる。止めた場所に帰属させ、止めなかったものは止めなかった側に数えることで、H.7 の論理が成り立つ。

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| AI の層を独立の工程として数える | H.4・ADR-0075 決定11 に反する。AI の確認を独立の確認として扱うことになる |
| 確定した人のゲート・確定した時点に帰属させる | トリアージの遅速で帰属が動く |
| 不採用だった指摘も、指摘が出たゲートに帰属させる | 人が退けた見逃しを上流の検出として隠す |
| 台帳に検出した層(人の層 / AI の層 / 機械の検査)を記録し、実欠陥の層別の検出の割合を出す | 層ごとの検出能力は 5.6.2 の注入で測る、と既に決めている。実欠陥の層別の割合を出すと、「実欠陥の X% は AI が見つけた」が人の確認を減らす根拠に使われ、ADR-0092 決定4 が退けた件数の量と同じ圧力を生む。H.6 の「適合性確認の結果を検出能力の測定値として示さない」と同じく、測定値の混同を招く |

### 反論されうる点

- 「層を記録しないと、AI の層が実際の欠陥でどれだけ働いたか分からない」。分からないことは認める。5.6.2 の注入の測定が層ごとの値を出しており、実欠陥の層別の値は二重の測定になる。将来、注入と実欠陥の乖離(`assurance-case.md:937`)を層ごとに確かめる需要が出たら、その時点で別 Issue とする
- 「検出したゲートの判断に争いが出る(G-5 の機械の検査が落とし、G-6 で人が気づいた等)」。最初に止めたゲートに数える、と書けば足りる。細目は起案の判断に委ねる

## R-4 重大度の 2 つの定義

### 結論

1. 〔認〕弁護できない欠陥である。理由は語が 2 つあることではなく、**2 つの定義が欠陥の台帳と委任の停止で交差している**ことにある
   - 欠陥トリアージ基準(`gate-criteria.md:1882-1888`)は 3 段階。Sev2 =「回避策が存在する」。台帳(`defect-ledger.md:13`)と `bug.yml` はこちらに従う
   - インシデント対応(`incident-response.md:26-31`)は 4 段階。Sev2 =「主要機能の停止・著しい劣化(回避策なし)」、Sev3 =「一部機能の劣化(回避策あり)」
   - 台帳は「運用で発生した Sev1・Sev2(ポストモーテムを書く障害)も、この台帳に行を足す」と書き、準拠テンプレートの障害時の補助ファイル(`incident.md:31,34`)は、ポストモーテムを書く Sev1・Sev2 を台帳の行にする。ポストモーテムの要否はインシデントの重大度で決まる
   - したがって、主要機能に障害があり回避策がある運用の事象は、インシデント対応では Sev3(ポストモーテム不要)、トリアージ基準では Sev2 になる。ポストモーテムが書かれず、台帳に行が足されず、`autonomy.mjs` は該当する変更種別の委任を止めない。**欠陥の指標の値が揃わないだけでなく、機械の統制(5.4.6 の委任の停止)が定義の差で抜ける**
2. 〔認〕誤っているのは**インシデント対応の側**である
   - トリアージ基準は G-7 基準2、欠陥の台帳、委任の停止(ADR-0081)、`bug.yml` の 4 つが参照する正本として運用されている。インシデント対応の表は手順の頁にあり、同じ名を別の意味で使っている
   - トリアージ基準は「Sev1 と Sev2 を分ける唯一の境界は回避策の有無」と明示し、回避策は文書化されなければ存在しないとまで定める。インシデント対応の表は回避策の有無を Sev2 と Sev3 の境界に置いており、境界の位置そのものがずれている
3. 〔護〕ただし、インシデント対応が**初動の緊急度**を別に持つこと自体は弁護する。当番が 15 分で即断する場面で回避策が文書化されているかを確かめる余裕は無く、「迷ったら高いほうに倒す」即断の分類は運用上必要である。Sev4(影響の無い異常)も初動の分類としては正当である。誤りは同じ名「Sev」を別の定義で使うことと、ポストモーテムと台帳の行の要否を初動の分類で決めていることにある
4. 揃え方(弁護の推す案)
   - インシデントの初動の分類は、トリアージ基準と別の名にする(例: 初動の緊急度)。Sev の名はトリアージ基準の定義だけに使う
   - ポストモーテムの要否と台帳の行の要否は、復旧の後に**トリアージ基準の定義で確定した重大度**で決める。初動の分類が高い場合も書く(高いほうに倒す趣旨を保つ)
   - 本件で揃える。別 Issue へ送らない。R-1 で流出の算出元を台帳の「運用」かつ Sev1/Sev2 に置く以上、定義が 2 つのままでは算出元が定まらず、送った先が決まるまで流出の指標も委任の停止も不確かなまま残るためである
5. 〔条〕判定者の食い違い(トリアージは AI の参加を許す、インシデントは人が判定する)は、**矛盾ではなく書き方の不足**として解く
   - トリアージ基準の「AI エージェントを参加させてよい」(`gate-criteria.md:1876`)は、判定の材料が観測可能な事象に限られることを理由にしている。この理由は材料を AI が集めることを正当化するが、AI が確定することまでは正当化しない
   - 重大度は G-7 基準2 の合否と委任の停止を動かす。AI の推定で確定した重大度でこれらが動けば、H.4(AI の推定を判定に数えない)に反する
   - よって「AI は判定の材料(観測した事象、影響範囲の推定)を出してよい。重大度を確定するのは人である」と明記する。インシデント対応の「AI は一次分析、人が重大度判定」と同じ形になり、食い違いは消える。トリアージ基準の参加の許可そのものは撤回しない

### 理由(信頼性)

同じ名の 2 つの定義は、読み手の誤読で済まず、ポストモーテム → 台帳 → 委任の停止という機械の経路で、止めるべき委任を止めない結果を生む。統制が定義の差で黙って抜ける状態は、本標準が最も避けるべき形である。

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 本件で扱わず別 Issue へ送る | 流出の算出元と委任の停止が、送った先の結論まで不確かなまま残る |
| トリアージ基準をインシデント対応の 4 段階へ合わせる | トリアージ基準が G-7・台帳・委任の停止・`bug.yml` の正本であり、回避策を唯一の境界とする設計に理由がある。合わせると出荷判定のステージ別のマトリクス全体を作り直すことになり、正しい側を誤った側へ寄せる |
| インシデント対応の初動の分類を廃止し、トリアージ基準だけにする | 初動で回避策の文書化を確かめる余裕は無い。即断の分類には別の役割がある |
| 重大度の判定から AI の参加を外す | 材料の収集を AI に任せる理由(観測可能な事象)は正当である。外すのは確定だけでよい |

### 反論されうる点

- 「初動の分類と確定した重大度を分けると、記録が 2 つになり手間が増える」。増えることは認める。ただし手間を理由に定義の交差を残すと、委任の停止が抜ける。判断軸は信頼性である
- 「`bug.yml` の選択肢の文言(Sev1 に『回避策が存在しない』の条件が無い、Sev3 の書き方が違う)もトリアージ基準とずれている」。認める。揃える範囲に含める(R-5)

## R-5 記録と降ろし先

### 結論

1. **新しい ADR**(連番の次)を起こす。決定は R-1〜R-4 の各結論。既存の ADR(0028・0075・0081・0092)の本文は書き換えない。ADR-0092 決定7 と選択肢の表の「#413 へ送る」は、新しい ADR から参照して受ける
2. **本文の変更**
   - `metrics.md:181-182`: 算出元を欠陥の台帳へ向け直す。「起票テンプレートで必須化」「GitHub API」「Sev1/Sev2 ラベル」を消す。数える行の条件(R-2)と帰属(R-3)を書く。母集団の限定は表の行の中に書く(適用範囲の書き方、#226)
   - 附属書H(`assurance-case.md:216,233,769,782,864`): 集計が入るまでは未測定と扱う旨を書く。H.7 の 4 つの 1 つと EV-0062 の差し替え条件は残す
   - 欠陥トリアージ基準(`gate-criteria.md:1876`): 「AI は材料を出す。重大度を確定するのは人」と明記する
   - インシデント対応(`incident-response.md:24-31`): 初動の分類を Sev と別の名にし、ポストモーテムと台帳の行の要否を、トリアージ基準で確定した重大度で決める
3. **準拠テンプレート**
   - 欠陥の台帳(`defect-ledger.md`、降ろし先 `defect-ledger-template`): 「検出したゲート」と「欠陥と判断した者(人の氏名。AI の名義を書かない)」の 2 列を足す。「検出の時点(出荷前 / 運用)」は変えない(`autonomy.mjs` と ADR-0081 を壊さない)
   - 障害時の補助ファイル(`incident.md`、降ろし先 `incident-artifact`): ポストモーテムと台帳の行の要否をトリアージ基準の重大度で決める旨へ改める
   - `bug.yml`: 重大度の選択肢の文言をトリアージ基準に揃える。「検出ゲート」の欄は**必須にしない**。入口の報告であり、確定ではないためである。任意の欄として足すかは起案に委ねるが、算出元にはしない。`bug.yml` は `impl-targets.yaml` に未登録であり、実装マークの降ろし先にするなら登録が要る
   - 集計(降ろし先 `evidence-aggregation`): 流出(台帳の運用かつ Sev1/Sev2 の確定した行)は既存の読み取りの延長で降ろせる。検出工程の集計は、降ろせるまで `state=undelivered` の実装マークで表示し続ける。降りていない規定を消さない
4. **根拠水準のマーク(EV)**
   - 「確定した欠陥に限る」判断: E1(間接)。SWEBOK・ODC・Meta JiT は anomaly と defect を分けるが、AI の起票を欠陥数から除くと明文化した規格・業界ガイドは見当たらない(`survey-413-2-external.md` §5)。差し替え条件の候補は、確定に限った集計と限らない集計の乖離を記録した事例
   - 「検出したゲートに帰属させ、不採用の後の顕在化は顕在化したゲートに数える」判断: E0〜E1。ODC の opener / closer の分け方に依るが、不採用の扱いの先例は確かめていない
   - EV-0062 は残し、差し替え条件の観測が未実装に依ることを見直しの時に扱う(新しい EV で開示するかは起案の判断)
5. **採らないと決めたことを明記する**: R-1〜R-4 の「採らない案」の表を ADR の「検討した選択肢」へ載せる。特に「起票者の区分を記録し両方の値を出す」を採らない理由(ADR-0092 決定4 との整合)は明記する。書いていないのか、課さないと決めたのかを読み手が区別できるようにする

### 反論されうる点

- 「附属書H の観測を残して未測定と書くのは、実装の約束の無い延命である」。実装マークの `review=` で見直しの期日を置けば、延命は台帳で見える。期日までに降りなければ、附属書H から外すかをそこで決め直す
