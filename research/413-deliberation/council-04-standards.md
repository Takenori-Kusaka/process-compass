## 総論: 規格の側から見た本件の形

1. 用語体系は、**報告されたもの**(anomaly。本標準の語では「報告」「指摘」)と、**修復または置換を要すると確かめられたもの**(defect。本標準の語では「欠陥」)を別の概念として持つ〔外・survey〕。ODC も、検出の時点に付ける属性(activity・trigger)と、修正の時点に付ける属性(defect type)を分ける〔外・survey(原典は確認、opener/closer の区分は二次)〕。本件の区別は新しい概念の発明ではない。本標準がこの2つを語として持っていないことが穴である
2. 本件の本体は、AI の起票の区別より手前にある。**規定の附属書(附属書H。`assurance-case.md:8` で「本附属書は規定です」)が、算出元の無い候補の指標を、保証の主張の観測と H.7(附属書H が自ら定める4つの1つ)に名指ししている**〔内・確〕。運用メトリクスの表は候補の一覧で(`metrics.md:71`)、手続3 は「実装前の指標を暫定として運用しない」(`metrics.md:52`)。規定が、採用されないことのありうる候補に依存し、しかもその候補は手続3 により運用できない。規定の書き方として成立していない
3. そこで本書は、「AI の指摘を区別するか」を単独で答えず、**測る母集団・測る単位・算出元・統制の母集団**を組で決める。どれか1つだけを決めると、残りの経路から同じ歪みが戻る

## R-1 算出元

### 結論

1. 指標「欠陥の検出工程」を、現行の定義(Issue の「検出ゲート」欄の集計、警戒サインは G-7 以降の**比率**)のまま残さない。**マージ後に検出された確定した欠陥の件数**(出荷の前の検証で検出 / 運用で検出の2区分)へ定義し直し、同じ期間に出荷した変更の件数と並べて示す。上流の確認が働いているかは、比率の分子で示さず、第5章 5.6.2 の欠陥注入の検出率(分母が既知)で示す。EV-0062 が既に組にしている2つの量である
2. 算出元は**欠陥の台帳**(`docs/defect-ledger.md`)とする。起票テンプレート(`bug.yml`)を算出元にしない。台帳は G-7 基準2 の入力で、運用の Sev1・Sev2 の行を足す規則と委任の停止の入力を既に持つ規定の記録である〔内・確〕(`defect-ledger.md:3,20,23`)
3. 台帳の「検出の時点」の値を、「出荷前 / 運用」の2値から「マージ前(G-5・G-6) / マージ後・出荷前 / 運用」の3値へ分ける。「運用」と空欄の意味(委任の停止に数える)は変えない(`autonomy.mjs` の読み方を保つ)
4. 「重大欠陥の流出」の算出元も、Sev ラベルの付いた Issue の起票数から、**台帳の検出の時点が「運用」で、重大度が Sev1・Sev2 の確定した欠陥の行**へ改める。`bug.yml` は重大度をラベルにしないため、現行の算出は数えられない〔内・確〕(`bug.yml:3,28-38`)
5. 附属書H(C4・C9 の観測、H.7、H.9 問5、EV-0062)は、候補の指標名ではなく**台帳の記録とその集計**を引く形に改める。規定の附属書は、規定の記録を引くべきで、採用の手続を経ない候補に依存してはならない
6. 集計が降りるまでは、附属書H の該当の観測は「未測定」と開示する。H.7 の他の行と同じ扱いである(`assurance-case.md:766,772-773`)。`metrics.md:182` の「起票テンプレートで必須化」は事実に反する記述なので、本件の決定と同時に除く

### 理由

- **比率の分子(上流での検出)の記録率を担保する手段が無い**。G-6 で見つかった欠陥の多くは PR の中で直され、Issue にも台帳にも残らない(内部調査 H7)。AI のレビューの指摘の採否の記録率も低い(AutoCommenter で明示的なフィードバックはコメントの約 10%)。Copilot の利用メトリクスは「適用」だけを数え却下を数えない〔外・survey〕。日本の実務でも、アジャイルではバグを記録せず即修正することが多いと記録されている〔外・survey(NTT データ)〕。分子が記録の振る舞いで動く比率は、工程の働きではなく記録の習慣を測る。AI が起票する分だけ分子が増える非対称(議題の前提)も、この構造の1つの現れにすぎない
- 封じ込め・DRE・DDP は分母に後工程の欠陥を取るため、上流で未確定の報告を数えると分子だけが膨らみ、構造的に上振れする〔外・survey(考察)〕。分母を確かめられない量を、規定の附属書の観測に置かない
- 下流の検出の件数は、記録の振る舞いで減らしにくい。運用の欠陥は台帳への記録が既に要求され(`defect-ledger.md:20`)、出荷後の Sev1・Sev2 は是正の記録を要する(`gate-criteria.md:596`)。DORA の不安定性の指標も、本番で介入を要した事後の事象で数え、指摘・報告の件数では数えない〔外・survey(dora.dev を確認)〕。本番側の事象で数える作法は業界の現在の実務と整合する
- 上流の働きを示す量は、本標準に既にある。欠陥注入の検出率は分母(注入した欠陥)が既知で、AI の指摘のうち所在が注入箇所を指すものだけを数える規則も降りている(`assurance-case.md:407`、IMPL-0157)。EV-0062 の差し替え条件は、もともと「注入欠陥の検出率の推移」と「G-7 以降で検出された欠陥」の対応で組まれている(`assurance-case.md:782`)。結論1 はこの組を、算出できる形に直すものである
- IPA 2017 で信頼性に直接つながる段は「上流工程での不具合摘出比率」だった(`research/408-deliberation/council-04-standards.md:201`)〔内〕。ただし IPA のデータは、レビューの記録票が整った開発の集計である。本標準は PR の中の修正を記録させない運用(人数1〜2名の体制、S0)を含む。上流の比率を同じ作法で採ると、記録が整った採用組織と整わない採用組織で値の意味が変わる。比率の形を採らない理由はここにあり、IPA の知見を否定するものではない
- マージ前を3値の1つとして残すのは、PR の中で直さずに台帳へ載せた欠陥(例: 別の Issue へ送った欠陥)の行を、マージ後の検出と取り違えないためである。マージ前の件数は集計に**使わない**。使えば上の非対称が戻る

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `bug.yml` に「検出ゲート」欄を足し、Issue の欄を算出元にする(`metrics.md:182` の文言を事実にする) | Issue は報告の器で、確定の器ではない。PR の中で直した欠陥は Issue にならず、上流の分子の記録率を担保できない。算出元を台帳と Issue の2か所に置くと、G-7 基準2 の母集団と流出の母集団が分かれる |
| 指標を附属書H の観測から外し、候補の一覧に残すだけにする | C9 は「出荷後の欠陥は原因のゲートへ戻る」を主張する。出荷後の欠陥を数える観測を外すと、C9 の崩れを示す観測がポストモーテムの有無だけになる。外すのではなく、規定の記録を引く形に直す |
| 現行の比率(G-7 以降の比率)を残し、上流の分子を PR の採否の記録から機械で数える | 採否の「採用」は欠陥の確定と同じではない(R-2)。正しいが価値の低い指摘も採用される〔外・survey(AutoCommenter)〕。採否の分類を「欠陥 / 改善 / 好み」へ細かく記録させれば分子は締まるが、その記録の欠落を確かめる手段が無く、欠落は値を下流寄りへ偏らせる |
| 指標名を残したまま、算出元の不在を EV マークで開示して運用を続ける | 手続3 が実装前の運用を禁じる(`metrics.md:52`)。EV マークは根拠水準の開示であり、算出できない量を算出できる量に変えない |

### 反論されうる点

- **上流の検出の分布を捨てることになる**(現場・品質監査からの反論が見込まれる)。答え: 捨てるのは「記録の習慣で値が動く上流の分子」であり、上流の働きは注入の検出率で示す。採用組織が上流の記録票を整えた場合に、その記録から比率を自ら測ることを本標準は禁じない(手引きで書く)。ただし規定の附属書の観測には使わない
- **出荷した変更の件数で並べると、変更の粒度で値が動く**。答え: 比率にせず、並べて示すにとどめる。警戒の水準は本標準が定めない。根拠が無いため EV マーク(E0)で開示する
- **件数が少ない体制では値が出ない**。答え: H.7 の「件数が足りない体制では未測定と開示する」(`assurance-case.md:772`)がそのまま掛かる

## R-2 数える母集団

### 結論

1. 本標準に「欠陥」と「報告」を語として置く
   - **報告**: 期待と異なる事象として起票・記録されたもの。起票した者(人・AI・機械)を問わない。`bug.yml` の起票は報告である(`bug.yml:2` の「期待した挙動と異なる」はこちらの定義に当たる)
   - **欠陥**: 報告のうち、要求・受入基準・仕様を満たさず、修復または置換を要すると**確定**したもの
2. 指標(R-1 の2つ)に数えるのは、**確定した欠陥に限る**。報告は数えない
3. 確定の操作的な定義: 台帳の行に、確定した者(**人の氏名**。AI の名義を書かない)と確定した日を記入したこと。AI は行の下書き・重大度の案を作ってよいが、確定した者の欄を書かない。台帳の別表が既に持つ「記録した者は人の氏名。AI の名義を書かない」(`defect-ledger.md:34`)と同じ型を、欠陥の行へ及ぼす
4. 確定した者に、作成を指示した者を**含めてよい**。独立性を求めるのは確定ではなく、**欠陥でないとする処分**の側である(下の理由)。報告を「欠陥でない」と処分した行は消さず、状態に「欠陥でない」と処分の理由と処分した者(人の氏名)を残す
5. 起票の経路(人 / AI / 機械 / 利用者)は台帳の属性として記録する。ただし**集計の母集団の条件にしない**。母集団の条件は確定だけである
6. 未確定の報告は、**統制の母集団には含める**。G-7 基準2 の集約では未確定の行を未解決として数え(重大度は報告の値)、委任の停止では運用の未確定の Sev1・Sev2 の行を停止に数える。**測定は確定に限り、統制は未確定を含める**。2つの母集団の違いを本文に明記する
7. 語「人確定」(自律レベル)は欠陥に使わない。名称は「確定した欠陥」とし、欄名は「確定した者」とする。「人が確定した欠陥」という複合語を規範に置かない

### 理由

- 24765 を引く SWEBOK は、defect を「修復または置換を要する」不備と定義し、anomaly を傘の語とする〔外・survey〕。DRE・DDP・フェーズ yield はいずれも分子・分母の単位を「欠陥」に置く〔外・survey(二次)〕。ただし誤検出・重複・無効の除外を明記した一次資料には届いていない〔未〕。本標準は除外を推定に任せず、確定の記録の有無という**観測できる操作**で母集団を定める
- 確定を人に限るのは、H.4(AI の推定を判定に数えない)、7.7.8 要求事項12(人の確認を経ていない AI の生成物を効果の証拠に数えない)、ADR-0091 決定2 と同じ型である〔内・確〕。これらは判定・証拠・観測を対象とし、測定の母集団には及んでいなかった(内部調査 3.2)。R-1 の指標は附属書H の観測であり、7.7.8 の評価の入力(下流の指標)でもあるため、母集団に未確認の AI の出力が入ると、要求事項12 を間接に破る(内部調査 1.3 の〔推〕)。本件で母集団まで及ぼすのは、既存の原則の適用範囲の穴を埋めることであり、新しい原則の追加ではない
- 業界の実務でも、AI の指摘の真偽は人の判断を真値にして数えている。Meta の JiT テストは AI の候補(weak catch)と人の問い合わせで確定したもの(strong catch)を分け、確定してから数える〔外・survey(原典を確認)〕。Anthropic の Code Review の誤検出率もエンジニアのマークを真値にする〔外・survey〕
- **受理(適用)を確定と同一視しない**。AutoCommenter は正しいが価値の低いコメントが正味で負の価値になりうるとし、CodeRabbit は手動の解決を受理に数えない〔外・survey〕。PR の採否の「採用」をそのまま欠陥の確定にすると、軽微な指摘で件数が増える。結論3 の確定は、台帳の行への記名であり、PR の採否とは別の記録である。R-1 でマージ前を集計に使わないため、PR の採否から台帳への写しを規則として求める必要も無い
- 確定者の独立性: ODC は defect type を通常は修正するプログラマが選ぶ〔外・survey〕。確定は修正の意味の判断を伴い、変更を知る者が最もよく判断できる。さらに、マージ後の欠陥を確定することは作成を指示した者の利益に反する(委任の停止・是正の起動に当たる)。自分の利益に反する確定を独立の者に限る理由は無い。逆に、作成を指示した者が持つ誘因は「欠陥でない」と処分すること、重大度を低く書くことである。だから処分の側を記録に残す。GitHub code scanning が却下の状態に理由を必須とする作法と同じ形である〔外・survey〕
- 処分の側に独立の者の承認まで課すかは、根拠が無い。本標準の他の規定(G-6 の作成を指示した者以外の確認)は承認を対象にし、報告の処分を対象にしていない。処分に独立を課さない判断は根拠水準 E0 で開示し、内部監査の観点(処分の行の抜き取り)で後から見る形にとどめる
- 起票の経路を母集団の条件にしない理由: 起票者が人でも AI の出力を貼っただけのことがあり、AI の起票でも人が確かめれば欠陥である。起票者の区分は真偽と独立で、母集団の条件として妥当でない。属性としては、未確定の報告の滞留を経路ごとに見るため(curl の事例で AI の起票の約 20% が slop、確認された脆弱性は約 5% 〔外・survey〕)と、内部監査で処分の偏りを見るために要る
- 統制の母集団に未確定を含める理由: 未確定の Sev1 の報告を G-7 から落とせば、確かめていない重大な報告を抱えたまま出荷できる。未確定を「無い」と扱うのは ADR-0028(未達と省略の区別)と逆の扱いである。台帳の既存の規則も、AI 起因を「特定できない」行は特定するまで委任を止める(`defect-ledger.md:23`)。未確定の報告も同じく、確かめるまで止める側へ倒す
- 「人確定」は `human-ai-boundary.md:86,385` の自律レベルの語で、変更ごとの関与の水準を指す〔内・確〕。欠陥の確定に同じ語を当てると、「人確定の変更」と「人が確定した欠陥」が混ざる。既存の近い型は PR テンプレートの「確定した者」(`template/.github/PULL_REQUEST_TEMPLATE.md:38,51`)と区分の確定者の記名(`deliverable-templates.md:683`)で、どれも「確定した者 = 人の氏名」の型である。欄名をこの型に揃える

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 区別しない(現行)。報告の件数を数える | AI の起票量で値が動き、確定に要する人の工数も見えなくなる。7.7.8 要求事項12 を間接に破る |
| 起票者の区分(人 / AI)を記録し、両方の値を指標として出す | AI の起票の件数は「採用しない指標」の「AI が生成した…レビューの指摘の件数」(`metrics.md:85`)そのものである。対の指標を指定できない(手続2)。起票者は真偽と独立で、人の起票の値も確定を経なければ母集団として妥当でない |
| 起票者が人のものだけを数える | 起票者の区分は真偽の代理にならない。AI が見つけ人が確かめた欠陥を落とし、AI の出力を人が貼った報告を入れる |
| PR の採否の「採用」を欠陥の確定とする | 受理は確定と同じではない。正しいが価値の低い指摘を数える |
| 確定した者から作成を指示した者を除く | 確定は指示した者の利益に反する方向の記録であり、独立を課す理由が無い。課すと、1〜2名の体制で確定できない欠陥が生じ、統制の母集団(未確定)に滞留する。歪みの源は処分の側にあり、処分を記録に残す |
| 未確定の報告を統制の母集団からも外す | 確かめていない重大な報告を抱えたまま出荷・委任できる。ADR-0028 と逆の扱い |
| 欠陥の定義を 24765 の条番号つきで引用する | 原文を確かめていない〔未〕。定義は本標準の語として書き、SWEBOK 経由の参照点として注記する |

### 反論されうる点

- **AI が未確定の報告を大量に台帳へ書けば、G-7 と委任が止まる**(curl 型の負荷)。答え: 止まるのは確かめるまでで、確かめる工数は報告の量に比例して生じる費用である。区別しない集計はこの費用を隠す。台帳へ行を書く経路を人に限ることは本書では提案しない(AI の自動起票を禁じる根拠が無い)。ただし、報告を台帳の行にする経路を採用組織が持つ場合は、その経路を構成に宣言させる案を起案に委ねる
- **記名だけで確定を満たす形骸化**(#408 起案 `council-01-drafter.md:165` の懸念)。答え: 確定の記名は、測定の母集団に入る条件であり、統制を解く条件ではない。記名を省けば行は未確定として統制に残る。記名を雑に付けた場合に歪むのは指標の値の側で、値は下流の件数であるため、雑な確定は件数を**増やす**向き(悪く見える向き)に働く。水増しで良く見せる経路にはならない
- **処分(欠陥でない)を作成を指示した者が単独でできるのは甘い**。答え: そのとおりで、根拠水準 E0 で開示する。処分の行は消さず、内部監査で抜き取る。独立の承認を課すかは、処分の件数と、後に運用で発覚した欠陥との対応が観測できてから決める

## R-3 工程の帰属

### 結論

1. 確定した欠陥の検出の時点は、**報告が記録された時点の工程**で決める。確定した時点・確定した者のゲートでは決めない
2. 誰が見つけたか(人の層・AI の層・機械の検査・利用者)は、工程ではなく**起票の経路**の属性で記録する(R-2 結論5)。「AI の層の工程」は置かない
3. 検出の時点と、原因のゲート(本来どこで捕まえるべきだったか)を混ぜない。原因のゲートはポストモーテム(C9)と是正の記録が持つ。台帳の検出の時点は、検出された事実の時点だけを書く
4. マージ前に AI の層が見つけて PR の中で直した欠陥は、台帳に載らず、R-1 の集計に入らない。AI の層の働きは 5.6.2 の注入の検出率で示す

### 理由

- ODC では trigger・activity は検出の時点(opener)に付け、ライフサイクルの早期に特定される。defect type は修正の時点(closer)に付ける〔外・survey〕。検出の工程は検証の工程への洞察を与える属性であり、確定の時点とは別の属性である。確定の時点で工程を決めると、トリアージの遅れ(確定までの日数)が工程の分布を下流へずらす
- H.4 は AI の推定による確認を「検出の層」と呼び、ゲートの判定に数えない確認と定める〔内・確〕(`assurance-case.md:314`)。層はゲートの中の確認の種別で、工程ではない。AI の層を工程として独立させると、ゲートの列(G-5〜G-8)と層の列が1つの軸に混ざる
- 原因のゲートを検出の時点と分けるのは、C9 の崩れの観測が「重大な欠陥の流出に原因ゲートの特定が無い」だからである(`assurance-case.md:216`)〔内・確〕。検出の時点の欄に原因のゲートを書かせると、ポストモーテムで特定すべきことを起票の時点で推測させることになる
- 「確定した人のゲートに帰属させる」案は、確定者の所属するゲート(例: 出荷判定者が確定した)で工程が決まる。同じ欠陥でも誰が確定したかで工程が変わり、測定の再現性が無い

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| AI の層を独立の工程として数える | 層とゲートの軸が混ざる。H.4 の定義と矛盾する |
| 確定した者のゲートに帰属させる | 確定者の選び方で工程が変わり、再現性が無い |
| 確定した時点の工程に帰属させる | トリアージの遅れが工程の分布をずらす |
| 原因のゲートで数える | ポストモーテムを経ない欠陥(Sev3 など)は原因のゲートを持たない。検出の時点の集計が成立しない |

### 反論されうる点

- **報告の時点が曖昧な場合**(運用の監視で AI が見つけ、人がマージ後の検証の記録へ写した等)。答え: 台帳の「検出の時点」は3値に粗くしてあり(R-1 結論3)、マージ後・出荷前と運用の境は出荷の記録で機械的に決まる。細かいゲート単位を求めないのは、この曖昧さを値へ持ち込まないためである
- **AI の層の実地の貢献が見えない**。答え: 見せる場所は 5.6.2 の検出率で、実欠陥の件数ではない。実欠陥の件数で AI の層の効果を示すと、7.7.8 要求事項11・12 の示し方の外に出る

## R-4 重大度の2つの定義

### 結論

1. 本件で揃える。**正本は欠陥トリアージ基準の重大度(3段階)とする**。台帳の重大度、流出の指標、是正の起動、委任の停止、G-7 基準2 は、すべてこの段で数える
2. 誤っているのは、インシデント対応の判定基準が**障害の初動の区分に、欠陥の重大度と同じ記号(Sev1〜Sev4)と語(重大度)を使っていること**と、台帳の「運用で発生した Sev1・Sev2(ポストモーテムを書く障害)」(`defect-ledger.md:20`)が2つの段を同じものとして結んでいることである。インシデントの4段階そのもの(初動期限とエスカレーションを決める区分)は、目的が違い、誤りではない
3. インシデント対応の区分は、欠陥の重大度と別の名前と記号へ改める(名前は起案に委ねる。E0〜E3・I1〜I4・P は既存の語と衝突するため避ける)。運用で欠陥が原因の障害が起きた場合は、ポストモーテムで欠陥トリアージ基準により欠陥の重大度を判定し、台帳に行を足す。台帳の括弧書き「(ポストモーテムを書く障害)」は除く
4. 判定者を揃える。**台帳に記録する重大度は、確定した者(人)が記入する**。AI は重大度の案を出してよい(`gate-criteria.md:1876` の「参加させてよい」はこの意味に限ると明記する)。インシデントの初動の区分は、現行どおり当番の人が判定する
5. `bug.yml` の重大度の選択肢の文言を、欠陥トリアージ基準に揃える。現行は Sev1 から「回避策が存在しない」の条件が落ち、Sev2 から「副次機能が停止する」が落ち、Sev3 の語も違う〔内・確〕(`bug.yml:28-38` と `gate-criteria.md:1882-1888`)。起票の時点の重大度は報告の値であり、確定の時点に確定した者が改めてよい

### 理由

- 是正の起動は「出荷後に発覚した欠陥のうち、重大度が Sev1 または Sev2 のもの(後掲『欠陥トリアージ基準』)」と、トリアージ基準の段を明示して引く〔内・確〕(`gate-criteria.md:596`)。G-7 基準2 と台帳の重大度の説明もトリアージ基準の段である(`defect-ledger.md:13`)。正本はすでにトリアージ基準の側にある
- 食い違いは境界で実害を生む。主要機能の障害で回避策が文書化されている場合、トリアージ基準では Sev2(是正の記録が要る、S2 では出荷不可、委任の停止に数える)、インシデント対応では Sev3(ポストモーテム不要、記録のみ)になる〔内・確〕。台帳の括弧書きがインシデントの段を経由して運用の行を足す条件を決めているため、**是正の起動と委任の停止が、インシデントの段で取りこぼされる**。これは計測の問題ではなく統制の欠落であり、本件の母集団の議論と切り離して後回しにできない
- 障害の緊急度(初動の区分)と欠陥の重大度は、業界の実務でも別の概念として扱うのが通例である(本書では特定の規格の条番号を引かない〔未〕)。本標準も重大度と優先度を別の概念として分けている(`gate-criteria.md:1867-1876`)〔内・確〕。同じ記号を2つの段に使うことは、この分離の作法と矛盾する
- 判定者: 台帳の重大度は G-7 の出荷の可否と委任の停止を動かす。AI が重大度を1段下げるだけで S2 の出荷不可が解ける。H.4 の「AI の推定による判定を判定に数えない」に照らし、記録される値は人が記入する。トリアージ基準が AI の参加を許した理由(判定材料が観測可能な事象に限られる)は、案を出す範囲では成り立つので残す

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 本件の範囲外として別 Issue へ送る | 是正の起動と委任の停止の取りこぼしを、流出の母集団の定義と同時に生む。母集団を「確定した Sev1・Sev2」と定めても、どの段の Sev かが2つあるままでは値が揃わない |
| インシデントの4段階を正本にし、トリアージ基準を合わせる | 是正の起動・G-7・台帳・委任の停止がトリアージ基準を引いており、4段階は回避策の有無で Sev2/Sev3 を分けるため「回避策は文書化されていなければ存在しない」(`gate-criteria.md:1890`)の規則と別の境界を持つ。欠陥の重大度としては情報が足りない(データ破損・認証認可の破れの扱いが無い) |
| 2つの段を1つに統合する | 初動期限とエスカレーションは事象の緊急度で決まり、欠陥の技術的な影響と同じ軸ではない。原因が欠陥でない障害(外部依存の停止など)もインシデントの段を要する |
| 対応表(インシデント Sev3 → 欠陥 Sev2 など)で写す | 「一部機能の劣化(回避策あり)」は欠陥の Sev2 にも Sev3 にも当たり、写しが一意に決まらない。ポストモーテムで改めて判定するほうが確実である |

### 反論されうる点

- **インシデントの記号を変えると、運用の現場の呼び方(Sev1 は全停止)と衝突する**。答え: 衝突を避けたいのは本標準の側である。欠陥の重大度は複数の統制を動かす規定の値で、記号の一致は取り違えを招く。障害の区分の記号を残す選択をする場合でも、台帳の括弧書きは必ず除き、ポストモーテムでの判定の規則を足す。この2点は記号の選択と独立に要る
- **改名は本件の議題(AI の起票の区別)から離れる**。答え: 判断軸は信頼性で、取りこぼしの経路が見つかった以上、範囲の外へ送ることを採否の理由にしない

| 起票者の区分(人 / AI)で両方の値を指標にする | AI の指摘の件数は採用しない指標。経路は真偽と独立 |
| PR の採否の「採用」を欠陥の確定とする | 受理は確定と同じではない |
| 確定者から作成を指示した者を除く | 確定は指示した者の利益に反する記録。歪みは処分の側 |
| 未確定の報告を統制の母集団から外す | ADR-0028 と逆の扱い |
| AI の層を独立の工程として数える | H.4 の層とゲートの軸が混ざる |
| 重大度の食い違いを別 Issue へ送る | 是正の起動と委任の停止の取りこぼしが残る |
| インシデントの4段階を欠陥の重大度の正本にする | 是正の起動・G-7・委任の停止がトリアージ基準を引く |
| 処分(欠陥でない)に独立の承認を課す | 根拠が無い。E0 で開示し、内部監査の抜き取りで見る |

### 反論されうる点

- **変更の面が広い**(台帳・集約・委任の判定・インシデント対応・附属書H)。答え: 変更量は採否の理由にしない。面が広いのは、算出元の無い指標を規定が引いていた穴の広さである
- **台帳の欄が増え、1〜2名の体制で記入の負荷が上がる**。答え: 増えるのは確定の記名・日・経路の3欄で、確定は1件ごとに1回である。記入しなければ行は未確定として統制に残るだけで、記載の欠落として差し戻さない設計にできる(起案に委ねる)

## 論点ごとの結論(1行)

- R-1: 検出工程の指標を Issue の欄の比率から「欠陥の台帳に載ったマージ後の確定欠陥の件数(出荷前の検証 / 運用)」へ定義し直し、上流は 5.6.2 の注入の検出率で示す。附属書H は台帳の集計を引き、降りるまで未測定と開示する。`bug.yml` に検出ゲートは足さない
- R-2: 指標の母集団は確定した欠陥(台帳の行に人の確定者を記名)に限る。報告と欠陥を語として分け、起票の経路は属性にとどめる。確定者に指示者を含めてよく、処分(欠陥でない)を記録に残す。統制(G-7・委任の停止)は未確定を含める
- R-3: 報告が記録された時点の工程に帰属させる。AI の層は工程ではなく起票の経路の属性。原因のゲートとは混ぜない
- R-4: 本件で揃える。正本は欠陥トリアージ基準。誤りはインシデントの初動区分が同じ記号を使うことと台帳の括弧書き。台帳の重大度は人が記入し、AI は案まで
- R-5: 新 ADR 1本、EV を3つ新設し EV-0062 の差し替え条件を改める、IMPL を台帳・集約・委任の判定・集計・`bug.yml`・常駐の規則に分けて付ける。採らない案10件を ADR に明記する
