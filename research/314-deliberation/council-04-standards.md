## 総論: 3つの層を混ぜない

外部の枠組みは、次の3つを別の属性として持ちます〔外 F1・F2・F11・F13・F14〕。

| 層 | 外部の例 | 本標準の対応 | 現状の欠け |
| --- | --- | --- | --- |
| 主張(実装されているか) | OSCAL SSP の `implementation-status` | `state` | 「降ろさないと決めた」と「予定」を区別しない(R-4) |
| 方法(何で確かめるか) | 29148 の IADT、800-53A の examine/test | `check` | 方法の要件と証拠の置き場が無い(R-1) |
| 深さ・対象の単位 | 800-53A の depth / coverage | (無い) | 節の単位の検査が `presence` と表示される(R-2) |
| 評価の結果(効いたか) | OSCAL AR の finding、SOC 2 Type II | (無い) | 台帳は運用の有効性を主張しないと書いていない |

本意見書の一貫した主張は、**1つの属性に2つの層の意味を負わせない**ことです。ADR-0061 が `state` と `check` を分けた理由(「1つの値で表すと、強いほうに読まれます」)を、残りの層にも同じく当てはめます。〔判〕

## R-1 検査の強さの分類(`check` の属性)

### 結論

1. `check` は**方法の単一値**として保つ。深さの属性は足さない。代わりに、各値の**適用の要件**を規約で閉じる
2. `machine` には、合否の基準と、陽性(違反で落ちる)・陰性(適合で通る)の対の試験の所在を必須にする。所在は新しい属性 `test=` に書き、検査はその試験ファイルの実在と、試験ファイルが当該の IMPL 番号を含むことを確かめる
3. `presence` は、**規定を担う単位**(欄・キー・行・ファイル)の有無を確かめる場合に限る。規定より粗い単位(節・ファイルの存在だけ)を確かめるものは `presence` と書かず、`manual` とし、`note` に機械が確かめる単位を書く
4. 未分類 100 件は一括で値を付けない。1件ずつ、上の要件に照らして値を決め、`machine` は `test=` を書けたものだけとする。`machine` と書かれた 19 件(内部 2.5)も同じ要件で見直し、試験を示せないものは `presence` か `manual` へ下げる
5. `impl-targets.yaml` の `check`(検査のスクリプト名)は、`checker` へ改名する
6. `test-check-impl.mjs` に、`check` の値が不正なマークで検査が落ちる陽性対照と、`machine` に `test=` を欠くマークで落ちる陽性対照を足す

### 理由

- 外部の通例は、要求ごとに主たる方法を1つ定め、方法と活動を区別する〔外 F2〕。`check` を単一値に保つ ADR-0061 の設計はこれと整合する。見出しを読むのは**活動**であり、規定の**方法**を `machine` や `presence` にしない〔外 F2〕
- 方法の印は検証可能性の証拠にならず、合否の基準を要する〔外 F3〕。`machine` の要件「実行して確かめた」(implementation-marking.md:69)は、記録の置き場が無いため第三者が再現できない。19 件に試験の名が無いこと〔内 2.5〕がその帰結である。Semgrep の ruleid/ok、OPA の許可・拒否の対〔外 F15・F16〕は、`machine` を**操作的に**定義する型を与える
- 試験ファイルが IMPL 番号を含むことの検査は、DO-178C の「要求に基づく試験」から試験へ辿れることの最小形である〔外 F7〕〔判〕。試験の中身が規定を実現しているかは機械で確かめられない。そこは限界の表へ書く
- `presence` の定義「記録・欄・ファイル・キーの有無」は、**規定を担う単位**を前提にしている。節の見出しの有無で行の規則を `presence` とするのは、800-53A の語で範囲(coverage)を偽ることに当たる〔外 F13〕〔自: implementation-marking.md:63〕
- 深さの属性を足さない理由: 本標準の3値は、800-53A の方法と深さの組のうち実際に使う組を既に序列で表している(`presence` ≒ examine/Review/Basic、`machine` ≒ test/Focused 以上)。属性を増やすと、深さと方法の組み合わせの多くが空になり、値の一致を第三者が判定する手順が増えるだけになる。浅さは上の3の要件(単位の閉じ方)で `presence` から締め出せる〔判〕
- 語の衝突: 台帳の列「検査のスクリプト」(19件)とマークの `check` が同じ語で別の意味を持つ〔内 1.3〕。規格の語彙は1語1義が原則である〔判〕

### 落とす案

| 案 | 落とす理由 |
| --- | --- |
| 深さ(depth)・範囲(coverage)の属性を足す | 上記。値の組の多くが空になり、判定の一致の手順を増やす。単位の要件で同じ効果が得られる |
| `machine` の真偽を note の自由記述に任せる(現状) | 記録の置き場が無く、第三者が再現できない。19 件の実例がある |
| 未分類を、降ろし先の検査スクリプトの有無から機械的に一括で分類する | スクリプトが在ることは、それが当該の規定を検査することを示さない(内部 1.2 の通り、`check-impl.mjs` は中身を見ない)。活動と方法の混同になる |
| `presence` を「節の単位」まで含むよう定義を緩める | 台帳の読み手は `presence` を「規定の有無を機械が見ている」と読む。ADR-0061 のコンテキストが挙げた「強いほうに読まれる」問題の再演になる |
| 評価の結果(違反を実際に止めた件数)の欄を今回足す | 本標準は運用の有効性(SOC 2 Type II 相当)を台帳で主張していない。欄を足す前に、主張しないことを明記するほうが先である(下の文の案) |

### 文の案(implementation-marking.md「検査の手段」へ)

- `check=machine` を書くのは、機械が規定の中身を検査し、違反を入れた入力で失敗すること、および適合する入力で通過することを、試験で確かめた規定に限る
- `check=machine` のマークには、`test=` に試験のファイルの所在を書く。試験のファイルは、当該のマークの識別子を含む
- `check=presence` を書くのは、規定を担う単位(欄・キー・行・ファイル)の有無を機械が確かめる規定に限る。規定より粗い単位(節の見出し、ファイルの存在)だけを確かめる規定は `check=manual` と書き、機械が確かめる単位を `note` に書く

本文(ですます調)。

> 台帳の `check` は、機械が確かめる方法を示します。規定が運用の中で守られていることは示しません。違反を実際に止めた件数は、台帳の対象の外です。

### 矛盾の確認

- ADR-0061 決定2「`check=machine` と書くのは…実行して確かめた規定に限ります」を具体化するもので、矛盾しない。ただし `test=` の新設と `presence` の単位の要件は ADR-0061 に無い決定のため、**新しい ADR**で定める(ADR-0061 の本文は書き換えない)
- ADR-0061 影響「`check=machine` の真偽を、機械は確かめない」は、`test=` の実在と識別子の照合によって**一部**が機械へ移る。新 ADR で「試験の中身が規定を実現していることは、なお機械は確かめない」と書けば、矛盾しない
- ADR-0061 決定3(既存の棚卸しは今回行わない)は、別の作業として残した棚卸しを本 Issue で行うことであり、矛盾しない

## R-2 `claude-md` の常駐の規則の検査

### 結論

1. 常駐の規則の行ごとの照合(内部 3.4 の案 A)を採る。`claude-md-resident.json` に、節ごとではなく**規則ごと**の照合の鍵(正規化した部分文字列)を持たせ、行の欠落を `absent` として落とす
2. 照合の検査には変異の試験を付ける。一覧の各鍵について、その行を消した `CLAUDE.md` で検査が落ちることを試験で確かめる
3. 行ごとの照合が入っても、値は `presence` とする(文がそこに在ることの確認であり、AI が従うことの確認ではない)。入るまでの間、節の単位しか確かめない 12 件と、既に `presence` と書かれた 6 件(0146, 0153, 0154, 0158, 0185, 0251)は `manual` とし、`note` に「節の見出しと本文の有無だけを機械が確かめる」と書く
4. 規則を生成区間へ移す案(案 C)は、本 Issue では採らない

### 理由

- 規定を担う単位は行である(テンプレートの CLAUDE.md 自体が「1行が1つの規則」と書く)〔自: template/CLAUDE.md 冒頭〕。節の見出しの有無は、R-1 の要件 3 により `presence` に当たらない
- 内部調査がコードから示した通り、行を消しても、本文を1行の `x` に替えても検査は通る〔内 3.2〕。規約の `presence` の定義より弱い検査が `presence` と表示されている〔内 3.3〕
- 照合の鍵の一覧は**閉じた集合**であり、変異の試験(各鍵を消すと落ちる)で検出力を全数確かめられる〔外 F25・F26〕。外部の CLAUDE.md の lint は参照先の実在と矛盾までで、規範の一覧からの網羅を検査しない〔外 F23〕。行ごとの照合は、この点で外部の慣行より一段強い追跡になる〔判〕
- 規則の文を AI が守るかは、文の存在の検査で示せない〔外 F22・F24〕。値を `machine` にしない理由である

## R-3 G-5 基準6(文脈ファイルの形式検査)

### 結論

1. 基準6 を2つの規定に分け、実装マークも2つにする(参照切れ / 分量の上限)。IMPL-0269 は分割する(番号は再利用しない。0104 の分割と同じ扱い)
2. **参照切れ**の検査をテンプレートの G-5 へ降ろし、集約の `needs` へ入れる。検査の前に、「参照」と「リポジトリ内」の定義を本文で閉じる
3. **分量の上限**は、3.11.4 要求事項1 の値が定まるまで降ろさない。`state=undelivered` のまま、R-4 の扱い(予定・Issue つき)にする
4. `gate-criteria.md:460` の文は、参照切れの検査が降りるまでの間、参照切れも降りていないと書くよう直す。これは R-3 の採否に依らず直す

### 理由

- 29148 の要求の特性(検証可能)の型に照らすと、「参照切れ 0 件」は合否の基準が書けるが、対象(どのファイルの、どの形の参照か)が本文に定まっていない〔自: gate-criteria.md:454〕。対象を閉じないまま検査を作ると、テンプレートが事実上の正本になる(implementation-marking.md「逆流」)〔判〕
- 参照切れは決定的に判定でき、是正の起動の3条件(実効的な偽陽性が無い・修正できる・既存の違反を解消してある)を満たしやすい種類の検査である〔自: gate-criteria.md:464〕〔判〕
- 分量の上限は値そのものが決まっていない(IMPL-0222)。値の無い基準を検査に降ろすと、テンプレートが値を決めることになる
- 現行の 460 行の文は、分量だけを「降りていない」と書き、参照切れに触れない。基準のうち降りていない範囲を読み手が過小に読む。未達の開示が不正確なことは、ADR-0028 の「未達と省略の区別」の前提を崩す〔判〕
- 「マークは規定ごとに付ける。1つのマークで節の規定がすべて済んだと扱わない」(implementation-marking.md)に照らし、2つの判定基準を1つのマークで追う現状は規約に合わない〔自〕

## R-4 降りていない規定の扱い(順序・降ろさない決定)

### 結論

1. `state` の値は増やさない。降りていない規定の**処置**を、別の属性 `plan=` で示す。値は閉じた語彙 `issue`(降ろす予定)と `declined`(テンプレートには降ろさないと決めた)の2つ。`state=undelivered` のマークだけが使える
2. `plan=issue` には Issue の番号(`issue=#NNN`)を必須とする。`plan=declined` には決定の所在(ADR の番号か審議の記録)と見直しの年月を必須とする。検査は ADR の実在と書式を確かめる
3. `plan` を欠く `undelivered` は「処置未定」として台帳の冒頭に件数を出す。検査は落とさない(ADR-0061 の未分類と同じ扱い)
4. **`declined` は「課さない」ではない**。本標準の規定は採用者に課したまま、準拠テンプレートが実装を持たないことだけを示す。台帳の表示は「本標準は課す。テンプレートは実装しない。採用者が実装する」とする
5. 降ろす順序の基準は定める。ただし期日の日数は定めない。順序の基準は根拠水準 E1 以下として EV でマークする
6. 名指しの4件: 0116・0117 は本 Issue で降ろす(0116 は書面の合意の中身を機械で確かめられないため上限は `presence`)。0118 は構成の表現(データ形式)を変えるため別の Issue へ送り `plan=issue` とする。0120 は note を 1.10.2 の現行に合わせて直し、`plan=issue`(#354)とする

### 理由

- OSCAL は「計画(期日つき)」「代替」「適用しない(理由つき)」を未実装と区別して持つ〔外 F10〕。NASA SWE-125 は適用外の正当化を第三者が点検する〔外 F6〕。IEC 61508 は推奨技法を使わない理由の詳述を求める〔外 F8〕。本標準のコアポリシー「書かれていない」と「課さないと決めた」の区別は、これらと同型であり、台帳だけがこの区別を持たない〔外 F32〕
- `state` に値を足さない理由: ADR-0061 は3つ目の値を「届いたかどうかと、何が確かめるかは直交する」として退けた。処置(予定か、降ろさないか)は、届いていないことを前提とする**従属の属性**であり、`state` の軸と別に持つほうが ADR-0061 の論理と一貫する。OSCAL が1つの列挙に入れているのは、OSCAL の `implemented` が本標準の `delivered` + `check` の両方を負うためで、そのまま写すと ADR-0061 の分離を崩す〔判〕
- `declined` と「課さない」を分ける理由: 準拠テンプレートは参照実装であり、規格の適合の範囲そのものではない。テンプレートが実装しないことを「規定が無い」と読ませると、内部の定型文(「案件からは『規定がない』ものとして扱われます」)の害を、決定の形で固定してしまう。外部でも、是正しないリスクは承認されたリスク受容として是正の項目と別に記録し、項目を消さない〔外 F29・F30〕
- 期日の日数を定めない理由: GSA・FedRAMP の期限は脆弱性の重大度に対するもので、統制の実装の順序を定めた規範は見つかっていない〔外 F29・F30、5章〕。値を写すと根拠の無い数値になる。代わりに Issue への結線と見直しの年月で、TBD の放置を防ぐ(GSA の「TBD は1四半期まで」の趣旨)〔外 F29〕
- 順序の基準を定める理由: CMMC は未達のまま認証を得てはならない要求を名指しで固定する〔外 F31〕。本標準にも、テンプレートが降ろさないまま放置してはならない規定がある(第5章 5.8.3 の一律で委譲できない領域、停止の申し立て、統制の弱化の検出)。これらを `declined` にできないと定める〔判〕
- 0116: 書面の合意は中身を機械で確かめられない〔内 5.1〕。欄の有無の確認(`presence`)が上限であると開示したうえで降ろせる。0117: 名簿の欄と集約の件数で降ろせる〔内 5.1〕。0118: 制限中の範囲を構成で表すことは、構成のデータ形式の変更である(テンプレートの CLAUDE.md「人へ戻す3つの場合」(b) に当たる)。方法の議題のこの会議で決めない〔判〕。0120: note が #313 の後の 1.10.2 に追いついていない〔内 2.6 #11〕。事実と違う表示は採否に依らず直す

### 落とす案

| 案 | 落とす理由 |
| --- | --- |
| `state` に `declined`(または `not-applicable`)を足す | ADR-0061 が退けた形であり、処置は `state` に従属する属性である。軸を混ぜる |

## R-5 スキルの文の検査(ADR-0064)の範囲

### 結論

1. 検査は**追跡の検査**(文から本標準の所在へ辿れるかの検査)であると明記し、遵守の検査として扱わない。台帳・規約の表示で、方法は inspection、確かめる単位は「印と所在の実在」と書く
2. 範囲は**正規表現を広げる形では**広げない。依頼の形「〜しないでください」(9 行)は、スキルの側を要求・禁止の文末へ書き直し、現行の検査の対象に入れる(内部 6.3 の案 B)
3. 太字の否定・平叙の否定(約 48 行)は、本 Issue では対象の外のまま残し、限界の表に件数とともに書く
4. スキルの遵守の評価(複数回の試行による挙動の評価)は、CI の検査として**課さない**と明記する
5. 「印と所在の検査がスキルと本標準の食い違いを減らす」という前提に、根拠水準マークを付ける(E0)

### 理由

- 文の構造の検査と効き目の相関は弱い(ρ=0.14)〔外 F22〕。エージェントがルールファイルを読む率も低い〔外 F24〕。この検査は遵守を示さず、DO-178C の型でいえば追跡の検査である〔外 F7〕。追跡の検査として正しく名乗れば、過大な主張にならない〔外 F13〕
- ADR-0063 は、本文と規定の附属書の依頼の形(14件)を書き直して廃した〔自: ADR-0063:112〕。スキルの規則が依頼の形で残るのは、本標準の語の方針と食い違う。書き直せば、検査の正規表現を変えずに対象へ入る。正規表現を広げると、文末で作る一覧が閉じない問題(implementation-marking.md「文末で作る一覧は閉じず」)を広げるだけになる〔判〕
- 太字の否定は、説明文と規則が混ざっており、機械で分けられない〔内 6.2〕。登録簿で誤検出を消す運用は、範囲の判定を人の登録へ移すだけで、検証の一貫性を上げない〔判〕
- 挙動の評価は非決定的で、複数回の試行と信頼性の指標を要する〔外 F21〕。決定的な CI の検査とは別の層であり、方法も確立していない(外部の根拠は単一の個人報告と査読前の1研究〔外 F21・F22〕)。課すと決めるだけの根拠が無い。却下を明記する

### 落とす案

| 案 | 落とす理由 |
| --- | --- |
| A. 対象の文末を正規表現で広げる | 説明文と規則を文末で分けられず、一覧が閉じない。ADR-0063 が廃した依頼の形を、検査が正規の形として認めることになる |
| C. 太字・箇条書きの構造で拾う | 誤検出の登録簿が要り、範囲の判定が人の登録に移る。検証の一貫性を上げない |
| D. 現状を維持する | 依頼の形の禁止 9 行は、書き直せば対象に入る。検出できるものを放置する |
| スキルの挙動の評価(pass@k / pass^k)を CI に課す | 非決定的で、決定的な検査の層に置けない。方法の根拠が単一事例と査読前の研究にとどまる |

### 文の案(implementation-marking.md「検査の限界」の表の直後へ)

本文(ですます調)。

> スキルの文の検査は、文から本標準の所在へ辿れることを確かめる追跡の検査です。AI の担い手がその文に従うことは確かめません。本標準は、スキルの文に従うことの評価を、CI の検査として課しません。挙動が試行ごとに揺れ、決定的な検査として合否を出せないためです。

限界の表の行の案。
