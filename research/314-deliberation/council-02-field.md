## R-1 検査の強さの分類(`check` の属性)

### 結論

1. 未分類 100 件は、**降ろし先の検査スクリプトの単位で**まとめて分類する(aggregate-evidence 45・verify-gate-contract 17・check-process-rules 15・check-d0 5・登録なし 18。内部 2.3)
2. 分類の確からしさは**非対称に**求める。`manual` と `presence` は弱い側の主張なので、1名の分類で足りる。`machine` だけに裏づけを課す
3. `machine` の要件を規約に定める。(a) 試験のファイルを属性 `test=` で名指す、(b) その試験がテンプレートの CI に結線されている、(c) 試験が「違反の入力で落ちる」(陽性)と「テンプレートそのものは通る」(陰性)の両方を含む。(a)(b) は `check-impl.mjs` が機械で確かめる
4. 深さの属性は足さない。浅さは、`presence` の定義の適用を正すこと(R-2)と、`note` に「確かめる単位」を書くことで表す
5. `impl-targets.yaml` の `check`(検査のスクリプト名)は `checker` へ改名する
6. `machine` のうち試験の名が `note` に無い 19 件(内部 2.5)は、上の (a)〜(c) で再確認する。試験が見つからないものは `presence` か `manual` へ下げる

### 理由

- 強さの過大表示が起きるのは `machine` だけです。`presence` や `manual` を誤って付けても、読み手は「機械は中身を見ていない」と受け取り、自分で確かめる側へ倒れます。誤りの向きが安全側です。全件に2名の独立の分類を課すと、#324 の残り 857 節と合わせて現場では回りません。回らない手続は形骸化し、信頼性を下げます
- 検査の強さは、マークの1件ずつの性質というより**検査スクリプトの性質**です。`aggregate-evidence.mjs` が有無だけを見る項目と中身を見る項目は、スクリプトを1回読めば仕分けられます。マークを番号順に1件ずつ見るより、見落としが減ります
- 外部 F3(合否の基準が要る)・F15/F16(OPA・Semgrep は陽性と陰性の対で規則を試験する)が `machine` の要件の型を与えます。現場の目で付け加えると、**陰性の対(誤検出しないこと)は、テンプレートそのものが CI を通ることで既に毎回確かめられています**。新たに陰性の固定入力を全件に用意させる必要はなく、「テンプレートが通る」を陰性として数えると明記すれば足ります
- `test=` を機械が確かめる理由: 規約(implementation-marking.md:69)の「実行して確かめた」は、確かめた記録の置き場を定めていません(内部 2.5)。ADR-0061 の影響は「`check=machine` の真偽を機械は確かめない」と認めています。ファイルの実在と CI への結線なら、`gate-g5.yml` を読むだけで機械が確かめられます(自分で確かめた。試験は `- run: node scripts/gate/test-*.mjs` の形で列挙されている)。試験の中身が規定を確かめているかは機械では分かりませんが、「名指した試験が存在しない・CI で動かない」という最も多い腐り方は止まります
- `impl-targets.yaml` の語の衝突は、保守する側が実際に読み違える種類の衝突です。台帳の列「検査のスクリプト」とマークの `check` が同じ語のままだと、`check=machine` を「スクリプトが登録されている」と読む人が出ます

### 他の案を落とす理由

- **深さの属性(SP 800-53A の depth/coverage。外部 F13)を足す案**: 落とす。3つ目の軸は、付ける人ごとに解釈が割れます。800-53A の深さは評価者が評価の計画に書くもので、実装者が1行ずつ自己申告するものではありません。本標準の問題(見出しの有無を `presence` と書いた)は、深さの軸が無いことではなく、`presence` の定義「記録・欄・ファイル・キーの有無」に照らして既に誤っていることです(内部 3.3)。定義の適用を正せば足ります
- **全件の変異試験(外部 F25)**: 落とす。304 件の規定と降ろし先の組に変異を掛ける仕組みは、作る手間に比べて捕まえるものが少ないです。陽性対照そのものが「違反を作り込んだ入力」であり、変異試験の要点(規則を壊すと検査が落ちる)は陽性の試験で既に満たされます。外部 F26(Google)も差分に絞って初めて実用になったと述べています。例外は R-2 の常駐の規則で、そこでは自動の変異が安く作れるため採ります
- **2名の独立の分類を全件に課す案**: 落とす(上の理由)。`machine` への格上げに限って、分類した者と別の者が `test=` の試験を読む、は採ってよいです

### 文の案(`community/implementation-marking.md` の「検査の手段」の箇条へ)

- `check=machine` には、属性 `test` に試験のファイルを書く。試験は、規定に反する入力で検査が失敗することを確かめるものとする。違反の無い入力で失敗しないことは、テンプレートそのものが検査を通ることで確かめたものとして数える
- `test` に書いた試験は、テンプレートの CI に結線されていなければならない。検査は、ファイルの実在と結線を確かめる。試験の中身が規定を確かめているかは確かめない
- `check` の値は、降ろし先の検査スクリプトが規定の中身を確かめる範囲で決める。節や見出しの有無だけを確かめる検査は、規定の行の有無を確かめないため、`presence` と書かない

本文(ですます調)の注記の案: 「`machine` と書いた規定だけに、試験の名を求めます。`presence` と `manual` は、機械が中身を見ていないことを示す弱い側の主張であり、誤って付けても読み手は自ら確かめる側へ倒れるためです。」

### 既存の ADR・条項との矛盾

- ADR-0061 決定2「`check=machine` と書くのは、機械が違反を検出することを実行して確かめた規定に限る」を具体化するもので、矛盾しない。ただし `test` 属性の追加と `impl-targets.yaml` の改名は、ADR-0061 の本文を書き換えずに**新しい ADR で足す**必要がある
- ADR-0061 決定3(棚卸しは今回行わない)は「別の作業とする」と送っており、本 Issue がその別の作業に当たる。矛盾しない

## R-2 `claude-md` の常駐の規則の検査

### 結論

1. **行の単位の検査を足す**。常駐の規則の一覧(`claude-md-resident.json`)に、テンプレートの `CLAUDE.md` から生成した**規則の行**(正規化した文)を節ごとに持たせ、案件の `CLAUDE.md` の同じ節にその行があることを確かめる。案件が足した行は妨げない
2. 対象は、実装マーク(`target=claude-md`)が指す規則の行に限る。規則の索引のすべての行は対象にしない
3. 一覧を生成する `--write-resident` の中で、行を1つずつ消した `CLAUDE.md` を作り、検査が落ちることを確かめる試験を自動で回す(安い変異試験)
4. 行の単位の検査が入るまで、`claude-md` の常駐の規則のマーク(未分類 12 件と `presence` 6 件)は `manual` と書き直す

### 理由

- 現場で起きる事故は「案件が既存の `CLAUDE.md` に節を写し、その中の行を自分の流儀に合わせて削った・弱めた」です。`template/README.md:44` は、既存の内容を残して節を含める持ち込み方を定めています。この持ち込みの場面こそ、見出しだけを残して行が欠ける経路であり、現在の検査は通します(内部 3.2。本文を `x` の1行にしても通る)
- 行の照合の誤検出を見積もります。案件が規則の行の文言を変える正当な理由は、ほとんどありません。規則の文言を変えることは標準の規定の書き換えであり、テーラリングの経路(`/process-change` と第8章)を経るべきものです。文言の変更で検査が落ちるのは、誤検出ではなく**真の検出**です
- 誤検出として残るのは、(i) 空白・表の区切り・強調の記号の差、(ii) テンプレートの版を上げたときに案件の行が古い、の2つです。(i) は正規化(空白の圧縮、`**` と表の `|` の除去)で消せます。(ii) は誤検出ではなく、新しい版の規則が案件へ届いていないことの検出で、まさに捕まえたい場面です。失敗の文に、テンプレートの該当の行をそのまま出せば、直す手間は貼り付け1回です
- 保守の手間: 照合の文字列を人が手で管理すると必ず腐ります。一覧はすでに `--write-resident` でテンプレートから生成し、`test-init-g5.mjs` が一致を確かめています(内部 3.1、claude-md-resident.mjs 冒頭注記)。行も同じ生成に載せれば、手で保守するものは増えません
- 対象をマークのある行に限る理由: 索引の全行を照合すると、テンプレート独自の補足(コマンドの例、所在の案内)の変更でも案件の CI が落ちます。標準の規定を運ぶ行だけが、案件で消えては困る行です

### 他の案を落とす理由

- **C. 規則を生成区間へ移し、全文一致に置く**(内部 3.4): 落とす。生成区間は「手で編集しない」区間です。常駐の規則まで入れると、案件が規則の近くに自分の補足を書く場所が無くなり、案件は `CLAUDE.md` の別の場所や別のファイルへ規則を書き直します。規則が二重になり、片方だけが更新される事故が増えます
- **規則ごとの照合の鍵(短い部分文字列)を人が選ぶ案**: 落とす。鍵を残して否定を外す(「〜しない」を「なるべく〜しない」にする)と通ってしまいます。人が選んだ鍵は版ごとに保守が要ります。行の全文の正規化照合のほうが、捕まえる範囲が広く、保守が自動です
- **D. 現状維持で `presence` と開示する**: 落とす。見出しの有無は、規約の `presence` の定義(記録・欄・ファイル・キーの有無)より弱く、`presence` と書くこと自体が過大表示です(内部 3.3)。現状維持なら少なくとも `manual` です
- **B. `presence` より弱い新しい値を足す**: 落とす。値を増やすより、検査を行の単位に強めて `presence` を正しく名乗るほうが、読み手の語彙が増えません

### 文の案

`community/implementation-marking.md` の「検査の手段」の箇条へ:

- 降ろし先が `CLAUDE.md` の常駐の規則であるマークは、規則の行の有無を機械が確かめる場合に限り `presence` と書く。節の見出しと本文の有無だけを確かめる場合は `manual` と書く

テンプレートの `claude-md-resident.mjs` の冒頭注記(ですます調)の案: 「実装マークが指す規則の行は、テンプレートの文を正規化して照合します。案件が行を足すことは妨げません。規則の行の文言を変えると失敗します。文言を変えることは標準の規定の書き換えであり、`/process-change` を経ます。」

### 既存の ADR・条項との矛盾

- ADR-0061 との矛盾は無い(値を増やさない)。`impl-targets.yaml:190-195` の `claude-md-resident` の説明「節の中の個々の行の有無は確かめない」は改める
- 第8章のテーラリングで、案件が `CLAUDE.md` の規則の文言を言い換えることを認めた記述があれば衝突する。私はそのような記述を見つけていない(全文は読んでいない。突合の担当へ依頼する)

## R-3 G-5 基準6(文脈ファイルの形式検査)

### 結論

1. **参照切れの検査を、テンプレートの G-5 に今回実装する**。対象は文脈ファイル(`CLAUDE.md`、`context/**`、`.claude/**/*.md`)の Markdown の相対リンクのファイルの実在。ジョブを集約の `needs` へ入れる
2. 見出しへのアンカー(`#...`)とバッククォートの中の経路は、失敗にしない。前者は対象の外と明記し、後者は件数を通知に出すだけにする
3. 分量の上限は**降ろさないまま**とし、`gate-criteria.md:460` を「分量の上限は降りていない。参照切れは降りている」と正確に書き直す。上限の値は 3.11.4(IMPL-0222)の決定を待つ
4. IMPL-0269 を2つに分ける(参照切れ = delivered/machine、分量 = undelivered/manual)

### 理由

- 参照切れは、エージェントが規則の詳細を読みに行った先が無い、という実害のある故障です。CLAUDE.md は「規則の索引」で、詳細は行末の所在にあると自ら述べています。所在が切れると、規則は「推測で補わないでください」と言いながら補うしかなくなります
- 相対リンクのファイルの実在は、決定的で誤検出の少ない検査です。外部 F23 の lint 群も、ここまでは確立した手法です
- アンカーを失敗にしない理由: 日本語の見出しの slug は描画系ごとに異なり(GitHub と Starlight で違う)、誤検出が多発します。誤検出に慣れた案件は基準6 のジョブを必須から外したくなり、`gate-criteria.md:468`(判定基準を実装する検査を必須の集約から外して基準を外してはならない)と正面から衝突します。誤検出の多い検査を入れることが、基準を守らせない誘因になります
- バッククォートの経路を失敗にしない理由: テンプレートの文には `feature/<機能ID>-task-<N>` のような型の例が多く、実在の経路と区別できません
- 分量の上限を今は失敗にしない理由: 上限の値の根拠は RC-07 の目安(200 行・6,000 トークン)だけで、再評価の登録はあっても実証がありません(内部 4.3)。根拠の無い値で CI を落とすと、案件は値を緩めるか分割を形だけ行います。どちらも信頼性を上げません

### 他の案を落とす理由

- **A. 両方を今実装する**: 分量の側を落とす(上の理由)。値を定めてから降ろす
- **C. 何も降ろさず開示を続ける**: 落とす。参照切れの検査は安く、誤検出が少なく、捕まえるものに実害があります。開示を続けるだけの理由がありません
- **D. 基準6 そのものを見直す**: 本 Issue では落とす。参照切れは基準として妥当です。分量の上限の妥当性は 3.11.4 の審議の論点です

### 文の案(`gate-criteria.md:460` の差し替え。ですます調)

「基準6 のうち、リポジトリ内の参照切れは、準拠テンプレートの G-5 が文脈ファイルの相対リンクのファイルの実在を確かめます。見出しへのアンカーの切れは確かめません。分量の上限は、上限の値(第3章 3.11.4)が定まっていないため、準拠テンプレートへ降りていません。」

### 既存の ADR・条項との矛盾

- `gate-criteria.md:454`(参照切れ 0 件)は「参照切れ」の範囲を定めていない。アンカーを対象の外とすることが基準の縮小に当たるかは、突合で決める必要がある。私はアンカーを含めて基準を満たしたと主張しないこと(対象の外と明記すること)で、縮小ではなく開示だと考える
- テンプレートの `g5-aggregate.mjs:124` の注意と `G-5.md:15` の行は、参照切れの側について改める

## R-4 降りていない規定の扱い(順序・降ろさない決定)

### 結論

1. `state` は2値のまま。**新しい属性 `plan` を足す**。値は `planned`(降ろす。追う Issue 番号を必須)と `declined`(降ろさないと決めた。決めた ADR か会議体の記録の所在を必須)。`state=undelivered` のときだけ書ける
2. 期日は課さない。代わりに見直しの年月(`review=YYYY-MM`)を必須にし、過ぎたものを台帳の冒頭に件数で出す(合否には使わない)
3. 順序の基準は3段: (i) 統制の弱化・一律で委譲できない領域・停止の申し立て・承認者の数に関わる規定、(ii) 出荷判定の証跡の集約の根拠になる規定、(iii) その他。(i) は `declined` にできない
4. 名指しの4件: IMPL-0120 の `note` を #313 後の 1.10.2 に合わせて今回直す。IMPL-0118 は (i) に当たり、本 Issue から専用の Issue を切って最初に降ろす。IMPL-0116・0117 は構成の欄の設計が要るため、それぞれ Issue を切って `plan=planned` とする。IMPL-0291 は #348 へ
5. 降ろし先の検討の重なり(#325・#333・#348・#349・#351・#354)は、その Issue 番号を `plan=planned` の追う先に書いて割り振る

### 理由

- 現場が台帳を読むとき知りたいのは「この規定はいずれ来るのか、来ないから自分で手当てするのか」です。今の `undelivered` はこの2つを区別しません(外部 F6・F10・F32)。区別が無いと、案件は全件を「いずれ来る」と読んで手当てを先送りします
- `state` に値を足さない理由: ADR-0061 の「検討した選択肢」は、`state` に3つ目の値を足す案を「届いたかと何が確かめるかは直交する」として落としています。「降ろすか降ろさないか」も、届いたかどうかとは別の軸です。別の属性で持つことが、ADR-0061 の論理と整合します(自分で確かめた)
- 期日を課さない理由: GSA・FedRAMP の期限(外部 F29・F30)は脆弱性の是正で、是正の要員が契約で確保されている組織の規範です。本標準の降ろし先の実装は保守者の手の空き次第で、期日を書いても守られません。守られない期日が並んだ台帳は、期日そのものを誰も読まなくなります。EV マークと同じ「見直しの年月」なら、過ぎたことを機械が件数で出せ、再判断の時点を強制できます。外部 F29 の「TBD は1四半期まで」の趣旨(未定のまま放置しない)は、見直しの年月で満たします
- (i) を `declined` にできない理由: 外部 F31(CMMC が POA&M に載せられない要求を名指しで固定する)。これらは、降りていないと AI の担い手が緩める向きへ動けてしまう規定で、案件が自前で手当てしない限り事故に直結します。降ろさないと決める余地を残すと、「手が回らない」で降ろさない決定が通ります
- IMPL-0118 を最初に置く理由: 7.9.2 の2名必須の制限中に、集約が承認者の数を上げないため、1名の承認で出荷の証跡が欠落なしになります(内部 5.1)。承認者の数は出荷判定の成立そのものに関わり、(i) と (ii) の両方に当たります
- 名指しの4件を本 Issue で実装しない理由: 0116・0117・0118 はいずれも `process.config.json` の欄の新設を伴い、契約検査と `/process-change` の経路に波及します。棚卸しの Issue の中で構成の設計を決めると、構成の設計の審議(調査・会議体)を経ないまま欄が入ります。変更量を嫌う理由ではなく、設計の審議を飛ばさない理由です

### 他の案を落とす理由

- **`state` に値を足す**: 落とす(上の理由。ADR-0061 の採らなかった理由と同じ論理)
- **`note` に「降ろさない」と書くだけ**: 落とす。自由文は機械が数えられず、台帳で「予定」と「決定」を分けて出せません
- **重大度ごとの期限**: 落とす(上の理由)。根拠水準マークで扱う種類の値でもあります(実証の無い期間)
- **順序を「難しさの低いもの」から**: 落とす。安さは採否の理由になりません。結果として claude-md の 10 件は安く、(i) に当たるものも多いため早く降りますが、それは (i) に当たるからです

### 文の案(`community/implementation-marking.md` の「降りていない規定の扱い」へ)

- `state=undelivered` のマークには、属性 `plan` を書く。値は `planned`(降ろす)と `declined`(降ろさないと決めた)とする
- `plan=planned` には、追う Issue の番号を `note` に書く。`plan=declined` には、決めた記録(ADR または会議体の決定)の所在を書く
- `plan` を書いたマークには、見直しの年月を属性 `review` に書く。見直しの年月を過ぎたマークの件数を、台帳の冒頭に出す。この件数を合否に使わない
- 統制を緩める向きの決定、一律で AI に委譲できない領域、停止の申し立て、承認者の数に関わる規定は、`plan=declined` にできない
- `plan=declined` のマークも削除しない。降りていない事実を表示し続ける

本文の案(ですます調): 「`declined` は、本標準がその規定を課さないと決めたことを意味しません。規定は案件に課されたままで、準拠テンプレートが実装を持たないと決めたことを意味します。案件は、その規定を自ら手当てします。」

### 既存の ADR・条項との矛盾

- ADR-0061「`state` は2値のまま」と整合する。属性の追加は新しい ADR で決める
- implementation-marking.md:89-95(削除しない・件数を合否に使わない)・EV-0136 と整合する。見直し超過の件数も合否に使わないため、EV-0136 の趣旨(件数を目標にしない)と衝突しない
- `declined` の規定を案件が自ら手当てする、という読みは、第1章の適用の表明(1.10.2。未達の件数を併記する)と関係する。`declined` を表明の未達の件数に数えるかは、突合で決める必要がある(私は数えるべきと考える)

## R-5 スキルの文の検査(ADR-0064)の範囲

### 結論

1. 検査の正規表現は広げない
2. 「〜しないでください」の 9 行は、要求・禁止の文末へ**書き直して**現行の検査の対象に入れる(内部 6.3 の B)
3. 太字の否定 約 48 行は、検査の対象に入れない。規則であるものを人が選び、書き直す作業を、#316(規定の表現形式の残り)へ送る
4. 検査の名と台帳の表示を「文の所在の追跡」とし、遵守を確かめるものではないと規約に明記する。根拠水準マークを付ける

### 理由

- 正規表現を「〜しない」「〜ない。」へ広げると、説明文(「この検査は個々の行を確かめません」)が大量に掛かります。誤検出を除くための登録簿が必要になり、その登録簿は版ごとに保守が要ります。保守の手間の割に、捕まえるのは「印の付け忘れ」だけで、標準の要求をスキルが落としていることは捕まえません(ADR-0064 の影響)
- 書き直しは、規則を規則の形にすることです。ADR-0063 は本文の依頼の形 14 件を書き直しており(自分で確かめた。0063:112)、スキルにも同じ扱いを当てるのが一貫します
- 遵守を主張しない理由: 外部 F22(構造の得点と効き目の相関 ρ=0.14)・F24(ルールファイルが読まれる率 3.5%)。文がスキルにあることと、エージェントが守ることは別です。現場の目では、文の検査が緑なのを見て「スキルで止めている」と思い込むのが最も危険な読み方です

### 他の案を落とす理由

- **A. 文末を広げる**: 落とす(誤検出と登録簿の保守)
- **C. 太字・箇条書きの構造で拾う**: 落とす。太字は強調にも規則にも使われ、構造では分けられません
- **D. 現状維持**: 一部を落とす。9 行は明確に規則であり、書き直せば検査に入るので、維持する理由がありません
- **遵守の評価(pass@k・pass^k。外部 F21)を CI に入れる**: 本 Issue では落とす。非決定的で費用の大きい評価を毎回の CI に入れると、ゆらぎによる失敗が誤検出として現れます。決定的な CI とは別の層として、評価の資産を置くかは別 Issue で審議する

### 文の案(implementation-marking.md の「スキルの文」の節へ)

- スキルの文の検査は、要求・禁止の文に所在か印があることを確かめる。スキルに従ってエージェントが振る舞うことは確かめない
- 依頼の形(「〜しないでください」)で書いた規則は、要求・禁止の文末へ書き直す

根拠水準マークの案:

```
:::caution[暫定 EV-NNNN / 見直し 2027-10]
**対象**: スキルの文の検査の範囲を、要求・禁止の文末を持つ文に限ること。
**根拠の水準**: E0(なし)。範囲の外の規則の形が、実行主体の挙動にどれだけ効くかの測定は無い。
**差し替え条件**: スキルの有無で対にした試行の、範囲の内と外の規則での遵守率の差。
:::
```

### 既存の ADR・条項との矛盾

- ADR-0064 の影響「対象を広げるかどうかは、検査を運用した後に決める」に対する決定に当たる。ADR-0064 の本文は書き換えず、新しい ADR か本 Issue の決定記録で「広げない。書き直しで対象に入れる」を残す
- ADR-0063(言語形式)と整合する

## R-6 附随

### A-11(IMPL-0115)

- 結論: `test-edition-end.mjs` の型で、`generate-profile.mjs --change` を通す試験を今回足す。足すまで IMPL-0115 の `note` に「入口を通した試験は無い」と書く
- 理由: 緩める向きの決定の拒否は、R-4 の (i) に当たる統制です。関数の試験は、入口がその関数を呼ばなくなる改修(呼び出しの経路の付け替え)を捕まえません。`generate-profile.mjs` は 4,500 行を超え、`deciderProblems` の呼び出しが4か所に散っています(内部 7.1)。経路の付け替えは現実に起きる種類の改修です。土台が既にあり(自分で確かめた)、作る手間も小さいです
- 落とす案: 「`machine` の要件として、すべてに入口の試験を課す」(内部 7.3 の C)は落とす。全件に課すと手間が大きく、捕まえるものが少ない規定も多いです。R-4 の (i) に当たる規定に限って入口の試験を求める、が釣り合います
- 文の案: 「統制を緩める向きの決定を拒否する規定で `check=machine` と書くものは、利用者が使う入口のスクリプトを通した試験を `test` に書く。」

### 台帳の定型文と IMPL-0042・0043

- 結論: 生成器(`impl-inventory.mjs:379-381`)の定型文を、降ろし先の種別で書き分ける(内部 8 の D)。`planned` の行は「実行層に実装がありません」、実在する降ろし先の行は「降ろし先はありますが、規定の全部は降りていません。降りていない部分は note にあります」。列見出しは「降ろし先」とし「(予定)」を外す
- 理由: 現行の文「案件からは『規定がない』ものとして扱われます」は、IMPL-0042 のように有無までは確かめている規定について事実と違います(内部 8)。種別は登録簿から機械が読めるので、書き分けに人の判断が要りません
- 落とす案: 70 件をすべて「降りた部分」と「降りていない部分」に分割する案(B)は、本 Issue では落とす。分割は R-1 の棚卸しで検査スクリプトを読むときに、その降ろし先の分だけ行う。一度に 70 件を分けると、分け方の誤りを見つける人がいません

### IMPL-0209・IMPL-0206

- 結論: IMPL-0209 は、`human-verify/SKILL.md:71` に禁止の文があるため、`note` を事実に合わせる。CLAUDE.md へ置くかは別に決める(記録を書く者がスキルを読む経路なら、スキルで足りる)。IMPL-0206 は射程を人が突き合わせてから同様に直す
- 理由: 誤った `note` は、降ろしたものをもう一度降ろす無駄な作業か、二重の規則を生みます

### 逆向きの追跡(どの規定にも辿れない強制)

- 結論: **全数の逆向きの追跡は採らない**。採るのは、テンプレートのコード・試験・スキルに書かれた `IMPL-NNNN` の番号が標準に実在することの検査(宙に浮いた番号の検出)だけ
- 理由: フック・CI の検査・スクリプトの分岐の一つ一つを規定へ対応づける仕組みは、作る手間が大きく、保守者が規則を足すたびに対応表の更新を課します。捕まえるもの(規定の無い強制)は、案件にとってはオーバーヘッドですが、安全側の誤りです。スキルの文については、ADR-0064 の印(テンプレート独自)が既に逆向きの追跡の役を果たしています。宙に浮いた番号の検出は、`grep` で作れて誤検出がほぼ無く、番号の削除・分割(IMPL-0104 のような)の後に古い番号が残る事故を捕まえます
- 採らないと決めたことの記録: 「準拠テンプレートの強制のすべてが本標準の規定へ辿れることは、確かめない。テンプレート独自の強制は、スキルの印(ADR-0064)とテンプレートの文書で開示する」と規約の「限界」の表へ書く

### `check` の値の陽性対照

- 内部 1.2 のとおり、`check` の値が3つ以外のマークで検査が落ちることの陽性対照が `test-check-impl.mjs` に無い。R-1 で `test` 属性を足すなら、その陽性対照(名指した試験が無い・CI に結線されていない)と合わせて足す
