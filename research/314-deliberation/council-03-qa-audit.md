## 総論: 監査の目から見た現状の問題

台帳は、読み手(採用者・監査人)が「この規定は守られる仕組みがあるか」を判断する唯一の一覧です。この立場から見た問題は、次の4つに集約できます。

1. **主張に検証の手がかりが無い**。`check=machine` の要件「実行して確かめた」(implementation-marking.md:69)は、どの試験で確かめたかを書く場所を持ちません。ADR-0061 の影響の節は「`check=machine` の真偽を、機械は確かめない」と自ら認めています。監査人が `machine` の54件を検証しようとしても、19件(内部 2.5)は手がかりがありません
2. **浅い検査が、定義より強い値で書かれている**。`claude-md` の `presence` 6件は、規約の `presence` の定義(記録・欄・ファイル・キーの有無)にすら届いていません。確かめているのは節の見出しと任意の1行で、その規則の行の有無ではありません(内部 3.3、原文で確認)
3. **一部だけ降りた規定を「対応する記述が無い」と書いている**。逆向きの過大ではなく過小の表示ですが、不正確な表示である点は同じです。ADR-0061 が既に認めて棚卸しへ送った事項です
4. **注記そのものの誤りを見つける経路が無い**。IMPL-0209 は「スキルに無い」と書きますが、スキルには在ります。さらに、そのスキルの行は「テンプレート独自」の印を持ち、本標準の所在(agent-trace-control)を引いていません。**ADR-0064 の追跡と実装マークの追跡が、同じ規定について互いに逆のことを述べています**(自分で確認した新しい事実)

本意見書の基本の姿勢は「**検証できない強い主張は、検証できる弱い主張へ下げる**」です。弱い表示は、頼る側にとって安全側の誤りです。強い表示の誤りは、統制の不在を隠します。

## R-1 検査の強さの分類(`check` の属性)

### 結論

- **R1-a**: `check=machine` の要件を規約に足す。(1) 試験の所在を `note` ではなく専用の属性 `test=` に書く、(2) その試験は違反を入れた陽性の例と、違反の無い陰性の例の両方を持つ、(3) 確かめる範囲が規定の一部なら、確かめない部分を `note` に書く
- **R1-b**: `check-impl.mjs` が `test=` の試験ファイルの実在を確かめる。これ自体は `presence` 水準の確認であることを規約に明記する(試験が規定を確かめているかは機械が確かめない)
- **R1-c**: 未分類100件の分類の規則は「**根拠を示せない値は弱い側へ倒す**」とする。`machine` は R1-a の要件を満たすものだけ。降ろし先の検査が何を見ているかを確かめられないものは `manual` とし、`presence` を推定で付けない
- **R1-d**: 分類は起案と確認を分ける。起案したセッションとは別のセッションが、作成側の説明を読まずに、降ろし先のコードと試験だけを見て全件を再分類し、食い違いを記録する(第3章 3.5.3 と入力の分離の考え方の自己適用)
- **R1-e**: `impl-targets.yaml` の `check`(検査のスクリプト名)を `script` へ改名する
- **R1-f**: 深さの属性(SP 800-53A の depth)は**今回足さない**。採らない理由を規約に書く
- **R1-g**: `test-check-impl.mjs` に「`check` の値が3つ以外なら落ちる」の陽性対照を足す(内部まとめ1: 陽性対照が無い)

### 理由

- 外部 F3(方法の指定は検証可能性の証拠にならない。合否の基準が要る)、F16(Semgrep の ruleid / ok の対)、F15(方針の単体試験)、F19(検証の記録に規則の版と証跡を添える)が、`machine` の主張に試験の所在と正負の対を結びつける根拠になる
- 対の両方を求めるのは、陽性の例だけでは「何でも落とす検査」を、陰性の例だけでは「何も落とさない検査」を見分けられないため
- 弱い側へ倒す規則は、ADR-0061 の決定理由「1つの値で表すと、強いほうに読まれる」をそのまま延長したもの。`presence` を推定で付けると、`claude-md` の6件と同じ過大が再生産される
- 起案と確認の分離: 100件を1つの文脈で分類すると、分類の誤りが同じ系統で揃う。本標準が採用者に課す分離(成果物を起案したセッションは判定の草案を作らない)を、本標準自身の台帳に課さない理由は無い
- 語の衝突: 台帳の列「検査のスクリプト」は登録簿の `check` から作られ、別の列「検査の手段」はマークの `check` から作られる。同じ語の2つの意味は、監査の場で読み違いを生む(内部 1.3、ADR-0061 は衝突に触れていない)

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| 深さの属性を足す(800-53A の Basic / Focused / Comprehensive) | 深さの段の判定基準を本標準は持っていない。基準の無い属性を304件に付けると、分類者の主観が新たな属性として固定される。R1-a の「確かめない部分を書く」で、浅さは規定ごとに具体的に開示できる。運用後に「確かめない部分」の記述が似た型に揃うなら、その時点で属性へ上げる |
| `machine` を細分する(関数の試験・入口の試験・実環境) | R-6 の A-11 の議論が示すとおり、細分は1件ごとの範囲の記述で足りる。値を増やすと、未分類の解消より先に再分類が要る |
| 変異試験を全件へ課す | 外部 F26 のとおり、差分に絞らなければ運用に乗らない。課すなら「`machine` へ上げる変更の時」に限る。本 Issue では規約の推奨にとどめる(下の文の案)。義務にする根拠の実測が無い |
| 未分類をそのまま残す(ADR-0061 決定3 の延長) | 決定3 は「材料が無い」ことを理由にした。内部調査で材料(降ろし先の検査スクリプト別の内訳。内部 2.3)は揃った。理由が消えた後も残すことは、却下の理由にならない |
| 分類を AI 1回で済ませる | 上の「起案と確認の分離」のとおり |

### 文の案(implementation-marking.md「検査の手段」の箇条への追加)

- `check=machine` には属性 `test` を必ず書く。値は、規定の違反を入れた例で検査が落ち、違反の無い例で検査が通ることを確かめる試験の所在とする
- 試験が規定の一部だけを確かめる場合は、確かめない部分を `note` に書く
- 根拠となる試験を示せない規定に `machine` を書かない。降ろし先の検査が何を見るかを確かめていない規定に `presence` を書かない。いずれも `manual` と書く
- 検査は、`test` の試験ファイルの実在を確かめる。試験が規定を確かめていることは確かめない
- 検査の手段を `machine` へ上げる変更では、規定の文または降ろし先を変えた変異を入れ、検査が落ちることを確かめることを推奨する

本文(ですます調)として次を添えます。

> 検査の手段の深さ(どこまで詳しく確かめるか)を、別の属性としては持ちません。深さの段を判定する基準が無いためです。浅さは、規定ごとに「確かめない部分」を注記で示します。

### 矛盾の検査

- ADR-0061 決定2「`check=machine` と書くのは…実行して確かめた規定に限る」の**要件を具体化する**もので、矛盾しない。ただし `test` 属性の追加はマークの書式の変更であり、ADR-0061 の決定の範囲を超える。**新 ADR で記録する**(ADR-0061 の本文は書き換えない)
- ADR-0061 決定3(棚卸しは今回行わない)は「今回」の範囲の決定で、本 Issue の棚卸しを禁じていない。新 ADR で「決定3 で残した棚卸しを行った」と記録する

## R-2 `claude-md` の常駐の規則の検査

### 結論

- **R2-a**: 常駐の規則の行ごとに識別の目印(例: 行末の `<!-- rule CR-NN -->`)を持たせ、`check-process-rules.mjs` が一覧の目印の実在を確かめる(内部 3.4 の案A)
- **R2-b**: この検査も `presence`(行の実在)であり、`machine` と書かない。行の文が改められても目印が残れば通るためである
- **R2-c**: 実装するまでの間、`claude-md` の常駐の規則のマーク(未分類12件と `presence` 6件)は `manual` とする。`note` に「節の見出しと本文の有無だけを機械が確かめ、この行の有無は確かめない」と書く
- **R2-d**: 目印の検査に、一覧の各行を1つずつ消した写しで検査が落ちることの試験を付ける(行ごとの陽性対照)

### 理由

- 現状の検査は、規定の行を消しても、節を任意の1行にしても通る(内部 3.2、原文で確認)。これは規約の `presence` の定義に届かない。**定義に届かない検査を `presence` と書くことは、R1 の過大の典型**である
- 常駐の規則は、採用者が既存の CLAUDE.md へ持ち込むときに落ちやすい(`claude-md-resident.mjs:3-5` の注記が経路を述べる)。落ちたときに検出されないのは、`state=delivered` の前提(案件の実行層に届く)を崩す
- 目印方式は、採用者が行の文を自分の言葉に改める余地を残す。全文一致(案C)よりも、案件の編集の余地とのかね合いが良い

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| C. 常駐の規則を生成区間へ移し全文一致で検査 | 全文一致は `machine` に近い強さを持つが、採用者が自分の CLAUDE.md の書きぶりへ合わせられなくなる。強さが上がる代わりに、案件が区間の外へ同じ規則を書き直す誘因が生まれ、二重の規則になる。本意見書は不採用とするが、他の立場から信頼性の面の利点が示されれば再考に値する |
| D. 現状維持で note に「節の単位」と開示 | 開示だけでは、行の脱落の検出という本来の目的を果たさない。開示は R2-c の暫定として採り、恒久策にしない |
| B のうち新しい値(presence より弱い区分)を足す | ADR-0061 の3値で表せる(`manual`)。値を増やす必要が無い |
| 照合文字列(規則の文の一部)で照合 | 採用者の言い換えで落ち、誤検出が生じる。誤検出のある検査は G-5 の原則(実効的な偽陽性が無いこと)に反する |

### 文の案(テンプレートの `claude-md-resident.mjs` 冒頭注記と規約の注記)

- 常駐の規則の行は、行末に識別の目印を持つ。検査は、一覧の目印がすべて CLAUDE.md にあることを確かめる
- 検査が確かめるのは目印の実在までであり、行の文の内容は確かめない
- 目印のある行を消すと、検査は失敗する。行の文を改めることと、行を足すことは妨げない

### 矛盾の検査

- `impl-targets.yaml:190-195` の `claude-md-resident` の説明「節の中の個々の行の有無は確かめない」を改める必要がある(登録簿の改訂。ADR ではない)
- ADR-0028(未達と省略の区別)と矛盾しない。採用者が行を意図して削る場合は、第8章の調整の経路に乗るべきで、黙って消せる状態のほうが ADR-0028 の趣旨に反する

## R-3 G-5 基準6(文脈ファイルの形式検査)

### 結論

- **R3-a(必須・本 Issue で行う)**: `gate-criteria.md:460` の開示を正す。基準6 の**参照切れと分量の上限の両方**が準拠テンプレートへ降りていないと書く。IMPL-0269 の note も同じ範囲に揃える
- **R3-b**: 参照切れ(リポジトリ内のリンクと所在の参照)の検査をテンプレートの G-5 に実装し、集約の needs へ入れる(内部 4.4 の案B)。検査の対象とする「文脈ファイル」の範囲(`CLAUDE.md`、`context/**`、`.claude/**` の Markdown 等)を同時に決める
- **R3-c**: 分量の上限は 3.11.4 要求事項1(IMPL-0222)の値の決定を待つ。値は能力依存の定数であり(RC-07 の登録)、決めるなら根拠水準マークを付ける
- **R3-d**: 基準そのものは緩めない(案D を採らない)

### 理由

- 現状の文は分量の上限だけを「降りていない」と書き、参照切れに触れない。読み手は「参照切れは降りている」と読める。**開示の欠落は、検査の欠落より重い**。検査が無いことを知っていれば採用者が補えるが、知らなければ補わない
- 参照切れはリポジトリ内で決定的に判定でき、偽陽性が小さい。G-5 の原則(実効的な偽陽性が無い・修正できる)を満たしやすい。手段の候補が明確な規定を降ろさずに置く理由が無い
- 分量の上限は値に実証が無く、値を決めずに検査だけを作ると、根拠の無い閾値で PR を止めることになる

## R-4 降りていない規定の扱い(順序・降ろさない決定)

### 結論

- **R4-a**: `state` の値は増やさない。「降ろさないと決めた」規定も `state=undelivered` のまま、**降りていない規定の節に表示し続ける**
- **R4-b**: 別の属性 `plan` を足す。値は `scheduled`(降ろす予定。Issue 番号を必須)・`declined`(降ろさないと決めた。理由・決めた者・見直しの年月を必須)の2つ。欠落は「未決」として件数を台帳に出す(`check` 欠落の扱いと同じ)
- **R4-c**: 台帳の降りていない規定の表に「扱い」の列を足し、`declined` の行も同じ表に残す。`declined` を別の節へ送らない
- **R4-d**: **`declined` を書けない規定を名指しで定める**。少なくとも、第5章 5.8.3 の一律で委譲できない領域、停止の申し立て、テストの失敗をテスト側の変更で解消する禁止を降ろし先とする規定。これらは降ろすまで `scheduled` とし、期限を持つ(外部 F31 の CMMC の型)
- **R4-e**: 順序は「(1) 統制の弱化を止める規定・人の確定を守る規定、(2) 出荷判定の根拠に効く規定、(3) その他」とする。この順序には実証が無く、根拠水準マークを付ける
- **R4-f**: 名指しの4件のうち、本 Issue で行うのは IMPL-0120 の note の更新(1.10.2 の現行に揃える)だけ。0116・0117・0118 は構成の欄と集約の拡張を要し、それぞれ別の Issue とし `plan=scheduled` で結ぶ。0291 は #348 へ

### 理由

- 監査人にとって最も危険なのは、「降ろさないと決めた」が「降りていない」の一覧から消えることである。`not-applicable` に当たる値を `state` に足すと、件数の表から外れ、読み手は統制が要らないものと読む。外部 F29(項目を消さない)、F30(降ろさない項目も閉じずに残し定期的に見直す)のとおり、別の経路にしても表示は残す
- 「予定」と「決めた」を区別しないと、`undelivered` は「誰も判断していない」と「判断した」が混ざる(外部 F6・F10・F32)。コアポリシーの「書かれていない」と「課さないと決めた」の区別を、台帳にも及ぼす
- `scheduled` に Issue 番号を必須にするのは、外部 F28・F29 の POA&M(期日・責任者のない計画を許す期間に上限)の最小限の写しであり、Issue が期日の所在になる
- 名指しの固定: どの規定でも `declined` にできると、降ろすのが難しい規定から順に `declined` になる誘因が生まれる。降ろせないまま運用してはならない規定を、規格の側で先に固定する(外部 F31)
- 名指しの4件を本 Issue でまとめて降ろさない理由は、量ではなく**検証の単位**である。構成の欄を足す変更と集約の出力を変える変更は、それぞれ試験と G-5 を要し、1つの変更に混ぜると何を確かめたかが追えなくなる

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| `state` に `declined`(または `not-applicable`)を足す | ADR-0061 決定1「`state` は2値のまま保つ」に反し、届いたかと扱いを1本の軸に混ぜる。表示から外れる危険も上記のとおり |
| note の文で「降ろさない」と書くだけ | 件数に出ない。機械が理由・決めた者・見直しの欄の欠落を検出できない |
| 順序を降ろす難しさ(低→高)で決める | 易しいものから降ろすと、出荷の判断に効く規定ほど後回しになる。信頼性の軸に合わない |
| 4件をこの Issue で降ろす | 上の検証の単位の理由 |
| 期限を日付で属性に持つ | 期日の正本が2か所(マークと Issue)になる。Issue 番号で結ぶ |

### 文の案(implementation-marking.md「降りていない規定の扱い」へ追加)

- `state=undelivered` のマークには属性 `plan` を書く。値は `scheduled`(降ろす予定)または `declined`(降ろさないと決めた)
- `scheduled` には、降ろす作業の Issue 番号を `note` に書く
- `declined` には、理由・決めた者・見直しの年月を `note` に書く。決めた者の欄へ AI の名義を書かない
- `declined` の規定も、降りていない規定の表に残す。別の節へ送らない
- `plan` を欠くマークを、検査は落とさない。台帳に「扱いが未決」の件数を出す
- 次の規定には `declined` を書かない(以下、名指しの一覧)

本文(ですます調)として次を添えます。

> 降ろさないと決めることは、規定を課さないと決めることではありません。案件からは規定が無いものとして扱われる状態が続くことを、決めた者が引き受けることです。

:::caution[暫定 EV-NNNN / 見直し 2027-10]
対象: 降りていない規定を降ろす順序(統制の弱化を止める規定・人の確定を守る規定 → 出荷判定の根拠に効く規定 → その他)。根拠の水準: E0。統制の自動化の順序を定めた規範は外部調査で見つからなかった(外部 5章)。差し替え条件: 降ろした規定の順と、その間に案件で起きた統制の逸脱の記録。
:::

### 矛盾の検査

- ADR-0061 決定1(`state` は2値)と整合する。`plan` は `check` と同じく直交の属性として足す。新 ADR が要る
- ADR-0028(未達と省略の区別)と同型。`declined` は「省略」ではなく「未達のまま引き受けた」であり、表示を続ける点で ADR-0028 の未達のゲートの扱いに一致する
- 規約の「降りていない規定の件数を合否にも警戒の条件にも使わない」(EV-0136)と矛盾しない。「未決」の件数も同じく合否に使わないと明記する

## R-5 スキルの文の検査(ADR-0064)の範囲

### 結論

- **R5-a**: 検査の水準を規約と ADR の後継で `presence` と明記する。「印の有無と所在の実在」を確かめるのであり、スキルの文が本標準と一致することも、エージェントが守ることも示さない。**この検査の通過を、スキルの規定が実行層へ届いた根拠として使わない**
- **R5-b**: 対象の文末に「〜ないでください」を足す。依頼の形の禁止は文末で一意に判別でき、説明文と混ざりにくい
- **R5-c**: 平叙の否定(「〜しない」)と太字の否定は、正規表現で拾わない。代わりに、スキルの規則の文を改めるときに要求・禁止の文末へ書き換える(内部 6.3 の案B)。書き換えを済ませた範囲を記録する
- **R5-d**: 検査の出力に、対象の外にある規則の候補の概数(「〜しない。」「〜しないでください」以外の否定の文末の行数)を**情報として**出す。合否に使わない
- **R5-e**: 検査が遵守を確かめないことに、根拠水準マークを付ける(効き目の根拠が無いことの開示)
- **R5-f**: IMPL-0209 に対応するスキルの行(`human-verify/SKILL.md:71`)は「テンプレート独自」ではなく本標準の所在を持つべきで、印を改める。同様の食い違い(実装マークが規定を持ち、スキルの印が独自と書く)を機械で突き合わせる

### 理由

- 外部 F22(構造の検査と効き目の相関は弱い)、F24(ルールファイルが読まれる率は低い)、F23(規範から指示ファイルへの網羅を検査する道具の先例が無い)。この検査を「スキルに規定が届いている」根拠に使うと、検出を装った presence になる
- 範囲を広げること自体は、`presence` の網羅を上げる。ただし文末で作る一覧は閉じない(implementation-marking.md:126)。誤検出の多い拡張は、印の付けすぎ(説明文への印)を生み、印の意味を薄める。判別が一意な「〜ないでください」だけを足す
- R5-f は自分で確かめた事実: 実装マーク IMPL-0209 は agent-trace-control.md の規定を降ろし先へ結び、スキルの行は同じ禁止を「テンプレート独自」としている。**ADR-0064 の印は、本標準に対応する規定が無いことを主張する**。2つの追跡の系統が同じ規定について逆を述べており、どちらの検査も通っている。両方向の突合(外部 F7)が無いことの実例である

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| A. 文末を広く足す(「〜しない」「〜ない。」等) | 説明文を大量に拾い、誤検出の登録簿が膨らむ。印が規則の目印として機能しなくなる |
| C. 太字・構造で拾う | 太字の否定約48行には説明文を含む(内部 6.2)。構造は規定の強さを示さない(ADR-0063 は文末で強さを示す) |
| D. 現状維持で限界を開示 | 開示は R5-a で採る。ただし判別が一意な形まで放置する理由は無い |
| 挙動の評価(pass^k)を CI へ入れる | 非決定的で CI の合否に向かない(外部 F21)。遵守の評価は別の層の課題として、本 Issue の範囲の外と明記する |

### 文の案(implementation-marking.md「検査の限界」への追加)

- スキルの文の検査は、印の有無と所在の実在を確かめる。検査の手段としては `presence` に当たる
- 検査の通過を、スキルの規定がエージェントに守られている根拠にしない
- 実装マークが本標準の規定を降ろし先へ結んだ文に、「テンプレート独自」の印を付けない

:::caution[暫定 EV-NNNN / 見直し 2027-10]
対象: スキルの文の検査が、本標準と食い違うスキルの文を減らすこと。根拠の水準: E0。規範から指示ファイルへの網羅を検査した先例は見つからず(外部 F23)、構造の検査と効き目の相関は弱い(外部 F22)。差し替え条件: 検査の導入前後で、条項の改訂時に見つかったスキルの食い違いの件数。
:::

### 矛盾の検査

- ADR-0064 の影響の節「検査が確かめるのは、印の有無と所在の実在までである」「対象を広げるかどうかは、検査を運用した後に決める」と整合する。R5-b は運用後の拡大の決定に当たり、新 ADR で記録する
- ADR-0063 決定2(平叙の動詞文を要求として読む)により、スキルの平叙の否定も規則である。R5-c はこの読みと整合し、検査が拾えない規則を文末の書き換えで検査の対象へ入れる

## R-6 附随

### A-11(IMPL-0115)

- 結論: `generate-profile.mjs --change` を通した端から端までの試験を足す(内部 7.3 の案A)。足すまでは IMPL-0115 の `note` に「変化点から緩める向きの項目を取り出す処理は試験していない」と書く。値は `machine` のまま、R1-a の `test` と範囲の記述で扱う
- 理由: 自分で確かめたとおり、現行の試験は `loosenItems` を手で組み立てる。外部の確認者の記名を拒否する判定は確かめているが、変更の差分から「独立レビュア: 協働 → 委任」を取り出す処理が席を取り落とせば、拒否は起きない。規定の違反(外部の確認者が緩める)は、取り出しの欠陥でも通る
- 落とす案: 案B(関数の試験で足りる)は取り出しの経路を確かめないため不可。案C(規約で関数か入口かを定める)は R1-a の「確かめない部分を書く」で足り、値の細分は R1 で落とした
- 矛盾: ADR-0061 決定2 の「実行して確かめた」を、規定の違反が実際に入る経路で確かめることと読む。矛盾しない

### 台帳の定型文と IMPL-0042・0043

- 結論: 一部だけ降りた規定は、降りた部分と降りていない部分の2つのマークに分ける(内部 8 の案B)。あわせて定型文を「次の規定は、実行層に対応する記述が無いか、規定の一部だけがあります。**降りていない部分は、案件からは『規定がない』ものとして扱われます**」へ改め、列見出しを「降ろし先」とし、`planned` の行に「(予定)」を付ける
- 理由: 分割は、降りた部分の `check` を正しく付けられる唯一の形である(0042 の有無の確認は `presence`、突合は `undelivered`)。定型文だけ改める案A は、行ごとにどの部分が降りていないかを示さない。台帳冒頭の文(implementation-ledger.md:12「規定が実行層へ降りていない場合…」)も同じ趣旨で改める
- 落とす案: 案C(`state` に値を足す)は ADR-0061 決定1 に反する。案A 単独は上記
- 矛盾: ADR-0061 の影響の節が棚卸しへ送った事項の処理。分割は IMPL-0104 → 0284〜0291 の先例(#311)と同じ扱い。識別子は再利用しない

### IMPL-0209・0206 の注記

- 結論: IMPL-0209 は note を事実へ改める(「スキル `human-verify` に在る。CLAUDE.md には無い」)。`state` は、記録を書く者が読む場所(スキル)に在るなら `delivered` へ改め、`check=manual` とする。R5-f のスキル側の印も同時に改める。IMPL-0206 は射程が同じかを人が突き合わせ、結果を note に書く
- 理由: 注記の誤りは、台帳の他の行の信頼を損なう。抽出11件中1件で誤り(内部 2.6)は、全数の点検が要ることを示す。R1-d の再分類の際に、note と降ろし先の一致も同じ別セッションが確かめる

### 逆向きの追跡

- 結論: 本 Issue では全数の逆向きの追跡を課さない。ただし `impl-targets.yaml` の登録のうち、どのマークからも指されない降ろし先の件数を台帳に出す(機械で数えられる最小の逆向きの網羅)

- 矛盾: ADR-0076(対象の棚卸し)は規定 → 降ろし先の向きの網羅であり、逆向きを扱わない。矛盾しない
