外部調査の結論のうち、規格の側から最も重いのは次の2点です。

1. **人の認証情報を AI の担い手と共有することを、明文で禁じた規範的な条文は、読めた範囲に無い**。800-53 の shared account は人どうしの共有を想定した書きぶりで、人とエージェントの共有を名指ししていない
2. 一方で 800-53 は、**人の代理で動くプロセスを、その人の識別へ結び付けること**を要求の中に置く(IA-2「associate that unique identification with processes acting on behalf of those users」、AU-10「an individual (or process acting on behalf of an individual)」)。つまり 800-53 の模型では、人の認証情報で動くエージェントは「代理のプロセス」であり、**説明責任はその人に残る**。崩れるのは説明責任ではなく、**人が判断したことの証拠**である

本標準の G-6 と 3.5.4 は「独立」を人の単位で定め、「AI と bot の名義による承認は数えない」と書きます。数えているのは、責任の帰属ではなく**人が確認したという事実**です。共有の構成で失われるのはこの事実の証拠であり、800-53 が保とうとする説明責任とは別のものです。以下の結論は、この区別に立ちます。

## R-1 共有の構成への要求の向き

### 結論

1. **黙らない。構成の入力として必ず問う**。AI の担い手ごとに、ホスティングの記録の上で操作が帰属するアカウント(以下「担い手の名義」)を記録させる。値は「専用の名義(人のアカウントと区別できる)」か「人のアカウントの認証情報で動く(名簿のどの人か)」のどちらか。**記録が無い担い手は、作成を指示した席の責任者のアカウントで動くものとみなす**(G-6 の「記録が無い変更は作成者と開発者の席の責任者を指示者とみなす」と同じ型。安全側に倒す既定値)
2. **全面の禁止(担い手を人の認証情報で動かしてはならない)は採らない**。ただし、**G-6 の承認、効力を持つ記録の記名と帰属の確認に用いる人のアカウントを、AI の担い手に使わせない**ことを要求事項として置く。満たせない構成は、第3章 3.5.3 の条件3 と同じ型で**列挙に無い離脱**として記録・表示する(第1章 1.10.2 の表に行を足す)。運用を止める禁止ではなく、主張の条件である
3. 専用の名義を**推奨**として書く(「〜するとよい」ではなく、要求事項2 を満たす手段の第一として示す)
4. 第1章 1.10.2 の既存の行「実行主体の文脈の認証情報を、席ごとに分けられない構成」は、**主語を「席どうし(担い手どうし)」と明記する**。人と担い手の共有は、別の行として足す。2名の体制が主張に至る条件の「席ごとに認証情報を分けている」にも、新しい条件を並べる

### 理由

1. **黙ることは信頼性の欠陥である**。外部 1.2・1.7 のとおり、ローカル実行のエージェントは利用者の認証情報で動くのが既定である。本標準の利用者の多数が、何も決めずに共有の構成に落ちる。G-6 の「AI と bot の名義による承認は数えない」(gate-criteria.md:949)は、この既定の構成では空文になる。それが G-6 の節のどこにも書かれていない(内部 1.3)。規格として、条項が既定の利用で機能しないことを読み手に知らせないのは許されない
2. **全面の禁止には規範の根拠が無い**。上の 0 の2のとおり、800-53 は代理のプロセスを人の識別へ結び付ける模型をむしろ前提にしている。GitHub の利用規約も、禁じるのは「1つのログインを複数の**人**で共有すること」で、エージェントによる自動化は所有者の責任として許す(外部 1.6、[確認])。人の認証情報でエージェントがブランチへ push する、PR を開く、コメントを書くこと自体は、本標準のどの統制も壊さない(R-2 のとおり、PR の作成者の別はむしろ安全側に倒れる)。壊れるのは、**本標準が人の行為として数える操作**だけである。要求は、壊れる操作に向けて書くのが正確である
3. **要求事項2 の根拠**。本標準自身の規定が根拠になる。3.5.4 は独立を自然人の単位で定め、G-6 は AI の名義の承認を数えない。これを機械で確かめられる前提は「人の承認に使うアカウントの操作は人の操作である」ことだけである。この前提を崩す構成を許したまま、独立した人の確認を経たと主張することはできない。外部の指針は同じ方向を向く: OWASP ASI03 は委任された利用者のセッションを識別の範囲に含め、固有の識別を持たないエージェントを「attribution gap」と呼ぶ。CISA ほかは「各エージェントを別個の主体として構成する」と書く。NIST NCCoE(DRAFT)は agent と human の識別を区別したうえで委任元へ結び付ける構図を検討する。800-53 AC-5 は職務の分離をアカウント管理と識別管理で強制すると解説する。SLSA の Two-party review は trusted person と trusted robot を別の役割として定義する。**いずれも禁止の明文ではないが、「人の確認を識別で示す」ことを求める点で一致する**
4. **離脱の型を選ぶ理由**。ADR-0083 は、条件と代償措置を定めない離脱を「列挙に無い離脱」とし、主張を妨げ、適用の表明は許す。共有の構成は、自己申告(Co-authored-by、記名者への聞き取り)より強い代償措置を持たない(外部 4.1・4.2: 署名も trailer も、人の名義の操作を人の操作と区別する証拠にならない)。代償措置を定められないものを「逸脱」(閉じた列挙)へ入れることはできない。未達(ゲートの状態)でもない。したがって列挙に無い離脱が、ADR-0083 の語彙で唯一正確な分類である。3.5.3 の条件3(認証情報が分かれない文脈)と同型であり、新しい分類を作らない
5. **手段が存在する**。要求事項2 は、主要なホスティングで満たせる。GitHub では、自動化専用の machine account(無料で個人ごとに1つ)、GitHub App の installation token、提供者の App(Claude Code Action・Copilot cloud agent など)が使える(外部 1.1・1.2・1.6)。実現の手段が無い要求ではない。他のホスティング(GitLab・Azure DevOps・Gitea)で同等の手段があるかは、本件の調査で確かめていない。条項は「ホスティングの記録の上で人のアカウントと区別できる名義」と書き、手段の名を入れない
6. **1〜2名の採用者への影響**
   - 1名の体制: 1.10.2 のとおり既に適用の表明しかできない。主張への影響は無い。増えるのは、担い手の名義の記録と、保証の開示への表示である
   - 2名の体制: 共有の構成のままでは、2つの主張に至らない。専用の名義を用意すれば至る。影響は大きいが、**2名の体制で G-6 を相互の承認で満たすとき、相手の承認が相手の AI の操作でないことを示す手段は、専用の名義のほかに無い**。影響の大きさを理由に条件を外せば、主張が中身を持たなくなる
   - 3名以上も同じ。規模で扱いを変える根拠は無い(1.10.2 の既存の行も「規模を問わない」)

### 反論されうる点

- **「ローカルで AI を使うほぼ全員が離脱を持つ。主張できる採用者がいなくなる」**。応答: 主張は、独立した人の確認を記録で示せる範囲に限るべきである。示せないのに主張できる規格は信頼されない。専用の名義は無償で用意できる(GitHub の場合)。主張を望む採用者に必要な手当ては1つで、具体的である
- **「800-53 IA-2 は代理のプロセスを人へ結び付けることを求めている。共有はむしろ IA-2 の模型どおりではないか」**。応答: そのとおりで、だから全面の禁止は採らない。IA-2 が保つのは説明責任であり、本標準の G-6 が数えるのは人が確認した事実である。後者を識別で示す根拠は IA-2 ではなく、AC-5(職務の分離を識別管理で強制する)と、本標準自身の 3.5.4 にある
- **「要求事項2 の『G-6 の承認に用いるアカウント』は、事前に決まらない(誰が承認するかは変更ごとに違う)」**。応答: 名簿に載る人のアカウントは、すべて承認に用いうる。実務上は「名簿の人のアカウントを AI の担い手に使わせない」と同値になる。条項は名簿の人のアカウントで書く方が検査しやすい。起草の委員に、どちらの文で書くかを委ねる
- **ISO/IEC 27002 5.16・5.17 の本文を読めていない**。共有の識別情報を条件つきで認める手引きがある、との二次情報がある(外部 2.4)。もし本文がそう書くなら、それは人どうしの共有の運用条件であり、本件の「人の確認を識別で示す」要求と衝突しないと考えるが、原典で確かめていない

## R-2 共有の構成で崩れる統制の扱い

### 結論

崩れるのは「説明責任」ではなく「人が判断した証拠」である(0 の2)。この区別で、統制ごとに扱いを分けます。

| 統制 | 共有の構成で起きること | 扱い |
| --- | --- | --- |
| G-6 の独立した人の確認(4条件と「AI と bot の名義の承認は数えない」) | 共有されたアカウントの承認が、人の承認と AI の承認のどちらか区別できない | **数える。ただし「自己申告の承認」として別に数え、件数を保証の開示の項目1 に出す**。構成は R-1 の離脱を持つので主張には至らない。G-6 の節に、この穴と扱いを明記する |
| 作成を指示した者の照合(既定値: 作成者と開発者の席の責任者) | PR の作成者は常に人のアカウントになる | **変えない**。作成者が指示者とみなされ、ブランチ保護が作成者の承認を止める。安全側に倒れる(外部 1.3 の Cursor の設計と同じ向き)。担い手が**別の人**のアカウントで動く場合は、その人も指示者とみなされ、承認が数えられなくなる。これも安全側であり、変えない。その旨を G-6 の節に書く |
| 効力を持つ記録の帰属(ADR-0106 決定3 の (A)(B)) | 記名者本人のレビュー、記名者のアカウントの作成・承認が、担い手の操作でありうる | **記名者のアカウントが担い手と共有されている場合は、帰属の確認者を置ける体制でも、記名を自己申告として記録ごとに開示する**(gate-criteria.md:121 の条件に、名簿に記名者以外がいない場合と並べて足す)。帰属の確認者は、記名者本人に操作の有無を確かめた旨を記録する(附属書H 観点28 の聞き取りを、確認の時点へ前倒しする) |
| PR の作成者の別(作成者のレビューを数えない、ブランチ保護の自己承認の禁止) | 同じアカウントの範囲では効く。別の人のアカウントで動く担い手には効かない | 変えない。担い手の名義の記録(R-1・R-3)で、どの人のアカウントが共有されているかを機械が知れるようにし、そのアカウントの操作を上の各行の扱いへ回す |
| 5.8.2 の AI の関与の記録(Co-Authored-By) | trailer は自由記述で、証拠ではない | 変えない。自己申告であることは既に 5.8.2 の性質。共有の構成では、これが AI の関与の**唯一の**記録になることを保証の開示の項目7 の注記で示す |
| 内部監査の観点6(1人が複数のアカウントを使っていないか) | 1つのアカウントを人と AI が使う構成を見ていない | 観点に「1つのアカウントを人と AI の担い手が使っていないか(担い手の名義の記録と突き合わせる)」を足す。観点28 は効力を持つ記録に限るため、G-6 の承認には観点6 側で掛ける |

保証の開示の置き場:

- **項目1(体制と独立性の成立状況)**に、担い手の名義の構成(専用 / 共有。共有なら名簿のどの人のアカウントか)と、自己申告の承認・自己申告の記名の件数を出す。独立性の成立状況そのものであるため
- **項目7(生成の条件と期間中の体制の変化点)**に、期間中の担い手の名義の変更を出す
- 8つ目の項目は足さない。7項目の構造(ADR-0056)は保証の主張の構成要素で分けており、名義は項目1 の「独立性の成立状況」の一部である

### 理由

1. **数えない、を採らない理由**。共有されたアカウントの承認を一律に数えなければ、共有の構成の G-6 は外部の確認者を置かない限り到達できなくなる。そのとき採用者が取るのは、G-6 を外す宣言か、記録を整えて見せることであり、どちらも記録の信頼性を下げる。共有されたアカウントの承認でも、説明責任はそのアカウントの人に残る(800-53 IA-2・AU-10 の模型、GitHub 利用規約の「所有者が最終的に責任を負う」)。責任のある人の承認として数え、証拠の水準(自己申告)を開示するのが、事実に最も近い記録である。主張の可否は R-1 の離脱が別に止めている
2. **ただし「人の承認」と同じ箱に入れない**。現行の「AI を示す語を含むアカウント名の人」の扱い(gate-criteria.md:950)が同じ型で、確認によって数えた承認の件数を項目1 に出す。共有の構成の承認も、機械で人と区別できない承認であり、同じ扱いに揃える。新しい仕組みを作らない
3. 作成を指示した者の既定値は、共有の構成で**強くなる**向きにしか働かない。強くなる向きの帰結を「崩れる」と書くと、読み手が直す必要の無いものを直す。崩れないことを明記する
4. 効力を持つ記録は、入った時点で検査の合否を変える(ADR-0106 決定1)。G-6 の承認より帰結が重い。ADR-0106 は帰属の確認者を置けない体制だけを自己申告の開示へ回したが、共有の構成は「確認者を置けても、記名者の操作の証拠が無い」点で同じ性質を持つ。ADR-0106 の「反論されうる点」は、この扱いを #429 に回しており、本件で閉じる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 共有されたアカウントの承認を G-6 で数えない | 理由1。説明責任の残る承認を無かったことにし、記録の改変の動機を作る |
| 共有されたアカウントの承認を、注記なしに人の承認として数える(現状) | G-6 の「AI の名義の承認は数えない」が空文であることを隠す |
| ホスティングの監査ログ(アクセスの種別・トークンの識別)で人と担い手を区別することを求める | 外部 3.3 のとおり GitHub の組織・企業の監査ログには手がかりがあるが、ユーザー所有のリポジトリでは使えず、保持は 180 日で、プラットフォームに依存する。**採用者が使えるなら補強として記録してよい**と手引きに書くにとどめ、要求にしない |
| 保証の開示に8つ目の項目「認証情報の共有」を足す | 理由は結論の末尾。独立性の成立状況の一部である |

### 反論されうる点

- **「自己申告の承認を数えるなら、R1 の変更が自己申告の承認1件で出荷できる」**。応答: できる。そしてその件数が開示され、構成は主張に至らない。R1 にだけ外部の確認者を要求する案は、構成の条件と変更ごとの条件の2層(3.5.4・ADR-0060 決定3)の外に新しい条件を作る。必要だと考える委員がいれば、R1 の扱いとして別に議論すべきで、規格の側からの根拠は持たない
- **「帰属の確認者に聞き取りをさせても、確認者は記名者の言葉を信じるだけ」**。応答: そのとおりで、だから自己申告として開示する。聞き取りの記録は、監査の時点(観点28)で初めて聞くより、効力の前に聞いた記録の方が事実に近い、という程度の意味である

## R-3 担い手の識別にアカウントを含めるか

### 結論

1. **3.4.2 の担い手の識別(モデルの版・指示資産の版・権限の組)に、名義を加えない**
2. ただし「権限の組」の意味を明記する: **担い手の名義がホスティングで持つ権限を含む**。人のアカウントで動く担い手は、その人の権限を持つ。専用の名義から人のアカウントへ移れば(またはその逆)、通常は権限の組が変わり、識別が変わる。これは既存の規定の読み方の明確化である
3. 担い手の名義は、**識別とは別の欄**として記録する。D-0 表7 に列「担い手の名義」(専用の名義ならホスティングの数値の識別子とログイン名、共有なら名簿の人の識別子)を足す。構成の `performer` にも同じ欄を足す。`/process-init` で問い、`/process-change` の種別で変える
4. **名義の変更を、変化点として名指しする**(第3章 3.13.1 の変化点4 の例示に「担い手の名義の変更(専用の名義 ⇄ 人の認証情報、共有する人の変更)」を足す)。向きは ADR-0055 決定5 に従う: 専用 → 共有は**緩める向き**(記名と理由を要する)、共有 → 専用は**厳しくする向き**(即時に適用)
5. 同じ名義のまま認証情報(トークン)を入れ替えることは、変化点にしない

### 理由

1. 3.4.2 の識別は、**席の判断を担えるかの確認の単位**である。確認の中身(過去の判定の再現、欠陥注入による検出)は、モデルと指示資産と権限で決まり、どのアカウントで操作が記録されるかでは変わらない。名義を識別に入れると、判断の能力に関係しない変化で確認が失効する。800-53 IA-4 は識別子の管理を、能力や権限の評価と別の管理策として置いている(IA-4 b. は識別子の選定の対象に individual・group・role・service・device を挙げるだけ)。識別子の管理と能力の確認を一つの組にまとめる規格上の理由は無い
2. 一方で、権限は確認の単位に既に入っている。人のアカウントで動けば担い手はその人の権限(管理者権限を含みうる)を持つ。「権限の組」が名義の持つ権限を含むと明記すれば、名義の変更のうち能力の前提を変えるものは、既存の規定で失効を起こす。新しい失効の契機を作らずに済む、のではなく、**失効すべき変化だけが失効する**ことが理由である
3. 名義を記録する欄が要るのは、R-2 の各扱いを機械が掛けるためである。とくに**専用の名義の数値の識別子を構成に登録すれば、その名義の承認を「AI の名義」として確実に数えない**ことができる。現行の判定は名義の語(AI・bot・モデル名)と bot の型に依る(内部 2.1)。machine account に人のような名を付ければ、語でも型でも見分けられない。登録された識別子による陽の判定は、語の推定より信頼できる。試験の fixture にだけある `aiNames` の鍵(内部 2.1)は、この欄の不在の表れである
4. CISA ほかは短命の資格情報を推奨する(「ephemeral credentials that expire when the job is complete」)。トークンの入れ替えを変化点にすると、推奨どおりの運用ほど変化点が増える。変化点は名義の単位に置く
5. 向きの判定は ADR-0055 決定5 の非対称に従う。専用 → 共有は R-1 の離脱を生み、人の確認の証拠を弱めるので緩める向きである

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 3.4.2 の識別に名義を加える | 理由1。能力の確認と識別子の管理を混ぜ、判断の能力に無関係な変化で確認が失効する |
| 名義を記録しない(識別にも欄にも入れない) | R-2 の扱いを機械が掛けられない。専用の名義を陽に判定できず、語の推定に残る |
| 名義を D-0 表5-2(人の名簿)に書く | 表5-2 は人の名簿であり、AI の担い手のアカウントを「載せない」と定めている(deliverable-templates.md:434)。名簿に AI を書かない検査(`rosterProblems`)とも衝突する。担い手の側(表7)に置くのが語彙と合う |
| トークンの入れ替えを変化点にする | 理由4 |

### 反論されうる点

- **「名義の変更で権限が変わらない場合(人のアカウントと専用の名義が同じ権限)、識別は変わらず確認は失効しない。それで良いのか」**。応答: 良い。能力の確認の前提が変わっていない。名義の変更そのものは変化点(結論4)として記録・通知され、R-1・R-2 の扱いが切り替わる。失効と記録を分けて扱うのが目的である
- **「権限の組の明確化は、採用済みの規定の意味を変えるのではないか」**。応答: 3.4.2 は「権限の組」が何の権限かを書いていない(内部 1.3)。どちらにも読める規定を一方に定めることであり、厳しくする向きの明確化である。ADR で決定として記録する

## R-4 名簿の数値の識別子による照合

### 結論

1. **第4章「アカウントと人の対応表」の数値の識別子の要求(gate-criteria.md:84)を維持する**。「ログイン名だけの対応表では、承認者を同定できたものとして扱わない」も維持する。緩めない
2. **照合の鍵を数値の識別子にする**。ホスティングが返す (ログイン名, 数値の識別子) のうち、数値で名簿の人へ対応づける。ログイン名が食い違えば所見(改名、または他人による取得の疑い)とする(内部 3.4 の M6)
3. 「リポジトリの外側で保守する」は、**目的で書き直す**: 対応表の変更が、判定される側の単独の操作で効力を持たないこと。手段として (a) リポジトリの外側の台帳、または (b) リポジトリの中の名簿で、変更が ADR-0106 の効力を持つ記録(D-0 の決定の記名)として帰属を裏づけられているもの、のいずれか。(b) は IMPL-0415(#428)が降りるまで未達として表示する。この書き直しは採用済み ADR(0070・0106)の本文を変えないので、新しい ADR に記録する
4. 準拠テンプレートの移行は、**M1(名簿の要素に数値の識別子を持たせる)+ M4(機械が識別子を引き、人が記名して入れる。引いた時点と確かめた者を記録する)+ M6(写しの識別子と名簿の食い違いを所見にする)** を採る。M5 のうち「ログイン名でしか照合できなかった承認を分けて数え、開示する」は採るが、**期限つきでログイン名の照合を同定に数える移行期間は採らない**
5. ログイン名でしか照合できなかった承認は、条文どおり**同定できていない承認**として扱う。G-6 の条件1 の「承認者を名簿と対応づけられない」に計上し、件数を保証の開示の項目1 に出す。厳しくする向きであり、即時に適用する(ADR-0055 決定5)。現にテンプレートが条文を満たしていないことを、実装マークで表示する(結論7)
6. **PR 本文の `@アカウント`**(作成を指示した者・委任の実施者・区分の確定者): 本文はログイン名でしか書けない。**検査の時点でホスティングに数値の識別子を引き、その識別子を写しに固定する**。照合はその識別子で行う。後日にログイン名から引き直さない
7. gate-criteria.md:84 に実装マークを付ける。現状は `state=undelivered` で表示する(ADR-0028・#222 の扱い)。IMPL-0125 の note を「数値の識別子は表示するが、席への対応はログイン名」と事実どおりに改める

### 理由

1. **ログイン名は識別子の再利用の防止を満たさない**。800-53 IA-4 d. は識別子の再利用の防止を求め、解説は「以前に使われた識別子を別の個人に割り当てないこと」と書く。GitHub のログイン名は改名で直ちに、削除後 90 日で他人が取れる(外部 3.1、[確認])。一方、REST の `id`(GraphQL の `databaseId`)は「durable user ID」とホスティング自身が書く(外部 3.2)。照合の鍵を数値にするのは、規格の要求とホスティングの仕様の両方から導ける。第4章の要求は正しく、誤っているのはテンプレートの実装と、マークの欠落である
2. **移行期間を採らない理由**。ADR-0083 決定1 は移行期間と失効を置かない型を採っている。ログイン名の照合を期限つきで「同定できた」に数えると、条文と逆の扱いを期間を区切って許すことになる。しかも期限は、その間の記録の信頼性を何も変えない。同定できていないものは同定できていないと表示し続け、数値の識別子を入れた時点で解消する方が、未達と省略の区別(ADR-0028)に合う。解消の手段(M4)は1回の操作で済み、手段が存在しない要求ではない
3. **M4 の危険(別人の識別子を固定する)の扱い**。いまの名簿のログイン名を引くと、改名・削除の後に他人が取った名なら別人の識別子が返る。数値の識別子は不変なので、**過去の写しが既に持つ識別子**(写しは `user.id` を必須にしている。内部 3.3)と突き合わせれば、同じログイン名に別の識別子が出たことを検出できる。人が記名して入れる前に、この突合の結果を示させる。名簿へ足すのは人(deliverable-templates.md:153)という既存の原則とも整合する
4. **「リポジトリの外側」を目的で書く理由**。外側に置く目的は、判定される側(AI の担い手を含む)が対応表を書き換えて承認者を作れないことである。テンプレートは名簿をリポジトリの中(`process.config.json`)に置き、担い手の編集を権限設定で止めているが、この差は標準にもテンプレートにも書かれていない(内部 3.2)。一方、名簿は D-0 の生成元であり、D-0 の決定の記名は ADR-0106 で効力を持つ記録になった。効力を持つ記録の帰属の裏づけは、まさに「判定される側の単独の操作で効力を持たない」ことを求める。目的が同じ2つの規定を、置き場所の違いで別々に満たさせる理由は無い。ただし (b) を満たすのは IMPL-0415 が降りた後であり、それまでは未達である。書き直しで未達を消すのではない
5. **PR 本文の `@アカウント`** は作成側が書く欄である(G-6 条件4 の注記のとおり、PR 本文は作成側の欄)。ここで要るのは書いた時点の対応だけであり、検査の時点で数値へ固定すれば、後日の改名・再取得の影響を受けない。後日に引き直すと、他人の取得したログイン名を指示者に解決する。指示者の取りこぼしは承認を数える向き(緩める向き)に働くので、引き直しは避ける
6. プラットフォームに依存しない書き方: 条項は「ホスティングが付与し、別の主体に再び割り当てない識別子」と書き、GitHub の `id`・`databaseId` は手引き(第5章)と準拠テンプレートに置く。node_id は形式が新旧で混在する(外部 3.2 [観測])ため、手引きでも比較の鍵に勧めない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 第4章の要求を緩め、ログイン名だけの対応表でも同定できたものとする | 理由1。IA-4 d. を満たさず、時間をおいた照合で別人に当たる |
| M2(人ごとに並行の欄 `accountIds`) | ログイン名と識別子の対がずれても検出できず、照合の鍵が2つになる。1つの要素に対で持たせる M1 の方が、食い違いを所見にできる |
| M3 だけ(名簿を外へ出すことを唯一の手段にする) | 置き場所は目的の手段の1つにすぎない(理由4)。外の台帳を CI と手元の両方が読む経路を全採用者に課す根拠が無い。外の台帳を選ぶ採用者には (a) として残す |
| M5 の期限つき移行期間(期限まではログイン名の照合を同定に数える) | 理由2 |
| 過去の名簿(IMPL-0094 の時点の名簿)へ、いまのログイン名から引いた識別子を書き戻す | 過去の時点の対応を、いまの対応で書き換える。過去の判定は、その時点の写しの識別子と、識別子を入れた後の名簿で照合する |
| PR 本文の `@アカウント` を数値の識別子で書かせる | 人が数値を写すことになり、5.8.2 の「人の転記に頼らない」と逆である。書き手はログイン名で書き、機械が検査の時点で固定する |

### 反論されうる点

- **「即時に適用すると、既存の採用者の G-6 が一斉に『承認者を名簿と対応づけられない』になる」**。応答: なる。それは現に条文を満たしていない事実の表示であり、テンプレートが条文を満たしていると見せてきた方が誤りである。解消は名簿へ識別子を入れる1回の操作で、テンプレートが手段(M4)を提供する。採用者の手間を理由に表示を遅らせない
- **「PR の時点の照合は、その瞬間のログイン名で引くので正しい。数値にする意味は後日の照合だけではないか」**。応答: 名簿のログイン名が古いとき(本人が改名し、旧名を他人が取った)、その瞬間の照合でも別人に当たる。名簿の側が数値を持たなければ、この食い違いは検出できない
- **「リポジトリの中の名簿を (b) で認めるのは、第4章の『外側』からの後退ではないか」**。応答: 目的は変えず、目的を満たす手段を2つにする。(b) は IMPL-0415 が降りるまで未達で、表示は続く。後退か否かは、判定される側が単独で対応表を変えられるかで判断すべきで、ファイルの置き場所では判断できない。起草・監査の委員がなお後退と見るなら、「外側」を維持して (b) を採らない形でも、他の結論は変わらない

## R-5 テンプレートの手段と記録

### 結論

1. **主たる手段は名義の分離であり、権限設定ではない**。テンプレートは `/process-init` で担い手の名義を問い(R-1・R-3)、専用の名義を選んだ場合は、その数値の識別子を構成に登録して、その名義の承認・レビュー・記名を数えない(陽の判定)。専用の名義の担い手は承認を**作れても数えられない**(Copilot cloud agent の「依頼者の承認を数えない」と同じ、勘定で守る型。外部 1.1・5 の1)
2. 共有の構成のための**抑止**として、次を置く。抑止であって、防止の証拠ではないと標準とテンプレートに書く
   - 常駐の規則(CLAUDE.md)を、宣言行のレビューに限らず「AI の担い手は、手段を問わず、承認・レビュー・マージの承認の操作を作らない」へ広げる
   - 権限設定: `gh pr review` の deny を維持する。ホスティングの API を直接呼ぶ経路(`gh api` の書き込み、GraphQL の mutation、他の HTTP クライアント)は、前置きの一致で網羅できない。読み取りまで止める deny は採らず、**`gh api` を ask(人が呼び出しごとに見る)**にする
3. 標準の文言(EV-0220 の本文、ADR-0106 の反論の節を引き継ぐ新 ADR)は、「権限設定と常駐の規則で塞ぐ」と書かない。「共有の構成では、担い手が人の名義で承認を作ることを、権限設定と常駐の規則で抑止するが、止めたことを記録で示す手段は無い」と書く
4. **新しい ADR を起こす**(番号は採番時)。決定: (i) 担い手の名義を構成の入力にし、記録の無い担い手を共有とみなす、(ii) 名簿の人のアカウントを担い手に使わせないことを要求事項にし、満たせない構成を列挙に無い離脱とする(1.10.2 に行を足す)、(iii) 共有の構成の承認・記名を自己申告として数え開示する、(iv) 3.4.2 の権限の組が名義の権限を含むことの明確化、名義の変更を変化点にする、(v) 照合の鍵を数値の識別子にし、移行期間を置かない、(vi) 「リポジトリの外側」を目的で書く。ADR-0035(席どうしの分離)は補う関係、ADR-0106 の「反論されうる点」の #429 への回送を閉じる関係として、ステータスの表に書く。採用済み ADR の本文は書き換えない
5. 根拠水準マーク
   - **新 EV**: 「主要なホスティングで、人のアカウントと区別できる専用の名義を、1〜2名の体制が用意できる」という前提。GitHub は利用規約と App の文書で確認(E1 相当の文書の確認、実機の運用負担は未測定)。他のホスティングは未確認
   - **新 EV**: 権限設定と常駐の規則による抑止の効き目。E0。差し替え条件: 担い手が API を直接呼んで承認を作った事例の件数、または欠陥注入(担い手に承認を作らせる指示)での抑止の結果
   - **EV-0220**: 差し替え条件の「共有する構成の比率(#429)」は、構成の入力ができれば測れるようになる。測り方(構成の `performer` の名義の欄の集計)を書き足す
6. 実装マーク
   - 担い手の名義の欄(構成・D-0 表7・`/process-init`・`/process-change` の種別): 新 IMPL。降りるまで undelivered
   - 名簿の人のアカウントを担い手に使わせない要求と、1.10.2 の離脱の表示: 新 IMPL
   - 共有の構成の承認・記名を自己申告として数える集約: 新 IMPL
   - gate-criteria.md:84(数値の識別子・対応表の保守): 新 IMPL。現状 undelivered
   - 常駐の規則の拡大と `gh api` の ask: IMPL-0417 の note を改めるか、新 IMPL。**IMPL-0417 の現 note が「担い手が宣言行のレビューを出さない」を delivered と表示していることは、API 直の経路を止めていない事実と合わせて note に書く**
7. テンプレートの中の前提の食い違い(`recording.md:121-130` は共有を想定内とし、`process-change/kinds/performer.md:39` は担い手ごとの別トークンを前提にする)は、新 ADR に合わせて両方を直す。`recording.md` の後退経路は「列挙に無い離脱を持つ構成の経路」と明記し、`performer.md` は名義の欄の値で分岐させる

### 理由

1. **権限設定は、担い手の手元の道具の使い方を縛るだけで、ホスティングの記録には何も残らない**。外部の指針は一致して、エージェントの統制を識別と短命の資格情報で行うことを求める(OWASP ASI03 の対策1・6、CISA ほかの「distinct principal」)。プロンプトや手元の設定は、プロンプトインジェクションや別の経路で外れる。標準が「塞ぐ」と書けば、記録で示せない統制を統制として数えることになる。これは ADR-0106 決定6 が退けた「機械の承認を人の確認に見せる」と同じ種類の誤りである
2. **勘定で守る型が、プラットフォームに依存しない**。どのホスティングでも、専用の名義に承認の権限を与えないことは難しい(GitHub の PR の書き込みの権限は、PR の作成とレビューを分けない)。作れることを前提に、作られた承認を数えない方が、手段の違いに左右されない。そのために要るのは名義の識別子の登録(R-3)だけである
3. `gh api` を deny にすると、読み取り(PR の検査に要る照会)まで止まる。前置きの一致で書き込みだけを選んで止める手段は無い。ask は人が呼び出しごとに見るので、人の関与を記録しない点では抑止にとどまるが、読み取りを壊さない。CISA ほかの「高い影響の操作を、人の事前の承認なしに自律で実行させない」とも合う
4. 新 ADR を起こすのは、決定 (ii)(v) が、適合の主張に至る条件と G-6 の数え方を変える、あとから変えにくい決定だからである。ADR-0083 決定1 により、要求事項・判定基準を変える改訂は版の番号 N を上げる改訂に当たる(第1版の発行の前である現在は作業中の版の変更)

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `Bash(gh api:*)` を deny にする | 読み取りを壊し、HTTP クライアントや GraphQL の他の経路は残る。網羅できない禁止を網羅したように見せる |
| 権限設定の deny を書き込みのエンドポイントごとに列挙して「止めた」とする | 前置きの一致では引数の順・別名・別の道具で外れる。止めたことを記録で示せない |
| 権限設定と常駐の規則を、共有の構成の代償措置として定め、離脱を「逸脱」にする | 理由1。記録で示せない手段を代償措置に数えられない(R-1 の採らない案と同じ) |
| ホスティングの監査ログを集約に取り込み、アクセスの種別で人と担い手を区別する | R-2 の採らない案と同じ。組織・企業のプランに限られ、プラットフォームに依存する。補強として手引きに書く |
| 専用の名義に承認の権限を与えないことを要求事項にする | 主要なホスティングで権限の粒度が足りない(理由2)。勘定で守れば足りる |
| 何も足さず、EV-0220 の注記のまま #429 を閉じる | 内部 2.2 の3 のとおり、G-6 の承認を常駐の規則は禁じてもいない。黙ったまま閉じることになる |

### 反論されうる点

- **「ask は、人が毎回承認ボタンを押す運用に慣れて形骸化する」**。応答: そのとおりで、だから抑止と書き、EV(E0)で効き目を未測定と開示する。主たる手段は名義の分離である
- **「専用の名義を作っても、担い手の環境に人の `gh` 認証が残っていれば、担い手はそれを使える」**。応答: 使える。5.8.6 の「認証情報への接触を実行時に拒否する」に、環境に既にある人の認証を担い手が使うことが当たるかは書かれていない(内部 1.3)。新 ADR の決定に含め、「担い手の実行環境に、名簿の人の認証情報を置かない」を 5.8.6 の側で明確化するのが一貫する。ただし、これは R-1 の要求事項2 の実効の条件であり、満たしたことを記録で示す手段がやはり無い。担い手の名義の記録(自己申告)と内部監査の観点6 で確かめる。起草の委員に、5.8.6 へ置くか 3.5.3 へ置くかの判断を委ねる
- **「1.10.2 に行を足すのは、適合の主張に至れる採用者を減らす。規格として採用を妨げる」**。応答: 規格の価値は、主張された適合が中身を持つことにある。人の確認を記録で示せない構成に主張を許せば、主張そのものの意味が下がり、すべての採用者が損をする。判断軸は信頼性であり、採用者の数ではない

## 論点ごとの結論(1行)

- R-1: 黙らず担い手の名義を構成の入力として必ず問う(記録が無ければ共有とみなす)。全面の禁止は採らず、名簿の人のアカウントを担い手に使わせないことを要求事項にし、満たせない構成を 1.10.2 の列挙に無い離脱として足す
- R-2: 崩れるのは説明責任ではなく人が判断した証拠。G-6 の承認と効力を持つ記録の記名は自己申告として数え件数を開示の項目1 に出す。指示者の既定値と作成者の別は安全側に倒れるので変えず、その旨を明記する
- R-3: 3.4.2 の識別に名義は加えず、権限の組が名義の権限を含むことを明確化する。名義は D-0 表7・構成の別の欄に置き、変化点4 に名指しする(専用 → 共有は緩める向き)
- R-4: 数値の識別子の要求は維持し、照合の鍵を数値にする(M1+M4+M6)。期限つきの移行期間は置かず、ログイン名だけの照合は同定できていない承認として即時に表示する。PR 本文の `@アカウント` は検査の時点で数値に固定する。「外側」は目的で書き直す
- R-5: 主たる手段は名義の分離と陽の識別子による不算入。権限設定と常駐の規則は抑止と明記し、`gh api` は ask、常駐の規則は承認・レビュー全般へ広げる。新 ADR・新 EV 2件・新 IMPL を起こし、gate-criteria.md:84 のマーク欠落を undelivered で直す
