## 0. 現場から見た前提の補正(議題の事実に足すこと)

### 0.1 崩れるのは「承認する側」のアカウントであって、「作成する側」ではない

議題は「人の認証情報を AI の担い手と共有する構成」を一括りにしています。現場で体制に当てると、共有が統制を壊す場所は**誰のアカウントを共有しているか**で全く違います。

| 共有しているアカウント | 起きること | G-6 への影響 |
| --- | --- | --- |
| 作成者 A のアカウントを A の担い手が使う | AI が開いた PR の作成者が A になる。ブランチ保護が A の承認を止める。作成を指示した者の既定値(`ci-gates.md:681`)も A になる | **ほぼ壊れない**。崩れるのは「AI が作った変更か人が作った変更か」の区別(5.8.2 の AI の関与の記録、`gate-criteria.md:933` の前提)だけ |
| 承認者 B のアカウントを B の担い手が使う | B の担い手が `gh api` で A の PR へ APPROVE を出せる。ホスティングもテンプレートも B の承認として数える(内部 §2.2-1・3) | **壊れる**。独立した人の確認の4条件のどれもこれを止めない(条件4 の挙動要約も担い手が書ける) |
| 記名者 C のアカウントを C の担い手が使う | 宣言行のレビューを担い手が出せる。記録だけの PR では C のレビューが作成者のレビューになり数えない(`recording.md:121`) | 効力を持つ記録の帰属が自己申告に落ちる(ADR-0106 の既知の限界) |

2名の体制で2人とも手元の Claude Code を既定のまま使うと、A は作成側、B は承認側として**両方の行に同時に当たります**。前段(#380)の現場の意見は「AI が本人の名義で承認を出せる」ことを前提に格上げしましたが、承認の側の問題としては整理していませんでした。本件の要求は「担い手が、**承認・記名を数える人**のアカウントで操作できないこと」を軸に置くのが、現場の実態に合います。

### 0.2 「専用アカウントがある」と「人の認証情報に届かない」は別のこと

手元の Claude Code に専用のアカウントのトークンを渡しても(例: 環境変数 `GH_TOKEN`)、同じ OS の利用者のキーリングと git の資格情報ヘルパーには人のトークンが残ります。担い手は `env -u GH_TOKEN gh ...`、`gh auth switch`、`gh auth token`、`git push`(資格情報ヘルパー経由)で人の名義へ戻れます [推測]。Codespaces は利用者のトークンを環境へ自動で入れます [要確認]。

現場で分けるべきは名義の有無ではなく、**担い手の実行環境から人の認証情報へ到達できるか**です。

| 形 | 例 | 人の認証情報への到達 |
| --- | --- | --- |
| 甲 ホスティング側で動く | Copilot cloud agent、Claude Code Action(既定の App)、Cursor の Automations | 構成上、到達しない(外部 1.1・1.2・1.3) |
| 乙 手元だが隔離した環境で、専用の名義だけを持つ | devcontainer・別の OS 利用者・仮想環境に、bot のトークンだけを置く | 到達しない(隔離が守られている限り) |
| 丙 手元の、人と同じ環境で、専用の名義のトークンも渡す | `GH_TOKEN` に machine user の PAT、キーリングに人のトークン | **到達する**。既定の経路は bot の名義になるが、担い手が戻ろうと思えば戻れる |
| 丁 手元の、人と同じ環境で、人の認証情報のまま | Claude Code・Codex CLI・Cursor のエディタ内の既定 | 到達する(外部 1.7) |

1〜2名の採用者の大半は丁、意識の高い採用者でも丙に留まると見ます [推測]。丙を「分離した」と数えると、名義の上の分離を到達の分離と取り違えます。

### 0.3 専用の名義の用意の負担(体制ごと)

| 体制 | 現実的な手段 | 負担 |
| --- | --- | --- |
| 1〜2名(個人のアカウントの下のリポジトリ) | 無料の machine account(利用規約上、個人アカウントのほかに1つ。外部 1.6)を作り、リポジトリへ招く。または独自の GitHub App | machine account: メールアドレス、2要素認証の秘密と回復コードの保管、PAT の発行と更新。App: 秘密鍵の保管、短命トークンを作る補助スクリプト。どちらも数時間の初期作業と、トークンの失効のたびの更新 |
| 1〜2名(組織の下) | 同上。組織の有料プランでは machine user が席を1つ消費する [要確認]。App は席を消費しない(外部 1.6) | 席の料金(Team で1席分の月額)[要確認] |
| 3〜9名 | 組織の独自 App を1つ、全員の担い手で共用する。利用規約は「Multiple users may direct the actions of a machine account」を許す(外部 1.6) | App の秘密鍵の保守者が要る(AI維持管理者の作業)。担い手ごとに作成を指示した者を残す仕組み(PR 本文の `@アカウント`)が必須になる。各人の手元の環境を乙にする作業が人数分要る |
| 10名以上 | 組織・企業の App、Copilot cloud agent、Claude Code Action へ寄せる(甲)。企業の監査ログ(`actor_is_agent`・`programmatic_access_type`・`hashed_token`)が使える(外部 3.3・4.4) | 手元の担い手(丙・丁)が残る限り穴は残る。誰が手元で動かしているかの棚卸しが要る |

もう1点、現場で見落とされやすいことがあります。**私有リポジトリで必須の承認(ブランチ保護・ルールセット)を使うには、個人の無料プランでは足りず、有料のプランが要ります** [要確認]。1〜2名の採用者が G-6 を機械で強制しようとすると、専用の名義より先にここで料金が掛かります。専用の名義の負担だけを過大に見積もらないほうがよいです。

### 0.4 専用の名義を作っても、その名義の承認は数えられうる

machine user は型が `User` で、書き込みの権限を持てば APPROVE を出せ、ホスティングは必須の承認に数えます [推測。App の承認の扱いと合わせて要確認]。テンプレートが AI を見分ける手段は名義の語の一致(`aiNameReason`)と `is_bot` だけです(内部 §2.1)。`ci-runner-01` のような名前の machine user は**人として数えられます**。専用の名義を推奨するなら、その名義を構成に登録し、**数値の識別子で数えない側へ寄せる**仕組みが同時に要ります(R-3)。名義を分けるだけでは、穴の位置が移るだけです。

## R-1 共有の構成への要求の向き

### 結論

- **禁止しない。黙らない。推奨と開示だけにもとどめない。構成の必須の入力として問い、問いの答えに承認の数え方と主張の条件を結び付ける**
- 問う単位は2つ
  - 担い手ごと: 動く形(0.2 の甲・乙・丙・丁)と、動く名義(App・machine user・人のアカウント)とその数値の識別子
  - 人ごと: 「**このアカウントの認証情報に、どれかの AI の担い手が到達できるか**」。承認・記名を数える人(G-6 の確認者・外部の確認者・効力を持つ記録の記名者・判定者)には必ず問う
- 答えが無い場合は「到達できる」とみなす(`ci-gates.md:681` の「記録が無ければみなす」と同じ型)。丙は「到達できる」に数える
- 1.10.2 との関係: 現行の行「実行主体の文脈の認証情報を、席ごとに分けられない構成」とは**別の行**を足す。「承認・記名を数える人のアカウントの認証情報に、AI の担い手が到達できる構成」。適用の表明はできるが、適合の主張と逸脱を伴う適合の主張の条件を満たさない。主語が席どうしでなく人と担い手なので、現行の行の解釈を広げて読ませない
- 専用の名義(甲・乙)は推奨として書く。義務にはしない

### 理由

1. **禁止は検証できない**。担い手が人の `gh` 認証で動いているかを、リポジトリの記録から機械で判定する手段はありません(外部 §5-3)。検証できない禁止を置くと、採用者は「共有していない」と書いて済ませます。これは条項が信頼性を生まず、偽の申告を生む形です。1〜2名ではほぼ全員が丁なので、禁止は「全員が違反か、全員が偽る」のどちらかになります
2. **推奨と開示だけでは、G-6 の数え方が変わらない**。0.1 のとおり、承認者の側の共有は G-6 の独立した人の確認を数え間違えさせます。開示しても、集約は承認を人の確認に数えたまま「G-6 達成」と出します。数え方に結び付けない開示は、読み手に「達成」と「開示」の両方を見せ、判断を読み手へ押し付けます
3. **黙るのは、既に割れている前提を放置すること**。テンプレートの中で `recording.md`(共有を想定内)と `performer.md:39`(担い手ごとに別のトークン)が食い違っています(内部 §2.2-5)。採用者は自分の構成がどちらの前提に当たるかを知る手段がありません
4. **入力として問えば、答えに応じて数え方を機械で切り替えられる**。人ごとの答えがあれば、集約はその人の承認を「到達できる人の承認」として別に数えられます(R-2)。規格・指針はいずれもエージェントに固有の識別を持たせる向きです(外部 §5-2: OWASP ASI03、CISA ほか、NCCoE、SLSA の trusted robot)。ただし明文の禁止は見つかっていないので、本標準が禁止へ踏み込む根拠は無く、主張の条件で扱うのが釣り合います
5. 1.10.2 の別の行にする理由は、現行の行の主語が席(レーン)どうしだからです(内部 §5-1)。人と担い手の共有を現行の行に読み込ませると、「席ごとに分けている」と書いた2名の体制が、共有のまま条件を満たしたと読めてしまいます(内部 §0-1)

### 体制ごとに回るか

- **1名**: 既に適用の表明までしか述べられません(`overview.md` の注記)。新しい行が当たっても、述べられることは変わりません。変わるのは、外部の確認者の承認を数えるときに外部の確認者自身の到達を問うことです。外部の確認者が自分の Claude Code を自分の認証情報で動かしていれば、その承認は自己申告つきになります。外部の確認者への問いは「あなたの AI はあなたのアカウントで動きますか」の1問で、手間は小さいです
- **2名**: 最も影響を受けます。2人とも丁なら、新しい行が当たり、適合の主張は述べられなくなります。主張を望む2名の体制は、少なくとも承認する側の環境を乙へ移すか、担い手を甲へ移す必要があります。手間は 0.3 のとおり数時間と、トークンの定期の更新です。ここを「重いから課さない」とは考えません。2名の体制が述べる適合の主張は「独立した人が確認した」を中身に持ち、その中身を記録から示せない構成で主張を述べさせるほうが、標準として信頼を失います
- **3〜9名**: 承認者は複数いるので、到達できない承認者を1人確保すれば、その人の承認で G-6 を満たせます。全員の環境を乙にする必要はありません。現場では「承認を担う人だけ、手元の担い手を隔離した環境で動かす」運用が現実的です
- **10名以上**: 甲へ寄せる組織が多いと見ます。残る手元の担い手を入力で棚卸しできることが、この体制での主な効用です

### 譲れない点

- 問いに答えが無いときは「到達できる」とみなす。逆向き(答えが無ければ分離とみなす)の既定値を置かない
- 丙(専用の名義のトークンを渡したが、人の認証情報も同じ環境にある)を、分離として数えない
- 共有の構成を、条件付きでも適合の主張へ入れない。入れるなら、到達を記録から示す手段を先に定める(R-2 の企業の監査ログの経路)

### 採らない案

- **共有の禁止**: 検証できず、1〜2名で全員が違反か偽りになる(理由1)
- **推奨と開示だけ**: G-6 の数え方を変えず、「達成」の表示が残る(理由2)
- **黙る**: テンプレート内の前提の食い違いを放置する(理由3)
- **1.10.2 の現行の行の解釈を広げる**: 主語の違いを隠し、内部 §0-1 の字面の抜け道を残す(理由5)
- **担い手ごとの問いだけで、人ごとの問いを置かない**: 承認を壊すのは承認者の側の到達で(0.1)、担い手の一覧から承認者の到達は導けない。担い手が「人のアカウントで動く」と書かれていても、それが誰のアカウントかが無ければ集約は数え方を切り替えられない

### 反論されうる点

- 「入力も自己申告で、偽れる点は禁止と同じだ」: 同じではありません。既定値を「到達できる」に置くので、何も書かなければ厳しい側に倒れます。偽るには積極的に「到達しない」と書く必要があり、その記名が残ります。加えて、テンプレートの env-check が担い手の環境で `gh auth status` を実行し、キーリングに名簿の人のアカウントがあれば「到達できる」と観測できます [推測。実装の可否は要確認]。観測と申告が食い違えば所見にできます。禁止にはこの観測の結び付け先がありません
- 「2名の体制から適合の主張を奪う」: 奪うのは、独立した人の確認を記録から示せない構成からの主張です。乙・甲へ移せば主張は戻ります。主張の可否を構成の選択で戻せる形にしているので、体制の人数で一律に奪う規定とは性質が違います
- 「1.10.2 の別の行は、許可(逸脱)の審議中の Issue(`overview.md` の注記)と重なる」: 重なります。代償措置を定めた許可にするかはその Issue で扱い、本件は列挙に無い離脱として行を足すところまでにとどめます

## R-2 共有の構成で崩れる統制の扱い

### 結論

崩れる統制ごとに次のとおり扱います。「到達できる人」は R-1 の人ごとの問いで「到達できる」(既定値を含む)とされた人です。

| 統制 | 何が崩れるか | 扱い | 保証の開示 |
| --- | --- | --- | --- |
| G-6 独立した人の確認 | 到達できる人の承認が、担い手の承認でないことを示せない | **数えない**を原則にする。ただし、承認の操作が担い手の到達しない経路で行われたことを記録で示せた承認は数える(下の「示す手段」)。示せない承認は、独立した人の確認を経ていない変更に計上する | 新しい項目「担い手が到達できる人のアカウントの承認と、そのうち数えた件数・示した手段」 |
| 作成を指示した者の照合 | 作成者が人のアカウントになるので、AI が作った変更かを名義で見分けられない(`gate-criteria.md:933`) | **現行のみなし(`ci-gates.md:681`)を保ち、開示する**。作成者が到達できる人なら、その人と開発者の席の責任者を作成を指示した者とみなす。G-6 の条件2 で数えない側に倒れるので、統制としては崩れない | 既存のみなしの表示に、「作成者のアカウントに担い手が到達できる」を理由として足す |
| 効力を持つ記録の帰属(ADR-0106) | 記名者のレビューを担い手が出せる | **人の確認で補う**(現行の `recording.md` の後退経路の手順4)。記名者以外の人がいなければ自己申告として開示する(現行どおり)。ただし補う人自身が到達できる人なら、その確認も自己申告に落ちる | 項目1(自己申告の記録)に、理由「記名者のアカウントに担い手が到達できる」を分けて出す |
| PR の作成者の別(AI 作成か人の作成か) | 5.8.2 の AI の関与の記録が Co-Authored-By の自己申告だけになる | **開示する**。Co-Authored-By を証拠として扱わない(外部 4.2)。委任の判定は作成者の名義でなく差分の分類で行っているので、委任は崩れない | 新しい項目の中に「作成者のアカウントに担い手が到達できる PR の件数」 |

承認の操作が担い手の到達しない経路で行われたことを**示す手段**は、現場で使えるものを次の2つに限ります。

1. 承認者の担い手が甲・乙で、承認者の認証情報へ到達しない(R-1 の入力で「到達しない」、かつ env-check の観測と食い違わない)
2. 企業の監査ログで、承認のイベントが利用者のブラウザのセッションによるもの(トークンによる操作でない)と確かめられる(外部 3.3 の `programmatic_access_type`・`hashed_token`、4.4)。10名以上の企業の契約でだけ使える。**レビューのイベントでこの区別が実際に取れるかは実機で未確認**

### 理由

1. **G-6 を「開示して数える」にすると、達成の表示が残る**。G-6 の価値は「独立した人が見た」で、到達できる人の承認はその中身を示せません。条件4 の挙動要約も担い手が書けるので、補いになりません。数えたまま開示すると、出荷の判定者は「達成」を材料に判断します。数えない側に倒し、示せたものだけを戻すのが、信頼性の判断として筋が通ります
2. **「人の確認で補う」は G-6 では成立しない**。G-6 の承認を別の人の承認で補うと、その別の人が実質の確認者になるだけです。補う人の承認を数えればよく、元の承認を数える理由がありません。一方、効力を持つ記録の帰属は「本人の記録か」の確認なので、別の人の帰属の確認が意味を持ちます(ADR-0106)。統制ごとに扱いを分ける理由はここにあります
3. **作成を指示した者の照合は、共有の構成でむしろ安全側に倒れている**。作成者が人のアカウントになれば、ブランチ保護がその人の承認を止め、みなしが開発者の席の責任者も止めます。ここに新しい扱いを足す必要は無く、開示の理由を足すだけで足ります
4. **保証の開示の既存の項目1(自己申告)へ全部入れない**。項目1 は記録ごとの自己申告の件数です。到達の問題は構成の性質で、すべての承認に横断して掛かります。項目1 に混ぜると、件数の多い記録の自己申告に埋もれ、構成の問題として読めなくなります

### 体制ごとに回るか

- **1名**: G-6 は外部の確認者の承認でしか成立しません。外部の確認者が到達できない人なら数え、到達できる人なら数えません。外部の確認者に「AI を自分のアカウントで動かさない」ことを頼むのは現実的です(外部の確認者は確認だけをする立場なので、手元の担い手を承認に使う理由が薄い)
- **2名**: 2人とも丁なら、G-6 はすべて「数えない」になり、G-6 は未達になります。これは今の実態の正直な表示です。乙へ移るのは、承認する側だけでも足ります(互いに承認するなら2人とも)
- **3〜9名**: 到達しない承認者が1人いれば回ります。到達できる承認者の承認は集約で別に出るので、PR ごとに誰に承認を頼むかを `/pit` が示せれば、現場の流れは止まりません
- **10名以上**: 監査ログの経路(手段2)が使えれば、手元の担い手を使う人の承認もブラウザの操作として示せます。使えない契約なら手段1 だけです

### 譲れない点

- 到達できる人の G-6 の承認を、示す手段なしに独立した人の確認へ数えない
- 示す手段に Co-Authored-By・署名・自己申告の宣言を入れない(外部 4.1・4.2)
- 新しい保証の開示の項目は、件数が 0 でも項目として出す(「書かれていない」と「該当が無い」を読み手が区別できるように)

### 採らない案

- **G-6 を開示だけで数える**: 理由1
- **G-6 を別の人の承認で補う**: 理由2。補う人の承認を数えれば済み、元の承認を数える根拠にならない
- **全統制を一律に「数えない」**: 作成を指示した者の照合は既に安全側に倒れており(理由3)、PR の作成者の別は委任の判定に使っていない。一律にすると、崩れていない統制まで未達として表示し、読み手が本当に崩れた箇所を見分けられなくなる
- **承認の本文に「本人が操作した」の宣言行を求めて数える**: 担い手が同じ文を書ける。自己申告を証拠に見せかけるだけ
- **承認の時刻・場所(端末の位置など)で本人の操作を推定する**: 推定の根拠が無く、外れたときに検出できない

### 反論されうる点

- 「2名の体制で G-6 がすべて未達になり、現場は入力を偽って『到達しない』と書く」: その危険はあります。だから R-1 で env-check の観測を結び付けます。キーリングに承認者のアカウントがある環境で担い手が動いていれば、観測は「到達できる」を返し、申告との食い違いを所見にします。完全ではありません(承認者が別の端末で担い手を動かしていれば観測できない)。根拠水準マークで開示します
- 「監査ログの経路は企業の契約にしか無い。プラットフォームを選ばない標準に合わない」: 条項は「担い手の到達しない経路で承認が行われたことを記録で示す」までにとどめ、監査ログはテンプレート側の降ろし方の1つにします。示す手段を持たないプラットフォームでは手段1 だけが残ります
- 「到達できる人の承認を数えないと、1名+外部の確認者の体制で、外部の確認者が手元の AI を使うだけで G-6 が消える」: 消えるのが正しい結果です。外部の確認者の承認は、1名の体制で G-6 を成立させる唯一の材料で、その中身を示せないなら成立させてはいけません

## R-3 担い手の識別にアカウントを含めるか

### 結論

- **3.4.2 の担い手の識別(モデルの版・指示資産の版・権限の組)には含めない**。識別は適合性確認の単位であり、名義を入れると名義の変更で確認が失効する
- 名義は**別の欄**に置く。担い手ごとに次を持つ
  - 動く形(甲・乙・丙・丁)
  - 動く名義の種別(App・machine user・人のアカウント)
  - 名義の数値の識別子とログイン名。人のアカウントの場合は名簿の人の識別子
- 置き場: 構成の `performer` に欄を足す。D-0 表7 に列を足す。`/process-init` に問いを足す(R-1 の担い手ごと・人ごとの2問)
- 名義の変更(丁 → 乙、人のアカウント → App など)は**変化点として名指しする**。ただし変化点4 の「識別の変更」には入れず、別の変化点にする。帰結は適合性確認の失効ではなく、「承認の数え方の再評価と、名簿の到達の欄の確認」
- 登録した担い手の名義の数値の識別子による承認・レビューは、名義の語に依らず**数えない**(0.4 の穴を塞ぐ)

### 理由

1. **名義の変更は、担い手の判定の挙動を変えない**。適合性確認は「人が確定した過去の判定を再現できるか」を確かめます(3.4.2 要求事項2)。同じモデル・同じ指示資産の担い手を、人のアカウントから App へ移しても、再現の結果は変わりません。名義を識別に入れると、分離へ移る改善のたびに確認が失効し、採用者は分離を先延ばしにします。信頼性を上げる操作に罰を付ける形です
2. 「権限の組」に名義が含まれると読む余地はあります。ただ、権限の組が指すのはエージェントの権限設定(何のコマンドを許すか)で、名義はその外側で決まります。読みを曖昧なまま残すと、ある採用者は名義の変更で失効させ、別の採用者は失効させない、という運用の割れが起きます。**名義は権限の組に含めない**と明記するのが良いです
3. **数値の識別子で数えない側へ寄せないと、専用の名義の推奨が逆効果になる**(0.4)。machine user の名前に AI を示す語を入れることを採用者に頼る形は、命名の規約に統制を預けることになります
4. 変化点にする理由は、名義の変更が R-2 の数え方を直接変えるからです。丁から乙へ移った承認者の承認は、移った日から数えられるようになります。いつから数えるかの境目を記録に残す必要があります

### 体制ごとに回るか

- **1〜2名**: 担い手は1〜2件、問いは2問増えるだけです。数値の識別子は App なら App の bot のアカウントの id、machine user ならその id で、`gh api users/<login> --jq .id` の1行で取れます(外部 3.2)。手で写させず、`/process-init` が取って人に確かめさせます
- **3〜9名**: 共用の App を1件登録すれば、全員の担い手が同じ名義になります。担い手ごと(モデルと指示資産の組)には複数の行があり、名義は同じ、という表になります。丙・丁の人がいれば、人ごとの到達の欄で出ます
- **10名以上**: 担い手の数が増え、名義も複数になります(Copilot・Claude Code Action・独自 App)。外部調査の bot の id(`Copilot` 198982749、`claude[bot]` 209825114 など)は既知の名義として雛形に入れてよい候補です。ただし雛形の id を採用者の環境で確かめずに使わせない

### 譲れない点

- 名義の変更で適合性確認を失効させない(理由1)
- 登録した担い手の名義の承認を、数値の識別子で数えない側へ寄せる(理由3)
- 名義の変更の記録に、変更の日時と確かめた人を残す。数え方の境目になるため

### 採らない案

- **3.4.2 の識別に名義を入れる**: 理由1。分離への移行に失効の負担を掛ける
- **名義の欄を D-0 表5-2(人の名簿)にだけ置く**: 人ごとの到達は表5-2 に置けるが、担い手の名義は担い手の属性で、表5-2 の「AI の担い手のアカウントは載せない」(`deliverable-templates.md:434`)と衝突する。担い手の名義は表7 に置き、人の到達は表5-2 に置く、と分ける
- **名義の欄を置かず、名義の語の一致だけで見分け続ける**: 0.4 の穴が残る
- **名義の変更を変化点にしない**: 数え方の境目が記録に残らず、過去の承認を新しい数え方で数え直す誤りが起きる

### 反論されうる点

- 「名義を識別に入れないと、名義が変わった担い手を同じものとして扱うことになる。乗っ取られた名義で動く担い手を見落とす」: 乗っ取りは名義の問題で、担い手の挙動の問題ではありません。名義の変化点として記録し、R-2 の数え方を再評価させるのが対処です。適合性確認を失効させても乗っ取りは見つかりません
- 「`performer.md:39`(担い手ごとに別のトークンを発行する)は、名義が担い手の属性だという前提だ。識別に入れないと矛盾する」: 矛盾しません。名義は担い手の属性ですが、識別(適合性確認の単位)の要素ではありません。ただし `performer.md:39` は「担い手ごとに専用のトークンがある」ことを前提にしているので、丁の体制ではその手順が空振りします。R-5 で、名義の形ごとに手順を分けて直します

## R-4 名簿の数値の識別子による照合

### 結論

- **数値の識別子の要求(`gate-criteria.md:84` の前段)は維持し、すぐに降ろす**。今は実装マークが無く、降りていない規定として台帳に出ていない(内部 §0-6)。まず undelivered のマークを付けて表示し、テンプレートを改めた時点で delivered にする
- **「リポジトリの外側で保守する」は改める**(新しい ADR で)。置き場の規定を、置き場が満たす性質の規定に置き換える
  - 担い手が変更できない(現行の `Edit(./process.config.json)` の deny と契約検査)
  - 変更の記名者が、変更で利益を受ける人でない記録が残る(現行の `/process-change` と `accountsConfirmed` の型)
  - 変更の履歴が残り、過去の時点の名簿を読める(IMPL-0094)
  - 外側に置く理由を組織が持つ場合(実名を公開のリポジトリに置かない、など)は外側に置いてよい
- テンプレートの移行は **M1(型の混在)+ M4(機械に id を引かせ、人が確かめて入れる)+ M6(写しの id と名簿の id の食い違いを所見にする)** を採る。M2・M3 は採らない。M5 は**表示としてだけ**採り、移行の期間に login だけの照合を同定に数えることはしない
- ログイン名でしか照合できなかった承認は、保証の開示に件数を出し、**同定できたものとして数えない**(`gate-criteria.md:84` の後段の文言どおり)。移行の猶予は置かない。その代わり、移行の手間を1回の `/process-change` で済む大きさまで下げる
- PR 本文の `@アカウント`(作成を指示した者・委任の実施者・区分の確定者)は、**PR の時点で機械が数値へ解決し、写しへ残す**。後の照合は写しの数値で行い、ログイン名を時間をおいて引き直さない

### 理由

1. **数値の識別子の要求は正しい**。ログイン名は改名で直ちに、削除で 90 日後に他人が取れます(外部 3.1)。NIST IA-4 d. は識別子の再利用を禁じます(外部 2.1)。名簿の照合をログイン名で続けると、過去の判定記録の判定者を、後から別人に対応づける経路が残ります
2. **移行の手間は小さい**。名簿の人数は 1〜2名で1〜2件、10名以上でも数十件で、1件ごとに API を1回引くだけです。数値の識別子は写し・PR の検査の入力・ホスティングの照会で既に取れています(内部 §3.3)。手間の大半は人が数値を確かめることで、これは名簿へ足す人が記名する現行の流れ(`deliverable-templates.md:153`)に乗ります
3. **M4 だけでは危ない**。改名済み・他人が取った後のログイン名を機械に解決させると、別人の id を固定します(内部 §3.4)。移行の時点で名簿にいる人は、たいてい今そのログイン名を使っている本人なので、危険は小さいです。ただ、外部の確認者や離れた人の行では当たりえます。そこで M6 を組み合わせ、過去の写しの (login, id) の組と解決した id が食い違えば、移行の時点で所見にします。過去の写しは数値を持っているので、検証の材料はあります
4. **M5 を「数える」で採ると、条項の文言と食い違う**(内部 §5-4)。猶予の期間に login だけの照合を同定に数えるのは、`gate-criteria.md:84` が「同定できたものとして扱わない」と書いたことの一時停止です。手間が小さい移行に猶予を付ける理由はありません。表示として段階を出すこと(id で照合できた件数、login でしか照合できなかった件数)は、未達と省略の区別(ADR-0028)に沿うので採ります
5. **「リポジトリの外側」を改める理由**。置き場の規定は、それ単独では信頼性を生みません。外側の表は、CI と `/pit` が検証できる形で読めず、誰がいつ変えたかの履歴も組織の道具に依ります。1〜2名の体制では、外側の表は表計算のファイルになり、名簿の変化に追いつかなくなると見ます [推測]。リポジトリの中の名簿は、担い手の編集の禁止・記名つきの変化点・版の履歴という、外側の表より検証できる性質を既に持っています。しかも D-0 表5-2 は人の名簿をリポジトリの中の文書に置いており、置き場の規定は既に標準の内側で食い違っています。外側の理由として書かれているのは識別子の再利用(`qms-document-control.md:55`)だけで、置き場の理由は本文に無いので、#321 の経緯(`research/phase4-standard/321-decision.md`)との突合は起草で要ります
6. **PR 本文の `@アカウント` は原理上ログイン名だが、時間の幅が短い**。本文を書いてから PR の検査が走るまでの間に改名が起きる危険は小さく、PR の時点で数値へ解決して写しに固定すれば、後の照合は数値で行えます。照合が危うくなるのは「時間をおいて引き直す」場合だけです

### 体制ごとに回るか

- **1〜2名**: `/process-change` を1回実行し、機械が引いた id を人が確かめれば終わります(数分)。外部の確認者の id は、外部の確認者に自分の id を答えてもらう形でもよいです(id は公開の情報で、聞く負担は小さい)
- **3〜9名**: 名簿の全員で一度に行います。新しく入る人の行は、入る時点で id を持たせるので、移行は1回だけです
- **10名以上**: 名簿が組織の台帳(IdP など)と別にあるなら、台帳の側に GitHub の id を持たせ、名簿へ写すほうが現場では回ります。外側に置く理由がある組織は、上の性質を満たす限り外側でよい、という改めた規定がここで効きます

### 形骸化の見立て

- **数値の識別子は形骸化しにくい**。一度正しく入れれば変わりません。ログイン名と違い、改名で直す必要もありません
- 形骸化しやすいのは**名簿そのものの更新**(人の出入りの反映)で、これは数値の識別子では直りません。監査の観点6 の受け持ちのままです
- 危ういのは「人が数値を手で写す」運用です。写し間違いは別人の id を指しうるので、M4(機械が引く)と M6(写しとの突合)を外さないでください
- 移行した後に、名簿の行の id と、その人のアカウントで出たレビューの id が一致しない所見が出たら、それは改名・取り違え・乗っ取りのどれかです。所見を無視する運用が続くと形骸化するので、所見を出荷の集約で数え、0 でないまま出荷できないところまで持っていくかは起草で決めてください(現場の意見は、出荷の集約で失敗にする)

### 譲れない点

- login だけの照合を、移行の期間であっても同定に数えない
- 機械が id を引いた場合も、人が確かめて記名して入れる。機械に名簿を書かせない
- 過去の時点の名簿(id を持たない)で行った過去の判定は、遡って無効にしない。過去の写しの数値と移行した名簿の数値で突き合わせ、一致すれば同定できたものとして扱い、一致しなければ所見にする

### 採らない案

- **M2(並行の欄 `accountIds`)**: login と id の対がずれる。照合の鍵が2つになり、どちらで照合したかを毎回確かめる必要が出る
- **M3(名簿を外へ出す)**: 理由5。外の表を CI が検証できる形で読めない。外へ出すこと自体を要件にしない
- **M5 を数える側で採る(猶予の期間に login の照合を数える)**: 理由4
- **M4 を単独で採る**: 理由3
- **`@アカウント` を数値の識別子で書かせる**: 人が PR 本文に数値を書くことになり、写し間違いと読めない本文が増える。解決は機械にさせる
- **「リポジトリの外側」を据え置き、テンプレートの現状を離脱として表示する**: 置き場の規定が信頼性を生まない以上、採用者全員に意味の無い離脱を表示させることになる

### 反論されうる点

- 「『リポジトリの外側』は、リポジトリの書き込みの権限を持つ者(担い手を含む)が名簿を書き換える危険への対処で、改めるのは緩める向きだ」: 対処の中身は「担い手や利害のある者が名簿を書き換えられない」ことで、それは性質の規定で直接書けます。外側の表は、書き込みの権限を持つ人(組織の管理者)が無記録で変えられる点で、むしろ弱い場合があります。緩める向きでなく、統制の対象を置き場から性質へ移す変更だと考えます。ただし、緩める向きと見る委員がいれば、ADR-0055 の型(緩める向きの変更の扱い)との突合を起草で行う必要があります
- 「移行の猶予を置かないと、標準の版を上げた日に全採用者の G-6 が未達になる」: なります。その日に `/process-change` を1回実行すれば戻ります。未達の表示を避けるために同定の要件を一時停止する理由になりません。テンプレートは、id の無い行を見つけたら「次に実行するコマンド」として移行を示すべきです

## R-5 テンプレートの手段と記録

### 結論

- **権限設定の deny は抑止として広げるが、分離の手段として数えない**。広げる範囲
  - `gh api` の書き込みの操作のうち、レビュー・承認を作るもの(`pulls/*/reviews` への POST、GraphQL の `addPullRequestReview`・`submitPullRequestReview` の mutation)
  - 名義を切り替える・人のトークンを取り出す操作(`gh auth token`・`gh auth switch`・`gh auth login`)
  - 実装マークは「抑止」として delivered にし、「担い手が人の認証情報へ到達しない」の要求は**別の実装マークで undelivered のまま表示する**
- **常駐の規則(`template/CLAUDE.md`)を広げる**。現行は宣言行のレビューに限ります。「人のアカウントで、承認・レビュー・PR の承認を出さない。G-6 の承認を含む」と書き、宣言行の有無に依らない
- **env-check で到達を観測する**。担い手の環境で `gh auth status` を実行し、名簿の人のアカウントがキーリングにあるか、`GH_TOKEN` の名義が登録した担い手の名義か、git の資格情報ヘルパーが人のトークンを返すかを記録する。観測は R-1 の申告と突き合わせる
- `/process-init` に2問を足す(R-1)。`/process-change` に種別「担い手の名義の変更」を足す(R-3)
- `recording.md:121-130` と `performer.md:39` の食い違いを直す。`performer.md` の手順を名義の形(甲・乙・丙・丁)ごとに分け、丁ではトークンの失効・発行の手順が空振りすることを書く
- 名簿の照合: `findPersonByAccount` を `{login, id}` で受ける形へ改め、`gate-g5.yml` から PR の作成者の `user.id` も渡す。`material-attribution.mjs` と `aggregate-evidence.mjs` が捨てている id を照合に使う(内部 §3.2 の表の「ある」「捨てている」の行すべて)
- 新しい ADR: **2件**に分ける
  - ADR-A「AI の担い手の名義と人の認証情報への到達を構成の入力にし、到達できる人の承認を独立した人の確認に数えない」(R-1〜R-3、R-5 の前半)
  - ADR-B「名簿の照合を数値の識別子で行い、対応表の置き場の規定を性質の規定に改める」(R-4、R-5 の後半)
  - 分ける理由: 降ろす時期と降ろし先が違い、片方が遅れても片方を delivered にできる。また ADR-B は `gate-criteria.md:84` の採用済みの規定の置き換えを含み、置き換えの範囲を ADR-A と混ぜないほうが後から読める
- EV: 少なくとも次の3件に根拠水準マークが要る
  - 到達できる人の承認を数えない規則(E0。実測の比率が無い。差し替え条件は EV-0220 と同じく「担い手が記名者の認証情報で動く構成の比率」と、乙へ移った採用者の件数)
  - env-check の到達の観測が、到達を見落とさないという前提(E0。別の端末・別の OS の利用者で担い手を動かす構成は観測できない)
  - 企業の監査ログでブラウザの操作とトークンの操作を見分けられるという前提(E0。レビューのイベントで実機の確認が無い)
- IMPL: 新しい規定ごとに付ける。とくに「担い手が人の認証情報へ到達しない」は、テンプレートが完全には降ろせない要求なので、**adopter を降ろし先にした undelivered のマーク**として表示し続ける。`gate-criteria.md:84` の数値の識別子にも、まずマークを付ける

### 理由

1. **deny は前置きの一致で、抜け道が構造上残る**。`gh api -X POST`、引数の順序の入れ替え、`curl` に `gh auth token` の出力を渡す形、スクリプトのファイルを書いて実行する形のどれも、前置きの一致では止めきれません [推測]。止めきれない手段を分離として数えると、R-2 の数え方が根拠を失います。広げるのは事故(プロンプト注入や担い手の取り違え)の確率を下げるためで、統制の証拠にはしません
2. **常駐の規則が G-6 の承認を禁じていないのは、規則として欠けている**(内部 §2.2-3)。宣言行のレビューだけを禁じ、宣言行の無い承認を禁じない規則は、G-6 の承認を担い手に出させても規則に反しない、と読めます。規則の範囲を「人のアカウントでの承認・レビュー」へ広げるのは、抑止の層を正しい位置に置くためです
3. **観測は申告を補う唯一の機械の手段**。到達を記録から証明する手段は無いので、少なくとも環境を観測し、申告と食い違えば所見にします。観測の限界は EV で開示します
4. ADR を2件に分ける理由は上に書いたとおりです。#380 の ADR-0106 は1件にまとめ、「#429 で扱う」を2つ残しました。その2つは独立に進められる性質なので、ここで分けておくのが後の運用に効きます

### 体制ごとに回るか

- **1〜2名**: 権限設定と常駐の規則は `/process-init` が生成するので、追加の手間はありません。env-check は採用者の環境で1回走るだけです。丁の採用者には「到達できる」の観測が出て、G-6 の数え方に反映されます
- **3〜9名**: 各人の環境で env-check を走らせる必要があります。全員の観測を集める経路(各人が結果を構成の変化点として記録する)が要り、ここが現場で最も漏れやすい作業です。承認を担う人の分だけは必須、それ以外は任意、と範囲を絞るのが回る形です
- **10名以上**: 甲へ寄せた担い手には env-check の対象がありません(ホスティング側で動く)。手元の担い手を使う人の棚卸しに env-check を使います

### 譲れない点

- deny と常駐の規則を、分離の証拠として数えない。実装マークの state で抑止と分離を分ける
- 「担い手が人の認証情報へ到達しない」の要求を、テンプレートが降ろせないことを理由に消さない。undelivered のまま表示する
- `recording.md` と `performer.md` の食い違いを、どちらの結論でも同時に直す

### 採らない案

- **`gh api` をすべて deny する**: 読み取りの照会(集約・`/pit`・env-check が使う)まで止まり、担い手が作業できなくなる。現場では deny を外す採用者が出て、抑止そのものが消える
- **`gh api` の書き込みを ask にする**: 承認の作成を人の確認(ask)にしても、確認するのは同じ人で、その人の名義で承認が出ることに変わりはない。人がうっかり許可すれば、記録の上は人の承認になる。ask は「人が知っている」ことを示すだけで、「人が確認した」ことを示さない。レビュー・承認の作成は deny にする
- **担い手のトークンを機械で発行・更新する仕組みをテンプレートに持たせる**: App の秘密鍵を担い手の環境に置くことになり、乙の隔離を崩しうる。発行は人(AI維持管理者)の作業とし、テンプレートは手順と期限の表示にとどめる
- **ADR を1件にまとめる**: 理由4
- **到達の要求を adopter の責任として標準から外す**: 「書かれていない」と「課さないと決めた」の区別が付かなくなる。要求は標準に置き、降ろし先が採用者であることを実装マークで示す

### 反論されうる点

- 「deny を広げても抜けるなら、広げる意味が無い」: 意味は事故の確率を下げることで、統制の証拠ではありません。だから実装マークの state を分け、R-2 の数え方は deny に依らない形にしています。広げずに放置すると、担い手が通常の作業の中で `gh api` でレビューを作る事故(悪意なく承認を出す)が残ります
- 「env-check を各人の環境で走らせ続ける運用は形骸化する」: 形骸化します。だから観測が無い人は「到達できる」とみなす既定値(R-1)を置きます。観測を怠れば厳しい側に倒れるので、怠っても統制が緩みません
- 「ADR を2件に分けると、互いに引き合う箇所(担い手の名義の数値の識別子による除外)がどちらに属するか曖昧になる」: 除外の規則は ADR-A に、数値で照合する仕組みは ADR-B に置き、ADR-A は ADR-B の照合を使う、と書けば足ります

## 論点ごとの結論(1行)

- R-1: 禁止も沈黙も推奨だけもせず、担い手の名義と「人のアカウントの認証情報に担い手が到達できるか」を構成の必須の入力として問い、答えが無ければ到達できるとみなし、1.10.2 に別の行(承認・記名を数える人のアカウントに担い手が到達できる構成)を足して主張の条件から外す
- R-2: G-6 は到達できる人の承認を数えない(担い手の到達しない経路を記録で示せたものだけ戻す)、作成を指示した者は現行のみなしを保って開示、効力を持つ記録は人の帰属の確認で補い不可なら自己申告、PR の作成者の別は開示。保証の開示に到達の新しい項目を置く
- R-3: 名義は 3.4.2 の識別に入れず(適合性確認を失効させない)、構成・D-0 表7 に別の欄を足し、名義の変更を数え方の再評価を伴う別の変化点にし、登録した担い手の名義の承認は数値の識別子で数えない
- R-4: 数値の識別子は維持してすぐ降ろし(まずマーク)、M1+M4+M6 で移行し猶予は置かず、login だけの照合は同定に数えず件数を開示する。「リポジトリの外側」は性質の規定へ改める。PR 本文の `@アカウント` は PR の時点で数値へ解決して写しに固定する
- R-5: `gh api` のレビュー作成と `gh auth token` 等を deny して抑止として扱い分離に数えない、常駐の規則を G-6 の承認まで広げ、env-check で到達を観測する。ADR は2件、EV 3件、到達の要求は adopter の undelivered として表示し続ける
