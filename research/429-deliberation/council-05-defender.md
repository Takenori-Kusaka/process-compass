# #429 会議体 委員意見: 弁護(現行の規定を弁護する立場)

- 日付: 2026-11-05
- 立場: 現行の規定を弁護する。現行の規定とは、席どうしの認証情報の分離(3.5.1・3.5.3・1.10.2、ADR-0035/0082/0083)だけを求め、人と担い手の認証情報の共有には触れない規定と、名簿をログイン名の文字列で照合する準拠テンプレートを指す。変える必要が本当にあるか、変えると何が壊れるかを問う。弁護できない欠陥は欠陥と認める
- 判断軸: 信頼性。変更量の少なさは採否の理由にしない。「1〜2名の採用者の負担」も、それだけでは採否の理由にしない。負担が**統制の形骸化(偽の記録・離脱の常態化)を招く**場合に限り、信頼性の論点として扱う
- 入力: `council-00-agenda.md`、`survey-429-1-internal.md`(以下「内部」)、`survey-429-2-external.md`(以下「外部」)、`research/380-deliberation/`、ADR-0106

## 0. 弁護の総論

弁護の立場から最初に認めることがあります。現行の規定は「黙っている」のではなく、**黙っていることで、満たしていない統制を満たしたように読ませる**箇所を持ちます。弁護はできません。

- 1.10.2 の2名の体制の条件「席ごとに認証情報を分けている」(overview.md:645)は、席の中で人と担い手が1つの認証情報を共有する構成でも字面上は満たせる(内部 §1.1 観察)。この構成で、適合の主張に至る道が開いている
- G-6 の「AI と bot の名義による承認は数えない」(gate-criteria.md:949)は、担い手が人のアカウントで出した承認を人の承認として数える。この穴は G-6 の節に書かれていない(内部 §1.3)
- 第4章 :84 の数値の識別子の要求は、準拠テンプレートで満たされておらず、実装マークも無い(内部 §0-6)。ADR-0028・#222 の「降りていない規定を表示し続ける」に反する

一方、弁護が守るべきものもあります。

1. **共有そのものを禁じる根拠は無い**。外部調査が読めた範囲で、人の認証情報をエージェントと共有することを明文で禁じた規範的な条文は無い(外部 §5-2)。NIST AC-2(9) の shared account は人どうしの共有を想定した書きぶりで、GitHub の利用規約も「複数の**人**で1つのログインを共有すること」を禁じる(外部 §1.6・§2.1)。ローカルの Claude Code・Codex CLI・Cursor のエディタ内は、利用者の認証情報で動くのが既定である(外部 §1.7)
2. **共有の害は向きで違う**。作成の側の共有(担い手が席の責任者の名義で PR を開く)は、作成者 = 指示した人になり、ブランチ保護が自己承認を止める側に倒れる(内部 §1.3 の gate-criteria.md:933 の行)。Cursor は意図してこの形をとる(外部 §1.3)。害が出るのは**承認・レビュー・記名の側**の共有である。共有を一律に扱う規定は、無害な側まで罰する
3. **名簿をリポジトリの中に置き、履歴で時点の対応を引く現行の形には、信頼性の利点がある**(R-4 で述べる)

以下、この3点を軸に論点ごとに述べます。

## R-1 共有の構成への要求の向き

### 結論

- **禁止しない**。共有の構成を**構成の入力として問う**(席ごと。「AI の担い手が、その席の責任者の認証情報で動くか」)。未回答の既定値は「共有する」とする(ローカル実行の既定に合わせ、安全側へ倒す)
- 専用の名義(GitHub App の installation、または machine account)を**推奨**し、共有の構成を**開示**する。推奨は理由と費用(後述)を添える
- 1.10.2 の表へ「人と担い手の共有」を一般の行として**足さない**。ただし、**承認・記名を出す席**(G-6 の確認者、帰属の確認者、例外承認・停止の解除の記名者)で共有する構成は、2名の体制が主張に至る条件「席ごとに認証情報を分けている」を満たさないものと明記する。この点は現行の弁護を諦める
- 作成の側だけの共有(開発者の席の担い手が席の責任者の名義で PR を開く)は、主張の条件に影響させない

### 理由

1. 禁止は、ほぼすべての1〜2名の採用者に、守れない規定を課す。守れない規定は、構成の入力に「共有しない」と偽って書く誘因を生む。偽の申告は、黙っているより信頼性を下げる。禁止を採らない理由は採用者の負担ではなく、**申告の真実性**である
2. 黙ることも採らない。外部の規格・指針(OWASP ASI03 の attribution gap と Identity Sharing、CISA ほかの「distinct principal」、NCCoE の agent と human の区別、SLSA の trusted person と trusted robot の区別)はすべて同じ向きを向く(外部 §2)。明文の禁止が無いことは、黙ってよい根拠にならない
3. 構成の入力として問えば、R-2 の統制ごとの扱いを機械が出し分けられる。問わなければ、テンプレートは名義でしか見分けられず、共有の構成を常に「分離している」と誤って扱う(内部 §2.2-1)
4. 承認の側の共有を主張の条件から外すのは、適合の主張が**外部に向けた表明**だからである。G-6 の「確認者を確かめられる」は、記録から確かめられることを意味する。承認の側で共有する構成では、記録から確かめられない。弁護は、ここで現行の字面を守れない
5. 作成の側の共有を条件から外さないことの害は小さい。作成者の名義が人になっても、G-6 は承認者を数える統制であり、指示した者の既定値(ci-gates.md:681)は作成者 = 人のとき正しく働く。AI の関与の記録(5.8.2 の Co-Authored-By)は自己申告に留まるが、これは共有しない構成でも同じである(外部 §4.2)

### 費用と席の制約(採否の理由ではなく、推奨の文に書く事実)

- GitHub の machine account は、無料の個人アカウントのほかに1つまで(外部 §1.6)。2名の体制で各人が1つずつ持てば足りる。組織のプランでは、machine account は有償の席を消費しうる。GitHub App は席を消費しない(外部 §1.6)
- ローカル実行の担い手に App のトークンを渡す経路は、採用者の手作業が多い。Claude Code Action は既定で App として動く(外部 §1.2)。手元の対話の担い手を専用名義で動かす手順の負担は、未測定である
- これらは推奨の実行可能性を示す事実であって、推奨を義務へ上げない理由ではない。義務へ上げない理由は理由1(申告の真実性)である

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 人と担い手の共有を禁止する | 理由1。守れない規定は偽の申告を招く。明文の禁止を支える外部の条文も無い |
| 黙る(現状維持) | 理由2・4。主張の条件を字面で満たせる穴が残る。弁護できない |
| 1.10.2 の表へ「人と担い手の共有」を一般の行として足す | 作成の側だけの共有まで離脱にする。害の無い構成を離脱にすると、離脱の表示が常態化して読み手が区別できなくなる(却下と未達の区別、ADR-0028 の趣旨に反する) |
| 専用の名義を義務にし、1〜2名の体制だけ免除する | 規模で信頼性の要求を変える根拠が無い。承認の側の共有は規模に依らず記録を確かめられなくする |

### 反論されうる点

- 「既定値を『共有する』にすると、専用の名義を持つ採用者も入力を書かない限り開示に落ちる」— 認める。安全側の既定値であり、書けば解ける。逆向き(既定値を「分離」)にすると、何もしない採用者が分離していると扱われる
- 「構成の入力も自己申告だ」— そのとおり。申告の正しさは機械で確かめられない。R-5 の錠と、監査の観点(内部監査の観点6 の拡張)で補う。申告を問うこと自体は、黙るより監査の手がかりを増やす
- 「承認の側の共有で主張に至れなくなる2名の採用者がいる」— いる。その採用者は今も、記録から確かめられない主張をしている。主張を失うのではなく、成り立っていなかったことが表示される
- 根拠水準: 共有の構成の比率、専用名義の運用の負担は未測定。EV で開示する(EV-0220 の差し替え条件と同じ値を引く)

## R-2 共有の構成で崩れる統制の扱い

### 結論(統制ごと)

| 統制 | 共有の構成で崩れるか | 扱い |
| --- | --- | --- |
| G-6 の独立した人の確認(4条件) | **承認の側で共有するとき崩れる**。担い手の承認が人の承認として数えられる | 数える。ただし「共有の構成の承認」として件数を分け、保証の開示の項目1(自己申告)に出す。R-5 の錠(担い手が承認・レビューを作る経路の拒否)を構成に入れていない席の承認は、**数えない** |
| 作成を指示した者の照合・既定値 | **崩れない**。作成者が人の名義になるので、既定値(作成者 = 指示した者)が正しく働く | 変えない。G-6 の節の「作成者が AI または bot である場合」の文に、共有の構成では作成者が人の名義になり、ブランチ保護が自己承認を止める側に倒れることを書き足す |
| 効力を持つ記録の帰属(ADR-0106) | 崩れる(ADR-0106 が既に認める)。帰属の確認者の承認も、確認者の席で共有していれば同じく崩れる | ADR-0106 の自己申告の開示を維持する。帰属の確認者の席の共有も、G-6 と同じ扱い(錠が無ければ数えない) |
| PR の作成者の別(reviewerCheck) | 一部だけ働く。作成者と同じ名義のレビューは止めるが、別の人の名義で動く担い手は止めない(内部 §2.2-2) | 変えない。働く範囲を限界として明記する |

保証の開示の項目は、新しい項目を足さず、**開示の前提(構成の申告)として席ごとの共有の有無を出し**、件数は項目1 に出す。共有の有無は、すべての件数の読み方を変えるため、件数の項目の1つではなく前提として置く。

### 理由

1. 崩れる統制と崩れない統制を分けずに「共有なら全部数えない」とすると、作成の側の共有のように害の無い構成まで G-6 を未達にする。未達の常態化は、未達の表示の意味を失わせる
2. 承認の側の共有を一律に「数えない」とすると、2名の体制のローカル実行の採用者は G-6 が常に未達になる。標準は「未達を表示し続ける」立場をとるので、未達そのものは許容できる。しかし、G-6 が常に未達の体制では、採用者は G-6 の記録を残す動機を失う。錠を条件に数え、自己申告として開示するほうが、記録が残り、監査が読める
3. 錠を数える条件にするのは、帰属を機械で確かめられない構成で、採用者が**できる最善の手当て**を数える条件にするためである。錠は証拠ではない(R-5)。だから数えた件数を自己申告として開示する
4. 自己申告の開示は、ADR-0106 が帰属の確認者を置けない体制で既に採った型(gate-criteria.md:121)と同じである。新しい型を作らない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 共有の構成の承認をすべて数えない | 理由1・2。作成の側の共有まで巻き込み、G-6 の未達を常態化させる |
| 共有の構成の承認をすべて数え、開示もしない(現状) | 弁護できない。担い手の承認を人の承認として数える穴を黙って残す |
| 共有の構成で、人の確認を別途課して補う(聞き取り・対面の確認) | 聞き取りは監査の観点28 が既に担う事後の手当てで、ゲートの時点の統制にならない。ゲートの時点に人の確認を足すと、その確認の帰属も同じ共有で崩れる(無限後退) |
| Co-Authored-By・署名の有無で担い手の操作を見分ける | 自由記述の trailer と鍵の署名は、人の名義の操作を人の操作と区別する証拠にならない(外部 §4.1・§4.2) |
| 開示に「共有の構成」の新しい項目を足す | 件数の項目と並べると、前提と結果が混ざる。前提として置く |

### 反論されうる点

- 「錠を条件に数えるのは、錠の有無を自己申告で数えることにならないか」— なる。錠の設定は担い手の手元の設定であり、CI からは見えない。だから数えた件数は自己申告として開示する。数えない案より記録が残る、という比較で採る。信頼性の差は小さい可能性を認め、EV で開示する
- 「G-6 の節に共有の構成を書き足すと、効力を持つ記録の範囲(#380)を超えて G-6 へ広げることになる」— 広げる。内部 §5-2 のとおり G-6 も同じ前提で崩れており、範囲を効力を持つ記録に留める理由は #380 の議題の範囲だけだった。範囲の都合で穴を残さない
- 根拠水準: 錠による抑止の効果は未測定

## R-3 担い手の識別にアカウントを含めるか

### 結論

- **3.4.2 の担い手の識別(モデルの版・指示資産の版・権限の組)に、アカウントを足さない**
- 代わりに、担い手の**動作の名義**(専用の名義のアカウントと数値の識別子、または「席の責任者の認証情報で動く」の別)を、識別と別の欄として構成・D-0 表7 に置く
- 動作の名義の変更は変化点(3.13.1)として扱い、構成と D-0 の更新・通知を要する。ただし、3.4.2 要求事項7 の**確認の失効の契機にはしない**。名義の変更が権限を変える場合は、「権限の組」の変化として既存の契機で失効する
- テンプレートの `process-change/kinds/performer.md:39`(担い手ごとに別のトークン)と `gate/reference/recording.md:121-130`(共有を想定内とする)の食い違いは**欠陥として認める**。動作の名義の欄に従って、両方の書き方を条件つきに改める

### 理由

1. 3.4.2 の識別は、**適合性確認の単位**である(要求事項1・7)。確認は、過去の判定の再現と欠陥注入の検出で担い手の挙動を確かめる。アカウントが変わっても、モデルと指示資産と権限が同じなら挙動は変わらない。識別に入れると、共有から専用の名義へ移る(推奨の向きの変更)だけで確認が失効し、再確認まで協働が上限になる。推奨の向きの変更を罰する規定は、R-1 の推奨と衝突する
2. 一方で、名義は G-6・帰属の統制の扱いを変える(R-2)。どこにも書かなければ、機械が出し分けられない。だから識別と別の欄に置く
3. 「権限の組」は、名義が持つ権限の範囲を既に含みうる。名義の変更が権限を変えるなら既存の契機で失効する。二重の契機を作らない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 識別にアカウントを足す | 理由1。推奨の向きの移行で確認を失効させる |
| どこにも書かない(現状) | 理由2。R-2 の扱いを機械が出し分けられない。テンプレート内の食い違いも残る |
| 表5-2(人の名簿)に担い手のアカウントを書く | 名簿に AI を書かない規定(deliverable-templates.md:434、`rosterProblems`)と衝突する。人の名簿と担い手の欄を混ぜない |

### 反論されうる点

- 「専用の名義へ移った時点で、担い手が新しい権限を持つことが多い。失効させないのは緩い」— 権限が変わるなら既存の契機で失効する。名義の変更だけで権限が同じ場合に限って失効させない。権限が同じかの判断を人の申告に委ねる点は残るため、変化点の記録に「権限の組を変えたか」を必須の問いとして置く
- 「名義の欄も自己申告だ」— R-1 と同じ。数値の識別子を書かせれば、写しの作成者・レビューの書き手の id と突き合わせられる(専用の名義の場合)。共有の場合は区別できないことを開示する

## R-4 名簿の数値の識別子による照合

### 結論

- 第4章 :84 の**数値の識別子の要求は維持する**。準拠テンプレートが満たしていないことと、実装マークが無いことは**欠陥として認める**。直ちに `state=undelivered` の実装マークを付け、降ろすまで表示し続ける
- 第4章 :84 と qms-document-control.md の「**リポジトリの外側で保守する**」は、維持を弁護しない。理由を欠く要求として、「判定される側が単独で書き換えられない場所で、変更の履歴が残る形で保守する」へ改めることを求める。この改定は新しい ADR で行う
- 移行の形: M1(要素の型の混在)を採り、M4(機械が id を引き、人が記名して入れる)と M6(ホスティングの (login, id) と名簿の (login, id) の食い違いを所見にする)を組み合わせる。M5(照合の段階の表示)は「表示」の部分だけ採る
- ログイン名でしか照合できなかった承認は、:84 の文言のとおり**同定できたものとして扱わない**。ただし :84 の適用範囲は「承認レビューを判定記録とする保全の条件」であり、G-6 の承認の数え方全体ではない。範囲を広げる場合は別に決める
- PR 本文の `@アカウント`(作成を指示した者・委任の実施者・区分の確定者)は数値にしない。検査の時点でログイン名から id へ解決し、解決した id を検査の結果に残す

### 理由

1. 数値の識別子の要求は正しい。ログイン名は改名で直ちに、削除後 90 日で他人が取れる(外部 §3.1)。NIST IA-4 d. の識別子の再利用の防止を満たさない。弁護の余地は無い
2. ただし、現行のログイン名の照合の危険は、議題が想定するより狭い。写しは承認の時点の (login, id) を両方持つ(内部 §3.3)。承認の時点で名簿のログイン名と一致したなら、その時点のログイン名は名簿の人のものであった蓋然性が高い。危険が出るのは、**名簿に書いた後、承認までの間に、そのログイン名が他人へ移った場合**と、**時間をおいた照合**である。M6 はこの前者を検出し、名簿に id を書けば後者が消える。弁護はここで「だからログイン名で足りる」とは言わない。言えるのは、移行の間の危険の大きさが限られていることだけである
3. 「リポジトリの外側」を弁護しないのは、要求の理由が書かれていないからである。qms-document-control.md の理由(匿名化と再取得)は数値の識別子の理由であって、置き場所の理由ではない。しかも外側へ出すと、時点の名簿への対応(IMPL-0094、gate-criteria.md:968)が読む**構成の履歴**を失う。リポジトリの中の名簿は、担い手の権限設定で編集を止め(`generate-profile.mjs:5530-5535`)、変更は PR とブランチ保護を通る。外側の表は、CI と `/pit` が読む経路と、読めないときの扱いを新たに要し、その表の変更の履歴と帰属を誰が保証するかが定まっていない。外側に置くほうが信頼性が高いと言える根拠は無い
4. M1 を採るのは、既存の文字列の名簿をそのまま通しつつ、id を持つ人から順に id で照合できるからである。M2(並行の欄)はログイン名と id の対がずれる。M3(外へ出す)は理由3
5. M4 の危険(改名済みのログイン名を解決すると別人の id を固定する)は、解決の結果を人が記名して入れる形で抑える。さらに、写しの過去の承認の (login, id) と解決した id が食い違えば所見にする(M6)。過去の承認があればその id が最も確かな出所である
6. M5 の「期限を置いてログイン名だけの照合を数える」は採らない。:84 の文言は「同定できたものとして扱わない」であり、移行期間に数えることは条項と食い違う。厳しくする向きの規定を、テンプレートの都合で緩めて運用しない。表示の部分(id で照合できた件数と、ログイン名でしか照合できなかった件数を分けて出す)は採る
7. PR 本文の `@アカウント` は、指示した者の自己申告の欄であり、書いた時点のログイン名で人を指す。数値を書かせても、書く者が正しい数値を書く保証は増えない。検査の時点で解決して残せば、時間をおいた照合の危険は消える

### 何が壊れるか(採用者への影響)

- 契約検査(`rosterProblems` :553-555)は今、文字列でない要素を拒否する。M1 では受け入れるよう改める。既存の名簿は壊れない
- `accountsConfirmed`・`changeLog[].accountConfirmations`・`resolveSigner`・D-0 の生成区間(IMPL-0301)・`process-change/kinds/accountable.md` の様式は、型の混在に合わせて改める必要がある(内部 §3.4 M1)。これは変更量の問題であって、採否の理由にしない
- 承認レビューを判定記録とする採用者は、名簿に id を足すまで、その記録が保全の条件を満たさないと表示される。今も満たしていない状態が、表示されるようになるだけである

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| :84 を「ログイン名でもよい」へ緩める | 理由1 |
| リポジトリの外側の要求を維持し、名簿を外へ出す(M3) | 理由3 |
| M2 並行の欄 | 対がずれる |
| M5 の期限つきでログイン名の照合を数える | 理由6 |
| PR 本文に数値の識別子を書かせる | 理由7 |
| node_id で照合する | 新旧の形式が混在する(外部 §3.2)。REST の `id`(= GraphQL の `databaseId`)を使う |

### 反論されうる点

- 「リポジトリの外側を改めるのは、#321 で決めた保全の条件を覆す」— 覆す。ただし #321 の決定の記録(`321-decision.md:52・70`)に置き場所の理由は無い。理由の無い要求を、理由のある要求(時点の名簿の対応)と衝突したまま残さない。新しい ADR で決める
- 「名簿をリポジトリの中に置くと、判定される側が名簿を書き換えて自分を確認者にできる」— 担い手には権限設定で止め、人には PR とブランチ保護で止める。1名の体制では本人が書き換えられるが、それは外側の表でも同じである。名簿の変更の記名は監査の観点6 が見る
- 根拠水準: M4 の解決の誤りの頻度、M6 が検出する食い違いの頻度は未測定

## R-5 テンプレートの手段と記録

### 結論

- **権限設定の deny は統制ではなくガードレールとして書く**。現行の文書が「権限設定で止める」と読める箇所(IMPL-0417、EV-0220)は、`gh api`・GraphQL の mutation・トークンを直接使う経路を止めないことを明記する。この点は弁護しない
- 権限設定の deny は、`gh pr review` に加え、レビューと承認を作る `gh api` の経路(`pulls/*/reviews` への POST、GraphQL の `addPullRequestReview`・`submitPullRequestReview`)を対象に広げる。前置きの一致では方法の指定(`-X`・`--method`・順序)で外れるため、PreToolUse のフックでコマンドを解析して拒否する形を採る
- `gh api` の全面の deny は採らない
- 常駐の規則(`template/CLAUDE.md:106`)は、宣言行のレビューに限らず、「担い手は、人の名義で承認・レビュー・判定の記名を出さない」へ広げる
- 新しい ADR を起こす。内容: 共有の構成を禁止せず構成の入力として問うこと、承認の側の共有の扱い、動作の名義を識別と別の欄に置くこと、名簿の数値の識別子と置き場所の改定、錠をガードレールとして位置づけること、採らない案
- EV: 錠の抑止の効果、共有の構成の比率、M4・M6 の誤りの頻度。IMPL: :84 の数値の識別子の照合(新規、undelivered から)、名簿の置き場所の要求、動作の名義の欄、承認の経路の錠、常駐の規則の拡張

### 理由

1. 共有の構成では、担い手は人と同じトークンを持つ。どの錠も、同じトークンで `curl` を叩く経路まで止められない。錠を統制として書けば、満たしていない統制を満たしたように読ませる(総論の欠陥と同じ型)
2. それでも錠を置くのは、R-2 の「数える条件」と、誤操作(担い手が指示を誤解して承認を出す)の防止に効くからである。悪意の担い手ではなく、誤った担い手を止める手段として信頼性に寄与する
3. `gh api` の全面の deny は、env-check(`adoption-trial.mjs:1235-1345`)・照会・M4 の id の解決など、テンプレートが読み取りに使う経路を壊す。読み取りを壊すと、採用者は deny を外し、ガードレールが丸ごと消える
4. 常駐の規則を宣言行に限る理由は、#380 の範囲の都合だった。G-6 の承認も同じく崩れる(R-2)ので広げる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `gh api` を全面に deny する | 理由3 |
| 現行の前置きの一致の deny だけで足りるとする | 方法の指定と GraphQL で外れる。弁護できない |
| 錠を統制(数えれば信頼できる)として書く | 理由1 |
| ADR を起こさず、条項の文言の修正だけで済ませる | 共有の構成を禁止しない判断、名簿の置き場所の改定は、あとから変えにくい方針の決定である |
| 担い手の操作を GitHub の監査ログ(`actor_is_agent`)で見分ける | 公式に確かめられたのは Copilot だけで、第三者のエージェント・ローカル実行で立つかは未確認(外部 §4.4)。組織の監査ログは企業・組織のプランに依り、180 日で消える。将来の選択肢として ADR に記録し、今は採らない |

### 反論されうる点

- 「フックの解析も、別の書き方(シェルの変数・スクリプトの経由)で外れる」— 外れる。だからガードレールと書く。外れる経路があることを開示し、数えた件数を自己申告として出す(R-2)
- 「錠を数える条件にすると、錠の設定を外した担い手の承認も、錠があると申告されれば数えられる」— そのとおり。CI からは錠の有無を確かめられない。この弱さは開示し、監査の観点で設定の版を確かめる。専用の名義を使えば、この問題自体が消える。これが R-1 の推奨の理由である

## 1. 論点ごとの結論(1行ずつ)

- R-1: 禁止せず、席ごとの構成の入力として問い(既定値は「共有する」)、専用の名義を推奨して開示する。1.10.2 に一般の行は足さないが、承認・記名を出す席の共有は2名の体制の主張の条件を満たさないと明記する(現行の字面は弁護しない)
- R-2: 崩れるのは承認の側(G-6・帰属の確認)だけで、作成を指示した者の既定値は崩れない。承認の側は錠を置いた席に限り数え、自己申告として項目1 に出し、共有の有無は開示の前提として出す
- R-3: 3.4.2 の識別にアカウントを足さず、動作の名義を別の欄(構成・D-0 表7)に置き、変化点にするが確認の失効の契機にはしない。テンプレート内の食い違いは欠陥として直す
- R-4: 数値の識別子の要求は維持し、未実装・マーク無しは欠陥と認めて undelivered を表示する。「リポジトリの外側」は理由を欠き時点の名簿の対応と衝突するので改める。移行は M1+M4+M6、M5 は表示だけ。PR 本文の `@アカウント` は検査の時点で id へ解決する
- R-5: deny は統制でなくガードレールと明記し、レビュー・承認を作る `gh api`・GraphQL の経路をフックで拒否する(`gh api` の全面 deny は採らない)。常駐の規則を承認全般へ広げ、新しい ADR・EV・IMPL を起こす
