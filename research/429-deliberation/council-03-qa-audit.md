## 0. 監査の立場から先に示す事実(調査に無い、または調査より踏み込んだもの)

### F-0 2つの問題を混ぜない: 「どのアカウントか」と「アカウントの向こうで誰が操作したか」

議題は、名簿の照合(R-4)と認証情報の共有(R-1〜R-3)を1つの Issue で扱います。監査の立場からは、この2つは**別の欠け**です。

| 欠け | 何が分からなくなるか | 数値の識別子で直るか |
| --- | --- | --- |
| 名簿の照合がログイン名 | 記録のアカウントが**名簿のどの人**か | 直る。id は再利用されない(NIST IA-4 d. の要求を満たす識別子) |
| 認証情報の共有 | アカウントの操作を**人が行ったか担い手が行ったか** | 直らない。共有の下では、id も login も同じ値を返す |

数値の識別子を入れても、共有の構成の帰属は少しも強くなりません。逆に、共有の扱いを決めても、改名・再取得による誤同定は残ります。会議体の結論で、片方の手当てがもう片方を直したかのように書かないことを求めます。

### F-1 共有の構成で、G-6 の独立した人の確認は「人が操作した」ことを示さない [確認]

2名の体制(A・B)を考えます。B が自分の手元で Claude Code を使えば、その担い手は B の `gh` の認証で動きます。これは既定の利用です(外部調査 1.2・1.7)。

1. A の担い手が A のアカウントで PR を開く(作成者 A。作成を指示した者の欄は空なので既定で A)
2. B の担い手が、B のセッションの中で `gh api repos/<o>/<r>/pulls/<n>/reviews -f event=APPROVE -f body='<8文字以上の挙動要約>'` を実行する
3. `check-pr.mjs:667-697` の `approverFindings` は、`author.login` が名簿の B に対応し、`is_bot` が偽、AI を示す語に当たらず、作成を指示した者でなく、挙動要約の最低限の形を満たすので、**B の独立した人の確認として数える**。集約(G-7)も同じ条件で数える

止めているのは権限設定の `Bash(gh pr review:*)` の deny だけです(`generate-profile.mjs:5527`)。次の経路はどれも止まりません。

- `gh api .../reviews` に `-f`/`-F` を付ける形。`gh api` は引数を足すと既定の方式が POST になるため、`-X POST` の文字列も現れない [確認: gh の仕様]
- `gh api graphql` の `addPullRequestReview` / `submitPullRequestReview`
- `gh auth token` で取り出したトークンを `curl` に渡す形
- `node -e` や担い手が書いたスクリプトの中から `gh` を呼ぶ形。権限設定の規則は担い手が入力したコマンドの文字列に掛かり、子プロセスには掛からない [推測: Claude Code の権限設定の作り。ただしテンプレート自身の `ghHosting`(`material-attribution.mjs:233`)が同じ形で `gh` を呼んでいる]

常駐の規則(`template/CLAUDE.md`)は、宣言行のレビューを出さないことしか定めていません。**G-6 の承認を担い手が出してはならないという規則は、常駐の規則にも権限設定にも無い** [確認]。挙動要約の最低限の形(8文字以上)は、担い手が苦もなく満たします。

監査で確かめられるのは「B のアカウントが承認した」までです。「B が読んだ」「B が操作した」は、ホスティングの記録(REST のレビュー、写し)からは確かめられません。GitHub の監査ログの `programmatic_access_type`・`hashed_token`・`user_agent` は Web の操作とトークンの操作を分けられますが、API で引けるのは Enterprise Cloud に限られ(外部調査 3.3)、ユーザー所有のリポジトリでは使えません。

### F-2 作成者の側の共有は G-6 を崩さない。崩すのは承認・記名を出す側の共有 [確認]

作成者 A の認証情報で担い手が PR を開いても、GitHub は作成者 A の自己承認を止め、`instructorsOf` の既定値(`check-pr.mjs:644-649`)は A を指示者とみなします。この向きの共有は、G-6 の勘定を崩しません。基準4 の本文(`gate-criteria.md:933`「変更の作成者が AI または bot である場合…」)は、作成者が人の名義の AI である場合に触れていませんが、結果として止める側に倒れます。

崩れるのは、**承認・宣言行のレビュー・帰属の確認・記名を出す人の認証情報を、担い手が使える構成**です。1〜2名の体制では、承認者も手元で担い手を使うので、ほぼ全員がこれに当たります [推測]。会議体が「共有するか」を問うとき、作成の側と承認の側を分けずに問うと、要求の向きが合いません(R-1)。

### F-3 後退経路の「代筆の有無を後から確かめられる」は、共有の構成では成り立たない [確認]

`recording.md:121-130` の後退経路は、記名者が「人が書く欄」を自分の名義のレビューのコメントとして書き、草案の文脈がそれを一字も変えずに写す手順です。根拠は「記名者のコメントが PR に残るため、代筆の有無を後から確かめられる」です。

この後退経路は、まさに**認証情報を共有する体制のために置いた**ものです(`recording.md:115-116`)。その体制では、記名者のアカウントのコメントを担い手が書けます(`gh pr review` は deny されていますが、`gh pr comment` と `gh api` は止めていません)。手順4 の「記名者以外の人の承認が帰属の確認になる」も同じです。確認者が見られるのは「記名者のアカウントが作成した」ことだけで、それは共有の下では帰属の証拠になりません。

**後退経路は、共有の構成でだけ使う手順なのに、共有の構成で成立の根拠を失っています**。見かけ上だけ成立する統制の典型です。

### F-4 改名・削除後の再取得で、名簿の人の承認と宣言行のレビューを第三者が出せる [確認・要実機]

`findPersonByAccount`(`config.mjs:601-606`)は `people[].accounts` の文字列と、レビューの `login` の一致で人を引きます。数値の識別子は写し(`record-copy.yml:82`)と PR の検査の入力(`gate-g5.yml:338`)に入っていますが、照合には使っていません(内部調査 3.2)。加えて、**レビューの書き手がリポジトリへの書き込みの権限を持つかを、どの検査も見ていません**(`author_association` を読むコードはテンプレートに無い)[確認]。

経路:

1. 名簿の人 P(`accounts: ["p-old"]`)が GitHub で改名する。旧名は直ちに他人が取れる(外部調査 3.1)。削除なら 90 日後
2. 改名を知らせる仕組みは無く、名簿は `p-old` のまま残る(改名を検出する検査も無い。M6 は未実装)
3. 第三者 Q が `p-old` を取得する
4. 公開リポジトリでは、書き込みの権限の無い者もレビューを出せる。その承認は必須の承認数に数えられないが、レビューとしては残る [要実機: REST の `state` が `APPROVED` で返ること。返るなら次が成り立つ]
5. Q の承認は、`approverFindings` で P の独立した人の確認に数えられる。ルールセットの必須の承認数(`team.json` は 1)は別の正規の承認で満たされていれば、**集約が求める2人目(軸C・軸E、`coreReviewerCount`)を Q が埋められる**
6. Q が宣言行のレビュー(`例外承認: <ID>`)を出すと、`reviewerCheck`(`material-attribution.mjs:67-80`)は P 本人の操作による帰属の裏づけとして数える。**P を記名者とする例外承認が、P の関与なしに効力を持つ**

非公開のリポジトリでは、Q が読み取りの権限を持たない限り 4 は成り立ちません。ただし、組織の中で旧名を別の社員が取る場合は成り立ちます。

改名の逆向き(P が改名後の新しい名前で承認する)は「名簿の人へ対応づかない」として数えられません。安全側に倒れますが、未達の理由が「名簿に無い」と表示され、改名という原因は表示されません。

### F-5 PR の時点の検査は、名簿に対応づかない指示者を黙って落とす [確認]

`instructorsOf`(`check-pr.mjs:644-649`)は、欄「作成を指示した者」の `@アカウント` を `findPersonByAccount` で引き、引けなかったものを `filter(Boolean)` で落とします。欄に記入がある(トークンが1つ以上ある)ので、作成者への既定値にも戻りません。

経路: 指示者 Y が改名した後に、欄へ旧名 `@y-old` が書かれる(テンプレートの複製・担い手の記憶・Issue からの写し)。`instructors` は空になり、**Y 本人の承認が G-6 の独立した人の確認として PR の時点で数えられる**。誤記(`@yamda`)でも同じです。

集約の側(`aggregate-evidence.mjs:1092・1736`)は「作成を指示した者を名簿と対応づけられない」として扱い、G-7 で差し戻します。PR の時点と出荷の時点で判定が割れており、PR の時点の検査を通った変更が出荷で初めて止まります。検出はされますが、PR の時点の表示は誤りです。

### F-6 判定者の数値の識別子の表示は、照合したように見えて照合していない [確認]

IMPL-0125(delivered)の欄「判定者(アカウントの数値の識別子と名簿の席)」は、`aggregate-evidence.mjs:445` が `user.id N / @login → 氏名` の形で出します。席への対応は login で引いており、id は写しの値を並べているだけです。名簿に id が無いので、id と人の対応はどこでも確かめていません。

監査人がこの表示を読むと、「数値の識別子で人を同定した」と読みます。**表示が、行っていない照合を示唆しています**。F-4 の経路で Q が出した判定は、Q の id と P の氏名が1行に並んで出ます。

### F-7 第4章 :84 の要求は、降りていないのに台帳に出ていない [確認]

内部調査 0.6 のとおりです。監査の立場から付け加えると、承認レビューを判定記録とする保全の条件の1つ目が満たされていないので、第4章の文言に従えば**テンプレートの採用者のすべての承認レビューは、承認者を同定できたものとして扱えない**状態です。それをテンプレートは同定できたものとして数え、標準の台帳はそれを表示していません。ADR-0028(未達と省略の区別)と #222 の扱いに反する状態が、いま続いています。これは R-4 の結論に依らず、本件で直す対象です。

### F-8 PR を経る記録のコミットの作成者は、メールアドレスで決まる [確認・推測]

`ghHosting`(`material-attribution.mjs:252`)は `commitAuthors` を `c.author.login` で取ります。GitHub はコミットの author のメールアドレスからアカウントを引くので、署名の無いコミットでは誰でも他人の noreply アドレスを author に書けます [推測: GitHub の仕様からの帰結。外部調査 4.1 の「署名は鍵を示すだけ」と同型]。`introducedBacking` の「記名者以外のコミットが混じっていない」(:186-189)は、author を偽ったコミットを見逃します。共有の構成に固有の穴ではありませんが、同じ照合の弱さとして記録します。

### F-9 権限設定の記述と実装の食い違い(付随) [確認]

`template/CLAUDE.md` の常駐の規則は「`gh pr merge` を実行しない `[機械]` 権限設定(`ask`)」と書きますが、`generate-profile.mjs:5549` の `standardBash` は `deny` です。強める向きの食い違いで実害はありませんが、#380 の crosscheck が IMPL-0417 で同型の食い違い(裁定は ask、実装は deny)を記録しており、規則の文が実装を正しく述べていない箇所が残っています。

## R-1 共有の構成への要求の向き

### 結論

- **禁止しない。黙らない。構成の入力として必ず問う**。問いの単位は担い手ごとで、「この担い手は、どのアカウントで動くか」(専用のアカウント・App の数値の識別子 / 席の責任者の認証情報 / それ以外の人の認証情報)とする。未回答は「共有」として扱う(安全側の既定)
- 問いの重みは**承認・記名を出す側**に置く(F-2)。作成だけを行う担い手の共有は、G-6 の勘定を崩さないことを本文に書く
- 推奨は分離(担い手ごとに専用のアカウントまたは App)。推奨の理由を「統制が機械で確かめられる構成はこれだけである」と書く。「良い慣行だから」とは書かない
- 1.10.2 の表(「実行主体の文脈の認証情報を、席ごとに分けられない構成」)へは**入れない**。1.10.2 の注記に、人と担い手の共有がこの行に当たらないこと、当たらないとした理由、その代わりに何が掛かるか(R-2 の開示)を書く。「書かれていない」と「課さないと決めた」を区別するためである
- 問いの回答は自己申告である。自己申告のまま置かず、**担い手の実行環境で機械が点検できる部分を点検する**(R-3・R-5 の env-check)

### 理由

- 禁止しない理由は、禁止が監査で確かめられないことにある。共有しているかどうかは、ホスティングの記録からは見えない(F-1)。確かめられない禁止は、採用者に「共有していない」と書かせる圧力にしかならず、記録の信頼性を下げる。外部調査でも、人の認証情報の共有を禁じる明文の規範は見つかっていない(NIST 800-53 の shared account は人どうしの共有。GitHub の規約は「1つのログインを複数の**人**で共有しない」で、自動化の責任を所有者に置く)。判断軸は信頼性であり、採用者の負担ではない
- 黙らない理由は、本標準の G-6・ADR-0106 の (A)(B)・作成を指示した者の既定値が、どれも「AI の操作は AI の名義で現れる」前提で書かれているからである。前提が崩れる構成を問わないままにすると、統制の表示が構成によって真にも偽にもなり、読み手は区別できない
- 1.10.2 へ入れない理由は、1.10.2 の行が守るもの(席どうしで承認と記名が同じ認証情報から出ないこと)と、共有が崩すもの(人の操作と担い手の操作の区別)が別だからである。入れると、ほぼすべての1〜2名の採用者が離脱を持ち、離脱の表が「AI を手元で使っている」ことの表示になり、本来の席の分離の離脱が埋もれる。ただし、これは判断であって実証ではないので、EV でマークする
- 推奨の向きは外部と一致する。OWASP ASI03(attribution gap)、CISA ほか(各エージェントを別個の主体として構成する)、NCCoE(agent と human を区別し、委任元に結びつける)、SLSA(trusted person と trusted robot の区別)。提供者の既定(Copilot cloud agent、Claude Code Action)も専用の名義である

### 監査で確かめられること

- 構成に担い手ごとの名義の回答があること(未回答は共有として表示されていること)
- 回答が「専用」の担い手について、その担い手の名義の数値の識別子が名簿の人のどの id とも一致しないこと(機械で確かめられる)
- 回答が「専用」なのに、AI の関与を示すトレーラ(Co-Authored-By の AI)を持つコミットの PR が、名簿の人のアカウントで作られている件数(食い違いの所見。自己申告の点検)
- 回答が「共有」の構成で、R-2 の開示が保証の開示の項目1 に出ていること

### 採らない案

- **共有を禁止する**: 確かめられない禁止は自己申告を偽らせる方向に働く。禁止の根拠になる明文の規範も無い
- **共有を 1.10.2 の列挙に無い離脱へ加える**: 上の理由。席の分離の離脱と別の欠けを1行に混ぜる
- **推奨と開示だけにして、構成では問わない**(#380 規格の委員の案): 開示の材料が無くなる。開示の項目を「導出は機械的な集約に限る」(`gate-criteria.md:1240`)で作るには、構成に回答が要る
- **既定を「分離」にして、回答が無ければ分離とみなす**: 既定の利用(ローカルの Claude Code)の実態と逆向きで、危険側の既定である

### 反論されうる点

- 「問うだけでは、共有している採用者の G-6 が実質的に弱いことは変わらない」。変わらない。変わるのは、弱いことが記録に出ることである。強くする手段(分離)は推奨として示し、分離した構成だけが受けられる表示(R-2)で差を付ける
- 「1.10.2 に入れないなら、共有の構成でも2名の体制が逸脱を伴う適合の主張に至れる。それは主張として過大ではないか」。この反論には一理がある。委員は、主張の条件へ入れるかを本件の判断として持たず、R-2 の開示が主張の文に必ず現れることを条件とする。過大かどうかは、開示を読んだ者が判断できる状態を作る。会議体が主張の条件へ入れる判断をするなら、委員は反対しない(厳しくする向き)。その場合も、席の分離の行とは別の行にすることを求める

## R-2 共有の構成で崩れる統制の扱い

### 結論

崩れる統制ごとに、次の表のとおり扱う。共通の原則は2つ。

- **数えないことで信頼性を上げようとしない**。共有かどうかは自己申告なので、数えない規定は「分離」と申告した構成で素通りする。数えない規定が働くのは、申告を正直にした採用者だけになる
- **成立と表示しない**。共有の下の承認・帰属は「アカウントの操作として成立、人の操作としては自己申告」と表示し、件数を出す。見かけ上の成立(F-3)を、手順の文から消す

| 統制 | 共有の下で何が崩れるか | 扱い | 開示の所在 |
| --- | --- | --- | --- |
| G-6 の独立した人の確認(4条件) | 承認したアカウントの人が操作した事実(F-1) | 数える。承認者の側の担い手が共有の構成である承認を「名義の共有の下の承認」として件数で出す。条件4 の挙動要約を、人の操作の証拠として扱わないことを本文に書く | 項目1(G-6 の成立状況の内訳) |
| 作成を指示した者の照合 | 欄を書くのは PR の作成者のアカウント(= 共有の下では担い手)。承認の後に欄を書き換えても承認は失効しない | 欄を自己申告と明記。**承認の後に欄が変わった PR は、その承認を数えない**(共有に依らない規則として足す。`userContentEdits` で機械が確かめられる)。PR の時点でも、名簿に対応づかない指示者があれば数えない(F-5 を直す) | 項目1(既定値でみなした件数と並べる) |
| 効力を持つ記録 (A) 宣言行のレビュー | 記名者のアカウントの操作が記名者本人の操作である事実 | 記名者の側が共有の構成なら、**1名の体制と同じく自己申告として記録ごとに開示する**。数える(効力は持つ)。ただし停止の解除は、記名者以外の人が記名者本人へ確かめた旨(日時・手段)を自分の名義で残した場合に限り「確認つき」と表示する | 項目1、記録ごとの注記 |
| 効力を持つ記録 (B) 記録を入れた変更 | 作成者・承認者のアカウントの操作者 | (A) と同じ。後退経路の手順4 の「帰属の確認」は、共有の下では帰属の確認と呼ばない。確認者が見たのはアカウントだけであることを本文に書く | 同上 |
| PR の作成者の別(ブランチ保護の自己承認の禁止) | 崩れない(F-2)。作成者の側の共有は止める側に倒れる | 本文(`gate-criteria.md:933`)に、作成者が人の名義の AI である場合も書き足す | 不要 |
| AI・bot の名義の承認を数えない | 名義で見分けられない | 規則は残す。共有の下では効かないことを規則の隣に書く(EV-0220 の記述を G-6 の節へも置く) | 項目1 |
| 記名(G-7・D-0・層1) | 記名の欄を誰が書いたか | (A)(B) と同じ帰属の表示。IMPL-0415(#428)を降ろすときに同じ区別を入れる | 項目1・7 |

保証の開示は、項目を増やさず**項目1 の内訳**に置く。項目1 は「体制と独立性の成立状況」であり、名義の共有は独立性の成立の条件だからである。担い手の名義の変更は項目7(期間中の体制の変化点)に出す。

### 理由

- G-6 を数えない案は、F-1 の経路を本当に塞ぐなら有効だが、塞げるのは申告した採用者だけである。申告を偽った採用者と正直な採用者で表示が逆転し、記録の信頼性が下がる
- 「人の確認で補う」を一般化しない理由: 補う確認も同じ共有の下で行われるなら、同じ欠けを持つ。停止の解除に限って確認つきの表示を置くのは、効力が最も大きく(判定される側の PR を通す)、件数が少なく、確認の聞き取りが監査で追えるからである
- 承認の後の欄の書き換え: 現行の G-5 は `edited` で再実行する(`gate-g5.yml:13`)ので、書き換えた後の本文で判定し直す。写し(`record-copy.yml`)はマージ時点の本文しか持たず、書き換えの履歴は残らない。「承認者が承認した時点の指示者」を事後に確かめる手段が無い

### 監査で確かめられること

- 項目1 の内訳に、名義の共有の下の G-6 承認・効力を持つ記録の件数が出ていること。0 件と未回答を区別していること
- 内部監査の観点28 を効力を持つ記録から G-6 の承認へ広げること。抜き取った承認について、承認者に操作の有無を聞き取る(手段・日時を記録)。観点6(1人が複数のアカウント)の隣に「1つのアカウントを人と担い手が使っていないか」を置く
- 承認の後に「作成を指示した者」の欄が変わった PR の件数(機械)

### 採らない案

- **共有の下の G-6 承認を数えない**: 上の理由。数えない規定が申告の正直さを罰する
- **共有の下の効力を持つ記録を受け付けない**: 1〜2名の体制で例外承認と停止の解除の手段がなくなり、承認を経ない回避(記録の外での運用)を招く。記録の外の運用は監査で見えない
- **Co-Authored-By・署名で人と担い手を区別する**: 外部調査 4.1・4.2 のとおり自由記述と鍵の証拠で、操作者を示さない
- **挙動要約の形の検査を強めて人の操作の証拠にする**: 担い手は形を満たす。中身は機械で確かめないと第4章が既に書いている
- **監査ログの `programmatic_access_type` を必須にする**: Enterprise Cloud に限られる。使える採用者の手段の例として附属書に置くことは妨げない

### 反論されうる点

- 「数えて開示するのは、AI の承認を人の承認として通すことの追認ではないか」。追認ではない。追認と区別するために、件数と所在を出す。追認を避ける本当の手段は分離であり、それを推奨し、分離した構成だけが「名義の共有の下の承認 0 件」を表示できる
- 「停止の解除だけ確認つきの表示を置く線引きは恣意的だ」。線引きは効力の大きさで引いた。例外承認にも広げる案は成り立つ。委員は反対しない

## R-3 担い手の識別にアカウントを含めるか

### 結論

- 担い手が動く名義を**記録する欄を足す**。構成の `performer` に `account`(専用の名義なら数値の識別子とログイン名、共有なら「席の責任者の認証情報」または名簿の人の id)を置き、D-0 表7 に列を足す
- ただし、3.4.2 の**識別の組(適合性確認の失効を引き起こす鍵)には入れない**。`performerKey`(`config.mjs:282-284`)は `[model, instructions, permissions]` のまま
- 名義の変更は変化点4 に**名指しで**加える(「担い手の名義の変更(専用 ⇄ 人の認証情報、名義の交代)」)。変化点の記録は日時を持ち、その前後で R-2 の表示を切り替える
- `/process-init` の8問に問いを足す、または `/process-change` の種別 `performer` で必ず問う。どちらでも、未回答を共有として扱う
- `performer.md:39`(担い手ごとに別のトークン)と `recording.md:121-130`(共有を想定内)の食い違いは、回答に応じて分岐する手順へ直す

### 理由

- 欄を足す理由: R-1・R-2 の表示と開示を「既存の記録からの投影」(`gate-criteria.md:1240`)で作るには、名義が記録に無ければならない。また、名義が変わった時点が分からないと、過去の承認がどちらの構成の下のものかを事後に区別できない
- 識別の組に入れない理由: 3.4.2 の失効は、適合性確認の根拠(その担い手が力量を示した証拠)がもう当てはまらないことを表す。名義は担い手の出力を変えない。名義の変更で失効させると、失効が「出力が変わったかもしれない」という意味を失う。名義の変更が権限を変える場合は、既に識別の組にある「権限の組」が失効を引き起こす。これは変更量の議論ではなく、失効という語の意味を保つための判断である
- 未回答を共有とする理由: 危険側の既定にしない(R-1)

### 監査で確かめられること

- 構成の `performer[].account` と D-0 表7 の列が揃っていること(契約検査で機械)
- 専用と回答した名義が名簿の人の id と一致しないこと(契約検査で機械。名簿に id が要るので R-4 に依る)
- 担い手の実行環境で `gh api user --jq .id` を引いた結果が、回答した名義と一致すること(env-check、点検の時点の事実として記録。継続を保証しない)
- 変化点の記録の日時と、R-2 の表示の切り替えの日時が一致すること

### 採らない案

- **3.4.2 の識別の組に名義を入れる**: 上の理由
- **名義を D-0 表5-2(人の名簿)へ書く**: 表5-2 は人の名簿で、AI を載せないと定めている(`deliverable-templates.md:434`)。名簿に AI の名義が混じると、`rosterProblems` の AI の名義の拒否と衝突する
- **名義を書かせず、env-check の観測だけで済ませる**: 観測は点検の時点の事実で、期間を通した構成の宣言にならない。宣言と観測の両方を持ち、食い違いを所見にする

### 反論されうる点

- 「env-check の `gh api user` は、担い手が別の認証を使っていれば(`GH_TOKEN` を切り替えるなど)意味が無い」。そのとおりで、点検は継続の保証ではない。点検を、回答が偽であることを見つける手段として置き、真であることの証明としては置かない
- 「1名の体制では、名義を分けても承認する人がいない」。1名の体制では G-6 は外部の確認者に依る。外部の確認者の側の共有も同じ問いの対象になるが、採用者の構成からは問えない。外部の確認者の名義は自己申告として開示する

## R-4 名簿の数値の識別子による照合

### 結論

- 第4章 :84 の**数値の識別子の要求は維持する**。理由を本文に書き足す(ログイン名は改名で直ちに、削除で 90 日後に他人が取れる。F-4 の経路)
- 「リポジトリの外側で保守する」は、**性質の要求に書き改める**: 「判定される側が、記名者以外の人の記名を経ずに変更できない置き場で、変更の履歴が残る」。準拠テンプレートの `process.config.json`(ブランチ保護と PR を経る、`accountsConfirmed` で本人以外の記名を要する)はこれを満たしうる。採用済みの条項の改めなので、新しい ADR で行う
- **本件で直ちに**、:84 に実装マーク(undelivered)を付け、台帳に出す(F-7)。M1 の実装が入った時点で delivered に改める
- 準拠テンプレートの移行は **M1 + M4(条件つき)+ M6 + 書き込みの権限の照合** とする
  - M1: `accounts` の要素に `{login, id}` を受ける。照合は名簿側に id があれば id で、無ければ login で行う
  - M4: id の解決は、`gh api users/<login>` を任意の時点で引く形にしない。**その人が自分で行った操作の記録**(写しのレビュー・PR の作成者の `user.id`)から引く案を `/process-change` が示し、人が記名して入れる。記録が無い人だけ `users/<login>` で引き、解決した日時と確かめた者を残す
  - M6: 写し・PR の検査で、ホスティングの (login, id) と名簿の (login, id) が食い違えば所見にする(改名・他人の取得の疑い)。名簿に id があり login だけが違う場合は改名、login が同じで id が違う場合は**別人**として、承認を数えない
  - 書き込みの権限: レビューの `author_association` が OWNER・MEMBER・COLLABORATOR でない承認を、G-6 にも (A) にも数えない(F-4 の 4 を塞ぐ。id の移行と独立に効く)
- **ログイン名でしか照合できなかった承認は、条項のとおり「同定できたものとして扱わない」**。移行の期間を設けて数える形(M5)は採らない。代わりに、名簿に id が無い間は G-6 を「未達(名簿に数値の識別子が無い)」と理由つきで表示し、解決のコマンドを示す。過去の承認は、写しに id があるので、名簿へ id を足した時点で**遡って同定できる**(id は不変なので、今の名簿の id で過去の写しを照合してよい)
- PR 本文の `@アカウント`(作成を指示した者・委任の実施者・区分の確定者)は、ログイン名で受けてよい。ただし、**PR の時点の検査が解決した id を出力し、写しへ含める**(本文を書いた時点に近い時刻で束縛する)。解決できない `@アカウント` は、PR の時点でも数えない側に倒す(F-5)。自己申告である旨は R-2 の表のとおり

### 理由

- 数値の識別子は、外部の規格(NIST IA-4 d.)と GitHub の仕様(REST `GET /user/{id}` の「durable user ID」)が同じ向きを示している。ルールセットの bypass も数値の `actor_id` で照合する。照合の鍵を改名で変わる値に置く理由が無い
- M5 を採らない理由: 条項が「同定できたものとして扱わない」と書くものを、移行の期間だけ数えると、表示が条項と逆のことを示す。ADR-0028 の未達と省略の区別は、未達を未達と表示するための決定である。移行の負担は、M4 の解決の手順と、写しから遡って同定できること(過去の承認を失わない)で下げられる。負担の大小は採否の理由にしないが、未達の表示が採用者に回復の手段を示すことは、表示の正しさの一部である
- 「外側」を性質に書き改める理由: 外側に置いても、置き場の書き換えを誰が確かめるかは決まらない。CI と `/pit` が読めない置き場は、照合を機械から人へ戻し、照合が行われたかを監査で確かめられなくする。条項が守ろうとしたもの(判定される側が対応表を書き換えて自分の承認を作れないこと)を、性質として書くほうが確かめられる。ただし、担い手は Bash から `process.config.json` を書ける(書き込みの遮断のフックは Edit・Write の道具にしか掛からない。`settings.json:76`)。性質の要求を満たすのは、ブランチ保護と PR の検査であり、手元の権限設定ではないことを本文に書く
- 書き込みの権限の照合を足す理由: id の移行が済んでも、名簿の id を持つ本人が書き込みの権限を失った後(退職など)に出した承認を、ホスティングは必須の承認に数えないのに、集約は数える。ホスティングが数えない承認を本標準が独立した人の確認に数える理由は無い

### 監査で確かめられること

- 名簿のすべての人のアカウントに id があること(契約検査)。無い人の承認が「同定できない」として件数に出ていること
- 写しの `user.id` と名簿の id の一致(集約で機械。M6 の所見の件数)
- IMPL-0125 の表示が、id で照合した結果を示していること(F-6 を直した後)。照合できなかった行に「login でのみ対応」と出ていること
- id の解決の記録(解決した日時・解決の出所・確かめた者)

### 採らない案

- **M2 並行の欄(`accountIds`)**: login と id の対が別の場所にあり、改名のときに片方だけ直る。照合の鍵が2つになり、どちらで照合したかが表示から分からない
- **M3 名簿を外へ出すことを既定にする**: 上の理由。採用者が組織の台帳を持つ場合に、そこから写す手段を示すことは妨げない
- **M4 を `users/<login>` の一括解決で行う**: 改名・再取得の済んだ login を解決すると、別人の id を不変の値として固定する。誤同定を恒久化する
- **M5 移行の期間を設けて login の照合を数える**: 上の理由
- **node_id で照合する**: 新旧の形式が混在する(外部調査 3.2 の観測)。データベースの id を使う

### 反論されうる点

- 「名簿に id が無い間 G-6 を未達にすると、既存の採用者の全員が一斉に未達になる」。なる。それが条項の今の文言どおりの状態であり、テンプレートが数えていたことのほうが誤りである。厳しくする向きの変更の即時適用(ADR-0055 の型)とも整合する。会議体が猶予を置くなら、猶予の間の承認を「同定できない承認」として件数に出し、成立の表示に混ぜないことを最低条件とする
- 「`author_association` は組織の外の協力者・外部の確認者の扱いを変える」。外部の確認者が書き込みの権限を持たない構成では、承認がホスティングの必須の承認に数えられず、ブランチ保護と集約の勘定が割れる。外部の確認者には COLLABORATOR の権限を与えるか、判定記録の様式で記録する(第4章の既存の経路)ことを手順に書く [要実機: 外部の確認者を COLLABORATOR にしたときの `author_association` の値]

## R-5 テンプレートの手段と記録

### 結論

- **権限設定を強制層と呼ばない**。`gh pr review` の deny、`gh api` の扱いを含め、権限設定は担い手の誤操作を止める層であり、共有の下で人の名義の操作を止める境界ではない(F-1)。IMPL-0417 の note をそのように改め、R-2 の開示が権限設定の有無に依らず出ることを確かめる
- それでも止める範囲は広げる(誤操作の防止として意味がある)
  - `Bash(gh api:*)` を `ask` にする(読み取りも含む)。`gh api` は引数を足すと POST になるため、書き込みだけを文字列で見分ける規則は作らない
  - `Bash(gh auth token:*)` を deny する
  - `Bash(gh pr comment:*)` を、効力を持つ記録の後退経路(F-3)のために `ask` にする
  - Bash の PreToolUse フックを足し、`pulls/*/reviews`・`addPullRequestReview`・`submitPullRequestReview`・`/merge` を含むコマンドを拒否する。回避できる(F-1 の子プロセスの経路)ことを、フックの「限界」の注記(`guard-write.mjs:16-17` と同じ形)に書く
- 常駐の規則を広げる: 「**G-6 の承認・変更要求・レビューの取り下げを、どの経路でも出さない**」「承認の後に『作成を指示した者』の欄を変えない」。宣言行のレビューに限らない
- 境界として効く手段は**認証情報の分離だけ**である。テンプレートは、担い手を専用の名義で動かす手順(担い手の実行環境に人の `gh` の認証を置かない、`GH_TOKEN` に専用のアカウントまたは App のトークンを渡す)を手引きとして持つ。既定にはしないが、R-1 の推奨の実装として示す
- 検査の追加: F-4(`author_association`)、F-5(PR の時点の指示者の未解決を数えない側へ)、F-6(id での照合と表示)、承認の後の指示者の欄の変更、M6 の食い違いの所見、env-check の `gh api user`
- 記録

### 理由

- 権限設定を境界と呼ばない理由: 共有の構成では、担い手は人と同じ権限をホスティングに対して持つ。手元の規則は、担い手が意図して(またはプロンプトインジェクションで)回避すれば効かない。境界と呼べば、R-2 の開示を「権限設定で塞いだから要らない」と読む余地を作る。#380 の裁定が `gh api` 直を止めないと明記したのは正しく、その記述を「止めているのは誤操作だけ」へ一般化する
- それでも広げる理由: 誤操作の防止は、担い手の意図しない承認(指示の取り違え)を減らす。減った件数を測れないので EV で効果を主張しない
- 分離を既定にしない理由: R-1 の理由と同じ。ただし、テンプレートが手順を持たなければ推奨は空文になる

### 監査で確かめられること

- 生成された `.claude/settings.json` に、上の deny・ask が guard の有効・無効の両方の分岐で入っていること(契約検査)
- Bash のフックが拒否した記録(`.claude/denied.log`)の件数。拒否が0件であることを安全の根拠にしない(フックの限界の注記)
- 常駐の規則の文と、権限設定の実装の一致(F-9 の型の食い違いが無いこと)
- 分離の手順を採った採用者で、担い手の PR の作成者が専用の名義になっていること(R-1 の監査項目)

### 採らない案

- **`gh api` の書き込みだけを文字列で deny する**: `-f`/`-F` で POST になる、GraphQL の mutation は本文の中にある、子プロセスから呼べる。見分けられたように見えて見分けていない規則になる
- **`Bash(gh api:*)` を deny する**: 担い手の読み取り(PR の状態の確認)を全部止め、担い手が `curl` やスクリプトへ回る動機を作る。`ask` にして人が都度見る
- **権限設定で塞いだことを理由に、共有の構成の開示を外す**: 上の理由
- **担い手の実行環境から人の認証情報を取り除くことを既定にする**: 1〜2名の採用者の既定の利用と逆向きで、既定にすると未回答・偽の回答が増える。手順として示し、採った構成を表示で区別する

### 反論されうる点

- 「`gh api` を `ask` にすると、担い手の作業の流れが頻繁に止まり、利用者が『常に許可』を選んで規則が消える」。起こりうる。そのため `ask` の効果を主張しない。規則が消えたかは権限設定の要約値の差分(既存の記録)で見える
- 「Bash のフックは回避できるのに置くのは見せかけではないか」。見せかけにしないために、限界を注記し、開示を権限設定に依らせない。フックは誤操作の防止としてだけ数える

## 論点ごとの結論(1行)

- R-1: 禁止も沈黙もせず、担い手ごとの名義を構成の入力として必ず問う(未回答は共有)。推奨は分離。1.10.2 には入れず、入れない理由を注記に書く
- R-2: 共有の下の G-6 承認と効力を持つ記録は数えるが「人の操作は自己申告」として件数を保証の開示の項目1 に出す。後退経路の「帰属の確認」「代筆を後から確かめられる」は共有の下で成り立たないと書き改める
- R-3: 名義の欄を構成の `performer` と D-0 表7 に足し、変化点4 に名指しする。3.4.2 の識別の組(失効の鍵)には入れない
- R-4: 数値の識別子の要求を維持し、login だけの照合は条項どおり同定扱いしない(移行の期間で数えない)。M1+M4(本人の操作の記録から解決)+M6、加えて `author_association` の照合。「外側」は性質の要求へ改める。:84 に実装マークを直ちに付ける
- R-5: 権限設定は境界でなく誤操作の防止と位置づけ直し、`gh api` の ask・`gh auth token` の deny・Bash フック・常駐の規則の拡大を足す。境界として効くのは認証情報の分離だけ。新しい ADR・EV 4件・IMPL を立てる
