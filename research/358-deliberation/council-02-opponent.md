## 0. 全論点に掛かる3つの前提

### 0.1 CLAUDE.md の行数は、標準自身の参考の値の手前にある

- E1 のとおり 197 行。3.11.4 要求事項1 の参考の値は 200 行(EV-0088)。本標準は「分量が増えるほど遵守率が下がる」を要求事項1 の根拠に挙げている
- 論点 A・B・C の規則を CLAUDE.md へ1行ずつ足すと、少なくとも 8〜10 行増え、テンプレート自身が標準の参考の値を超える。上限の値は採用者が定める(ADR-0084)ので違反ではない。ただし、**標準が根拠として挙げた機序(遵守率の低下)を、標準の準拠テンプレートが自ら招く**ことになる
- 結論: 行を足すなら、同じ変更で既存の行を補助ファイルへ移すか統合し、200 行以内に保つことを条件にする。行数の増加を「delivered の件数が増えた」と引き換えにしない

### 0.2 3.11.3 の文言と「指示文だけの禁止」が食い違っている

- 3.11.3 は「遵守が必須の規則を誘導層に書いてはなりません」と書く。文字どおりに読むと、誘導層へ書くこと自体を禁じている
- IMPL-0221 の注記は「誘導層(指示ファイル)だけに書かず」と読み替えている。テンプレートの CLAUDE.md は、既に 5.8.5 の禁止事項2・4・5 を「指示文」だけで置いている
- 論点 A の5件(要約の禁止・再現の説明の禁止・費用を理由に急がせることの禁止・申告の完了率の禁止・中間へのマージの禁止)は、いずれも「してはならない」の規定で、機械の手段が無い。これらを CLAUDE.md へ置いて delivered にすると、3.11.3 の文言の上では「必須の規則を誘導層に書いた」ことになる
- 結論: **3.11.3 の文言を、注記の読み(誘導層だけに置いて担保されたものとして扱ってはならない。機械の手段の無い必須の規則は、指示文と人の確認の所在を併記する)へ改めるべき**である。食い違いの解消なので軽で扱える。これを直さずに A を降ろすと、降ろした行が標準の別の条項に反して見える

### 0.3 「確認(ask)」は人の確認ではなくなっている

- `survey-303.md` §2.2(2026-10 時点の提供者の文書)は、Claude Code v2.1.283 以降で `auto` が対話のセッションの開始の既定モードであり、確認を分類器が行うと記録している
- survey.md の D の記述「Edit・Write の既定は確認」と、既に delivered の IMPL-0199(秘匿情報の読み取りと強制層の編集を ask に置く)は、`auto` のもとでは人が確かめることを意味しない
- 結論: D の判断では「ask = 人の確認」を前提にしない。IMPL-0199 の注記の読み方の問題は本件の範囲の外なので、既存の Issue へ申し送る(新規の起票はしない)

## A 指示文で運べる行動の規則(IMPL-0206・0208・0257・0282・0491)

降ろすと信頼性が下がる場合:

- **IMPL-0206(操作の要約の禁止)は、範囲を定めずに置くと既存の記述と衝突する**。PR の様式は「## 変更の概要」を持ち、AI が書いている。CLAUDE.md 11 行目は「セッションの開始時にも要約が入る」と書く(機械の出力)。「エージェントの操作の要約を AI に生成させない」とだけ書くと、AI は (i) 変更の概要を書かなくなるか、(ii) 書いてよいと自己判断する。どちらに転ぶかは決まらない。これは 3.11.5 の「既存の記述と矛盾しないか」が機械で確かめられないことの実例になる
- **IMPL-0491 を delivered にすることは ADR-0124 決定4 に反する**。決定4 は「`git merge` と `git push` の組は降りていない」と明記し、AI の担い手の拒否はフックの経路に限って降りた扱いにした。CLAUDE.md に行を足しても、このマークの主題(AI の担い手の拒否、`target=guard-bash-hook`)は降りない
- IMPL-0491 の現在の `plan=scheduled` も、ADR-0124 が維持した ADR-0084 決定4(降ろす手段の無い規定を `scheduled` と表示し続けない)と食い違っている

降ろさないと信頼性が下がる場合:

- 0208・0257・0282 は、AI の担い手が書く場所(保証の開示・PR の本文・承認の催促)で起きる挙動である。指示文以外の手段が無く、指示文すら無ければ、担い手は規則を知る経路を持たない。指示文は弱いが、無いよりは強い

結論:

- 0208・0257・0282: **採る(a1)**。条件は、(1) 0.2 の 3.11.3 の文言を同じ変更で直す、(2) マークは `state=delivered check=presence`(単位: 行)とし、`[機械]` の印を付けない、(3) 0.1 の行数を保つ。0208 は既存の行「モデルの系統・提供元の違いを、確認の強さの根拠として書かない」と同じ節へ統合し、行を増やさない
- 0206: **条件つきで採る**。行の中に範囲を書く(対象は人が操作を確かめる材料として示す要約。PR の「変更の概要」は意図の説明であり差分の読みを代替しない、と区別する)。区別を書けないなら降ろさない。5.8.6 要求事項8 の「操作の要約」の範囲が条項で定まっていないなら、それは定義の欠けであり、軽で条項に足す
- 0491: **delivered にしない**。CLAUDE.md の行は別のマーク(`target=claude-md check=presence`)として足してよい。0491 本体は `undelivered` のまま残し、`plan` は ADR-0124 決定4 の帰結に合わせる(`scheduled` でも `adopter` でもない。ADR-0084 決定4 に従い、表示の形を議長が裁定する)
- a2(詳細を補助ファイルへ置き、CLAUDE.md は所在だけ)は、禁止の規則には**採らない**。再利用層は呼び出したときだけ作用する(3.11.3)。常時効くべき禁止を呼び出し時だけの層へ置くことは、表示より担保が弱い。ただし、0.1 の行数を保つために、既存の手順的な行を補助ファイルへ移すことは採る

## B 指示資産の保守(IMPL-0221・0223・0224・0227)

降ろすと信頼性が下がる場合:

- **3.11.5 の「機械検査」の3点のうち、「既存の記述と矛盾しないか」は決定的に判定できない**。自然言語の規則どうしの矛盾の判定を CI に置くなら、LLM による判定しかない。非決定的な結果を合否に使う案は ADR-0084 の R-5 で既に退けている(偽陽性で落ちる検査になる)。合否に使わない LLM の判定を「機械検査」と称すると、AI の出力を検証の根拠にすることになり、ADR-0012(AI の出力は未検証の入力)と食い違う
- 「コードベースから導出できる内容でないか」は、形(木の図の記号、パッケージ名と版の列)の検出までしかできない。検出 0 件は「導出できない」を示さない。合否に使うと、検出されない形で書けば通る検査になる
- 「総分量が上限内か」は数えられるが、上限の値を ADR-0084 が採用者へ委ねた。テンプレートが既定の値を置くと ADR-0084 の決定(IMPL-0222 は `plan=adopter`)に反する
- **CODEOWNERS による AI維持管理者のレビューの必須は、team のルールセット(`require_code_owner_review: false`)では効かない**。雛形の行はコメントのまま(ADR-0087)。行を有効にしただけで delivered とすると、team の体制では担保が無いのに担保があるように見える
- `CONTROL_FILES` へ `CLAUDE.md`・`.claude/skills/` を足す案は採らない。`CONTROL_FILES` は陰性の確認(3b)を要し、誘導層の変更に「止まった/止まらなかった」を書かせることになる。survey が書くとおり、誘導層に陰性の確認を求める条項は無く、これは新しい義務になる(重)

降ろさないと信頼性が下がる場合:

- 個人の作業環境の指示(`CLAUDE.local.md`・手で作った `.claude/settings.local.json`)は、`.gitignore` に無いため共有資産へ入りうる(P5)。置ける担保を置いていない
- 指示資産の変更が誰の承認も経ずに入る経路が、team の体制で開いている

結論:

- 0221・0223・0224: **採る(b1)**。`check=presence`。0221 の行は 0.2 の文言の改めと一体で書く。0224 は「書かない」の行に加え、木の図の記号と依存の列の形の**検出の一覧**を PR へ出してよい。その場合は合否に使わず、検出の限界の文を毎回出す(`check-pr.mjs` 4b の型)
- 0227 は**4つに分ける**(マークは規定ごとに付ける。implementation-marking の規約)
  - (1) 個人のファイルの除外: `.gitignore` へ2つを足す。加えて、PR の変更に2つのパスが現れたら G-5 を失敗させる検査を足し、`check=machine` とする(`git add -f` を `.gitignore` は止めない)。**採る**
  - (2) AI維持管理者のレビュー: `CONTROL_FILES` とは別の一覧(指示資産の一覧)を設け、統制の設定の承認(3c)と同じ照合で、席の責任者本人の承認を要する。陰性の確認は課さない。`--require-control-approval` が無い体制で効かないなら、その旨をマークの注記に書き、効く体制だけを `machine` にする。**条件つきで採る**
  - (3) 総分量: 採用者が値を構成に書いたときだけ判定し、値が無ければ「未設定」と出す(通過と出さない)。**採る**(ADR-0084 と矛盾しない。値を置かないため)
  - (4) 矛盾: 降ろさない。`check=manual`、確かめる者は AI維持管理者(四半期の棚卸しと変更のレビュー)
- b3 について: **3.11.5 の3点目以外の書き方も含め、「機械検査する。3点とする」を改めるべき**と考える。改める向きは、削除ではなく分離である。「総分量と、導出できる内容の形の検出は機械で行う。既存の記述との矛盾は、AI維持管理者がレビューと棚卸しで確かめ、機械の検出(重複・同じ核の文言の否定)はその材料とする」。理由は、判定できないものを「機械検査」と書いた条項は、採用者に LLM の判定を検査と称して置かせる誘因になるためである。これは条項の改廃であり、**重へ上げる論点**として扱うことを求める

## C 外部ツールの統治(IMPL-0228・0229)

降ろすと信頼性が下がる場合:

- **`.mcp.json` は「採用するツールの一覧」の全部ではない**。利用者の範囲(user・local)のサーバーは `~/.claude.json` にあり、案件の設定で止められない(P4)。空の `.mcp.json` を置いて IMPL-0228 を delivered にすると、版管理の一覧の外のツールが動いていても一覧は空のまま正しく見える
- 権限の規則 `mcp__<server>__<tool>` で、一覧に無いサーバーの道具を案件の側で拒否できるかは確かめていない(全サーバーの包括の拒否を書けるかが未確認)。確かめずに「権限を限った」と書かない

降ろさないと信頼性が下がる場合:

- 現状では `.mcp.json` を足す PR が AI維持管理者の承認を経ずに入る(survey §1 C)。3.11.6 要求事項5 の穴が実際に開いている。これは降ろせる

結論:

- **c1 を条件つきで採る**。`.mcp.json` を `CONTROL_FILES` と CODEOWNERS の雛形へ足す(外部ツールの付与は権限の付与であり、強制層に当たる。陰性の確認は意味を持つ)。この部分は IMPL-0229 の要求事項5 として `check=machine` にできる
- 空の `.mcp.json` は置いてよいが、IMPL-0228 の注記に「利用者の範囲のサーバーを止めない。一覧は案件の範囲の一覧に限る」と書く。包括の拒否を提供者の文書と実機で確かめられたら、その規則を足して範囲を広げる。確かめられなければ、利用者の範囲の統制は組織の管理の設定(`allowedMcpServers`)によるとして `plan=adopter` の別のマークに分ける
- 要求事項2・4(提供元の確認、説明文を信頼できない入力として扱う)は判断であり、`check=manual`。記録の置き場(PR の本文の節)を決めて presence にするのはよい
- c2(文書だけ)は採らない。承認の穴は機械で塞げる

## D 実行環境の拒否の既定(IMPL-0200)

降ろすと信頼性が下がる場合:

- **d2(sandbox)を delivered にすることは、強く反対する**。ネイティブの Windows では隔離せずに実行する(P1)。所有者の環境も Windows である。さらに、隔離はシェルだけに掛かり、Edit・Write・MCP・フックは隔離の外にある。設定を置いて delivered と表示すれば、Windows の採用者には何も効いていないのに「既定の拒否が降りた」と読まれる。設定を置くこと自体は、効く環境と効かない環境を注記に書けば、例として許容する
- d1(権限設定で既定の拒否)は、survey の範囲では成り立たない(Edit は確認になる。P2)。ただし、survey は許可モード `dontAsk`(`survey-303.md` §2.2 に名がある)を確かめていない。`dontAsk` が許可リストに無い操作を拒否するモードなら、書き込み・ネットワーク(`WebFetch`・`curl` を含む Bash)の既定の拒否に近づく手段になる。**確かめないまま d1 を退けるのも、確かめないまま採るのも、どちらも採らない**
- 仮に `dontAsk` で既定の拒否ができても、許可するパスは静的な一覧になる。「タスクの対象のパスに限る」には届かない。この部分を delivered にしてはならない

条項の欠陥:

- **5.8.6 要求事項3 の「書き込みの許可は実装計画のタスクの対象のパスに限る」は、定義が欠けている**。(i) タスクの外の書き込み(仕様・計画・判定記録の起案、`Spec: setup`)の範囲を定めていない。(ii) 書き込みの時点で「どのタスクの作業か」を誰が実行環境へ伝えるかを定めていない。エージェント自身がタスクを宣言して許可のパスが決まるなら、それは許可範囲をエージェントの操作で変えることになり、要求事項6 に反する。(iii) 要求事項10(計画のパスと実際のパスの差を機械で出す)は事後の検出であり、要求事項3 が実行時に満たせない場合の位置づけが書かれていない
- 結論として、**要求事項3 を改めるべき**である。改める向きの候補は「許可の範囲は、人が確定した実装計画の対象のパスの和と、成果物の置き場の固定の一覧に限る。タスクの単位での限定は要求事項10 の差の検出で補う」。書き込みの範囲は安全に掛かる事項なので、**重へ上げる論点**とする

降ろさないと信頼性が下がる場合:

- 現状でも置ける担保はある。秘匿情報の経路の読み取りを ask から deny へ上げること(auto のもとで ask は人の確認でない。0.3)は、要求事項4 を満たさないが、要求事項1 の「接触」の一部を実行時に拒否する。これは置ける

結論:

- IMPL-0200 を3つ(要求事項3 の書き込み、要求事項3 のネットワーク、要求事項4)に分ける
- 書き込み: `undelivered`。要求事項3 の改めの裁定を待つ。`dontAsk` の確認の結果に関わらず、タスクの単位の限定は降りていないと表示する
- ネットワーク: `dontAsk` と `WebFetch(domain:…)` を提供者の文書と実機で確かめてから決める。確かめるまで `undelivered`
- 要求事項4: `plan=adopter`(参照できない位置への配置はリポジトリの外の構成である)。ADR に理由を書く。読み取りの deny への引き上げは、要求事項1 の一部として別のマークで delivered にしてよい
- d3 は「降ろさない」ではなく、上の分割の帰結として部分に適用する

## E 生成の条件の自動の記録(IMPL-0207)

降ろすと信頼性が下がる場合:

- **e2(指示資産の版を履歴から導出する)は近似の値である**。セッションは開始時に CLAUDE.md を読む。同じセッションの中で CLAUDE.md を改めたコミットの後のコミットは、開始時の版で生成されうる。作業ツリーの未コミットの変更も履歴に残らない。親のコミットの版を「生成時の指示資産の版」として出すと、近似を記録として出すことになる。5.8.2 は「観測できる事実」を求めている
- **実行の識別子(`session_id`)は、引き当てる先が残っていなければ鍵として働かない**。引き当てる先は開発者の手元の実行の記録で、保持も監査の側からの参照も定めていない。鍵だけを記録して「記録した」と表示すると、5.8.2 の目的(影響範囲の絞り込み)を果たさないのに果たしたように見える
- e1 のうち、`git commit` を検出して `updatedInput` でコマンドを書き換える形は採らない。ヒアドキュメント・`-F`・`--amend` の書き換えで、担い手のコミットを壊しうる。強制層のフックが担い手のコマンドの意味を変えることになる
- 環境変数 `CLAUDE_CODE_SESSION_ID` は文書の約束ではない(P3)。頼らない

降ろさないと信頼性が下がる場合:

- 指示資産の版を記録しないと、ある版の指示の問題が判明したときに影響範囲を判定できない(5.8.2 本文)。出荷の集約の「最終変更のコミット」(IMPL-0178)は成果物ごとの対応を持たない

結論:

- **e1 を条件つきで採る。条件を満たせなければ e3**。条件は、(1) SessionStart のフックで開始時の HEAD・指示資産のハッシュ・作業ツリーの未コミットの有無・`session_id` を記録する(導出ではなく観測)、(2) コミットへの結びつけはコマンドの書き換えによらない、(3) 実機の Claude Code で確かめる、(4) 実行の識別子は「引き当てる先の保持は採用者による」と注記し、識別子の記録と引き当て先の保持を別のマークに分ける
- e2 は**採らない**。近似を出すなら「推定」と表示しなければならず、推定の値を 5.8.2 の記録とは扱えない

## F 入力の記録の保持(IMPL-0492)

降ろすと信頼性が下がる場合:

- **f1 は、書き込みの権限を持つワークフローに他の実行の成果物を取り込ませる**。`ai-review.yml` は「どのジョブもこの成果物を取り込まない(書き込みのジョブへ渡さない)」を設計の不変条件として注記している(#371・ADR-0115 の文脈)。成果物を上げる手順は差し込み口の前にあるが、成果物の名前の選び方・実行の特定(PR の先頭の SHA と一致する実行か)・バイト列のままの写しを誤ると、`contents: write` のジョブに PR の側で影響を受けた内容が入る。実機(GitHub Actions)で確かめていない変更を delivered にしてはならない
- f1 の代わりに、マージの時点で `record-copy.yml` が入力の記録を作り直す案も考えられる。これは採らない。AI レビューは push ごとに走り、その時点の既定ブランチの指示を読む。マージの時点の作り直しは別の時点の値であり、近似を記録として出すことになる
- f2 の「保持の設定を採用者が確かめる」は、公開のリポジトリでは成り立たない(90 日が上限。P6)。`plan=adopter` と表示すると、公開のリポジトリの採用者には実装の手段が無いのに手段があるように見える

降ろさないと信頼性が下がる場合:

- 四半期の初めの約2日分の実行が、抜き取りの時点で消えうる。抜き取りの母集団が欠けたまま、それを知らずに抜き取ると、抜き取りの結果が母集団全体を代表すると誤読される

結論:

- **f1 は、実機の確認を条件に採る**。確認の項目は、(1) 成果物の取得を PR の先頭の SHA と一致する `ai-review` の実行に限る、(2) 写しはバイト列のままで、写した側でハッシュを照合する、(3) スクリプトを実行しない、(4) `actions: read` を足すことの陰性の確認(3b)を記録する。実機の確認まで `undelivered`
- 確認が済むまでの表示は、非公開のリポジトリ(保持を 400 日まで延ばせる)と公開のリポジトリ(延ばせない)で分ける。公開のリポジトリについて、抜き取りの母集団から欠けうる期間を抜き取りの記録に書く旨を注記へ足す。抜き取りの周期を条項で変える案は、本件では採らない(H.12 の改めになり、本件の範囲を超える)

## G 書き込みの遮断のフックの試験(IMPL-0187・0198)

降ろすと信頼性が下がる場合:

- **試験が示すのはフックの判定の論理までである**。(1) フックが Claude Code から呼ばれること(`settings.json` の `PreToolUse` の `matcher: Edit|Write|MultiEdit|NotebookEdit` の結線)は、フックを直接起動する試験では確かめられない。(2) Bash の書き込み(`node -e` による書き出し、リダイレクト)は guard-write の外で、guard-bash も強制層のファイルへのシェルの書き込みを止めない
- IMPL-0198 は「許可範囲の変更をエージェントに実行させない」(5.8.6 要求事項6)を含む。G の試験で 0198 全体を `machine` にすると、Bash の経路が開いたまま要求事項6 が機械で担保されたと表示される
- 試験の場面を、一時の置き場へ写したフックで作るのは差し支えない。ただし、写す元は試験の実行の時点のテンプレートのファイルでなければならない(固定の写しを試験に持つと、フックの変更を試験が見ない)

降ろさないと信頼性が下がる場合:

- E3 で 37 場面が期待どおりと確かめた。試験が無いままでは、フックの変更で遮断が外れても誰も気づかない。`check=manual` を続ける理由は無い

結論:

- **g1 を採る**。条件は、(1) 試験に `settings.json` の `PreToolUse` の結線(matcher に4つの道具名、コマンドが guard-write を指す)を読む場面を含める(`:ng` は結線を外した写し)、(2) 0187 は `machine` へ改める(ロック中のテストへの書き込みの遮断と、ロックの外の通過)、(3) 0198 は2つに分ける。拒否の記録と Edit 系の強制層の遮断は `machine`、要求事項6(許可範囲の変更をエージェントに行わせない)は Bash の経路が開いているため `manual` のまま、その旨を注記に書く、(4) 試験を `gate-g5` の contract ジョブの `run:` から、`|| true` などを付けずに実行する(machine の要件3)

## 議長への要点

1. A は 0208・0257・0282 を採る。0206 は範囲を行に書けるときだけ採る。0491 は ADR-0124 決定4 により delivered にしない。現在の `plan=scheduled` も ADR-0084 決定4 と食い違う
2. CLAUDE.md は 197 行で、標準の参考の値 200 行(EV-0088)の手前にある。足す行は同じ変更で相殺することを条件にする
3. B は 0227 を4つに分ける。個人のファイルの除外(PR の検査つき)と総分量(値は採用者)は降ろす。矛盾は manual。AI維持管理者のレビューは `CONTROL_FILES` と別の一覧で行い、陰性の確認を課さない
4. **3.11.5 の「機械検査の3点」は改めるべきで、重へ上げることを求める**
5. C は `.mcp.json` を統制の設定と CODEOWNERS の雛形へ足す。ただし利用者の範囲のサーバーは止めないので、IMPL-0228 の範囲を注記で限る
6. D の sandbox を delivered にすることには反対する(ネイティブの Windows では効かず、Edit・Write は隔離の外)。`dontAsk` モードは未確認で、確かめてから判断する。**5.8.6 要求事項3 は定義が欠けており、改めるべきで、重へ上げることを求める**
7. E は SessionStart での観測による記録なら採る。履歴からの導出(e2)は近似なので採らない。`updatedInput` でコミットのコマンドを書き換える形も採らない
8. F の f1 は実機の確認(実行の特定・ハッシュの照合・陰性の確認)を条件にする。公開のリポジトリで `plan=adopter` と表示しない
9. G は採る。ただし 0198 を分け、要求事項6 の部分は Bash の経路が開いているため manual に残す。試験には `settings.json` の結線の場面を含める
10. 範囲の外の発見: `auto` モードが既定になったため、ask は人の確認ではない(`survey-303.md` §2.2)。IMPL-0199 の注記の読み方に掛かる。新規の起票ではなく、既存の open Issue へコメントで申し送る
11. 2委員の結論が割れる可能性が高い論点は B(3.11.5)と D(要求事項3)である。受付の規則(intake「審議の重さ」)により、重への引き上げを議長が判断する
