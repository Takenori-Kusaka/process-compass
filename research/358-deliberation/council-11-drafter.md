## H-1 3.11.5「変更時に機械検査する」の3点

### 推す案

- **(a) 条項を改める**。機械が判定できる項目と、人が判断する項目を分ける。AI の指摘は判断の材料として使ってよいが、検査にも判断にも数えない
- 2委員が指摘した型(判定できないものを「機械検査」と書くと、LLM の判定を検査と称させる誘因になる)は、外部の調査とも整合する。業界の道具が決定的に検査できるのは分量・参照の実在・設定と重なる規則の型の照合だけで、LLM を使う道具は判定に印を付けて決定的な検出と分けている(survey-external §1.1)。規格は検査の手段が何を見逃すかを記録することを前提にする(同 §1.2。T2・TEVV、二次資料を含む)

### 条項の文言の案(3.11.5 の箇条の3つ目と2つ目を差し替え)

- 指示資産の変更は、**AI維持管理者の承認を必須とする**。必須とする手段(所有者定義、承認を要する必須の検査)は問わない
- 変更時に機械検査する。検査項目は次の2つとする
  - 総分量が上限内か。上限は組織が定める(3.11.4 要求事項1)。上限を定めていない間は、検査の結果を「上限未設定」とし、通過として扱わない
  - 機械で検出できる形の検出。少なくとも、常駐させる規則の欠落と、コードベースから導出できる内容の典型の形(ディレクトリの木、依存の一覧)を検出する
- 既存の記述と矛盾しないか、コードベースから導出できる内容でないかは、**AI維持管理者が変更のレビューで判断する**。機械の検出が0件であることを、矛盾や導出できる内容が無いことの根拠にしてはならない
- AI による矛盾・重複の指摘を、レビューの材料に用いてよい。指摘は機械検査にもレビューの判断にも数えない。用いたときは、指摘の内容と採否を記録に残す(附属書H H.4 の条件5 と同じ形)

文言の理由:

- 「所有者定義により」を手段の限定から外す。所有者定義(CODEOWNERS)は `team.json`(`require_code_owner_review: false`)では必須にならない。テンプレートが実際に効かせられるのは、既定ブランチの定義で走る `gate-g5-base` の承認の照合である。文言が手段を CODEOWNERS に限ると、効く手段で降ろしても条項の字面に合わず、効かない手段で降ろすと担保が無い
- AI の指摘の扱いを条項に書くのは、書かなければ採用者が LLM の判定を「機械検査の3点目」として置くためである。ADR-0012(AI の出力は未検証の入力)と H.4(AI の推定は判定に数えない)の投影であり、新しい義務ではない

### 採らない案と理由

- 3点を条項に残し、矛盾の検査を `plan=adopter` にする案: 採用者にも手続が無い。ADR-0124 決定4 と同じ型で、表示が事実に反する
- 矛盾の検査を LLM の判定で合否に使う案: 非決定の結果を合否に使う案は ADR-0084 の R-5 で退けた。退ける理由は変わっていない
- 形の検出の0件を「導出できる内容でない」の記録とする案: 検出の外の書き方で通る

## H-2 5.8.6 要求事項3「書き込みはタスクの対象のパスに限る」と隔離

### 推す案

- **(a) 要求事項3 を改める**。起案(council-01 D-2)の「既定ブランチの計画のタスクから範囲を選ぶ」形は、担い手がどのタスクでも選べるため、実際に効く境界は**人が承認した計画の対象のパスの和**である。タスク単位の限定は境界ではなく、選んだタスクの外の書き込みを担い手自身の誤りから守る補助にすぎない。この実態を条項に書かずに「タスクの対象のパスに限る」と表示すれば、境界を偽る
- 外部の調査でも、タスク単位のパスの許可を持つ提供者は無い。単位は作業ディレクトリ・ブランチ・コンテナで、タスクの境界は環境の境界で近似している(survey-external §2.1)。最小権限の規格は「任務に必要な範囲」を求めるが粒度を定めず、LLM06 は許可の判断を担い手の外で強制することを求める(同 §2.2)

### 条項の文言の案(要求事項3 を3つの文に分ける)

- 書き込みとネットワークは既定を拒否とし、許可する範囲を列挙する。コマンドの実行は許可リストによる
- 書き込みの許可は、**人が承認して既定ブランチへ入った実装計画の対象のパスの和**と、案件が定めた成果物・記録の置き場の固定の一覧に限る。許可の範囲を定める入力は、担い手が書き換えても範囲が変わらない場所(既定ブランチの版)から読まなければならない(要求事項6)
- 作業中のタスクの対象のパスの外への書き込みは、要求事項10 の差で示す。実行時にタスク単位で拒否する場合も、タスクを選ぶ操作が範囲を広げないことを要する
- ネットワークの許可は必要な宛先に限る

文言の理由:

- 計画の起案中の書き込み(仕様・計画・判定記録、`Spec: setup`)は固定の一覧で扱う。担い手が計画を書いても、範囲が広がるのは G-4 を経て既定ブランチへ入った後で、人の承認を経る。要求事項6 と両立する
- 「既定ブランチの版から読む」は要求事項7(指示を対象の変更から書き換えられない場所に置く)と同じ型で、作業ブランチの計画を書き換えて範囲を広げる経路を塞ぐ

### テンプレートへ降ろすもの

| 部分 | 降ろし方 | 効く範囲 |
| --- | --- | --- |
| ファイルの道具の書き込み | guard-write に許可の一覧を足す。許可 = 既定ブランチの先端(`git show <既定>:<計画>`)の全計画の「変更の対象パス」の和 + 構成の固定の一覧(`docs/specs/**`・`docs/self-heal/**`・`context/**` ほか)。一覧の外の Edit・Write・NotebookEdit を遮断して `denied.log` に `out-of-scope` で残す。既定ブランチが読めない・計画が読めないときは固定の一覧だけを許す(開く向きに倒さない) | 全 OS。Bash の書き込みは含まない |
| タスク単位の補助 | `self-heal start --task` と同じ印があるとき、そのタスクの外への書き込みを遮断する。印は範囲を狭めるだけで、印を消しても上の和へ戻るだけ | 全 OS |
| シェルの書き込み・読み取り | `sandbox.enabled: true`、`filesystem.denyWrite` に強制層、`denyRead` に秘匿情報の経路 | macOS・Linux・WSL2 だけ(P1) |

| 状態の表示 | SessionStart(`next.mjs --brief`)が、ネイティブの Windows か `sandbox.enabled` が偽なら「シェルの隔離: なし。Bash の書き込み・通信は止まらない」を毎回出す | 全 OS |

- 権限のモードの `dontAsk`、`permissions.blockWritesOutsideWorkingDirectories`(v2.1.314 以降)、`denyInsteadOfPrompting`(利用者・管理の設定だけ)は、提供者の文書と実機で確かめてから採る。後者は案件の設定で効かないので、採用者への推奨として ADR-0126 へ書く

## H-3 IMPL-0491(git merge と push の組)

### 推す案

- **マークの主題を改め、降ろし先を CLAUDE.md の常駐の行へ移す**。gate-criteria の本文は既に「本標準は、既定ブランチ以外へ取り込むマージを拒否する設定を課しません」と書き、禁止は人の手順とマージの後の検出で支える(ADR-0124 決定4)。現在の IMPL-0491(`target=guard-bash-hook`)は、本文が課さないと決めたフックの拒否を降ろし先にしており、`scheduled` も `adopter` も事実に反する。条項は改めなくてよい。マークが条項より多くを主張している
- AI の担い手に禁止を届ける手段は指示文しか無い。L-1 で 0208・0257・0282 を同じ型で delivered にしたのと揃える

### 文言の案(CLAUDE.md「判断の確定と委任」の行)

- **既定ブランチ以外へ取り込むマージをしない**。`git merge` で取り込んで `git push` する組も当たる。既定ブランチの変更を作業ブランチへ取り込む同期は当たらない。`gh pr merge` と API のマージはフックが止めるが、`git merge` と `git push` の組は止まらない(標準 第4章「積み重ねた変更とゲート」)
- 行に `[機械]` を付けない。止まる経路は既存の行(IMPL-0255)が `[機械]` で示す

### マークの扱い

- IMPL-0491: `target=claude-md-resident state=delivered check=presence`。注記に「指示文だけ。担い手がその行に従うことは確かめない。PR を経ない取り込みはマージの後の検出(IMPL-0248)にも掛からない」
- フックによる `git merge`+`git push` の拒否は、ADR-0126 の「課さない」の一覧へ載せ、ADR-0124 決定4 を引く(棚卸しの `not-imposed`)

### 採らない案と理由

- undelivered のまま残す案: 付けられる `plan` が無い。表示が事実に反し続ける
- 資格情報の範囲(Copilot の型)を採用者に求める案: ADR-0124 決定4 の「採用者もホスティングの上で実装する手段を持たない」を覆す材料が外部の調査に無い(survey-external §4)
- 採用者への影響: 変わらない。人の手順(`.github/rulesets/README.md`)と検出は既存のまま

## H-4 生成の条件の自動の記録(IMPL-0207)

### 推す案

- **観測の記録とコミットのトレーラの組。ただしコマンドを書き換えない**。反対委員の指摘(確認の画面と実際のコマンドの食い違い、ヒアドキュメント・`-F`・`--amend` での破損)を受け、`updatedInput` は採らない。代わりに git の `prepare-commit-msg` フックでトレーラを足す。git の正規の仕組みで、コミットのメッセージに残り、利用者は `git log` で見られる
- 手順
  1. SessionStart のフックが観測を書く: `session_id`(P3)、開始時の HEAD、指示資産(`CLAUDE.md`・`AGENTS.md`・`.claude/**`)の木の hash、未コミットの変更の有無。置き場は端末ごとの `.claude/run/<session_id>.json`(`.gitignore`)
  2. PreToolUse(Bash)は `git commit` を検出したら、入力を変えずに「この session の commit が起きる」印(`.claude/run/pending.json`、時刻つき)を書くだけにする
  3. `prepare-commit-msg` が印(数十秒以内)を読み、`Agent-Run: <session_id>` と `Agent-Context: <開始時の HEAD の短縮>/<指示資産の hash>[+dirty][+changed]` を足す。`+changed` はコミットの時点の指示資産の hash が開始時と違う場合。印が無い・古い場合は足さない(人のコミットに付かない)
- 版管理に入るのはトレーラだけ。観測のファイルは版管理に入れない
- 「指示資産の版を履歴から導出する」(e2)は採らない。開始の後の変更と未コミットの変更を誤る(council-02)。観測の値に `+changed` を残すことで、導出では区別できない場合を記録に出す

## H-6 CLAUDE.md の行数と 3.11.3 の文言

### (a) 相殺の条件

- **相殺を条件にしない**。規則を削って行数を保つことは、実証の無い参考の値(ADR-0084)のために既知の禁止を落とす取引で、信頼性を下げる。コアポリシーの「最小限の変更という動機は存在しない」にも当たる
- ただし次の2つは行う。どちらも規則を落とさない
  - **主題が同じ行の統合**: 0208 を既存の「モデルの系統・提供元の違いを、確認の強さの根拠として書かない」の行と1行にする(保証の開示等に書いてはならない主張、という同じ主題)。核の文言の変更なので常駐の規則の一覧を同じ変更で改める
  - **行の中の手順の移動**: 冒頭の原則(「1行が1つの規則で、詳細は所在」)に反して手順を抱える行は、詳細を補助ファイルへ移す。規則の文は残す
- 分量は H-1 の新 A で行数と文字数を毎回出す。ADR-0126 に「テンプレートの CLAUDE.md は参考の値を超えうる。参考の値は上限ではない」を、根拠水準のマーク(行数と遵守の関係の実証が無い)つきで書く

### (b) 3.11.3 との食い違い

- **食い違う**。字面は「誘導層に書くこと」を禁じ、テンプレートは機械の手段の無い禁止を CLAUDE.md に多数置く。後者を消すのは誤りで(担い手に規則が届く経路が無くなる)、条項の字面が趣旨(同じ節の caution の「守られるという前提で統制を設計してはならない」)より強く書けている
- 文言の案: 「**遵守が必須の規則を、誘導層に書いたことで守られるものとして扱ってはなりません**。遵守が必須の規則は強制層へ降ろします。強制層へ降ろす手段が無い規則は、誘導層へ書いたうえで、機械では止まらないことと、違反を見つける手段(人の確認・事後の検出)の所在を併記します」
- テンプレートの「規則の索引」の `[機械]` の印の説明は、この文言をそのまま実装している。IMPL-0221 の行(L-3)は、この文言に合わせて「止まらないことと、見つける手段の所在を行に書く」とする

## H-7 IMPL-0492(入力の記録の保持)

### 推す案

- **記録用ブランチへ運ぶ形(f1)を主とし、実機の確認まで `undelivered plan=scheduled issue=358 review=2027-05` を保つ**
- 実機の確認の項目
  1. 取り込む成果物を、PR の先頭の SHA と一致し、既定ブランチの定義(`.github/workflows/ai-review.yml`、`pull_request_target`)で走った実行に限る
  2. 同じ名前の成果物を、差し込み口の後の手順が上げ直せないこと(重複の名前の上げが失敗すること)
  3. バイト列のままで写し、写した側で sha256 を照らす。中身を実行・展開しない
  4. PR のすべての push の実行を写す(抜き取りの単位は実行ごと)。成果物が既に無い実行は「入力の記録なし(理由)」を写しに残す
  5. マージされずに閉じた PR でも動く(H.12 の母集団を歪めない)
  6. `actions: read` を足すことの陰性の確認(3b)を記録する
- 記録用ブランチへ運ぶ以外の形
  - 非公開のリポジトリで成果物の保持を抜き取りの周期の最大(約 92 日)を超える値(例: 120 日)にする形は、採用者の選択肢として認める。確認の後の表示を「公開: f1 による」「非公開: f1 または保持の設定」とし、保持の設定は `/pit` が `retention-days` と構成を照らして足りなければ出す
  - 外部の保管庫へ運ぶ形は採用者の選択(`plan=adopter` の別のマーク)。業界の実務の型で、取り出せることの確認を求める(survey-external §5)
- 確認までの間も、公開のリポジトリでは「四半期の初めの実行は抜き取りまでに消えうる。抜き取りの記録に欠けうる期間を書く」を注記と抜き取りの手順に出す

## 範囲外: `auto` のモードのもとでの ask

- `auto` のもとでは ask は分類器の判定で、人の確認ではない(council-02 0.3)。IMPL-0199 の注記の「確認つき」は、人の確認と読まれうる
- 本件では、秘匿情報の読み取りを deny へ上げる(H-2)ことで、その部分は ask に頼らなくなる。強制層の編集の ask は guard-write の遮断(0198)が支えるので残してよい
- IMPL-0199 の注記に「`auto` の権限のモードでは ask は人の確認にならない」を足すことを、既存の open Issue へコメントで申し送る。新規の起票はしない
