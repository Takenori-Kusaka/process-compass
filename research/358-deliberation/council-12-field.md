## H-1: 3.11.5「変更時に機械検査する」の3点

- **推す案**: 条項を改める(起案・反対と同じ向き)。機械の検査は「総分量」と「機械で検出できる形」に限る。矛盾と導出の判断は AI維持管理者のレビューへ移す。AI による検出はレビューの材料として使ってよいと明記し、通過の根拠にさせない
- 現場の理由: 指示資産の差分には、実際に AI のレビューを当てたくなる。禁じれば手元で黙って使われ、記録に残らない。許して位置づけを決めるほうが記録が残る。一方で「AI が矛盾なしと言った」が承認の代わりに使われる事態は、日常の PR で必ず起きる。だから、使ってよいことと根拠にしてはならないことを同じ文に書く
- **採らない案と理由**
  - 3点を残して `plan=adopter`: 採用者にも手段が無い。採用者の現場では LLM の判定を「機械検査」と呼んで置くことになる(反対委員の指摘のとおり)
  - 「依存の一覧の形」を検出したら失敗: F3 のとおり、送信の統制のための版の固定が誤検出になる。誤検出で止まる検査は、例外の一覧が育って形骸化する。**木の図の記号(`├──`・`└──`)は失敗でよい**(正当な使い道が指示資産に無く、誤検出が少ない)。依存の形は検出の一覧に出し、合否に使わない
  - 総分量を行数だけで数える: F2 のとおり、1行が 430 字に達する。行を連結すれば行数は減る。行数と文字数の両方を出す
- **マーク(IMPL-0227 を5つに分ける)**

| 部分 | target | state | check |
| --- | --- | --- | --- |
| AI維持管理者のレビュー(指示資産の一覧で本人の承認を要する。陰性の確認は課さない) | pr-checks | delivered | machine(`test-control-approval.mjs`)。承認の要求を有効にしない体制では効かないことを注記 |
| 総分量(行数と文字数を出す。値は構成。無ければ「未設定」と出し、通過と出さない) | pr-checks | delivered | machine |
| 形の検出(木の図は失敗、依存の形は一覧) | pr-checks | delivered | machine(木の図)。注記に「検出しなかったことは導出できない内容であることを示さない」 |
| 矛盾・導出の判断 | claude-md(AI維持管理者の手順) | 条項を改めた後は delivered | manual(確かめる者: AI維持管理者) |
| 個人用のファイルの除外 | pr-checks | delivered | machine |

- **文言の案**(3.11.5 の3つ目の箇条を置き換える): 「変更時に、総分量が上限内か(上限は 3.11.4 要求事項1 で組織が定めた値。分量は行数と文字数で数える)と、機械で検出できる形(ディレクトリの木の図など)を機械で検査する。既存の記述と矛盾しないか、コードベースから導出できる内容でないかは、AI維持管理者がレビューで判断する。この判断に AI の検出を材料として使ってよい。AI の検出の結果と、機械の検出が0件であることを、矛盾や導出できる内容が無いことの根拠として記録してはならない」。ADR-0012(AI の出力は未検証の入力)、附属書H H.4(AI の確認は検出の層)と同じ扱いである
- **採用者への影響**: 指示資産の PR に AI維持管理者の承認が要る(1名の体制は 3c と同じ扱い)。分量の値を定めるまで「未設定」が出続ける。AI のレビューの結果は指摘として残し、承認の欄には書かない

## H-2: 5.8.6 要求事項3「書き込みはタスクの対象のパスに限る」と隔離

### (a) 条項を改める

- **推す案**: 反対委員の向きで改める。許可の単位を「人が確定した実装計画の対象のパスの和」と「構成に列挙した成果物・記録・基盤の置き場」にする。タスク単位の一致は要求事項10 の差の突合で確かめる
- 現場の理由(具体の場面)
  1. **担い手がタスクを宣言しても、実質は和になる**。担い手は承認済みのタスクのどれでも宣言できるため、宣言を切り替えれば全タスクの和へ書ける。タスク単位の限定は「うっかり」を止めるが「意図」を止めない。止められない範囲を「限った」と書く条項は、表示が担保を上回る
  2. **複数のセッション**: 1つの作業ツリーで2つのセッションを動かすと、作業ツリーごとの「作業中のタスクの印」が取り合いになる。和なら印が要らず、取り合いが起きない
  3. **タスクの外の作業**: 仕様・計画・判断記録の起案、`Spec: setup`(`SETUP_FILES`)の変更、人がその場で頼む README の誤字の修正。いずれも計画に無い。列挙の置き場が無ければ毎回止まる
  4. **誤検出の後の迂回**: 止まり続けると、現場は `guard.enabled: false` に手を伸ばす。今の guard-write では、この1つのスイッチで強制層の遮断(IMPL-0198)まで外れる。範囲の限定は、強制層の遮断と別のスイッチにしなければならない
- **採らない案**: タスク単位の限定を現行の文言のまま delivered にする(起案)。上の 1・2 により、表示が担保を上回る。条項を改めずに `undelivered` を続ける案も採らない(どの提供者もタスク単位の許可パスを持たない。`survey-external.md` §2.1。降ろす見込みが無い)
- **文言の案**(要求事項3): 「書き込みとネットワークは既定を拒否とし、許可する範囲を列挙する。書き込みの許可は、人が確定した実装計画の対象のパスと、構成に列挙した成果物・記録・開発の基盤の置き場に限る。列挙の追加と、範囲の限定を外すことは、人の操作で行う(要求事項6)。タスクごとの範囲との一致は、要求事項10 の突合で確かめる。ネットワークの許可は必要な宛先に限る。コマンドの実行は許可リストによる」

### (b) テンプレートへ降ろすもの

1. **guard-write の範囲の限定**(Edit・Write・MultiEdit・NotebookEdit): 既定ブランチの先端の実装計画の「変更の対象パス」の和と、構成の列挙の外への書き込みを遮断する。計画は `git show <既定ブランチ>:<計画>` で読む。手元の既定ブランチが古く、承認済みのタスクが止まるときは、拒否の文に「`git fetch` の後に再試行」を出す(安全側に止まり、直し方が分かる誤検出は許容する)。計画を読めないときも止める。スイッチは `guard.enabled` と分ける
2. **大文字小文字の正規化**(F1): ネイティブの Windows と macOS では、照合の前にパスと型の両方を小文字へそろえる。現状の強制層の遮断にも掛かる欠陥であり、範囲の限定を足す前に直す
3. **sandbox**: macOS・Linux・WSL2 向けに設定を置く。`filesystem.denyWrite` に強制層・ロックのファイル・範囲の列挙のファイルを置く。これで guard-write が塞げない Bash の書き込み(`echo >`・`node -e`)が、効く環境でだけ塞がる。担い手が隔離の外での実行を求める経路(Bash の道具の隔離を外す引数)を設定で閉じる手段があるかを実機で確かめる。[未確認: 記憶。`allowUnsandboxedCommands` という設定があると記憶するが、提供者の文書で確かめていない]
4. **秘匿情報の経路の読み取りを ask から deny へ上げる**: `auto` のもとで ask は人の確認ではない(範囲外の節)。deny は Bash の `cat .env` を止めない(隔離の効かない環境では特に)ことを注記に書く
5. `/pit`(env-check)が、ネイティブの Windows では「シェルの隔離なし」と出し続ける(`process.platform` で決定的に判定できる)

## H-3: IMPL-0491(git merge と push の組)

- **推す案**: 3つに分ける
  1. CLAUDE.md の行「既定ブランチ以外へ取り込むマージをしない(既定ブランチからの同期は当たらない)。`git merge` と `git push` の組は機械では止めない」を、**別のマーク**(`claude-md-resident`・delivered・presence)で置く。`[機械]` を付けない
  2. 0491 の本体(条項の義務)は、**事後の検出**を手段として `undelivered plan=scheduled` に置き直す。G-5 の `pr-rules` が、既定ブランチへの PR のコミットのうち、2つ目の親が既定ブランチから到達できないマージコミットを一覧に出す(合否に使わない)。既定ブランチからの同期は2つ目の親が既定ブランチの履歴にあるので区別できる。手段があるので、ADR-0084 決定4 の「手段の無い規定を scheduled と表示し続けない」に当たらない
  3. `gh pr merge` と API のマージの拒否は既存の IMPL-0255 のまま
- **採らない案と理由**: 指示文の行だけで 0491 を delivered にする(起案)。マークの主題(取り込み先を既定ブランチに限る)は行では担保されない。`undelivered plan=scheduled` のまま据え置く(現状)。降ろす手段を示さない scheduled は ADR-0084 決定4 に反する。ルールセットの Restrict updates を既定にする案も採らない。積み重ねた変更の中間のブランチへは担い手の push が要り、push と取り込みを区別できない
- 検出の限界(注記へ): ローカルの `git merge --squash` で作った通常のコミットは検出できない。検出が0件であることを、中間へのマージが無かった根拠にしない(5.8.6 要求事項9 と同じ型)
- **採用者への影響**: 最終の PR に一覧が出る。正しい流れ(中間の PR は既定ブランチ以外へ取り込まない)では一覧は空になる。誤検出は、人が手元で同僚のブランチを取り込んだ場合に出る。それは条項の義務に当たるので、誤検出ではない

## H-4: 生成の条件の自動の記録(IMPL-0207)

- **推す案**: コマンドを書き換えない、観測による記録。実機で確かめるまで `undelivered plan=scheduled`
  1. SessionStart のフックが、`session_id`・開始の時点の HEAD・指示資産(`CLAUDE.md`・`AGENTS.md`・`.claude/**`)のハッシュ・未コミットの変更の有無を記録する
  2. コミットへの結びつけは git の `commit-msg` フックで行う。PreToolUse(Bash)は、`git commit` を含むコマンドを見たら「このセッションが今コミットする」という短命の印を書くだけで、入力を書き換えない。`commit-msg` は印があるときだけトレーラ `Agent-Run`・`Agent-Context` を足し、印を消す。印の無いコミット(人が手で打ったコミット)には足さない
  3. 記録の置き場は `git rev-parse --git-common-dir` の下(版管理の外、作業ツリーの外)。Claude Code が作る worktree は片付けで消えるため、作業ツリーの中の記録は失われる
- 現場の理由
  - `updatedInput` で書き換える案(起案)は、日常の書き方とぶつかる。Claude Code は `git add … && git commit -m "$(cat <<'EOF' … EOF)"` のような複合のコマンドとヒアドキュメントで頻繁にコミットする。起案は複合のコマンドを拒否するとしたが、それでは毎回のコミットが一度止まる。止まるたびに担い手が書き直し、書き直しの中でトレーラを手で書き写す誤りの経路が開く
  - F5 のとおり `git commit` は allow にあり確認の画面が出ないので、「画面と実行の食い違い」の懸念は、このテンプレートでは弱い。それでも、強制層のフックが担い手のコマンドの意味を変える形は、`--amend`・`-F`・`--no-edit` との組で壊れうる(反対委員)。採らない
  - SessionStart の観測だけ(反対委員)では、記録が手元に残るだけで、レビュアーと出荷の集約に届かない。届く担い手はコミットである。`commit-msg` は git の文書にある手段(`survey-external.md` §3)で、コマンドを変えない
- **採らない案**: 履歴からの導出(e2。近似。未コミットの変更とセッション中の指示資産の変更を誤る)。環境変数 `CLAUDE_CODE_SESSION_ID` への依存(文書の約束ではない)
- 確かめる項目(実機): 複合のコマンド・ヒアドキュメント・`--amend` で正しく1回だけ足ること。人のコミットに足さないこと。`--no-verify` の扱い(guard-bash で拒否するか)。複数のセッションが同じ作業ツリーで同時にコミットするときに印が混ざらないこと(印に `session_id` を入れる)
- Claude Code 以外の基盤: `plan=adopter`(識別子の取り出し方が基盤ごとに異なる)
- **採用者への影響**: `/process-init` が `core.hooksPath` を設定する。公開のリポジトリでは `session_id` が履歴に出る。値は URL ではないが、公開の可否を構成で選べるようにする(出さない選択をした場合は、手元の記録だけになることを `/pit` に出す)

## H-6: CLAUDE.md の行数と 3.11.3 の文言

### (a) 相殺の条件

- **推す案**: 相殺を条件にしない。分量は行数と文字数で出し(H-1)、採用者が上限を定めたときだけ判定する。同じ主題の行は統合する(0208 は既存の「モデルの系統・提供元」の行と同じ節で統合する、反対委員の案に賛成)

### (b) 3.11.3 の文言

- **食い違う**(反対委員と同じ)。テンプレートの CLAUDE.md は `[機械]` の印の無い行を多数持つ(印のある行は 20)。文字どおりに読めば、それらは 3.11.3 に反する
- **文言の案**: 「遵守が必須の規則を、誘導層にだけ書いて守らせたものとして扱ってはなりません。強制層へ降ろせる規則は強制層へ降ろします。降ろす手段の無い規則は、誘導層に書いたうえで、機械では止まらないことと、人が確かめる所在(または事後の検出)を併記します」
- 現場の理由: 担い手に規則を届ける経路は誘導層しか無い場合がある。「書いてはならない」は、規則を担い手に知らせない方向へ誤読される

## H-7: IMPL-0492(入力の記録の保持)

- **推す案**: 記録用ブランチへ運ぶ案(f1)は実機の確認まで `undelivered plan=scheduled`。それまでの間、非公開のリポジトリについては `retention-days` を構成の値から取る(上限は 400 日と組織の設定)形を併せて置く
- 確認の項目(実機)
  1. 運ぶ実行の特定は、PR のイベントの `pull_request.head.sha` と一致する `ai-review` の実行に限る。スカッシュのマージではマージのコミットの SHA が先頭と違うため、マージの SHA で探してはならない
  2. 同じ先頭に再実行で複数の成果物があるときの選び方(最新の成功、または全部)
  3. バイト列のままの写しと、写した側でのハッシュの照合。成果物の中のスクリプトを実行しない
  4. `actions: read` を足す変更の陰性の確認(3b)の記録
  5. マージされずに閉じた PR の扱い(H.12 の母集団に入るなら閉じたときも動かす)
- **採らない案**: マージの時点で入力の記録を作り直す(別の時点の値で、近似を記録として出す)。公開のリポジトリで `plan=adopter`(公開では保持を延ばす手段が無い)
- 公開のリポジトリの注記: 確認が済むまで、抜き取りの記録に「保持の期限で欠けうる期間」を書く
- **採用者への影響**: 非公開のリポジトリはすぐに欠けを減らせる(費用は保存の容量)。公開のリポジトリは確認が済むまで欠けうる期間を開示し続ける

## 出発点(L-1〜L-7)への付記

- L-5 に条件を足す。F4 のとおり、テンプレート自身のスキルが MCP サーバーを local scope(`~/.claude.json`)へ足すよう案内している。`.mcp.json` を置き場として統制しても、テンプレートの案内が統制の外へ誘導する。同じ変更でスキルの案内を改めるか、local scope の登録を 3.11.6 の採用の記録(判断記録)へ書く手順を置く。覆しはしない

## 範囲外: `auto` の権限のモードのもとでの ask

- 現場では `auto` が対話の既定で、ask は分類器が通すか止めるかを決める。人の確認ではない
- PreToolUse のフックの終了コード 2 と deny は、モードに依らず効く。したがって本件の設計は「ask で人が確かめる」を担保に数えず、フック・deny・sandbox だけを数える。H-2 の (b) 4 はこの帰結である
- IMPL-0199 の注記(ask を人の確認として書いている部分)の読み方の修正は、既存の open Issue へ申し送る。確認を拒否へ変える設定(`denyInsteadOfPrompting`)は利用者・管理の設定だけで効くので、採用者に求める事項として ADR-0126 に書く
