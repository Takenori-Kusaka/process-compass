### B-4 条項を改めるか(明言)

- **改めるべきである**。3.11.5 の「変更時に機械検査する。検査項目は…の3点とする」は、「矛盾しないか」「導出できる内容でないか」を機械が判定することを要求している。この判定は、テンプレートにも採用者にも実装できない。`scheduled` と書けば降ろす見込みを偽り、`adopter` と書けば採用者に不可能を課す。ADR-0084 決定4 は「課さないと決めた規定は条項を改める」、ADR-0124 決定4 は「手段の無い規定を scheduled・adopter と表示することは事実に反する」とした。同じ型である
- 改めの案: 「変更時に機械検査する。総分量の上限の超過と、機械で検出できる形(常駐の規則の欠落、ディレクトリの木の図・依存の一覧の形)を検査する。既存の記述との矛盾と、コードから導出できる内容であるかの判断は、AI維持管理者のレビュー(本節の2項目め)で行う。機械の検出が0件であることを、矛盾や導出できる内容が無いことの根拠にしない」
- これは条項の改廃で、受付の「重へ上げる」条件に当たる。反対委員の結論に依らず、**この部分だけを重の審議へ分けて送る**ことを起案する。B の他の部分は軽で進める。改めるまでの間、該当部分のマークは `state=undelivered plan=scheduled` とし、`issue=` に重の審議の Issue を書く(`adopter` にしない)

## D 実行環境の拒否の既定(IMPL-0200)

採る案: **(d1)+(d2) で降ろせる範囲を降ろし、降ろせない部分を (d3) として ADR-0126 へ書く**。マークを4つに分ける。

1. **書き込みの既定の拒否(ファイルの道具)**: 権限設定の既定は「確認」で、拒否ではない(P2)。確認は 5.8.6 の冒頭が言う形骸化の経路であり、拒否に数えない。権限のモードに、許可の規則に無い道具を確認せずに拒否するモード(`dontAsk`)がある、と起案者は理解している。survey の P1〜P6 には無いので、**提供者の文書と実機で確かめてから採る**。成り立てば、`defaultMode` をこのモードにし、書き込みの許可を `Edit(./src/**)` などの列挙にする。成り立たなければ、guard-write のフックに「許可の一覧に無いパスへの書き込みを遮断する」を足す(フックはモードに依らず働く。E3 で遮断の経路は確かめた)
2. **タスクの対象のパスへの限定**: guard-write に、作業中のタスクの印(`self-heal` のロックと同じ型の、端末ごとのファイル)があるとき、**既定ブランチの先端の実装計画**の当該タスクの「変更の対象パス」の外への書き込みを遮断する機能を足す。範囲を定めるのは G-4 を経て既定ブランチへ入った計画で、担い手が選べるのは人が承認した範囲のどれかだけである。したがって要求事項6(範囲の変更を担い手の操作で行わせない)と衝突しない。タスクの外の作業(仕様・計画・記録の起案、`Spec: setup`)の書き込みの範囲は、1. の列挙で扱う。試験は `test-guard-write.mjs` に対を足す(`check=machine`)
3. **シェルとネットワーク**: `sandbox` の設定(`enabled`、`network.allowedDomains` をホスティングと依存の取得先に限る、`filesystem.denyWrite` に強制層、`denyRead` に秘匿情報の経路)を置く。WebFetch は宛先の許可の列挙に限る。ただし、隔離はネイティブの Windows で効かず、ファイルの道具・MCP・フックに掛からない(P1)。隔離が効いていない実行を `/pit`(env-check)が「隔離なし」と出す手段があるかを実機で確かめ、無ければこの部分は `check=manual` で、確かめる者を AI維持管理者とする
4. **秘匿情報を参照できない位置へ置く(要求事項4)**: リポジトリの設定では実現できない。置き場はリポジトリの外(秘密の管理の仕組み・CI の秘密)の問題である。`plan=adopter`。ADR-0126 に、理由「秘匿情報の配置は端末と組織の基盤で決まり、リポジトリの設定は読み取りの制限(要求事項4 が頼るなと定める手段)しか持たない」と、採用者に求めること「秘匿情報を作業ツリーと担い手の利用者の範囲の外へ置き、置き場を D-0 へ書く。作業ツリーに `.env` を置く運用は 5.8.6 に適合しない」を書く

- 1.〜3. のうち実機で確かめられなかった部分は `state=undelivered` に残す。降ろした部分も、Bash による書き込み(`echo >` 等)がネイティブの Windows ではどの層にも止められないことを注記へ書く。5.8.6 の本文(拒否を実装していない実行基盤の案件は 5.8.6 に適合しない)により、この限界は採用者の適合の判定に直結するので、`/pit` に出し続ける
- 5.8.6 は `impl-no-adopter.yaml` に無いので、4. を `adopter` にすることは ADR-0084 決定4 と衝突しない

## E 生成の条件の自動の記録(IMPL-0207)

採る案: **(e1)**。実行で成り立つことを確かめるまで `undelivered` に残す。(e2) の「指示資産の版は履歴から導出する」は、作業ツリーに未コミットの指示資産の変更がある場合と、セッションの開始の後に指示資産が変わった場合に誤った版を出すので、単独では採らない。

- SessionStart のフックが、入力の `session_id`(P3)と、開始の時点の指示資産の版(`CLAUDE.md`・`AGENTS.md`・`.claude/**` の木の hash と、未コミットの変更の有無)を、端末ごとのファイル(`.gitignore` へ)へ書く
- PreToolUse(Bash)のフックが `git commit` を検出したら、`updatedInput` でコマンドの末尾へ `--trailer "Agent-Run: <session_id>" --trailer "Agent-Context: <版>[+dirty]"` を足す。担い手に値を書き写させない(書き写しは誤りと捏造の経路になる)。複合のコマンド(`&&`・`;`・パイプ)の中の `git commit` は書き換えずに拒否し、単独で実行させる
- `pr-rules` が、`Co-Authored-By` を持つコミットに2つのトレーラがあるかを確かめる(`check=machine`、試験の対)。値が真の実行を指すかは確かめない(注記へ)
- 実行の識別子は、実行の記録(transcript)が残っていて初めて意味を持つ。記録の保持は利用者の端末の設定に依る。ADR-0126 に「実行の識別子の記録は、実行の記録の保持を保証しない。保持の期間と置き場は採用者が定め、D-0 へ書く」を書く
- Claude Code 以外の担い手(`session_id` を出さない基盤)は `plan=adopter`。理由は「識別子の取り出し方が実行の基盤ごとに異なる」(ADR-0084 決定4 の IMPL-0279 と同じ型)

## F 入力の記録の保持(IMPL-0492)

採る案: **(f1)**。(f2) は採らない。公開のリポジトリでは成果物を 90 日を超えて保てず(P6)、四半期の初めの実行が抜き取りの時点で消える。設定を確かめる手順を採用者に求めても、公開のリポジトリには満たす手段が無い。

- `record-copy.yml`(マージを契機に動く)に、PR の先頭のコミットの AI レビューの実行の成果物(inputs.json)を読み、記録用ブランチの `records/ai-review/<PR 番号>/` へ写す手順を足す。権限は `actions: read` を足すだけにする。AI レビューのジョブに書き込みの権限を与える案は採らない(PR を契機に動く側へ書き込みを与えると、信頼できない変更から記録用ブランチを書き換える経路になる)
- 写すときに sha256 を照らし、成果物が既に無い・照合が合わない場合は、写さずに「入力の記録なし」を記録する(欠けを消さない)
- マージされずに閉じた PR は写らない。抜き取りの母集団に閉じた PR が入るかを H.12 と突き合わせ、入るなら閉じたときも動かす
- 書き込みの権限を持つワークフローの変更で、`CONTROL_FILES` に当たる。GitHub Actions の実機(一時の試行のリポジトリ)で確かめるまで `undelivered` に残す。確かめた後も、ワークフローの静的な試験だけでは規定を確かめたことにならないので `check=manual`(確かめる者: AI維持管理者。`env-check` の項目に足す)とする

## G 書き込みの遮断のフックの試験(IMPL-0187・0198)

採る案: **(g1)**。試験(`test-guard-write.mjs`)は既に contract ジョブ(`gate-g5.yml`)の `run:` に結線されており、目印 `IMPL-0187:ng/ok`・`IMPL-0198:ng/ok` を持つ。両マークを `check=machine test=template/scripts/gate/test-guard-write.mjs` へ改める。

- 試験に1場面を足す。`.claude/settings.json` の PreToolUse の matcher が `Edit|Write|MultiEdit|NotebookEdit` を持ち、guard-write を呼ぶこと。フックの単体が正しくても、結線が外れれば遮断は起きないため
- 注記に、Bash による書き込みを遮断しないこと(既存)と、試験は Claude Code がフックを呼ぶことまでは確かめないことを書く

## CLAUDE.md の行数(197 行、参考の値 200 行)

- A の5行、B-1 の3行、C の1行で約 206 行になり、参考の値を超える
- **参考の値に収めるために規則を削らない、縮めない**。参考の値は実証の無い値で(ADR-0084 決定3・決定4、IMPL-0222 は `adopter`)、実証の無い値のために既知の禁止を落とせば、信頼性を下げる取引になる。既存の行を短くすることも採らない。核の文言を変えることは標準の規定の書き換えで(ADR-0084 決定2)、規則ごとに審議を要する
- 一方で、行数が増えるほど担い手が読み落とす懸念はある(3.11.4 要求事項1 の趣旨)。B-3 の総分量の検査で、テンプレートの出荷の時点の行数と文字数を出し、採用者が上限を定めたときに超過が見えるようにする。テンプレートは上限を定めない
- ADR-0126 に「テンプレートの CLAUDE.md は参考の値の 200 行を超える。参考の値は上限ではない。上限は採用者が定め、超えるなら採用者が規則をスキルへ移すかを判断する。テンプレートの側で削らない理由」を書く。根拠水準のマークを付ける(行数と遵守の関係に実証が無い)

## ADR-0126 に書く「降ろさない」の一覧(起案)

| 部分 | 理由 | 採用者に求めること |
| --- | --- | --- |
| 3.11.5 の矛盾・導出の機械の判定 | 判定の手続が存在しない | (重の審議で条項を改めるまで)AI維持管理者のレビューで判断する |
| 利用者の範囲の MCP サーバー | 案件の設定に優先する手段が無い | 組織の管理の設定で限る |
| 秘匿情報の配置(5.8.6 要求事項4) | リポジトリの外の配置の問題 | 作業ツリーの外へ置き、D-0 へ書く |
| ネイティブの Windows のシェルの隔離 | 隔離が動かない | 隔離が動く基盤で担い手を動かすか、別の隔離を置く |
| Claude Code 以外の実行の識別子・実行の記録の保持 | 基盤ごとに異なる | 取り出し方と保持の期間を D-0 へ書く |
