## 0. 全議題に掛かる監査の基準

監査人は、台帳の `delivered` を「守られていることが確かめられている」と読みます(ADR-0061 のコンテキスト)。そこで、各議題を次の4つの基準で評価します。

| # | 基準 | 違反の例 |
| --- | --- | --- |
| Q1 | 1つのマークは、確かめ直せる1つの主張だけを持つ。主張の一部だけが確かめられるなら、マークを分ける | 遮断できる経路とできない経路を1つの `machine` に束ねる |
| Q2 | 機械の検査・人の確認・AI の確認を、記録の上で混ぜない。AI の確認は H.4 の「AI の推定による判定」で、判定に数えない。機械の検査の名で記録しない(ADR-0012) | LLM の判定を「機械検査の通過」と記録する |
| Q3 | 指示文だけの規則の `presence` は、「行がある」ことしか示さない。注記に、挙動を止めないことと、違反を誰がどこで見つけるか(または誰も見つけないこと)を書く | `presence` の注記が単位だけで、違反の検出の所在が無い |
| Q4 | 確かめた証跡は、抜き取りの時点まで、担い手が書き換えられない置き場に残る | 端末ごとのファイルにだけ残る記録、90 日で消える成果物 |

確認(ask)は、`auto` の権限のモードのもとでは人の確認ではありません(反対委員 0.3、`survey-303.md` §2.2)。本書は、ask を人の確認の担保に数えません。

## H-1: 3.11.5「変更時に機械検査する」の3点

### 推す案

- **条項を改める**。現在の文は「矛盾」「導出できる内容」を機械が判定すると読める。監査人がこの条項に照らして採用者を確かめると、適合の証跡になり得るのは LLM の判定の記録だけになる。これは H.4 の「AI の推定による判定は判定に数えない」と食い違い、監査の上で適合を確かめる手段が無い条項になる
- 改め方は、機械の検査・人の確認・AI の確認の3つを条項の文の上で分ける。AI の確認は使ってよいが、H.4 の検出の層として記録させ、判定と通過に数えさせない
- 人の確認は、承認だけでは監査で区別できない。AI維持管理者のレビューの記録に、2項目(矛盾・導出)を確かめたことと結論が残る欄を置く。欄が無いと、「承認した」と「2項目を確かめた」を監査で分けられない

### 採らない案と理由

| 案 | 理由 |
| --- | --- |
| 条項を残し、矛盾・導出を `plan=scheduled` で表示し続ける | 降ろす手段が存在しない。ADR-0084 決定4・ADR-0124 決定4 の「事実に反する表示」に当たる |
| 同じく `plan=adopter` | 採用者にも手段が無い。不可能を課したまま、採用者が LLM の判定を「検査」と称して置く誘因になる |
| LLM の判定を合否に使う | 非決定的な合否は ADR-0084 R-5 で退けた。H.4 の条件4(合否条件に入れない)にも反する |
| 2項目を条項から削る | 矛盾の除去は 3.11.3 が AI維持管理者の職掌の中心に置いたもので、削ると職掌の確認の対象が消える。判定の担い手を人へ移せば足りる |

## H-2: 5.8.6 要求事項3 と隔離

### 推す案

- **(a) 要求事項3 を改める**。監査人は現在の文で採用者を確かめられない。タスクの外の作業(仕様・計画・記録の起案、`Spec: setup`)の書き込みの範囲が定義に無く、どの書き込みが「範囲外」かを判定する基準が無い。基準の無い要求事項は、監査で適合とも不適合とも言えない
- 改め方は、許可の範囲を**人が確定した記録の和**で定める。範囲の構成要素はいずれも既定ブランチの先端に入り、担い手が選べず、監査人が後から再び引ける。タスク単位の限定は要求事項10(計画と実際のパスの差)で事後に検出する
- **(b) テンプレートへ降ろすもの**
  - guard-write: 既定ブランチの先端の実装計画の対象パスの和と、固定の一覧(成果物の置き場)の外への Edit・Write・NotebookEdit を遮断する。範囲は担い手の宣言に依らない。起案のタスクの印による絞り込みは、和より狭める向きだけなので要求事項6 に触れないが、監査の担保には数えない(担い手が任意のタスクを選べるため)
  - 秘匿情報の経路の読み取りを ask から deny へ上げる(要求事項1 の「接触」の一部。`auto` のもとで ask は人の確認でない)
  - `permissions.blockWritesOutsideWorkingDirectories`(v2.1.314 以降と外部の調査が記す)。実機で確かめたうえで、キーを置く
  - sandbox の設定は置いてよいが、**担保として表示しない**。効いたことの証跡(その実行で隔離が効いていた記録)が残らないため、監査で確かめ直せない

## H-3: IMPL-0491

### 推す案

- **0491 を CLAUDE.md の行で delivered にしない**。0491 の主題は「AI の担い手が git merge と git push の組で取り込むこと」の拒否で、降ろし先は `guard-bash-hook` である。行を足しても主題は降りない。降ろし先と主題の違う降ろし方は、監査人に担保を読み違えさせる(Q1)
- CLAUDE.md の行は**別のマーク**として足す(`claude-md-resident` / delivered / presence、単位: 行)。注記に「指示文だけ。git merge と git push の組を止めず、PR を経ない取り込みはマージの後の検出(IMPL-0248)にも掛からない」と書く(Q3)
- 0491 の表示は `scheduled` に残してよい条件を1つ確かめる。押し上げの後の機械の検出の手段がありうる [推論・未確認]: 作業ブランチへの push を契機に、新しいマージのコミットの第2親が既定ブランチから辿れないかを調べれば、中間の層への取り込みのうちマージのコミットを作る形を検出できる。既定ブランチからの同期(第2親が既定ブランチ上)とは区別できる。`--squash` と rebase の形は拾わない
- 手段が実機で成り立てば、0491 は `plan=scheduled` が事実に合う(ADR-0084 決定4 と両立する)。成り立たなければ、ADR-0124 決定4 の帰結に合わせ、主題を「課さない」とする条項の文(既にある「拒否する設定を課さない」)に結び、棚卸しの `not-imposed` へ移す。どちらにするかを決める期限を `review=` に置く

### 採らない案と理由

- 0491 を delivered にする: 上記(Q1)。ADR-0124 決定4 は「git merge と git push の組は降りていない」と明記した
- 根拠の無いまま `scheduled` を続ける: ADR-0084 決定4 に反する。上の検出の手段の確かめを `scheduled` の根拠として注記に書かない限り採らない

### 採用者への影響

- 行が1行増える。検出の手段が成り立てば、作業ブランチへの push に CI の契機が足される

## H-4: 生成の条件の自動の記録(IMPL-0207)

### 推す案

- SessionStart のフックで観測した値(`session_id`、開始の時点の HEAD、指示資産の木の hash、未コミットの変更の有無)を記録する。履歴からの導出(e2)は近似で、5.8.2 の「観測できる事実」に当たらない
- **監査の論点は置き場**である。端末ごとのファイル(`.gitignore`)だけでは、抜き取りの時点に監査人が引けない(Q4)。コミットへ結びつける必要がある
- 結びつけは、Claude Code の `updatedInput` によらず、**git の `commit-msg` フック**(`git interpret-trailers`)で、観測の記録からトレーラ `Agent-Run`・`Agent-Context` を足す形を推す [推論・未確認]。git の標準の仕組みで、確認の画面のコマンドと実行のコマンドが食い違わない。`--no-verify` で外せるため、`pr-rules` が `Co-Authored-By` を持つコミットにトレーラがあるかを確かめ、欠けを出す(machine)。値が真の実行を指すかは確かめない(注記)
- 指示資産の版は「開始の時点の版」と表示する。セッションの中で指示資産を変えたコミットの後のコミットには「版の混在の可能性」を出す

### 採らない案と理由

- `updatedInput` でコマンドを書き換える: 人が見たコマンドと実行されたコマンドが食い違う。監査の証跡(実行の記録)の上で、何が実行されたかの読みが割れる
- 履歴からの導出: 近似を記録として出すことになる

### マークの扱い

| 部分 | state・check |
| --- | --- |
| 観測の記録とトレーラの付与(Claude Code) | 実機で確かめるまで undelivered / plan=scheduled。確かめた後に delivered / machine(欠けの検出の試験) |
| 実行の記録(transcript)の保持 | undelivered / plan=adopter。識別子は引き当て先が残って初めて働く。識別子の記録と保持を同じマークにしない(Q1) |
| Claude Code 以外の基盤 | undelivered / plan=adopter(識別子の取り出し方が基盤ごとに異なる。IMPL-0279 と同じ型) |

- 識別子を公開の履歴へ出すことの可否は採用者が決める。出さない場合の代わりの置き場(記録用ブランチ)を ADR に書く

## H-5: IMPL-0198 の check と要求事項6

### 推す案

- **3つに分ける**。1つの `machine` にすると、Bash の経路が開いたまま要求事項6 が機械で担保されたと読まれる(Q1)

| 部分 | state・check |
| --- | --- |
| 拒否の記録(`.claude/denied.log`。要求事項5) | delivered / machine(`test-guard-write.mjs`) |
| Edit・Write・NotebookEdit による強制層への書き込みの遮断と、`settings.json` の PreToolUse の結線 | delivered / machine(結線の場面を `:ng`・`:ok` に含める) |
| 許可範囲の変更を担い手の操作で行わせない(要求事項6)の全体 | undelivered / plan=scheduled |

- 要求事項6 を `manual` の delivered にすることは採らない。要求事項6 は「満たさない実行基盤では要求事項1 の拒否は成立しない」と定める。シェルから `.claude/settings.json` を書けば、その端末のセッションで許可範囲が広がる。これは人の確認で事後に拾えない局所の変更で、「人が確かめている」とは言えない
- 共有の範囲(既定ブランチへ入る強制層の変更)は、統制の設定の承認(AI維持管理者本人の承認)で止まる。この部分が既存のマークで担保されていれば、0198 の注記から所在を引く
- `scheduled` の根拠: 隔離の `filesystem.denyWrite` に強制層を置けば、隔離の効く基盤ではシェルからの書き込みを止められる。効かない基盤(ネイティブの Windows)は `/pit` に出し続ける

## H-6: CLAUDE.md の行数と 3.11.3 の文言

### (a) 相殺の条件

- **相殺を条件にしない**。参考の値の 200 行は実証の無い値(EV-0088、ADR-0084 決定3・4)で、条件にすれば実質の上限になり、値を採用者へ委ねた ADR-0084 と食い違う。相殺のために既知の禁止を落とすと、監査で確かめられる行が減る
- 代わりに開示する。総分量の検査(H-1)の出力に、テンプレートの出荷の時点の行数と文字数を出し、ADR に「参考の値を超える。上限ではない。行数と遵守の関係は未実証」を根拠水準のマークつきで書く
- 手順的な行を補助ファイルへ移すことは、行ごとの判断として妨げない(条件にはしない)

### (b) 3.11.3 との食い違い

- **食い違う**。現在の文「遵守が必須の規則を誘導層に書いてはなりません」は、文字どおりでは、テンプレートの CLAUDE.md の印の無い禁止の行(5.8.5 の禁止事項など)と A の5件を、条項に反して見せる。監査人は、テンプレートそのものを 3.11.3 の不適合として指摘できてしまう
- 改める。改めた文に「違反を見つける確認の所在を行に併記する」を含めると、Q3 が条項の要求になり、監査で確かめられる

### 条項の文言の案(3.11.3)

> 遵守が必須の規則を、誘導層にだけ置いて守られたものとして扱ってはなりません。強制が必要な規則は強制層へ降ろします。強制層で止める手段の無い必須の規則を誘導層に置くときは、止める仕組みが無いことと、違反を見つける確認(人の確認、または事後の機械の検出)の所在、または見つける手段が無いことを、その行に書きます

### マークの扱い

- IMPL-0221 は delivered / presence(単位: 行)に加え、**テンプレートの CLAUDE.md の禁止事項の表の「止める仕組み」の列が空でないこと**を常駐の規則の検査で確かめる(machine。列が空の行を `:ng`)。指示文だけの行が、その旨を書かずに残ることを機械で止められる

### 採用者への影響

- 採用者が足す禁止の行にも、止める仕組みか検出の所在を書く手間が増える

- 確認の項目(監査が確かめ直すための証跡を含む)
  1. 成果物の取得を、PR の先頭の SHA と一致する `ai-review` の実行に限る
  2. バイト列のまま写し、写した側で sha256 を照らす。合わない・既に無いときは写さず「入力の記録なし」を記録する(欠けを消さない)
  3. 成果物の中のスクリプトを実行しない。`actions: read` を足すことの陰性の確認(3b)を記録する
  4. 記録用ブランチの写しを、担い手と PR の側から書き換えられない(記録用ブランチの保護の設定を確かめ、陰性の確認に含める)
  5. 写しから監査人が取り出せることを、写した直後に1回確かめる(PCI の二次資料の「取り出しを試す」の型)
- 抜き取りの記録に、母集団の定義(マージされずに閉じた PR を含むか)と、「入力の記録なし」の件数を書く。欠けた件数が分からない抜き取りは、母集団を代表すると読まれる

### 採らない案と理由

| 案 | 理由 |
| --- | --- |
| `retention-days` を 90 より大きくする | 公開のリポジトリは 90 日が上限で、超えた値は黙って切り詰められる [推論: P6 の「上限を超えられない」]。書いた値と実際の保持が食い違う |
| マージの時点で入力の記録を作り直す | 別の時点の値で、近似を記録として出す(反対委員) |
| `plan=adopter`(保持の設定は採用者) | 公開のリポジトリには満たす手段が無い |
| 抜き取りの周期を縮める | H.12 の改めで本件の範囲を超える |

- 記録用ブランチの外の保管(オブジェクトの保管庫)は採用者の選択として ADR に書いてよい。テンプレートの担保には数えない

## 範囲外: `auto` のもとでの ask

- テンプレートの CLAUDE.md の行(「guard.enabled の構成では拒否。それ以外は確認つき」)と IMPL-0199 の注記は、ask を人の確認と読ませうる。監査では、ask の担保を人の確認に数えない。IMPL-0199 の注記に「`auto` の権限のモードでは確認を分類器が行う」を足すことを、既存の Issue へ申し送る(起票しない)
