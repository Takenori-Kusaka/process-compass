## 1. 採る案と理由

**案 B′: 本文だけで、(1) 衝突の解消、(2) 例示の正本を本文へ置いて2つの区分に分ける、(3) ADR は新設せずステータスの節への注記で足りる。**

調査の案 B を次の2点で強める。

1. **例示の正本を 5.5.1 に置く**。3.5.5 に「取り消せない操作の例」の行を書くには、参照先に例示がなければならない。例示が template にしか無い状態は、本標準が規格として自立していない。例示は ADR-0041・ADR-0053 決定2 の「列挙は例示」の範囲であり、基準(取り消せない時間帯が存在すること)を変えない
2. **区分は排他でない**と明記する。同じ操作が両方に当たることがある(例: 配備の環境の保護規則を、ブランチを経ずに設定 API で直接外す。統制の弱化であり、外した時点で効果が生じるため取り消せない時間帯も生じうる)。排他と読ませると、両方に当たる操作を片方の経路だけで止める抜けが生じる。両方に当たるなら両方の経路(`state:needs-platform` と `state:needs-owner`)で止める

理由は信頼性の3点。(a) 衝突した文面は、L841 だけを読む者に needs-owner の併記を落とさせる。安全側の経路が文面の衝突で開かないのは欠陥である。(b) 例示が同じ列に並ぶと、配備の起動(取り消せない操作)と配備の統制の削除(統制の弱化)が、#329 決定2 の規則と統制の弱化の規則のどちらで止まるか読めなくなる(#329 17節)。(c) 例示の正本が準拠テンプレートにしか無いと、テンプレートを直すたびに規格が動く。

案 A(分けない理由を書くだけ)は採らない。調査は「2つの定義は既に別」とするが、定義が別でも例示の置き場が無い限り、読み手は template (c) の「削除」から混同する。

## 6. 自案の弱点

1. **2.3 で例示を本文へ置くと、template (c) の右欄と二重管理になる**。`template-fields.yaml` の検査(必須欄の両方向)が、5.5.1 の追加文と衝突しないかを `npm run check` で確かめていない。衝突すれば 2.3 を落とし、3.5.5 の表の左欄を「5.5.1 の基準に当たる例」とだけ書く縮小版にする
2. **「配備のワークフローの起動」を取り消せない操作の例とするのは、5.5.1 箇条1(後段で人が自ら起動する上流の編集は当たらない)との境界が曖昧**。起動そのものは当たり、起動する人の承認(環境の承認)は門である、という読みで整合させたが、読み手が箇条1 と取り違える余地がある
3. **「両方に当たりうる」の行は、設定 API による直接変更という具体例を1つしか持たない**。単一事例に近い。根拠水準マークを付けるべきか迷う。私は「規定の積であって新しい値ではない」としてマークを付けない案を採るが、議長が実証を欠くと見るなら EV を付ける
4. **ADR のステータスの節への注記は、機械の検査で縛られていない**。ADR-0038 の読み手が注記を読み落とせば、当時の「不可逆4操作」の引用がそのまま残る。`lint` が語彙(採用 / 一部置き換え …)を厳密に検査する場合、「採用(日付)」の後ろの文が通るかを確かめていない。ADR-0078 のステータスの節が既に文を持つ前例に拠った
5. **template 側(c)・L43・handoff.md・claude-md-resident.json は直せない**。本文が先に変わると、template の常駐の規則と本文が一時的に食い違う。L43 が L882 の併記条件を写していない差は、現在も既に存在する。Issue に残す一覧は調査 6.2 のとおりでよいと考える。加えて、(c) の右欄の「削除」を「データの削除」に直すことを一覧へ足す(同音異義の原因そのもの)
6. 併記条件の正本を L882 とし L841 が写す形は、2か所の文面を手で揃える二重管理を残す。1か所へ寄せる案(L841 を L882 への参照のみとする)もあるが、L841 は受信箱の表の読み手が最初に当たる所で、参照だけにすると衝突の再発は防げる代わりに読み手の負担が増える。どちらを採るかは議長の裁定に委ねる
