## 中

### M-1 検索の上限(1000 件)で、外した Issue を黙って落とす

- **実態**: `fetchScMItems` のページ送りは、`first:50` × 20 ページ(1000 件)で、`hasNextPage` が真のまま何も言わずに抜ける。GitHub の検索も 1000 件までしか返さない。2つ目の検索 `is:issue updated:>=<確定の日>` は、ラベルに関係なく、確定の日の後に更新された全 Issue を返す。活発なリポジトリでは、1つのステージの間に 1000 件を超えうる。超えた分にある「外した Issue」は削除に数えられず、変動率を小さく出す。1巡目 H-2 と同じ向きの誤りである
- **直しとの食い違い**: 同じ直しは、出来事が 100 件を超える Issue について「黙って欠かずに読めないと出す」とした。件数の上限は同じ扱いになっていない
- **再現**: `cx2.mjs` 4b。21 ページ目に外した Issue を置くと、`{pagesRead:20, err:null, has99:false}` になる
- **同じ形**: `fetchClosedUnits` も 20 ページで黙って抜ける(直しの前からある。0374 の材料にかかわる)
- **直しの案**: ページの上限に達して `hasNextPage` が真なら、例外を投げて「読めない」と出す(`issueCount` が 1000 を超えるときも同じ)。2つ目の検索は、`updated:>=` に `-label:"SC-M"` を加えて範囲を狭める。いま付いている Issue は1つ目の検索で読む。gh の注入の試験に、上限を超える場面の ng を足す

### M-2 確定の日の前に閉じた Issue を、確定時の個数から除くのに、追加・削除には数える

- **実態**: 直しで、`scMChanges` の `baseline` から「確定の日以前に閉じた Issue」を除いた。`added`・`removed` には同じ除外が無い。閉じた後にラベルを整理すると(外す・付ける)、変動に数える
- **再現**: `cx2.mjs` 5。開いた SC-M 1件(#30)、09-10 に閉じて 10-05 にラベルを外した #31、09-12 に閉じて 10-06 にラベルを付けた #32。結果は `{baseline:1, added:1, removed:1, rate:2}`。実際のスコープの変化は 0 なのに、変動率が 200% になる
- **影響**: 変動率を大きく出す。安全側の向きではある。ただし、価値責任者が 7.6 の発火を判断する材料が実態と食い違う。SKILL.md の「外すと削除(SC-P・SC-B へ移す・分割して外す)に数えます」とも合わない。閉じた Issue のラベルの整理は、SC-P・SC-B へ移すことではない
- **直しの案**: 確定時の母集団と、変動を数える対象を同じにする。出来事の日に Issue が閉じていたものは、追加にも削除にも数えない。`closedAt` と出来事の日を比べる。fixture の試験に、この場面の ng を足す。0377・0614 は undelivered なので、直しは B20 の後の単位でもよい。その場合は 0614 の note に開示する

## 低

- **L-1 出来事の日付は UTC のまま**: 1巡目 L-1 の直しは `fetchClosedUnits` の `closedAt` だけを手元の日付に直した。`scMChanges` は、出来事の `at` と `closedAt` を UTC の先頭 10 字で、手元の暦の `confirmedOn` と比べる。`cx2.mjs` 1a では、JST 10-01 08:30(UTC 09-30 23:30)に外すと、確定の前の出来事として扱われ、削除にも確定時の個数にも入らない。`cx2.mjs` 6 では、JST 10-01 01:00 に閉じた Issue を、確定の日以前に閉じたとして母集団から除く。同じ出力の中で、2つの暦が混ざる。**直しの案**: `localDay(new Date(at))` で比べる
- **L-2 「外すと更新の日が進む」前提を確かめていない**: 和集合の2つ目の検索は、ラベルを外すと Issue の `updatedAt` が進むことを前提にする。この前提を試験でも実環境でも確かめていない。pit-in-template では、作成時に付けたラベルの `LabeledEvent.createdAt` が `updatedAt` より1〜2秒後だった(#45〜#49。読み取りだけで確かめた)。後で外したときの挙動は確かめていない。0614 の note の開示は「GitHub から読む部分は試験で確かめていない」の一般的な文だけである。**直しの案**: 降ろす単位(B20 の後)で、外した Issue が `updated:>=` に入ることを実環境で1回確かめ、記録に残す
- **L-3 出来事の無い Issue を落とす**: 今 SC-M が付いていて、ラベルの出来事が読めない Issue(ラベルを削除して `label` が null になった出来事、移管された Issue など)は、`events.length` が 0 で除かれる。`remaining` が減り、「対象外」へ寄る(`cx2.mjs` 3a・3b)。直しの前も `remaining` には数えていなかったので、回帰ではない。**直しの案**: 1つ目の検索で返った Issue は、出来事が無くても `open` なら `remaining` に数える
- **L-4 試験の弱さ**: `IMPL-0614:ok 確定の日以前に閉じた Issue は…` の2つ目の条件(`!fetched.find((i) => i.number === 12 && ch2.baseline === 3)`)は、1つ目の条件が真なら常に真で、意味を持たない。ページ送りの場面(`hasNextPage` が真)の試験が無い(`cx2.mjs` 4a で手で確かめた)。L-1 の直し(`fetchClosedUnits` の暦)にも試験が無い(「既存の試験が通過」は、直しの正しさを示さない)
- **L-5 手引きに SG の後の扱いが無い**: pit/SKILL.md は、SG の後は完了の条件が一致しても「算定できない」と出ることを書かない。0377・0614 が降りていないことも書かない。実行の出力は理由を出すので、誤った判断には至らない
- **L-6 「完全に一致」と ADR**: 0374 の note は「完全に一致」を「一致」へ改め、NFKC と末尾の句点の同一視を開示した(1巡目 L-2)。採用済みの ADR-0173 決定2 は「完全に一致」のままである。note の開示で閉じる扱いは、1巡目の直しの案のとおり。ただし ADR と実装の差は残る。H-1 の裁定で 0374 を扱うときに、厳密な一致へ戻すか、差を裁定に記録するかを決める
