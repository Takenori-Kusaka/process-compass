### H-1 0377・0614 は、適合する案件では区分(甲・乙・丙)も変動率も出ない。それなのに delivered / check=machine と表示している

- **表示**: 0377 の note(`exception-escalation.md` 496 行)は「区分(甲・乙・丙・算定できない・対象外)を出す」と書く。SG の後は算定しないことを開示していない(開示は 0374 の note だけにある)。0614 の note(同 291 行)は、変動率を出すと書く

### H-2 SC-M のラベルを外した Issue を取得しない。削除(SC-P・SC-B へ移す)が数えられず、変動率を小さく出す

- **実態**: `fetchScMItems`(next.mjs、diff の 404 行。`q=repo:… is:issue label:"SC-M"`)は、GitHub の検索の `label:` で絞っている。この絞り込みは、**今その名前のラベルが付いている** Issue だけを返す。ラベルを外した Issue は結果に入らない。その結果、`removed` は数えられず、その Issue の確定時の数も `baseline` から落ちる。0614 の note の「ラベルを外すことを削除に数える」と食い違う
- **付随する問題**
  - 前のステージで完了して閉じた SC-M の Issue は、ラベルが残る限り `baseline` に入り、変動率を薄める
  - `timelineItems(first:100, itemTypes:[LABELED_EVENT,UNLABELED_EVENT])` はすべてのラベルの事象を数える。`state:*` の遷移が多い Issue では、SC-M の事象が 100 件の外へ落ちうる
- **再現**: `cx.mjs` の 6a・6b。確定時 2 件のうち 1 件を外した履歴を入れると `{baseline:2, removed:1}`。検索が返す形(外した Issue を除いた形)を入れると `{baseline:1, removed:0}` になり、変動率は 50% から 0% に変わる。6c では、前のステージの閉じた Issue が baseline に入る
- **直しの案**: ラベルで絞らずに、確定の日以降に更新された Issue の SC-M の事象を集める。または、ラベルの事象を検索せずに読む経路を使う。baseline は「確定の日に開いていた、または確定の日の後に閉じた」Issue に限る。gh の呼び出しを注入できる形(`recordPickupUndecided` の `run` と同じ形)にして、GraphQL の応答の fixture で ng(外した Issue が削除に数えられる)を試験する

## 中

### M-1 SC-M のラベルの運用を、文書に書かずに前提にしている。ADR-0173 決定4 と緊張する

- **実態**: ラベル名 `SC-M` は `next.mjs` の定数(`SC_M_LABEL`)にしか無い。SKILL.md・CLAUDE.md・ラベルの定義のどれにも、付け方が書かれていない(`grep -rn SC-M template` の結果は next.mjs だけ)
- **影響**: ラベルを付けない採用者には「対象外(未完了の SC-M が 0 件)」と出る。「対象外」は、本文 7.7.3 で SC-M を置かないことを表す確定した区分である(合格とも不合格とも書かない)。SC-M があるのにラベルが無いだけの案件を、確定した区分へ誤って入れる
- **既存の決定**: ADR-0173 決定4 は IMPL-0851 について「層の帰属を機械が読めるラベルの運用は課さないと決めた」と定める。0377 の note には「ラベルと照らす」とある。課すか課さないかが本文の中で揃っていない
- **直しの案**: ラベル付きの SC-M が 0 件のときは、企画書が「実測なし」と書く場合を除いて「算定できない(SC-M のラベルが無い)」と出す。ラベルの付け方は SKILL.md に書く。ADR-0173 決定4 との関係は議長が裁定する(採用者への新しい義務に当たるなら重)

## 低

- **L-1 TZ のずれ**: `closedAt` は UTC の日付で切り(`dayNum` が先頭 10 文字を読む)、`today` は手元の日付(`localDay`)を使う。たとえば 2026-11-05 01:00 JST に閉じた Issue は、前の期(〜11-04)に入る(`cx.mjs` 2)。直しの案: `closedAt` を手元の日付へ直してから比べる
- **L-2 「完全に一致」より緩い**: `isDefaultDoneCondition` は NFKC と末尾の句点(全角の「．」を含む)を同一視する(`cx.mjs` 4b)。ADR-0173 決定2 と note は「完全に一致」と書く。直しの案: 緩める範囲を note に書く
- **L-3 残りの期間の入力**: `--remaining-periods` は整数しか受けない。誤った値(`3.5`・`-1`・`abc`)は、何も知らせずに「入力なし」になる。端は `ceil` で丸める。実際の残りが 3.5 期のときに 3 と入れると、甲が乙になりうる(`cx.mjs` 5c)。直しの案: 読めない入力を出力に書く。丸め方を note に書く
- **L-4 /pit の遅延**: `fetchPickupComments` は、/pit を実行するたびに、リポジトリの全 Issue のコメントを `--paginate` で読む(timeout 60 秒)。コメントの多いリポジトリでは遅くなり、時間切れになる。表示だけなので、例外は捕まえている
- **L-5 数える単位**: `PR #N` を指定すると、宣言行は PR へ書かれ、PR の番号で数えられる。裁定の「作業単位の Issue」と一致しない。誰が書いた宣言行も数える(偽造できる。表示だけ)
- **L-6 書けなかった件数**: `--offline` で書かなかった件数を、権限で書けなかった件数と同じ数に混ぜている。裁定は「権限が無い」と書く。note は開示している
- **L-7 存在しない節**: SKILL.md と出力の見出しは「見込みの報告の Issue の節『材料の集計』」を指す。この節を持つ Issue の様式は、テンプレートに無い
- **L-8 記録の件数**: `impl-unit8.md` は test-next-records を「110 件」と書く。実際に流すと 109 件だった
