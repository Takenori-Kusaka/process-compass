## 所見

### R-1 高 IMPL-0216 は5指標のうち2つが降りていないのに delivered/machine になっている

- 根拠: `src/content/docs/phase4-process-design/roles-responsibilities.md` 3.10.8 の表(5指標)と IMPL-0216 の note「判定当日に初めて出た論点の比率と資料公開から判定までの日数は集計していない」。
- 規約: `community/implementation-marking.md` の「降りていない規定の扱い」の最後の項目は、降ろし先がある規定の全部または一部が無い場合を、降りていない規定の表に置くとしている。同じコミットは IMPL-0175 について、「並びだけが降りた。表現・強調は降りていない。一部だけ降りた規定は降りていない側に置く」として undelivered に残した。0216 は同じ形なのに delivered にしていて、同じ束の中で扱いが割れている。
- 食い違い: 台帳は 3.10.8 を「機械が確かめる」と表示する。しかし2指標は機械も人も集計していない。特に「資料公開から判定までの日数」は、pre-review.mjs が公開の時点と T をすでに持っており、決定可能である。降ろす予定の部分であって、機械で閉じない部分ではない。
- 直しの案(どちらか): (a) IMPL-0216 を `state=undelivered check=manual plan=scheduled issue=325` に戻し、降りた3指標を note に書く。(b) マークを分ける。3指標は `delivered check=machine` のまま残す。「資料公開から判定までの日数」は新しい `undelivered plan=scheduled` のマークにする。「判定当日に初めて出た論点の比率」は意味を読むため、`manual`(確かめる者: 決定者)の別のマークにする。台帳での見え方は (b) のほうが正確である。

### R-2 高 IMPL-0979 は PR を持たないゲートの期限超過を検出しないのに delivered/machine になっている

- 根拠: 第7章 7.5 の条文の対象は「判定期限を超過」で、ゲートを限っていない。会議体の決定の期限の超過(3.9.3)も同じ扱いとしている。note は「PR を持たないゲートは確かめない」と書く。試験(`test-review-queue.mjs` 118〜134 行)は G-6 と G-3(context/decisions/)の場面しか持たない。
- 食い違い: G-1・G-7・G-8・SG の判定期限の超過と、会議体の決定の期限の超過は、機械が検出しない。どのマークもこれを追っていない。IMPL-0369 は D-0 の様式の行(`check=presence`)を追うだけで、検出は追わない。R-1 と同じく、一部だけ降りた規定である。
- 直しの案: マークを分ける。PR で判定するゲート(G-2/G-4・G-3・G-6)の検出は `delivered check=machine` のまま残す。PR を持たないゲートと会議体の決定の期限は、新しい `undelivered plan=scheduled` のマーク(issue=445)にする。分けないなら、0979 全体を undelivered に戻す。

### R-3 高 IMPL-0210 の `check=machine` は、規定の違反を検出する試験を持たない

- 根拠: 3.10.3 は「判定資料は次(5項目)を含まなければなりません」と定める。試験の目印のうち `IMPL-0210:ng`(79 行)は「T の5営業日前より前には起票しない」で、これは起票の時点の場面である。3.10.3 の違反(5項目を欠く判定資料)には当たらない。`:ok` の側も、5つの見出しを置いた雛形を起票することまでしか見ない。起案者が見出しを消すか空のまま公開しても、何も検出しない。
- 規約: `machine` は「機械が規定の中身を検査し、違反を止めるか件数で出す」もので、`:ng` は「違反の入力で検出する」場面でなければならない。`lint:impl` は目印の有無しか見ない(要件の表の後の注記)。目印の場面が規定の違反に当たるかは、この突合で確かめる事項である。
- 直しの案: `state=delivered check=manual` とし、note に「確かめる者: 決定者(判定の当日に5項目の充足を確かめる)」を書く。雛形を降ろしたので、delivered は保ってよい。機械の検査にするなら、公開した判定資料で5つの見出しが欠けているか空であるものを注意に出す処理と、その ng/ok を足す。見出しの有無は決定可能だが、中身の充足は機械で閉じない。

### R-4 中 IMPL-0283 は「または G-1 で合意した値」の側が降りていない

- 直しの案: 合意した値の側を `undelivered plan=scheduled`(様式の欄と読む処理。issue=443)の別のマークへ分ける。分けないなら、note に「G-1 の値を合意した案件では、その値による検出は降りていない」と、検出の漏れの向きを書く。

### R-5 中 IMPL-0681 の note が IMPL-0979 と食い違う

- 根拠: 0681 の note は「第7章 7.5 の代理判定者の指名の求めは、7.5 の節が未決(pending)で、いまは追うマークが無い」と書く。一方、7.5 の IMPL-0979 は、このコミットで delivered/machine になり、判定期限の超過で代理の指名を求める通知を追っている。
- 直しの案: 0681 の note の該当の句を「判定完了時間の超過で 7.5 の措置を求める通知は IMPL-0979 が追う(PR を持たないゲートは R-2 のとおり降りていない)」に改める。条文の「自動的な再割り当てを第一の手段にしない」に当たる試験の場面も無い。実装は再割り当てをしないので違反は起きないが、note に「再割り当ての処理を持たないことで満たす(試験の場面なし)」と一句足すとよい。

### R-6 中 定期の workflow と関数の結線を、どの試験も見ない(0680・0681・0682・0979・0136・0283・0571・0210・0213・0215・0216・0219 に共通)

- 実態: 5本の試験はどれも純関数(queueActions・flowActions・plan・metricsFor など)を固定の入力で呼ぶ。`review-queue-control.yml`・`pre-review.yml`・`flow-observation.yml` を読む試験は無い(`scripts/` で各 yml を名指すのは pre-review.mjs と preflight.mjs の一覧だけ)。schedule の契機や関数を呼ぶ run の行を消しても、contract は通る。
- 規約と先例: 規約の `machine` の3要件(試験の実在、ng/ok の対、contract からの実行)は満たしている。規約は「delivered は実物を読んで確かめたもの。実行では確かめていない。実環境で確かめていない点は note に書く」としていて、実物の GitHub で未確認のまま `delivered` を表示することを許している。先例も同じ形である。実行の経路を試験せずに純関数の試験で `machine` とした項目(IMPL-0458・0439・0331 など)が既にある。schedule の workflow を降ろし先とする既存のマーク(IMPL-0226・0850・0951)は manual だが、関数の対の試験を持たないためで、反例にはならない。したがって規約には違反しない。高とはしない。
- それでも中とする理由: これらの条文の要求の実体は「自動で通知する」ことである。規約の「入口についての規定なら、関数を直接呼ぶ試験では足りない」の趣旨にも近い。そして workflow の結線の破損は、純関数の試験からは見えない。各 note の「実物の GitHub では未確認」は、GitHub の権限や応答の形を開示しているが、「workflow の契機と呼び出しの行を試験が見ていない」ことは開示していない。
- 直しの案: (a) 3つの yml に、schedule(または pull_request_target)の契機と、`node scripts/gate/<名>.mjs` を呼ぶ run の行があることを確かめる静的な試験(決定可能)を足し、contract から実行する。たとえば既存の test-push-trigger.mjs の型で書ける。(b) または、各 note の「実物の GitHub では未確認」に「workflow の契機と呼び出しは試験で見ていない」を足す。(a) は template を触るので、並行の束との直列の規則に従う。

### R-7 低 IMPL-0682 の同時保有の数え方は、条文より狭い

note は、未応答の指名だけを数える近似であることを開示している。応答した後も承認していない PR は数えないため、条文の「判定待ちとして同時に抱える件数」より検出が少ない側に倒れる。開示があるので低とした。検出が漏れる向き(上限を超えても知らせない場合がある)を note に明記するとよい。
