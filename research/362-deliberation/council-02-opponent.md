# #362 会議体 委員2(反対)

- 立場: 反対。有力な案(方式 F。次点 G)と、起票者の提案「持ち込める範囲を広げる」の両方に、欠陥がある前提で当たる
- 材料: `survey.md`(観測 O1〜O8)、`template/.github/workflows/gate-g5.yml`・`delegation.yml`・`ship-evidence.yml`、`template/scripts/gate/preflight.mjs`・`delegation.mjs`・`aggregate-evidence.mjs`・`adoption-trial.mjs`・`g5-aggregate.mjs`・`verify-gate-contract.mjs`、ADR-0085、第5章 `template-repository.md`
- 表記: 「読解」はコードと本文を読んだ結果。「推測」は実機で確かめていない解釈。本委員は実機の確認を行っていない

## 0. 結論の先出し

- 方式 E(絞りを外し、ジョブの `if:` で絞る)は採れない。迂回(O4)が実機で出ており、テンプレートの集約の書き方では窓すら要らない可能性が高い(§1.1)
- 方式 F を調査のとおりの形(ジョブ ID `gate-g5` のまま、名だけ式で替える)で採ることには反対する。安全が「skipped のジョブの名を GitHub がどう表示するか」という文書に無い振る舞いに載り、その振る舞いがジョブ ID へ戻る方向に変わると、迂回が**黙って**戻る(§1.2)
- 受け入れられるのは、**どの文書外の振る舞いの変化でも、必須チェックが満たされない側(マージが止まる側)へ倒れる形**だけである。G、または F の強化形 F'(集約のジョブ ID も `gate-g5` から外す)を、§4 の条件つきで受け入れる
- 条件を満たす実機の確認(テンプレートの `gate-g5.yml` そのもので行うもの)が揃わないなら、A(止める)を維持し、H の手引きを足す。A は持ち込める範囲が狭いだけで、統制を黙って外さない
- 事前点検の `default-branch` は「外す」のではなく「`gate-g5.yml` の push の契機が既定ブランチを覆っているかを読む」項目へ**置き換える**。単に外すと、旧版の `gate-g5.yml`(`branches: [main]`)を持つリポジトリが素通りする(§3)

## 1. 各方式への反論

### 1.1 方式 E: 採れない

調査の O3・O4 は検証用の最小のワークフローでの観測です。テンプレートの集約は、さらに悪い形をしています(読解)。

- 集約 `gate-g5` は `if: always()` で、`needs` の9ジョブが skipped のとき `contains(needs.*.result, 'failure')` は偽になる
- 続く分岐で `needs.config.outputs.configured != "true"` なら警告を出して `exit 0` する。`config` が skipped なら出力は空で、この分岐に入る
- したがって、集約の `if:` に既定ブランチの条件を足し忘れた E では、既定ブランチでないブランチへの push のたびに、名が `gate-g5` で**結論が success** の check run が先頭のコミットに付く。PR の `gate-g5` が作られる前の窓に依らず、必須チェックが満たされる(推測。調査の §3 の末尾と同じ見立て)
- 集約にも条件を足せば skipped になり、窓の迂回(O4)へ縮むだけで、消えない
- さらに、出荷の集約の後退経路(`g5FromCheckRuns`)は完了の時刻が最も新しい check run を採るため、push の実行を再実行すれば PR の失敗を上書きできる(調査 §5.5)

E は、迂回を「時間の窓」か「常時」のどちらかで必ず作ります。条件を付けても救えません。

### 1.2 方式 F(調査のとおりの形): 反対

F の安全は、O5 で観測した「skipped のジョブの check run の名は、式を評価しないまま式の文字列になる」に依ります。この振る舞いが変わる方向は3つあります。

| GitHub の振る舞いの変化 | 表示される名 | 結果 |
| --- | --- | --- |
| 現状(O5) | 式の文字列 | 迂回なし |
| skipped でも名の式を評価する | `gate-g5-not-default` | 迂回なし |
| 評価できない名をジョブ ID へ戻す | `gate-g5`(ジョブ ID) | **O4 の迂回が戻る** |

3つ目は、未評価の文字列を画面に出すのを「表示の不具合」として直すときに、自然に選ばれうる修正です。戻っても、どの検査も失敗しません。統制が外れたことを、誰も知らないまま運用が続きます。

信頼性を判断軸に置く以上、「いまは安全で、ある変化で黙って危険になる」構造は採れません。根拠水準のマークで開示し、env-check で見張るという緩和は、見張りの周期の間は外れたままであることを認めるものです。故障の向きを変えられるのに、開示で済ませる理由がありません(§2 の F')。

F に対する、その他の指摘です。

- **契約検査の静的な読み取りが届かない**。`g5-aggregate.mjs` は冒頭で「ジョブの if が常に偽になっていないか」を確かめないと明記している。E・F は9ジョブ以上に同じ条件の `if:` を足す。1つのジョブだけ条件の書き方がずれても、どの検査も気づかない(読解)
- **ジョブを足すたびに条件を書き写す保守の義務**が生じる。足し忘れたジョブは、既定ブランチでない push で実際に動く。成功すれば、その実行の結論が success になり、`gh run list --workflow gate-g5 --status success` に当たりうる(下記)
- **実行の結論への依存**。出荷の証跡(`ship-evidence.yml` 125 行)と env-check の項目3(`adoption-trial.mjs` 1849 行)は、`--status success` でワークフローの実行を探す。O8 は「すべてのジョブが skipped の実行は success に当たらない」ことを観測したが、実行の結論の決まり方も文書で確かめていない。env-check の項目3 は `--commit` で絞らないため、既定ブランチでない push の実行が success に数えられると、成果物の無い実行を拾って「不一致」を出す(安全側の誤報。推測)
- **同じコミットを指す複数のブランチ**。既定ブランチの先頭から作っただけのブランチの push は、既定ブランチのコミットに skipped の実行を足す(O8)。出荷の証跡は `--status success --limit 1` で救われるが、救われる理由は上と同じ結論の決まり方である

### 1.3 方式 G: 条件つきで受け入れる

G は、既定ブランチでない push で skipped になるのが呼び出し側のジョブ(名 `default-push`)で、呼ばれる側のジョブ名(`gate-g5`)が展開される前に止まります。名の決まり方がどう変わっても、skipped の check run が `gate-g5` になる経路は思い当たりません(推測)。故障の向きが構造で決まっている点で、F より強いと評価します。

それでも次の欠陥は残ります。

- **出荷の証跡と env-check の探し方が変わる**。`--workflow gate-g5` は呼び出し側の実行に当たらない。改めを漏らすと、出荷の証跡は「gate-g5 の成功した実行が無い」を出し続ける。黙っては外れない(欠落として出る)が、全案件の出荷の証跡が欠落を常に出す状態は、欠落の表示を読み流す習慣を生む
- **強制層のファイルが1つ増える**。呼び出し側のファイルを消す・条件を書き換える変更は、統制の設定の変更として AI維持管理者の承認の対象に足し、`CONTROL_FILES`・`TEMPLATE_WORKFLOWS`・逆向きの追跡へ登録する必要がある
- **呼び出しの意味の差**。呼ばれる側の `github.event_name` は呼び出し側の `push` になり、`github.event.before` も呼び出し側の事象から来る(読解。公式文書で確かめる必要がある)。契約検査の比較の相手が変わらないことを、実機で確かめるまで受け入れない
- **`delegation.yml` の `workflow_run: workflows: [gate-g5]`**。G では既定ブランチの push の実行が `gate-g5` の名で完了しなくなる。委任の判定は `workflow_run.event == 'pull_request'` だけを扱うので影響は無いはずだが、登録の意図を本文に残す

### 1.4 既定ブランチでない push で起動する実行の副作用(E・F・G 共通)

| 場面 | 影響 | 向き |
| --- | --- | --- |
| 実行の数 | すべてのブランチへの push で、ジョブが skipped の実行が1つ増える。F では `delegation.yml` の `workflow_run` も完了のたびに起動する(判定のジョブは skipped) | 一覧の雑音。課金はほぼ無い |
| `delegation.yml` の concurrency | 群は `head_sha` で切られ、GitHub は群の中の**待機中**の実行を新しいもので取り消す。同じ head_sha で、push 由来の無意味な実行が PR 由来の判定し直しを押し出す競合がありうる(推測) | 委任のマージが起きないだけ。安全側だが、生存性の欠陥 |
| 再実行 | skipped の実行を再実行しても skipped のまま(O3)。名も変わらない | 影響なし |
| `workflow_dispatch` | 下記 §1.5 | **危険側** |
| タグの push | `branches` を書かないとタグでも起動し、`github.ref_name` は既定ブランチと同じ名のタグで条件を満たす(調査 §5.7) | `branches: ['**']` と `github.ref == format('refs/heads/{0}', …)` で塞ぐことを条件にする |
| PR の基底が既定ブランチでない | PR の契約検査は `base_ref` と比べるので変わらない。積み重ねた PR のマージによる、既定ブランチでないブランチへの push は、いまも契約検査を走らせない | 現状と同じ |

### 1.5 現状にすでにある、同じ型の経路(範囲外の発見。推測)

`gate-g5.yml` は `workflow_dispatch` を持ちます。書き込みの権限を持つ者が既定ブランチでないブランチで手動起動すると、`pr-rules`(`if: github.event_name == 'pull_request'`)は skipped、集約は `if: always()` で success になり、**名が `gate-g5` の成功した check run がそのブランチの先頭のコミットに付きます**(読解)。PR を開いた直後、PR の `gate-g5` が作られる前に手動起動の結果が付いていれば、O4 と同じ窓でマージできる可能性があります。

これは #362 の方式に依らず、現状の A にもある経路です。

- 本件の結論は、この経路を広げても狭めてもならない。F' を採るなら、名の式を「`pull_request` と既定ブランチへの push だけが `gate-g5`」とし、手動起動も別の名にすれば、同じ変更で塞げる
- 実機で確かめる。確かめられたら、新規の起票ではなく、統制の迂回を扱う既存の open Issue へコメントで足す(申し送りの規則に従う)

### 1.6 契約検査の push の比較(`github.event.before`)の意味

| 案 | 比較の相手 | 意味は変わるか |
| --- | --- | --- |
| A・H | `main` への push の直前の `main` の先頭 | 変わらない |
| D(名の列挙) | 列挙した**既定ブランチでない**ブランチ(例: `develop`)への push でも走り、そのブランチの直前の先頭と比べる | **変わる**。既定ブランチの主系列でない比較が契約検査の結果として残る |
| E・F・F'・G | 既定ブランチへの push の直前の既定ブランチの先頭 | 変わらない(条件が既定ブランチに限るため) |

E・F・F'・G のどれでも、比較の意味は変わりません。ただし G では、呼ばれる側で `github.event.before` が呼び出し側の事象から来ることの確認が要ります(§1.3)。強制の push で直前の先頭が到達できないときの扱い(`git fetch … || true`)は、現状と同じで、本件では変えません。

## 2. 対案 F'(F の強化形)

F の欠陥は「文書に無い振る舞いが一方向に変わると黙って危険になる」ことでした。集約のジョブ ID を `gate-g5` でない名(例: `g5-aggregate`)へ変え、名を式で与えると、どの振る舞いでも `gate-g5` になりません。

| GitHub の振る舞い | 既定ブランチでない push(skipped) | PR・既定ブランチへの push(実行) |
| --- | --- | --- |
| 未評価の式を表示(O5) | 式の文字列 | 式を評価して `gate-g5`(`jobs.<id>.name` の `github` は文書にある。SRC-0730 c2) |
| skipped でも評価 | `gate-g5-not-default` 等 | `gate-g5` |
| ジョブ ID へ戻す | `g5-aggregate` | — |
| 実行するジョブでも名の評価に失敗 | — | `g5-aggregate` か式の文字列。**必須チェックが Pending のまま残り、マージが止まる**(SRC-0573 c3 と同じ向き) |

すべての行で、故障は「マージが止まる」側へ倒れます。代わりに次を改める必要があります。

- `verify-gate-contract.mjs` 797 行(`^\s{2}gate-g5:` でジョブ ID を探す)と `g5-aggregate.mjs` の `G5_AGGREGATE_JOB`。集約の識別をジョブ ID から「名の式が `pull_request` で `gate-g5` を返すジョブ」へ改めるか、ID を新しい名に固定する
- 既存の採用者にとっては契約の変更であり、版の切り替え(`/process-change`)の手引きが要る

F' と G のどちらを採るかは、議長の裁定に委ねます。本委員は、文書の裏付けの差で G をわずかに上に置きますが、部品の増え方では F' が小さいと見ます。どちらでも、§4 の条件は同じです。

## 3. 事前点検の `default-branch` を外すことの危険

調査 §5.3 は「止める項目から外せる」とします。単に外すと、次の危険があります。

- **旧版の `gate-g5.yml` の素通り**。事前点検は、手元のファイルが新しい書き方かを見ていない。旧版の複製(`branches: [main]`)を持ち込んだリポジトリ、案件で `gate-g5.yml` を書き換えたリポジトリは、名が `trunk` でも止まらなくなり、push の契約検査が黙って走らない。いま `default-branch` が塞いでいるのは、名ではなくこの状態である
- **初期化の後の改名の穴は、いまも開いている**。事前点検は持ち込みの時にしか走らない。A のもとで、初期化の後に `main` を `trunk` へ改名したリポジトリは、push の契約検査が黙って止まる。出荷の証跡は「gate-g5 の成功した実行が無い」を欠落として出すので出荷の時点では見えるが、それまでの構成の書き換えは検出されない(読解)。F'・G はこの穴も塞ぐが、A・H を維持するなら別に塞ぐ必要がある
- **既定ブランチを読めないときの読み方**。`preflight.mjs` の `defaultBranch()` は、`origin` の HEAD も手元の `main` も無いと現在のブランチを既定ブランチとみなす。止める理由に使わなくなっても、作業ブランチで点検したときに誤った名を事実として記録する。読めなかったことを記録に残す
- **既定ブランチが出荷の系列でないリポジトリ**。git-flow の型で既定ブランチを `develop` にし、`main` から出荷するリポジトリは、名の制限を外すと持ち込める。本標準は既定ブランチの主系列を適用の開始と出荷の範囲の基準にする(第1章 1.10.1、第5章の出荷の範囲)。そのリポジトリでは、契約検査は `develop` で走り、出荷の範囲は `develop` の先頭までと読まれる。名の制限は、この型を偶然に止めていた

よって、`default-branch` は次の項目へ置き換えることを求めます。

1. 止める: `gate-g5.yml` の push の契機が既定ブランチを覆わない(ファイルを読んで判定する。名では判定しない)
2. 告げる: 既定ブランチが `main` でない。既定ブランチを本標準の主系列(適用の開始・出荷の範囲の基準)として扱うことを、一覧へ載せる
3. 事実: 既定ブランチの読み方(`how`)。読めなかった場合はその旨

加えて、契約検査(PR の実行)で `github.event.repository.default_branch` と push の契機を照らし、初期化の後の改名を検出することを求めます。これは A・H を維持する場合にも要ります。

## 4. 受け入れの条件(F' または G)

| 番号 | 条件 | 理由 |
| --- | --- | --- |
| K-1 | 実機の確認を、**テンプレートの `gate-g5.yml` そのもの**(9ジョブ・`if: always()` の集約・`config` の未設定の分岐)で行う。場面は、既定ブランチでない push の直後の PR とマージの試み、既定ブランチの先頭から作ったブランチの push、既定ブランチと同じ名のタグの push、既定ブランチでないブランチでの手動起動、既定ブランチへの push の契約検査(`--base` の比較)、出荷の証跡の取り込み、env-check の項目3、`delegation.yml` の `workflow_run` | 調査の O1〜O8 は最小のワークフローで、テンプレートの集約の分岐(§1.1)を通っていない |
| K-2 | 文書に無い振る舞いのどの変化でも、必須チェックが満たされない側へ倒れる形にする(F' か G)。素の F は採らない | §1.2 |
| K-3 | 条件は `branches: ['**']` と `github.ref == format('refs/heads/{0}', github.event.repository.default_branch)` で書く。`ref_name` で書かない | タグの経路(§1.4) |
| K-4 | F' では条件を1か所へ集める(`config` だけに付け、他は `needs` で連鎖させる等)。静的な試験で「条件を持つジョブ」と「集約の名の式」を確かめる | ジョブごとの書き写しの漏れを検査が見ない(§1.2) |
| K-5 | 事前点検は §3 の3項目へ置き換える。契約検査で初期化の後の改名を検出する | §3 |
| K-6 | `next.mjs` の `defaultBranch()` を同じ変更で `origin` の HEAD から読む形へ直す | 止める項目を外した途端に表へ出る欠け(調査 §5.6) |
| K-7 | 残る文書外の依存(G の check run の名の組み立て、実行の結論の決まり方)を根拠水準のマークで開示する | ADR-0026 |
| K-8 | ADR-0085 の決定(止める項目に「既定ブランチが `main` でないこと」)を、新しい ADR で置き換える。ADR-0085 の本文は書き換えない。ADR-0085 が退けたのは C(案件ごとに強制層を変える)であり、F'・G はその却下と矛盾しないことを新しい ADR に書く | 採用済み ADR の扱い |
| K-9 | 常駐の規則の核の文言「main は常にリリース可能に保つ」(調査 §5.8)は、本件で直さないなら、`main` 以外のリポジトリで字義どおりに読めない既知の食い違いとして記録する | 「書かれていない」と「直さないと決めた」の区別 |
| K-10 | §1.5 の手動起動の経路を実機で確かめ、F' を採るなら同じ名の式で塞ぐ。G を採るなら既存の open Issue へ足す | 本件の結論が、同じ型の経路を残したまま「迂回は無い」と書かないため |

K-1 と K-2 のどちらかが満たせないなら、A を維持し、H の手引き(改名の手順と、改名できない場合に持ち込めない理由)と、§3 の「初期化の後の改名の検出」だけを入れることを求めます。

## 5. A(止める)と H(手引き)の強さ

- 文書外の振る舞いに一切依らない。迂回を作る経路が増えない
- 持ち込みの時点で止まるので、統制が外れたまま運用が始まることが無い
- 弱さは2つ。1つは、持ち込める組織を絞ること。標準が要求事項としてではなく、準拠テンプレートの実装の都合でリポジトリの名を決めることになる。外部の CI・配備・ミラーが既定ブランチの名に結び付いている組織に、改名の費用を負わせる。もう1つは、初期化の後の改名の穴(§3)を塞いでいないこと
- 判断軸は信頼性であり、持ち込みやすさではない。したがって、F'・G が K-1 の確認を通らない限り、A のほうが信頼できる。逆に、K-1・K-2 を満たした F'・G は、A の2つ目の弱さ(改名の穴)も塞ぐので、信頼性でも A を上回る

## 6. 採らない案と理由

| 案 | 理由 |
| --- | --- |
| B(`branches` に式) | 不正なワークフローになり、すべての push で失敗の実行が出る(O1) |
| C(初期化が `branches:` を書き換える) | 案件ごとに強制層の定義が違う。ADR-0085 で退けた理由がそのまま当たる。改名のたびに強制層の変更が要る |
| D(名の列挙) | 列挙の外を持ち込めない。列挙した既定ブランチでないブランチで、比較の意味が変わる(§1.6)。`develop` は PR の元にもなるため、`if:` で絞ると E と同じ迂回が戻る |
| E | 迂回を窓か常時で作る(§1.1) |
| F(調査のとおりの形) | 文書外の振る舞いの変化で、迂回が黙って戻る(§1.2)。F' で置き換える |
| 事前点検の `default-branch` を単に外す | 旧版の `gate-g5.yml` が素通りする(§3) |
| 文書外の依存を根拠水準のマークと env-check の見張りだけで受ける | 故障の向きを構造で変えられるのに、見張りの周期の間の外れを受け入れることになる |
| §1.5 の手動起動の経路を、本件のために新規に起票する | 実行で確かめていない。確かめた後、既存の open Issue へ足す |
