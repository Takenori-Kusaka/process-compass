# #362 会議体 委員1(起案)

- 立場: 起案。`survey.md` の方式 A〜H と観測 O1〜O8 を材料に、採る方式を1つに絞って示す
- 判断軸: 信頼性。とくに「統制が黙って外れる経路を作らないこと」。変更の量は採否の理由にしない(CLAUDE.md のコアポリシー)
- 読んだもの: `survey.md`、`template/.github/workflows/gate-g5.yml`(契機・`contract`・集約)、`template/scripts/gate/preflight.mjs`(`defaultBranch`・`default-branch`・`TEMPLATE_WORKFLOWS`)、`template/.github/workflows/ship-evidence.yml`(125 行付近)、`delegation.mjs` の条件3、`aggregate-evidence.mjs` の `g5FromCheckRuns`、`next.mjs` の `defaultBranch`、ADR-0085 の事実の表と採らなかった案の表

## 1. 採る方式: G(再利用のワークフロー)を主とし、§5.7 のタグの塞ぎを組み込む

### 1.1 形

- `gate-g5.yml` から `on.push` を外し、`on.workflow_call` を足す。`pull_request` と `workflow_dispatch` は残す
- 新しい強制層のワークフロー(仮称 `gate-g5-push.yml`)を置く
  - 契機は `on.push.branches: ['**']`。ブランチに限り、タグの push では起動しない
  - ジョブは1つ。ジョブ ID と名はどちらも `gate-g5` と異なる固定の文字列(仮称 `default-push`)。式の名を使わない
  - 条件は `if: github.ref == format('refs/heads/{0}', github.event.repository.default_branch)`。`ref_name` を使わない(タグと区別しないため。SRC-0730 c3)
  - `uses: ./.github/workflows/gate-g5.yml`。`permissions` は `gate-g5.yml` の現在の値(`contents: read`・`pull-requests: write`・`issues: read`)を呼び出し側で与える
- `gate-g5.yml` の中の `if: github.event_name == 'push'` の分岐(`contract` の `github.event.before` との比較)は変えない。呼ばれたワークフローの `github` コンテキストは呼び出し側の事象を指すため、そのまま働くはずである(§4 の実機で確かめる)

### 1.2 理由

方式を「必須チェック `gate-g5` の名を持つ check run が、どの経路で作られうるか」で比べました。

| 案 | 既定ブランチでない push で `gate-g5` の名の check run が生じるか | その保証が何に依るか |
| --- | --- | --- |
| E | 生じる(skipped)。O4 で失敗する変更がマージされた | — |
| F | 生じない(O6) | 集約の名の式の評価。skipped のジョブの名を式の文字列のまま出す振る舞いは文書に無い。ジョブ ID へ戻す振る舞いに変われば、O4 の迂回が黙って戻る |
| G | 生じない(O7) | ファイルの構造。push を契機とするワークフローに、名が `gate-g5` のジョブが1つも無い。呼ばれた側の check run は `呼び出し側の名 / 呼ばれた側の名` になる |

F と G は、どちらも O4 の迂回を実機で塞ぎました。差は、塞いでいる理由の頑健さです。F は、文書に無い表示の振る舞い(skipped のジョブの名の扱い)に統制の成否を預けます。その振る舞いが変われば、誰も気付かないまま必須チェックが効かなくなります。これはまさに「統制が黙って外れる経路」です。G は、push のワークフローの定義に `gate-g5` という名の文字列が存在しないことに依ります。表示の振る舞いが変わっても、無い名は生じません。

G は、ほかの面でも F より信頼性が高いと判断します。

- 既定ブランチの名を実行時に読むため、持ち込みの後に既定ブランチを改名しても追随する(C は改名のたびに強制層の書き換えが要る)
- `gate-g5.yml` の9つの検査ジョブに既定ブランチの条件を足さずに済む。F は全ジョブへ条件を足す必要があり、1つでも足し忘れると既定ブランチでない push で検査が走り、`github.event.before` との比較が既定ブランチの履歴でない比較になる
- 委任の条件3(`delegation.mjs` は名の完全一致)と出荷の集約の後退経路(`g5FromCheckRuns` は `check_name=gate-g5`)は、名が `default-push / gate-g5` の check run を拾わない。§5.5 の2つの懸念がどちらも生じない

G の代価は、強制層のファイルが1つ増えることと、出荷の証跡の取り込み経路を変えることです。代価は採否の理由にしませんが、増えたファイルが**黙って消える**経路は新たに生じるので、§3.4 で塞ぎます。

### 1.3 重へ上げるかの判定

G は、テンプレートの1つの定義をすべての案件で同じに使います。強制層のワークフローを案件ごとに変える経路は生じません(survey §6)。新しい義務も採用者に課しません(既定ブランチを `main` にする義務が、逆に無くなる)。軽のまま進めてよいと考えます。

## 2. 事前点検の `default-branch`: 止める項目から外し、事実の記録に残す

- 止める項目 `default-branch` を外す。G では既定ブランチの名に依らず push の契約検査が走るため、名が `main` でないことは統制が外れる状態ではなくなる
- 既定ブランチの名と読み方(`facts.defaultBranch`。`origin` の HEAD・手元の `main`・現在のブランチ)は、事実として点検の出力に残す。読み方が「現在のブランチ」だった場合は、その旨を告げる(読み違いの可能性を読み手が判断できるように)
- 代わりに、止める項目 `gate-g5-push-workflow` を足す。`gate-g5-push.yml` が無ければ止める。理由は `gate-g5-workflow` と同じで、push の契約検査を走らせるのはこのファイル自身であり、欠けは契約検査では見つからないためである
- 「告げる」へ格下げして残す案は採らない。止める理由が無くなった事実を告げ続けると、読み手は対処の要る事項と受け取る

## 3. 付随の修正

### 3.1 `next.mjs` の既定ブランチ(§5.6): 同じ変更で直す

- `/pit` の `defaultBranch()` を、`preflight.mjs` の `defaultBranch` と同じ読み方(`origin` の HEAD を先に読む)へ直す。可能なら同じ関数を共有し、読み方の二重化を無くす
- 事前点検を外すと、`trunk` などのリポジトリが初めて正規の経路で入ってくる。そこで `/pit` が済んだタスクを数えないのは、次の一手の提示を誤らせる欠陥である。切り離して後回しにすると、外した直後から欠陥のある状態で動く。だから同じ変更に含める
- `adoption-trial.mjs` の後退(`main`・`master`)は、`gh repo view` を先に読むため実害は小さい。ただし同じ読み方へ揃えるかを実装で判断し、揃えない場合は理由を残す

### 3.2 タグの push(§5.7): 方式の一部として塞ぐ

- §1.1 の `branches: ['**']` と `github.ref == format('refs/heads/{0}', …)` の2つで塞ぐ。片方だけでは足りないとは限らないが、`branches` は起動そのものを、`if:` は既定ブランチへの限定を担い、役割が違うので両方を置く
- 既定ブランチと同じ名のタグの push で起動しないことを実機で確かめる(§4.2)

### 3.3 常駐の規則の「main は常にリリース可能に保つ」(§5.8): 本件では書き換えず、扱いを明記して既存の Issue へ寄せる

- 核の文言の変更は標準の規定の書き換えに当たる(ADR-0084 決定2)。本件(軽)の範囲で文言を変えない
- ただし「書かれていない」と「課さないと決めた」を区別するため、本件の裁定に「既定ブランチが `main` でない案件では、核の文言の `main` は既定ブランチを指すものと読む。文言の改めは別に扱う」と記録する案を出す。この読み替えを標準の本文へ置くかは、議長の裁定に委ねる
- 後継は新規に起票せず、常駐の規則を扱う既存の open Issue へコメントで足す(メモリの「後継は既存の Issue へ寄せる」)

### 3.4 G に伴って必ず改めるもの

- 出荷の証跡(`ship-evidence.yml` 125 行): 探す先を `gate-g5-push.yml` の成功した実行に改める。`workflow_dispatch` で `gate-g5.yml` を直接走らせた実行も今は当たるので、後退として `gate-g5` も探す。順は push のワークフロー → `gate-g5` とする
- 契約検査(`verify-gate-contract.mjs`・`g5-aggregate.mjs`): `gate-g5-push.yml` の形を検査に足す。契機が `branches: ['**']` でタグを含まないこと、ジョブが1つで名と ID が `gate-g5` でないこと、条件が `refs/heads/` の形であること、`uses` が `./.github/workflows/gate-g5.yml` を指すこと
- 契約検査: `gate-g5.yml` に `on.push` が無いことを検査する。戻れば、既定ブランチの push の検査が二重になり、push 由来の `gate-g5` の名の check run も復活する
- 一覧と統制の設定: `TEMPLATE_WORKFLOWS`、CODEOWNERS の対象(`.github/workflows/` は既に `@ai-maintainer`)、統制の設定の変更の承認(ADR-0115)の対象、逆向きの追跡の登録、IMPL-0238 の降ろし先へ新しいファイルを加える
- 標準の本文: 第4章 IMPL-0238 の「`gate-g5.yml` が…既定ブランチへの push を契機に」を、新しいファイルからの呼び出しの形へ改める。第5章 `template-repository.md` の事前点検の表から「既定ブランチが `main` でない」を外し、本文末尾の「push の契機を案件ごとに変える案は採りませんでした」は維持する(G でも案件ごとに変えないため)。EV-0167 の対象から「既定ブランチが `main` でないリポジトリを止めること」を外す
- ADR: ADR-0085 は採用済みのため書き換えない。事前点検の止める項目の変更と push の契機の構造の変更を、新しい ADR で一部置き換えとして記録する

## 4. 試験として確かめるべきこと

### 4.1 静的な試験(`npm run check` と `template/` の試験)

- `test-adoption.mjs`: 「既定ブランチが main でなければ止める」を、「`trunk` で止めない」「`gate-g5-push.yml` が無ければ止める」の2つへ置き換える
- `test-adoption.mjs` の `TEMPLATE_WORKFLOWS` とテンプレートの一覧の一致の試験が、新しいファイルで通ること
- 契約検査の試験: §3.4 の各検査について、正の例と、崩した例(`gate-g5.yml` に `push` を戻す、呼び出し側のジョブ名を `gate-g5` にする、`branches` を外す、条件を `ref_name` にする、`uses` の先を変える)がそれぞれ落ちること
- テンプレートのすべてのワークフローを走査し、`gate-g5.yml` の集約のほかに、名または ID が `gate-g5` のジョブが無いことの試験。名の衝突による迂回を、ファイルを増やしても防ぐため
- `next.mjs`: 既定ブランチが `trunk` で `origin/HEAD` を持つ一時のリポジトリで、済んだタスクを数えること

### 4.2 実機(既定ブランチ `trunk` の一時のリポジトリ。**テンプレートの実物の `gate-g5.yml` で**)

survey の実機は検証用の最小のワークフローでした。実物の9ジョブと権限で次を確かめる必要があります。

| 番号 | 確かめること | 期待 |
| --- | --- | --- |
| T1 | 機能ブランチへ push し、PR を開いて直ちにマージを試みる(PR の検査が落ちる変更) | 拒否される。push の実行の check run は `default-push`(skipped)だけ |
| T2 | 機能ブランチへの push の後、push の実行を再実行してからマージを試みる | 拒否される |
| T3 | `trunk` へ、変化点の記録を経ない構成の書き換えを push する | `default-push / gate-contract` が失敗する(`github.event.before` との比較が呼ばれた側で働く) |
| T4 | `trunk` への通常の push | `default-push / gate-g5` が success。成果物 license-scan・test-results が呼び出し側の実行に付く |
| T5 | 出荷の証跡のワークフローを T4 のコミットで走らせる | 新しい探し方で T4 の実行が当たり、2つの成果物を取り込む |
| T6 | 名が `trunk` のタグを push する | push のワークフローが起動しない |
| T7 | 委任のマージの条件3と出荷の集約の後退経路を、T1 の PR で走らせる | push の実行の check run を拾わない |
| T8 | 持ち込みの後に既定ブランチを `trunk` から `develop` へ改名し、T1・T3 を繰り返す | 強制層を書き換えずに追随する |
| T9 | 既定ブランチが `main` のリポジトリで T1・T3・T4・T5 | 回帰が無い |
| T10 | 旧来のブランチ保護(ルールセットでない)で T1 | 拒否される(survey §5.2 の推測の確認) |

- 実機の結果で `ci-gates.md` 922〜923 行の「既定ブランチへの push を契機とする契約検査は、実際の GitHub 上で実行していない」を改められるなら改める
- 実環境の確認(env-check)に、`gate-g5-push.yml` の直近の既定ブランチの実行が存在することの確認を足すかを、実装で判断する(push の契約検査が走っていないことを、出荷より前に知るため)

## 5. 根拠水準のマークが要る箇所

| 箇所 | 実証を欠く前提 | 解く条件 |
| --- | --- | --- |
| G の安全性の記述(第5章・新しい ADR) | 呼ばれた側の check run の名が `呼び出し側 / 呼ばれた側` になり、skipped の呼び出し側のジョブが呼び出し側の名で残ること。観測は O7 の1例だけ | T1・T2 の通過と、env-check または試行での継続の観測 |
| 呼ばれた側の `github.event.before` | 呼ばれた側の `github` コンテキストが呼び出し側の push の事象を指すこと | T3 |
| 出荷の証跡の取り込み | 呼ばれた側で上げた成果物を、呼び出し側の実行の ID で取れること | T5 |
| タグの塞ぎ | `branches: ['**']` でタグの push が起動しないこと(SRC-0701 からの読解) | T6 |
| 旧来のブランチ保護 | ルールセットと同じ評価になること(survey §5.2 の推測) | T10。確かめない場合は、テンプレートの手段がルールセットである旨を併記して範囲を限る |

実機で T1〜T10 を確かめた項目は、その時点の観測として「YYYY-MM-DD 時点」を添え、GitHub の振る舞いの変更に備えて見直しの時期を置きます(マークを外すのではなく、見直しの時期を持つ形にする)。

## 6. 採らない案と理由

| 案 | 採らない理由 |
| --- | --- |
| A 現状 | Issue の問題(`main` でないリポジトリへ持ち込めない)が残る。改名を強いることは、既存のリポジトリの運用・外部の参照を壊す負担を採用者へ課す |
| B 式で書く | 不正なワークフローになり、どのブランチへの push でも失敗の実行が出る(O1) |
| C 構成から生成 | 強制層のワークフローを案件ごとに変える経路を作る(ADR-0085 の採らなかった案の理由と同じ)。既定ブランチの改名のたびに強制層の変更が要り、改め忘れると push の検査が黙って止まる |
| D 名の列挙 | 列挙の外の名を持ち込めない。列挙の中の既定ブランチでないブランチ(例: `develop`)への push で契約検査が走り、既定ブランチの履歴でない比較になる |
| E 絞りを外し `if:` で絞る | 必須チェックを迂回して、失敗する変更をマージできた(O4)。委任のマージが常に止まり、出荷の集約の後退経路が skipped を採りうる(§5.5) |
| F E + 集約の名を替える | 迂回は塞げた(O6)が、その成否が文書に無い表示の振る舞いに依る。振る舞いの変更で迂回が黙って戻る。G で同じ目的を構造で果たせる以上、表示の振る舞いに統制を預ける理由は無い。ただし T1〜T10 で G が成り立たないと分かった場合の次善として記録に残す |
| H 改名を求め続け、手引きだけ書く | A と同じく Issue の問題が残る |
| 事前点検の `default-branch` を「告げる」へ格下げ | 止める理由が無くなった事項を告げ続けると、対処の要る事項と誤読される(§2) |
| 常駐の規則の核の文言を本件で改める | 標準の規定の書き換えに当たり(ADR-0084 決定2)、軽の範囲を超える(§3.3) |
