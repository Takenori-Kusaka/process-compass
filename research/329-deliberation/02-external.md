## 0. 骨格(10 行)

1. GitHub の私的リポジトリでは、**環境の必須レビュアーと待機タイマーは Free・Pro・Team のいずれでも使えない**(上位の Enterprise 側のみ)【原 T329-01】。G-8 の成立条件「実行環境の承認操作」(論点 1)を満たせるのは Enterprise の私的リポジトリと、公開リポジトリだけである
2. 環境そのもの(配備ブランチ・タグの制限)は Pro・Team の私的リポジトリで使える。Free の私的リポジトリでは環境を設定できない【原 T329-01・02】
3. ルールセットとブランチ保護は、公開は全プラン、私的は Pro・Team・Enterprise Cloud で使える。Free の私的リポジトリは両方とも使えない【原 T329-04・05】。ルールセットの Evaluate モードと組織単位の規則は Enterprise 側【抜 SRC-0343。T329-04 の頁では Evaluate への言及が無かった】
4. 環境の秘密情報は、Free の私的リポジトリでは使えない【原 T329-01】。論点 2(資格情報を起動元のブランチで書き換えられるファイルの中だけに置かない)の代替が「環境の秘密情報」だと、Free の私的では取れない。Pro・Team では取れる(必須レビュアー無しで)
5. `workflow_dispatch` は任意のブランチ・タグへ向けて起動でき(API・CLI)、実行の `GITHUB_REF` は起動先の ref になる【原 T329-06】。既定では書き込み権限を持つ全員が起動できる【原 T329-07】。環境の配備ブランチ規則は `GITHUB_REF` に照合される【抜 293】ので、Pro・Team の私的でも**起動元ブランチの制限は取れる**(必須レビュアー無しで)。ただし公式がこの組合せを明記してはいない(推論)
6. 規格・指針は、防止型の統制が技術的に取れないとき、**代替の統制を認めるが、免除とはしない**。SOC 2 CC5.1 は T1+代替統制【抜 SRC-0538】、PCI DSS は証明つきの代替統制【原 352】、SLSA は水準を分けて主張できる範囲だけを主張させる【抜】。検出型を単独で十分とする明文は、確かめた範囲に無い【二 T329-13】
7. SLSA v1.2 Source は、統制の**継続性**(履歴の途中で途切れたら新しい版から数え直す)と、統制が働いている**証拠の同時生成**を求める【原 T329-09】。判定記録の置き場の履歴を規則で止められない構成は、SLSA の言葉では「継続性を主張できない」状態に当たる
8. DORA は、配備の承認を**同僚のレビュー(作成者以外の承認)と自動化**で満たし、外部の承認組織は変更失敗率を下げなかったとする【原 T329-10】。本標準の G-8 を「人の承認操作」に絞らず、作成者以外の承認が記録に残ることを核にする選択を支える
9. OpenSSF Scorecard は、管理者権限の無いトークンで見えない設定を**評価から外す**(「無視してよい」)。単独メンテナのレビューは「実施不能な場合がある」と明記する【原 T329-11】。見えないことを合格にも不合格にもせず、開示する形である
10. 手動の起動の統制として公式が示す手段は、環境の保護規則(必須レビュアー・配備ブランチ)、CODEOWNERS による `.github/workflows` の変更承認、Actions policies の actor・event 規則【原 T329-08・07】。PR を経ない起動を防ぐ専用の機能は無い

## 1. GitHub の機能のプラン別の提供(2026-11-15 時点、公式本文)

論点 1・2 の前提になる事実。公式文書の文言を優先し、要約ツールの出力が原文と食い違った箇所は原文で直した(ルールセット)。

読み取れなかった点:
- 「Free の私的」の環境が使えないことは、文書の文言(Free は公開のみ)からの読みで、設定画面では確かめていない
- 「管理者による保護規則の迂回を許す」設定の提供範囲の文言(T329-01 quote 4)は、Free・Pro・Team の私的でどちら向きに効くかを文脈から確定できなかった【未】。迂回を禁じられるかは Enterprise 側かどうかを、設定画面で確かめる必要がある
- 組織の所有か個人の所有かで、Team の PR 必須レビュー(`Required pull request reviewers`)の提供が変わるか。プラン比較の頁は私的リポジトリで Pro・Team に「ブランチ保護」を載せる【原】が、環境の必須レビュアーは載せない

含意(選択肢への):
- G-8 の成立条件を「環境の必須レビュアーによる承認操作」に固定すると、私的リポジトリで Enterprise 以外は構造的に満たせない。公開リポジトリは満たせる。これは**ツールの限界であって、採用者の怠慢ではない**。条件を機能名で書く案(O-機能)と、満たすべき性質(作成者以外が配備の前に承認し、その事実が改ざんされにくい場所に残る)で書く案(O-性質)の差が出る
- 性質で書く場合、機能が無いプランでは、承認の記録を判定記録(例: PR の承認 + 実行記録)へ広げる案が出る。ただし判定記録の置き場の履歴を止める手段(ルールセット)も Free の私的には無い(論点は 4 節)
- 「Pro・Team では秘密情報と配備ブランチの制限は取れるが、承認は取れない」という中間のプランがある。**プラン別の階段**を条項に持ち込むか、性質だけを書くか、の選択が要る

## 2. 論点 1: G-8 の成立条件が機能に依ること

### 2.1 世の中の実務

- 承認の主体: DORA は「作成者以外が承認する」ことを職務の分離の核とし、ピアレビューで満たせるとする。承認は開発基盤に記録する【原 T329-10】。承認を**実行環境の操作**に限る実務は、規格には見当たらない。GitHub の機能が特殊な形で、規格が求めるのは「独立した承認が記録されること」である
- 規格の型(352 の T1〜T4 を流用)。SLSA は Level を分けて、満たせない者には低い水準だけを主張させる(T3/T4)。SOC 2 CC5.1 は代替統制を選べとする(T1)。PCI DSS は制約の証明と代替統制と毎年の再審査を条件とする(T2)【抜 352】
- SSDF v1.1 は人数や承認の主体を条項にせず、環境の分離と保護(PO.5)、コードの最小権限での保護(PS.1.1)を求める【抜 SRC-0718、原 T329-12】。実装手段は組織が選ぶ
- NIST SP 800-53 の CM-5(変更へのアクセス制限)・AC-5(職務の分離)の原文は、公式カタログを開けず【未】。352 では二次の写し止まり

### 2.2 本標準が取り得る選択肢への含意(列挙。採否は書かない)

| 案 | 内容 | 先例 | 弱点 |
|---|---|---|---|
| A | 成立条件を性質で書き、手段は例示にとどめる(環境の必須レビュアー、PR の承認の記録、外部の承認システム) | SSDF は手段を指定しない。DORA はピアレビュー | 「性質が満たされたか」を機械で閉じにくい(manual か adopter になる) |
| B | 機能のあるプランでは環境の承認、無いプランでは判定記録(PR 承認+実行記録)を成立条件とする、2段 | SLSA の水準分け(T3)。PCI の代替統制(T2) | プラン名を条項に入れると GitHub の改定で陳腐化する。実行で確かめにくい |
| C | 環境の承認を維持し、満たせない構成は「未達」として開示する(現行の延長) | Scorecard の「見えない設定は評価から外し開示」 | 私的・非 Enterprise の大多数が恒常的に未達になり、未達の表示が意味を失う |

「1名体制でも適合を主張できる」と明示した規格の先例は確かめた範囲に無い(352 の記録)。一方、実行できない場合の努力義務や代替統制を書く T1・T2 は先例が複数ある。

## 3. 論点 2: 資格情報を、起動元のブランチで書き換えられるファイルの中だけに置かない

### 3.1 世の中の実務

- 公式の推奨: 環境の秘密情報は、必須レビュアーの承認までジョブから読めない【原 T329-08】。ただしこの保護はレビュアーがあって初めて効く。レビュアーが無い環境でも、環境の秘密情報は**配備ブランチの制限**と組み合わせられ、起動元のブランチが許可外ならジョブは環境へ入れない【抜 293・原 T329-01】
- リポジトリの秘密情報は、書き込み権限を持つ全員が読める【原 T329-08 "Any user with write access ... has read access to all secrets"】。ワークフローの書き換えで取り出せる。したがって「ファイルの中に資格情報を置かない」と同時に、「リポジトリ単位の秘密情報に置いて済ませる」は代替にならない
- 外部の秘密情報の置き場(クラウドの鍵管理・OIDC の信頼条件に ref・環境を含める)は、GitHub の文書の外で、今回は調べていない【未】。OIDC の `sub` に環境や ref を含める方式は一般に知られるが、公式文書を取得していないため、この調査では事実として扱わない
- Scorecard の Token-Permissions は、ワークフローの権限を既定で読み取りに絞り、書き込みをジョブ単位で宣言することを最高点とする【原 T329-11】。「起動元で書き換えられる」を前提に、権限を縮める方向の統制である

### 3.2 含意

- プラン別の取りうる代替: Free の私的 = 環境の秘密情報も取れない(外部の置き場しかない)。Pro・Team の私的 = 環境の秘密情報+配備ブランチの制限(承認なし)。Enterprise 私的と公開 = 必須レビュアーまで取れる
- 「未達として開示」(現行の扱い)が足りるかは、規格の型で言えば T4 に近い(主張できない水準を開示)。SLSA は主張できる水準だけを主張させる形で、未達の列挙だけでは終えない。**未達の開示に加えて、代替の最低限(例: 資格情報の権限を縮める、短命にする)を課すか**が選択肢になる
- OIDC など外部の置き場を条項にするなら、採用者への新しい義務に当たる(重の審議の対象)

## 4. 論点 3(と #352 から寄せられた置き場の履歴): PR を経ない起動と、ブランチ上のワークフローの書き換え

### 4.1 手動の起動の実態

- `workflow_dispatch` は、ワークフローのファイルが**既定ブランチに在る**ときだけ起動の入口が出る【原 T329-06】。ただし任意のブランチ・タグへ向けて起動でき、`GITHUB_REF` はその ref になる【原 T329-06】。ブランチ上で書き換えたワークフローを、そのブランチへ向けて起動できるという報告がコミュニティにある【二、293 が引く https://github.com/orgs/community/discussions/49688 ほか】。公式がこの経路を危険として明記した箇所は、今回取得した範囲に無い【未】(Secure use の頁は workflow_dispatch に触れない【原 T329-08】)
- 起動の資格: 既定で書き込み権限を持つ全員【原 T329-07】。actor 規則で人・ロール・App・チームに絞れ、event 規則で `workflow_dispatch` ごと止められる【原 T329-07】。プランの条件は頁に無い【未】
- 公式が示す緩和: 環境の配備ブランチ規則(`GITHUB_REF` 照合。ブランチ・タグの選択、保護ブランチのみ、名前の型)【抜 293、原 T329-01】、環境の必須レビュアー【原 T329-08】、CODEOWNERS で `.github/workflows` の変更を承認制にする【原 T329-08】
- 「保護ブランチのみ」の意味はブランチ保護規則の有無で、ルールセットが含まれるかは文書に無い【抜 293】
- ブランチ保護・ルールセットは、**ブランチへの push と PR のマージ**を制御する。ワークフローの起動そのものは制御しない。起動を止めるのは actor・event 規則と環境の規則である

### 4.2 業界の統制の型(今回の確認の範囲)

| 統制 | 型 | 取れるプラン | 出典 |
|---|---|---|---|
| 環境の配備ブランチ制限 | 防止 | 公開・Pro・Team・Enterprise | T329-01 |
| 環境の必須レビュアー(自己承認禁止) | 防止 | 公開・Enterprise 私的 | T329-01 |
| CODEOWNERS による workflow の変更承認 | 防止(PR 経由の変更のみ) | ブランチ保護と併用。必須レビューが要る | T329-08 |
| actor・event 規則 | 防止 | 【未】 | T329-07 |
| 配備の実行記録の突き合わせ(誰が・どの ref で・何を) | 検出 | 全プラン(実行記録は取得可能) | 【二】 |
| 通知(管理者・独立した機能への) | 検出 | 全プラン | 【二 T329-13】 |

### 4.3 判定記録の置き場の履歴を止められない構成(#352 の寄せ)

- 先例の骨格: SLSA v1.2 は、統制の継続性を履歴の全体で要求し、途切れたら**新しい版から数え直す**。統制が働いている証拠は、更新と同時に生成することを要求する【原 T329-09】。置き場の履歴を規則で止めない構成は、継続性を満たさない。SLSA はそれを「その統制を主張しない」で処理し、満たした範囲の水準だけを主張させる
- 352 の措置案(要約値を、書き換え権限者の異なる別の置き場に実行ごとに追記して突き合わせる)は、検出型の補完に当たる。SOC 2 の小さな体制の実務で言われる「検出型+記録+残余リスクの受容」と型は同じ【二 T329-13】。ただし、1名体制では2つの置き場の権限者が同一人物になる。**SOC 2 の解説も、1名では独立性を装えない前提で、代替統制は残余リスクの文書化とセットにする**【二】
- 「検出型だけで防止型の代わりになるか」について、明文で認める規格・指針は確かめた範囲に無い【二 T329-13】。監査人が予防の関門を併置して期待するという解説がある一方、実行できない場合の代替統制は CC5.1 が認める【抜】。つまり**代替としては認めるが、適合の水準を同じとはしない**、が最も近い読み

### 4.4 含意(選択肢)

- 手動の起動と PR 経由でない変更を、risk-catalog の「配備の自動化の不備」に明記して受け止める(案 X)。受け止める手段は、(a) 防止: 環境の配備ブランチ制限と起動者の限定、(b) 検出: 実行記録の突き合わせ、(c) 開示: 取れない構成の未達の表示
- 防止型が取れないプラン(Free の私的)では (b)(c) だけになる。(a) の取れるプラン(Pro・Team の私的)では、承認なしの配備ブランチ制限だけでも、**任意ブランチからの起動は塞げる**(推論。公式の明記は無い)
- 「ブランチ上のワークフローの書き換え」は、書き込み権限者であれば可能で、環境の秘密情報と配備ブランチ制限があれば秘密情報は読めない。リポジトリの秘密情報だけに頼る構成は破れる【原 T329-08】

## 6. 会議体への問い(裁定ではない)

1. G-8 の成立条件は、機能(環境の承認操作)で書くか、性質(作成者以外の承認が配備の前に改ざんされにくい場所へ残る)で書くか。性質で書くなら、機械で閉じない部分を manual・adopter で開示するか
2. プラン別の階段(取れる統制が段で違う)を、条項に持つか、持たずに性質と未達の開示だけにするか
3. 未達を開示するだけで足りるか。主張できない水準(SLSA の T4)を設けるか、代替の最低限(権限の縮小、配備ブランチ制限、実行記録の突き合わせ)を課すか。課すなら採用者への新しい義務なので重の審議である
4. 1名の体制の扱い(352 の弱点と同じ)。独立性を装わない前提で、残余リスクの受容の記録を代替とするか
5. 手動の起動を risk-catalog に載せる場合、受け止めを防止(配備ブランチ制限)と検出(実行記録)のどちらまで書くか。どちらも公式機能の推論部分を含む
