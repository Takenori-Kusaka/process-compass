# #329 品質監査の委員の意見書

立場: 内部監査・第三者の審査の目。他の委員の意見書は読んでいない。読んだもの: 01-internal.md、02-external.md、および原文として `gate-criteria.md` の 160-181・1805-1860、`qms-document-control.md` の 36-42、`overview.md` の 167-170・558・646-648・696-719、`ci-gates.md` の 954-978、ADR-0133 全文、ADR-0083 の区分の記述、`risk-catalog.md:101`。template は読んでいない(01-internal の実行記録に頼る。頼った所は「未確認」と書く)。

## 0. 先に結論(監査の目で見た3点)

1. 区分の割れは、**適合の主張の成否は壊さない**。`overview.md:646-648` のとおり、未達・記録の欠落・列挙に無い離脱は、適合の主張と、逸脱を伴う適合の主張のどちらも同じように妨げる。壊れるのは主張の成否ではなく、**何を数えて何を表示するか**(件数の再現性)と、読み手の理解である。一番重い欠陥は「未達」と「離脱」の差ではなく、`ci-gates.md:956` の**空白**(区分が無い=表示の根拠が無い)である
2. G-8 は、現行の第4章では**決断の記録**であって配備を止める門ではない。この事実が、保証の開示や risk-catalog から読み取れない。表示と実態の食い違いの本丸はここである
3. 配備の統制は、template に配備のワークフローが無い(IMPL-0237 `plan=adopter`)ため、**誰が・いつ・何を根拠に配備したか**を標準側の証拠から辿れない。監査人が得られるのは採用者の自己申告と、ホスティング側の実行記録(採用者が保存していれば)だけである

## 2. 論点1: G-8 の成立条件

### (1) 監査の証拠の有無と弱さ

- **ある証拠**: G-8 の判定記録(テンプレ4。層1 の版、出荷判定者の異議、上申の欄)。集約が欄の有無を検査する(01-internal 2.3 の `aggregate-evidence.mjs`、`test-aggregate-records` 135 件一致。私は再実行していない)。記名者の帰属は、ADR-0109 決定3 により「帰属を裏づけた G-7・G-8 の判定記録の記名者」で判定する。つまり**名簿の人であること、基底ブランチへ入った時点、署名コミットか PR の記録**は、ホスティングの記録で第三者が辿れる
- **弱い所**:
  1. 決断の記録が**配備より前にあること**を示す証拠が、配備の側に無い。配備のワークフローが標準の外だからである。判定記録の時刻と配備の実行の時刻を突き合わせるのは、採用者次第
  2. 判定記録が指す**対象のコミットと、実際に配備された成果物の一致**を、標準の機構は確かめない(確かめる機構を私は見つけていない。01-internal の `ship-evidence` は出荷の証跡であって配備の実行ではない。未確認)
  3. 3名未満の体制での出荷判定者 × 事業決裁者の兼務は、記録の記名者が実質1人になる。これは既に列挙に無い離脱として表示される(`overview.md:702`)ので、表示は一貫している。弱いのは証拠ではなく、独立性そのもの
- Environment の承認ログは、使えるプランでは**プラットフォームが帰属を保証した強い証拠**になる(承認者・時刻・対象の ref)。判定記録の記名より、改ざんされにくい。これを成立条件から外すと、使える採用者から強い証拠が減る。したがって「成立条件から外す」と「補助の証拠として推奨する」は両立させるべきである

### (2) 支持する案と理由

**1-A + 1-B の核**(qms L41 を G-7 の行にならって直し、`ci-gates.md:956` の空白を削る。Environment の必須レビュアは「採用者が足してよい補助の証拠」と位置づける)に、次の2点を足す。

- a. 判定記録と Environment の承認が**食い違う場合の優先順位**を書く: 判定記録が正本。判定記録が無い配備を Environment の承認だけで通した場合は、記録の欠落として扱う(承認操作だけでは記録にならない、という既存の文を残す根拠になる)。理由: 優先順位を書かないと、監査人は二つの証拠のどちらを信じるかを採用者に尋ねるしかなくなる
- b. **G-8 は決断の記録であり、配備を止める門ではない**と、第4章の G-8 の節に1文で書く(M-1・M-3 の根)。理由: 事実を書くだけで新しい義務ではない。書かないと、G-8 を「ゲート」と呼ぶ語感が、止める統制があるという誤認を生む。表示と実態の一致に必要

1-D(配備が判定記録の通過を読んでから動く形)は、**未達の計画つきで本文に先行して置く**ことを支持する。理由: 監査人が最も欲しい証拠(配備の前に決裁があった)を機械で与える唯一の案だから。ただし新しい義務(重)であり、template が及ぶ。ここでの裁定は「方向として採る」か「採らないと決めて理由を残す」かの二択。後者なら、「G-8 は配備の前提を機械で確かめない」と明記する。どちらも「書かれていない」よりよい

### (3) 採るべきでない案と理由

- **1-C(Environment の承認操作を成立に残し、使えないプランは判定記録で代える逸脱)**: ADR-0133 と矛盾するだけでなく、**成立条件が2本になり、監査人がどちらの証拠を見るべきかをプランの知識から導く**ことになる。プランは変わる(外部の調査 T329-01 は 2026-11-15 時点)。条項が陳腐化する
- **1-E(却下・現状維持)**: qms L41 の誤り(承認操作を操作とし、同じ行で記録にならないと書く)が残る。直さない理由が見当たらない
- **外部の調査の案 B(プラン別の2段)**: プラン名を条項に入れる。GitHub の改定で証拠の基準が動く。採らない

### (4) 機械で閉じる条件と閉じない条件

| 条件 | 区分 | 理由 |
| --- | --- | --- |
| G-8 の判定記録の必須欄(層1 の版・異議・上申)の存在 | 機械(既に降りている) | 存在・構文 |
| 記名者が名簿の人で、出荷判定者の席の責任者と別人 | 機械(帰属の裏づけは既存) | 値の一致 |
| 判定記録が指す対象のコミットと、出荷の証跡のコミットの一致 | 機械で閉じうる(**未確認**: 既存の集約が既に行うかは template を読んでいない)。既に無ければ、template を要するので undelivered | 値の一致 |
| 判定記録の時刻が、配備の実行の時刻より前 | 配備の実行記録を読む機構が標準に無いので**閉じない → adopter** | 実行記録は採用者の基盤にある |
| 配備の資格情報が参照に結び付くか((a)(b)(c)) | 閉じない → adopter(IMPL-0237 のまま)。`env-check` は事実を読むが適合の判定に使わない | 受け手が確かめるか、は外部のシステムの挙動 |
| 事業決裁者の受容判断の質 | 閉じない → manual | 自由な文の意味 |

### (5) 自分の見立ての弱点

- template を読んでいないため、集約が「対象のコミットの一致」や「判定記録の時刻」をどこまで読むかを確かめていない。ここが既に閉じているなら、(1)の弱い所2は弱くない
- 「Environment の承認は強い証拠」は、プラットフォームの記録の信頼を前提にした見立てで、実機では確かめていない(外部の調査 5 節 1 のとおり、プランの機能も文言だけ)
- 1-D を「方向として採る」と言いながら、その費用(配備のワークフローの雛形を持たない ADR-0090 決定6 の理由)を重く見ていない。雛形が未達を配るという理由は、監査の目でも妥当で、これを覆す証拠を私は持たない

## 3. 論点2: 配備の資格情報の置き場(プランに依る)

### (1) 監査の証拠の有無と弱さ

- **ある証拠**: 未達の記録の3項目(開いている経路・経路を持つ主体と直接書き込めるか・狭める措置と止めないもの)。`env-check` が Actions の既定の権限、PR の承認の可否、Environment の配備の参照の限定を**読んで4値で記録する**(IMPL-0351。読めなければ未確認で通過にしない)。これは検出型の良い証拠で、**未確認を通過にしない**設計は監査として評価できる
- **弱い所**:
  1. 「手段が無い」の判断(契約・プラン)は、採用者の主張。**費用による選択と制約による不能を、記録の上で区別できない**。標準は「手段が無い場合」と「使わないと決めた場合」を分けて記録させるが(`:1839-1840`)、分けたラベルの真偽は確かめられない(Green Book の費用を理由にしない論点。01-internal 3.2 の3)
  2. M-5: (c) が満たされているという主張(配備先がリポジトリの外)に証拠を求めない
  3. 配備のワークフローを足したのに未達の記録を書かない場合を、機械は検出しない(M-2)。**未達の網羅性が自己申告**である。これは本件で一番弱い
  4. `env-check` の読みは、実際の GitHub の応答で確かめていない(#346)
- 外部の調査によれば、検出型だけで防止型の代わりとして認める規格は見つかっていない(02-external 4.3)。SOC 2 CC5.1 は代替統制を認めるが、独立性を装えない前提で残余リスクの文書化とセット。本標準の現行は、検出型(env-check の事実の記録)を「狭める措置」として書かせ、**満たす手段には数えない**(`:1848`)。これは規格の読みと一致する

### (2) 支持する案と理由

**2-A(現状維持 + 「課さないと決めた」の明記)**。明記する内容: (i) 外部の秘密情報の置き場を満たす形に加える要件は定めない、(ii) プラン固有の逸脱・代償措置は定めない、(iii) 検出型の統制は満たす手段に数えない(既に `:1848` にある。これを再掲する)。理由: ADR-0133 が閉じた列挙を D-1 に保つ判断と整合し、かつ**検出型は満たしたことにならない**という原則が、置き場の履歴(`gate-criteria.md:180`)でも配備でも同じ形で通る。監査人にとって、同じ原則が別の条項でも同じ結論を与えることは、適合の主張を読む際の予見性になる

あわせて、**自己申告の穴を表示で開示する**: 配備の統制の未達の網羅性は採用者の申告に依ると、根拠水準マークまたは IMPL の note で書く(降りていないのではなく、**機械では閉じない**ことの開示)。既に IMPL-0237 は `check=manual plan=adopter` で、その開示にはなっている。足りないのは、採用者向けの保証の開示側の文である(未確認)。

### (3) 採るべきでない案と理由

- **2-B(外部の秘密情報の置き場を (a) に広げる)**: 外部の置き場が参照を確かめるかは、監査人が確かめられない外部システムの挙動で、確かめる手段を標準が持たない。(b) の「受け手が確かめる」が既に同じ穴を持つ(EV-0184 が E1 間接と開示)。同じ穴を増やすだけで、成立の主張が増え、証拠は増えない
- **2-C(プランに依る未達の条件と代償措置を閉じた列挙へ)**: 条件が機械で閉じない(ADR-0133)。さらに、**代償措置の条件の判定者が採用者**になる。採らない
- **2-D(手段が無い構成では、手動の配備と判定記録とする)**: 監査の目では**統制として成り立たない**。標準の言う「手動の配備」が `workflow_dispatch` なら、これは `ci-gates.md:965` が書いた脆弱な経路そのもの(選んだブランチのファイルで動く)で、むしろ防止型を弱める。リポジトリの外での人手の配備を意味するなら、それを「証拠が無く、自己申告」にする。どちらの読みでも統制の強さが上がる根拠が無い。採らない
- **2-E(env-check の読みで狭める措置の欄を機械で埋める)**: 方向は支持するが、本件の範囲外(#361・template)。却下ではなく先送り。ただし未確認の項目を「通過にしない」現行の設計は崩さない

### (4) 機械で閉じる条件と閉じない条件

| 条件 | 区分 |
| --- | --- |
| 設定の事実(既定の権限・PR の承認の可否・配備の参照の限定)を4値で記録、読めなければ未確認 | 機械(delivered。実機の応答では未確認) |
| 未達の記録の3項目が埋まっている | 機械で閉じうる(存在・構文)。**ただし未達の記録がそもそも書かれているかは閉じない**。配備のワークフローの検出が前提 |
| 配備のワークフローがリポジトリにあるか(あれば未達の記録または (a)(b)(c) の証拠を要する) | 機械で閉じうる(存在)。template を要する。undelivered で表示 |
| (a)(b)(c) を満たすか | 閉じない → adopter(IMPL-0237) |
| 「手段が無い」と「使わないと決めた」の真偽 | 閉じない → manual。人の記名のみ |
| 配備先がリポジトリの外で、資格情報が届かない | 閉じない → adopter |

### (5) 自分の見立ての弱点

- 「配備のワークフローがあるか」を機械で検出する案は、template を要し、配備先が案件ごとに違う(ADR-0090 決定6)ことと緊張する。存在の検出が `.github/workflows/` の走査で足りるのか、私は確かめていない
- 検出型は代わりにならない、という整理は、規格に**明記が無い**(02-external)ことに依る。明記が無い=禁じられていない、でもある。私の支持は規格ではなく、置き場の履歴での既存の扱い(検出型を課したうえで離脱)との整合に拠る

## 4. 論点3: 配備の自動化の不備のリスクの受け止め

### (1) 監査の証拠の有無と弱さ

- 手動の起動について、**誰が・いつ・何を根拠に**起動したかの証拠は、標準の機構の外にある。ホスティングの実行記録が持つ(起動した者・起動先の ref・コミット・時刻。私の知識で、本件の調査では確かめていない)。ただし:
  1. 実行記録の保存期間には上限がある(既定値は設定で変わる。私の知識で未確認)。監査が数年後なら消えている可能性がある。標準が保存を求めていない
  2. 環境を使わない構成(Free の非公開、または `environment:` を外したジョブ)では、配備の記録が環境の配備の履歴に残らない(`ci-gates.md:973` は、環境が無ければ保護規則の無い環境が自動で作られ、**決裁の無い配備が環境を経た配備として残る**ことを注意している。これは逆向きに、記録が「経た」ように見える誤りを生む)
  3. 「何を根拠に」= 判定記録との結び付きは、標準の機構に無い(論点1の弱い所1・2)
- ADR-0123:75 の申し送り(既定でないブランチでの `workflow_dispatch` が `gate-g5` の名の check run を付ける)は、**証拠の真正性に関わる**。監査人は check run の名で G-5 の通過を読む。偽装できる経路が既知で、申し送り先の Issue が未確認(01-internal 9節)。これは本件より重い論点を含むが、追跡先が確かでないこと自体が、標準の統制の穴である

### (2) 支持する案と理由

**3-A + 3-B の一部**: risk-catalog の受け止めの欄を、実態に合わせる。

- 「緊急の修正でも PR を経る運用」は、PR を経る変更についての受け止めに限る。PR を経ない起動とブランチ上のワークフローの書き換えは、別の経路として**行に書き、受け止める規定(第4章 G-8 の資格情報の置き場、`ci-gates.md` の統制の置き場)へ辿れるようにする**
- 受け止めが**防止ではなく、資格情報の結び付きと未達の開示**であることを書く(防止が取れない構成がある事実を行から読めるようにする)

理由: リスクの一覧は規範ではないが、監査人は一覧と統制の対応を見て、受け止めが実態に届いているかを判断する。実態に届いていない受け止めは、**誤った安心を与える表示**で、本コアポリシーの「書かれていない」と「課さないと決めた」の区別以前の問題である

3-D(ADR-0123 の申し送り)は、**本件に含めない**が、追跡先を確かめて裁定の記録に書くことを支持する。確かめないまま終えると、申し送りが所在不明になる。

### (3) 採るべきでない案と理由

- **3-C(手動の起動の禁止)**: 実務(タグの配備・再実行・緊急の復旧)と衝突し、守られない禁止になる。守られない禁止は監査人が最も嫌う(書かれた統制と実態の乖離を生む)。採らない
- **外部の調査の案 X (b)「検出: 実行記録の突き合わせ」を、標準の要件として課す**: 方向は支持するが、突き合わせの対象の記録の保存と、突き合わせる者(誰がやるか、1名の体制では同一人物)が閉じない。要件にせず、手引きまたは adopter とする

### (4) 機械で閉じる条件と閉じない条件

| 条件 | 区分 |
| --- | --- |
| risk-catalog の行が、参照先の規定(節)を指す。参照先の実在 | 機械(`lint:refs` が節番号の実在を検査する)。**意味の整合は閉じない** |
| 受け止めの欄が「PR を経ない起動」を含むか | 機械では閉じない(自由な文) → manual。回帰は edit の指摘(編集の分類)として、独立の突合で見る |
| 手動の起動の実行記録の保存と突き合わせ | 閉じない → adopter |
| ADR-0123 の申し送り先の Issue の実在 | 機械で閉じうる(`gh issue view`)。裁定の段階で人が1回確かめれば足りる |

### (5) 自分の見立ての弱点

- 実行記録に起動者・ref・コミットが残る点は、私の知識で、本件の調査(02-external の 4 節)は「公式がこの経路を危険として明記した箇所は無い」までで、記録の項目は確かめていない
- 3-A を「意味を変えない」と見ているが、「受け止めが防止でない」と書くのは、読み手の受け取りを変える。edit の分類で済むかは議長の判断で、私の見立てより重く扱うかもしれない

## 5. 論点 D-3(#352 の置き場の履歴)と、区分の割れ

### (1) 監査の証拠の有無と弱さ

- 置き場の履歴は、**検出型の統制が既に必須**(`gate-criteria.md:171-179`: 走査・先頭の固定・署名)で、規則で止められない構成は「列挙に無い離脱」として表示される(`:180`)。つまり**証拠(走査の結果・先頭の識別子の記録)は既に監査人が得られる形で存在する**。弱いのは、止められないこと(防止型の欠如)そのものと、「書き込める主体を限れないこと」が構成ごとの定型の文での開示に留まること(`:181`)
- D-3 の文案(別の置き場に要約値を追記して突き合わせる)は、**権限者が異なること**が前提で、これは機械で閉じない(ADR-0133 の理由)。1名の体制では同一人物で、独立性を装う。外部の調査 4.3 の SOC 2 の解説も同じ前提を置く。証拠の価値が、採用者の申告に依る

### 区分の割れについて

| 統制 | 現行の区分 | 監査の評価 |
| --- | --- | --- |
| 配備の資格情報 | 未達(ゲートの状態) | M-1。G-8 の判定基準の外に未達がある。ADR-0083 の定義(ゲートの状態)と合わない。同じ ADR の定義によれば、記録があり、ゲートが判定されうるのに条件と代償措置を定めない状態は「列挙に無い離脱」の定義に当たる |
| 置き場の履歴 | 列挙に無い離脱 | 定義に合う。ただし**判定記録の置き場は G-7 の記録の構成の属性**で、ゲートの状態ではない |
| G-8 の必須レビュア | 空白 | 区分が無い。最も悪い。論点1の 1-A で、そもそも成立条件でなくなるので、空白は消える(区分の問題でなく条項の誤りだった) |

### (2) 支持する案と理由

- **D-b(型の統一だけを裁定し、D-3 の措置は採らない)** を支持する。D-a(足さない)でも結論は近いが、ADR-0133:40 は「プランに依る統制の扱いは #329 の裁定を待つ」と書いて**宿題を明示**している。ここで型を決めないと、宿題が閉じない
- 統一する規則の案(私の見立て): **「構成の属性として、本標準が記録と表示を定めたが、条件と代償措置を定めないもの」は列挙に無い離脱。「ゲートの判定の結果」としての不充足と、判定そのものができない状態は未達**。この規則で分けると、(i) 置き場の履歴は離脱のまま、(ii) 配備の資格情報は**構成の属性なので離脱**になる。ただし (ii) は ADR-0090 決定2・ADR-0028 を置き換え、閉じた列挙の表(`overview.md:700-709`)を1行足す(離脱が9つになる)ことになる。ADR-0133 の「8つ」と IMPL-0237 の文、`unmet[]` の意味(template が配備の未達を `unmet[]` に入れているかは未確認)に及ぶ
- したがって、**どちらかに揃えるなら (ii) を離脱へ寄せる**のが、定義に合う。ただし、もう一つの揃え方がある: 配備の資格情報を **G-8 の判定基準の行として足し**(#3 として)、ゲートの未達にする。こちらは G-8 の判定基準(5.7.2 の決断の記録)に配備の統制を入れるので、論点1の「G-8 は決断の記録」という整理と衝突する。したがって採らない
- 揃えない場合でも、**なぜ別かを1文で書く**(最低限)。書かない現状が最悪

### (3) 採るべきでない案と理由

- **D-c(D-3 を採る)**: 検出型を足して離脱の名を変える案で、F-4・ADR-0133:88 と矛盾する。権限者が異なることを機械で確かめられない。採らない
- **検出型だけで防止型の代わりと認める**: 認めない。理由: (i) 規格に明記が無い、(ii) 検出する主体(集約・走査)の設定を書き換えられる者が、防止を欠く原因の同じ権限者である場合が多く、検出が防止の代わりをする保証が無い(置き場の履歴では集約が基底ブランチの外の走査を行うので独立に近いが、設定を持つのは同じ採用者)、(iii) 既存の標準は、検出型を課したうえでも離脱と定めた(`:180`)。**検出型は補完であり、等価ではなく、状態(離脱・未達)を消さない**という1つの規則を、全ての条項に通すのが筋
- **区分を「未達」へ全て寄せる**: ADR-0083 の選択肢の段が既に採らないと書いた(未達はゲートの状態。`unmet[]` の意味を壊す)。再検討の契機が無い

### (4) 機械で閉じる条件と閉じない条件

| 条件 | 区分 |
| --- | --- |
| 列挙に無い離脱の表示(定型の文・件数)が保証の開示に出る | 機械(既に降りている部分あり。構成に欄の無い4つは IMPL-0521 で undelivered) |
| 離脱の区分の判定(ゲートの状態か構成の属性か) | 条項を書く側の規則。機械は区分を決めない。edit の突合で見る |
| 置き場の履歴の走査・先頭の固定・祖先の確認 | 機械(delivered) |
| 規則で止められているか | 機械で閉じうる(ホスティングの設定の読み)。ただし未確認(権限不足)の扱いは既存のとおり通過にしない |
| 2つの置き場の権限者が異なる(D-3) | 閉じない → adopter。採らない |
| 1名の体制の独立性 | 閉じない。適用の表明まで(ADR-0133 決定2) |

### (5) 自分の見立ての弱点

- 配備の資格情報を離脱へ寄せる私の案は、ADR-0090 決定2 が「未達」を選んだ理由を読み切っていない。未達の3項目の記録(開いている経路など)は、離脱の定型の文より情報量が多く、採用者への有用性は未達の方が高いかもしれない。区分の名よりも**記録の項目の質**が監査の価値を決めるのであれば、名は動かさず、理由の1文を書くだけで足りる、という弱い案が残る。私はこれを排除できていない
- 離脱が9つになると、1名の体制だけでなく、Free の非公開のリポジトリの採用者が、配備を足した時点で適合の主張を失う(未達でも同じ)。件数への影響を測っていない。EV-0160 の観測の対象

## 6. 議長への要望(監査の目からの最低限)

1. G-8 は決断の記録であり、配備を止める門ではないと、第4章に1文で書く(事実の明記)
2. 区分は、揃えるか、別である理由を1文で書く。空白(`ci-gates.md:956`)は残さない
3. 検出型の統制は補完であって、未達・離脱の状態を消さない、という1つの規則を、置き場の履歴・配備の資格情報の双方に通す
4. 未達の網羅性が採用者の申告に依ること(配備のワークフローを足して書かない場合を機械が検出しない)を、根拠水準マークまたは IMPL の note で開示する
5. ADR-0123 の申し送り先の Issue の実在を確かめ、裁定の記録に書く
6. risk-catalog の受け止めの欄は、PR を経ない起動を含む実態に合わせる
