### H-1 効力を持つ記録の裏づけの列挙に、組織の決裁の仕組みの経路が無い(裁定の漏れ)

- 所在: gate-criteria.md:169-171(効力を持つ記録の列挙)、exception-escalation.md:58(7.3)
- 根拠: 裁定 4.2 は「L135 の列挙・L143 の列挙に1項目ずつ足す」と指示した。実装は判定記録の列挙(L160-165)にだけ項目を足した。効力を持つ記録の列挙(L169)は、導入の文を「組織の決裁の仕組みの記録による裏づけを除き、機械が確かめられるもの」へ改めたのに、その除外が指す項目が列挙に無い。7.3 は「その記録の所在の参照を入れる変更の帰属の確認を裏づけにしてよい(同節)」と同節を引くが、同節の効力を持つ記録の列挙には経路が無い。#460 の主な対象(D-0 の決定・層1・例外承認・停止の解除)は効力を持つ記録である。よって、標準の表示(7.3・ADR-0264 決定5・ADR-0106 の置き換えの行)と規範の本文が食い違う。成立条件1(L1872。層1 の記名)は、効力を持つ記録の帰属(IMPL-0415)で数えるため、この経路を数える規範が本文に無い状態になる
- 直し方: L169 の列挙へ3つ目の項目を足す。「組織の決裁の仕組みの記録(適用: 記名者がホスティングの操作をせず、当該の仕組みで決裁した場合): 所在の参照を入れる変更の帰属の確認。確認者の条件・確かめる内容・宣言行は前掲の判定記録の項目と同じ。効力は参照が基底ブランチへ入った時点に生じる」。L174〜177(照合なし・抜き取り・不一致・API)が判定記録と効力を持つ記録の両方に掛かることを、文で明示する

### H-2 「氏名・日付の欄を求めない」と書いた注記と、同じ標準の様式に残る人が記入する欄が食い違う。しかも未達の表示が無い

- 所在: overview.md:191(注記)。deliverable-templates.md:329(D-0「承認日時 / 承認者: <氏名>(<役職>)」)・1046-1047(企画書「起案者 <氏名> / 起案日」「決裁者(事業決裁者): <氏名> / 決裁日」)・1303(テンプレ7「承認者 / 承認日」)・1540(表15「合意 | 役割 | 氏名 | 日付」)・1725(テンプレ11「連署日」)・2136-2143(テンプレ9「決裁者 | 日付」「承認者 | 承認日」)。gate-criteria.md:452(G-1 前提条件3「承認者・承認日・承認した版」)
- 根拠: 注記は「本標準は、…承認者が書き込む氏名・日付の欄を求めません」と断言する。裁定 4.1 は、テンプレ4・11・12 と L1482 だけを D1 へ送った。実装の undelivered マーク(IMPL-1038〜1040)も、この3つだけを表示する。上の欄はマークも D1 への送りも無い。とくに企画書の「決裁者 / 決裁日」は、#460 の出発点(G-1 の二重の記録)そのものである。G-1 の本文(gate-criteria.md L456 付近の新しい段落)は「様式の判定記録を重ねて作りません」と書くのに、企画書の様式は決裁者と決裁日の記入を求め続ける。読み手は、「求めない」と決めた欄と、まだ降りていない欄とを区別できない(CLAUDE.md「却下は成果である」、ADR-0028 の未達の表示)。所有者の決定(2026-11-27)にも反する状態が、表示なしに残る
- 直し方: 次のどちらかを行う。(a) 注記に限定を足す。「第6章の様式に残る承認者・日付の欄は、束 D1 で決裁の記録の所在へ改める(IMPL-…)」。(b) 上の各様式について、IMPL-1039・1040 と同じ形の undelivered マークを足す(d0-template・project-brief-template・plan-template・safety-risk-assessment-template など、impl-targets.yaml に登録済みの降ろし先)。どちらにする場合も、裁定 4.1 の「変えない」の一覧がこれらを漏らしたことを、議長が裁定の追記として記録する。#458 の enablement.md 合意書の節5 と同じ扱いにする

### M-1 G-1 前提条件1 の確認方法を改めたが、降りている実装(IMPL-0679)は frontmatter の承認者・承認日時を読む

- 所在: gate-criteria.md:450(前提条件1)・454(IMPL-0679 state=delivered)、deliverable-templates.md:329・600(IMPL-0782「承認者(frontmatter の approver)・承認日(approved_at)」)
- 根拠: 確認方法を「承認の記録(D-0 の決定の記録の所在)」へ改めた。一方、IMPL-0679 の note は「承認者・承認日時は frontmatter から読む」のままで、delivered と表示される。D-0 を組織の決裁の仕組みで承認した案件では、check-d0 が「G-1 の審議を開始できません」で止める。新しい経路が降りた実装に阻まれる。それを示す undelivered マークが無い(IMPL-1037 は D-0 の申告の表だけを扱う)
- 直し方: 前提条件1 の行に、D-0 の承認を所在の参照で受ける検査の undelivered マーク(target=d0-template、束 D1)を足す。あるいは IMPL-1037 の note を広げ、frontmatter の approver・approved_at を所在の参照へ読み替えることを含める

### M-2 「記名者本人のアカウントの操作で帰属を裏づける」の文が、第3の経路と矛盾したまま残る

- 所在: overview.md:111(1.4「効力を持つ記録」の定義の末尾)、gate-criteria.md:160(判定記録の列挙の導入「記名者本人のアカウントの操作として、次のいずれかに限る」)・169(「記名者本人のアカウントによる操作で帰属を裏づける」)、gate-criteria.md:273(EV の対象の文)
- 根拠: 組織の決裁の仕組みの経路は、記名者のホスティングのアカウントの操作ではない(適用の文が「記名者がホスティングの操作をせず」と書く)。導入の文の「記名者本人のアカウントの操作として」は、第3の経路を文の上で排除する。1.4 の定義も同じ。裁定 1.7 は、帰属の確認の定義の拡張を明記すると決めた。しかし、上位の原則の文(本人のアカウントの操作)の拡張は、ADR-0264 にも本文にも書かれていない
- 直し方: 3箇所を「記名者本人の操作(ホスティングのアカウントの操作、または組織の決裁の仕組みでの本人の認証を経た操作)で帰属を裏づける」の形へ改める。ADR-0264 決定5 に、ADR-0106 決定3 の「本人のアカウントの操作」の語の範囲も一部置き換えると書き足す

### M-3 「人が書く欄は判定者本人が自分の言葉で書く」の表の行に、事前の定義の例外が掛かっていない

- 所在: gate-criteria.md:136(表「人が書く欄」の行「判定者本人が、自分の言葉で書く」)と 139(事前の定義で確認した項目を満たす箇条)
- 根拠: 表の行は、確認した項目を含む人が書く欄の全部に、例外なしで「自分の言葉で書く」を課す。下の箇条は、決裁(G-1・G-8・SG ほか)について確認した項目を事前の定義で満たしてよいとする。表と箇条の向きが逆で、どちらが優先かが本文から読めない。附属書C の「AI に生成させない」は保つべきだが、「自分の言葉で書く」と事前の定義の関係は書き分けが要る
- 直し方: 表の行の末尾へ「確認した項目は、決裁に限り承認の意味の事前の定義で満たしてよい(後掲)」を足す

### L-3 IMPL-1041〜1043 を manual にした扱いは規則に合う。ただし「確かめる者」が、実装が無い間は確かめられない者になっている

- 直し方: 確かめる者を、帰属の確認者(参照を入れる変更を承認するとき)と、プロセス内部監査(抜き取りのとき)へ改める。ADR-0264 決定7 か影響の節に、「降りるまでは manual で表示する」を1文足す
