## #350 PR レビューだけの差し戻し

### 決めること
宣言行(`G-6: 差し戻し / 基準 N`)を持たない PR レビューは、差し戻し率の分子に数えない。この決定(#311 の帰結)を、5.4.6 の分子の規定(:191)に**理由とともに明記する**。「書かれていない」と「数えないと決めた」を区別させる。

### 変える箇所
- 標準 :191 の分子の項へ、次の趣旨を足す。宣言行の無いレビュー(ホスティング上の CHANGES_REQUESTED のみのもの等)は数えない。理由は2つ。(1) 基準の番号を引いたかは宣言行の構文でしか機械で決められず、PR 本文・コメントの自由な文から番号を読むと意味の判定になる。(2) 数えない向きは差し戻し率が低く出る側、すなわち 0% の継続の発火が増える停止の側へ倒れ、見逃しにならない
- 数えないことで生じる誤発火の受け皿は IMPL-0295(欠陥の台帳の「引き下げの点検の記録」、扱い: 誤発火)と相互に参照する
- IMPL-0285(delivered)の note は既に「宣言行の無いレビューは数えない」と書く。変えない。Issue 本文の前提(IMPL-0285 が G-6 の判定記録だけを数える)の訂正は、Issue へのコメントで行う(標準の編集ではない)
- テンプレート: 変更なし。`/pit` の注記の件数表示は、案C を条件つきにする(下記)

### 閉じ方
- machine(既存): 宣言行の構文の検査、帰属の確認(`AM:512-572`)
- manual: 宣言行を書くべき差し戻しを書いたか。内部監査(観点23)
- 案C(宣言行の無いレビューの件数を `/pit` に表示)は、**テンプレートの記録の写し(`records/reviews/`)が宣言行の無いレビューを残す場合にだけ**実装する。写しはマージの時点に宣言行を取り出す設計であり(IMPL-0285 の note)、宣言行の無いレビューはオフラインの履歴からは見えない可能性が高い。見えないものの件数を機械の表示にすると、表示と実態が食い違う。見えないなら、件数表示を約束せず、限界を文言で開示する(「数えていない」は文で書き、件数は出さない)。実装の担当が写しの内容を確かめて決める

### 却下する案
- 案B(PR の本文・コメントから基準番号を抽出して数える): 自由な文の意味の判定で機械で閉じない。GitHub の CHANGES_REQUESTED を数えれば番号の無い差し戻しも入り、第4章 共通ルール3 と :191 の分子の定義に反する。数える向きは、差し戻し率が実際より高く出て 0% の継続を見落とす側(見逃し)へ倒れうる

### 突合
第4章 共通ルール3、:191-192、:195(0% を避ける目的の差し戻し自体は禁じない)、#311 decision.md と矛盾しない。重へ上げる条件(数える方向へ変える)に当たらない。

## #349 窓と最小標本の構成化

### 決めること
構成に窓の欄(整数の月数、既定 2、下限 2)を足す。これは差し戻し率専用でなく、**第2区分の共通の窓**とする(手戻り率を将来実装するときも同じ値を使う。#348 の前に置く)。最小標本は欄を持たず、定数 30 のまま。変更は `/process-change` の緩める向きの経路(決定した者の記名と理由、`changeLog[]` への記録)とする。

### 変える箇所
- 標準:
  - :190 の「窓の長さは2行目の継続の期間(EV-0146)と同じ値」を、「継続の期間は観測の窓の長さと同じ。既定は2か月。組織が窓を長くしたときは、継続の期間も同じ長さになる」へ書き換える
  - :159 の表の「2か月継続」を「観測の窓の長さの継続(既定 2か月)」へ。EV-0146 の対象を「継続の期間の既定値」と読み替える
  - これは意味を変える。既定値の挙動は変わらないが、「窓を長くすると継続の期間も延びる」を新たに規範にする。ゆえに**編集ではなく軽の裁定の対象**とし、議長が裁定して記録する
  - 窓を長くした値を G-1 に記録することは第4章 要求事項1 が既に求める。その旨を :238 の近くへ参照として足す
  - IMPL-0268(undelivered)を delivered へ改める。窓は構成化、最小標本は固定を note に残し、「固定は意図した設計(下げてはならない)」と書く
- テンプレート: 構成のスキーマに窓の欄を足す。`AM:43` の定数を、構成から読んだ値(未設定なら 2)に置き換える。履歴の読み出しの起点(`AM:661-662`)も窓から導く。`/process-change` に窓を扱う種別(または `settings` の個別の値)を足し、短くする向きは拒否する(下限 2)。`/pit` と保証の開示に、窓の長さの現在値を出す
- 規則データ: 構成のスキーマの変更が規則データに及ぶ場合は `npm run template:kb` で複製を更新する

### 効力日
窓を長くする変更は、その変更の登録日より後の評価から効く。過去の評価を遡って当て直さない(遡ると過去の 0% の継続による停止が消える)。引き下げで止めた種別は、既存のとおり評価の日より後の登録の判定でしか戻らない。窓を長くしたことだけでは停止を解かない。

### 閉じ方
- machine: 型・整数・下限 2・未設定時の既定・窓の値の表示・短くする向きの拒否
- manual: 窓を長くした理由の妥当性(記名と理由は機械が存在を確かめるだけ)。内部監査
- 最小標本は欄を持たないため、「下げる」は構成の形として表現できない(machine で閉じる)

### 上限を置かない理由(案C の却下)
窓を過度に長くすると検知は鈍る。それでも上限を置かない。
- 窓が履歴の長さ・最小標本を満たせないほど長いと、IMPL-0286 により判定不能となり、種別が**止まる**。窓を長くして検知を黙らせる経路が、そのまま停止の側へ倒れる。形骸化の方向には働かない
- 上限の値には実証が無く(E0)、標準に無い規則を新設すれば採用者への新しい制約になる。重に上がる点であり、必要性を示す実証もない
- 残る欠点は、窓を長くした分だけ 0% の継続の発見が遅れること。これは「緩める向き」として記名と理由を要し、窓の現在値を保証の開示に出すことで開示する。根拠水準マークで「上限を置かないのは、判定不能が停止に倒れる設計に拠る。実運用での遅れは未検証」と書く(新規の EV。台帳は `evidence:write` で再生成)

### 却下する案
- 案B(最小標本の欄を持ち、30 未満を拒否): 上げる方向は検知を遅らせる統制の弱化で、窓と二重の欄になる。標準が許したのは窓を長くすることだけ(:238)。必要が実証されるまで欄を足さない
- 案D(構成化せず L1 運用): 標準が「窓を長くしてかまいません」と許した手段が無いまま、G-1 の記録とテンプレートの使う値が食い違う。採らない

### 突合・実装で確かめる点
`verify-gate-contract`、構成スキーマ、`template:kb` の複製の乖離検査、旧い構成の既定の導出、`test-check-delegation.mjs` の fixture(窓 2 か月前提。`suite-fixtures-encode-decisions` に従い、既定値のまま通ることを先に確かめる)。ADR-0081 L141・L146 と矛盾しないことは survey で確認済み。

### 重への引き上げ
案どおりなら不要。ただし議長が窓の上限を置く裁定をした場合は重へ上げる。

## #348 手戻り率

### 決めること
テンプレートは手戻り率を**算出しない**と決める(IMPL-0291 は undelivered のまま)。「降ろさないと決めた」ことと理由を明記し、採用者の手段への委ね方を整える。

### 理由(信頼性による)
- 案B(取り込み後の再作成をトレーラから算出)は、:193 の分子(取り込まれた後**または不採用となった後**)の一部しか読めない。分子が小さく出る向きは、基準を超えない側、すなわち**発火しない側**へ倒れる。:225「発火しない引き下げを備えているものとして扱ってはならない」と、テンプレートが引き下げを備えたという表示の間に実態の差が生じる。差し戻し率が数え漏れで停止の側へ倒れる設計と逆向きで、非対称になる
- 基準値の欄だけを足し、集計を持たなければ、発火しない欄が残る。装飾の欄であり、備えたように見える
- 案C(計画表の「やり直し」の欄を読む)は、人が書く欄を入力にする。書き漏らしと書き換えは機械で閉じない。委任された変更が計画表を書き換えられる経路(:256)を塞ぐ追加の設計が要る。信頼できる集計になると言えない
- 案D は B と C の欠点を併せ持つ

### 変える箇所
- IMPL-0291 の note は現行の理由(基準値を構成に持たない・不採用の変更を履歴から読めない)を維持し、次を足す。分子の一部しか読めない算出は発火しない側へ倒れるため備えたものとして扱えない。計画表の欄は機械で閉じない。ゆえに降ろさない。確かめる者と `review=2027-04` は維持する。`plan=scheduled` が適切かは議長が裁定する。降ろす見込みが無いなら `plan=adopter` に改める(「降ろすかもしれない」と「降ろさない」の区別を保つ。私見: B・C を却下した以上 `adopter` が正確)
- 標準の分子の定義(:193)は変えない。ADR-0081 の原則(自動の引き下げ)に触れない
- 保証の開示・`/pit` の既存の「集計していない」注記(`AM:47-48,708,716`)が、基準値と手段の記入有無とともに出ていることを、実行で確かめる。出ていなければ欠陥として直す
- Issue の受け入れ条件1(算出できないなら理由を記録)は、上の note で満たす。Issue 本文の IMPL 番号の誤り(0285 → 0291)はコメントで訂正する
- 根拠水準マーク: 「窓内にタスク30件を満たす小規模チームがほとんど無い」といった推測は書かない(未検証)。書くなら EV でマークする

### 閉じ方
- adopter / manual: 採用者は `basis.detection.reworkRate` に書いた手段で集計し、内部監査(観点23)で確かめる。構成の記入有無は machine(既存)
- 「手戻り率が基準を超えても発火しない」は、根拠水準マークではなく IMPL-0291 の undelivered 表示で開示する(降りていない規定の表示。台帳が出す)

### 却下する案
B・C・D(上記)。別途、将来 B のトレーラ算出を下限の補助表示として出す案は、「表示と実態の食い違い」を避けるため、分子の定義を変える裁定を伴うなら重へ上げる。今回は採らない。

### 重への引き上げ
不要。分子の定義を変える(標準を B に合わせる)案、基準値の既定値を置く案を採らないため。

## #340 事象2 `start` を呼ばない自己修正

### 決めること
`start` を呼ばない自己修正は検知しない。**強制できているのは `start` を呼んだ範囲だけ**と明記する。強制できていない範囲を、別の IMPL として undelivered・adopter で表示し続ける。

### 理由
- フックによる検知(案B)は、テストの失敗が続く中の修正反復と、テストを先に書く TDD 作業を区別できない。`guard-write.mjs` はロックの外(テストを先に書く作業)を遮断しない設計。反復の数も失敗の同一性もフックから確かめられない。機械で決められない条件であり、誤検知の費用が大きい
- 案D(PR 検査で連続した修正コミットを数える)は件名の意味に依る。案E(テスト実行を `self-heal.mjs` 経由に限る)は採用者の実行基盤への新しい義務で、エージェント以外の経路を止められない。重の条件に当たる点でもあり、採らない
- 案C(`/implement` に「失敗したら start」と書く)は既に `implement/SKILL.md` にロックの説明がある。指示資産であり強制ではない。重ねても統制は増えない。強制と指示の区別を開示することで足りる

### 変える箇所
- `roles-responsibilities.md` IMPL-0272 の note(:1795): 「別 Issue」の曖昧な一文を、「ロックの外の反復は強制の範囲に入らない」へ改める。delivered(強制の範囲は `start` を呼んだ単位)のままにする。範囲が部分であることが読み手に分かるよう、note の冒頭に範囲を書く
- 新しい IMPL を足す。対象: 3.12.10 要求事項1 のうち、`start` を呼ばない反復。`state=undelivered check=manual plan=adopter`。note は「準拠テンプレートは、ロックの外の自己修正の反復を検知も遮断もしない。採用者が実行基盤の側で、テスト実行の経路を `self-heal.mjs` に限る等の手段で強制する。確かめる者: 採用者」。IMPL-0279(ADR-0084 で adopter)と同じ形
- `phase5-implementation/template-repository.md:984` 付近の「迂回」の一覧へ、`start` を呼ばない反復を足す(既にシェルからの迂回を載せている)
- 保証の開示の「強制できる範囲」の記述に、同じ限界を書く(テンプレート側。突合で、書きぶりが既存の限界の書き方と揃うか確かめる)
- 要求事項5 の本文は**変えない**。要求事項5 は採用者への規範であり、テンプレートが全範囲を強制できないことは、要求事項5 の下で採用者が基盤で補う事項になる。ここで「`start` を呼ばない運用では自律実行を解禁してはならない」と書き足すと、採用者への新しい義務または要求事項5 の読み替えになり、安全に当たるため重へ上がる。書かずに、限界の開示と IMPL の表示で閉じる
- `/pit` 等で自己修正が `start` 経由でないことを示す手段は持たない。ロックの有無の表示(`status`)は既存

### 閉じ方
- machine(既存): `start` を呼んだ範囲の強制(`test-self-heal.mjs`、42 件)
- manual / adopter: ロックの外の反復。根拠水準マークは付けない(「検知しない」は実証に基づく事実で、評価値ではない)。一方、「ロックの外の自己修正はまれである」といった頻度の推測は書かない(未検証。書くなら EV でマーク)

### 重への引き上げ
上記のとおり、要求事項5 を強める記述を足す場合、または `start` を呼ばない自己修正を禁止・必須の記録とする場合は、重へ上げる。本案はそれらを含まない。
