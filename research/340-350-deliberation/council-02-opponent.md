## #350 PR レビューの差し戻し(調査の推奨: A+C = 数えない・件数を表示)

### 反対論

1. **調査は「誤発火」と言うが、危険の向きを一方向にしか見ていない**。調査は「数えない側は差し戻し率が低く出て、0% の継続の発火が増える(停止の側 = 安全側)」と言う。
   発火が増える害は小さくない。(a) 5.4.6 自身が「検出が罰になる」ことを恐れて1行目を設計している(`:187`)。実際に人が差し戻した(GitHub の CHANGES_REQUESTED)のに数えられず、引き下げられると、レビューアは「差し戻しは宣言行を書かないと効かない」と学ぶ。(b) 逆に、引き下げが不当に続くと採用者は構成を緩める(委任範囲を外す、種別を止める)方向へ流れる。**誤発火は戻らない**(`:221` 付近「誤発火と記録しても、引き下げた範囲は戻りません」)。戻すのは 5.4.5 の判定だけである。安全側は無償ではない。
2. **偽の 0% の継続を検知する危険は、Issue の主張そのもので、調査は退けきれていない**。窓の中で実際には差し戻しがあるのに、宣言行が無いので 0% と読む。これは「検知の誤発火」であり、同時に「記録が無い差し戻しは差し戻しとして存在しない」という扱いを標準が選んだことになる。選んだ理由は #311 の裁定(番号を引かない差し戻しは数えない = 形だけの差し戻しで 0% を避ける抜け道を塞ぐ)であって、**宣言行の無いレビュー**(番号は PR 本文に書いてある場合を含む)の扱いは、その理由から自動には出ない。番号の有無と宣言行の有無は別の軸である。
3. **調査の表(c)と節2が食い違っている**。#350 の表(c)は「窓の分子に入れず」と書き、節2は「コミットと対応づけられない差し戻しは差し戻し率の分子には入れている(`AM:268-271` の `ownRejections` は対応づけた記録だけ)」と書く。どちらが実装か。`AM:190-197` を読んで確定しないまま、(c) と (b) を「同じ向き」と書くのは根拠が足りない。分子に入れているなら (b) と向きが違い、(b) だけを外す理由が要る。
4. **C(件数の表示)は A に付ければ足りるのではなく、別の統制である**。「表示」は検査ではなく読み手頼みである。件数が 0 でない場合に、次の一手が「数えていない差し戻しがあります」と**停止の解除や誤発火の記録への導線**まで出すかが、信頼性を決める。

### 対案(1つ)

**A+C に、宣言行の無い承認レビュー(CHANGES_REQUESTED の写し)の件数を窓ごとに出し、その件数が 0 でない月に限り、0% の継続の発火を「保留・人の確認」へ変える(自動の引き下げはしない)**。
数えない決定(分子の定義)は維持する。分子を変えないので重へ上がらない。ただし「0% の継続の発火に、数えていない差し戻しの存在という機械で決められる条件(件数 > 0)を加える」ため、引き下げの手前に人の確認を挟む形の変更になる。
→ これは ADR-0081 の「自動の引き下げ」の原則に触れうる(期限つきの判定を拒否権として採らなかった #311 の裁定、`research/311-deliberation/decision.md:40-46`)。**触れるなら採れない**。その場合の対案は、次の縮小版である。

縮小版: 発火は自動のままにし、**発火時に必ず「数えていない差し戻し N 件」を理由欄に出す**。誤発火の記録(IMPL-0295)へ書く者が、その場で確かめられるようにする。機械で閉じるのは「件数が理由に出ること」だけ。

### 受け入れる条件

- 節2/(c) の食い違い(分子に入れているか)を、実装を読んで一文で確定する
- 数えない理由として「番号を引かない」ではなく、**宣言行の無いレビューは判定記録ではない**(第4章 G-6「承認レビューを判定記録とする条件」)ことを根拠に書く(番号の有無と宣言行の有無を混ぜない)
- 発火時の理由欄に件数が出る(縮小版)

## #349 窓の構成化(調査の推奨: 窓だけ構成化。最小標本は欄を持たない)

### 反対論

1. **「窓を長くすることは緩める向き」という前提が成り立たない**。窓の中の件数が最小標本(30)に満たないと「判定不能」で、発火しない。窓を長くすれば件数が増え、**判定不能が評価可能に変わり、0% の継続が発火しうる**。小さいチームでは、窓を長くすることは検知を**強める**側に働く場合がある(標準が窓を長くしてよいとする理由もこれである。`:236-238`)。他方、すでに評価可能なチームでは、窓を長くすると発火が遅れる(弱まる)。つまり向きは状態に依存する。調査は `settings` の「足すのは緩める向き」と同型だと言うが、同型とは言えない。**緩める向きと決めて記名と理由を要求すると、強める向きの変更にまで摩擦を課す**。
2. **効力日の遡及(調査が軽の会議体に回した点)は、機械で閉じる**。窓を構成で変えたとき、変更前の期間の評価を遡って当てるか。遡ると、過去の 0% の継続が消えうる(統制の弱化の抜け穴)。ここを裁定なしに実装へ回すと、実装者の選択が標準の規定になる。「窓を長くした効力日より後の評価にだけ新しい窓を当てる」と決められるなら、決定可能な条件(日付の比較)であり、manual にせず machine で閉じるべきである。調査はこれを「軽の会議体で裁定する点」と書くだけで、閉じ方を示していない。
3. **窓に上限が無いことは「統制の弱化」である**。上限を置くと重へ上がるので避けたい、という都合が調査の書きぶりに見える(「新しい規則」)。しかし、上限が無いまま構成化すると、`/process-change` の記名と理由だけで、窓を事実上無限にして 0% の継続の検知を止められる。標準 `:225` の「発火しない引き下げを備えているものとして扱ってはなりません」と、構成の形が両立しない。上限を禁止として置かなくても、**窓がある値を超えたら保証の開示に「検知が実質働かない」と出す**ことは、新しい制約ではなく開示であり、重へ上げずに済む。
4. **最小標本を欄に持たない案は、半分の解決でしかない**。窓を長くするだけでは、週に数件しか変更の無いチームは 6 か月でも 30 件に届かない。届かないチームは「判定不能が続く」ままで、第2区分は永続的に計測できない範囲になる。標準はそれを許す(判定不能は発火しない状態)。ただし、**判定不能が続く事実を採用者が自分の構成で解決する手段を、窓だけでは与えない**。最小標本の欄を持たず、窓を長くしても足りないチームには、L1 運用以外の道が無い。これは「降ろさないと決めた」と明記すべき事項である(調査 案D の言い方を、案Aにも適用する)。
5. **`:190` の「継続の期間と同じ値」を直す方法が、意味の変更を含む**。窓 = 継続の期間 なら、窓を長くすると「継続」の期間も長くなる。EV-0146(継続の期間の既定値)を窓の既定値へ読み替えるのは、編集ではなく意味の変更である。intake.md は編集に当たるかを会議体に回している。反対の立場は、**意味の変更として扱い、EV-0146 の見直しの時期を前倒しする記録を残す**ことを求める。

### 対案(1つ)

**窓の欄を足す(下限 2、整数、第2区分の共通)。変更は、向きを問わず `/process-change` で記名と理由を要する(緩める/強めるの分類をしない)。効力日より前の評価には新しい窓を遡って当てない(日付の比較で machine)。窓が既定値の3倍(6か月)を超えるとき、保証の開示と `/pit` に「窓が長く、検知は遅れる」と常時表示する(禁止ではなく開示なので重へ上げない)。最小標本の欄は持たず、持たない理由と、届かないチームの扱いを標準へ明記する。**

### 受け入れる条件

- 「緩める向き」と決めるなら、判定不能から評価可能へ変わる強める向きの扱いを併記する
- 効力日の扱いが machine で閉じる
- 窓の長さが保証の開示に常に出る(上限の代わり)
- `:190` の直しは意味の変更として EV-0146 の扱いを記録する

## #348 手戻り率(調査の推奨: A = 実装せず開示、IMPL-0291 は undelivered のまま)

### 反対論

1. **A は、Issue の指摘(第2区分の2本の検知のうち1本が全く無い)を「開示」で閉じ、実質何も変えない**。標準は手戻り率の引き下げを定める(ADR-0081、自動の1段階の引き下げ)。テンプレートが実装しない限り、採用者が「手戻り率で引き下がる」ことは起きない。`/pit` の注記だけで、採用者が自分の手段を備えるかは**内部監査(観点23)頼み**である。観点23 が確かめるのは年次の監査の側で、毎月の窓の評価ではない。頼った結果、手戻りが増えても何も起きない状態になる。コアポリシーの言う「頼った結果、決めるべきことが漏れる」ケースに当たる。
2. **B(下限の算出)を「数え漏れが発火しない側へ倒れる」から退けるのは、論理が逆**。差し戻し率が停止の側へ倒れることを美点にするなら、手戻り率の下限が発火しない側へ倒れることは、何も無いより悪くない。何も無い状態(A)は「常に発火しない」。下限は「少なくとも取り込み後の再作成は発火する」。**下限は A より常に強い**。問題は、下限を完全な手戻り率として見せることだけで、それは開示で防げる(`:225`)。
3. **機械で閉じる部分があるのに manual にしている**。実装計画の状態「やり直し」の行数は構文として数えられる(案C)。人が書く欄の改ざん・書き漏らしは閉じないが、**欄にある値の集計・基準値との比較は決定可能**。調査は「書かれた正しさは manual」と全体を manual 側に寄せているが、閉じる部分と閉じない部分を分けていない。コアポリシーの「機械の検査にするのは、決定可能な条件だけ」に従えば、決定可能な部分は機械にすべきである。
4. **基準値の欄が無い、が実装しない理由として弱い**。基準値の欄を足すことは、第4章 要求事項1 が既に「組織が定め、記録する」と求めるものを構成に持つだけで、intake.md 自身が新しい義務に当たらないと見ている。#349 の窓の欄と同じ設計(第2区分の共通の欄)で足せる。欄が無いことは実装を止める理由ではなく、実装の一部である。

### 対案(1つ)

**案C の限定版を実装する**: 実装計画の「やり直し」の行を読み、窓内のタスクの母数に対する比を、構成の基準値(欄。未設定なら「基準値未設定(発火しない)」と表示)と比べる。基準値の既定値は置かない(置くなら EV と外部の調査が要る → 重)。分子は「計画表の記録」と明記し、トレーラ側の値との一致は求めない(案D は採らない)。限界は IMPL-0291 の note と開示に書き、「計画表は人が書く」「不採用の後の再作成は計画表の記録に依る」を根拠水準マークで開示する。計画表を委任の範囲から外すかは、`:256` との突合で確かめる。
IMPL-0291 は部分達成(delivered と undelivered の分割)とし、消さない。

### 受け入れる条件(A を受け入れる場合)

- 基準値の欄を構成に持たないことを、「降ろさないと決めた」と標準に明記する
- `/pit` と保証の開示に、手戻り率が**未集計であること**が毎回出る(今も出ているなら、その機械検査の存在を確かめる)
- 内部監査の観点23 が毎月の評価に代わらないこと、代替の手段(採用者の集計)の実施頻度を G-1 に記録させる

## #340 事象2 `start` を呼ばない自己修正(調査の推奨: A = 検知しない・開示)

### 反対論

1. **A は 3.12.10 要求事項5 と衝突する**。要求事項5 は「停止条件を強制できない環境で自律実行を解禁してはならない」と定める。実行で確かめたとおり、`start` を呼ばない自己修正は、スクリプトからは見えず遮断もされない。これは**強制できない環境**である。開示は強制ではない。開示を足して自律実行の解禁を維持すると、標準の要求事項に反したまま運用が進む。調査は「関係を明記する必要がある」と書くだけで、衝突を認めていない。衝突があるなら、解決は「開示」ではなく「要求事項5 の適用範囲の明確化」か「解禁の条件の追加」であり、後者は重へ上がる(安全に当たる)。
2. **B・D・E を一律に「機械で閉じない」で退けるのは、検討が浅い**。B(フックで検知)はテスト失敗の後のロック無しの連続修正を見る案で、TDD と区別できないと調査は言う。しかし、**テストファイルを変えずに、テスト対象の本体ファイルを、直近の失敗したテスト実行の後に連続して変える**ことは、フックの入力(ツール呼び出しの履歴)から決定可能な条件にできる余地がある(閾値の妥当性は別。誤検知は警告にとどめれば害は小さい)。実際に試験をして確かめずに退けている(調査は `iterate`/`status` の挙動を確かめたが、フックの検知を試作して誤検知率を測っていない)。
3. **「別 Issue」の再送**。IMPL-0272 の note に「別 Issue」と既出で、#340 事象2 がその別 Issue のはずである。ここで「開示」に落とすと、「別 Issue」は永遠に閉じる先が無い。**後継の持ち主が不在のまま undelivered が増える**。

### 対案(1つ)

**開示に、解禁の側の条件を1つだけ加える**: 自律実行のモード(`mode` 種別)を解禁する構成の変更に、採用者の記名の確認事項「停止条件を強制できるのは `start` を呼んだ範囲に限ると理解している」を含める(`/process-change` の既存の記名・理由の欄に載せる。新しい義務ではなく、既存の解禁の記録に事実を1行足す)。IMPL-0272 は部分達成の note へ「強制の範囲」を明記する。フック(B)は、警告のみの試作を別 Issue へ移す(受け入れ条件つき: 誤検知率を実測)。

### 受け入れる条件(A を受け入れる場合)

- 要求事項5 との関係を、「強制できない範囲を残したまま解禁を認める」ことの是非として明示し、**認める理由**を書く(これを書けなければ、重へ上げる)。重へ上げる点: 「強制できていない範囲があるまま、自律実行の解禁を認める記述を変える場合」(intake.md)。A は記述を変えないので軽に残れるが、現状の記述が要求事項5 と整合するかの確認は軽でも省けない
- 「別 Issue」の持ち主が決まっている(B の試作の Issue を起票する、または既存の Issue へ足す)
