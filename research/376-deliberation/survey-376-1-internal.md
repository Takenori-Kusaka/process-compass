# #376 内部調査: 任免と緩める向きを同じ変化点に含むときの向きの優先

- 調査日: 2026-11-05
- 対象: 標準(第3章 3.13、第5章 template-repository「向きの扱い」)、ADR-0055・0088・0089・0106、準拠テンプレート `template/`(72a98bd)、回帰スイート `scripts/regress/`、記録 `research/319-deliberation/`
- 方法: 読解のみ。回帰スイートとテンプレートは実行していない(実行で確かめるべき点は末尾に挙げる)

## 0. 要点

1. **標準は「変化点の向き」を1つの値として定めていない**。3.13.3 は向き(緩める・厳しくする・未達の発生)を変更ごとに扱い、任免は「統制の向きにかかわらず、決定として扱う」直交の軸として置く。3.13.4 の記録の6項目にも「向き」の欄は無い。単一値の `changeLog[].direction`(`appoint` を含む5値)は、準拠テンプレートの表現である
2. **記名の照合は向きの値に依らない**。`deciderProblems`(generate-profile.mjs 2171 行)は、任免の項目(`appointItems`)と緩める向きの項目(`loosenItems`)を項目ごとに照合し、1つの `decidedBy` に**両方の要件を同時に課している**。`direction` は表示(D-0 改訂履歴・PR の検査の見出し・出荷の集約)と「記名を要するか」の粗い判定(`SIGNED_DIRECTIONS = ['loosen','appoint']`)にだけ使われ、どちらの値でも記名と帰属の照合の対象になる
3. **向きの優先(loosen > appoint)は #318 で生じたものではない**。2026-10-01 の初期実装(テンプレート ff13247)から、導出は `loosens.length ? 'loosen' : appoint…` で、コメントも「任免と名簿の表記の変更は、緩める向きを含まない場合に『任免の決定』とする」。同じ期待値ファイルの「2名 poc cl0」は、任免を含む変化点で p302 時点から `向き loosen` を期待しており、印も無い
4. **「元の注記」は appoint と arising の優先を述べたもので、loosen との優先ではない**。matrix-sweep.mjs 197 行の注記は、3名を割る変化点(離脱 = 発生)の場面で、向きが `arising` か `appoint` であることを受け入れる文脈にある。X-6(decision.md §8)と ADR-0089 はこれを「任免を緩める向きより優先する」根拠として引いたが、注記の射程を超えている
5. **Issue 本文の「ADR-0087 の決定5」は誤記**。代償措置の終了を緩める向きの行として出すと定めたのは ADR-0088 決定5。ADR-0087 決定5 は決裁権限規程の文の直しである
6. 2名 mvp・growth cl0 の行では、署名者(1人目)が変更前の決定者で、かつ緩める行の席(AI維持管理者)の責任者・変更後の決定者でもあるため、どちらの向きでも記名の照合の結果は変わらない。**向きの値が変えるのは表示だけ**である

## 1. 向きの定義と記名・表示の規定

### 1.1 標準

| 所在 | 規定 |
| --- | --- |
| 第3章 3.13.3 向きの表(1975 行〜) | 緩める: 記名と理由。決定するのは対象の席の責任者、または D-0 表1 の決定者。独立レビュアの席の責任者が外部の確認者なら決定者に限る。AI の名義を受け付けない / 緩める(ステージを前へ戻す): SG の判定 / 厳しくする: 即時 / 未達の発生: 決定として扱わない。人が実際に減った場合に限る |
| 第3章 3.13.3 任免の表(1982 行〜) | 「席の責任者の任免は、統制の向きにかかわらず、決定として扱う」。任命・交代・後任: D-0 表1 の決定者の記名と理由(「緩める向きでない交代にも要する」)/ 決定者その人を替える: 前任の決定者、前任者が離脱済みなら組織上の任命権者 / 初回の記入: 決定者の席に記入する人 |
| 第3章 3.13.3 箇条 | 任免に記名を求める理由は「替わった者の名義で緩める向きの決定が通るため」。いずれの記名も AI の名義を受け付けない |
| 第3章 3.13.4 記録 | 記録5「決定した自然人」(単数)。任命権者の記名で決定者を任命した場合はその旨。**向きの欄は無い** |
| 第5章 template-repository 540 行 | dry の出力の「向き」: 緩める向きと決定できる者、厳しくする向き、引き下げた運用形態 |
| 第5章 template-repository 595 行「向きの扱い」 | 緩める・厳しくする・発生・任免・名簿の表記の変更・決定者の交代・ステージを戻す、を**行ごとに**扱う。任免を「向き」の表に並べているが、優先の順は書いていない |

標準のどこにも、1つの変化点が複数の種類の変更を含むときに向きを1つへ寄せる規定は無い。標準の構造は「変更ごとに扱いを決める」であり、単一値の向きを要求していない。

### 1.3 準拠テンプレートの実装(72a98bd)

- 向きの値: `DIRECTION_LABEL`(config.mjs 298 行)= loosen「緩める」/ appoint「任免の決定」/ tighten / arising / none。`SIGNED_DIRECTIONS = ['loosen', 'appoint']`(308 行)
- 導出(generate-profile.mjs 2101〜2111 行):

```js
// 向き「発生」は、人が実際に減った変化点に限る。任免と名簿の表記の変更は、緩める向きを含まない場合に「任免の決定」とする
const direction = loosens.length ? 'loosen'
  : appointItems.length || renameItems.length ? 'appoint'
  : departure && arising.length ? 'arising'
  : tightens.length ? 'tighten' : 'none';
```

  優先は loosen > appoint > arising > tighten > none。5421 行でも、規則の承認で有効になった委任があれば `loosen` へ上書きする
- 記名の照合(`deciderProblems`、2171 行): 1つの `decidedBy` に対して
  - `appointItems` の各項目: 変更前の決定者(`priorDecider`)、前任者が離脱済みなら変更前から名簿にある組織上の任命権者。初回の記入は決定者の席に記入する人
  - `renameItems`: 決定者。決定者本人の行は任命権者または本人以外の席の責任者
  - `loosenItems` の各項目: `allowedDeciders(config, item.seat)` = **変更後の**構成での対象の席の責任者と D-0 表1 の決定者。`holderOnly`(担い手の名義)は席の責任者に限る。外部の確認者の独立レビュア席は決定者に限る
  - どれか1つでも満たさなければ拒否(5248〜5252 行)。記名が無いときの拒否・案内も、任免と緩める向きで別々に出る(5299〜5318 行)
- 表示: `renderChangeReport` は「統制を緩める向きの変更」と「席の責任者の任免・決定者の変更」を**別の節**に出し、それぞれの決定できる者を書く。単一値の向きは、D-0 改訂履歴の表(3310 行)、PR の検査6b の見出し(check-pr.mjs 659 行)、出荷の集約(aggregate-evidence.mjs 3982・5410 行)、次の一手(5553 行)のラベルにだけ現れる
- 記録: `changeLogEntry` は `direction` 1つと `decidedBy`・`reason` 1つを持つ。任免と緩める向きの項目は `diff` の行として残るが、どの行が任免でどの行が緩める向きかの区分は記録に残らない(`appointerSigned` だけは別の欄)
- 帰属の照合(#428、material-attribution.mjs 562 行): `decisionNeedsAttribution(e)` = `decidedBy` があり、かつ `SIGNED_DIRECTIONS.includes(direction)` または名簿の変更。**loosen・appoint のどちらでも対象になる**ので、向きの値で帰属の照合が外れることは無い。照合するのは `decidedBy` のアカウントの帰属だけで、席の要件(誰が決定できるか)は PR の時点では再照合しない(要件の照合は `/process-change` の適用の時点)
- 構成の整合(config.mjs 1587 行、verify-gate-contract.mjs 630 行): `SIGNED_DIRECTIONS` の記録に `decidedBy` と `reason` が無ければ問題。これも両値で同じ

## 2. 1つの変化点に任免と緩める向きが同時に入るとき

### 2.1 今の挙動

- 向き: `loosen`(緩める向きの行が1件でもあれば)
- 要求する記名: 1つの `decidedBy` が、任免の要件と緩める向きの要件の**両方**を満たすこと(要件の積)。「両方の要件を同時に課す形」は、既存のコードで既に実装されている
- 2名 mvp・growth cl0 の具体(matrix-sweep.mjs 84〜101 行): 1回目の変化点で1人目が全席に記入(初回の記入)。2回目で2人目を名簿へ足し、独立レビュアと AI運用担当者の席を2人目へ任命、記名は1人目。2人目の確認者により G-6 の未達が解け、ADR-0088 決定5 によりカバレッジの下限 90 → 80 が AI維持管理者の席(`RULE_APPROVER_SEAT`)の緩める行として出る
  - 任免の要件: 変更前の決定者(事業決裁者 = 1人目)→ 満たす
  - 緩める向きの要件: 変更後の AI維持管理者の席の責任者(1人目のまま)または変更後の決定者(1人目)→ 満たす
  - したがって、向きが `appoint` でも `loosen` でも、受け付けの可否・記名者・帰属の照合は同じ。違いは改訂履歴等のラベル「任免の決定」か「緩める」かだけ
- 2名 poc cl0: 同じ入力(任免を含む)で、p302 から `向き loosen`(下限 90 のとき既に)。緩める行が下限以外にあったことになる。どの行かは読解では特定していない(実行で確かめる。§6)。この行は印なしで loosen を期待しており、mvp・growth の印と矛盾する

### 2.2 任免の記名と緩める向きの記名の要件の差

| 観点 | 任免 | 緩める向き |
| --- | --- | --- |
| 照合の時点の構成 | 変更**前**(`priorDecider`) | 変更**後**(`allowedDeciders(config)`) |
| 決定できる者 | 変更前の D-0 表1 の決定者。前任者が離脱済みなら組織上の任命権者(体制の外。変更前から名簿に `external`+`appointer`)。初回の記入は決定者の席に記入する人 | 対象の席の責任者、または D-0 表1 の決定者。担い手の名義は席の責任者に限る。外部の確認者の独立レビュア席は決定者に限る |
| 席の責任者本人 | 決定できない(決定者でない限り)。新任の決定者は自分の任命を自分で確定できない | 決定できる |
| 組織上の任命権者 | 前任の決定者が離脱済みのときだけ決定できる | 決定できない(席の責任者でも決定者でもない) |
| 1つの変化点での自己 | 新任の決定者は不可 | 変更後に席の責任者・決定者になった人が可能 |

要件の積が空になる、または狭まる組み合わせ(読解から導いた仮説。試験は未確認):

- (a) **任命権者の記名 + 緩める向き**: 前任の決定者が離脱済みで任命権者が任免を記名する変化点に、緩める行が混ざると、任命権者は緩める行を決定できず拒否される。ADR-0088 決定5 の「その変更の記名で決める。別の記名の儀式は要さない」は、この場合に成り立たない。回避は変化点を分けること(先に任命権者が決定者を任命し、次に新しい決定者が緩める行を含む変化点を記名する)
- (b) **決定者の交代 + 緩める向き**: 任免は変更前の決定者 P、緩める行は変更後の席の責任者か変更後の決定者 N。P が対象の席の責任者として残らない限り、積は空になる
- (c) 1回目と2回目の変化点が同じ人の記名で通る今の matrix-sweep の行は、(a)(b) に当たらない

**突合の所見**: X-6 の根拠のうち「元の注記」は、matrix-sweep.mjs 197 行の「第3巡: 任免を同じ入力に含む場合、向きは『任免の決定』(出荷できない状態の発生は arising の一覧に残る)」である。この注記は、3名を割る変化点(離脱 = 発生)に席の付け替えを含めた場面で、向きを `arising` か `appoint` と受け入れる判定の説明であり、**任免と発生の優先**を述べている。他の場面(new.mjs 30・65・370 行、replay.mjs 99 行、scenarios.mjs 328 行)の `direction === 'appoint'` も、すべて任免と発生(または厳しくする)の組である。任免と緩める向きの組で appoint を期待した場面は、mvp・growth の2行のほかに無い。そして2行の「元の期待 appoint」は、p302 では緩める行が無かった(下限 90 のまま)ことの帰結にすぎず、優先の決定を表していない。同じ入力の poc 行は loosen を期待していた。

X-6 の結論「決定できる者が変わる挙動を、決定なしに固定しない」は、今のテンプレートについては事実と合わない。決定できる者は向きの値ではなく項目ごとの照合で決まり、どちらの値でも要件は同じである(§1.3)。印が固定しているのは表示のラベルの差である。ただし、どちらの優先も ADR・標準に書かれていない点(X-6 の指摘の核)は正しい。

## 4. 案ごとの整合

前提: 「緩める向きの変更を AI が決めない」(3.13.3、5.5.7)と「効力を持つ記録の帰属」(ADR-0106)は、記名の照合と `decisionNeedsAttribution` が担う。両方とも `SIGNED_DIRECTIONS` の2値を区別しない。

### 案A appoint を優先する(導出を直す)

- 整合: 3.13.3「任免は統制の向きにかかわらず決定」と語の上では近い。記名・帰属の照合は変わらない(appoint も SIGNED)
- 不整合・損失
  - 改訂履歴・PR の検査・出荷の集約のラベルが「任免の決定」になり、同じ変化点に**緩める向きの変更が含まれることが単一値の表示から消える**。3.13.3 が緩める向きを重く扱う非対称(5.4.5・5.4.6)と、読み手(監査・品質保証部門)の見え方が逆になる。詳細は `diff` と変化点の報告に残るが、記録の要約で緩める向きが見えなくなる
  - 5421 行の上書き(規則の承認による委任の有効化)とも優先が食い違うため、そちらの扱いも決める必要がある
  - poc 行の期待(loosen)を改めることになり、改める根拠の決定が要る
  - 任免の要件が緩める向きの要件を包含するわけではない(§2.2: 照合の時点も決定できる者の集合も違う)。「任免の記名があれば緩める行も決まる」と読める表示は誤解を生む

### 案B loosen を優先する(今の導出を決定として記録し、期待値を改める)

- 整合: 今の実装(初期実装からの優先)、poc 行の期待、5421 行の上書き、ADR-0088 決定5「同じ差分の中に緩める向きの行として出す」と同じ側。緩める向きを要約に出すので、非対称の表示とも合う
- 不整合・損失: 単一値から「任免を含む」ことが消える。任免の表示は `diff` と報告の節、`appointerSigned` に残るが、改訂履歴の向きの欄からは読めない。3.13.4 記録5 の任命権者の旨は `appointerSigned` で別に出るので失われない
- 受け入れ条件の形: 優先の決定を ADR に書き、`changed.by` に引いて mvp・growth の期待を loosen へ改め、印を外す

### 案C 変化点を分ける(任免と緩める向きを同じ変化点に入れない)

- 整合: 単一値の向きと単一の記名者の記録(3.13.4 記録5「決定した自然人」)が素直に対応する。§2.2 (a)(b) のように要件の積が空になる組を、手続として解く形でもある
- 不整合
  - **ADR-0088 決定5 と衝突する**。決定5 は終了の行を「未達を解く変更の差分の中に」出し、「別の記名の儀式は要さない」と定める。2人目の任命そのものが未達を解くため、任免と終了の行は入力として分けられない(任免を出せば、同じ差分に終了の行が出る)。分けるには、終了の行を次の変化点へ送る(黙って戻さない、とは両立するが「同じ差分」に反する)か、決定5 を置き換える新しい ADR が要る
  - 利用者の手数が増える。強制にするなら、混在を拒否する新しい拒否の理由が要る
- 部分採用の形: 混在を拒否せず、要件の積が空のとき(§2.2 (a)(b))にだけ「変化点を分ける」案内を出す。既存の拒否の文言(2195 行付近の「後任の任命は、別の変化点として…」)の延長にある

### 案D 両方の記名を要する(向きを複数の値で記録する、または要件を表示に出す)

- 要件の側: 1人の記名者に両方の要件を課す形は、既に実装されている(§1.3)。追加の実装は要らない
- 2人の記名者(任免は決定者、緩める行は席の責任者)を別々に求める形は、`decidedBy` が1つの今のスキーマでは表せない。スキーマと 3.13.4 記録5(単数)、ADR-0106 の帰属の照合(記名者ごとに裏づけ)を改める必要がある。標準は「どちらか一方の要件を満たす1人」で足りると読め、2人を要する根拠は標準・ADR に無い
- 表示の側: 向きを集合(例: `directions: ['loosen','appoint']`)で持つか、単一値のまま「緩める(任免を含む)」のような複合のラベルを出す形。`SIGNED_DIRECTIONS.includes(e.direction)` の3か所(config.mjs・verify-gate-contract.mjs・material-attribution.mjs)と表示の5か所を改める。旧い記録との互換(移行)が要る
