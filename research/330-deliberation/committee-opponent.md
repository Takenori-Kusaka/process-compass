# #330 反対委員の意見

日付: 2026-11-17。担当: 軽の会議体の反対委員。読んだもの: intake.md、Issue #330、template-repository.md:855-868、gate-criteria.md:977-1030・1625-1645、exception-escalation.md:26-90、assurance-case.md 観点16、ADR-0033。template/ は未取得で、実行はしていない。

## 結論

受付の見立て(項目4 への継続期間の併記を軸に、例外承認で珍しい構成を受ける)のうち、併記には賛成する。例外承認で受ける部分には反対する。論点 B は再審議しないことに賛成するが、A-3 は編集と決めつけない。

## 論点1: 例外承認(第7章 7.3)で「未実施を続けたい」を受ける案 — 反対

- 7.3 は「基準の不充足」を、承認・記録・回収つきで先へ進める手続である(exception-escalation.md:22-24, 40)。任意の検査の未実施は、現行の条文では G-5 の不充足ではない。通過である(template-repository.md:862)。通っているものに例外承認は要らず、承認の行を作る契機がない。受付の「既存の歯止めそのもの」は、その歯止めが働く入口が無いので成り立たない。
- 入口を作る(未実施が続く場合に例外承認を要求する)なら、それは採用者への新しい義務であり、受付が「採らない」とした失敗扱いと実質が同じになる。軽から重へ上げる条件に当たる。
- 7.3 の期限の効力(L62-63)は IMPL-0574・0575 が undelivered で、集約は期限を日付と比べていない(L68, L77)。降りていない歯止めを頼りに、別の穴を閉じたことにしてはならない。
- 省略(テーラリングの宣言、ADR-0028)で受ける案は、基準2・5 を外す宣言が許されるかを確かめていない。許されないなら、「道具が存在しない」採用者の受け皿が無いまま残る。
- 代案: 受け皿を別に作らない。珍しい構成は、未実施のまま項目4 に期間つきで開示し続けることを正規の姿とする。未実施の継続は異常ではなく、見えていることが条件である。例外承認の語は条文に出さない。
- この条件なら賛成: 例外承認で受ける対象を「基準を満たさないと決めたもの」(例: 基準2 の Critical/High を残して出荷)に限り、未実施の継続はそこに混ぜない。

## 論点2: 項目4 へ「未実施が続く期間」を併記する案 — 条件つきで賛成

- 項目6 の型(L1633, L1642)の転用は妥当。評価を含めない(L1635)にも合う。
- 見落とし1: 起点が定まっていない。項目6 は「最初の出荷」が起点で、受付は「SG-0」と「実装の開始(G-4 通過)」を混ぜて書いている(intake A-4 は SG-0、A-2 は実装の開始)。none.json の期限は SG-0 だが、gate-criteria.md:980 は実装の開始を G-4 の通過後とする。起点が違えば、同じ検査の継続期間が違う値になる。起点を 1 つに決め、機械が読める記録(G-4 の判定記録の時刻)に限る。
- 見落とし2: 併記は、読む者が出荷判定者で、G-8 は異議なしで通れる(L1934)。見えるだけで止まらない。破られたとき失うのは、受容を求められる出荷判定者・事業決裁者の判断の質である。この損失を条文に書くなら、観点14(受容と異議の対応)への結線まで書く。結線が無いと開示が死文になる。
- 見落とし3: 項目4 は「集約が合否に使った検査に限る」(L1625 の導出元)。未実施の検査は合否に使われていない。「実施」の定義と、未実施の検査名を出す導出が矛盾しないかを、aggregate-evidence.mjs の実物で確かめるまで賛成を確定しない。受付も未確認と認めている。
- 代案: 継続期間の数値を出さず、「未実施の検査名の列挙」と「実装の開始の記録の有無」だけを出す案がある。数値の起点争いを避けられる。ただし継続が見えにくい。
- この条件なら賛成: 起点を 1 つに固定する、項目4 の導出元の記述を未実施に拡げる、手順(どのコマンドを足すか)は手引きへ置く、観点14 に結線する。

## 論点3: 実装の開始後の空コマンドの扱い — 失敗にしないことには賛成、ただし範囲を分ける

- 受付の「lint の道具が無い言語を門前払いにする」は、lint・licenses には当たる。依存監査(audit)とカバレッジには当たらない。依存監査は、どの言語の採用者でも道具が存在する。一括で「任意」と呼ぶこと自体が粗い。
- 見落とし4: 現行の表(template-repository.md:858-862)が「静的解析」と「依存監査」を同列にしている結果、G-5 基準2「Critical/High = 0 件」(L733)が、静的解析と脆弱性スキャンの 2 つで 1 基準である。一方だけ未実施でも通る読みが成り立つか、実物(集約)で確かめる。成り立つなら、これは項目4 の併記より重い実体の穴である。
- 代案: 失敗にする義務は新設しない。ただし基準2 の文に「未実施の側を 0 件に数えない」を足すかを、重の論点として議長が裁定する。足すと採用者への新しい義務になるので、軽の範囲では足さない。
- この条件なら賛成: 軽の範囲は、開示(項目4)と手引きの書き換えまで。基準の読みを変える提案が出たら重へ上げる。

## 論点4: 論点 B と A-3(template-repository.md:862)— 編集と決めつけない

- 「カバレッジが空でも通る」を直すのは、受付は編集とする。反対ではないが、L862 は表の行を「未実施として通す」から「失敗にする」へ変える場合がある(言語のアダプタで製品のコードがあるときのカバレッジ)。それは意味の変更で、ADR-0124 決定1 が既に決めたことを本文へ反映する作業とみるなら編集に当たる。ADR-0124 が本文の反映を済ませたかを先に確かめる(受付も確認していない)。済んでいないなら、それは #360 の取り残しで、#330 の範囲ではなく #360 へ返す。
- 「対象なし」と「製品のコードあり」の境は、IMPL-0475 の範囲(目印)と IMPL-0239 の範囲(目印を持たないコード)が分かれている。後者が undelivered のまま、表の行だけ「失敗」と書くと、書いたことが実装に届かない状態が増える。降りていない規定は消さず表示する規則に従い、IMPL を足して undelivered で出す。
- 論点 B を再審議しないことに賛成。

## 論点5: IMPL-0234・IMPL-0239 の扱い

- 受付の「機械の検査: 空のコマンドの検出と表示(失敗にしない)」に賛成。ただし、これで IMPL-0234 の `state` を delivered にしてよいのは、「通知を出して通す」部分だけである。note にある「依存の取得失敗で検査器の入力が欠けたとき、各検査器が失敗で終わるか」は別の未確認事項で、delivered にすると未確認が消える。IMPL を分割して残す。
- IMPL-0239 の「記録の3項目(基準・理由・時刻)」と「実装の開始後に用いない」は、実行で確かめるまで undelivered のまま。#330 の裁定で変えない。

## 採らない案(反対委員として追加)

- 例外承認で未実施の継続を受ける(論点1)。入口が無く、作ると新しい義務になる。
- 起点を SG-0 と G-4 で曖昧にしたままの併記。
- 外部の調査を省くこと自体は、開示の追加だけなら賛成。ただし論点3 の基準2 の読みを変える案が出たら、外部の調査(SonarQube 等)が要るので、重へ上げる。
