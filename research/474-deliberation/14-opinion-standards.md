# #474 委員の意見: 規格の委員

- 立場: 規格策定の作法(規定と参考の別、適合の定め方、テーラリング、参照実装・適合試験の位置)に照らす。判断軸は信頼性。安さ・変更量は理由にしない
- 記号: 01 の「型 1〜5」(線の引き方)・[台帳 SRC-]・[新規 N-]、02 の「型 A〜E」(実装の分け方)・§1.x・事例 1〜6
- 未確認の点は確かなこととして使わない。使う場合は「(未確認)」と付ける。特に: 24748 が「手引きは要求でない」と明記する条、12207:2017 以降の完全適合とテーラリングの条番号、SSDF の原文(02 §1.8)、Jakarta が RI を廃した理由

## 2. 線の基準の文案

### 2.1 標準(規定の部分)に属するかの問い

1 つの規定について、次を順に問う。

1. **第三者が、採用者の記録と証跡だけを見て、はい/いいえで確かめられるか。**(Directives 5.5 の「検証できる要求だけ」。いいえなら要求にしない)
2. **規定が述べるのは、満たすべき結果・残す証跡・用意するものとその項目・決め方(誰が・いつ・何を根拠に)・下限の、いずれかか。**(いいえなら、順序つきの手順・道具の操作・実装の説明である。3 へ進まず行き先の決め方へ)
3. **特定の製品・機構(ホスティング、ルールセット、特定の AI 製品)の語を除いても、同じ要求が書けるか。**(書けないなら、結果へ言い換える。言い換えて 1 を満たせばその文を残し、元の語は実装の例へ。言い換えられなければ実装の例へ)
4. **値(数・閾値・期間)は採用者の事業・製品・過去のトラブルで変わるか。**(変わるなら標準は値を持たず、「定義すること」「定義が無いときの扱い」「下限」だけを持つ。2.2 参照)
5. **これを欠くと「標準に従っている」と言えなくなるか。**(いいえなら要求にせず、推奨か手引きへ)
6. **(新設・変更のとき)この要求を満たす実装が、少なくとも 1 つの実装の例で確かめられたか。**(いいえなら、要求に「実装の例で未確認」の表示を付ける。落とす理由にはしない。02 (c) の関門)

問 1〜5 のどれかが「いいえ」の記述は、規定の部分に置かない。問 6 は属するかではなく、表示の条件である。

### 2.2 下限と値の区別

先例の使い方を整理する。Scrum は完成の定義を「組織の標準があれば全チームの最低限」とし、なければチームが作る [台帳 SRC-0640 c1]。SLSA はレベル、OpenSSF は MUST で下限を置き、上は自由にする(01 型 5)。共通フレームも尺度を規定せず関係者間で決める(二次資料 [新規 N-10])。値そのものを規定する先例は、確かめた範囲に無い。

標準が数を持ってよいのは次の 3 つに限る。

- **下限**: 「その数を下回ると、目的が論理的に達成されない」と書ける数(例: 承認者が 0 名なら承認でない)。判定の問い: **数を変えると目的の達成の判定が変わるか。** 変わるなら下限、変わらず程度の差になるなら値
- **既定**: 採用者が自分の値を定めるまでの暫定の扱い。必ず根拠水準マーク(ADR-0026)を付け、「各社が定義して置き換える」と書く
- **外から決まる数**: 法令・安全規格が定める数。標準は繰り返さず引用で書く(Directives 5.7、外部の制約は情報 7.6 [台帳 SRC-0633 c2,c7])

持たないもの: 検知の閾値、時間の長さ、件数の上限、サイズ。これは所有者の線引き(検知の値は各社)と同じ向きである。「下限」と書かれた数が、実は値(程度の差)になっていないかを、問 4 で 1 条ずつ検査できる。

### 2.3 落ちた記述の行き先

| 落ちた理由 | 行き先 | 決め方 |
|---|---|---|
| 問 1 が「いいえ」(確かめられないが、採用者の判断を助ける) | 手引き(参考。規範語を使わない) | 読み手の判断の助けになるか。ならなければ削除 |
| 問 2・3 が「いいえ」(手順・製品の機構) | 実装の例 | 動く形で初めて意味があるか。結果への言い換えが成り立つなら、言い換えた結果を標準に残し、手順だけを実装の例へ |
| 問 4(値) | 実装の例の既定値、または手引きの目安(根拠水準マーク付き) | 値の根拠を示せるか。示せなければ削除 |
| 問 5 が「いいえ」 | 手引き(推奨)か削除 | 欠いても適合の判定が変わらないか |
| どの行き先でも誰の役にも立たない | 削除 | 削除は「課さないと決めた」と記録する(下の 5 の規定の台帳) |

**削除と移動は、消すのでなく、行き先を記録する。** コアポリシーの「採らないと決めたことを明記する」に沿い、落とした規定の一覧を残す。

## 3. 「手順を持たない」の一段厳しい線について

01(c)の指摘は正しい。12207 のタスク・ASPICE の基本プラクティスは活動の水準で、本標準が「順序つきの手順は持たない」とするのは、それより厳しい。

見解は、本標準の「決め方」「ゲート」「例外承認」は、**手順ではなく、満たすべき結果と制約である**。理由と境目は次のとおり。

- **ゲート**: 「通過の条件(判定基準)と、通過を示す記録」である。条件と記録は結果の記述で、手順ではない。ゲートの実施の仕方(誰がどの画面で押すか)は手順で、実装の例にある
- **決め方**(誰が・いつ・何を根拠に決めるか): 責任の所在と根拠は結果の制約である。12207 でいえばタスクに近い要素(責任・時期)を含む。ここは先例より厳しくせず、**「入れ替えても同じ証跡が得られるなら手順、順序が結果の条件(承認は出荷の前)なら制約」**で線を引く。前後関係の制約は標準に残す
- **例外承認**: 例外の記録・承認者の権限・期限・再審が結果である。「申請書を出し、レビューを受け、承認を得る」の流れは手順である

この線は、12207 と異なる位置に引くことを意味する。そのため、**手順を持たないことの代償を開示する**。先例は活動の指標と評価者によって空洞化を防ぐ(01 型 2)。本標準は活動を持たない代わりに、(a)証跡の最小の項目(2.1 問 2 の「項目」)、(b)下限、(c)省略と未達の宣言、(d)プロセス内部監査(既存)で空洞化を見る。これらでも「数だけ満たして中身が無い」は機械で閉じない。これは manual・adopter で開示する(CLAUDE.md の統制の閉じ方)。厳しい線を選ぶ根拠は、24748-3 が述べる理由、つまり実装の多様さが個別の手順の詳細化を不可能にする [新規 N-3] と、AI と道具が変わる速さ(所有者の線引き)である。先例上は「より厳しい選択」であって「先例にない選択」ではない。この選択が正しいかの実証は無く、根拠水準マークで開示する。

## 4. 適合の定め方

実装を標準の検査から外した後、「従っている」は採用者が**要求ごとの宣言**で定める。構成は 12207 の修整適合(修整本文を宣言する [新規 N-2])と 15289 5.1(媒体・名称・分割は自由 [台帳 SRC-0377])を土台にする。

1. **適合の表**: 要求ごとに次の 3 状態を宣言する
   - 満たす: 証跡の所在を書く
   - 省略: テーラリングの宣言(理由・責任者・見直し時期)。12207 の修整適合に当たる。標準がテーラリングで省略を許す要求だけ
   - 未達: ADR-0028 の `unmet`。省略と区別し、消さずに出し続ける
2. **適合の範囲**: 「従っている」は、宣言した範囲(上の表)に対してだけ言える。表を出さない主張は適合の主張として受け付けない
3. **自己申告の位置**: 型 D と OpenSSF Best Practices(自己申告+一部の自動検査)[新規 N-17]に当たる。自己申告は信頼性が最も弱い型である。補う仕組みは、既存のプロセス内部監査(自分の組織の別の目)と、採用者側の機械の検査(実装の例があれば使える)。第三者の認証は先例(Khronos・CNCF の型 B)にあるが、本標準は取り入れない。理由: 認証機関と費用の前提が無く、決定可能な条件しか見ない害(02 型 B)もある。取り入れないと決めたことを明記する
4. **実装の例の位置付け**
   - 冒頭と各例の入口に「規範でない。使うことは適合の要件でも十分条件でもない」と表示する(Directives 24.5 の注記と同じく、要求事項・不可欠な指示を含まない [台帳 SRC-0633 c8]。SSDF の実装例は「必須でなく出発点」とされる(原文は未確認)。24748 は別規格の手引き(明文は未確認)。SLSA は仕様が残り実装は退いた(事例 5))
   - 実装の例の中に規範語(してはならない等)を置かない。置くなら「標準の何条を実現する例」と対応を書く(ADR-0064 の、スキルの文に標準の所在か「テンプレート独自」の印を付ける型と同じ向き)
   - 「参照実装」の名を使わない。02 の型 C(RI)と事例 3(GlassFish)を避けるため、「実装の例」を保つ
   - 実装の例を使った採用者は、使った範囲を適合の表の「証跡の所在」として書ける。使うこと自体では「満たす」にならない(中身を確かめるのは採用者)
5. **標準の側の表**: 要求ごとに「実装の例で満たされたか」の表を持つ(型 D)。空欄は「不明」であり、満たされたことにしない(事例 6)。満たされていない要求は消さず表示する(ADR-0028 と同じ扱い)

## 5. 2026-11-16 の決定と ADR-0040・0028 の扱い

11-16 の決定(準拠テンプレートは標準を体現し連動させる。使えば準拠する)は、置き換えが要る。「使えば準拠する」は、実装の例を十分条件にする。これは、実装が標準の一部であると読ませる型 C に近く、実装の保守と標準の改訂が結び付く害を持つ。「体現する」は、標準を実装した例としての質を指す語としては残せる(連動の約束ではなく、実装の例の側の目標として)。

新しい ADR に書くべき決定の骨子(5 行以内):

1. 標準の規定の部分は、結果・証跡・用意するものとその項目・決め方・下限だけを定め、値・手順・特定技術・実装を持たない。属するかは 2.1 の問いで決め、落ちた記述の行き先と、課さないと決めたことを記録する
2. 準拠テンプレートは「実装の例」であり規範でない。使うことは適合の要件でも十分条件でもない。2026-11-16 の決定の「使えば準拠する」を置き換える。名称は「参照実装」を使わない
3. 適合は、採用者が要求ごとの 3 状態(満たす・省略・未達)の表で宣言する。標準の検査は実装の実在を条件にせず、実装の例の側が各要求への対応を自己申告・試験する。標準は対応表を持ち、満たされていない要求を表示し続ける。版の表示に、新設・変更の要求の確認の有無を載せる
4. ADR-0040: 決定 1(様式は第 6 章の部分集合)・3・4(omit に理由、逆の指示を書かない)を、標準側の準備物の項目として残し、検査の対象を「標準に実在する項目」へ移す。「template に欄があるか」の検査は実装の例の側の義務にする。ADR-0028: 決定の本体(未達を省略と区別し出し続ける)は標準の要求として維持し、契約検査(決定 5)は実装の例へ移す
5. 置き換える決定(ADR-0040 の検査の置き場、ADR-0033 決定 2・0077 の template 必須の結線、ADR-0089 の回帰の置き場、標準 1.10.1 の適用の開始)を列挙し、各 ADR の本文は書き換えず、この ADR から「置き換える範囲」を指す

## 6. 各案への賛否

| 案 | 賛否 | 理由 |
|---|---|---|
| 1 | 反対 | 線が無く、規定と参考を読み手が識別できない(Directives 7.1)。基準が無いと同じ議論が Issue ごとに再発し、11-27 の「引く」方針に沿った裁定を再現できない。信頼性の理由である。変更量が少ないことは理由にしない |
| 2 | 線には賛成、単独には反対 | 先例(型 1・5)が支える線である。ただし 02 (c): 実装を外すなら、実装できない規定を防ぐ関門が要る。案 2 は、標準の検査から実装を外す一方で、この関門を置かない。「紙の標準」(事例 2。ただし一方的な出典)の害を防げない |
| 3 | 反対 | 表示だけの分離は、要求の識別(7.1・20.2)としては正しいが、線を引かない。「参照実装」は型 C で、事実上の標準の害(事例 3)を持つ。同じ文書・連動の維持は、所有者の「やりすぎ」への答えにならない。ただし 3 層の表示の考え方は、2.1 の問 1・2 と 4.4 に取り込む |
| 4 | 賛成(修正つき) | 線は案 2、関門は型 D・B の手立て。修正は 4 点。(a)「少なくとも 1 つの実装の例で満たせた」は独立でない単一の実装で、GlassFish・Web SQL の害を持つ。IETF は独立した 2 つを求める。現状の 1 つしか無い事実を、根拠水準マークで開示し、独立した 2 つ目の実装の例(試行の事例など)が出たとき見直す。(b) 版の条件は「表示」にする(案 5)。入口に実装を要求しない先例(RFC 7942)に合い、実装の例の障害が標準の公開を止めない独立性も得る(03 補足 3)。(c) 自己申告の表は空欄=不明とし、意味の判定は manual と adopter で開示する。(d) 試験が決定可能な条件しか見ない害(型 B)を、表の凡例に書く |
| 5 | 賛成 | 案 4 の(b)の形。標準の版は「公開」と「確認済み」を分けて表示する |

総括: 線は問 2.1 で引き、関門は案 4(+案 5)で置く。判断の核は、実装を外すことそのものではなく、「外した後も、実装できない規定と空洞な適合の主張を、開示によって読み手が見分けられる」状態を保つことである。それが保てない部分は、manual・adopter・根拠水準マークで「閉じていない」と表示する。

## 付記: 本意見が確かめていないこと

- 12207:2017 の完全適合・修整適合の条番号と、完全適合でテーラリングを許さない規定の現行版での有無
- 24748 系が「手引きは要求でない」と明記する条、SSDF の原文
- 独立した 2 つの実装の例を、本標準でどう数えるか(採用事例の独立性の定義)。ソロ期で採用者が事実上いない状況での実証は無い
- 自己申告の適合の表が、実際に空洞化を防ぐかの実証。先例の OpenSSF の自己申告の有効性は、本調査では確かめていない
