## 0. 案に無い欠陥(最優先。実物で確かめた)

### 0.1 検証の呼び出しの無いテストの検出は、JS 系でほぼ働かない

`ASSERTION` は `should` を単語として拾う。実行して確かめた(node で `ASSERTION` を適用)。

| 追加行 | 判定 |
| --- | --- |
| `it('should add numbers', () => {});` | **アサーション行とみなす(true)**。中身が空でも |
| `expect(true).toBe(true);` | アサーション行とみなす(中身が無意味でも。これは B1 の範囲) |
| `it("works", () => { foo(); });` | 拾わない(正しい) |
| `@Test void shouldWork() {}` | 拾わない(`shouldWork` は語の境界で当たらない) |

`it('should …')` は Jest・Vitest・Mocha で最も普通の題の付け方である。空のテストが、題の語 `should` のせいでファイルの「アサーション1件以上」を満たし、一覧に出ない。案 5.1(3)は「`isAssertionLine` の数を数える」としており、**既存の `ASSERTION` を流用する限り、IMPL-B は最も典型の空テストを取りこぼす**。

- 案の限界の文(ファイル単位の近似・列挙の外の検証・弱いアサーション)は、この取りこぼしを開示していない。`should` は「列挙の外の検証」ではなく、列挙の**内側の誤り**である
- 要求: (1) テストの題の文字列を除いた残りで数える、または `should` を新しい検出の側では数えない。(2) 流用するなら、既存の IMPL-0204(削除行のアサーションの検出)への影響を `test-check-pr.mjs` の回帰で確かめる(案 5.1 の `ASSERTION` の行は「決める」止まりで、この欠陥に気付いていない)。(3) EV-A の差し替え条件に「題の語による取りこぼし」を入れる。(4) **実装の前に、この1行を含む場面を試験へ先に足す**(取りこぼしの再現を先に固定する)
- これを直さずに IMPL-B を `delivered check=machine` と表示すると、表示と実態が食い違う(CLAUDE.md の「表示と実態が食い違う高は直す」に当たる)。直すまでは state を `delivered` にしない案が安全

## 1. 争点への賛否

### Q1 G-6 の判定者への新しい義務。差し戻しまで書くか: **新しい義務である。書く。ただし書き方を直す。揃える向きは強い側**

- 新しい義務である。既存の 5.8.5 後段は「必須の確認事項として示す」までで、「確かめられない行は差し戻す」を持たない。案の 3 の問い(破られたとき誰が何を失うか)が示す損失(出荷判定者が台帳だけを突合して署名する)は、「示すだけ」では防げない。示されても読まれなければ同じである。判断軸が信頼性なら、強い側に寄せる
- ただし**強い側へ寄せるなら、既存の検証を弱める変更の一覧にも同じ文を足し、1つの文で両方の一覧を覆う**べきである。2段落で強さが違うと、採用者は「前者は読んで差し戻し、後者は示されれば足りる」と読む。既存の段落へ足す変更は新しい義務の追加(重)であり、この会議体が扱える範囲内。ADR-0262 に書く
- 「確かめられない行がある」は**判定可能な文ではない**(誰が・何をもって確かめたか)。5.8.5 禁止事項2 の改め(読んだ承認と読まない承認が記録から区別できない)と同じ欠陥を作る。条文は結果を書く規律なので、**確認の結果を行ごとに承認の記録(G-6 の承認レビューの本文)へ残す**ことを結果として書く。残す中身は行ごとの処置(1.1 の3区分)だけで、記名欄は増やさない(本人の承認の記録に含める。記名欄を求めない方針と両立)。処置の無い行が残る変更は G-6 を通さない。これなら「示した」と「読んだ」が記録で区別でき、機械でも「行数と処置数の一致」は確かめられる(決定可能な条件)。内容の正しさは manual のまま
- 案 IMPL-C は `check=manual` のみ。上の「行数と処置数の一致」を機械の検査にできる部分があるので、manual 一本にするか、一致だけ machine にするかを裁定で決めること。私は後者(machine は存在と数の一致だけ。意味は manual と開示)を推す。ただし 3 巡の枠に収め、機械の検査を増やしすぎない

### 1.1 条文の一意性の欠陥(未完了の印の処置の書き方)

案 1.2 は「台帳の行があるか、**この変更の受入基準を満たすのに要らない箇所か**」と書く。2つ問題がある。

1. **負債台帳の既存の義務(`deliverable-templates.md:770` 「妥協・TODO・仮実装はすべて記録する」)と衝突する**。「受入基準に要らない箇所なら台帳が無くてよい」は、すべて記録する義務の例外を、一覧の確認の文の側から新設している。要らない箇所でも仮実装は仮実装であり、記録の義務は残る。例外を作るなら、義務の側(第6章の台帳)を改める決定になり、本件の範囲外
2. 「要らない箇所」は判定者ごとに揺れる(受入基準との関係は文脈依存)

案: 処置を **3 区分に閉じる**。(i) 台帳の行を引く(識別子)。(ii) 妥協・仮実装ではない(語が文字列・文書・テストの題・抽象の基底の未実装の例外など)と理由を一語で書く。(iii) いずれでもなければ差し戻す。「受入基準に要らない」は処置にしない。これなら既存の義務と矛盾せず、誰が読んでも同じ分類になる(分類は manual)

検証の呼び出しの無いテストの問いも直す。案は「受入基準のどの項目を確かめているか」だが、これは**追跡の問い**で、**検証の有無の問い**ではない。空のテストも、題から受入基準の項目に対応づけられる(題が項目を名乗る)。必要な問いは「確かめている呼び出しはどれか」(ヘルパ・枠組み固有の検証の名)である。処置は (i) 検証を担う呼び出しの名を挙げ、受入基準の項目を引く、(ii) 検証を要さない(型・コンパイルだけの確認など。理由を書く)、(iii) いずれでもなければ差し戻す

### Q2 偽陽性と読み飛ばし。節を分けるか: **分ける。識別子の注釈を採らないことには同意する**

- 節を分ける理由は読み飛ばしだけでなく、**処置の種類が違う**こと(上の 1.1)。既存の一覧(検証を弱める変更)は人が意図して行った操作で、新規 2 種は書き残し・空洞である。同じ節にすると、偽陽性の多い側が読まれなくなり、案の懸念(既存の一覧まで読まれなくなる)が現実になる。分けて、各節に件数と「検出しない形」を並べる
- 一覧の偽陽性の量は実測が無い(EV-A は E0)。「読み飛ばされる」の閾値は誰も持たない。ここは根拠水準マークで開示し、観測の源(G-6 の確認の記録での「(ii) 妥協ではない」の割合)を差し替え条件に入れる。処置を記録に残せば、(ii) の割合から偽陽性の率が後で測れる。**行ごとの処置の記録は、偽陽性率の観測手段にもなる**(案が EV-A の観測を「拾い漏れの事例と誤検出の件数」としている点を、処置の記録で具体化できる)
- 識別子の注釈(1.8)を採らない結論に同意。AI が注釈を埋めれば一覧から消える。ただし理由の根拠が G-6.md 手順2 の準用で、独立の根拠にはなっていない。そこで足す: 注釈で結ぶ型は、**注釈の欠けを検出する側に倒す**と成立する(known-failure は欠けを出す)が、未完了の印は「注釈が無いこと」が正常な形(普通の TODO)なので、欠けを検出対象にできない。この非対称が本質の理由である。ADR-0262 にはこちらを書く

### Q3 設定の鍵を置かないこと・言語ごとの語の一覧: **鍵を置かないことに賛成。言語別の語の一覧を template が持つことは「細かい定義を増やさない」に反しない。ただし条文の「2語」の定義は足りない**

- 鍵を置かない理由(作成側が書き換えて一覧を消す経路)は妥当。ただし案の補足「`guard.json` の鍵の追加そのものが統制の設定の変更の承認を要する」は、鍵を置いても消せないという反論になり、**理由として自己矛盾**する(承認を要するなら経路にならない)。理由は「採用者の設定の差を条文が追認し、採用者ごとに検出の範囲が変わる(一覧の正本の意味が割れる)」へ差し替える。これは正本を既定ブランチの定義の検査とする既存の考え方と整合する
- 言語別の語の一覧は定数として template に置く。方針の「細かい定義を増やさない」は条文・定義の語彙の増加を指し、検出の実装の定数ではない(`SKIP_MARKS` が先例)。反しない。ただし**条文の2語(「未完了を示す印」「検証の呼び出しを持たない追加のテスト」)が、採用者に「自分の言語で何がそれに当たるか」を一意に伝えない**。条文は結果を書く規律でも、採用者が自分の検査(アダプタ7種外の言語)を持つときに従う定義が要る。最低限の定義(「実行しても何も完了しない記述」「テストとして登録され、結果を左右する呼び出しを1つも持たない」)を附属書側の手引きでなく **条文の1文**で持つこと。ここは細かい定義の増加ではなく、規範の意味の確定である
- 用語の衝突: 5.8.5 後段は「印」を **skip・xfail の付与(落ちることを期待する印)** の意味で既に使う。新しい「未完了を示す印」は同じ段落の隣で別の意味の「印」になる。読み手が混同する。別の語(例: 「未完了の記述」「仮実装の語」)にする。語を替えるときは台帳・実装マークの note も揃える

### Q4 保留テスト: **R1 に求めない案に賛成する。ただし「課さないと決めた」の書き方を案より強める**

- 外部の根拠(ImpossibleBench・SpecBench。E2)は研究の推奨で、規程の先例が確認されていない(案が引く外部調査の記述を、私は一次で再確認していない)。新しい義務を課す根拠として足りない。採らない
- ただし理由が「先例が見つかっていない」だけだと、後で先例が出たとき覆す理由が曖昧になる。**覆す条件を ADR-0262 に書く**(例: 保留テストを規程に採った実務の事例、または G-6 基準1 の記録で決め打ちが通った事例が観測されたとき見直す)。「課さないと決めた」と「いまは足りない」を区別できる形にする(コアポリシー)
- H.11 の行の書き方(案「機械では防げない。G-6 基準1 が唯一の層」)は、**「唯一の層」が過剰**。5.8.4 の段階「中」(テスト先行)・自己修正ロック(IMPL-0187)は決め打ちの一部を防ぐ(テストを読み取り専用にするのは外部の推奨の一部と案自身が F-4 で書く)。「唯一」と書くと H.11 が F-4 と矛盾する。「テストの外の入力で挙動を見る層は G-6 基準1 だけ」と**層の範囲を限定して**書く
- 求める結論になった場合は案どおり所有者の確認を要する(候補2)

### Q5 H.2 に「保守性を主張しない」を書くこと: **会議体で足りる(ADR-0051 の適用)。ただし「所有者へ報告する」で閉じるのでなく、ADR に適用であることの根拠を書く**

- ADR-0051 は使いやすさを判定しない決定。保守性の追加は、製品の品質特性を標準が判定しないという同じ線の適用で、新しい範囲を作らない。むしろ書かないことの方が範囲を曖昧にする(C3)
- 私が見る限りの注意点は 2 つ。(1) H.2 の行の「代わりに示すもの」に **技術負債台帳の記録**を置くのは、保守性の代わりではなく、記録の義務の別の目的であり、読み手に「台帳があるから保守性は担保された」と読ませる恐れがある。行は「代わりに示すものは無い。台帳・4指標は保守性を主張する根拠にならない」とした方が、「主張しない」と整合する。(2) 「理解しやすさ・変更しやすさ」と括弧で副特性を書くのは、H.10「品質特性の規格との対応表は作らない」に近づく。括弧を外すか、本標準が定義する範囲に限る(案は 25010 の副特性を並べない=整合と書くが、括弧が実質それを行っている)
- ただし G-6 基準2(挙動を自分の言葉で説明できる)との区別を H.2 の行に書く案は、**主張しないことを説明するのに主張の側の語を持ち込む**ので、一文で足りる(「基準2 は挙動の理解であり、保守できることの主張ではない」)。長く書かない

## 2. その他の論点への意見

### 2.1 条文の置き場(5.8.5 の後の段落の直後)

案は「検証を弱める変更」と別の語として直後に足す。置き場に異論がある。5.8.5 の表は「禁止事項」で、後段の検出の段落は禁止事項3 の検出の材料として位置づく。**未完了の印は禁止事項3(テストの失敗をテスト側の変更で解消する)と無関係**で、同じ節に置くと、読み手は「禁止事項の検出の一種」と読む。節の見出しで範囲を示す規約(#226。節全体に掛かる適用範囲は見出しへ併記)に従い、**新しい小見出しを立てる**(適用: 全リスク区分)。D2 が「リスク区分に依らず出す」と決めたのに、適用範囲の併記が案に無い。`npm run scope:write` の対象になるので、書き漏れると台帳に出ない

### 2.2 EV の識別(EV-A を新しく立てる案)

賛成。EV-0247 の対象を広げない理由(識別子は対象と結びつく)は妥当。ただし EV-A の差し替え条件に、**0.1 の題の語の取りこぼし**と、**処置の記録の (ii) の割合**を入れる。見直し 2027-05 は EV-0247 と揃えるのに賛成

IMPL-A・B の `check=machine` は、0.1 の欠陥が直るまで開示できない。IMPL-B の note に「ファイル単位の近似」を書くだけでは足りない。取りこぼす形(題の語・追加行の外のアサーション・自前の検証)を note に列挙する

### 2.4 E2(附属書C への1文)

賛成。ただし「説明できない複雑さは質問・差し戻しの理由になる」は、G-6 に基準7を足さないまま差し戻しの理由を増やす。手引きは要求事項ではない(ADR-0040 の扱い)ので、**手引きの文を根拠に差し戻してよいのか**を採用者が迷う。「差し戻しの理由」でなく「質問してよい観点」とする。差し戻しの根拠は既存の基準2(理解できないまま承認しない)に置き、手引きはその具体化にとどめる

### 2.5 B1 の ADR への記録

賛成。1点: B1 の「重複の比率を合否に使わない理由が書かれていない(F-5)」を ADR-0262 が補う、は**決定の変更でなく補記**と案は書く。ADR-0137・0159 は採用済みで本文を書き換えられない(CLAUDE.md)ため、補記は新 ADR 側にだけ書き、旧 ADR との対応を明記すること。これは案の方向と同じだが、実装の段で IMPL-0230 の note を書き換えない(旧 ADR を覆す形に見える)よう念を押す
