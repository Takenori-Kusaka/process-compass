## 1. 案に無い重大な欠陥(最優先)

### 1.1 `ASSERTION` は「テスト名の語」を検証と数える

`ASSERTION` は `\b(expect|assert\w*|should|toBe|Equal|Equals|...)\b` を行のどこでも照合する(`:303`)。コメント行だけが `ASSERTION_IN_COMMENT` で別扱いで、文字列は除かない。したがって次は、アサーション無しの空のテストなのに「アサーションあり」と数えられ、一覧に出ない。

- `it('should return the user', () => {})`(`should` が題名にある。Jest・Vitest の慣用で最も多い形)
- `def test_assert_user_created(): pass`(`assert\w*` が関数名に当たる)
- `test('expect nothing', ...)`、`func TestEqualFoo(t *testing.T) {}`(`Equal` が関数名に当たる)
- `# TODO: assert later` は COMMENT_LINE なので `ASSERTION_IN_COMMENT` を見るが、その定義は未確認。コメントの中の `assert` を数えるなら、コメントだけで通る

案の 5.1 は「`isAssertionLine` の数が0のファイル」と書くが、**この数え方が空のテストの典型形を数えない**。IMPL-0204 の削除行の検出では、「消えたアサーション」を対で追うため、この近似が許容できた(題名の語は消えた行と足した行の両方に出て相殺する)。新しい検出では相殺が無く、近似がそのまま取りこぼしになる。表示(「検証の呼び出しの無いテストを検出する」)と実態(題名に should を持つ空のテストは検出しない)が食い違う。

必要な対処(案への修正):
1. 新しい検出専用に、**題名・関数名・文字列リテラル・コメントを除いてから**検証の語を数える。それができない言語がある(構文の分析が要る)なら、その旨を限界の文に出し、「題名の語を検証と数える」ことを開示する。除かずに「検出する」と書くのは不可
2. 少なくとも `should` は検証の語から外す(`expect`・`assert` は呼び出しの形 `\bexpect\(`・`\bassert\w*\(`・`assert ` に絞る)。ただし既存の `ASSERTION` を変えると IMPL-0204 の回帰が動く。案 5.1 は「足すかを実装の段で決める」としたが、**変える方向(絞る)を決める点も要る**。専用の正規表現を持つほうが、既存の IMPL-0204 を動かさず安全
3. `test-check-pr.mjs` の場面に「題名に should/assert/Equal を含む空のテスト」を必ず入れる(案 5.1 の場面の列挙に無い)

### 1.2 ファイル単位の近似の穴(案は限界として開示するが、悪用経路は書いていない)

- 追加行に本物のアサーションが1つでもあれば、同じファイルの10個の空のテストは出ない。AI が空のテストを量産するとき、1つに形だけの `expect(x).toBeDefined()` を付ければ一覧は空になる
- 既存のテストのファイルに空のテストを足す場合、追加行だけ見るので、既存の行のアサーションは数えない。この方向は過検出(安全側)。だが逆に、テストの定義の語が追加行に無い(既存の `describe` の中へ中身だけ足す)と、そもそも対象にならない
- テストのパスの外(`testPatterns` に当たらない場所。`e2e/`・`spec/`・`__tests__` の外のヘルパ・`conftest.py` の類)に置いた空のテストは、未完了の印の検出では「製品のコード」側に回り、テストの定義の語の検出では「テスト」側に入らない。**どちらの検出にも入らない谷間が生じる**。`testPatterns` の定義の正本(`guard.json`)は採用者が持つので、谷間の大きさは採用者ごとに違う。限界の定型の文に「`testPatterns` に依存する」と書くこと
- 作成側が `testPatterns` の外へテストを置けば、既存の IMPL-0204 の対象からも外れる。これは既存の穴で、本件で新しく生じたものではないが、案が「テストのパスの外」を製品側として読む結果、**TODO の検出と IMPL-0204 の間で同じファイルが別の側に数えられる**ことは書いてほしい

### 1.3 未完了の印の「印を避けた書き方」

案は「列挙の外の語」を拾わないと開示する。それは正直だが、抜け道の主要な形は列挙の外の語より、次の3つである。

- コメントの外の語(`raise NotImplementedError` を `raise RuntimeError("todo")` に、`throw new Error("TODO")` を `"not yet"` に)。AI は検出語を避けて書き直す学習をする(5.8.5 後段が「印の書き換えで回避される」と A3 を退けた理由と同じ)。一覧は合否でなくても、**一覧が空であることを「未完了が無い」証跡として読まれる**のが問題で、限界の定型の文が確実に併せて読まれる構造が要る
- ファイルの分割・リネームで「追加行」に見えない形(`git mv` の類。類似度判定で既存の行として扱われると、印を含む既存の行を移した場合は拾わないのは正しいが、大きく書き換えた移動で印が混じると見落とす)
- 既存の行に印が在るまま実装を空洞化する変更(印の無い削除。例: 実装を `return null` に置換)。案が「拾わない」と書く形で、開示済み

## 2. 争点ごとの意見

### Q1: G-6 の新しい義務か。差し戻しまで条文に書くか

- 新しい義務を課す。G-6 の判定者に、確認の材料が2つ増え、確かめられない行がある変更の差し戻し義務が付く。案の「新しい義務は無い」(1.1 表)は弱すぎる。3 節(所有者の方針)の「ほぼ受けられる」も、義務の量でなく様式の数で測っている。ADR-0262 の本文では、**判定者への義務の追加であることを明示**する
- 差し戻しまで書くことに賛成(強い側に寄せる)。理由は表示と実態の一致。既存の「検証を弱める変更」が「確かめる」までしか書かないのは、既存の側の弱さで、`gates/G-6.md` 手順2 が実質の差し戻しを補っているにすぎない。**揃えるなら強い側へ**。ただし既存の IMPL-0204 の条文を同じ ADR で書き換えると採用済みの条文の変更になる。新 ADR で置き換える形(「採用済み ADR の本文は書き換えない」)を踏み、IMPL-0204 の note に「差し戻しの文は IMPL-C で補う」と書く程度にとどめる案を推す
- ただし、差し戻しの根拠は「確かめられない行」で、判定者の主観で変わる。**確かめた結果をどこに残すか**(証跡)が案に無い。案の 3 節は「確認した者の氏名・日付の欄を置かない」とするが、これは記名欄の話で、結果の記録の話ではない。承認レビューの本文に「一覧 N 行を確認、うち台帳の行 K、要らない箇所 M」を書くことを G-6 の判定記録の結果の欄として求めるか、求めないかを決め、求めないなら**「確認したこと」が証跡で確かめられない(IMPL-C = manual。確かめる者: 判定者本人)と開示**する。現案の IMPL-C「delivered check=manual」は、実態は「判定者が読んだ」ことを後から確かめる手段が無い。manual と開示するのは正しいが、delivered と表示するのは強すぎる。`state=delivered` ではなく、既存の G-6 の他の manual 項目と同じ扱いか確かめてほしい(私は確かめていない)

### Q2: 偽陽性と読み飛ばし、節を分けるか、識別子の注釈

- 読み飛ばしの危険はある。偽陽性が多い一覧は、判定者が読まなくなる(アラート疲れ)。特に未完了の印の一覧は、`NotImplementedError`(抽象の基底)で常に埋まる言語がある。**節は分ける**(既存の検証を弱める変更の一覧と混ぜない。混ぜると偽陽性の多い側が正しい側を巻き込む)。0件でも出す定型の文が増えるので、一覧の見出しに件数を出し、0件の節は1行にする
- 識別子の注釈を採らないことに賛成。AI が埋められる点は案のとおり。**ただし裏返しの問題が残る**: 注釈が無い以上、判定者は台帳との突合を自力で行う。台帳が長いと確認が実質できない。これは案が認める「確かめられない行は差し戻す」の運用で吸収できるが、差し戻しの頻度が高いと、採用者は一覧の語を避ける書き方(1.3)へ寄る。この動機を ADR に書いておく(却下の副作用の開示)

### Q3: 設定の鍵を置かないこと、言語ごとの語の一覧

- 鍵を置かないことに賛成。作成側が書き換える経路になる点は監査上の決定的な理由。ただし、**偽陽性を除く正規の手段が無いこと自体が、一覧を無視する圧力を生む**。代案: 鍵は置かず、除外を「G-6 の判定者の確認の結果」として一覧の行ごとに許す(= 現案の運用)にとどめ、除外を恒久化する手段を設けないと ADR に明記する
- 言語ごとの語の一覧を template が持つのは、条文に置かない限り「細かい定義を増やさない」に反しないと読む。ただし 1.1 のとおり、語の一覧は**照合の対象の取り方(題名・文字列の除外)とセット**でないと意味を持たない。語だけを並べて「検出する」とするのは表示と実態がずれる。限界の定型の文に「題名・文字列を除かない場合は、その旨」を出すこと

### Q4: 保留テスト

- R1 に求めることに反対(案どおり採らない)。理由: 研究のベンチマークの推奨で、プロセスの規程の先例が無く、採用者への新しい義務を、実証の無いまま課すことになる(コアポリシーの「重」の領域)。採るなら所有者の確認が要るという案の整理に同意
- H.11 の書き方(「機械では防げない。G-6 基準1 が唯一の層」)は足りる。ただし「唯一の層」と書くと、**5.8.4 の段階「中」以上のテスト先行生成と R1 の変異試験が効かないと読める**。案の 1.3 の本文は3つを並べているので、H.11 の行も3つを並べ、「決め打ちには効かない層」と「効く層」を分けて書くこと。変異試験は決め打ちの実装(テストの入力だけを返す)を殺せないことが多い。それを書かないと開示が過大
- 「採らない」を明記する(保留テストは「課さないと決めたこと」)ことは正しい

### Q5: 保守性の主張外の明記

- ADR-0051 の適用として会議体で決めてよい。ただし**範囲の明記が「保守性の統制を一切持たない」と読まれないよう**、H.2 の行の「代わりに示すもの」に、実際に在る統制(台帳・G-6 基準2 の説明可能性・4指標の傾向)を書いてある点は良い。1つ補う: 「G-6 基準2 は保守性を主張しない」と案は書くが、H.2 の行はその区別を示すと言いながら、行の本文に基準2 の文言が無い。行に入れるか、ADR にだけ書くかを揃えること
- 所有者への報告は案のとおり(適用であり決定は要さない。事後に報告)。ただし、所有者の過去の決定(「守備範囲」)の解釈が割れうる点を、報告に1行書く

## 3. 案の他の点への異論

1. **H.3 の対応づけ(案 2.2)を ADR にだけ書く点**。H.3 の規則「どの主張も支えない検査は廃止の候補」は、判定者が H.3 を見て行う。H.3 の表に書かず ADR にだけ置くと、廃止の議論のときに ADR を読まない者は検査を孤立と見る。対応づけを `impl-targets` か IMPL の note に書く(台帳から辿れる)ほうが、読み手に届く。案は H.3 の行を変えない方針だが、**IMPL-A/B の note に支える主張(C4・C5・C7)を書く**ことを求める
2. **EV-A を E0 で立てて見直し 2027-05 とする点**。差し替え条件が「拾い漏れの事例と一覧の誤検出の件数」だが、1.1 のとおり現行の数え方は既に取りこぼしが確定している。実装の前に作った例で取りこぼしを測らず E0 のまま降ろすと、EV の「実証が無い」と開示した水準を超えて、**既知の欠陥を暫定のまま出荷**する。実装の段で最低限、題名の語の取りこぼしを直してから出荷すること
3. **0件でも定型の文を出すので「止まった検査に気付ける」(案 3 節の第3項)**。定型の文は検査が走らなくても、前の PR の本文からコピーできる。文の存在は検査の実行の証跡にならない。気付けるのは「文が出ない」場合だけで、「古い文が残る」場合は気付けない。IMPL-0204 と同じ残存リスクとして H.11 に一言書く
4. **IMPL-B の note「ファイル単位の近似」だけでは開示が足りない**。1.1・1.2 の「題名の語を数える」「1つの本物のアサーションで他の空のテストが隠れる」「`testPatterns` に依存する」まで note と限界の文に書く。undelivered は立てないとの案(個々の単位の検出を規範に置かない)は、規範を「ファイル単位に書く」ことと対でなければならない。条文が「検証の呼び出しを持たない追加のテスト」と書き、実装が「アサーションの語が0件のファイル」であれば、条文と実装の間に表示の差がある。**条文を「検証の呼び出しを持たないテストの追加を含むファイル」と実装の粒度に合わせるか、個々の単位は undelivered(partial)と開示するか**を決めること。私は前者(条文を実装に合わせる)を推す
5. **A2 の「G-5 の合否に使わない」の維持**に賛成。ただし、**合否にしない一覧は、G-6 が無い構成(R3 など)で誰も読まない**。G-6 を実施しないリスク区分の変更では、この一覧は出ても読む者が居ない。案の 1.5 の D2「R2・R3 でも出す」は、読み手が居る前提。R3 に G-6 が無いなら、一覧は未読のまま出る。D2 の効果の主張を弱め、「R2・R3 では判定者の有無に依る」と書くこと(未確認: R2・R3 での G-6 の実施の有無は私は確かめていない)

## 6. 審議の重さについて

私の指摘 1.1 は実行で確かめた欠陥(コードを読んだ。実際に `it('should ...', () => {})` を流して確かめてはいない。確かめるのは実装の段の最初の仕事とする)。重大度は「高」(表示と実態の食い違い)。重へ上げる条件には当たらないが、**実装へ進む前に、この点を実行で確かめる**ことを条件に付ける。
