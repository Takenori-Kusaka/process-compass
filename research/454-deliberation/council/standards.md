# #454 会議体 意見書: 規格の委員

- 日付: 2026-11-27。立場: 規格策定機関の目(結果と証跡を求め手段を指定しない。閾値の根拠。規格との整合)
- 読んだもの: `decision-draft.md`、`external.md`、5.8.5 の後の段落(`human-ai-boundary.md:1240-1245`)。`internal.md` と template の実物(`check-pr.mjs` の `ASSERTION` など)は読んでいない。その点は「未確認」と書く
- 規格の本文(25010・5055・29119)は外部調査も未読である。規格を引く主張は、すべて二次情報に依る

## 総評

案の骨格(A2・B1・C2・D2・E2。新しいゲートと基準を足さず、既存の型の拡張で受ける)には賛成する。ただし、規格としての書き方に欠陥が4つある。(1) 条文の語が実装の粒度と食い違う。(2) 採らない理由の一つが、規格の読み方として弱い。(3) H.2 の「代わりに示すもの」が過剰な主張になっている。(4) 適用範囲の併記が落ちている。いずれも案の直しで足りる。

## 争点ごとの意見

### Q1 差し戻しまで条文に書くか: 揃える。強い側へは寄せない

- 既存の 5.8.5 の後段(`:1240`)は「必須の確認事項として示す」までで、差し戻しを書かない。新しい段落にだけ「確かめられない行がある変更は差し戻す」を書くと、読み手は「弱める変更の一覧は差し戻しを伴わない」と読む。同じ型の2つの一覧で義務の強さが割れるのは、規格として避ける
- 必須の確認事項は、確かめられないまま承認しない、を含意する。G-6 は承認の関門だからである。差し戻しの文は条文でなく `gates/G-6.md` と附属書C に置けば足りる(手順は手引きへ、という方針とも合う)
- 強い側へ寄せるには、既存の IMPL-0204 の条文を改める必要がある。これは意味を変える改訂で、編集の指摘に当たらない。本件の範囲を越える
- 結論: 新しい段落は「必須の確認事項として示す」までにする。確かめられない行の扱いは、2つの一覧に共通の1文を手引きへ置く。この結論は、G-6 の承認が確認の欠けを許さない定めが第4章に在ることを前提にする。その定めは未確認なので、突合で確かめてほしい

### Q2 一覧の読み飛ばし: 節を分ける。偽陽性の実測を採用の条件にする

- 節を分けることには賛成する。性質が違うからである。弱める変更は既存の検証の減少で、新しい2種は追加の中身の欠けである
- 読み飛ばしの危険は、偽陽性率で決まる。外部調査は、条件の多い品質ゲートが無視されること(FND-0021)と、アサーション検出の誤分類が多いこと(Panichella ら)を示す。案は偽陽性の形を列挙するだけで、率を見ていない
- 特に Go は、`if got != want { t.Errorf(...) }` の形が主流で、`assert` の語を使わない。`isAssertionLine` が `t.Error`・`t.Fatal` を数えるかは未確認である。数えないなら、Go の採用者では「検証の呼び出しの無いテスト」が常に出る。これは致命的な読み飛ばしの原因になる
- 求めること: 採用の前に、既存の実装の試行(例: 試行用リポジトリや template の試験の事例)で、7言語の典型的なテストを通し、誤検出の件数を記録する。EV-A の差し替え条件に書くだけでなく、導入の条件にする
- 識別子の注釈(1.8)を採らないことには賛成する。理由は案のとおり(AI が埋められる)

### Q3 設定の鍵と言語差

- 条文に語の一覧を置かず template が持つことは、「細かい定義を増やさない」に反しない。定義でなく実装の手段だからである。規格の書き方としても正しい(29119 でも、試験完了基準は戦略で定め、検出の語は規格に書かない)
- 鍵を置かない理由(5.2)は弱い。本標準は、一覧の正本を既定ブランチの定義で走る検査の出力とすると既に定める(`:1245`)。検査が既定ブランチの側の鍵を読むなら、PR の変更で鍵を書き換えても、そのPRの一覧には効かない。鍵の変更は、それ自体が差分に出る。この読みが実装で成り立つかは未確認(`guard.json` の読み出し元を見ていない)
- 結論: 鍵は置かない案に反対はしない。ただし理由を「PR 側が書き換えて消せる」から「導入時の誤検出の実測を見てから決める」に改める。ADR-0262 の「課さないと決めたこと」に、見直しの条件(誤検出が多く、読み飛ばしが起きた場合に、既定ブランチ側で読む鍵を検討する)を書く。「決めた」と「未決」を区別できる状態を保つ

### Q4 保留テスト: 求めない。ただし H.11 の書き方を直す

- 求めない案に賛成する。理由は2つある。(1) 保留テストは手段の指定であり、結果として書き直せない。書くなら「実装の担い手が見ない検証が在ること」になるが、その条件を満たす構造を採用者が組める標準的な形が無い。(2) 根拠が E2(研究のベンチマーク)で、規程の先例は未確認である
- 採らない理由の表現を直す。「外部に先例が見つかっていない」は不在の確認であり、調べた範囲を限定しない書き方は避ける。「調べた範囲(2026-11-27 の台帳と検索)で見つからなかった。見直しは先例が現れた場合」とする。コアポリシーの「却下は成果である」に沿い、見直しの条件を付ける
- H.11 の文言「機械では防げない。G-6 基準1 が唯一の層」は、案の 1.3(歯止めは G-6 基準1、5.8.4 の段階「中」以上、R1 の変異試験)と食い違う。「唯一」は事実として誤りになり得る。表示と実態の食い違いである。「機械の合否では防げない。残る層は、G-6 基準1、5.8.4 のテスト先行とロック、R1 の変異試験。R2・R3 では前2者だけ」と書く
- 補足: 5.8.4 のロックは、自己修正の間のテストの書き込みを遮断する。これは ImpossibleBench の推奨の一部である。実装の担い手からテストを隠すものではない。「一部が既に在る」の書き方は、隠す構造が無いことを併記する

### Q5 H.2 に保守性の行: ADR-0051 の適用として会議体で決めてよい。所有者へは報告する

- H.2 は「主張しないこと」の開示で、採用者に新しい義務を課さない。ADR-0051 の線の適用と読める。ADR の原則(守備範囲)を広げるのではなく、既存の範囲を明記する行である。議長の案(報告はする)に賛成する
- ただし行の文言に欠陥がある。「代わりに示すもの」の欄に、技術負債台帳と4指標の傾向を置くと、これらが保守性の証跡のように読める。台帳は妥協の記録で、保守性の測定ではない。4指標は adopter の傾向の確認である(IMPL-0230)。H.2 の列の意味が「主張しない代わりに示すもの」なら、「保守性の証跡ではない」と明記するか、欄を「関連する記録(保守性の証跡ではない)」に改める
- 25010 の副特性を並べないことに賛成する(H.10 の対応表を作らないこととの整合)。ADR のコンテキストで「定義する規格がある(本文未読)」とだけ書く案も妥当である。下位特性の名称(モジュール性ほか)を ADR に書く場合は、二次情報であることを併記する

## 案に無い欠陥

1. **条文と実装の粒度の食い違い(高)**: 条文の語は「検証の呼び出しを持たない追加のテスト」だが、実装はファイル単位の近似である(1.2・5.1)。1つのファイルに10件のテストが在り、1件だけが検証を持つ場合、ファイルは出ない。条文の読み手は「テスト単位で検出される」と読む。表示と実態の食い違いである。条文の語を、実装が決められる粒度へ合わせる。例: 「追加行にテストの定義が在り、検証の呼び出しが無いテストのファイル」。IMPL-B の note だけで開示する案では足りない。条文が過大に読める
2. **適用範囲の併記(中)**: 案は一覧をリスク区分に依らず出す(D2)。隣の変異試験は R1 だけである。5.8.5 の節に新しい段落を足すと、読み手は変異試験の範囲(R1)を引き継いで読みうる。#226 と ADR-0039 に従い、段落に「適用: R に依らない」を併記する。見出しでなく段落の中でもよいが、別の段落に限定を置かない
3. **B2 の理由に使う規格の読み方(中)**: 「規格も合格水準を定めない。標準が閾値を置くと規格より踏み込む」は理由として弱い。25010 は品質モデルで、5055 は弱点の数え上げの規格である。どちらも、プロセス標準の関門の閾値を定める位置に無い。規格が定めないことは、標準が定めてはならない理由にならない。かつ、外部調査は規格本文を読んでいない。ADR-0262 の決定3 は、この理由を外し、閾値の実証が E0〜E1 であること(Sonar の既定値は調整の産物)と、3条件の条件1 を満たさないことだけに拠る。規格に触れるなら、根拠水準マークで「本文未読」を開示する
4. **H.3 への対応づけの置き場(中)**: 2.2 は、一覧が支える主張(C4・C5・C7)を ADR にだけ書く。H.3 末尾は「どの主張も支えない検査」を廃止の候補にする。廃止の判断を行う改善サイクルが読むのは H.3 であり、ADR を読むかは未確認である。H.3 の表に足すと「足さない」の読み方が割れる、という懸念は分かる。代案: H.3 の表は変えず、5.8.5 の新しい段落の末尾に、支える主張の番号を1句で書く。これなら、H.3 の規則に反さず、読む箇所で対応が見える
5. **語の衝突(低)**: 「検証」は本標準で広い意味(検証と妥当性確認の検証)を持ちうる。「検証の呼び出し」は、期待結果の照合(アサーション)を指す。語彙の台帳との突合が要る。突合の結果によっては「期待結果の照合」へ改める
6. **29119 の扱い(低)**: 外部調査は、29119 がテストの十分性(オラクルの質)を直接定める箇所を確認できなかった。案はこれと矛盾しない(十分性の水準を置かない)。ただし一覧が0件でも、十分性の証跡にならない。この旨を H.11 の行に書く。「検証の呼び出しが在ること」は、検証が十分であることを意味しない。形だけの照合への最適化(Goodhart、台帳 TH07)は一覧では防げない

## 採らない案の表への異論

- 「保留テストを R1 に求める」「偽陽性を除く設定の鍵」: 上のとおり、理由の文言と見直しの条件を直す。採否は変えない
- 「重複・複雑度の閾値で合否(B2)」: 理由から「規格との比較」を外す(欠陥3)。採否は変えない
- 「checked coverage(D3)」: 「降りない規定になる」に加え、外部調査が相関の定量を未確認と書く点を理由に残す。他の理由と並べ、E 水準の開示を付ける
- 表に無い案として、**「一覧を出すが、G-6 の必須の確認事項にしない(参考表示のみ)」**を記録に足す。却下の理由: 参考表示は、確認の結果が記録に残らず、判定者が読まない運用を許すため。却下を明記しないと、「書かれていない」と「課さないと決めた」が区別できない
- 表に無い案として、**「条文を1語(『未完了の印』)だけにして、アサーション無しのテストは手引きだけに置く」**がある。新しい義務を最小にする案だが、最小の変更という動機は採否の理由にならない。信頼性の軸では、規範にあるほうが IMPL で追える。この案も、却下として記録する

## 判断軸(信頼性)での結論

- 賛成: A2、B1、C2(文言を直す)、D2、E2、ADR-0262 の立て方、保留テストを求めない
- 条件付き賛成: 一覧の導入(7言語の誤検出の実測を条件にする)、鍵を置かない(見直しの条件を ADR に書く)
- 直し: 条文の語の粒度(欠陥1)、適用範囲の併記(欠陥2)、B2 の理由(欠陥3)、H.2 の欄(Q5)、H.11 の「唯一」(Q4)
- 重への引き上げや所有者の決定を要する点は、見つからなかった
