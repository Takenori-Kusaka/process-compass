## 争点ごと

### Q2(主管): 一覧の偽陽性と読み飛ばし

**危険はある**。既存の `weakeningFindings` は対象が少なく(削除・skip・xfail・テストだけの変更)、一覧が出れば意味がある。新しい2種は件数の桁が違い得る。次を【推測】する。

未完了の印(`INCOMPLETE_MARKS`)で、案の列挙のまま実装すると出やすい誤検出:

1. 製品のコードの領域が「テストのパスの外のファイルの追加行」すべてになる(案 1.2 の表)。文書(`.md`)・設定(`.yaml`・`.json`)・ロックファイル・生成物・ADR の本文の `TODO` の語が全部入る。標準の文書リポジトリでは `TODO` の語の登場自体が多い
2. 製品の意味で `TODO` を使う実装(タスク管理アプリの `Status.TODO`、列挙子、文字列)。案は「行注釈の中に限って読む」とするが、行注釈の判定は言語ごとに違い(`//`・`#`・`--`・`/* */`・`<!-- -->`)、既存の `COMMENT_LINE` は行頭だけを読む。行末の注釈は拾えず、文字列の中の `//` は注釈と誤る
3. **移動・改名・整形の差分**: ファイルの移動、関数の移動、インデントの変更(フォーマッタ)は、`-U0` の差分では「追加行」に既存の印がそのまま出る。案の「拾わない形: 既存の行に在る印」は、追加行だけを見る方式では実現できない(同じ PR の削除行と突き合わせないと区別できない)。大きなリファクタの PR で一覧が溢れ、確認の義務が「全部読めない」に変わる
4. 抽象の基底・インタフェース・プロトコルの `NotImplementedError`(案が自認)。AI が新しい基底クラスを足すたびに出る

検証の呼び出しの無いテスト(`noAssertionTests`)で出やすい誤検出と見逃し:

1. **誤検出**: 「追加・変更したテストのファイル」を対象にし、追加行に定義の語が在って追加行のアサーションが0件、で出す(案 1.2)。テスト名の変更・引数の整形・既存のテストの先頭行だけを触る編集で、アサーションの行が差分に出ない場合は**必ず**出る。リファクタ系の PR で常時鳴る
2. **誤検出**: `ASSERTION`(:303)は `verify(`(Mockito)、`pytest.raises`、Rust の `#[should_panic]`(`should_panic` は `\bshould\b` に当たらない)、Kotest の `shouldBe`、Go の「エラーが出ないこと」だけを確かめる煙試験、`cy.should` 以外の E2E の待機を数えない。案 5.1 も `verify(` などを足すかを「実装の段で決める」と保留している。**保留にせず、条文の前に決める**必要がある。数えない形の既知の一覧が、限界の文に出る形で偽陽性の主因になる
3. **見逃し(重大)**: ファイル単位の近似は、「5つ追加して1つだけ空」を拾えない。AI が複数のテストをまとめて足す現実の形に対し、**一番有害な空のテストが、同じファイルの別のテストの `expect` に隠れる**。限界の文に書くだけでは、「0件=空のテストが無い」と読む採用者が出る。0件の文は「ファイルに1つもアサーションが無い場合だけ拾う」と、**不在の意味を狭く言い切る**形にすべき
4. アサーション逃れ: `assert True`・`expect(x)` だけ、`expect(...).toBeDefined()` は数えられて通る。これは弱いアサーションで案が既に認めている(B1)。一覧が0件でも安心できない旨を、G-6 の判定者向けの手引きにも一文入れる

**節を分けるか**: **分ける**。既存の「検証を弱める変更」の節と新しい2つの節を同じ節に混ぜると、件数の多い新しい一覧が、件数の少ない既存の一覧(削除されたアサーション・skip)を埋める。順序は、現行の既存の一覧を先に、新しい2つを後ろにする。各節の先頭に件数を出し、**1行に圧縮した0件の文**にする(`renderG6Material` が0件でも限界の文を3つ・5つ出すと、読まれない節が増えて固定の文が壁になる)。限界の定型の文は、1つのブロックにまとめて末尾へ置く案を採る

**一覧の上限**: 案は件数の上限を課さないとしている(採らない案の表)。同意する。ただし、**表示の上限**(ファイルごとに3行まで示し、残りは件数だけ)は別の話で、判定者が読む量の問題である。件数を判定の入力にはしない、表示だけを丸める。この区別を条文でなく手引きと実装に置く。丸めた分を「確かめられない行」と読ませない規則も要る

**1.8(識別子の注釈)を採らないことへの同意**: 同意する。現場で `pit-in: debt id=` を足すのは、AI が埋めて一覧から消える(案の指摘どおり)。一方、**台帳と突き合わせる判定者の手間は現場の費用になる**。代替の軽い案として、一覧の行に台帳の `D-NNN` を判定者が書く義務は課さないまま、**技術負債台帳の差分が同じ PR に在るか**だけを、一覧の見出しに示す(PR が台帳を触っているか。決定可能。合否にしない)ことを検討に値する。IMPL を増やさない場合は不採用でもよい

### Q1・Q3・Q4・Q5 への現場の意見

- **Q1(差し戻しまで条文に書くか)**: 現場の意見は、**強い側(差し戻しまで書く)に寄せる**。理由は、「確かめる」までしか書かないと、一覧を見て承認した記録だけが残り、現場では「読んだ」で足りる。ただし差し戻しの対象は「確かめられない行」であり、**偽陽性と分かった行は確かめた結果になる**ことを手引きに明記する。そうしないと、偽陽性の多い一覧が差し戻しの山になる
- **Q3(設定の鍵と言語の差)**: 鍵を置かない案に賛成。ただし、現場の偽陽性の主因は言語ごとの書式の差なので、**言語ごとの語の一覧は template の定数に必要**。条文でなく定数と限界の文に置く前提なら「細かい定義を増やさない」には反しない(採用者が読む場所が template の定数だけになる)。`ASSERTION` の拡張(`verify(`・`raises`・`should_panic`・`shouldBe`)は、既存の IMPL-0204 の削除行の検出に効くので回帰を流す、という案の記述は正しい。**決めずに残さないこと**
- **Q4(保留テスト)**: 求めない案に賛成。R1 でテストを実装の担い手から隠す運用は、現場では担い手の分離・環境の二重化が要り、小規模の体制(1〜2名と AI)では実行できない。H.11 の書き方は「機械では防げない。G-6 基準1 が唯一の層」より**「人の確認だけが残る層である」**と書き、**その確認が効いている実証は無い**ことを根拠水準マークで開示する。「唯一の層」は、変異試験(R1 の弱いアサーション)の効く範囲を弱く読ませる
- **Q5**: 現場の専門外。ただし、現場の読み手は「主張しない」と書かれていれば区別できる。範囲の明記なので決める側の判断に任せる

## 案に無い欠陥・代案

1. **誤検出の主因を先に潰す**: 製品のコードの未完了の印は、**拡張子で絞る**(ソースのコードだけ。文書・設定・ロックファイルを除く)。生成物は既存の `GENERATED_MARK`(:303 付近)を使う。同じ PR の削除行に同じ本文が在る追加行は一覧から除く(移動・整形の対策)。この3つは決定可能な条件で、IMPL の本数は増えない。**これが無いと A2 は現場で鳴りっぱなしになる**
2. **「変更したテストのファイル」を「新しいテストの定義の行が追加されたファイル」へ狭める**: 定義の語が追加行に在り、**同じ語が削除行に無い**(名前の変更でない)ものだけを数える。リファクタ系の誤検出を減らす。案の「追加・変更したテストのファイル」は広すぎる
3. **ファイル単位の近似の見逃しを、定型の文でなく名前に出す**: 一覧の見出しを「アサーションの語が1つも無い追加のテストのファイル」にする。「検証の呼び出しの無いテスト」と書くと、個々のテストの単位まで見たと読まれる(5.3 の IMPL-B の note に書くだけでは足りない)。条文の語(案 4 節の「検証の呼び出しを持たない追加のテスト」)も同じ読み違いを起こす。**条文の語を「アサーションの語が1つも無い追加のテストのファイル」へ変える**か、近似であることを条文に1句入れる
4. **適用の見出し**: CLAUDE.md の「適用範囲の書き方」により、新しい段落が R1〜R3 すべてに掛かる(案 D2)なら、見出しへ併記が要る。**R3 の確認の軽さ**を考えると、「各行を確かめて差し戻す」まで R3 に求めるかを明記する。R3 は表示のみで、判定者の確認の義務を R1・R2 に限る案もあり得る(D2 の「リスク区分に依らず出す」は表示の話で、確認の義務の話と別にできる)。会議体で議長が決める
5. **0件の文の出し方**: 現状の `renderG6Material` は0件でも限界の文を出す型。追加の2節が各々長い限界の文を持つと、一覧が空の PR でも G-6 の材料が長大になる。**1つの限界ブロックへ統合**して、節ごとに1行(0件)にする
6. **実装の段での確認事項**: 5.1 の「決めるかを実装の段で決める」が多い(`ASSERTION` の拡張・Rust の `#[test]`・台帳の観点)。裁定に持ち込まず、実装の段へ丸ごと移すと、偽陽性の許容の水準が決まらないまま入る。少なくとも `ASSERTION` の拡張は、IMPL-0204 の回帰で影響を確認する条件を裁定に書く

## 採らない案の表への異論

- **「偽陽性を除く設定の鍵」を採らない**: 賛成。ただし理由が「作成側が鍵で一覧を消す」だけでは弱い。鍵が `guard.json`(統制の設定の変更の承認を要する)に在るなら、AI が単独で書き換えられない。**本当の理由は、鍵を足す採用者の手続・保守の負荷と、鍵が増えて一覧の意味が採用者ごとに変わること**(採用者間で「0件」の意味が揃わない)。理由の書き換えを提案する。結論は変わらない
- **「未完了の印の件数の上限」**: 賛成。ただし**表示の丸め**とは別である旨を表に足す(上のQ2)
- **「保留テストを R1 に求める」**: 賛成。理由に「小規模体制では担い手の分離が実行できない」を加える
- **表に無いが記録すべき採らない案**: 「一覧に出ない確認事項(0件)の記録を判定者に求める」(記名の欄に近い)。採らない。0件の文が出ることで足りる
- 既存の「検証を弱める変更」の節を、新しい2つの節と**同じ節に混ぜる案**を、表に採らない案として足す(上のQ2)
