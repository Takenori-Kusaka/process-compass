## 1. 立場と、全体の見立て

1. **外部の規格の型に照らすと、4 件のうち 2 件は「標準が世の中の型より遅れている」、2 件は「起票の案が世の中の型から外れている」**。遅れているのは #255(下方トレースを設計・計画の段で見ない。S0 ではどこでも見ない)と #256 の一部(未確定事項の扱いが様式の注記にしかない)。外れているのは #257 の「代替案の必須化」(規格・欠陥報告・SARIF のどれも課さない)と #258 の「往復の禁止」(規格・ベンダー・OSS の方針のどれも禁じない)
2. **#255 は判定基準の表に行を足す形で採る**。ASPICE SWE.2・SWE.3、DO-178C、ISO 26262 は下方の網羅を設計の段で求め、CMMI REQM SP1.5 は計画と要求の整合を名指しする。Spec Kit は同じ時点(タスク生成後・実装前)で同じ数を出す。一方、規範文書に「対応の有無を数える独立の手続」の先例は無く、外部の根拠は E1 にとどまる。確認方法の段落(ADR-0051 型)は ADR-0048 決定3 で KB へ降りないので、判定者が差し戻す基準を持たない現状を直せない
3. **#256 は「前提」を外部の語に揃えて定義し、観測済み / 想定の標識は課さないと明記する**。GSN・PMBOK は前提を「立証しない言明」と定義し、検証状態の欄を持つ様式の先例は無い。標識は `CB` L64 の破れ方と同じ形で破れる。代わりに、未確定事項の解消を判定基準の表へ上げる(NASA の TBD/TBR と同じく、確かめていないものを「確かめた」の側に置かせない)
4. **#257 は規格の finding の型(所在 + 照らした基準 + 見た事実)で採り、代替案は課さないと明記する**。SRC-0002 の代替案は検証器が持つ正解の候補であり、原典 §5 は「列挙できない検査は知っていることだけを報告すべき」と書く。代替案の必須化の根拠に使えない
5. **#258 は往復を規制しないと明記し、既存の入力の分離(3.5.3・H.4 条件2)が往復の 2 巡目以降にも掛かることだけを書く**。DO-178C・IEC 61508 の「独立」は責任の分離であり、多様性(異なる系統)は別の技法である。Knight & Leveson(1986)以来、独立に作っても独立に故障しないことが知られている。系統の異質性は「求めない」と書き、「推奨しない」までは書かない(測定の向きが割れている)

## 3. 論点ごとの詳細

### F-1 G-4 の時点で受入基準 → タスクの網羅を見るか

**判定: 採る(1A)。**

まず現行の読みを確定する。`GC` L97「判定者が評価するのは、当該ゲートの判定基準と、全ゲート共通の通過条件だけです」、L106「当該ゲートの判定基準に無い懸念 | 判定前の非同期コメント期間。基準に加えるなら本章の改訂」。G-4 基準2 の文は「タスク分解の粒度が1タスク=1レビュー単位」で、確認方法の括弧も「1タスクのPRが独立レビュー可能なサイズ」と粒度に限る。**現行の文言では、G-4 の判定者は「タスクの無い受入基準」を理由に差し戻せない**。これは #255 の「欠落」の確認であり、決定の記録に書く。

規格に照らした理由。

- **下方(上位 → 下位)の網羅を、テストより前の段で求めるのが規格の型である**。ASPICE 4.0 SWE.2 BP3(アーキテクチャ ↔ ソフトウェア要求)、SWE.3 BP4、DO-178C の要求 ↔ 設計、ISO 26262 の「realization in the design」、IEC 62304 §5.3.6 の注記(いずれも二次資料・公開プレビュー)。本標準が受入基準の側から数える箇所は G-7 基準1 と附属書E E.5 順1 だけで、どちらも実装の後である。**S0 は G-7 を省略する**(`tailoring-guide.md` L433、確かめた)。全ステージで適用されるゲートで受入基準の側から数える箇所は 0 である
- **規格の「下位」は工学の成果物で、作業のタスクを名指しするのは CMMI REQM SP1.5 だけである**(二次資料)。ただし本標準の実装計画は「変更の対象パス」(テンプレート L9・L16)を持ち、実行環境の書き込み範囲を決める。タスクは設計の要素への割当を兼ねる。ASPICE SWE.2 型の先例に当たると読める(survey-291-1 問い2 への私の答え)
- **実務の型も同じ時点で同じ数を出す**。Spec Kit `/analyze` は tasks の生成後・implement の前に「Requirements with zero associated tasks」と「Coverage % (requirements with >=1 task)」を出す(PR #491 と現行 main で確かめた)
- 外れる点: 規格・ツールのどちらにも「対応の有無だけを数える独立のゲートの基準」の先例は無い(FND-0107)。Spec Kit は勧告にとどめる。これは置き方(F-2)の論点であり、見るか否かの論点ではない

選ばなかった案。

- 1B 見ない(現状維持): S0 で受入基準の側の網羅がどこにも出ない。判定者が差し戻す基準を持たないままになる。後段の G-7 で同じ欠落が「テストの無い受入基準」として出るのは S1 以上に限られ、しかも合否にせず開示へ回る(`GC` L699)
- 1C 課さないと明記する: 課さない理由として挙がる 3 つ(後段で足りる・束と両立しない・タスクは工学の成果物でない)は、それぞれ S0 の省略、F-2 の両立の整理、変更の対象パスの役で崩れる

Filetto の事例(問い1)について: Issue 本文の文は「受入基準 → タスク」とも「前提 → 受入基準」とも読め、原文(254 系メモ)は履歴に無い。**本判定は Filetto の事例に乗らない**。乗るのは規格の時点の型と、S0 の空白という標準の内部の事実である。

根拠水準: E1(規格の規範は間接。タスクを名指ししない)。暫定マークを付ける(F-2 に併記)。

### F-2 置き方・正当にタスクを持たない受入基準・「束につき 1 Task」

**判定: 採る(2A + 3B)。**

文の案(`GC` G-4 の表に行を足す。表の升は体言止め、確認方法は 1.7.3 の語彙の制約の外の記述):

選ばなかった案。

- 2B 基準2 の確認方法へ足す(ADR-0051 型): 上記のとおり降りない。ADR-0051 決定2 は G-2 基準1(受入基準の形式)の確認で価値 → 受入基準を見る置き方で、基準の文が「受入基準」を対象にしている。G-4 基準2 は粒度の文で、網羅を足すと別の問いが入る

- 2F G-5 の検査: G-5 は PR の段で、G-4 の承認より後に走りうる。計画の承認の時点で欠落を止められない
- 2G G-7 基準1 の前倒し: G-4 の時点でテストは無い。テストの未作成を G-4 の理由にすると ADR-0036・IMPL-0010 に反する(テンプレートの G-4 スキル L22 も同じ)

### F-3 識別子の 3 体系・G-7 基準1 の記述と実装の差・G-2 基準1 が降りていないこと

**判定: 採る(識別子の要件)+ 本 Issue で直す(G-7 の記述)+ G-2 は表外の開示を確かめる。**

### F-4 テンプレ1 の前提で「観測で確かめた / 想定」を区別するか

**判定: 課さないと明記する(A1-5)。**

文の案(第6章 テンプレ1 の前文。主語「本標準」の文は 1.7.2 により課さないことの表明): 「本標準は、機能仕様の前提に、観測で確かめたか否かの標識を求めません。前提は、立証せずに置く言明です(第1章 1.4)。観測で確かめた事項は前提ではありません。受入基準、または依存する外部の事実として、確かめた記録の所在とともに本文へ書きます。」

理由。

- **語が外部と逆になる**。GSN 第3版「意図的に立証しない言明」(FND-0240)、PMBOK「証明や実証なしに真とみなす要素」(FND-0242)。「観測で確かめた前提」は、これらの定義では証拠で支える主張の側に移る。前提の欄の中に検証状態を持つ様式の先例は確認されていない
- **標識は `CB` L64 の破れ方で破れる**(確かめた)。「参照する側が標識を読まない」「標識の付与そのものが自動になる」「未検証の記述が量で上回る」。案件層は G-2 基準3 の登録先そのもので、同じ基盤である。L64 の却下の出典 ADR は辿れない(F-15)が、却下の理由の文は本文にあり、覆す材料は調査に無い
- **#256 の懸念(AI が推測した既定値が前提へ流れる。Spec Kit の informed guess、HiL-Bench FND-0112)への答えは既にある**。前提は案件層への登録を経ないと G-2 基準3 を満たさず、案件層への書き込みは PR で文脈オーナー(人)が承認する(`CB`「文脈の変更も PR で行う」「承認は文脈オーナー=人間」、確かめた)。誰がいつ承認したかは変更履歴で示す(L72)。ラベルではなく承認の記録で示すのが本標準の型であり、安全分野の型(ISO 26262 SEooC の AoU を統合する側が妥当性確認する。二次資料)とも、ラベルで「確認済み」を宣言しない点で一致する

選ばなかった案。

- A1-0 現状維持: 「書かれていない」と「課さないと決めた」が区別できない
- A1-1 列を足す: 上記の 3 点。加えて、効果の測定が無い(FND-0110)
- A1-2 未観測の前提を未確定事項へ回す: 前提は定義上すべて未立証で、全件が未確定事項になる。未確定事項は G-2 の通過前に解消する(F-5)ので、前提という欄が成り立たなくなる。NASA の「前提はベースライン化の前に確認すべき」(FND-0241)は、値の TBR とは別に、前提を確認の対象として残す形であり、前提の欄を消す根拠ではない
- A1-3 所在の欄が空なら想定と読む: 所在の欄が埋まった行は「前提ではない事項」であり、上の文案のとおり本文へ移すほうが語と整合する
- A1-4 テンプレ10 の規律を案件の前提へ及ぼす: テンプレートは案件の前提を台帳へ混ぜないと明記し(`10-assumption-ledger.md` L7)、ADR-0018 決定8 は評価の軸の違いで統合を退けた。テンプレ10 の規律(劣化を観測で定義)は、標準の前提が運用中に崩れることを観測するための仕組みで、案件の前提の妥当性確認とは時点が違う。非対称は意図したものとして、上の文の中で前提の扱いを示せば足りる

根拠水準: 課さないことの判断は E1(外部の定義と先例の欠如)。見直しの材料: G-2 を通過した後に崩れた案件の前提の件数と、その前提が承認の記録を持っていたか。暫定マーク: `暫定 EV-NNNN / 見直し 2027-10`。

### F-5 G-2 基準3・未確定事項・ID 併記の食い違い

**判定: 採る。**

- **未確定事項を判定基準の表へ上げる**。現状、「G-2/G-4 通過には解消が必要」は様式の中の注記(`DT` L399、確かめた)にしかない。1.7.2 は注記を規定として読まない。ADR-0048 決定3 により KB へも降りない。様式の注記にある要求は、要求として効いていない。文の案(G-2 の表):

  | --- | --- | --- |

- `q6`「前提が崩れていることを理由に、判定を機械的に停止してはなりません」は標準の前提の台帳の規律で、仕様の未確定事項には掛からない。未確定事項は件数で機械が止めるのではなく、判定者が基準6 で判定する(機械は件数を示す)

選ばなかった案: A2-0 現状維持(注記の要求が効かない)。A2-2 観測の記録の所在を数える(F-4 で標識を課さないので対象が無い)。A2-4 基準3 は登録に限ると明記(ID の対応が見えない穴が残る)。

根拠水準: 未確定事項を表へ上げることは、標準の内部の整合(ADR-0036・0048、1.7.2)から導く判断で、マークを要しない。

### F-6 語「前提」の定義

**判定: 採る(A3-1)。**

文の案(`OV` 1.4 の表に行を足す): 「| 前提 | 立証せずに真とみなして置く言明。崩れたときに影響を受ける対象を併せて書く。ゲートの開始の条件を指す『前提条件』とは別の語である |」

- GSN 第3版・PMBOK と揃う。標準が自ら置く前提 A-T1〜A-K3 も、立証せずに置き、運用中の観測で劣化を確かめる対象であり、同じ定義に収まる
- 「前提条件」(ゲートを開始するために整っている状態)は、標準の中で別の意味で使われている(`GC` L31)。注記で分ける
- 選ばなかった案: A3-0 定義なし(4 つの意味の混在が残り、F-4 の課さない理由が語に依れない)。A3-2 依存と前提に分ける(29148 の「前提と依存関係」の語義を原典で確かめていない。IEEE 830 型の雛形は対の語として並べるだけ。分ける根拠が無い。テンプレ1 の見出し「前提・依存」はそのままでよい)。A3-3 課さないと明記(定義しないと F-4 が語義に依れない)
- 根拠水準: 語の定義であり、マークを要しない

### F-7 根拠水準マーク(ADR-0026)を案件へ課すか。観点7

**判定: 課さないと明記する(B1)+ 観点7 を本 Issue で直す。**

文の案(`OV` 1.7 の末尾、1.7.5 の後へ節を足すか、1.9 に置く): 「本標準は、根拠水準のマーク(E0〜E3)を、本標準を適用する者の文書に課しません。マークは、本標準の記述の根拠の強さを読者へ開示するものです。附属書I の導入前の検証の記録に書く根拠の水準(要件⑥)は、この例外ではなく、検証の結果の一般化を限るための記載です。」

理由。

- ADR-0026 のコンテキストは「本サイトの規程には、実証に基づかない値が多数含まれます」で、対象は標準自身である(確かめた)。マーク規約は `community/`(プロジェクトの運営規約)にある
- #290 E-11 と 1.7.5 は「本標準が自ら行う作業を採用者へ課さない」と決め、理由を「列挙が十分かを記録で判定できず」とした。マークも同じで、付け忘れを機械で検出できない(`evidence-marking.md` L86-90)。網羅を記録で判定できない義務を採用者へ課すと、監査で確かめられない要求事項が増える
- 規格が利用者に根拠の段階の語彙を付けさせる先例は、今回の範囲では見つからない(GSN/Assurance 2.0 の残存疑念の記録、26262 の AoU の文書化は、段階の語彙を課さない)。検索の範囲が狭く、否定の根拠としては弱い(survey-291-2 5 章の限界を引き継ぐ)

**観点7 の誤り**: 観点7「根拠水準マークの見直し期限が超過していないか」は、採用組織の監査者(案件に関与していない担い手)に、採用組織の文書に無いマークを見させている。標準のマークの見直しは標準の所管の作業で、採用組織の監査では直せない。出所は初期の一括取り込みより前で ADR が無い。**誤りは観点7 の側である**。文の案: 「| 7 | 組織が自ら付した見直し期限(D-0 体制図の見直し期限、検査の除外・依存の例外に付した見直し期限、範囲を限った受容の期限)が超過していないか | 期限を延長し続けている |」。列挙の中身は反映の担当がテンプレートの実在の期限の欄と突き合わせて確定する(D-0 は `check-d0.mjs`、例外は `dependabot.yml` の注記で確かめた)。

選ばなかった案: B0 現状維持(課さないと決めた記録が無い)。B2 組織の値に限って書かせる(組織の値の多くは E0 で、全件に付くと区別の意味を失う。`CB` L64 の破れ方3 と同じ)。B3 案件の前提へ流用(E0〜E3 は「答えが効くことの根拠の強さ」で、前提が成り立っているかとは軸が違う。ADR-0018 決定8 と同じ問題)。B4 推奨として置く(推奨は記録されず、効いたかが分からない。推奨の根拠も無い)。

根拠水準: E1。`暫定 EV-NNNN / 見直し 2027-10`。差し替え条件: 採用組織の内部監査・是正の記録で、組織が置いた値の根拠の弱さが流出の原因として観測された件数。

### F-8 AI の指摘 1 件が含むべき中身

**判定: 採る(1C + 1D の一部)。代替案は課さないと明記する。**

文の案(`AC` H.4 の条件の表の後。条件5 の「指摘の内容」を定義する。新しい条件6 にはしない):

- 「条件5 の指摘の内容は、次を含まなければなりません。」
  | # | 含めるもの |
  | --- | --- |
  | 1 | 所在(ファイルと行、受入基準の識別子、または成果物の欄) |
  | 2 | 照らした基準(受入基準・規約・判定基準のどれに反するか) |
  | 3 | 見た事実。実行して確かめた場合は、実行したことと観測値と、その記録の所在(CI の実行、ログ、操作証跡)。実行していない場合は、実行していないこと |
- 「本標準は、AI の指摘に代替案(修正案)を求めません。修正は作成側の責任です。」

理由。

- **規格の finding の型と一致する**。ISO 19011 3.10「収集した監査証拠を監査基準に対して評価した結果」(第三者の用語集)、ISO/IEC 17021-1 9.4.5.3「特定の要求事項に対して記録し」「客観的証拠を詳細に特定」(CQI/IRCA の記事。二次)。SARIF 2.1.0 は result の message と locations を必須、fixes を任意とする(GitHub・AWS の文書。二次)。欠陥報告(ISTQB・29119-1 の定義。講義資料の二次)は「期待値と実際の値」「再現手順」を項目にする。#257 の 3 値のうち「実行・観測」は欠陥報告の型、「代替案」は製品の既定(FND-0222、E0)で、**規格の側は代替案を要素に入れない**
- **SRC-0002 を代替案の必須化の根拠に使えない**(問い1 への答え)。原典で、代替案は環境の「受け付けられる命令」の一覧で検証器が持つ正解の候補、経路は検証器 → 修復エージェント(機械 → 機械)、§5「列挙できない検査では、検証器は知っていることだけを報告すべき」(survey-291-3 2.1 の原典の引用)。AI レビューの指摘 → 人の経路に移すと、§5 の条件と逆向きになる。散文と JSON の差 0〜2pt は F-11 の傍証にとどめる
- **監査は処方的な助言を禁じる側にある**(ISO Guide 62 の指針。フォーラムの引用で二次)。Google の指針も「修正は作成者の責任」(原典)。代替案は ADR-0023 の「結論」(この形で直せば足りると読める)に近づき、FND-0088 は修正案が採られやすいことを示すが、正しいから採られることは示さない
- **「実行していない」と書かせる理由**: 静的に読むだけの AI レビューも条件を満たせる。実行の捏造(FND-0091、E3)は、記録の所在を添えさせることで、作成側の記載の照合(`pr-workflow.md` の「検証方法と結果」)と同じ形に還元される。所在の実在を機械で検査する装置は今回は足さない。条件5 の四半期の抜き取り(AI維持管理者、`AC` の確かめる時点と者の表、確かめた)で人が見る。装置を足すかは #290 E-2 の条件の下で、抜き取りの結果を見て判断する

選ばなかった案。

- 1A 現状維持: 条件5 の「指摘の内容」が空で、感想が内容として残る
- 1B 課さないと明記する: 規格の型があり、所在と根拠は静的なレビューでも満たせる。課さない理由が立たない
- 1E 3 値をすべて課す: 代替案の必須化に規格・欠陥報告・SARIF・指針の先例が無く、唯一の数値の根拠(SRC-0002)は転用できない。静的なレビューで実行を書けない
- 1F 代替案を「判明している場合に限り」: 「任意」は 1.7.3 が廃した語。許容(添えてよい)と書く理由も無い(書かなくても禁じていない)。課さないと書けば足りる

根拠水準: E1(規格の型は人の監査・欠陥報告のもので、AI レビューの指摘で効果を測った資料は無い)。条件5 の定義の拡張であり、EV-0059 の差し替え条件(欠いても検出率に差が無い条件は外す)の測定に含める。新しい暫定マーク: `暫定 EV-NNNN / 見直し 2027-10`。差し替え条件: 中身の要件を満たす指摘と満たさない指摘の、採用率と注入欠陥の検出率の差。

### F-9 「懸念がある」型の指摘

**判定: 採る(2D)+ 提出時の不成立は課さないと明記する。**

文の案(`AC` H.4、F-8 の表の後): 「所在または照らした基準を欠く AI の出力は、レビュアが採否の欄に『不採用(所在・根拠なし)』と記録します。条件1 の検出率の計上では、所在を欠く出力を検出に数えません。本標準は、AI の出力を提出の時点で不成立とする手続を設けません。」

- 2C(提出時に不成立)を採らない理由: 形式の欠落の機械検査は 5.7.4 要求事項3 で許されるが、「懸念」型の多くは所在を書いた上で根拠が空疎な形で出る。それを落とすのは記述の実質の判定で、要求事項1 に当たる。製品は不成立にせず、残すか理由つきで棄却する(FND-0223)。監査も証拠の弱い記録を観察事項・改善の機会へ格下げし、捨てない(CQI/IRCA 系の解説。区分名の規格上の位置は未確認)
- 2E(区分を分けて格下げ)を独立には採らない理由: 区分を付ける主体が決まらず、区分の付与が自動になれば `CB` L64 の破れ方2 と同じ形になる。検出率の計上から所在の無い出力を外すことは、注入欠陥との照合の定義から導けるので、区分を新設せずに済む
- 2A・2B: 採否の記録の中で扱う形(2D)は既存の条件5 の運用で完結し、記録が残る。現状維持より信頼できる
- 根拠水準: E0〜E1(BMAD の棄却の型は自己報告の 1 件)。F-8 の暫定マークに含める

### F-10 3.10.4 意見の様式との関係

**判定: 採る(3C)。**

文の案(`RR` 3.10.4 の箇条の後): 「AI の担い手が出す指摘は、本節の意見に当たりません。附属書H H.4 によります。」あわせて H.4 に「AI の指摘は、判断への賛否ではなく、基準に照らした事実の主張として扱います」。

- 規格の型は、指摘(finding: 証拠で支える事実の主張)と意見(判断への賛否)を分ける。3.10.4 は「賛否と理由」「代替案または充足すべき条件」で、意見の様式である
- 3.10 の場は、起案者が「意見を求めるレビュアを記名で指名する」手続である(3.10.2、確かめた)。AI は記名の主体にならない(5.5.6・3.5.4 帰結1 の席の責任者の考え方)
- 3.10.4 の動機は「反対の表明だけで進行を止められる」ことへの歯止め(`pre-review-automation.md`)で、合否に使わない AI の指摘は進行を止める力を持たない
- 「人には様式があり AI には無い」という起票の非対称は、F-8 で AI の側に規格の型の要件を置くことで解く。人と同じ様式に揃える(3B)と、AI に「賛否」を求めることになり、F-8 の「事実の主張」と逆になる
- 選ばなかった案: 3A(主体の限定の文言が無く、AI の出力に 3.10.4 が掛かるかが読めないまま)。3B(上記)。3D(人のレビューコメントへ要件を広げる。附属書C の改訂で本 Issue の材料に無い。別 Issue の候補として記録する)

### F-11 出力形式

**判定: 課さないと明記する(4B)。**

文の案(`AC` H.4): 「本標準は、AI の指摘の書式(自由記述、JSON などの構造化形式)を定めません。定めるのは、指摘が含むものです。」

- 5.7.2「記入すべき構造を規定します」と同じ型で、書式ではなく含めるものを課す
- 4C(定めてはならない)を採らない: 採用組織が SARIF のような構造を選ぶことは、5.7.4 要求事項3 の形式の欠落の機械検査の前提になりうる。規格が利用者の書式の選択を禁じる理由は無い。#257 の受入条件の文言「規定してはならない」は、標準が規定しないことを指すと読む
- 4D(許容を明記): 課さないと書けば、組織が選べることは読める。許容の文を足す理由が無い
- 理由に SRC-0002 の 0〜2pt を主に使わない(修復課題の測定)。FND-0083 の「効いているのは要求した値であって書式ではない」と並べ、どちらも傍証と書く
- 根拠水準: 課さない判断であり、マークは要しない(理由の文に測定の範囲を書く)

### F-12 分けた AI 同士の往復

**判定: 課さないと明記する(1B)+ 採る(1F、入力の分離の適用範囲)。**

文の案(`HB` 5.8.4 の末尾、または `AC` H.4 の「数えてはなりません」の後):

- 「本標準は、AI 同士の往復(反論・討論・合意までの反復)を禁じません。往復の収束は、検出の層にも独立した確認にも数えません(附属書H H.4)。」
- 「往復の2巡目以降に、作成側の説明・反論・推論の過程を確認側へ渡した構成は、H.4 条件2 を満たしません。その確認側の AI を検出の層に数えません。確認側へ渡してよいのは、仕様・受入基準・差分と、テストや実行の結果です。」(3.5.3 要求事項1・2 の適用の明記。新しい規範ではない)
- 「往復の反復の上限と停止は、フェーズ5 計算資源の停止条件によります。」(所在を引くだけ。値を足さない)

理由。

- **往復を禁じた規格・ベンダー指針・OSS 方針は無い**(survey-291-4 2.2、「無い」とは断定しない)。禁じているのは人の承認なしの提出(LLVM)と AI の承認を必須承認に数えること(GitHub の既定無効)で、本標準の H.4 条件4 と 5.8.5 の側にある
- **測定上の最良の構成は合意で止める往復である**(FND-0081、同一モデル、内側のループは収束か上限 5 巡で終わり、採点は隠しテスト)。禁止(1C)と終了条件の規制(1D)は、この構成を禁じる。素朴な往復(根拠なしの合意)が最下位という同じ論文の結果は、「数える」側で H.4 が既に塞いでいる
- **独立の規格の型**: DO-178C は独立を「人またはツール」による責任の分離で達成するとし(arXiv:2311.04344 の引用で二次)、ツールは適格性確認を前提にする。生成モデルの適格性の立証経路は成立しない(5.8.1)。往復した AI の合意は、どの意味でも独立に当たらない。これは「数えない」の根拠であって、往復の禁止の根拠ではない
- 1F は既存の条件の適用範囲を明らかにするだけで、新しい装置を足さない。条件2 の確認は AI維持管理者が人として行う(`AC`、確かめた)
- **受入条件を「既に満たされた」と記録してよいか**(問い1): よい。ただし日付と所在を付ける。H.4 の該当行は cb41fcb(2026-10-01)で入り、#258 の起票(2026-08-14)より後である。3.5.4 帰結4 と ADR-0054 決定7 は「数えない」まで。本 Issue の ADR に「#258 受入条件3・4 のうち、数える側の規定は H.4・3.5.4 帰結4 で満たされた。往復の手順を禁じないこと、異質性を求めないことは本 ADR で決めた」と書く。H.4 の行の ADR の根拠が無いことは F-15 で直す

選ばなかった案。

- 1A 現状維持: 「数えないなら何でもよい」の読みが残り、課さないと決めたことが読めない
- 1C 禁止: 上記。加えて、附属書E E.2 の工程3⇄4・E.7 の自己修正ループとの境界を「往復」の語で切れない。根拠 4 件のうち 3 件に帰属・読みの誤り(FND-0014・0076・0078)
- 1D 終了条件の規制: 最良の構成の終了条件を禁じる。終了の後に人の判定と決定論的な検査がある限り、合意で止めても判定へ流れない
- 1E 往復の各指摘に根拠を課す: 往復の中の発言は記録されない。根拠を課すのは記録に残る指摘(F-8)で足り、同じ要件を 2 か所に書かない(1.7「同じ事項の規定は1か所」)。F-8 の要件は往復の出力にも掛かる
- 1G 上限を課す: 値の根拠が E0 で、Adversarial Review の上限も付録内で 5 と 7 が食い違う。既存の停止条件(基盤で止める)の所在を引けば足りる

根拠水準: 1B は E2(FND-0081 の単一の測定と、禁止の先例の欠如)。1F は ADR-0054 の EV-0041(E2)による。新しい暫定マーク: `暫定 EV-NNNN / 見直し 2027-10`。差し替え条件: 往復を用いた AI の層と用いない層の、注入欠陥の検出率と、往復の後に人が「AI 同士で合意済み」として読み流した事例(条件5 の抜き取りで見つかった件数)。

### F-13 系統の異質性

**判定: 課さないと明記する(2B のうち「求めない」まで)。**

文の案(`RR` 3.5.4 帰結4 の理由の段落へ足す): 「本標準は、モデルの系統・提供元の異質性を求めません。系統の異なるモデルの間でも誤りは強く相関し(2026-09 時点)、独立に開発した版が独立に故障しないことは、多版プログラミングの実験(1986年)以来知られています。」

- 航空・機能安全の独立は責任の分離(人・組織、適格性確認したツール)で、多様性を独立の条件にしない(DO-178C・IEC 61508 の二次資料)。多様性は別の技法として扱われる
