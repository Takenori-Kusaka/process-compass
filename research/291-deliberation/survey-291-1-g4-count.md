## 0. 要約(10 行)

1. **G-4 の判定基準 5 件に、受入基準の側から対応するタスクの有無を数える基準は無い**(`gate-criteria.md` L285-289)。同じ形の「上位 → 下位」の数え上げは G-2 基準1 の確認方法にある(L166。価値 → 受入基準。ADR-0051 決定2 で「新しい判定基準ではなく確認方法への追加」として置いた)
2. 受入基準の側からの数え上げは、別の段に 2 つある。G-7 基準1(受入基準 → テスト、機械、IMPL-0040)と附属書E E.5 順1(受入基準 → テスト、人)。どちらも実装の後である。**軸B で S0 は G-7 を省略する**(`tailoring-guide.md` L433)。どのステージでも適用されるゲートで受入基準の側から数える箇所は、現状 0 である
3. **現行の文言のもとで、G-4 の判定者が「タスクの無い受入基準」を理由に差し戻せるかは疑わしい**。判定の範囲は「当該ゲートの判定基準と全ゲート共通の通過条件だけ」で、「基準に無い懸念」は非同期コメント期間へ回す(L97・L106、ADR-0036 L91、IMPL-0010)。基準2(粒度)の確認方法「実装計画のタスク一覧」を広く読めば拾えるが、文言は粒度に限られる
4. タスク → 受入基準の向きは、テンプレ7 の自己点検(`deliverable-templates.md` L921)、テンプレート `07-implementation-plan.md` L14、`task-breakdown` スキル L23・L65 が課している。テンプレ7 は冒頭で「受入基準 CR-1〜CR-M」と上位の総数を書かせる(L909)ので、受入基準の側の数え上げに要る材料は様式の上にそろっている
5. **機械化の材料は準拠テンプレートに既にある**。`verification-trace.mjs` の `readAcceptanceCriteria`(L161-177)が `specs/F-NNN/spec.md` の受入基準を `F-NNN/AC-N` で列挙し、`plan.md` の「対応する受入基準」列は番号で書かれる(テンプレート L9-12)。G-4 の時点でこれを突き合わせる検査は無い。番号の体系は標準(CR-N)とテンプレート(# 列の番号、スクリプトは F-NNN/AC-N)で揃っていない
6. 「判定基準の表の行を増やさない」の所在は ADR-0057 の帰結 L243 で、**その ADR の変更に限った記述**である。「判定の総数を増やさない原則(ADR-0013)」は ADR-0013 に無いことを ADR-0074 決定11 #2 が記録済み(原則として立てるかは別 Issue)。行を足すことを一般に禁じる採用済みの決定は、確認した範囲に無い
7. 外部: 双方向トレーサビリティは DO-178C・IEC 62304・ISO 26262-8・ASPICE 4.0(SWE.1〜6 の各 BP)・CMMI REQM SP1.4 がそろって課す(FND-0106・0237・0239)。ただし対象は**工学の成果物(要求・設計・コード・テスト)の間**で、作業計画のタスクは対象外。計画との整合を名指しするのは CMMI REQM SP1.5「計画・活動・成果物を要求と整合させる」と、WBS の 100% ルール(作業は範囲の 100% を含む)である
8. 対応の有無を内容の判定と切り離して数える**ツールの先例はある**。GitHub Spec Kit の `/analyze` は tasks 生成後・implement 前に「タスクが 1 件も無い要求」と Coverage %(タスクを 1 件以上持つ要求の割合)を出す。ただし対応づけは LLM の推定で、結果は勧告(implement を止めない)。規範文書に、独立した手続・ゲートとして置いた例は無い(FND-0107・0237 の注記と同じ)
9. 数え上げの弱点は外部も明記する。ASPICE 4.0 は「リンクの存在は情報の整合を必ずしも意味しない」と各 BP の注記に書き、SWE.2 注記9 は「アーキテクチャがトレースしない非機能要求がありうる」とする。本標準では「受入基準の束につき 1 Task」(L918)なので、全受入基準を列挙した 1 タスクで件数は 0 になる。逆に、件数を満たすためのタスクの細分は「分割しすぎない」と当たる。禁止形の受入基準(例: テンプレートの「ログへ出力してはならない」)は、実装タスクを持たないことが正当でありうる
10. 選択肢は論点1 で 3、論点2 で 7、論点3 で 5、論点4 で 4 立てた(どれも現状維持・課さないと明記を含む)。会議体への問いは 9。Filetto の事例が「受入基準 → タスク」の欠落だったのかは、Issue 本文の文言から確定しない(5 章)

- 規格はそろって**下方(上位 → 下位)の網羅を設計の段(テストの前)でも求める**(ASPICE SWE.2・SWE.3、DO-178C の要求 ↔ 設計、26262 の realization in the design、62304 §5.3.6)。この点で、本標準が下方の数え上げを G-7(テスト)にしか持たないのは、規格の時点の置き方より遅い
- ただし規格の「下位」は**設計・コード・テストという工学の成果物**で、作業計画のタスクではない。タスク(作業の単位)と要求の対応を名指しするのは CMMI REQM SP1.5(計画・活動の整合、手段はレビュー)だけで、数え上げの形は無い
- 本標準の実装計画は、テンプレ7 の「変更の対象パス」(テンプレート L16)を持ち、実行環境の書き込み範囲に使うなど、設計の割当の役も兼ねる。タスクを「設計への割当」とみなすか「作業の単位」とみなすかで、ASPICE SWE.2 型の先例に当たるか SP1.5 型に当たるかが分かれる(判断は会議体)
- 規格は網羅のリンクと内容の整合を**分けて書く**(ASPICE 注記11「リンクの存在は整合を必ずしも意味しない」、UL「整合はレビューでのみ」、DO-178C の 2 項目の並置)。FND-0237 の注記どおり、分けたうえで「対応の有無だけを数える独立の手続」として置いた条文は無い
- 機械化について、DO-178C・DO-330 は検査の機械化に「出力の人手レビューかツール認定」を条件に付ける(FND-0238)。本件の数え上げは推定を含まないため、条件の厳しさは推定ツールより低いと読める(推論。原文は機械化の種類で区別していない)

| 2D G-4 の前提条件にする(機械) | G-1 と同じく前提条件の表を G-4 に置き、「タスクの無い受入基準が 0 件(理由つき除外を除く)」を満たさなければ判定を開始しない | 「前提条件は機械的に検査し、人の判断を介在させません」(L34)に合う。判定者の負担を増やさない | 正当な例外に除外の印が要る。前提条件の表が G-4 に新設になる | ADR-0048 決定4(前提条件と判定基準の区別)と整合。f1 の 3(形式的な欠落)の範囲 |

| 2F G-5 の検査にする(PR 単位) | 仕様・計画を含む PR に、G-5 基準4(曖昧語)と同じ形で「タスクの無い受入基準 0 件(理由つき除外を除く)」を掛ける | 機械で止まる。除外の印の型(ADR-0062 決定4)を流用できる | G-5 は PR の段で、G-4 の判定の後に走りうる(計画の承認と PR の順序による)。G-5 の基準を足す変更になる | ADR-0073 L49 の 3 条件(偽陽性の扱い)を満たす必要。ADR-0074 で量の制約は無い |
| 2G G-7 基準1 を前倒しする | 受入基準 → テストの数え上げを G-4 に移す/重ねる | 既存の実装(`verification-trace.mjs`)を流用できる | **G-4 の時点でテストは存在しない**(テストは実装より先に生成するが、G-4 は仕様と分解の承認)。テストの未作成を G-4 の理由にすると ADR-0036 L91・IMPL-0010(次工程の材料の未完成を理由にしない)と、テンプレートの G-4 スキル L22 に反する。テンプレートの「テストの方針」表(c9)を対象にするなら当たらないが、それはテストではなく方針の記入 | ADR-0036 と衝突(テストそのものを対象にする場合) |

### 論点3 機械か人か、何を数えるか

| 案 | 中身 | 利点 | 欠点 | 既存 ADR との関係 |
| --- | --- | --- | --- | --- |
| 3A 人が数える(判定者) | G-2 基準1 と同じく判定者が確かめる | 正当な例外(禁止形・既存で満たす)を判定者が見分けられる | 30 件規模で数え落とし。記録が残らない(b3 の差し替え条件が測れない) | ADR-0051 と同型 |
| 3B 機械が数え、人が判定する | 機械が件数と一覧を出し、判定者が例外を見て差し戻す | 数え落としが無い。f3 の懸念(推定の追認)に当たらない(推定を含まない) | 機械の出力を人が追認する構成になる(f3 の一般論) | 5.7.4 要求事項2・3 と整合 |
| 3C 機械が合否を決める | 0 件でなければ止める(2D・2F) | 例外の扱いを除外の印で閉じれば決定論的 | 正当な例外に除外の印を求める運用が増える。束で素通りする(2.5)ため、合否に使っても網羅を保証しない | ADR-0073 L49 の 3 条件の確認が要る |
| 3D 件数の開示だけ | G-7 基準1 と同じく件数を保証の開示へ出し、合否にしない | b5 と同じ扱いで揃う | S0 は保証の開示(G-7)も省略の側。G-4 の記録に件数欄を置くなら様式の変更 | IMPL-0040 と同型 |
| 3E 数えない(課さないと明記) | 論点1 の 1C | — | — | — |

付随(案ではない): どの案を採っても、**数え上げは対応の有無を見るだけで、束ねたタスクによる素通りと、対応を書いたが実装しないタスクを捕まえない**(2.5)。前者は「受入基準の束につき 1 Task」との関係を、後者は G-6 基準1・G-7 基準1 との分担を記録する必要がある。

## 4. 会議体への問い

1. Filetto の事例(Issue 本文「PO が受入基準に前提を書いた。Dev が実装計画の作成時に確認し、受入基準30件に該当するものが1件も無いことを発見」)は、受入基準 → タスクの欠落か、前提(または価値)→ 受入基準の欠落か。後者なら G-2 側(G-2 基準1・基準3、#256)の問題で、G-4 の数え上げでは捕まらない。原文(254 系メモ)は履歴に無い。どちらと読むかを決めてから採否に入るか
2. 実装計画のタスクを、規格の「下位の成果物」(ASPICE SWE.2 型の設計への割当)とみなすか、「作業の単位」(CMMI SP1.5・WBS 型)とみなすか。前者なら設計の段の下方トレースとして規格の先例が強く、後者なら先例は整合のレビューと分解の規則にとどまる
3. 現行の文言で、G-4 の判定者は「タスクの無い受入基準」を理由に差し戻せるか(1.1。基準2 の確認方法の読み方)。差し戻せないと判断するなら、それ自体が #255 の「欠落」の確認になる
4. S0 で G-7 が省略され、受入基準の側の数え上げがどこにも無いことを、本件の判断材料にするか(全ステージ適用の G-4 に置く理由になるか)
5. 置き方を、表の行(2A・2C、KB へ降りる)にするか、確認方法の段落(2B、ADR-0051 型、ADR-0048 の抽出では降りない)にするか、前提条件(2D)・G-5(2F)・提示のみ(2E)にするか。G-2 基準1 の数え上げが KB へ降りていない現状を、本件と併せて扱うか
6. 「受入基準の束につき 1 Task」と数え上げの効き目は両立するか。全受入基準を 1 タスクへ列挙した計画を、粒度(基準2・4)で差し戻せることで足りるとみなすか
7. 正当にタスクを持たない受入基準(禁止形・既存の実装で満たす・非機能)を、除外の印(ADR-0062 決定4 型)で扱うか、判定者の判断で扱うか。機械の合否に使う場合、ADR-0073 L49 の 3 条件(実効的な偽陽性が無い)を満たすと言えるか
8. 識別子の 3 体系(CR-N・番号・F-NNN/AC-N)を本 Issue で揃えるか。G-7 基準1 の標準の記述(取り込む記録に計画の対応を含む)と実装(テストの参照だけ)の差を、本 Issue で扱うか
9. 「判定の総数を増やさない」は原則として立っていない(ADR-0074 決定11 #2)。本件の置き方の判断を、その原則の採否(別 Issue)より先に行うか、待つか
