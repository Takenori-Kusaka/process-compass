## 0. 議論の前に確かめた事実(議題に無いもの)

## R-1 フローと予測の担い手を置くか

### 結論

- 新しい席を置かない。席の下に名前のついた役割(SDM・デリバリー担当など)も置かない
- 担い手の置き場を作るのではなく、**活動を定め、その実行者を D-0 表1 に記名させる**。活動は次の3つに限る
  - 状態ラベルの無い作業単位と滞留した作業単位の検出と、非同期の通知(2.10.4、3.5.5 要求事項7 の検出の部分)
  - 間に合わない見込みの評価(2.10.6。R-4)
  - エスカレーションレポートの項目1〜4 の草案(7.6。既に AI に生成させてよいとされている、`exception-escalation.md:259`)
- 実行の列に AI の担い手を書いてよい。ただし、通知と見込みの記録は人の責任者へ届くこと、決定の列は価値責任者であることを条件にする(ADR-0091 の「実行の列に AI だけが書かれた場合」と同じ考え方)
- **割当・再配分・スコープ層の調整・量の選択の権限を、この実行者に持たせない**(P1)。状態ラベルの付与・遷移を、語彙の表の「付ける席」に限ると明文化する(P4)

### 理由

1. 監査の観点では、「誰の務めか」が記名されていない活動は確かめようがありません。現状、滞留の通知は IMPL-0283 の「確かめる者」が計画の Issue の担当者になっているだけで、運用の時点で通知を出す務めを負う者がいません〔確〕。起票者の不足感は、席の不足ではなく**活動の実行者の未記名と、実行層への未達**だと読みます
2. 席を足すと ADR-0054(責任者は記名の自然人)・席の全数9・RACI・任命基準・兼務表・レーンの表をすべて改めることになり、さらに SEAT_CEILING に無い席は最も緩い上限で動く(#409 の弁護・現場の指摘)〔内〕。席を足して得られるのは名前だけで、監査で確かめられる事項は増えません
3. 名前のついた役割の層は、附属書A A.7・ADR-0080 の「チームの中の役割の呼び名と分担を定めない」に当たります〔確〕。Kanban の SDM を名指しするなら ADR-0080 M-4(スクラム以外の手法を名指ししない)にも当たります〔確〕
4. 外部の先例(SDM・Scrum Master)はどちらも割当の権限を持ちません〔外〕。本標準の側でも、案件内の要員の再配分は B-2、状態ラベルの無い作業の再配分は価値責任者、SC-P/SC-B は価値責任者の単独判定と、決定の置き場がすでに決まっています〔確〕。割当の権限を持つ担い手を置くと、決定の置き場が2つになり、監査は「どちらの名義の決定が正か」を判定できなくなります(P1)
5. 1〜2名の体制では、実行者も決定者も同じ人になります。それでも記名を求めるのは、活動が誰の務めでもない状態を防ぐためで、兼務の記録として書けば足ります。AI の担い手を実行者に置ける体制なら、人の負担はむしろ減ります
6. #409 の判断(ゲートを持たない機能は活動の担い手として記名)をそのまま一般の基準にはしません(突合 F-8)。ただし本件の機能もゲートを持たず判定を持たない点で同じであり、**同じ受け止め方が当てはまる**と判断します

### 反論されうる点

- 「AI に検出と通知を任せるなら、それは 3.5.5 要求事項7 の主体を価値責任者から移すことではないか」 → 移しません。要求事項7 の「検出し、再配分する」のうち、検出だけを実行者が担い、再配分の判断と付与は価値責任者が行います。ただし本文の要求事項7 は検出と再配分を1つの務めとして書いているので、分けて読めることを明記する必要があります
- 「D-0 表1 に行を足すのは様式の変更であり、ADR-0019 の新しい様式を設けないに反する」 → ADR-0019 が退けたのは場と会議体です。表1 の行は既存の様式の行の追加で、#409 で先例があります。ただし行を足さず、既存の行(体制と運用形態)の注記で受ける案も比べる価値があります
- 「状態ラベルの付与を付ける席に限ると、AI維持管理者や監査担当の現行の付与と矛盾しないか」 → 語彙の表は既に「付ける席」を列で持っており、限定は表の読み方を明文化するだけです。矛盾は突合で確かめてください〔未〕

## R-2 チケットごとの「人だけ」と「AI 協働」の見積もり

### 結論

- **記録させない(課さない)**。様式に欄を置かない
- 採用組織が任意に記録する場合の用途の限定を、1文だけ置く。人だけの見積りは見積り時の仮定であり、作業単位ごとの見積りを合計した値を含め、AI の効果・削減の実績、7.7.8 の比較の基準値、人の評価に使ってはならない(7.7.9 要求事項9 の範囲を作業単位の見積りへ広げる。P6)
- テンプレ7 の「見積」列(RC-03)は変えない。ただし EV-0087 の差し替え条件が、課していない実績工数の記録に依存している点(事実6)を、後継の論点として渡す

### 理由

1. 反実仮想は同じ課題で観測できず、2026-02 の METR の追試は実験の場でも課題単位の計測が成立しないと判断しました〔外〕。観測できない値を欄にすると、欄が埋まった時点で「記録された値」として扱われます。監査は、仮定として書かれた値と実測の値を、書かれた後から区別できません
2. 人だけの見積りは、大きく書くほど削減が大きく見える値です(7.7.9 の理由、`exception-escalation.md:469`)〔確〕。作業単位ごとに書かせれば、案件の段の差額を禁じた ADR-0093 の禁止を、合計という形で迂回できます(P6)
3. 2.10.2 は規模を工数ではなく件数で合意させます〔確〕。作業単位に二重の工数見積りを置いても、規模の合意にも進捗の観測にも入力の行き先がありません。行き先の無い記録は「参考として測るだけ」に当たり、運用メトリクスはこれを成り立たないとしています(`metrics.md:42-46`)〔確〕
4. 課さないことを明記しないと、「書かれていない」と「課さないと決めた」が区別できません。用途の限定の1文はそのために要ります

### 反論されうる点

- 「起票者の目的は見積りの精度を上げることで、記録が無ければ学習できない」 → 学習の材料は、ADR-0093 の見積りと実績の差(案件の単位)と、R-4 の完了スループットの実測で取れます。作業単位の AI 協働の見積りと実績の差は、記録してよい(禁止しない)が課さない、という線です
- 「記録を禁止しないなら、結局は流用される」 → 流用の出口(評価・比較の基準値・削減の主張)を禁じ、観点20 と H.8 で確かめます。記録そのものの禁止は、確かめられないので採りません

## R-3 人の工数と AI の工数(トークン・処理時間・費用)の実績

### 結論

- **AI の消費(トークン・処理時間・費用)は記録させる**。ただし新しい記録ではなく、既存の器に限る。費用は 7.7.1 の AI実行予算と 7.7.8 の総費用の AI実行の行、診断は運用メトリクスのトークン効率(機能単位)。集計の単位は機能・案件とし、失敗した実行も分母に入れた成功あたりの費用として見る(7.7.2 の単位あたり値の分母の定めと整合する)
- **人の工数を、作業単位×人の粒度で記録させない**。総費用の検証・修正・教育・管理の区分に要る人の工数は、区分ごとの集計値として取り、個人へ絞り込める形で保存しない(P2)
- 用途の限定を本文に置く。AI の消費と人の工数の記録を、人の評価・目標値・チーム間の順位・AI の効果の証拠に使ってはならない。既存の 7.7.8 要求事項3 と三識の原則4・5 を、工数の記録にも掛ける
- 監査は観点20 で確かめる。観点20 の所見の例に「工数・velocity・見積りの精度・AI の消費量に目標値を置いた指標」を足す(新しい観点は足さない)

### 理由

1. 費用の記録はツールの側で取れ(Claude Code の OpenTelemetry 出力など)〔外〕、7.7.1・7.7.4 の自動の上程はこの記録が無いと働きません〔確〕。記録しない選択肢は、既存の予算統制を止めることになり、採れません
2. 一方、ツールの出力は利用者ごとのトークンと費用を出せます〔外〕。人ごとに見える形で保存すると、Amazon の利用量ランキングの停止(二次報道)と同じ経路が開きます〔外〕。保存の粒度を機能・案件に限るのは、三識の「個人へ絞り込む機能を実装しない」と同じ理由で、見られる可能性そのものが行動を歪めるためです(`metrics.md:223`)〔確〕
3. 人の工数を作業単位で記録させると、その記録の唯一の新しい用途は人ごとの比較になります。費用の5区分は集計値で足ります
4. 観点20 は既に人事評価の規程・目標設定の様式の写しを証跡に取ると定めており(`assurance-case.md:272, 946, 990`)〔確〕、#408 の裁定が求めた「観点は保証の主張の観測の担当として置く」(ADR-0086)を新設なしで満たせます。照合できるのは文書までという限界は、既存の記述どおり開示します

### 反論されうる点

- 「AI の消費は同じ課題でも30倍ばらつく。機能単位でも意味のある値にならない」 → だから診断用に限り、評価の入力にしません。既存のトークン効率の扱いと同じです。費用の統制は合計で行えば足ります
- 「人の工数を記録しないと、総費用の検証・修正の区分が見積りのままになる」 → 7.7.8 要求事項4 はそれを見積りとして開示させる形で受けています。代理の記録(PR のレビュー時間など)から取る道もあります。個人の工数記録を新設する理由にはなりません
- 「観点20 の照合は文書止まりで、運用の実態を確かめられない」 → そのとおりです。本委員はこの限界を受け入れます。運用の実態を監査が確かめようとすれば、個人の記録を監査が集めることになり、守りたいものと逆になります

## R-4 velocity 相当の量と、間に合わないものの警告

### 結論

- **工数の velocity を置かない**。容量の量は、既存の完了スループット(件数)と滞留期間の対で表す(2.10.2・運用メトリクス)
- 完了スループットの数え方を直す(P3)
  - 「完了」で閉じた作業単位だけを数え、計画外・重複で閉じたものを除く
  - 規模の合意の記録(2.10.2 要求事項4)に、作業単位の定義を書かせ、実測にも同じ定義を使う
  - 完了スループットに目標値を置かない、人・チーム間で比べないことを明記する
- 反復(スプリント)の中の容量の計画は、ADR-0080 が定めない「事業ステージより短い期間の計画の方法」に当たる。**定めない**
- 警告は、事業ステージの期日に対する見込みとして定める(2.10.6 の範囲。ADR-0080 決定1 は 2.10 の事項を規定の範囲に残している)
  - 見込みの評価: 残る作業単位(着手していない確約範囲・計画範囲を含む)の件数と、直近の完了スループットの幅と、残る期間で評価する。手法(モンテカルロなど)は定めない。評価の日付・入力・結果を記録させる
  - 評価が「間に合わない」となった時点で、価値責任者へ非同期で通知し、2.10.6 の手続を始める
  - 滞留と見込みの通知は、担当者が AI の担い手であっても、その席の責任者(人)へ届ける
- 7.6 の日程の段階1 の報告先「プロジェクト責任者」を、定義のある宛先(価値責任者)へ直す。段階2 の「部門責任者・PMO」も D-0 体制図のエスカレーションの経路で読むことを明記する(事実1)
- IMPL-0283 は降りるまで未達として表示し続ける。見込みの評価には別の実装マークを付け、降りないなら未達として表示する

### 理由

1. 工数の velocity は ADR-0019 決定3(規模は工数でなく実測スループット)と正面から衝突し、velocity を比較・評価に使う弊害は観察されています〔外〕。置く理由がありません
2. ただし件数のスループットにも水増しの経路があり(P3)、現行の対の指標(滞留期間)は分割の歪みを部分的にしか拾いません。小さく割った作業単位は早く閉じ、滞留期間の分布ごと短くなるためです〔未: 本委員の推論。実測は無い〕。数える対象と単位の定義を記録させれば、監査が前後で突合できます
3. 期日を越える経路(P5)は、担い手の不在より、**見込みの算出の欠如と通知の未達と宛先の未定義**で開いています。担い手を置いても、何をもって見込みとするかが無ければ、警告は担い手の裁量になり、監査は「警告すべき時点」を特定できません。評価の入力と日付を記録させれば、期日を越えた案件について「見込みの記録が期日より前にあったか」を確かめられます
4. 見込みの評価は、手法を課さずに入力と記録だけを課すという点で、ADR-0093 の見積りの記録と同じ型です。モンテカルロ予測や #NoEstimates を必須にしない外部調査の判断(課すべきでないこと6)とも整合します〔外〕
5. 7.6 の宛先の不一致は、警告の配送先が実在しない状態です。既存の条項の誤りとして直すべきで、本件の担い手の議論と切り離しても成り立ちます

### 反論されうる点

- 「見込みの評価を定めるのは、ADR-0019 が退けた精度を装った見積り手法ではないか」 → 2.10.2 の禁止は規模の合意に掛かり(ADR-0080 決定4 の適用範囲)、見込みの評価は合意ではなく観測です。入力も工数ではなく件数と実測スループットです。ただし、見込みの評価の結果を確約範囲の上限の引き上げの根拠にしてはならない(2.10.2 要求事項3 の準用)と書き添える必要があります
- 「着手していない項目を入れると、S0 の初回は実測が無く評価できない」 → S0 の初回は確約範囲を置かない(2.10.2 要求事項2)ので、見込みの評価は「実測なし」と記録すればよく、未測定として開示します。85パーセンタイルも G-1 の合意値も無い場合も、未設定と記録させるべきです
- 「閉じた理由で数え分けるのは GitHub の機能への依存だ」 → 規範は「完了した作業単位だけを数える」と書き、GitHub の閉じた理由は実装の例として手引きに置けば、ツール中立を保てます
- 「7.6 の宛先の修正は本件の範囲外だ」 → 範囲外と判断されるなら、後継の Issue へ送ることに異論はありません。ただし放置はしないでください

## R-5 記録

### 結論

- 新しい ADR を起こす(2026-11-04 時点で ADR-0093 の次の空き番号)。ADR-0019・ADR-0080・ADR-0093 は置き換えず補う
  - ADR-0019 へ: 見込みの評価の入力と記録、完了スループットの数え方
  - ADR-0080 へ: フローと予測の担い手を役割の名で置かないこと(M-4・A.7 の適用)
  - ADR-0093 へ: 要求事項9 の禁止を作業単位の見積りの合計へ広げること
- 課さないと決めたことの表を ADR に置く
  - 新しい席(フロー・予測・デリバリーの担い手)
  - 名前のついた役割の層(SDM・スクラムマスター相当の名指し)
  - 担い手への割当・再配分・スコープ層の調整の権限
  - 工数の velocity と、反復の中の容量の計画の方法
  - チケットごとの「人だけ」「AI 協働」の見積りの欄
  - 人の工数の作業単位×人の粒度の記録
  - AI の消費量の利用者ごとの集計・順位
  - 見込みの評価の手法の指定
- 根拠水準のマーク: 見込みの評価の入力と記録(E0)、完了スループットを完了の理由で数え分ける判断(E0)、人の工数を個人の粒度で記録させない判断(E1。Austin、Holmström & Milgrom、二次報道の利用量ランキングの停止)
- 実装マーク: 状態ラベルの付与を付ける席に限る規範(claude-md-resident)、見込みの評価と人の責任者への通知(next-role。降りなければ未達)、ラベルを付けたアカウントと付ける席の突合の検査(evidence-aggregation。降りなければ未達)。IMPL-0283 は消さずに表示し続ける
- 後継へ送る論点: EV-0087 の差し替え条件が課していない実績工数の記録に依存している点(事実6)。準拠テンプレートのテンプレ7 に見積の列が無い点(事実7)

### 理由

1. #407〜#409 は各々 ADR を起こしており、本件の決定(担い手の扱い、警告の算出、工数の記録の粒度)はそのどれにも属しません。ADR-0091 に書かれた「ゲートを持たない機能は活動の担い手として記名」の判断を一般化しないこと(突合 F-8)を守るためにも、本件の当てはめは本件の ADR に書くべきです
2. 課さないと決めたことの表が無いと、起票者と同じ不足感を持った次の読み手が、同じ提案を繰り返します。採らない案は、ADR-0080 M-7(#267 の対応づけを本文へ降ろさない)の先例と並べて読めるように書きます
3. 監査の観点では、降りていない規定を消さずに表示し続けることが、警告の未達(P5)を隠さない唯一の手段です

### 反論されうる点

- 「ADR を新しく起こすより、ADR-0019 の補足で足りる」 → 補足は採用済み ADR の本文の書き換えに近く、運用規則(採用済み ADR の本文は書き換えない)に当たります。ADR-0080 の冒頭のように、新しい ADR から既存の ADR を補う形が適切です
- 「状態ラベルの付与の限定は、#312 の写像の決定の範囲で、本件で決めるべきでない」 → 決める場がどこであれ、本件でフローの担い手を AI に置ける形にするなら、同時に塞がないと P4 が開いたままになります。本件で決められないなら、少なくとも未達として表示してください
