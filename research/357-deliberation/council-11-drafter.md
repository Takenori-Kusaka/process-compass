- 入力: `council-10-agenda.md`、`intake.md`、`survey.md`、`survey-external.md`。標準の本文と template/(wip-357、501aed3)を読んで確かめた。ほかの委員のファイルは読んでいない

- 判断軸: 信頼性。変更量の少なさは理由にしない

## 全体の設計の方針(各議題に共通)

1. **区分(external)と席の限定は、構成の整合として拒む**。人の属性で席への配置を拒む前例(任命権者。`template/scripts/gate/config.mjs:1515-1525` namingProblems)と同じ場所に置く。namingProblems は configIntegrityProblems(`config.mjs:1717-1726`)から呼ばれ、変化点の入口と出荷の証跡の集約の両方で効く。入口だけに置くと、既存の構成と手で書き換えた構成が素通りする
2. **組織の事実(上長・部門・法人・リリースの権限)を名簿へ足して「段を満たす」と導く形は採らない**。自己申告の値から適合を導くと、確かめていないものを確かめたと読ませる。機械は「記録の申告を比べる」と「構成から導ける矛盾で**引き下げる**」だけを行う。満たす向きの判定は人の記録(判定記録・評価の報告)に置く(ISO 26262-2 6.4.9 注3・6.4.10.1 と同じ形。`survey-external.md:104-112`)
3. **記録の有無と形は機械が確かめ、中身は確かめない**。確かめない範囲は出力の文で毎回開示する(IMPL-0450 の「段2 以上の距離は機械では確かめていない」と同じ型。`tailoring-guide.md:964`)
4. **名簿の未知の欄は拒否へ改める**(議題10)。新しい欄を足す前提として必須。黙って捨てる経路(`survey.md:331-339` E4・E7)を残したまま欄を足すと、旧い版のテンプレートが新しい欄を消し、記録上は no-change の変化点として残る

## 議題1 外部の確認者を責任者に置ける席の限定(論点 E、IMPL-0463、X-2)

### 結論: 採る(1-a・1-b・1-c とも)

### 理由

- 3.5 は「外部の確認者を責任者に置ける席は、独立レビュアの席に限る(体制の規模によらない)」と既に定める(`roles-responsibilities.md:418`)。テンプレートはこれに反する構成を受け付け、人数を誤って数える(X-1。`survey.md:142-147` 確認1a・1b・E1・E1b・E1c)
- 人数の誤りは、氏名の確認で本人の記名を有効にする(`config.mjs:449-452, 491`。O-1)。1〜2名・受託で発注側の価値責任者を external にすると体制が1名になり、本人の申告が確認として通る。統制が名簿の印1つで外れる
- 外部の確認者を事業決裁者の席に置くと、D-0 表1 の決定者として緩める向きの決定権を持つ(X-2。`config.mjs:1426-1437` の除外は独立レビュアの席だけ)。3.5 :417 の趣旨(外部の確認者に緩める向きの決定権を与えない)が、席を変えるだけで迂回される
- 既存の suite の fixture に、external の人を独立レビュア以外の席に置くものは無い(`survey.md:167`)。過去の決定を壊さない

### 具体案

**1-a 置き場: 構成の整合(namingProblems)。入口と集約の両方**

- `config.mjs` の namingProblems(:1515)の席の巡回に1条件を足す。席の役割が `independent-reviewer` でなく、責任者が名簿の `external: true` の人なら問題を返す
  - 文言の例: `${label} の責任者: "${氏名}" は外部の確認者(名簿の external)として名簿にある。外部の確認者を責任者に置ける席は独立レビュアの席に限る(標準 第3章 3.5)。体制の内の人として載せる(external を外し、体制の人数に数える)か、体制の内の人を責任者に置く`
- 新しい関数は作らず namingProblems に入れる。理由: 任命権者の拒否と同じ層に置き、集約では「記名を受け付けられません」として記載の欠落に数わる経路(`config.mjs:1726`)をそのまま使う
- 変化点の入口(generate-profile.mjs の任免・名簿の変化点)は、変化点を当てた後の構成に namingProblems を掛けている(E6b・E6c で拒否されたのと同じ経路。`survey.md:149-150`)。【推】追加の入口の検査は要らない。実装の時に、種別 roster(external の印だけを変える変化点)でも同じ経路を通ることを試験で確かめる

**1-b X-2 を限定の範囲として明記する**

- 3.5 :418 の後ろに1文を足す(文案の要旨): 「この限定により、外部の確認者は D-0 表1『体制と運用形態』の決定者になれない。表1 の既定と異なる決定者を置く場合も、体制の内の人とする」
- テンプレートの D-0 表1 の決定者は席(`structureDeciderSeat`。`config.mjs:1409-1412`)なので、1-a の拒否で塞がる。governance の他の決定者の欄が名簿の人を直接指す箇所があれば、同じ条件を掛ける【推: 実装の時に governance の欄を洗う】
- IMPL-0463 の note に、人数だけでなく「決定者の席に座ると緩める向きの決定権を持つ経路(X-2)」を書き足したうえで delivered にする

**1-c 既存の構成の移し方**

- 猶予の期間は置かない(migrate の原則「猶予の期間は置かない…緩める向きの補いは無い」`template/.claude/skills/process-change/kinds/migrate.md:9`)。版を上げた時点で集約は欠落を出す
- 直し方は2つで、どちらも既存の変化点の種別で足りる
  1. 区分の訂正: 名簿の当人の `external` を外す(体制の内として数える)。**締める向き**の変化点として扱い、記名は D-0 表1 の決定者。決定者の席の責任者が当の外部の確認者である場合(E1b の構成)も、その人の記名を受け付ける。区分を正す変化点を、誤った区分の人が出せない形にすると、直す経路が無くなるため。緩める向きの決定権を与える経路ではない(人数が増え、本人の氏名の確認が使えなくなる向き)
  2. 席の責任者の交代: 体制の内の人を責任者に置く(通常の任免)
- 人数の境界をまたぐ場合(1名 → 2名、2名 → 3名): 区分の訂正と、回答 `q-team-size` の訂正を**同じ変化点**で受け付ける。headcountProblems(`config.mjs:1608-`)が食い違いを既に返すので、別々の変化点にすると途中の構成が必ず欠落になる。同じ変化点で両方を書くことを案内(accountable.md・roster の案内)に書く
- 区分を正した結果、氏名の確認が「確認待ち」になる(本人以外の記名が要る)。これは正しい帰結であり、補わない
- /pit(next.mjs)と D-0 の生成は、拒否の文に直し方の2つを並べて出す

### 試験で固定すること(test-roster-rules.mjs へ足すか、新しい test-external-seat-limit.mjs)

1. 3〜9名で価値責任者・出荷判定者・事業決裁者のそれぞれを external の人にする変化点 → 拒否
2. 独立レビュアの席を external の人にする変化点 → 受け付け(既存の test-roster-rules.mjs:76-79 の固定を保つ)
3. 1〜2名・受託(E1c の構成)の初回の記入 → 拒否
4. 既に限定に反する構成(fixture で直接作る)に configIntegrityProblems → 「記名を受け付けられません」を返す(集約の欠落)
5. 区分の訂正を、当の外部の確認者である決定者の記名で出す → 受け付け
6. 区分の訂正で人数の境界をまたぎ、回答を同じ変化点で改める → 受け付け。回答を改めない → 拒否(headcountProblems)
7. 区分を正した後、本人の記名による氏名の確認が「確認待ち」になる

### 採らない案と理由

- 入口だけで拒み、集約では見ない: 既存の構成と、変化点を経ない書き換えが残る。集約の時点の整合の検査を置いた理由(`config.mjs:1710-1716` のコメント)に反する
- 拒まず注意を出すだけ: 人数の誤りが氏名の確認・兼務・G-6 の適用に連鎖する。注意では統制が外れたまま出荷できる
- 移行の猶予(版の後の一定期間は注意): migrate の原則に反し、期間の経過で戻る運用を生む
- 区分の訂正の記名を「誤った区分の人以外」に限る: 1名の体制では記名できる人がいなくなり、直す経路が消える

### 新しい義務 / EV

- 新しい義務: 無し。条項(:418)は確定済みで、テンプレートが追い付く。1-b の1文は既存の限定の帰結の明記
- EV: 要らない(値・前提を置かない)

## 議題2 3名以上の体制で外部の確認者を独立レビュアの席の責任者に置く扱い(論点 F)

### 結論: 条件つきで採る。認める。(イ)の3条件を人数によらず掛ける

### 理由

- 3名以上で外部の確認者を独立レビュアに置く実需はある【推】。段2 以上の距離を内部で得られない組織(同じ上長の下の3〜9名)が、外部の評価者で距離を得る形は、軸E が既に予定している(`tailoring-guide.md:1003`「外部の評価者を人の名簿へ登録して満たす」)。IEC 61508・EN 50716 も評価者を組織の外から得ることを排さない(`survey-external.md:90-119`)
- 禁じると、テンプレートが現に受け付けている構成(E2。`survey.md:188`)を落とし、得られるものが無い。危うさは「外部の人が席を負う」ことではなく、「力量の確認と席の規定への合意を経ずに席を負う」ことである。危うさは人数によらない
- (イ)の3条件の箇条は既に「適用: 外部の確認者を独立レビュアの席の責任者に置く体制」と書かれ、人数で限っていない(`roles-responsibilities.md:416`)。:419 の「定めていない」だけが空白である。読みが2つに割れる(`survey.md:190`)状態を、強い側(掛ける)に閉じる
- 緩める向きの決定権の除外(IMPL-0115)は人数によらず既に働く(`survey.md:186`)。3条件だけが人数で切れる理由は無い

### 具体案

- 3.5 :419 を差し替える(文案の要旨): 「3名以上の体制でも、外部の確認者を独立レビュアの席の責任者に置くことができる。条件は(イ)の3つと、緩める向きの決定権の除外による。外部の確認者は体制の人数に数えない。3名以上の体制の兼務の禁止(独立レビュア × 開発者)は、外部の確認者にも当てる」
- 表「置き方」の適用(3名未満)は残す。3名以上では(ア)の効果(構成上の G-6 は未達のまま)が生じない(体制の内の人が独立レビュアに座れる)ため、表の効果の列は 3名未満にしか意味が無い。表の下に「3名以上の体制では、(ア)は名簿に載せる置き方として使え、承認は G-6 の4条件で数える」を1行
- テンプレート: 議題3 の (イ)の記録の欄を、独立レビュアの責任者が external のとき**人数によらず**求める。3名以上の E2 の出力にも 3.5 の(イ)を案内する
- headcountProblems が外部の確認者で3名を満たしたことにしない挙動(確認2b)は保つ

### 試験で固定すること

1. 3〜9名で独立レビュアを external の人にし、(イ)の記録あり → 受け付け、G-6 は required
2. 同じで (イ)の記録なし → 議題3 の扱い(入口で拒否・集約で欠落)
3. 内の人2名+外部の確認者で「3〜9名」の回答 → headcountProblems が食い違いを返す(既存の挙動の固定)

### 採らない案と理由

- 3名以上では外部の確認者を独立レビュアに置けないとする: 段の距離を外部で得る経路(軸E)と矛盾する。既存の構成を落とし、信頼性が上がらない
- 3名以上では3条件を掛けない((ア)と同じ軽さで席を負わせる): 席を負う者の力量と規定への合意が確かめられないまま、全変更の確認を任せることになる。人数が増えても外部の確認者その人の危うさは変わらない
- 空白のまま残す: 読みが割れたまま採用者ごとに扱いが違う。規格として不適

### 新しい義務 / EV

- 新しい義務: **有り(軽い)**。3名以上で外部の確認者を独立レビュアに置く採用者に、(イ)の3条件の記録を求める。ADR-0127 に記録する
- EV: 要る。EV-0104(E1)の対象を「人数によらず掛ける判断」へ広げるか、新しい EV-0253 を置く。根拠の水準 E1(間接。ISO 26262-2 6.4.10.1 の「責任者の指定と力量の管理」、IEC 61508 の評価者の独立)。差し替え条件: 3名以上で(イ)を使う構成の数と、外部の確認者が責任者の独立レビュアによる見逃しの件数

## 議題3 (イ)の条件の記録(論点 A、IMPL-0116)

### 結論: 採る。独立レビュアの席に専用の欄を置く。既存の `competence`(3.4.3)とは別にする。機械が確かめるのは記録の有無と形まで

### 理由

- 3.4.1 の確認(任命基準の確認。独立レビュアは実際の差し戻し記録で)と 3.4.3 要求事項1(AI を使わずに判断できる力量)は別の要求である(`survey.md:36`)。同じ欄に載せると、片方の記録で両方が満たされたと読まれる
- (イ)の3条件は「すべて満たす場合に限る」前提条件である(`roles-responsibilities.md:416`)。欄が無いまま G-6 を「適用」と出すと、満たしていない前提の上に、全変更の確認を担う席が成立したと表示する。現行の出力は 3.4.3 だけを案内し、3.4.1・合意に触れない(E3。`survey.md:42`)
- 様式(D-0・テンプレ8)だけに置くと、機械は存在すら確かめられない。テンプレ8 は委託・受託の合意の様式で、内製の1名の体制の外部の確認者には当たらない
- 社内の手順に任せる現行の IMPL-0116 の形は、採用者が何も置かなくても台帳の上で区別が付かない

### 具体案

**構成の欄**(`seats.independent-reviewer.external`。席の許可の一覧 `generate-profile.mjs:4656` に足す。独立レビュア以外の席に書けば拒否)

```json
"external": {
  "competence": { "confirmedAt": "YYYY-MM-DD", "confirmedBy": "<本人以外の確認した者>", "record": "<3.4.1 の確認に用いた成果物の所在(実際の差し戻し記録)>", "validUntil": "YYYY-MM-DD" },
  "agreement":  { "agreedAt": "YYYY-MM-DD", "record": "<書面による合意の所在>" }
}
```

- 欄の名は仮。3.4.3 の `competence` と並べたときに区別が付く名にする(例: `externalTerms`)
- `validUntil` を必須にする。3.4.1 要求事項5「確認の有効期間を定める。無期限としない」(`roles-responsibilities.md:109` 付近の表)による
- `confirmedBy` の検査は既存の 3.4.3 の検査(`generate-profile.mjs:4672-4690`)に倣う: 自然人、本人でない、確認日が発効日より後でない
- `agreement` は合意の**存在**と所在だけを持つ。守秘・対価・利害の中身には立ち入らない(ADR-0060 決定2。`adr/0060-…md:64-76`)。署名者の欄は置かない(合意の当事者は採用者の組織と当人で、構成の名簿の人とは限らない)【推】

**入口の検査**(generate-profile.mjs の任免の変化点)

- 独立レビュアの席の責任者を external の人にする変化点(新任・既存の席への上書き)で、`external.competence` と `external.agreement` がそろわなければ拒否。前提条件だから、暫定任命(3.4.1「暫定任命」)は使わせない。3.5 の(イ)は暫定任命の例外を定めていない
- 既存の席へ後から記録を足す変化点(任免を伴わない)も受け付ける(1-c と同じ移し方の経路)
- 期限切れ(`validUntil` < 今日)の記録は、満たさないものとして扱う

**集約**(aggregate-evidence.mjs。configIntegrityProblems から呼ぶ関数 `externalReviewerTermsProblems(config, { today })` を config.mjs に置く)

- 独立レビュアの責任者が external で、記録が無い・形が不正・期限切れ → 記載の欠落。文言: 「独立レビュアの席の責任者(外部の確認者)の、(イ)の条件の記録(力量の確認(3.4.1)・書面による合意)が無い / 期限切れ。G-6 を適用として扱えない」
- 保証の開示の項目7 に、3.4.3 の行と**別の行**として出す
- 出力に毎回「記録の所在の有無と形だけを確かめた。確認の中身と合意の中身は確かめていない」を添える
- D-0 節9(competence の節。`generate-profile.mjs:3150-`、D0_OPTIONAL_SECTIONS)に、外部の確認者の行として力量の確認(3.4.1)と合意の所在を生成する。check-d0 の生成区間の一致(:3397)はそのまま効く

### 試験で固定すること

1. 1名・外部の確認者を独立レビュアに置く変化点で記録なし → 拒否(E3 の現行の受け付けを改める)
2. 記録あり → 受け付け。G-6 required(test-roster-rules.mjs:76-79 の固定を、記録つきの fixture へ改める。**過去の fixture の決定を変える**ので、ADR-0127 に「ADR-0060 決定2 の効果は記録を前提とする」と書く)
3. `external` の欄を価値責任者の席に書く → 拒否
4. confirmedBy が当人 → 拒否。AI の名義 → 拒否
5. validUntil の経過 → 集約で欠落(期限で緩まない。期限で締まる向き)
6. 3.4.3 の `competence` だけがある → 欠落(片方で両方を満たさない)

### 採らない案と理由

- 既存の `seats[].competence` を流用する: 2つの要求が1つの記録で満たされたと読まれる(上)
- テンプレ8 に置く: 内製の外部の確認者に当たらない。機械が読めない
- 社内の手順のまま(降ろさない理由を ADR に書く): 記録の欄を置く費用は小さく、置かないと前提条件の不在を G-6「適用」として表示し続ける。降ろさない理由が信頼性の側に立たない
- 合意の中身(守秘・利害)の欄を置く: ADR-0060 決定2 が立ち入らないと決めた
- 入口で受け付けて集約だけで欠落: 前提条件の無い任命を記録上は成立させる。入口で拒むのが前提条件の素直な形

### 新しい義務 / EV

- 新しい義務: 無し(条項は確定済み)。ただし採用者は、これまで「置き場を決めて残す」だった記録を構成の欄へ書くことになる。様式の変更として ADR-0127 に書く
- EV: 新しく要らない。EV-0104 が対象を覆う

## 議題4 席の責任者でない確認者の力量と、件数・区別の出力(論点 B、IMPL-0117)

### 結論: 採る。名簿の行に記録を持たせる。「依頼した本人による確認」は記録の値から集約が導く(申告の印を置かない)

### 理由

- 承認は人ごとに数える(名簿の人へアカウントで対応づける)。力量の確認も人ごとの属性であり、名簿の行が人の正本である。別の記録にすると、人の同定を2か所で持つ(ADR-0087 決定3 の「正本が二重になるとずれる」と同じ問題)
- 3.4.1 は件数と区別の表示を求める(`roles-responsibilities.md:139-140`)。区別を申告の印(`selfRequested: true` など)にすると、書かなければ区別が消える。記録の値(確認した者)と変更の記録(作成を指示した者)から導けば、申告に依らない
- 力量の確認は、受託で発注側が受注側の個人の可否を決める形(第2集 問13 の職務経歴書・面談)に接する(`survey-external.md:55, 171`)。記録は「誰が確認したか」だけを持ち、可否の決定の記録にはしない

### 具体案

**名簿の欄**(`people[].reviewCompetence`。名は仮。名簿の許可の一覧(議題10)に足す)

```json
{ "confirmedAt": "YYYY-MM-DD", "confirmedBy": "<確認した者>", "record": "<3.4.1 の確認に用いた成果物の所在>", "validUntil": "YYYY-MM-DD" }
```

- 検査: 自然人、AI の名義でない、確認日が発効日より後でない、validUntil 必須。**confirmedBy が当人であることは拒否**(自己確認)
- 確認した者は名簿の外の名も受け付け、「(名簿の外)」と出す(既存の competence の扱い。`survey.md:34`)
- 席の責任者本人(3.4.3)の記録とは別の欄。独立レビュアの席の責任者が名簿にもいる場合は、3.4.1 の記録として `people[].reviewCompetence` を読む【推: 議題3 の `external.competence` と1つにまとめるかは実装で決める。まとめるなら名簿の側へ寄せる】

**「依頼した本人」の判定**

- 条項の「確認を依頼した本人」は、変更の確認を依頼した者=その変更の作成を指示した者(G-6 の instructors)と読む。読みを 3.4.1 の本文に1文で明記する(文案: 「依頼した本人とは、当該の変更の作成を指示し、確認を依頼した者をいう」)。条項の文脈は G-6 の変更ごとの承認であり(`roles-responsibilities.md:142`)、決定者や任命者ではない
- 集約は承認ごとに判定する: 承認者 R の `reviewCompetence.confirmedBy` が、その変更の instructors のいずれかに当たれば「依頼した本人による確認」
- 「確認済みの者がいない体制では」の条件: 集約は、名簿に有効な `reviewCompetence` を持つ人(R と confirmedBy 以外)、または独立レビュアの席の有効な記録を持つ人がいれば「確認済みの者がいる」とみなし、そのうえで依頼した本人による確認があれば**注意**を足す(「確認済みの者がいる体制での、依頼した本人による確認」)。出荷は止めない(条項 :140)

**集約の出力**(保証の開示の項目1。aggregate-evidence.mjs の変更ごとの独立の判定(:1473-1484)の後に数える)

- 行1: 「力量の確認の記録が無い確認者による確認: N 件(変更の一覧)」。記録が無い・期限切れ・形が不正をここに数える
- 行2: 「依頼した本人による確認: M 件」。行1 と重ならない
- いずれも承認を数えたうえで出す(数えない側へ倒さない。条項 :138)。項目1 の既存の件数(席の責任者でない承認の件数など)と同じ表に並べる
- 出力の注記: 「確認の記録の有無と、確認した者と作成を指示した者の一致だけを確かめた。確認の中身は確かめていない」

### 試験で固定すること

1. 記録の無い名簿の人の承認 → G-6 の承認に数え、行1 に1件
2. confirmedBy = 作成を指示した者 → 行2 に1件、行1 には数えない
3. confirmedBy = 当人 → 入口で拒否
4. validUntil 経過 → 行1 に数える
5. 3.4.3 の未確認が従来どおり項目7 に出る(IMPL-0117 の note の既存の挙動)
6. いずれの件数も出荷を止めない(欠落に数えない)

### 採らない案と理由

- 別の記録ファイル(records ブランチの力量台帳): 人の同定が二重になる。名簿の交代と同期しない
- 申告の印で区別する: 書かなければ区別が消える。導ける値を申告にしない
- 「依頼した本人」を D-0 表1 の決定者や任命者と読む: 条項の文脈(変更ごとの確認の依頼)と合わない
- 記録の無い確認者の承認を数えない: 条項 :138 と ADR-0060 決定4 が「数えたうえで開示」と決めた。名簿にだけ載せる置き方を抜け道にしない理由も条項にある(:142)

### 新しい義務 / EV

- 新しい義務: 無し(3.4.1 は確定済み)。「依頼した本人」の読みの明記は定義の欠けの補い
- EV: EV-0105(E0)が覆う。差し替え条件の観測(件数)が、この出力で初めて取れるようになる。EV-0105 の差し替え条件に「集約の項目1 の2行」を観測の源として書き足す

## 議題5 2名必須の制限(論点 C、IMPL-0118、X-3)

### 結論: 採る。発動と解除の記録に範囲・対象の人・根拠・記録した者を持たせ、集約が該当範囲の承認を確かめる。解除の記録の形を足す

### 理由

- 7.9.6 は「発動と解除: 日時、対象とした範囲、根拠となった測定結果」の記録を求める(`exception-escalation.md:728`)。テンプレートは範囲・対象の人を受け取って黙って捨て、解除を記録する形が無い(X-3。E5・E5b)。条項が求める記録を、テンプレートが**消している**状態であり、未達より悪い
- 範囲を持たない限り、7.9.2 の制限は記録の上だけの存在で、承認の数に何も効かない(X-4)
- パス単位で承認者の数を上げる前例(コア機能の coreReviewerCount・touchesCore。`config.mjs:2134-2160`)があり、仕組みを再利用できる。GitHub のルールセットも 2026-02 からパスごとの必須の承認数を持つ(`survey-external.md:186`)
- 一時的な強化の先例(ISO 2859-1 の切替え規則、SRE のエラーバジェット方針)は、入る条件・出る条件・解除を承認する者を事前に規則に置く(`survey-external.md:179-181`)。解除の記録の形は欠かせない

### 7.9.6「機械による発動は行わない」との関係

- 発動=制限に入るという**判断と記録**。これは人(品質保証の機能)が行う。集約が、記録された発動に従って該当範囲の承認を確かめることは、発動の帰結の検査であり、発動ではない
- 7.9.6 の表の「機械による発動」の行に1文を足す(文案の要旨): 「記録された発動に基づき、出荷の証跡の集約が該当する範囲の承認を確かめることは、機械による発動に当たらない。機械は制限に入れることも、解除することもしない」
- 自動解除をしない(7.9.3)も、解除の記録が無い限り制限が続く形で満たされる。期間で解除しない

### 具体案

**変化点の記録**(種別 notice。`generate-profile.mjs:4810-4825` の入力の検査と :5631 の記録を改める。notice.md の記録例を改める)

```json
{ "kind": "notice", "event": "restriction",
  "restriction": { "id": "R-2026-001", "person": "<名簿の人(制限の対象)>", "paths": ["src/payments/**"], "category": "<見逃した欠陥の類型>", "basis": "<根拠となった測定結果の所在>", "recordedBy": "<品質保証の機能を担う者>" },
  "notice": { "to": "<出荷判定者>", "at": "YYYY-MM-DD" } }
{ "kind": "notice", "event": "restriction-release",
  "restriction": { "id": "R-2026-001", "basis": "<連続2回の検出の記録の所在>", "recordedBy": "<同>" },
  "notice": { "to": "<出荷判定者>", "at": "YYYY-MM-DD" } }
```

- 入口の検査: person は名簿の人で AI でない。paths は1つ以上の glob(`**` を許す。範囲が広い側は締める向き)。basis・recordedBy 必須、recordedBy は自然人(O-4 を塞ぐ)。release は既存の発動中の id を要し、二重の解除・発動の無い解除を拒否
- 範囲の限定の注意: paths が `**` だけのとき、「7.9.2 は見逃した欠陥の類型に対応する範囲に限る」を注意として出す(拒否はしない。広げる向きは安全側)
- 未知の欄の黙った捨て(E5)を拒否へ改める(議題10 と同じ方針を notice にも当てる)

**導出**(config.mjs に `activeRestrictions(config)`): changeLog の発動のうち、対応する解除が無いもの。構成に別の状態の欄は持たない(正本を changeLog の1か所にする)

**集約**(aggregate-evidence.mjs。変更ごとの独立の判定の後、`restrictionApprovalProblems(config, unit, activeRestrictions)`)

- 変更のファイルが制限の paths に当たり(matchGlob。touchesCore と同じ関数)、かつ承認者に制限の対象の人が含まれるなら、その変更は**対象の人以外の独立した承認者が少なくとも1名**いることを要する(承認者の合計で2名以上)
- 満たさない変更 → 記載の欠落。文言: 「PR #N: 承認権限の一時制限(R-2026-001、対象 鈴木 一郎、範囲 src/payments/**)の範囲の変更を、対象の人の承認だけで数えている。独立レビュアを2名とする(標準 第7章 7.9.2)。確保できない場合は 7.9.4 の例外決裁による」
- 対象の人が承認していない変更には掛けない(制限するのは当人の単独の承認権限。7.9.2 の「制限するのは人ではなく権限の範囲」・ADR-0067 決定2)
- 承認の時点で判定する: 承認の日時が発動の通知日より前・解除の通知日より後のものには掛けない
- 7.9.4 の例外決裁の記録があれば欠落でなく、例外の行使として項目へ出す(既存の例外の経路に乗せる)【推: 例外の記録との結び方は実装で確かめる】
- 保証の開示に「発動中の制限: 一覧(id・対象・範囲・発動日)」と「期間中に解除した制限」を出す(7.9.6 の四半期の確認の材料)
- ブランチ保護は自動では設定しない。GitHub の required reviewer rule はチームを単位とし、名簿の個人と対応しない(`survey-external.md:195`)。検出は集約で行う(ADR-0109 の検出の原則)。PR の検査(check-pr.mjs)は同じ関数で注意を出す

### 試験で固定すること(新しい test-restriction.mjs)

1. 発動中・範囲内・対象の人だけの承認 → 欠落
2. 同じで別の人の承認が加わる → 通る
3. 範囲外の変更 → 掛けない
4. 対象の人が承認していない範囲内の変更 → 掛けない
5. 解除の後の承認 → 掛けない。発動の前の承認 → 掛けない
6. 期間がいくら経っても解除の記録が無ければ続く(時計を進めても変わらない)
7. 発動の無い id の解除 → 拒否。basis・recordedBy の無い発動・解除 → 拒否
8. 旧い形の発動の記録(範囲の無い `event: "restriction"`) → 議題10 の扱い
9. test-edition-end.mjs:192(restriction の通知を受け付ける)は、新しい形の fixture へ改める

### 採らない案と理由

- 範囲中は全変更の承認者数(requiredApprovals)を上げる: 制限は範囲と当人の権限に限る(7.9.2)。全変更を止めると業務を止めるだけで、条項が退けた全権の停止に近づく
- 構成に「制限中の範囲」の状態の欄を持つ: 正本が changeLog と二重になる。解除の書き忘れ・戻し忘れでずれる
- ブランチ保護(ルールセット)へ自動で写す: チーム単位で個人に対応しない。プランに依る。検出で足りる
- 範囲を類型の文字列だけで持つ: 機械が承認と結べない。類型は category に残し、照合は paths で行う
- 7.9.6 を「集約による検査も行わない」と読み、降ろさない: 記録を消す現状が続き、7.9.2 は効かない。条項の趣旨(測定を隠す動機を作らない)は、発動と解除を人が記録することで守られる

### 新しい義務 / EV

- 新しい義務: 無し。7.9.6 が既に範囲・根拠の記録を求める。記録した者の記名は 7.9.6 の「記録する者」の記録の形
- EV: 新しく要らない(2名の値は既存の条項の値)。7.9.6 の1文の追記は読みの明記

## 議題6 組織上の距離の段2 以上(論点 D、IMPL-0184・0344・0452・0080、X-7)

### 6-a 結論: 名簿に上長・部門・法人・リリースの権限の欄を足して段を導く案は**採らない**。記録の段と根拠を比べる現行の形(IMPL-0450)へ揃え、構成から導ける矛盾で**引き下げる照合**を足す

#### 理由

- 段2〜4 の条件(直属の上長・指揮系統・資源・法人・利害)は、すべてリポジトリの外の組織の事実である(`survey.md:239`)。名簿に書けば自己申告の値で、それを比べて「段を満たす」と出すと、確かめていないものを確かめたと読ませる
- 調べた規格に、自己申告の属性で独立を「満たす」と判定する例は無い。ISO 26262-2 は水準を安全計画で宣言し、指定された責任者の報告で残す(`survey-external.md:104-112, 137`)。機械可読な属性で判定する Entra の例は、人事のディレクトリという**別の正本**から取る(`survey-external.md:134`)。採用者のリポジトリの名簿はその正本ではない
- 一方で、構成が既に持つ事実から**段の申告と矛盾すること**は導ける。矛盾の検出は引き下げる向きにしか働かず、確かめていないものを確かめたと読ませない

#### 具体案

- 新しいモジュール `template/scripts/gate/org-distance.mjs` に共通の関数を置く:
  `stepCheck(config, { signer, against: [人...], recordedStep, basis, required, insiderCap })` → `{ recorded, effective, ok, unmet[], capped[] }`
  - 記録した段(`stepOf`。`cl-judgment.mjs:101`)と段の根拠の有無
  - 引き下げの照合(上限の段):
    1. 1〜2名の体制の内の人 → 段1(既存。`cl-judgment.mjs:349-360`)
    2. 確認者が出荷判定者・事業決裁者の席の責任者 → 段1 を上限(段2 の「確認者が対象のリリースの権限を持たない」に反する。席から導ける)【推: リリースの権限の定義の明記が要る。下の条項案】
    3. 確認者と against の人の `team` がともに記入され同じ → 段2 を上限(段3 の「作成の部門から独立」に反する)
    4. 確認者が体制の内の人(external でない) → 段3 を上限(段4 は別の法人を要する)
    5. 確認者が AI の名義 → どの段にも数えない(既存)
  - 上限により記録の段から下げた場合は「記録した段 段3 を段2 として数えた(理由)」と出す
  - 出力に毎回「段2 以上の距離は機械では確かめていない(記録の申告)。機械は構成から導ける矛盾で引き下げただけ」
- cl-judgment.mjs(判定の確認者)を `stepCheck` へ寄せる。挙動は変えない(test-cl-judgment.mjs の固定を保つ)うえで、上限 2〜4 が加わる
- 条項(tailoring-guide.md 軸E :1007-1009)の改め: 「準拠テンプレートが機械で確かめるのは、段1 と、記録に書いた段・段の根拠の有無、構成から導ける矛盾による引き下げまでである。段2 以上の距離そのもの(上長・指揮系統・資源・法人・利害)は、判定記録・附属書F F.7 の記録と、独立した安全性の評価・内部監査で人が確かめる」。第1章 1.4 の段2 の「リリースの権限」に、「出荷判定者・事業決裁者の席の責任者、出荷の経路の統制を迂回できる権限を持つ者を含む」を足す(定義の欠けの補い)
- マークの扱い:
  - 新しい IMPL-0513(delivered、test-org-distance.mjs): 記録の段の比較と引き下げの照合
  - IMPL-0344・0452・0184 は、「距離そのものを機械で確かめる」部分を**降ろさないと決めた**規定として扱う。`state=undelivered plan=adopter` とし、note に「本標準は、段2 以上の距離を準拠テンプレートの機械で確かめないと決めた(ADR-0127)。確かめる者: 判定記録の記名者と、独立した安全性の評価(附属書F)・内部監査 観点6」と書く。消さずに表示し続ける(#222 の規則)

### 6-b 結論: 採る(自己申告で「満たす」と出さない)

- 集約・cl-judgment の文言で「満たす」「確認済み」を使わず、「記録の段 段N(申告)が求める段に届く」と書く。表示の区分は「届く(申告)」「届かない」「引き下げにより届かない」の3つ
- 試験で、段2 以上を求める確認の通る出力に「機械では確かめていない」の文が必ず含まれることを固定する(既存 test-cl-judgment.mjs:194 の固定を安全性の評価者へ広げる)

### 6-c 結論: ADR-0069 決定2 の範囲に名簿は入らない、と読む。ただし本件で名簿へ組織の属性を新しく足すことはしない

- 決定2 の文言は「席と受信箱」(`adr/0069-…md:53`)。名簿の所属(`team`)は表5-2 が別に定める(`deliverable-templates.md:152`)。名簿は人の正本で、席の定義ではない
- 既存の `team` は表5-2 の「所属」で、10名以上の規則と、6-a の上限3(引き下げ)にだけ使う。満たす向きには使わない
- IMPL-0462 の note の「席と名簿に組織の所属を持たせない(ADR-0069 決定2)」は ADR の語と食い違う(X-8)。議題7 の改めと合わせて直す
- ADR-0127 に「ADR-0069 決定2 は席と受信箱の決定であり、名簿の表5-2 の欄を妨げない。名簿の所属を独立の満たす向きの判定に使わない」を書く(読みの確定。ADR-0069 の本文は書き換えない)

### 6-d 結論: 採る(O-5 の食い違いを解く)

## 議題8 発注側による受注側の席の責任者の任免への関与(論点 G。法令)

### 結論: 採る(扱う)。外部の制約の注記に第3集 A7・第2集 問13 を足し、**本標準の既定が、外部の制約で例示された形の記録を生まないよう**、受託の構成での任免の決定者の既定を改める

### 理由

- 本標準自身の既定が、問題の形の記録を生む。D-0 表1「体制と運用形態」(責任者の任免)の既定の決定者は事業決裁者(`deliverable-templates.md:209`)で、軸D は事業決裁者を発注側に置く(`tailoring-guide.md:654, 661`)。既定どおりに運用すると、受注側の席の責任者の任免の変化点に発注側の人の記名(decidedBy)が残る(`survey.md:275`)。これは第3集 A7 の「特定の者を指名して業務に従事させる」「特定の者について就業を拒否する」と同じ形を記録の上で取る(`survey-external.md:45-47`)。記録は実態の判断の材料として突き合わされる(`survey-external.md:40`)
- 「扱わないと明記する」だけでは、規格の既定が採用者を不利な記録へ導く状態が残る。規格として信頼できない
- 法令の判断はしない(ADR-0069 決定3)。改めの理由は、適法性の評価ではなく、「選任した者が責任を負う」というプロセスの理由で立てる。IPA のモデル契約も、各当事者が自らの責任者を選任し、要員の変更は相手方へ**通知**する形を採る(第3条第5項・第4条・第5条。`survey-external.md:31-35, 64-66`)

## 議題9 内部監査の観点6 に「名簿の完全性」を足すか(論点 H。新しい義務)

### 結論: 条件つきで採る。観点6 に「欠けた記載」と「区分の誤り」の所見の例を足す。欠けた記載の所見は、名簿に任命権者がいないことを条件に使う規定(ADR-0122 の例外・1名の自己の任命)を使う体制に限る

### 理由

- 機械は名簿に書かれたものしか見ない。名簿の欠け(実在する任命権者を載せない)と区分の誤り(体制の内の人を external と載せる)は、機械の検査をすべて通る形で統制を外す。議題1 の拒否も、external の印を偽れば通る(区分の誤りは席の限定の前提を壊す)
- 現行の観点6 の所見の例は「書かれた人が実在するか」(過剰な記載)の向きだけである(`assurance-case.md:261`、`survey.md:294`)。D-0 の注は既に「観点6 で、在籍・アカウント・所属の記録と突合する」と書く(`deliverable-templates.md:156`)ので、突合の活動そのものは既存の義務。足すのは突合の向き(欠け・区分)の明示である
- ADR-0122 決定2(`adr/0122-…md:46`)は、例外の体制で任命権者を名簿へ置くことを推奨にとどめる。一方で例外の条件は「体制の内に当事者以外で記名できる者(組織上の任命権者を含む)がいない」(`roles-responsibilities.md:2045-2053`)。条件の真偽は名簿の外の事実で決まり、確かめる場所が監査しかない。確かめる場所を名指さないと、例外の条件は名簿の書き方だけで満たせる
- NIST AC-2(j)(l)・AC-2(7)・AC-5 は、アカウントの定期レビュー・人事の異動との整合・特権の割当ての監視を一般的な統制とする(`survey-external.md:203-206, 218`)。名簿と人事の正本との突合は実務の形である。任命権者を名指す公的な例は無い(`survey-external.md:219`)ので、所見の例は本標準の規定(例外の条件)に結び付けて限定する

### 具体案

- 附属書H H.3 観点6 の行(`assurance-case.md:261`)を改める
  - 確かめること: 現行に「名簿に載せるべき人が名簿の外にいないか、名簿の区分(体制の内・外部の確認者・組織上の任命権者)が実態と一致しているか」を足す
  - 所見の例: 現行に「体制の内の人を外部の確認者として名簿に載せている(体制の人数・席の限定・氏名の確認の扱いが変わる)」「自分に関わる変更の例外・1名の自己の任命を使った体制で、実在する組織上の任命権者が名簿の外にいる(適用: ADR-0122 の例外、または 1名の自己の任命を使った体制)」を足す
  - 機械で検出できない側に「名簿の区分が実態と一致するか、名簿の外に任命権者がいないか」を足す
- phase6-operation/process-audit.md:153 の観点6 の「機械で検出できないもの」に同じ2つを足す
- 突合の材料は人事の正本(在籍・組織図・雇用・契約の記録)。材料の名は例示にとどめ、特定の制度を課さない
- 所見を見つけた後の扱いは既存の内部監査の是正による。新しい手続を作らない
- 表5-2 の「全員載せる」(`deliverable-templates.md:155`)に任命権者を足すことは**しない**。ADR-0122 決定2 の「推奨にとどめる」を変えない。監査は「載せないなら例外の条件の真偽を確かめる」役で、載せる義務は課さない
- ADR-0122 の差し替え条件の観測の源(`roles-responsibilities.md:2074`)に「観点6 の欠けた記載・区分の誤りの所見」を加える
- 実装マーク: 新しい IMPL-0515(target=プロセス内部監査の手順の降ろし先。`impl-targets.yaml` の既存の監査の降ろし先を使う【推: 実装で降ろし先を確かめる】)

### 採らない案と理由

- 足さない(抜け道を IMPL-0483・0342 の note の開示だけにする): 開示は抜け道があることを示すが、確かめる者を名指さない。例外の条件が名簿の書き方で満たせるままになる

## 議題10 欄の無い旧い構成の互換と、名簿の未知の欄(論点 J)

### 結論: 採る。名簿(と種別 notice)の未知の欄を**拒否**へ改める。構成の形式の版を上げ、旧い版のテンプレートが新しい欄を黙って消す経路を塞ぐ。欄の無い旧い構成の表示は、欄ごとに「前提条件か」「開示か」で決める

### 理由

- 未知の欄を黙って捨てると、書いた本人は記録したと思い、記録は no-change で残る(E4・E7。`survey.md:333-334`)。席・governance・delegation・settings は既に拒否している(`generate-profile.mjs:4656, 4728, 4752, 5049`)。名簿だけ扱いが違う理由は無い
- 欄を足すと、旧い版のテンプレートが新しい欄を消す(`survey.md:339`)。形式の版を上げれば、知らない版の構成は契約検査が失敗にする(migrate.md:9)ので、消える前に止まる
- 実務も、未知の欄の扱いを明示する(Kubernetes の Ignore・Warn・Strict。`survey-external.md:226`)。統制の記録には Strict が相当

### 具体案

**未知の欄の拒否**

- `config.mjs:663` rosterProblems に許可の一覧を置く: `id, name, external, appointer, accounts, nameConfirmed, accountsConfirmed, team, reviewCompetence`(議題4)。ほかは「people[n] に書けない欄があります(…)。書けるのは …」で拒否
- `generate-profile.mjs:822-837`(名簿の正規化)は、許可の一覧に無い欄を捨てる前に拒否する(入口で止める)
- 種別 notice の未知の欄(E5)も同じく拒否
- 構成の形式の版を1つ上げる(migrate の種別で移す)。移行の処理は欄を補わない(緩める向きの補いを置かない)

**欄の無い旧い構成の表示**(欄ごと)

| 欄 | 旧い構成の読み | 表示 | 理由 |
| --- | --- | --- | --- |
| 外部の確認者を独立レビュア以外の席に置く(議題1) | 限定に反する | 記載の欠落 | 条項は確定済み。人数・決定権・氏名の確認に連鎖する |
| (イ)の記録(議題3) | 前提条件の記録が無い | 記載の欠落 | 前提条件の無い G-6 の「適用」を表示し続けない。直し方は記録を足す変化点1つ |
| 名簿の `reviewCompetence`(議題4) | 確認の記録が無い | 「力量の確認の記録が無い確認者による確認」の件数に数える(開示) | 条項が「数えたうえで開示」と定める。欄の無いことがそのまま条項の表示になる |
| 制限の記録の範囲(議題5) | 範囲・対象の人が分からない | 「範囲の分からない発動中の制限 N 件(判定できない)」として保証の開示に出し、範囲を記録し直す案内を出す。欠落にはしない | 旧い記録は範囲を捨てられており、採用者の手元にも残っていないことがある。判定できないものを適合・不適合のどちらにも倒さない(Entra の fallback の形。`survey-external.md:228`)。発動中のまま残るので、解除の記録が要ることは変わらない |
| 安全性の評価者の段(議題6-d) | 段の記載が無い | 未達。CL1 以上は出荷しない(`tailoring-guide.md:1004`) | 段の記録は既に求められていた。過去の判定記録を書き換えさせない(未達の表示で済む) |
| テンプレ8 の価値責任者の行(議題7) | 行が無い | 未達 | 照合ができない事実の表示。不一致の証拠ではない |
| `team`(既存) | — | 従来どおり「判定できない」 | 変えない |

- 共通: 旧い構成に対する出力には、何を足せば判定が変わるかを1行で添える
- 互換の期間・猶予は置かない(migrate の原則)

### 試験で固定すること

1. people[] に manager を書く変化点 → 拒否(E4 の受け付けを改める)
2. 未知の欄だけの変化点 → 拒否(E7 の no-change の受け付けを改める)
3. notice の未知の欄 → 拒否
4. 旧い形式の版の構成を新しい版の契約検査に掛ける → migrate を案内して失敗。新しい版の構成を旧い版で → 失敗(知らない版)
5. 上の表の各行の表示

### 採らない案と理由

- 未知の欄を受け付けて残す(拡張の欄として保持): 機械が読まない値が「記録した」ように見え、未達と区別が付かない
- 警告して捨てる(Warn): 書いた値が残らないのは同じ。統制の記録には足りない
- 旧い構成をすべて「未確認」(注意)にそろえる: 前提条件の欠け(議題1・3)を注意で通すと、条項が確定している統制を版の新旧で外せる
- 移行の処理で欄を既定値で補う(例: 旧い制限の範囲を `**` にする): 実態と違う値を記録へ書き込む。緩める・締めるのどちらの向きでも、記録を作り出すことになる

### 新しい義務 / EV

- 新しい義務: 無し(採用者は版の移行を1回行う)
- EV: 要らない

## ADR-0127 に書く決定の骨子(起案)

1. 外部の確認者を責任者に置ける席の限定を、構成の整合として拒む(議題1)。区分の訂正は締める向きの変化点
2. 3名以上でも外部の確認者を独立レビュアの席に置ける。(イ)の3条件は人数によらず掛ける(議題2)
3. (イ)の記録と、席の責任者でない確認者の力量の記録を構成の欄に置き、有無と形を機械が確かめる(議題3・4)。「依頼した本人」は作成を指示した者
4. 2名必須の制限の発動・解除の記録の形と、集約による該当範囲の承認の確認。集約の確認は機械による発動に当たらない(議題5)
5. 段2 以上の距離は機械で確かめない。記録の申告の比較と、構成から導ける矛盾による引き下げにとどめる。ADR-0069 決定2 は名簿を妨げないが、名簿の所属を満たす向きの判定に使わない(議題6)
6. 受託の価値責任者はテンプレ8 との照合で確かめる(議題7)
7. 受託で受注側の席の任免は受注側が決め、発注側へは通知とする。法令の評価は含まない(議題8)
8. 内部監査 観点6 に欠けた記載・区分の誤りの所見を足す(議題9)
9. 名簿の未知の欄の拒否と形式の版の更新(議題10)
- 採らない案: 名簿に組織の属性を足して段・所属を導く、ルールセットへの自動の写し、任命権者の掲載の義務、旧い構成の猶予
