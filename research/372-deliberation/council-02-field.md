## R-2 テンプレ8 第12項

### 推す案

**第12項を本件の範囲に入れて見直す。「費用の負担者を実行環境の所有者と一致させる」の要求(`tailoring-guide.md` 806〜818 行の表の1行目と 818 行、`deliverable-templates.md` 1418 行)を外し、締結時に決めて記録する形へ改める。欄は実行環境の種類ごとの行に分ける。様式の記入済みの値を消す。「所有」の語を使わない。**

改めた後の第12項の欄(案):

| 実行環境の種類 | 利用の契約を結び請求を受ける組織 | 費用の負担者 | 上限で実行を止める操作を持つ組織 | 受注側への提供の形 |
| --- | --- | --- | --- | --- |
| エージェントが動く場所(要員の端末・実行基盤) | | | | |
| CI の実行 | | | | |
| 生成 AI のサービスの利用権(席・API の鍵) | | | | |
| クラウドの計算資源 | | | | |

- 「受注側への提供の形」の値は、`提供しない` / `委託の契約の中に定める` / `委託の契約と別の契約に定める` のいずれかと、その契約の所在。値の適否(法令上どれが要るか)を、本標準は評価しない(R-1 の注記を引く)
- 費用の負担者と、上限で止める操作を持つ組織が異なる場合は、上限へ到達したときに止める者と、止めたことを負担者へ渡す経路を記録する
- 既存の2欄(期間あたりの上限額と到達時の措置、上限を超える実行を許可する手続と承認者)は維持する。上限到達での強制停止(第3章 3.12.10、816 行)と「超過を検知して報告する構成を採らない」も維持する
- 様式の雛形 `<実行環境を所有する側>`(1367 行)と、準拠テンプレートの記入済みの値 `**実行環境を所有する側**`(`template/templates/08-ai-sla.md` 171 行付近)を消し、空欄にする

### 理由(所在つき)

1. **「一致させる」の要求は、根拠の検査を経ていない**。#168(2026-08-07)由来で、ADR も根拠水準マークも無い(内部 136 行)。コアポリシー(調査・会議体・突合)より前の規定である。本件の調査で、この要求が法令の論点(問13・問14 の双務契約、取適法の購入・利用強制と減額)に正面から接すると分かった(内部 143〜145 行)。根拠の無い要求を、法令と接すると分かった後も据え置く理由は、信頼性の軸からは出てこない
2. **要求が守ろうとしている性質は、負担者の同一性ではなく、上限で実行が止まることである**。818 行の理由は「所有していない側へ負担させた場合、費用を抑える操作はその側にありません」。費用を抑える操作は、表の2行目(上限額と強制停止)と 816 行(第3章 3.12.10)で既に締結時に決める。上限で止まることが記録されていれば、負担者が誰でも費用は上限を超えない。負担者と止める者が分かれるときに要るのは、止める者を記録することと、止めたことの経路である。性質を直接記録するほうが、代理の要求(負担者=所有者)より確かである
3. **現場の契約の形と合わない**。(a) 準委任では、受注側の AI の費用を経費として単価に含めて請求することが多い(頻度は**未実証**)。受注側が所有し、費用は最終的に発注側が払う。この場合の「負担者」が誰かを、今の文言は決めない。(b) 発注側が GitHub の組織で受注側の要員へ Copilot の席を割り当てると、課金は付与の時点から発注側に掛かる(外部 252・258 行)。(c) エージェントが動く端末は受注側、CI は発注側、AI の契約者は発注側、と分かれる(内部 143 行)。「実行環境を所有する側」は一意に決まらず、欄が1つしか無いため、記入者はどれか1つを書いて残りを落とす
4. **記入済みの値は、決めていないことを隠す**。準拠テンプレートの様式は、費用の負担者の欄を太字の値で埋めた状態で配る(内部 153 行)。現場では、埋まっている欄は契約の協議で読み飛ばされる。発注側が設備を提供するのかどうか、提供するならどの契約に書くのかを決めたかが、様式から読めない。決めたことと決めていないことを区別できない様式は、合意の記録として信頼できない
5. **契約の手数と要員の交代**。提供の形とその契約の所在を1つの欄に書いておけば、要員が交代したとき・監査のとき・法務の確認のときに、席と環境がどの契約で提供されているかを1か所で引ける。今は様式のどこにも書く場所が無く(内部 146 行)、#317 の現場の委員が同じ欠落を挙げていた(`research/317-deliberation/council-02-field.md` 269 行)
6. **費用の負担を規格に含めない、という起草の規則とも当たる**。ISO/IEC 専門業務用指針 箇条4 と JIS Z 8301 箇条4 f) は、契約に関する要求事項(費用の負担を含む)を規格に含めないとされる(#309 規格の委員、内部 139 行)。#309 は主語を「締結時に決めて記録する」へ寄せた。第12項の「一致させる」だけがその形から外れている
7. **「所有」の語が告示の判断基準と衝突する**。告示の具体的判断基準は「機械、設備、資材等の所有関係、購入経路等の如何を問うものではない」とする(内部 75・84 行)。本標準が同じ「所有」を費用の軸に使うと、読み手は告示の問いと本標準の問いを混同する。本標準の中でも「実行環境」は主にエージェントの側を指し(第1章 1.4、第5章 5.8.6。内部 143 行)、CI を含むかが読み手に委ねられている。語を新しく定義するより、欄を種類ごとに分け、「利用の契約を結び請求を受ける組織」「上限で実行を止める操作を持つ組織」と事実で書くほうが、記入のばらつきが減る

### 理由(所在つき)

1. **注記の信頼性は、引いた文が原文と一致することに依る**。693 行の注記は、照合が部分であることを注記の中で開示している(`tailoring-guide.md` 695 行)。同じ型を新しい注記にも当てる。開示せずに要約だけを置くと、採用者の法務は本標準の要約を一次資料の代わりに読む
2. **引かない資料を「未確認」と記録しておかないと、次の改訂で同じ調査を繰り返す**。#317 は「未確認」を調査メモにだけ残し(内部 45〜47 行)、ADR の影響の1行で送った(ADR-0087 164 行)。何が確かめられていないかが ADR に無かったため、本件の調査は #317 の未確認から掘り直した。ADR の本文に未確認を列挙する
3. **ADR を1本にするのは、R-1 と R-2 が同じ不整合を両側から直すからである**(R-2 の「据え置き」案を落とした理由)
4. **利用規約は改版が速い**。法令の注記と同じ時点の書き方だけでは古さに気付けない。カードの claim に版を持たせ、見直しを同じ軸D の EV-0108(2027-04)に揃えると、軸D の外部の制約を1回で見直せる
5. **「書かれていない」と「課さないと決めた」の区別**(CLAUDE.md のコアポリシー)。現場では、標準に書かれていない事項は「決めなくてよい」と読まれる。課さないと決めた事項を「本標準が定めないこと」に書けば、採用者は当事者が決める事項だと分かる
