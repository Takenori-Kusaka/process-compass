## 1. 立場と、全体の見立て

1. **現場の事故の筋は 1 本である。「検査」と「公開・配布」が因果で繋がっていない**。`ci.yml` は main への push で走るようになったが、`deploy.yml`・`publish-standard.yml` は同じ push で独立に走り、検査の失敗を待たない。ソロ期は main へ直接 push し、ルールセットは 0 件なので、**push を止める仕組みは無い。止められるのは公開と配布だけで、その止め方は `needs` 1 つでワークフローの中に書ける**(管理者の操作が要らない)。J-1・J-3・J-4 の改善は、J-2 で繋がなければ「落ちたことが後で分かる」に留まる。J-2 を最優先に置く
2. **#277 の 1 文案は語を取り違えている。標準に新しい規範は要らず、既存の語で 1 文の区別を書けば足りる**。検査器の入力が無い(サブモジュール未取得)は「対象なし」ではなく「未実施」で、標準は未実施と通過の区別を既に要求している。黙って通る 2 本は、ADR-0033 が退けた形を実行層が持ち込んだ不備である
3. **管理者の設定に頼る部分(Environment・ルールセット)は、頼った事実を実行の時点で確かめて失敗させる形にする**。設定を忘れると、存在しない Environment が保護なしで自動作成され、素通しになる。文書に「設定してください」と書くだけでは、忘れたときに何も起きない。ADR-0052 決定3「運用は忘れられます。データは検査できます」をワークフローにも当てる
4. **標準側の新しい節(配布ブランチの保護・段の中の順序・検査定義の鮮度での事前停止)は、どれも課さないと明記する**。根拠が各 1 件で、Free の私的リポジトリではルールセットも Deployment branches も使えず、小さい案件では「書いたが止まらない」設定か、毎回押し通す停止に堕ちる。代わりに、**既存の文の事実の誤り**(`ci-gates.md` L879 の G-8、`git-strategy.md` L147、プランの制限の不記載)を直す。これは信頼性の問題で、量の問題ではない
5. **範囲の外で、配布の形そのもの(孤立コミットへの force push)が ADR-0052 決定2 の前提を崩しうる**。本 Issue の受入条件の外だが、#281 の保護を足しても解けない。別 Issue に送り、会議体を経る

## 3. 論点ごとの詳細

### J-1 検査の一覧を 1 か所に置く

**判定: 採る(1-A + 1-B)。**

- 一覧の正本は `package.json` の `check` とする。#292 で `ci.yml` は `npm run check` を 1 回呼ぶ形になり、CI 側に一覧が無くなった。**書き写しが残っているのは説明の側(e1〜e6)だけ**で、6 か所すべてが `check` と食い違っている(e1 は 7 本、e3〜e6 は 2 本)。10-08 時点の 12 本から 18 本へ増えた速度で、列挙はまた腐る
- 説明の側の文の案(CLAUDE.md の「コマンド」節の例):「`npm run check` — 公開前の全検査。中身は `package.json` の `check` が正本。CI(`ci.yml`)は PR と main への push で同じ `npm run check` を走らせ、通らなければ公開・配布しない」。README・CONTRIBUTING・PR テンプレート・`project-management.md` L57 も同じ趣旨で列挙をやめる。L66「CI(textlint + ビルド)を required status check に指定する」は「CI の `check` ジョブを必須の検査に指定する」へ改める(移行時の手順が誤った名前を指定させる事故を防ぐ)
- 1-B: `check` の中に、ワークフローの構成を確かめる検査を 1 本置く。確かめること: (i) `ci.yml` に template の取得と `npm run check` がある (ii) 公開・配布のジョブが検査のジョブを `needs` に持つ(J-2) (iii) `dist/standard` へ push し、Pages へ配備するワークフローが他に無い。ワークフローの YAML の決定的な読み取りで、偽陽性が無く、違反は直せ、現時点の違反は J-2 で解消する。G-5 の 3 条件(ADR-0073 決定2)と ADR-0074 の型に乗る
  - 根拠: #276 の事象そのもの(CLAUDE.md が「CI が同じチェックを実行」と書いたまま、`ci.yml` は 2 本だった期間が 2 か月以上)。AI が `ci.yml` を書き換える体制では、同じ後退が再び起こりうる。E2(本リポジトリの観察)
- 落とした案:
  - 1-C(文書に一覧の表を置き突合): 一覧が第 3 の正本になる。ADR-0052 が却下した型と同じ。突合の検査を置いても、表を直す手間だけが増え、検査の集合そのものの正しさは上がらない
  - 1-D(列挙を直すだけ): 腐る速度が実測で分かっている。直した日から再び乖離する
  - D3(集約ジョブの出力を正にする): `check` は `&&` の直列で、出力は既に実行記録として CI に残る。集約ジョブを別に作る理由が無い。必須の検査を指定する段(PR フロー移行)では、`check` ジョブ 1 つが集約の役を担う
  - 説明文の列挙を検出して失敗させる検査: 自然文の検出は偽陽性を出す(G-5 の 3 条件の 1 つ目に当たらない)。列挙をやめた後は、レビューで足りる

### J-2 公開・配布が CI を待たない

**判定: 採る。公開と配布を `ci.yml` のジョブにし、`needs: check` で繋ぐ。**

- 現状: `deploy.yml`・`publish-standard.yml` は main への push で `ci.yml` と並走し、検査が落ちても公開と配布が終わる。ソロ期は push を止める仕組みが無く(ルールセット 0 件、私的な案件の Free プランならそもそも使えない)、**止められる最後の地点が公開・配布である**。これを止めないと、J-1・J-3・J-4 の検査はすべて「後で分かる」になる
- 形: `ci.yml` に `deploy`・`publish` のジョブを置き、`needs: check`、`if: github.event_name == 'push' && github.ref == 'refs/heads/main'`。公開は `check` ジョブの `build` が作った `dist/` を `actions/upload-pages-artifact` で上げ、`deploy-pages` で配る。`withastro/action` による 2 回目のビルドをやめる(**検査したビルドと公開するビルドを同一にする**。ADR-0052 決定1 の「配布物そのもの」の考えを公開にも当てる)
- 配布(`publish`)のパスの絞り込み(`src/content/docs/**` ほか)は、ジョブの中で `github.event.before..github.sha` の差分を見て判定する。差分が取れない場合(初回の push 等)は配布する側に倒す
- `[skip ci]` の扱い: `graphify-update.yml` の自動コミットは、検査も公開も起動しない。その結果、公開されるのは常に検査を通したコミットの内容になる(graphify-out はサイトに載らない)。人が `[skip ci]` を書いた push も公開されない。**検査を経ない公開の経路が消える**のは意図した挙動である
- 落とした案:
  - `workflow_run`(CI 完了を契機に別ファイルで公開): 既定ブランチの定義で走り、`head_sha` の checkout・`conclusion == success`・`event == push`・`head_branch == main` の絞り込みを手で書く必要がある。どれか 1 つを書き漏らすと、PR の CI の成功で公開が走る・別の SHA を公開する事故になる。2 つのファイルの間の因果が読み手から見えにくい
  - ルールセットの必須の検査で main への push を止める: ソロ期の運用(main 直 push)と両立しない。私的な案件の Free プランでは使えない
  - 現状維持して、落ちたら手で戻す: 落ちたことに気づく前に、案件の submodule が壊れた配布物を取り込みうる。止められるのに止めない理由が無い

### J-6 配布ブランチと手動起動

**判定: 運営は採る。標準の新しい節は課さないと明記する。`ci-gates.md` L879 の事実は直す。ルールセットは先送り。**

運営(本リポジトリ):

- 脅威を 2 つに分ける
  - **事故**: 保守者か AI が、作業ブランチから配布を手で起動する。走るのは作業ブランチのファイルで、ファイルには起動元の確認が残っているので、ジョブ先頭の `if: github.ref == 'refs/heads/main'` が止める
  - **意図した迂回**: 書き込み権限を持つ者がブランチ上のファイルを書き換える(確認を消す、`environment:` を外す、push を契機とする別のワークフローを置く)。ファイルの中の手段は効かない。効くのは `dist/standard` 側の保護だけ
- 採る手段:
  1. 配布のジョブは J-2 で `ci.yml` に入り、`push` かつ `main` のときだけ走る。`workflow_dispatch` からは配布しない。配布が失敗したときの再配布は、その実行の再実行(同じ SHA・同じ ref)で行う。**手動起動の起動元という論点そのものを消す**(7-D)
  2. `environment: standard-dist` を付ける。Environment は**管理者が設定画面で先に作り**、Deployment branches を `main` に限り、管理者の迂回を禁じる。順序を誤ると、保護規則の無い Environment が自動作成され素通しになる
  3. ジョブの中で、Environment の保護規則を API で読み、main への限定が無い(自動作成の素通しを含む)なら失敗させる。**管理者の操作を忘れたことが、配布の失敗として見える**。`GITHUB_TOKEN` でこの API が読めるかは未確認。読めなければ、この手段は実装マークを `undelivered` にして運営の頁に開示する
  4. `VERSION.md` に `GITHUB_REF` と `GITHUB_SHA` を両方書く(SLSA の `externalParameters` と `resolvedDependencies` の分け方。survey-293-2 §2.3)。main 以外から配られたことが、配布物を見れば分かる
  5. 止まらない経路を、`ci.yml` の配布のジョブの注記と `project-management.md`(または運営の頁)に書く: ブランチ上でファイルを書き換えた場合、`contents: write` を持つ他のワークフロー(`graphify-update.yml`)からの書き込み、管理者が保護を外した場合
- 先送り: `dist/standard` のルールセット(Restrict updates・Block force pushes)。正規の配布も `GITHUB_TOKEN` で force push しており、`github-actions` をバイパスに指定できるかが未確認(survey-293-1 §5)。指定できないなら、配布用の GitHub App かデプロイキーを Environment の秘密情報に置く形になり、その形を決める材料が足りない。足りないのは「`GITHUB_TOKEN` をルールセットのバイパス対象に置けるか」の一次資料と、置けない場合のデプロイキーの保管の設計
- 管理者の設定が要る部分(2 と、先送りのルールセット)は、**受入条件「publish-standard に Environments 承認と ref の確認がある」の判定に、設定画面の操作の完了を含める**。保守者が設定したことは 3 の実行の成功で確かめる。ワークフローの変更だけで受入条件を満たしたと扱わない
- 「Environments 承認」の語の扱い: 受入条件は承認(required reviewers)を求めるように読めるが、1 名体制で承認者を置くと、自分の配布を自分で承認する儀式になる(書式だけの遵守)。配布は G-8(出荷の決裁)ではなく、正本の写しの書き出しである。**required reviewers は置かず、Deployment branches の限定だけを使う**と受入条件の読み方を記録する

標準側:

- 理由: 根拠は publishing-hub と本リポジトリの各 1 件。外部の公式の方向(GitHub Pages の Actions 公開+環境の保護)は「配布ブランチを守る作法」ではなく「配布ブランチを使わない作法」で、条項の根拠にならない。そのうえ、**Free の私的リポジトリではルールセットも Deployment branches も使えない**。条項にすると、その案件は「書いたが効かない設定」を置くか、逸脱を書くかのどちらかになる
