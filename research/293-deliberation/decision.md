## 1. 検査の一覧と CI の結線(J-1・J-2)

### J-1

- 全委員が 1-A + 1-B(正本は `check`、説明の側は参照のみ)で一致した
- 理由: 列挙した 8 か所はすべて古くなっていた(10-08 の 12 本から現在まで増えた。E2、自己の観察)。直しても同じ形で古くなる(1-D を落とす理由)。一覧の文書を足す 1-C は、ADR-0052 が却下した「第3の正本」と同型
- `scripts/check-ci-wiring.mjs` が確かめること(YAML の構造を読むだけで、実効的な偽陽性が無い。G-5 の 3 条件・ADR-0074 の型を満たす):
  1. `ci.yml` の契機に `pull_request` と、`main` への `push` がある
  2. ジョブ `check` に、`run` がちょうど `npm run check` の手順がある。その手順にもジョブにも `if:`・`continue-on-error` が無い
  3. ジョブ `check` が template のサブモジュールを取得する
  4. `.github/workflows/` のうち、Pages へ配備するジョブと `dist/standard` へ書くジョブは `ci.yml` にあり、`needs` に `check` を含む
  5. 全ワークフローが最上位に `permissions:` を明示する
  6. 配布のジョブが `environment:` を持つ(J-6)
  7. 失敗の文言は、欠けた条件と、正本が `package.json` の `check` であることを出す
- 散文の列挙を機械で禁じる案は課さないと明記する(散文の検出は偽陽性を生み、G-5 の 3 条件の 1 つ目を満たさない)
- CLAUDE.md の「コマンド」の行も列挙をやめ参照へ改める。CLAUDE.md は利用者の指示ファイルなので、PR で変更点を明示して了承を得る(擁護)
- `project-management.md` の PR フロー移行の手順(L66)は「CI の `check` ジョブを必須チェック(strict)にする」へ改める

### J-2

- 4 委員が `needs`、擁護が `workflow_run` を推した
- `needs` を採る理由: (1) 同じ実行の中で同じ SHA が保証される。(2) `workflow_run` は既定ブランチのファイルで起動し、`head_sha` の受け渡しと契機の絞り込みを手で書く分だけ誤りの入口が増える。完了の順に起動するため、古い版が新しい版を上書きしうる(起草)。(3) 公開物を検査したビルドそのものにできる(現状は 2 回目のビルドを配っている。起草・現場の発見)
- 擁護の論点(待たない理由を書いた決定は無い)は `needs` でも満たす
- 帰結: textlint の違反 1 件でサイトの更新が止まる。DoD「サイトに公開されている」の遅れは信頼性の代償として受け入れる(擁護の問い 2)
- 本リポジトリは案件ではないので、`ci.yml` の変更に「統制の設定の陰性の確認」は課さない(起草の問い 5)。代わりに `check-ci-wiring.mjs` が結線を確かめる

## 2. 対象・入力が無いとき(J-3)

### 運営

- 現状は同じ `check` の中に 3 方針が並ぶ: `check-template-drift` は飛ばす、`check-gate-criteria`・`check-provisions` は「(一致)」「違反なし」と黙って通す、`check-impl` は失敗する
- 3-A(手元は未実施と出して続け、CI では失敗。規格・擁護・現場)と 3-B(常に失敗。起草・品質保証)が割れた
- **3-B を採る**。理由: (1) `check-impl` が既に template 無しで失敗するため、「クローン直後に `npm run check` を失敗させない」(`check-template-drift.mjs` 冒頭の注記)はすでに成り立っていない。3-A を採っても手元の `check` は通らない。(2) 手元と CI で「`npm run check` が通った」の意味が割れると、監査で説明できない(品質保証)。(3) テンプレート自身が入力の欠落を失敗として扱っている(spec-lint・config・g5-local。起草の発見)。(4) J-5(3) により手元の通過は判定ではないので、手元で止まる害は往復の手間に留まる
- 失敗の文言に `git submodule update --init --recursive` を出す。README・CONTRIBUTING の手順に初期化を足す(J-9)
- 空のディレクトリ(初期化していないサブモジュール)も「無い」に数える
- `check-template-drift.mjs` 冒頭の注記の方針は、この裁定で改める

### 標準

- 起票の文(4-A)は採らない: G-5 L509・ADR-0033 決定2 と字面で衝突する。誤りは起票の文の側。起票の事象は「対象が無い」ではなく「入力が無い」
- 標準は既に「未実施」と「通過」を区別している(保証の開示 項目4、附属書H C3)。足りないのは、入力の欠如を「対象なし」と名乗らせない区別だけ(現場)。ADR-0033 は「対象なし」の理由の中身を限っていないため、入力の欠如を理由に書けば今の文面で通る(規格の発見)
- 文の案(第4章 G-5「検査対象が存在しない場合の扱い」、L509 の段落の後):
  「検査器が読む入力(検査の対象を取得するための依存・サブモジュール・生成物など)が実行環境に無いために実施できなかった検査は、『対象なし』に当たりません。G-5 の判定では、実施しなかった検査として失敗に数えなければなりません。『対象なし』として記録してはなりません。」
- 限定「G-5 の判定では」は擁護の問い 1 に答える。手元の実行は J-5(3) により判定ではないので、案件が手元でどう扱うかは縛らない
- 例示は「など」で開く。例示に無いもの(秘密情報が無くて呼べない外部 API)が逃げる懸念(現場の問い 1)には、定義の側(「検査器が読む入力」)で答える
- ADR-0033 の置き換えではなく、決定2 の範囲の明確化。ADR-0077 に記録する
- G-5 の基準の数(ADR-0013 決定1)は変えない。失敗の経路を足すのは基準ではなく判定の扱い(擁護の問いへの答え)
- 実装マーク: テンプレートの G-5 のジョブ(`spec-lint` ほか)は既に入力の欠落で失敗する。降ろし先の実在を確かめて `delivered`。確かめられなければ `undelivered`
- 根拠水準: 機序(入力の欠如で黙って通った実例 2 本)は E2、外部の実務(pytest の終了コード 5 ほか、既定で失敗)は二次。効果の測定は無いが、規範は事実の区別であり EV は付けない。可用性の害(依存の取得の一時的な失敗で G-5 が止まる)は再実行で吸収する

## 3. 配布物の検査と CI の段(J-4・J-5)

### J-4

- 全委員一致。ADR-0052 決定1 の文面「配布物そのものを検査する」は配布物を限定していない。`dist/standard` は同じ生成器の出力で、範囲の拡張ではなく実装の欠落(規格)。新しい決定の置き換えではないので、ADR-0077 に解釈を記録する

### J-5

- (1) 課さないと明記する(全員一致)。外部の実務は fail-fast と全件報告で割れ、どちらも合否を変えない効率の事項。文は「段の中の検査の順序は定めない。段の判定は、その段の全検査の結果で行う」
- (2) 課さないと明記する(全員一致)。製品の先例が無く、根拠は 1 件(E1)。古い定義への対策は、公式の判定が基底の最新に対して行われること(必須の検査の strict・基底の構成)で担う。EV-0137 は J-6 に使うので、この判断には EV-0138(E1、見直し 2027-10、差し替え条件: 手元で古い検査定義のまま通り、CI でも検出されずに既定ブランチへ入った欠陥の件数)
- (3) 採る(全員一致)。G-5 L421 の帰結を明文にする。フェーズ5 は種別が未定で規範を担えないので第4章へ置く。`compute-strategy.md` の表の「PR」は 1 名の体制(PR を経ない)に当てはまらないので「必須の検査の集約」に直す(規格の発見)。1 名の体制の段の構成を `compute-strategy.md` に書き足すかは別 Issue

## 4. 配布ブランチと手動起動(J-6)

### 機序(全委員が確かめたこと)

- ファイルの中の確認(ref の確認・`if:`)は、起動元のブランチでファイルを書き換えれば消せる。書き込み権限を持つ者(本リポジトリの作業ブランチへ push する AI のセッションを含む)は、`push` の契機を足したワークフローを自分のブランチに置けば、`contents: write` で `dist/standard` を強制 push できる(規格の発見 2)。#281 の「手動起動の起動元」より範囲が広い
- 参照した Environment が存在しなければ、保護の無いものが自動で作られる。管理者は既定で保護を迂回できる。必須レビュアは Free・Pro・Team の私的リポジトリで使えない(GitHub Docs、2026-10-23 取得。現場・規格)
- `dist/standard` は配るたびに孤立コミットへ強制 push され、15 回の配布のうち 14 回分がどの参照からも到達できない(品質保証・現場の発見)。案件が submodule で固定した旧版を取り直せる保証が無く、ADR-0052 決定2(受け取り側が版を知る)の目的を崩す
