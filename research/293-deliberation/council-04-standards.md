## 1. 立場と、全体の見立て

1. **本 Issue の大半は、標準の条項ではなく本リポジトリの構成管理(ISO/IEC/IEEE 12207 の構成管理・リリースの管理に当たる活動)の不備である**。検査の一覧の食い違い(J-1)、公開・配布が検査に従わないこと(J-2)、配布物を配る前に検査しないこと(J-4)は、どれも既に本標準と ADR-0052 が自ら課している規律を、本リポジトリが守っていない事象である。標準に新しい文を足す理由にはならない。直すのは実行層である
2. **標準の側で足すべき文は 2 つに限られる**。(i) 「実施できなかった検査」を「対象なし」から区別し、通過させない(J-3)。外部の多数派(pytest・Jest・ESLint は既定で失敗、明示で通過)と同じ型で、ADR-0033 の論理(実施していない検査を実施した記録を残さない)の帰結である。(ii) G-5 の判定の置き場を「必須の検査の集約」と書き、手元の結果を判定の証跡にしない(J-5 (3))。Pro Git・pre-commit.ci の一次文書が共有する立場である
3. **配布の保護(J-6)は、外部の根拠が「publishing-hub の 1 件」より強い**。GitHub Pages の公式文書は既定ブランチだけが配布できる環境の保護を勧め、Scorecard はリリースブランチの保護と最上位の書き込み権限を減点し、Deployment branches の照合が `GITHUB_REF` に対して行われることは GitHub の一次文書にある。ただし、これらは**製品の仕様と安全の実務**であって、この文脈での効果の測定ではない(E1)。標準側は `CG`「デプロイゲート」に、既に書いている G-8 の実装手段が効かなくなる条件(自動作成・管理者の既定のバイパス・プランの制限)の開示と、資格情報をファイルの外で縛る形を置く。規範を本文へ足すことはしない
4. **段の中の順序と検査定義の鮮度(J-5 (1)(2))は、課さないと明記する**。前者は規格にも一次文書にも無く、二次の実務は「安い順」と「並列で全件報告」の両方を勧めて割れている。後者は製品先例が無く(手元を拒否する製品は見つからない)、本標準は既に CI 側で基底の構成で判定する(`CG` L141-148)・ルールセットの例に strict を入れている(`GS` の例)
5. **本サイトの注記(J-7)は、規格の注記の作法(JIS Z 8301: 注記は要求を含まず、事実を書く)に照らして直す**。`GS` L147 の「CI 必須」は、ルールセット 0 件の本リポジトリでは偽である。外すより、事実に合わせて書き直す方が、段階導入の実例としての価値(1 名体制で何が止まらないか)を残せる

## 3. 論点ごとの詳細

### J-1 検査の一覧を 1 か所に置く方法

**判定: 採る(運営)。標準側は課さないと明記する。** 案 1-A + 1-B。

外部の型との照合:

- 必須チェック名とワークフローの一致を検査する公式機能は GitHub に無い(調査 2 §2.4、一次)。実務の対処は「集約ジョブを 1 つだけ必須にする」「一覧と CI を突合するスクリプト」で、いずれも二次(qaskills、個別リポジトリ)。**外部の根拠は E1(間接)で、型として「1 つの集約を正本にし、書き写さない」が多数である**
- 本標準は採用者に同じ型を既に課している: 第4章 G-5 L421(判定基準を実装する検査は必須の検査の集約に含めなければならない)、ADR-0074 決定2(集約に入っていることを機械で確かめる)、テンプレートの `verify-gate-contract.mjs`。本リポジトリだけが自分の型を外れている

採る形:

- 一覧の正本は `package.json` の `check` とする。CLAUDE.md L60・README L66・CONTRIBUTING L18/L24・PR テンプレート L11・`PM` L57/L66 は、中身を列挙せず「中身は `package.json` の `check` が正本」と書く。`PM` L66 の「CI(textlint + ビルド)を required status check に指定する」は「CI のジョブ `check` を required status check に指定する」へ直す
- `check` の中に、本リポジトリの CI の契約の検査を 1 本置く(1-B)。確かめるのは、(i) `ci.yml` が `pull_request` と main への `push` で `npm run check` を実行する、(ii) その前に `template` のサブモジュールを取得する、(iii) 公開と配布のジョブが `check` に従う(J-2)、の 3 つ。いずれもファイルの構造の照合で、実効的な偽陽性が出ない(G-5「是正の起動」の 3 条件の 1 つ目を満たす)
- 説明の側に古い列挙(「textlint + ビルド」「textlint + build」)が戻ることは、`provision-forms.yaml` の「廃した言い回し」の型で止める。CLAUDE.md・README・CONTRIBUTING・`.github/` が走査の置き場に入っているかは起草が確かめる(私は確かめていない)

落とした案:

- **1-C(一覧の文書を置いて突合)**: 一覧そのものが第 3 の正本になる。ADR-0052 の検討した選択肢が同じ理由で退けている。外部の二次例(必須チェックと文書の 4 者突合)はあるが、本リポジトリは `ci.yml` が `check` を呼ぶ形なので、文書の一覧は検査の対象を増やすだけで漏れを減らさない
- **1-D(列挙を直すだけ)**: 10-08 の 12 本から 18 本へ増えた実績がある。書き写す限り再び古くなる
- **D3(集約の実行記録を正にする)**: 実行記録は「走ったもの」の正本で、「走らせるべきもの」の正本にならない。`check` が `&&` で直列のため、最初の失敗以降の検査は記録に現れない

標準側: 新しい文を置かない。理由は上のとおり G-5 L421・ADR-0074 決定2 が既に採用者へ課している。**「課さないと明記する」の書き先は #293 の ADR の「採らなかったこと」とする**(本文に「本リポジトリの一覧の置き方」を書く場所は無い)。

根拠水準: 1-B の検査は機序の照合で、効果の測定を要しない(暫定マーク不要)。

### J-2 公開・配布が CI を待たない

**判定: 採る(運営)。** 案 1-E。

- 構成管理の型: ISO/IEC/IEEE 12207 の構成管理プロセスは、リリースの管理として「承認された構成品目だけを出す」活動を置く(原典を開いていない。記憶による要約)。本リポジトリで「承認」に当たるのは `check` の成功である。現状は検査が落ちても公開・配布される(調査 1 §1.1.2、`deploy.yml` を私も確かめた)
- GitHub Pages の公式は、Actions で公開し `github-pages` 環境に「既定ブランチだけが配布できる」保護を付ける型を勧める(調査 2 §2.3、一次。私は未読)
- 採る形: `deploy` と `publish` を `ci.yml` と同じワークフローのジョブにし、`needs: check` と `if: github.event_name == 'push' && github.ref == 'refs/heads/main'` で繋ぐ。同じ実行の中なので、検査したコミットと公開・配布するコミットが同じであることが構造で保証される。`publish` のパスの絞り込み(`src/content/docs/**` ほか)は、ジョブの中の差分判定へ移すか、毎回配る(生成は決定的なので、内容が同じなら `dist/standard` の差分は `VERSION.md` だけになる。どちらにするかは現場に委ねる)
- 次点の `workflow_run`: 既定ブランチ上のファイルで走り、`conclusion == 'success'` と `head_sha` の受け渡しを自分で書く必要がある。書き漏らすと失敗した実行でも起動する。採らない理由はこれで、同じ保証を構造でなく記述に頼る
- 2-B(`publish` の中で `npm run check` 全体を再実行): 同じ実行の中で `needs` を使えば重複で、`workflow_run` を使う場合にだけ意味がある。採らない
- `graphify-update.yml` の `[skip ci]` のコミットは、`check` が走らないので公開・配布もされない。内容は `graphify-out/` だけで、サイトにも配布物にも入らないため、害は無い。ただし「main の先頭が検査済みでないことがある」事実は、J-7 の書き直しで書く

標準側: 置かない。G-7・G-8 とデプロイゲートが既に「出荷・配備は判定の後」を定めている。

### J-3 検査の対象が無いときの扱い

**判定: 採る(運営 + 標準)。**

外部の型との照合(調査 2 §2.1。pytest は私が逐語で確かめた):

| 型 | 製品 | 本標準の対応 |
| --- | --- | --- |
| 既定で失敗、明示で通過 | pytest(終了コード 5 を 0 と区別)、Jest(`--passWithNoTests`)、ESLint(`errorOnUnmatchedPattern` 既定 true) | G-5 の「対象なし」= 明示の記録による通過。**同じ型** |
| 既定で通過 | go test(`[no test files]`)、Codecov(`if_not_found` 既定 success)、GitHub のジョブ条件スキップ | 本標準は採らない(ADR-0033 は記録を通過の根拠にする) |
| 未実施を別の値で残す | Scorecard の inconclusive、GitHub 秘匿情報の規則(未走査を通過にしない) | **本標準に無い**。J-3 で足す |

「既定で失敗」は多数派だが普遍ではない(go test)。根拠は E1(製品の既定であって、この文脈の測定ではない)。ただし本論点の判定は、外部の多数に乗ることではなく、ADR-0033 の論理から導く。

(a) 入力が無い と (b) 対象なし の区別:

- (b) G-5 の「対象なし」は、**案件の中に検査の対象そのものが存在しない状態**(`GC` L509・L538「適用しているが、現時点で対象が存在しない状態」)
- (a) は、**対象は存在しうるが、検査器が読む入力が実行環境に無いために検査を実施できなかった状態**。#277 の `check-gate-criteria.mjs` 3 方向目は、KB は存在する(サブモジュールの中に)のに、取得していないので読まなかった
- ADR-0033 決定2 は「対象が存在しない理由」を記録の項目に求めるが、理由の中身を限っていない(自分で確かめた発見 1)。**(a) を「対象なし(理由: サブモジュール未取得)」と記録すれば、現行の文面のまま通過になる**。ADR-0033 が防ごうとした「実施していない検査を実施した記録」(`GC` L509)が、別の経路で入る。標準の側の抜け穴である

標準の文の案(置き場: 第4章 G-5「検査対象が存在しない場合の扱い」。状態の表に行を足し、表の直後に段落を置く):

> | 未実施 | 適用しており対象も存在しうるが、検査の入力を実行環境で得られず、検査を実施できなかった状態 |
>
> 検査の入力(取得すべき依存、参照する複製、読み込む構成など)を実行環境で得られなかった基準は、「未実施」です。**「未実施」の基準を、通過として扱ってはなりません。「対象なし」として記録してはなりません**。「対象なし」の記録に書く理由は、案件の中に対象が存在しないことでなければなりません。

- 文末は JIS Z 8301 の禁止(してはならない)と要求(しなければならない)を、第1章 1.7 の表現形式へ写したもの
- 実装マーク: テンプレートの `g5-local.mjs` は依存の取得の失敗を失敗に数えている(調査 1 n12)。`gate-g5` の集約の扱いは起草が確かめて `delivered` か `undelivered` を付ける
- ADR: ADR-0033 を置き換えない。「対象なし」の定義を狭め、別の状態を足すので、#293 の新 ADR に「ADR-0033 決定2 の『理由』を、対象が存在しないことに限る(補う)」と記録する。採用済み ADR の本文は書き換えない
- 根拠水準: 禁止そのものは ADR-0033 の論理の帰結で、実証を要する値を含まない(暫定マーク不要と判断する)。品質保証が「未実施を失敗にすると、取得の一時的な失敗で G-5 が止まる」害の評価を求めるなら、それは E1 として暫定マークを付け、見直しの条件を「未実施による失敗のうち、再実行で通った件数と、実は対象なしだった件数」とする

本リポジトリの運営(採る形):

- 3-A: `check-gate-criteria.mjs` 3 方向目は KB が無ければ「実施しなかった(理由)」を出す。通過時の「(一致)」は KB を見た場合に限る
- 3-D: `check-provisions.mjs` は空のディレクトリも「検査できなかった置き場」に数える
- 3-C: 手元(環境変数 `CI` が無い)では「実施しなかった」を出して続け、CI では失敗にする。4 本の「飛ばす」検査と `check-impl.mjs`(現在は手元でも失敗)をこの形に揃える。理由: `check-template-drift.mjs` の「クローン直後に失敗させない」は手元の利便として正当で、手元の結果は公式判定ではない(J-5 (3))。公式判定の場(CI)で未実施を通すと、上の標準の文に本リポジトリが自ら反する
- 落とした案: 3-B(常に失敗)は、手元の利便を理由なく捨てる。公式判定は CI で守れるので、手元で失敗させても信頼性は増えない。3-E(現状維持)は黙った通過が残る。4-A(原案の文をそのまま)は `GC` L509 と字面で逆で、ADR-0033 を置き換える材料(「対象なし」の記録で通した誤りの事例)が無い。4-C(標準に足さない)は、上の抜け穴が残る。4-D(`skip` と理由を標準の規範に)は、手元の表示の仕様で、規範の水準に置く事項でない

### J-4 配布物そのものの検査段

**判定: 採る(運営)。** 案 2-A + 2-C。

- ADR-0052 決定1 の文面は「**配布物の中身が正本と一致すること**を検査します」で、配布物を限定していない。コンテキストが扱ったのはテンプレートの KB だが、決定は一般の形で書かれている。`dist/standard` は同じ生成器の出力を案件へ配る配布物であり、決定1 に入る。**帰結の「`npm run check` が検査する」は手段の記述で、範囲を限る文ではない**。新 ADR で ADR-0052 を置き換える必要は無く、#293 の ADR に「決定1 は `dist/standard` を含む」と解釈を記録すれば足りる(擁護が「範囲の変更」と読むなら対立点になる。4 章)
- 採る形:
  - `check-gate-criteria.mjs` に `--kb <path>` を足す(既定は従来の場所)。`publish` は生成の直後、push の前に `dist-standard/tailoring-kb.json` を検査し、落ちたら配らない
  - `source.commit` は、空・`unknown`・配る SHA と異なる、のいずれでも失敗にする(現状 `!kb.source?.commit` だけを見るので `unknown` が通る。調査 1 §1.2.2)。SLSA Provenance v1 は来歴に解決したコミット(`resolvedDependencies` の `gitCommit`)を置く例を示す(調査 2、一次。私は未読)。ADR-0052 決定2 の「生成元のコミット」が実際のコミットであることまで確かめるのは、この型に合う
  - `publish` は J-2 のとおり `check` の成功の後にだけ走る(2-C)
- 落とした案: 2-B は J-2 の形では重複。2-D(週次の事後検査)は、誤配を配った後に見つける形で、ADR-0052 の「配る前」の趣旨(決定4 の順序「直す → 配る」)に反する
- 根拠水準: EV-0038(件数の検査で足りるか、E2、見直し 2027-02)を引き継ぐ。新しい暫定マークは要らない

### J-5 #280 の残り

#### (1) 段の中の順序 — 課さないと明記する

- 規格(12207・SWEBOK の検証の章)に「検査の実行順序」の規定は無い(私の知る範囲。SWEBOK は確かめていない)。一次文書にも無い。二次の実務(oneuptime、joshka)は「安い検査を先に」と「独立した検査は並列で全件報告」を同時に勧め、層ごとに選べと書く(調査 2 §2.2)
- 順序は漏れ(信頼性)ではなく待ち時間に効く。どの順でも、必須の検査の集約がすべての基準を含めば、通る変更の集合は同じである
- 文の案(置き場: `CS`「ローカルファーストの多段検査」の表の下): 「段の中の検査の順序は定めません。どの順序でも、必須の検査の集約が判定基準を実装するすべての検査を含めば、判定は変わりません。」
- 落とした案: 5-A(参考として書く)は、フェーズ5 に種別が無い(1.8 注記)ため、参考のつもりの「並べる」が規範と読まれうる。5-B(規範)は根拠が無い

#### (2) 検査定義が基底で更新されていたら手元で止める — 課さないと明記する

- 製品の対策は「CI 側で基底の最新に対して検査する」(必須チェックの strict、マージキュー)と「依存の固定と自動更新」(pre-commit autoupdate、Renovate、Actions のロックファイル)で、**手元の実行を拒否する先例は見つからない**(調査 2。不在の証明ではない)。ロックファイルのポリシーは実行前に止めるが、止める対象は固定漏れで、検査定義の更新ではない
- 本標準は既に、基底の構成・記録で判定する規定(`CG` L141-148)と、ルールセットの例の `strict_required_status_checks_policy: true`(`GS`)を持つ。手元が古い定義で通っても、公式判定(J-5 (3))は基底の最新で行われる
- 起票の根拠はがんばりクエスト 1 件、pre-ready の落ち回数は測定不能(E2 未満。E0〜E2)
- 文の案(置き場: `CS`、(1) の直後): 「手元の検査を、基底のブランチで検査の定義が更新されたことを理由に止めることは求めません。検査の定義の鮮度は、必須の検査が基底の最新に対して判定することで担保します([CI/CD ゲート構成](/process-compass/phase5-implementation/ci-gates/))。」
- 落とした案: 5-C(規律として書く、EV マーク)は、効果も先例も無く、E0 の規律を採用者へ課す。5-D(テンプレートへ実装)は強制層の追加で、G-5「是正の起動」の 3 条件のうち「実効的な偽陽性が無い」を満たすか判定できない(検査スクリプトの無関係な変更でも止まる)

#### (3) 「手元の通過は公式判定ではない」 — 採る(標準)

- 外部: Pro Git は、クライアント側のフックは clone で複製されず、方針の強制はサーバ側で行えと書く。pre-commit.ci は手元の利用を opt-in とし、同じ構成を CI で走らせる(調査 2 §2.2、一次。私は未読)。「CI が唯一の正」という言い回しの公式文書は見つからない(調査 2 §5)。**型は一致しているが、根拠は製品・道具の文書で E1**
- 置き場: 本文。フェーズ5(`CS`)は種別が無く、本文に従属する(1.8)。規範を `CS` に置くと、規範か説明かが定まらない。G-5 の「判定基準を実装する検査と集約」(L421 の段落の直後)に置く
- 文の案:

  > G-5 の判定は、必須の検査の集約の結果で行わなければなりません。手元で実行した検査の結果を、G-5 の判定の証跡としてはなりません。手元の検査は、集約で落ちる変更を早く見つけるための手段です。

- 1 名体制(PR を経ない)でも成り立つよう、判定の場を「PR」と書かない(自分で確かめた発見 4)。あわせて `CS` の表の PR の段の「ゲートとしての公式判定」を「必須の検査の集約による G-5 の判定([第4章](...))」と直し、1 名体制では既定ブランチへの push の検査がこれに当たると注記する
- 実装マーク: `g5-local.mjs` L15 が既に明記している。降ろし先は `impl-targets.yaml` に登録する(未登録なら起草が足す)。`delivered`・`presence`
- 根拠水準: 規範は判定の場所の定義で、実証を要する値を含まない(暫定マーク不要)
- 落とした案: 6-A(`CS` に置く)は上の種別の理由。6-C(現状で足りる)は、標準側に規範の文が無く(調査 1 §1.3.1)、テンプレートの明記が「テンプレート独自」と読まれうる(ADR-0064 決定1 の論法)

### J-6 #281 配布用ブランチの保護と手動起動の起動元

**判定: 本リポジトリは採る。標準側は開示と手段の記述を採り、本文への規範は課さないと明記する。**

機序(一次文書から導けること):

- `workflow_dispatch` では `GITHUB_REF` は起動を受けたブランチで、走るのはそのブランチ上のファイル(調査 1 w5、一次)
- Deployment branches の規則は `GITHUB_REF` に照合される(私が逐語で確かめた)。したがって起動元を main に限った Environment は、別ブランチからの起動を止める。ただし `environment:` の指定を消したファイルには効かない
- 管理者は既定で保護を迂回できる(私が逐語で確かめた)。存在しない Environment は保護なしで自動作成される(調査 1 w1 の逐語)
- 自分で確かめた発見 2: `push` の契機を作業ブランチのファイルに足すだけで同じ権限が得られる。**ファイルの中の確認(7-A)はどれも、そのファイルを書き換えられる者に対して効かない**

本リポジトリで採る形(7-B + 7-C を、資格情報の置き場まで含めて):

1. Environment `publish-standard` を**先に**作る(自動作成を避ける)。Deployment branches を `main` に限る。「Allow administrators to bypass」を外す
2. `dist/standard` へ書く資格情報を `GITHUB_TOKEN` から外し、その Environment の秘密情報(配布専用の GitHub App のトークンか deploy key)に置く。Environment の外のワークフローは資格情報を得られない
3. `dist/standard` にルールセット(Restrict updates・Block force pushes・Restrict deletions)を置き、バイパスを 2 の主体だけにする。**`GITHUB_TOKEN`(github-actions)をバイパスに入れてはならない**。入れると、どのブランチのワークフローもバイパスする
4. ワークフローの最上位の権限を `contents: read` にする(Scorecard Token-Permissions。私が確かめた)。`graphify-update.yml` もジョブ単位に移す
5. 二重化として、ジョブ先頭で `github.ref == 'refs/heads/main'` を確かめ、`VERSION.md` に起動元の ref(`GITHUB_REF`)とコミットを並べて書く。SLSA Provenance v1 の `externalParameters`(利用者が渡した ref)と `resolvedDependencies`(解決したコミット)の区別に当たる。SLSA は ref の記録を必須としないが、外部入力を下流で検証しなければならない(MUST)とする(調査 2、一次。私は未読)
6. 止めている事実(1〜3)と止まらない経路(リポジトリの管理者による設定の変更、ルールセットのバイパス主体の資格情報の漏えい)を `PM` に書く
7. `workflow_dispatch` は残す(7-D を採らない)。理由: 1〜3 の後は、main 以外からの起動は Environment で止まる。再配布の手段を消す理由が無い

- 1〜3 は管理者の設定画面の操作を要する。**受入条件3「Environments 承認と ref の確認」は、設定が行われた時点で満たす。ワークフローの変更だけで満たしたと扱ってはならない**(実施は利用者。#293 はそれまで閉じない)
- 受入条件の「承認」を required reviewers と読むかは、現場に委ねる。私の見立て: 1 名体制では main へのマージそのものが配布の決裁であり、push ごとに本人の承認を求めても、本人の自己承認になり独立の確認にならない(`qms-document-control` L41 の「承認者として登録されている」を形式で満たすだけ)。required reviewers は置かず、Deployment branches を本質とする。置かない理由を `PM` に書く

標準側:

- 外部の根拠は publishing-hub の 1 件より強い: GitHub Pages の公式(既定ブランチだけが配布できる環境の保護を勧める)、Scorecard(Branch-Protection は既定ブランチと**リリースブランチ**を見る。ただし配布ブランチがリリースブランチに数えられるかは文書から判断できない)、Token-Permissions、Dangerous-Workflow。**ただしどれも製品・評価器の基準で、この文脈での効果の測定ではない(E1)**
- 本文に規範を置かない理由: 配布の形は案件ごとに違い(コンテナの registry、パッケージの公開、配備)、ブランチへの force push は本リポジトリと publishing-hub に固有の形である。本文の水準で書けるのは「配備・配布の統制は、統制される側が書き換えられる場所に置かない」という一般則だが、これは既に `CG` L142(統制の設定の変更に陰性の確認を求める)と第4章 G-5 L421 の趣旨にある。新しい規範を足しても、判定できる基準にならない
- 置くもの(`CG`「デプロイゲート」。フェーズ5 の手段の記述として):

### J-7 標準の文の事実の誤り
