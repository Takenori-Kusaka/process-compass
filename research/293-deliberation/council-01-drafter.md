## 1. 立場と全体の見立て

1. **本 Issue の大半は運営の欠陥で、標準の欠陥ではない**。ただし 2 点は標準の文の欠陥である。(a) G-5 は「対象が無い」を定めるが、「検査器の入力が無い」を定めていない。#277 の起票の文はこの 2 つを取り違えており、字面のまま置けば ADR-0033 決定2 と衝突する。正しいのは ADR-0033 で、足りないのは区別の 1 文である(J-3)。(b) デプロイゲートの記述は、Environments の自動作成と起動元のブランチに触れず、案件の G-8 を黙って素通しにしうる(J-6)
2. **検査の一覧の正本は `package.json` の `check` 1 か所に置き、ほかは列挙しない**。一覧の文書を足す案は、ADR-0052 が却下した「一覧そのものが第3の正本になる」の型である。機械で確かめるのは「`ci.yml` が `npm run check` を合否に使っている」ことだけでよく、これは G-5 L421 の型をそのまま本リポジトリへ当てる(J-1)
3. **公開と配布は、検査したものを、検査が通った後にだけ出す**。`deploy.yml`・`publish-standard.yml` を `ci.yml` の中の後続のジョブ(`needs: check`)へ統合し、公開するサイトは `check` が作ったビルドを使う。`workflow_run` は、完了の順で古い版が新しい版を上書きしうるので採らない(J-2)
4. **#281 の受入条件「Environments 承認」は、そのまま採らない**。1名の期間に起動者が自分で承認する記録は、G-8 の承認(`qms-document-control.md` の成立の条件)と同じ語で別物を残す。採るのは Environment の配布ブランチの規則(main に限る)と、ジョブ先頭の ref の確認と、ファイルの外で止めている事実・止まらない経路の文書化である。受入条件の書き換えを、理由つきで Issue に記録する(J-6)
5. **段の中の順序と、基底での検査定義の更新による手元の停止は、課さないと明記する**。前者は判定を変えない。後者は製品の先例が無く、根拠は 1 件で、同じ目的は既にある規定(ルールセットの strict、基底ブランチから読む規則)が CI の側で担っている。「手元の通過は G-5 の判定ではない」だけは第4章 G-5 に規範として置く(J-5)

### J-2 公開と配布が CI を待たない

**判定: 採る。** `ci.yml` に統合し、`needs: check` で繋ぐ。

ワークフローの案(要点だけ):

```yaml
on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:

permissions:
  contents: read

jobs:
  check:
    # 現行の手順 + main への push と手動のときだけ、ビルドを Pages の成果物として渡す
    steps:
      - ...(現行どおり)
      - run: npm run check
      - if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
        uses: actions/upload-pages-artifact@<版>
        with: { path: dist }
      - id: changed   # 配布の対象が変わったか(push の前後の差分。手動は常に真)
        run: ...

  deploy:
    needs: check
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request'
    permissions: { pages: write, id-token: write }
    environment: { name: github-pages, url: ... }
    concurrency: { group: pages, cancel-in-progress: false }
    steps:
      - uses: actions/deploy-pages@v5

  publish:
    needs: check
    if: github.ref == 'refs/heads/main' && github.event_name != 'pull_request' && needs.check.outputs.distChanged == 'true'
    permissions: { contents: write }
    environment: dist-standard
    concurrency: { group: publish-standard, cancel-in-progress: false }
    steps:
      - name: 起動元の確認
        run: test "$GITHUB_REF" = refs/heads/main
      - ...(J-4)
```

- 現行の `publish-standard.yml` のパスの条件(`src/content/docs/**`・`src/data/**`・`scripts/build-template-kb.mjs`)は、`check` のジョブで push の前後の差分から出す。差分が取れない場合(`before` が 0 のコミット)は真に倒す
- 最上位の権限は `contents: read` に下げ、書き込みはジョブ単位にする(Scorecard の Token-Permissions と同じ向き)
- `graphify-update.yml` の `[skip ci]` のコミットは公開も配布も起動しない。対象の範囲(`graphify-out/**`)はサイトと配布物に入らないので、それでよい(記録のみ)

選ばなかった案:

- `workflow_run` で `ci.yml` の完了を待つ: 完了の順で起動するため、先に push したコミットの検査が後に終わると、古い版が新しい版を上書きする。`head_sha` を checkout し直し、`head_branch`・起動の種類・リポジトリを確かめる手当てが要り、条件の漏れが黙った誤配になる。同じファイルの `needs` は同じコミットを保証する
- 各ワークフローが自分で `npm run check` を走らせる: 同じ検査を 3 回走らせ、どれかの手順が `check` から外れると機械の確認(J-1 の 5)が複雑になる。検査したビルドと配るビルドも分かれたまま
- 現状のまま開示だけする: 検査が落ちても公開・配布されることを、文書で知らせても止まらない。標準の公開物そのものが検査の外に出る

根拠水準: 設計の判断(E0 だが運営の決定)。`needs` の挙動は GitHub の文書どおりで、実行で確かめる(実装の受入)。

### J-3 検査の対象・入力が無いとき

**判定: 採る。** 運営は「入力が無ければ失敗」に揃える。標準は G-5 に区別の 1 文を置く。起票の文は採らない。

運営(本リポジトリ):

- 空のディレクトリは「無い」に数える(`check-provisions.mjs` の置き場の判定、`build-template-kb.mjs` の `defaultOut()` も同じ)
- `check-template-drift.mjs` L9-10 の「クローン直後に npm run check が失敗する構成にしないため」の注記は削る。理由は下の「選ばなかった案」
- `zenn/` は検査が読まないので対象外(現行どおり)

標準(第4章 G-5「検査対象が存在しない場合の扱い」、「対象なし」の記録の項目の段落の直後。規定の文末):

> 検査が判定に用いる入力のうち、検査の対象でないもの(比べる相手の複製、検出語の一覧、基準値、検査器自身)を、検査の入力と呼びます。**検査の入力が実行環境に無いことは、「対象なし」に当たりません**。対象は存在しており、検査が実施されていないからです。**検査の入力が無いまま終えた検査を、通過として扱ってはなりません**。その検査は失敗させ、欠けた入力を結果に出します。

- 「対象」と「入力」の区別は、G-5 の表の理由の列(「実行するテストを持たない」「コードが存在しない」)が対象の側だけを語っていることと揃う。カバレッジの「対象なし」(`ci-gates.md` L866)は、製品のコードという**対象**が無い場合で、この文と衝突しない
- 実装マーク: `spec-lint` を降ろし先に `delivered`・`machine`(検出語の知識ベースが無い・空なら失敗)。アダプタを使う G-5 のジョブが入力の欠落で落ちるかは確かめていないので、実装者が確かめ、確かめられないジョブは別の識別子で `undelivered` を付ける(1 つの値で強い方に読ませない。ADR-0061)
- 新 ADR(ADR-0077)に、ADR-0033 決定2 を変えないこと、区別を足したこと、起票の文を退けた理由を記録する
- 根拠水準: 規範の理由は ADR-0033 の理由(「実施していない検査を実施したという記録が残る」)からの演繹で、値を含まない。必要性の根拠は本リポジトリの 2 件(E2)と外部の多数派の既定(失敗側。E1)。演繹で立つ禁止なので暫定マークは付けない。ただし「テンプレートの全ジョブが既に満たす」は確かめていないので、実装マークの state で開示する

選ばなかった案:

- 4-A 起票の文「検査の対象が存在しないとき、検査を通過として扱いません」: ADR-0033 決定2「記録したうえで通過させる」と字面で衝突する。採るなら ADR-0033 の置き換えになるが、覆す材料が無い(G-5 の局面の設計は文書のみの初期の変更を想定し、それは変わっていない)。誤りは起票の文の側で、起票の事象は「対象が無い」でなく「入力が無い」だった
- 4-C 標準に足さない: G-5 の規範の字面は「対象なし」しか扱わない。入力の欠落で黙って通る経路は、本リポジトリで 2 件実在した。案件の検査器も同じ形を作りうる(ESLint・Jest の既定は失敗だが、go test・Codecov は通過。調査 2.1)。テンプレートが既に満たしている振る舞いを規範に上げるだけで、案件の負担は増えない
- 4-D `skip` と理由を規範にする: 「実施しなかったと出せば通過でよい」と読まれる。CI の結果の一覧では終了コード 0 の `skip` は通過と区別されない(調査 1.2.1)。`g5-local.mjs` の `skip` は構成が未設定の(=対象の)場合で、入力の欠落は失敗に数えている
- 3-C 手元は飛ばし、CI では失敗: 同じ `npm run check` が手元と CI で別の結果を出す。`compute-strategy.md` L108「ローカルで通れば CI でも通る」を、設計として破る
- 3-A 飛ばしたと出すだけ: 終了コード 0 のままで、CI の通過と区別されない
- 3-E 現状維持: 同じ `check` の中に「飛ばす・黙って通す・失敗」の 3 方針が並び、どれが正か読み手が決められない。「クローン直後に失敗させない」は便利さの理由で、信頼性の理由ではない。失敗の文言に取得の命令を出せば、利用者は 1 手で戻れる

### J-6 #281 配布の保護

**判定: 運営は採る。標準はデプロイゲートの改訂に限って採る。配布ブランチの 1 節は課さないと明記する。**

## 4. 他の委員に問いたいこと

1. 現場へ: J-3 で、template を読む検査を手元でも失敗させる(3-B)。クローン直後に `npm run check` が落ちることは、取得の命令を文言に出せば実害がないと見たが、手元で template を取得できない環境(社内のプロキシ等)の利用者がいるか。いるなら 3-C ではなく、その環境で `npm run check` を通過と呼ばない別の命令を用意する案のほうがよいか
2. 品質保証と監査へ: J-6 で必須レビュアを置かない判断は、1名の期間の自己承認を「記録として誤読される」とした。監査の側から見て、「承認が無い」配布と「自己承認がある」配布のどちらが説明しやすいか
3. 規格へ: J-3 の「検査の入力」の定義は、ISO/IEC/IEEE 29119 や JIS の語彙で既に名前がある概念か(test basis・test item・test environment のどれに当たるか)。既存の語があるなら、その語に揃えたい
4. 擁護へ: J-3 の 1 文は ADR-0033 決定2 を変えずに足す、と起草は読んだ。G-5 の「判定基準は8つのまま変えない」(決定1)の局面の設計に、入力の欠落で失敗する経路を足すことが、決定1 の「段階で基準の数が変わらない」と衝突しないか
5. 全員へ: J-2 で `deploy.yml`・`publish-standard.yml` を `ci.yml` へ統合すると、`ci.yml` の変更は ci-gates の「統制の設定の陰性の確認」に当たる種類の変更になる(本リポジトリは案件でないので課されない)。本リポジトリ自身がこの確認を行うか、行わないと明記するか
