## 1. 立場と、全体の見立て

1. **本 Issue の大半は、新しい規範の不足ではなく、既に決めたことが実物で成り立っていない事象である**。ADR-0052 決定1・2(配布物を検査し、版を記録する)は `dist/standard` で成り立っていない。ADR-0033 決定2 の論拠(実施していない検査を実施した記録にしない)は、`check-gate-criteria.mjs` の 3 方向目と `check-provisions.mjs` の空ディレクトリで破られている。直す側は実物であり、ADR ではない
2. **#277 の 1 文案「検査の対象が存在しないとき、検査を通過として扱いません」は、字面のまま採ってはならない**。第4章 G-5 L509 と ADR-0033 決定2 に正面から反する。誤りは ADR ではなく、起票の文の語の選び方にある。#277 の事象は「対象が存在しない」ではなく「検査器の入力が実行環境に無い」で、別の事象である。標準に足すなら、この 2 つを分ける 1 文に限る(J-3)
3. **#293 の受入条件 2「submodule 不在は『対象なし』として明示される」と、受入条件 3「Environments 承認」は、そのまま受入条件にしない**。前者は ADR-0033 の語を誤用している(サブモジュールの不在は「対象なし」ではなく「未実施」)。後者は、1名の体制で自己承認を要求する形になり、記録として成立しない(`qms-document-control.md` L41・L43、Prevent self-review)。保護の実体は Environment の配布ブランチの制限である
4. **#280 の 3 点のうち、段の中の順序と検査定義の鮮度は「課さないと明記する」**。前者は信頼性ではなく効率の事項で、外部の実務も「層ごとに選べ」で割れている。後者は製品先例が無く、根拠は 1 事例である。PR の判定を基底ブランチの構成・記録で行う既存の規定(`CG` L141・L143・L148、`template-repository.md` L712)と CI の再実行で、信頼性の上の害は塞がれている
5. **標準本文の「本サイト」の自己言及は、検査で真を保てない限り、規範の頁に置く価値より誤る危険が大きい**。`GS` L147 の注記は誤っている(誤りは注記の側。行の要件は正しい)。`CG` L281 の注記は現に真で、直さない

### J-1 CI で走る検査の一覧を 1 か所に置く

**判定: 採る(運営)。1-A + 1-B。**

- 正本: `package.json` の `check`。#292 で `ci.yml` が `npm run check` を 1 回呼ぶ形になったため、`ci.yml` の側に一覧は無い。乖離が残るのは説明の側だけである(調査 1 §1.1.3)
- 説明の側の文の案(列挙をやめ、正本を指す):
  - CLAUDE.md L60: 「`npm run check` — 検査の一覧は `package.json` の `check` が正本。push 前に必ず通すこと。CI(`ci.yml`)は PR と main への push で同じコマンドを実行する」。**CLAUDE.md は利用者の指示のファイルであり、書き換えは利用者の了承を得てから行う**(エージェントの判断だけで変えない)
  - README L66・CONTRIBUTING L18: 「`npm run check` # 全検査(一覧は package.json の check)」。あわせて、手順に `git submodule update --init --recursive template` を足す(J-9 の 1)
  - CONTRIBUTING L24、PR テンプレート L11、`PM` L57: 「`npm run check` が通る」とだけ書き、「textlint + build」を消す
  - `PM` L66: 「CI のジョブ `check`(`ci.yml`)を required status check に指定する」
- 機械の確認(1-B): `check` の中に、`ci.yml` が (i) `pull_request` と `push`(main)を契機に持ち、(ii) `run: npm run check` の手順を持ち、(iii) その手順・ジョブに `continue-on-error` が無いことを確かめる検査を置く。テンプレートの `verify-gate-contract.mjs`(IMPL-0142)と同じ型で、本リポジトリへの適用である。ADR-0074 の型(G-5 の 3 条件)で見ても、YAML の読み取りで偽陽性が無く、修正でき、作業ツリーに違反が無い
  - 限界として書くこと: この検査は `ci.yml` が `check` を呼ばなくなった変更を、手元の `npm run check` で止める。CI 自身が呼ばなくなれば CI では走らない。ブランチ保護の必須チェック名との突合はしない(ルールセット 0 件)

  - 1-C(一覧の文書を置き、突合する): ADR-0052 の検討した選択肢「一覧そのものが第3の正本になる」で既に退けた形。退けた理由を覆す材料は無い

  - D3(集約の実行記録を正にする): 本リポジトリは `check` が 1 ジョブで、集約ジョブを別に持たない。実行記録は乖離の後でしか見えない

### J-2 `deploy.yml`・`publish-standard.yml` が CI を待たない

**判定: 採る(運営)。** 両方を、同じコミットの `ci.yml` の成功の後にだけ走らせる。

- 形: `on: workflow_run: workflows: [CI] types: [completed]`、ジョブの条件に `github.event.workflow_run.conclusion == 'success' && github.event.workflow_run.event == 'push' && github.event.workflow_run.head_branch == 'main'`、checkout は `ref: ${{ github.event.workflow_run.head_sha }}`。`publish-standard.yml` は `VERSION.md` のコミットにも `GITHUB_SHA` ではなく `head_sha` を書く(J-4・J-6)
- `workflow_dispatch` は両方に残す(失敗後の再実行の経路)。配布は J-6 の Environment の制限で起動元を main に限る
- `publish-standard.yml` のパスの条件(`src/content/docs/**` ほか)は `workflow_run` では使えない。生成器が決定的で、同じ内容なら `dist/standard` の差分が `VERSION.md` だけになる。毎回配るか、ジョブの中で前回の配布と比べて変化が無ければ push しないかは、実装者が決める(どちらも信頼性に差が無い)
- 選ばなかった案:
  - `ci.yml` の中に公開・配布のジョブを `needs: check` で置く: 同じ実行の同じコミットで確実だが、PR を契機とするワークフローに `pages: write`・`contents: write` のジョブが同居する。ジョブ単位の権限と `if` で閉じられるが、Scorecard の Token-Permissions(最上位は読み取り、書き込みは必要なジョブだけ)の勧めと、ファイルの単位で権限の範囲が見える現状を崩す。`workflow_run` で同じ保証が得られる
  - 独立のまま、失敗時の公開を開示するだけ: 正本(GitHub Pages)と案件の取り込み先(`dist/standard`)に、検査に落ちた版が出る。待たせない理由を記録した決定は無く、守る過去の決定が無い
- `graphify-update.yml` の `[skip ci]` のコミットでは CI が走らないため、公開・配布も走らない。中身は `graphify-out/` だけで公開物に入らないので、害は無い。これを書き留める
- 根拠水準: 運営の事項で EV マークは要らない。`workflow_run` の `head_branch` が push のときに `main` を返すことは GitHub Docs で確かめていない(実装者が確かめる)

### J-3 検査の対象・入力が無いときの扱い

**判定: 採る。** 運営は 3-A + 3-C + 3-D。標準は 4-B を 1 文に限る。4-A(1 文案をそのまま置く)は採らない。

#### 標準側

- **ADR-0033 決定2 は誤っていない**。案件の最初の変更が文書だけになることは、本標準の順序から必ず導かれる(ADR-0033 の影響の節)。この局面で検査を失敗させると、標準に従う案件が必ず G-5 で止まる。1 文案を字面のまま置けば、ADR-0033 の置き換えになり、その材料(「対象なし」で通した記録が害を生んだ事例)は調査に 1 件も無い
- 事象の区別: 「対象なし」は**案件に対象が存在しない**状態(`GC` L536 の表「適用しているが、現時点で対象が存在しない状態」)。#277 の事象は**対象は存在するが、検査器が読む先が実行環境に無い**状態で、検査が実施されていない。ADR-0033 決定2 の論拠「0件の合格として残すと、実施していない検査を実施したという記録が残る」は、後者にこそ当たる
- 文の案(`GC`「検査対象が存在しない場合の扱い」、L530 の「実装が存在する段階で…」の段落の後):
  > 検査の実行環境に、検査の入力(検査が読むファイル、検査に要る依存)が無いことは、「対象なし」に当たりません。この場合、その検査を実施しなかったものとして、失敗に数えなければなりません。
- 実装マーク: テンプレートの `g5-local.mjs` L33-38 と CI の `gate-g5` は、依存の取得の失敗を失敗に数える(調査 1 n12)。降ろし先は既存の登録に無い(`g5-local` の id は無い)。`gate-contract` は集約の構成を読むだけで、入力の有無を見ない。降ろし先を新設するか、`state=undelivered` で付けるかは実装者が `impl-targets.yaml` を見て決める。降りていないなら `undelivered` で表示し続ける
- 根拠水準: 定義の部分(入力の不在は「対象なし」でない)は ADR-0033 決定2 の論拠からの帰結で、マークは要らない。「失敗に数える」の選択は、外部の多数派(pytest・Jest・ESLint・coverage.py は既定で失敗。go test・Codecov は通過)に乗る判断で、効果の測定は無い。**`:::caution[暫定 EV-NNNN / 見直し 2027-04]`、E1**。差し替え条件: 入力の不在で失敗した検査のうち、環境の一時的な不具合(取得の失敗の再試行で通るもの)が過半を占め、検査を外す変更(ADR-0074 決定4 の「外した」の記録)が生じた場合
- 新 ADR: ADR-0033 を補う決定として、新 ADR に記録する(置き換えではない。ADR-0033 の状態行は変えない)
- 選ばなかった案:
  - 4-A: 上のとおり ADR-0033 決定2・`GC` L509 と衝突する。誤りは 1 文案の語
  - 4-C(標準に足さない): テンプレートの実装(依存の取得の失敗を失敗に数える)が標準に根拠を持たないまま残る。採用者が「入力が無いので対象なし」と読む余地を残す。ADR-0033 決定6 は「実装が存在する段階」の限定で、入力の不在を直接には塞がない
  - 4-D(`skip` の記録の様式を規範にする): 記録の項目は「対象なし」について既に L524-528 にある。入力の不在は記録して通すものではなく失敗にするものなので、様式を足す必要が無い
  - A3(未実施・対象なし・通過を別の値で残す): 結果を別の値で残すことは望ましいが、CI の上で非 0 に丸められる(調査 2 §2.1)。合否の規則として失敗を定めれば足りる
  - A4(検査ごとに通過側・失敗側を宣言させる): 宣言で外せる規則は、ADR-0028・0036・0071 が退けた「記入者の裁量で外す欄」と同型

#### 運営側(本リポジトリの検査)

- 3-A: `check-gate-criteria.mjs` の 3 方向目で KB が無ければ「配布した知識ベースの検査を実施しませんでした(template/ 未初期化)」を出す。現在は KB を見たときと同じ「(一致)」を出しており、記録が偽になっている
- 3-D: `check-provisions.mjs` は、置き場が空のディレクトリのときも「検査できなかった置き場」に数える
- 3-C: 飛ばす 4 本と上の 2 本は、環境変数 `CI` が真なら失敗にする。手元では飛ばした旨を出して通す
  - これは `check-template-drift.mjs` L9-10 の過去の決定(クローン直後に失敗させない)を、手元について守る。CI ではサブモジュールを取得している(#292)ので、飛ばす場面は取得の失敗か取得の手順の削除しか無く、どちらも止めるべきである
  - `check-impl.mjs` が手元でも失敗させる振る舞いは変えない。過去の決定より厳しい側にあり、誤りではない。統一は信頼性を上げないため、統一だけを理由に変えない
- 3-B(手元でも全体を失敗): 採らない。drift の L9-10 の決定を覆す材料が無い。ただし README・CONTRIBUTING に初期化の手順を足す(J-9 の 1)
- 3-E(現状維持): 採らない。黙って通る 2 本は記録を偽にしている
- #293 の受入条件 2「submodule 不在は『対象なし』として明示される」は、「submodule 不在は『実施しなかった』として出力され、CI では失敗する」へ読み替えて閉じる。理由を Issue に書く

### J-4 配布物そのものの検査段

**判定: 採る(運営)。2-A + J-2。** 新 ADR は要らない。

- `check-gate-criteria.mjs` に `--kb <path>` を足し、`publish-standard.yml` の「知識ベースを生成する」の直後・push の前に `node scripts/check-gate-criteria.mjs --kb dist-standard/tailoring-kb.json` を走らせる。落ちたら配らない
- 検査の中身: ADR-0052 決定1(判定基準の総数が第4章と一致)、決定2(`source.commit` が在り、`'unknown'` でなく、配る版の `head_sha` と一致)、決定3(`criteriaComplete` が全ゲートで `false`)。`'unknown'` を通している現状は決定2 の実物の欠落で、テンプレート側の KB の検査にも同じく当てる(J-9 の 2)
- ADR-0052 との関係: `publish-standard.yml` は初版から ADR-0052 決定2・4 をコメントで引いており、`dist/standard` は作った時点から ADR-0052 の配下として扱われていた。決定1 の「配布物」に `dist/standard` が入ると読むのが、実装者の当時の理解とも合う。食い違うのは帰結の「`npm run check` が検査する」という置き場の記述だけで、帰結は決定ではない。採用済み ADR の本文は書き換えず、本 Issue の新 ADR(J-3)の経緯に「`dist/standard` の検査は配布のワークフローに置いた」と 1 文残す
- 選ばなかった案:
  - 2-B(配布の中で `check` 全体を走らせる): J-2 で CI の成功を前提にするため重複する。重複は害ではないが、配布のワークフローがサブモジュールを取得するようになり、配布の失敗の原因が増える。配布物の検査は生成した物そのものに当てる 2-A で足りる

  - 2-D(週次の事後検査): 誤配を配った後でしか見つけない。案件は submodule でコミットを固定するため、誤った版が案件の記録に残る
- EV-0038(件数の一致で足りるか)は動かさない。本件は件数の検査を置く場所の欠落で、件数で足りないことを示す事例ではない

### J-5 #280 の残り

### J-6 配布用ブランチの保護と手動起動の起動元

#### 運営(本リポジトリ)— 採る(7-A + 7-B)。ルールセット(7-C)は先送り

- **順序が決定的に重要**: 利用者が先に Environment `dist-standard` を作り、配布ブランチを `main` に限る(「Selected branches and tags」)。管理者の迂回を外す。**そのあとで**ワークフローに `environment: dist-standard` を足す。逆の順序だと、参照した名前で保護の無い Environment が自動で作られ、保護したつもりで素通しになる(調査 2 §2.3【一次】)
- ワークフロー側: ジョブ先頭で `github.ref`(`workflow_run` では `head_branch`)が main であることを確かめ、違えば失敗させる。これは起動元の枝でファイルを書き換えれば外せる。誤操作(手動起動の枝の選び間違い)を止めるもので、悪意の変更は止めない。その旨をコメントと文書に書く
- 必須レビュアは置かない。1名の体制では起動者と承認者が同じ人になり、Prevent self-review を使えない。`qms-document-control.md` L41・L43 の「承認者として登録されている者の操作」の形だけを満たす自己承認は、承認の記録として意味を持たない。**#293 の受入条件 3「Environments 承認」は「Environment の配布ブランチの制限」へ読み替えて閉じる**。理由を Issue に書く
- 止まらない経路の文書化(置き場: `PM` の Git 戦略の節か、`publish-standard.yml` の冒頭のコメント。両方を勧める):
  - `contents: write` を持つワークフロー(`graphify-update.yml`、任意の枝で足されたワークフロー)は、`GITHUB_TOKEN` で `dist/standard` へ書ける。Environment はこれを止めない
  - ルールセットは 0 件で、`dist/standard` は保護されていない
- 7-C(`dist/standard` のルールセット)は**先送り**。足りない材料: ルールセットのバイパス主体に GITHUB_TOKEN(github-actions)を指定できるか、またはデプロイキーを指定でき、デプロイキーを Environment の秘密情報に置けば main からの配布だけが書けるか。調査 1・2 とも確かめていない(調査 2 は「デプロイキーの記載は頁に無い」)。確かめたうえで、閉じる設計(ルールセットで更新を制限し、バイパスを Environment の秘密情報にだけ置く鍵に限る)を別 Issue で採否する
- 7-D(`workflow_dispatch` を外す): 採らない。J-2 の `workflow_run` と Environment の制限で起動元は main に限られ、失敗後の再配布の経路が要る。外しても、任意の枝で `on: push` のワークフローを足せば書ける経路は残り、守りにならない
- **これらの設定は利用者の操作を要する**。本 Issue の実装者はワークフローと文書の変更までを行い、設定が済むまで「Environment 未設定」を文書に開示し続ける

#### 標準 — 既存の文の限界を開示する(採る)+ 配布用ブランチの要求事項は課さないと明記する

- 文の案(`CG`「デプロイゲート」の箇条書きに足す。フェーズ5 の記述):
  - 「Environment は、ワークフローが参照する前に作り、保護規則を設定する。参照した名前の Environment が無ければ、保護規則の無い Environment が自動で作られる。この構成での操作は、承認者として登録された者の操作ではないため、G-8 の承認の記録として扱わない([QMS 文書管理](/process-compass/phase6-operation/qms-document-control/))」

- 置き場: `CG` デプロイゲート。7-E の `risk-catalog.md` は採らない。リスク台帳は受け止めの所在を示す表で、構成の限界の開示に向かない
- 選ばなかった案:
