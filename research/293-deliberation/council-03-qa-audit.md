## 1. 立場と全体の見立て

1. **本 Issue の中心は「CI が正しいかどうか」ではなく、「検査を通らずに外へ出る経路があるか」である**。作業ツリーの `ci.yml` は `npm run check` を走らせる。しかし、公開(`deploy.yml`)と配布(`publish-standard.yml`)は検査の成否を待たない。入力の無い検査は 2 本が「一致」「違反なし」と出して通る。配布は任意のブランチから起動でき、起動元のファイルを書き換えれば ref の確認も Environment も外れる。**3 つとも、出力の上では合格と区別できない**。監査の側から見て、これは「検査が無い」より悪い。検査した記録が偽になるからである(ADR-0033 が「0件を合格として扱う」を退けた理由と同じ)
2. **一覧の正本は `package.json` の `check` 1 か所にし、説明の側では列挙しない**。そのうえで、ワークフローが `check` を呼び、公開と配布がその成功に従うことを、静的な契約検査で確かめる。文書の列挙は、作った瞬間から古くなる。10-08 から 7 本以上増えた事実が示す
3. **#277 の 1 文案は、字面のままでは採れない**。G-5 の「対象なし」(ADR-0033 決定2)と衝突する。ただし衝突を理由に何も置かないのも誤りである。標準には「対象が存在しない」と「検査器が対象を読めなかった」を分ける語が無い。案件の CI でも、取得の漏れ(サブモジュール・部分取得・パスフィルタ)で同じ黙った通過が起きうる。**「対象なし」の定義の側を絞る 1 文**を G-5 に置く
4. **配布の保護は、ファイルの外の 3 段(Environment の配布ブランチの規則・環境の秘密情報・ルールセット)で閉じ、強制 push をやめる**。ジョブ先頭の ref の確認は、誤操作の検出として残すが、統制として数えない。管理者(ソロ期は所有者)が設定を変えられることは消せないので、開示する。標準側には「統制と資格情報を、起動元のブランチで書き換えられるファイルの中だけに置かない」を置く。根拠は publishing-hub 1 件ではなく、GitHub の一次文書の挙動と、テンプレート自身の `delegation.yml` の穴である
5. 採る案は、どれも**証跡が残る形**に限る。設定の存在は、配布のジョブの事前確認と定期の確認で記録に出す。「設定した」と文書に書くだけの形は採らない

### J-2 公開と配布が CI を待たない

**判定: 採る。**

- 要件: 公開(Pages)と配布(`dist/standard`)は、**同じコミットに対する `npm run check` の成功の後にだけ**実行する。公開と配布のジョブは、そのコミットを取り出す
- 実装(推す): `ci.yml` に公開と配布のジョブを移し、`needs: check` と `if: github.event_name != 'pull_request' && github.ref == 'refs/heads/main'` を付ける。依存が 1 ファイルの中に見え、J-1 の契約検査が静的に確かめられる
- 配布の契機は、現状どおり本文・データ・生成器の変更に限ってよい。限るなら、パスの判定もジョブの中に置き、契約検査の対象にする。配る内容が前回と同一なら、新しいコミットを作らない(J-6 で履歴を積むため)
- `[skip ci]` のコミット(graphify)は、どのジョブも起動しない。次の push で全体が検査される。この経路は開示する

選ばなかった案:

- 現状維持: CLAUDE.md は Pages を「正本」と書く。検査(根拠水準・節番号・実装マーク・判定基準の件数)に落ちた正本が、自動で公開される。正本の信頼性を直接損なう
- `workflow_run`(別ファイルのまま CI の完了で起動): 要件は満たせる。ただし依存がワークフロー名の文字列で結ばれ、名前を変えると黙って動かなくなる(安全側に倒れるが、気づかれない)。`head_sha` を取り出す手順を書き忘れると、既定ブランチの先頭を配る。推さないが、要件と契約検査を満たせば認める
- 公開・配布のジョブで `npm run check` を重ねて走らせる(2-B): 同じ検査を 2 回走らせても、検査の成否と公開の結び目は変わらない。結び目を `needs` で作るほうが記録が 1 つになる

根拠水準: 運営の決定。マークは不要。

### J-3 検査の対象が無いときの扱い

**判定: 採る(運営)+ 採る(標準。ただし原案の文は採らない)。**

運営(本リポジトリの検査):

- 3-B + 3-D を採る。検査器の入力(template のサブモジュール)が無いとき、`check-gate-criteria.mjs`・`check-provisions.mjs`・`check-template-drift.mjs`・`check-skill-provisions.mjs`・`check-recalibration-registry.mjs`・`check-template-fields.mjs` は、`check-impl.mjs` と同じく**失敗**させ、初期化の手順(`git submodule update --init --recursive template`)を出す

- 理由: (1) 同じ `npm run check` の中に、飛ばす 4 本・黙って通す 2 本・失敗 1 本が並んでいる。監査で「どの結果が実施を意味するか」を説明できない (2) 飛ばす理由(クローン直後に失敗させない)は、`check-impl.mjs` が失敗するため既に成り立っていない(発見6) (3) 本リポジトリに、template が無いまま `check` が通ってよい正当な場面は無い。公開と配布は template を要しないが、J-2 で `check` の成功の後にだけ走る
- 3-C(手元では飛ばし、CI では失敗)を採らない理由: 手元と CI で同じコマンドの意味が変わる。`CS` L108「ローカルで通れば CI でも通る」を、本リポジトリ自身が崩す。手元で飛ばした結果を「通った」と読む誤りが残る
- 3-A(「飛ばした」と出すだけ)を採らない理由: 終了コードが 0 のため、CI の結果の一覧では通過と区別できない。出力の文言は記録として読まれない
- 3-E(現状維持)を採らない理由: 「(一致)」と「違反なし」は、検査した記録を偽にする。ADR-0033 が「0件を合格として扱う」を退けた理由そのものである

標準:

- 原案の文「検査の対象が存在しないとき、検査を通過として扱いません」(4-A)は採らない。`GC` L509「『対象なし』として証跡へ記録したうえで通過させます」と ADR-0033 決定2 に字面で逆である。採れば ADR-0033 の置き換えになるが、覆す材料(対象なしの記録で通した誤りの事例)は調査に無い
- 4-C(何も足さない)も採らない。ADR-0033 の「対象が存在しない」は、案件のリポジトリに対象が無いことを前提に書かれている。しかし、その前提を文で定めていない。**案件の CI が検査器の読む先を取得しなかった場合(サブモジュール・部分取得・パスの絞り込み)、検査器から見れば対象は 0 件である**。この状態を「対象なし」として記録して通す読みを、現行の文は止めていない。ADR-0033 決定6 が止めるのは「実装が存在する段階」だけで、基準6・7 のように実装の有無と関係の無い対象には効かない
- 採る文(4-B を、語の定義として置く)。置き場は `GC`「検査対象が存在しない場合の扱い」の第 2 段落の直後:

> ここでいう「対象が存在しない」は、案件のリポジトリに検査の対象が無いことを指します。検査器が読む先(サブモジュール・生成物・取得しなかったファイルなど)を実行環境へ取得できなかった場合は、これに当たりません。この場合は、検査を実施できなかったものとして、失敗に数えなければなりません。「対象なし」の記録に書く理由は、リポジトリに対象が無いことの説明でなければなりません。

- テンプレートは既に降りている(`g5-local.mjs` の「依存の取得の失敗で実施できない検査は失敗に数える」、調査 n12)。実装マーク `target=g5-local`(降ろし先の登録を足す)と、CI 側(gate-g5 のジョブ)に当たるものを付ける。CI 側でこの区別が実装されているかを私は確かめていない。確かめて降りていなければ `state=undelivered` で付ける
- ADR との関係: ADR-0033 の置き換えではない。決定2 の「対象が存在しない事実」の範囲を定めるもので、決定2 の理由(実施していない検査を実施したという記録を残さない)から導かれる。#293 の新 ADR に「ADR-0033 決定2 の語の範囲の明確化」として記録する。ADR-0033 の本文は書き換えない
- 根拠水準: 文そのものは ADR-0033 の理由からの演繹で、新しい値を持たない。ただし「案件の CI で取得漏れによる黙った通過が起きる」ことの観測は本リポジトリの 1 件(E2)と、外部の fail closed の勧め(二次)だけである。**暫定マーク E1**(この文脈での測定は無い)、見直し 2027-10。差し替え条件: 案件の G-5 の記録で、「対象なし」の理由が取得の失敗だった件数と、この文で失敗にした件数のうち、正当な対象なしだったもの(偽陽性)の件数

### J-6 配布用ブランチの保護と手動起動の起動元

**判定: 採る(運営・標準とも)。**

#### 運営(本リポジトリ)

| # | 措置 | 置き場 | 起動元の枝でファイルを書き換えた場合 |

| a | **配布ブランチを孤立させず、前回の配布コミットへ積む**(親 = 前回の `dist/standard` の先頭)。強制 push をやめる | ワークフロー | — |

- (c) の理由: Environment の配布ブランチの規則は `GITHUB_REF` に照合される(一次、survey-293-2 2.3)。起動元の枝のファイルで `environment:` を残せば規則で止まり、消せば秘密情報に届かない。ルールセット(b)が `GITHUB_TOKEN` の書き込みを止めるので、どちらでも配れない。**Environment は参照より先に作る**(存在しない名前を参照すると保護なしで自動作成される。一次)
- 必須の承認者について: ソロ期は自分で承認することになり、独立の確認にはならない(Prevent self-review を有効にすると配れない)。それでも、AI が main へ push した版を人が見ずに案件へ配る経路を閉じ、承認者と時刻が記録に残る。「決められた場所では必ず人間が触る」の場所として置く。独立でないことは (f) で開示する

- 選ばなかった案: 7-A(ファイルの中だけ)は、起動元の枝で外せる。7-B(Environment まで)は、`environment:` を消した枝の `GITHUB_TOKEN` が `contents: write` で書ける。7-C は採る案に含む。7-D(`workflow_dispatch` を外す)は、push を契機とする任意の枝のワークフローが `dist/standard` へ書ける経路を閉じない(問題は手動起動ではなく、書き込みの権限がファイルの中で決まること)。C3(アーティファクトの配布へ寄せる)は、案件が submodule で参照する形(pit-in-template#35)を変える。本 Issue の材料で決められない。**先送り**とし、何が足りないか(案件側の取り込み方の要件)を別 Issue に書く

#### 標準(`CG`「デプロイゲート」に 1 節)

- 文の案(`CG` L877 の箇条の後):
