### 1.2 必須になる条件が条文でどう書かれているか(食い違い)

条件は4つの出所に分かれ、同じではない。

1. **CL3**(0763): 規則 r-e-cl3。故障挿入とミューテーションの両方を「必須チェック」と書く。案件ごとの値(`answers['q-criticality']`)。
2. **F.2 の Q1「人身への危害が生じうる制御があるか」**: 起案(`ruling-deferred-draft.md` L312)は「CL3 または Q1 が はい」と書く。しかし条文側では、F.4 の表は **ミューテーション=安全関連部で HR、R1 で R、R2 で R**、**故障挿入=安全関連部で HR、R1 で R**(`safety-verification.md` L156-164)。つまり附属書F が HR とするのは「安全関連部」であって「CL3」ではない。CL3 は規則 r-e-cl3 の note が F.4 を引いて必須チェックに格上げしている(F.4 は「強く推奨。しない理由を記録」で、必須ではない)。**F.4 の HR(理由を記録すれば省ける)を G-5 の失敗(省けない)に格上げする**点が、新しい義務の核である。
3. **安全関連部の判定**: G-7 基準7 が「Q1 が はい、または CL2・CL3」を安全関連として扱う(F.2 本文)。起案の「CL3 または Q1」は CL2 を落とす。CL2 の扱いは条文で未決(r-e-cl2 は CI の必須チェックを強化しない。`tailoring-guide.md` L1117 は CL2 を「同左」)。
4. **規制業**(0836): 軸C の `q-quality: quality-regulated`。CL とは別軸。

**Q1 は構成に機械の値として存在しない**。template の `process.config.json` の `ci` は `coverageThreshold` `failOnSeverity` `allowedLicenses` `strengthened` のみ。`config.mjs` に Q1 の参照は無い(grep で見つからず。2026-11-19)。CL3 と規制業は `answers` から読めるが、Q1 を条件にするなら構成に値を足す必要がある。さもないと「条件に当たる構成」を機械が判定できない。

**R との関係(ADR-0039 決定4)**: CL は案件ごと、R は変更ごと。F.6 は「R1 の変更を優先」と書く(変更ごと)。毎回の PR で全量を回すのではなく、F.6 の表「実行範囲=差分に対する増分実行」が条文上の答え。案件ごとに段を必須にし、変更ごとの範囲は増分で絞る二層になる。R1 の優先は、段の存在の検査(案件ごと)では閉じず、変更ごとの判定になる。

### 1.3 「故障挿入」と「ミューテーション」の重なり(条文の曖昧さ)

F.5 の分類表(L181-190): 「実行前の挿入=ミューテーション試験として CI で実行する」「実行時の挿入=運用から切り離した環境(試験台の実機または模擬環境)」「ハードウェアによる挿入=専門部門の設備」。つまり**CI で回せる故障挿入=ミューテーションであり、独立の `faultInjection` 段として CI に置けるのは「実行時の挿入」のうち模擬環境で回せるものだけ**。起案の3段(mutation・faultInjection・regulatory)のうち faultInjection は、mutation と区別できる内容が CI 上にほぼ無い。実機・試験台のものは CI の外。段を分ける理由と中身を条文で定義しないと、空でない別名のコマンドで通せる。

### 1.4 ADR-0151 のどこを広げるか

ADR-0151 決定1: 空の任意の検査(lint・audit・licenses・install)は失敗にしない。「テストの実行と秘匿情報の混入検査は、この扱いを受けない」。決定3: 継続の長さで差し戻さない・閾値を課さない・**7.3 の例外承認の対象にしない(「7.3 は基準の不充足を承認する手続で、未実施の通過には入口が無い」)**。検討した選択肢で「実装の開始後は空を失敗にする」を「採用者への新しい義務(重)」として採らなかった。
実装の所在: `template/scripts/gate/adapter.mjs` L72 の `OPTIONAL = new Set(['lint','audit','licenses','coverage','install'])` 以外が空なら失敗(L75-83)。冒頭 L12 の注釈は必須の段を test・secretScan と書く。広げる対象は**決定1 の「任意」の線引き**: 新しい段 mutation・faultInjection・regulatory を、条件つきで「必須」側へ入れる(adapter.mjs は段の集合を固定の定数で持つため、条件つきの判定の導入が必要)。

また `gate-g5.yml` の集約ジョブ(L514-527)は needs の列挙が固定で、`mutation` 等のジョブを足さないと集約に入らない。条文 `gate-criteria.md` L772「判定基準を実装する検査は集約の合否に含めなければならない」。

### 1.5 7.3 が G-5 に使えない根拠の所在(起案の言い方は不正確)

起案(L312)は「7.3 の例外承認は G-5 に使えない」と書く。条文の所在は次のとおり。
- `exception-escalation.md` L62: 7.4 が後回しを禁止とした対象(G-4・G-5 の判定)を**実施しないまま**進めるために 7.3 を用いない。ただし同行は「実施した判定・検証で個々の判定基準を満たさない場合に本節を用いることは、条項が例外を認めないと定めた基準を除き、妨げない」と続く。L181 の表は G-5 を「禁止」(短縮の禁止)。
- 7.3 の要求事項2は「満たさない**基準の項目番号**」を記録させる(L26-)。
- 判定基準は G-5 の8つ(`gate-criteria.md` L744-757)。ミューテーション・故障挿入・規制要件はこの8基準のどれでもない。

よって、(a) 段が空=実施していない、は L62 により 7.3 の対象外(根拠あり)。(b) 段を実施して閾値を満たさない場合に 7.3 を使えるかは、新しい段が「基準」になるかで変わり、現状は**未規定**。「G-5 に使えない」と一括りにすると L62 の後半と食い違う。ADR-0151 は「未実施の通過」に限って入口が無いと言っており、実施した検査の閾値割れは扱っていない。

### 2.1 外部から言えること(確認できた範囲)

- 機能安全の規格は故障挿入を**強さを段階づけた手法の一つ**として扱い(推奨/強く推奨)、「CI の合否の必須の段」とは書かない(B5 の抜粋の範囲)。必須の段にするのは本標準の判断であり、規格を根拠にできない。これは規則 r-e-cl3 の reason が「機能安全の規格が人数を求める、という主張ではない」と書く態度と揃う。
- Google の実務(B1)は、変異を変更行に絞り、開発者に生き残りを見せる運用。**スコアの閾値で合否にする**根拠は B1 の要旨からは取れない。ツール既定(B2)も break=null で、落とす閾値は利用者が置く値。
- 閾値を合否にすることへの批判(B3)は、同値変異・遺産コード・開始値の恣意。F.6 が「外部の数値をそのまま閾値にしない・既存コードの実測から較正」と書くのは、この批判と整合する(推測: 起案者はこの批判を読んでいない可能性があるが、結果は一致)。
- 「必須のジョブが skip されると通過になる」穴は、GitHub の仕様として文書化されている(B10・B11)。`gate-g5.yml` の集約ジョブは `if: always()` で needs の結果を見る型で(L514-527)、failure・cancelled を落とす。**skipped は落とさない**(`contains(needs.*.result,'failure')||'cancelled'` のみ。L528)。新しい段を条件つきジョブ(`if:`)にすると、条件が偽のとき skipped になり、集約は通る。「空なら失敗」を実装するなら、段の判定を skipped ではなく明示の失敗で返す設計が要る。

## 3. 選択肢と3つの問い

### 論点1 必須になる条件の書き方

| 案 | 内容 | 利点 | 難点 |

### 論点2 閾値

- **2-a 標準が数値を置く**: F.6 が「本標準は値を定めない」と明記し、外部の数値をそのまま使わないとある。実証の裏づけも見つからない(B2 の 80/60 は表示の既定値)。置けば条文の自己矛盾になる。採らない案の候補。
- **2-b G-1 で案件が定めて記名(起案)**: F.6 と整合。構成の値 `ci.mutationThreshold` を機械が読み、記名と日付は G-1 の記録。**値の妥当性(実測からの較正か)は機械で閉じない**(manual/adopter で開示)。閾値が0でも「段は在る」。「閾値の存在と数値の型」までを機械で検査し、値の妥当性は判定者。
- **2-c 閾値の代わりに「変更行の生き残り0件、または理由つきの除外」**: B3 の「変更行に絞れば初日から通せる」に近い。ただし F.6 の「スコアの閾値による合否」の条文を変える。
- 閾値の未設定の扱い: 1.7.7(値が無ければ宣言の欠落)に従う案と、段の失敗にする案がある。ADR-0166(IMPL-1001)は分量の上限の未設定を欠落に数えず G-7 を落とさないと決めた前例で、同じ型を取るか、安全関連で変えるかが論点。

### 論点3 CI で実行できない段(HIL・外部の認証機関)

- **3-a(起案)**: 採用者のコマンドが外部の実行の記録(所在・日付・版)を照らし、無ければ失敗。コマンドは任意の中身を返せるため、「記録を照らす」ことが実質あるかは機械で閉じない(論点5)。
- **3-b 7.3 の例外承認**: 1.5 のとおり、実施しない=L62 で対象外。実施して基準を満たさない=未規定。段を新しい基準にしない限り、7.3 は入口が無い。3-b を採るなら、段を基準の側へ入れる条文改訂が要る(採用者への義務が増える)。
- **3-c 段を CI に置かず G-7(出荷判定)の記録で受ける**: 附属書F F.7 の安全適合性の検証記録(様式 09)。G-5 は機械判定・即時という性格(`gate-criteria.md` L744 見出し)。実機の結果は即時でないため、G-7 側に置くほうが性格に合う、という見方がある。ただし「空なら G-5 失敗」という所有者の方針とは別の案。
- 外部認証機関の検査は、規格の求める独立した確認(第1章 1.4 の距離の段)の領域で、CI の段の仕事ではない(推測)。

### 論点4 小さいチーム

- 条件に当たる構成は、すでに大半が小さいチームでは成立しない: r-c-regulated-small-team-not-allowed(1〜2名×規制業は構成を認めない)、CL1 以上×1〜2名も構成を認めない(`rules-criticality.yaml` L111 のコメント・ADR-0028)。**よって条件に当たる構成は、3名以上が前提で、小さいチーム固有の省き方は既存の規則が先に塞いでいる**。新しい省略の条項は要らない、という答えが条文から導ける(事実)。
- 残る場合: Q1=はい のみの構成(CL が低く、チームが小さい)。ここは論点1-c と同じ問題。
- 変異試験の時間は小さいチームほど響く(推測)。増分を採用者のコマンドが受けるので、標準が省き方を書く必要はない。

### 論点5 「コマンドが在るが中身が空」の開示

- adapter.mjs の検査は `cmd.trim()` が空かだけ(L75)。`true` や `echo ok` のコマンドは通る。F.6 の「生き残りの一覧を残す」も、出力の存在までしか確かめない(推測: 出力の形式を決めないかぎり)。
- 機械で閉じる範囲(決定可能): 段のコマンドが空でない・閾値が数値・出力ファイルが存在・出力に閾値と算出値が構文として載る・算出値≧閾値。閉じない範囲(自由な文の意味): コマンドが本当に変異を作っているか、閾値の較正が実測に依るか、除外が不当でないか。CLAUDE.md のコアポリシー(統制の閉じ方を裁定で決める)に従い、manual/adopter として根拠水準マーク(ADR-0026)で開示する。既存の前例: ADR-0151 決定4。
- 実行での確認(陰性の確認): 起案は「実装の段で確かめる」。調査としては、`gate-g5.yml` の `if:` による skipped の穴(2 の末尾)を、実装後に実行で確かめることを推す。

## 4. 既存の ADR・条項との突合で気づいた矛盾

1. **起案(L312)の「CL3 または Q1」は、F.4 の「安全関連部」(HR)・G-7 基準7 の「Q1 または CL2・CL3」と一致しない**。CL2 が落ちる。また F.4 の HR は「しない理由を記録すれば省ける」で、必須ではない。ADR で「HR を G-5 の失敗へ格上げする」と明示しないと、F.4 の本文と食い違う。
2. **規則 r-e-cl3 の note は「故障挿入試験とミューテーション試験を CI の必須チェックに加える」だが、F.5 の分類では CI で回る故障挿入=ミューテーション**(1.3)。独立の `faultInjection` 段の中身が定義されていない。
3. **「7.3 は G-5 に使えない」は不正確**(1.5)。L62 の後半と食い違う。ADR に書くなら「実施しない通過」に限ると書く。
4. **ADR-0151 決定3「閾値を課さない」は継続期間(N 出荷)の閾値の話**で、ミューテーションスコアの閾値とは別。ただし読み手が混同しうる。ADR 本文で区別する。
5. **ADR-0151 の検討した選択肢「実装の開始後は空を失敗にする」を採らなかった理由**(道具の無い言語・社内の閉じた道具の採用者を抜け道か例外の連続に追い込む)は、本件でも成り立つ。条件を CL3・規制業等に狭めることで解けるか、は会議体の論点。mutation の道具の無い言語(ADR-0151 が挙げた型)では、3-a の外部の記録を照らす経路が実質の唯一の入口になる。
6. **G-5 の基準は8つで変えない**(`gate-criteria.md` L1008「判定基準は8つのまま変えません」)。新しい段を失敗にするなら、基準の追加か、既存の基準(1 または 2)の内訳かを決める必要がある。基準にしない段が失敗を出すと、7.3 の項目番号・G-8 の異議・保証の開示の対応づけが宙に浮く。
7. **ADR-0040(様式は第6章の部分集合)**: 閾値を様式 06 の欄にしない起案は整合。構成の値(`ci.mutationThreshold`)は template-fields の対象外だが、構成の値の宣言の欠落(1.7.7)との関係を確かめる必要がある。
8. **規制業の regulatory 段(0836)の中身が未定義**。r-c-regulated は「規制要件の自動チェック」とだけ書き、何を照らすか(どの規制・どの規則集)を条文が持たない。ミューテーションと違い、F.6 に当たる手続の節が無い。段の枠だけを置くと、中身が空の `true` で通る典型になる。外部の先例(B13)は policy as code だが、IEC 62304・FDA・FISC の具体は見つからなかった。
9. **起案の「regulatory は規制業」と IMPL-0839(規制業の AI 生成箇所の追跡)・IMPL-0837(規制当局向けエビデンス)**との境界が未整理。0837 は issue=355 で別に追う。

## 5. 確かめられなかった点

- ISO 26262-6 の表の正確な表番号と ASIL ごとの強さ(二次資料間で不一致)。IEC 61508-3 Table B.2 の SIL3・4 の強さ。DO-178C・EN 50128/50716・ISO/IEC/IEEE 29119-4 でのミューテーション/故障挿入の扱い。いずれも原文未読。
- Petrović らの本文の数値(生き残り提示の採用率、有用と判定された割合)。要旨のみ。
- PIT の incremental/history の仕様、mutmut の incremental。
- 医療(IEC 62304・FDA)・金融(FISC・PCI DSS)の自動適合チェックの具体的な先例。見つからなかった(不在の確認ではない)。
- カオスエンジニアリングのゲート化は分散システムの可用性の実務で、安全関連の故障挿入(F.5)への適用の先例は見つかっていない。
- Q1 を構成が持つか(grep で見つからなかったのみ。他の経路で持つ可能性は残る)。
- 小さいチームでの変異試験の所要時間の実測は無い。
- 実行での確認はしていない(adapter.mjs・gate-g5.yml は読んだだけ)。skipped の穴が本件の設計で実際に開くかは、実装後の陰性の確認が要る。
