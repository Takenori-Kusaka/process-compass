外部から言えること【推測を含む】:
- 期間を機械的な固定値で定める型(会社法: 2週間/1週間)は、同時に「全員の同意による省略」と「定款による短縮」の二つの逃げ道を持つ。固定値と全員同意が併存するのが法の型。
- 期間を持たず、沈黙を同意とする型(Apache: 72時間、lazy consensus)は、72時間を下限の目安としつつ、コード変更では適用しない除外を持つ。「沈黙=同意」は、本標準の R1(沈黙を同意と読み替えない)と逆向きの型で、R2・R3 の扱いに近い。
- 緊急経路(ITIL)は期間の最短値ではなく、「誰が(ECAB の構成)」「どれだけ急いで(例: 24時間)」「後で何をするか(実施後レビュー)」を定める。数値は組織ごと。
- 機械の強制の型は二つ。止める型(GitHub 必須チェック・Gerrit の `submittableIf`)と、通知にとどめる型(本標準の現状)。止める型は例外(GitHub の管理者回避、Gerrit の `overrideIf`)を必ず持つ。

## 4. 既存の ADR・条項との突合で気づいた矛盾

1. **IMPL-0214 と 3.10.5 の食い違い**: IMPL-0214 のマークは R2 に `pre-review-closed`(受付終了+全意見へ起案者の応答)を必須とするが、3.10.5 の R2 は「異議なしとみなして判定へ進む」。応答が付かない意見が残っていても R2 は進める条文と読めるため、R2 の必須チェックは条文に無い義務になる【確認】。3.10.4 の「起案者は全ての意見へ応答を記載する」を進行の条件にする根拠は、3.10.2 の T−1 行にある程度。マークを条文に合わせて見直す必要がある。
2. **ADR-0200 決定4 と impl-targets.yaml 355**: 双方が「必須にしない・重の審議に残す」と書く。審議の結論が「作る」なら、両方の書き換えが要る【確認】。
3. **IMPL-0830 の note とテンプレートの検出の範囲**: 議長の案は「公開が遅い」と「締切が T−2 より遅い」の両方を検出するとするが、template の読めた範囲(463〜494)は公開だけ【確認、全文は未読】。
4. **EV-0281 の二つの前提**: 7.4 の限定列挙に事前レビュー期間が無い点は、所有者の決定(30)で「7.4 を適用した工程ゲートに限り短縮できる」とされ、読み B(3.10.2 が経路を置く)が採られた。ただし 7.4 の「ここにないものを短縮してはなりません」と B の関係は、7.4 側に注記が無い限り読み手には矛盾に見える【推測】。7.4 に一文足すか、3.10.2 側に「7.4 の限定列挙の例外ではない。G-6 などの行為の短縮ではなく、その事前レビュー期間の短縮」と書くかの二つ。
5. **G-6 の応答・判定の時間と T−5**: G-6 は応答1営業日・判定2営業日(gate-criteria 1285)。工程ゲートに 3.10.2 の T−5 を課すと、G-6 の SLA の方が短い。3.10.1 は工程ゲートに非同期コメント期間のみを課すとするが、期間の長さまで規定するかは本文から読み切れていない【要突合】。もし工程ゲートでは通常期間でも T−5 より短い運用が既にあるなら、下限の議論は工程ゲートでは、現状の運用との差を先に確かめる必要がある。
6. **3.10.9 の「R1 と同じ扱い」の範囲**: 3.10.5 の「判定へ進めない」だけを指すのか、3.10.2 の R1 の長い期間(T−10)も指すのかが条文から決まらない【確認:条文は「3.10.5 の R1 と同じ扱い」と書く】。下限の議論で、必須応答ロールを含む R2 案件の期間が T−10 かどうかで結論が変わる。
