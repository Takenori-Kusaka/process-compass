### 1.2 語の定義(`overview.md` 用語表 [確認])

- 席: ロールの別称(責務と判定ゲートの組)。責任者: 席の結果責任を負う記名の自然人、席ごとに1名。担い手: 席の作業を行う実行主体(人、または AI の実行主体の文脈)。独立は人の単位でのみ用いる。
- 認証情報: 用語表に独立の定義は無い。`:126` の「分離」は「作業領域・セッション・認証情報が別」、`:140` は3.5.3 の「認証情報」を「実行主体の文脈を分ける単位としての、担い手の資格情報」とする。つまり**認証情報の単位は席でなく担い手(文脈)**。
- 担い手の名義: 専用・共有・未申告。人のアカウントとの共有は別の行で既に離脱。

### 1.3 同一人物が複数の席を兼ねるとき、1つの認証情報で帰属が損なわれない根拠(条文側)

- ADR-0082 の根拠は G-7 条件4=「承認したアカウントを人へ対応づけて確かめる」。アカウントと人の対応は `gate-criteria.md:90`(数値の識別子で名簿の人へ対応づける)による。**1アカウントが1人に対応する限り、同一人物が席を兼ねても対応は崩れない。崩れるのは、1アカウントを複数の自然人が使うとき**。 [確認](条文の連鎖)。この連鎖を一文で書いた条文は見つけていない [推測を含む]。
- 禁止でない組(価値責任者×技術判断者、事業決裁者×価値責任者ほか)は、3.5 が人の単位の兼務を許している。人の兼務を許し、その人の認証情報を分けさせると、許可した兼務が構成の離脱になる。これが食い違いの実質。
- 人の単位で兼務が禁止の組なら、同一人物は既に 3.5 の禁止(または D-1・列挙に無い離脱)に当たる。認証情報の共有を理由に重ねて数える必要は薄い [推測]。

### 1.4 AI の実行主体の認証情報の扱い

- 名義の行: 担い手を宣言した席で、名簿の人のアカウントを使える構成=共有、未申告も共有扱い。専用は数値の識別子で申告し、実行環境で照合(`roles-responsibilities.md:715-726`、ADR-0107)。
- template の機械: `template/scripts/gate/config.mjs:198-216` の `sharedCredentialForbiddenPairs` は、禁止の組(`separations`、unit: context を除く)の2席の担い手が同じ数値の識別子の専用アカウントを申告した場合だけ離脱に数える。禁止でない組のAI-AI 共有は数えない(IMPL-1004)。
- 席ごとの認証情報の区別を AI の担い手に課す条文は、禁止の組を除き見つからなかった。

### 1.5 離脱に数えたときの帰結

- 列挙に無い離脱があれば、適合の主張と逸脱を伴う適合の主張は出せず、述べられるのは適用の表明まで(`overview.md` 1.10.2)。措置は定めない(ADR-0133)。数えた件は表明の「列挙に無い離脱の一覧」に載る。
- 1名の体制は、出荷判定者×事業決裁者と AI維持管理者×AI運用担当者の兼務で既に常に離脱。同一人物の兼務側を緩めても、1名の主張の名は変わらない [確認(ADR-0133 決定2)]。影響を受けるのは 2名以上の体制。
- template の contract: 名簿は「同じ数値の識別子のアカウントを2人に書く」ことを**拒否する**(`config.mjs:826-830`、1つのアカウントは1人に対応づける)。一方 ADR-0147 は、AI の担い手の共有申告は「拒否すると構成を記録できず離脱を表示できないため、拒否せず注記」と決めた。扱いが対象ごとに違う [確認]。

### 問い3: 共有が避けられない場面を、新しい条項なしで受けられるか

- 7.3 は使えない: `exception-escalation.md:60` が認証情報の分離を対象外とし、条項が名指した場合だけ対象になる。名指した前例は G-8 の配備の資格情報のみで、理由は「日付のある行為で解ける」こと(ADR-0141 決定5)。恒常的な break-glass はこの基準に合わない [確認+推測]。
- 案I(定義で外す): 項(2)の「同じ認証情報を使う」を「使用の時点で個人が識別されないまま使う」に限る。共有の認証情報へ入る前に個人が認証され、その記録が残る場合は当たらない。根拠は C1 の IA-2(5)、C2 の 8.2.2(操作を個人へ帰属)。結果と証跡だけを書く型(問い1の方針)に合う。**新しい条項を足さずに受けられる**。ただし「個人が識別される」は機械で閉じない(manual、根拠水準マークが要る)。
- 案II(離脱のまま開示): 緊急用の共有は離脱に数え、適合の主張を出さない。避けられるのに避けない場合と区別できず、採用者が緊急用アカウントを申告しなくなる動機を生む(ADR-0134 が退けた型と同じ懸念 [推測])。
- 案III(新しい条項で 7.3 を名指す): 例外は期限付きの形になるが、break-glass は期限で解けない。**採らない方向**を調査者は推す [推測]。
- ソロ(1名)と同一人物の兼務: 項(2)は「別の自然人」を要するため当たらない。禁止の組は項(1)と既存の離脱(出荷判定者×事業決裁者など)に残る。1名の体制の主張の名は変わらない(§1.5)。

### 問い5: 3.5.3 側を変えないこと

- 意味は変えない: 条件1(586)・レーンの定義(589)・表前文(652)・IMPL-0299 のレーン設計は触らない。表3 の理由文(`:666`「席ごとに分けられる」)と 3.5.1 の「ロールごとに」(`:544`)は、**語の食い違いなので文言の直しが要る**(編集に近い)。「3.5.3 を変えない」は意味では成り立つが、字面は 2 か所に及ぶ。
- 3.5.3 を「席ごと」に揃えた場合(所有者は不採用): 全ての席が別の認証情報を持つ。7つのロール別 clone(3.5.1)と受信箱ラベルが指すレーン(ADR-0037)の設計が崩れ、禁止でない兼務を許した 3.5 と 3.5.2 の例外、template の `MAILBOX` と D-0 の写像、IMPL-0299・IMPL-0649・IMPL-0829 が連動して変わる。1〜2名の体制は、許した兼務ごとに認証情報の別を求められ、実質的に兼務を禁止する。

## 4. 既存の ADR・条項との突合で気づいた矛盾

1. 1.10.2(710・730・739)の「席ごと」と 3.5.3 条件1・表前文の「禁止の組」が割れる(本件の核)。さらに同じ 3.5.3 の表3 の理由文(666)が前者に寄る。
2. ADR-0133 決定3 の「認証情報を席ごとに分けていない構成は離脱」は、採用済みの文で書き換えない。新 ADR で一部置き換えることになる。ADR-0035 決定2 の表の3も同様。
3. IMPL-1004 の文面(「兼務を禁止した組でない席どうしの認証情報の共有は数えていない」)は、直したあと、同一人物分は「離脱でない」、別人分は「数えていない」に分かれる。IMPL-0521 の note と ADR-0147 決定2 の「両方の読みで離脱に当たる部分だけを機械にする」も、読みが変わる。
4. 名簿の contract(別人の重複を拒否)と、AI の共有申告(拒否しない)の扱いの差(§1.5)。
5. 同じ issue=446 の計画マークとして IMPL-0651・IMPL-0900(移行支援担当×出荷判定者の組が template に無い)が残っている。認証情報の食い違いとは別の論点で、本群の範囲か未確認。
6. 7.3 の対象外と、問い3 の案I の関係。案I は 7.3 を使わず、定義で外すので矛盾しない。案III は 7.3 の対象の限定(ADR-0134・0141)を拡げる。
7. 1.10.2 の注記(730・739)の「席ごとに認証情報を分けている」は、2名の体制が主張に至る条件の1つ。ここを書き換えないと条件の文だけ古くなる。
8. 附属書・template 側の波及(D-0 節12 の表「認証情報を共有している範囲」=IMPL-0829、構成書の注記)の中身は読んでいない。

## 5. 確かめられなかった点

- ISO/IEC 27002:2022 の 5.16〜5.18・8.2 の本文、PCI DSS v4.0.1 の 8.2.1 の原文と 8.2.2 の条件の原文、SOX の ITGC、GitHub の two-person review における同一人物の複数アカウントの扱い。
- 同一人物が複数の席を1つの認証情報で兼ねても帰属が損なわれないことを、一文で書いた条文(§1.3 は連鎖からの読み)。
- 「3名の同一人物の承認」の ADR の個別の突合(grep の「同一人物」は多数の ADR に出るため、本件への直接の関係は追っていない)。
- template の D-0 様式・構成書で、認証情報と席の対応が現在どう書かれているかの全体(config.mjs の関連部分のみ読んだ)。
- 項(2)を採ったとき、機械が数える対象の誤検出・見逃しの実測。実行して確かめたものは無い。
