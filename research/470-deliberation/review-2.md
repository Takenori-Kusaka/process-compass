## 新しい所見

### N-1(高・表示と実態の食い違い)「プロセス構成のファイルに触れる変更には規則を当てない」は、コードではファイル 1 つを除くだけ

- 所在: 本体 `human-ai-boundary.md` 5.5.1 の規定 B の新しい箇条「プロセス構成のファイルに触れる変更には、規則を当てない。規則の変更そのものを、外した変更に数えない」、IMPL-1081・1082 の note「プロセス構成のファイルに触れる変更を除いた変更に当て」。template `check-pr.mjs` と `aggregate-evidence.mjs` の `matchable`(`process.config.json` のパスを変更の一覧から除くだけ)
- 再現:
  - 場面 A: 規則 `tools/**` の下で、`process.config.json`(task.maxChangedLines)と `tools/a.js` を同じコミット(R3)で変えた。集約はこのコミットを「外した」1 件に数えた(hits = internal-tools)
  - P1: 同じ形の PR に、check-pr は「規則に当たる変更である(当たった規則: tools)…読む対象から外れる」と知らせた
  - 場面 F: 規則 `**` の下で、正規の経路(変化点)と同じく `process.config.json` と `PROCESS-PROFILE.md` を同時に変えて規則の理由を直した(R2)。このコミットは「外した」件数に入った。今回の直しで、規則を変えると PROCESS-PROFILE.md に規則の表が出る。そのため、変化点を通した規則の変更はほぼ必ずこの形になり、R1-2 は正規の経路で直っていない。試験の場面は `process.config.json` だけを変えるので、この経路を見ていない
- 影響: 条文と note は「触れる変更」を外さないと言い、確定の場の知らせと開示の件数は外したと言う。広い規則の下では、規則自身の変更の記録を規則が外せる
- 直し方の案: 両方の `matchable` を「変更のどれかが `process.config.json`(名前の変更の元を含む)なら、その変更に規則を当てない(matched を空にする)」へ直す。試験に「構成と規則のパスのファイルを同じ変更で触れる」「構成と PROCESS-PROFILE.md を同時に変える」場面を、check-pr と集約の両方へ足す。コードを直さないなら、条文と note を「プロセス構成のファイル(process.config.json)そのものは規則に当てない」へ直し、正規の経路の規則の変更が件数に入ることを開示する(ただし R1-2 の裁定に反する)

### N-2(高・表示と実態の食い違い)安全重要度を範囲の途中で変えた構成で、開示が、確定の場で外した変更を「当てていない」と出す。条文の新しい箇条の理由づけが逆向き

- 所在: 本体 5.5.1 の新しい箇条「範囲の途中で安全重要度を CL1 以上から下げた構成では、集約は全規則を『当てていない』と表示し、外した件数を出さない。外した範囲を少なく見せる側ではなく、多く見せない側に倒す」。ADR-0276 の「影響」の同じ趣旨の行。IMPL-1082 の note。template `aggregate-evidence.mjs` の `noApply = cl1Of(config) || … || items.some((i) => i.notApplied)` と、`choiceReviewOf` の `cl1Of(config)`(HEAD の構成)
- 再現:
  - 場面 B(下げる): CL1 で規則 `tools/**` を置き、CL0 へ下げるコミット、続けて `tools/b.js` のコミット(R3)を積んだ。後のコミットは hits = internal-tools(確定の場の check-pr は、基底が CL0 なので「当たる」と知らせる。基底が CL0 の当たりの知らせは試験の場面で確かめた)。集約の行は「当てていない(安全重要度 CL1 以上・規制業の案件では、規則を置いても外さない)」だけで、外した件数が出ない
  - 場面 C(上げる。条文は書いていない): CL0 で `tools/a.js` のコミット(R3)の後に CL1 へ上げた。最初のコミットは、確定の場で「当たる」と知らされた形なのに、集約は HEAD の CL1 から notApplied にし、行は「当てていない」だけになる
- 影響: 規定 B の件数の開示は「外した範囲を読み手へ示すため」に出す。上の 2 つの場面では、確定の場で読まなかった変更があるのに、内側と外側の開示は「外していない」と言う。条文の「多く見せない側に倒す」は、外した件数を 0 と見せる(少なく見せる)ことで、文が実態と逆である。安全重要度を上げる場面(案件が重くなったとき)はまれではなく、条文にも開示が無い。test-direct-commit-rules の場面「変更の親の版が安全重要度 CL1 以上なら、HEAD が CL0 でも当てていない旨を出す」は、この表示を正しいものとして固定している
- 直し方の案: 変更ごとの判定(親の版の CL・規制業)だけで数え、規則ごとに「外した N 件 / 当てていない M 件 / 範囲の変更 T 件」と出す。`noApply` は、どの変更にも当てていない場合だけに限る。`choiceReviewOf` の `cl1Of(config)`(HEAD)は外し、確定の場の check-pr と同じ線(PR の基底と先頭)にそろえる。条文の箇条と ADR の行は「途中で安全重要度を変えた構成でも、変更ごとに外した件数と当てていない件数を出す」に直し、test-direct-commit-rules の同じ場面の期待を直す。直さないなら、条文の文の理由づけを「外した変更があっても件数を出さず、少なく見せる」と正しく書き、外側の開示にも同じ限定を出す
