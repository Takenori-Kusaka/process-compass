## 論点1 どの案を採るか → (c2) を推す

- 理由1(ADR-0112 との整合): ADR-0112 決定1 は、S1 の軽さの所在の1つを「独立レビュー(G-6)の範囲(コア機能)」と決めた(`gate-criteria.md:1289`、`tailoring-guide.md:490`)。同じ決定は、その限定を項目2 に載せるとも決めた(`gate-criteria.md:1290・:1429`)。一方、集約は `g6Applied`(`aggregate-evidence.mjs:2322`)で範囲を見ず、場面A と B は同じ結果になる(survey §3)。採用済みの決定が実装に届いていない状態で、しかも項目2 が掛けていない緩和を宣言している。直すのは実装である
- 理由2(ADR-0065 との整合): ADR-0065 決定1 の前提3(`adr/0065:46`、`tailoring-guide.md:511`)は、S0 の期間の未確認の変更を限定なしに欠落とする。ADR-0112 も「決定1 を維持する」と書いた(`adr/0112:19`)。(c2) は前提3 の字句を変えないので、採用済み ADR の読み替えを要しない。規定として書く量は、非対称の理由の1文で足りる
- 理由3(非対称を規定として正当化できる): S0 の変更は、コア指定が無い期間(前提1、`:509`)に「全部使い捨て前提」(`:473`)で書かれた。コアと非コアの区分は、S1 への切り替えで後から付く(`:480`)。後から付けた区分で S0 の変更を範囲の外へ出すと、S1 で宣言するパスを狭めるほど過去の未確認が消える。S1 の期間の変更は、区分を知ったうえで書かれる。`:480` の「PoC がそのまま本番化する事故」とも向きが合う
- 書き方の案(`tailoring-guide.md:490` の直下、前提3 の表の注記の両方に置く): 「S1 の G-6 の範囲(コア機能)は、S1 以降の期間の変更に掛かる。S0 の期間の変更には掛からない。前提3 のとおり、S1 以降の出荷の範囲に入れば全変更を確かめる」。期間は変更の親のコミットの構成の事業ステージで分ける(先例 `aggregate-evidence.mjs:2576-2598` の `stageOf(before)`)
- 新しい義務: 無い。S0 の扱いは現行の本文の字句と実装のまま。S1 の扱いは現行の本文(ADR-0112)のままで、実装を本文へ寄せるだけである

### 他の案を落とす理由

- (a) のみ: 前提3 の字句(全変更)と S1 の範囲の食い違いを、本文に残す。どちらに従うかが読み手に委ねられ、規定として閉じない
- (b): ADR-0112 決定1 と EV-0230 を改め、S1 の採用者へ非コアの変更の独立レビューを課す。採用者への新しい義務と ADR の決定の変更に当たり、**採るなら重へ上げるべき**。本件の材料には、ADR-0112 の判断を覆す新しい事実が無い。食い違いの原因は実装の未達であり、決定の誤りを示す実行の結果は無い
- (c1): 前提3 を狭める。採用済み ADR-0065 決定1 の文言を新 ADR で読み替えることになる。理由3 のとおり、後から付けた区分で過去の未確認を外す抜け道を開く。信頼性を下げる向きなので採らない
- (c3): 本文と実装の差を開示で残す。ADR-0112 決定2(升とエンジンの出力の一致)の趣旨に反し、項目2 の宣言を不正確なまま残す。採らない

## 論点2 パスを宣言していない構成の扱い

- 推す扱い: `core-only` でもコア機能のパスが未宣言(`touchesCore` が null、`config.mjs:2087-2091`)なら、全変更を欠落に数える。欠落の文に「コア機能のパスが未宣言のため、G-6 の範囲を限れない」を添える。項目2 の「範囲の限定(コア機能)」の表示も、未宣言のときは「宣言したが掛けていない(パスが未宣言)」と出す
- 理由: `tailoring-guide.md:584` の「黙って全変更の数で通さない」と同じ規則を G-6 の範囲にも使える。未宣言を範囲の外として通すと、宣言しないことが最も軽くなる。追跡中のファイルに1件も当たらない宣言も、`corePathsOf` のとおり未宣言と扱う(`config.mjs:2061-2063`)
- 新しい義務か: 無い。未宣言の S1 は今の実装と同じ数え方である。S1 の軽さを得るのにパスの宣言が要る、という条件が明示されるだけである。本文へ「範囲の限定はコア機能のパスの宣言を前提とする」を書く

## 論点3 コア機能の判定の材料 → `:584` の定義(2つのパス、`corePathsOf`)へ揃える

- 理由: 同じ G-6 の中で、軸C「高」のコア機能2名(`:584`、IMPL-0091)が既に2つのパスで判定している。G-6 の範囲だけ別の定義にすると、1つのゲートでコア機能が2通りになる。`riskFloor.rules[].paths` はリスク区分を上げる宣言であり、それを範囲に含める方が数える変更が多い(安全側)
- `:181`(10名以上、IMPL-0084、`protectedPaths` だけ)は本件で揃えない。揃えると 10名以上の採用者に別所属のレビュアの対象を広げる義務が増え、本件の範囲の外の新しい義務になる。差の存在と「本件では揃えないと決めた」ことを記録し、既存の open Issue へコメントで送る。揃えるなら重
- 落とす案: `protectedPaths` だけに揃える案は、IMPL-0091 の判定を狭めることになり、品質「高」の採用者のコア機能2名の対象を減らす。採らない

## 論点4 ブランチ保護との差

- 推す扱い: ホスティングの必須の承認数は変えない(`generate-profile.mjs:1054`)。本文の G-6 の範囲の箇条(`:490` 付近)へ「ホスティングの必須の承認数はパスで分けられないため、PR の経路では全変更に承認が掛かる。範囲の限定が効くのは、出荷の証跡の集約が数える欠落である」と書き、項目2 の範囲の限定の行にも同じ旨を出す
- 理由: 本文より厳しい側の差であり、本文の統制を割らない。差を書かないと、採用者は S1 で非コアの PR を承認なしで併合できると読む
- 落とす案: 承認数を0にし、CODEOWNERS のコードオーナーのレビューでコア機能だけを止める案。所有者の割り当てと名簿の対応を新しく要し、パスの宣言の誤りがそのまま無承認の併合になる。ホスティング側の錠を外す変更であり、本件の材料では信頼性を確かめられない。採らない(要るなら別の Issue で重として扱う)

## 論点5 実装の印

- `tailoring-guide.md:490` と `gate-criteria.md:1289` の G-6 の範囲の箇条: `target=evidence-aggregation` の IMPL を新設する。集約を直して試験を足すまでは `state=undelivered`、試験(S1 の非コアの変更を欠落に数えない、S0 の期間の非コアの変更は数える、未宣言は全変更で数える の3場面)が通ったら `delivered check=machine`
- 非対称の注記(論点1)と未宣言の扱い(論点2)は、同じ IMPL に含めるか連番で分ける。試験の場面が別なので分ける方が追いやすい
- `gate-criteria.md:1406` の表の行2: 集約 `aggregate-evidence.mjs:3420-3445` が実装済みなので、`target=evidence-aggregation state=delivered` の印を付ける。試験は `test-tailoring-declaration.mjs`
- ブランチ保護の差の開示(論点4)は記述の規定であり、実行主体の挙動を制約しないので印は付けない
- 印を足した後に `npm run impl:write` で台帳を再生成する
