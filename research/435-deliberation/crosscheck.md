## 3. 指摘

### X-1 コア機能のファイルを移す PR が範囲の外になる(重大度: 中)

- 所在: `template/scripts/gate/aggregate-evidence.mjs:1914`(`git diff --name-only`)と `g6ScopeOf`
- 根拠: `git diff` の既定では名前の変更を検出する。`--name-only` は移した先のパスしか出さない。`src/core/a.js` を `src/ui/a.js` へ移す PR は、親の版と HEAD の版のどちらのパスにも当たらず、`outOfScope: true` になる(X2)。移した先で中身を書き換えても、類似度が閾値を超える限り同じ結果になる。宣言を狭めずにコア機能のコードを範囲の外へ出せる。歯止め2(後から狭めた宣言で範囲の外へ出さない)の趣旨に反する
- 「高」にしない理由: PR の経路では、ブランチ保護の必須の承認が引き続き掛かる。漏れるのは、4条件(名簿・指示者でない・外部・挙動要約)を満たさない承認の欠落の計上に限られる。同じ形は軸C「高」のコア機能2名(IMPL-0091)の判定にも以前からある
- 直し方の向き: 範囲の判定に渡すファイルの一覧に、名前の変更の元のパスを含める(`--no-renames`、または `--name-status -M` の両側)。移す前のパスで判定する場面を試験に足す。IMPL-0091 の同じ形は、既存の Issue へ足す

### X-2 「移行の後の最初の出荷」が S0 からの移行に限られている(重大度: 中)

- 所在: `rangeHasS0Period`、IMPL-0469・0470 の note、項目2 の数え方の文
- 根拠: 裁定2 は「移行の後の最初の出荷は、全変更で数える」とだけ書き、移行の元を限らない。実装は「出荷の範囲に親の版が S0 のコミットを含む」場合だけを対象にする。S2→S1 の移行(X5)と、S1 の範囲 all→core-only の移行(X8。CL1→CL0 の判定のやり直しなど)では、同じ出荷の中で移行の後の PR を限定する。移行の前の PR は、親の版が S1・core-only でないため全変更で数えられる(安全側)。差が出るのは、移行の直後の PR に限られる
- 直し方の向き: 議長が裁定2 の「移行」の範囲を明らかにする。移行の元を限らない読みなら、条件を「出荷の範囲に、親の版の構成が S1・core-only でないコミットを含む」へ広げ、項目2 の文と note を合わせる。S0 に限る読みなら、裁定の記録にその旨と理由を書く

### X-3 項目2 の状態の文が、範囲を限らなかった一部の変更を出さない(重大度: 低)

- 所在: `g6ScopeStateText`
- 根拠: 状態の文を変えるのは、HEAD の版でのパスの未宣言と、S0 から移った後の最初の出荷の2つだけである。親の版だけが未宣言の場合(X1)と、親の版が S1・core-only でない場合(X5・X8)には、一部の PR を全変更で数えている。それでも状態の文は「範囲の限定(コア機能)」のままになる。理由の欄の数え方の文が一般の規則を書いているため、開示が誤りになるわけではない
- 直し方の向き: 範囲を限らず数えた PR があれば、状態に件数を添える(例: 「うち N 件は範囲を限らず数えた」)

### X-4 CL1 以上の回答で古い core-only の構成のとき、PR ごとの限定が残る(重大度: 低)

- 所在: `g6ScopeOf`(段階と範囲だけを見て、安全重要度を見ない)
- 根拠: X6 では、PR は範囲の外に出る。一方で `pendingTightenings` の blocking が欠落に出るため、出荷は止まる。統制は保たれている。ただし、厳格化を適用するまで欠落の一覧に PR が並ばない
- 直し方の向き: 親の版か HEAD の版の回答が CL1 以上なら範囲を限らない分岐を、二重の歯止めとして足す。採らないなら、そう決めた旨を記録に残す
