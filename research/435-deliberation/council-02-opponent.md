# #435 会議体(軽) 委員2: 反対の立場

- 時点: 2026-11-11。本体 abb1e54、準拠テンプレート a15584f。読んだ所在は行番号つきで引く
- 立場: 起案されそうな (a)/(c2) の弱点を突く。欠陥と認めるものは認める

## 0. 欠陥と認めるもの

- 保証の開示の項目2 が「範囲の限定(コア機能)」を宣言している(`aggregate-evidence.mjs:3426・:3435`)。一方で集約の欠落の計上は範囲を見ない(`:2322` の `g6Applied`、`:2350` の `exceptionNeeded`)。**開示が、掛けていない緩和を主張している**。調査 §3 の場面A・B で再現済み。これは本件で必ず直す欠陥であり、(c3) の「差を開示で残す」は採れない
- 前提3(`tailoring-guide.md:511`)が戻る先の範囲を書かず、S1 の升(`:470`「適用(コア機能)」)と字句で食い違う。これも欠陥と認める

## 1. どの案を採るか

- 推す案: **(c2)。ただし §2〜§4 の4つの歯止めを条件にする**。歯止めの無い (a)/(c2) には反対する
- 理由: 本文の S1 の統制は「コア機能」(`:490`、`gate-criteria.md:1289`、ADR-0112 決定1)にあり、実装の方が本文から外れている。本文を厳しくする (b) は採用者への新しい義務(S1 の非コアの変更にも独立レビュー)を課し、ADR-0112 決定1 と EV-0230 を改める。CLAUDE.md の基準で**重**に当たり、軽の会議体では決められない
- (a) 単独を落とす理由: 前提3 の字句(全変更)と食い違いが残る
- (c1) を落とす理由: S0 の期間の変更を、**S1 へ移った後に宣言したパス**で遡って判定する(調査 §4.5)。宣言者は欠落を減らしたい側にいるので、後から狭く宣言すれば S0 の欠落が消える。前提3 を狭めるのは ADR-0065 決定1 の変更に当たり、軽では決められない。(c1) を採るなら重へ上げるべき
- 軽で決めることへの警告: (c2) は**実装を緩める向き**である。新しい義務は無いので軽の要件には当たる。ただし緩和の根拠 EV-0230 は E1(`tailoring-guide.md:496-500`)である。緩和を実効化すれば、暫定の判断が初めて機械の統制を外す。独立の突合では、§2〜§4 の抜け道を重大度の候補として必ず検査させる。「高」が出たら重へ上げる

## 2. パスを宣言していない構成の扱い

- 未宣言の構成と、宣言が追跡中のファイルに1件も当たらない構成(`config.mjs:2051` の `corePathsOf`。tracked を渡せば空振りを未宣言と扱う)は、**全変更を欠落に数え**、「コア機能のパスが未宣言のため範囲を限れない」と理由を添える。`:584` の「黙って全変更の数で通さない」と同じ向きにする
- 未宣言を範囲の外として通すと、「宣言しないこと」が最も軽くなる。逆向きの誘因は信頼性を壊す
- 宣言が狭すぎる抜け道: 様式は「全部非コアは不可」(`deliverable-templates.md:1075`)だが、機械は確かめない。`touchesCore` が偽になった変更の件数と比率を、項目2 の範囲の限定の行に**必ず併記**させる(「範囲外として数えなかった変更 N 件 / 全 M 件」)。読み手が狭すぎる宣言を見抜ける。件数を出さないまま範囲の外へ落とすことは採らない
- 遡って狭める抜け道: 集約は HEAD の構成で判定する(調査 §4.5)。出荷の直前にパスを狭めれば、S1 の期間の過去の変更も範囲の外へ出る。コア機能かどうかは、**変更の親の版の構成(`configAt`、`aggregate-evidence.mjs:1429`)と HEAD の構成のどちらかで当たれば、コア機能**とする(厳しい側の和)

## 3. S0 から S1 へ移る境目

- (c2) は期間を「変更の親のコミットの構成の事業ステージ」で分ける(`:2576-2598` の `stageOf(before)` が先例)。この分け方には**リベースの抜け道**がある。S0 の期間に書いた変更を、S1 へ移った後の main へリベースすると、親の構成が S1 になる。その結果、S0 の変更が S1 の軽い扱い(非コアは範囲外)を受ける。逆向き(古い S0 の基点から分けたブランチ)は厳しい側に倒れるので害は無い
- 機械はこの区別を完全には付けられない(作成日時は書き換えられる)。そこで次を条件にする
  - 移行の記録(`:480` の G-1 の条件「省略したゲートを適用へ戻し、コア指定をやり直す」。`/process-change` の記録)が無い構成は、S1 でも全変更を数える
  - 移行の後の最初の出荷の範囲は、全変更を数える(S0 の作業が持ち込まれやすい区間)。2回目の出荷から core-only を効かせる。この扱いは根拠が無いので EV で暫定を開示する
  - 境目を機械が区別しきれないことを、本文の前提3 の近くに「確かめない」として書く(`:515` の「機械が確かめるのは前提3 の扱いまで」の範囲を正確にする)
- 非対称の理由(S0 は区分が無い期間に使い捨て前提で書かれた)は (c2) の案どおりに書く。前提3 の字句と ADR-0065 は変えない

## 4. コア機能の判定の材料

- G-6 の範囲は **`corePathsOf`(`protectedPaths` と `riskFloor.rules[].paths` の和)** に揃える。`:584` の定義と、軸C「高」の実装(IMPL-0091、`aggregate-evidence.mjs:1416-1423`)に一致する。区分の下限のパスは「リスクを上げる」宣言なので、それを G-6 の範囲の外にするのは安全側に反する
- `protectedPaths` だけ(`:181`)に揃える案は落とす。宣言した下限のパスに触れる変更が独立レビューの範囲の外になり、緩める向きが二重になる
- 1つの標準に「コア機能」の機械の定義が2通りある(`:181` と `:584`。実装でも IMPL-0084 と IMPL-0091)のは欠陥と認める。ただし `:181` を揃えると10名以上の規則の判定の範囲が変わる。本件では揃えず、食い違いとして既存の open Issue へ送る。「揃えなかった」ことを記録に明記する

## 5. ブランチ保護との差

- ブランチ保護の必須の承認数は `generate-profile.mjs:1054` で範囲を見ない。GitHub はパスで承認数を分けられない(調査 §2.4)。そのため (c2) の緩和が実際に効くのは、**PR を経ないコミット**と、4条件を満たさない承認の PR だけになる
- これは逆の誘因である。PR を経れば非コアの変更にも承認が要り、PR を経なければ欠落にならない。ブランチ保護を迂回した方が軽くなる。歯止めとして、**PR を経ないコミットは S1 でも範囲を限らず欠落に数える**ことを条件にする(範囲の限定は、PR の経路で承認の4条件を満たさない場合にだけ効く)。これが採れないなら (c2) は信頼性を下げるので反対する
- 承認数を0へ下げる案は採らない(コア機能の PR の承認まで外れる)。CODEOWNERS による分割は採用者の任意とし、本文へ「PR の経路ではホスティングの必須の承認が全変更に掛かる」と開示する

## 6. 実装の印

- `tailoring-guide.md:490` と `gate-criteria.md:1289` の箇条に IMPL を付ける。`state=delivered` にできるのは、集約の試験が次の4点を固定してからとする。それまでは `undelivered` で表示する
  1. S1・CL0・宣言ありで、PR を経た非コアの変更は欠落に数えない
  2. 未宣言・空振りの宣言は全変更を数える
  3. S0 の期間の変更は全変更を数える(前提3)
  4. PR を経ないコミット(§5)と、親の版か HEAD でコアに当たる変更(§2)は数える
- 表の行2(`gate-criteria.md:1406`)にも IMPL を付ける。実装は `aggregate-evidence.mjs:3420-3445`。項目2 の表示には「範囲外として数えなかった件数」を加え、IMPL-0448 の試験(`test-tailoring-declaration.mjs`)で固定する
- 実装が入るまでの間も、開示の誤りは残せない。暫定として、項目2 の「範囲の限定」に「集約は現在、全変更を数えている」と添える

## 7. 採らない案の記録

- (c1): 遡った宣言で S0 の欠落を消せる。ADR-0065 決定1 の変更に当たり、重
- (c3): 開示が実装と食い違ったまま残る
- 歯止めの無い (a)/(c2): 未宣言・狭い宣言・遡った縮小・リベース・PR の迂回の5つの抜け道がある
