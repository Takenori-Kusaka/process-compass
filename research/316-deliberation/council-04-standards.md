# 会議体 #316 意見書 04: 規格(standards)の立場

- 日付: 2026-10-24
- 立場: 規格作成の作法(ISO/IEC 専門業務用指針 第2部 第9版、JIS Z 8301:2019、IEEE SA Standards Style Manual 2021、RFC 2119/8174)に照らして論じる。判断軸は、適合を主張する者と判定する者が、**文面だけから同じ要求事項の集合を取り出せるか**(識別可能性)である
- 根拠の表示: 〔内〕= survey-316-1-internal、〔外〕= survey-316-2-external、〔確〕= 本意見書のために自分で本文・テンプレートを読んで確かめたもの、〔推〕= 規格の原文を読めていない推測
- JIS Z 8301 は、私も原本を読んでいない。JIS の記述はすべて〔外〕の転載経由であり、EV-0096 の水準(E1)を超えない

## 0. 前提の整理(全議題に掛かる)

1. **規格の作法の核は「要素の種別を先に決め、文の形はその中でだけ効く」である**〔外 1.1・1.3・2.3〕。文末をいくら整えても、その文が載っている要素の種別が決まっていなければ、適合の条件かどうかは決まらない。R-1 が他の議題の前提になる
2. **JIS と ISO の向き**: JIS は平叙の「…する。」を要求の形の筆頭に置く(表3)。ISO は表3〜7 に現在形を置かず、平叙文を statement(情報)とする〔外 2.1・2.2〕。本標準は ADR-0063 決定2 で JIS の側(平叙の動詞文は要求)を採り、反対案「要求は『しなければなりません』に限り、平叙文は説明」を、書き換え漏れが義務の消失になるという理由で退けた〔確 ADR-0063〕。私はこの選択を**維持すべき**と考える。理由は3つ
   - 本標準は日本語で書かれ、日本の採用者・監査者は JIS の読み方で読む。ISO の読み方を採ると、JIS に慣れた読み手は平叙文を要求と読み、ISO に慣れた読み手は説明と読む。読み手の母集団に合わせるのが識別可能性に効く
   - 取りこぼしの向き。平叙=要求なら、誤りは「説明が要求に読まれる」側へ倒れ、監査で過剰に問われるだけで済む。平叙=説明なら、誤りは「要求が消える」側へ倒れる。信頼性の軸では前者が安全
   - ISO 側に寄せても日本語の文末に shall に当たる専用の印は無い(RFC 8174 の大文字に当たるものも無い〔外 2.4〕)。結局「しなければなりません」への全面書き換えが要り、その漏れが義務の消失になる
   - ただし、JIS の側を採る代価は「本体の規定要素から説明の平叙文を追い出すこと」であり、JIS はそれを注記・参考の附属書・解説への分離で払っている〔外 2.1 含意〕。本標準はこの代価を払い切っていない(R-3 の約 160 文)。**JIS の側に立つと宣言するなら、追い出しの作業までが一体である**
3. **定義語の一義性**: 箇条3(1.4)に置いた語は文書全体でその意味に限る(ISO 指針 5.6「Identical wording should be used to express identical provisions」〔外 5.2〕、用語の作法)。R-7 の「逸脱」と、R-5 で見つけた識別子 AC-N の衝突(後述)はこの規則の違反である

## R-1 フェーズ5・6 の頁の種別

### 結論
**フェーズ5・6 の全頁を、一体として「参考(手引き)」と宣言する**。頁ごとの種別分けは採らない。1.8 の「従属」という第3の区分を廃し、1.5 の2値(規定・参考)のうちの参考へ入れる。そのうえで:

1. フェーズ5・6 の頁に、要求と禁止の文末を置かない(参考の附属書と同じ扱い。1.5「参考の附属書に、要求事項と禁止を置きません」を広げる)
2. 本文がフェーズ5・6 を「によります/に規定します」で引く 39 件〔内 1.3〕を、すべて読み、2つに分ける
   - **委任型**(内容が本文に無い。例: `roles:80` 監査担当の任命基準、`human:646` 欠陥注入の記録に含める事項、`human:870` 操作の記録の項目、`tailoring:856` 様式): 内容を、製品名を落として本文(または規定の附属書)へ移す
   - **実装の所在の案内**(本文に要求があり、頁は手段): 「〜参照」の形へ改める
3. 頁が自ら置く定め(`template-repository` の定め1〜3、`git-strategy:39` の hotfix の緩和、`label-mailbox` の「義務化」)は、本文へ移すか、手引きの推奨・例示へ改めるかを1件ずつ決める。**緩める向きの定めは本文へ移さない限り効力を持たないと明記する**
4. 実装マーク 65 件は、規範の所在である本文の節へ付け替える(番号は保つ。ADR-0063 が附属書I の 2 件で採った処理と同じ)。`implementation-marking.md:35` は「参考の附属書にはマークを置きません…本文の所在にマークを付けます」と既に定めており〔確〕、フェーズ5・6 を参考とすれば同じ規則が掛かる。同 `:183` の「対象の頁」からフェーズ5・6 を外す
5. 各頁の表題(または frontmatter と冒頭)に「(参考)」を表示する。JIS 20.4・ISO 20.2 が附属書の見出しの下に種別を書かせるのと同じ〔外 1.1・1.3〕
6. 「第5章 4.5.2」の衝突: **手引きの頁は、本標準の条項番号と同じ形の番号を振らない**。`label-mailbox.md` の 4.1〜4.7 を廃し、第7章 `:232` は頁の表題と節名で引く〔確 `exception-escalation:232`〕。実行は #328、原則は本議題で決める
7. 移行が済むまで、移していない規範の件数を 1.8 の注記に開示する(暫定。EV を付ける)

### 理由
- **本標準自身の 1.7 が、フェーズ5 を規定にすることを許さない**。1.7 は「特定の製品名・組織内の口頭文脈に依存する表現は用いない」と定める〔確 `overview` 1.7 の箇条〕。フェーズ5 は GitHub・Claude Code・ラベル名・スクリプト名で書かれている。規定にするには製品名を抜く必要があり、抜いたものは本文の条項そのものになる。つまり「規定のフェーズ5」は、本文の写しか、1.7 違反のどちらかにしかならない
- **従属という区分には外部の先例が無い**〔外 7 の 1〕。ISO・JIS は要素の単位で規定か参考かを示し、IEEE は箇条単位の informative の札すら禁じる(「Interspersed normative and informative text is not allowed」)。JIS は本体・附属書・解説の3層を持ち、解説は「規格の一部ではない」〔外 1.3〕。フェーズ5・6 の性格(実装と運用の手段、本文を繰り返す)は、JIS の解説、または ISO/IEC/IEEE 24748-3(12207 の適用の指針、要求を繰り返さない)に当たる〔外 1.2〕
- **適合に数えるかが書かれていない要素は、識別可能性を壊す**。現状、1.5 はフェーズ5・6 を規定にも参考にも入れておらず、19 頁の禁止の文末が適合の条件かどうかを、誰も文面から決められない〔内 1.1〕
- 「迷う文は要求」(1.7.2)をフェーズ5・6 に掛けると、GitHub 固有の手順が要求になる。掛けないと、本文が「によります」で引く委任型の内容が効力を失う。どちらも誤りで、内容を本文へ上げるほかに整合する道が無い

## R-2 「〜できません/できない」

### 結論
1. **本文と規定の附属書の、文末(地の文の文末・箇条の末尾・表の升の末尾)に「〜できません/〜できない」を使わない**と 1.7.1 に定め、`lint:provisions` で機械検出する
2. 禁止の意味の 29 件〔内 2.1〕は、禁止の形(「〜しません/〜してはなりません」)へ改める。主文 16 件は規範の強さが変わらないことを確かめて改め、再掲 13 件は引いている規定の所在を示す形へ改める
3. 能力・不能の 93 件は、文末を可能性・能力の否定の形へ改める。1.7.1 の「可能性・能力」の行に否定の形「〜不可能です/〜ことはありません/〜場合はありません」を足す。文の途中の「できない」(「機械で検出できない事項は」「出荷できない状態」)は残してよい
4. その他 11 件のうち評価語(「受容できない」)は、判定者の判断の内容として「受容しない」へ、名称(「出荷できない状態」)は文中の名詞句として残す

### 理由
- JIS は「…できる/…できない」を許容と可能性・能力の文末のどちらにも使わない。禁止は表3 の「…(し)てはならない/…(し)ない」、能力の否定は「…不可能である」〔外 2.1〕。ISO で cannot は表6(可能性・能力)にだけ現れ、禁止には shall not を使う〔外 2.2〕。**どちらの作法でも、文末の「できない」を禁止に使う余地は無い**
- 「できません」は、禁止(本標準が認めない)と不能(事実として不可能)の両方に読める。禁止を不能と読まれると、規範が事実の記述へ落ち、強さを失う。例: `roles:349`「3 つの席は、どの2つも責任者を同一人物にできません」〔確〕は禁止だが、能力の記述としても読める
- **文末の形を禁じれば、機械は意味を判定しなくてよい**。1.7.4 は「できます」の意味の判定を人に委ねているが、「できません」は形で一律に禁じられるので、検査が閉じる。意味の判定(禁止か不能か)は、書き換えの時に1回だけ人が行えばよい

### 他の案を落とす理由
| 案 | 落とす理由 |
| --- | --- |
| 1.7.1 の禁止の行に「〜できません」を足す | 能力の否定と形が同じになり、93 件の能力の記述がすべて禁止と読まれる。JIS・ISO のどちらにも先例が無い |
| 1.7.1 の可能性・能力の行に「〜できません」を足し、禁止の 29 件だけ直す | 書き手が今後「できません」で禁止を書いたとき、能力として読まれ、規範が消える。形で区別できないものを形の表に入れることになる |
| 禁止の 29 件だけ直し、表と検査は触らない | 再発を止める手段が無い。読んでいない 114 件が生じたのと同じ経路が残る |

### 文の案(1.7.1 の箇条へ追加)
- 文末の「〜できません」を、規定の文末に使わない。禁止には禁止の形を、能力・可能性の否定には「〜不可能です」「〜ことはありません」「〜場合はありません」を使う。禁止と能力の否定が同じ形になるためである
- 文の途中の「〜できない」は、能力の記述として使ってよい(例: 「機械で検出できない事項は、人が確かめる」)

### 既存との矛盾と残る問題
- ADR-0063 の影響の節(「できません」の意味は今回読んでいない)を閉じる。ADR-0063 と矛盾しない
- **非対称が残る**: 1.7.1 は肯定の「〜できます」を可能性・能力の文末として残している。JIS は肯定の「…できる」も表5・表6 の文末に使わない〔外 2.1〕。本標準はこの点で既に JIS とずれている。本議題では決めず、EV-0096 の照合の対象として記録し、別 Issue で扱うことを提案する(肯定は許容への誤読が ADR-0063 で 10 件書き直し済みで、残る誤読の向きは許容の消失であり、禁止の消失より軽い)〔推: 誤読の重さの比較は私の判断〕

## R-3 平叙の「〜します」

### 結論
1. **平叙の動詞文は要求と読む、という ADR-0063 決定2 の向き(JIS の側)を維持する**。ISO の側(statement)へ移らない(理由は 0 の 2)
2. 1.7.2 の説明の類「主語が本標準である文」を、**主語が本標準またはその部分(本章・本節・次の表・図・附属書)である文**へ広げる。メタの文(「本節は…を規定します」「次の表に示します」)は、本標準の構成を述べる文で、適用する者に義務を課しえないので、説明として扱ってよい。JIS の適用範囲の「この規格は,…について規定する。」と同じ型である〔推: JIS の適用範囲の定型文を原本で確かめていない。転載・通常の規格票の慣行による〕
3. 因果・事実の「〜します」(「形骸化します」「依存します」「生成します」など、抜き取りで 10/60)は、**類を足さずに書き換える**。理由の文(〜ためです)、可能性の形(〜ことがあります/〜おそれがあります)、名詞で結ぶ文、注記のいずれかへ移す
4. **全件(420)を読む**。抜き取りの推計(約 160、110〜210)で済ませない。読み手は EV-0096 の差し替え条件どおり 2 名とし、一致しない文を記録する
5. 機械の検査は、メタの文(主語が本章・本節・次の表…)の検出に限って足す(説明として通すための登録)。因果の文は機械で判定しない(1.7.4 を維持)

### 理由
- JIS の側に立つ代価は、規定要素から説明の平叙文を追い出すことである〔外 2.1 含意〕。メタの文は、本標準自身の構成を述べる文で、誰の行為も規定しない。これは説明の類として閉じた形(主語で判定できる)で書ける
- 因果の文は、主語も文末も要求の文と区別できない。「AI エージェントは…を生成します」を説明の類に入れると、「AI エージェントは…を記録します」(要求)と形で区別できない。類を足すと「迷う文は要求」の安全側の既定が崩れる。**書き換えのほうが、形と意味の対応を保てる**
- 全件を読む理由: 抜き取りの 95% 区間で約 100 件の幅がある。適合の条件の集合が 100 件の幅で不定な規格は、識別可能性を満たさない

### 他の案を落とす理由
| 案 | 落とす理由 |
| --- | --- |
| ISO の側(平叙は statement、要求は「しなければなりません」だけ)へ移る | ADR-0063 が退けた案。書き換え漏れが義務の消失になる。日本の読み手の JIS の読み方と逆になる |
| 因果の文の類も 1.7.2 へ足す | 形で区別できず、要求が説明へ逃げる経路になる |
| 抜き取りの推計で残りを決める | 区間の幅が適合の条件の不定の幅になる |
| 説明の文をすべて注記へ出す | メタの文まで注記にすると本文の流れが壊れ、注記の数が判定に関係ない文で膨らむ。メタの文は主語で閉じて判定できる |

### 文の案(1.7.2 の箇条の差し替え)
- 主語が本標準、またはその部分(本章・本節・次の表・図・附属書)である文。「本標準は〜を課しません」「本節は〜を規定します」は、本標準の構成と、課さないと決めたことの表明であり、本標準を適用する者への要求・禁止ではない

1.7.1 の表に「不必要」(〜する必要はありません/〜しなくてよい)の行を足す。JIS 表5 の不必要の形に当たる〔外 2.1〕。「〜を要します」「〜を求めます」は要求の別形として書き換え、表に足さない(同じ強さの形を増やすと検査の対象が開く)。こと止めは本文・規定の附属書の規定の文末に使わないと明記する(JIS 表3 が要求に用いない形〔外 2.1〕)。

### 既存との矛盾
- ADR-0063 決定2 と矛盾しない(維持し、1.7.2 の説明の類の境界を明確にする)。#345(主語の無い「設けません」)は本議題の書き換えの対象に含まれる。範囲は #345 に寄せ、同じ文を2つの Issue で直さない

## R-4 参考の附属書 C・E・G・I の平叙の要求らしい文

### 結論

## R-5 様式・記入例の食い違い

### 結論
1. 1.7.2 に「**様式の記入例の文は、本標準を適用する者の文書の文の見本であり、本標準の規定ではない**」と宣言する。外部に先例が無いので EV を付ける〔外 3.1〕
2. **受入基準の文の形は、規定の附属書B を正本とし、テンプレ1・テンプレートの様式・スキルはそれに合わせる**。附属書B のひな形の文末は「〜しなければならない/〜してはならない」へ改める(こと止めを廃する)
3. EARS の型の名は附属書B の名(英語の原名を併記)に統一する
4. **受入基準の識別子に AC-N を使わない**。第7章 7.x の前提の充足状態の記号 AC-0/AC-1/AC-2 と衝突する〔確 `exception-escalation:543-545`、テンプレート `10-assumption-ledger.md`〕。標準の例 CR-N にそろえ、テンプレートの様式・スクリプト・試験(`F-NNN/AC-N`)を改める
5. 「再提出の期限」の欄を、標準のテンプレ4 とテンプレートの `04-gate-record.md` に足し、`template-fields.yaml` の t4 に登録する

### 理由
- 注記・例に要求・推奨・許容を書かないのは ISO・JIS・IEEE・W3C で一致する〔外 3.1〕。記入例の「しなければならない」を残すなら、それが本標準の規定ではないと宣言しないと、規格の作法の違反に見える。宣言は1か所(1.7.2)で済む
- 文末の選択: 受入基準は採用者の**要求仕様**であり、その中の文は要求の文である。EARS の原典は shall を使う〔推: EARS の原論文を本議題では読み直していない〕。こと止めは JIS が要求に用いない形〔外 2.1〕で、命令・列挙・要求のどれとも読める。平叙の「〜する」は JIS では要求、ISO では statement で、採用者の読み手(AI の実行主体を含む)によって読みが割れる〔外 2.2〕。**明示の「しなければならない」だけが、JIS・ISO・EARS のどれで読んでも要求である**
- 識別子: 本標準の中で記号 AC-N が2つの意味を持つのは、R-7 の「逸脱」と同じ定義語の一義性の違反である。採用者のリポジトリでは受入基準と前提台帳が並ぶので、「AC-2」が受入基準2 か「不成立」かを文脈で決めることになる。テンプレ1 は「記法は組織が定める」と書く〔確 `deliverable-templates:452`〕が、テンプレートは本標準の様式の部分集合(ADR-0040)であり、標準が定めた記号を別の意味で再利用してよい理由にならない
- 再提出の期限: 本文が差し戻しと同時に確定させる事項としている〔確 `gate:97`、内 4.2 `roles:701`〕のに、記録の欄が無い。記録で判定を閉じる決まり(ADR-0036)の下では、欄の無い確定事項は確定したことを示せない。スキルだけが書く現状は、スキルが本文の要求を実装しながら、様式がそれを落としている形である

### 他の案を落とす理由
| 案 | 落とす理由 |
| --- | --- |
| 様式の記入例を附属書B のこと止めへ合わせる | こと止めは JIS が要求に用いない形。読みが割れる |
| 平叙の「〜する」へそろえる | JIS と ISO で読みが逆。採用者の文書の読み手を選べない |
| 記入例の文末を自由とし、宣言だけ置く | 正本(附属書B)とテンプレートの食い違いが残り、spec-lint・スキルがどちらに合わせるかが決まらない |
| AC-N を標準の例へ採り、第7章の記号を改める | 第7章の記号は標準が定義した記号で、様式・台帳・スキルが既に引く。受入基準の記号は標準が「組織が定める」とした側であり、動かすのは組織の側の記号が筋。〔推: 波及の件数は両方を数えていない。数えて逆の結論になるなら、一義性さえ保てばどちらを動かしてもよい〕 |
| 再提出の期限を語彙の表から外す | 期限の無い差し戻しは、滞留を止める手段を失う。本文の要求を、様式に欄が無いという理由で落とすことになる |

### 文の案
1.7.2 の箇条へ追加:
- 様式の記入例の文。本標準を適用する者が書く文書の文の見本であり、本標準の規定ではない。記入例の「〜しなければならない」は、その文書の中の要求を示す

附属書B のひな形(例): 「<トリガー> のとき、システムは <応答> しなければならない」「システムは <禁止の挙動> してはならない」

テンプレ4 の欄: 「再提出の期限(差し戻しの場合): YYYY-MM-DD」

### 既存との矛盾
- ADR-0040 と矛盾しない(必須欄の存在の検査の両方向に、t4 の期限の欄を足す)。ADR-0063 と矛盾しない(附属書B は規定)。IMPL-0009 の note「2値に限る(単位: 欄)」とは別の欄で、矛盾しない
- 1.7.2 の宣言の EV は、外部に先例が無いことを根拠の水準 E0 として開示する

## R-6 禁止事項の番号の重なり

### 結論
1. **番号の正本は、禁止を規定する本文の条項に置き、引くときは条項で修飾する**。「第5章 5.8.5 の禁止事項3」「第8章 テーラリングの禁止事項7」と書き、裸の「禁止事項N」を本文・規定の附属書・フェーズ5・6・テンプレートのどこでも使わない
2. **テンプレートは独自の番号を禁止事項の連番の続き(6〜9)に振らない**。テンプレートの 6 は第4章 G-5 の規範なので「第4章 G-5」と引く。7〜9(ラベル、qm-blocked、外部ホスト)はテンプレートの運用の規則であり、本文に根拠が無いなら別の名前空間(例: 「テンプレートの規則 T-1」)にする。本文に根拠を置くべきものかは、R-1 の 3 と同じく1件ずつ決める
3. 廃止した禁止事項の番号は再利用しない(NIST SP 800-53 の作法)。欠番は欠番として残し、廃止の版を記す
4. `ci-gates.md:144` の「禁止事項6」と、`template-repository.md` の「規則と担保の対応」は、修飾した形へ改める

### 理由
- 手引き・補足文書は本体の番号を引き、自前の連番を振らない(NASA の SWE-NNN、DO-178C の補足文書)〔外 4〕。本件の衝突は、手引き側(テンプレート)が本体の連番を延長したことで生じた
- 同じ「禁止事項7」が第8章とテンプレートで別の事項を指す〔内 4.3〕。番号で引かれた禁止が誤った事項に結びつくと、監査とスキルの両方が誤った規範を確かめる。条項による修飾は、ISO の列挙の引き方(「5.8.5 の c)」)と同じで、名前空間が条項で自動的に分かれる〔推: ISO 指針の列挙の参照の箇条番号は本議題で確かめていない〕
- 版の前置(ASVS 型)は採らない。本標準は 1.10.3 で版を持ち、適合の主張は版を名指す〔確 1.4 の定義表〕。番号を永続させ再利用しない(NIST 型)なら、版の前置は要らない

### 他の案を落とす理由
| 案 | 落とす理由 |
| --- | --- |
| 全文書で通しの番号(1〜14 など)を振る | 第5章(実行時の禁止)と第8章(テーラリングの禁止)は性格が違い、1つの連番にまとめる理由が無い。片方の改訂で他方の番号が動く |
| テンプレートの 6〜9 を 10〜13 へずらす | テンプレートの独自の規則に本体の番号の形を与え続ける。根拠の所在が見えないまま「禁止事項」と呼ばれる |
| ASVS 型の版の前置 | 1.10.3 の版と二重になる。再利用の禁止で足りる |

### 文の案(第1章 1.7 の箇条へ追加)
- 番号を振った列挙(禁止事項・要求事項・判定基準)を引くときは、条項で修飾する(例: 「第5章 5.8.5 の禁止事項3」)。廃止した番号は、再び使わない

- 第5章 5.8.5 の「番号は附属書E E.9 と共通」〔内 4.3〕は、E.9 が移された後の残りであり、改める。IMPL-0185〜0189 の番号は変えない。テンプレートの `CLAUDE.md`・`claude-md-resident.json`・`boundaries.md` の番号の改訂が要る(テンプレートの規則の索引の行は ADR-0064 の所在の印の対象)

## R-7 その他の食い違いと語

### R-7a 初期化を PR で入れるか
- **結論**: 本文に機構(PR)を書かず、**結果を要求する**。「適用の開始のコミットは、R1 の変更として記録を伴う」の形で第1章 1.10.1 に置き、PR はテンプレートの既定の手段とする。フェーズ5 の 2 頁は、テンプレートの既定(PR)を書き、`git-strategy.md:127` は PR を経ない場合の代替として書き直す
- **理由**: PR は GitHub の機構名で、1.7 の製品名の禁止に当たる〔確 1.7〕。#286 で観測された欠陥は「記録の欠落」であり、機構の選択ではない〔内 4.4〕。実質(初期化を R1 とするか)は他の委員の領域で、私は形だけを述べる
- **矛盾**: ADR-0068 は適用の開始を初期化のコミットと定め、手段を決めていない〔内 4.4〕。結果の要求を足すことと矛盾しない

### R-7b hotfix
- **結論**: `git-strategy.md:39` の「事業ゲートの事前決裁を事後報告に切り替える」を削る。本文に根拠が無く〔内 4.5〕、R-1 の結論の下で参考の頁が置く緩和は効力を持たない。緩和が要るなら第7章の例外承認の条項として本文に置く(別 Issue)。「独立レビューを省略しない」は、本文 G-7 `:901`(例外承認で事前確認なしに出荷してよい)〔確〕より厳しい。手引きが厳しい既定を示すことは許されるが、**テンプレートの既定であって本標準の要求ではない**と書く。「5 つに限定」は要求の形なので、テンプレートの既定の列挙へ改め、テンプレートに hotfix の種別が無い食い違いを解く(足すか、列挙から外す)
- **理由**: 1.8「フェーズ5 の記述は本文の要求事項を狭めない」は、緩和(要求を減らす)と強化(要求を増やす)の両方を頁に禁じていると読める。手引きが厳しい既定を示すことと、要求を増やすことを区別しないと、採用者は G-7 の例外の経路を使えないと誤読する

### R-7c JIS Z 8301(EV-0096)

- **理由**: 本標準は 1.7 の文末で JIS の側に立つ(R-3)と決めている。立つ側の原典を読んでいない状態で、R-2・R-3・R-5 の結論が JIS に依っている。費用・手間は採否の理由にならない
- 2019 年版より新しい版・追補の有無は、私も確かめていない〔推〕

### R-7d catalog.md の SRC-0633〜0639

| 一般の意味(目的からの逸脱 ほか) | 約18 | 文脈ごとに「外れ」「ずれ」等へ | 定義語の一般語用法を残さない |

- 1.4 の注記に、ISO 9000 の deviation permit(実現の前の許可)・concession(特別採用)と本標準の逸脱・例外承認の対応を、**近似**として置く。一致とは書かない〔外 5.1 含意〕
- **機械の検査**: 改名後、廃した言い回しの登録簿に「委任の範囲の逸脱」「意図的な逸脱」「規範の逸脱」を載せ、公開ドキュメントとテンプレートの全体で検出する(ADR-0063 決定4 の機構)。テンプレートの出力(PR の様式・証跡の項目名)も同時に改める。#354 の 1 と範囲を分ける(テンプレート側は #354、語の決定は本議題)
- **矛盾**: 1.4 の注記(`overview:165`)が改名を #316 へ送っており、本結論で閉じる。採用済み ADR の本文に「逸脱」の事象の用例がある場合は書き換えず、新 ADR で語を置き換える
