## 1. 立場と全体の見立て

1. **規格の側から見て最も大きいのは K-1 で、問題は「技術検証の置き場」ではなく、変更管理の欠落である**。ISO 9001 8.3.6・ISO/IEC/IEEE 12207 の構成管理・ISO 10007 は、どれもベースライン後の変更を「識別し、レビューし、許可する」入口へ流す。本標準は、コードの変更にはこの入口を持つ。一方、ゲートを通った機能仕様・判断記録を変えるときの入口を持たない。技術検証の結果は、その入口を叩く契機の 1 つにすぎない。置き場の新設より先に、この入口を本文に書く
2. **規格は場所を定めず、到達性・保持・完全性を定める**(SLSA v1.2 Source、NIST SSDF PS.3、ISO 9001 7.5.3)。K-1 の探索の記録の置き場と K-7 の添付証跡の置き場は、この形に揃える。場所は課さないと明記する。ただし**本標準自身の判定が読む記録**(G-7 が読む G-5 の結果、出荷の証跡)の保持は、プラットフォームの既定に置いたままにできない。ここは課す側である(発見 3)
3. **規格は検査の厳しさを、規模ではなくリスク・安全度で変える**(ISO/IEC/IEEE 29119-2、IEC 62304 の安全クラス、IEC 61508-3 の SIL 別の表)。本標準も R(変更ごと)と CL(案件ごと)で変える。K-8 の規模下限は、この系譜から外れる。課さないと明記する
4. **K-2・K-3・K-6 は、既存の規格・ベンダー指針が「後段の門は前段を置き換えない」「AI の擬似読者は代表利用者の試験ではない」「指摘の書式は流儀が割れる」と示す領域である**。免除(K-2 の 2-C)、要求事項化(K-3 の 3-D)、観点の固定(K-6 の 3 軸)は採らない。K-2 は「操作」の範囲の定義(2-B)で答える
5. **他組織が従える形かどうかで、フェーズ5 の頁に置いた規範的な文が問題になる**。`stacked-pr.md` は実在しない強制層を強制層と書き(発見 2)、`label-mailbox.md` は ADR-0053 が廃した語を残す。規定と実装が食い違う文は、採用者に誤った適合の確信を与える。どちらも本 Issue で直す

## 3. 論点ごとの詳細

### K-1 S1 以降の技術検証、再判定の経路、S0 の探索の記録

**判定: 採る(変更管理の入口を第4章に新設)。技術検証の専用の様式・ステージ・置き場は課さないと明記する。SG-0 へ渡す出力は既存の決断の記録で定める。**

#### 何が欠けているか(規格の側からの読み)

- 規格は、承認(ベースライン化)した成果物を変えるとき、変更を識別し、レビューし、許可する入口を持つ。ISO 9001:2015 8.3.6 は「設計・開発の間または後に行った変更を識別し、レビューし、管理する」ことと、変更・レビュー結果・許可・悪影響を防ぐ処置の記録を求める【二次】。ISO/IEC/IEEE 12207 の構成管理(変更要求の評価と承認)と ISO 10007 も同じ形である【既知】。調査 2 の SEBoK のベースラインの定義も「正式な変更管理手続によってのみ変更できる」とする【二次】
- 本標準のコードの変更には、この入口がある(リスク区分・G-6・判断記録・7.3)。附属書H の対応表は 8.3.6 をそれで満たすと示す(`AC` L826)
- **ゲートを通った機能仕様・判断記録を変えるときの入口は、本文に無い**。「再判定」の全出現のうち、成果物の変更を契機にするものは無い。5.5.1 は「受入基準・スコープ・公開インタフェース・データ形式を変える選択 → 人へ戻す」(`HB` L251 の上の行)と書くが、戻した先でどのゲートを受け直すかを書かない。5.7.2 の「判断が変わる条件」も「再判定へ戻す経路になります」(`HB` L659)と書くが、誰がどのゲートへ戻すかを書かない。2.10.8 は範囲の逸脱だけを G-4 で拾う
- #250 の 3 つの選択肢 (a)〜(c) がどれも根拠を欠いたのは、この入口が無いためである。起票者の「戻り幅を裁量にすると最小に選ばれる」という懸念も、入口の欠落の帰結である

#### 採る案

#### 採る案

第5章 5.5.1 の表の後に注記を置く(正本は本文。原則4 は参照に改める)。

> 「取り消せない操作」は、**取り消せない時間帯を直接生じさせる操作**を指す。ブランチ上の編集(公開の設定を書く、設定ファイルを変える)は、取り消せない時間帯を生じさせるのが後段の別の操作(マージ、反映の起動)である限り、取り消せない操作に当たらない。後段の操作が取り消せない操作に当たる。

#### 選ばなかった案を落とす理由

- 5-A(課金形態を区別しないとだけ書く): 3.12.7 の「消費の前に強制する上限」が、定額では提供者の上限に置き換わって成り立ったように読める。提供者裁量の上限は容量の保証にならない(ISO/IEC 20000-1 の容量管理・供給者管理の考え方【既知】、Anthropic の Max の上限は非公開で裁量による【一次・調査 2】)
- 5-B(そのまま、7.7.1 に消費率の読み替え): 読み替えの値(上限の消費率)は提供者が公開しない(調査 2「固定のトークン数上限は公開されていない」)。測れない値を予算の区分に置けない。区分の定義を課金形態から外す形にした
- 単価・比率の数値の条項化: Copilot が半年内に課金方式を変え、読み取り倍率がモデルの世代で 0.1 → 0.025〜0.05 に変わった。規格は数値を置かず、記録させる形を取る(調査 2 の A)
- ログの日次の複製(#274 提案3): 3.12.2 は消費実績を経路の側で記録する。手元のログの保全は経路の外の利用でだけ問題になり、それは 3 の未達として扱う。課さないと明記する

### K-6 AI の反対理由の構造化

**判定: 観点・反対理由・欠落の自己申告は課さないと明記する。実行ごとの入力の範囲を記録することだけを採る。**

#### 採る案

- `AC` H.4「指摘の書式」の後に: 「本標準は、AI の確認に、観点ごとの所見、反対理由、確かめていない範囲の申告を求めません。観点を定めるのは案件です。AI が申告する『確かめていない範囲』は、自己申告であり、確認の範囲の根拠にしません」
- H.4 条件5 の「確かめる中身」に足す: 「その実行が入力として受け取った対象(差分・ファイルの範囲)が、実行の記録から分かること」。機械が実行の記録から書く。AI の出力に書かせない
- 理由: 指摘を受けた人が過信しないために要るのは、AI が何を見たかの事実で、AI がどう反対したかの形ではない。IEEE 1028 のレビューの報告、ISO 19011 の監査報告は、対象と範囲の記載を求める【既知】。これは H.4 条件4(通過を理由に人の確認を減らさない)を、記録の上で支える

#### 選ばなかった案を落とす理由

- 6-B(欠落の列挙を含める値に): 自己申告で、「なし」と書く形、中身の無い充足(FND-0097)を招く。ADR-0075 決定7 が「実行・観測値・代替案を求めない」とした理由(確かめずに必須化すると捏造を誘う、FND-0091)がそのまま当たる
- 6-C(観点を案件が登録し、観点ごとに所見か「所見なし」): 「所見なし」の欄は 6-B と同じ破れ方を持つ。観点ごとの欄を課すことと、決定10(書式を定めない)の区別がつかない
- 調査 2 の A・B(必須欄、SARIF への写像): 指摘の理由欄を構造化した規格は無く、重大度の段数も製品ごとに割れる(3 段・5 段・2 段+ブロック)。SARIF は組織が選んでよく(決定10 が妨げない)、標準が指定する理由が無い
- 調査 2 の C(却下側の語彙を「誤り / 正しいが見送り / 対処済み」に分ける): 採否の記録の語彙で、K-6 の範囲外。ADR-0075 決定8 の「不採用(所在・根拠なし)」と併せて別 Issue で検討する価値はある(K-9)

#### 根拠水準

- 入力の範囲の記録: E1。暫定マーク。差し替え条件: AI の確認の後に人が見落とした欠陥のうち、AI の入力の範囲の外にあったものの件数
- 3 軸の構造化の支持は FND-0083(E3、効いたのは値で書式ではない)、FND-0224(E0)、FND-0221(導入翌日の drift、前後比較なし)で、課す根拠に届かない

### K-7 PR に添付する証跡の置き場

**判定: 添付の置き場と様式は課さないと明記する。本標準の判定が読む記録の保持を課す。**

#### 採る案

1. `pr-workflow.md`「human-verify」に: 「本標準は、human-verify に画面・DOM などの添付を求めません。添付する場合の置き場と保管は、組織の文書管理規程によります([QMS 文書管理](…) と同じ扱い)。添付の有無と所在は、確かめたことの根拠になりません(第4章 G-2 基準3 の理由と同じ)」
2. `ci-gates.md` の出荷の証跡の集約に置く規定:
   > 出荷の証跡の集約が読む記録(各 PR の G-5 の結果)と、集約の出力(保証の開示を含む)を、プラットフォームの既定の保持(CI の成果物、チェックの記録)に置いたままにしてはなりません。少なくとも当該出荷の G-8 の判定の後、組織の保管期間まで到達できる置き場へ移します。
   - GitHub の CI の成果物とチェックの記録の保持は既定 90 日(公開リポジトリは最大 90 日)で、2026-10-01 からはチェックの記録にも当たる、と開示する(一次で確認)
   - テンプレート: 集約が `g5: 'unknown'` を「必須チェックを経ずにマージされた可能性」と表示する(L1565)のは、保持の期限切れと区別できない。原因の候補に「チェックの記録の保持期間切れ」を加え、マージの時点の G-5 の結果をリポジトリへ残す。実装マーク `undelivered`
3. 保持期間そのものは本標準が定めないまま(`qms-document-control.md` L139)

#### 選ばなかった案を落とす理由

- 7-B(置き場を定め、必須にしない): 規格は場所を定めない(SSDF PS.3、SLSA)。置き場を書くと採用組織の文書管理規程と二重になる
- 7-C(human-verify の所在を出荷の集約で収集・保全): 所在の実在しか機械は見られない(G-2 基準3 の理由、ADR-0075 決定3)。集めた所在が確かめたことを示さない
- 調査 2 の C(高リスク区分で署名付き attestation): GitHub は artifact attestation を個別の文書ファイルの署名に使うべきでないとする(FND-0100)。非公開リポジトリでは Enterprise Cloud が要る。承認ごとに何を確かめたかの署名様式は ADR-0056 の却下表が退けている
- 調査 2 の A(保持期間 ≥ 保守期間を要求): 期間の値は規制・契約で決まり、一般の規格に無い(調査 2 §7)。本標準は期間でなく「既定に置いたままにしない」に留める

#### 根拠水準

- 2 は E1(一次文書から機序が確定。テンプレートの実装を読んで確かめた)。暫定マーク不要とみる(実証を要する値を置かない)

### K-8 実装向けの検査の規模の下限

**判定: 課さないと明記する(8-A)。基準3 の測る量の食い違いは本 Issue で直す(誤りはテンプレートの側)。**

#### 採る案

- 第4章 G-5「検査対象が存在しない場合の扱い」に: 「本標準は、カバレッジの判定に、測定対象の規模の下限を置きません。実装が存在する段階では、規模にかかわらず測定し判定します。検査の厳しさは、変更のリスク区分([第3章 3.8.1])と案件の安全重要度で変えます」
- 小さい分母の割合が何も述べないこと(#254)は認める。その情報は割合ではなく、各受入基準に「違反すると失敗するテスト」があること(テンプレ1)と、R1 の変異試験(H.4)が担うと書く
- 基準3 の基準値の欄で、測る量(新規コード / 全体)を組織が記録する形にする。本文の目安は「新規コード 80%」のまま。テンプレートの `coverage-check.mjs` は全体の行の割合で比べ(L60-71)、その旨をどこにも記録しない。テンプレートは既定を新規コードにするか、構成に `coverageScope` を置いて記録する。誤りはテンプレート(標準の目安と違う量を記録せずに測っている)

#### 選ばなかった案を落とす理由

- 8-B(規模下限を構成の欄、下限未満を「判定しない」と記録): 「判定しない」は ADR-0033 決定7 の 3 区分(通過・対象なし・未達)に第 4 の状態を足す。実施しなかった検査を通過として扱う製品既定(FND-0194: skipped を success、Codecov の if_not_found)と同じ形に寄る。規模の閾値で検査要否を決める規格は確認できない(調査 2 §8)
- 8-C(新規コードに揃え、新規コードの行数が下限未満の変更は判定しない): SonarQube の 20 行の下限(FND-0193)と同じ型で、小さい変更ほど判定されない状態が常態化する。IEC 62304 は分割による低クラス化に歯止め(寄与関係で高クラスへ引き上げる)を置く【二次・調査 2】。変更の規模で外す仕組みは、分割で外れる経路を開く
- 調査 2 の B(規模の上振れで追加要求する片方向): 本論点(下限)と別で、規模による追加要求は既にタスクの分割基準と区分の下限が扱う

#### 根拠水準

- 課さない判断: E1(規格の系譜と製品既定の害の事例)。暫定マーク: 見直し 2027-10。差し替え条件: 実装の規模が小さい段階で 100% を示した後、同じコードで欠陥が流出した件数

## 4. 他の委員に問いたいこと

1. **擁護へ**: K-1 の「承認済みの成果物の変更」は、ADR-0036 決定4(当該ゲートの基準のみで判定)と `GC` L333(新しい経路を設けない)の、どちらかを覆すと読むか。私は、ゲートを増やさず既存のゲートへ戻す入口であり、L333 は受容拒否の節に限った文と読む。覆すと読むなら、附属書H の 8.3.6 の対応表をどう正すか(対応を外すか)を示してほしい
2. **現場へ**: K-1 で「機能仕様の変更は G-2 を受け直す」とすると、受入基準の文言の小さな修正まで G-2 に戻る。変更の範囲を「受入基準・前提・スコープ外」に限ったが、誤字の訂正のような変更を外す線を引くべきか。引くなら、ADR-0044 決定4(自己申告の閾値)に当たらない引き方があるか
3. **品質保証と監査へ**: K-7 の「既定の保持に置いたままにしない」は、内部監査の観点として確かめられるか。確かめられないなら、出荷の集約が自ら記録の期限(各 PR のマージ日 + 保持日数)を出す形が要るか
4. **起草へ**: K-2 の「マージがそのまま発行を起動する構成では、マージが取り消せない操作に当たる」は、本リポジトリ自身(`main` への push で Pages へ反映)と準拠テンプレートの `next.mjs`(出荷の実行を AI に実行させない)の運用を変えるか。変えるなら、それは K-2 の帰結として受け入れるか
5. **全員へ**: K-4 の判定の場所(既定ブランチへ入る PR)は、ネイティブのスタックの一括マージ(最上段のマージで下の層をまとめてマージ)で、中段の PR の G-6 の承認を何として記録するかを決めていない。層ごとの承認を G-6 に数えるのか、最上段で全体を見た承認だけを数えるのか。私は後者が SLSA Source L4 と揃うと考えるが、ADR-0058(層数の目安)と理解の分散(G-6 の目的2)の側から反論があれば聞きたい
6. **全員へ**: K-6 の「入力の範囲の記録」は、ADR-0075 決定7(条件を増やさない)の範囲内(条件5 の確かめる中身の追加)と読めるか。読めないなら課さないと明記する側へ倒す
