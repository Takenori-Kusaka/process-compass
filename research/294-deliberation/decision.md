## 1. 確定した版を変える場合(K-1)

- 全委員が「欠けているのは技術検証に固有の手続ではなく、確定した版を変えたときにどのゲートをやり直すかが本文に無いこと」で一致した(起草・規格・擁護。品質保証・現場も同じ帰結)
- 戻り幅を変わった成果物で機械的に決める。#250 の核心(案件が最小の戻り幅を選ぶ)を閉じる。ISO 9001 8.3.6、12207 の構成管理の変更管理と同じ形(規格。原典は有償で未確認、二次)
- 文の案(第4章、ゲートの共通ルールの後):
  - 「工程ゲートを通過した成果物(機能仕様の受入基準・前提・スコープ外、判断記録)を変える場合は、その成果物を確定した工程ゲートの判定を、変更後の成果物で受け直さなければなりません。受入基準・前提・スコープ外は G-2(S0 で統合したゲートでは G-4)、判断記録は G-3 です」
  - 「変更の契機(技術検証の結果、顧客の要望、障害など)によって、受け直すゲートを変えてはなりません」
- G-2 基準3: 判定者は前提の引き受け手である(L272、#291 X-9)。引き受けない場合を「閉じていない未確定事項」として前提条件1 を満たさず提出者へ戻す、と書く(擁護・起草・品質保証)。今の本文では、判定者は引き受けを断る手続を持たないまま名が残る(品質保証)
- 「技術検証」の種別・様式・置き場・ステージは課さないと明記する。技術検証は実装計画の通常のタスクとする。理由: 本標準の経路は成果物の変化で起動し、契機で起動しない。種別を設けると、検証と名付けなかった変更が経路の外に出る
- 1-C(前提の行に検証タスクを書かせ、着手の前提条件にする)は採らない: ADR-0036 決定3 が禁じる持ち越しに当たる(起草)
- 1-A(何もしない)は採らない: 確定した版を変えたときの扱いが本文に無い事実が残る
- S0 の探索の記録(ADR-0072 決定4 から): 置き場は課さない。SG-0 の判定記録の決断の記録(5.7.2)に「確認した事項・確認していない事項」を書き、依った探索の記録へ到達できることを求める。確認していない技術的な問いは S1 の前提か検証のタスクへ移す
- 機械の確認: 受入基準が G-2 で確定した版から変わったのに新しい G-2 の判定記録が無い状態を、出荷の集約で拾う(現場)。テンプレートに無いので `undelivered`(IMPL-0107 の残りと突き合わせる)
- 附属書H の ISO 9001 対応表の 8.3.6 の行は、この節の新設を受けて対応先を直す(規格の発見: 実態より強く対応を示していた)
- 根拠水準: 機序は E1(Filetto・publishing-hub の事例の引用、現物は未確認)。新しい規範は「既に確定の定義から出る戻り」を書き出すもので、EV は付けない。ただし機械の確認が `undelivered` である事実は表示し続ける

## 2. 取り消せない操作(K-2)

- 全員一致で 2-B(定義)。免除の形(2-C・2-D)は採らない: 門が実在するか、効くかを実行主体または登録の手続が判定することになる。1〜2 名の体制や委任のマージでは後段の門が人でなくなる。GitHub の門は既定で管理者が迂回できる(ADR-0077)。外部も「後段の監視は前段を置き換えない」(Codex)、承認疲れ(OWASP ASI09、二次)
- 文の案(5.5.1 の注記ではなく本文の定義として):
  - 「取り消せない操作とは、取り消せない効果を、他の者の操作を介さずに生じさせる操作をいいます。効果が後段の操作で初めて生じる編集は、後段の操作を人が行う場合(5.5.5 項目4)に限り、取り消せない操作に数えません」
  - 「既定ブランチへの取り込みや push が発行・本番への反映を直接起動する構成では、その取り込み・push が取り消せない操作に当たります。委任(5.5.4)によるマージの対象にしてはなりません」
- 統制の弱化は取り消せない操作とは別の停止の事由として残す(品質保証)。原則4 の例示に両者が同じ列に並ぶことの是非は別 Issue
- 原則4 は 5.5.1 の定義を引く形にする。本文に従属しない記述にしない
- 免除を置かないことを本文に明記する(「後段に人だけが通せる門が残ることを理由に、停止を省いてはなりません」)
- EV-0039 の差し替え条件との整合は実装時に確かめる(品質保証)
- ADR-0053 決定5 とは衝突しない(対象の定義であり、公開前の査読の段の新設ではない)

## 3. 読者役と AI の指摘(K-3・K-6)

### K-3

- 全員一致で要求事項にしない。理由: #279 の根拠は ADR-0051 決定1 が扱わないと決めた「利用者が用途に気づけるか」に重なる。組織外への発行の前の工程は ADR-0053 決定5 が退けた形。根拠は単一事例と自己実施 1 回(E2 以下)。H.4 条件1 の欠陥注入で文脈の欠落を測る方法が無い
- AI のサブエージェントは「文脈ゼロ」ではない(指示ファイル・道具の定義・起動の指示を受け取る。調査 2 の一次文書)。「文脈ゼロで確かめた」と記録できてしまう経路を閉じる 1 文を H.4 に置く(品質保証・起草):「確認側へ渡した入力(自動で読み込まれる指示ファイル・道具の定義・起動の指示を含む)を列挙できない確認を、文脈を渡していない確認として記録してはなりません」
- 附属書C(参考)の手引き: 渡すのは成果物だけ / AI に読ませるなら指示ファイルの自動読み込みが無い場所で起動する / 読者役の感想は根拠にしない。重視する案件は受入基準の側へ書く(擁護)

### K-6

- 全員一致で課さない。ADR-0075 決定7・10 と同じ向き。覆す材料は E0 の資料と前後比較の無い事例だけ。スキーマを満たしたまま drift した観測(FND-0221)、範囲の自己申告(FND-0091)
- H.4「指摘の書式」の後に書く: 反対理由の列挙・観点ごとの所見・確かめていない範囲は、含める値として課さない。組織が指示資産に置くことは妨げない。効いたかは条件1 の検出率で確かめる。**その申告を確認の範囲の根拠にしてはならない。確認の範囲は、確認側へ渡した入力の記録で示す**(品質保証・規格)
- 入力の記録を機械が実行の記録から書くこと(規格)は手段として書き、テンプレートの実装の有無で `delivered`/`undelivered` を付ける

## 4. スタック型 PR(K-4)

- 事実: テンプレートのルールセットは既定ブランチだけを対象にする。`team.json` は `dismiss_stale_reviews_on_push`・`require_last_push_approval`・strict を持つため、既定ブランチへ着地する PR には G-5・G-6 が掛かる(現場・規格・起草)。調査 1 の「中間マージで G-5・G-6 が要求されない」は既定ブランチへの取り込みについては言い過ぎ。失われるのは層ごとの確認の粒度
- `stacked-pr.md` L95・L176 の「必須チェックが中間層の先行マージを拒否する」は機構として成り立たない(全員)。強制していない検査を「強制層」と書くのは #222 の方針に反する。書き直し、`undelivered` の実装マークで表示する
- 段階1 の前提条件(文の案):
  - 「G-5 の起動を、PR の基底ブランチで絞ってはなりません」
  - 「G-5・G-6 は、既定ブランチへ取り込む PR で成立します。既定ブランチ以外を基底とする PR をマージしてはなりません。下の層から順に既定ブランチへ取り込み、上の層の基底を付け替えます」
  - 「合わさった差分への承認を、層ごとの確認に数えてはなりません」(品質保証)
- ルールセットを機能ブランチへ広げる案(4-B の原案)は採らない: 直接の push の扱いを実機で確かめておらず、着地の保護で足りる(現場)
- pr-rules の基準値: 直接の親(`github.base_ref`。ネイティブのスタックの中段では親ブランチを指す、規格が一次文書で確認)から読むと、閾値の変更と製品のコードの同時変更を禁じる規則(禁止事項6)を抜けうる。**既定ブランチから読む**(起草)。スタックの基底(`stack.base.ref`、規格)はネイティブに限られ、手動のスタックに無い
- 前提表を「ネイティブのスタック / それ以外」に分けて 2026-10-23 時点へ更新する。EV(E1、見直し 2027-04、差し替え条件: ネイティブのスタックの CI・必須チェックの挙動を実機で確かめた結果)
- 4-D(GitHub 標準機能の推奨)は両論併記に留める

## 5. 費用(K-5)

- 7.7.1 の定義は従量を前提にしているが、統制の構造(上限・到達時の扱い・消化の報告)は定額にもそのまま及ぶ(擁護)。新しい指標は足さない(現場)
- 文の案:
  - 3.12.7: 「上限には、提供者が課す利用上限を含めます。提供者が課す上限を、組織が設定した上限に数えてはなりません。上限に達したときの扱い(待つ・従量へ移る・止める)を G-1 で決めます」
  - 7.7.1 注記: 「AI 実行予算は課金形態(従量・定額)を前提にしない統制の単位です。定額では、消化率を利用上限に対する割合として読み替えます。消費の実績を取れない場合は 0 でなく未測定と報告します」
  - 3.12.2: 「組織が用意した契約(定額を含む)は正規の経路です。個人で契約した経路は、定額であっても正規の経路に当たりません」
  - `compute-strategy.md`: キャッシュの費用構造(書き込みの割増、読み出しの割引、TTL、承認待ちが TTL を超えると割増が再発する)を数値なしで書く。「キャッシュの失効を、人の承認を急がせる理由にしてはなりません」。EV(E1、見直し 2027-04)
  - `metrics.md` トークン効率: 診断用であり、7.7.8 の評価の入力に使わない
- 手元の記録の日次の複製は課さないと明記する: 提供者の保持の仕様に依り、本標準の判定が読む記録ではない
- 5-A(課金形態を区別しない)は採らない: 定額で上限の強制を測れない事実が隠れる(品質保証)

## 6. 証跡の置き場と規模の下限(K-7・K-8)

### K-7

- 添付の置き場と様式は課さない(全員)。所在を必須にすると G-2 基準3 の理由(L238: 所在の記録が確認の代わりに通る)をそのまま開く。署名の様式は ADR-0056 が却下済み
- 到達性を採る(現場・規格・品質保証): 「判定記録・出荷の証跡が指す記録は、組織が定める保管期間のあいだ到達できなければなりません。CI 基盤の既定の保持を、保管とみなしてはなりません」。置き場は `qms-document-control.md`(保管)と `ci-gates.md`(G-7 の集約)
- 事実の開示: GitHub の成果物の既定の保持 90 日、2026-10-01 以降のチェックの履歴の保持の変更。テンプレートの G-7 の集約は保持切れの PR の G-5 を「必須チェックを経ずにマージされた可能性」と誤って示しうる(規格、一次文書と実装で確認)。テンプレートの `ship-evidence.yml` は証跡を成果物にだけ置き `retention-days` を指定しない(現場)。どちらも `undelivered` で表示し、テンプレートの保管の設計は別 Issue
- G-7 の集約が「検証方法と結果」の文を PR の識別とともに写し、後の改変を検出する案(品質保証)は、テンプレートの保管の設計と同じ Issue へ送る

### K-8

- 規模の下限は課さないと明記する(全員)。理由: 下限未満の「判定しない」は ADR-0033 決定7 の 3 区分に無い 4 つ目の状態になり、FND-0194(未実施を通過として残す)と同じ形。外部の規格(29119・62304・61508)は規模でなくリスク・安全度で厳しさを変える(二次)。下限を置くと分割で判定を避けられる。本標準は小さい PR を推す
- 測る量を採る: 「G-5 基準3 の基準値は、測る範囲(全体か、変更で加えたコードか)を併せて企画時に決め、記録しなければなりません。記録と保証の開示には、割合・範囲・分母を出します」
- テンプレートの `coverage-check.mjs` は全体の行の割合だけを測り、分母を記録しない。標準の目安(新規コード 80%)と食い違う。`undelivered` で表示する
- アダプタが基準3 を測らずに通す件(go・none・undetermined、`coverageSummary: null`)は #330(未実施の長期化)へ足す
