### 元 Issue の要点(起票 2026-08-14、実証案件 Filetto の G-2 再判定の棄却から)

## 論点2 — #278 不可逆な操作の停止条件に「その操作の後に人だけが通せる門が残っているか」を足すか

### 元 Issue の要点(起票 2026-09-23、publishing-hub の運用から)

- 現状: `label-mailbox.md` 4.2 原則4 は基準(取り消せない時間帯の存在)だけで停止を決める。操作の位置(人の門の手前か、門を迂回するか)を見ない
- 問題: 字面どおりだと、人が承認してマージした成果物を発行する工程にも毎回 `state:needs-owner` が立つ。前段の承認を後段が再現する二重化で、ADR-0053 決定5 が却下した「判定だけが増える」形へ別の入口から戻る。発行に至る経路の一部(ブランチ上で `published: true` と書く)すら AI ができなくなる
- 根拠: publishing-hub の AGENTS.md「その操作より後に、人だけが通せる門が残っているか」。門は `main` への PR のマージ。手前に門を重ねても防御は増えず作業だけが増えた。Environment 承認で承認を待った実行は記録に 1 件もない。**門を迂回する操作(手動の公開ワークフロー起動)は人だけの操作として残している**
- 提案: 原則4 に但し書き。免れる条件 3 つ(すべて満たす場合のみ)— (1) 門が実在し D-0 に誰が通すか書かれている、(2) 門が対象を一意に特定し、門の後で差し替えられない、(3) 迂回経路を強制層で塞ぐ。免れた場合も起動は記録に残す
- 起票者自身の前提条件: **ADR-0028(未達の表示を消さない)・ADR-0029(出荷判定者の例外)と衝突しないこと。門を 1 本に集約する書き方が未達の表示を消す方向に働かないこと**
- 範囲外: 「組織外」の定義(ADR-0053 決定4 のまま)、強制層の具体的実装。根拠は単一事例(E2)で EV マーク要

- ADR-0053 決定5 は判定の追加を却下したが、逆向きの限界(承認済みの門の手前に停止を重ねない)は書いていない

## 論点3 — #279 査読に「文脈ゼロの読者役」の層を置くか

### 元 Issue の要点(起票 2026-09-23、publishing-hub の運用から)

- 現状: `review-guide.md` の目的は統制と理解の分散の 2 つ。3 パス方式の準備でレビュアは受入基準と PR 本文を開く=書き手と同じ文脈で読む前提。`review-package.md`「このパッケージが埋められない穴」は文脈の欠落を「埋める」側からだけ扱う
- 問題: 組織外の読者へ渡る成果物(公開文書・LP・外部向け仕様・顧客が触れる UI)で、前提・呼び名・略語の欠落は前提を共有する読み手に見えない。「文脈を渡した査読は、文脈が要ることを見つけられない」
- 根拠: publishing-hub の editorial-review.md。事実の査読と文脈ゼロの読者を両方回す。SNS 10 本は事実の査読で [止める] 0 件、読者役では 9 本が 1 投稿目から何の製品か分からず。本の改訂では機械検査エラー 0 の後に事実の査読が [止める] 29 件・[直す] 184 件。成立条件は「渡さないこと」。読者役の感想は根拠にしない
- 提案: (1) review-guide に 4 層(機械/文脈を持つ査読 G-6/文脈ゼロの読者役/決裁)の定義、(2) 第3の層を「成果物が組織外の読者へ渡る場合」に限る(内部の PR レビューへ広げない)、(3) review-package に「この層にはパッケージを渡さない」、(4) 指摘の採否を `community/feedback-workflow.md` の区分 A〜E へ接続
- 範囲外: G-6 への適用、読者役を人か AI かの選択(LLM は人の読者の代わりにならないが、書き手と同じ文脈の査読より第三者に近い、という限界つき)。根拠は単一事例

### 突合コメント(2026-10-08、判定: 未対応)

- review-guide「入力の分離」が渡さないのは作成側の説明・主張・推論であって、仕様・受入基準・差分は渡す。文脈の欠落を検出器にする層ではない
- 「文脈ゼロ」「読者役」「コールドリード」は公開ドキュメントに 0 件
- 受ける語彙は既にある: 附属書H H.4「検出の層」(ゲートの判定に数えない確認)。review-guide「AI をレビューに使う場合」は AI の確認を検出の層としてのみ数える。読者役を置くなら、G-6 と並ぶ判定ではなく検出の層の 1 つとして、組織外の読者へ渡る成果物に限る形が整合(H.6「組織の外へ渡すとき」とも接続)
- 本プロジェクト自身が #286 で 1 回実施(プロセスを知らない利用者役が README だけを読んでテンプレートを通し、重大 3 件 N1〜N3)。条項にはしていない。附属書I の「目隠し」は注入の位置を知らせないことで別物
- 会議体の論点: (a) 読者役が LLM であることの限界と H.4 の 5 条件の関係、(b) 指摘の採否を区分 A〜E へ乗せる形、(c) E2 のため EV マーク要

## 論点4 — #273 の残り: スタック型 PR の CI の発火条件と、GitHub 標準のスタック機能(2026-07)

### 元 Issue の要点(起票 2026-09-20、実証案件 がんばりクエスト の PO セッション)

- 観測: runbook の危険閾値「未統合 PR 20 本」の下で、統合 PR 1 本に 181 本・1,368 ファイルが入った。止まったのは装置ではなく人の手番。PR 本数の閾値は AI 駆動で意味が薄い
- スタック型 PR: 実証案件は stacked PR を採用しなかった。理由は ci.yml が `pull_request: branches: [main, develop]` で発火し、feature を base にした PR で CI が 1 つも動かないため。「当時の GitHub の機能と CI の制約」。オーナーは「スタック型 PR に対応できることが重要」
- 提案: (1) Git 戦略の閾値を本数から経過日数と手番停止の検出へ、(2) スタック型 PR のページに段階1 の前提として「CI がどの base でも発火する設定」を明記

### 突合コメント(2026-10-08、判定: 一部)

- (1) は対象を持たない。標準はトランクベースで develop を置かず、統合 PR という工程が無い。停滞の検出は時間軸で既にある(2.10.4 滞留期間、第4章 レビュー SLA、7.5)。旧 runbook は日数閾値も持っていたが 28.8 日の空白が生じた(FND-0254・0266)。**閾値を変えるのではなく検知に措置を結びつけるのが本標準の構成**
- (2) は暗黙にしか書かれていない。stacked-pr.md「各層が満たすべき条件」2(G-5 が通る)と ci-gates.md の骨格例 `on: [pull_request]` は前提を満たすが、「`branches` を絞ると段階1 が成立しない」とは書いていない。前提確認は 2026-08-05 時点で、GitHub 標準のスタック型 PR(2026-07-30 public preview、スタックの基底の規則で全段が評価、FND-0141)を反映していない
- 残る論点: 段階1 の前提に CI の発火条件を明記し、GitHub 標準のスタック型 PR で前提表を更新する

### 外部調査(TH10-Q2、`themes/TH10-repo-git-pr-ci.md` L50-80、L175)

- FND-0141(E1): GitHub 標準のスタックは各 PR をスタックの基底の規則で評価し、main 向け `pull_request` ワークフローは変更なしで全段発火。代償は CI 使用量が段数倍、全ブランチ間の線形履歴が必須、Web の Rebase stack ボタンが committer を書き換えて署名を失わせ、署名必須のブランチ保護を破る
