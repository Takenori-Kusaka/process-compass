## 1. 立場と全体の見立て

1. **小規模チームで規定が形骸化するのは、「止める場所」が実際の危険の場所とずれたときである**。止まるたびに人がラベルを外すだけなら、人は中身を見なくなる(調査 2 の OWASP ASI09 の承認疲れ)。K-2 は止める場所を「取り消せない時間帯を直接生む操作」へ合わせ直す。緩めるのではない。合わせ直すと、既定ブランチへの取り込みが公開を直接起こす構成では、取り込みそのものが止まる側に入ることも明らかになる
2. **手戻りを減らすのは「戻れること」より「戻る先が機械的に決まること」である**。K-1 は、覆された成果物が属するゲートへ戻す(受入基準なら G-2、判断記録なら G-3)と書けば、戻り幅を誰の裁量にもしない。加えて、受入基準を G-2 なしで書き換えた状態を機械で拾う。拾えなければ、条文があっても現場は「PR で受入基準を直す」だけで先へ進む
3. **新しい様式・欄・層を足す案は、AI が数秒で埋める欄になる**。K-6(反対・欠落の列挙)、K-3(読者役の層の規定化)、K-8(規模の下限)は、どれも埋める・数える作業を増やし、効いたかを測る手段が無い。課さないと明記する。ただし K-3 は、AI のサブエージェントで「文脈ゼロ」をやると、プロジェクトの指示ファイルが専門語を教えてしまうという落とし穴を、参考の手引きに書く価値がある
4. **テンプレートが標準の主張を実装していない箇所が、論点の中に 3 つある**。中間層の先行マージの「検査」(K-4)、証跡の保持(K-7)、カバレッジの範囲(K-8)である。本文の文を直すか、テンプレートを直すかを、論点ごとに決める。決めないまま本文に強制層と書き続けるのは、#222 の方針(降りていない規定は `undelivered` で見せ続ける)に反する
5. **小規模チームの大半は定額プランで動いている**。7.7.1 は従量だけを前提にし、定額の現場は「当てはまらない」として読み飛ばす。定額の上限の性質(非公開・可変)を、既存の 3.12.7「上限到達時の扱いを事前に決める」へ繋げる(K-5)。これは新しい義務ではなく、既存の義務の適用範囲を書き出すことである

## 3. 論点ごとの詳細

### K-1 S1 以降の技術検証と、S0 の探索の記録

**判定: 採る(1-B + 1-D)。作業単位としての新設・専用の様式・「検証の完了を実装着手の前提条件にする」は課さないと明記する。**

現場から見た事実。

- #291 以後の G-2 では、測っていない技術の前提を前提の欄へ移せば基準3 は通る(`GC` L168)。判定者は基準に無い懸念を判定へ持ち込めず、非同期コメント期間へ回す(L106)。**ここまでは正しい設計である**。判定で止めるべきでないものを止めないことは、現場の待ち時間を減らす
- 欠けているのは、前提が崩れたときの帰り道である。5.7.2 の「判断が変わる条件」は「再判定へ戻す経路になります」と書く(`HAB` L659)が、誰がどのゲートへ戻すかが無い。テンプレ2 の「顕在化が分かる兆候」も同じ
- 担い手(AI)の側には既に止まる仕組みがある。5.5.1 は「受入基準・スコープ・公開インタフェース・データ形式を変える選択」を人へ戻す(`HAB` L251)。検証の結果で受入基準を変えたくなった AI は、そこで止まる。**止まった後、人が何をすればよいかが書かれていない**
- 人が何もしなくても先へ進めてしまう。G-2 の判定記録は確定した版(コミット)を指すが、確定の後の受入基準の変更を機械は見ない(IMPL-0107 の注記)。現場で最も起きやすい「最小の戻り幅」は、G-2 へ戻らず、PR で受入基準を直して進むことである。G-6 のレビュアは差分を見るが、それが G-2 の確定をやり直すべき変更かは判定の対象ではない

採る内容。

1. **戻る先を、覆された成果物で決める**(1-B)。技術検証の結果(またはその他の観測)が、承認済みの受入基準・前提・判断記録を覆した場合、覆された成果物が属するゲートの判定をやり直す。受入基準・前提の欄なら G-2、判断記録なら G-3。G-2 をやり直した機能では、続く G-4 もやり直す。戻り幅の選択を案件の裁量にしない
2. **確定の後の受入基準の書き換えを機械で拾う**。機能仕様の受入基準の節が、最新の G-2 の判定記録の「対象」が指すコミットから変わっているのに、それより新しい G-2 の判定記録が無い状態を、出荷の証跡の集約で欠落として出す(PR の時点で出すかは別 Issue。K-9)。実装マークは `undelivered` から始める
3. **確かめた結果、前提が保たれた場合は、やり直しを求めない**。前提の行をそのまま残してよい。確認のたびに判定を足すと、検証をしないほうが速いという誘因を作る
4. **探索・技術検証の記録の置き場を案件層とする**(1-D。#289 の D-11 で私が出した 4-C + 4-D をここで引き受ける)。SG-0 へは、実装スタックの判断記録(ADR-0034)と実現性の判定だけを渡し、探索の記録を判定の入力にしない。S1 へ移る時点で、S0 の探索の記録を保管領域へ移す。S1 以降の技術検証の記録も案件層に置き、案件の終了で保管領域へ移す(既存の案件層の規則のまま)。様式は置かない

### K-2 不可逆な操作の停止に「後段の人の門」を足すか

**判定: 採る(2-B: 対象の操作の定義)。#278 の 3 条件による免除(2-C)と、門の事前登録(2-D)は採らない。**

現場から見た事実。

- テンプレートの AI は、既にマージを自分で実行しない。`T/.claude/settings.json` の `ask` に `gh pr merge`・`git push --force`・`npm publish` があり、`T/CLAUDE.md` の (c) は取り消せない操作で止まる。#278 の問題はマージではなく、**マージより前の編集**(ブランチ上で `published: true` と書く)にまで原則4 の停止が掛かる読みである
- 字面どおりに読むと、公開スイッチを書く編集のたびに `state:needs-owner` が立ち、人はそれを外してから PR をレビューし、マージで再び見る。同じ人が同じ判断を 2 回する。1〜2 名のチームでは、ラベルを外す作業は「中身を見ない承認」の練習になる
- 逆向きの穴もある。本リポジトリ自身がそうであるように、既定ブランチへの push が公開を直接起こす構成は珍しくない。そこでは**取り込みそのものが取り消せない操作**である。5.5.5 項目4(本番環境への反映の承認は人が確定)はこれを人へ戻すが、委任(5.5.4)の条件4「単独で取り消せ」は登録の時点で人が確かめるだけ(`T/scripts/gate/delegation.mjs` L50)で、「取り消せない時間帯」の基準(原則4、第8章)との関係が書かれていない。2-B で操作を定義すれば、この関係も同じ文で決まる

採る内容。

- 5.5.1 の「取り消せない操作」を、**取り消せない時間帯を直接生じさせる操作**と定義する。成果物を書き換える編集は、取り消せない時間帯を生じさせるのが後段の別の操作(既定ブランチへの取り込み、ワークフローの起動、配備)である限り、これに当たらない。後段の操作がこれに当たる
- 既定ブランチへの取り込みが、組織外への発行・本番への反映を直接起こす構成では、その取り込みが取り消せない操作に当たる。委任(5.5.4)の条件4 を満たさない
- 門を迂回する起動(手動の公開ワークフロー、直接の配備)は、取り消せない操作に当たる(#278 の起票者の運用と同じ)

文の案(第5章 5.5.1 の表の直後。規定)。

> 「取り消せない操作」は、取り消せない時間帯を直接生じさせる操作を指します。成果物を書き換える編集は、取り消せない時間帯を生じさせるのが後段の別の操作(既定ブランチへの取り込み、ワークフローの起動、配備)である限り、取り消せない操作に当たりません。その後段の操作が当たります。既定ブランチへの取り込みが組織の管理外への発行や本番環境への反映を直接起こす構成では、その取り込みが取り消せない操作に当たり、委任(5.5.4)の対象になりません。後段に人の判定があることを理由に、取り消せない時間帯を直接生じさせる操作を担い手に実行させてはなりません。

### K-3 査読に「文脈ゼロの読者役」の層を置くか

| GitHub 標準のスタックだけを前提にする(手動・他のツールを対象外) | テンプレートは手動の段階1を前提にしている。採用組織の GitHub 以外のホスティング(GHES は未提供)を外す理由が無い |

根拠水準: GitHub 標準のスタックの挙動は E1(一次文書。参照ページは取得時点でもプレビューの表記で、changelog と食い違う)。変化が速い。**暫定マーク E1 / 見直し 2027-04**。差し替え条件: 準拠テンプレートで GitHub 標準のスタックを使い、`github.base_ref` の値と、中間層の先行マージ・着地の保護の挙動を実機で確かめた記録。

### K-5 定額の上限とプロンプトキャッシュ

**判定: 採る(5-B + 5-C + 5-D)。ログの日次の複製(#274 提案3)は課さないと明記する。**

現場から見た事実。

- 1〜5 名のチームの多くは定額プラン(Claude Max など)で動く。7.7.1 は AI 実行予算を「従量費用」と定義し、「席数を単位とする年次予算の枠組みでは、実際の消費との差を検知できません」と書く(`EE` L277)。定額の現場はこの節を「自分には当てはまらない」と読み飛ばす
- 定額の制約は金額ではなく上限である。上限は非公開で可変(調査 2、Anthropic の一次)。#274 では上限の枯渇でリリースが止まった。3.12.7 の「上限到達時の扱いを G-1 で事前に合意し記録」は、まさにこの場面のための規定なのに、定額の上限に掛かると書かれていない。上限到達後に追加の従量(API 単価、月の支出上限つき)へ移れるプランもある。待つか・移るか・止めるかは、事前に決めないとその場で「移る」が選ばれる
- `MT` のトークン効率は「課金・使用量レポートを機能ID 単位で集計」で、定額では算出元が無い。#274 のログの日次の複製は、これを手元のログで埋める試みだった。複製を課すと、算出元の無い指標のために運用作業が 1 つ増える

文の案。

- 7.7.1 の表の後(規定)

  > 定額の利用契約で AI を使う場合、AI 実行予算の統制の対象は、金額ではなく利用上限の消費です。利用上限は提供者が定め、公開されず変わりうるものとして扱います。上限への到達は第3章 3.12.5 の「利用上限で使えない期間」に当たり、到達したときの扱い(上限の回復を待つ・従量の利用へ移る・実行を止める)は 3.12.7 のとおり企画承認(G-1)の時点で決めて記録します。従量の利用へ移る場合は、支出の上限をあわせて決めます。

- 3.12.7 の「上限に到達した場合の扱い」の項に「提供者が定める定額の利用上限を含む」を足す
- `CS`「AI トークン予算の管理」に 1 項(数値なし)

  > エージェントの費用の多くは、出力ではなく、呼び出しのたびに読み直される常駐の文脈(キャッシュの読み取り)が占めうります。比率はキャッシュの保持時間・呼び出しの間隔・モデルの世代で変わります。常駐の文脈を減らすことが費用に効きます([第3章 3.11.4](/process-compass/phase4-process-design/roles-responsibilities/))。人の承認待ちがキャッシュの保持時間を超えると、書き込みの割増が再び生じます。これを人の確認を急がせる理由にしてはなりません。

- `MT` のトークン効率の行に「診断用。第7章 7.7.8 の評価の入力にしない。利用レポートが機能単位で得られない契約では未測定とする」を足す
- 課さないと明記: 手元のログの退避・複製を求めない(3.12.2 の消費実績の報告で足り、定額では提供者の利用状況の表示によると書く)

落とした案。

| 案 | 落とす理由 |
| --- | --- |
| 5-A 課金形態を区別しないと明記するだけ | 「席数単位では検知できない」の文と両立しない。上限で出荷が止まる定額の失敗の型に、既存の 3.12.7 を届かせない |
| ロール別 turn 比率を指標にする | 7.7.8 要求事項3 と衝突し、突合で不採用が確定(蒸し返さない) |
| キャッシュの比率(57% など)を本文に書く | 39〜70% と揺れ、倍率もモデル世代で変わる(FND-0046・0047)。条項にすると半年で誤りになる |

根拠水準: 定額の上限の性質は E1(提供者の一次文書)、キャッシュの費用構造は E2(公開の実測 2 件と #274)。**`CS` の 1 項に暫定マーク E2 / 見直し 2027-04**(価格体系の変化が速い)。差し替え条件: 提供者の価格・上限の体系の変更、または採用案件でキャッシュの読み取りの比率を測った記録。7.7.1 の読み替えは既存の義務の適用範囲を書き出すもので、値を含まない(マーク不要)。

### K-6 AI の反対理由の構造化出力

**判定: 課さないと明記する(6-A)。**

現場から見た事実。

- AI に「反対理由を 3 軸で出せ」「確かめていない範囲を書け」と要求すると、AI は毎回それを埋める。「確かめていない範囲: 実行時の挙動」「UX 観点: 特になし」が定型文として並ぶ。5.7.2 が人の「確認していない事項」に「なし」を認めないのは、人が書く欄だからで、AI の出力では「なし」以外の定型文が同じ役を果たす
- #268 自身が、スキーマ導入の翌日に 4 PR 連続の drift を記録している(FND-0221)。うち 1 件は反対理由 3 件を満たしたまま証跡の置き場がずれた。導入の前後の比較は無い
- 効いているかを見る手段は既にある。H.4 条件1 の欠陥注入の検出率である。出力に何を書かせたかではなく、注入した欠陥を見つけたかで測る。組織が観点の列挙を要求したければ、指示資産で要求し、検出率で効きを確かめればよい。H.4 はそれを妨げない(「組織が欄の欠落を検査するために構造を定めることは妨げません」)
- 3 軸の 1 つは UX で、ADR-0051 と当たる

文の案(附属書H H.4「指摘の書式」の段落の後。規定)。

> 本標準は、AI の確認の出力に、反対の理由、観点ごとの所見、確かめていない範囲を、含める値として課しません。含める値は所在と根拠です(条件5)。組織がこれらを指示資産で求めることは妨げません。求めた値が欠陥の検出に効いたかは、条件1 の検出率で確かめます。値を出力したことを、確認が行われた根拠にしてはなりません。

落とした案。

| 案 | 落とす理由 |
| --- | --- |
| 6-B 欠落の列挙を含める値に足す | AI は定型文で埋める。条件5 の語を広げる形でも、ADR-0075 決定7(条件を増やさない、実行・代替案を求めない)の趣旨に当たる。効果の測定はレビューの指摘で無い |
| 6-C 案件が登録した観点ごとに所見か「所見なし」を出させる | 決定10 で書式を定めないとした直後に、観点ごとの欄を課す形になる。「所見なし」の欄は埋める作業で、検出率との関係は測られていない |

根拠水準: 課さない判断は EV-0134(E2)と FND-0221(単一事例)に依る。**暫定マーク E2 / 見直し 2027-10**。差し替え条件: 同じ AI の確認で、反対理由・欠落の列挙を要求した場合としない場合の、注入欠陥の検出率の差。

### K-7 PR に添付する証跡の置き場

**判定: 画面・DOM 等の添付は課さないと明記する(7-A)。所在が指す先の到達性を採る(調査 2 の B を本文の要求事項にする)。7-B・7-C は採らない。**

現場から見た事実(冒頭の発見 3)。

- human-verify は 3 要素の文で、分量の下限が無い(`PW` L125-137)。この設計は現場で回る。添付を必須にすると、スクリーンショットを貼るための作業と、貼ったことを確認したことにする経路(G-2 基準3 の理由、`GC` L238)が同時に生まれる
- しかし、テンプレート自身の出荷の証跡が 90 日で消える。`ship-evidence.yml` は保証の開示を Actions の成果物にだけ置き、保持を指定していない。判定記録の「添付」の記入例は CI の実行を指す。前回の出荷との比較・知財潔白性の検査記録の取り込みも、成果物の保持の期間内でしか働かない。出荷の間隔が 3 か月を超える小規模チームでは、次の出荷の時点で前回が「前回なし」になる
- 標準は保管期間を組織に委ねる(`qms-document-control.md` L139)。委ねること自体は正しい(調査 2: SSDF・SLSA も置き場を規定しない)。欠けているのは「実行基盤の既定の保持は、組織が決めた保管期間ではない」という一文で、これが無いと、組織は何も決めずに 90 日の保管を採ったことになる

文の案。

- `PW`「human-verify を自動化しない理由と、様式の最小化」の末尾(課さないと明記)

  > 画面の記録・DOM などの添付を求めません。添付する場合の置き場と保管は、自組織の文書管理規程によります。添付の有無と所在は、確かめたことを示しません。

- 第6章 テンプレ4「添付」の注記(規定。判定記録・トレーラ `Verification`・保証の開示が指す所在に掛ける)

  > 所在として書く記録は、自組織が定める記録の保管期間のあいだ到達できる場所に置かなければなりません。CI の実行基盤の成果物・実行の記録の既定の保持期間を、記録の保管期間とみなしてはなりません。

- 実装マーク: `ship-evidence`(既存の降ろし先)へ `undelivered`。テンプレートは、保証の開示・`evidence.json`・品質レポートを、保持の期間を構成から読んで指定するか、リポジトリ(または組織が指定する保管先)へ残す。どちらにするかはテンプレート側の設計判断として別に決める(K-9)
- `qms-document-control.md` L139 の行に「実行基盤の既定の保持期間を保管期間とみなさない」を足す

落とした案。

| 案 | 落とす理由 |
| --- | --- |
| 7-B 置き場だけを定め、必須にしない | 置き場の規定は採用組織のリポジトリ構成とホスティングに依存する。画像をリポジトリに置く容量・機密の問題もある。到達性で求めれば置き場は組織が選べる |
| 7-C human-verify の所在を出荷の集約で保全 | 集約が読む範囲を、人が書いた文の中の所在へ広げる。所在の先が揮発していた場合の扱いが新たに要る。到達性の要求で、保全の責任は所在を書いた側に置ける |
| 署名付きの attestation を要求 | 非公開リポジトリでは有償プラン依存(調査 2)。承認ごとに何を確かめたかの署名は ADR-0056 で却下済み |
| 保管期間そのものを標準が定める | 規制分野・契約で決まる(調査 2)。ISO 9001 7.5.3 も組織が決める |

根拠水準: 到達性の要求の形は SLSA v1.2・SSDF PS.3 と同型(E1)、保持の既定値は GitHub の一次文書(E1)。値を含まない規定で、実証を要する主張はしない。マークは要らない。テンプレートの保持の不足は事実の確認(ワークフローの記述を読んだ。実機では未確認)。

### K-8 実装向けの検査の規模の下限

**判定: 規模の下限は課さないと明記する(8-A)。測る範囲を定めて記録させることを採る(8-2 の解消)。8-B・8-C は採らない。**

現場から見た事実。

- 2 行のコードで 100% は「何も述べていない」(#254)。ただし隠してもいない。保証の開示には割合と下限が出る。害は、読む人が 100% を安心の材料にすることで、これは割合の分母を併記すれば解ける(下の文の案)
- 規模の下限が害になるのは、**変更で加えたコード**の割合に掛けた場合である。本標準は小さい PR を推す(G-4 の粒度、スタック型 PR)。新規コードに 20 行の下限を掛けると、推奨どおりに小さく切った PR ほど判定されない。AI は変更を細かく切るのが速いので、分割で下限の下に入る経路が常に開く(調査 2: IEC 62304 は分割による低クラス化に寄与の規則で歯止めを置く)
- 基準3 の目安は「新規コード 80%」(`GC` L408)、テンプレートは全体の行の割合で比べる(`coverage-check.mjs` の `total.lines.pct`)。どちらの割合を見ているかが記録にも保証の開示にも出ない。下限の議論より先に、これが現場で読み違いを生む

文の案(第4章 G-5「検査対象が存在しない場合の扱い」の後。規定と課さないと明記の文)。

> 本標準は、カバレッジの判定に、測定の対象の規模の下限を置きません。実装が存在する段階では、規模にかかわらず測定し判定します。変更で加えたコードの割合に下限を置くと、小さく分けた変更ほど判定されなくなり、分割によって判定を避ける経路が開くためです。
>
> 基準3 の基準値は、測る範囲(製品のコードの全体か、変更で加えたコードか)とあわせて企画時に定めます。測定の記録と保証の開示には、割合に加えて、測る範囲と、分母の行数を示します。

- テンプレート: `process.config.json` に測る範囲の項目(既定は `total`)、`coverage-check.mjs` の記録に範囲と分母(`raw.total.lines.total`)を書き、集約の出力に出す。実装マーク `undelivered`(降ろし先は `g5-adapter` か `ship-evidence`)
- G-5 基準3 の目安の「新規コード」は、上の「測る範囲」の例示へ改める(目安が範囲を 1 つに決めているように読める誤りは本文の側)

落とした案。

| 案 | 落とす理由 |
| --- | --- |
| 8-B 規模の下限を構成の欄として置き、下限未満を「判定しない」と記録 | 「対象なし」「未達」「省略」に加えて 4 つ目の状態を作る(ADR-0033 決定7 の向きに反する)。下限未満の状態は「実施しなかった検査が通過として残る」(FND-0194)と同じ形になる |
| 8-C 新規コードに揃え、下限を新規コードへ掛ける | 上の分割の経路。小さい PR ほど判定されない。SonarQube の既定(FND-0193)は製品の既定値であって、効果の測定ではない |
| 案A ステージで有効化 | ADR-0033 決定1・ADR-0050 で却下済み(蒸し返さない) |

根拠水準: 規格は規模でなくリスク・安全度で強度を変える(調査 2、29119・62304・61508。二次・既知)。分割の経路は機序からの推論(E0)。**課さない判断に暫定マーク E1 / 見直し 2027-10**。差し替え条件: 採用案件で、分母の小さい割合の通過の後に、その範囲で欠陥が見つかった件数(分母の併記で読み違いが減ったかを含む)。

## 4. 他の委員に問いたいこと

1. **起草へ**: K-1 の「承認済みの成果物が覆った場合」を第4章「判定の範囲」の後に置く案は、ADR-0036 決定4(判定は当該ゲートの基準のみ)と当たらないと読んだ。やり直しの判定も当該ゲートの基準で行うからである。この読みで新しい ADR の決定として書けるか。ADR-0075 決定4 の「閉じ方3(前提として引き受ける)」と、後で前提が崩れたときのやり直しを同じ ADR に並べるべきか
2. **品質保証と監査へ**: K-1 の機械の検査(受入基準の節が G-2 の対象のコミットから変わった)を、出荷の集約で「記載の欠落」に出すのと、G-7 の判定で差し戻しの理由にするのと、どちらが監査で読める記録になるか。受入基準の節の「変わった」を、曖昧語の除外の印の追加のような形の変更まで拾うと、やり直しの判定が形式の作業になる。差分の範囲をどう切るか
3. **規格へ**: K-2 の「直接生じさせる操作」の定義は、ISO/IEC/IEEE 12207 の変更管理や NIST SP 800-53 の CM-5 の語彙と並べて違和感が無いか。「後段に人の判定があることを理由に、直接生じさせる操作を担い手に実行させてはならない」の 1 文は、委任(5.5.4)の条件4 の読み替えとして足りるか、5.5.4 の側にも書くべきか
4. **擁護へ**: K-7 の「実行基盤の既定の保持期間を保管期間とみなさない」は、`qms-document-control.md` L139「保管期間は本標準が定めない」を崩さないと考える(期間ではなく、期間を決めたかを問う)。崩すと読むなら、どの決定を覆すことになるか
5. **全員へ**: K-4 で、必須チェックの規則を機能ブランチへ掛けると直接の push が拒否される、という推論を私は実機で確かめていない。確かめた委員がいれば、4-B の原案(ルールセットの拡張)を落とす理由をそれで差し替えたい。拒否されないなら、着地の保護に加えて機能ブランチへの必須チェックを任意の強化として書ける
6. **全員へ**: K-3 で「課さないと明記」と「附属書C に手引き」を同時に置くのは、判定の語として 1 つに収まらない。議長が「課さないと明記する」で記録し、手引きを付帯とする扱いでよいか
