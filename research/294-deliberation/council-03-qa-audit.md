## 1. 立場と全体の見立て

1. **8 論点のうち 4 つ(K-1・K-4・K-7・K-8)は、元 Issue が書いた問題より手前に、記録と実態の食い違いがある**。K-1 は「引き受けた」と記録される判定者が断れないこと。K-4 は強制していない検査が強制層として書かれていること。K-7 は確認の一次記録(文)そのものの保全。K-8 は割合だけが残り分母が残らないこと。起票者の提案(置き場の新設・免除・添付の置き場・規模の下限)をそのまま採るより、**食い違いを直す方が信頼性に効く**
2. **免除の形の規定は、監査の立場からは原則として採らない**。免除の条件を満たしたかを誰が判定し、判定の誤りがどこに残るかが書けない規定は、検証できない。K-2 では、免除ではなく**「取り消せない時間帯を開く操作はどれか」の定義**として書き、人が行う操作が門である場合だけを扱う。その門が人でない経路(委任・自動マージ・迂回の起動)は、停止のまま残す
3. **「文脈ゼロ」「確かめていない範囲」「添付の所在」のように、書き手の申告で成り立つ値を記録の根拠にしない**。K-3・K-6・K-7 はどれも、申告を増やす案では検証できる記録にならない。採るのは、**偽りの表示を禁じる規範**(渡した入力を列挙できないのに「文脈ゼロ」と記録してはならない、等)と、機械が実際に知っている値(渡した入力、分母、PR の識別)を記録に残すことである
4. **課さないと決めたものは本文へ書く**。K-3・K-6 の主案、K-5 の手元の記録の退避、K-8 の規模の下限は「課さないと明記する」。ただし、どれも課さない理由の中に「その代わりに何が記録に残るか」を書く。理由だけを書いた「課さない」は、監査で「書かれていない」と区別できない
5. **実証は全論点で薄い**(E1 規範・E2 単一事例)。条項を置く論点はすべて暫定マークを付け、差し替え条件を**記録から数えられるもの**に限る(数えられない条件は見直しの材料にならない)

## 3. 論点ごとの詳細

### K-1 S1 以降の技術検証の置き場と再判定の経路、S0 の探索の記録

**判定: 採る。** 次の 3 つを置く。

**(1) 前提の引き受けを断れることを、前提条件1 の中に書く**(置き場: 第4章「未確定事項(前提条件1)」、L264 の段落の後。テンプレ1 の注記、テンプレ4 の「引き受けた前提」の欄)

> 前提として引き受ける閉じ方は、判定者が引き受けた場合に限り成立する。判定者が引き受けないとした事項は、閉じていない未確定事項に数え、前提条件1 を満たさないものとして提出者へ差し戻さなければならない。引き受けない場合、判定者は、その前提の「崩れたときの影響」のうち引き受けられないものを判定記録に書かなければならない。

- 理由: 現行は「引き受けるのは G-2 の判定者」と書き、判定記録に引き受けた者の名を残す(L264)。一方で基準3 は ID の有無だけを見て(L168)、基準に無い懸念は持ち込めない(L106)。**判定者は記録上は引き受けた者だが、実態は断れない**。監査で「この前提を引き受けたのは誰か」を辿ると判定者に行き着くが、判定者には選択肢が無かった。名前の付いた責任と権限の不一致は、記録が実態を偽る典型である
- ADR-0036 決定4(判定は当該ゲートの基準のみ)と当たらない。前提条件1 の閉じ方の成立要件を書くだけで、基準の外の懸念を持ち込む経路ではない。断る理由を「崩れたときの影響」(仕様に書かれた値)に限るので、判定者の内規を持ち込む経路にもならない
- ADR-0075 決定4 の 3 つの閉じ方は変えない。3 つ目が「判定者の引き受け」で成立することを書き出すだけである。ただし ADR-0075 の会議体がこの帰結を意図したかは確かめていない(調査 1 も同じ)ので、新 ADR に「決定4 の閉じ方3 の成立要件を補う」と記録する

**(2) 崩れた前提を発動条件に、その前提を引き受けたゲートへ戻す**(置き場: 第4章 G-2 の後に「引き受けた前提が崩れた場合」の節。5.7.2 の「判断が変わる条件」の段落に主体と行き先を足す)

> 引き受けた前提が崩れたことが分かった場合、分かった者は、その前提の案件層の ID と、崩れたことを示す観測を記録しなければならない。前提を引き受けた判定記録の対象の成果物は、そのゲートへ差し戻す。差し戻し先を、案件の判断で変えてはならない。
> 判断記録の「判断が変わる条件」が生じた場合も、同じく、その判断記録を承認したゲート(G-3)へ差し戻す。

- 戻り幅は「その前提を引き受けたゲート」で機械的に決まる。#250 の「戻り幅を案件の裁量にすると最小に選ばれる」に対する答えはこれである。判定記録に引き受けた前提の ID が残る(L264)ので、**どこへ戻すかは記録から一意に引ける**。監査で検証できる
- G-3「新しい経路を設けません」(L333)は、事業決裁者の受容拒否の節に掛かる文で、前提の崩れを発動条件にする経路を禁じていない。新しいゲートは作らない。ただし「新しい経路」と読まれうるので、新 ADR に「L333 の範囲は受容拒否の節である」と記録する
- 「崩れたことを示す観測」の記録を求めるのは、崩れたという申告だけで差し戻しが起きる経路(差し戻しの乱用)と、崩れたのに記録しない経路の両方を、観測の有無で監査できるようにするためである。後者(記録しない)は機械では止められない。**止められないことを開示する**(実装マークは `check=manual`)
- 技術検証の置き場(#250 の (1))はこの形で答える。**S1 以降の技術検証は、前提を確かめる作業(閉じ方2)か、引き受けた前提が成り立つかを確かめる作業のどちらかである**。前者は G-2 の前に終わり、後者は結果が「崩れた」なら上の経路に乗る。どちらも置き場は既存(仕様の本文・案件層)で、新しい成果物は要らない

**(3) S0 の探索の記録の置き場と SG-0 へ渡す出力**(ADR-0072 決定4 の送り。置き場: 第2章 2.6 末尾の L183 を置き換える。テンプレートの `context/projects/` の README)

> 探索(S0)の記録は、案件層のコンテキスト(`context/projects/`)に置く。量と書式は定めない。SG-0 の判定者は、基準「技術的実現性が確認されている」の判定で依った探索の結論と、その記録の所在を判定記録に書かなければならない。SG-0 の通過後、探索の記録は削除せず保管する([ADR-0025])。

- 監査の観点の理由: SG-0 の基準「技術的実現性が確認されている」は、何に依って確認したかの記録が無いと、判定の後から検証できない。依った結論を判定記録に残せば、S1 で前提が崩れたとき「SG-0 で何を確かめ、何を確かめていなかったか」を辿れる
- 所在の記録が確認の代わりに通る経路(G-2 基準3 の理由、L238)には当たらないようにする。**SG-0 の判定者が書くのは「依った結論」で、所在はその結論を辿るための索引である**。所在の実在を機械が見ても、それを確認とは数えない、と同じ節に書く
- 量・書式を課さない(ADR-0072 決定4 と同じ)。289 の申し送り(4-D: S1 への移行時に保管領域へ)は「削除せず保管」で受ける

**選ばなかった案**

- 1-A(課さないと明記): 判定者の権限の不一致と、影響を書かせて戻らない前提の表が残る。「未定義ではなく既存の経路で扱う」と答えても、既存の経路(G-3 拒否・5.7.2)のどれも発動条件と主体を持たないので、答えが検証できない
- 1-B の原案(覆された成果物の所属するゲートへ): 「覆されたか」の判断を案件に残す。前提の ID から引く形の方が、記録から一意に決まる
- 1-C(検証タスクを作業単位として置き、G-4 で依存の先頭にあるかを見る): G-4 の基準を増やし、タスクの存在が確認の代わりに通る(タスクがあることと、確かめたことは別)。前提の表に「確かめる手段」の欄を任意で置く案も、ADR-0075 決定3 が退けた「確かめた/想定」の区別の入口になる
- 「検証の完了を実装着手の前提条件とする」(#250 の (2) の後半): ADR-0036 決定3 の条件付き通過に当たる
- S0 のスパイクの様式を新設する: 量・書式を課さない ADR-0072 決定4 と当たり、効果の測定も無い

**根拠水準**: E1(SEBoK のベースライン後の変更管理、Nygard の置き換え、SAFe の Spike。いずれも戻り幅の規定ではない)+ 単一事例(Filetto、原文未読)。暫定マークを付ける。差し替え条件: (a) 判定者が引き受けを断った件数と、そのうち後に確かめて本文へ書いた件数、(b) 引き受けた前提が崩れた件数と、そのうち引き受けたゲートへ差し戻された件数(差し戻されなかったものは経路の不全)。見直し 2027-10。

**新 ADR が要る**: 要る。ADR-0075 決定4 の閉じ方3 の成立要件、前提の崩れによる差し戻し、ADR-0072 決定4 の送りの回収を記録する。ADR-0036・0072・0075 は覆さない(補う)。

### K-2 不可逆な操作の停止条件に「後段に人だけが通せる門」を足すか

**判定: 採る(取り消せない操作の定義として)。免除は課さないと明記する。**

置き場は第5章 5.5.1(本文が正本。原則4 はフェーズ5 で本文を狭められない: `overview.md` L291)。原則4 は 5.5.1 を参照する。

> 取り消せない操作とは、取り消せない時間帯をその操作が開くものをいう。ブランチ上の編集で、取り消せない時間帯を開くのが後段の別の操作である場合、その後段の操作が 5.5.5 項目4 の本番環境への反映の承認(または発行の承認)として人が行うものに限り、その編集を取り消せない操作に数えない。
> 次の場合は、編集の段で人へ戻さなければならない。
> - 後段の操作を人が行わない場合(委任の変更のマージ、自動マージ、予約された公開、後段の起動を担い手が行う構成)
> - 編集が統制を弱める場合(検証ゲート・ガード・重要なテストの削除を含む。原則4 の例示)
> - 後段の門を通らずに取り消せない時間帯を開く操作(手動のワークフローの起動、直接の反映)。これは、それ自体が取り消せない操作である
> 後段に人の門があることを理由に、取り消せない操作そのものの停止を免れてはならない。

- **免除ではなく定義にする理由**: #278 の 3 条件(門の実在・一意性・迂回の閉塞)は、誰が満たしたと判定するのかが書けない。実行主体に判定させると、委任の条件2(該当の判定を行為する AI 自身にさせない)と同じ理由で採れない。迂回の閉塞は、管理者の迂回の既定(GitHub の Environments は既定で管理者が迂回できる: 調査 2)や IMPL-0237 の undelivered があり、実行主体には確かめようがない。定義の形なら判定は不要で、「後段の操作を人が行うか」は 5.5.5 項目4 が既に要求している
- **EV-0039 との関係(発見 4)**: 免除を置くと、「基準を満たすのに停止されなかった件数」(差し替え条件 (b))に免除による不停止が混ざり、基準の誤りを測れなくなる。定義の形では、上流の編集はそもそも基準を満たさないので (b) を汚さない
- **ADR-0028・0029 との関係(1〜2 名体制)**: 1 名体制では、原則4 の停止(`state:needs-owner`)の宛先も、後段のマージを行う者も同じ本人である。停止を残しても、同じ人の 2 回目の操作が増えるだけで、独立性は増えない。**失わないために要るのは、後段の操作が人の明示の操作であること**で、上の「後段の操作を人が行わない場合は停止」で担保する。G-6 の未達の表示(ADR-0028)は停止条件と別の装置で、この定義で消えない
- **委任(5.5.4)との関係**: 委任の条件4(単独で取り消せる)により、取り消せない時間帯を開く変更は委任の対象外である。上の「委任の変更のマージは停止」は条件4 と同じ向きで、矛盾しない。マージで公開する構成(既定ブランチへの push で配備する)では、その変更は条件4 を満たさないことを 5.5.4 の注記に書き足す
- **原則4 の削除の例示(発見 3)**: ブランチ上の削除は取り消せない時間帯を開かない。停止の根拠は統制の弱化(ADR-0038)で、取り消せないことではない。定義を書くと、この例示の根拠が「取り消せない」ではないことが表に出る。**原則4 の例示の書き方が誤り**(取り消せない操作と統制の弱化を同じ列に並べている)で、本 Issue で例示を 2 つの根拠に分けて書く
- 監査で残る弱点: 人がマージするとき、そのマージが公開であると知っているかは記録に残らない。D-0 に「既定ブランチへのマージは組織外への発行である」を書かせる案は、D-0 の統制の検査(`ci-gates.md` L216-221)の項目を増やすので、この判定では課さない。代わりに、5.5.5 項目4 の承認が人の明示の操作であることを要件にする。知らずに承認したかは、事後の観測(公開を意図しなかった公開の件数)で数える

**選ばなかった案**

- 2-A(無条件のまま、課さないと明記): ブランチ上で公開の設定を書く編集まで停止の対象に読める状態が残る(調査 1 の 2-3)。本リポジトリ自身、既定ブランチへの push で公開するので、字面どおりなら全変更が停止の対象になり、停止が常態化して形骸化する。形骸化した停止は記録の上だけの統制である
- 2-C(3 条件の免除): 上の通り、判定の主体が書けず、EV-0039 を測れなくし、迂回の閉塞を実行主体が確かめられない
- 2-D(構成への門の事前登録): 実行主体に判定させない点は良いが、5.5.4 の委任の登録と別の登録を作り、第5章が「別々に登録しない」とする構成に反する。登録の失効を監視する手続も新しく要る。定義の形で同じ効果が得られる

**根拠水準**: 定義そのものは E1(第8章「設計で下げられない危害」の基準を写す)。後段の人の門が前段の停止の代わりになるという判断は E2(publishing-hub 1 件、原文未読)。外部の実務はベンダー自身が「後段は置き換えない」と書く(Codex。調査 2)ので、**この判定は後段で前段を置き換えない形に留めた**。暫定マークを付ける。差し替え条件: 上流の編集を停止しなかった変更のうち、後段の人の操作の前に取り消せない時間帯が開いた件数(1 件でも生じたら定義が誤り)。見直し 2027-10。

**新 ADR が要る**: 要る。ADR-0053 決定1 の基準を「操作が開く」で定義し、決定5(判定工程を足さない)を守る形であることを記録する。ADR-0053 は覆さない。

### K-3 査読に「文脈ゼロの読者役」の層を置くか

**判定: 課さないと明記する。あわせて、偽りの表示を禁じる 1 文を採る。**

置き場: 附属書H H.4 の「数えてはならないもの」の後(規定)。附属書C には参考の手引きを置いてよいが、規範は H.4 に置く。

> 本標準は、組織の外へ渡る成果物に、成果物だけを入力にする確認(読者役)を置くことを課さない。置く場合は、検出の層の条件(H.4)に従い、条件を確かめるまで検出の層に数えない。
> 確認側へ渡した入力(指示ファイル、道具の定義、起動の指示を含む)を列挙できない確認を、文脈を渡していない確認として記録してはならない。

- 課さない理由: (a) AI のサブエージェントは指示ファイル・道具の定義・起動の指示を受け取る(調査 2、Claude Agent SDK の一次)。「文脈ゼロ」は申告でしか成り立たない。(b) H.4 条件1(欠陥注入の検出率)を「文脈の欠落」という欠陥で測る方法が附属書I に無い。課すと、条件を確かめられない層が規定上必要になり、未測定が常態になる。(c) 照らす基準が無い。読者に伝わるかは ADR-0051 が判定基準にしないと決めた。案件が重視するなら受入基準に書き、その受入基準に照らせば既存の G-2・G-6 で扱える。(d) 根拠は publishing-hub 1 件と本プロジェクトの #286 の 1 回(E2)で、外部に AI 読者役の有効性の一次研究は見つかっていない(調査 2)
- 禁止の文を置く理由: 課さなくても、案件が置いて記録する場合がある。そのときに「文脈ゼロで読ませた」と記録すれば、渡した指示ファイルの影響が記録から消える。**記録の偽りを防ぐのは要求事項として書く必要がある**。列挙は機械が持っている値(起動の指示、読み込まれる指示ファイルの一覧)で足りる
- #279 の提案(4)の接続先 `community/feedback-workflow.md` は本リポジトリへのフィードバックの手続で、採用組織の手続ではない(調査 1 の 3-2)。採否は H.4 条件5 と ADR-0075 決定8 による。**提案(4)は誤り**と記録する

**選ばなかった案**

- 3-B(附属書C に参考として置くだけ): 参考なので偽りの表示を禁じられない。手引きだけが置かれると、「文脈ゼロの確認を経た」という記録が規範の外で増える
- 3-C(H.4 の検出の層の種別として規定): 条件1 を測る方法が無いまま種別を足すと、数えられない層の規定が増えるだけ。ADR-0075 決定12(系統の異質性を求めない)と同じ扱いで足りる
- 3-D(組織外へ渡る成果物に要求): ADR-0053 決定5 が却下した「発行前の独立した判定工程」と同型。ADR-0051 とも当たる

**根拠水準**: 課さない判断は E2(反証も実証も単一事例)。禁止の文は E1(サブエージェントの入力の仕様の一次)。暫定マークを課さない判断に付ける。差し替え条件: 組織外へ渡った成果物について、受入基準に照らして事後に見つかった前提・呼び名の欠落の件数と、読者役を置いた案件・置かない案件の比較。見直し 2027-10。

### K-4 スタック型 PR の CI の発火条件と GitHub 標準のスタック機能

**判定: 採る(4-B の改案 + 実装マーク + 前提表の更新)。ネイティブのスタックを前提を満たす構成として書くことは先送り。**

置き場: `SP` の前提の確認・段階表・フェイルセーフ・AI への指示、`ci-gates.md` の「基底ブランチから読む」節。本文側は第4章 L1307(手順はフェーズ5 に規定)のまま。

文の案(`SP` 段階1 の前提条件、「なし」を置き換える):

> 既定ブランチ以外を基底とする PR のマージは、G-5・G-6 の証跡にならない。G-5 の判定と G-6 の承認は、既定ブランチへ着地する PR の上で成立する。上の層を下の層のブランチへマージした場合、既定ブランチへの承認は合わさった差分に対するものになり、層ごとの確認として数えてはならない。
> G-5 の検査を、既定ブランチ以外を基底とする PR でも発火させる(ワークフローの契機で基底を絞らない)。

- **監査で見た実態(発見 5)**: テンプレートのルールセットは既定ブランチだけを対象にし、`dismiss_stale_reviews_on_push` と `require_last_push_approval` を持つ。上の層を下の層へマージすると、下の層の PR にコミットが入り、既定ブランチへの承認は取り直しになる。**G-5・G-6 を経ずに main へ入る経路は、テンプレートの既定の構成では見つからない**。見つかったのは、層ごとに見たことになっている G-6 が、実際には合わさった差分で成立する経路である。スタックの目的(小さく見る)が記録の上だけで達成されたことになる
- **実装マーク(発見 6)**: `SP` の「中間層の先行マージを検査で拒否」(L95)と「強制層(中間層のマージを検査で拒否)」(L176)に、`state=undelivered` の実装マークを付ける。降ろし先の登録が要るかは `impl-targets.yaml` を見て決める(見ていない)。検査を作るまでの間に「強制層」とだけ書いて印が無い状態は、#222 の方針に反する。**誤りは本文**(降りていない規定を降りたように書いている)
- **ネイティブのスタックの前提表**: 2026-07-30 のパブリックプレビューと 2026-10-06 の GA(github.com 全プラン。GHES は今後)、規則がスタックの基底で評価されること、CI 使用量が段数倍、線形履歴が必須、GA で Rebase stack が署名付きの置換コミットを作るようになったこと(プレビュー時の署名喪失の記述は更新が要る)を載せる。reference の頁は取得時点で preview 表記のまま(調査 2)なので、確認日を書く
- **先送りの中身**: pr-rules は基準値・例外承認の台帳を基底ブランチから読む(`ci-gates.md` L146)。ネイティブのスタックで `github.base_ref` が直接の親を指すなら、未マージで未レビューの下層のブランチから閾値を読むことになり、「PR の中で基準値を上げて通す経路を塞ぐ」設計が層を跨いで成り立たない。**これを確かめるまで、ネイティブのスタックを段階1 の前提を満たす構成として書かない**。足りない材料: ネイティブのスタックの PR でのイベントの `base_ref` の値と `github.event.pull_request.stack.base.ref` の値の実測(確認の方法は、テンプレートの試行のリポジトリで 2 層のスタックを作り、`gate-g5` のログに両方を出す)
- **確かめていない経路(要確認)**: 必須ステータスチェックは head の SHA に付く。手動スタックで上の層の PR を下の層を基底にして `gate-g5` 成功まで進め、下の層のマージ後に既定ブランチへ付け替えたとき、再実行の前に古い基底で得た成功でマージできる時間帯があるか。テンプレートは `edited` を契機に含むが、付け替えで発火するかを確かめていない。`strict_required_status_checks_policy: true` で最新化が要るので実際には再実行される見込みが高いが、**見込みであって確認ではない**。確かめる作業を実装の段へ送る

**選ばなかった案**

- 4-A(課さないと明記、日付の更新だけ): 強制していない検査が強制層と書かれたまま残る
- 4-B の原案のうち「ルールセットの対象を機能ブランチへ広げる」: `pull_request` の規則を全ブランチに掛けると、作業ブランチへの直接の push まで止まり、1 タスク=1 ブランチの運用(`git-strategy.md`)が成り立たない。ブランチ名の型(例 `stack/**`)で限る構成は、型に従わないブランチで素通りし、監査で検証できない
- 4-C を今の材料で採る: 上の先送りの理由
- 4-D(エージェントのスタックの負担増を「導入しない判断」へ): 採ってよいが、FND-0142 と FND-0143 は単一事例どうしで向きが逆(E2)。監査の立場からは中立。足すなら EV マークを付ける

**根拠水準**: 事実の記述(GitHub の機能)は E1(公式の changelog・docs)。volatility が高く、見直しを 2026-12 とする。段階1 の前提の文は本文の G-5・G-6 の成立要件を写すだけで、新しい判断ではない。

### K-5 定額の上限の性質と、プロンプトキャッシュの費用構造

**判定: 採る(5-B の改案 + 5-D)。手元の記録の日次の退避は課さないと明記する。5-C は参考として置く。**

文の案(第3章 3.12.7 の末尾。7.7.1 の表の注記から参照する):

> 定額の契約で AI 実行基盤を使う場合、消費の制約は提供者が定める利用上限であり、その値は保証されず変動する。組織が接続経路の上で消費の前に強制する上限を持てない場合、その状態を本節の要求を満たせない状態として D-0 に記録しなければならない。上限到達時の扱い(停止、従量の利用への切替と支出の上限、人へ戻す)は、定額の場合も G-1 で合意し記録する。

- 監査の理由: 5-A(課金形態を区別しない)を採ると、定額で運用する案件は 7.7.2 の消化率を 0 か空欄で埋め、3.12.7 の強制を満たしたように見える。**測れないものを測れないと記録させる**のが要である
- 3.12.2(直接接続を認めない)は定額でも緩めない。個人の定額契約を利用者が直接使う形(#274 の実証案件の形)は 3.12.2 を満たさない。調査 1 の 5-2 が「規定の外にある」と書いたのは誤りに近い: 規定の外ではなく、**規定に反した状態**である。本文はそれを未達として記録させる形で受ける(緩めない)

- 5-C(キャッシュの費用構造): compute-strategy に数値なしで書く(常駐の文脈の再読が費用の多くを占めうる、比率は TTL・頻度・モデル世代で変わる、人の承認待ちが TTL を超えると書き込みの割増が再発する)。フェーズ5 の記述で、要求事項ではない。数値を書かない形でも、57%(n=1)と 39〜70%(FND-0047)に依るので E2 の暫定マークを付ける
- 手元の記録の日次の退避(#274 の (3)): 課さないと明記する。消費の実績の記録は接続経路の側の責任(3.12.2)で、手元の記録を正本にすると、経路の外の利用を記録の上で正規化する。経路で取れない場合は上の「未測定」で扱う

**選ばなかった案**

### K-6 AI の反対理由の構造化出力

**判定: 課さないと明記する。**

置き場: 附属書H「指摘の書式」の EV-0134 の後。

> 本標準は、AI の確認の出力に、観点ごとの反対理由、確かめた範囲または確かめていない範囲の申告を含めることを求めない。組織が求めた場合も、その申告を確認の範囲の根拠にしてはならない。確認の範囲は、確認側へ渡した入力の記録で示す。

- 理由: (a) 「確かめていない範囲」は AI の自己申告で、読んでいない作業を完了と報告する現象(FND-0091 E3)の上に立つ。人の決断の記録の「確認していない事項」(5.7.2)は記名した人が責任を負う欄で、同じ型を AI に持ち込んでも責任の主体が無い。(b) 反対理由のスキーマを満たしたまま証跡の置き場がずれた観測がある(FND-0221)。欄の充足は内容を示さない(ADR-0075 決定10 と同じ向き)。(c) business/UX/security の観点を標準が指定すると、UX は ADR-0051 と当たり、観点の選択は案件の価値の指定になる。組織が観点を定めることは決定10 の「構造を定めることは妨げない」で既に許されている
- 「確認の範囲は渡した入力の記録で示す」を書く理由: 確認の範囲として監査で検証できるのは、機械が持っている値(渡した差分・仕様・受入基準)だけである。H.4 条件2(入力の分離)の確認と同じ記録で足り、新しい欄は要らない
- FND-0083(E3)・FND-0224(E0)の支持は「要求した値」が効いたとする。所在と根拠(ADR-0075 決定7)が既に値を求めている。観点別の比較が効くかは、AI の指摘で測られていない

**選ばなかった案**

- 6-B(欠落の列挙を含める値に足す): 上の (a)。自己申告の範囲を記録すると、人のレビュアが「AI が見た範囲」を確認済みと読む経路が開く
- 6-C(案件が観点を登録し、観点ごとの所見を値に含める): 組織が定めることは既に妨げられていない。標準が「観点ごとに『所見なし』を出させる」と書くと、「所見なし」が確認した証拠として読まれる(5.7.2 で「なし」を確認していない兆候とする作法と逆向き)

**根拠水準**: E2(FND-0221 の単一の観測、FND-0083 は値の効果を示すが観点別の効果を AI のレビューで測っていない)。暫定マークを付ける。差し替え条件: 観点別の値を求めた組織と求めない組織の、注入欠陥の検出率と採用率の差(5.6.2 の記録から数える)。見直し 2027-10。

### K-7 PR に添付する証跡の置き場

**判定: 採る(確認の文の保全)。添付物の置き場・保持・署名は課さないと明記する。**

文の案(第4章 G-7 の出荷の証跡の集約を定める箇所。`PW`「human-verify を自動化しない理由」の後に参照):

> 出荷の証跡の集約は、対象範囲の変更の「検証方法と結果」の記載を、変更の識別(PR の番号とマージのコミット)とともに出荷の証跡へ写さなければならない。写した後に PR の側の記載が変わった場合、その差を記録の改変として扱う。
> 本標準は、画面・DOM などの添付物を求めず、その置き場・保持期間・署名を定めない。添付の有無と所在を、確かめたことの根拠にしてはならない。
> CI の成果物の既定の保持期間を、記録の保管とみなしてはならない。記録の保管期間は自組織の文書管理規程による。

- **監査で見た実態(発見 9)**: 「人が動かして確かめた」の一次の記録は PR 本文の文で、出荷の集約は有無を見る(`aggregate-evidence.mjs` L873)。文はマージの後も編集でき、プラットフォームの移行で失われうる。保管の主体はどこにも書かれていない(`qms-document-control.md` L139 は期間を組織に委ねるだけ)。**添付物の置き場より、文そのものの保全が先**である。集約が文を写していればこの指摘は半分で済むが、確かめていない(本文の写しの有無は実装の段で確かめる)
- 文を写すことは、記述の実質性を機械で判定すること(5.7.4 要求事項1)に当たらない。写すだけで、内容は判定しない。集約が読む範囲を広げることは ADR-0074(上限を置かない)と当たらない
- 添付を課さない理由: 添付の所在を必須にすると、G-2 基準3 の理由(L238「記録の所在を書けば確かめたことになる経路を開く。機械が見られるのは所在の実在まで」)をそのまま開く。#271 の実証案件の最終形(統合のマージに署名)は承認の事実の署名で、ADR-0056 の却下表(承認ごとに何を確かめたかの署名様式を採らない)と同じ線で採らない。GitHub の attestation は個別ファイルの署名に使うべきでないと提供者自身が書く(FND-0100)
- CI の成果物の保持の文を置く理由: 既定 90 日、2026-10-01 以降はチェックの履歴も設定に従って消える(調査 2、一次)。判定記録が CI の実行の URL を所在として指している場合、90 日後には所在の先が無い。**所在が実在しなくなった記録を、所在があった記録と区別できなくなる**ので、保管とみなさないことを明記する

**選ばなかった案**

- 7-B(置き場だけ定めて必須にしない): 置き場を定めると、置き場に何かがあることが「確かめた」の代用になる。必須でなくても、置いた案件では所在が確認の代わりに通る
- 調査 2 の A(保持期間 ≥ 保守期間、改ざん検知を要求): 保持期間は組織の文書管理規程による(L139)という既存の決定と当たる。改ざんの検出は、上の「写した後の差を改変として扱う」で文に限って満たす。添付物にまで掛けると署名の基盤が要り、非公開リポジトリでは有償のプランに依存する(調査 2)

**根拠水準**: E1(SLSA・SSDF は到達性と保管を求め置き場を規定しない。GitHub の保持の一次)。文の写しの効果は測られていない。暫定マークは文の写しの要求に付ける。差し替え条件: 出荷の後に、写した記載と PR の記載が食い違った件数。見直し 2027-10。

### K-8 実装向けの検査の規模の下限

**判定: 規模の下限は課さないと明記する。分母の記録と、測る量の明示を採る。**

置き場: 第4章 G-5「検査対象が存在しない場合の扱い」の L534 の段落の後、G-5 基準表の基準3 の確認方法。

> 本標準は、カバレッジの判定に、測定対象の規模の下限を置かない。実装が存在する段階では、規模にかかわらず測定し判定する。
> 基準3 の証跡には、割合とともに、測定対象の量(行数または文の数)を残さなければならない。
> 基準値を設定するときは、何の割合を比べるか(全体、新規のコードなど)を併せて決めて記録する。検査は、記録した量を測らなければならない。
> 検査の道具を持たないために測定しなかった基準は、通過ではなく未実施として G-5 の判定で失敗に数える。

- **規模の下限を採らない理由**: 下限未満を「判定しない」と記録する 8-B は、「対象なし」とも通過とも違う第 3 の状態を作り、ADR-0033 決定7(状態を増やさない)と L534 に当たる。実施しなかった検査を通過として残す製品の既定(FND-0194)と同じ型になる。8-C(新規のコードに下限)は、小さい変更ほど判定されない状態を常態にし、分割で下限を下回る回避を生む(62304 の寄与の規則に当たる歯止めが要る: 調査 2)。外部の規格は規模でなくリスク・安全クラスで強度を変える(29119・62304・61508、多くは既知・二次)。規模で強度を変える規格は見つかっていない
- **分母を残す理由(発見 7)**: #254 の「2 行で 100% は何も述べていない」は正しいが、述べていないことが記録から読めないことが問題である。分母が証跡にあれば、監査人は「2 行中 2 行」を読める。新しい状態を作らず、弱い信号を隠さない。`coverage-check.mjs` の `writeResult` に分母を足すのは 1 行の変更だが、変更の量は理由にしない。理由は、記録が実態を表すことである
- **測る量を明示する理由**: 基準3 の目安は「新規コード 80%」(L407)、テンプレートは全体の行の割合で比べる(`coverage-check.mjs` L60-71)。どちらを採るかは組織の決定でよいが、**証跡の「85%」が何の 85% か読めない**。全体の割合なら、テストの無い大きな変更が既存の高い割合に紛れて通る。規模の下限より、こちらの方が大きな穴である
- **測る道具の無い基準(発見 8)**: `go`・`none`・`undetermined` のアダプタは基準3 を測らずに `exit 0` で通す。IMPL-0234 が undelivered で開示しているが、本文に「測る道具が無い」の扱いが無いので、開示が規定の欠落を補っている状態である。ADR-0077 の「入力の欠如は対象なしでなく未実施の失敗」と同じ線を、道具の欠如に延ばす。`go` は標準の道具でカバレッジを出せるので、アダプタの側を直せる
- #254 の突合の後継題名案にあった「判定記録の整合検査を PR 時点で走らせるか」は、#294 の論点の文に入っていない。G-5 の基準を増やす話で(ADR-0033 決定1・#290「基準は 8 つのまま」)、別 Issue へ送る(K-9)

**選ばなかった案**

- 8-B・8-C: 上の理由
- 8-A だけ(分母と測る量を足さない): #254 の指摘(下限 90% が何も述べていない)を記録の上で読めないまま残す

**根拠水準**: 下限を課さない判断は E1(外部の規格は規模で強度を変えない。SonarQube の 20 行の下限は製品の既定で、効果の測定は無い)。分母の記録・測る量の明示は記録の要件で、根拠水準の対象になる判断を含まない。暫定マークは下限を課さない判断に付ける。差し替え条件: 実装の開始から一定期間に、分母の小さい通過の後に見つかった欠陥の件数。見直し 2027-10。

## 4. 他の委員に問いたいこと

1. **起草へ**: K-1 の「判定者が前提の引き受けを断れる」は、ADR-0036 決定4 の「当該ゲートの基準のみ」と当たらないと私は読んだ(前提条件1 の閉じ方の成立要件で、断る理由を仕様の「崩れたときの影響」に限るため)。当たると読むなら、判定者の名を引き受けた者として記録に残す L264 の方を外すべきか。**責任の記録と権限の不一致は、どちらかを動かさないと解けない**
2. **現場へ**: K-1 の「崩れたことが分かった者は観測を記録し、引き受けたゲートへ差し戻す」を、実装の途中の担い手(AI を含む)が実際に起こすか。起こさない場合に記録から気づく手掛かり(前提の ID を引く PR の差し戻し、テストの失敗の傾向など)は何か。私は機械では止められないと開示する案にしたが、現場の観測があれば `check=manual` より強くできる
3. **規格へ**: K-2 で、変更管理の規格(事前承認済みの標準変更、CAB)・職務分掌(SOX、NIST CM-5(4))に、「後段の承認を前段の停止の代わりにする」ことを禁じる、または許す明文の先例はあるか。調査 2 は #278 を対象にしておらず、ベンダーの「置き換えない」しか材料が無い
4. **擁護へ**: K-2 の定義の形は、ADR-0053 決定1(基準で定義)の基準を「操作が開く」で絞る。これを決定1 の読み替えと見るか、置き換えと見るか。置き換えなら新 ADR で ADR-0053 の状態を「一部を置き換え」にする必要がある(ADR-0071 の語彙)
5. **全員へ**: K-7 で、出荷の集約が PR 本文の文を写すことに、組織外へ渡す保証の開示(氏名と自由記述を出さない: `qms-document-control.md`)と当たる箇所はあるか。写すのは出荷の証跡(組織内)で、開示へは件数だけを出す想定である
