## 1. 審議すること 1〜6 への見解

### 1. 案A は所有者の決定と懸念に答えているか: 反対(単独では答えていない)

- **S1 は答えている。ただし 1 か所だけ**。S1 の非コア変更で、template が人の承認 1 以上を求めている(`team.json` の `required_approving_review_count: 1`、`require_code_owner_review: false`。generate-profile.mjs 1103 は `required` なら `Math.max(1, reviewerCount)`)。規範より厳しい実装を揃える価値はある。S1 の 3 名で 1 日 12 件、うちコア 30% と置くと、独立の人が読む件数は 12 → 約 4 件になる
- **S2 は 1 件も減らない**。1 日 30 件を 2 名で読むと 15 件/人/日。時間は R1 10 件×… ではなく、3 件(R1)×40 分+12 件(R2)×20 分+15 件(R3)×10 分=計 8.5 時間を、2 名で割ると 4.3 時間/人/日。読むだけで 1 日の半分以上で、制御1 の同時 3 件を守ると、1 人が抱える 3 件が捌けるまで次を指名できない。**作る側は待つか別の作業へ回るしかない**。案A の後も、この数字は変わらない
- 変わるのは、O-2〜O-6 で委任が開いた後の R3 だけである。R3 の登録した種別(15×60%=9 件)が事後の抜き取りへ移れば、事前に読む件数は 30 → 21 件、時間は 8.5 → 7.0 時間(3.5 時間/人)になる。**この減り分は案A の成果ではなく O-2〜O-6 の成果**で、案A は「表を書いた」ことになる。所有者の期待(人の負担が目に見えて減る)に対し、案A が単独で渡せる減りは S1 の非コアだけである
- しかも委任は S2 の R3 にしか立たない(HAB 5.5.4 の条件2 が R3、条件5 がコア除外。proposal 診断6 のとおり)。**S2 の R1・R2 の 70%(21 件)は、ステージ連動の表を書いても動かない**。ここが所有者の言う「人がボトルネックになる構成」そのものである
- 結論: 案A は**必要条件であって十分条件ではない**。採るなら、S2 の R2 について別の手(§2)を同じ束で示す。示せないなら、所有者へ「S2 の R2 は減らない」と**数で**開示する(起草 §4 の最後の段落は文で書いているが、数が無い)

### 2. 「作るのを止める」の扱い: 条件つき賛成

- 起草 §6 の分け方(積み増しを止める/取り込みを止める)は正しい。所有者の理由は「リソースが空く」ことで、**取り込みの遅れ**ではない。R1・R2 とコア機能の取り込み停止を床に残すことは安全側で、私も怖いので賛成する
- ただし**手を止めない先**が無いと、絵に描いた餅になる。S2 の 2 名のレビュアが 15 件/人を抱え、作成側の 6 名が上限に当たった時、「G-6 を要しない作業へ回る」先は、仕様・テスト・負債の返却に限られる(起草 §6 の2)。その量は 1 日分に足りない。**待ち時間の穴を埋める仕事は、作る前に計画へ載せておかなければ無い**。手引きに「上限に達した日の仕事の候補」を置くことは足さずに済む(既存の負債台帳と仕様の仕事)ので、条文にせず手引きだけでよい
- 争点5 の「上限が空いた瞬間に押し寄せる害」は現実に起きる。解決は、押し寄せた分を**リスク順に並べる**(起草 §6 の3)に加え、**R1・R2 を先に読み、R3 を後ろへ**にとどめる。新しい義務は足さない

### 3. 既定値を置かない扱い: 条件つき賛成。引き下げ側 V2・V3 は対象から外す

- 起草 §7 の(iv)(未設定は当月の全件を事後に確かめる)は、V7・V9 で賛成する。ただし**現場にとっては重い**。V9 を決めない採用者は、委任した全件を毎月読むことになる。つまり「決めないほうが読む量が多い」ので、決める誘因になり、O-2 とも合う。ゲーミングの向きは健全
- V7(窓の最小標本 30)は、template が `MIN_SAMPLE` を import して初期化まで落ちる(DI §3)。欄を足す直しは、初期化を壊しやすい。**欄の新設より、まず試験の入力へ値を渡す形に直す**ことを先にする
- **V2・V3 は外す(起草 (b)に賛成)**。「AI 起因の Sev1・Sev2 が起きたら 1 段下げる」を採用者が「2 件までは下げない」と決められると、事故の後で止められなくなる。現場は事故の後に初めて怖さに気づく。引き下げの発火は規則で、閾値ではない。ここは弱めると安全に当たるので、重の審議なしには触らない
- V4(窓 2 か月)は、template が既に「長くする向きだけ」を受けている。対象に含めてよい
- V8(同時保有 3 件)は(ii)=通知を出さないに賛成だが、**1 点危ない**。通知が無いと、S2 のレビュアが 3 件を超えて抱えても誰も気づかない。値を決めた者は少なく、通知の無い構成が既定になる。「止めない通知」は O-2 と衝突しない(DI §7)ので、通知は残し、値が無い間は**全件に対する日次の件数表示**に倒すほうが現場に優しい。ただし新しい出力を足すことになるので、足さずに済むか(既存の `review-queue.mjs` が数を出しているか)を確かめてから決める

### 4. 既存 ADR の一部置き換えの記録の置き場: 条件つき賛成(起草の 4)

## 2. 推す案と、採用初日の変更 1 件の流れ

**推す案: 案A+「S2 の R2・R1 を数で開示する一文」+ 手を止めない先の手引き。案 B・C・E は採らない。**

## 3. 自分の立場から見た最大の危険

**危険1(実装): CODEOWNERS 方式の自己承認の穴と、パス宣言の漏れ**。

- 3 名の S1 で、コア機能のコードオーナーが 1 名なら、その人が書いた PR は GitHub の規則上、本人が承認できない(推定。実機で未確認)。別の人を加えるしかなく、体制が 2 名になった日にコア機能の PR が通らなくなる。**止まるのは「コア機能に触れる PR」で、一番急ぐものから止まる**
- パスの宣言を漏らすと、コア機能の変更が独立の確認なしに入る(起草 §3 案A の破られたとき)。歯止めは未宣言なら全変更、既存の IMPL-0469 の歯止めと同じ。**怖いのは宣言の「古さ」**: 機能が増えてパスが広がり、宣言が追いつかない。S1 は事業が動く段階で、ディレクトリの再編が日常的に起きる。名前の変更の元のパスを含める判定(IMPL-0469)は残すべきである
- **誰が何を失うか**: 価値責任者と顧客。コア機能(事業の約束を担う所)の欠陥が、独立の目なしに本番へ出る。復旧の責任は席の責任者にあり、その人は事前の確認の機会を持たなかった

**危険2(設計): S2 の R2 の負担が減らないのに、「ステージに連動した」と開示される**。

- 現場は「連動した」と読み、S2 で人が減ったと誤る。レビュア 2 名で 30 件を回す構成を組み、待ちが出て、「待たせてはならない」ので G-6 を急ぐ。結果は X-09・X-11 の形だけの承認である。**人が読み切れない量に形だけの確認を課すことは信頼性を下げる**(判断軸)。失うのは品質監査の席と、事故後の説明責任を負う価値責任者である
- 対策は、案Aの本文に「S2 の R2・R1 は事前に読み、減らす手は L2 の配分と R3 の登録だけ」と**数と一緒に**書くこと

## 5. 起草の案の事実の誤り(見つけたもの)

1. **proposal §2.1 の S1 の R1 の升**: 「前+記 ※1」と書くが、IMPL-0469 の注記は「R1 は例外承認を要する」で、G-6 ではない。※1 の本文は「G-6 か例外承認」と両論を併記し、表と注記が食い違う。表の升は「例外承認+記」か、注記の読みを確かめて直す(§10 の未確認と同じ点)
2. **proposal §2.2 の S1 の「必須の承認 1 以上」**: 実装は 2 つの出所がある。`team.json` は `required_approving_review_count: 1` の固定、generate-profile.mjs 1103 は `Math.max(1, reviewerCount)`(reviewer 数)。S2 の 8 名で承認数が 8 になるのか 1 のままか、どちらが効くかを書いていない。**現場には致命的な差**(承認が 8 件要れば、30 件/日は回らない)。確かめる必要がある(私は実行していない。読みだけ)
3. **proposal §4 の「案A は新しい義務を足さない」**: コア機能のパスの宣言(`delegation.protectedPaths` と区分の下限の規則のパスの和)は既にある、と起草は読むが、CODEOWNERS 方式を採ると、パスに加えてオーナー(人)の割当と、本人以外の承認者の確保が要る。**採用者への新しい作業になる**。(b) の G-5 の検査方式なら足さずに済む
4. **proposal §4 の「R2 を委任へ上げることは EV-0040 の差し替え条件が禁じています」**: I2 §7 の6 は「EV-0040 の差し替え条件に『R2 の上限を委任へ上げる根拠にしない』と明記」で、EV-0040 を根拠にしないという書き方である。「禁じる」は強い。ADR-0054 決定3・4(運用形態の上限)のほうが禁止に近い。所在を揃えて書く
5. **proposal §2.1 の S0 の R3 非コア「本」の升**: S0 は「コア指定なし」(TG 543)なので、S0 の R3 は全部が非コア。表では S0 の R3 の列が「(コア指定なし)」と「本」で分かれており、読み手を迷わせる。S0 の R3 は 1 列でよい
6. **proposal §6 の 2**: 「自分が任命基準を満たすなら他の人の変更の確認」は、S2 の作成側(6 名)が確認者になれるかを、任命基準(G-6 の席)に頼っている。任命基準を満たす人数は多くないので、「手を止めない先」にはほぼならない。数を見て書く
