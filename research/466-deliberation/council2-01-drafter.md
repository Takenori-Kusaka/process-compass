## 3. 自分の立場から見た最大の危険

- **危険**: 案A+ を実装しても、S2 の R2 の事前の読みと、S1 の「下限に当たらない R1」の扱いの 2 点で、所有者の期待(負担の目に見える減少)と規範の厳しさ(減らさない)の差が残り、また「答えていない」と再び差し戻される。もう 1 つは、template が「コア機能のパス」しか機械で拾えず、パスで表せない区分(R1)を取りこぼすこと
- **起きたとき誰が何を失うか**: (a) 所有者は 2 回審議を重ねても期待した負担減を得られず、標準への信頼を失う。(b) S1 の採用者は、パス宣言の漏れた R1(外部契約・公開 IF の変更など)が独立の事前確認なしに入るという**見えない穴**を負う。失う確認の機会は、事後に取り返しにくい種類の変更のもの。歯止め(未宣言なら全変更へ倒す)は、宣言の漏れ(宣言はあるが不十分)には効かない
- 緩和: S1 の R1 は区分の確定の記名(記)が機械で必須であること、S1 → S2 で全変更へ戻ること、出荷の証跡の集約が「独立の確認を経ていない変更の件数」を出すこと(TG 615)。穴は残るので、根拠水準マークと保証の開示に書く

## 5. 起草の案の事実の誤り・食い違い

1. **S1 の R1 の升の読みと案A の降ろし方が整合しない**。提案 表2.1 は S1・R1 を「前+記」とし、注 ※1 は「下限のパスに当たらない R1 は G-6 か例外承認を要する」と読む。一方、案A は S1 の承認をコア機能のパス(`delegation.protectedPaths` と下限のパスの和)に降ろすと言う。**パスに当たらない R1 は、パスの宣言では拾えない**。この読みが正しければ案A は注 ※1 を満たせず、「規範の中身を変えない」が崩れる。提案 §10 も「注記の読みで未確認」と認めている。実装の前に、IMPL-0469 の注記の読みと TG の G-6 の節(core-only の定義)を、この点だけ確かめる要がある。どちらかが誤りなら、表 2.1 の S1・R1 は「記+本(下限のパス以外)」へ直すか、R1 を機械で別に拾う手段を足すかの二者択一になる(後者は足す提案で、足さずに済む前者を先に検討)
2. **template の現況の記述**: 提案 §2.2 は S2 の「抜」の升が実際には「前」になると書く(委任のマージが既定で無効)。罠 A・B・C は verify-traps.md で確認済みで正しいが、**罠 C は「有効にしたあと」の挙動が実機で未確認**(verify-traps C の末尾)。表の「抜」が初日から効くかは、実機の確認(許しが出た試験用リポジトリ)が前提。案A+ の「初日から抜」は、その確認の後でしか書けない
3. **GitHub の挙動の推定**: 提案 §3 案A と §10 は「必須の承認数 0 +コードオーナーの承認必須」を実機で未確認と書いており、正しい扱い。team.json は現状 `required_approving_review_count:1`・`require_code_owner_review:false`(確かめた)。**1〜2 名の体制(コードオーナーが自分だけ)で、作成者が自分の PR を承認できない扱いと衝突する可能性**を、提案は検討していない。実機で確かめる項目へ足す
4. 提案 §1 診断3 の「規範どうしは矛盾しない」は、文の上では正しいが、HAB 66 の「人間が全ての変更を確認する」と G-6 が同じ語「確認」を使う読みの危険(争点8)を、診断では軽く扱っている。誤りではないが、重みの付け方が実害に比べて軽い
5. 提案 §5.2 の語を含むファイル数は grep の値で、検証はしていない(私も未確認)。範囲の判断(1.5)には影響しない
