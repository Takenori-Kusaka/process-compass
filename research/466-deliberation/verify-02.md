## 2. 新しい所見

### 高

**N1. 窓を長くすると、いまも「緩める向き」として記録され、記名者が絞られる。ADR-0273 の「非対称は外す」と実装が食い違う(表示と実態の食い違い・決定の取り違え)**
- 所在: template `scripts/init/generate-profile.mjs` 2566-2570。コメントは「長くするのは緩める向き…短くするのは強める向き」のまま。`push(…, -wb, -wa, M)` は、長くすると `loosenItems` に入る(1773-1781)。`loosenItems` は `deciderRowProblems`(2982〜)で、記名者を席の責任者か D-0 表1 の決定者に限る。強める向きの行には、この限りが無い。`test-loosening-decider.mjs` は「長くする変更は緩める向きとして変化点に残る」を期待したまま。`autonomy.mjs` 482 の利用者向けの文も「観測の窓を長くする(種別 settings。緩める向きの決定者の記名…)」のまま
- 見た事実: ADR-0273 の決定1 は「『長くするのは緩める向き』の非対称は外し、長くする・短くするのどちらも、決定した者と理由を記録して受ける」と書く。置き換えの表と ADR-0129 の状態の節も同じ。`kinds/settings.md` からも「長くするのは緩める向き」を消した。ところが実装は、長くする記録を緩める向きとして扱い、記名者を絞る。`fix-01.md` §3 は「向きは記録の分類で、拒否には使わない」と書くが、`deciderRowProblems` を読む限り、分類は記名者の拒否に使われている。あわせて、未定義の窓の前の値を `?? WINDOW_MONTHS`(2)で読むので、二つの症状がある。初めて 2 か月を定める記録は変化点の差分の行を作らない。初めて 4 か月を定めると「2か月 → 4か月」と、実在しない前の値を表示する
- 照らした決定: ruling §13 H2(ADR-0129 決定2 の「長くするのは緩める向き」を置き換える)、P4 §6・3 版 §4.7-10(非対称を外す)
- 直し方の案: 観測の窓の変化点の行を、向きを付けない形(`push` の b と a を同じ値にする。例: 手戻り率の基準値の method の行)へ改め、未定義の前の値を「定めていない」と出す。試験の期待・482 の文・コメントも揃える

**N2. 本文の第5章の表に「下限2」が残る(表示と実態の食い違い)**
- 所在: `src/content/docs/phase5-implementation/template-repository.md` 656(第2区分の差し戻し率の行)「組織が定める値で既定は無い・下限2」

- 直し方の案: 「下限は月で数える構造の1か月」へ改める(編集の指摘として扱える)

### 中

**N3. 定めていない値の一覧が評価の日を渡さず、委任の判定の「未定義」と食い違う**
- 所在: `detection-values.mjs` の `undefinedValues`(66-68 行)は、`observationWindowDefined(config)`・`minSampleOf(config)`・`loadLimitOf(config)` を、評価の日を渡さずに呼ぶ。`review-queue.mjs` 156・376 の `loadLimitOf(config)`、`autonomy.mjs` 639 の `priorWindowExists` の `minSampleOf(config)` も同じ
- 見た事実: fixture(asOf 2026-10-20)で、窓を初めて 2026-10-02 に記録した。`autonomyState` の状態は「未定義」で、検知は働いていない。一方、`undefinedValues` の一覧(/pit・保証の開示・集約の 3 か所に出る)には、観測の窓が出ない。種別ごとの文は「定めていない…次の評価の日(2026-11-01)から 2か月」と正しく出るので、開示は一部で残る。2099 年の日付で記録した `loadLimit` は、いま効く(`loadLimitOf` が 3 を返す)。構成の検査は、未来の日付を拒まない
- 直し方の案: `undefinedValues(config, day)` に評価の日(`/pit` では当月 1 日、`review-queue` では当日)を渡す。`priorWindowExists` には `minSampleOf(config, m)` を渡す

**N4. 記録の足し手の照合が、本文の適用範囲より広く当たる**
- 所在: GC 1442(「取り込んだ後に作る G-6 の判定記録(適用: 差し戻しの是正と、PR を経ない R2 の確認の記録…)」)。template `aggregate-evidence.mjs` 2177-2196・2247-2255
- 見た事実: `recordNotCounted` は、委任の形態を除くすべての G-6 の判定記録に、足し手の照合(`recordAdderMatches`)を当てる。記録が取り込みの後に足されたかは見ない。たとえば PR の中で開発者が書いて取り込んだ記録も、作成者が判定者と一致しなければ数えない。ずれの向きは数えない側(厳しい側)で、緩めてはいない。ただし、本文に書いていない条件を採用者へ課している。読んだだけで、実行では確かめていない
- 直し方の案: 本文の対象を「G-6 の判定記録のファイル(承認レビュー・委任の記録を除く)」へ広げるか、実装を取り込みより後に足された記録に限る。どちらにするかは議長が決める

**N5. 出荷判定の記録のコミットを読めないとき、前後を照らさずに数える**
- 所在: `aggregate-evidence.mjs` 2181(`if (!c7) continue;`)・2182(`if (!changeRev) continue;`)
- 見た事実: 本文と IMPL-1068 は「前後を履歴から読めない記録は数えない」と書く。実装は、合格した G-7 の記録のコミットを引けないと、その G-7 を飛ばす。その結果、記録は数える側に倒れる。祖先の関係が読めない場合(`covers` が null)は、数えない側に倒れる。読んだだけで、浅い取得の場合に `recordCommitOf` が null を返すかは確かめていない
- 直し方の案: `c7` が null のときは、数えない側(`recordAfterShipment`、読めない旨の理由)へ倒す。作業ツリーにだけある G-7(未コミット)は、別の扱いとして明記する
