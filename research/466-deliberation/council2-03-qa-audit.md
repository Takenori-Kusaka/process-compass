## 1. 審議すること 1〜6 への見解

### 1.1 案A は所有者の決定と懸念に答えているか: 条件つき賛成

- 答えている所: S1 の template が全 PR に承認を要する(generate-profile.mjs 1103。ブランチ保護はパスで分けられない)。これが「人が全部を見る」体験の実体である、という P2 の診断4 は、コードで確かめられた。S1 の非コアの待ちが無くなる。ADR-0065・ADR-0112 が決めた規範へ実装を揃えるだけで、新しい義務は無い
- 答えていない所: 所有者の懸念「人の読める量に作る量を合わせる」に対して、S2 の R1・R2 と未登録の R3 は何も減らない。P2 §4 はこれを隠さず書いているので誠実だが、所有者へ返すときは「S0・S1 は減る、S2 は減らない、減らすには R2 の上限の改め(重の審議)が要る」を先頭に置くこと。ここを濁すと、所有者の決定を実現したと言えない
- 条件(監査の側から、案A を通す前提):
  1. **偽りの宣言の誘因は増える**。P2 の案A の記述「現行と同じ」は誤りである(§5-2)。現行 template は S1 も S2 も全 PR に承認を要したので、S2 を S1 と偽っても得るものが無かった。案A 後は、S2 の組織が S1 と宣言し続けると全 PR の承認が要らなくなる。歯止めは manual(IMPL-0108、TG 616。I2 §4)のまま。**増えた分を「偽りの宣言の誘因が増える」と保証の開示に書く**。機械の検査は足さない(ADR-0065 の却下表で、成立を機械で確かめる手段が無いと決着済み)
  2. **フェイルクローズを維持する**。コア機能のパスが未宣言なら全変更に承認を要する側へ倒す(P2 の案A に既にある)。さらに、品質「高」の S1 はコア機能に承認 2 名を要する(`rules-quality.yaml` 14-18。I2 1.3)。ブランチ保護はパスで承認数を分けられないので、品質「高」のとき CODEOWNERS 方式が 2 名を保てるかを、試験用リポジトリで確かめるまで、品質「高」以上は全変更・現行の承認数のままにする
  3. **出荷の集約を同時に直す**。ADR-0112 の影響の欄: 集約は core-only を読まず、S1 の非コアで独立の確認が無い変更を「欠落」に数える。template の承認だけを揃えて集約を直さないと、S1 の全変更が毎回「欠落」と出て、赤が常態化する。これは所有者の言う「読まれない証跡」そのものになる。IMPL-0469 の降ろしが集約に届いているかを #435 で確かめ、揃えて直す
  4. 案A は S1 の template を緩める実効を持つ。ステージ別の緩和の実測は無い(EV-0101・EV-0230。I2 §7 の #15)。**根拠水準マークの対象に含める**。P2 の「足すもの: なし」は、マークを数えていない

### 1.2 「作るのを止める」(§6): 条件つき賛成

- 「判定依頼の積み増しだけを止め、手は止めない」に狭める案(P2 §6)は、所有者の理由に答えている。「取り込みの停止は R1・R2・コア機能で床として残す」は監査の側から必須である。事後へ移す経路が R3 の登録種別にしか無い(HAB 601)ので、R1・R2 を確認者が空くまで取り込まないのは、止める定めではなく、事後の確認で取り返せないことへの措置である
- 条件: 待ち行列の外に積まれた変更が、上限が空いた時点で一度に押し寄せる害(P2 争点5)は、手引きで受ける。**押し寄せたときに「判定の時間が足りず通した」を作らない**ことを、GC 2622「帯域を理由に判定を省略しない」の再掲で残す。新しい様式は足さない。滞留は既存の review-queue の通知(IMPL-0682)で見える

### 1.3 既定値を置かない扱い(§7): 条件つき賛成。V2・V3 は対象外に賛成

- **V2・V3(引き下げ側の事象の件数)は、採用者が決める値にしてはならない**。「Sev1・Sev2 が 2 件までは下げない」と書けると、安全に関わる引き下げを採用者が遅らせられる。事故後に最初に問われる値である。P2 の (b)(V2・V3 を外し、規則として書き直す)に賛成。V4(差し戻し率 0% の継続の月数)は形骸化の検知の閾値で、採用者が決めてよい
- (iv)「未設定は当月の全件を事後に確かめる」(V7・V9): 採用者に有利な誘因を逆にする点は妥当である。ただし**監査の側から見ると、全件の事後確認が実際に行われたかを、機械が確かめられる形にしないと、最も重い手続が最も形骸化する**。次の 1 点だけは決定可能な条件なので、機械の検査にできる。「期間内に委任で先へ進めた変更の件数 = その期間の G-6 の判定の記録(事後)の件数」(値の一致)。確認の質は manual のまま、manual と書いて開示する。新しい様式は要らない(既存の G-6 判定記録と、HAB 628 の期間の開示を使う)
- 採用者が緩い値を置いた場合(V7 を 1、V9 を 1 など): 標準は既定値を持たないので、「緩すぎる」と指摘する基準が無い。代わりに、**採用者が置いた値を、期間の開示(HAB 628)へそのまま載せる**。標準が範囲を決めず、事故の後に「この値で運用していた」と説明できる状態にする。値を載せる欄は既存の開示の行で足りる
- 「未設定」は期間で消さず、決めるまで表示し続ける(P2 §7 の ADR-0028 整合に賛成)。未設定を緑にしない(判定不能は緑ではない)
- 委任を使わない採用者に値を聞かない(P2 の (i) への反論)は妥当。聞くのは O-4 の対話の中だけ

### 1.4 ADR の置き換えの記録の置き場(§8): 選択肢 4 は、所有者の確認なしには採れない

- 選択肢 4 の暫定の例外(index.md ルール 3 への 1 文)は、ADR の運用ルールの改めである。所有者は「ADR の範囲は別の Issue で審議する」と述べた。この束がルールを黙って先に改めるのは、所有者の決定と逆向きになりうる。**ask に載せて、所有者が許すか決める**
- 監査上の要点は 1 つだけ: ADR-0158 を開いた人が、置き換えを見て、行き先を辿れること。選択肢 1(ステータスの節の書き換えは、ルール 4 が許す範囲)と選択肢 2 の組み合わせで、これは満たせる。語彙(ルール 3)との食い違いは、ステータスに「ADR 外の裁定による一部置き換え」と日付つきで書いて開示する。ルールは改めない
- 所在の実在(研究の記録のファイルが存在するか)は、決定可能な条件なので機械で確かめられる。`check-adr-links.mjs` の既存の検査へ 1 行足せば足りる(P2 §8 は会議体に委ねた)。監査の側は足すことに賛成。ただし research/ はサイトに公開されないので、**公開される本文の側にも置き換えの要旨を 1 文置く**(GitHub の URL だけでは足りない)

## 3. 最大の危険と、起きたときに誰が何を失うか

- **危険: S2 に達した組織が S1 のまま宣言し続け、かつコア機能のパスを一部しか宣言しない**。案A 後の template は、宣言の外のパスの変更を、独立の確認なしに取り込む。宣言は 2 つとも自己申告で、機械の歯止めが無い(I2 §4。IMPL-0108・IMPL-0745 は manual)
- 事故が起きた後の説明: 「S1 と宣言した。コア機能は X と宣言した。本人が見た」までは言える。「なぜ S1 のままか」は、SG-1 の判定記録の不在でしか説明できない。出荷の証跡の件数は残るが、S1 では常に 0 でない件数が出るので、読まれない証跡になる
- 失うもの: **価値責任者**(S1 から S2 へ移す責任を IMPL-0108 で負う)が、移行の判断の不在を問われる。**採用組織の品質保証**は、「標準に従って運用していた」と説明するとき、標準側の歯止めが manual だったことを自分で開示する羽目になる。**利用者・顧客**は、独立の目を経ない変更の被害を受ける。標準は、manual と書いて開示した範囲でしか守られない(ADR-0026)
- 緩和(新しい様式なし): 条件 1 の開示。S1 の G-7 の判定者が、独立の確認を経ていない変更の件数を、出荷のたびに読む(既存)。S1 → S2 の SG-1 の判定記録に、コア機能のパスの宣言の見直しを含めることは、**既に TG 553 が「コア指定のやり直し」を G-1 の条件に置いている**ので、足さずに済む

## 4. 採らない案と理由

- **案B(ステージで委任の入り口を変える)**: S0・S1 に効く升が無い(P2 診断6)。効く所は品質「高」の非コアで、ADR-0112 決定2 と衝突する。監査の側は、事後へ移す経路が増えるほど、事後の確認の実施を説明する負担が増えるので、増やさない
- **案C(自律レベルの既定をステージで置く)**: 初期化の回答だけでレベルが上がる。ADR-0030 の「判定と記録を経ずに統制を緩める経路」に当たる。偽りの宣言の誘因を増やす。採らない
- **案D(本文だけ直す)**: 表と実際の挙動の食い違いが開示のまま残る。所有者の体験の原因(template)が直らない
- **案E(S1 の非コアに事後の抜き取りを足す)**: 人の作業を増やす向きで、そぎ落としと逆。既存の件数の読みで足りる(§2)
- **(i)(立ち上げで全員に値を決めさせる)**: 質問が増える。委任を使う採用者にだけ O-4 の対話で聞く
- **(iii)(template が例の値を置く)**: 例が既定値として働く。「置かない」と書いて実装が持つ食い違いになる(P2 §7 と同意見)
- **V2・V3 を採用者の値にする(a)**: 安全に当たる。採用者が引き下げを遅らせられる

## 5. 起草の案の事実の誤り・欠け

1. **P2 §2.1 の凡例**「CL1 以上と品質『高』以上は、全ステージで S2 の列と同じ」は誤り。品質「高」・CL0 の S1 は、G-6 が core-only のまま(I2 1.3 の導出の実測)。S2 と同じなのは CL1 以上と、品質「高」の S0。I2 1.4(3)にも同じ食い違いがある(品質「高」以上の S1 を全変更とする一方、実測は core-only)。P2 の表を直す前に、エンジンで再度導出して確かめること
2. **P2 §3 案A「ステージの偽りの宣言: 現行と同じ」**は誤り。template の S1 を緩めると、S2 を S1 と偽る得が生じる(§1.1 条件 1)。「偽りで得られるものを増やさない」は成り立たない
3. **P2 §3 案A「足すもの: なし」**は、根拠水準マーク(ADR-0026。ステージ別の緩和の実測が無い。I2 §7 の #15)と、出荷の集約の直し(ADR-0112 の影響の欄が #435 へ送ったもの)を数えていない
4. P2 §3 案A「17 件のどれとも矛盾しない」は、#15(実測が無い)と #17(#435 の食い違い)を「矛盾しない」と数えている。これらは矛盾ではなく、先に確かめる前提である。#17 は案A の前提として扱う
5. P2 §1 診断4「必須の承認数が 1 以上」は、コードでは `Math.max(1, reviewerCount)`(generate-profile.mjs 1103)。承認数は人数に連動する。品質「高」の 2 名との関係(§1.1 条件 2)を、P2 §10 の未確認に加える
6. P2 §8 の「ルール 3 は語彙を定める」とルール 4 の「ステータスの節だけ書き換えてよい」の組み合わせで選択肢 1 が成り立つかを、P2 は「ルール 3・4 の改めが要る」と書いた。ステータスの節の書き換え自体はルール 4 が許す。改めが要るのは語彙(ルール 3)の側だけで、選択肢 1 +「ADR 外の裁定による」の注記で、ルールを改めずに開示できる(§1.4)
