## 1. 診断(10 行)

1. **規範は既にステージに連動している**。G-6 は S0 で省略、S1 でコア機能だけ、S2 で全変更です(TG 543)。CL1 以上と品質「高」以上は、どのステージでも緩めません

3. **ただし、2 つの仕組みが同じことを別々に定めて食い違っている、という診断は半分だけ正しい**。L1 の「確認」は、エージェントの実行の監視です(HAB 98)。G-6 は、作成者と別の人による独立の確認です。対象が違うので、規範どうしは矛盾しません。食い違って見えるのは、5.4.2 の語が G-6 と同じ語(確認)を使い、しかも監視者が誰かを書かないからです
4. **実際に全変更を人が読ませているのは、準拠テンプレートである**。S1 は G-6 の状態が「適用(core-only)」なので、ブランチ保護の必須の承認数が 1 以上になります(generate-profile.mjs 1103)。必須の承認数はパスで分けられません(IMPL-0471 の開示)。そのため、**S1 でもコア機能以外を含む全 PR に、人の承認が要ります**。規範より厳しい側です。S0 は 0 件です
5. S2 で人が読む量を減らす経路は、委任(5.5.4)だけです。ところが template ではマージが既定で無効で、罠 A・B が委任を止めます(verify-traps.md)。O-2・O-3・O-4・O-6 の決定で、この経路は開きます
6. **委任が効く範囲は、構造の上で S2 にほぼ限られる**。S0 には事後へ移す G-6 がありません。S1 の非コアには G-6 が掛かりません。S1 のコアは、委任の条件5 が除きます。残るのは、S2・CL0・R3・非コアと、品質「高」の S0 の非コア(R3)だけです

## 4. 起草者の推奨

**案A を推します**。理由は 3 つです。

1. 所有者の「事業フェーズに連動するべき」は、規範の上では既に満たされています。欠けていたのは、(a) それを読める 1 枚の表と、(b) template がその表どおりに動くことです。案A はこの 2 つだけを直します
2. 案B と案C は、新しい経路か定義を足します。しかも人の読む量には効きません
3. 案A は新しい義務を足しません(§8)

**案A でも残る負担を、隠さずに書きます**。S2 では、R1・R2 と、登録していない R3 を、変更ごとに人が事前に読みます。これは減りません。減らす経路は、委任(R3)と、担保水準 L2 による読む深さの配分(GC 1531・1539)だけです。R2 を委任へ上げることは EV-0040 の差し替え条件が禁じています。所有者が S2 の R2 の負担まで減らしたいなら、それは本束の範囲を超える重の審議(R2 の上限の改め)になります。

## 6. 「作るのを止める」の扱い

- 制御2(GC 2610「新たな判定依頼を作らず、実装計画へ差し戻す」「生成を止めます」)は、G-6 が掛かる升(表 2.1 の「前」)でだけ働きます。S0 には掛かりません
- 所有者の理由(アサインしたリソースを空いたまま待たせることは不可能)は、**人と AI の手を止めること**に当たります。一方、**取り込みを止めること**(確認の無い変更を入れない)は、GC 2622「帯域を理由に判定を省略しない」によるもので、緩められません。2 つを分けます
- 案(条文ではなく骨子):
  1. 止めるのは「判定依頼を積み増すこと」だけとする。手は止めない
  2. 上限に達した間、作成側は G-6 を要しない作業へ回る。表 2.1 の「本」「記+本」の升の変更(S1 の非コアなど)、仕様、テスト、負債の返却、そして自分が任命基準を満たすなら他の人の変更の確認
  3. 積まれた判定待ちは、リスクの順(R1、CL1 以上、コア機能を先)に並べる。手引きにとどめる(ruling-draft 論点3 の裁定4 と同じ)
  4. 帯域の不足が続くなら、GC 2632 の手段の順(分割の総量を減らす → レビューパッケージ → 人数を増やす)と、S2 なら委任の登録(5.5.4)を見直す
- **止めることを残す範囲**: 取り込みの停止は全ステージ・全区分で残す(床)。とくに R1・R2 とコア機能は、事後へ移す経路が無い(5.5.4 は R3 だけ)ので、確認者が空くまで取り込まない。理由は、事後の確認で取り返せない変更だからである
- 足すもの: 制御2 の文の書き換え(生成 → 判定依頼の積み増し)と、2 の 1 文。新しい義務ではなく、止める対象を狭める向き

| V9 抜き取り 5件 | **(iv)** | 当月の全件を事後に確かめる | 無し(数は手続側。mode.md が受ける) |

- **(i) を採らない理由**: /process-init の質問が増える(所有者の方針と逆)。ただし V7・V9・V4 は委任を有効にする採用者にしか意味が無いので、O-4 の決定(/process-init が委任の登録の案と有効化の手順を対話で出す)の対話の中で聞く。委任を使わない採用者には聞かない
- **(iii) を採らない理由**: template の例の値が効くなら、1.7.7 の「既定値」と同じ働きをする。標準は「値を置かない」と書き、実行層が既定値を持つ食い違いになる(DI §5 の注意)
- **(iv) の根拠**: ADR-0158 決定2 の論(止めない構成では基準値を書かないことが最も得になる)は、(iv) では成り立たない。値を書かないと、全件を事後に確かめる負担が残るためである。ゲーミングの誘因が逆向きになる。O-2 の「止めない」とも合う
- **ADR-0028 との整合**: 「未設定」は、決めるまで表示し続ける。期間で消さない
- **引き下げ側の値(V2・V3・V4)を対象に含めるか**(所有者の決定文から読めない):
  - (a) 9 個すべてを対象にする。V3 を採用者が決めると「2 件までは下げない」が書ける。安全に当たるので重の審議へ上げる要がある
  - (b) **V2・V3 を外す**。「AI 起因の重大事象が起きたら下げる / 起きていない」は統計の閾値ではなく規則である(HAB が「統計の閾値ではない」と明記。DI V2)。根拠水準の E0 のマーク(EV-0154)は、値の根拠ではなく規則の根拠として書き直す。V4 は対象に含める
  - (c) V2・V3・V4 を外す(引き下げ側はすべて現行の既定値のまま)
  - 起草者の推奨は (b)。V4 は窓の長さで、template が既に「長くする向きだけ」を構成で受けている。外す理由が弱い

## 8. ADR-0158 の一部の置き換えの記録の置き場

**前提の事実**

- adr/index.md の運用ルール3 は、状態の語彙を「一部置き換え(→ ADR-MMM の決定 n)」と定める。ルール4 は「決定を変えるときは新しい ADR で置き換える」「採用後に書き換えてよいのはステータスの節だけ」と定める。ルール5 は両側が互いを指すことを求める
- `check-adr-links.mjs` は状態の行の「置き換え(→ ADR-N)」の順方向だけを検査する。研究の記録を指す書き方は ADR 番号を含まないので、**検査を通るが、何も確かめられない**(`test-adr-links.mjs` の `successorsIn` の読み)
- research/ は GitHub Pages に公開されない。サイトの読み手は research の記録へリンクで辿れない(GitHub の URL なら辿れる)
- **置き換えの範囲は ADR-0158 だけではない**。O-2 は ADR-0081 決定5(差し戻し率の判定不能で止める)にも当たる。ADR-0158 決定1 はその決定5 を手戻り率へ広げたもの。O-5 は ADR-0081 の「2か月の値は変えない」(DI §6)と ADR-0097(値の型)に、O-3 は ADR-0129 に当たる可能性がある。会議体で全数を確かめる

**選択肢**

| # | 置き場 | ルールとの関係 | 弱み |
| --- | --- | --- | --- |
| 1 | ADR-0158(と ADR-0081)のステータスの節に「一部置き換え(→ Issue #466 の裁定 n。research/466-deliberation/ruling.md)」と書く | ステータスの節の書き換えはルール4 が許す。ただし語彙(ルール3)と「新しい ADR で置き換える」(ルール4)に反する | ルール3・4 の改めが要る。それ自体が ADR の範囲の問題で、所有者は別 Issue で審議するとした |
| 2 | 本文の該当の条項(HAB 5.4.6 の停止の表、TG 343)に、置き換えの注記と裁定の記録への GitHub の URL を置く。ADR は触らない | ルールに触れない | ADR-0158 が「採用」のまま古い決定を書き続ける。ADR を読む人は誤る。ルール5 の相互の指し示しが無い |
| 3 | ADR の索引(adr/index.md)に、置き換えの注記の表を置く | ルールに触れない | 個別の ADR を開いた人には見えない |
| 4 | 1 と 2 を両方行い、index.md のルール3 に「ADR の範囲の審議(別 Issue)の結論までの間、新しい ADR を起こさない改廃は、裁定の記録を後継に指してよい」と 1 文の暫定の例外を足す | ルールを明示して改める | 暫定の例外が残り続ける危険。別 Issue の番号と期限を併記して抑える |

**起草者の推奨は 4**。理由: ADR を開いた人にも本文を読む人にも置き換えが見え(1・2)、ルールとの食い違いを黙って作らない。暫定の例外は、別 Issue で ADR の範囲を決めるまでの橋渡しに限る。ルール5 の相互の指し示しは、裁定の記録の側に ADR-0158 決定 n を書くことで保つ。機械の検査は足さない(研究の記録の実在は lint:refs の範囲外。所在の存在の検査を足すかは会議体で決める)。

## 9. 会議体で争点にすべき点(割れそうな順)

1. **案A で所有者の「連動するべき」に答えたことになるか**。規範は既に連動しているので本文の中身は変えない、という起草者の読みは、所有者の期待(人の負担が目に見えて減る)と合わないかもしれない。S2 の R2 の負担が残ることを、所有者へどう示すか
2. **S1 の非コアを、独立の目なしに取り込む実装を本当に降ろすか**。規範は既にそう決めている(ADR-0112・IMPL-0469)。ただ template が厳しい側で動いてきた。弁護・品質監査の委員は、実装の厳しさを「意図しない保護」として残す論を立てうる
3. **(iv)「未設定は全件を事後に確かめる」は O-5(採用者が決める)を守っているか**。事実上の既定の挙動を標準が持つことにならないか。1.7.7 の 3 つの型のどれに当たるか
4. **引き下げ側の値を O-5 の対象に含めるか**(§7 の (a)〜(c))。(a) なら重
5. **「作るのを止める」を「判定依頼の積み増しを止める」へ狭めることの是非**。待ち行列の外で生成された変更が、上限が空いた時点で一度に押し寄せる害(X-09・X-11 の形だけの承認)を、どう受けるか
6. **ADR の置き換えの記録の置き場**(§8)。ルールの暫定の例外を足すか
7. **記号の変更(担保水準)を本束に入れるか**(§5.2)
8. **L1 の監視者を「作成を指示した人」と書くことが、1〜2名の体制で何を変えるか**。現行でも独立の確認は未達のまま(ADR-0028)だが、読みを固定すると「本人が見たので足りる」と誤読される危険がある
