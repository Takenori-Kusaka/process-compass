## 1. 現行: S2 の R2 の変更 1 件の流れ

R1・R2・R3 を分けるのは**取り消しの手段と影響の範囲**です(RR 3.8.1)。

| 区分 | 取り消し | 影響 |
| --- | --- | --- |
| R1 | 相手方の同意を要する(外部の契約・公開インタフェース・データ形式)。認証・認可・個人データ、事業継続に影響する | 外部に及ぶ |
| R2 | 人手の作業を要するが、自組織の判断だけで戻せる | 限定した実利用者 |
| R3 | 自動化された手段で完結する | 組織内に留まる |

S2・CL0・標準品質・確認者を置ける体制で、非コアの R2 の変更 1 件にかかる人の行為と、それぞれが防ぐ事象を並べます。

## 2. 所有者の 3 つの例外を、観測できる条件に落とす

方針: 新しい区分と定義を足さない。既存の区分・規則・宣言の読みで受ける。

| 例外 | 受ける既存の仕組み | 取り込む前に決定可能か | 受けきれない部分 |
| --- | --- | --- | --- |
| 1 破壊的な変更 | **R1 の定義**(相手方の同意を要する取り消し・公開インタフェース・データ形式・認証認可・個人データ)と、**区分の下限の規則**(パスから R1 を導く。G-5 が低い記載を落とす)。R2 の定義自体が「自組織だけで戻せる」ので、戻せない変更は定義の上で R2 ではない | パスに当たるものは機械で決まる。当たらないものは e(人の区分の確定) | 規則に当たらず、本人も R2 と書いた R1 相当。現行の R3 の自己記載と同じ形の残余で、項目3 と H.11 に開示済みの型 |
| 2 大規模な手戻り | **コア指定・確約範囲(SC-M)のパス**(5.5.4 条件5 と同じ `corePathsOf`)と、**判断記録の要否の規則**のパス(公開インタフェース・永続化のスキーマ・データの移行・構成単位の境界。lifecycle 2.6)。どちらも、誤ると上に積んだ作業ごと作り直しになる所として組織が既に宣言している | 機械(パスの当たり。基底ブランチから読む) | 宣言が古い・漏れている場合。未宣言なら全変更を事前へ倒す既存の歯止め(IMPL-0469)を当てる |
| 3 着手の順番が基礎からでない | 順番は **G-4 で人が決める**(実装計画の「依存」の列、コア指定)。基礎に当たる設計の選択は **G-3 が取り込む前に判定する**(lifecycle 2.6 要求事項4)。基礎を作る変更は例外2 の判断記録の要否の規則に当たる | 計画と規則に当たる範囲は決まる | **計画の依存の順を変更ごとに照らす検査は無い**(template の検査は受入基準とタスクの対応だけ)。順を外れた変更は、事後の確認の基準1(仕様との一致)と G-7 で見つかる。足すなら「トレーラのタスクの依存先が基底ブランチに入っている」の検査で、決定可能だが新しい検査になる(§9 争点5) |

- 帰結: **事前に残す範囲 =「R1(記載か下限)」∪「コア指定・SC-M のパス」∪「判断記録の要否の規則のパス」∪「統制の設定のファイル」**。最後は既存の gate-g5-base(AI維持管理者の承認)がそのまま掛かる
- 所有者の「作り直しは悪くない」は、ADR-0071 決定6(可逆であることを理由に判断記録を省かない)と矛盾しない。この案は判断記録を省かず、**コードを読む時点だけを動かす**

## 4. 起草者の推奨: 案R(案R' は会議体で採否を争う)

### 4.1 理由

1. **利用者に届く前に、全件を人が確かめる性質を保つ**。所有者の 3 点(どこまで確認できているか・それを示すか・基準を満たすか)は、出荷の時点で判定される。案R はその時点に全件の確認を揃える。案P・Q は、届いた後か、確認されない変更を出す
2. **R2 の「人手で戻す」が問題になるのは出荷の後**。出荷の前なら、取り消しは既定ブランチの revert で済む。委任の条件4 が案R には構造の上で当たらない(案P・Q では当たる)
3. **出荷の前の締めは既にある**。G-7 基準5 は、G-6 を適用する体制で独立の確認を経ていない変更を欠落にして差し戻す(GC 1710)。待てないときの正規の経路は 7.3 の例外承認で、回収の期限と回収責任者を伴う(GC 1714、ADR-0036 決定3)。**新しい締めの仕組みを足さない**
4. 委任の判定不能・抜き取り数・最小標本の値(ADR-0158・0081・0129、O-5 の値)に依らない。全件なので、判定不能も「止める」も起きない。所有者の「止めない」と同じ向き
5. 案P は案R に対して、人の読む量が同じ(全件の場合)で、利用者への露出だけが増える。抜き取りにすれば案Q と同じ問題を持つ。**案R に支配される**ので落とす
6. 案Q は、測った値が無いこと(EV-0040 の差し替え条件)と条件4 で効く量が小さいことが、ruling-draft-02 §4.2 のとおり残る。案R を入れれば、案Q で得たい「取り込みを待たない」は案R が与える。案Q で上積みされるのは「出荷の後へ回す」だけで、利用者への露出と引き換えになる。**本束では採らない**
7. 案S は G-6 の単位と挙動要約の単位を変え、ADR-0067・GC 1426 まで及ぶ。案R' が同じ便益の大半を、単位を「機能」に留めて得る

### 4.3 事後の確認の中身

- **誰が**: 独立レビュアの席の人。作成を指示した者でなく、名簿の人で、AI の名義でない(G-6 の 4 条件そのまま)。品質「高」でもコア外は 1 名(r-c-high はコア機能だけ 2 名)
- **いつ**: 取り込んだ後、その変更を含む出荷の判定(G-7)まで。**新しい期限の値を置かない**(O-5)。経過は §4.4 で見える
- **何を**: G-6 の基準1〜6 と挙動要約。対象はマージしたコミットに固定する。あわせて例外に当たらないこと(R1 でない・コアでない)を確かめ直す
- **全件**。抜き取りにしない。理由: 抜き取られない変更は確認されないまま顧客に届き、所有者の (1)(3) を出荷の時点で言えなくなる
- **記録**: 判定記録の様式(テンプレ4)を記録用ブランチへ置く(承認レビューはマージ済みの PR に付けられない見込み。推定)
- **問題が見つかったとき**: 変更要求として記録し、出荷の前に直す変更(同じ経路を通る)か取り消し(revert)で解く。区分を R1 またはコアへ確かめ直した変更は、R1・コアの扱いを出荷の前に満たすまで欠落(既存の「委任の識別を持つ変更が R3 でない」と同じ型)
- **同じ種類を事前へ戻す自動の規則は置かない**。利用者は出荷前の全件の確認で守られ、見つかった不具合の費用は作り直しの費用(所有者が受け入れたもの)であるため。差し戻しの件数は開示に出す(§9 争点3)
- **所有者の「止めない」との関係**: 作る人も取り込みも止めない。止まるのは「確かめていない変更を含む出荷」だけで、これは既存の G-7 基準5 である。急ぐ出荷は 7.3 の例外承認で出せる

| --- | --- | --- |
| 出荷の前に独立の確認を記録した | 独立した人の確認を経た変更に数える。項目3 の確定の形態に「出荷の前に確認」として内訳を出す | 内訳の 1 行が新しい |
| 確認の記録が無い | 記録の欠落。差し戻す(出荷から外す=取り消すか、確認する) | 既存(GC 1710) |
| 確認の記録は無いが 7.3 の例外承認が対応づく | 欠落にしない。項目5 の状態が有効の例外に出る。回収の期限までに独立の確認で回収する | 既存(GC 1710・1714) |
| 確認で R1・コアへ確かめ直した | R1・コアの扱いを満たすまで欠落 | 既存の型の当てはめ |

- **採らない**: 「未確認」と開示するだけで出す(判定者の記名なし)。最も緩い経路だけが使われるため(ADR-0101 の却下の理由と同じ)
- 開示の項目1: 独立性の成立状況に「出荷の前の確認」を足す。項目3: 確定の形態の内訳に足す。どちらも既存の記録からの投影で、人の記入は増えない
- 出荷の間の見え方: 「取り込んだが確かめていない変更」の件数と、最も古いものの経過日数を、/pit と期間の開示に出す(機械。値も閾値も置かない。出荷の直前にまとめて読む形骸化を見えるようにするため)

## 5. 事業ステージの表(ruling-draft-02 §2)への反映

凡例に 1 つ足す: **出** = 取り込んだ後、出荷判定までに、作成を指示した者以外の人が全件を読んで確かめる(G-6 を出荷の前で判定)。

| 場面 | 2 版の「裁定の後」 | 案R の後 |
| --- | --- | --- |
| S0・R1/R2/R3 | 記+本 / 記+本 / 本 | 同じ |
| S1・コア機能・R1/R2 | 前+記 | 同じ(例外2) |
| S1・コア機能・R3 | 前 | 同じ |
| S1・非コア・R1 | 記+例 | 同じ |
| S1・非コア・R2 / R3 | 記+本 / 本 | 同じ(S1 の非コアは元から独立の確認を課さない) |
| S2・R1 | 前+記 | 同じ(例外1) |
| S2・R2・コア機能か判断記録の要否の規則に当たる | 前+記 | 前+記(例外2・3) |
| S2・R2・それ以外 | 前+記 | **記+出(減る。取り込みを待たない)** |
| S2・R3・登録した種類 | 後 | 同じ |
| S2・R3・登録していない・非コア | 前 | **出(減る)** |
| S2・R3・コア機能 | 前 | 同じ |

- CL1 以上・規制業: すべて「前」。変えない。品質「高」: コア機能は 2 名で「前」、非コアの R2 は「記+出」
- 取り込みが配備を起動する構成: 「出」の行は「前」のまま(§4.2 条件4)
- 実装: S1 の (β)(ruling-draft-02 §4.1)を一般化する。gate-g5-base が承認を必須にする PR の集合を、S1 は「コア機能のパス」、S2 は「コア機能 ∪ 判断記録の要否の規則 ∪ R1(記載か下限) ∪ 統制の設定」にする。仕組みは 1 つで、集合だけがステージで変わる。**(β) の実機の確認が済むまで、S2 にも適用しない**(2 版 §4.1 裁定4 と同じ順序)

## 8. 所有者へ示す平易な説明(15 行以内)

いま、中くらいの変更(取り消すのに人手は要るが、自社だけで戻せるもの)は、次の流れです。

1. 作った人(AI に指示した人)が中身を確かめる
2. 機械がテストや検査を通す
3. 別の人が「これは中くらいの変更で、壊すものではない」と区分を確かめる
4. **別の人が中身を読み、動きを自分の言葉で書いて承認するまで、取り込めない**
5. 出荷の前に、機械が「全部の変更が読まれたか」を数える

案では、4 を「取り込んだ後、出荷の前までに、別の人が全部を読む」へ移します。作る人も取り込みも待ちません。読まれていない変更は、今と同じく出荷できません(急ぐときは、別の人が理由と回収の期限を書いて出す今の手続があります)。顧客に届くものは、今と同じく全部が人に読まれています。

次の変更は今と同じく、取り込む前に別の人が読みます。壊すと元に戻すのに相手の同意が要るもの、事業の約束を担う機能、作り直すと上の作業ごとやり直しになる土台(データの形・公開の窓口など、設計の記録が要ると決めた所)、安全や規制に関わる案件の変更です。取り込むとすぐ本番へ出る仕組みの会社は、取り込み=出荷なので、何も変わりません。

## 9. 会議体で争点にすべき点(反対の委員への問い)

1. **区分の確定(e)を取り込む前に残すか**: 残すと、別の人の取り込み前の行為が 1 件ごとに残る。外すと、規則に当たらない R1 が取り込まれ、その上に変更が積まれる。反対の委員へ: e を外したとき、出荷の前の確認で見つけても手戻りが大きくなる具体の変更の型を挙げよ。逆に、e を残すと所有者の意図が実現しない具体の場面を挙げよ
2. **出荷の直前の一括の確認が形だけになる場面**: 出荷が迫った確認者が 40 件を 1 日で読む、など。反対の委員へ: §4.4 の表示と欠陥注入(5.6.2。G-6 の人の層)で足りない具体の場面と、足りない理由を出せ。足すなら、人の記入と新しい値を足さない形で出せ
3. **自動で事前へ戻す規則を置かないこと**: 反対の委員へ: 差し戻しが続いても利用者に届かないのに、戻す規則が要る場面(確認者の読みの質が落ちる、など)を、記録から決定可能な条件で出せ
4. **確かめていない変更の上に後の変更が積まれる場面**: 出荷の間隔が長い組織(四半期など)で、未確認の変更が数百件たまり、1 件の差し戻しが連鎖の取り消しになる。反対の委員へ: §2 の例外2 の規則のパスで受けられない具体の型を挙げよ。受けられないなら、期限の値を置かずに塞ぐ方法を出せ
5. **着手の順番(例外3)を変更ごとに照らす検査を足すか**: 足すと、タスクの記録を持たない変更(不具合の修正など)の扱いが要る
6. **案R' を採るか**: 累積の差分が規模の基準値を超える常態にならないか。中間の版を読まないことで見落とす型(途中で入って最後に残った意図しない変更)があるか。累積にもパス1 を全体に掛ければ足りるか
7. **コア機能も「出」にできないか**(所有者の考え方を最後まで当てると、コアも出荷の前に全件を読めば足りるとも読める)。起草者はコアを残した(例外2、5.5.4 条件5、S1 の表との整合)。賛否を問う
8. **委任(R3 の登録)との食い違い**: 登録した R3 は出荷の後の抜き取り、登録していない R3 は出荷の前の全件になる。登録が「負担を減らす」ではなく「出荷の後へ回す」になる。これで登録の誘因が逆に働かないか

## 10. 確かめられなかったこと

- **出荷の証跡の集約が、マージの後に作った G-6 の判定記録(記録用ブランチの様式)を、出荷の前の確認として数えるか**。マージの時刻を写しの扱いに使う箇所はある(aggregate-evidence.mjs 554-591・820)が、判定記録の日付とマージの時刻の前後で数え方が変わるかは読んでいない。案R の機械の締めはこれに依る
- GitHub でマージ済みの PR に承認のレビューを付けられるか(付けられない、は推定)
- (β) の一般化(S2 で承認を必須にする PR の集合を広げる)の実機の挙動。ruling-draft-02 §4.1 の (β) 自体が未確認
- 取り込みが配備を起動するかを、構成や workflow から機械で決められるか。template の workflow には配備の定義が無く、採用者の側の構成である
- 実装計画の「依存」の列を照らす検査が template に無いことは、grep で `並列可` を読む所が試験とスキルだけであることから推したもので、全数は読んでいない
- 外部に「マージの後・出荷の前に全件を人が読む」型の一次の資料は今回探していない。external.md の X-12(人がマージを押す)・X-23(段階的配布)は近いが同じではない。根拠水準は E0 とする
- ADR の運用: owner-answers-01 の追記は「この束では新しい ADR を起こさない」、ruling-draft-02 の冒頭は「指揮役の伝言で ADR を起こす運用へ戻した」。起草者は後者に従って §6 を書いた。番号 0275 の可否は議長が確かめる
