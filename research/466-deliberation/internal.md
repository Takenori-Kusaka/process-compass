## 2. 委任(HAB 5.5.4、HAB 545-644)

前提(HAB 547-551): 委任で移るのは判定の**時点**で、判定者は人(席の責任者)のまま。AI の確認は検出の層で承認ではない。根拠は「AI が代わりに読んだこと」でなく「壊れたことを検出でき、壊れたら取り消せること」。

適用範囲の見出しは「適用: CL0・R3 の変更」。**「CL0 かつ R3」の根拠 ADR: ADR-0054 決定3・4(R の上限)と ADR-0039(R は変更ごと、CL は案件ごと。「案件の CL からリスク区分依存の条項の適用外を導かない」)、CL1 以上・規制業は協働に落とす(HAB 531。IMPL-0596)**。CL0 の条件(条件1)の独立の根拠(なぜ CL1 以上は委任できないか)は ADR-0054 の本文では確認できなかった(推定: R と別軸の安全の上乗せ。ADR-0014 の安全重要度)。

- 開発者の席が協働のとき: 開発者の席の責任者(人)の承認があるときだけマージ(HAB 602、delegation.mjs 17 行)。**独立レビュアだけの委任で人の確認がゼロの変更は作らない**
- 5.5.4 の末尾: 「条件の緩い別経路を置かない」(HAB 565、TG 337)。ADR-0054 は「同じ結果を導く手続を2つ持つと、条件の緩いほうだけが使われる」を理由にする(GC 2630 も同旨)

## 3. 流入の制御(GC 2544-2643)

- 前提(GC 2219-2223): 「分割の基準は生成側の都合でなく**レビューする側の帯域**」「行数は代理指標。逐行読解する場合だけ代理として機能する。影響範囲の機械的提示・実行可能な保証・リスクに応じた審査深度で、同じ帯域で扱える変更は大きくなる」
- 「流入を絞る」(GC 2601-2614): 制御1 = レビュアあたりの同時保有数の上限(既定3件)。制御2 = 指名先が確保できなければ新たな判定依頼を作らず**実装計画へ差し戻す**。「待ち行列へ積む代わりに、生成を止めます」
  - 値: EV-0011(見直し 2027-08)。**根拠水準 E0(なし)**。差し替え条件は自組織の同時保有数と審査時間・差し戻し率の関係
  - 較正の歯止め(GC 2446-2455): 自動更新しない・引き上げは実績以外の根拠・四半期観測/半期以上で更新
  - ADR: ADR-0200(B18 第1群)・ADR-0173(滞留の観測)。標準側の導入の根拠 ADR は本調査で特定できなかった(要確認)
- 帯域不足への手段の順(GC 2632-2636): (1) 分割の総量を減らす → (2) 判定に要する労力を下げる(レビューパッケージ) → (3) 判定できる人数を増やす。さらに「**帯域を理由に判定を省略しない**」(GC 2628)、「AI による事前審査を合否条件として挿入する手段は採らない」(GC 2638。IMPL-0586)
  - **「作るのを止める」(制御2)は最後の手段として置かれているわけではなく、制御1・2 は手段の順の外にある**。順の(1)「分割の総量を減らす」が「流入を絞る」を指す(GC 2634)。(2) のレビューパッケージはその次。**推定**: Issue の「最後の手段に下げられるか」は、順の入れ替えでなく、(2) の実装(#464)が先に効くか、および (3) の前に置く手当ての追加かの問い
- レビュー SLA(GC 2544-2587): 応答1営業日・判定完了2営業日。催促 → 代理を指名する者への通知 → 人による代理指名。自動の再割り当てを第一にしない
- 実装(template): 
  - review-queue-control.yml(93 行): schedule(毎時17分)・pull_request_target・workflow_dispatch(既定 dry-run)。review-queue.mjs が (a) チームだけ指名の PR へ個人の指名を求める(IMPL-0680)、(b) 応答超過で催促・2倍超過で通知(IMPL-0681)、(c) 未応答の指名が上限(既定3)を超えたレビュアへ PR で知らせる(IMPL-0682)。**指名は外さない。差し戻しの実行は人**。必須チェックにしない。いずれも delivered / machine / test-review-queue.mjs。ただし「実際の GitHub 上で実行して確かめていない」(2026-11-18)。「数えるのは未応答の指名で、応答後も判定待ちの PR は数えない(標準の制御1 より狭い近似)」
  - flow-observation.yml(58 行): 開いた作業単位の着手からの経過が、直近の完了の85パーセンタイルを超えたら Issue へ通知(IMPL-0283、ADR-0173)。滞留の観測であり流入の制御ではない
- 「偏りの監視」(GC 2589-2599)は IMPL-0584 **undelivered**(plan=adopter。ADR-0216。個人の評価への転用を避けるため template は個人単位の集計を出さない)

## 4. L1 の「人が全部の変更を確認」の中身(G-6 と review-guide)

- G-6 判定基準(GC 1395-1402): (1)仕様と実装の一致(受入基準の項目ごとに挙動を確認)(2)レビュアが挙動を自分の言葉で説明できる(挙動要約 1〜2 文)(3)コア機能・判断記録の要否の規則に当たる変更は設計意図の記録(4)レビュアが作成指示者本人でない(5)依存の追加時は G-5 基準8の一覧の印の付いた行を読む(6)変更の検証の記録がある
- 人が行う行為(review-guide.md 36-60 付近): パス1 仕様突合(約10分、差分の全体)・パス2 品質確認(約10分)・パス3 理解(約10分、挙動要約)。1人1日の件数の目安 3〜4 件(review-guide.md 175)。承認は**差分を変える更新のたびに失効**(GC 1426)。承認者の数: 通常 1 名(独立レビュアの席の責任者)、軸C(規制業)・軸E(CL3)・コア機能は 2 名(GC 1444・1455)
- **リスク区分で確認の深さは既に変わっているか**: 
  - 変わる箇所(規範): ①委任の変更(R3・7条件)は G-6 の判定時点が事後の抜き取りへ移る(GC 1604-1621)。②基準値超過の変更は区分の下限を R2 へ上げ、人の確認を掛ける(GC 2339・IMPL-0049)。③R1 の変更は G-5 の変異試験の段が空なら失敗(ADR-0244)・テスト生成の分離を強くする(ADR-0012)・G-6 未達のまま出荷する場合は第7章 7.3 の例外承認を要する(GC 1628-1634。EV-0051 E1)。④R1・R2 の区分は作成指示者以外の自然人が確定・記名(RR 1114)。⑤担保水準 L1・L2(GC 2254-2262): 影響範囲の機械的提示+実行可能な保証があれば行数上限を緩和(L1)、リスクを採点して審査深度を変える運用があれば行数上限を規範から外す(L2)。**根拠水準 EV-0006: E2(単一事例。Meta 系の事例、対象は上位5%の低リスクかつ確信度が高いもの。53.5万件中33.1万件自動着地)**。L2 の稼働は「機械で検証することを課さない」(自己申告+決定者の確認)
  - 変わらない箇所: 委任しない R3(委任の7条件を満たさない、または登録外の R3)は協働で、**R1・R2・R3 のいずれも G-6 の基準1〜6 と1変更1承認が同じ**。G-6 の基準そのものはリスク区分で変わらない。R3 でも委任でなければ、人が差分の全体にパス1 を行い、挙動要約を書く。**R3 の変更で、委任の外にある「軽い確認」の定めは見つからなかった**(推定ではなく、G-6 の全基準と GC 1524-1541 を読んだ結果。template G-6.md のリスク区分の言及は R3 の委任の事後化と R1 の例外承認のみ)
  - 深さの配分(GC 1524-1541): 逐行に読む箇所を限ってよいのは、根拠が機械の導出か実行可能な保証である場合に限る。パス1 は常に差分の全体。「変更のリスクで人の確認を配分する運用は 5.5.4 と L2(担保水準)が受ける」(GC 1539)。**ADR-0101 は「5.5.4 と別に、リスク層別の自動承認を新設」と「論点の外の差分を事後の抜き取りに回す」を採らないと決めた**(5 委員一致、ADR-0101 92-93 行。理由: 受け皿は 5.5.4 と L2 に既にある。条件の緩いほうだけが使われる)

## 7. 一文の要約と L1 の既定の食い違い(Issue の指摘が事実か)

- 一文: 「マシンは人間より速い。それでも、決められた場所では必ず人間が触る」(ADR-0027 37、overview.md 23)。「決められた場所」を定義する条文は見つからなかった(grep)
- **事実**: L1 の定義は「人間が全ての変更を確認する」(HAB 66)。ベースラインは L1(HAB 70)。テンプレートは登録した種別以外すべて L1(autonomy.mjs)。登録した種別は、①7条件+登録の根拠4点が必要、②窓の最小標本30と手戻り率基準値が揃うまで止まる、③マージの実行は既定無効かつ実機未確認。よって**初期状態では、決められた場所=全部の変更**になる。Issue の指摘は条文の読みとして**事実**
- **反証の材料**:
  1. 「全部の変更を人が確認」の内側にも、基準値以内の変更に対する深さの配分(GC 1531、機械の導出)と、R3 の委任の経路が条文としてある
  2. 規模の基準値超過・R1 などは「人の確認を足す」側の統制。基準値以内でも G-5(機械)が全件に掛かるので、**人が確認する前に機械が全件を止める**
  3. 5.4.4 の R1・R2・R3 の上限表は、L1 より上を R2 以上で認める(R2→L2、R3→L3)ため、定義上は「全部」が既定の上限ではない。ただし template は L2 を支えず、R2 も L1 側で動く(ADR-0081 決定6)ので、**テンプレートを採用した組織には当たらない(反証にならない)**
  4. 担保水準 L1・L2(GC 2254)で、人の読み方の深さを変える経路はある。ただし自己申告で、EV-0006 は E2(単一事例)。template の宣言は根拠のパスの実在と見直し日だけ確かめる(GC 2383)
  5. 「テーラリングで最小構成は L2 から始められる」は、テーラリングの規則(rules-criticality.yaml 90)の `autonomy.maxLevel` が**上限**を決める(CL2 で L2 上限)ことで、**開始点ではない**。autonomy.mjs は上限が L3 未満なら登録を拒む。最小構成が L2 から始められる経路は見つからなかった
- **まとめ(事実)**: 「全部」が既定であることは事実。ただし人の確認がボトルネックになるかは、(a) G-6 の1件あたりの所要(パス1〜3で約30分、1人1日3〜4件の目安)と (b) 流入の上限(既定3件)に依る。**Issue の主張のうち、条文で確かめられないのは「実測でボトルネックになっている」こと。採用組織の運用の記録は無い**(EV-0011・EV-0040 の差し替え条件の観測は未収集)
