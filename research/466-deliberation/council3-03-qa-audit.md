- 日付: 2026-11-27。立場: 採用組織の品質保証部門・内部監査。本文と template は変えていない。他の委員の意見書は読んでいない

- 前提: 所有者の考え方(品質は、管理された基準に対する確認の状態・対外の開示・基準の充足で決まる)は、品質保証として筋が通っている。本意見書は、それが**成り立つ条件**を問う

## 1. 見解

### 1. 案R は所有者の決定を信頼性を落とさずに実現しているか — 条件つき賛成

- 案R は、人の確認を「取り込みを止める時点」から「出荷を止める時点」へ移す。品質保証の側から見ると、**統制が予防から発見へ移る**。発見の統制が成り立つ条件は 3 つ。(a)確認が済んでいない量が機械で見える(b)出荷の判定が、それを知らずに通らない(c)確認の記録が後から作れない。案R の起草は (b) を既存の G-7 基準5 で持つ。(a)(c) は不足がある(下記 §2 と §3 の C1・C2)
- **人が読む件数は減らない**。案R は所有者の懸念(人の読める量に作る量を合わせる構成)に、半分だけ答える。答える半分: 作る側・取り込みは待たない。答えない半分: 読む量の上限は残る。上限に達すると、取り込みの待ちではなく**出荷の待ち**として現れる。出荷の待ちは、未確認の件数と最古の経過日数(起草 §4.4 末・§7 の 5)で機械が数えて示せる。これが、所有者の「いまどこまで確認できているか」を数える指標になる。**表示(§7 の 5)を足す案に賛成**。会議体の争点にせず足すのがよい。理由: 出荷の直前の一括の確認の形骸化を見る道具が、これ以外に無い
- 出荷の直前にまとめて読む形骸化: 形の上の承認は、取り込む前でも同じ型で起きる(ADR-0059 が既に扱う)。新しいのは**時間の圧力**だけ。塞ぐのは (i)挙動要約の自筆(既存の G-6)(ii)欠陥注入(5.6.2。形だけの承認の検出の唯一の統制)(iii)確認の記録の時刻と件数を確認者ごとに開示に出す(値は置かない)。(iii) は既存の記録からの投影で、人の記入は増えない
- 案P・Q は、利用者に確認前に届く変更が出る。品質保証としては「確認できている範囲」が出荷の時点で言えない。落とす。案R' は、累積の差分の読み方が G-6 の単位を変えるので、本束では採らない(§5)

### 2. 事後へ移して信頼性が落ちる場面と最小の条件 — 表は §3

要点だけ先に書く。品質保証が最も警戒するのは、**確認の記録そのものの信頼性**である。案R は確認の記録が取り込みの後に作られる。ところが現行の記録の仕組みは、取り込みの時点を基準に作られている。

- `record-copy.yml` は PR のマージを契機に承認レビューの写しを取り、**取り下げ・編集されたものは写しに残らない**(IMPL-0354)。マージの後に提出されたレビューは、突合で「所見」止まりで、G-6 に数えない扱い(IMPL-0435)。案R の確認は記録用ブランチの判定記録(様式4)に置く(proposal-03 §4.3)。**これは写しの突合の外**にある。事故の後に「確認済み」を遡って書けるかを、既存の突合は検出しない(推定。起草 §10 の第1項が未確認と認めている点と同じ根)
- 条件(機械で閉じる): 確認の記録は (1)記録用ブランチへ**追記のみ**で置かれ、その記録のコミット時刻(ホスティングが観測した時刻)が G-7 の判定記録の時刻より前(2)記録のコミットの作成者のアカウントが、対象の変更の作成者・指示した者と別(アカウントの数値の識別子で照らす。既存の G-6 の4条件の再利用)(3)記録が対象とするコミットの識別子が、出荷の範囲のマージのコミットと一致する。**3 つとも決定可能で、新しい欄は要らない**。(3) は起草の「対象はマージしたコミットに固定する」を機械の検査へ落としただけ。足りなければ、突合の対象に「事後の確認の記録」を加える(集約の変更。人の記入なし)

### 3. 所有者の 3 つの例外 — 起草の読みは概ね足りる。ただし 1 点を条件にする

- 例外1・2: R1 の定義・区分の下限・コア指定・SC-M・判断記録の要否の規則のパスで受ける起草の読みは、決定可能で足りる。残余(規則に当たらず本人も R2 と書いた R1 相当)は、現行の R3 の自己記載と同じ型で、開示済み。**e(別の人による区分の確定)を取り込む前に残す**起草に賛成。監査の側から言えば、e は**取り込み時点で作成者以外の人が 1 人関与する**唯一の統制で、職務分離の説明の足場になる(§4 の SOC 2)。e を外す案には反対する
- 例外3(着手の順番)を照らす検査が無い点: 起草は「足さない」。品質保証としては**足さなくてよいが、開示を条件にする**。理由: 順番の誤りは G-4(人)と事後の確認の基準1 で見つかる。検査を足すと、タスクの記録の無い変更(不具合の修正)の扱いが要り、使えない経路が増える。条件: 「依存の順を機械が照らしていない」ことを保証の開示の「機械で確かめていない範囲」に 1 行で出す(既存の開示の投影。人の記入は増えない)

### 4. H.4 条件4 — **維持する。ただし適用の範囲を 1 文で明確にする**

- 分ける。**(ア)変更の種類・領域(決定可能な条件)で人の確認の時点を変える**ことは、AI の推定を使わない。条件4 の対象外。所有者の決定と案R は (ア) である。**(イ)AI のレビューの通過で人の確認を減らす**ことは、条件4 が禁じるもの。Anthropic の Claude Approvals の既定の例(通過で 2 人から 1 人)は (イ) で、同じ文書が「分類器の答えは PR の本文で誘導されうる」と自ら開示している(A-13・A-14)。**公開の実務に (イ) があることは、(イ) を採る理由にならない**。実務の側が危険を自認している
- 範囲を限るのでなく、**維持して (ア) を条件4 の外と明記する**のがよい。条件4 を狭めると、「AI の通過」と「決定可能な条件」の線が曖昧になり、将来の改正が (イ) を滑り込ませる足場になる。置き換えは却下。監査の側から見て、条件4 は「AI の推定を統制の根拠にしない」という一貫した線で、第三者の説明が単純になる
- 注意: 起草は ADR-0054 決定3・5.5.4 の「委任の登録」を残している。AI の推定を使っていないので、条件4 とは矛盾しない

### 5. 値の案

- **未定義のとき検知を働かせずに進める形: 条件つき賛成**。条件は 3 つで、いずれも起草が既に持つ。(1)出荷の証跡の集約の宣言の表に、定義していない値と**働いていない検知の名**を毎回出す(`aggregate-evidence.mjs` の分量の上限の先例)(2)保証の開示に同じ内容を出す(3)人の確認が消えた分の代わりの行為(当月の全件の事後の確認)を残す。**働いていない検知を数字の欠けでなく名前で出す**のが要点で、対外の説明(顧客の監査・SOC 2)で意味が通る
- **案X(規則として残す)に賛成**。案Y は、事故の後に同じ種類の変更が人の確認なしに続く。事故の後の説明(「なぜ止めなかったか」)が立たない。ただし起草 §9 の 1 は「事後の確認の記録が翌月末まで不足なら委任を止める」(RD2 §4.4)を塞ぐ手段にしている。これは所有者の「止めない」と緊張する。**規則であって値でない**と整理して、ask で明示せよ
- 形だけの確認の検知が働いたときの「止める」: **変えない**に賛成。ここを警告に倒すと、形骸化した人が自分を点検する形になる(起草 §4)。止める先は事前の確認で、作業は止まらない
- 1.7.7 の第 4 の型: **足す**ほうが監査の説明は単純。「組織が定める値」の記録が無いとき「基準を満たさない」を、検知の値だけ条項ごとに書き換えると、権限の境界・受容の基準(同じ型を使う条項)の読みを緩める誤読が出る。型を分ければ誤読は起きない。足さずに済ませる案(条項ごとの書き換え)は、条項が増えるほど例外の漏れが出る。ただし第 4 の型は「検知・知らせ・抜き取り」に**限る**と条項で閉じること

### 6. 起草の事実の誤り・食い違い(所在つき)

1. proposal-03 §1 の g は、G-7 基準5 が「G-6 の記録があるか」を数えると書く。実際は ADR-0054(186 行)で「独立した人の確認を経ておらず、**G-6 の判定を事後へ移した変更でもない**」変更を欠落にする。**「事後へ移した変更」は委任(R3)の識別が既にある**。案R の「出荷の前の確認」を同じ識別で数えると、委任と混ざる。起草 §4.4 の内訳の 1 行を**別の項**で数えること(これが「新しい 1 行」の中身。足りている)
2. proposal-03 §4.1 の 2: 「出荷の前なら revert で済む」は、**後の変更が積まれていると成り立たない**(起草自身が §9 の 4 で認める)。理由の 2 つ目としては強すぎる。「後の変更が依存していない範囲で」と限定すること
3. proposal-03 §4.2 条件4(取り込みが本番を起動しない構成): 現代の多くの採用者は main への取り込みで配備が走る。その採用者では案R は**何も変えず**、所有者の意図(待たせない)は実現しない。起草は「何も変えない」と認めるが、**この割合の見積もりが無い**。adopter の申告だけでは、起動する構成なのに「起動しない」と申告する経路が閉じない。機械で検出できる範囲(workflow の push 契機に配備の定義があるか)は警告として出せる。決定可能な範囲だけ機械で数え、残りは adopter で開示せよ
4. proposal-04 §9 の 1 と §2: 「止めない」と言いながら、委任の事後の確認の不足では止める(RD2 §4.4)。**同じ文書の中で「止めない」の範囲が揺れている**。所有者へ平易に示すときに、「値が無いことでは止まらない。確認の不足では止まる」と分けて言うこと
5. proposal-03 §10 が未確認とする、集約が事後の判定記録を「出荷の前の確認」に数えるか。**案R の機械の締めはこの 1 点に依る**。実装の前に実行で確かめることを条件にする(書いていない現状のまま採ると、表示と実態が食い違う「高」が出る恐れがある)

## 4. SOC 2 など第三者の監査での職務分離の説明

- 外部の資料(external.md X-19・X-20): 規格が求めるのは**職務分離と追跡可能な承認の記録**で、全変更の事前の人の承認ではない(読めた範囲)。SOX の実務(二次)は「開発者が自分の変更を本番へ直接出せない」「承認者と配備者を分ける」。自動承認が要件を満たすとする権威ある資料は見つからなかった(未確認)
- 案R の説明: 統制の対象を「本番への反映」に置く。**本番への反映の前に、作成者と別の人の確認(事後の確認の記録)と、出荷判定・本番反映の記名がある**。取り込み時点では作成者と別の人が**区分の確定**で関与する。したがって、「作成者が単独で本番へ出せる経路が無い」ことを示せる。**出荷の前の独立の確認で足りる**。ただし条件がある。(1)取り込みが本番を起動する構成では足りない(C7・C9)。(2)C1 の記録の信頼性が要る。監査人は、確認の記録が後から作られていないかを標本で見る。(3)監査の言い方は「予防でなく発見の統制」になる。発見の統制を認めるかは監査人と採用者の判断で、**本標準は認められると保証できない**。この限界を保証の開示の文に書く(根拠水準 E0)
- 作成者が出荷判定者を兼ねる小さな体制は、G-7 の記名の独立が成り立たない。既存の規定(1〜2名の体制の例外承認・外部の席)に委ねる。案R で新たに悪化する点ではない

## 5. 採らない案と理由

- **案P**: 確認前に利用者へ届く。「確認できている範囲」を出荷の時点で言えない。落とす
- **案Q**(登録した R2 の種類だけ委任): 抜き取られない変更は確認されないまま届く。測った値が無い(EV-0040)。落とす
- **案R'**(累積の差分): 途中で入って最後に残った意図しない変更を、累積では見落とす型がある。G-6 の単位(承認した差分に対して数える。GC 1426)を変える。確認の記録の対応づけが複雑になり、C1 の機械の検査を弱める。落とす。作り直しで捨てた途中の版を読む手間は、品質の側では許容する(読む量が増える弱みは、未確認の件数の表示で見える)
- **案S**(出荷の差分を 1 回で読む): 規模が基準値を超えるのが常態になる(推定)。形だけの確認の最も強い誘因。落とす
- **条件4 の置き換え・範囲の縮小**: §1 の 4 のとおり維持する。AI の通過を根拠に人の確認を減らす経路は、公開の実務にあっても採らない
- **案Y(事故の後は警告のみ)**: 事故の後の説明が立たない。重の審議の対象でもある。落とす
- **例外3 の機械の検査**: 使えない経路を増やす。開示で受ける

## 6. 自分の立場から見た最大の危険

**確認の記録が事故の後に作られても、既存の突合が検出しないこと(C1)**。起きたとき、出荷判定者と品質責任者が「出荷の前に誰が何を確かめたか」を説明できなくなる。顧客の監査・第三者の監査では、予防の統制を外した上に、発見の統制の記録も信頼できない状態になる。本標準の保証の開示は「確認できている範囲」を実態より広く見せ、**表示と実態が食い違う**。この危険は、案R の条件(§1 の 2)を実装の前に機械で閉じ、実行で確かめれば塞がる。塞がないまま案R を採ることには反対する。
