# 議長の裁定(#380 判定記録だけの PR に GitHub のルールセットが課す1件の承認)

入力: 議題 `council-00-agenda.md`、調査 `survey-380-1-internal.md`・`survey-380-2-external.md`、意見 `council-01-drafter.md`(起案)・`council-02-field.md`(現場)・`council-03-qa-audit.md`(品質監査)・`council-04-standards.md`(規格)・`council-05-defender.md`(弁護)。

## 0. 裁定の骨格

Issue #380 は「条項(記名者以外の承認を課さない)が強制層へ降りていない」という問題として起票された。5名の委員はいずれも、問題の立て方そのものを退けた。基底ブランチへ入る記録には働きの違う2種類があり、ADR-0070 決定6 はそれを一括した。

| 区分(本文での呼び方) | 該当する記録 | 誤った帰属が入ったときの害 |
| --- | --- | --- |
| 判定記録 | 様式(G-1・G-7・G-8・SG、対象が PR でない判定)、承認レビューの写し、保証の開示 | 開示に「自己申告」と出る。事後の照合(IMPL-0128)で足りる |
| **効力を持つ記録** | 例外承認の台帳の行、停止の申し立ての解除の記録、層1(項目4 が解除の権限者を定める)、D-0 の決定の記名 | 基底ブランチへ入った時点で、PR の時点の検査の合否と権限者の照合を変える。判定される側が自分の例外・解除を差し込めば、マージは事後の開示では取り消せない |

ADR-0070 の誤りは、前者の性質から導いた「承認を課さない」を後者にも及ぶ文で書いたことと、後者に残る承認を「取り込みの事務」と呼んだことである。前者についての決定の核(写しを機械で取り、記名者以外の判定を課さない)は正しい。

**監査の新しい事実(品質監査 F-1・F-3、現場 §0)**: 残る承認 1 件は、議題が書いたほどの統制ではない。PR の時点の照合は名前だけで、承認は `require_code_owner_review: false` のため誰のものでも数えられる。3名以上の体制では、X が「承認した者: Y」と書いた台帳の PR を開き、無関係の Z が承認すれば、X の例外が成立する。停止の解除も同じ構造である。したがって「残る承認があるから足りている」とは言えず、承認を外す方向も、承認を残す方向も、そのままでは信頼性を満たさない。

## R-1 条項の向き — 裁定: 分割して見直す

- **判定記録**には「記名者以外の者の判定を課さない」を維持する。ホスティングの規則が一律に承認を課す場合、その承認は**転記の確認**であり、判定記録の欄にしない。転記の確認をする者は、複製が置き場の記録と一致することを機械の検査の結果で確かめる
- **効力を持つ記録**は、ADR-0070 決定6 の「課さない」の対象から外す。新しい要求として、「**効力を持つ前に、記名者本人のアカウントによる操作で帰属を裏づける。名前の一致だけを裏づけに数えない**」を課す。記名者本人の操作を機械が確かめられない場合(記名者が記録を足した変更の作成者で、認証情報を AI の担い手と共有している構成を含む)は、記名者と別のアカウントの人の承認を**帰属の確認**として経る。帰属の確認は統制であり、事務ではない。確認者は中身の妥当性を判定しない
- 用語: 裁定の時点では「判定の材料とする記録」と書くとした(語彙を増やさないため)。独立の突合で、第1章 1.4 の「判定の材料」(判定者が読む記録)と意味が衝突すると指摘され、「効力を持つ記録」(起案・規格の案)へ改め、「転記の確認」「帰属の確認」とともに 1.4 へ足した。列挙で閉じ、列挙に無い記録を効力を持つ記録として扱わない
- 誤っているのは ADR-0070 決定6 の範囲と語である。ADR-0078 の原理(判定の材料を、判定される側が同じ変更で用意できない形にする)は正しい。現行はそれを「既定ブランチの先端から読む」で実装していたが、帰属を確かめない代用だった

採らない案:

- 条項をそのまま維持し、IMPL-0124 を undelivered のまま表示し続ける(弁護の初期の立場の一部)。降ろすと統制が壊れる規定を、降ろすべき規定として表示することになる
- すべての記録の取り込みに記名者以外の承認を課す。ADR-0070 が解消した「中身を見ない承認」を判定記録にも戻す
- 残る承認を言い換えるだけで帰属の裏づけを足さない。F-1 の経路が開いたまま残る
- 効力を持つ記録を条項の対象外と書くだけで要求を置かない。「書かれていない」と「課さない」の区別がつかない

## R-2 例外承認と停止の解除の受け皿 — 裁定: 対象の PR 上の記名者本人のレビューを第一の受け皿に加え、基底ブランチの経路にも帰属の照合を課す

委員5名とも a3 を採った。条件を合成する。

**(A) 対象の PR の上の記名者本人のレビュー**(宣言行つき、状態を問わない)。次をすべて満たすものに限り効力を持つ。

1. レビューのアカウントが人の名簿の人のアカウントに対応し、AI・bot の名義でない
2. そのアカウントが、対象の PR の作成者のアカウントと異なる。例外承認では、加えて作成を指示した者でない。停止の解除では、層1 の項目4 の権限者の席の責任者である(現行の照合を引き継ぐ)
3. レビューの対象のコミットが、PR の先頭のコミットと一致する。承認の後の push で失効する
4. 停止の解除は、ラベルを付けた最後の時刻より後に提出されている
5. 例外承認は、宣言行が台帳の行の識別子を指し、PR の先頭(または基底ブランチ)の台帳にその行があり、行の承認した者がレビューの書き手と同じ人である。行の内容は、レビューの対象のコミットに固定されるため、書き手が見た版である(起案の「一字一致」は採らない。対象のコミットへの固定で同じ効果が得られ、二重の転記を書き手に課さない)
6. 取り下げられたレビューは数えない

**(B) 基底ブランチの台帳の行・解除の記録**(後退経路。対象が PR でない場合と、条件2 を満たせない構成で要る)。名前の照合に加え、その行・記録を基底ブランチへ入れた PR の作成者または承認したレビューの書き手のアカウントが、記名者のアカウントであることを、PR の時点の検査がホスティングの記録で確かめる。記名者が作成者の場合は、ルールセットが課す他者の承認が帰属の確認になる。確かめられない(ホスティングの記録を読めない、PR を経ずに入った)記録は数えない。品質監査 F-1 の経路を、この照合で塞ぐ

- 台帳の行は、第7章 7.3 の要求事項4(登録と追跡)の記録として残す。効力の源はレビュー(A)または帰属の照合(B)である
- 1名の体制で作成者と記名者が同じアカウントの場合、(A) は成立しない(条件2)。現行の `exceptionFor` と同じ結論で、緩めていない。(B) で外部の確認者の承認が帰属の確認になる

採らない案:

- a1 台帳と解除を `records` へ移し、検査が `records` を読む。`records` は書き込みの権限を持つ者とジョブのトークンが追記・変更できる(EV-0185、#379 未決)。帰属の確認が無いまま承認の門だけが消える
- a2 署名コミットだけで裏づける。署名の鍵と名簿のアカウントの結び付きを確かめていない。1〜2名の体制で鍵の運用を既定にする根拠が無い
- 現行の承認 1 件に CODEOWNERS と `require_code_owner_review: true` を足して承認者を権限者へ寄せる。`docs/gates/` に複数の席が同居し、作成者本人は承認できない。帰属を確かめる仕組みとして形が合わない
- Issue のコメント・PR 本文を受け皿にする。第4章が退けている
- 台帳の行とレビューの欄の一字一致(起案)。対象のコミットへの固定で足りる

## R-3 出荷の PR — 裁定: 「承認するのは出荷判定者本人」を誤りとして直す

- 出荷の PR は、記録用ブランチの判定記録と写しを機械が複製した運搬であり、判定記録である。その承認は転記の確認で、承認者は複製の一致の検査(verify)の結果を確かめる。G-7 の判定は G-7 の様式にある
- 出荷の PR を開く者は限らない(人であること)。承認するのは、開いた者以外の人である。GitHub では作成者は自分の PR を承認できない
- 出荷判定者が自分で開き、他者が承認する構成では、その承認が転記の確認であることを開示する(保証の開示の項目1 の既存の扱い)
- IMPL-0355 の「確かめる者: 出荷判定者(出荷の PR を承認するときに…)」を改める

採らない案: Actions・App・PAT に出荷の PR を開かせる・承認させる(承認の件数に数えられるか未確認で、機械の承認を人の確認に見せる)。bypass。出荷判定者本人の承認を判定として求める(GitHub では成立しない)。

## R-4 テンプレートの手段 — 裁定

- 既定にしない手段: `required_reviewers` の「一律 0 + パス条件で 1 件を足し戻す」(合成の規則の公式の記述も実機の検証も無く、失敗したときに開く構成で、ユーザー所有のリポジトリでは使えない)、bypass、exempt、Actions・App の承認を件数に数える形、承認の強制を gate-g5 へ移すこと
- 本文はプラットフォームの機能名を使わずに書く。パス単位の承認の規則・免除を持つホスティングでは、免除してよいのは判定記録に限り、効力を持つ記録を免除へ含めてはならない
- 準拠テンプレートの既定ブランチのルールセットに bypass actor を置かないことを、試験で確かめる(品質監査: 契約検査が bypass_actors を見ていない)
- `plan=adopter` は使わない
- IMPL-0124 は、規定を「記名者以外の者の判定を課さない。課される承認は転記の確認」へ改めたうえで delivered にする。**反論されうる点として明記する**: 言い換えで未達を消すように見える。消していないことの根拠は、(1) 記録用ブランチの経路で様式と写しは承認なしで入る、(2) 残る承認(出荷の PR)の確認者が見るものを機械の検査の結果に定めた、(3) 新しく課す要求(帰属の裏づけ)は別の IMPL で表示する、の3つである

## R-5 付随のずれ — 裁定

- H-1(出荷の PR の自己承認): R-3 で直す
- H-4(層1 の改版と直接の push の禁止): 層1・D-0 を効力を持つ記録に数える。直接の push の禁止は維持する。ADR-0057 の却下行(層1 の改版に PR を課す)の理由「記名と二重になる」は、帰属の確認が中身を承認しない点で当たらない。ただし層1・D-0 の帰属の照合を PR の時点で機械が確かめる実装は本件で降ろさない。IMPL を undelivered(plan=scheduled、後継 Issue)で表示する。現場委員の「層1 の統制は別の会議体へ」は、統制の向きをここで決め、降ろし方を後継へ回す形で受ける
- H-5(RECORD_PATHS が層1・D-0 を含み条項より広い): 狭めない。集約の RECORD_PATHS は「Risk・Verification のトレーラを要しないコミット」の判定に使う一覧で、帰属の要求の範囲ではない。その旨をコードの注記に書き、効力を持つ記録の一覧を別に持つ(`MATERIAL_RECORD_PATHS`)
- H-6(EV-0111 の差し替え条件が書き換えだけを数える): EV-0111 の対象を判定記録に狭め、差し替え条件に「記名者以外による追記の件数」を足す。効力を持つ記録の帰属の要求は、新しい EV(E0)で開示する
- H-7(AI の担い手が本人の認証情報で動く): 議題の外。帰属の裏づけがホスティングの記録に依る方式すべての前提の崩れである。本件では、(i) AI が宣言行のレビューを出さないことを準拠テンプレートの常駐の規則と権限設定(`gh pr review` を ask)で降ろし、(ii) アカウントの分離を構成の入力にするかは後継の Issue へ回す
- 名簿の照合が数値の識別子でなくログイン名で行われている(準拠テンプレートの `findPersonByAccount`)。第4章「アカウントと人の対応表」の要求との差は本件の前からあり、本件の検査も同じ関数を使う。後継の Issue へ記録する

## 実装の中で決めたこと(裁定の補い)

- **帰属の確認者を置けない体制**: (B) の照合で、記名者が作成者で記名者以外の人の承認が無い場合、名簿に記名者以外の人がいなければ、自己申告として受け付ける(PR を経ないコミットも、author が記名者なら同じ)。受け付けた記録は保証の開示の項目1 の自己申告の記録に出す。数えない形にすると、1 名の体制で停止の解除が永久に成立しなくなるため(起案の R-1 の「帰属の確認者を置けない体制では…開示へ出す」を採った)。名簿に外部の確認者がいれば、その承認を要する
- **照合に使うコミット**: 台帳の行・解除の記録を「最初に足したコミット」ではなく「最後に変えたコミット」で照合する。行の中身を後から書き換える変更の帰属を見るため
- **レビューの再評価**: gate-g5 を `pull_request_review` で起動しない。`github.base_ref` が空になり、基底との比較を前提とするジョブが飛ばされたまま集約のジョブが通過しうるため。レビューを出した後は最後の実行を再実行する(レビューの一覧は実行のたびに API から読む)
- **PR の先頭**: gate-g5 は `PR_HEAD_SHA`(`github.event.pull_request.head.sha`)を渡す。checkout がマージのコミットを取り出すため、HEAD はレビューの対象のコミットと一致しない
- **権限設定**: `gh pr review` の拒否は、従来 guard.enabled のときだけ効く `standardBash` にあった。ステージと guard.enabled に依らず効く `standardReview` へ移した
- **番号**: IMPL-0413(pr-checks)、IMPL-0414(evidence-aggregation)、IMPL-0415(層1・D-0・SG。#428)、IMPL-0416(rulesets)、IMPL-0417(agent-settings)。後継の Issue は #428(層1・D-0・SG の帰属)と #429(AI の担い手の認証情報の共有、名簿の数値の識別子)
- **附属書H**: 内部監査の観点28 を足した。観点26・27 の「準拠テンプレートの検査は降りていない」は #426 で降りた後の記述へ改めた(本件の突合で見つけたずれ)
