# 会議体 #380 弁護の委員の意見

- 立場: 現行の条項(第4章「判定記録を基底ブランチへ入れる操作」、ADR-0070 決定6「記名者以外の承認を課さない」)と、現行のテンプレートの構成(既定ブランチの承認 1 件が残り、CODEOWNERS で承認者を記名者へ寄せる誘導)を弁護する。変える必要が本当にあるか、変えると何が壊れるかを問う。弁護できない欠陥は欠陥と認める
- 入力: `council-00-agenda.md`、`survey-380-1-internal.md`、`survey-380-2-external.md`。加えて現物を読んだ箇所: `gate-criteria.md:99-133`、ADR-0070 決定3〜7 と却下表、ADR-0057 の却下行(`:509`)、`ci-gates.md:153,169`、`template/.github/rulesets/README.md:71-93`、`template/.claude/skills/gate/reference/recording.md:94-103`、`template/.github/CODEOWNERS:44-59`、`template/scripts/gate/check-pr.mjs`(`exceptionFor`・`stopFindings`)、`aggregate-evidence.mjs:1266-1278`(RECORD_PATHS)、`ship-evidence.yml:20-45,240-262`

## 0. 弁護の総論(先に結論)

弁護できるもの、できないものを先に分ける。

| 対象 | 弁護の可否 | 一言 |
| --- | --- | --- |
| 条項の向き(記録の取り込みに記名者以外の承認を課さない)を、**様式・写し・出荷の PR**に当てること | 弁護する | 判定はすでに別の場所で記名者が行った。取り込みの承認者は中身を判定する材料を持たない。ADR-0070 の背景(`:53` 中身を見ない承認)は今も正しい |
| 条項が**例外承認の台帳・停止の解除**を同じ「判定記録だけ」に括り、残る承認を一律に「取り込みの事務」と呼ぶこと | **弁護できない(欠陥)** | この 2 つは G-5 が既定ブランチから読む**判定の材料**である。残る承認は、判定される側が自分の材料を単独で入れる経路を塞ぐ統制として働いている。ADR-0070 決定6 は「現行どおり先に」と書いただけで、この役割を論じていない |
| テンプレートが残す承認 1 件(`team.json` 以上)そのもの | 弁護する(台帳・解除・層1 について) | 外せば統制が消える。外さずに置いていることは、結果として正しかった |
| テンプレートの「残る承認の承認者は記名者本人」(README `:91`)と CODEOWNERS の誘導 | **弁護できない(欠陥)** | `team.json` は `require_code_owner_review: false`、CODEOWNERS の行は雛形のまま無効。誘導層すら既定で効いていない。3 名以上では、判定される側が書いた行を、記名者でない第三者が承認して通せる |
| 出荷の PR の手順「出荷判定者が開き、出荷判定者が承認する」(H-1) | **弁護できない(欠陥)** | GitHub では作成者は自分の PR を承認できない(外部調査 1.2【確認】)。成立しない手順を「記名者本人の操作」として書いている |

したがって弁護の結論は「条項の向きは維持する。ただし条項の**適用範囲の切り方**と**残る承認の呼び方**が誤っている。誤っているのは ADR-0070 の側であり、ADR-0078 と `ci-gates.md:153` の側ではない」である。

## R-1 条項の向き

### 結論

- 「記名者以外の承認を課さない」という向きは**維持する**。逆向き(記録だけの PR に記名者以外の承認を課す)へ改めることに反対する
- ただし条項の対象を 2 つに分けて書き直す必要がある。これは欠陥の是正であり、向きの変更ではない
  - (a) **判定の記録**: 判定がすでに成立した後の記録(様式 G-1・G-7・G-8・SG・PR でない判定、承認レビューの写し、出荷の PR の複製)。現行どおり、記名者以外の承認を課さず、他者の承認は取り込みの事務
  - (b) **判定の材料として既定ブランチから読まれる記録**: 例外承認の台帳の行、停止の申し立ての解除の記録、および同じく既定ブランチから読まれる層1(停止の解除の権限者を定める項目4)。これには「記名者以外の承認を課さない」ではなく、「**判定される側の操作だけで既定ブランチへ入らない(効力を持たない)**」を要求事項として置く
- (b) に記名者以外の承認を**課す**ことは求めない。満たし方は、記名者本人のアカウントに結び付いた操作を機械が確かめること、または判定される側以外の者の承認のどちらかとする(R-2)

### 理由

1. ADR-0070 決定6 は、自らを ADR-0057(層1 の改版)・第5章 CI/CD・ADR-0067(2 名の目的は変更の取り込みの統制)の一般化と位置づけた。ADR-0067 の論理に照らすと、台帳の行と停止の解除は「変更の取り込みではない」とは言えない。行が入った瞬間に、別の PR の合否が変わるからである。`ci-gates.md:153` は理由を「台帳へ自分の例外を足す、という形で検査を通せないようにする」「判定の材料を、判定される側が同じ変更で用意できない形にする」と書く。ADR-0070 の一般化は、この 2 つの記録について一般化の前提を満たしていなかった
2. 残る承認が統制として働いている事実は、内部調査 §5・H-2 のとおりで、`check-pr.mjs` の `exceptionFor` を読んでも裏づけられる。PR の時点の照合は、承認した者の**名前**が名簿の人へ対応づくこと、AI の名義でないこと、対象の PR の作成者でないことまでで、記名者本人の操作を確かめない。名前は判定される側が書ける。2 名体制では、GitHub の作成者の自己承認の禁止により、判定される側が開いた台帳の PR は相手(= 記名者)の承認でしか入らない。統制は、条項ではなく GitHub の仕様が偶然に担っている
3. 一方で (a) の向きを守る理由は今も有効である。様式・写しの承認者は判定の材料を持たない(ADR-0070 背景)。出荷の PR の中身は機械の複製で、verify ジョブが `records` ブランチとの一致を検査する(README `:80`)。ここに記名者以外の承認を判定として課しても、確かめられる事柄が増えない。ADR-0070 決定6 の第3項が書くとおり、G-7 で判定される側は出荷判定者ではない
4. 逆向き(記名者以外の承認を一律に課す)へ改めると壊れるもの
   - 1 名と外部確認者の体制で、外部確認者が中身を判定できない様式・写しへの承認を、制度として再び求めることになる(ADR-0070 `:53` の構造の復活)
   - ADR-0057 の却下行(`:509`。層1 の改版に別の承認者を課すと記名の意味と二重になる)、ADR-0058(PR 2 本・承認 2 回の却下)と正面から衝突する
   - 1 名・checks-only の体制では、承認を課す相手がいない。G-6 未達の体制に、満たせない要求を足すだけになる
5. (b) を「判定される側の操作だけで入らない」と書く理由は、2 名体制で記名者以外の承認者が判定される側そのものになりうるからである(内部調査 §5「2名・相互」)。「記名者以外の承認」を課しても、承認者が判定される側なら統制にならない。守るべきものは「誰が承認したか」ではなく「判定される側が単独で材料を用意できないこと」であり、これは `ci-gates.md:153` の原理そのものである

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 条項を現行の文のまま維持し、残る承認を「事務」と呼び続ける | (b) について事実と合わない。残る承認が統制として働いているのに「事務」と書くと、採用者は外してよいと読む。パス単位の免除を持つプラットフォーム(Gitea の Unprotected file patterns、Azure DevOps のパスフィルタ)へ移った採用者が、条項に忠実に (b) の承認を外し、統制を失う |
| 条項を逆向きにし、記録だけの PR に記名者以外の承認を課す | 理由4。(a) で ADR-0070 が解いた問題を再発させる |
| (b) を条項の対象外と書くだけで、要求事項を置かない | 「書かれていない」と「課さないと決めた」の区別がつかない。何が統制なのかを採用者が知る手段がなくなる。統制を GitHub の偶然の仕様に預けたままになる |
| (b) に「記名者以外の承認」を課す | 理由5。2 名体制で承認者が判定される側になりうる。1 名体制で満たせない |

### 反論されうる点

- 「(b) を分けるのは、条項を ADR-0070 の後から複雑にするだけで、テンプレートは既に承認 1 件を残しているのだから現行で足りる」— 足りない。承認者を判定される側以外に限る仕組みが無い。3 名以上の体制では、判定される側 B が「承認した者: A」と書いた台帳の PR を、C が承認すれば入る。A は何もしていない。現行のテンプレートは 2 名体制でしかこの穴を塞いでいない
- 「層1 を (b) に入れるのは ADR-0057 の決定に反する」— ADR-0057 が避けたのは「別の承認者を課して記名と二重にすること」であり、層1 の改版を判定される側が単独で行えることを認めた決定ではない。`check-pr.mjs` は停止の解除の権限者を既定ブランチの層1 から読む(`stopFindings`)。層1 の項目4 を書き換えられれば、解除の権限者を自分にできる。層1 は (b) の性質を持つ。ただし (b) の要求は「判定される側の操作だけで入らない」であり、記名者以外の承認を課すものではないため、ADR-0057 の却下理由とは衝突しない
- 「(a)(b) の区別は、プラットフォームの都合を標準へ持ち込んでいる」— 持ち込んでいない。区別の根拠は「既定ブランチから読まれて別の変更の合否を左右するか」という記録の機能であり、どのプラットフォームでも成り立つ
- 根拠水準: (b) の統制が実際に自己の例外の差し込みを止めた事例は無い。経路が開くことは仕様と現物のコードからの推論である(E0)。新しい EV で開示すべきである

## R-2 例外承認の台帳と停止の解除の受け皿

### 結論

- **受け皿は変えない**。例外承認・停止の解除の人が書く欄は、現行どおり様式・台帳に書く(第4章 `:99`、ADR-0070 決定3)
- **基底ブランチへ先に入れる規定も維持する**(第4章 `:109`、ADR-0078、`check-pr.mjs` の既定ブランチの先端からの読み取り)
- 変えるのは**帰属の裏づけと、その照合の時点**である。G-5 が既定ブランチの台帳の行・解除の記録を読むときに、名前の照合に加えて、**記名者本人のアカウントに結び付いた操作**を確かめる。候補は次の 2 つで、どちらかがあればよい
  1. その行・記録を既定ブランチへ入れた PR に、記名者の席の責任者のアカウントによる承認レビューがある
  2. 対象の PR の上に、記名者の席の責任者のアカウントによるレビュー(状態を問わない)があり、本文の宣言行が台帳の行の識別子または解除の記録のファイルを指す
- これにより、現行で GitHub の作成者の自己承認の禁止が偶然に担っている統制を、本標準の検査が自ら担う形になる。3 名以上の体制、管理者の直接の push、採用者が bypass を足した構成でも、判定される側の単独の操作では効力を持たない
- 内部調査の a3(受け皿を対象の PR 上のレビューへ**広げる**)は、上の候補 2 の形に**縮めて**採る。レビューは「受け皿」ではなく「裏づけ」とする

### 理由

1. 裏づけを変える方が、受け皿を変えるより信頼性が高い。第4章 `:107` は既に「記名者本人の操作(署名コミット、または記名者の承認レビュー)を、記名の帰属の裏づけとする」と書いている。欠けているのは、その裏づけを (b) について**効力を持つ前に**確かめることだけである。現行では IMPL-0128 の照合が G-7 の集約で事後に開示するだけで、しかも台帳の行は照合の対象外である(内部調査 §4)
2. 受け皿を様式・台帳に残す理由は、ADR-0070 の却下表にある。「全ゲートの記録をレビューへ寄せる」案は「G-8・SG・例外承認は決断の記録(人確定)を要し、レビューに置き場が無い」として退けられた。例外承認の台帳は第7章 7.3 の技術負債台帳であり、期限・返却の追跡を台帳の行が担う。行をレビューの本文へ移すと、台帳の行と承認の文が 2 か所に分かれ、どちらが正かを決める規定が要る。a3 をそのまま採ると、ADR-0070 決定3 の受け皿の限定と、その却下理由を同時に覆すことになる
3. 基底へ先に入れる規定を残す理由
   - 停止の解除は、保留された変更から独立した行為として先に成立していなければならない(第7章 7.11)。解除の記録を保留された PR の中へ置くと、PR の作成者(判定される側)が記録の入った PR の中身を握る
   - 台帳は、対象の PR がマージされずに閉じられても、承認した例外の記録として残る必要がある(内部監査と G-7 の集約が読む)
   - スタック型の PR で下の層の材料を読ませない理由(`ci-gates.md:153`、EV-0139)は、裏づけを変えても消えない
4. 候補 1・2 の両方を認める理由は、体制ごとに使える方が違うためである。2 名体制で AI が別のアカウントを持つなら候補 1(現行の `recording.md:98-100` の手順が成り立つ)。記名者のアカウントで AI が動く体制(認証情報の共有)では、記名者は自分の開いた台帳の PR を承認できないが、対象の PR の上に COMMENT のレビューは出せる(`G-4.md:22`、`ci-gates.md:652` の実機確認)ので候補 2 が使える
5. 候補 2 のアカウントは記名者の席の責任者のアカウントに限る。名前ではなく、アカウントの数値の識別子と名簿(`people[].accounts`)で照合する。判定される側が用意できない材料は、名前ではなくアカウントの操作である

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| a1 台帳・解除を記録用ブランチ `records` へ移し、G-5 が `records` を読む | `records` は書き込み権限者とジョブのトークンが追記できる(EV-0185、IMPL-0353 未達)。判定される側が `records` へ自分の例外を直接 push できる。ADR-0078 の原理と衝突する。#379 の結論が出る前に、統制の材料を書き換え可能な場所へ移すことになる |
| a2 記名者の署名コミットを PR の時点の唯一の裏づけにする | 署名の鍵と名簿のアカウントの結び付きを API で確かめられるか未確認(内部調査 §9-3)。1〜2 名の体制で署名の普及を前提にできない。候補の 1 つとして足すことは妨げないが、唯一の手段にはしない |
| a3 受け皿そのものを対象の PR 上のレビューへ広げる | 理由2。ADR-0070 決定3 と却下表の理由を覆す。台帳(7.3)の行と承認の文が分かれる。レビューの本文はマージの前に編集でき、編集の後に検査が再実行される保証を別に作る必要がある |
| 台帳の行を対象の PR の中で足し、記名者のレビューで裏づける(記録だけの PR を無くす) | 理由3。停止の解除の独立性と、閉じられた PR の例外の記録の残存を失う。`check-pr.mjs` の「同じ PR で足した記録は数えない」を廃する理由が、1 名体制の待ち時間の解消以外に見当たらない。待ち時間は信頼性の論点ではあるが、統制の材料を判定される側の PR へ入れる代償に見合わない |
| 現状維持(残る承認 1 件に統制を預ける) | 理由1。3 名以上の体制と、bypass を足した構成で穴が開く。統制が GitHub の仕様の偶然に依存し、他のプラットフォームでは持ち越せない |

### 反論されうる点

- 「1 名と外部確認者の体制では、停止の解除の取り込みが外部確認者の承認待ちのままになる(第7章 7.11 の解除の時点が他者の都合に依る)」— 認める。弁護の結論はこの待ちを解かない。ただし弁護の立場から付け加えると、(b) について外部確認者の承認は (a) と違って中身を見られる承認である。解除の理由と、申し立てた者の見解を退けたかは短く、外部確認者が判断できる。1 名体制で唯一の独立した目が解除を見ることは、統制として意味がある。待ちを解くために解除を判定される側の単独の操作へ戻すのは、信頼性の向きに反する
- 「候補 2 は、認証情報を共有する体制では AI が記名者のアカウントでレビューを出せるので、裏づけにならない」— そのとおり。その場合は現行どおり自己申告として開示する(第4章 `:107`)。候補 2 は認証情報の共有を解かないが、悪くもしない。共有の体制の弱さは H-7 の論点であり、本件で隠さず開示に出す
- 「候補 1 の『その行を入れた PR』を機械が特定できるか」— コミットから PR を引く API はあるが、スカッシュ・リベースで特定が崩れる場合の扱いは実装で決める必要がある。特定できない行は裏づけ無しとして扱い、緩める向きの代替を持たない(`ci-gates.md:153` の型)
- 「PR の時点の検査が強くなると、いま通っている台帳の行が通らなくなる」— 通らなくなる行は、記名者本人の操作が確かめられない行である。それは本来通すべきでない。移行の期間の扱い(既存の行の扱い)は起案側で決める
- 根拠水準: 候補 2 で GitHub がレビューのアカウントの数値の識別子を返し、`pull_request_review` の契機で gate-g5 を再実行できることは、仕様からの推論で実機未確認。降ろす前に実機で確かめる

## R-3 出荷の PR の承認(H-1)

### 結論

- H-1 は**欠陥として認める**。README `:79,81`、`ship-evidence.yml:29,245,257`、`template/README.md:142` の「出荷判定者が開き、出荷判定者が承認する」は GitHub で成立しない
- 出荷の PR は (a) に属する。ADR-0070 の「記名者以外の承認を課さない」「他者の承認は取り込みの事務」は、出荷の PR については正しく、維持する
- 手順を次のとおり改める
  - PR を開くのは、出荷判定者**以外**の人(ship-evidence を起動した人、AI維持管理者など)または AI の担い手の専用のアカウントとする。出荷判定者は承認する。承認者 = 記名者が、G-7 の記名の強い裏づけになる
  - 出荷判定者が自分で開くしかない体制(1 名と外部確認者で、AI が本人のアカウントで動く場合)では、他者の承認は取り込みの事務と開示し、G-7 の様式の裏づけは `records` ブランチへの push(弱い裏づけ)または署名コミットに落ちることを保証の開示へ出す
  - 1 名・checks-only の体制では承認が無いため、手順の問題は生じない
- 文書は「出荷判定者本人が承認する」を、成立する条件(PR の作成者が出荷判定者でないとき)つきで書く。成立しない場合に何が起きるかも書く

### 理由

1. 出荷の PR の中身は機械の複製で、verify ジョブが `records` ブランチとの一致を検査する。判定される側(出荷の範囲の変更の作成者と指示者)が材料を用意できる経路は、複製の一致の検査が塞いでいる(ADR-0070 決定6 第3項)。ここで承認者を誰にしても、確かめられる事柄は増えない。したがって承認者の問題は帰属の裏づけの強さの問題であって、統制の問題ではない
2. `ship/<日付>` のブランチは `GITHUB_TOKEN`(github-actions[bot])が push するので、`require_last_push_approval` の下でも出荷判定者の承認は数えられる。障害は「作成者は自分の PR を承認できない」の一点で、開く人を変えれば解ける
3. 機械に PR を開かせる案は、現行のテンプレートが退けた理由(README `:83`。Actions に PR の作成を許す設定は機械の承認も許す。`GITHUB_TOKEN` の PR は検査を起動しない。PAT は人の名義の操作を機械が行う)がそのまま残る。AI の担い手の専用のアカウントは人の名義でないため、PAT を退けた理由には当たらない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 「Allow GitHub Actions to create and approve pull requests」を有効にして機械に開かせる | 機械の承認で required approving review を満たせる状態を作る(GitHub 自身が 2022 年に抜け道として塞いだ。外部調査 4.3) |
| 出荷判定者の PAT で機械が開く | 人の名義の操作を機械が行う(README `:83`) |
| 出荷の PR に出荷判定者以外の承認を判定として課す | 理由1。(a) について ADR-0070 の解いた問題を再発させる |
| 出荷の PR を bypass で入れる | ADR-0070 決定7。強制層の縮小 |
| 文言を直さず、IMPL-0128 の照合で欠落にならないから足りるとする | 欠落にならないのは、G-7 の様式が `records` への push で裏づけられるからで、手順が書く「出荷判定者本人の承認」とは別の裏づけである。成立しない手順を規範として書き続けることは、採用者を誤らせる |

### 反論されうる点

- 「開く人を出荷判定者以外にすると、1〜2 名の体制では開く人がいない」— 2 名体制では相手が開ける。1 名体制で AI の専用のアカウントを持たない場合は、開示に落ちることを書く。成立しない体制を成立すると書くより信頼できる
- 「AI の専用のアカウントを前提にすると、`/process-init` の構成に無い前提を足すことになる」(H-7)— 足すのは前提ではなく選択肢である。構成で AI の担い手のアカウントを別にするかを問う設問の要否は R-5 または別 Issue で扱う

## R-4 テンプレートの手段と採用者への委任

### 結論

- **パス条件の `required_reviewers`(一律 0 + 否定パターンで足し戻す構成)**: テンプレートの既定にしない。採用者の選択として認める場合も、実機で各パスの実効の要件を確かめる手順と、強制層の構成の変更としての記録(ADR-0038)を要する
- **bypass(`always`・`pull_request`・`exempt`)**: 採らない。ADR-0070 決定7 を維持する
- **GitHub App・Actions による承認**: 採らない
- **CODEOWNERS の誘導**: 誘導層として残す。ただし `require_code_owner_review: true` へ切り替えて遮断に格上げする案は採らない。現行の「残る承認の承認者は記名者本人」(README `:91`)は、誘導であって成立を保証しないと書き改める
- **IMPL-0124 の扱い**: (a) について GitHub の強制層へ降りていない事実は変わらない。`state=undelivered` で表示し続ける。(b) は R-1 の新しい要求事項として別の実装マークを起こし、R-2 の検査(G-5 の照合)を降ろし先にする。IMPL-0124 の注記の「承認者を記名者本人に限る手順は /gate と CODEOWNERS で降ろす」は、効いていない誘導を降ろし先のように書いているので改める
- **plan=adopter**: (a) について GitHub の採用者に委ねることは採らない。採用者にも縮小以外の手段が無い(`crosscheck.md:186` の裁定を維持)。パス単位の免除を持つプラットフォーム(Gitea・Azure DevOps・GitLab の Code Owners のセクション)では、採用者が (a) を降ろせることを、プラットフォームごとの満たし方として書く。ただし (b) のパスを免除へ含めてはならないことを、同じ箇所に書く
- **標準はプラットフォームを選ばない**: 条項は (a)(b) の要求として書き、どのプラットフォームでどう満たすかは準拠テンプレートに置く(ADR-0035 の型)

### 理由

1. `required_reviewers` の構成は、すべての PR の承認を否定パターンの正しさに預ける。一律の承認数を 0 にした上でパスで足し戻すため、パターンの誤り(または `.gitignore` 風と fnmatch の表記の揺れ。外部調査 1.3【未確認】)が、既定ブランチの全 PR の承認の欠落として黙って現れる。強制層を縮小しない原則(ADR-0070 決定7、第4章 `:110`)に対し、縮小と等価になりうる構成を既定に置けない。加えて、ユーザー所有のリポジトリでは使えず(外部調査 1.3【確認】)、契約検査(`verify-gate-contract.mjs` の承認数の検査)と env-check の承認数の照合が一律の値を前提にしているため、検査の側も作り直しが要る。動作も未検証である
2. 仮に `required_reviewers` が動いても、免除の範囲を (a) に限らなければ (b) の統制が消える。現行の RECORD_PATHS は (b) を含む(H-5)。手段の採否より先に、範囲の定義が要る
3. bypass はアクター単位でパスを見ない(外部調査 1.4【確認】)。パスの限定をアクターの側で実装すると、その実装が新しい統制点になり、強制層の外へ出る。`exempt` は監査記録を残さない
4. App・Actions の承認は、数えられるかの報告が割れている(外部調査 4.3)。人の確認の記録を機械の承認で満たす形は、本標準の前提(人が触る場所)と逆である
5. CODEOWNERS を遮断へ格上げすると壊れる: `docs/debt-ledger.md` の所有者を価値責任者 A にして `require_code_owner_review: true` にすると、A のアカウントで AI が台帳の PR を開いたとき、A は承認できず、他の所有者もいないのでマージできない。1 パスに 1 席しか置けず、`docs/gates/` には出荷判定者・解除の権限者・SG の判定者の記録が同居する(内部調査 §4)。遮断の役は R-2 の G-5 の照合が担い、CODEOWNERS は承認の依頼先を表示する誘導に留める

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `required_reviewers` の構成を `team.json` の既定にする | 理由1・2 |
| Bot・App を `pull_request` モードの bypass に置き、記録だけの PR を App がマージする | 理由3。ADR-0070 決定7、却下表 |
| Actions・App の承認で承認数を満たす | 理由4 |
| `require_code_owner_review: true` を `team.json` の既定にする | 理由5。記名者のアカウントで AI が動く体制で台帳・解除の PR が詰まる |
| IMPL-0124 を `plan=adopter` にして GitHub の採用者へ委ねる | 採用者に取れる手段は bypass(統制の弱化)か未検証の `required_reviewers` だけ。既定でない構成を採用者に勧める形になる |
| IMPL-0124 を delivered と書き換える(残る承認を事務と再定義して) | (a) について承認 1 件が残る事実は変わらない。降りていない規定を消さない規則(#222)に反する |

### 反論されうる点

- 「`required_reviewers` を採用者の選択として認めるだけでも、(b) を誤って免除する採用者が出る」— そのため (b) を免除に含めてはならないことを、満たし方の記述と同じ行に書く。加えて R-2 の G-5 の照合は、承認の有無に依らず (b) の効力を確かめるので、誤って免除しても (b) の統制は残る。R-2 の検査が先に降りることが、R-4 の委任の前提になる
- 「IMPL-0124 が undelivered のまま、計画の Issue を持たずに残る」— `plan=scheduled` の Issue は、GitHub の機能の変化を見張る見直しの年月として残すのが妥当である。計画が無いことを隠すより、プラットフォームの制約として開示し続ける方が信頼できる。plan の値の選び方は起案側の判断に委ねる

## R-5 付随のずれと記録

### 結論

- **H-4(層1 の改版と直接の push の禁止)**: 本件で直す。ただし「層1 に PR を課さない」へ戻す向きでは直さない。ADR-0057 の「PR を課さない」の趣旨は「記名者以外の承認を課して記名と二重にしない」であり、直接の push の禁止(PR 経由で gate-g5 の検査を通すこと)はこの趣旨に触れない。新しい ADR で ADR-0057 の当該行の読み方を明記し、層1 を R-1 の (b) に置く(停止の解除の権限者を定めるため)。`template/CLAUDE.md` の「記録だけのコミットには要らない」も同じ読み方へ揃える
- **H-5(RECORD_PATHS の範囲)**: 本件で直す。RECORD_PATHS の役割(製品の変更に数えない置き場)と、条項の対象(記名者以外の承認を課さない記録)を別の語・別の一覧にする。集約の識別を変える必要は無いが、(a)(b) の区別を集約のコードの注記と README に書き、RECORD_PATHS を免除の範囲として使ってはならないことを明記する
- **H-6(EV-0111 の差し替え条件)**: 本件で直す。差し替え条件に「記名者以外の者による (b) の記録の追加」と「記名者本人の操作が確かめられないまま効力を持った (b) の記録の件数」を足す。EV-0111 の対象は (a) に縮める。(b) には新しい EV を起こす(E0。統制が止めた事例も、開いた経路が使われた事例も無い)
- **新しい ADR**: 要る。ADR-0070 は採用済みで本文を書き換えないため、決定6 のうち「台帳・解除の残る承認を事務と呼ぶ」部分と、出荷の PR の手順を、新しい ADR で置き換える。置き換えるのは範囲の切り方と呼び方で、向き(記名者以外の承認を課さない)は置き換えない
- **IMPL**: R-4 の結論のとおり。IMPL-0124 は (a) に限って undelivered を続け、注記を改める。(b) の要求事項に新しい IMPL を起こし、降ろし先は G-5(`check-pr.mjs`)。出荷の PR の手順の是正(R-3)は、IMPL-0355 の注記の「確かめる者: 出荷判定者(出荷の PR を承認するときに…)」も同時に直す
- **H-7(AI の担い手のアカウント)**: 本件で直すのは開示の文言まで。構成の設問を足すかは別 Issue とする

### 理由

1. H-4 と H-5 は、R-1 の (a)(b) の区別を入れると同じ根から出ていることが分かる。層1 と D-0 は判定記録ではなく、層1 は判定の材料でもある。RECORD_PATHS が (a)(b) と層1・D-0 を一括していることは、集約の目的(変更の単位に数えない)では誤りではないが、条項の免除の範囲として読まれると (b) の統制を外す。本件で区別を入れる以上、同時に直さないと、区別が一覧の側で崩れる
2. H-6 を直さないと、新しい ADR の判断を測る手段が無い。git の履歴で検出できるのは書き換えであって、(b) の追加ではない。差し替え条件が論点を測らない EV は、見直しの期日が来ても何も判断できない
3. 新しい ADR を起こす理由は、採用済みの ADR-0070 の決定6 の一部が事実と合わないと会議体が判断するためで、決定変更は新しい ADR で行う規則による

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| H-4 を「層1 の改版は直接の push を許す」へ直す(ルールセットに例外を作る) | 既定ブランチの強制層の縮小(ADR-0070 決定7)。層1 は (b) の性質を持ち、判定される側の単独の改版を許せない |
| H-5 で RECORD_PATHS を条項の対象と同じ範囲に狭める | 集約の目的(層1・D-0 の改版を製品の変更に数えない。ADR-0057 S54)を壊す。一覧を分けて名づければ足りる |
| H-4・H-5・H-6 を別 Issue へ送る | R-1 の区別と同じ根の欠陥であり、分けると区別の導入と一覧・EV の不整合が並存する期間ができる |
| ADR-0070 を全面的に置き換える | 向きは正しい。置き換える範囲を決定6 の一部と出荷の PR の手順に限ることで、ADR-0070 のうち維持する判断(決定1〜5・7・8)を読み手が区別できる |

### 反論されうる点

- 「層1 を (b) に置くと、層1 の改版にも記名者本人の操作の確認が要り、ADR-0057 の簡素さが失われる」— 失われるのは手間であって信頼性ではない。層1 の項目4 を判定される側が単独で書き換えられる状態を残す理由にはならない。ただし (b) の要求は「判定される側の操作だけで入らない」であり、層1 の記名者(組織の品質保証の責任者)本人の操作で満たせるため、別の承認者を課すことにはならない
- 「D-0 も席と責任者を定めるので (b) に入るのではないか」— 入る可能性が高い。名簿と席の割り当てを判定される側が書き換えれば、記名者の照合そのものが崩れる。D-0 の改版には既に D-0 表1 の決定者の記名と check-d0 があるが、効力を持つ前の本人の操作の確認は未確認である。起案側で D-0・構成(`process.config.json` の `people[].accounts`)を (b) に含めるかを突合してほしい。弁護の立場からは、含めない理由を見つけられなかった
