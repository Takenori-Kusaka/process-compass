## 先に示す見立て: 本件の核心は「承認の有無」ではなく「効力の発生と帰属の裏づけの順序」

議題は「記名者以外の承認を課すか」の二択で立っている。規格の立場から見ると、この立て方そのものが2種類の記録を混同している。

| 区分 | 該当 | 記録が機械に読まれる時点 | 帰属が偽だったときの害 |
| --- | --- | --- | --- |
| **判定記録**(結果を残す記録) | G-1・G-7・G-8・SG の様式、承認レビューの写し | 出荷判定(G-7)の集約 | 「誰が判定したか」が自己申告になる。保証の開示で読み手へ届く |
| **効力を持つ記録**(他の変更の合否を左右する記録) | 例外承認の台帳の行、停止の解除の記録、層1(品質保証の方針)の権限者の定め、D-0・構成の名簿 | **PR の時点**(`check-pr.mjs` が既定ブランチの先端から読む。`ci-gates.md:153`、`check-pr.mjs:7,499,981`) | 判定される側が、自分の変更を通す材料を自分で用意できる。開示は事後であり、取り込みは既に起きている |

ADR-0070 決定6 は、前者について正しい。記録の取り込みに別の承認者を課しても、承認者は中身を判定せず(ADR-0070 `:53`)、記録の真正性は上がらない。真正性を支えるのは記名者本人の操作だけである。

しかし決定6 は、後者を「現行どおり基底ブランチへ先に入れる」とだけ書き、残る承認がそこで何をしているかを論じなかった(内部調査 H-2)。後者にとって問題は「誰が承認したか」ではなく、**記名者本人の操作で帰属が裏づけられる前に、記録が効力を持ってしまうこと**である。PR の時点の照合は名前だけ(`ci-gates.md:169`)で、台帳の行は IMPL-0128 の照合の対象外である。

この見立てから、R-1〜R-5 を次のように答える。

## R-1 条項の向き

### 結論

- 「記名者以外の承認を課さない」は、**判定記録について維持する**
- **効力を持つ記録については、この条項の対象から外し、別の要求を新設する**: 「効力を持つ記録は、記名者本人の操作(記名者に対応づけたアカウントの操作の記録)を機械が確かめるまで、効力を持たない。判定される側の操作は、この裏づけに数えない」
- 現行の「残る承認 1 件」は、効力を持つ記録の統制として**頼れない**。これを「事務」と呼び続けることは誤りであり、同時に「唯一の人の門」として温存することも誤りである
- どちらが誤りか: **ADR-0070 決定6 の適用範囲が誤り**である(効力を持つ記録まで判定記録と同じ類に入れた)。決定6 の原理(他者の承認は記録の真正性を上げない)そのものは誤りでない

### 理由

1. **残る承認は、体制によって統制として働いたり働かなかったりする**。2名・相互の体制では、判定される側 B が「承認した者: A」と書いた台帳の行を出すと、B 以外の書き込み権限者 = A の承認が要り、結果として A が見る。3名以上では、`team.json` は `require_code_owner_review: false` で CODEOWNERS の行も雛形のまま(内部調査 §4)なので、**判定される側でも権限者でもない C の承認 1 件で、B の書いた偽の行が基底ブランチへ入る**。1名+外部確認者では、外部確認者は材料を持たない。体制によって効いたり効かなかったりする統制を、標準は統制として数えられない
2. **「事務」という呼び名が、唯一の門を自ら弱めている**。標準と README(`rulesets/README.md:92`)は、記名者以外の承認者に「その承認は事務であり、判定ではない。承認者は中身を判定していない」と告げている。2名体制で A に届く台帳の PR について、A は「中身を見なくてよい」と読める。統制として頼られている操作を、標準が「見なくてよい操作」と説明している。これは記録の真正性の観点で最も悪い組み合わせである
3. **職務の分離の一般原則と整合させるには、行為者で分ける必要がある**。両立しない職務は「例外を求める者(判定される側)」と「例外を承認する者(7.3 の権限者)」、「停止された者」と「解除する者(7.11 の項目4 の権限者)」である。分離を担保すべきなのは、承認の効力を発生させる操作を誰がしたかであり、ファイルの取り込みに何人が承認したかではない。7.3 自身が「承認した者」と「記録した者」を別の欄に分け、台帳へ書き込んだ者と権限者が別でありうると明記している(`exception-escalation.md:57`)。したがって、台帳へ書いた事実は承認の帰属を何も示さず、**帰属は書き込みとは別の、権限者本人の操作でしか示せない**。これは本標準の既存の構造から直接導かれる
4. **記録の真正性の一般原則(帰属が記録の内容ではなくシステムで示されること)とも整合する**。ADR-0070 の調査(`gate-record-01`)が整理した「帰属・同時性・対象とのリンク・改変不能」のうち、帰属を名前の欄で示す形は ADR-0070 自身が退けた(「氏名・日時・対象を手で書く欄は、誰が判定したかを裏づけない」)。台帳の行の「承認した者」の欄も同じ性質の欄であり、PR の時点で名前だけを照合する現行(`ci-gates.md:169`)は ADR-0070 の判断と食い違っている
5. **効力を持つ記録に「自己申告として開示」の後退経路を認めてはならない**。判定記録の自己申告は、G-7 の読み手へ届き、そこで評価される。効力を持つ記録の自己申告は、開示が届く前に変更を取り込ませる。7.3 は「5つの事項のいずれかが空欄の記録は例外承認の成立を示さない」と定める。帰属の裏づけの無い承認は、承認した者の欄が実質的に空であるのと同じ扱いにするのが整合的である

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| R1-a 条項を現行のまま維持し、IMPL-0124 を undelivered で表示し続ける | 3名以上で統制が効かない事実(理由1)と、「事務」の呼び名が唯一の門を弱める事実(理由2)を放置する。表示を続けても、自己の例外の差し込みは止まらない |
| R1-b 条項を逆転し、記録だけの PR に記名者以外の承認を常に課す | ADR-0070 の背景(承認者が中身を見ずに承認するしかない構造)を再生する。他者の承認は帰属を裏づけない。3名以上では権限者でない者の承認で足りるので、自己の例外の差し込みも止まらない。ADR-0057・0058・0067 との矛盾も復活する |
| R1-c 残る承認を「材料の取り込みの統制」と呼び替え、IMPL-0124 を台帳・解除について「意図した状態」とする(内部調査 §7(c) 論点2) | 呼び名を変えても、承認者を権限者に限る仕組みが無い(CODEOWNERS は誘導層で既定では無効)。統制として数える条件(誰が承認するか)を満たさないものを統制と呼ぶことになる |
| R1-d 承認者 ≠ 記名者の効力を持つ記録を欠落に数える | ADR-0070 の却下行(`:149`)と同じ理由で採らない。問題は承認者の一致ではなく、記名者本人の操作の有無である。記名者本人の操作があれば、取り込みの承認者が誰でもよい |

### 反論されうる点

- **「ADR-0070 の却下行(記録 PR の承認者 ≠ 記名者を欠落に数える)と同じことをしている」**。応答: 違う。却下行は欄の揃った判定記録を欠落と扱うことを退けた。本案は、効力を持つ記録について「裏づけの無い承認は効力を持たない」とするもので、記録を欠落と数えるのではなく、効力の発生条件を定める。ただし、新しい ADR で ADR-0070 決定6 の範囲を明示的に狭めないと、読み手は区別できない
- **「1名体制では、記名者本人が判定される側でもあり、行為者の分離は成り立たない」**。応答: 成り立たない。7.11 は既に「申し立てた者と解除の権限者が同一人物である体制では、その旨を記録する」と定める。1名体制では同一人物の旨の記録を代替統制とし、保証の開示へ出す(SRC-0538 の台帳の要約にある「分離が実際的でない場合の代替統制」、SRC-0419 の小規模組織の代償措置の型)。統制を外すのではなく、成り立たないことを開示する
- **「効力を持つ記録の範囲が広がり、層1 や D-0 まで巻き込む」**。応答: 巻き込むべきである(R-5 H-4・H-5)。層1 の項目4 は解除の権限者を定め、`check-pr.mjs:499` が PR の時点で読む。判定される側が層1 の権限者の欄を書き換えられるなら、解除の統制は全部無意味になる
- 根拠水準: 本結論を支える事例は無い。3名以上での差し込みの経路は構成(ルールセットと CODEOWNERS の既定値)からの推論で、実際に起きた事例も実機の再現も無い。新しい EV で E0 として開示すべきである

## R-2 例外承認の台帳と停止の解除の受け皿

### 結論

- **a3 を採る**。例外承認と停止の解除の受け皿に、**対象の PR 上の、権限者本人のアカウントのレビュー(宣言行つき、状態を問わない)**を加える。PR の時点の検査(G-5)は、ホスティングの記録からこのレビューを読み、効力の条件とする
- 受け皿の条件は、標準では**プラットフォームの機能名を使わず**に書く:
  1. 対象の変更に結び付いたホスティングのレビューの記録である
  2. 書き手のアカウントの数値の識別子が、名簿で権限者の席に対応づけられている(第4章「アカウントと人の対応表」と同じ条件)
  3. 宣言行を案件の構成で事前に定める(例: `例外承認: 基準 N / 理由 … / 期限 YYYY-MM-DD / 回収責任者 …`、`停止の解除: 理由 …`)
  4. 停止の解除は、申し立ての時点より後に出されたレビューに限る(現行の「ラベルを付けた日より前の解除は数えない」を受け継ぐ)
  5. 例外承認は、レビューが対象とした版より後の変更で失効する(第4章 G-6 の「承認の後の変更による失効」と同じ考え方)
  6. AI の名義のアカウント、判定される側(対象の変更の作成者・作成を指示した者)のアカウントは数えない。1名体制の同一人物は、その旨の記録をもって受け付け、開示する
- 7.3 の要求事項4(技術負債台帳への登録)と 5(継続的な報告)は残す。台帳の行は、レビューの写しから**機械が起こす**(人が書く欄は一字も変えない)。台帳の行はもはや効力の源ではなく、追跡の記録になる。したがって「台帳は基底ブランチへ先に入れる」の要求は外せる
- **既存の経路(基底ブランチの台帳・解除の記録)は廃止せず、同じ裏づけの条件を課す**。対象が PR でない例外(成果物が対象)や、ホスティングにレビューが無い場合の後退経路として要るためである。この経路では、記録を入れた変更に権限者本人の操作(権限者のアカウントの承認レビュー、または名簿の鍵で検証できる署名コミット)が無ければ、G-5 は行を数えない
- a1(records へ移し既定ブランチの読み方を変える)は**採らない**

### 理由

1. a3 は、効力の源を「判定される側が書けない場所」に置く唯一の案である。対象の PR 上のレビューの書き手のアカウントはホスティングが記録し、判定される側は他人のアカウントでレビューを出せない(認証情報を共有しない限り)。台帳のファイルは誰でも書ける
2. a3 は1名体制でも成立する。作成者本人もコメントの状態のレビューは出せる(`ci-gates.md:652` の実機確認、`G-4.md:22`)。承認の件数を一つも増やさない
3. a3 は ADR-0078 の原理「判定の材料を、判定される側が同じ変更で用意できない形にする」(`ci-gates.md:153`)を保つ。現行はこの原理を「既定ブランチの先端から読む」で実装しているが、それは材料の帰属を確かめない代用であった。a3 では、材料はそもそも判定される側が作れない
4. 第4章の受け皿の考え方と整合する。第4章は「対象が PR として存在する判定では、判定者本人のレビューの本文」を受け皿とする。例外承認と停止の解除も、対象が PR である場合は「対象が PR として存在する判断」であり、これらだけを様式に限っていた理由は ADR-0070 の却下表にある「決断の記録(人確定)を要し、レビューに置き場が無い」である。宣言行と本文で決断を書けるなら、この理由は PR が対象の場合には当たらない
5. 写しの経路が既にある。`record-copy.yml` はマージ時にレビューを写す(`record-copy.yml:4-6`)。例外承認・解除のレビューも同じ写しに乗る

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| a1 台帳・解除を records ブランチへ移し、`check-pr` が records を読む | records は書き込みの権限を持つ者とジョブのトークンが追記・変更できる(EV-0185、IMPL-0353 未達、#379 未決)。判定される側が書ける場所へ効力の源を移すことになる。PR の時点の照合も名前だけのまま |
| a2 台帳の PR で権限者の署名コミットを PR の時点で確かめる(だけにする) | 後退経路としては採る(結論の最後の項)。既定にしない理由: 署名の鍵と名簿のアカウントの結び付きを API で確かめられるかが未確認(内部調査 §9 の3)、`records-signed.json` は規制業・CL2 以上に限られ、1〜2名で署名の鍵の運用を既定にする根拠が無い |
| 現行どおり台帳の PR に承認 1 件を残し、CODEOWNERS と `require_code_owner_review` で承認者を権限者に寄せる | Code Owner の要件は「所有者の誰か1人」で、1パスに1席しか置けない(内部調査 §4: `docs/gates/` に出荷判定者・解除の権限者・SG の判定者が同居)。作成者本人は承認できないので、権限者が自分で行を書くと別の所有者の承認が要る。権限者の操作を確かめる仕組みとして形が合わない |
| 例外承認・解除を Issue のコメントで受ける | 第4章が退けている(対象のコミットに固定されず、削除できる) |
| PR 本文に例外承認・解除を書かせる | 第4章 G-6 の条件4 のとおり、PR 本文は作成側の欄である。判定される側が書ける |

### 反論されうる点

- **「レビューの本文は後から編集できる」**。応答: 編集できる。対策は2つで、(i) マージ時の写し(既存の `record-copy.yml`)、(ii) G-5 が読んだ本文の要約値をチェックの結果に残すこと。ただし (i) の置き場 records は EV-0185 のとおり書き換えられないとは言えず、この弱さは #379 の結論に依存する。a3 はこの点で現行より悪くならないが、良くもならない
- **「認証情報を共有する体制(AI が権限者のアカウントで動く)では、判定される側の AI が権限者の名義でレビューを出せる」**。応答: 出せる。これは a3 固有の穴ではなく、ホスティングの記録で帰属を示す方式すべての前提の崩れである(第4章のアカウントと人の対応表の前提)。R-3 で述べる AI の担い手のアカウントの分離を推奨し、共有する体制では「帰属の裏づけが認証情報の共有で弱まっている」旨を開示する
- **「ADR-0070 決定3(受け皿は2つに限る)を改めることになる」**。応答: 改める。決定3 の「2つ」は変わらない(レビューの本文か様式か)。変わるのは、例外承認と停止の解除を「それ以外」から「対象が PR のときはレビュー」へ移すことである。採用済み ADR の本文は書き換えず、新 ADR で置き換える
- **「7.3 の要求事項4 の台帳を機械が起こすと、台帳の記録者が機械になる」**。応答: 7.3 は記録した者と承認した者を分けており、記録した者が機械であることは禁じていない。承認した者の欄は権限者本人のレビューから写す。人が書く欄を機械が生成しない(附属書C)ことは守られる
- 実機で、権限者のレビューを G-5 が API で読み、失効の条件を判定できるかは確かめていない。降ろす前に実機の確認を要する

## R-3 出荷の PR の承認(H-1)

### 結論

- **現行の文言(「出荷判定者が開き、出荷判定者本人が承認する」)は誤りであり、本件で直す**。作成者が自分の PR を承認できないホスティングでは、この手順は成立しない(外部調査 1.2【確認】)。成立しない手順を「記名者本人の操作」として書くことは、記録の真正性の説明として不正確である
- 出荷の PR は**効力を持つ記録ではなく、判定記録の写しの運搬である**。中身の真正性は、PR 上で CI が同じ集約を再実行し records と一致を検査すること(IMPL-0355)で担保されている。出荷判定の帰属は、records ブランチの G-7 の様式の記名者の操作(と、望むなら出荷の PR 上の出荷判定者のレビュー)で示す
- したがって出荷の PR については、条項「記名者以外の承認を課さない」を**判定記録の条項としてそのまま維持**し、残る承認は(効力を持つ記録と違って)本当に事務である。ここは ADR-0070 の判断が正しい
- 手順の書き方:
  - **既定**: PR を開くのは出荷判定者以外の主体(ship-evidence を起動した人、または AI の担い手の専用アカウント)。出荷判定者が承認する。承認者 = 記名者となり、帰属の裏づけが一つ増える
  - **出荷判定者しか PR を開けない体制**(1名、AI が本人のアカウントで動く): 出荷判定者が開き、宣言行つきのコメントのレビューを残す。必須の承認件数を満たす他者の承認は**事務**として開示する
  - 1名+外部確認者: 外部確認者の承認が付く。それは事務であり、外部確認者に中身の判定を求めない旨を手順に書く。ADR-0070 が解消した「中身を見ない承認」の構造はここに残るが、出荷の PR の中身は機械の検査が担保しているため、真正性の欠落ではない。**降りていない規定として表示し続ける**(IMPL-0124 を出荷の PR に絞って残す)
- 規制業(承認 2 件): 少なくとも1件は記名者以外の承認になる。事務として開示する。規制の要求する署名と PR の承認を同一視しない(第4章の既存の定め)

### 理由

1. 出荷の PR の中身は、人の判断ではなく機械の複製であり、CI の一致の検査がある。ここで人の承認を統制に数えると、検査の上に意味の無い承認を重ねることになる(ADR-0058・0067 の趣旨)
2. ADR-0066 決定2 は、G-7 の記名者が範囲内の変更の作成者・指示者・G-6 の承認者でないことを求める。出荷の PR の作成者・承認者が誰かは、この行為の条件に触れない。出荷判定者が出荷の PR を承認しても、自分の記録を自分で突合することにはならない(突合は CI がする)
3. AI の担い手の専用アカウントは、職務の分離の一般原則(行為者の識別を分ける)とも、出典台帳 SRC-0539(エージェントごとの ID、人と実行基盤の ID の分離を求める)の要約とも整合する。内部調査 H-7 の穴(既定の利用では常に開示側に落ちる)も同時に縮める。ただし本標準が専用アカウントを**義務**にする根拠は無い(1〜2名の負担と、ホスティングの利用規約がプラットフォームごとに違う)。推奨と開示にとどめる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 出荷の PR を `GITHUB_TOKEN` で開く | 既定で作れず、作れる設定は機械の承認も許す(README `:85`)。開いても検査が起動しない |
| 個人のトークン(PAT)で機械に PR を開かせる | 人の名義の操作を機械が行う。帰属の記録を偽らせる構成になる(README `:85` の判断を保つ) |
| 出荷の PR を bypass で通す | ADR-0070 決定7 と ADR-0038。強制層の縮小 |
| 出荷の PR を廃止し、records を正とする | records は書き換えられないとは言えない(EV-0185)。基底ブランチへ入れる要求(遅くとも G-7)は記録を製品と同じ履歴へ固定するためにあり、#379 の結論より前に外せない |
| 出荷判定者本人の承認を必須(欠落)にする | 1名体制と AI が本人のアカウントで動く体制で、出荷できなくなる。記名者の帰属は G-7 の様式で示せる。ADR-0070 の却下行(`:149`)と同じ理由 |

### 反論されうる点

- **「専用アカウントを推奨するだけでは、既定の利用(Claude Code が本人の gh 認証で動く)は変わらない」**。応答: 変わらない。そのため開示が要る。義務にするなら、ホスティングごとの機械アカウントの扱いと費用を調べてからにすべきで、本件の範囲では根拠が足りない
- **「出荷の PR の残る承認は事務だと言いながら、IMPL-0124 を undelivered で残すのは矛盾」**。応答: 矛盾しない。規定は「課さない」であり、テンプレートは GitHub の制約で「課している」。課されている承認が事務であることと、規定どおりに降りていないことは両立する。表示を消すと、読み手は「課されていない」と誤読する
- 外部確認者の承認が事務であると手順に書くと、外部確認者が別の PR(G-6 の本体の変更)でも中身を見なくなるおそれがある。出荷の PR に限って書く必要がある

## R-4 テンプレートの手段と採用者への委任

### 結論

| 手段 | 判断 |
| --- | --- |
| G-5 がホスティングのレビューを読む(R-2 の a3) | **採る**。テンプレートで降ろせる(plan=scheduled) |
| ルールセットの `required_reviewers`(一律 0 + パス条件で足し戻す) | **既定にしない。採用者の任意の構成としても、本件では推奨しない** |
| bypass actor(`always`・`pull_request`) | **採らない**(ADR-0070 決定7 を保つ) |
| `exempt` | **採らない**(監査の記録を残さない) |
| App・Actions の承認を必須の承認件数に数える | **採らない** |
| CODEOWNERS + `require_code_owner_review` | 誘導層としてのみ。遮断に数えない(現行どおり) |
| AI の担い手の専用アカウント | 推奨。義務にしない(R-3) |

- **plan=adopter とする範囲は無い**。効力を持つ記録はテンプレートが a3 で降ろす。出荷の PR の残る承認は、統制を弱めずに外す手段が採用者にも無い(突合 F-9 の裁定 `crosscheck.md:186` と同じ判断)。IMPL-0124 は出荷の PR に絞り、`plan=scheduled` のまま、プラットフォームの制約で降りていない旨を note に書く
- **GitHub 以外のプラットフォーム**: 標準の条項は「記名者本人の操作の記録」「効力の発生の条件」「取り込みに課された他者の承認の開示」で書き、機能名を書かない。プラットフォームごとの実現は準拠テンプレートと附属書の側で示す。パス単位の承認規則・免除を持つプラットフォーム(外部調査: Azure DevOps のパスフィルタつき必須レビュア、GitLab の Code Owner のセクション、Gitea の Unprotected file patterns)で記録のパスを免除してよいのは**判定記録だけ**であり、効力を持つ記録には免除を適用しない、と条項に書く

### 理由

1. `required_reviewers` の「一律 0 + 足し戻し」は、**失敗したときに開く(fail-open)構成**である。パターンの誤り・追加漏れ・否定の評価順の誤解のどれでも、そのパスの承認が 0 になる。しかも一律の承認数とチームの承認の合成の規則は文書に無く(外部調査 1.3【未確認】)、動作の実証も無い。強制層の既定値を 0 に下げて足し戻す構成は、ADR-0038 の「強制層の縮小」に当たると読むのが自然である。ユーザー所有のリポジトリでは使えないので、1〜2名の採用者の多くに届かない
2. bypass はアクター単位でパスを見ない。「記録だけ」の判定が App や CI の実装へ移り、その検査自体が新しい統制点になる(外部調査の考察)。決定7 を覆す新しい事実は調査に出ていない
3. 機械の承認を承認件数に数える形は、GitHub 自身が 2022 年に抜け道として塞いだ経緯があり、2026 年時点で数えられるかどうかの報告も対立している(外部調査 4.3)。7.11 の要求事項3 は解除に AI の名義を受け付けない。機械の承認で効力を持つ記録を取り込む構成は、この要求と正面から衝突する
4. 本標準はプラットフォームを選ばない(第4章「ツールを変えると判定の成立要件が変わる構成にしてはなりません」)。パス単位の免除を持つプラットフォームで、効力を持つ記録まで免除してしまうと、プラットフォームを変えただけで自己の例外の差し込みが開く。条項の側で区分を書いておかないと、プラットフォームの機能が統制の有無を決めてしまう

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `required_reviewers` をテンプレートの既定にする | 理由1。ユーザー所有で使えず、動作も未確認 |
| `required_reviewers` を「組織所有のリポジトリ向けの任意の構成」として README に載せる | 実機で確かめていない構成を、統制の弱化の向きで採用者へ示すことになる。a3 で効力を持つ記録が台帳の PR を要しなくなれば、残るのは出荷の PR だけで、そこは機械の検査が担保している。足し戻しの構成で得られる便益(出荷の PR の事務の承認を1件減らす)は、fail-open の危険に見合わない。実機の検証の後に別 Issue で再提起することは妨げない |
| plan=adopter で採用者に委ねる | 採用者が取れる手段は bypass か `required_reviewers` で、いずれも上のとおり既定にできない構成である。既定でない構成を採用者に勧める形になる |
| GitHub 以外のプラットフォームの実現を標準本文に書く | 本標準は機能名を本文の規範に置かない(ADR-0035 の型)。附属書・テンプレートで扱う |

### 反論されうる点

- **「`required_reviewers` を組織向けに示さないのは、組織の採用者から選択肢を奪う」**。応答: 禁じてはいない。ADR-0070 決定7 と同じく、組織が選ぶなら `state:needs-platform` の経路で統制の構成の変更として記録する。示さないのは既定と推奨だけである
- **「a3 の実装は G-5 にホスティングの API への依存を足す」**。応答: 足す。ただし G-5 は既に PR のラベルの履歴とレビューを読んでいる(IMPL-0059、G-6 の照合)。新しい種類の依存ではない
- Azure DevOps・GitLab・Gitea の機能の記述は外部調査の一次資料の読みに依り、本委員は実機で確かめていない。Gitea の Unprotected file patterns が PR の承認件数に効くかは未確認(外部調査 5.3)

## R-5 付随のずれと記録

### 結論

| 項目 | 本件で直すか | 内容 |
| --- | --- | --- |
| H-1(出荷の PR の自己承認) | **直す** | R-3 のとおり。README `:79,81`、`ship-evidence.yml:245,257-259`、`template/README.md:142`、`recording.md:98-101` の文言 |
| H-4(層1 の改版と直接の push の禁止) | **直す。ただし ADR-0057 の向きとは逆に** | 層1 は効力を持つ記録である(項目4 が解除の権限者を定め、`check-pr.mjs:499` が PR の時点で読む)。直接の push を止めるルールセットは誤りでなく、**ADR-0057 の却下行「層1 の改版にも PR を課す」の理由づけが、効力を持つ記録について不足していた**。層1 の改版にも R-1 の要求(記名者本人の操作が確かめられるまで効力を持たない)を掛ける。PR を課すか否かではなく、効力の条件で書く |
| H-5(RECORD_PATHS の範囲) | **直す** | 集約の「記録だけの PR」を、判定記録(`docs/gates/**`・`docs/records/**`・`docs/evidence/**`)と効力を持つ記録(台帳・層1・D-0・構成・`PROCESS-PROFILE.md`)に分ける。後者を「記録だけ」として変更の単位から外す扱いをやめ、記名者本人の操作の照合の対象に入れる。標準の条項の「判定記録だけのコミット」と範囲を一致させる |
| H-6(EV-0111 の差し替え条件) | **直す** | 差し替え条件に「記名者以外の者による追記」を足す。加えて効力を持つ記録について新しい EV を起こす(下記) |
| H-3(IMPL-0124 の note) | **直す** | 「承認者を記名者本人に限る手順は CODEOWNERS で降ろす」の記述は、既定で効いていない(`require_code_owner_review: false`)。出荷の PR に絞り、事実に合わせる |

### 記録の構成(提案)

- **新 ADR**(番号は起案時に採番): 「判定記録と効力を持つ記録を分け、効力を持つ記録は記名者本人の操作が確かめられるまで効力を持たない」
  - ADR-0070 決定3(例外承認・停止の解除の受け皿)と決定6(条項の範囲)を部分的に置き換える。原理(他者の承認は真正性を上げない)は保つ
  - ADR-0057 の却下行「層1 の改版にも PR を課す」の理由づけを、効力を持つ記録について補う(却下そのものは保つ。PR の承認者を課すのではなく、記名者本人の操作を効力の条件にする)
  - 「採らないと決めたこと」を明記する: `required_reviewers` の足し戻しを既定にしない、bypass・exempt・機械の承認を採らない、AI の担い手の専用アカウントを義務にしない、records への移設を #379 の前に採らない
- **EV**:
  - EV-0111 は対象を判定記録に絞り、差し替え条件に「記名者以外による追記の件数」を足す(識別子は再利用しない規則に照らし、対象の意味が変わると判断するなら新しい番号を起こす。起案側の判断に委ねる)
  - 新 EV(E0): 効力を持つ記録を記名者本人の操作で裏づければ、判定される側による自己の例外・解除の差し込みが止まるという判断。差し替え条件の案: 「効力を持った例外承認・解除の記録のうち、権限者本人の操作の裏づけが無かった件数」と「判定される側のアカウントが効力を持つ記録を足した件数」(いずれも G-7 の集約で数える)
  - 新 EV(E0): 3名以上の体制で、残る承認 1 件が権限者でない者によって満たされうるという判断(構成からの推論で、事例も実機の再現も無い)
- **IMPL**:
  - 新 IMPL(`target=pr-checks`、`plan=scheduled issue=380`): G-5 が例外承認・停止の解除をホスティングのレビューから読み、R-2 の条件1〜6 を確かめる
  - 新 IMPL(`target=pr-checks` または `evidence-aggregation`): 基底ブランチの台帳・解除・層1 の行を、記録を入れた変更の権限者本人の操作で照合し、裏づけの無い行を数えない
  - IMPL-0124: 出荷の PR に絞って undelivered を維持。note を事実に合わせる
  - IMPL-0128: 照合の対象に台帳の行を加えるか、効力を持つ記録は新 IMPL へ移したことを note に書く

### 理由

1. H-4・H-5 は R-1 と同じ根から出ている(効力を持つ記録を「記録だけ」の類に入れていた)。R-1 だけ直して層1 と D-0 を残すと、判定される側は台帳ではなく層1 の権限者の欄を書き換えれば同じ結果を得る。片方だけ塞ぐ統制は、塞いでいない方へ攻撃を移すだけで、信頼性を上げない
2. H-6 は、本件の決定を検証できるかに直結する。差し替え条件が「書き換え」だけを数える限り、本件で塞ぐ事象(追記による差し込み)は測られず、EV は永久に反証されない形になる
3. H-1 は文言の誤りで、議論の結論に依らず直すべきもの。成立しない手順を規範として残すことは、手順に従った採用者に「本人の操作で裏づけた」と誤認させる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| H-4〜H-6 を別 Issue に分ける | 理由1。片方だけ塞ぐ状態を、別 Issue が閉じるまで公開し続けることになる。分けるなら、本件の ADR に「層1・D-0 は未対処」と明記し、undelivered で表示する必要がある(分けるより一緒に直すほうが記録が単純になる、という理由ではなく、穴を開いたまま公開しないという理由で一緒に直す) |
| H-4 を ADR-0057 の向き(層1 の改版に PR を課さない)へ寄せ、直接の push を許すルールセットにする | 層1 は効力を持つ記録であり、直接の push を許すと判定される側が権限者の欄を書き換えられる。強制層の縮小(ADR-0038) |
| RECORD_PATHS を条項の「判定記録」に合わせて狭めるだけにする | 狭めた残り(層1・D-0・構成)が通常の変更として G-6 の承認を要するようになる。それは R1-b と同じく、記名者以外の承認を真正性の代わりにする形である。効力を持つ記録には別の扱い(記名者本人の操作の照合)が要る |

### 反論されうる点

- **「層1・D-0・構成の改版を効力を持つ記録として扱うと、`/process-change` の既存の経路と二重になる」**。応答: 本委員は `/process-change` が記名者本人の操作を確かめているかを読んでいない。起案の前に突合が要る。既に確かめているなら、新 IMPL はその照合を G-5 の読みに結び付けるだけになる
- **「効力を持つ記録」という語の新設は、ADR-0070 が語彙を増やさないとした判断(却下表「承認イベント・属性・固定を語彙に加える」)に反する」**。応答: 既存の語で区別できるなら新設しない。候補は「PR の時点で読む記録」「判定の材料になる記録」(`ci-gates.md:153` の既存の言い回し)。語の選定は起案側に委ねるが、**区分そのものは要る**
- 本意見全体が、「判定される側が自分の例外を差し込む」事象の発生を前提にしているが、発生の事例は無い。事例が無いことは、統制を外してよい理由にはならない(SRC-0419 の台帳の要約: 費用だけを理由に統制を省かない)。ただし、根拠水準は E0 として開示する

## まとめ(論点ごとの結論)

- R-1: 「記名者以外の承認を課さない」は判定記録について維持し、台帳・解除・層1 などの効力を持つ記録は対象から外す。効力を持つ記録は記名者本人の操作を機械が確かめるまで効力を持たない、と新設する。誤りは ADR-0070 決定6 の適用範囲
- R-2: a3(対象の PR 上の権限者本人のレビューを受け皿に加え、G-5 が読む)を採る。基底ブランチの台帳・解除は後退経路として残し、同じ裏づけを課す。records への移設(a1)は採らない
- R-3: 「出荷判定者が開き本人が承認」は成立しないので直す。既定は出荷判定者以外(専用アカウント等)が開き出荷判定者が承認。開けない体制では他者の承認を事務として開示し、IMPL-0124 を出荷の PR に絞って表示し続ける
- R-4: `required_reviewers` の足し戻し、bypass、exempt、機械の承認はいずれも採らない。plan=adopter の範囲は無い。条項は機能名を使わず書き、パス単位の免除を持つプラットフォームでも免除してよいのは判定記録だけと定める
- R-5: H-1・H-3〜H-6 を本件で直す。層1・D-0・構成も効力を持つ記録として扱い(ADR-0057 の却下の理由を補う)、RECORD_PATHS を2つに分け、EV-0111 に追記を足し、新 ADR・新 EV(E0)・新 IMPL を起こす
