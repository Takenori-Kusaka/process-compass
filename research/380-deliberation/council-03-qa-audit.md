- 作成日: 2026-11-05

## 0. 監査の立場から先に示す事実(調査に無い、または調査より踏み込んだもの)

### F-1 残る承認 1 件は「判定される側以外の誰かが見た」ことしか保証しない。記名された承認者本人の同意は保証しない

`exceptionFor`(`check-pr.mjs:446-475`)が台帳の行に確かめるのは4点です。状態、承認した者が名簿の人で AI の名義でないこと、承認した者が**対象の PR の作成者でない**こと、理由と期限です。承認した者の照合は**名前**で行います(`resolveSigner`)。台帳の行を誰が書き、誰が台帳の PR を承認したかは、PR の時点でも集約でも確かめていません(台帳の行は IMPL-0128 の照合の対象外。`aggregate-evidence.mjs:2213-2219`)。

3名以上の体制では、次の経路が**現行でも開いています**。

1. 判定される側 X が、台帳の PR を自分で開く。行には「承認した者: Y」と書く
2. 第三者 Z が、台帳の PR を承認する。Z は Y の同意を確かめる立場にない
3. X の対象の PR は、`approver(Y) ≠ author(X)` で例外承認を得て通る

承認 1 件が塞いでいるのは「X が単独で」という経路だけです。「Y の名を借りて」という経路は塞いでいません。したがって R-1 を「残る承認があるから統制は足りている」と評価することはできません。

### F-2 監査の証跡は、いまは揃っている。揃っていることを誰も突き合わせていない

`record-copy.yml` は、**マージされたすべての PR**(`:49`。記録だけの PR を含む)について、作成者 `author{id,login}` と `reviews[]` の `user{id,login,type}`・`state`・`commit_id`・`body` を `records/reviews/pr-<n>.json` へ写します(`:24-26`)。台帳の PR の作成者と承認者は、記録として残っています。欠けているのは突き合わせです。台帳の行の「承認した者」が、台帳の PR の作成者か承認者のいずれかに一致するか(数値の識別子で)を、集約は見ていません。

### F-3 停止の解除の記録も名前の照合だけで成立する

`stopFindings`(`check-pr.mjs:489-531`)は、基底の層1 の項目4 の権限者と解除の記録の記名を照合し、AI の名義を退け、ラベルを付けた日より前の記録を数えません。記録を誰が書き、誰が基底へ入れたかは見ません。保留された PR の作成者が別の PR で解除の記録を書き、権限者の名を記すことは、F-1 と同じ構造で起こりえます。

### F-4 写しはマージされた PR だけに作られる

`record-copy.yml:49` は `merged == true` のときだけ動きます。閉じた PR の上のレビューは写されません。これは R-2 の案 a3(対象の PR 上のレビューを受け皿にする)で効いてきます。

## R-1 条項の向き

### 結論

**見直す。ただし向きは「緩める」ではなく「区別する」**。現行の条項は2種類の記録を1つの規定で扱っており、その点が誤りです。

- 判定記録(様式・承認レビューの写し)を基底へ入れる操作には、**記名者以外の承認を課さない**。ADR-0070 の決定6 の核はここで維持する
- **PR の合否を左右する材料**(例外承認、停止の解除、前倒しの SG の記録)は、条項の対象から外す。代わりに要求を結果で書く。「**判定される側は、自分を対象とする材料を単独で、また他人の名を借りて、成立させられないこと**」
- 残る承認を「取り込みの事務」と呼ぶ現行の文(`gate-criteria.md:107` 末尾)は、材料については誤り。材料に付く承認は事務ではなく、**材料の取り込みの統制**である。出荷の PR に付く承認は、R-3 のとおり事務と呼んでよい

### 理由

- 様式と写しは、置き場が基底でなくても集約が records から読みます(`ship-evidence.yml:22-23`)。基底へ入れる操作は運搬であり、第三者の承認は中身の判定を伴いません(ADR-0070 `:53` の「中身を見ない承認」)。ここで第三者の承認を課すことは、信頼性を上げずに形骸化を生みます。ADR-0070 の判断はこの範囲では正しい
- 台帳と解除は性質が違います。`check-pr.mjs` が既定ブランチの先端から読むのは、「判定の材料を、判定される側が同じ変更で用意できない形にする」ためです(`ci-gates.md:153`)。この設計は、**基底へ入る前に判定される側以外が介在する**ことを暗に前提にしています。条項がその介在を「事務」と呼び、課さないと定めると、条項自身が `ci-gates.md:153` の前提を外します。ADR-0070 は決定6 で「現行どおり基底へ先に」(`:98`)と書きましたが、残る承認の役割を論じていません。誤りは ADR-0070 の一般化の範囲の側にあります
- 「事務」と呼ばれた操作は、監査の対象から外れます。現に F-1・F-3 の照合が欠けているのは、この承認を統制と認めていないことの帰結だと見ます

### 監査で確かめられること

- 材料(台帳の行、解除の記録)ごとに、その材料を基底へ入れた PR の番号、作成者の数値の識別子、承認者の数値の識別子、記名された者。すべて `records/reviews/pr-<n>.json` から取れる(F-2)
- 「記名された者が、その材料の PR の作成者でも承認者でもない」件数。0 であるべき。1件でもあれば、名前を借りた経路の疑いとして保証の開示に出す
- 「材料の PR の作成者または承認者が、その材料の対象の PR の作成者と同一」の件数(判定される側が自分の材料の取り込みに関わった件数)

### 採らない案

- **条項を現行のまま維持し、残る承認を事務と呼び続ける**。F-1 の経路を統制として扱わない状態が続き、監査は照合の欠けを見つける根拠を持たない
- **条項を字義どおり降ろし、材料にも承認を課さない**(パス単位の免除・bypass・records への移設)。判定される側が単独で自分の例外・解除を入れる経路が開く。名前の照合だけでは塞げない(F-1・F-3)
- **すべての記録に第三者の承認を課す方向へ戻す**。ADR-0058・ADR-0070 が退けた「中身を見ない承認」を復活させる。様式と写しには信頼性の上積みが無い

### 反論されうる点

- 「材料も記録であり、区別は恣意的だ」。区別の基準は、機械が PR の合否に読むかどうかである。`check-pr.mjs` の `atPolicy` と `git show ${base}:` で読むものを列挙でき、恣意ではない。ただし、この列挙を標準の側に持つか準拠テンプレートの側に持つかは、R-5 の H-5 と一緒に決める必要がある
- 「結果で書くと、プラットフォームごとの満たし方が曖昧になる」。曖昧さは R-4 で手段の例示と禁止の列挙で埋める。手段を条項に書き込むと、プラットフォームを選ばない方針と衝突する

## R-2 例外承認の台帳と停止の解除の受け皿

### 結論

**a3(対象の PR 上の記名者本人のレビュー)を、条件つきで第一の受け皿として採る**。現行の台帳の PR の経路は残し、F-1 の照合を足したうえで代替の経路とする。a1(records への移設)は #379 が書き換えの防止または検出を定めるまで採らない。a2(署名コミット)は単独の受け皿として採らず、強化の手段として残す。

a3 の成立条件(すべてを PR の時点で機械が確かめる。満たさないレビューは数えない):

1. レビューの提出者は、名簿の人のアカウントに**数値の識別子**で対応づく(login は改名できるため使わない)。AI・bot の名義を受け付けない(`user.type` は API の値で見る)
2. 例外承認では、提出者が対象の PR の作成者でも、作成を指示した者でもない。停止の解除では、提出者が基底の層1 の項目4 の権限者の席の責任者である
3. 停止の解除では、レビューの提出がラベルを付けた最後の時刻より後である(現行の `stopFindings` の条件を引き継ぐ)
4. 例外承認のレビューは、提出時の `commit_id` を持つ。対象の PR の先頭がその後に変わった場合の扱い(例外を先頭に結ぶか、PR に結ぶか)を決める。監査の立場からは**先頭に結ぶ**ことを推す。結ばないと、例外を得た後に別の変更を足して通せる
5. 取り下げ(dismiss)されたレビューは数えない。本文が提出後に編集されたレビューは数えない(GraphQL の `lastEditedAt` で見られるかは**未確認**。確かめられないなら、本文を宣言行と識別子だけにし、編集の影響を最小にする)
6. マージ時の写し(`record-copy.yml`)がそのレビューを含むことを、出荷の集約が確かめる。写しに無い例外・解除は欠落とする

第7章 7.3 は例外を台帳へ記録することを求めます。a3 では、台帳の行は**成立の場ではなく一覧**になります。行は写しから機械が起こし、成立の裏づけとしてレビューの識別子を必ず持たせます。識別子の無い行、写しと合わない行を集約が出します。

### 理由

- a3 では、成立の裏づけが「記名者本人のアカウントの操作」になり、名前の照合(F-1・F-3)から抜けられます。承認 1 件の経路より強い統制です
- PR の作成者本人でも COMMENT のレビューは出せるため(`ci-gates.md:652`、`G-4.md:22`)、1名の体制でも成立します。ただし例外承認は条件2 で作成者本人を退けるので、1名の体制では例外承認は成立しません。これは現行の `exceptionFor` と同じ結論であり、緩めていません
- 記録だけの PR が例外・解除について消えるため、残る承認 1 件の問題(IMPL-0124)のうち2つが、承認を外さずに解けます

### 監査で確かめられること

- 例外・解除ごとに、レビューの識別子、提出者の数値の識別子、提出日時、`commit_id`、写しの所在
- 成立に数えたレビューのうち、提出者が名簿の席と合わない件数、対象の PR の作成者と同一の件数、写しに無い件数
- 現行の台帳の PR の経路を使った材料について、R-1 の3つの件数

### 採らない案

- **a1 records への移設**。records は書き込みの権限を持つ者と `GITHUB_TOKEN` が追記・変更できます(EV-0185、IMPL-0353 未達)。判定される側が records へ自分の例外を書けば、承認の門も通らずに材料が成立します。F-1 より悪い。#379 が書き換えの検出を定め、かつ PR の時点でその検出を読めるようになるまで採らない
- **a2 署名コミットを PR の時点の合否に使う**。署名の鍵と名簿のアカウントの結び付きを API で確かめられるかは未確認です(内部調査 §9-3)。1〜2名の体制で署名の運用を前提にできるかも分かりません。署名を持つ構成(`records-signed.json`)では強化として数えてよい
- **Issue のコメントを受け皿にする**。第4章 `:100` が退けたとおり、対象のコミットに固定されず削除できる
- **台帳の PR の経路を廃止する**。レビューを提出できないホスティング、または API で読めない構成の採用者が残る。代替として残し、F-1 の照合を課す

### 反論されうる点

- 「第4章 `:99` と ADR-0070 決定3 は、例外承認と停止の解除の受け皿を様式に限っている」。そのとおりで、a3 は条項と ADR の改定を要する。限った理由は「対象が PR として存在しない」場合を想定したためと読める。例外承認と停止の解除は対象が PR そのものであり、G-6 と同じ扱いが当てはまる
- 「レビューの本文は編集でき、180日で監査ログが消える」。写しをマージと同じ時期に取ることで受ける。ただし写しの置き場 records は EV-0185 のとおり書き換えられないとは言えない。a3 の証跡の強さは、#379 の結論に依存する。この依存を EV で開示する
- 「閉じた PR の解除は写されない」(F-4)。閉じた PR はマージされないため、解除の効果が生じない。監査上の欠落にはならない。ただし再び開いた PR では、解除のレビューが写しに入るかを確かめる必要がある

## R-3 出荷の PR の承認(H-1)

### 結論

**H-1 は事実の誤りとして直す。出荷の PR の承認は、取り込みの事務と位置づけてよい**。

- 出荷の PR を開くのは出荷判定者(人)。現行どおり。CI を起動させるために人が開く必要がある
- 承認者を「出荷判定者本人」と書かない。GitHub では作成者が自分の PR を承認できない(外部調査 1.2)。README `:79,81`、`recording.md` の該当行、`ship-evidence.yml:245,257`、`template/README.md:142` の文言を直す
- 出荷判定者以外の承認は事務である。G-7 の判定の帰属は、records への判定者本人の直接の push(と署名)で裏づけ、出荷の PR の承認には依らない
- 1名で checks-only の体制では承認が無い。1名と外部確認者の体制では、外部確認者の承認が付く。2名の体制では相手の承認が付く。いずれも事務として開示する

### 理由

- 出荷の PR の中身は機械の複製であり、`verify` ジョブが records と一致することを検査します(README `:80`)。承認者が中身を判定する必要は無く、ADR-0070 の「事務」の定義がそのまま当てはまります。R-1 の材料とは違い、判定される側が自分に有利な材料を差し込む経路ではありません
- 成立しない手順を「記名者本人の操作」と書き続けると、監査は承認者と記名者の不一致を毎回の所見として拾い、所見が常態化して意味を失います。誤った文書が監査を形骸化させます

### 監査で確かめられること

- 出荷の PR ごとに、作成者(出荷判定者であること)、承認者、`verify` の結果、マージの後に先頭が変わっていないこと(`dismiss_stale_reviews_on_push`・`require_last_push_approval`)
- G-7 の様式の帰属の裏づけ(records への push の author、署名の有無)。現行の IMPL-0128 の照合でよい
- **要確認**: 出荷の PR に、複製と保証の開示以外のファイル(例: 台帳の行、層1)を足した場合に `verify` が失敗するか。README `:80` は「記録の置き場の既存のファイルの変更・削除も失敗」とするが、置き場の外の追加や台帳の行の追加を止めるかは書いていない。止めないなら、出荷の PR が R-1 の材料の抜け道になる。出荷の PR を事務と呼ぶ前提は「中身が複製だけであること」を機械が確かめることである

### 採らない案

- **Actions(`GITHUB_TOKEN`)に PR を開かせる・承認させる**。README の判断どおり。2022 年に GitHub 自身が抜け道として塞いだ経緯があり、承認の数え方も 2026 年時点で報告が割れている(外部調査 4.3)
- **PAT で機械が人の名義で開く**。人の名義の操作を機械が行う形になり、帰属の記録が偽になる
- **出荷の PR に bypass を与える**。ADR-0070 決定7 のとおり既定ブランチの強制層の縮小。`exempt` は監査記録を残さず論外
- **AI 専用アカウントに開かせ、出荷判定者が承認する形を既定にする**。成り立つが、構成に AI のアカウントの別を問う手段が無い(H-7)。採用者の選択肢として手順に書くことは妨げない

### 反論されうる点

- 「出荷の PR の承認を事務と呼ぶと、出荷判定者の判断が PR の上に残らない」。判断は G-7 の様式に残り、様式は records と複製の両方にある。PR の承認は判断の場でない
- 「外部確認者に中身を見ない承認をさせる構造が残る」(議題 :12)。残る。ただし出荷の PR では機械が中身を検査しているため、承認者が見ないことで失われる統制は無い。材料(R-1)の承認と違い、事務と開示して足りる

## R-4 テンプレートの手段と採用者への委任

### 結論

- **標準の側**: 条項は結果で書く(R-1)。手段については、**禁止を列挙**する。材料のパスについて、承認の免除・bypass・PR を経ない直接の push を許す構成は、記名者本人の操作を合併の前に機械が確かめる仕組みと組にしない限り、条項を満たさない
- **準拠テンプレートの既定**: a3(R-2)を実装し、既定ブランチのルールセットは現行(`team.json` 以上は承認 1 件)を維持する。パス条件の `required_reviewers`、bypass、App の承認は既定にしない
- **plan=adopter の範囲**: IMPL-0124 を `adopter` にしない。材料の統制は採用者任せにできない型である(停止の申し立ては `impl-no-adopter.yaml` の登録簿に当たる)。採用者へ委ねてよいのは、様式と写しを記録だけの PR で入れる場合の承認を免除する手段(パス条件の `required_reviewers` など)だけで、それも統制の弱化として `state:needs-platform` で記録する
- **GitHub 以外**: Azure DevOps のパス別の Required の自動レビュア、GitLab の Code Owner のセクション(`!`・`^`)、Gitea の Unprotected file patterns を、手段の例として附属書に挙げてよい。ただし Gitea の Unprotected file patterns を材料のパスに当てることは**禁止の例として明記する**。PR を経ない直接の push では G-5 が走らず、判定される側が自分の例外を基底へ直接入れられる

### 理由

- 外部調査のとおり、GitHub にはパス単位で承認件数を変える公式の手段が無く、`required_reviewers` を使う構成は未検証で、ユーザー所有のリポジトリでは使えません(外部調査 1.3・4.1)。未検証の構成を既定にすると、適用した採用者は統制を満たしたと誤認します
- bypass はアクター単位でパスを見ません。「記録だけ」の判定が App の実装へ移り、その実装が新しい統制点になります(外部調査 4.2)。`exempt` は監査記録を残さず、観点(3)に正面から反します
- a3 は承認を外さずに材料の PR を不要にするため、免除の手段を探す必要自体を減らします

### 監査で確かめられること

- env-check の所見に、既定ブランチの bypass actor(現行で所見あり)、`exempt` の有無、`required_reviewers` の構成、Actions の承認を許す設定(現行で mismatch)が出ること
- **契約検査の欠け**: `verify-gate-contract.mjs` は `bypass_actors` と `require_code_owner_review` を見ない(内部調査 §3)。少なくとも、ルールセットのファイルに bypass actor を足す変更を契約検査が所見にすることを求める
- 採用者が免除の手段を入れた場合、`state:needs-platform` の記録と D-0 の決定者の記名があること

### 採らない案

- **一律の承認 0 と `required_reviewers` の否定パターンを既定にする**。未検証(外部調査 4.1)、チーム必須、ユーザー所有で不可。加えて材料のパスを否定パターンに含めると R-1 の統制が外れる
- **GitHub App を `pull_request` モードの bypass に入れ、記録 PR を App がマージする**。統制点が App の実装へ移り、App の検査の信頼性を誰も保証しない。既定にしない(ADR-0070 決定7 と同じ)
- **App・Actions の承認を承認件数に数える構成**。数えられる条件が確かめられない(外部調査 4.3)。数えられた場合は機械の承認が人の承認の代わりになり、第5章の人の門の規定に反する
- **IMPL-0124 を `plan=adopter` にする**。採用者にも材料を安全に免除する手段が無い(crosscheck F-9 の裁定と同じ)

### 反論されうる点

- 「禁止の列挙はプラットフォームの機能名を条項へ持ち込む」。機能名は附属書の例に置き、条項は「PR の検査を経ない取り込み」「アクター単位の素通り」という性質で書く
- 「a3 は GitHub の API(レビューの `user.id`・`commit_id`)に依存しており、プラットフォームを選ばない方針に反する」。条項は「記名者本人のアカウントの操作を、合併の前に機械が確かめる」と書き、a3 は GitHub での一つの実装と位置づける。他のホスティングでは同等の操作(Azure DevOps の投票、GitLab の承認)で満たせる

## R-5 付随のずれと記録

### 結論

| 項目 | 本件で直すか | 結論 |
| --- | --- | --- |
| H-4 層1 の改版と直接の push の禁止 | **直す(決定を記録する)** | 準拠テンプレートが層1 の改版に PR を課すことを、意図した強化として新しい ADR に書く。ADR-0057 `:509` の「層1 の改版に PR を課さない」は、層1 が `check-pr.mjs` の材料(項目4 の解除の権限者。`:499` で基底から読む)になった時点で前提が変わったと記録する |
| H-5 RECORD_PATHS の範囲 | **直す** | 「記録だけの PR」を2つに分ける。判定記録(`docs/gates/**`・`docs/records/**`・証跡など)と、**統制の文書**(`docs/quality-assurance-policy.md`・`docs/D-0-governance.md`・`PROCESS-PROFILE.md`・`docs/debt-ledger.md`)。後者を変更の単位から外さない |
| H-6 EV-0111 の差し替え条件 | **直す** | 「書き換え」に加え、「材料の記名者が、その材料を基底へ入れた操作(作成・承認・レビュー)のいずれにも現れない件数」と「判定される側が自分を対象とする材料の取り込みに関わった件数」を足す |
| H-7 AI の担い手のアカウント | 本件で論点として記録し、別 Issue | `/process-init` に AI の担い手のアカウントを別にするかの問いを足すかは #380 の範囲外。ただし R-3 の手順の前提なので、未決として明記する |

記録:

- **新しい ADR** を1つ立てる。ADR-0070 の決定3(受け皿の限定)と決定6(記名者以外の承認を課さない、の範囲)を部分的に置き換える。採用済みの ADR-0070 の本文は書き換えない
- **EV**: a3 の証跡の強さ(写しの置き場が #379 に依存すること。E0)。レビューの本文の編集を検出できるかの未確認(E0)。EV-0111 は差し替え条件を改める。EV-0115 は、材料について第三者承認を廃止していないため測れないことを開示する
- **IMPL**: a3 の PR の時点の検査(`check-pr`)、材料の記名者と取り込みの操作者の照合(集約。IMPL-0128 の対象を台帳の行と解除の記録へ広げる)、出荷の PR の文言の是正(rulesets/README・recording.md・ship-evidence.yml・README)、出荷の PR の中身を複製だけに限る検査(R-3 の要確認が否なら)、契約検査の bypass actor の所見。IMPL-0124 は、条項の範囲の改定に合わせて対象を判定記録に限り、材料は新しいマークへ移す。降りるまで undelivered を表示し続ける
- **採らない案**: R-1〜R-4 の採らない案をすべて ADR の「却下した選択肢」に書く。とくに「パス単位の免除を材料に当てる」「exempt」「Actions の承認」「Gitea の Unprotected file patterns を材料に当てる」「IMPL-0124 を adopter にする」

### 理由

- H-4: 層1 の項目4 は、誰が停止を解除できるかを決めます。層1 を PR も他者の目も経ずに変えられると、判定される側が項目4 を自分の席へ書き換え、自分の停止を解除できます。これは R-1 の材料と同じ型の経路です。テンプレートの「直接の push の禁止」は偶然の強化ではなく必要な統制であり、ADR-0057 の決定と食い違ったまま放置すると、後の改定で「ADR-0057 どおりに PR を外す」方向へ緩められる危険があります
- H-5: 現行では、層1・D-0 だけを変える PR は記録だけの PR と識別され、変更の単位に数えず、IMPL-0128 と G-5 だけを見ます(`aggregate-evidence.mjs:1333-1337,1388-1412`)。停止の解除の権限者を変える層1 の改版が、独立した確認・緩める向きの変更の検査の対象から外れます。R-1 で条項の範囲を判定記録に限るなら、集約の範囲も揃えないと、条項と実装の食い違いが新しく生まれます
- H-6: #380 の論点は追記であり書き換えではありません。現行の差し替え条件では、F-1 の経路が使われても件数が 0 のまま残り、暫定の判断が実証されたように見えます。測れない差し替え条件は、根拠水準のマークの意味を失わせます

### 監査で確かめられること

- 層1・D-0 の改版の PR が、変更の単位として集約に現れ、独立した確認と緩める向きの検査を受けたこと
- EV-0111 の新しい差し替え条件の2つの件数が、出荷の集約から毎回出ること(写しから機械が数えられる)
- 新しい ADR の却下の欄に、本意見書の採らない案が載っていること

### 採らない案

- **H-4・H-5・H-6 を別 Issue へ送り、本件では条項だけを直す**。H-5 は R-1 の範囲の改定と同じ定義の問題であり、分けると条項と集約の範囲が食い違った状態でリリースされる。H-4 は R-1 の材料と同じ経路の問題である。H-6 は本件の判断の差し替え条件そのものである
- **H-4 を ADR-0057 どおりに直す(テンプレートで層1 の改版の PR を外す)**。上の理由で統制の弱化になる
- **H-5 で RECORD_PATHS を条項(判定記録)に合わせて単に狭めるだけにする**。台帳を判定記録から外すと、台帳の行の追加が製品の変更として規模・リスク区分の検査に掛かり、例外承認の取り込みが過剰に重くなる。2つの区分を立て、統制の文書には独立した確認と緩める向きの検査を当てる形にする

### 反論されうる点

- 「H-4 は ADR-0057 の改定であり、#380 の範囲を超える」。範囲を超えるのは事実だが、同じ型の経路(基底から読む統制の材料を、判定される側が変えられるか)であり、決定を分けると片方だけが緩められうる。少なくとも新しい ADR に「層1 は材料である」と記録し、ADR-0057 の当該行の前提が変わったことを示す
- 「統制の文書を変更の単位に数えると、1名の体制で層1 の記名の改版が独立した確認を要し、進めなくなる」。1名の体制は G-6 が未達として開示される体制であり、その開示の中で扱う。統制の文書だけを確認の対象から外す理由にはならない

## 論点ごとの結論(1行)

- R-1: 見直す。判定記録(様式・写し)には記名者以外の承認を課さない、を維持し、PR の合否を左右する材料(例外承認・停止の解除)は条項から外して「判定される側が単独で、また他人の名を借りて成立させられないこと」と結果で書く。材料に付く承認を「事務」と呼ぶ現行の文は誤り
- R-2: a3(対象の PR 上の記名者本人のレビュー。数値の識別子・作成者でない・層1 の権限者・ラベルの後・先頭に結ぶ・写しにあること)を第一の受け皿として採る。台帳の PR は代替として残し、記名者と取り込みの操作者の照合を足す。a1 は #379 まで採らない
- R-3: H-1 は誤りとして直す。出荷の PR は出荷判定者が開き、他者の承認は事務と開示する。前提として、出荷の PR に複製以外のファイルが入ったら失敗することを確かめる(要確認)
- R-4: 既定ブランチのルールセットは維持し、required_reviewers・bypass・App の承認は既定にしない。IMPL-0124 を adopter にしない。材料のパスへの免除・直接の push(Gitea の Unprotected file patterns を含む)を禁止の例として明記する
- R-5: H-4・H-5・H-6 は本件で直す(層1 は材料として PR を課す、RECORD_PATHS を判定記録と統制の文書に分ける、EV-0111 に追記と名前の借用の件数を足す)。新しい ADR で ADR-0070 の決定3・6 を部分的に置き換える。H-7 は未決として記録し別 Issue
