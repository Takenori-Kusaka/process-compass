## 0. 現場から見た前提の補正(議題の事実に足すこと)

議題は「残る承認 1 件が、判定される側の書き足しを事実上塞いでいる」とします。現場の目で体制ごとに当てると、**塞いでいるのは 2名・相互の体制で、判定される側が自分のアカウントで台帳の PR を開いた場合だけ**です。それ以外では塞いでいないか、塞ぐ代わりに形骸の承認を生んでいます。

| 体制 | ルールセット | 判定される側 B が「承認した者: A」と書いた台帳の行を自分で出したとき | 判定の記名者 A の AI が A のアカウントで台帳の PR を出したとき |
| --- | --- | --- | --- |
| 1名(G-6 未達) | checks-only | 承認が無いので止まらない。PR の時点の照合は名前だけ(`ci-gates.md:169`、`check-pr.mjs:464`) | 同左。ただし判定される側と記名者が同一の人なので、そもそも例外の承認者 ≠ PR の作成者の照合(`check-pr.mjs:466`)で止まる |
| 1名+外部確認者 | team | 外部確認者の承認が要る。外部確認者は台帳の中身を判断する材料を持たず、通すかどうかは外部確認者の応答次第(内部 §5) | 同左。承認は**中身を見ない承認**(ADR-0070 `:53` の構造の再発) |
| 2名・相互 | team | A の承認が要る → **ここだけ実際に塞がる** | B の承認が要る。B は例外を受ける側。承認は形骸(B が止める理由は無い) |
| 3〜9名 | team(`require_code_owner_review: false`) | **第三者 C の承認で通る**。C は台帳の行の「承認した者: A」が A 本人の意思かを確かめる手段を持たない。CODEOWNERS の行は雛形のまま無効(内部 §4) | C か B の承認。形骸 |
| 10名以上 | team / safety / regulated | safety・regulated は Code Owner の承認を要するが、`docs/debt-ledger.md` の所有者は価値責任者の席の**誰か1人**で足り、A 本人とは限らない(外部 §2) | 同左 |

現場の結論として、**残る承認 1 件は「統制」ではなく「偶然そこにある門」**です。効くかどうかが「誰のアカウントで PR を開いたか」と「人数」で決まり、3名以上ではほぼ効いていません。議題の「唯一の人の門」という評価は 2名・相互の体制に限って正しく、一般化すると過大評価になります。

もう一点、**認証情報の共有**(Claude Code が本人の `gh` 認証で動く既定の使い方)では、AI が本人の名義でレビューも承認も出せます。プラットフォームの上で「人が操作した」ことを示す手段は、どの案でもこの前提が崩れると消えます。どの案を採っても、AI の担い手の名義を人と分けるか、本人の名義の操作に人の確認を挟むかを決めなければ、帰属の裏づけは成り立ちません(H-7 を本件の前提に格上げする)。

## R-1 条項の向き

### 結論

- **「記名者以外の承認を課さない」(ADR-0070 決定6)は維持する**。他者の承認を帰属の裏づけにしない、という向きは正しい
- ただし、例外承認と停止の解除について ADR-0070 は**誤っている点がある**。「現行どおり基底へ先に」(`:98`)とだけ書き、PR の合否を左右する材料を**何が認証するか**を決めていない。その空白を、残る承認 1 件が偶然埋めているだけである。誤りは条項の向きではなく、**台帳・解除の真正性の要件の欠落**の側にある
- 新しい ADR で ADR-0070 を補う。中身は「PR の合否の材料になる記録(例外承認・停止の解除)は、**記名者本人の認証された操作**で成立したことを、**PR の時点で機械が確かめる**。他者の承認で代えない」。この要件を置いたうえで、R-2 の受け皿を決める

### 理由

1. §0 のとおり、残る承認は 3名以上の体制で判定される側の書き足しを塞げない。これを統制と位置づけ直す案(内部 §7 c 論点2「材料の取り込みの統制」)は、効かない門に統制の名を与えることになり、信頼性の判断として誤り
2. 逆に、承認を外して何も足さない案は、2名・相互の体制で実際に効いていた門を外す。条項を字義どおり降ろすだけでは H-2 の経路が開く
3. 求めるべきは「誰か他の人が承認したこと」ではなく「記名者本人がしたこと」である。これは ADR-0070 の向き(他者の承認は事務)と矛盾しない。むしろその一般化である

### 体制ごとに回るか

- 1名: 例外の承認者が PR の作成者でない要件(`check-pr.mjs:466`)は現行のまま残るので、1名の自己例外は外部確認者を要する。外部確認者は**例外そのもの**を判断する立場になり、形骸の取り込みの承認ではなくなる
- 2名・相互: 記名者本人の操作が要件になるので、PR を誰のアカウントで開いても同じ強さで塞がる
- 3〜9名・10名以上: 第三者の形骸の承認で通る経路が消える

### 譲れない点

- 例外承認・停止の解除の真正性を、**名前の照合だけで済ませない**。PR の時点で、プラットフォームが認証した操作者を確かめる
- 他者の承認を、例外承認・停止の解除の裏づけに数えない(形骸の承認を統制と書かない)

### 採らない案

- 残る承認 1 件を「材料の取り込みの統制」と位置づけ直し、IMPL-0124 を意図した状態とみなす案: 3名以上で効かない門を統制と開示することになる
- 条項を「記名者以外の承認を課す」へ反転する案: ADR-0070 が除いた形骸の承認(`:53`)を、例外承認・解除のたびに全体制で再発させる

### 反論されうる点

- 「2名・相互では残る承認が効いている。補う要件の実装が済むまで外すべきでない」: 同意する。R-2 の受け皿が実装されて照合が delivered になるまで、ルールセットの承認は外さない(移行の順序の問題であり、向きの問題ではない)
- 「記名者本人の操作も、認証情報の共有の下では AI の操作と区別できない」: 正しい。§0 のとおり前提として扱い、R-2・R-4 で塞ぐ手段(名義の分離、または本人の名義の操作への人の確認)を要件にする

## R-2 例外承認の台帳と停止の解除の受け皿

### 結論

- **a3 を採る**。例外承認と停止の解除の受け皿を、**対象の PR の上の、記名者本人のレビュー**(宣言行つき。状態は APPROVE か COMMENT)へ広げる。`check-pr.mjs` がレビューを API で読み、次を確かめる
  - レビューの提出者のアカウントが、名簿の人の `accounts` に対応し、その人が権限の席(例外承認: 承認の権限者。停止の解除: 層1 の項目4 の受容者)の責任者であること
  - 例外承認では、提出者が対象の PR の作成者・作成を指示した者でないこと(現行の欄の要件を保つ)
  - 停止の解除では、提出がラベルを付けた日時より後であること。見解を退けた解除の上申先と日付が宣言の中にあること
  - レビューの本文が提出者以外に編集されていないこと(GitHub は書き込みの権限を持つ者が他人のコメントを編集できる。GraphQL の `editor`・`lastEditedAt` で確かめる。**実機で未確認**)
- 台帳(`docs/debt-ledger.md`)は**登録簿として残す**。行は人が書き足すのでなく、マージの契機で `record-copy.yml` がレビューの写しを記録用ブランチへ置き、出荷の PR が台帳の行として運ぶ(7.3 の記録の要求は台帳で満たす)。台帳の行を PR の合否の材料に使うのはやめる
- これにより、**例外承認・停止の解除のための記録だけの PR が無くなる**。残る記録だけの PR は出荷の PR だけになる(R-3)
- a1(records への移設のみ)は採らない。a2(署名コミットで本人の操作を確かめる)は、a3 を使えないプラットフォームでの代替として残す

### 理由(現場)

1. **待ちが消える**。現行は、停止の解除が「解除の記録の PR を開く → 他者の承認を待つ → マージ → 対象の PR の gate-g5 を再実行」の4段で、解除の時点が承認者の都合に依る(内部 §5、7.11 の解除の権限と食い違う)。a3 は対象の PR へレビューを1件出せば済み、gate-g5 は `pull_request_review` の契機で再実行できる
2. **一つの台帳ファイルへの同時の追記が消える**。10名以上で例外承認が並行すると、`docs/debt-ledger.md` を変える PR どうしが衝突し、直列化する。現場では衝突の解消に AI の担い手が手を入れ、そのたびに承認がやり直しになる(`dismiss_stale_reviews_on_push: true`)。a3 では対象の PR ごとに閉じる
3. **形骸の承認が実質の判断に変わる**。1名+外部確認者では、外部確認者は「台帳の PR の取り込み」ではなく「この例外そのもの」をレビューとして出す。中身を見ない承認が、中身を見る承認へ置き換わる
4. **判定される側の書き足しを、人数に依らず塞ぐ**。提出者の識別はプラットフォームが認証し、判定される側は他人の名義でレビューを出せない。§0 の 3名以上の穴も塞がる
5. 作成者本人でも COMMENT のレビューは出せる(`ci-gates.md:652` の実機確認、`G-4.md:22`)。1名の体制でも様式が成立する

### 判定される側の書き足しをどう塞ぐか(案ごと)

| 案 | 塞ぎ方 | 現場の評価 |
| --- | --- | --- |
| a3 対象の PR の上の記名者本人のレビュー | 提出者の識別(プラットフォームの認証)と名簿・席の照合。本文の他者による編集の検出 | **塞がる**。ただし認証情報の共有の下では AI が本人の名義でレビューを出せる → 下の「譲れない点」の名義の要件が要る |
| a1 records への移設、check-pr が records を読む | 塞げない。records は書き込みの権限者とジョブのトークンが追記できる(EV-0185)。照合は名前だけ | 現行より弱い。2名・相互で効いていた門も消える |
| a2 a1 + 署名コミットの検証 | 署名の鍵と名簿のアカウントの結び付き | 1〜2名で署名の設定は普及していない。しかも AI が本人の端末で動くと**同じ鍵で署名する**ので、署名は人の操作を示さない。a3 と同じ前提(名義の分離)が要るうえに手間が多い |
| 現行(基底へ記録だけの PR、承認 1 件) | 2名・相互で、判定される側が自分で開いた場合だけ塞がる | §0 のとおり体制で効き目が変わる |

### 体制ごとに回るか

- 1名(checks-only): 例外承認は外部の人が対象の PR へレビューを出せば成立する。外部の人がいなければ例外承認は使えない(現行と同じ。未解決事項・前提の受容の経路を使う)。停止の解除は本人が層1 の項目4 の受容者としてレビューを出す。申し立てた者と解除した者が同一の場合の記録(`check-pr.mjs:505`)は現行どおり
- 1名+外部確認者: 外部確認者は対象の PR を見て例外を判断する。手間は「別の PR を承認する」から「対象の PR にレビューを1件出す」へ変わり、増えない
- 2名・相互: 相手の PR にレビューを出す。G-6 のレビューと同じ画面で済む
- 3〜9名: 権限の席の責任者が対象の PR にレビューを出す。第三者の形骸の承認は経路から消える
- 10名以上: 例外承認の件数が多い組織ほど、台帳の衝突が消える効果が大きい。席の責任者が複数いる場合は名簿の席で照合する

### 譲れない点

- **AI の担い手が、記名者本人の名義でレビューを出せない状態を、構成の要件にする**。手段は2つのどちらか。(i) AI の担い手を人と別の名義(専用のアカウントか App)で動かす。(ii) 本人の名義で動かすなら、レビューの提出(`gh pr review`、`gh api` での reviews の POST)を、エージェントの権限設定で人の確認(`ask`)にする。現行の `gh pr merge` の `ask`(`template/.claude/settings.json:57`)と同じ扱いにする。どちらも取れない構成は、例外承認・解除の帰属を「自己申告」として保証の開示へ出す
- 宣言行の書式を固定し、機械が読む。散文から推測で読み取らない
- 停止の解除は、**ラベルを外しただけでは解けない**現行の性質(`ci-gates.md` の停止の申し立て)を保つ
- レビューの写しはマージの契機で記録用ブランチへ置く(現行の `record-copy.yml`)。ホスティングの保持の期限で消える前に取る

### 採らない案

- a1(records への移設だけ): 判定される側の書き足しを塞げない。現行より弱い
- 台帳の行と a3 のレビューの両方を合否の材料にする二重化: 食い違ったときの裁定の規則が要り、現場では「どちらを直すか」で止まる。合否はレビュー、登録簿は台帳と役割を分ける
- Issue のコメントを受け皿にする案: 第4章の除外理由(コミットに固定されず削除できる、`gate-criteria.md:100`)がそのまま当たる

### 反論されうる点

- 「第4章 `:99` と ADR-0070 決定3 が、例外承認・解除の受け皿を様式に限っている」: 限った理由は「対象が PR として存在しない」ことである。例外承認と停止の解除は、対象が PR として存在する(どちらも `PR #<番号>` を対象に取る)。理由が当たらないので、受け皿の限定を改める。新 ADR で ADR-0070 決定3 の該当部分を置き換える
- 「レビューの本文は編集できる」: 他者による編集は検出して不成立にする。本人の編集は、マージの契機の写しで固定する。マージより前の本人の編集は、本人の意思の変更として扱ってよい
- 「COMMENT のレビューは `dismiss_stale_reviews_on_push` で消えないので、例外承認の後に判定される側が差分を足せる」: 例外承認は「どの基準を」「どこまで」免除するかを内容の欄に持つ。後から足した差分がその基準に触れたら、gate-g5 が再び失敗する(免除は名指しの基準だけに効く)。ただし、例外の内容が「この PR の規模の超過」のように差分の大きさに依る場合は、レビューの `commit_id` と現在の先端を比べ、先端が進んだら再提出を求める規則を足すかを、起草で決める(現場の意見は、規模・カバレッジのような差分の量に依る例外だけ再提出を求める)
- 「a3 は GitHub の API に依る。プラットフォームを選ばない標準に合わない」: 条項は「記名者本人の認証された操作」「PR の時点で機械が確かめる」までにとどめ、レビューという手段はテンプレート側の降ろし方にする。R-4 を参照

## R-3 出荷の PR の承認(H-1)

### 結論

- H-1 は**文言の誤りとして直す**。「出荷判定者が開き、出荷判定者本人が承認する」は GitHub で成立しない(外部 1.2「Pull request authors cannot approve their own pull requests.」)
- 出荷判定者の帰属の裏づけは、出荷の PR の承認ではなく、**記録用ブランチへ本人が push した G-7 の様式**と、**出荷の PR の上の出荷判定者本人のレビュー**(複製の検査の結果を確かめた旨の宣言行。開いた者が本人なら COMMENT、そうでなければ APPROVE)とする
- PR を開くのは人(現行どおり。`GITHUB_TOKEN` と PAT は採らない、`rulesets/README.md:85`)。誰が開いてもよい。出荷判定者以外が開いた場合は、出荷判定者が承認する。出荷判定者が開いた場合に付く他者の承認は、取り込みの事務として開示する
- 出荷の PR の承認 1 件は、team 以上の構成では残る。IMPL-0124 は**出荷の PR について** undelivered で表示し続ける(R-4)

### 理由(現場)

1. 出荷の PR の中身は、記録用ブランチの複製と品質レポートで、複製の一致は verify ジョブが機械で確かめる(`rulesets/README.md:79`)。人がこの PR で判断することは「検査の結果を見たか」だけで、判断の実体は G-7 の様式にある
2. 「出荷判定者以外が開く」を必須にすると、1名+外部確認者で AI 専用のアカウントを持たない構成では、外部確認者が出荷の PR を開く手間が増え、かつ外部確認者の承認が要る(作成者は承認できない)ので結局出荷判定者は承認できない。必須にしても何も強くならない
3. 出荷の PR のマージの遅れは、出荷そのもの(タグの push)を止めない。遅れても、記録が基底へ入るのが遅れるだけである。ただし「遅くとも G-7 で基底へ」(`gate-criteria.md:109`)を満たさない状態が続くので、遅れは見える化する

### 体制ごとに回るか

- 1名(checks-only): 本人が開き、COMMENT で宣言し、本人がマージする。承認は要らない。回る
- 1名+外部確認者: 本人が開き、COMMENT で宣言する。外部確認者の承認(事務)が要る。出荷1回につき1件で、頻度は低い。形骸の承認だが、事務と開示しているので統制と誤認されない。外部確認者の応答待ちの期間は `/pit` と次の出荷の集約に出す
- 2名・相互: どちらかが開き、出荷判定者が承認する。回る
- 3〜9名・10名以上: AI 専用のアカウントや出荷の当番が開き、出荷判定者が承認する。回る

### 譲れない点

- 成立しない手順を「記名者本人の操作」と書き続けない。`rulesets/README.md:79,81`、`ship-evidence.yml:245,257-259`、`template/README.md:142`、`recording.md:91` を同時に直す
- 出荷の PR の他者の承認を、出荷判定の裏づけに数えない

### 採らない案

- 出荷判定者以外が開くことを必須にする案: 理由 2
- 機械(`GITHUB_TOKEN`・App・PAT)に出荷の PR を開かせる、または承認させる案: 現行の不採用の理由(`rulesets/README.md:85`)を保つ。機械の承認を承認数に数える形は、2022 年に GitHub 自身が塞いだ抜け道であり、2026 年時点で数えられるかも報告が割れている(外部 4.3)
- 出荷の PR を App の bypass でマージする案: R-4

### 反論されうる点

- 「1名+外部確認者で、出荷のたびに形骸の承認が要る。ADR-0070 の趣旨に反する」: 反する。ただし外す手段は既定ブランチの強制層の縮小(bypass・承認数 0)しかなく、ADR-0070 決定7・ADR-0038 と衝突する。頻度が出荷1回に1件であることと、事務として開示されることから、残すほうが信頼性の損失が小さいと判断する。この判断は実測に基づかないので、根拠水準マーク(暫定)で開示する
- 「外部確認者が verify の結果を見る分は実質がある」: 認める。ただし標準の上は事務と書く(外部確認者は G-7 の判定者ではない)

## R-4 テンプレートの手段と採用者への委任

### 結論

| 手段 | 採否 | 理由(現場) |
| --- | --- | --- |
| `required_reviewers`(パス条件)で一律 0 + 足し戻し | **既定にしない**。採用者の選択としても勧めない | ユーザー所有のリポジトリで使えない(外部 1.3)。1〜2名の多くはユーザー所有。組み合わせの挙動は公式の記述も実機の確認も無い(外部 4.1)。一律 0 にすると、パターンの書き漏れのファイルは承認なしで入る(否定の向きの既定で、漏れが緩める側に倒れる) |
| bypass(App・人・`pull_request` モード) | **既定にしない**(ADR-0070 決定7 を保つ)。組織が選ぶ場合は `state:needs-platform` で統制の弱化として記録 | パスを見ない(外部 1.4)。「記録だけ」の判定が App の実装へ移り、その実装が新しい統制点になる。`exempt` は監査の記録を残さないので、どの構成でも採らない |
| App・Actions による承認 | **採らない** | 承認数に数えられるかが確かめられない(外部 4.3)。数えられたとしても、機械の承認で人の門を満たす形になる |
| 承認の強制を gate-g5 の検査へ移し、ルールセットの承認数を 0 にする | **採らない** | `pull_request` のワークフローは PR の側の定義で動くので、PR が検査そのものを書き換えうる。プラットフォームの承認数は PR から変えられない。強制層の縮小(ADR-0038) |
| CODEOWNERS の雛形を有効にする | 誘導層として**既定で有効にする方向で検討**(遮断に数えない現行の扱いは保つ) | 現行は雛形のままで誘導層すら効いていない(内部 H-3)。ただし a3 を採れば台帳・解除の所有者の行は不要になり、`docs/gates/`・`docs/records/` の出荷判定者の行だけが残る |
| a3 の照合(R-2)と、エージェントの権限設定でのレビュー提出の `ask` | **テンプレートで降ろす** | 本件で唯一、人数とプラットフォームのプランに依らず効く |

- `plan=adopter` とする範囲: **出荷の PR に残る承認 1 件の扱いだけ**を、プラットフォームの側にパス単位の承認規則を持つ採用者(Azure DevOps の自動レビュアのパスフィルタ、GitLab の Code Owners のセクションの `^`・`!`。外部 5.1・5.2)の実装に委ねる。GitHub の採用者には手段が無いので、GitHub の上では `scheduled`(プラットフォームの機能の変化を見直しの時期に確かめる)で undelivered を表示し続ける
  - 例外承認・停止の解除は adopter にしない。7.11 の停止の申し立ては採用者任せにできない登録簿の型(`impl-no-adopter.yaml:20`)であり、テンプレートで降ろせる(R-2)
- GitHub 以外のプラットフォーム: 条項は結果で書く。「PR の合否の材料は、記名者本人の認証された操作で成立し、判定される側が同じ変更で用意できない」「その確認を PR の時点で機械が行う」。手段(レビュー、署名、パス単位の承認規則)は書かない。Gitea の Unprotected file patterns(外部 5.3)のように記録のパスの直接の push を許す機能は、判定される側も直接 push できるので、それだけでは条項を満たさないと注記する

### 体制ごとに回るか

- 1〜2名(ユーザー所有のリポジトリが多い): `required_reviewers` もチームも使えない。a3 と権限設定の `ask` だけが効く。追加の費用はレビュー1件
- 3〜9名(組織のリポジトリ、Team プラン): `required_reviewers` は使えるが、上の理由で既定にしない
- 10名以上: 同上。組織が bypass を選ぶなら、統制の弱化の記録と、App の「記録だけ」の判定の検査を誰が持つかを D-0 に書く

### 譲れない点

- 既定ブランチの強制層を縮小する手段(bypass・承認数 0・`exempt`)を、記録の流れを楽にするために既定へ入れない
- `plan=adopter` にするなら、採用者に実在する手段があることを示す(crosscheck F-9 の裁定「採用者にも手段が無い」を、プラットフォームごとに分けて書き直す)

### 採らない案

- 表のとおり。加えて「GitHub 以外のプラットフォームを推奨する」記述: 本標準はプラットフォームを選ばない

### 反論されうる点

- 「`required_reviewers` は組織のリポジトリでは強制層の手段であり、未確認を理由に退けるのは調査不足」: 実機で確かめれば採用者向けの手引きにはできる。ただし否定のパターンで緩める側へ倒れる構成は、パターンの書き漏れが統制の弱化になる。現場では強制層のパターンの保守を誰が持つかが決まらないまま放置されやすい
- 「出荷の PR を adopter にするのは、GitHub の採用者を見捨てている」: GitHub の上の手段が無いことを undelivered で表示し続ける。見えないまま済ませるより信頼性が高い

## R-5 付随のずれと記録

### 結論

| 項目 | 本件で直すか | 現場の意見 |
| --- | --- | --- |
| H-1(出荷の PR の自己承認) | **直す** | R-3 |
| H-5(`RECORD_PATHS` の範囲) | **直す** | `RECORD_PATHS` に層1・D-0・`PROCESS-PROFILE.md` が入っていると、統制を変える PR が「記録だけの PR」として変更の単位から外れる(`aggregate-evidence.mjs:1335-1337`)。承認者を減らす D-0 の変更が、記録と同じ扱いで集約を素通りしうる。判定記録(`docs/gates/**`・`docs/records/**`・台帳)と、統制の文書(層1・D-0・構成書)を分ける。a3 の採用で台帳の扱いも変わるので、同じ変更で揃える |
| H-6(EV-0111 の差し替え条件) | **直す** | 「記名者以外の者が記録を書き換えた件数」に、(i) 記名者以外の者が例外承認・解除を**書き足した**件数(a3 の照合で不成立になった件数で数えられる)、(ii) 記録だけの PR の承認待ちの期間、(iii) 認証情報の共有の構成の件数(保証の開示から数えられる)を足す。追記は git の履歴で書き換えとして見えないので、今の条件では本件の論点を測れない |

| H-3(IMPL-0124 の降ろし先) | **直す** | a3 を採れば、IMPL-0124 は出荷の PR だけを指す。note を書き換え、例外承認・解除は新しい IMPL へ分ける |
| H-7(AI の担い手の名義) | **直す** | R-2 の譲れない点。`/process-init` に「AI の担い手は人と別の名義で動くか」を問う(または既定値を決め、`/process-change` の変化点に加える) |

### 新しい ADR・EV・IMPL(現場の提案)

- **ADR(新)**: 「PR の合否の材料は、記名者本人の認証された操作で成立させ、PR の時点で機械が確かめる」。ADR-0070 の決定3(受け皿の限定)の例外承認・停止の解除の部分と、決定6 の「現行どおり基底へ先に」を置き換える。決定7(bypass を既定にしない)は保つ。H-4 を本件で決めないことを明記する
- **EV(新、暫定)**: (a) 「対象の PR の上のレビューの提出者の識別が、人の操作を示す」という前提は、名義の分離か提出の `ask` に依る。単一の事例にも支えられていない。(b) 「出荷の PR の事務の承認を残すほうが、強制層を縮小するより信頼性の損失が小さい」という判断。(c) 本意見 §0 の体制ごとの効き目は推論で、採用者の実測が無い
- **IMPL(新)**: (1) `check-pr.mjs` が対象の PR のレビューから例外承認・停止の解除の宣言を読み、提出者・席・日時・編集者を照合する(target=gate-g5)。(2) エージェントの権限設定でレビューの提出を `ask` にする(target=agent-permissions 相当。`impl-targets.yaml` の登録を確かめる)。(3) `record-copy.yml` が宣言の写しを置き、出荷の PR が台帳の行へ運ぶ。(4) `RECORD_PATHS` の分割(target=evidence-aggregation)
- **IMPL-0124**: 出荷の PR に限って undelivered を保つ。`plan` は GitHub の上で `scheduled`(見直し時期にプラットフォームの機能を再確認)、他のプラットフォームの採用者向けに手段の所在を note へ書く

### 採らない案(本件の記録として残すもの)

- 残る承認 1 件を統制と位置づけ直す(R-1)
- records への移設だけ(R-2 a1)
- 署名コミットを既定の裏づけにする(R-2 a2。代替としては残す)
- 出荷判定者以外が開くことの必須化(R-3)
- `required_reviewers` の一律 0 + 足し戻しの既定化、bypass の既定化、`exempt`、機械の承認、承認の強制の検査への移管(R-4)
- 台帳の行とレビューの二重の合否の材料(R-2)

### 反論されうる点

- 「H-4 を分けるのは先送りである」: 先送りではなく、論点の対象が違う(判定記録の帰属と、統制の文書の改版の統制)。分ける理由と、本件で決めないことを ADR に書けば、「書かれていない」と「課さないと決めた」は区別できる
- 「H-5 を直すと、層1・D-0 の改版の PR が変更の単位に数えられ、リスク区分・検証方法の欄が要る。手間が増える」: 増える。統制の文書の改版を、記録と同じく素通りさせるより信頼性が高い

## 論点ごとの結論(1行)

- R-1: 「記名者以外の承認を課さない」は維持。誤りは ADR-0070 が台帳・解除の真正性の要件を欠いた側にあり、残る承認 1 件は 3名以上で効かない偶然の門なので統制と位置づけ直さず、「記名者本人の認証された操作を PR の時点で機械が確かめる」要件を新 ADR で補う
- R-2: a3(対象の PR の上の記名者本人のレビュー+宣言行を check-pr が提出者・席・日時・他者の編集で照合)を採り、台帳は登録簿として写しで運ぶ。AI が本人の名義でレビューを出せないこと(名義の分離か提出の `ask`)を譲れない要件にする。a1 は不採用、a2 は代替
- R-3: H-1 は文言の誤りとして直す。開くのは人なら誰でもよく、出荷判定者の裏づけは G-7 の様式と本人のレビュー。team 以上で残る承認 1 件は事務として開示し、IMPL-0124 を出荷の PR に限って undelivered で表示し続ける
- R-4: `required_reviewers` の一律 0+足し戻し・bypass・`exempt`・機械の承認・承認の検査への移管はどれも既定にしない。テンプレートは a3 と権限設定で降ろす。`plan=adopter` は出荷の PR を他のプラットフォームで扱う範囲に限り、条項は手段でなく結果で書く
- R-5: H-1・H-3・H-5・H-6・H-7 は本件で直す。H-4 は事実の記述だけを直し、層1 の改版の統制は別 Issue の会議体にかけ、本件で決めないことを ADR に明記する。新 ADR・暫定 EV 3件・IMPL 4件を起こす
