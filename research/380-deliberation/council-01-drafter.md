## 0. 起案の骨格

本件の議論を1つの区別に集約する。ADR-0070 は「判定記録だけのコミット」を一様に扱った。しかし基底ブランチへ入る記録には、働きの違う2種類がある。

| 区分(仮称) | 該当する記録 | 記録が働く時点 | 誤った帰属が入ったときの害 |
| --- | --- | --- | --- |
| **証跡の記録** | 様式(G-1・G-7・G-8・SG・PR でない判定)、承認レビューの写し、保証の開示(`docs/evidence/`) | 判定は既に別の場所で成立している。記録は後から確かめる材料。G-7 の集約(IMPL-0128)が事後に帰属を照合する | 開示に「自己申告」と出る。開示は事後でも働く |
| **効力を持つ記録** | 例外承認の台帳の行、停止の申し立ての解除、前倒しの SG、層1(項目4 が解除の権限者を定める)、D-0(緩める向きの決定の記名) | 基底ブランチへ入った瞬間に、G-5 の合否・権限者の照合を変える(`check-pr.mjs:7,481,499,981`) | 判定される側が自分の例外・解除・権限を差し込み、PR を通せる。事後の開示では取り消せない(マージ済み) |

ADR-0070 決定6 は、前者の性質(事後の照合で足りる)から導いた「記名者以外の承認を課さない」を、後者にも及ぶ文で書いた。後者については「現行どおり基底ブランチへ先に」とだけ残し、残る承認が担っている役割を論じなかった(内部 H-2)。**誤っているのは、条項の範囲と、残る承認を「事務」と呼んだ語である**。証跡の記録に関する決定の核(写しを機械で取り、記名者以外の判定を課さない)は正しい。

以下の案は、この区別を本文へ入れ、効力を持つ記録には「**効力を持つ前に、記名者本人の操作を機械が確かめる。確かめられない場合に限り、記名者と別のアカウントの人が帰属を確かめる**」を課す。

## R-1 条項の向き

### 結論

- 条項を**分割して見直す**。証跡の記録については「記名者以外の者の判定(内容の承認)を課さない」を維持する。効力を持つ記録については、ADR-0070 の「課さない」を撤回し、帰属の確認を効力の前に置く
- 残る承認 1 件を「取り込みの事務」と呼び続けない。役割を2つに分けて名づける
  - 証跡の記録の取り込み(出荷の PR): **転記の確認**。承認者は verify ジョブの結果だけを確かめる。判定ではない
  - 効力を持つ記録の取り込み(記名者本人の操作を機械が確かめられない場合): **帰属の確認**。承認者は、記録が記名者本人のものであることを確かめる(中身の妥当性は判定しない)。統制であり、事務ではない
- 新しい ADR-0106 で、ADR-0070 決定3(受け皿の限定)の一部と決定6(承認を課さない)の範囲、ADR-0057 の却下行「層1 の改版にも PR を課す」を置き換える

```markdown
### 判定記録を基底ブランチへ入れる操作

基底ブランチへ入る記録を、働きで2つに分けます。

| 区分 | 該当する記録 | 帰属を確かめる時点 |
| --- | --- | --- |
| 証跡の記録 | 様式(G-1・G-7・G-8・SG、対象が PR でない判定)、承認レビューの写し、保証の開示 | 出荷判定(G-7)の集約。事後でよい |
| 効力を持つ記録 | 例外承認の記録、停止の申し立ての解除、前倒しで要る SG の記録、品質保証の方針と受容の基準(層1)、D-0 の決定の記名 | 記録が判定・照合に効力を持つ前 |

効力を持つ記録は、基底ブランチへ入った時点で、変更の検査の合否と権限者の照合を変えます。事後の開示では、既にマージされた変更を取り消せません。

- 証跡の記録を基底ブランチへ入れる操作に、**記名者以外の者の判定を課さない**。記名者本人の操作(署名コミット、記名者本人の push、または記名者のレビュー)を、記名の帰属の裏づけとする。裏づけの無い記録は、記名が自己申告であることを保証の開示へ出す(後掲 G-7「保証の開示」)
- 証跡の記録を運ぶ変更に、ホスティングの規則が一律に承認を課す場合、その承認は**転記の確認**である。承認者は、複製が置き場の記録と一致することを機械の検査の結果で確かめる。記録の中身を判定しない。転記の確認を判定記録の欄にしない
- 効力を持つ記録は、**効力を持つ前に、記名者本人の操作で帰属を裏づける**。裏づけは、記名者のアカウントによる操作を機械が確かめられるものに限る。記名の名前の一致だけを裏づけに数えない。記名者のアカウントが、記録を足した変更の作成者または最後に push した者のアカウントと同じ場合は、本人の操作として確かめられたものに数えない
- 前項の裏づけを機械が確かめられない場合は、**記名者と別のアカウントを持つ人による帰属の確認**を、効力の前に経る。帰属の確認は、記録が記名者本人のものであることを確かめる統制であり、取り込みの事務ではない。確認者は記録の中身の妥当性を判定しない。帰属の確認者を置けない体制では、記名が自己申告であることを、効力を持った記録ごとに保証の開示へ出す
- 判定記録と写しを基底ブランチへ入れるのは、**遅くとも出荷判定(G-7)** である。効力を持つ記録は、効力が要る時点より前に入れる
- 既定ブランチの強制層を、写しのために縮小しない。置き場の形(既定ブランチの外のブランチ、CI の成果物)は、準拠テンプレートが定める
- **採らない形**: 効力を持つ記録を、記名者本人の操作を確かめないまま承認の要件だけを外して入れる構成(パス単位の承認の免除、bypass、検査を掛けない別ブランチへの移設)。判定される側が自分の例外・解除を足して自分の変更を通す経路を開くためである
```

### 案(ADR)

`src/content/docs/adr/0106-records-with-effect-and-attribution-before-effect.md`(仮題「効力を持つ記録は、効力の前に帰属を確かめる」)。

- 決定1: 基底ブランチへ入る記録を「証跡の記録」と「効力を持つ記録」に分ける(上表)
- 決定2: 証跡の記録には記名者以外の者の判定を課さない(ADR-0070 決定6 の核を保つ)。ホスティングが課す承認は転記の確認と呼ぶ
- 決定3: 効力を持つ記録は、効力の前に記名者本人のアカウントの操作で裏づける。できない場合は別アカウントの人が帰属を確かめる。いずれもできなければ記録ごとに開示する
- 決定4: 例外承認と停止の解除の受け皿に、対象の PR の上の記名者本人のレビューを加える(R-2)
- 決定5: 出荷の PR の承認者を出荷判定者本人と書かない(R-3)
- 決定6: 層1・D-0 の改版を効力を持つ記録に数え、ADR-0057 の却下行「層1 の改版にも PR を課す」の判断を、層1 が機械の照合に読まれる構成について置き換える(R-5 H-4)
- 置き換える範囲: ADR-0070 決定3 の「例外承認、停止の解除」を様式に限る部分、決定6 の「記名者以外の承認を課さない」の範囲(効力を持つ記録に及ぶ部分)と「他者の承認は事務」の語。ADR-0057 の当該の却下行。ADR-0070・0057 の本文は書き換えず、`index.md` と各 ADR の状態欄の扱いは ADR 運用ルールに従う(「一部置き換え: ADR-0106」)

### 理由

1. **既存の統制の実態に一致させる**。台帳と解除を既定ブランチの先端から読む設計(ADR-0078、`ci-gates.md:153,162`)の理由は「判定される側が同じ変更で材料を用意できない形にする」である。ところが PR の時点の照合は名前だけ(`check-pr.mjs:464-466`)で、その理由を実際に支えているのは「基底ブランチへ入る前に誰かの承認がある」ことである(内部 H-2)。条項が「その承認は事務」と書いたまま放置すると、次に誰かが字義どおり承認を外したとき(パス単位の免除、bypass)、統制が消える。条項が統制の所在を誤って記述していることが、信頼性の欠陥である
2. **ADR-0070 の動機を保つ**。ADR-0070 が解消したのは「承認者が判定材料を持たないまま中身を承認する」構造(`0070:53`)である。帰属の確認と転記の確認は、承認者の判断の対象を、承認者が確かめられるもの(本人のものか、検査が通ったか)に限る。中身を見ない承認ではなく、見るべきものが定まった承認になる
3. **先例の型がある**。ISO 9001 7.5.3 や電子記録の規制は、承認の記録に「誰が承認したかを特定できること」を求めるが、承認者の数を求めない。帰属を本人のアカウントで裏づける要求は、第4章の保全の条件(アカウントの数値の識別子)の延長である。外部の調査では、GitHub もパス単位の免除を持たず「承認の件数はブランチに属し、パスは承認者の選び方にだけ効く」設計である(外部 §3・考察)。本案はホスティングの設計と逆らわない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. 条項をそのまま維持し、IMPL-0124 を undelivered のまま表示し続ける | 降りていないのではなく、**降ろすと統制が壊れる**規定を、降ろすべき規定として表示し続けることになる。計画(plan=scheduled)の終点が統制の除去になる。降りていない規定の表示は、降ろすべき規定に限って意味を持つ |
| B. 条項を撤回し、すべての記録の取り込みに記名者以外の承認を課す | ADR-0070 が解消した「中身を見ない承認」(`0070:53`)を、証跡の記録にも戻す。1 判定ごとの記録 PR と他者の承認(旧 `/gate`)へ逆行する。ADR-0057・0058・0067 との食い違いも戻る |
| C. 残る承認を「材料の取り込みの統制」と言い換えるだけで、帰属の裏づけを足さない | 語を直しても、承認者が何を確かめるかが定まらない。2名・相互の体制では承認者が判定される側であることが多く(内部 §5)、「誰かの承認」が帰属を確かめない |
| D. 効力を持つ記録だけを条項の対象外と書き、要求を置かない | 「書かれていない」と「課さないと決めた」の区別がつかない。帰属の要求が空白になり、名前だけの照合が残る |

### 反論されうる点

- **「区分が増え、読み手の負担が増す」**: 2区分の表を節の冒頭に置き、効力を持つ記録を列挙で閉じる。列挙に無い記録は証跡の記録として扱う(既定は軽い側)。列挙の追加は効力を持つ記録を増やす向き(厳しくする向き)の変更にする
- **「帰属の確認は、1名+外部確認者の体制で外部確認者の負担になる」**: 負担は残る。ただし本案では、AI の担い手が別のアカウントを持つ構成なら外部確認者は不要になる(記名者本人のレビューで足りる)。認証情報を共有する構成に限り外部確認者の帰属の確認が要る。この構成は、AI の操作と記名者の操作を機械が区別できない構成であり、人の確認を省く根拠が無い
- **「ADR-0057 の『記名の意味と二重になる』を破る」**: 帰属の確認者は中身を承認しないので、記名と二重にならない(R-5)
- **「証跡の記録にも、判定される側の追記の経路がある(EV-0185)」**: その通り。証跡の記録の改ざんは #379 で扱う。本案は効力を持つ記録だけを効力の前の確認へ移し、証跡の記録は事後の照合のままにする。#379 の結論と独立に成り立つ

## R-2 例外承認の台帳と停止の解除の受け皿

### 結論

- **内部案 a3 を採る**。ただし条件を2つ足す。(i) レビューのアカウントが、対象の PR の作成者・最後に push した者のアカウントと異なること。(ii) レビューの `commit_id` が PR の head と一致すること
- 例外承認の台帳の行は、**対象の PR の中で足してよい**ことにする。行の効力は台帳の行ではなく、承認した者本人のレビューから来る。台帳の行は 7.3 要求事項4 の登録と追跡のために残し、機械がレビューとの一致を確かめる
- 条件 (i) を満たせない構成(認証情報の共有)と、対象が PR でない例外・解除では、現行の「基底ブランチへ先に入れる記録の PR」を残す。その PR の承認は**帰属の確認**(R-1)
- a1・a2(records への移設)は採らない

### 理由

1. **帰属がアカウントに結び付く**。名前の照合(現行)は、判定される側が承認者の名前を書けば通る。レビューは記名者のアカウントでしか出せない。判定される側は、記名者の認証情報を持たない限り材料を用意できない。ADR-0078 の理由を、現行よりも直接に満たす
2. **記録だけの PR が消える**。対象の PR の中で効力が完結するため、別の PR の承認待ち(1名+外部確認者で解除が外部確認者の応答に依る問題。内部 §5)が無くなる
3. **1名でも成立する範囲がある**。AI の担い手が別のアカウントで PR を開く構成では、記名者本人(作成者でない)がレビューを出せる。作成者本人でも COMMENT は出せる(`ci-gates.md:652` の実機確認、`G-4.md:22`)が、条件 (2) により作成者本人のレビューは数えない。作成者と記名者が同じアカウントのとき、そのレビューが本人によるものか AI によるものかを機械は区別できないためである
4. **承認の後の push で失効させる**。例外承認は「この変更」に対する承認であり、承認の後に中身が変われば対象が変わる。G-2〜G-4 の `commit_id == head` の検査(ADR-0070 決定4)と揃える

## R-3 出荷の PR の承認(H-1)

### 結論

- **事実の誤りを直す**。「承認者: 出荷判定者本人」(`rulesets/README.md:79`、`ship-evidence.yml:245,257`、`template/README.md:142`、`recording.md:91`)は、出荷判定者が PR を開く手順と両立しない(外部 §1.2「Pull request authors cannot approve their own pull requests」)
- 出荷の PR は**証跡の記録の運搬**である。中身は機械の複製で、verify ジョブが記録用ブランチとの一致を検査する。G-7 の判定は `records/gates/` の様式(出荷判定者本人の push)で成立している。したがって承認は**転記の確認**であり、承認者は出荷判定者である必要が無い
- 既定: **出荷判定者が PR を開く**(人の操作で gate-g5 と verify が起動する)。承認を課す構成では、**出荷判定者以外の書き込みの権限を持つ人が、verify の成功を確かめて承認する**。checks-only の構成では承認は無い
- AI の担い手が別のアカウントを持つ構成では、そのアカウントが PR を開き、出荷判定者が承認してもよい(任意)。いずれの形でも、承認を判定に数えない

### 案(本文)

`gate-criteria.md` 節「判定記録を基底ブランチへ入れる操作」(R-1 の書き換え後)の「転記の確認」の項に、1文を足す。

```markdown
  出荷判定(G-7)の記録を運ぶ変更では、承認者が出荷判定者本人である必要は無い。G-7 の判定は様式で成立しており、運ぶ変更は判定ではない。出荷判定者が自ら開いた変更を、本人が承認できないホスティングがあるためである
```

| CODEOWNERS + `require_code_owner_review` | 既定を変えない(team.json は false のまま)。所有者は通知の宛先 |
| 対象の PR の上の記名者本人のレビュー(R-2) | **採る**(テンプレートの既定) |
| plan=adopter | **使わない**。IMPL-0124 は R-1・R-3 の書き換えで規定そのものが変わる(下記) |

本文には、プラットフォームを選ばない形で、次の2点を書く。(1) パス単位の承認規則・免除を持つホスティングでは、**証跡の記録だけを変える変更**に限り、承認の免除を構成してよい。(2) 効力を持つ記録を変える変更を、免除の対象に含めてはならない。

### 案(本文)

`ci-gates.md:634-645` の節(R-1 の挿入先 4)の末尾に、次を足す。

```markdown
- パス単位で承認の規則を変えられるホスティング(自動レビュアにパスの除外を持つもの、Code Owner の区分を任意にできるもの、列挙したファイルだけの変更に直接の取り込みを許すもの)では、証跡の記録の置き場だけを変える変更に限り、承認を課さない構成にしてよい。効力を持つ記録(第4章)の置き場を、その範囲に含めてはならない
- パス単位の規則を持たないホスティングで、承認の件数を一律に下げてパスの条件で足し戻す構成、特定の主体に規則を素通りさせる構成(bypass)は、本標準の既定にしない。組む場合は、強制層の縮小として記録する([ADR-0038](/process-compass/adr/0038-detection-handoff-of-control-weakening/))。監査の記録を残さずに規則を素通りさせる指定(GitHub の `exempt`)は、効力を持つ記録の経路に用いてはならない
- 機械(ジョブのトークン、アプリ)による承認を、承認の件数に数えない。承認数に数えられるかがホスティングの設定と版で変わり、2026-11 時点で報告が割れているためである
```

`exempt` の禁止は新しい規範なので IMPL を付ける。

```markdown
<!-- impl IMPL-0416 target=rulesets state=delivered check=manual note="効力を持つ記録の経路に、監査の記録を残さない素通り(exempt)と、承認の件数を一律に下げてパスで足し戻す構成を用いない。準拠テンプレートのルールセットは bypass_actors を持たず、required_reviewers を置かない。採用者が改めた構成は env-check の所見(既定ブランチの bypass actor)に出るが、合否にしない。確かめる者: AI維持管理者(ルールセットを改める変更のレビューで確かめる)" -->
```

### IMPL-0124 の扱い

- R-1 の書き換えで、IMPL-0124 が追う規定(記名者以外の承認を課さない)は、「証跡の記録に記名者以外の者の判定を課さない」へ変わる
- 準拠テンプレートでは、様式と写しは `records` へ承認なしで入り(IMPL-0356 の構成)、出荷の PR の承認は転記の確認として案内される(IMPL-0414)。記名者以外の者の判定は課されていない
- したがって IMPL-0124 を、note を新しい規定に合わせて改め、`state=delivered check=manual` にする案を出す。識別子は保つ(同じ規定の改訂であり、削除ではない)。降りていない規定の表示から外れることは、規定が変わった結果であり、表示を消すための言い換えではないことを ADR-0106 に書く

```markdown
<!-- impl IMPL-0124 target=rulesets state=delivered check=manual note="証跡の記録を基底ブランチへ入れる操作に、記名者以外の者の判定を課さない。準拠テンプレートは様式と写しを記録用ブランチ records(pull_request の規則を持たない)へ置き、出荷の PR で基底ブランチへ運ぶ。出荷の PR に付く承認は転記の確認(verify の結果を確かめる)であり、判定記録の欄にしない(ADR-0106。#380 で規定を改めた)。確かめる者: AI維持管理者(ルールセットと rulesets/README を改める変更のレビューで確かめる)" -->
```

### 理由

1. `required_reviewers` は、ユーザー所有のリポジトリで使えない(外部 §1.3)。準拠テンプレートの利用者の多い 1〜2 名の個人所有の構成で成り立たない。動作も未確認(外部 §4.1)。パターンの誤りで製品のコードの承認が消える向きに壊れる。R-2・R-3 の後、免除を要する記録の PR がほぼ残らないため、この危うさを負う理由が無い
2. bypass はアクター単位でパスを見ない(外部 §1.4)。「記録だけ」の判定が App や CI の実装に移り、その検査自体が新しい統制点になる。`exempt` は監査の記録を残さず、統制が作動したことを後から示せない
3. 機械の承認は 2022 年に GitHub 自身が抜け道として塞いだ経緯があり(外部 §4.3)、2026 年時点で数えられるかの報告が割れている。数えられるかどうかに依る条項は書けない
4. 他のホスティングにはパス単位の規則がある(外部 §5)。本標準はホスティングを選ばないため、許す範囲(証跡の記録)と許さない範囲(効力を持つ記録)を性質で書けば足りる

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| `required_reviewers` の構成を、組織所有のリポジトリ向けの選択肢として準拠テンプレートへ同梱する | 動作が未確認(外部 §4.1・§6)。同梱すると推奨と読まれる。実機で確かめた記録が出てから、別の Issue で扱う |
| IMPL-0124 を `plan=adopter` にする | 採用者に勧められる手段が bypass(統制の弱化)しか無い(crosscheck F-9、`crosscheck.md:186`)。既定でない構成を採用者に勧める形になる |
| IMPL-0124 を undelivered のまま残す | R-1 の採らない案 A と同じ |
| IMPL-0124 を削除して新しい番号を振る | 同じ条項の範囲の改訂であり、台帳の履歴を追えるほうが監査に資する |

### 反論されうる点

- **「IMPL-0124 を delivered にするのは、規定の言い換えで未達を消す行為だ」**: 最大の論点になると見込む。応答は2つ。(1) 規定の変更は、統制の所在の誤りを直すという独立の理由(R-1)から来ている。(2) 変更後の規定が求めるもの(記名者以外の者の判定を課さない)は、テンプレートで実際に満たされている。代わりに新しく課した要求(効力の前の帰属の確認、IMPL-0413)は undelivered で表示する。表示される未達の総量は減らない
- **「他のホスティングでのパス単位の免除を許すと、範囲の誤りが起きる」**: 範囲を効力を持つ記録の列挙で閉じ、それを含めることを禁じる。範囲の確かめは、ホスティングごとに採用者の env-check 相当で行う(準拠テンプレートは GitHub だけを持つ)

## R-5 付随のずれと記録

### H-4 層1 の改版と直接の push の禁止 — 本件で直す

**結論**: 層1 と D-0 は、効力を持つ記録に数える(R-1 の表)。層1 の項目4 は停止の解除の権限者を定め、`check-pr.mjs:499` が既定ブランチの層1 から読む。判定される側が層1 の項目4 を書き換えて自分を権限者にできれば、解除の統制が外れる。ADR-0057 の却下行「層1 の改版にも PR を課す」(`0057:509`)の判断は、層1 が機械の照合に読まれる現行の構成と合わない。準拠テンプレートは実際には直接の push を止めており(`rulesets/README.md:23`)、文書と実装が食い違っている。

**案**:

- ADR-0106 決定6 で、ADR-0057 の当該の却下行の判断を置き換える。要求は PR そのものではなく「効力の前の帰属の確認」(R-1)。PR を経る構成では、記名者(層1 の記名者・D-0 の決定者)本人のアカウントのレビュー(作成者・最後に push した者と別)で裏づけ、できなければ別アカウントの人の帰属の確認を経る。帰属の確認者は中身を承認しないので、「記名の意味と二重になる」(ADR-0057 の却下理由)に当たらない
- 本文: 第4章の R-1 の表に層1・D-0 を挙げる(挿入済み)。層1 の規定の所在(第6章 テンプレ11、または第1章の品質保証の層の節)で「層1 の改版を記録だけのコミットとして PR を課さない」と書いた箇所があれば、同じ趣旨へ改める(本起案では所在を全数で確かめていない。反映の担当が `grep '層1 の改版'` で洗う)
- テンプレート: `template/CLAUDE.md` のブランチとコミットの節「記録だけのコミットには要らない」は、トレーラ `Risk`・`Verification` の要否の規則であり、層1 の扱いとは別である。注記で「記録だけのコミットも既定ブランチへは PR で入る(ルールセットが直接の push を止める)」と補う
- check-pr は、層1 と D-0 を変える PR で、記名者本人のレビュー、または作成者でない人の承認があることを確かめる(現行の承認 1 件の構成では後者が成り立つ。checks-only では成り立たないので開示へ)。マークは IMPL-0415 に含める

**採らない案**: 層1 を記録用ブランチへ移す(check-pr が読む材料を書き換え可能な場所へ移す。a1 と同じ理由)。層1 の改版を PR なしの直接 push に戻し、ルールセットに例外を作る(パス単位の免除が無く、bypass になる)。

### H-5 RECORD_PATHS の範囲 — 本件で直す(範囲を狭めるのではなく、用途を分ける)

**結論**: `RECORD_PATHS`(`aggregate-evidence.mjs:1278`)の用途は「製品の変更に数えない」の識別であり、条項の「判定記録だけ」とは別の概念である。両者を一致させようとして `RECORD_PATHS` を狭めると、層1・D-0・台帳の改版が製品の変更に数えられ、別の欠落を生む。**用途を分けて名づける**。

**案**:

- `RECORD_PATHS` はそのまま残し、コメントを「製品の変更に数えない置き場。承認の要否・帰属の確かめ方とは別」に改める
- 新しい一覧 `EFFECTIVE_RECORD_PATHS = ['docs/debt-ledger.md', 'docs/quality-assurance-policy.md', 'docs/D-0-governance.md']` と、`docs/gates/**` のうちゲート欄が「停止の解除」または前倒しの SG の様式を、効力を持つ記録として識別する。集約は、これらを変えた PR・コミットについて、記名者本人のアカウントの操作(レビュー・push・署名)か帰属の確認(作成者・最後に push した者でない人の承認)の有無を照合し、無ければ保証の開示の項目1 へ「効力を持った記録の帰属が自己申告」として件数で出す
- 現行の IMPL-0128 の照合が様式だけを対象にし、台帳の行を対象外にしている(内部 §4)欠けを、ここで閉じる

```markdown
<!-- impl IMPL-0415 target=evidence-aggregation state=undelivered check=presence plan=scheduled issue=380 review=2027-01 note="効力を持つ記録(例外承認の台帳の行、停止の解除、前倒しの SG、層1、D-0 の決定の記名)を変えた変更について、記名者本人のアカウントの操作(対象の PR の上のレビュー、push、署名)または帰属の確認(作成者・最後に push した者でない人の承認)の有無を照合し、無いものを、効力を持った記録の帰属が自己申告である件数として保証の開示の項目1 に出す。IMPL-0128 の照合が様式だけを対象にしていた欠けを閉じる(単位: 行)" -->
```

挿入先は `gate-criteria.md` の IMPL-0128 の直後(現 `:133` の後)。

### H-6 EV-0111 の差し替え条件 — 本件で直す

**結論**: EV-0111 の対象を証跡の記録に狭め、差し替え条件に追記を足す。効力を持つ記録は EV-0221 で別に開示する。識別子は保つ(本文の暫定マークの改訂。ADR の本文ではない)。

**案**(`gate-criteria.md:115-121` を置き換える):

```markdown
:::caution[暫定 EV-0111 / 見直し 2027-04]
**対象**: 証跡の記録(様式・写し・保証の開示)を基底ブランチへ入れる操作に、記名者以外の者の判定を課さないという決定。
**根拠の水準**: E2(単一事例)。
**差し替え条件**: 出荷ごとの、(1) 記名者以外の者が証跡の記録を書き換えた件数、(2) 記名者以外の者が証跡の記録を足した件数(帰属の照合で、記名者本人の操作で裏づけられない記録の件数として集約が出す)。(1) が1件でもあれば、または (2) が出荷の記録の過半を占める状態が続けば、記名者本人の操作に限る条件を強める。

先例(ADR-0057 の層1 の改版に PR を課さない決定)は決定であり、実証ではありません。この先例のうち層1 の部分は ADR-0106 で置き換えました。支えているのは、記録の PR に判定者以外の承認者を課した構成で、承認者が中身を見ずに承認するしかなかった1件の訴えです。追記は git の履歴の書き換えとして現れないため、(2) は履歴ではなく帰属の照合で数えます。
:::

:::caution[暫定 EV-0221 / 見直し 2027-04]
**対象**: 効力を持つ記録に、効力の前の帰属の確認(記名者本人のアカウントの操作、それができなければ別のアカウントの人の確認)を課せば、判定される側が自分の例外・解除・権限を差し込む経路を塞げるという判断。帰属の確認者に中身の判定を求めなければ、中身を見ない承認の問題(ADR-0070 の背景)に当たらないという判断を含む。
**根拠の水準**: E1(推論)。
**差し替え条件**: 出荷の集約が出す、効力を持った記録のうち帰属が自己申告の件数(IMPL-0415)と、帰属の確認を経た記録のうち後に記名者が自分の記録でないと申し出た件数。後者が1件でもあれば、帰属の確認の手順(確認者が記名者へ確かめる手段)を規定する。

差し込みが起きた事例も、起きないことの測定もありません。現行の承認 1 件がこの経路を事実上塞いでいたことは、検査の読み方(既定ブランチの先端、名前の照合)からの推論です(research/380-deliberation の内部調査 H-2)。
:::
```

EV-0221 の挿入先は R-1 の書き換え後の節、効力を持つ記録の項の直後。追加後に `npm run evidence:write`、`npm run impl:write`、`npm run scope:write` を実行する。

### H-7(議題外。関連として記録する)AI の担い手のアカウント

R-2 の経路が使えるかは、AI の担い手が記名者と別のアカウントで PR を開くかに依る。構成(`process.config.json`)と `/process-init` の8問に、この入力があるかは確かめていない(内部 H-7)。**本件では直さない。別の Issue を起こす**ことを提案する。理由: 構成の入力の追加は `/process-change` の種別と D-0 の生成区間に及び、本件の論点(帰属の確かめ方)と独立に設計できる。それまでは、認証情報を共有する構成で R-2 の経路が使えず後退経路になることを、`recording.md` と保証の開示で示す。
