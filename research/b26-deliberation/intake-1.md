- `gh api repos/<repo>/actions/permissions/artifact-and-log-retention` は `{"days":90}` を返した。90 日は**ログと成果物**の保持期間である

- 残る欠けは、実行の記録の手による削除(UI・API)と、確かめていない長期の上限だけである。どちらも出力から区別できない

### 3.1 IMPL-0899 期日に間に合わない見込みの手続(#443)

- **方針**: (1) 結果は「手続を見込みの時点で始め、順序を入れ替えない」こと。証跡は既存の記録(2.10.5 の調整の記録、7.6 のレポート、7.3 の例外承認)に残る。新しい記録を課さない(ADR-0178)。(2) 該当しない(手続そのものの規定)。(3) 破られると、価値責任者が SC-M を守る順序を飛ばし、事業決裁者が知らないうちに期日か基準が動く。失うのは事業決裁者の判断の機会
- **降ろし方**: (c) 手引き。`handoff.md` の節「エスカレーション」のレポートの表の後に、note の3つの例を置く。(i) 7.6 の報告の項目1・2 に、手順1 で削った SC-B・SC-P と残りを書く例。(ii) 様式 04「価値責任者の調整」の理由に「2.10.6 手順1」と書く例。(iii) SC-M に触れる疑いが出たら 2.10.5 の表の行4 へ回す例。あわせて、順序(範囲 → 期日 → 基準)と、手順2 と SC-M の変更を価値責任者が決めないことを1行で書く
- **機械にする条件**: なし。順序の遵守は層の帰属を機械が読めない(ADR-0173 決定4)
- **マーク**: `state=delivered check=manual`。note の「降ろすまでは…」の文を外し、「確かめる者: 価値責任者(EV-0321)」を残す。`plan=`・`review=` を外す
- **反対の立場**: 手引きだけでは止まらない。→ 応答: 止める手段の候補(順序の機械の照合)は ADR-0173 決定4 が採らないと決めた。指示文であることは template の CLAUDE.md の規則の索引の印の無い行と同じ扱いで、新しい開示は要らない
- **採らない案**: 順序の違反を判定記録の並びから機械で検出する(層の帰属を読めない)。見込みの評価の記録の欄を足す(ADR-0178 が課さないと決めた)

### 3.3 IMPL-0175 確認を求める項目の表現・強調(#443)

- **方針**: (1) 結果は提示の並び・表現・強調が周期的に変わること。証跡は PR の本文(提示はそこに残る。ADR-0173 の採らない案「提示した版を記録する欄」のとおり、新しい記録を課さない)。(2) 該当しない。(3) 同じ見た目に慣れて確認が形骸化し、判定者の確認の質が落ちる。失うのは出荷判定者と事業決裁者が頼る G-6 の確認の実効性
- **降ろし方**: 二つに分ける
  - **強調**: (a) 機械。`review-order.mjs` が、並びと同じ種(ゲート・対象・ISO 週)から、太字で示す項目を1つ決めて出す(例: 出力の行頭に `**` を付ける位置を週ごとに変える)。項目の文と番号は変えない。R3 は回さない(並びと同じ)。決定可能(同じ種で同じ出力、週が変われば位置が変わる)
  - **表現**: (c) 手引き。`/gate` の SKILL.md 74 行の段落に、確認を求める**前置きの文の言い回し**(例: 「確かめましたか」と「根拠の所在を書いてください」)を判定記録の草案の起案者が週ごとに変えてよいこと、**基準の文そのものは変えない**ことを書く。表現の検査は作らない(意味を読む検査になる)
- **マーク**: `state=delivered check=manual test=…` は付けない形(manual)。note を「並びと強調は review-order.mjs(試験 test-review-order.mjs)、表現は手引き。確かめる者: G-6 の判定者」に改める。SKILL.md 74 行の「表現・強調は回さない」の文を改める
- **反対の立場**: 強調の位置を機械で回すのは細かい定義の追加ではないか。→ 応答: 欄も構成の値も足さない。既存の出力の見た目を変えるだけで、5.7.5 の条文が名指す要素である。条文の引く研究(2015年)は外観の変更だけが慣れに効いたとしており、強調は降ろす価値が最も高い
- **採らない案**: 表現を機械で言い換える(基準の意味が変わる危険。AI の言い換えは確定の記録に入る)。強調も手引きだけにする(外観の変更が人任せになり、条文の研究が効くとした部分が降りない)。提示した版を記録する欄(ADR-0173)

### 3.4 IMPL-0283 滞留の閾値の「G-1 で合意した値」(#443)

- **方針**: (1) 合意した値を超えた未完了の作業単位に通知が出ること。証跡は企画書の欄(G-1 の判定の材料)と Issue のコメント。(2) 該当しない。(3) G-1 で85パーセンタイルより短い値を合意した案件で、合意と実際の通知の基準が食い違い、担当者と価値責任者が滞留を知るのが遅れる。失うのは価値責任者の早期の警告(2.10.6 の見込みの評価の材料)
- **条件**(決定可能): `brief-estimates.mjs` に、企画書の欄「滞留と判定する経過時間」を `N日`・`N週間`・`N週` として読む関数を足す(`unitPeriodDaysOf` と同じ書式)。`flow-observation.mjs` は `docs/project-brief.md` を読み、値が読めればその日数を閾値に使う(このとき最小の標本数を求めない。合意した値は標本に依らない)。欄が空・「85パーセンタイル」の語を含む・企画書が無いときは、現行の85パーセンタイルを使う。値があるのに書式が読めないときは、85パーセンタイルを使い、注意に「合意した値を読めない」と出す。通知の文に、使った閾値の出所(合意した値 / 85パーセンタイル)を書く
- **様式**: 様式 06(と profiles の写し3つ)の欄に、第6章と同じ例 `<実測サイクルタイムの85パーセンタイル、または合意した値。合意した値は N日・N週間 で書く>` を置く。欄は新設しない
- **試験**: `test-flow-observation.mjs` に ng/ok を足す(合意した値 3日で、標本 0 件でも 4日経過の作業単位に通知する。2日経過は通知しない。書式が読めない値は注意を出して85パーセンタイルに戻る)。`test-brief-estimates.mjs` に読み取りの対を足す。どちらも既に gate-g5.yml から実行されている(結線の変更は要らない)
- **マーク**: `state=delivered check=machine test=template/scripts/gate/test-flow-observation.mjs`。note から「降りていない部分」の文を外す。「実物の GitHub では未確認」(workflow の契機)は残す
- **反対の立場**: 「または」は、短い方を採る読みもある。→ 応答: 議長は「G-1 で合意した値があればそれを使う」を採る。合意は案件がその値を基準にすると決めたことで、短い方を機械が選ぶと、合意より長い値を合意した案件で合意に無い通知が出る。どちらの読みかは note に開示する。G-1 の通過の後に企画書を書き換えた場合を機械は区別しない(企画書の版の照合は G-1 の判定記録の側の務め)ことも note に書く
- **採らない案**: 短い方を機械が選ぶ(上のとおり)。ステージ移行ゲートの判定記録にも同じ欄を足す(条文は G-1 だけを名指す。細かい定義が増える)。様式 04 に欄を足す
