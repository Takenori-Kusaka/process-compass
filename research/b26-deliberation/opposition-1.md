## 3.3 IMPL-0175: 異議あり(2 点)

**論拠 A: 強調を回すのは害が益を上回りうる。** 案は「太字で示す項目を週ごとに1つ決める」。確認を求める項目の太字は、読み手に「この項目が重要」という意味を付ける。重要度と無関係な項目に周期的に付けると、(1) 確認の注意を重要でない項目へ誘導する(G-6 の判定者が自分の確かめるべき項目を取りこぼす側に働く)、(2) 太字が意味を失うことを学ばせ、慣れを加速させうる。条文が引く研究(5.7.5 本文)は「外観を変えた場合にのみ耐性が生じた」であり、この研究の外観は警告の見た目全体で、「項目の一部を強調する」ことの安全性は示していない。intake §3.3 の応答は研究の読みを根拠にするが、研究の外観の変更を太字の位置の回転へ写す部分は推論である(根拠水準マークの対象。案はこの開示を挙げていない)。

加えて、`review-order.mjs` の出力は SKILL.md 74 行で「項目の文と番号は変わらず」と手引きされ、項目は箇条書き・基準の名で書かれる。`**` を行頭に付けると、`splitItems`(121 行)や後段の草案への貼り付け、機械が読む欄との境界で壊れうる。`test-review-order.mjs` の「文が変わらない」の期待を「印を除いて比べる」形に直す(§4.3)のは、検査を弱める方向の変更である。

**論拠 B: 「細かい定義を増やさない」(所有者 2026-11-16)との関係。** 欄は増えないが、強調の位置の決定規則(何を太字にするか、R3 の扱い、項目数 1 のとき)という新しい規則が決定可能な部分として加わる。案の「例: 行頭に ** を付ける位置を週ごとに変える」は例の域で、規則が未決のまま機械にすると、実装が新しい定義を作る。

**論拠 C: 表現の側は「してよい」で、条文は「変更する」。** 案の手引きは「起案者が週ごとに変えてよい」とする。条文の「周期的に変更する」を、任意の許可で降ろしたと表示するのは `delivered` として強すぎる。また条文の根拠(文言を変えても慣れは防げない)に照らすと、表現を回す手引きは効果の無い義務を adopter に課すことになる。Q-B26-1 の問いに自ら触れているのだから、先に所有者の裁定を待つ方が筋で、この段で表現を delivered に含めない方が正直。

**代案**: (1) 強調は機械で回さず、手引きに「確認欄の外観(罫・見出しの形・並びの区切り)を週ごとに変えてよい」までとする。(2) もしくは、並びだけが降りた状態を note で明示して `undelivered` のまま Q-B26-1 の裁定を待つ(条文と根拠の食い違いの疑いを自分で挙げた以上、先に解く)。(3) 強調を機械にするなら、決定規則(項目数・R3・番号の付け方)を先に議長が裁定し、試験の ng/ok に「太字が箇条書きの記号を壊さない」を入れる。

## 3.4 IMPL-0283: 異議あり(2 点)。方向は妥当

**論拠 A: 合意した値のとき最小の標本数を求めない点は妥当。** 現行コード(flow-observation.mjs 70〜74 行)は標本不足で全体を打ち切るため、S0 の初期に合意した値が働かない。合意は標本に依らない、という案の読みを支持する。

**論拠 B: 「合意した値があればそれ」は、実測の 85 パーセンタイルが合意より短い場合の通知を失わせる。** 条文は「または」で、どちらも閾値として認める。合意が 14 日で実測 85 パーセンタイルが 6 日なら、案では 6〜14 日の項目が滞留でなくなる。これは intake が自ら挙げた被害(短い合意でも通知が遅れる)の逆の向きで、害は「見逃し」の側に出る。滞留の通知の目的は早期の警告(2.10.6)であり、見逃しは誤通知より害が重い。案は「合意より長い値だと合意に無い通知が出る」と理由を述べるが、通知は「確かめてください」のコメント1回で、ラベルを変えない(ADR-0094)。誤通知の害は小さく、見逃しの害は大きい。この非対称を案は評価していない。

**代案**: 合意した値があり実測の標本も足りるときは、短い方を閾値とする。標本が足りなければ合意した値だけを使う。これは「または」の両方を満たす読みで、合意を置いた意味(基準を厳しくする側にも働く)を損なわない。この読みなら条文の解釈の開示も不要になる(「どちらかを超えた」と読むだけ)。少なくとも、どちらの読みを採ったかと採らなかった案(短い方)の記録(議長の裁定)を `research/b26-deliberation/` に残すこと。

**論拠 C: 「G-1 の後の書き換えを区別しない」害。** 企画書は G-1 の後も変わる文書である(ステージごとの更新)。合意した値を無断で長くすれば通知が止まり、判定記録の版との突き合わせは機械が行わない。案は「G-1 の判定記録の側の務め」とするが、その務めを担う検査が存在しない(check-g1.mjs は G-1 の通過時の検査)。この穴は note の開示だけでは「誰が失うか」への答えにならない。**代案**: 値の読み取り時に、企画書の当該欄の値が G-1 判定記録の「参照した版」と食い違うかを検出するのは意味の検査ではなく決定可能(版の一致)であり、少なくとも注意として出せる。出せないなら、根拠水準マーク(新規 EV)で、「G-1 後の書き換えは検出しない」ことを開示する。note の記述で済ませる案は ADR-0026 に弱い。

**付記**: 書式を 06 の 4 か所(本体+profiles 3 つ)へ揃える点は妥当。`unitPeriodDaysOf` を共用するなら、「N日」「N週間」以外(営業日、「2週」と「2週間」の混在、全角数字)で読めないと扱うことを試験の ng に入れること。

## 3.5 IMPL-0145: 異議あり(事実の誤り 1 件、state の上げ方 1 点)

**事実の誤り(直しの範囲が狭い)**: 案は 164・173 行の 2 か所の文を改めるとするが、保持期間に言及する出力の文は他にもある。enforcement-inventory.mjs の `読めない: …権限(Actions の読み取り)か保持期間の外の可能性があります`(158 行)と、`窓の中の実行の記録が 0 件でした(保持期間の外の実行は一覧に出ません)`(160 行)。観測(runs と jobs は 90 日の後も残る)が正しければ、この 2 文も事実に合わない。試験にも固定がある: test-enforcement-inventory.mjs 87 行は `/0 件でした\(保持期間/` を期待する(案は 90・99 行だけを挙げている)。直すなら 4 か所と、試験の 87・90・99 行を揃えること。直さずに delivered へ上げると、表示と実態が食い違う(CLAUDE.md の「表示と実態が食い違う高は直す」に当たる)。

**論拠: 観測 1 回(2 リポジトリ)で delivered に上げてよいか。** 観測は GitHub の仕様の確認として妥当だが、(1) 公式文書の記述でなく、2026-11-19 の応答の観察である。GitHub はログの保持と実行の記録の保持を別に扱うが、将来変わりうる。(2) 実行の記録の保持の上限は文書にあるか確認していない(案も「確かめていない長期の上限」と認めている)。(3) 組織・Enterprise の設定やプランで実行の記録の保持が異なる可能性がある。案は EV で開示するというが、`delivered` は「降りている」を意味し、台帳に出なくなる(implementation-marking.md の「降りていない規定の扱い」)。開示付きの根拠の弱い前提と、降りた表示を両立させるのは、「降りていない」の表示を消してから前提を見直す順になる。

**代案**: `delivered/machine` に上げてよいが、条件を付ける。(i) 公式文書(Actions の REST API・保持期間の説明)を出典台帳 `research/sources/` に 1 件登録し、EV の根拠にする。(ii) 注意の条件(最も古い実行が窓の始まりより後)は変えず、文は「実行が無かった」か「記録が消された(手動削除・上限)」のどちらかとして出す(案の文はこれに近い)。(iii) EV の見直し日は 2027-05 で妥当だが、差し替え条件に「実行の記録が保持期間で欠けた事例が 1 件でも現れたら undelivered へ戻す」と書く。

## 3.6 IMPL-0979: 異議あり(target の不整合・表示の強さ)

**論拠 A: マークの target と降ろし先が食い違う。** 現行マーク(exception-escalation.md 245 行)の `target=review-queue-control` は `.github/workflows/review-queue-control.yml` を指し、impl-targets.yaml の説明も IMPL-0979 を同ワークフローの置き場とする。案は手引き(handoff.md)で降ろすが、target はそのままか。降ろし先の実在は「ファイルの存在」しか検査されないので、手引きを消しても `lint:impl` は通る。台帳は「review-queue-control に降りている」と表示し、PR を持たないゲートの対応が workflow に無いことは note を読まないと分からない。**代案**: 手引きの側の部分を別のマークに分けて `target=handoff-reference` を付ける(一部だけ降りた規定は降りていない側に置く、という台帳の自分の規則に合わせる。IMPL-0899 は既に handoff-reference)。1つのマークで済ませるなら、台帳の降ろし先の欄が手引きも含むよう impl-targets.yaml の `review-queue-control` の description を直す。

**論拠 B: 「delivered・manual」は実態より強い。** PR のゲートは機械が期限超過を数え、宛先へ通知する。案の手引きは、PR を持たないゲートで「上程した者が自分で期限を数え、超過したら宛先へ知らせる」とする。つまり、期限を落とす者(待たせている者、または上程を忘れた者)自身の自発に頼る。害の面でも、intake 3.6 は「害は遅れに留まる」とするが、G-7(出荷判定)・G-5・SG の遅れは、出荷の停止または強制の遅れに及ぶ。「安全・法令に及ばない」の断定は、G-7・SG については確かめていない。

方針 3 問への応答: (1) 結果と証跡は D-0 節6 の宛先の記名と上程の Issue のコメントで、手引きはそれに留まる。(2) 例外承認では受けられない、は妥当。(3) 破られたとき失うのは上程した者でなく、判断を待たされる事業決裁者と、遅れで影響を受ける出荷の相手。ここが「確かめる者: 上程した者と宛先」では、確かめる者と失う者が別になる。

**代案**: ADR-0175 の(d)(adopter)のように、`plan=adopter decision=ADR-NNNN` として「採用者が自ら実装する(手引きは雛形)」と表示する。もしくは `delivered/manual` のまま、note に「機械は PR を持たないゲートの超過を検出しない」を残す(案のとおり)。後者を採るなら、台帳の「確かめる者」を宛先(D-0 節6 の者)だけにし、期限を落とす側を確認者にしない。

## 3.7 IMPL-0497: 異議あり(判定の精度)

**論拠 A: 文字列の包含の偽陽性・偽陰性。**
- 偽陽性(行があると誤判定): 起点 `#12` を「対象」に含む判定は `#123`・`#124` も含む。語の境界が要る(enforcement-inventory.mjs は既にジョブ名に前後が英数字でない語としての一致を使い、試験に ng/ok を持つ。同じ方式を使うこと)。案は「`#N` を含む行」としか書いていない
- 偽陽性: 同じ Issue 番号が別の話(参照・過去の言及)として対象欄に書かれても対応と読む
- 偽陰性(欠けと誤判定): 対象欄が「PR #12」でなく URL 形式(`https://github.com/.../pull/12`)や、複数の PR をまとめた行(「#12 #15」)、`GH-12` で書かれていれば、番号が合わず「欠け」と出る。是正の記録は人が書く欄で、書式は固定でない(defect-ledger.md 36 行)
- 偽陰性: `state:needs-platform` を付けた履歴は「統制の弱化の検知」だけではない。強制層の変更の通常の経路(IMPL-0645 などの別の目的)にも使われる。起点の全てが是正の対象ではなく、この印を起点にすると、是正が要らない件を「欠け」として出し続ける(偽陽性の山)

**論拠 B: `missedTypes` は類型の名で、注入の記録の識別ではない**(adoption-trial.mjs 262 行は `Object.entries(byType)` のキーを返す)。案の「注入の記録の識別を含む行」は、識別を出す所が現状に無い。`missedTypes` が過去の導入前の検証から永続する値であれば、一度見逃した類型は、台帳に行が一度ついても、その後の再検証で再び欠けと出うる(期間の窓が無い)。

**論拠 C: 定義の増加。** 案は「`#N` か識別を含む行」と書式を固定せず、機械の判定が書式の暗黙の定義になる。defect-ledger.md の様式に「対象の欄の書き方」(例: `PR #12` または注入の記録の識別)を足すのが先で、これは様式側の細かい定義の増加に当たる。所有者の方針(2026-11-16)に照らすと、「一覧に出す(合否に使わない)」という弱い扱いなら許容できるが、手引きの 41 行の書き換え(「確かめる」と言い切る)は誇張になりうる。

**代案**: (i) 語の境界つきの一致(`#12` が `#123` に当たらない)、(ii) 起点を `state:needs-platform` でなく、統制の弱化の検知の引き渡しの記録(第3章 3.5.5 の記録)に限る。限れなければ、`needs-platform` 起点は「候補」として別の見出しで出し、欠けと断定しない、(iii) 41 行の改めは「機械は番号を含む行の有無を一覧に出す(合否に使わない)。含まない行・URL 形式の行は漏れうる」と偽陰性を開示する、(iv) 試験に ng(`#12` と `#123`)・ok(URL 形式でも通る/通らない旨)を入れる。
