## R-1 手順の全体の置き場

### 結論

**標準に「持ち込みの要求事項」を置き、手順はテンプレートの文書に置く**。要求事項は、それぞれ機械か人の記名で確かめられる形に限る。要求事項は次の4つ。

1. 適用の開始より前に、既存の統制の資産を棚卸しして記録する
2. 棚卸しで見つけた資産ごとに、統合・置き換え・対象外の扱いを人が決めて記録する
3. 適用の開始のリビジョンより前の履歴に、本標準への準拠を主張しない(既存。1.10.1)
4. 実環境で、統制が効いていることを確かめる(R-4)

### 理由

- 現場から見て、手順書は既存のリポジトリの数だけ例外が出ます。F-1〜F-6 はどれも「試した1件のリポジトリに無かった」から漏れたものです。手順を標準に固定すると、次の漏れも標準の改訂待ちになります
- 一方で、テンプレートの文書だけに置くと、テンプレートを使わない採用者(自前で実装する組織)には何も掛かりません。F-3 のような「黙って無効」は、どの実装でも起き得ます【外】K10
- 規格は持ち込みの手順を持たず、適合の型とテーラリングを持つ【外】S1〜S5。CMMI の導入の手引きは「現状の写し → 差 → 使われているかの確認」を最初に置く【外】S4。要求事項1・2 はこの順序を要求の形に落としたものです
- 棚卸しの対象は列挙を例示とせず、**統制に効くファイルと設定の種類**で定めます。指示ファイル、エージェントの設定(権限・フック)、所有の指定、CI のワークフローと必須チェック、ブランチ保護とルールセット、言語と測定器、静的解析の設定です

### 他の案を落とす理由

- 「手順の全体を標準に置く」: 落とす。GitHub・Claude Code の仕様に依存する手順は、標準の改訂の周期より速く変わる(Evaluate の提供範囲【外】K3、AGENTS.md の読み込み条件【外】P1)。標準を特定の製品の手順書にしない
- 「事実と定めだけ(現状維持)」: 落とす。要求事項が無いので、F-1〜F-6 のどれを見落としても「準拠している」と言えてしまう
- 「テンプレートの文書だけ」: 落とす。理由は上のとおり。テンプレートの README の「各案件の技術判断に委ねる」は、標準に対応の無い規範の例であり(内部 3 節)、この形を増やさない

### 文の案(フェーズ5「既存のリポジトリへ持ち込む」へ。規範の箇条書き)

- 適用の開始より前に、既存のリポジトリが持つ統制の資産を棚卸しし、案件の記録に残す。対象は、エージェントの指示ファイル(入れ子を含む)、エージェントの設定(権限とフック)、所有の指定、CI のワークフローと必須チェック、ブランチ保護とルールセット、言語ごとの試験と被覆の測定器、静的解析の設定
- 棚卸しで見つけた資産ごとに、統合・置き換え・対象外のいずれかを決め、決めた人を記名する。AI の名義で決めない
- 棚卸しに無い資産は、対象外と決めたものとして扱わない。記録の欠落として表示する
- 測定の外に置いた言語・ディレクトリは、対象外として宣言に書く。書かずに測定の外へ置かない

### 既存の ADR・条項との矛盾

- 1.10.1「観測だけの期間は適用の開始より前に置く」と整合する。棚卸しは開始前の準備
- 1.10.1「導入中の状態を設けない」とは矛盾しない。棚卸しは状態ではなく記録
- SKILL.md 210 行「既存ファイルからスタックを推測して埋めない」とは、**検出と推測を分ければ**矛盾しない。検出(`go.mod` がある)は事実として示し、回答(どのスタックで測るか)は人が書く。R-2 で詳述
- ADR-0068 決定7 の「先送り」を解く。採用済みの ADR は書き換えず、新しい ADR で置き換える

### 既存の違反の基準線

**認める**。ただし次の4条件を付ける。これは統制の緩和ではなく、現場で起きる緩和(下)を塞ぐための担保です。

1. 基準線は**適用の開始より前**、初期化の PR の中で記録する。開始の後に基準線を作り直さない
2. 基準線を確定するのは技術判断の席の人(記名)。AI の名義を受け付けない
3. 基準線は**減る向きだけ**を機械が許す。件数・対象のファイルが増える変更は、閾値・除外設定の変更(禁止事項6)として扱う
4. 基準線の件数を保証の開示に出し続ける

理由です。1.10.1 は「適用の開始より前の変更は、本標準の要求事項の対象としない」と定めています。開始前に書かれたコードの違反で G-5 を落とすのは、この条項より広く掛けていることになります。そして基準線を認めないと、現場は次のどれかをします。いずれも基準線より悪い結果になります。

- アダプタの `lint` の対象を狭める(`adapters/**` は強制層。変更は通るが、何を外したかが開示に出ない)
- `coverageSummary` を `null` にして「実施しない」で通す(#330 の穴。F-5 の python では現実の逃げ道)
- 閾値を下げる(記名は残るが、新しいコードにも緩い閾値が掛かる)

ESLint の bulk suppressions と diff-cover が、既存の負債を記録して新規分だけを止める型の前例です【外】T10・T11。

### 他の案を落とす理由

- 「全部を警告で続行(現状)」: 落とす。F-2・F-3 が黙って外れる
- 「初期化がファイルからスタックを判定して埋める」: 落とす。SKILL.md 210 行の禁止の理由(回答は利用者の状況)は正しい。検出の結果は人へ示すだけ
- 「基準線を認めない」: 落とす。理由は上のとおり。現場の逃げ道のほうが開示が少ない
- 「基準線を開始後も作り直せる」: 落とす。閾値の緩和と区別できなくなる【外】§5-9

### 文の案

- 準拠テンプレートの初期化は、書き込みの前に既存のリポジトリを検査する。統制を黙って外す状態(目印の無い指示ファイル、フックの登録の欠け、所有の指定の重複と雛形の残り、既定ブランチの名の不一致)を見つけたら、何も書かずに止まる
- 既存のコードの静的解析の違反と被覆の不足は、基準線として記録してよい。記録は適用の開始より前に行い、技術判断の席の人が記名で確定する。基準線を増やす変更は、閾値・除外設定の変更として扱う

基準線の4条件は実証を欠くため、本文へ入れるときは EV マークを付ける(案: 「基準線が恒久の除外にならないこと」は未検証。差し替え条件 = 基準線を記録した採用者で、件数が減ったかの観測)。

## R-3 併合した履歴と適用の開始

### 結論

- 適用の開始のリビジョンより前の履歴は、**集約の対象の外**とする(1.10.1・ADR-0083 のとおり)。【外】K12 の SLSA Source の連続性の考え方と一致する
- 開始より前の履歴を**1件ずつ分類しない**。開示は「適用の開始より前のコミット N 件(対象外。内訳を区別しない)」の1行にする。テンプレート由来かどうかの識別をやめる
- 併合の禁止(定め1)の担保は、集約での識別ではなく、**持ち込みの検査での根のコミットの数**(R-2)と棚卸しの記録に移す

### 理由

- 今の識別は「親が無く、全ファイルがテンプレートの一覧に当たるコミット」だけを除きます【内】2.2。数年の履歴を持つリポジトリでは、開始より前のコミットのほぼ全部が「製品のコードを変えたコミット」と出ます。これは事実ですが、本標準が何も主張しない範囲の内訳です。読み手は件数の大きさを統制の弱さと読みます
- 1件ずつの分類は、大きな履歴で出荷のたびに重くなります(F-8)。時間切れは証跡の欠落につながり、信頼性を下げます
- トレーラは来歴を証明しない【外】K13。テンプレート由来の識別を精密にしても、主張の根拠にはなりません
- 件数そのもの(`git rev-list --count`)は残します。開始を遅らせて履歴を範囲の外へ逃がす操作が、件数で見えるためです

### 他の案を落とす理由

- 「既知のテンプレートのコミットの一覧と照合して識別する」: 落とす。テンプレートの版ごとに一覧を配る必要があり、F-9(タグが無い)の現状では維持できない。識別できても主張は変わらない
- 「現状維持(1件ずつ分類して開示)」: 落とす。上の理由

### 文の案

- 適用の開始のリビジョンより前の履歴は、本標準の要求事項の対象としない。件数だけを開示し、内訳を分類しない
- テンプレートの履歴を併合していないことは、適用の開始より前に、根のコミットの数で確かめる。根のコミットが2つ以上あるときは、その由来を棚卸しへ記録する

### 既存の ADR・条項との矛盾

- 本文の事実5・6 と定め1 の理由の行(「テンプレート由来の初期コミットを一覧から除く扱い」)の書き換えが要る。事実は残し、定め1 の担保の所在を改める
- IMPL-0119・IMPL-0304 の note は「件数を出す」を含むので、件数を残せば矛盾しない

## R-4 実際の GitHub 上での検証の計画

### 結論

1. **検証の計画は標準の本文に置かない**。本文には EV-0107 の差し替え条件(既存)を置き、計画は Issue と research に置く
2. **検証は保守者が自分で行う**。採用者の記録を待たない。#338 の受け取りの経路は無く、待てば EV-0107 は見直しの 2027-04 を越える
3. 検証用のリポジトリは、現場の典型を**意図して作る**。既定ブランチ `master`、旧来のブランチ保護、パスで絞った既存のワークフロー、開いている PR、ルートの CODEOWNERS、既存の `.claude/settings.json`、python(poetry)と go の両方、数千件の履歴
4. env-check の結果に「権限が足りず読めない」を「未確認」と分けて持たせる
5. `checks-only` の穴を塞ぐ。G-6 を適用しない構成でも、必須チェック `gate-g5` の適用を確かめる。「該当なしで確認済み」にしない
6. env-check の項目に、効いている CODEOWNERS の所在・`codeowners/errors` の API の結果・必須チェックの発行元(GitHub Actions)を足す
7. 確認は人が一度記名する。出荷の証跡の集約が、出荷のたびに同じ API を読み、記名の記録との差を**検出の層として**出す。機械の読み取りを確認済みにしない

### 理由

- 初期化はルールセット `checks-only` の適用を案内するのに、env-check はその適用を確かめません【内】5節、`adoption-trial.mjs` 1304 行【自】。現場の小さな体制(G-6 なし)ほど、ここが唯一の強制です
- 権限が足りないときの扱いは、Scorecard が「満たした」と数え、terraform が欠落と空を混同した前例があります【外】K5・K6。直し方が違う(管理者が実行し直す/ルールセットを適用する)ので、結果の値を分けます
- 必須チェックは名前だけで照合されます。`checks-only.json` は発行元を固定していません【自】。同名のコミットステータスを書ける者は通せます【外】K9。発行元の固定は検証の項目に入れます
- 管理者は障害対応でブランチ保護を外し、戻し忘れます。一度の確認では乖離を捉えられません【外】K7・K8。毎回の人の記名は、現場では形骸化します。人の記名は一度にし、乖離の検出を機械に持たせます
- Evaluate のモードは Enterprise Cloud の文書にしか現れません【外】K3。計画の前提にしません

### 他の案を落とす理由

- 「計画を標準に置く」: 落とす。誰が・どのリポジトリでは標準の要求事項ではない。R-1 と同じ理由
- 「採用者の記録を待つ」: 落とす。上の理由

- 「定期のワークフローが確認済みを書く」: 落とす。ボットの読み取りを人の確認に数えることになる(CLAUDE.md「AI が確認済みにしない」)

### 文の案(附属書I I.11 要件⑦ の注記、または集約の項目4 へ)

- 出荷の証跡の集約は、出荷の時点の実環境の設定を読み、記名の確認の記録との差を表示する。この読み取りを確認済みとして記録しない

## R-5 旧い版のテンプレートで生成した構成の移行

### 結論

- **Copier・Terraform の型を採る**。構成に形式の版を持たせ、版を跨ぐ移行を宣言し、`/process-change` の種別(案: `migrate`)が1本の PR として出す
- **読むときに既定値で補うのは、結果が従来と同じか、より厳しい場合に限る**。判定が緩む向きになる補いは、補わずに契約検査を失敗にする
- **未知の版(スクリプトより新しい版)は拒否する**(F-7 を塞ぐ)
- A-3 で落ちる構成に**猶予を設けない**。経路は `migrate` で再生成し、G-6 を未達として表示すること
- 版の欄の無い宣言と D-0 は、**遡って埋めない**。移行の時点の日付で版を書き足し、それより前の期間は記録の欠落として数え続ける

### 理由

- 現場から見て、契約検査が落ちたときに一番困るのは「何をすれば戻るか」が版ごとにばらばらなことです。今は、要約値の連鎖・A-3・`nameConfirmed`・`coverageScope` で、直し方がそれぞれ違います【内】3節。1つの種別で、跨いだ移行をまとめて出せば、PR を1回読めば済みます
- 「同じか厳しい向きだけ補う」は、今の補いの実例(`coverageScope` が無ければ `whole`、`standard` が無ければ作業中の版)と一致します。この線で、Renovate 型の無期限の読み替え【外】T7 の利点(旧い構成が動き続ける)を、緩める向きでだけ捨てます
- 猶予は 1.10.1(経過措置なし)と ADR-0083 決定2(移行の期間と失効を置かない)に反します。Kubernetes 型【外】K1 は採れません。現場としても、A-3 で落ちるのは「独立が成り立っていない」構成であり、猶予の間は統制が無いのに有るように見えます
- 移行器の出力を検証なしに確定させない【外】T9。だから PR にします

### 他の案を落とす理由

- 「Renovate 型(無期限の読み替え)だけ」: 落とす。A-3 は意味の変更で、読み替えると緩む
- 「Kubernetes 型(猶予期間)」: 落とす。上の理由
- 「移行の手段を置かず、エラーの文言で `/process-change` を案内する(現状)」: 落とす。複数の破壊的な変更が重なると、採用者は1つずつ赤を潰すことになる

### 文の案(テンプレートの文書。標準へは第1行だけ)

- 構成を読むときに、欠けた欄を既定値で補うのは、判定の結果が補う前と同じか、より厳しくなる場合に限る。それ以外は、欠けを契約の検査の失敗とする
- 準拠テンプレートの構成は形式の版を持つ。読み手のスクリプトが知らない版の構成は、読まずに失敗する
- 旧い版の構成は、`/process-change`(種別 `migrate`)で現行の版へ移す。移行は PR として出し、強制層の変更として扱う

### 既存の ADR・条項との矛盾

- `schemaVersion` の意味を「連鎖の有無」から「形式の版」へ広げるなら、要約値の連鎖の判定(`< 1`)と両立させる(連鎖は版 1 以上の性質として残す)
- テンプレート README の「遡って書き換えない・埋め戻さない」と整合する
- 1.10.3 の 505 行が #315 へ送った D-0 の扱いに答える

## R-6 テンプレートの更新の取り込みと、既存の採用者を壊す変更

### 結論

1. 構成に、取り込んだテンプレートの**コミットの識別**と、知識ベースの版を記録する。書くのは道具だけで、手で編集しない(Copier の `_commit`、cruft の `.cruft.json` と同じ型【外】T1・T3)
2. テンプレートは、既存の採用者の検査を落とし得る変更ごとに、**機械が読める一覧**(識別、何が落ちるか、検出の方法、移行の手段)を持つ。保守者の義務として ADR に置く
3. 取り込む前に、採用者のリポジトリで新しい検査を**読み取りだけで**走らせる手段(取り込みの試行)を配る。落ちる箇所を取り込みの PR の前に知れるようにする
4. **猶予は置かない**(R-5 と同じ)。告知と試行の手段が、猶予の代わりの担保
5. 取り込まない判断は許す。ただし構成に記録したテンプレートの識別がそのまま残り、適用の表明はその識別を名指す(ADR-0083 決定2 の「旧い版への主張は期限なく有効」と同じ構図)
6. テンプレート README の「各案件の技術判断(G-3/例外承認等)に委ねる」「促してください」は、上の規範で置き換える
7. #332 との分担: #332 は `dist/standard`(本文と知識ベース)の受け取り側の検査、#315 はテンプレートのスクリプト・スキル・ワークフローの取り込み

### 理由

- 今は、採用者が何を取り込んだかを誰も言えません。テンプレートにタグも無い(F-9)。適用の表明が「どの検査で確かめたか」を名指せないのは、表明の信頼性の欠けです
- ADR-0084 は「落ち始めうる」と影響に書くだけです【内】1.2。採用者は、取り込みの PR を出して CI が赤になって初めて知ります。現場の手戻りとしては、取り込みの PR が `state:needs-platform` を経て長く開いたままになり、その間に製品の PR が溜まる形になります
- 取り込みの試行は、safe-settings の dry-run の型です【外】K7。採用者のリポジトリの構成とファイルを読むだけで、書き込まないので、強制層の変更に当たりません
- 取り込みの手段は、cruft の `link` に当たる「既存の案件を後からテンプレートの識別へ結び付ける」操作も要ります【外】T3。今の採用者は全員、識別の記録を持たないためです

### 他の案を落とす理由

- 「自動の同期(ボットが更新の PR を出す)」: 今は落とす。テンプレートにタグが無く、更新の単位が定まらない。タグの発行の規則を先に決める(#331 と関係)
- 「更新ごとに README へ個別の節を足す(現状。#296 の節)」: 落とす。一般の手順が無く、節が増えるほど読まれなくなる
- 「破壊的な変更に猶予期間を設ける」: 落とす。R-5 と同じ

### 文の案

- 準拠テンプレートの構成は、取り込んだテンプレートのコミットの識別を持つ。この欄は道具だけが書く
- 準拠テンプレートの保守者は、既存の構成の検査を失敗させ得る変更を出すとき、変更の一覧へ、失敗する条件・検出の方法・移行の手段を書く。一覧に無い破壊的な変更を出さない
- テンプレートの更新を取り込まない案件は、構成に記録したテンプレートの識別を、適用の表明で名指す

### 既存の ADR・条項との矛盾

- ADR-0083 決定2(移行の期間と失効なし)・1.10.1 と整合する
- ADR-0084 の影響の4 は、保守者の側の義務が無いまま影響を書いている。新しい ADR で義務を足す。ADR-0084 の本文は書き換えない
- ADR-0077 決定6(`dist/standard` は本文と知識ベースだけ)とは矛盾しない。スクリプトの配布元はテンプレートのリポジトリのまま
