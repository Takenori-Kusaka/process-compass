## R-1 手順の全体の置き場

**結論**: 標準には「持ち込みが済んだと言える要求事項」だけを置き、手順はテンプレートの文書に置く(案 B)。ただし要求事項は**開始より前の活動へ掛けず、適用の開始の記録の内容として掛ける**。テンプレート README の規範の文(485〜486 行「各案件の技術判断(G-3/例外承認等)に委ね」)は、標準に対応する条項を置くか、手引きの文へ書き直すかのどちらかにし、**根拠条項の無い規範を残さない**。

**理由**
- 監査は「何に照らして」確かめるかが要る。手順だけがテンプレートにあり、標準に要求事項が無ければ、採用者ごとに持ち込みの良否を判定する基準が無い。監査人は手順の逸脱を指摘できても、不適合とは言えない
- 一方、手順の全体は実 GitHub と python・go で一度も通っていない(EV-0107 は E2)。通していない手順を規定にすると、**確かめていない手順に従ったことを適合の根拠にする**ことになり、主張が過大になる
- 第1章 1.10.1 は「適用の開始より前の変更は要求事項の対象としない」と定める。持ち込み(開始前の準備)そのものへ要求事項を掛けると、この条項と矛盾する。矛盾を避ける唯一の形は、**開始の記録が持つべき内容**として要求することである。欠ければ記録の欠落として表示でき、開始は動かない(ADR-0083 決定5 と同じ型)
- 外部 S1〜S5: 規格は持ち込みの手順を書かず、適合の形とテーラリングを書く。CMMI(S4)は「現状の写し → 差」を最初に置く。写しの**結果**を開始の記録に残すことは、規格の型(適合の形を規定、手順は手引き)と整合する

**他の案を落とす理由**
- 案 A(手順の全体を標準へ): 却下。E2 の単一事例を規定へ昇格させる。手順の各段を監査可能にするには実走の記録が要るが、無い
- 案 C(すべてテンプレートの文書へ): 却下。テンプレート README に既に標準の裏付けの無い規範があり(内部 §3)、監査で追跡できない状態が続く。#310 C-7(フェーズ5 は本文に従属)とも合わない

**文の案**(第1章 1.10.1 への追記。箇条書き)

- 既存のリポジトリへ持ち込んで適用を開始する場合、適用の開始の記録に、開始の時点で既に存在した統制の資産の一覧と、その扱いを含める。一覧の対象は、エージェントへの指示ファイル(入れ子を含む)、コード所有者の定義、既存の CI と必須チェック、既存のブランチ保護とルールセット、カバレッジの測定の手段、対象の言語である
- 一覧の各行の扱いは「残す」「統合した」「無効にした」「未確認」のいずれかで記録する。「未確認」は、確かめたことを表さない
- 一覧の欠けは記録の欠落として表示する。適用の開始は動かさない
- 持ち込みの手順は、本標準の要求事項ではない。準拠テンプレートの文書が手順を示す

本文(template-repository.md): 「持ち込みの手順の全体は、要求事項として定めていません。準拠テンプレートの手順は手引きです。手順に従ったことは、適合の根拠になりません。」

**矛盾**: 1.10.1 と整合させるため、要求の対象を「開始の記録」に限った。ADR-0068 決定7(手順の全体を先送り)は手順を定めないことを維持するので矛盾しない。一覧の対象の6項目は外部調査(K4・K9・K10・P1・P2・P5)と 1 事例(事実1)に基づくので、**EV(新規)で開示する**(E2〜E3、差し替え条件は R-4 の実走)。

## R-2 初期化が既存のリポジトリで検出し、告げ、止まること

**結論**: 判断軸は「**`configured: true` を書く前に止める**」。適用の開始は動かせない(ADR-0083 決定5)ため、既知の失敗を抱えたまま開始の境を刻ませない。

## R-3 併合した履歴と適用の開始

**結論**
1. 開始のリビジョンより前の履歴には**主張しない**(1.10.1 の既存の規定)を、**併合した履歴にも及ぶ**と明記する。SLSA Source v1.2(外部 K12)が支える
2. 「テンプレート由来」の識別は**行わない方向へ寄せる**。いまの判定(親が無く、全ファイルが一覧に当たる)は出所の証明ではない。表示の名を「テンプレート由来」から事実の記述(「親を持たず、テンプレートの一覧のファイルだけを持つコミット」)へ改める。トレーラ・作者・ファイルの一覧で出所を主張しない(外部 K13)
3. 定め1(併合しない)を維持する。**開始の後に無関係の履歴を併合したら、集約で別の区分として出し、記録の欠落に数える**(免除しない)
4. **開始のリビジョンは既定ブランチの第1親の連鎖の上で決める**。V-4 のとおり、いまの実装は併合した別の履歴の `configured: true` を開始にしうる。開始の前の集合も、開始のコミットの全祖先(第2親を含む)で取る

**理由**
- 監査で問うのは「どの時点から、途切れずに統制が効いているか」である。出所の推定で一部の履歴を除外すると、除外の基準そのものが監査の対象になり、しかも検証できない
- V-4 の穴は過小の主張ではなく境の誤りである。ADR-0083 決定5 は「境を履歴の1コミットに固定し後から動かせない」とするが、併合で境が別の履歴へ移れば、その前提が崩れる。「早い側は安全」(ADR-0083)は1本の履歴の上での議論で、別の履歴の上の境には当たらない
- 開始後の無関係の併合を免除すると、記録の無い変更を併合で持ち込む迂回路になる

**他の案を落とす理由**
- 既知のテンプレートのコミットの一覧と照合して識別する: 却下。一覧はテンプレートの版ごとに要り、照合しても「同じハッシュを持つ」ことしか言えない。開始前は主張しないので、識別して得るものが無い。開始後は免除しないので、識別は要らない
- トレーラ(例 `Imported-From:`)で識別: 却下。誰でも書ける(K13)

**文の案**(1.10.1 への追記)

- 適用の開始より前の履歴には、履歴の出所(採用者の過去の変更、併合した他のリポジトリの履歴、テンプレートの開発履歴)によらず、適合を主張しない
- 適用の開始の境は、既定ブランチの第1親の連鎖の上の1コミットとする。併合した他の履歴の中のコミットを境にしない
- 適用の開始の後に、共通の祖先を持たない履歴を併合した場合、併合した側のコミットは要求事項の対象とし、記録が無ければ記録の欠落として表示する

**矛盾**: ADR-0083 決定5 の「configured: true になった最初のコミット」を**第1親の連鎖の上で**と限定する。採用済み ADR の本文は書き換えず、新 ADR で補う(決定5 の適用範囲の明確化)。V-4 は読解による推論なので、**実装の前に再現の試験(fixture、#319)で確かめる**ことを条件とする。

**根拠**: 内部 §2.2、外部 K11・K12・K13、V-4(自分でコードを読んで確認、実行は未了)。

## R-4 実際の GitHub 上での検証の計画

**結論**
1. 検証の計画(誰が・どのリポジトリで)は**標準に置かない**。本リポジトリの Issue と research に置く。標準には EV-0107 の差し替え条件だけを置き、条件を具体化する
2. env-check の結果を**4値**にする: 確認済み / 不一致(読めて、構成と違う。ルールセットが無いことを含む)/ 未確認(読めない。理由に「権限不足」「gh が無い」等を区別して書く)/ 対象外(構成が要しない。**確認済みと別の値**)
3. **`checks-only` の穴を塞ぐ**: G-6 が無効でも、必須チェック gate-g5 の適用は確かめる。「確認済み・対象外」の重ね書き(V-1)をやめる
4. バイパス主体と旧来のブランチ保護を**確かめていないことを記録に書く**。読めるなら読み、読めなければ未確認とする(外部 K5・K6)。必須チェックの発行元の固定(V-3)は、ルールセットへ `integration_id` を入れるかを別に決める(下記)
5. 一回の確認は**時点の確認**として表示する。出荷の証跡の集約は、env-check の日付が集約の範囲より前なら「範囲の中の実効は確かめていない」と出す。定期の自動の再確認は**本 Issue では課さない**(実装と権限の前提が無い)と明記し、EV で開示する

**理由**
- 計画(人・リポジトリ)は保守の作業で、他組織が従う要求事項ではない。標準に書けば、計画の未達が標準の欠陥に見える
- 外部 K5(Scorecard)は読めない設定を満たしたと数え、K6 は欠落と空を混同した。V-1・V-2 は同型の穴が env-check にある。ADR-0028(未達と省略の区別)の延長として、**読めなかった・無かった・対象外・確かめた**を同じ値にしない
- バイパス主体があれば、ルールセットが効いていても管理者は迂回できる。それを確かめずに「確認済み」と書けば過大な主張になる
- 統制は確認の後に無効にできる。一回の確認を範囲全体の保証として読ませない。ただし定期の自動確認を要求しながら実装が無ければ、全採用者が未達になるだけで信頼性は上がらない。だから「表示する」に留め、課さないことを明記する

**他の案を落とす理由**
- 計画を標準の附属書へ: 却下(上記)
- 定期の再確認を必須に: 本 Issue では却下。safe-settings・Allstar(K7・K8)は継続の実装を持つ前例だが、採用者に管理者権限のトークンを常駐させる前提が要る。統制の弱化の新しい経路を作りうる。再検討の Issue を起こす
- ルールセットの Evaluate で試行: 却下。無料の文書に無い(K3)

**EV-0107 の差し替え条件(具体化の案)**
- 実 GitHub 上で、既存のリポジトリへ持ち込み、初期化の PR が必須チェック gate-g5 を通り、出荷の集約までを通した記録。記録は API の応答の識別(ルールセット id、実行の id と URL)を持つ
- env-check が実環境で「確認済み」に到達した記録が少なくとも1件(いまは0件。内部 §5)。あわせて、権限不足のトークンで「未確認(権限不足)」に倒れる記録
- 既存のワークフローとの併存(パスの絞り付きの CI がある場合を含む)、旧来のブランチ保護との重なり、開いている PR への必須チェックの効き方
- python と go の既存のリポジトリでの試行
- 作成者の側が通した記録は、作成者の側の記録であると開示し続ける。採用者の記録で置き換えるまで水準を上げ過ぎない

**文の案**(template-repository.md「実環境の統制の確認」に関わる本文。ですます調)

「実環境の統制の確認の結果は、確認済み・不一致・未確認・対象外の4つで記録します。対象外を確認済みに数えません。読めなかった項目は、理由(権限の不足、gh が無いなど)とともに未確認とします。ルールセットの例外の対象(バイパス)と、旧来のブランチ保護を確かめていない場合は、その旨を記録に書きます。確認は時点の確認です。出荷の証跡の集約は、確認の日付が集約の範囲より前であれば、範囲の中で統制が効いていたことを確かめていないと表示します。定期の自動の再確認は課しません。」

**必須チェックの発行元**: ルールセットに `integration_id`(GitHub Actions)を入れる案を**採る方向で R-4 の実走の項目に入れる**。入れずに済ませるなら、名前だけで満たしうることを記録に書く。実 GitHub での挙動を確かめていないので、この会議では規定にしない。

**矛盾**: ADR-0028 と整合(区別の拡張)。附属書I I.11 要件⑦(`adoption-guide.md`)の「3項目」の文言は、値の区分を変えるので要件⑦の側も直す。adoption-guide 408 行の「3項目とも確認済みになった時点から」の判定の効力の規定は、対象外を確認済みに数えない形に合わせて読み替えが要る(書記へ)。

**根拠**: 内部 §5、外部 K3〜K9、V-1〜V-3(自分で確認)。

## R-5 旧い版のテンプレートで生成した構成の移行

**結論**: 型は「**版の欄 + 宣言した移行を `/process-change` で PR として出す**」(Copier・Terraform の型)。未知の版は**拒否**する。猶予(Kubernetes の型)と黙った読み替え(Renovate の型)は採らない。

1. 構成に**形式の版**を持たせる。いまの `schemaVersion`(連鎖の有無)を形式の版として扱うか、別の欄にするかは実装で決める。いずれにせよ、**テンプレートが知る版より新しい版は契約の検査で落とす**(V-5 の穴を塞ぐ)
2. 旧い版の構成は、読むときに既定値で補ってよい。ただし補った値が**判定に効く欄**(席・ゲートの状態・委任・閾値)なら、補った事実を注記で出し続け、移行の記録が入るまで消さない
3. A-3 で落ちる構成(1〜2名で確認者を名簿から確かめられないのに G-6 が未達でない構成等)は、**落とし続ける**。経路は `/process-change` による再生成で、席の責任者は人が記入する。機械と AI は席を埋めない
4. 移行は適用の開始を動かさない。連鎖の起点より前の構成と記録は、書き換えの有無を確かめられないと表示し続ける(template-repository.md 778 行の既存の開示)
5. 版の欄の無い宣言と D-0: **遡って書き換えない**。`/process-change` 種別 `edition` で版を記載した時点から欠けが止まる。記載の前の範囲の記録の欠落は、その範囲の件数に残る

**理由**
- 猶予を置くと、確かめられない構成(確認者がいないのに G-6 有効)を一定期間「通る」と表示する。監査の側から見て、**現在の規則が成立しないと知っている状態を通す**のは過大な主張である。1.10.1(経過措置を置かない)と ADR-0083 決定1(移行期間と失効を置かない)とも矛盾する
- 黙った読み替えは、判定に効く値を利用者が見ないまま決める。Renovate の読み替えは依存の更新の構成で、合否の判定の構成ではない。前例の用途が違う
- 未知の版を通さないことは、外部の全ての型(T2・K2)に共通する。V-5 はそれに反する
- 遡って書き換えない理由: 書き換えれば、書き換えた後の記録が当時の記録に見える。ADR-0028・README 488〜495 行(欠落を埋め戻さない)と同じ

**他の案を落とす理由**
- 移行のスクリプトで構成を自動で書き換え、記録だけ残す: 却下。席・確認者の欄を機械が埋めることになりうる。ESLint の移行器(T9)も出力の無修正の動作を保証しない
- 猶予期間(Kubernetes 型): 却下(上記)

**文の案**(template-repository.md に新しい節「旧い版で生成した構成」。箇条書き)

- 構成は形式の版を持つ。準拠テンプレートが知らない版の構成は、契約の検査で落とす
- 旧い版の構成の欄は、読むときに既定値で補う。補った欄が判定に効く場合は、移行の記録が入るまで注記で出し続ける
- 規則の強化で落ちるようになった旧い構成に、猶予を設けない。経路は `/process-change` による再生成であり、席の責任者は人が記入する
- 移行は適用の開始を動かさない。連鎖の起点より前の構成と記録は、書き換えの有無を確かめられないものとして表示する
- 版の記載の無い宣言と D-0 体制図を遡って書き換えない。版を記載するまでの範囲の記録の欠落は、その範囲に残す

**矛盾**: 1.10.1・1.10.3 の「旧い構成と D-0 の移行は #315 で扱う」を本決定で閉じる(1.10.3 の当該行を「template-repository の節による」へ改める)。ADR-0083 決定1 と整合。「補った事実を注記で出し続ける」は新規の規定で、**判定に効く欄の範囲**は実装で列挙して固定する。

**根拠**: 内部 §2.3、外部 T2・T7・T9・K1・K2、V-5(自分で確認)。

## R-6 テンプレートの更新の取り込みと、既存の採用者を壊す変更

**結論**
1. **採用者が取り込んだテンプレートの版(コミット)を構成に記録する**。書くのは初期化と `/process-change`(新しい種別、例 `template-update`)だけで、手で編集しない(Copier の `_commit`、cruft の `.cruft.json` と同型。T1・T3)
2. 記録は**主張であって証明ではない**。テンプレートの版ごとに強制層のファイルの要約値の一覧を配り、採用者側の検査が「記録した版と一致しないファイル N 件」を**表示**する(失敗にしない。採用者の正当な書き足しがあるため)。配布物の受け取り側の真正性の検査は #332 へ渡す
3. 取り込みは**ファイルの複製の PR**とし、git の併合で取り込まない(R-3 の3と同じ理由)。PR は統制の設定の変更として陰性の確認を要し、強制層の縮小を含めば `state:needs-platform`
4. **テンプレートの版と本標準の版を混同しない**。テンプレートを更新しても、従う本標準の版は変わらない。版を変えるのは種別 `edition` だけ(ADR-0083 決定1)
5. 採用者を壊す変更(検査の強化)を出す側の規則を、**保守の手続**(`community/standard-editions.md`)と ADR に置く。採用者への要求事項にはしない:
   - 既存の採用者を落としうる変更は、リリースの記録にその旨と影響する構成の条件を書く
   - 移行の経路(`/process-change` の種別、または再生成の手順)を同じ変更で用意する。経路の無い強化を出さない
   - 猶予は置かない(R-5 と同じ)
   - 要求事項を変える強化は版の N を上げる(EV-0158 の既存の規則)
6. テンプレート README 485〜486 行の「各案件の技術判断(G-3/例外承認等)に委ね」は書き直す。**取り込まないことは例外承認ではない**(基準を満たさない経路ではなく、旧いテンプレートに留まる選択)。取り込みの判断は技術判断(G-3)で、ADR に記録する、とする

**理由**
- 版の記録が無いと、監査人は採用者の検査が「どの検査で」通ったのかを特定できない。合格の意味がテンプレートの版に依るのに、版が記録されていない(V-6)
- 自己申告の版だけでは改ざん・部分取り込みを見分けられない。だから要約値の照合を添える。ただし採用者の書き足し(定め2)は正当なので、不一致は表示に留める
- 壊す変更の規則は保守者の義務で、採用者の義務ではない。採用者に「告知を読め」と課しても検査できない

**他の案を落とす理由**
- 版を記録しない(現状): 却下(上記)
- 自動同期(bot の PR): 本 Issue では却下。強制層を外部の bot が書き換える経路を作る。統制の弱化の新しい入口になりうる。採るなら別の Issue で、bot の PR も陰性の確認を経る設計が要る
- `dist/standard` を submodule で固定して更新する: 却下。`dist/standard` はスクリプト・スキル・ワークフローを配らない(ADR-0077 決定6、内部 §3)。テンプレートの更新の手段にならない

**文の案**(template-repository.md。ですます調)

「構成は、生成と更新に使った準拠テンプレートのコミットを記録します。記録を書くのは初期化と構成の変更の手続だけです。この記録は主張であり、配布したファイルと一致することの証明ではありません。強制層のファイルが記録した版と一致しないときは、その件数を表示します。テンプレートの更新はファイルの複製の変更として取り込み、履歴を併合しません。テンプレートを更新しても、従う本標準の版は変わりません。」

**#332 との分担**: #315 = 採用者の構成に何を記録し、どの経路で取り込むか。#332 = 配布物(本文・知識ベース・テンプレート)の真正性を受け取り側でどう確かめるか。要約値の一覧の生成と署名は #332 へ。

**矛盾**: ADR-0083 決定1(版は発行したものだけ)と整合(テンプレートの版は本標準の版ではないと明記)。ADR-0084 影響 187 行(更新で gate-g5 が落ち始めうる)は、5 の「移行の経路を同じ変更で用意する」で補う。ADR-0077 決定6 と整合。

**根拠**: 内部 §3、外部 T1・T3・T4・T7、V-6(自分で確認)。
