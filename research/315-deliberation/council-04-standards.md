# #315 会議体 意見書 04 — 規格(standards)の立場

- 委員の立場: 既存規格(ISO/IEC/IEEE 12207・15288・33001、ISO/IEC 専門業務用指針、JIS、IPA 共通フレーム、SWEBOK、CMMI)の作法に照らして、本標準が何を規範に置き、何を手引きに置くかを論じる
- 作成日: 2026-10-24。読んだもの: `issues-context.md`、`council-00-agenda.md`、`survey-315-1-internal.md`、`survey-315-2-external.md`、本文(`overview.md` 1.5・1.7・1.8・1.10、`tailoring-guide.md`「調整は宣言を伴う」「準拠テンプレートが備える手段」、`exception-escalation.md` 7.3.1・7.3.2、`gate-criteria.md` 597 行・G-5 基準3、`assurance-case.md` 項目4、`adoption-guide.md` I.11 要件⑦)、ADR-0064・0068・0077・0083・0084、テンプレート(`adoption-trial.mjs` 1295〜1312 行、`config.mjs` 1596〜1663 行、`README.md` 476〜512 行)
- 他の委員の意見書は読んでいない

## 0. 根拠の水準の断り

- 規格の本文は1つも読めていない。外部調査(S1〜S7)もプレビュー・目録・要約経由である。以下で規格の作法として述べることのうち、外部調査に無いものは**記憶による推測**と明記する
- 記憶による推測(本文未読)として使うもの:
  - (推測A) ISO/IEC 専門業務用指針 第2部は、規格の要求事項を「検証できる結果」として書き、手順の記述を要求事項にしないことを原則とする。手順を要求するのは試験方法など、手順そのものが結果を決める場合に限る
  - (推測B) 12207・15288 の附属書A(テーラリングプロセス、規定)の作業に「テーラリングに影響する状況を特定し記録する」がある
  - (推測C) 12207・15288 の適用の手引きは、別の規格(ISO/IEC/IEEE 24748 系)に分けて置かれている。ISO/IEC 33014 はプロセス改善の手引きである
  - (推測D) ISO 9001 の文書化した情報の管理は、記録の訂正を履歴として残し、遡って消すことを認めない向きである
- 本標準 1.7.1 の EV-0096 の注記に、本標準自身が ISO/IEC 専門業務用指針 第2部 箇条7 を原典で確かめたとある。要求・推奨・許容の種類の立て方はこれに依れる

## 1. 横断の所見(全議題の前提)

### 1.1 フェーズ5 のページは、規範の置き場として使えない

`overview.md` 1.8(316〜323 行)は、フェーズ5 を「本標準の構成の外にあり、本文に従属する」とし、ページごとの種別(規定・参考)を「定めていません」と注記しています(自分で確認)。したがって `template-repository.md` の「定め3件」(61〜63 行)は、要求事項として効くのかどうかが文面から決まりません。他組織が従う規格としては、これは欠陥です。読み手は「定め」を要求と読みますが、1.5 の構成には入っていません。

**持ち込みについて採用者を拘束したい事項は、本文(第1章・第8章)か規定の附属書へ置く必要があります**。フェーズ5 に残せるのは、確かめた事実と、本文の要求事項を満たす手段の説明です。

### 1.2 本文は、準拠テンプレートへ要求を課す前例を持つ

第8章「準拠テンプレートが備える手段」(110 行)は「準拠テンプレートは、変化点を構成へ反映する手段を備えなければなりません」と本文で要求しています(自分で確認)。規格が「適合する実装手段」に要求を課す形で、規格の作法として不自然ではありません(推測A の範囲)。ただし本文は方法中立(ADR-0080)で、1.7 は製品名に依存する表現を禁じます。本文に書く要求は「エージェントへの指示を与えるファイル」「必須の検査」のように一般の語で書き、`CLAUDE.md`・ルールセットの名はフェーズ5 と実装マークへ置きます。

### 1.3 「適用の表明」と「適合の主張」と「保証の開示」を混ぜない

持ち込みの論点の多くは、適合の主張の範囲(1.10)ではなく、保証の開示(附属書H)の件数の正しさの問題です。規格の作法では、主張の範囲は開始の時点で切ります(SLSA K12 も同じ)。開始より前の履歴をどう数えるかは、開示の情報の質の問題であり、適合の条件ではありません。この区別を各議題で保ちます。

### 1.4 3つの「版」を区別する

| 版 | 所在 | 本文の扱い |
| --- | --- | --- |
| 本標準の版(第N版) | `edition.yaml`、構成の `standard.edition` | 1.10.3。移行の期間と失効を設けない |
| 準拠テンプレートの版(実装の版) | テンプレートのコミット | 定めが無い。構成に記録しない(自分で確認: `config.mjs` に生成元のテンプレートを記録する欄は無い) |
| 構成の形式の版 | `schemaVersion` | 0/1 は「要約値の連鎖の有無」で、形式の版ではない(内部調査 2.3、`config.mjs` 1596 行を自分で確認) |

R-5・R-6 の混乱の多くは、この3つを1つの「版」として論じることから来ます。

## R-1 手順の全体の置き場

**結論**: 本文に**要求事項(結果の形)**を置き、手順の全体は**準拠テンプレートの文書**(README・スキル)に手引きとして置く。フェーズ5 のページは、事実と、要求事項と手順の対応を示す説明に改める。

**理由**

- 外部調査 S1〜S5 のとおり、読めた範囲の規格は持ち込みの手順を本体に持たず、適合の型とテーラリングの過程を規定する。手順は採用者の改善の手引き(CMMI Adoption Guidance、S4)に置かれている。規格の作法でも、要求事項は検証できる結果で書き、手順は手引きへ分ける(推測A・C)
- 本標準は他組織が従う規格であり、手順をすべて手引きに置くと、採用者ごとに確かめる事項が漏れる。漏れて困る事項だけを、結果の形の要求事項として本文に置く
- 本文に置く要求事項は次の2つとする
  1. **テーラリングの宣言に、適用の開始の時点で既に効いている統制と指示を記載する**(適用: 既存のコードまたは履歴を持つリポジトリで適用を開始する案件)。根拠は推測B(テーラリングに影響する状況の記録)と CMMI の「現状の写し → 差」(S4、外部)。Claude Code が矛盾する指示を任意に選ぶこと(P1、外部)、既存の CODEOWNERS が黙って優先されること(K10、外部)は、記載しなければ判定の記録に現れない
  2. **準拠テンプレートは、初期化の時点で、構成の前提と食い違う既存の資産を検出して表示する手段を備える**(R-2 で中身を決める)。第8章 110 行と同じ形
- 開始より前の履歴の扱いは、1.10.1 の1つ目の項目(「適用の開始より前の変更は、本標準の要求事項の対象としない」)で既に足りる。同じ事項を2か所に書かない(1.7)
- テンプレートの README 485〜486 行の「各案件の技術判断(G-3/例外承認等)に委ねられます」「促してください」は、標準に対応する条項が無く、依頼の形で強さが決まらない(1.7.1)。しかも例外承認(7.3)は判定基準を満たさないまま進める経路であり、更新の取り込みの判断の経路ではない(7.3.1、自分で確認)。R-6 で置き換える

## R-2 初期化が既存のリポジトリで検出し、告げ、止まること

**結論**: 「止める」「告げる」の境は、**黙って無効になる統制かどうか**で引く。黙って無効になるものは止める(または機械の検査で失敗させる)。後の検査で見える形で失敗するものは告げるだけにする。既存の違反の基準線(ベースライン)を新しい経路として認めない。

| 対象 | 扱い | 理由 |
| --- | --- | --- |
| 目印の無い既存のエージェント指示ファイル(`CLAUDE.md`、`AGENTS.md`、入れ子のもの) | **止める**(構成を `configured: true` にする前に、終了コードを非0 にする) | 矛盾は失敗せず、どちらかが任意に選ばれる(P1・P2、外部)。止めても適用の開始は始まっておらず、1.10.1 と当たらない。現状でも後で CI が落ちる(内部 2.1)ので、早く止めるだけである |
| `CODEOWNERS` の雛形の行(`@OWNER`)の残り、複数の置き場の `CODEOWNERS` | 初期化は**告げる**。コードオーナーの承認を要求する構成では、実環境の統制の確認が**確認済みにしない** | 不正な行は黙って飛ばされ、置き場は最初の1つだけが効く(K10、外部。自分では確かめていない)。ルールセットの「コードオーナーの承認を要する」を読んで確認済みにすると、効いていない統制を効いていると数える。これは附属書H 項目4「検査の手段が構成に書かれていることを、実施と読まない」(規定、自分で確認)に反する |
| `coverage` のスクリプトの欠落 | **告げる** | G-5 が集計ファイルの欠如で失敗する(内部 事実4)。入力の欠如を失敗に数える規定(`gate-criteria.md` 597 行、ADR-0077 決定3)が既にあり、隠れない。止めると1名の採用者が開始できず、未達を表示して開始する道(1.10.1)を塞ぐ |
| `.gitignore` の行の欠け | **告げる** | どの行が統制を担うかを確かめた記録が無い。担う行が特定されたら、その行だけを上の「黙って無効になる」側へ移す |
| 既存のコードと履歴の存在 | **告げる**(件数と、開始より前の履歴は主張の対象外であること) | 1.10.1 で扱いは決まっている。告げるのは読み手の誤解を防ぐ説明である |

- 検出と推測の区別: `SKILL.md` 210 行の禁止は「既存ファイルからスタックを推測して埋めること」である。ファイルの有無を確かめて表示することは推測ではない。R-1 の文の案の第2文で区別を書く
- **基準線について**: 既存の違反を記録して新規分だけを止める型(T10・T11、外部)を、本標準の新しい経路として置かない。理由は3つ
  1. 判定基準を満たさないまま進める経路は 7.3.1 の3つに閉じている(自分で確認)。4つ目を作ると経路の選択が事後の裁量になる(7.3.1 の理由の文)
  2. カバレッジは、G-5 基準3 の測る範囲の既定が「変更で加えた・変えたコード」であり(605 行、自分で確認)、基準線を要しない。範囲は企画時に人が決めて記録する
  3. 静的解析などほかの基準で既存の違反が問題になるなら、基準3 と同じく**基準の測る範囲**として企画時に人が決め、範囲を広げる向き(より多くを除く向き)を緩める向きとして扱う形で足りる(禁止事項6 と同じ)。範囲の外に残る既存の違反は 7.3.2 の未解決事項として技術負債台帳へ置く。G-5 のほかの基準に範囲の概念があるかは確かめていない(要確認)

**他の案を落とす理由**

- すべて止める: `coverage` の欠落で止めると、未達を表示して開始する道を塞ぐ。止める理由(黙って無効になる)の無いものまで止めると、止める意味が薄まる
- すべて告げるだけ(現状): 指示ファイルの矛盾と `CODEOWNERS` の無効は、後の検査でも失敗として現れない(後者は env-check が確認済みにしうる)。告げた文は読まれなければ効かない
- 基準線を例外承認の一種として認める: 例外承認は成果物が存在する時点の基準の不充足を認める手続で(7.3.1)、開始の時点の一括の免除とは型が違う。開始の後の観測だけの期間(1.10.1 が禁じる)と区別がつかない

**文の案**(フェーズ5 `template-repository.md`。説明の文。本文の要求事項の手段として)

> 初期化は、区間の目印を持たないエージェントへの指示のファイルを見つけると、構成を設定済みにせずに止まります。指示が食い違うと、エージェントがどちらかを選び、検査では失敗として現れないためです。`coverage` のスクリプトの欠け、`.gitignore` の行の欠け、`CODEOWNERS` の雛形の行の残りは、初期化の出力に示します。

実装マーク(新規、`target=init-profile` 等の登録済みの降ろし先から選ぶ)を付け、`CODEOWNERS` の確認は R-4 の env-check の扱いと組にする。

**矛盾の検査**: IMPL-0123 の note(`CODEOWNERS`・`.gitignore` を確かめない)を改める。ADR-0084(常駐の規則の照合)と矛盾しない(その前段に当たる)。ADR-0050(強制層を段階にしない)と矛盾しない(基準線を置かないため)。

## R-3 併合した履歴と適用の開始

**結論**: 本文の新設はしない。開始のリビジョンより前を主張の対象外とすることは 1.10.1 で既に定まっている。テンプレート由来の識別に**トレーラ・作者・メッセージを使わない**ことをフェーズ5 に「採らない」として書く。併合した履歴を製品の変更に数える現在の集約は、**安全側の誤り**として残す。

**理由**

- SLSA Source v1.2(K12、外部、要約経由)の「開始のリビジョンより前には主張をしない」は、1.10.1 の1つ目と3つ目の項目と同じ形である。規格の作法でも、適合の主張の範囲は期間で切る。新しい要求事項は要らない
- 併合した 47 件が「製品のコードを変えたコミット」と出るのは、開示の件数が実際より多く出る誤りである。多く出る向きは、統制の無い変更を隠さない。少なく出る向き(テンプレート由来として除く)の識別を誤ると、製品の変更が開示から消える
- トレーラは誰でも書ける文字列で、出所を証明しない(K13、外部)。トレーラでテンプレート由来と認めると、開始前の製品の変更を開示から消す経路になる
- 識別するなら、テンプレートの公開の履歴のコミットの識別子(ハッシュ)との一致だけが検証できる。これを集約に入れるかは実装の判断で、本文は課さない。入れる場合も、一覧から除くのではなく「テンプレートの履歴と一致」として件数を別に出す(現状の親を持たない初期コミットの扱いと同じ形)

**他の案を落とす理由**

- 開始より前の履歴を集約の対象から完全に外す: 開始前に製品のコードを変えた件数(項目1・5)は、採用判断者が開始の前の状態を知る材料であり、消すと情報が減る。1.10.1 は「要求事項の対象としない」と定めるだけで、開示を禁じていない
- 定め1(履歴を併合しない)を本文の要求事項にする: 併合しても主張の範囲は変わらず、開示が安全側にずれるだけである。結果に影響しない手順を要求にしない(推測A)。手引きとしてテンプレートの文書に置く
- 併合を検出して止める: 併合は開始より前の行為で、1.10.1 により要求の対象外である

**文の案**(フェーズ5。説明)

> テンプレートの履歴を併合した場合、併合したコミットは、適用の開始より前の製品の変更として件数に出ます。コミットのトレーラ・作者・メッセージで、テンプレート由来かどうかを見分けることはしません。誰でも書ける文字列であり、開始より前の製品の変更を件数から消す経路になるためです。

**矛盾の検査**: ADR-0083 決定5 と矛盾しない。ADR-0068 決定7 の定め1 は、R-1 の新 ADR で「手引き」へ位置付けを改める。

## R-4 実際の GitHub 上での検証の計画

**結論**

1. 検証の計画(誰が・どのリポジトリで・何を)は**本文に置かない**。保守者の活動として Issue と `research/` に置き、本文には EV-0107 の差し替え条件を、ADR-0045 決定1 に沿って**対立仮説を分けられる形**に書き直して置く
2. 検証は**保守者が自前の検証用リポジトリで行う**。採用者の記録を待たない
3. env-check の状態の値は **確認済み / 未確認の2値のまま**とし、「権限不足で読めない」は理由の区分として未確認の中に持つ
4. `checks-only`(G-6 無効)の構成で、必須チェック gate-g5 の適用を「確認済み・対象外」とする現状は、**附属書H 項目4 に対する不適合**として直す(新しい要求ではない)
5. 再確認は暦の周期ではなく、**出荷判定(G-8)ごとの集約で読み直す**向きで検討する(EV マークを付けて置く)

**理由**

- 計画は本標準の要求事項ではなく、本標準の根拠を作る保守者の作業である。規格の本文に検証の計画を書いた例は知らない(推測)。本文に置くと、計画の変更が版の改訂になる
- ADR-0045 は「待機は中立な選択ではない」とする。採用者の記録を待つと、EV-0107 は見直しの期日(2027-04)まで E2 のまま残る。作成者側の1回でも、現状の手元の試行(事実6件)より水準が上がる
- 現在の EV-0107 の差し替え条件は「通しの記録」と書くだけで、何が観測されたら定めを改めるかを書いていない(自分で確認、78〜84 行)。ADR-0045 決定1 に合わない。ただし同 ADR 決定5 は以後のマークに適用するとしているので、書き直しは新たな判断として行う
- 状態の値を増やさない理由: 1.7.3 と ADR-0049 は升の語を閉じた語彙に保つ。採用判断者にとって「権限不足」も「未適用」も、統制が確かめられていない点で同じであり、合否に差を付けてはならない(Scorecard が読めない設定を満たしたと数えた K5、欠落と空を混同した K6 は、いずれも値を混ぜたことが原因で、値の数の不足ではない)。理由の区分は、次に誰が動くか(管理者の権限を持つ人)を示すために要る
- `checks-only` の穴: `adoption-trial.mjs` 1304 行は、G-6 が無効かルールセットが無いと、ルールセットの項目を `status: 'confirmed', notApplicable: true` にする(自分で確認)。初期化は `checks-only.json`(必須チェック gate-g5)の適用を案内する(内部 2.1)。確かめる対象(必須チェック)があるのに「確かめる項目なし・確認済み」と出すのは、附属書H 項目4「未実施と『対象なし』の区別」「検査の手段が構成に書かれていることを、実施と読まない」(規定、自分で確認)と、`gate-criteria.md` 597 行(入力の欠如を対象なしにしない)の趣旨に反する。本文を改めるのではなく、実装を本文に合わせる
- 再確認: 確認済みの記録は構成が変われば未確認へ戻る(`adoption-guide.md` 517 行、自分で確認)。しかし、構成を変えずに管理者が GitHub 上でルールセットを外した場合は戻らない。safe-settings・Allstar(K7・K8、外部)は継続の検出を置く。新しい周期を作らず既存のゲート(G-8)に付けるのは、第8章「新しいゲート・会議体・台帳を設けません」の型に合わせるためである。ルールセットの規則は非管理者の権限でも読めるとされる(K5、外部。自分では確かめていない)ので、CI の権限で読めるかは試してから決める

**他の案を落とす理由**

| 案 | 落とす理由 |
| --- | --- |
| 計画を本文に置く | 本文は採用者への要求事項の置き場である(1.7)。保守者の作業を要求の文末で書くと、採用者への要求と読まれる |
| 採用者の記録を待つ | ADR-0045 の「待機は中立でない」。附属書I の 9 回の検証もすべて作成者側が演じたもので、実環境の「確認済み」の経路は一度も通っていない(内部 5) |
| 3値目「権限不足」を状態に足す | 閉じた語彙を広げ、確認済みと未確認の間の値として読まれる余地を作る |
| 1回の確認で足りるとする | 構成を変えない設定の変更を検出しない |
| Evaluate モードで試してから有効にする手順を書く | Enterprise Cloud の文書にだけ現れる(K3、外部)。小規模の採用者に課せない |

**文の案**(EV-0107 の差し替え条件の書き直し。注記の中)

> **差し替え条件**: 観測の源は、保守者が実際の GitHub 上の検証用リポジトリ(既存のワークフロー・旧来のブランチ保護・`CODEOWNERS`・開いている PR を持つもの)へ、3つの定めに従って持ち込み、初期化から最初の出荷の集約までを通した記録です。統制が効いていないのに、初期化の出力・G-5・実環境の統制の確認・出荷の集約のどれも未確認または失敗を出さなかった場面を数えます。1件でもあれば、その場面を止める定めを足す向きで見直します。0件で、python と go の各1件の試行でも0件であれば、根拠の水準を上げ、手順の全体を手引きとして書く向きで見直します。

**矛盾の検査**: ADR-0028(未達と省略の区別)・ADR-0077 決定3 と同じ向き。ADR-0049 と矛盾しない(値を足さないため)。`checks-only` の修正は強制層の検査の強化であり、ADR-0074 決定3・ADR-0084 の承認の規定(AI維持管理者)を経る。

## R-5 旧い版のテンプレートで生成した構成の移行

**結論**

1. 構成に**形式の版**を持たせ、`schemaVersion` の意味を「形式の版」に改める(連鎖の有無は形式の版から導く)。**対応していない版(実装が知るより新しい版を含む)は読まずに失敗させる**
2. 移行の型は**宣言した移行を `/process-change` で実行し、PR として人に見せる型**(Copier・Terraform 型)を採る。読み替えを無期限に続ける型と、猶予期間の型は採らない
3. A-3 で落ちる構成は、**落ちることを正しい表示として保つ**。経路は既存の `/process-change` による再生成で、移行の型の1件として登録する
4. 版の欄の無い宣言と D-0 は、**遡って書き換えない**。版の欄を足した時点からを記録し、それより前は 1.10.3 のとおり記録の欠落として残す

**理由**

- 未知の版を黙って通す実装は、読めた範囲の前例に無い(Terraform はエラー、Copier は最低版で中止。外部 §2・§5-7)。現状の `chainProblems` は `schemaVersion` が `CHAINED_SCHEMA_VERSION` 未満のときだけ問題にし、2 以上の値をそのまま通す(`config.mjs` 1661 行、自分で確認)。新しいテンプレートで書いた構成を旧いテンプレートの検査が読むと、知らない欄を無視して通る
- 読み替えの型(Renovate)は、名前の変更には向くが、意味が変わる移行(A-3 のように、同じ値が別の主張になるもの)を黙って読み替えると、構成の主張と実態がずれたまま通る
- 猶予期間の型(Kubernetes)は、1.10.1「経過措置を設けない」と 1.10.3「移行の期間を設けない」(自分で確認)、A-3 の審議で猶予を置かなかった判断(内部 2.3)と当たる
- A-3 で落ちる構成は、確認者を確かめられないのに G-6 を未達と表示しない構成であり、構成が実態と違う主張をしている。ADR-0028 の立場では、落ちることが正しい。移行は、その主張を直す手段であって、落ちないようにする手段ではない
- 版の欄の無い宣言を遡って埋めない理由は、テンプレート README 488〜495 行(遡及改変の禁止)と同じで、記録の訂正を履歴として残す作法(推測D)にも合う。宣言の版の欄を足すことは新しい日付の宣言の更新であり、過去の期間の欠落を消さない

**標準の版との関係(重要)**

- 1.10.3 は、旧い版に従う案件が旧い版への主張を期限なく続けてよいとする。一方で、テンプレートの検査は常に最新の実装で判定する。採用者が第1版で宣言した後に、第2版の要求事項を実装したテンプレートの更新を取り込むと、第1版の案件が第2版の要求で落ちる
- 版が未発行の今は全採用者が作業中の版にいるので、問題は現れていない。第1版の発行の前に決める必要がある
- 本意見の案: **要求事項を変える検査の変更を含むテンプレートの更新は、本標準の版の切り替え(`/process-change` 種別 `edition`、第8章 要求事項1〜4 のやり直し)と同時にだけ取り込む**。テンプレートが版ごとに旧い検査を保つ案は、保守の負担ではなく、旧い検査の欠陥を直せなくなる点で信頼性を下げるので採らない(EV-0159 の差し替え条件「欠陥のある版」と同じ問題を、実装の側で抱え込むため)

**他の案を落とす理由**: 上の理由の各項のとおり。加えて「移行のスクリプトを置かず、再初期化を求める」案は、再初期化が全問を聞き直し、何が変わったかを特定できない(第8章 110 行の理由と同じ)ため採らない。

**文の案**(第1章 1.10.3 の項目として追加。である調)

- 準拠テンプレートの更新のうち、要求事項・禁止・判定基準を実装する検査を変えるものは、版の切り替えと同時に取り込む。版を切り替えずに取り込んだ案件は、取り込んだ検査が実装する版に従うものとして表示する

(フェーズ5。説明)

> 構成は形式の版を持ちます。検査は、自身が対応する版と異なる形式の版の構成を読まずに失敗させます。旧い形式の構成は、`/process-change` が宣言された移行を適用して新しい形式へ改め、その差分を PR で示します。版の欄の無い D-0 には、欄を足した日付から版を記録し、それより前を書き換えません。

**矛盾の検査**: 1.10.1・1.10.3・ADR-0083 決定1 と矛盾しない(猶予を置かない)。1.10.3 の「旧い版への主張を期限なく続けてよい」と、テンプレートの検査が最新で判定する実装との間に、**現にある潜在の食い違い**を上で指摘した。どちらが誤りかは、文面からは本文が正で、実装の取り込み方の規則が欠けている。

## R-6 テンプレートの更新の取り込みと、既存の採用者を壊す変更

**結論**

1. 採用者が取り込んだ**準拠テンプレートの版(コミット)を構成に記録する**。書くのは取り込みの道具だけで、手で編集しない(既存の「構成を手で編集しない」規則の範囲)
2. 採用者を壊す変更の規則は2層に分ける
   - 保守者の義務(告知・移行の手段): **`community/standard-editions.md`(標準の保守の手続)**に置く。本文に置かない
   - 採用者の義務(取り込みの判断の記録): 新しい要求事項は作らず、既存の「統制の設定の陰性の確認」(`gate-criteria.md` 519 行)と強制層の変更の承認(ADR-0074 決定3・ADR-0084)に乗せる。R-5 の 1.10.3 の項目で、要求を変える取り込みを版の切り替えに結び付ける
3. **猶予期間は置かない**。採用者は取り込む時点を選べるので、取り込まないことが事実上の猶予になる。取り込んだ後に落ちることは、統制として受け入れる
4. テンプレート README 485〜486 行(「技術判断(G-3/例外承認等)に委ねられます」「促してください」)は、上の2の採用者の義務の所在を引く説明の文に置き換える
5. #332 との分担: #315 は**版の記録と告知**、#332 は**受け取った配布物の真正性と一致の検査**

**理由**

- 生成元の版を記録して手で書き換えない型は、Copier・cruft に共通する(T1〜T3、外部)。記録が無いと、採用者の検査がどの版の実装で判定したかを、出荷の証跡から再現できない。附属書H の開示が「どの検査で判定したか」を名指せないことは、証跡の再現性の欠陥である(推測を含む。H の各項目に版の欄が要るかは確かめていない)
- 保守者の義務を本文に置かない理由: 本文は採用者への要求事項の置き場である(1.7)。ADR-0083 も、版の発行の手続を本文でなく `community/standard-editions` に置いた(決定1 の末尾、自分で確認)。同じ分け方に揃える
- 保守者が告知する中身: 更新ごとに、新たに失敗しうる検査、その検査が実装する本文の条項(または実装の欠陥の修正であること)、移行の手段。区分は R-5 の「要求事項を変える検査の変更か、実装の欠陥の修正か」で、前者は版の番号 N の改訂と対応する(1.10.3 の N の境、EV-0158)
- 猶予を置かない理由: R-5 と同じく 1.10.1・1.10.3 と当たる。ADR-0084 影響 4 が既に「落ち始めうる」ことを受け入れている(自分で確認)。受け入れるなら、その旨と移行の手段を告知の中身として必ず出すことで足りる
- 例外承認を取り込みの判断の経路にしない理由: R-1 のとおり、7.3.1 の経路の使い分けに反する

**他の案を落とす理由**

| 案 | 落とす理由 |
| --- | --- |
| 自動の同期(上流への結び付きと定期の PR) | 更新の PR は強制層を変え、AI維持管理者の承認と陰性の確認を要する(ADR-0084)。自動で流れてきても判断は人に残り、量だけが増える。結び付けの道具(cruft `link` 型)の採否は実装の判断として残し、本標準は課さない |
| 破壊的な変更に猶予期間を置く | 1.10.1・1.10.3 と当たる。猶予の間、旧い検査で通った変更が残る(ADR-0068 の却下理由と同じ) |
| 版の記録を採用者が手で書く | Copier が手での更新を禁じる理由(差分が予測不能になる、T1)と、本テンプレートの構成の規則と同じ |
| 告知の規則を本文の要求事項にする | 本文の宛先(採用者)と義務を負う者(保守者)が違う |

**文の案**(`community/standard-editions.md` に節を足す。説明と手続)

> 準拠テンプレートの更新を出すときは、新たに失敗しうる検査、その検査が実装する本標準の条項、既存の構成を改める手段を、更新の記録に書きます。条項の要求を変える検査の変更は、版の発行と組にします。

(準拠テンプレート README の 485〜486 行の置き換え。説明)

> テンプレートの更新は自動では反映されません。取り込む PR は統制の設定を変える PR であり、本標準 第4章「統制の設定の陰性の確認」と、強制層の変更の承認([ADR-0084](...))によります。要求事項を変える検査の変更を含む更新は、版の切り替え(第1章 1.10.3)と同時に取り込みます。

**矛盾の検査**: ADR-0077 決定6(`dist/standard` は本文・知識ベース・VERSION・LICENSE だけを配る)と矛盾しない。ただし配布物にテンプレートの版が無いので、構成に記録する版は準拠テンプレートのリポジトリのコミットを名指す。ADR-0064 と矛盾しない(README の文に所在を付ける形になる)。
