# 会議体の議題(#315 既存のリポジトリへ準拠テンプレートを持ち込む手順の全体)

入力: `issues-context.md`、`survey-315-1-internal.md`(内部)、`survey-315-2-external.md`(外部)。本文は `phase5-implementation/template-repository.md`「既存のリポジトリへ持ち込む」(38〜84 行、EV-0107、IMPL-0123)、第1章 1.10.3(`overview.md` 505 行)、ADR-0083(94 行)・ADR-0084(187 行)。テンプレートは `template/scripts/gate/`(`generate-profile.mjs`・`adoption-trial.mjs`・`aggregate-evidence.mjs`・`verify-gate-contract.mjs`・`check-process-rules.mjs`)と `template/README.md`(479〜510 行)。

## R-1 手順の全体の置き場(標準 / テンプレートの文書)
- 現状: 標準は事実 6・定め 3 だけで、手順の全体は定めないと 42 行で明言。テンプレートの README は更新を「各案件の技術判断」へ委ねる(要請の書き方。標準に対応する条項が無い)
- 外部: 規格(12207 の Annex A・33001・共通フレーム2013)は持ち込みの手順を定めず、テーラリングと適合の形を定める。手順は改善の手引き(CMMI Adoption Guidance v4.0: 現状の対応付け → 差の特定 → 実際に使われているかの確認 → 段階の展開 → 検証)にある
- 問い: 標準に要求事項(何を満たせば持ち込めたと言えるか)を置き、手順はテンプレートの文書に置くか。標準に置く要求事項は何か(既存の資産の棚卸し・適用の開始の時点・開始前の履歴の扱い)

## R-2 初期化が既存のリポジトリで検出し、告げ、止まること
- 現状: 初期化は git を呼ばず、既存のコード・履歴を検出しない。`coverage` のスクリプトの欠落を告げない。目印の無い既存の `CLAUDE.md` は警告だけで続行し、後で CI が落ちる。`CODEOWNERS`(`@OWNER` の置き換え)と `.gitignore` の行を確かめない(IMPL-0123 の注記)。スキルにはファイルから技術スタックを推測しない規則がある(`SKILL.md` 210 行)
- 外部: Claude Code は CLAUDE.md があると AGENTS.md を読まず、矛盾する指示はどちらにも従い得る。CODEOWNERS は3つの置き場の最初だけが効き、不正な行は黙って飛ばされる。Renovate は持ち込みの PR が併合されるまで何も変えない。既存の負債は記録した基準線で新規の違反だけを止める形(ESLint の bulk suppressions、diff-cover)。基準線の確定は人
- 問い: 何を検出して止め、何を告げるだけにするか。既存の指示ファイル(CLAUDE.md・AGENTS.md・入れ子)。カバレッジの欠落。既存の違反の基準線を認めるか(閾値の緩和との区別)

## R-3 併合した履歴と適用の開始
- 現状: 証跡の集約は、親の無いコミットでファイルがすべてテンプレートの一覧に一致するものだけをテンプレート由来と見る。併合した履歴は製品の変更に見える。ADR-0083 は適用の開始を `configured: true` の最初のコミットとした
- 外部: SLSA Source v1.2 は、統制の主張を特定の開始のリビジョンから途切れなく続けることを求め、それより前は主張しない。トレーラは自由記述で出所を証明しない
- 問い: 開始のリビジョンより前の履歴を集約の対象の外とするか。テンプレート由来の識別を何で行うか

## R-4 実際の GitHub 上での検証の計画
- 現状: env-check の「確認済み」の経路は実環境で一度も動いていない(読み取りだけを実行し 3 項目とも未確認)。G-6 が無効か `checks-only` の構成では、ルールセットの項目を「該当なしで確認済み」にし、`gate-g5` の必須チェックの適用を確かめない(`adoption-trial.mjs` 1304 行)。既存のワークフローとの共存、旧来のブランチ保護との重なり、開いている PR への影響、`@OWNER` の置き換え、初期化の PR が実環境で `gate-g5` を通るかを見ない
- 外部: 管理者の権限が無いと読めない項目を満たしたと数える例(Scorecard)。欠落と空の取り違え(Terraform provider)。パスの絞りで必須チェックが飛ぶと PR が永久に待つ。ブランチ保護とルールセットは重なり、厳しい側が効く。Evaluate モードは Enterprise Cloud の文書にだけ現れる。safe-settings・Allstar は継続の逸脱の検出
- 問い: 検証の計画(誰が・どのリポジトリで・何を)を標準に置くか。env-check に「権限不足で確かめられない」の結果を分けるか。一回の確認か定期か。`checks-only` の穴を塞ぐか。EV-0107 を差し替える条件

## R-5 旧い版のテンプレートで生成した構成の移行
- 現状: 版の欄は `schemaVersion`(ハッシュ連鎖の有無の 0/1)だけ。移行のスクリプトは無い。旧い構成は読み込み時に既定値で補う。A-3 の帰結で、旧い 1〜2 人の構成(G-6 を `omitted` にした S0 等)と、独立レビュアが出荷判定者を兼ねる 3 人以上の構成が契約検査で落ちる。猶予は設けなかった。#313 は版の欄の無い旧い宣言と D-0 の移行を #315 へ送った
- 外部: 3つの型(Renovate: 旧い名前を読み続け書き換えの PR を出す / Copier・Terraform: 版ごとの移行を宣言 / Kubernetes: 非推奨の期間と往復の無損失)。どれも未知の版を黙って通さない
- 問い: どの型を採るか。未知の版・旧い版をどう扱うか(拒否・読み替え・移行の PR)。A-3 で落ちる構成への経路。版の欄の無い宣言と D-0

## R-6 テンプレートの更新の取り込みと、既存の採用者を壊す変更
- 現状: 自動の同期は無い。`dist/standard` は本文・知識ベース・VERSION・LICENSE だけを配り、スクリプト・スキル・CLAUDE.md・ワークフローは配らない。テンプレートは `dist/standard` を参照しない。更新の PR は統制の設定に当たるファイルを変えるので、陰性の確認の記録が要る。#314 の常駐の規則・参照切れ、A-3、ハッシュ連鎖、#296 の `nameConfirmed` が既存の採用者を壊した例
- 外部: Copier・cruft は生成元のテンプレートの版と回答を記録し、手で編集しない。cruft だけが既存の案件を後からテンプレートへ結び付ける(`link`)。GitHub のテンプレートリポジトリは一回きりの複製で生成元への結び付きが無い
- 問い: 採用者が取り込んだテンプレートの版を構成に記録するか。採用者を壊す変更(検査の強化)を出すときの規則(告知・猶予・移行の手段)を標準・ADR に置くか。#332(受け取り側の検査)との分担
