## 1. 擁護の総論

本件の調査は「足りないもの」を多く挙げますが、そのうちの多くは**統制の穴ではなく、開示の過多か、後段の検査で止まっているもの**です。穴と過多を分けずに足すと、規定が肥大し、どれが統制でどれが案内かを読み手が区別できなくなります。

- 安全側に倒れているもの(擁護する): 併合した履歴が「製品の変更 47 件」と出ること(過多の開示。V7)、旧い構成が契約検査で落ちること(隠れた未達の検出。V8)、`coverage` の欠落で G-5 が落ちること(fail-closed)
- 危険側に倒れているもの(変えるべきと認める): env-check の `checks-only` の「確認済み」(V2)、目印の無い `CLAUDE.md` で適用の開始が切られること(V1)、未知の版を通すこと(V5)、README の語の取り違え(V3・V4)

ADR-0068 決定7 が手順の全体を先送りにした理由(「確かめていない手順を示すと、読み手は従った結果を本標準に帰す」)は、#315 の時点でも何も解消していません。実 GitHub での通しの記録も、python・go の試行も、今回の調査で増えていません(内部 5 節、外部 4 節末)。**理由が残っている決定を覆すには、新しい事実が要ります**。

## R-1 手順の全体の置き場

**結論**: 案「標準は手順の全体を定めない(ADR-0068 決定7・EV-0107 を維持)。標準に置く要求事項は、既に第1章 1.10.1 と template-repository の3つの定めにあるものに留め、新しい要求事項は1つだけ足す(開始の前に止まるべき条件)。手順はテンプレートの文書に置き、標準はそれを要求事項とみなさない」を採ります。

**理由**

1. 外部の調査は、12207(第1版・第2版)・共通フレーム2013・33001 のいずれも持ち込みの手順を本体に置かず、採用者の改善計画(CMMI Adoption Guidance)に委ねていると報告しています(外部 1 節の結論)。規格の作法として、現行の「定めない」は先例と一致します(根拠: 外部。規格は本文未読のため EV が要る点も外部の指摘どおり)
2. 「何を満たせば持ち込めたと言えるか」は、本標準では既に答えが出ています。**持ち込めたかどうかという状態を設けない**のが第1章 1.10.1 の意図的な決定(「導入中」を設けない)です。開始の後は導いた要求事項のすべてが掛かり、満たさないものは4つの表示に出ます。「持ち込みの完了」の要求事項を新設すると、1.10.1 が退けた「段階の呼び名」を裏口から入れることになります(ADR-0068 却下表「準備中などの案件の状態を新設する」と同じ失敗)
3. 「既存の資産の棚卸し」を要求事項にする案には反対します。棚卸しの記録は存在を示せても、内容の十分さを判定できません(CMMI 自身が「存在」と「使用」を分けよと書くのは、存在の記録が使用を示さないからです。外部 S4)。判定できない要求事項は、記録の様式を埋める遵守を生みます(#300・#310 C-9 で「内容の良否は課さない」とした理由と同じ)
4. 一方、README の規範(V4)は標準に根拠の無い要求を採用者へ課しており、しかも例外承認の経路を誤用しています。これは直すべきです

**他の案を落とす理由**

- 「手順の全体を標準に置く」: ADR-0068 決定7 の理由が解消していない。未検証の手順を標準の名で示すと、従った結果の不具合を標準に帰すことになる
- 「要求事項(棚卸し・開始の時点・開始前の履歴)を標準に新設する」: 開始の時点と開始前の履歴の扱いは 1.10.1 に既にある(二重化すれば2つ目の規範になる。#306 B-2 で一覧を置かなかった理由と同じ)。棚卸しは上の理由3

**文の案**(template-repository.md「既存のリポジトリへ持ち込む」の冒頭の段落の次へ。本文)

> 持ち込みの手順は、準拠テンプレートの文書が示します。その手順は本標準の要求事項ではなく、従ったことは適合の根拠になりません。本標準が持ち込みに課すのは、第1章 1.10.1 の適用の開始の規定と、下の定めだけです。

テンプレート README 485〜486 行は、次の規範に置き換えることを求めます(テンプレート独自の印を付ける)。

> - テンプレートの更新の取り込みは、強制層の変更として扱う(`state:needs-platform`)。取り込むかどうかの判断を、例外承認の経路で扱わない

**既存との矛盾**: 無し。ADR-0068 決定7・1.10.1・#310 C-7(フェーズ5 は本文に従属)と整合します。README の V3・V4 は ADR-0028・ADR-0083 決定3 と矛盾しており、誤りは README の側です。

## R-2 初期化が既存のリポジトリで検出し、告げ、止まること

**結論**: 「止める」は1つ(目印の無い既存の `CLAUDE.md`)に限り、**構成を書く前に**止める。`coverage` の欠落・既存のコミットの有無・入れ子の指示ファイル・`AGENTS.md` は告げるだけ。`CODEOWNERS` は `@OWNER` の残存と置き場の重複だけを機械で確かめる。**既存の違反の基準線の仕組みは新設しない**。

**理由**

1. 目印の無い `CLAUDE.md`: 後段の `check-process-rules`(gate-entry)で止まるので、統制の穴そのものではありません。しかし V1 のとおり、初期化は構成を先に書くので、そのまま初期化のコミットを作ると**適用の開始が、常駐の規則を欠いた状態で切られます**。ADR-0083 決定5 は開始を動かさないので、後から直しても開始の時点の欠けは残ります。開始の前に止めれば、これは開始より前の準備(1.10.1)の中で解決できます。止める位置を前へ移すだけで、新しい規範は要りません。ADR-0083 決定5 を守るための変更です
2. `coverage` の欠落: G-5 が fail-closed で止めます(事実4)。初期化で止めると、`undetermined` のスタックや go(`coverageSummary: null`、#330)で、初期化そのものができなくなります。告げるだけで足ります
3. 既存の履歴・コードの検出: 開始より前の変更は要求事項の対象外(1.10.1)で、集約は件数を開示します(V7)。止める理由がありません。告げることは許容しますが、**検出の結果で設問の回答を埋めてはならない**(スキル 210 行の禁止)。検出と推測を分けて書く必要があります
4. 入れ子の `CLAUDE.md`・`AGENTS.md`: 外部 P1・P2 のとおり矛盾は黙って片方が選ばれますが、矛盾しているかを機械は判定できません。ADR-0084 は照合をファイルの単位の閉じた集合で行うと決めました。入れ子のファイルを一律に拒否すると、正当なモノレポを止めます。**一覧を告げ、人へ渡す**のが、判定できないものを判定したことにしない形です
5. `CODEOWNERS`: 外部 K10 のとおり、不正な行と置き場の重複は失敗せず黙って無効になります。`@OWNER` の文字列の残存と、`.github/`・ルート・`docs/` の複数の置き場は、偽陽性の無い決定的な検査で確かめられます(ADR-0073 決定2 の3条件を満たす)。IMPL-0123 の note「確かめない」のうち、この2点は降ろすべきです。`.gitignore` は否定のパターンがあるため行の存在では判定できず、行の照合は偽の安心を生みます。確かめるなら `git check-ignore` で代表のパス(証跡・秘匿情報)を判定する形に限ります
6. 基準線(ESLint の bulk suppressions 型): **反対します**。外部 5 節 9 自身が「基準線は閾値の緩和と見分けがつかない」と書いています。本標準は既に、基準を満たさないまま進める経路を3つ(例外承認・前提の受容・未解決事項)に閉じ、その場で選ばないと決めています。基準線は4つ目の経路になり、禁止事項6(閾値・除外を機能変更と同じ PR で変えない)の外で既存の違反を合法化します。網羅率については V6 のとおり差分の網羅率の経路が既にあります

**他の案を落とす理由**

- 「検出したものをすべて止める」: 開始より前の事柄で止めることになり、1.10.1 の「開始前は対象外」と食い違う。go・`undetermined` で初期化が不能になる
- 「告げるだけで、`CLAUDE.md` も止めない(現行)」: V1 の帰結(開始の時点に欠けが固定される)を残す
- 「基準線を、人の記名で確定させて認める」: 人の記名があっても、経路が4つになることは変わらない。前提の受容(技術負債台帳)で同じ事態を記録できる

**文の案**(template-repository.md の定め2 の理由の後へ。本文と箇条)

> 準拠テンプレートの初期化は、目印の無い既存の `CLAUDE.md` を見つけたら、構成を書く前に止まります。止まらずに構成を書くと、常駐の規則を欠いた状態が適用の開始になるためです。
>
> - 初期化は、既存の `coverage` のスクリプトの欠落、入れ子の指示ファイル(`CLAUDE.md`・`AGENTS.md`)、`.github/CODEOWNERS` 以外の置き場の `CODEOWNERS` を告げる。告げた内容で設問の回答を埋めない
> - `CODEOWNERS` に雛形の所有者(`@OWNER`)が残っていること、置き場が複数あることを、機械で確かめる
> - 既存の違反を基準線として記録し、新しい違反だけを止める仕組みは設けない。既存の違反は、基準を満たさないまま進める3つの経路のいずれかで記録する

**既存との矛盾**: 無し。ADR-0083 決定5 を守る方向。IMPL-0123 の note は、降ろした部分に合わせて改める(マークの更新)。

## R-3 併合した履歴と適用の開始

**結論**: **現行を維持します**(定め1「併合しない」+ 開始前は件数の開示だけ)。テンプレート由来の識別を広げる仕組み(既知のテンプレートのコミットの照合・トレーラ)は採りません。開示の文に「開始前の履歴は準拠の証跡に数えない」ことを明示する1文だけを足します。

**理由**

1. 併合した履歴が「製品の変更 47 件」と出ることは、**過多の開示**であって統制の穴ではありません(V7)。開始前の変更は欠落にも証跡にも数えないので、誤って主張が強まる経路がありません。安全側に倒れた現象を、識別の仕組みを足して消す必要は薄いです
2. SLSA Source v1.2 の「開始リビジョンより前に主張しない」(外部 K12)は、ADR-0083 決定5 と 1.10.1(開始前は対象外)と**既に一致**しています。外部の調査は現行を補強しており、変更の根拠になりません
3. テンプレート由来を「識別」する仕組みは、新しい穴を生みます。トレーラは誰でも書け(外部 K13)、既知のコミットの一覧の照合は、テンプレートの側がハッシュの一覧を保守し続ける負担と、一覧の改竄・取り違えの検査を新たに要します。いずれも、件数を減らすほうへ働く仕組みであり、**開示を減らす向きの仕組みは誤れば隠す経路になります**(ADR-0028 決定3「隠す経路を設けない」)
4. 定め1 は、併合という操作そのものを持ち込みで行わないと定めており、原因の側で止めています

**他の案を落とす理由**

- 「開始前の履歴を集約の対象の外とする(件数も出さない)」: 開始前に製品のコードを大量に変えてから初期化する形(開始の直前の駆け込み)が見えなくなる。件数の開示は、開始の時点の選び方を読み手が評価する材料
- 「既知のテンプレートのコミットの一覧で識別する」: 上の理由3

**文の案**(template-repository.md「持ち込みのコミットは、構成の初期化より前に置きます」の段落の末尾へ。本文)

> 適用の開始より前の履歴は、併合したテンプレートの履歴を含めて、準拠の証跡に数えません。件数を開示するのは、開始の時点より前に何が変わったかを読み手が知るためであり、その変更が本標準に従ったことを示すものではありません。

**既存との矛盾**: 無し(ADR-0083 決定5・1.10.1・定め1 と同じ向き)。

## R-4 実際の GitHub 上での検証の計画

**結論**: (1) env-check の `checks-only`・G-6 無効の「確認済み・対象外」(V2)は**塞ぎます**(変えるべきと認める)。(2) 「権限不足で読めない」は、状態を3つ目に増やさず、`unconfirmed` のまま理由の区分として出します。(3) 検証の計画(誰が・どのリポジトリで)は標準に置かず、Issue と調査メモに置きます。EV-0107 の差し替え条件は現行のまま維持します。(4) 定期の再確認は課さず、確認の日時を出荷の証跡に出すことを求めます。

**理由**

1. V2 は、ADR-0028 の考え方(目的を達成する構成を示せないものを、成立していると表示しない)に反します。初期化が `checks-only` の適用を案内しておきながら、その適用を読まずに「確認済み」とするのは、外部 K5(Scorecard が読めない要件を満たしたと扱う)と同じ型の誤りです。ここは擁護できません。G-6 無効でも、必須チェック `gate-g5` が既定ブランチに効いているかは確かめる対象です
2. 「権限不足」を独立の状態にする案には、半分だけ賛成します。外部 K6 の「欠落と空の取り違え」は防ぐべきですが、状態の値を増やすと、「未確認(権限不足)」が「未確認」より軽い値として読まれ、事実上の第3の合格になります。**状態は `confirmed` / `mismatch` / `unconfirmed` のまま**とし、`unconfirmed` の理由に「権限不足で読めない」を区別して書く(識別の鍵の欠落と、応答の欠落を混ぜない)のが、ADR-0028 の型(表示は消さず、理由で区別する)と合います
3. 検証の計画は保守者の作業であり、採用者への要求事項ではありません。標準の本文に保守者の試験計画を置くと、計画の実施状況が規範の一部になり、未実施のときに規範が空文化します。EV-0107 の差し替え条件(実 GitHub での通しの記録の4項目と、python・go の試行)は既に「何があれば差し替えるか」を定めており、計画の受け皿として足ります。不足は、env-check の「確認済み」の経路が実環境で一度も通っていない(内部 5 節)ことを差し替え条件へ足すことだけです
4. 定期の再確認(safe-settings・Allstar 型。外部 K7・K8)は、乖離の検出として有効ですが、周期の値に根拠がありません。根拠の無い周期を課すと EV が増えるだけで、周期の間の乖離は相変わらず見えません。確認の時点を出荷の証跡に出せば、古い確認は読み手に見えます。周期の導入は、採用者の記録(#338 の経路)が集まってから判断するべきです
5. Evaluate モードを前提にしない(外部 K3)は賛成です。現行の手順も前提にしていません

**他の案を落とす理由**

- 「計画を標準に置く」: 上の理由3
- 「定期の再確認を課す」: 上の理由4。値の根拠が無い
- 「`checks-only` は G-6 無効の構成なので対象外のままでよい」: 初期化が適用を案内している統制を、確かめずに確認済みと出す。擁護できない

**文の案**(template-repository.md「実装の制約」または ci-gates の集約の項目4 の近くへ。箇条)

> - 実環境の統制の確認は、構成が独立レビュー(G-6)を要しない場合も、必須チェック(`gate-g5`)が既定ブランチに効いているかを確かめる。確かめずに確認済みとしない
> - 読み取りの権限が足りずに読めなかった項目は、未確認とし、権限の不足を理由として記録する。読めなかった項目を、満たした項目にも該当しない項目にも数えない
> - 出荷の証跡には、実環境の統制の確認を行った日時を出す

EV-0107 の差し替え条件へ足す1項目(注記の中):「実環境の統制の確認が、実際の GitHub で確認済みに至った記録」。

**既存との矛盾**: (1) は IMPL(env-check の降ろし先)の note の改訂を要します。ADR とは矛盾しません。附属書I I.11 要件⑦ の文言が「確認済み」の定義を持つなら、それと突合が要ります(未確認。突合の段で確かめてください)。

## R-5 旧い版のテンプレートで生成した構成の移行

**結論**: **A-3 で猶予を設けなかった判断を維持します**。移行の型は「拒否 + 拒否の文の中の移行の経路(`/process-change` での再生成)」(現行)を正とし、Kubernetes 型の猶予期間と Renovate 型の黙った読み替えは採りません。足すのは2つ: 未知の版(既知より大きい `schemaVersion`)の拒否(V5)と、版の欄の無い宣言・D-0 は**記録の欠落のまま残し、遡って書き換えない**ことの明記です。

**理由**

1. A-3 で落ちる構成は、**未達であるべきものが未達として表示されていない構成**です。落とすことは、ADR-0028 決定5(未達の記録が無い状態への書き換えを失敗させる)の実装であって、採用者を「壊す」ことではありません。猶予を置くと、猶予の間、隠れた未達を承知で表示しないことになります。これは ADR-0028 が退けた「期間で消える表示」の裏返し(期間の間だけ現れない表示)です
2. 1.10.1 は経過措置を設けないと定め、ADR-0083 決定1 は移行期間と失効を置かないと定めています(EV-0159)。テンプレートの構成の移行にだけ猶予を置けば、本文と実行層で経過措置の有無が食い違います
3. 外部の3型は、どれも**正しかった構成の形が変わる**場合の型です(名前の変更・形式の変更)。A-3 は、**元から誤っていた表示を検出した**場合であり、型が違います。前例の当てはめを誤らないよう区別するべきです。形式だけが変わる場合(`standard` の欄の無い構成、`coverageScope` の無い構成)は、現行も既に読み替えで動かし続けています(Renovate 型)。つまり現行は、**形式の変更は読み替え、表示の誤りの検出は拒否**という使い分けをすでにしており、これは筋が通っています
4. 移行のスクリプト(Copier 型)は、外部 T9(ESLint)のとおり、ロジックを持つ構成を写せません。本件の移行は体制(名簿・席)の事実の記入を要し、機械が変換できるものではありません。人が `/process-change` で記名する現行の経路が正しいです
5. 未知の版の拒否は、外部のすべての前例が一致しており(外部 5 節 7)、現行の穴です(V5)。認めます
6. 版の欄の無い宣言・D-0: 1.10.3 は既に記録の欠落に数えると定めています。移行の手順を作って欄を「埋める」と、README の禁止(過去の欠落を埋め戻さない)と衝突します。**次の宣言のやり直し(再テーラリング)から欄を書き、過去の欠けは欠落のまま残す**のが ADR-0028 決定3 と README 2 節に合います

**他の案を落とす理由**

- 猶予期間(Kubernetes 型): 理由1・2
- 黙った読み替え(A-3 の構成を読み替えて通す): 未達の表示を機械が消す経路になる。ADR-0028 決定5 と正面から矛盾
- 移行のスクリプト: 理由4

**文の案**(template-repository.md に「旧い版で生成した構成」の小節を足す。本文と箇条)

> 準拠テンプレートの検査を強めたとき、旧い版で生成した構成が契約の検査で落ちることがあります。落ちるのは、強めた検査が、旧い構成の表示の誤り(未達であるべきものが未達でないなど)を見つけた場合です。この場合に猶予の期間を設けません。猶予の間、誤った表示が続くためです。
>
> - 構成の形式だけが変わった場合(欄の追加)は、欄の無い構成を従来の意味で読み続ける
> - 検査を強めた結果として落ちる構成には、拒否の文の中で、直す経路(`/process-change`)を示す
> - 準拠テンプレートが知らない構成の版は、拒否する。読めた範囲で読み進めない
> - 版の記載の無い宣言と D-0 体制図は、記録の欠落のまま残す。遡って版を書き足さない。次にテーラリングの宣言をやり直すときに、版を書く

**既存との矛盾**: 無し。ADR-0028 決定5、1.10.1(経過措置なし)、ADR-0083 決定1(移行期間なし)、1.10.3(D-0 の欠けは記録の欠落)、README 2 節と同じ向きです。ADR-0083 決定5 の「旧い構成の移行は #315 で扱う」には、本結論で答えます。

## R-6 テンプレートの更新の取り込みと、既存の採用者を壊す変更

**結論**: (1) 採用者を壊しうる検査の強化に**猶予は置かない**(R-5 と同じ理由)。(2) 代わりに、テンプレートの保守者に**告知の義務**を置く: 落ちうる構成・検査と直し方を、更新の記録に書く。置き場は標準の本体ではなく保守の手続(`community/standard-editions` の隣、または同ページ)。(3) 採用者の構成へ「テンプレートの版」の欄を新設することは**採りません**。取り込んだテンプレートのコミットは、取り込みの PR の記録に書きます。(4) 受け取り側の検査は #332 に委ね、本件では重ねません。

**理由**

1. 告知は、統制を緩めずに採用者の手戻りを減らせる唯一の手段です。ADR-0084 は「落ち始めうる」を影響に書いただけで、採用者が更新の前に知る経路がありません。これは認めます
2. 告知の義務を標準の本体(採用者への要求事項)に置くのは主語の誤りです。告知するのは保守者であり、採用者ではありません。版の発行の手続を保守の手続に置いた ADR-0083 決定1 と同じ置き場が正しいです
3. 「テンプレートの版」の欄(Copier の `_commit` 型。外部 T1〜T3)に反対する理由: 本テンプレートの取り込みは**ファイルの部分的な複製**であり(定め1・定め2、README「自動追従は行われません」)、構成に1つのコミットを書いても、各ファイルがその版である保証になりません。外部 K13(トレーラは来歴を証明しない)と同じく、書いた値は来歴の主張であって証明ではなく、**強い主張として読まれる値を、確かめる手段なしに置く**ことになります。加えて、欄の追加は構成の要約値の連鎖に入り、`/process-change` の種別を増やします。知識ベースの生成元のコミットは既に表示されています(IMPL-0305 の note)。取り込みの PR に「取り込んだテンプレートのコミットと、取り込んだファイルの範囲」を書けば、事実の記録として足ります
4. 更新を取り込む PR は、既に統制の設定のファイルの変更として陰性の確認を要し、`state:needs-platform` を経ます(内部 3 節)。新しい経路は要りません。R-1 の README の改訂で、この既存の経路を名指せば足ります
5. 「破壊的な変更なら版の N を上げる」案: ADR-0083 決定1 は、要求事項・判定基準・規則データ・必須欄の変更で N を上げると定めています。既存の要求事項を正しく実装し直しただけの検査の強化(A-3 等)は、要求事項を変えていないので N を上げる理由になりません。N を上げる条件を「採用者が落ちるか」へ広げると、版の意味が「要求の変更」から「実装の変更」へずれ、EV-0158 の基準が崩れます。告知の義務で受けるのが筋です

**他の案を落とす理由**

- 猶予・非推奨期間: R-5 の理由1・2
- 構成へのテンプレートの版の欄: 理由3
- 破壊的変更で N を上げる: 理由5
- 自動の同期の仕組み(cruft `link` 型)の新設: 部分的な複製という前提と合わず、同期の結果を人が確かめる経路(陰性の確認)を迂回しうる。#332 の受け取り側の検査が決まる前に作ると重複する

**文の案**

`community/standard-editions.md`(保守の手続。本文と箇条):

> 準拠テンプレートの検査を強める変更は、既存の採用者の構成や記録を落とすことがあります。保守者は、その変更を出すときに、次を更新の記録に書きます。
>
> - 落ちうる構成・記録と、落とす検査の名
> - 直す経路(`/process-change` の種別、または直す対象のファイル)
> - 落とす理由が、従来の表示の誤りの検出か、要求事項の変更か
>
> 検査を強める変更に、猶予の期間を設けません。要求事項を変えない検査の強化は、版の番号 N を上げる理由にしません。

テンプレート README(テンプレート独自の印を付ける。箇条):

> - テンプレートの更新を取り込む PR には、取り込んだテンプレートのコミットと、取り込んだファイルの範囲を書く

**既存との矛盾**: 無し。ADR-0083 決定1(版の N の条件・保守の手続の置き場)、ADR-0084 影響(更新で落ちうる)、ADR-0074 決定3(強制層の変更は AI維持管理者の承認)と整合します。ADR-0084 の影響の記述は書き換えず、新しい ADR(本件)で告知の義務を足します。

## 2. 新たに生む統制の穴と肥大への警告(全議題に共通)

- **状態の値を増やさない**: 「権限不足」「移行中」「持ち込み中」「基準線内」はいずれも、既存の表示(未達・記録の欠落・逸脱・列挙に無い離脱、`unconfirmed`)の外に新しい値を作り、軽い値として読まれる。1.10.1 の「導入の途中を表す状態を設けない」と同じ理由で退ける
- **開示を減らす向きの仕組みに注意する**: テンプレート由来の識別、基準線、猶予はいずれも、表示を減らす向きに働く。誤れば隠す経路になる(ADR-0028 決定3)。採るなら、減らした件数を別に開示する設計を伴う必要がある
- **規範の置き場を増やさない**: 手順をテンプレートに、要求事項を標準に置く分け方は採るが、テンプレートの手順に要求の文末(「しなければならない」)を書かない(#310 C-10 のスキルの印の規則を README にも当てる)
- **EV**: 本意見書の結論のうち、R-4 の「確認の日時を出せば周期は要らない」は推論であり、実証が無い。採用するなら EV を起こす。R-5 の「形式の変更は読み替え、表示の誤りの検出は拒否」の使い分けは、外部の前例の型の区別に依る自分の解釈であり、外部の調査に同じ区別は書かれていない
