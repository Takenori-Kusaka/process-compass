## R-1 手順の全体の置き場

### 結論
- **要求事項は本文(第1章 1.10)に置く。手順はテンプレートの文書に置く**。フェーズ5 の `template-repository.md` は、要求事項を準拠テンプレートでどう満たすかの記述へ改める
- 本文に置く要求事項は3つ。(1) 適用の開始より前に、既存の資産の棚卸しを記録する。(2) 適用の開始より前の履歴に、適用の表明と主張を及ぼさない(既存の 1.10.1 の再確認。持ち込みの場面へ明示で当てる)。(3) 持ち込みで重なる統制のファイルは、標準の規則を欠いたまま開始しない
- テンプレートの README「テンプレート更新時の既存案件への影響と運用ルール」の 1 節は、R-6 の条項を引く形へ書き直す(依頼形をやめる)

### 理由
- 本標準は他組織が従う規格。手順をテンプレートの文書にだけ置くと、テンプレートを使わない採用者には何も掛からない。棚卸しの欠けは採用者ごとに違う漏れになる
- 一方で手順(ファイルの複製の仕方、コマンドの順序)は GitHub・言語・テンプレートの版に依存する。規格の本体に置くと版の N を上げる理由が手順の都合で生じる(ADR-0083 決定1)
- 上位規格は持ち込みの手順を書かず、適合の型とテーラリングを置く(外部 S1・S2)。手順は CMMI Adoption Guidance の「現状の写し → 差 → 使われているかの確認」の順(外部 S4)。本文に置く要求事項(1)は、この「現状の写し」を要求に落としたもの

### 落とす案
- **手順の全体を本文に置く案**: 却下。GitHub・node に依存する手順が要求事項になり、python・go で未試行の手順を規範として課すことになる(EV-0107 の水準 E2 のまま規範化する)
- **テンプレートの文書だけに置く案(現状の延長)**: 却下。V8 のとおり、README に本文の対応の無い規範が既に生じている。規範の正本が2か所に分かれる状態を固定する

### 文の案(第1章 1.10.1 の末尾へ「既存の資産を持つ案件」の小節を足す。1.10.4 とせず 1.10.1 の中に置くのは、適用の開始の条件だから)

> #### 既存の資産を持つ案件での適用の開始
>
> 既に製品のコード・履歴・CI を持つリポジトリで本標準の適用を始めるときは、適用の開始より前に、次を行います。持ち込みの手順は定めません。手順は採用者の環境(リポジトリの基盤、言語)に依存するためです。準拠テンプレートでの手順は[準拠テンプレートリポジトリ](/process-compass/phase5-implementation/template-repository/)が示します。
>
> - 適用の開始より前に、既存の資産の棚卸しを記録する。対象は、エージェントへの指示ファイル(入れ子のものを含む)、CI のワークフローと必須チェック、ブランチの保護の設定、変更の所有者の定義、カバレッジの測定の手段、使っている言語
> - 棚卸しの記録は、適用の開始のコミットより前か、同じコミットに置く。記録の無い開始は、記録の欠落として表示する

> - 既存のコードが持つ違反を記録し、新しい違反だけを止める設定(基準線)は、検査の除外設定として扱う(R-2)

## R-2 初期化が既存のリポジトリで検出し、告げ、止まること

### 結論
- 初期化の前段に**事前点検**(`scripts/init/preflight.mjs`)を置く。`/process-init` は点検が止めたら生成へ進まない。点検は**ファイルと git の事実を読むだけ**で、回答を埋めない(スキルの「既存ファイルからスタックを推測しない」と両立させる。検出は表示、推測は回答の代入)
- 止める(終了コード 1、何も書かない)ものと、告げる(棚卸しの記録へ書き、続行)ものを分ける

| 項目 | 扱い | 判定の方法 |
| --- | --- | --- |
| 目印の無い既存の `CLAUDE.md` | 止める | 区間の目印の欠如。V1 の警告を停止へ改める |
| 常駐の規則を欠く既存の `CLAUDE.md` | 止める | `check-process-rules` を生成の前に同じ照合で走らせる |
| テンプレートの入口と異なる既存の `AGENTS.md`、入れ子の `CLAUDE.md`・`AGENTS.md`、`CLAUDE.local.md`、`.claude/CLAUDE.md` | 止める | 名前で走査(`node_modules` 等を除く)。人が統合し、棚卸しの記録へ「統合した/残す理由」を書くまで止める(外部 P1・P2、V7) |
| `CODEOWNERS` が3つの置き場の2つ以上にある | 止める | 最初の1つだけが効く(外部 K10) |
| `CODEOWNERS`・`.gitignore` がテンプレートの行を欠く | 止める | 行の包含の照合(定め2 の機械化。IMPL-0123 の note の穴を塞ぐ) |
| node で既存の `package.json` に `coverage` が無い | 止める | 定め3 の機械化。事実4 で G-5 が必ず落ちる |
| 既定ブランチが `main` でない | 止める | V6。`gate-g5.yml` の push 契機を改める PR を先に要する |
| 共通の祖先を持たない併合(R-3) | 止める | 併合コミットの親どうしの `git merge-base` が無い |
| `@OWNER` が残る `CODEOWNERS` | 告げる | 新規のリポジトリでも初期状態のため止めない。env-check で確かめる(R-4) |
| 既存のコミットの件数、既存のワークフロー(名前・契機・パスの絞り) | 告げる | 棚卸しの記録へ件数と一覧 |

- **既存の違反の基準線**: 本標準は基準線の仕組みを新たに設けない。既存の違反を記録して新規分だけを止める設定は**検査の除外設定**として扱い、禁止事項6 と緩める向きの変更の規則をそのまま当てる。適用の開始より前に置く基準線は準備に当たる。開始の後に基準線の件数を増やす変更は緩める向きの変更(記名を要する)。カバレッジの既存の不足は、既にある `ci.coverageScope: changed`(ADR-0079、差分で測る)で受ける

### 理由
- 事実2・4 と V1 のとおり、現状は初期化が通り、後で CI が落ちる。落ちる場所が遅いほど、適用の開始の後に未達と欠落の件数が積まれる。開始の前に止めるほうが件数の表示が正しくなる
- 外部の前例は「黙って片方が選ばれる」「黙って無効」(P1・K10・K9)。黙る経路は、ファイルの有無ではなく実効の構成で見る必要がある。初期化の時点で見られるのはファイルの層まで。実効の層は R-4 の env-check に分担させる
- 基準線を独立の仕組みにしないのは、外部 §5-9 の指摘どおり閾値の緩和と見分けがつかないから。既存の除外設定の規則に入れれば、新しい語も新しい判定者も要らず、禁止事項6 の機械の検査がそのまま効く

### 落とす案
- **全部を告げるだけにする案**: 却下。事実3 で「目印2行で通る」経路が実際にあった。告げるだけでは同型の経路を残す
- **全部を止める案**: 却下。`@OWNER` は新規のリポジトリの初期状態でもあり、止めると新規の採用者の初期化が通らない。python・go は試していないため止める条件を書けない
- **基準線を本標準の新しい経路として定める案**: 却下(上記)。経路は3つ(例外承認・前提の受容・未解決事項)に閉じており、4つ目を足す根拠が無い
- **点検がスタックを推定して回答の既定値にする案**: 却下。スキルの禁止に反する。点検は表示だけ

## R-3 併合した履歴と適用の開始

### 結論
- **適用の開始より前の履歴には主張を及ぼさない**(1.10.1 の既存の規定)を、集約の表示でも明示する。保証の開示の「構成の初期化より前に、製品のコードを変えたコミット」の行に「適用の開始より前。本標準の要求事項の対象外」を併記する。件数は出し続ける(隠さない)
- **テンプレート由来の識別は拡張しない**。代わりに、併合そのものを事前点検で止める(R-2 の定め1)。初期化の後に共通の祖先の無い併合が入った場合は、契約検査が失敗させる
- 適用の開始の境は ADR-0083 決定5 のまま動かさない

### 理由
- SLSA Source v1.2 は、統制の主張を開始のリビジョンから連続させ、前には主張しない(外部 K12)。1.10.1 と同じ形で、補強の根拠になる
- 識別を広げる手段は、テンプレートのコミットの一覧との照合か、トレーラ。一覧は採用者が持つテンプレートの版ごとに変わり、配布物に含まれない(ADR-0077 決定6 の配る中身に無い)。トレーラは誰でも書け、出所の証明にならない(外部 K13)。どちらも「テンプレート由来だから数えない」という除外を作り、除外の判定が誤れば製品の変更が開示から消える。数えすぎ(現状)は安全な向き、数え漏れは危険な向き
- 併合を止めれば、識別すべき対象そのものが生じない。止める判定(親どうしに共通の祖先が無い)は誤りの余地が小さい

### 落とす案
- **テンプレートの既知のコミットの一覧で除外する案**: 却下(上記。数え漏れの向きの誤りを作る)
- **併合した履歴を許し、境より前なので放置する案(現状)**: 却下。境より前でも、保証の開示に 47 件の「製品の変更」が出る(事実6)。開示の読み手を誤らせる
- **適用の開始を、棚卸しの記録のコミットへ動かす案**: 却下。ADR-0083 決定5 と 1.10.1(開始は動かない)に反する

### 文の案(`template-repository.md`、定めの表の後)

> 適用の開始より前のコミットは、件数だけを保証の開示に出します。本標準の要求事項の対象でないことを、同じ行に書きます(第1章 1.10.1)。テンプレート由来のコミットを件数から除く扱いは、親を持たない1コミットに限ります。それより広く除く識別は採りませんでした。識別を誤ると、製品のコードの変更が開示から消えるためです。

- 降ろし方: `aggregate-evidence.mjs` の文言(3478 行付近)、`verify-gate-contract.mjs` に「適用の開始の後の、共通の祖先の無い併合」を problems として足す
- 実装マーク: `IMPL-0314 target=evidence-aggregation state=undelivered`、`IMPL-0315 target=gate-contract state=undelivered`

## R-4 実際の GitHub 上での検証の計画

### 結論
- **検証の計画は本文に置かない**。本文は EV-0107 の差し替え条件だけを持つ(現状どおり)。計画は Issue と `research/` に置き、記録を本文の EV へ引く
- **EV-0107 を2つに分ける**: node の実 GitHub での通しの記録で差し替える部分と、python・go の試行で差し替える部分。1つの EV に束ねると、片方が済んでも差し替えられない(新しい EV を起こし、EV-0107 は node 側に狭める。採番は再利用しない)
- **env-check の状態を3値にする**: `confirmed` / `not-met`(読めて、規則が無いか満たさない)/ `unreadable`(権限・API・識別の欠如で読めない)。後の2つはどちらも確認済みに数えない。`unreadable` は理由を必須にする(外部 K5・K6)
- **`checks-only` の穴を塞ぐ**: G-6 が無効でも、既定ブランチに必須チェック `gate-g5` が効いていることを確かめる。`notApplicable` は、構成がブランチの保護を一切要しない場合に限る。初期化が常に `checks-only` を案内する以上、その場合は生じないはずで、生じたら `not-met`
- **旧来のブランチ保護との重なり**を読む(`repos/{repo}/branches/{branch}/protection`)。重なりは不合格にせず、記録へ実効値として書く(外部 K4)
- **CODEOWNERS の誤り**を `codeowners/errors` の API で読み、誤りの行が1行でもあれば `not-met`(外部 K10)
- **一回か定期か**: 人が記名する確認は、持ち込みの時点と、強制層の変化点(構成・ワークフロー・ルールセットのファイルを変えた変更の後)に要する。加えて、`ship-evidence` のワークフローが同じ読み取りを機械で行い、記名の確認との差を出荷の証跡に出す(検出の層。確認済みには数えない)。GitHub の設定はリポジトリの外で変わるため、コミットを契機にした確認だけでは乖離を見落とす(外部 K7・K8)

### 理由
- 「確認済み」の経路は実環境で一度も通っていない(内部 5)。読めなかったことを満たしたことにする検査器は実在する(外部 K5)。現行の2値は「読めない」と「無い」を同じ値にし、採用者が次に何をすべきか(権限を得る/設定する)を分けられない。ADR-0028 の「未達と省略の区別」と同じ理由で、区別を値で持つ
- `checks-only` では G-5 の結果がマージを止める唯一の機械の担保。そこを確かめないのは、確かめる価値の最も高い項目を外している(V3)

### 落とす案
- **検証の計画を本文の要求事項にする案**: 却下。計画は保守者の作業であり、採用者の要求事項ではない。本文に置くと、計画の都合で版を上げることになる
- **作成者の検証を待たず、採用者の記録だけで差し替える案**: 却下。採用者の記録の受け取りの経路は #338 で未定。作成者の検証用リポジトリ(個人と組織の2種、組織はルールセットの読める権限で)で先に通す
- **Evaluate のモードで試してから有効にする手順**: 却下。無料の文書に状態が無い(外部 K3)。小規模の採用者に課せない
- **env-check を持ち込みの1回に限る案**: 却下(上記の乖離)
- **定期の機械の読み取りを確認済みに数える案**: 却下。人の記名を要する現行の規則(CLAUDE.md「AI が確認済みにしない」)と、検出の層の規定に反する

## R-5 旧い版のテンプレートで生成した構成の移行

### 結論
- **型は「版の欄 + 版ごとの直接の移行 + PR として人に見せる」**(Terraform の state upgrader と Copier の `_migrations` の組み合わせ)を採る
- 構成へ**形式の版**の欄 `formatVersion`(整数)を足す。`schemaVersion` の意味(連鎖の有無)は変えない。意味を広げると、既存の値の解釈が2通りになる
- 移行は `/process-change` の種別 `migrate` で行う。旧い形式の版ごとに、現行の版への直接の変換を1つずつ持つ(連鎖しない)。出力は PR で、強制層の変更として AI維持管理者が承認する
- **未知の版(現行より新しい、または変換の無い版)は契約検査が失敗させる**。黙って読まない
- **猶予の期間は置かない**。旧い形式の構成は、移行するまで契約検査が落ちる。A-3・要約値の連鎖・`nameConfirmed` の現行の扱いを、この規則の事例として位置付ける
- **移行は判定の値を書き換えない**。A-3 のように、規則の強化で構成の値(G-6 の状態)が変わる場合、移行は値を変えず、契約検査の失敗のまま `/process-change`(種別 `accountable`・`settings`)の記名の変更へ渡す
- 既定値で補って読む既存の欄(`standard` の無い構成、`seats`、`ci.coverageScope`)は、**従来の挙動の維持として読み続ける**(Renovate の型)。ただし移行の PR で、補った値を明示の値として書くかを人に示す。`standard` は ADR-0083・IMPL-0305 の規定(欄を足すのは種別 `edition` だけ)を優先し、移行でも足さない
- **版の欄の無い宣言と D-0**: 遡って書き換えない。次に D-0 を改めるときに版の欄を書く。それまでは 1.10.3 のとおり記録の欠落に数える。移行の手順は置かない(置くと「過去の宣言に版があった」ように見える書き換えになる)

### 理由
- 現状は「読むときに補う」と「契約検査で落とす」が、規則ごとにその場で選ばれている(内部 2.3)。どの変更が採用者を落とすかを、構成の側から判別できない。版の欄があれば、落ちる理由が「形式が旧い」か「値が規則に反する」かを分けて出せる
- 前例はすべて未知の版を黙って通さない(外部 §2 の表、K2)。現状の「欄が無ければ作業中の版として読む」は `standard` に限っては規定済みの意図的な扱いだが、形式全体に広げてはならない
- 猶予を置かないのは 1.10.1(経過措置なし)と ADR-0083(移行期間と失効を置かない)の帰結。猶予を置くと、猶予中は検査が通る状態=観測だけの期間を開始の後に置くことになる

### 落とす案
- **Renovate の型だけ(無期限の読み替え)**: 却下。A-3 のように、旧い値そのものが規則に反する場合を読み替えでは扱えない
- **Kubernetes の型(猶予期間と往復)**: 却下。1.10.1・ADR-0083 と矛盾する
- **移行が A-3 の値まで自動で直す案**: 却下。G-6 を未達へ変えるのは体制の判断の記録であり、移行の道具が人の記名を代えることになる(外部 T9 の「移行器の出力を検証なしに確定させない」)
- **`schemaVersion` の意味を広げる案**: 却下(上記)

### 文の案(`template-repository.md` に「構成の形式の版と移行」の節を新設)

> 構成は、形式の版(`formatVersion`)を持ちます。形式を変える更新は、この版を1つ上げ、旧い版ごとに現行の版への移行を1つずつ持ちます。
>
> - 形式の版が現行と違う構成は、契約の検査で失敗する。移行は `/process-change` の種別 `migrate` で行い、PR で AI維持管理者が承認する
> - 移行の手段の無い版と、現行より新しい版の構成は、契約の検査で失敗する
> - 移行は、ゲートの状態・席・名簿の値を変えない。規則の強化で値が規則に反するようになった構成は、移行の後も契約の検査で失敗し、記名を伴う構成の変更を要する
> - 移行の猶予の期間を設けない(第1章 1.10.1)
> - 版の記載の無い宣言と D-0 を、遡って書き換えない。次に改めるときに版を書く

- 降ろし方: `config.mjs`(`formatVersion` と移行の表)、`generate-profile.mjs --change` の種別 `migrate`、`.claude/skills/process-change/kinds/migrate.md`(新規)、`verify-gate-contract.mjs`(版の検査)、試験 `test-migrate.mjs`(旧い形式の fixture。#319 の置き場と合わせる)
- 実装マーク: `IMPL-0317 target=config-change-log state=undelivered`(移行の記録を `changeLog` の種別 `migrate` として残す)
- `formatVersion` の欄の無い現行の構成の扱い: 欄の無い構成を形式の版 0 とし、版 0 → 1 の移行は「欄を足すだけ」とする。これを入れる更新そのものが採用者を落とす変更になる(R-6 の規則の最初の適用例)

### 矛盾の検査
- ADR-0083 決定1(移行期間と失効を置かない): 本案は構成の形式の移行であり版の切り替えではない。猶予を置かない点で整合
- IMPL-0305(欄の無い構成は作業中の版として読み、再生成でも欄を足さない): 移行でも `standard` を足さないため整合。ただし `formatVersion` を足すと構成の要約値は変わる。`migrate` は変化点の記録として連鎖に入れる
- README 488〜495 行(遡って書き換えない): D-0 の扱いが整合
- 根拠: 内部 2.3、外部 T1・T2・T7・T9・K1・K2。V5 は自分で確かめた

## R-6 テンプレートの更新の取り込みと、既存の採用者を壊す変更

### 結論
- **採用者が取り込んだテンプレートの版を記録する**。構成(`process.config.json`)ではなく、取り込みの記録のファイル `.pit-in-template.json` に、テンプレートのリポジトリ・コミット・取り込んだ日時・テンプレートの配布時点の各ファイルの要約値を置く。手で編集しない(Copier・cruft の型。外部 T1・T3)。構成に置かないのは、構成の変更は体制の判断の変化点であり、道具の版の更新と混ぜると変化点の意味がぼやけるため
- 要約値は**乖離の表示**に使い、合否には使わない。出荷の証跡に「テンプレートの版」と「テンプレートから変えた強制層のファイルの一覧」を出す。採用者の改変は許すが、見えるようにする
- 既存のリポジトリへの後付けは、取り込みの記録を初期化と同じ PR で作ることで行う(cruft の `link` に当たる)
- **取り込みは強制層の変更として扱う**。AI維持管理者(人)が承認し、`state:needs-platform` を経る。取り込まないことは許す(旧い版の主張は期限なく続けてよい。ADR-0083 決定1)。README の「技術判断(G-3/例外承認等)」は誤りとして改める(V8。例外承認は基準を満たさないまま進む経路で、更新の取り込みとは別の事象)
- **採用者を壊す変更の規則(保守者の義務)を ADR と `community/standard-editions.md` に置く**
  - テンプレートの変更のうち、既存の構成・リポジトリで検査を新たに落としうるもの(検査の強化、形式の版の上げ)は、テンプレートの変更の記録に「既存の採用者で落ちうる検査」と「直し方」を列挙する。列挙の無い強化を出さない
  - 取り込みの前に、新しい版の検査を採用者のリポジトリへ書き込まずに走らせる手段(`node scripts/gate/template-update.mjs --check <新しい版のディレクトリ>`)を配る
  - 猶予の期間は置かない(R-5 と同じ)
- **#332 との分担**: #332 は配布物(`dist/standard`)の受け取り側の検査(生成元の確かめ)。#315 は、取り込みの記録・乖離の表示・壊す変更の告知と事前の試走。重なる「生成元の確かめ」は #332 に寄せ、取り込みの記録は #332 の検査の入力になる形で設計する

### 理由
- 現状、採用者がどの版の強制層で動いているかを、採用者自身も監査人も知る手段が無い(内部 3)。#314・A-3・連鎖・`nameConfirmed` と、壊す変更は既に4回起きている。版の記録が無ければ、どの直し方を当てるかも決められない
- 取り込みの判断を「技術判断」とすると、強制層の縮小(古い検査のまま留まる)も拡大も同じ扱いになり、ADR-0084 影響の「強化の承認は AI維持管理者」と食い違う

### 落とす案
- **構成に `template.commit` を足す案**: 却下(上記。変化点の意味が混ざる。要約値の連鎖へ道具の更新を入れることになる)
- **自動の同期(Renovate・safe-settings 型の更新 PR)を標準化する案**: 今は却下。自動の更新 PR は強制層の変更を機械が起案することになり、承認の手順は既にあるが、起案の道具の信頼性を確かめていない。必要になったら別 Issue で議論する(却下の理由を ADR に明記)
- **テンプレートの側で過去の版との後方互換を保証する案**: 却下。強化を止める理由になり、信頼性の軸に反する
- **要約値の不一致で合否を落とす案**: 却下。採用者の正当な改変(定め2 の書き足しなど)が常に落ちる

### 文の案

本文(第1章 1.10.3 の箇条の後):

> - 準拠テンプレートの更新を取り込むことは、強制層の変更として扱う(第3章 3.13)。取り込まないことは妨げない
> - 取り込んだ準拠テンプレートの版(生成元のコミット)を記録する。記録の無い版は、出荷の証跡に「不明」と表示する

`community/standard-editions.md`(保守者の手続)へ:

> 準拠テンプレートの変更のうち、既存の構成とリポジトリで検査を新たに失敗させうるものは、変更の記録へ、落ちうる検査と直し方を列挙して出します。取り込みの前に検査を書き込まずに走らせる手段を、同じ変更で配ります。移行の猶予の期間は設けません。

- 降ろし方: `.pit-in-template.json`(新規)と生成(`generate-profile.mjs` の初回、`template-update.mjs`)、`aggregate-evidence.mjs` の表示、`template/README.md` の該当節の書き直し(標準の条項を引く形へ)、`template/CHANGELOG.md`(新規。落ちうる検査の列挙)
- 新しい降ろし先: `src/data/impl-targets.yaml` へ `template-origin`(取り込みの記録)を登録
- 実装マーク: `IMPL-0318 target=template-origin state=undelivered`、`IMPL-0319 target=evidence-aggregation state=undelivered`(版と乖離の表示)
- 根拠水準: 告知と事前の試走で採用者の破損を防げるかは未実証。`:::caution[暫定 EV-0168 / 見直し 2027-04]`

### 矛盾の検査
- ADR-0084 影響(強化の承認は AI維持管理者): 整合。README の現状(V8)が矛盾しており、こちらを改める
- ADR-0083 決定1: 取り込まない採用者は旧い版の主張を続けられる。作業中の版の採用者は、取り込みの記録がコミットの識別を与える(表明に必要な「配布物のコミットの識別」を満たす)
- ADR-0077 決定6(配る中身): 変えない。テンプレートは `dist/standard` を参照しないまま
