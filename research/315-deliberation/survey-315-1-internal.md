## 6. 論点の候補

1. **手順の全体の置き場**: 標準(フェーズ5 template-repository の節を規定として拡張)か、テンプレートの文書(README・スキル)か。#310 C-7 でフェーズ5 は本文に従属すると宣言済み。テンプレートの README には標準に対応の無い規範(「技術判断(G-3/例外承認等)に委ねる」)が既にあり、どちらを正とするかを決める必要がある
2. **実 GitHub での検証の計画**: 何を、誰が、どのリポジトリで通せば EV-0107 を差し替えられるか。作成者が自前の検証用リポジトリで通すか、採用者の記録を待つか(#338 の受け取りの経路と同型)。env-check の「確認済み」の経路が実環境で未通過であることを、同じ計画に入れるか
3. **env-check の `checks-only` の穴**: G-6 無効の構成で必須チェック gate-g5 の適用を確かめない現状を、未確認として出すか(ADR-0028 の扱いとの整合)
4. **初期化が既存のリポジトリを検出するか**: 既存のコード・履歴・`coverage` の欠落・目印の無い `CLAUDE.md` を、初期化が告げる/止まる。止める場合、スキルの「既存ファイルからスタックを推測しない」禁止(SKILL.md 210 行)との関係(検出と推測の区別)
5. **`CODEOWNERS`・`.gitignore` の機械の確認**: 定め2 のうち降りていない部分(IMPL-0123 の note)。`@OWNER` の置き換え漏れを含めるか
6. **併合した履歴の識別**: 定め1(併合しない)で足りるとするか、集約がテンプレート由来の履歴を識別する(既知のテンプレートのコミットの一覧との照合など)か
7. **旧い構成の移行の型**: 現状は「読むときに補う」後方互換と、規則の強化で契約検査が落ちる場合(A-3、#314、連鎖、`nameConfirmed`)の混在。移行のスクリプト・形式の版(`schemaVersion` の意味の拡張)・猶予を置かない現行の方針(1.10.1 の経過措置なし、ADR-0083 の失効なし)との整合
8. **旧い D-0 と宣言の移行**(1.10.3 の 505 行が #315 へ送ったもの): 版の欄の無い宣言・D-0 を、記録の欠落のまま残すか、移行の手順を定めるか。遡って書き換えない(README 488〜495 行)との関係
9. **テンプレートの更新の受け取りの手段**: `dist/standard` は本文と知識ベースだけを配る。スクリプト・スキル・`CLAUDE.md` の更新の取り込み方(複製・差分・併合)と、その PR の扱い(統制の設定の変更、`state:needs-platform`、陰性の確認)を定めるか。#332 と重なる
10. **更新が既存の採用者を落とすことの扱い**: ADR-0084 は「落ち始めうる」を影響に書くだけ。破壊的な変更の告知(版の N の改訂との対応。EV-0158)・取り込み前の確認の手段(`--dry-run` の類)を設けるか、落ちることを統制として受け入れると明記するか
11. **python・go の試行**: 試行の範囲と、go の `coverageSummary: null`(#330)を先に決めないと、go の持ち込みは G-5 基準3 を「実施しない」で通る
12. **持ち込みのコミットの数え方**: 複製の1コミットが pre-init の「製品の変更 1 件」と出ることを、そのまま開示とするか(現行)、持ち込みの印で区別するか
