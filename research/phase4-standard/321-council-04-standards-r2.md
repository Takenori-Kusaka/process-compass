## 1. 先に結論

- **5 名は、問いの骨格で一致しています**。ADR-0036 決定1 の維持、承認の操作だけで成立させる案の却下、機械が出す欄と人が書く欄の分離、PR 本文・Issue コメントを受け皿にしないこと、記録だけのコミットに記名者以外の承認を課さないこと、`exempt` の不採用、承認までの時間を合否にしないこと、保全の条件を標準に書くこと、承認の失効の粒度を #296 へ送ることです(2 章)
- **争点は 4 つに絞れます**。A 写しを基底ブランチへ入れる時点と Bot の bypass、B G-2・G-4 の受け皿と判定者が作成者である場合、C 記録だけのコミットを強制層でどう扱うか、D 1 名体制で何が変わるか。いずれも既存の決定と「矛盾」するのは一部の案だけで、大半は「未規定」であり、本文で埋める問題です(3 章)
- **争点 A の判定**: 監査側の「マージごとに Bot が `pull_request` モードの bypass で固定」は、ADR-0038 の「強制層の縮小」(`adr/0038-…:46`)に当たり、`rulesets/README.md:41`「強制層に置いた項目だけが、遮断できたものとして数えられます」と `agent-trace-control.md:52`「強制層に置けない項目は、遮断できたものとして扱いません」の下では、**App が記録の置き場の外へ書ける経路を「遮断していない」と開示したうえでしか成立しません**。監査側が補いとして挙げた集約の検査(App のコミットが `RECORD_PATHS` の外に触れていないか)は検出であって遮断ではなく、ADR-0028 決定6「代償措置は未達の解消として扱わない」(`adr/0028-…:43`)と同じ扱いになります。したがって、標準は bypass を要求も推奨もせず、**要求事項を「写しを承認と同じ時期に機械が取り出し、記名者以外が書き換えられない場所へ置く。既定ブランチの強制層を縮小しない。基底ブランチへ入れるのは遅くとも出荷判定(G-7)」の 4 点で書き、置き場の形(既定ブランチの外のブランチ、成果物など)は準拠テンプレートに委ねる**形を推します。監査側の「承認と同じ時間帯」の要求と、弁護役の不変条件 8「強制層へ穴を開けない」は、この形で両立します
- **争点 A の付随**: 現場の「G-7 の PR に承認レビューの写し(`evidence.json`)を同梱」は、`ci-gates.md:146`「判定の材料を、判定される側が同じ変更で用意できない形にする」に**触れません**。G-7 で判定される側は出荷の範囲の変更の作成者・指示者であり、出荷判定者ではありません(ADR-0066 が出荷判定の記名者を指示者と G-6 の承認者から分けています)。ただし条件が 2 つ要ります。写しは集約(機械)が生成し、G-7 の PR の上で CI が同じ集約を再実行して一致を検査すること(人が上書きできない)。停止の解除・例外承認の台帳の行・基準値を同じ PR で変えないこと(現行 `ci-gates.md:146`・`:155` のまま)
- **争点 B の判定**: 起案側・現場の「G-2・G-4 は仕様 PR の承認レビュー本文」は、第5章 QMS 対応表が既に「仕様ファイルの PR 承認とマージ」を G-2・G-4 の承認の記録と対応づけている(`qms-document-control.md:37`〜`:38`)ため、**判定者が仕様 PR の作成者でない場合に限って整合**します。判定者が作成者(git の作者)である場合、ブランチ保護が承認を止める(`roles-responsibilities.md:350`)ので、承認レビューは存在しえず、判定記録(様式)に戻ります。現場の「作者本人のコメント形式のレビューに宣言を書く」は、承認でない操作を承認の記録に対応づける形であり、QMS 対応表の原則「どの操作がどの承認へ相当するかを事前に定めた場合だけ」(`:33`)の型から外れるため、採りません。受け皿を 3 つに増やさないという現場自身の注文(02 Q4)とも合います。版の識別子の罠(02 §2.3)は、対象を「機能の ID + PR 番号」で人が書き、マージ後のコミットの識別子を集約が併記する(機械が出す欄)ことで解けます
- **争点 C の判定**: 「記録だけのコミットに記名者以外の承認を課さない」は、`ci-gates.md:609`(判定記録は無条件に製品の変更の対象外)、ADR-0057:509(層1 に PR を課さない)、ADR-0058:110(PR 2 本・承認 2 回の却下)、ADR-0067:36(承認者 2 名の目的は変更の取り込みの抑止)の一般化であり、5 名が一致しています。GitHub がパス単位の免除を持たないため、**要求事項を本文に書き、降ろし先をルールセット(新規登録)として `state=undelivered` で表示し続ける**形は、`implementation-marking.md:24`(対象は実行主体の挙動を制約する規定)・`:80`(`undelivered` は削除の対象でなく表示し続ける。未達のゲートと同じ扱い)、ADR-0028 の型に沿います。第1巡で私はこれを ADR-0050:60「強制層に置く規則の選び方の誤り」の型としましたが、正しくは同じ箇所の 2 つ目「遮断の範囲の誤り — 規則は正しいが、遮断の対象が広すぎる」の型です。PR と承認を課す規則そのものは製品の変更に対して正しく、範囲を絞れないのがホスティングの制約です。訂正します。残る記録 PR の承認者を記名者本人に限る手順(起案側 3.2、弁護役 4.1 B)は誘導層とテンプレートの手順で降ろし、一致しない承認は「事務」として開示します(監査側 Q4)。起案側の「承認者が記名者と一致しない記録 PR を欠落に数える」は、記録の欄が揃っているのに記録を欠落と扱うため ADR-0036 決定1 と矛盾し、採りません
- **争点 D の判定**: 1 名体制では、承認を強制するルールセットを置かない(`rulesets/README.md:21`)ため、記録 PR の第三者承認の問題は元から生じません(弁護役)。本改訂で 1 名体制に起きる変化は、機械が出す欄の転記で手入力が消えることだけです。起案側が自分の弱点 5 として書いたとおり、**1 名体制では往復は軽くなりません**。これを決定の記録に明記します。ルールセットを使えない構成(`template/README.md:115`)では、記録の日時がすべて自己申告になることを、ADR-0028 と同じ型で開示します
- **規制業(軸C)・CL2 以上(軸E)**: 現場の「変更ごとの G-6 の判定記録を G-7 の時点で承認イベントから生成する」は、`tailoring-guide.md:508`・`template/templates/04-gate-record.md:104` の「変更ごとに G-6 の判定記録を残す。PR の承認だけでは記録にならない」と対立します。査察で承認イベントの写しが受理された一次事例が無い(03 §8.5)ため、規制業では現行を維持し、文言だけを「承認レビューは属性の出所になるが、判断の中身の監査対応書式と変更ごとの記録が無ければ記録にならない」へ改めます(監査側 5 章)。軽量化は差し替え条件(査察・監査での受理事例)に送ります
- **根拠水準の呼称の揺れ**: 現場(02)は「E3 = 見積り」「E4 = 意見」の意味で使っており、標準の語彙(`evidence-marking.md:29`〜`:32`: E0 なし / E1 間接 / E2 単一事例 / E3 複数)と**逆向き**です。現場の E3・E4 はすべて E0 に読み替えます。また「重い手続は記録を消す(`236b:326`、7.7 倍)」は別領域の研究であり、定義上 E1(隣接する領域の研究はあるが、この文脈での測定はない)です。02・03・05 は E2 としていますが、E1 に揃えます(6 章)
- **改訂の経路**: 新 ADR は **ADR-0070**(既存の最大は ADR-0069)。ADR-0036 を**補い**、置き換えません。ADR-0036 の決定1〜4 と却下表はすべて残ります。ADR-0067:10「置き換えません。…目的の記録を足します」と同じ型です(5 章)
- **新語を要しません**。「承認イベント」「属性」「固定」は標準に無い語であり、「承認レビュー」「承認の操作」「機械が出す欄」「人が書く欄」「写し」「基底ブランチへ入れる」で組めます(第1巡 6 章)。本書の以下の文も、この語で書きます

## 3. 争点 A〜D の突合表と判定

採点の語は 3 つです。**整合**(既存の決定の帰結、または一般化)、**矛盾**(既存の決定と両立しない。どちらが誤りかを書く)、**未規定**(既存の決定が触れていない。本文で埋める)。

- 版の識別子の罠は、**対象を「機能の ID + PR 番号」で人が書き、マージ後のコミットの識別子(`merge_commit_sha`)を集約が併記する**ことで解きます。IMPL-0107 の `check=manual` は、版の識別子の有無を機械が読む形へ上げられます(新しいマークで補い、IMPL-0107 の note は変えない)。これは起案側 Q2 の「機械が出す欄」の適用です

- 1 名体制で本改訂が変えるのは、**機械が出す欄の転記で手入力が消えること**だけです。往復(記録 PR の作成と CI 待ち)は残ります。決定の記録に「1 名体制では、本決定は記録 PR の往復を軽くしない」と明記します。起票者の体制がこれに当たるなら、起票者の訴えの半分(往復)は本 Issue では解けず、#296 の失効の粒度と、テンプレートの `/gate` の手順(AI の担い手が push と PR を担い、人は結果欄とマージだけ)で扱います

## 4. 決定の記録の候補文

主宰が ADR-0070 と Issue #321 の決定の記録に書く文の候補です。文体は ADR の本文に合わせています。

### 4.1 決定

1. **判定記録の媒体を限定しない**。工程ゲートの判定は、判定記録の作成をもって成立する(ADR-0036 決定1。変えない)。判定記録とは、第4章「判定の成立」が定める欄(判定者・判定日時・対象・結果・確認した項目・差し戻し理由)が埋まった記録であり、第6章 テンプレ4 はその様式の正本である。欄を運ぶ媒体を、本標準は様式のファイルに限定しない。ホスティングの承認レビューが欄を運び、案件の構成が事前に対応づけ、第5章の保全の条件を満たすとき、その承認レビューは判定記録である。欄を運ばない操作(Issue のクローズ、PR のマージ、ラベルの遷移)は、引き続き事務である(ADR-0036 却下表を維持)
2. **機械が出す欄と人が書く欄を分ける**。判定者・判定日時・対象(PR 番号、コミットの識別子、承認レビューの識別子)・結果・参照した D-0 の版・提出日時は、強制層の記録(承認レビュー、PR のメタデータ、基底ブランチの構成)から、推定を含まない写しとして機械が出してよい。出所を併記する。挙動要約・確認した項目・確認していない事項・差し戻し理由(項目番号と再提出の期限)・決断の記録・リスク区分の確定者の記名は、人が自分の言葉で書く。AI に生成させない(第6章 テンプレ4、附属書C)。第6章の欄は 1 つも減らない。ADR-0040 の omit でも逆の指示でもなく、欄の出所の指定である
3. **人が書く欄の受け皿は 2 つに限る**。変更ごとの判定(G-6)は承認レビューの本文、それ以外は判定記録(様式)。PR 本文は作成側の欄であり、Issue のコメントはコミットに固定されず削除できるため、受け皿にしない
4. **G-2・G-4 は判定記録(様式)を既定とし、判定者が仕様 PR の作成者でない構成に限り、仕様 PR の承認レビューの本文を媒体として認める**。本文に確定の宣言と確認した項目を要する。この承認は受入基準の確定であり、独立した人の確認(G-6)に数えない(ADR-0060 決定)。対象は「機能の ID + PR 番号」を人が書き、マージ後のコミットの識別子を集約が併記する
5. **写しは承認と同じ時期に機械が取り出し、記名者と判定される側が書き換えられない場所へ置く**。写しに含める最小の組は、承認レビューの識別子・状態・対象のコミット・提出時刻・アカウントの数値の識別子とログイン名・本文・PR 番号・マージのコミット、および同じ期間の bypass・保護の変更の記録(取れないプランでは「取れない」と写しに書く)。写しは要約と評価を含まない。附属書G の投影と区別する
6. **判定記録と写しを基底ブランチへ入れるのは、遅くとも出荷判定(G-7)である**。入れる操作に、記名者以外の承認を課さない。記名者本人の操作(署名コミット、または記名者の承認レビュー)を帰属の裏づけとし、裏づけの無い記録は、記名が自己申告であることを保証の開示へ出す。G-7 の PR に写しを同梱する場合、CI が同じ集約を再実行して一致を検査する
7. **既定ブランチの強制層を、写しのために縮小しない**。bypass actor を足さない。`exempt` を用いない。組織が bypass を伴う構成を選ぶ場合は、統制の弱化として `state:needs-platform` の経路で記録し、App の名義の変更が人の承認を経ない経路であることを保証の開示へ出す
8. **承認レビューを記録と認める条件を標準に書く**。成立の条件(欄の充足、書き手、対象の固定、承認の後の push による失効、承認者ごとの最後の状態)は第4章。保全の条件(アカウントと実在の人の対応表と数値の識別子、承認の意味の事前の定義、写しの取り出しと保持、組織の文書管理規程の対象に写しを含めること、PR の承認が電子署名の要件を自動的に満たさないこと)は第5章 QMS 文書管理。条件を満たさないホスティングでは、判定記録(様式)へ戻る。これにより、ツールを変えても成立要件は変わらない
9. **規制業(軸C)・CL2 以上(軸E)は、変更ごとの G-6 の判定記録と監査対応書式を維持する**。文言を「承認レビューは機械が出す欄の出所になる。判断の中身の監査対応書式と変更ごとの記録が無ければ記録にならない」へ改める
10. **形骸化の抑止は既存の手段(挙動要約の形、同一の文、変更の規模、検出能力の測定、内部監査の抜き取り)で足りる**。承認までの時間・コメントの有無・差分量は観測値として出し、内部監査のリスクに基づく抽出の条件に加える。合否にしない。「機械が見るのは形だけ」の限界(EV-0083)は、承認レビューの本文に置いた欄にも掛かる
11. **QMS 対応表の語を改める**。列名「成立の条件」を「承認の記録として扱う条件」へ。G-7 の行「判定記録のマージ」を「判定記録を基底ブランチへ入れること。入れる操作に記名者以外の承認を課さない」へ。G-2・G-4 の行に「判定者が仕様 PR の作成者でない場合。この承認は独立した人の確認(G-6)ではない」を足す。G-8 の行に「決断の記録はテンプレ4 に残す。承認操作だけでは記録にならない」を足す
12. **1 名体制では、本決定は記録 PR の往復を軽くしない**。変わるのは機械が出す欄の転記だけである。ルールセットを使えない構成では、記録の日時が自己申告であることを保証の開示へ出す
