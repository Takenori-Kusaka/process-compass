# 調査メモ: 事業ステージ別の欠陥トリアージ基準（Issue #100）

- 調査日: 2026-08-05
- 対象 Issue: #100 「事業フェーズ(DR0/DR1/DR2)に応じたバグ・トリアージ基準の明文化」
- 目的: 「重大欠陥ゼロ」の一律適用を避け、ステージごとのリスク許容度に応じた基準を定める

---

## 1. 調査結果

### 1.1 重大度(Severity)と優先度(Priority)の分離

実務では両者を明確に分離する運用が定着している。

| 概念 | 性質 | 決める主体 |
| --- | --- | --- |
| 重大度(Severity) | 技術的な影響の大きさ。製品のリスク露出を表す | 技術側(観測可能な事実で判定) |
| 優先度(Priority) | いつ直すかの順序。事業判断 | 事業側(市場・契約・利用者影響で判定) |

- 最高重大度は「システムの完全な停止、または主要機能の停止で回避策が存在しない状態」と定義される。この状態では、解決するまでテストまたは本番運用を継続できない。
- ブロッカー欠陥は「システムを停止させ、利用者の作業継続を妨げる致命的な欠陥」と定義される。
- 優先度の判断入力は、事業影響・顧客影響(影響利用者数と顧客層)・収益またはコンプライアンスのリスク・リリース状況の4点である。

出典:
- https://www.qamadness.com/bug-severity-vs-priority/
- https://birdeatsbug.com/blog/bug-severity-vs-priority
- https://plane.so/blog/bug-triage-process-how-to-run-it-and-what-to-prioritize
- https://www.browserstack.com/guide/bug-severity-vs-priority

**本標準への含意**: 重大度は AI が観測可能な事実から機械的に判定でき、優先度は人間の事業判断である。この分離が、Issue の問い「AI と人間でブレなく共有する方法」への回答になる。重大度の判定基準を観測可能な事象のみで書けば、AI と人間の判定は一致する。

### 1.2 製品成熟度の段階

- MVP は価値・需要・行動に関する仮説を検証するものであり、主たる役割は洞察の獲得である。
- MMP(Minimum Marketable Product)は、テスト参加者ではなく実利用者に向けた最初の版であり、商用提供に耐える状態を指す。
- これらは「迅速な検証 → 市場適合 → 長期的な維持」という連続体上にあり、各点で投資額・利用者への露出・確実性の水準が異なる。

出典:
- https://www.invensislearning.com/blog/mvp-mmp-mlp-guide/
- https://modall.ca/blog/mvp-vs-mlp-vs-map-software-development

**本標準への含意**: 露出する利用者の性質(社内・限定利用者・一般利用者)が、許容できる欠陥の水準を決める。ステージ名ではなく**利用者への露出**を基準に書くほうが、テーラリングで破綻しにくい。

### 1.3 安定性の定量指標(クラッシュ率)

Issue の問い「定量メトリクスとどう紐づけるか」に対する調査結果である。

| 指標 | 値 |
| --- | --- |
| クラッシュフリーセッション率の中央値 | 99.95% |
| 上位25%(75パーセンタイル) | 99.99% |
| iOS 実測 | 99.93% |
| Android 実測 | 99.81% |

業種別の目安:

| 業種 | 目安 |
| --- | --- |
| 一般消費者向け | 99.5% 以上 |
| 小売 | 99.7% 以上 |
| 金融 | 99.9% 以上 |
| 医療・ヘルスケア | 99.9% 以上 |

運用の実例として、「最初の1%の利用者でクラッシュフリー率が99.3%を下回ったら展開を停止する」という段階的展開の閾値設定が用いられる。また、利用者が体感するクラッシュ率が1.09%を超えるアプリは、配信プラットフォーム側で露出を下げられる場合がある。

出典:
- https://www.luciq.ai/blog/benchmarking-crash-free-sessions-for-mobile-apps-whats-a-good-crash-free-rate
- https://mwm.ai/glossary/crash-free-rate
- https://www.businessofapps.com/data/app-performance-rates/
- https://www.getyourguide.careers/posts/how-we-automate-the-app-release-monitoring-at-getyourguide

**本標準への含意**: 数値そのものは業種・製品形態で変わるため、標準に固定値を書かない。標準が規定するのは「ステージごとに閾値を設定し、企画時に合意すること」および「閾値を下回った場合の措置」である。参考値は目安として示す。

## 2. 設計判断

### 2.1 重大度の定義は観測可能な事象のみで書く

「業務に重大な支障」のような主観的表現を使わない。AI が判定に参加するため、判定材料を観測可能な事象に限定する。

| 重大度 | 定義(観測可能な事象) |
| --- | --- |
| Sev1 | システムまたは主要機能が停止する。データが破損または消失する。認証・認可が破られる。回避策が存在しない |
| Sev2 | 主要機能に障害があるが、記述可能な回避策が存在する。または副次機能が停止する |
| Sev3 | 機能は動作するが、表示・操作性・性能が仕様を満たさない。業務は継続できる |

「回避策が存在するか」が Sev1 と Sev2 を分ける唯一の境界である。回避策は文書化されていなければ存在しないものとして扱う。

### 2.2 露出する利用者を基準に許容水準を決める

ステージ名ではなく、露出する利用者の性質を判断基準にする。

| ステージ | 露出する利用者 | Sev1 の扱い | Sev2 の扱い | Sev3 の扱い |
| --- | --- | --- | --- | --- |
| S0 探索 | 社内・実験参加者 | 回避策を文書化すれば継続可 | 記録のみ | 記録のみ |
| S1 価値確立 | 限定した実利用者 | コア機能では出荷不可。非コアは既知の不具合として公開すれば可 | 記録し次サイクルで返却 | 記録のみ |
| S2 スケール | 一般利用者 | 出荷不可(例外なし) | 出荷不可。ただし例外承認の対象 | 記録し計画返却 |

S0 で Sev1 を許容できるのは、影響が実験参加者に限定され、かつ回避策が伝達できるためである。露出が広がると同じ欠陥でも許容できなくなる。

### 2.3 定量指標は「設定すること」を義務化する

固定値を標準に書かず、次を規定する。

- 企画承認(G-1)の時点で、ステージごとの安定性指標と閾値を合意して記録する
- 閾値を下回った場合、出荷判定(G-7)は不合格とする
- 閾値の変更は、例外承認手続([第7章](/process-compass/phase4-process-design/exception-escalation/))を経る

### 2.4 「既知の不具合」は成果物として扱う

S0・S1 で Sev1 を許容する場合、既知の不具合の一覧が成果物になる。台帳に記録するだけでは利用者へ伝わらないため、次を要求する。

- 現象・影響範囲・回避策・解消予定を1件ずつ記載する
- 回避策が書けない項目は、既知の不具合として公開してはならない
- ステージ移行ゲート(SG)で、未解消の既知の不具合を一覧として提出する
