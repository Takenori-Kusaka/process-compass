# #321 会議体 03 — QA・内部監査・規制対応の意見書

- 作成日: 2026-10-23 / 立場: 出荷判定者・内部監査・規制当局の査察官・SOX 監査人
- 入力: `321-council-00-brief.md`、`gate-record-00〜03`、第4章 G-6〜G-8、`qms-document-control.md`
- 問い: この記録で、1 年後に第三者が「誰が、どの立場で、何を見て、何を決めたか」を再現できるか
- 根拠水準の表記: 本標準の語彙(E0 なし / E1 間接 / E2 単一事例 / E3 複数)を使います。brief の「E4」は、本書では E0(なし)と読み替えます。条文も事例も無い推測には、その旨を E0 と明記します
- 本書は帳票を守る立場では書きません。手入力帳票が現に何を保証していないかを、先に述べます

## 1. 先に結論

- 手入力帳票の「判定者・判定日時」は、監査の立場では**自己申告**である。帰属(誰が)と同時性(いつ)を帳票自体は裏づけない(01 §7.3)。裏づけるのは、システムが時刻印した承認イベントと、その承認が指す改訂(`commit_id`)である
- ただし承認イベントは「誰が・いつ・どの改訂に・承認か否か」しか持たない。**「どの立場で・何を見て・何を見なかったか・なぜ」は持たない**(03 §8.2)。この欠落は、人が書く欄でしか埋まらない
- したがって、承認イベント**単独**を成立要件にする案と、手入力帳票**単独**を成立要件にする案は、どちらも採らない。採るのは、**属性は強制層の記録から機械が転記し、判断の中身は承認者本人が承認に伴って書き、その組をリポジトリへ固定する**形(折衷)である
- ADR-0036 決定1「記録の作成をもって成立」は維持する。変えるのは「記録」の定義である。記録は**情報項目**(Who / When / What / Outcome / Reason / 立場)であり、ファイルという媒体ではない(ISO/IEC/IEEE 15289 5.1、IEC 62304 B.8.2。01 §3)
- 承認イベントを記録と認めるには、GitHub が満たさない条件が 7 つある(本書 3 章)。条件を標準に書かずに「GitHub にある」と言う記録は、監査で**記録が無い**と評価される。特に、監査ログ 180 日、退会による ghost 化、承認本文の編集、exempt bypass の 4 つは、1 年後の再現を直接に壊す(02 §9.2)
- 固定(リポジトリへ写すこと)は、人の承認を要さない機械の複製として、**マージごと**に行う。人が記名して固定を引き受けるのは出荷判定(G-7)である。規制業と CL2 以上では、変更ごとの固定を G-7 を待たずに完了させる
- PR に紐づかないゲート(G-1〜G-4・G-8・SG)は、判定記録(テンプレ4)の記名を維持する。これらは業界でも帳票が残っている領域であり(03 §8.2)、承認イベントに「判断が変わる条件」「確認していない事項」の受け皿が無い
- 「中身を見ずに承認」を機械で判定する手段は無い。標準はこの限界を既に書いている(`gate-criteria.md:492`)。足せるのは、内部監査の**抽出条件**に承認の速さとコメントの不在を加えることまでである。合否にしない(5.7.4)
- 記録 PR の往復が減ることは、採否の理由にしない。採る理由は、手入力の帰属と同時性が弱いこと、および重い手続が記録を消すこと(`236b:326`。E2)の 2 つである

## 2. Q1〜Q7 への回答

### Q1 成立要件

**回答: ADR-0036 決定1 を維持し、「判定記録」の定義を媒体から情報項目へ改める。**

- 維持する理由は、決定1 の論理(記録が無ければ判定の存在が自己申告になる。`adr/0036-gate-closure-by-record.md:61`)が、承認イベントにもそのまま当てはまるからです。承認の操作があっただけでは「何を見て決めたか」が自己申告どころか無記録になります。標準は既に「承認の操作があったことだけでは数えない」と書いています(`gate-criteria.md:465`)
- 改める理由は、成立要件の列挙(`gate-criteria.md:65`「判定者・判定日時・結果・確認した項目・差し戻し理由が埋まっていること」)が欄の充足で書かれており、欄の出所を限定していないからです。判定者と判定日時を、人の手入力でなくシステムの時刻印から埋めることは、この列挙に反しません。むしろ規制側の要求(「誰が・いつ」はシステムが記録する。Part 11 11.10(e)、Annex 11 §12.4、ER/ES 用語定義。01 §7.1)に近づきます
- 成立の時点は、次の 2 つが揃った時点とします。(a) 強制層の記録に、承認者・時刻・対象の改訂・結果が残っていること。(b) 承認者本人の判断の中身(G-6 では挙動要約。差し戻しでは満たさない項目番号と再提出の期限 `gate-criteria.md:85`)が、(a) と同じ事象に伴っていること。(b) を欠く承認は、現在と同じく「数えない」(`gate-criteria.md:472`)
- 「PR のマージは事務」(`gate-criteria.md:66`)は変えません。マージは承認の後に起きる別の事象であり、承認の記録を含みません。QMS 対応表の「仕様ファイルの PR 承認とマージ」「判定記録のマージ」(`qms-document-control.md:37`・`40`)は、第4章と食い違っています。対応表の側を改め、「承認(本文に当該ゲートの宣言と判断の中身を伴う)」を記録、「マージ」を事務と書き分けるべきです
- 監査の立場からの注意: 成立の時点が一意に決まらない記録は、同時性(Contemporaneous)を示せません。承認イベントは `submitted_at` で一意に決まります。手入力帳票の「判定日時」は決まりません。この差が、Q1 で承認イベントを属性の出所として認める最大の理由です

### Q2 属性と判断の分離

**回答: 認める。人が書く欄の受け皿は、G-6 では承認レビューの本文に限る。PR に紐づかないゲートでは判定記録のファイルとする。PR 本文と Issue コメントは受け皿にしない。**

- 承認レビューの本文を受け皿にする理由は、本文が `commit_id`・`submitted_at`・承認者のアカウントと同じオブジェクトに乗るからです(02 §6.1)。判断の中身が、対象の改訂と時刻に機械的に結びつきます。これが Part 11 11.70「署名と記録の恒久的リンク」と PIC/S 9.5「変更後は未署名として表示」の構造に相当します(01 §1.1・§6.2)
- PR 本文を受け皿にしない理由は、PR 本文の編集権が起案者にあるからです。承認者の判断を起案者が書き換えられる構造は、帰属(Attributable)を壊します。本標準は既に、判定の材料を判定される側が用意する形を禁じています(`ci-gates.md:146`)。PR 本文に置いてよいのは、起案者の側の記載(作成を指示した者、区分の確定者 `roles-responsibilities.md:776`)だけです
- Issue コメントを受け皿にしない理由は、削除できるからです。提出済みレビューは削除できませんが、コメントは削除できます(02 §1.2 と `Managing disruptive comments`)。削除できる場所に置いた判断は、Enduring を満たしません
- 別ファイルは、PR に紐づかないゲートの受け皿として残します。ファイルの弱点(帰属・同時性が自己申告)は、Q4 で述べる署名コミットと記名の突合で補います
- 承認本文の編集について: 本文は承認後に編集でき、編集履歴の内容は作者が消せます(02 §1.5)。したがって**固定(Q3)の時点で本文を複製し、以後の編集は複製との不一致として検出する**ことが、受け皿として認める条件です。これを欠くと「承認時に何を書いたか」が再現できません
- ADR-0040 との関係: 属性の欄を承認イベントへ移すことは「欄を落とす(omit)」でも「標準と逆の指示」でもなく、**欄の出所の変更**です。ADR-0040 の枠に無いため、新しい ADR で決める必要があります。テンプレ4 の欄名は残し、出所(人の記入 / 強制層からの転記)を欄ごとに明示する形が、様式の正本(ADR-0010)を動かさずに済みます

### Q3 置き場と固定

**回答: 固定は求める。ゲートごとの手作業の記録 PR は求めない。マージごとに機械が複製を固定し、出荷判定(G-7)で出荷判定者が固定された集合を記名で引き受ける。規制業・CL2 以上は、変更ごとの固定の完了を G-7 の前提にする。Bot による固定は `pull_request` モードの bypass に限って認め、exempt は禁じる。**

- 固定を求める理由は 4 つです。いずれも 02 §9.2 の「消える・変わるケース」です
  - 監査ログは 180 日で消える。bypass・保護の上書き・ルールセットの変更の証跡は、Enterprise でなければストリーミングもできない(02 §3)
  - 承認者が退会すると ghost になり、レビュー単体から承認者を同定できない(02 §1.6)
  - 承認本文は編集でき、元の文面は消せる(02 §1.5)
  - リポジトリの移管でルールセットは引き継がれず(02 §1.4)、削除で全損する
- 固定の単位をマージごとにする理由は、固定が人の判断を含まない機械の複製(真正な複製。MHRA 6.11.2 の true copy)だからです。人の承認を要さないので、記録 PR の往復は生じません。G-7 まで待つと、出荷間隔が 180 日を超えた場合に bypass の証跡が先に消えます。マージごとなら、承認と同じ時間帯に複製が残ります(02 §9.1「承認と同じ時間帯に自動で行う」)
- 出荷判定者が G-7 で引き受けるのは、「出荷の範囲の全変更について、固定された複製が存在し、集約の入力と一致していること」です。これは現在の基準5「全ゲートの通過記録 欠落 0 件」(`gate-criteria.md:565`)の突合対象を、ファイルから複製へ広げるだけです。出荷判定者の署名の意味(`gate-criteria.md:741`)は変えません
- Bot の bypass について: 記録固定の App を `exempt` に置く案は採りません。exempt は Rule insights にも監査ログにも出ません(02 §4.1)。監査証跡を「利用者が止められない」ことを求める MHRA 6.13・PIC/S 9.6 の趣旨に反します。`pull_request` モードなら bypass の事実が残ります
- bypass がパス単位に絞れない穴(02 §5.3)への補い: 内部監査の観点に「App の名義のコミットが記録の置き場(`RECORD_PATHS`。`aggregate-evidence.mjs:973`)の外に触れていないこと」を加え、集約でも機械検査します。App の鍵が漏れた場合の検出手段がこれしかないことは、開示します(E0。この検査で実際に不正を検出した事例は無い)
- 複製に含める最小の組は 02 §9.1 のとおりです。レビュー `id`、`state`、`commit_id`、`submitted_at`、`user.id` と `user.login`、PR 番号、`merge_commit_sha`、本文。これに、固定の時点のルールセット id と、同じ期間の bypass・`policy_override`・`repository_ruleset.*` の監査ログの抜粋を加えます。監査ログの抜粋は Free プランでは API で取れません(02 §3)。取れない場合は「取れない」と複製に書き、保証の開示の項目1 へ出します。隠さないことが ADR-0028 の方針です
- 「投影を正本として保管しない」(`deliverable-templates.md:829`)との整理: 複製は要約と評価を含まない真正な複製であり、附属書G の投影(要約を含む)ではありません。この区別を本文に書く必要があります

### Q4 PR に紐づかないゲート

**回答: G-1〜G-4・G-8・SG は判定記録(テンプレ4)の記名を維持する。記録だけのコミットには PR と別の承認者を課さない。代わりに、判定者本人の署名コミットと、記名との一致を機械が確かめる。G-8 の実行環境の承認操作は強制層であり、決断の記録を代替しない。**

- これらのゲートは、業界でも帳票が残っている領域です。設計レビュー(ISO 13485 7.3.5「審査対象・参加者・日付・結果・処置」。01 §3.1)、リリース判定(03 §8.2)。理由は、PR 承認に「独立したレビュアー、審査対象、決定、処置」の構造化された置き場が無いからです。G-8 の決断の記録(確認していない事項、判断が変わる条件、受容したリスク、出荷判定者の異議 `deliverable-templates.md:511`〜`514`)は、実行環境の承認操作のどこにも乗りません
- 判定者が成果物の作成者でもあるゲート(G-2・G-3・G-4・G-7。`adr/0060-…:58`)と、ブランチ保護(作成者は自分の PR を承認できない)の折り合い: **ゲートの判定と、ファイルを基底へ入れる承認を、別の事象として扱います**。仕様ファイルの PR を誰が承認するかはブランチ保護の事務であり、G-2 の判定ではありません。G-2 の判定は、価値責任者が版(コミットの識別子)を特定して記名した判定記録で成立します(`adr/0063-…:66`、`deliverable-templates.md:460`)。QMS 対応表の G-2・G-4 の行(`qms-document-control.md:37`〜`38`)は、この整理に合わせて改めるべきです。「文章として問題ない」と「受入基準を確定する」が同じ承認ボタンに畳まれる問題は、03 §7.2 の ADR の失敗例と同じ構造です
- 記録だけのコミットに PR と別の承認者を課さない先例は、層1 について既にあります(`adr/0057-…:509`「記名の意味と二重になる」)。`docs/gates/` にも同じ理由が当てはまります。ただし監査の立場では、PR を経ない記録だけのコミットには、**帰属の裏づけ**が別に要ります
  - 判定者本人の署名コミット(GPG/SSH で Verified)であること。署名は「誰がコミットを作ったか」の証跡であり(02 §6.4)、判定者本人が記録を署名コミットする形(02 §9.3 案 C の変形)でだけ、記名と帰属が一致します
  - コミットの署名者(アカウント)が、記録の「判定者」の記名と名簿で対応づくこと。対応づかない記録は、現在の `qms-document-control.md:86`「記入すること自体は誰にでもできる」と同じ扱い(自己申告)として、保証の開示に出す
  - 記録の置き場(`RECORD_PATHS`)の外に触れていないこと
- 1 名体制・2 名体制で、判定者の署名コミットを強制層で止められない(ルールセットが PR を課す `team.json:12`〜`16`)場合: ルールセットの `conditions` を記録の置き場で分ける方法は GitHub に無い(02 §4.1「パス単位に絞れない」)ため、記録だけの PR は残ります。その PR の承認者は判定者本人でないため、**承認者の承認は「判定」ではなく「ファイルの取り込みの事務」**と明記します。承認を要求するのは強制層の都合であり、成立要件ではありません。ここは「ツールの制約で手続が増える」場所であり、ADR-0050 の「強制層に置く規則の選び方」の型で扱う候補です
- G-8 について: 実行環境の承認操作を強制層の記録として受け入れます(誰が・いつ・どの環境へ)。集約で、環境の承認者が名簿の事業決裁者の席に対応づき、G-8 の決断の記録の記名者と一致することを確かめます。一致しない場合は、記名が自己申告であるとして保証の開示に出します。決断の記録そのものは代替しません

### Q5 保全

**回答: 書く。条件の一覧は 3 章。章の割り当ては、要求(何を満たすか)を第4章 G-7 の基準5 と第6章 テンプレ4 の注記、機構(どう満たすか)をフェーズ5 の `qms-document-control.md` と `ci-gates.md`、規制業・CL2 以上の追加要求を第8章 軸C・軸E に置く。GitHub 以外へは、ホスティングが満たすべき性質の一覧として一般化する。**

- 標準に書く理由: 01 §7.4 の条件(保持・取り出し・改変不能・帰属表・意味の定義)を標準側で規定しないと、「GitHub にある」は記録の証拠になりません(01 §7.5)。`qms-document-control.md:44`「対応表はリポジトリの外側で保守する」と `:45`「対象と意味を PR の記述へ残す」は既にありますが、保持期間・user.id・エクスポート・bypass の証跡は書かれていません
- 保管期間の値は標準で決めません(現在の `qms-document-control.md:139`「自組織の文書管理規程による」を維持)。規制ごとに異なるためです(ISO 13485 4.2.5 は機器の寿命以上かつ出荷から 2 年以上、Part 11 11.10(e) は対象記録と同じ期間。01 §3.1・§1.1)。標準が求めるのは、**組織の規程の対象に、ホスティングの承認の記録(複製)を含めること**です。これが無いと、Enduring の責任が誰にも無い状態になります
- GitHub 以外への一般化: 承認イベントを記録の属性の出所として認めるホスティングは、次を提供しなければならない、と書きます。(1) システムが付与する時刻印、(2) 一意のアカウント(共有・bot の識別が可能)、(3) 対象の改訂への紐づけと、改訂後の失効、(4) 提出済み承認の削除不能、または削除の監査記録、(5) 電子形式での取り出し。提供しないホスティングでは、承認イベントを属性の出所に使えず、従来どおり判定者の記名で記録します。これで Q7 の「ツールを変えると成立要件が変わる」は、「ツールを変えると媒体の適格性が変わる」に置き換わります
- 承認の意味の定義: `state = APPROVED` だけでは意味になりません(Part 11 11.50(a)(3)、MHRA 6.14。01 §1.4)。「G-6 を適用する構成の既定ブランチへの PR の承認は、G-6 の変更ごとの確認である」と標準と構成に書き、承認本文の挙動要約がその宣言を兼ねます。G-2・G-4 を PR 承認で記録しない(Q4)ので、意味の多義は生じません
- 電子署名との関係: GitHub の承認は Part 11 の電子署名の技術要件(再認証・氏名・意味の表示)を満たしません(01 §1.4 表)。ただし電子署名が要るのは基礎規則が署名を求める記録だけです(FDA 2003、製薬協解説)。標準は「社内の判定記録に電子署名が要るか」を決めません。`qms-document-control.md:49` の注意書きに「PR の承認」を加え、所管部門が決める旨を書きます

### Q6 形骸化の抑止

**回答: 機械で「中身を見たか」は判定できない。現在の 4 層(挙動要約の形、同一文の検出、検出能力の測定 5.6.2、内部監査の抜き取り)を維持し、内部監査のリスクに基づく抽出条件に「承認までの時間が差分の大きさに比して短い」「コメントも変更要求も無い承認だけの PR」を加える。合否にはしない。限界は開示する。**

- 「LGTM スメル」は研究上も検出方法が無い(Doğan & Tüzün 2022。03 §5.3)。本標準の 5.7.4「記述の実質性を機械的に判定して承認の可否を決めてはならない」(`human-ai-boundary.md:657`)は、この研究と整合します。変えません
- 実証のある指標を抽出条件に使う根拠: 議論の無い変更は欠陥を持ちやすい(McIntosh ら。E2)、コメント無しレビューは LGTM スメル 3.5 倍で承認後コミットが多い(Gön ら。E2)、200 LOC/時超の承認を「性急」とみなす指標(Kemerer & Paulk、McIntosh。E1)。03 §5.2・§5.3。これらは**抽出の重みづけ**に使え、合否には使えません。Waydev の閾値(10%・25%)は製品の目安であり、根拠になりません(02 §7)
- 抽出条件は `process-audit.md:63`〜`68`(無作為とリスクに基づく抽出の併用)に足します。監査の対象は、記録の中身(挙動要約が変更を説明しているか)と、承認後コミットの有無(`commit_id` と最終 head の一致)です。後者は機械で出せます(02 §7)
- 承認の回数を増やす方向は採りません。権限プロンプトの 93% を承認(Anthropic。E2)と、承認ごとの署名様式の却下(`adr/0056-…:165`)に従います
- 宣言(挙動要約)の形の検査は、既に E0 のマーク(EV-0083)付きで置かれています。承認本文へ移しても同じ限界が掛かることを、同じマークの対象に加えます
- 限界の開示: 「機械が確かめるのは形と、承認が最終の改訂を指しているかまでであり、承認者が変更を読んだかは確かめない。確かめるのは内部監査の抜き取りと、検出能力の測定である」を、G-6 の本文に 1 文で明記します。現在の `gate-criteria.md:492` は形についてだけ書いています

### Q7 ツール依存の吸収

**回答: 「記録の意味論は標準が持ち、媒体はホスティングが持つ」で足りる。ただし 2 つを足す。(a) 媒体に求める性質の一覧(Q5)。(b) ツールに依存しない形(複製)への固定(Q3)。この 2 つが無い整理は、ADR-0036 の却下理由をそのまま再現する。**

- ADR-0036 が「Issue のクローズで成立」を却下した理由は「ツールを変えると判定の成立要件が変わる」(`adr/0036-…:101`)です。承認イベントについて同じ批判を避けるには、成立要件を情報項目(Who / When / What / Outcome / Reason / 立場)で書き、ホスティングはその情報項目の**出所**にすぎないと位置づけます。出所が変わっても要件は変わりません
- それでも残るのは、ツールの移行で過去の記録が失われる問題です。GitHub Enterprise Importer はルールセットを移行しません(02 §1.4)。レビューが移るかは明記されていません。複製をリポジトリに持っていれば、リポジトリと一緒に移ります。これが「ツールに依存しない形」の意味です。Gerrit がレビューの footer をコミットに焼き込む(02 §6.5)のと同じ考え方で、GitHub では Bot の複製で代えます
- SOX の監査人が見るのは、母集団を**システムから直接引けるか**(03 §3.1)です。ファイル中心の記録では、母集団は git の履歴から別に作り、記録と突合する必要があります。承認イベント中心では、PR の一覧が母集団になります。どちらでも「PR を経ていないコミット」は git から数える必要があり、集約は既にそうしています(`aggregate-evidence.mjs:525`)。ツールを変えても、母集団の出所が git であることは変わりません

## 4. 監査の再現性テスト

3 問を、3 つの案に当てます。「答えられる」は、1 年後に案件に関与していない者が、記録だけから導けることを指します。

### 問1: 1 年後に、PR #N の G-6 を誰が承認したか

| 案 | 答え | 根拠と限界 |
| --- | --- | --- |
| 承認イベント中心(GitHub 上のレビューだけ) | **条件付きで答えられる** | レビューは削除できず(02 §1.2)、`commit_id`・`submitted_at`・ログイン名が残る。承認者が退会していれば `ghost` になり、誰かが分からない(02 §1.6)。「どの立場で」は承認時点の名簿(git の履歴)から引ける(ADR-0057 S53)。承認が「要件として要求されていた」のか「bypass で承認なしでも通ったのか」は、180 日を過ぎると監査ログから消える(02 §3)。リポジトリが移管・削除されていれば答えられない |
| ファイル中心(`docs/gates/` の手入力) | **「誰が記名したか」には答えられるが、「誰が承認したか」には答えられない** | 記名は自己申告。本人が書いたことを示す証跡が、記録 PR の承認(承認者は判定者でない)かコミットの署名に無ければ、帰属は示せない(01 §7.3)。判定日時も自己申告であり、後から書けたかどうかを区別できない。「対象 PR #N」の承認が、マージされた改訂を指していたかは、ファイルに書かれない |
| 折衷(属性は複製、判断は承認本文、G-7 で記名) | **答えられる** | 複製に `user.id`・login・`commit_id`・`submitted_at`・本文・承認時点の名簿の席がある。退会・移管・本文の編集に耐える。bypass の有無は固定の時点の監査ログの抜粋で残る(Free プランでは「取れない」の記録になる)。承認者が本当に読んだかは、どの案でも答えられない |

### 問2: G-8 の判断が変わる条件は何だったか

| 案 | 答え | 根拠と限界 |
| --- | --- | --- |
| 承認イベント中心(実行環境の承認操作) | **答えられない** | 環境の承認は、誰が・いつ・どの環境へ、しか持たない。「判断が変わる条件」「確認していない事項」「受容したリスク」「出荷判定者の異議」の欄が存在しない。03 §8.2「リリース判定の記録は PR で代替されていない」のとおり |
| ファイル中心 | **答えられる** | 決断の記録の欄(`deliverable-templates.md:512`)。「確認していない事項」が空欄・「なし」の記録は無効(`:564`)。記名の帰属は自己申告だが、G-8 は 1 件の決裁であり、記名者と環境の承認者の一致を機械で突合できる(Q4) |
| 折衷 | **答えられる** | G-8 はファイル中心を維持する。環境の承認操作は帰属と時刻の裏づけに使い、決断の記録を代替しない |

### 問3: 2026-Q3 に出荷した変更のうち、独立した人の確認を経ていないものはどれか

| 案 | 答え | 根拠と限界 |
| --- | --- | --- |
| 承認イベント中心 | **概ね答えられる** | 母集団はマージ済み PR の一覧と、PR を経ていないコミット(git)。各 PR の承認者を名簿と指示者に照らす(4 条件 `gate-criteria.md:469`〜`472`)。承認が無い PR は、bypass で通ったものも「承認なし」として現れる。限界: AI が作成した PR の指示者は PR 本文(起案者の記載)に依存する。退会者は ghost。承認後の本文の編集は検出できない |
| ファイル中心 | **安全側には答えられるが、記録の欠落と未確認を区別できない** | 判定記録が無い変更は「未判定」(ADR-0036 の意味論)。ただし「確認したが書き忘れた」と「確認していない」を区別できず、Q3 の終了後に判定日時を Q3 内として書き足しても検出できない(同時性の欠如)。母集団は git から別に作る必要がある |
| 折衷 | **答えられる** | 出荷の範囲の複製が母集団と一致していることを G-7 で突合済み。各変更について、承認者・指示者・名簿の対応・挙動要約の有無・最終改訂との一致が複製にある。限界は承認イベント中心と同じ(指示者の記載、ghost)だが、ghost は `user.id` で補える |

結論: 承認イベント中心は問2 で落ち、ファイル中心は問1 と問3 の帰属・同時性で落ちます。折衷だけが 3 問に答えます。ただし折衷も「承認者が変更を読んだか」には答えません。これはどの案でも同じであり、内部監査の抜き取りと検出能力の測定で扱う領域です。

## 5. 規制業(軸C)・CL2 以上(軸E)と、それ以外の構成で要求を分けるか

**分ける。境界は現在の軸C「規制業」と軸E「CL2 以上」をそのまま使う。分ける項目は、固定の時点・監査対応書式の中身・保管と評価の組織側の作業の 3 つである。属性の出所(承認イベント)と判断の受け皿(承認本文)は分けない。**

| 項目 | 規制業(軸C)・CL2 以上(軸E) | それ以外 |
| --- | --- | --- |
| 属性の出所 | 承認イベント(条件 1〜13) | 同じ |
| 判断の受け皿 | 承認本文(挙動要約)+ 監査対応書式(2 人目・安全性の評価者。`deliverable-templates.md:496`) | 承認本文 |
| 固定の時点 | **変更ごと**。マージの後、G-7 を待たずに複製が固定されていることを G-7 の前提にする。固定されていない変更は記録の欠落 | マージごとの機械の複製を推奨し、**G-7 の時点で固定されていること**を要求する |
| 「PR の承認だけでは記録にならない」(`deliverable-templates.md:503`、`tailoring-guide.md:508`) | **維持する。ただし文言を改める**。「承認イベントは属性の出所になる。判断の中身(監査対応書式)と変更ごとの固定が無ければ記録にならない」 | 当てない |
| 保管 | 組織の文書管理規程の対象に複製を含める(条件 11)。ツールの評価(条件 16)。電子署名の要否の判定(条件 17) | 保管は規程による(現行)。評価と電子署名の判定は求めない |
| 監査証跡のレビュー(条件 15) | 内部監査の観点に加える | 同じ(観点は体制によらない) |

- 境界の根拠: 規制業で変更ごとの固定を要するのは、ISO 13485 7.3.9「変更は実装の前にレビュー・承認し、記録を維持する」と IEC 62304 8.2.1「承認が実装に先行する」(01 §3)が、変更単位の記録を前提にしているためです。出荷単位でまとめて固定すると、出荷までの間に承認本文が編集される窓が開きます。非規制でこの窓を許容する判断は E0 です(7 章)
- CL2 以上を規制業と同じ側に置く根拠は、テンプレ4 が既に監査対応書式を「規制業の監査対応書式、または CL2 以上の体制で必須」としている(`deliverable-templates.md:496`)ことと、機能安全規格が独立性の水準の記録を求める(IEC 61508 Table 4・5、ISO 26262-2 表1。01 §4)ことです。承認イベントは独立性の水準を持たないため、監査対応書式で補う必要があります
- SOX の IT 全般統制の対象(財務報告に関わるシステム)は、本標準の「規制業」の定義に入るかが明確でありません。SOX 監査が要るのは母集団の完全性と SoD の証拠(条件 8・10・13)であり、Part 11 の電子署名ではありません。軸C の定義に当たるかは主宰の整理に委ねます。本書は決めません
- FDA の査察や認証機関の監査で、GitHub の PR 承認を記録として提示して受理された一次事例は見つかっていません(03 §8.5)。標準は「承認イベントが規制当局に受理される」と書いてはなりません。書けるのは「規格が求める属性を満たす」ことまでです

## 6. 採ってはならない案と理由

| # | 案 | 理由 |
| --- | --- | --- |
| 1 | 承認イベント(`APPROVED`)単独を成立要件にする | 判断の中身が無い。MHRA 6.15「問題の有無の明示」、PIC/S 7.5「何が決定に影響したか」を満たさない。本標準が既に禁じている(`gate-criteria.md:465`)。LGTM スメルが記録として通る |
| 2 | 手入力帳票の氏名・日時を成立要件のまま残し、承認イベントを参考情報にする | 帰属と同時性が自己申告のまま。規制側は「誰が・いつ」をシステムが記録することを求める(01 §7.1)。承認イベントの方が強い記録であるのに弱い方を正本にする構成は、監査で説明できない |
| 3 | 手入力の値と承認イベントが食い違ったとき、手入力を優先する | 「正確(Accurate)」の原則に反する。システム生成の値が正であり、食い違いは所見である(Annex 11 §6 は手入力に第二者確認を求める。01 §2.2)。食い違いは保証の開示に出し、どちらが正しいかは内部監査が決める |
| 4 | 記録固定の App を `exempt` に置く | bypass が監査に出ない(02 §4.1)。監査証跡を黙って止める構成は PIC/S 9.6・MHRA 6.13 に反する。02 §9.3 案 B の却下と同じ |
| 5 | App・bot・`GITHUB_TOKEN` の承認を人の承認に数える | ADR-0028 決定7。GitHub の公式仕様が未定義(02 §4.2)。Chromium が Rubber Stamper に OWNERS 承認を与えない理由(他者の関与なしに着地できる悪用経路。03 §4.4)がそのまま当てはまる |
| 6 | PR 本文または Issue コメントを、承認者の判断の受け皿にする | PR 本文は起案者が編集できる(帰属の破壊)。コメントは削除できる(Enduring の欠如)。Q2 |
| 7 | 承認までの時間・コメント数・差分量を合否にする | 5.7.4(`human-ai-boundary.md:657`)。研究上も検出方法が無い(03 §5.3)。閾値は製品の目安しか無い(02 §7)。自明な変更を誤検出し、閾値を満たす経路が通過の経路になる |
| 8 | 「GitHub にあるから記録がある」とし、複製を持たない | 監査ログ 180 日、ghost、本文の編集、移管でのルールセットの消失(02 §9.2)。Enduring・Available を満たさない。1 年後の再現(4 章 問1)に落ちる |
| 9 | 書き忘れた G-6 の判定記録を、事後に「事前の承認」として書き足すことを認める | 同時性の欠如。事後の確認は「独立した人が確認し、G-6 の判定記録を残したうえで突合し直す」(`gate-criteria.md:588`)経路で、事後の確認として記録する。委任の変更を人の判定と同じ語で記録しない規定(`deliverable-templates.md:560`)と同じ理由 |
| 10 | 規制業の「PR の承認だけでは記録にならない」を単純に撤廃する | 監査対応書式の中身(2 人目・安全性の評価者)と変更ごとの固定は、承認イベントに乗らない。5 章。撤廃ではなく文言の修正 |
| 11 | 記録だけのコミットに、PR と判定者以外の承認者を課し続ける(成立要件として) | 記名と二重になる(`adr/0057-…:509`)。承認者は判定者でないため、その承認は判定を裏づけない。強制層の都合で PR が残る場合は、承認を事務と明記する(Q4) |
| 12 | 保管期間の値を標準で決める | 規制ごとに異なる(ISO 13485 4.2.5、Part 11 11.10(e)、SOX)。現行の「組織の規程による」を維持し、規程の対象に複製を含めることだけを求める |
| 13 | 承認ごとに「何を確かめたか」の署名様式を足す | ADR-0056 却下表(`adr/0056-…:165`)。検出能力を示さない書類が増える。挙動要約で足りる |
| 14 | 1 人目と 2 人目の承認を、記録 PR の承認(ファイルの取り込み)で代える | 記録 PR の承認者は変更を見ていない。「2 件の確認」(`gate-criteria.md:482`)に当たらない |

## 7. 根拠水準マークが要る箇所

| # | 箇所 | 水準 | 理由と差し替え条件の候補 |
| --- | --- | --- | --- |
| 1 | 非規制の構成で、固定の時点を G-7 まで許す判断 | E0 | 固定を遅らせることで失われた記録(承認本文の編集、ghost 化)の件数を、採用者の内部監査で集める。1 件でもあれば、マージごとの固定を要求事項へ上げる |
| 2 | 規制業・CL2 以上で、変更ごとの固定を G-7 の前提にする判断 | E1 | 規格は変更単位の記録と保持を求める(ISO 13485 7.3.9、Part 11 11.10(e))が、固定の周期そのものは定めていない。査察で複製を提示し受理された事例が出れば E2 へ |
| 3 | App のコミットが `RECORD_PATHS` の外に触れていないことの機械検査を、bypass の穴の補いとする判断 | E0 | この検査で不正を検出した事例は無い。App の鍵の漏洩を検出した事例、または検出できなかった事例が出たら見直す |
| 4 | 内部監査のリスクに基づく抽出条件に「承認までの時間が差分に比して短い」「コメントも変更要求も無い承認」を加える判断 | E2 | Gön ら(コメント無しレビューは LGTM スメル 3.5 倍)、McIntosh ら(議論の無い変更は欠陥を持ちやすい)。ただし OSS の測定であり、本標準の文脈での測定は無い。2 期分の監査記録で、この条件で抽出した対象の所見率が無作為抽出と差が無ければ外す(`process-audit.md:174` と同じ型) |
| 5 | 承認本文の挙動要約の形の検査(EV-0083)を、承認イベントへ移した後も同じ限界として開示する | E0(既存 EV-0083 の対象の拡張) | 新しいマークを増やさず、EV-0083 の対象に「承認本文に置いた場合」を加える |
| 6 | 折衷が記録 PR の往復を減らし、かつ記録の信頼性を下げないという主張 | E0 | 往復の減少は設計上の帰結であり測定していない。信頼性については、手入力と承認イベントの食い違いの件数(6 章 #3)を集め、食い違いが承認イベントの誤りだった事例が出たら見直す。`236b:326` の 7.7 倍(E2)は様式の欄数についての証拠であり、PR の本数についての証拠ではない。流用しない |
| 7 | 「承認イベントは規制当局・認証機関に受理される」という含意を持つ文 | 書かない | 一次事例が無い(03 §8.5)。E0 でマークして書くのではなく、書かない。書けるのは「規格が求める属性を満たす」まで |
| 8 | 複製に含める最小の組(02 §9.1 の 8 項目+ルールセット id+監査ログの抜粋) | E1 | Part 11 11.50(a) と 02 の調査から組んだ値。査察で不足を指摘された項目が出たら足す |
| 9 | 承認の失効の粒度(`dismiss_stale_reviews_on_push` とリベースだけの push) | 本 Issue の範囲外 | #296 に送られている(`295/decision-spec.md:64`)。本書は「承認は承認した内容に束縛される」を不変条件として前提にするだけ |

## 8. 本書が決めていないこと

- SOX の IT 全般統制の対象が、本標準の軸C「規制業」に入るか(5 章)
- 記録だけのコミットを PR なしで受け付けるために、ルールセットの構成をどう分けるか。GitHub ではパス単位の除外ができない(02 §4.1)ため、記録 PR が残る構成は避けられない場合がある。その場合の承認を事務と明記することまでが本書の提案であり、強制層の構成は実装の問題として council-field・survey-github の意見に委ねる
- 承認イベントを属性の出所にした後の、G-7 基準5 の「出荷の範囲の記録の数え方」(`aggregate-evidence.mjs:371`〜`375` がファイルの追加で数えている)の実装
- 電子署名が要る記録かどうか(条件 17)。組織の所管部門が基礎規則に照らして決める。標準は決めない(`qms-document-control.md:49` と同じ姿勢)
