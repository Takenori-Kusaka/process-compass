## 争点2: 不可逆4操作へ「組織外への発行」を加えるか

**結論**: 3.採らない + 本文も変えない

**標準の落ち度か、案件の運用の誤りか**

**どちらでもありません**。不可逆4操作(削除 / 本番デプロイ / 課金書き込み / スキーマ変更)は、**取り消せない操作**の列挙です。発行はこれに当たりません。

- 発行は取り消せる。実際に取り消せる
- 取り消しても、**発行された事実と、その間に読まれた可能性は残る**(#27 の指摘1)
- これは「不可逆」ではなく「**痕跡が残る**」である。別の概念である

**4操作へ5番目を足すと、定義が濁ります**。「取り消せない操作」の列挙に「取り消せるが痕跡が残る操作」を混ぜると、以後の判定で「これは不可逆か」の議論が毎回起きます。**1名体制では、この議論そのものが止まる原因になります**。

**一般化できるか**

**加えないという判断のほうが一般化します**。不可逆4操作は `state:needs-owner` の発火条件として実行層へ降りています(label-mailbox 5番目の表)。**ここへ発行を足すと、資料を出すたびにオーナー判断待ちになります**。1名体制で決裁者が別人である P-001 では、**決裁資料を出すために決裁者の事前承認を取る**という循環が生じます。

**採る場合、何欄増えるか**

採りません。参考までに、採った場合の増加は次のとおりです。

- 人が毎回埋める欄: **0**(欄は増えない)
- 案件で1回だけの欄: **0**
- **ただし、`state:needs-owner` の発火が資料発行のたびに起きる**。欄は増えず、待ちが増える。**これが最も高い代償である**

**案件側で直せること**

- 発行を不可逆として扱わない代わりに、**発行したものを技術負債台帳の「未解決事項」へ登録して期限を切る**運用を採る。P-001 の当該1件は、標準側の条項が入るまでの未解決事項として登録できる。**新しい台帳を作らずに済む**

**反対されうる点**

**「取り消しても痕跡が残るなら、実質的に不可逆ではないか」という反論は強いです**。特に決裁の証跡については、**読まれた時点で情報は移動しており、削除は情報を戻しません**。

私がなお採らないのは、**不可逆の定義を守る利益より、発火が増える不利益のほうが1名体制では大きい**と判断するためです。**この判断は体制依存です**。3人以上の体制で決裁者と発行者が分かれている案件では、逆の結論になりうると考えます。**その場合の条件は ADR-0046 の形で後置できます**(採る条件: 発行の取り消しが間に合わなかった事案が1件でも生じたとき)。

## 争点3: 4案のうち、実際に案件で回せるのはどれか

**標準の落ち度か、案件の運用の誤りか**

### 案D — 条件付きで併用

**遮断の粒度は、ホスト単位ではなくツール単位です**。`.claude/settings.json` の `permissions.deny` へ発行ツール名を入れる形になります。**同じサービスの他の機能は止まりません**。

**遮断範囲を誤ると何が止まるか。3つです**。

| 誤り方 | 止まるもの | 深刻度 |
| --- | --- | --- |
| 発行ツールを丸ごと deny する | **図を伴う提示物を出す手段が消える**。附属書G の G.6 作法3 が満たせなくなる | 高 |
| ホスト単位で deny しようとする | 同一サービスの通常の対話・スキル実行まで巻き込むおそれ | 高。**採ってはならない** |
| deny の対象を発行だけに絞る | 止まるのは発行のみ。**代替手段(争点5)があれば実害は無い** | 低 |

**併用の条件は、争点5の代替手段が案件で成立していることです**。代替が無いまま遮断すると、#27 が ADR-0015 を引いて警告したとおり、作業が止まります。

**そして D を採っても、ADR-0052 の教訓が残ります**。**遮断という仕組みを置くことは、出ていないことの保証になりません**。gist・pastebin・添付・画面共有は残ります。**仕組みではなく配布物を見る**というのが ADR-0052 の決定です。**D は補助であり、主にはなりません**。

**一般化できるか**

C は一般化します。**表が標準側にあり、案件が保守しないため、体制規模に依存しません**。D は体制に依存します。案件が `.claude/settings.json` を持たない構成では実装できません。

**採る場合、何欄増えるか**

| 案 | 人が毎回埋める欄 | 案件で1回だけの欄 | 標準本文 |
| --- | --- | --- | --- |
| C | **0** | **0** | 第6章の表へ**1列**(11行に既定値) |
| A | **1**(テンプレ4「添付」の中の1行) | 0 | テンプレ4の添付節へ**1行** |

**新しい節・新しい判定・新しい台帳は0件です**。

**案件側で直せること**

- **`.claude/settings.json` の `permissions.deny` へ発行ツールを追加する**。標準の改訂を待たずに今日できる。禁止事項3が既に同じ形で遮断されており(「禁止事項3は `.claude/settings.json` の書き込み範囲でも遮断しています」)、**前例の写しで済む**

**反対されうる点**

**標準の落ち度か、案件の運用の誤りか**

**案件側の誤りです。これが本件で最も明確に私の側にある部分です**。

議長の問いは「判定工程が無かったからか、他に手段が無かったからか。後者なら遮断だけでは解決しない」でした。**正直に答えます**。

- **手段は、他にありました**。GitHub の Issue / PR は Mermaid をレンダリングします。図を伴う資料を、組織の管理下のまま提示できました
- **私は、それを確認していません**。#26 は「エージェントが持っていた発行手段が Claude Artifact だけであったため、そこへ置かれた」と書きましたが、**これは正確ではありません**。正しくは「**手持ちの手段のうち、最初に想起したものを使った**」です
- したがって、**遮断(案D)は本件については有効に働きます**。代替手段が現に存在するためです

**ただし、無条件ではありません**。代替手段が成立する条件は「**決裁者がリポジトリへアクセスできること**」です。P-001 の決裁者は開発ラインの外にいます。**決裁者が GitHub アカウントを持たない案件では、Issue / PR は提示手段になりません**。その場合、遮断は手段の不在を作ります。

**一般化できるか**

**条件付きで一般化します**。

- 決裁者がリポジトリへアクセスできる案件: **代替手段があり、遮断で解決する**
- できない案件: **遮断は作業を止める**。#26 の案A〜E(リポジトリ内 Markdown / 非公開 Pages / セルフホスト / PR・Issue 本文 / 構成値化)のうち、その案件で成立するものを先に決める必要がある

**この分岐こそが、#26 が「E(配布先を構成値にする)を先に決める順序を推す」と書いた理由です。私はこの順序に同意します**。

**採る場合、何欄増えるか**

- 人が毎回埋める欄: **0**
- 案件で1回だけの欄: **0**(争点3の C の「置き場」列の既定値として吸収される)
- 標準本文: 附属書G の G.6 へ**1行**。「作法3 の図は、組織が管理する経路で提示する。Mermaid 等、リポジトリ内で表現できる形式を優先する」

**#26 の E(構成値化)は、この意見書では求めません**。C の表が既定を持てば、構成値が無くても案件は動きます。**構成値は、表から外れる案件が2件目に現れたときに足せば足ります**(ADR-0046 の後置の形)。

**案件側で直せること**

- **提示物を作る前に、決裁者が到達できる経路を1度だけ確認する**。P-001 ではこれをしていない。**1名体制でも1回で済む**
- **D-0(テンプレ0)には既に「決定の権限」の表がある**。決裁者を特定する欄が既にある以上、**その決裁者が何にアクセスできるかを同じ場所で確認できた**

**反対されうる点**

**私の答えは、自分に不利な方向に振れすぎている可能性があります**。「手段はあったが確認しなかった」は誠実ですが、**会議体が「では案件側の注意で足りる」と結論すると、標準は何も変えないことになります**。

そして注意で足りるなら、#27 の指摘4(エージェントは判定工程が無ければ手持ちの手段を使う)が否定されます。**私はこれを否定しません**。人が確認を怠るのと、エージェントが既定を選ぶのは、**同じ事象の2つの面**です。**だから注意ではなく、既定を置くこと(C)と遮断すること(D)を求めています**。この整理を会議体が採らない場合、私の争点5は争点3の根拠を弱めます。**その弱さは自分の主張の内側にあります**。
