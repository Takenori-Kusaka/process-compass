## 1. 先に結論

- **ADR-0036 決定1(判定記録の作成をもって成立。記録の無い状態は未判定)は維持する**。決定1 が規定するのは記録の**存在と欄**(判定者・判定日時・結果・確認した項目・差し戻し理由 `gate-criteria.md:65`)であり、媒体でも置き場でもない。改訂案が攻撃しているのは決定1 ではなく、テンプレート独自の置き方(`docs/gates/` + 記録 PR + 判定者以外の承認者)である
- **承認イベントを成立要件に置く案は却下する**。承認イベントは「承認の操作があった」ことの機械の記録であり、「どの基準と突き合わせたか」「何を確認しなかったか」「差し戻すなら何番の項目か」を持たない。決定1 が自己申告を排した対象は「判定の存在」ではなく「基準との突合の存在」である(`gate-criteria.md:68`)
- **折れる点を 3 つ認める**。(a) 帳票の氏名・日時の欄は、それ自体では Who / When の証拠にならない(規制側の評価は 01 7.3 のとおり)。(b) 記録 PR に判定者以外の承認者を重ねる現行テンプレートの構成は、「承認の回数を増やさない」(03 8.4)に反し、標準が既に認めている「記録だけのコミットは PR を経なくてよい」(`ci-gates.md:609`、ADR-0057:509)とも揃っていない。(c) 決定1 に根拠水準マークが無い(00 5 章注)。いずれも**決定1 を変えずに直せる**
- 起票者の事象のうち、**事実として成り立たない主張が 2 つ**ある。「本体 PR をリベースすると対象 SHA が変わり記録を作り直す」(対象は PR の番号で書ける `template/templates/04-gate-record.md:20`)、「`check-pr.mjs` は基底の `docs/gates/` だけを読むため本体 PR の記録を数えない」(それは停止の解除と例外承認の話であり、G-6 の承認者の数は `docs/gates/` を読まず合否にもしない `00:406`)
- **G-6 については改訂しなくても起票者の問題は解ける**。G-6 の記録は承認レビュー(挙動要約つき)で既に成立する(`gate-criteria.md:480`、`aggregate-evidence.mjs:509`)。テンプレートの `next.mjs` が承認イベントを読まない(`00:458`)なら、それはテンプレート側の実装が標準より厳しいだけである
- **Bot による記録の固定は認めない**。bypass はパス単位に絞れず(02 4.1)、`exempt` は監査に出ない(02 5.3)。「強制層に置いた項目だけが遮断できたものとして数えられる」(`template/.github/rulesets/README.md:41`)と両立しない
- 改訂するなら、**守るべき不変条件を 9 つ**挙げる(5 章)。このうち「承認の操作があったことだけでは数えない」(`gate-criteria.md:465`)を落とすと、起票者自身の懸念(中身を見ずにマージ)が正規化される

## 2. Q1〜Q7 への回答

### Q1 成立要件 — 維持する

決定1 を維持します。置き換えません。理由は 3 つです。

第一に、決定1 の文言は媒体を規定していません。成立要件は「判定記録の作成。判定者・判定日時・結果・確認した項目・差し戻し理由が埋まっていること」(`gate-criteria.md:65`)です。`docs/gates/` は第5章の図(`label-mailbox.md:225`)とテンプレート(`template/.claude/skills/gate/SKILL.md:12`「置き方はテンプレート独自」)にだけ現れます。起票者の事象は全てテンプレートの置き方に起因しており、決定1 を改廃する理由になりません。

第二に、承認イベントは決定1 が要求する欄のうち「確認した項目」「差し戻し理由」を構造として持ちません(02 7 章: APPROVE では本文を省略できる。03 8.2: PR は「誰がどの立場で何を審査し何を決めたか」の置き場を持たない)。差し戻しに要する「満たさない判定基準の項目番号、再提出の期限」(`gate-criteria.md:85`)を CHANGES_REQUESTED のどこに持たせるかは決まっていません(00 8.3)。欄を持てない媒体を成立要件にすると、欄は事務へ落ちます。それは決定1 を置き換えるのではなく、却下案「判定記録の作成を事後の事務のままとする」(`adr/0036-gate-closure-by-record.md:103`)の復活です。

第三に、P-001 の停止(`adr/0036-gate-closure-by-record.md:14`〜`16`)は「材料が揃い、レビューも済み、Issue も閉じられていた」状態で起きました。レビューが済んでいたとは、承認イベントが存在していたということです。**承認イベントがあっても工程は止まった**。承認イベントを成立要件に置けば P-001 は再発しない、とは言えません。止まった原因は「何をもって閉じるかが本文に無い」ことであり、決定1 はそれを「記録の作成」と定めた。媒体を変えても、この答えは変わりません。

折れる点: 決定1 には根拠水準マークがありません(`00:703`)。「記録がなければ判定の存在が自己申告になる」は論理ですが、「記録を成立要件にすると P-001 の停止が起きない」は E2(単一事例)です。マークを足します(6 章)。

### Q2 属性と判断の分離 — 分離は認める。機械転記は「記録の作成」ではなく「事務」として認める

属性(誰が・いつ・何に・結果)と判断の中身(挙動要約・確認していない事項・差し戻し理由)を分けて考えること自体は、既存の語彙にあります。第7章 7.3 は「記録した者」と「承認した者」を別の欄に置き(`exception-escalation.md:50`・`57`)、D-0 の記録は承認者の同定を所有者定義による承認で、日時をマージ日時で満たしています(`deliverable-templates.md:338`)。

認める形:

- 属性を承認イベントなどから**機械が下書きへ転記する**こと。`recording.md:24` は、AI の担い手が記録を起こし判定者本人が結果欄を確定する運用を既に前提にしている。転記は記録の作成ではなく、作成の補助である
- 判断の中身の受け皿は、G-6 では承認レビューの本文(`gate-criteria.md:480`、`G-6.md:17`)、それ以外のゲートでは判定記録(テンプレ4)。**PR 本文は受け皿にしない**。作成側の記載は挙動要約に数えない(`gate-criteria.md:472`)のと同じ理由で、PR 本文は作成側の文書である。Issue コメントも受け皿にしない。PR 本文は削除できないがコメントは削除できる(02 1.2)

認めない形:

- 転記された属性だけで「判定者の記名」を代えること。判定は記名の記録で成立する(`adr/0054-seat-accountable-performer.md:88`)。記名は責任の引受であり、ログイン名の転記は引受ではない。ログイン名と自然人の対応は名簿で引く(ADR-0057 S53)が、対応づけは照合であって記名ではない
- 転記された属性を「改ざんされない」ものとして扱うこと。転記先がファイルなら、ファイルは手で書き換えられる。転記元が API の応答なら、応答の真正性はホスティングの信用に依存する(02 9.3「全案に共通する穴」)。転記は照合の材料であり、記録の本体は判定者の記名と判断の中身である

### Q3 置き場と固定 — ゲートごとに作る。基底への固定は事務。Bot の固定は認めない

- **記録はゲートごとに、判定の時点で作る**。G-7 でまとめて固定する案は採らない。記録が後追いになれば「判定者が実際に基準と突き合わせたかどうかを誰も確かめられない」(`label-mailbox.md:230`)。規制側も Contemporaneous を求める(01 2.1)。出荷の集約が「範囲内に追加されたファイル」で今回の記録を数える(`aggregate-evidence.mjs:371`〜`375`)のは、ゲートごとに作られる前提の上にある
- **基底ブランチへ入れることは、標準では「固定の事務」であり成立要件ではない**。記録だけのコミットは製品の変更に数えず、PR を経なくても集約が受け付ける(`ci-gates.md:609`、`aggregate-evidence.mjs:973`)。層1 の改版に PR を課さない先例がある(`adr/0057-organizational-quality-assurance.md:509`)。**テンプレートのルールセットが `docs/gates/` に例外を持たない(`team.json:5`〜`6`)のは、集約の側と揃っていない**(`00:524`)。これはテンプレートの欠陥であり、標準の決定ではない
- **Bot による固定は認めない**。bypass はアクター単位で全規則に効き、パス単位には絞れない(02 4.1・5.3)。App の鍵が漏れれば既定ブランチの任意のファイルを書ける(02 9.3 案 A の穴)。`exempt` は Rule insights に出ない(02 4.1)。記録を固定するために強制層へ穴を開けるのは、「強制層に置いた項目だけが遮断できたものとして数えられる」(`rulesets/README.md:41`)を自ら崩す行為であり、ADR-0038 の「強制層の縮小」(`adr/0038-…:46`)に当たる

折れる点: 記録だけのコミットに PR を課さないことを、GitHub のルールセットはパス単位で実現できません(02 4.1、5.2)。「標準は PR を課していない」と言っても、テンプレートが既定ブランチの保護を維持する限り、記録は PR を経るか、bypass を持つ誰かが押し込むかのどちらかです。この矛盾の解き方は 4 章に書きます。決定1 とは独立の問題です。

### Q4 PR に紐づかないゲート — ファイル。判定者が作成者でもあるゲートは「判定者が記録 PR を承認する」形で折り合う

- G-1〜G-4・G-8・SG の記録は判定記録(ファイル)に置く。これらに承認イベントは存在しないか、存在しても対象が違う(G-2 の対象は「機能 ID + 受入基準の版のコミット」`deliverable-templates.md:460`。仕様ファイルの PR の承認は、その版の確定の事務であって判定基準 5 点との突合ではない)。QMS 対応表の「G-2 | 仕様ファイルの PR 承認とマージ」(`qms-document-control.md:37`)は「どの操作がどの承認へ相当するか」の宣言(同 `:33`)であり、成立要件の規定ではない。この食い違い(00 2.8 注)は対応表の側の文言を整えることで解く(4 章)
- **判定者が成果物の作成者でもあるゲート(G-2・G-3・G-4・G-7、ADR-0060:58)では、判定者が「自分の成果物の PR」を承認できないのは正しい挙動**であり、折り合うべき対象ではない。折り合いが要るのは「記録 PR」のほうである。記録 PR の作成者が判定者本人なら、判定者は自分の記録 PR を承認できず、別の承認者が要る。これが起票者の「記録 PR にも判定者以外の承認者が要る」の正体である
- 折り合いの形: **記録の草案は判定者以外の文脈(AI の担い手のレーン、または別の人)が起こして PR を開き、判定者がそれを承認する**。`recording.md:24` の運用そのもの。判定者は記録 PR へ push しない(`require_last_push_approval` で自分の承認が無効になるため)。この形では、記録 PR の承認イベントが**判定者本人の承認**になり、承認イベントの Who / When(02 9.1 の最小の組)が判定者の記名を裏づける。「属性は機械、判断は人」を、決定1 を変えずに満たせる。`docs/gates/**` を CODEOWNERS で判定者のロールへ割り当てれば、記録の置き場の承認者を固定できる(02 4.3)
- ただし、草案を起こす文脈は成果物を起案した文脈であってはならない(第3章 3.5.3「成果物を起案したセッションは、その成果物の判定の草案を作らない」`template/CLAUDE.md` 判断の確定と委任)。この形を 1 名体制へ持ち込む余地はない。1 名体制(未達)では承認を強制するルールセットを置かない(`rulesets/README.md:21`)ので、記録 PR の承認者の問題は元から生じない

### Q5 保全 — 書く。第4章 共通ルールの「記録」の節に、承認イベントを記録の媒体に用いる条件として書く

承認イベントを G-6 の記録として認めている以上(`gate-criteria.md:480`)、認める条件を標準が持たないのは欠落です。これは決定1 の改廃ではなく、決定1 の「記録」の定義を媒体ごとに補う追加です。

書く場所: 第4章「判定の成立」の節(`gate-criteria.md:57`〜`72`)に「記録の媒体」の小節を足し、第5章 `qms-document-control.md:44`〜`45`(対応表・意味の記述)と附属書I 要件⑦(`adoption-guide.md:498`)を参照する。

条件(01 7.4 と 02 9.1 から。GitHub 固有の語を使わない):

| 条件 | 標準の語での表現 |
| --- | --- |
| 帰属 | 承認したアカウントが名簿の自然人に対応づく(ADR-0057 S53)。共有の認証情報の承認は数えない(`adr/0035-…:84`) |
| 同時性 | 日時はホスティングが付与したものを用いる。人が転記した日時を日時に数えない |
| 対象の固定 | 承認は対象の版(コミットの識別子)に束縛される。対象が変われば失効する(#296 T-09) |
| 意味 | 「承認」がどのゲートのどの判定に当たるかを、案件の構成で事前に宣言する(`qms-document-control.md:33`) |
| 保持 | 案件の記録と同じ期間、ホスティングの外へ取り出せる形で残す。取り出しは承認と同じ時期に自動で行う。監査ログの保持は 180 日(02 3 章) |
| 消失への備え | アカウントの消滅(ghost 化)に備え、数値の識別子と名簿の対応を取り出しに含める(02 1.6) |
| 迂回の記録 | 承認を省ける者(bypass・admin)の存在と、その行使の記録を保持する(02 9.1) |

GitHub 以外への一般化: 条件は媒体に依らない語で書き、ホスティングごとの満たし方は第5章と準拠テンプレートが持つ。これが Q7 の「意味論は標準、媒体はホスティング」の実体です。

### Q6 形骸化の抑止 — 現行の 4 条件を維持し、機械で判定しない限界を開示し続ける

- 抑止の手段は既にある。挙動要約の必須(`gate-criteria.md:459`)、承認の操作だけでは数えない(`:465`)、同一の文を 2 件目に数えない(`:483`)、規模の基準値と区分 R2(ADR-0058)、内部監査の抜き取り(`:483`)、検出能力の実測と承認権限の一時制限(ADR-0059:52)
- **新しい機械の検査を足さない**。「中身を見たか」の機械検出は研究上も未解決(03 5.3: LGTM スメルは検出方法を提案できず除外された)。承認までの時間・コメント数の閾値は自明な変更を誤検出する(02 7 章)。記述の実質性を機械で判定して承認の可否を決めることは禁じられている(`human-ai-boundary.md:657`)
- 開示の継続: 「機械が見るのは形だけ」(`gate-criteria.md:492`、EV-0083)を落とさない
- 改訂案への反証: 承認 1 クリックで記録が成立する形は、形骸化を**正規化**する。実証では、コメントなしの承認は LGTM スメルを 3.5 倍示し、承認後のコミットが多い(03 5.3)。承認に宣言を添える方式が実証と整合する(03 8.4)。本標準の挙動要約はその宣言である。改訂が条件4(`:472`)を保つなら形骸化は悪化しないが、承認イベントの存在だけで成立させるなら悪化する

### Q7 ツール依存の吸収 — 「意味論は標準、媒体はホスティング」で足りる。ただし「成立」は標準の側に残す

ADR-0036 が「Issue のクローズで成立」を却下した理由(`adr/0036-…:101`)は、承認イベントにもそのまま掛かります。承認イベントは「ツールの状態」であり、ホスティングを変えれば存在しなくなります。業界の実務がホスティングの状態を記録にしていない点は重要です。kernel はトレーラ、Gerrit はコミットの footer、Prow は書き戻しのコメントであり、「承認をホスティングサービスの状態ではなくコミットのメッセージか Bot の書き戻しに写している」(02 6.5「共通点」)。Gerrit が消えても承認の記録はクローンに残る(02 6.5)。

整理:

- 成立要件 = 欄が埋まった記録の存在(標準が持つ)
- 媒体 = 記録をどこに置くか(構成が宣言し、ホスティングと準拠テンプレートが持つ)
- 承認イベント = 媒体の一つ。Q5 の条件を満たすときだけ、G-6 の記録の媒体に数える。他のゲートでは、属性の転記元に用いてよいが媒体にしない

この整理で「ツールを変えると成立要件が変わる」は起きません。変わるのは媒体だけです。足りないのは、Q5 の条件を標準が書いていないことです。

### 4.2 解けない部分(決定1 とは独立に、決めるべきこと)

- **記録だけの変更に PR を課さないことを、GitHub の既定ブランチで実現する方法**。ルールセットはパス単位の除外を持たない(02 4.1)。選択肢は、(i) 記録 PR を 1 本残し B の形で承認者を判定者本人にする、(ii) 記録を別のブランチ・別のリポジトリに置く(02 9.3 案 D。「記録はコードと同じ履歴にある」を失う)、(iii) bypass を持つ Bot(認めない)。弁護役は (i) を推す。理由は、記録 PR の承認イベントが判定者の記名を裏づける副産物を持つため。E4(未実証)
- **承認イベントの保全の条件(Q5)**。標準に無い。足す(追加であり、改廃ではない)
- **決定1 の根拠水準マーク**。無い。足す
- **`strict_required_status_checks_policy` を外すことの扱い**。往復の直接の原因だが、外すと「CI が最終の状態で走った」保証が落ちる。これは ADR-0038 の統制の弱化(閾値の緩和)に当たり、ADR-0050 の型(段階で緩めず、置く規則の選び方を直す `adr/0050-…:60`)で扱う。弁護役は外すことに反対する。#296 の結論を待つ

## 7. 弁護役の結語

起票者の訴えは、**テンプレートの置き方**(`docs/gates/` + 判定者本人が作る記録 PR + strict)への訴えであり、ADR-0036 決定1 への訴えではありません。決定1 は媒体を規定しておらず、G-6 を承認レビューで記録することも既に認めています。改訂案の「属性を機械、判断を人」は、現行の語彙(記録した者 / 承認した者、`recording.md:24` の草案と確定の分担)で既に表現でき、4.1 B の形なら承認イベントを判定者の記名の裏づけに使えます。

折れた点は 3 つです。帳票の氏名欄は Who / When の証拠にならない。記録 PR に第三者の承認を重ねる現行テンプレートは、標準が認めている「記録だけのコミット」の扱いと揃っておらず、価値の低い承認を増やしている。決定1 に根拠水準マークが無い。いずれも決定1 を変えずに直せます。

折れない点は 1 つです。**承認イベントを成立要件に置かない**。承認イベントは「確認した項目」「確認していない事項」「差し戻しの項目番号と期限」を持たず、ホスティングの状態であり、認証情報を共有する体制では氏名欄と同じ弱さに落ちます。決められた場所で人間が触ったことを示すのは、承認ボタンではなく、人が自分の言葉で書いた記録です。
