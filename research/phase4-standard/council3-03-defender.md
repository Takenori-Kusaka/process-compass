## 第1部: 弁護できるもの

### 争点1: 独立した判定工程を新設する(#27 案 B)

**弁護の骨子**

標準は、この事象を**目視の判定ではなく実行時の遮断で扱うと、すでに決めています**。

`phase5-implementation/agent-trace-control.md` は、附属書E E.6 の5事象を「目視の対象から外し、遮断と機械判定へ振り分ける」設計を規定します(L12)。5事象のうち3つが事前遮断へ振り分けられ、その1つが**「想定していない外部への通信を行った」**です(L20)。振り分けの理由は同ページ L30 に書かれています。

> 3つの事象は、いずれも**起きてから見つけるより、起こさないほうが確実です**。

同ページ L10 は、目視での確認がなぜ成立しないかを明示しています。

> 1回のタスクで数十から数百の操作が実行される環境では、痕跡を遡って探す作業は時間の制約のもとで確認済みの印を付ける操作へ縮退します。これは第5章 5.6 が防止すべきとする形骸化そのものです。

案 B は、**遮断で扱うと決めた事象を、人間の判定工程へ戻す提案**です。標準が自ら「縮退する」と書いた形式へ戻します。

**変更を採ると何を失うか**

第一に、**第5章 5.5 の4種類の共通の理由が壊れます**。同節 L180 は、4種類が人間に留まる理由を「**結果責任(A)を負う者による判断でなければ責任の所在を失う**」ためと定めています。「この資料をどこへ置いてよいか」は、結果責任の所在の問題ではなく**設定の問題**です。5つ目として並べると、4種類を貫いている理由が消えます。

第二に、**判定者を2名新設します**。#27 は「Audit(可否)+ PO(範囲)」を挙げますが、ADR-0038 決定2 は逆の方向を採りました。

> 検知者は事実確認までに留め、許容可否を判断しない

ADR-0038 が置いたのは**判定ではなく引き渡し先の指定**です。同 ADR 決定4 は「引き渡し先が分からないことを、自分で決める理由にしない」と書き、経路の指定で扱いました。#27 が指摘する「どちらが判定するかが未定であるため、誰も判定しない」は、ADR-0038 が扱った問題と同型であり、**同じ解法(引き渡し先の指定)で処理できる可能性が検討されていません**。

第三に、ADR-0013 / ADR-0019 の「判定・会議体・様式を増やさない」方針を、初めて明示的に破ります。

**提案側が答えていない問い**

- 案 B の判定工程は、案 D(遮断)を実装した後に、**なお残る事象を何件見込むのか**。遮断が既定拒否である以上、判定の対象は「許可先の追加要求」だけになる。それは既存の `state:needs-platform` の対象である
- 判定工程を置いた場合、**判定を経ずに発行された事象を、何が検出するのか**。検出手段が無ければ、工程の存在は遵守を意味しない(ADR-0052 決定1 と同じ論点)

### 争点2: 標準が「組織外」「機密区分」を定義すること

**弁護の骨子**

**標準はこの欄をすでに持っており、値を書くのは案件だと決めています。**

`deliverable-templates.md` テンプレ8(AI-SLA 合意確認書)の「6. 権利と責任」に、次の欄があります(L621)。

| 項目 | 記載 |
| --- | --- |
| 秘密情報を外部サービスへ送出することの可否 | |

**空欄です。標準は可否の基準を定めず、案件が記入する欄として置きました。** 同じ表には「生成物の権利帰属」「第三者の権利侵害が生じた場合の対応」が並び、いずれも契約側の合意事項として扱われています。

これは ADR-0041 決定5(範囲の妥当性を判定する検査を置かない)、ADR-0051 決定2(受入基準の内容そのものは判定しない。対応の有無だけを見る)と同じ設計です。**標準は欄の存在を要求し、値の妥当性を判定しません。**

第3章 3.4.1 は「外部との契約に関わる決定」を AI へ委譲できない領域としており、この欄が契約書の添付に置かれていることと整合します。

**変更を採ると何を失うか**

標準が独自の機密区分を持つと、**組織の情報管理規程と二重になります**。二重になった場合、どちらが優先するかを標準が決めなければならず、それは標準が組織の統制体系の上位に立つことを意味します。ADR-0051 決定1 が「扱うと標準が製品の良し悪しを判定することになる」として避けた構図と同じです。

**提案側が答えていない問い**

- #27 は「判定者が決まっていない」と書くが、**テンプレ8 のこの欄が案件で空だったのか、テンプレ8 自体を作らなかったのか**が書かれていない。前者なら欄の不備、後者なら適用の欠落であり、対処が異なる
- 委託ではない自社開発の案件で、この欄に相当するものをどこへ置くかは確かに未定である。しかしそれは**欄の置き場所の問題**であり、判定工程の新設とは別である

### 争点3: 成果物の種別ごとの配布先表を標準側へ持つこと(#27 案 C)

**弁護の骨子**

ADR-0041 決定1 は「列挙は網羅でないことを、列挙のある箇所で明記する」と定めました。配布先の分類表は、まさに列挙です。

標準は同種の表について、すでに強い留保を置いています。`deliverable-templates.md` L817 は危険源カテゴリの一覧に対し次を書きます。

> **同分類を網羅とみなしてはなりません**。**攻撃面で構成されているため、攻撃者を想定しない失敗様式が原理的に含まれません**。

案 C は「表から外れる場合だけ判定する」設計であり、**表が網羅であるという前提でのみ成立します**。網羅でない表に対してこの設計を採ると、**表に載っていない成果物が無判定で通る経路が正式化されます**。これは表が無い現状より悪い状態です。

**変更を採ると何を失うか**

表の保守を標準が負います。ADR-0044 決定4 は「判断記録(ADR)の様式は変更しない」、決定2 は「探索の結果を記録させない」と定め、記録と保守の増加そのものを回避しました。同 ADR 「粒度の先例が存在しない」の節が示すとおり、**表の粒度を決める先例が本標準にも外部規格にもありません**。

**提案側が答えていない問い**

- 表の行は「決裁資料」「レビュー資料」といった**成果物の種別**で立てるのか、「公開ホスト」「組織管理ホスト」といった**配布先の種別**で立てるのか。#27 は前者を書くが、危険の源は後者にある
- 表から外れた場合の判定者は Audit とされるが、**表に載っているが値が誤っている場合**を誰が見るのか

### 争点4: 根拠が n=1 であること

**弁護の骨子**

`community/evidence-ledger.md` の「根拠とした事例」欄を検査した結果、**EV-0033 / EV-0034 / EV-0036 / EV-0037 のすべてが案件 P-001 です**。EV-0019 も P-001 の決裁1件です。ADR-0035 / 0036 / 0039 / 0050 / 0051 / 0052 は、いずれも同一案件から出ています。今回で系列が続きます。

## 第2部: 弁護できないもの

### 争点A: 秘匿情報の統制が、リポジトリの外で完結する発行を対象にしていない

**弁護を試みた形**

「標準は出る方向も見ている」と主張しようとしました。根拠候補は2つです。

- `roles-responsibilities.md` 3.12.8 要求事項2「**機密情報の送出を検査する仕組みを、接続経路の上に置く**」(L905)
- G-5 基準7 秘匿情報の混入検査。台帳への記録による通過を認めない強い規定(`gate-criteria.md` L233 / L254)

**なぜ成立しないか**

**どちらも、本件の経路を対象にしていません。**

3.12.8 の「接続経路」は、3.12 全体の主題である**モデル基盤への接続経路**です。同節の前後がそれを示します。3.12.5 は「代替の接続先へ切り替える手順」、3.12.7 は「接続経路の上でチーム単位の上限を設定し」、3.12.10 は「接続経路またはエージェント実行基盤の上で強制する」と書きます。**検査の対象はモデルへ送る入力であり、生成した成果物の発行先ではありません。**

G-5 基準7 の対象は、`gate-criteria.md` L254 が明示しています。

> **リポジトリ全体が常に対象である**。実装がなくても対象は存在する

**リポジトリの外で完結する発行は、どちらの対象にもなりません。** これは方向の非対称ではなく、**対象の空白**です。私が弁護を試みた「方向」という枠組み自体が誤りでした。

**ただし、変更の範囲をここまでに限るべき**

- 新しい判定工程ではなく、**既存の対象定義の空白を埋めること**に限る
- G-5 基準7 の文言「リポジトリ全体」を書き換える必要はない。当該基準は**リポジトリへの混入**という別の危険を扱っており、統合すると両方が曖昧になる
- 埋めるべきは**発行そのものの遮断**であり、争点B の範囲と一致する。二重に規定を置かない

### 争点B: 発行手段が強制層から外れており、標準自身の規定に反している

**弁護を試みた形**

「禁止事項はすでにある」と主張しようとしました。`template/CLAUDE.md` の禁止事項9 が、まさにこの事象を名指ししています。

> 9 | **事前承認のない外部パブリックホスト(個人用 Claude Artifacts や公開 Pastebin 等)へ決裁資料やログを配置(発行)する** | 組織の管理外に機密情報や意思決定証跡が流出し、ガバナンスとセキュリティが破綻(インシデント化)するため

**なぜ成立しないか**

**理由は2つあり、いずれも決定的です。**

**第一に、この条項は事象の後に追加されたものです。** git 履歴を検査しました。

```
2182777  2026-08-14 14:35:23 +0900
fix: Issue #32 の完全解決:CLAUDE.md における Filetto 混入の除去、
     外部ホスト公開禁止の追加、pristine 検証の強化
```

`git log -S "外部パブリックホスト" -- CLAUDE.md` の結果はこの1件のみです。**事象の時点には存在しませんでした。** 事後の追記を、事前の統制として弁護できません。

**第二に、追加先は誘導層です。** 同じ `template/CLAUDE.md` は、禁止事項の表の直後に自ら次を書いています。

> 禁止事項3は `.claude/settings.json` の書き込み範囲でも遮断しています。**指示への遵守だけに依存しません**。

**禁止事項9 には、対応する強制層がありません。** `template/.claude/settings.json` を実測した結果、`permissions.deny` の27項目に外部発行を止めるものは無く、`ask` に入っているのは `curl` / `wget` / `git push` / `gh pr create` / `npm publish` のみでした。**artifact 発行系の手段は、いずれの層にも掛かっていません。**

標準は、この状態を自ら失格としています。

- `roles-responsibilities.md` 3.11.3(L731)— 「**指示ファイルへ書いた内容が必ず守られるという前提で統制を設計してはなりません。強制が必要な規則は強制層へ降ろします**」
- `agent-trace-control.md` L52 — 「**強制層に置けない項目は、遮断できたものとして扱いません**」

**標準自身の定義により、禁止事項9 は現在「遮断できていないもの」として扱わなければなりません。** 弁護できません。

**ただし、変更の範囲をここまでに限るべき**

**#26 案 D と #27 案 D は、標準への新規定を要しません。既存規定の実装です。**

要求は2箇所にすでにあります。

- `agent-trace-control.md` L36 — ネットワークの既定は**拒否**。「依存関係の取得先など、必要な宛先のみ許可する」。**適用条件は付いていない**

したがって範囲は次に限るべきです。

- 標準本文への追記は**行わない**。要求はすでにある
- 判定工程・判定者・様式を**増やさない**
- 許可先の追加は既存の `state:needs-platform` の対象とし、新しい経路を作らない

ADR-0052 が「配る仕組みはあるが、配っていない」を4件目として記録した**その当日**に、5件目が同じ形で現れています。会議体はこれを新規の空白としてではなく、**同じ形の再発として**扱うべきです。

### 争点C: 同じ要求が、片方は無条件、片方は条件付きで置かれている

**弁護を試みた形**

- 判定を増やさない。整合の明示は本文の1行で足りる

## 第3部: 会議体への警告

### 1. 「標準に無い」という主張の検査結果

**不正確です。** 該当する規定を6件、実物から確認しました。

| # | 出所 | 内容 | 適用条件 |
| --- | --- | --- | --- |
| 1 | `agent-trace-control.md` L20 | E.6「想定していない外部への通信を行った」を**事前に遮断する**へ振り分け | **無条件** |
| 2 | `agent-trace-control.md` L36 | ネットワークの既定は**拒否**。必要な宛先のみ許可 | **無条件** |
| 3 | `developer-guide.md` L107 / L115 | E.6 の表。「差し戻し、影響を確認する」。「起きてから探すのではなく、**実行時に拒否します**」 | **無条件** |
| 4 | `deliverable-templates.md` L805 / L866 | D-8 段階1で**空間上の限界(到達できるネットワーク)**を宣言。RRS1 に「外部通信の既定拒否と、許可先の明示的な列挙」 | 4条件のいずれか |
| 5 | `deliverable-templates.md` L621 | テンプレ8 に「秘密情報を外部サービスへ送出することの可否」欄 | 委託契約時 |
| 6 | `template/CLAUDE.md` 禁止事項9 | 外部パブリックホストへの決裁資料・ログの発行を禁止 | **事象の後に追加**。誘導層のみ |

**結論**: 標準は当該事象を**無条件の規定として持ち、降ろし先(強制層)まで指定しています。テンプレートの強制層に実装がありません。**

**前回の会議体が出した判定(9件中6件が「標準に無い」ではなく「届いていない/読んでいない」)と同じ形です。** 本件は7件目に当たります。

### 2. 議題の立て方の偏り

**(a) 案 D は標準の変更を要さないのに、標準の変更として議題化されている。**

#26 と #27 は同じ事象から起票され、**両方が案 D(遮断)を最終案に挙げています**。しかし議題は「共有範囲を判定する工程を標準へ追加するか」の形で立てられています。**案 D は既存規定の実装であり、標準の審議事項ではありません。** 工程追加の可否を先に議論すると、設定1件で済む部分が判定の新設と抱き合わせで決まります。

**審議の順序を入れ替えるべきです。** 先に案 D を実装対象として切り離し、**遮断を掛けた後になお残る事象**について案 A / B / C を審議してください。切り離さない場合、遮断が実装されないまま判定工程だけが増える結末になりえます。

**(b) 提案側が自ら挙げた未確認事項が、検査されないまま前提になっている。**

#27 の「確認できていないこと」は次を書いています。

> 標準本文(process-compass)側に、本文書が把握していない配布先の条項が存在するかは未確認である。存在する場合は、テンプレートへ届いていないことが問題になる(ADR-0014 と同じ形)。

**この未確認事項は、検査の結果、事実でした。** 提案側は正しい可能性を自分で書いており、その分岐を検査せずに「工程が無い」を表題にしています。**#27 の表題は、本文の記述と矛盾しています。**

**(c) 事象の後に禁止事項9 が追加された事実が、議題へ反映されていない。**

会議体は「規定が無い状態」を審議する形で招集されていますが、実際に審議するのは「**誘導層にはあり、強制層に無い状態**」です。この差は、案 A / B(判定の追加)と案 D(遮断)のどちらを採るかを直接決めます。**規定が無いなら規定を書く必要がありますが、誘導層にあるなら降ろすだけで済みます。**

なお、禁止事項9 の追加自体が ADR-0038 決定4 と同型の望ましい振る舞い(引き渡し先が分からなくても抱え込まない)であった点は、記録に値します。**問題はその後の降ろしが止まっていることです。**

**(d) n=1 を却下の理由に使わないこと。**

私は第1部 争点4 で n=1 を確認しましたが、**却下の根拠としては使いません**。ADR-0045 決定1 が求めるのは母数ではなく、**対立仮説を分離できる差し替え条件**です。本件は書けます。

- 遮断を設定した後、**外部ホストへの発行が試行された件数**と、そのうち**拒否された件数**
- 拒否のうち、**許可先の追加要求へ転じた件数**

さらに ADR-0045 決定3 は「既存の観測機構の出力を優先して使う」と定めます。**本件には既存の出力があります。** `template/.claude/guard.json` の `denyLog`(`.claude/denied.log`)と、`agent-trace-control.md` L39「拒否された操作は**記録へ残す**」です。**新しい台帳を作らずに数えられます。**

**したがって n=1 は、この提案に対して却下の弾になりません。** 私はこの弾を撤回します。

**(e) 前回の一次情報(回避率)を、遮断へそのまま当てないこと。**

BCMA の66%回避、16欄→7欄で報告7.7倍、FCA の却下ゼロ CAB は、いずれも**人間に作業を課す装置(様式・報告工程・承認会議)を増やしたときの回避率**です。案 D は装置ではなく**既定値の変更**であり、回避には設定の編集を要します。そして `template/.claude/settings.json` は自身の編集を `deny` しています(`Edit(./.claude/settings.json)` / `Edit(./.claude/guard.json)`)。**回避の経路が構造的に異なります。**

**この弾は案 A / B / C(判定・様式の追加)に対しては有効で、案 D に対しては無効です。** 私の側の材料を、私が誤用しないよう明記します。

**(f) 「標準を読まなくても分かる」という帰属論は成立しません。**

事前に私へ渡された論点のうち、「組織外の公開ホストへ決裁資料を出す危うさは標準を読まなくても分かる」という反論は、**使えません**。**標準を読めば書いてありました**(上表の1〜3)。ADR-0051 が「見て気づけるか」を問う工程について「標準の落ち度ではない」と判定できたのは、**標準が本当にそれを扱っていなかったから**です。本件は条件が違います。

帰属の形は次へ変わります。**標準の落ち度ではなく、標準の実装層への降ろしの落ち度です。** これは ADR-0014 が扱った形であり、ADR-0052 が4件連続として数えた形です。
