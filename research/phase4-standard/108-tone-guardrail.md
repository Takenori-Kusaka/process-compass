# 調査メモ: 内部文脈用語の排除と再発防止のガードレール（Issue #108）

- 調査日: 2026-08-05
- 対象 Issue: #108 「『音声メモ』などの内部・非公式用語を完全排除し、エンタープライズなトーンへ統一する」
- 目的: 現行ドキュメントの内部文脈用語を洗い出し、再発を機械的に防ぐ仕組みを設計する

---

## 1. 現状調査（2026-08-05 時点の全走査結果）

`src/content/docs/` 配下の全 Markdown / MDX を、内部文脈語・口語表現・一人称表現の観点で走査した。

### 1.1 明確な違反

| ファイル | 内容 |
| --- | --- |
| `phase3-gap-analysis/insourcing-bcp.md` | 「音声メモの言葉を借りれば」— 読者が参照できない内部資料への言及 |

Issue 本文が挙げていた `phase2-aidlc/po-centric-team.md` の「元ネタ」表現は、2026-08-05 時点で既に存在しない。

### 1.2 違反ではないと判定したもの

| 該当 | 判定理由 |
| --- | --- |
| `gate-criteria.md` / `review-guide.md` の「なんとなく不安」 | 禁止すべき差し戻し理由の**引用例**であり、記述者の口語ではない |
| `vision/01-goal.md` の「私たち」 | ビジョンページはプロジェクトの意思表明であり、規程本文ではない。一人称の使用が妥当 |
| `community/style-guide-diagrams.md` の「執筆者(人・AI)」 | 運営ドキュメントの記述として妥当 |
| 各所の「オーナー」 | コンテキストオーナー・コードオーナー等の役割名であり、内部文脈語ではない |

結論として、内部文脈語の残存は1件のみであった。したがって本 Issue の主眼は**一括置換ではなく、再発防止のガードレール構築**にある。

## 2. ガードレールの設計

### 2.1 実務プラクティスの調査

- ドキュメントの文体・用語を機械的に検査する手法は定着しており、Vale、textlint、write-good 等が用いられる。
- Vale は `words.yml` に回避すべき語彙を列挙し、検出時に警告を出す構成を提供する。用語集（vocabulary）をスタイル定義から分離して管理できる点が特徴である。
- Datadog は Vale を導入し、レビュー前に CI が文体規約への違反を指摘する運用を採っている。
- 一般に、リンターを CI/CD に組み込むことで、文体違反が公開へ到達する前に阻止できるとされる。

出典:
- https://vale.sh/
- https://www.datadoghq.com/blog/engineering/how-we-use-vale-to-improve-our-documentation-editing-process/
- https://buildwithfern.com/post/docs-linting-guide
- https://www.netlify.com/blog/a-key-to-high-quality-documentation-docs-linting-in-ci-cd/

### 2.2 本プロジェクトでの採用方針

Vale の導入は見送る。理由は次のとおりである。

- 本プロジェクトは既に textlint（`preset-ja-technical-writing`）を CI と保存時フックの双方に組み込んでおり、検査経路が二重になる
- Vale は日本語の形態素解析を前提としないため、日本語の語検出は正規表現ベースになる。それであれば既存の Node スクリプト方式（`scripts/*.mjs`）で十分である
- 依存パッケージを増やさない

採用する構成:

- `scripts/check-tone.mjs` を新規作成し、禁止語リストと正規表現で `src/content/docs/**` を走査する
- `npm run check` に組み込み、CI（`ci.yml`）と push 前検査の双方で発火させる
- 検出時は該当ファイル・行番号・理由・推奨する言い換えを表示して終了コード1で失敗させる
- コードブロック内および HTML コメント内は検査対象から除外する（テンプレートの記入例に禁止語が現れるため）
- 引用として正当な使用のために、行末に `<!-- tone-ok: 理由 -->` を置くと当該行を除外する

### 2.3 禁止する語の分類

| 分類 | 例 | 理由 |
| --- | --- | --- |
| 内部資料への言及 | 音声メモ、元ネタ、議事録によれば、オーナー様 | 読者が参照できない資料に依存する記述 |
| 主観的な強調 | めっちゃ、すごく、ヤバい、ぶっちゃけ | 規程の客観性を損なう |
| 断定を避ける口語 | 〜な感じ、〜だと思います、たぶん | 要求事項の効力が不明確になる |
| 検討の痕跡 | TODO、後で書く、あとで直す、仮置き | 未完成の記述が公開される |

## 3. 追加した執筆規約

第1章 1.7（記述の原則）に既に「特定の製品名・組織内の口頭文脈に依存する表現は用いない」を規定済みである（#97）。本 Issue では、これを機械検査で担保する。

あわせて、執筆者向けの規約ページ（`community/`）に禁止語の一覧と除外方法を記載し、検査に落ちたときの対処を参照できるようにする。

## 4. 未解決事項

- 禁止語リストは運用しながら育てる。誤検出が続く語は除外するか、`tone-ok` の注記で個別に許可する。
- 英語ロケールを追加した場合は、英語向けの禁止語リストを別途定義する必要がある。
