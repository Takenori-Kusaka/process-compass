# 調査メモ: 例外(ファストトラック)規程と乱用防止（Issue #101）

- 調査日: 2026-08-05
- 対象 Issue: #101 「厳格な期日ターゲットに適合するための例外(ファストトラック)規程の策定」
- 目的: 動かせない期日に対処する例外手続と、その乱用を防ぐ制約を定める

---

## 1. 調査結果: 緊急変更(Emergency Change)の運用

IT サービス管理の実務では、通常の変更手続を短縮する「緊急変更」が制度として存在する。本 Issue が求めるファストトラックと同じ構造であり、運用上の知見が蓄積されている。

### 1.1 適用条件

緊急変更は、**重大な問題への即時対応が必要な場合に限って**用いられる。具体例は、サービス停止、セキュリティ侵害、顧客または業務に影響する障害である。

### 1.2 承認と事後レビュー

- 承認は緊急変更諮問委員会(ECAB)が行う。
- **展開後に必ず全面的なレビューを実施**し、統制を確保して再発を防ぐ。
- 未テストの変更は長期的にさらに大きな損害を生む可能性があるため、実施後に再評価して是正する運用が一般的である。

### 1.3 一般的な失敗パターン

調査で挙げられている典型的な失敗は次の3点である。

1. **「緊急」区分の過剰使用**
2. 文書化の不足
3. 変更後レビューの省略

さらに、ECAB が緊急変更に対する**「形式的な承認(rubber stamp)」となり、変更管理者の責任回避の手段と化す**事例、および ECAB 自体が価値の流れのボトルネックになる事例が報告されている。

### 1.4 監視すべき指標

乱用の検知には次の指標が用いられる。

- 緊急変更の発生率
- 承認までの所要時間
- ECAB が承認した変更の成功・失敗比率

## 2. 設計判断

### 2.1 ファストトラックの適用条件を「期日の性質」で限定する

「急いでいる」は適用条件にならない。適用できるのは、**遅延した場合に組織の外部で不可逆な損失が生じる期日**に限る。

| 適用できる期日 | 適用できない期日 |
| --- | --- |
| 顧客との納品契約 | 社内の目標日 |
| 展示会・発表会などの公開日 | 期初に置いた見込み |
| 規制対応の法定期限 | 上位者の期待 |
| サービス終了(EOL)に伴う移行期限 | チームの意欲的な目標 |

この区別を書かないと、すべての期日が「動かせない期日」として申告される。

### 2.2 何を後回しにできるか・できないかを明示する

短縮できる対象を限定列挙する。列挙にないものは短縮できない。

| ゲート | 後回しの可否 |
| --- | --- |
| G-6 独立レビュー | 可(実施期限を定めた後追い) |
| G-3 技術設計判断の記録(ADR) | 可(記録のみ後追い。判断自体は実施する) |
| G-7 出荷判定の一部項目 | 可(項目を特定した限定的な短縮) |
| G-4 機能仕様承認 | **不可** |
| G-5 自動検証(CI) | **不可** |
| 認証・認可・データ保全に関する検証 | **不可** |

G-4 と G-5 を不可とする理由は、この2つを外すと「何を作ったか」と「動作するか」の双方が不明な状態で出荷することになるためである。この状態はリスクの引き受けではなく、リスクの把握放棄である。

### 2.3 乱用防止の制約（Issue の問いへの回答）

1.3 の失敗パターンに直接対応する制約を置く。Issue が例示した「2期連続適用不可」のような単純な回数制限だけでは、期末ごとの常態化を防げないため、**発生率・回収の完了・承認者の負荷の3方向から制約する**。

| # | 制約 | 対応する失敗パターン |
| --- | --- | --- |
| 1 | 未回収のファストトラック項目が残っている間、同一案件で新たなファストトラックを申請できない | 過剰使用 |
| 2 | 事業ステージあたりの適用回数の上限を、企画承認(G-1)の時点で合意して記録する | 過剰使用 |
| 3 | 適用後、定めた期限内に事後レビューを実施する。未実施の場合、当該案件のファストトラック権限を停止する | 変更後レビューの省略 |
| 4 | 承認者は記名し、承認理由を記録する。理由の記載がない承認は無効とする | 形式的な承認 |
| 5 | 発生率・回収完了率・適用後の欠陥発生率を継続的に測定し、会議体へ報告する | 全般 |

制約1が最も強い抑止になる。回収を伴わない限り次が使えないため、「とりあえず通す」運用が成立しない。

### 2.4 リスクの定量提示

Issue は「AI が未テストコードのリスク・未解決バグの影響を定量化し、決裁者へシミュレーションを提示する」ことを求めている。本標準では、AI が生成する申請書に次の項目を必須とする。

- 短縮するゲートと、それによって検証されないまま残る範囲(ファイル・機能・受入基準の単位)
- 未解決欠陥の一覧と重大度
- 影響を受ける利用者の範囲
- 回収に要する見積工数

「シミュレーション」の精度は現時点で保証できないため、標準が要求するのは**未検証範囲の特定**である。確率的な予測ではなく、事実として何が検証されていないかを示す。

### 2.5 第7章の既存規定との統合

第7章 7.3 は既に例外承認の5要求事項を規定している。ファストトラックはその特殊形として位置づけ、追加の制約(2.1〜2.4)を重ねる構成にする。用語と承認手続を二重に定義しない。
