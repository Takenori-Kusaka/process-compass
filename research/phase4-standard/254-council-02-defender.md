# 254 会議体 弁護役の意見 — 標準に足すものは無い

作成日: 2026-08-14 / 役: 弁護役(現状維持の論証)
対象: Filetto(P-001)PO による Dev-A / Dev-B 分割案と、標準上の位置づけの3質問

本書の目的は、標準を守ることではありません。**誤った結論を通さないこと**です。潰せなかったものは第3節に正直に書きます。

## 1. 各仮説の成否

### 仮説A — 実例2件は分割がなくても起きた: **成立**

PO が挙げた2件は、いずれも **Dev-A / Dev-B の分割を導入する前の、現行の単一 Dev レーンで発生しています**。分割後の観測ではありません。したがって「分割したから捕まった」という因果は、提示された証拠からは導けません。

さらに、2件はいずれも**標準が既に持っている手続の作動**として説明が付きます。

| 実例 | 既存の条項 |
| --- | --- |
| 受入基準30件を数え、該当0件を発見した | 附属書E E.5 順1(受入基準ごとに対応が存在するかを数え上げる)。同節は「確認の範囲が有界である」ことを設計理由に挙げ、**基準そのものの欠落はテストでは検出できない**ため人が数えると明記する |
| 抽出経路5つを実際に動かし、.docx にページ位置が無いことを実測した | 5.8.1(AI の出力は未検証の入力であり、決定論的な検証を経て初めて成果物になる) |

調査メモ `254-adversarial-role-evidence.md` の第7節も、この2件を「視点の分離」ではなく**外部観測の取得**に分類しています(実例1は仕様の列挙による突合、実例2は実行接地)。同メモの第6節の仕分け表では、**視点だけを分けた構成の効果量は CCR の F1 +4.0pt にとどまり、外部観測を取りに行かせる構成は +19〜44pt** です。**2件が示したのは後者の効果であって、前者ではありません**。

補足として、**視点の分離は無害ですらありません**。同質パネルでの有害改訂率89%(arXiv:2606.19826)は、同一モデル同士の突き合わせで**正しかった側が壊れる方が多数派**だったことを示します。分割は無料の追加ではありません。

### 仮説B — 2件は PO の成果物の誤りであり、Dev レーン分割の根拠ではない: **成立**

2件の構造を並べます。

| | 誤りを作った側 | 誤りを見つけた側 |
| --- | --- | --- |
| 実例1 | PO(受入基準) | Dev(実装計画の作成時) |
| 実例2 | PO(未実測の前提) | Dev(実装時の実測) |

**Dev が Dev 自身の成果物を否定した例は1件もありません**。2件が実証しているのは、**工程間の引き渡しにおける作成者と検査者の分離**が働いたことです。これは既に標準が持っています。

- 5.2「AI が生成した成果物は、その生成を指示した者以外の人間が確認する」
- 3.5 兼務禁止表「作成指示者 × 独立レビュア(同一成果物)= 禁止」

Dev-A / Dev-B は **Dev レーンの内側の分割**であり、PO → Dev の引き渡しとは別の軸です。**実例が支持する構造と、提案されている構造が一致していません**。

したがってこの2件は、PO 自身が第2段階として構想している「PO が成果物を作らない体制へ移す」ことの根拠にはなりますが、**Dev レーンを2つに割ることの根拠にはなりません**。

### 仮説C — 標準は既にこの活動を持っている: **一部成立、一部不成立**

**不成立の部分**: 5.8.4 の段階「中」を根拠に挙げることはできません。5.8.4 の射程は**テスト生成における独立性**です。表の4段階はすべて「テストを実装より先に生成し、テスト生成に実装コードを渡さない」という、テストと実装の関係に限定して書かれています。PO が Dev-B に担わせようとしているのは、**仕様・帳票・スライド・実装計画といった非テスト成果物の前提**であり、5.8.4 の文言はここに掛かりません。「5.8.4 が既に同じことを言っている」という主張は**成り立ちません**。

**成立の部分**: それでも「新しい置き場は要らない」という結論は維持できます。既存の条項で足ります。

| 活動 | 既存の条項 |
| --- | --- |
| 上流成果物の欠落を数え上げて突き返す | E.5 順1〜4(有界な確認。順5だけが範囲不定) |
| 未検証の前提を検証してから成果物とする | 5.8.1 |
| 別セッション・別文脈で検証を回す | 5.8.4 段階「弱」(R3)。段階「中」(R2)はこれを含む |
| 生成主体と検査主体の文脈を分ける | 3.5.3(作業領域・セッション・認証情報の3点) |
| 稀な欠陥を意図的に出現させ、検出能力を測る | 5.6.2 欠陥注入 |

**Dev-B が行うと説明されている作業は、すべて既存の条項の下で実行できます**。PO が実際にやったこと(数える、動かす)は、E.5 と 5.8.1 が既に求めていることです。**やっていることに名前を付け直す必要はありません**。

### 仮説D — 質問2は既に明文で規定済み: **成立**

質問2「Dev-B の出力はどのゲートでも判定に使えないという理解でよいか」の答えは、第4章「帯域を理由に判定を省略しない」節に明文であります。

> **AI による事前審査を合否条件として挿入する手段は採りません**。(中略)AI の指摘は(中略)**注意を向ける材料として提示し、合否には用いません**。

5.7.4 要求事項2(自動的な判定は、人間への提示に限って用いる)も同じ結論です。**理解のとおりであり、新しい条項は不要です**。ただし「質問として成立していない」とまでは言えません。**PO が確認を求めること自体は正当**であり、答えは「既に書いてある」です。

質問3(「監査の入力」以外の扱いがありえるか)にも既に答えがあります。**「注意を向ける材料」は監査の入力より強い扱いです**。実例2件はどちらも**差し戻し**に至っています。差し戻しは合否判定ではなく、前工程への返却です。ゲートの合否を左右せずに実行できます。**PO が想定している「監査の入力」より、標準は既に一段強い経路を与えています**。

### 仮説E — Dev-B を新ロールとして立てることは有害: **成立(ただし条件付き)**

Dev-B を**ロール**として立てると、次がすべて連鎖します。

| 波及先 | 追加されるもの |
| --- | --- |
| 3.5 兼務禁止表 | Dev-A × Dev-B の可否の行 |
| 3.5.1 ロールとレーンの写像 | 8行目のロールと既定レーン |
| 3.5.3 文脈の分離 | 作業領域・セッション・認証情報の3点を Dev-B 分だけ追加 |
| Label Mailbox 4.3 | `state:*` 語彙の10種目 |
| Label Mailbox 4.3.1 | 復路(Dev-B → Dev-A、Dev-B → PO)の遷移定義 |
| D-0 体制図 | 兼務の記録の追加 |

Label Mailbox 4.2 原則5 は「**語彙を必要最小限に抑える**」「伝達する経路が明確である限りラベルを増やさない」と定めています。Dev-A → Dev-B の伝達経路は**既に `state:needs-dev` で足りて**おり、原則5 に照らして語彙の追加は認められません。

#249 は、Filetto の1名が既に**7ロールを兼務**し、それが 5.6 の形骸化へ直行すると指摘しています。**8つ目を足す提案は、この指摘を悪化させます**。「AI が担うから人の負荷は増えない」という反論は成り立ちません。**兼務の判定単位は人だけではなく、実行主体の文脈も含む**(3.5.3)ためです。ロールが増えれば、文脈の管理対象も増えます。

**条件付きである理由**: 上の批判は「**ロールとして立てる**場合」に限って成立します。ロールを増やさず、Dev レーンの内側でセッションだけを分ける構成であれば、3.5.3 と 5.8.4 段階「弱」の範囲内であり、ラベルも増えません。**この形は潰せませんでした**(第3節 穴3)。

## 2. 起案側が言い出しそうな案を、先回りして潰す

### 「ISO/IEC/IEEE 29119-1 Annex E.3 の a) が規格上の位置づけである」

**採れません**。E.3 の a) は "the lowest level of independence (i.e. **no independence**)" として置かれた**目盛りの原点の記述**であり、a) に固有の手続・要求は**一切ありません**。さらに 29119-1 は Clause 2 で informative と明記され、規範ではありません。

加えて、同 E.3 は非対称を明記しています。**動的コンポーネントテストでは a) が黙認される一方、開発者が行う静的テスト(ピアレビュー)で同じ独立性ゼロを適用することは「通常、受け入れられるとは考えられていない」**。Dev-B が行うのは仕様・帳票・前提の検討であり、**動的テストではなくレビュー側**です。**規格は、この用途にこそ a) を認めていません**。

IEC 61508-1(最下位が independent person)、ISO 26262-2 Table 1(最下位の I0 ですら別人)、DO-178C 6.2.e(開発者以外)は、いずれも**目盛りの下端を「別人」に置いています**。同一モデルの Dev-A / Dev-B は、この目盛りに**載りません**。位置づけを与えることは、載っていないものを載せる操作です。

### 「CCR に有意差がある(F1 +4.0pt、d=0.52)」

**新条項の根拠になりません**。理由は2つあります。

- 絶対水準が F1 28.6% であり、**注入した欠陥の71%を見逃す**。検出手段の主柱にできない
- 効果の由来は**文脈の分離**であって役割の分離ではない(同論文は SR2 対照で反復要因を除去している)。**文脈の分離は 5.8.4 段階「弱」が既に規定済み**であり、Filetto が R2 なら段階「中」がこれを含む

**既にある規定の効果を、新しい枠組みの根拠として二重計上しています**。

### 「役割を名乗らせれば挙動が安定する」

**逆です**。persona の付与は MMLU で -3.6〜-5.3pt の悪化が報告されています(Wharton, 2026-03)。EMNLP 2024 Findings も、2,410問・4系統で**役割付与が無付与を上回らない**と報告しています。**名乗りには精度上の効果がありません**。効果があるとすれば、名乗りではなく課される作業内容です。

### 「Dev-A と Dev-B が一致したなら、その結論は信頼できる」

**標準の条項として書けません**。9判定者のパネルの実効独立票数は 2.18(名目の24.2%)であり、パネルの利得は最良単体に対して 0.2pt でした(arXiv:2605.29800)。誤りの相関は系統ではなく**項目の難しさ**に集中します。ベンダーを変えても解けない相関を、**同一モデル内の役割分離で解けるはずがありません**。

### 「G-6 の未達を、少しでも埋めることになる」

PO 自身が否定していますが、**議論の途中で必ず再浮上するため、ここで塞ぎます**。3.5.2 の比較表は、作成指示者 × 独立レビュアの1人での達成を「**不可能**(見る人が同一である以上、目的が成立しない)」と明記し、扱いを「**未達として表示し続ける**」と定めています(ADR-0028)。

**Dev-B を置くことの最大の危険は、未達の表示が「対策済み」に見えることです**。標準は「書かれていない」と「課さないと決めた」を読み手が区別できる状態を要求しています。同じ理由で、**未達と緩和も区別できなければなりません**。

### 「Dev-B の出力を、判定の参考情報として記録に残す」

**残すこと自体は禁じられていません**。ただし 5.7.2 の決断の記録の4欄(確認した事項/確認していない事項/判断が変わる条件/受容したリスク)に**新しい欄を足す必要はありません**。Dev-B の実測結果は「確認した事項」に、実測できなかった範囲は「確認していない事項」に、既存の欄で記載できます。**様式を増やさないでください**。

## 3. それでも残る穴(弁護役の立場からも否定できなかったもの)

### 穴1 — 受入基準に書かれた前提の根拠水準を、標準が問うていない

実例2件が共通して捕まえたのは、**PO が書いた前提が未実測だった**ことです。G-2 の判定基準5件を見ます。

| # | 基準 | 前提の実証を問うか |
| --- | --- | --- |
| 1 | 受入基準が検証可能な形式 | 問わない(形式のみ) |
| 2 | 曖昧語が残っていない | 問わない |
| 3 | 暗黙の前提が案件層コンテキストに**登録済み** | **登録を求めるだけで、実測を求めない** |
| 4 | スコープ外事項が明記 | 問わない |
| 5 | 範囲がスコープ3層へ割り当て済み | 問わない |

**「ExStruct と Docling は位置を返す」という前提は、基準3を満たしたうえで誤っていられます**。登録すれば通ります。

本プロジェクトは根拠水準マーク(ADR-0026)を**自らの執筆規約**として持ちますが、これは `community/` 配下の運用規約であり、**標準が案件へ課す要求事項ではありません**。**自分に課しているものを、規格として他組織に課していない**という非対称が残っています。

**この穴は Dev-B とは無関係です**。埋めるなら G-2 の判定基準か第6章の様式であり、レーンの分割ではありません。**私はこれを潰せませんでした**。

### 穴2 — 上流成果物を下流の担い手が数え上げる経路が、G-4 の判定基準に無い

実例1が起きたのは**実装計画の作成時**、すなわち G-4 の前後です。しかし E.5 の「検証の順序」は**差分を検証する段階**に置かれています。G-4 の判定基準を見ます。

- 基準2(粒度)・基準4(規模)は**タスク側の性質**しか見ない
- 第6章 テンプレ7 のチェックリスト「各タスクがどの受入基準に対応するか明記した」は**起案側の自己申告**であり、対応の欠落を突き返す経路ではない
- 基準5(範囲内外の判定)は記入の有無のみ

つまり「**受入基準の側に、対応するタスクが1件も無いものが残っていないか**」を数える手続が、G-4 の判定基準として規定されていません。E.5 順1 の裏返しに当たる検査です。**実例1は、標準に書かれていない手続によって捕まりました**。

**これも Dev-B とは無関係です**。埋めるなら G-4 の基準であり、レーンの分割ではありません。**潰せませんでした**。

### 穴3 — ロールを増やさずセッションだけ分ける構成は、私の批判を全て回避する

仮説Eの批判は「ロールとして立てる場合」にしか掛かりません。Dev レーンの内側でセッションを分けるだけなら、次がすべて成立します。

- 3.5.3 の文脈の分離条件(作業領域・セッション・認証情報)の範囲内
- Label Mailbox の語彙は増えない(`state:needs-dev` のまま)
- 兼務表・写像表・遷移表の改訂が不要
- 5.8.4 段階「弱」が求める「別セッション・別文脈」と同型

**この形は潰せません**。ただし、**潰せないことは新条項が要ることの証明ではありません**。むしろ逆で、**既存の条項の下で実行できる**ことの証明です。案件が D-0 に書けば済みます。**標準へ何かを足す理由にはなりません**。

### 穴4 — 5.8.4 の独立性4段階は、テスト生成にしか掛かっていない

仮説Cで述べたとおりです。仕様・帳票・実装計画といった**非テスト成果物**に対して、「順序と入力による独立性」を求める条項は標準にありません。実例2件はどちらも非テスト成果物でした。

**これは真の空白です**。ただし、埋めるとしても**5.8.4 の射程の拡張**であって、新しいロールでも新しい章でもありません。**枠組みではなく、既存の表の適用範囲の問題です**。

### 穴5 — 5.8.4 の警告は「足しにならない」までで、「引き算になる」を述べていない

5.8.4 の現行の文言はこうです。

> 同一のモデルを用いる限り、担当のエージェントを分けても事前学習の知識という共通の原因が残ります。**エージェントを分けたことをもって独立性を確保したとみなしてはなりません**。

これは**加算を禁じる**規定です。「分けても独立性の足しにはならない」までしか述べていません。**分けることが有害でありうるとは述べていません**。

調査が出した数値は、この水準を超えています。

| 数値 | 出典 | 現行条項が説明できるか |
| --- | --- | --- |
| 同質パネルの有害改訂率 **89%**(正しかった答えが議論で壊れる方が多数派) | arXiv:2606.19826 | **説明できない**。5.8.4 は「足しにならない」としか言っていない |
| 誠実な異質ピア1体の追加で **35%** へ低下、初回正答の反転率 31% → 6% | 同上 | **説明できない**。異質性という変数が 5.8.4 の4段階に存在しない |
| MAD が CoT / 自己整合に劣後(MMLU 80.73% 対 67.87〜80.40%) | ICLR 2025 Blogpost | **説明できない**。分けない構成のほうが良い場合があることを述べていない |
| persona 付与で **-3.6〜-5.3pt** | Wharton 2026-03 | **説明できない**。役割の名乗りに関する規定が無い |

**この差は条項の強さを変えます**。現行の文言のもとでは、Dev-A / Dev-B のような分割は「独立性としては数えないが、やる分には構わない」と読めます。89% の数値が正しければ、**やり方によっては正味で悪化します**。禁止すべきとまでは言いませんが、**「無害である」という読み方を許している現行の文言は、実証と食い違っています**。

同じことは 5.8.4 の4段階の変数にも及びます。段階「弱」「中」は**順序と入力**の軸で書かれており、**異質性(別のモデル系統)の軸がありません**。実証では異質ピア1体の投入が 89% → 35% という最大の効果を出しています。**標準の目盛りに、最も効く変数が載っていません**。

**弁護役としても、これは潰せませんでした**。ただし、これは Dev-B を置く理由にはなりません。**逆に、置くことを慎重にする理由です**。

### 穴6 — 29119-1 E.3 の非対称を、標準は原理として持っていない

29119-1 Annex E.3 は、独立性ゼロ(作成者本人)の扱いを**適用場面で分けています**。

- 動的コンポーネントテスト: 独立性ゼロが「よく見られる」と黙認される
- ピアレビュー(開発者が行う静的テスト): 同じ独立性ゼロは「**通常、受け入れられるとは考えられていない**」

**本標準は、この非対称を結果としては実現しています**。

| 側 | 標準の該当 |
| --- | --- |
| 動的テストは実施者側で回してよい | 附属書E E.7 自己修正ループ、`implement` スキル(エージェントがテストを実行する) |
| レビューは自己では成立しない | 3.5 兼務禁止表、3.5.2 の比較表「1人での達成は**不可能**」 |

**しかし、非対称の理由を原理として書いた箇所がありません**。2つの規定が独立に存在するだけで、両者を貫く判定基準が無いのです。

**これは実務上の欠落です**。新しい活動が現れたとき、それをどちら側へ分類するかを決める基準がありません。**Dev-B の活動がまさにその例です**。

- 実測(5経路を動かす)は**動的テスト側**であり、実施者本人が行ってよい
- 前提の妥当性の判断(「この受入基準は成り立つか」)は**レビュー側**であり、本人では成立しない

**現行の標準は、この2つを分ける基準を与えません**。したがって「Dev-B の出力をどう扱うか」という PO の質問3に、原理からは答えられません。第4章の明文(合否に用いない)で答えは出ますが、**それは個別の禁止であって原理ではありません**。

原理を書くなら、置き場は 5.8.4 の前(独立性の総論)です。**新しいロールではありません**。

### 穴7 — 「反証は測定結果を伴わなければ受け付けない」という制約が無い

調査は、外部観測を伴う反証が +19〜44pt、伴わない自己批判が +0.5pt であることを示しています(2607.06636 / 2607.14167 / 2502.03492)。この差は大きく、**「測定を伴わない反証を受け付けない」という制約には条項としての価値がありえます**。

しかしこれも**レーンの分割とは独立**です。誰が反証するかによらず、**反証の受理条件**の話です。置き場があるとすれば 5.8 であり、第3章ではありません。

### 4.2 標準側の欠陥として書くこと

**弁護役の立場からでも、次は標準側の欠陥です。**

**(a) 私が第1節で根拠にした条項の半分は、実装マークを持っていません。** E.5 の検証の順序、5.8.4 の4段階、5.8.1、5.6.2 のいずれにもマークがありません。実装台帳(`community/implementation-ledger.md`)に `undelivered` が1件も無いのは、**降りていない規定が無いからではなく、降りていない規定にマークが付いていないから**です。

**#222 の運用の前提が崩れています**。「降りていない規定(`state=undelivered`)は消さずに表示し続ける」という規定は、**マークを付ける対象が網羅されている場合にしか働きません**。標準全体で実装マークは19件です。この規模の標準に対して19件は、網羅を主張できる数ではありません。**台帳が「全て delivered」を示していることが、逆に検査の未実施を示しています**。

**(b) 5.8.4 段階「弱」は、実行層に存在しません。** Filetto がリスク区分 R3 の変更で「別セッション・別文脈で検証を回す」ことを求められても、`tailoring-kb.json` にも CLAUDE.md にも「セッション」の語がありません。**構成から導出されないため、実行主体は起動時にこれを知りません**。

これは第1節・仮説Cの私の主張に直接効きます。私は「5.8.4 段階『弱』が既にあるから新条項は不要」と書きました。**条項としては存在しますが、Filetto へは届いていません**。**私の論証の一部は、届いていない条項に寄りかかっていました**。訂正します。

**(c) 3.5.3 の文脈分離の3条件は、知識ベースの語彙に対応物を持ちません。** `separations` の `scope` は `same-work-product` / `same-project` という**成果物と案件の単位**しかありません。3.5.3 が定める**セッションと認証情報の単位**を表現できません。ADR-0035(実行主体の文脈による分離)が知識ベースへ降りていないということです。

これも仮説Eに効きます。私は「Dev-B をロールとして立てると 3.5.3 の管理対象が増える」と批判しました。**3.5.3 が実行層に無いのであれば、増える対象がそもそも管理されていません**。批判の前提が弱まります。

**(d) 5.6.2 の欠陥注入は、テンプレートに一片も降りていません。** 標準は 5.6.1 で「AI の生成品質が上がるほどレビューは形骸化しやすくなる」と述べ、5.6.2 でその対抗手段を7項目にわたって規定しています。**それが実行層に無いということは、Filetto の形骸化は測定されないということです**。#249 が指摘した1名7ロールの体制で、**形骸化の検出手段が実装されていません**。

### 4.3 この検査から出る、Dev-B とは無関係な結論

## 5. 弁護役の結論

**Dev-A / Dev-B の分割を、標準へ新しいロール・新しい節として書き込む理由は見つかりませんでした**。

- 実例2件は、分割の効果ではなく**外部観測の効果**であり、かつ**工程間の分離**(PO → Dev)が働いた例である(仮説A・B)
- PO が実際に行った作業は、E.5 順1・5.8.1・3.5.3・5.8.4 段階「弱」の**条項の下で実行できる**(仮説C)
- 質問2・質問3の答えは**既に明文にある**(仮説D)
- ロールとして立てれば、兼務表・写像・ラベル語彙・遷移表が連鎖的に増え、#249 の指摘を悪化させる(仮説E)

**ただし、この結論には第4節の留保が付きます**。私が「既にある」と主張した条項のうち、**5.8.4 段階「弱」・3.5.3 の3条件・5.6.2 は、Filetto の実行層へ届いていません**。条項としてはあり、統制としてはありません。**「標準は持っている」という私の論証は、条項の水準では成立し、統制の水準では一部成立しません**。

**PO の相談は無駄ではありませんでした**。この相談が可視化したのは Dev レーンの分割の必要性ではなく、次の3つです。

| 見つかったもの | 節 | 埋める先 |
| --- | --- | --- |
| 受入基準の前提の根拠水準を、標準が問うていない | 穴1 | G-2 判定基準 |
| 上流成果物を下流の担い手が数え上げる経路が無い(`task-breakdown` はタスク側からしか検査しない) | 穴2 | G-4 判定基準 / `task-breakdown` スキル |

**いずれも Dev-B を置いても埋まりません**。**起案側がこの会議で通すべきなのは、新しいレーンではなく、G-2 基準3 の強化と、実装マークの網羅性検査です**。
