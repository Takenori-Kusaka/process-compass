### K13 承認者の同一性を確かめてから、独立した人の確認に数える(F1・F12)

1名体制で、AI が作った変更を指示した本人が承認すると「独立した人の確認あり」に数えられた。別アカウントの承認も通った。保証の開示の根幹なので、数える条件を定める。

- 名簿 `people[]` に、リポジトリ上のアカウント(`accounts[]`)を持たせる
- 承認を「独立した人の確認」に数えるのは、次をすべて満たす場合に限る
  1. 承認したアカウントが、名簿の人へ対応づく
  2. その人が、当該変更の作成を指示した者でない
  3. 構成上、G-6 が未達でも「成立しない(責任者が同一)」でもない。ただし、承認した人が名簿で外部の確認者である場合は数える
- 作成を指示した者は、PR 本文の欄「作成を指示した者」(複数可)から取る。欄が未記入のときは、PR の作成者(人のアカウントの場合)と、開発者の席の責任者を指示者とみなす。この場合は「指示した者は既定値による」と表示する
- 対応づかない承認は数えず、「承認者を名簿と対応づけられない」として未確認の件数へ入れる
- 2名体制で、2人とも指示に関与した変更は、相互の確認では成立しない(第3章 3.5)。未確認に数える
- 未確認が1件でもあれば、附属書H H.6 の定型の文を出す
- 標準側: `ci-gates.md` の「保証の開示の出力」と「実装の制約」を上に合わせる。テンプレ(PR の様式)へ欄「作成を指示した者」を足すかは、既存の様式の欄との重複を確かめて決める(あれば流用)
- 限界として開示する: 名簿のアカウントの記載が正しいかは機械で確かめない(架空の2人目を書ける)。監査観点6 で確かめる

### K14 R1 を G-6 未達のまま出荷するときの例外承認を、G-7 で突合する(F2)

- 既存の基準(判定記録と例外の完備を見る基準)の読みとして書けるなら、基準を足さずにその基準の説明へ書く。書けないなら基準を足す(`criteria:write` で複製を更新する)
- テンプレート: 証跡の集約で、R1 かつ独立した人の確認なしの変更に、例外承認の記録が対応づかなければ `gaps` へ入れて fail

### K15 即時通知の通知者と記録(F3)

### K37 変化点を経ない書き換えを検出する(重大1)

- 構成(`process.config.json`)は、`/process-change` だけが書き換える。手での編集を案内している記述(構成書、初期化スキル)を改める
- `changeLog[]` の各記録に、適用後の構成の要約値(`changeLog` 自身を除いた構成のハッシュ)と、直前の記録の要約値を持たせる(連鎖)。契約検査は、現在の構成の要約値が最後の記録と一致すること、連鎖が切れていないこと(切り詰め・差し替えの検出)を確かめる
- CI(PR)では、基底ブランチの構成と比べる。構成が変わっているのに `changeLog` の追記が無い、または基底の `changeLog` が先頭部分として保たれていない場合は fail
- 回答ファイルからの再生成は、最後の記録の要約値と一致する場合だけ通す。一致しない場合は `/process-change` を案内して拒否する
- 限界として開示する: 要約値ごと書き換える改ざんは、基底ブランチとの比較と、構成が強制層であること(変更は AI維持管理者の承認を要する)で止める。ローカルだけでは防げない

### K38 3名以上で、兼務禁止に当たる席の同一人物化を拒否する(重大2)

- 3名以上の体制で、独立レビュアと開発者(および第3章 3.5 が兼務を禁じる他の組)の責任者を同一人物にする変更は拒否する。10名以上で分離を必須とする組も同じ(中7)
- 1〜2名では逸脱または未達として記録する(現行どおり)

### K39 「発生」は、人が実際に減ったときに限る(重大3)

- 向き `arising`(記名を待たず即時)を適用するのは、名簿の体制内の人が減った、または席の責任者が名簿から外れた場合に限る
- 人が減っていないのに、回答・席の入力で独立レビューや承認数を下げる変更は、緩める向きの決定である。記名と理由を要する(第3章 3.13.2)

### K40 中4〜11 と軽

- 中4: 規則の検査(全域の指定、変更種別、決定者の名義)は、席の運用形態の同時指定に依らず、書き込む前に必ず行う
- 中5: 委任の変更の「検証方法と結果」は、担い手が実行結果の証拠として書く(5.5.6)。人の記入を要求しない。表示名は K17 に合わせる。トレーラは、マージの経路の有無にかかわらず書く(K41)
- 中6: 1人 → 2人で確認者の回答を変える必要があることを、`/process-change` が案内する(名簿の体制内が2名になり、回答が「確認者なし」のままなら、残作業へ出す)
- 中7: 10名の境界で変わる項目(レビューの方式、承認者の方式)を差分へ出す
- 中8: 適合性確認の実施者は AI維持管理者の席の責任者、承認者は当該の席の責任者に限る(第3章 3.4.2)。名簿と照合する
- 中9: 担い手の識別の変更と同時に出された再確認は、記録の `performer` が新しい識別と一致し、確認日が変更日以降である場合にだけ有効とする。委任へ戻すのは緩める向きであり、席の責任者の記名を要する(5.5.7「引き下げた範囲は、緩める向きの手続を再度経るまで戻さない」)。無ければ協働へ下げる
- 中10: 承認だけの変化点で席が協働のまま残る場合は、その旨と、残っている手続を表示する
- 中11: K42 による
- 軽: ルールセットの README、CLAUDE.md:60 の語(「判断が不十分な場合」を 5.5.1 の3つの場合へ)、`sgRecord` は実在するファイルを指すこと、入力値の検査(回答値、運用形態、期間の前後)、名義の検査の正規化(全角、片仮名の読み)、`samePersonAsDecider` の比較、席を空欄にして人が抜けたときの案内、カバレッジ下限の引き継ぎ(代償措置の表示と実際の下限を一致させる)
- 名義の検査の限界(役職名、別の文字種による回避)は、機械で閉じない。名簿は人が記入するものとし、監査観点6 で確かめる旨を開示する
- 変更種別と標準変更カタログの照合: 構成に登録した種別の一覧(`delegation.changeTypes[]`。登録した者と日付を持つ)を持たせ、規則の `changeType` はこの一覧にあるものだけを受け付ける(K32・K33 の登録の主体と対応する)

### K41 委任した変更のマージの経路を実装する(場面13)

第1巡では「今回の範囲を超える」として実装を見送った。再検証で、委任は宣言できても人の作業が減らないと指摘された。AI に任せる運用形態が標準にあっても、テンプレートで運用できなければ、体制の入れ替わりへ追随できるとは言えない。見送りを改める。

- **該当の判定**(5.5.4 条件1・2・3・5・7 のうち機械で判定できるもの)を、決定的な検査として実装する。判定のコードと構成は基底ブランチから読む。PR の側から判定を書き換えられない形にする。AI に判定させない
  - 条件1: 構成が委任を許している(CL0・規制業でない・出荷できない状態でない)
  - 条件2: 変更したファイルがすべて、承認済みの1つの規則の範囲に入り、除外と強制層に触れない。PR のリスク区分が R3。席が委任を宣言し、適合性確認が有効
  - 条件3: G-5 の必須チェックが通過している
  - 条件5: 確約範囲とコア指定のパスを構成に持たせ(登録されていれば)、触れる変更を対象外にする
  - 条件7: すべてのコミットにトレーラ `Delegated: <規則ID>` がある
  - 条件4(取り消しの実績)と条件6(事後の抜き取り)は、登録時と事後の人の判断であり、変更ごとの機械の判定に含めない。その旨を出力する
- 判定の結果は、必須でないステータスとして PR へ出す(該当 / 該当しない理由)
- **マージの実行**は、既定で無効とする。組織がリポジトリの変数で明示的に有効化し、必須承認を回避できる権限のトークンを用意したときだけ動く。無効のあいだは、現行どおり協働として人の承認を待つ
- 機械は承認のレビューを付けない。「人の事前確認を経ていない変更として、規則 <ID> により先へ進めた。承認ではない」と PR へ記録する
- 実際の GitHub 上で実行して確かめていないことを、README・`ci-gates.md`・実装マークの note に明記する。IMPL-0026 は、実環境での確認が取れるまで `undelivered` のままとする
- 標準側: 第5章 5.5.4 と `ci-gates.md` に、判定を基底ブランチから読むこと(行為する側が判定を書き換えられないこと)を要求として書く

### K42 D-0 と構成の二重記入を無くす(中11、詰まる箇所)

- D-0 の様式のうち、構成から導ける部分(席・責任者・担い手・運用形態の表、委任の範囲、改訂履歴)を生成区間にし、`/process-change` が書き換える。人が書くのは、決定の理由と記名だけにする
- D-0 の検査は、生成区間が構成と一致することを確かめる。不一致は fail
- 標準側(テンプレ0 の注記、3.13.4)に、構成から導ける欄は生成してよく、その場合は構成を正とする、と書く

## 再現手順の詳細を受けた補足(K38・K40 の確定)

再現手順は `tmp/reverify-scenarios/details.md`。

### K38 の確定(重大2)

- 3名以上の体制で、独立レビュアの席と開発者の席の責任者を同一人物にする変更は**拒否する**。出荷判定者=開発者を拒否している現行の扱いと揃える。3名以上では、席を引き受けられる別の人がいる
- 席の作業を複数の人が担うこと(開発者が5名いる、など)は妨げない。拒否するのは、判定の記名を行う席の責任者が、判定される側の席の責任者と同一である構成である
- 構成書・契約検査・保証の開示の表示を一致させる(片方だけ「適用する」と出さない)

### K40 中9 の確定(担い手の識別の変更と、再確認の同時申告)

新しい版を採用する前に適合性確認を済ませておく運用を、第3章 3.4.2 は禁じていない。「常に協働へ落とす」は採らない。ただし、入力のまとめ方で記名を省ける経路は閉じる。

- 識別の変更と同じ変化点で出された適合性確認を有効とするのは、次をすべて満たす場合に限る
  1. 記録の担い手の欄が、新しい識別と一致する
  2. 記録が旧い記録の使い回しでない(確認日が旧い記録の確認日より後である)
  3. 実施者が AI維持管理者の席の責任者、承認者が当該の席の責任者である(中8)
  4. 当該の席の責任者が、新しい識別で委任を続ける決定として記名し、理由を書く(`decidedBy`・`reason`)
- 1つでも欠ければ、協働へ下げる。表示と記録を実際の状態に合わせる(「協働を上限とする」と出しながら委任のまま、を無くす)
- 標準側(5.5.7、3.4.2)へ、採用前の確認と記名による切り替えを書く

### K40 中10 の確定(2つめの記名で有効になる)

- 席の責任者が委任を宣言し、規則が承認待ちである間、宣言した意図(委任)と決定者を保持する。AI維持管理者の承認が入った変化点で、委任を有効にする。再宣言を要求しない
- 承認待ちの間は協働として動くことと、残っている手続を表示する
- 規則の決定者と承認者が同一人物かどうかの記録は、規則の決定者と比べる

### K40 軽の追加

- 即時通知の残作業は、3.13.6 の全事象で出す(K15)
- 適合性確認の記録だけの追加を「構成の変更なし」と記録しない
- 継続中の「AI が使えない期間」を後から閉じる入力を持つ
- 出荷できない状態の理由文を、原因(人数の減少 / 安全重要度の上昇)で書き分ける

### K13 の補足(開発者の席だけの委任)

- 開発者の席だけが委任で、独立レビュアが人として事前に承認した変更は、G-6 については「独立した人の確認あり」である(K13 の条件を満たす場合)。「人の事前確認を経ていない変更」に数えない。トレーラ `Delegated` は、開発者の席の変更ごとの検証を担い手へ委ねたことの識別として別に数える
- この場合、現在のルールセットのままマージできる。「委任の範囲の変更も協働として扱う」という記述は、G-6 を事後へ移す委任(独立レビュアの席の委任)に限って書く

### K16 の確定(承認の失効として書く)

- 適合性確認を承認した席の責任者が交代した(離脱を含む)とき、承認は新しい責任者へ引き継がれない。結果責任を負う者が受け入れていない担い手を、委任で動かさないため
- 失効するのは承認である。担い手の識別が変わっていなければ、確認の記録(事例と結果)は有効なまま残る。新しい責任者は、既存の記録を読んで承認し直せば足りる。確認の再実施は要しない
- 承認し直すまで、協働を上限とする(厳しくする向き。即時)。離脱の変化点は止めない
- 標準側: 3.4.2、3.13.3、5.5.7、ADR-0055 決定3。3.4.2 の「失効の契機は担い手の識別の変化」は、確認の記録の失効についての文として残す
