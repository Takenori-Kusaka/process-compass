## 3. 論点A の問いへの回答

### 問1 5.5 を維持するか

改めます。現行の 5.5 は「判断の種類」と「担当ロール」を1つの表で結び、ロールごと人へ固定しています。1名体制では、これは「1人が全判断を確定する」と同義です。承認は回数が増えるほど阻止率が落ちます(序盤約 17% から 50 回超で約 5%)[FND-0010]。全件を人へ通す規定は、5.6 が防ごうとしている状態を自ら作ります。

| 人に固定するもの | 根拠 |
| --- | --- |
| 全成果物の結果責任(A)。記名の自然人1名 | 3.2、5.2。外部指針も説明責任を人と組織に置く [FND-0004] |
| R1 の決定と不可逆な操作の確定 | 5.4.4、ADR-0053。外部も承認点を不可逆・高影響の行為に置く [FND-0002] |
| 本番反映の承認(記名) | 5.4.3 の不変条件2 |
| 席の運用形態を AI 側へ広げる決定 | 5.4.3 の不変条件4 |
| 5.8.3 の4項目 | 変更しない |

| 担い手の運用形態へ委ねるもの | 条件 |
| --- | --- |
| R3 の判断の確定(価値・技術・理解の確認) | 責任者が範囲を宣言する。委譲しても A は責任者に残る(3.6 と同じ構造) |
| R2 の判断の起案と材料の提示 | 確定は人 |

運用形態は「人のみ / 協働 / AI 自律」の3値とし、上限は 5.4.4 の対応(R1→人が確定、R2→協働、R3→AI 自律可)をそのまま使います。新しい尺度を足しません。

条件が1つあります。**R3 かどうかを、行為する AI 自身に判定させません**。リスク評価を行為者の LLM 自身が付ける構成には独立性がありません [FND-0002]。AI は人へ戻すべき場面で戻さずに進みます(E3)[FND-0012]。判定は対象パス・変更種別・依存差分による機械規則に置き、規則で R3 と分類できなかったものは協働へ落とします。出発点は第8章「対象にできる変更の境界」と 3.7.4 の標準変更カタログです。拡張は事後の記録を根拠にします。

この改正で過剰エスカレーションが減るかは分かりません。外部が原因に挙げるのは指示の書き方とモデル世代で [FND-0011]、ロール指定が効かない測定もあります [FND-0009]。根拠水準は E0 です。戻し先を明示すると不正な回避が減る測定はあります [FND-0093]。境界と出口の両方を置き、「範囲内なのに聞いた件数」と「範囲外なのに確定した件数」を測ります。

### 問2 独立レビュアと出荷判定者の席を AI が担えるか

独立レビュアの席の運用形態は、リスク区分で分けます。R3 に限って AI 自律を認めます。R2 では協働とし、AI の所見を入力にして人が承認します。R1 では人のみとします。「独立」は次の組で定義します。

| 定義の候補 | 現場で強制・確認できるか | 扱い |
| --- | --- | --- |
| 別人 | アカウントとブランチ保護で確認できる。1名体制では成立しない | R1・R2 の確定に求める |
| 別文脈(作業領域・セッション・認証情報) | 3.5.3 で強制できる | AI が担う検証の必要条件。単独では足りない(再現率 27.1%)[FND-0087] |
| 入力の切り離し(仕様は渡す。作成側の主張と会話は渡さない) | レビュー入力を組み立てるコマンドで強制できる | 必要条件。説明文を除くと検出が戻る測定がある [FND-0087] [FND-0082] |
| 外部の観測(欠陥注入の検出率、事後抜き取り、取り消しの実績) | 自動で実行できる | 必要条件。測定の無い AI 検証は「未測定」と表示する |
| 別モデル系統 | 提供停止と利用上限で維持できない [FND-0023]。効果の符号も割れる [FND-0080] | 要件にしない。併用は任意 |

#268 の実測(33 日で 42 回の drift、指示の追加 5 回で変化なし)は単一事例ですが、対応する外部測定があります [FND-0082]。AI の席には 5.4.6 の自動引き下げ(差し戻し率 0% が続く)を同じ条件で掛けます。

出荷判定者の席は協働に固定します。G-7 は記録と基準の突合で、読解を前提にしない設計です(第4章)。突合は機械が行い、残存リスクの受容と署名は人が行います。**AI 自律の出荷判定席は要りません**。人の判定を経ない経路は、標準変更カタログ(3.7.4)が既に持っています。育てる対象はカタログです。

### 問3 1名体制・2名体制での成立

席は消しません。責任者は1名体制では全席同じ人になります。独立性はリスク区分で型を分けます。外部の規範も「課さない / 外部に置く / 代償措置で維持する」の3型に分かれます [FND-0016] [FND-0017] [FND-0018] [FND-0189]。

| 体制 | R3(機械規則で分類できた範囲) | R2 | R1 |
| --- | --- | --- | --- |
| 1名 | 人の事前レビューを課さない。AI 検証+取り消しの実績。事後抜き取りの実施者がいなければ、その旨を未達として表示 | 外部に置けなければ未達(ADR-0028)。AI 検証は代償措置で、未達の解消に数えない | 外部に置く |
| 2名 | 同上。抜き取りは相手が行う(開発ラインの内側である旨を表示) | 相互レビューで成立 | 相互レビュー。必要なら外部 |

現行の軸A は、1〜2名の全変更について独立レビューを外部へ求めます。AI が1セッションで 19 PR を出す体制では続きません(#270)。外部の人を R1 へ集中させれば、依頼は四半期に数件で済み、続けられます。

**保証されなくなるもの**: 1名体制の R2 の変更は、別の人が出荷前に見ることなく出ます。AI の再レビューは注入欠陥の約 73% を見逃した測定があります [FND-0087]。残るのは、壊れたことを後から検出して取り消せる状態だけです。現行も同じ状態を「未達」と表示していますが、案件単位の表示は慣れで読まれなくなります(5.7.5)。リリースごとの件数で出します(4章 問5)。

1名体制には、もう1つ守られていない要求があります。開発者(検証)の席は、変更ごとに挙動を自分の言葉で説明することを求めます(3.3 の挙動検証・理解記録、3.4)。19 PR の全件にこれを行う1人はいません。R2 の挙動検証を「変更単位」から「リリース単位の受入基準との照合」へ移す調整を、検討の対象として挙げます。**保証されなくなるもの**は、変更単位での人の理解です。コア指定の機能は変更単位のまま残します。効果の実証はありません(E0)。

1名+AI で解けないもの(調整役の不在、手戻りの未計測)は外部記録とも対応します [FND-0030]。標準は「解けない」と先に書き、未達として表示させる側に立つべきです(#267)。

### 問4 変化点に何を数えるか

| 変化点 | 数えるか | 起きたときの扱い |
| --- | --- | --- |
| 人の増減・交代(席の責任者または担い手が変わる) | 数える | 席を割り直す。人数の境界(2→3、4→5、9→10)を跨げば、例外の失効と未達の解消・発生を出力する |
| 担い手の運用形態の変更 | 数える | AI 側へ広げる向きは判定を要する(資格確認・理由・記名)。人側へ戻す向きは自由(5.4.5 と 5.4.6 の非対称) |
| モデル・ハーネス・指示資産の版の変更、提供停止 | 数える | AI 自律の席を協働へ自動で下げ、資格確認をやり直す(3.12.5 の要求3 と同じ向き) |
| 軸 A〜E の回答の変化(ステージ移行、目的の変更による品質・安全重要度・開発形態の変化) | 数える | 再テーラリング。不変条件に反すれば拒否する |
| 確約範囲(SC-M)の変更 | 数える | 既存の手続(第2章 2.10、第8章 軸D)。構成は変えない |
| 納期だけの変更 | **構成の変化点に数えない** | 「構成の変更なし」を記録する。納期を理由に統制を外す要求は、緩める向きの変更として扱う |
| 短期の不在 | 数えない | 3.9.3 の代理指名による |
| サブエージェントの起動数、誘導層の文言の修正 | 数えない | 3.11.4 の保守で扱う |

納期の変更を外すのは、5軸のどれも動かさないためです。現場で統制が落ちるのは納期が詰まったときなので、コマンドは納期の変更も入力として受け、「納期を理由に外せない項目」を出力します。目的・納期の変更を扱う外部規定は二次解説の水準です [FND-0192]。体制・AI 編成への変化点管理の転用例は束にありません [FND-0020]。

更新するのは D-0 の承認者(小さい体制では事業決裁者を兼ねる1名)で、作業はコマンドが行います。記録は、変化点ログ・D-0 の版・構成の差分・失効または発生した例外と未達の一覧です。「変更なし」も記録します(ADR-0015 決定10 と同じ扱い)。

**実行を人の記憶に任せません**。宣言した人数と直近の承認者・コミッタの数、宣言したモデルと実際に動いたモデルの不一致は機械で検出します。指定したモデルが実際に動くとは限りません [FND-0059]。

### 問5 AI を担い手に置くときの任命基準の確認

3.4.1 の5要求を、そのまま AI の担い手へ読み替えます。

| 3.4.1 の要求 | AI の担い手での対応物 |
| --- | --- |
| 任命に先立ち充足を確認し記録する | AI 自律へ上げる前に資格確認を実行する |
| 実務の成果物または演習の記録で確認する | 検証の席は、当該リポジトリでの欠陥注入の検出結果(5.6.2。AI のレビュー層も対象)。判断の席は、協働期間の決定のうち人が覆した件数。全席共通で、人へ戻すべき仕込み事例で止まるか |
| 判定者・日・用いた成果物・結果を残す | 加えて担い手の識別(モデルの版・ハーネス・指示資産の版)を残す |
| 確認を経ない任命は暫定任命 | 暫定の間は協働(人の併記)。単独で確定させない |
| 有効期間を定める | 期間ではなく**担い手の識別が変わるまで**。変わった時点で失効する |

主要3社は数週間間隔で世代を更新しています [FND-0023]。期間で切る有効期間は実態に合いません。

## 4. 論点B の問いへの回答

### 問1 最上位の主張

「このプロセスを回せば品質保証できる」とは書けません。書けるのは次です。

> 本標準に従って作った成果物について、誰が結果責任を負い、変更ごとに何を・誰が(人か AI か、どの独立性で)確かめ、何を確かめていないかを、証跡付きで示せる。壊れたことを検出し、取り消せる。

| 保証するもの | 保証しないもの |
| --- | --- |
| 各成果物の結果責任者が記名の自然人1名に特定されていること | 欠陥が無いこと |
| 変更ごとのリスク区分と、実際に通した検証経路の記録 | 仕様そのものの妥当性(価値仮説の当否) |
| 未実施・未達・逸脱が、通過と区別されて表示されること(ADR-0028) | テスト計画の十分性(ADR-0041)、知財の潔白(ADR-0021) |
| 検出能力の測定値(人の層と AI の層。標本数つき) | 承認した人が実際に理解していたこと |
| 取り消しの手順と実行の実績 | AI の出力の正しさ(5.8.1) |

主張の範囲を限定して明示する先例はあります。供給網の規格は来歴と完全性に範囲を限り、コード品質を範囲外と明記します [FND-0100]。

### 問2 AI による検証を「検証」に数える条件

| 数えてよい条件(すべて満たす) | 数えてはならない条件(いずれか) |
| --- | --- |
| 文脈が分離している(3.5.3 の3点) | 作成と同じセッション・作業領域・認証情報 |
| 入力が切り離されている(仕様は渡す。作成側の主張は渡さない) | 作成側の PR 説明文や会話を読んだうえでの判定 [FND-0082] |
| 所見が証拠を伴う(実行したコマンドと出力、落ちるテスト、該当行) | 証拠を伴わない通過の表明 [FND-0091] |
| 担い手の識別が記録されている(5.8.2) | 識別が変わった後で、検出能力を測り直していない |
| 当該リポジトリで検出能力を測ってある(5.6.2) | 測定が無い |
| 対象が R3 である(R2 では人の判定の入力まで) | R1、安全関連(5.8.3)、記述の実質性による可否の決定(5.7.4) |

決定論的な機械検査は、従来どおり検証に数えます(5.8.1)。人の承認の入力が AI の要約だけである場合、その承認を人の検証に数えません(3.10.12)[FND-0228]。

### 問3 人の確認が形骸化していないことの対外的な示し方

示すものは3つです。

- 捕捉率。欠陥注入の検出率を、人の層と AI の層で分けて示す(5.6.2、5.7.6 の主指標)。標本数を併記する
- 差し戻し率。0% を良い状態として示さない(3.9.4、5.4.6)
- 1人1日あたりの人の判定件数。上の2つが良くても、この値が大きければ判定は形だけと読める [FND-0010] [FND-0160]

3つ目が現場の主張です。形骸化への対処は、承認の儀式を重くすることではありません。**人へ届く件数を絞ること**です。形式的な承認の追加は変更失敗率を下げないという報告もあります [FND-0104]。A-3 のリスク区分による配分は、この数値を下げる手段です。1名体制でも、AI の席が別文脈から注入すれば、人は注入箇所を知らないまま測定を受けられます。

挙動要約の必須化が形骸化を防ぐという実証はありません(E0)。「防いでいる」とは言わず、「測っている」と言います。

### 問4 証跡の最小集合と、装置の肥大との両立

| # | 証跡 | 出どころ | 追加の作業 |
| --- | --- | --- | --- |
| 1 | 体制と席の宣言(責任者・運用形態・未達・逸脱) | `process.config.json` のスナップショット | なし |
| 2 | 変更一覧とリスク区分、通した検証経路の件数 | PR・コミットのトレーラ、分類規則の出力 | なし(分類規則の初期設定が1回) |
| 3 | G-5 の結果。未実施を通過と区別する(#254)[FND-0027] [FND-0194] | CI | なし |
| 4 | G-6 の記録(承認者が人か AI か、担い手の識別、挙動要約) | 承認レビュー | 人の挙動要約は現行どおり |
| 5 | G-7 の突合結果、残存リスク、負債台帳の差分 | `aggregate-evidence.mjs` | 残存リスクの受容は人が書く(5.7.2) |
| 6 | 検出能力の測定値(実施日・標本数・担い手の識別) | 資格確認の出力 | 仕込みの事例集の用意が1回 |
| 7 | 期間内の変化点ログ | 構成ファイル | なし |

**7項目のうち、人が毎回書くのは4の挙動要約と5の残存リスクだけです**。どちらも現行の要求で、増えません。残りは作業の副産物を集約スクリプトが集めます。したがって、現場は追加の作業なしで証跡を出せます。例外は2つです。リスク区分の機械規則と、仕込みの事例集の初期設定です。これを案件ごとに書かせれば装置が増えます。テンプレートが既定を持つべきです。

両立の条件は次の3点です。

- 開示は生成物にする。手で書く証跡を新設しない
- 開示を守る機械検査の hard-fail は「主張と実体の一致」に限る(人が承認したと書いてあるのに承認記録が無い、など)。体裁と網羅性は警告に留める。#269 の線引きによるが、規格・製品の先例は束に無い [FND-0234]
- 案件側に保証の論証を書かせない。書かせれば、製品より大きな文書がもう1つ増える [FND-0067]

### 問5 独立性を満たせない体制での開示

等級(A・B・C)は付けません。リリースごとに、件数で出します。

| 区分 | 変更数 | 人の独立レビュー | AI 検証(条件充足) | 機械検査のみ |
| --- | --- | --- | --- | --- |
| R1 | 2 | 2(外部) | 2 | 0 |
| R2 | 14 | 0(**未達**) | 14 | 0 |
| R3 | 31 | 事後抜き取り 0(**実施者なし**) | 31 | 0 |

適合の表明は「適合(未達: G-6 の R2 分)」のように、未達を外さずに書きます。等級は一度付くと目標になります(#269 の Goodhart の観測)。件数は読み手が自分の基準で読めます。

## 5. 採らない案と理由

| 案 | 採らない理由 |
| --- | --- |
| A-1 単独 | 変化点手続は要る。ただし AI の確定範囲が「なし」のままでは、人が全判断の待ち行列になる(#248 #249)。回せない統制は、宣言なしの迂回を生む [FND-0156] |
| A-2 | ロール単位では粗すぎる。1つの席に R1 と R3 の判断が混在する。二択では「人のみ」の席も、担い手の識別も書けない。外部分類も役割単位の二値ではない [FND-0001] |
| A-4(単位として) | 結果責任の割当・ゲート・受信箱が席に載っている。外すと誰が A かを辿れない。許可プロンプトは人の承認が最も形骸化する場でもある [FND-0010]。切り方としては取り込む |
| AI 自律の出荷判定席 | 標準変更カタログが同じ機能を持つ。席を足すと経路が二重になる |
| 別モデル系統を独立の要件にする | 維持できない要件は守られない。効果の測定も割れる [FND-0080] |
| 保証水準の等級化 | 等級が目標になる。件数の開示で足りる |
| B-2 単独 | 問答は主張の体系を持たない。問いが変わるたびに足され、互いに矛盾しても検出できない |
| B-3 を規範にする | 原典の未読箇所(ISO/IEC 42001 附属書A、ISO/IEC 29110 の SI 工程)が残る。読めていない規格への適合は言えない |
| 案件ごとに保証の論証を書かせる | 文書が製品を超える再現になる(#267 #270) |

## 6. 実行層に要るもの

現状のテンプレートは、`/process-init` の再実行で体制の変更を扱います。8問をすべて聞き直す方式で、変化点の種別・失効する例外の検出・変化点ログ・担い手の運用形態を持ちません。`roles[]` は AI を全ゲートの `mustNotJudge` に固定しています。

### 構成ファイル(`process.config.json`)に足す欄

| 欄 | 内容 |
| --- | --- |
| `seats[].accountable` | 責任者(記名の自然人)。空は検査で落とす |
| `seats[].mode` | `human` / `collab` / `ai-auto` |
| `seats[].performer` | AI の担い手の識別(モデルの版・ハーネス・指示資産の版) |
| `seats[].fallback` | AI が使えないとき(利用上限・提供停止)の扱い。`human` または `stop` |
| `seats[].qualification` | 資格確認の実施日・用いた事例集・結果。識別が変われば失効 |
| `aiScope` | R3 と分類する機械規則と、AI が確定してはならないパス |
| `changeLog[]` | 変化点の記録(種別・日付・理由・承認者・構成の差分) |

検証の席は turn の過半を使います(#274 の QM 64%)[FND-0060]。上限が尽きて最初に止まるのは検証です。`fallback` を書かせる理由です。

### 変化点を反映するコマンド(`/process-change`)

| 入力 | 値 |
| --- | --- |
| 種別 | `member-join` / `member-leave` / `seat-reassign` / `mode-change` / `performer-change` / `axis-change` / `schedule-change` |
| 対象 | 人・席・軸のいずれか、変更後の値、発効日 |
| 理由と承認者 | 緩める向きでは必須 |

| 出力 | 内容 |
| --- | --- |
| 構成の差分 | 適用前に表示する。席・ゲートの状態・必須承認数・未達・逸脱 |
| 失効・発生の一覧 | 失効する例外(3名到達で ADR-0029)、解消する未達、新たに生じる未達と逸脱 |
| 向きの判定 | 厳しくする向きは即時適用。緩める向きは理由と記名を要求し `/adr-write` へ渡す |
| 再生成 | `PROCESS-PROFILE.md`、`CLAUDE.md` のマーカー区間、D-0 表1の差分(人名は人が確認する) |
| 残作業 | ブランチ保護の適用コマンド(実行しない)、発行・失効させる認証情報、期限つきの資格確認、人へ戻る判定件数の見込み(直近 30 日の区分別件数) |
| 記録 | `changeLog[]` への追記。「構成の変更なし」も記録する |
| 拒否 | 不変条件に反する場合は理由つきで終了する |

### 併せて要るもの

- 未反映の検出(`check-seats.mjs`)。宣言と実態のずれを CI とセッション開始時に検査する。対象は人数、モデルの識別、D-0 の `next_review`
- 強制層への降ろし。AI が確定してはならない範囲は権限設定・ブランチ保護・実行前フックに置く(3.11.3)
- 自席カード。常時ロードへ入れるのは、その実行主体の席・確定してよい範囲・戻し先の3点だけ。全席の表は入れない。常時ロードしない規則は読まれないことがあり [FND-0033]、読み取りは費用の過半を占める [FND-0047]
- 資格確認(`/seat-check`)。仕込みの事例集を席の担い手へ通し、結果を `qualification` へ書く
- 保証の開示。`aggregate-evidence.mjs` の出力へ、問4 の7項目と問5 の表を足す
- 決定の記録。AI が確定した R3 の決定は、コミットのトレーラ(席・形態・区分)に残す。別の文書を作らない

## 7. 残るリスクと根拠水準の弱い箇所
