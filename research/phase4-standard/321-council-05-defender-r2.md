- 作成日: 2026-10-23
- 立場: 第1巡で ADR-0036 決定1 を擁護した弁護役。第2巡では、第1巡の 5 つの意見書を突き合わせ、残った 4 つの争点について各案を反証し、自分の第1巡の主張のうち折れるものを折れたと書く

## 1. 先に結論

- **争点 A**: 固定の時点は「写しはマージごとに機械が作り、基底ブランチへ入れるのは G-7 で記名者が 1 本の PR を承認する」の二段を採ります。監査側の「マージごと」は時点について正しく、起案側・規格整合の「bypass 不採用」は経路について正しい。両立させる鍵は、**写しの置き場を既定ブランチのルールセットの外(同一リポジトリの記録用ブランチ)に置くこと**です。ルールセットは参照名で条件づけられる(`team.json:5`〜`6`)ため、既定ブランチの保護に穴を開けずに、マージ時の `GITHUB_TOKEN` が写しを push できます。App も bypass も要りません。写しの真正性は「原本が参照できる間に突合した事実と、突合した者の記名」で担保し、原本が消えた後に新たに証明する手段は無いと開示します(02 9.3「全案に共通する穴」)
- **争点 B**: 折れます。第1巡の案 B(記録の草案を判定者以外の文脈が起こし、判定者が承認する)は衝突を解きますが、G-2・G-4 ではコストに見合いません。採るのは現場の変形案「仕様 PR への判定者本人のレビュー(**承認の状態を問わない**)+ 宣言行 + `commit_id` とマージ時 head の一致の機械検査」です。監査側・規格整合が「衝突」と呼んだものは、承認の **APPROVED 状態**を成立要件に読んだときにだけ生じます。G-2・G-4 は「別の人による確認」ではなく「確定」であり(ADR-0060:58、`gate-criteria.md:170`)、ブランチ保護が止める自己承認(目的は変更の取り込みの抑止、ADR-0067:36)とは別の事象です。自分の仕様に自分で宣言する記録は、**版の確定の記名**として意味を持ちます。意味を持たないのは「独立した確認」としての読みだけで、G-2 はそれを課していません
- **争点 C**: (ii) 判定者を bypass に置く案は却下します。人のロールの無条件 bypass はルールセットの意味を失わせ(02 5.3)、Bot の bypass より悪い。採るのは (i)+(iii) の併用です。ただし B を折った結果、記録だけの PR は **G-7(出荷ごと 1 本)・G-8・SG・例外承認・停止の解除**にしか残らず、判定ごとの往復は消えます。残る PR には第1巡の案 B(記名者は push せず、草案は別の文脈が push し、記名者が承認する)を当て、集約が「承認者 = 記名者」を検査します。これで現場 2 章の「A が B の記録を空承認する」構造は消えます。強制層がパスを区別できないことは IMPL `undelivered` で表示し続けます
- **争点 D**: 起案側の弱点 5「1 名体制では何も軽くならない」は、媒体に APPROVED 状態を要する前提の帰結であり、争点 B を折れば崩れます。`checks-only.json` は承認を強制せず(`rulesets/README.md:21`)、直接 push だけを止める(`:23`)ため、ソロの G-2・G-4 は「仕様 PR へ本人のレビューを 1 本書く」で成立し、記録 PR(現場 2.3: 操作 4 回)が消えます。G-6 は未達で元から記録が無く、現場の「2 回」は正しい。ただし PR の作成者本人が COMMENTED のレビューを提出できることは実機未確認です(E3)
- 第1巡の自分の主張のうち、**4 点を撤回**します(3 章)。「承認イベントを成立要件に置かない」は撤回しません。採る形はいずれも「欄が埋まった記録の存在」を成立要件に保ち、ホスティングの状態を成立要件にしていません

## 2. 争点ごとの反証

### 争点 A — 固定の時点と Bot

#### A-1 各案の反証

| 案 | 主張 | 反証 | 判定 |
| --- | --- | --- | --- |
| 起案側 | G-7 で集約が 1 本の PR を開き、出荷判定者が承認。Bot の bypass は一切不採用 | 固定を G-7 まで待つと、マージから G-7 までの窓で (a) 承認本文の編集履歴の内容が作者・write 権限者に消される(02 1.5)、(b) 承認者の退会で `user.id` ごと ghost 化する(02 1.6)、(c) 180 日で bypass・override の証跡が消える(02 3 章)。起案側自身が弱点 4 で「写しを作る時点で原記録が読めない事態を扱っていない」と認めている。**写しを G-7 の時点で初めて作る形は、監査側の 3 点の指摘に答えていない** | 経路(bypass 不採用)は正しい。時点は折れるべき |
| 監査側 | マージごとに App が `pull_request` モードの bypass で真正な複製を既定ブランチへ固定。G-7 で集合を引き受ける | (1) `pull_request` モードでも「PR を作れば何でも通る」(02 9.3 案 A の穴)。bypass はパス単位に絞れない(02 5.3)ため、App の鍵が漏れれば既定ブランチの任意のファイルを書ける。監査側はこれを「App の名義のコミットが `RECORD_PATHS` の外に触れていないこと」の機械検査で補うが、自ら E0 と認めている(03 意見書 7 章 #3)。(2) **App の署名は写しの内容の真正性を何も証明しない**。署名が示すのは「その App がコミットした」ことだけであり、API 応答どおりの内容かは示さない(02 案 E の穴と同じ)。`GITHUB_TOKEN` の API コミットも github-actions[bot] の署名で Verified になる(02 5.1)ので、App が足すのは bypass できる能力だけである。(3) 監査側が bypass を要するのは「既定ブランチへ固定する」と決めたからであり、固定先を既定ブランチに限る理由は示していない | 時点(マージごと)は正しい。経路(bypass)は折れるべき |
| 現場 | G-7 の PR に承認イベントの写し(`evidence.json`)を同梱。Bot は転記に限り可、`exempt` 不可。ソロには装置を増やさない | 起案側と同じ窓の問題を持つ。現場は Q5 で「写しの固定が現場で唯一実行できる保全」と言うが、G-7 で初めて API を引く形では、180 日を超える出荷間隔・退会・本文の編集の内容の消去に写しが追いつかない。「Bot は転記に限り可」は正しいが、転記の**時点**を G-7 に置いたままでは転記の価値が半減する。装置を増やさない要求は、マージ時の転記が既存の `ship-evidence.yml` の延長(ワークフロー 1 ステップ)で済むなら両立する | 受け皿(G-7 の PR)は正しい。写しを作る時点は折れるべき |
| 規格整合 | 判定時点に改変不能な場所にある記録だけ G-7 まとめ固定が整合。Bot bypass は ADR-0038 の形で記録 | 条件の立て方は正しい。ただし「承認レビューは改変不能」は本文について成り立たない(編集でき、履歴の内容は消せる。02 1.5)。改変不能なのは `state`・`commit_id`・`submitted_at`・`user` であり、判断の中身(本文)は改変可能である。したがって**本文を含む写しは、判定の時点に近い時点で機械が作らなければ「改変不能な場所にある記録」にならない**。規格整合の条件を厳密に当てると、本文の固定は G-7 まで待てない | 条件は正しい。条件を当てると結論がマージごとの写しに倒れる |

#### A-2 写しの真正性を何が保証するか

問いは「集約の信用、App の署名、承認レビューの API 応答」のどれかです。答えは「どれか 1 つ」ではなく、**時間の順に重ねる**ことです。

| 時点 | 真正性の根拠 | 限界 |
| --- | --- | --- |
| 原本が参照できる間(マージ直後〜180 日・退会・移管まで) | 承認レビューの API 応答。写しは API 応答から機械が作り、以後いつでも再取得して突合できる | ホスティングの信用に依存する。それを超える手段は無い(02 9.3 共通の穴) |
| G-7(原本がまだ概ね参照できる時点) | 出荷判定者が、集約が API から再取得した値とマージ時の写しの一致(件数と内容)を見て、写しの集合を記名で引き受ける。一致の突合は機械が行い、人は突合の結果を見る | 一件ずつ原本を見る確認ではない(起案側 Q3 と同じ扱い) |
| 原本が消えた後 | git の履歴(写しを入れたコミットの作者 = ワークフローの bot、実行 id、G-7 の PR の承認レビューの id)と、既定ブランチの `non_fast_forward`(`team.json:24`) | **新たに真正性を証明する手段は無い**。証明できるのは「G-7 の時点で突合した記録がある」ことまで |

この順序から導かれるのは、**突合の時点を原本の寿命より前に置く**ことです。写しをマージごとに作るのは「改変不能だから」ではなく「原本と突合できる間に作るから」です。G-7 の記名は「突合した者」の記名であり、写しの内容を保証するのは突合の事実です。App の署名はこの表のどこにも登場しません。署名が証明するのはコミットの主体であり、`GITHUB_TOKEN` の bot 署名で足ります。

#### A-3 採る案: 記録用ブランチへのマージごとの写しと、G-7 の 1 本の PR

- 写しは、PR のマージを契機にワークフロー(`GITHUB_TOKEN`、`contents: write`・`pull-requests: read`)が API から引き、**既定ブランチのルールセットの外にある記録用ブランチ**(例 `gate-records`)へ push する。ルールセットの条件は参照名であり(`team.json:5`〜`6`)、既定ブランチの保護はこのブランチに掛からない。bypass actor を足さない。`GITHUB_TOKEN` は bypass actor に置けない(02 4.1)が、保護の無いブランチへは置く必要が無い
- 写しの最小の組は 02 9.1 のとおり(レビュー `id`・`state`・`commit_id`・`submitted_at`・`user.id`・`user.login`・本文・PR 番号・`merge_commit_sha`)。写しを作ったワークフローの実行 id を併記する
- 記録用ブランチには `non_fast_forward` と `deletion` だけのルールセットを置く(承認の規則を置かない)。`GITHUB_TOKEN` の push は fast-forward なので止まらない。人が写しを書き換えれば人の名義のコミットとして残り、集約が「記録用ブランチのコミットの作者がワークフローの bot でない」を欠落に数える。無料の私有リポジトリ(ルールセット不可 `template/README.md:115`)ではこの保護も置けず、検出だけになる。既定ブランチと同じ扱いである
- G-7 で、集約が記録用ブランチの写しを再取得した値と突合し、G-7 の判定記録とともに**1 本の PR**で既定ブランチへ入れる。承認者は出荷判定者本人(争点 C の案 B の形)。これで「記録はコードと同じ履歴にある」(02 案 D が失う性質)は G-7 の時点で回復する
- 規制業(軸C)・CL2 以上(軸E)では、監査側 5 章のとおり「出荷の範囲の全変更について写しが記録用ブランチに存在すること」を G-7 の前提にする。本案ではこれが既定で満たされるため、構成で分ける必要が無い。分けるのは組織側の作業(保管規程・ツール評価・電子署名の要否)だけである
- 既定ブランチへ Bot が直接固定する構成を組織が選ぶ場合は、bypass actor の追加として ADR-0038 の統制の弱化の経路で記録する(規格整合の線)。本標準の既定にはしない

#### A-4 折れる / 折れない

- 折れる: 「記録はゲートごとに、判定の時点で作る。G-7 でまとめて固定する案は採らない」(第1巡 Q3)。記録(承認レビュー)は判定の時点に作られており、写しもマージごとに作られる。基底ブランチへ入れる時点が G-7 であることは、この二段が揃えば ADR-0036:103「事後の事務」の却下に当たらない
- 折れない: 既定ブランチの bypass actor に Bot を置かない。App を使わない。`exempt` を使わない
- 条件つき: 記録用ブランチの案は実装していない(E0)。`GITHUB_TOKEN` が保護の無いブランチへ push できること、`pull_request: closed` の契機で `merged == true` を読めることは GitHub の一般の挙動から推定した(E3)。並行マージで fast-forward が競合する場合の再試行は実装の問題として残る

### 争点 B — G-2・G-4 の受け皿

#### B-1 「衝突」の正体

監査側・規格整合が「判定者が作成側になりうるため、ブランチ保護の『作成者は自分の PR を承認不可』と衝突する」と言う衝突は、次の 2 つを混ぜたときにだけ生じます。

| 事象 | 目的 | 根拠 |
| --- | --- | --- |
| 仕様 PR の承認(ブランチ保護が数える APPROVED) | 1 名の確認だけでは変更を取り込めない状態を作る | ADR-0067:36。`require_last_push_approval` の要点は「承認を得たあとに自分で push して内容を変えられる」ことの抑止(`rulesets/README.md:43`) |
| G-2・G-4 の判定 | 価値責任者が、確定する版を特定して記名する | `gate-criteria.md:170`「受入基準の確定は、人が、確定する版を特定して、判定記録へ記名する行為」。ADR-0060:58「結果責任者が内容を確定する行為です。別の人による確認ではありません」 |

G-2 の判定を仕様 PR の **APPROVED** に乗せると、ブランチ保護は「作成者 = 判定者」を止めます。これは止めるべきものを止めているのではなく、**別の目的の規則が、目的の異なる記録を巻き込んでいる**だけです。乗せる先を「判定者本人のレビュー(状態を問わない)」にすれば、巻き込みは起きません。

#### B-2 「自分の仕様を自分で承認する記録は意味を持つか」

持ちます。ただし「承認」ではなく「確定」として持ちます。

- G-2・G-4 が記録するのは「価値責任者が、この版を受入基準として引き受けた」ことである。これは版の固定(`commit_id`)と記名と時刻(`submitted_at`)で成り立つ。仕様の作者が誰かは、この意味に影響しない
- 意味を持たないのは「独立した確認」としての読みである。G-2 はそれを課していない(ADR-0060:58)。独立した確認が要るのは G-6 であり、そこでは基準4 と 4 条件が別に掛かる(`gate-criteria.md:463`〜`472`)
- 監査側が引く 03 §7.2「『文章として問題ない』と『受入基準を確定する』が同じ承認ボタンに畳まれる」は、**宣言行を課せば解ける**。`G-2: 通過` の宣言行を持つレビューだけを G-2 の記録と読み、宣言行の無い承認(取り込みのための承認)は G-2 に数えない。これは QMS 対応表の「事前に対応を定めた操作だけを承認として扱う」(`qms-document-control.md:33`)の適用である
- 手入力のファイルは、同じ「確定」を、人が打った SHA(現場 2.3 の罠)と人が打った日時で記録する。レビューは同じ確定を、機械が束縛した `commit_id` と機械の時刻で記録する。**ファイルのほうが強い点は 1 つも無い**。ファイルが勝るのは構造(確認した項目・差し戻し理由の欄)だけであり、それは本文の見出し語で運べる(起案側 Q2)

#### B-3 第1巡の案 B は衝突を解くか

解きます。記録の草案を判定者以外の文脈(3.5.3 `roles-responsibilities.md:529`)が起こして PR を開き、判定者が承認すれば、判定者は最後の push 者ではなく、自分の作成物の PR でもないので、承認は止まりません。承認レビューの Who / When が判定者の記名を裏づけます。

しかし G-2・G-4 では採りません。理由は 3 つです。

- 判定ごとに記録 PR が 1 本残る。B-2 の形は PR を増やさず、同じ Who / When / What を判定の瞬間に得る。信頼性で同等、同時性で案 B が劣る(記録 PR の承認は判定の時刻から遅れる。02 案 C の穴)
- 案 B は 1 名体制で成立しない。別の文脈(AI のレーン)が草案を起こせても、`checks-only.json` は承認を数えない。B-2 の形はソロでも同じ手順で成立する(争点 D)
- 案 B は「記録 PR の承認」と「仕様 PR の承認」の 2 つの承認を判定者に求める。承認の回数を増やさない(03 8.4)に反する

案 B は撤回せず、**残る記録だけの PR(G-7・G-8・SG・例外承認・停止の解除)に当てる**形へ縮めます(争点 C)。

#### B-4 機械検査が強くなる点

承認の状態を問わないことの代償は、`dismiss_stale_reviews_on_push` が COMMENTED のレビューを失効させないことです。宣言行つきレビューが指す `commit_id` より後に push があれば、確定した版と取り込まれた版がずれます。これは集約が `commit_id == マージ時の head` で機械検査でき(02 7 章)、ずれた変更は「確定していない版を取り込んだ」として欠落に数えます。現行の IMPL-0107 は版の識別子の有無を機械で確かめず内部監査に委ねている(`gate-criteria.md:178`)ので、**レビューを媒体にすると、ファイルより検査が強くなります**。

#### B-5 採る案

- G-2・G-3・G-4 のうち、対象の成果物(仕様・ADR)が PR として存在する場合: 判定者本人のレビュー(APPROVED / CHANGES_REQUESTED / COMMENTED を問わない)。本文の 1 行目に宣言(`G-2: 通過` / `G-2: 差し戻し / 基準 N / 期限 YYYY-MM-DD`)、続けて確認した項目を見出し語で。対象の版 = レビューの `commit_id`。集約が `commit_id == マージ時 head` を検査する
- 成果物が PR として存在しない場合、ホスティングが争点 A の条件を満たさない場合: 判定記録(ファイル)。これは代替ではなく後退経路(起案側 Q7)であり、「同じ結果を導く手続を 2 つ持つと緩いほうだけが使われる」(`gate-criteria.md:1208`)には当たらない。緩いほうが既定であり、重いほうは使えないときにだけ現れる
- 規格整合の「承認レビューを受け皿にできる 2 条件」のうち、条件2(判定者が作成者・指示者と別の人)は **G-6 の独立の条件であって媒体の条件ではない**。G-2 の媒体に求めるのは条件1(`commit_id` で固定できる)だけである。この点で規格整合に同意しない
- 折れる: 第1巡 Q4「G-1〜G-4・G-8・SG の記録は判定記録(ファイル)に置く」の G-2・G-3・G-4 の部分。撤回する

### 争点 C — 記録だけのコミットに別の承認者を課さない、の実装

#### C-1 まず母数を数える

争点 B を折ると、強制層(`team.json` 以上)の下で記録だけの PR が残る場面は次だけです。

| 場面 | 頻度 | 残る理由 |
| --- | --- | --- |
| G-7 出荷判定(写しの集合 + G-7 の判定記録) | 出荷ごと 1 本 | PR に紐づかない。現場も「ここは PR で構わない」(現場 2.4) |
| G-8 リリース決裁(決断の記録) | リリースごと | 実行環境の承認操作は決断の記録を運ばない(監査側 Q4) |
| SG ステージ移行 | 稀 | 会議体の判定 |
| 例外承認(7.3)・停止の解除(7.11) | 稀 | 基底ブランチの記録だけを読む設計意図(`ci-gates.md:146`・`155`)。PR の中の記録を使えない |

判定ごとの往復(現場 2.2 の手順 9〜17)は、G-6 が承認レビュー、G-2・G-4 が仕様 PR のレビューになった時点で消えます。争点 C が扱うのは、残る稀な PR の承認者を誰にするかです。

#### C-2 各案の穴

| 案 | 穴 | 「A が B の記録を空承認する」構造 |
| --- | --- | --- |
| (i) Bot が PR を開き、CODEOWNERS で判定者本人が承認 | (a) `require_code_owner_review` は `team.json:14` で false。有効にすると既定の `* @OWNER`(`CODEOWNERS:10`)により全 PR が OWNER の承認を要し、体制の運用が変わる。(b) 所有者の誰か 1 人で足り、bypass actor は素通り(02 4.3)。(c) `GITHUB_TOKEN` が PR を開けるかは組織設定に依存する(起案側 弱点 8)。(d) strict の下で基底が進めば更新 → 再承認が残る(記録 PR を本体の後に開き、すぐ入れれば小さい) | **消える**。承認者は記名者本人。A は関与しない |
| (ii) 判定者の署名コミットを直接 push(判定者を bypass に置く) | 直接 push には `always` モードが要る。人のロールへの無条件 bypass は「ルールセットの意味を失わせる」(02 5.3)。判定者は自分が指示した AI の変更も既定ブランチへ押し込める。Bot の bypass より悪い(Bot は鍵、人は意思)。署名コミットの価値(帰属)は PR の中の署名コミットでも同じに得られ、直接 push を正当化しない | 消えるが、代償が強制層そのもの |
| (iii) `undelivered` の IMPL として表示し、記録 PR 1 本を受け入れる | 実装ではなく開示である。PR 1 本の承認者を誰にするかを決めなければ、現行の「判定者以外の承認者」が残る | 単独では**消えない** |

#### C-3 採る案: (i) の形を CODEOWNERS の強制なしで採り、(iii) で開示する

- 残る記録だけの PR は、**記名者は push せず**、草案を別の文脈(AI のレーン、または別の人。3.5.3)が push して PR を開き、**記名者本人が承認する**(第1巡の案 B)。`require_last_push_approval` と両立する
- `require_code_owner_review` は有効にしない。`* @OWNER` の既定が全 PR に掛かる副作用を避ける。代わりに**集約が「記録の置き場だけの PR の承認者 = 記名者」を検査し**、一致しない PR(第三者が承認した記録 PR)を記名の無い記録として欠落に数える(起案側 3.2)。CODEOWNERS は、記録の置き場の所有者を記名者の席に割り当てる形で**案内として**置く(強制はしない)
- 規制業(`regulated.json`、承認 2 名)では、記録 PR にも 2 件目の承認が強制される。2 件目は記名者本人ではあり得ないため、**取り込みの事務の承認**であると明記し(監査側 Q4)、ゲートの記録に数えない。これは強制層がパスを区別できないことの帰結であり、消せない
- 第4章「判定の成立」に「判定記録だけのコミットに、記名者以外の承認を課さない」を要求事項として書き(規格整合 4(c))、降ろし先をルールセットに新規登録して `state=undelivered` で表示し続ける。GitHub がパス単位の免除を持つようになった時点で `delivered` に変わる
- 折れる: 第1巡 4.2「(i) 記録 PR を 1 本残し B の形で承認者を判定者本人にする。弁護役は (i) を推す」は、**G-2・G-4 を含めて推していた**。それを撤回し、残る稀な PR に限る
- 折れない: (ii) は却下。bypass に人を置かない

#### C-4 「A が B の記録を空承認する」は消えるか

消えます。G-6(承認レビュー)、G-2・G-4(仕様 PR のレビュー)には記録 PR が無く、G-7 の PR の承認者は出荷判定者本人です。残るのは規制業の 2 件目の承認だけであり、それは事務と明記します。現場 2.2 の手順 14・16(A の承認・再承認)は無くなり、手順 15(本体マージ後の更新)は G-7 の PR が本体の後に開かれるため起きません。

### 争点 D — 1 名体制

#### D-1 食い違いの原因

起案側の弱点 5 は「判定者が自分で成果物を push すると自己承認が止まり、AI と同じアカウントでも止まる。この体制では全ゲートが判定記録ファイルへ戻り、記録 PR の往復は残る」です。現場は「ソロは 2 回で済む」です。

両者は違うゲートを数えています。現場の「2 回」は G-6(未達。記録が無い `rulesets/README.md:19`)であり、起案側の「戻る」は G-2・G-4 です。起案側の推論は正しいが、**前提が「媒体は APPROVED 状態を要する」**です。争点 B でその前提を外せば、起案側の結論は崩れます。

#### D-2 `checks-only.json` の下で何が変わるか

`checks-only.json` は `pull_request` の規則を持たず(承認を強制しない)、`required_status_checks`(`strict: false`)と `non_fast_forward`・`deletion` だけです。直接 push は止まり、PR は必須チェックだけでマージできます(`rulesets/README.md:23`)。

| ゲート | 現行(現場の見積り、E3) | 争点 B を折った後 | 変わる理由 |
| --- | --- | --- | --- |
| G-2・G-4 | 仕様 PR のマージ 1 + 記録 PR(9 欄 1・push 1・マージ 1)= **4** | 仕様 PR への本人のレビュー 1(宣言 + 確認した項目)+ マージ 1 = **2** | 記録 PR が消える。SHA は `commit_id` が束縛し、人が打たない(現場 2.3 の罠が消える) |
| G-6 | 未達。0 | 未達。0 | 何も変わらない。現場の「2 回」(Ready とマージ)はこれ |
| G-7 | 集約・9 欄・push・マージ・タグ = **4** | 同じ。写しは記録用ブランチから集約が引く | 出荷ごと 1 本。現場も受け入れている |
| 無料の私有(ルールセット不可) | 直接 push 可。検出だけ(`template/README.md:115`) | 同じ。宣言つきレビューは PR があれば書ける。PR を経ない直接 push は集約が欠落に数える(現行) | 強制層が無い構成では、記録の媒体を変えても止める力は増えない。増えるのは検出の鍵(`commit_id`・`submitted_at`) |

#### D-3 残る弱さと開示

- PR の作成者本人が COMMENTED のレビューを提出できることは、UI の挙動からの推定である(E3)。02 10 章の未確認事項に無い。実機で確かめる。できなければ、ソロの G-2・G-4 は「PR のレビューコメント(review comment)ではなくレビュー(review)」を使えず、ファイルへ戻る
- AI と判定者が同じ認証情報を使う体制(ADR-0035 条件3 を満たさない)では、レビューを AI が判定者の名義で提出できる。これは手入力のファイルでも同じ(AI が判定者の名義でファイルを書ける)であり、媒体を変えても強くも弱くもならない。5.5.6「AI の担い手の名義で確定しない」を止める機械の手段は無い。現行どおり内部監査と開示に残す
- ソロで軽くなるのは G-2・G-4 だけである。「ソロの記録 PR の往復」は G-2・G-4 の往復であり、それが消える。起案側の「何も軽くならない」は撤回されるべきだが、「G-6 が軽くなる」とも言えない。G-6 は未達であり、未達は未達のまま見せる(ADR-0028)

#### D-4 折れる / 折れない

- 折れる: 第1巡 Q4 末尾「この形(案 B)を 1 名体制へ持ち込む余地はない。1 名体制では記録 PR の承認者の問題は元から生じない」。前段は正しいが、後段は「承認者の問題」だけを見ており、記録 PR そのものの往復(操作 4 回)を見落としていた
- 折れない: 1 名体制で G-6 の記録を作らせない。未達の表示を消さない

- 仕様 PR そのものの取り込みの承認(2 名体制で判定者が push した場合に A が承認する形)が G-6 の対象か。仕様ファイルは `ci-gates.md:609` の無条件の除外に無く、製品の変更として扱われる。これは本件の範囲外だが、争点 C の「空承認」が仕様 PR の側に残る可能性として記録する

## 6. 弁護役の結語

第1巡で弁護役が守ったのは「記録の無い判定は未判定」「承認の操作だけでは数えない」「記録の固定のために強制層へ穴を開けない」の 3 つでした。第2巡でもこの 3 つは残ります。折れたのは、記録の**媒体と時点**についての自分の保守的な前提です。G-2・G-4 の記録をファイルに留める理由は、ブランチ保護との衝突を「承認の状態」の問題と読んだことにあり、それは確定と確認の取り違えでした。G-7 まとめ固定を退けた理由は、写しの時点を G-7 と同一視したことにあり、写しをマージごとに作れば退ける理由は消えました。

監査側へは、時点について同意し、経路について同意しません。bypass を開かずに同じ時点に写しを作る置き場があるなら、bypass を開く理由は無い。起案側・現場へは、経路について同意し、時点について同意しません。G-7 で初めて作る写しは、起案側自身が弱点 4 で認めた穴を塞いでいない。規格整合へは、条件の立て方に同意し、G-2 の媒体に独立の条件を課す点に同意しません。

決められた場所で人間が触る、という一文の要約は変わりません。変わるのは、触った痕跡を人に打ち直させないことです。
