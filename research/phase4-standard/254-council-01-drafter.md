# 254 会議体 01 — 起案側の案(Filetto の Dev-A / Dev-B 分割)

作成日: 2026-08-14 / 立場: 起案側
対象: P-001 Filetto(人1名 + AI エージェント体制、G-6 独立レビューは未達のまま運用)
問い: Dev レーンを「作る(Dev-A)」と「壊しにいく(Dev-B)」へ分ける構成を、Filetto はどう運用すべきか

本稿は Filetto の運用案です。標準の改訂案ではありません。新しい概念語は導入せず、既存の条項の語彙だけで組み立てます。

## 0. 先に結論

- **Dev-B は新ロールではない。Dev レーン内の作業分担である**
- **Dev-B の「主張」は、どのゲートの合否条件にもならない。ただし Dev-B が生んだ「測定結果」は、G-5 の検査へ載せた時点で判定に使われる**。境界は主体ではなく、反証が決定論的に再実行できる形になっているかである
- **「監査の入力」以外の扱いはある**。既存の「判定に要する労力を下げる」経路がそれに当たる。効果を記述する枠組みも既にある
- **順序(1) → (2) → (3) は正しい**。ただし「実測を義務づけること」は先取りしてよい。先送りすべきなのは「レーンを常設すること」だけである
- **標準への還元は3つに分かれる**。既にあるのに降りていないもの **5件以上**(4-1)、無くて書く価値があるもの **4件**(4-2)、書かないと決めるべきもの **8件**(4-3)。最も書く価値が高いのは **4-2-4**(G-4 に受入基準の側からの数え上げを置く)である
- **弁護役の反証4件はすべて正しく、うち1件は私の論証を折った**。5.8.4 の射程はテスト生成に限られ、**D-4 は標準上の根拠を持たない**。格下げした。詳細は「弁護役への応答」による

## 1. 3つの質問への回答

### 1.1 質問1 — この構成に標準上の位置づけはあるか。新ロールか、Dev レーン内の分担か

**Dev レーン内の分担です。新ロールを立ててはなりません。**

根拠となる条項は4つです。

**(a) 3.5 兼務ルールは「禁止する組み合わせ」を列挙する形式である。**
Dev-A と Dev-B の組は、禁止表のどの行にも当たりません。「作成指示者 × 独立レビュア」でも「開発ライン × 出荷判定者」でもないからです。両者はいずれも実行(R)であり、結果責任(A)を負いません。**禁止表に当たらない以上、分割そのものは許可されています**。標準の許可を得るために新ロールを起こす必要はありません。

**(b) 5.5 の判断4種類はすべて人間のロールである。**
価値判断・技術判断・理解の確認・記録の確認の4つは、担当ロールがすべて人間であり、AI へ割り当てられません。Dev-B はこの4つのどれも担いません。**したがって Dev-B は 5.5 のロール体系に席を持ちません**。席を持たないものをロールとして D-0 体制図へ書くと、体制図が実態と異なる読み方を許します。

**(c) 3.5.3 により、Filetto では「人の単位」の分離が成立しない。**
兼務は人と実行主体の文脈の2つの単位で判定し、**いずれか一方でも同一なら分離は成立しません**。Filetto は人が1名です。Dev-A / Dev-B を分けても人は同じであり、人の単位では分離しません。ロール名を2つ立てると、体制図の上には分離があるように見え、実態には無い、という記録が残ります。3.5.2 が「**役割の名称を分けただけでは分離になりません**」と書いているのはこの事態を指します。

**(d) 5.8.4 が、この構成を名指しで否定している。**
> エージェントを分けたことをもって独立性を確保したとみなしてはなりません

Dev-A / Dev-B の分割は、この一文の対象そのものです。

以上より、**Filetto が採るべき位置づけは「Dev レーンの作業手順を2段に分ける」であり、体制上の分離ではありません**。

:::

なお、これは Dev-B に意味がないという結論ではありません。ただし**その意味は標準の条項ではなく、実証にのみ支えられています**。調査 r2 の CCR(文脈を切った再レビュー、F1 24.6% → 28.6%、d=0.52)がそれです。効果は小さく、追加基盤は要りません。**小さく無料で効くものとして、案件の裁量で採ってください。標準の要求ではありません**。

**Filetto が書くべき記録**: D-0 体制図には「Dev レーン(1名 + AI)」の1行のみを書きます。Dev-B は体制図ではなく、レーンの作業手順(実装計画テンプレート、CLAUDE.md 等)へ書きます。G-6 が未達である事実は、これまでどおり未達として表示し続けます(ADR-0028)。**Dev-B を足したことを、未達の解消として記録してはなりません。**

### 1.2 質問2 — 出力はどのゲートでも判定に使えない、という理解でよいか

**「合否条件にできない」は正しく、「判定に使えない」は言い過ぎです。** 標準は主体で切らず、形で切っています。

**(a) 合否条件にできないこと** — 第7章「帯域を理由に判定を省略しない」

> AI による事前審査を合否条件として挿入する手段は採りません。……AI の指摘は……**注意を向ける材料として提示し、合否には用いません**

Dev-B が書いた所見・懸念・評価は、この「AI の指摘」です。**通す方向へは一切使えません**。「Dev-B が反証を試みて否定できなかった」は、いかなるゲートの通過根拠にもなりません。同節が続けて述べるとおり、これを許すと偽陰性が「事前審査を通過した」という記録として残ります。

**(b) それでも判定に効く経路が2つある**

**経路1: G-5 の検査へ落としたとき。**
Dev-B が実測で得た反証を回帰テスト・検査スクリプト・突合スクリプトの形にすれば、それは G-5 の判定基準1(全テスト GREEN)または該当する決定論的検査に載ります。このとき判定しているのは検査であって Dev-B ではありません。**Dev-B は検査を1件増やした実行(R)にすぎず、判定へは一切関与していません**。ここに標準上の矛盾はありません。

実例2(.docx がページ位置を持たない)は、この経路へ落とすべき典型です。実測して終わりにすると、同じ誤った前提が次の仕様でまた書かれます。**落とす先があって初めて、反証は再発を止めます**。

**経路2: 止める方向には使える(非対称)。**
Dev-B の否定が成立したとき、PO はそれを理由に成果物を差し戻します。これは合否条件ではなく差し戻しです。標準はこの非対称を既に持っています。事前レビューの自動化(高リスク事項の自動ラベル)の規定がそれです。

> 機械の判定は一次判定です。**引き上げは誰でもできますが、引き下げは技術判断者の記名を要します**

**厳しくする方向は機械に開き、緩める方向には人の記名を課す**。Dev-B の扱いはこれと同型です。Dev-B は成果物を止められますが、通せません。

**(c) 5.8.1 が上位にある**

> AI の出力は、それ自体では成果物になりません

Dev-B の出力も AI の出力です。**Dev-B の反証それ自体も「未検証の入力」です**。Dev-B が「ここが壊れる」と書いたことは、壊れることの証明ではありません。証明は添付された観測です。したがって PO は Dev-B の文章ではなく、**添付された測定結果を読みます**。これが 1.3 の作業定義の根拠になります。

**Filetto への回答**: 「どのゲートでも判定に使えない」ではなく、「**Dev-B の言葉は通す方向に使えず、Dev-B が採った観測は検査へ落とせば判定に使われる**」と理解してください。

### 1.3 質問3 — 「監査の入力」以外の扱いはあるか。待ち行列を短くする効果を記述する枠組みはあるか

**どちらもあります。新設は要りません。**

**(a) 「判定に要する労力を下げる」経路**

第7章は、帯域不足への手段を順序つきで列挙しています。

> - 分割の総量を減らす
> - **判定に要する労力を下げる(レビューパッケージの提示)**
> - 判定できる人数を増やす

**Dev-B の出力は、この2番目に当たります**。判定を代行せず、判定に要する労力だけを下げる位置です。同じ節が「AI による事前審査を合否条件にしない」と書きながらこの手段を認めていることが、両立の証拠です。**標準は「AI が判定を軽くすること」を否定していません。否定しているのは「AI が判定の一部を担うこと」です。**

さらに事前レビューの自動化は、この作業を明示的に AI へ割り当てています。

| 作業 | 担い手 |
| --- | --- |
| 判定基準ごとの充足状況の記入 | AIエージェント |
| 高リスク事項の検出 | 静的解析・AI |
| **意見の内容 / 判定** | **人** |

**実例1(受入基準30件を数えて該当0件を発見)は、この表の1行目そのものです**。判定基準ごとの充足状況を機械的に記入した結果、充足0件が露呈した、という構造です。新しい活動ではありません。**既に標準が AI へ割り当てている作業を、Filetto が実際にやった**というだけです。

**(b) 効果を記述する枠組み**

これも既にあります。Dev-B を「レビュー負荷削減手段」として登録し、その効果測定の記録へ載せてください。第7章の同時保有数の初期値較正が、この記録を参照する形になっています。Filetto の規模で意味のある観測量は次の3つです。

- PO へ到達する前に落ちた件数(Dev-B が反証を成立させ、Dev-A へ戻った件数)
- PO が判定に要した時間と変更規模の比(5.6 が計測を求めているもの)
- **Dev-B が反証を試みて否定できなかったのに、PO が差し戻した件数**(= Dev-B の見逃し)

3番目を必ず取ってください。1番目だけを見ると、Dev-B の効果は常に良く見えます。

**(c) ただし、この経路には標準が予告している危険がある**

5.6.1 が正面から述べています。

> **AIの生成品質が上がるほど、レビューで見つかる欠陥は稀になり、レビューはより形骸化しやすくなります**。品質の向上と監督の劣化は同時に進みます

Dev-B が判定前によく落とすほど、PO が判定で見つける欠陥は稀になります。出現率の低下は見逃し率を 0.07 から 0.30 へ動かします。**Dev-B の導入は、PO の判定を確実に形骸化させる方向へ働きます**。これは副作用ではなく、機構上そうなります。

**したがって Filetto は、Dev-B の常設と 5.6.2(欠陥注入による検出能力の測定)を同時に始めてください**。5.6.2 は「AI によるレビュー層も対象とする」と明記しています。注入する主体は PO、検出を測られる主体は Dev-B です。**AI 層のみを対象にすれば、1名体制でも 5.6.2 の要件は成立します**(成立の検証は応答 A-4)。

**ただし順序に条件が付きます。** 5.6.2 は「**反映の経路を持たない注入を実施してはならない**」と定めています。見逃された類型を自動検査へ反映する先、すなわち G-5 の CI 機構が無い状態で注入を始めると、5.6.2 自身への違反になります。**初版は「Dev-B の導入と同時に」と書きましたが、正しくは「(1) の CI 機構の後」です**(応答 A-4)。

## 2. Dev-B に課すべき作業定義

「壊しにいく」という指示では実行できません。調査 r2 の判定は明確です。役割の名乗りに精度上の効果はなく(MMLU で -3.6〜-5.3pt)、効いているのは外部観測です(+19〜44pt)。**したがって Dev-B へ与えるのは人格ではなく作業手順です**。

次の7項目を義務とします。

### D-1 規則を列挙してから、1件ずつ突き合わせる

- 受入基準・仕様・法定要件を**先に番号つきで列挙**する。列挙を省いて「網羅的に検証せよ」と指示しない
- 列挙した規則1件につき、突合の結果を1件書く。**結果は「該当あり(証跡)」「該当なし」の二値**とする
- 突合の総数と該当数を数値で出す
- 根拠: 調査 r2 の 5.1(仕様の内容を素で与えると30件中27件、計画だけなら2件。誤警報も 33% → 0%)。実例1と同じ構造

### D-2 測定結果を伴わない反証は提出させない

- Dev-B の提出物は、**主張1件につき次の3つを必ず伴う**。伴わない主張は提出物として受け付けない
  - 何を実行したか(コマンド・入力・環境)
  - 観測値(出力そのもの。要約ではない)
  - 代替案(この前提の代わりに何が成り立つか)
- 根拠: 調査 r2 の 5.2(位置・観測値・代替案を返すと +42〜44pt。**代替案を落とすとベースライン近傍へ戻る**)。実例2がこの系統
- **これが Dev-B の中核です**。他の6項目を落としても、これだけは落とせません

### D-3 「懸念がある」を書かせない

- 提出できるのは「**否定できた(証跡つき)**」「**否定を試み、否定できなかった(試行の記録つき)**」の2つのみ
- 「懸念がある」「注意が必要」「〜の可能性がある」は提出物として不成立とする
- 根拠: 3.10.4(意見の様式)が人の意見に課している規律と同じ。**様式を課さないと、反証は感想へ退行する**

### D-4 別セッション・別作業領域で起動し、Dev-A の生成履歴を渡さない

**この項目だけは、標準上の根拠を持ちません。** 初版は 5.8.4 段階「弱」と 3.5.3 を根拠にしていましたが、どちらも掛かりません(応答 A-1)。**案件の裁量措置として採ってください。**

- 作業領域(worktree)とセッションを分ける。Dev-B へ渡すのは**成果物と仕様のみ**。Dev-A の思考過程・作業ログ・「なぜこうしたか」を渡さない
- 根拠は調査 r2 の CCR のみ(F1 24.6% → 28.6%、d=0.52)。**渡すと文脈が合流し、この効果は消えます**
- **禁止事項**: この措置をもって「5.8.4 の段階『弱』を満たした」と記録してはなりません。CCR は**注入欠陥の 71% を見逃す水準**であり、水準の充足として記録させてはならないものです(4-3-1 と同じ理由)

### D-5 Dev-A と Dev-B を往復させない

- Dev-B は Dev-A へ反論しない。**観測を PO へ提出して終了**する
- Dev-A へ戻すかどうかは PO が決める
- 根拠: 調査 r2 の 2.4(同質パネルの有害改訂率 89%)、2.1(討論は自己整合に負ける)。**同一モデル同士の往復は、正しかった答えを壊す方が多数派です**
- これは PO の案(「同じものを2回作らせて突き合わせる構成ではない」)と整合します。**討論構成へ滑らせないための明示的な歯止め**として書いてください

### D-6 成立した反証は、検査へ落とす

- Dev-B が否定に成功した項目は、**回帰テスト・検査スクリプト・突合スクリプトのいずれかへ変換**して G-5 へ載せる
- 変換できないもの(前提の誤りの訂正など)は、仕様側へ書き戻す
- 根拠: 1.2(b) の経路1。**落とさなければ、同じ誤りが次の成果物で再発します**

### D-7 persona 文言を書かない

- 指示に「あなたは批判者です」「敵対的に評価してください」と書かない。書くのは D-1〜D-6 の手順のみ
- 根拠: 調査 r2 の 3(persona は効果なしか負の効果。MMLU -3.6〜-5.3pt。「正しくあること」より「正しく聞こえること」を優先させる)
- **Dev-B という名称は、PO が手順の束を指すための呼び名にとどめてください。モデルへ名乗らせないでください**

### 課さないと決めたこと(明示)

- **Dev-B に合否の意見を書かせない**(1.2(a))
- **Dev-B の結論を2回取って一致を見る運用を採らない**。根拠: 調査 r2 の 4.1(9判定者で実効2.18票、合議の利得 0.2pt)。「2回とも同じだったから正しい」は成立しません
- **Dev-B に Dev-A の実装を読ませてからテストを書かせない**。5.8.4 の趣旨に反します

## 3. 順序判断への評価

PO の計画: (1) 判定前に落とす CI 機構 → (2) PO が成果物を作らない体制へ → (3) Dev-A / Dev-B 分割。

**この順序は正しく、懸念も正しい。ただし1点だけ修正します。**

### (1) が先である根拠

Dev-B の反証を落とす先が G-5 です(D-6)。**落とす先が無い状態で Dev-B を常設すると、発見が一過性の材料で終わり、再発を止めません**。また 5.6.2 の測定も、決定論的な検査層が無ければ「Dev-B が見逃したのか、そもそも検査対象でなかったのか」を切り分けられません。(1) は (3) の前提です。

### (2) が (3) より先である根拠

5.2 が次を要求しています。

> AI が生成した成果物は、**その生成を指示した者以外の人間が確認する**

Filetto は G-6 が未達です。3.5.2 の表が述べるとおり、「作成指示者 × 独立レビュア」は**1人での達成が不可能**であり、欠けるのは独立性ではなく**目的そのもの**です。この状態で PO 自身が成果物を作ると、確認する人間が生成を指示した者と一致し、**未達がさらに深まります**。

したがって「PO が作らない」は、Filetto に残された数少ない実効的な分離です。**Dev-B を足しても、この分離は1ミリも回復しません**(1.1(c)(d))。回復しないものを先に足すと、回復したように見える記録だけが残ります。**(2) が先です。**

### (3) を先に立てたときに起きること(PO の懸念の裏づけ)

PO の言う「止める機構が無いまま作る速度だけ上がる」は、5.6.1 の機構そのものです。Dev-B が事前によく落とすほど、PO が判定で出会う欠陥は稀になり、**判定の基準そのものが移動します**。止める機構(G-5)が無い状態でこれが進むと、速度の向上と監督の劣化が同時に起きます。**PO の懸念は標準の条項に裏づけられています。順序を守ってください。**

### 修正する1点 — 「実測の義務」は先取りしてよい

分けるべきは2つです。

| 対象 | 扱い |
| --- | --- |
| **Dev-B をレーンとして常設すること** | (1)(2) の後。PO の計画どおり |
| **D-1(規則の列挙と1件ずつの突合)と D-2(測定結果の添付義務)** | **今日から Dev-A の作業手順の中で実行してよい** |

#### 4-2-1. 仕様に書いた前提について、観測で確かめたか否かを区別する

**何が書かれていないか**

第6章テンプレ1の「前提・依存」欄が求めるのは、次だけです。

> この仕様が依存する前提。案件層コンテキストへの登録済み ID を併記

テンプレート側も「前提 / 崩れたときの影響」の2列です。**その前提を実際に観測で確かめたのか、書き手の想定にすぎないのかを区別する欄がありません。**

**書かないと何が起きるか(Filetto で現に起きたこと)**

実例2がこれです。PO が「ExStruct と Docling は位置を返す」を**未実測のまま**受入基準の前提として書きました。仕様は G-2 / G-4 を通ります。誰も止めません。**前提が誤っていることは、実装段階で5経路を実際に動かして初めて判明しました。**

これは Dev-B の有無と関係のない失敗です。段階「中」のテスト独立性(実装より先にテストを書く)を完璧に守っても捕まりません。**誤った前提から書かれた受入基準は、その前提の下では正しいテストを生みます。** 検証の独立性は、前提の誤りを検出しません。

さらに Filetto は G-6 が未達で人が1名です。したがって**仕様の前提が一度も他者に触れられないまま実装まで到達する経路が、標準に適合したまま成立します**。

**既存のどの条項と接続するか**

標準は同じ規律を、既に別の場所へ書いています。前提の台帳(テンプレ10)は次を課しています。

> **充足状態を自己申告で決めないでください**。観測した事象の欄が空のまま AC-0 とした行は、記録として成立していません

**標準が置いた前提には「観測した事象」を要求し、案件が置いた前提には要求していない** — これが非対称です。しかも台帳自身が「案件が独自に置いた前提は機能仕様書の『前提』欄で扱う。この台帳へ混ぜないでください」と、案件側の前提を明示的に切り離しています。**切り離した先に、同じ規律がありません。**

接続先はほかにもあります。

- **5.8.1(未検証の入力として扱う)** — AI が書いた仕様の前提も未検証の入力である。ただし「誰が、何をもって検証するか」が前提については定まっていない
- **G-2 基準3** — 「暗黙の前提が案件層コンテキストに登録済み」/ 確認方法「コンテキスト基盤の案件層の差分確認」。**確認しているのは登録の有無だけである**。「ExStruct と Docling は位置を返す」は、**基準3を満たしたうえで誤っていられる**
- **G-2 / G-4 の未確定事項欄** — `NEEDS CLARIFICATION` の解消を通過条件にしている。**未確定であることは検査されるが、確定していると書かれた前提が実は未検証であることは検査されない**
- **ADR-0026 の制度上の位置** — 根拠水準マークは `community/` 配下の**執筆規約**であり、標準が案件へ課す**要求事項ではない**。自分に課しているものを、規格として他組織に課していない
- **ADR-0026(根拠水準のマーク)** — 本プロジェクトは自分自身に「実証を欠く記述は暫定 EV マークで開示する」を課している。**標準は、自分に課している規律を案件へ課していない**

**根拠の水準**

- **単一事例**(Filetto の実例2)。ただし失敗様式そのものは一般的である
- **実証あり**(調査 r2 の 5.1)— 仕様の内容を素のテキストで与えると30件中27件のバグを捕捉、内容なしで計画だけを立てさせると2件。誤警報は 33% → 0%。**前提の中身を明示的に扱うことの効果量は大きい**
- ただし上記の実証は「テストへ接地させる効果」であり、「前提の検証状態を記録させる効果」を直接測ったものではない。**この転用には飛躍がある。条項化する場合は暫定として扱うべきである**

**書く価値の判断**

信頼性の観点で書く価値があります。**プロセスの目的は手戻りを減らすことであり、誤った前提は最も高い位置で発生して最も遠くまで伝播します。** 実装段階まで生き残った誤った前提は、受入基準・実装計画・テストのすべてを巻き込みます。実例2はこの経路をたどりました。前提1件につき「確かめたか」を書く費用に対して、見逃しの帰結が大きく非対称です。

#### 4-2-2. AI が提出する指摘に、様式を課す

**何が書かれていないか**

標準は 3.10.4 で**人**の意見の様式を定めています。しかし **AI が提出する指摘の様式は、どこにも定めていません**。事前レビューの自動化は「高リスク事項の検出 = 静的解析・AI」と割り当てていますが、その出力が何を含むべきかを規定していません。

**書かないと何が起きるか**

指摘が感想へ退行します。「〜の可能性がある」「注意が必要」だけが並ぶ提出物は、読み手に検証の手がかりを与えず、**それでいて「AI がレビューした」という記録として残ります**。第7章が危惧する「偽陰性が事前審査を通過したという記録として残る」と同じ構造が、様式の欠如からも生じます。

Filetto では、実例1・実例2がいずれも**測定結果を伴っていた**から機能しました。30件を数えた件数があり、5経路を動かした観測がありました。**この2件がうまくいったのは、たまたま様式が満たされていたからです。標準は、それを再現させる要求を持っていません。**

**既存のどの条項と接続するか**

- **3.10.4(意見の様式)** — 人へ課している規律の対になる。人には様式があり AI には無い、という非対称は説明できない
- **5.8.1(未検証の入力)** — AI の指摘も未検証の入力である。検証できる形で出さなければ、受け手は検証できない
- **第7章(AI の指摘は注意を向ける材料として提示する)** — 「材料として提示する」の中身を定義する位置。現状は「材料」の要件が空である
- **事前レビューの自動化** — 高リスク事項のラベル付与の隣に置ける

**根拠の水準**

- **実証あり、効果量が大きい**(調査 r2 の 5.2)— 位置・観測値・代替案を返す構成で Qwen-14B +44pt、Llama-8B +42pt。**散文と JSON の差は 0〜2pt であり、効いているのは書式ではなく値**。とくに**代替案を落とすとベースライン近傍へ戻る**
- **実証あり**(調査 r2 の 5.3)— 追加フィードバックなしの自己批判は +0.5pt。実行フィードバックを伴うと 8.97%、その上で批判を書かせると 11.76%。**順序が逆では伸びない**
- 単一事例ではない。複数モデル・複数課題で検証されている

**書く価値の判断**

信頼性の観点で書く価値があります。**この要求を課すか課さないかで、AI の指摘の実効性が +0.5pt の系統と +42〜44pt の系統に分かれます。** 標準が「AI に検出を担わせる」と書きながら様式を定めないことは、効果のない側を既定にすることと同じです。なお実証が示すとおり、**書式(JSON か散文か)を規定してはなりません。規定すべきは含めるべき値です**。

#### 4-2-3. 分けたエージェント同士を往復させない

**何が書かれていないか**

5.8.4 は「エージェントを分けたことをもって独立性を確保したとみなしてはなりません」と書いています。これは**分割を独立性と誤認することへの禁止**です。しかし、**分割したエージェント同士を討論・往復させたときに品質が劣化する**ことは書かれていません。

**書かないと何が起きるか**

案件は自然に討論構成へ滑ります。「AI を2体立てたのだから、意見を突き合わせて合意させよう」は、標準を読んだ実務者が到達する素直な発想です。5.8.4 を読んでも止まりません。**5.8.4 は「合意しても独立性ではない」と読めるだけで、「合意させると悪化する」とは読めないからです。**

Filetto の PO は現時点で滑っていません(「同じものを2回作らせて突き合わせる構成ではない」と明言している)。**しかしそれは PO の判断であって、標準がもたらしたものではありません。** 次の案件が同じ判断に至る保証はありません。

**既存のどの条項と接続するか**

- **5.8.4** — 同じ節の続きに置ける。「分けても独立性ではない」の次に「分けたうえで往復させると悪化する」が来る順序は自然である
- **5.8.1** — AI の出力どうしを突き合わせた結果も、依然として未検証の入力である

**根拠の水準**

- **実証あり、効果の向きが明確**(調査 r2 の 2.4)— Llama-3.1-70B / MATH-hard で**同質パネルの有害改訂率 89%**。誠実な異質ピアを1体入れると 35% へ低下。**4モデル系統 × 3ベンチマークで符号が一貫**
- **実証あり**(調査 r2 の 2.1)— 計算量を揃えると討論は自己整合に負ける(GSM8K で自己整合 95.67% 対 MAD 63.87〜94.93%)
- **実証あり**(調査 r2 の 4.1)— 9判定者の実効独立票数 2.18、合議の利得 0.2pt。**「2者が一致したから正しい」は成立しない**
- 単一事例ではない

**書く価値の判断**

信頼性の観点で書く価値があります。**有害改訂率 89% は、正しかった答えが議論によって壊れる方が多数派だったという意味です。** 標準が明示的に止めなければ、案件は「AI を増やすほど良くなる」という直感に従います。**効果がないのではなく、負に効きます。** 課さない選択は、劣化を既定にすることです。

なお、これは「AI を複数立てるな」ではありません。**往復させるな**です。それぞれが独立に観測を採って人へ提出する構成は、4-2-2 の系統に乗ります。

- **機械化できる**。内容に踏み込まず対応の有無だけを見るため、G-2 基準1 と同じく決定論的に検査できる。第7章が禁じる「AI による事前審査」に当たらない

**なお、4-2-1 と 4-2-4 は別々に書く必要があります。** 4-2-4 は「対応があるか」を数え、4-2-1 は「その前提を確かめたか」を問います。**実例2(未実測の前提)は、4-2-4 の数え上げでは捕まりません** — 前提に対応する受入基準は存在していたからです。両方が要ります。

## 5. Filetto の運用として採らない案(記録)

第4節は標準の側の判断です。本節は Filetto の運用の側で、検討したうえで**採らないと決めた**ものです。

| 案 | 却下の理由 |
| --- | --- |
| Dev-B を新ロールとして D-0 体制図へ書く | 人が1名である以上、3.5.3 の人の単位で分離しない。体制図に実態のない分離が残る(4-3-2 と同根) |
| Dev-B を D-0「8. 独立性の確認」の該当者欄へ書く | 同欄が問うのは「開発ラインから独立した出荷判定者」「案件に関与していない点検の実施者」「監査の窓口」。**Dev-B はいずれでもない**。満たせない項目は空欄にせず未達として記録する、という同欄の指示に従う |
| Dev-B を G-6 未達の代償措置として登録する | 3.5.2 が代償措置を認めるのは「開発ライン × 出荷判定者」の1組のみ。**この例外を他の禁止の組み合わせへ広げない**と明記されている |
| Dev-B の「否定できなかった」を G-5 の追加基準にする | 第7章が禁じている。偽陰性が通過記録として残る |

| Dev-B に Dev-A の実装を読ませてからテストを書かせる | 5.8.4 の趣旨に反する |
| 標準の改訂を待ってから (3) を始める | 4-2 の4件は Filetto の運用を止めない。**第2節の D-1〜D-7 は、標準の改訂を待たずに今日から作業手順として書ける**。とくに D-1 は 4-2-4 の内容を案件側で先に実行するものであり、条項の成立を待つ理由がない |
