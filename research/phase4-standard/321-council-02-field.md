# #321 会議体 02 — 現場(1〜3 名 + AI エージェント体制の実務者)の意見書

- 作成日: 2026-10-23
- 立場: 準拠テンプレート(pit-in-template)を実際に使う側。AI エージェント(Claude Code 等)が実装し、人が判定する体制で、**判定 1 件あたりの人の操作回数・待ち時間・やり直しを数える**役
- 入力: `321-council-00-brief.md`、`gate-record-00-internal-inventory.md`(4 章・8 章)、`gate-record-02-github-mechanics.md`、`gate-record-03-industry-practice.md`、テンプレートの現物(`template/templates/04-gate-record.md`、`template/.claude/skills/gate/SKILL.md`、`gates/G-4.md`・`G-6.md`・`G-7.md`、`reference/recording.md`、`template/.github/rulesets/*`、`template/.github/CODEOWNERS`、`template/.github/PULL_REQUEST_TEMPLATE.md`)
- 根拠水準: 本文のステップ数は、テンプレートの手順と GitHub の規則を読んで導いた**見積り**であり、実測ではない(E3)。現場の態度を述べた箇所は意見(E4)。7 章にまとめる

## 1. 先に結論

- **ボトルネックは帳票ではなく、帳票を基底へ届ける儀式である**。判定 1 件につき「ブランチ・複製・手入力 9 欄・push・PR・承認依頼・承認・ブランチ更新・再承認・マージ」が本体 PR の外にもう 1 周ある。2 名体制の G-6 で人の操作は本体 3 回に対し記録 PR 7 回、規制業では本体 6 回に対し記録 PR 10 回(2 章、E3)
- **記録 PR のやり直しは確率ではなく必ず起きる**。「記録の作成 → ラベル → 事務」の順序(`template/.claude/skills/gate/SKILL.md:65`)で記録 PR を本体より先に開くと、本体がマージされた時点で記録 PR の基底が古くなり、`strict_required_status_checks_policy` がブランチ更新を要求し、`dismiss_stale_reviews_on_push` が承認を落とす(`template/.github/rulesets/team.json:13`・`22`)。更新 → CI → 再承認が記録 PR に構造的に組み込まれている(E3)
- **現状の手続は、中身を見ない承認を制度として要求している**。2 名体制では、本体の作成を指示した A が、B の G-6 判定記録 PR の承認者になるしかない(作者 B は自分の PR を承認できない)。A が見るべき中身はそこに無い。規制業では同じことが 2 回(承認と再承認)起きる。「中身を見ずに承認」を抑えたいなら、まず制度が強いる空承認を無くすのが先である
- **手入力の属性は、現場では必ず後追いになる**。判定日時・判定者・対象・D-0 の版は、人が打つ値であり、記録 PR が詰まれば「あとでまとめて」書かれる。打った日時は判定の時刻ではなく記入の時刻になる。これは `label-mailbox.md:230` が禁じる「記録の後追い」を、手続のほうが生んでいる状態である
- **Q1 への答え**: ADR-0036 決定1「記録の作成をもって成立」は維持する。置き換えるのは「記録 = `docs/gates/` のファイル」というテンプレートの置き方である。成立要件は「Who / When / What / Outcome がシステム付与の値で固定され、判断の中身を判定者本人が同時に書いたこと」へ言い換える。ファイルは、そのうち PR に紐づかないゲート(G-7・G-8・SG)と、規制業の変更ごとの記録(G-7 で生成して固定)に残す
- **現場が「これなら残す」と言える最小の形**(5 章): G-6 は承認レビュー + 本人の挙動要約だけ。G-2・G-4 は仕様 PR への判定者のレビュー(承認、または作者本人なら宣言コメント)で、`commit_id` が受入基準の版になる。G-7 は従来どおりファイル 1 枚だが、その PR に出荷範囲の承認イベントの写し(`evidence.json`)を同梱して固定する。**判定 1 件あたりの記録専用の PR を 0 本にする**
- **現場の立場からも採らない案**(6 章): 承認ボタンだけで成立(挙動要約なし)、AI が起案した挙動要約を人が OK するだけ、記録を本体 PR へ同梱して判定者が push(2 名体制で最後の push 者が判定者になり承認が数えられない)、bot の `exempt` bypass、承認の失効を切って往復を減らす、G-7 でまとめて手で日時を打つ
- **「重い手続は記録を消す」は現場の実感と一致する**。ただし 236b の 7.7 倍(`236b:326`)は別領域の単一事例(E2)で、本件の定量実証は無い。本意見書で主張するのは「手続が記録の欠落と後追いを**構造的に**生む」ことまでである

## 2. 現状の手順 — 3 構成 × G-4 / G-6 / G-7 の人の操作のステップ表

### 2.1 数え方

- 「人の操作」= 人が手を動かす 1 回(欄を埋める、ボタンを押す、コマンドを打つ)。AI の担い手が行える作業(ブランチ作成、様式の複製、材料の表の起こし、push、PR 作成、ラベル)は 0 に数える
- 「待ち」= CI の完走、または別の人の応答を待つ回数
- 判定そのもの(差分を読む、仕様を読む、欠落を読む)は数えない。それは残すべき 1 回である
- 登場人物: A = 作成を指示した者(AI に実装させた人)、B = 独立レビュア / 価値責任者 / 出荷判定者、C = 2 人目の承認者(規制業)。CODEOWNERS は既定の `* @OWNER`(`template/.github/CODEOWNERS:10`)で、OWNER = C とする
- 前提: ルールセットはテンプレートどおり。ソロ = `checks-only.json`(承認なし、`strict: false`)、2 名 = `team.json`(承認 1、stale 失効、最後の push の承認、strict)、規制業 = `regulated.json`(承認 2、コードオーナー、署名、strict、`d0-check`)
- 記録 PR はスキルの手順どおり作る。`SKILL.md:12` が「判定記録をリポジトリへコミットして残す」と言い、ルールセットが既定ブランチへの直接 push を止める(`README.md:23`)ため、記録はすべて PR を経る。G-6 の標準書式では集約が承認レビューだけで数える(`aggregate-evidence.mjs:509`)が、スキルの表は G-6 にも補助ファイルを割り当てており(`SKILL.md:31`)、現場(と AI の担い手)は「作れ」と言われたものを作る。**機械が要らないと知るのは集約を読んだ後**である

- **コミット識別子の罠**: 判定者が仕様 PR の head の SHA を記録に書くと、squash マージで既定ブランチに同じ SHA は残らない(02 §8)。既定ブランチの SHA を書くには、仕様 PR をマージしてから記録を書く。すると「記録の作成 → 事務(マージ)」の順序が逆になる。現場はどちらかの規則を破る。機械は版の識別子を検査しない(IMPL-0107 `check=manual`)ので、破っても出荷までは分からない

### 2.4 G-7 出荷判定

| 構成 | 人の操作 | 待ち |
| --- | --- | --- |
| ソロ | 集約の実行(AI)、欠落を読む(—)、9 欄 + 未消化の節 1、push 1、マージ 1、タグ push 1 | **4** | CI 1 |
| 2 名(出荷判定者 B) | 上記 + A の承認 1(+ 基底が進めば更新 1・再承認 1) | **5〜7** | CI 1〜2、人 1〜2 |

- G-7 は出荷ごとに 1 回なので、往復の総量は小さい。**ここは現場も PR で構わない**。問題は出荷の範囲内の G-6・G-4 の記録が出荷直前にまとめて書かれる(2.5)ことのほうである
- 2 名体制で G-7 の記録を承認するのは A、つまり範囲内の変更の指示者である。ADR-0066 が「G-7 の記名者は指示者でも G-6 の承認者でもない」と求めるのは記名者であって承認者ではないため規則には触れないが、承認の意味は無い

### 2.5 現場で実際に起きること(E4、意見)

- 記録 PR は**本体の後回し**になる。本体が動かなければ事業が止まるが、記録が無くても出荷判定まで何も止まらない(`gate-criteria.md:72` の検出は G-7)。結果、記録は出荷直前に N 件まとめて書かれ、「判定日時」欄には記入日か、記憶で遡った日が入る。**手入力の日時は、判定の時刻を記録しない**
- まとめ書きの N 件は 1 本の PR に入る。承認者 A は N 件の記録をまとめて承認する。1 件ごとの承認より、さらに見ない
- 「ブランチを更新」を誰が押すかで承認が無効になる体制では、現場は**先にマージしてから記録を書く**ことを覚える。順序の規則(`SKILL.md:65`)は守られなくなる。守られない規則は、守られている規則の信用も下げる
- AI の担い手は「全ゲートで作成」(`SKILL.md:3`)に従い、G-6 でも記録ファイルを起こす。集約が承認レビューで足りると扱うことを知らない。人は AI が出した手順に乗る。**テンプレートが求める量と、機械が要る量の差を、現場は埋められない**

## 3. Q1〜Q7 への回答

### Q1 成立要件 — 決定1 を維持し、「記録」の定義を言い換える

- 維持する: 「記録の無い判定は未判定」(ADR-0036 決定1、`gate-criteria.md:57`)。現場にとってこの原則は守りやすい。守りにくいのは原則ではなく置き方である
- 置き換える: 「記録 = テンプレ4 のファイル」という、テンプレート独自の置き方(`SKILL.md:12`「置き方はテンプレート独自」)。標準本文は媒体を規定していない(00 §8.3)ので、標準側の決定1 は動かさずに済む
- 成立要件の言い換え案(現場の言葉): **「誰が・いつ・何に・どちらの結果か」を、判定者が打ち込んだ値でなくシステムが付けた値で固定し、「何を見てそう判断したか」を判定者本人がその場で書いていること**。ファイルか承認イベントかは問わない。G-6 では承認レビュー(承認者 ≠ 指示者、`commit_id`、`submitted_at`、本人の挙動要約)が既にこれを満たす(`gate-criteria.md:480`)
- 理由(信頼性): 手入力の属性は自己申告であり、後から打てる(01 §「同時性」)。ADR-0036 が記録を要求した理由は「自己申告を排す」(`:61`)である。**手入力の日時は決定1 の趣旨に反する**。承認イベントのほうが決定1 に忠実である
- 現場が維持を求めるもの: 「記録が無ければ未判定」を機械が出し続けること(`next.mjs`、集約の欠落)。これが無いと、記録はさらに書かれなくなる

### Q2 属性と判断の分離 — 認める。人が書く欄の受け皿は「判定の瞬間に押すもの」と同じ場所

- 認める。属性(判定者・日時・対象・結果・D-0 の版)は機械が転記し、判断の中身(挙動要約、確認していない事項、差し戻し理由と再提出の期限、持ち込まないもの)は人が書く
- 受け皿は、**判定者が判定の瞬間に操作する場所の本文**である。別の場所に書かせると、後追いになる
  - G-6: 承認レビューの本文(現行どおり)。1 行目を `G-6: 通過` の宣言にし、続けて挙動要約。差し戻しは変更要求レビューの本文に `G-6: 差し戻し / 基準 2 / 期限 YYYY-MM-DD`。2 値の語彙(`gate-criteria.md:78`)と、差し戻しに要する項目番号・期限(`:85`)の置き場がこれで決まる
  - G-2・G-4: 仕様 PR への判定者のレビュー本文。判定者が仕様の作者でもある場合(ADR-0060 `:58`、ソロ)は承認できないので、同じ PR へのコメント形式のレビュー本文に同じ宣言を書く。自己申告であることは変わらないが、**時刻と対象(`commit_id`)はシステムが付ける**。ファイルより弱くならない
  - G-7・G-8・SG: PR に紐づかない。ファイルのまま。ただし G-7 の PR を 1 本にまとめる(Q3)
  - 停止の解除・例外承認: 基底ブランチの記録のまま(`ci-gates.md:146`・`155` は設計意図。現場も同意する。頻度が低く、判定される側が材料を用意できない形に価値がある)
- 人が書く欄を Issue コメントや別ファイルに置く案は採らない。Issue は PR と 1 対 1 でなく、別ファイルは記録 PR を復活させる
- ADR-0040 との関係: 属性を承認イベントへ移すのは「欄を落とす(omit)」ではない。欄は残り、書き手が人から機械に変わる。「標準と逆の指示」でもない。**第三の形「転記」として ADR で位置づける**ことを求める(00 §8.3 が未決と指摘した点)
- 現場の条件: 転記した属性を、人が**上書きできない**こと。転記の出力(evidence.json)を手で直せるなら、転記の意味が無い。集約が API から引き直した値と一致しなければ欠落にする(現行の「記録と基底の実体の不一致」の検査と同じ線)

### Q3 置き場と固定 — ゲートごとの固定は求めない。G-7 でまとめて固定する。Bot は「転記」に限って認める

- ゲートごとにファイルを基底へ入れることは求めない。2 章のとおり、これが記録 PR を 1 件ごとに生む
- G-7 でまとめて固定する。出荷判定者が集約し、`evidence/evidence.json` と G-7 の判定記録を**同じ PR**で基底へ入れる。写しに含める値は、レビュー id・`state`・`commit_id`・`submitted_at`・`user.id`・`user.login`・本文・PR 番号・`merge_commit_sha`(02 §9.1 の最小の組)。この PR は現行でも存在する(2.4)ので、往復は増えない。現行の `ship-evidence.yml` は成果物を Actions に置くだけでリポジトリへコミットしない(`ship-evidence.yml:94`〜`103`)。ここを変える
- 「出荷の範囲で追加された判定記録」の数え方(`aggregate-evidence.mjs:371`〜`375`)は、ファイルの追加から「範囲内の PR の承認イベント + 範囲内に追加されたファイル」へ変える。G-6 の件数は PR の数で機械が決められる
- Bot による固定は、**転記**(承認イベントの写しを基底へ置く)に限って認める。bypass は `pull_request` モード、`exempt` は不可(02 §9.3 案 B の結論に同意。監査に出ない actor で記録を固定するのは目的と矛盾する)。Bot が承認レビューを付けること、結果欄を書くことは認めない(ADR-0028 決定7)
- ただし現場の実情として: 無料プランの私有リポジトリではルールセット自体が使えない(`template/README.md:115`)。そこでは bypass の問題は生じず、出荷判定者が直接 push する。Bot の仕組みは「ルールセットがある構成だけに要る追加の装置」であり、**ソロの現場には要らない**。装置を増やすこと自体が #270 の型(装置が製品を越える)に近づくので、まず人が G-7 の PR で固定する形を既定にし、Bot は選択肢に留める
- 規制業の変更ごとの G-6 の記録(`deliverable-templates.md:503`)は、**G-7 の時点で承認イベント 2 件と本文 2 件から生成し、同じ G-7 の PR で固定する**。人が書く行(安全性の評価者・評価の記録の所在)は `docs/safety/` の記録だけのコミット(`gates/G-6.md:35`)で既に PR 無しが許されている。「変更ごとに記録ファイルがある」は保たれ、属性は同時性を持ち、手順 9〜18 が消える

### Q4 PR に紐づかないゲート — 「仕様 PR への判定者のレビュー」と「G-7 の PR」の 2 つに集約する

- G-2・G-4: 判定の対象は仕様の版である。仕様は PR で入る。判定者のレビューの `commit_id` が、そのまま「確定した受入基準の版のコミット識別子」になる。**2.3 の SHA の罠が消える**(squash 後も `refs/pull/N/head` で到達できる。02 §8。保証が無い点は Q5)
- 判定者が仕様の作者でもある場合: ブランチ保護は作者の承認を止める。折り合いは「承認」でなく「宣言」で付ける。作者本人のコメント形式のレビューに `G-4: 通過` を書く。集約は承認の状態でなく宣言の行を読む。ADR-0060 が「別の人による確認ではない」(`:58`)と言うとおり、これは独立した確認ではないが、判定の存在と時刻の記録にはなる。**ソロの記録に求められるのは「後から日時を偽れない」ことだけ**であり、それはファイルより強い
- G-1: 企画書の PR(あれば)への事業決裁者のレビュー。無ければファイル。頻度が低く、現場は PR でよい
- G-7・G-8: ファイル。1 出荷 1 本の PR。G-8 の「実行環境の承認操作」(`qms-document-control.md:41`)は属性の記録になるが、決断の記録(確認していない事項・異議・上申)は人の文であり、G-7/G-8 の PR に置く
- SG: ファイル。会議体の判定であり、頻度が低い
- 現場からの注文: **受け皿を 3 つ以上に増やさない**。「G-6 はレビュー本文、G-4 は Issue、G-7 はファイル、G-8 は環境の承認」のように散ると、AI の担い手が迷い、人が探せない。「PR に紐づく判定は PR のレビュー本文、紐づかない判定は G-7 の PR」の 2 つに揃える

### Q5 保全 — 標準に書く。ただし現場が運用できる項目に絞る

- 書く章: 第5章 QMS 文書管理(`qms-document-control.md`)の「アカウントと実在する人物の対応表」(`:44`)、「承認の対象と意味」(`:45`)の隣。附属書I の要件⑦(`adoption-guide.md:498`)に検査項目として足す
- 現場が運用できる条件(標準に要求事項として書いてよいもの)
  - 承認・判定の時点の名簿にアカウントと `user.id`(数値)を持つ。login は再取得される(02 §1.6)。名簿は既にある(`people[].accounts[]`)ので、欄を 1 つ足すだけ
  - 承認の意味の定義: レビュー本文 1 行目の宣言 `G-N: 通過 / 差し戻し`。SOP でなく、テンプレートの PR 雛形とスキルが書き方を持つ
  - `dismiss_stale_reviews_on_push` と `require_last_push_approval` を有効にする(現行どおり)。失効の粒度は #296
  - 出荷ごとに承認イベントの写しをリポジトリへ固定する(Q3)。これが**現場で唯一実行できる保全**である。監査ログのストリーミングは Enterprise 限定で、180 日(02 §3)はソロ・2 名の現場には無関係な数字になる。リポジトリに固定した写しは、リポジトリと同じ寿命を持ち、アーカイブで凍結できる
- 現場が運用できない条件(標準に要求事項として書かない)
  - 監査ログのストリーミング・定期エクスポート(Enterprise か、人手の定期作業。ソロでは回らない)
  - GitHub App による固定(鍵の管理が記録の信頼性の上限になる。02 §9.3)
  - これらは規制業(軸C)のテーラリングの手引きに置く
- GitHub 以外への一般化: 標準は「システムが付けた属性 + 対象への固定 + 承認者 ≠ 指示者 + 失効」を要求事項として書き、GitHub / GitLab / Gerrit のどの操作がそれに当たるかの対応表はテンプレートが持つ。Gerrit の `Reviewed-by` footer や GitLab の `bypass_reason` は対応表の行であって、標準の条項ではない

### Q6 形骸化の抑止 — 制度が強いる空承認を消すことが第一。次に小ささ、宣言、抜き取り

- 第一: **制度が要求する空承認を無くす**。2 章の記録 PR の承認(A が B の記録を承認)は、「中身を見ない承認」を毎回練習させる。承認疲れ(03 §6.2、93% 承認)は承認の総数で起きる。意味の無い承認を 1 件減らすことは、意味のある承認を 1 件守ることと同じである
- 第二: 変更の小ささ(ADR-0058、03 §8.4)。現場で効くのはこれだけと言ってよい。AI が出す 1,000 行の PR は、どんな様式を課しても読まれない
- 第三: 宣言(挙動要約)を本人が書く。形の検査(8 文字、定型句の除外)は維持する(EV-0083)。現場は「8 文字書けば通る」ことを知っているが、**書く瞬間に差分を思い出す**効果はある(E4)。AI に起案させた文を人が貼る形だけは、この効果を消す
- 第四: 情報としての提示。集約の品質レポートに、承認までの時間と差分の行数を**閾値なしで**並べる(02 §7 の計測できる値)。閾値を置かないのは、実証が無い(Waydev の 10% / 25% は製品の目安)ためと、閾値を置けば最短経路が「閾値の直上で承認」になる(ADR-0059 `:30` と同じ型)ため
- 第五: 内部監査の抜き取り(現行)。機械で中身を判定しない限界は、集約の出力に「機械が見たのは形だけ」と毎回出す(現行の `04-gate-record.md:100` の文を品質レポートにも出す)
- 現場からの反対: 承認の回数を増やす案(bot の事前承認、AI レビューを必須チェックに)は採らない。回数は注意を薄める

### Q7 ツール依存の吸収 — 「意味論は標準、媒体はホスティング」で足りる。ただし「事象が属性を持つか」を基準に書く

- ADR-0036 が Issue のクローズを却下した理由は「ツールを変えると成立要件が変わる」(`:101`)。現場の言葉で言い直すと、**Issue を閉じる操作は誰にもいつでもでき、何に対して閉じたかを持たない**。承認レビューは「その SHA に・その人が・その時刻に押した」ことをシステムに残す。違いは「ツールか否か」ではなく「事象が Who / When / What を持つか」である
- 整理: 標準は「記録に要る属性と、それが自己申告でないこと」を書く。ホスティングのどの事象がそれを満たすかはテンプレートが宣言し(`process.config.json` か対応表)、集約がその宣言どおりに読む。ホスティングを変えたら対応表を変える。成立要件(属性の集合)は変わらない
- これで足りる理由: 現行の D-0 の記録が既に同じ形である(`deliverable-templates.md:338`「要求事項1 を所有者定義による承認、要求事項2 をマージ日時…で満たす」)。先例がある
- 現場の注文: 対応表が無いホスティングでは「承認イベントは記録にならず、ファイルで残す」へ**自動で倒れる**こと。対応表の無い状態で承認だけ数える構成を作れないようにする(構成の検査)
- QMS 対応表(`qms-document-control.md:37`〜`41`)と第4章 `:66` の食い違い(00 §2.8 注)は、この整理で解ける。「PR 承認とマージ」のうち、承認が成立要件(属性を持つ事象)、マージは事務(属性を持たない状態遷移)である。対応表の語を「PR 承認」に揃える

## 5. 現場が「これなら残す」と言える最小の形 / 「これでは残さない」形

### 5.1 これなら残す

- **G-6**: 承認ボタン + 本文 1 行目 `G-6: 通過` + 自分の言葉の挙動要約 1〜2 文。それだけ。差し戻しは変更要求 + `G-6: 差し戻し / 基準 N / 期限 YYYY-MM-DD`。人の操作 1 回。判定の瞬間に、判定の場所で、判定者が押す
- **G-2・G-4**: 仕様 PR に判定者が同じ形のレビュー。承認できない立場(作者本人)ならコメント形式で同じ宣言。対象の SHA は打たない(レビューの `commit_id` が対象)。人の操作 1 回
- **G-7**: 集約を AI が実行し、欠落が 0 になったら、出荷判定者が様式の人の欄(確認した項目・未消化・署名の意味の確認)を書く。属性(範囲・日時)は機械が埋める。承認イベントの写しを同じ PR に入れる。1 出荷につき PR 1 本、人の操作 3〜4 回。**これは今と同じ量**であり、現場は受け入れている
- **G-8・SG・停止の解除・例外承認**: 現行のファイル。頻度が低い
- 様式の欄: 人が打つ欄は「判断の中身」だけ。判定者名・日時・対象・D-0 の版・区分の確定者は、機械が転記するか、PR 本文の既存の欄(`確定した者:`)から読む。**打つ欄を 9 から 2〜3 にする**。236b の 16 → 7 欄(E2)と同じ向きである
- 機械が出し続けるもの: 「記録が無い = 未判定」の表示(`next.mjs`)、G-7 の欠落。これが無いと最小の形でも書かれなくなる

### 5.2 これでは残さない(省略する・後で書く)

- 判定 1 件ごとに、判定者以外の承認が要る PR を立てる形。承認者は「見るものが無い承認」を押すことになり、**押す側が先に形骸化する**
- strict policy の下で、本体より先に開く記録 PR。更新・再承認が必ず要る形は、現場では「本体をマージしてから、あとで」になる。あとで書く記録の日時は判定の時刻でない
- 判定者が、GitHub が既に知っている値(氏名・日時・PR 番号・SHA・D-0 の版)を打ち直す様式。打ち直しは誤記と後追いの源であり、裏づけにならない(Issue 本文の指摘に同意する)
- 2 人が 1 ファイルを順に編集する様式(規制業の 2 人目の行)。push の順で承認の有効性が変わる仕組みの上では、現場は順番を調整する作業を「記録」より先に覚える
- 判定の対象 SHA を、判定者が自分で選んで書く様式(G-4)。squash 後に消える SHA か、マージ後の SHA かを現場が決められない

## 6. 現場の立場からも採ってはならない案と理由

| 案 | 現場が楽になる点 | 採らない理由 |
| --- | --- | --- |
| 承認ボタンだけで成立(挙動要約なし) | 操作 1 回で済む。本文を書かなくてよい | 「押した」は記録だが「見た」の痕跡が無い。コメントなしレビューは LGTM スメルが 3.5 倍、承認後コミットが多い(03 §5.3、Gön ら)。現場で最も安く形骸化する経路。挙動要約は残す |
| AI が起案した挙動要約を人が貼る・直す | 書く時間が 0 になる | 要約は理解の証拠であり、生成物は証拠にならない(`04-gate-record.md:98`、ADR-0023 `:32`)。「差分を思い出す瞬間」が消える。附属書C の「AI 転記」そのもの |
| 判定記録を本体 PR に同梱し、判定者が push(案 IV) | 記録 PR が消える | 2 名体制で判定者が最後の push 者になり、自分の承認が `require_last_push_approval` を満たさない。作者は承認できない → 詰まる。加えて、マージまでの間に作者が記録ファイルを編集できる(判定される側が判定の材料を触れる形。`ci-gates.md:146` の趣旨に反する) |
| Bot の bypass を `exempt` にする | Rule insights が埋まらない。設定が単純 | 監査に出ない(02 §4.1)。記録を固定する主体が記録に残らない。規制業で最初に指摘される |
| `dismiss_stale_reviews_on_push` / `require_last_push_approval` を切る | 更新 → 再承認の往復が消える | 承認が内容と切れる。承認後の push で中身を変えられる(`rulesets/README.md:43`)。往復の原因は本体でなく記録 PR にあるので、記録 PR を消せば本体の往復は #296 の粒度の問題だけになる |
| G-7 でまとめて、人がファイルを手で書く(日時は手入力) | 日常の操作が 0 になる | 後追いの制度化。属性が全て申告値になる。「まとめて固定」は**写し(機械の値)**に限る |
| ラベル `state:*` の遷移を記録にする | 操作 1 回 | ラベルは誰でも付けられ、対象も持たない。projen も「ラベルはセキュリティ統制ではない」(03 §6.1)。ADR-0036 の却下理由そのもの |
| AI レビューを G-6 の 1 件目に数える | 2 名要求が 1 名で済む | AI の確認は検出の層(ADR-0028 決定7、`gate-criteria.md:477`)。1 名体制で「独立した確認」が成立したことになり、未達の表示が消える。未達は未達のまま見せる(ADR-0028) |
| 承認者の数を減らす(規制業 2 → 1) | 操作半減 | 本件の問題は承認者の数でなく、記録 PR が要求する**意味の無い承認**の数である。意味のある承認を減らしてはならない(ADR-0067、EV-0102 の差し替え条件を満たしてから) |

## 7. 根拠水準マークが要る箇所

## 補遺: 現場が主宰に求める決定の順序

1. 先に決める: Q1(定義の言い換え)と Q7(事象が属性を持つか、を基準にする)。これが決まれば Q2〜Q4 は帰結である
2. 次に決める: Q3 の「G-7 でまとめて固定」を既定にし、Bot を選択肢に置くこと。ここが決まらないと、テンプレートの `/gate` スキルと `ship-evidence.yml` の直し方が決まらない
3. 最後に決める: Q5・Q6。これらは標準の章立ての問題であり、現場の操作回数には効かない
4. 本件で決めない: 承認の失効の粒度(#296)。本体 PR の往復はそちらで扱う。記録 PR の往復を消せば、本体の往復だけが残り、問題が切り分けられる
