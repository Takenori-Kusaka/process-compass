## 2. 反証と食い違いへの応答

### 2.1 事実として成り立たない 2 つの主張(弁護 §3 #3・#4)— 認める

両方とも認めます。

- **リベースで対象 SHA が変わり記録を作り直す**: 成り立ちません。変更を対象とする判定の対象は PR の番号で書けます(`template/templates/04-gate-record.md:20`「PR の番号(`PR #12`)またはコミットの識別子」)。コミットの識別子が要るのは G-2・G-4 の受入基準の版(同 `:36`)だけで、これは実装 PR のリベースと無関係です。第1巡で私がこの主張を自分の論拠にしていなかったことは確かですが、brief の「事象」をそのまま引き継いで反論しなかったのは落ち度です
- **check-pr が基底の `docs/gates/` だけ読むから本体 PR の記録を数えない**: 成り立ちません。基底だけを読むのは停止の解除(`check-pr.mjs:349`)と例外承認の台帳であり、G-6 の承認者の数は `docs/gates/` を読まずに PR のレビューから数えます(`check-pr.mjs:436-438`)。第1巡 Q3 で「停止の解除と例外承認の台帳は現行どおり基底から読む」と書いたのは、この点では弁護役と同じ立場でした

ただし現場 §2.3 の「コミット識別子の罠」(G-2・G-4 の版を仕様 PR の head で書くと squash 後に残らない)は別の事象であり、成り立ちます。これは 2.4 で、様式の対象の欄を「仕様が基底ブランチへ入った後の識別子」に限ることで解きます。

### 2.3 監査側との食い違い: 写しの真正性と保持は G-7 だけで足りるか — 足りない。時点は折れ、bypass は折れない

監査側の 17 条件(03 §3)に第1巡の案を当てると、出荷判定まで写しを作らない形は次で落ちます。

| 条件 | G-7 まで写しを作らない形の欠け |
| --- | --- |
| 2(`user.id` の保存) | 出荷までに承認者が退会すると ghost 化し、写しを作る時点で `user.id` が取れない |
| 7(本文の編集が元を覆い隠さない) | 承認から出荷までの間、本文の編集の窓が開く。編集履歴は作者が消せる(02 §1.5) |
| 10(bypass の事実が監査に出る) | 出荷間隔が 180 日を超えると `policy_override`・bypass の監査ログが先に消える |
| 11(対象と同じ期間の保持) | 同上 |

したがって**写しの時点はマージごと**に改めます。これは監査側の案を採ります。再現性テスト(03 §4)の問 2 は G-8 を様式のまま残すので落ちません。問 1・問 3 は、写しの時点をマージごとに改めることで、監査側の折衷案と同じ答えになります。

採らないのは、写しを**基底ブランチ**へ Bot の bypass で入れる部分です。理由は第1巡と同じで、bypass はパス単位に絞れず(02 §5.3)、App の鍵が記録の信頼性の上限になり(02 §9.3 案 A の穴)、強制層の縮小(ADR-0038:46)に当たります。弁護(§3 #9)・規格整合(要記録)・現場(装置が増える)も同じ向きです。

**両立させる形**: 写しの置き場を、基底ブランチではなく、同じリポジトリの記録用ブランチにします。

- ルールセットは `ref_name` でブランチを選べる(`team.json:5-6` は `~DEFAULT_BRANCH` だけを対象にしている)。記録用ブランチには別のルールセットを置き、`pull_request` の規則を**置かない**。置くのは `non_fast_forward`・`deletion`、規制業・CL2 以上では `required_signatures`。bypass actor は誰にも与えない
- マージを契機に走るワークフローが、承認レビューの写し(02 §9.1 の最小の組: `id`・`state`・`commit_id`・`submitted_at`・`user.id`・`user.login`・本文・PR 番号・`merge_commit_sha`)をこのブランチへ置く。基底ブランチには触れない。基底ブランチのルールセットは一切緩めない
- 写しは監査側の言う「人の判断を含まない機械の複製」であり、承認は人の承認レビューに残る。ADR-0028 決定7 に触れない(規格整合 §3 の E の整理と同じ)
- 出荷判定(G-7)で、集約が記録用ブランチの写しとホスティングから引き直した承認レビューを突き合わせ、不一致(本文の編集・dismiss・ghost 化)を所見として出す。写しを基底ブランチへ入れる PR は出荷ごとに 1 本、承認者は出荷判定者本人(第1巡と同じ)

真正性については、監査側の案と同じく「API の応答と写しを作る機械の信用」に依存します。これはどの案にも共通の穴で(02 §9.3)、超えるには承認者本人の署名コミットしかありません。本案では、規制業・CL2 以上で `required_signatures` を記録用ブランチに課し、様式の記録は判定者本人の署名コミットとすることで、**様式の側だけ**この穴を塞ぎます。承認レビューの写しの側は塞げません。開示します。

第1巡で 02 案 D(専用ブランチ)を「記録が製品と同じ履歴にある性質を失う」として却下しました。この却下を**写しと様式の仮置きに限って撤回**します。出荷ごとに基底ブランチへ入れるので、出荷された状態では常に製品と同じ履歴にあります。失うのは出荷と出荷の間の期間だけで、その期間に写しが無いことのほうが(監査側の 4 条件)重い欠けです。

### 2.4 規格整合との食い違い: G-2〜G-4 の受け皿 — 様式に戻す

第1巡 Q4 の「成果物を判定者以外が push し、判定者が承認する」は、次の 2 体制で成り立ちません。

- **1 名体制**: 判定者が自分のアカウントで AI の担い手を動かす(認証情報を共有する。ADR-0035 条件3 を満たさない)のが通常の形であり、PR の作成者 = 判定者になる。作成者は自分の PR を承認できない。`checks-only.json` は承認の規則を持たないので止まりはしないが、「判定者の承認レビュー」が存在しない以上、受け皿も存在しない
- **2 名体制で判定者が起案側**: 価値責任者 B が自分のアカウントで AI に仕様を起こさせ push した場合、B は作成者であり承認できない。A が承認できるが、A は価値責任者ではないので、その承認は G-4 の判定ではない(ADR-0060:58「結果責任者が内容を確定する行為」)

成り立つのは、AI の担い手が別のアカウントで push する体制だけです。体制によって受け皿が変わる形は、「同じ結果を導く手続を 2 つ持つと条件の緩いほうだけが使われる」(`gate-criteria.md:1208`)に当たります。**したがって G-1〜G-4・G-8・SG は様式に戻します**。規格整合・監査・弁護の 3 者と同じ立場です。

ただし規格整合 §4(a) の「判定者が仕様の PR の作成者でない場合は、その PR の承認レビューを判定記録の媒体にできる」は**採りません**。同じ理由(`:1208`)で、G-2・G-4 の媒体は体制に依らず様式の 1 つに揃えます。承認レビューを媒体にするのは G-6 と区分の確定だけです。これは規格整合の自案に対する反対意見です。

現場 §3 Q4 の「作者本人ならコメント形式のレビューに宣言を書く」も採りません。コメント形式のレビューは、承認の操作ではない点で ADR-0036 の却下理由(ツールの操作)により近く、「確認した項目」の構造を持ちません。現場が求めた「対象の SHA は打たない」「時刻はシステムが付ける」は、様式のまま次で満たします。

- **対象の版**: 仕様が基底ブランチへ入った後の識別子を、判定の草案を起こす文脈が `git log` から埋める。仕様 PR のマージは G-2・G-4 の事務ではなく、版管理の操作である(規格整合 §4(a) の対応表の直し方と同じ)。「記録の作成 → ラベル → 事務」(`SKILL.md:65`)の事務は Issue・ラベルの操作であり、仕様 PR のマージを含まない。これで現場 §2.3 の罠は消える
- **判定日時**: 人が書く欄のまま残す(判定の時刻は判定者しか知らない)。機械は記録用ブランチで受け取った時刻を併記し、集約が両者の差を閾値なしで出す。差が大きい記録は内部監査の抜き取りの材料(現場 §7 の見直し条件と同じ測り方)
- **判定者**: 記名のまま。規制業・CL2 以上では署名コミットのアカウントと記名の一致を集約が確かめる(監査 Q4)
- **PR**: 記録用ブランチには PR の規則が無いため、記録だけのコミットに PR も承認者も要らない。これが標準の立場(`ci-gates.md:609`、ADR-0057:509)そのものである

「判定者が成果物の作成者でもある」ことは折り合いの対象ではなくなります。様式は判定者本人が書き、判定者本人が記録用ブランチへ置きます。ブランチ保護の自己承認の禁止は、PR の規則が無い場所では掛かりません。

### 2.6 現場と弁護の食い違い: 同梱すると詰まるか — 両方正しく、対象が違う

`require_last_push_approval` は「最新のレビュー可能な push を、push した本人以外が承認しなければならない」です(02 §2 `gate-record-02:64`)。

- 現場の案 IV(判定記録を**本体 PR** へ同梱し、判定者が push する)は詰まります。G-6 の判定者 B が push すると、B の承認は最後の push の承認にならず、作成者 A は承認できません。正しい指摘です
- 弁護の 4.1 B は本体 PR への同梱ではなく、**別の記録 PR** を起案文脈が開き、判定者は push せず承認だけする形です。判定者は最後の push 者でないので詰まりません。弁護の文面に「同梱」はありません

両者は衝突していません。どちらにも残るのは、G-6 で判定者の承認が**判定そのもの**である以上、判定者は本体 PR へ push してはならないという制約です。改訂後の案では G-6 の記録は承認レビューの本文なので、同梱も記録 PR も生じません。G-2〜G-4 は 2.4 のとおり記録用ブランチへ置くので、PR 自体が生じません。残るのは停止の解除・例外承認の基底ブランチへの PR だけで、ここは弁護の B(起案文脈が開き、権限者本人が承認)を採ります。アカウントが分かれていない体制では他者の承認で入れ、その承認は判定ではなく取り込みの事務であることを本文に明記します(監査 Q4)。

### 2.7 1 名体制: 弱点 5 と現場の「ソロは 2 回」— 弱点 5 を改める

現場の「ソロは 2 回」は G-6 の数です。G-6 は 1 名体制で未達(`template/README.md:19`)であり、記録を作らないので 2 回で済みます。私の弱点 5 は G-2〜G-4・G-7 の記録 PR を指していました。対象が違い、食い違いではありません。

改訂後の形で 1 名体制の G-4 を数え直します(現場 §2.3 の数え方。E3)。

| 操作 | 現行(現場の見積り) | 改訂後 |
| --- | --- | --- |
| 仕様 PR のマージ | 1 | 1 |
| 様式の 9 欄 | 1(欄 9) | 1(欄 2〜3: 結果・確認した項目・差し戻し理由。残りは草案文脈が埋める) |
| push | 1 | 1(記録用ブランチへ。署名コミット) |
| 記録 PR のマージ | 1 | 0 |
| 合計 | 4 | 3。打つ欄は 9 → 2〜3 |

弱点 5 の「何も軽くならない」は撤回します。残るのは、1 名体制の記録の帰属が本人の署名だけに依ること(これは ADR-0060 が「別の人による確認ではない」と決めたとおりで、本件で変えない)と、`checks-only.json` の体制では記録用ブランチの保護も無いこと(無料プランの私有リポジトリ `template/README.md:115`。現行の基底ブランチと同じ)です。

### 3.2 記録用ブランチの規則

- 対象はテンプレートが定める 1 本のブランチ。ルールセットの `conditions.ref_name` でそのブランチだけを選ぶ
- 置く規則: `non_fast_forward`、`deletion`。規制業・CL2 以上では `required_signatures`。`pull_request` と `required_status_checks` は置かない
- bypass actor は誰にも与えない。`exempt` を使わない。基底ブランチのルールセットは変えない
- 書き込む者: 判定者本人(様式。署名コミット)と、マージを契機に走るワークフロー(承認レビューの写しと、受け取った時刻の記録)。ワークフローの書き込みは `GITHUB_TOKEN` の `contents: write` で足り、App の鍵を要しない。`required_signatures` を課す構成では GitHub が署名する API 経由のコミット(02:14 `createCommitOnBranch`)を使う
- 置き場は追記だけ(既存のファイルを書き換えない)。書き換えは集約が「成立済みの記録の書き換え」として所見に出す(現行の検査と同じ線)
- `next.mjs` と集約は、基底ブランチの `docs/gates/` に加えて記録用ブランチを読む。「記録が無い = 未判定」の表示は保つ(現場 §5.1 が維持を求めた点)

## 4. なお残る弱点

1. **記録用ブランチの形は実機で検証されていない**(E0)。`createCommitOnBranch` が `required_signatures` を満たすこと、マージを契機のワークフローが記録用ブランチへ push できること、GitHub Actions の `GITHUB_TOKEN` がルールセットの無い別ブランチへ書けることは、文書上は成り立つが、準拠テンプレートでは 1 回も回していない。`ship-evidence.yml` 自体が実機未検証(第1巡 弱点 3)の上に積む
2. **承認レビューの写しの真正性は、依然として API の応答と写しを作る機械に依る**。署名コミットで塞げるのは様式の側だけ。監査側の案も同じ穴を持つが、本案はそれを解決したとは主張しない
3. **様式の「判定日時」は人が書く欄のまま**。「受け取った時刻」を併記して差を出すが、差の大きさで合否を決めない以上、後追いの記録を機械が止めることはない。現場 §2.5 の「出荷直前にまとめて書く」は、差が可視化されることで抑止されると見込むが、実証は無い(E0)
4. **記録の置き場が出荷と出荷の間で 2 か所になる**(基底ブランチの停止の解除・例外承認と、記録用ブランチのそれ以外)。現場の「受け皿を 3 つ以上に増やさない」には収まるが、`next.mjs` が 2 か所を読む分、実装の誤りの余地が増える
5. **G-6 の承認レビューに「確認した項目」の構造は依然として無い**(規格整合 §4(b))。基準3・基準5 の記載を本文に要することで部分的に埋めるが、機械が見るのは見出し語の有無だけ。8 文字の形骸化(ADR-0059)の限界はそのまま
6. **本体 PR の基底の更新による再承認の往復は残る**(#296)。起票者の訴えの半分はここにあり、本件では答えない
7. **無料プランの私有リポジトリ**では記録用ブランチも保護できず、改訂後の形は「判定者が直接 push する」現行と同じ強さにしかならない。テンプレートの README が既に開示している制約(`template/README.md:115`)であり、本案で新たに悪化はしないが、改善もしない
