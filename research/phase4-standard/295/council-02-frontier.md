# 会議体 #295 意見書02: AI 先進の現場(リスクと結果指標で統制する側)

- 提出日: 2026-10-11
- 読んだもの: council-00-brief、inventory-01-summary、research-01-external、ADR-0047、gate-criteria「タスクの分割基準」(822-983)、metrics.md の較正の歯止め、`check-pr.mjs`(380-640)、`config.mjs`・`generate-profile.mjs` の該当行。council2-01 の冒頭のみ。コードは**読んだだけで実走していない**。PR の JSON に何が入るか(検査の結果・承認の commit oid)は未確認で、下の案で要るものは「要確認」と書く

## (1) 立場と、守ろうとする失敗

**守る失敗: 標準が形骸化すること。** 固定の定数が能力向上の恩恵をすべて遮断すると、チームは標準を回避・偽装する。今回の実走が示したとおり、300〜400 行の PR だけが通り、足場の 950 行も 200 行・40 ファイルの横断も通らない。ここで偽装が起きると、遮断の数が減っても、起きるのは「計測される量だけを小さく見せる」行動で、レビューの質は上がらない。ただし結果指標だけの統制は後追いである。**事前に効く機械的な形を先に置き、結果指標は制動と失効の契機に使う**。

## (2) 具体案

### 論点1 上限の既定の扱い: 「遮断」から「審査深度の引き上げ」へ。遮断は未保証行だけに残す

行数の代わりに機械で測るもの(すべて `check-pr.mjs` が基底ブランチの構成と変更の一覧から算出できる形):

| 量 | 定義 | 使い方 |
| --- | --- | --- |
| 変更行(CL) | 製品コードの、ファイルごとの max(追加, 削除)の合計。テスト・fixture・snapshot・文書は別に集計 | 観測と警告 |
| 未保証行(UCL) | CL のうち、実行可能な保証の担保範囲に入らない行。`riskFloor` 規則または `delegation.protectedPaths` に当たるファイルの行は、担保範囲にあっても**割り引かず全行を数える** | 合否と深度の根拠 |
| 影響の広がり(M) | 触れたモジュール数。モジュールは構成の `task.modules[]`(パスの glob)で宣言する。ファイル数は観測だけにする | 警告と深度 |
| 同一 Task の累計 | 同じトレーラ `Spec: F-NNN / Task-N` を持つ、直近 14 日の PR の UCL の合計 | 分割による回避の検出 |

超過時の既定(L0 の値を示す。これは暫定値で E0):

| 状態 | 既定の扱い |
| --- | --- |
| UCL ≤ 400 かつ M ≤ 3 | 通常 |
| 400 < UCL ≤ 1200、または M > 3、または累計 > 800 | **合格のまま**。PR へ `size:over` を付け、(a)「超過の理由と保証」の節の記入、(b)区分の下限を R2 へ引き上げ(既存の `riskFloorOf` の仕組みをそのまま使う。R2 は指示した者以外の人の確定を要する)を課す。計測値は自動で記録する |
| UCL > 1200 | **差し戻しを既定**(ADR-0047 の既定を、ここだけに残す)。例外承認は下の論点3の簡素化した経路 |

これは ADR-0047 の部分的な置き換えになる。蒸し返しではなく、前提が変わった根拠を挙げる。(i) ADR-0047 自身の EV-0033 に「差し戻しがあり、例外承認の実績が 0 件の状態が 2 四半期続けば、経路が回避されている。その場合は上限を合否から外す」という差し替え条件がある。今回の指摘と実走は、経路が日常では使えなかったことの観測であり(四半期の計数ではないので E1)、条件を機械的に満たしたとは言わない。ただし、条件が予見した状態の別の現れとして扱う根拠になる。(ii) 外部調査で、規模の上限を合否にして欠陥が減った査読付き実証は【未確認】。400 の出自は 1 回のレビューセッションの目安で PR の合否ではない。一方、DORA は時間基準、Meta はリスクスコアで深度を変える【確認】。

### 論点2 算定方式

- **max(追加, 削除)**。書き換えを 2 倍に数えない。純削除は CL に入れず、ファイル数と区分の下限(`kinds: delete`)で扱う。純削除に論理が隠れる懸念は、削除の行を観測に出して見張る
- **テスト・fixture・snapshot は CL へ算入しない**。別に集計し、「製品の行に対するテストの行」を表示する。AI が製品コードを fixture や test のディレクトリへ置く偽装は、`task.nonProductPaths`(glob)を**閾値ファイル扱い**にして防ぐ。基底の構成から読み、同じ PR での変更を禁止事項6の検査に掛ける(既存の `THRESHOLD_FILES` と同じ扱い)。既存テストの変更の一覧(T-17)は残す
- 生成物は、**基底に印を先に入れる要件を残す**(印を持つ基底のファイルだけを除外)。この要件は偽装への歯止めなので緩めない。ただし印を足すだけの専用の PR を、UCL が 0 になる軽い経路として扱う

### 論点2b L1/L2 の宣言と検査の最小の形

構成へ次の 1 ブロックだけを足す。書き換えは `/process-change` だけ(人の確定)。

```json
"task": {
  "softLines": 400, "hardUnassured": 1200,
  "modules": [{ "id": "api", "paths": ["src/api/**"] }],
  "assurances": [
    { "id": "mut-core", "kind": "mutation", "paths": ["src/core/**"], "job": "mutation", "minScore": 70 }
  ]
}
```

- `kind` は gate-criteria の表で認めた 3 種(`mutation` / `property` / `contract`)と構造差分に限る。可視化・AI 要約は認めない(既存の線引きを維持)
- **水準は宣言でなく導出する**。`assurances` が空なら L0。空でなく、`job` が基底の必須ステータスチェックに含まれ、PR で成功していれば、その担保範囲の行が UCL から外れる(= L1)。「名乗る」欄は作らない。標準の「自己申告ではなく条件の充足」に合う
- **L2 は、テンプレートに降ろさない**。リスクの採点器と取り消し可能性の担保が要る。`<!-- impl ... state=undelivered -->` で、標準の規定のまま表示し続ける(消さない)。足場の暫定の代用として、`riskFloor` に 1 つも当たらず、全行が担保範囲にあり、可逆と宣言された変更を深度「低」とする形は、結果指標の実績が貯まるまで提案に留め、採用は求めない
- 要確認: 必須チェックの取得(`verify-gate-contract` がブランチ保護を読めるか)、PR の JSON に検査の結果が入るか。無ければ `gh pr checks` を足す

### 論点3 例外の経路と 1 名体制

- 日常の経路から「PR 2 本」を外す。**例外承認は同じ PR の独立した人のレビュー**(本文の先頭が `例外承認(規模):` で理由つき)にする。作成者は自分のレビューを足せないため、同じ PR で足した行を数えない原則は保たれる。既存の `approverFindings`(最後の状態・挙動要約・指示者の除外)をそのまま使える。台帳の行は、マージ後に集約の側が PR の記録から起こす(判定完了時間と規模の記録は ADR-0047 の決定2を維持)。要確認: 台帳へ自動で足す書き手の権限
- **1 名体制**: 独立した人が居ないので、独立性は**主張しない**。400 < UCL ≤ 1200 の段は、人の確定の代わりに「作成者本人の記名の確定と 24 時間の冷却」で通す。この段が検出の層として弱いことを、`/pit` の注記へ出し続ける(ADR-0028 の「未達と省略の区別」)。UCL > 1200 は、トレーラ `Solo-Exception:` と理由、24 時間の冷却、記録で通す。これは**独立レビューの代替ではない**と明記する。1 名体制の独立性の不足は別の条項の課題で、ここでは取り繕わない

### 論点4 能力依存の値の失効

- 契機は「能力の変化」。**機械で拾える契機**: `Co-Authored-By` は標準が必須とする(モデル名・版)。基底の履歴に無い名称の初出を `check-pr` が通知し、再評価の Issue の起票を促す(自動で値は変えない)。暦の失効(EV の見直し日)は先に来るほうが効く併用
- 再評価の手順は Anthropic の記事(2026-03-24【確認】)のとおり、**値ごとに「符号化した仮定」「その仮定を崩す観測」「残す・外す・移す」を記録**する。足場は撤去でなく移動するという反対の資料は、結論の選択肢に「移す」を設けて受ける。最初から外す方向と決めない。**対称**である: 新しい版が能力を下げることもあるので、引き上げ側だけの契機にしない
- 結果指標の制動(後追いの補強): 過去 90 日、超過段の PR のうち、取り消し・14 日以内の同一ファイルの修正が、通常段の 2 倍以上かつ件数 10 以上なら、**自動で既定(論点1 の遮断)へ戻す**。**厳しくする向きは自動、緩める向きは人**(Notion の ratchet の前例【確認】)。測定は git の履歴(revert・fix のコミット)からで、自己申告に依らない。metrics.md の歯止め 1 との緊張: 「既定へ戻す」は実績から基準を計算するのでなく、標準の既定へ戻すだけなので、規定 1 の除外として明文化する

### 論点5 ほかの定数

| 項目 | 案 |
| --- | --- |
| カバレッジ 80%(全体) | **基底の実測を下回らない**(ratchet)+ 変更行のカバレッジを観測。80% は新規の足場の既定に降格。下げる変更は人の確定(禁止事項6のとおり) |
| 自己修復 3 回 | 上限があること(A)は維持。値は構成の既定にとどめ、**同一の失敗の再発(同じテスト・同じエラー)を検出したら回数に関わらず停止**を足す。反復数の分布は観測 |
| 全 PR・全 push の承認失効 | 承認の commit と現在の HEAD で**木または patch-id が同一**(リベースだけ)なら承認を維持。それ以外は失効。承認を緩める向きではなく、無駄な失効だけを外す。要確認: PR の JSON に承認の commit oid が入るか |
| 「30 分・100 行」の AI への指示 | AI への指示としては削る。「1 つの受入基準の束につき 1 Task で、独立に検証できる」へ置き換える。人のレビューの SLA は人の側に残す |
| 委任の規模条件 | **ここは譲る**。人の確認が無い経路なので、総行数の上限(CL ≤ 400)と M ≤ 3 を残す。UCL に置き換えると、担保の設定の誤りがそのまま人の確認なしで通る |
| S-04/05/07(マーク無し) | まず根拠水準のマークを付ける(開示の規則)。S-05「8 時間超は分割必須」は AI の見積に意味が薄く、観測へ移す。S-07 の帯域は人の側の値として、自組織の実測から導く手続へ |

### 論点6 維持するもの(P4)

行数を能力と切り離す立場だからこそ、次は**固定**する: 独立性と兼務禁止、追跡性(Spec トレーラ)、記録の存在、閾値・除外設定と製品コードの同時変更の禁止(`nonProductPaths`・`assurances` も同じ扱い)、AI 名義の拒否、人の確定(R1・R2)、緩める向きの変更を AI が決めないこと、保証の「リスク区分の下限に当たるパスは割り引かない」。これらは能力が上がっても弱めない。

## (3) 他の立場への反論

- **統制を守る側「大きな PR は、能力が上がっても人は読めない。遮断を外せば素通りになる」**: 同意する点が 1 つある。**総行数でなく、人が読めない部分を数えるのが UCL**で、担保が無い行は従来どおり遮断に近い扱いになる。担保済みの行は、AI が出したテストを含めて、実行された保証であって読解の代替ではなく、gate-criteria が既に L1 として認めている。反論の核は、遮断が偽装を呼ぶ点。「遮断を外すと素通り」は、深度の引き上げ(R2 確定)で逆に人の関与が増える設計で受ける
- **較正・失効の標準運営の立場「自動で既定へ戻すのは較正の自動化の禁止に反する。取り消しは慎重に」**: 厳しくする向きだけに限る。緩める向きは人。禁止の理由(出し切らない動機)は、緩める自動化に当てはまる。厳しくする自動化には、成果を隠す動機が逆向きに生じる(隠したい側は取り消しの履歴を消せない。git の履歴に依るため)
- **懐疑役「UCL も max も新しい代理指標で、同じ Goodhart」**: そのとおりで、行数より良いとは実証していない(下の根拠水準)。違いは、(i)保証の担保範囲は実行結果であり、行数のように見かけで減らせない、(ii)偽装の経路を 3 つ(fixture への移し替え・分割・担保の設定の空洞化)機械で見張る、の 2 点。実証を欠く判断として開示し、制動で拾う
- **懐疑役「固定の定数を別の定数に替えただけ」**: 数値(400・1200・14 日・2 倍)は E0。固定の数値をなくす案ではない。**数値の位置づけを、合否から、深度の引き上げと制動の契機へ移す案**である

## (4) 自案が失敗する条件(自分で落とす)

1. **担保の空洞化**: `minScore: 0` の変異テスト、アサーションの無いテスト、除外の広い contract を `assurances` へ登録すれば、UCL は容易に 0 になる。`assurances` と閾値は閾値ファイル扱いで同時変更を禁じるが、**初回の設定は検査の対象外**(既存の `initial` の扱い)。初回を AI が緩く書き、人が見落とす経路は塞げていない。人の確定(`/process-change`)に頼る
2. **分割による回避**: 同一 Task の累計は同じトレーラを分けることで逃げられる(別の Task 番号を付ける)。検出は警告までで、後追い
3. **制動が効かない**: 超過段の件数が少ない(n < 10)と制動は永久に発動しない。小さいチームほど効かない。1 名体制では結果指標がほぼ無力
4. **制動の指標の誤り**: 取り消しと 14 日以内の修正は、変更失敗の代理でしかない。軽微な修正が多い文化では誤検知する。また、修正を別のブランチ名・別のファイルで隠せば検出できない
5. **1 名体制の冷却**: 24 時間の冷却と本人の確定は、独立した確認ではない。この段は、実質は記録を残すだけ。標準が言う「決められた場所では必ず人間が触る」の人は触っているが、独立ではない
6. **能力の契機が逆になる**: 新しいモデル名の初出は、単なる名称の変更でも発火する(通知疲れ)。逆に、同じ名称のまま能力が変わる場合は拾えない
7. **R2 への引き上げが回避を誘う**: 400 を少し超えるだけで R2 の確定が要るなら、400 に収める偽装(整形・分割・fixture)が起きる。400 の段の手前の増加(380〜400 に集中)を分布で見る。**これが出れば、案は失敗している**

## (5) 根拠水準と、実証が無い部分

- 論点1 の数値(400・1200・M>3・累計 800)、UCL の定義、max 方式、制動の倍率・件数・窓: **E0**(設計判断。実証なし)
- 「上限の合否が欠陥を減らす実証は無い」: 外部調査の【未確認】を引いた。**無いことの証明ではない**
- リスクで深度を変える方式の有効性: Meta の事例【確認】は単一組織・モノレポ・自動テスト基盤が前提で、gate-criteria の EV-0006(E2)と同じ限界を持つ。UCL の方式そのものは Meta の事例でも検証されていない。**本案の UCL は、gate-criteria の L1 の「実行可能な保証で確認範囲を限定する」を機械の形にした私の翻訳**で、事例による支持は無い
- ratchet(厳しくする向きは自動、緩める向きは人): Notion【確認】。ただしコード品質の lint の事例で、PR の規模の制御への転用は未検証
- 能力の契機の再評価: Anthropic 2026-03-24【確認】。**ソフトウェア標準の条項に失効条件を組み込んだ規定は【未確認】**で、先例が無いまま提案している
- 全体の意見: ADR-0047 の置き換えに足る**観測**は、今回の指摘と実走(E1)だけ。採るなら、`EV` を新設して四半期の計数(a・b・c と、超過段の取り消し率)で検証する条件を付ける。実証が出るまでは、既定を深度の引き上げに置くこと自体が暫定である
