## 1. 立場と、守ろうとする失敗

守る失敗は2つあり、互いに逆向きである。

- 失敗A: 利用者の主張を前提にして、根拠なく上限を緩める・外す。確認の価値が最も上がる時期(AI が作る量が増える時期)に、確認の入口を自分で壊す
- 失敗B: 現行の遮断を「安全だから」と維持する。安全を担保した証拠は無いのに、利用者を止め続け、回避(分割・偽装)を生む

どちらの失敗も「証拠が無いまま動く」点で同じである。本意見書は、**証拠が無い箇所を無いと書いたうえで、証拠が要らない最小の変更だけを残す**。

## 2. 論点への回答

### 論点(1) 利用者の指摘は本当か

結論: **「AI が賢くなるほど PR が大きくなる」は、一部の母集団でだけ支持され、「ほぼ 100% で落ちる」は能力の話ではない**。

証拠(research-01-external から。水準は同書の【】に従う):

| 観測 | 内容 | 読み方 |
| --- | --- | --- |
| DX 400 社超【確認】 | 中央値 44→72 行(1.6 倍) | 中央値は 400 の約 5分の1。AI 比率は自己申告 |
| 単一組織【二次】 | 中央値 66→210 行、「大」13%→33% | 1社。一般化不可 |
| LinearB【二次】 | p75: AI支援 408 行、エージェント 293、非支援 157 | AI 支援 PR のおよそ 4分の1 が 400 行を超える程度。「ほぼ全部」ではない |
| AIDev(TH10) | 中央値 90 対 88 行 | OSS は差なし。母集団で割れる |
| CMU/Stanford【二次】 | PR 量 3.1 倍に対しレビュワー 1.5 倍。AI 起源 PR は初回レビューからマージまで約 20% 長い | 帯域が逼迫している証拠であり、「大きくしてよい」の証拠ではない |
| LinearB【二次】 | 最大の変更ほど最短のレビューしか受けない | 大きい PR が増えると、確認が薄くなる側に倒れる |

つまり、外部の数値は「PR は中央値で 1.6〜3 倍になった。ただし 400 行には遠い」「大きいものほど薄く見られている」であり、**上限を上げる根拠にならない**。能力の向上が人の帯域を広げたという観測は、調査の範囲に1件も無い。

「ほぼ 100%」の原因は、実走(results.json)から3つに分けられ、いずれも能力と無関係である。

1. **機械が上限を働かせたのは 2026-10-02 が初めて**。`git log -S` で、`check-pr.mjs` に「変更行数」の検査が入ったのは dfc2fef(#286、2026-10-02)である。#247 の P-001 は「`process.config.json` の値を読む検査が0件」と報告しており(council2-01-field.md:93)、それ以前の「利用者は上限を食らわなかった」と、いまの「ほぼ 100%」は、**機械が働いたかどうかの差**であり、PR の大きさが変わった証拠ではない。上限は 9日前に初めて遮断として降ろされたばかりである
2. **算定が実装の約 2 倍を数える**。S1(300 行)は通り、S2(実装 300+テスト 300=600 行)は落ちる。テストを同量書く規律(標準が求める側)に従うだけで、実装 200 行超の機能は落ちる。S9(実装 250+fixture 900)も落ちる。これは「AI が大きく作った」のでなく、**算定方式が標準の「レビューする負荷」から外れている**(検証可能性が高い fixture まで逐行読解の負荷に数える)
3. **初回の足場(S8: 950 行、3 ファイル)が落ちる**。これは定常状態でなく、案件ごとに1回の事象である。「ほぼ 100%」の語感の一部は、導入直後の PR に偏って観測された可能性がある(推測。利用者の PR の分布は本リポジトリに無い)

さらに、**「案件が 1 PR に詰め込みすぎた」可能性を、現時点では落とせない**。標準は「1タスク=1レビュー単位」を実装計画(G-4)で設計すると定め、上限超過は「実装計画へ差し戻す」である。つまり、定常的に 400 行を超えるなら、(a) 計画のタスク粒度が系統的に粗い、(b) 上限が系統的に低い、のどちらかであり、**どちらかを区別する分布(PR ごとの実装行数・テスト行数・タスク数)を誰も持っていない**。LinearB の「AI 支援のコミットはファイル数が少ない=PR は大きいがコミットは細かい」は、(a)(束ねている)を示唆するが【二次】、決め手ではない。

判断: 指摘は事実(実走で再現)だが、「原因は能力の向上」は未実証。**まず利用者の PR 分布(`git log --numstat` で足りる。読み取りのみ)を取る**。これは費用が最小で、以降のすべての案の前提を判別する。

### 論点(2) 「人間のレビュー速度前提の定数は時代遅れ」という前提

この前提には正しい部分と誤った部分がある。

- 誤り: レビューする側の帯域は AI の進化と独立に固定である。AI が作る量が増えるほど、**確認の価値は上がり**、確認の入口を緩める根拠にはならない。DORA の AI Note(「機械生成コードの小片でも、認知負荷は行当たりで人手コードより高い可能性」【確認】)、CMU の 1.5 倍対 3.1 倍【二次】は、すべて帯域が足りない側を指す。「上限は AI が賢くなるほど逆行する」は、**生産側の能力で消費側の定数を語る誤り**である
- 正しい: 行数が帯域の代理として弱いこと。標準自身が Qt/Chrome 追試(レビュー指標を含まないモデルのほうが同等以上の適合度)を引き、「行数は独立した原因ではない」と書いている(gate-criteria.md:841-845)。利用者の「時代遅れ」は、**実は「行数が悪い代理だ」という既知の弱点**の別の言い方であり、AI とは関係が無い

したがって、「定数が時代遅れ」を理由にする案(値を上げる、能力世代で失効させる)は落とす。「行数が悪い代理」を理由にする案(算定の修正、行数以外の観測の併用)は残る。

### 論点(3) 緩和・観測化案は Goodhart・偽装・形骸化を招かないか

招く。ただし、**現行の遮断も同じ誘因を持つ**ので、片方だけを欠陥とは言えない。

| 案 | 招く失敗 | 根拠 |
| --- | --- | --- |
| 上限を上げる | 目標値のスライド。400→800 は根拠が同じく無く、「上限が高いほど大きい PR が出る」ことは LinearB の最大変更ほど薄いレビュー【二次】と整合 | 水準 E0 |
| 観測のみ(上限なし) | 確認の入口が消える。値の域が `generate-profile.mjs:3409` に無い(実装も要る)。ADR-0047 が却下し、EV-0033 が再開条件を予約している | ADR-0047 |
| 警告+審査深度の引き上げ | 警告は読まれなくなる(慣れ)。審査深度の引き上げは、AI レビュアが深度を満たしたと称する経路(#268・TH07 の滑り落ち)を作る。深度を測る観測量が無い | 一般論。実証無し(E0) |
| L1/L2 の宣言欄 | 宣言は自己申告の欄になる。標準は「水準は自己申告ではなく条件の充足を記録で示す」(gate-criteria.md:874)。テンプレートは影響範囲の提示・実行可能な保証の存在を機械で確かめられず、「宣言→緩和」だけが降りる | 実走: 宣言欄も検査も無い(inventory) |
| 現行の遮断 | 分割(1PR を 7PR へ。eBay の指摘【二次】)、テスト・fixture の別 PR 化、算定対象外のパス(`test/**` を除く運用)への移動 | 標準が「レビューを分割して対処しない」と書くが、機械は分割を検出しない |

なお、**現行の遮断で偽装が起きているかは未観測**である。テンプレートは超過の記録も、分割の痕跡も、保存しない(inventory: 較正の母集団を保存・集計するコードが無い)。これは遮断を守る側にも、緩める側にも、証拠が無いことを意味する。

### 論点(4) 遮断維持が安全を担保している証拠はあるか

**無い**。

- サイズ上限を合否にして欠陥が減った査読付き実証は【未確認】(research-01-external:43)。「35% 減」は出典不明で不採用
- 400 行の出自は 2006 年の SmartBear/Cisco(1チームの観察研究、商用ツール会社)で、PR の合否閾値でも AI 生成コードでもない。標準自身が「2010年代以降に独立して再検証した研究を確認できていない」と書く(gate-criteria.md:922)
- ファイル数 15・層数 3 には、標準自身が実証が無いと書く(同:923-924)
- 標準自身が、遮断として運用してはならないと書く(同:943)

遮断が担保しているのは**安全ではなく、「超過の記録が例外承認の行として残る」という副産物**だけである。ここまでは認める。

もう1点。ADR-0047 の EV-0033 は、**(a) 差し戻した件数 > 0 かつ (b) 例外で通した件数 = 0 が 2 四半期続けば、上限を目安のみへ降ろす**と、自ら再開条件を定めている。いまのテンプレートは (a)(b)(c) を数えるコードを持たない。つまり、**標準が自分に課した「失敗の検知条件」が、実装側で検知不能**である。現状は「遮断が失敗しているか否か」を、誰も判定できない。これは標準・テンプレートの両方が、較正の入力を自ら断つ構造(ADR-0047 が指摘した打ち切りと同型)で、**ADR-0047 の決定が実行層で未達**だと言える。

### 論点(5) 棚卸しの分類の誤り

要約表のみに基づく(全項目の表は未読)。限定付きで指摘する。

- **A とされた項目のうち、数値に能力依存の疑いがあるもの**: S-15 独立レビュー「2 名」、S-16「3 名境界」、S-17 コア理解「2 名」。人数そのものは**独立性の構造から導かれる下限**(1名では独立が成立しない)であり、能力の影響を受けない。ただし「3 名」「10 名」などの境界は、A と B が混在する。分類は項目ごとでなく、**条項の中の数値ごと**に分けるべきである
- **B とされた項目のうち、構造の不変条件を含むもの**:
  - **T-09 全 PR・全 push の承認失効**: 「承認は、承認した内容に束縛される」は構造の不変条件(A)。B なのは粒度(全 push)のみで、ここを緩めて「承認が内容と切れる」方向へ倒すと、承認の形骸化に直結する。粒度の見直しは、束縛を保つ方法(差分が変わらない push では失効しない等)に限る
  - **T-08 自己修復 3 回**: 「有限回で止まり、人へ戻す」は A。「3」は B
  - **T-21 SLA / T-26 力量確認 92 日 / T-30 見直し周期 / S-14 自律度引き上げに 3 か月**: 観測窓や周期は、**稀な事象を観測するための統計的な長さ**であり、モデルが賢くなっても短縮できない。B(能力依存)と書くと、「能力が上がったから短くしてよい」が導かれる。これは誤りで、**観測の窓は能力でなく、事象の頻度で決まる**
  - **T-10 委任の規模条件**: 委任が自動マージを許す範囲を 400/15 に縛ることは、規模の代理というより「自動マージが許される影響の上限」である。A の側面がある。T-01 を緩めても、T-10 が連動して緩むのは意図とは限らない(`config.mjs:1109-1117` が同じ値を共有する)。**切り離して扱うべき**
- **分類 C(合否にしてはならない観測量)の見落とし**: 超過した PR の規模・判定完了時間は、**「合否にしてはならない」ではなく「保存されていない」**。C に入れる前に、まず収集の実装が要る。分類を決めても、観測がゼロなら意味が無い

### 論点(6) 他の立場が見落とす最小の失敗

他の立場(統制を守る側・AI 先進の現場・標準運営)は、おそらく**値・算定・水準の宣言**といった「規則の側」を触る案になる。それらは標準側の改訂(ADR・条項・語彙の突合)を要し、時間がかかり、証拠も無い。**利用者を今すぐ救う最小の変更は、規則を動かさずに、通す経路を安くすること**である。

### 残す最小の案

三つに絞る。いずれも標準の規範(差し戻しが既定。例外承認で通せる)を変えず、実装を標準へ揃える。

**案M1: 例外承認の経路を、1 PR・1 人の承認で完結させる**

- 現状: PR 2 本・人の承認 2 回・マージ 1 回(inventory)。PR 番号が作成後にしか決まらず、台帳の行は後から入れる
- 実走で確認した事実: **作成者が AI 名義の場合、1名体制でも承認が成立する**(`exceptionFor` を solo + `claude-bot` で呼ぶと `matched: [D-001]`)。したがって「1 名体制では使えない」は、**人が PR の作成者である場合に限る**。inventory の記述は修正されるべきである(論点5の分類より先の事実誤認)
- 不変条件として固定するもの: 承認が (i) 対象の内容より前に存在し、(ii) 作成者と別の主体によって行われ、(iii) AI 名義でない(T-31)。**「同じ PR で足した行は数えない」はこの (i)(ii) の実装であり、緩めない**
- 変更する部分: 承認の手段を台帳の行(基底への先行 PR)から、**CI が読める、承認者(人)のアカウントによる記録**(例: PR への承認ラベルの付与。付与者が作成者でなく、名簿の人であること。付与のイベントを CI が読む)へ広げる。台帳への記録は、マージ時に追記する。これで PR 1 本、承認 1 回、マージ 1 回になる
- 未検証: ラベルのイベントの付与者を、CI が確実に読めるか(権限・API・フォークの PR)。偽造の経路(作成者が自分でラベルを付ける)を、リポジトリの権限だけで塞げるか。**ここは実走が要る。確かめるまで、案M1 は「候補」であり、採用の根拠にしない**

**案M2: 超過を記録して保存する(較正の母集団を作る)**

- 現状: `check-pr.mjs:529` は通知文を出すだけで、保存しない(inventory)。標準の ADR-0047 決定2(超過レビューの判定完了時間と規模を記録)・決定3(充足率による較正)・EV-0033 の (a)(b)(c) の計数が、実行層で未達
- 変更: 超過(通った・止まった)ごとに、規模・ファイル数・判定完了時間を機械が保存し、四半期ごとに (a)(b)(c) と、規模の区間ごとの SLA 充足率を、人の判断の材料として出す。**閾値を自動で動かさない**(gate-criteria.md:977)
- 効果: これが無いと、案M1 で通過が楽になっても、上限が妥当かを誰も判定できない。**通過が多いことが、較正の最も強い証拠になる**(通過が 100% なら 400 は低すぎ、あるいは計画の粒度が粗い。どちらかを分布が教える)

**案M3: 算定の標準との不一致を、標準側から先に確定する**

- テスト・fixture の算入は、標準の記述が「判断記録・仕様・設計文書を除く」としか書いておらず、**テスト・fixture の扱いは標準が未規定**である。テンプレートが算入しているのは、「規定が無い」からの既定である。これを「除く」と決めるのは、緩和であり、ADR と会議体を要する(コアポリシー)。ここでは**決めない**
- ただし先に、標準の取り残し(`pr-workflow.md:42-46` の ±400 行、`task-size.md:35` の第 85 パーセンタイル、T-18/T-19/T-24 の不整合)は、決定の自由度が無い(標準の他の箇所が既に決めている)ので、会議体を待たずに直す価値がある

### 最小の案の順序と、費用に依らない理由

M2 → M1 → M3 の順。M2 は M1 の前提(通過が増えたとき、判定できる状態)であり、**判断軸は信頼性**である。費用の小ささを理由にしない。M1 単独は「通すことを楽にするだけ」で、形骸化を招く(下記)。M2 が揃って初めて、M1 は較正の入力を作る装置になる。

## 4. 他の立場への反論(想定)

- 統制を守る側: 「遮断を緩めると、AI が大きな変更を通す」。→ 案M1 は遮断を緩めず、**通す経路に人の確認を残す**。むしろ、現行の経路が使いにくいために、人が確認しないまま遮断を回避する(分割、算定対象外パスへの移動)ことを減らす。ただし、案M1 が「承認ラベルを機械的に付ける」運用に堕ちる(形骸化)危険は残る。M2 が通過率を可視化し、100% に近ければ、それを較正の入力として扱う
- AI 先進の現場: 「能力が上がるのだから、上限は上げるべき」。→ 能力が人の帯域を上げたという観測が無い(論点1・2)。上げる根拠は、現行値の根拠と同水準の E0
- 標準運営: 「P1〜P5 を条項化する」。→ P1・P2 は現行の標準(規範はレビュー可能性、較正手続)と重複し、P3 は契機が観測不能。P4 は異論無し(固定)。P5(合否にしてよい観測量と、傾向に留める観測量の区別)は有用だが、**収集の実装が先**

## 5. 自案が失敗する条件(自分で落とす)

1. 利用者の PR の分布が、**計画どおりの 1 タスク=1 レビュー単位でも、中央値が 400 行を超える**場合。そのとき、400 は系統的に低く、較正(充足率)に従って上げるべきで、M1 は延命に過ぎない。M2 の分布がそれを教える(M2 が先の理由)
2. 利用者の組織で、**規模 600〜1000 行の変更の SLA 充足率が 8 割以上**だった場合。標準自身の測定(gate-criteria.md:968)で上限が動く。懐疑役の「帯域は固定」は、実測に負ける
3. 案M1 の承認手段(ラベルなど)を、**CI が改ざん耐性をもって読めない**場合。そのとき、M1 は採れず、現行の 2 PR 経路を残す。代替は、PR 番号を先に確保する(空の PR を先に作る)手順の自動化だが、それも未検証
4. 「機械が上限を働かせたのは 10-02 が初めて」は、`git log` の `-S` 検索に基づく。**利用者が別のバージョンのテンプレートを使っていた場合は当たらない**。利用者の使ったバージョンは未確認
5. M1 の通過が日常化して、人の承認が確認を伴わなくなる(形骸化)。これは起こりうるし、本意見書は防げない。防ぐのは M2(承認から判定完了までの時間と、事後のリバート・差し戻し率の併記)で、事後にしか検知できない
6. 「大 PR ほど薄く見られる」は LinearB【二次】1件。確認していない
