## 1. 法的な枠組み（日本）

### 1.1 一次情報

文化審議会 著作権分科会 法制度小委員会「AIと著作権に関する考え方について」【概要】、令和6年4月、文化庁著作権課。

- 出典: https://www.bunka.go.jp/seisaku/bunkashingikai/chosakuken/pdf/94057901_01.pdf （2026-08-06 取得）
- 本体（令和6年3月15日）: https://www.bunka.go.jp/seisaku/bunkashingikai/chosakuken/pdf/94037901_01.pdf

:::caution
本資料は概要版である。原文が自ら次のとおり断っている。

> この資料は、文化審議会著作権分科会法制度小委員会で取りまとめられた「AIと著作権に関する考え方について」（以下「考え方」）の概要をまとめたものです。正確な記載内容は「考え方」本体をご確認ください。

> 「考え方」は、現行の著作権法の解釈について、公表時点における、小委員会としての一定の考え方を示すものです。「考え方」それ自体は法的な拘束力を有するものではなく、また現時点で存在する特定の生成AIやこれに関する技術について確定的な法的評価を行うものではありません。

**法的拘束力はない**。本標準が「準拠」と書いてはならない。
:::

### 1.2 3つの段階を分けて考える

原文は「AI開発・学習段階」「生成・利用段階」「AI生成物の著作物性」を**別の問題として分ける**としている。本標準が扱うのは**生成・利用段階**である。学習段階（法第30条の4）は、モデルを開発する事業者の問題であり、利用者の統制対象ではない。

### 1.3 生成・利用段階の判断基準（Q1）

> ＡＩを利用して生成した画像等をSNS等にアップロードして公表したり、複製物を販売したりする場合は、通常の著作権侵害と同様の基準で、侵害となるか否かが判断されます。

> すなわち、生成された画像等に既存の画像等（著作物）との類似性（創作的表現が共通していること）及び依拠性(既存の著作物をもとに創作したこと)が認められ、かつ、権利制限規定の対象外である場合は、既存の著作物の著作権侵害となります。

**AI が生成したことによる特別な扱いはない**。侵害の要件は従来どおり **類似性 + 依拠性** である。

### 1.4 依拠性は推認される（Q2 — 本調査で最も重要な所見）

> 生成AIの開発・学習段階で当該既存の著作物が学習されていた場合は、AI利用者が既存の著作物を認識していない場合でも、通常、依拠性があったと推認される

原文は但し書きも置いている。

> ただし、当該生成AIについて「学習に用いられた著作物の創作的表現が、生成・利用段階において出力される状態となっていない」場合には、AI利用者がこの事情を主張・立証することで、依拠性がないと判断される場合はあり得ます。

さらに、学習データに含まれるか不明な場合についても次のとおりである。

> 生成物と類似する既存の著作物が学習データに含まれているか不明な場合でも、権利者としては「AI利用者が既存の著作物にアクセス可能であったこと」や「生成物に既存の著作物との高度な類似性があること」等を立証すれば、依拠性ありと推認させることができる

**含意（本標準の設計の起点）**:

- **「AI が書いたので知らなかった」は抗弁にならない**。依拠性は推認される
- 但し書きの立証（出力される状態にないこと）は、**モデルの内部に関する立証であり、利用者側では通常行えない**
- したがって**利用者が制御できるのは類似性の側だけ**である。規定は「類似性を下げる措置」と「措置を講じた記録」に置くほかない

### 1.5 生成が適法でも利用が適法とは限らない

> 「AIによる生成物の生成」が適法に行える場合でも、「生成物の利用」（SNSへのアップロード等）まで直ちに適法となるものではなく、場面ごとに適法性の判断が必要である

**開発中の生成と、出荷する成果物への組み込みは別の場面である**。したがって検査の位置は G-5（生成の直後）だけでなく G-7（出荷の判定）にも要る。

### 1.6 責任主体

> 既存の判例からすると、生成物の生成･利用に伴って著作権侵害が生じた場合、以下のような要素によっては、AI利用者だけでなく、AI開発等を行う事業者が、著作権侵害の主体として責任を負う可能性があります。

事業者の責任を**高める**要素として「侵害物が高頻度で生成されること」「類似物を生成する蓋然性の高さを認識しながら抑止措置を取っていないこと」、**低める**要素として「防止措置を取っていること」が挙げられている。

**利用者側の責任が消えるわけではない**。事業者と併存しうるという記述である。

## 2. 事業者の知財補償（Q5）

### 2.1 一次情報: Microsoft Customer Copyright Commitment（CCC）

- 出典: [Customer Copyright Commitment Required Mitigations — Microsoft Learn](https://learn.microsoft.com/en-us/azure/foundry/responsible-ai/openai/customer-copyright-commitment)（2026-07-13 更新、2026-08-06 取得）

原文の要点。

> The Customer Copyright Commitment ("CCC") is a provision in the Microsoft Product Terms that describes Microsoft's obligation to defend customers against certain third-party intellectual property claims relating to Output Content.

> If a customer tenders a claim for defense, the customer will be required to demonstrate compliance with all relevant requirements, both on this page and as listed in the Product Terms.

**GitHub Offerings についての記述（2026-04-03 発効）**:

> The below are the only required mitigations that apply to GitHub Offerings, and as of April 3, 2026, there are no additional required mitigations. Use of the Duplicate Detection filter feature is no longer required for CCC coverage. This feature remains available for optional use.

### 2.2 所見

- 補償の**条件は変動する**。従前は複製検知フィルタの利用が補償の要件であったが、2026-04-03 に要件から外れた
- 補償を受けるには、**要件への適合を利用者が立証する**必要がある。適合の記録を残していなければ補償は機能しない
- Azure OpenAI のコード生成では、いまも「protected material code モデルを annotate または filter モードで有効にすること」が要件であり、annotate モードを選んだ場合は「出力に付されたライセンスに従うこと」が条件になっている

**含意**: **補償の存在を、検査を行わない理由にしてはならない**。補償は条件付きであり、条件は事業者の都合で変わる。本標準が求めるのは、補償の有無によらず成立する自組織側の記録である。

## 3. 機械検査で何ができるか（Q4）

### 3.1 2つの別問題を混同しない

| 対象 | 何を調べるか | 成熟度 |
| --- | --- | --- |
| **依存関係のライセンス** | 取り込んだライブラリのライセンスと、その条件（表示義務、派生物の開示義務など） | 実務として確立している |
| **生成されたコード片の由来** | 生成物が既存の著作物と創作的表現において類似するか | **確立していない** |

前者は成果物の構成を調べる作業であり、後者は表現の類似を判断する作業である。**同じ「知財チェック」という語で括ると、前者の成熟度が後者へ誤って転用される**。

### 3.2 依存関係の検査にも限界がある

Software Composition Analysis(SCA)ツールの精度を Java プロジェクトで評価した研究(ESEC/FSE 2023)では、**脆弱性検出の F1 スコアの平均は 0.475** と報告されている。依存関係の解決を適切に扱うと偽陽性が 34.24%、偽陰性が 6.91% 減るとされる。

- 出典: [Software Composition Analysis for Vulnerability Detection: An Empirical Study on Java Projects (ESEC/FSE 2023)](https://dl.acm.org/doi/10.1145/3611643.3616299)

:::caution
この研究が測っているのは**脆弱性検出**であり、**ライセンス検出の精度ではない**。本調査では、ライセンス検出の精度を測った査読研究を特定できなかった。**「ライセンス検出の精度は F1 0.475」と書いてはならない**。ここから言えるのは「依存関係の自動解析は完全ではない」という方向のみである。
:::

### 3.3 複製検知の位置づけ

生成物と公開コードの一致を検知する機能は、事業者側の機能として提供されている（2.1 の Duplicate Detection 等）。ただし次の理由から、**合否条件にしてはならない**。

- 一致検知は完全ではない。検出されなかったことは、混入がないことの証明にならない
- **合否条件にすると、検出されなかった結果が「潔白である」という記録として残る**。これは 1.4 の推認に対して何の防御にもならない
- 2.1 のとおり、機能の位置づけ自体が事業者の都合で変わる

## 5. 結論

### 5.1 Q3 への回答: 両立する

「生成手段を問わない検収」と「知財潔白性の結果責任」は**別の軸**であり、両立する。

- 検収は**仕様適合**の判定である（受入基準を満たすか）
- 知財潔白性は**成果物の属性**である（他者の権利を侵害していないか）

**知財潔白性は AI 固有の問題ではない**。人が書いたコードにも他者の著作物は混入しうる。したがって「AI を使ったかどうか」で要求を変える設計は誤りである。**生成手段を問わないまま、成果物の知財潔白性を全件に求める**のが正しい構成となる。

これは 1.3 の「通常の著作権侵害と同様の基準で判断される」という考え方とも整合する。

### 5.2 設計への反映

| # | 結論 | 反映先 |
| --- | --- | --- |
| 1 | 知財潔白性の要求を **AI の利用有無で変えない**。全件に適用する | 第4章 |
| 2 | **依存関係のライセンス検査は合否条件にする**。実務として確立しており、機械判定に載る | 第4章 G-5、フェーズ5 |
| 3 | **生成物の複製検知は合否条件にしない**。実施と結果の記録を求める。偽陰性を潔白の根拠にしない | 第4章 G-5・G-7 |
| 4 | **検査の記録を G-7 のエビデンスに加える**。1.5 のとおり、生成の適法性と出荷の適法性は別の場面である | 第4章 G-7、フェーズ5 |
| 5 | **事業者の補償に依拠して検査を省略することを禁じる**。補償は条件付きであり、条件は変動する | 第6章 テンプレ8 |
| 6 | 検知の限界を明記し、**限界を前提に責任配分を書く**。受注側に「検出されなかったこと」ではなく「定めた検査を実施し記録したこと」を求める | 第6章 テンプレ8、第8章 軸D |
| 7 | 判定の総数を増やさない。G-5 は機械判定であり判定者の帯域を消費しない。G-7 は記載事項が1つ増えるのみ | — |

### 5.3 書いてはならないこと

- 「著作権法に準拠」「文化庁の考え方に準拠」— **考え方に法的拘束力はない**
- 「複製検知により知財潔白性を保証する」— 検知は完全ではない
- ライセンス検出の精度に関する具体的な数値 — 一次情報がない
- IPA モデル契約の条項番号 — 逐語確認していない
