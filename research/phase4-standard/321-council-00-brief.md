## 2. 事象(起票者の訴え)

準拠テンプレートでは、ゲート判定 1 件ごとに `docs/gates/*.md` を人が氏名・日時・対象を手入力し、記録のための PR を作って承認・マージする。これが開発のボトルネックになっている。

- 判定 1 件ごとに記録 PR が 1 本増える。`team.json` では記録 PR にも判定者以外の承認者が要る
- `strict_required_status_checks_policy` + `require_last_push_approval` で、基底が進むたびにブランチ更新 → 承認失効 → 再承認 → CI 再実行が本体 PR と記録 PR の双方で起きる
- 停止の解除・例外承認の台帳は基底ブランチだけを読むため、本体 PR の中で用意できない(これは設計意図。`ci-gates.md:146`)
- 氏名・日時の手入力は、誰が承認したかを裏づけない。裏づけているのは承認イベントのほう

起票者の仮説: 帳票の手間で統制するのではなく、ブランチルール(強制層)でマージを止めるべきである。帳票の記入自体を AI に任せられないのは非効率である。懸念は「中身を見ずに承認・マージされること」。

## 3. 調査の要点(主宰の抜粋。詳細は各メモ)

- 規格が記録に求めるのは **Who / When / What / Outcome / Reason の帰属と改変不能**。「文書」という形式は求めない。IEC 62304 B.8.2 は「データベースの記録」で可、FDA CSA 2026 はログ・監査証跡の使用を推奨(01)
- 手入力帳票は帰属と同時性が自己申告に依存し、規制側では弱い。優れるのは理由・観点を自由に書ける点だけで、それはコメント欄でも同じ(01)
- GitHub の承認は Part 11 の**電子署名**要件は満たさない(再認証・氏名・意味の表示)。ただし電子署名要件が掛かるのは基礎規則が署名を求める記録だけで、社内の判定記録には掛からない(01)
- 承認イベントを記録と認める前提条件: 保持(監査ログは 180 日。API は Enterprise 限定)、ログイン名と実名の対応表、承認の意味の SOP 定義、commit_id 固定と stale 失効、理由は人が書く欄(01・02)
- 消える・変わるケース: 本文の編集(履歴は残る)、dismiss(DISMISSED で残る)、退会で ghost 化(user.id の事前保存が要る)。レビューと PR は削除不可。squash merge 後も head SHA と `refs/pull/N/head` は残っていた(公式保証なし)(02)
- Bot の承認: Copilot は数えない(公式)。App の承認が数えられるかは公式に未記載。bypass はパス単位に絞れない。`exempt` は監査に出ない(02)
- 業界の最小の形: **ツール生成の承認イベント + 承認者 ≠ 起案者の機械保証 + stale 失効**。SOX 監査は母集団の完全性を別途検査する(03)
- 属性は機械・判断は人: kernel の `Reviewed-by` 宣言、Gerrit の Verified / Code-Review 分離、Prow の `/lgtm` と `/approve` 分離、Chromium の Rubber Stamper は検証可能に安全な変更だけ(03)
- 手入力帳票が残る領域: 設計レビュー(820.30(e))、リリース判定の署名、Part 11 電子署名。理由は「誰がどの立場で何を審査し何を決めたか」を PR が構造として持たないため(03)
- 「中身を見たか」の機械検出は研究上も未解決。実務側は承認に**宣言**を添える(kernel、Innolitics、Chromium)(03)
- 承認の回数を増やさない(承認疲れ: 権限プロンプトの 93% を承認)。bot は承認しないか、検証可能に安全な範囲だけ(03)
- 重い手続は記録を消す(様式を 16 欄から 7 欄にして報告が 7.7 倍。`236b:326`)(00)

## 4. 既存の決定との関係(00 の 8 章から)

- **許している**: G-6 を承認レビュー(挙動要約つき)で記録すること。記録だけのコミットを PR なしで集約が受け付けること。層1 の改版に PR を課さないこと(ADR-0057)。PR 2 本・承認 2 回の構成を却下した先例(ADR-0058)
- **禁じている**: 記録の無い判定を通過とすること。PR のマージ・Issue のクローズ・ラベルを成立要件にすること(ADR-0036)。ツールを変えると成立要件が変わる構成。AI・bot の名義の承認。AI に挙動要約を書かせること。成立済みの記録の書き換え。判定の材料を判定される側が同じ変更で用意すること
- **決めていない**: 判定記録の媒体と置き場(標準本文は `docs/gates/` を規定していない)。承認イベントが成立要件か事務か。属性と判断の中身を分けて記録する形。PR に紐づかないゲートの受け皿。記録だけの変更に強制層が PR を課すか。承認の失効の粒度(#296 送り)。承認イベントの保全と保管期間。QMS 対応表(`qms-document-control.md:37-41`)と ADR-0036 の整理

## 5. 決める問い

各意見書は、Q1〜Q7 に番号で答える。「決めない」「本 Issue の範囲外」も答えとして認める。ただし理由を書く。

- **Q1 成立要件**: ADR-0036 決定1「判定記録(テンプレ4)の作成をもって成立」を維持するか、置き換えるか。置き換えるなら成立要件を何にするか
- **Q2 属性と判断の分離**: 判定記録の欄を「属性(誰が・いつ・何に・結果)」と「判断の中身(挙動要約・確認していない事項・差し戻し理由・採否の理由)」に分け、属性を強制層の記録(承認イベント等)から機械が転記する形を認めるか。認めるなら、人が書く欄の受け皿はどこか(承認レビューの本文、PR 本文、Issue コメント、別ファイル)
- **Q3 置き場と固定**: 記録を `docs/gates/` のファイルとして基底ブランチへ入れることを、ゲートごとに求めるか、出荷判定(G-7)でまとめて固定するか、求めないか。Bot による固定を認めるか(bypass の扱い)
- **Q4 PR に紐づかないゲート**: G-1〜G-4・G-8・SG の記録の受け皿をどこに置くか。判定者が成果物の作成者でもあるゲートで、ブランチ保護(作成者は自分の PR を承認できない)とどう折り合うか
- **Q5 保全**: 承認イベントを記録と認める条件(保持期間・実名対応表・user.id の保存・承認の意味の定義・エクスポート)を標準に書くか。書くならどの章か。GitHub 以外のホスティングへの一般化
- **Q6 形骸化の抑止**: 「中身を見ずに承認」を何で抑えるか。宣言(挙動要約)の形の検査、変更の小ささの基準(ADR-0058)、承認までの時間、議論の有無、内部監査の抜き取り。機械で判定しない限界の開示
- **Q7 ツール依存の吸収**: ADR-0036 が「Issue のクローズで成立」を却下した理由(ツールを変えると成立要件が変わる)を、承認イベントについてどう扱うか。「記録の意味論は標準が持ち、媒体はホスティングが持つ」という整理で足りるか

## 6. 議論の規律

- 起票者の提案が正しいという前提を置かない。却下は成果である
- 安さ・変更量の少なさを採否の理由にしない。判断軸は信頼性。ただし「重い手続は記録を消す」も信頼性の問題として扱う
- 条項の引用は `path:line` で。棚卸し(00)に無い行を引くときは、実在を確かめる
- 新しい概念語を作らない。既存の語彙(強制層、記録、承認、挙動要約、成立、事務、未達)で組み立てる
- 根拠の無い判断は、根拠水準マーク(E1〜E4)を添える
