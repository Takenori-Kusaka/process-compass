## 0. 先に事実確認を訂正します

議長の整理は「秘匿情報の統制は入る方向しか見ていない」でした。**この整理は、本標準が既に持っている出る方向の機構を1つ見落としています**。

[第5章 エージェントの追跡と統制](/process-compass/phase5-implementation/agent-trace-control/)は、遮断対象を4つ挙げています。

| 対象 | 既定 | 許可する範囲の決め方 |
| --- | --- | --- |
| 書き込み | 拒否 | 実装計画のタスクが対象とするパス |
| 読み取り | リポジトリ内は許可 | 秘匿情報を含む経路を除外する |
| **ネットワーク** | **拒否** | 依存関係の取得先など、必要な宛先のみ許可する |
| コマンド実行 | 許可リスト | 実行を許すコマンドを列挙する |

**外向きの既定拒否は、本標準に既にあります**。claude.ai への発行は、この表の3行目に当たるはずでした。

では、なぜ止まらなかったのか。**発行が「ネットワーク」として現れなかったためです**。

| 統制 | 対象 | claude.ai への発行 |
| --- | --- | --- |
| agent-trace-control 要求1 | 書き込み・ネットワーク・コマンド実行 | **いずれにも現れない**。実行基盤が組み込みで持つ機能であり、宛先の設定を経由しない |
| [第3章 3.11.6](/process-compass/phase4-process-design/roles-responsibilities/) | エージェントへ**追加する**ツール(外部連携サーバ) | **対象外**。追加していない。最初から付いている |

**穴は「出る方向が無いこと」ではありません。「実行基盤が最初から持っている手段が、どちらの統治の対象にも入らないこと」です**。3.11.6 は追加するツールを、agent-trace-control は設定できる経路を統治します。**組み込みの発行手段は、その2つの隙間に落ちます**。

この診断が正しければ、争点3 の答えは「新しい工程を置く」ではなく「既存の遮断の対象定義を直す」になります。以下、その線で書きます。

## 争点1: 不可逆4操作へ「組織外への公開」を加えるか

**結論**: **1. 採る**。ただし列挙へ1行足す形ではなく、**選定基準を本文へ書き、列挙をその基準の非網羅の例示へ変える**形で採ります。

### 理由

**第一に、本標準は既に「公開」を不可逆と判定しています**。

[第8章 安全重要度](/process-compass/phase4-process-design/tailoring-guide/)の「設計で下げられない危害」は次の4つです。

- 人体への危害(不可逆)
- **外部へ出た情報(公開、第三者への送信、漏えい)**
- 外部との間で確定した取引(送金、発注、契約の成立)
- 第三者の資産・環境への物理的な影響

同節はこう定めます。

> これらは「取り消し操作を用意した」ことをもって区分を下げられません。取り消しの可否ではなく、**取り消せない時間帯が存在すること**で判定します。

**発行を削除しても、発行されていた時間帯は消えません**。#27 の「発行が取り消せる場合でも、発行された事実は残る」は、この条文の判定基準にそのまま一致します。**新しい判断ではなく、既にある判断を別の場所へ書き写す作業です**。

**第二に、「4操作は実行環境への作用である」という整理は成り立ちません**。

| 不可逆4操作 | 軸E の「設計で下げられない危害」の対応行 |
| --- | --- |
| 削除(検証ゲート・ガード・重要テスト) | (証跡の喪失。軸Eには対応行を持たない) |
| 本番環境へのデプロイ | 第三者の資産・環境への影響 |
| **課金が発生する書き込み** | **外部との間で確定した取引(送金、発注)** |
| データベース・スキーマ変更 | (データの不可逆な変換) |

**課金書き込みは実行環境への作用ではありません。外部との取引の確定です**。4操作の3番目が既に「情報・価値が組織の外へ出て確定する」類型を含んでいます。軸E がその行の**すぐ上に**「外部へ出た情報」を置いている以上、**片方だけを4操作から外す根拠が標準内に存在しません**。

**第三に、選定基準は既に文章として存在します**。軸E の「取り消せない時間帯が存在すること」です。**4操作は、この基準を満たす操作の列挙です**。基準を書かずに列挙だけを置いたことが、今回の欠落を生みました。[ADR-0038](/process-compass/adr/0038-detection-handoff-of-control-weakening/)決定1 が統制の弱化について「性質で定義する。パスで定義しない」と決めたのと、同じ誤りです。

> パスの列挙で定義しません。パスは変更のたびに規定の改訂を要し、列挙の漏れが検知の漏れになります。

**列挙の漏れが検知の漏れになりました**。これが #27 で観測された事象です。

### 「組織外の定義を標準ができない」への回答

**定義しません。定義する必要がありません**。

本標準は既に、定義せずに遮断する形を持っています。agent-trace-control の「**既定を拒否に置く**」です。ネットワークについて、標準は「どの宛先が危険か」を定義していません。**「許可した宛先の外を拒否する」という構造だけを定義し、宛先の列挙を案件へ渡しています**。

同じ形をそのまま使います。

| 標準が定める | 組織・案件が定める |
| --- | --- |
| 発行先の既定を拒否に置くこと | 許可する発行先の列挙 |
| 列挙の外への発行を不可逆操作として扱うこと | 何をもって「組織が管理する領域」とするか |
| 列挙が存在しない案件は、発行の手段を持たないこと | — |

**「組織外」を標準が定義する必要はありません。組織が「内」を列挙すれば、外は差集合として決まります**。これは軸C のテーラリング(水準を段階で動かす)とは構造が違います。軸C は標準が3水準を用意して案件が選ぶ形ですが、ここは**標準が構造だけを置き、値を持たない**形です。近いのは軸C ではなく、**agent-trace-control のネットワーク許可リストと、第8章 軸A の担い手の指定**です。

既定値は1つだけ置きます。**案件のリポジトリと、案件の構成が指定した発行先**。これは[ADR-0047](/process-compass/adr/0047-limit-is-default-not-cutoff/)の作法により、上限ではなく既定として置きます。

### 定義の書き直し

第5章 4.2 原則4 を次へ改めます。

> **4. 不可逆操作はオーナー(価値責任者)へエスカレーションする**
>
> 不可逆操作とは、**実行後に取り消せない時間帯が存在する操作**をいいます(判定は[第8章 安全重要度](/process-compass/phase4-process-design/tailoring-guide/)の「設計で下げられない危害」によります)。次の5類型が該当します。**この列挙は網羅ではありません**([ADR-0041](/process-compass/adr/0041-scope-is-not-exhaustive/))。
>
> 1. 削除(検証ゲート、ガード、重要テストの削除を含む)
> 2. 本番環境へのデプロイ
> 3. 課金(クラウドや外部API)が発生する書き込み
> 4. データベース・スキーマ変更
> 5. **案件の構成が許可した発行先の外へ、成果物を発行・共有・送信すること**
>
> 列挙の外を探す義務は課しません(ADR-0041 決定4)。**列挙の外が遮断されるのは、既定を拒否に置く構成によります**。

**「不可逆4操作」の呼称を「不可逆操作」へ改めます**。件数を名称へ埋め込んだことが、追加を定義の変更のように見せていました。

### 根拠水準

**要ります**。根拠は初回適用案件 P-001 の1件のみであり、E2(単一事例)です。[ADR-0045](/process-compass/adr/0045-replacement-conditions-must-discriminate/)決定3 に従い、**既存の観測機構の出力を使います**。agent-trace-control 要求3 は「拒否された操作を、後から参照できる形で記録できる」ことを既に求めています。

差し替え条件は次のとおりです。**3つの観測を分けて数えます**。

| 観測 | 意味 |
| --- | --- |
| a. 発行先の許可リスト外への操作が拒否された記録 | **遮断が作動している** |
| b. 許可リスト外への発行が事後に発見された件数 | **遮断に穴がある**。経路を特定して塞ぐ |
| c. a も b も 0 のまま経過した期間 | 発行の必要が生じていない |

- **b が1件でも生じたとき**: 遮断の対象定義が不足している。定義を改める(規定の妥当性は否定されない)

**「N案件分の実績」だけを条件にしていません**。a と b と c は、遮断の作動・遮断の穴・不発生という3つの対立仮説をそれぞれ別の観測へ写します。

### 反対されうる点(自分の案の最も弱いところ)

**類型5は、他の4つと違って「案件の構成」に依存します**。1〜4は構成を参照せずに判定できますが、5は許可リストが存在しなければ判定できません。**許可リストを持たない案件では、類型5は形式的に全ての発行を不可逆操作にします**。テンプレートから作った直後の案件は、この状態から始まります。

これは[ADR-0050](/process-compass/adr/0050-enforcement-layer-is-not-staged/)が扱った「立ち上げ期に強制層が実務を止めた」事象と同じ形です。ADR-0050 は「ステージで緩和しない。強制層の設計として扱う」と決めました。**したがって既定値を、緩和ではなく設計として置く必要があります**。前掲の「案件のリポジトリ」という既定は、その最小の答えのつもりですが、**リポジトリへの Markdown 出力だけで決裁資料が成立するかは、P-001 の実績では確かめていません**(#26 案A の「図表の表現力が下がる」がそのまま残ります)。

もう1つ。**「取り消せない時間帯が存在する」という基準は、書き込みも読み取りも捕捉します**。文字どおり読めば、ほぼ全ての操作が該当しかねません。歯止めは軸E の列挙(危害の帰結が外部へ及ぶこと)ですが、**この歯止めは列挙で与えられており、基準そのものからは導けません**。基準による定義へ移す利点を主張しながら、基準の外延を列挙に頼っている点が、この案の内部矛盾です。**今回はこれを承知で採ります**。列挙のみの状態より、基準と列挙が併記された状態のほうが、次の欠落を検出できるためです。

## 争点2: 判断の種類を5つ目として足すか

**結論**: **3. 採らない + 本文も変えない**。第5章 5.5 の4分類を変えません。**足す必要がないことを、本 ADR の記録で示します**。

### 理由

**#27 の「どちらが判定するかが未定であるため、誰も判定しない」は、事実として誤りです**。標準は既に答えを持っており、[ADR-0038](/process-compass/adr/0038-detection-handoff-of-control-weakening/)がそれを決めています。

Issue はこう書いています。

> 共有範囲は統制の問題であるため Audit の職務に見えるが、「この資料を誰に見せるか」は範囲の決定であり PO の職務でもある。どちらが判定するかが未定であるため、誰も判定しない。

**「Audit の職務に見える」を、標準は明示的に否定しています**。ADR-0038 決定3 の理由がそのまま当てはまります。

> **監査担当を引き渡し先にしません**。監査は、プロセスが標準に適合しているかを事後に検証する職務です。個別の変更の許容可否を決める場にすると、監査が実行の当事者になり、次の監査で自らの判断を監査することになります。

**個別の発行の可否を監査が決めると、次の監査で監査が自らの判断を監査します**。争点1 で類型5 を不可逆操作へ入れた以上、**可否の判定者は自動的に決まります。事業決裁者(オーナー)です**。監査が見るのは、その判定が記録として成立していたかだけです。

そして、判断は1つではなく**2つに分解できます**。分解すると、既存の4分類のどれに当たるかが決まります。

| 判断 | 5.5 の種類 | 担当ロール | 根拠 |
| --- | --- | --- | --- |
| **どの発行先を許可リストへ載せるか** | **価値判断**(範囲の決定) | 価値責任者 | [ADR-0019](/process-compass/adr/0019-scope-commitment-three-layers/)決定7 が範囲の増減を価値責任者の単独判定と定める構造と同型 |
| **許可リストの外へ出すことを認めるか** | **価値判断**(不可逆操作の受容) | 事業決裁者 | 第5章 4.2 原則4。[ADR-0024](/process-compass/adr/0024-decision-as-risk-acceptance/)の「決定はリスクの受容である」 |
| 許可リスト外への発行が起きていないかの確認 | **記録の確認** | 出荷判定者 | 3.10.3 の判定資料と G-7 の記録突合 |

**「情報を外へ出してよいか」は、独立した判断の種類ではありません。範囲の決定です**。何を確約範囲に入れるかと、どこへ出すかは、いずれも**線を引く判断**であり、価値責任者が担う類型です。

5.5 はこう定めています。

> 5.8.3 との違いは、**禁止の理由**です。(中略)本節の4種類は、**結果責任(A)を負う者による判断でなければ責任の所在を失う**ため人間が担います。

**5.5 は「判断の内容」の分類ではなく、「なぜ人間でなければならないか」の分類です**。発行の可否が人間でなければならない理由は、結果責任の所在にあります。**既存の4分類の枠組みそのものです**。

### 分類を増やすことの影響

増やすと3つが壊れます。

1. **[ADR-0035](/process-compass/adr/0035-separation-by-execution-context/)決定2 の兼務判定が5×5になります**。3.5 の兼務禁止表は役割×役割で構成されており、判断の種類は担当ロールへ写像されています。5つ目の種類には対応する新ロールがないため、**種類とロールの対応が1対1でなくなります**
2. **[ADR-0037](/process-compass/adr/0037-label-points-to-lane-not-role/)のラベル語彙に、指す先のないラベルが生じます**。第5章 4.2 原則5 は「伝達する経路が明確である限りラベルを増やさない」と定めます。**経路は `state:needs-owner` で既にあります**
3. **5.5 は「1名に集中させず、種類ごとに担当を分けます」と定めています**。種類を増やして担当ロールを増やさない改訂は、この一文と整合しません

### 実装形態

**不要**。ただし**却下したことを読み取れる状態にします**([ADR-0051](/process-compass/adr/0051-usability-out-of-scope/)決定1 の作法)。新 ADR の「検討した選択肢」へ、**判断の種類を増やす案とその却下理由**を書きます。

### 変更の総量

すべて0件です。本文の増減もありません。新 ADR の中の1つの表の行が増えるだけです。

### 根拠水準

**要りません**。既存の条項(ADR-0038 決定3、5.5、4.2 原則5)からの演繹であり、実証を要する新しい主張を含みません。

### 反対されうる点

**「範囲の決定だから価値判断である」という写像は、私の解釈です**。5.5 の価値判断の定義は「何を作るか、どの順序で作るか」であり、**発行先はどちらでもありません**。文言に厳密に照らせば、5.5 の4種類のいずれにも当たらないという #27 の指摘のほうが正確です。

私は「4種類は判断の内容ではなく人間性の理由による分類である」と読み替えることで写像を成立させています。**この読み替えは 5.5 の本文に明示されていません**。同節の後段(5.8.3 との違いの説明)から導いたものです。

より正直な形は、**5.5 の価値判断の定義文を「何を作るか、どの順序で作るか、どこまでを外へ出すか」へ拡張する**ことでしょう。ただしこれは 5.5 の本文の改訂であり、「本文も変えない」という私の結論と矛盾します。**この点は会議体の判断を仰ぎます**。私は、定義文を広げるより、写像を新 ADR へ記録するほうが、次の類例(判断の種類にうまく収まらない新しい判断)への作法として再利用できると考えます。

## 争点3: 標準が置くのは工程か、遮断か、両方か

**結論**: **1. 採る — 遮断のみを置きます**。案 C(配布先の表)と案 D(発行手段を権限から外す)を**1つの機構として**採り、案 B(独立した判定工程)を却下します。案 A(判定記録の欄)は**条件付きで後置**します([ADR-0046](/process-compass/adr/0046-deferred-with-conditions/))。

### 理由

**C と D は別の案ではありません。同じ機構の許可側と既定側です**。

agent-trace-control のネットワークの行がそうであるように、「既定は拒否」(D)と「許可する宛先の列挙」(C)は、1つの構成の2つの面です。#27 が「C と D は併用できる」と書いた併用は、**実装上は1つの設定です**。したがって「工程が1つ増える」というコストは発生しません。

**案 B を却下する理由は3つです**。

1. **判定の総数を増やします**。本標準は判定を増やさない作法を一貫して採っています。[ADR-0019](/process-compass/adr/0019-scope-commitment-three-layers/)決定10「新しいゲートを設けない」、決定12「差し引きを示す」、ADR-0051 決定2「新しい判定基準ではなく、確認方法への追加」。**発行のたびに1判定を置く案は、この作法の反対です**
2. **人が判定する工程は、遮断が無い限り迂回されます**。第5章はこう定めます。「**強制層に置けない項目は、遮断できたものとして扱いません**」。判定工程は誘導層です。#27 自身が「判定工程が無い状態では、エージェントは自分が持っている発行手段を使う」と観測しました。**工程を置いても、手段が残る限り同じことが起きます**
3. **判定の対象を定義できません**。「組織外へ出す成果物すべて」を対象にするには、発行を検知する必要があります。**検知できるなら遮断できます**。検知できないなら工程も起動しません

**案 A を後置する理由**。判定記録へ「この資料の配布先はどこか」の欄を足す案は、コストが低く、遮断の穴を事後に発見する手掛かりになります。ただし [ADR-0052](/process-compass/adr/0052-delivery-is-verified-at-the-destination/)の結論が直接効きます。

> **運用は忘れられます。データは検査できます**。

**欄を足しても、書かれなければ検出できません**。まず遮断を置き、遮断の記録(争点1 の観測 a・b)で足りるかを見ます。足りないと分かった時点で欄を足します。

**採る条件**(ADR-0046 決定2 の要件を満たす形で書きます)。

> 争点1 の観測 b(許可リスト外への発行が事後に発見された件数)が**1件以上生じ、かつその発行がゲート判定を伴う成果物であったとき**。この場合、遮断の記録だけでは発見できなかったことになるため、判定記録の欄を新設する。

### 逸脱の経路

許可リスト外へ発行する必要が生じた場合の経路を、**新設しません**。既存の経路に載ります。

```
発行の試行 → 強制層が拒否 → state:needs-owner を付与 → 事業決裁者が判定
```

判定が「認める」であった場合、これは基準未達のまま先へ進む決定であるため、**[第7章 7.6](/process-compass/phase4-process-design/exception-escalation/)の例外承認の対象**です。7.3 / 7.6 の既存の手続をそのまま用います。**新しい様式を作りません**。

### #26(仕組みの不在)への回答

#26 は Platform 宛の別 Issue ですが、**争点1 の類型5 は、#26 の案 E を前提にしないと成立しません**。許可リストを置く場所が要ります。

標準の側は、置き場所を指定しません([ADR-0010](/process-compass/adr/0010-data-doc-interface/)のデータ・文書の界面による)。標準が要求するのは次の3点です。

| # | 要求 |
| --- | --- |
| 1 | 許可する発行先を、案件ごとに版管理下の構成として指定できる |
| 2 | 指定の変更が、エージェント自身の操作では行えない(agent-trace-control 要求4 と同じ) |
| 3 | 指定が存在しない案件では、リポジトリの外への発行が拒否される |

**要求3 が、既定を「拒否」にする実体です**。テンプレート側での実装形態は、#26 の案 E(`process.config.json` の項目)が要求1と2を満たします。

### 実装形態

- **争点1 の新 ADR に含める**(別 ADR を立てません。定義の変更と遮断の設置は1つの決定です)
- **条文の修正**: agent-trace-control の遮断対象表と要求仕様
- **強制層**: 発行先の既定拒否
- **案 A**: 条件付きで後置。新 ADR の帰結節へ条件を記録する

### 変更の総量

争点1 の表に含まれます。**追加の判定・会議体・台帳はいずれも0件です**。

### 根拠水準

**要ります**。争点1 と同じマーク1件で足ります。**遮断のみで足りるという判断そのものが、実証を持ちません**。差し替え条件は争点1 の a / b / c を共有します。**特に b は、案 A を後置から採用へ移す条件でもあります**。1つの観測が2つの決定の分岐を与える形にしています。

### 反対されうる点

**遮断の実装が、標準の要求仕様を満たす基盤に依存します**。agent-trace-control は「実装の手段を指定しません」と定めていますが、**組み込みの発行手段を無効化できる設定を持たない実行基盤では、要求3 が満たせません**。その場合、本標準の作法に従えば「遮断できたものとして扱わない」となり、**案件は発行手段を持つエージェントを使えないことになります**。これは実務上かなり強い制約です。ADR-0050 が扱った事象1(遮断範囲の誤りで担当が仕事をできなくなった)と同じ形の事故を招きうると考えます。

もう1つ。**私は案 B を「判定を増やす」として却下しましたが、争点1 で類型5 を不可逆操作へ入れたことにより、実質的にはエスカレーションという判定が1つ増えています**。「判定の総数は増えない」という主張は、**遮断が正常に働き、逸脱が生じない場合にのみ正しい**。逸脱のたびに事業決裁者の判定が起動します。P-001 の実績で発行がどの程度の頻度で必要になるかを、私は把握していません。

## 争点4: ADR-0051 の論法が、ここでも使えるか

**結論**: **半分だけ使えます。「扱わない」という結論は使えません**。

### ADR-0051 の論法の構造

0051 は2つの理由で対象外としました。

| # | 理由 | 本件へ当てはまるか |
| --- | --- | --- |
| 1 | **判定できない**。使いやすさの判定は評価者の主観に依存し、5.7.4 が禁じた記述の質の判定と同じ構造になる | **当てはまりません** |
| 2 | **扱うと標準が製品の良し悪しを判定することになる** | **当てはまりません** |

**理由1 が当てはまらない根拠**。「発行先が許可リストに載っているか」は**列挙との照合**であり、機械判定できます。主観の入る余地がありません。**判定できないのは「その資料を出してよいか」の中身であって、「許可された宛先か」ではありません**。本件の争点1 は前者を標準の判定対象にしていません。

**理由2 が当てはまらない根拠**。発行先の遮断は、製品の良し悪しを判定しません。**判定するのは、統制が設計どおり作動したかです**。これは本標準の中核の対象です。

### 決定的な違いは帰属です

0051 は、帰属の確認をこう結論しました。

> 「見て気づけるか」を問う工程が標準に無い | **標準の落ち度ではない**

理由は、受入基準の内容は案件側の仕様設計であり、標準は受入基準の内容を規定しないためです。

**本件は逆です。標準は、エージェントに与える権限を規定しています**。3.11.6(外部ツールの統治)、agent-trace-control(既定拒否)、5.4.3 不変条件4(適用範囲の拡大を AI が決定してはならない)。**権限を規定する立場を採った以上、権限の穴は標準の落ち度です**。

| | ADR-0051(使いやすさ) | 本件(発行先) |
| --- | --- | --- |
| 標準はこの領域を規定しているか | **していない**。受入基準の内容は案件側 | **している**。エージェントの権限は標準の対象 |
| 判定は機械化できるか | できない | **できる**(許可リストとの照合) |
| 扱うと標準が何を判定することになるか | 製品の良し悪し | **統制の作動**。本標準の中核 |
| 結論 | 扱わない | **扱う** |

### 使える半分

0051 決定3 の形は、そのまま使えます。

> **標準は、何を価値とするかを指定しません**。指定するのは、価値として書いたものに受入基準が対応しているかだけです。

これを本件へ写すと、争点1 で述べた形になります。

> **標準は、何を出してよいかを指定しません**。指定するのは、**出してよい先の列挙が存在するか**と、**列挙の外への経路が塞がれているか**だけです。

**0051 が確立したのは「扱わない」という結論ではなく、「中身を規定せずに構造だけを規定する」という作法です**。本件はその作法を使い、結論だけを逆にします。

### 実装形態

**不要**。新 ADR の「検討した選択肢」へ、**ADR-0051 と同型の扱い(対象外とする)を検討し、却下した記録**を1行残します。**却下は成果です**。「使いやすさは扱わないのに、なぜ発行先は扱うのか」という問いは必ず出ます。**答えを本 ADR に残さなければ、次の会議体は同じ比較をやり直します**(ADR-0046 コンテキストの「保留と書くと条件が消える」と同じ)。

### 変更の総量

0件。新 ADR の表に1行。

### 根拠水準

**要りません**。既存 ADR の論法の適用可否の判定であり、実証を要しません。

### 反対されうる点

**「標準が規定している領域だから落ち度である」という論法は、広く取りすぎると標準の責任範囲が無限に広がります**。本標準はエージェントの権限を規定していますが、規定しているのは**要求仕様**であって、実行基盤が持つ全機能の統治ではありません。「組み込みの発行手段まで標準が見るべきだった」という私の主張は、**同じ論法で「実行基盤が持つ他の全機能も見るべきだった」まで進みます**。

歯止めは ADR-0041 決定4(列挙の外を探す義務は課さない)に置くつもりですが、**義務を課さないことと落ち度を認めることは両立しにくい**と自覚しています。より弱く、より正確な言い方は「**落ち度ではないが、今回の観測により列挙の不足が判明したため直す**」でしょう。その言い方であれば ADR-0041 と矛盾しません。**私はこちらを推します**。

### 標準が定義できるものと、できないもの(総括)

議長からの問い「標準が工程だけを置き、基準を組織へ委ねる形が成立するか」への答えです。

**成立します。ただし工程ではなく、既定値の向きを置く形でです**。

| 標準が定義する | 根拠 |
| --- | --- |
| 不可逆操作の**選定基準**(取り消せない時間帯が存在すること) | 第8章 軸E の既存の判定文言 |
| 発行先の**既定を拒否に置く**構造 | agent-trace-control「既定を拒否に置く」 |
| 許可リストの**指定手段が満たすべき要求**(版管理・エージェントによる変更の禁止) | agent-trace-control 要求2・要求4 |
| 逸脱時の**判定者**(事業決裁者)と**経路**(`state:needs-owner` → 7.6) | ADR-0038 決定3、ADR-0037 |

| 標準が定義しない | 委ねる先 |
| --- | --- |
| 「組織外」の範囲 | 組織(許可リストの内側を列挙することで、外は差集合として決まる) |
| 何を出してよいかの基準 | 組織 |
| 許可リストの置き場所と形式 | テンプレート・案件(ADR-0010 のデータ・文書の界面) |
| 発行の遮断の実装手段 | 実行基盤(agent-trace-control「実装の手段を指定しません」) |

**この構成は軸C のテーラリングとは別物です**。軸C は標準が3水準を用意して案件が選ぶ形ですが、本件は**標準が値を1つも持たない**形です。同型なのは軸C ではなく、**agent-trace-control のネットワーク許可リスト**です。本件は、その機構に対象を1つ足す提案として読むのが最も正確です。
