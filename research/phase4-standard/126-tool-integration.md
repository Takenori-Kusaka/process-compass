## 1. プロセスのテーラリングに関する規格・標準の考え方

### 1.1 ISO/IEC/IEEE 12207:2017 — 「テーラリングしても適合を主張できる」枠組み

**確認できたこと（複数ソース一致、規格本文は未取得）**:

12207:2017 は適合（conformance）の主張方法を 2 系統に分けている。

- **完全適合（full conformance）**
  - **タスクへの完全適合**: 宣言したプロセスのアクティビティ・タスクの全要求を満たす場合に主張できる
  - **アウトカムへの完全適合**: 宣言したプロセスの必須アウトカムをすべて達成した場合に主張できる
- **テーラード適合（tailored conformance）**
  - 完全適合の資格を満たさないプロセス集合を、本規格を基礎として構築する場合、**Annex A に規定されたテーラリングプロセスに従って**箇条を選択・修正する
  - テーラリングした本文（tailored text）を**宣言する**
  - テーラード適合は、**テーラリング後のアウトカム・アクティビティ・タスクが達成されたことを示す**ことで達成される

**Annex A は normative（規定）**であり、本規格のテーラリングを実施するために必要な基本アクティビティを定義する。テーラリングの根拠は「テーラリングの理由・影響を受けるプロセス・影響の性質と範囲」の形で記録することが求められる。

- ISO 公式（書誌・Scope）: https://www.iso.org/standard/63712.html
- CSA（採用版の Scope 記載。conformance の 2 系統に言及）: https://www.csagroup.org/store/product/CAN-CSA-ISO-IEC-IEEE%2012207:18/
- ANSI Webstore（同上）: https://webstore.ansi.org/standards/csa/csaisoiecieee122072018
- Wikipedia（二次、Annex A の位置づけ）: https://en.wikipedia.org/wiki/ISO/IEC_12207
- 参考: 前身の ISO/IEC 12207:2008（IEEE 版、公開 PDF）— Annex A "Tailoring process" の構造が確認できる: https://wildart.github.io/MISG5020/standards/IEEE-12207-2008.pdf

**この論点の要旨（本 Issue に直結）**: 規格の世界では「テーラリングは適合の放棄ではない」。ただし条件が 3 つある。

1. **規定されたテーラリング手順に従う**こと（勝手な省略ではない）
2. **何をテーラリングしたかを宣言・文書化する**こと（差分の可視化）
3. **テーラリング後の状態で、アウトカムの達成を実証できる**こと（削っても目的は残る）

→ テーラリング・シミュレーターの出力は「調整済みプロセス」だけでなく、**「標準からの差分」と「その理由」をセットで出力**すべき、という規格側の裏付けになる。

### 1.2 ISO/IEC/IEEE 24774:2021 — プロセス記述の要素

**確認できたこと（規格本文は未取得、ISO 公式書誌 + SEBoK に依拠）**:

- 24774 は「プロセス記述の仕様（Specification for process description）」。旧版は TR（技術報告書）で "Guidelines"、2021 年版は国際規格（IS）となり "Specification" へ昇格している
- 記述要素として最も頻繁に使われるものを規定: **title（名称）/ purpose（目的）/ outcomes（アウトカム）/ activities（アクティビティ）/ tasks（タスク）/ information item（情報項目）**
- **最小限の記述は Name・Purpose・Outcomes の 3 要素**。inputs / outputs / activities / tasks は必要に応じて追加でき、必須ではない（SEBoK による要約）
- process outcome = プロセス目的の達成が成功したことの**観察可能な結果**
- 目的は、プロセス参照モデル間の**一貫性**を促し、理解可能・比較可能・管理可能にすること

- ISO 公式（2021 年版）: https://www.iso.org/standard/78981.html
- IEEE SA: https://standards.ieee.org/ieee/24774/10126/
- SEBoK "Process Description"（二次だが SE 分野の標準的解説）: https://sebokwiki.org/wiki/Process_Description
- ISO 公式（2010 年版 TR、要素の列挙が Scope に記載）: https://www.iso.org/standard/53815.html

**本 Issue への含意**: 知識ベース（`src/data/tailoring/practices.yaml` 等）のプラクティス記述スキーマは、**最低限 name / purpose / outcomes を持つべき**。「アウトカムは観察可能な結果として書く」という規定は、テーラリング時に「タスクは削るがアウトカムは残す」という判定を可能にする前提条件になる。

### 1.3 ISO/IEC 33020 — プロセス能力レベルはテーラリングに使えるか

**確認できたこと（規格本文は未取得。iteh.ai の書誌ページおよび複数解説に依拠）**:

- 能力（capability）は **6 段階の順序尺度**: レベル 0 Incomplete / 1 Performed / 2 Managed / 3 Established / 4 Predictable / 5 Innovating（33020:2015 で従来の "Optimizing" が "Innovating" に改称）
- 各プロセス属性は **N-P-L-F の 4 段階**で評定する: Not achieved（0〜15%）、Partially achieved（>15〜50%）、Largely achieved（>50〜85%）、Fully achieved（>85〜100%）

- ISO 公式（2019 年版）: https://www.iso.org/standard/78526.html
- iteh.ai 書誌（2015 年版）: https://standards.iteh.ai/catalog/standards/iso/1dd38d57-46ca-486c-b5a5-2463ae851cb7/iso-iec-33020-2015
- ISACA Journal（COBIT 5 PAM の 330xx 対応。レベルと N-P-L-F の解説、二次）: https://www.isaca.org/resources/isaca-journal/issues/2018/volume-1/a-cobit-5-pam-update-compliant-with-isoiec-330xx-family

**評価（考察）**: 33020 は**「今どこにいるか」の測定**の枠組みであり、**「何を適用すべきか」の選択**の枠組みではない。テーラリングの直接の根拠には使えない。ただし次の 2 点で流用価値がある。

- **N-P-L-F の 4 段階評定**は、診断ツールの「現状の実施度」入力の尺度としてそのまま使える（自己申告を 0/1 の二値にしないための先例）
- **レベル 1→2→3 の順序**（まず実施 → 管理 → 標準化）は、提案の**実施順序**の根拠になる。「Established（組織標準化）を、Performed（実施できている）より先に勧めない」というルール制約に落とせる

### 1.4 CMMI — 組織標準プロセスのテーラリング指針に求められる要素

**確認できたこと（CMMI 本文は有償。wibas 等の解説に依拠、二次情報）**:

CMMI-DEV の Organizational Process Definition（OPD）SP 1.3「Establish Tailoring Criteria and Guidelines」が、テーラリング指針に求める内容は以下。

- 組織標準プロセス集合と組織プロセス資産を**どう使って defined process を作るか**の記述
- defined process が**満たさなければならない要求**（削ってはいけない下限）
- **行使できる選択肢**と、選択肢を選ぶ**基準**
- テーラリングを**実施・文書化する手順**
- **ライフサイクルモデルの選択基準**、**プロセス要素の選択基準**
- defined process を文書化するための**標準（様式）**
- 組織標準プロセスからの**逸脱（waiver）の申請・承認手順**

また、柔軟性（ドメイン・顧客の性質・コスト/納期/品質のトレードオフ等の文脈変数への対応）と、組織横断の一貫性（組織標準・目標・戦略が適切に扱われること）の**バランス**が必要とされる。

- wibas OPD SP 1.3: https://www.wibas.com/cmmi/opdsp-13-establish-tailoring-criteria-and-guidelines
- wibas OPD 概要: https://www.wibas.com/cmmi/organizational-process-definition-opd-cmmi-dev
- cmmi.co.uk OPD: https://www.cmmi.co.uk/cmmi/OPD.htm

**本 Issue への含意**: CMMI が要求する要素のうち、本標準の知識ベースにまだ明示的な受け皿がない可能性が高いのは **(a) 削ってはいけない下限（必須要求）の明示**、**(b) waiver（逸脱）の申請・承認手順**の 2 つ。テーラリング・シミュレーターは「省略可」を提案するだけでなく、「これは省略不可」「省略するなら誰の承認が要る」を返す必要がある。

### 1.5 【日本の公的先例】デジタル庁「デジタル・ガバメント推進標準ガイドライン」のテーラリング

**確認できたこと（デジタル庁 公式 PDF。ただしテキスト抽出に失敗したため、検索エンジンが抽出した同 PDF の本文断片に依拠。ページ番号未確認）**:

- 定義: **「テーラリングとは、個々のプロジェクトの特性等に応じて、手続・手順や成果物などを適切に調整して適用することをいう。」**
- 実施主体: **PJMO**（プロジェクト推進組織）。「PJMO は、プロジェクトを主体的に推進する必要があるため、政府情報システムに関する法令や各府省で定められているルールを順守することを前提に、プロジェクトの目的や特性等を踏まえて、テーラリングを適切に実施するものとする」
- 前提となる問題認識: 第3編 IT マネジメントは「多くのプロジェクトに共通する状況を前提として実施内容を示している」ため、**画一的に適用してもプロジェクトが目指す成果を達成できない懸念**がある
- 専門家からの支援・助言を受けることができる

- デジタル庁「標準ガイドライン 解説書（第3編第1章 IT マネジメントの全体像）」2025-06-19 版: https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/e2a06143-ed29-4f1d-9c31-0f06fca67afc/573c839f/20250619_resources_standard_guidelines_guideline_03.pdf
- DS-100 デジタル・ガバメント推進標準ガイドライン（2025-05-27 改定案）: https://www.digital.go.jp/assets/contents/node/basic_page/field_ref_resources/44df7733-3df2-4e47-bf0b-85c0353c20c7/0dd18334/20250527_meeting_executive_guideline_draft_02.pdf
- 政府CIOポータル 標準ガイドライン群: https://cio.go.jp/guides/

**これが重要な理由（考察）**: 本標準は日本語圏の読者を対象としている。**「テーラリング」という語は、日本政府の公式ガイドラインに既に定義済みの用語である**。本標準がこの定義と整合する語義を採ることで、日本の SIer・受託開発・公共調達の文脈にそのまま接続できる。デジタル庁の定義は「手続・手順や成果物などを適切に調整して適用すること」であり、本標準の「調整済みプロセスを提案する」という目標と一致する。

**建前と実運用の乖離に関する所見（考察、裏付けは弱い）**: デジタル庁ガイドラインは「法令・府省ルールの順守を前提に」という制約を明示的に置いている。これは実務上、テーラリングが「削れるものを削る」方向に流れやすいことへの牽制と読める。同種の牽制（削ってはならない下限の明示）は、本標準のシミュレーターにも必要。

## 2. 安全重要度による分類軸の実例

### 2.1 IEC 62304 — ソフトウェア安全クラス A / B / C

**確認できたこと（規格本文は有償・未取得。複数の独立した解説が一致、二次情報）**:

| クラス | 判定基準（危害の程度） |
|---|---|
| A | 傷害または健康被害が起こり得ない |
| B | 傷害は起こり得るが重篤ではない |
| C | 死亡または重篤な傷害が起こり得る |

分類の性質:

- **最悪ケースの故障シナリオ**で判定する。意図した便益や正常運用時の挙動では判定しない
- **ソフトウェア項目（コンポーネント）ごとに分類**し、**最上位のクラスがシステム全体のクラスを決める**
- クラスが上がるほど、ライフサイクル・検証・文書化の要求が厳しくなる

要求の増分の仕方（この「積み上げ方式」が本 Issue にとって最も重要）:

- クラス A: ソフトウェア要求 と ソフトウェアリリース の文書化
- クラス B: 上記に加えて **ソフトウェアアーキテクチャ** と **ソフトウェア検証** の文書化
- クラス C: 上記に加えて **詳細設計** の文書化

- Johner Institute（二次、医療機器規制の定番解説）: https://blog.johner-institute.com/iec-62304-medical-software/safety-class-iec-62304/
- Greenlight Guru（二次）: https://www.greenlight.guru/blog/iec-62304-software-safety-classes
- OpenRegulatory IEC 62304 Walkthrough（二次）: https://openregulatory.com/articles/iec-62304-walkthrough
- MD101 Consulting（第2版でのクラス判定、二次）: https://blog.cm-dm.com/post/2024/03/15/Is-my-software-in-class-A,-B,-C-IEC-62304-2nd-edition

**構造の抽出**: **危害の深刻度 1 軸 × 3 段階。上位クラスは下位クラスの要求を包含する（入れ子・単調増加）。** 段階が上がるごとに「作らねばならない成果物」が追加される。

### 2.2 NASA NPR 7150.2 — ソフトウェアクラス A〜F（〜H）

**確認できたこと（NASA 公式ドメイン。ただし Requirements Mapping Matrix 本体は未取得）**:

クラス定義（NASA Software Engineering Handbook 7.02 より要約）:

| クラス | 内容 |
|---|---|
| A | 有人宇宙飛行システムと直接やり取りする地上・飛行ソフトウェア（機体運用、クルー安全、主要ミッション機能） |
| B | 無人宇宙機・大型航空機の主要ミッション目的を担うソフトウェア（推進・誘導・コマンド） |
| C | ミッション支援（副次的な科学目的、データ解析、施設運用、試験） |
| D | 基礎的な科学・工学ソフトウェア（設計ツール、二次データ解析、実験室運用、意思決定支援）。故障の影響は軽微 |
| E | 研究・技術開発ソフトウェア（設計コンセプト検討等）。「欠陥は単一ユーザまたは小グループに影響し得る」 |
| F | 業務・IT インフラ（財務システム、全社アプリケーション等） |

分類の判断基準（5 観点）:

1. NASA システム内での**用途**
2. NASA プログラムにとっての**重要度**
3. **人間の依存度**（human dependence）
4. **開発・運用の複雑さ**
5. **エージェンシーの投資額**

要求の増減の仕方:

- 「クラス A〜E はエンジニアリング系ソフトウェアを、適用される NPR 7150.2 要求の**多い順**に並べたもの」。クラス F 以降は業務・IT 系で NPR 7120.2 の要求の多い順
- **Requirements Mapping Matrix** を用い、**下位クラスおよび非安全クリティカル指定のソフトウェアでは、適用される要求の数と厳格さがスケールバックされる**
- 「クラス分類は、本質的にソフトウェアエンジニアリング要求の**事前テーラリング（pre-tailoring）**を提供する」
- **安全クリティカル指定は、A〜H のクラスとは別軸**で付与される（重要）
- マトリクスにはテーラリング欄・テーラリング根拠・**承認署名欄**が含まれる（NASA-HDBK-2203）

- NASA SWEHB 7.02 Classification and Safety-Criticality（一次）: https://swehb.nasa.gov/display/SWEHBVD/7.02+-+Classification+and+Safety-Criticality
- NASA SWEHB SWE-020 Software Classification（一次）: https://swehb.nasa.gov/display/7150/SWE-020+-+Software+Classification
- NPR 7150.2D Appendix C Requirements Mapping Matrix（一次、NODIS）: https://nodis3.gsfc.nasa.gov/displayDir.cfm?Internal_ID=N_PR_7150_002D_&page_name=AppendixC
- NPR 7150.2D 本体（一次、NODIS）: https://nodis3.gsfc.nasa.gov/displayDir.cfm?t=NPR&c=7150&s=2D

**未確認**: 各クラスに何件の要求が適用されるかの具体的な件数。Appendix C のマトリクス表自体は取得できていない。

**構造の抽出**: **多要因の総合判定 1 軸 × 6〜8 段階 + 独立した安全クリティカル・フラグ。** そして本 Issue にとって決定的な発想が「**分類とは事前テーラリングである**」という NASA の明示的な位置づけ。

### 2.3 DO-178C — ソフトウェアレベル A〜E と目標数

**二次情報のみ（DO-178C 本文は RTCA の有償文書。複数の独立ソースが同一数値を提示している）**:

| レベル | 故障状態の重大度 | 目標数 |
|---|---|---|
| A | Catastrophic（壊滅的） | 71 |
| B | Hazardous（危険） | 69 |
| C | Major（重大） | 62 |
| D | Minor（軽微） | 26 |
| E | No safety effect（安全影響なし） | 0 |

- Rapita Systems DO-178 ガイド（二次、認証ツールベンダ）: https://www.rapitasystems.com/do178
- eInfochips（二次、同数値）: https://www.einfochips.com/blog/understanding-do-178c-certification-artifacts-and-software-life-cycle-data-items-for-various-dals/
- Ansys（二次）: https://www.ansys.com/simulation-topics/what-is-do-178c
- arc42 Quality Model（二次）: https://quality.arc42.org/standards/do-178c

**未確認**: 「独立性（independence）をもって満たすべき目標数」（レベル A で 30 件台と言われる）は一次確認できていない。**本標準で数値を引用するなら 71/69/62/26/0 までに留めること。**

**数値の検証について**: 依頼で警告のあった「根拠なき数字」とは性質が異なる。71/69/62/26 は DO-178C Annex A の Table A-1〜A-10 を数え上げた**決定的な数値**であり、複数の独立した業界ソースが完全に一致している。ただし RTCA 原典を直接確認していない以上、本標準では「二次情報による」と注記すべき。

**構造の抽出**: **故障の重大度 1 軸 × 5 段階。段階を目標（objective）の件数で定量的に表現している。** 「レベル E は目標ゼロ = プロセス要求なし」という下限の置き方が、テーラリングの下限設計として参考になる。

### 2.4 EU AI Act — リスク 4 区分

**確認できたこと（EU AI Act の条文解説サイト。EU 公式条文そのものは未取得）**:

| 区分 | 扱い |
|---|---|
| 許容できないリスク（Unacceptable） | **禁止**。ソーシャルスコアリング、操作的 AI、脆弱性の悪用、公共空間でのリアルタイム顔認証（原則）等。展開自体が違法なので「義務」は存在しない |
| 高リスク（High） | 厳格な義務。**リスクマネジメントシステム、データガバナンス、技術文書、人間による監督（human oversight）、品質マネジメントシステム**の確立。提供者（provider）と利用者（deployer）で義務の重さが異なる |
| 限定的リスク（Limited） | **透明性義務**のみ。「エンドユーザが AI とやり取りしていることを認識できるようにする」（チャットボット、ディープフェイク）— Article 50 |
| 最小リスク（Minimal） | 義務なし。スパムフィルタ、ゲーム等、現行 AI アプリの大半 |

高リスクの判定（Article 6）:

- Annex I の法令が対象とする製品の**安全コンポーネント**であり、第三者適合性評価が必要なもの、**または**
- Annex III の用途リスト（雇用選考、教育アクセス、法執行、給付適格性判定等）に該当するもの
- **例外**: 狭い手続的タスクの実行、先行する人間の判断の改善、パターン逸脱の検出などで、人間のレビューを置き換えないものは自動的には高リスクとならない
- ただし Annex III 用途で**自然人のプロファイリング**を行うものは常に高リスク

施行スケジュール: 2024-07-12 発効、禁止規定は 2025-02-02 から適用。

- artificialintelligenceact.eu High-level summary（EU 公式ではないが条文全文と対照可能な参照実装的サイト）: https://artificialintelligenceact.eu/high-level-summary/
- Article 6 条文: https://artificialintelligenceact.eu/article/6/

**構造の抽出**: **1 軸 × 4 段階だが、上限側が「禁止」で閉じている**点が他と決定的に異なる。IEC 62304 や DO-178C は「厳しくすれば何でも作れる」が、AI Act は「どれだけ厳しくしても作ってはいけない領域」を置く。また判定が**用途リスト（列挙）＋除外規定**という形式で、危害の深刻度からの演繹ではない。

### 2.5 IMDRF SaMD — リスク区分 I〜IV（2 軸マトリクス）

**確認できたこと（IMDRF/SaMD WG/N12FINAL:2014。PDF は取得タイムアウト。IMDRF 公式 PDF の URL は特定済み、内容は検索抽出と複数解説に依拠）**:

2 軸で判定する。

- **軸1: 医療状況・状態（State of healthcare situation or condition）** — Non-serious（非重篤）→ Serious（重篤）→ Critical（危機的）
- **軸2: 提供する情報の重要性（Significance of information provided）** — Inform clinical management（他の情報と併せて判断材料の一つ）→ Drive clinical management（臨床判断の主要な根拠だが他情報と併用）→ Treat or diagnose（情報単独で直ちに臨床行為を決定する）

区分の割り当て（3×3 マトリクス）:

| 医療状況 \ 情報の重要性 | Treat or diagnose | Drive | Inform |
|---|---|---|---|
| Critical | **IV** | III | II |
| Serious | III | II | I |
| Non-serious | II | I | I |

**この表の各セルの割り当ては複数の二次解説から再構成したもので、N12 原典での逐語確認はできていない。** ただし「Critical × Treat/diagnose = IV（最高）」「Non-serious × Inform = I（最低）」の両端は複数ソースで一致している。

- IMDRF/SaMD WG/N12FINAL:2014（一次、URL 特定済み・本文未取得）: https://www.imdrf.org/sites/default/files/docs/imdrf/final/technical/imdrf-tech-140918-samd-framework-risk-categorization-141013.pdf
- IMDRF/SaMD WG/N81 FINAL:2025（一次、より新しいリスク特性化文書）: https://www.imdrf.org/sites/default/files/2025-01/IMDRF_SaMD%20WG_Software-Specific%20Risk_N81%20Final_0.pdf
- Complizen（二次）: https://www.complizen.ai/post/samd-risk-categories
- UL Solutions（二次）: https://www.ul.com/insights/software-medical-device-why-defining-intended-use-and-risk-categorization-critical

**構造の抽出**: **2 軸 × 各 3 段階 → 4 区分に縮約。** 対角線上のセルが同じ区分に落ちる（縮約写像）。他の分類が「危害の深刻度」1 軸なのに対し、IMDRF は **「危害の深刻度」×「システムの決定への関与度」** を掛け合わせている。**これは本標準の設計にそのまま応用できる唯一の 2 軸モデル。**

### 2.6 5 実例に共通する分類の構造（考察）

| 実例 | 軸の数 | 段階数 | 判定の方法 | 増減するもの |
|---|---|---|---|---|
| IEC 62304 | 1（危害の深刻度） | 3（A/B/C） | 最悪ケース故障の帰結 | 必須成果物（入れ子で追加） |
| NASA NPR 7150.2 | 1（総合）+ 安全フラグ | 6〜8（A〜F/H） | 5 観点の総合判断 | 適用要求の件数と厳格さ |
| DO-178C | 1（故障の重大度） | 5（A〜E） | 機体レベルの安全性評価から割当 | 目標（objective）の件数 |
| EU AI Act | 1（用途 + 影響） | 4（禁止/高/限定/最小） | 用途リスト列挙 + 除外規定 | 義務の種類（禁止で上限が閉じる） |
| IMDRF SaMD | **2**（状況の深刻度 × 情報の重要性） | 3×3 → 4 区分 | マトリクス縮約 | 規制上の管理の厳しさ |

**共通する構造として抽出できるもの**:

1. **軸はほぼ常に「危害の深刻度」**。技術的複雑さやチーム規模ではない
2. **段階は 3〜5 が主流**。6 段階以上（NASA）は複数ドメインを 1 表に押し込んだ結果であり、単一ドメインなら 3〜4 が実用的
3. **単調増加・入れ子**: 上位段階は下位段階の要求を包含する。「上位では別のことをする」ではなく「上位では追加でこれもする」
4. **段階の差は「成果物の有無」か「目標/要求の件数」で表現される**。抽象的な「より厳格に」ではなく、**列挙可能な差分**として定義されている
5. **分類は事前テーラリングである**（NASA の明示的な言明）。分類とテーラリングは別物ではなく、分類が最も粗いテーラリングの単位
6. **深刻度の軸と「AI/システムがどれだけ決定に関与するか」の軸は分離できる**（IMDRF、および EU AI Act Art.6 の「人間のレビューを置き換えないものは高リスクでない」という除外規定）

## 3. 提案書・診断結果の出力フォーマット

### 3.1 推薦の説明可能性（explainability）と受容・信頼

**確認できたこと（査読論文・学術出版）**:

- 推薦の説明インタフェースがシステムの透明性を提供し、ユーザの受容を高めることは、エキスパートシステムや知的教育システムを含む複数分野で認識されてきた（Pu & Chen, *Knowledge-Based Systems*, 2007「Trust-inspiring explanation interfaces for recommender systems」）
  - https://www.sciencedirect.com/science/article/abs/pii/S0950705107000445
- **重要なニュアンス（本標準の設計に直結）**: Cramer らのコンテンツベース美術推薦システムの実験では、**「なぜその推薦をしたか」の説明は推薦の受容（acceptance）を高めた**が、**システムそのものへの信頼（trust）は透明性によって改善されなかった**。また**システムの確信度（certainty）の提示は信頼・受容のいずれにも影響しなかった**
  - Vrije Universiteit Amsterdam 公式レコード: https://research.vu.nl/en/publications/the-effects-of-transparency-on-trust-in-and-acceptance-of-a-conte/
- 説明可能性の統合は推薦の精度を改善し、ユーザ満足と信頼を有意に高めるという報告もある（Frontiers in AI, 2024）
  - https://www.frontiersin.org/journals/artificial-intelligence/articles/10.3389/frai.2024.1410790/full
- 透明性を提供する説明は、**グローバルな説明（意思決定プロセス全体の説明）**と**ローカルな説明（個別推薦の説明）**の 2 種類に分けられる
- 透明性・信頼と知的システム受容の関係についての利用者調査（*Electronic Markets*, 2022）: https://link.springer.com/article/10.1007/s12525-022-00593-5

**含意（考察）**: 「説明を付ければ信頼が上がる」と単純化しないこと。実証されているのは主に**受容（この推薦に従おうと思う度合い）**への効果である。そして**確信度スコアの提示には効果がない**という知見は、シミュレーターに「マッチ度 87%」のようなスコアを出す設計を採らない根拠になる。出すべきは**理由**であって**スコア**ではない。

### 3.2 自動化バイアスと Cognitive Forcing Function

**確認できたこと（ACM 査読論文、政府系シンクタンク報告書）**:

- 自動化バイアス = 自動システムに過度に依拠する傾向。自動推薦に過剰な重みを与え、独立した検証を減らし、システムの誤りをそのまま引き継ぐ。**高リスク・高認知負荷のタスクで特に強い**
- Buçinca, Malaya, Gajos「To Trust or to Think: Cognitive Forcing Functions Can Reduce Overreliance on AI in AI-assisted Decision-making」*Proc. ACM Human-Computer Interaction* 5(CSCW1), 2021
  - https://dl.acm.org/doi/10.1145/3449287
  - **主要な知見**: cognitive forcing は、単純な説明可能 AI（XAI）手法よりも**過剰依存を有意に減少させた**。しかし、**過剰依存を最も減らした設計に対して、被験者は最も低い主観的評価を与えた**（効果と好感度がトレードオフ）
- Cognitive Forcing Function の手段: 内省を促すプロンプト、意図的な遅延（AI の回答を見る前に自分の判断を出させる）、根拠の記述を必須にする
- 摩擦は必要だが、過剰な妨害は認知負荷を増やし、タスク成績や信頼を下げる。**適切に較正する必要がある**
- CSET（ジョージタウン大）Issue Brief "AI Safety and Automation Bias"（2024-11）: https://cset.georgetown.edu/wp-content/uploads/CSET-AI-Safety-and-Automation-Bias.pdf

**含意（考察、本 Issue の核心）**: **提案ツール自身が自動化バイアスの発生源になる。** 「あなたの組織にはこのプロセスが最適です」と断定的に出力すると、利用者は自分で考えずに受け入れる。本標準が第7章相当で自動化バイアス対策を規定しているのに、その標準を配るツールが自動化バイアスを誘発するのは自己矛盾。

ただし Buçinca らの「効果的な設計ほど嫌われる」という知見も直視が必要。**摩擦は全ての推薦に一律にかけるのではなく、影響の大きい推薦（安全重要度が高い、取り消しにくい）に絞ってかける**のが妥当な折衷案（本標準の R1〜R3 の考え方と整合する）。

**日本語圏の様式の先例として抽出できる要素（考察）**:

1. **回答時間の明示**（30 分）— 診断への着手障壁を下げる
2. **絶対評価ではなく「望まれる水準」との差分表示** — スコア単体ではなく「あるべき姿とのギャップ」を見せる

### 4.1 ISO 9001 箇条 10.2（不適合及び是正処置）/ CAPA の標準的構成

**二次情報のみ（ISO 9001 本文は有償。日本語のコンサル解説複数に依拠。文言は JIS Q 9001 の訳語ベース）**:

10.2.1 は、不適合が発生した場合に組織が行うべきことを a〜f で列挙する。

- a) その不適合に**対処**し、必要に応じて処置の結果に対応する
- b) **再発防止のため原因を除去する必要性を評価**する（是正処置の必要性の評価）
- c) 必要な処置を**実施**する
- d) とった処置の**有効性をレビュー**する
- e) 必要に応じてマネジメントシステムの**変更**の要否を判断する
- f) とった処置の**文書化した情報を保持**する

10.2.2 は、不適合の性質・とった処置・是正処置の結果について、文書化した情報を保持することを求める。

**用語の区別（重要）**:

- **不適合（nonconformity）** = 要求事項を満たしていないこと
- **修正（correction）** = 検出された不適合を除去するための処置（応急処置）
- **是正処置（corrective action）** = 不適合の**原因を除去し、再発を防止**するための処置

- ISO/IATF SCHOOL 10.2.1 解説（二次）: https://iatf-school.com/iso-10-2-1/
- ISO/IATF SCHOOL 10.2.2 解説（二次）: https://iatf-school.com/iso-10-2-2/
- アイムス 不適合と是正処置（二次）: https://aims.co.jp/corrective-action
- TBC ソリューションズ 附属書 SL 箇条解説 10.2（二次）: https://tbcs.jp/column/2026/02/17/

**未確認**: ISO 9001:2015 本文の逐語（a〜f の正確な訳文）。上記は複数の日本語解説の一致に基づく再構成。**本標準で引用するなら JIS Q 9001:2015 の原文確認が必須。**

**本標準への含意（考察）**: 「修正 / 是正処置」の区別は、本標準の欠陥トリアージ（Sev1〜3）およびインシデント対応の記述に直接対応する。**「直した」と「再発しないようにした」を分けて記録する**という要求は、AI 生成コードの欠陥対応でも同じ構造で使える。

## 5. 本標準への提言

### 5.1 (a) 安全重要度の軸の切り方

#### 提言 1: 記号は `CL0`〜`CL3`（Criticality Level）を提案する

既存語彙（S0-S2 / SG-0..2 / G-1..8 / B-1..4 / D-0 / R1-R3 / L1-L3 / E1-E3 / Sev1-3 / Hz・Hs・Ex・Oc・Av・SR1-4・RRS1-3 / T-0..4 / TG-1..3 / EN-1..3）と照合した結果、**`CL` は未使用**であり衝突しない。

- `SC` は SG（セーフガード？）と視覚的に紛らわしいため不可
- `C` 単独は短すぎて他と混同しやすいため不可
- `R` は R1-R3（決定の取り消し可能性）で使用済み。**安全重要度と取り消し可能性は別軸として維持すべき**なので流用しない

#### 提言 2: 4 段階、単調増加・入れ子、判定は「最悪ケースの帰結」

IEC 62304 の「最悪ケース故障シナリオで判定」「上位が下位を包含」「コンポーネントごとに分類し最上位がシステムを決める」という 3 原則をそのまま採る。段階数は 3〜5 が実例の主流であり、日本の一般 IT を最下段に置くために **4 段階**とする。

| 記号 | 名称（案） | 判定基準（最悪ケースの帰結） | 典型例 |
|---|---|---|---|
| **CL0** | 一般 | 経済的損失・業務中断に留まり、身体的危害も法的義務も生じない | 社内ツール、コンテンツサイト、実験的プロダクト |
| **CL1** | 準規制 | 個人の権利・利益に実質的な影響（金銭、信用、機会の喪失）。回復可能 | 決済、与信、人事評価支援、EU AI Act の限定的リスク相当 |
| **CL2** | 規制 | 規制当局の適合性評価または第三者認証の対象。身体的危害が起こり得るが重篤ではない | SaMD 区分 I–II、EU AI Act 高リスク、IEC 62304 クラス B 相当 |
| **CL3** | 生命重要 | 死亡または重篤な傷害が起こり得る | 車載制御、SaMD 区分 III–IV、IEC 62304 クラス C、DO-178C レベル A/B 相当 |

さらに **EU AI Act の「禁止」に対応する上限**を、レベルではなく**独立した判定**として置く（NASA が「安全クリティカル指定」をクラスと別軸で持つのと同じ構造）。すなわち「CL4」は作らず、**`CL-X`（適用禁止判定）**という別種のフラグとする。段階を伸ばすと「厳しくすれば作ってよい」という誤読を招くため。

#### 提言 3: 第 2 軸として「AI の決定関与度」を掛ける — ただし新しい記号は作らない

IMDRF の 2 軸構造は本標準に応用できるが、**第 2 軸は既に L1〜L3（AI 自律レベル）と E1〜E3（AI 実行形態）として存在する**。新記号を増やすのではなく、**`CL × L` のマトリクスでプロセス要求を決定する**設計を推奨する。

- 例: `CL3 × L3`（生命重要 × AI が自律的に決定）は許容しない（= `CL-X` に落ちる）
- 例: `CL0 × L3` は本標準の Fast Track を全面適用できる
- これにより、既存語彙を再利用しつつ IMDRF 型の 2 軸縮約を実現できる。新記号は `CL` 1 系統のみで済む

#### 提言 4: 段階の差は「列挙可能な差分」で定義する

5 実例すべてに共通する最重要の設計原則。**「CL2 ではより厳格に検証する」のような抽象表現を禁止し、「CL2 では第6章テンプレ9（安全リスクアセスメント）が必須、CL1 以下では任意」のように、成果物名・ゲート名・会議体名の列挙で差分を定義する。**

DO-178C が「レベル A = 71 目標、レベル D = 26 目標」と件数で表現しているように、本標準も**「CL3 では必須成果物 N 件」を数えられる形**にすること。これは `constraints.yaml` の設計要件でもある。

#### 提言 5: NASA の「分類 = 事前テーラリング」の位置づけを明示的に採用する

`CL` はテーラリングの入力パラメータの一つではなく、**最も粗い粒度のテーラリング結果そのもの**であると本文に書く。ルールエンジンは「まず CL でベースラインを決め、次に S0/S1/S2 やチーム規模で微調整する」という 2 段構えになる。

### 5.2 (b) 出力フォーマットの構成

「お仕着せのルール」ではなく「自発的な QMS 構築のナビゲーター」として機能させるための、7 ブロック構成を提案する。各ブロックに、その根拠となる調査知見を紐づける。

**ブロック 1: 診断結果の要約（あなたの状況の言い換え）**

- 入力した組織条件を、標準の語彙（S1、CL2、L2 等）に翻訳して**復唱**する
- ここでスコアや成熟度レベルを出さない。3.1 の知見（確信度スコアの提示は信頼・受容に影響しない）に基づく
- 根拠: §3.1（Cramer et al.）、§3.3（スコアボードではなく鏡）

**ブロック 2: 標準からの差分（テーラリング宣言書）**

- 「適用する」「簡略化する」「適用しない」の 3 分類で、**標準本文の全項目**に対する判定を一覧にする
- ISO 12207 のテーラード適合が要求する「テーラリングした本文を宣言する」に対応。**この一覧そのものが、後で監査・説明に使える成果物になる**
- 根拠: §1.1（テーラード適合の 3 条件）、§1.5（デジタル庁のテーラリング定義）

**ブロック 3: 各判定の理由（note / reason / source）**

- 既存の知識ベースが規則に note・reason・source を必須としているのは正しい設計。**それを出力に露出させる**
- グローバルな説明（判定ロジック全体）とローカルな説明（この項目がこう判定された理由）の**両方**を出す
- 根拠: §3.1（説明は受容を高める / グローバル・ローカルの 2 種類）

**ブロック 4: 削ってはいけない下限（必須項目と、その理由）**

- CMMI OPD SP 1.3 が要求する「defined process が満たさなければならない要求」に対応
- とくに CL2/CL3 では、法令・規制に紐づく項目を「テーラリング対象外」として**明示的にロック**する
- デジタル庁が「法令・府省ルールの順守を前提に」と置いているのと同じ構造
- 根拠: §1.4（CMMI）、§1.5（デジタル庁）

**ブロック 5: 変更可能性の提示（この判定を変えたいときの操作）**

- 「この項目を適用したい/外したいなら、入力のどれをどう変えればよいか」を示す
- 外す場合は **waiver（逸脱）の申請先と承認者**を示す。CMMI が要求する waiver 手順、および NASA のマトリクスにテーラリング根拠欄と承認署名欄があることに対応
- **これが「お仕着せ」を回避する中核。**ツールの出力を「変更できないもの」ではなく「交渉可能な草案」として提示する
- 根拠: §1.4（waiver 手順）、§2.2（NASA の承認署名欄）

**ブロック 6: 自動化バイアス対策（限定的な摩擦）**

- **全項目に摩擦をかけない。**Buçinca らの知見（最も効果的な設計が最も嫌われる）を踏まえ、**CL2 以上、または R3（取り消し不能）に該当する判定に限って** cognitive forcing を適用する
- 具体的手段: 該当項目に「この判定を自組織の文脈で検証した根拠を記入してください」という**記入必須欄**を置き、未記入のまま最終出力（PDF/Markdown）を生成できないようにする
- 併せて、出力の冒頭に「本ツールの出力は決定ではなく草案である。CL2 以上の判定については、あなたの組織の責任者が検証する必要がある」という**限界の明示**を置く
- 根拠: §3.2（Buçinca et al. 2021、CSET 2024）

**ブロック 7: 改善ロードマップ（順序付きの次の一歩）**

- チェックリストではなく**順序付き**にする。ISO/IEC 33020 のレベル 1→2→3 の順序（実施 → 管理 → 標準化）を採用し、「Established を Performed より先に勧めない」というルール制約を置く
- 各ステップに「所要の目安」と「達成したと言える観察可能な結果（outcome）」を書く。24774 の「アウトカム = 観察可能な結果」に対応
- **時系列での再診断を前提とした設計**にする（IPA ベンチマークの「過去 2 回分同時表示」の先例）
- 根拠: §1.2（24774 のアウトカム）、§1.3（33020 の能力レベルの順序）、§3.3（改善ロードマップ）、§3.4（IPA）

**採用しないことを推奨する要素**:

- **総合スコア / マッチ度（%）**: §3.1 で確信度提示の効果がないことが示されている。また §3.3 の「スコアボード化」の落とし穴に直結する
- **他社比較を単独で出す**こと: §3.4 の考察の通り、現状追認に転びやすい。出すなら「望まれる水準」に相当する絶対基準を必ず併記する
- **成熟度レベルによるラベリング（「あなたの組織はレベル 2」）**: 本標準は評価機関ではない。ラベルは組織内の政治的な材料になり、改善から目を逸らさせる

**入力フォーマットについての追加提言**:

- 現状の実施度の入力は 2 値（やっている/やっていない）ではなく、**ISO/IEC 33020 の N-P-L-F 4 段階**を採る（§1.3）。日本語では「未実施 / 一部実施 / 大部分実施 / 完全実施」
- IPA ベンチマークの先例に倣い、**設問数と所要時間を冒頭に明示**する（§3.4）
