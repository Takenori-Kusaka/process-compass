# #321 決定の記録 — ゲート判定記録の成立手続

作成日: 2026-10-23 / 作成: 主宰
入力: 調査 4 本(`gate-record-00`〜`03`)、会議体 第1巡 5 名(`321-council-01`〜`05`)、第2巡 3 名(`-r2`)
対象 Issue: #321

この文書は会議体の結論です。反映(ADR-0070、本文、テンプレート)はまだ行っていません。

## 0. 起票者への答え

起票者の訴えは「帳票の手間で統制するのではなく、強制層でマージを止めるべき。帳票の記入を AI に任せられないのは非効率」でした。会議体の答えは次のとおりです。

- **半分は正しい**。氏名・日時・対象の手入力は、誰が判定したかを裏づけません(`qms-document-control.md:86`)。裏づけるのはホスティングの承認レビューです。これらの欄は機械が出してよく、人は書かなくてよい
- **半分は採らない**。判断の中身(挙動要約・確認した項目・確認していない事項・差し戻し理由)は理解の証拠であり、AI に書かせると証拠でなくなる(`04-gate-record.md:98`、ADR-0023)。ここは人が書く。ただし書く場所は、別ファイルではなく**判定の瞬間に押すレビューの本文**でよい
- **ボトルネックの正体は帳票ではなく「帳票を基底ブランチへ届ける儀式」**。現行テンプレートは、判定 1 件ごとに記録 PR を立て、判定者以外の承認者を課す。これは標準の決定(ADR-0057:509 層1 に PR を課さない、ADR-0058:110 PR 2 本・承認 2 回の却下、`ci-gates.md:609` 記録だけのコミットは製品の変更でない)と揃っていなかった。2 名体制では、本体 PR の指示者が相手の記録 PR を**中身を見ずに承認するしかない**構造を制度が作っていた(02 §2、E0)。起票者の懸念「中身を見ないままマージ」は、現行の手続が自ら生んでいた
- **ADR-0036 決定1「記録の作成をもって成立」は変えない**。変えるのは「記録 = `docs/gates/` のファイル」というテンプレートの置き方と、記録を届ける手続

起票者の主張のうち、事実として成り立たないもの 2 点も記録します。「リベースで対象 SHA が変わり記録を作り直す」(対象は PR 番号で書ける `04-gate-record.md:20`)、「`check-pr.mjs` は基底の `docs/gates/` しか読まない」(停止の解除・例外承認の台帳に限る。G-6 の承認者数は `docs/gates/` を読まない `check-pr.mjs:438`)。

## 1. 決定

### D1 判定記録の媒体を限定しない(ADR-0036 決定1 を補う)

工程ゲートの判定は、判定記録の作成をもって成立します(ADR-0036 決定1。変えない)。判定記録とは、第4章「判定の成立」が定める欄が埋まった記録であり、第6章 テンプレ4 はその様式の正本です。**欄を運ぶ媒体を、本標準は様式のファイルに限定しません**。ホスティングのレビューが欄を運び、案件の構成が事前に対応づけ(`qms-document-control.md:33` の型)、第5章の保全の条件(D8)を満たすとき、そのレビューは判定記録です。欄を運ばない操作(Issue のクローズ、PR のマージ、ラベルの遷移、承認の操作そのもの)は引き続き事務です(ADR-0036 却下表、`gate-criteria.md:465`)。

### D2 機械が出す欄と人が書く欄を分ける

| 機械が出す欄(推定を含まない写し。出所を併記) | 人が書く欄(判定者本人が自分の言葉で。AI に生成させない) |
| --- | --- |
| 判定者(アカウントの数値の識別子と名簿の席)、判定日時、提出日時、対象(PR 番号・コミットの識別子・レビューの識別子)、結果(宣言行から)、参照した D-0 の版、承認の数、作成を指示した者との別 | 挙動要約、確認した項目、確認していない事項、差し戻し理由(項目番号と再提出の期限)、決断の記録、比較した選択肢の採否の理由、リスク区分の確定者の記名 |

第6章の欄は 1 つも減りません。ADR-0040 の omit でも逆の指示でもなく、**欄の出所の指定**です(先例: 7.3 の記録者/承認者、D-0 の要求事項、IMPL-0062)。「転記」の語は附属書C「AI 転記」と衝突するため使わず、「機械が出す欄」「写し」と書きます。

### D3 人が書く欄の受け皿は 2 つに限る

- **対象が PR として存在する判定**(G-6、および G-2・G-3・G-4 で仕様・ADR が PR として存在する場合): 判定者本人のレビューの本文
- **それ以外**(G-1・G-7・G-8・SG、例外承認、停止の解除、対象が PR でない場合、ホスティングが D8 を満たさない場合): 判定記録(様式)
- PR 本文(作成側の欄 `gate-criteria.md:472`)と Issue コメント(コミットに固定されず削除できる)は受け皿にしない

### D4 G-2・G-3・G-4 のレビューの条件

弁護役 第2巡 B-5 を採ります。規格整合 第2巡の「判定者が作成者でない構成に限る」は採りません。理由: G-2・G-4 は**確定**であって独立した確認ではない(ADR-0060:58、`gate-criteria.md:170`)。ブランチ保護が作成者本人の APPROVED を止めるのは「1 名の確認で取り込めない状態を作る」(ADR-0067:36)という別の目的の規則であり、確定の記録を巻き込む理由にならない。

- 判定者本人のレビューであること。**状態(APPROVED / CHANGES_REQUESTED / COMMENTED)を問わない**
- 本文の 1 行目に宣言行(`G-4: 通過` / `G-4: 差し戻し / 基準 N / 期限 YYYY-MM-DD`)。続けて確認した項目を見出し語で。宣言行の無い承認は、取り込みの事務であり G-2・G-4 に数えない
- 対象の版 = レビューの `commit_id`。集約が `commit_id == マージ時の head` を検査し、ずれた変更は「確定していない版を取り込んだ」として欠落に数える(現行 IMPL-0107 `check=manual` より強い)。人は「機能の ID + PR 番号」を書き、マージ後のコミットの識別子は集約が併記する
- **この承認を G-6 の独立した人の確認に数えない**。QMS 対応表の G-2・G-4 の行にその旨を足す
- 様式は後退経路。「同じ結果を導く手続を 2 つ持つと緩いほうが使われる」(`gate-criteria.md:1208`)には当たらない。レビューが既定であり、様式は対象が PR でないときにだけ現れる

### D5 写しは承認と同じ時期に機械が取り出し、記名者と判定される側が書き換えられない場所へ置く

写しに含める最小の組: レビューの識別子・状態・`commit_id`・`submitted_at`・アカウントの数値の識別子とログイン名・本文・PR 番号・マージのコミット、および同じ期間の bypass・保護の変更の記録(取れないプランでは「取れない」と写しに書く)。写しは要約と評価を含まず、附属書G の投影と区別します。監査ログは 180 日で消える(`gate-record-02` §3)ため、G-7 の時点で初めて作ることは認めません(`qms-document-control.md:117`)。

### D6 基底ブランチへ入れるのは遅くとも出荷判定(G-7)。入れる操作に記名者以外の承認を課さない

- 判定記録と写しを基底ブランチへ入れるのは、遅くとも G-7
- 記録だけのコミットを基底へ入れる操作に、**記名者以外の承認を課さない**(ADR-0057:509、`ci-gates.md:609`、ADR-0067:36 の一般化)。帰属の裏づけは記名者本人の操作(署名コミット、または記名者の承認レビュー)。裏づけの無い記録は、記名が自己申告であることを保証の開示へ出す(`qms-document-control.md:86` の型)。残る記録 PR に他者の承認が付く場合、それは取り込みの事務と明記する
- G-7 の PR に写しを同梱する場合、CI が同じ集約を再実行して一致を検査する(出荷判定者は判定される側でない。ADR-0066:53。`ci-gates.md:146` に触れない)
- 停止の解除・例外承認の台帳は現行どおり**基底ブランチへ先に入れる**(`ci-gates.md:146`・`:155`)

### D7 既定ブランチの強制層を、写しのために縮小しない

bypass actor を足さない。`exempt` を用いない。監査側の「マージごとに Bot が bypass で既定ブランチへ固定」は採りません。理由は「GitHub でできない」ではなく、強制層の縮小(ADR-0038:46)であり、`rulesets/README.md:41`・`agent-trace-control.md:52` の下では「App の名義の変更は人の承認を経ない」と開示してしか成立しないからです。組織が bypass を伴う構成を選ぶことは禁じませんが、`state:needs-platform` の経路で統制の弱化として記録し、標準の既定にはしません。

D5〜D7 を両立させる置き場の形(既定ブランチの外の記録用ブランチ、CI の成果物)は**準拠テンプレートが決めます**(`adr/0035-…:101` の型)。起案側 第2巡 §3.2 の記録用ブランチ(`non_fast_forward`・`deletion`、規制業・CL2 以上は `required_signatures`。`pull_request` も bypass も置かない)を第一候補とし、実機で確かめてから降ろします(E0)。

### D8 レビューを記録と認める条件を標準に書く

- 成立の条件(第4章): 欄の充足、書き手が判定者本人、`commit_id` による対象の固定、承認の後の push による失効(G-6)または `commit_id == head` の検査(G-2〜G-4)、承認者ごとの最後の状態、変更要求の本文に満たさない基準の項目番号と期限
- 保全の条件(第5章 QMS 文書管理): アカウントと実在の人の対応表と数値の識別子、レビューの意味(宣言行)の事前の定義、写しの取り出しの時期と保持、組織の文書管理規程の対象に写しを含めること、PR の承認が電子署名の要件(Part 11 11.50・11.200)を自動的に満たさないこと
- 条件を満たさないホスティングでは様式へ戻る。これにより、ツールを変えても成立要件は変わらない(ADR-0036:101 の却下理由を保つ)

### D9 規制業(軸C)・CL2 以上(軸E)は、変更ごとの G-6 の判定記録と監査対応書式を維持する

文言を「承認レビューは機械が出す欄の出所になる。判断の中身の監査対応書式と変更ごとの記録が無ければ記録にならない」へ改めます(`deliverable-templates.md:503`、`tailoring-guide.md:508`)。現場の「G-7 で機械生成」は、査察で受理された一次事例が無いため採らず、差し替え条件(EV)へ送ります。

### D10 形骸化の抑止は既存の手段で足りる。観測値は合否にしない

挙動要約の形(8 文字・承認の語だけでない)、同一の文、変更の規模(ADR-0058)、検出能力の測定、内部監査の抜き取り。承認までの時間・コメントの有無・差分量は観測値として出し、内部監査のリスクに基づく抽出の条件に加える(`process-audit.md:63`〜`:68`)。閾値を置けば最短経路が「閾値の直上で承認」になるため合否にしない。「機械が見るのは形だけ」の限界(EV-0083)は、レビュー本文に置いた欄にも掛かる。

### D11 QMS 対応表の語を改める

列名「成立の条件」→「承認の記録として扱う条件」。G-7 の行「判定記録のマージ」→「判定記録を基底ブランチへ入れること。入れる操作に記名者以外の承認を課さない」。G-2・G-4 の行に「判定者本人のレビュー(宣言行つき)。この承認は独立した人の確認(G-6)ではない」。G-8 の行に「決断の記録はテンプレ4 に残す。承認操作だけでは記録にならない」。第4章と対応表に実質の対立は無く、語の誤りです。

### D12 1 名体制で変わる範囲を明記する

1 名体制(`checks-only.json`)では、G-2・G-4 は仕様 PR への本人のレビューで記録でき(操作 4 → 2、E0)、機械が出す欄の手入力が消えます。本体 PR の基底の更新による再承認の往復は本決定では軽くなりません(#296)。ルールセットを使えないプランでは記録の日時が自己申告であることを保証の開示へ出します(`template/README.md:115`)。
