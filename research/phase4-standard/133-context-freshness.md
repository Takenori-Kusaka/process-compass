## 1. Q1 落とすか、警告にするか

### 1.1 一次情報

*Software Engineering at Google*、第20章「Static Analysis」(著者 Caitlin Sadowski、編集 Lisa Carey)。Google における静的解析の運用から得られた指針である。

原文の記述。

> Produce less than 10% effective false positives

これは新しい検査を既定で有効にする際の4条件のひとつである。プラットフォーム全体の実効偽陽性率は "just below 5%" と述べられている。

ビルドを落とす条件について。

> We either enable a compiler check as an error (and break the build) or don't show it in compiler output.

コンパイラへ組み込んでビルドを落としてよいのは、**highly mechanical で実効的な偽陽性がない**解析に限るとされる。それ以外はコードレビューの時点で提示する。

実効偽陽性の定義も示されている。

> An issue is an "effective false positive" if developers did not take some positive action after seeing the issue.

- 出典: [Software Engineering at Google — Chapter 20: Static Analysis](https://abseil.io/resources/swe-book/html/ch20.html)（2026-08-07 取得）。書籍版は Winters, Manshreck, Wright 編、O'Reilly、2020年
- 関連: [Lessons from building static analysis tools at Google (CACM 2018)](https://dl.acm.org/doi/10.1145/3188720)（本文は 403 のため未取得）

### 1.2 所見

**2つの選択肢しか置いていないことが要点である**。「落とす」か「そもそも出さない」かであり、**無視できる警告として出し続ける構成を採っていない**。

判定の基準は「機械的で、実効的な偽陽性がないか」である。ここでいう偽陽性は技術的な誤検出ではなく、**開発者が見て何も行動しなかったもの**を指す。技術的に正しくても行動につながらない指摘は、偽陽性として数える。

### 1.3 本標準への当てはめ

検知の対象を性質で分けると、扱いが機械的に決まる。

| 検査 | 機械的か | 実効偽陽性 | 扱い |
| --- | --- | --- | --- |
| 文脈内のリポジトリ内パス・リンクの参照切れ | 機械的 | ない | **落とす** |
| 1ファイルの分量の上限超過 | 機械的 | ない | **落とす** |
| コードの変更と文脈の更新の乖離 | 対応関係の推定を含む | ある | **落とさない。警告としても出さない** |
| 記述と実態の意味的な食い違い | 機械的でない | 判定できない | 機械が判定しない |

乖離は「落とす」にも「そもそも出さない」にも当てはまらない。**第三の置き場が要る**。

## 2. Q2 対応関係の特定

Issue が指摘するとおり、**ファイルの対応表を人が別置きで保守すると、その表自体が陳腐化する**。

本標準は既に CODEOWNERS で文脈ファイルの責任者を機械的に紐づけている(フェーズ5 `context-base.md`)。ただし CODEOWNERS が表すのは「ファイル → 人」であり、「文脈 → コードの範囲」ではない。

**対応を文脈ファイル自身へ同居させる構成であれば、別置きの表にならない**。文脈ファイルを削除すれば対応も同時に消え、文脈ファイルを移動すれば対応も一緒に動く。陳腐化の対象になるのは記述の内容であって、対応の所在ではない。

乖離の定義も、意味的な判定を避けて機械的に置ける。

> **その文脈ファイルが担当する範囲のコードが、当該文脈ファイルの最終更新以降に一定回数以上変更された状態**

これは変更履歴だけで判定でき、内容を読まない。

## 3. Q3 検知と削減のどちらを主とするか

第3章 3.11.4 は既に次の根拠を持っている。

- 指示の分量が増えるほど遵守率は下がる(提供者側の記載)
- 入力長の増加に伴い精度が非一様に低下する(2025年の研究報告)
- 指示ファイルの付与で成功率は改善せず、推論費用が平均2割超増えた(2026年の評価)

**「多く書く」方向の解決は、精度と費用の両面で不利である**。したがって次の順序になる。

1. **記載内容の削減を主とする**。3.11.4 要求事項5(コードベースから導出できる内容を記載しない)を守れば、乖離しうる記述そのものが減る
2. **検知は削減の入力として位置づける**。乖離の検知は、削除・保管の候補を挙げるために行う

**忘却のプロセスは、鮮度の維持だけでなく分量の抑制としても機能する**。両者は同じ操作である。

## 4. Q4 外す判断を AI に行わせてよいか

**行わせない**。第3章 3.11.4 要求事項3 は既に「削除と統合の権限を1名(AI維持管理者)へ集約する」と定めている。本 Issue で新たに緩める理由はない。

AI が行ってよいのは**候補の提示**までである。これは第5章 5.7.4(記述の質を機械判定して承認可否を自動決定しない)、および第4章 G-4(範囲内外の判定を機械が行わない)と同じ切り分けである。

誤って外した場合に取り返せる必要があるため、**削除ではなく保管とし、復帰の条件を定める**。

## 5. 何を外すかの基準

意味的な判定を要しない基準を優先する。

| 基準 | 判定 | 意味判定 |
| --- | --- | --- |
| **読み込まれていない** | 3.11.4 要求事項6 の読み込み実績が一定期間 0 回 | 不要 |
| 乖離が閾値を超え、棚卸しで更新されなかった | 変更履歴 | 不要 |
| コードベースから導出できる | 要求事項5 の違反 | 一部必要 |
| 重複または矛盾 | 他の記述との突合 | 必要 |

**「読み込まれていない」を主たる基準に置く**。実績に基づき、意味の判定を要さず、**そもそも効果を持っていない記述**を特定できる。3.11.4 要求事項6 が既に読み込み実績の記録を求めており、新しい計測を追加しない。

## 6. 結論(設計への反映)

| # | 結論 | 反映先 |
| --- | --- | --- |
| 1 | **乖離の検知でビルドを落とさない。警告としても出さない**。台帳へ記録し、既存の四半期の棚卸しの入力とする | 第4章 G-5、第3章 3.11.4 |
| 2 | **参照切れ(リポジトリ内)と分量の上限超過は落とす**。機械的で実効偽陽性がない | 第4章 G-5、フェーズ5 |
| 3 | **対応関係を文脈ファイル自身の frontmatter に書く**。別置きの対応表を作らない | フェーズ5 |
| 4 | 乖離を**変更履歴だけで定義する**。内容を読まない | フェーズ5 |
| 5 | **記載内容の削減を主とし、検知はその入力とする** | 第3章 3.11.4 |
| 6 | **外す判断を AI に行わせない**。候補の提示までとする | 第3章 3.11.4 |
| 7 | **削除ではなく保管とする**。保管領域はエージェントの参照対象から外す。復帰の条件を定める | 第3章 3.11.4、フェーズ5 |
| 8 | 外す基準の主は**「読み込まれていない」**。既存の読み込み実績を用い、新しい計測を追加しない | フェーズ5 |
| 9 | **新しい判定の場を作らない**。既存の四半期の棚卸しへ入力を足す | 第3章 3.11.4 |
