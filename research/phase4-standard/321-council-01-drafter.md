## 1. 先に結論

- **成立要件は変えない**。ADR-0036 決定1「判定記録の作成をもって成立」は維持します。変えるのは「判定記録」の供給の仕方です。判定記録を**属性**(誰が・いつ・何に・結果)と**判断の中身**(挙動要約・確認していない事項・差し戻し理由・採否の理由)の 2 層に分け、属性は強制層の記録から機械が転記し、判断の中身だけを人が書きます
- **人が書く欄の受け皿は、変更ごとのゲートでは承認レビューの本文**です。これは新設ではなく、G-6 で本文に既に書かれている形(`gate-criteria.md:480` の「2件目の承認(自分の挙動要約つき)」)を、属性の転記と組み合わせて全ゲートへ広げるものです
- **判定ごとの記録 PR は廃します**。記録のファイルは出荷(G-7)の時点に、集約が範囲内の全判定を 1 本の PR へ固定し、出荷判定者がそれを承認します。記録の PR は出荷ごとに 1 本、承認者は G-7 の判定者本人です。これは ADR-0058 が「PR 2 本・承認 2 回」を退けた先例(`adr/0058-…:110`)と同じ向きです
- **承認イベントを記録と認める条件を標準に書きます**。保持(出荷の集約が承認イベントの写しを git へ固定する)、実名対応表(既存 `qms-document-control.md:44`)、承認の意味の事前定義(既存 `qms-document-control.md:33`)、対象の固定(`commit_id` とマージ時の head の一致、stale 失効)、bypass の監査(exempt の禁止)の 5 条件です。満たさないホスティングでは、判定記録ファイルの経路へ戻ります
- **Bot の bypass は採りません**。記録の固定は「集約が PR を開き、出荷判定者が承認する」形にし、Bot を bypass actor に置きません。bypass はパス単位に絞れず(02 §5.3)、App の鍵が記録の信頼性の上限になるためです
- **規制業(軸C)の監査対応書式は維持**します。Part 11 の電子署名と設計レビュー(ISO 13485 7.3.5)の構造は、PR の承認が持たないものです(01 §1.4、03 §8.2)
- **承認の失効の粒度(基底の更新による再承認の往復)は本 Issue で決めません**。#296 の T-09 へ送ります。ただし「承認は承認した内容に束縛される」(`295/council-04-skeptic.md:88`)は不変条件として保ちます
- 起票者の「帳票の記入を AI に任せる」は、**属性の転記に限って採り、判断の中身については却下**します。AI が書けるのは機械が決められる値だけです(`template/templates/04-gate-record.md:98`、ADR-0023)

## 2. Q1〜Q7 への回答

### Q1 成立要件 — 維持する。「判定記録」の供給の仕方を変える

ADR-0036 決定1 を維持します。理由は 3 つです。

- 決定1 の論理は「記録がなければ判定の存在そのものが自己申告になる」(`adr/0036-gate-closure-by-record.md:61`)である。承認イベントも記録であり、この論理と衝突しない。衝突するのは「承認の操作があったこと」を成立要件に置く案であり、それは既に「承認の操作があったことだけでは数えません」(`gate-criteria.md:465`)で退けられている
- 成立要件の実体は「判定者・判定日時・結果・確認した項目・差し戻し理由が埋まっていること」(`gate-criteria.md:65`)であり、媒体は書かれていない(00 §8.3)。成立要件を変えずに、欄の供給源を変えられる
- 規格は「文書」という形式を求めていない(01 §7.2。ISO/IEC/IEEE 15289 5.1、IEC 62304 B.8.2「a record in a database」、FDA CSA 2026)。「欄が埋まった記録」という成立要件は、規格が求める Who / When / What / Outcome / Reason(01 §7.1)と同じ粒度である

置き換えるとしたら候補は「承認イベントの提出をもって成立」ですが、これは採りません。承認イベントは Reason(判断の中身)を自動では持たず(01 §0)、G-1〜G-4・G-8・SG には対応する承認イベントがありません(00 §8.3)。成立要件を承認イベントに置くと、PR に紐づかないゲートが成立しなくなります。

決定1 には根拠水準マークが無い(00 §5)ので、本案を採る場合は決定1 に差し替え条件を置きます(6 章)。

### Q2 属性と判断の分離 — 認める。受け皿は承認レビューの本文と判定記録ファイルの 2 つ

認めます。分離の線は次のとおりです。

| 層 | 欄(テンプレ4、`deliverable-templates.md:460-511`) | 供給源 | 書く者 |
| --- | --- | --- | --- |
| 属性 | 対象(PR 番号・コミットの識別子)、判定者、判定日時、結果、参照した D-0 の版、提出日時、非同期コメント期間 | 承認イベント(`id`・`state`・`commit_id`・`submitted_at`・`user.id`・`user.login`)、PR のメタデータ、基底の構成書 | 機械が転記 |
| 判断の中身 | 挙動要約、確認した項目、確認していない事項、差し戻し理由(項目番号・再提出の期限)、決断の記録(選択肢・異議・上申)、リスク区分を確定した者の記名 | 人が書く本文 | 判定者本人 |

この分け方は、第7章 7.3 が「記録した者」と「承認した者」を別の欄にした構造(`exception-escalation.md:57`)と同じであり、Vanta の「承認イベントは機械が集め、例外の理由は人が書く」(03 §3.3)、kernel の「属性は git、Reviewed-by の中身は人の宣言」(03 §4.1)と同じ分担です。

人が書く欄の受け皿は 2 つ認め、他は認めません。

- **承認レビューの本文**(変更ごとのゲート、および対象の成果物が PR として存在するゲート): 挙動要約の受け皿として本文が既に認めている(`gate-criteria.md:480`、ADR-0057 S52 `adr/0057-…:476`)。判断の中身の各欄を、見出し語つきで本文に書く。見出し語は 5.7.4 の「構造を規定する」(`human-ai-boundary.md:625`)の形を保ち、機械は見出し語の有無と「確認していない事項」の「なし」不可(`deliverable-templates.md:564`)だけを見る
- **判定記録ファイル**(対象が PR として存在しないゲート、承認イベントを記録と認める条件を満たさないホスティング、規制業の監査対応書式): 現行のテンプレ4 のまま
- **PR 本文は受け皿にしない**。PR 本文は作成側が書くものであり、「作成側が書く検証の記載は、挙動要約に数えない」(`gate-criteria.md:472`)。リスク区分の確定者の記名だけは PR 本文でも数える現行(`ci-gates.md:415`)を維持する
- **Issue コメントは受け皿にしない**。Issue は対象のコミットに紐づかず、承認イベントの `commit_id` に相当する固定が無い(01 §7.4「対象とのリンク」)

ADR-0040 との関係は「欄を落とす(omit)」でも「標準と逆の指示」でもなく、**欄の供給源の指定**です。様式の正本(第6章)の欄は 1 つも減りません。テンプレート側の様式は、属性の欄を「機械が転記する」と注記するだけで、ADR-0040 決定1 の部分集合の関係を保ちます。

### Q3 置き場と固定 — ゲートごとには求めない。出荷(G-7)で 1 本の PR に固定し、出荷判定者が承認する

ゲートごとに `docs/gates/` のファイルを基底へ入れることは求めません。出荷判定(G-7)の時点に、集約が次を 1 本の PR として基底へ固定します。

- 範囲内の全判定の属性(承認イベントの写し。02 §9.1 の最小の組: レビュー `id`・`state`・`commit_id`・`submitted_at`・`user.id`・`user.login`・PR 番号・`merge_commit_sha`)
- 判断の中身(承認レビューの本文の写し。編集履歴がある場合は、承認の時点の文を採る)
- 判定記録ファイルで残した判定(そのまま)
- G-7 の判定記録(出荷判定者が記名する。これはファイルであり、人が書く)
- bypass・`policy_override`・ルールセットの変更の有無(02 §9.2)

この PR の承認者は**出荷判定者本人**です。集約(Bot)は PR を開くだけで、承認もマージもしません。これにより、出荷判定者の承認レビュー(`Verified` なマージ)が「写しが承認の時点の原記録と一致していること」の記名になります。出荷判定者がこの一致を一件ずつ確かめるのではなく(`gate-criteria.md:608` と同じ扱い)、集約が原記録を API から引いて写しを作ったこと、写しの件数が範囲と一致することを確かめます。

理由は次のとおりです。

- 判定ごとに記録 PR を足す形は、ADR-0058 が「1 名体制で閉じ、回避の動機を生む」として退けた「PR 2 本・承認 2 回」と同じ構造である(`adr/0058-…:110`)。記録 PR に「判定者以外の承認者」が要る現行(`team.json:12-16`、00 §4.8 注)は、記名と承認の二重化であり、層1 について既に退けた理由(`adr/0057-…:509`)がそのまま当たる
- 出荷の時点の固定は、保持の要件(Part 11 11.10(e)「対象記録と同じ期間」、01 §7.4)を、監査ログの 180 日(02 §3)と無関係に満たす。写しは git の履歴に入り、承認者の退会で `ghost` 化しても `user.id` が残る(02 §1.6)
- 記録は製品と同じ履歴に残る。専用ブランチ・別リポジトリ(02 案 D)が失う性質を失わない
- 出荷の範囲の記録の数え方は、現行の「範囲内に追加されたファイル」(`aggregate-evidence.mjs:371-375`)から「範囲内のマージの承認イベント + 範囲内に追加されたファイル」へ変える。承認イベントは PR 番号と `merge_commit_sha` で範囲に対応づく

**Bot による固定(bypass)は認めません**。02 §9.3 の案 A(`pull_request` モード)は筋が良いとされていますが、bypass はパス単位に絞れず(02 §5.3)、App の鍵の保護が記録の信頼性の上限になります。記録の信頼性を「人の承認がある」から「鍵が漏れていない」へ置き換えることになり、これは統制の弱化(ADR-0038 `adr/0038-…:46`「強制層の縮小」)に当たります。`exempt` は監査に出ない(02 §4.1)ため、記録の目的と矛盾します。

**停止の解除と例外承認の台帳は現行どおり基底ブランチから読みます**(`ci-gates.md:146`・`155`)。起票者はこれもボトルネックに挙げていますが、「判定の材料を判定される側が同じ変更で用意できない」は判定の信頼性の核心であり、頻度も低い(例外承認は 7.3 の手続、停止の申し立ては 7.11)。解除・例外承認の記録の PR は残ります。ただし承認者は解除・例外承認の権限者本人であり(`exception-escalation.md:596`・`619`)、判定者以外の承認者は要りません。この 1 点は強制層の設定の問題であり、3 章の「記録の置き場だけの PR」の扱いで吸収します。

### Q4 PR に紐づかないゲート — 対象の成果物の PR があればその承認レビュー、無ければ判定記録ファイル

ゲートごとに受け皿を決めます。

| ゲート | 判定者(`gate-criteria.md:114-798` の見出し) | 対象が PR として存在するか | 受け皿 |
| --- | --- | --- | --- |
| G-1 企画承認 | 事業決裁者 | 企画書(テンプレ6)の PR があれば存在 | 企画書の PR の承認レビュー本文。無ければ判定記録ファイル |
| G-2 要件合意 | 価値責任者 | 受入基準の版のコミット(`deliverable-templates.md:460`)を含む仕様の PR | 仕様の PR の承認レビュー本文。QMS 対応表(`qms-document-control.md:37`)と一致 |
| G-3 技術設計判断 | 技術判断者 | ADR・設計の PR | ADR の PR の承認レビュー本文。AWS の ADR プロセス(03 §7.1)が会議を置く理由は「文章の是認」と「責任者の採用」の畳み込みであり、本標準は判定者が 1 人で記名するため畳み込みは起きない |
| G-4 機能仕様承認 | 価値責任者または委譲先 | 機能仕様の PR | 仕様の PR の承認レビュー本文(`qms-document-control.md:38`) |
| G-6 独立レビュー | 独立レビュア | 変更の PR | 承認レビュー本文(現行) |
| G-7 出荷判定 | QA(出荷判定者) | 出荷の記録 PR(Q3) | 判定記録ファイル(G-7 の記録は人が書く。`qms-document-control.md:40`「判定記録のマージ」と一致) |
| G-8 リリース決裁 | 事業決裁者 | 実行環境の承認操作(`qms-document-control.md:41`) | 属性は実行環境の承認操作から転記。決断の記録(`deliverable-templates.md:507`)は判定記録ファイル。頻度はリリースごとであり、帳票の負担は小さい |
| SG ステージ移行 | 第8章の判定者 | 構成・D-0 の PR | D-0 の PR の承認レビュー本文。「AI の利用の評価」の節(`deliverable-templates.md:574`)は本文の見出し語として書く |

**判定者が成果物の作成者でもある場合**(G-2・G-3・G-4・G-7。ADR-0060 は禁じない `adr/0060-…:58`)の折り合いは次のとおりです。

- 成果物を**判定者以外が push し、判定者が承認する**形を正とする。AI の担い手が仕様を起こし、価値責任者が承認する形は、`recording.md:24`「判定者の発言を転記して記録を起こす場合も、結果欄の確定は判定者本人が行う」と同じ構造である。ブランチ保護は最後に push した本人の承認を止める(`require_last_push_approval`)だけなので、この形は止まらない
- ただし ADR-0035 の条件3(認証情報の分離 `adr/0035-…:84`)を満たさない体制(AI と判定者が同じアカウント)では、push した者と承認する者が同じアカウントになり、ブランチ保護が止める。この体制では判定記録ファイルへ戻る。**1 名体制では本案は何も軽くしない**。これは 4 章の弱点 5 に書く
- 作成を指示した者と判定者が同一である G-2〜G-4・G-7 の承認は、「別の人による確認ではない」(`adr/0060-…:58`)ことを集約が開示する。本案はこの開示を変えない。G-6 の 4 条件の「作成を指示した者でない」は G-6 だけの条件であり、他のゲートへ広げない

### Q5 保全 — 書く。第5章 CI/CD ゲート構成と QMS 文書管理へ。第4章には媒体非依存の一文だけ

書きます。置き場は次のとおりです。

- **第4章「判定の成立」**(`gate-criteria.md:55-74`): 「判定記録の欄は、ホスティングの承認の記録から機械が転記した値で埋めてよい。転記した値を記録と数える条件は第5章による」の 1 段落。第4章は意味論だけを持つ
- **第5章 `qms-document-control.md` 「承認権限のマッピング」**(`:31-45`): 既存の表(`:35-41`)に G-1・G-3・SG の行を足し、「成立の条件」の列に Q4 の受け皿を書く。「アカウントと実在する人物の対応表」(`:44`)と「対象と意味を残す」(`:45`)は既にある。足すのは次の 3 条件
  - **保持**: 出荷の集約が、承認の記録の写し(`id`・`state`・`commit_id`・`submitted_at`・`user.id`・`user.login`・PR 番号・`merge_commit_sha`・本文)を記録の置き場へ固定する。ホスティングの監査ログの保持期間に依存しない
  - **対象の固定**: 承認が指すコミットが、マージの時点の head と一致する。一致しない承認は数えない。承認の後の push で承認を失効させる設定を強制層に置く(現行 `team.json:12-16`)
  - **bypass の監査**: 承認を省いて取り込んだ変更(`policy_override`・bypass)を集約が読み、独立した人の確認を経ていない変更に数える。監査に出ない bypass(`exempt`)を記録の置き場に対して設定しない
- **第5章 `ci-gates.md`**: 転記の実装(API から引く欄、写しの形式、範囲の数え方)
- **附属書I**(`adoption-guide.md:575`「実環境の識別」): 査察で GitHub の画面と突合する鍵に、写しのファイルのパスと承認の `id` を足す

**GitHub 以外への一般化**: 条件は属性名(承認者の一意の識別子、対象のコミット、提出時刻、状態、本文)で書き、GitHub の API 名は `ci-gates.md` の実装側にだけ置きます。GitLab(MR 承認、再認証あり 03 §1.3)、Gerrit(Code-Review ラベルがコミットの footer に焼き込まれる 02 §6.5)は条件を満たします。条件を満たさないホスティング、またはルールセットを使えないプラン(`template/README.md:115`)では、判定記録ファイルの経路へ戻ります。この後退経路があるため、ツールを変えても成立要件は変わりません(Q7)。

**Part 11 の電子署名が要る記録**(基礎規則が署名を求める記録)は、本条件を満たしても承認イベントだけでは足りません(01 §1.4)。これは現行の「規制業では PR の承認だけでは記録にならない」(`deliverable-templates.md:503`)で既に書かれており、変えません。

### Q6 形骸化の抑止 — 承認の回数を減らすことが本案の抑止装置。計測値は記録に添え、合否にしない

「中身を見ずに承認」を機械で判定しないことは、本標準が既に決めています(`human-ai-boundary.md:657` 5.7.4、ADR-0059 `adr/0059-…:30`)。研究上も未解決です(03 §5.3、Doğan らが LGTM スメルだけ検出法を提案できなかった)。本案の抑止は次の組み合わせです。

- **承認の回数を増やさない**。これが本案の中核である。判定ごとの記録 PR の承認(判定者以外)を廃すことで、1 件の承認の重みを保つ。承認が増えるほど 1 件への注意が減る(FND-0010、`adr/0054-…:45`。Anthropic の 93% は 03 §6.2)
- **宣言の形の検査**(既存): 挙動要約の最低限の形(`gate-criteria.md:492`、EV-0083)、同一の文の 2 件目不算入(`gate-criteria.md:483`)、「確認していない事項」の「なし」不可(`deliverable-templates.md:564`)。本案はこれを承認レビュー本文の全欄へ広げる。限界(8 文字の形骸化)は既に開示されている
- **変更の小ささ**(既存、ADR-0058): 規模の超過を区分 R2 と規模の確認で扱う。形骸化の抑止で実証があるのは変更の小ささと読む速度である(03 §8.4)
- **計測値を記録に添える**(新規、合否にしない): 承認までの時間、レビューコメント数、差分量、`commit_id` と最終 head の一致(02 §7)。集約が出荷の証跡へ出し、内部監査の抜き取り(`gate-criteria.md:483` の「内部監査の抜き取り」)の選び方の材料にする。閾値で合否を決めない(自明な変更の誤検出。02 §7)
- **検出能力の実測と承認権限の一時制限**(既存、ADR-0059 `adr/0059-…:52`)。形骸化の検知はここが担う

機械で判定しない限界は、附属書H H.7「承認の件数と署名では示さない」(`adr/0056-assurance-argument.md:142`)に既に開示されています。本案で足す開示は「承認レビュー本文の構造の検査は、見出し語の有無と文字数だけを見る」の 1 文です。

### Q7 ツール依存の吸収 — 「意味論は標準、媒体はホスティング」で足りる。ただし後退経路が要る

ADR-0036 が「Issue のクローズで成立」を却下した理由は「ツールを変えると判定の成立要件が変わる」(`adr/0036-…:101`)です。本案はこの却下に抵触しません。

- 成立要件は「欄が埋まった判定記録」のままであり、ツールを変えても変わらない
- 変わるのは**欄の供給源**である。供給源がホスティングの承認の記録であるか、人が書いたファイルであるかは、成立要件ではなく成立の手段である
- 却下案「Issue のクローズで成立」との違いは、クローズが Who / When / What / Outcome のうち What(対象のコミット)と Outcome(判定の 2 値)を持たないことである。承認イベントは `commit_id` と `state` を持つ。QMS 文書管理が「事前に対応を定めた操作だけを承認として扱う」(`qms-document-control.md:33`)としているのは、この違いを操作ごとに定めるためである

「記録の意味論は標準が持ち、媒体はホスティングが持つ」の整理で足ります。ただし 1 つ足します。**条件を満たさない媒体では判定記録ファイルへ戻る後退経路**を標準に書くことです。後退経路が無いと、ホスティングを変えた途端に記録が成立しなくなり、却下理由と同じ事態になります。

第4章・ADR-0036 と QMS 対応表の食い違い(00 §2.8 注)は、この整理で解けます。QMS 対応表の「PR 承認とマージ」は**操作を記録の供給源として事前に定めた表**であり、第4章の「PR のマージは事務」は**操作そのものを成立要件にしない**と言っています。両者は同じことを別の向きから書いています。ただし対応表の G-7「判定記録のマージ」は、マージを成立要件に読める書き方なので、「判定記録の作成(マージは事務)」へ直します。

## 4. 自分の案の弱点

1. **承認レビュー本文の構造は、手入力と同じ弱さを持つ**。判断の中身(確認していない事項、差し戻しの項目番号と期限)は本文に人が書くため、「なし」不可の検査と見出し語の検査を本文でも行うことになり、8 文字の形骸化(ADR-0059)と同じ限界が本文の全欄に広がる。属性の信頼性は上がるが、判断の中身の信頼性は 1 ミリも上がらない。本案が主張できるのは「属性の自己申告が消える」ことと「承認の回数が減る」ことまでである
2. **差し戻しと `CHANGES_REQUESTED` の対応は本文頼みである**。変更要求は「満たさない項目番号・再提出の期限」(`gate-criteria.md:85`)の欄を持たない(00 §2.1 注)。本文に書かせる形は機械が形しか見られず、差し戻しの記録は現行の判定記録ファイルより弱くなりうる。差し戻しの記録だけは判定記録ファイルを求める案(折衷)は、「同じ結果を導く手続を 2 つ持つと条件の緩いほうだけが使われる」(`gate-criteria.md:1208`)に抵触する
3. **出荷の範囲の数え方の改修は実機で検証されていない**。`ship-evidence.yml` は 2026-10-01 時点で実機未検証(`ship-evidence.yml:19-20`)であり、本案はその上にさらに「承認イベントの写しを含む PR を開く」工程を足す。`refs/pull/N/head` の保持(02 §8)は公式の保証が無く、写しを作る時点で原記録が読めない事態を扱っていない
4. **写しの真正性は API の応答と集約の信用に依存する**。写しを固定する集約が改ざんされれば検出できない(02 §9.3「全案に共通する穴」)。出荷判定者の承認は「写しが原記録と一致する」ことの一件ずつの確認ではない。これを超えるには承認者本人が記録へ署名コミットする形しかなく、それは判定ごとの記録 PR へ戻ることである。規制業が監査対応書式を維持する理由はここにある
5. **1 名体制・認証情報を共有する体制では何も軽くならない**。判定者が自分で成果物を push すると自己承認が止まり、AI と同じアカウントでも止まる(ADR-0035 条件3)。この体制では全ゲートが判定記録ファイルへ戻り、記録 PR の往復は残る。起票者の体制がこれに当たるなら、本案は起票者の訴えに答えていない
6. **基底の更新による承認の失効は本案で解けない**。`strict_required_status_checks_policy` と `dismiss_stale_reviews_on_push` の組み合わせによる再承認の往復は #296 T-09 の論点であり、本案は「承認は承認した内容に束縛される」を不変条件として扱うため、緩める方向を採れない。起票者の訴えの半分はここにあり、本 Issue の範囲では残る
7. **CODEOWNERS は「所有者の誰か 1 人」で足り、bypass actor を素通りさせる**(02 §4.3)。判定者の席を CODEOWNERS に割り当てても、席に複数人がいれば誰が判定者かは承認イベントからしか分からず、admin の bypass は止まらない。本案は bypass を集約が読んで欠落に数える形で塞ぐが、`exempt` が設定されていれば読めない(02 §9.2)。ルールセットの設定の定期点検は人の作業である
8. **GitHub App・`GITHUB_TOKEN` による PR の作成の可否は組織の設定に依存する**(02 §4.1・§5.2)。集約が出荷の記録 PR を開けない組織では、人が開くことになり、その人が記名者と別なら 3.2 の「承認者 = 記名者」は成立する(push した者と承認者が別)が、記名者本人が開く場合は自己承認が止まる
