## 共通の原則(今回の指摘に共通する欠陥への対処)

**標準が定めたことのうち、テンプレートに降りていないものは、実装するか、降りていないと書く**。どちらもしていない箇所を残さない。

- 標準側: 実装マーク(`state=undelivered`)と、`ci-gates.md`・`template-repository.md` の「実装の制約」へ書く
- テンプレート側: README と、該当するスキル・出力へ「機械では確かめていない」と書く
- 出荷判定者が読む品質レポートには、G-7 の基準ごとに「機械が確かめた結果」か「機械では確かめていない。出荷判定者が次の記録と突合する」かを出す

## 独立した人の確認と、G-7 の突合(品質保証の検証)

### K44 PR の識別を、件名の番号に依らない形へ(QA-G1)

- コミットを PR の変更として扱うのは、そのコミットが当該 PR のマージコミット(`mergeCommit`)と一致する場合に限る。件名に `(#N)` があっても、一致しないコミットは PR を経ていないコミットとして扱う
- マージコミットを取得できない PR の番号を持つコミットは、PR を経ていないコミットとして扱い、その旨を表示する
- スカッシュ以外のマージ方式(マージコミット、リベース)でも、PR のコミットが二重に数えられない・直接コミットに誤って数えられないことを場面で確かめる。扱えない方式があれば「実装の制約」へ書く

### K45 G-7 の基準ごとに、機械が確かめる範囲を正直に出す(QA-G2、RC-L8)

- `ci-gates.md` の「判定基準との対応」の表へ、基準ごとにテンプレートの実装の有無を書く。実装に無い項目(テスト消化率、未解決の重大欠陥、負債の記録漏れ、欠陥注入の残存など)を「欠落で fail」と書かない
- 「QA は突合するだけで判定できます」を、機械が確かめる範囲と、人が突合する範囲を分けた記述へ改める
- テンプレートの品質レポートは、G-7 の基準1〜9 のそれぞれについて、機械が確かめた結果、または「機械では確かめていない。出荷判定者が次の記録と突合する: <記録>」を出す
- 基準5(全ゲートの通過記録): 機械で導ける範囲を実装する。構成で適用するゲートごとに、当該出荷の範囲の判定記録の件数を出す。変更が `Spec:` トレーラで仕様を指す場合は、その仕様の機能仕様承認(G-4)の判定記録の有無を確かめ、無ければ `gaps`。導けないゲート(出荷に対応する記録の数を機械で決められないもの)は、件数を表示し、人が突合する範囲として出す
- 実装しなかった基準は、実装マーク(undelivered)を `ci-gates.md` の該当箇所へ付ける(target は `evidence-aggregation`)

### K46 G-6 を適用する体制で、独立した人の確認が無い変更は記録の欠落(QA-M1)

- 構成で G-6 を適用する体制では、独立した人の確認(K13 の条件)を経ておらず、G-6 を事後へ移した変更でもない変更は、`gaps` へ入れる。件数の表示だけで通さない
- G-6 が未達の体制(1〜2名で確認者なし)では、現行どおり未確認として開示する(R1 は例外承認を要する)
- 標準側: 第3章 3.5 と第4章 G-6 の「ブランチ保護で機械強制」を正確にする。PR の作成者が AI・bot の場合、ブランチ保護は作成を指示した者の承認を止めない。止めるのは、出荷の証跡の集約である

### K47 挙動要約を伴わない承認は、独立した人の確認に数えない(QA-M2)

- 第4章 G-6 と第5章は「要約を伴わない承認は差し戻し」と定める。集約も、レビュアの挙動要約が無い承認を数えない(数えない理由 `no-reviewer-summary`)。G-6 を適用する体制では K46 により `gaps`
- `ci-gates.md` の「fail させない」を改める

### K48 例外承認の突合を、記録の中身まで見る(QA-M3)

- 例外承認が対応づくのは、記録が当該の変更(PR 番号またはコミットの識別子)を対象として明示し、状態が有効(返却済み・失効でない)で、承認した者の記名・理由・期限が記入されている場合に限る
- 台帳の様式(テンプレ3)へ、承認した者の欄が無ければ足す(第7章 7.3 の要求)。標準側とテンプレート側の両方。必須欄として登録する
- 番号の文字列が他の行に含まれるだけでは対応づけない

### K49 承認の後に変更要求が出た PR(QA-M4)

- レビューは、レビュアごとの最後の状態で数える。承認の後に同じ人が変更要求を出した場合、取り下げられた承認は数えない

### K50 出荷判定者と事業決裁者の兼務(QA-M5)

異議の仕組み(ADR-0056 決定5)は、異議を書く者と、読んで受容する者が別の人であることを前提にしている。同じ人が兼ねると、受容が自己完結する。

- 3名以上の体制では、出荷判定者の席と事業決裁者の席の責任者を同一人物にしない(拒否)
- 1〜2名の体制では、逸脱として記録し、保証の開示の項目1 へ「異議を書く者と、残存リスクを受容する者が同一である」と表示する
- 標準側: 第3章 3.5 の兼務禁止の表へ足す。ADR-0056 決定5 へ前提として書く。`src/data/processes/integrated.yaml` の分離の定義へ足す。附属書H H.5 と H.11 へ
- 採らなかった案: 1〜2名でも禁止する(1名体制を宣言できなくなる。未達・逸脱を正直に表示するという ADR-0028 の方針に合わない)

### K51 即時通知の対象と通知先(QA-M6、SC-軽)

- 即時に知らせる事象へ、次の2つを足す: 独立レビュー(G-6)が成立から未達・成立しないへ変わる変化、出荷判定者の席の責任者の交代
- 通知先: 出荷判定者の席の責任者。出荷判定者の席の責任者が交代する変化点では、前任者にも通知する。前任者が離脱済みの場合は、D-0 表1「体制と運用形態」の決定者へ通知する
- 品質保証部門を置く組織は、D-0 に部門の通知先を定めてよい。定めた場合は、すべての即時通知をそこへも送る(構成の `governance.qaNotice`。任意)。本標準は部門の設置を要求しない(H.12 の語の対応と同じ)
- 通知する者と通知先が同一人物である場合(1人体制など)は、通知の入力を要求しない。「通知する者と通知先が同一」と自動で記録し、表示する

### K52 附属書H の補足(QA-M7・M8、QA-L2、RC-L4・L6)

- H.12 へ足す: 出荷基準と欠陥トリアージ基準を定める場への関与/欠陥注入(検出能力の測定)の実施主体と件数は組織が定める旨(本標準は定めない)/名簿の初回の確認/G-8 の記録の後の再集約/欠陥が流出したとき(第7章、フェーズ6 の該当手順への参照)/受託で受け入れる側の作業/記録の保管期間/権限の一時制限(7.9)の通知を受けた後の作業。各行は条項への参照と作業の1行。条項に定めが無い作業は「本標準は定めない。組織が定める」と書く
- H.12 と H.4 が引く条項のずれ(RC-L6 の4か所)を、実際に定めている条項へ直す
- H.10 へ ISO 9001 の箇条 8.3(設計・開発。8.3.4 管理、8.3.6 変更)、9.3(マネジメントレビュー)、10.2(不適合及び是正処置)との対応を書く。対応を示さない箇条は「示さない」と書く。`vision/04-traceability.md` の「附属書H は箇条番号を引用していない」を実態へ
- H.6 の表示例を、実際の出力へ合わせる(委任の件数の出方、K53 の語)

## 語と条項の食い違い(突合の検証)

### K53 「人の事前確認を経ていない変更」の語を1つの定義へ(RC-M1)

- **標準の定義を正とする**: G-6 の判定を事後へ移した変更を指す
- 実行層の `withoutPriorHuman`(トレーラ `Delegated` のうち、独立した人の事前の承認が無いもの)は、「独立した人の事前の承認が無い委任の変更」と呼び分ける。その内訳として、G-6 を事後へ移した変更と、それ以外(未確認。K46 により G-6 を適用する体制では `gaps`)を出す
- 旧い書き方(委任の変更は事前の承認の記録を持たない、と一律に書く)を直す: テンプレートの判定記録の様式、gate-record スキル、`qms-document-control.md`、IMPL-0027 の note、`ci-gates.md`、`git-strategy.md`、テンプレートの `CLAUDE.md`・implement スキル、附属書H の例

### K54 開発者の席の委任で、検証欄の書き手と Ready 化を定める(RC-S1)

- 「検証方法と結果は人が書く」「AI の記載は差し戻してよい」「Ready にするのは人」は、**人確定・協働の変更**についての定めである。各行の中へ限定を書く(ADR-0039)。対象: `pr-workflow.md`、附属書C `review-guide.md`、`developer-guide.md`
- 開発者の席の委任の範囲の変更では、担い手が実行結果の証拠を書き、担い手が Ready にしてよい。レビュアは、検証欄が担い手の記載であることを理由に差し戻さない。挙動要約と3パスは、事前に承認する独立レビュア(人)が行う
- 第5章 5.5.6 と `pr-workflow.md` に、委任の変更を Ready にする者を書く。テンプレートの権限設定が担い手の Ready 化を妨げていれば、委任の範囲に限って通す形を検討し、できなければ「実装の制約」へ書く

### K55 登録の前提と根拠を、テンプレートへ降ろす(RC-M2)

- 変更種別の登録(`delegation.changeTypes[]`)に、登録の根拠を持たせる: 5.4.6 の検知条件を何で計測するか(`basis.detection`)、取り消しを実行した実績の所在(`basis.rollback`)、既存のテストで検出できることの根拠(`basis.tests`)。未記入の種別は登録を受け付けない
- 機械が確かめるのは記入の有無だけである。内容は、登録する者(B-4、または D-0 表1 の決定者)が判定する。その旨を README・スキル・「実装の制約」へ書く
- テンプレートの README の「7条件を満たせば切替」の案内へ、登録の前提を足す
- 標準側: 5.5.4 の登録の表へ実装マークを付ける

### K56 抜き取りの実施者の旧文言(RC-M3)、異議の理由の欄(RC-M4)

- 「(席の)責任者が事後に抜き取りで確かめる」を「独立レビュアの席の責任者が」へ: テンプレートの D-0 の様式・README・判定記録の様式・gate-record スキル・`delegation.mjs` の出力文、標準のテンプレ4 の注記
- 異議の欄の説明へ「第4章 G-8 の4事項に当たる場合は理由を書く」を足す: 第5章 5.7.2、標準のテンプレ4、テンプレートの判定記録の様式

### K57 事項3 の件数の定義(RC-M5)

- 事項3 は「独立した人の確認を経ていない変更の件数、または構成上の未達のゲートと逸脱の数が、前回の出荷より増えた」とする。どちらか一方の増加で当たる
- 第4章 G-8、附属書H H.5 と例、フェーズ6、集約を合わせる

### K58 委任の期間ごとの保証の開示(RC-M6、QA-M9)

- 集約に、出荷の範囲によらず期間を指定して保証の開示を出す入力を足す(期間の起点と終点)。期間の開示は、委任で先へ進めた変更と、事後の抜き取りの結果を出す
- 定期の実行(月次を既定)のワークフローを用意する。実環境で確かめていない旨を書く
- 期間の開示への G-8 の受容と異議は、判定記録(テンプレ4)の「対象」へ期間を書いて記録する。集約は、期間の開示に対応する記録の有無と、異議の欄を確かめる
- 標準側: `ci-gates.md` へ出し方と制約。実装マーク

### K59 突合の軽い指摘(RC-L1〜L10)

- L1: 第8章の図と文が「7条件を満たせば G-6 は事後」と読めないよう、限定(独立レビュアの席の委任)を図と文の中へ

## 体制の変化点(場面の検証)

### K60 席の責任者の任免は、決定の権限を持つ者の記名を要する(SC-重大1)

- 席の責任者を任命・交代させる変化点は、D-0 表1「体制と運用形態」の決定者の記名と理由を要する。人の離脱そのもの(名簿から外れる、席が空く)は「発生」であり、記名を待たない。後任を座らせる・別の人へ替えるのは決定である
- 決定者の席(既定は事業決裁者)の責任者を替える変化点は、前任の決定者の記名を要する。前任者が離脱済みの場合は、名簿へ外部の人として登録した組織上の任命権者の記名を要する。この場合は「決定者の任命を、組織上の任命権者の記名で行った」と表示する
- 1人体制の初回の記入(全席が未記入の状態から、本人が自分を書く)は、初期の設定として記名と理由つきで受け付ける
- 標準側: 3.13.3 の「決定」の段階がこの読みで書かれているかを確かめ、足りなければ足す

### K61 引き継ぎで行き止まりを作らない(SC-中2・3・4)

- AI維持管理者の席の責任者が交代した場合、前任者が承認した規則は承認待ちになる。新任者が `ruleApprovedBy` で承認し直せる(規則を消して足し直すことを要求しない)
- 適合性確認の実施者が名簿から外れても、確認の記録は有効なまま残る(第3章 3.4.2)。承認し直しの検査で、記録時点の実施者を現在の名簿と照合しない
- 席の責任者の交代の後、その席の委任を新任者が引き継ぐ入力を1つにまとめる: 適合性確認の承認し直しと、その席の規則の決定の記名のし直しを、新任者の記名と理由で同時に受け付ける。スキルの例をこの入力へ直し、拒否の文に直し方を出す
- 規則の範囲を広げたとき、承認済みの範囲は有効なまま残し、広げた部分だけを承認待ちにする(K40 の趣旨)

### K62 PR を経ない体制でも、書き換えの検出が出荷までに働くようにする(SC-中5、QA-L4)

- 契約検査(要約値の連鎖と、前の版との比較)を、既定ブランチへの push でも実行する(比較の相手は push の直前のコミット)
- 出荷の証跡の集約は、連鎖の検査と、構成の整合(契約検査の該当部分)を実行し、不整合を `gaps` へ入れる
- 回答と名簿の矛盾(回答は確認者なし、名簿には外部の確認者を席へ記入、など)を検出する
- 標準側: 「実装の制約」を実態へ

### K63 委任の経路の穴(SC-中6・7)

- G-6 を事後へ移す委任で、行為した席(開発者の席)が委任でない、またはその席の規則に該当しない変更は、開発者の席が協働である。この場合、開発者の席の人による検証が変更ごとに要る(5.5.6)。機械がマージを実行する条件へ、開発者の席の責任者(人)の承認があることを足す。案内の文も「人の記入を要求しません」と出さない
- トレーラ `Delegated` を持つ変更のリスク区分が R3 でない場合、集約は「委任の範囲の逸脱」として `gaps` へ入れる

### K64 初期化のコミット(SC-中8)

- テンプレート由来の初期コミットなど、構成の初期化の記録より前の履歴は、対象外(`pre-init`)として扱い、件数を表示する
- `/process-init` が作るコミットには、スキルの例でトレーラ(`Risk`・`Verification`)を書く。`Verification` には契約検査の結果を書く

### K65 場面の軽い指摘

- 協働へ下げずに切り替える条件4 の記名は、当該の席の責任者に限る
- 日付の検査: 実在しない日付、未来の確認日、変化点より前の通知日を拒否する。事例と結果が旧い記録と同一の適合性確認は、機械で判別しない。限界として開示する
- `sgRecord` は `docs/gates/` 配下の判定記録に限る
- B-4 を置かない体制の登録者の既定と、変え方の案内
- 確約範囲の内側・強制層を指す規則は、登録時に警告する(判定では常に対象外)
- 差分と通知の表示を、名簿の識別子でなく氏名で出す
- D-0: 版を下げる変更を拒否する。D-0 が無い状態で変化点を適用しない。承認者と承認日は、変化点の決定者と日付から生成する
- 10名以上の兼務禁止の拒否文、初期化の記録の日付の形、トレーラの位置の案内
- 承認だけの変化点で委任が有効になる場合、向きを「緩める」として記録する(決定者は宣言時の者)
