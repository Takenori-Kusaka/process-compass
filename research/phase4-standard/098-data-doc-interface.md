# 調査メモ: データ(YAML)とドキュメント(Markdown)のインターフェース設計（Issue #98）

- 調査日: 2026-08-05
- 対象 Issue: #98 「integrated.yaml データモデルとフェーズ4ドキュメントの参照関係を整理する」
- 目的: YAML 側の変更がドキュメントのガイドラインを壊さないインターフェースを、実務のプラクティスを根拠に定める

---

## 1. 現状の問題（着手前の観察）

`src/data/processes/integrated.yaml`（476行）と `src/content/docs/phase4-process-design/` の記述には、次の重複がある。

| 重複している内容 | YAML 側 | ドキュメント側 |
| --- | --- | --- |
| ゲートの判定基準 | `gates[].criteria` | 第4章の判定チェックリスト |
| ゲートの承認者 | `gates[].approver` | 第4章の見出し（例: 価値責任者・48時間） |
| ロールの責務 | `roles[].responsibility` | 第3章の任命基準・RACI |
| 成果物の説明 | `workProducts[].description` | 第6章の様式 |

同じ事実が2か所にあるため、片方だけを更新すると乖離（ドリフト）が発生する。どちらが正本かが定義されていないことが根本原因である。

## 2. 参照した実務プラクティス

### 2.1 Single Source of Truth と docs-as-code

- API 仕様（OpenAPI 等）を単一の正本として扱い、SDK・ドキュメントを生成することで、実装とドキュメントの乖離を防ぐ構成が定着している。
- ドキュメントをコードと同じリポジトリ・同じレビュー経路・同じ CI に載せる docs-as-code では、**CI にリンク切れ検査・スタイル検査・プレビュービルドを組み込むことでドリフトを大幅に削減できる**とされる。
- 「すべての鍵となるデータを一度だけ定義し、製品ビルドとドキュメントビルドの双方へ供給する」（True Single Sourcing）という考え方が、YAML と文書を併用する構成の基本形である。

出典:
- https://docopslab.org/blog/true-single-sourcing/
- https://sourcegraph.com/blog/documentation-as-code
- https://konghq.com/blog/learning-center/what-is-docs-as-code
- https://buildwithfern.com/post/api-documentation-best-practices-guide

### 2.2 要求のトレーサビリティと安定識別子

- トレーサビリティとは、要求の発生から仕様化・実装・運用までを前方向および後方向へ追跡できる性質である。
- 要求文書・モデル・テストは「同一情報の異なる表現」であり、独立に更新されるため整合性の維持が課題になる。
- 実務では**安定した一意識別子（ID）を付与し、表現間の結合点を ID に限定する**手法が用いられる。文言そのものを結合点にすると、表現の変更で追跡が切れる。

出典:
- https://en.wikipedia.org/wiki/Requirements_traceability
- https://www.sodiuswillert.com/en/blog/implementing-requirements-traceability-in-systems-software-engineering

## 3. 設計判断

### 3.1 正本の分担

「同じ事実を2か所に書かない」ことは、本プロジェクトの構成では実現できない。データは構造を、文書は判断の根拠を表現する必要があり、両者は粒度が異なるためである。したがって**同じ事実の重複を許容したうえで、要素ごとに正本を定める**方針を採る。

| 情報の種類 | 正本 | 従属側の扱い |
| --- | --- | --- |
| 要素の存在・識別子・関係（フェーズ、ゲート、ロール、成果物、タスク、順序、参照関係） | `integrated.yaml` | 文書は ID とラベルで参照する |
| 判定基準の内容・閾値・期限・様式・例外の扱い | フェーズ4の各章 | YAML の `criteria` 等は要約であり、正本ではない |
| 用語の定義 | 第1章 1.4 | YAML の `name` は表示名であり、定義ではない |

### 3.2 結合点を ID に限定する

- 文書から YAML を参照する場合は、`id`（例: `g-ship`）またはラベル（例: `G-7`）を用いる。名称や説明文の一致を前提にしない。
- YAML から文書を参照する場合は、`href` にページのスラッグまでを指定する。**見出しアンカーへは張らない**。章の見出しは改訂で変わるため、アンカー参照は壊れやすい。
- ラベル（`G-1` 等）は文書側の通し番号であり、`id` との対応は YAML の `label` フィールドで固定する。この対応表が唯一の翻訳層である。

### 3.3 YAML 側の記述粒度の制限

`gates[].criteria` は「何を確認するか」の要約に留め、閾値・数値・期限を書かない。閾値は組織ごとに変わるため文書側（およびテーラリング規則）が持つ。

- 良い例: `受入基準が検証可能な形式で記述されている`
- 避ける例: `テストカバレッジが80%以上である`

### 3.4 変更手順の固定

構造の変更は必ず YAML から行う。

1. `integrated.yaml` を変更する（要素の追加・削除・ID の変更）
2. `npm run check` でスキーマ検証と内部リンク検証を通す
3. 影響する章の文書を更新する

逆順（文書を先に変更し YAML を後追いする）を禁止する。文書側が新しい要素を語り始めると、データに存在しない要素が標準として流通するためである。

### 3.5 検証の自動化

現時点で `npm run check` が提供する検証は次のとおりである。

- Zod スキーマによる YAML の構造検証（`src/content.config.ts`）
- 内部リンクの検証（存在しないページへのリンクを検出）
- textlint による文体検証

不足している検証（後続の課題）:

- YAML の `id` 参照の整合（`roles[].id` を `activities[].roles` が正しく参照しているか）
- 文書が言及するラベル（`G-1` 等）が YAML に存在するか

これらは フェーズ5（プロセス実装）の CI 設計で扱う。

## 4. 実装内容

1. スキーマ（`src/content.config.ts`）に、ロールおよび成果物からドキュメントへの参照（`href`）を追加する。ゲートには既に存在するため、要素間で表現を揃える。
2. `integrated.yaml` のロール・成果物に `href` を付与し、第3章・第6章へ接続する。
3. 第6章に「データとドキュメントのインターフェース」節を新設し、上記 3.1〜3.4 を規定する。
4. ADR-0010 として決定を記録する。
