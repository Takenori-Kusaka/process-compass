### 「検証の空洞化」を受け入れる理由 — 統合が私の反対理由を消しました

第1ラウンドで私は「性能評価の不正確性」を落としました。理由は「**危険源として立てても Hs / Ex / Oc / Av を付けられない**」でした。これはメタな指摘であり、表の1行にならないと考えたためです。

**安全QA の統合は、この反対理由を消します。** 「テストを通すためにテスト側を書き換える / 失敗を握り潰す / 限定的なベンチマークで対策済みとする」を**検証が検証として機能しなくなる**という一点にまとめれば、危険源として具体的になり、4パラメータが付きます。**Ex は「検証をエージェントが実行する頻度」、Av は「書き換えに人が気づけるか」で見積もれます。**

**ただし1点、条件を付けます。** Cox 2008 が指摘した「SR の順序づけ能力が検証されていない」という論点は、**「検証の空洞化」に統合されていません**。統合されたのはエージェントの挙動としての側面だけです。**Cox への応答は議題3-8 の限界の明示で別に扱ってください。** 安全QA も 3-8 で別に扱っており、そこは一致しています。**この2つが混ざると、「検証の空洞化を危険源に立てたから Cox に答えた」という誤読が生まれます。**

### 「監視能力の飽和」を Hz として立てるべきでない理由 — 循環します

**これを Hz として立てると、Av の見積りが循環します。**

Av は「危害の回避または制限の可能性」= **人が気づいて止められるか**です。一方、危険源「監視能力の飽和」の内容は **人が気づけなくなること**です。

この危険源に Av を付けようとすると、「**人が気づけなくなることに、人が気づけるか**」を見積もることになります。**記入者は Av2 か Av3 を機械的に書き、判定の根拠欄には「監視が飽和したら気づけない」と同語反復を書きます。** 表の1行が消費されて、何も新しい情報が出ません。

**そして安全QA 自身が、実効のある処方箋を議題3-4 で別に出しています。**

> 承認点の追加を根拠に Av を下げてはなりません。ただし、追加後に1人あたりが処理する判断の件数と、その件数で判断の内容を読み切れる根拠を記録した場合はこの限りではありません

**これは Av の記入規則であり、Hz の行ではありません。** 飽和という機序が効くのは、**他の危険源の Av を見積もるとき**です。飽和それ自体を1行にしても、その行の中でしか働きません。

**私の判定: 議題3-4 の記入規則は採る。Hz の行は落とす。** 安全QA の提案のうち、実効を持つ側を残し、重複する側を落とします。

### 「意図からの乖離」を落とす理由 — 既存の類型と Ex の見積り規則で二重になります

**ASI10「目的からの逸脱」が既にあります。** 安全QA の「意図からの乖離」との差は、**「動作期間が長くなるにつれて」という条件だけ**です。

**その条件は、既に Ex の見積り規則に入っています。** テンプレ9 の記入注意はこう書いています。

> Ex は「そのツールが呼ばれる頻度」と「**自律実行が継続する時間**」の積で見積もる

**「動作期間が長い」は Ex を上げる要素であり、独立の危険源ではありません。** ASI10 の Ex を長時間側で見積もれば、同じものが表に出ます。さらに「時間上の限界(自律実行の上限)」の欄(制限の表)とも重なります。**同じ事象が3箇所に現れます。**

## 質問2: 第3の装置(分類を使わない導出経路)が案件へ降りてきたら、何をすることになるか

**回答: 安全QA の案(軽量版に UCA を1件以上)は耐えられます。ただし目的を達成しません。代案を出します。**

### まず、実際に何をするかを書きます

安全QA の提案は、テンプレ9 軽量版に次を置くものです。

```
## 2b. 不適切な制御動作(軽量版でも1件以上)
| ID | 制御動作 | 観点 | 危害に至る条件 | 対応する Hz |
| UCA-01 | | 与えない / 与える / 時期 / 継続時間 | | |
```

P-001 でこれを埋めるとき、私がやることは次です。

1. **制御構造を頭の中に置く。** エージェント / 私 / CI / GitHub / 本番環境の5要素。801行に例示があるので、図は描きません
2. **制御動作を列挙する。** 「PR を作る」「ブランチへ push する」「CI を起動する」「ファイルを書く」「外部へ HTTP を出す」「サブエージェントを起動する」
3. **各動作について4観点で危害条件を考える**
4. **1件を選んで書く**

**所要時間は、真面目にやって30分から1時間です。案件で1回なら、耐えられます**(訂正B の基準)。

### それでも目的を達成しない理由

**「1件以上」という要求は、記入者に最も書きやすい1件を選ばせます。そして最も書きやすい1件は、たいてい既に ASI で拾えているものです。**

上の手順3で、私が最初に思いつくのはこれです。

> 「与える」観点 — レビューを経ずに本番へデプロイする制御動作を与えてしまう

**これは ASI05(未検証コードの実行)そのものです。** UCA-01 として書けば要求は満たされ、機械検査も通り、**分類の外は1件も探されていません**。

**分類の外を探させるには、「1件以上」ではなく「どの観点で探すか」を指定する必要があります。**

### 代案 — 時間軸の2観点を指定する

**4観点のうち、コーディングエージェントで分類の外を生成するのは、時間軸の2つだけです。**

| 観点 | そこから出るもの | ASI に対応物があるか |
| --- | --- | --- |
| 与えない | レビューを求めずに進む | **ある**(ASI05 / ASI09) |
| 与える | 与えてはならない権限で操作する | **ある**(ASI02 / ASI03) |
| **早すぎる / 遅すぎる** | **停止の指示が間に合わない。承認の求めが多すぎて処理が遅れる** | **ない** |
| **長すぎる / 短すぎる** | **自律実行が長く続き、当初の目標から動作が離れる** | **ない** |

**ここが今回の回答の要点です。** 質問1 で私が Hz から落とした2件 —— **「監視能力の飽和」と「意図からの乖離」** —— は、**時間軸の2観点から自動的に導出されます**。

- 「遅すぎる」→ 承認の求めが多すぎて、人の応答が追いつかない = **監視能力の飽和**
- 「長すぎる」→ 自律実行が続くうちに、当初の目標から動作が離れる = **意図からの乖離**

**分類に2行足す代わりに、導出経路を指定すれば、同じものが出ます。しかも「なぜそれが危険源になるか」が案件の文脈で書かれます。**

**具体の代案**:

```markdown
## 2b. 制御動作の観点による洗い出し(軽量版でも実施する)

**時間の観点2つについて、各1件以上書きます**。他の2観点(与えない / 与える)は任意です。
時間の観点を必須にする理由は、危険源の分類が攻撃面で構成されており、
**時間に起因する失敗様式を含まない**ためです。

| ID | 制御動作 | 観点 | 危害に至る条件 | 対応する Hz |
| --- | --- | --- | --- | --- |
| UCA-01 | | 早すぎる / 遅すぎる | | |
| UCA-02 | | 長すぎる / 短すぎる | | |
```

### 差し引き

| | 欄 |
| --- | --- |
| 安全QA 案(Hz 6件 + UCA 1件) | Hz +2行 × 19欄 = **+38欄** / UCA +1行 × 5欄 = **+5欄** |
| **私の代案(Hz 4件 + UCA 時間軸2件)** | Hz +0 / UCA +2行 × 5欄 = **+10欄** |

**差し引きは −33欄です。** ADR-0013 決定2(差し引きが負であることを提案の要件とする)を満たします。

**ただし、この計算には条件があります。** Hz の2行は、案件が該当ありと判定した場合にだけ埋まります。**該当なしと判定する案件では、差し引きは −5欄まで縮みます。** 誇張しないよう書いておきます。

### 手法の名前について — 安全QA の自己批判に同意します

安全QA は自分でこう書いています。

> **制御構造図なしの UCA は STPA ではありません**。……手法の名前を借りながら手順を守らないのは、私が 774行に対して批判しているのと同じ形の誤りです

**同意します。そして解決策は簡単です。STPA と名乗らないでください。**

私の代案では見出しを「**制御動作の観点による洗い出し**」としました。**手法の名前を出さなければ、手順を守っていないという批判は成立しません。** 774行の誤りは「網羅性」という主張の側にあり、手法の借用そのものではありませんでした。**主張しなければ、批判の的が消えます。** これは安全QA が横断1 で立てた原則(強い主張をするときにだけ証拠を要求する)を、手法の名前へ適用したものです。

**反対されうる点**: 名前を出さないことで、**この手順が何に由来するのかが読み手に分からなくなります**。稟議で「STPA に基づく」と言えなくなるのは、実務上の損失です。私はこれを受け入れますが、**稟議での説明可能性を重く見る立場からは反対されえます**。

## 質問3: 昇格の禁止は、P-001 で実際に効くか

**回答: 効きも止めもしません。適用対象がゼロだからです。そして私は、第1ラウンドの結論を変更します。**

### 最初に、事実を出します

**P-001 で 7.3 の例外承認を使ったことは、一度もありません。適用件数はゼロです。**

これは第1ラウンドで書くべきでした。**G-2 停止のときも、7.3 は使っていません。** 私が止めたとき、それは例外承認を経て進む事案ではなく、判定そのものが成立しない事案でした。

**したがって、昇格の禁止(未回収の例外承認がある間は次のゲートで通過を出せない)を今 P-001 へ入れても、掛かる対象がありません。** 空振りします。

### この事実が何を意味するか

**7.3 の適用件数がゼロであることは、2通りに読めます。**

1. **逸脱が起きていない。** 基準を満たさないまま進めた場面が実際になかった
2. **7.3 を回避している。** 逸脱はあったが、7.3 を使わない形で処理した

**私は、この2つを自分で区別できません。** 記録があるのは前者を支持する形(記録がないので逸脱もない)ですが、**それはまさに 7.3 を回避したときにも同じ見え方をします。**

**そして EV-0021 の差し替え条件が「3案件分のゲート判定記録と、7.3 の例外承認の適用件数」であることは、この区別が付かないことを制度側も認識しているからだと読めます。**

### 結論の変更 — 「1. 採る」から「4. 保留」へ

**訂正A の枠組みを自分の案に当てると、私の第1ラウンドの順位づけは誤りでした。**

第1ラウンドで、私は「一貫性の強制」を **台帳が空だから保留** としました。同じ論理は昇格の禁止にも当たります。**7.3 の適用が0件なら、参照すべき過去の例外承認も、止める対象の未回収項目も、どちらも存在しません。** 片方だけ採り、片方を保留にした線引きに根拠がありませんでした。

**さらに悪いことに、私は逆の順序で採っていました。**

| 装置 | 種類(訂正A) | 空振り時のコスト | 実装後に 7.3 の使用を減らす力 |
| --- | --- | --- | --- |
| 一貫性の強制(参照 ID の列挙) | **書く手間** | 「該当なし」1回分 | **弱い** |
| **昇格の禁止** | **工程を止める** | ゼロ | **強い** |

**私は、7.3 の使用を最も強く抑止する装置を第1位に置き、最も抑止しない装置を保留にしていました。** 「重い手続は記録を消す」という自分の主張と、正面から矛盾します。

**したがって結論を変更します。**

| 装置 | 第1ラウンド | **第2ラウンド** |
| --- | --- | --- |
| 昇格の禁止 | 1. 採る | **4. 保留** |
| 一貫性の強制(監査役の層1・層2) | 4. 保留 | **1. 採る** |
| 自動失効 | 3. 変えない | 3. 変えない(昇格の禁止に帰着するため、同じ保留に従う) |
| 総量管理 | 3. 変えない | 3. 変えない |

**一貫性の強制を採る側へ動かす理由**は、監査役の設計が私の反対理由を消したためです。監査役は層3(判断の一貫性の判定)を明示的に要求せず、層1・層2(参照 ID の列挙と実在検査)だけに絞りました。**しかも「該当なし」と書いた行を、台帳の実データで反証できる形になっています。**

> 3. 同一基準項目番号の過去エントリが存在するのに「該当なし」と書かれていない —— 突合検査

**これは、自己申告を機械が反証できる数少ない形です。** 現場から見て、**書く手間は「該当なし」1回分、工程は止まりません。** 訂正A の分類で最も安い側にあります。台帳が空の間は空振りしますが、**空振りのコストが1回分の記入で済むなら、溜まってから足すより先に置くほうが安い**という監査役の主張に同意します。

### 昇格の禁止の差し替え条件 — 保留を解く条件を明示します

**次のどちらかが満たされた時点で、昇格の禁止を再協議してください。**

1. **7.3 の適用件数が、いずれかの案件で3件を超えたとき**
2. **7.3 を経ずに基準未達のまま進んだ事案が、事後に1件でも見つかったとき**

**2 が重要です。** 1 は「7.3 が使われている」ことの確認であり、2 は「7.3 が回避されている」ことの確認です。**私が今区別できない2つの読みは、2 が観測された時点で決着します。**

### 保留の間、代わりに何なら守れるか

**止めずに、見えるようにします。**

> **ゲート判定記録に、当該案件の未回収の例外承認の件数を表示する。判定の可否には影響しない。**

- **書くのは CI です**(技術負債台帳の未返却行のうち、7.3 由来のものを数える)
