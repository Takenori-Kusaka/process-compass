## P-1 価値責任者 × 技術判断者の兼務の境界

**結論**: **第8章 軸A の3段(1〜2名 許容 / 3〜9名 非推奨 / 10名以上 禁止)を正とし、第3章 3.5 の表とテンプレートの様式をこれに揃える**。5名の境界は廃する。人数の軸を代替の統制へ替える案は、本議題では採らない(#338 へ残す)。

### 理由

1. **第3章の「5名未満」が誤っていることを示せる**。誤りは値の大小ではなく、検出できない境界であることにある
   - 決定の記録が無い。内部 1.6 は「5名・10名そのものを決めた ADR は見当たらない」とする。grep で `5名未満` を引き直し、本文 L306 とテンプレの D-0 L80 の2か所だけに当たることを確かめた
   - EV マークが無い。ADR-0026 は、実証に基づかない値にマークを課す。マークの無い値は、規定として不完全である
   - 3.13.1 の変化点(L1548)にも、設問 `q-team-size` の選択肢にも5名が無い。4名から5名への増員を手続も機械も捉えない。**越えたことが分からない境界は、守られたかを確かめられない**。信頼性の上で欠陥である
2. **第8章の値は、検出と開示の仕組みを持つ**
   - 10名は変化点にあり、設問の選択肢にあり、エンジン(`sizeSeparations`)とスキル(`headcount.md` L32・`dry-run.md` L40)が拒否する
   - `config.mjs` の `headcountProblems` は、名簿と席から数えた人数が回答の3名・10名の境界と食い違えば出す。`generate-profile.mjs` L4309 はそれを拒否に使う(自分で確かめた)
   - 10名には EV-0148(E0)が付いている。根拠は弱いが、弱いことが開示されている
3. **5〜9名を「禁止」にすると、新しい禁止を足すことになる**。機械は5〜9名の兼務を一度も拒否していない。ADR-0066 は禁止の範囲を広げることについて「根拠になる記録と測定は、確認できていません」として、広げなかった。同じ基準を当てると、5〜9名の禁止にも根拠が無い
4. **外部も5の側を支えない**。人数で役割の分離を決める規格・枠組みは見つかっていない(外部 5)。Team Topologies の「5」は信頼関係の数で、分離の閾値ではない(外部 F13)

## P-2 3.5.1 の既定の写像

**結論**
1. **ADR-0066 の分離は正しい。置き換えない**
2. **写像の表を直す**。独立レビュアは QM レーン(`state:dev-done`)、出荷判定者は別のレーン(`state:ready-to-merge`)、事業決裁者は独立(`state:needs-owner`)。文脈オーナーと AI運用担当者の行を足す(ラベルは持たない)
3. **レーンの写像は残す**。ADR-0037 の決定1〜4 を維持する
4. 新しい ADR を1本起こし、ADR-0037 を**置き換えず補う**ものとして記録する

### 理由: ADR-0066 の分離は誤っていない

外部の調査は「作成者と確認者の2者分離が一般的で、確認者と出荷者を別にする一般の要求は見当たらない」とする(外部 F14・7 Q2)。これは ADR-0066 を覆さない。

1. **ADR-0066 の分離は、2者分離の適用であって、その外への拡張ではない**。G-7 の基準5 は G-6 の通過記録を突合し、成立条件4 は独立の成立状況を確かめる(gate-criteria L881-892 を自分で読んだ)。G-6 の判定記録は独立レビュアが作った成果物である。G-7 はそれを確認する行為である。独立レビュアが出荷判定者を兼ねると、作成者(G-6 の記録の作成者)が確認者(G-7)を兼ねる。外部の主流の「作成者 ≠ 確認者」を、記録という成果物に当てたものである
2. 外部の先例(Google・GitHub)は、出荷の統制を「レビュー済みの成果物だけが本番へ入る」機械の来歴で担保している(外部 F14)。本標準は、その担保の一部を人による記録の突合(G-7)に置く。突合を人に置く以上、突合する人が突合される記録を作った人であってはならない
3. 外部は ISO 26262 の I3(リリース権限からの独立)を同じ向きの候補として挙げる(外部 F3。未確認)。逆向きの根拠(分離が欠陥の流出を増やす、など)は外部に1件も無い
4. ADR-0066 は弱い根拠を既に開示している(EV-0103、E1)。根拠の弱さを理由に決定を外すなら、外したほうの判断にも測定が要る

外部の示唆「R1 に限って課す」(外部 7 Q2)は採らない。席の兼務は構成の条件で、案件ごとに決まる。リスク区分は変更ごとに決まる(ADR-0039)。変更ごとに出荷判定者の席の責任者を入れ替えることはできない。独立の2層(3.5.4、ADR-0060 決定3)の構成の層へ、変更ごとの条件を混ぜることになる。

### 理由: 写像の表は誤っている(譲る)

- 3.5.1 の条件1(L484)は「禁止または△とされた組み合わせを、同一レーンへ写像しない」と定める。既定の写像は、独立レビュアと出荷判定者(禁止)を QM へ、事業決裁者と価値責任者(△)を PO へ置く。**同じ節の中で、既定が条件に反している**。本文 L472-476 と L484 を自分で照合した
- 3.5.3 は、同一の文脈が禁止された2つの役割を担ってはならないと定める。レーンは作業領域・セッション・認証情報の組である(ADR-0037 決定1)。セッションを分けても、作業領域と認証情報を共有すれば文脈は分離しない(3.5.3 の3条件)。QM レーンへの同居は、文脈の単位でも禁止に当たる
- ADR-0037 の「圧縮それ自体は設計であり、誤りではありません」は、ADR-0037 の時点では正しかった。当時、独立レビュア × 出荷判定者は禁止の組ではなかった(ADR-0066 のコンテキストが、規則データの禁止は開発者 × 出荷判定者だけだったと記録している)。**原則は今も正しく、ADR-0066 の後に例の1つが成り立たなくなった**。ADR-0037 の決定の文は QM の圧縮を定めていない(圧縮はコンテキストの表にある)。したがって ADR-0037 を置き換える必要は無い

## P-3 `state:dev-done` の受け手

**結論**: **受け手は独立レビュア(G-6 の判定者)とする**。正本は Label Mailbox 4.3.1 の遷移表。`ready-to-merge` の受け手は出荷判定者とする(P-2)。

### 理由

- 4.3.1 の遷移表は既に「`dev-done` → 独立レビュー承認 → `ready-to-merge`」「`dev-done` → BLOCK 検出 → `qm-blocked`」と定めている。遷移表の上では、`dev-done` を受けて動くのは独立レビューである。**誤っているのは 4.3 の語彙表の「次に動くロール」欄の「QM(出荷判定者)」、`pr-workflow.md` L33、`handoff.md` L10 の3か所**である。いずれも、独立レビュアと出荷判定者が同じ QM にいた時期の書き方が残ったものである
- 機械(`next.mjs` L579)は既に独立レビュアが `dev-done` で G-6 を判定する。G-6 の判定者は独立レビュア(第4章 L750)
- 「自分のロールの受信箱だけを見る」(3.5.3)の下で、1つのラベルが2つのロールの受信箱にあると、拾う者が決まらない。受信箱は1ラベル1ロールに限る必要がある。**差し戻しのラベル(`qm-blocked`)は、独立レビュアも出荷判定者も付けてよい**。受け手が開発者1つに決まるため、付与側が複数でも曖昧さは生じない
- 順序: G-6(PR ごと)→ `ready-to-merge` → 出荷判定者のレーン → G-7(出荷の範囲ごと。基準5 で G-6 の記録を突合)。G-7 の起動は、出荷の範囲の状態から `next.mjs` が出す(L618-629 を確かめた)。ラベルで起動する必要は無い

## P-4 人の名簿

**結論**: **名簿を標準の様式(テンプレ0)に置く。置き場は表5 の下とする**。別の表番号は起こさない。「表5(人の名簿と席)」という本文と ADR-0065 の呼び方を、そのまま正しくする。

### 理由

- テンプレ0 L103 は「現任者の個人名は表5にのみ書きます」と定める。名簿は個人名の一覧であり、**この原則から、置き場は表5 以外に無い**。表5 の下に「席の責任者本人の力量の確認」の表を置いた先例もある(L154)
- 名簿を外す案(本文の呼び方を改める案)は、ADR-0065 決定5(確認者の有無を名簿と席から導く)の土台を外す。採用済みの ADR の決定を、様式の欠落に合わせて弱めることになる。誤っているのは ADR ではなく様式である
- 外部も、分離を課す標準には名簿が要るとする(外部 7 Q3。ISO 13485 5.5.1・8.2.6、NIST AC-5)。ISO 9001 5.3 が文書化を求めないことは、本標準が分離の規則を課す以上、名簿を外す根拠にならない

### 必須の欄

規則が実際に使う欄だけを必須にする。使い道の無い欄は足さない。

| 欄 | 使う規定 |
| --- | --- |
| 識別子 | 席の責任者の欄との照合 |
| 氏名(自然人) | 記名の照合。AI の担い手は載せない(表7 に書く) |
| 区分(体制の内 / 外部の確認者) | 第8章 L156 の数え方、3.5 の外部の確認者の置き方(ア) |
| リポジトリのアカウント | G-6 の承認者を人へ対応づける(第4章 G-6) |
| 所属(10名以上の体制) | 第8章 軸A の10名以上の規則(IMPL-0084・IMPL-0085) |
| 氏名の確認(本人以外の記名 / 自己申告) | #296 L-9 と追加の裁定。1名の名簿は自己申告として開示する |

テンプレートの `appointer`・`accountsConfirmed` は、標準の必須欄にしない。テンプレートが持つことは妨げない(ADR-0040: 様式は部分集合、必須欄の存在だけを検査する)。`template-fields.yaml` へ上の欄を足し、両方向の検査に載せる。

### IMPL-0278 の注記は実装と合っていない(譲る)

自分で `config.mjs` L768-808 と `generate-profile.mjs` L4309 を読んだ。

- 準拠テンプレートは、席の責任者と名簿から体制の内の人数を数える(`Math.max(insiders, rosterInsiders)`)。3名と10名の境界で回答と食い違えば出し、生成は拒否する。注記の「名簿から数えない」「食い違いを検出しない」は事実に反する
- ただし、軸A の規則の適用は今も回答(`q-team-size`)で決まる。10名以上と回答して名簿が空の構成は、どの分岐にも当たらず出ない
- 注記を「名簿と席から数えた人数と回答の食い違いを、3名と10名の境界で出して拒否する。規則の適用は回答で決め、名簿の人数で決めない。10名以上の回答で名簿が空の構成は出さない」へ改める。降りていない部分が残るため、`state=undelivered` のまま置く

**他の案を落とす理由**

| 案 | 落とす理由 |
| --- | --- |
| テンプレ0 に別の表(表9 など)を新設 | 「個人名は表5にのみ」と衝突する。本文・ADR-0065 の「表5(人の名簿と席)」の引用が別の表を指すことになり、ADR は書き換えられない |
| 名簿を置かず、本文の呼び方を改める | ADR-0065 決定5 と G-6 の判定、第8章 L156 の数え方が、標準の様式で確かめられなくなる |

### 文の案(テンプレ0)

> 表5 の下に、人の名簿を置きます。名簿には、席の責任者と、席の責任者でない担い手(人)と、外部の確認者を載せます。AI の担い手は載せません(表7 に書きます)。人数(第8章 軸A)と G-6 の確認者の有無(第4章 G-6)は、この名簿と表5 の席から導きます。

- 名簿の欄は、識別子・氏名・区分(体制の内 / 外部の確認者)・リポジトリのアカウント・所属・氏名の確認とする
- 所属は、10名以上の体制で必須とする
- 名簿へ名前を足すのは人とする。AI の担い手が足してはならない

- 根拠: 内部 3、外部 F5・F6・F15・7 Q3。IMPL-0278 の実装は自分で確かめた

## P-5 表の記号の語彙

**結論**: **△・○ を 1.7.3 の語彙へ置き換える。1.7.3 に記号を足さない**。

### 理由

- overview L213 は「表の升に入れる語は、1.7.3 の語彙に限る」と定める。3.5 の表は規定の表であり、これに反する。**自己矛盾であり、譲る**
- 記号を語彙へ足すと、△ が非推奨か限定つきの許容か禁止かを読み手が決めることになる。1.7.3 が「省略可」「任意」を廃した理由(どちらとも読める)と同じ欠陥を持ち込む
- 置き換え: ○ → 許容。価値責任者 × 技術判断者 → 「許容(1〜2名)、非推奨(3〜9名)、禁止(10名以上)」(P-1)。事業決裁者 × 価値責任者 → P-6

**他の案を落とす理由**

| 案 | 落とす理由 |
| --- | --- |

- 3.5.1 の条件1: 「3.5 の兼務の表で**禁止**または**非推奨**とされた組み合わせを、同一レーンへ写像しない」
