# 会議体 #312 意見書 02 — 現場(3〜9名のチームのテックリード)

- 日付: 2026-10-23。ブランチ `work/312`。本書以外のファイルは変更していない
- 立場: 3〜9名のチームのテックリード。実際には1人が複数の席を持つ。判断の軸は、規則が小さなチームで実際に悪い決定を止めるか、人を割り当てられるか、追う境界と記録が増えすぎないか
- 根拠の区分: **[内部]** = `survey-312-1-internal.md`、**[外部]** = `survey-312-2-external.md`、**[自確]** = 本書の筆者が本文・テンプレートを直接読んで確かめたもの(所在を併記)

## 0. 現場から見た前提(先に書く)

1. **席の分離と相互の検査は別物です**。G-3 の判定者は技術判断者だけで、価値責任者は G-3 に関与しません。G-2・G-4 の判定にも技術判断者は関与しません [自確: `gate-criteria.md` G-3 見出しと判定基準1〜5、G-4 見出し]。3.5 の表が「価値と技術の相互チェックが消える」と書く相互チェックは、どの手続にも書かれていません。席を分けても、2人が互いの判断を読む保証は無いということです
2. **3名で、価値責任者×技術判断者を分けた構成は組めます**。3名を A・B・C とし、A=価値責任者+出荷判定者、B=技術判断者+開発者+事業決裁者+AI維持管理者、C=独立レビュア+AI運用担当者とすると、現行の禁止の組(開発者×出荷判定者、独立レビュア×出荷判定者、出荷判定者×事業決裁者、開発者×独立レビュア、AI維持管理者×AI運用担当者)をすべて満たします [自確: 3.5 の表 L302-315 と L319-321 から手で総当たり]。**人が足りないことは、この組の兼務を許す理由になりません**。問題は人数ではなく、分けた後に何が検査されるかです
3. **追う境界の数は、それ自体が信頼性の問題です**。現行は 3・5・10 の3つの境界を持ちますが、5 は変化点(3.13.1 L1548)にも設問(`q-team-size`)にもエンジンにも無く、越えたことを誰も捉えません [内部 1.7・2.1、自確: 3.13.1]。小さなチームは人の出入りが激しく、捉えられない境界は守られません
4. **IMPL-0278 の注記は実装より古いです**。`config.mjs` の `headcountProblems`(L773-805)は、席の責任者と名簿から数えた人数と回答の食い違いを 1〜2名/3〜9名/10名以上の境界で両方向に出し、`verify-gate-contract.mjs` L512 と `generate-profile.mjs` L4309 が拒否に使います [自確]。「回答と名簿の人数の食い違いを検出しない」は事実と違います

## P-1 価値責任者×技術判断者の兼務の境界

### 結論

**人数の境界(5名・10名)を、この組からは外します**。体制の人数によらず「許容(条件つき)」とし、条件として、兼務の事実の記録と、G-3 の判定記録を兼務者以外の人が読んで異議の有無を記名することを課します。体制の内に兼務者以外の人がいない1名体制では、条件の2つ目が成立しないため、逸脱として記録し表示し続けます。新しい EV(E0)を付けます。

### 理由

- **境界の値に根拠がありません**。外部に、役割の兼務を人数で決める規格・枠組みは見つかっていません [外部 5]。5 には EV が無く、10 の EV-0148 は対象に価値責任者×技術判断者の禁止を含みません [内部 2.1、自確: `tailoring-guide.md` EV-0148 の対象の行]
- **ADR-0066 が、同じ型の案を退けています**。ADR-0066 は「10名以上の体制でだけ、禁止の範囲を広げる」案を「人数で独立の意味が変わる理由を示せない」として採りませんでした [自確: ADR-0066 検討した選択肢]。価値責任者×技術判断者だけを人数で禁止に切り替える理由も、同じく示せません。3名が特別なのは、禁止の組から総当たりで導かれる構造上の値だからで、5・10 はそうではありません
- **失われる牽制を直接補うのは、席の分離ではなく「他人が読むこと」です**(0. の1)。外部の作法も、分離できない場合は代替の統制と理由の記録で補い、費用だけを理由に外しません [外部 F6・F8・F10]。実務家の議論も、人数ではなく「誰が誰を牽制するか」で兼務を論じています [外部 F12]
- **現場のコストに見合います**。G-3 は技術上の選択(ADR)に掛かる判定で、頻度は PR より桁違いに低いです。判定記録1件を読み、異議の有無を記名する手間は、名ばかりの技術判断者を立てるより小さく、記録に嘘が入りません
- **追う境界が減ります**。この組について境界を持たなければ、5 を変化点・設問・エンジンへ足す作業も、越えたことを捉え損なう事故も生じません

## P-2 3.5.1 の既定の写像

### 結論

**ADR-0066 の分離は保ちます**。既定の写像で、独立レビュアと出荷判定者を別のレーンへ分けます。事業決裁者も PO レーンから外し、独自のレーン(決裁のみ。作業領域を持たなくてよい)とします。写像に文脈オーナーと AI運用担当者の行を足します。ADR-0037 の「圧縮は設計であり、誤りではない」の部分を置き換える新 ADR を起こします。

### 理由

- **レーンの定義が、そのまま矛盾を作っています**。ADR-0037 決定1 はレーンを「作業領域・セッション・認証情報の組」と定めます [自確: ADR-0037 決定1]。独立レビュアと出荷判定者を同じレーンに置く既定は、3名以上で別人に置くことを義務づけた2つの席に、同じ認証情報を既定で与えることになります。3.5.1 の理由1(認証情報を分けて作成者≠承認者を機械で強制する)と、同じ節の条件1 に反します [内部 2.2]
- **現場の追加コストはほぼありません**。3名以上では2つの席は別人で、各人は自分のアカウントで動きます。レーンが1つ増えても、増えるのは写像の表の行であり、作業ツリーの数ではありません。同一人物が兼ねる3名未満は、既に 3.5.2 の逸脱として記録されています
- **ADR-0066 の分離は、現場でも意味があります**。G-6 は PR ごと、G-7 は出荷の範囲(複数の PR・リリース)ごとに行います [自確: テンプレート `gates/G-7.md` L24「出荷の範囲の PR(またはリリース)」]。単位も頻度も違う2つの判定を同じ受信箱に置くと、PR ごとに出荷判定者が呼ばれる運用になります。外部に一般の要求は無い [外部 F14・Q2] ものの、ADR-0066 は EV-0103(E1)で開示済みであり、覆す新しい記録はありません
- **事業決裁者は AI の作業領域を要しません**。決裁は人が読んで記名するもので、PO レーンに同居させる理由がありません。同居させると、条件1 の対象の組(事業決裁者×価値責任者)を既定で同じレーンへ置くことになります

## P-3 `dev-done` の受け手

### 結論

**`state:dev-done` の受け手は独立レビュアだけとします**。G-6 を通過したら独立レビュアが `state:ready-to-merge` を付けます。出荷判定者は PR ごとのラベルの受け手にしません。G-7 は出荷の範囲ごとに行い、その依頼は出荷の範囲を単位に渡します。ラベルの遷移の正本はフェーズ5 `label-mailbox.md` 4.3・4.3.1 とし、3.5.1 は受信箱を引くだけにします。

### 理由

- **順序が決まっています**。G-7 は G-6 の通過記録を突合するため、G-6 が先です [自確: `gate-criteria.md` G-7 基準5 と基準5 の突合の規定]。`dev-done` は PR の実装が済んだ状態で、次に動くのは G-6 の判定者です。テンプレートの機械(`next.mjs` L579)は既にこの形です [自確]
- **2つの受信箱に同じラベルを置くと、拾う人が決まりません**。「自分のロールの受信箱だけを見る」規則の下で、両者が拾うか、両者が相手が拾うと思って滞留します [内部 2.3]。現場で最も多い滞留の型です
- **出荷判定者を PR ごとに呼ぶ運用は回りません**。G-7 は3営業日の判定で、範囲の PR をまとめて突合します [自確: G-7 見出し、テンプレート `gates/G-7.md`]。PR ごとにラベルで呼べば、3〜9名のチームでは出荷判定者が全 PR の待ち行列になります
- `ready-to-merge` の付与者を独立レビュアに限ると、「QM が独立レビューを完了し、マージを承認した」という現行の定義の中の主語の混同(独立レビュアと出荷判定者)が解けます

| 出荷判定者(文書の現行) | G-6 の判定者が受信箱で指されなくなり、3.5.1 の条件2(判定者のロールはラベルで指せる)に反する |
| 両方(機械の現行) | 上記の滞留。ADR-0066 の分離を、受信箱の上で再び同居させる |
| 新しいラベル(例: G-7 依頼)を足す | 経路が既にある場合はラベルを増やさない(第5章 4.2 原則5、#217)。出荷の範囲の依頼は `/pit` と出荷の証跡の集約の出力が既に担う [自確: `gates/G-7.md` L24]。伝達の欠落が確かめられたら 4.6 の手続で足す |

## P-4 人の名簿

### 結論

**標準の様式(テンプレ0)に人の名簿を置きます**。表5 を「表5(人の名簿と席)」の名に合わせ、表5-1 席と責任者(現行の表5)と表5-2 人の名簿の2つで構成します。表の番号「表5」は保ち、本文と ADR-0065 の引用を生かします。必須の欄は最小にします。IMPL-0278 の注記を実装に合わせて改めます。

### 理由

- **本文が名簿に依存して判定しているのに、様式に名簿がありません**。G-6 の確認者の有無、軸A の人数、外部の確認者の置き方(ア)は、いずれも名簿の記載で判定すると定めています [内部 3.2]。様式に無い欄で判定させる規定は、適合を主張する組織が何を書けばよいか分かりません
- **分離の規則を課す以上、誰と誰が別人かを示す記録が要ります** [外部 Q3、F5・F6]。ISO 9001 が文書化を求めないことは [外部 F15]、分離の規則を持たない一般の QMS の話で、本標準には当てはまりません
- **現場の手間は増えません**。テンプレートは既に `people[]` を持ち、D-0 節1 に生成しています [自確: `templates/00-d0-governance.md` L50-63]。標準の様式がこれに追いつくだけです。1名体制なら1行です
- 席と名簿を別の表番号にすると、5か所以上の引用(第1章 L381、第4章 G-6、第8章 L156・L189、ADR-0065)を書き換える必要があり、採用済み ADR は書き換えられません

### 必須の欄(表5-2)

| 欄 | 必須の範囲 | 理由 |
| --- | --- | --- |
| 識別子 | 必須 | 席の責任者・記名の欄からの参照 |
| 氏名 | 必須 | 記名の自然人の照合 |
| 体制の内外 | 必須 | 外部の確認者・任命権者を人数から除く(第8章 L156) |
| リポジトリ上のアカウント | 必須(G-6 を適用する体制、または外部の確認者を置く体制) | 承認を名簿の人へ対応づける(G-6 の4条件) |
| 所属 | 必須(10名以上の体制) | 10名以上の規則の判定(IMPL-0084・0085) |

- 担う席(責任者 / 担い手)は表5-1 から導けるため、表5-2 に重ねて書かない
- `nameConfirmed`・`accountsConfirmed`・`appointer` は準拠テンプレートの実装の欄であり、標準の必須欄にしない(テンプレートの様式は標準の部分集合ではなく、実装を足すことは妨げない)

### 文の案(テンプレ0)

> 表5 は、席と責任者(表5-1)と、人の名簿(表5-2)で構成します。人の名簿には、席の責任者と、席の責任者でない担い手(人)と、外部の確認者を記入します。AI の担い手は記入しません。体制の人数は、表5-2 の体制の内の人で数えます。

- 表5-2 に載らない人が行った承認・記名は、独立した人の確認に数えない
- 表5-2 の記載が正しいかは、プロセス内部監査で確かめる(ADR-0065 L71 のとおり)

`template-fields.yaml` のテンプレ0 の必須欄へ、表5-2 の識別子・氏名・体制の内外を足す(両方向の検査が働く)。

### IMPL-0278

注記の「回答と名簿の人数の食い違いを検出しない」は、`headcountProblems`(`config.mjs` L773-805)と、それを拒否に使う2か所 [自確] と合いません。**注記を改め、状態を見直します**。残る未達は「人数の正本を名簿とし、回答を初期化の見込みに留める」ことのうち、回答を入力として受け続けている点だけです。状態を delivered にするか、残る点を注記して undelivered を保つかは、実装を読む委員の確認を待ちます。

### 既存の ADR・条項との矛盾

- ADR-0065 決定5「表5(人の名簿と席)」と整合する(名に中身を合わせる)。A-3 の決定(名簿と席から導く)とも整合する
- テンプレートの D-0 節1 は既に名簿を持つため、矛盾しない。`README.md` L159 の欄の説明の欠け(`team`・`accountsConfirmed`)は別に直す

## P-5 表の記号の語彙

### 結論

**3.5 の表の記号を 1.7.3 の語彙へ置き換えます。語彙は足しません**。○ は「許容」、△ は P-1・P-6 の結論に従って「許容(条件)」と書きます。準拠テンプレートの D-0 節2 の「可」「不可」「5名未満のみ可」「小規模のみ可」も同じ語へ揃えます。

### 理由

- 1.7.3 は表の升の語を限り、限定は括弧に書くと定めています [自確: `overview.md` 1.7・1.7.3]。△ は「避けたい」の強さが 1.7.1 の推奨しない・禁止のどちらか決まらず、5〜9名の食い違い(P-1)を生んだ原因そのものです
- 語彙を足すと、「避けたい」が要求か推奨かを新たに定義する必要があり、既存の6語で表せない強さは無いからです
- テンプレートの様式は、利用者が最初に読む表です。標準と別の語で書くと、P-1 のような食い違いがまた様式から生じます

### 他の案を落とす理由

- 1.7.3 に △・○ を足す: 強さの定義が「非推奨」「許容」と重なる語を2つ増やすだけになる
- 表の外の注記で読み替える: 「同じ事項の規定は1か所に書く」(1.7)に反する

### 文の案

- 価値責任者 × 文脈オーナー / 技術判断者 × 開発者 / 技術判断者 × AI維持管理者: 「許容」
- 価値責任者 × 技術判断者: 「許容(兼務を D-0 体制図へ記録し、G-3 の判定記録を兼務者以外の人が確かめる)」(P-1)
- 事業決裁者 × 価値責任者: 「許容(兼務を D-0 体制図へ記録する)」(P-6)
- 3.5.1 の条件1 の「△(避けたい)」は、P-2 の文の案のとおり「許容に条件が付く組み合わせ」と改める

### 既存の ADR・条項との矛盾

- ADR-0037 L64 の「△(避けたい)」は書き換えない。P-2 の新 ADR に「ADR-0037 の△は、本 ADR 以降の許容(条件つき)と読む」旨の読み替えを1行置く
