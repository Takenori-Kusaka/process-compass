## #290(本 Issue)

引き継ぐ論点:
- #267 の残り: 装置(検査・ゲート・ルール)の総量の上限と、減らす判断を誰が行うか
- #270: 装置修理 PR の比率の定義、「ルール化の進み」の片側の警戒サイン
- #269 の残り: 附属書B のチェックリストに escape clause を置くか

受入条件:
- 装置の総量の上限または観測の形が第6章・第7章で決まっている(置かない場合はその理由)
- 附属書B の escape clause の採否が記録されている

**議長の注記**: #290 本文は escape clause を「当てはまらない項目を外す規定」と書くが、#269 の突合コメントが引く INCOSE R8/R9(FND-0243)の escape clause は、要求文の中の逃げ道の句(「可能な限り」「必要に応じて」等)を避ける規則であり、意味が異なる。#269 本文の提案は「基準が言い訳に転用されるパターンまで書く(Pre-PMF だから、が未完成の言い訳に読み替えられた)」。どの意味で採否を決めるかを、調査と会議体で確かめる。

## #267(閉) 一人が 5 ロールを 7 か月運用して解けなかった 4 点と「80 点で止める」

起票の要旨(実証案件 がんばりクエスト、1 名と Claude Code、7 か月): オーナーが「すべてのブロッカーを機械で入れることは不可能。機械的な打ち手は、その打ち手を守る打ち手を呼び、無限ループになる。80 点を目標値とし、残り 20 点を詰めるための装置は持たない」と、装置の追加を凍結した。直近 14 日の Issue の 56% が装置・プロセス起因、顧客に届く変更は 24%。検査スクリプト 61 本。バックアップの沈黙を防ぐ検査が本番を 3.5 時間止めた。提案: 「ゲートを増やす上限」と「上限に達したときに誰が減らすか(Platform ロール)」を第8章か第6章の警戒サインに。「装置の総数は ratchet で増やせない。置換・統合は増加に当たらない」まで明確化が要った。

突合の結果(一部): 採った形 = ADR-0056 決定10「論証のどの主張も支えない検査・記録は、改善サイクルで廃止の候補に挙げる。統制を外すときは理由を記録する。論証のために新しいゲートと検査を足さない」(附属書H H.3 末尾、ADR-0057 で維持)。保証の開示の「項目は増やさない」、第4章「判定基準の表の行は増やさない」。運用メトリクスの指標の総数上限(上限到達で新指標を採るなら 1 つ廃止、2 期連続で次の一手へ接続しなかった指標は廃止候補)。**ただし検査装置(CI の検査本数)の上限ではない**。「ゲートを増やす上限」の数値、「上限で誰が減らすか」の席、装置起因の変更比率の警戒サインは、標準に無く、採らないと決めた記録も無い。Platform に当たるのは AI維持管理者(3.11、`state:needs-platform`)で、強制層の変更を承認する権限はあるが、減らす責務は書かれていない。逆向きに、メトリクス「ルール化の進み … ゼロが続く(ゲートが成長していない)」の警戒サインがある。実測注記: 「装置 0.76 倍」は再計測で再現せず(FND-0229)、PR の 55〜65% が装置起因と検査スクリプト 61 本は確認(FND-0230)。凍結後、検査スクリプトは 61→47 本(FND-0196)。

## #270(閉) 品質ゲートを強化し続けたら装置が製品の 0.76 倍、PR の 60% が装置修理、装置が顧客を止めた

起票の要旨: 検証装置 51,607 行 / 製品 67,687 行(0.76)、検査スクリプト 63 本(10 本未参照)、直近 20 PR の 12 本が装置自身の修理、open Issue の 10% が「同 class N 例目」の装置修理、19 PR を merge して open Issue が 140→144(1 PR ≈ 1 follow-up、真の不具合は 5%)。3 つの読み: 生成AI の費用構造(足すのが安すぎる)/ 1 事故 1 装置の設計方針 / 人間の仕組みの移植(AI は埋めることに最適化し、守る動機が無い)。実証案件は 3 の比重が大きいとし、「守らなくてよい形にする(生成する・消す)」が効いた。提案: 第6章の警戒サインに装置比率と装置修理 PR の割合(閾値は目標にせず、上がり続けたら減らす判断の契機)。第8章に「人間向けの装置を AI に課すとき、生成か削除を先に検討する」。

突合の結果(一部): 歯止めの骨格は ADR-0056 決定10、G-5「判定基準は 8 つのまま」、3.11.4 要求事項3(削除と統合の権限を AI維持管理者 1 名へ集約)・4・6、Label Mailbox `state:needs-platform`(テスト装置・リント・CI/CD 等の削減・自動生成・統合を AI維持管理者へ)、3.11.3「遵守が必須の規則を誘導層に書いてはならない」、ADR-0050、PR 運用「必須欄をすべて手で書かせない」「該当なしを書かせない」。**装置比率は採らなかった**(定義により同時点の値が 0.35〜1.36 に動き 0.76 は再現しない FND-0229・0262。第6章「閾値を目標にしない」「実績を基準へ機械的に変換しない」の前提が崩れる)。「直近 20 PR の 60% が装置修理」はおおむね再現(FND-0230)。残る論点: 「ルール化の進み」の警戒サインが片側だけ(増え続ける側が無い)。CI/CD ゲートの「同種の指摘が 3 回でルール化」も足す方向にしか働かない。定義を固定した「PR に占める装置修理の割合」を置くか。

## #269(閉) 受入基準とチェックリストを厳格にするほど AI は微差の修正へ向かった

起票の要旨: 完了の定義を 3 段階で厳しくした(close → AC 検証マップ → 主張と実体の一致を独立した機械検証で)。副作用: 体裁検査が統合 PR を 4 日止めた(実体は 60 件中 57 件緑)、ルールとコンテキストの過多(常時ロード 16 万バイト)、hard-fail の「残 NG 0 件」が嘘の 0 件宣言を誘う。落ち着いた線引き: 機械が hard-fail で守るのは「主張と実体の一致」だけ、体裁は警告、正直に書ける逃げ道(残 NG > 0 は追跡 Issue 付きの受容宣言で通す)。提案: 第4章に「機械判定は真正性に限定」、**附属書B(EARS)に「基準が言い訳に転用されるパターンまで書く」(「Pre-PMF だから」が未完成の言い訳に読み替えられ、禁止節を足した)**、ゲートの総量の上限。

突合の結果(一部): 線引きは 5.7.4・CI/CD ゲート構成・pr-rules で成立。逃げ道は ADR-0028・G-5「対象なし」・G-7・7.3。残る論点: 附属書B に「基準が言い訳に転用されるパターン」(escape clause)の記述が無い。INCOSE R8/R9 の先例(FND-0243)。ゲートの総量の上限は #270 と同じ論点。

## #289 から送られた論点(research/289-deliberation/decision.md D-12・D-13・D-15)

- #275 原則5「判断基準には、基準が言い訳に転用されるパターンまで書く」(既存: プロセス内部監査「開示が免罪符になることへの歯止め」、G-7「受容の対象は開示された事実」、テンプレ10「注意して進める は認めない」、5.7.5 が個別にある。横断の要求は無い)。#269 の附属書B の提案と同じ問い

- #289 D-13(ADR-0073): 是正の起動に検査装置の不具合を含め、対策は「足す・直す・外す」から選ぶ。総量の上限は #290 で決めると書いた
- テンプレートに `rule-candidate` ラベルと「ルール化の進み」の集計が実装されていない(#289 の調査・反映で判明)

## 既に決まっていること(蒸し返さない。覆すなら材料を示す)

- 装置比率(検証装置行数 / 製品行数)は定義が安定しないため指標として採らない(FND-0262、突合 #270)
- ADR-0056 決定10(論証を支えない検査は廃止の候補。論証のために新しいゲートと検査を足さない)
- 運用メトリクスの指標の総数上限と廃止の規則
- 件数を起動条件にした昇格の義務は課さない(ADR-0073)
- 採用済み ADR の本文は書き換えない
