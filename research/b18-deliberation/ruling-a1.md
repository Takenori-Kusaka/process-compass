## 2. 共通の裁定

### 2.1 試験の結線と `gate-g5.yml`

- `check=machine` の要件3(試験が集約 `gate-g5` のジョブの `run:` から実行される)のため、**既に結線された試験のファイルへ場面を足すことを第一にする**。使うもの: `test-check-pr.mjs`・`test-brief-estimates.mjs`・`test-check-delegation.mjs`・`test-cl-judgment.mjs`・`test-model-adoption.mjs`・`test-recalibration.mjs`・`test-adoption.mjs`・`test-next-records.mjs`・`test-reach-forecast-record.mjs`・`test-roster-ids.mjs`・`test-guard-bash.mjs`(どれも `gate-g5.yml` の gate-contract のジョブにある)
- 新しい試験のファイル(`test-review-queue.mjs`・`test-flow-observation.mjs`・`test-pre-review.mjs`・`test-run-record.mjs`)は、`gate-g5.yml` の gate-contract のジョブへ `run:` の行を1行ずつ足して結線する。**この行の追加は、後回しの理由(0931・0191 が変える G-5 の起動と段の構成)に当たらない**と裁定する。B15 の差分(`../b15/template`、origin/main との比較)に `gate-g5.yml` は無いことを確かめた。ただし template で並行する担当(#328)がいるため、結線は単位の最後のコミットに分け、rebase の衝突をそこに限る
- 結線した行には `|| true`・`if:`・`continue-on-error` を付けない(`implementation-marking.md` の要件3)

### 2.2 新しい workflow と必須チェックの関係

- 新しく足す workflow は `review-queue-control.yml`・`flow-observation.yml`・`pre-review.yml` の3つ。**どれも必須チェックにしない**。ルールセット(`.github/rulesets/*.json`)の `required_status_checks` は `gate-g5` と `gate-g5-base` だけのまま変えない。必須にするかは 0214 と同じ重の審議に属する
- ジョブに `gate-g5` の名を付けない(`push-trigger.mjs` の `pushTriggerProblems` が、ほかのワークフローの `gate-g5` の名のジョブを落とす。ADR-0123)
- 契機は `schedule` と `workflow_dispatch` を基本にする(定義と検査のスクリプトを既定ブランチから読むため)。PR の事象で即時に動かすものは `pull_request_target` とし、**PR の先頭を checkout しない**(変更のファイルの一覧は API で読む)。`pull_request` と `pull_request_review` は使わない(`delegation.yml` 45 行と同じ理由)
- 権限は要るものだけ: `contents: read`、`pull-requests: write`(レビュー依頼の宛先を読む・コメントする)、`issues: write`(Issue へのコメント)
- `scripts/gate/preflight.mjs` の `TEMPLATE_WORKFLOWS`(41 行)へ3つを足す。足さないと、導入前の点検が既存の CI のワークフローとして一覧に載せる。Node の版の固定(`.github/gate-node-version`)を各 workflow に使う(`test-gate-node.mjs` が見る範囲を実装の段で確かめる)
- 通知は GitHub の上のコメントと記名(`@login`)に限る。GitHub の外への通知の経路は採用者の任意(#359 の裁定2 と同じ)。ADR-0175 決定2 により、通知の基盤を理由に (d) にしない(テンプレートが GitHub の上で届けられるため)

### 2.3 安全関連部の範囲の置き場(0594・0919 が使う。0766 も後で使う)

- 安全関連部の範囲は、**既存の区分の下限の規則 `riskFloor.rules[]` に `floor: "R1"` と `safetyRelated: true` を持つ規則として宣言する**。新しい構成のキーを作らない(`config.mjs` に `riskFloor` の検査は無く、B15 に触れない。`check-pr.mjs` の `riskFloorOf` は未知の属性を無視する)
- 理由: 第5章の表「安全関連部 = R1 固定・L1 固定・人確定」のうち R1 固定は、既に区分の下限の照合(IMPL-0062)で G-5 が強制する。同じ規則に印を足せば、範囲の正本が1つで済む。F.7 の記録の「安全関連部の切り分け」(様式 09)は自由な文のまま残し、構成の宣言との一致は人が確かめる(機械で閉じない)
- 採らない案: (1) 構成に `autonomy.safetyPaths` を新設する(正本が2つになり、`config.mjs` の検査を要する)。(2) F.7 の記録の範囲の欄を glob の書式に改める(様式に細かい定義が増え、記録の文と機械の値を1つの欄に混ぜる)。(3) F.2 の Q1 が「はい」の案件を全体で L1 にする(本文が「切り分けを定めずに全体を安全関連として扱うと…AI の活用が全面的に停止する」と戒めている。`human-ai-boundary.md` の表の下)

### 2.4 営業日の暦(0681・0682・0979・0210・0213・0219 が使う)

- 共有の関数を新規の `scripts/gate/business-days.mjs` に置く。土日を除く。祝日は任意のファイル `.github/business-holidays.txt`(1行に YYYY-MM-DD)から読む。無ければ土日だけを除き、**出力に「祝日を数えていない」と必ず書く**
- 日付は引数で渡し、関数は時計を読まない(`exception-expiry.mjs` と同じ。回帰の時計依存を避ける。記憶「回帰スイートの時計依存」)

### 2.5 台帳の行の印(0567・0610・0645 が使う)

- 技術負債台帳(様式 03)に**新しい区分も新しい欄も足さない**。区分を足すと、`aggregate-evidence.mjs` の `r.kind === '例外'` の5か所(B15 の範囲)の読みが変わる。欄を足すと `config.mjs` の `LEDGER_COLUMNS` を変える
- 代わりに、既存の欄の先頭に決まった語を書く:
  - ファストトラック(7.4)の行: 区分「例外」、**内容の先頭を `ファストトラック(短縮: <ゲート>)` とする**。様式 03 の節「ファストトラックの例外承認」に1行足す
  - コア機能の理解の保持者が1名以下の是正(3.4.3)の行: 区分「負債」、**対象を `コア理解: <コア機能の名前>` とする**(名前は運用引き継ぎ文書の節2 の名前と同じ文字列)
- 印の無い行は、機械が当該の種類の行として見分けられない。その事実を検査の出力と note に書く(印を書かないことが抜け道になる点の開示)。印の付け忘れを機械で捕まえることはしない(意味を読む検査になる)

### 2.6 新規 ADR

**ADR-0200 を1件起こす**(要旨)。表題の案: 「B18 第1群の降ろし方で採用者が書く記録の約束を決める」。

1. 安全関連部の範囲を `riskFloor.rules[]` の `safetyRelated: true` の R1 規則として宣言する(§2.3)。F.2 の Q1 が「はい」で宣言が無い構成は、登録した変更種別を止める(0594)
2. ファストトラックとコア理解の是正の行を、既存の欄の先頭の語で見分ける(§2.5)。区分と欄を足さない
3. 営業日は土日と任意の祝日のファイルで数え、祝日を数えていないことを開示する(§2.4)
4. 新しい観測と通知の workflow を必須チェックにしない(§2.2)。必須にするかは 0214 の重の審議に残す
5. 課さないと決めたこと: 印の付け忘れの機械の検出。安全関連部の宣言と F.7 の記録の文の一致の機械の照合

理由: どれも採用者のリポジトリに書かれる約束で、あとから変えると採用者の記録の読み方が変わる。ADR-0175 は降ろし方の4区分までで、約束の形を決めていない。番号は 0200(#328 が ADR を使わない見込み)。0201〜0209 は使わない。
