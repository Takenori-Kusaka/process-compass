### 1.2 統制の弱化の扱い

- 定義と検知者の職務境界は ADR-0038。検知者は許容可否を判断せず引き渡す。3.5.5「統制の弱化を検知したときの引き渡し」〔確〕
- 第4章 G-5「是正の起動」(`gate-criteria.md:696-719`)は「統制の弱化の検知」を起点の1つに置く。**「検査を外す変更の記録」の記名を済ませて外した縮小は起点に当たらない。記名の無い縮小は当たる**(`:719`)〔確〕
- 第4章 G-5「統制の設定の陰性の確認」(`gate-criteria.md:731-757`)
  - 統制の設定(閾値・除外設定・必須の検査・ルールセット・フック・権限と、それらを動かす検査装置)を変える変更では、変更後でも止まるべきものが止まることを確かめた結果を記録する。強める向きも対象(IMPL-0134、delivered・presence)〔確〕
  - 検査を意図して外す変更は、結果「外した」として、外した検査・止めていた場面・外した後に止めるもの・受け入れた者の4つを記録する(IMPL-0143、delivered・presence)〔確〕
  - 根拠水準: 陰性の確認の効果は測られていない(`:757`)〔確〕
- 第4章 G-5「基準値と除外設定の変更」: 閾値・除外設定を製品のコードと同じ PR で変えると pr-rules が失敗(IMPL-0202、delivered・machine)〔確〕
- 緩める向きの閾値の変更は `/process-change` と記名を要する(check-pr の注意文。`check-pr.mjs:1391`)〔確〕

## 2. 準拠テンプレートのワークフロー(`template/.github/workflows/`)

### 2.1 一覧(トリガ・checkout・スクリプトの読み元)

GitHub の挙動の前提〔外〕: `pull_request` のイベントでは、ワークフローの定義(yml)は PR のマージのコミット(`refs/pull/N/merge`)から読まれ、既定の `actions/checkout` も同じコミットを取り出す。`pull_request_target`・`workflow_run`・`schedule` は既定ブランチの定義で動く。`workflow_dispatch` は起動時に選んだ ref の定義で動く。

| ワークフロー | トリガ | checkout する ref | `scripts/gate/` の読み元 | 定義(yml)の読み元 | 必須チェックか |
| --- | --- | --- | --- | --- | --- |
| `gate-g5.yml` | `pull_request`(opened・synchronize・reopened・edited・labeled・unlabeled)、`push: main`、`workflow_dispatch` | 既定(PR ではマージのコミット)。全ジョブで ref の指定なし〔確〕 | **PR の側**(マージのコミット)〔確〕。`./.github/actions/setup-stack`・`adapters/*.json` も PR の側〔確〕 | PR の側〔外〕 | **はい**(集約ジョブ `gate-g5`) |
| `gate-entry.yml` | `pull_request`(paths: D-0・brief・`process.config.json`・`CLAUDE.md`)、`schedule`、`workflow_dispatch` | 既定(マージのコミット)〔確〕 | PR の側〔確〕 | PR の側〔外〕 | `d0-check` は safety・regulated で必須 |
| `ship-evidence.yml` の `verify` | `pull_request`(paths: `docs/records/**`・`docs/gates/**`・`docs/evidence/**`)、`workflow_dispatch`(verify_pr) | **`github.event.pull_request.base.ref`**(基底)。PR の先頭は `pull/N/head` を別に fetch〔確〕 | **基底の側**〔確〕 | **PR の側**〔外〕。ref の指定そのものを PR が書き換えられる | いいえ(どのルールセットにも無い)〔確〕 |
| `ship-evidence.yml` の `evidence` | `push: tags v*`、`workflow_dispatch` | 既定(タグ・選んだ ref) | 起動の ref | 起動の ref | — |
| `delegation.yml` | **`pull_request_target`**、`workflow_run`(G-5 の完了)、`workflow_dispatch` | **`github.event.repository.default_branch`**〔確〕 | 既定ブランチ〔確〕 | 既定ブランチ(`workflow_dispatch` を除く)〔確・外〕 | いいえ(`delegation-eligibility` は必須にしない) |
| `record-copy.yml` | `pull_request: closed`(merged のとき) | 既定〔確〕。コメントは「マージ後の基底ブランチの定義を読む」と書く(`:60`) | 同左 | **要確認**(マージで入った PR の yml が使われうる)〔推〕 | いいえ |
| `ai-review.yml` | `pull_request`(opened・synchronize・ready_for_review) | 既定(マージのコミット)〔確〕 | `process.config.json` を PR の側から読む〔確〕 | PR の側〔外〕 | いいえ(必須にしないと明記) |
| `assurance-period.yml`・`context-drift.yml` | `schedule`・`workflow_dispatch` | 既定ブランチ | 既定ブランチ | 既定ブランチ | — |

要点:

- **必須チェック `gate-g5` を出すワークフローは、定義もスクリプトも PR の側で動く**。PR が `gate-g5.yml` の集約ジョブを `exit 0` に替える、`needs` から `pr-rules` を外す、`scripts/gate/check-pr.mjs` の `CONTROL_FILES` を空にする、のいずれでも、その PR の `gate-g5` は通りうる〔推。実機未確認〕
- `pr-rules` は `--policy-base origin/<既定ブランチ>` で、**基準値・名簿・規則・台帳・停止の解除を既定ブランチから読む**(`gate-g5.yml:369-377`、`check-pr.mjs:1212-1250`)〔確〕。つまり**データは基底、コードは PR の側**という半分の構成である。#294 / ADR-0078 で入った。コードまで基底から読む形にはなっていない〔確〕
- 契約検査(`verify-gate-contract.mjs`)は、`gate-g5.yml` の集約の `needs` と `continue-on-error` の不在(IMPL-0142)、ルールセットの雛形の `required_status_checks` に `gate-g5` があること(`:818-821`)を確かめる。しかし契約検査そのものが PR の側で動く〔確〕。また読むのは**リポジトリの中の雛形の JSON**であり、実際に適用されたルールセットではない〔確〕
- `test-check-delegation.mjs:245-254` は `delegation.yml` が PR の先頭を checkout しないこと、`pull_request_target` で動くことを確かめる。この試験も `gate-g5` の中、すなわち PR の側で動く〔確〕
- `ship-evidence` の verify は「スクリプトは基底、定義は PR の側」。ADR-0109 の申し送りの通り、yml の `ref:` を `head` に替える・手順を消すことが PR の中でできる〔推〕。ただし verify は必須チェックではないので、書き換えなくても失敗のまま入れられる(#379 P-5)〔確〕
- `delegation.yml` は本テンプレートで唯一、基底から読む構成を採る。ただしヘッダーに「2026-10-01 時点で実際の GitHub 上で実行して確かめていない」とある(`:26`)〔確〕

- 全雛形で、必須チェックは `context` の名前だけ。**送り手(`integration_id`)を縛らない**〔確〕。同じ名前のステータスを、別のワークフローのジョブ名や、`statuses: write` を持つトークンからの commit status で出せる可能性がある〔外〕
- **ルールセットの `workflows` 規則(required workflows)は、どの雛形にも無い**〔確〕
- 雛形の README は「既定ブランチのルールセットに bypass actor を置かない」を決めている(`rulesets/README.md:37,97`)〔確〕
- CODEOWNERS の雛形は、強制層の行(`/.github/workflows/`・`/scripts/gate/`・`/.github/rulesets/`・`/.github/CODEOWNERS` ほか)を `@ai-maintainer` へ割り当てるが、**すべてコメントのまま**。既定は `* @OWNER` の1行(`CODEOWNERS:9,26-36`)〔確〕
- したがって、雛形のまま適用した `team`・`checks-only` の構成では、ワークフローと検査のスクリプトを書き換える PR を、AI維持管理者の承認なしに機械が止める層は無い。`safety`・`regulated` でも、CODEOWNERS の行を有効にしなければ `* @OWNER` の承認で足りる〔推〕

### 2.3 G-5(pr-rules)が検査の書き換えをどう扱うか

- 対象の判定: `CONTROL_FILES`(`check-pr.mjs:328-333`)= `.claude/settings.json`・`.claude/guard.json`・`.claude/hooks/**`・`.github/workflows/**`・`.github/rulesets/**`・`CODEOWNERS`(3か所)・`scripts/gate/**`・`scripts/vendor/**`・`adapters/**`。加えて閾値・除外設定のファイル〔確〕
- 対象外: 基底に無いファイル(初回の設定)、基底の構成が未設定、依存の更新の bot の PR(`:1398-1401`)〔確〕
- 求める記録: PR 本文の `## 統制の設定の陰性の確認`。結果「止まった」なら場面と確かめた者(AI の名義でない)。結果「外した」なら4欄と受け入れた者(AI の名義でなく、構成に AI維持管理者の席の責任者があればその人)(`negativeCheckProblems`・`removalProblems`、`:351-389`)〔確〕
- **統制の弱化の検出は無い**。check-pr は「変更が緩める向きか強める向きか」を判定しない。結果の欄を「止まった」と書けば、緩める変更でも AI維持管理者の記名は求められない〔確〕。緩める向きの判定は人(書き手の自己申告)に依る〔確〕
- **AI維持管理者の記名は、本文のテキストの欄であり、本人の操作(承認のレビュー・署名)と結び付いていない**。PR の作成者が `受け入れた者: <AI維持管理者の氏名>` と書けば通る〔確〕。ADR-0106・0109 が判定記録に求めた帰属の確認(名簿の数値の識別子との照合)は、この欄には掛かっていない〔推。突合で確かめる〕
- 所有する組織の同意の欄と照合は**無い**(IMPL-0340 の note のとおり)〔確〕
- そもそも上記の検査のコードが、検査される PR の側で動く(2.1)〔確〕

### 2.4 AI レビュー(#369 に関係する部分)

- `ai-review.yml` は `pull_request` で起動し、既定の checkout(PR の側)。レビューの実装は未設定で、コメントで「指示は基底ブランチから読む。PR 自身の変更から読んではならない。基底の指示でレビューさせる仕組みはまだない(IMPL-0333 は降りていない)」と書く(`:58-64`)〔確〕
- 有効化の判定(`aiReview.enabled`)も PR の側の `process.config.json` から読む〔確〕
- このワークフローは必須チェックではなく、合否に使わない。#369 の論点は G-5 の合否ではなく、**附属書H H.4 条件3(AI の確認を検出の層に数える条件)**の成立に掛かる〔確〕

## 5. 案ごとの整合

評価の軸: (i) 同じ PR の書き換えで `gate-g5` を通せなくなるか、(ii) 同意の記録(IMPL-0340)を機械で確かめられるか、(iii) 既存の ADR・規定との整合、(iv) 安全上の注意、(v) 体制・プランへの依存。

### 5.1 案(a) 基底の側の検査を `pull_request_target`(または `workflow_run`)で走らせる

- 何を基底で走らせるかが要点。**G-5 の全体を基底へ移すことはできない**。基準1(テスト)・基準3(カバレッジ)・静的解析は、PR の製品コードを実行することが目的だから〔確〕
- 現実的な分割(先例は `delegation.yml`)
  - 基底で走らせる: PR のコードを**実行しない**検査。pr-rules(差分のパス・本文・API のデータを読むだけ)、契約検査、陰性の確認の照合、CONTROL_FILES の変更の検出、AI維持管理者・所有する組織の承認の照合
  - PR の側で走らせる(`pull_request`、権限は read): テスト・カバレッジ・静的解析・秘密情報の走査
  - 集約: `workflow_run`(既定ブランチの定義)で PR 側の結果を読み、基底の判定と合わせて必須チェックを出す。PR 側の結果と成果物は**信頼しないデータ**として扱う。PR が CONTROL_FILES を変えた場合、PR 側の結果は書き換えた定義で作られたものと読む
- 整合
  - 第5章 5.5.4 の委任の経路の要求事項2「判定のコードと構成は基底ブランチから読む」、第4章 G-8 の「書き換えられる場所の中だけに置かない」と同じ論理で、適用漏れを塞ぐ形になる〔確〕
  - pr-rules は既にデータを `--policy-base` から読む(ADR-0078)。コードの読み元をそれに揃える変更になる〔確〕
  - ADR-0109(記録の置き場は防止でなく検出)とは対象が違う(記録 vs 判定のコード)。防止へ寄せるなら、なぜ G-5 は防止かの理由が要る〔推〕
- 安全上の注意〔外。外部調査で裏づけを要する〕
  - `pull_request_target` は既定ブランチの文脈で、書き込みの権限を持つ `GITHUB_TOKEN` と秘密情報に届く。**PR の先頭を checkout して実行すると、任意のコードの実行になる**(いわゆる pwn request)。テスト・依存の導入・アダプタのコマンド・`./.github/actions/setup-stack` を PR の側から実行してはならない
  - PR の題名・本文・ブランチ名をシェルへ式展開しない(スクリプトの注入)。`delegation.yml` には試験がある(`test-check-delegation.mjs:248`)〔確〕。`gate-g5.yml` の pr-rules は `PR_TITLE`・`PR_BODY` を `env:` で渡しており、式展開ではない〔確〕
  - check-pr は PR の先頭のファイルを**データとして**読む(`atHead('process.config.json')`・`docs/debt-ledger.md`、`check-pr.mjs:1238,1319`)〔確〕。`import` や実行はしていない〔推〕。基底へ移すときは、この「読むだけ」を試験で固定する必要がある
  - フォークからの PR でも `pull_request_target` は秘密情報に届く。採用者が公開リポジトリでフォークを受ける場合の扱いが要る
  - `permissions` をジョブ単位で最小にする(ADR-0090 の影響に残る「workflows の最小権限」と重なる)〔確〕
  - `workflow_run` で PR 側の成果物を読むとき、成果物は PR が作れる。ファイル名・パスの検証と、展開先の隔離が要る
- **送り手の問題が残る**: 基底の判定が `GITHUB_TOKEN` で出すステータス・チェックは、PR の側のワークフローが同じ名前で出すものと送り手(GitHub Actions の App)が同じになる〔推〕。**`integration_id` を GitHub Actions に固定しても、PR が足したワークフローの同名のジョブとは区別できない**〔推。要実機〕。区別するには、判定だけが持つ資格情報(既定ブランチに限った Environment に置いた専用の GitHub App の鍵など。ADR-0090 の (a) の形)でステータスを出し、ルールセットの `integration_id` をその App に固定する必要がある〔推〕
- 体制への依存: 小さい。`pull_request_target` はどのプランでも使える〔外〕。App を作る形は採用者の準備が増える

### 5.2 案(b) 検査の書き換えを含む PR を、別の必須の承認で止める

- 形の候補
  - (b1) CODEOWNERS の強制層の行を有効にし、ルールセットで `require_code_owner_review: true` にする。いまの雛形は行がコメントで、`team.json` は false〔確〕
  - (b2) ルールセットの `pull_request` 規則のパス単位の必須レビュアー(`required_reviewers`)で、`.github/workflows/**`・`scripts/gate/**` などに AI維持管理者のチームの承認を課す〔外〕。雛形の README が既定にしないと決めたのは「承認の件数を 0 にしてパスで足し戻す構成」(`rulesets/README.md:97`)であり、件数を残したままパスで足す形はこれに当たらない〔推〕
  - (b3) 基底で走る照合(案(a) の一部)が、CONTROL_FILES を変える PR に、名簿の AI維持管理者の数値の識別子(ADR-0108)による承認のレビューを求める
- 整合
  - 3.11.2 の「強制層の変更は AI維持管理者が承認する」を、本文の欄(自己申告)から**本人の操作**へ移す。ADR-0106 の「効力を持つ前に記名者本人の操作で帰属を裏づける」と同じ向き〔推〕。ただし陰性の確認・「外した」の記録は、効力を持つ記録の閉じた列挙(`overview.md:107`)に**入っていない**〔確〕。入れるなら列挙を広げる(厳しくする向きの)判断が要る
  - ADR-0087 は CODEOWNERS の行を「コメントのまま置く。有効にする道具の側の扱いは #358 と重なる」とした(`:80`)〔確〕。(b1) は #358 の範囲と当たる
  - CODEOWNERS 自身の書き換え: コード所有者の判定は PR の基底の側の CODEOWNERS で行われる〔外。要確認〕。そうなら PR が所有者の行を消しても、その PR には効かない
- **同意の記録(IMPL-0340)との接点**: 強制層を所有する組織は、軸D の定義上「リポジトリと CI の管理権限を持つ側」であり、ルールセットを設定できる。所有する組織が強制層のパスに自組織の指名者の必須レビューを置けば、「事前の同意」を、**構成に席の組織を持たせないまま**機械で強制できる〔推〕。IMPL-0340 が未達である理由(構成が席の組織を持たない、ADR-0069 決定2)を迂回できる可能性がある
  - ただし標準が同意を求めるのは**緩める向き**だけ。ルールセットは向きを判定できないため、全変更に同意を課すことになる(標準より厳しい)。向きの判定を人に残すか、全変更に課すことを許すかは会議体の論点〔推〕
  - 「事後の提出」を選んだ組織には、この形は当たらない
- 安全上の注意: 承認の後の push で承認を失効させる(`dismiss_stale_reviews_on_push`・`require_last_push_approval`。雛形は true)〔確〕。管理者の bypass は残る(ADR-0109 の開示)〔確〕
- 体制への依存: **大きい**。1名の体制では、作成者と AI維持管理者が同一で、GitHub は作成者の承認を数えない〔外〕。2名の体制では、もう1人が AI維持管理者を兼ねる必要がある。席の兼務の規則(ADR-0082)、1名の体制の行(第4章 G-5、IMPL-0238)との突合が要る〔推〕
- (b) だけでは、`gate-g5` を書き換えた PR が「通過」と表示される状態が残る。承認者は表示を信じずに差分を見る必要がある。承認の判断材料として、基底の側の判定(案(a)・(f))の有無が効く〔推〕

### 5.3 案(c) ルールセットの required workflows(`workflows` 規則)を使う

- 組織のルールセットで、別のリポジトリ(固定した ref・SHA)のワークフローをマージの前に必須にする機能〔外〕。定義が対象のリポジトリの外にあるため、PR は定義を書き換えられない〔外〕。必須の扱いは名前でなくルールセット自体が持つため、同名のジョブによる偽装の論点が生じにくい〔推。要確認〕
- 整合
  - ADR-0087 の「強制層を所有する組織」が組織のルールセットを持つ形と合う。委託で、所有する組織の側に統制を置ける〔推〕
  - 第4章 G-8 の規定(書き換えられる場所の中だけに置かない)の G-5 版として、最も直接の手段になる〔推〕
- 注意
  - 定義が外にあっても、既定の checkout は PR のコードを取り出す〔外〕。**`scripts/gate/**` を PR の側から実行すれば問題は残る**。ワークフローの中で基底を checkout するか、検査のスクリプトもワークフローのリポジトリへ置く必要がある〔推〕
  - 起動のイベント(`pull_request`・`pull_request_target`・`merge_group` のどれで動くか)と、それに伴う権限・秘密情報の扱いは要確認〔外〕
  - 準拠テンプレートは単一のリポジトリの雛形。中央のワークフローのリポジトリを要する構成は、テンプレートの形を変える〔確〕
- 体制・プランへの依存: **大きい**。組織のルールセットは組織のアカウントとプランを要する。個人のアカウントのリポジトリでは使えない可能性が高い〔外〕。ADR-0090 の未達の区分(手段が無い / 手段はあるが使わないと決めた)で扱う先例がある〔確〕。標準は特定の製品の機能を指定しない書き方を採っている(5.8.6「拒否の実装の手段は指定しません」など)。要求は性質で書き、機能は例示に留めるのが既存の書き方である〔確〕

### 5.4 案(d) 開示で足りる

- 形: 同じ PR で検査を書き換えられることを、保証の開示(附属書H の項目1・4)と env-check の所見に固定の文で出す。ADR-0109(書き込みの主体を限れないことの開示)と同じ形〔確〕
- 整合
  - ADR-0109 は記録の置き場で「防止を課さず、検出と開示」を採った。同じ立場を強制層へ広げる形で、既存の決定と最も衝突が少ない〔確〕
  - ただし ADR-0109 の検出は「書き換えは G-7 の集約で欠落になる」に支えられている。G-5 の書き換えを G-7 で検出する仕組みは**まだ無い**〔確〕。ADR-0109 自身が「開示は決定1〜4 と組で採る。開示だけでは数え方が変わらない」と書いた(決定 `:71`)〔確〕
  - 3.11.3「遵守が必須の規則を誘導層に書いてはならない」。必須チェックが自分の定義を守れないなら、強制層の看板と実態が食い違う。開示だけで済ませると、附属書H H.9 問15 と軸D の「強制層の所有」の記録が名目になる(#317 の A2 の指摘そのもの)〔推〕
- 安全上の注意: 新しい攻撃面を作らない
- 体制への依存: 無い

### 5.5 そのほかの案

- (e) **G-7 の事後の検出**: 出荷の証跡の集約が、範囲内で CONTROL_FILES を変えた PR を数え上げ、AI維持管理者(と、所属が異なる場合は所有する組織の指名者)の**承認のレビュー**が名簿の識別子で付いているかを照合し、欠ければ欠落にする。ADR-0109 の「検出で扱う」と組になる〔推〕
  - 注意: 集約(`aggregate-evidence.mjs`)も `scripts/gate/` にあり、タグの時点の定義で動く。検査を緩める PR が集約も緩めていれば、検出は外れる〔推〕。集約を前回の出荷の版で動かすか、CONTROL_FILES の差分そのものを開示に出す必要がある
  - 承認のレビューは record-copy が写しを records へ置く(ADR-0070・0109)。照合の材料は既にある〔確〕
- (f) **基底の側で「書き換えの検出」だけを置く**: `pull_request_target` で、PR のコードを checkout せずに API で差分のパスだけを読み、CONTROL_FILES に触れる PR に必須でないステータスと PR へのコメント(「この PR の gate-g5 は書き換えた定義で動いている」)を出す。PR のコードを一切実行しないので攻撃面が最小〔推〕。止めないが、案(b) の承認者の判断材料になり、記録に残る
- (g) **push のルールセットのパスの制限**: `.github/workflows/**`・`scripts/gate/**` への push を、AI維持管理者(bypass)以外に禁じる〔外〕。最も強い防止だが、プランへの依存、bypass actor を置かない雛形の決定(`rulesets/README.md:37,97`)との衝突、1名の体制での運用が論点〔確・推〕
- (h) **マージのキュー**: 必須チェックを `merge_group` で合成コミットに掛ける。定義は合成コミット(PR の変更を含む)から読まれるので、本件は解けない〔外・推〕。採らない候補として記録する価値がある
- (i) **検査のスクリプトを固定した版から読む**: `scripts/gate/` を PR の作業ツリーでなく、標準の配布(`dist/standard`)のタグや知識ベースの版から取り出して動かす。yml は PR の側に残るため、単独では効かない〔推〕

### 5.6 同意の記録(IMPL-0340)を「この検査で確かめるか」の材料

- 機械で確かめる前提が欠けている点〔確〕
  - 構成は席の組織を持たない(ADR-0069 決定2)。同意が要る(所属が異なる)かを機械は知らない
  - 事前の同意の**置き場**が様式で固定されていない(#317 突合 `crosscheck.md:54,58`)。事後の提出の置き場はテンプレ8 第9項に書かせる
  - 緩める向きかを機械は判定しない(2.3)
- 案ごとの届き方
  - (a)・(b3)・(e): 置き場(PR 本文の欄、または承認のレビュー)と指名者のアカウントを決めれば照合はできる。適用の有無は、テンプレ8 の記録を構成へ写すか、所有する組織の指名者を名簿に載せる必要がある。ADR-0087 は判定の結果を受け取る者について「構成へ写さない」を採った(description)。同じ方針との突合が要る〔推〕
  - (b2)・(c): 所有する組織がルールセットで強制するなら、構成に組織を持たせずに済む。向きは判定しない〔推〕
  - (d): 確かめない。IMPL-0340 は undelivered のまま、計画を別の形(`plan=adopter` など)へ移すかの判断になる〔推〕
- G-5 の検査が PR の側で動く限り、同意の照合を pr-rules へ足しても、同じ PR で照合を外せる。**同意の照合を降ろす前提として、検査の読み元の論点を先に決める必要がある**〔推〕。Issue の「決めること」の1番目と2番目は独立ではない

## 7. 突合の材料(会議体へ渡す)

- **IMPL 番号の誤記**: Issue の IMPL-0334 は IMPL-0340 の誤り。ADR-0086 は ADR-0087 の誤り(0 節)。受け入れ条件の候補「`issue=` の付け替え」は済んでいる
- **先例との不揃い**: 「判定のコードと構成を基底から読む」は委任の経路(5.5.4)と配備(G-8)で要求事項・禁止になっているが、G-5 には無い。会議体は「G-5 に同じ規定を置く」か「G-5 は置かないと決めて理由を書く」かのどちらかを明記する必要がある(却下も成果として書く)
- **データとコードの読み元の分裂**: pr-rules は基準値・名簿・台帳を既定ブランチから読む(ADR-0078)のに、そのコードは PR の側で動く。ADR-0078 の時点で、コードの読み元を論じた記録があるかは未確認(本調査の範囲外)
- **AI維持管理者の記名の強さ**: 「外した」の「受け入れた者」は本文のテキストの欄で、本人の操作と結び付かない。ADR-0106 の効力を持つ記録の閉じた列挙に入っていない。3.11.2 の承認権限との関係で、列挙へ足すか、帰属の確認を課さない理由を書くかが論点
- **緩める向きの判定**: 標準(3.11.2・軸D)は同意を「緩める向き」に限るが、機械は向きを判定しない。機械で確かめる形を採るなら、向きに依らず課すか、向きを人の申告に残すかを決める
- **ADR-0109 との立場の一貫性**: 記録の置き場は「防止でなく検出」。G-5 の検査装置で防止を採るなら、その違いの理由(判定の前に効く/後に効く。ADR-0106 の「事前に効く読み手」の区分が手掛かり)を書く
- **CODEOWNERS の雛形(#358)**: 案(b1) は #358 の範囲と重なる。ADR-0087 は行をコメントのまま置いた
- **体制ごとの成立**: 1名・2名の体制で、AI維持管理者の承認を機械で強制する形は自己承認の問題に当たる。第4章 G-5 の1名の行(IMPL-0238)、ADR-0082 の兼務の境界との突合が要る
- **#369 との分担**: AI レビューの指示(データ)と G-5 の判定(実行されるコード)は機構が違う。ただし #369 の yml も `pull_request` で動く限り同じ穴を持つ(4.1)

## 8. 要約

- G-5 の必須チェック `gate-g5` は、定義(yml)も検査のスクリプトも PR の側で動く。同じ PR で両方を書き換えれば、その PR の判定を通せる可能性が高い(コードで確認、実機は未確認)
- 必須チェックは名前(`context`)だけで送り手を縛らず、ルールセットの雛形に required workflows も無い。CODEOWNERS の強制層の行はコメントのままで、`team` の構成ではコード所有者のレビューも課さない
- pr-rules は統制の設定の変更に陰性の確認を求めるが、緩める向きを判定せず、AI維持管理者の記名は本文のテキストで、本人の操作と結び付かない。同意の記録(IMPL-0340。Issue の IMPL-0334 は誤り)の照合は無い
- 「判定のコードを基底から読む」は委任の経路(`delegation.yml`、`pull_request_target`)と G-8 で既に規定されている。G-5 には無い。案(a) は先例と揃うが、PR のコードを実行しない範囲に限る必要と、送り手の同一性の問題が残る。案(b)・(c) は体制とプランへの依存が大きい。案(d) は ADR-0109 と揃うが、G-7 の検出が無いと開示だけになる
- 同意の照合は、検査の読み元を決めた後でないと同じ PR で外せる。#369 は指示というデータの読み元で機構が違うが、yml が PR の側である限り同じ穴を持つ
