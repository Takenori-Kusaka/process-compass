## R-1 検査の読み元

### 推す案

**(a) を要求事項として置き、(b) を組にする。(e) を事後の検出として足す。(c) は手段の例示に留め、要求しない。**

1. G-5 の判定のうち、**PR のコードを実行しない部分**(pr-rules、契約検査、陰性の確認の照合、`CONTROL_FILES` の変更の検出、承認の照合)は、判定のコードと定義を基底(既定ブランチ)から読み、変更の側が書き換えられない文脈で動かすことを要求事項にする。書き方は製品の機能でなく性質で書く(「判定のコードと定義を、判定される変更が書き換えられない場所から読む」)。`pull_request_target`・`workflow_run` は準拠テンプレートの実装の例とする
2. PR のコードを実行せざるを得ない部分(テスト・カバレッジ・静的解析)は基底へ移せない(内部 `:180`)。この部分は (b)「`CONTROL_FILES` に触れる変更は、push した者と別の者の承認を要する」で統制する
3. (e) 出荷の集約で、範囲内の `CONTROL_FILES` を変えた PR と承認の有無を数え上げる。ただし集約のコードは前回の出荷の版(または基底の版)で動かすことを条件とする(内部 `:241`)

### 理由(所在つき)

- **規格の要求から直接導ける**
  - SP 800-204D 5 の前提: "the driver tools or build control plane execute at a higher level of trust than the individual functional steps"(外部 `:206`)。判定(制御面)を、判定される変更(個々のステップ)と同じ信頼水準、すなわち変更の側で動かしている現状は、この前提に反する
  - SP 800-204D 5.1.1: 証拠は "signed by a trusted component of the build framework that is not under the control of the developers"、"a process with a higher level of trust or isolation than the build itself"(外部 `:207`)。必須チェック `gate-g5` の成功は G-5 の証拠である。PR の作者が定義を書き換えられる構成は "under the control of the developers" に当たる
  - SP 800-204D 3.1.5 は「検査が CI の中で迂回されうる」ことを信頼喪失の原因に挙げる(外部 `:205`)。本件はその具体の型である
  - SSDF PS.1.1 は configuration-as-code を保護対象の「コード」に含め、Example 4 で code owner のレビューを挙げる(外部 `:194-195`)。PO.3.2 Example 3 は pipelines-as-code を求める(外部 `:190`)。パイプラインがコードである以上、PS.1 の「意図した安全の性質を迂回する無許可の変更」(外部 `:193`)の防止の対象になる
  - SLSA Source L3 は技術的統制の継続的な強制の証拠を求める(外部 `:133,135`)。PR が自分の検査を外せる構成では、G-5 という統制の継続を主張できない(外部 `:139` の解釈。SLSA の原文は CI の定義を名指ししない。この点は解釈である)
- **業界の実務は一様に「定義を変更の側の外に置く」型を採る**
  - Prow の既定はジョブの定義を中央の `infra-config` に置く(外部 `:153`)。inrepoconfig を許すと危険が増えることを KEP 自身が書く(外部 `:155`)
  - GitHub ruleset workflows は別のリポジトリの ref・SHA から定義を読む(外部 `:58,67,73`)
  - GitLab pipeline execution policy は security policy project に定義を置き、プロジェクトが上書き・スキップできない(外部 `:168-171`)
  - 3つの製品は実装が違うが、性質は同じである。性質の側を要求にすれば、製品・プランに依らない規定になる
- **本標準の既存の規定との整合**
  - 委任の経路は「判定の規則と構成は基底ブランチから読む」(第5章 5.5.4、IMPL-0026 `human-ai-boundary.md:462`)。配備は「起動元のブランチで書き換えられる場所の中だけに置いてはならない」(`gate-criteria.md:1521`)。G-5 だけが規定を欠く(内部 `:54,282`)。同じ論理の適用漏れであり、G-5 だけ外す理由は見当たらない
  - pr-rules は既にデータ(基準値・名簿・台帳)を既定ブランチから読む(`template/.github/workflows/gate-g5.yml:369-377`、ADR-0078)。コードだけが PR の側にある分裂は、データの読み元を固定した目的(下の層の基準値で判定しない)を、コードの書き換えで外せる状態にしている
- **(b) を組にする理由**: (a) は層 B のうちテストの部分を塞がない(R-2)。この残りを塞ぐ型として、規格と実務は「自己承認を許さない別人の承認」を一致して挙げる
  - SP 800-204D 5.1.2 "Developers with “merge approval” permissions cannot approve their own merges."(外部 `:208`)
  - SSDF PS.1.1 Example 4 "Have the code owner review and approve all changes made to the code by others."(外部 `:195`)
  - OpenSSF SCM Best Practices "Repository Should Not Allow Committer Approvals" / "Default Branch Should Require New Code Changes After Approval To Be Re-Approved"(外部 `:145`)
  - Scorecard Branch-Protection の Tier 2・4・5(最新の push の承認、code owner のレビュー、古い承認の取り消し)(外部 `:118-121`)
  - SLSA Source L4 二者レビューと、レビュー中の追加変更のレビュー(外部 `:136`)
- **(e) を足す理由**: SSDF PO.3.2 Example 6「ツールとログを監視し、方針違反と異常な挙動を検出する」(外部 `:190`)、PW.6.1 Example 2「ツールの予期しない変更を監査する」(外部 `:196`)。事前の (a)(b) が管理者の bypass で外れる経路(ADR-0109 決定5 `0109-records-detect-not-prevent.md:71` の開示の項目)を、事後に数え上げで拾う

### 他の案を落とす理由

- **(c) ruleset workflows を要求にしない**: 組織・Enterprise の設定であり、個人所有のリポジトリで使えない(外部 `:57,74-75`)。GitLab の対応機能も Ultimate に限る(外部 `:172,176`)。製品の機能を要求事項にすると、要求の成否がプランで決まり、規定の信頼性(誰が読んでも同じ合否)が落ちる。SSDF も "does not prescribe how to implement each practice"(外部 `:197`)。本標準の既存の書き方も性質で書く(内部 `:226`)。**(c) は (a) の性質を満たす手段の1つとして例示する**。さらに (c) 単独では層 B を塞がない(外部 `:76`)ため、例示にも「検査のロジックも定義の側に置くこと」を併記する
- **(d) 開示だけ: 採らない**。ADR-0109 自身が「開示は決定1〜4 と組で採る。開示だけでは数え方が変わらない」と書く(`0109-records-detect-not-prevent.md:71`)。G-5 には組になる検出が無い(内部 `:233`)。SLSA L3 の継続性の証拠も示せない。開示は (a)(b) で塞げない残り(R-2 の層 B のテスト部分、管理者の bypass)に限って使う
- **(f) 書き換えの検出だけ: (a) に吸収する**。(a) の基底の判定が `CONTROL_FILES` の変更を検出するので、独立の案としては採らない。(a) を採れない採用者の狭める措置としては残しうる(ADR-0090 決定4 の「適合の手段」と「狭める措置」の区別 `0090-job-token-and-deploy-credential-binding.md:102` に倣う)
- **(g) push のパスの制限: 要求にしない**。雛形の「bypass actor を置かない」決定と衝突する(内部 `:244`)。bypass を置けば、bypass を持つ者が検査を変えられる点は (b) と同じで、追加の信頼性が小さい。プランの条件も未確認(E-10)
- **(h) マージのキュー: 採らない**。合成コミットの定義で動くので本件は解けない(内部 `:245`)。「採らない」と明記する
- **(i) 固定した版のスクリプトだけ: 単独では採らない**。yml が PR の側なら読み元の指定を書き換えられる(内部 `:246`)。(a) の実装の中で、スクリプトの取り出し元として使うことは妨げない

### 条件と留保

- **(a) は PR のコードを実行しない範囲に限る**。`pull_request_target` で PR の先頭を checkout して実行するのは、Security Lab が名指しで危険とする構成である(外部 `:36`)。Scorecard Dangerous-Workflow はこの組み合わせを Critical として検出する(外部 `:113-114`)。要求事項に次を付ける
  - PR の内容はデータとして読むだけにする(`git show`・API)。PR の側のスクリプト・依存・アダプタのコマンド・ローカルの action を実行しない
  - ジョブの権限を最小にする。PR の題名・本文をシェルへ式展開しない(内部 `:191`)
  - 「読むだけ」を試験で固定する(内部 `:192`)。`delegation.yml` の試験(`test-check-delegation.mjs:245-254`)と同じ型
  - 採用者の Scorecard の Dangerous-Workflow に掛かることが予想される。掛かる理由と、PR のコードを実行しないことの試験を、テンプレートの README に書く(未実証: Scorecard が checkout の有無だけで判定するなら誤検出になる。外部 `:114` は「安全に使われているかまでは検証しない」とする)
- **個人所有・無償のプラン**: (a) は `pull_request_target` がどのプランでも使えるので成り立つ(内部 `:197`。未実証、E-4)。(b) は別人の存在が前提で、1名の体制では作成者の承認が数えられない(外部 `:87`、内部 `:213`)。AI エージェントが別のアカウントで push し、人が承認する構成なら「push した者と承認者が別」は成り立つ(外部 `:95`。未実証)。成り立たない体制は未達として開示する(ADR-0028 の未達と省略の区別、ADR-0090 決定2 の「手段が無い / 使わないと決めた」の区分)
- **ADR-0109 との立場の違いの理由を書く**: ADR-0109 は判定記録を「G-7 の集約。事後でよい」記録と区分し、検出を採った(`0109-records-detect-not-prevent.md:103`)。G-5 の必須チェックはマージの前に効く判定であり、事後の検出では、緩めた検査で入った変更がすでに効力を持つ。ADR-0106 の「事前に効く読み手」の区分(同 `:103` が引く)に当たるので、防止を採る。この理由を新しい ADR に書く
- **(a) の判定を必須チェックにする経路は未実証**: `pull_request_target`・`workflow_run` のジョブが出すチェックが PR の先頭に付き、ルールセットの必須チェックとして数えられるか(E-4)。確かめるまで暫定マークを付ける

## R-2 定義とスクリプトの2層と、送り手

### 推す案

**3つの層に分けて条項を書く。層 A(定義)と層 B(判定のスクリプト)は同じ要求「変更の側の外から読む」で扱う。層 B のうち PR のコードの実行(テスト等)は、結果を信頼しないデータとして扱い、R-1 の (b) で統制する。層 C(送り手)は性質の要求として置き、満たさない構成は未達として開示する。**

| 層 | 対象 | 要求 | 満たす手段の例 | 満たさない場合 |
| --- | --- | --- | --- | --- |
| A 定義 | 判定のワークフローの定義(yml)、ジョブの依存(`needs`)、起動の契機 | 判定される変更が書き換えられない場所から読む | `pull_request_target`・`workflow_run`、ruleset workflows(SHA 固定)、GitLab pipeline execution policy | 未達 |
| B1 判定のスクリプト | `scripts/gate/**`、`adapters/**` の判定の規則、契約検査 | 層 A と同じ場所から読む。PR の内容はデータとして読むだけにする | 基底の checkout、配布の版の固定 | 未達 |
| B2 PR のコードの実行 | テスト・カバレッジ・静的解析(PR の製品コードを動かすこと自体が目的) | 結果は信頼しないデータ。PR が層 A・B1 の対象または B2 を動かす定義に触れた場合、その PR の B2 の結果は書き換えた定義で作られたものと扱い、R-1 (b) の承認を要する | `pull_request`(権限は read)で動かし、`workflow_run` で受け取る | (b) の承認が無ければ未達 |
| C 送り手 | 必須チェックの結果を出す主体 | 判定される変更の側から同じ名前の結果を出せない送り手に限る | 判定だけが持つ資格情報の App(既定ブランチに限った配備の環境の秘密情報)と、ルールセットの `integration_id` の固定 | 未達。固定の文で開示 |

### 理由(所在つき)

- **層 A と層 B1 を同じ要求で扱う理由**: 定義だけを外へ出しても、定義が PR の側のスクリプトを呼ぶ限り塞がらない。これは Prow の KEP-2291 が既存の攻撃経路として原文で明記する("a rogue pull requestor changing the scripts that are being executed during a test run"、外部 `:154`)。GitHub ruleset workflows・GitLab の policy でも同じである(外部 `:76,179`)。層 A だけを要求すると、製品の機能を使っても名目の適合になる。**定義とロジックを1組の要求にすることが、3つの製品の実務の限界から導かれる**(外部 `:229-230`)
- **層 B2 を分ける理由**: SP 800-204D PULL-PUSH_REQ-3 は CI を「ネットワーク・特権・秘密情報に届かない隔離環境で動かす」か「書き込み権限を持つ保守者の承認まで遅らせる」かを求める(外部 `:210`)。B2 はこの前者(権限の無い `pull_request`)で動かし、結果を基底の判定がデータとして受け取る。Security Lab の二段構成(権限の無い `pull_request` と `workflow_run`)と同じ型である(外部 `:40`。原文の引用は未取得)。B2 の結果は PR が作れるので、PR が B2 の定義を変えた場合は、後者(保守者の承認)に倒す。Prow も同じく `/ok-to-test` 等の org member の承認で統制する(外部 `:156,161`)
- **層 C を要求にする理由**: SP 800-204D 5.1.1 は、証拠が「開発者の管理下に無い、信頼された構成要素」で作られることを求める(外部 `:207`)。層 A・B1 を基底で動かしても、PR が足したワークフローが同じ名前の成功を出せるなら、必須チェックは基底の判定を表さない(内部 `:196`)。層 C を欠くと、層 A・B1 の要求は送り手のすり替えで外れる
- **`integration_id` を GitHub Actions に固定するだけでは層 C を満たさない**: ルールセットの送り手の指定は「アプリ」を縛る(外部 `:45,49`)。どのワークフローのどの版から送られたかは縛らない(外部 `:52`。原文は限界を明記しない。推測)。基底の判定と PR の側のジョブは同じ App(GitHub Actions)から送られる。これは「人・外部トークンによる偽の status」を止める狭める措置であり、適合の手段に数えない。ADR-0090 の「`GITHUB_TOKEN` は短命でも (a)(b) に当たらない」(`0090-job-token-and-deploy-credential-binding.md:60`)と同じ論理であり、G-8 の (a)(b)(c) の形(`gate-criteria.md:1521-1527`)を G-5 の送り手へ写す

### 他の案を落とす理由

- **層を分けず「CI の定義を保護する」とだけ書く案: 採らない**。外部の3製品が層 A だけを塞ぎ、層 B を残すことが原文で確かめられている(外部 `:154,161`)。分けない条項は、層 A の手段で適合と読まれる
- **層 B2 も基底で動かす案: 採らない**。PR の製品コードを `pull_request_target` で実行することになり、Security Lab・Scorecard Dangerous-Workflow が危険とする構成そのものになる(外部 `:36,114`)。信頼性(検査の真正)を得るために、より重い脅威(書き込み権限と秘密情報への到達)を開く
- **送り手の論点を開示だけで済ませる案: 単独では採らない**。開示は層 C の未達の表示として使う。満たす手段(専用の App と `integration_id`)が個人のアカウントでも作れるなら(未実証。GitHub App は個人のアカウントでも作成できるという知識に依る。本会議体では確かめていない)、「手段が無い」ではなく「使わないと決めた」未達になる(ADR-0090 決定2 `0090-job-token-and-deploy-credential-binding.md:72-79`)。どちらかを記録に書かせる
- **Scorecard の Branch-Protection の満点で足りるとする案: 採らない**。Scorecard は必須チェックが1つ以上あることを数えるが、送り手やワークフローの版を検査しない(外部 `:124`)。採用者の外部評価が満点でも本件は残る。この事実は保証の開示に書く価値がある(読み手が Scorecard の点数を本件の適合と誤読しないため)

### 条件と留保

- **層 C の未達の扱いは E-3 の結果で変える**: PR が足した同名のジョブで必須チェックが通るか、`integration_id` を固定した場合に区別できるか(内部 `:268`)は未実証。区別できると確かめられれば、層 C の手段の表を改める。それまでは暫定マークを付ける
- **層 B2 の「書き換えた定義で作られた結果」の判定は、基底の側の差分の読み取りで行う**。PR の側の自己申告に依らない。読み取りの安全(フック・`.gitattributes` のフィルタ・submodule の取得で PR のコードが動かないこと)は E-11 で確かめる
- **管理者の bypass は層 A〜C のどれも塞がない**。ADR-0109 決定5 の開示の項目1(`0109-records-detect-not-prevent.md:71`)に、G-5 の判定装置の分を足す。SLSA Source の「Named References の変更の記録」(外部 `:132`)に相当する、ルールセットの変更の記録の読み取りを事後の検出(R-1 (e))に含めることを検討する(ルールセットの履歴の API の可否は未確認)
- **ISO/IEC 27001:2022 A.8.4・A.8.32 は引かない**。原文を取得できていない(外部 `:219`)。二次情報だけで条項の根拠にしない

## R-3 所有する組織の同意の記録(IMPL-0340)と AI維持管理者の記名

### 推す案

**両方とも本人の操作(承認のレビュー)と結び付けて機械で確かめる。確かめる場所は R-1 (a) の基底の判定(事前)と、R-1 (e) の出荷の集約(事後)の2か所。ただし扱いを分ける。**

1. **AI維持管理者の受け入れ**: `CONTROL_FILES` に触れる PR について、向きに依らず、名簿の数値の識別子(ADR-0108)で照合した AI維持管理者の席の責任者の承認のレビューを、基底の判定が確かめる。本文の欄「受け入れた者」は記録として残すが、照合の正は承認のレビューとする。これを効力を持つ記録の閉じた列挙(ADR-0106 決定1)へ足す(厳しくする向き)
2. **所有する組織の同意**: 標準の要求は「事前の同意」と「事後の提出」の2形(ADR-0087 決定2)。事前の同意は、所有する組織が指名したアカウントの承認のレビューとして表す形を、照合できる形として定める。照合の要否(所属が異なるか)は機械が知らないので、要否は人が読む記録(テンプレ8 第9項)のまま残し、**指名者が名簿に載っている場合に限り**機械が照合する。事後の提出は、出荷の集約が期限の超過を数える
3. 所有する組織が自らルールセットのコード所有者・パス単位の必須レビュアーで同意を強制する構成は、上の照合の代わりに認める(手段の例示)

### 理由(所在つき)

- **本文の欄では自己承認を止められない**: いまの「受け入れた者」は PR の作成者が氏名を書けば通る(内部 `:134`)。SP 800-204D 5.1.2「merge approval の権限を持つ開発者は自分のマージを承認できない」(外部 `:208`)、SSDF PS.1.1 Example 4「他者の変更を code owner がレビューし承認する」(外部 `:195`)、OpenSSF SCM「Workflows Should Not Be Allowed To Approve Pull Requests」「Repository Should Not Allow Committer Approvals」(外部 `:145`)はいずれも**承認の主体の真正**を求める。テキストの記名は主体を表さない。本人の操作(承認のレビュー)だけが、ホスティングが主体を確かめた記録になる
- **向きに依らず課す理由**: 3.11.2 の AI維持管理者の承認は、強制層の検査の追加・削除・統合を含み、緩める向きに限っていない(`roles-responsibilities.md:1328`、内部 `:25`)。したがって承認のレビューを全変更に課すことは、標準の要求を本人の操作へ移すだけで、要求を広げない。規格と実務(CODEOWNERS、Scorecard Tier 4、SSDF PS.1.1)も向きを区別しない。機械が向きを判定できない(内部 `:133`)ことは、向きに依らない形なら問題にならない
- **同意の要否を機械に判定させない理由**: 構成は席の組織を持たない(ADR-0069 決定2、内部 `:251`)。ADR-0087 は判定の結果を受け取る者を構成へ写さないと決め、席の責任者と所有する組織の一致を必須にする案を却下した(`0087-outsourcing-gate-placement-enforcement-ownership-and-authority-sources.md:146`、内部 `:74,255`)。要否の判定を機械へ移すと、これらの決定を覆す。照合の対象(指名者のアカウント)だけを名簿に載せる形なら、組織の所属を構成に持たせずに済む(未実証: 名簿へ指名者を載せることが ADR-0087 の「構成へ写さない」に当たるかは突合で確かめる)
- **事前に確かめる理由**: G-5 はマージの前に効く。緩めた検査で入った変更は、マージの時点で効力を持つ。ADR-0106 の「効力を持つ前に記名者本人の操作で帰属を裏づける」(内部 `:206`)の区分に当たる。事後の集約だけでは、緩めた検査が効いている期間を残す
- **事後にも確かめる理由**: 管理者の bypass は事前の照合を外す(ADR-0109 決定5)。SLSA Source L2 以上の「Named References の変更を、いつ・誰が行ったか記録する」(外部 `:132`)、SSDF PO.3.2 Example 6 の監視(外部 `:190`)に当たる数え上げを、出荷の集約で行う。承認のレビューの写しは record-copy が records へ置いており、材料は既にある(内部 `:242`)
- **所有する組織がルールセットで強制する形を認める理由**: 軸D の「強制層を所有する組織」はリポジトリと CI の管理権限を持つ側である(内部 `:209`)。GitHub・GitLab の中央の強制の機能は、まさにこの組織が下位のリポジトリへ統制を課すための機能である(外部 `:57-58,167-171`)。所有する組織が自らの設定で強制するほうが、受託側のテンプレートの照合より上位の信頼水準にある(SP 800-204D 5 の前提、外部 `:206`)

### 他の案を落とす理由

- **本文の欄の照合を続け、本人の操作と結び付けない案: 採らない**。上の理由で、自己承認を止めない。G-5 の判定装置が強制層である以上(3.11.3、内部 `:24`)、その変更の承認が誘導層の自己申告に留まるのは、3.11.3「遵守が必須の規則を誘導層に書いてはならない」と食い違う(内部 `:234`)
- **緩める向きだけに承認のレビューを課す案: 採らない**。向きの判定が書き手の自己申告になり(内部 `:133`)、「止まった」と書けば記名が要らない現状の穴が残る。3.11.2 自体が向きを限らない
- **同意の要否を構成から機械に判定させる案: 採らない**。ADR-0069 決定2・ADR-0087 の却下と衝突し、それらを覆す根拠(新しい事実)が本会議体に無い
- **IMPL-0340 を `plan=adopter` へ移して照合を降ろさない案: 採らない**。照合できる形(指名者の承認のレビュー)が定まれば、テンプレートで降ろせる。採用者へ委ねると、委託の境界で最も統制が弱い場所(席の責任者が所有する組織に属さない場合)を検査しないまま配ることになる
- **pr-rules(PR の側)へ同意の照合を足すだけの案: 採らない**。同じ PR で照合を外せる(内部 `:258`)。R-1 (a) が前提である

### 条件と留保

- **1名の体制**: 作成者と AI維持管理者が同じ人で、GitHub は作成者の承認を数えない(外部 `:87`、内部 `:213`)。AI エージェントが別のアカウントで PR を作る構成なら、人の承認のレビューは成り立つ(未実証)。人が自ら作る PR では成り立たない。この場合は未達とし、1名の体制の行(第4章 G-5、IMPL-0238)と兼務の境界(ADR-0082)との突合で、自己承認を数えないことを明記する。SLSA L4 も "Trusted Robot" への例外を認めるだけで、人の自己承認を認めない(外部 `:136`)
- **承認の後の push**: `dismiss_stale_reviews_on_push`・`require_last_push_approval` が雛形で true(内部 `:212`)。基底の判定でも、承認のレビューが PR の先頭のコミットに付いていることを照合する。SLSA L4「レビュー中の追加変更もレビューする」(外部 `:136`)、Scorecard Tier 5(外部 `:121`)に対応する
- **陰性の確認・「外した」の記録を効力を持つ記録の列挙へ足すこと**は、厳しくする向きの変更である(ADR-0109 の補いの前例 `0109-records-detect-not-prevent.md:17`)。足すのは「AI維持管理者の承認のレビュー」と「所有する組織の指名者の承認のレビュー」であり、陰性の確認の結果の欄(人が書く記述)そのものは列挙へ入れない。記述の帰属まで操作で裏づける要求は、規格に根拠を見つけていない
- **EV**: 同意の要件の根拠水準 EV-0177(E0、内部 `:67`)は変わらない。照合の形を変えても、同意を要件にすることの効果の実証にはならない

## R-4 #369 との分担、実機の確認、記録

### 推す案

**分担案1 を採る。#371 が「判定する側の定義とロジックを、判定される変更の外から読む」共通の要求と機構(R-1・R-2)を決め、#369 はその上で AI レビューの指示の読み元を実装する。統合しない。実機の確認は、条項を `delivered` にする前の条件とし、採否の決定の前提にはしない。新しい ADR を1つ起こす。**

### 理由(所在つき)

- **分担案1 の理由**: #369 の指示はデータだが、それを読む yml が `pull_request` で動く限り、読み元の指定そのものを PR が書き換えられる(内部 `:168`)。附属書H H.4 条件3 の「書き換えられない保護の下にあること」(`assurance-case.md:336`)は、層 A の要求が無いと成立しない。Prow・GitLab・ruleset workflows はいずれも「中央の定義」を先に置き、その上で個々の入力を読む(外部 `:153,168,58`)。共通の層を先に決める順が、実務の構造と一致する
- **統合しない理由**: トリアージは範囲が異なるとして重複にしなかった(内部 `:156`)。#369 は合否に使わず H.4 条件3 に掛かる。#371 は必須チェックの合否そのもの(内部 `:164`)。受け入れ条件が違う。統合すると、一方の未達がもう一方の完了を止める
- **分担案2(#369 を先に単独で降ろす)を採らない理由**: yml が PR の側のまま IMPL-0333 を `delivered` にすると、規定(5.8.6 要求事項7 `human-ai-boundary.md:1076`)を満たさない実装を「降りた」と表示する。降りていない規定を表示し続ける規則(CLAUDE.md #222)に反する
- **実機の確認を採否の前提にしない理由**: R-1〜R-3 の推す案は、E-1・E-2 が「通らない」(PR の側の定義が使われない)と出ても変わらない。SP 800-204D・SSDF の要求は性質であり、GitHub の現在の挙動が偶然に安全でも、規定の根拠は残る。ただし**手段の表と開示の文は実機の結果で変わる**ので、`delivered` の前に確かめる
- **新しい ADR を起こす理由**: ADR-0087 の G-5 の行「置き先を持たない。強制層を所有する組織の CI で判定する」(内部 `:55`)を補う決定であり、ADR-0109(記録は検出)と違う立場(G-5 は防止)を採る理由を記録する必要がある。採用済み ADR の本文は書き換えない
