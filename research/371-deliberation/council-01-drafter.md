## R-1 検査の読み元

### 推す案

**案(a) を「PR のコードを実行しない判定」に限って規定し、PR のコードを実行せざるを得ない判定には案(b) の形(変更の側から外せない、AI維持管理者本人の操作による承認)を組にして課す。両者を製品の機能でなく性質で書き、案(c)・(b1)・(b2) は性質を満たす手段の例として置く。**

規定の文案(第4章 G-5 に新しい小節「判定のコードの読み元」を置く想定。見出しの適用範囲は、統制の設定の陰性の確認と同じ対象に揃える):

> #### 判定のコードの読み元
>
> このゲートの判定のうち、変更のコードを実行せずに行える判定(PR 単位の検査、集約の契約の検査、統制の設定の変更の検出と、その記録の照合)は、**判定のコードと構成を、判定の対象となる変更を取り込む先の版(既定ブランチの先端)から読まなければなりません**。変更の側に含まれる判定のコードと構成で判定する構成は、この規定を満たしません。変更の側は、判定の入力(差分・本文・ファイルの中身)としてだけ読み、実行しません。
>
> 変更のコードを実行することが目的の判定(基準1〜3 のテスト・カバレッジ・静的解析など)は、変更の側で実行します。統制の設定([第1章 1.4](/process-compass/phase4-process-design/overview/))を変える変更では、変更の側で作られた判定の結果を、書き換えられた定義で作られた結果として扱います。**その結果だけで、このゲートを通過させてはなりません**。この変更には、AI維持管理者の承認([第3章 3.11.2](/process-compass/phase4-process-design/roles-responsibilities/))を、承認者本人のアカウントの操作(ホスティングの承認のレビュー)で、変更が既定ブランチへ入る前に得ます。この承認の要求は、変更の側から外せない形で置きます。
>
> 手段は指定しません。性質を満たす手段の例は、既定ブランチの定義で起動する判定(フェーズ5)、既定ブランチの側の所有者の定義で評価されるコード所有者のレビューの必須、対象のリポジトリの外に定義を置いた必須のワークフローです。

理由(所在つき):

1. **先例との不揃いを、規定の側で解く**。5.5.4(`human-ai-boundary.md:449`)と G-8(`gate-criteria.md:1521`)は同じ論理(書き換えられる場所の中の確認は、書き換えれば外れる)で要求事項・禁止を置いた。G-5 の必須チェック `gate-g5` は、強制層の中で最も多くの規定が降りている先(`target=pr-checks`・`gate-g5-workflow` の IMPL が多数)であり、その真正性だけが規定を欠く。内部 7 節が言う通り、会議体は「同じ規定を置く」か「置かないと決めて理由を書く」かのどちらかを書く必要がある。置かない理由として成り立つものを、起案の側では見つけられなかった(後掲「他の案を落とす理由」)
2. **データの読み元(`gate-criteria.md:1911`、ADR-0078)とコードの読み元が割れている状態は、データの規定の効き目そのものを損なう**。`gate-g5.yml:369-377` は基準値・名簿・台帳を既定ブランチから読むが、読むコードは PR の側にある。PR が `--policy-base` の手順を消せば、データの規定も外れる〔未実証。E-1・E-2〕。コードを基底へ揃えることは、既に採った規定を名目にしないための要件である
3. **ADR-0109(記録は防止でなく検出)と矛盾しない理由が書ける**。ADR-0109 は判定記録を「G-7 の集約。事後でよい」と区分し、事前に効く読み手(委任の判定と名簿の提案)は別に扱った(`0109-records-detect-not-prevent.md:103`)。ADR-0106 決定3 も「効力を持つ記録は、効力を持つ前に帰属を裏づける」とした。G-5 の判定のコードは、**変更が入った時点から、その変更自身と以後のすべての変更の合否を変える**。事前に効く読み手の典型であり、ADR-0106・0109 の区分に従えば検出でなく事前の統制の側に入る。この区分を新しい ADR に明記すれば、立場の一貫性は保てる
4. **規格の要求から導ける**。SP 800-204D 5 の前提(制御面は個々のステップより高い信頼水準で動く)、3.1.5(検査は迂回されうる)、SSDF PS.1.1(configuration-as-code を最小権限で保護)と Example 4(code owner のレビュー)、SLSA Source L3(技術的統制の継続の証拠)(外部 3.1・3.2・2.2)。いずれも実装を指定しないため、性質で書く本標準の書き方(5.8.6「拒否の実装の手段は指定しません」、内部 5.3)と合う
5. **G-5 の全体を基底へ移せないことを規定の側で認める**。テストを基底で走らせても PR のコードは検査できない(内部 5.1)。だから「実行しない判定は基底から」「実行する判定の結果は、統制の変更では人の承認を伴う」の二つに分けて書く。後者は新しい権限ではなく、3.11.2 の既存の承認権限を、本文の欄(自己申告)から本人の操作へ移すだけである(R-3 で詳述)
6. **個人所有・無償のプランで成り立つ**。`pull_request_target`・`workflow_run` はプランに依らない〔外部 1.1。プランの条件は未実証〕。コード所有者のレビューの必須は、個人所有の public リポジトリのルールセットで使える(外部 1.7、Free の "full feature set")〔個人所有での動作は未実証。E-7・E-8〕。required workflows(案(c))は組織・Enterprise が前提(外部 1.4)だが、例示に留めるので規定の成立を妨げない

### 条件・留保

- **規定は「満たす手段が無い構成」を想定して書く**。採用者のプラン・所有の形で推す案の手段がどれも使えない場合は、第1章 1.10.2 の列挙に無い離脱として記録し、保証の開示に定型の文で出す。ADR-0109 決定1 が「ホスティングの規則で履歴の書き換えを止められない構成」を列挙に無い離脱で扱った先例(`:53`)に揃える。未達(ゲートについての区分)にするか列挙に無い離脱にするかは、G-5 というゲートの判定の性質に当たるので**未達**のほうが近いとも読める。起案としては「未達(手段が無い / 手段はあるが使わないと決めた)」(ADR-0090 決定2、`0090-*.md:72-84`)の2区分を推す。G-5 という特定のゲートの判定の真正性であり、置き場の性質ではないためである。会議体で決める
- 「既定ブランチの先端から読む」と「基底ブランチから読む」の語の選択。5.5.4 は「基底ブランチ」、`gate-criteria.md:1911` は「既定ブランチの先端」(スタックの上の層で基底が下の層になるため)。G-5 はスタックの上の層にも掛かるので、**`:1911` の語(既定ブランチの先端)に揃える**。5.5.4 の語は委任の経路の範囲で今のままでよい
- **〔未実証〕基底で動く判定が出す結果を必須チェックとして数えられること**(E-4)。数えられない場合、推す案の「変更の側から外せない形」は、コード所有者のレビューの必須(手段の例の2つ目)だけが担う。規定の文はこの場合も成り立つ(手段を指定しないため)が、準拠テンプレートの実装の形が変わる
- **〔未実証〕コード所有者の判定に基底の側の CODEOWNERS が使われること**(E-7、外部 1.5 も原文未確認)。PR の側が使われるなら、手段の例から外す
- 適用の範囲。統制の設定の陰性の確認の対象(`gate-criteria.md:734`)と同じにする。G-5 の真正性の規定を、陰性の確認と別の対象で書くと、二つの一覧がずれる
- 第8章の調整で外せる規定にはしない。G-5 はすべての段階で適用(`gate-criteria.md:681`)であり、その判定の真正性を外す調整を置く理由が無い

## R-2 定義とスクリプトの2層と、送り手

### 推す案

**2層を、規定の語の定義で一つに束ねる(「判定のコード」= ワークフローの定義と、それが実行する検査のスクリプト・その読み込み先)。そのうえで、層を分けた手段の例に「定義だけを外へ出し、スクリプトを変更の側から実行する構成は、この規定を満たさない」と明記する。送り手は、独立の要求事項にせず、R-1 の「変更の側から外せない形」の判定の中で扱う。満たせない構成は未達として開示し、env-check に設定の事実を読ませる。**

文案(R-1 の小節の続き):

> 判定のコードは、ワークフローの定義と、それが実行する検査のスクリプトとその読み込み先です([フェーズ5 計算資源の戦略](/process-compass/phase5-implementation/compute-strategy/)の「検査の定義」と同じ範囲)。定義だけを変更の側から読まない形にしても、その定義が変更の側の検査のスクリプトを実行するなら、判定のコードを変更の側から読んでいます。
>
> 判定の結果を、変更の側のワークフローが同じ名前と同じ送り手で出せる構成は、「変更の側から外せない形」に当たりません。必須の検査が名前だけで指定され、送り手を限らない構成がこれに当たります。

理由(所在つき):

1. **2層を別々の要求事項に割らない理由**。外部 4 節の整理の通り、定義の中央化(層A)だけを塞ぐ仕組み(GitHub ruleset workflows・GitLab pipeline execution policy・Prow)は、定義が PR 側のスクリプトを呼ぶ限り層B を塞がない(Prow KEP-2291 の原文 "a rogue pull requestor changing the scripts that are being executed during a test run"、外部 2.4)。層ごとに要求を書くと、層A だけを満たした構成が「定義の規定を満たした」と読まれ、名目の適合が生まれる。一つの語で両方を含め、例示の側で外す構成を名指しするほうが、読み手が誤りにくい
2. **語の出所が既にある**。`compute-strategy.md:124` は「手元の検査の定義(検査のスクリプト・テンプレート・その読み込み先)」と書く。新しい語を作らず、この範囲を引く(用語の二重化を避ける。CLAUDE.md の語彙の方針)
3. **送り手を独立の要求事項にしない理由**。送り手の固定(`integration_id`)が止めるのは、人や外部のトークンによる偽の status だけで、どのワークフローのどの版かは縛らない(外部 1.3。原文は限界を明記せず、推測)〔未実証。E-3〕。「送り手を GitHub Actions に限る」を要求にすると、同じ App で動く書き換えたワークフローを通すため、要求を満たしても性質を満たさない。性質(変更の側から同じ名前・同じ送り手で出せない)で書けば、送り手の固定が効く構成(判定だけが持つ資格情報で出す結果)と効かない構成を、読み手が区別できる
4. **送り手の問題は、G-5 の外にも及ぶ**。`check-delegation.mjs:226-231` は、委任の判定で PR の先頭のコミットのチェックの一覧を名前と結論で読む。`delegation.yml:37-40` は `workflow_run` で gate-g5 の完了を受ける。委任の判定のコードは基底から読む(5.5.4)が、**判定が入力に使う G-5 の結果は、PR が書き換えた定義・同名のジョブで作れる**〔未実証。E-1・E-3〕。R-1 の規定を G-5 に置けば、委任の判定の入力の真正性も同じ規定に依れる。委任の側に別の規定を足さないで済むのは、規定の数を減らすためではなく、同じ問いを二か所で別々に答えさせないためである(答えがずれる)
5. **判定だけが持つ資格情報で結果を出す形は、G-8 の (a) と同じ結び付け**。既定ブランチに限った Environment に置いた専用の App の鍵で結果を出し、ルールセットの必須の検査の送り手をその App に固定する形(内部 5.1 末尾)は、G-8 (a)「配備を許す参照に限った、配備の環境の秘密情報」(`gate-criteria.md:1523`)と同じ形である。ADR-0109 は専用の App の鍵を「新しい信頼の根になる」として記録用ブランチの書き込みの限定に採らなかった(`0109-*.md:77`)。ここで違うのは、ADR-0109 では App が**迂回者**として書き込みを独占する案であり、管理者は規則を外せるため防止が成り立たなかったことである。本件の App は結果の**送り手**であり、管理者の迂回は別の開示(ADR-0109 決定5)で既に扱われる。したがって ADR-0109 の却下の理由はそのまま当たらない。ただし鍵の運用の負担は同じであり、1〜2名の体制で既定にする根拠は無い(ADR-0109 の採らなかった案「署名コミットだけで裏づける」の理由と同じ)。**例示に置き、準拠テンプレートでは既定で無効の部品にする**(委任のマージの Environment と同じ扱い、`ci-gates.md` 実装の表「マージの実行の有効化」)

## R-3 所有する組織の同意の記録(IMPL-0340)と AI維持管理者の記名

### 推す案

**(1) AI維持管理者の承認は、向きに依らず、統制の設定を変える変更すべてで、承認者本人のホスティングの承認のレビューで成立させる。照合は R-1 の基底から読む判定で行い、変更の側の pr-rules に置かない。(2) 所有する組織の同意は、機械に向きを判定させない。「事前の同意」を、所有する組織が自らの指名者の承認を強制層のパスに課すホスティングの規則で行う形を、事前の同意の置き場として規定する。構成に席の組織を持たせない(ADR-0069・ADR-0087 決定3 を維持)。(3) 承認を置けない体制は自己申告として開示し、G-7 の集約で数える。**

文案(第4章 G-5「検査を外す変更の記録」の「受け入れるのは AI維持管理者です」の段落の後、および R-1 の小節へ):

> 統制の設定を変える変更の AI維持管理者の承認([第3章 3.11.2](/process-compass/phase4-process-design/roles-responsibilities/))は、AI維持管理者の席の責任者本人のアカウントによる、変更の先頭のコミットへの承認のレビューで成立します。本文の欄に名前を書いたことを、承認に数えません。承認の後に足されたコミットは、承認を失効させます。「外した」の記録の「受け入れた者」は、このレビューの書き手と一致しなければなりません。
>
> この照合は、判定のコードを既定ブランチの先端から読む判定で行います(前掲「判定のコードの読み元」)。
>
> AI維持管理者の席の責任者のほかに承認者を置けない体制(変更の作成者のアカウントと、AI維持管理者の席の責任者のアカウントが同じ体制)では、作成者本人のアカウントの操作を受け付け、承認が自己申告であることを変更ごとに開示します。出荷の証跡の集約は、出荷の範囲の統制の設定を変えた変更のうち、承認のレビューで成立したものと自己申告のものを分けて数えます。

第8章 軸D「強制層の変更の承認と、所有する組織の同意」の箇条への追加の文案:

> - 「事前の同意」は、所有する組織が、強制層のパスを変える変更に、自らが指名した者の承認のレビューを要するホスティングの規則(コード所有者のレビューの必須など)を置き、指名した者がその変更を承認したことで行う。テンプレ8 第9項に、規則の所在と指名した者を記録する。規則を置かない「事前の同意」は、同意の記録の置き場(変更ごと)を同じ欄に書いた場合に限る(適用: AI維持管理者の席の責任者が、強制層を所有する組織に属さない場合)
> - 規則が向きを判定しないため、強める向きの変更にも指名した者の承認が要る構成になる。本標準は、緩める向きに限って同意を求める。所有する組織がそれより広く課すことを妨げない

理由(所在つき):

1. **向きに依らない承認は、新しい要求ではない**。3.11.2 の承認権限は「指示資産の変更(強制層の検査の追加・削除・統合を含む)」を AI維持管理者が承認すると書き、向きで限っていない(`roles-responsibilities.md:1328`)。G-5 の陰性の確認も「強める向きの変更も対象」(`gate-criteria.md:734`)。機械が向きを判定しないこと(内部 2.3)は、AI維持管理者の承認については欠陥にならない。全変更に課せばよいからである。今の pr-rules は「外した」のときだけ記名を求め、「止まった」と書けば AI維持管理者の記名を求めない(内部 2.3)。これは 3.11.2 より弱い降ろし方であり、本件で 3.11.2 の側へ揃える
2. **本文の欄の記名を承認に数えない理由**。PR の作成者が `受け入れた者: <氏名>` と書けば通る(内部 2.3)。ADR-0106 決定3 は「名前の一致を裏づけに数えない」と定めた(`0106-*.md:54-56`)。「外した」の記録は、`check-pr.mjs` の合否を変える(記名があれば外す変更が通る)。第1章 1.4 の「効力を持つ記録」の定義「変更の検査の合否、権限者の照合 … を変える記録」(`overview.md:107`)に中身が当たるのに、閉じた列挙に入っていない。列挙へ足すか、記名でなくレビューで承認を成立させるかのどちらかが要る。起案は**後者**を推す。列挙へ足すと、記録の転記の経路(記録だけの PR・記名者本人のレビュー)を経る手続が増えるが、承認そのものが PR の上のレビューで成立すれば、記録は承認の写しで足りる。ADR-0106 決定4 の受け皿(対象の PR の上の記名者本人のレビュー。書き手は名簿の人、AI の名義でない、PR の作成者と異なる、先頭のコミットと一致、承認の後の変更で失効。`0106-*.md:58-62`)と同じ形を使えるため、新しい照合の関数を作らずに済む(ADR-0109 決定3「同じ強さ・同じ関数で照らす」と同じ方針)
3. **照合を pr-rules に置かない理由**。R-1 の通り、変更の側で動く照合は同じ変更で外せる。内部 5.6 末尾の指摘「同意の照合を降ろす前提として、検査の読み元の論点を先に決める必要がある」は正しい。R-1 と R-3 は独立ではない
4. **照合の材料は名簿の数値の識別子で読む**。ADR-0108(名簿は数値のアカウントの識別子で照らす)に揃える。ログイン名で照らさない
5. **所有する組織の同意を、ホスティングの規則で行う形を推す理由**。強制層を所有する組織は、軸D の定義で「リポジトリと CI の管理権限を持つ側」(ADR-0087 決定2、`0087-*.md:67`)であり、ルールセットとコード所有者を設定できる。この組織が自らの指名者の承認を強制層のパスに課せば、構成が席の組織を持たない(ADR-0069)ままで、同意の無い変更はホスティングが止める。IMPL-0340 を未達にした理由「構成が席の組織を持たないため、同意の要否を機械で判定できない」(`implementation.md:97`、内部 1.4)を、組織の情報を構成へ写すことなく解ける。受け取る者を構成へ写さないと決めた ADR-0087 決定3(`0087-*.md:87`。正本の二重化を避ける)とも衝突しない
6. **事前の同意の置き場が様式で固定されていない欠け**(#317 の突合 `crosscheck.md:54,58`、内部 1.5)を、この箇条で埋める。事後の提出には置き場の記録が既に要件になっている(`tailoring-guide.md:749`)のに、事前の同意には無い不揃いを解く
7. **1名・共有の名義の体制の扱い**。GitHub は作成者の承認を数えない(内部 5.2)。AI の担い手が専用のアカウントで PR を作る構成(第3章 3.5.3「人と AI の担い手の名義」、`roles-responsibilities.md:622`)なら、1名の体制でも人の AI維持管理者が承認のレビューを出せる〔未実証。外部 4 が「接続点」として挙げた推測〕。共有の名義(人のアカウントで AI が操作する)では、作成者と承認者が同じアカウントになり成り立たない。この場合は ADR-0106 決定3 の「帰属の確認者を置けない体制では、記名者本人のアカウントの操作を受け付け、自己申告であることを記録ごとに開示する」(`0106-*.md:56`)と同じ扱いにする。新しい区分を作らない

## R-4 #369 との分担、実機の確認、記録

### 推す案

**(1) 分担は内部 4.1 の分担案1。#371 が共通の規定(判定と検出の層の入力を作る定義を、変更の側から書き換えられない形で読む)と、その手段の型を決める。#369 は統合しない。#369 は AI レビューの指示(データ)の読み元を、#371 で決めた型の上で実装する。(2) 標準の文言は実機の確認の前に書く。降ろし先の IMPL を `delivered` にするのは、手段に関わる実機の確認(E-3・E-4・E-7・E-11 と、追加の E-13・E-14)の後に限る。一時のリポジトリの作成は外部への作用を含むため、ユーザーの承認を得てから行う。(3) 新しい ADR を1つ起こし、EV・IMPL・開示を下記のとおり置く。**

理由(所在つき):

1. **#369 を統合しない理由**。守るもの(指示というデータ / 実行される判定のコード)、合否への影響(H.4 条件3 / 必須チェック)、降ろし先(IMPL-0333 / G-5)が違う(内部 4.1 の表)。トリアージも「重複とはしない」とした(`research/triage-370-401.md:78-84`)。統合すると、IMPL-0333 の受け入れ条件(delivered)が #371 の手段の確認に縛られ、指示の読み元という独立に降ろせる部分まで遅れる
2. **#371 を先に決める理由**。#369 の yml も `pull_request` で動く限り、「基底から読む」手順そのものを PR が書き換えられる(内部 4.1)。H.4 の表の「書き換えられない保護の下にあること(保護の設定と、その設定の変更に AI維持管理者の承認を要すること)」(`assurance-case.md:337`)は、R-3 の推す案(1)(統制の設定の変更の承認をレビューで成立させる)が無いと届かない。#369 単独で delivered にすると、H.4 条件3 を満たしたと読まれる名目の適合になる
3. **#369 の手段の注記**。AI レビューは PR の差分を**読むだけ**で、PR のコードを実行しない。したがって R-1 の「変更のコードを実行せずに行える判定」の側に入り、`pull_request_target` で既定ブランチの指示を読む形が使える〔推〕。ただし PR の題名・本文・差分をモデルへ渡すため、プロンプトの注入で書き込みの権限のトークンや API の鍵を使わせる経路がある。権限の最小化と、AI の確認を承認にも合否条件にもしない既存の規定(5.5.4 の箇条、附属書H H.4)を #369 の実装の条件として申し送る
4. **文言を先に書いてよい理由**。推す案の規定は性質で書き、手段を指定しない(R-1)。性質の要求は、GitHub の仕様の文書(外部 1.1 の【事実】: `pull_request` は定義をマージのコミットから読む)だけで立つ。E-1・E-2 はこの事実の実機での裏づけであり、規定の要否は変えない。一方、どの手段が性質を満たすか(E-3 送り手、E-4 基底の判定を必須として数えられるか、E-7 基底の CODEOWNERS、E-11 PR のコードを実行しないこと)は、準拠テンプレートの実装と、手段の例の書き方を変える。だから IMPL の状態だけを実機の確認に縛る。`delegation.yml` が「実際の GitHub 上で実行して確かめていない」(`delegation.yml:27`)まま IMPL-0235 を undelivered にした先例(`human-ai-boundary.md:463`)に揃える
5. **一時のリポジトリ**。メモリ「通し実行用の一時リポジトリ」によれば pit-in-trial-54 は削除済みで、手順で作り直す。`GITHUB_TOKEN` は PR を作れないため、PR は人が開く。リポジトリの作成・PR の作成は外部への作用であり、会議体と裁定の範囲を超える。**裁定は「いつ・何を確かめるか」までを決め、作成の実行はユーザーの承認の後とする**

### 記録の起案

**新しい ADR(1件)**: 題「G-5 の判定のコードを変更の側から読まず、統制の設定の変更の承認を本人のレビューで成立させる」。決定の骨子:

1. G-5 の判定のうち変更のコードを実行しない判定は、判定のコード(定義とスクリプトと読み込み先)を既定ブランチの先端から読む(R-1・R-2)
2. 変更のコードを実行する判定の結果は、統制の設定を変える変更では、それだけで G-5 を通過させない。AI維持管理者本人の承認のレビューを、変更の側から外せない形で要する(R-1)
3. 送り手を独立の要求にせず、「変更の側から同じ名前・同じ送り手で出せる構成は外せない形に当たらない」で扱う。満たせない構成は未達(手段が無い / 使わないと決めた)として開示する(R-2、ADR-0090 決定2)
4. AI維持管理者の承認は向きに依らずレビューで成立させる。「受け入れた者」はレビューの書き手と一致させる。承認者を置けない体制は自己申告として開示し、集約で数える(R-3)
5. 所有する組織の事前の同意を、所有する組織が置くホスティングの規則と指名者のレビューで行う形を規定し、事前の同意の置き場の欠けを埋める。構成に組織を写さない(R-3)
6. 既存の決定との関係: ADR-0109 の「検出」は判定記録(事後に効く記録)の決定であり、本 ADR は事前に効く読み手(ADR-0106 の区分、ADR-0109 `:103`)である G-5 の判定のコードの決定である。ADR-0087 決定2・3 は維持し、その突合の欠け(`research/317-deliberation/crosscheck.md:54,58`)を埋める。ADR-0106 決定4 の受け皿の形を再利用する。採用済み ADR の本文は書き換えない
7. 採らなかった案: 下表

**根拠水準(EV)**: 識別子は台帳で採番し、ここでは番号を決めない。
- G-5 の判定のコードを既定ブランチの先端から読むことの効果: E1(間接。SP 800-204D 5 の前提・3.1.5、Prow の中央のジョブの定義、5.5.4・G-8 の同じ論理)。差し替え条件: 実機の確認 E-1〜E-4 の結果と、採用者の統制の設定の変更の陰性の確認で見つかった書き換えの件数。見直し 2027-05
- 承認をレビューで成立させることの効果: E1(SSDF PS.1.1 Example 4、SP 800-204D 5.1.2、Scorecard Branch-Protection)。見直し 2027-05
- 送り手を縛れないことの前提: E0(推測。原文は限界を明記しない、外部 1.3)。差し替え条件: E-3・E-14 の結果。見直し 2027-02(実機の確認で早く差し替えられるため短くする)
