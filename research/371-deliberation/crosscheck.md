### C-4 PR の時点の照合と出荷の集約で「統制の設定を変えた変更」の範囲が食い違う(重大度: 中)

- 所在: `template/scripts/gate/aggregate-evidence.mjs:1822`(`controlTouchedOf(prFiles.map((f) => ({ path: f })))`。閾値の一覧は既定の `THRESHOLD_FILES` だけ)。対して `template/scripts/gate/check-pr.mjs:1400`・`:1460` 以降は、アダプタの `thresholdFiles` を足した `thresholdGlobs` と、`process.config.json` の閾値の鍵の変更を数える
- 根拠: 標準 G-5「統制の設定の変更の承認」は「照らす場所は2つ」とし、集約は「出荷の範囲で統制の設定を変えた変更と、その承認のレビューの有無を照らす」。裁定 R-3「確かめる場所は2つ」。集約の側は (1) アダプタが足した閾値・除外のファイル、(2) `process.config.json` の閾値の変更、(3) 名前の変更の元(`git diff --name-only` は改名の後の名前だけを出す)を数えない。PR の時点の判定が外れた構成(gate-g5-base を必須にしていない構成)では、集約が唯一の照合になるのに、その範囲が狭い
- 直し方の向き: 集約も check-pr.mjs と同じ関数で範囲を決める(マージの前の版のアダプタの `thresholdFiles`、`process.config.json` の閾値の鍵の差分、`--name-status -M` の改名の元)。2つの照合の範囲が一致することを試験で固定する

### C-5 保証の開示の「層ごとの充足と未達」が定型の文で、未達を出さない(重大度: 中)

- 所在: `template/scripts/gate/aggregate-evidence.mjs:5125` 付近(「G-5 の判定のコードの読み元(定義 / 判定のスクリプト / PR のコードの実行 / 結果の送り手)」の行)。IMPL-0461(`gate-criteria.md` の項目1 の箇条の直後)は「準拠テンプレートの構成の事実の定型の文」と書く
- 根拠: 裁定 R-4「保証の開示に、R-1・R-2 の層ごとの充足と未達を出す」、R-2「開示の表では、定義・判定のスクリプト・PR のコードの実行・送り手の層を分けて示す」。今の行は採用者の実際の構成を読まず、「定義・判定のスクリプト・構成とも既定ブランチ」と常に書く。採用者が gate-g5-base.yml を消した・書き換えた構成でも、層の行は充足を示し続ける。未達は次の行(env-check の3値)にしか出ず、それも記録の時点の値である
- 直し方の向き: 層ごとの値を、出荷の時点の既定ブランチの実物から導く(gate-g5-base.yml の有無と起動の契機、checkout の ref、`--require-control-approval` の有無、必須チェックの名前)。読めない層は「確かめていない」と出す。定型の文を残すなら、「準拠テンプレートの既定の構成の説明であり、この案件の構成を確かめた値ではない」と行の中に書く

### C-6 1名の体制の「自己申告」が、本人の操作も申告も無いまま成立する(重大度: 中)

- 所在: `template/scripts/gate/material-attribution.mjs:428` 付近(`alone || (sh && !sh.confirmable)` のとき、作成者が席の責任者というだけで `backed: true, how: 'self-attested'`)。標準 `gate-criteria.md:728`(「席の責任者本人のアカウントの操作を受け付け」)
- 根拠: 裁定 R-3「1名の体制では、別の者の承認が得られない。自己申告として区別して開示する」。実装では、席の責任者のアカウントで PR を作っただけで通る。AI の担い手が席の責任者と名義を共有する構成(`sh && !sh.confirmable`)では、AI がそのアカウントで作った統制の設定の変更が、人の操作を1つも経ずに gate-g5-base を通る。標準の「本人のアカウントの操作を受け付け」は、どの操作かを書いていない。読み手は「何かを申告した記録がある」と読むが、実際には作成の事実だけである。開示は残るので経路は見えるが、「申告」と呼ぶ根拠が無い
- 直し方の向き: 受け付ける操作を標準に書く(例: 作成者の事実だけを受け付ける。または、席の責任者のアカウントによる本文の宣言・マージの操作を要する)。名義を共有する構成では、その操作が AI のものでありうることを、保証の開示の自己申告の件数の行の中に書く。実装は、選んだ操作の記録を集約の項目1 に出す。どちらを採るかは裁定に戻す(新しい要求を足すかどうかの判断を含むため)

### C-7 checkout の ref がブランチ名で、定義とスクリプトの版がずれうる(重大度: 低)

- 所在: `template/.github/workflows/gate-g5-base.yml:52`、`template/.github/workflows/record-copy.yml:73`(`ref: ${{ github.event.repository.default_branch }}`)
- 根拠: `pull_request_target` の定義はイベントの時点の既定ブランチのコミット(`github.sha`)から読まれる。ブランチ名の checkout は、ジョブが動いた時点の先端を取り出す。標準は「判定のコード」を定義とスクリプトをまとめた1語とした(R-2)。承認の後の再実行(本件で手順として求めている)では、定義は元のイベントの版、スクリプトは再実行の時点の先端になる。どちらも基底なので PR の側からは突けないが、1つの判定が2つの版のコードで動き、判定の記録からどの版で判定したかが読めない
- 直し方の向き: `ref: ${{ github.sha }}` にして定義とスクリプトを同じ版に揃える(record-copy はマージの後に入ったコミットとの関係を確かめて決める)。判定の報告に、判定に使った既定ブランチのコミットを出す

### C-8 承認の取り下げ・変更要求の後も、gate-g5-base の成功が残る(重大度: 低)

- 所在: `template/.github/workflows/gate-g5-base.yml:35`(契機に `pull_request_review` が無い。理由はファイルの冒頭のコメントに書かれており、正しい)
- 根拠: 承認の後に再実行して成功した check run は、承認を取り下げ(DISMISSED)・変更要求に替えても、次の push・本文の編集まで成功のまま必須チェックを満たす。標準の「承認の後に足されたコミットは、承認を失効させる」(`gate-criteria.md` の承認の箇条)は push については実装どおり成り立つ(`commit_id` と PR の先頭の照合、取得した先頭とイベントの先頭の照合)。取り下げは扱っていない。出荷の集約は最後の状態で照らすので事後には検出される
- 直し方の向き: 実装を変えるなら、取り下げのイベントを `pull_request_target` の契機では拾えないため、限界として ADR-0115 の「影響」か gate-g5-base.yml の限界のコメントに書く。G-7 で検出される旨を添える

### C-9 env-check の「満たす」が、gate-g5-base.yml の中身を見ていない(重大度: 低)

## 確かめて指摘の無かった項目

- ワークフローの安全性(gate-g5-base.yml)
  - `actions/checkout` は既定ブランチを取り出し、`persist-credentials: false`・`submodules: false`。PR の先頭は `git fetch --no-recurse-submodules` で取るだけで、check-pr.mjs は `--head` のとき `git show`・`git ls-tree`・`git diff` で読む。`analyzePr` の中で作業ツリーを読む箇所は `head` が無いときの分岐だけで、PR のファイルを `node` で実行・import する経路は見当たらない(E-11 の範囲。gitlink は未確認のまま、ADR に明記あり)
  - 依存の導入・アダプタ・手元の action・キャッシュ・成果物のアップロードは無い。秘密情報は `GITHUB_TOKEN` だけ
  - PR の題名・本文・作成者・ラベル・ブランチ名は、すべて `env:` を通して渡しており、`run:` への式展開は無い。`$GITHUB_OUTPUT` へ書く値は `jq -c` の1行の JSON で、改行を含まないため、固定の区切り文字でも注入の経路にならない
  - permissions は `contents: read`・`pull-requests: read`・`issues: read` で、使う API(PR のレビュー、issue の events、GraphQL のレビューの編集者)に要る範囲に収まる
  - 結果はジョブの結果(check run、名前 gate-g5-base)で出し、commit status を出さない(AR-1)。ルールセットの雛形4本と契約検査に gate-g5-base を足した
  - GitHub Security Lab の「Preventing pwn requests」の注意(PR の先頭を checkout しない、PR のコードを実行しない、式展開しない、書き込みの権限を与えない)は、ファイルの冒頭に禁止として書かれ、静的試験の変異で固定されている
- 承認の照合
  - `controlApprovalBacking` は、書き手ごとの最後の状態が承認のレビューを、`reviewerCheck`(名簿の数値の識別子・AI と bot の名義でない・作成者でない・書き手以外の編集なし・`commit_id` が PR の先頭)で照らす。ログイン名は理由の文に使うだけ。本文の記名は数えない
  - 承認の後の push: レビューの `commit_id` と PR の先頭の照合で失効し、取得した先頭とイベントの先頭が違えば失敗する(古い実行の再実行で通らない)
  - 1名の体制は `selfAttested` として集約に区別して出る(C-6 の留保つき)。向きに依らず掛け、依存の更新の bot の PR も対象(J-3 と合う)
- CONTROL_FILES に `.github/actions/**` と `.github/gate-node-version` が入った(R-2)。gate-g5-base が読む他の物(`scripts/gate/**`・`scripts/vendor/**`・`process.config.json` の閾値・`.claude/guard.json`)は既に入っている。名簿(`process.config.json` の seats・people)の変更は統制の設定に入っていないが、効力を持つ記録(D-0 の決定の記名、IMPL-0415・0431)として別に裏づけられており、抜けとは判断しない
- record-copy.yml: `pull_request_target` の `closed` へ移り、`if: merged` は既定ブランチの定義にある。checkout は既定ブランチで PR の先頭を取り出さない。PR の値は `env:` で渡す。60 行目の誤ったコメントは直った(AR-2)。書き込みは `contents: write` のリポジトリの全体だが、既定ブランチはルールセットが止め、記録用ブランチへの追記に絞る仕組み(ADR-0109)は変わっていない
- 効力を持つ記録の列挙(ADR-0106): 第1章 1.4 の表と第4章の効力を持つ記録の表の両方に、承認の記録を足した。env-check は `satisfied`・`unsatisfied`・`unconfirmed` の3値で、記録の無い・旧い記録は `unconfirmed` と読む
- 文の規約: EV-0233 は `:::caution[暫定 EV-0233 / 見直し 2027-05]` の書式で、対象・根拠の水準・差し替え条件がある。IMPL の書式は台帳の形に合う。内部リンクは `/process-compass/` を含む。適用範囲は見出しへ併記されている(「統制の設定の変更の承認(適用: 統制の設定を変える変更)」)
- ADR-0087: 差分はステータスの節への1段落の追記だけで、決定とコンテキストの本文は書き換えていない
- 裁定の各項の反映: R-1(性質で要求、判定の種類で分ける、例示に留める、採らない案)、R-2(判定のコードの1語、送り手の固定を適合の手段に数えない)、R-3(本人のレビュー、数値の識別子、2か所、列挙への追加、1名の自己申告、事前の同意の形)、R-4(#369 へ条件を渡す、ADR-0115、EV-0233)、AR-1〜AR-3 は本文に入っている。未反映は J-5・J-7・J-8(C-1〜C-3)
