## R-1 検査の読み元

### 推す案

**案(a) の限定形を要求事項にし、案(b3) を組にする**。案(e) を事後の検出として足す。

1. 要求事項(性質で書く。製品の機能を指定しない): **G-5 の判定のうち、変更のコードを実行しない部分(統制の設定の変更の検出、陰性の確認・「外した」の記録の照合、強制層の変更の承認の照合)の判定のコードと構成は、基底ブランチから読む。変更の側に含まれるコードと構成で判定する構成は、この規定を満たさない**。5.5.4 条件2 の箇条(`human-ai-boundary.md:449`)と同じ書き方に揃える
2. 統制の設定(`CONTROL_FILES`、`check-pr.mjs:328-333`)を変える変更には、AI維持管理者の席の責任者**本人の承認のレビュー**を、名簿の数値の識別子(ADR-0108)で照合して求める。照合は 1. の基底の側で行う(案(b3))
3. テスト・カバレッジ・静的解析など、変更のコードを実行する部分は変更の側で動かしてよい。その結果は「書き換えた定義で作られうる結果」として扱い、2. の承認で真正性を補う
4. 出荷の証跡の集約(G-7)が、範囲内で統制の設定を変えた変更を数え上げ、2. の承認の帰属が裏づかないものを欠落にする(案(e))。集約は、直前の出荷のタグの版の検査のコードで動かす。今回の範囲で集約そのものが変わっていれば、その差分を開示に出す

### 理由

- **自己承認の経路を閉じる仕組みは、読み元を基底に置くことでしか成り立たない**。判定のコードが基底にあれば、判定のコードを変える PR は、変える前の版(基底)の判定を受ける。基底の判定が 2. の承認を求める限り、検査を緩める PR は、緩める前の検査で AI維持管理者の承認を求められる。読み元が変更の側のままだと、照合をいくら足しても同じ PR で外せる(内部 5.6 末尾)。監査は、自分で外せる照合を統制に数えない
- 先例との一貫性。G-8(禁止)と 5.5.4(要求事項)は同じ論理で書かれている(Q4)。G-5 だけ置かないなら、その理由を書く義務がある。置かない理由を探したが、見つからなかった。G-5 の通過はマージの前に効き、事後に取り消せない(Q5 の区分で事前に効く側)。G-8・5.5.4 より弱く扱う根拠にならない
- ADR-0109 との違いを説明できる。ADR-0109 の対象は記録の置き場で、書き換えは G-7 の集約で欠落になり、出荷の前に止める機会がある。G-5 の書き換えは、マージを通した時点で効力を持つ。ADR-0106・0107 が事前に効く記録を事前に裏づける側へ置いたのと同じ区分で、G-5 の判定装置を防止の側へ置く。立場の不一致ではなく、同じ区分の適用である
- 規格の要求から導ける。SP 800-204D 5 の「制御面は個々のステップより高い信頼水準で動く」、5.1.1 の「証拠は … 開発者の管理下にない部品が … 生成する」、5.1.2 の「merge approval の権限を持つ開発者は自分のマージを承認できない」(外部 3.2)。SSDF PS.1.1 の configuration-as-code の保護と Example 4 の code owner の承認(外部 3.1)
- 個人所有・無償のプランで成り立つ。`pull_request_target` と、リポジトリ単位のルールセットの必須チェック・承認の要求は、個人の公開リポジトリでも使える(外部 1.1・1.7。〔外〕)。先例の `delegation.yml` が同じ構成をテンプレートの中で既に持つ(内部 2.1)。ただし `delegation.yml` 自身も実機で動かしていない(`delegation.yml:26`)
- 1名の体制でも 2. は成り立ちうる。担い手(AI)が専用の名義で PR を作り、人が承認する構成では、作成者と承認者が別になる(外部 4)。名義を共有する構成では成り立たず、ADR-0107 決定3 の「その人がいない体制では自己申告として受け付け、区別して開示する」に従う

### 条件と留保

- 基底の判定は、変更のファイルを**データとしてだけ**読む。`import`・実行・依存の導入・`./.github/actions/*` の実行・アダプタのコマンドを変更の側から行わない。題名・本文・ブランチ名を式展開しない。これを試験で固定する(内部 5.1、E-11)。未実証
- `permissions` はジョブ単位で最小にする。フォークからの PR の扱い(E-12)を採用者向けに書く
- 基底の判定が出すステータスが、ルールセットの必須チェックとして数えられることは未実証(E-4)。数えられない場合、1. は「必須でない表示」に落ち、統制に数えられない。その場合は R-2 の扱いに従って開示する
- 管理者がルールセットを外せることは、どの案でも残る。ADR-0109 決定5 の開示の項目1 にそのまま含める
- 3. の残余: 変更の側のテストそのもの(テストのファイル)を弱める変更は `CONTROL_FILES` に入らない。本件の範囲では扱わない。テストを弱める変更の扱いは既存の規定(実装の修正ループの書き込みの範囲)に依り、本件はその規定を変えない
- 効果(緩める変更が実際に止まる率)は測られていない。根拠水準マークを付ける(R-4)

## R-2 定義とスクリプトの2層と、送り手

### 推す案

1. **規定の文で2層を明示して両方を掛ける**。「判定のコードと構成」の「コード」は、ワークフローの定義(呼び出しの順序・`needs`・checkout の ref・実行する手順)と、定義が呼ぶ検査のスクリプト・アダプタの両方を指すと、用語の注記で書く。どちらか一方だけを基底から読む構成は満たさない、と明記する
2. 準拠テンプレートの `ship-evidence` の verify(スクリプトは基底、定義は変更の側。内部 2.1)を、1. を満たさない例として本文または手引きで名指しする。テンプレート自身の構成を「満たしている」と読める状態に置かない
3. **送り手**: 縛れないことを開示する。ルールセットの雛形の必須チェックに、送り手を GitHub Actions に限る指定(`integration_id`)を加える。これで止まるのは人・外部トークンの偽の status だけであり、ワークフローは区別しない、と雛形の README と開示の固定の文に書く
4. 同名のジョブによる偽装は、送り手の指定ではなく、R-1 の 2. で扱う。ワークフローを足す・変える PR は `.github/workflows/**` に触れ、`CONTROL_FILES` に当たる。基底の判定が AI維持管理者本人の承認を求めるので、偽装のジョブを足す PR は承認の経路を通る
5. 判定だけが持つ資格情報(専用の App の鍵)で必須チェックを出す形は、**要求事項にしない**。手段の例として書き、採用者が足すことは妨げない

### 理由

- 外部の3つの仕組み(ruleset workflows・pipeline execution policy・Prow)は、どれも定義だけを外へ置き、スクリプトの書き換えを塞がない。Prow の KEP-2291 が原文で認める(外部 2.4、4)。規定が「定義」とだけ書けば、採用者は定義を外に置いて満たしたと読む。監査は、満たしたと読める構成が実際には外せる状態を、最も危険な食い違いと見る。2層を文で分けて両方を掛けるのは、そのためである
- 2. は開示の正直さの問題である。テンプレートは標準に準拠する雛形として配られる。雛形の一部が規定を満たさないなら、雛形の側で黙っているより、名指しで書く方が読み手の誤読を防ぐ
- 3. の送り手の指定は、止める範囲が狭くても、人が手で status を立てる経路を塞ぐ。止める範囲を正直に書けば、過大な主張にならない。逆に、指定を足しただけで「送り手を縛った」と書く開示は不正直になる。外部 1.3 の推測(ワークフローを区別しない)は原文が限界を明記していない。これも未実証として書く
- 5. を要求事項にしない理由: 専用の App の鍵は新しい信頼の根になり、鍵の置き場の統制が別に要る。ADR-0109 は同じ理由で記録の置き場の専用の App を退けた(採らなかった案の1行目)。G-5 で採るなら ADR-0109 の理由との違いを示す必要があるが、R-1 の 2. で偽装の経路が承認の経路に乗るため、鍵を足す利得は「承認の経路の取りこぼし」に限られる。1〜2名の体制に鍵の管理を課す根拠を、いまは持たない

### 条件と留保

- 同名のジョブが2つの結果(基底の失敗と、変更の側の成功)を出したとき、ルールセットがどちらで判定するかは未実証(E-3)。基底の判定の失敗が勝たない場合、R-1 の 2. の承認は、承認者が表示に騙されないことに依る。この場合は、基底の判定が、変更の側のワークフローに必須チェックと同じ名前のジョブ・ステータスがあることをデータとして読み、PR へ明示の警告と失敗を出す。それでも区別できない残余は開示する
- 基底の判定の必須チェックの名前は、変更の側の `gate-g5` と別の名前にする。同じ名前だと、E-3 の結果に依らず、2つの結果が混ざって読めない。未実証
- 4. は `CONTROL_FILES` に `.github/workflows/**` が入っていることに依る。この一覧そのものも基底から読む(R-1 の 1.)。一覧を変更の側から読む構成は、一覧から外す PR で自己解除できる

## R-3 所有する組織の同意の記録(IMPL-0340)と AI維持管理者の記名

### 推す案

1. **強制層の変更の AI維持管理者の承認を、本人の操作で裏づける**。統制の設定を変える変更(向きに依らない)に、AI維持管理者の席の責任者本人の承認のレビューを、名簿の数値の識別子で照合して求める(R-1 の 2.)。本文の欄「受け入れた者」の名前の一致は、裏づけに数えない(ADR-0106 決定3 と同じ扱い)
2. **定義と列挙の食い違い(Q2)を、列挙の側の誤りとして直す**。「外した」の記録と、強制層の変更の承認を、第1章の効力を持つ記録の列挙へ加える。定義の文は正しく、列挙が書き落としていると判断する。列挙に加えれば、帰属の確認・名義の共有の扱い(ADR-0107 決定3)が自動で掛かる
3. 照合は**基底の判定**で行う(R-1 の 1.)。変更の側の pr-rules に照合を足すだけでは、IMPL-0340 を delivered にしない
4. **所有する組織の同意**: 機械が向きを判定できる変更に限り、同意を本人の操作で裏づける。対象は、結果「外した」の変更と、閾値を緩める向きに変える変更(数値の比較で向きが決まるもの)。所有する組織が指名した者の承認のレビューを、名簿の数値の識別子で照合する。同意が要るか(席の責任者と所有する組織の所属が違うか)は、テンプレ8 第9項の記録を人が読んで構成へ「同意の要否」と指名者の識別子だけを写し、所属そのものは写さない
5. 機械が向きを判定できない緩め(定義の書き換え、除外の追加の一部など)は、書き手の申告に残す。申告の欄を「止まった」と「緩めた」で分け、「緩めた」を選べる欄にする。申告であることを開示に出す
6. 事前の同意の置き場を様式で固定する(#317 突合 `crosscheck.md:54,58` の書き落とし)。置き場は、対象の PR の上の指名者本人のレビュー、または様式の記録に指名者本人の承認を付けたもの。ADR-0106 決定4 の受け皿と揃える

### 理由

- 監査の照合は「記名がある」ではなく「記名者が操作した」を確かめる。名前の一致だけの記名(Q1)は、PR の作成者が書ける。検査を緩める変更を、緩める者が AI維持管理者の名前で承認できる。これは自己承認の経路そのものである
- 2. を列挙の誤りと判断した理由: 第1章の定義は性質(合否を変える記録)で書かれ、列挙は「に限る」で閉じている。「受け入れた者」は記入の有無で pr-rules の合否を変える(`check-pr.mjs:375-385`)。性質に当たるものが列挙に無いのは、ADR-0106 が判定記録・例外承認の経路だけを見て列挙したためと読める(推測。ADR-0106 の記録に強制層の変更を論じた箇所は見当たらなかった)。定義を狭めて合わせる案は、性質の側を捨てる。列挙に足す
- 1. を向きに依らず課すのは、3.11.2 の承認の権限が強制層の変更(追加・削除・統合)を向きに依らず対象にしているためで、標準より厳しくならない(内部 1.1)。向きの判定を機械に求めないので、Q3 の「向きを書き手が選べる」穴も、承認の側で塞がる
- 4. を機械で判定できる向きに限る理由: 同意の要求は緩める向きだけに掛かる(ADR-0087 決定2)。全変更に同意を課すと標準より厳しくなる。向きを機械で決められない変更にまで課さない代わりに、決められる変更は確実に照合する。所属を構成へ写さない方針(ADR-0069 決定2、ADR-0087 の description)は、「要否」と「指名者の識別子」だけを写すことで保つ。所属は人が読む記録に残る
- 5. の欄の分け方は、自己申告を消せないことを前提に、申告の選択肢を正直にする。いまの様式は「止まった」「止まらなかった」「外した」で、緩めたが外していない変更を書く欄が無い。書く欄が無い申告は、正直な書き手にも「止まった」を選ばせる

## R-4 #369 との分担、実機の確認、記録

### 推す案

1. **分担案1 を推す**。#371 が「判定のコードと構成(指示を含む)は、判定される変更が書き換えられない版から読む」共通の規定と機構を決める。#369 は、その上で AI レビューの指示の読み元を実装する。統合(分担案3)はしない
2. **実機の確認は、状態を delivered に変える前の条件にする**。規定の文(性質の要求事項)は実機の結果を待たずに書けるが、降ろし先の state を delivered にすること、開示の固定の文を確定することは、少なくとも E-1・E-2・E-3・E-4・E-7・E-11 の結果の後にする。結果が出るまで、IMPL は undelivered のまま表示し続ける
3. 一時のリポジトリを作る確認は、外部への作用を含む。**実施するかは所有者が決める**。会議体と委員は実施を決めない。実施しない間は、該当の記述に根拠水準マークを付けて「実機で確かめていない」と書く
4. **新しい ADR を起こす**。内容: G-5 の判定のうち変更のコードを実行しない部分の読み元(R-1)、2層の明示(R-2)、強制層の変更の承認と同意の帰属(R-3)、効力を持つ記録の列挙への追加(ADR-0106・0109 を補う)、ADR-0109 との区分の説明(事前に効くか)、採らない案の一覧
5. EV・IMPL
   - EV: (i) 基底の判定と承認の組が、緩める変更を止める効果は測られていない、(ii) 送り手の指定がワークフローを区別しないこと、(iii) 基底の判定の必須チェックとしての扱い(E-3・E-4)。いずれも `:::caution[暫定 EV-NNNN / 見直し …]` で付ける
   - IMPL: R-1 の 1.・2.、R-3 の 2.・4.・6. に新しい実装マークを付け、undelivered で表示する。IMPL-0340 は、基底の判定で照合が動いて実機で確かめた後に限って delivered にする。変更の側の照合を足しただけで delivered にしない
   - IMPL-0333(#369)は、AI レビューのワークフローの定義も変更の側で動く限り undelivered のまま。#369 の受け入れ条件に「#371 の共通の機構の上で」を加える
6. 開示: 保証の開示の項目1 に、固定の文で次を出す。管理者がルールセットを外せること、送り手の指定がワークフローを区別しないこと、変更の側で動くテストの結果は書き換えた定義で作られうること、1名・共有の名義の体制での強制層の変更の承認が自己申告であること。どれも「確かめた / 適用されていない / 確かめていない」で出し分ける(ADR-0109 決定5 の形)

### 理由

- 分担案1: #369 の指示はデータ、#371 の判定はコードで機構が違う(内部 4.1)。しかし #369 の yml も変更の側で動く限り、「基底から読む」手順そのものを書き換えられる。#369 を先に降ろすと、附属書H H.4 条件3 の「書き換えられない保護」に届かないまま delivered と読まれる(内部 4.1)。共通の規定を先に置くのが、開示を正直に保つ順序である。統合しない理由は、合否への影響が違う(H.4 条件3 か、必須チェックか)ため、受け入れ条件と検査が混ざると、どちらが降りたかを読み手が区別できなくなるからである
- 2.: 監査は、実機で動かしていない統制を「降りた」と数えない。先例の `delegation.yml` は実機で確かめていないことをヘッダーに書いている(`delegation.yml:26`)。同じ扱いを続ける。規定の文を待たせない理由は、規定の要否は E の結果で変わらないためである。E-1 が「通らない」と出ても、変更の側で判定する構成の危うさは残る(定義の書き換え以外の経路、E-2)
- 3.: 委員は外部への作用を決める立場にない。所有者の判断を経ない実施は、記録と本人の操作の結び付きを、委員自身が崩すことになる
- 4.: G-5 に読み元の規定を置くことは、あとから変えにくい方針の決定であり、ADR-0106・0109 の決定を補う。採用済み ADR の本文は書き換えられない
- 6.: ADR-0109 決定5 と同じく、開示は決定と組で採る。開示だけで済ませる案は R-1 で退けた

## 要約

- R-1: G-5 のうちコードを実行しない判定(統制の変更の検出、陰性の確認と承認の照合)の読み元を基底ブランチに限る要求事項を置く。強制層の変更には、AI維持管理者本人の承認のレビューを名簿の識別子で照合して求める。G-7 の事後の検出を足す。(c) は例示にとどめ、(d) 単独・(g)・(h) は採らない
