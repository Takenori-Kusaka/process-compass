## 先に認める欠陥(弁護の範囲の外)

弁護の委員として、次の4点は欠陥と認める。今の構成を守る理由にならない。

2. **AI維持管理者の記名が本文のテキストである**。`removalProblems` は「受け入れた者」の欄の名前を構成の席の責任者と照らすだけで(`check-pr.mjs:372-388`)、本人の操作と結び付かない〔確〕。作成者が他人の名前を書けば通る。「AI維持管理者の承認」の看板と実態が食い違う
3. **結果を「止まった」と書けば、AI維持管理者の記名が要らない**。3.11.2 は AI維持管理者が「指示資産の変更(強制層の検査の追加・削除・統合を含む)」を承認すると定める(`roles-responsibilities.md:1328`)〔確〕。機械が記名を求めるのは結果「外した」のときだけで(`check-pr.mjs:351-389`)、緩める変更を「止まった」と申告すれば記名は不要になる〔確〕。標準の要求と機械の確認の範囲がずれている
4. **(内の調査に無い新しい指摘)`CONTROL_FILES` が、`gate-g5` が実行する複合アクションと Node の版のファイルを含まない**。`gate-g5.yml:185` は `./.github/actions/setup-stack` を、`:47`・`:66`・`:184` は `.github/gate-node-version` を使う〔確〕。`CONTROL_FILES`(`check-pr.mjs:328-333`)は `.github/workflows/**`・`.github/rulesets/**` を含むが、`.github/actions/**` と `.github/gate-node-version` を含まない〔確〕。`setup-stack` の中身を差し替える PR は、陰性の確認の節を求められない〔推。試験で確かめていない〕。CODEOWNERS の雛形の強制層の行にも `/.github/actions/` が無い(`CODEOWNERS:26-36`)〔確〕。どの案を採っても、強制層の範囲の列挙(3.11.3)と機械の対象の列挙の突き合わせが要る

以下の弁護は、この4点を直すことを前提にしている。

## R-1 検査の読み元

### 推す案

**要求は性質で書き、手段は (b) を既定、(a) を条件付きの選択肢とする**。具体的には次の形である。

- 要求事項(G-5 に新設): **強制層(検査の定義・検査のスクリプト・検査の動作環境・閾値と除外設定)を変える変更を、その変更自身が書き換えた検査の合格だけで取り込んではならない**。取り込みの前に、次のどちらかを要する
  - (b) 強制層の所有者の本人の操作による承認。ホスティングが取り込みの条件として強制し、承認の後の push で失効するもの
  - (a)/(c) 判定される変更が書き換えられない場所の定義とコードで行う判定
- 準拠テンプレートの既定は (b)。CODEOWNERS の強制層の行を有効にした雛形と、`require_code_owner_review`・`require_last_push_approval`・`dismiss_stale_reviews_on_push` を全構成で true にする
- (f)(基底の側で、PR のコードを実行せずに「この PR の gate-g5 は書き換えた定義で動いている」を出す必須でない通知)を、(b) の承認者の判断材料として足す
- どちらも満たせない構成(1名で、行為する AI と人が同じアカウントを使う場合、個人所有で private かつ無償のプランの場合など)は、ADR-0090 決定2 の区分(手段が無い / 手段はあるが使わないと決めた)で**未達として開示**する。省略にしない

### 理由

- **防ぐべきものは「書き換えた検査で通ること」そのものではなく、「書き換えを人が見ずに取り込むこと」である**。G-5 の全体を基底へ移すことはできない。テスト・カバレッジ・静的解析は PR の製品コードを実行することが目的である(内 5.1)〔確〕。PR の側で動く判定は、どの案でも残る。残る以上、強制層の書き換えを止める最後の層は、取り込みの前の人の承認になる。外の調査でも、個人所有のリポジトリで使える GitHub 標準の手段は人による統制(code owner のレビュー、最新の push の承認)だけである(外 4)〔確〕
- **(b) はホスティングが基底の側で強制する**。必須のレビューの判定は、ワークフローの定義にもスクリプトにも依らない。ADR-0109 決定5 が開示に出すのと同じ「管理者はルールセットを外せる」の残余は残るが、PR の作成者は外せない〔推〕。ただし、コード所有者の判定に PR の基底の側の CODEOWNERS が使われることは**未実証**(E-7、外 1.5 も原文未確認)
- **規格の要求に合う**。SSDF PS.1.1 Example 4 は configuration-as-code の変更に code owner のレビューと承認を例示する(外 3.1)。SP 800-204D 5.1.2 は「merge approval の権限を持つ開発者は自分のマージを承認できない」と書く(外 3.2)。OpenSSF Scorecard の上位の段は code owner のレビューと最新の push の承認で、CI の定義を基底から読む型は評価の軸に無い(外 2.1)。ruleset workflows・pipeline execution policy は、いずれも最上位の有償プランに限られる(外 1.4・2.5)
- **本標準のロール分離に接続する**。行為する AI のアカウントが push し、人が承認する形なら、「push した者 ≠ 承認した者」が1名の体制でも成り立つ(外 4)〔推〕。AI の担い手のアカウントの区別は ADR-0107 の系統で既に扱っている

### 他の案を落とす理由

- **(a) を要求事項の唯一の形にすることは採らない**(選択肢としては残す)。理由は4つ
  1. **送り手の問題が解けない**。基底の判定が `GITHUB_TOKEN` で出すチェックと、PR が足したワークフローの同名のジョブが出すチェックは、送り手(GitHub Actions の App)が同じになる(内 5.1、外 1.3)〔推〕。`integration_id` を GitHub Actions に固定しても区別できない。区別には判定だけが持つ専用の App の鍵が要る。**送り手を解かない (a) は、必須チェックを偽装できる穴を残したまま「基底から読んでいる」と読ませる**。これは今の構成より読み手を誤らせる。E-3 の結果が出るまで、(a) の効果は**未実証**
  2. **攻撃面を足す**。`pull_request_target` は書き込みの権限を持つトークンと秘密情報に届く(外 1.1・1.2)。今の `gate-g5.yml` は全体で `pull-requests: write` を宣言している(`gate-g5.yml:28-30`)〔確〕。判定のジョブを `pull_request_target` へ移すと、同じ権限が既定ブランチの文脈で、フォークの PR にも渡る(E-12)。分割を誤って PR の先頭を checkout し、`npm ci`・`./.github/actions/setup-stack`・アダプタのコマンドを1つでも実行すれば、pwn request になる(外 1.2)。Scorecard は Dangerous-Workflow を Critical に置く(外 2.1)
  3. **複雑さが誤設定を生む**。(a) の現実的な形は「基底の判定(`pull_request_target`)+ PR の側の実行(`pull_request`)+ 集約(`workflow_run`)」の3つの経路である(内 5.1)。`workflow_run` は PR が作れる成果物を読み、パスの検証と隔離が要る。この構成を雛形として配り、採用者が自分のスタックに合わせて書き換える。書き換えのたびに、上の 2. の条件を崩す機会が生じる。**先例の `delegation.yml` も、実際の GitHub 上で実行して確かめていない**(`delegation.yml:26-28`)〔確〕。先例を根拠に同じ形を必須の検査へ広げるのは、未検証の形を2つに増やすことである
  4. **安全を守る試験が、守られる側で動く**。`delegation.yml` が PR の先頭を checkout しないことを確かめる試験(`test-check-delegation.mjs:245-254`)は、`gate-g5` の中、すなわち PR の側で動く(内 2.1)〔確〕。(a) の「PR のコードを実行しない」を試験で固定しても、その試験を同じ PR で外せる。結局、試験を外す変更を止めるのは (b) の承認である
- **(c) ruleset workflows を要求事項にすることは採らない**(例示に留める)。組織・Enterprise の機能で、個人所有のリポジトリでは使えない(外 1.4)。標準は製品の機能を指定しない書き方を採っている(内 5.3)。さらに、定義を外へ出しても、定義が PR の側の `scripts/gate/` を呼ぶ限りスクリプトの書き換えは効く(Prow KEP-2291、外 2.4)。(c) は要求事項の (a)/(c) の側を満たす手段の1つとして書く
- **(d) 開示だけは採らない**。ADR-0109 自身が「開示は決定1〜4 と組で採る。開示だけでは数え方が変わらない」と書く(ADR-0109 `:71`)〔確〕。3.11.3 の「遵守が必須の規則を誘導層に書いてはならない」にも反する(内 5.4)。今の構成を弁護する立場でも、開示だけで足りるとは言えない
- **(g) push のパスの制限は採らない**。bypass actor を既定ブランチに置かないという雛形の決定(`rulesets/README.md:37,97`)〔確〕と衝突する。AI維持管理者を bypass に置けば、管理者が承認なしに強制層を変えられる経路を新しく作る。プランの条件も残る(E-10)
- **(h) マージのキューは採らない**。定義は合成コミット(PR の変更を含む)から読まれるため、本件を解かない(内 5.5)〔推〕
- **(i) スクリプトを固定した版から読む案を単独では採らない**。yml が PR の側に残るため、読み元の指定そのものを書き換えられる(内 5.5)〔推〕

### 条件と留保

- (b) を既定にする前提は E-7(PR の基底の CODEOWNERS が使われるか)である。**未実証**。PR の側の CODEOWNERS が使われるなら、(b1) は自己解除でき、(b2) パス単位の必須レビュアー(E-8)へ寄せる必要がある
- (b) の効果、すなわち承認者が強制層の差分を実際に読んで緩みを見つける割合は測られていない。**未実証**。暫定マーク(EV)で開示する。G-5 の陰性の確認(`gate-criteria.md:757`)と同じ根拠水準である
- (b) は「gate-g5 が通過と表示される」状態を残す。承認者が表示を信じる危険を、(f) の通知で下げる。(f) は `pull_request_target` で動くが、PR の先頭を checkout せず、API で差分のパスだけを読み、権限は `pull-requests: write` と `statuses: write` に限る。この条件を満たせないなら (f) も採らない(E-11・E-12 で確かめる)
- (a) を選んだ採用者には、条件を要求事項として課す: PR のコードを作業ツリーへ取り出して実行しない / PR の先頭のファイルは `git show` か API でデータとしてだけ読む / ジョブごとに権限を最小にし、秘密情報を参照しない / 必須チェックの送り手を判定だけが持つ資格情報に結び付ける。**最後の条件を満たさない (a) は、要求事項の (a)/(c) の側を満たしたと数えない**
- 1名の体制で (b) を満たすには、行為する AI が人と別のアカウントで push することが要る。同じアカウントなら未達として開示する。第4章 G-5 の1名の行(IMPL-0238、`gate-criteria.md:1298`)の「取り込みそのものを止めることは求めない」との関係を突合で確かめる。私の見解は、1名の行は変更の要求を経ない体制の規定であり、変更の要求を経る体制での強制層の承認とは別の場面である〔推〕

## R-2 定義とスクリプトの2層と、送り手

### 推す案

- **条項では2層を分けず、「強制層を変える変更」として一体で扱う**。分けるのは手段の側の注記だけにする。R-1 の要求事項の括弧の中に、定義(ワークフローのファイル)・スクリプト(`scripts/gate/**`)・動作環境(複合アクション・道具の版の固定・アダプタ)を列挙する
- **手段の注記として、「定義だけを外へ出す手段は、スクリプトを外へ出さない限り要求事項を満たさない」を明記する**。ruleset workflows・pipeline execution policy・中央のジョブ定義を例示するとき、必ずこの限定を同じ行に書く
- **送り手(`integration_id`)は、固定を要求しない。確かめていないことを開示し続ける**。今の手引き(`template-repository.md:130`。内 1.5)の「確かめていないことを記録に書く。固定するかは、実際の GitHub 上で確かめてから決める」を維持する。E-3 の結果で見直す
- R-1 の欠陥4 を受け、`CONTROL_FILES` と CODEOWNERS の強制層の行に `.github/actions/**` と `.github/gate-node-version` を足す。以後、ワークフローが参照するローカルのファイル(`uses: ./...`、`*-file:`)が `CONTROL_FILES` に入っていることを、契約検査で確かめる

### 理由

- **今の構成では、2層の露出は同じである**。`pull_request` では定義もスクリプトも PR の側で動く(内 2.1)〔確〕。片方だけを守っても、もう片方で外せる。承認の要求(R-1 の (b))は差分のパスで掛かるため、2層を同じ強さで覆う。分けて書く必要が生じるのは、定義だけを外へ出す手段を採る場合だけである
- **2層を条項で分けると、片方だけで適合を主張させる**。外の調査は、ruleset workflows・GitLab・Prow のいずれも、定義が PR の側のスクリプトを呼ぶ限りスクリプトの書き換えを防がないと整理した(外 4、Prow KEP-2291 の原文)〔確〕。条項が「定義を書き換えられない場所に置く」とだけ書けば、組織のルールセットで定義を固定した採用者が、スクリプトを PR の側で動かしたまま適合を主張できる。信頼性の点で、これは今の構成より悪い。今の構成は少なくとも、何も防いでいないことが読める
- **層は2つでは足りない**。欠陥4 のとおり、定義とスクリプトの間に「定義が呼ぶ動作環境」(複合アクション、Node の版、`package.json` の `check`、アダプタ)がある。`gate-g5.yml:185` の `setup-stack` はその例である〔確〕。2層と書けば3つ目を落とす。列挙で書き、列挙と機械の対象を突き合わせる検査を置く方が漏れが出にくい
- **送り手の固定は、本件の穴を塞がない**。送り手を GitHub Actions に固定して止まるのは、人や外部のトークンが出す偽の status だけである(外 1.3)〔推。原文は限界を明記しない〕。PR の書き手は、送り手を偽るまでもなく、yml を書き換えれば同じ App から成功を出せる。固定は本件と別の脅威(外部の統合の名前の衝突)への対策である
- **送り手の固定の誤りは、取り込みを全面的に止める**。`integration_id` を誤った App の識別子にすれば、正しい `gate-g5` も数えられず、全 PR が止まる〔推〕。止まる向きなので安全側ではあるが、採用者は止まりを解くために管理者の bypass を使い、その操作が恒常化する危険がある〔推〕。実機で値を確かめていない固定を雛形に書くことは、誤設定の雛形を配ることになる

### 他の案を落とす理由

- **2層を別々の条項にする案は採らない**。上の「片方だけで適合を主張させる」による
- **送り手を GitHub Actions の App に固定することを要求事項にする案は採らない**。本件の穴を塞がず、雛形の誤設定の危険を足す。E-3 で「固定すれば外部の統合の偽装が止まり、誤設定の危険が小さい」と確かめられたら、任意の強化として雛形に書く
- **判定だけが持つ専用の App で送り手を区別する案を、既定にすることは採らない**。R-1 の (a) を選んだ採用者の条件としてだけ課す。App の鍵の保管は ADR-0090 の (a) の形(配備を許す参照に限った Environment の秘密情報)を要し、鍵の漏えい・期限切れ・権限の過大という新しい失敗の形を足す〔推〕。(b) を既定にする構成では、送り手が偽られても取り込みには人の承認が要るため、送り手の区別の価値は小さい

### 条件と留保

- 「(b) を既定にすれば送り手の区別の価値は小さい」は、(b) が強制層の差分に必ず掛かる場合に限る。強制層に触れない PR で、同名のジョブを足すワークフロー(`.github/workflows/**` の新しいファイル)は強制層の変更に当たるので (b) に掛かる〔推〕。外部の統合が出す偽の status は (b) に掛からない。後者の重みは E-3 で確かめる。**未実証**
- 「ワークフローが参照するローカルのファイルを契約検査で確かめる」検査も PR の側で動く。この検査を外す変更は `scripts/gate/**` の変更であり、(b) で止まる。検査が単独で防ぐのではなく、承認者に見落としを残さないための列挙の補助として置く

## R-3 所有する組織の同意の記録(IMPL-0340)と AI維持管理者の記名

### 推す案

- **AI維持管理者の承認は、本文の欄から本人の操作(PR の承認のレビュー)へ移す**。強制層を変える変更すべてに掛ける。結果「止まった」「外した」で区別しない(R-1 の欠陥3 を直す)
- **確かめる場所は2つに分ける**
  - 取り込みの前(防止): ホスティングが強制するコード所有者のレビュー(R-1 の (b))。強制層のパスの所有者を AI維持管理者の席(のチーム)にする
  - 出荷の前(検出): G-7 の集約が、前回の出荷より後に強制層を変えた PR を数え上げ、AI維持管理者の席の責任者の承認のレビューが名簿の数値の識別子(ADR-0108)で付いているかを、record-copy の写しとホスティングの記録で照らす。欠ければ欠落にする(内 5.5 の (e))。ADR-0109 の「検出で扱う」と同じ立場である
- **pr-rules(PR の側)の本文の欄の照合は残す**。ただし判定に数えず、作成者の記入の誤りを早く知らせる補助と位置づける。照合の結果を「承認を確かめた」と表示しない
- **所有する組織の同意(IMPL-0340)は、構成に席の組織を持たせないまま、所有する組織がホスティングの規則で強制する形を「事前の同意」の機械の確認として認める**。所有する組織が強制層のパスに自組織の指名者の必須レビューを置けば、指名者の承認が取り込みの条件になる(内 5.2)。この場合、同意は全ての向きの変更に掛かる。標準(緩める向きに限る)より厳しい側であり、標準が禁じるものではない
- 「事後の提出」と、所有する組織がホスティングの規則を置かない構成では、機械は確かめない。IMPL-0340 は `state=undelivered` のまま、note を「事前の同意をホスティングの規則で強制する構成を除き、適用の有無と同意の記録は AI-SLA 合意確認書から人が読む」に改める

### 理由

- **本文の欄は、誰でも書ける**(R-1 の欠陥2)〔確〕。ADR-0106 は効力を持つ記録に「効力を持つ前に記名者本人の操作で帰属を裏づける」を課し、ADR-0109 決定3 は署名の無い author の一致を帰属に数えないとした(ADR-0109 `:15`・`:61`)〔確〕。強制層の承認はそれらと同じく、取り込みの効力を左右する記名である。テキストの名前の一致に留める理由が無い
- **確かめる場所を PR の側に置けば、同じ PR で外せる**。照合を pr-rules へ足しても、`check-pr.mjs` を書き換えれば外れる(内 5.6)〔確〕。だから防止はホスティングの規則に置き、PR の側の照合は補助に下げる。ここは今の構成の弁護を取り下げる。今の構成(PR の側の検査 + 本文の記名)は、記名の照合について信頼できない
- **検出を G-7 の集約に置く理由**: 取り込みの前の防止は管理者の bypass と E-7 の結果に依る(R-1)。防止が外れた場合の後ろ盾が要る。集約は承認のレビューの写し(ADR-0070・0109)を材料に持ち、新しい材料を要しない(内 5.5)〔確〕
- **向きを機械で判定しない**。緩める向きかどうかは、閾値の数値なら判定できるが、スクリプトの書き換え・ワークフローの手順の削除では判定できない〔推〕。判定できない部分を人の申告に残せば、今の「止まった」の自己申告と同じ穴になる。全ての向きに承認を掛ける方が穴が無い。3.11.2 は向きに依らず AI維持管理者の承認を求めているため、標準とも合う(`roles-responsibilities.md:1328`)〔確〕
- **構成に席の組織を持たせない**。ADR-0069 決定2・ADR-0087 は構成へ写さないことを採った(内 1.4・5.6)。所有する組織がホスティングの規則で強制する形なら、この方針を変えずに事前の同意を機械で強制できる

### 他の案を落とす理由

- **pr-rules に所有する組織の同意の欄と照合を足して IMPL-0340 を delivered にする案は採らない**。同じ PR で外せる照合を「降りた」と表示することになり、未達の表示より読み手を誤らせる。さらに、同意が要るか(所属が異なるか)を構成が知らない(ADR-0069 決定2)〔確〕
- **構成に席の組織を持たせて同意の要否を機械で判定する案は採らない**。ADR-0087 の決定を覆す理由が本件から出てこない。ホスティングの規則による強制で足りる
- **同意を緩める向きに限って機械で求める案は採らない**。向きを機械で判定できない(上記)
- **承認のレビューを防止の側だけで確かめ、G-7 の検出を置かない案は採らない**。管理者の bypass と E-7 の結果に依存する1層だけになる
- **G-7 の検出だけを置き、防止を置かない案(ADR-0109 の立場をそのまま広げる案)は採らない**。ADR-0109 の判定記録は G-7 で集約する事後の記録だった(ADR-0109 `:103`)〔確〕。強制層の変更は、取り込んだ時点から以後の全ての PR の判定を変える。事前に効く対象であり、ADR-0109 自身が事前に効く読み手を決定4 で別に扱ったのと同じ区分に当たる〔推〕

### 条件と留保

- **G-7 の検出は、集約自身を緩める変更に弱い**。集約(`aggregate-evidence.mjs`)は `scripts/gate/` にあり、タグの時点の定義で動く(内 5.5)〔確〕。集約を緩める PR が承認なしに入れば、検出も外れる。対策として、集約が強制層の差分のファイルの一覧を、開示に定型の文で常に出す(検出が外れても、変えたことは読める)。集約を前回の出荷の版で動かす案は、正当な集約の改善を次の出荷まで効かせない副作用があり、私は推さない〔推〕
- 承認のレビューを名簿の数値の識別子で照らす前提は、名簿の識別子が正しいことである(ADR-0108)。名簿そのものの書き換えは構成の変更であり、別の経路で扱われている
- 1名の体制では、作成者と AI維持管理者が同じ人なら、承認のレビューを付けられない(作成者は自分の PR を承認できない。外 1.5)。行為する AI が別のアカウントで PR を作り、人が承認する形なら成り立つ〔推〕。成り立たない構成は、G-7 の検出で「承認なし」として件数を開示し、未達とする。欠落にして出荷を恒久的に止めるかは、ADR-0109 の例外承認の受け皿(`:51`)と同じ扱いを推す
- 所有する組織のホスティングの規則による事前の同意の効果は**未実証**(EV-0177 の E0 を引き継ぐ)

## R-4 #369 との分担、実機の確認、記録

### 推す案

- **#369 との分担は分担案1(内 4.1)**。#371 が「強制層(AI レビューの指示の置き場を含む)を変える変更は、その変更自身が書き換えた検査・指示だけで取り込まない」と、その手段(R-1 の (b) を既定)を決める。#369 は、その上で AI レビューの指示を基底から `git show origin/<base>:<path>` などで読む形を実装する
- **#369 を #371 へ統合しない**(分担案3 を採らない)。分担案2(#369 を先に降ろし、yml の書き換えの残余は #371 の側で開示する)も採らない

- **一時のリポジトリの作成は、外部への作用を含むため、利用者の承認を得てから行う**。作業の主体(このワークフローの委員や議長)は、承認なしに作らない。作った場合は確かめた後に削除し、作成・削除の日と結果を記録に残す(メモリ「pit-in-trial-repo」の手順)
- **新しい ADR を1つ起こす**。ADR-0087 の G-5 の行「置き先を持たない。強制層を所有する組織の CI で判定する」(ADR-0087 `:52`)は維持し、「所有する組織の CI で判定する」だけでは同じ PR の書き換えを止めないことを、新しい ADR で補う(置き換えではなく補う)

  - IMPL: G-5 の新しい要求事項(強制層の変更の承認をホスティングで強制)、G-7 の集約の承認のレビューの照合、`CONTROL_FILES` の範囲と契約検査の突き合わせ。IMPL-0340 の note の改め(R-3)。実機で確かめるまでは `state=undelivered` で表示し続ける

### 理由

- **分担案1**: #369 の yml も `pull_request` で動く限り、「基底から読む」手順そのものを PR が書き換えられる(内 4.1)〔推〕。H.4 条件3 の「書き換えられない保護の下にあること(その設定の変更に AI維持管理者の承認を要すること)」(`assurance-case.md:336`)を満たすのは、#371 の承認の仕組みである。#369 の実装だけでは届かない
- **統合しない理由**: 機構が違う。指示はデータで、基底から読んでも PR のコードを実行しない(内 4.1)。#369 は `pull_request_target` を要さずに実装でき、#371 の結論を待たずに試験を書ける。統合すると、この安全な部分が #371 の未決の論点(送り手、実機の確認)の待ちに巻き込まれる。トリアージ(`triage-370-401.md:78-84`)の「重複とはしない」とも合う
- **分担案2 を採らない理由**: 開示だけで #369 を delivered にすると、H.4 条件3 が成り立ったように読ませる。R-1 で (d) 開示だけを落としたのと同じ理由である
- **実機を先に行う理由**: 本件の主張そのもの(書き換えた yml で gate-g5 が通る)が実機で確かめられていない(E-1、#379 の実機未確認1)〔確〕。R-1 で (b) を既定にする前提(E-7)、(a) を落とす理由の1つ(E-3)も**未実証**である。前提を確かめずに条項を書けば、ADR-0070 決定7 の「実機で確かめてから降ろします」が閉じないまま残った経緯(ADR-0109 `:23`)を繰り返す。確かめられない項目は、EV で未実証と開示したうえで決める
- **新しい ADR で補う理由**: ADR-0087 の G-5 の行は「人の判定者がいない機械のゲートのため」置き先を持たないとした。この理由は今も正しい。足りないのは「その CI が同じ PR で書き換えられる」ことへの手当てで、#317 の会議体(`council-03-qa-audit.md:12,70`)が指摘し本件へ送った論点である(内 1.3)〔確〕。採用済み ADR の本文は書き換えない

### 他の案を落とす理由
