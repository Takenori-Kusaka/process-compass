# #371 会議体 委員の意見: 現場(個人所有・無償のプランを含む GitHub の採用者)

- 日付: 2026-11-05
- 立場: 個人所有のリポジトリ・無償のプランを含む採用者。設定の手数、ワークフローの複雑さ、`pull_request_target` の運用の危険を重く見る
- 入力: `council-00-agenda.md`、`survey-371-1-internal.md`(以下「内部」)、`survey-371-2-external.md`(以下「外部」)、`template/.github/workflows/delegation.yml`・`gate-g5.yml`、第4章 `gate-criteria.md`
- 判断軸は信頼性。変更量の少なさを理由にしない。実証の無い前提には「未実証」と書く

## 現場から見た前提(全 R に共通)

1. **個人所有・無償のプランで使える機械の層は、リポジトリ単位のルールセット(必須チェック・送り手の指定・コード所有者のレビュー・最新の push の承認)まで**(外部 1.7、`:99-104`)。ruleset workflows は組織・Enterprise の機能で、個人所有では使えない(外部 1.4、`:57,71,74`)
2. **個人所有の private リポジトリを Free で運用する採用者には、そもそも必須チェックもブランチ保護も掛からない**(外部 1.7 `:100`。保護ブランチ等は private では Pro / Team 以上)。この採用者では `gate-g5` は「必須」でなく、本件の穴より手前で強制層が成立していない。本件の結論は、この採用者に新しい防止を与えられない。開示の対象として扱う(未実証: 現行の料金表の目視確認は外部調査の穴 3 に残る)
3. 1名の体制では、GitHub は作成者自身の承認を数えない(内部 5.2 `:213`、外部 1.5 `:87`、1.6 `:95`)。人による統制の層(案 b)は、1名の体制では機械の上で成立しない
4. 本テンプレートで唯一基底から読む `delegation.yml` は、実際の GitHub 上で実行して確かめていない(内部 `:110`、`delegation.yml:26`)。**基底から読む構成の運用の実績は、本プロジェクトの中にまだ無い**(未実証)

## R-1 検査の読み元

### 推す案

**案(a) を、PR のコードを実行しない判定に限って採り、案(f)(書き換えの検出の表示)を同じジョブに含める。案(b) は2名以上の体制の追加の層として求める。** 具体的には次のとおり。

- 要求事項は性質で書く: 「G-5 の判定のうち、PR のコードを実行せずに行える判定(差分のパス・PR 本文・統制の設定の変更の検出・陰性の確認と記名の照合・契約検査)は、判定のコード(定義と検査のスクリプト)を基底ブランチから読む。変更の側から読まない」。5.5.4 の委任の経路の要求事項2(内部 `:51`)、G-8(内部 `:50`)と同じ形に揃える
- 製品のコードを実行する判定(テスト・カバレッジ・静的解析・秘密情報の走査)は `pull_request` のまま PR の側に残す。その結果は、PR が統制の設定を変えた場合に「書き換えた定義で作られた結果」として表示する(内部 5.1 `:180-184`)
- 製品の機能は例示に留める(内部 `:226` の既存の書き方)。テンプレートの実装の例は `pull_request_target`(または `workflow_run`)で、PR の先頭を checkout しない

### 理由

- **採用者の全員が使える手段はこれしか無い**。`pull_request_target` はどのプランでも使え(内部 `:197`)、個人所有の public リポジトリでも成り立つ。案(c) は個人所有で使えない(外部 `:74`)。案(b) は1名の体制で成り立たない(前提 3)。全体制に掛かる防止の手段は (a) だけである
- 先例との不揃いを解く。委任の経路は「判定のコードを基底から読む」を要求事項に置き(`delegation.yml:34-38,75,115`)、G-5 には無い(内部 `:54`)。同じ PR で緩められる判定は、必須の看板と実態が食い違う(3.11.3 の「遵守が必須の規則を誘導層に書いてはならない」。内部 `:234`)
- データはすでに基底から読んでいる(`--policy-base`、ADR-0078。内部 `:106`)。コードを基底へ揃えると、現場の運用者にとって「判定の材料も手順も main のもの」という1つの説明で済む。半分だけ基底という現状は、運用者が誤解しやすい
- SP 800-204D の「制御面は個々のステップより高い信頼水準で動く」(外部 `:206`)、SSDF PS.1.1(外部 `:194`)と向きが合う

### 現場として付ける条件

1. **`pull_request_target` の危険の封じ込めを、要求事項と試験で固定する**。Security Lab が名指しで危険とする形(信頼できない PR の checkout)を作らない(外部 `:36`)
   - PR の先頭を checkout しない。PR の側のファイルは API か `git show` でデータとして読むだけにする。依存の導入・アダプタのコマンド・`./.github/actions/setup-stack` を走らせない(内部 `:190`)
   - `permissions` はジョブ単位で最小(`contents: read`・`pull-requests: read`・状態を出す権限だけ)。秘密情報を渡さない
   - PR の題名・本文・ブランチ名を式展開しない。`env:` で渡す(内部 `:191`)
   - これらを試験で固定する(`test-check-delegation.mjs:245-254` と同じ型)。ただしその試験も PR の側で動く点は R-2 で扱う
   - 条件を満たすかは、実機で確かめるまで未実証(E-11・E-12)
2. **テンプレートの更新(`npm run template:kb` の複製、上流の pit-in-template の取り込み)で、基底の判定が新しい形式を読めずに偽の失敗を出す経路を、手順として用意する**。基底の判定で、判定のコードを更新する PR を判定するのは本件の狙いどおりである。ただし形式の変更(構成の欄の追加など)を基底の古いコードが拒むと、採用者は更新を取り込めなくなる。この経路が無いと、現場は基底の判定を外す方向へ流れる(未実証: 頻度は測っていない)
   - 求めるもの: 基底の判定は、読めない形式を「失敗」ではなく「判定のコードの更新を含む。AI維持管理者の承認(R-3)を要する」と表示する。黙って通さない
3. **初回の設定(基底に判定のファイルが無い)を扱う**。現行の check-pr は基底に無いファイルを対象外にする(内部 `:131`)。基底の判定を導入する最初の PR は、基底の判定なしで入る。これは避けられない。初回であることを記録と開示に出す
4. 状態を出す名前は、`gate-g5` と別の名前にし、ルールセットの雛形の必須チェックに足す。雛形を適用する採用者の手数は、名前を1つ足すだけで増えない(雛形の JSON を適用する手順は既存)

### 他の案を落とす理由

- **案(c) ruleset workflows: 要求事項としては採らない。例示として書く**。個人所有のリポジトリで使えない(外部 `:74`)。プランの要件も実質 Enterprise と読める(外部 `:75`、未確認)。使える採用者には (a) より強いが、定義が外にあっても PR の側のスクリプトを呼べば層 B は残る(外部 `:76`)。中央のワークフローのリポジトリを要する形は、単一リポジトリの雛形という準拠テンプレートの形を変える(内部 `:225`)。ADR-0090 の未達の区分(手段が無い / 手段はあるが使わないと決めた)で、個人所有の採用者には「手段が無い」として開示する
- **案(b) 別の必須の承認: 単独では採らない。2名以上の体制の追加の層として求める**。1名の体制で成り立たない(前提 3)。また (b) だけでは、書き換えた `gate-g5` が「通過」と表示されたまま承認者に届く(内部 `:214`)。承認者が表示を信じずに差分を読むことを、現場は期待できない(未実証)。(a)(f) の表示と組で初めて、承認の判断材料がそろう
  - (b1) CODEOWNERS の強制層の行を有効にする件は #358 と重なる(内部 `:207`)。現場としては、雛形のコメントの行を `/process-init` で実在のアカウントへ置き換える手数は小さいと見る。ただし CODEOWNERS の判定が基底の側で行われるかは未確認(E-7、外部 `:86`)
- **案(d) 開示だけ: 採らない**。ADR-0109 の開示は、G-7 の集約での欠落の検出と組で採った(内部 `:233`)。G-5 の書き換えを後で検出する仕組みは無い。開示だけでは数え方が変わらない。ただし、(a) でも塞げない残り(前提 2 の private の Free、R-2 の送り手、1名の体制)は開示する
- **案(g) push のパスの制限: 採らない**。bypass actor を置かない雛形の決定(`rulesets/README.md:37,97`)と衝突し、個人所有では bypass のリストに人を置けない(外部 `:102`)。1名の体制では本人が書き換えを行う唯一の人であり、運用できない。プランの条件も未確認(E-10)
- **案(h) マージのキュー: 採らない**。合成のコミットから定義を読むので、本件を解かない(内部 `:245`)。採らないことを記録する
- **案(i) 固定した版のスクリプト: 単独では採らない**。yml が PR の側なら、読み元の指定を書き換えられる(内部 `:246`)。(a) の中で基底を読むなら不要

### 留保

- (a) で塞げるのは「PR のコードを実行しない判定」だけである。テスト・カバレッジの結果は、統制の設定を変えた PR では PR の側の定義で作られる。これは塞げず、表示と開示で扱う
- `delegation.yml` を含め、基底から読む構成の実機の確認が無い。要求事項の採否はいま決めてよいが、テンプレートの実装は E-1・E-3・E-4・E-11・E-12 を確かめるまで `state=undelivered` として表示し続ける(R-4)

## R-2 定義とスクリプトの2層と、送り手

### 推す案

1. **層 A(定義)と層 B(スクリプト)を、要求事項の上では「判定のコード」として1つに扱う**。基底から読むものは、定義とスクリプトの両方とする。定義だけを基底へ移し、スクリプトを PR の側から呼ぶ形は、要求事項を満たさないと明記する
2. **開示と表示の上では2層を分けて書く**。採用者の構成ごとに、どの層が塞がり、どの層が残るかを表で出す(下表)
3. **送り手は、機械で縛ることを要求しない。開示し、G-7 の事後の照合で補う**。専用の GitHub App による固定は、手段として例示する

| 構成 | 層 A(定義) | 層 B(スクリプト) | 同名の状態による偽装 |
| --- | --- | --- | --- |
| 現行(`pull_request` だけ) | 残る | 残る | 残る |
| (a) を採った後、GITHUB_TOKEN で状態を出す | 判定の範囲では塞ぐ | 判定の範囲では塞ぐ | 残る(未実証) |
| (a) に専用の App と `integration_id` の固定を足す | 塞ぐ | 塞ぐ | 塞ぐ(未実証) |
| (c) ruleset workflows(組織・Enterprise) | 塞ぐ | PR の側のスクリプトを呼ぶなら残る | 生じにくい(未確認) |
| テスト・カバレッジ(どの構成でも PR の側) | 残る | 残る | — |

### 理由

- 2層を1つに扱う理由: 外部の3つの実務(ruleset workflows・GitLab の pipeline execution policy・Prow)は、いずれも定義だけを中央へ置き、スクリプトの書き換えを残す(外部 `:229-230`、Prow KEP-2291 `:154,161`)。「定義を守った」と書けば守られたと読む採用者が出る。要求事項で両方を求めないと、条項が名目になる
- 開示で2層を分ける理由: 現場の運用者は、どの結果を信じてよいかを PR ごとに知る必要がある。テスト・カバレッジの結果は、統制の設定を変えた PR では書き換えた定義で作られる(R-1 留保)。これを1行の「書き換えられうる」で済ませると、全結果を疑うか、全結果を信じるかの2択になる
- 送り手を要求しない理由
  - `integration_id` を GitHub Actions に固定しても、どのワークフローから出たかは縛れない(外部 `:52`、推測)。PR の側のワークフローも、権限を求めれば同じ App・同じ名前で状態を出せる(内部 `:196`、推測)。(a) の基底の判定にも同じことが言える。名前を変えても、PR は新しいワークフローで同じ名前を出せる
  - 区別できるのは、判定だけが持つ資格情報で状態を出す専用の App だけである(内部 `:196`)。これは採用者に、App の作成・鍵の保管・既定ブランチに限った Environment の設定・鍵の更新の運用を課す。個人の採用者にとって、この手数は G-5 の他の全設定より大きい(未実証: 手数を測っていない)。鍵の扱いを誤ると、新しい漏えいの面になる
  - 手数が大きいことを不採用の理由にはしない。不採用の理由は、**全採用者に要求すると、満たせない採用者が「未達」の表示に慣れ、表示そのものが信頼を失う**ことである。要求は性質(送り手が判定の側に限られること)で書かず、限界の開示で書く。App を使える採用者には例示で道を示す
- 事後の照合で補う理由: 送り手を縛れなくても、マージの後に「統制の設定を変えた PR に、AI維持管理者の承認のレビューが付いているか」は、record-copy の写し(ADR-0070・0109。内部 `:242`)から照合できる。偽の状態でマージされた PR も、承認の欠けとして G-7 で欠落になる。ADR-0109 の「防止でなく検出」と同じ立場で、防止できない残りを検出へ回せる

### 現場として付ける条件

- G-7 の事後の照合(案 e)は、照合のコードも `scripts/gate/` にあり、出荷の時点の版で動く(内部 `:241`)。範囲の中で集約のコードを変えた PR があれば、その事実を集約の出力に固定の文で出す。照合のコードを前回の出荷の版で動かす形は、手順が複雑になり、現場が誤りやすい(未実証)。採るかは起草で比べる
- 同名の状態の扱い(既存の失敗と新しい成功が同じ名前で並んだとき、ルールセットがどう判定するか)は E-3 で確かめるまで未実証。結果によって開示の文を変える

### 他の案を落とす理由

- **定義だけを基底へ移す形(2層を分けて、層 A だけを要求する案)**: 採らない。層 B が残り、要求事項が名目になる(上の理由)
- **専用の App による送り手の固定を、全採用者に要求する案**: 採らない(上の理由)。例示として残す
- **送り手について何も書かない案**: 採らない。「必須チェックが通った」を「判定が通った」と読む誤りを、採用者が避けられない

### 留保

- 表の「塞ぐ」は、いずれも実機で確かめていない(E-1〜E-4)。確かめるまで、表は EV のマークを付けて出す

## R-3 所有する組織の同意の記録(IMPL-0340)と AI維持管理者の記名

### 推す案

1. **AI維持管理者の記名は、統制の設定を変える PR(`CONTROL_FILES` と閾値・除外設定に触れる PR)のすべてで、本人の承認のレビューと結び付けて機械で確かめる**。照合は名簿の数値の識別子(ADR-0108)による。緩める向きに限らない
2. 確かめる場所は2つ: **マージの前は R-1 の基底の判定**、**マージの後は G-7 の事後の照合**(R-2)。PR の側の pr-rules には置かない
3. **1名の体制では、承認のレビューを求めない。本文の記名(自己申告)を受け付け、自己申告であることを判定の出力と保証の開示に区別して出す**
4. **所有する組織の同意(IMPL-0340)は、緩める向きの申告がある PR に限って、所有する組織の指名者の承認のレビューを求める**。指名者のアカウントは構成へ写さず、基底ブランチのテンプレ8 第9項から読む。向きの判定は人(書き手の申告と AI維持管理者の確認)に残す
5. IMPL-0340 は、R-1 の基底の判定が実機で確かめられるまで `state=undelivered` のまま表示し続ける

### 理由

- 承認のレビューに結び付ける理由: いまの記名は本文のテキストで、PR の作成者が AI維持管理者の氏名を書けば通る(内部 `:134`)。3.11.2 は強制層の変更を AI維持管理者が承認すると定める(内部 `:25`)。テキストの欄はその承認の証拠にならない。ADR-0106 の「効力を持つ前に記名者本人の操作で帰属を裏づける」と同じ向きである(内部 `:206`)
- 向きに限らず課す理由: 機械は緩める向きを判定しない(内部 `:133`)。向きを書き手の申告に任せると、「止まった」と書けば記名を免れる(内部 `:133`)。2名以上の体制では、承認のレビューは1回の操作で済む。統制の設定を変える PR は製品の PR より少ない(未実証: 頻度を測っていない)
- 1名の体制で求めない理由: GitHub は作成者自身の承認を数えない(前提 3)。求めると、1名の体制では統制の設定を一切変えられなくなるか、管理者の bypass が常態になる。どちらも記録の信頼を下げる。標準はすでに、1名の名簿では本人の記名を自己申告として受け付け、区別して開示する形を採っている(`gate-criteria.md:1017`、IMPL-0266 `:1073`)。同じ形に揃える
- 2名の体制の扱い: 作成を指示した者が AI維持管理者を兼ねる場合、もう1人の承認が要る。兼務の境界は ADR-0082 と突合する(内部 `:213`)。突合は起草の側で行う
- 同意を緩める向きに限る理由: 標準が同意を求めるのは緩める向きだけ(3.11.2、軸D。内部 `:25,210`)。全変更に所有する組織の承認を課すと、上流のテンプレートの取り込み(`scripts/gate/**` の更新)のたびに委託元の承認が要る。標準より厳しい義務を、標準の規定なしに機械で課すことになる。現場では、委託元の承認待ちで更新が滞り、古い検査が残る(未実証)
  - 申告の偽りの扱い: 緩める変更を「緩めない」と申告すれば、同意の照合を免れる。これを塞ぐのは、上の 1 の AI維持管理者の承認のレビューである(AI維持管理者が向きを確かめる)。AI維持管理者が受託側の人なら、委託元は事後にしか気付けない。この残りを開示に出す
- 指名者をテンプレ8 から読む理由: 構成は席の組織を持たない(ADR-0069 決定2。内部 `:65`)。ADR-0087 は判定の結果を受け取る者を構成へ写さない方針を採った(内部 `:255`)。構成へ写す形はこれと突合が要る。テンプレ8 第9項は所有の記録の置き場として既にあり(IMPL-0339。内部 `:26`)、基底から読めば同じ PR で書き換えられない。読めない形式なら照合できないと表示する(未実証: テンプレ8 第9項に指名者のアカウントの欄を足すかは起草で決める。欄を足すなら template-fields.yaml の両方向の検査に掛かる)
- 基底の判定と G-7 の両方に置く理由: 基底の判定は送り手の偽装で迂回されうる(R-2)。G-7 は記録の写しを見るので、マージの後に迂回を欠落として数えられる

### 他の案を落とす理由

- **pr-rules(PR の側)に同意の照合を足す案**: 採らない。同じ PR で照合を外せる(内部 `:258`)。照合を降ろしたと表示して、実際には外せる状態は、未達の表示より悪い
- **所有する組織がルールセットのパス単位の必須レビュアー(b2)・ruleset workflows(c)で同意を強制する案**: 要求事項にしない。例示として書く。個人所有のリポジトリでは使えない、または未確認(E-8・E-9)。使える採用者には、構成に組織を持たせずに強制できる良い形である(内部 `:209`)。ただし向きを判定できないため全変更に課すことになり、上の「同意を緩める向きに限る理由」と衝突する。使う採用者には、全変更に課すことを採用者が選んだと記録させる
- **事後の提出を選んだ組織にも、マージの前の承認を求める案**: 採らない。ADR-0087 決定2 が事後の提出を認めた(内部 `:72`)。事後の提出は G-7 の事後の照合で、期限の内に提出があるかを確かめる対象にする
- **AI維持管理者の記名を本文の欄のまま残し、開示だけする案**: 採らない(上の理由)。ただし 1名の体制では、この形を自己申告として残す

### 留保

- 承認のレビューを名簿の識別子で照合する形は、判定記録(ADR-0106・0109)で使っている。陰性の確認の記録は効力を持つ記録の閉じた列挙に入っていない(内部 `:206`)。列挙を広げるかは突合の論点として起草へ渡す
- 承認の後の push で承認を失効させる設定(`require_last_push_approval`。雛形は true。内部 `:212`)が前提である。この設定を外した採用者では、承認の後のすり替えが残る。外部 1.6(`:94`)

## R-4 #369 との分担、実機の確認、記録

### 推す案(分担)

**分担案1 を推す**(内部 `:170`)。#371 が「判定と指示を基底から読む」共通の性質と、`pull_request_target` の封じ込めの条件(R-1 の条件 1)を決める。#369 はその上で、AI レビューの指示の読み元を実装する。#369 を #371 へ統合しない(トリアージの「重複とはしない」`triage-370-401.md:78-84` を保つ)。

### 理由

- #369 の yml も `pull_request` で動く限り、「基底から読む」手順そのものを PR が書き換えられる(内部 `:168`)。共通の機構を先に決めないと、#369 を降ろしても H.4 条件3 の「書き換えられない保護の下にあること」に届かない
- 統合しない理由: 守るもの(指示というデータ / 実行される判定のコード)と、合否への影響(H.4 の検出の層 / 必須チェック)が違う(内部 4.1 `:160-166`)。受け入れ条件と IMPL も別である
- **現場として最も重く見る点: AI レビューを `pull_request_target` で動かす形は、G-5 の判定より危険である**。AI レビューは PR の差分と本文を読み、外部の API の鍵を使う。`pull_request_target` では書き込みの権限を持つトークンが同じジョブにある(外部 `:33,37`)。PR の本文や差分に書いた指示で AI の担い手を誘導されると(プロンプトの注入)、道具を持つ担い手は書き込みの権限で動きうる(未実証)。#371 の封じ込めの条件は「PR のコードを実行しない」だが、AI レビューでは PR の内容が担い手への入力そのものになる。#369 には次の条件を足して渡す
  - AI レビューのジョブに書き込みの権限と道具の実行を与えない。結果の書き込み(コメント)は別のジョブへ、信頼しないデータとして渡す
  - 指示だけを基底から読むなら、`pull_request` のままでも API で基底の ref の指示を読める(内部 `:166`)。この形を採る場合、yml の書き換えの残りは #371 の開示へ入れる

### 実機の確認(E-1〜E-12)

- **いつ**: 条項の採否(要求事項を置くか)は実機を待たずに決めてよい。要求事項は性質で書くためである。**テンプレートの実装を `state=delivered` にするのは、実機で確かめた後に限る**
- **最低限、先に確かめるもの**: E-1・E-2(本件の前提)、E-3・E-4(基底の判定を必須として数えられるか、偽装の可否)、E-11・E-12(`pull_request_target` の安全の前提)、E-5(record-copy の定義の読み元。R-2・R-3 の事後の照合が依る)、E-7(CODEOWNERS の読み元)。E-8〜E-10 はプランの条件の確認で、開示の文を決める材料として後でよい
- **どこで**: 使い捨ての一時のリポジトリ。**個人所有の public リポジトリ**で確かめる(本件の結論が最も厳しく掛かる採用者の条件だから)。組織の条件(E-8〜E-10)は、組織のアカウントが無ければ「確かめられない」と記録する。推測で埋めない
  - E-12(フォークからの PR)は、別のアカウントからのフォークが要る。用意できなければ未確認として残す
- **外部への作用**: 一時のリポジトリの作成・PR の作成・ルールセットの適用は、利用者の GitHub アカウントへの作用である。**会議体の委員・起草のエージェントの判断で行わない。利用者の承認を得て行う**。手順はメモリの通し実行の一時リポジトリの手順に従う。確かめた後は削除する。`GITHUB_TOKEN` は PR を作れない点(メモリ pit-in-trial-repo)に注意する
- `delegation.yml` の未確認(`:26`)も、同じ一時のリポジトリで併せて確かめる。本件の基底の判定と同じ構成の実績になる

### 記録
