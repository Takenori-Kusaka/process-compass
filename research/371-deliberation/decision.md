# 議長の裁定(#371 同じ PR でワークフローとゲートの検査を書き換えて検査を緩められる)

入力: 議題 `council-00-agenda.md`、調査 `survey-371-1-internal.md`・`survey-371-2-external.md`、意見 `council-01-drafter.md`(起案)・`council-02-field.md`(現場)・`council-03-qa-audit.md`(品質監査)・`council-04-standards.md`(規格)・`council-05-defender.md`(弁護)。

## 0. 骨格

5 委員とも欠陥を認めた。G-5 の必須チェックは、定義もスクリプトも PR の側で動き、検査を緩める変更が緩めた検査を通る。AI維持管理者の記名は本文の欄で、本人の操作に結び付かない。「判定のコードを基底から読む」規定は委任の経路(5.5.4)と G-8 にあるのに、G-5 に無い。規格は実装を指定しないが、検査の定義・ロジックの変更を自己承認させない要求は SP 800-204D 5・5.1.1・5.1.2、SSDF PS.1.1、SLSA L3 から導ける(規格)。要求は手段ではなく**性質**で書く(5 委員)。

Issue の訂正: IMPL-0334 は IMPL-0340(issue=371 へ付け替え済み)、ADR-0086 は ADR-0087。

## R-1 検査の読み元 — 裁定: 性質で要求し、判定の種類で分ける

- **変更のコードを実行しない判定**(G-5 の pr-rules 等): 判定のコードと判定に使う構成を、基底ブランチ(既定ブランチの先端)から読む。5.5.4・G-8 と同じ論理(起案・現場・品質監査・規格)。手段の例: `pull_request_target` で PR のコードを checkout せず、PR の差分と本文をデータとして読む形
- **変更のコードを実行する判定**(テスト・ビルド等): その結果は信頼しないデータとして扱う。統制の設定(強制層・検査・判定のコード)を変える変更は、その変更自身が書き換えた検査の合格だけでは取り込まない。push した者と別の者、すなわち AI維持管理者本人の承認のレビューを、PR の側から外せない形(ホスティングが強制する規則)で求める(5 委員)
- 事後の検出: 出荷の証跡の集約(G-7)が、統制の設定を変えた変更と、その承認のレビューの有無を照らす(品質監査・規格・弁護)
- 手段の例: ホスティングが強制するコード所有者の承認、ルールセットの required workflows。例示に留め、適合の手段を一つに決めない(5 委員)。`pull_request_target` は送り手の偽装を解かず、誤設定の危険があるため、唯一の形にしない(弁護)
- 満たせない構成(個人所有・無償のプランで規則を強制できない等)は未達として開示する。env-check に3値(満たす・満たさない・確かめていない)で記録させる(起案)
- 採らない: (d) 開示だけ、G-7 の事後の検出だけ、push のパス制限、マージのキュー、(g)(h)(i)(内部調査の案)。いずれも、緩めた検査を通る経路を塞がない

## R-2 2層と送り手 — 裁定

- 「判定のコード」を、定義・スクリプト・その読み込み先をまとめた1語とする。定義だけを外へ出す構成は、要求を満たさない(起案・現場・弁護)。開示の表では、定義・判定のスクリプト・PR のコードの実行・送り手の層を分けて示す(規格・現場)
- 送り手(必須チェックの `integration_id`)の固定は、独立の要求にしない。「PR の側から同じ名前・同じ送り手で結果を出せる構成は、外せない形に当たらない」として扱う(起案)。送り手の固定は狭める措置であり、適合の手段に数えない(規格)。確かめていないことの開示を続ける(弁護)
- 弁護の委員の新しい指摘: 準拠テンプレートの統制の設定の一覧(`CONTROL_FILES`)が `.github/actions/**` と `.github/gate-node-version` を含まない。本件で足す

## R-3 同意の記録と AI維持管理者の記名 — 裁定

- AI維持管理者の受け入れ(強制層・検査の追加・統合・削除の承認と、外した旨の受け入れ)は、本人の承認のレビューで成立させる。本文の記名の欄は承認に数えない。照らすのは名簿の数値の識別子(ADR-0108)。向きに依らず掛ける(5 委員)
- 確かめる場所は2つ: 基底から読む判定(R-1)と、出荷の証跡の集約(G-7)(規格・弁護)
- この承認の記録を、効力を持つ記録の列挙(ADR-0106)へ加える(品質監査。列挙の書き落とし)
- 1名の体制では、別の者の承認が得られない。自己申告として区別して開示する(現場)
- 所有する組織の事前の同意(IMPL-0340): 所有する組織が置くホスティングの規則と、指名者本人のレビューで行う形を規定する。構成へは写さない(起案)。その形で確かめられない同意は、未達のまま残す(弁護)

## R-4 #369 との分担、実機の確認、記録 — 裁定

- #369 とは統合しない(分担案1)。#369 は、AI レビューの指示を、本件で定める「基底から読む」型の上で実装する。AI レビューのプロンプト注入の危険(指示を変更が書き換えられる)を、#369 への条件として渡す(現場・規格・弁護)
- 実機の確認: 所有者の判断(2026-11-05、ダイアログで「public の一時リポジトリで行う」)にもとづき、個人所有の public の一時リポジトリで E-1〜E-12(と起案の委員の E-13〜E-15)を確かめ、終わったら削除する。秘密情報は置かない。**実機で確かめるまで、関係する IMPL は delivered にしない**(5 委員)。実機の結果が裁定の前提と食い違えば、裁定を改める
- ADR-0115 を新設し、ADR-0087 を補う(#373 が ADR-0113、#372 が ADR-0114)。ADR-0087 の状態の節に追記する
- EV-0233: 性質で書いた要求を、個人所有・無償のプランでどこまで満たせるかは、実機の確認の範囲にしか支えられない。見直し 2027-05
- 保証の開示に、R-1・R-2 の層ごとの充足と未達を出す

## 採らない案(まとめ)

| 案 | 理由 |
| --- | --- |
| 開示だけ / G-7 の事後の検出だけ | 緩めた検査を通る経路を塞がない |
| `pull_request_target` を唯一の形にする | 送り手の偽装を解かず、誤設定の危険がある |
| ruleset workflows を必須にする | 個人所有のリポジトリで使えない。例示に留める |
| 定義だけを外へ出す | スクリプトの書き換えを防げない |
| 送り手の固定を適合の手段に数える | 偽の status しか止めない |
| 本文の記名を承認に数える | 本人の操作に結び付かない |
| #369 と統合する | 対象(データ)と機構が違う |
| push のパス制限・マージのキュー・(g)(h)(i) | 内部調査の評価のとおり、経路を塞がないか体制・プランへの依存が大きい |

## 実機の確認を受けた追加の裁定(2026-11-05、`probe-371.md`)

実機の確認は、裁定の前提と合った(E-1・E-2・E-3・E-5・E-6・E-11・E-14)。書き換えた yml でも gate-g5 は通り、同名のジョブや PR の側から出す commit status でも必須チェックを満たせた。送り手を GitHub Actions に固定しても区別されなかった。個人所有・無償のプランでは required workflows(E-9)、パス単位の必須レビュアー(E-8)、push のパスの制限(E-10)が API に拒否された。

- **AR-1(E-4)**: 基底から読む判定の結果は、**check run** で出す形に限る。`pull_request_target` の判定を check run で出す形は必須チェックとして数えられ、PR の側の同名の成功で上書きされなかった。commit status で出す形は、PR の側が後から上書きできた。手段の例にこの条件を書く
- **AR-2(E-5)**: マージせずに閉じた PR で、record-copy が PR の側の定義のまま `contents: write` の権限で動いた。書き込みの権限を持つワークフローを PR の側の定義で動かす経路は、本件の論点(PR の側の定義で統制が動く)そのものであり、本件で直す。書き込みの権限を持つワークフローは基底の定義で動かし、PR のコードを checkout しない。record-copy.yml 60 行目の誤ったコメントを直す
- **AR-3(副次の観測)**: 作成者が唯一のコード所有者のとき、コード所有者のレビューは何も止めず、作成者本人の承認も拒否された。1名の体制では R-1 の「別の者の承認」をホスティングで強制できない。R-3 の自己申告の開示で扱う(新しい要求は足さない)
- 確かめていない項目(E-7 の本題・E-12・E-13)は、所有者と別のアカウントが要るため行っていない。関係する IMPL は、これらに依らない部分だけを delivered にし、依る部分は undelivered として残す。EV-0233 の範囲に含める

## 実装の判断への裁定(2026-11-05、`implementation.md` の J-3・J-5・J-7・J-8)

- **J-3**: Dependabot のワークフローの更新も、統制の設定の変更として AI維持管理者の承認の対象にする。維持する。送り手が誰であっても、統制の設定を変える変更は同じ扱いである(R-1)
- **J-5**: 採用の日より前の変更を欠落に数えない扱いは維持する。ただし「採用の日より前」かどうかは、自己申告の日付ではなく、基底ブランチの第1親の連鎖のコミットで決める(#373 の X-1〜X-3 と同じ原則)
- **J-7**: 新設の `gate-g5-base.yml` と、record-copy の closed 契機は、実機で動かしていない。R-4 の「実機で確かめるまで delivered にしない」に当たる。所有者の承認(2026-11-05、#371 の実機の確認のための public の一時リポジトリ)の範囲で、実装した版を一時リポジトリで動かして確かめる。確かめるまで、該当する IMPL は undelivered とする
- **J-8**: IMPL-0340・IMPL-0460(所有者と別のアカウントが要る確認に依る)は、新しい Issue を起こさず、既存の #361(実際の GitHub 上での持ち込みの検証)へ付け替える(2026-11-05 の所有者の方針)

## 独立の突合への裁定(2026-11-05、`crosscheck.md`)

- **C-1(高)**: J-7 の裁定どおり、実装した版を実機で確かめるまで、IMPL-0455・0456・0459 は undelivered にする。確認(`probe-371b.md`)で動作を確かめた部分だけを delivered に戻す。IMPL-0456 の note は、確認用のワークフローでの E-4 の結果と、実装した版での結果を区別して書く
- **C-2・C-3**: J-5・J-8 の裁定を反映する(採用の日の判定を基底ブランチの第1親の連鎖のコミットで行う、IMPL-0340・0460 を issue=361 へ)
- **C-4**: 出荷の集約が数える統制の設定の範囲を、check-pr と同じにする(アダプタの閾値、process.config.json の閾値、改名の元を含める)
- **C-5**: 開示の層の行は、構成の実際の充足(env-check の3値)から出し、未達を出す
- **C-6**: 1名の体制の自己申告は、本人のアカウントの操作(PR へのコメントのレビュー等、本人が出せる操作)を名簿の数値の識別子で照らして成立させる。本人の操作の無い自己申告は数えない
- **C-7〜C-9**: 実装の担当が直す
- **C-10**: 裁定に無い却下(App の鍵)は、ADR の「採らなかった案」から外し、「決定の外」として書く
- **C-11**: 準拠テンプレートのリポジトリ(pit-in-template)の main への直接の push は、所有者の作業の指示(本件を含む Issue の処理で、テンプレートは main へ push する)にもとづく。採用者のリポジトリで AI維持管理者が承認する手続とは別である。この旨を ADR-0115 の状態の節に書く

## 修正の報告への裁定(K-1・K-2)

- K-1: IMPL-0457・0458・0461 は、出荷の集約・env-check・保証の開示の手元で動く判定であり、ホスティングの振る舞いに依らない。手元の試験で確かめられるので、delivered を維持する
- K-2: checkout を `github.sha` へ替えず、F-1a で確かめた形(既定ブランチの名前)を保ち、版を出す手順と限界を記す扱いを維持する。替えた形は実機で確かめていない
