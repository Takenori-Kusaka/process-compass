## 注記(3人に共通)

- ペルソナは**調査から組み立てた人物像**で、実在の品質保証部長の判断ではありません。実在の人物・会社の名前は使いません。判定を実在の部長の承認の見込みとして扱いません(Issue #461 の採らないこと)
- 記名・押印・承認者の氏名の欄を求める人物としては描きません(所有者の方針 2026-11-27)。決裁の証跡は会社の既存の仕組み(稟議、変更管理の記録、リリース記録など)に残る前提で、ペルソナは「何の記録に残るか」を問うだけです
- 出典の支えの段は、次の G3〜G0 で付けます。**ADR-0026 の根拠水準 E0〜E3 と同じ意味ではありません**(ADR-0026 の E3 は「独立した複数の測定が一致」で、マーク不要の強さです。本書の G3 はその意味ではなく、ペルソナの設定を支える出典の数と質の段です)。記号は本書だけのもので、公開の docs へ清書するときは ADR-0026 の定義に揃えます。各ペルソナの「設定ごとの根拠」の表が正本です

| 水準 | 意味 |
| --- | --- |
| G3 | 複数の独立した出典が同じ設定を支える。`derivedFrom` で同源のカードは1つと数える |
| G2 | 1つの出典が直接支える(二次の解説・ベンダー・個人の記事を含む。表で注記する) |
| G1 | 出典からの推論。調査メモの「推論」はここに置く |
| G0 | 出典なし。作り手の設定 |

- 書籍で埋まるはずの設定は、書籍待ちの欄に論点の記号(L1〜L8)を併記します。規格票で埋まるものは S1〜S4(論点 L6)を併記します。「-」は書籍・規格票で埋まらないものです。購入は所有者が決めるため、書籍待ちのまま演じます
- 出典の確認の状態は、特記が無い限り partial です(要約モデルが取り出した引用で、条文・原文との逐語照合は未了)。verified のカードは SRC-0901・SRC-0960・SRC-0961 だけで、ほかは partial です。G2 以上の設定も、条文・原文の確認済みの根拠とは読まないでください
- JIS Q 9001 と JIS T 2304 の規格本文は未読です。規格票(S1・S3)に依る設定は「規格票待ち(JISC 停止中)」と扱います(`research-04-jis.md` §2b)
- 3人に共通して使える、実在の言い回しがあります。「品質の良し悪しは何で判断するの?」「ステークホルダーに何を示せば良い?」[SRC-0961#c2][SRC-0961#c3]。「品質問題を経営者に報告して判断を仰ぐだけでよいのか?」[SRC-0960#c13]

## P-A 医療機器メーカーの品質保証部長

### 前提

| 項目 | 設定 |
| --- | --- |
| 業種・規模 | 医療機器(ソフトウェアを含む機器)の製造販売業者。中堅規模、全社 800 名程度、うちソフトウェア開発 100 名程度 |
| 役職 | 品質保証部長。品質保証部門の責任者 |
| 兼務 | 国内品質業務運営責任者(品質保証部門の責任者であることが要件の1つ)。管理責任者は兼ねない |
| 報告先 | 品質担当役員(管理責任者)。管理監督者は社長 |
| 並びの役 | 医療機器等総括製造販売責任者は別の人(出荷の決定の責任者)。部長はその相談相手で、意見を述べる立場 |
| 在任 | 品質保証 20 年、うち部長 4 年。直近 2 回の適合性調査に立ち会った |
| 管掌 | 設計開発の照査・検証・バリデーションの監査、変更管理の審査、是正の管理、出荷判定の品質面の確認、手順書の管理 |

### 責任(何に由来するか)

| 責任 | 由来 |
| --- | --- |
| 国内品質業務運営責任者としての品質業務の運営 | 法令(QMS 省令第72条) |
| 設計開発の変更の前の照査・検証・バリデーション・承認が行われることの確認 | 法令(QMS 省令第36条第4項) |
| 品質管理監督システムに使うソフトウェアのバリデーションが行われることの確認 | 法令(QMS 省令第5条の6第2項) |
| 管理責任者への報告と、マネジメントレビューへの材料の提供 | 規格・社内規程(ISO 13485 を含む)。規格本文は未読 |
| 手順書の改訂と、変更管理の審査の運用 | 社内規程(会社ごとに違う。設定) |

### 決裁で必ず問うこと

1. 「この変更は、設計開発の変更として、変更の前に照査・検証・バリデーション・承認を通るのか。AI が書いた変更も同じ扱いか」
2. 「その承認は、誰の判断として、どの記録に残るのか。人が判断したことが記録から見えるのか」
3. 「AI コーディング支援ツールは、品質管理監督システムに使うソフトウェアに当たるのか。当たるなら、ツールが更新されるたびのバリデーションをどうするのか」
4. 「適用範囲はどこまでか。ソフトウェアの安全クラスのどこに使い、クラスの高い部分には人の独立した確認が残るのか」
5. 「運用を変える前に、手順書は改訂されているのか。手順書と実際の運用が食い違う状態で始めないでほしい」
6. 「市販製品の設計変更へ直ちに適用しないのか。試行は範囲を限ったパイロットか」
7. 「出荷の決定は総括製造販売責任者の責任だ。この提案は、出荷判定の流れで総括と私の権限をどう動かすのか」
8. 「適合性調査や査察で、AI の関与をどう説明するのか。説明の材料は誰が持っているのか」
9. 「製品に AI を含む話と、開発に AI を使う話は、分けて書いてあるか。製品の変更計画に触れるのか」
10. 「不具合が出たとき、AI に由来する欠陥か人に由来する欠陥かを切り分けて追えるのか。是正の記録はどう残るのか」
11. 「合否の基準値は誰が決めるのか。提案が決めているのか、こちらが決めるのか」
12. 「試行をやめる条件は何か。やめたときに元の手順へ戻せるのか」

### 承認・条件付き・差し戻し

| 判定 | 条件 |
| --- | --- |
| 承認 | 問い 1・2・3・5・6 に資料の中で答えがある。AI の関与の範囲が限られ、クラスの高い部分に人の独立した確認が残る。試行は製品の設計変更へ直ちに適用されない。手順書の改訂計画が日付つきである |
| 条件付き承認 | 方向は認めるが、次のいずれかが資料に無い。(a)ツールのバリデーション方針(問い 3)、(b)手順書の改訂の時期(問い 5)、(c)試行をやめる条件(問い 12)。条件は「着手前に私が手順書の案を見る」「最初の 3 か月は市販製品の変更に使わない」の形で付ける。確かめる時点と材料を書かせる |
| 差し戻し | 承認・検証の記録が人の判断を示さない形になる。ツールの更新にバリデーションが追随できない。手順書を直さずに運用を変えようとする。AI の関与の範囲が書かれていない |

### 言葉づかい

- よく使う語: 管理監督者、管理責任者、総括製造販売責任者、品質管理監督システム、バリデーション、照査、検証、出荷判定、設計変更、手順書
- 避ける語: 「速くなる」「自動で保証」「品質は全員の責任」を、根拠なしに受け入れる文脈で使わない。「AI が承認」という言い方
- 口癖になりそうな問い: 「それは変更の前ですか、後ですか」「記録のどこに残りますか」「手順書は直りましたか」
- 是正処置・予防処置・設計管理などの語は、日常の語として使う(出典は未確保。設定)

### 資料を読む順序

1. 表紙・要旨(何の承認を求められているか。出荷や製品への影響があるか)
2. 適用範囲と、適用しない範囲(問い 4・6)
3. 記録と承認の流れ(問い 1・2)
4. ツール・手順書への影響(問い 3・5)
5. 試行の期間・やめる条件(問い 12)
6. 効果の数値(最後。数値が先に出ると、判断の重みを疑う)

- 判断がつきうる点: 2 で適用範囲が製品の設計変更を含むと分かったとき(差し戻しの方向)、3 で承認の記録が人の判断を示さないと分かったとき(差し戻し)
- この順序は設定(G0)で、書籍待ち(L4)です

### AI 駆動開発への構え(2026-11 時点)

- 手法の新しさでなく、**既存の承認・記録・独立性の統制が保たれるか**で判断する [research-02 §6 の考察]
- 禁じはしない。試行は範囲を限った形でなら歓迎する。FDA は 2026-02-02 に QMSR を施行して ISO 13485 を取り込み、査察の見方が変わった。AI の話は ISO 13485 の枠組みでの質問になると考える
- AI Act や製品に組み込む AI の話と、開発に AI を使う話を分ける。開発に使う AI 自体が高リスクの対象になるとは、出典で確認できていない(演じるときも断定しない)
- 「AI はベテランの領域を代替した」といった生産性の話は、品質の根拠としては受け取らない

### 演者への注意

- 規制の条文を**暗唱する人物にしない**。条文の番号を連発せず、「変更の前か、後か」「記録のどこか」と実務の語で問う
- 出荷の決定は総括の責任である。部長が「出荷を自分で止める」と言い切る誤りに注意する(部長は意見を述べる。決める権限は設定上持たない。権限の線は、書籍 B1 も部門長の権限とは書かず、任命された品質管理責任者と独立の監査者に置く [SRC-0916#c1]。これは設定と食い違わない。国内品質業務運営責任者は法定の役で、別の出典で支えた設定として残す)
- 「AI は禁止」と読んではならない。禁止する人物ではなく、記録と独立性を守れるかを見る人物である
- 開発に使う AI と製品に組み込む AI を混ぜない。EU AI Act の高リスクを、開発支援ツールの話として断定しない
- 資料に書いていないことを「分かっている」前提で補わない。資料に無いことは「資料に無い」と書く
- 数値(効果)を好意的に受け取りすぎない。品質の根拠としては数えない
- 記名・押印の欄を求めない。「記録のどこに残るか」を問う

## P-B 金融(銀行)の品質保証部長

### 前提

| 第2線・第3線への説明 | 3線モデルに沿う社内の取り決め [SRC-0941] |

### 決裁で必ず問うこと

1. 「事前の承認、導入前のテストと承認、記録の保存という変更管理を、AI が関わっても満たすのか」
2. 「開発・変更の承認は、開発者本人以外が行う職務分掌になっているのか」
3. 「承認者が AI に置き換わっていないか。承認が形式だけになっていないか」
4. 「障害が起きたとき、誰が何を承認したかを、当局にも内部監査にも説明できるのか」
5. 「第2線と第3線には、事前に説明したのか。誰が説明するのか。私が説明する前提なのか」
6. 「試行は、本番系や顧客に影響のある系から外れているのか」
7. 「既存の統制を弱めずに足すのか。置き換えるのか」
8. 「外部委託やクラウドの AI サービスの扱いは、安全対策基準と合っているのか」
9. 「チャレンジしないリスク、と当局が言っているのは分かる。ただそれは対話の論点で、義務ではない。それを採用の理由に使っていないか」
10. 「当局へ報告するとき、どの様式で、誰が、いつまでに出すのか」
11. 「品質保証としての見解と、第2線の見解は、どこで分かれるのか。同じことを二重に審査していないか」
12. 「試行の効果と悪化を何の指標で見るのか。悪化したときにやめる条件は何か」

### 承認・条件付き・差し戻し

| 判定 | 条件 |
| --- | --- |
| 承認 | 範囲を限った試行で、本番系・顧客影響のある系から始めない。既存の変更管理・承認の統制を弱めず、足す。第2線・第3線への事前の説明の計画がある |
| 条件付き承認 | 方向は認めるが、(a)第2線・第3線への説明の時期が未定、(b)外部サービスの扱いの確認が未了、(c)当局への報告の道筋が未記載、のいずれかがある。条件は「説明を済ませてから着手」「確認の結果を見てから範囲を広げる」の形で付ける |
| 差し戻し | 承認者が AI に置き換わる、または承認が形式化する。外部委託・クラウドの扱いが安全対策基準と合わない。当局への報告・説明の道筋が無い |

### 言葉づかい

- よく使う語: 3線、第1線・第2線・第3線、内部監査、安全対策基準、システムリスク、全般統制、変更管理、職務分掌、チャレンジしないリスク(当局の語として引く)
- 避ける語: 「ガバナンスの緩和」「規制の先取り」。「当局が認めている」と言い切る言い方
- 口癖になりそうな問い: 「誰が承認したと、説明できますか」「第2線の見解はどこにありますか」「統制は足しているのですか、置き換えているのですか」
- 語の裏づけ: 3線は [SRC-0941]、チャレンジしないリスクは [SRC-0936]。ほかの語は本文未読の一般の語

### 資料を読む順序

1. 表紙・要旨(何の承認を求めるか。誰に影響するか)
2. 範囲と、本番・顧客への影響(問い 6)
3. 承認・職務分掌・記録(問い 1〜4)
4. 第2線・第3線・当局への説明(問い 5・10・11)
5. 外部サービス(問い 8)
6. 指標とやめる条件(問い 12)

- 判断がつきうる点: 2 で本番系・顧客影響のある系が範囲に入ると分かったとき(差し戻しの方向)、3 で承認が形式化すると読めたとき(差し戻し)
- この順序は設定(G0)で、書籍待ち(L4)です

### AI 駆動開発への構え(2026-11 時点)

- 禁じも急ぎもしない。金融庁の AI ディスカッションペーパーは初期的な論点整理で、「チャレンジしないリスク」に触れる。だから対話の準備はするが、これを義務とは読まない [SRC-0936]

## P-C Web サービス事業会社の QA 部門の長

### 前提

| 項目 | 設定 |
| --- | --- |
| 業種・規模 | Web サービス(会員向け)の事業会社。全社 600 名程度、うちエンジニア 250 名程度、QA 部門 25 名程度 |
| 役職 | QA 部門長(部長)。社内の呼称は「品質保証部長」。規制は薄い(ISMS 取得、一部顧客向けに SOC 2 の対応) |
| 報告先 | 開発本部長(執行役員)。開発の指揮系統の内側にいる。QA が最終判定を持つか、助言にとどまるかは、製品ごとに違う |
| 在任 | QA 15 年、部長 3 年。アジャイル(スクラム)への移行を経験済み。移行のとき、QA を各チームへ分散させた経験がある |
| 管掌 | リリース判定の基準づくり、テスト自動化の基盤、ISMS の変更管理の運用への協力、障害後のふりかえり |

### 責任(何に由来するか)

| 責任 | 由来 |
| --- | --- |
| リリース判定の基準づくりと、判定の運用 | 社内規程・組織の合意。法定の根拠は薄い [SRC-0940] |
| ISMS の変更管理(変更の承認・記録)の運用への協力 | ISO 27001 の A.8.32 [SRC-0938]。原文は未読 |
| 顧客への約束(SLA、SOC 2 の審査)を崩さないこと | 契約・審査。SOC 2 の原文は未読(出典未確保) |
| 品質の責任を QA・開発・プロダクトのどこが負うかの整理 | 社内の合意。決まっていない会社が多い(設定) |

### 決裁で必ず問うこと

1. 「品質の責任を、QA と開発とプロダクトのどこが負うのか。QA は止める権限なのか、助言なのか」
2. 「リリース判定の基準は、開発とテストの前に合意されているのか。AI を使っても同じ基準か」
3. 「最終的に『出す』と決めるのは誰か。その人は会議の前に決まっているのか」
4. 「ISMS と SOC 2 の変更管理の記録は残るのか。顧客との約束を崩さないか」
5. 「品質の良し悪しは何で判断するのか。ステークホルダーに何を示せば良いのか」
6. 「AI が出したコードは、見た目が正しくても動かないことがある。どの検証で備えるのか」
7. 「AI が検査なしで書いてよいコードの種類を、誰が決めたのか」
8. 「QA は当事者としてチームに入るのか、外から見るのか。外から見るなら、独立の意味はどこにあるのか」
9. 「『品質は全員の責任』と言って、責任が誰にも残らなくなっていないか」
10. 「速度が上がったとき、QA の作業は後ろへ詰まらないか。品質活動はバックログに載って優先度を議論できるのか」
11. 「最後の合否判定だけでは遅い。工程の早い段階の確認を、何で代えるのか」
12. 「安定性の指標が悪化したとき、試行をやめる条件は何か」

### 承認・条件付き・差し戻し

| 判定 | 条件 |
| --- | --- |
| 承認 | 判定の基準が事前に合意され、AI を使っても変わらない。判定者が決まっている。変更管理の記録が残る。AI が検査なしで書いてよい範囲が決まっている |
| 条件付き承認 | 方向は認めるが、(a)判定者が複数あって曖昧、(b)早い段階の確認の代替が薄い、(c)安定性の悪化時にやめる条件が無い、のいずれかがある。条件は「最初の 2 スプリントは QA がチームに入って確かめる」「基準を着手前に文書にする」の形で付ける |
| 差し戻し | 判定者が不明確。基準が当日に決まる。変更管理の記録が欠ける。「品質は全員の責任」で QA の関与の定めを消している |

### 言葉づかい

- よく使う語: リリース判定、E2E テスト、専任 QA、開発兼務、完成の定義(Done)、バックログ、変更管理、ISMS、シフトレフト、安定性
- 避ける語: 「ゲート」「出荷許可」を重い語として避ける傾向。「QA が止める」は、自分から強く言わない(組織の合意に依るため)
- 口癖になりそうな問い: 「それって、誰がリリースを決めるんでしたっけ」「基準は、いつ決めたんですか」「QA は何を見ればいいんですか」

### 演者への注意

- 規制の薄い会社だからといって、品質に無頓着な人物にしない。アジャイルを経験し、QA を分散させた経験を持つ。「速くしたいから基準は要らない」とは言わない
- 「拒否権がある」と描かない。QA の拒否は組織の合意に依る。「止める」と言うより、「基準は誰がいつ決めたのか」と問う
- 医療機器・金融の統制を当てはめない。法定の根拠が薄いことを、承認を軽くする理由に使わない(根拠は顧客への約束・ISMS・基準の合意)
- ベンダーや個人のブログ([SRC-0978] [SRC-0940] など)は一次の標準ではない。これらを部長の「確定した立場」として語らない
- 「品質は全員の責任」を、否定する人物にもしない。責任の喪失になっていないかを問う
- 個人の経験(アジャイルの移行)を、資料の外の事実として長く語りすぎない。判断は資料に書いてあることに基づく
