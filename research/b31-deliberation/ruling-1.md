## 1. 改め

### 1.1 順と push(反対の高1・起案の点5。一致)

- `unjudgedGateExceptions` の改め(案 §1.4)は **U6c と同じ単位**で入れる。U6a では exception-expiry.mjs に行の約束の関数を足すだけで、`unjudgedGateExceptions` の挙動は変えない。案 §1.4 の「内容が渡されないときは subject の形だけで判定する」は**採らない**(IMPL-0996 が delivered のまま実態だけ弱まる窓を作る)
- **template の push は1回**: U6a・U6b・U7 は作業ツリーでコミットして bundle へ退避し、B30 の push の後に載せ直して U6c・U8 を足し、回帰の全量の後に template と本体を対で push する。途中の状態(段は受けるが G-7 が取り下げを指示する)を採用者へ出さない
- 実装の順: U6a → U6b → U7 →(独立の突合 1回目)→(B30 の push)→ 載せ直し → U6c → U8 →(独立の突合 2回目は U6c・U8 と1回目の直しの差分)

### 1.2 印の下限(割れた点 a。反対の案を採る)

- 印は固定語 **`変異試験の閾値割れ`** だけにする。`(下限: N)` の書式・スコアとの機械の比較・その試験は**採らない**
- 理由(議長): 下限を書くのは行の書き手で、0 を書けば空になる。承認の後にコミットが変われば、先頭一致の (A) で承認が効かなくなる。残るのは同じ先頭での再実行の揺れだけで、失うのは承認した者の目の前の PR の中に限られる。所有者の方針(細かい定義を増やさない。破られたとき誰が何を失うかで細かさを決める)に照らし、新しい書式に釣り合わない
- 代わりに: 受けたときの段の出力の1行(スコア・閾値・行の ID・承認した者)を証跡とし、手引き(exception-paths.md)に「承認した者は、宣言行のレビューを出す前に段の出力のスコアを読む。受容した理由の欄にスコアを書く」を置く。受けたスコアの妥当性は manual(確かめる者: 承認した者・G-6 の判定者)と IMPL-0931 の note に書く
- 行の約束は案 §1.2 の表から 4 を除き、3 を「内容の先頭が印 `変異試験の閾値割れ`」に改めた 8 条件

### 1.3 段の入力と push の経路(起案の点1・2 を採る)

- `exceptionFor` は対象の照合が `PR #N` の形のため使わない。行の約束は exception-expiry.mjs の新しい関数に1か所で置き、帰属は `exceptionReviewBacking` をそのまま使う
- gate-g5.yml: `GH_TOKEN` は取得の別ステップだけに付ける。取得は `.mjs` に置き、試験できる形にする(入力は一時ファイルの所在で段へ渡す)。権限の追加が要らないことを実装の担当が現物で確かめて記録する。レビューを出した後の再実行の案内は「失敗したジョブの再実行」と書く
- push の経路: 「`merged == true` かつ `merge_commit_sha == HEAD` かつ `base.ref == 既定ブランチ` の PR がちょうど1件」のときだけ、その PR の行で照らす。基底の台帳は `github.event.before` の点から読む。(A) の先頭は API の PR の `head.sha`、作成者・本文も同じ PR のレコードから取る。取れない・0件・2件以上は受けない
- マージの方式: 確かめる対象は squash(テンプレートの既定)。merge commit・rebase・merge queue は照合が取れたときだけ受け、取れなければ失敗のまま。実際の GitHub での応答は確かめていないので、**新しい根拠水準マーク**で開示する(cron の EV と分ける)
- `PR #N` の形で印がある行への診断の文(案 §1.2 の 2 の後段)は採らない。候補が無いときの案内(行の書き方の所在)で足りる
- 閾値を変える PR で行を足しても、段は基底の構成の閾値で読む。これを試験の場面で固定する(反対の 6)

### 1.4 U7(割れた点 b・c・d)

- 降ろす(案 §4.1 のとおり。付け替え・adopter・undelivered のままは採らない)
- **比較の起点は置かない**(反対の案)。H.1 は「週次の定期実行」までで、範囲を定めていない。範囲は段のコマンドが決める。7日前の起点(`.mjs` でもワークフローの1行でも)は採らない
- **閾値割れは終了 0**(案のまま)。H.1 の「合否条件にしない」の文面に従う。スコアと閾値の比較は、段の出力の1行とジョブの要約(`GITHUB_STEP_SUMMARY`)に出す。ジョブを失敗にする案(反対)は採らない(理由: H.1 の文面。閾値を下回ったままの構成で毎週の失敗が続くと、失敗の表示を見過ごす習慣を作る)。コマンドの終了コードが 0 でない・行が壊れているときは失敗にする(実行できなかった事実)
- 週次の型(`PIT_IN_MUTATION_MODE=weekly`)は、イベントが `schedule` か `workflow_dispatch` のときだけ有効にする。`pull_request`・`push` では無視して通常の判定に戻す(起案の改め 6)
- **IMPL-1036 は delivered・check=manual**(反対の案)。確かめる者: G-6 の判定者(週次の結果を読む)。note に、機械が見るのは workflow の存在と形・週次の型の段の挙動(試験の所在)だけであること、既定のコマンドは空で何も測らないこと、定期実行が止まったことを検知する経路が無いこと、実際の cron で確かめていないことを書く。書式(`community/implementation-marking.md`)が delivered・manual と test の併記を許さないときは、書式に従い、実装の記録に書いて議長へ返す
- 新しい根拠水準マーク(週次の所要時間・費用の実測が無い)は案のとおり

### 1.5 開示と表現(反対の 5・7・8)

- IMPL-0996 の note と ADR-0243 に「G-7 が見るのは行の形(対象・印)と帰属・期限だけである。段がその行で閾値割れを受けたことは、段の出力の1行(ジョブのログ。保持の期限がある)と承認した者の宣言行に頼る(manual)」と書く。案 §2・§6 の「段が行を結ぶので当たらない」は採らない
- ADR-0243 の決定6 は「狭める」でなく「置き換える」と書く。ADR-0224 決定7 の原文を1行引く
- 返却の目安に上限が無いこと(遠い日付を書ける)は既存の例外の行と同じで、機械は見ない。README の項に1文で開示する
