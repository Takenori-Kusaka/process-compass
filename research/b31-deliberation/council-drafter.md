### 1-b. 段のジョブで入力が取れるか

- **fork の PR**: `pull_request` の `GITHUB_TOKEN` は fork では読み取りだけになるが、レビューの一覧(REST)と `reviews{editor}`(GraphQL)は読める。pr-rules の「PR のレビュー」ステップが同じ呼び出しを既に fork で行っている。**権限 `permissions` の追加は要らない**(ワークフローの権限は `contents: read` `pull-requests: write` `issues: read` で、読む側は足りる)。
- **イベント**: `pull_request_review` では起動しない(gate-g5.yml 23〜26 行の既存の定め)。レビューを出した後は「失敗したジョブの再実行」で足りる(再実行はイベントのペイロードを保つので `pull_request.head.sha` は不変で、レビューは API から読み直す)。**案の「gate-g5 の最後の実行を再実行する」は、「失敗したジョブを再実行する」へ書き分ける**。全体の再実行は変異試験をもう1回走らせ、スコアの揺れで下限を割る恐れがあるため。
- **改める点 1(トークンを段のコマンドへ渡さない)**: adapter.mjs 138 行は `env: {...process.env}` で製品のコマンドを走らせる。段のステップの `env` に `GH_TOKEN` を足すと、PR 側のテストコマンドが読める。**取得は別のステップで行い、一時ファイルへ書き、`GH_TOKEN` を付けるのはそのステップだけにする**。段のステップへ渡すのはファイルの所在だけ。案の「一時ファイルへ書き、所在を渡す」の方針のままだが、「段のステップへ `GH_TOKEN` を足さない」を条文にする。
- **改める点 2(取得を試験できる形にする)**: レビューの jq(pr-rules 538〜549 行。`edited_by` の合成を含む)をそのまま複製すると、2か所が食い違ったとき `edited_by` が欠けて (A) が全て落ちる。取得と整形は、`scripts/gate/` の `.mjs`(例 `mutation-pr-context.mjs`。`gh` を `spawn` し、偽の `gh` で試験できる形。test-ship-evidence-steps.mjs の先例)に置き、出力は1つの JSON(`{pr:{number,authorLogin,authorId,headSha,body,baseRef}, reviews:[…]}`)。環境変数は `PIT_IN_PR_CONTEXT`(所在)の1本だけにする(案の5本を減らす)。pr-rules の取得を同じ `.mjs` へ寄せるかは、pr-rules を触る範囲が増えるので**今回は寄せない**。代わりに試験で両者の jq 出力の鍵の集合が一致することを静的に確かめる。
- 取得に失敗したときは空にして「読めない」として受けない(案のまま)。
- `@アカウント` の指示者は、トークンの無い呼び出しでは `lookup` が無く、ログイン名の解決に落ちる(check-pr.mjs 1292〜1294 行)。段はトークンを持たないので、**`@` で書かれた指示者は「対応づかない」として受けない側へ倒す**(`lookup` を渡さない呼び出しでの名簿の一致は、識別子で確かめた結果ではない)。ただし取得を別ステップで行うので、そのステップが指示者の `@` を識別子へ解決して JSON に入れる形もとれる。簡単な前者を採る。

## 2. push の経路(§1.3)

**結論: 案のまま(照合の方針)+ 改める(4点の明記)**。

- `GET /repos/{r}/commits/{sha}/pulls` の仕様は「既定ブランチにあるコミットは、そのコミットを入れたマージ済みの PR を返す」。マージの方式別の見立て(**実 GitHub での確認はしていない。EV の対象**):
  - squash: PR の `merge_commit_sha` が squash のコミット(= push の HEAD)。成り立つ。
  - merge commit: `merge_commit_sha` がマージのコミット(= HEAD)。成り立つ。
  - rebase and merge: `merge_commit_sha` は再適用後の先頭のコミットで、PR の1件の push では HEAD と一致するはず。ただし中間のコミットは一致しない。確証が無い。
  - merge queue のマージグループ: 別の合成コミットを経るため確証が無い。
- 方式で成り立たないときは**失敗側に倒す**のが信頼できる(案の「確かめられない → 受けない」のまま)。ホスティングの記録が取れない経路を、名前や本文の「(#N)」から推すことはしない。テンプレートの既定のマージは squash(template/CLAUDE.md)なので、README 項23 に「照合を確認する対象は squash の1件の push。rebase・merge queue は照合が取れた場合に限り、取れなければ失敗のまま。実 GitHub で確かめていない」と書き、根拠水準マークで開示する(U7 と同じ EV にまとめず、別の EV)。
- **改める点 3**: 判定の条件は「`merged == true` かつ `merge_commit_sha == HEAD` かつ `base.ref == 既定ブランチ` の PR がちょうど1件」。案は「該当が2件以上は受けない」としているので、`base.ref` の確認を足す(スタック型 PR の中間の層が別の PR として混ざらないように)。
- **改める点 4(基底の台帳の取り方)**: push の「基底にある ID」は `github.event.before`(PIT_IN_DIFF_BASE が既に持つ)の台帳で読む。HEAD^ ではない(rebase では HEAD^ に PR のコミットが入る)。PR の経路の `origin/<既定ブランチ>` と対になる。行は PR-N が足したので基底に無く、(A) が要る。
- **改める点 5(レビューの照合の値)**: push では (A) の `head` は API の PR の `head.sha`(マージ時点の先頭)。HEAD ではない(squash の HEAD は別の SHA)。`author` も `instructorsOf` の本文も同じ PR のレコードから取る。これは案に書かれていない。試験は「PR の先頭が HEAD と異なる(squash)ときも (A) が通る」場面を足す。
- 取得は 1-b の `.mjs` が行い、push では `PIT_IN_PR_CONTEXT` に PR-N のレコードとレビューを入れる。`workflow_dispatch` は受けない(案のまま)。

## 4. U7 の「7日前の最後のコミット」

**結論: 改める(単純にする)**。

- 「既定ブランチの7日前の最後のコミット」は、`git rev-list -1 --before="<日時>" origin/<既定ブランチ>` で決定できる(全履歴を取得するので足りる。日時は実行の時刻から1つに決まる)。決定可能ではあるが、`.mjs` に置くと時計に依る関数が増え、回帰の時計依存(memory: regression-suites-clock-dependence)を再生産する。
- **より単純な形**: 起点の計算は**ワークフローの1行(シェル)に置き、`PIT_IN_DIFF_BASE` へ入れる。得られなければ設定しない**。`.mjs` は時計を読まない。段の週次の型は「`PIT_IN_DIFF_BASE` があれば渡す、無ければ渡さない」だけ。試験は「環境変数が有れば子に渡る・無ければ渡らない」の2場面で足り、7日の算出は試験の対象にしない(算出の誤りは起点が広がる/狭まるだけで、合否に影響しない。週次は合否条件ではない)。
- **改める点 6(週次の型の入口)**: `PIT_IN_MUTATION_MODE=weekly` は、`PIT_IN_EVENT` が `schedule` または `workflow_dispatch` のときだけ有効にする。`pull_request`・`push` では無視して通常の判定に戻す。PR の側から環境変数 1 本で段を「合否にしない」型に落とせる経路を塞ぐ(ワークフローの定義の変更は ADR-0115 が受けるが、環境変数の取り違えを機械で閉じる)。
- 週次の型の閾値は作業ツリーの構成(`baseConfig` が無い)から読む(既定ブランチの上で走るので同じ)。注意の出し方は案のまま。
- コマンドが道具の側の閾値(`thresholds.break`)で終了コード 1 を返すと、週次のジョブは失敗になる。H.1「合否条件にしない」は gate-g5 の集約とブランチ保護に入らないことで満たす。ただし**定期実行のジョブの失敗は、GitHub が通知する。かつ公開のリポジトリは60日間の活動が無いと定期実行が止まる**。README 項23 に書く(実 GitHub の挙動は確かめていない)。

## 5. U6c の前に U6a・U6b・U7 を push してよいか

**結論: 改める(U7 は先に push してよい。U6a・U6b は U6c と同じ push にする)**。

- 途中の状態で採用者が損をする場面(現物の読みから): U6a で段が行を受ける → 採用者が儀式(行・レビュー・再実行)を終えて PR を通す → 出荷判定で、集約が `unjudgedGateExceptions` により「準拠テンプレートの G-5 は…例外承認で解かない…**状態を『取り下げ』にする**」と指示する。この文は、段が受けた行を取り下げさせる(逆の指示)。案の「安全の側に倒れる」は事実だが、手順を最後まで踏んだ採用者が最後に止められ、逆の指示を受ける。**採用者の費用が増え、表示が誤誘導になる**。
- 案の §1.4 の「内容が渡されないときは subject の形だけ」で欠落にしない緩和は、この指示の矛盾を避ける意図だが、印の無い `G-5 PR-N` の行まで欠落から外す(弱い向き)。削れるもの 1 のとおり採らない。
- したがって: U6a の実装・U6b の本文・U7 は作業ツリーで先に進めてよい。**push は U7(独立。gate-g5 の集約に入らず、段の週次の型は U6a のコードと結ぶだけ)を先に出してよいが、U7 は U6a と同じ mutation-stage.mjs・adapter.mjs を触るので、U6a の差分が入った後に作る(案の直列のまま)。U6a が push 前なら、U7 の push も U6a と一緒に待つ**。実際に先に push できるのは、U6a を含めない形で U7 を切り出せる場合だけ。切り出しが無理なら、U6a・U6b・U7 を U6c(と U8)と**1つの push の束**にする。
- この場合、README 項23 の「U6c の前後の差」は不要になる(途中の状態を採用者へ出さない)。IMPL-0931・1029 の「U6c まで undelivered」の扱いは、同じ push で delivered にできるので簡単になる(途中の開示の定義が減る)。
- 代わりに #445 を閉じる時期は、B30 の push に依る(案も同じ)。B30 が長引くなら、指揮役が U6a・U6b・U6c の順序を B30 の push の時期と相談する。**途中の状態を出すこと自体は、採らない案として記録する**。

## 6. 案への追加(穴の補い)

1. **受けた事実の証跡**: 段の出力の1行に、行の ID・スコア・下限・承認した者・(A) のレビューの識別子とレビューの対象のコミットを含める。集約がログを読まない(保持の期限がある)ので、台帳の行と PR のレビューが正本で、段の出力は補助(案の「受けないもの」の記録と同じ位置づけ)。
2. **時計**: `localDay()` は実行環境の現地の日付。Actions は UTC で、期限の日付の境で受否が変わる。案の「日付を引数で受け、関数は時計を読まない」のとおり。試験の期限は固定の日付(案のまま)。
3. **score と閾値の尺度**: 下限・閾値・スコアを同じ尺度(0〜100)で比べる。`parseMutationResult` の尺度が 0〜1 なら印の下限と食い違う(今回は読んでいない。実装の担当が確かめる)。
4. **二重の受け入れ**: 同じ PR に2行(下限の違う)があれば、条件を満たす行が1つでもあれば受ける(案のまま)。出力の ID は、最初に満たした行のうち、下限が最も高い行にする(決定的にする)。
5. **gate-g5.yml の `contract` ジョブ**: 新しい試験(段の取得の `.mjs`・週次の型)を `gate-contract` の run 一覧へ足す。足さないと CI で走らない(test-adapter.mjs は既に一覧にある)。新しい試験のファイルを作るなら一覧への追加と `verify-gate-contract` の結線が要る。既存の test-adapter.mjs に置けば不要。
6. **ADR-0243 の決定 4 の文言**: 「ホスティングの記録で確かめたときだけ」を、「マージの方式別の確認は squash の1件の push に限る(未確認の方式は受けない)」と、課さないことを明記する。
