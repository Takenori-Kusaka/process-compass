# #457 再審議 会議体 意見(現場委員)(2026-11-27)

立場: AI エージェントで日々 PR を回す開発者とレビュアの目。読んだもの: CLAUDE.md、r2-intake.md、r2-options.md、r2-external.md、ADR-0267、#467 の本文。本文の行は自分で確かめた分だけ「確認」と書く。

## 1. 先に答える: 追跡を読むのは誰で、いつか(現場の前提)

| 読む者 | いつ | 何を探すか | 入口 |
| --- | --- | --- | --- |
| レビュア | PR の Ready 時 | 差分と PR の要約。追跡の鎖は辿らない(**推測**。r2-external が引く Copilot の文書も「要約と差分を見る」とする[二]) | PR の画面 |
| 保守者 | 数か月後。`git blame` でその行のコミットに着いたとき | なぜこう書いたか | squash 後のコミット → PR の番号 → PR の画面 |
| インシデント対応 | 障害時 | 同じ条件の変更の一覧、直前に変わったもの | トレーラ、宣言の履歴 |
| 内部監査・決裁者 | 抜き取り | 「後から説明できるか」の標本 | 判定の記録 → PR |

**平時に鎖を読む人はいない**(推測)。読まれるのは事後の3者で、いずれも入口は「main の1コミット」である。すると追跡の設計は「変更ごとに全部書く」(push)ではなく、「1コミットから辿り直せる」(pull)でなければならない。所有者の「チケットのように」は、現場では Issue → PR → コミットの形で既にある(r2-external の総括と一致)。足りないのは新しい様式ではなく、**入口の PR に何が残るか**である。

## 2. 論点1: 一続きの追跡

### 採る案: 1-B'

1. **入口を PR に一本化して書く**。手引きに「1つの変更を後から辿る順序」を置く。起点は main のコミット → PR(本文)→ トレーラ `Spec`(目的・受入基準・タスク)→ 検証の記録(G-6 基準6)→ 理由(5.5.1)→ `Agent-Run`。新しい欄は作らない。
2. **K7・K8 を本 Issue で直す。順序は「直す、確かめる、書く」**。直す前に道筋だけ書くと、書いた道は既定の運用で途中が切れる。
3. H.3 の行は**2行のまま**にし、列の文だけ改める。1行に寄せない(区分の導出が粗くなる、は r2-options の指摘に同意)。
4. K1(Issue 番号・`setup` の変更は目的に辿れない)は、道筋の限界として同じ場所に開示する。

### K7・K8 の現場の実態

- **確認**: `phase5-implementation/pr-workflow.md` L123 は理由を「選択の時点のコミットのメッセージ」へ勧める。git-strategy の手引きは squash マージを既定、マージ済みブランチを自動削除と書く。勧めどおりに途中のコミットへ書くと、既定の運用では main に残らない恐れがある。
- **確認**: 集約スクリプトは squash を方式の1つとして数える(template `aggregate-evidence.mjs` L1807・L1847 に 'squash' の語)。squash 後のコミットから PR を引く仕組みはある。中身は読んでいない。
- **推測(要実行での確認)**: GitHub の squash の既定のメッセージは、リポジトリの設定で「PR の題と本文」「PR の題とコミットの並び」のどちらにもなる。ci-gates L168 は前者(引用)を前提とするので、途中のコミットのメッセージは落ちる。設定の取り方で結果が変わるので、K7 は template の既定の設定での観測が先である。
- 現場の感覚(推測): エージェントは途中のコミットを細かく切る(試行錯誤で 10 本以上)。そのメッセージへ理由を書かせると、**書いた本人(エージェント)は書いたつもり、読む側は何も見つからない**。破られて失うのは書き手ではなく後の保守者である(r2-intake §7 と一致)。

### K8 の直し方への意見

r2-options の (a) PR の本文へ写す、(b) スカッシュの設定を変える、に加え、現場から次を挙げる。

- **(c) 証拠を PR の段階で採る**: マージ前の CI は PR のコミットの全トレーラが見える唯一の時点である。そこでトレーラを集約して証拠として保存し、squash 後に履歴から探さない。**集約スクリプトがマージ後の履歴を読む設計か、PR 段階の API を読む設計かは、確かめていない**。確かめる者を議長が指名してほしい。
- 現場の好みは、人にも AI にも手で写させない形(a か c)。(a) の「PR の本文の末尾へ写す」を手作業にすると、IMPL-1033 の限界が「書き忘れ」へ姿を変えるだけである。機械が写すこと、写した値が PR のコミットと一致することは、決定可能な検査にできる。
- 直るまでは H.3 の「最も弱い止め方」へ `未達` として出す(r2-intake のとおり。ADR-0028)。

### 退ける案と理由

| 案 | 理由 |
| --- | --- |
| 1-D チケット様式の新設 | 欄を埋めるのは AI になる。ステップの欄は 5.8.6 要求事項8(AI に操作の要約を書かせない)と衝突する。AI が埋めた6欄は「もっともらしく均質」になり、レビュアは読まなくなる(**推測**。FND-0020・0070・0228 の向きと一致)。#467 の「読まれない証跡」の典型 |
| 1-C 追跡の要求事項化 | 識別子での参照を G-6 基準6 に課すと、差し戻しの理由が「形式」になり、形式だけを満たす記入に寄る(FND-0020)。文書・設定の PR(K1)では受入基準が無く、例外規則が要る。K3 は様式の注記に止める(機械の検査にしない) |
| H.3 を1行にまとめる | 「機械の記録(拒否・パスの差)」と「人の記録」の止め方の区分が1升に混ざる。導出が粗くなる |
| 1-A 現状維持 | K7・K8 を放置する。採らない |

### 残る懸念

- 道筋は手引きで、守られたかを機械は確かめない。ただし「辿れるか」は、抜き取りの監査で実際に辿ってみる(1コミットから PR・Spec・検証の記録へ到達できるか)という実行の確認で閉じられる。**書く量でなく、辿れた件数で測る**ほうが現場の負担に合う。
- 「リンクの存在は整合を意味しない」(Automotive SPICE 4.0 の注記、r2-external 引用)。道筋は整合を保証しない。この限界は書く。

## 3. 論点2: 「何を調査したか」の範囲

### 採る案: 2-A + 2-C(広げない。調査の結果は既存の器へ)

**エージェントが自分で書く「調査の記録」で、実際に何が残せるか。**

| 種類 | 例 | 残せるか | 事後の作文か |
| --- | --- | --- | --- |
| (i) 実行の事実 | 読んだファイル、実行したコマンド、検索 | 機械が残せる(実行の記録。`Agent-Run`) | 作文ではない。ただし量が多く**ほぼ読まれない**(推測)。何が効いたかは分からない |
| (ii) 判断に効いた資料の所在 | 「AC-3 に依った」「規約 X に従った」 | 5.5.1 の理由の形(L447)が既に求める | 選択の時点なら事実。後からだと作文に寄る |
| (iii) 調べた結論の言い換え | 「A と B を検討し A が適切と判断」 | 書ける | **大半は事後の作文**。思考の連鎖の忠実さ(20% 未満、r2-external [二])の向きと一致。本物の動機は書かれない |
| (iv) 調べなかったこと | 「X は見ていない」 | **残せない**。エージェントは見ていないものを知らない | — |

所有者が価値を置く「何を調査して、どのインプットに基づいたか」のうち、**残せて作文にならないのは (i) と (ii)** である。(ii) は ADR-0267 が既に覆っている。(i) は機械の記録で、保持は採用者に委ねられている(IMPL-0512)。現場で本当に欲しいのは調べた量ではなく (iv)(見落とし)で、記録では取れない。

### 退ける案と理由

- **2-B(全変更で調査を残す)**: 書くのは AI で、(iii) が量産される。レビュアは毎回同じ型の文を読み飛ばす。ADR-0267 が退けた「全選択に理由」と同じ欠点。
- **2-D(実行の記録の保持を標準の義務にする)**: 事実は残るが、読む者は事故・監査のときだけ。会話に秘密・個人情報が入る。採用者への新しい義務で、読まれない証跡を増やす。#467 の観点に逆行する。ただし「保持が採用者次第」という状態(IMPL-0512)は、K5・K6 の欠けとして開示し続ける。
- **第7章の例外承認で受ける案**: 調査の記録は満たす基準ではないので、例外の対象にならない。全変更に常態で掛かる記録を例外で受けると台帳が埋まる(ADR-0267 の採らない案と同じ)。

### 追加の提案(r2-options に無い案)

- **2-E 調査そのものが作業のとき、成果物は成果物として扱う**: 人が「X を調べて」と指示した作業では、調査の結果が成果物(research のメモ、判断記録の代替案)である。これは追跡の記録ではなく納品物で、既存の確認の対象になる。所有者の言う「何を調査したか」の大半は、現場ではこの形で既にある。手引きに一文で示す。

### 残る懸念

- AI が読まずに書いた場合を記録から見分けられない(ADR-0267 の限界と同じ)。(i) の保持が採用者次第である点。いずれも開示で受ける。
- 「新しい ADR で採らない旨を残す」案は、現場には効かない記録が増えるだけである。ADR-0267 の「採らないと決めたこと」の表へ1行足すか、論点3 の ADR と1本にまとめて書くほうがよい。決めるのは議長。

## 4. 論点3: モデルの版

### 現場で版は何の役に立ち、立たないか

| 立つ | 立たない |
| --- | --- |
| 「いつから挙動が変わったか」を区切る印。変化点の起票(3.13.1)、宣言の更新(推測) | **再現**(非決定性、別名。r2-external の限界の節) |
| 宣言と実態のずれの検出(3.13.5)。FND-0059(E2)は指定と実際が違った事例(引用) | **説明**。レビュアは版を見て差分の良し悪しを決めない(推測) |
| インシデントで「同じ条件の変更の一覧」を作る(引用) | 「この版だから信頼できる」の根拠。正しさは検証の記録が担う(5.8.2 L1158 の趣旨。引用) |
| 安全関連部の構成管理(safety-verification 要求2。引用) | |

実績: 影響範囲を絞れた例は無く、標準自身が E0 と開示している(引用)。

### 採る案: 3-A + 3-D

- 所有者の意見のうち、**「説明・証跡としての価値は無い」は採る**。H.3 の行(L298)の証拠の列から版を外し、C10・変化点・影響範囲の側の表示へ移す。ADR-0012 決定3 の「再現できず」(X2)は、本件で置き換えてよい。
- **「版を記録する価値は無い」は採らない**。規格が版を取る目的は構成管理・変更管理であり(r2-external)、3.13.5 と安全関連部が依る。ただし**費用が「ほぼ無い」のは、自動で出る場合に限る**。現状、モデルの識別は担い手が `Co-Authored-By` へ書き、導出元からの自動は未達(IMPL-1034)である(引用)。手で書く運用では、別名のまま書く、書かない、複数のモデルが動いたのに1つだけ書く、が起きる(推測)。
- 3-D(確かさを先に上げる)を同時に採る。

### 退ける案と理由

- **3-B(変更ごとの記録をやめる)**: 穴5つ、うち安全関連部は重の審議の外の議題。やめて減る負担もほぼ無い(自動のため)。
- **3-C(期間の記録で代える)**: 宣言と実態がずれたとき(FND-0059)、期間の記録は実態を映さない。複数のモデルが並行で動く構成では一意に決まらない。ただし K8 の影響を受けない利点がある。変更ごとの記録が既定で落ちる間は、宣言の改訂履歴の日付を粗い補助として手引きに併記してよい(補助であり、代替ではない)。

### 残る懸念

- 版の記録が実際に使われた実績が無い(E0)。使われなければ「読まれない証跡」として #467 で再び問われる。E0 の差し替え条件へ「使われた実績が出ないとき縮小を検討する」を入れる。
- 担い手が自己申告するモデル名の正確さは**確かめていない**(推測)。実行基盤の設定から機械が書く形が先である。

## 5. 最も重い懸念

**標準の鎖と版の記録は、既定の運用(squash、ブランチ自動削除)で途中が切れる(K7・K8)。その上に「一続きの追跡」を名乗ると、現場には「辿れるはず」という誤った安心だけが残る。**

- 破られたとき失うのは書き手ではない。後の保守者・インシデント対応・監査人である。書いた者は書いたつもりのままである。
- 論点1 の価値は、K7・K8 が直ることに依る。論点3 の「記録を保つ」も同じである。**直せなければ、1-B' も 3-A も `未達` の表示を伴って採る**。
- 実行での確認が出る前に、K8 の直し方(a/b/c)を決めない。私の (c) は確かめていない案である。

## 6. 議長への勧め

1. **K7・K8 を本件の範囲で直し、実行での確認を条件にする**。IMPL-1052(D1 で降ろす)の記録先の文を先に直す。直るまで H.3 に `未達` を出す。
2. 論点1 は 1-B'。H.3 は2行のまま。「道筋」は手引きの1節。追跡できたかは、抜き取りで1コミットから辿る確認で測る。
3. 論点2 は広げない。手引きの一文(調査が作業なら成果物として扱う。2-E)と、採らない旨の1行で足りる。
4. 論点3 は、ADR-0012 決定3 の置き換え(X2)と H.3 の移し替え。版の記録は保つ。自動の記録(IMPL-1034)を先に進める。E0 の差し替え条件に「使われた実績」を入れる。
5. 所有者の意見への回答は、2点を分けて書く。**採る**: 版は説明の証跡ではない。全記録は取らない。**採らない**: 調査の欄の新設。版の記録の廃止(影響範囲・ずれの検出・安全関連部の構成管理が失われる)。
6. 例外承認(第7章)では受けない。記名欄は足さない。

## 7. 確かめていないこと

- 集約スクリプトが squash 後のトレーラをどの時点・どの入力で読むか(語の存在までは確認、中身は未読)。
- 担い手の自己申告するモデル名の正確さ。
- エージェントが細かく切るコミットの実数(推測)。
- r2-intake の行番号の引用(H.3 L298 ほか)は再確認していない。確認したのは pr-workflow L123 の文と git-strategy の squash 既定の文だけである。
