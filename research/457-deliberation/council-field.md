# #457 会議体 意見(現場委員)

立場: AI エージェントで日々 PR を回す開発者・レビュアの目。記録の負担、形骸化、AI の後付けの作文を問う。確認した本文: human-ai-boundary 5.5.1(L436-443)、pr-workflow L113-121。

## 結論

案 B に条件付きで賛成する。案 C・D・E の不採用に賛成する。ただし B の文案は、現場では次の形で形骸化する。修正を求める。

## 論点ごと

### 1. 理由を 5.5.1 の記録へ含める(案 B): 賛成(条件付き)
- 賛成の理由: 5.5.1 は既に「選択を記録する」を全変更に課している。理由の有無で負担はほとんど変わらない。後任が「制約か偶然か」を区別できる点が現場の実益である。
- 欠陥1: **書き手が AI なら負担が小さい、は形骸化の根拠になる**。案の第1節は、危険は読む側にあるとする。書く側にも危険はある。AI は理由を無料で、もっともらしく書ける。「保守性のため」「一般的なため」が全選択に付くだけの形になる。arXiv:2505.05410 を引きながら、案は書く側の定型化を防ぐ手を持たない。
- 欠陥2: **「差分から読み取れる選択は書かなくてよい」は AI が判定できない**。AI は自分の選択を自明と見なしがちで、書き漏らす。反対に、何でも書く側にも倒れる。範囲を定める基準が主観のままである。

### 2. 範囲を絞る基準(代わりの案)
- 理由を書く対象を「退けた案があった選択」と「外部の制約に従った選択」に限る。書く内容は、退けた案とその理由、または従った制約の所在(受入基準の項番、既存コードの規約、依存の制約)とする。
- 利点: 書く者が客観的に判定でき、定型文の「最適なため」を排除できる。後から読む者が欲しい情報(なぜほかでないか)にも合う。
- 限界: 自由な文の意味は機械で確かめられない。案どおり manual とし、根拠水準マークで開示する。これには賛成する。

### 3. 書く時点
- 欠陥3: 案は記録先をコミットのメッセージか PR の本文とするが、**書く時点を決めていない**。PR の Ready 直前にまとめて書くと、後付けの作文になる。
- 手引き(pr-workflow)で、選択の時点のコミットのメッセージへ書くことを推奨する。条文には置かない。結果と証跡までという所有者の方針に合う。

### 4. 第7章の例外承認で受けられないか
- 受けられないという案の結論に賛成する。7.3 は満たさない基準の例外であり、記録の中身の定義ではない。
- 追記したい点: 7.3 を「理由を書けなかった」逃げ道にしないよう、5.5.1 の理由は例外承認の対象外と明記する必要はない。そもそも基準ではないため、書かないほうがよい(書くと対象に見える)。

### 5. 破られたとき誰が何を失うか
- 案の表に賛成する。1つ補う。理由が定型文化したとき、失うのは 5.5.1 の確定の場の人である。「まとめて確認する」が、読まない承認に縮退する。人の席の責任者が最初に失う。

### 6. 作成側の主張として扱い、検証の根拠にしない
- 賛成する。ただし、**G-6 手順5(入力の分離)で既に担保されている**。5.5.1 へ同じ文を足すと重複し、将来の食い違いの原因になる。参照で足りる。案 6 節3 の「重複なら足さない」の判断に同意する。足すなら一文の参照に止める。

### 7. 案 C・D・E
- 不採用に賛成する。C は入力の分離を壊す。D は全変更の ADR で渋滞し、レビュアの注意が尽きる。E は会話の全文を理由の記録と見なす誤りで、現場も読まない。

### 8. 統制と未達
- manual で閉じ、EV を E0 で付けることに賛成する。差し替え条件に「理由欄が定型文の割合」を置くのは良い。測り方(何を定型と数えるか)を実装の担当が1行で定義すること。
- template の変更を束 D1 へ回し、IMPL を undelivered とすることに賛成する。注意: テンプレートの PR 様式は既に「何を、なぜ」と求めている。降りていないのは主に CLAUDE.md の常駐の行と skill 手順3 である。マークの note にそう書き、「様式は先行している」ことを読み手に区別させる。

### 9. 範囲の外(§2.6)
- 本束へ混ぜない。ed 候補は議長が直す。軽の2件は既存の open Issue へコメントで足す(後継は既存の Issue へ寄せる方針)。

## 裁定の案への修正要求(要約)
1. 書く範囲の基準を「退けた案がある選択、または外部の制約に従った選択」へ客観化する。
2. 書く時点の手引き(選択の時点のコミット)を pr-workflow へ置く。
3. 作成側の主張の扱いは、G-6 手順5 への参照だけにする。
4. 書く側の定型化を、危険として第1節の表へ足す。
