# #356 反対委員の意見(軽の審議・A 降ろし方)

担当: 反対委員。対象は intake.md 表 A の 19 件。B-1〜B-6 には意見を書かない。template は `origin/main` を `git show` で読んだ(行番号は `scripts/gate/aggregate-evidence.mjs`=agg、`scripts/gate/adoption-trial.mjs`=trial)。

## 立場

降ろす側の誘因は強い。19 件が `undelivered` のまま台帳に出続けるのは気持ちが悪いからである。しかし「降りていない」の表示は、それ自体が信頼性の開示として機能している(`undelivered` は消さず表示し続ける、が本プロジェクトの規則)。無理に降ろして得るのは台帳の見かけであり、失うものが 3 つある。

1. **偽りの安心**。部分的な機械の検査(標識の文字列の存在など)が通ったことが、「流出しない」「測れた」と読まれる。条文自身が「4層あるので流出しないと記録してはならない」と書いている。検査を足すほど、この記録をしたくなる誘因が増える。
2. **決定可能でない条件の偽装**。周知の 6 項目の中身、欠陥の性質(規約上指摘されるべき)、難度の較正、停止の申請の妥当性は、自由な文の意味である。欄の存在を機械で確かめると「確かめた」ように見えるが、確かめたのは欄が空でないことだけである(`isFilledValue` の類。trial:139 が `file`・`line`・`type` の存在だけを見るのと同じ水準)。
3. **採用者の既存の運用を壊す**。出荷の集約(ship-evidence は `push: tags: ['v*']`、ship-evidence.yml:58-60)を失敗させる変更は、全採用者の出荷を止める。項目6 は現在、記録が無ければ「未測定」で通る(agg:4372-4380 の読み方)。第4層(IMPL-0192)で「scanRun が無ければ失敗」にすると、欠陥注入を一度もしていない採用者(附属書H が認める多数派の運用)のタグが全て落ちる。

運用中の継続の欠陥注入は、附属書H が実施主体と件数を組織に委ね、未測定を正当な値として受け入れる運用である。template が演習の仕組み(`scripts/drill/`、`.github/rulesets/drill.json`、`seeded-error-scan.yml`)を持てば、採用者は「入れた以上は使わねばならない」仕組みを抱え、使わないと未達の表示が常時出る。これは細かい定義の増加であり、柔軟性の喪失である。

所有者の 3 つの問いに照らすと、(1) 結果と証跡までは条文で足りており、手順(ブランチの名、トレーラの形、期限の削除)を機械にするのは手引きの領分の固定である。(2) 運用中の継続の注入をしない構成は、項目6 の「未測定」と第7章の例外承認で既に受けられる。(3) 破られたとき失うものが大きいのは「流出」と「個人の識別子」の 2 つだけで、他の 17 件は測定の妥当性(未測定として開示される)に留まる。

## 起案側が出すと予想する案への反論

### 予想される案1 「第1〜4層を、決定可能な存在の検査として一式降ろす」

反論:

- **squash の穴**。intake 2章の実行で、squash(既定の文)ではトレーラは 0 件、本文の文字列では 1 件であった。第2層の「取り込みの拒否」をトレーラで書けば抜ける。本文の grep にすれば、squash の文を書き換える通常の操作で抜ける。どちらも「通常の操作の範囲」の内で、条文が約束する「通常の操作の範囲で流出が起きない」を満たさない。GitHub 上の squash は未確認(intake 自身が注記)で、確認前に固めるのは実証を欠く。
- **履歴を書き換えない約束は検査できない**。「標識の失われる履歴の書き換えをしない」は、強制 push を拒む保護の設定に依る。ルールセットを使えないホスティングでは効かない。効かない環境が「保護の欠落」として表示されるだけでは、採用者は演習を実施したまま流出の保証を失う。
- **四層の存在 = 安全、の誤読**。4 層が全部通ったことの出力は、「走査した」「標識なし」である。人が手で写した変更は止まらない(条文自身が開示)。出力に「手での写しは検査の外」と常に並記しなければ、条文が禁じる「流出しないと記録する」を、template が自動で出すことになる。
- **全出荷への波及**。第4層は ship-evidence(タグの push で動く、ship-evidence.yml:58-60)が読む。適用の宣言の無い採用者に「scanRun が無い」を失敗にすれば、演習をしない採用者の全タグが落ちる。失敗にしない形(未測定で通す)にすれば第4層の「記録が無い出荷は失敗」を満たさない。条文と実装のどちらかが誤りになる。これは降ろし方でなく**適用範囲の条項**(新しい義務)の問題であり、軽の範囲を越える。

### 予想される案2 「集約が `scanRun` を読み、`blind: false` と同じ方式で未測定へ」

反論: `scanRun: false` と「走査記録なし」は異なる。agg:4372-4380 の `unmeasurableReason` は「測定値として数えない」ための仕組みで、「失敗させる」仕組みではない。同じ読み方を流用すると、「未測定」で通ってしまい第4層の要求(失敗)を満たさない。逆に失敗にすると、K-3 の指摘通り template は標準より強くなる。強い側へ倒す根拠を、軽の審議で与えるのは不適切である。

### 予想される案3 「周知・性質・停止は様式の欄と manual で降ろし、台帳をほぼ全部 delivered にする」

反論: `delivered check=manual` は、本件で既に先例がある(0157・0162 は delivered manual だが、対の試験が無い、#314)。manual で降ろした 17 件は「降りた」と数えられ、台帳の `undelivered` が減る。しかし実際は、template に新しい欄が増えただけで、確かめる者は同じである。**台帳の見かけが良くなることは、信頼性の向上ではない**。`plan=adopter` として「採用者の運用」と明示するほうが、「書かれていない」と「課さないと決めた」を区別するプロジェクトの原則に沿う。

### 予想される案4 「0627・0666 は 7.9 の発動を、注入の結果から機械で検出して記録の欠落を出す」

反論: K-2 は B-5 の争点である。条文は「何から数えるか」を書いていない。範囲で数えるなら識別子は要らないが、IMPL-0118 は「対象の人」を要する。機械で検出して制限の記録を促す仕組みを置けば、5.6.2 が禁じる「措置の実装への組み込み」に当たりうる。固めてから B で解くと、直す先が template の実装まで広がる。

## 反対の立場でも降ろすべきと認めるもの

失うものが取り消せない、または個人に及ぶものに限る。

1. **0047 第3層(リリース候補の走査)**。出荷の後は取り消せない。標識の文字列の存在は決定可能で、運用中の継続の注入をしない採用者にとっては検査が空で通るだけで、出荷を壊さない。条件: (a) トレーラ解析だけでなく `%B` 全体を走査する、(b) 標識の文字列を単一の定数にして B-4 で変わっても 1 か所で直せる、(c) 通ったことを「流出なし」と出さず「標識の残存なし(手での写しは対象外)」と出す。
2. **0197 の template 自身の出力**。識別子の欄を持たないことの検査。ただし先に trial の `perFinder`・`finders` と条文の突合が要る(条文が「検出者を識別する欄を含めない」と言う以上、`finders` の名簿を出力へ出すのは緊張する。ADR-0067 決定6 で説明済みかを確かめる)。
3. **0196 の依存の定義ファイルへの注入の警告**。決定可能な一部だけ。
4. **0168 の注記の訂正**。降ろし先の変更ではなく編集の指摘。会議体を開かず、議長が直して独立の突合を 1 回行う。
5. **0160 の 1 文**。様式とスキルへ置くのみ。

## 手続上の指摘

- 19 件を一括で「降ろす/降ろさない」とせず、規定ごとに分けて裁定すること。0168 は食い違いの解消(編集の指摘)、0197 は template と条文の突合、0192 は適用範囲の新しい義務で、種類が異なる。0192 の適用範囲の限り方が新しい義務に当たるなら、intake 4章の規則により、割れた点として B(重)へ上げる。
- `plan=adopter` にする 9 件は、ADR に「なぜ template に降ろさないか」を書く。理由は「安さ」ではなく、決定可能でないこと(意味の問題)・降ろすと偽の安心を生むこと・採用者の運用に依ることの 3 つに限る。
- 採らない案の記録: 「19 件すべてを manual で降ろして `undelivered` を 0 にする」を、台帳の見かけのための案として却下する。
