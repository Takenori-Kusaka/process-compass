# #356 軽の審議 起案委員の意見(A=降ろし方)

担当: 起案委員。範囲は intake.md 表 A の 19 件。B-1〜B-6 には意見を書かない。A の案が B の結論に依るときは、表の最右列に依ると書く。template は `git -C template show origin/main:<path>` で読んだ(checkout は読んでいない)。行番号は origin/main のもの。

## 立場

準拠テンプレートは標準を体現し、連動させる。したがって、降ろせるものは降ろし、`plan=adopter` は「template が確かめる手段を持てない」ものにだけ認める。本件では、検討した 19 件のどれも `adopter` にしない(下の表)。ただし「降ろす」は、機械の検査だけを指さない。所有者の3つの問いに照らして、降ろし方を3種に分ける。

1. **機械の検査**(`machine`)は、**破られると取り返しがつかないもの**(注入した欠陥の製品への流出)と、適合の主張の信頼に響く記録の欠落にだけ使う。条件は決定可能なもの(文字列の存在・値の一致・日付の前後)に限る
2. **様式の欄・実在の確認**(`presence`)は、欄・キー・ファイルの有無までを確かめる
3. **手引き**(スキル・様式の注意書き)と `delivered check=manual` は、意味を機械で閉じない規定に使う。先例は IMPL-0157・0162(`delivered manual`)。台帳に「人が確かめる」と出るので、機械の検査の見かけにはならない

破られたときの損失が測定の妥当性だけにとどまる規定(頻度・難度・内と外・説明の提示との併用・停止の申請)には、機械の検査を足さない。細かい定義を増やさないため、新設する構造は次の2つに絞る。(i) 継続の注入の台帳 1 ファイル `docs/seeded-errors/ledger.json`(キーは下の「台帳のキーと根拠の条項」の 13 個)と、それを読む 1 本の検査 `scripts/gate/check-drill-ledger.mjs`。(ii) 標識の定数(接頭辞 `drill/`・`Seeded-Error:`)を 1 か所に置く。台帳を持たない採用者(継続の注入をしない)は、台帳が無いことで失敗しない。項目6 の「未測定」と G-8 の基準5 が既に受けている(intake §5(2))。

### 読んで確かめた事実(降ろし方の前提)

- criteria の各項目は、未記入なら `adoption-trial.mjs:337`「基準『…』が未記入」を出す(記入者は :331)。基準の表へ行を足せば未記入の検査に乗るかは、項目の読み取りの行を読んでいない。実装の担当が確かめる
- manifest が要るのは `injector`・`file`・`line`・`type` だけ(:136-139)。性質(要件3〜9)は manifest に無い
- 人ごとの検出の添字 `perFinder[...].hits` を `seeded-errors.json` へ書く(:236-243 付近。ADR-0067 決定6、見つける者が名簿から離れたときの読み直しのため)。率は出さないが、添字の数から人ごとの検出数は導ける。0160 の「人ごとの率を出さない」を `machine` にしない根拠の一つ
- 欠陥の台帳 `defect-ledger.md:31-33` に節「是正の記録」(起点「欠陥注入の見逃し」)があり、スキル `adoption-trial.md` 手順13が類型ごとに行を足すと案内する。同 :40 は「**機械はこの対応を確かめない**(…標準の IMPL-0497)」と書く。対応の機械の検査は IMPL-0497 の領分で、本件の範囲外
- 集約は、トレーラを `git log --format=...%(trailers:key=...)` で読む基盤を持つ(`aggregate-evidence.mjs:1325` 付近)。check-pr は PR のコミットをホスティングから引く(`check-pr.mjs:87`・:1467)。ただし intake §2 の実行確認で、squash 後は `%(trailers:...)` が 0 件、本文の文字列(字下げされる)には残る。標識の走査は**トレーラの解析でなく本文の文字列(`^[ \t]*Seeded-Error:` の行)**で行う
- 集約の項目6 は検出率だけを読み(:4098-4130)、`blind:false` の層を測定値にしない(:4372-4380)。`scanRun` は読まない
- ship-evidence.yml の冒頭の注記は、license-scan を別ジョブの成果物として取り込む経路(#286)を述べる。この経路の実行の中身(L80 以降)は読んでいない

## 反対委員が突くと予想する弱点と、それへの答え

1. **「delivered・manual は降りた体裁だけで、規定は守られない」。**
   答え: 台帳が `check=manual` を「人が確かめる」と表示する(ADR-0061)。先例は 0157・0162。意味を機械で閉じない規定を機械に見せると、統制の閉じ方の裁定(CLAUDE.md)に反する。逆に、`undelivered` のままにすれば、手引きの一文すら届かない。手引きは「規定がない」と読まれる状態を直す。降ろし先の文と確かめる者を note に書くので、確かめる者が空であれば検査が落とす。

2. **「台帳と検査の新設は、細かい定義の増加で、採用者の負担になる」。**
   答え: 台帳は継続の注入をする採用者にだけ要り、無ければ失敗しない。キーは条項の根拠を持つ 13 個に限り、新しい語彙(階級・点数・しきい値)を足さない。頻度・内外の割合・延長の回数はあえてしきい値を持たず、表示だけにした。標準の条文に無い数を template が作ると、標準より強い template(K-3 の轍)になる。

3. **「標識の走査を文字列で行うと、誤検出が増える(コミット本文に `Seeded-Error:` を引用しただけで落ちる)」。**
   答え: 誤検出は止める側に倒れる。流出は取り消せず、誤検出は PR の本文を直せば消える。損失の非対称が、(3) の問い(破られたとき誰が何を失うか)で決まる。squash の後に字下げされて残る形を拾うには、トレーラの解析では足りない(intake §2 の実行確認)。引用を許す例外は、第7章の例外承認で受ける。

4. **「0160 の『人ごとの率を出さない』は、`perFinder.hits` が人ごとの検出数を導けるので、すでに破れている」。**
   答え: これは本件の降ろし方の問題でなく、template の既存の設計(ADR-0067 決定6)と条文の緊張である。0160 を `manual` にとどめたのは、その緊張を機械の「適合」で覆わないためである。議長が、(a) 添字を残す、(b) 率でなく集合として扱うと note に開示する、のどちらかを裁定する。私の推す案は (b)。名簿から離れた者の読み直しという実用があり、率は出していない。

5. **「第3層・第4層を ship-evidence の中に置くと、同じジョブで書いた記録を同じジョブで読むだけで、独立でない」。**
   答え: 第4層の条文は「走査を実施したことの記録を渡し、記録が無い出荷を集約で失敗させる」(記録の有無の検査)で、走査の独立は求めていない。独立は第3層の失敗条件の厳しさ(1 件でも)で担う。別ワークフローで走らせて成果物で渡す案もあるが、`evidence/` が `.gitignore` の下で別ジョブに届かない問題(#288 第4巡)を再び抱える。license-scan の先例(#286)の取り込みは、別の実行の `headSha` の照合まで要り、複雑になる。

6. **「0193 を undelivered のまま残すのは怠慢で、(d) も `holds[]` に手書きさせればよい」。**
   答え: 条文は「緊急時に止める判断を担当者へ求めてはならない」と定める。ファストトラックを発動した最も余裕のない時点で、台帳へ 1 行足させる設計は、条文の違反である。発動の記録が機械で読めて初めて、自動の停止になる。降ろし先の前提が無いことを開示して残すのが、「降りていない規定は表示し続ける」に沿う。

7. **「`plan=adopter` が 0 件では、連動を強調しすぎで、template が肥大する」。**
   答え: 肥大を抑える工夫は 3 つ。(a) 台帳検査は 1 本、(b) 手引きはスキル 1 本(`artifacts/seeded-error-drill.md`)と既存スキルへの数行、(c) 機械は 4 件(流出に直結)に絞る。`adopter` は「template が確かめる手段を持てない」ときの区分で、本件の規定は手引きで届けられる。届けられない唯一の例が 0193 (d) だが、これは「採用者の責任」でなく「template の前提の欠落」なので、`adopter` でなく `scheduled` にとどめる。

8. **「標識の可視性(K-1)を A で無視している」。**
   答え: 無視していない。0190・0191・0047・0192・0195 を B-4 に従属と表に書き、定数 1 か所にした。A で決めるのは条件の形(文字列の存在・接頭辞)までで、名と形は B-4 の後に確定する。B-4 が決まるまで、これらの実装は着手しない案を推す。着手の順は、B に依らない 0160・0163・0196・0164・0168・0821(手引き)から。

## 採らないと自分で決めた案

- **`plan=adopter` を 0194 の席の照合・0164 の頻度・0195 の報告の手段に付ける案**: 採らない。降ろせないわけでなく、降ろす価値が小さいだけである(損失は測定の妥当性にとどまる)。降ろす価値が小さいものは、手引きと欄で足りる。`adopter` にすると、台帳に「採用者が実装する」と出て、template が何も届けなかったように読まれる
- **0194 の申請者・承認者の席を名簿で照合する機械の検査**: 採らない。席の名と責任の割り当ては採用者に依り、照合を足すと失敗の原因が増える。損失が測定の妥当性にとどまる(intake §5(3) の最後の行)ので、欄の実在で足りる
- **0196 の `seal` が依存の記録ファイル(`package.json`・各種ロックファイル)を拒否するガード**: 採らない。一覧は網羅できず、通ったことが安全の根拠に読まれる(適合の主張の信頼に響く)。要件8 が破れても、標識を持つコミットは取り込めず、第3層の走査で止まる。ガードは第2〜4層の上に重ねる必要が無い
- **0160 の「人ごとの率を出さない」を機械の検査にする案**: 採らない。`perFinder.hits` の既存の設計と緊張があり、率のキーが無いことを確かめても、添字から導けることを覆わない

- **0627 の発動を機械の失敗にする案(制限の記録が無ければ集約を落とす)**: 採らない(B-5 に依るが、私の立場として)。5.6.2 の「措置を実装へ組み込まない」と衝突し、演習が隠蔽の対象になる(条文自身の理由)。一覧に出して人が決める
