## 1. B-1 運用中の注入で、秘匿が成り立たない層を未測定にする要求

- **判定**: 採る。ただし範囲は「表示」に限る
- **条文の案**(5.6.2 の「事前の周知」の後に1段落。見出しに併記する適用: 運用中の継続の注入の結果の開示)
  - 「個々の注入の時期・箇所の秘匿が成り立たなかった層(注入する者が見つける者を兼ねる層、標識や箇所が見つける者に知られた層)の検出率は、測定値として載せません。秘匿の不成立と併記し、未測定として扱います」
- **課さないこと(明記する)**: 秘匿を成り立たせる体制の要求(注入者を分ける義務)。層の秘匿の不成立を理由にした是正の義務。ADR-0133 決定1 の「条件も措置も定めない」は保つ
- **理由**
  - 要求事項2 は既に条文にある。破れた層の値を測定値に載せることは、条文の義務を満たしていない値を、満たしたものとして読ませる。新しい行動の義務ではなく、既存の義務の結果の表示である
  - template は既に `blind: false` を測定値にしない(K-3)。標準が課さないままだと、template だけが強く、他の実装は載せうる。信頼の差が実装によって生じる
  - ADR-0133 決定1 の理由「措置を足すと測れたと読まれる」は、措置の話である。本案は載せることを止める向きで、この理由と逆向きに働く
- **落とす案**
  - 現状のまま、template の挙動を標準の注記で開示するだけ: 注記は規範ではない。他の実装が載せる余地が残り、読み手が実装ごとに別の意味で値を読む
  - 附属書I 要件③ を必須に格上げする: 要件③ は推奨のまま(#352 の訂正)。附属書の格上げは影響が広い
- **降ろし方**: 層ごとの `blind` の宣言があるかを機械が見る(存在)。`blind: false` の層が測定値の欄にあれば失敗(決定可能)。宣言が真かは自由な文の意味で、manual(確かめる者: 品質保証の担当)。template は既に前者を行う。及ぶ変更は 6 章の一覧
- **根拠水準**: 暫定 EV-NEW-A。注入者と発見者の分離は方法の前提だが、規格が要件にした形は確かめていない(IEEE 1028・29119 の本文は未読)。差し替え条件は、外部の確認者の評価と、`blind: false` の層が実際に載った件数
- **小さいチーム**: 1〜2名は常に未測定になる。新しい作業は無く、「未測定」と書くだけ。しない選択(継続の注入をしない)も残る

## 2. B-2 1.10.2 の秘匿の行を外すか

- **判定**: 残す
- **理由**
  - 行(1〜2名の体制、離脱の条件)は適合の主張を止める。B-1 は、主張が続く場合の値の表示を規律する。条件も効果も違うので二重にならない
  - ADR-0133 の決定から2日で、契機(EV-0160・EV-0265 の観測、#329 の裁定)は未発生。調査は外す根拠を示せなかった
  - 外せば主張の条件を緩める向きになる。信頼を判断軸にするなら、実証の追加が無いまま緩めない
- **落とす案**: 未測定へ一本化。測定の成立条件は離脱ではない、という読みは筋が通る。ただし、1〜2名で秘匿が成り立たないことを主張の水準で開示する行は、読み手に対して唯一の目印である。外す前に、読み手がそれを失って困らないことを確かめる必要がある
- **先送りにしない**: 契機が来たときの見直しは ADR-0133 の既存の枠による

## 3. B-3 注入する者を体制の外に置けることを条文に書くか

- **判定**: 課さないと明記する(条文には書かない)。手引きに書く
- **手引きの案**(フェーズ5)
  - PT 型の例: 外部の提供者が注入し、受け手は日常の手順で扱い、結果は提供者へ返る
  - 採用者が外部の注入者に求める条件の一覧: 周知の範囲、同意、流出の経路を開けない、守秘。UMN の件を、条件を欠いた例として引く
  - 条件は採用者と注入者の契約に委ねる。本標準は課さない
- **問い2への答え**: 例外承認では受けられない。調査のとおり、7.9.4 は制限下の例外決裁で、5.6.2 の免除ではない。しかも外の者が注入すれば、1.10.2 の行の条件(分けられない場合)に当たらず、そもそも離脱でも違反でもない。**新しい条項も例外承認も要らず、条文の読みで受かる**
- **落とす案**: 条文へ書く。外部の注入者の義務を書き始めると、公平性・守秘・同意の定義が増える。誰が課すかが空いたまま書くと、空の条項になる
- **破られたとき**: 条件を欠いた外部の注入は周知なしの注入になる。これは要求事項3(周知なしの禁止)が既に受けている。追加の条項は要らない

## 4. B-4 標識の可視性と秘匿(K-1)、B-6 手順の文、4層の文案

B-4 と B-6 は同じ文で解けるので、一つにまとめる。

### 4.1 診断

- 衝突の原因は、条文が**標識の置き場**(コミットのメッセージ)と**取り込みの拒否の手順**を決めていることにある。結果の書き方にすれば、置き場は手引きへ移る
- 先例(TIP・TIBER)は、印を受け手の目に入らない層で処理している。ただし git では、PR を見る者に見える面(題・本文・メッセージ・ブランチの名・作成者)を完全には隠せない。**「印を見つける者から隠したまま機械が取り込み前に拒否する」先例は無い**(調査 1.2)
- 隠して取り込み前に拒否する方式(指紋と外の台帳)は、台帳を持つ CI を要し、フォークの PR には渡らない。注入者=発見者の体制では台帳が秘密にならない

### 4.2 条文の案(5.6.2 実装上の要求の4層と周辺)

| 層 | 現行 | 案 |
| --- | --- | --- |
| 第1層 | 演習用のブランチでだけ注入。取り込み先を持たせない。判定の記録を採取した時点で閉じ、期限で削除 | 注入は、本番のブランチへ取り込む先を持たない場所でだけ行う。演習の変更が閉じられた記録と、場所が期限内に削除された記録を残す |
| 第2層 | 標識を必須。標識を含むコミットの取り込みを拒否。標識の失われる書き換えをしない | 注入したコミットは、機械が読める標識(識別子と期限)で識別できる。標識を欠いた注入をしてはならない。標識を持つ変更が本番のブランチへ入らないことを、取り込みの前または出荷の前に機械が確かめる。演習の場所で、標識の失われる履歴の書き換えをしない |
| 第3層 | 変更なし | 変更なし(無条件の走査。譲らない) |
| 第4層 | 変更なし | 変更なし |

- 「ブランチの名」「スカッシュ」「drill/」は条文に現れない形になる。名と例はフェーズ5 の手引きへ
- **残す手順の文**: 「標識の失われる履歴の書き換えをしない」。これは安全に直結する禁止で、標識が消えると第3層が見落とす。結果の文には直せない
- **緩める向きの開示**: 取り込みの拒否が「前または出荷の前」になる。取り込み前の拒否を必須にすると、隠す方式が条文に反する。この緩みは、第1層(取り込み先が構造として無い)と第3層・第4層(無条件で毎回走る)が受ける。取り消せない流出は止まる。ただし第2層の拒否が効かない構成で、注入が本番の履歴へ入った場合に、出荷の前まで気づかない遅れが生じる
- **根拠水準**: 暫定 EV-NEW-B。「前または出荷の前」で流出を止められるという判断は、手元の git(4通りの取り込みと5通りの指紋照合)の実行だけで支える。GitHub 上の squash は未確認

### 4.3 手引き(フェーズ5)に置く二つの方式

| 方式 | 標識の置き場 | 秘匿 | 取り込み前の拒否 | 向く体制 |
| --- | --- | --- | --- | --- |
| 既定(トレーラ) | コミットの本文 | 成り立たない。演習のレビュー面に標識が見える。未測定として扱う(B-1) | 保護ブランチ宛の PR で標識の文字列を検査(存在) | 秘匿を求めない、または秘匿が元から成り立たない体制 |
| 台帳と指紋 | リポジトリの外の台帳の塩付きハッシュ | 台帳に触れない者には成り立つ | CI が台帳を持つ場合だけ。持たなければ出荷の前の走査だけ | 注入者を分けられる体制 |

- 既定のトレーラ方式は、秘匿を犠牲にして機械の確実さを取る。そのことを手引きで隠さない。測定値としての扱いは B-1 の文が決める
- squash の文を書き換える運用の採用者は、標識が本文から消える。トレーラ方式では第3層が拾えない(`IMPL-0047` の note が開示済み)。台帳と指紋の方式を併用する、と手引きに書く

### 4.4 B-6 の手順の文

| 現行の文 | 案 | 残す/移す |
| --- | --- | --- |
| 報告は1つの操作で完了する形にする | 報告に要する操作を、通常の指摘より重くしない | 結果に改める。ラベルや1つのコマンドは手引きの例 |
| 演習の識別子を添えて報告する | 気づいた箇所と内容を添えて報告する。演習の識別子との突合は、注入する側が行う | 改める(下記) |
| 判定の記録を採取した時点で閉じ | 演習の変更が閉じられた記録を残す | 時点の指定を外す |
| ブランチは期限で削除する | 場所が期限内に削除された記録を残す | 証跡に改める |

- **「演習の識別子を添えて報告」は K-1 の別の顔である**。見つける者が識別子を知っているなら、標識が見えている。注入に気づいた者は、識別子ではなく、気づいた箇所と内容を報告し、突合は台帳を持つ側が行う。PT の「結果は提供者へ返る」と同じ形である
- **番号の安定**: 番号 IMPL-0195 の意味(気づいたときの手続)は保つ。表の行番号は変えない(ADR-0076)。写した記録の番号は動かない
- **削れる条項**: 手順の文4本(上表の上から4行)。結果の文に統合し、条文は短くなる。足すのは、場所の削除の記録の1文だけ
- **落とす案**: 手順を全部手引きへ移し、条文には結果だけ残す。「してはならない」まで外すと、何が不適合かが曖昧になる。除去型の禁止と標識の書き換えの禁止は、破られると流出に直結する

## 6. B-5 7.9 の発動を何から数えるか

- **判定**: 採る。二層(範囲・類型で数え、知らせるだけ。誰の権限かは人が決める)
- **7.9.1 の案**
  - 行1: 「注入した欠陥を、同じ範囲・同じ類型で、連続2回、または直近3回のうち2回見逃した」(主語を人から範囲・類型へ)
  - 行2: 5.6.3 の区分が「意図的な違反」に当たった(人の手続。1回で発動)。主語は人のまま
  - 追記: 数えるのは範囲・類型・結果(検出/見逃し)の列で、検出者・見逃した者の識別子を使わない
- **7.9.2 の案**: 「検知された者の承認」を「検知された範囲の承認」に改める。IMPL-0118 の集約が既に範囲で数えている(「だれが承認したかに依らない」)。条文を実装に合わせる
- **誰の権限かは品質保証が決める**: 5.6.3 の判別は人の手続。範囲の承認権限者の誰に制限を掛けるかは、機械が決めない。5.6.2 の「措置を実装へ組み込まない」と整合する
- **意味が変わる点の開示**: 主語が人から範囲に変わる。これは編集の指摘ではない(調査の指摘どおり)。個人の不利益は減る向きで、範囲全体の2名要件を負う者が増える向きである。小さい体制では範囲=人で、実質は変わらない
- **落とす案**
  - 人で数える: 5.6.2 の識別子の禁止と、措置の組み込みの禁止に衝突する。フィッシング訓練の逆効果の知見(約19,500名)とも反する
  - 機械が発動まで決める: 措置の組み込みに当たる。演習が隠蔽の対象になる
- **根拠水準**: 閾値(連続2回)は EV-0064 のまま。単位を範囲×類型にする判断は暫定 EV-NEW-C(CLIA の「検査室×項目」との類比。E1)。件数が足りない体制では発動しない旨は条文に既にある
- **問い3**: 人を数える設計が破れると、レビューする個人が人事上の不利益を受け、報告が止まる。この線は細かく書く。範囲を数える設計が破れても、失うのは測定の妥当性だけ

## 7. 必ず通す3つの問い

1. **満たすべき結果と証跡までか**: 4.4 のとおり。手順の文4本を結果と証跡へ改め、ラベル・コマンド・ブランチの名は手引きへ。残すのは、破ると流出に直結する禁止3つ(除去型・標識の失われる書き換え・申告だけで止めること)
2. **例外承認で受けられないか**: 外部の注入者、注入者=発見者、運用中の注入をしない構成は、新しい条項なしに、既存の行(1.10.2)・項目6 の未測定・条文の読みで受かる。例外承認は 7.9.4 の枠で、5.6.2 の免除には使えないので、使わない。使うのは、標識の文字列を含むコミットの偽の失敗だけ(ADR-0139 の裁定のとおり)
3. **破られたとき**: 

| 破れ方 | 失う者と失うもの | 書く細かさ |
| --- | --- | --- |
| 注入が製品へ届く | 製品の利用者と採用者(取り消せない) | 細かく書く(第3・4層、標識の失われる書き換えの禁止、除去型の禁止) |
| 秘匿が破れた層が測定値になる | 保証の読み手の信頼 | B-1 の一文(表示だけ) |
| 人で数える | レビューする個人 | 識別子を使わない一文 |

## 8. 条項を足す分と、削る分

- **小さいチーム**: 継続の注入をしなければ、ほぼ何も増えない。する場合は「未測定」の表示と、場所の削除の記録だけが増える

## 9. 採らない案のまとめ

| 案 | 採らない理由 |
| --- | --- |
| B-1: 注記だけで開示 | 規範でない。実装ごとに読み手が別の意味で値を読む |
| B-2: 秘匿の行を外す | 契機が未発生。主張の条件を緩める。読み手が目印を失う |
| B-3: 外部注入者の義務を条文へ | 誰が課すかが空のまま、定義だけが増える |
| B-4: 取り込み前の拒否を必須のままにする | 隠す方式が条文に反する。フォークの PR で台帳が渡らない |
| B-4: 標識を git notes に置く | squash・cherry-pick で失われる。第3層の前提が崩れる |
| B-4: 秘匿の要件を「箇所」に限る(案D) | 標識で注入と分かる。TIP の「合成と分かる」問題と同型 |
| B-5: 人で数える | 識別子の禁止・措置の組み込みの禁止に衝突 |
| B を待つ6規定を `scheduled` のまま残す | 実行の計画が無いまま残すことになる。理由を書けるので ADR-0084 の枠に収まる |

## 11. 確かめていないこと

- GitHub 上の squash・rebase の挙動。手元の git だけ
- 指紋方式の偽の一致の率、注入した行を一部だけ直された場合
- ADR-0133 決定5 の本文(調査も読んでいない)。引いたのは決定1。突合の担当が決定5 と決定1 の対応を確かめる
- 規格(IEEE 1028・29119・ISO/IEC 17043)の本文。「規定が無い」とは言えない
- B-1 の「秘匿の不成立」の範囲を、標識が見える層まで含める線引き。含めると採用者の新しい義務に近づく。議長が、重の枠(新しい義務)に当たるかを裁定する
