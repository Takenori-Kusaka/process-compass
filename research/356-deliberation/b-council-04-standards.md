## 0. 先に開示すること

- **規格の本文は誰も読めていない**。IEEE 1028-2008 は、米 NRC の指針(SRC-0523)が是認した規格として台帳にあるだけで、欠陥注入の規定を確かめた記録は無い。ISO/IEC/IEEE 29119 は SRC-0691(-3 のカタログ、abstract 読み)と SRC-0545(CTFL)だけで、欠陥注入の指標の規定は確かめていない。ISO/IEC 17043 は台帳に無い。よって本意見書は「規格がこう要求する」とは**言わない**。規格の立場で言えるのは、(a) 規格が要求として書く形(検証できる結果と証跡)に条文が合っているか、(b) 既存の ADR・条項と矛盾しないか、の2点である
- **突合の訂正(1件)**: 調査と議題は「ADR-0133 決定1」を B-1・B-2 の根拠にしている。実際は、秘匿の行を表に残す根拠が決定1 の表、**運用中の未測定の要求を置くかを #356 へ寄せた**のが決定5 である。つまり B-1 は ADR-0133 が明示的に残した問いで、置いても ADR-0133 の変更にならない。B-2(行を外す)は決定1 と決定5 の両方に触れる

## 1. 争点ごとの意見

### B-1 注入者=発見者の層を「未測定」とする要求を本文に置くか

- **判定: 課さないと明記する(第三の置き方)**。本文に新しい義務は置かない。ただし「標準は課さない。template は推奨(附属書I 要件③)を `blind: false` の層の扱いとして実装している」ことを、附属書I の注または ADR で開示する。開示は義務を足さない
- 理由(規格・整合):
  1. 規格が要件にしている確証が無い(0 章)。確証の無い測定条件を適合の要求に昇格させない
  2. 1.10.2 の離脱で、秘匿の不成立は既に適合の主張を止める。条項を足すと「離脱として開示」と「未測定として載せない」の二重になり、同じ事実に2つの帰結が付く。どちらが適合の主張に効くのかが読み手に決まらない
  3. 新しい要求は検証できる形でなければならない。「未測定として扱う」は、集約の挙動(`blind: false` を載せない)なら決定可能だが、採用者の運用中の台帳は template に無く(ADR-0139 決定3)、採用者側は manual にしかならない。確かめられない義務を足すと、適合の主張の信頼を下げる
- 落とす案: 「条項として置く」。落とす理由は上の1〜3。変更量は理由にしない
- 付記: K-3(template が標準より強い)は矛盾ではない。標準の要求の上限を template が上回ることは許される。矛盾になるのは、template が逆の指示を書くとき(`template-fields.yaml` の omit の規定)で、これは該当しない。開示だけで足りる
- 根拠水準: 暫定。規格の本文が未読。見直しは規格の本文を読んだとき(下記 4 章)

### B-3 注入する者を体制の外に置けることを条文に書くか

- **判定: 課さないと明記する(条文に書かない)。手引き(フェーズ5)に例を置く**。ADR に「条文は注入する者の所属を定めておらず、外の者が注入すれば 1.10.2 の当たる条件(分けられない場合)に当たらない」と読みを記録する
- 理由: 1.10.2 の条件は既に所属を問わない。書くと外部の注入者への義務(同意・周知・公平性・守秘。PT の ISO/IEC 17043 に相当するもの)を書き始めることになり、その内容は規格未読のまま書けない。UMN の件は、条件を欠いた外部注入が害になる反面教師で、条件を書かないまま「書ける」とだけ示すことが最も危ない。手引きの例は、PT の形(提供者が検体を作り、受け手は日常の手順で扱い、結果は提供者へ返る)を借りる。ただし「小規模のソフトウェアの先例は見つからなかった」ことを例に書く
- **落とす案**: 「条文に書く」。落とす理由は上。また「外部の者が注入すれば離脱に当たらない」と読むことは、離脱を逃れる抜け道にもなる。注入者が分けられていても、偏り(1.1)や、注入の台帳に触れる者が秘匿を破る場合は残る。適合の主張は、注入者=発見者の層を測定値に載せないことを B-1 の第三の置き方で守る
- 問い2への答え: 本件は新しい条項を足さずに読める。例外承認は要らない(7.9.4 は制限された状態の決裁で、5.6.2 の免除ではない。調査 4 章(2) の指摘どおり)
- 根拠水準: 暫定(先例が無い)

### B-4 標識の可視性と秘匿の衝突(K-1)

**意見の核心**: 衝突の原因は、条文が**標識の置き場(コミットのメッセージ、ブランチ名)を結果の文に混ぜて決めている**ことである。さらに、5.6.2 の条文の内部にも矛盾がある(次の段落)。

- **条文内の矛盾の発見**: 「注入に気づいたときの手続」の手続1は「演習の識別子を添えて報告する」と書く。同じ節は「演習かどうかの判別を、担当者へ求めません」とも書く。識別子を添えられるのは、標識が見えている場合だけである。標識が見えないと(秘匿が成り立つと)、報告者は識別子を知らない。**標識が見える設計と、秘匿の設計は、条文の中ですでに両立していない**。K-1 は第2層と要求事項2 の間だけでなく、手続1 とも衝突する
- **判定: 採る。ただし条文は結果で書き、置き場は選べるようにして、置き場ごとの帰結を条文で定める**。案の中身:
  1. 第2層を「注入は、取り込みの前に機械が識別できる印を持つ。印を含む変更の本番への取り込みを拒否する」と書き、**置き場(メッセージ・ブランチ名・外の台帳)を条文から外す**(調査の案 E の一般化)。置き場の例は手引きへ移す
  2. **印をレビューする者の目に入る場所(メッセージ・ブランチ名・PR の画面)に置く場合、その層は秘匿が成り立たない層として、B-1 と同じく測定値に載せない**。つまり「印は見えてよい。ただし見えるなら、その層の検出率を測定値と称しない」。これは調査の案 D(要求事項2 を「箇所」に限る)を採らずに、秘匿を弱めずに衝突を解く。測定の妥当性を失うのは測定値の側であり、流出の統制(第2〜4層)は保たれる
  3. 手続1 を「気づいた者は、演習の疑いとして、通常の指摘と同じ操作で報告できる。識別子の突合は機械または品質保証の機能が行う」に直す。担当者に識別子を求めない(条文内の矛盾を解く)
- 現状への効き方: ADR-0139 により運用中の継続の注入は全規定が採用者の領分で、導入前の検証の記録は外に置かれ封じられる(IMPL-0162)。template の中で標識がレビューに見える場面は、いま無い。K-1 の実害は、採用者が運用中の注入を始めたときに初めて生じる
- 落とす案と理由:
  - 案 A(現行のまま): 条文内の矛盾(手続1)を解けない
  - 案 B(git notes): squash・cherry-pick で標識が消え、第2層が効かない(実験)。流出の統制を損なうので不可
  - 案 C(外の台帳 + 指紋)を**必須とする**: 台帳に触れる者が注入者=発見者の体制で秘匿にならず、取り込み前の拒否は CI が秘密の台帳を持つ場合だけ。偽の一致の率が未検証で、決定不能な点を機械の検査にできない。**選択肢として許す(上の1の置き場の一つ)**が、必須にはしない
  - 案 D(要求事項2 を「箇所」に限る): 「注入された PR か」の判別が測定を歪める(TIP の「画像が合成と分かる」問題と同型)。秘匿を弱めるのは、実証なしに主張の条件を動かす
  - 案 E(ブランチ名を外す): 採る(上の1に含める)
- 問い1への答え: 置き場は手順であり、結果(取り込み前に機械が識別して拒否する)と証跡(拒否の記録・走査の記録)だけを条文に残す。問い3: 失うもの(流出)は取り消せないので、流出の統制(IMPL-0047・0192)は無条件で保つ。測定の妥当性の側は、未測定の表示で受ける
- 根拠水準: 暫定。「印を見つける者から隠したまま、機械が拒否する」には先例が無い(調査 1.2)。「見えるなら測定値に載せない」は新しい整理で、実証は無い。EV を新規に追加する(差し替え条件: 採用者の運用中の注入の件数と、印が見えた場合の検出率の差の観測)
- **IMPL-0047 との整合**: 走査の標識の文字列は定数1か所(ADR-0139 決定1)。置き場を広げても、メッセージ上の標識の走査は残る。外の台帳の照合は既に任意の入力(`--ledger`)で、整合する

### B-5 7.9 の発動を何から数えるか(K-2)

- **判定: 採る。数える単位は範囲・類型とし、制限の対象は範囲の承認権限を持つ役割の全員にする。誰が見逃したかは数えない。意図的な違反(7.9.1 の行2)だけは、5.6.3 の人の手続による**(調査の選択肢 1 を基にし、3 の二層を一部取り込む)
- 理由(整合):
  1. 5.6.2 は台帳と出力に識別子を含めず、見逃しへの措置を実装へ組み込まない。人を数える設計は、この禁止と正面から衝突する
  2. 7.9.2 は「制限するのは人ではなく権限の範囲」と書く。範囲で数えるのが条文の趣旨に合う。2名必須の制限は範囲の全承認者に掛かるので、個人を特定しなくても成り立つ
  3. 医療の PT(調査 1.4)は、発動も停止も「検査室 × 項目」を単位にする。7.9.1 が借りている先例と同型になる(閾値 EV-0064 は E1 のまま)
- **条文の修正(意味を変える。編集の指摘ではない)**: 7.9.2 の目的の段落「検知された者の承認を単独では数えない」を「該当する範囲では、承認を単独で数えない」へ。行1 の主語は「同じ類型の注入を連続2回…見逃した(範囲で数える)」と明記する
- **突合で出る矛盾**: IMPL-0118(delivered・machine)は制限の記録に「対象の人」を必須とする。範囲で数えるなら、この欄は「範囲」(paths)と「記録した者」に絞る。**template を触るため本束では一覧に挙げるだけ**(下 3 章)。IMPL-0118 の note の「だれが承認したかに依らない」は、範囲で数える設計と既に整合している
- 小さい体制: 範囲と人がほぼ一致する(1名の範囲)。条文が既に「件数の不足」の開示を求める。単位を決めても発動しないことの開示で受ける
- 落とす案: 「人で数える」(5.6.2 と衝突。小さい体制では実質1に収束するだけ)。「二層(機械は知らせるだけ、制限の対象は品質保証が決める)」は、制限の対象を決める手続が人に残り、機械で閉じない。**意図的な違反の1回発動の経路だけに限って採る**
- 根拠水準: 暫定(EV-0064 は E1)。範囲で数える単位の妥当性を測った資料は無い
- 先送りの要否: 先送りしない。先送りすると IMPL-0627・0666 の note が矛盾したまま残る

### B-6 5.6.2 の手順の文を、結果と証跡の文に改めるか

- **判定: 採る。ただし、検証できなくなる文は直さない**。B-4 の結論の後に直す(従属の順に合わせる)
- 規格の観点(要求は検証できる形で書く): 結果の文に直すと検証可能性が**上がる**ものと**下がる**ものがある
  - 直す(検証可能性が上がる、または変わらない): 「演習の変更は、判定の記録を採取した時点で閉じ」→「演習の変更は、記録の採取の後に本番へ取り込まれない状態で閉じられ、閉じた記録が残る」。「ブランチは期限で削除する」→「期限を過ぎた演習用ブランチが残らず、削除の記録が残る」。これらは手順(時点・方法)を外し、状態と証跡を残す
  - 直さない: 「報告は1つの操作で完了する形にする」。「通常の指摘より重くしない」は相対で検証しにくい。「1つの操作」は数えられる。報告の摩擦を下げる意図(形骸化の防止)を最も直接に表す。**手順に見えるが検証できる結果なので条文に残す**(調査の案とは異なる)。手続1 の識別子の部分だけを B-4 に従って直す
- 落とす案: 全面的に手引きへ移す。理由: 「何を満たせば適合か」が曖昧になる(調査の「移さない案」と同じ)。逆に、移さない案(現行のまま)は手続1 の矛盾を温存するので採らない
- 採用者が写した記録の番号の安定(ADR-0076): 意味を保てば番号は保てる。IMPL-0190・0195 の note を直す
- 根拠水準: 規格の本文が未読のため、検証できる形に関する判断は一般論による。暫定

## 4. 問いへの通し

1. 結果と証跡か: 第1・2層の置き場と時点の手順を結果へ。報告の「1つの操作」だけは検証できる結果なので残す
2. 例外承認で受けられないか: 外部注入者・注入者=発見者は新しい条項なしで読める(1.10.2)。**例外承認は5.6.2 の免除に使えない**ので、使う案は採らない。7.9.4 の枠を消費するだけで、免除としては働かない
3. 破られたとき誰が何を失うか: 流出(利用者・採用者。取り消せない)は第3・4層を無条件に保つ。印の可視と数える単位の誤り(測定の妥当性、個人の不利益)は、未測定の表示と、人を数えない設計で受ける。細かく書くのは前者だけ

## 5. 削れる条項・小さいチームでの省き方

- 削れる: 第1層の `drill/` の例、第2層の置き場の限定、5.6.2 手続1 の識別子、7.9.2 の「検知された者」(いずれも条文を結果に直して手順を外す。条項数は増えない)
- 足す条項は無い。足すのは「印が見える層は測定値に載せない」の一文のみ(B-4 の2)。これは 1.10.2 の既存の枠を使う
- 小さいチーム: 1〜2名で注入者=発見者なら、1.10.2 の離脱と未測定の表示で受ける(新しい作業なし)。運用中の注入をしない選択は残る。流出の統制は無条件の走査1回(ADR-0139)

## 6. 確かめていないこと

- IEEE 1028・ISO/IEC/IEEE 29119・ISO/IEC 17043 の本文。公開プレビューも未取得。規格に欠陥注入の規定が「無い」とは言えない。読んだ結果、独立の注入者を要件にしていた場合は B-1 を再審議する
- CLIA の発動条件は既存メモ頼み(調査 6 章)。5.5 の閾値の借用元の確からしさは変わらない
- B-4 の「見えるなら測定値に載せない」は、運用中の注入を行う採用者の観測が無い。実装は template に無い
- GitHub 上の squash・rebase の実挙動は未確認(調査 3.2 の確かめていない点 1〜5)
