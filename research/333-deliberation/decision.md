# #333 議長の裁定の案

作成日 2026-11-15。審議は軽(起案と反対の2委員)。template は 1e30869、本体は d1707e0 の時点で確かめた。標準・template は変更していない。判断軸は信頼性で、変更量は理由にしていない。

## 0. 所有者に上げる点

重へ上げる点は無い。採用者への新しい義務(保管日数の入力の必須化、外部の保管への引き渡しの必須化、構成のキーの追加)は置かない。安全・ADR の原則の変更にも当たらない。

ただし、次の2点は所有者の確認を求める(裁定の案に含めたが、2委員の案のどちらとも違う形である)。

1. **IMPL-0243 を `plan=adopter` にする**。「組織が定める保管期間のあいだ到達できる」ことの充足を、準拠テンプレートは今後も実装しないと決める。規定は課したままで、新しい義務ではない(K-7 が既に課している)。ただし「予定(scheduled)」の表示が「採用者が実装する」へ恒久に変わる
2. **G-5 の結論を、出荷の時点ではなくマージの時点で写す**(record-copy の写しへ欄を足す)。2委員はどちらも「PR ごとの G-5 の結論を残す」ことを推したが、時点は出荷の時とした。議長が時点をマージへ改めた(理由は 2.2)。record-copy.yml の権限に `checks: read` が増える(読み取りだけ)

## 2. 理由

### 2.1 事象1

- **「範囲を絞った delivered」は規約に合わない**。`implementation-marking.md` は、降ろし先が実在し規定の一部がそこに無い場合を「undelivered とし、無い部分を note に書く」と定める(「降りていない規定の扱い」の末尾の箇条)。`state` は2値で、マークは規定ごとに付ける。IMPL-0243 の規定は「保管期間のあいだ到達できる置き場に残す」であり、期間を知らないテンプレートはこれを満たしたと言えない。note を言い換えて delivered にすると、ADR-0109 の「言い換えで未達を消したのではないか」と同じ反論を、本文を改めないまま受ける
- **1つの規定を2つに割ることはしない。ただし本文は2文ある**。1文目「到達できなければなりません」と2文目「CI 基盤の既定の保持を、保管とみなしてはなりません」は別の規定である。現状は2文目にマークが無い。2文目は準拠テンプレートの振る舞い(証跡を成果物だけに置かない)で満たせ、存在・digest の一致・追加のみという決定可能な条件で閉じる。そこで、1文目は IMPL-0243(undelivered・adopter)、2文目は新しいマーク(delivered・machine)とする。起案の「機械が閉じた部分を台帳で見せる」と、反対の「期間の充足を delivered と言わない」が両立する
- **`plan=adopter` が当たる**。期間の値は組織の文書管理規程が定め、リポジトリの寿命(削除・移管)も組織が決める。テンプレートが実装できる余地が無い。`plan=scheduled` のままにすると、降りる見込みの無い規定が「予定」と出続け、表示が実態と食い違う。第4章「判定の成立」は `impl-no-adopter.yaml` の節に当たらない(確認済み)。`decision=` が要るため ADR を新設する
- **置き場は基底ブランチ(出荷のブランチ経由)にする**。既に品質レポートと記録用ブランチの先頭が同じ経路で基底ブランチへ入る(ship-evidence.yml (b))。署名を課す構成の経路(createCommitOnBranch)も、追加したファイルを一括で運ぶ形で既にある。verify ジョブが「追加以外の変更は失敗」を検査している。ADR-0109 決定2 は「出荷の後は基底ブランチの複製を正とする」。既定ブランチのルールセット(PR と承認)は、記録用ブランチの規則(履歴の書き換えと削除だけ)より強い
- **コミットは保管の充足を示さない**。コミットに保持期限の規定が無いことは、公式の記述が無いことからの読みである(research-supplement 1)。バイパス権限者には削除・書き換えの禁止が効かない。ゆえに表示は「写した」にとどめ、根拠水準マークで開示する
- **前回の証跡の読み先も直す**。「前回の出荷の証跡を取り込む」は成果物(ship-evidence)だけを見ており、90 日を過ぎると「前回なし」になる。写した先から読めなければ、置き場を作っても集約が使わない

### 2.2 事象2

- **日付の比較は決定できない**。保持日数はリポジトリ・組織・企業の3層の設定の結果で、下限は 1 日である。集約のトークンで読めることは確かめられていない。構成へ日数を足す案は、採用者の宣言が実態と食い違えば文言が誤る。「保持の内なら保持切れでない」も、実際の設定を知らなければ言えない
- **反対の「並べて断定しない」だけでは、IMPL-0244 の規定(区別して出す)が降りない**。区別の材料が無いからである。材料は、マージの時点の記録にしか無い
- **record-copy は既にマージの時点で動き、写しを記録用ブランチへ置く**。同じ時点で、head の gate-g5 の check run(集約の `g5FromCheckRuns` と同じ API)を読み、写しへ足せる。マージの時点では保持切れは起こらない。写しの変更は履歴の走査が検出する(ADR-0109 決定1。`records/` の下の追加以外の変更)
- 出荷の時点で残す案(2委員の案)は、マージから出荷までが保持期間より長い PR を救えない。その PR こそが誤示の対象である
- 写しの値は、保持切れの後はホスティングと照合できない。ADR-0109 決定2 は、照合できない写しで G-6 を数えない。同じ向きで、**写しの値で G-5 を充足に数えない**。欠落のまま、文だけを分ける。強制層を緩めない(ADR-0038 に触れない)

### 2.3 事象3

- 取り込みの欠けは、コードの読みと集約の実行で確かめられている(research-supplement 2(b))
- 同一コミットの条件は、既存の `gh run list --commit "$target"` で構造上は満たす。値の一致(実行の headSha と対象)として明示して確かめる
- **議長が見つけた食い違い**: 既定ブランチへの push の gate-g5 は、測る範囲が「変更」のとき、起点を push の直前のコミット(`github.event.before`)にする(gate-g5.yml L244〜254)。取り込む値は「最後の push の差分の被覆」で、出荷の範囲の被覆ではない。集約は今、範囲と分母は出すが起点を出さない。値を取り込めば「実施(88%)」が出荷の範囲の値に読める。起点と限定を同じ行に出す

### 2.4 事象4

- record-copy は、マージの時点の PR の題名と本文の全文を既に写しへ入れている(record-copy.yml の `body`)。ハッシュを足す必要が無い
- 反対の「書き込み権限者が両方を書き換えられる」は、写しの側については当たらない。写しの変更は履歴の走査が欠落として検出する(ADR-0109)。残るのは、マージより前の編集(写しがそれを正として写す)と、規則のバイパスである
- ADR-0109 決定2 は、レビューの本文について「写しを取った時点の値を記録とし、ホスティングの側の変化を所見にする」。PR の本文の比較は、同じ原則を同じ形(所見)で当てるだけで、原則を変えない
- 集約は今、「検証方法と結果」の有無をホスティングの今の本文で読む(`api ?? prRecordFromCopy`)。マージの後に書き足した記載も「あり」と数える。所見を出せば、出荷判定者がそれを知れる

## 5. 実装の指示

順序: #334 の template の変更が入った後に、その先頭から始める(template は直列)。`check-pr.mjs`・`test-check-pr.mjs` には触れない。試験は新しいファイルに置き、`gate-g5.yml` へは `run:` の行の追加だけを行う。template のコミットは、コミットのたびに bundle へ退避する。識別子は実装の時点の最大の次を採る(本作業ツリーの最後は IMPL-0519・EV-0259。以下 IMPL-A・IMPL-B・EV-A と書く)。

### 5.1 template: 一式の写し(事象1)

1. **新規 `scripts/gate/evidence-manifest.mjs`**(純粋な関数を export し、CLI を持つ)
   - `write --dir <一式の置き場> --run <実行の識別> --target <対象のコミット> --range <範囲>`: 置き場のファイルごとに `{path, sha256, bytes}` を並べ、`manifest.json` を書く。欄: `schemaVersion: 1`、`range`、`target`、`recordedAt`、`run`(ship-evidence の実行)、`inputs`(取り込み元の gate-g5 の実行の識別と headSha。無ければ null)、`files[]`、`note`(定型文「リポジトリへの写し。組織が定める保管期間の充足は示さない」)
   - `verify --dir <置き場>`: manifest の各ファイルの存在と sha256 の一致、manifest に無いファイルが置き場に無いことを確かめる。不一致は終了コード 1 と一覧
   - `workflowProblems(text)`: ship-evidence.yml の本文を読み、(a) upload-artifact の `ship-evidence` に `retention-days:` がある (b) 一式を `docs/evidence/` へ写す手順(`evidence-manifest.mjs write`)がある (c) verify ジョブが `evidence-manifest.mjs verify` を呼ぶ (d) `coverage-result` の取り込みがある、の欠けを返す
2. **`.github/workflows/ship-evidence.yml`**
   - upload-artifact(`ship-evidence`)へ `retention-days: 90` を足す(ai-review.yml と同じ値)。注記: 「一時置き。保管ではない。リポジトリ・組織の設定の上限を超える値は効かない(上限の扱いは実機で未確認)」
   - (b) の手順で、品質レポートの後に、一式を `docs/evidence/<day>-<safe>/`(既にあれば `-<RUN_NUMBER>` を付ける)へ置く。対象: `evidence.json`、`assurance-disclosure.external.md`、あれば `license-scan.json`・`test-results.json`・`coverage-result.json`・`dependency-diff.json`。`evidence-manifest.mjs write` で manifest を作り、`git add -f` する。品質レポートの今の置き場(`docs/evidence/<day>-<safe>.md`)と verify の印 `out=` は変えない。`evidence/previous/` と `ship-pr-url.txt` は写さない
