# #333 起案の委員の意見

軸は信頼性(保管期間のあいだ証跡に到達できるか、決めるべきことが漏れないか)。安さ・変更量は理由にしない。機械で閉じるのは値の一致・存在・構文だけとし、他は manual か adopter で開示する。標準・template は変更していない。

## 全体の立場

- 保管期間の値はテンプレートが決めない。本文(gate-criteria.md L241)が「組織が定める」とし、値は定めないと明記している。テンプレートは置き場と、期間を入力に取る比較だけを持つ
- 新しい義務は課さない見込み。K-7 が既に置いた「到達できなければならない」を降ろすだけで、保管期間を定める義務も外部引き渡しの義務も足さない(候補 D は採らない)。ただし 2 節の `evidenceRetentionDays` の入力を process-init の必須の問いにするなら、採用者への入力が増える。必須にはせず、未設定なら既定 90 日と仮定した旨を出力に出す形を推す。議長はここを軽のまま扱えるか確かめてほしい

## 事象1 証跡の置き場と保持 — 推す案: A(records ブランチへ追記)

- 理由: 成果物は上限(公開 90 日、非公開 400 日、組織の上限が掛かる。遡らない)があり、組織の期間が超えれば消えるのを避けられない(案 C は期間の長短を設定の運に委ねる)。コミットには保持期限の規定が無く、リポジトリが残るあいだ到達できる(補い 1 節。記述が無いことからの読みで、公式の明言ではない)。records(record-copy.yml)と出荷の PR(docs/evidence/ へ品質レポート)という先行例があり、集約が読む経路も既にある
- 保管するものは research 6 節の(ア)(イ)(ウ)の全部。(ア)は済み。evidence.json と外へ渡す開示(イ)、レポートが指す元の記録の写し(ウ: test-results・license-scan・coverage-result の JSON と、範囲内の PR ごとの G-5 の結論)を `records/ship/<日付>-<範囲>/` へ追記する。ログや大きな成果物は入れない。JSON と digest の一覧だけにする
- 変更の所在: `template/.github/workflows/ship-evidence.yml`(upload-artifact の後に records への追記の段。既存の上書きを拒み、追記のみ)。`retention-days` も明示する。値はリポジトリの設定を超えない範囲で採用者の設定に合わせ、成果物は「写しを取るまでの一時置き」と位置づける
- 機械の検査(決定可能な条件のみ): 追記先ファイルの存在、記録した digest と内容の一致、既存パスの上書きが無いこと。試験は template/scripts/gate に違反と適合の対を置く(例 test-ship-records.mjs)
- 機械で閉じないもの: 書き込み権限者・ルールセットのバイパス権限者による追記や差し替え(補い 1 節のとおりバイパスには禁止が効かない)と、リポジトリの外での保管期間の充足。これは adopter(外部の WORM や文書管理へ引き渡すか、バイパスを絞るか)で、根拠水準マークで開示する
- 実装マーク: IMPL-0243 は範囲を「リポジトリが残るあいだ到達できる置き場(records)へ残す」に絞って delivered、check=machine、test=上の試験にする。「組織の期間を満たすこと」は別の新しい IMPL(check=manual、undelivered、確かめる者は内部監査)として残す。全部を delivered にすると、期間の充足まで機械が保証したように読める。それは表示と実態の食い違いになる
- 想定される反論:
  - 「リポジトリの膨張」。JSON と digest だけで、ログを入れないので限られる。膨張が問題になる採用者は、外部の保管へ引き渡す側に寄せられる
  - 「コミットは改変できる」。履歴に残り、集約が走査で検出する(ADR-0109)。防止ではなく検出であり、そう開示する
  - 「評価版のリポジトリが消えたら終わり」。そのとおりで、採用者の保管の確認(adopter)として残す
- 採らない案: B(リリース資産)は出荷の単位以外を覆えず、不変リリースは有効化前に及ばない(adopter の設定に依る)。補助としては勧めてよいが、置き場の本体にはしない。C は単独では保管にならない。D は新しい義務で重になる。E は保持を解かず、attestation の保持期間も確かめられなかったので保管の根拠にしない。ただし E は A の補強として別 Issue に回す余地がある

## 事象2 保持切れの誤示(IMPL-0244) — 推す案: 三分類

- 実行で確認済み(補い 2 節 a): 空の rollup は「必須チェックを経ずにマージされた可能性」と同じ文になる。入力が同じなので、入力を足さない限り区別できない
- 推す案: aggregate-evidence.mjs に PR の mergedAt と保持日数(`process.config.json` の `evidenceRetentionDays`、未設定は既定 90 日と仮定してそう表示)を入力に足す。g5 が 'unknown' のとき、マージ日が保持期間の外なら「保持切れの可能性(確認不能)」、内なら現行の文を出す。条件は日付の比較で、決定可能
- 肝心な点: 保持切れを理由に合格へ寄せない。両方とも欠落として出し続け、文言と次の行動だけを分ける(保持切れ側は records の写しを見るよう案内する)。事象1 の(ウ)で PR ごとの G-5 の結論を records に残せば、以後の集約は保持切れでも records から読める。今回は過去の PR には遡れないと明記する
- 変更の所在: `scripts/gate/aggregate-evidence.mjs` L2964 付近と L2121 付近、試験 test-g5-aggregate.mjs に「保持の外で空」と「保持の内で空」の対を足す。IMPL-0244 は delivered、check=machine、test=その試験
- 反論: 「保持日数の設定は採用者の宣言で、実際と食い違いうる」。そのとおりで、食い違えば文言が誤る。ゆえに両方とも欠落として出し、保持切れ側にも「経ていない可能性は排除できない」と書く。誤分類で合格に倒れる経路を作らない
- 採らない案: gh の API で実際の設定を読む案は、権限と提供範囲(github.com 以外)が確かめられていないので採らない

## 事象3 coverage の取り込み — 推す案: 配線を足す

- ship-evidence.yml の「知財潔白性の検査記録を取り込む」の段へ、test-results と同じ形で `gh run download ... --name coverage-result --dir evidence` を `|| ::warning::` つきで足す。gate-g5.yml は既に上げている(if-no-files-found: ignore なので、無い場合は warning 経由で未測定のまま。隠さない)
- 試験: ワークフローの文字列に coverage-result の取り込みがあることの確認(構文・存在)と、coverage-result.json を置いたときに「実施(…%)」になる既存の動作の確認。実機の出荷は未確認のまま、根拠水準マークで開示する。標準の条項ではないので実装マークは増やさない。軽(回帰)
- 採らない案: 実行しないで「常に未測定」と文書に注記して済ませる案。取れる値を取らない設計は、開示の信頼性を下げる

## 事象4 「検証方法と結果」の改変の検出 — 推す案: 標準の条件にせず、テンプレートで写しのハッシュを比べる

- record-copy の写しに、PR 本文の「検証方法と結果」の節のハッシュ(sha256)を足す。集約は、出荷の時点の PR 本文のハッシュと比べ、不一致を「承認後に本文が変わった」という欠落(要人の確認)として出す。値の一致なので決定可能
- 閉じないこと: 文の意味の妥当性、写しを書く権限者による差し替えの防止。manual と adopter で開示する。マージ後の誤字訂正でも不一致になるので、失敗にせず、人の確認を求める表示に留める
- 標準の条項にはしない。ADR-0109 の原則(写しの突合)の枠内の欄の追加で、標準の判定の条件を変えない。条件にする場合は重で、このままでは足りない。実装マークも新設しない
- 採らない案: 本文の文を全文複製して意味を比べる案(自由な文の意味は機械で閉じない)。E(署名)は到達性を解かず、PR 本文には当たらない
