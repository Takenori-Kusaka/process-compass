# #333 反対の委員の意見

確認日 2026-11-15。立場は、Issue の提案と、テンプレートに保管の仕組みを足す方向の案への反対。反対のための反対はしない。却下するものと残すものを分ける。安さ・変更量の少なさは理由にしない。判断軸は、表示と実態が食い違わないこと、機械で閉じる範囲を超えて「保管」「検出」と名乗らないこと。

## 0. 先に認める点(何もしない案の損失)

- 証跡の指す先は現に消える。`ship-evidence.yml` の upload-artifact は retention-days が無く、既定 90 日で、evidence.json・外へ渡す開示・ship-pr-url.txt が消える。レポートが指す元の記録(gate-g5 の成果物、check-runs)も、2026-10-01 以降は保持の設定に従う。「何もしない」は、本文(gate-criteria.md の「判定が指す記録の保管」)が置いた到達性の要求に、テンプレートが答えないまま採用者が運用に入ることを意味する。IMPL-0243 と IMPL-0244 が undelivered で出続けるのは正しいが、期限(review=2027-04)まで放置してよい理由にはならない
- 事象(2)は、保管の置き場とは独立の欠陥である。保持切れと未経由が同じ文で出ており、実行でも確認された(research-supplement 2(a))。表示が実態より強い(「必須チェックを経ずにマージされた可能性」)ので、これは直すべき

したがって「全部を落とす」立場は採らない。以下、事象ごとに評価する。

## 1. 事象(1) 置き場と保持

### 前提の問い 1: テンプレートが置き場を決めることは「組織が定める保管期間」と両立するか

本文は保管期間の値を定めず、組織の文書管理規程に委ねている。テンプレートが置き場を決めれば、次の 2 つの食い違いが起こりうる。

- 置き場の寿命と組織の期間のずれ。コミットは「リポジトリが残る限り」残るが、リポジトリの削除・移管・アーカイブの規程は組織が持つ。リポジトリの外の保管期間との対応は採用者の確認が残る(research.md 案 A の短所)
- 「テンプレートが保管した」という表示が、組織が定める期間を満たしたという表示に読まれる。期間を知らないテンプレートは、満たしたとは言えない

結論: テンプレートは「置き場を提供する」ことはできるが「保管した」と表示してはならない。表示は「この置き場に写した(期間の充足は採用者が確認)」までにとどめる。

### 候補ごとの評価

**案 A(records ブランチ、または出荷の PR で docs/evidence/ へ一式をコミット)**
- 残す価値はある。既に先行例(record-copy.yml、出荷の PR)があり、集約が読む経路もあり、保持が CI の設定に依らない点は、成果物に勝る
- ただし「保管」と表示するには問題がある。書き換え・削除の禁止はバイパス権限者に効かない(公式: Restrict deletions は bypass 権限者を除く。research-supplement 1 の末尾)。テンプレートは bypass actor を置かない方針だが(rulesets/README.md L72・L147)、これは採用者の設定が方針どおりであることを前提にする。方針と実態の一致は env-check の所見で継続して確かめる仕組みがあるが、それは「検出」であって「防止」ではない
- 条件: 表示は「リポジトリ内の写し。追記のみを集約が検出する。書き込み権限者の改変の防止は含まない」とする。バイナリや大きい成果物をコミットしない。置くのは digest つきの索引(何が、どこに、どの digest であったか)と、小さい本体に限る。大きい本体は別の置き場(案 B・D)へ。ここで膨らませない理由は、リポジトリの肥大が、将来の保持の運用(履歴の整理)で書き換えを誘発するから(変更量の少なさとは別の、信頼性の理由)
- 「出荷の品質レポート(ア)は既にコミットされる」。(ア)に対する新規の実装は要らない。新たに足すのは(イ)(ウ)の索引と digest だけにする

**案 B(リリースの資産)**
- 条件つきで残す。immutable releases を有効にすれば資産の追加・変更・削除ができない(公式、2025-10-28 一般提供)。これは書き込み権限者にも効く点で A より強い
- 落とす部分: 有効化の設定はリポジトリまたは組織の設定で、有効化前のリリースには及ばない。テンプレートは設定を強制できない。したがって「不変」と書いてはならない。表示は「不変リリースが有効な場合に限り資産の差し替えができない(採用者の設定。adopter)」。有効かどうかを API で読めるなら、決定可能な条件として機械で確かめられる(実在の検証が要る。未確認なので、ここでは「確かめられるなら」とだけ言う)
- 出荷の単位以外(gate-g5 の都度の記録)を覆わない。ここで覆えると言ってはならない

**案 C(retention-days の明示)**
- 単独では保管ではない。上限(公開 90 日、非公開 400 日、組織・企業の上限)があり、設定は遡らない。本文が「CI 基盤の既定の保持を保管とみなしてはならない」と言う以上、retention-days を上限まで上げても、本文の言う保管にはならない。上げることは「消えるまでの猶予」を延ばすだけで、表示してよいのはそこまで
- ただし A や B の補助として入れる価値はある(索引が指す本体が、猶予のあいだ読める)。明示の有無は構文で閉じるので機械の検査にできる。値が組織の期間以上かは manual。個別指定の上限は未確認(research-supplement 1)なので、「上限まで」と書かない
- 却下する言い方: 「C で IMPL-0243 を delivered にする」。本文と矛盾する

**案 D(外部の保管への引き渡しを採用者に委ねる)**
- 本文の委ね方と最も整合する案で、これを残すべき中心と考える。ただしテンプレートが提供するのは降ろし口(引き渡す対象の列挙、digest の出力、固定名の出力)だけで、引き渡しの実行と保管期間の充足は adopter。ここを「delivered」と言ってはならない
- 重への分岐: 採用者に「保管期間を定める」「外部へ引き渡す」義務を新しく課すなら、intake のとおり重である。ただし本文は既に「組織が定める保管期間」の到達性を要求している。本件でテンプレートが降ろし口を提供するだけで、新しい義務を標準に足さないなら、軽にとどまる。降ろし口に「引き渡さない場合は、その旨を構成に記録する」といった要件を課すと新しい義務になる。この境界は議長が決める。私は、降ろし口の提供だけに留めることを勧める

**案 E(attestation)**
- 保管の案としては落とす。保持と到達性を解かない。attestation の保持期間は公式で確かめられていない(research-supplement 1)。未確認のものに保管を頼れない
- 改変検出の補助として書くことはできるが、その場合も bundle を自前で保管する前提になる。それは A や D の中に収まるので、独立の案としては立てない

### 事象(1)の推奨(反対の側から)

- 採る: A の最小形(索引と digest を records 系の追記に写す)+ D の降ろし口 + C の明示(補助)。B は「採用者が不変リリースを有効にした場合の任意の置き場」として記述にとどめ、既定にしない
- 落とす: C 単独での delivered、E 単独、B を既定にすること
- IMPL-0243 の状態: 上の構成でも、期間の充足は機械で閉じない。state は delivered にせず、本文の要求のうち「到達できる置き場に写す」部分だけを降ろし、期間と引き渡しは manual / adopter として根拠水準マークで開示する(`:::caution[暫定 EV-NNNN / 見直し YYYY-MM]`)。undelivered の表示を消すのは、実機で通しの実行(出荷の PR の作成を含む。2026-10-23 時点で未確認と明記されている)を確かめた後にする
- 実機未確認: records への書き込みは 2026-10-23 に確認済みだが、出荷の PR の通しの実行は未確認。未確認のものを新しい保管の経路の前提にしない

## 2. 事象(2) 保持切れと未実施の区別

### 前提の問い 3: 機械で決定可能か

- 日付の比較自体は決定可能だが、入力が足りない。保持日数は、リポジトリ・組織・企業の三層の設定の結果で、組織・企業の上限はリポジトリの token から読めるとは限らない。公開か非公開か、2026-10-01 前後かの条件もある。集約が「保持の設定」を読めない場合、比較はできない
- 空の rollup は、ブランチ保護を適用しない場合の「経ていない」と機械的に同じ入力になる(research-supplement 2(a) の限界)。したがって、日付が保持の期間の内か外かだけで「保持切れ」と断定するのは危険。外であることは必要条件にすぎない。外であっても本当に経ていない可能性は残る
- 内であれば、保持切れでは説明できない。この方向(内なら保持切れと言わない)は決定可能で、強く言える

### 評価

- 今の文(「必須チェックを経ずにマージされた可能性」)は、保持切れが原因でも出るので、確かに誤示を含む。ただし、これを「保持切れ」に置き換えるのも逆の誤示になる
- 推奨: 区別を断定にしない。マージ日が(読めた、または構成にある)保持の期間の外なら「保持切れで読めない可能性。経ていない可能性と区別できない」と、2 つの可能性を並べて出す。内なら従来の文のまま。保持の設定を読めない場合は、並べる文を出す(既定の 90 日を仮定して断定しない)。判定を「確認済み」へ上げない。欠落として数えるかの扱いは変えない(強制層を縮小しない。弱める方向の変更は ADR-0038 の問題になる。審議の対象が「未確認を、確認済みの欠落とも確認済みの充足とも言わない」ことに閉じるよう、議長は確かめる)
- 機械の検査にする範囲: 「期間外のとき、保持切れの可能性の文が出る」「期間内のとき出ない」の 2 つの値の試験。manual: 設定値が実態と合うか
- 偽の gh による模擬しかなく、実機の保持切れは未再現。この点を試験の限界として開示する
- 保管(1)とは独立に直せる。ただし(1)で索引を残すなら、索引に G-5 の結果を残すことで、保持切れの後も区別できるようになる(これが(1)を足す、事象(2)に対する本当の根拠)。順序は、(1)の索引が先に動いてから、保持切れの区別が意味を持つ

## 3. 事象(3) coverage の取り込み

- 配線の欠けは、コードの読み(ship-evidence.yml は license-scan と test-results のみ)と集約側の動作の実行で補強されたが、ワークフロー自体は実行していない。実機未確認のまま直すことへの反対は、半分だけ認める
  - 直すこと自体は、gate-g5.yml が coverage-result を上げているのに取り込みが無いという静的な事実があるので、実機を待つ必要は薄い。誤っても「未測定」の表示に戻るだけで、強い表示への誤りではない
  - ただし「直した」と言うには、ワークフローを実行した確認が要る。実機の確認が無いなら、IMPL や台帳に「配線を足した。実機の通しは未確認」と書く。取り込んだ値が未測定より強い表示(実施 88%)になる方向の変更なので、取り込む成果物が当該コミットのものかの確認(別の実行の成果物を取らない)を条件にする。ここを誤ると、他の PR の coverage を表示する、表示が実態より強い誤りになる
- 軽の編集(配線の欠け)として扱える。会議体の論点にしない

## 4. 事象(4) 「検証方法と結果」の文の写しと改変の検出

- 写しを同じ場所に置くなら検出にならない。PR 本文は編集でき、写しを records に置いても、書き込み権限者が両方を書き換えられる。record-copy の既存の写しは、集約が履歴の走査とホスティングとの突合で検出する構造に頼っており(ADR-0109)、PR 本文について同じ突合を行うには、ホスティング側の改版の履歴が読める必要がある。GitHub の PR 本文の編集履歴は API では限られる(確かめていない。未確認として扱う)
- 検出できるのは、写しの時点(マージ時)と、集約の時点で本文が食い違うこと、までである。写しをマージ時に records へ置くので、写しの後の改変は検出できるが、写しの前(マージ直前)の改変と、写しと本文の両方を書き換える権限者は検出できない
- 評価: 「検出」と名乗るには条件が足りない。落とす対象は、「改変を検出する」と表示すること。残すとしても「マージ時の写しとの不一致を出す。書き込み権限者による両方の書き換えは検出しない」という限定を、同じ行に書く(適用範囲の書き方の規約: 限定を別段落に置かない)
- ADR-0109 との突合: 写しの対象の追加は ADR-0109 の突合の原則の延長に見えるが、PR 本文の性質(マージ後に編集できる、対象を絞る必要)が record-copy の対象(承認レビュー)と違う。同じ原則の適用か拡張かは、突合の担当に確かめさせる
- 本文(標準)の判定の条件にはしない。テンプレートの検査にとどめ、manual / 暫定の根拠水準マークで開示する。標準に載せるなら重
- 推奨: 保留または却下。事象(1)の索引で digest を残す設計が先にあれば、その一項目として「検証の文の digest」を足す形で済むかを後で見る。独立の機能として足さない。この Issue の受け入れ条件は「実装する(または実装しない理由を記録する)」なので、実装しない理由の記録は成果として成立する

## 5. 採る場合に付ける条件と開示(まとめ)

| 事項 | 機械で閉じる | manual / adopter | 開示 |
| --- | --- | --- | --- |
| 索引の写し(A) | 存在・digest の一致・追記のみ・指す先の実在 | 権限者の改変の防止、期間の充足 | 根拠水準マーク。「保管」でなく「写し」と表示 |
| 引き渡しの降ろし口(D) | 対象の列挙と digest の出力 | 実際の保管と期間 | adopter。IMPL-0243 は undelivered を維持し、降りた部分と残る部分を note に書く |
| retention-days(C) | 明示の有無 | 値が期間に足りるか | 補助であることを明記 |
| 保持切れの区別(2) | 期間外・内の分岐の値 | 設定値の実態との一致 | 2 つの可能性を並べる。断定しない。偽の gh による試験で実機未再現と開示 |

| 改変の検出(4) | マージ時の写しとの不一致 | 権限者の両方の書き換え | 見送りを推奨。採るなら限定を同じ行に書く |

## 6. 重への上げ方

- 案 D で採用者へ新しい義務(期間を構成に定める、引き渡しを必須にする)を課すなら重。降ろし口の提供だけなら軽
- 事象(4)を標準の判定の条件にするなら重
- 安全に当たる点は見つからなかった
- 私の割れる点: 案 A を入れるかどうか。起案の側が「索引で十分に保管を名乗れる」と言うなら、バイパス権限者の問題から、私は名乗ることに反対する。名乗らなければ賛成する
