## 現場から見た全体の注意

現場は、基準を読むより先に「次に何をすればゲートが通るか」を `/gate` と集約スクリプトの出力から読む。条文の文言より、**手引き(gates/G-N.md)と機械の出力が、実際の運用の標準**になる。したがって次を前提に意見を述べる。

- 条文だけ直して手引きと機械の出力が直らなければ、現場は古い手引きに従う。この Issue の論点のうち、1・2・3・7 は template に及ぶ。標準の本文を直した日から手引きが直るまで、食い違いが運用で固定される(IMPL の undelivered が、その窓の表示である)
- 判定者(人)は多忙で、基準の数が増えても1件の判定に使える時間は変わらない。基準が増えると、確認の質ではなく**「確認した項目」の欄の書き方**が省略される
- 例外承認は、日常の逃がし弁である。月に数件は使われる前提で、安全に係るものだけを別に扱う

## 論点1 S0 の G-2 → G-4 統合の中身

- **賛成。条項は足さない**。intake の見立て(「統合」の語義を1段落で定義する)に同意する
- 現場の実態: template の gates/G-4.md は、すでに S0 の統合を前提に書かれている(「引き受けた前提」「引き受けない前提」の2項目、G-2 の基準3 の扱い)。つまり手引きの側は基準3 を G-4 で確かめる形で動いている。食い違うのは標準の表だけで、現場は表を見ずに手引きどおり運用する。表と手引きのずれは、誤読ではなく**表の読み飛ばし**として現れる
- 抜け道: 「統合」が定義されないと、S0 では G-2 の基準2(曖昧語)・4(やらないこと)が誰にも確かめられない。AI が書いた仕様の曖昧語は、S0 でこそ多い(速く書くため)。ただし S0 の損失は手戻りで、CL1 以上は G-6・G-7 が S0 でも適用されるため、取り返しのつかない事故には直結しない
- 定義の書き方の要望: 「G-2 の前提条件1と判定基準1〜5を、G-4 の判定記録の確認項目として確かめる」と**項目の数を変えずに場所だけを動かす**と書く。G-4 の基準を6から11に増やす書き方は不可。判定者が11項目を24時間で確かめる運用は成立しない
- G-4 基準5 と G-2 基準5 の循環: 「G-4 の判定欄が G-2 基準5 を兼ねる」の1文で足りる。S0 では層の割り当てと範囲内外の判定を同じ記入で行うことになり、現場にとって手間は減る
- 採らない案への賛否: (a) S0 専用基準の新設は反対(義務増と判定者の負荷)。(b) S0 で G-2 を省略に改めるのは反対(層の割り当てが誰にも無くなる)。(c) 規則データの注記だけを直すのは反対(本文との食い違いが残る)
- 例外承認で受けるか: 受けない。統合を採らない S0(G-2 をそのまま適用)は例外ではなく通常の選択

## 論点2 G-2 基準1 の数え上げの置き場

- **位置の移動に賛成**。段落に残すと、手引きに降りない。降りない規定は、現場では「無い」と同じに扱われる(段落の文を読むのは標準を通読した人だけ)
- 懸念: 機械が「受入基準に対応しない価値」の一覧を出すと、現場は**一覧が空であることを合格と読む**。ADR-0051 決定2 は「内容は判定しない、対応の有無だけ」と定める。一覧が空でも、受入基準が価値と無関係な文でも通る。G-4 基準6 と同じ構成にし、「機械は合否を出さない。判定者が一覧を見て判定する」を手引きにそのまま写すこと
- 抜け道: 企画書の観点3 に価値を1行も書かなければ、一覧は空になる。価値の欄が空の企画書は、数える以前に G-1 の問題である。ここを機械の検査にすると定義が増えるため、採らない(判定者の目に任せる)
- 損失: 価値のある受入基準の欠落。安全ではない。適合の主張の信頼には響くが、細かく書く対象ではない

## 論点3 G-4 基準5 の置き場

- **代案Aに条件つきで賛成**。空欄の判定欄は、前提条件(機械が見る)として扱う。基準5 は、記入された判定(SC-M / SC-P / SC-B / 範囲外)の妥当性だけに絞る
- 現場の実態: 現行は「空欄の場合、判定を開始しない」が基準の表の行にあり、gates/G-4.md も IMPL-0542 も「空欄なら判定を始めない」と書く。つまり現場は既に**前提条件として運用している**。標準の表が運用に追いついていない形で、置き場の訂正は運用の追認になる
- 条件: 基準番号の付け直し(基準6 が5になる)を避ける。基準5 を「記入された判定の妥当性」として番号ごと残し、空欄の条件だけを前提条件の表の行2 へ移す。宣言行の「基準 N」・KB・テンプレート・IMPL 注記の再番号付けは、現場にとって差し戻し理由の読み違いの原因になる(「基準 5 で差し戻し」と書いた過去の記録が別の意味になる)
- 代案Bは反対しない(影響は小さい)。ただし、第4章冒頭の定義が弱まる。代案Cは基準5 が消え、範囲外の見落としを判定者の目が見る場所が無くなるため反対
- 損失: 範囲外の見落とし。適合の信頼に響く。ただし G-4 の範囲外判定は人の判断で、機械の構造では閉じない

## 論点4 「判定の総数」原則

- **原則を立てない(B)に賛成**。新しい原則は、採用者への義務ではなく標準自身の改訂の自己拘束である。現場には直接の影響がない。ただし立てると、ゲートの追加の提案が出るたびに「総数」が議論の的になる。ADR-0074(検査の機構に上限を設けない)との衝突を、現場の運用者は説明できない
- 引用の訂正: ADR 本文は書き換えない規則のため、新 ADR か注で「原則は採用していない」と置く。現場は「ADR-0016:50 に書いてあるから総数は守られているはず」と読む可能性があるため、引用元の側に気づける印を付けること
- 第4章 :724 と enablement.md:148 の同趣旨の文は、**採用者が直接読む場所**である。ADR の引用の訂正より先に、こちらを読んで誤解する側が多い。この2か所の文が「原則」と読めるなら直す。読めない(単なる説明)なら触らない。これは議長が文を読んで決めるところで、現場からは確認しきれていない(未確認)

## 論点6 安全重要度の判定基準と7.4の禁止を7.3の対象外とするか(重)

### 現場の日常

例外承認は、緊急の障害対応・閾値の少し手前・未確定事項を残して進めたいときの経路で、月に数件使われる。台帳に1行書き、承認者が記名し、期限と回収責任者を置く。これが5分で終わる経路であることが、現場が黙って離脱しない理由になっている(#353 での私の懸念と同じ)。重くすると、記録に出ない離脱になる。

### 実物を読んで確かめたこと

- 7.3 は、対象を「ゲートの判定基準」と、条項が7.3を名指した事項に限る。安全重要度(CL)の判定そのもの(G-1 前提条件2: 判定の記録と判定者の記名)は、判定基準ではなく**前提条件**である。前提条件を満たさない場合は「判定を開始せず、提出者へ差し戻す」(第4章冒頭)。7.3は「判定基準を満たさないまま」進める手続なので、**前提条件には元から効かない**と読むのが素直
- ところが現場がそう読むとは限らない。EV-0271 が「定めていない」と記録している状態は、前提条件の不充足まで7.3で受けられると読む余地を残す。AI が「例外承認で CL の記名を後追いにする」台帳の行を書き、承認者が記名すれば、台帳の様式上は成立してしまう
- 集約スクリプト(aggregate-evidence.mjs)は、例外承認の行を CL や対象のゲートで拒まない。読んだ範囲では、台帳の行の5事項が揃っていれば、G-4 / G-5 / 認証・認可・データ保全の検証を対象とする行も「変更の例外承認」として対応づく。7.4 が禁じる対象への行を拒む検査は無い(IMPL-0567 は undelivered)。つまり**7.4 の禁止列挙は、いま現場では書いてあるだけで効いていない**
- 7.4 の後回しの禁止(G-4・G-5・認証・認可・データ保全の検証)は、7.4(ファストトラック)の中の規定である。7.3 の一般の例外承認にそのまま係るかが曖昧。ファストトラックは「7.3の特殊形」と書かれるため、特殊形で禁じたものを一般形で認められるなら、禁止は迂回できる。**迂回の経路が現場に最も近い**:「ファストトラックではなく、通常の例外承認として出す」で済む

### 賛否と代案

| 案 | 現場の意見 |
| --- | --- |
| A 現状維持(EV-0271 の観測待ち) | **反対**。観測は「1件でも」だが、観測される経路は集約を通る。台帳の行は機械が読むが、それが安全の検証かを区別する欄が無い。観測されるのは事故の後になる。現場で破られても、誰も気づかない |
| B 安全重要度が掛かる基準だけ対象外 | 判定そのもの(CL の判定・記名)に限れば**賛成**。判定に応じた活動(CL1 以上の安全適合性の検証)まで一律に外すのは**反対**。規格より厳しくなる(外部調査 3.1)だけでなく、現場に抜け道を作る(下記) |
| C 対象外にせず、承認者を上位に限る | 活動の緩和には**賛成**。ただし「上位」の定義を増やさない |

**現場の案(B と C の合成)**

1. **CL の判定そのもの**(判定の記録と判定者の記名、G-1 前提条件2)は、7.3の対象外と明記する。これは新しい条項ではなく、前提条件の定義(第4章冒頭)を7.3の対象の限定の項目に1行写すだけ。もともと前提条件は7.3の射程外なので、**義務を増やさず、読みを固定する**
2. **CL1 以上の案件で、安全適合性の検証の緩和を7.3で求める場合**は、承認者が「作成を指示した者でなく、実装した者でない」ことに加え、**承認の記録に当該の CL を書く**。この条件は新しい承認の階層ではなく、既存の台帳の様式の「理由」欄に CL を書かせるだけで済む。記録が残れば、事故の後に「誰が何を失うか」を辿れる
3. **7.4 の禁止列挙**(G-4・G-5・認証・認可・データ保全の検証)は、**7.3の一般の例外承認でも迂回できない**と7.4の冒頭に1行で明示する。「ファストトラックの禁止は、7.3 の例外承認の対象外でもある」と書く。これは新しい義務ではなく、既存の禁止の射程の明示である
4. 外部調査の「独立した評価者」(26262・61508)の形は、本標準では **G-6 の独立した人の確認と、同一人物の承認の禁止**で既に近い形が取れている。新しい独立の段(別部門・別組織)は足さない。細かい定義の増加になり、小規模組織で成立しない

### 破られたとき誰が何を失うか

- 判定そのものを免除した場合(案の1が無い状態): 安全クラスが付いていない案件の出荷。失うのは**利用者の安全**。記録の上では、台帳に承認者の記名が残る
- 検証を緩和した場合: 承認者が責任を負う。現状は承認者の記名だけで、事故の後にしか見つからない
- 7.4 の禁止対象の迂回: 認証・認可・データ保全の検証を後追いにした出荷。失うのは**顧客のデータ**。取り消せない

### 例外承認で受けられるか(方針2)

判定そのものは、例外承認で受ける対象ではない(元から効かないと読み、明記で固定する)。判定に応じた活動の緩和は、**例外承認で受ける**。条項を新設せず、既存の7.3の枠内で「理由欄に CL を書く」だけで足りる。7.4 の禁止は新設ではなく既存の禁止の再掲。

### 機械で閉じるか

機械で閉じるのは「台帳の行の理由に CL の値があること」と「対象が7.4の禁止列挙のゲート番号を含まないこと」の存在・構文の検査だけ。承認の妥当性は機械では閉じない。これらは manual / undelivered として根拠水準マークで開示する(EV-0271 に記録済みの構造を保つ)。

### 未確認

- 集約が CL を見て例外の行を拒む経路が別にあるかは、grep の範囲で見つけていない(読み落としがありうる)
- CL1 以上で例外承認が実際に使われた事例は無い。上の抜け道の使われ方は想像であり、実証は無い

## 論点7 前提条件の混在(2.8 と G-1 の表)

- **(i) SR4**: 2.8 が正。「SR4 が残る間は G-1 の審議を開始しない」は安全に係るため、G-1 の前提条件の表へ行3として足す。前提条件の新設ではなく、既存の2.8との一致である。現場の実態: check-d0 は SR4 を見ず、check-g1 は SR4 の語を持たない。いまは**誰も止めない**。表に書いて、手引きと検査が追う(IMPL-0849 の降ろし)のが筋。機械の検査にできるのは、テンプレ9の SR4 の欄の「残存」の値の存在までで、危険源の評価の妥当性は人
- **(ii) D-0 の期日超過**: 対象が SG であって G-1 ではない。check-d0 は G-1 を止め SG を止めない。現場の実態は G-1 を止める形で動いているため、**2.8の文を G-1 の停止へ改める**のが追認で最も軽い。SG の前提条件を書く表は第4章に無く、SG に「始めない」を足すと新しい前提条件を作る。D-0 が期限切れの案件で SG(投資の継続判断)を進めたい場面は現場には多く、止めると SG が詰まる。止めるなら理由が要る。理由がないまま止めることは、現場の運用を重くするだけである
- 採らない候補(「前提条件の混在」を新しい節として定義する)は、第4章冒頭で定義済みのため同意

## 現場が最も懸念する点

論点6 の案の3(7.4 の禁止は7.3でも迂回できない)を書かないと、**ファストトラックの禁止列挙が事実上、通常の例外承認で迂回される**。現場は「ファストトラックを申請するより、通常の例外承認で出す方が楽」と読む。案の1〜3 は、条項の新設ではなく既存の規定の射程の明記であり、方針(1)(2)に収まる。破られたときに失う者が利用者である以上、安さではなく信頼性で採る。
