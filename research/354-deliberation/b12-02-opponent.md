## 1. IMPL-0120(表明の様式の値の行)

起案の (a) に**賛成**。ただし次の4点を条件にする。

1. **件数の出どころを裁定で固定する(P-4)**。記録の欠落の件数は、`claimForRange.name` を下げる式と同じ `gaps.length` とする。`gaps` は記録の欠落のほか記載の欠落なども含む(既存の blockers の文も「記録の欠落などの欠落」)。数え方を狭めると、名を下げた理由の件数と併記の件数が別になる。広い側(多く数える側)を採り、行の語を「記録の欠落など(集約の欠落の一覧)」とし、種別を分けていないことを note に書く。未達の件数も、名を決める `claimBase.unmet` の数とする
2. **0 件と「無し」を省かない**。1.10.2 は「無い場合は 0 件と書く」「無い場合は無しと書く」を求める。既存の 6180 行は逸脱の一覧を空のとき出さない(`listedDeviations.length ?`)。新しい行は常に出す
3. **作業中の版でコミットが読めないとき**: `workingDraftLabel` は `kbSource.commit` が16進でないときコミットを付けない。そのときは「コミットの識別なし(適用の表明に必要な併記を欠く)」と明示する。黙って省くと、併記を欠く表明を出しうる
4. **試験の足場**: `test-edition-end.mjs` は集約を通さず `config.mjs` の関数を直接呼ぶ。集約の本体(6000 行台の品質レポート)は試験で回せない。値の行を組む純粋な関数を `config.mjs` に置いて export し、集約はそれを呼ぶ。試験は関数を呼ぶ。入口(コマンド)の規定ではないので関数の試験で足りる(implementation-marking.md「machine の要件」)。gate-g5.yml 171 行が `test-edition-end.mjs` を走らせており、結線の要件3 を満たす

採らない(起案と同じ): 表明の文を機械が書く案(ADR-0083 の「表明する者が述べる」と名義)。

追加の留意: 組織の外へ渡す形(`external`)では、既存の行と同じ扱いにする。離脱の一覧の文に保持者の名が入りうる(5409 行の「数えなかった: 名(理由)」)。外へ渡す形では一覧を識別だけにするか、既存の 6180 行の扱いに揃える。

## 2. IMPL-0309(同じ案件の再開)

起案の (d)+(c) に**条件つきで賛成**。

- 新 ADR(0165)が要る。implementation-marking.md 134 行は「ADR-0084 の後に adopter とした規定は、decision= が指す ADR の決定に記録する」「理由を書けない規定は scheduled」と定める。ADR-0083 決定2 は理由(再開の経路を持たない)を書くが、採用者に求めることを書いていない。採用済みの ADR は書き換えない
- 付け替えの代案を比べた。#446(体制・構成・委任・D-0・**変化点の反映**)は `changeLog` の種別の追加を範囲に読める。しかし、降ろす意図の無い項目を scheduled で積むことになり、先送りの表示になる(scheduled は「降ろす予定がある」の意味)。採らない
- **起案の理由づけの1点に反対する**: 起案は「再開は新しい案件として始め直す道が既にある」と書く。これは 1.10.4 が塞ぐ型(終了して別の案件として始め直し、件数を数え直す)そのものである。同じ案件かどうかは人の判断で、標準も template も、別の案件として始め直すことを勧めてはならない。ADR と README にこの道を書かない
- **README の1文を実態に合わせる**: template は終了の後の構成の変更を `notice` のほかは拒む(IMPL-0307)。起案の文(「終了と再開の間を記録の欠落として表示し…」)だけでは、採用者がどこで表示するのかが分からない。template に表示の場所が無いことと、表明する者が表明の文の中で述べることを書く
- 本 Issue の規定は no-adopter の登録(`impl-no-adopter.yaml`)に当たらない(1.10.4 は登録に無い)

### 3.2 機械で一部を数える案(起案が挙げていない代案)

ワークフローの YAML(`environment:` と `secrets.*`)と env-check の配備の参照の限定から、(a) の形を推定する案を検めた。採らない。

- 配備のジョブの特定が推定になる(名前・権限からの推測)
- (b) の受け手の検証と (c) の配備先の拒否は、リポジトリの外にあり読めない
- env-check の3項目は「G-8 の適合の判定には使わない」(ADR-0090 決定6・README 659 行)。数えた結果を名に効かせると、この決定と食い違う
- 部分の検出を「数えた」と表示すると、確かめていない (b)(c) を確かめたと読ませる

### 3.3 adopter にするときの条件(P-6)

adopter の開示を標準の台帳だけに置くと、採用者の出力で食い違いが残る。次を同じ束で入れる(手引き (c) と出力の文。新しい欄・規則は足さない)。

1. `template/scripts/init/generate-profile.mjs` 3654 行の「数えません」の列挙に「配備の資格情報を、配備を許す参照に結び付けていない構成(7.3 の例外承認を経たものを除く)」を足す
2. 品質レポートの名の行(aggregate-evidence.mjs 6180 行)か、IMPL-0120 で足す行に、「配備の資格情報の離脱は数えていない(表明する者が確かめる)」を固定の文で添える

### 3.4 弱点(残る)

述べられる名は、配備の資格情報の離脱がある構成でも「適合の主張」と出しうる。3.3 の文で「数えていない」と読めるようにするが、名そのものは下がらない。IMPL-1003・IMPL-1004(ADR-0147 決定3)と同じ型の開示で、ADR-0165 に根拠水準マークで書く。
