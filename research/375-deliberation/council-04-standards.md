## R-1 同じ変化点での確認と使用

### 推す案

**案(a)**: 名簿へ足すのと同じ変化点で、本人以外が記名した氏名の確認を、その変化点の任命・記名の判定に数える。

ただし、次の**評価の順序**を ADR の決定として書き、実装の条件にする(条件の詳細は下の「条件や留保」)。

1. 記名者の資格(確認の記名者・任免の決定者)を、**変化点の前の構成**で照らす
2. 1 を通った記名による確認を、仮の記録としてこの変化点の構成に載せる
3. 確認を受ける者(付与される者)の前提条件は、2 の後の構成で照らす

「回帰か決定か」については、**事実としては回帰であり、解釈の確定としては決定である**、と扱うよう推す。#296 の付記(ADR-0079 決定7)はこの経路を議論しておらず(内部 §3.1。「同じ変化点」の検索で当たり無し)、評価の位置は付記の前後で変わっていない(内部 §2.4)。付記の意図(自己確認を塞ぐ)の外で結果が変わったので、回帰である。一方、標準 G-6(gate-criteria.md L1017)は確認と使用の前後を定めていない(内部 §1.1)。「書かれていない」状態を「課さないと決めた」状態へ移すのは決定であり、ADR に記録する。

### 理由(所在つき)

1. **外部の規格が求めるのは論理の前後であり、取引の分割ではない**
   - 21 CFR 11.100(b) は "Before an organization establishes, assigns ... the organization shall verify the identity" と、確認を割当の**前**に置く(外部 §1.1 L16)。同じ条の (c) は "prior to or at the time of such use" と「同時」を明示して許す(外部 §1.1 L17・L20)。この書き分けから、(b) は「同時」を許していないと読むのが文言に忠実である。ただし (b) が要るのは**確認の完了が割当に先行すること**であり、「別の機会」までは要らない(外部 §1.1 L23〜25)。上の評価の順序 1→2→3 は、確認の完了(記名の検査を通った記録)を割当(任命の検査)に先行させるので、(b) の文言を満たす
   - NIST SP 800-63A-4 は、確認の成功 → 加入を1つのセッションで終える形を基本とし(IAL3 は "The successful on-site identity proofing session concludes with the enrollment"。外部 §1.4 L62)、分かれる場合のために継続コードを用意する(同 L64)。分割は例外の扱いである
   - NIST SP 800-53 IA-12(1) は、上長・スポンサーの承認を "the registration process ... includes" と登録の手続の**中に**含める(外部 §1.3 L49・L51)
   - NIST SP 800-53 AC-2 c は、役割の所属の前提条件を課すことを求めるが、満たす時点は組織に委ねる(外部 §1.2 L32・L41)
   - ISO/IEC 27002:2022 5.18 の「認可の手続の完了の後に有効化する」趣旨は、二次資料でしか確かめていない(外部 §1.6。原文は未確認。穴 2)。二次資料の記載どおりなら、これも完了と行使の前後であり、取引の分割ではない
   - ISO/IEC 29115 は加入の段階と資格情報の管理の段階を別の段階として並べる(外部 §1.5 L86)。段階の区分が取引の分割を要するかは、本文を読んでいないため**未実証**(外部 穴 3)
2. **業界の実務は、確認と承認を1つの申請の直列の段にする**
   - Microsoft Entra は、身元の証明(Verified ID)を同じ申請の中で行い、承認者がその結果を見て同じ申請を承認する(外部 §2.2 L126〜128)。製品として禁じるのは自己承認だけである("Approvers aren't able to approve their own access package requests"。同 L122)
   - Okta は、確認の作業と承認を "a linear series of steps" として1つの申請に並べる(外部 §2.3 L139)
   - 独立の担保は「段の順序」と「段を担う人の分離」であり、取引の分割ではない(外部 §5 L204)
3. **案(b) の先例は、本件の対象と種類が違う**
   - GitHub の CODEOWNERS は基底ブランチの構成で審査者を決め(外部 §2.4 L149)、Kubernetes RBAC は "already have" の権限で結び付けの可否を決める(外部 §2.5 L163)。どちらも変更前の状態で読むのは**判定の規則と、操作する者の権限**である(外部 §2.5 L169、§4.2 L196)
   - 本件の氏名の確認は、**付与される者(Dupont)の前提条件**であり、操作する者(山田)の権限ではない(外部 §4.2 L198)
   - 本標準のテンプレートも、すでにこの区分に沿っている。任免の記名者の資格は変更前の構成で照らす(template HEAD `generate-profile.mjs` L2181「この変化点で名簿へ足した任命権者は記名できない」、L2182 の `isAppointer(before, decidedBy)`、L2187「変更前の D-0 表1 … の決定者」、L2188「この変化点より前に記載した人」)。記名者の資格は前の状態、付与される者の前提条件は変化点の中、という区分は、Kubernetes RBAC と IAM の両方と整合する
4. **ADR-0078 決定3 の原理と矛盾しない**
   - ADR-0106 L19 は、ADR-0078 決定3 の原理を「判定の材料を、判定される側が同じ変更で用意できない形にする」と要約し、記名者本人のアカウントの操作が伴う記録は同じ PR で足しても数える、と補う
   - 本件で、氏名の検査で判定されるのは Dupont の名義である。材料(確認)を用意するのは山田であり、判定される Dupont ではない。Dupont が自分で用意する経路は、本人の記名の拒否(HEAD L5228)、`confirmedNames` の `self`(config.mjs の HEAD の `confirmedNames`)、記名者の名義の検査の3か所で塞がる(実行 §確認4 L237)。この原理に照らしても、案(a) は許される
5. **案(a) は付記が塞いだ経路を開け直さない(観測)**
   - 本人の記名・AI の名義の記名・名簿に無い者の記名・記名なし・AI を示す語を含む名義どうしの確認は、試作 a1〜a3 で、いまの版と同じ理由・同じ件数で拒否された(実行 §確認4 L217〜223・L233)
   - p302 で開いていた X-decider と R1b は、試作でも閉じたまま(実行 L249〜252)
6. **監査の追跡は損なわれない**
   - 800-63A 第5章は、確認の手順の記録をアカウントに持たせる(外部 §1.4 L66)。本件では1件の変化点の記録に `nameConfirmations`・`decidedBy`・任命の差分が並び、確認者と順序が読める(外部 §5 L208、内部 §5.3 の「記録の確かさ」)。分割しないと監査が損なわれる、という主張を支える外部の規定は見当たらない

### 他の案を落とす理由

- **案(b) 前の変化点での確認を要する: 採らない**
  - 規格の要求として見当たらない(上の理由 1)。業界の主流とも合わない(理由 2)。先例は対象の種類が違う(理由 3)
  - 案(b) が主張する「確認が効力を持った後に使う」保証を、実際には作らない。2つの変化点を同じ PR に入れると、`decisionRecordFindings` は2件の記録を同じ PR の作成者・承認者で照合する(実行 §確認3 L117)。保証を作るには「前の変化点を含む PR が基底ブランチへ入った後」と定める必要があり、これは ADR-0106 の効力の時点に踏み込む別の決定になる(内部 §5.3 帰属の行)。保証の無い手順を課すのは、オーバーヘッドだけを足して信頼性を上げない形である
  - 独立の度合いは変わらない。2回とも記名するのは同じ山田でよい(内部 §5.3 独立性の行、外部 §4.1 L186)
  - 委任の席では手順そのものが成り立たない(実行 §確認6 L284。R-3 で扱う)
  - 1名の名簿は同じ変化点で通る(実行 O-1)。案(b) は1名と2名以上の扱いを非対称のまま残し、1名から2名へ移る変化点(O-2)を拒否し続ける
- **案(c) 開示の区別: R-4 で扱う**。R-1 の採否としては、案(a) の上に載る追加であり、案(a) と対立しない
- **案(d) 同じ変化点なら確認と任命に別の記名者を求める: 採らない**
  - NIST SP 800-53 AC-5 は、分離する職務を組織が定めるとし、確認と任命を分けるべき職務として名指ししない(外部 §2.1 L112・L115)。Entra も確認と承認を同じ人に持たせるかを方針の設定に委ねる(外部 §2.2 L134)
  - 本標準 3.13.3 は、1つの変化点の記名者を、すべての行の要件を満たす1人とする(roles-responsibilities.md L1996。作業ツリーの版)。案(d) はこの定めと正面から食い違う
  - 四眼原則の観点で問題になりうるのは「確認者と任命の決定者が同じ1人」であることだが(外部 §4.1 L187)、それは案(a)・(b) のどちらでも同じであり、本件の論点ではない。この危険が実際に事故を生むかは**未実証**である。課さないと決めた旨を ADR に書く
- **案(e) 名簿への追加と `nameConfirmed` の旗を同じ変化点で拒否する: 採らない**。確認の手順そのもの(名簿を渡して記名する)が成り立たなくなる(内部 §5.4)。外部の規格にも、確認の旗と名簿への登録を別の取引に分ける要求は無い(800-63A は未確認の申請者のアカウントも作れ、その状態を記録する。外部 §1.4 L65)
- **案(f)**: R-2 で扱う

### 条件や留保

1. **確認の記名者の資格を、変化点の前の構成で照らす**。この変化点で名簿へ足した人が、同じ変化点で他人の氏名を確認できないようにする。任命権者の扱い(HEAD L2181〜2182)と同じ形である。Kubernetes RBAC の "already have"(外部 §2.5)と同じく、操作する者の資格は前の状態で読む
   - いまの版で、この変化点で名簿へ足した人の記名が確認として通るかは、実行で確かめていない(**未実証**。実行の S-nonroster は名簿に無い者の記名だけを見た)。実装の前に、その場面の試験を足して確かめる
2. **評価の順序 1→2→3 を ADR の決定の本文に書く**。21 CFR 11.100(b) の「Before」を満たす根拠は、この順序にある。順序が実装で崩れると(たとえば仮の記録を記名の検査の前に載せると)、案(a) は (b) の要求を満たさなくなる
3. 仮の記録が持つのは、この変化点の入力の `decidedBy` と、`diffConfig` が作った `nameConfirmItems` の `id` に限る(実行 L131)。別の値を差し込む欄を作らない
4. **留保**: 21 CFR Part 11 の前文(62 FR 13430)の §11.100(b) への注釈を読んでいない(外部 穴 1)。FDA が「同じ手続の中の確認と割当」について見解を示していれば、本意見の根拠 1 が変わりうる。JIS Q 27001:2023・JIS Q 27002 の本文も確かめていない(外部 穴 2・4)。規制業の案件(Part 11 が掛かる案件)への当てはめは、これらを確かめるまで暫定とし、根拠水準のマーク(ADR-0026)で開示する

## R-2 評価の時点を揃える範囲

### 推す案

**一般原則を ADR に書き、そのうえで検査ごとの割り当てを表で閉じる**。どちらか一方ではなく両方を置く。

一般原則(案):

- **操作する者(記名者)の資格は、変化点の前の構成で照らす**。確認の記名者・任免の決定者・任命権者が当たる
- **付与される者の前提条件と、構成から導く表示・記録は、この変化点で記名の検査を通った記録を足した後の構成で照らす**。席の責任者の名義・適合性確認の承認者と実施者の名義・`nameOverrides`・[上書き] の表示が当たる
- 1つの変化点の中で、同じ問い(この氏名の確認が効いているか)に、検査ごとに違う答えを出さない

検査ごとの割り当て(template HEAD `72a98bd` の行):

| 検査 | 所在 | 照らす構成 | 理由 |
| --- | --- | --- | --- |
| 席の責任者・適合性確認の承認者・名簿の名義(`namingProblems`) | `generate-profile.mjs` L5058 | 記録を足した後 | 付与される者の前提条件。R-1 の本体 |
| [上書き] の出力 | L5345 | 記録を足した後 | 構成から導く表示。契約検査・構成書・`nameOverrideDetails` は記録を足した後の構成で上書きを表示しており(実行 §確認7 L303・L305)、出力だけが食い違う |
| 記録の `nameOverrides` | L5454 | 記録を足した後 | 契約検査が過去の記録の記名を照らすときに読む(実行 L305、verify-gate-contract.mjs L636)。記録が表示と食い違うと、後の監査で「その時点の上書き」を誤って読む |
| この変化点で出された適合性確認の権限(`qualificationAuthorityProblems`) | L5074 | 承認者の**名義**は記録を足した後。承認者の**資格**(席の責任者であること)は R-2 の範囲外 | 承認者の名義は付与される側の前提条件と同じ問いである(実行 X-qual-accountable の a1〜a3 に残る2件目。実行 L276) |
| 決定した者の記名(`nameProblems(config, change.decidedBy)`) | L5069 | 記名者の資格として前の構成と同じ結果になることを試験で固定する | 実行では a2 と a3 で全場面が同一だった(実行 L273)。理由は、本人の記名による確認が2名以上で `self` のまま効かないため。どちらで照らしても結果が変わらないことを試験で固定し、変わる入力が現れたら前の構成を正とする |
| 氏名の確認の記名(L5224 の `nameProblems`、L5228 の本人の拒否) | L5216〜5232 | 前の構成(名簿への所属を含む) | 記名者の資格。R-1 の条件 1。いまは `config`(変更を当てた後の名簿)で照らしているため、この変化点で名簿へ足した人が名簿の人として通る可能性がある(**未実証**) |
| `clampSeats` の `ctx` | L700 | `changeLog` を持つ構成 | R-3 で扱う。評価の時点ではなく、記録を渡していない問題 |

### 理由(所在つき)

1. **一般原則が要るのは、規格がこの区分を一般の形で持つからである**
   - Kubernetes RBAC は、操作する者の権限を "already have" で照らし、要求で作る権限を数えない(外部 §2.5 L163・L166)。IAM の実務は、付与される者の前提条件(本人確認・資格の提示)を同じ申請の前の段で満たし、後の段がそれを見る(外部 §2.2 L127、§4.2 L194・L197)
   - 外部 §4.2 L199 が指摘するとおり、検査ごとに時点を選ぶと「名簿の追加と任命は後の構成、氏名の確認だけは前の構成」という混在が生じる。いまの不具合はまさにこの混在である(内部 §2.2「2つの検査の時点が食い違っている」)。原則を書かずに検査ごとに決めると、次に検査を足す人が同じ混在を作る
2. **検査ごとの表が要るのは、原則だけでは実装が検査できないからである**
   - 本件の不具合は、a1(L5058 だけ)では直らず、a2(L5345・L5454 まで)で直った(実行 L208〜209・L393)。原則だけを書くと、どこまで直せば足りるかを実装者が判断することになり、a1 で止まる危険がある
   - 表に挙げた検査を、それぞれ場面の試験で固定する。これは ADR-0089 決定3 の「決定を固定する回帰の試験」の形に沿う
3. **記録と表示の一致は、監査の記録の要件である**
   - 800-63A 第5章は、確認の状態と手順の記録をアカウントに持たせる(外部 §1.4 L66)。21 CFR Part 11 は記録の正確さを前提とする(§11.10(a) の妥当性確認。本件の外部調査では原文を引いていない。**未実証**)。同じ変化点の記録(`nameOverrides`)と、同じ時点の構成から導く表示(構成書・契約検査)が食い違う状態は、どちらの記録が正かを監査者が決められない
   - この食い違いは案(b) でも確認の変化点で常に現れる(実行 L90〜91)。R-1 の採否と独立に直す

### 他の案を落とす理由

- **検査ごとに決めるだけ(原則を書かない): 採らない**。上の理由 1。混在を再生産する
- **一般原則だけを書く: 採らない**。上の理由 2。a1 で止まる実装を防げない
- **すべての名義の検査を、記録を足した後の構成で一律に照らす(内部 §5.4 案(f) の最大の形): 採らない**。記名者の資格まで後の構成で照らすと、この変化点で名簿へ足した人が、同じ変化点で記名者の資格を得る。Kubernetes RBAC が防いでいる昇格の形(外部 §2.5 L162)を開く。任命権者についてテンプレートが前の構成で照らしている設計(template HEAD L2181〜2182)とも逆になる

### 条件や留保

1. 表の「承認者の資格(席の責任者であること)」を同じ変化点で得てよいか(X-qual-accountable は、同じ変化点で Dupont を席の責任者にし、同時に承認者にしている)は、氏名の確認とは別の問いである。本件では結論を出さず、範囲の外と明記する。3.4.2 の承認者の定めと ADR-0110(作業ツリーの版)の記名の要件を行ごとに照らす規定との突合が要る
2. 原則の文言は、本標準の語(「変化点の前の構成」「記録を足した後の構成」)で書き、IAM 製品の語(stage、request)を持ち込まない
3. 決定した者の記名(L5069)は、前後どちらで照らしても結果が変わらないことが、実行の 21 場面でしか確かめられていない(実行 L273)。3名以上・委任の席・1名から2名へ移る場面を試験に足す

## R-3 委任の席(`clampSeats`)の回帰の候補

### 推す案

**本件で直す。回帰として扱う**。`clampSeats`(template HEAD `generate-profile.mjs` L697〜、呼び出しは L800)が名義の検査に渡す `ctx`(L700 `{ seats, people, delegation, governance }`)に、`changeLog` を含む構成を渡す。

あわせて、同じ `ctx` を受け取る `ruleStanding`(L678〜。`ruleDeciderProblems(ctx, rule)`・`ruleApprovalProblems(ctx, rule)`・`changeTypeProblems(ctx, …)` を呼ぶ)も、名義の検査で記録を引くかを洗い出す。委任の規則を決めた者・承認した者が AI を示す語を含む氏名の人であれば、同じ形で拒否される見込みがある(**未実証**。実行はこの経路を流していない)。

### 理由(所在つき)

1. **標準に対する不適合であり、解釈の余地が無い**
   - G-6 は、本人以外の人が記名した確認は「効く」と定める(gate-criteria.md L1017)。前の変化点で山田が記名して記録した Dupont の確認は、契約検査・集約では `other`(本人以外の記名)として数えられている(実行 §確認7 L298〜301)。同じ構成を、委任の席の判定だけが `invalid` と読む(実行 L275)
   - R-1 は「同じ変化点の確認を数えるか」という解釈の問いだったが、R-3 は**前の変化点で正しく記録した確認**を数えない問題である。どの案を採っても、標準の文言が効くとする確認が効いていない
2. **外部の規格に照らしても、確認を終えた者への付与を拒む理由は無い**
   - 21 CFR 11.100(b)・800-63A・IA-12 が求めるのは「確認の完了 → 付与」の前後である(外部 §5 L203)。確認が完了し記録された者に付与を拒むことは、どの規格の要求からも導けない
   - 800-63A 第5章は、確認の結果をアカウントの記録に持たせ、後の判断がそれを読む形を求める(外部 §1.4 L66)。記録を持たない文脈で判定するのは、記録を読まずに判断する形であり、この考え方に反する
3. **回帰である**
   - p302 は受け付けた(実行 X-qual-3step。実行 L263・L275)。付記(`4af67c5`)が `aiNameBlocked` を記録で判定するよう改めたことで、記録を持たない `ctx` が初めて結果を左右した(実行 L282)。根の場面と同じ構図である
   - #296 の会議体が委任の席の扱いを変える意図を示した記録は無い(内部 §3.1)
4. **信頼性の観点で、放置の害が大きい**
   - 手順の上で正しい確認を終えても委任にできないため、利用者は「協働までは宣言できます」の案内に従って席を協働に留めるか(実行 L270)、構成を手で書き換えたくなる。後者は本標準が禁じる形である(ADR-0055 L132「構成を書き換えるのは、変化点の手続だけとする」)。正しい状態を拒む検査は、手順の外への迂回を誘う(迂回が実際に起きるかは**未実証**)
   - 案(b) を推す委員にとっても、案(b) の手順(前の変化点で確認してから使う)は委任の席で成り立たない(実行 L284)。直さない限り、どちらの案も委任の席では手順を持たない

### 他の案を落とす理由

- **別 Issue に切り出す: 採らない**。原因が同じ付記にあり(実行 L282)、R-2 の原則(「付与される者の前提条件は記録を足した後の構成で照らす」)の適用先の1つである。別に扱うと、R-2 の表に穴が残ったまま ADR が出る
- **委任の席では AI を示す語を含む氏名の人を責任者にしない、と決める: 採らない**。G-6 の確認の仕組み(L1017)を委任の席だけで無効にする根拠が、規格にも本標準にも無い。委任は人の確認を減らす向きの運用であり、慎重に扱う理由はあるが、それは席の上限・規則の承認(L708 の `ruleStanding` の呼び出し)で扱われている。名義の検査で塞ぐのは、目的と手段が合わない

### 条件や留保

1. 直した後に、委任の席の場面を回帰の試験へ足す。少なくとも次を固定する
   - 前の変化点で本人以外が確認した人を責任者にし、委任にできる(X-qual-3step の (3)。実行 L263)
   - 同じ変化点で確認した人の場合(X-qual-split・X-qual-accountable)は、R-1・R-2 の結論に従う
   - 本人の記名による確認・AI の名義の記名による確認の人は、委任にできないまま(拒否の件数と理由を印と同じく集合で照合する。ADR-0089 決定4)
2. 回帰の試験は、AI を示す語を含む氏名の人を委任の席に置く場面をいま持たない(実行 L283)。この場面の欠落が、付記の影響を見逃した原因である。scenarios の「F. 名義の機械検査の上書き」(scenarios.mjs L388〜)を、技術判断者の任命だけでなく委任の席・適合性確認の承認者へ広げる
3. `ruleStanding` の洗い出しの結果、同じ形の拒否が見つかれば同じ修正に含める。見つからなければ、その旨を実行の記録に残す

## R-4 記録・開示・ADR

### 推す案

1. **新しい ADR を起こす**。ADR-0079 決定7 は書き換えない(採用済みの本文)。新 ADR は ADR-0079 決定7 を「補う」として、次を決定に書く
   - R-1: 同じ変化点の確認を数える。評価の順序(記名者の資格は前の構成 → 記録を足す → 付与される者の前提条件)
   - R-2: 一般原則と、検査ごとの割り当ての表
   - R-3: 委任の席の判定は記録を持つ構成で照らす。回帰の修正である旨
   - 採らない案: (b)・(d)・(e)・(f) の最大の形・別 Issue への切り出し・(c) の新しい欄。各理由は R-1〜R-3 のとおり
   - **課さないと決めたこと**を明記する: 「確認と使用を別の変化点(別の PR)に分けること」「同じ変化点で確認者と任命の決定者を別の人にすること」
2. **記録・開示の区別(案(c)): 新しい欄は足さない。ただし、保証の開示に確認の記録の所在を出す**
   - 同じ変化点で確認して使った旨を表す旗は足さない。1件の変化点の記録に `nameConfirmations`・`decidedBy`・任命の差分が並ぶため、旨は記録から導ける(内部 §5.4 案(c))。800-63A 第5章が求めるのも「確認の手順の記録」であり、確認と付与が同じ取引かの旗ではない(外部 §1.4 L66)
   - 代わりに、G-6 の「確認した氏名は … 確認によって通した旨とともに出る」(gate-criteria.md L1017)の出力に、**確認の記名者と、確認を記録した変化点(changeLog の番号と日付)**を出す。プロセス内部監査の観点6 が、任命の記録と同じ記録かを機械に頼らず読める
3. **帰属(ADR-0106)が前後を保証しないことを、ADR の「反論されうる点」と G-6 の注記で開示する**
   - 確認と任命の前後は、変化点の中の評価の順序で保証する。帰属の確認(ADR-0106 決定3)は、同じ PR に入れた記録を同じ PR の操作で照合するため(実行 §確認3 L117)、前後を保証しない。これは案(a)・(b) のどちらでも同じである、と書く
   - 確認と任命は、PR が基底ブランチへ入った時点で同時に効力を持つ。21 CFR 11.100(b) の「Before」を論理の前後で満たすという読みは、前文(62 FR 13430)を読んでいないため暫定である
4. **根拠水準のマーク(ADR-0026)**: 次の2つに `:::caution[暫定 EV-NNNN / 見直し 2027-05]` を付ける(番号は台帳の次の番号を使う。見直しの月は、外部 穴 1・2・4 を埋める期間として半年を置く案)
   - 「規格(21 CFR 11.100(b)、NIST SP 800-63A-4、IA-12(1))は確認と付与の論理の前後を求め、別の取引への分割を求めない」。Part 11 の前文、ISO/IEC 27002:2022 5.18・JIS Q 27001:2023 の原文を確かめていない
   - 「確認者と任命の決定者が同じ1人であることを、同じ変化点で許しても独立を損なわない」。事故の事例も測定も無い(外部 §4.1 L187)
5. **実装マーク(#222)**: G-6 L1017 に足す評価の時点の規定へ IMPL を付ける。降ろし先はテンプレートの変化点の手続(`impl-targets.yaml` に登録済みの降ろし先から選ぶ)。回帰の試験で固定してから `state=delivered`、固定するまでは `undelivered`。既存の IMPL-0266 の注記(gate-criteria.md L1070。「`changeLog` の `nameConfirmations` と `decidedBy` がある場合だけ効く」)は、同じ変化点の記録を含む旨を足すかを突合する
6. **回帰スイートの印の外し方**
   - 根(scenarios.mjs L400)の `knownFailure: J1` と、連鎖の2場面(L402・L403)の `dependsOn` を外す。期待値は元のまま(反映)なので `changed` は要らない(内部 §5.2「回帰の試験」)
   - 節の `fixes`(L391 `['ADR-0054 決定1', 'ADR-0079 決定7', '#296']`)に新 ADR の決定を足す。Issue だけの引用で外さない(ADR-0089 決定3)
   - 付記が塞いだ経路と、R-1 の条件 1 の経路を拒否として固定する場面を足す: 本人の記名(S-self)・AI の名義(S-ai)・名簿に無い者(S-nonroster)・記名なし(S-nosign)・AI を示す語の名義どうし(S-mutual・S-mutual4)・**この変化点で名簿へ足した人の記名による確認**(実行に無い。新規)。受け付けとして固定する場面: 1名から2名へ移る変化点(O-2)・2名を同時に確認して任命(S-mutual3)・委任の席(R-3)
   - 印の見直しの月は 2026-12 である(scenarios.mjs L398)。過ぎると run.mjs が失敗にする(内部 §4)。12 月中に外すか、外せなければ見直しの月を延ばす理由を記録する
7. **拒否の文の案内を直す**。config.mjs L514〜517(HEAD の L517 の括弧書き)は、`nameConfirmed: true` を既に書いた入力にも「nameConfirmed: true を書く」と案内する(内部 §2.3)。案(a) では根の場面で拒否が出なくなるが、2名以上で記録の無い確認・本人の記名による確認の場合の案内として、「本人以外の名簿の人の記名で /process-change を通す」に改める

### 理由(所在つき)

- 新 ADR が要るのは、標準が確認と使用の前後を定めておらず(内部 §1.1)、どちらの向きも標準の解釈を確定させる決定だからである(内部 §5.1)。向きを AI が決めないため(ADR-0089 決定3、内部 §5.1)、会議体の結論を人が採って ADR に記録する
- 新しい旗を足さないのは、800-63A が求める記録(確認の手順と状態)が既に1件の記録にあり、旗を読む者と、読んで何を判断するかが定まらないからである(内部 §5.4 案(c))。読む者の定まらない欄は、記録の負担だけを増やし信頼性を上げない
- 帰属の開示を書くのは、ADR-0106 の読み手が「前の変化点に分ければ効力の前後が保証される」と誤読しうるからである。実行 §確認3 がその誤読を否定する観測を持つ

### 他の案を落とす理由

- **ADR を起こさず、テンプレートの修正だけで印を外す: 採らない**。ADR-0089 決定3 が求める「先に存在する決定」が無いまま、拒否していた入力を受け付けに変えることになる(内部 §5.1)
- **ADR-0079 の本文に追記する: 採らない**。採用済み ADR の本文は書き換えない(CLAUDE.md「意思決定の記録」)
- **「同じ変化点で確認して使用した」旨の旗を記録と開示に足す(案(c)): 採らない**。上の理由。代わりに確認の記録の所在を出す
- **EV のマークを付けない: 採らない**。外部 穴 1・2・4 を埋めないまま規格に整合すると書けば、実証を欠く判断を開示しないことになる(ADR-0026)
