## 監査の観点から先に置く問い

監査が記録に求めるのは、次の3つが**記録だけから**読めることです。

1. 確認した者が、確認される本人ではなく、AI の名義でもなく、名簿の人であること(独立)
2. 確認が、それに依存する使用(任命・記名)より論理的に先に済んでいたこと(順序)
3. 確認と使用の記名が、記名者本人の操作に帰属すること(帰属。ADR-0106 決定3)

案の比較は、この3つが案ごとにどう変わるかで行います。

## R-1 同じ変化点での確認と使用

### 推す案

**案(a) 同じ変化点の確認を、その変化点の任命・記名の判定に数える**。あわせて、これを「回帰の修正」としてではなく、**標準の解釈を確定させる決定**として ADR に記録する(扱いは R-4)。分類は「回帰であり、かつ決定を要する」とする。

### 理由(所在つき)

1. **独立は案(a) で弱まらない**。本人以外の記名かどうかの検査は、この変化点の入力で行われている(`template/scripts/init/generate-profile.mjs` L5216〜5232。L5229 で「本人の記名では確定できません」)。加えて `confirmedNames`(`template/scripts/gate/config.mjs` L391〜407)は、記名者が名簿に無い記録(L397)、本人の記名(L398 の `self`)、AI を示す語を含む名義の本人以外の記名(L400)を数えない。probe 確認4 は、試作 a1〜a3 で S-self・S-ai・S-nonroster・S-nosign・S-mutual・S-mutual2・S-mutual4 がいまと**同じ理由・同じ件数**で拒否されることを観測した。監査が最も恐れる抜け道(本人が自分を確かめる、AI 同士が確かめ合う)は、案(a) で開かない
2. **案(b) は独立を1件も増やさない**。前の変化点に分けても、記名するのは同じ山田でよい(内部 §5.3 の独立の行、外部 §4.1)。監査の目から見て、同じ人が2回記名した記録は、1回記名した記録より独立していない
3. **案(b) は順序の保証を作らない**。帰属の検査(`decisionRecordFindings`)は、同じ PR に入れた2件の記録を、同じ PR の作成者・承認者で照合する(probe 確認3 の表、A・B・C の3通り)。確認の記録と任命の記録は同じ時点で帰属を得る。「前の変化点」は記録の並びを作るだけで、**確認が効力を持った後に使った**ことの証跡にならない。監査の目から見ると、保証しない順序を保証のように見せる記録は、無い記録より有害である(読み手が保証を読み取るため)
4. **案(a) の方が、帰属の失敗に対して原子的である**。1件の記録に確認と任命が載るため、帰属が裏づけられなければ両方が同時に効力を失う(probe 確認3 の対照: a1〜a3 で R0 を受け付けた後、B・C は errors 1 件)。案(b) を同じ PR で行うと結果は同じだが、別の PR に分けた場合、確認の PR だけが入り任命の PR が落ちる中間の状態が生じる。中間の状態そのものは害が小さいが、案(b) が順序の保証を得るにはこの分割が必須になり、手順が増えるだけで独立は増えない
5. **外部の規格は論理の前後を求め、取引の分割を求めない**。21 CFR 11.100(b) は "Before … the organization shall verify"(外部 §1.1)、NIST SP 800-63A-4 は1セッションで確認から加入までを基本の形とする(外部 §1.4)。IA-12(1) は承認を登録の手続の中に含める(外部 §1.3)。案(a) は、1つの変化点の中で「確認の記名の検査 → 確認を数える → 任命の検査」の順を守ることで、この前後を満たす
6. **意図の記録が無い**。#296 の付記の目的は自己確認の経路を塞ぐことであり(内部 §3.1。`research/296-deliberation/decision.md` L152、`implementation.md` L446)、同じ変化点の扱いを議論した記録も、前の変化点を求める記述も無い。G-6(`src/content/docs/phase4-process-design/gate-criteria.md` L1017)と ADR-0079 決定7(`src/content/docs/adr/0079-coverage-scope-approval-binding-self-heal.md` L57・L109)も前後を定めていない。いまの拒否は決定の帰結ではなく、評価の位置(L5058)と記録の位置(L5429〜5452)の食い違いの帰結である(内部 §2.2・§2.4)
7. **いまの拒否の文が、監査の追跡を誤らせる**。L5058 の拒否は `config.mjs` L514〜517 の文「名簿の該当者へ nameConfirmed: true を書く」を案内する(probe 確認1 の全文)。入力は既にそれを書いている。記録の上では、利用者が案内どおりにしても拒否される。案内と挙動が食い違う統制は、利用者に回避(氏名の表記を変える、`nameConfirmed` を外して別の名義で書くなど)を促す。回避の動機は記録の正しさを損なう(推測。実地の観測は無い。**未実証**)

### 他の案を落とす理由

| 案 | 採らない理由 |
| --- | --- |
| (b) 前の変化点での確認を要する | 独立を増やさない(理由2)。同じ PR では順序の保証を作らず(理由3)、保証を得るには「前の PR が基底ブランチへ入った後」という別の手順が要るが、それを検査する箇所はテンプレートに無い(probe 確認3 の推測)。委任の席では手順が成り立たない(probe 確認6、X-qual-3step。R-3)。外部の規格に根拠が無い(外部 §5)。GitHub CODEOWNERS・Kubernetes RBAC の先例は判定の規則・操作者の権限を前の状態で読むもので、付与される者の前提条件ではない(外部 §2.4・§2.5) |
| (c) 案(a) に、同じ変化点で確認して使った旨の開示を足す | R-1 の判定としては (a) と同じ。開示の要否は R-4 で扱う |
| (d) 同じ変化点なら確認者と任命の決定者を別の者にする | 同じ変化点に限って課す理由が無い。前の変化点に分ければ同じ1人で済むため、分割で逃げられる統制になる。四眼の論点(確認する者と任命する者が同じ1人)は案(a)・(b) で差が無く(外部 §4.1)、本件の範囲の外の論点である。課すなら変化点の数によらず一律に課す形でなければ統制として成り立たない。本件では採らず、R-4 の「採らない案」に理由を書く |
| (e) 名簿の追加と `nameConfirmed` の旗を同じ変化点で拒否する | 確認の手順そのもの(名簿を渡して記名する)が成り立たなくなる(内部 §5.4)。採る理由が無い |
| (f) 名義の検査すべての評価の時点を揃える | R-2 で扱う |

### 条件と留保

- **条件1**: 案(a) を採るなら、評価の時点を揃える範囲は R-2 の a2 以上とする。L5058 だけを直す a1 は、この変化点の記録の `nameOverrides` を空のまま残す(probe 4 節の表、R0 の a1 の欄)。監査の目から見ると、a1 は「確認の上書きが効いていないのに、AI を示す語を含む氏名を席の責任者にした」と読める記録を作る。**a1 は案(a) の実装として受け付けない**
- **条件2**: 案(a) が新しい自己確認の経路を開かないことを、回帰の試験の場面で固定する。probe の S-self・S-ai・S-nonroster・S-nosign・S-mutual・S-mutual4・X-decider を、同じ変化点で拒否される場面として加える。案(a) の主張(抜け道を開かない)は、いまは試作の観測にしか支えられておらず、試験に固定されていない
- **条件3**: 向きは AI が決めない(内部 §5.1、`research/319-deliberation/council-05-defender.md` L71)。案(a) は機械の検査が拒否する範囲を狭めるため、人の決定(ADR の承認)を経る
- **留保1**: 案(a) で「確認と使用の論理の前後」を守るのはコードの評価の順序であり、記録の中の順序ではない。1件の記録の中で、確認が任命より先に評価されたことを記録そのものは示さない。監査はこれを「受け付けた記録は、受け付けの時点の検査を通った」という手続の保証に頼って読むことになる。手続の外の書き換えは 3.13.5 が検出し、検出できない偽の追記は案(a)・(b) のどちらでも防げない(R-2 の留保)。この点で案の差は無い
- **留保2**: 「同じ変化点で確認しても、前の変化点で確認しても、確認の確かさは変わらない」は、記名者が同じ1人である限りで成り立つ論理の主張である。確認の中身(実在の確かめ)の質が、変化点を分けることで上がるか下がるかの観測は無い(**未実証**)

## R-2 評価の時点を揃える範囲

### 推す案

**一般原則を ADR に書き、そのうえで原則が掛かる検査を ADR の中で列挙する**。原則と列挙の両方を置く。

- 原則: 検査を2種類に分ける
  - **記名の正しさの検査**(記名者が本人以外か、名簿の人か、AI の名義でないか)は、**この変化点の入力**で照らす
  - **確認が効いているかの判定**(`nameConfirmedValid`・`aiNameBlocked`・`nameOverrides` を経るもの)は、**この変化点の記録を足した後の構成**で照らす
- 列挙(テンプレート `72a98bd` の行):

| 検査 | 所在 | 扱い |
| --- | --- | --- |
| 席の責任者・適合性確認の承認者・名簿の記名 | `generate-profile.mjs` L5058 `namingProblems(config)` | 記録の後の構成で照らす |
| 出力の `[上書き]` の行 | 同 L5345 `nameOverrides(config)` | 記録の後の構成で照らす |
| 記録の `nameOverrides` | 同 L5454 `nameOverrides(config)` | 記録の後の構成で照らす(下の「記録の意味」) |
| 決定した者の記名 | 同 L5069 `nameProblems(config, change.decidedBy)` | 記録の後の構成で照らす(結果は変わらない。原則に例外を作らないため) |
| 氏名の確認の記名者の名義 | 同 L5224 `nameProblems(config, change.decidedBy, { requireRoster: true })` | 記録の後の構成で照らす(同上)。本人の記名の拒否(L5229)は入力で照らしたまま残す |
| この変化点で出された適合性確認 | 同 L5072〜5076 `qualificationAuthorityProblems(config, s, …)`(`config.mjs` L1390〜) | 記録の後の構成で照らす |
| 委任の席の上限 | 同 L700 `clampSeats` の `ctx` | R-3。記録を持つ構成で照らす |
| 通知先の記名 | 同 L5155・L5158 の `nameProblems(config, change.notice.to / toPerson.name, …)` | 原則の対象として列挙し、結果が変わる入力があるかを試験で確かめる(probe は試していない) |

### 理由(所在つき)

1. **原則だけでは監査できない**。どの検査が原則に従っているかを、監査はコードの行で確かめる。列挙が無ければ、原則に従わない検査を見つける基準が無い。今回の事象そのものが、評価の位置(L5058)が記録の位置(L5429〜5452)より前にある、という列挙されていなかった食い違いから生じた(内部 §2.2)
2. **列挙だけでは、次に足す検査に掛からない**。#296 の付記は `aiNameBlocked` を記録で判定する形へ改めたが(内部 §2.4)、既存の呼び出しの位置を見直さなかった。その結果、L5058 のほかに L5345・L5454(probe 確認2)、L700(probe 確認6)、L5072〜5076(probe 確認6 の X-qual-accountable)の、少なくとも4か所に同じ構図が残った。新しい検査を足すたびに個別に決める形では、同じ漏れが繰り返される。原則があれば、足す側が「この検査はどちらの種類か」を問える
3. **記録の `nameOverrides` は、監査の順序の証跡そのものである**。契約検査は過去の記録の記名を「その時点の記録(`nameOverrides`)か、現在の名簿」で確かめる(`verify-gate-contract.mjs` L635〜636)。L5454 が記録の前の構成で評価すると、確認を記録した変化点の `nameOverrides` が空になる(probe 確認2 の (1)、4 節の a1)。監査の読み手は、その変化点の時点で上書きが効いていなかったと読む。案(a) で同じ変化点に任命が載る場合、記録は「上書きが効いていない氏名を責任者にした」と読める。**記録が事実と逆のことを言う状態は、監査が最も避けたいもの**であり、a1 を受け付けない理由(R-1 条件1)である
4. **決定した者と確認の記名者を記録の後の構成で照らしても、新しい経路は開かない**。probe の a2 と a3 の結果は 21 場面のすべてで同一だった(probe 確認6 の箇条)。理由は、同じ変化点の確認で効くのは本人以外の記名に限られ(`config.mjs` L398〜400)、記名者自身の確認は2名以上の名簿では `self` のまま効かないためである。原則に例外を作らずに済む
5. **アカウント名の確認と揃う**。`accountsConfirmed` は、記録が足された後の構成で判定されている(内部 §2.5)。氏名だけが記録の前で判定される非対称は、根拠の無い差である

### 他の案を落とす理由

| 案 | 採らない理由 |
| --- | --- |
| a1(L5058 だけ) | 記録の `nameOverrides` が事実と逆を言う(理由3)。回帰の試験の根の期待と連鎖の場面も満たさない(probe 4 節) |
| a2 で止め、決定した者・確認の記名者・適合性確認を前の構成のまま残す | 結果が変わらない検査を前の構成のまま残すと、原則に例外が生じ、なぜ例外かを説明する記述が要る。説明できる理由が「結果が変わらないから」しか無く、それは将来の変更で崩れる。適合性確認(L5072〜5076)は結果が変わる(probe X-qual-accountable)ため、残す理由が無い |
| 検査ごとに決め、原則を書かない | 理由2。次の検査で同じ漏れが起きる |
| 原則だけを書き、列挙しない | 理由1。監査の基準にならない |

### 条件と留保

- **条件1(不変条件の明記)**: 理由4 の「新しい経路を開かない」は、`confirmedNames` が AI を示す語を含む名義の本人以外の記名を数えないこと(`config.mjs` L400)に依存する。この行が緩むと、AI を示す語を含む2名を同じ変化点で足して互いに確かめ合う経路(S-mutual)が、記録の後の構成で照らすことで開く。ADR にこの依存を不変条件として書き、S-mutual・S-mutual4 を回帰の試験で固定する
- **条件2(実装の形)**: 列挙の各箇所へ個別に「仮の記録」を差し込む形(probe の `withThis()`)では、仮の記録と L5429〜5452 で実際に足す記録とが、将来ずれうる。**実際に足す記録の項目を先に作り、それを評価と書き出しの両方に使う**形を求める。仮の記録と本物の記録が別に作られる限り、「評価に使った記録」と「残した記録」の一致は保証されない(監査の観点では、評価の根拠と保存した証跡が同じものであることが要る)
- **条件3(記録の意味の定義)**: 記録の `nameOverrides` を「この変化点を反映した後に効いている上書き」と定義し、標準の記録の表(3.13.4。作業ツリーの `roles-responsibilities.md` L2033〜。未コミットの差分があるため行は動きうる)か ADR に書く。いまはこの欄の時点が定義されていない
- **留保(本件の外の監査の所見)**: 契約検査の過去の記録の照合(`verify-gate-contract.mjs` L635〜636)は、記録の `nameOverrides` に無い名義を**現在の名簿**で確かめる。後の変化点で確認した氏名が、それより前の記録の記名を遡って正当にする形である。ただし、手続を経ない構成の書き換えと変更記録の切り詰め・差し替えは 3.13.5 が機械で検出する(作業ツリーの同ファイル L2079〜、IMPL-0034)。検出できないのは、要約値を合わせて偽の記録を追記する改ざんであり、これは 3.13.5 が自ら限界として開示している。その改ざんでは `nameOverrides` の値も偽れるため、照合を記録の値だけに絞っても防げない。**したがって、この所見は本件でも後継の Issue でも直す理由に至らないと判断する**。記録として残すにとどめる

## R-3 委任の席(`clampSeats`)の回帰の候補

### 推す案

**本件で直す。分類は回帰とする**。直し方は R-2 の原則に従い、`clampSeats` へ渡す構成(`generate-profile.mjs` L700 の `ctx = { seats, people, delegation, governance }`)に、この変化点の記録を足した後の `changeLog` を持たせる。修正の向きは緩める向き(いま拒否している委任を受け付ける)なので、R-1 と同じ ADR の決定を根拠に置く。

### 理由(所在つき)

1. **構図が根の場面と同じで、原因が同じ付記である**。`clampSeats` は L714(責任者)・L719(適合性確認の実施者)・L721(承認者)で `nameProblems(ctx, …)` を呼ぶ。`ctx` は `changeLog` を持たないため、`confirmedNames`(`config.mjs` L393 で `config?.changeLog ?? []` を読む)は常に空になり、2名以上の名簿では確認が `invalid` になる。p302 は名簿の旗だけで通したため、`ctx` に記録が無くても結果に響かなかった(内部 §2.4 の `aiNameBlocked` の行)。#296 の付記が判定を記録へ寄せたことで、記録を持たない評価の位置が初めて結果を左右した(probe 確認6 の推測)。#296 の会議体がこの経路を議論した記録は無い(内部 §3.1)
2. **前の変化点で正しく確認した人でさえ拒否される**。X-qual-3step の (3) は、山田(本人以外・名簿の人・AI の名義でない)が前の変化点で確認した Dupont を、委任の席の責任者として拒否した(probe 確認6 の表と拒否の全文)。これは案(a)・(b) のどちらの立場からも正しくない拒否であり、議論の余地が少ない。案(b) を採る者にとっても、案(b) の手順が委任の席では成り立たない(probe まとめ 2)
3. **原則を書いて既知の違反を残すと、監査上の不適合を自ら残すことになる**。R-2 で原則を ADR に書く以上、同じ原則に反すると分かっている箇所を残せば、準拠テンプレートが標準の決定に反した状態で配布される。後継の Issue へ分けると、その間の期間について「既知の不適合」の開示が要り、開示を書く手間と読み手の負担が、直すより大きい理由は見当たらない
4. **拒否の向きが安全側でも、正しくない拒否は統制を弱める**。委任にできない席は協働に留まるため、直接の危険は小さい。しかし、案内(`config.mjs` L517 の「nameConfirmed: true を書く」)どおりにしても通らない統制は、利用者に回避を促す(R-1 理由7。**未実証**)。たとえば責任者を別の人に書き換えて委任を通し、実際の判断は元の人が行う、という記録と実態の乖離は、監査が最も見つけにくい種類のずれである(推測)

### 理由(所在つき)

1. **区別を足さない理由**: 1件の変化点の記録に、`nameConfirmations`・`decidedBy`・差分の行ごとの種類(3.13.4 の表の #7、IMPL-0445 の `rowKinds` の `appoint`)が並ぶ。同じ変化点で確認して任命したことは、記録から導ける。新しい欄は、それを読む者と、読んで何を判断するかが定まるときに限って足すべきである(内部 §5.4 の (c) の所見)。監査の立場で考えても、同じ変化点か前の変化点かで判断を変える場面が見当たらない。確認と任命を同じ山田が記名することは、変化点を分けても起こるためである(R-1 理由2)。読む者のいない欄は、記入の誤りだけを増やす
2. **帰属の前後を明記する理由**: 監査が最も誤読しやすいのはここである。`confirmedNames` は `/process-change` の時点で作業ツリーの記録を数え(`config.mjs` L391〜407)、ADR-0106 決定3(`adr/0106-material-records-attributed-before-effect.md` L54〜56)の帰属は PR の時点で確かめる(probe 確認3)。案(a) でも案(b) でも、確認は帰属の前に構成の中で数えられる。効力(基底ブランチへ入ること)は帰属の後に限られ、確認と使用は同じ PR の検査で同時に裏づけられ、同時に落ちる。この性質を書かなければ、読み手は「前の変化点で確認した」記録を「帰属を得た確認の後に使った」と誤って読む(案(b) を採った場合に特に起こる)。書けば、本標準が保証するのは**確認と使用が帰属なしに効力を持たないこと**であり、**確認が使用より先に効力を持つこと**ではない、と読み手が区別できる
3. **G-6 に1文を足す理由**: いまは前後が「書かれていない」(内部 §1.1 の末尾)。CLAUDE.md のコアポリシーは「書かれていない」と「課さないと決めた」を読み手が区別できる状態を求める。ADR だけに書くと、採用組織が G-6 を読んだときに、同じ変化点の確認が効くかどうかが分からない。テンプレートの挙動(本件で受け付けに変わる)と標準の文言を一致させるために、本文に置く
4. **ADR を1件にまとめる理由**: R-1〜R-3 は同じ原則(確認が効いているかの判定は、記録を足した後の構成で照らす)の適用である。分けると、原則がどの ADR にあるかを、読み手が探すことになる
5. **EV を付ける理由**: 外部の規格の読みには穴がある。21 CFR Part 11 の前文の注釈、ISO/IEC 27002:2022 5.16・5.18 の原文、ISO/IEC 29115 8.1 の本文、EU GMP Annex 11 を確かめていない(外部 §6 の穴 1・2・3・5)。27002 は二次資料だけである(外部 §1.6)。「規格は取引の分割を求めない」は見た範囲の原文に基づく読みであり、ADR の理由に使うなら `:::caution[暫定 EV-NNNN / 見直し YYYY-MM]` で開示する。見直しは穴 1・3 を埋める時期に置く(穴 3 は ITU-T X.1254 で無償で埋められる見込み。外部 §1.5)
6. **印を外す手順の理由**: ADR-0089 決定3(`adr/0089-regression-suite-under-version-control.md` L58〜)は、期待値を改めるときに先に存在する決定を引くことを求める。本件は期待値を改めない(p302 と同じ「反映」へ戻す)ため `changed` は要らないが、印を外す根拠として新しい ADR を引く(内部 §5.5 の ADR-0089 の行)。印の見直し月 2026-12 を過ぎると `run.mjs` が失敗にする(内部 §4 の印の働き)ので、テンプレートの修正 → テンプレートの main へ入る → 参照を進める → 印を外す、を同じ版の範囲で行う。順序を逆にすると、根が「予期せず通った」で落ちる(probe 確認5 の回帰スイート全体)
