## R-1 同じ変化点での確認と使用

### 推す案

**案(a) を採る。同じ変化点で、本人以外が記名した氏名の確認を、その変化点の任命・記名の判定に数える。** あわせて、標準の文言を「書かれていない」状態から「定めた」状態へ移す。G-6 L1017 に次の趣旨の1文を足す(起案。文体は箇条書きの「である調」)。

> 確認は、記録した変化点の中から効く。同じ変化点の任命と記名の判定に数える。ただし、確認の記名の要件(本人以外・名簿の人・AI の名義でない)を、その変化点の任命と記名の判定より先に照らし、要件を満たした確認だけを数える。

D-0 表5 の欄の定義(L153・L422)は改めない。「確認した者と日付」は、同じ変化点で任命した場合も同じ日付・同じ記名者として読めるためである。

分類: **回帰である**。ただし、標準が前後を定めていなかったため、閉じるには解釈を確定させる決定(ADR)を要する。回帰と呼ぶ根拠は、(1) p302 は受け付けた(probe 確認1・確認8)、(2) #296 の会議体は同じ変化点の扱いを議論していない(内部 §3.1)、(3) 同じ変化点の確認の記名の正しさは L5216〜5232(作業ツリー L5276〜5292)がその変化点の入力で照らしており、確認が効くかだけを前の構成で照らす食い違いは設計の意図として説明できない(内部 §2.2)、の3点である。回帰を決定で追認しない(期待値を「拒否」へ反転させない)。

### 理由

1. **文言の上で、確認は変化点の記録の一部である**。G-6 L1017 は「名簿の変更として確認の旨を記録する」と書く。名簿の変更は変化点の記録(3.13.4)の一行であり、同じ記録の任命の行と同じ記名者・同じ日付を持つ。確認の記録が載った変化点で確認を効かせないと読むには、「記録した変化点の次の変化点から効く」という限定が要る。その限定は標準のどこにも無い(内部 §1.1)。案(a) は文言の素直な読みに沿う
2. **外部の規格の要求は論理の前後であり、取引の分割ではない**。21 CFR 11.100(b) の "Before" は確認の完了が割当に先行することを求めるが、別の手続を要求しない(外部 §1.1)。NIST SP 800-63A-4 は1セッションでの確認 → 加入を基本とする(外部 §1.4)。IA-12(1) は承認を登録の手続の中に含める(外部 §1.3)。起案した1文の「先に照らし、要件を満たした確認だけを数える」は、この論理の前後をそのまま規定にする
3. **自己確認の経路を開かない(観測)**。試作 a1〜a3 で、本人の記名・AI の名義の記名・名簿に無い者の記名・記名なし・AI を示す語の名義どうしの確認は、いまと同じ理由・件数で拒否された(probe 確認4)。本人の記名は3か所で塞がる。受け付けに変わったのは、本人以外で AI の名義でない名簿の人(山田)が記名した場面だけである
4. **1名の名簿と2名以上の名簿の扱いが揃う**。1名の名簿では、いまも同じ変化点で確認して任命できる(probe O-1)。2名以上だけが別の変化点を要するのは、G-6 L1017 の「ただし、1名の名簿では」の例外の範囲(本人の記名を受け付けること)を越えた非対称であり、例外の文言から導けない
5. **帰属(ADR-0106)は弱まらない**。同じ変化点の1件の記録は、山田本人の操作と山田以外の承認を要する(probe 確認3 の対照)。確認と任命の両方の記名が1件の帰属で裏づけられる
6. **3.13.3 の「行ごとに照らす」と組み合わせて書ける**(ADR-0110 が確定すれば)。変化点の各行の要件を照らす順序を「確認の行 → 確認に依存する行」と定めれば、行ごとの照合の枠組みのまま書ける

### 条件・留保

- **前後の順序を規定の文言に入れる**。「同じ変化点の確認を数える」だけを書くと、確認の記名の検査を後回しにする実装を排除できない。「確認の記名の要件を先に照らし、要件を満たした確認だけを数える」を必ず書く
- ADR-0110 は作業ツリーの起案で未確定である。本件の文言を 3.13.3 の「行ごとに照らす」に依存させるなら、ADR-0110 の確定を待つか、本件の文言を G-6 の側で完結させる。起案は G-6 の側で完結させた(上の1文)。3.13.3 の側には「行の要件の照合の順序」を書かない。理由: 3.13.3 は記名者の資格を扱い、確認の効力は G-6 が持つ規定であるため、置き場を分ける

- 監査の観点: 「先に確認の記録が履歴に載ってから任命するほうが監査で順序を追いやすい」(#319 擁護者の反対の見方)には、3.13.4 の1件の記録に確認の行と任命の行が並ぶことで答える。分けることで監査人が得る情報は確認できない(内部 §5.3)。この判断も未実証(監査人の読み取りを確かめていない)

## R-2 評価の時点を揃える範囲

### 推す案

**一般原則として標準に書き、検査ごとの当てはめは ADR の表で列挙する。** 原則は次の2文に分ける(起案。G-6 L1017 の R-1 の1文の直後に置く)。

> 変化点が名簿の人に与える確認(氏名の確認・アカウント名の確認)の効力は、その変化点の記録を足した後の構成で照らす。確認の記名の要件と、変化点の記名者の資格は、変化点の入力と変化点の前の名簿で照らす。

前段は R-1 の帰結を全検査へ及ぼす規定であり、後段は既にある規定(3.13.3 の「変更前の D-0 表1 の決定者」、任命権者の「この変化点より前に記載した人」)を確認として並べる文である。後段は新しい要求を課さない(ただし下の留保1)。

### 理由

1. **本件の欠陥は、検査ごとに照らす時点を決めていたことから生じた**。同じ変化点の確認の記名は入力で照らし、確認の効力は前の構成で照らす、という2つの検査の食い違いが原因である(内部 §2.2)。probe はさらに、`[上書き]`・`nameOverrides`・`qualificationAuthorityProblems`・`clampSeats` の4か所で同じ形の食い違いを見つけた。検査ごとに決める形を残すと、次に検査を足すときにも同じ食い違いが入る。原則を標準に置き、テンプレートの側は「記録を足した後の構成」を1回だけ作って全検査へ渡す形にすべきである(実装の形は起案の範囲外だが、ADR の決定に「1か所で作る」と書くことを推す)
2. **前段と後段の区分は、外部の先例の区分と一致する**。GitHub の CODEOWNERS と Kubernetes の RBAC は「判定の規則・操作者の権限」を変更前の状態で読み、IAM 製品は「付与の前提条件」を同じ申請の前の段の結果で読む(外部 §4.2)。本標準の記名者の資格(誰が決定できるか)は前者、氏名の確認(名簿の人を記名の欄に使えるか)は後者に当たる。既存の 3.13.3 も、任免の決定者を「変更前の」決定者で照らしており、後段はこれと同じ形である
3. **決定した者・確認の記名の検査を後の構成で照らしても、穴は開かない**。記名者自身の名義の確認を同じ変化点で記録すれば、それは本人の記名になり、2名以上では効かない(config.mjs L391〜407 の `self`、L416〜 の `invalid`)。probe の a2 と a3 は全場面で同一だった。原則を一律に掛けても結果が変わらない検査を、例外として列挙から外す理由は無い。例外を作るほうが、次の改修で食い違いを生む
4. **アカウント名の確認と書き方が揃う**。アカウント名の確認は既に、記録が足された後の構成で効力を照らしている(内部 §2.5)。前段に「氏名の確認・アカウント名の確認」と並べて書くことで、G-6 L1016 と L1017 の対称が文言の上でも保たれる

### 条件・留保

1. **後段は、確認の記名者の資格について、いまの実装より厳しい読みを含む可能性がある(未確認)**。いまの L5224 は確認の記名者を変化点の後の名簿で照らす(`nameProblems(config, …, { requireRoster: true })`)。このため、同じ変化点で名簿へ足した人が、別の人の氏名の確認を記名できる読みが残る。任命を含む変化点では記名者は変更前の決定者に限られるため問題にならないが、確認だけの変化点(probe R1 の (1) の形)では、同じ変化点で足した人の記名で確認が効くかを確かめていない。これは案(a)・(b) のどちらでも同じであり、本件の原因ではない。**後段の文言を「変化点の前の名簿」と書くかどうかは、probe で確認だけの変化点の挙動を確かめてから決める**。確かめるまでは後段を「変化点の記名者の資格は、第3章 3.13.3 による」とだけ書き、確認の記名者の名簿の時点を定めない形に退く。未実証

3. 原則の前段は、氏名とアカウント名の2種の確認に限る。ほかの記録(適合性確認の承認、規則の承認)を同じ変化点の中で数えるかは本件で決めない。それらは「確認」ではなく決定であり、既に個別の規定(3.4.2、第5章 5.5.7)を持つ。**本件の原則を広げないことを ADR に明記する**

## R-4 記録・開示・ADR

### 推す案

1. **記録と開示に、新しい欄・新しい開示の項目を足さない**。同じ変化点で確認して使ったことは、3.13.4 の1件の記録に確認の行(`nameConfirmations`)・記名者(`decidedBy`)・任命の行が並ぶことで読める。足すのは、確認の変化点の記録の `nameOverrides` と出力の `[上書き]` の行を正しく出すこと(R-2 の当てはめ)だけである。これは新しい開示ではなく、既存の記録の欠落の修正である
2. **「課さないと決めた」を標準の文言に置く**。G-6 L1017 の R-1・R-2 の文の後に、次の1文を足す(起案)。
   > 確認と、確認した氏名の使用(任命・記名)を、別の変化点に分けることを求めない。変化点を分けても、確認が効力を持った後に使ったことは保証されないためである。記録が効力を持つ時点は、判定記録を基底ブランチへ入れる操作による(前掲「判定記録を基底ブランチへ入れる操作」)。
   最後の文の参照先は、ADR-0106 決定3 の規定の置き場(G-6 の同じ節の「判定記録を基底ブランチへ入れる操作」。L1012 付近で前掲として引かれている)とする
3. **新しい ADR を起こす**(番号は ADR-0110 の次。ADR-0110 は #376 が使う)。題の案:「氏名の確認は記録した変化点から効く。確認の効力は記録を足した後の構成で、記名者の資格は変化点の前で照らす」。決定の構成:
   - 決定1: 同じ変化点の確認を、その変化点の任命・記名の判定に数える。確認の記名の要件を先に照らす(R-1)
   - 決定2: 確認の効力は記録を足した後の構成で照らす。記名者の資格は 3.13.3 による。テンプレートは「記録を足した後の構成」を1か所で作り、当てはめの表の全検査へ渡す(R-2)
   - 決定3: `clampSeats` の欠陥は G-6 L1017 の不履行として直す。期待値を変える決定ではない(R-3)
   - 決定4: 記録・開示の欄を足さない。分けることを求めない(本節の1・2)
   - 採らない案: 案(b)・(d)・(e)、R-2 の「検査ごとに決める」「a2 の範囲だけ」、R-3 の「別 Issue」「追認」「`undelivered`」、本節の「開示の欄を足す」。理由は各節の表のとおり
   - 回帰か決定か: 回帰と分類した理由(R-1 の3点)と、それでも ADR を要する理由(標準が前後を定めていなかったため、解釈を確定させる)
4. **EV を1件新設する**(番号は台帳の次の連番。再利用しない)。対象は R-1 の1文。案:
   > `:::caution[暫定 EV-NNNN / 見直し 2027-05]` 対象: 名簿へ足すのと同じ変化点で、本人以外が記名した氏名の確認を、その変化点の任命・記名に数える規定。根拠の水準: E1(間接)。差し替え条件: 採用組織で同じ変化点で確認して任命した件数と、そのうち後で氏名の確認の誤り(実在しない人・AI の担い手だった)が見つかった件数を、変化点を分けた場合と比べた結果。

### 理由

- 1(欄を足さない): 開示の項目は、読み手がそれを見て何かを判断するために置く。「同じ変化点で確認して使った」を見た監査人・出荷判定者が、何を止め、何を確かめるかを定められない。分けた場合と比べて誤りが多いという測定も無い。読み手の判断に結び付かない欄は、記入の負担と、読み飛ばされる表示を増やすだけで、信頼性を上げない。800-63A-4 が記録に求めるのも確認の状態と手順であり、同じセッションか否かではない(外部 §1.4)
- 2(分けないことを明記する): 本件の原因の一部は、標準が前後について沈黙していたことにある(内部 §1.1)。「書かれていない」を残すと、次の実装者が再び検査ごとに解釈を選ぶ。CLAUDE.md のコアポリシーのとおり、採らないと決めたことを読み手が区別できる形にする
- 2 の後半(効力の時点の参照): 「前の変化点で確認すれば安全」という誤った安心を標準が与えないためである。probe 確認3 は、分けても同じ PR の操作で帰属を得ることを示した

- 5(IMPL を delivered と主張しない): 本件の回帰は、テンプレートの側に試験が無かったために、本体の回帰スイートでしか見えなかった(内部 §2.6)。降ろした規定を固定する試験がテンプレートの側に無いまま `delivered` とすると、テンプレートの単独の改修で再び落ちうる
