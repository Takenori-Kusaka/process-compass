## R-1 同じ変化点での確認と使用

### 推す案

**案(a)(同じ変化点の確認を数える)を、下の条件 C1〜C4 つきで推す**。今の挙動(案(b) の事実上の固定)を守ることは推さない。分類は「回帰」とし、ADR では「標準が定めていなかった前後を、案(a) の形で確定する解釈の決定」として記録する。回帰の扱いだけで済ませて ADR を書かない形には反対する(標準が黙っている以上、どちらに倒しても解釈の決定であるため。内部 §5.1)。

### 理由(所在つき)

弁護の立場から今の実装を守る論拠として、次の4つを検討した。どれも成り立たなかった。

1. **意図の記録**: 「前の変化点で確認させる」という意図の記述は、標準(gate-criteria.md L1017)、D-0 表5、ADR-0079 決定7(L55〜57)、#296 の5名の意見書・裁定・突合・実装のどこにも無い(内部 §1.1・§3.1)。今の挙動を決定として守るには、守る対象の決定が存在しない。存在しない決定を後から作って期待値を「拒否」へ反転させるのは、#319 の擁護者が退けた禁止事項3 と同じ形である(319 council-05-defender.md L72)
2. **実装の内部の一貫性**: 今の実装自身が、同じ変化点の確認を前提に組まれている。`diffConfig` が `nameConfirmItems` を作り(generate-profile.mjs L1553〜1566 付近。内部 §2.2)、L5216〜5232 がこの変化点の `decidedBy` を本人以外かどうか検査し、L5452 が記録へ書く。数えないのは L5058 の `namingProblems(config)` だけである。前の変化点を要求する設計なら、L5216〜5232 で「同じ変化点で確認した人を、同じ変化点で使えない」と告げるはずだが、その文は無い。拒否の文(config.mjs の `aiNameBlocked` の案内。内部 §2.3)も「nameConfirmed: true を書く」と案内し、既に書いた利用者を行き止まりへ送る。**今の挙動は、自分の案内と矛盾する**
3. **今の実装が「前の変化点」の手順を最後まで持っていない**: 案(b) を事実上の規則とみなしても、その手順は2か所で破れている(probe 確認2・確認6)
   - 確認を記録する変化点そのものの `changeLog[].nameOverrides` が空で、`[上書き]` の行も出ない(L5345・L5454)。契約検査・構成書は上書きを表示するため、記録と表示が食い違う。案(b) では確認の変化点が必ず独立するので、この食い違いは常に現れる
   - 委任の席では、前の変化点で本人以外が確認した人を責任者にできない(`clampSeats` の `ctx`、L700。X-qual-3step の (3))。案(b) の手順は委任の席では成り立たない
   - 弁護すべき「今の実装」は、案(b) としても欠陥を持つ。守る対象として完結していない
4. **外部の先例**: 案(b) を支える最も強い先例は GitHub の CODEOWNERS(基底ブランチの構成で判定)と Kubernetes RBAC である(外部 §2.4・§2.5)。本標準にも同じ原理がある。ADR-0078 決定3 の「判定の材料を、判定される側が同じ変更で用意できない形にする」(ADR-0106 L19 が維持を明記)である。弁護の論拠として最も有望だったのはこれである。しかし本標準は、この原理の適用を ADR-0106 決定4(L19)で既に限定している。対象の PR の上で記名者本人のレビューにより帰属を裏づけた行は、同じ PR で足したものでも数える。理由は「記名者本人のアカウントの操作が伴うため、判定される側が自分だけで用意した材料に当たりません」である。本件の確認の記録も ADR-0106 決定3(L54〜56)の帰属を要し、記名者(山田)は確認される本人(Dupont)と別人である。本標準自身の先例に照らすと、同じ変化点の確認は「判定される側が自分だけで用意した材料」に当たらない。外部の規格(21 CFR 11.100(b)、800-63A-4、IA-12(1))も論理の前後だけを求め、別の取引に分けることを求めていない(外部 §5)

### 条件と留保(案(a) を受け入れる条件)

弁護の役目として、案(a) の弱点を挙げる。どれも満たされなければ、案(a) の実装に反対する。

- **C1 仮の記録と本物の記録を1つにする**: probe の試作は、L5058 の前で `withThis()` という仮の記録を組み、L5452 で別に本物の記録を組む(probe 「案(a) の試作」)。2つの組み立てが並ぶと、将来どちらかだけが改められたとき(例: `nameConfirmations` の絞り込みを本物の側にだけ足す)、判定に数えた確認と、記録に残る確認が食い違う。判定と記録の食い違いは、まさに今回の欠陥の型である。**この変化点の記録の確認の部分を1回だけ作り、判定と書き出しの両方で同じものを使う**ことを実装の条件にする。試作の形をそのまま採ることには反対する
- **C2 確認者の資格を、どの時点の名簿で照らすかを決める**: L5224 は確認の記名者を `nameProblems(config, change.decidedBy, { requireRoster: true })` で照らす。`config` は**変更を当てた後の名簿**である。したがって、同じ変化点で名簿へ足した人(例: 高橋)が、同じ変化点で別の人(Dupont)の氏名を確認できる形に見える。外部 §4.2 は、変更前の状態で判定する設計を「操作者(付与する者)の権限」に、同じ申請の前の段を数える設計を「付与される者の前提条件」に、と分けた。案(a) を推す側は、この区分で氏名の確認を後者に置く。そうであれば、**前者に当たる確認者の資格は変更前の名簿で照らすのが首尾一貫する**。任免の決定者は既に変更前の決定者で照らしている(generate-profile.mjs L2113〜2127・L2218「変更前の D-0 表1 の決定者」)。確認者だけが変更後の名簿で照らされている
  - この経路が実際に開くかは**未実証**(probe は試していない)。任命を伴う変化点では、記名者が変更前の決定者であることを要するため(L2185・L2215)、同じ変化点で足した人が記名して任命まで通すことはできない見込みである(コードの読み。未実証)。開くのは「同じ変化点で足した人が、任命を伴わない変化点で他人の氏名を確認する」形で、これは**案(a) によって新しく開くものではなく、今の実装でも次の変化点から効く**(`confirmedNames` は記録の時点の名簿を問わない。config.mjs L391〜)
  - 条件: 本件の ADR で、確認者の資格を変更前の名簿で照らすかを決める。照らす場合は、名簿が空からの初回の記入と1名の体制を例外にする(Kubernetes の bootstrapping と同じ形。外部 §2.5)。照らさない場合は、その理由と、照らさないと決めた旨を書く。決める前に probe で経路の有無を確かめる
- **C3 開け直さないことを場面で固定する**: 案(a) は、本人の記名・AI の名義の記名・名簿外の記名・記名なし・AI を示す語の名義どうしの確認を、今と同じ理由と件数で拒否した(probe 確認4)。これは試作での観測であり、テンプレートの試験に同じ変化点の経路の試験は無い(内部 §2.6)。**probe の場面(S-self・S-ai・S-nonroster・S-nosign・S-mutual・S-mutual2・S-mutual4・X-decider・R1b)を回帰スイートか `test-roster-rules.mjs` へ移して固定する**ことを条件にする。固定しないまま拒否を外すと、将来の改めで自己確認の経路が開いても気づけない
- **C4 拒否の文を直す**: 案(a) で根の場面は拒否されなくなるが、確認の記録が無い・無効な場合の拒否の文は残る。その文が「nameConfirmed: true を書く」だけを案内し、本人以外の記名が要ることを告げない形(内部 §2.3)は、既に旗を書いた利用者を行き止まりへ送る。記名の要件(本人以外の名簿の人の `decidedBy`)まで案内する形へ改める

留保:

- 「確認と任命を1つの記名にまとめると、記名する人が確認を任命のついでに扱い、確認の重みが下がる」という懸念は、弁護の側に残る唯一の実質の論拠である。ただし**未実証**であり、変化点を分けても記名者は同じ山田で、手順が1回増えるだけである。乾式の実行(`--dry-run`)は「人の名簿: Claude Dupont の氏名を実在の人の氏名として確認した(名義の機械検査の上書き)」の行を別に出す(probe 確認8)。この表示を保つことで懸念に応える。表示を消す改めは受け入れない

## R-2 評価の時点を揃える範囲

### 推す案

**「この変化点の記録を足した後の構成」で一律に照らす一般原則(案(f) の一般化)には反対する**。代わりに、ADR へ**検査を2つの類に分ける原則**を書き、その原則に基づく検査ごとの割り当てを表で列挙する形を推す。

- 類A(記名される者の前提の事実): その氏名の人を名簿に置き、席の責任者として載せてよいか。**この変化点の確認の記録を数える**
- 類B(記名する者・承認する者の資格): この変化点で記名・承認・実施する者が、その行為をしてよい者か。**この変化点の確認の記録を数えない**。同じ変化点で確認した氏名の人を、同じ変化点の記名者・承認者・実施者にすることは受け付けない

検査ごとの割り当て:

| 検査(`72a98bd` の行) | 類 | 照らす構成 | 今の実装との差 |
| --- | --- | --- | --- |
| `namingProblems`(L5058。名簿と席の責任者) | A | この変化点の記録を足した後 | 改める(根の場面) |
| `namingProblems` のうち適合性確認の承認者の欄 | B | 足す前 | 改めない。`namingProblems` が A と B を1つの関数で混ぜて返すため、分けて呼ぶ必要がある(下の C5) |
| `[上書き]` の出力(L5345)と記録の `nameOverrides`(L5454) | 表示と記録 | 足した後 | 改める。**案(a)・(b) のどちらを採っても改める**。確認の変化点の記録が、その変化点の構成から導く表示と食い違うのは、どちらの案でも欠陥である(probe 確認2) |
| 決定した者の記名(L5069) | B | 足す前 | 改めない。試作 a3 は足した後で照らしたが、結果は a2 と全場面で同じだった(probe 確認6)。差が出ないのは、今の `confirmedNames` が本人の記名を2名以上で効かせないからにすぎない。将来その規則が改まったとき、変化点が自分の記名者の資格を自分の記録で作る形が開く。**差が出ないことを、類B を足した後で照らす理由にしない** |

| 適合性確認の実施者・承認者(L5071〜5076 `qualificationAuthorityProblems(config, …)`) | B | 足す前 | 改めない。X-qual-accountable の2件目の拒否(probe 確認6)は、この原則による**意図した拒否**として残す。今は意図の記述が無いまま残っているので、ADR に「採らない」と書く |
| 任免・緩める向きの決定者(L2113〜2127・L2185・L2215) | B | 変更前の決定者 | 改めない。既に変更前の構成で照らしている |
| `clampSeats`(L700〜722) | 責任者は B、承認者・実施者も B | 足す前(前の変化点までの記録を持つ構成) | R-3 |

### 理由(所在つき)

- **一律に「足した後」で照らすと、本標準が意図して変更前で照らしている検査を壊す**。任免の決定者は「変更前の D-0 表1 の決定者」で照らす(generate-profile.mjs L2218・L5312)。roles-responsibilities.md L1994 は「新任の決定者が、自分の任命を自分の記名で確定してはならない」と定める。この変化点の記録・構成を、記名者の資格の判定に数える原則を一般に立てると、L1994 の禁止と同じ型の自己の権限づけ(変化点が自分の記名者の資格を自分で作る)を許す原則になる。案(f) を一般原則として書けば、その原則が将来の検査にも及ぶ。信頼性の軸では、検査を書く人がこの区別を毎回思い出せる形にする必要がある
- **区分の根拠は外部の調査そのもの**: 外部 §4.2 は、変更前で判定する設計を「判定の規則・操作者の権限」に、同じ申請の前の段を数える設計を「付与される者の前提条件」に分けた。案(a) を推す論拠はこの区分の後者である。前者まで足した後で照らすなら、案(a) の論拠を自分で崩す
- **ADR-0078 決定3 の原理との整合**: 「判定の材料を、判定される側が同じ変更で用意できない形にする」(ADR-0106 L19 が維持)。類A の確認は、記名者本人の操作の帰属(ADR-0106 決定3)を伴い、記名者と確認される本人が別人なので、決定4 と同じ理由で原理に反しない。類B を足した後で照らすと、記名者(判定される側)の資格を同じ変更の記録で作ることになり、原理に正面から反する
- **検査ごとの列挙だけでも不足する**: 列挙だけにすると、新しい検査を足すときに、どちらで照らすかの基準が無い。原則(類A・類B)と列挙(表)の両方を ADR に置く

## R-3 委任の席(`clampSeats`)の回帰の候補

### 推す案

**本件で直す。回帰と認める**。弁護の立場から見ても、これは今の実装を守れない点である。今の実装の事実上の規則(前の変化点で確認してから使う)が約束する経路を、今の実装自身が塞いでいるためである。

### 理由(所在つき)

- `clampSeats`(generate-profile.mjs L697)は `const ctx = { seats, people, delegation, governance }`(L700)で `nameProblems` を呼ぶ(L714〜722)。`ctx` は `changeLog` を持たないため、`confirmedNames`(config.mjs L391〜)は常に空を返し、2名以上の名簿では AI を示す語を含む氏名の確認がすべて `invalid` になる。前の変化点で本人以外(山田)が確認した Dupont を責任者とする席を、委任にできない(probe 確認6 の X-qual-3step の (3))。p302 は受け付けた。構図は根の場面と同じで、付記が `aiNameBlocked` を記録で判定するよう改めた(内部 §2.4)とき、記録を持たない評価の位置が取り残された
- 弁護の論点として「委任は緩める向きの決定であり(ADR-0055 決定3 の理由。roles-responsibilities.md L1991)、AI を示す語を含む氏名の人を委任の席の責任者にすることへ厳しく倒すのは安全側だ」と主張できるかを検討した。採らない。理由は3つある
  1. 標準にその区別は無い。G-6(gate-criteria.md L1017)は、本人以外の記名による確認が効けば記名を受け付けるとだけ定め、委任の席を除外していない
  2. 拒否の文(probe 確認6 の全文)は「nameConfirmed: true を書く」を案内するが、既に書いて記録もある利用者には取りうる手段が無い。手段の無い拒否は、人の判断を記録に残す道を塞ぐだけで、安全側に倒したことにならない
  3. 同じ席を委任でなく協働で持つことは受け付けている。氏名への疑いが根拠なら、協働でも疑うはずである。拒否の根拠が氏名の確かさではなく `ctx` の欠落であることを示している
- 回帰の試験は AI を示す語を含む氏名の人を委任の席の責任者にする場面を持たない(probe 確認6 の推測。scenarios.mjs の「F.」は技術判断者の任命だけ)。#319 の移行でも本件の会議体でも、試作が無ければ見つからなかった。**放置すれば、同じ型の欠陥が試験の外に残っていることを知りながら出す**ことになる

### 範囲(弁護の側からの追加の指摘)

`clampSeats` の `ctx` は、責任者の欄のほかに次の検査へも渡る。どれも `changeLog` を持たない構成で名義を照らす。

| 箇所(`72a98bd`) | 照らす名義 |
| --- | --- |
| L709 `ruleStanding(ctx, r)` → L681 `ruleDeciderProblems(ctx, rule)` → config.mjs L1292 `nameProblems(config, rule.decidedBy, …)` | 委任の規則を決定した者 |
| L709 → L685 `ruleApprovalProblems(ctx, rule)` → config.mjs L1378 `nameProblems(config, rule.approvedBy, …)` | 規則を承認した AI維持管理者 |
| L719〜720 | 適合性確認の実施者 |
| L721〜722 | 適合性確認の承認者 |

AI を示す語を含む氏名の人が AI維持管理者の席の責任者である場合、その人が承認した委任の規則がすべて無効になる見込みである(コードの読み。**未実証**)。`ruleDeciderProblems` も config.mjs L1292 で `nameProblems(config, rule.decidedBy, …)` を呼ぶため、規則を決定した者についても同じことが起きる見込みである(コードの読み。**未実証**)。条件:

- **C6** `clampSeats` を直すとき、責任者の欄だけでなく、`ctx` を通る名義の検査すべてを対象にする。probe で、AI維持管理者・規則の決定者・適合性確認の実施者を AI を示す語を含む氏名(前の変化点で確認済み)にした場面を流し、今の版で拒否されること、修正の後に受け付けることを確かめる
- **C7** `ctx` に渡す記録は「この変化点の記録を足す前の、前の変化点までの記録」とする。`clampSeats` の検査はどれも R-2 の類B(席の責任者が委任を宣言する、規則を決定・承認する、適合性確認を実施・承認する)に当たるためである。この変化点の記録まで渡すと、同じ変化点で確認した人を同じ変化点で委任の席の責任者・承認者にでき、R-2 の L5071〜5076 の拒否と食い違う
- **C8** `buildConfig`(L746)は `clampSeats` を構成の組み立ての中で呼ぶ(L800)。記録を渡すために組み立ての入力を改める。改めたら、`buildConfig` を直接呼ぶテンプレートの試験(test-roster-rules.mjs L59 ほか)で、記録を渡さない呼び出しが今の挙動のまま残ることを確かめる。記録を渡し忘れた呼び出しが黙って `invalid` へ倒れる形は、今回の欠陥と同じ型なので、渡さない場合は名義の検査の側で「記録を持たない構成」を区別できる形が望ましい(実装の方法は起案の委員に委ねる)

## R-4 記録・開示・ADR

### 推す案

1. **記録**: 新しい欄は足さない(案(c) は採らない)。同じ変化点で確認して使った旨は、1件の `changeLog` の要素に `nameConfirmations` と任免の差分が並ぶことから導ける(内部 §5.4)。ただし、導けることを**機械が使える形で固定する**: 記録の `nameOverrides`(L5454)をこの変化点の確認まで数える形へ直し(R-2)、その値が「その時点の記録」として契約検査に読まれる(verify-gate-contract.mjs L636。probe 確認7 の補足)ことを試験で固定する
2. **開示**: 保証の開示には、確認の記名者の区別(本人以外・自己申告・未記録。`nameOverrideDetails` の `how`)を今のまま出す。「同じ変化点か」の区別は出さない。区別して読者が判断を変える場面が見当たらないためである
3. **帰属(ADR-0106)の前後の開示**: ADR に次を明記する。「変化点の中の前後(確認の記名の検査 → 確認を数える → 任命の検査)は機械が保証する。確認と任命の帰属は同じ PR で裏づけられ、確認が効力を持った後に任命が効力を持つという時間の前後は保証しない。変化点を分けても、同じ PR に入れれば同じである(probe 確認3)。時間の前後を求める規定は、標準にも外部の規格にも見当たらないため課さない」。**採らないと決めた旨として書く**
4. **ADR**: 新しい ADR を1つ起こす。ADR-0079 決定7 は書き換えず、「評価の時点を定めていなかった点を補う」と関係の表に書く。決定に含めるもの:
   - R-1 案(a) と条件 C1〜C4
   - R-2 の類A・類B の原則と検査ごとの表(C5)
   - R-3 の `clampSeats` の修正と範囲(C6〜C8)
   - 採らない案: (b)・(c)・(d)・(e)・(f)、a1・a3、時間の前後の保証、委任の席の意図した拒否。それぞれ理由を書く
5. **EV**: 「確認と任命を1つの記名にまとめても、確認の重みは下がらない」は**未実証**である(R-1 の留保)。`:::caution[暫定 EV-NNNN / 見直し YYYY-MM]` を付ける。見直しの材料は、同じ変化点で確認した記録の件数と、後に氏名の確認が誤りと分かった件数(採れる案件があれば)。番号は `npm run evidence:write` の前に台帳で次の番号を確かめて振る
6. **IMPL**: G-6(gate-criteria.md L1017)の氏名の確認の注記(IMPL-0266、L1070)に、評価の時点(類A・類B)を足すか、新しい IMPL を起こす。`clampSeats` の修正が本件で入らないなら `state=undelivered` で表示し続ける
7. **回帰スイートの印(#375、見直し 2026-12)の外し方**:
   - 根(scenarios.mjs L400)の `knownFailure` と連鎖の2場面(L402・L403)の `dependsOn` を外す。期待値は改めないので `changed` は要らないが、`fixes` に本件の ADR の決定を足す(ADR-0089 決定3 の趣旨。Issue だけの引用で外さない)
   - 外すのは C1・C3・C5 を満たした実装が入った同じ変更の中だけにする。印だけを先に外す、実装だけを先に入れて印を「予期せず通った」まま置く、のどちらも採らない(probe 確認5 のとおり、実装が入ると印は「予期せず通った」で落ちる)
   - 足す場面: C3 の拒否の場面一式、O-2(1名から2人目を迎える)、X-qual-accountable(類B の意図した拒否)、X-qual-3step(前の変化点で確認した人を委任の席へ。R-3 の後は受け付け)、R1 の (1) の記録の `nameOverrides`(R-2 の記録と表示の一致)、C2 で決めた確認者の資格の場面

### 理由(所在つき)

- 案(c) の新しい欄を落とすのは、弁護の側にとって譲歩ではない。弁護の論拠として最後に残る「分けたほうが監査で順序を追いやすい」(319 council-05-defender.md L71)を検討したが、1件の記録の中に確認と任命が並び、記名者と日付も1つなので、順序は記録から読める(内部 §5.3「記録の確かさ」、外部 §5 の監査の観点)。読む者の決まらない欄は、記録と表示の食い違いの種を増やすだけである
- 帰属の前後を開示するのは、案(a) を推す側が「確認 → 使用の前後を守る」と書いたとき、読み手が時間の前後(先に効力を持つ)まで保証されると誤読しうるためである。21 CFR 11.100(b) の "Before" は論理の前後と読むのが文言に沿う、という外部 §1.1 の読みは**解釈**であり、FDA の前文(62 FR 13430)は取得できていない(外部 §6 の穴1)。この読みに頼る記述には根拠水準の開示が要る。規制業(CL・規制業の案件)で同じ変化点の確認を受け付けるかは、穴1 を埋めるまで暫定として扱う(EV で示す)

### 留保

- 弁護の委員として、今の実装を「意図した決定」として守る論拠は見つけられなかった。会議体がそれでも案(b) を採るなら、少なくとも R-1 の理由3 の2件(確認の変化点の `nameOverrides`、委任の席)を直し、拒否の文を「前の変化点で確認を記録してから任命する」と案内する形へ改め、1名の名簿の扱いとの非対称を ADR に書く必要がある。どれかが欠ければ、案(b) は手順を持たない規則になる
