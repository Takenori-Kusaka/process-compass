## 1. 標準の規定

### 1.1 氏名の確認(`nameConfirmed`)を定める箇所

AI を示す語(モデル名・提供者名など)を含む実在の氏名の扱いは、第3章ではなく**第4章 G-6** と**第6章 テンプレ0(D-0 表5)**に置かれている。

| 所在 | 内容 |
| --- | --- |
| `src/content/docs/phase4-process-design/gate-criteria.md` L1017(G-6 独立レビュー、L974 からの節) | 表5 の人の氏名が AI を示す語を含む場合は、人が実在を確かめたうえで、**名簿の変更として**確認の旨(`nameConfirmed`)を記録する。確認は**その本人以外の人が記名した場合に限り**効く。本人の記名・AI の名義の記名・記録の無い確認では効かない。ただし体制の内の人が1名の名簿では本人の記名を受け付け、自己申告の氏名として区別して出す。記録の無い確認も1名の名簿では効かせたまま未記録として出す。AI の担い手の判断で確認の旨を書いてはならない |
| 同 L1016 | アカウント名の確認(`accountsConfirmed`)。アカウントの本人以外が記名した名簿の変更に限る |
| 同 L1070(IMPL-0266 の注記) | 氏名の確認は、`changeLog` の `nameConfirmations` と `decidedBy` がある場合だけ効き、記録の無い確認は契約検査が落とす。`test-roster-rules.mjs` が固定する |
| `deliverable-templates.md` L153・L422(D-0 表5 の欄「氏名の確認」) | 確認した者(本人以外)と日付。1名の名簿では自己申告と明記する |
| `phase5-implementation/template-repository.md` L632 | 「記名を受け付けられない」の説明。実在の氏名は人が確認した旨を名簿へ書いて通し、表示する |

**いずれの箇所も、確認と、確認した氏名の使用(任命・記名)の時間的な前後を定めていない**。「同じ変化点で確認し、同じ変化点でその人を席の責任者にする」場合の定めは無い。課さないと決めた旨の記載も無い(「書かれていない」状態)。

### 2.2 `/process-change` の評価の順序(`template/scripts/init/generate-profile.mjs`)

| 行 | 処理 | 照らす構成 |
| --- | --- | --- |

**原因の確認**: Issue の記載どおり、L5058 の `namingProblems(config)` は、L5429 で足す記録(`nameConfirmations`・`decidedBy`)を見ない。場面の入力では、名簿の内の人が4名(山田・佐藤・鈴木・Dupont。任命権者は `external`)となるため、Dupont の確認は `invalid` と判定され、`aiNameBlocked` が「モデル名または提供者名を含む」を返す。L1360 の席の責任者の検査がそれを「技術判断者(Tech Lead) の責任者: "Claude Dupont" は …」として拒否する。

**本人以外の記名かを照らす時点**: 2つの検査が別々の時点で照らしている。

1. 確認の記名の正しさ(本人以外か、名簿の人か、AI の名義でないか)は、L5216〜5232 が**この変化点の入力(`change.decidedBy`)**で照らす。同じ変化点の記名を検査している
2. 確認が効いているか(`aiNameBlocked`)は、L5058 が**変更前までの記録**で照らす。同じ変化点の記名を数えない

1 は同じ変化点の確認を前提に組まれており(`nameConfirmItems` を作り、記名を検査し、記録へ書く)、2 だけがそれを数えない。設計の意図として前の変化点を要求するなら、1 で「同じ変化点で確認した人を同じ変化点で使えない」旨を出すはずだが、そうした文も試験も無い。

### 2.3 拒否の文が案内する手順

拒否の文(config.mjs L514〜517)は「同じ語を含む実在の氏名の場合は、人が確認したうえで、名簿の該当者へ nameConfirmed: true を書く」と案内する。場面の入力は既に `nameConfirmed: true` を書いている。どちらの案を採っても、**この案内は場面の状況に合っていない**(案(b) なら「前の変化点で確認を記録してから任命する」、案(a) なら拒否が出ない)。

- 印の働き(`scripts/regress/suite/lib.mjs` L112〜L192): 根は、拒否の理由の集合が `match` の1件とちょうど一致して落ちたときだけ通る。予期せず通ると失敗。`review` の月を過ぎると `run.mjs` L304 が失敗にする。連鎖の2場面は、根が落ちている間は「根に従属して落ちる」として通り、根が落ちているのに通ると失敗する
- 期待値を改めるときの形式: ADR-0089 決定3。改める根拠の決定(ADR の決定・K 番号・標準の条項)を `changed: [{ by, on, from }]` に引く。Issue だけの引用は認めない。`scripts/regress/check-fixes.mjs` が形と実在を検査する

## 5. 案ごとの整合

### 5.1 判断の前提

- 標準(G-6 L1017、D-0 表5)は「本人以外の記名」だけを定め、確認と使用の前後を定めていない(1.1)。どちらの案も、標準の文言と矛盾しない。したがって、**どちらを採るかは標準の解釈を確定させる決定であり、ADR に記録する**(受け入れ条件の候補の1つめ)
- いまのテンプレートの挙動から見ると、案(a) は**いま拒否している入力を受け付ける**向きの変更であり、案(b) はいまの挙動を決定として固定する。#319 の擁護者が述べたとおり(council-05-defender.md L71)、AI が期待値を「拒否」へ反転させること、AI が拒否を外すことのどちらも、決定の引用なしには行えない(ADR-0089 決定3。決定を引かない期待値の改めは第5章 5.8.5(human-ai-boundary.md L1024)の禁止事項3 に当たるとする)。**向きを AI が決めない**
- 3.13.3 の「緩める向き」は統制の設定の変更の分類であり、テンプレートの検査の誤りの修正を直接に分類するものではない。ただし案(a) は機械の検査が拒否する範囲を狭めるため、人の決定を要する扱いにするのが安全側である

### 5.2 案(a) 同じ変化点の確認を数える(評価の順序を直す)

**形**: L5058 の `namingProblems` を、この変化点で足す確認の記録を仮に載せた構成(`{ ...config, changeLog: [...config.changeLog, { decidedBy: change.decidedBy, nameConfirmations: nameConfirmItems の id }] }`)で照らす。L5216〜5232 の記名の検査は、そのまま残す。

**自己確認の経路が開かないか**(確認者が任命される本人でないことをどう照らすか):

| 経路 | 仮の記録で照らしたときの結果 | 理由 |
| --- | --- | --- |
| Dupont が自分で確認し、自分を任命する(体制の内が2名以上) | 拒否のまま | `confirmedNames` が `self` と判定し(L391〜407)、2名以上では `invalid`(L416〜)。加えて L5228 が本人の記名を拒否する。二重に塞がる |
| AI の名義の者が記名する | 拒否のまま | `confirmedNames` は本人以外の記名で、記名者の名義が AI を示す語を含めば数えない。L5224 の `nameProblems` も拒否する |
| AI を示す語を含む2名(例: Claude Dupont と Gemini Sato)を同時に足し、一方が他方を確認する | 拒否のまま | 記名者の名義が語を含むため、本人以外の記名として数えない(config.mjs L400 の `aiNameReason(e.decidedBy)`)。記名者自身の確認は `self` で、2名以上では効かない |
| 名簿に無い者が記名する | 拒否のまま | `confirmedNames` は記名者が名簿に無ければ数えない。L5224 も拒否する |
| 体制の内が1名(本人だけ) | **変わらない** | いまも `unrecorded`・`self` が効くため、同じ変化点で確認して任命できる。案(a) が変えるのは2名以上の名簿だけ |

確認者が本人でないことは、仮の記録の `decidedBy` と確認される人の `id` の比較(`confirmedNames` の `self`)と、L5228 の比較の2か所で照らされる。いずれも名簿の `id` で比べる(`findPerson`・`personKey`)。仮の記録に載せる `decidedBy` は、この変化点の入力そのものであり、別の値を差し込む欄は無い。**案(a) によって新しく開く自己確認の経路は、コードを読んだ範囲では見つからない**(実行での確認は 6 節)。

**ADR-0106(効力を持つ記録の帰属)**: 名簿の変更と任免を含む1件の記録は、`decisionNeedsAttribution` が真になり、山田の本人のアカウントの操作による帰属を要する。1件の帰属で、確認と任命の両方の記名が裏づけられる。案(b) と比べて帰属の弱まりは無い。

**ADR-0107(名義)**: 担い手が山田と名義を共有する構成では、山田の操作だけでは帰属に数えない。これは確認と任命のどちらにも同じく掛かり、案(a)・(b) で差が無い。

**整合の利点**: アカウント名の確認(2.5)と同じく、記名を検査した確認を、その変化点の判定に数える形になる。1名の名簿と2名以上の名簿で、同じ変化点の扱いが揃う(いまは1名だけ通る)。

**範囲の論点**: 仮の記録で照らすのを `namingProblems`(席の責任者・適合性確認の承認者)に限るか、L5068 の `change.decidedBy` の検査にも及ぼすか。`decidedBy` に同じ変化点で確認される本人を書く形は、2名以上では本人の記名として L5228 が拒否し、1名ではいまも通る。どちらに置いても結果は変わらない見込みだが、どの検査を仮の記録で照らすかを決定の中で明示する必要がある。

**回帰の試験**: 根の印を外し、連鎖の2場面の `dependsOn` を外す。期待値は p302 と同じ(反映)のため `changed` は要らない。自己確認・AI の名義の記名・相互の確認が同じ変化点でも拒否される場面を足すと、案(a) が開かないと主張する経路を固定できる。

### 5.3 案(b) 前の変化点での確認を要求する(決定として記録する)

**形**: 同じ変化点で確認した氏名を、その変化点の記名(席の責任者・適合性確認の承認者・決定した者)に使えないと定める。

**利点として挙げられているもの**: 確認の記録が履歴に先に載り、監査で順序を追いやすい(council-05-defender.md L70 の反対の見方)。

**整合の論点**:

| 観点 | 評価 |
| --- | --- |
| 独立性 | 増えない。2回とも記名するのは同じ決定者(場面では山田)でよい。確認と任命に別の記名者を求める規定は、標準にもテンプレートにも無い |
| 帰属(ADR-0106) | 確認の記録の帰属は PR の時点で確かめられる(`/process-change` の時点ではない)。2つの変化点を同じ PR に入れれば、任命の時点で確認の記録はまだ帰属を裏づけられていない。**「前の変化点」は記録の順序を作るだけで、確認が効力を持った後に使うことを保証しない**。保証を求めるなら「前の変化点の記録が基底ブランチへ入った後」と定める必要があり、それは 3.13 の手続(最初のゲート判定より前に改める)と ADR-0106 の効力の時点に踏み込む別の決定になる |
| 記録の確かさ | 1つの記録に、確認(`nameConfirmations`)・記名者・任命の差分が同じ日付で並ぶ。順序は1つの記録の中でも読める。分けることで失われる情報も、得られる情報も、確認できない |
| 一貫性 | アカウント名の確認とも、1名の名簿の扱いとも、非対称のまま残る。1名の名簿でも前の変化点を求めるかを、あわせて決める必要がある |
| 手順の案内 | いまの拒否の文(config.mjs L514〜517)は前の変化点を案内しない。案(b) を採るなら、文と `accountable.md` の手順を改める必要がある |
| 回帰の試験 | 根の期待を「拒否」へ改め、`changed: [{ by: 'ADR-NNNN 決定N', on, from: '反映' }]` を残す(ADR-0089 決定3)。連鎖の2場面は、2つの変化点に分けた経路の場面へ付け替える。前の変化点で確認してから任命する経路が通ることを、新しい場面で固定する |

## 7. まとめ

- 拒否の原因は Issue の記載どおり、`generate-profile.mjs` L5058 の `namingProblems(config)` が、L5429 で足す確認の記録より前に評価されることにある。評価の位置は付記の前後で変わっておらず、付記が `aiNameBlocked` を記録で判定するよう改めたことで、初めて結果を左右した
- 同じ変化点の記名の正しさ(本人以外か)は、L5216〜5232 がその変化点の入力で検査している。確認が効くかだけが、その記録を数えない。2つの検査の時点が食い違っている
- 標準(G-6 L1017・D-0 表5)と ADR-0079 は確認と使用の前後を定めていない。#296 の会議体がこの経路を議論した記録は無い。前の変化点を求める意図を示す記述も無い
- 案(a) は、コードを読んだ範囲では自己確認の経路を開かない。本人の記名は2か所で照らされる。案(b) は記録の順序を作るが、独立性も効力の前後の保証も作らない
- どちらを採っても、標準の解釈を確定させる決定として ADR に記録する。向きは AI が決めない
