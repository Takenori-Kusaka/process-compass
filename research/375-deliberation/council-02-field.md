## R-1 同じ変化点での確認と使用

### 推す案

**案(a) 数える**。本件を**回帰**として扱い、同時に「確認と使用の前後は、論理の前後(確認の記名の検査 → 確認を数える → 任命・記名の検査)で足り、別の変化点を要さない」ことを**決定として ADR に記録する**。回帰か決定かの二者択一ではなく、「回帰であった」ことと「前後の解釈を確定する」ことの両方を書く。

### 理由(所在つき)

1. **現場では、正しい入力が誰にも直せない理由で拒否されている**
   - 拒否の文(template `scripts/gate/config.mjs` L514〜517)は「名簿の該当者へ nameConfirmed: true を書く」と案内する。場面の入力はそれを既に書いている(内部 §2.3、probe 確認1 の全文)。利用者は案内どおりにしたのに同じ拒否を受け、文からは「変化点を2つに分ければ通る」ことに辿り着けない。拒否の文が実際の通し方を示さない検査は、手順として信頼できない
   - 同じ変化点の記名の正しさ(本人以外か)は L5216〜5232 がこの変化点の入力で照らし、確認が効くかだけを L5058 が記録の前の構成で照らしている(内部 §2.2)。テンプレート自身が「同じ変化点で確認する」前提で `nameConfirmItems` を作り、記名を求め、記録へ書く。前提を組んだ側が、最後に自分の記録を数えない形であり、設計の意図というより評価の位置の取り残しと読める
2. **1〜2名の体制が、2人目を迎える変化点で詰む**
   - probe O-2: 1名の名簿 [山田] から、AI を示す語を含む氏名(例: Claude は実在の名前として珍しくない)の2人目を足して任命する変化点が拒否される。p302 と試作は受け付けた。1名のときは同じ変化点で通るのに、2名になる瞬間だけ通らない。採用組織の側から見ると、規則が人数の境界で説明なく変わる
   - 案(a) は、1名の名簿と2名以上の名簿で「同じ変化点の確認を数える」扱いを揃える(内部 §5.2 整合の利点)
3. **自己確認の経路は開かない(実行で確認済み)**
   - probe 確認4: 本人の記名・AI の名義の記名・名簿に無い記名・記名なし・AI を示す語の名義どうしの相互の確認は、試作 a1〜a3 でもいまと同じ理由・同じ件数で拒否された。本人の記名は 3 か所で塞がる(L5069・L5224・L5229)
   - #296 の付記で塞いだ X-decider と記名なしの確認(R1b)は、試作でも閉じたまま(probe「p302 の版での同じ場面」)
4. **外部の規格・実務は論理の前後を求め、取引の分割を求めない**
   - 21 CFR 11.100(b) は "Before" だが別の取引を要する文言は無い。NIST SP 800-63A-4 は1セッションで確認から加入までを基本形とする。IA-12(1) は承認を登録の手続の中に含める。Entra・Okta は1申請の直列の段で、禁じるのは自己承認(外部 §1.1・1.3・1.4・2.2・2.3・§5)
5. **案(b) は手数を倍にするのに、信頼性を足さない**
   - 2回とも記名するのは同じ山田でよく、独立性は増えない(内部 §5.3、外部 §4.1、#319 の擁護者 council-05-defender.md L70〜71)
   - 2つの変化点を同じ PR に入れれば、帰属の検査(`decisionRecordFindings`)は2件を同じ PR の作成者・承認者で照合する(probe 確認3)。「前の変化点で確認した」は効力の前後を保証しない。保証するには「確認の PR が基底へ入った後に任命の PR を出す」手順が要り、それは PR を2本、承認を2回に増やす。1〜2名の体制では承認者が1名しかいないことが多く、待ち時間がそのまま工程の停止になる。手数を倍にして得るものが「記録の順序」だけで、その順序は1件の記録の中でも読める(内部 §5.3 記録の確かさ)

| (f) 範囲を名義の検査すべてへ広げる | R-2 で扱う | 範囲の問いであり、R-1 の採否とは別 |

### 条件と留保

- **向きは人が決める**。案(a) は機械の検査が拒否する範囲を狭める向きであり、AI が期待値や拒否を外すことは決定の引用なしには行えない(ADR-0089 決定3、内部 §5.1)。本意見書は推す案を示すだけで、採否は会議体の裁定と人の決定による
- 「回帰」とする根拠は、(i) p302 で受け付けていた、(ii) 付記(#296、ADR-0079 決定7)の意図は自己確認を塞ぐことで、同じ変化点の確認を拒否する意図を示す記述が無い(内部 §3.1)、(iii) テンプレート自身が同じ変化点の確認を組んでいる(内部 §2.2)、の3つ。ただし標準(gate-criteria.md L1017)は前後を定めていないため、「書かれていない」状態を「課さないと決めた」状態へ移す決定は要る
- 留保(未実証): GitHub の CODEOWNERS 型の「統制の構成を変える変更は変更前の構成で判定する」原則(外部 §2.4・§4.2 反対の読み)を本標準が一般に採るべきかは、本件の範囲では決めない。本件の氏名の確認は「付与される者の前提条件」であって「判定の規則」ではない、という区分(外部 §4.2)で案(a) を支える。この区分が他の変化点でも保てるかは確かめていない
- 留保: 監査の追跡が案(b) で良くなる、という主張(council-05-defender.md L70 の反対の見方)を支える事例・規定は見当たらない(外部 §5 監査の観点)。逆に案(a) で監査の追跡が損なわれる事例も無い。どちらも未実証であり、R-4 の開示で補う

## R-2 評価の時点を揃える範囲

### 推す案

**一般原則として書き、適用する検査を名指しで列挙する**(原則だけ、または検査ごとの個別の決定だけ、のどちらにもしない)。原則は次の区分による。

- **付与される者の前提条件**(その名義を記名の欄に使えるか。氏名の確認が効いているか)は、**この変化点の記録を足した後の構成**で照らす
- **操作者の資格**(誰がこの変化点を決定できるか。任免の決定者か、本人の記名か)は、**変化点の入力と変化点の前の構成**で照らす。いまのとおり

列挙する範囲は probe の a3 に、適合性確認の承認者を加えたもの。

| 検査(template HEAD の行) | 照らす構成 | 理由 |
| --- | --- | --- |
| `namingProblems`(generate-profile.mjs L5058) | 後 | 根の場面。R-1 |
| `[上書き]` の出力(L5345)と記録の `nameOverrides`(L5454) | 後 | 確認の変化点の記録が自分の確認を数えず、構成から導く表示と食い違う(probe 確認2・4)。案(a)・(b) のどちらでも現れる食い違いで、直さないと契約検査が過去の記録の記名を照らすとき(verify-gate-contract.mjs L636)に記録と表示の二重の正本が残る |
| 決定した者の記名の `nameProblems`(L5069)と、氏名の確認の記名の `nameProblems`(L5224) | 後 | a2 と a3 で結果の差は 0(probe 確認6)。差が無いから外すのではなく、名義の検査の時点を1つに揃えるために含める。差が出ないことは試験で固定する |
| この変化点で出された適合性確認の承認者(L5071〜5076 の `qualificationAuthorityProblems(config, …)`) | 後 | X-qual-accountable で、a1〜a3 にも「適合性確認の記録(承認者の名義)」の拒否が残る(probe 確認6)。名義の確認が効くかは前提条件であり、承認の資格(当該の席の責任者か)の検査とは別。資格の検査は変えない |
| 本人の記名の拒否(L5229)、任免の決定者の検査、L1994 の自己任命の禁止 | **前**(変えない) | 操作者の資格。後の構成で照らすと、変化点が自分の決定の資格を自分で作る形になる(外部 §2.4 CODEOWNERS・§2.5 RBAC の先例が防ぐ形) |

### 理由(所在つき)

1. **本件の原因は、検査ごとに時点を各自で選んでいたこと**。L5216〜5232 は入力、L5058 は記録の前、契約検査は記録の後(内部 §2.2・probe 確認7)。個別に1か所ずつ直すと、次に足す検査がまた別の時点を選ぶ。a1 だけでは足りず a2 まで要ったこと(probe 確認4 の表)、`clampSeats` という4つめの時点が見つかったこと(probe 確認6)が、その実例である
2. **採用組織にとって、検査の時点は見えない**。利用者が見るのは拒否の文だけで、どの検査がどの時点で照らしたかは分からない。時点がばらばらだと、同じ名義が出力では上書きされず、構成書では上書きされる、という食い違いが利用者の目に出る(probe 確認2 の (1) の行: 記録の `nameOverrides` は空、契約検査は上書きを表示)。どちらを信じればよいか、利用者には判断できない
3. **原則と列挙の両方を書く理由**: 原則だけでは、実装者が「この検査は前提条件か資格か」を判断する余地が残り、本件と同じ取り残しが起きる。列挙だけでは、新しい検査を足すときの判断基準が無い。原則で判断の軸を与え、列挙で現在の範囲を確定し、試験で固定する
4. 実装の形としては、「この変化点の記録を足した後の構成」を1つの関数で作り(probe の `withThis()` に当たる)、前提条件の検査はすべてそれを通す形を勧める。L5429〜5452 で実際に足す記録と、仮の記録の値(`decidedBy` と `nameConfirmItems` の id)が別々に組み立てられると、両者がずれたときに再び食い違う。同じ値から両方を作るべきである(未実証: 試作は別々に組み立てており、ずれの試験はしていない)

### 他の案を落とす理由

- **検査ごとに個別に決め、原則を書かない**: 採らない。理由1。次の検査で同じ問題が再発する
- **a1(L5058 だけ)**: 採らない。回帰の試験の根の期待(出力の上書きの行)と連鎖の「changeLog に上書きした氏名が残る」を満たさず(probe 確認4・5)、確認の変化点の記録と表示の食い違いが残る
- **案(f) を全面に(操作者の資格の検査まで後の構成で照らす)**: 採らない。任免の決定者・本人の記名の検査を後の構成で照らすと、変化点が自分の資格を作る。いまは3か所で塞いでいる自己確認の経路(probe 確認4)の防御を、自ら弱める方向になる

### 条件と留保

- 拒否の文を、原因に合わせて分けることを条件に加える。2名以上の名簿で、`nameConfirmed: true` は書いてあるが本人以外の記名の確認が無い場合、いまの文(config.mjs L514〜517)は「nameConfirmed: true を書く」としか言わない。「本人以外の名簿の人が decidedBy に記名して確認を記録する(この変化点でもよい)」と言うべきである。1名から2名になった場合は「2人目が加わったので本人以外が記名し直す」(`nameConfirmationNotices` の文、config.mjs の同関数)を拒否の文にも出す。文言の分かりやすさは、案(a) の採否と独立に要る
- 留保(未実証): 列挙の外に、同じ時点の問題を持つ検査がまだあるかは、probe の 21 場面の範囲でしか確かめていない(アカウント名の確認を同じ変化点で行う場面は未試験。probe「試験していないこと」)。実装の際に、名義・確認を引く呼び出しをすべて洗い出し、表に載せる

## R-3 委任の席(`clampSeats`)の回帰の候補

### 推す案

**本件で直す。回帰として扱う**。`clampSeats`(generate-profile.mjs L697〜、呼び出し L800)の名義の検査に、名簿の変更の記録(`changeLog`)を持つ構成を渡し、R-2 の原則(前提条件は記録を足した後の構成)で照らす。別 Issue へ切り出して本件を閉じる形は採らない。

### 理由(所在つき)

1. **詰みであり、回避の手順が無い**
   - `const ctx = { seats, people, delegation, governance }`(L700)は `changeLog` を持たない。`confirmedNames` は常に空になり、2名以上の名簿では AI を示す語を含む氏名の確認は常に `invalid` になる(probe 確認6 の推測1)
   - その結果、X-qual-3step: 前の変化点で山田が正しく確認し、次の変化点で任命し、3つめの変化点で委任にしようとしても拒否される。変化点をいくつに分けても通らない。拒否の文は「協働までは宣言できます」(probe の全文)で、委任へ進む手段を示さない
   - 採用組織の側から見ると、「Claude」「Gemini」等を含む実在の氏名の人は、2名以上の体制では**委任の席の責任者に永久になれない**。人の氏名で席の運用形態が決まることになり、本標準の運用形態の選択(第5章 5.5.6 の席の上限)とは無関係の理由で委任が封じられる
2. **根の場面と同じ構図の回帰**。p302 では受け付けた(probe 確認6 の表)。#296 の付記が `aiNameBlocked` を記録で判定するよう改めたため、記録を持たない評価の位置が初めて結果を左右した(probe 確認6 の推測1)。付記の意図(自己確認を塞ぐ)に、委任の席を封じる意図は含まれていない(内部 §3.1)
3. **R-1 の決定が、これを直さないと半分しか効かない**。案(a) を採っても `clampSeats` は残る(probe 確認6 の推測3)。同じ変化点で確認して任命までは通り、委任だけが通らない。利用者は「確認の記録が効いた」と表示(契約検査の `::warning::名義の機械検査を人が上書きした`、probe 確認7)を見た後に、同じ人の委任で「名義が AI」と拒否される。同じ構成の上で、同じ名義が効いているとも効いていないとも出る。これは R-2 の理由2 の食い違いのうち最も分かりにくいものである
4. **回帰の試験に現れていない**。scenarios.mjs の「F. 名義の機械検査の上書き」は技術判断者の任命だけで、委任の席を持たない(probe 確認6 の推測2)。別 Issue へ送ると、試験の無いまま本件が閉じ、利用者の側で初めて見つかる。本件で場面を足して固定すべきである

### 他の案を落とす理由

- **別 Issue へ切り出す**: 採らない。理由3・4。根と原因の構図が同じで、R-2 の原則の適用範囲そのものである。切り出すと、R-2 の列挙が委任の席を欠いたまま確定する
- **委任の席では氏名の確認を数えない、と決定する**(現状の追認): 採らない。根拠となる要求が標準にも ADR-0079 にも無い(内部 §1.1・§3.1)。委任の席の責任者を人の氏名で絞る理由は、AI の名義を責任者にしないこと(ADR-0054 決定10、ADR-0055)であり、それは本人以外の記名の確認で既に満たされる
- **案(b) で回避させる**: 成り立たない。前の変化点の確認も数えないため(理由1)

### 条件と留保

- 直した後に、次の場面を回帰の試験へ足すことを条件とする: (1) 前の変化点で本人以外が確認した人を、委任の席の責任者にして委任にできる、(2) 同じ変化点で確認・任命・委任・適合性確認(承認 その人)を行える(R-1・R-2 を採る場合)、(3) 本人の記名だけの確認・AI の名義の記名の確認では、2名以上の名簿で委任にできない(拒否のまま)、(4) 1名の名簿では現行どおり
- `clampSeats` の中の `ruleStanding(ctx, r)`(L708)も同じ `ctx` を使う。委任の規則の決定者・承認者の名義の検査が同じ問題を持つかは、確かめていない(未実証)。直す際に同じ範囲で調べる
- 留保(未実証): `clampSeats` に記録を持たせる修正の試作と回帰は、probe でも行っていない(probe「試験していないこと」)。修正の後に、テンプレートの試験一式と回帰スイート全体を流して、委任・協働の判定がほかの場面で変わらないことを確かめる

### 理由(所在つき)

1. **新しい欄を足さない理由**: 欄を足すと、採用組織は記入し、監査は読む。しかし「同じ変化点で確認した」ことを読んで何を判断するのかが定まっていない(内部 §5.4 案(c))。判断の無い欄は記入の手数と記入漏れの検査だけを増やす。必要な事実(誰が・いつ確認し、いつ任命したか)は既存の記録に載っている
2. **帰属の開示が要る理由**: 開示しないと、採用組織の責任者は「慎重を期して変化点を分ける」運用を自主的に選び、それで前後が保証されたと誤解する。手数を払って、保証の無いものを保証と思い込む形は、信頼性の点で最も悪い。逆に、前後の保証が本当に要る組織(規制業など)には、「確認の PR が基底へ入った後に任命の PR を出す」ことが必要だと分かる形で示すべきである(probe 確認3 の推測)
3. **新しい ADR の理由**: 採用済み ADR の本文は書き換えない(CLAUDE.md の ADR の規定)。ADR-0079 決定7 は「本人以外の記名」を決め、時点を決めていない(内部 §1.3)。時点を確定するのは新しい決定である
4. **場面を足す理由**: 案(a) が開かないと主張する経路を、試験として固定しないと、次の改修で開いても気づかない(内部 §5.2 回帰の試験)。p302 で開いていた X-decider と R1b(probe「p302 の版」)は、付記で塞いだ経路そのもので、試験の無いまま案(a) を入れるのは信頼性を下げる

### 他の案を落とす理由

- **記録の欄「同じ変化点で確認・使用」を足す(案(c) の記録版)**: 採らない。理由1。出力の1行(`/process-change` の差分の報告に、確認と任命が同じ変化点である旨を出す)に留めるなら、記入の手数が増えないため妨げない。ただし必須にはしない
- **帰属の前後を機械で保証する(確認の PR が入った後でないと任命を受け付けない)**: 採らない。前の変化点を要しないと決める R-1 と矛盾し、1〜2名の体制の承認者の待ちを工程の停止に変える。外部の要求にも支えられない(外部 §5)。要る組織が自ら課せることを開示で示す
- **印を外さず、見直しの月を延ばす**: 採らない。回帰と判断した以上、拒否を残す理由が無い。延ばすと、採用組織は延ばした期間、正しい入力を拒否され続ける

### 条件と留保

- 既に変化点を分けて確認した採用組織の過去の記録は、確認の変化点の `nameOverrides` が空のまま残る(probe 確認2)。記録は書き換えない。契約検査は現在の名簿でも確かめるため(verify-gate-contract.mjs L636)落ちない見込みだが、過去の記録を持つ構成で流して確かめていない(未実証)。実装の際に、分けた経路で作った構成に修正後の契約検査を流す場面を足す
- 拒否の文の改め(R-2 の条件)を、本件の受け入れ条件に含める。文が直らないと、R-3 の委任の拒否や、2名以上の名簿で記名の無い確認の拒否で、利用者が通し方に辿り着けないままになる
- テンプレートの改修は、テンプレートの作業ツリーに別のセッションの未コミットの変更がある(generate-profile.mjs ほか。本意見書の冒頭)。行番号と試作の差分は HEAD `72a98bd` に対するもので、実装の前に当て直しが要る
