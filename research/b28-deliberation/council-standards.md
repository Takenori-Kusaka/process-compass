# 束 B28 会議体 — 規格の委員の意見(IMPL-1029)

作成 2026-11-20。立場は、既存の ADR(0151・0200・0224)・条項(附属書F F.6・附属書H H.1/H.3・第7章 7.3)・語彙・外部の規格や実務との整合、および規範の文として決定可能か。前提(回答 43・44、指揮役の決定)は覆さない。Web は調べていない。読んだ現物は adapter.mjs の段の空の扱い(54〜80 行)、F.6 の 280〜286 行、H.3 の表、ADR-0224 の決定1・6・13。

## 0. 総評

- 方向は支持する。ただし条文(H.1 の追加文)が絶対の言い方(「通過させてはなりません」)なので、機械が通す例外(対象なし・R1 の判定不能・R1 を判定できない契機)を IMPL-1029 の note で開示しないと、表示と実態が食い違う。これが最大の整合上の指摘である
- 閾値の無い構成で機械が閉じるのは「走った形跡の構文」までで、検出力の十分さは閉じない。C4・H.3 の「測っている」を「十分」と読ませない書き方が要る(論点1)
- 外部の調査では、変異試験の対象コミットの欄も、報告の真正性の先例も見つからなかった。これを根拠に、機械の範囲を出力の約束に絞る案は規格の立場から支持する(論点5)

## 論点1 閾値の無い構成での証跡の確かめ方

- **結論: 修正して賛成**
- 機械で閉じる(決定可能): 段の出力に (a) スコアの行(数値、または変異体 0 件を示す明示の値)、(b) 生き残りの一覧の所在の行(空でない)、(c) 閾値が構成にあるときは段が出力のスコアと数値比較した結果、が在ること。構文だけを見る。閾値が無いときは「閾値を定めていないため合否を判定していない」を注意に出す
- 修正点1: **変異体 0 件(文書のみ・テストのみの差分)を表す値を出力の約束に持たせる**。無いと、R1 の変更が文書や設定だけのときに偽の失敗が出る。外部の調査では、PIT は failWhenNoMutations が既定 true、cargo-mutants は差分に対象が無いとエラー化と、道具で既定が割れる。偽の失敗は採用者を `|| true` へ追い込み、段の意味を消す。ただし「0 件」の明示値も `echo` で満たせる。これは開示する(安全でなく適合の主張の信頼に響く)
- 修正点2: **閾値は基底ブランチの構成から読む**(riskFloor と同じ)。PR 側の構成から読むと、同じ PR で閾値を 0 に下げて通せる。案の §1.2 は「基底の構成を段へ渡す」とあるので、閾値の読みも基底であることを明記する。ADR-0224 の決定6 が今どちらから読むかは未確認なので、実装で確かめる
- 修正点3(誘因の歪み): 閾値を設定すると 7.3 の承認が要る失敗が増え、設定しないと増えない。最小の手間を選ぶ採用者は閾値を設定しない。これは回答 44 の帰結で覆さないが、ADR に「閾値を定めない構成は、走った事実と結果の所在だけを証跡とし、検出力の十分さを主張しない」と書く。破られたとき失うのは、C4 を読む出荷判定者と採用者の顧客で、スコア 0% でも通った R1 の変更を「測っている」と読んでしまう点
- 閉じない(manual・開示): コマンドが実際に変異を作るか、スコアが実測か。EV-0339 の対象に足す(案の §1.3 のとおり)。確かめる者は G-6 の確認者と内部監査の抜き取り
- 追加の指摘: 閾値なしで通った注意は、ジョブのログにしか残らない。段の出力 3 行を GITHUB_STEP_SUMMARY にも出す程度なら、新しい仕組みでなく表示の位置の指定で済む。集約へ件数を載せる案(乙)は所有者が採らなかったので提案しない

## 論点2 G-5 で止めることと H.3「検証に数えない」の重ね方

- **結論: 案に賛成(H.3 の文は変えない)。ただし「死文になる」を理由に外さない**
- 理由: 2つは別の層である。G-5 は止める側(PR の通過)、H.3 は保証の主張の側(何を検証に数えるか)。H.3 が実際に働く場面は、(a) G-5 を経ない変更(直接 push)、(b) 対象なしで段を実施しないとされた変更、(c) R1 の判定が下限だけになり段が必須にならなかった場合、(d) 閾値を定めず、通ったが十分と言えない場合。(a)〜(c) は機械が通す抜け道なので、H.3 が最後の防波堤として残る。外すと、その抜け道の分だけ「測っていない R1 の変更」が検証に数えられる
- 重ねの書き方: H.1 の追加文は「実施の義務」、H.3 は「数える条件」と、一文ずつ役割を分けるだけにする。H.3 に G-5 への参照を足す程度は編集(ed)に当たる。重ねて書く定義を増やす案は、安全にも適合の主張の信頼にも響かないので不要
- 破られたとき失うのは、保証の主張を読む出荷判定者。H.3 を外す案を採ると、直接 push の R1 の変更に C4 の根拠が残らない
- 閉じ方: 条文の関係なので機械で閉じるものは無い。lint:refs が H.1 と H.3 の参照の実在を見る範囲に留まる

## 論点3 R1 の判定の源と push の経路

- **結論: PR の経路は案に賛成。push の経路は修正(トレーラだけにせず、区分の下限も使う)**
- PR の経路: 本文の区分と下限(基底の構成の規則)の高いほう。ADR-0039(R は変更ごと)と、既存の pr-rules の判定と同じ値を使うので、2つのジョブが食い違わない。下限を基底から読む点が重要で、PR 側で規則を弱められない
- push の経路: トレーラ `Risk:` は書く者が省ける。トレーラの欠落は出荷の集約が既に欠落として扱うが、それは事後で、G-5 の段が必須になる根拠にならない。**下限は人の判断に依らず決定可能**なので、push の範囲の全変更ファイルに riskFloorOf を掛け、トレーラの R1 との高いほうを採る。これなら案の「push は確かめない」(丙)の抜け道(トレーラを書かずに R1 を直接 push)を塞げる
- 追加の指摘1: R1 の判定に使う入力が読めないとき(gh の失敗、本文が空、merge_group・workflow_dispatch・schedule など PR でも push でもない契機)の扱いを決めておく。案は「判定できない」の扱いを書いていない。F.6 の Q1 が読めない場合は「判定できない」と注意に出して必須にしない前例(ADR-0224)がある。同じ型で、**下限だけで判定し、「本文を読めないため下限だけで判定した」を注意に出す**。黙って必須にしないと、API の障害で R1 が素通りする
- 追加の指摘2: スカッシュマージでは、PR の本文の区分とマージ後のコミットのトレーラが一致しない。push の経路は PR を経たコミットを再判定するのか。再判定するなら失敗してもマージ後で止められない(検出の層)。その位置づけを ADR に書く。破られて失うのは、直接 push の運用(ソロ期)をする採用者の R1 の変更の検出力の主張
- 開示するもの(manual): 人が区分を低く確定したこと。3.8.1 と G-6 が受ける既存の統制で、案どおり

## 論点4 既存の採用者の移行と template の既定

- **結論: 案に賛成(空を置く)。移行の書き方に2点を足す**
- 既定のコマンドを置く案に反対: 外部の調査 §2・§4 によると、道具の終了コードが合否を意味する程度が道具ごとにばらつく(mutmut は記述を確認できず、gremlins は版・経路で食い違い、Stryker4s・go-mutesting 系は未確認)。template が 7 つのアダプタに既定を置くと「この道具で R1 の検出力を測れる」と template が保証することになる。保証できない既定は、適合の主張の信頼を上げず、採用者の G-3 の技術選定も奪う
- 一定期間の注意にとどめる案に反対: 所有者が採らなかった乙の変形。猶予は、従う版の切り替え(`/process-change` 種別 edition)の時点を採用者が選ぶことで既に実現している。新しい期限の定義は不要
- 追加の指摘1(移行の時機): 案は「取り込み後の最初の R1 の PR で落ちる」。突然の失敗は `|| true` や `echo` の動機になる。**段が必須でない PR でも、キーが空・無いときは「この構成では R1 の PR で G-5 が失敗します」を注意に出す**。案は「必須でなければ注意で通す」だが、注意の中身を指定していない。決定可能で費用が小さく、移行の事故を減らす
- 追加の指摘2: 取り込みだけして従う版を切り替えない採用者の扱い。移行の注意は「同時に取り込む」と書くが、機械は強制しない。切り替えずに新しい段が効く(または効かない)状態を、README に事実として書く
- 追加の指摘3(偽装の最安値): 空を失敗にすると、最も安く満たす道は `true` か `echo` に出力の約束の行を固定で書くことになる。外部の調査(§3.6)にも、これを突き合わせる先例は無い。機械で閉じない統制として、EV-0339 の差し替え条件に「R1 の変更で常に成功するコマンドが段に置かれた件数」を足す案(案の §1.3)に賛成。数える者が誰かを書く(内部監査の抜き取り)
- 閉じ方: 在否と構文は機械。コマンドの実質は adopter(G-3 の技術選定の記録)と manual

## 論点5 外部の記録を照らすコマンドで機械が見る範囲

- **結論: 案に賛成(出力の約束だけ)。対象のコミットの SHA の突合は採らない**
- 規格の立場からの理由: (1) 外部の調査では、変異試験の共通の報告形式(mutation-testing-report-schema)にコミット・git の欄が無く、Stryker Dashboard は version(SHA)を URL の側に持つ。報告の側に載せる先例が無いまま、本標準が欄を定めると本標準の独自の規格になる。ADR-0224 決定10 の「規格を根拠に引かない、本標準の判断」とは別に、独自の欄を増やす費用が採用者へ及ぶ (2) 署名・証明(attestation)の先例は検索していない、と調査が明記している。実証を欠くので、機械の検査にせず根拠水準マークで開示する (3) 突合は `echo` で満たせ、CLAUDE.md の「改ざんの防止は機械で閉じない」に当たる
- 開示: 記録の真正・新しさ・当該の変更に対するものかは確かめない。確かめる者は G-6 の確認者と内部監査の抜き取り。EV-0339 に足す
- 採らない案として記録する: (a) 対象コミットの SHA の突合、(b) 記録の日付の新しさの機械検査(決定可能だが、古い記録を `touch` で新しく見せられる)、(c) 署名の要求。理由は上の (1)〜(3)
- 追加の指摘(後続の候補。今は採らない): mutation-testing-report-schema の JSON を受けて、状態の列挙からスコアを再計算し、出力の約束の行と照らす検査は、構造化された記録を要求する分だけ `echo` より偽装が高くつく。ただし道具ごとに出力の形が違い(mutmut・gremlins・PIT は未確認)、template が変換を持つことになるので、本件では採らず、手引きに「共通形式で出力すると将来の検査に載せやすい」と書くにとどめる。この判断も根拠水準マーク付きで

## 追加の指摘(論点を越えるもの)

1. **H.1 の追加文と機械の食い違い**: 「段のコマンドが空のまま G-5 を通過させてはなりません」は絶対の文だが、adapter.mjs は `targetState` が present でないと、ALWAYS でない段を「実施しない」で通す(54〜62 行)。R1 の変更でも、対象が無い構成なら段が空で通る。H.1 の文を「対象が存在する構成では」と限定するか、IMPL-1029 の note に開示する。限定は節全体でなく、この文の中に書く(scope-marking の規約。限定を別の段落へ置かない)。破られたとき失うのは、条文だけを読む採用者と監査者
2. **F.6 284 行の改めの文言**: 案の文「段を実施したうえでスコアが閾値に届かない場合も 7.3 の対象」は、閾値を定めていない R1 だけの構成では「届かない」が起こらない。**「閾値を定めている場合」を文の中に入れる**。同じ段落の前の文(閾値を定めないまま通過させてはならない)は案件の条件に限ることを、見出しでなく行の中で保つ
3. **F.6 の表の「優先」と H.1 の「必須」**: 案は食い違いでないとして文言の判断を会議体へ渡している。読み手には食い違いに見える。編集(ed)として「R1 の変更ごとの実行は H.1 による必須。ここでの優先は増分の範囲の優先順位」と直すのが安全。意味は変えない
4. **ADR-0244 の置き換えの書き方**: ADR-0224 決定13 の文を「置き換える」と書くとき、決定1・6・7・9 を保つことと、決定6 の範囲(案件の条件)を R1 へ広げなかったことを同じ段落に書く。「閾値を求めない」と「段は必須」は別の決定で、混ぜると決定6 が R1 に及ぶと読まれる
5. **「課さないと決めたこと」の明記**: R1 だけの構成に閾値を求めないこと、段が空・閾値未設定の 7.3、道具の既定の提供、対象コミットの突合、CHANGELOG.md の新設。いずれも、読み手が「書かれていない」と「課さないと決めた」を区別できるよう、ADR の該当の節と README の移行の注意に並べる(案の §1.5 の注意には、採らない旨の1行が無い)
