# 束 B28 会議体 現場の委員の意見(IMPL-1029)

作成 2026-11-20。立場は小さいチームの採用者。読んだもの: answers-1.md、ruling-draft-1.md(§1・§3・§4)、research-ext-1.md(§0〜§3)、intake-1.md の見出し。現物(adapter.mjs ほか)は読んでいない。実行での確認はしていない。以下は読んだ文書からの意見である。
前提(覆さない): 回答 43・44。R1 の変更で段が空なら G-5 失敗、7.3 では受けない、R1 だけの構成の閾値は求めない、移行の注意は README の1項。

## 総括

- 論点1・2・5 は案に賛成(論点1 は注意の出し方を修正)。論点3 は push の経路について修正。論点4 は「空を置く」に賛成、ただし取り込みの日の負担を下げる手引きを条件とする
- 現場の関心は2つ。(a) 取り込み後の最初の R1 の PR が緊急の修正のとき、止まる出口が無いこと (b) 増分の実行時間の公開の実測が無いこと(research-ext §1.2)

## 論点1 閾値の無い構成での証跡の確かめ方

- 結論: 案に賛成。機械は「スコアの行がある・数として読める・一覧の所在の行がある」までを見る。修正: 注意の文は R1 の PR ごとに出ると読み飽きられるので、段の出力の1行にとどめ、G-7 の集約には件数だけ出す(PR ごとの注意を集約の本文へ積まない)
- 理由: 閾値を求めないのは回答 44 で確定。その代わりの証跡がスコアと一覧の所在であり、行の存在と構文は決定可能で閉じる。小さなチームは閾値の較正に使える履歴が無く(research-ext に較正の実測なし)、最初から閾値を求めると適当な値(例 50)を書いて形だけ通す
- 破られたとき: スコア 0 や `echo "score 0"` でも通る。失うのは G-6 の確認者と、C4 の「検出力を測っている」を読む第三者。採用者本人は失わない
- 閉じ方: 在否と構文は machine。実際に測ったかは manual。開示は EV-0339 と IMPL-1029 の note。スコアが著しく低い R1 の PR を通した件数は、閾値を定めない構成の宣言として adopter に開示させる(新しい欄は足さない。段の出力と集約で足りる)

## 論点2 G-5 で止めることと H.3「検証に数えない」の重ね方

- 結論: H.3 は残す。重ねる文は足さない(案の方向に賛成)
- 理由: G-5 を経ない変更(直接 push、G-5 が構成されない期間)では H.3 の帰結が唯一の歯止めになる。死文ではない。「止める」への一本化は、止められない経路の保証の主張を黙って落とす
- 破られたとき: 一本化すると、G-5 を迂回した変更が「検証に数えられる」ままになる。失うのは適合の主張の信頼
- 閉じ方: H.3 の帰結は manual(保証の主張の側)。G-5 の側は machine。定義を増やす提案はしない(新しい定義は適合の主張の信頼に響かない)
- 一点: 手引きに「G-5 が落ちたことと H.3 の帰結は別の話で、後者は人の判断の対象」と1行だけ置く。条文は変えない

## 論点3 R1 の判定の源と push の経路

- 結論: PR の経路は「本文の区分と下限の高いほう」に賛成。push の経路のトレーラ `Risk: R1` には反対(修正案は「push の経路では確かめない」を開示)
- 理由
  - トレーラは書き忘れると R1 と判定されずに通る。安全側に倒れない機械は、書いた人の誠実さに頼る点で PR の本文の区分と同じだが、PR は pr-rules が下限と突き合わせる。push には下限の突合がない
  - 小さなチームは直接 push が多い(CLAUDE.md の本体もソロ期は main へ直接)。トレーラの習慣を増やすと手順が増え、忘れても何も起きないので守られない
  - 案の自分の記述(§4 論点3 の第三案)どおり、PR を経ないコミットは出荷の集約で欠落になる。そこで止まるなら二重の機械は要らない
- 破られたとき: push で R1 の変更を入れた者は、変異試験なしの R1 を出荷の集約の欠落で止められる。止まらない構成(集約を使わない採用者)では何も止まらない。失うのは適合の主張の信頼
- 閉じ方: PR の判定は machine。push は閉じない。manual とし、確かめる者は G-6 の確認者と内部監査の抜き取り。IMPL-1029 の note に「push の経路は R1 を判定しない」と書く
- 条件: 出荷の集約が push 経路を実際に欠落にすることを、実装の担当が試験で示すこと。示せなければ、トレーラ案を再検討する
- 細かい定義を増やす提案(トレーラの書式の厳密化)は、安全にも取り消せない操作にも響かない。採らない

## 論点4 既存の採用者の移行と template の既定

- 結論: 7つのアダプタに空を置く案に賛成。既定のコマンドは置かない。取り込みの猶予も採らない(回答 43)。ただし次を条件とする
  1. README の1項に、スタック別の最小のコマンド例を書く(置くのではなく例示)。実在する道具だけ。research-ext §2 の表のうち終了コードを確認できたもの(cargo-mutants、Stryker JS/.NET、PIT、cosmic-ray)を先に。mutmut と gremlins は終了コード未確認なので例に載せないか、未確認と書く
  2. 段のジョブに時間の上限(timeout-minutes)を手引きで勧める。理由: 公開の実測が無く(research-ext §1.2)、小さなチームの CI の分単位の費用が見積もれない。全量の実行は Bitcoin Core で 30 時間超の事例がある
  3. 費用の見込みは根拠水準マークで開示する(単一事例にも満たない実測なし)。EV-0339 の差し替え条件に「R1 の PR あたりの実行時間の実績」を足す
- 理由: 取り込みの日には落ちない(R1 の PR が無ければ)。落ちるのは最初の R1 の PR で、そのとき道具の導入に半日かかるのが現場の実態。G-3 の技術選定を template が先取りしないことには同意する
- 破られたとき: 空のまま取り込んだ者は、最初の R1 の PR で止まる。失うのは採用者の時間(自分の PR が出せない)
- 閉じ方: 空なら失敗は machine。道具の選定と較正は adopter

## 論点5 外部の記録を照らすコマンドで機械が見る範囲

- 結論: 出力の約束だけ(案に賛成)。SHA・日付の一致は見ない
- 理由: 外部の調査では、報告のスキーマ(mutation-testing-report-schema)に対象のコミットの欄が無く、真正性の先例も無い(research-ext §3.1)。SHA を書かせても `echo` で満たせて改ざんを防がない。道具の無い言語の小さなチームには、外で手で実行して貼る作業が既に重い。そこへ照合の手順を足すと、使われなくなる
- 破られたとき: 古い記録や他の変更の記録を貼られても通る。失うのは G-6 の確認者と第三者
- 閉じ方: 出力の約束は machine。記録の真正・新しさ・範囲は manual。確かめる者は G-6 の確認者と内部監査の抜き取り
- 任意の手引き: 外部の記録がスキーマ形式なら、スコアを再計算できる(決定可能)。ただし機械の義務にはしない(言語を絞る定義が増え、信頼を足さない)。手引きに「再計算してよい」と書くだけにとどめる

## 追加の指摘

1. **R1 の緊急の修正の出口が無い**: 段が空の通過に 7.3 を使えないのは正しい(判定をしないまま進める使い方になる)。しかし道具を入れていない採用者の R1 のセキュリティ修正は、導入が済むまで出せない。残る出口は「外部の記録を照らすコマンド」に `echo` を置くこと(論点5 のとおり機械は止めない)で、実質の抜け道が正規の出口と区別がつかなくなる。提案: 手引きに「道具未導入での緊急の修正は、外部で実行した記録を貼る経路が正規。貼れないなら人の判断で記録する」と書き、そこへ至る前に取り込みの注意(移行の項目1)で道具を入れておくよう促す。条文は変えない。響く先は安全(緊急の修正が止まる)と適合の主張の信頼(抜け道の見分けがつかない)
2. **変異ゼロの差分の扱い**: 増分の実行で被試験コードに変更がない PR(テストのみ、文書のみ)は、PIT の `failWhenNoMutations` の既定(research-ext §2.2、推測を含む。要実行確認)や cargo-mutants の「変異体なし」のエラーで、コマンドが非ゼロを返しうる。R1 の PR でも起きる。結果、正当な PR が偽の失敗になる。提案: 手引きに「変異体ゼロのときの出力(スコアは n/a と書く等)をコマンド側で整える」例を書く。機械の出力の約束にスコア n/a を足すかは、echo の抜け道を広げるので論点1 の範囲で慎重にする。実装の担当が実行で確かめるまで決めない
3. **並行する PR の費用**: R1 の PR が複数あるとき、段が同時に走り CI の分が嵩む。concurrency の設定を手引きに1行(同じ PR の古い実行を止める)。費用の上限は採用者が決める。安全には響かない
4. **集約の skipped との整合**: 段のジョブは構成済みなら常に走り、必須でなければ success で終わる(§1.2)。この設計は ADR-0224 決定8 と整合するので賛成。ただし R1 の判定が段の中で行われるため、判定の誤り(本文の区分が空など)で必須のはずが成功に倒れる経路がないことを、test-adapter の ng の組に1つ足すこと(本文の区分が空 + 下限が R1)
5. **README の移行の注意の文案**: 項目4「取り込み後の最初の R1 の PR で落ちる」は正直で良い。項目1 の「差分に絞る実行を勧めます」は、根拠水準のマーク(増分は網羅ではない、research-ext §1.1 の公式の文言)を添える。増分は全量の代わりにならず、ドリフトを拾うために定期の全量を勧める旨を手引きに(R2 の週次は undelivered で開示済みなので、重複させず参照だけ)

## 採らないと決めてよいこと(現場の立場から)

- 道具の既定のコマンドを template に置かない(G-3 の判断を奪う)
- 取り込みから一定期間は注意にとどめる(回答 43 に反する)
- 外部の記録に SHA を書かせる(echo で満たせる)
- push のトレーラによる R1 の判定(論点3)
- 閾値を R1 だけの構成にも必須にする(回答 44)

## 機械で閉じる / 閉じない まとめ

| 項目 | 閉じ方 |
| --- | --- |
| R1 か(PR の本文と下限の高いほう) | machine |
| 段が空・キー無しで失敗 | machine |
| 出力の行の存在と構文 | machine |
| 閾値ありの大小 | machine |
| push の経路の R1 | manual(開示) |
| 外部の記録の真正・新しさ・範囲 | manual(G-6 と内部監査) |
| コマンドが実際に変異を測るか | manual |
| 費用・実行時間の見込み | adopter(根拠水準マークで開示) |
