# 286 準拠テンプレートの運用性 — 設計の案(2026-10-01)

- Issue: #286。評価: `286-template-usability-assessment.md`
- 本書は案である。反対の立場からの点検を経て確定する

## 設計の原則

1. **規則を常時読み込みから外すときは、必ず「機械で担保する」か「必要な時点で確実に読ませる」の一方と組にする**。外すだけにしない(外した規則が読まれないことがある。FND-0033、E2)
2. **AI に覚えさせず、状態から次の一手を機械が出す**。利用者も AI も、プロセスの全体を知らなくてよい形にする
3. **成果物とゲートの知識は、1つの入口から木構造で辿る**。スキルを成果物の数だけ並べない。入口が、いま要る1枚だけを読ませる
4. 標準の条項は変えない。テンプレートの実装と、フェーズ5 の実装の記述(`template-repository.md`)を変える。常時読み込みの量の目標は、根拠水準マークつきの暫定値として置く

## 決定の案

### A. 常時読み込みを縮める

- `CLAUDE.md` は、毎回の作業に要るものだけにする:
  - このリポジトリの開発のしかた(3行): 「迷ったら `/pit` を実行する。次の一手はそれが出す」
  - 人へ戻す3つの場合と、受信箱のラベル(1回だけ書く)
  - 一律に AI へ委譲できない領域(4行)
  - 機械が止める禁止事項の一覧(1行ずつ。理由と詳細はスキルへ)
  - コミットの規約(トレーラの一覧。詳細は implement スキルへ)
- 生成区間は、ロールの全行を出さず、構成の要約(体制の規模、運用形態が協働・委任の席、出荷できない状態の有無、自分が担うロールを知る方法)と、詳細の所在だけにする
- 「まず読むもの」から PROCESS-PROFILE.md と process.config.json の全文を外す(読むのはコマンドの出力)
- 場面限定の内容(受信箱の各ロールのコマンド、委任の経路、例外承認の経路、タスクの粒度の根拠、巨大 PR の論考)は、該当するスキルの補助ファイルへ移す
- **目標**: 初期化後の `CLAUDE.md` を 4,000 トークン以下(推定)にする。暫定値として根拠水準マーク(E1)。見直しの観測量: 移した規則の違反の件数(G-5・集約・監査で検出したもの)。移した規則の違反が、移す前より増えたら、その規則を常時読み込みへ戻す

### B. 入口のコマンド `/pit` と、状態を出すスクリプト

- `scripts/gate/next.mjs`(決定的。AI に判定させない)が、構成・判定記録・台帳・D-0・ブランチと PR の状態から、現在の段階と、次に実行するコマンドを1〜3個出す。理由を1行ずつ添える
  - 例: 「構成が未設定 → `/process-init`」「D-0 が無い → `/process-change`(初回の記入)」「受入基準が無い機能 → `/spec-write F-xxx`」「出荷の範囲で G-7 の記録が無い → `/gate G-7`」
- `/pit` のスキルは、`next.mjs` を実行してその出力に従うだけの短いスキルにする
- **すべてのスキルの最後の手順を「`node scripts/gate/next.mjs` を実行し、出力された次のコマンドを示す」にする**
- `generate-profile.mjs` と `/process-change` の出力の末尾に、次の一手を出す

### C. セッションの開始時に状態を注入する

- `SessionStart` のフックで `node scripts/gate/next.mjs --brief` を実行し、数百トークンの状態(段階、次のコマンド、出荷できない状態や未達の有無)を文脈へ入れる
- `.claude/settings.json` の `hooks` へ1項目を足す変更になる。この設定は人の操作で見直された強制層であるため、**足すのは追加の1項目だけとし、既存の項目は変えない**。オーナーへの報告に明記する

### D. 成果物とゲートの知識を木構造にする

- `/artifact <種別>` のスキル: 入口の SKILL.md(短い)と、成果物ごとの補助ファイル `artifacts/<テンプレ番号>-<名前>.md`(目的・読み手・形式、作成の手順、レビューの観点、機械の検査)。入口は、指定された種別の1枚だけを読ませる。テンプレ00〜10 のすべてを揃える
- `/gate <ゲート>` のスキル: 現在の gate-record を入口と、ゲートごとの補助ファイル `gates/G-N.md`(判定基準、材料の集め方、判定記録の書き方、機械の検査)へ分ける。G-1〜G-8・SG を揃える
- `/process-change` は、入口と、変化点の種別ごとの補助ファイルへ分ける
- 既存のスキル(spec-write、task-breakdown、implement、human-verify、adr-write)は残し、`/artifact` と `/gate` の補助ファイルから参照する
- スキルの入口(SKILL.md)の目標: 1本あたり 2,000 トークン以下(推定)。補助ファイルは1枚あたり 3,000 トークン以下。暫定値(E1)

### E. 遵守を機械で担保する

| 規則 | 現状 | 担保の案 |
| --- | --- | --- |
| テストの失敗をテストの変更で解消しない(禁止事項3) | 自己修正のロック中だけフックで遮断。PoC では遮断が外れる | フックの遮断を段階に依らず有効にする(PoC でも外さない)。加えて G-5 に、既存のテストの変更(削除・期待値の変更)を検出して PR 本文の理由の欄を必須にする検査を足す |
| 変更規模の上限 | PR では検査されない | G-5 で検査する。上限を超えたら、例外承認の記録(台帳の行)が PR を対象として示している場合だけ通す |
| トレーラ `Spec:` | 出荷時の集約でだけ見る | G-5 で PR のコミットごとに検査する |
| 閾値を機能変更と同じ PR で変えない(禁止事項6) | 検査なし | G-5 で、構成の閾値・除外設定のファイルと製品のコードが同じ PR で変わったら失敗させる |
| ブランチ保護 | 1〜2名はルールセットなし。3名以上も適用は手作業 | 1〜2名にも、必須チェック(gate-g5)だけを持つルールセットを用意する。適用の手順を `/process-init` の残作業に出す。出荷の集約で、マージされた PR が gate-g5 の成功を持たない場合を欠落にする(適用されていないことを、事後に機械で検出する) |
| `state:*` ラベル、ブランチ名 | 指示文だけ | 機械で担保しない。指示文に残し、限界として開示する(ラベルは受信箱の運用の問題であり、出荷の統制ではないため) |

### F. 知らない利用者の最初の出荷

- README の冒頭に「始め方」を5手順で置く(テンプレートから作る → `/pit` → 出力に従う)。用語の説明は、出てきた時点でコマンドが1行で添える
- `/process-init` の設問は、専門用語を使わない言い換えを併記する(現状の8問)

### G. 記述の食い違い

評価の「軽」の5件を直す。

## 採らなかった案

- **成果物とゲートごとに独立したスキルを並べる(20本超)**: スキルの説明文の一覧そのものが常時読み込みになり、選択も AI に委ねることになる。入口を2本(`/artifact`・`/gate`)にし、木構造で辿る
- **常時読み込みの規則をそのまま残し、量の目標を置かない**: 評価で約8割が場面限定であった。反証(長さが成功率に効かない測定)はあるが、外した規則を機械で担保する組とすれば、量を減らす不利益は小さい
- **ラベルとブランチ名まで機械で強制する**: 受信箱の運用は体制ごとに違い、強制の誤検出で作業が止まる不利益が大きい

## 点検を受けた改訂(確定)

反対の立場からの点検の判定は「直して採る」。指摘を次のとおり取り込み、これを確定の設計とする(上の案と食い違う箇所は、本節が正)。

### A の改訂: 規則は消さず、常駐の索引に残す

- **機械の担保が無い規則は、`CLAUDE.md` から外さない**。1規則1行の索引として常駐させる(常駐した指示はよく守られる: FND-0052、E2。スキルは評価の56%で呼ばれなかった: FND-0033、E2)
- 外すのは、規則の**説明・理由・手順・場面限定の詳細**だけ(受信箱の各ロールのコマンド、委任の経路の詳細、例外承認の経路の詳細、タスクの粒度の根拠、巨大 PR の論考、参照リンク)。外した詳細は、索引の各行から補助ファイルの所在で辿れるようにする
- 規則ごとの対応表(規則 / 常駐の索引に残すか / 機械の担保 / 詳細の所在)を `template-repository.md` に置き、禁止事項と人へ戻す場合の全数を載せる。担保できないものはその旨を書く
- 実装マークの降ろし先 `claude-md` は、常駐の索引に残る規則については有効なまま。詳細をスキルへ移した規定は、降ろし先をスキルのファイルへ登録して付け替える(`src/data/impl-targets.yaml` の登録。標準の条項の文言は変えない)
- 量の目標は置くが、**導出は実測による**: 索引化した後の量をトークナイザに近い計測で測り、その値を上限として置く。暫定値(E1)

### 見直しの観測量: 固定の場面集で遵守を実測する

- 違反の検出件数を観測量にしない(担保の無い規則は0件に偏る)
- 固定の場面集(人へ戻すべき場面、テストを書き換えたくなる場面、委任の範囲外の変更、例外の経路を選ぶ場面、など8〜10場面)を用意し、改訂前と改訂後のテンプレートで AI の担い手に実行させ、規則を守ったかを数える。改訂後に遵守が下がった規則は、詳細を常駐へ戻す
- 場面集は `template/` の外(本体の `research/`)に置き、検証の手順として残す

### B の改訂: 次の一手は、機能ごと・ロールごと。人の判断待ちを終端にする

- `next.mjs` は、機能(F)ごとに状態を出す。並行する機能を1つにまとめない
- 次の一手がロールによって違う場合は、ロールごとに出す
- **人の判断を要する状態(ゲートの判定、R1・R2 の決定、例外承認、緩める向きの決定)は「人の判断待ち」として終端で出す**。AI の担い手が実行するコマンドを出さず、待つ相手(席と受信箱のラベル)を出す
- 状態を決められない場合は「判定できない」と理由を出し、推測で次のコマンドを出さない

### C: 変えない(SessionStart の1項目の追加。出力の上限と、実行に失敗した場合は何も注入しない挙動を確かめる)

### D の改訂: 補助ファイルは正本を二重にしない

- 成果物の補助ファイルは、欄の一覧を書かない。様式の正本はテンプレートの `templates/NN-*.md`(標準の第6章との対応は既存の必須欄の検査が見る)。補助ファイルが持つのは、目的・読み手・形式、作成の手順、レビューの観点、機械の検査の所在だけ
- 「入口が1枚だけ読ませる」は指示に従うかどうかに依る。`next.mjs` の出力に、読むべき補助ファイルの所在を出し、選択を AI に委ねない。それでも読まれない危険は限界として開示する
- 運用の工程(テンプレ05 運用引き継ぎ、障害時)も補助ファイルを揃える

### E の改訂

| 規則 | 確定の担保 |
| --- | --- |
| 禁止事項3(テストの失敗をテストの変更で解消しない) | 自己修正のロックは、スクリプト(`scripts/gate/self-heal.mjs start`)で始め、フックがロック中の書き込みを遮断する。PoC でも遮断を外さない。ロックの外(テストを先に書く作業)は遮断しない。既存のテストの変更(削除・期待値の変更)は、G-6 の材料(レビューの観点)として PR に一覧を出す。理由の欄を担保にしない(AI が埋められるため) |
| トレーラ `Spec:` | G-5 で、PR 本文またはスカッシュのメッセージになる PR のタイトル・本文を検査する(コミットごとに見ない) |
| 変更規模の上限 | G-5 で検査する。算定の除外規定(生成物・ロックファイル・一括整形)を再利用する。例外は、**基底ブランチの**台帳に PR を対象とする例外承認の行がある場合だけ通す(同じ PR で足した行は数えない) |
| 閾値と機能変更の同時変更(禁止事項6) | 同じ PR で閾値・除外設定と製品のコードがともに変わった場合だけ失敗させる。閾値だけの PR と、初回の設定(基底に構成が無い)は通す |
| ブランチ保護 | 1〜2名にも必須チェックだけのルールセットを用意する。私有リポジトリでルールセットが使えるかは GitHub のプランに依るため、使えない場合の扱い(事後の検出だけになる)を README に書く。出荷の集約で、gate-g5 の成功を持たない PR を欠落にする |

### 受入条件5 の検証の手順

- 知らない利用者を演じる担当が、`README.md` だけを読んで始める。体制は1名+AI と 3名の2通り。模擬の gh を使う
- 出荷の定義: 最初の機能について、受入基準 → 実装 → G-5 → G-6(3名の場合)→ G-7 の証跡の集約が欠落なしで通り、G-8 の記録を書けること
- 実際の GitHub 上での実地は行えない。その旨を開示する

### 実装の段取り(1段ずつ)

1. 段1: A(索引化)・B(next.mjs と /pit)・C(SessionStart)・F(始め方)・G(食い違い)・E のうち禁止事項3 のロック
2. 段2: D(/artifact・/gate・/process-change の木構造)と、E の残り(G-5 の検査、ルールセット)
3. 段3: 検証(遵守の場面集の前後比較、知らない利用者の通し)
