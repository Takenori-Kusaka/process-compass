# 286 通しの検証で見つかった箇所と、修正の決定(2026-10-01)

- 検証: プロセスを知らない利用者を演じる担当が README だけを読み、Claude Code(sonnet、非対話)を AI の担い手として、1名+AI と 3名で最初の機能を出荷するまで進めた。記録は `tmp/eval286-novice/`(`log-A.md`・`log-B.md`・`runs/`・`harness/`)。費用 約10.9ドル
- 判定: 両方とも「条件つきで出荷できた」。次の一手の案内は、構成から G-4、実装、出荷前まで正しく働いた。人の判断待ちで AI は止まり、待つ席を示した。AI が規則を外れた場面は確認されなかった
- 条件: 利用者が強制層のワークフローを直したこと、初回の G-5 を通す基盤を AI と数往復して足したこと

## 修正の決定

### N1 初期化した直後に G-5 が落ちる(重大)

- `templates/00-d0-governance.md` の「(1人体制など)」を、禁止語に当たらない言い換えへ改める
- 禁止語の検査(`spec-lint`)の対象を、機能仕様の置き場に限る。様式(`templates/`)と生成物は対象外にする。CI と手元で同じ範囲を見る(引数なしの既定の範囲を CI と同じにする)
- テンプレートの全ファイルに対し、初期化の直後に G-5 の手元の検査が通ることを、回帰の試験に足す

### N2 初回の G-5 を通す基盤が無い(重大)

- `/process-init`(`--stack node`)が、アダプタの検査が求める最小の基盤を生成する: `package.json`(`test` と `coverage` のスクリプト)、秘匿情報の検査の設定、空のテストの雛形。ロックファイルは `npm install` で作る手順を案内する
- 基盤だけの最初の変更が `pr-rules` で落ちないよう、トレーラ `Spec: setup` を、変更が設定・ツール・雛形のファイルだけに収まる場合に限って受け付ける(製品のコードを含めば通常どおり仕様を要する)
- 他のスタック(python、go、none)も、同じ考え方で最小の基盤を出すか、出せない場合は初期化の出力で作るべきファイルを列挙する

### N3 出荷の証跡のワークフローが G-5 の結果を取り込めない(重大)

- `ship-evidence.yml` の成果物の取り込みを、`gh run download` で対象のコミットの gate-g5 の実行から取る形へ改める(`download-artifact@v4` に実行の識別子を渡していなかった)。検証の担当のパッチ(`tmp/eval286-novice/harness`)を参考にする
- 実際の GitHub 上で確かめていない旨を、ワークフローの冒頭と `ci-gates.md` の「実装の制約」に残す

### N4 中程度

- 手元で集約するとき、`GITHUB_REPOSITORY` が無いと全 PR が欠落になる: リポジトリを `git remote` から推定し、推定できなければ `--repo` を求める。原因を出力に書く
- `next.mjs` が、G-7 の判定記録を PR で取り込んだ後も「G-7 の判定記録がない」と出し続ける: 出荷の範囲と判定記録の対応を直す
- 3名の体制で、初期化のときに案内どおり main へ直接入れたコミットが G-6 の欠落になる: 初期化と `/process-change` が書くファイルだけのコミット(構成、構成書、`CLAUDE.md` の生成区間、D-0、`.claude/guard.json` など初期化が書くもの)は、初期化の記録として対象外にする。または初期化の案内を PR 経由に改める。どちらにするかは実装で判断し、理由を報告する
- AI が手元で実行した禁止語の検査が、CI より狭い範囲を見て「0件」と報告した: N1 の既定の範囲で解消する
- 兼務の拒否に対して AI が「4人目が要る」と誤って案内した: 拒否の文に、その体制の人数で取れる選択肢(席の割り当ての組み替え、1〜2名なら逸脱として記録)を出す
- 企画書の観点1・2 の扱いが実行ごとに変わった: `/artifact 06` の補助ファイルに、観点ごとに誰が何を書くかを明記する

### N5 軽い

- 次の一手の出力で、初めて出る用語(G-4、席、運用形態、委任など)に1行の説明を添える
- PR の様式で人が書く欄を、毎回手で埋める手間: 欄の説明を短くし、例を添える(人が書く欄であることは変えない)
- README の graft の手順の食い違いを直す

### 開示する境界の事例

- 自己修正のロックを解いた後、AI が自分で書いたテストの期待値を直し、人はその中身を確かめなかった。テストを先に書く作業として許している範囲であり、既存のテストの変更は G-6 の材料として PR に一覧が出る。1名体制では確かめる人がいないため、保証の開示の項目1 にそのまま出る

## 2回目の通しの検証(2026-10-02)と、追加の修正の決定

- 記録: `tmp/eval286-novice2/`(`log-A.md`・`log-B.md`・`runs/`・`harness/`)。47回、約11.1ドル
- 判定: 1名+AI・3名とも、**強制層を直すことなく**出荷まで到達した。人の手当てが要ったため「条件つき」。前回の重大3件は解消(ワークフローの取り込みは手順の上で。実際の GitHub では未確認)。新しい重大は無い
- AI は判定・記名を代筆せず、ロック中のテストを書き換えなかった。機械が止めたもの: PR の様式の誤り、リスク区分の欠落(出荷前)。機械が止めず人が直したもの: 仕様の範囲の書き誤り、訂正の注記の主体の誤り、D-0 節3 の手書きで版を上げなかったこと

### N6 前提の台帳を作れない(中)

- 前提の台帳(テンプレ10)の定義が、外部のサイトにしか無かった。`/artifact 10` の補助ファイルに、標準の要約(何を書くか、全ゲートの共通条件との関係)を置く。`next.mjs` が、台帳が無い時点で作成を案内する
- ゲートの判定基準を満たさない場合の例外承認(変更でなくゲートの判定が対象)は、台帳の「対象」に `G-N F-NNN`(ゲートと機能)で書けるようにする。変更を対象とする例外承認(PR・コミット)と区別して照合する

### N7 文書だけの PR でリスク区分の未記入を止めない(中)

- G-5 の `pr-rules` で、PR 本文のリスク区分の未記入を、変更の種類に依らず失敗にする(記録だけの PR と `Spec: setup` の PR も含む。区分は変更ごとに確定する記録であるため)

### N8 判定記録の結果欄の書き方で、次の一手が理由を示さない(中)

- `next.mjs` は、判定記録はあるが結果欄が「通過」「差し戻し」のどちらとも読めない場合に、記録の所在と理由(「結果欄が2値のどちらでもない」)を出す
- `/gate` の補助ファイルで、転記の注記などは結果欄ではなく本文に書かせる

### N9 軽い

- D-0 節3(決定の権限)を書き込む手段が無い: `/process-change` の種別 `settings` で `governance` と合わせて書けるようにするか、手で書く欄であることを様式と `next.mjs` で示す(どちらにするかは実装で判断)
- 共著者のトレーラと、担い手の宣言のずれの警告に、直し方の案内を添える
- 企画書の置き場が2か所ある: 1か所に揃える
- 判定時刻の矛盾を、集約が「D-0 の版の不一致」としてだけ出す: 判定記録の時刻が変化点より前か後かのずれであることを、出力に添える
