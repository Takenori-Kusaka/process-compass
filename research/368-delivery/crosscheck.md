## 結論

要求事項5 の中心(記録が無ければ着手しない)は、入口まで通して働いています。記録が無い場合・読めない場合・導けない場合のほとんどは、安全側(`[着手しない]` か `[判定できない]`)に倒れます。

ただし、**記録があっても、それが遷移の前提に当たる記録かどうかを確かめていない場面**が3つあります(X-1・X-2・X-3)。どれも「着手してよい」を誤って出す側の欠陥です。`check=machine` の主張の範囲を狭めるか、直してから delivered にすることを勧めます。重大度「高」は付けていません。3つとも、同じ判定記録の欠落を出荷の証跡の集約(G-7)が後で拾う余地があり、着手の時点の網の抜けにとどまるためです。

## 指摘

### X-1 `state:needs-dev` の前提の記録が、状態の遷移の表から導かれていない(重大度: 中)

- **所在**: `template/scripts/gate/next.mjs` の `INTAKE_RULES['state:needs-dev']` と、その上の注記「前提の判定記録は、標準 第3章 3.5.5 のラベルの語彙(付ける席)と状態の遷移(遷移の契機)から導く」。同じ対応を、IMPL-0331 の note、`handoff.md` の表、本体のコミットの本文も持つ
- **根拠**: 3.5.5 の語彙で、`state:needs-dev` は「価値責任者・技術判断者・事業決裁者が、**判断の後に**開発者へ着手を渡した」状態です。遷移の表で `needs-dev` へ入る契機は、`needs-po`(価値責任者が判断を記録に残す)、`needs-tech`(技術判断者が **G-3 の判定記録**を作成する)、`needs-owner`(決裁を記録に残す)の3つです。実装は、どの経路でも G-2・G-4 の通過を求めます。これは 3.5.5 からではなく、`/implement` の前提(第5章 5.8.5)と次の一手の条件から来ています
  - 抜け: 技術判断者が G-3 の記録を作らずに `needs-tech` → `needs-dev` と替えても、G-2・G-4 が過去に通っていれば `[着手してよい]` が出る。要求事項5 の違反がそのまま通る
  - 足し過ぎ: 機能へ対応づけない作業単位(技術的負債など、G-3 だけを経る作業)は、記録が揃っていても常に `[判定できない]` になる。要求事項5 が求めない停止である
- **直し方の向き**: 遷移の前提を「どの席が付けたか」で分けるか、少なくとも `needs-tech` を経た作業単位に G-3 の記録を求める。G-2・G-4 を求める部分は第5章 5.8.5 を根拠として書き分け、3.5.5 から導いたとは書かない。導けない部分は IMPL-0331 の note から別の `undelivered` の印(`scheduled`)へ切り出す(X-7 と同じ扱い)

### X-2 前提の記録を「最新の判定」でなく「どれか1件」で読む(重大度: 中)

- **所在**: `next.mjs` の `passed()`(`records.some(...)`)と `intakeCheck` の G-6 の分岐(`own.some(...)`)
- **根拠**: 実行で、G-4 の通過の後に差し戻しの記録がある機能、G-6 の通過の後に差し戻しの記録がある PR の `state:ready-to-merge` が、どちらも `[着手してよい]` になりました(上表)。テンプレートの出力自身が「判定者が新しい記録で判定する(成立した記録は書き換えない)」と書くとおり、効いている判定は最新の記録です。ラベルと最新の判定が食い違う作業単位は、要求事項5 の「判定記録が無い」に当たります。逆向き(qm-blocked で古い差し戻しの後に通過)も `[着手してよい]` になりますが、こちらは開発者が差し戻しに対応するだけなので害は小さい
- `passed()` は次の一手と共有する既存の関数で、この欠陥は #368 より前からあります。#368 はそれを着手の確認へ持ち込みました
- **直し方の向き**: 対象・ゲートごとに最新の記録(判定日時の順)を取り、その結果で判定する。次の一手にも同じ影響があるため、既存の open Issue があればそこへ寄せる。無ければ実行で確かめた欠陥として起票する

### X-3 構成にゲートのキーが無いと「有効でない」とみなして着手させる(重大度: 中)

- **所在**: `intakeCheck` の機能の分岐(`active.length === 0` で `start`)と、`config.mjs` の `isGateActive`(`state` が無ければ false)
- **根拠**: `configured:true` で `gates` が無い構成、`g2` のキーだけが無い構成で、記録が無くても `[着手してよい]` になりました。同じ `config.mjs` の `gateState()` は、キーが無ければ `required` とみなします。着手の確認は緩い側を使っています。壊れた・古い構成は「記録を導けない」場合であり、実装自身の方針(導けなければ `[判定できない]`)と食い違います
- **直し方の向き**: ゲートのキーが無い、または `state` が語彙に無いときは `[判定できない]` にする。`omitted`・`unmet` と明示されたときだけ「有効でない」とする。試験へ ng の場面を足す

### X-4 `state:ready-to-merge` の差し戻し先のラベルが、ラベルの語彙の「付ける席」と食い違う(重大度: 中。標準側の判断を要する)

- **所在**: `renderIntake` の hold の出力「ラベルを判定者の受信箱へ替える」と、G-6 の判定者の受信箱の導出。実行での出力は「独立レビュア。受信箱 `state:dev-done`」
- **根拠**: `state:ready-to-merge` を受けるのは出荷判定者です。指示どおりなら、出荷判定者が `state:dev-done` を付けます。3.5.5 の語彙で `state:dev-done` を付ける席は開発者・AI維持管理者だけで、状態の遷移の表にも `ready-to-merge` → `dev-done` はありません(`ready-to-merge` から出るのは `qm-blocked` と完了だけ)。要求事項5 の「判定者へ差し戻す」と語彙の表が、この場面で両立していません。テンプレートが片方を選んだことは、どこにも開示されていません
- `state:needs-dev` の差し戻し(開発者が `state:needs-po` へ替える)は、遷移の表の「実装中に価値・事業の判断が要ると分かった」に当たり、食い違いません
- **直し方の向き**: 標準の側で、要求事項5 の差し戻しに使うラベルを決める(語彙の表へ例外の行を足す、または `state:needs-po` 経由とするなど)。決まるまでは、テンプレートの出力で ready-to-merge の hold を「付ける席の規則と両立しないため人へ戻す」として扱い、IMPL-0331 の note に未解決として書く

### X-5 読めない記録で、手順に無い出力と終了コードが出る(重大度: 低)

- **根拠**: `docs/gates/` に `.md` の名のディレクトリを置くと、終了コード 1、`[next] 判定できない: EISDIR ...` が出ました。手順は `[着手してよい]`・`[着手しない]`・`[判定できない]` の3つの見出しと、着手しない2つだけを書き、終了コードに触れません。「判定できない」の語を含むので多くの読み手は止まりますが、見出しの形が違います
- **直し方の向き**: `--intake` の分岐で例外を捕まえて `[判定できない]`(4)を出す。手順に「終了コードが 0 でなければ着手しない」を足す
