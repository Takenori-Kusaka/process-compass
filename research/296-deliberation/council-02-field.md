## 1. 立場と、全体の見立て

1. **現場で規定が守られない最大の理由は、値の大小ではなく、数える主体が担い手自身か、数えていないかである**。自己修復の回数は担い手の申告である。AI起因の手戻り率は、行が AI の生成かを識別できず、テンプレートに集計が無い。運用メトリクスは週次の集計ジョブが無く、表の 25 行(三識を含む)はどれも自動では集計されていない。値の妥当性を論じる前に、**機械が観測していない数を規範の合否に使っている箇所を外すか、観測させる**。これを本 Issue の第一の軸にする
2. **形骸化の危険が大きいのは「人の再操作を日常にする」設定である**。全 push の承認の失効と strict の組み合わせは、小規模チームで PR が並行するたびに再承認を要する(GitHub の挙動は調査 2 の一次文書の要約に依る。実機は未確認)。再承認は、集約が本文の無い再承認を前の要約で数えるため、**読まずに押す操作へ劣化しやすい**。ただし失効を緩めると、承認と内容が切れる。緩める方向ではなく、**束縛を規範に書き、差分が同一であることを機械が確かめた場合だけ引き継ぐ**方向で解く
3. **全体の行カバレッジで遮断する既定は、既存のコードに入れる採用組織で恒常的な失敗を生み、基準値の引き下げか除外設定へ流れる**。本文の目安(新規コード)と K-8 の「範囲を記録」に、テンプレートの既定を合わせる。ratchet は採らない。分母の小さい差分の揺れは K-8 が下限を置かないと決めたので、揺れは分母の表示で読み手に渡す
4. **新しい義務・指標・比例の抽出は、1〜5 名のチームでは担い手がいない**。監査の抽出を変更件数に比例させると、AI で変更件数が増えたチームほど監査が流し読みになる。バックログの純増を指標にすると、AI が見つけた後続を起票しない圧力になる。どちらも課さないと明記する
5. **値そのもの(80%・3 回・5 倍・10 名・14 日・30 件・20 件)は、利用者の分布が無い以上、動かす材料が無い**。動かさずに根拠水準マークを付け、差し替え条件が名指しする観測を**集約が実際に出す**ようにする。出ていない観測を差し替え条件にした暫定マークは、見直し日に何も起きない

## 3. 論点ごとの詳細

### L-1 カバレッジの遮断(T-07)

**判定: 採る(範囲の既定を変更で加えたコードへ)。ratchet は課さないと明記する。**

現場の見立て。

- テンプレートは全体の行の割合で遮断する(`T:scripts/gate/coverage-check.mjs` L17・L62-64)。新規のリポジトリでは全体と新規が一致するので困らない。困るのは既存のコードへ導入する場合で、全体が 80% に届かない限り、どの PR も落ちる。現場で起きることは 2 つしかない。基準値を下げる(機能と別の変更・技術判断者の承認、`DG` L120)か、測定の対象から外す(`c8 --include` の範囲を狭める)。どちらも「通る」ためだけの変更で、`GC` L1617 が自ら書いた「閾値の意味が失われます」そのものである
- 本文の目安は「新規コード 80%」で、K-8 は範囲を企画時に記録させる。テンプレートの既定が全体である限り、採用組織の大半は既定のまま走り、本文の目安は読まれない。**既定が規範を決める**のが現場の実情である
- 未達の代償措置 ci-strict で導出値が 90% に上がる(`T:scripts/init/generate-profile.mjs` L662)。これが掛かるのは G-6 未達の体制、つまり 1 名体制である。全体 90% は、1 名で既存のコードを抱える現場に最も重い

採る案(7-A を基本に、7-B の選択を残す)。

- テンプレートの既定の範囲を「変更で加えたコード」にする。構成 `ci.coverageScope: added | whole`(既定 added)。結果の JSON に `scope`・`pct`・`covered`・`total`(分母)・未被覆の行(ファイルと行番号の上位 N 件)を出す。全体の割合は観測として常に併記する
- 実装の当て: python の `coverage.json` は行単位の実行・未実行を持つ(coverage.py の JSON の既知の形式。テンプレートで出るかは未確認)。node は c8 に `--reporter=json`(coverage-final.json)か lcov を足す。`git diff --unified=0 <基底>...HEAD` の追加行と突き合わせる。go・none・undetermined は #330 の範囲で、ここでは触らない
- 先に直せるもの: 全体の範囲でも、分母は既に読んでいる(`coverage-check.mjs` L41)。範囲と分母を結果に書くことは差分の実装と独立に直せる。IMPL-0246(集約が取り込まない)は証跡の保管の別 Issue と重なるので、本 Issue では IMPL-0245 だけを `delivered` へ動かす

### L-2 承認の失効(T-09)

**判定: 採る(規範を本文へ)。自己申告の分類による持ち越しは課さないと明記する。**

現場の見立て。

- `team.json` は `dismiss_stale_reviews_on_push`・`require_last_push_approval`・strict を持つ(Python で読み出して確かめた)。2〜5 名で AI の PR が並行すると、1 本をマージするたびに他の PR が古くなり、strict が基底の取り込みを求め、取り込みで承認が失効する(失効の挙動は調査 2 の要約に依る)。同じ PR を何度も承認し直すことになる
- 集約は、本文の無い再承認を直前の承認の要約で数える(`aggregate-evidence.mjs` L674)。テンプレートが再承認を軽くしているので、現場では再承認は「ボタンを押すだけ」になる。**負担そのものより、再承認が読まない操作として習慣化することが形骸化**である
- 一方、`checks-only.json` には pull_request の規則が無い。G-6 を未達・簡略にした体制(1 名体制が典型)では、外部の確認者が承認した後に AI が push しても、承認はそのまま残る。集約は承認の版と取り込んだ版を比べない(`lastReviewStates` は状態だけで数える)。**1 名体制こそ、外部の確認者の承認の後に担い手が手を入れる経路が開いている**
- `adoption-trial.mjs` L1317-1322 は `regulated`・`safety` のときだけ失効の設定を確かめる。現場の大半が使う `team` では確かめない

採る案(9-A に、機械の同一だけを引き継ぐ形を足す)。

- `GC` G-6「承認を独立した人の確認に数える」の表に条件5 を足す: 「5 | 承認が、取り込んだ版の差分に対するものである | 数えない。承認の後に差分を変える変更が加わった場合、その承認を数えない。差分が同一であることを機械で確かめられる場合(基底の取り込みだけで、変更の差分が一致する場合)に限り、承認を引き継いでよい」。文末は「数えない」(表の他の行と同じ形)と「引き継いでよい」(許容)
- 箇条に足す: 「承認の後の変更が差分を変えないことを、作成者・担い手の申告や変更の種類の分類で認めてはなりません」(〜してはならない)
- 強制層: ルールセットは全 push の失効のまま変えない。マージの時点で止まるのは強制層だけであり、集約は出荷の時点で働く(`git-strategy.md` の説明と同じ弱さ)。引き継ぎは集約の側の数え方として実装し、`checks-only` でも働く。実装マーク `target=evidence-aggregation state=undelivered`(レビューの API が承認時の commit を返すかが未確認のため、実装の段で確かめる)
- `team` の実環境の確認(`adoption-trial.mjs`)と契約検査(`verify-gate-contract.mjs`)で `dismiss_stale_reviews_on_push` を確かめる。`adoption-guide.md` L489 と `template-repository.md` L330 の列挙をそろえる
- 再承認の負担は、規範を緩めずに手段で下げる。merge queue(基底の取り込みを担い手の PR に求めない)を `git-strategy.md` に選択肢として書く。ただし GitHub の merge queue が承認を保つか、利用できるプランは確かめていない(先送りの材料として書く)

挙動要約の引き継ぎ(発見 8)について: 差分が変わった後の再承認に、前の版の要約を引き継がせるかは決めておく必要がある。私の案は、**条件5 で数えない承認の要約は引き継がない**(集約の L674 の引き継ぎを、差分が同一の場合に限る)。差分が変わったなら、要約は新しく書く。1〜2 文であり、読まずに押す操作を止める最も安い歯止めである。これは他の委員に問う(4 章)。

選ばなかった案。

- 9-B(差分の木・patch-id の一致で失効させない、ルールセットの失効を外す): マージの時点の止めが消え、集約の出荷時点の検出に移る。統制の弱化であり、ADR-0073 決定6 の陰性の確認を要する。私の案は強制層を残したまま、数え方の側で同一だけを引き継ぐので、弱化に当たらない
- 9-C(粒度の緩和を認めないとだけ書く): 本文に束縛の規範が無い欠落と、`checks-only` の穴が残る
- 9-D(先送り): API の確認は実装の段で足りる。規範の欠落を、実装の確認待ちで残す理由にならない
- Gerrit 型の「変更の種類」による持ち越し: 種類の分類を誰が付けるかが問題になる。AI の担い手が付ければ申告であり、ADR-0073 決定1 が退けた「分類で閾値を外せる」と同型になる

根拠水準: 束縛の規範は構造の不変条件の書き出しで、EV は付けない。引き継ぎの条件(差分の同一)も機械の判定で、実証の主張ではない。

### L-3 自己修復の反復の停止(T-08)

**判定: 採る。規範を本文へ置き、回数と「同一」は機械が数える。**

現場の見立て(発見 1)。

- 今のテンプレートでは、回数は担い手の申告である。`iterate` を呼ばずに直し続ければ上限は来ない。`start` を呼ばなければロックも無い。止まるのは、担い手が手順(`SKILL.md`)どおりに自分の回数を数えた場合だけである
- 依頼の「総数でなく同一の失敗の連続で」を、申告の上でやれば、担い手は失敗の表示を変えるだけで連続を切れる
- 現場で見えている失敗の形は、同じテストを落とし続ける場合と、直すたびに別のテストを落とす場合(もぐら叩き)の 2 つである。後者は「同一の連続」では止まらない。総数の上限は外せない

採る案(8-C + 8-A、ただし数えるのは機械)。

- 本文: 5.8.5(禁止事項3 の節。IMPL-0187 の置き場)の後に置く。「自動検証の失敗を担い手へ入力して修正させる往復は、組織が定めた回数で止めなければなりません。上限に達したら保留とし、人が受入基準へ戻るかを判断します。回数は、担い手の申告ではなく、検証の実行の記録で数えなければなりません」。回数の初期値は 3、登録簿 RC-05 のまま
- 「同一の失敗の連続で早く止めることができる」(許容)を本文に置く。「同一」は、失敗したテストの識別の集合が一致することとし、担い手の判断で同一・別を決めてはならない
- テンプレート: `iterate` が `adapter.mjs run test` を実行し(`stop --reason pass` と同じ)、通れば `pass` で終える、落ちれば失敗したテストの識別の集合をロックに記録し、総数が N に達するか、同じ集合が 2 回続いたら保留にする。識別の集合はスタックごとに出力形式が違う(node test・pytest)。取れないスタックでは総数だけで止め、その旨を出す
- 限界の開示: `start` を呼ばない自己修正はロックの外であり、止まらない。遮断も効かない。これは機械では止められないので、本文の規範の実装マークに `note` で書く(`state` は 2 段階。総数と記録は `delivered` にできたら、`start` の外は限界として開示する)
- E.7(参考)を直す: 「同じ失敗を3回繰り返す場合、原因は実装ではなく受入基準の不備であることが多い」は頻度の主張で根拠が無い。「同じ失敗が続く場合は、受入基準の不備を疑います」へ改める。「第7章 7.7.2 の指標へ算入」は行き先が無い(発見 7)。7.7.1 の AI 実行予算の消化へ含める、と行き先を直す。反復の記録の置き場(`.claude/self-heal.log` は追跡されない)は、テンプレートでは保留の記録を受信箱のラベルの記録に残すことで足りる

根拠水準: 3 回は E1(調査 2: 関数単位のベンチマークで改善は最初の 2〜3 回に集中。リポジトリ規模の作業への外挿は未検証)。EV を RC-05 の本文の置き場に付け、見直しは EV-0089 と同じ 2027-04。差し替え条件: 採用組織の保留の件数と、保留から受入基準の修正に至った件数の比、保留の手前で通過した反復回数の分布(テンプレートが記録を残すことが前提)。同一の連続 2 回は 7.9.1 の型(EV-0064、E1)にそろえた値で、E0 として同じ EV に含める。

選ばなかった案。

- 8-B(総数を外して同一の連続へ置き換える): もぐら叩きが止まらず、費用の歯止めが消える
- 8-D(有限であることだけを求め、形を課さない): 有限を誰が数えるかを決めないと、申告で終わる。本 Issue の核心はそこにある
- 8-E(先送り): 「同一」の比較の方法は、取れるスタック(node・python)では取れる。取れないスタックは総数だけで止めると書けば、先送りの理由にならない
- 附属書E のまま手引きにする: ADR-0076 決定7 で実装マークを置けず、テンプレートが止めている理由が本文に無い状態が続く

ADR-0073 決定1 との関係: 決定1 は是正・機械の検査への移行を件数で起動する義務を退けたもので、ループの停止条件ではない。ただし「分類は申告で決まり、閾値は分類で外せる」という論法は、同一の判定にそのまま当たる。だから同一を機械の集合の一致に限る。矛盾はなく、新 ADR は要らない(本 Issue の ADR に関係として書く)。

### L-4 手戻り率(S-11)

**判定: 合否化は課さないと明記する。名称を分ける案を採る。**

現場の見立て。

- 行が AI の生成かは、コミットのトレーラでしか分からない。AI を多用するチームでは、ほぼすべてのコミットに AI のトレーラが付き、人が直した行も AI のコミットに入る。squash で 1 コミットになる。**行の帰属は推定ですらなく、ほぼ全行が分母になる**
- 14 日以内の書き換えは、速い反復では常態である。AI と小さい PR を回すと、昨日の実装を今日直すのは手戻りでなく前進である。これを出荷判定の合否にすると、書き直しを避ける、つまり改善を翌々週へ遅らせる動機になる
- テンプレートに集計は無い(調査 1)。合否条件にしても、現場は計算できず、G-1 に閾値だけ書いて傾向も見ない。印だけの規定になる

採る案(11-A + 11-C)。

- `GC`「指標の定義」: 「AI起因の手戻り率」を「AI起因の短期書き換え率」に改める。定義は同じ。窓 14 日・母数の下限 30 件・観測窓 四半期に EV(E0。差し替え条件: 窓の長さを変えた場合の値の安定性の観測、2 四半期の実測)。母数の下限の単位を「期間内に AI が生成した行を含む変更の件数」と書き、行の比率と件数の下限の単位の関係を明記する
- 「合否条件にしてよい指標」の表: 行を「**合否条件にしてはならない**。傾向の確認に留める」へ改め、理由を一発承認率と並べて書く。「行の帰属はコミットの単位でしか取れない」「短期の書き換えには、速い反復の通常の修正が含まれ、合否にすると修正を遅らせる」
- 委託契約で定量の指標を求められる場合は、この量を名称と定義を併記して報告に使うことは妨げない(既存の「独自の指標名」の規定のまま)
- 「手戻り率」の参照先を 1 つずつ定める: `MT` 分類別の表の「手戻り率」(PR の差し戻し比率+やり直し件数)を正とし、5.4.6 の検知条件の「手戻り率」はこれを引く。三識の「短期の手戻り率」は、第4章の「AI起因の短期書き換え率」を引くと書く(発見 2)

選ばなかった案。

- 11-B(条件を足して合否化を残す): 自動集計・行の帰属・対の指標の 3 つを G-1 で満たせる現場は、私の知る範囲では無い。満たせない条件を並べた合否化は、条件を満たした記録だけを作らせる
- 11-D(定義を持たない): 委託契約の現場では「AI の品質を数字で」と求められる。定義が無いと、各社が名だけ同じ別の量を出す。定義を残し、合否から外すほうが混乱を減らす
- 11-E(先送り): 外部の一次資料(SPACE)は活動の指標の合否化を否定し、合否化を支持する資料は見つかっていない(調査 2)。窓の出典は未確認だが、合否から外す判断には要らない

根拠水準: 合否から外す判断は、測れない量を合否に使わないという構造の判断で E1(SPACE・DORA の記述的利用、調査 2 の一次)。

### L-5 監査の抽出(S-23)

**判定: 比例は課さないと明記する。単位の定義を採る。**

現場の見立て。

- 1〜5 名のチームでは、内部監査は外部か、案件に関与していない少数の人が担う。四半期に 5 件以上を読むのが帯域の上限に近い
- 比例させると、AI で変更が週に数十件になるチームほど抽出が増え、監査が流し読みになる。`PA` L63「全件の点検は監査の側の帯域を超える」と同じ問題が、比例でも起きる
- 「件」の単位が無い。リスクに基づく条件は「案件」で書かれている(`PA` L72-78)。案件が 1 つしかない小さな組織では、案件の条件はすべて同じ案件を指し、リスクに基づく抽出が意味を持たない

採る案(23-C + 23-B)。

- `PA`「頻度は四半期を既定とし、1回あたり5件以上を抽出します」の前に: 「抽出の単位は変更(PR、または PR を経ずに既定ブランチへ入ったコミット)とします」。リスクに基づく条件は「…を適用した変更、またはその変更を含む案件」と変更の単位でも読めるように書き直す
- 「本標準は、抽出数を変更の件数に比例させることを課しません。抜き取りの目的は形骸化の検知であり、ゲートの代わりではないためです。抽出数は、[運用メトリクス]の較正により、組織が監査の記録から定めます」
- 監査記録に「母集団、抽出の方法、件数、選んだ根拠」を書かなければならない(ISO 19011 附属書 A.6 の型。二次資料)。既にある記録の様式に欄があるかは確かめていない。あれば参照に留める

選ばなかった案。

- 23-A(比例): 統計的には母集団が大きいほど比率は下がり(AS 2315、ISO 2859-1、IAF MD 1 の平方根則。調査 2)、主要な規格に比例の流儀は無い。現場では帯域を超え、流し読みを生む

### L-6 10 名の境界(S-16)

### L-8 PR 分布の実測と規模の算定

**判定: 実測は先送り。集約の出力の拡張と匿名の書き出しを採る。5 倍は動かさない。**

実測。

- 本プロジェクトは利用者のデータを持たない。先送りの記録に足りないものを書く: 採用組織の集約の出力(行数・ファイル数の分布、超過の理由の内訳、別集計の倍率の分布)を 3 組織分
- そのために、**集約が差し替え条件の観測を出すこと**を先にする(PR-C)。EV-0084 の差し替え条件は「別集計が基準の数倍を超えた PR の件数」を名指しするが、集約は別集計の合計しか出さない(調査 1)。出ていない観測を差し替え条件にした暫定マークは、2027-04 に何も差し替えられない
  - `sizeObservation` に、超過の理由(行数・ファイル数・別集計)の内訳と、別集計の倍率(別集計の行数 ÷ 基準行数)の 4 区間(〜1・1〜2・2〜5・5 超)を足す。`measureCommitSize` が真偽値だけを返す箇所(L740)を、理由を返す形へ変える
- 匿名の書き出し(PR-B の軽い形): 集約が規模の観測だけを、パス・名前・PR 番号を含まない JSON に書き出す。提出は採用組織の任意で、本プロジェクトの community 頁に提出の方法を書く。**採用組織に義務を課さない**。これが無ければ、標準の E0 の値は採用組織が何年使っても E0 のままである

5 倍。

- 下げない。AI のエージェントの PR はテストを同梱する割合が上がり、テストを含む PR の行数は大きい(調査 2、arXiv 2601.03556。プレプリント)。2〜3 倍に下げると、テストを丁寧に書く AI の PR が常に size:over になり、R2 へ上がり、規模の確認が「テストなので」の定型文になる。テストを同梱する行動を罰する
- 抜け道(テストのパスへ製品のコードを置く)は、5 倍までは開いている。これは限界の開示に既にある。上の倍率の分布を出せば、2〜5 倍の帯に PR が集まるかで抜け道の利用を観測できる

`CODE_EXTENSIONS`。

- 文書の置き場の中の判定を反転する: 文書の置き場(`DOC_ONLY_DIRS`)の中では、文書・データの拡張子(`.md`・`.mdx`・`.txt`・`.rst`・`.adoc`・画像・`.pdf`・`.json`・`.yaml`・`.yml`・`.csv`)以外を製品のコードとして数える。拡張子の無いファイルは先頭行の shebang で判定する(Linguist と同じ手筋、調査 2)。`evidence/` は `.gitignore` にあり、通常の PR には現れないので反転しても文書の PR の誤検出は増えない
- `GC` 限界の開示を実装に合わせて直す(発見 6。誤りは本文の開示の側。反転の後は、開示を「文書・データの拡張子として登録したもの以外は数える」へ改める)

ファイル数だけの超過。

- 現状のまま(行6 で size:over、規模の確認を要する)。AI は広く浅い機械的な変更(名前の変更、import の書き換え)をよく作る。30 ファイルに散る 60 行は、レビュアが最も流し読みする形である。「読み切れたか」を問う意味がある
- 「行数が基準値の 1/4 以下なら軽くする」は採らない。値は機械で判定できるが、1/4 に根拠が無く、名前の変更に紛れた 1 行の挙動の変更を拾う機会を減らす。「機械的な変更」の自己申告で軽くする経路は、課さないと明記する
- ただし行6 の「確認の記入以外の合否に使わない」と、行1 の「区分の下限を R2 へ引き上げる」の関係が読めない。テンプレートは R2 へ上げる。行6 に「区分の下限の引き上げ(行1)は、ファイル数の超過にも掛かる」と書き、合否に使わないのは「規模の確認の記入の内容」であると明確にする。#295 の骨格 D1(観測のみ)は本文が正、という調査 1 の判断に同意する

`/pit` の注記。

- 採る(テンプレートの手引き。本文の規範にしない)。PR を作る前に分割できれば、レビューの後の分け直しという手戻りが最も安く減る。現場で最も効く項目である。`next.mjs` が作業ブランチの差分を `check-pr.mjs` と同じ算定で測り、基準値の 8 割を超えたら「分割を検討。超えるなら規模の確認の欄を人へ」と注記する。8 割は E0 で、手引きなのでマークは要らない

選ばなかった案。

- PR-D(起草者が分布を集めることを課さないと明記する): 匿名の書き出しは義務ではなく、課さないと書く必要は無い。書くと、データを得る唯一の経路を閉じたように読める
- 倍率を下げる: 上のとおり
- 拡張子を足すだけ: 新しい拡張子のたびに漏れる。拡張子なしは閉じない

### L-9 名義と宣言

**判定: 採る(4 件)。前回比は先送り。**
