## 1. 立場と、全体の見立て

1. **本 Issue の定数の多くは、値より先に「数えたことの記録」が欠けている**。カバレッジは測った範囲が記録と一致するかを誰も見ない(発見3)。自己修正の反復は担い手の申告で数え、記録は端末から出ない(発見1・2)。承認は承認した版を見ずに数える(L-2)。監査の抽出は母集団を記録しない(L-5)。手戻り率は行の帰属を確かめる手段が無いのに合否に使える(L-4)。**値を較正する前に、値が実態を映す経路を閉じる**のが監査の側の順序である
2. **「承認は承認した版に束縛される」は G-6 の規範として置く**。いま束縛を担っているのはルールセットの設定値だけで、ルールセットの無い構成(`checks-only`)と管理者の迂回(ADR-0077)では、集約が承認と取り込んだ版を比べないため、古い承認がそのまま「独立した人の確認」に数えられる。束縛の粒度の緩和(持ち越し)は、判定を機械が行える場合に限って将来検討する(先送り)
3. **申告で外せる条件・申告で数える計数を新しく足さない**。自己修正の「同一の失敗」を担い手の記述で判定する案、ファイル数の超過を「機械的な変更」の申告で軽くする案、承認の持ち越しを「些末な変更」の申告で認める案は、すべて ADR-0073 決定1・ADR-0044 決定4 と同じ理由(分類は申告で、閾値は分類で外せる)で落とす。足すなら、機械が自分で観測した値(テストの実行結果・差分の一致)に限る
4. **差し替え条件が観測できない EV は、暫定のまま固定される**。EV-0084 は「別集計が基準の数倍を超えた PR の件数」を差し替え条件に名指しするが、集約はそれを出さない。PR 分布の実測を先送りするなら、少なくとも採用組織の手元で差し替え条件の観測が出る状態にしておかなければ、見直し日(2027-04)に何も判断できない
5. **比例の抽出、ratchet、バックログの純増の対の指標は、いずれも課さないと明記する**。比例は主要な監査規格に支持が無く(調査 2)、ratchet は前期の実績を次期の基準にする形(`MT`「実績を基準へ機械的に変換しない」)、純増は起票を控える圧力を生む(ADR-0074 決定8)。いずれも、覆す新しい材料が調査に出ていない

### L-1 カバレッジの遮断(T-07)

**判定: 採る(範囲の一致の確認と記録)。ratchet は課さないと明記する。80%・90% に暫定マークを付ける。**

監査の問いは「基準値以上」の記録が何を示しているかである。K-8 で、基準値は測る範囲とともに記録すると決まった。ところが今のテンプレートでは、次の 3 つがそれぞれ別の場所にあり、互いを照合しない。

- 企画時に記録した範囲(K-8 の記録。テンプレートにはまだ置き場が無い)
- 構成の基準値(`ci.coverageThreshold`、既定 80、ci-strict で 90)
- 実際に測った範囲(node は `package.json` の `c8 --include`、python は `pyproject.toml`・`.coveragerc` の `omit`)

3 つめは製品のコードと同じ変更で変えられる(`.coveragerc` は python の `thresholdFiles` に入るが、`package.json`・`pyproject.toml` は入らない。`check-pr.mjs` L73 の開示)。`--include` を狭めて分母から未テストのファイルを外せば、全体の割合は上がる。K-8 の記録は「全体」のまま正しく見える。**これが本論点で最も大きい記録と実態の食い違いの経路である**。

採る案(7-B を基にし、照合を足す):

1. 構成に範囲を置く(`ci.coverageScope: whole | added`)。結果の JSON に `scope`・`denominator`(測定の対象の行数)を書く。ここまでは今の `coverage-check.mjs` に書き足せる。IMPL-0245 のうち「範囲と分母を記録する」部分は `delivered` へ動かせる
2. **測っていない製品のコードを数える**。`coverage-check.mjs` は既に `productFiles()` を持つ。istanbul の要約(`coverage-summary.json`)はファイルごとの項を持つ。製品のコードのうち要約に現れないファイルの件数を結果に出し、1 件以上あれば通知する。`scope: whole` を名乗る結果で測っていない製品のコードがあるなら、範囲の名乗りが偽であるため失敗させる(#286 の「測定対象 0 行で製品のコードがあれば失敗」と同じ論理の延長)
3. 契約検査が、企画時の記録の範囲と構成の範囲の一致を確かめる。記録の置き場はテンプレートの企画書の様式の欄に置く(置けなければ `undelivered`)
4. 変更で加えたコードの範囲(`added`)は、行の情報と `git diff` の追加行の突き合わせが要る。node 以外の行の情報は調査 1 が確かめていない。IMPL-0245 を分け、`added` の実装を新しい IMPL で `undelivered` として表示し続ける。既定の範囲は全体のままにするが、**結果と保証の開示に「全体」と書き、標準の目安(新規コード)ではないことを読ませる**

文の案(`GC` 基準3 の小節「カバレッジの測る範囲と規模」に足す):

- 「測る範囲を、製品のコードを測定の対象から外すことで狭めてはなりません。測定の対象に現れない製品のコードがある場合、その件数を G-5 の結果に出します。コードの全体を測る範囲として記録した基準値で、測定の対象に現れない製品のコードがある場合は、基準3 を満たしません」
- 「測定の対象を定める設定(対象・除外のパターン)は、基準値と除外設定の変更(前掲)に当たります」— これにより、同じ PR で製品のコードと測定の対象を変えることが禁止事項6 の対象になる。テンプレートが `package.json` の中の設定を検査できない限界は、今の開示(`check-pr.mjs` L73)を本文の限界の節へ写す

`GC` L1603・L1615-1617 と K-8 の食い違い: **誤りは L1603・L1615-1617 の側である**。K-8(ADR-0078 決定6)は後から明示的に決めた規範で、全体を選ぶ案件を認めている。L1603 の「新規に変更した範囲に限定した機械判定(G-5 の基準)」は、G-5 の基準のすべてが新規の範囲に限られるかのように書くが、基準7(秘匿情報)などはそうでない。L1615-1617 は「全体の絶対値を条件にすると恒常的に不合格」という理由を述べており、K-8 の範囲の選択の判断材料として残す価値がある。直し方: L1603 の行を「G-5 の基準(基準3 は、企画時に記録した範囲で)」へ改め、L1615-1617 を「基準3 の範囲を全体にすると、既存の負債で恒常的に不合格となりうる。範囲は G-5 基準3 の小節により企画時に決める」と、K-8 へ従属させる。あわせて節の適用範囲を見出しへ移す(発見8)。

ratchet(7-C): **課さないと明記する**。理由は 3 つ。

- `MT`「実績を基準へ機械的に変換しない」規定1・2 に当たる。基準値を書き換えない形(基底の測定値との比較だけ)でも、前期の実績が次期の合否を決める構造は同じである
- 基底の測定値は、誰かが書き、どこかに保存する値になる。その値の書き換えは閾値の変更と同じ統制を要するが、今の置き場(`evidence/` は `.gitignore`、成果物は保持期限つき。K-7)では改ざんも消失も検出できない。**ratchet の合否は、守られていない記録に依る合否になる**
- 外部の実務では、削除で見かけ上の割合が上がる(調査 2 の二次資料)。全体の割合の ratchet は、未テストのコードを消すか測定の対象から外す向きに働き、上の経路 1 と同じ食い違いを生む

文の案(`GC` 基準3 の小節の末尾): 「本標準は、基底の測定値を下回らないこと(ratchet)を合否の条件に課しません。前期の実績を次期の合否の基準にする形であり([運用メトリクス](/process-compass/phase6-operation/metrics/)「実績を基準へ機械的に変換しない」)、基底の測定値を統制の設定と同じ水準で保管する手段を本標準は定めていないためです」

80%・90%: 80% に暫定マーク(EV-0143、E1 間接: 外部の実務の既定値 Sonar way の新規コード 80%、Google の任意の段階。実証ではない)。見直し 2027-10。差し替え条件: 範囲・分母つきの G-5 の結果を集めた採用組織で、基準値の前後での出荷後の欠陥・変異スコアの差。90% は**本文に値が無い**。軸C「高」と未達の代償措置は「引き上げ」とだけ書く(`TG` L505・L843)。テンプレートの 90 は標準の値ではなくテンプレートの既定であると `template-repository.md` に書き、RC-06 の名称を「カバレッジの下限(80%。強める構成でテンプレートは 90%)」へ改める。本文に 90 を書き足すことは採らない(数値の根拠が 80 以上に無い)。

選ばなかった案:

- 7-A(差分を既定にする): 方向は標準の目安と合うが、node 以外で行の情報が出せるかを確かめていない。既定を実装の無い範囲にすると、未実装の範囲で「通過」が出る。`undelivered` で表示し続けるほうが記録が正しい
- 7-D の後半(全体を遮断に使う既定を推さないと書く): 全体を選ぶ案件は K-8 で認めた。推さないと書くと K-8 と食い違う
- 7-E(マークだけ付けて先送り): 範囲の食い違いの経路が残る。マークは値の根拠を開示するが、測った量が記録と違う問題は開示しない

### L-2 承認の失効(T-09)

**判定: 採る(G-6 の規範と、集約による照合)。粒度の緩和(持ち越し)は先送り。**

確かめた事実:

- G-6 の 4 条件(`GC` L725-730)と箇条(L735〜)に、承認がどの版に対するものかの条件は無い
- 束縛は `pr-workflow.md` L196 の手順と、ルールセット `team`・`safety`・`regulated` の `dismiss_stale_reviews_on_push`・`require_last_push_approval` にだけある
- `checks-only.json` は `pull_request` の規則を持たない。G-6 が未達・簡略化の構成(1 名体制で外部の確認者に頼る構成を含む)では、外部の確認者が承認した後に作成側が何を push しても、その承認は残る
- 集約の `lastReviewStates` は GitHub の状態だけで数え、取得する項目(`PR_FIELDS`)にレビューの commit を含めていない
- 管理者はルールセットを迂回できる(ADR-0077)。迂回してマージした PR の古い承認も、集約は数える
- `verify-gate-contract.mjs` は `require_last_push_approval` だけを見る。`adoption-trial.mjs`(env-check)は `regulated`・`safety` でだけ dismiss と last push を見る

監査の観点では、**「独立した人の確認を経た」という記録と、確認された版と取り込まれた版の一致という実態が、ルールセットの設定値によってしか結びついていない**。設定値が無い・迂回された構成では、記録は実態と食い違ったまま出荷の開示に載る。#295 の懐疑役の分類(束縛は構造の不変条件 A)に同意する。

文の案(`GC` G-6 の表に条件5 を足す):

| # | 条件 | 満たさない承認の扱い |
| --- | --- | --- |
| 5 | 承認の対象の版が、取り込んだ版と同じである | 数えない。「承認の後に変わった版を取り込んだ」として、独立した人の確認を経ていない変更に計上する |

箇条に足す文:「承認は、承認した版に対するものとして数えなければなりません。ルールセットが承認を失効させる構成でも、出荷の集約は、承認の対象の版と取り込んだ版を比べます。ルールセットの設定は、この比較に代わりません(管理者は迂回できる。[ADR-0077](/process-compass/adr/0077-repository-ci-wiring-and-distribution/))」

比べ方: 承認の commit と、マージした PR の最後の commit(squash の前の先端)の一致。一致しない場合でも、両者の間の PR の差分が同一であると機械が確かめられる場合(先端どうしの差分の木の比較)は、将来の持ち越しの論点として先送りする。今回は**一致だけを数える**。

実装マーク: 集約の照合は IMPL-0259 で付け、`gh` が承認の commit を返すことを確かめて実装できれば `delivered`、確かめられなければ `undelivered`。契約検査と env-check が、`pull_request` 規則を持つすべてのルールセットで `dismiss_stale_reviews_on_push` と `require_last_push_approval` を確かめる(`team` を含める)。`adoption-guide.md` L489 の要件⑦の列挙に「push で古い承認を無効にする設定」を足し、`template-repository.md` L330 と揃える(誤りは `adoption-guide.md` の列挙の欠落)。

粒度(全 push 失効):

- **持ち越しは先送り**。足りない材料: (a) 基底の取り込み(Update branch)と `strict` の組み合わせで再承認が何回生じているかの実測(上の照合を入れれば、集約が「承認の後に版が変わった件数」と「その後に再承認された件数」を出せる)、(b) 差分が同一であることを機械で判定する方法(Gerrit の `TRIVIAL_REBASE`・`NO_CODE_CHANGE` はサーバが判定する。GitHub には同等の機能が無い)。**持ち越しを採るとしても、判定は機械が行う形に限り、作成者・承認者の「些末な変更」の申告では認めない**と、今の時点で ADR-0079 に書く
- 9-B(ルールセットの失効を外して集約へ移す)は採らない: マージの時点で止まらなくなり、検出が出荷の時点まで遅れる。統制の弱化であり、ADR-0073 決定6 の陰性の確認の負担に見合う利点が示されていない
- 9-C(緩和を一切認めないと明記する)は採らない: 機械が差分の同一を判定できる場合まで閉じる根拠は無い。先送りとして「何が足りないか」を残すほうが正確である
- 9-D(全体の先送り): 規範の欠落は材料の不足ではない。`checks-only` で古い承認が数えられる事実は、今の記録で確かめられる

根拠水準: 条件5 は承認の定義から導く構造の規範で、EV は付けない。GitHub の失効の挙動を本文に書くなら E1(一次文書の要約)で開示する。

### L-3 自己修復の反復の停止(T-08)

**判定: 採る。規範を本文へ置き、総数の上限を残し、同一の失敗の早期停止を機械の観測に限って足す。反復と保留・解除の記録を追跡される場所へ残す。**

確かめた事実(発見1・2): 計数は担い手の申告で、記録は追跡から外れ、解除の名義は照合されない。E.7 は参考の附属書であり(`DG` 冒頭「適合の条件に数えません」)、本文に反復の上限の規定は無い。ADR-0076 決定7 により E.7 に実装マークを置けないため、テンプレートの停止は「規範の無い強制」になっている。

監査の観点の帰結:

- 停止という構造(有限回で止め、人が受入基準へ戻る)は本文の規範にしなければ、実装マークで追跡できず、未達の表示もできない
- 「同一の失敗」を担い手が判定する形で足すと、失敗の表示を変える・テスト名を変えるだけで連続が切れる。申告で外せる閾値である(ADR-0073 決定1 と同型)。**機械が自分で実行したテストの結果から、失敗したテストの識別の集合を取り出して比べる**形に限る
- 総数の上限を外す 8-B は、違う失敗が交互に続く場合に止まらない(OpenHands は交互のパターンを別に検出している。調査 2)。費用の歯止め(E.7 L133)も失う

文の案(第5章 5.8.5 の禁止事項3 の直後。規範):

- 「自動検証の失敗を AI に入力して修正させる往復は、組織が定める回数(初期値 3 回)で止め、人が受入基準と分割を確かめるまで再開してはなりません」
- 「往復の回数と停止・再開の記録は、修正を行う担い手の申告によらず残し、変更の記録から辿れる場所に置かなければなりません。停止を解く者は人であり、その記名を記録します。AI の名義の記録は数えません」
- 「同じ失敗が続く場合に早く止める条件を定めるときは、失敗の同一を、検査が出力した失敗の識別から機械で判定します。担い手の説明で同一かどうかを決めてはなりません」(望ましい、ではなく条件つきの義務。早期停止そのものは課さない)

テンプレート(実装マーク IMPL-0260〜):

- `iterate` がテストを自ら実行し(`stop --reason pass` と同じ `adapter.mjs run test`)、失敗したテストの識別を記録する。直前と同じ集合が 2 回続いたら保留(既定 K=2。7.9.1 の「連続 2 回」の型)
- 記録を `.claude/self-heal.log` から追跡される置き場へ移すか、PR の本文・判定記録に保留と解除の要約を写す。どちらもできなければ `undelivered`
- `release --by` の名義を名簿の人に対応づけ、`aiNameReason` に当たる名義を拒否する
- 限界の開示は残す: ロックを始めずに修正を続ける経路は機械で止められない(SKILL.md L80 と同じ)

E.7 は手引きとして残し、本文を引く形にする。**E.7 L130「同じ失敗を 3 回繰り返す場合、原因は受入基準の不備であることが多い」は外す**。出典の無い経験則の主張で、マークを付けても「多い」を差し替える観測が定義できない。E.7 L133 の「7.7.2 の指標へ算入」は、7.7.2 に反復の指標が無いため、「7.7.2 の AI 実行費用に含める」へ改める。

根拠水準: 上限 3 回に暫定マーク(EV-0144、E1: 関数単位のベンチマークで改善が最初の 2〜3 回に集中するプレプリント 2 本。リポジトリ規模への外挿は未検証)。早期停止の K=2 はテンプレートの既定であり本文に値を書かない(書くなら E0)。見直し 2027-10。差し替え条件: 追跡された反復の記録から得た、保留に至った往復の回数の分布と、保留の後に受入基準が改められた割合。

選ばなかった案:

- 8-B(総数を同一の失敗の連続へ置き換える): 上記
- 8-D(停止の形を課さず、有限であることだけ求める): 有限の要求は採るが、計数と記録の要求を欠くと、有限の上限が申告で無効になる
- 8-E(先送り): 「同一の失敗」の比較の方法は、機械が実行したテストの識別に限れば決められる。スタックごとの出力形式の違いは実装の問題で、規範の先送りの理由にならない

### L-4 手戻り率(S-11)

**判定: 採る。合否化を外し、名称を分け、母数の規定を締める。**

合否化を外す理由(監査の観点):

- 分母の「AI が生成した行」を確かめる手段が本文に無い。トレーラはコミット単位で、人と AI が同じコミットに書いた行の帰属は推定になる。**推定に依る値で合否を記録すると、判定記録が実態を裏付けない**
- `MT` 手続3(自動集計の実装をもって採用)を満たした実装が無い(テンプレートは計算しない)。合否に使う指標が、本文自身の採用の手続を満たしていない
- 外部の一次資料(SPACE)は単独の活動指標を報酬・罰に使わないとし、合否化の支持は見当たらない(調査 2)。隣の一発承認率は既に「合否条件にしてはならない」

文の案(`GC`「合否条件にしてよい指標」の表): 「AI 生成行の短期書き換え率 | **合否条件にしてはならない**。傾向の確認に留める。行の帰属は推定であり、記録で裏付けられないため」

名称(11-C):

- 第4章の量 → 「AI 生成行の短期書き換え率」(本標準の定義である旨は今の L1587 のまま)
- 運用メトリクスの AI協調の「手戻り率」→ 分子が流れの「差し戻し率」と同じ量であるため(発見6)、**統合する**。「実装計画表の『やり直し』件数」だけを残すなら別名(「タスクのやり直し件数」)にする
- 5.4.6 の「手戻り率」→ どの定義を指すかを書く。委任の登録の `reworkRate` と、三識の「短期の手戻り率」も同じ定義へ寄せる。「重複ブロック率」は定義を置くか、対の指標から外す
- 同名の量を 4 つ並べたまま「独自の指標名を業界の標準指標であるかのように用いてはならない」(L1587)を課すのは、本文が自分の規定を守っていない状態である

母数の規定(発見5): 要求事項3 の後段を「観測窓(初期値 四半期)を定め、窓の中の件数が母数の下限(初期値 30 件)に満たない場合は、その窓の値を判定に用いてはなりません」へ改める。「または」を外す。**要求事項3 は合否化を外しても残す**。5.4.6 の第2区分(差し戻し率・重複率・手戻り率)と ADR-0059 がこの要求事項3 を引いているためである。置き場は「AI 品質指標の扱い」の節に留めるなら見出しの適用範囲に「5.4.6 の検知条件」を加える。

### L-5 監査の抽出(S-23)

**判定: 比例は課さないと明記する。単位と母集団の記録を採る。**

確かめた事実: `PA` の抽出は「1 回あたり 5 件以上」「件数が確保できない規模では四半期の全件」。リスクの条件は「案件」で書かれる。記録の表(L284-290)は「抽出した対象と抽出方法」を持つが、**母集団(何件の中から抜いたか)を持たない**。所見 0 件の期だけ「抽出した対象の一覧」を残す(L279)。

監査の観点の帰結:

- 母集団を記録しない抽出は、「全件を見た」のか「5 件だけ見た」のかを、監査の監査(外部の審査)が確かめられない。ISO 19011 A.6 の要約(調査 2、二次)は母集団・抽出基準・方法・件数・結果の記録を求める
- 「対象を当事者に選ばせてはならない」(L82)は、無作為の部分を再現できなければ確かめられない。乱数の種や抽出の手段を記録すれば、第三者が同じ抽出を再現できる
- 「件」の単位が無いため、案件を 5 件選んで各 1 変更を見ても、1 案件の 5 変更を見ても、同じく「5 件」になる

文の案(`PA`):

- 「抽出の単位は変更(PR、または PR を経ずに取り込んだコミット)とします。リスクに基づく抽出は、条件に当たる案件を選び、その案件の期間内の変更から抽出します」
- 記録の表に「母集団(期間・範囲・件数)」と「無作為の抽出を再現できる手段(用いた乱数の種、または抽出の手順)」を加える
- 「件数が確保できない規模」を「期間の母集団が 5 件未満の場合」と定める

比例(23-A)は課さないと明記する。文の案:「本標準は、抽出数を母集団の件数に比例させることを課しません。統計的な抽出では、母集団がごく小さい場合を除き、抽出数は母集団の大きさにほとんど依らず、許容する逸脱率と信頼の水準で決まります。比例は、変更の件数が増えるほど監査を全件の点検に近づけ、本節の前提(全件の点検は監査の帯域を超える)と衝突します。抽出数は、較正の適用先として、抽出方法別の所見の検出率から組織が定めます」。根拠は PCAOB AS 2315(一次)と IAF MD 1 の平方根則(一次、劣比例)。

登録簿: RC-11 を「監査の周期と抽出数」へ広げる(依らない)。AI の検査が充実したことを理由に抽出数を減らす読みを、要求事項4 で閉じるためである。事後監査の抜き取り数(EV-0004)も同じ行に含める。

選ばなかった案: 23-A(比例): 上記。23-D(先送り): 単位と母集団の記録は材料を待たずに決められる。抽出数の値そのものは EV-0010 の差し替え条件のまま残す(新しいマークは要らない)。

### L-6 10 名の境界(S-16)

**判定: 採る(暫定マーク)。能力依存の定数の登録簿には載せないと明記する。**

### L-8 PR 分布の実測と規模の算定

**判定: 実測は先送り。差し替え条件の観測は採る。個別の項目は下のとおり。**

実測(PR-A): 先送り。足りないもの: 採用組織の手元の規模の分布。本プロジェクトの PR 履歴は母集団の代わりにならない(調査 1)。値は EV-0084・EV-0089 の見直し日(2027-04)まで動かさない。

## 4. 他の委員に問いたいこと

1. **現場の委員へ**: L-2 の条件5 で、`strict` と失効の組み合わせによる再承認の負担が増えるわけではない(ルールセットのある構成では、今も失効している)。増えるのは `checks-only` の構成での「数えない」表示だけである。この表示が 1 名体制の運用を止めると見るか。止めると見るなら、承認の後の push を外部の確認者に再確認させる以外の手段があるか
2. **起草の委員へ**: L-3 で自己修正の上限を本文(5.8.5)へ上げると、実行層の挙動を制約する規範が 1 つ増える。附属書E のまま手引きに留めて、テンプレートの停止を「テンプレート独自」と表示する案と比べ、どちらが記録と実態の食い違いを小さくすると見るか
3. **規格の委員へ**: L-5 で「無作為の抽出を再現できる手段」の記録を求めることは、ISO 19011 や監査の実務で一般か。乱数の種の記録まで求める規格・ガイドを知っているか
4. **擁護の委員へ**: L-4 で 5.4.6 の母数の下限未満を「計測できない」に数えると、小さい体制は L2 以上を適用できなくなる。ADR-0059・ADR-0054 決定4 の範囲で、これを強める向きの変更として読めるか。覆す決定と読むなら、どの ADR のどの決定か
5. **全員へ**: L-1 の「`scope: whole` を名乗る結果で測っていない製品のコードがあれば基準3 を満たさない」は、既存の案件で一斉に失敗を生みうる(テストの無いスクリプトを `src` の外に置く構成)。失敗にするか、件数の開示に留めるか。監査の立場は、名乗りが偽である以上は失敗だと考えるが、移行の扱い(初回の通知期間)の要否を問いたい
