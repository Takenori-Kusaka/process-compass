## 1. 立場と全体の見立て

1. **既存の規格は、数値を置かず「事前に決めて、記録し、逸脱を説明する」形を取る**。DO-178C・IEC 62304 は割合でなく未被覆の説明と事前の受入基準を、ISO 19011 は抽出の件数表でなく抽出の記録を、ISO/IEC 29110 は人数でなく工数と範囲を使う(いずれも二次資料)。本標準の固定の定数(80%・3 回・14 日・5 件・10 名・20 件)は、どれも外部では規格の値でなく、ベンダーの既定値か慣行値である。**値を変える根拠も、値を守る根拠も無い**。したがって本 Issue の主な仕事は値を動かすことではなく、(a) 根拠水準を開示する、(b) 値の意味(範囲・単位・分母・数える者)を定める、(c) 規範の置き場を正す、の 3 つである
2. **規格の形として最も重い欠陥は 3 つある**。G-6 に版への束縛の規範が無い(L-2)。停止の規範が参考の附属書にある(L-3)。合否に使える指標を、本文が測る手段を持たない定義で書いている(L-4)。どれも数値の問題ではなく、他の組織が「何に従えばよいか」を文面から読めない問題である
3. **比例・ratchet・上限の廃止など、構造を変える案の多くは外部の規格に支持が無い**。監査の抽出を母集団に比例させる規格は見当たらない(AS 2315、IAF MD 1 は劣比例)。ratchet は Sonar が退け、規格は採らず、本標準自身の較正の規定1・2 に当たる。これらは「課さないと明記する」で閉じる
4. **差し替え条件が観測できないマークは、マークとして機能しない**。EV-0084 の差し替え条件が名指す「別集計が基準の数倍を超えた PR の件数」を、集約は出していない。マークを付けた以上、差し替えの観測を出す実装は本 Issue で採る(L-8)。実測そのもの(利用者の分布)は、本プロジェクトが収集の経路を持たないので先送りとし、何が足りないかを書く
5. **起票の文言の多くは、そのまま採ると誤る**。「固定 5 件」は下限 5 件である(L-5)。「総数でなく同一の失敗の連続で止める」は、総数の歯止めを外す(L-3)。「ファイル数だけの超過を軽くする」は、#295 の骨子(観測のみ)ではなく採用済みの本文(行6)が正である(L-8)。「バックログの純増を対の指標に」は、私自身が #290 で先送りした案だが、今回の検討で対として逆へ動かないと分かったので退ける(L-10)

## 3. 論点ごとの詳細

### L-1 カバレッジの遮断

**判定: 採る(範囲の構成・分母・本文の読み分け)+ ratchet は課さないと明記する。**

外部の位置。

- 規格(DO-178C・IEC 62304、二次)は割合の閾値を課さず、受入基準を事前に定めることと、未被覆の説明を求める。ベンダーは新規コード 80%(Sonar way)、変更行の patch と全体の project の 2 本(Codecov)、全社で強制しない・変更の閾値を全体より高く置く段階(Google、査読)と分かれる
- 本標準は #294 K-8 で「範囲を企画時に決めて記録し、割合・範囲・分母を出す」と決めた。これは 62304 の「事前に定めた受入基準」の型と同じで、外部とずれていない

本文どうしの食い違い(`GC` L1603・L1615〜1617 と K-8)の判定。

- L1603 は「新規に変更した範囲に限定した機械判定(G-5 の基準)を合否条件とする」、L1615 は「新規に追加・変更した範囲へ限定します」と要求の文末(1.7.1)で書く。K-8 は全体を選んだ案件を認める。**両立しない。誤りは L1603・L1615 の側**とする。理由: K-8 は会議体と突合を経た新しい決定で、ADR-0078 決定6 に記録されている。L1615 の理由(既存の負債で恒常的に不合格になる)は正しいが、それは範囲を選ぶときの判断材料であって、全体を禁じる理由にはならない(全体の基準値を負債に合わせて置く組織もある。Google の段階は全体と変更の両方に値を持つ)
- 文の案(`GC`「新規に変更した範囲へ限定する」を改める): 「既存のコードがある案件では、基準3 の測る範囲を、変更で加えたコードとすることが望ましい。全体の割合を基準にすると、既存の負債によって恒常的に不合格になるか、負債に合わせた低い基準値を置くことになる」。L1603 の行は「G-5 の基準(基準3 は、企画時に記録した測る範囲で判定する)」とする
- あわせて「AI 品質指標の扱い」の適用範囲を見出しへ移す(L-11 の 2)

テンプレートの既定(7-A と 7-B の組み合わせ)。

- 構成 `ci.coverageScope: added | whole` を置き、結果の JSON に `scope`・`denominator`(測定の対象の行数)・`pct` を書く。既定は `added`(本文の目安の例と揃える)。行の情報を出せないアダプタでは `whole` を使い、そのことを結果と保証の開示に出す。IMPL-0245 は実装と試験ができた範囲を `delivered` にし、残りを note に書く
- 7-B 単独(既定を全体のまま)は採らない: 本文の目安と既定が食い違い続け、採用者の大半は既定のまま使う。K-8 の記録は満たせても、記録された範囲が本文の推奨と逆になる
- 実装できない場合の落とし方: 本 Issue の受入条件は「採るものは実装・台帳まで降りている」である。`undelivered` のまま残すことは降りていない規定の表示として正当だが、その場合も結果の JSON に `scope: whole` と分母を書くこと(範囲を選べなくても記録はできる)は本 Issue で行う

ratchet(7-C)は課さないと明記する。

- 文の案(`GC` 基準3 の小節の末尾): 「本標準は、基準3 の判定を、前回の測定値を下回らないこと(ratchet)で行うことを求めません。前回の実績を次の基準にする形は、実績を基準へ機械的に変換しない規定(運用メトリクス 規定1・2)に当たります」
- 落とす理由: 基準値を書き換えない形(基底との比較だけ)でも、前期の実績が当期の合否を決める点で規定1 と同じ動機を生む。Sonar は「生産的か疑問」として提供していない(二次寄り)。規格に前例が無い。削除で見かけの割合が上がる(二次)

80%・90% の根拠水準。

- 80%(目安): EV(E0、見直し 2027-10)。「広く信じられている」は E0(`evidence-marking.md` L36)。Sonar way・Google の段階と一致するが、それは慣行の一致であり測定ではない。差し替え条件: 範囲と分母を記録した G-5 の結果のうち、基準3 を通過した変更の出荷後の欠陥と変異スコアの分布
- 90%: 本文に値が無く、テンプレートだけが持つ。**規範の値がテンプレートにしか無い状態は、他の組織が従える形ではない**。`TG` L843 の「CI 基準の厳格化(カバレッジ+静的解析)」に「初期値: 基準3 の基準値 90%」を書き、同じ EV(E0)の対象に含める
- 未被覆の箇所の説明(DO-178C 型)は**課さないと明記する**(本 Issue では)。安全重要度の高い案件の構造カバレッジは附属書F の範囲で、そこへ持ち込む材料は今回の調査に無い

### L-2 承認の失効

**判定: 採る(G-6 に版への束縛の規範を置く)。持ち越しは条件つきの許容として書く。**

外部の位置。

- SLSA(一次、v1.0-rc1 Threats A2): 「Source control platform invalidates approvals whenever the proposed change is modified」「Only the version that is actually reviewed is the one that is approved」。供給網の規格の中で、承認と版の束縛は明文の脅威対策である
- GitHub(一次): 失効は差分を変える push に加え、Update branch・基底への別 PR の取り込み・merge base の変化でも起きる。粒度はルール単位の on/off だけ
- Gerrit(一次ミラー): trivial rebase・no code change の持ち越しを copyCondition で宣言できる。GitLab: コードオーナーのファイル単位の失効
- つまり「束縛」は規格と実務の一致した不変条件で、「粒度」はプラットフォームの能力で変わる

文の案(`GC` G-6、承認を数える 4 条件の後の箇条)。

- 「承認は、承認した版に対するものとして数える。承認の後に、取り込む差分が承認した版の差分から変わった場合、その承認を数えない」
- 「承認の後の更新(基底の取り込み・付け替えを含む)で差分が変わらないことを理由に承認を持ち越してよいのは、取り込みの時点で働く強制層が、承認した版と取り込む版の差分の同一を機械で確かめる場合に限る(許容)。作成者・AI の申告で持ち越してはならない」

この形の理由。

- 規範が強制層の設定値(`dismiss_stale_reviews_on_push`)と手順(`pr-workflow.md`)にしか無いと、ルールセットを置かない構成(`checks-only.json` は pull_request の規則を持たない)で束縛が消えても、集約はそれを検出しない(`lastReviewStates` はレビューの状態だけを見る。確認済み)。G-6 の 4 条件は「承認を数えるのは条件をすべて満たす場合に限る」と書いており、版の条件はそこに入るのが筋である
- 持ち越しを許容として書くのは、規範を GitHub の設定に縛らないためである。規格は特定の製品の挙動を要求にしない。Gerrit のように取り込みの時点で同一を確かめられる基盤では、持ち越しても不変条件は破れない。GitHub ではそれを表現できないので、テンプレートは全失効のままにする

実装(テンプレート)。

- 集約(`aggregate-evidence.mjs`)・G-5(`check-pr.mjs`)・委任(`delegation.mjs`)が、承認の `commit_id`(REST の応答にあることを一次文書で確認)を取り込んだ版の先端と比べ、違えば数えない。`checks-only` の構成でも束縛が効く。持ち越しの機械の確認(木・patch-id の同一)は実装しない(取り込みの時点の強制層でないため、許容の条件を満たさない)
- `adoption-trial.mjs` の実環境の確認で、`team` でも `dismiss_stale_reviews_on_push`・`require_last_push_approval` を確かめる。`verify-gate-contract.mjs` も `dismiss_stale_reviews_on_push` を見る
- ルールセットの変更ではないので ADR-0073 決定6 の陰性の確認は要しない。ただし集約の数え方を厳しくする変更なので、陰性の場面(承認の後に push した PR が数えられない)を試験に置く

選ばなかった案。

- 9-B(粒度を内容で決め、ルールセットの失効を外す): 判定がマージの時点の強制層から事後の集約へ移る。SLSA の A2 の対策(プラットフォームが無効化する)から外れる。Datadog が失効の無効化を検知ルールにしている(二次)ことも、業界がこれを逸脱と見ている材料である
- 9-C(緩和を課さない、だけを書く): 規範の欠落(G-6 に束縛が無い)が残る
- 9-D(先送り): 調査 1 が「確認できなかった」とした 2 点(GitHub の失効の範囲、レビューの API の commit)は、一次文書で確かめた。残る材料(再承認の回数の実測)は束縛の採否に効かない

再承認の負担について。strict と全失効の組み合わせでは、基底が進むたびに再承認が要る。これは規模を小さく保つ規定と「ゲート滞留時間」で観測する。負担を理由に束縛を外す材料は無い。

根拠水準: 束縛の規範は脅威への対策の書き出しで、値を持たないので EV は付けない。

### L-3 自己修復の反復の停止

**判定: 採る(停止の規範を本文へ移す)。同一の失敗の連続による早期の停止は先送り。総数の上限を連続へ置き換えることは課さないと明記する。**

規格の形の問題。

- E.7 の「反復回数の上限を定める」「上限に達した場合、人が仕様へ戻る。実装の再試行を続けない」は要求の形である。ADR-0063 決定1 は参考の附属書に要求事項を置かないと決め、5.8.5 などへ移した。E.7 はその直し残しである。テンプレートは本文に無い規範で実行主体を止めている。実装マークは参考の附属書に置けない(ADR-0076 決定7)ので、今は追跡もできない
- 文の案(`HB` 5.8.5 の注記の禁止事項3 の箇条の後、または 5.8 の新しい小節): 「自己修正の反復には上限を定めなければならない。上限に達した場合は反復を止め、人が受入基準へ戻る。上限の値は組織が定める(初期値: 3 回。運用メトリクスの登録簿 RC-05)。上限に達した後の再開は人が行う」
- 実装マーク: `target=implement-skill`(または既存の降ろし先)`state=delivered`、note に「回数は実行主体がスキルの手順に従って自ら数える(`self-heal.mjs iterate`)。フックは数えない。ロックを終えて始め直すと回数は 0 から始まる」と書く。これは開示であり、遮断の主張ではない

同一の失敗の連続(8-A)を先送りにする理由。

- 自分で確かめた事実: 数える者は止められる側の AI である。同一の失敗を数える仕組みを同じ経路に足しても、呼ばなければ数えられない。H.4 は「外部の観測を持たない自己修正を検出の層に数えない」と書く。停止にも同じ考え方が当たる
- 外部(OpenHands の stuck detector)は、実行基盤の側で行動と観測の反復を数える。本標準の型に置き換えるなら、数えるのは実行主体の外(フックがテストの実行の結果を記録する等)でなければならない
- 足りないもの: (a) 反復を実行主体の外で数える仕組み(フックの対象の拡大)の実現性、(b)「同一の失敗」を機械で比べる単位(失敗したテストの識別の集合。スタックごとの出力の形式)、(c) 反復数の分布の観測(`.claude/self-heal.log` は追跡されない)。(a) が無いまま (b) を足すと、規範は増えても信頼性は上がらない

総数を連続へ置き換えること(8-B)を課さないと明記する理由。

- 違う失敗が続く限り止まらず、費用の歯止めが消える。研究(Olausson ICLR 2024 は査読、Debugging Decay・Arimbur はプレプリント)は利得が最初の 2〜3 回に集中すると報告し、回数を重ねる向きを支持しない
- 文の案(ADR に記録): 「反復の上限を、同一の失敗の連続だけで置き換えることを採らない。総数の上限が費用の歯止めである」

その他。

- E.7 L130「同じ失敗を3回繰り返す場合、原因は実装ではなく受入基準の不備であることが多い」は削る(テンプレートの `implement/SKILL.md` の規則3 も)。マークで残す案は採らない。理由: 根拠が無いうえ、外部の研究は別の原因(自己批評の質)を指しており、受入基準へ戻る理由を誤った断定で与える。人が受入基準へ戻る理由は「上限に達したこと」で足りる
- E.7 の「7.7.2 の指標へ算入」は、7.7.2 に該当する指標が無い(L-11 の 3)。「AI実行費用の単位あたり値の分子(期間内の AI 実行費用)に含まれる」と書き直す
- 3 回の根拠水準: E1(関数単位のベンチマークの研究で、リポジトリ規模のエージェントでの測定は無い)、見直し 2027-10。差し替え条件: 上限で保留になった件のうち、人が受入基準を直した割合と、保留を解いて再試行した後に通った割合

### L-4 手戻り率

**判定: 採る(合否化を外し、名称を分け、5.4.6 の参照先を定める)。**

- 第4章の量(14 日以内に書き換えられた行 ÷ AI が生成した行)は、AI が生成した行を識別する手段が本文に無い。トレーラはコミット単位である。測定の手段を持たない量を「閾値を G-1 で確定した場合に限り合否条件」にすると、閾値を確定した組織は検証できない合否を持つ。ISO/IEC Directives Part 2 は規格の要求に検証可能性を求める(本プロジェクトは #290 E-10 で同じ原則を採った)
- 外部: SPACE(一次)は活動指標を単独で報酬・罰に使わないとし、DORA は rework rate を記述として扱う。行単位の churn(GitClear、2 週間)はベンダーの白書で、AI の帰属を行単位で識別していない。合否化を支持する資料は無い
- 文の案:
  - `GC` 指標の定義の表: 名称を「AI 生成行の短期書き換え率」に改める。「名称と定義を必ず併記して用いなければならない」はそのまま
  - 合否の表: 「AI 生成行の短期書き換え率 | **合否条件にしてはならない**。傾向の確認に留める」。理由の箇条: 「AI が生成した行の識別は推定であり、分母を記録から確定できない」
  - `HB` 5.4.6 の表と「計測できない検知条件」の表: 「手戻り率」を「手戻り率(運用メトリクスの AI協調の定義)」とする。PR 単位で自動集計でき、L2 以上の適用の可否を測定の手段の無い量に依らせない
- 14 日・30 件・四半期に EV(E0、見直し 2027-10)。30 件と四半期は 5.4.6 の母数の下限にも使われるので、マークは「閾値の設定と較正」の要求事項3 の段落に付ける。差し替え条件: 母数の下限の前後で、5.4.6 の検知条件の発火の件数と、発火した後に確かめられた監督の劣化の件数
- 選ばなかった案:
  - 11-B(合否化を残し条件を足す): 足す条件(自動集計・行の単位・対の指標)を満たす手段が無い間、条件は空文になる
  - 11-D(定義そのものをやめる): 委託契約で AI 関与の品質を数値で扱う需要(この節の適用範囲)に、名称と定義を併記する型を示す価値は残る。傾向の確認としては使える
  - 11-E(先送り): 行の帰属の方法が見つかっても、合否化を支える外部の資料が無いことは変わらない

### L-5 監査の抽出

**判定: 比例は課さないと明記する。単位の定義と抽出の記録を採る。**

- 外部: 母集団に比例させる規格は見当たらない。AS 2315(一次)は、母集団がごく小さい場合を除き母集団の大きさは件数にほとんど効かず、件数を決めるのは許容逸脱率と予想逸脱率だとする。IAF MD 1(一次)は √x の劣比例と無作為枠 25%。ISO 19011 A.6(二次)は判断による抽出と統計的抽出を併記し、母集団・抽出の基準・方法・件数・結果の記録を求める
- 文の案(`PA`「対象の抽出」):
  - 「抽出の単位は変更(PR とその判定記録)とする。リスクに基づく抽出の条件は、変更を選ぶ案件の条件として読む」
  - 「抽出のたびに、母集団(期間と範囲)・単位・方法(無作為かリスクに基づくか)・件数を記録しなければならない」
  - 「抽出数を、母集団の件数に比例させることを求めない。抽出の件数を決めるのは、検出したい逸脱の率と、見逃しを許す水準であり、母集団の大きさではない。抽出数の見直しは、抽出方法別の所見の検出率(EV-0010 の差し替え条件)による」

- EV-0010 の対象に「抽出の単位」を加える(E0 のまま)
- 選ばなかった案: 23-A(比例を足す)は規格に支持が無く、L63 の帯域の問題を比例でも起こす。23-D(先送り)は、単位の定義と記録の要求について材料の不足が無い(規格の型で決まる)ので当たらない。抽出数の値そのものは EV-0010 の見直しで扱う

### L-6 10 名の境界

**判定: 採る(根拠水準のマーク)。組織が境界を定める形は課さないと明記する。軸の替え方は別 Issue。**

- 外部: Scrum Guide 2020(一次、自分で確認)は 1 チームを「typically 10 or fewer people」とする。チーム規模と生産性の負の関係は頑健だが、境界の値は支持されない(Gote ほか、一次)。ISO/IEC 29110(二次)は適用対象を 25 人以下で定めつつ、プロファイルの切り替えを人数でなく工数と範囲で行う
- 文の案(`TG` 軸A の表の直後): EV(E0、見直し 2027-10)。対象: 10 名の境界と、10 名以上の列の規則(兼務禁止、コア機能の別チームのレビュー、出荷判定の QA 部門・専任、仕様承認の委譲の推奨、検証の担い手を分ける)。本文に「10 名は慣行値であり、Scrum Guide 2020 が 1 チームの上限として挙げる『10 名以下』とは境界の置き方が 1 名異なる。チームが 1 つしかない体制では『別チーム』の規則は所属の欄で『判定できない』と出る」と書く。差し替え条件: 9 名以下と 10 名以上の体制で、コア機能の変更の別チームのレビューの有無と、出荷後の欠陥・取り消しの比較

### L-10 運用メトリクス

**判定: 採る(区分の定義と誤りの修正)。バックログの純増を対の指標にすることは課さないと明記する。**

区分の定義。

- 外部: 指標の数の上限を定めた一次資料は無い。SPACE(一次)は「少数の指標を少なくとも 3 つの次元で」、対の緊張を意図とする。ISO/IEC/IEEE 15939(二次の理解)は情報ニーズから測定量を選ぶ構造で、数の上限を置かない。本標準の上限 20 件は EV-0012(E0)で既に開示されている。上限を外す新しい材料は無いので、上限は保つ
- 誤りの正体: 本文の表(21 行、三識を含め 25 行、`GC` の健全性の表 4 行と重複)は、**標準が示す候補の一覧**である。手続3 は「自動集計の実装をもって採用」とし、採用するのは組織である。上限 20 件を候補の表の行数に当てると、標準の起草者の書き足しが組織の上限を食う
- 文の案(`MT`「指標を増やして対処しない」): 「上限は、組織が正式指標として採用した指標に掛ける。正式指標とは、手続1〜4 を満たし、自動集計を実装したものをいう。本ページと第4章の表は候補であり、上限の件数に数えない。初期値は正式指標 20 件とする」。L69 の「現在の指標体系はこの範囲に収まります」は削る
- L303「手集計が必要な指標は上の表に存在しません」を、「人の抜き取りを含む行(挙動要約の品質の文面、生成案の採否の分布)は、抜き取りの部分を正式指標の値に含めない」へ改める
- 選ばなかった案: M-B(初期値を行数に合わせる)は、根拠無しに値を動かす。M-C(行を減らす)は、2 期の運用記録が無く手続の条件を満たせない。M-F(先送り)は、区分の定義には材料の不足が無い

バックログの純増。

- #290 で私(規格)は、純増を完了スループットの対の指標の候補として先送りした。今回、手続2 の定義(歪んだときに逆へ動く指標)に照らして確かめた。完了スループットの歪みは、Issue を細かく割る、未完了のまま閉じるの 2 つである。細かく割れば流入も増え、純増は動かない。未完了のまま閉じれば純増は下がり、スループットと同じ向きに動く。**どちらの歪みにも逆へ動かないので、対の指標の要件を満たさない**
- 加えて、ADR-0074 決定8 の理由(起票の抑制へ向く)が残る。覆す材料は無い
