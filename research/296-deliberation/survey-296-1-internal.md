### 矛盾・欠落

1. 「承認は承認した版に束縛される」は、#295 の懐疑役が構造の不変条件(A)と分類したが、標準の規範の文としては G-6 に無い。強制層(ルールセット)の設定値として存在するだけ
2. ルールセットを置かない構成(`checks-only`、私有リポジトリでルールセットを使えないプラン)では束縛が働かず、集約もそれを検出しない
3. `team` の実環境の確認で、`dismiss_stale_reviews_on_push` と `require_last_push_approval` を確かめていない(ファイル側は契約検査が `require_last_push_approval` を見る)
4. `adoption-guide.md` L489 と `template-repository.md` L330 で、要件⑦が確かめる設定の列挙が揃っていない
5. 失効の粒度(全 push)を変える案は、GitHub の設定では表現できない。表現するなら集約・G-5 の側で、レビューの commit と版の比較(木または patch-id)を実装することになる

### 選択肢

- 9-A(規範を本文に置き、強制は現状のまま): G-6 に「承認は、承認した版に対するものとして数える。承認の後に版が変わった場合、その承認を数えない」を置く。ルールセットの設定は全 push の失効のまま。集約が、レビューの commit と取り込んだ版を比べ、ルールセットの無い構成でも数えない(実装マーク)
- 9-B(粒度を内容で決める): 承認の後の push が差分を変えない(木の一致、または patch-id の一致。基底の取り込みだけの更新を含む)場合は失効させない。ルールセットの失効を外し、判定を集約と G-5 へ移す。強制層からレビュー側の検査へ移るため、マージの時点で止まらなくなる(`ci-gates.md` L858 と同じ弱さ)。統制の弱化に当たり、ADR-0073 決定6 の陰性の確認が要る
- 9-C(課さないと明記する): 失効の粒度の緩和を課さない・認めないと明記する(理由: 懐疑役の分類。束縛を緩める向きは形骸化に直結)。再承認の負担は、規模を小さく保つ規定と滞留の指標で見る
- 9-D(先送り): 足りないもの: GitHub が基底の取り込み・リベースで承認を失効させるかの一次文書での確認、レビューの API が commit を返すかの確認、`strict` と失効の組み合わせで再承認が何回要るかの実測
- いずれの案でも: 要件⑦の確認の列挙を揃える(`team` でも `require_last_push_approval` を確かめるか)

### 矛盾・欠落

1. L69 の「この範囲に収まります」は、21 行(三識を含めれば 25 行)に対して誤り
2. 「正式指標」の区分が無いため、上限 20 件の適用先が定まらない
3. L303 の「手集計が必要な指標は存在しない」は、少なくとも人の抜き取りを含む行がある点で言い過ぎ
4. 完了スループットに対の指標が書かれていない。手続2 と食い違う(既存の行が手続を満たしているかを確かめた記録が無い)
5. バックログの純増を対の指標にする案は、ADR-0074 決定8 の「採用しない」の見直しになる。見直すなら決定8 の理由(起票の抑制へ向く、変更と起票の関係を機械で辿れない)に答える必要がある

### 選択肢

- M-A(区分を定義して数え直す): 「正式指標」を「自動集計が実装され、対の指標が指定された行」と定義し、表に区分の列を置く。上限 20 件は正式指標にだけ掛ける。満たさない行は「候補」とする
- M-B(上限の値を改める): 表の行数に合わせて初期値を改める。EV-0012 の差し替え条件(参照回数と打ち手への接続率)の観測は無く、値を動かす根拠も無い
- M-C(行を減らす): 上限に収まるまで廃止の候補を選ぶ(L60 の手続)。2 期分の運用記録が無く、手続の条件を満たせない
- M-D(誤りの文だけ直す): L69 の「収まります」を事実(行数と、区分が未定義であること)へ改め、区分の定義を先送りする
- M-E(課さないと明記する): バックログの純増を対の指標にしないことを維持し、完了スループットの対の指標は作業単位の滞留期間(L194、L202 で既に対として扱う)と書く
- M-F(先送り): 足りないもの: 2 期分の指標ごとの参照回数と打ち手への接続率(EV-0012)。採用組織の運用記録
