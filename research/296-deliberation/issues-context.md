## 1. 論点ごとの経緯

### T-07 全体の行カバレッジ 80%(strengthen で 90%)の遮断

- 元の依頼(#296 本文): 標準は「新規コードで 80%、組織で調整」。テンプレートは全体の行の割合を遮断に使う。基底を下回らない形(ratchet)か差分カバレッジへ
- #295 の扱い: 棚卸しで B(能力依存)、効きの上位 7 位。会議体で、統制を守る側は「全体は観測へ移し、差分カバレッジを合否に残す」、先進の現場は「基底の実測を下回らない(ratchet)+変更行は観測、80% は新規の足場の既定へ降格」。決定は先送り(D9。理由: 検査基盤の変更が大きい)
- #295 の登録: 登録簿 RC-06「カバレッジの下限(80%・90%)」、能力に「依る」、担っている保証の移り先は「受入基準ごとのテスト(G-5)」
- 後の拘束(#294 / ADR-0078 決定6、`research/294-deliberation/decision.md` K-8):
  - 規模の下限を課さないと明記した(EV-0142)。下限未満の「判定しない」は ADR-0033 決定7 の 3 区分に無い状態になるため
  - G-5 基準3 の基準値は、測る範囲(全体か、変更で加えたコードか)を併せて企画時に決めて記録する。記録と保証の開示に割合・範囲・分母を出す
  - テンプレートの `coverage-check.mjs` が全体しか測れず分母を記録しないことは `undelivered`(IMPL-0245)。集約が coverage の結果を取り込まないことも `undelivered`(IMPL-0246)
  - アダプタが基準3 を測らずに通す件(go・none・undetermined、`coverageSummary: null`)は #330 へ送った。証跡の保管の設計(ship-evidence が coverage を取り込まない件を含む)は別 Issue
- 他の拘束: ADR-0065(影響): G-6 未達の代償措置 ci-strict でカバレッジの導出値が 80%→90%。テンプレートは導出値が下がっても自動で下げない。運用メトリクス「実績を基準へ機械的に変換しない」規定1〜4(ratchet の形と緊張する。`survey-296-1-internal.md` T-07)
- 残る問い: (a) テンプレートの既定の測る範囲を全体のままにするか、変更で加えたコードにするか、(b) ratchet を採るか、(c) 80%・90% の値に根拠水準マークを付けるか、(d) IMPL-0245 を `delivered` へ動かす実装を本 Issue で行うか

### T-09 全 PR・全 push の承認失効(`dismiss_stale_reviews_on_push`)

- 元の依頼: G-6 の規範(承認の存在と内容への束縛)と、ルールセットの粒度
- #295 の扱い: 棚卸しで B、効きの上位 9 位。会議体で、統制を守る側は「承認後の変更が差分の実質に触れたときに失効。機械判定できない間は失効側」、先進の現場は「承認の commit と現在の HEAD で木または patch-id が同一(リベースだけ)なら維持」、懐疑役は「『承認は承認した内容に束縛される』は構造の不変条件(A)。B は粒度(全 push)だけ。緩めて承認が内容と切れる向きは形骸化に直結」。決定は先送り(D9)
- 後の拘束:
  - ADR-0078 決定3(K-4): スタック型 PR は既定ブランチへの取り込みで G-5・G-6 を成立させる。合わさった差分への承認を層ごとの確認に数えない。`team.json` の `dismiss_stale_reviews_on_push`・`require_last_push_approval`・strict を既定ブランチの保護として前提にした
  - ADR-0073 決定6: ルールセットを変える変更は統制の設定の変更であり、PR に陰性の確認の記録を要する
  - ADR-0077: GitHub の門は既定で管理者が迂回できる(ADR-0078 K-2 の理由でも引いた)
  - ADR-0067: 2 名の承認の目的は「1 名の確認だけでは取り込めない状態」。承認の数え方は G-6 の 4 条件
- 残る問い: 標準の G-6 に「承認は承認した版に束縛される」を本文の規範として置くか(現在は `pr-workflow.md` の手順の記述と `git-strategy.md` の設定例だけ)。失効の粒度を変えるか。ルールセットを置かない構成(`checks-only`)での束縛をどう扱うか

### T-08 自己修復の反復 3 回 → 「同一の失敗の連続」で止める

- 元の依頼: 総数でなく「同一の失敗の連続」で止める形へ。標準 developer-guide E.7 は「同じ失敗を 3 回」
- #295 の扱い: 棚卸しで B。統制を守る側は「停止という構造を維持の本体とし、回数は設定値で較正対象」、先進の現場は「上限は維持。同一の失敗の再発(同じテスト・同じエラー)を検出したら回数に関わらず停止を足す。反復数の分布は観測」、懐疑役は「有限回で止まり人へ戻すは A、3 は B」。決定は先送り(D9)
- #295 の登録: RC-05「自己修復の反復上限 3回」、能力に「依る」、保証の移り先「上限で保留にして人が受入基準へ戻る」
- 後の拘束: ADR-0076 決定7「参考の附属書にマークを置かない」。E.7 は附属書E(参考)にあり、規範にするなら本文へ置く必要がある。ADR-0075 決定11(AI どうしの往復を禁止しない)・H.4 の「外部の観測を持たない自己修正を検出の層に数えない」(IMPL-0153)は、自己修正の結果の数え方であり、停止の条件ではない
- 残る問い: 依頼の文言(「総数でなく」)は、総数の上限を外す読みと、総数の上限に足す読みの両方を取れる。会議体で切り分ける

### S-11 手戻り率(14 日窓、AI 生成行数が分母)の条件つき合否化

- 元の依頼: 見直し
- #295 の扱い: 棚卸しで C(合否にしてはならない観測量)と分類。統制を守る側・標準の運営者の意見書は、規模の確認の形骸化を「超過 PR の手戻り」で見る失敗条件に使った。決定は先送り(D9)
- 後の拘束: ADR-0072・ADR-0074(量を指標にしない、対の指標を指定できない量は採らない)。運用メトリクス「参考値として測ることはできない」(指標の追加は統制)。ADR-0073 決定1(件数を起動条件にした義務を課さない)
- 残る問い: 「閾値を G-1 で確定した場合に限り合否条件」を残すか外すか。同名の「手戻り率」が本文に 3 通りの定義で並ぶ問題(`survey-296-1-internal.md` S-11)

### S-23 監査の抽出率を変更件数に比例させる(四半期 5 件の固定)

- 元の依頼: 抽出率を変更件数に比例させる
- #295 の扱い: 棚卸しでは「S-23 監査の周期」を B に置き、決定 D6 で RC-11「監査の周期」を「能力に依らない」と登録した。抽出数は登録簿に無い。決定は先送り(D9)
- 注意: 本文の値は「1回あたり5件以上」(下限)で、件数が確保できない規模では四半期の全件(`process-audit.md`)。「固定 5 件」は正確な要約ではない。委任の事後監査の抜き取りは別の値(月次、当月の全件と 5 件のいずれか少ないほう。EV-0004)
- 後の拘束: 運用メトリクスの較正の規定(抽出数と頻度は較正の適用先。前期の所見件数から機械的に決めない)。ADR-0073 決定1
- 残る問い: 比例させる母数の単位(案件か、変更か、記録か)。本文の「件」が何を数えるかが未定義

### S-14・S-18/19 本文の再評価(能力依存の定数の登録簿の最初の運用で)

- 元の依頼: 登録簿の最初の運用として本文を再評価する
- #295 の扱い: S-14(自律度の引き上げの観測窓 3 か月)は RC-09「能力に依らない」。S-18/19(コンテキスト量・context rot)は RC-07(CLAUDE.md 200 行・6,000 トークン)「依る」。標準の運営者は S-18 を「能力依存が最も強い。観測へ移す候補」とした。決定は先送り(D9)
- 登録簿の規定(`metrics.md` 要求事項1〜5): 契機は performer の変化点と半期の暦だけ、値を自動で変えない、人が「残す・外す・移す」を記名で記録、能力に依らない周期は能力向上を理由に短縮しない
- 状況: 登録簿の再評価の記録はまだ 1 件も無い(テンプレートの `docs/calibration-register.md` は表の見出しだけ)。本プロジェクト自身は採用組織ではなく、登録簿の契機(performer の変化点)を持たない
- 残る問い: 「最初の運用」を誰が・何の契機で行うか。本 Issue の会議体が標準の起草者として再評価するのか、採用組織の運用を待つのか

### 利用者の PR 分布の実測

- 元の依頼: 実装行・テスト行・fixture 行・ファイル数・タスク数/PR の実測。懐疑役の要求1。規模の基準値そのものの妥当性はこれが無いと決められない
- #295 の扱い: EV-0084・EV-0089 の差し替え条件に入れた。集約(`sizeObservation`)が採用組織の手元で分布を出すようにした(IMPL-0100)
- 制約: **本プロジェクトは利用者のデータを持たない**。利用者のリポジトリへのアクセスも、テレメトリも無い。集約は採用組織の手元で動き、結果は送られてこない。本プロジェクトと pit-in-template 自身の PR 履歴は単独の保守者の文書主体のリポジトリで、母集団の代わりにならない
- 残る問い: 実測を「先送り(何が足りないか)」として記録するか、採用組織から分布を受け取る経路(任意の提出の様式)を設けるか
