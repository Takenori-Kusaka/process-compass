## S-1(重大度「高」): go の基準3 と、ADR-0085 決定2 と ADR-0121 の食い違い

### (a) どちらの ADR が誤りか — 見解

**誤りは ADR-0085 決定2 の go の箇条(「go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない」)である。ADR-0121 決定4 は正しい。ただし ADR-0121 のステータスの表が、決定2 の理由を「製品のコードが単一のスタックの場合に限って成り立つ」と残したことは、誤りを半分だけ直した状態であり、これも改める。** 両立する読み方は無いと判断する。理由は次の4つ。

1. **本文の規定と正面から衝突する**。第4章 G-5 は「実施していない検査が通過として残る」ことを、規模の下限を置かない理由として退けている(`gate-criteria.md` 998 行。ADR-0033 決定7 の区分に無い状態)。「実装が存在する段階では、規模にかかわらず測定し、基準値と比べます」(996 行付近)とも書く。入力を欠いて実施できなかった検査は「未実施の検査として失敗に数えなければなりません」(934 行)。宣言の外のスタックも同じく失敗に数える(714 行)。go の現状(製品のコードがあり、`coverageSummary` が null のため code 0 で通す)は、この「実施していない検査の通過」そのものである。ADR-0085 決定2 は事前点検で止めない理由を述べた決定で、G-5 の判定の規則を変える権限を持たない。下位の理由づけが本文の規範と食い違うなら、誤りは理由づけの側にある
2. **「黙っては外れない」という事実の前提も成り立っていない**。`coverage-check.mjs:259-263` は警告を出して code 0 を返すだけで、集約 `gate-g5` は成功(緑)になる。記録は test ジョブのログと成果物 `coverage-result` の `measured:false` に留まる。しかも出荷のワークフローは `coverage-result` を取り込まず、保証の開示ではすべての構成でカバレッジが「未測定」と出る(IMPL-0246、undelivered)。つまり go の「実施しない」は、判定者が見る2つの面(必須チェックの色、保証の開示)のどちらにも、ほかの構成と区別できる形で現れない。ADR-0085 が品質保証の委員の「受容の記録が無ければ止める」を退けた理由(「G-5 の失敗と『実施しない』の記録と二重になる」)は、go については G-5 の失敗が存在しないため、二重にならない
3. **同じ状態を、構成の形によって逆に扱っている**。ADR-0121 決定4 と `coverage-check.mjs:417-425` は、手書きの要素で受けた go を「報告が無ければ未実施として失敗」とする。言語のアダプタ go を選んだ構成だけが、同じ「go のカバレッジの報告が無い」状態で通る。より正式な経路(テンプレートが用意したアダプタ)を選んだ採用者ほど統制が弱いのは、標準の規範の一貫性を欠く。ADR-0121 の表が「単一のスタックの場合に限って成り立つ」と書いたのは、混在の穴を塞ぐことに焦点を置き、単一の go の構成の側を突合しなかったためと読む
4. **外部の規格の読みとも合わない**。29119-3 の型は、測れない・満たさないことを禁じはしないが、逸脱として理由と残留リスクを記録し、判断へ回すことを求める(`survey-external.md` §5)。本標準でその「判断へ回す」経路は、基準値の変更(/process-change の記名)か未達の記録であり、黙った通過ではない。SonarQube の「報告の無い実行可能な行は未被覆」は本標準の向きに近く、Codecov・diff-cover の既定(通す)は本標準の規範と逆向きで、基準にできない

**推す扱い**: 新 ADR で ADR-0085 決定2 の go の箇条(理由の部分)を**一部置き換え**、ADR-0121 のステータスの表の当該の読み(単一のスタックでは成り立つ)を**補う**。採用済みの本文は書き換えず、両 ADR のステータスに置き換え・補いの注記を足す(ADR-0085 が ADR-0121 から受けた注記と同じ形)。ADR-0085 決定2 の**結論(事前点検ではカバレッジの測定の穴を止めない)は維持する**。G-5 が失敗するようになれば、止める位置は G-5 にあり、事前点検で重ねて止める必要は無いため。ADR-0121 決定4 は維持する。

### (b) go で基準3 を測る手段

**推す案: coverage.out(`go test -coverprofile`)1つで全体と変更の範囲を測る。行への落とし方は、ソースを go の構文木で読んで文の範囲を得て、各文に重なるブロックの回数を割り当て、文の開始行を被覆の行とする(gocov・Azure/gocover と同じ方式)。** node(istanbul)・python(coverage.py)と同じ「文の開始行」の近似に揃う。

- 実装の形
  - アダプタ `go.json`: `coverageSummary` と `coverageDetail` を `coverage.out` にし、新しい欄 `coverageFormat: "go-coverprofile"` を置く(node は `istanbul`、python 系は `coverage-py`)。`coverageDetail` があれば istanbul と見なす現行の読みをやめ、形式で読み手を選ぶ
  - 文の範囲を出す小さな Go のプログラムを準拠テンプレートに置く(例 `scripts/gate/go-stmts/main.go`。`go/parser`・`go/ast` だけを使い、ファイルごとの文の開始・終了の位置を JSON で出す)。test ジョブは setup-go を済ませているため、`go run` で動く。coverage-check.mjs はその JSON とプロファイルを突き合わせ、行の実行回数の Map を作って既存の `changedScopeCoverage` へ渡す
  - 全体の割合は「Σ(回数>0 の文の数)/ Σ 文の数」(`go tool cover -func` の total と一致することを調査で確認済み)
  - import のパスは `projectDir` の `go.mod` の module 行でファイルのパスへ戻す。go.work の複数 module と replace は、戻せないファイルを「測っていない製品のファイル」に数え、黙って落とさない
  - 試験: `test-coverage-scope.mjs` に go の固定の写し(プロファイル・文の範囲の JSON・差分)を足し、node の試験として回す。Go のプログラム自体は、テンプレートの CI に setup-go を置いて、調査の素材(`360d/go/`)と同じ型の固定のリポジトリで回す。両方が無いうちは delivered にしない
- 本文: 基準3 の「変更の範囲の分母は、加えた・変えた行のうち、被覆の記録で文の開始行に当たる行で数えます」に、「被覆の記録が文の行を持たない形式(go のプロファイル)では、ソースの構文から求めた文の開始行に、重なるブロックの回数を割り当てます」を足す。go の `&&`・`||` の内側を測らない限界(go の cover の仕様)を、既存の近似の開示と同じ段に書く
- **採らない案**
  - ブロックの開始行だけ(案A): ブロックの2文目以降を落とし、分母の取りこぼしが node より大きい(調査で 7 行。文は 8)
  - ブロックの範囲の全行(案B)・空行と括弧を除いた範囲の全行(案C、sonar-go・gocover-cobertura の方式): 被覆したブロックの継続行・注釈の行を被覆に数え、割合を上へ寄せる(調査で 38.46%、文の割合は 25%)。先例はあるが、本標準の分母の定義(文の開始行)と違う近似を go だけに持ち込み、開示を2本にする。「業界に先例が無いから退ける」のではなく、割合を上へ寄せる向きと定義の不一致を理由に退ける
  - 変更の行に重なるブロックを分母に入れ、文の数で重み(go-patch-cover の方式。軽の審議の起案の案): 実務の先例があり、ブロック内の文は同時に実行されるため被覆の判定そのものは正しい。ただし、1行の変更で大きなブロック全体の文が分母に入り、変更していない文を変更の範囲に数える。構文木の方式が得られる以上、分母を「変更した文」に限る方が定義に忠実で信頼性が高い。軽の審議の私の案を、この理由で改める
  - `go tool cover -func` の表示の値を読む: 変更の範囲を出せず、表示の文字列の形に依る

### (c) 既存の go の採用者に新しい失敗を課す移行

**推す案: 猶予の期間・警告だけの段を置かない。テンプレートの取り込み(種別 `intake`)を採用者が選ぶ時点を、新しい既定の切り替えの点とする。** 外部の型でいえば Go の GODEBUG(既定を利用者の宣言した版に結びつける)に当たり、ADR-0085 決定6(取り込みは採用者の選択で、取り込まないことは許す)が既にその仕組みを持つ。

- 落ちうる場面を ADR-0085 決定6 の保守者の義務に従って列挙し、テンプレートの変更の告知(README の変更点、`/process-change intake` の出力)に書く
  1. 範囲の記録が無い・whole の go の構成: 全体の割合が基準値を下回れば基準3 で落ちる
  2. 範囲 changed の go の構成: 現行は契約検査で落ちていたものが、測られるようになる(緩む向きではなく、正しく測る向き)
  3. coverage.out が出ない・0 文で製品のコードがある構成: 落ちる((d))
- 直し方の案内: テストを足す。基準値を改めるなら `/process-change` 種別 settings の記名(緩める向き。由来の記録 IMPL-0346 に乗る)。範囲を changed にする(新しいコードにだけ掛ける Clean as You Code の型。古いコードの是正を求めずに済む)も同じ記名で選べる。**範囲の無い構成を黙って changed へ読み替えない**(本文の既存の規定)
- 取り込みの前に手元で試す手段: `g5-local.mjs` が coverage を回すことを確かめ、告知に「取り込みの前に g5-local で基準3 の値を見る」を書く
- **採らない案**
  - 猶予の期間(例 2版・6か月は警告だけ): 猶予の間、実施していない検査の通過が続く。ADR-0085 決定5・ADR-0121 が同じ理由で既に退けている。外部の PEP 387・Kubernetes の型は「使えなくなる機能」の告知で、本件は「本文が既に禁じている通過」を直す欠陥の修正であり、型が違う
  - 既存の go の構成だけを凍結して旧の挙動を残す(ESLint の一括の抑止・ratchet の型): 基準値の自動追従は本文が退けている(ratchet を課さない)。旧の挙動を残す欄は、未実施の通過を構成の値で選べる第3の状態を作る
- 告知と記名: 取り込みの記名(intake は自然人の記名)が、新しい失敗を受け入れたことの記録になる。新しい記名の欄は足さない

### (d) 測れない構成(coverage.out が出ない)の扱い

- coverage.out が無い: 失敗(現行の「集計ファイルが無い」と同じ)。対象なしにしない
- プロファイルの文の総数が 0 で製品のコードがある: 失敗(現行の 0 行の規則 `:276-288` をそのまま当てる)
- 文の範囲のプログラムが動かない(go の道具が無い、構文の誤り): 失敗。案内に理由を出す。通過へ倒さない
- ビルドタグ・cgo などでプロファイルに載らない `.go` の製品のファイル: whole では「測っていない製品のファイルの数」に入れ、changed で変えたなら `unmeasured` として失敗(node の現行と同じ)
- **一般化**: go を直すだけでは、`coverageSummary` を持たないアダプタが今後足されたとき同じ穴が開く。`coverage-check.mjs:259-263` の分岐を「製品のコードがあれば未実施として失敗(基準3 未充足)、無ければ対象なし」に改める。対象なしの記録の3項目は IMPL-0239(#330)の範囲で、ここでは合否の向きだけを直す

## S-2: 「テストのみの変更で失敗が解消した変更」(IMPL-0204 の一部)

### 推す案

1. **本文の文を、差分から検出できることと、実行で示すことに分けて書き直す**。現行の「検証を弱める変更(…、テストだけの変更で失敗が解消した変更)は、差分から機械で検出し」は、差分からは「テストだけの変更」までしか分からず、「失敗が解消した」は差分に無い事実である(survey.md 論点A §5.2)。書かれたとおりには誰も実装できない規定を残すと、読み手は「いずれ降りる」と受け取り、降りないまま見直しの年月が過ぎる。改める文の要旨:
   - 差分から検出して G-6 の必須の確認事項に示すのは、「製品のコードを変えずに、既存のテストを変えた変更」とする
   - 「テストの変更で失敗を解消した」ことは、基底の版のテストを変更後の製品のコードへ流して確かめる(旧版で落ち新版で通るテストのファイルを示す)。これも G-5 の合否に使わない
   - 自己修正のループの内側は、テストへの書き込みの遮断(IMPL-0187)が受け持つ
   - これは規定を弱める改めではない。課す中身(機械で検出し G-6 へ示す)を変えず、検出できる形に定義し直す。重の審議の記録とともに新 ADR に書く
2. **マークを分ける**
   - 新マーク A(静的な表示): 「製品のコードを変えずに既存のテストを変えた PR」を pr-rules の一覧に「テストだけの変更」として出す。delivered・machine・test=test-check-pr.mjs。note に「失敗が解消したかは見ていない」と書く
   - 新マーク B(再実行による確認): 基底の版のテストを先頭の製品のコードへ流す。undelivered・plan=scheduled・issue は #360 が閉じる前に後継へ移す(範囲外の節)。実装の要点(製品のコードを実行するため PR の側の gate-g5 で流す、統制の設定を変える PR では信頼しない、新しいテストのファイルは旧版が無いので対象外と表示する。SWE-bench の偽の合格の欠陥と同じ穴を作らない)を note に書く
   - IMPL-0204 の残り(skip・xfail の付与、アサーションの削除、期待値の改め)は S-7 の形で delivered へ
- **採らない案**
  - 静的な近似を、IMPL-0204 の delivered に含めて「テストのみで解消」を降ろしたと表示する(軽の審議の私の案): ローカルで解消した失敗、同じ PR で製品とテストを変えた場合(自己修正のほとんど。ImpossibleBench の測定でも、試験の改変は特別扱い等と組み合わさる)が隠れる。近似の名で規定の名を名乗ることになり、表示が実態より強い。私の軽の案を、この理由で取り下げる
  - 履歴型(push ごとの check runs の遷移): ループはローカルで回り、失敗は push されない。force-push で前の先頭が消える。取りこぼしが静的な近似と同じ型で、GitHub の読み取りの経路と権限を増やすだけ。採らない(却下として記録)
  - 本文から「テストだけの変更で失敗が解消した変更」を落とす: 禁止事項3 の主要な型(外部の測定で、AI の不正の主な型が試験の改変)を検出の対象から外すことになる。採らない
- 採用者への影響: 新マーク A は表示だけで合否を変えない。新マーク B は降りるまで変化なし

## S-3: 落ちることを期待する印の欄と、予期せず通った場合の失敗

### 推す案

標準の3つの欄(Issue・照合する失敗の理由・見直しの時期)と2つの失敗(予期せず通った、別の理由で落ちた)を、**準拠テンプレートが道具を問わない書式で定め、枠組みごとに届く範囲を表で開示する**。

- 書式: 印の直前の行に置く注釈 `known-failure: issue=<番号> match="<照合する失敗の理由>" review=YYYY-MM`(言語の注釈の記号で前置する)。様式(実装計画のテストの方針)と `/implement` の手順に書く。Issue だけでなく理由と時期を必須にするのは本文どおり
- 検出: pr-rules が、追加行の xfail 相当の印(`@pytest.mark.xfail`・`pytest.xfail(`・`test|it.fails(`・`test|it.failing(`・`expectFailure`・`@unittest.expectedFailure`、新マークの検出の一覧と同じ)を拾い、注釈の欄の欠けを G-6 の確認事項に表示する。**G-5 の合否に使わない**(本文 5.8.5 の後の段落)。欄の欠けを失敗にするなら新しい義務で、ADR-0089 決定3 の「形の検査は合否に使う」は process-compass 自身の回帰の試験の規則であり、採用者の製品のテストに持ち込まない
- 予期せず通った場合の失敗
  - python: アダプタの pytest のコマンドに `-o xfail_strict=True` を足す。採用者の設定に依らず XPASS が失敗になる。試験で確かめられる(delivered にしうる)
  - Jest `test.failing`・Vitest `test.fails`: 枠組みの既定で常に厳格。テンプレートの部品ではないため、delivered の根拠にせず、表に「枠組みの既定に依る」と書く
- 別の理由で落ちた場合の失敗
  - python: `raises=` を持たない xfail を、欄の欠けと同じく表示する
  - JS: 準拠テンプレートに小さな補助(例 `scripts/test-support/known-failure.mjs`。本体を実行し、投げなければ「予期せず通った」で失敗、投げた理由が `match` に当たらなければ「別の理由」で失敗、当たれば通過として記録)を置く。走者を問わずに使え、node:test の `expectFailure` が版で黙って無視される問題(ADR-0089 決定4)を避けられる。process-compass 自身の `knownFailure` の型を採用者向けに移すもの
  - go・JUnit 5 など印を持たない枠組み: 印そのものが無い。採用者が自前の印を作るなら、上の書式と2つの失敗を自ら実装する
- 検出の対象の範囲: 追加行の印と、基底に無い新しいテストのファイルの印。別名経由(`const run = CI ? it : it.skip`)・設定による除外は拾えない旨を開示する

## S-6: IMPL-0102(L2 の採点の稼働)の扱い

## 結論の要約

- **S-1**: 誤りは ADR-0085 決定2 の go の理由の箇条(未実施の通過は本文 G-5 に反し、「黙っては外れない」の前提も成り立たない)。新 ADR で一部置き換え・ADR-0121 を補い、go は構文木で文の開始行を得る方式で coverage.out から全体と変更を測る。猶予なし・取り込みを切り替えの点とし、測れない構成と集計の無いアダプタは失敗。表示の誤りとして直ちに新マークで開示
- **S-2**: 本文を「製品のコードを変えずにテストを変えた変更の検出」と「基底の版のテストの再実行による確認」に書き分け、前者を新マークで delivered、後者を新マークで undelivered・scheduled。近似を IMPL-0204 の delivered に含める私の軽の案は取り下げる
- **S-3**: テンプレートが道具を問わない注釈の書式を定めて欄の欠けを表示し、python は strict と raises、JS は補助で2つの失敗を降ろす。印を持たない枠組み(go・JUnit 5)は新マークで plan=adopter
- **S-4**: マークの主題を「拒否する設定」から本文の禁止そのものへ改め、手順(presence)とマージの後の検出(保証の開示へ出す。合否に使わない)で delivered。拒否はしないと新 ADR に書く。adopter の私の軽の案は取り下げる
- **S-5**: IMPL-0255 は guard-bash が拒否する経路に限って delivered・machine。`git merge`+`git push` の経路は新マークで undelivered・scheduled(#359、IMPL-0250 と同じ部品)。`--base` の付け替えは塞がない
- **S-6**: IMPL-0102 を「記録で示す」の確認へ改め、delivered・manual(確かめる者は変化点の決定者と AI維持管理者)。L2 の null を効かせた出力に「根拠の中身は確かめていない」を定型で出す。機械の検証は課さないと新 ADR に書く
- **S-7**: A は新しいテストのファイルと期待値の対を含め、根拠は PR 本文の表(識別子)を正にして表示だけ。A' は既定ブランチの先端から読み、読めない升とテストのパスを別に表示。C は入力の一覧を PR のコメントにも残す。D の python は branch の意味を開示。IMPL-0479 は #361 へ移す
- **範囲外**: `rulesets` の重複は id を1つにし、重複の鍵を check-impl で検出する。python のテストのファイルの算入と CRLF の試験は本件で直す
