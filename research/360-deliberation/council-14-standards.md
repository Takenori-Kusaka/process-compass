## 0. 規格の目で見た前提の整理

議題の各論点に共通する、語彙と規則の確認です。以下の評価はこの整理に依ります。

1. **G-5 の検査の状態の語は4つで閉じている**。通過・失敗・対象なし(ADR-0033。記録して通す)・未実施(失敗に数える。第4章 G-5「検査対象が存在しない場合の扱い」の最後の段落、ADR-0077、ADR-0121 決定4)。「判定しない」「実施しない」を通過として残す第5の状態は、ADR-0078 の不採用 K-8(「3区分に無い4つ目の状態になり、未実施を通過として残す」)と ADR-0121 の不採用 (c3)(「対象なしにも未実施にも当たらない第3の通過の状態を作る」)が、二度退けている
2. **マークの `state` は2値**(ADR-0084 決定4)。`undelivered` の `plan` は `scheduled`(降ろす予定がある。`issue` と `review`)か `adopter`(準拠テンプレートは実装せず、採用者が自ら実装する。規定は課したまま。`decision`)。「課さない」は `plan` の値にしない。課さないと決めたことは、条項を改めて書く(ADR-0084 決定4・不採用の表)
3. **マークは規定の単位で付け、降りた部分と降りていない部分は分ける**。前例は IMPL-0475(delivered)と IMPL-0239(undelivered)、IMPL-0476(第1段 delivered)と IMPL-0479(第2段 undelivered)。1つのマークに降りた部分と降りていない部分を束ねて `delivered` にすると、降りていない部分が台帳から消える(ADR-0026・ADR-0084 の「降りていない規定を表示し続ける」に反する)
4. **マークの note は、条項が求めていない手段を規定として書いてはならない**。マークは条項を運ぶ。条項が「してはならない」と行為を定めるとき、マークが「拒否する設定」を降ろす対象に書くと、条項に無い義務がマークの側で生まれる(S-4 で効く)
5. **表示の誤りは最優先で直す**(ADR-0084 決定4 の降ろす順序の1段目)。実装より強い記述も弱い記述も、表示の誤りに当たる
6. **採用済み ADR の本文は書き換えない**。決定の一部を置き換えるときは、新しい ADR に置き換える箇所を名指し、置き換えられる ADR のステータスの節に注記を足す(ADR-0085 のステータスの節に ADR-0086・0087・0121 が注記を足した前例)

## S-1: go の基準3 と、ADR-0085 決定2 と ADR-0121 の食い違い

### (a) どちらの ADR が誤りか

**誤りは ADR-0085 決定2 の理由の箇条(go の部分)にあります。ADR-0121 は、その誤りの射程を狭めただけで、単一のスタックの go について誤った前提を追認した点で、誤りを引き継いでいます。** 両立する読み方はありません。

根拠は3つです。

1. **ADR-0085 決定2 の前提は事実として成り立っていない**。決定2 は「go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない」と書きます。実装(`coverage-check.mjs:259-262`)は「判定を実施しない扱いで記録します」と警告を出し、**code 0(通過)**を返します。G-5 の集約は通過として読みます。出荷の証跡の側も、`coverage-result` を取り込まないため(IMPL-0246)、go に限らず全員が「未測定(集計ファイルがありません)」と出ます。go が測られていない事実を、PR の判定でも出荷の開示でも、go に固有の事実として示す経路はありません。「黙っては外れない」は成り立っていません
2. **「実施しない」と記録して通すことは、G-5 の語彙の外の状態である**。§0 の1のとおり、通過として残る「実施しない」は、ADR-0078 K-8 と ADR-0121 (c3) が退けた第5の状態そのものです。go のプロファイルは `coverage.out` として出ており、対象(製品のコード)も存在します。対象なしではありません。測る入力を読まずに通しているので、未実施です。未実施は失敗に数えます(第4章 G-5、ADR-0077、ADR-0121 決定4)
3. **ADR-0121 の内部で扱いが割れている**。ADR-0121 決定4 は、手書きの要素(none の stacks)で受けたスタックについて「報告の無い要素は未実施として失敗に数える」とします(突合 X3-1)。同じ状態(集計の無いスタック)を、言語のアダプタ go で受けた場合だけ通すのは、宣言の形によって基準3 の当て方が変わることになり、ADR-0121 決定1 の「各スタックの検査が、それぞれ集約の合否に入らなければならない」と両立しません。ADR-0121 のステータスの表が「決定2 の理由は、製品のコードが単一のスタックの場合に限って成り立つ」と書いたことが、誤りの追認です。node では成り立ち、go では成り立ちません

外部の整合も同じ向きです。ISO/IEC/IEEE 29119-3 の試験の完了報告は、完了の基準を満たさない場合に「理由の説明」と「逸脱」「残留リスク」を記録して判断へ回す形を取ります(survey-external §5。条文の番号は未確認)。現状の go は、PR の判定で警告を出すだけで、逸脱としての記録も判断への回付もありません。29119 の最低限にも届いていません。本標準の G-5 は、未実施を失敗に数える点で 29119 より厳しい具体化であり、それ自体は 29119 と矛盾しません。外部の道具の既定(Codecov の `if_not_found: success`・diff-cover の未計測の通過)は通す向きですが、Codecov は設定で向きを選べる形を持ち、SonarQube は未被覆として落とす向きです。道具の既定を、本標準の語彙を曲げる根拠にはできません。

### ADR の置き換えの形

新しい ADR(番号は議長が採番)で、次の2か所を置き換えます。採用済みの ADR-0085・ADR-0121 の本文は書き換えません。

| 置き換える箇所 | 新しい ADR での扱い |
| --- | --- |
| ADR-0085 決定2 の箇条「カバレッジの測定の穴は止めない。node では G-5 の test ジョブが失敗し、go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない。…品質保証の委員の『受容の記録が無ければ止める』は、G-5 の失敗と『実施しない』の記録と二重になるため採らない」の**理由の部分** | 理由を「すべてのアダプタで、測れない基準3 は G-5 の未実施として失敗に数えるため、黙っては外れない」に改める。結論(事前点検では止めない)は維持する。品質保証の委員の案を採らない理由も、改めた後の G-5 の失敗との二重として維持する(go の失敗が実装された後に限って理由が成り立つため、実装と同じ変更で採用する) |
| ADR-0121 のステータスの表の ADR-0085 決定2 の行の「製品のコードが単一のスタックの場合に限って成り立つ」 | 「理由は、集計を持つアダプタ(node)の単一のスタックでだけ成り立っていた。go のアダプタでは単一のスタックでも成り立たず、黙った通過が残っていた」に改める。ADR-0121 決定1・決定4 は維持する(本件の決定は決定4 の「未実施は失敗に数える」を言語のアダプタへ同じく当てるもの) |

- ADR-0085 と ADR-0121 のステータスの節に、置き換えの注記を足す(§0 の6 の前例)
- 新しい ADR のコンテキストに、誤りの経路を書く。ADR-0085 の審議で「実施しない」という語が G-5 の語彙と照合されなかったこと、ADR-0121 の審議で単一のスタックの go が実行で確かめられなかったこと。どちらも内部の突合で語彙の照合を欠いた型であり、見直しの契機に「G-5 の状態の語の照合」を足す
- 準拠テンプレートの警告の文「判定を実施しない扱いで記録します」は、語彙の外の語なので改める。表示はゲートの単位で「基準3 未充足」、検査の単位で「未実施(カバレッジを測れない)」とする(ADR-0121 決定4 の表示の語に揃える)

### (b) go で基準3 を測る手段

**推す案: AST で文の範囲を得て、文の開始行へ戻す方式(gocov の型)。** 全体の割合は、プロファイルの文の数(`Σ count>0 の NumStmt / Σ NumStmt`)で出し、`go tool cover -func` の total と一致させる。

| 案 | 評価 |
| --- | --- |
| **AST で文の開始行へ戻す(推す)** | 分母の定義が node(istanbul の文の開始行)・python(coverage.py の文の行)と同じ「変更の行に開始行がある文」になる。ADR-0079 が開示した近似(「変更の範囲の分母が文の開始行で数える近似」)が、そのまま3つのスタックに当たる。ADR-0121 決定4 の「要素ごとに同じ基準値と比べる」は、スタックの間で割合の意味が揃っていることを前提にしている。意味の揃わない割合を同じ基準値と比べるのは、基準値の意味を崩す。外部では gocov・Azure/gocover が実際にソースの AST から文の範囲を得ている(survey-external §1.5 [確認: ソース])。survey.md 論点D §2.2 の「文の開始行を厳密には得られない」は、プロファイル単体の話であり、改める |
| 変更した行に重なるブロックを分母に入れ、文の数で重み(go-patch-cover の型。起案の軽の案) | 採らない。分母に、変更していない文が入る(10 文のブロックの1行を変えると 10 文が分母に入る)。node・python の分母の定義と違う割合を同じ基準値と比べることになる。実務の先例はあるため、「先例が無いから」ではなく「分母の定義が他のスタックと揃わないから」退けると記録する |
| ブロックの開始行だけ(案A) | 採らない。ブロックの2文目以降の行を落とし、取りこぼしが node より大きい |
| ブロックの範囲の全行(案B。sonar-go・gocover-cobertura の既定) | 採らない。空行・注釈・閉じ括弧と、被覆したブロックの継続行を被覆に数え、割合を上へ寄せる(試行で 38.46% に対し文の割合 25%)。sonar-go と gocover-cobertura が採っており、**業界に先例はある**。退ける理由は先例の有無ではなく、割合が上へ寄ることと分母の定義が揃わないことだと記録する |

- 実装の前提: AST の解析には go の処理系が要る。go の採用者の CI では setup-go が既に走っている。解析に失敗したとき、ブロックの方式へ黙って戻してはならない。未実施として失敗にする(戻すと、割合の意味が実行ごとに変わる)
- パスは import のパスから `go.mod` の module で戻す。go.work・replace は扱いを確かめるまで、戻せないパスを「測っていない製品のファイル」に数える(現行の node の扱いと同じ向き。黙って飛ばさない。外部の道具の「ファイルを飛ばす」型は採らない)
- 根拠水準: AST の方式は手元の試行もまだ無い(survey.md は案A・B だけを試行)。CI での実行まで EV で開示する。近似の開示(文の開始行)そのものは事実の開示であり EV は要らない

### (c) 既存の go の採用者に失敗を課す移行

**推す案: 猶予の期間を置かない。ADR-0085 決定6 の保守者の義務(落ちうる検査と直し方の列挙、書き込まずに試す手段の同梱)で告知する。**

- これは採用者への新しい義務ではない。基準3 は go の採用者にも初めから掛かっており、準拠テンプレートが規定に黙って違反していた(ADR-0121 のコンテキストの「条項の空白ではなく、既存の規定への黙った違反」と同じ型)。標準の条項は変えない。審議が重である理由は、ADR の原則(決定2 の理由)の変更にある
- 猶予を置かないことは、ADR-0085 決定5(猶予の期間を置かない。成立しないと分かっている状態を通すため)・決定7(Kubernetes・Renovate の猶予を採らない)・ADR-0121 決定4(猶予の期間は置かない)と整合する。猶予を置く案は、これら3つの採用済みの決定を新しい ADR で置き換える必要があり、置き換える理由(猶予の間の黙った通過を受け入れる理由)を本件で示せない
- 外部の移行の実務(PEP 387・GODEBUG・Evaluate)は、**それまで正当だった挙動**を変える場合の型です。本件は違反の是正であり、GODEBUG でもセキュリティの修正は全版に新しい挙動を当てます(survey-external §2 [確認])。是正に移行の段を当てる根拠は外部にもありません

## S-2: 「テストのみの変更で失敗が解消した変更」(IMPL-0204 の一部)

### 推す案

**履歴型(PR の先頭が更新されるごとの test ジョブの結論と、2つの先頭の間の差分)を検出の手段にする。静的な近似は、規定の検出として数えない。条項の観測の単位を「push された記録」と明記し、push されなかった履歴を検出の対象にしないことを、課さないと決めた事項として書く。**

理由:

1. **条項の文の内部に、観測できない対象が入っている**。条項は「差分から機械で検出し」と書きますが、「失敗が解消した」は差分の性質ではありません。差分だけからは判定できず、どの近似も条項の文を満たしません。規格としては、近似を選ぶ前に条項の観測の単位を直すべきです。「差分と、PR の上で記録された検査の結果から」とし、記録の外(手元で解消して push しなかった失敗)を検出の対象にしないと書きます。手元の側は、5.8.5 の禁止事項3 と、自己修正のロック中のフック(IMPL-0187)が受け持ちます
2. **履歴型だけが、条項の語「失敗が解消した」を記録で示せる**。静的な近似(製品のコードを変えず既存のテストを変えた PR)は、失敗があったかを見ません。失敗の無い PR のテストの整理にも印が付き、本来の対象(失敗をテストで消した変更)と区別できません。IMPL-0203 が既に既存のテストの変更を一覧に出しているので、静的な近似が足すのは「製品のコードの変更なし」の事実だけです。事実として一覧に添えることは妨げませんが、規定の検出を降ろしたと数えてはなりません
3. ImpossibleBench(survey-external §4.3)は、試験の改変が AI の不正の主な型であること、試験を読み取り専用にしても他の型が残ることを示します。近似を `delivered` と表示すると、取りこぼしが台帳から消えます。反対の委員の懸念と整合します

採らない案:

| 案 | 理由 |
| --- | --- |
| 静的な近似を `delivered` と表示する(起案の軽の案) | 条項の語「失敗が解消した」を見ない。降りていない部分が台帳から消える(§0 の3) |
| 再実行型(新しい製品のコードに旧版のテストを流す) | 検出する性質が違う。旧版のテストが落ちて新版が通ることは「期待を変えた」ことを示し、5.8.5 の後の段落の1つ目の箇条(期待値の改めと根拠)の対象である。失敗の解消の検出ではない。加えて、PR の側で製品のコードを流すため、統制の設定を変える PR では信頼しないデータになり(`gate-g5.yml:9-13`)、SWE-bench の事例のとおり新規の試験のファイルの扱いに穴が出やすい |
| G-5 の合否に使う | 条項(この検出を G-5 の合否に使ってはならない)に反する。不安定な試験の修正など正当な変更と区別できない |
| push されなかった履歴の検出を、`undelivered` の別のマークとして残す | 降ろす手段が原理的に無い規定を `scheduled` にすると、計画の無い計画を表示する。`adopter` も、採用者に実装の手段が無い。条項を改めて課さないと書くのが正しい(ADR-0084 の「課さないは plan の値にしない」) |

### 実装マークの扱い

- IMPL-0204 は、検証の弱体化(skip・xfail の付与、アサーションの削除)・テストのみの変更で失敗が解消した変更・根拠を引かない期待値の改めの3つを束ねている。**3つ(と S-3 の印の欄)に分ける**。IMPL-0204 は弱体化の検出に残し、ほかは新しいマークにする
- テストのみの変更で失敗が解消した変更のマーク: 履歴型が実装され、記録した API の応答で違反と適合の対の試験ができるまで `undelivered plan=scheduled`。実装の後は `delivered check=machine`。note に、force-push の前の先頭は timeline の before/after で辿ること、1回の push に積んだ中間のコミットは見えないこと、手元で解消した失敗は対象外であること(条項で課さない)を書く
- 静的な近似の事実(製品のコードの変更なし)を一覧に添えるなら、IMPL-0203 の note に足す。新しいマークにしない(規定を運ばないため)

### 採用者への影響と移行

- 合否に使わないため、新しい失敗は生じない。G-6 の確認事項が増える
- 条項の文の改め(観測の単位の明記)は、採用者に新しい義務を課さない(求める検出の範囲を記録で観測できる部分に限る向き)。新しい ADR に記録する

## S-3: 落ちることを期待する印の欄と、予期せず通った場合の失敗

### 推す案

**準拠テンプレートが印の欄の書式を定める。欄の組は ADR-0089 決定4 の語(Issue・照合する失敗の理由・見直しの時期)に揃え、置き場は枠組みに依らない一覧のファイルとする。欄の欠けは表示に留め、G-5 の失敗にしない。予期せず通った場合・別の理由で落ちた場合の失敗は、枠組みごとに降り方が違うので、枠組みごとにマークを分けて表で開示する。**

1. **書式を定めるのはテンプレートの役である**。条項は欄の中身を定め、書き方を定めていません(survey.md 論点A §4.1)。書き方が決まっていないと、欄の有無を機械で確かめる相手がありません。本標準自身の回帰の試験は、ADR-0089 決定4 で同じ欄を `knownFailure: { issue, match, on, review }` の形で持っています。採用者向けの書式の語を別に作ると、同じ概念に2つの語ができます。欄の名と意味を揃えます
2. **置き場は、枠組みに依らない一覧(例: `tests/known-failures.json` の行ごとに、試験の識別・Issue・照合する理由・見直しの時期)を推す**。Jest・Vitest は印に理由の引数を持たず、Go と JUnit 5 には印そのものが無い(survey-external §4.1 [確認])。注釈の書式を枠組みごとに定めると、枠組みごとに検査が割れます。Chromium の TestExpectations と Mozilla のマニフェストも、試験の外の一覧で Issue と期待する結果を持つ型です(survey-external §4.2)
3. **欄の欠けを G-5 の失敗にしない**。条項は「検証を弱める変更の検出を G-5 の合否に使ってはならない」と書きます。印の付与の検出は、この「検証を弱める変更の検出」そのもので、欄の欠けの検査はその検出に乗ります。ADR-0089 決定3 が形の検査を合否に使ったのは、本標準自身の回帰の試験に限った決定です。採用者の製品の試験へ広げるなら条項の改めが要り、本件で改める理由がありません。加えて、印の検出は正規表現に依り、別名の経由(`const run = CI ? it : it.skip`)を取りこぼします(survey.md §5.1)。合否に使うと、別名へ逃げる誘因を作ります
4. **見直しの時期を過ぎた印を、テンプレートで失敗にしない**。本文は「見直しの時期を過ぎた印を失敗にすることは、…本標準の要求には含めません。本プロジェクトの回帰の試験だけが、その扱いを採ります」と明記しています。テンプレートの検査で採用者に課すと、条項に無い義務がテンプレートの側で生まれます(§0 の4)。過ぎた印の件数の表示は妨げません。6 か月の上限(EV-0183)も持ち込みません
5. **検出の対象**: 追加行の `xfail`・`test.failing`・`test.fails`・`expectFailure`・`@unittest.expectedFailure` の付与と、一覧のファイルの行の追加。基底に無い新しいテストのファイルを含める(§1 の合意)

予期せず通った場合・別の理由で落ちた場合の失敗の降り方(枠組みごと):

| 枠組み | 予期せず通ったら失敗 | 別の理由で落ちたら失敗 | テンプレートが降ろせるもの |
| --- | --- | --- | --- |
| pytest | `strict=True` か ini の `xfail_strict` で得られる | `raises` で例外の型までは限れる。メッセージの照合は無い | `xfail_strict` が設定されているかの検査と表示。照合する理由の一致は降ろせない |
| Jest `test.failing`・Vitest `test.fails` | 既定で得られる(常に厳格) | 例外を限る手段は文書に無い | 予期せず通った場合は枠組みで満たされる旨の開示。照合は降ろせない |
| Go `testing`・JUnit 5 | 印が無い | 印が無い | なし。印を使うなら採用者が補助の関数を書く |

### 採らない案

| 案 | 理由 |
| --- | --- |
| 欄の欠けを G-5 の失敗にする | 上の3。条項の文と衝突し、ADR-0089 決定3 の射程を黙って広げる |
| 見直しの時期を過ぎた印をテンプレートで失敗にする | 上の4。本文が要求に含めないと明記している |
| 注釈の書式を枠組みごとに定める | 枠組みごとに検査が割れ、印の無い枠組み(Go・JUnit 5)で書く場所が無い |
| 照合できない部分を含めて1つのマークで `delivered` | §0 の3 |

### 実装マークの扱い

- 印の欄の書式・検出・欄の欠けの表示: 1つのマーク。実装の後 `delivered check=machine`
- 予期せず通った場合の失敗: pytest の `xfail_strict` の検査を降ろすなら `delivered check=machine`、Jest・Vitest は枠組みの既定に依ることを note に書く
- 別の理由で落ちた場合の失敗(照合): **`undelivered plan=adopter`**。理由は、照合の手段が採用者の試験の枠組みに依存し、主な枠組みが手段を持たないことです(ADR-0084 決定4 の IMPL-0277・0279 と同じ型の理由。「実行の基盤に依存する」)。この節は `impl-no-adopter.yaml` の登録簿に当たりません。`decision=` は新しい ADR の決定とし、上の表を採用者に求めることとして書きます(「印を使うなら、照合する理由が一致しない失敗を試験の失敗にする補助を置く」)。`scheduled` にしないのは、テンプレートが採用者の枠組みごとの補助を持つ計画を示せないためです。計画が立てば `scheduled` へ移せます

### 採用者への影響と移行

- 合否に使わないため、新しい失敗は生じない。一覧のファイルの書式が新しく示される
- 照合を `adopter` にすることは、規定を課したまま(採用者の側の責任であること)を表示する。採用者が印を使う場合に限って効く

## S-4: 人による中間の層のマージ(IMPL-0248・0254)

### 推す案

**`scheduled` でも `adopter` でもなく、マークの運ぶ規定を条項に合わせて直す。条項が求めるのは「してはならない」という行為の禁止であり、拒否する設定ではない。行為の禁止は、手順(指示)とマージの後の検出で降ろし、拒否の設定を本標準は課さないと条項と ADR に明記する。**

1. **IMPL-0248・0254 の note は、条項に無い手段を規定にしている**。条項(第4章「積み重ねた変更とゲート」の2つ目の箇条)は、マージの行為を禁じます。拒否の設定を求めていません。note の「拒否する設定」は、条項の側に無い義務をマークの側で作っています(§0 の4)。人の行為の禁止を、指示の行と検出で降ろす形は、本標準の他の禁止(5.8.5 の禁止事項4「差分を確認せずに承認する」は CLAUDE.md の行で `delivered check=presence`)と同じ扱いです
2. **`scheduled` は事実に反する**。`scheduled` は「降ろす予定がある」です。GitHub と GitLab のどちらにも「中間のマージだけを拒む」設定が無いことを、提供者の文書で確かめています(survey.md B-3、survey-external §3.2・§3.3)。見直しの年月を付けても、降ろす計画は立ちません
3. **`adopter` も事実に反する**。`adopter` は「採用者が自ら実装する」です。採用者も GitHub の上では実装できません。採用者に統制があると誤読されます(反対の委員の指摘を支持する)。ADR-0084 決定4 は「理由を書けない規定は `adopter` にせず」と定めており、採用者に求めることを書けない
4. **外部の実務は、中間のマージを規則でなく道具の手順で避けている**(ghstack・spr・Graphite。survey-external §3.1)。本標準の「手順と事後の検出」は、この実務と同じ性格であり、検出を足す点で実務より強い

マージの後の検出の位置づけ:

- **出荷(G-7)の材料として保証の開示に件数と PR を出す。G-7 の失敗にしない**。既定ブランチへの着地で G-5・G-6 は改めて掛かり、失われるのは層ごとの確認の粒度です(本文の説明の段落)。失敗にすると、本文 1046 行・1050 行の「検出を合否に使わない」系統の判断と釣り合わず、§4 の採らない案とも衝突します
- 検出は禁止の違反の発見なので、**是正(第7章)の入口に結ぶ**。表示だけで終わらせない。出荷判定者が件数を読み、是正の記録を起こすかを決める
- 検出は IMPL-0250(層の合わさった差分への1件の承認を層ごとの確認に数えない。#359)の材料になる。同じ検出を2度作らない
- GitHub 標準のスタックで基底が既定ブランチのものは、検出から除く(EV-0139 の実機未確認を開示に残す)

### 採らない案

| 案 | 理由 |
| --- | --- |
| `plan=adopter`(起案の軽の案) | 上の3 |
| `undelivered plan=scheduled` のまま(反対の軽の案) | 上の2。計画の立たない `scheduled` は表示の誤りの一種になる |
| ルールセットを既定以外へ広げる | ADR-0078 決定3 が採らないと決めた。手動のスタックの直接の push と両立しない(survey.md B-3) |
| 検出を G-7 の失敗にする | 上の「位置づけ」 |
| GitHub 標準のスタックの採用を義務にする | 公開プレビューで提供の範囲が未確認(survey-external §3.1)。採用者の手段の例として手引きに書くに留める |

### 実装マークの扱い

- IMPL-0248 と IMPL-0254 は同じ規定を二重に運んでいる(どちらも人の中間のマージの拒否)。運ぶ規定を2つに分け直す: (i) マージの後の検出(記録の写しの `base.ref`、写しの届かない構成では PR の一覧の API)を出荷の集約が出す — `delivered check=machine`(試験の後)。(ii) 手順の禁止(スタック型 PR の頁と CLAUDE.md の指示の行)— `delivered check=presence`(単位: 行)
- note から「拒否する設定」と「ask で人へ戻る」(事実の誤り。guard-bash は拒否する)を除く
- 識別子は再利用しない。運ぶ規定が条項の同じ箇条であるため、既存の2つの識別子の note を改めて使い、改めた理由を新しい ADR に書く
- 条項(または説明の段落)に「本標準は、中間の層のマージを拒否する設定を課さない。提供者に手段が無い。禁止は手順とマージの後の検出で運ぶ」と書く。却下を本文に残す

### 採用者への影響と移行

- 新しい失敗は生じない。保証の開示に件数が出る
- 記録用ブランチ(records)を初期化していない構成・無償の私有では、写しが届かないため API で引く。引けない場合は「確かめていない」と出し、0 件と出さない(ADR-0085 決定4 の4値と同じ考え方)

## S-5: AI による中間の層のマージ(IMPL-0255)

### 推す案

**`delivered` にしてよいのは、フックが実際に拒否する経路(`gh pr merge`・API による PR のマージ)に限る。通る経路は note に列挙して開示する。あわせて条項の「既定ブランチ以外へ取り込むマージ」の語の範囲を明確にする。**

1. **条項の語に曖昧さがある**。文字どおりに読むと、作業のブランチへ既定ブランチを取り込む同期(`git merge origin/main`)も「既定ブランチ以外へ取り込むマージ」に当たります。括弧の「手動のスタックの中間の層のマージ」が意図を示しますが、規定の文として範囲を確定していません。禁じるのは「既定ブランチへ入っていない他の層の変更を、層のブランチへ取り込むこと」です。手段は PR のマージに限らず、手元の併合と push、他の層の先頭を層のブランチへ push すること(`git push origin B:A`)を含みます。既定ブランチからの同期は含みません。この明確化は新しい義務ではなく、語の範囲の確定です。新しい ADR に記録します
2. **フックは抑止の層であり、完全な拒否を名乗らない**。guard-bash 自身がそう開示しています(survey.md B-6 の1)。`git merge` と `git push` の組、`git push origin B:A`、担い手が書いたスクリプトから API を呼ぶ経路は通ります。全経路を塞げると表示すれば、表示の誤りです
3. **塞げる経路は塞ぐ**。`git merge` の引数が既定ブランチの参照でも現在のブランチの上流でもない場合の拒否は、判定の材料がコマンドの中にあり、正当な同期を巻き込みにくい。フックの拒否に足し、違反と適合の対の試験を置くことを推す(信頼性の向上。抑止の層として)
4. `gh pr create --base <層>`・`gh pr edit --base` は PR を作る・付け替える操作で、マージではありません。手動のスタックの正当な操作です。塞ぎません
5. 塞げない経路(push による取り込み、スクリプトの API)は、S-4 のマージの後の検出と、#359(IMPL-0250)の層の合わさった差分の検出で事後に拾う。AI の側だけ別の検出を作らない

### 採らない案

| 案 | 理由 |
| --- | --- |
| guard-bash の拒否を根拠に全体を `delivered`(起案の軽の案) | 通る経路が残り、表示の誤りになる |
| `gh pr create --base` を拒否する | マージではなく、正当な操作を止める |
| 通る経路を開示せず、検出だけに頼る | フックで塞げる経路(`git merge`)を塞がない理由が無い |

### 実装マークの扱い

- IMPL-0255: 降ろし先を `rulesets` から guard-bash のフックへ移す。`delivered`。`check` は、フックに違反と適合の対の試験があれば `machine`、無ければ `manual`(確かめる者: AI維持管理者。フックかその設定を変えたとき)。note に、拒否する経路と通る経路の一覧を書く
- 通る経路の事後の検出は S-4 の (i) と #359 のマークで運ぶ。IMPL-0255 に束ねない
- note の「ask で人へ戻る」の誤りを直す

### 採用者への影響と移行

- AI の担い手の `git merge` の一部が新しく拒否される(足す場合)。人へ戻す経路で受ける。告知は ADR-0085 決定6 に従う

## S-6: IMPL-0102(L2 の採点の稼働)の扱い

### 推す案

**`delivered check=manual`。確かめる者を名指し、手順を置く。L2 で規模の基準なしを効かせた出力に「根拠の中身は確かめていない」旨を定型で出す。条項に「採点の稼働の機械の検証は課さない」と明記する。**

1. **条項が求めるのは記録で示すことで、機械の検証ではない**。本文(担保水準の表の後)は「水準は自己申告ではなく、条件の充足を記録で示します」と書きます。IMPL-0102 の note の「機械の検証」は、条項に無い手段を規定にしています(§0 の4。S-4 と同じ型)。検査できる条件を条項で定めないと決めた(§1 の合意 E)以上、機械の検証を `scheduled` にしておくのは計画の無い計画を表示することになります
2. **`adopter` は当たらない**。採用者に求めることが「自らの採点を機械で検証する」になり、条項に無い義務を採用者へ渡します
3. **課さないことは条項で書く**(ADR-0084 決定4)。「L1・L2 の宣言の条件の充足は、機械では確かめない。機械が確かめるのは、根拠のパスの実在と見直し日まで。条件の充足は、変化点の決定者が根拠の中身を条件に照らして確かめる」と書き、採らないと決めた案(採点のワークフローの実在・採点の出力の記録の照合を条項にする)を新しい ADR の不採用の表に残す
4. **定型の文を出す**。保証の開示 項目4 の読み方(「検査の手段が構成に書かれていることを、実施と読まない」)と、本文の限界の開示(「根拠の中身(条件の充足)は確かめない」)に合います。node で、無関係な `README.md` を根拠に指した L2 が成立することを確かめています(survey.md E-2)。出力の側で開示しないと、規模の基準なしが効いた事実だけが残り、機械が確かめたと読まれます
5. **宣言者と確かめた者が同じ人のときは、その旨を表示する**。1〜2名の体制では、宣言者と変化点の決定者が同じ人になりえます。確かめる者を名指すだけでは、自己の確認を確認と読ませます。同一である事実を表示し、止めない(体制で避けられないため。独立性の開示の型に揃える)

### 実装マークの扱い

- IMPL-0102 は同じ条項の文(「記録で示します」)に付いているので、識別子を保ち、note を改める: 「L1・L2 の宣言の条件の充足を、変化点の決定者が根拠の中身を L2 の条件に照らして確かめる。手順は /process-change の種別 settings に置く。機械は確かめない(条項で課さない)。確かめる者: 変化点の決定者(宣言を変える /process-change の出力を読むとき)。宣言者と同じ人であれば、その旨を出力に出す」
- `plan`・`issue`・`review` を除く(`delivered` には書けない)
- 手順の実効は実証が無いので、新しい EV で開示する(EV-0006・EV-0084 の本文は書き換えない)

### 採用者への影響と移行

- 新しい失敗は生じない。L2 の採用者は、規模の基準なしが効いた PR の出力に定型の文を見る。宣言を変えるときに、根拠の中身を条件に照らす手順が加わる

## S-7: 一致した部分 A〜E の最終の形

### A(IMPL-0204)

- 検出の範囲: 追加行の skip・xfail 相当の付与、基底に無い新しいテストのファイルの中の付与、削除行のアサーション、同じ hunk の中の削除と追加のアサーションの対(改めた期待値の旧・新として出す。本文は「旧い期待値・新しい期待値・引いた根拠」の一覧を求める)
- 根拠の欄の書式: **PR 本文の表**(`ファイル:行 | 旧 | 新 | 根拠`)を推す。旧・新の列は機械が差分から作り、根拠の列を作成側が埋める。根拠は識別子(ADR の決定・受入基準の行・規程や本標準の条項)に限り、Issue の番号だけは根拠に数えない(本文)。自由記述の理由の欄は求めない(ADR-0089 決定3 の考え方)。識別子が解決できない・欄が無いものを表示する。合否に使わない(§1 の合意)
- 表を置く PR 本文は、判定が指す記録として保管期間のあいだ到達できなければならない(ADR-0078 決定4)。記録の写し(record-copy)が PR 本文の表を運ぶことを確かめる。運ばないなら写しに足す
- 本文の「機械の検出が付けたラベル」と `/human-verify` 順4 の語を、正本(PR のコメントとジョブの要約)に合わせて改める。条項の語の改めなので新しい ADR に記録する

### A'(IMPL-0205)

- 計画は既定ブランチの先端から読む(本文の「PR 単位の検査が読む基準値…は既定ブランチの先端から読む」と同じ原理)。計画が既定ブランチに無い PR(計画を同じ PR で作る)は「計画が既定ブランチに無い」と出し、PR の側の計画と差を参考として出す
- 読めない升は「対象パスを読めない」と出す。0 件として黙らない
- テストのパスは、計画の「テストの方針」の表の置き場を読めればそれと照らし、読めなければ別の枠(計画の対象の外のテストのパス)で出す。差から隠さない(要求事項10 は差を出すことを求め、テストのパスを除いていない)
- 合否に使わない。`delivered check=machine`

### C(IMPL-0253・0155)

- **保存期間**: Actions の成果物・要約の既定の保持(90 日)は、四半期の抜き取りの間隔と同じかそれより短い。ADR-0078 決定4 は「CI 基盤の既定の保持を、保管とみなしません」と定めています。四半期の抜き取りで確かめる記録を、Actions の保持だけに置くことは決定4 に反します。ワークフローが列挙した入力の一覧(パスと sha256)を、記録用ブランチの写しへ運ぶ。一覧はワークフローが作るもので、AI の出力ではないため、書き込みのジョブへ渡しても IMPL-0333 の注入の条件(AI の出力を書き込みのジョブへ渡さない)に当たらない。写しへ運べるまで、保持の部分は `undelivered plan=scheduled` で別のマークにする
- 列挙できる入力の記録と欠落の表示は `delivered`、道具にしか分からない入力は差し込み口の契約(§1 の合意)。実機の確認は IMPL-0464(#361)

### D(IMPL-0259 の python)

- coverage.py の文の行で測り、node と同じ近似(文の開始行)を開示する。開示の文は ADR-0079 の近似の開示に揃え、スタックごとに別の言い回しを作らない
- `# pragma: no cover` の行(excluded_lines)が分母に入らないこと、それが閾値・除外設定の同時変更の検査に掛からないことを開示する(node の ignore の注記と同じ限界)
- パスの区切りと所在(projectDir)の連結は実装の事実。開示は要らない
- python を go と別のマークにする(S-1 の実装マークの2)

### IMPL-0479

- 本件では降ろさない(§1 の合意)。#360 を閉じると、`issue=360` が閉じた Issue を名指すことになる(ADR-0084 決定4 は、閉じた Issue を名指さないことを Issue を閉じる者が確かめるとする)。閉じる前に移す

## 結論の要約

- **S-1**: 誤りは ADR-0085 決定2 の理由(go を「実施しない」と記録して通すことは G-5 の語彙の外の第5の状態で、未実施は失敗に数える)。ADR-0121 はその誤りを単一のスタックで追認した。新しい ADR で両者の該当箇所を置き換え(本文は書き換えずステータスの節に注記)、go は AST で文の開始行へ戻して node・python と同じ近似で測る。測れなければ未実施で失敗。猶予なし(ADR-0085 決定5・7、ADR-0121 決定4 と整合)。告知は ADR-0085 決定6。IMPL-0259 の note の表示の誤りを先に直す
- **S-2**: 履歴型を検出の手段にし、静的な近似は検出として数えない。条項の観測の単位を「push された記録」と明記し、push されなかった履歴の検出は課さないと条項に書く。IMPL-0204 を分け、実装と試験まで `undelivered scheduled`
- **S-3**: テンプレートが ADR-0089 決定4 と同じ語の欄の書式を、枠組みに依らない一覧のファイルで定める。欄の欠けと見直しの時期の超過は表示だけ。照合する理由の一致は枠組みに依るので `undelivered plan=adopter`(新しい ADR に枠組みごとの表)
- **S-4**: `scheduled` も `adopter` も事実に反する。マークが条項に無い「拒否の設定」を運んでいるのを直し、手順(`delivered presence`)とマージの後の検出(`delivered machine`。G-7 の材料・是正の入口、失敗にしない)で降ろす。拒否の設定を課さないことを条項と ADR に書く
- **S-5**: `delivered` はフックが拒否する経路に限り、通る経路を note に列挙する。`git merge` の他の層の参照の拒否をフックに足す。条項の「既定ブランチ以外へ取り込むマージ」の範囲(既定ブランチからの同期を含まない、push による取り込みを含む)を明確にする
- **S-6**: `delivered check=manual`(確かめる者: 変化点の決定者)。規模の基準なしが効いた出力に「根拠の中身は確かめていない」を定型で出し、宣言者と確かめた者が同じなら表示する。機械の検証は課さないと条項に書く
- **S-7**: A は PR 本文の表(旧・新は機械、根拠は識別子)で表示のみ、ラベルの語を本文から改める。A' は既定ブランチの先端の計画、読めない升とテストのパスを隠さず出す。C の保持は ADR-0078 決定4 により Actions の既定に頼らず記録用ブランチへ運び、届くまで別のマークで `undelivered`。D の python は ADR-0079 の近似の開示に揃える。IMPL-0479 は #360 を閉じる前に open の Issue へ移す
- **範囲外**: `rulesets` の重複を直し、id の重複を `check-impl` で失敗にする。python の全体の割合からテストのファイルを除き、文の割合を読む(猶予なし・告知)。CRLF の試験を直す
