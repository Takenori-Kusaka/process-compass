## 論点A: 検証の弱体化の検出(IMPL-0204)と、計画のパスとの突合(IMPL-0205)

### A-1 IMPL-0204: 何を検出するか

#### (1) 推す案

既存の IMPL-0203(`check-pr.mjs` の「既存のテストの変更」)を広げ、次の5類を、PR ごとに1つの一覧として出す。合否には使わない。

| 類 | 検出 | 入力 |
| --- | --- | --- |
| a. skip 相当の付与 | **追加行**の skip の形(`.skip(`・`.todo(`・`xit(`・`xdescribe(`・`@pytest.mark.skip`/`skipif`・`pytest.skip(`・`@unittest.skip*`・`t.Skip*`・`@Disabled`・`@Ignore`・`{ skip: true }` ほか)。`.only(` も他の試験を走らせなくするため含める | 追加行。**基底に無い新しいテストのファイルも対象**にする |
| b. 落ちることを期待する印の付与 | 追加行の `@pytest.mark.xfail`・`pytest.xfail(`・`test/it.fails(`・`test/it.failing(`・`expectFailure`・`@unittest.expectedFailure`・`{ todo: … }` | 同上 |
| c. アサーションの削除 | 削除行のアサーション(現行の ASSERTION) | 削除行 |
| d. 期待値の改め | 同じ hunk の中で、削除行のアサーションと追加行のアサーションが対になるもの。**旧・新の両方**を示す(`:1048` は旧・新・根拠の一覧を求める。現行は旧しか出さない) | hunk の対 |
| e. テストだけの変更 | PR の全体で製品のコードを変えず(規模の算定の製品の行が 0)、かつ a〜d のいずれかがある PR に、PR 単位の印を付ける | PR 全体 |

- 現行の `check-pr.mjs:1957`(`if (!e.removed) continue;`)は、行を足すだけで書ける skip・xfail を素通りさせる。調査が実行で確かめている。a・b は追加行の検査なしには成り立たない
- 新しいテストのファイルの skip も含める。理由: `/implement` は受入基準から別の文脈でテストを先に作る。そのテストが skip で入れば、受入基準が検証されないまま G-5 を通る。「既存の検証を弱める」ではないが、「skip 相当の付与」(`:1046`)に当たる
- ASSERTION の正規表現は、試行で見つかった誤検出を減らす向きで改める。行の注釈の部分を外してから照らす。`should` は `.should` と `should(` の形に限る。取りこぼしの型(`XCTAssert*` など語頭でないもの)も足す。改めた正規表現は、違反と適合の対の場面(#314 の作法)で固定する
- 試行の分母は作った37例であり、実在の分布ではない。誤検出の率は表示の文に書かず、本文の開示に「件数の率は測っていない」と書く

#### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 削除行の検査だけを広げる(Issue の文の読みの1つ) | skip・xfail の付与の多くは行の追加だけで書けるため、主要な弱体化を取りこぼす(調査の実行で確認) |
| 条件つきの skip(`skipif(sys.platform…)`・`if testing.Short()`)を一覧から外す | 正当な場合が多いのは確かである。ただし、正当かどうかの区別を機械に持たせないことが `:1046` の前提である。外せば、条件を書くだけで検出を逃れる経路ができる。一覧には出し、類を「条件つき」と分けて示す |
| 「テストだけで失敗が解消した」を check runs の履歴から判定する(調査の A 型) | 自己修正のループは手元で回り、失敗した状態は push されない。force-push で前の先頭は一覧から消える。拾えるのは「CI で落ちてから、テストだけの push で通った」の場合だけになる。拾えなかったことを読み手が「無かった」と読む危険のほうが大きい。不安定な試験の再実行でも同じ形が出る。手元のループは IMPL-0187(ロック中のテストへの書き込みの遮断)が受け持つ |
| 基底の版のテストを PR の先頭の製品へ流し直す(調査の C 型) | 出力は「期待を変えないと通らなかったテスト」で、d(期待値の改め)の一覧と同じ集合を、別の手段で数え直すことになる。PR の側のコードの実行になり、統制の設定を変える PR では信頼できない(`gate-g5.yml:9-13`) |
| 一覧の件数に上限を置く、または件数で止める | `:1050` が課さないと決めている |

e(静的な近似)は「テストのみの変更で失敗が解消した変更」の**近似**である。製品とテストを同じ PR で変えた場合を拾わない。これを note と本文の開示に書き、`:1046` の4類の1つを完全に降ろしたとは書かない。

### A-2 IMPL-0204: ラベルか、コメント・要約か

#### (1) 推す案

**正本は、PR へのコメント(既存の印 `<!-- pit-in:g6-test-changes -->` の upsert)、ジョブの要約、`evidence/pr-checks.md` の3つとする。ラベルは付けない**。あわせて、`:1083` の「機械の検出が付けたラベル」と `/human-verify` 順4 の「機械判定が付けたラベル」を、「機械の検出が出した一覧(5.8.5 の後の段落)」と改める。

理由:

1. 確認するのは「どのファイルの、どの行が、どう変わったか」である。ラベルはこの中身を運べない。ラベルが運ぶのは「何かある」という1ビットだけで、G-6 の判定者は結局コメントを読む
2. ラベルは書き込みの権限を持つ誰でも外せる。外しても確認事項から消えないようにするには、停止の申し立てと同じく付け外しの履歴で判定する仕組みが要る。そうしても守れるのは1ビットにとどまる。コメントは実行ごとに作り直されるため、手で消しても次の実行で戻る
3. `:1046` 自体は手段を固定していない。ラベルを名指すのは `:1083` の説明の文と note である。現状、テンプレートにはラベルを付ける機械判定が無く、`:1083` と `/human-verify` 順4 は指す先の無い記述になっている。これは食い違いの解消であり、規範の改廃ではない(軽の範囲)

「必須の確認事項」の担保: `/gate G-6` の補助ファイルに、一覧の各行に照らして受入基準の変更との対応を確かめる手順は既にある(`G-6.md:12`)。ここへ a・b・d・e の類を足す。

#### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| ラベルを付ける(note どおり) | 上の1〜3。加えて、PR の側の gate-g5 で付けると PR の側のスクリプトに依る。既定ブランチの側で付けるには書き込みのジョブを分ける型(ai-review.yml の前例)が要る。そこまでして得るものが1ビットである |
| ラベルとコメントの両方を出す | 正本が2つになり、食い違ったとき(人がラベルを外した、など)にどちらを信じるかの規則が要る |
| G-6 の承認レビューの本文に、一覧の各行への言及を機械で求める | 承認者への新しい義務になる(重の範囲)。加えて、言及の文は AI が書けるため、形を満たして中身の無い記録を生む(ADR-0089 決定3 が自由記述の理由の欄を求めなかったのと同じ理由)。本件では採らない。必要なら別の重の審議に送る |

### A-3 期待値の改めの根拠の欄の書式と、G-5 の合否との関係

#### (1) 推す案

- **テンプレートが書式を定める**。置き場は PR 本文の節「## 期待値の改め」の表 `| ファイル | 旧 | 新 | 根拠 |` とする。根拠の升には識別子だけを書く(`ADR-NNNN 決定N`・`F-NNN/AC-N`・規程または本標準の条項番号)。Issue の番号だけの行は根拠に数えない(`:1048`)。自由記述の理由の欄は置かない(ADR-0089 決定3 と同じ理由。AI が埋められる)
- 機械は、d の各候補のファイルについて、次の3つを**表示する**だけにする: (i) 根拠の行が無い、(ii) 識別子が解決できない(`context/decisions/ADR-NNNN*.md` の実在、`specs/F-NNN/spec.md` の受入基準の表の実在)、(iii) Issue の番号だけを引いている
- **G-5 の失敗にはしない**。理由: d の検出そのものに誤検出(行の移動・整形)がある。欠けで止めると、誤検出の行にも根拠の行が要るようになる。作成側は、決定を確かめないまま根拠の行で埋めて通そうとする。これは `:1046` が禁止の理由に挙げた「正当な変更まで止まり、検査の除外が常態化する」と同じ型の害である
- 引いた決定が改めた挙動を本当に定めているかは、機械では確かめない。EV-0182 の事例はここで起きた。G-6 の確認事項として表示の文に定型で添える
- 印(xfail 相当)の欄: 標準 `:1049` は、Issue・照合する失敗の理由・見直しの時期の3つを印に持たせることを求める。枠組みの多くは、この3つの欄を持たない。テンプレートは、印の直前の行の注釈の書式を定める(例 `# known-failure: issue=#123 match="…" review=YYYY-MM`)。b の検出で、欄の欠けた印を表示する
- 「予期せず通った・別の理由で落ちた場合を失敗とする」は、採用者の試験の枠組みの設定に依る。pytest は `strict=True` と `raises=` で近づけられる。Jest の `test.failing` は失敗の理由を照合できない。Go には標準の印が無い。テンプレートは枠組みごとの書き方を `/implement` の補助に示す。**照合できない枠組みは、その旨を開示する**。ここは別のマークに分ける(下記 A-5)

#### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 根拠の欄の欠けを、ADR-0089 決定3 に倣って G-5 の失敗にする | ADR-0089 決定3 が形の検査を合否に使うのは、本プロジェクト自身の回帰の試験である。そこでは場面のデータの `changed` の欄として改めが構造で特定でき、誤検出が無い。採用者の製品のテストでは改めを差分の正規表現で推定するため、誤検出がある。前提が違う。`:1046` の禁止の理由がそのまま当てはまる |
| 根拠をテストのコードの注釈に書かせる(`// basis: ADR-0012 決定2`) | 期待値の行ごとに注釈が増え、残り続ける。後の改めで注釈が古くなっても、それを確かめる手段が無い。PR の単位で改めの一覧と根拠を対にするほうが、`:1048` の「その変更で改めたものに限って示す」に合う |
| 書式を定めず、採用者に任せる | 機械が (i)〜(iii) を表示できなくなる。結果として、根拠を引かない改めは G-6 の人の目だけに頼ることになる |

### A-4 IMPL-0205: 計画の「変更の対象パス」と実変更の突合

#### (1) 推す案

- `readPlanMappings` と同じ型で、`specs/F-NNN/plan.md` の「タスク」の表から「変更の対象パス」の列を読む関数を1つ作る。IMPL-0200(#358。書き込みの範囲を対象パスに限る)も同じ関数を使う。同じ列を2つの読み方で読まない
- **計画は既定ブランチの先端から読む**(IMPL-0249 の `--policy-base` と同じ)。理由: PR の先頭から読むと、同じ PR で対象パスを広げれば差が消える。これは様式07 の「エージェントが自分で範囲を広げてはならない」を素通りさせる
- 既定ブランチに計画が無い場合(スタックの下の層で計画を足した、計画と実装が同じ PR にある)は、先頭の計画で突き合わせる。そのうえで「計画が既定ブランチに無いため、PR の側の計画で突き合わせた」と出す
- PR の中で「変更の対象パス」の列そのものを変えた場合は、その変更を別に一覧へ出す
- 出力は (a) どのタスクの対象パスにも当たらない変更、(b) テストのパス(別枠)、(c) 読めない升(バッククォート無しなど)の3つ。`Spec: setup`・bot・文書だけの PR は対象外として、その旨を出す
- 合否には使わない。`:1079` は「出す」を求めている。止めることは求めていない

#### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 先頭の計画だけで突き合わせる | 上の理由。同じ PR で範囲を広げられる |
| 対象パスの外の変更を G-5 の失敗にする | 採用者への新しい義務(重)になる。計画の誤りかどうかの判断は人に属する(様式07「計画の誤りとして差し戻す」) |
| テストのパスを差から除く | 除外の規則が、テストの置き場に偽装した製品のコードの抜け道になる。別枠で出せば足りる |

## 論点B: 中間の層へのマージの拒否(IMPL-0248・0254・0255)

### (1) 推す案

**ルールセットを手段にしない**。拒否は AI の担い手の経路だけで成り立たせる。人の経路は事後の検出で補う。人について「拒否」が成り立たないことは、`delivered` に見せない。

1. **AI の担い手**: `guard-bash.mjs` が `gh pr merge`(`--auto` を含む)と、マージの API(`gh api -X PUT …/merge`)を一律に拒否している(調査で実行して確認。`test-guard-bash.mjs` に場面がある)。中間の層へのマージもこれで止まる。IMPL-0255(AI への指示の表の強制層)は、降ろし先を `guard-bash-hook` へ移して `delivered` にする。note には、フックが抑止の層であることを書く。止めない経路(`git merge` で上の層を下の層へ併合して push する、担い手が書いたスクリプトから API を呼ぶ)も開示する
2. **人**: GitHub の規則では、既定ブランチ以外へのマージだけを拒否し、層のブランチへの直接の push を許す形を組めない(調査 B-3。提供者の文書で確認。規則は ref の更新に掛かり、経路を区別しない。`bypass_mode=pull_request` は向きが逆)。手動のスタックの運用(層のブランチへ push を重ねる)と両立する拒否は、テンプレートでは降ろせない。IMPL-0248・0254 は `undelivered` のまま、`plan=adopter` に改める。採用者が取れる手段は3つあり、`decision=` の新 ADR に列挙する。(i) GitHub 標準のスタックへ寄せる(EV-0139、実機未確認)。(ii) 組織所有の公開リポジトリか Enterprise Cloud で merge queue を使う。(iii) 手順の遵守と事後の検出に頼る。(iii) では拒否が成り立たないことも ADR に書く
3. **事後の検出(新しいマーク、delivered)**: `record-copy.yml` の写しは `base.ref` を既に残している。基底が既定ブランチでないマージ済みの PR を、出荷の集約(`aggregate-evidence.mjs`)で一覧に出す。GitHub 標準のスタックで基底が既定のものは除く。一覧は、IMPL-0250(#359。合わさった差分への1件の承認を層ごとの確認に数えない)の材料にもなる。**G-7 の失敗には数えない**。表示に留める
4. **note の事実の誤りを直す**: IMPL-0248・0255 の note、`stacked-pr.md:190`、テンプレートの CLAUDE.md の索引の行は「ask で人へ戻る」と書いている。実際はフックが拒否する。実装のほうが強いため、記述を実装に合わせる。`stacked-pr.md:106`・`:109` の「手段は未確定」も、新 ADR の結論へ改める
5. **ADR-0078 との関係**: ADR-0078 決定3(K-4)の「ルールセットの対象を機能ブランチへ広げる案は採らない」は維持する。理由は補強される。文書の範囲では、広げると層のブランチへの直接の push も止まる側に寄る。新 ADR はこれを補足として記録する。ADR-0078 を置き換えない(結論が同じであるため)

### (2) 採らない案

## 論点C: AI の確認の入力の記録(IMPL-0253)と、所在・根拠の欠落(IMPL-0155)

### (1) 推す案

**マークを分ける**。ワークフローが自分で列挙できる部分はテンプレートの決まった手順で降ろす。差し込む道具にしか分からない部分は、差し込み口の契約で受ける。契約が守られなかったことは、機械が表示する。

1. 決まった手順「入力を記録する」(差分の書き出しの後、レビューの実行の前)。既定ブランチのスクリプトが、次の値を `inputs.json` と要約へ書く。指示ファイル・差分・変更したファイルの一覧のパスと sha256、既定ブランチと PR の先頭の SHA、自動で読み込みうるファイルの候補(既知の名前の一覧)。**候補の一覧が網羅でないことを表示に書く**(ADR-0041 と同じ作法)
2. 差し込み口の契約: 差し込みの実装は、道具の実行の記録から、起動の指示・道具の定義・実際に読み込んだ指示ファイルを `tool-inputs.json` へ書く
3. 決まった手順「入力の記録と指摘の欠落を示す」(レビューの後)。次の3つを要約へ表示する。`tool-inputs.json` が無い実行の「確認側へ渡した入力を列挙できない。文脈を渡していない確認として記録してはならない」。候補にあって、読み込んだとも止めたとも申告していないファイル。指摘ごとの所在・根拠の欠落
4. 指摘の構造(`findings.json`)は**勧める**に留める。散文の出力は拒まない。散文には「構造が無いため欠落を検査していない」と表示する。欠落の表示は指摘を消さず、並べ替えない。ジョブを失敗にしない。check run と commit status は出さない(ADR-0115 決定2)。表示の文に「所在が正しい箇所を指すか、根拠が成り立つかは確かめていない」を定型で添える(H.4「構造を満たしたことを内容の根拠にしてはならない」)
5. `claimsExecution`(実行の結果を述べる指摘かどうか)の欄を置く。真で `runRecord` が空なら表示する。この欄は AI の申告であり、偽と申告された実行の主張は機械では拾えない。そのことを開示し、四半期の抜き取りに残す
6. 欠落の表示は、PR へ書くジョブ(`ai-review-notice`)へ渡さない。件数も渡さない。IMPL-0333 の注入の条件(AI の出力を書き込みのジョブへ渡さない)を保つため
7. 保存: 要約の保存期間(既定 90 日。外部未確認)は、四半期の抜き取りの間隔と同じかそれより短い。`actions/upload-artifact` を許す形の一覧へ加え、保存期間を明示する。抜き取りがその期間の内に行われることを `/gate` か AI維持管理者の手順に書く。保存期間の実際の上限は、実装の時に提供者の文書で確かめる
8. 許す形の一覧(`AI_REVIEW_FIXED`、手順の並びの検査、変異の試験)を改める。改めた定義の実機での振る舞いは、IMPL-0464(#361)の (c) に加える

### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 差し込みの `run:` の中で記録させる(今の一覧のままで書ける。調査の試行 B・C) | 採用者の任意の実装になり、テンプレートが降ろしたことにならない。記録が無い実行を、機械が「列挙できない」と表示する根拠も持てない |
| 指摘の構造を契約として課し、構造の無い出力を拒む | H.4「書式を定めない」と、「所在か根拠を欠く指摘を提出の時点で不成立とすることは課さない」の両方に反する |
| 欠落の件数を PR のコメントへ出す | 差分に誘導された出力で件数を操作できる。書き込みのジョブへ AI の出力から導いた値を渡すことになる |
| 道具の申告(`tool-inputs.json`)を、道具が実際に受け取った入力の証拠として扱う | 差し込みの実装が記録を加工できる。H.4 は「入力の記録は、確かめたことを示さない」とする。ここでの表示は「列挙できない」の検出だけに使う |
| `claimsExecution` を置かず、本文の語(「実行した」「通った」)から実行の主張を推定する | 意味の判定を語の照合で代用することになり、誤検出と取りこぼしの両方が大きい。推定であることを読み手が区別できない |
| IMPL-0253 を1つのまま `delivered` にする | 道具にしか分からない入力は、テンプレートが実装しない。1つのマークで `delivered` にすると、部分的な配送を完全な配送に見せる(ADR-0048 決定3) |

### (3) 実装マークの扱い

## 論点D: node 以外の変更の範囲のカバレッジ(IMPL-0259)と、複数のアダプタ(IMPL-0479)

### D-1 IMPL-0259

#### (1) 推す案

**python と go の両方を本件で降ろす**。

- アダプタに `coverageFormat`(`istanbul` / `coverage-py` / `go-coverprofile`)を足す。形式は宣言で決め、中身から推定しない
- **python**: `coverage.json` の `executed_lines`・`missing_lines` は文の開始行の集合であり、node と同じ近似になる(調査で確認)。読み手は `projectDir` からの相対パスを連結し、区切りを `/` に揃える。`excluded_lines`(`# pragma: no cover`)は分母に入らない。行内の pragma が閾値・除外設定の検査に掛からないことは node の ignore の注記と同じなので、同じ開示に並べる
- **go**: プロファイルはブロック単位で、文の行が出ない。調査の案A(ブロックの開始行だけ)と案B(ブロックの範囲の全行)のどちらも採らない。採るのは**案D: 変更した行に重なるブロックを分母に入れ、文の数(`numStmt`)で重みを付ける**。被覆は `count > 0` で判定する。理由:
  - 案A は、開始行が変更の外にあるブロックの中を変えたとき、その変更が分母に入らない。見えない穴になる
  - 案B は、被覆したブロックの空行・注釈・閉じ括弧を被覆に数え、割合を**上へ**寄せる。下限の判定で上へ寄る近似は、通してはならない変更を通す向きに働く
  - 案D は、ブロックの中の文が一緒に実行される(基本ブロック)ことと合う。`go tool cover` の文の割合と同じ単位になる。分母の単位は行ではなく文になるため、結果の `approximation` に形式ごとの近似を書く
- go の全体の割合も、`coverageSummary` を null のままにせず、同じプロファイルから出す(Σ被覆の文 / Σ文)。`go.mod` の `module` 行で import のパスをファイルのパスへ戻す。go.work と replace は扱わず、その旨を開示する
- `NODE_MEASURABLE` の固定をアダプタごとの拡張子へ替える。node 専用の案内の文をアダプタごとにする
- 既存の構成は変えない。新しく生成する python・go の構成は、`coverageDetail` を持つため既定が changed になる。これは ADR-0079 決定1(既定を変更の範囲にし、測れない場合だけ全体)の帰結である。`test-coverage-scope.mjs:62`・`:134` の fixture は、この決定の帰結として改める。過去の決定を覆すものではない

#### go が基準3 を測らずに通している食い違い

- 事実: go のアダプタでは、範囲に依らず基準3 が `measured:false` の code 0 で通る(調査で実行して確認)。ADR-0085 決定2 は、これを「実施しないと記録するため黙っては外れない」と許した。一方 gate-criteria は、宣言の外のスタック(`:714`)と入力を欠いた検査(`:934`)で、未実施を失敗に数える
- 推す扱い: **IMPL-0259 で go が測れるようになれば、go についての食い違いは解消する**。null のアダプタを code 0 で通す経路(`coverage-check.mjs:259-263`)そのものは、none の手書きの要素の外と undetermined にも残る。これは IMPL-0234(#330「任意の検査のコマンドが空のときは通知を出して通す」)の範囲なので、#330 へコメントで寄せる。本件ではその経路を失敗に変えない。失敗に変えると ADR-0085 決定2 の理由を置き換えることになり、軽の範囲を超えるためである
- 既存の go の採用者は、テンプレートを取り込むと基準3 が初めて判定され、落ちる場合がある。締める向きの変更であり、ADR-0085 決定6 に従って、落ちうる検査と直し方(下限の較正、`coverageScope` の選択)を影響の節へ列挙する。猶予の期間は置かない(ADR-0121 と同じ理由。猶予の間は黙った通過が続く)

#### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| python だけを降ろし、go は undelivered のまま残す | go の近似は案D で行と文の単位の差を開示すれば足りる。残せば、go の基準3 が測られずに通る状態が続く。測れる手段が手元で確かめられた以上、残す理由が信頼性の側に無い |

| 既存の go・python の構成の範囲を changed へ書き換える | 範囲の選択は企画時の決定である(ADR-0078 決定6)。テンプレートの取り込みで黙って書き換えない |

## 論点E: L2 の採点の稼働の機械の検証(IMPL-0102)

### (1) 推す案

**検査できる条件を条項で定めない**。機械の検証を課さないと決めたことを、新 ADR に記録する。L2 の条件の充足は、宣言の変化点で人が根拠の中身を読んで確かめる。この手順をテンプレートに置く。

理由:

1. テンプレートで L2 が効くのは、規模の基準値を null にできることだけである。効く範囲も狭い(R3・区分の下限が R3・コアのパスに触れない変更。`check-pr.mjs:1286`)。L2 は G-6・承認・委任の扱いを変えない
2. 調査の候補のうち、ファイルの実在で確かめる候補1は、常に低いスコアを返すジョブでも通る。機械の検査が成り立ったように見えて、中身を確かめない。これは今の「根拠のパスの実在」と同じ型の確かめを、もう1つ重ねるだけになる
3. 候補3(閾値と審査深度の対応の照合)は、テンプレートに審査深度を変える機構が無いため、照合の相手が無い
4. 候補2(全 PR に採点の出力があるか)は検査できる。ただし、採用者に「採点の出力を記録に残す」という新しい義務を課すことになる。採用の事例は EV-0006 の単一事例だけである。この状態で検査の条件を条項に書けば、根拠の無い条件を規範にすることになる

### 推す案の補い(テンプレートの手順)

- `/process-change` の `kinds/settings.md` の担保水準の節に、次の手順を置く: 決定者は、L1・L2 へ上げるとき、`basis` が条件(L2 では採点の稼働と取り消し可能性)の充足を示すかを読む。機械は中身を読まない(無関係な README を指しても成立することを、調査で実行して確かめた)
- この手順を置いたうえで、IMPL-0102 の主題を「L2 の条件の充足を記録で示すこと(`:1854`)」に改める。`delivered check=manual` にし、確かめる者は「変化点の決定者(L1・L2 へ上げるとき、根拠の中身を条件に照らして読む)」と AI維持管理者(統制の設定の承認)とする。note には、機械の検証を課さないと決めたこと(新 ADR)と、根拠の中身を機械が読まないこと(`:1955`)を書く
- 手順を置かないなら、IMPL-0102 は `undelivered` のまま残す。主題を変えて `delivered` に見せることはしない

### (2) 採らない案

| 案 | 採らない理由 |
| --- | --- |
| 候補2(採点の出力の記録の存在を出荷の集約で確かめる)を条項にする | 採用者への新しい義務(重)。根拠は単一事例(EV-0006)。採点の正しさは確かめられない |
| 候補1(採点のワークフローの実在)を確かめる | 中身を確かめない形の検査を足すだけになり、「機械が確かめた」という誤った安心を生む |
| IMPL-0102 を `plan=scheduled` のまま残し続ける | 条件を定めないと決めた以上、降ろす予定は無い。予定の表示が偽になる |
| IMPL-0102 を、手順を足さずに `delivered` へ書き換える | 確かめる者の手順が無いまま主題だけを変えると、降りていない規定を降りたように見せる(ADR-0048 決定3) |
| L2 の宣言を自己申告のまま受ける(手順を置かない) | ADR-0058 の不採用の表 `:114` が退けた形骸化の型である |

### (3) 実装マークの扱い

IMPL-0102 は、上の手順を `settings.md` へ置いたうえで `delivered check=manual`(降ろし先 `process-change-skill`)とする。`decision=` は不要だが、機械の検証を課さないことは新 ADR の「課さないと決めたこと」に書く。見直しの契機は2つ置く。採用者が L2 を宣言した事例が現れたとき。テンプレートが審査深度を変える機構を持ったとき。

### (4) 新しい義務になるか

推す案では、ならない(条件を条項で定めないため)。もう1委員が候補2 などの条件を定める案を推した場合は、受付の定めどおり重へ上げる。

## 新 ADR(1本)に記録するもの

- A: ラベルではなく一覧を正本にしたこと。根拠の欄の書式。根拠の欄の欠けを G-5 の失敗にしないこと(ADR-0089 決定3 との前提の違い)。印の照合が枠組みに依る部分を `adopter` にしたこと
- B: ルールセットで中間の層へのマージだけを拒否できないこと(提供者の文書、2026-11-12)。人の側を `adopter` にした理由と、採用者の手段の選択肢。事後の検出を出荷の判定に数えないこと。ADR-0078 決定3 を補足し、置き換えないこと
- C: 道具にしか分からない入力を `adopter` にしたこと。構造を勧めに留めたこと
- D: go の近似に案D を選んだこと。IMPL-0479 を #330 へ送ったこと。go の採用者への締める向きの影響
- E: L2 の採点の稼働の機械の検証を課さないこと。見直しの契機

## 結論の要約

- **A**: skip・xfail は追加行(新しいテストのファイルを含む)で検出し、削除・改めは旧と新を対にして出す。テストだけの変更は静的な近似として開示する。正本はラベルではなく、コメント・要約・証跡の一覧とし、`:1083`・`/human-verify` の「ラベル」は改める。期待値の根拠の欄は、PR 本文の表(識別子だけ)としてテンプレートが書式を定める。欠けは表示だけで G-5 の合否に使わない。IMPL-0205 は計画を既定ブランチの先端から読み、表示だけにする。IMPL-0204・0205 は delivered。印の照合のうち枠組みで照合できない部分は、新しいマークの adopter に分ける。新しい義務にはならない
- **B**: ルールセットは手段にしない(文書の範囲で、手動のスタックと両立する拒否を組めない。ADR-0078 決定3 を補足し、維持する)。AI の側は guard-bash の拒否で IMPL-0255 を delivered にする。人の側の IMPL-0248・0254 は adopter と新 ADR にする。写しの `base.ref` による事後の検出を、表示だけの新しいマークとして降ろす。note の「ask」は「guard-bash が拒否」へ直す。新しい義務にはならない
- **C**: マークを分ける。ワークフローが列挙できる入力の記録と、「列挙できない」・所在と根拠の欠落の表示は、決まった手順で delivered にする(IMPL-0253 の一部と IMPL-0155)。道具にしか分からない入力は、差し込み口の契約に置き、新しいマークの adopter にする。構造は勧めに留め、合否に使わず、PR へ書くジョブへは渡さない。新しい義務にはならない
- **D**: IMPL-0259 は python と go の両方を delivered にする(go は重なるブロックを文の数で重み付けする。go の基準3 が測られずに通る食い違いはこれで解消する。null の経路そのものは #330 へ寄せる)。IMPL-0479 は、動的な matrix の未検証の穴があるため本件では降ろさず、#330 へ移して実機の確認を受け入れ条件にする。新しい義務にはならない
- **E**: 検査できる条件を条項で定めない(新しい義務を課さないため、軽のまま)。`/process-change` に、根拠の中身を条件に照らして読む決定者の手順を置いたうえで、IMPL-0102 を delivered(manual)にする。手順を置かないなら undelivered のまま残す
- **範囲外**: rulesets の id の重複と CRLF の試験の欠陥は、本件で直す(同じ作業で触るため)。python の全体の割合の水増しは本件で扱うことを推す(議長が範囲外と裁けば既存の Issue へ寄せる)。null のアダプタの通過は #330 へ寄せる
