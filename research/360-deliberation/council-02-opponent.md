# 会議体(軽) 委員2: 反対(#360)

- 日付: 2026-11-12
- 立場: 反対。起案の意見(council-01)は読んでいない。受付 `intake.md`・調査 `survey.md` と、本文・ADR・テンプレートの該当箇所を自分で読んで書いた
- 判断軸: 信頼性。変更量・費用は採否の理由に使わない
- Issue 本文の「各規定を降ろして delivered にする」は起票者の案として扱い、前提に置かない

## 0. 総論: 本件で delivered と書くことの危険

調査の結果を読むと、10件のうち「マークの全部を機械が確かめる形で降ろせる」ものは1件も無い。どのマークにも、機械が確かめられる部分と確かめられない部分が混ざっている。たとえば、検出の取りこぼし、AI の道具の実際の受け取り、実機の GitHub の挙動、引いた決定の中身がそうである。

`implementation-marking.md` は「マークは規定ごとに付ける。1つのマークで節の規定がすべて済んだと扱わない」と定め、「迷ったら弱い値を書く」と定める。本件で最も大きい危険は、1つのマークに束ねた複数の規定を、確かめられる部分だけで delivered に変えることである。そうすると、確かめていない部分が台帳から消える(偽の安心)。

そこで、全論点に共通する条件を先に置く。

| # | 共通の条件 | 理由 |
| --- | --- | --- |
| K-1 | 1つのマークが束ねる規定のうち、確かめられない部分は**新しいマークへ分け、`undelivered` のまま表示する**。前例は IMPL-0333(delivered)と IMPL-0464(実機で確かめていない部分。undelivered)の分割 | 降りていない規定は消さずに表示し続ける(CLAUDE.md #222、ADR-0048 決定3「降りないものを、降りたように見せない」) |
| K-2 | 機械の出力のうち「0 件」「欠落なし」「対象なし」は、**検出した形の一覧と、検出しない形の一覧を同じ出力に定型で添えて**出す | 5.8.6 要求事項9(拒否が0件であることを根拠にしない)と同じ型の誤読が、検出の一覧でも起きる |
| K-3 | `check=machine` にしてよいのは、違反と適合の対の試験(`:ng`/`:ok`)がある部分だけである。実機の GitHub・実際のモデルで確かめていない部分には、その旨を note に書く | `implementation-marking.md` の machine の要件。「3つの確かめは試験の中身が規定を正しく確かめていることを示さない」 |
| K-4 | 表示だけの検出は、誤検出を減らしてから出す。誤検出が多いまま出すと、読む者が一覧を読み飛ばすようになり、必須の確認事項が形骸化する | 5.8.5 の後の段落が合否に使わない理由として挙げる「検査の除外が常態化する」と同じ現象が、表示でも起きる |

## 論点A: IMPL-0204(検証の弱体化の検出)

### A-1 反対する点と、代わりに求める条件

**(a) IMPL-0204 を1件の delivered にすることに反対する。** note は性質の違う4つを束ねている。

| 束ねたもの | 機械で確かめられる範囲(調査 5.1〜5.3) | 判定 |
| --- | --- | --- |
| ① 追加行の skip 相当・落ちることを期待する印の付与、削除行のアサーション | 形の検出はできる。取りこぼしがある(別名経由の skip、早期の return、注釈化、設定での除外、製品のコード側の無効化、採用者独自の印) | 降ろせる |
| ② テストのみの変更で失敗が解消した変更 | 厳密には判定できない(調査 5.2)。静的な近似 B は、製品とテストを同じ PR で変える場合を取りこぼす。自己修正のほとんどはこの場合である | 近似だけで delivered にしてはならない |
| ③ 根拠の決定を引かずに改めた期待値 | 根拠の欄の有無と、識別子が解決できるかまでは確かめられる。引いた決定が挙動を定めているかは確かめられない(EV-0182 の事例そのもの) | 欄の検査だけ降ろせる |
| ④ ラベルを付けて「必須の確認事項」にすること | 一覧を出すことはできる。G-6 の判定者が実際に確かめたかを機械で担保する経路は無い(調査 2.2) | 「示す」までは降ろせる。「確かめた」は人 |

求める条件は次のとおり。

- ①は delivered(check=machine)にしてよい。ただし、試験は追加行の skip・xfail の場面を `:ng` に持つこと(現行の IMPL-0203 は削除行だけを見るため、行の追加だけで書ける付与を素通りする。調査で実行して確かめた事実)
- ②は**別のマークへ分け、undelivered のままにする**。近似 B を降ろす場合も、出力名は「テストだけの変更(製品のコードの変更なし)」とする。「テストのみの変更で失敗が解消した変更」と名乗ってはならない。名乗ると、取りこぼした大半(製品とテストを同時に変えた自己修正)を確かめたと誤読させる。近似 C(基底の版のテストを先頭の製品のコードで流す)は「期待を変えないと通らなかった」を実行で示せる唯一の案だが、PR の側で製品のコードを実行するため、統制の設定を変える PR では信頼できない。実機の確認も無いため、本件では採らない
- ③は「根拠の欄が無い」「解決できない識別子を引いた」の表示までとする。出力に「引いた決定が改めた挙動を定めているかは確かめていない」を定型で添える(K-2)。識別子の実在の確認は、AI が実在する ADR 番号をもっともらしく埋めれば通る。欄が揃ったことを根拠の成立として表示してはならない
- ④は、出力を G-6 の材料として示すところまでを delivered とする。判定者が確かめたことは `check=manual`(確かめる者: G-6 の判定者)と note に書く。承認レビューの本文に項目ごとの言及を求める形は、採用者への新しい義務なので本件(軽)では採らない

**(b) ラベルを正とすることに反対する。コメント(一覧)を正とし、ラベルは使わないか索引に限る。**

- ラベルは書き込みの権限を持つ誰でも外せる。外せば、G-6 の確認事項が見えなくなる。停止の申し立てと同じく付け外しの履歴で判定する形にすると、新しい判定の経路が増え、その経路の試験が要る
- 現行の pr-rules は PR の側のスクリプトで動く(`gate-g5.yml`)。ラベルを付ける処理を足しても強度はコメントと変わらない。既定ブランチの側(gate-g5-base)へ置くなら、書き込みのジョブを分ける型(ai-review.yml の前例)が要る。また、ラベルの付与に要る権限は調査で確かめていない([推測])
- 標準の本文 `human-ai-boundary.md` の「機械の検出が付けたラベル」(要求事項10 の後の段落)と `/human-verify` の順4 は、指す先が無い記述である。本件でラベルを付けないなら、この2か所を「機械の検出が出した一覧」へ直す。これは要求の変更ではなく、指す先の食い違いの解消である(5.8.5 の後の段落そのものは「必須の確認事項として示す」とだけ書き、手段を固定していない)

**(c) 合否に使わない条項との関係。** 根拠の欄の欠けを G-5 の失敗にする案に反対する。

- 5.8.5 の後の段落は、検証を弱める変更の検出を G-5 の合否に使うことを禁じる。③の候補は「削除行のアサーション」の正規表現で特定するため、①と同じ誤検出(注釈の `should`、試験名の `should`、移動・整形)を持つ。誤検出の行に根拠を求めて失敗にすると、正当な PR が止まる。止まった PR では、もっともらしい識別子の埋め込みが常態化する。これは ADR-0089 決定3 が自由記述の理由を求めない理由と同じ現象である
- ADR-0089 決定3 が欄の形の検査を合否に使うのは、process-compass 自身の回帰の試験に限る。回帰の試験は、場面を構造で書き、対象を誤検出なく特定できる。採用者の製品のテストは、そうなっていない。前提が違うので、ADR-0089 を採用者へ広げる根拠にはならない

**(d) 誤検出の削減を、降ろす条件に含める(K-4)。**

- 現行の ASSERTION の `should`・`Equal` は語として広い。呼び出しの形(`\bshould\s*\(` など)に絞るか、削除行と追加行を組で見て「同じ行の移動」を除く
- 基底に無い新しいテストのファイルの skip・xfail も一覧に入れる。新しい受入基準のテストを最初から skip で入れることは、既存の検証の弱体化ではない。しかし、その受入基準を検証していないことになる。現行は対象外である

**(e) 本文 `human-ai-boundary.md` の要求事項10 の後の段落にある「何も出ていないときに痕跡を読む作業は求めません」との緊張を指摘する。**

検出には構造的な取りこぼしがある(調査 5.1)。そのため、「出ていなければ読まなくてよい」は、検出の網羅の範囲を人の確認の範囲にしてしまう。文を改めて「読むこと」を課すと新しい義務になるため、本件では改めない。代わりに K-2 に従い、出力に「検出しない形」を列挙し、5.8.5 の後の段落に取りこぼしの形を限界として開示する。開示は義務を足さない。

**(f) 落ちることを期待する印の欄と挙動に、マークが無い。** 5.8.5 の後の2つ目の箇条には、印に Issue・理由・見直しの時期を持たせることと、予期せず通った場合・別の理由で落ちた場合を試験の失敗とすることが書かれている。これは実行主体の挙動を制約する規定である。しかし、IMPL-0204 の note は「付与の検出」だけを持ち、欄と strict の挙動にはマークが無い(定義の欠け)。テンプレートは枠組みごとに欄を強制できない(pytest の xfail は reason と strict を持ち、Issue と時期の欄を持たない。Jest・Go には相当が無い。調査 4.2 [推測])。新しいマークを足し、undelivered と表示する。plan を scheduled にするか adopter にするかは議長が決める。ここを IMPL-0204 の delivered に含めてはならない。

### A-2 受け入れられる案

- check-pr.mjs の既存の一覧(IMPL-0203)を広げる形にする。対象は、追加行の skip・xfail・only、新しいテストのファイル、削除行のアサーション(誤検出を絞る)、テストだけの変更(製品のコードの変更なし)、期待値の旧・新の対、根拠の欄の有無と解決。どれも合否に使わず、PR のコメントとジョブの要約へ出す
- 根拠の書き場所は PR 本文の節(例「## 期待値の改め」)とする。根拠は識別子で書き、Issue 番号だけは根拠に数えない。欄が無いことは表示するだけにする
- 出力の末尾に、検出する形・検出しない形・確かめていないこと(根拠の中身)を定型で置く
- 本文の「機械の検出が付けたラベル」と `/human-verify` 順4 を「一覧」へ直す

### A-3 実装マークの扱い

| マーク | 扱い |
| --- | --- |
| IMPL-0204 | 範囲を①と③の表示へ絞り、`delivered check=machine test=template/scripts/gate/test-check-pr.mjs`。note に「合否に使わない。0 件は弱体化が無いことを示さない。引いた決定の中身は確かめない」を書く |
| 新マーク(②) | テストのみの変更で失敗が解消した変更の判定。`undelivered plan=scheduled`。近似を降ろした場合も、近似の名前と取りこぼしを note に書く |
| 新マーク(④の人の側) | G-6 の判定者が一覧の各項目を確かめること。`check=manual`(確かめる者: G-6 の判定者)。既存の G-6 のマークに含まれているなら足さない(突合で確かめる) |
| 新マーク(f) | 落ちることを期待する印の欄と strict の挙動。`undelivered` |

### A-4 新しい義務か

①〜④の表示は義務を足さない(軽のまま)。次の場合は重へ上げる。根拠の欄の欠けを G-5 の失敗にする場合、承認レビューに項目ごとの言及を課す場合、本文の「痕跡を読む作業は求めません」を改める場合。

## 論点A': IMPL-0205(計画の対象パスと実変更の突合)

### A'-1 反対する点と、代わりに求める条件

- **計画を PR の先頭から読むことに反対する。** 先頭から読むと、同じ PR で対象パスを広げれば差が消える。様式(テンプレ7)の「エージェントが自分で範囲を広げてはならない」は、そのまま素通りになる。計画は既定ブランチの先端から読む(IMPL-0249 と同じ「判定される側が用意した材料で判定しない」の型)。あわせて、PR の中で「変更の対象パス」の列を改めたこと自体を一覧に出す
- **既定ブランチに計画が無い場合を「差なし」にしてはならない。** 計画と実装を同じ PR に入れた場合などは、「計画が既定ブランチに無いため突き合わせていない」と出す(ADR-0028 の未達と省略の区別)
- **対象パスが広すぎて突合が空になる場合を表示する。** `**` や `src/**` を書けば差は常に 0 になる。広さの良し悪しは機械に判断させない。ただし、対象パスがリポジトリの製品のファイルの大半に当たる場合はその旨を出す。0 件の差が「範囲内に収まった」と読まれるのを防ぐためである(K-2)
- **テストのパスを黙って差から外さない。** 外すと、テストの書き換えが範囲の外にあっても見えなくなる。テストのパスは別枠で出す
- 読めない升(バッククォートが無い、文章)は「対象パスを読めない」と出す。readPlanMappings の方針と揃える
- 合否には使わない。要求事項10 は「出す」だけを求めている。止めると、範囲の外の正当な修正(計画の誤り)を差し戻す手続が、計画の改めではなく検査の回避に流れる
- IMPL-0200(#358)と同じ列を読むため、読む関数を1つにする。2つの読み方が分かれると、書き込みの範囲と突合の範囲が食い違う

### A'-2 受け入れられる案

調査 5.4 の案のうち、次の組み合わせなら受け入れられる。計画は既定ブランチの先端から読む。列の変更を一覧に出す。テストは別枠で出す。読めない升と計画が無い場合を表示する。合否に使わない。

### A'-3 実装マークの扱い

`delivered check=machine`。ただし、試験に次の場面がある場合に限る。範囲外の変更の `:ng`、範囲内の `:ok`、同じ PR で対象パスを広げた場面、計画が既定ブランチに無い場面。note に「範囲の広さの妥当性は確かめない」を書く。

### A'-4 新しい義務か

ならない(軽)。

## 論点B: IMPL-0248・0254・0255(中間の層へのマージの拒否)

### B-1 反対する点と、代わりに求める条件

**(a) ルールセットを既定ブランチ以外へ広げる案に反対する。** ADR-0078 決定3(K-4)は、「ルールセットの対象を機能ブランチへ広げる案は採りません」と決めている。調査 B-3 の文書の読みでは、広げれば層のブランチへの直接の push も止まる見込みがある。その場合、手動のスタックそのものが成り立たない。しかも「止まる」は文書からの推論で、実機では確かめていない。確かめていない手段を採って ADR-0078 を置き換えることは、信頼性の向上にならない。

**(b) 「ルールセットでは成り立たない」を事実として書くことにも反対する。** 調査が確かめたのは提供者の文書の範囲であり、【推論】を含む(`update` 規則がマージを止めるか、既定以外を対象にした必須チェックが直接の push を拒むか)。降ろさない理由を ADR に書くなら、根拠水準のマーク(EV)を付け、見直しの年月を置く。差し替え条件には「提供者が、経路(push と PR のマージ)を区別する規則を提供した場合」と「実機の確認で文書の読みが外れた場合」を書く。

**(c) AI の側を guard-bash.mjs のフックで delivered にすることに、条件を付ける。**

- フックは `gh pr merge` を一律に拒否する(調査で確かめた事実)。3件の note が書く「ask で人へ戻る」は実装より弱い記述であり、直す必要がある。ただし、フックは抑止の層であり、`git merge` と `git push` の組を通す(調査 B-4 で確かめた事実)。この組は、上の層を手元で下の層へ併合して push する経路で、効果は中間の層への取り込みと同じである
- したがって、IMPL-0255 を「AI 単独では中間のマージに至らない」と書いて delivered にすることに反対する。至る経路が実在する。delivered にするなら、範囲を「AI の担い手による PR のマージ(`gh pr merge`・マージの API)の拒否」に限る。`git merge` と `git push` の経路が止まらないことを note に書く

**(d) 人の中間のマージを `plan=adopter` にすることに反対する。**

- adopter は「採用者が自ら実装する。規定は課したまま」という意味である。しかし、採用者も GitHub の上では実装できない。merge queue は組織所有の公開リポジトリか Enterprise Cloud の私有に限られ、個人所有では使えない。採用者が実装できない規定を adopter にすると、実装が無いまま統制が台帳の上で済んだように見える
- 正しい表示は、「拒否の手段が提供者に無いため、人の中間のマージは手順の遵守と事後の検出で扱う。拒否は降りていない」である。拒否のマーク(IMPL-0248・0254)は `undelivered` のまま残す。`decision=` で新しい ADR を指せるよう、plan は scheduled のまま見直しの年月を置く。台帳から消してはならない

**(e) 事後の検出(調査 B-6 の案6)は採る。ただし、拒否と書かない。**

- record-copy の写しの `base.ref` が既定ブランチでないマージを、出荷の集約で一覧に出す。記録が届かない構成では、API の PR 一覧から代わりに引く
- 検出は「層ごとの確認の粒度が失われた」ことを示すだけで、マージを止めていない。出力にその旨を書く
- 検出を G-7 の失敗にする場合、または人の記録(受容の記名)を求める場合は、採用者への新しい義務になる。本件(軽)では表示に留める

**(f) 降ろし先の重複を先に直す。** `src/data/impl-targets.yaml` で `rulesets` の鍵が2回定義され、後勝ちで `team.json` が有効になっている。3件の実在の検査はこの値で行われている。範囲外の発見として流すのではなく、本件のマークの検査に直接掛かる欠陥として、本件で直すべきである。

### B-2 受け入れられる案

1. ルールセットを広げない(ADR-0078 決定3 を維持)
2. 新しい ADR で「中間の層へのマージを拒否する手段がホスティングに見当たらない」ことを記録する。EV マークと見直しの年月を付け、未確認の点(調査 B-6 の (a)〜(c))を列挙する
3. AI の側は、既存のフックの拒否を範囲を限って記録する。`git merge` と `git push` の経路は止まらないと開示する
4. 人の側は事後の検出を降ろし、表示に留める
5. note の「ask」の誤りと、impl-targets の重複を直す

### B-3 実装マークの扱い

| マーク | 扱い |
| --- | --- |
| IMPL-0248・0254(人を含む拒否) | `undelivered` のまま。target を rulesets から外すか、正しい降ろし先へ改める。note に「ホスティングに手段が見当たらない(EV)。事後の検出は新マーク」と書く |
| IMPL-0255(AI への指示の強制層) | AI による PR のマージの拒否に範囲を限るなら、`delivered`(target=guard-bash-hook。フックの試験が拒否の `:ng` と通過の `:ok` を持つなら machine、持たないなら manual)。`git merge` と `git push` の経路は新マーク(undelivered)へ分ける |
| 新マーク(事後の検出) | `delivered check=machine`(試験がある場合)。note に「止めない。検出は事後」と書く |

### B-4 新しい義務か

拒否を降ろさない記録、事後の検出の表示は、義務を足さない(軽)。次の場合は重へ上げる。ルールセットを広げて ADR-0078 決定3 を置き換える場合、検出を出荷の失敗にする場合、受容の記名を求める場合。

## 論点C: IMPL-0253・0155(入力の記録、所在・根拠の欠落の表示)

### C-1 反対する点と、代わりに求める条件

**IMPL-0253(入力の記録)**

- **ワークフローが列挙できる入力の記録を、「確認側へ渡した入力の記録」として delivered にすることに反対する。** 列挙できるのは、ワークフローが用意したものと、道具が読み込みうるものの上限である。モデルが実際に受け取ったものではない。とくに作業ツリーの全体は checkout され、読み取りの道具は禁じられていない。そのため、「読み込みうるファイルの候補」の一覧は網羅でも実際でもない。表示に「上限であり、実際に読み込まれたものではない」「既知の名前の一覧であり網羅ではない」を定型で添える(K-2、ADR-0041 の作法)
- 道具の側の入力(起動の指示、道具の定義、実際に読み込んだ指示ファイル)は、差し込みの実装が書く契約のファイルに依る。テンプレートが確かめられるのは、ファイルの有無と欄の揃いまでである。**この部分を別のマークへ分ける**(K-1)。契約のファイルが無い実行には、「確認側へ渡した入力を列挙できない」と表示する。表示があれば欠けが見えるため、adopter にしても統制は消えない。そのため、この部分は plan=adopter を受け入れられる(decision は新しい ADR)
- **保存期間の食い違いを解かないまま delivered にすることに反対する。** note は「AI維持管理者が四半期の抜き取りで確かめる」と書く。一方、要約の保存期間は既定 90 日と見られ、四半期の間隔より短い([外部未確認])。抜き取りの時点で記録が消えていれば、確かめる者の手順は空になる。artifact の保存期間を明示して残すか、抜き取りの手順を保存期間の内側に置くかを決め、決めた内容を note に書く。保存期間は提供者の文書で確かめる
- 許す形の一覧(`AI_REVIEW_FIXED`)を改めずに、差し込みの `run:` の中で記録を書く形(調査の試行 B・C)は、採用者の任意の実装であり、テンプレートが降ろしたことにならない。この形で delivered にしてはならない

**IMPL-0155(所在・根拠の欠落の表示)**

- **`claimsExecution` のような、AI が自分で申告する欄を機械が信じる形に反対する。** 実行の結果を述べながら申告を偽にした指摘は、欠落の表示を素通りする。欄を置くなら、出力に「実行の結果を述べているかは、AI の申告に依る。機械は本文を判定していない」を定型で添える。欄が無いことによる見逃しを、表示の側で明らかにする
- 「欠落なし」を内容の成立として表示してはならない(ADR-0075 決定10、H.4)
- **実際のモデルの出力で確かめないまま delivered にすることに反対する。** fixture の JSON で lint を試験しても、実際の道具は散文しか返さないかもしれない。その場合、表示は毎回「構造が無いため欠落を検査していない」になり、読まれなくなる(K-4)。IMPL-0464(b)と同じ限界であり、実機の確認(#361)を済ませるまで、実際の出力に効くかは undelivered として表示する
- 欠落の件数を、書き込みのジョブ(`ai-review-notice`)へ渡さない。調査 3.3 のとおり、差分に誘導された出力で件数を操作できる。IMPL-0333 の注入の条件にも反する
- 構造は契約として「勧める」に留める。散文を拒まない(ADR-0028・ADR-0075 決定10)

### C-2 受け入れられる案

調査 5.1 の骨子(入力を記録する決まった手順、差し込み口の契約、欠落を表示する決まった手順。いずれも既定ブランチのスクリプトで、合否にせず、指摘を消さない)は受け入れられる。ただし、次の4つを条件とする。許す形の一覧を改め、変異の試験を足す。定型の限界の文を添える。保存期間を解く。マークを分ける。

### C-3 実装マークの扱い

| マーク | 扱い |
| --- | --- |
| IMPL-0253 | ワークフローが列挙できる入力の記録に範囲を絞り、`delivered check=machine`(test=test-base-judge-workflow.mjs と新しいスクリプトの試験) |
| 新マーク(道具の側の入力) | `undelivered plan=adopter decision=<新 ADR>`。テンプレートは契約と「列挙できない」の表示までを持つ |
| IMPL-0155 | 欄の欠落の表示に範囲を絞り、`delivered check=machine`。note に「所在の正しさ・根拠の成立・実行の申告の真偽は確かめない。AI維持管理者の抜き取り」を書く |
| 新マーク(実機) | 実際のモデルの出力で、契約のファイルと表示が出ること、注入で表示を偽装できないこと。`undelivered plan=scheduled issue=361`(IMPL-0464 へ寄せられるなら新設しない) |

### C-4 新しい義務か

ならない(軽)。条件は2つある。構造を「勧める」に留めること、欠落を失敗にしないこと。構造を課す場合、または欠落を合否に使う場合は、ADR-0075 決定10 との関係が変わるため重へ上げる。

## 論点D: IMPL-0259・0479(node 以外の変更の範囲、複数のアダプタ)

### D-1 反対する点と、代わりに求める条件

**(a) go のアダプタが基準3 を測らずに通している食い違いを、IMPL-0259 の実装の副産物として黙って解消することに反対する。**

- 現状、go では基準3 が範囲に依らず code 0 で通る(調査 2.3 で実行して確かめた事実。coverage-check.mjs は警告を出して「判定を実施しない扱いで記録」する)
- この扱いは、採用済みの ADR-0085 決定2 が理由として明記している。「go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない。これは ADR-0028 の『未達』ではない」。ADR-0121 も、この理由の射程を単一のスタックに限っただけで、理由そのものは維持している
- 一方、ADR-0121 は手書きの要素(none の stacks)の報告の無い要素を未実施として失敗に数える。同じ「集計が無い」状態が、go では通過、none の要素では失敗になる。これが既存の決定どうしの食い違いである
- IMPL-0259 で go に被覆を足すと、coverage.out が出ない構成は失敗に変わる。既存の go の採用者には締める向きである。これは ADR-0085 決定2 の理由の一部を否定し、go の採用者に新しい失敗を課す。**この部分は重へ上げるべきである。** 軽の2委員で決めてよい範囲を超える。どちらの決定が誤りかを決める突合も要る

**(b) python は降ろしてよい。ただし、近似と穴を開示する。**

- coverage.json の `executed_lines ∪ missing_lines` は文の開始行で、node と同じ近似になる(調査で実行して確かめた事実)
- 行内の除外の注記(`# pragma: no cover`)は分母から外れる。また、閾値・除外設定の同時変更の検査(thresholdFiles)に掛からない。新しく足した製品のコードに注記を書けば、変更の範囲の分母から黙って外せる。node の `/* istanbul ignore */`・`/* c8 ignore */` も同じ穴であり、本文に開示が見当たらない。変更の範囲の分母を「測っていない」に寄せるかは本件で決めなくてよい。少なくとも、除外の注記で外した行の数を結果に出す。それができないなら、限界として開示する
- `source` を書かない既定では、全体の割合にテストのファイルが入る。`branch = True` では `percent_covered` の意味が変わる(調査で確かめた事実)。changed の判定はテストを除くため影響しない。ただし、同じ PR の結果に並ぶ whole の値の意味が揺れる。範囲外として既存の Issue へ寄せてよいが、本件の開示の文には書く
- パスの区切り(Windows では `\`)と projectDir の連結は、試験で `:ng` を持たせる

**(c) go の行への落とし方は、割合を上げる向きの案を採らない。**

- 案B(ブロックの範囲の全行)は、被覆したブロックの空行・注釈の行・閉じ括弧の行を被覆に数え、割合を上げる(試行で 25% → 38.46%)。基準値と比べる値が甘くなる向きの近似は、信頼性を下げる
- 案A は分母を取りこぼす。代わりに次の案D を候補として試すよう求める。変更の行に1行でも掛かるブロックを数え、そのブロックの文の数(numStmt)で重みを付ける。これは go 自身の文の割合を、変更に触れたブロックへ限ったものになる。どの案を採るにしても、go の近似は node・python と別の近似として開示し、根拠水準のマーク(EV)を付ける。実際の go の採用者の分布で確かめた事例は無い

**(d) IMPL-0479 を本件で delivered にすることに反対する。**

- 動的な matrix の空の配列、脚の失敗の `needs.result` への伝わり方、成果物の名前の衝突は、実機の GitHub Actions でしか確かめられない(act は無い)。空の matrix が「飛ばし」になれば、集約は Success と読む。これは ADR-0121 が塞いだ「if: で飛ばしたジョブを Success と報告する」穴を、別の経路で開け直すことになる
- 第1段で宣言の外の通過は既に塞がっている(ADR-0121)。第2段が無いことによる不足は、利便と、手書きの要素で changed を測れないことである。急いで未検証のワークフローを出荷する理由にはならない
- 降ろすときの条件は2つである。一時のリポジトリでの実機の確認を受け入れ条件に入れること。空の matrix を明示の失敗にする手順を置くこと。順序は IMPL-0259 の後とする

### D-2 受け入れられる案

- IMPL-0259 を python について降ろす(形式の宣言 `coverageFormat`、読み手の一般化、拡張子の固定の撤去、案内の文、試験)
- go は、(a) の決定を重で行ってから降ろす。重の結論が出るまでは、go の「実施しない」を通過とする現状を、本文の基準3 の節に開示する。開示は義務を足さないため、軽で行ってよい
- IMPL-0479 は undelivered のまま(review=2027-05)にする

### D-3 実装マークの扱い

| マーク | 扱い |
| --- | --- |
| IMPL-0259 | python と go を分ける。python の部分は `delivered check=machine test=template/scripts/gate/test-coverage-scope.mjs`。fixture の「python は whole」(test-coverage-scope の 62・134 行)は決定の変更として改め、改めた根拠をこの審議の決定に引く(ADR-0089 決定3 の型)。go の部分は新マークで `undelivered`、重の結論を待つ |
| IMPL-0479 | `undelivered` のまま。note に「実機の確認を降ろす条件とする」を書く |
| 新マーク(除外の注記) | 行内の除外の注記が thresholdFiles の検査に掛からないこと。開示か検出かを決めるまで `undelivered` |

### D-4 新しい義務か

python は軽のまま。**go は重へ上げるべきである**。ADR-0085 決定2 の理由を否定し、既存の go の採用者に基準3 の失敗を新しく課すためである。IMPL-0479 は降ろさない限り義務を足さない。

## 論点E: IMPL-0102(L2 の採点の稼働の検査できる条件)

### E-1 反対する点と、代わりに求める条件

**(a) 条件を条項で定める案に反対する(本件では)。**

- 調査 E-3 の候補のうち、最も検査しやすい候補2(PR ごとの採点の出力の記録)は、常に低いスコアを返すジョブでも通る。条件を条項に書けば、「条件を満たした」が採点の妥当性の根拠として読まれる。これは偽の安心であり、ADR-0058 の採らなかった案「L1・L2 の宣言を自己申告のまま降ろす → 形骸化する」と同じ帰結になる
- 候補3(閾値と審査深度の対応の照合)は、テンプレートが審査深度を変える機構を持たないため、照合の相手が無い
- 条件を定めることは採用者への新しい義務であり、受付の定めにより重へ上げる対象である。軽で定めてはならない

**(b) ただし、「定めない」で現状を据え置くことにも反対する。** 現状には偽の安心が実在する。

- 本文は「水準は自己申告ではなく、条件の充足を記録で示します」と書く。ところが、根拠に無関係な `README.md` を指した L2 の宣言が `valid: true` になり、R3・コア外の変更で規模の基準なし(null)が効く(調査で実行して確かめた事実)
- 機械が「L2 の宣言は有効」と出すたびに、読み手は条件の充足が確かめられたと読む。限界の開示は gate-criteria.md の別の段落にあるが、出力の側には無い

求める条件は次のとおり(どれも義務を足さない)。

1. 規模の基準なしを L2 の宣言で効かせた PR の出力に、「L2 の宣言の根拠は実在と見直し日だけを確かめた。採点の稼働と取り消し可能性は確かめていない」を定型で出す(K-2)
2. 「条件を条項で定めない」と決めるなら、それを「まだ定めていない」と区別して記録する(CLAUDE.md の「却下は成果である」)。ADR-0058 決定5 は「検査できる条件が定まっていない」ため undelivered としており、これは保留の書き方である。本件で定めないと決めるなら、理由(候補2 は定数のスコアで通る。候補3 は照合の相手が無い)と見直しの契機を、新しい ADR か本件の決定に書く
3. 本文の「条件の充足を記録で示します」の確かめ手(現状は IMPL-0101 の変化点の決定者)を IMPL-0102 の note に名指す。確かめる者のいない「記録で示す」を残さない
4. IMPL-0102 の plan を見直す。本件で「定めない」と決めた後も scheduled と review=2026-11 のままにすると、予定があるかのような表示になる。見直しの年月を EV-0006 の見直し(2027-08)へ揃えるなど、表示を実態に合わせる

### E-2 受け入れられる案

条件を条項で定めない。そのうえで、E-1 の1〜4を行う。L2 の緩和は規模の基準なしに限り、R3・下限 R3・コア外という機械の限定を保つ。この限定が、確かめられない宣言の被害を抑えている。

### E-3 実装マークの扱い

IMPL-0102 は `undelivered` のまま。note に次を書く。定めないと決めた理由と記録の所在、確かめる者(変化点の決定者・AI維持管理者)、出力に限界を出すこと。出力の定型の文には新しいマークを付ける(delivered、試験で `:ng`/`:ok`)。

### E-4 新しい義務か

「定めない」と決める限り、ならない(軽)。**起案が条件を条項で定める案を推す場合、結論が割れるため重へ上げるべきである。**

## 結論の要約

- **A(IMPL-0204)**: 1件の delivered に反対する。skip・xfail の追加行、アサーションの削除、根拠の欄の有無の表示(合否に使わない。コメントを正とし、ラベルにしない)だけを delivered にする。「テストのみの変更で失敗が解消」と、落ちることを期待する印の欄・strict の挙動は、別マークで undelivered とする。根拠の欄の欠けを G-5 の失敗にするなら重へ上げる
- **A'(IMPL-0205)**: 計画を既定ブランチの先端から読み、列の改め・計画の不在・広すぎる対象パスを表示し、合否に使わないことを条件に delivered を受け入れる。軽
- **B(IMPL-0248・0254・0255)**: ルールセットを広げない(ADR-0078 決定3 を維持)。人の拒否は undelivered のまま、ADR に EV 付きで理由を残す(adopter にしない)。AI は PR のマージの拒否に範囲を限って記録し、`git merge` と `git push` の経路を開示する。事後の検出は表示として降ろす。impl-targets の重複を直す。検出を出荷の失敗にするなら重へ上げる
- **C(IMPL-0253・0155)**: ワークフローが列挙できる入力の記録と、欄の欠落の表示だけを delivered にする。道具の側の入力は plan=adopter、実機の確認は #361 の側で undelivered とする。保存期間の食い違いを解くこと、自己申告の欄を信じないこと、構造は勧めるに留めることを条件とする。軽
- **D(IMPL-0259・0479)**: python は近似と除外の注記の穴を開示して delivered にする。**go は重へ上げるべきである**(測らずに通す現状は ADR-0085 決定2 が明記しており、解消は採用者へ新しい失敗を課す)。それまでは現状を開示する。IMPL-0479 は実機の確認を条件として本件では降ろさない
- **E(IMPL-0102)**: 条件を条項で定めない(定めるなら重へ上げる)。ただし据え置きにはせず、規模の基準なしを効かせた出力への限界の定型、「定めない」決定と理由の記録、確かめる者の名指し、plan と見直しの年月の修正を求める
