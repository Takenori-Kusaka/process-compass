- 本文の規定(第4章「積み重ねた変更とゲート」): 既定ブランチ以外へ取り込むマージをしてはならない
- 本文の規定(5.8.6 要求事項10): 実装計画の対象のパスと実際に変更されたパスの差を機械で突き合わせて出す

## 2. 議題

### S-1(重大度「高」): go の基準3 と、ADR-0085 決定2 と ADR-0121 の食い違い

- 事実: go のアダプタ(`template/adapters/go.json`)は `coverageSummary` が null で、coverage-check.mjs は基準3 を測らずに code 0(通過)・警告だけにする。範囲を「変更」にした構成だけは契約検査が止める。whole と範囲の記録の無い構成は止まらない
- ADR-0085 決定2(90 行): 「カバレッジの測定の穴は止めない。node では G-5 の test ジョブが失敗し、go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない」
- ADR-0121 決定4: 手書きの要素で受けたスタックも基準3 を未実施のまま通さない。報告の無い要素は未実施として失敗に数える
- 問い: (a) どちらの ADR が誤りか(または両立する読み方があるか)。(b) go で基準3 を測る手段(coverage.out からの全体・変更の範囲。行への落とし方: ブロックの開始行 / 範囲の全行 / 変更行に重なるブロックを文の数で重み)。(c) 既存の go の採用者に新しい失敗を課すなら、移行の扱い(猶予・警告の期間・表示・記名)。(d) 測れない構成(coverage.out が出ない)の扱い

### S-2: 「テストのみの変更で失敗が解消した変更」(IMPL-0204 の一部)

- 厳密な機械判定はできない(survey.md 論点A 5.2)。静的な近似(PR で製品のコードの変更が無く、既存のテストを変えた)、履歴型(push ごとの check runs)、再実行型(新しい製品のコードに旧版のテスト)の3つ
- 問い: どれを降ろすか、近似を delivered と表示してよいか、別のマークに分けるか

### S-3: 落ちることを期待する印の欄と、予期せず通った場合の失敗

- テンプレートには xfail・skip の語も無い。枠組みごとに印の機能が違う(pytest strict xfail・Jest test.failing・Vitest test.fails・Go は無い)
- 問い: テンプレートが印の書式(Issue・照合する失敗の理由・見直しの時期)を定めるか、検出の対象をどこまでにするか、照合できない枠組みのマークの扱い

### S-4: 人による中間の層のマージ(IMPL-0248・0254)

- GitHub の規則ではマージだけを拒否できない(survey.md 論点B)。採用者も GitHub の上では実装できない
- 問い: `plan=adopter`(採用者が実装する)か `undelivered` のまま `scheduled` か、別の表示か。マージの後の検出をどう位置づけるか(表示か、出荷の材料か)

### S-5: AI による中間の層のマージ(IMPL-0255)

- guard-bash は `gh pr merge` を拒否する(実行で確認)。`git merge` と `git push` の組、`gh pr create/edit --base` の付け替えは通る
- 問い: delivered と表示してよい範囲、通る経路を塞ぐか開示するか

### S-6: IMPL-0102(L2 の採点の稼働)の扱い

- 検査できる条件を条項で定めない点は合意(§1)。残る問い: マークを delivered(manual。確かめる者を名指す手順を置く)・undelivered・adopter のどれにするか。L2 で規模の基準なしを効かせた出力に「根拠の中身は確かめていない」旨を出すか

### S-7: 一致した部分 A〜E の最終の形

- §1 の合意のうち、実装の形で決めるべきこと: A の検出の範囲(新しいテストのファイル、削除と追加のアサーションの対、根拠の欄の書式を PR 本文の表にするか)、A' の対象パスの読めない升とテストのパスの扱い、C の記録の保存期間(Actions の既定 90 日と四半期の抜き取り)、D の python の近似の開示、IMPL-0479 の扱い(#360 に残すか、既存の別の Issue へ移すか)
