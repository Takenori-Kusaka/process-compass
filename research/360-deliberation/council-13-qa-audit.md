4. 基底の側のジョブ(`gate-g5-base.yml:148`)は、既定ブランチの `check-pr.mjs` を、PR の先頭をデータとして流しています。結果はジョブの要約へ書きます(`check-pr.mjs:2090`)。つまり IMPL-0203 の一覧は、**既定ブランチのコードで計算した写しが既に要約にある**。PR の側(`gate-g5.yml` の pr-rules)のコメントは、PR の側のスクリプトで計算したものです

## S-1(重大度「高」): go の基準3 と、ADR-0085 決定2 と ADR-0121 の食い違い

### (a) どちらが誤りか(見解)

**誤りは ADR-0085 決定2 の go の句です。ADR-0121 が「補う」の表に書いた射程の限定も、その誤りを一部引き継いでいます。ADR-0121 決定4 の原則は正しいと判断します。**

理由は次のとおりです。

1. ADR-0085 決定2 の句は「go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない」です。この句は、**未実施を記録することを、外れないことの十分条件として扱っています**。しかし第4章 G-5 は、通過と未実施を区別し、未実施を失敗に数えるよう求めます。根拠は次の4か所です
   - 934 行: 入力を欠いて実施できなかった検査
   - 714 行: 宣言の外のスタック
   - 998 行: 「実施していない検査が通過として残る」状態の否定
   - 保証の開示 項目4: 未実施と通過の区別
2. 現在の実装は、警告と `measured:false` を残したまま G-5 を通過させます。これは「未実施の記録つきの通過」です。本文が禁じる、対象なしでも未実施(失敗)でもない第3の状態に当たります。ADR-0121 は「(c3) 告げて開示するだけで通す」を、まさにこの理由で退けました
3. 「黙っては外れない」の事実の前提も弱いものです。記録は警告の1行と、出荷の集約の「未測定」だけです。台帳のマークも本文の開示もありません(前提の事実1)。`go.json` の note は、判定がどこかで行われていると読ませます(事実2)。黙っていない、とは言えません
4. ADR-0085 決定2 は、品質保証の委員の「受容の記録が無ければ止める」を退けました。理由は「G-5 の失敗と『実施しない』の記録と二重になる」です。go には G-5 の失敗がありません。したがって、**退けた理由も go については成り立ちません**
5. ADR-0121 の「補う」の表は、決定2 の理由が「製品のコードが単一のスタックの場合に限って成り立つ」と書きます。go の単一スタックでは成り立ちません。この限定は、ADR-0085 の誤りを単一スタックの側に残しています。一方、ADR-0121 決定4 の「手書きの要素で受けたスタックも基準3 を未実施のまま通さない。報告の無い要素は未実施として失敗に数える」は、第4章と整合します。言語のアダプタだけが同じ状態を通すと、手書きの要素より言語のアダプタの方が緩くなります。これは逆転です

**扱い**: 新しい ADR を起こし、ADR-0085 決定2 の go の句と、ADR-0121 の「補う」の表の射程の記述を置き換えます(採用済み ADR の本文は書き換えません)。

- ADR-0085 決定2 の結論は維持する。結論とは「事前点検ではカバレッジの測定の穴を止めない」ことである
- 止める位置は G-5 の基準3(coverage-check)とする。これは ADR-0121 と同じ置き方である

両立する読み方は採りません。両立させるには、「実施しない」の記録を対象なしか通過のどちらかに数える必要があります。どちらも第4章に反します。

### (b) go で基準3 を測る手段

**推す案: プロファイル(`coverage.out`)と、ソースの AST から得る文の開始行を組み合わせる(gocov 系の方式)。**

- 全体の割合: プロファイルの `Σ(count>0 の NumStmt) / Σ NumStmt` で出す。`go tool cover -func` の total と一致する(survey 論点D §2.2 で確認)。`coverageSummary` に null を置く状態を無くす
- 変更の範囲: 次の手順で数える
  1. ソースを `go/parser`・`go/ast` で読み、文の開始行を得る
  2. 各文に、それを含むブロックの回数を割り当てる
  3. 変更の追加行に開始行がある文を分母に入れる
- 1つの基本ブロックの中の文は、すべて同じ実行回数を持つ。したがって、文ごとの被覆は**近似ではなく正確**である。近似は「どの文を変更とみなすか」だけに残り、node・python と同じ「文の開始行」の近似になる。近似の開示を1本にできる
- 外部の先例: gocov・Azure/gocover が AST で文の範囲を得ている(survey-external §1.5)。survey 論点D §2.2 の「文の開始行を厳密には得られない」は、プロファイル単体の話であり、前提を改める
- 補助の go のプログラムは、テンプレートの `scripts/gate/` に置き、test ジョブの中で `go run` で流す。go のアダプタの環境には setup-go があるため、新しい依存は要らない

**採らない案と理由**

| 案 | 採らない理由 |
| --- | --- |
| 範囲の全行(gocover-cobertura の既定・sonar-go) | 閉じ括弧・空行・被覆したブロックの継続行を被覆に数え、割合を上へ寄せる(試行で 38.46%。文の割合は 25%)。上へ寄る誤差は、基準値の判定で通してはならない変更を通す向きの誤差である。業界に先例はある。先例が無いから退けるのではない |
| ブロックの開始行だけ | ブロックの2文目以降の変更を分母から落とす。node より取りこぼしが大きく、近似を別に開示する必要が生じる |
| 変更に重なるブロックを分母に入れ、文の数で重みを付ける(go-patch-cover・軽の起案) | 実務の先例があり、AST を要さない利点はある。しかし、変更していない文をブロックごと分母に入れる。大きなブロックの1行の変更で、変えていない文の被覆が割合を決める。近似の向きが node・python と違い、開示が2本になる。AST の案が取れる以上、劣る |

**実装マーク**:

- IMPL-0259 を分ける。python と go の変更の範囲の測定を `delivered check=machine`(違反と適合の対を持つ試験。`test-coverage-scope.mjs`)にする
- 新しいマークを起こし、「go のアダプタで基準3 を全体の範囲でも測り、報告が無ければ未実施として失敗に数える」ことを `delivered check=machine` で示す。ADR-0121 決定4 と同じ規定を言語のアダプタへ降ろすもので、IMPL-0476 の手書きの要素の扱いと対になる
- 試験の固定(`test-coverage-scope.mjs:62`・`:134`)は過去の決定を固定している。新しい ADR を引いて改める

### (c) 既存の go の採用者に新しい失敗を課す移行

**推す案: 猶予の期間・警告の段・基準線を置かない。テンプレートの取り込み(種別 `intake`。記名の自然人)の時点で新しい判定が効く形とする。** これは既存の仕組みそのものです。

- 外部の型(GODEBUG の「宣言した版に既定を結びつける」)は、本標準では ADR-0085 決定5・決定6 がすでに満たしている。採用者は取り込みを行うまで旧い判定のままであり、取り込みは記名を要する強制層の変更である
- 保守者の義務(`standard-editions.md` 79 行〜)に従い、テンプレートの README の告知に次を列挙する
  - 落ちうる検査(coverage-check の go の判定、範囲の記録が無い構成の whole の判定)
  - 直し方(テストを足す、または基準値を /process-change で分けた変更として改める)
  - 書き込まずに試すコマンド(`node scripts/gate/coverage-check.mjs` を手元で流す)
- **本文の側にも開示を足す**。「この版より前の準拠テンプレートの go の構成は、基準3 を測らずに G-5 を通す」と書く。対象は、取り込みをまだ行っていない採用者である。ADR-0085 決定6 の `template.commit` で、構成がどの版から来たかを読める。監査人はその版を見て、基準3 の判定の有無を判断できる
- 過去の出荷は遡って判定し直さない。出荷の証跡はすでに「未測定」を出しており、記録として誠実である。取り込みの変化点の記録に「以前の出荷は基準3 未測定であった」旨を書かせる(`/process-change intake` の欄。記録の手順であり、新しい義務ではない)

**採らない案と理由**

| 案 | 採らない理由 |
| --- | --- |
| 猶予の期間・`informational` の段(外部の通例) | 段の間、G-5 の緑と基準3 未測定が並ぶ。それこそが本件の欠陥である。ADR-0085 決定5・決定7、ADR-0121、`standard-editions.md` 90 行が猶予を退けている。外部で通例であることは、成立しないと分かっている状態を通す理由にならない |
| 既存の go の古いコードを基準線として凍結する(Clean as You Code・ratchet) | ADR-0085 決定7 が「基準を満たさないまま進める4つ目の経路」として退けた。閾値の緩和と機械で区別できない。なお、範囲を changed にした構成は、もともと新しいコードだけを測る。古いコードで落ちる心配は whole を選んだ構成に限られ、それは採用者が選んだ範囲である |
| 既存の構成の範囲を黙って changed へ読み替える | 緩める向きの黙った読み替えに当たる(ADR-0085 決定7)。既存の構成は値を変えない。新しく生成する構成だけが、`generate-profile` の既定で changed になる |

### (d) 測れない構成(coverage.out が出ない)

**推す案: すべて失敗(未実施)とし、理由を出す。通過の分岐を残さない。**

| 場合 | 扱い |
| --- | --- |
| `coverage.out` が無い | 失敗(既存の「集計ファイルが無い」と同じ) |
| プロファイルを読めない、または形式が違う | 失敗 |
| `go.mod` が projectDir に無い、`go.work` の複数 module、`replace` で戻せないパス | 失敗。「この構成は測れない」と理由を出す。手書きの要素(`none` の `stacks`)で受ける道を案内する |
| 製品の `.go` ファイルがプロファイルに載らない(パターンの外、ビルドタグ) | changed では未計測として失敗(既存の node と同じ)。whole でも一覧に出し、失敗にする。go 1.22 以降は、テストの無いパッケージも 0 として載る。載らないことは、測る対象の外にあることを意味する |
| ツールチェーンが 1.22 より前 | テストの無いパッケージが載らず、whole の割合が上へ寄る。プロファイルの頭の行やツールチェーンの版を読み、1.22 より前なら失敗にする。少なくとも、上へ寄る旨を開示する |

**採らない案**: 測れないときに警告で通す現状の分岐。理由は (a) の 1〜3 と同じです。

**即時の修正**: `go.json` の note の誤った記述を削ります。go の実装が本件で入らない場合も、暫定として `coverageSummary` null の通過を「未実施(失敗)」に改めます。測れないまま緑を出す期間を作りません。

## S-2: 「テストのみの変更で失敗が解消した変更」(IMPL-0204 の一部)

**推す案: 別のマークに分ける。静的な近似は、範囲を名乗る表示として降ろす。規定の本体は `undelivered` で残す。**

1. 新しいマーク A: 静的な近似。PR 全体で製品のコードに変更が無く、基底にあるテストを変えた PR に「テストだけの変更」と出す。`delivered check=machine` とする。note には「静的な近似。同じ PR で製品のコードも変えた場合と、ローカルで解消した失敗は検出しない」と書く
2. IMPL-0204 のうち「テストのみの変更で失敗が解消した変更」の部分: `undelivered plan=scheduled` とする。降ろす手段は再実行型(案C)を目標とする。案C は、PR の先頭の製品のコードに対して、基底の版のテストを流す方式である。降ろす条件は実機の CI での確認とする(IMPL-0479 と同じ理由)
3. 出力は、該当が 0 件のときも、近似が見ない場合を定型の文で必ず出す。本文 1083 行の「何も出ていなければ読まない」と組み合わさると、0 件が「解消は起きていない」と読まれるためである

**採らない案と理由**

| 案 | 採らない理由 |
| --- | --- |
| 近似を IMPL-0204 に含めて delivered(軽の起案) | 外部の測定(ImpossibleBench)では、試験の改変が主要な型である。そして、同じ PR で製品と試験を変える自己修正が多数を占める。近似はその多数を見ない。delivered の表示と 0 件の表示が重なると、見ていない部分を確かめたと読ませる。ADR-0048 決定3(降りないものを降りたように見せない)に反する |
| 履歴型(push ごとの check runs)を主に据える | ローカルの自己修正ループと force-push で、中間の失敗は記録に残らない(survey 論点A §5.2)。取りこぼしの向きが近似と同じで、足しても多数を拾わない。補助の表示としても、0 件が「失敗は無かった」と読まれる害が利得を上回る |
| 近似も降ろさず、全体を undelivered | 近似は、製品を変えずに試験だけを変えた PR を確実に拾う。拾えるものを拾わない理由は無い。範囲を名乗れば偽の安心は防げる |

**抜け道の評価**: 近似は PR の側のスクリプトで動きます。それでも、既定ブランチのコードで同じ計算をした写しを正本にします(S-7 の A を参照)。そうすれば、`check-pr.mjs` を書き換えた PR が検出を消しても、正本は残ります。

**採用者への影響**: 表示だけです。合否は変わりません(1046 行)。移行は要りません。

## S-3: 落ちることを期待する印の欄と、予期せず通った場合の失敗

**推す案: テンプレートが印の書式を定め、検出と欄の欠けを表示する。予期せず通った場合の失敗は、枠組みごとに降りる範囲を表で開示する。照合できない部分は別のマークで `undelivered plan=scheduled` とし、`adopter` にしない。**

1. 書式: 印の隣の注釈に `pit-in:known-failure issue=#N match="<照合する理由>" review=YYYY-MM` を置く。枠組みに依らない。注釈は版管理の中に残り、試験と一緒に動く。PR 本文は後から書き換えられるため、印の欄の置き場にしない
2. 検出(S-7 A の一部): 追加行の xfail 相当の付与を検出する。対象は基底に無い新しいテストのファイルを含む。欄が欠けた印は表示する。合否には使わない(1046 行。軽の合意 A と同じ)
3. 予期せず通った場合の失敗。枠組みごとの扱いは次の表のとおり

| 枠組み | 予期せず通った場合 | 別の理由で落ちた場合 | マーク |
| --- | --- | --- | --- |
| pytest | `xfail_strict = true` が設定に無ければ、契約検査で失敗にする。機械で確かめられる | `raises=` は例外の型までしか照合しない。理由の文の照合は無い | 通過の失敗化は delivered machine。照合は undelivered |
| Jest `test.failing`・Vitest `test.fails` | 常に厳格。枠組みが満たす | 照合の手段が無い | 通過の失敗化は delivered(枠組みに依ることを note に書く)。照合は undelivered |
| Go・JUnit 5 | 期待する失敗の印が無い。既知の失敗は skip でしか書けない。skip は弱体化として検出される | — | undelivered。「印が無いため、予期せず通ったことは検出できない」と開示する |

4. 照合と Go の部分の計画は `scheduled` とする。テンプレートが、アダプタごとの補助を同梱する計画にする。本標準はすでに回帰の試験で同じ補助(ADR-0089 決定4、`lib.mjs` の `knownFailure`)を実装しており、手本がある

**採らない案と理由**

| 案 | 採らない理由 |
| --- | --- |
| 照合できない部分を `plan=adopter`(軽の起案) | 採用者ごとに補助を作り直させることになる。多くの採用者は作らない。それでも台帳の表示は「採用者が実装する」となり、統制が採用者の側にあると読まれる。テンプレートに手本がある以上、`scheduled` が正直な表示である |
| 全体を1つの undelivered のまま(軽の反対) | 検出と pytest の strict の契約検査は、今すぐ機械で確かめられる。降ろせる部分を降ろさないと、降りている部分と降りていない部分の区別が台帳から読めない |
| 印の欄を PR 本文の表に置く | PR 本文は後から書き換えられる。試験と離れるため、印を残したまま欄だけが古くなる |
| 欄の欠けを G-5 の失敗にする | 1046 行と衝突する。失敗にするなら条項の改めであり、本件の範囲を越える |

**採用者への影響**: pytest の採用者は、`xfail_strict` が無ければ取り込みの後に契約検査で落ちます。直し方(`pyproject.toml` の `[tool.pytest.ini_options]` に `xfail_strict = true`)を告知に列挙します。猶予は置きません(S-1(c) と同じ理由)。

## S-4: 人による中間の層のマージ(IMPL-0248・0254)

**推す案: マークを2つに分ける。**

1. 拒否の部分(IMPL-0248・0254): `undelivered plan=scheduled` のまま残す。note を書き換え、拒否の手段がホスティングに無いことを書く。根拠は GitHub・GitLab の文書(survey B-3、survey-external §3.3)である。見直しの契機は、プラットフォームの機能の変化(GitHub のスタック型 PR の一般提供、マージだけを拒む規則の追加)とする。issue は、#360 を閉じた後も開いている既存の Issue へ寄せる
2. 新しいマーク: マージの後の検出。`delivered check=machine`(試験つき)とする。対象は、記録の写しの `base.ref` が既定ブランチでないマージである。検出の結果は**出荷の証跡に一覧で出す**。出荷の失敗にはしない(軽の合意 B)。ただし、G-7 の判定者が読む材料の欄とし、IMPL-0250(層の合わさった差分への承認)の材料にもする
3. 検出の表示は次の3値とする
   - 検出あり
   - 0 件(写しを読めた)
   - 未確認(写しが無い構成。records が未初期化、または無料の私有リポジトリ)

   写しが無い構成では、API の PR の一覧から `base.ref` を引く。引けなければ「未確認」と出す。**「0 件」と「読めなかった」を区別しないと、事後の検出は偽の安心になる**(ADR-0085 決定4 の4値と同じ理由)

**採らない案と理由**

| 案 | 採らない理由 |
| --- | --- |
| `plan=adopter`(軽の起案) | 採用者も GitHub の上では拒否を実装できない(survey B-3。外部の道具も規則で拒否せず、手順で避けている)。`adopter` は「規定は課したまま、採用者が自ら実装する」と読まれる。監査人は採用者に、実装できない統制の証跡を求めることになり、監査の項目が成り立たない |
| ルールセットを機能ブランチへ広げる | 直接の push が止まり、手動のスタックと両立しない。ADR-0078 決定3 を維持する(軽の合意) |
| 事後の検出を出荷の失敗にする | 正当に修復した層(戻して既定ブランチへ着地し直した場合)まで止まる。止めることが条項の目的(層ごとの確認の粒度)を回復しない。止める代わりに、判定者が読む欄にする |
| 検出だけを delivered にして、拒否のマークを消す | 降りていない規定は表示し続ける(ADR-0026・ADR-0083)。「してはならない」が人の手順だけに依ることを、台帳から消さない |

**採用者への影響**: 出荷の証跡に一覧が増えます。合否は変わりません。records を初期化していない構成では「未確認」が出続けます。これは事実の表示です。

## S-7: 一致した部分 A〜E の最終の形

### A(検証を弱める変更の検出)

- **正本は、既定ブランチのコードで計算した写しとする**。`gate-g5-base` の base-judge が流す `check-pr.mjs` の結果で、ジョブの要約に出る(前提の事実4)。PR のコメントは便宜の写しとする。正本を PR の側の計算にしない理由は2つある
  - `check-pr.mjs` を書き換えた PR は検出を消せる。統制の設定の承認で取り込みは止まるが、レビューの時点の表示は消える
  - コメントは書き込みの権限を持つ者が編集・削除できる
- 検出の範囲:
  - 追加行の skip・xfail 相当の付与(基底に無い新しいテストのファイルを含む)
  - 削除行のアサーション
  - 削除と追加のアサーションの対(旧・新を出す。1048 行の一覧の材料)
  - 試験の注釈化(削除行の `it(` と追加行の `// it(` の対)
- テストの実行の設定ファイル(`jest.config.*`・`vitest.config.*`・`pytest.ini`・`pyproject.toml` の pytest の節)が `thresholdFiles` に入っているかを、実装の時に突き合わせる。入っていなければ、設定による除外(`testPathIgnorePatterns`・`--deselect`)が素通りする。入っていないものは足す
- **0 件のときも、検出が見ないものを定型で出す**。別名経由の skip、早期の return、製品のコードの側で検証を無効にする変更、採用者独自の印が対象である(前提の事実5)
- 期待値の改めの根拠の欄: PR 本文の節「## 期待値の改め」の表(`ファイル:行 | 旧 | 新 | 根拠`)とする。合否には使わない。PR 本文は書き換えられるため、監査の正本はマージの時点の記録の写し(record-copy)とする。根拠の識別子(ADR・受入基準・条項)の実在を確かめ、Issue の番号だけの根拠を表示する
- 本文 1083 行と `/human-verify` 順4 の「ラベル」の語は「検出の一覧」へ改める(軽の合意)

### A'(対象のパスの突合)

- 計画は既定ブランチの先端から読む(軽の合意)。同じ PR で計画の対象パスの列を変えた場合は、その差分を別の一覧に出す。広げても突合には効かない。それでも、広げようとした事実は判定者に見せる
- 基底の計画に無いタスク(同じ PR で足したタスク)は「基底の計画にタスクが無い」と出す。先端の計画で代用しない
- 読めない升は「対象パスを読めない(Task-N)」と件数で出す。差が無いことと区別する
- テストのパスは除外せず、「対象パスの外のテストのパス」として別枠で出す。黙って外すと、テストの置き場の外にある製品のコードの変更が混ざっても見えない
- `Spec: setup`・bot・文書だけの PR は「対象外(理由)」と出す。黙らない

### C(AI レビューの入力の記録と欠落の表示)

- 保存期間: Actions の既定 90 日は四半期の抜き取り(約 92 日)より短い。**抜き取りの時点で記録が消えた実行を「問題なし」と読む穴がある**。推す案は次のとおり
  - 入力の記録(`inputs.json`)を記録用ブランチへ写す。入力の記録は、ワークフローが既定ブランチの側で列挙したもので、AI の出力ではない。したがって、書き込みのジョブへ渡しても IMPL-0333 の条件(AI の出力を書き込みのジョブへ渡さない)に反しない
  - 欠落の表示(AI の出力から導く)は写さず、ジョブの要約に留める
  - 抜き取りでは、記録が無い実行を「記録の欠落」と数え、「問題なし」に数えない
- artifact の保存期間を延ばす案は、提供の上限を本件で確かめていない(外部未確認)。主な手段にしない

## 結論の要約

- **S-1**: 誤りは ADR-0085 決定2 の go の句(未実施の記録を、外れないことの十分条件とした)であり、ADR-0121 の射程の限定もそれを引き継いだ。ADR-0121 決定4 の原則を正とし、新しい ADR で置き換える。go は coverage.out と AST の文の開始行で全体と変更の範囲を測る。測れない構成はすべて未実施(失敗)とする。移行は猶予・基準線なしで、記名の取り込みの時点で効かせ、告知と本文に開示する。go.json の誤った note は直ちに削る
- **S-2**: 静的な近似は、範囲を名乗る別のマークで delivered にし、0 件でも見ない場合を必ず出す。「テストのみで解消」の本体は undelivered scheduled とし、再実行型を実機の確認つきで目標にする
- **S-3**: テンプレートが注釈の書式を定め、検出と欄の欠けを表示する。予期せず通った場合の失敗は枠組みごとに降りる範囲を表で開示する(pytest の strict は契約検査)。照合と Go は scheduled とし、adopter にしない
- **S-4**: 拒否は undelivered scheduled のまま、手段が無い事実を note に書く。adopter にしない。マージの後の検出を別のマークで delivered にし、出荷の証跡の判定者の材料として「検出あり / 0 件 / 未確認」の3値で出す
- **S-5**: `gh pr merge`・API のマージの拒否だけを delivered machine にする。`git merge`+`git push`・`--base`・スクリプトからの API の経路は、別のマークで開示する。事後の検出もこの経路を拾わないことを明記する
- **S-6**: IMPL-0102 は undelivered adopter(決定は新しい ADR)とする。決定者が根拠を読む手順(delivered manual。確かめ手を名指す)と、L2 の null に「中身は確かめていない」を出す定型の文(delivered machine)を別のマークで降ろす
- **S-7**: A の正本は既定ブランチのコードの写し(基底の側のジョブの要約)とし、0 件でも限界を出す。A' は計画の列の変更・基底に無いタスク・読めない升・テストのパスを黙らずに別に出す。C は入力の記録を記録用ブランチへ写し、記録の欠落を「問題なし」に数えない。IMPL-0479 は開いている実機の確認の Issue へ移す
- **範囲外**: rulesets の重複は直し、id の重複の検査を足す。python のテストの算入は締める向きの欠陥として本件で直す(取り込みの時点で効かせる)。CRLF は試験の側で直す
