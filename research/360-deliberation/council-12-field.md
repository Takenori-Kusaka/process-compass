## S-1(重大度「高」): go の基準3 と、ADR-0085 決定2・ADR-0121 の食い違い

### 現場から見た事実(確認したこと)

- go の採用者の PR では、`coverage-check.mjs` が `coverageSummary が null` の分岐(261 行)で code 0 を返す。ジョブ test は緑で、ログに警告が1行出るだけになる。結果の JSON は `measured:false`
- 「実施しない」がどこに残るかを辿った。出荷の集約(`aggregate-evidence.mjs:3664`)が保証の開示に「未測定(coverageSummary が null)」と書く。PR の時点では、G-5 の集約(gate-g5)の合否に何も入らない。G-6 の判定者が PR で目にするのは緑のチェックだけになる
- 本文 `gate-criteria.md` 935 行は「未実施の検査として失敗に数えなければなりません」と定める。ADR-0121 決定4 は、手書きの要素について同じ状態(集計の無い要素)を失敗に数えた
- つまり現場の実感では「go は基準3 が無いのと同じ」。開発者はこの警告を読まない。go のチームは、カバレッジが 0% でも出荷まで気づかない

### (a) どちらの ADR が誤りか

**ADR-0085 決定2 の理由の一文が誤り。ADR-0121 の「単一のスタックなら決定2 の理由は成り立つ」という補いも、go については誤り。** ADR-0121 決定4 の原則(未実施は失敗に数える)が正しい。

理由:

1. 決定2 の理由「go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない」は、記録の所在を取り違えている。記録は出荷の集約にだけ現れ、G-5 の判定(PR ごとの合否)には現れない。G-5 の通過として残る以上、「黙って外れる」の実態そのものになる。node の「test ジョブが失敗する」と同列に並べたのは誤り
2. 本文は、実施できなかった検査を対象なしと区別して「失敗に数えなければならない」と定める(935 行)。決定2 の理由は、未実施の通過を「記録があるから可」とした。本文の規定より弱い扱いを ADR が理由として置いたことになり、ADR が本文に負ける
3. ADR-0121 は「止める位置を事前点検ではなく PR ごとの検査に置く」と決めた。go の単一のスタックは、PR ごとの検査で止めていない。ADR-0121 は決定2 の射程を「単一のスタックの場合」に限っただけで、単一の go の場合の理由の誤りを見落とした
4. 両立する読み方(「実施しない」と記録する = 失敗に数えない未実施を認める、という例外)は採らない。ADR-0121 の表で退けた案「(c3) 告げて開示するだけで通す」と同じ第3の通過の状態になる。node の採用者には課し、go の採用者には課さない、という偏りを、本文のどこも正当化していない

**決定2 の結論(事前点検では止めない)は維持する。** 現場としてもこれに賛成する。持ち込みの時点で止めると、go のリポジトリはテンプレートを入れること自体ができなくなる。止める位置は PR ごとの G-5 の検査とする。採用済みの ADR は書き換えず、新しい ADR で決定2 の理由の一文と ADR-0121 の補いの該当部分を置き換える。`preflight.mjs:17・280・281` の文言(「go では『実施しない』と記録するため黙っては外れない」)も、同じ誤りを採用者へ表示しているので改める。

### (b) go で基準3 を測る手段

推す案: **`coverage.out` 1つで全体と変更の範囲の両方を測る。変更の範囲は「変更した行に重なるブロックを分母に入れ、ブロックの文の数で重みを付ける」(go-patch-cover と同じ方式)。** 全体は Σ(回数 > 0 のブロックの文の数) / Σ 文の数とする。`go tool cover -func` の total と一致する(survey.md D §2.2 で確認済み)。

現場としての理由:

- 開発者が手元で再現できる。全体の値は `go tool cover -func` の total と一致し、go の開発者が普段見る数字と同じ単位(文)になる。変更の範囲も go-patch-cover で同じ値を出せる。CI の値と手元の値が食い違う検査は、すぐに信用されなくなる
- go の実行回数はブロック単位でしか記録されない。ブロックの中の文はすべて同じ回数を持つため、ブロック単位の重み付けは、go の計測が持つ情報をそのまま使う。行へ落とす案A・B のような推測の規則を足さない
- 誤りの向きは厳しい側に寄る。大きな未被覆のブロックの中の1行を変えると、そのブロックの文がすべて分母に入る。「変えた行は少ないのに落ちた」という苦情は出うるが、通してはならない変更を通す向きではない。苦情の多寡は見直しの契機にする
- node の実装(coverage-check.mjs)の中だけで計算でき、テンプレートに go のプログラムを足さない

採らない案:

| 案 | 採らない理由 |
| --- | --- |
| ブロックの開始行だけ(案A) | ブロックの中の2文目以降の変更が分母から落ちる。取りこぼしが node の近似より大きい |
| ブロックの範囲の全行(案B。gocover-cobertura・sonar-go が採る) | 空行・注釈・閉じ括弧が分母と被覆に入り、割合が上へ寄る(試行で 38.46% と文の割合 25%)。先例はあるが、上へ寄る向きは通過してはならない変更を通す側の誤り |
| AST で文の開始行へ戻す(gocov 系) | 分母の精度は最も高く、node・python と近似を揃えられる。しかし go のパーサを使うには、統制の設定(強制層)に go のプログラムを足し、go の版・モジュールの解決という新しい壊れ方を抱える。被覆の回数そのものはブロック単位から変わらない。いまは採らないが退けもしない。見直しの契機(分母の水増しで正当な変更が落ちる苦情が出た場合)に残す |
| 外部サービス(Codecov の patch status)へ委ねる | 既定で、報告が無くても通る(`if_not_found: success`)。採用者の設定に依り、本標準の「未実施は失敗」を担保できない |

実装で決めておくこと(現場で詰まる所):

- パスの戻し方: import のパスを `projectDir` の `go.mod` の module 行で相対パスへ戻す。戻せないファイル(go.work の別の module、replace)は「測っていない製品のファイル」として失敗にし、案内の文で「go.work の複数の module は手書きの要素(none の stacks)で module ごとに whole で報告する」と直し方を示す。直し方の無い失敗にしない
- 同じブロックが複数回出る場合(`-coverpkg` を使う構成)は、ブロックの位置で束ね、回数は最大値を取る
- 生成されたコード(`*.pb.go`、モック)が go のリポジトリでは多い。proto を変えた PR で、生成物の未被覆のブロックが分母を埋める。これを放置すると、採用者は基準値を下げる方向へ逃げる。除外は採用者が明示する一覧に限る。その一覧のファイルは `thresholdFiles` に入れ、製品のコードとの同時変更の検査に乗せる。go 公式の生成物の目印(`// Code generated ... DO NOT EDIT.`)による自動の除外は採らない。目印の1行を足すだけで手書きのファイルを外せるためである。目印のあるファイルの件数と分母に占める割合を、結果に表示するに留める
- `_test.go` はプロファイルに載らない。python の件(範囲外の項)と違い、テストのファイルが全体の割合を押し上げることは無い

### (c) 既存の go の採用者に新しい失敗を課す移行

推す案: **猶予の期間は置かない。新しい失敗は、テンプレートの取り込みの PR そのものに現れるようにする。その PR の説明と ADR-0085 決定6 の「落ちうる検査」の列挙で、直し方を3つ示す。**

- 新しい coverage-check.mjs は PR の側の gate-g5(test ジョブ)で動く。だから取り込みの PR の時点で、既存のコードの全体の割合が基準値に届かない構成は落ちる。外部の実務の「宣言を上げた利用者だけが新しい既定を受ける」(Go の GODEBUG と `go.mod` の版)と同じ型になる。採用者がテンプレートを取り込んだ時点で受ける。無関係な機能の PR が突然赤くなる事態は起きない。これが現場にとって最も大事な点である
- 猶予(警告だけの期間)を置かない理由: 猶予の間は、いまの「黙った通過」がそのまま続く。ADR-0121 が猶予を退けた理由と同じになる。現場の実感としても、警告の期間は読まれずに過ぎ、期限の日に同じ混乱が起きる
- 取り込みの PR で落ちたときの直し方(失敗の文と取り込みの手引きに書く):
  1. 範囲を変更にする: `/process-change`(種別 settings)で `ci.coverageScope: changed` を記録する。統制の設定の変更として、記名と AI維持管理者の承認を要する。古いコードの是正を求めず、新しく変えたコードにだけ基準を掛ける(Clean as You Code の型)。既存の go の採用者には、これを第一の道として案内する
  2. 全体のまま、基準値を改める: 基準値の変更は既存の手続(閾値・除外設定の変更、記名)に乗せる。下げた事実は変化点に残る
  3. テストを足して届かせる
- 範囲を記録していない既存の go の構成は、ADR-0079 に従い全体として判定する。変更の範囲へ黙って読み替えない。取り込みの PR で全体の判定が落ち、上の1を選ぶ、という流れになる
- 新しく生成する go の構成の既定は changed にする(generate-profile は `coverageDetail` の有無で既定を決めるため、自動でそうなる)
- 表示: 取り込みの PR の失敗の文に「go の基準3 は、これまで測られずに通っていた(テンプレートの欠陥)。この版から測る」と書く。採用者の落ち度ではなく、テンプレートの欠陥の解消であることを明示する。記録の上では、この版より前の go の出荷の保証の開示に「未測定」が出ていた事実を消さない

### (d) 測れない構成(`coverage.out` が出ない)

- coverage のコマンドが成功したのに `coverage.out` が無い(採用者がコマンドを書き換えた等)場合は、集計ファイルが無い場合(coverage-check.mjs 267 行)と同じく**失敗**にする。「未実施(カバレッジの記録が無い)」と表示し、アダプタの coverage のコマンドを案内する
- 製品のコードが無い段階(G-4 の前の文書だけの変更)は、従来どおり対象なしとする(IMPL-0239 の範囲)
- `coverageSummary` が null のアダプタで code 0 を返す分岐そのものを、未実施の失敗に改める。go が測れるようになれば、この分岐に来る構成は「製品のコードがあるのに集計を持たない構成」だけになり、通してよい場合が残らない
- テストが落ちてプロファイルが出ない場合は、基準1 で既に落ちている。基準3 の表示は「基準1 の失敗により未実施」とし、二重に原因を探させない

### 実装マークの扱い

- IMPL-0259(node 以外の変更の範囲): python と go を降ろして **delivered**(test=test-coverage-scope.mjs)。go の近似(ブロック単位・文の数の重み)は、node・python の「文の開始行」と別の近似として結果の `approximation` と本文で開示する。根拠水準のマーク(EV)を付ける(採用者の実データでの誤差は未測定)
- go の全体の割合を測らずに通していた欠陥の解消は、本文 935 行(未実施は失敗に数える)に掛かる実装として、新しいマーク(番号は議長が採番)を **delivered**(machine)で付ける。IMPL-0259 の note に混ぜない。変更の範囲の測り方と、未実施を失敗にする原則は、別の規定だからである
- test-coverage-scope.mjs の fixture(62 行の「python は whole」、134 行の「PY で changed は失敗」)は、過去の決定を固定している。決定の変更として改め、新しい ADR を引く

## S-2: 「テストのみの変更で失敗が解消した変更」(IMPL-0204 の一部)

### 推す案

- **静的な近似は表示として降ろすが、規定の名で呼ばない。** 表示の名は「製品のコードを変えずに既存のテストを変えた PR」とし、「失敗が解消した変更」とは書かない。表示の正本は §1 の合意どおり PR のコメントとジョブの要約にする
- **規定の本体(失敗が解消した変更の検出)は undelivered(plan=scheduled)に残す。** 計画の手段は履歴型とする。PR の先頭が更新された各時点で test ジョブが失敗から成功へ変わり、その2つの先頭の差がテストのパスだけである組を表示する。実機の GitHub でしか確かめられない(check runs の取得、force-push の後の旧い先頭)ため、IMPL-0479 と同じく実機の確認を降ろす条件にする

### 現場としての理由

- AI エージェントの自己修正のほとんどは「同じ PR で製品とテストを両方変える」形になる(survey.md A §5.2、外部の ImpossibleBench でも試験の改変が主な型)。静的な近似はこれをまったく拾わない。この近似を delivered と表示すれば、現場は「検出がある」と思い込んで読まなくなる。拾っていない部分が台帳から消えるのが最悪の結果になる
- 一方で、静的な近似の表示に害は少ない。テストだけの PR は数が少なく、読む手間は小さい。テストの整理や不安定な試験の修正という正当な変更も出るが、名前が正確なら判定者は誤読しない
- 履歴型は、CI を帰還のループに使うエージェント(リモートで動き、CI の失敗を読んでテストを直す型)を直接捉える。ローカルのループは IMPL-0187 のフック(ロック中のテストへの書き込みの遮断)が受け持つ。両者で内と外を分担できる

### 採らない案

| 案 | 理由 |
| --- | --- |
| 静的な近似を「近似」と明記して delivered に含める(起案) | 規定の対象の大半(製品とテストの同時変更)を拾わない。delivered の表示が、拾っていない事実を台帳から隠す |
| 再実行型(新しい製品のコードで旧版のテストを流す) | 試験の時間が2倍になる。仕様の変更に伴う正当な期待値の改めもすべて出て、表示が常に埋まる。PR の側でしか流せず、統制の設定を変える PR では信頼できない。現場では毎 PR の待ち時間に跳ね返り、無効化の圧力になる。履歴型の実機の確認の結果、取りこぼしが大きいと分かった場合の次の候補に残す |
| 表示を G-5 の失敗にする | 本文 1046 行と衝突する(合意の範囲) |

### 実装マーク

- IMPL-0204 を分ける。(1) skip・xfail の付与・アサーションの削除・期待値の改めの検出の表示(S-7 の範囲)= **delivered**。(2) 製品のコードを変えずに既存のテストを変えた PR の表示 = (1) と同じマークの note に「静的な近似。失敗の解消は判定しない」と書いて含める。(3) 失敗が解消した変更の検出 = 新しいマーク、**undelivered・plan=scheduled**(手段は履歴型、実機の確認を条件とする。見直しの年月を持つ)

### 採用者への影響

- 新しい失敗は無い。PR のコメントに表が1つ増える。テストだけの PR でだけ出るので、日々のノイズは小さい

## S-3: 落ちることを期待する印の欄と、予期せず通った場合の失敗

### 推す案

- **テンプレートが印の書式を定める。** 枠組みに依らず、印の直前の1行に注釈で書く形にする。例: `// pit-in:expected-failure issue=#123 match="ZeroDivisionError" review=2027-05`(python は `#`)。pytest は、これに加えて `@pytest.mark.xfail(raises=..., strict=True)` を併記するよう手引きに書く
- 検出の対象は、S-7 の追加行の xfail 系の検出(`@pytest.mark.xfail`、`pytest.xfail(`、`test.failing`、`test.fails`、`it.fails`、`expectedFailure`)とする。検出した印の直前に書式の行が無い場合、または欄(issue・match・review)が欠ける場合、`review` を過ぎた場合は、表示する。G-5 の失敗にはしない(期待値の根拠の欄と同じ扱い。§1 の合意)
- 予期せず通った場合の失敗:
  - pytest: 契約検査で、テストに `xfail` が使われているのに pytest の設定(pyproject.toml・pytest.ini・setup.cfg)に `xfail_strict = true` が無い構成を**失敗**にする。xfail を使っていない採用者には何も起きない。標準はすでに「予期せず通った場合は試験の失敗」と求めており、この失敗は新しい義務ではなく既存の規定の担保である
  - Jest `test.failing`・Vitest `test.fails`: 枠組みが常に厳格なので、テンプレートの追加は要らない。そう開示する
  - Go: 落ちることを期待する印が枠組みに無い。`t.Skip` は skip として S-7 の検出で扱う。「予期せず通る」状態は起こりえない、と開示する
- 「別の理由で落ちた場合は失敗」の照合: pytest の `raises` だけが枠組みで担保できる。Jest・Vitest は枠組みに手段が無い。ただし採用者は、印を使わずに特定の例外を期待するアサーション(`expect(() => f()).toThrow(SpecificError)`)で書ける。これは採用者の側に実際の手段がある

### 現場としての理由

- 書式を定めないと、規定は誰にも実行されない。いまのテンプレートには xfail の語すら無い(survey.md A §4.2)。採用者は印に Issue も期限も書かず、検出もできない。注釈の1行の書式なら、どの枠組みでも書け、機械も一つの正規表現で読める
- 期限切れや欄の欠けを失敗にすると、古いリポジトリの取り込みの PR で、既存の xfail がすべて赤くなる。直すべき対象は多いが、一度に直せない。表示に留めれば、触った PR から順に直せる
- `xfail_strict` の検査は、使っている採用者にだけ掛かる。設定1行で直せ、直し方が明確である

### 採らない案

| 案 | 理由 |
| --- | --- |
| 書式を定めず undelivered のまま(反対) | 採用者の側に書き方の手本が無いまま、規定が台帳に残り続ける。現場では「何を書けばよいか分からない規定」になる |
| 枠組みごとに別の書式(pytest は reason の中、Jest は試験の名前の中) | 機械の読み方が枠組みの数だけ増える。採用者が混在のリポジトリで2通りを覚える |
| 欄の欠け・期限切れを G-5 の失敗にする | 本文 1046 行の趣旨(検出を合否に使わない)と、取り込み時の一斉の赤 |
| 印の件数の上限 | 本文 1050 行が課さないと定める |

### 実装マーク

- 書式・検出・欄の欠けと期限切れの表示・pytest の `xfail_strict` の契約検査 = **delivered**(machine)
- Jest・Vitest の「別の理由で落ちた場合の失敗」= 新しいマーク、**undelivered・plan=adopter**。note に、枠組みに照合の手段が無いこと、採用者は特定の例外を期待するアサーションで書けることを書く。ここでの adopter は、採用者が実際に実装できるため誤読を生まない(S-4 と対照的)
- Go は「印の機能が枠組みに無い」ことを note に書く。マークを作らない(降ろす先の機能が存在しない)

### 採用者への影響

- python で xfail を使い、`xfail_strict` を設定していない採用者は、取り込みの PR で契約検査が落ちる。直し方は設定1行。ADR-0085 決定6 の「落ちうる検査」に列挙する
- それ以外の採用者は、PR のコメントの表示が増えるだけ

## S-4: 人による中間の層のマージ(IMPL-0248・0254)

### 推す案

- **undelivered のまま、plan=scheduled。adopter にしない。** 計画の中身は「GitHub の公式のスタック型 PR(2026-07-30 から公開プレビュー)が一般提供になり、提供の範囲(個人所有のリポジトリで使えるか)を確かめた時点で、手動のスタックからの移行の手引きと検査を降ろす」とする。見直しの年月を持たせる
- **マージの後の検出は別のマークで delivered にする。** 位置づけは出荷の材料とする。出荷の集約が、写しの `base.ref` が既定ブランチでないマージを一覧にし、G-7 の判定者が読む項目に載せる。失敗にはしない(§1 の合意)
- 加えて、検出の時期を早める。出荷は数週間後になることがある。それまで気づかなければ、層ごとの確認の粒度を失った変更の上に次の層が積まれる。マージの直後に、記録の写しのジョブの要約へ「既定以外へのマージ」を出す。PR へのコメントは書き込みの権限を `pull_request_target` のジョブへ足すことになるため、書き込みのジョブを分ける既存の型(ai-review の notice)に限って検討する

### 現場としての理由

- adopter と書けば、採用者は「自分が実装すべき統制がある」と読み、探しても手段が無い(GitHub にも GitLab にもマージだけを拒む設定が無い。外部の調査で確認)。実装できない義務の表示は、台帳を読む意味を失わせる
- 小規模チームで手動のスタックを使う機会は多くない。事故の型は「急いで上の層を下の層へマージした」であり、事後に必ず見える形にすれば、次から避けられる

### 採らない案

| 案 | 理由 |
| --- | --- |
| plan=adopter(起案) | 採用者も GitHub の上では実装できない。統制が採用者の側にあると誤読される |
| ルールセットを機能ブランチへ広げる | ADR-0078 決定3。手動のスタックの直接の push が止まる(§1 の合意) |
| 基底が既定でない PR を失敗にする検査 | 正当に開いている上の層の PR が常に赤くなる。現場では赤が常態になり、赤そのものを読まなくなる |

### 採用者への影響

- 新しい失敗は無い。出荷の材料に1項目が増える。手動のスタックの手順書(`stacked-pr.md`)に「公式のスタックが使えるなら、そちらを使う」を推奨として書く(EV-0139 の実機の確認の後に限る)

## S-5: AI による中間の層のマージ(IMPL-0255)

### 推す案

- マークを分ける。`gh pr merge` と `gh api -X PUT .../merge` の拒否(guard-bash。実行で確認)= **delivered**(test=guard-bash の試験)。範囲を note に限定して書く
- 通る経路(`git merge` と `git push` の組、`gh pr create/edit --base` の付け替え)= **塞がずに開示する**。新しいマーク **undelivered・plan=scheduled** とし、note に経路を列挙する
- 3件の note の「ask で人へ戻る」は事実の誤りなので、「フックが拒否する」へ直す(§1 の合意)

### 現場としての理由(塞がない理由)

- `git merge` は、AI エージェントが日常的に使う。既定ブランチの更新を作業ブランチへ取り込む操作(`git merge origin/main`)である。一律に塞げば、エージェントは毎回人へ戻るか、`rebase` 等へ回り道をする。統制は形骸化し、許可の一覧が雑に広げられる
- 上の層を下の層へ取り込んだかどうかは、コマンドの文字列からは区別できない(ブランチの役割がフックに分からない)。区別できない拒否は誤検出になる
- `gh pr create --base feature/a` は、スタックを作る正当な操作そのものである
- 開示に加えて、マージの後の検出(S-4)で、PR のマージを経た経路は拾える。`git merge` と `git push` の経路は PR のマージを経ないため拾えない。これも開示に書く

### 採らない案

| 案 | 理由 |
| --- | --- |
| guard-bash の拒否を根拠に、全体を delivered(起案) | 通る経路が残る。delivered の表示が、残りを隠す |
| `git merge` の後の `git push` を一律に拒否する | 日常の操作を壊し、許可の一覧の拡大を招く |

### 採用者への影響

- 挙動の変化は無い。台帳の表示が正確になるだけ

## S-6: IMPL-0102(L2 の採点の稼働)の扱い

### 推す案

- **IMPL-0102 は undelivered に残す。** 規定の名(機械の検証)を delivered と表示しない。note を「条件を条項で定めないと決めた(新しい ADR)。機械の検証は、テンプレートがリスクの採点を入力として受け取る機構を持つまで降ろさない」に改める。plan は scheduled のまま、見直しの年月を EV-0006 の見直し(2027-08)にそろえる。確かめる者は、来歴の無い「計画の Issue の担当者」ではなく、変化点の決定者と AI維持管理者と名指す
- **人の確認を delivered(manual)の別のマークにする。** `/process-change`(種別 settings)で L1・L2 へ上げるとき、決定者が根拠の中身を L2 の2条件(採点の稼働・取り消し可能性)に照らして読み、照らした結果を変化点に書く手順である
- **規模の基準なしを効かせた PR には、毎回定型の表示を出す**(delivered、machine)。「規模の基準なし(L2)を適用した。根拠 `<パス>` の実在と見直し日だけを機械で確かめ、根拠の中身(採点が稼働しているか)は確かめていない」。PR のコメントとジョブの要約に出す

### 現場としての理由

- 無関係な `README.md` を根拠に指しても L2 が成立する(survey.md E-2 で確認)。宣言の変更には AI維持管理者の承認が掛かる。だが承認者が根拠を開いて読む手順が無い。一度通れば以後の PR で何も見えない。毎回の表示は、G-6 の判定者が「この PR は行数の上限が外れている」と気づく唯一の場所になる
- 表示は基準なしが効いた PR にだけ出る。L2 を使う採用者は少なく、ノイズにならない

### 採らない案

| 案 | 理由 |
| --- | --- |
| IMPL-0102 を delivered(manual)にする(起案) | 規定は「機械の検証」の担保を指す。人の手順を置いたことで同じマークを delivered にすると、機械で確かめていないことが台帳から消える |
| plan=adopter | 採用者にも、条件が定まらない以上、検査を作る手段が無い |
| 条件を条項で定める | 新しい義務(§1 の合意で定めない) |

### 採用者への影響

- L2 の採用者は、基準なしが効いた PR に定型の表示が出る。宣言を上げる採用者は、変化点に照らした結果を書く手間が1回増える。失敗は増えない

## S-7: 一致した部分 A〜E の最終の形

### A の検出の範囲

- 新しいテストのファイル(基底に無い)も対象に含める。skip つきの新しいテストのファイルは、いまは素通りしている(実行で確認)
- 削除行と追加行のアサーションを、同じ hunk の中で対にして「期待値の改め(旧 → 新)」として出す。削除だけの行は「アサーションの削除」として別に出す
- **ノイズを減らす手当てを必ず入れる。** 入れないと、整形・移動の PR で表が膨らみ、判定者は読まなくなる
  - 空白を詰めて同じ内容の削除行と追加行は、同じ差分の中なら「移動」として数え、件数だけ出す
  - アサーションの正規表現から、注釈の中の語(`// should`)と試験の名前の中の `should` を外す(誤検出の実例。survey.md A §5.1)
  - 条件つきの skip(`skipif(sys.platform...)`、`testing.Short()`)は出す。ただし「条件つき」と別の欄に分け、無条件の skip と並べない
  - 表は1つの PR で上位の数件を出し、全件の件数と、全件をジョブの要約に置いた旨を書く。件数の上限ではなく、表示の折り畳みである(本文 1050 行に触れない)
- 根拠の欄の書式: **PR 本文の節 `## 期待値の改め` の表**(`ファイル | 旧 | 新 | 根拠`)にする。根拠は識別子に限る(ADR・F-NNN の受入基準・条項。Issue だけは不可。ADR-0089 決定3 に倣う)。機械は、検出した改めと表の行を突き合わせ、表に無い改めと、解決できない識別子を表示する。失敗にはしない
  - コードの注釈にしない理由: 改めのたびにテストのコードへ根拠の行が溜まり、削除の検出の対象にもなる。PR 本文なら、AI エージェントが PR を作るときに書く場所が一つに決まる

### A' の対象パス

- 読めない升(バッククォートが無い、文章)は「Task-N の対象パスを読めない」と表示する。0 件として黙って通さない
- テストのパス(guard.json の testPatterns)は、差の本体と別の枠に出す。含めると、ほぼすべての PR でテストのパスが差に並び、本当の差が埋もれる
- 同じ PR で計画の「変更の対象パス」の列を変えた場合は、その事実を別に表示する(既定ブランチの先端から読むため、差は消えない)
- `Spec: setup`・bot の PR・文書だけの PR は対象外とし、対象外である旨を出す

### C の記録の保存期間

- Actions の成果物の既定の保存期間は 90 日で、四半期の抜き取りの境に当たる。期の初めの PR の記録は、抜き取りの時点で消えうる
- 入力の一覧(パスと sha256)は、記録用ブランチ(records)の写しへ残す。既存の record-copy の経路に乗せる。records を初期化していない構成では、保存期間の不足を保証の開示に出す。`retention-days` を延ばす案は、私有のリポジトリで 90 日を超えられない提供者の制約があるため、手段にしない

### D の python

- 近似は node と同じ「文の開始行」と開示する。加えて次を開示する: `# pragma: no cover` の行は分母に入らず、行内の注記は閾値・除外設定の同時変更の検査に掛からない(node の ignore の注記と同じ限界)
- branch を有効にした構成で値の意味が変わらないよう、全体は `percent_statements_covered` を読む
- `coverage.json` のキーは projectDir からの相対・OS の区切りなので、所在で連結して `/` に寄せる(Windows の手元の g5-local で食い違わないため)

### IMPL-0479

- 本件で降ろさない(合意)。open の Issue を表題で検索した範囲では、スタックの第2段を扱う既存の Issue は #360 だけだった。後継を新しく起こさず、#360 を閉じる時点で残るなら、議長が台帳の issue= を付け替える先を決める。実機の確認(一時のリポジトリ、動的な matrix が空のときの結果)を降ろす条件として note に書く。IMPL-0259 が先に降りれば、第2段で要る「スタックごとの変更の範囲」の部品がそろう

## 範囲外

### `impl-targets.yaml` の id `rulesets` の二重定義

- 直す(合意)。作業ツリーには、216 行の id を `rulesets-readme` に改める**コミット前の変更**が既にある(`git status` で確認。`scripts/check-impl.mjs` にも4行の変更がある)。これまで照合が使っていたのは後の定義(team.json)なので、`rulesets` を team.json に残す向きは、既存の7件の `target=rulesets` の意味を変えない。現場として賛成する。check-impl に id の重複を失敗にする検査を足すことを推す(同じ欠陥の再発を止める)

### python の既定の `--cov` で全体の割合にテストのファイルが入る件

- 本件で直すことを推す。全体の割合がテストの行で押し上げられ(試行で 12 文中 5 文がテスト)、基準3 を実際より楽に通している。これは S-1 と同じ種類の「黙った緩み」である
- 手段: coverage-check.mjs が `coverage.json` のファイルごとの値から、guard.json の testPatterns に当たるファイルを除いて全体を数え直す。採用者の設定(`[tool.coverage.run] source`)に頼らない。設定に頼ると、書かない採用者だけが緩いまま残る
- 移行: 既存の python の採用者の全体の割合は下がる。S-1 と同じく、取り込みの PR に現れ、同じ3つの直し方を示す。落ちうる検査に列挙する

### `test-base-judge-workflow.mjs:79` が CRLF で落ちる件

- 本件で直すことを推す。Windows の開発者が手元で契約検査の試験を流すと偽の失敗が出る。手元の検査の偽の失敗は、「手元では落ちるが CI では通る」という慣れを生み、本物の失敗を見逃す原因になる。読み取りで `\r\n` を `\n` に寄せる。変更は試験の側だけで、判定の挙動は変えない
