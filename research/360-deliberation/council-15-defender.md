## 総論: 弁護の物差し

現状を弁護する理由として認めるのは、次の3つだけとします。「変えると手戻りが多い」は理由にしません。

1. **現状が、本文の規定の文言と既存の ADR の理由に照らして正しい**。変える案が、決めたことを黙って覆していないか
2. **変える案が、降りていないものを降りたように見せないか**(ADR-0026・ADR-0083・`implementation-marking.md`「降りていない規定の扱い」)。表示の語の変更は、統制を足さずに台帳の見え方だけを良くする最も安い経路であり、最も警戒すべき変更です
3. **変える案が、採用者の既存の構成に、告知と直し方の無い新しい失敗を課さないか**(ADR-0085 決定6 の保守者の義務)

この物差しで見ると、本件の現状には弁護できるもの(ADR-0078 決定3、undelivered の表示の維持)と、弁護しきれないもの(go の基準3 の通過)が混ざっています。後者は、弁護人として最も強い形で検討したうえで、弁護を断念します(S-1)。

## S-1: go の基準3 と、ADR-0085 決定2 と ADR-0121 の食い違い

### S-1-1 ADR-0085 決定2 を弁護する、最も強い議論

次の4つが、決定2 の go の扱いを弁護する最も強い議論です。

**(弁1) 決定2 の判断の対象は事前点検であって、G-5 ではない。** 決定2 は「カバレッジの測定の穴は事前点検で止めない」と決めたものです。go の記述はその理由として置かれました。結論(事前点検では止めない)は ADR-0121 も維持しています。結論は今も正しい。止める位置は PR ごとの検査であり、持ち込みの時点ではありません。

**(弁2) 「黙っては外れない」は事実として成り立っている。** [確認] go のアダプタでは、coverage-check が「判定を実施しない扱いで記録します」と警告を出します(`coverage-check.mjs:261`)。保証の開示の機械の検査の欄は「未測定(coverageSummary が null)」を出します(`aggregate-evidence.mjs:3664`)。ADR-0028 の考え方(未達と省略を区別し、無言で省かない)に照らせば、開示がある以上「黙った省略」ではありません。

**(弁3) 本文の「未実施は失敗に数える」の文言は、go の場合を直接には指していない。** [確認] 本文の規定は2か所です。一つは `gate-criteria.md:934` で、対象は「実行環境が検査器の読む入力を欠くため実施できなかった検査」です。もう一つは `:714` で、対象は「宣言の外のスタック」です。go の単一のスタックで、テンプレートのアダプタが判定の部品を持たない場合は、どちらにも文言の上では当たりません。テンプレートの部品の欠けは、本来は実装マーク(undelivered)で開示するものです。採用者の G-5 を落として示すものではありません。これは ADR-0026・ADR-0083 の分担に沿った読み方です。

**(弁4) 規格の側も、測れないことを一律に失敗とはしない。** 外部の調査 §5 によると、ISO/IEC/IEEE 29119-3 は、完了の基準を満たさない場合を「逸脱・残留リスクとして理由を報告し、判断へ回す」形で扱います。Codecov と diff-cover も、既定では報告が無くても通します(§1.6)。

### S-1-2 それでも弁護が成り立たない理由

上の4つを検討しましたが、決定2 の **go の半分の理由** は弁護できないと判断します。決め手は次の3つです。

1. **G-5 の通過は、基準3 を満たしたという主張である。** 基準3 の値は「基準値以上」です(`:663`)。測っていない値は「基準値以上」ではありません。測らずに通す正規の経路は「対象なし」だけで、本文 `:914` は「**実装が存在する段階で、この扱いを用いてはなりません**」と定めています。go の採用者の製品のコードがある PR で gate-g5 が緑になると、記録の上では、実装がある段階で対象なしと同じ効果の通過が起きています。弁3 の「文言が直接は指していない」は、この禁止を回避する読み方になってしまいます
2. **開示は通過を正当化しない。** ADR-0121 は「(c3) 告げて開示するだけで通す」案を、「対象なしにも未実施にも当たらない第3の通過の状態を作る」として退けました(採らなかった案の表)。go の「未測定のまま通過」は、まさにこの第3の状態です。弁2 の「黙ってはいない」は、ADR-0121 がすでに理由として退けた論法です。ADR-0121 は基準1 の「例外なし」を根拠に挙げました。ただし基準3 にも例外の規定はありません。対象なしの表(`:901`)が基準3 に認めるのは、測定の対象のコードが無い場合だけです
3. **同じ状態を、テンプレートは2か所で逆に扱っている。** 手書きの要素(none の stacks)で `coverageSummary` を報告しない要素は「基準3 の未実施」として失敗にしています(`coverage-check.mjs:417-425`、ADR-0121 決定4、突合 X3-1)。go のアダプタの `coverageSummary: null` は、構造の上ではこれと同じ状態です。それなのに通過させています。同じ事実に逆の判定を出すテンプレートは、どちらの判定も信頼できません

弁3 の「テンプレートの欠けはマークで開示するもの」という分担論にも、限界があります。マーク(undelivered)が開示するのは「**統制が働いていない**」ことです。「本文が失敗とすべき状態を、テンプレートが合格と記録する」ことまでは開示しません。後者は降りていない規定ではなく、テンプレートの欠陥です(IMPL-0475 が直した型と同じ)。そもそも、go の基準3 が測られないことを開示するマークは、本文に1件もありません [確認: IMPL-0259 は変更の範囲だけ、IMPL-0234 はコマンドが空の場合だけ]。弁3 の分担論に立っても、現状は開示の欠けです。

弁4(規格・道具)は、移行の設計の材料にはなります(S-1-5)。しかし本標準の基準を下げる理由にはなりません。本標準は ADR-0121 で「規格の要求より強い側を選んだ」と明記しています(`:756`)。

### S-1-3 (a) どちらの ADR が誤りか: 見解

- **誤りは ADR-0085 決定2 の理由のうち、go に関する半分である**(「go では G-5 基準3 を『実施しない』と記録するため、黙っては外れない」)。決定2 の結論(事前点検では止めない)と、node の半分(test ジョブが失敗する)は正しく、維持すべきです
- **ADR-0121 決定4 の原則(報告の無い要素は未実施として失敗に数え、合算しない)が正しい**
- **ただし ADR-0121 にも誤りが1つある。** ステータスの表で、決定2 の理由は「製品のコードが単一のスタックの場合に限って成り立つ」と射程を限りました。この書き方は、単一のスタックの go についても理由が成り立つと**追認した**ことになります。正しい射程は「node(と python)の単一のスタックに限って成り立つ。go のアダプタでは単一のスタックでも成り立たない」でした。ADR-0121 は混在の欠陥③を扱う審議だったため、単一の go の通過を検査しなかったと見られます [推論]
- 両立する読み方(弁3)は検討しましたが、本文 `:914` の禁止を回避する読み方になるため採りません
- 処理: 採用済みの ADR の本文は書き換えません。新しい ADR で、ADR-0085 決定2 の go の理由を置き換えます。ADR-0121 のステータスの表の射程の記述(go を含めた点)も補います。ADR-0085・ADR-0121 のステータスの欄に、置き換えの注記を足します(ADR-0085 のステータスに ADR-0121 の注記を足した前例と同じ形)

### S-1-4 (b) go で基準3 を測る手段: 弁護の対象と推す形

**全体の割合**: coverage.out の文の割合(Σ 被覆したブロックの文の数 / Σ 文の数)を使います。`go tool cover -func` の total と一致することを確かめています(survey 論点D §2.2)。行へ落とす必要がありません。go 自身の単位(statements)であり、近似の論点が生じません。

**変更の範囲**: ここで、本文の現状の定義を弁護します。本文はすでに分母を定めています。「変更の範囲の分母は、加えた・変えた行のうち、被覆の記録で**文の開始行に当たる行**で数えます」(`:968` 付近)[確認]。3つの案をこの定義に照らします。

| 案 | 本文の定義との関係 | 弁護人の評価 |
| --- | --- | --- |

| ブロックの範囲の全行(sonar-go・gocover-cobertura。2委員が退けた案) | 本文の定義と違う(文の開始行ではない) | 退けられた案の弁護として、次を記録に残すべきである。業界に先例があること(sonar-go は空行・括弧を除く)。`go tool cover -html` の見え方と一致し、開発者が画面で見る被覆と同じになること。退ける理由は「割合を上へ寄せる(被覆したブロックの継続行を被覆に数える)」ことであり、先例の欠如ではない。この理由は試行(38.46% 対 文の割合 25%)で裏づけられている。弁護したうえで、退けることに同意する |

### S-1-5 (c) 既存の go の採用者への移行

ここでは、既存の ADR の「猶予の期間を置かない」を弁護します。外部の実務(PEP 387 の2年、GODEBUG の4版、Evaluate の段)は段を踏むのが通例です(外部 §2)。それでも本標準では猶予を置くべきではありません。理由は次の3つです。

1. ADR-0085 決定5 と ADR-0121 は、猶予を退けた理由として「猶予の間は黙った通過が続く」を挙げています。今回の通過は、S-1-2 のとおり本文が禁じる状態です。猶予を置くことは、その状態をテンプレートが期間つきで認可することになります
2. **猶予に当たる仕組みは、すでに取り込みの側にある。** ADR-0085 決定6 は「取り込まないことは許す」とし、取り込みを記名の強制層の変更としています。決定5 は、検査を変える取り込みを版の切り替えと同時に行うとしています。既存の go の採用者の複製は、取り込むまで旧い挙動のままです。これは GODEBUG の「宣言した版に既定を結ぶ」型と同じ働きを、採用者の取り込みの判断で持っています。テンプレートの中に猶予のスイッチを足すと、2つ目の経路になり、記名を経ずに旧い挙動へ戻せる口になります
3. 猶予のスイッチを置くと、統制の設定に「基準3 を測らない」を選ぶ欄ができます。これは弱める向きの設定であり、置けば例外の入口になります(ADR-0121 が受容の記録の新設を退けた理由と同じ)

そのかわり、ADR-0085 決定6 の保守者の義務を、省かずに履行することを条件にします。

- 落ちうる検査として列挙する: 基準3 が初めて判定され、基準値に満たなければ test の段が落ちること。範囲の記録の無い既存の構成は、全体(文の割合)で判定すること。本文は「範囲を記録していない構成を変更の範囲へ黙って読み替えてはならない」と定めています。新しく生成する構成だけが changed になります
- 直し方を列挙する: テストを足す。または `/process-change`(settings)で基準値を記名で見直す
- 書き込まずに試す手段: 取り込みの前に手元で coverage-check を通せる手順を同梱する
- 基準値は、全体の文の割合で決めた値を、変更の範囲の値として流用させない(`:964` と同じ)

### S-1-6 (d) 測れない構成(coverage.out が出ない)

- node の現行と同じ扱いにします。製品のコードがあるのに集計の記録が無ければ「集計ファイルが無い」として失敗にします(`coverage-check.mjs:266` と同じ)。対象なしにしません(`:914`)
- 製品のコードが0行なら、現行の「測定対象が0行」と同じく対象なしとして記録します
- go のアダプタの note の「ワークフロー側の go tool cover の出力で判定してください」は、実在しない段を指しています [確認: survey 論点D §1.4]。誤った案内なので削除します

### S-1-7 実装マークの扱い

- 実装する前の現状: go の基準3 が測られずに通ることを開示するマークが無い。これは開示の欠けである。直す PR より前に表示を足すなら、新しいマークを undelivered(plan=scheduled、issue=360)で置く
- 実装した後: go の全体の割合と失敗の扱い(新しいマーク、または IMPL-0259 と分ける)を delivered(machine)にする。違反と適合の対の試験(集計の無い go、基準値未満の go、製品のコードが0行の go)を条件にする
- IMPL-0259(変更の範囲)は、python と go のそれぞれで、違反と適合の対の試験がそろった時点で delivered にする。go の近似が本文の定義(文の開始行)と違う形を採る場合は、本文の改正が入るまで delivered にしない

## S-2: 「テストのみの変更で失敗が解消した変更」(IMPL-0204 の一部)

### 弁護する案

**現状の undelivered を、この部分については維持する**。マークを分け、この部分を新しいマークの undelivered(plan=scheduled)として表示し続けます。軽の反対の委員の案を弁護します。

### 変えない理由・変えたときに失うもの

- 本文の規定の対象は「テストのみの変更で**失敗が解消した**変更」です。静的な近似(製品のコードを変えずに既存のテストを変えた PR)は、「失敗」も「解消」も見ていません。近似を delivered と表示すると、マークの note が規定を狭く言い換え、言い換えた範囲で「降りた」と表示することになります。これは**マークによる規定の縮小**です。台帳を「降ろしたつもり」の一覧にしないという、`implementation-marking.md` の目的に反します
- 外部の測定(ImpossibleBench)では、AI の不正の主な型は試験の改変でした。ただし特別扱い・演算子の上書きのように**同じ PR で製品のコードも変える型**が残ります(外部 §4.3)。自己修正ループの大半は製品とテストを同じ PR で変えます。近似が拾わない範囲こそ危険の中心であり、そこを delivered の表示で覆うことになります

### それでも変える場合の条件

- 静的な近似を**表示として出すこと**には反対しません。ただし、新しいマークの note と出力に、拾わない形(ローカルで解消した失敗、同じ PR の製品とテストの同時の変更、push の間の force-push)を定型で添えることを条件にします
- delivered にしてよいのは、再実行型(基底の版のテストを PR の先頭の製品のコードに流す)を降ろし、違反と適合の対の試験を持ったときに限ります。その場合でも「仕様変更による正当な改めと区別しない」ことを note に書きます
- plan=adopter にはしません。この検出は、採用者の実装の有無で統制が消える型です。`impl-no-adopter.yaml` の 3.5.5「統制の弱化の検出」と同じ理由が当たります [推論。5.8.5 は登録簿に無い。登録するかは議長の判断]

### 採用者への影響と移行

表示だけなので、新しい失敗はありません。移行の手当ては要りません。

## S-3: 落ちることを期待する印の欄と、予期せず通った場合の失敗

### 弁護する案

現状(どのマークも付いていない)は弁護しません。**印の規定は本文にあるのにマークが無い状態は、開示の欠け**だからです。弁護するのは「undelivered の表示を先に置き、照合できる範囲を枠組みごとに表で開示する」案です。

### 論点ごとの見解

- **テンプレートが印の書式を定めること**: 反対しません。本文が求める3つの欄(Issue・照合する失敗の理由・見直しの時期)を、テンプレートが採用者の製品のテスト向けの書式に落とすのは実装の役割です。ただし書式は、印の行の近くの注釈(リポジトリの中に残り、差分で読まれ、履歴が残るもの)に置くべきです。PR 本文には置きません [推論]
- **検出の対象**: 追加行の印(xfail 系・`test.failing`・`test.fails`)に、3つの欄があるかを表示します。合否には使いません(本文の「印の件数の上限と、期待値の差分による機械の阻止は課さない」と、検出を G-5 の合否に使わない定めを弁護します)
- **予期せず通った場合の失敗**: これは表示ではなく、**本文が「試験の失敗とする」と定めた合否の規定**です。機械で確かめられる範囲は機械で確かめるべきです
  - pytest: `xfail_strict = true`(または各印の `strict=True`)を構成で確かめられます。契約検査で確かめる形は delivered(machine)にできます
  - Jest・Vitest: 枠組みが常に厳格です。確かめることはありません。ただし「別の理由で落ちた場合」は照合できません
  - Go・JUnit 5: 期待する失敗の印がありません。印の規定の対象そのものが生じません。採用者が skip で代用すれば、それは検証の弱体化の検出の対象になります
- **照合する失敗の理由**: 照合できるのは pytest の `raises` だけです。ほかの枠組みで照合できない部分は、新しいマークの undelivered(plan=scheduled)とし、枠組みの表を note に書きます

### plan=adopter を採らない理由

軽の起案の「照合できない部分を plan=adopter」に反対します。`adopter` は「規定は課したまま、採用者が自ら実装する」意味です(`implementation-marking.md:129`)。Jest で「別の理由で落ちたら失敗」を実装するには、採用者が枠組みを拡張する必要があります。採用者に現実の手段があるとは言えません。手段の無い実装を採用者へ委ねる表示は、統制が採用者の側にあると誤読させます(S-4 と同じ問題)。採用者が実装できると示せる枠組みに限って、`decision=` に手段を書いて adopter にすることは妨げません。

### 採用者への影響と移行

pytest の strict を契約検査で求めると、既存の python の採用者に新しい失敗が生じます。xfail を使い、strict を設定していない構成が落ちます。S-1-5 と同じく、猶予は置かず、ADR-0085 決定6 の列挙と直し方(ini に1行)を条件にします。

## S-4: 人による中間の層のマージ(IMPL-0248・0254)

### 弁護する現状

**ADR-0078 決定3(ルールセットの対象を機能ブランチへ広げない)を維持する。** **IMPL-0248・0254 は undelivered(plan=scheduled)のまま表示し続ける。**

### ADR-0078 決定3 を変えない理由(強めて述べる)

- 決定3 の採った時点の理由は「直接の push の扱いを実機で確かめておらず、着地の保護で足りる」でした。今回の調査で、前半は**提供者の文書で裏づけられ、強まりました**(survey 論点B B-3)。`pull_request`・`update` の規則は、対象のブランチへの直接の push を止めます。bypass_mode に「push は迂回でき、マージは迂回できない」値はありません。手動のスタックは層のブランチへ push を重ねる運用です。対象を広げれば、手動のスタックそのものが成り立ちません
- 後半(着地の保護で足りる)も維持できます。中間の層のマージの実害は「層ごとの確認の粒度の喪失」です。既定ブランチへの着地では G-5・G-6 が掛かります。層ごとの承認の欠けは IMPL-0250(#359)が扱います
- 広げたときに失うもの: 手動のスタックの運用、または作業ブランチへの直接の push の自由(bypass に開発者を入れればマージも迂回でき、拒否が意味を失う)。外部の道具(Graphite・ghstack・spr)も、中間のマージをプラットフォームの規則で拒否していません(外部 §3.1)。拒否の手段を持つ実務は見つかっていません

### 変える条件(ADR-0078 決定3 を置き換えてよい場合)

- GitHub が、基底のブランチで PR のマージを制限する規則、または push とマージを分ける規則(GitLab の Allowed to merge / push の分離の逆向き)を提供したとき
- 本標準が手動のスタックをやめ、GitHub 標準のスタック(2026-10-06 一般提供。構造として中間の層への着地を起こさない)へ寄せると決めたとき。その場合はルールセットを広げる必要そのものが無くなります

### plan=adopter を採らない理由

`adopter` は「採用者が自ら実装する」という主張です。採用者も GitHub の上では拒否を実装できません(外部 §3.2・GitLab も同じ)。adopter と書けば、台帳は「統制は採用者の側にある」と表示します。実在しない統制の所在を表示することになります。降りていない規定を表示し続ける原則の目的は、統制の空白を見えるままにすることです。adopter はこの空白を「委任済み」に見せ替えます。

### scheduled の維持は誠実か

「降ろす予定」の表示が、実現の見込みの無い予定にならないかという反論が考えられます。scheduled には実在の経路が2つあります。一つは、GitHub 標準のスタックへの誘導と、その上の層の検査(EV-0139 の実機の確認)。もう一つは、提供者の規則の追加の監視です。note に「提供者の文書の範囲では、手動のスタックと両立する拒否は組めない」と書きます。見直しの契機に上の2つを書きます。そうすれば scheduled は誠実な表示になります。それでも、見直しを重ねても経路が無いと分かった場合の扱いは残ります。そのときは `plan` に新しい値を足すのではありません。本文の規定の文を「拒否の設定」から改めるかを、重の審議で決めるべきです(ADR-0084 の、「課さない」を plan の値にしない原則を弁護します)。

### マージの後の検出の位置づけ

- **表示として降ろし、出荷(G-7)の失敗にしない**(§1 の合意を弁護します)。理由は3つです。(1) 起きたマージは取り消せず、出荷を止めても層ごとの確認は戻りません。止めると、履歴の書き換えか免除の申請へ圧力が向きます。(2) 着地の G-5・G-6 は掛かっています。(3) 中間のマージは記録の欠落ではありません。欠落として数えると、ADR-0083 決定3 の「記録の欠落」の語の意味が広がります
- ただし、検出の結果を IMPL-0250(層の合わさった差分への1件の承認を層ごとの確認に数えない)の材料として渡すことを条件にします。表示だけで終わらせず、層ごとの確認の欠けの判定に届けます
- 検出は新しいマークで delivered(machine)にします。IMPL-0248・0254 を delivered にする根拠には使いません(検出は拒否ではありません)
- 3件の note の「ask で人へ戻る」は事実の誤りなので直します(§1 の合意)

### 採用者への影響と移行

表示だけなので、新しい失敗はありません。records を初期化していない構成では写しが届きません。その場合は検出が働かないことを出力に出します。

## S-5: AI による中間の層のマージ(IMPL-0255)

### 弁護する案

**IMPL-0255 の全体を delivered にしない**。マークを分けます。

- 分けた1件: 「AI の担い手による `gh pr merge` と、REST の merge の呼び出しの拒否」。`test-guard-bash.mjs` に場面があります [確認: 24〜39 行]。delivered(machine)にできます。note に、フックは抑止の層であることを書きます(フック自身の開示と同じ)
- 残り: `git merge` と `git push` の組で中間の層へ取り込む経路は undelivered(plan=scheduled)とし、通る経路を note に列挙します

### 通る経路を塞ぐ案に反対する理由

- `git merge` は、既定ブランチの変更を作業ブランチへ取り込む正当な操作でもあります。手元の併合と push の組を一律に拒否すると、正当な作業を止めます。止められた担い手は、迂回(スクリプトから API を呼ぶ)へ向かいます
- `gh pr create/edit --base <機能ブランチ>` は、手動のスタックを作る正当な操作そのものです。塞げばスタックが作れません
- 塞いでも、フックは抑止の層であり、担い手が書いたスクリプトの経路は残ります。塞いだことを根拠に delivered と表示すれば、残る経路が台帳から消えます
- したがって、塞がずに**開示する**ことを推します。開示の文は、拒否する経路・通る経路・通る理由(正当な操作と区別できない)の3つにします

### 変える条件

push の先が既定ブランチ以外で、かつ push する内容が別の作業ブランチの併合を含む場合に限って識別できると、実行で示せたときは、その形だけを拒否の対象へ足すことを再検討します。誤検出(既定ブランチの取り込み)を試験の対で示すことが条件です。

### 採用者への影響

既存の拒否の範囲は変わりません。note と台帳の表示が正確になるだけです。

## S-6: IMPL-0102(L2 の採点の稼働)の扱い

### 前提として弁護すること

§1 の合意「検査できる条件を条項で定めない」を弁護します。ADR-0058 決定5 と不採用の表(:108「UCL・モジュール数の導出 → 機械で検査できる条件が定まらず、自己申告・偽装の余地が大きい」)の理由は今も当たります。survey E-3 でも、自己申告を超える候補(採点の出力の記録・承認との照合)は、テンプレートが審査深度を変える機構を持たない限り照合の相手がありません。

### そのうえでの見解: plan=scheduled のままにはできない

定めないと決めた以上、IMPL-0102 の現状(undelivered・plan=scheduled・「検査できる条件が定まっていないため降ろしていない」)は**表示として誤りになります**。降ろす予定が無いからです。`implementation-marking.md:132` は「課さないと決めた規定は、条項を改め、`not-imposed` へ移す」と定めています。この規則を弁護します。したがって、次のように進めます。

1. 新しい ADR に「L2 の稼働を機械で検証する条件を定めない」と、その理由を書きます
2. 本文 `:1854`「水準は自己申告ではなく、条件の充足を記録で示します」の**確かめ手**を明記します。機械は根拠の実在と見直し日だけを確かめます。根拠の中身が L2 の条件を満たすかは、変化点の決定者(人)が確かめます。いまは `:1955` が限界として開示しているだけで、誰が確かめるかが本文に無いためです
3. IMPL-0102 は、機械の検証の規定としては `not-imposed` へ移します。人の確かめの規定には新しいマークを付けます

### 人の確かめのマークを delivered(manual) にしてよいか

条件つきで認めます。delivered(manual) は、「手順が置かれた」ことと「確かめる者が名指されている」ことを示すだけです。確かめたことは示しません。そこで、次の2つがそろったときに限ります。

- `/process-change`(settings)に、決定者が根拠の中身を L2 の条件(採点の稼働・閾値による審査深度・取り消し可能性)に照らして読み、読んだ結果を変化点の記録に書く手順があり、記録の欄の欠けを機械が示すこと
- L2 で規模の基準なし(null)を効かせた出力に、「根拠の中身(条件の充足)は確かめていない。確かめたのは根拠の所在の実在と見直し日だけ」を定型で出すこと。採ることを推します。理由は survey E-2 の node での確認です。無関係な `README.md` を根拠にした L2 の宣言で、基準なしが効きました。出力がこの事実を黙っていると、緩和が自動で与えられたように読めます(要求事項4「宣言は記録であり、緩和を自動で与えない」に反する見え方)

adopter にはしません。根拠の中身を読む手順はテンプレートが置けます。採用者に委ねる理由がありません。

### 採用者への影響

出力の定型の文と、記録の欄が増えます。欄の欠けを表示だけにすれば、新しい失敗はありません。欄の欠けを失敗にする場合は、L2 を宣言した採用者に新しい義務が生じます。その場合は重の審議の範囲(採用者への新しい義務)として別に扱うべきです。

## 結論の要約

- **S-1**: ADR-0085 決定2 の go に関する理由が誤りであり、結論(事前点検で止めない)と node の理由は正しい。ADR-0121 決定4 の原則は正しいが、ステータスで「単一のスタックなら成り立つ」と go まで追認した射程の書き方は誤り。新 ADR で両方を補う。go の全体は文の割合、変更の範囲は AST で文の開始行へ戻して本文の分母の定義に合わせる。採用者の取り込みの判断で移行を受け、テンプレートの中に猶予は置かない(決定6 の列挙は必須)。coverage.out が無ければ失敗にする
- **S-2**: 静的な近似で delivered にしない。マークを分けて undelivered(scheduled)を維持し、近似は拾わない形を添えた表示に限る。delivered は再実行型を降ろしたときだけ
- **S-3**: マークが無い現状は開示の欠けなので、表示を足す。pytest の strict は契約検査で delivered(machine)、照合できない枠組みは表つきで undelivered(scheduled)。adopter は手段を示せる場合に限る
- **S-4**: ADR-0078 決定3 を維持する(文書の確認で理由が強まった)。IMPL-0248・0254 は undelivered(scheduled)のままとし、見直しの契機を note に書く。adopter にはしない。マージの後の検出は別のマークで表示として降ろし、IMPL-0250 へ渡す
- **S-5**: `gh pr merge` と API の拒否だけを分けて delivered(machine)。`git merge` と `git push` の組と `--base` の付け替えは塞がず、undelivered で経路を開示する
- **S-6**: 条件を定めない決定を維持する。IMPL-0102 の機械の検証は not-imposed へ移し、本文に確かめ手(変化点の決定者)を明記する。人の確かめは、手順と定型の文「根拠の中身は確かめていない」がそろって初めて delivered(manual)
- **S-7**: 新しいテストのファイルとアサーションの対を検出の範囲に入れる。根拠の欄はテストのコードの注釈を推す。読めない升とテストのパスは別の枠で表示する。C の保存期間は ADR-0078 決定4 に合わせ、90 日のままでは delivered にしない。IMPL-0479 は #360 から open の Issue へ移す
- **範囲外**: `rulesets` の重複は、マークごとに指す実体を決めて id を分け、重複を検査で拒否する。python のテストのファイルの算入は直す(決定6 の列挙つき)。CRLF は読み込みの側で正規化して直し、照合は緩めない
