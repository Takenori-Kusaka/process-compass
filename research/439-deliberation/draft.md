### 2.1 事実

### 2.2 競わせる案

| 案 | 中身 | 破れを捉える時点 | オフラインの原則 |

| A | `npm run check`(`lint:impl`)の中で `gh` へ問い合わせる | 次に検査が走ったとき | **破る** |

| C | 検査の外に、Issue の事象で動くワークフローを置く(`issues: closed`・main への push・月次・手動)。同じスクリプトを手元でも実行できる | 閉じた時点 | 保つ(`npm run check` は変えない) |

### 2.3 起案の推す形: C + E。D の手順は残す

1. **スクリプト**(仮: `scripts/check-impl-plan-issues.mjs`)。中核は純粋な関数「マークの一覧と、閉じた Issue の番号の集合を受け取り、閉じた Issue を名指すマークを返す」。入力の取り方を2つ持つ
   - `--closed-from <ファイル>`: 番号の一覧を読む(試験と、オフラインの再現に使う)
   - 引数なし: `gh` で、マークが名指す番号だけの状態を問い合わせる
   - マークの読み取りは `lib/impl-inventory.mjs` の既存の関数を使い、コードフェンスの中の見本を数えない
   - 見つからない番号・Issue でなく PR である番号も所見にする
2. **ワークフロー**(仮: `.github/workflows/impl-plan-issues.yml`)。`ci.yml` の `check` には入れない
   - 契機: `issues: [closed]`、main への push(docs の下の変更)、月次、`workflow_dispatch`
   - 既定ブランチの木でスクリプトを実行する。所見があれば実行を失敗にし、閉じた Issue へ「この Issue を名指すマーク(識別子と所在)」をコメントして**開き直す**(`issues: write` はこのジョブにだけ付ける。`evidence-review.yml` と同じ付け方)
   - 月次と push の契機は、閉じた後に足されたマーク(既に閉じた Issue の番号を書く誤り)と、ワークフローが動かなかった期間の取りこぼしを拾う
3. **E**: `lint:impl` に、`issue=` の番号が `issue-index.tsv` に在り種別が issue であることの検査を足す。番号の打ち間違いと PR の番号の名指しを、オフラインで落とす。新しい後継の Issue を名指すときに写しの更新(`npm run issues:snapshot`)を強いる
4. **手順(D)は残し、道具を与える**: `implementation-marking.md` 136 行を改める。閉じる者は、閉じる前に `npm run impl:issues`(仮)を手元で実行する。`Closes #N` を書くコミットは、付け替えを同じ push に含める
5. **新しい ADR**(番号は実装の時点の次の番号)で、ADR-0084 の決定 R-4 の1項と採らなかった案の表の1行を置き換える。「検査(`npm run check`)はオフラインで実行する」は保つと明記する

開き直しを推す理由: 規約は「0 件を確かめてから閉じる」である。0 件でないまま閉じた状態は規約の違反で、開き直しは違反の前の状態へ戻す操作に当たる。開き直せば、台帳が計画として表示する Issue は open に戻り、表示と実態の食い違いが、付け替えを待たずに解ける。公開を止める必要が無い。

## 3. 反対の立場からの反論

### 3.1 付け替えについて

1. **新規 2 件は多い。#359・#358 を開き直せば足りる**。#359 の裁定は「#359 に残す」と書いた。誤りは閉じたことであり、誤りを戻すのが最短で、マーク 12 件を書き換えずに済む。note の「#359 の裁定」という参照とも合う
2. **#326 は溜め場になる**。#326 は「決めること: 各項目を検査として足すか、限界として開示するか」の1行しか受け入れ条件を持たない。3 件を足すと、降ろす計画ではなく棚に置くだけになる。IMPL-0132 は ADR-0024 決定12 が「検査する」と決めた規定で、「足すかどうか」を問う #326 の枠に入れると、決定済みのものを未決に戻す
3. **IMPL-0492 を #361 へ寄せると、needs-owner の Issue の範囲が広がる**。#361 は所有者が典型的なリポジトリを用意する作業で、受け入れ条件は env-check の記録である。record-copy の確認の項目(7 項目)を足すなら、#361 の受け入れ条件へ明記しないと、閉じるときにまた取り残す
4. **IMPL-0174 を付け替えるだけでは、食い違いを別の Issue へ運ぶだけ**。予定の無い `scheduled` は、閉じた Issue の名指しと同じ種類の表示と実態の食い違いである

### 3.2 検出について

1. **C は公開を止めない。食い違った台帳が公開され続ける**。本件の欠陥は「表示と実態の食い違い」で、議長の基準では巡の数に関わらず直す「高」である。検査の外に置くと、赤い実行を誰も見なければ D と同じになる。`evidence-review.yml` の Issue が読まれているかの記録も無い
2. **機械による開き直しは、人の閉じる判断を機械が覆す**。本標準の一文の要約は「決められた場所では必ず人間が触る」である。所有者が意図して閉じた Issue(重複・取り下げ)を機械が開き直すと、所有者は付け替えより先に機械と争うことになる。`Closes #N` のコミットと付け替えのコミットが別の push だと、正しい手順の途中で開き直しが起きる
3. **B のほうが決定論的で、公開を止められる**。写しに状態の列を足し、`lint:impl` が落とす。写しの鮮度は、push の前の手順(`npm run issues:snapshot`)へ入れればよい。ADR-0089 が状態を書かなかった理由は差分の雑音だけで、名指された番号だけの小さな写しを別のファイルにすれば雑音は小さい
4. **E は本件の欠陥を1件も捉えない**。14 件はすべて実在する Issue である。受け入れ条件3 に対して E は関係が薄く、変更を増やすだけである
5. **検出が「`issue=` を書かない」誘因にならないか**(ADR-0076 決定5)。`plan=scheduled` には `issue=` が必須なので書かないことはできないが、閉じた Issue を避けるために、合わない open の Issue へ機械的に寄せる誘因は生まれる。#326 への 3 件が既にその兆しである
6. **ADR の決定の置き換えを軽で行ってよいか**。ADR-0084 は 5 委員の会議体を経た決定である

### 4.2 検出

| 論点 | 裁定の案 | 理由 |
| --- | --- | --- |
| 検出するか | **する**。ADR-0084 の「機械で検出しない」を新しい ADR で置き換える | 人の手順は 8 件中 4 件で破れ、2 週間以上検出されなかった。信頼性の軸で、D だけの継続は採れない |
| 置き場 | **C**(検査の外のワークフロー + 手元の同じスクリプト) | 破れが起きる時点(閉じた時点)で捉えるのは C だけ。`npm run check` のオフラインの原則を保つ |
| 公開を止めるか(反論 3.2-1) | 止めない。代わりに、所見のある Issue を開き直して食い違いそのものを解く(Q2 の所有者の答えによる) | 公開を外部の状態で止めると、木が変わらないのに CI の結果が変わる。ADR-0084 が暦について退けた形と同じ |
| 開き直し(反論 3.2-2) | **所有者に問う**(Q2)。議長の推す形は「コメントして開き直す」。`Closes #N` と付け替えが別の push になる場合は、手順(付け替えを同じ push に含める)で避ける。意図した閉じ(重複・取り下げ)でも、マークが名指す限り台帳は計画として表示するので、開き直しか付け替えのどちらかが要る | コメントだけの形は次点。食い違いが付け替えまで残る |
| E(反論 3.2-4) | **採る**。本件の 14 件は捉えないが、付け替えの作業そのものが新しい番号を書く操作で、打ち間違いが起きる場所である。決定可能でオフラインで閉じる条件を機械にしない理由が無い | — |
| 誘因(反論 3.2-5) | 合わない Issue へ寄せることは機械で閉じない。manual とし、付け替える者が寄せ先の Issue へ受け入れ条件の案をコメントで足すことを手順に書く。根拠水準マークで開示する | — |
| 重さ(反論 3.2-6) | 軽のまま。置き換えるのは決定の1項で、その理由である原則は保つ。独立の突合で「高」が出たら重へ上げる(CLAUDE.md の条件) | — |

### 4.3 採らない案(記録)

| 案 | 採らない理由 |
| --- | --- |
| A: `npm run check` の中で GitHub へ問い合わせる | オフラインで同じ結果を出す原則(ADR-0084・ADR-0089)を破る。認証の無い環境・レート制限・フォークの PR で結果が変わる。木が同じでも、誰かが Issue を閉じると main の検査が落ちる。採るなら重の審議が要る |
| B: 状態つきの写しを版管理へ置く | 写しが古い間、検査は通る。破れは「閉じた直後」に起きるので、写しが最も古い時点に当たり、通過の表示が実態と食い違う(検査が保証していないことを保証したと読ませる)。鮮度を push の前の手順に頼ると、D と同じ人の手順へ戻る。機械に写しを更新させると、Issue の事象ごとに main へのコミットが生じる。`issues-snapshot.mjs` が状態を書かないとした設計とも合わない |
| D だけ: 人の手順と開示 | 4 件の破れが実測された。開示しても、台帳が閉じた Issue を計画として表示する状態は直らない |
| 閉じた Issue を名指す件数を台帳の冒頭に出すだけ | 台帳の生成はオフラインで、状態を知り得ない(B と同じ問題) |
| `review=` を過ぎたマークで検査を落とす | ADR-0084 が退けた(暦で CI が落ちる)。本件は変えない |
| 本件で IMPL-0174 を `adopter` へ改める | `decision=` が指す記録が無い。条項の審議を要する |
| 7 件だけを直し、残る 7 件を別の Issue にする | 同じ欠陥で、同じ検出の前提になる |
