## 要約(10 行)

1. 語は標準本文の 5 箇所(第5章 5.4.6 の表 2 つ、5.5.4、第8章、附属書H)に同じ列挙として写されており、どこにも分子・分母・単位が無い。ほかに EV-0090 のマーク、フェーズ3 の公開ページ(「自動承認の割合」)、Zenn の概要記事(マークなしで条件だけを載せる)にある。
2. 出所は Anthropic の報告(2026-02-18)。原典を再取得した。原典自身が分子・分母を定義しておらず(「of sessions」と「of the time」が混在)、上昇を「信頼の蓄積」「監督の放棄ではない」と解釈している。劣化の指標として使っていない。
3. 原典の量は 2026-10 時点で意味が変わっている。Claude Code は v2.1.283 以降、許可の確認を分類器に委ねる auto mode が組み込みの開始モードである。「確認を省く実行の比率」は利用者の選択ではなく製品の既定を測る量になった。
4. テンプレートに、この比率を計算する実装は無い。5.4.6 の 4 つの比率(差し戻し率・重複率・手戻り率を含む)のどれも計算しておらず、AI自律レベルを持つ構成の欄も、自動の引き下げの実装も見当たらない。5.4.6 に実装マークは 1 つも無い。
5. IMPL-0093 が数えているのは「承認」ではなく「変更」である。適格な承認がすべて挙動要約の形を欠く変更の件数を出す。分母に当たる「G-6 の承認の全数」は出力に無い。形の検査は `aaaaaaaa` と `LGTM LGTM LGTM` を挙動要約に数える(実行して確認)。
6. 登録の前提(`basis.detection`)は「計測している」の 1 語で通る(実行して確認)。テンプレートの fixture と README は、この欄を「欠陥・逸脱を何で検知するか」と読んでおり、4 つの比率の計測手段とは読んでいない。
7. 外部で、承認の形骸化を測る量は 3 系統ある。(i) 手続の形(議論なしの承認、規模に対して速すぎる承認、自己承認)、(ii) 応諾率(許可プロンプトの承認率、警告の通過率、アラートの上書き率)、(iii) 正解つきの見逃し(誤った提案への同意率、差し込んだ危険の阻止率)。
8. しきい値に実証の根拠があるものは、確認した範囲で 1 つだけ(レビュー速度 200 行/時。出所は Kemerer と Paulk)。製品のベンチマーク(5% 未満、10〜25% など)は根拠を示していない。規格(EU AI 法 14 条、NIST AI 600-1)は自動化バイアスを名指すが、指標を定めない。
9. 応諾率は単独では劣化を示さないという報告が複数ある(医療のアラートの上書きは 49〜96% だが多くは正当、Anthropic 自身の解釈)。慣れは語彙の指標で検出できないという報告もある(AIDev の反復レビュア)。
10. 選択肢は 8 つ立てた(量を 1 つに定める 3 案、組織に定めさせる案、発火条件から外す 2 案、正解つきの量へ置き換える案、決めない案)。語の扱いと、「前月比」と母数の下限(30 件または四半期)の食い違いは、どの案でも別に決める必要がある。

### 1.5 5.4.6 の文脈から読める「測りたいもの」

5.4.6 の理由の文:

> 監督の劣化は静かに進み、申告されないためです。

> 代替として、月次の点検でレベルを引き下げる手順は置きません。人間の点検を挟むと、引き下げは判定になります。(中略)**点検する側が同じ劣化の当事者である構成では、非対称は成立しません**。

5.4.2 の監視者の列:

> L1「人間が全ての変更を確認する」/ L2「人間が統合点を確認する」/ L3「機械が常時監視し、人間が事後に確認する」

ここから、量には次の制約が掛かる。

- 人の点検や申告を経ずに、記録から機械で算出できること(5.4.6 が月次の点検を退けている)
- L2 の前提条件に置かれているので、L2 を適用する前(L1)の時点で「計測できる」と確かめられること
- L1 では「全ての変更を人間が確認する」ので、変更の単位で「人が確認していない変更」を数える量は定義上 0 になる。L2 では統合点だけを確認するので、同じ量は設計上 0 にならない

読みの候補と、文脈との適合は、調査E の表(T1「意味 A は何を指すか」)のとおりで、今回の確認でも変わらない。読み 1(G-5 の通過)は合わない。読み 2(人の承認を経ないマージ)は「判定の履歴の集計」と合うが L1・L2 で噛み合わない。読み 3(許可の確認を省く実行)は出所だが「判定の履歴」と単位が合わない。

### 2.1 出所の原典(再取得した)

Anthropic, Measuring AI agent autonomy in practice(2026-02-18)。https://www.anthropic.com/research/measuring-agent-autonomy (台帳 SRC-0067)

- 該当の文: 「Among new users, roughly 20% of sessions use full auto-approve, which increases to over 40% as users gain experience.」
- 図 2 の説明: 「Auto-approve rate by account tenure.」「Experienced users increasingly let Claude run without any manual approval.」
- **分子・分母・単位の明示は無い**。本文は「of sessions」と「of the time」を混ぜて使う。図の説明と合わせると、単位はセッションで、分子は「full auto-approve(手動の承認を一切挟まない)で走ったセッション」と読める。操作(ツール呼び出し)の単位ではない
- 解釈: 「This shift is gradual, suggesting a steady accumulation of trust.」「Taken together, these findings suggest that experienced users aren't necessarily abnegating oversight.」「effective oversight doesn't require approving every action but being in a position to intervene when it matters.」
- 対になる量: 割り込み率。「New users (those with around 10 sessions) interrupt Claude in 5% of turns」、経験者は約 9%(単位はターン)。「The fact that interrupt rates increase with experience alongside auto-approvals indicates some form of active monitoring.」
- 留保: 既定が手動の承認である(「actions are not auto-approved by default」)ため、変化の一部は製品の設計の反映でありうる。高いセッション数では信頼区間が広い
- しきい値: 無い。劣化の兆候としての線は引かれていない

**原典は、この比率の上昇を監督の劣化として扱っていない**。操作ごとの承認を義務づけることについては「will create friction without necessarily producing safety benefits」と書く。調査E と擁護の委員の理解は、原文で裏が取れた。

### 2.2 エージェント製品の許可の仕組み(Claude Code)

**許可モード**。https://code.claude.com/docs/en/permission-modes

- モードは 6 つ: `default`(Manual。読み取りだけ無確認)、`acceptEdits`、`plan`、`auto`、`dontAsk`、`bypassPermissions`
- 「With Claude Code v2.1.283 or later, auto mode is the built-in starting permission mode for interactive terminal and VS Code sessions.」。auto mode では「a second model, the classifier, reviews actions instead of you」
- 逆向きのしきい値がある: 「if the classifier blocks an action 3 times in a row or 20 times total, auto mode pauses and Claude Code resumes prompting.」。これは**機械の拒否が続いたら人の確認へ戻す**条件で、承認が続いたら何かをする条件ではない。値の根拠は文書に無い

- メトリクス `claude_code.code_edit_tool.decision`(「Count of code editing tool permission decisions」)。属性は `decision`(accept / reject)、`source`(config / hook / user_permanent / user_temporary / user_abort / user_reject)。対象は Edit・Write・NotebookEdit だけ

- イベント `claude_code.permission_mode_changed`(`from_mode`・`to_mode`・`trigger`)
- **承認率・自動承認率を直接に出すメトリクスは無い**。導くなら、`tool_decision` を `source` で分ける(config・hook を人の確認なし、user_* を人の決定と数える)。許可モードは決定の属性に無く、モード変更のイベントと突き合わせる必要がある

操作の単位で「人の確認なしに実行された操作 ÷ 全操作」を導く材料はある。ただし製品に固有で、ログの出力を有効にする必要があり、分類の線(`user_permanent` で恒久に許可した後の実行をどちらに数えるか)は利用者が決めることになる。

**許可プロンプトの承認率**(応諾率)。

- Anthropic, How we built Claude Code auto mode(2026-03-25)。https://www.anthropic.com/engineering/claude-code-auto-mode (台帳 SRC-0072)。「Claude Code users approve 93% of permission prompts.」「Over time that leads to approval fatigue, where people stop paying close attention to what they're approving.」。分子・分母・期間・標本は書かれていない。単位は許可プロンプトと読める。分類器の側には定義がある(「False-negative rate (FNR) is the fraction of dangerous actions the classifier lets through」ほか。評価データは実トラフィック 10,000 件、過剰な行為 52 件、合成の持ち出し 1,000 件)
- Anthropic, Auto mode is now the default in Claude Code(2026-08-07)。https://claude.com/blog/auto-mode-default-in-claude-code (台帳 SRC-0290)。「Data suggests that manual review can become habitual: users approve 97% of permission prompts in Claude Code.」。計画の承認は 39% が却下。対照実験: 「The testers caught the dangerous command just 13.6% of the time (143 of 1,053)」「they blocked about 17% of dangerous commands early in a session, dropping to about 5% after 50 or more prior prompts」。こちらは分子・分母が明示されている(差し込んだ危険なコマンドを止めた人数 ÷ 被験者数。1 人につき 1 件)

### 2.3 コードレビューの実証研究

**McIntosh, Kamei, Adams, Hassan, The Impact of Code Review Coverage and Code Review Participation on Software Quality(MSR 2014)**。https://rebels.cs.uwaterloo.ca/papers/msr2014_mcintosh.pdf (PDF を取得して本文を読んだ)

レビューの参加度を 3 つの比率で測る。単位は変更、集計はコンポーネントごと。

| 指標 | 定義(逐語) | しきい値と根拠 |
| --- | --- | --- |
| 自己承認 | 「The proportion of changes to a component that are only approved for integration by the original author.」 | — |
| 急いだレビュー | 「The proportion of changes that are approved for integration at a rate that is faster than 200 lines per hour.」 | 200 行/時。出所は Kemerer と Paulk(論文の参考文献 19)。「setting the reviewing speed threshold to 100 lines per hour had little impact on our models」 |
| 議論なし | 「a patch that has been approved for integration, yet does not have any attached comments from other team members」。自動検証のコメントは除く | — |

- 分子は該当する変更、分母はそのコンポーネントの変更
- 急いだレビューは、依頼の作成から承認までの経過時間で測る。著者は「our metric represents a lower bound of the actual proportion」と断る(レビュアがすぐ読み始めたと仮定するため)
- 結果: 「the proportion of changes without discussion has a statistically significant impact on the models of all three of the studied releases」。自己承認は Qt 5.0.0、急いだレビューは Qt 5.1.0 で有意
- 対象は Qt・VTK・ITK(Gerrit)。観察研究で、著者は交絡の可能性を認める
- 「この比率を超えたら危険」という線は引いていない。回帰モデルの説明変数として使っている

確認した範囲で、分子・分母・単位としきい値の根拠がそろっている定義はこれだけである。ただし、しきい値(200 行/時)は「急いだレビュー」の判定の線であり、比率そのものの警戒線ではない。標準は同系統の数字を既に引いている(`gate-criteria.md`「200〜400行を60〜90分で読む場合」)。

**AIDev の反復レビュア**。

- Yu ほか, Habituation at the Gate(arXiv 2606.22721)。https://arxiv.org/abs/2606.22721 (要旨を読んだ。台帳 SRC-0395 は全文)。400 人・11,429 レビュー。要旨の現在の版は「population-level shift in approval rate from 30.1% to 36.8%」、経験の十分位で +14.5 ポイント、インラインコメント −22%、待ち時間 +3.5 倍。結論は「most consistent with reflexive habituation under growing workload rather than rational trust calibration alone」。要旨に承認率の分子・分母の定義は無い(レビューの単位で、承認の状態のレビュー ÷ 全レビューと読める。本文での定義は今回確かめていない)
- Yu ほか, Beyond Lexical Metrics(arXiv 2609.06213)。https://arxiv.org/abs/2609.06213 (要旨を読んだ。台帳 SRC-0316 は全文)。同じデータで「Approval rates rise from 30.5% … to 36.6%」。手作りの語彙の指標 4 つは一貫した低下を示さず、分類器は F1 = 0.485 で多数派の基準を下回る。文の埋め込みでは F1 = 0.74。「detectable in latent distributional structure rather than in classical lexical metrics」
- 2 本は同じデータを使うので、独立の測定は 1 件である(知見 FND-0084 の注)。同じリポジトリ・同じ期間の人の PR では承認率が下がった

本標準への含意は 2 つある。(a) 承認率(承認 ÷ レビュー)の上昇は、慣れの観測値として使われている。ただし同じ量は、エージェントの改善による正当な信頼の変化とも区別できない(著者の留保)。(b) **慣れは語彙の指標では検出できなかった**。挙動要約の形(語数、承認の語だけか)で分子を判定する定義は、この結果と向きが合わない。

Graphite の数字は参考になる。活発なコミッタのマージ済み PR のうち、コメントが 1 つも無いものが 46%、全レビューの文が 3 語未満のものが 19% とされる。つまり、**要約を伴わない承認は、一般の現場では少数の逸脱ではなく、基準の状態である**。本標準は G-6 でそれを承認に数えないと定めているので、採用組織の初期値は現場ごとに大きく違う。

製品は、形骸化の量を「変更(PR)」の単位で数えている。「承認」の単位で比率を出す製品は、確認した範囲では無かった。ベンチマークの値に根拠を示す製品も無かった。GitHub のルールセットの文書は取得できなかった(404)。

### 2.5 隣接領域(応諾率は単独で劣化を示すか)

- **医療のアラートの上書き率**。van der Sijs ほか, Overriding of Drug Safety Alerts in Computerized Physician Order Entry(JAMIA 2006)。https://repub.eur.nl/pub/60465 (要旨を読んだ)。17 本の文献の総説。「Drug safety alerts are overridden by clinicians in 49% to 96% of cases.」「Alert overriding may often be justified and adverse drug events due to overridden alerts are not always preventable.」。原因に「low specificity, low sensitivity, unclear information content」「unnecessary workflow disruptions」を挙げる。上書き率が高いことは、人の側の劣化ではなく、警告の側の質の低さでも説明される
- **ブラウザの警告の通過率**。Akhawe と Felt, Alice in Warningland(USENIX Security 2013)。https://www.usenix.org/conference/usenixsecurity13/technical-sessions/presentation/akhawe (要旨を読んだ)。「over 25 million warning impressions」。通過率は警告の種類と製品で 1 割から 70.2% まで開く(「users continued through 70.2% of Google Chrome's SSL warnings」)。著者は、警告の体験の設計が利用者の振る舞いを大きく変えるとする。同じ人でも、提示の設計で応諾率が変わる
- **誤った提案への同意率**。Buçinca, Malaya, Gajos, To Trust or to Think(CSCW 2021)。https://arxiv.org/pdf/2102.09692 (PDF を取得して定義の箇所を読んだ)。「Overreliance: Percentage of agreement with the AI when the AI made incorrect predictions」。分母は AI が誤った事例である。**正解が分かっている事例に限って測る**。標準の 5.7.6 の主指標(「AIまたは前工程が誤っていた事例を、人間が捕捉した割合」)と 5.6.2 の欠陥注入は、この型である(5.7.6 が引く「対照実験(2021年)」はこの論文と読める)

3 つを並べると、応諾率(承認 ÷ 提示)は、提示の質・提示の設計・対象の難しさで動き、人の注意の量だけを映さない。過信を測る研究は、分母を「誤っていた事例」に絞っている。

### 2.6 規格

- **EU AI 法(規則 2024/1689)14 条 4 項 (b)**。https://artificialintelligenceact.eu/article/14/ (EUR-Lex の HTML は本文が取得できず、この転載で読んだ)。監督する者が「to remain aware of the possible tendency of automatically relying or over-relying on the output」「(automation bias)」であることを求める。指標・しきい値・測り方は定めない
- **NIST AI 600-1(生成 AI プロファイル)**。https://nvlpubs.nist.gov/nistpubs/ai/NIST.AI.600-1.pdf (PDF を取得して 2.7 節を読んだ)。「This phenomenon is an example of automation bias, or excessive deference to automated systems.」。Human-AI Configuration をリスクの 1 つに挙げるが、過信を測る指標は定めない(「automation bias」「over-rel」で全文を検索した範囲)
- **ISO/IEC/IEEE 15939:2017(測定プロセス)**。公開プレビュー(https://assets.vde-verlag.de/iec-normen/preview-pdf/info_isoiecieee15939%7Bed1.0%7Den.pdf)で、まえがき・適用範囲・目次を読んだ。「This document does not catalog measures, nor does it provide a recommended set of measures to apply on projects. It does identify a process that supports defining a suitable set of measures that addresses specific information needs.」「The users of this document are responsible for selecting a set of measures for the project」。附属書A(参考)は測定情報モデルで、目次に「A.2.3 Base measure」「A.2.4 Derived measure」「A.2.5 Indicator」がある。**第3節の定義の本文はプレビューに含まれず、読めなかった**

規格の側は、測定量を規格が固定せず、情報ニーズから測定量を定義する手続を定める形を取る(15939 の適用範囲)。AI の規制と指針は、自動化バイアスを名指すが数値化しない。「この比率が何倍になったら権限を下げる」という形の規定は、確認した規格には無かった。

## 3. 選択肢

決めることは 3 層に分かれる。(I) 量をどうするか、(II) 語をどうするか、(III) しきい値と窓をどうするか。(I) の案を 8 つ立てる。(II)(III) は 3.9・3.10 に分けた。推しは書いていない。

どの案でも、A1〜A5 の 5 箇所と EV-0090、派生物(A8・A9)の扱いが要る。採用済みの ADR-0054 の本文(決定4 の 106・108 行)は書き換えられないので、量や前提を変える案は新しい ADR で置き換える形になる。

### 3.1 案1: 挙動要約を伴わない承認の比率に定める(監査の委員の案)

- 定義: 分子 = 承認した者自身の挙動要約を伴わない承認、分母 = G-6 の承認。数える単位(承認か変更か)と時点(差し戻しの前か後か)を併せて決める
- 良くなること: 5.6 の形骸化の定義と防止手段に直結する。L1 でも値を持つので、L2 の前提として確かめられる。証跡から第三者が再計算できる。既存の検査関数(`hasBehaviorSummary`)を使える
- 壊れること・弱点
  - IMPL-0093 の現在の出力は変更の単位で、分母(承認の全数)を出さない(1.7 の (2))。承認の単位にするなら集約の改修が要る。変更の単位にするなら「適格な承認がすべて要約を欠く変更 ÷ 変更」になり、委員の文面と違う量になる
  - G-6 を適用する体制では、分子は差し戻されて 0 へ寄る(1.7 の (4))。差し戻しの前で数えるなら、PR の取り込み時点の記録を残す仕組みが要る
  - 形の検査は 8 文字の無意味な文字列で通る(1.7 の (3))。分子から外れる最短の経路が「8 文字書く」になる。5.7.4 が警告する「長く書けば通るという新しい形の形骸化」と同じ型である。AIDev の研究は、慣れが語彙の指標で検出できないと報告する(2.3)
  - `metrics.md` の「挙動要約の品質」(欠落数)と測る対象が重なる。同じ量を「傾向の確認」と「自動の引き下げ」の両方に使うことになる
  - この量の上昇が監督の劣化を示すという測定は無い。近い実証は McIntosh ほかの「議論なしの承認」(出荷後の欠陥と有意。2.3)で、定義は同じではない
- 変える必要があるもの: 5.4.6 の表 2 つ、5.5.4、第8章、附属書H、`metrics.md`(定義の行)、`aggregate-evidence.mjs`(分母と時点)、EV-0090(差し替え条件は実測 3 か月分を求めるので、定義だけでは外れない)、新しい ADR

### 3.2 案2: 人の確認なしに実行された操作の比率に定める(出所の原義)

- 定義: 分子 = 人の確認を経ずに実行されたエージェントの操作(または、確認を一切挟まないセッション)、分母 = 全操作(全セッション)
- 良くなること: 語の出所と一致する。5.4.1 の「監視者」(エージェントの動作を誰がどの時点で見ているか)を直接に測る。L2(統合点だけを人が確認する)での監督の様式の変化を拾える唯一の案である
- 壊れること・弱点
  - 原典が分子・分母を定義していない(2.1)。標準が新たに定義することになる
  - 原典は上昇を劣化と解釈していない。ベンダーは高い承認率を、確認を減らす根拠に使っている(2.2)。向きが 5.4.6 と逆である
  - 2026-10 時点で、確認を省く実行は製品の既定である(2.2)。比率は製品の版と設定で段になって動き、人の監督の変化を映さない
  - 計測は実行基盤のテレメトリに依る。Claude Code では導けるが(2.2)、製品ごとに取り方が違う。標準の「特定の製品を指定しない」と両立する取り方を別に決める必要がある。第三者が証跡から再計算しにくい(監査の委員の指摘)
  - A2・A5 の「判定の履歴を期間で集計する仕組み」と単位が合わない。この説明も改めることになる
- 変える必要があるもの: 5.4.6(必要なものの列)、附属書H(「前者は判定の履歴の集計であり」)、`phase5-implementation/agent-trace-control.md`(確認を省いた実行の集計の要求を足す)、テンプレートに集計の実装、新しい ADR

### 3.3 案3: 人の事前確認を経ない変更の比率に定める

- 定義: 分子 = 委任で先へ進めた変更(トレーラ `Delegated`)、または独立した人の確認を経ていない変更、分母 = 該当範囲の変更
- 良くなること: 既存の件数(保証の開示の項目1)から導ける。「判定の履歴の集計」と合う。単位が変更で、製品(Meta RADAR、Rewind、LinearB)の数え方と同じ
- 壊れること・弱点
  - L1・L2 では定義上 0 で、L2 の前提にならない(調査E)。種別を登録した月に必ず跳ね、登録の直後に発火する
  - 「独立した人の確認を経ていない変更」を分子にすると、未達(体制の制約)と委任(決定)を混ぜる。未達と省略の区別(ADR-0028)と緊張する
  - 委任の側の引き下げは 5.5.7 が既に持つ(「事後の抜き取りで逸脱を検知したら、該当範囲を協働へ引き下げる」)。二重になる
  - 語を「自動承認」のままにすると 5.5.4 の禁止と正面から衝突する。改名が前提になる
- 変える必要があるもの: 5 箇所の語、A2 の区分(L2 の前提から外す)、新しい ADR

### 3.4 案4: 量を標準が固定せず、組織に定めさせる(定義の要件だけを課す)

- 定義: 標準は「人の確認が省かれている度合いを示す比率を 1 つ以上定める」ことを求め、分子・分母・単位・算出元の記録・母数の下限・しきい値を組織が記録する。記録先は D-0 か `basis.detection`。同じ表の「変更の重複率または手戻り率が基準を超えた \| 組織が定めた値」と同じ形にそろえる
- 良くなること: 実行基盤の違い(2.2)を吸収できる。測定量を規格が固定しないという 15939 の形(2.6)と合う。A8(フェーズ3 の「定めた水準を超えた」)と形がそろう。監査人は、組織が書いた定義で再計算できる
- 壊れること・弱点
  - 組織間で値を比べられない。「前月比2倍」という標準の初期値は意味を失う(量が違えば倍率の意味も違う)
  - 「何を定義すれば足りるか」の下限を書かないと、現状の自己申告と変わらない。`basis.detection` が 1 語で通る挙動(1.7 の (5))は、欄を構造化しない限り残る
  - 規格の委員の指摘(「組織に委ねるなら、委ねたと書く必要があります」)には応える。監査の委員の指摘(同じ証跡から 2 人の監査人が逆の判定を出せる)には、組織内でしか応えない
  - 採用組織に定義の仕事を渡す。現場の委員の懸念(真面目な組織ほど上がれない)は、定義の手引きが無いと残る
- 変える必要があるもの: 5.4.6 の表(初期値の列)、5.5.4「登録の根拠の記録」、`config.mjs` の `CHANGE_TYPE_BASIS`(欄の構造)、fixture(`delegation-eligible.json`)、D-0 の様式、`src/data/template-fields.yaml`、新しい ADR

### 3.5 案5: 行を廃し、課さないと明記する

- 定義: 5.4.6 の表から行を外し、第2区分を差し戻し率・重複率・手戻り率の 3 つにする。「承認の比率の上昇を、引き下げの条件として課さない」と理由つきで書く
- 良くなること: 定義できない量を発火条件と前提から外す。5.4.6 自身の文(「**発火しない引き下げを、備えているものとして扱ってはなりません**」)と整合する。応諾率が単独では劣化を示さないという外部の報告(2.5)、標準自身の一発承認率への警告(1.6)と向きが合う。指標の総数の上限(EV-0012)に触れない
- 壊れること・弱点
  - 人が確認を省き始めることを拾う検知条件が、5.4.6 から無くなる。残る条件のうち近いのは「独立レビューの差し戻し率が0%のまま推移した \| 2か月継続」だけである。差し戻し率が 0% でない形骸化(たまに差し戻すが、大半は読まずに通す)は拾えない
  - L2 での監督の様式の変化(統合点の確認が省かれる)を測る条件が無いままになる
  - ADR-0054 決定4 が写した列挙を変えるので、新しい ADR が要る
- 変える必要があるもの: 5 箇所から語を除く、EV-0090 を外す(台帳の再生成)、A8・A9、新しい ADR

### 3.6 案6: 発火条件から外し、傾向の確認へ格下げする

- 定義: 量(案1〜3 のどれか、または複数)を `metrics.md` の警戒サインとして定義し、5.4.6 の自動の引き下げと、L2・登録の前提からは外す。一発承認率と同じ扱い(「**合否条件にしてはならない**。傾向の確認に留める」)にする
- 良くなること: 観測は続けられる。実証の無い量で権限を自動で動かすことを避ける。EV-0090 の差し替え条件(3 か月分の実測)を、発火条件に戻すかどうかの判断材料として使える
- 壊れること・弱点
  - 5.4.6 は月次の点検を退けている(「人間の点検を挟むと、引き下げは判定になります」)。傾向の確認は人の点検であり、5.4.6 が「成立しない」とした形になる。この行に限って非対称を手放すことを、明示して決める必要がある
  - 「眺めているだけの指標を残さない」(`metrics.md`)に当たるおそれがある。次の一手への接続を書く必要がある
  - 指標を 1 つ足すなら、総数の上限に掛かる
- 変える必要があるもの: 5.4.6 の表と区分、`metrics.md`、5 箇所の列挙、新しい ADR

### 3.7 案7: 正解つきの量へ置き換える(検出率の低下で発火させる)

- 定義: 承認の比率(手続の量)をやめ、「誤っていた事例を人が捕捉した割合」の低下を発火条件にする。算出元は 5.6.2 の欠陥注入(工程単位の検出率)と、5.7.6 の主指標
- 良くなること: 過信を測る研究が採る型である(2.5 の Buçinca ほか、2.2 の Anthropic の対照実験)。応諾率の交絡(対象の質が上がれば承認は増える)を避けられる。5.6.1 が述べる「**AIの生成品質が上がるほど、(中略)レビューはより形骸化しやすくなります**」に対し、品質の向上と監督の劣化を分けて測れる
- 壊れること・弱点
  - 標準は 2 つの量を意図して分けている。5.5.4:「登録の判定で確かめる計測は、5.4.6 の引き下げを発火させるための集計です。保証の開示の項目6 に載る検出能力の測定(5.6.2 の欠陥注入)とは、別の量です。項目6 が「未測定」であることは、それだけでは登録を妨げません。」。この案は ADR-0054 決定4(108 行)と正面から食い違う
  - 欠陥注入は件数の蓄積が要り(「対象者あたり約100件」)、小さい体制では測定が成立しない。L2 の前提に置くと、多くの体制が L1 に留まる
  - 附属書H の主張 C6(「検出能力は測定され、低下は権限の制限として作動する」)は 5.4.6 を根拠に挙げている(`assurance-case.md` 213 行)。この案は C6 の文面と合うが、現在の 5.4.6 の表に検出率の行は無い。食い違いは現状でもある
- 変える必要があるもの: 5.4.6 の表と区分、5.5.4 の該当の段落、附属書H、ADR-0054 決定4 を置き換える新しい ADR、項目6 が未測定の体制の扱い

### 3.8 案8: 決めない(EV-0090 のまま見直しの時期まで待つ)

- 定義: 量も語も変えない。EV-0090 の見直し(2027-04)まで現状を保つ。併せて「未定義のあいだ、この条件を計測できていることを L2 以上の適用と種別の登録の根拠に数えない」と書くかどうかを決める(現場・監査・擁護の 3 委員が文の案を出し、#300 では足さなかった)
- 良くなること: 実測(採用組織の集計)が出てから決められる。根拠の無い定義で発火条件を固定しない
- 壊れること・弱点
  - EV-0090 の差し替え条件は「定義」と「その定義で集計した3か月分の実測」である。**定義が無いと実測が始まらない**。待っても材料は増えない(監査の委員の争点 3:「それは送っても手に入りません」)
  - 「前提に数えない」と書かない場合、自己申告で L2 と登録の前提を満たせる状態が続く(1.7 の (5))
  - 「前提に数えない」と書く場合、第2区分の 4 つのうち 1 つが欠けた状態を「計測できる」と扱うことになる。A2・A3 の文面(4 つを列挙して「計測できない範囲へ適用しません」)をどう読むかを併せて書く必要がある
- 変える必要があるもの: (書く場合)5.4.6 のマークの本文か表の行。実装マーク(`state=undelivered`)を足すかどうか

## 4. 会議体への問い

1. **測りたいのは何か**。5.4.6 の「監督の劣化」は、(a) エージェントの動作を人が見なくなること(5.4.1 の監視者。案2)、(b) 変更が人の確認なしに進むこと(案3)、(c) 人の承認から中身が抜けること(5.6 の形骸化。案1)、のどれを指すのか。L2 の定義は「人間が統合点を確認する」であり、L2 で起きる劣化は (a) に近い。(c) は L1 でも起きる。どれを L2 の前提に置くのが筋か。
2. **手続の量で権限を自動で動かしてよいか**。応諾率と承認の形は、対象の質・提示の設計・書き方で動く(2.5、1.7 の (3))。標準は一発承認率を「合否条件にしてはならない」と定め、理由を「この指標を上げる最短の経路は指摘を控えること」とする。同じ理由は、承認の比率を自動の引き下げの条件に使うことにも当たるのか。当たるなら、案5〜7 のどれで受けるか。当たらないなら、何が違うのか。
3. **5.4.6 の検知条件と、項目6 の検出能力を、別の量のままにするか**。ADR-0054 決定4 は意図して分けた。過信の研究は正解つきの量で測る(2.5)。附属書H の主張 C6 は「検出能力は測定され、低下は権限の制限として作動する」の根拠に 5.4.6 を挙げる。分けたままにする理由は何か。分けるなら、5.4.6 の側に残す量は何を測るのか。
4. **未定義のあいだの前提の扱いを、今回書くか**。#300 では「前提に数えない」の文を足さなかった。定義を置く案(1〜4)でも、EV-0090 は実測 3 か月分が出るまで残る。そのあいだ、L2 以上の適用と種別の登録は、この条件を計測できていることを前提に数えるのか。数えないなら、`basis.detection` の記入は何を書けば足りるのか(fixture の記入例は欠陥の検知手段を書いている。1.7 の (6))。
5. **実装が無い状態を、条項の側でどう表示するか**。5.4.6 の 4 つの比率はどれも計算されておらず、自動の引き下げの実装も、実装マークも無い(1.7 の (1))。量を定義しても、算出して発火させるものが無ければ「発火しない引き下げ」のままである。定義と同時に実装マーク(`state=undelivered`)を付けるのか。集約(出荷・期間ごとに人が起動)を算出元にする場合、5.4.6 が退けた「人間の点検を挟む」形と何が違うのか。
6. **語を改めるなら、どちらを動かすか**。意味 A(量)を改名するか、意味 B(期限超過の禁止。5 箇所とテンプレート)を改名するか、量そのものを廃するか。改名する場合、旧称との対応を本文に残すか。
