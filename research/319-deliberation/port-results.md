### 2.3 時計(R-3)

- `lib/clock.mjs` を `NODE_OPTIONS=--import` で読み込ませ、引数なしの `new Date()`・`Date()`・`Date.now()` を止める。子プロセスと、子の子まで止まることを、`run.mjs` が走らせる前に確かめる。git の時刻は `GIT_AUTHOR_DATE`・`GIT_COMMITTER_DATE` で同じ時刻にそろえ、これも走らせる前に確かめる
- スクリプトごとに時刻を宣言した(`// @regress {"now": ...}`)。`TZ=UTC` に固定した

| スクリプト | 宣言した時刻 | 根拠 |
| --- | --- | --- |
| v3・v3b・scenarios・new・replay・tz・acquire・unit・matrix-sweep | 2026-10-01T12:00:00Z | #284・#285 の反映のコミット(2026-10-01)。replay は裁定どおり 2026-10-01 で入力をそのまま使える |
| stages・s5-init-pr・verify-n | 2026-10-02T12:00:00Z | #286 の反映のコミット(2026-10-02) |
| t288・t288b・trial | 2026-10-08T12:00:00Z | #288 の反映のコミット(2026-10-08) |
| clock(新設) | 2026-10-01T23:59:00Z | 日付の境の場面のため |

- 時刻を 12:00 にした理由: 最初に 03:00 で流すと、trial の「合否の基準の記入日時 `${TODAY} 09:00` がコミットの時刻より後」で 8 場面が落ちた。trial・lib288 は記入日時・判定日時を 09:00・10:00 と直書きしており、実行の時刻がそれより後であることを前提にしている
- **判断を要した点(時計の刻み)**: 全部のコミットを 1 つの時刻に止めると、trial の 6 場面が落ちた(封じた注入の記録の後に見つける者の記録をコミットした、という順序を、テンプレートがコミットの時刻で確かめるため)。そこで時計を「宣言した時刻から始まり、子プロセスを起動するたびに 1 秒進む論理の時計」にした。試験の補助が刻みを進め、子プロセス・git・試験のプロセス自身に同じ時刻を渡す。実時間に依らないので、誰がいつ流しても同じ時刻の列になる(p302 を 2 回流し、全場面の合否が一致した)。裁定の「時計を止める」を、決定的な刻みとして実装したことになる。これで足りるかは第2段の突合で確かめてほしい
- 止まらない時計(引数なしの `Intl.DateTimeFormat().format()`・`formatToParts()`)をテンプレートのスクリプトが使っていないことを、`run.mjs` が走らせる前に確かめる。いまのテンプレートでは 0 件。検出の正規表現は使い捨ての場面で確かめた(変数に入れてから `format()` を呼ぶ形は拾えない)
- テンプレートには時刻を差し替える入口を足していない
- 時刻を明示した場面(新設 `suite/clock.mjs`、9 場面): 時計が子プロセスと git に届くこと、日付の境の前は翌日の発効日を未来として拒否すること、境の後は書かない発効日が翌日になり、前日の発効日を「最後の変化点の記録の日付より前」として拒否すること(調査で sweep が 68 件落ちた事象の形)、`next_review` の前日は「過ぎています」と出さず、過ぎた後は D-0 の検査が落ちること。confirmedAt は v3 の t7-4-future(確認日が発効日より後で拒否)と t7-4-yamada(同じ日で反映)が宣言した時刻のもとで確かめる。clock は新設なので、いまのテンプレートの事前点検(#315)に合わせて、`@OWNER` を置き換え、回答の JSON を複製の外に置いた(テンプレートの `test-init-g5.mjs` と同じ形)。p302・pre311・いまのどれでも 9 場面とも通る
- 元の時限(2026-12-01 の confirmedAt、2027-04-01 の next_review)は、時刻を宣言したため消えた。`stages.mjs` の `HH:60`(毎時 59 分)は、時刻が 12:00 から始まり刻みが秒単位のため起きない(判定日時は 12:01 で書かれる)。コードは直していない

### 2.4 移植で残る限界

- Windows: gh の代役は Node のスクリプトで、Windows では `execFileSync('gh')` から呼べない(`.exe` だけを探す)。`run.mjs` は走らせる前の確認で止まり、その旨を出す。黙って本物の gh を呼ぶことは無い
- 時計: `performance.now()`・`process.hrtime` は止めない。Node 以外のプロセス(git を除く)の時刻は止まらない
- 代役の確認: 代役が呼ばれたことは確かめるが、呼ばれた引数までは確かめていない
- 実行時間: このコンテナ(4 CPU)で、並列 8 で p302 が 4 分 1 秒、事前点検に適応したいまが 5 分 6 秒。sweep の 4 分割がそれぞれ 235〜300 秒で律速する

## 6. ADR-0060 の却下は、fixture のほかの理由でも成り立つか(R-4)

ADR-0060 の採らなかった案の表(125 行)の行「(決定2)外部の確認者を、担い手だけに限る」は、理由を 2 つ挙げる。

1. 「全変更を外部が確認する体制から、承認の強制と、確認漏れを欠落にする検査が消える」
2. 「準拠テンプレートの README と回帰の fixture が席の責任者の形を固定しており、覆す材料が無い」

確かめたこと:

- 理由 1 は、fixture によらず標準の規定から導ける。標準の第3章(`roles-responsibilities.md` 406〜415 行、ADR-0060 決定2 の表)は、(イ)外部の確認者を独立レビュアの席の責任者に置く体制でだけ、G-6 を適用し、確認を経ていない変更を記録の欠落にすると定める。(ア)名簿に載せるだけの体制では G-6 は未達のままで、確認した変更だけを数える。外部の確認者を担い手に限ると、(イ)の形が無くなり、外部の確認者しか独立の確認者を置けない 1〜2 名の体制では、G-6 の適用(承認の強制と、欠落にする検査)へ至る経路が無くなる
- 理由 1 を支える別の決定: ADR-0054 決定1 は担い手を「席の作業を実際に行う実行主体」とし、責任者と分ける。ADR-0054 決定8 の G-6 の 4 条件の 1(承認した者が D-0 体制図に記載した人へ対応づく。外部の確認者を含む)と 3(G-6 が未達の体制では、承認した人が外部の確認者である)は、外部の確認者を人の名簿の人として扱う。担い手に限る案は、決定8 の条件の主語とも合わない
- テンプレートの挙動(移した試験で確かめた): scenarios「外部の確認者を置く」(外部の確認者を独立レビュアの席の責任者に置く → 未達の解消、`gates.g6.state === 'required'`、契約検査が通る)と「外部の確認者が名簿から外れ、席を本人が引き取る」(→ 未達の発生: G-6)は、p302・pre311・いま(適応)のどれでも通る。v3b の b3 と new の 14-7 は、外部の確認者を手で書いた構成を契約検査が止めることを確かめ、これもどれでも通る
- テンプレートの README には「独立レビュアの席の責任者」の記載が残る(396・430 行の付近)
- 理由 2 の fixture は、ADR-0060 の採用(2026-10-13)の時点では構成管理の外(`tmp/`)にあった。移した後は `scripts/regress/suite/scenarios.mjs` などとして構成管理の下にある。ただし裁定 R-4 のとおり fixture は決定の記録ではないので、理由 2 は決定の根拠としては弱い
- 結論(事実として): ADR-0060 の当該の却下は、理由 1(標準の第3章 3.5 の(ア)(イ)の効果の規定と、ADR-0054 決定1・8)で成り立つ。fixture に依る理由 2 を除いても、却下は覆らない
