## R-1 何を、どこへ、どの形で移すか

### 結論

- **場面の単位で選ぶ**。移すのは、固定する決定を名指せて、期待値を持つ場面だけとする。**既存の試験の形へ書き直し**、スイートをそのまま入れない
- **置き場は親(process-compass)**。いまのテンプレートと、標準から作り直した知識ベースに対して流す。**場面と決定の対応表を持ち、機械で検査する**(各場面は ADR 番号、あれば決定 ID か K 番号を 1 つ以上持つ)
- **r3 は廃する**(廃した理由と、確かめられなくなったことを記録する)。**元のスイートは、走らせない証拠として履歴へ入れる**。利用者の端末の原本を消すかは、利用者が決める

### 理由

- ADR-0060 は fixture を却下の根拠に使った(Q4)。根拠に使われた物は、後から辿れなければならない。いまは履歴の外にあり、監査で ADR-0060 の理由を検めようにも、当時の fixture を特定できない。外部 A5・A6(構成品目に試験スクリプト・試験データを含める。文書化した情報を消失から保護する)と合う
- 「場面の数」を検証の量として数えると、期待値の無い行(Q8)、文言だけを固定する行(v3 の「不可逆4操作」。内部 2.4)、入力が無く走らない行(verify-n N7)が混ざる。決定を固定していない行を数えると、固定の範囲を過大に主張することになる
- 書き直しが要る理由は、そのままでは安全と移植性が成り立たないからである。`fresh.sh` は外側のリポジトリへコミットしうる(内部 5.1)。終了コードが伝わらない(Q7)。Windows の絶対パスを持つ(内部 5.2)。毎時 59 分に `HH:60` を書く(内部 4.1)
- 親に置く理由: スイートは知識ベースの作り直しを要し、テンプレート単独の CI では流せない(内部 8)。固定する決定は標準の決定であり、正本も親にある
- 対応表を持つ理由: 外部 F3 は、検査の規則が ADR と結ばれていないことを浸食の原因に挙げる。#319 の 16 件も、場面が固定する決定が分かっていれば、時計か回帰かの切り分けがもっと早く済んだ(内部 3)

### 文の案(ADR へ入れる決定の文)

- 決定を固定する試験の場面は、固定する決定の識別子(ADR 番号。あれば決定 ID)を 1 つ以上持つ
- 検査は、場面が指す決定の実在を確かめる。決定を指さない場面は、決定を固定する試験に数えない
- 期待値を持たない場面は、決定を固定する試験に数えない
- 文言の有無だけを確かめる場面は移さない。文言は、廃した言い回しの登録簿と実装マークが扱う
- 履歴の外にあった元のスイートは、走らせない記録として `research/319-.../legacy-suite/` へ置く。作業用の複製(`w/`)は置かない。置いた内容の一覧と要約値を記録に残す

- ADR-0066 の「fixture は決定の記録ではない」とは整合する。本案でも試験は決定の記録ではなく、決定に実装が従っていることの証拠である

## R-2 いま落ちる場面の扱い

### 結論

- **移す前に、すべての失敗場面を分類する**。原因の分からない失敗に「落ちることを期待する」印を付けて入れない。分類ごとの扱い:

| --- | --- | --- |

| 決定が変わった | v3 1(ADR-0078)、new 1・matrix 3 行(ADR-0088)、stages 20(#291 突合・ADR-0079)、t288 6・s5-init-pr 1(ADR-0079) | 変えた決定を引いて期待値を改める。R-4 の手続による |
| 入力が古い(決定 A-4) | replay 5(`s4-acc3.json`) | ADR-0066 の帰結として入力を直す。ADR-0066 が主張した直しの未了分として記録する |
| 判断が要る | scenarios 3(同じ変化点での氏名の確認と任命) | 新しい Issue へ回し、人が決める。決まるまでは「落ちることを期待する」印で入れる |

- **分類の確定は、起案した文脈と別の文脈が行う**。「判断が要る」分類の結論は人が書く。印は自前の仕組みで持ち、Node 22 の `expectFailure` は使わない(Q1)

### 理由

- 原因の分からない失敗に印を付けると、本物の後退を印が隠す。外部 C5(Google)は、隔離が本物の不具合を隠しうると明記する。今回も、時計の 15 件が A-4 の入力の 5 件を隠していた(内部 3.2 追記)。**印は、原因が特定済みで、決定を待っている場面に限る**
- scenarios の 3 件は、記録からは回帰か決定の帰結かを決められない(内部 2.4)。#296 の付記は同じ変化点での確認と任命の可否を書いていない。試験の作者が期待値を選ぶと、試験が決定を作ることになる。それは ADR-0066 の原則(試験は決定の記録ではない)に反する
- 印を付けて走らせ続ける理由: どちらの向きに決まっても、挙動の変化が表に出る。予期せず通ったら失敗にすれば、誰かが黙って挙動を変えたことを検出できる(外部 D1・D2)
- 印の要件: (a) Issue を名指す。(b) 期待する失敗の文を照合し、別の理由で落ちたら通常の失敗とする(外部 D1 の `raises`、D3 の `match`)。(c) 予期せず通ったら失敗とする。(d) 見直しの年月を持つ
- Node 22 で `expectFailure` を書くと、何も言わずに逆の結果を出す(Q1)。CI の Node を上げても、手元の古い版で黙って逆転する危険は残る。試験の枠組みの側で、印を自前で解釈する
- 起案者と別の文脈が分類を確定する理由: #302〜#310 では担当が期待値の改めと「固定していた決定ではない」という判断を同じ文脈で行った(`implementation-A.md` 3 節)。内容は妥当だったが、replay の入力の漏れは誰も見つけなかった(Q5)。第3章 3.5.3(起案したセッションは判定の草案を作らない)と同じ構造である

### 文の案(ADR へ入れる決定の文)

- 落ちる場面は、移す前に分類する。分類は、期待値を改めた文脈と別の文脈が確定する

- 原因を特定していない失敗には、印を付けない
- 印の付いた場面の一覧と件数は、検査の出力に毎回出す

### 既存の ADR・条項との矛盾

- 根拠: 内部(2.4・3)、外部(C5・D1〜D3)、自分で確かめた Q1・Q5

## R-3 時計

### 結論

- **試験の側で直す。テンプレートに時刻を差し替える入口を足さない**
- 直し方: (a) 日付を実行日からの相対で書く。(b) 「今日」を読み込み時に 1 回だけ計算せず、変化点を書く直前に作業の場所の最後の記録の日付から求める。(c) 時限の値(`next_review: 2027-03-31`、`confirmedAt: '2026-12-01'`、`reviewBy: '2026-12-31'`)を相対へ改める。(d) 開始と終了で日付が変わった実行は「日付の境をまたいだ」と出して失敗にし、自動で再実行しない
- `mock.timers` を時計の解決策として採らない(Q2)

### 理由

- 日付の判定は子プロセスの中で行われる。試験の側の凍結は、判定する側の時計に届かない(Q2)。外部 C1・C2 の定石(時計を包んで差し替える)は、同じプロセスの中で判定する試験を前提にしている
- 製品に入口を足すと、K65(過去の発効日を受け付けない)と `check-d0.mjs` の期限切れの検出を、環境変数ひとつで外せるようになる。その環境変数は、エージェントが同じ環境で設定できる。これは統制の弱化に当たり、本件(試験の整備)の範囲で決めてよい変更ではない。CLAUDE.md の `state:needs-platform` の領分である。加えて、試験が通るのは差し替えの経路であり、本番の経路ではなくなる
- 日付の境をまたいだ実行を自動で再実行しない理由: 再実行は外部 C5 の flaky 指定と同じく、本物の失敗を見逃させる方向に働く。境をまたいだことを明示して落とせば、人が事情を見て流し直せる。誤って通すより、明示して落とすほうが信頼できる
- (b) で記録の日付を使う理由: 内部 4.1 の sweep の 68 件は、親の `TODAY` と子が書いた記録の日付のずれで起きた。正しい「今日」を知っているのは、子が書いた記録である

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| テンプレートに時刻の入口(環境変数・引数)を足す | 統制を外す入口が本番にも残る。試験が本番の経路を通らなくなる |
| 入口を足し、本番では拒否する | 「本番か」を判定する条件も、同じ環境で偽れる。判定の条件そのものが新しい攻撃面になる |
| `faketime` 等で外から時計を止める | 環境に無い(内部 4.1)。Windows・macOS での再現性が無い |
| 日付の直書きを残し、時限の前に手で直す | 2026-12-01・2027-04-01 に必ず落ちる。誰かが期限の前に気づく仕組みが無い |

### 文の案(ADR へ入れる決定の文)

- 決定を固定する試験は、実行日に依らず同じ結果を返す。日付は実行日からの相対で書く
- 試験が渡す日付は、作業の場所の最後の記録の日付から求める
- 開始と終了で日付が変わった実行は失敗とし、その旨を出す。自動で再実行しない
- 準拠テンプレートに、時刻を差し替える入口を設けない。設けると、過去の発効日の拒否と期限切れの検出を、実行時の設定で外せるためである

### 既存の ADR・条項との矛盾

- 矛盾は無い。テンプレートの強制層を変えない
- 根拠: 内部(3・4)、外部(C1・C2・C5)、自分で確かめた Q2

## R-4 期待値を変えるときの手続

### 結論

- 決定を固定する場面の期待値の変更には、(1) **決定の引用**(変更より前に存在する決定を対応表の欄へ書く)、(2) **記録**(反映の記録に「変わった場面・固定していた決定・扱い」の表。`implementation-A.md` 3 節の形)、(3) **別の文脈の確認**(表と差分の突き合わせ)を求め、(4) **出力を期待値へ写すモード(`-u` 相当)を作らない**
- 規則と期待値を同じ変更で改めることは認める(決定の変更は両方の同時の改めを要する)。機械が合否に使うのは形(場面が決定を指す・その決定が実在する)だけで、期待値が変わったこと自体は一覧に出す

### 理由

- 禁止事項3 との境: 禁止事項3 が禁じるのは「失敗を消すために」テストを変えることである。決定が先に変わり、その決定に従って期待値を改めることは禁じていない。両者を区別するのは**決定が先に存在すること**であり、これは記録の日付と対応表の欄で確かめられる。決定が無いまま期待値を改めれば、それは禁止事項3 に当たる
- 外部 B5: 期待値の更新は「落ちたら上書き」に縮退しやすい。自動の作り直しのモードを持たないことと、別の文脈の確認を課すことが、その歯止めになる
- 形だけを合否に使う理由: 第5章 5.8.5 は、検証の弱化の検出を G-5 の合否に使うことを禁じる。正当な変更と区別できないためである。本案の形の検査は、決定の引用の有無で区別するので、この理由に当たらない。ただし引用の真偽(その決定が本当に期待値の変更を要するか)は機械では確かめられない。そこは別の文脈の確認が担う
- #302〜#310 の位置づけ: 内容は正当だった。決定 A-6 が先にあり、表も残した。手続には 3 つの欠陥があった。(i) 構成管理の外の複製で直した。(ii) 元のスイートを直さず、ADR-0066 の帰結の文が主張する状態を誰も持たなかった(Q5)。(iii) replay を流さず、入力の直しが漏れた。いずれも「直した」という記録と実物が離れたことが原因で、期待値の改め方の誤りではない

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| 期待値の変更をすべて人の承認とする | この標準の作り手はいまソロ期で、PR を経ない。人の確認を形式だけ課すと、確認済みの印へ縮退する(第5章 5.6)。別の文脈の突合と記録の表のほうが、実際に検査が行われる |
| 規則と期待値を別の変更に分ける | 決定の変更では、どちらか一方だけの版が必ず落ちる。分けると、間の版で落ちることを許す運用か、印の乱用を生む |
| 期待値の変更を検出して CI を落とす | 5.8.5 の理由(正当な変更と区別できない)にそのまま当たる。除外が常態化する |
| 出力の写しで期待値を作り直すモードを持つ | 外部 B2・B5。盲目的な上書きが最大の弱点 |

### 文の案(ADR へ入れる決定の文)

- 決定を固定する場面の期待値は、変更より前に存在する決定を引いて改める。決定を引けない変更は、禁止事項3 に当たるものとして扱う
- 期待値を改めた反映の記録には、変わった場面・固定していた決定・扱いの表を置く
- 表と差分の突き合わせは、期待値を改めた文脈と別の文脈が行う
- 検査は、場面が決定を指すことと、その決定の実在を確かめる。期待値が変わったことは一覧に出し、合否に使わない
- 出力を期待値へ写す自動の手段は設けない

## R-5 「採らない」と決めた文と、廃した言い回し

### 結論

- **反映の作業に探索の手順を足し、結果を記録に残すことを要件にする**。記録には、探した語・範囲・件数・各件の扱いを書く。結果の残らない手順は、監査で行われたかを確かめられない
- **却下した案のうち挙動を持つものは、否定の場面として試験へ入れる**。対応表の決定の欄に、却下を示す印を付ける(例: 「条件付き通過という値は無い」→ その値で判定を書くと拒否される場面)。語の検索より強い固定になる
- 登録簿: **`by` の実在を検査に足す**(Q3。指す ADR のファイルがあること、Issue の書式であること)。**句ごとの自己試験(当たるべき文例・当たってはならない文例)を任意の欄として足し**、部分一致の誤検出を句ごとに固定する(外部 E1 の prh の `specs`)
- 検査の範囲: **移した回帰の試験を含める**(拒否を確かめる文例は行ごとの `retired-ok: 理由` で除く)。**zenn は #320 で決め、本件では決めない**(含めるなら、未初期化を `template/` と同じく失敗に数える)。**research は含めない**

### 理由

- #302〜#310 で登録簿は「当時 20 句」で、採らなかった文の一部しか担っていなかった。語の登録は、決定のたびに担当が句を選んだ分だけである(内部 7)。漏れを減らすのは、手順の結果を記録させることと、挙動を試験で固定することである
- `by` の実在を確かめない登録簿は、記録から辿れることを保証しない。66 句の `by` が ADR を正しく指しているかを、いまは誰も確かめていない
- research を含めない理由: 調査と審議の記録は、廃した語を当時の文脈で正しく含む。含めると `retired-ok` が散らばり、外部 E3 の指摘(抑止が文書中に散ると、何が許されているかが分からない)に当たる

### 他の案を落とす理由

| zenn を本件で含めると決める | #320 と範囲が重なり、同じことを 2 か所で決めることになる |

## R-6 CI と実行時間・知識ベースへの依存

### 結論

- 決定を固定する試験(sweep を除く)は、**`npm run check` へ入れる**。通らなければ公開と `dist/standard` への配布が走らない。全体の終了コードへ失敗を伝え(Q7)、`ci.yml` に `timeout-minutes` を明示する
- **sweep(768 組)は毎回は流さない**。規則データ(`src/data/tailoring/`)を変えたとき・標準の版を切る前・週次に流し、結果を記録して失敗を Issue にする
- 知識ベースは親が一時の場所へ作り直し、サブモジュールの作業ツリーに対して流す。作業の場所は親の作業ツリーの外(`os.tmpdir()`)に置き、最上位を確かめる。テンプレートの `gate-g5.yml` へは入れない

### 理由

- 決定を固定する試験が公開を止めないなら、決定と違う標準が公開されうる。判断軸は信頼性であり、5 分程度の延長(内部 8: runall2 約 3 分 25 秒 + ほか約 2.5 分)は採否の理由にならない
- sweep を毎回流さない理由は、時間ではない。sweep は回答の総当たりで、規則データが変わらない限り結果が変わらない。流す条件を「規則データの変更」に結べば、固定の強さは毎回流すのと同じになる。ただし、規則データの変更を検知して流す結線が無ければ、この主張は成り立たない。結線を `check-ci-wiring.mjs` の検査の対象に含める
- 作業の場所を親の作業ツリーの外に置くのは、内部 5.1 の事故(外側のリポジトリへのコミット)を構造で防ぐためである
- 残る穴: テンプレートのリポジトリへ直接入った変更は、親がサブモジュールを進めるまで、この試験で確かめられない。テンプレートの単位の試験(`gate-g5.yml`)が一部を担う。この穴は記録に書き、塞いだと主張しない

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| 別のジョブにして、公開を止めない | 落ちても公開される。決定と違う標準が出る |
| sweep も毎回流す | 固定の強さは、条件つきで流す案と同じ。日付の境をまたぐ危険が、実行時間に比例して増える(内部 4.1) |
| テンプレートの CI に入れる | 知識ベースを作れない(内部 8) |

### 文の案(ADR へ入れる決定の文)

- 決定を固定する試験は、公開と配布の前提の検査に含める
- 総当たりの試験は、規則データを変えたとき、標準の版を切る前、週次に流す。結果を記録し、失敗を Issue にする
- 試験の作業の場所は、リポジトリの作業ツリーの外に作る

## R-7 標準の側の規定

### 結論

- **規定する**。次の 3 点を第5章 5.8.5 の後の段落の補足として置く。新しい禁止事項は足さない
  1. **検証の根拠に使う試験は、構成管理の下に置く**。作業ディレクトリ・個人の端末にだけある試験の結果を、ゲートの判定の根拠に数えない
  2. **期待値の改め**は、それが由来する受入基準または決定を引く。引けない改めは禁止事項3 に当たる
  3. **「落ちることを期待する」印の付与**は、5.8.5 の「`skip` 相当の付与」に当たる。印には、Issue・期待する失敗・見直しの時期を持たせる
- **課さないと決めたことを明記する**: 印の件数の上限、特定の試験の枠組み・スナップショットの形式、時計の差し替えの方式、期待値の変更を G-5 の合否に使うこと

### 理由

- 附属書H H.1 は、AI が書いたテストを検証に数える条件を「期待値が人の承認した受入基準に由来すること」としている(assurance-case.md 308 行)。期待値が後から由来なく改められれば、この条件は黙って崩れる。条項 2 は、H.1 の条件を期待値の改めの時点まで延ばすものである
- 条項 1: AI の作業では、作業用の試験が一時の場所に大量に作られる。#319 はその実例である。外部 A5・A6 と合う。現行の標準で構成管理に触れるのは「指示の保存」(5.8 の表、safety-verification.md 94 行)だけで、試験資産には触れていない
- 条項 3: 印の付与は、検証を弱める変更である。現行の 5.8.5 の列挙(「`skip` 相当の付与」)に当たるかどうかが読み手で割れる。明記すれば割れない。降ろし先(IMPL-0204)は `state=undelivered` のまま表示し続ける
- 上限を課さない理由: 外部 C4 の上限(8 件・1 週間)は例示で、実証が無い。見直しの時期を印に持たせることで、放置の検出を担う

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| 規定しない(本標準の作り手の内部の運用に留める) | 同じ欠陥(試験が一時の場所にあり、期待値が由来なく改められる)は採用者にも起きる。H.1 の条件が期待値の改めで崩れる穴が残る |
| 新しい禁止事項を足す | 内容は禁止事項3 と 5.8.5 の段落の解釈の明確化であり、新しい禁止ではない。番号を増やすと、テンプレートの CLAUDE.md の表と実装マークが増え、同じ事項が 2 か所になる(第1章 1.7) |
| 印の件数・期間の上限を課す | 根拠となる値が無い |

### 文の案(第5章 5.8.5 の後の段落へ足す本文。ですます調)

> ゲートの判定の根拠に使う試験(スクリプト・入力・期待値)は、構成管理の下に置きます。作業ディレクトリや個人の端末にだけある試験の結果は、判定の根拠に数えません。
>
> 試験の期待値を改めるときは、その期待値が由来する受入基準または決定を引きます。由来を引けない期待値の改めは、5.8.5 の禁止事項3 に当たります。
>
> 「落ちることを期待する」印をテストに付けることは、検証を弱める変更(`skip` 相当の付与)に当たります。印には、対応する Issue、期待する失敗の内容、見直しの時期を書きます。期待と違う内容で落ちたテストと、予期せず通ったテストは、失敗として扱います。
>
> 本標準は、印の件数の上限、試験の枠組み、時計の差し替えの方式を定めません。

- 条項 2・3 の「見直しの時期」の運用には、根拠水準マークを付ける。`:::caution[暫定 EV-NNNN / 見直し 2027-04]`。印の期限による放置の検出が有効であるという実証は無い(外部 D の小括: 期限を機械で強制する公式の仕組みは見つからなかった)。実装マークは、条項 1 は降ろし先を確かめてから付け、条項 3 は IMPL-0204 と同じ `pr-checks` へ `state=undelivered` で付ける
