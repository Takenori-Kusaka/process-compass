もう一つ、外部調査に無い定義を足します。回帰試験の古典的な定義(IEEE Std 610.12-1990、ISO/IEC/IEEE 24765 が継承)は「変更が意図しない影響を生んでいないこと、**系が規定された要求になお適合していること**を確かめる選択的な再試験」です〔記憶〕。要点は後半です。規格の言う回帰は**要求に結ばれた**再試験であり、外部 B1 の特性記述試験(書いた時点の振る舞いを固定し、正しさを推論しない)とは別物です。この区別が R-1・R-2・R-4 の軸になります。

結論として、規格群が一致して言えるのは「試験のスクリプト・データ・ツールは構成品目である」(SWE-081 は一次、61508-3・CMMI・DO-178C は趣旨の一致)までです。「期待値の更新の手続」「既知の失敗の印」「時計の差し替え」を定める規格の条文は、外部調査にも本委員の知識にもありません。後者は業界の実務(Jest・Node・pytest・Fowler)であり、規格の要求として書いてはなりません。

## R-1 何を、どこへ、どの形で移すか

**結論**: 決定を名指せる場面だけを、決定を固定する回帰試験として本リポジトリ(親)の `scripts/` の下へ、既存の試験の形(Node のスクリプト、`npm run check` から実行)へ書き直して移す。各場面は固定する決定を **ADR の番号と決定の番号**で名指し、対応する IMPL マークがあれば `IMPL-NNNN:ng`/`:ok` の目印を付ける。新しい対応表(第3の正本)は作らない。決定を名指せない場面は移さず、その旨と理由を記録する。再現できないもの(r3・verify-n の N7・ta)は廃し、何を確かめていたかを記録する。原本は版管理の下へ凍結した記録として取り込み、利用者の端末の `tmp/` の扱いは利用者が決める。

**理由**:

- 構成品目であることが規格群の一致点である(0 節)。版管理の外の試験の結果は、判定の根拠として到達できない(既存の決定 7)。移さない選択肢は無い
- 規格の言う回帰は要求に結ばれた再試験である(0 節の定義)。スクリプトのコメントにある K 番号は `research/` の下書きの番号で、決定の正本ではない(K の多くは ADR-0054〜0056 へ畳まれた〔内〕)。名指す先を ADR にすれば、`npm run lint:refs` の型で実在を確かめられる
- `check=machine` の目印の仕組み(既存の決定 6)は、規定と試験を結ぶ既存の正本である。別の対応表を足すと、ADR-0077 決定1 が退けた「第3の正本」と同じ形になる。移植は、`manual` のまま残っている IMPL マークを `machine` へ上げる材料にもなる
- 決定を名指せない場面(matrix の出力行、tok の計測)は特性記述であり、変化を検出しても決定の破れを意味しない〔外 B1〕。matrix は期待値を持たず #318 の変化を合否に出さなかった〔内 2.4〕。決定を固定すると称して移せば、確かめていないものを確かめたと読ませる
- テンプレートの下へ置かない理由: (1) 標準から作り直した知識ベースを要し、テンプレート単独では流せない〔内 8〕、(2) `template/` は採用者へ配られる。本プロジェクトの保守の試験を採用者の必須の集約へ入れる根拠が無い
- 再現できない試験は、構成品目から再現できない以上、検証の証拠にならない(IEC 61508-3 6.2.3 の「正確な維持」の趣旨)。黙って消すと「書かれていない」と「廃すると決めた」が区別できない(コアポリシー)。quarto-cli の例〔外 D8〕も、止めるときに理由と復帰の作業を残している

**他の案を落とす理由**:

- 全場面をそのまま持ち込む: Windows の絶対パス・GNU 依存・`git init` の失敗の黙殺(外側のリポジトリへコミットしうる)〔内 5.1〜5.3〕を構成品目に入れることになる。試験環境が試験対象と構成を汚しうる形は、FAA AC 00-69 3.1 が影響分析の対象に検証環境を含める趣旨と相容れない
- 場面と決定の対応表を新設する: 上記(第3の正本)
- テンプレートへ置く: 上記

**文の案**(本リポジトリの運営の規定。`community/` の頁へ):

- 決定を固定する回帰試験は、本リポジトリの版管理の下に置き、`npm run check` から実行するものに限る
- 各場面に、固定する決定を ADR の番号と決定の番号で書く。研究メモの番号(K 番号など)だけを書かない
- 決定を名指せない場面を、決定を固定する試験として数えない
- 試験の作業用の複製は、リポジトリの作業ツリーの外(`os.tmpdir()` の下)に作り、作った複製が最上位であることを確かめてから書き込む
- 再現できない試験は廃し、確かめていた決定と、廃した理由を記録に残す

**矛盾**: ADR-0066 110 行の記述と事実の食い違い(1 節の1)を、新 ADR に記録する。それ以外の矛盾は無い。

**原本の扱い**: `tmp/legacy/` の原本(スクリプトと入力。`w/` の生成物を除く)を `research/319-deliberation/` の下へ、改変せずに取り込み、ハッシュの一覧を添える。実行の対象にはしない(記録)。`research/` は登録簿の検査の範囲外であり、過去の記録を書き換えさせない点でも適切である〔確: `retiredScan.roots`〕。利用者の端末の原本を消すかは取り消せない操作であり、利用者が決める。

## R-2 いま落ちる場面の扱い

**結論**: 分類が決まっている失敗(期待値が古い・決定が変わった)は、移す前に、変わった決定の ADR を名指して直す。分類が決まらない scenarios の 3 件は、**新しい Issue を立てて人の判断へ回し**、それまでは元の期待(「反映」)を表した場面に「落ちることを期待する」印を付け、Issue の番号を結んで走らせ続ける。予期せず通れば失敗にする。replay の 5 件は入力 `s4-acc3.json` を ADR-0066 に合わせて直す。分類の確定は人(保守者)が行い、AI は根拠つきの分類の案を出すまでとする。

**理由**:

- ADR-0073 決定2 の3条件の3つ目(既存の違反の解消)から、落ちる場面を落ちる形のまま `check` に入れられない
- 期待値の古い場面を、根拠無しに「落ちることを期待する」で一括して包むと、外部 B5・C5 の危険(更新の盲目化、隔離が本物の後退を隠す)をそのまま作る。内部 2.4 は全件の原因を特定しており、包む理由が無い
- scenarios の 3 件は、#296 の付記が同じ変化点での確認と任命を定めていない〔内 2.4〕。**規定されていない振る舞い**であり、回帰とも決定の帰結とも言えない。これは公開のインタフェース(構成の変更の受け付け)の選択であり、人へ戻す場合(b)に当たる。担当が期待値を変えて閉じれば、決定の無い仕様変更を試験が固定する
- 印を「元の期待 + 落ちることを期待」にする理由: Issue の結論が「拒否が正しい」なら新 ADR とともに期待値を変え、「回帰」ならテンプレートを直した時点で strict の印が知らせる(外部 D1・D2 の strict xfail の型)。どちらの結論でも、検出の機会を失わない
- replay の 5 件は ADR-0066 の決定の帰結で、ADR-0066 自身が「fixture を同時に直す」と定めている。直し残しの是正であり、新しい判断ではない
- 分類は「何が決まっていたか」の判断で、標準の解釈そのものである。AI の推定による判定を判定に数えない附属書H H.4 の趣旨を、本リポジトリの運営にも当てる

**他の案を落とす理由**:

- 全部を直してから移す: scenarios の 3 件は直す向きが決まっていない。直せない
- 全部を印付きで入れる: 上記(盲目的な隔離)
- scenarios の 3 件の期待値を「拒否」へ変える: 決定の無い振る舞いを固定する。ADR-0066「本文を正とする」の裏返しで、試験が決定を作ることになる

**文の案**:

- 落ちる場面を、原因と分類(期待値が古い / 決定が変わった / 回帰 / 決定が無い)を確かめずに印で包まない
- 「決定が無い」に分類した場面は、Issue を立てて人の判断へ回す。判断が出るまで、場面は元の期待のまま、落ちることを期待する印と Issue の番号を付けて走らせる
- 落ちることを期待する印を付けた場面が通ったら、試験を失敗にする

**矛盾**: 無い。ADR-0028(未達と省略の区別)・CLAUDE.md の「降りていない規定を消さずに表示し続ける」と同じ型である。

**実装上の注意〔確〕**: CI の Node は 22(`ci.yml`)。Node 22.22.0 で `{ expectFailure: true }` を試したところ、印は無視され通常の失敗になった。外部 D3 の `expectFailure` は v24.14.0 以後で、使えない。スイートは独自の `check()` を持つので、印の意味(strict。Issue の番号を必須にする)は自前で実装する。rustc の tidy〔外 D7〕は接頭辞しか見ないが、本リポジトリは Issue の番号の形まで確かめる。

## R-3 時計

**結論**: 試験の側で時計を固定する。製品のコード(テンプレート)に時刻を差し替える入口を足すことは採らない。固定は、子プロセスへ届く形(`NODE_OPTIONS` の `--import` で `Date` を差し替える前処理)で行い、場面の日付は固定した時刻からの相対で書く。日付の境・時刻帯は、時刻を明示して作る場面で確かめる。時限(2026-12-01、2027-04-01)は固定で解消する。**2026-12-01 より前に移植を終える**。

**理由**:

- 本委員が確かめた〔確〕: (1) `node:test` の `mock.timers`(Node 22 では experimental)は同じプロセスの `Date` しか止めず、`execFileSync` で起動した子の Node は実時刻を返した。スイートの場面は `generate-profile.mjs` などを子プロセスで起動するので、外部 C2 の手段は**このスイートには効かない**。(2) 環境変数で基準時刻を渡し、`NODE_OPTIONS="--import <clock.mjs>"` で `Date` を差し替えると、子の Node へも固定した時刻が届いた。スイートは既に `mockgh-prs.mjs` を `--import` で注入しており〔内 0.1〕、同じ型である
- 製品へ入口を足さない理由: K65(最後の記録より前の発効日を受け付けない)は統制である。「今日」を環境変数で動かせる入口は、本番で発効日の検査を外す経路になり、統制の弱化に当たる。試験のためだけに製品へ置く経路は、DO-178C が不活性コードとして説明を求める類型である〔記憶〕。外部 C1(Fowler)の「時計を包む」は設計の推奨で、包んだ時計を外から差し替えられる入口を本番に残せとは言っていない
- 相対の日付: scenarios の `2026-10-01` の直書き、replay の架空の日程(10-01〜12-20)、`next_review: 2027-03-31`、`confirmedAt: '2026-12-01'` は、すべて「固定した時刻」に対する相対で書けば、時限が消える〔内 3・4.1〕
- 境をまたぐ実行: 固定した時刻は実行の時間だけ進む形にすれば、`TODAY` の一回計算と子プロセスの日付が一致する。内部 4.1 の sweep の 68 件の失敗(UTC 0 時をまたいだ)は、この型で再現しなくなる。境そのものは、23:59:59 に固定した場面を明示して確かめる(stages の `HH:60` も同様)
- 限界(開示): `Date` の差し替えは git のコミットの日時やシェルの `date` には届かない。テンプレートが git の履歴の日時を判定に使う経路があるかは、本委員は確かめていない。移植のときに洗い出す

**他の案を落とす理由**:

- テンプレートに入口を足す: 上記(統制の弱化・本番での悪用)
- `mock.timers`: 子プロセスへ届かない〔確〕
- `faketime`: 環境に無い〔内 4.1〕。Windows・macOS での再現性も下がる
- 時計に依存する場面を隔離する: 時刻帯・日付は K60・K65 の決定そのものの主題であり、隔離すれば決定を固定しなくなる

**文の案**: 本リポジトリの運営の規定にとどめる。

- 決定を固定する回帰試験は、実行の日時に依らず同じ結果になるように、試験の側で時刻を固定する
- 試験のために、製品(準拠テンプレート)へ時刻を差し替える入口を置かない

**矛盾**: 無い。

## R-4 期待値を変えるときの手続

**結論**: 決定を固定する場面の期待値を変える変更は、(a) その場面が名指す決定を置き換える ADR(または同じ変更で置く ADR)を名指すか、(b) 場面が決定ではなく付随する出力(文言・前の値・模擬の形)を固定していたと分類し、場面を決定の不変条件を確かめる形へ書き直すか、のどちらかとする。(a) では規則・本文・期待値を同じ変更で直してよい(ADR-0066 の型)。期待値の更新を自動で行う仕組み(スナップショットの一括更新)は置かない。#302〜#310 の複製の中の直しは、**構成管理の外での変更**として新 ADR に記録し、是正(本 Issue)の起点とする。

**理由**:

- 禁止事項3 は「テストの失敗を、テスト側の変更で解消する」ことを禁じる。`ci-gates.md` は、受入基準の変更に伴う正当な書き換えがあることを認め、区別を人のレビューに置いた〔確〕。決定を固定する試験では、受入基準に当たるのが ADR である。決定が変わっていないのに期待値を変えれば、禁止事項3 と同じ構造になる〔外 B5〕
- (b) を設ける理由: 内部 2.4 の失敗の多くは、決定ではなく文言(v3 の K65)・前の値(new の 90%→80%)・模擬の形(t288 の `commit.oid`)を固定していた。回帰が要求への適合を確かめるもの(0 節の定義)なら、場面は不変条件(「拒否される」「記名を要する」)を確かめるべきで、付随する出力を固定した場面は直すのが正しい。これは期待値の差し替えではなく、場面の欠陥の是正である
- 理由の欄を必須にしない: `ci-gates.md` が採らなかった理由(AI が埋められる)は本リポジトリにも当てはまる。代わりに、(a) の ADR の名指しは `lint:refs` の型で実在を確かめられる構造であり、欄の記入とは違う
- 自動更新を置かない: Jest・Node・ApprovalTests の公式の手引きが一致する〔外 B2〜B4〕
- 複製の中の直しの位置づけ: 直した場面で流した結果は、構成品目から再現できない検証である。ADR-0066 110 行の記述が replay の直し残しを見落としたのは、この形の直接の帰結である(1 節の1)。決定そのものを無効にはしない(決定の根拠は試験ではなく本文と審議)が、「回帰で確かめた」と言える範囲から除く

**他の案を落とす理由**:

- 期待値の変更に、変更ごとの理由の欄と人の記名を必須にする: 理由の欄は既存の設計で却下済みで、却下の理由がそのまま当てはまる。本リポジトリはソロ期で、作成者と別の人の確認は成り立たない。成り立たない確認を記録上求めれば、承認と誤読される(ADR-0077 決定6 の「必須レビュアは置かない」と同じ理由)
- 規則と期待値を別の変更に分けることを求める: 分けた間の版では `check` が落ちるか、規則が試験無しで入る。ADR-0066 が同時に直すと決めている
- 機能変更と同じ変更での期待値の変更を禁じる(テンプレートの禁止事項6 の型): 閾値・除外設定と違い、期待値は決定と同時に変わるのが正しい場合がある。区別できない禁止は偽陽性を生む(ADR-0073 の3条件の1つ目)

**文の案**:

- 決定を固定する場面の期待値は、場面が名指す決定を置き換える ADR を名指す変更でだけ変える
- 場面が決定ではなく付随する出力を固定していた場合は、期待値を差し替えず、決定の不変条件を確かめる形へ場面を書き直す
- 期待値を自動で更新する手段を、検査の経路に置かない

**矛盾**: ADR-0066 決定(同時に直す)と整合する。禁止事項3 とは、`ci-gates.md` の「正当な書き換え」の区別を ADR の名指しで具体化する関係で、矛盾しない。

## R-5 「採らない」と決めた文と、廃した言い回し

**結論**: (1) 反映の作業に、決定の「採らなかった案」ごとに、識別できる句があるかを判断する手順を足す。句があれば登録簿へ足し、句で表せない場合はその旨を決定の記録に書く。全文の検索を検査にはしない。(2) 登録簿の各句には由来の欄 `by` が既にある〔確: `provision-forms.yaml`〕。足すのは、`by` が実在する ADR を指すことの機械の確認である(現状は確かめていない〔確: `check-provisions.mjs` 360 行は `by` を表示するだけ〕)。(3) zenn を検査の範囲へ入れるかは #320 で決める。research は入れない(過去の記録を書き換えさせない)。

**理由**:

- 「採らない」と決めた文は散文であり、検索の結果を合否に使えば偽陽性が出る。ADR-0073 の3条件を満たさない。句へ落とせたものだけを検査にする形は、textlint-rule-prh・Vale の登録簿の型〔外 E1・E2〕と同じである
- 句で表せないことを記録させるのは、「検査に載っていない」と「載せられないと決めた」を区別するためで、コアポリシーの「採らないと決めたことは明記する」の適用である
- `by` の実在の確認は、外部 E 小括と F3(ADE)が指摘する「規則と決定が結ばれていないことによる浸食」への手当てである。結びの欄はあるが検査が無い、が現状である
- research を範囲に入れない理由: research は審議の記録であり、ISO 9001 7.5.3 の趣旨(記録の完全性の保護)から、後の決定で書き換えさせるべきでない。zenn は正本から派生した発信物で、正本と食い違うことは問題だが、サブモジュールの取得を CI に足さないと ADR-0077 決定3(入力の欠如は失敗)で `check` が落ちる。#320 と同じ論点であり、ここで決めると二重になる

**他の案を落とす理由**:

- 採らなかった文の全文検索を検査にする: 偽陽性(上記)
- 各句に試験(prh の `specs` の型)を持たせる: 部分一致の誤検出は `retired-ok` で個別に扱えており、本 Issue の失敗(句が手順に無かった)とは別の問題。必要が示されたら別に扱う。**本 Issue では採らない**

**文の案**(運営の規定。`community/provision-forms.md`):

- 決定を反映するときは、決定が採らなかった案ごとに、その案を識別できる句があるかを判断する。句があれば登録簿へ足し、無ければ句で表せない旨を決定の記録に書く
- 登録簿の句の `by` は、実在する ADR を指さなければならない(`npm run lint:refs` が確かめる)

**矛盾**: 無い。

## R-6 CI と実行時間・知識ベースへの依存

**結論**: 決定を固定する回帰試験は、親の `npm run check` へ入れる(`ci.yml` の `check` ジョブで走り、公開・配布はその通過を待つ)。テンプレートの `gate-g5.yml` へは入れない。実行時間に上限を置かない。sweep(768 組合せ)も、時計の固定の後に `check` へ入れ、定期実行に回さない。ジョブの停止の歯止めとしての `timeout-minutes` は、量の上限ではないので置いてよい。

**理由**:

- 知識ベースを標準から作り直す必要があり、テンプレート単独の CI では流せない〔内 8〕。親の `check` はサブモジュールとしてテンプレートを得ており、両方が揃う唯一の場所である
- ADR-0077 決定1 は検査の一覧の正本を `check` に限った。`check` の外の別ジョブにすれば、正本が2つになる。決定2 は公開・配布を検査の通過に繋いだ。回帰を外せば、決定を破った版が公開される経路が残る
- 定期実行は、ADR-0077 が配布物の事後検査を「配った後にしか見つからない」として却下した型である。IEC 61508-3 表 A.8 の「影響を受けるモジュールの再検証」〔記憶〕の趣旨も、変更ごとの再検証である
- ADR-0074 決定1 は実行時間の上限を置かないと決めている。runall2 と残りで約 5〜6 分、sweep で 8〜11 分〔内 8〕は、上限を理由に外す根拠にならない。止まらないジョブを止める `timeout-minutes` は量の管理ではなく故障の検出であり、決定1 と矛盾しない
- 開示: テンプレートのリポジトリ単独の変更は、親がサブモジュールを進めるまで回帰に掛からない。規則の正本は親にあり(CLAUDE.md)、テンプレートの更新を取り込む変更が親の `check` を通る、が関門になる。採用者の側にこの試験は届かない(届ける根拠も無い。R-7)

**他の案を落とす理由**:

- `gate-g5.yml` へ入れる: 知識ベースが作れない。採用者の必須の集約に本プロジェクトの保守の試験が入る
- sweep を定期実行にする: 上記
- 時間の上限を置き、超える試験を外す: ADR-0074 決定1 に反する

**文の案**: `package.json` の `check` に `test:regression`(仮)を加える。運営の規定には書かない(ADR-0077 決定1 により、一覧を散文に列挙しない)。

**矛盾**: 無い(上記の3つの ADR に沿う)。手元で速く流す別名を置くことは妨げないが、ADR-0077 決定5 により手元の結果は証跡にならない。

## R-7 標準の側の規定

**結論**: 採用者へは、**G-5 の判定に数える試験(スクリプト・入力・期待値)を、判定の対象と同じ版管理の下に置くこと**だけを、第4章「判定が指す記録の保管」の隣に規定として足す(根拠水準マークを付ける)。期待値の更新の手続と、既知の失敗の印の方式は、標準では規定しないと明記する。時計の扱いは規定しない。

**理由**:

- 足す1文は、既存の決定 7(判定が指す記録は到達できなければならない)からの帰結である。版管理の外の試験の結果に基づく G-5 は、何を確かめたかを後から再現できず、自己申告と区別できない。#319 はその実例である(試験が利用者の端末の `tmp/` にだけあり、消えかけた)。規格の側でも SWE-081(一次)と 61508-3 6.2.3・CMMI CM・DO-178C の趣旨が一致する
- 既存の条項は近いが、これを言っていない: 附属書I の Q14(`adoption-guide.md` 299 行)は「テストを自組織のリポジトリに置く」を退出の文脈の**主張**として書き、要求事項ではない。`safety-verification.md` の追加要求2 は生成に用いたモデルと指示の構成管理で、試験資産ではない〔確〕。`構成品目` の語は本標準の本文に無い〔確〕
- 期待値の更新の手続を規定しない理由: 採用者の側では、`ci-gates.md` が既に「既存のテストの変更は合否に使わず、一覧を G-6 の材料にする。理由の欄は採らない」と決めている〔確〕。これに重ねて手続を課すと、同じ論点に2つの規定ができる。禁止事項3 と 5.8.4 の後の段落が、AI による解消を既に止めている
- 既知の失敗の印を規定しない理由: 印の方式は言語・試験の枠組みに依る実装の選択で、規格の条文が無い(0 節)。「`skip` 相当の付与」は既に検証の弱体化として G-6 の必須の確認事項に挙がっている(`agent-trace-control.md` 69 行)〔確〕。印を付けて落ちる試験を集約から外す行為はこれに当たる
- 時計を規定しない理由: 実装の技法であり、規格・規範の根拠が無い。標準が技法を課すと、方法の中立(ADR-0080)に反する

**他の案を落とす理由**:

- 第5章・第7章に構成管理の節を新設し、試験資産・期待値の更新・既知の失敗を規定する: 期待値の更新は既存の設計と重複・衝突し、既知の失敗の印は根拠の無い技法の強制になる。構成管理の全体を規定するなら 12207・15288 の本文を読む必要があり、本標準はそれを読んでいない(1.3)
- 何も規定しない: 既存の決定 7 の帰結を書かずにおくと、採用者は「試験は CI で流れていれば足りる」と読める。#319 の事象が採用者でも起きうる

**文の案**(第4章「判定が指す記録の保管」の後に置く段落。本文はですます調):

> G-5 の判定に数える試験(試験のスクリプト、入力のデータ、期待値)は、判定の対象と同じ版管理の下に置かなければなりません。版管理の外にある試験の結果を、G-5 の判定に数えてはなりません。結果だけが残り、試験そのものを後から再現できない判定は、何を確かめたかを示せないためです。

> :::caution[暫定 EV-NNNN / 見直し 2027-10]
> **対象**: G-5 の判定に数える試験を、判定の対象と同じ版管理の下に置くことを求めること。
> **根拠の水準**: E1(間接)。試験資産を構成品目に含める規範(NASA NPR 7150.2 SWE-081 は一次。IEC 61508-3:2010 6.2.3 は一部、CMMI の構成管理は二次)と、本プロジェクトの単一事例(#319)による。規定が手戻りを減らすことの測定は無い。

> 本標準は、期待値を更新する手続と、落ちることが分かっている試験の扱いの方式を規定しません。既存のテストの変更は G-6 の材料として一覧に出し(フェーズ5 CI/CD ゲート構成)、試験の削除と `skip` 相当の付与は検証の弱体化として扱います。

- 実装マーク: 足す規範に `<!-- impl ... target=pr-checks または契約検査 ... -->` を付け、降ろせなければ `state=undelivered` で表示し続ける。降ろし先の選定は起案担当へ委ねる
- 適用範囲: 全ての変更(R・CL に依らない)。見出しへの併記は要らない

**矛盾**: 既存の決定 7 の具体化であり、置き換えではない。`ci-gates.md` の「理由の欄を採らない」決定とは、手続を規定しないことで衝突を避ける。附属書H H.10 の箇条番号の規律に従い、本文に ISO 9001 の箇条番号を書かない。
