## 1. 事前点検で初期化が止まる件(移した版のまま、900 件)

### 1.1 事実

- いまの作業ツリーで移した版をそのまま流すと、初期化(`generate-profile.mjs --answers answers.json`)が事前点検(`scripts/gate/preflight.mjs`)で止まる。止める項目は2つで、`.github/CODEOWNERS` の `@OWNER` の残りと、資産の一覧(`docs/adoption-inventory.md`)の欠けである。後者の「既存の資産」の正体は、場面が作業用の複製へ書いた `answers.json` である

- 適応の2つを足すと、900 件の失敗は 47 件まで減る(adapt)。残る 47 件は、2 節以下で個別に分類する

### 1.2 分類: I(fixture・入力が決定に反する)

- 引く決定: ADR-0085 決定2(初期化の前に、書き込まない事前点検を置く。`@OWNER` の残りと、資産の一覧の欠けを止める)。テンプレートの `9c13c3e`(#315)から
- スイートが固定する決定(K 番号・Issue)のどれも、事前点検の挙動を主張していない。止まるのは作業用の複製の作り方が ADR-0085 の前提(採用者が `@OWNER` を置き換え、既存の資産を一覧へ載せる)に反するためである。製品の回帰ではなく、期待値を変える話でもない
- 「決定が変わった(D)」と書く案もありうる。ただし直すのは期待値ではなく作業用の複製(入力)なので、R-2.3 の別(I)に置く。調査 319-1 2.3 は「fixture が古い(決定が変わった)」と書いており、分類の名が違うだけで、直し方の見立ては同じである

### 1.3 移した試験の側で直すこと

1. `run.mjs` の `fresh()` で、`git add` の前に `.github/CODEOWNERS` の `@OWNER` を試験用の名へ置き換える。ADR-0085 は「直し方: @OWNER を実在のアカウントかチームへ置き換える(人が決める)」とする。試験の作業用の複製では、試験の作者がその人に当たる
2. 同じ `fresh()` で、`git init` の後に `.git/info/exclude` へ `/answers.json`・`/change.json` を足す。テンプレート自身の `test-init-g5.mjs` は回答の JSON を作業の場所の外へ置く形を取る。どちらの形でも事前点検は同じ結果になる。15 本のスクリプトが `gen('--answers', 'answers.json')` を使うため、除外の形のほうが変更が1か所で済む。**ただし、変更量は採否の理由にしない**(CLAUDE.md)。除外の形を勧める理由は、場面の入力の書き方(作業用の複製の中の `answers.json`)を元のまま保ち、p302 との一致の確認で比べる基準を変えないためである
3. 適応が事前点検を黙らせたままにならないよう、適応を外した複製で初期化が事前点検に止められることを確かめる場面を1つ置く(`suite/clock.mjs` の前置きと同じ形で足せる)。そうしないと、ADR-0085 の挙動が回帰しても、このスイートは気づかない。テンプレートの試験が既に確かめている場合は、その所在を処置の表に書けば足りる
4. 適応を入れた版で、p302・pre311 でも全場面の合否が変わらないことを確かめる(R-1.2 の一致の確認)。`@OWNER` の置き換えと除外の行は、p302 の版でも無害である(probe の p302 の実行で確かめた。5 節)

## 3. 照合を厳しくして一致しなかった2場面

問い: 照合を厳しくしたことで「別の理由で拒否されていた」ことが露わになったのか、照合の範囲の定め方の問題か。

確かめ方: p302(`ec8ecd6`)と adapt(いま)で、両場面の出力の全文を得た(p302 は `REGRESS_CAPTURE=1`)。

### 3.1 scenarios「ステージを前へ戻す(記名なし) → 拒否」

- p302 の出力の `[エラー]` の行は1件だけで、「統制を緩める向きの変更を含みます。決定した者の記名(decidedBy)と理由(reason)が要ります。決定できるのは、対象の席の責任者、または事業決裁者の席の責任者(D-0 表1「体制と運用形態」の決定者)です。AI が決めてはなりません」である
- 「ステージ移行ゲート(SG)の判定による」は、p302 では「構成の差分」「統制を緩める向きの変更」の節の行(`回答 q-biz-phase: mvp → poc(事業ステージを前へ戻す。ステージ移行ゲート(SG)の判定による。…)`)と、「残作業」の行にある
- いまの出力の `[エラー]` も同じ1件である(付録 A の 47 場面の出力と同じ)
- 場面の入力は記名も `sgRecord` も持たない。記名の欠けで止まるのは、評価の順序として正しい。SG の判定記録が要ることは、同じ節の後続の場面(`sgRecord` の所在なし・実在しない・リポジトリの外)が理由の照合で確かめている
- 結論: **別の理由で拒否されていたのではない**。元の場面は2つの事柄(拒否の理由が記名の欠けであること、この変更が SG の判定による変更として分類されていること)を、出力の全体への1回の照合で確かめていた。厳しい照合は前者だけを見る形になり、後者の語を探す範囲から差分の節を外した。照合の範囲の定め方の問題(P)である

### 3.2 v3「決定者が残っている間、任命権者を名簿へ足す…→ 拒否」

- p302 の出力の `[エラー]` は1件で、「席の責任者の任免(または D-0 表1 の決定者の変更)を含みます。統制の向きにかかわらず決定であり、決定した者の記名(decidedBy)と理由(reason)が要ります。決定できるのは、変更前の D-0 表1「体制と運用形態」の決定者です。…(標準 第3章 3.13.3)」である
- 差分の節は「人の名簿: 追加 別部 長(組織上の任命権者)」の1行だけで、任免の節に「人の名簿: 別部 長 を組織上の任命権者として置く — 決定できる者: 変更前の D-0 表1「体制と運用形態」の決定者」がある。ほかの変更は無い
- いまの出力の `[エラー]` も同じ
- 結論: 拒否の理由は、場面の名が言う「決定者の記名を要する」そのものである。**別の理由で拒否されていたのではない**。期待の語は、拒否の対象(任命権者を置くこと)を差分の節で確かめていた。照合の範囲の定め方の問題(P)である

### 3.3 直し方の提案

- 2場面とも、照合を「拒否の理由」と「差分の節」の2つの確かめに分ける(2.5・2.8 の表)。語は元のまま使い、期待値は変えない。差分の節は見出しで区切って照合する(出力の全体を照合の範囲に戻さない。品質保証 Q6 の懸念は、別の節の同じ語で通ることだったため)
- これは期待値の変更ではなく、移植の照合の直しである(R-1.2)。p302 での一致の確認の対象に含める。5 節で p302 の結果を書く
- 補助 `lib.mjs` に「差分の節の中で語を照合する」関数を足す形が、ほかの場面にも使える。ほかの `refused` の場面で、期待の語が差分の節にだけある場面がほかに無いかは、本書では網羅していない(7 節)
