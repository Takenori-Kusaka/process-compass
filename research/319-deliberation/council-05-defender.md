## 0. 擁護者としての総論

1. 内部調査は「固定していた決定そのものが破られた場面は見つからなかった」と結ぶ。**この結論には同意しない**。少なくとも 2 件は、決定が黙って変わったか、決定の無いまま挙動が変わった疑いが残る
   - v3 の K65 の場面: 内部調査は「決定が変わった(文言を固定していた)」と分類した。しかし ADR-0078 は基準(取り消せない時間帯の存在)を**変えないと明記**している。場面が落ちたのは、文言が変わったためではない。エージェントが常に読む指示の層から、ADR-0053 決定1 の基準が消えたためである。期待値を新しい定義の文へ差し替えると、この消失が固定される
   - scenarios の 3 件(氏名の確認と任命を同じ変化点で行う): #296 の付記が決めたのは「誰が確認を記名するか」である。「確認と任命を別の変化点に分ける」ことは、どの決定にも無い。p302 では受け付けていた。挙動は実装の評価順で変わった
2. 決定の正本は ADR である(A-6 の判断を維持する)。ただし、会議体は fixture を決定の根拠として引いてきた(A-6 の 48 行)。fixture は「決定の記録」ではないが、**決定が守られていることの唯一の実行可能な証拠**である。この二面を両方満たす形で移す必要がある
3. 変更の採否の軸は信頼性である。下の各案では、移植の手間・実行時間の短さを理由にしない

## R-1 何を、どこへ、どの形で移すか

**結論**: 決定(ADR の決定・K 番号・#Issue の決定)を名指す場面は、**全件を移す**。除外できるのは、(i) 再現できないもの、(ii) 同じ主張を既存の試験が持つと場面の単位で確かめたもの、に限る。除外した場面は「廃した場面」として、理由とともに対応表へ残す。移植は 2 段で行う。第1段は、元のスイートに近い形のまま移し、同じテンプレートの版で元の結果と場面ごとに一致することを確かめる(等価の確認)。既存の試験の形への書き直しは第2段で行う。置き場は親のリポジトリ(process-compass)とする。

**理由**

- 選んで移すと、選ばなかった場面が固定していた決定が、記録なしに無防備になる。内部調査 1.2 の照合は語の一致であり、「無い」側だけが強い。既存の試験に「ある」と判断して落とすには、場面ごとに主張の一致を確かめる必要がある(内部調査自身が断っている)
- 書き直しを先に行うと、移植の過程で期待値が変わっても気付けない。等価の確認には基準点が要る。p302(テンプレート `ec8ecd6`)で全スクリプトの出力行数まで組A の記録と一致した結果(内部調査 0.2)が、その基準点になる
- 置き場: スイートは標準から作り直した知識ベースを要する(内部調査 8 節)。テンプレートの `gate-g5.yml` は採用者へ配られ、知識ベースを作れない。標準の決定を固定する試験を採用者のリポジトリへ配る理由も無い。親に置く
- `replay` の入力 24 件(`reverify-scenarios/in/`)は、試験の入力そのものである。構成品目として同じ場所へ入れる(外部調査 A5: CMMI CM・NASA SWE-081 は試験データを構成品目に含める)
- 対応表を持つ: 各場面に「固定する決定」の欄(ADR 番号と決定番号。ADR へ畳まれていない K 番号は `research/phase4-standard/284-285-fix-spec*.md` の K 番号と、その旨)を持たせる。外部調査 F3 は、検査が決定と結ばれていないことを浸食の原因に挙げる。今回の分類(どの失敗が決定の変更か)を決める手掛かりが、スクリプトのコメントしか無かった
- ADR-0028(未達と省略の区別)を固定する scenarios の場面は、既存の試験(`test-tailoring-engine.mjs` の「S0 の G-6」)と重なって見える。重なりを確かめるまで、両方を残す

**r3(`fix288-r3/`)と再現できないもの**

- r3 は `src/inspection.js` が無く再現できない(内部調査 6 節)。連鎖で単独で流せない。**移さない**。ただし、r3 が固定していた #288 の決定を対応表に列挙し、trial・trial-r7・`test-adoption.mjs` のどれが代わりに固定するかを書く。代わりが無い決定は「固定する試験が無い」と表示し続ける(未達のゲートを消さずに表示する ADR-0028 と、降りていない規定を消さない #222 の扱いに揃える)
- ta(trial に置き換わった)、verify-n の N7(入力が無い)、tok(合否なし)も同じ扱い。消すのではなく、廃した理由を書く

**利用者の端末の `tmp/` の原本**

- 移植した試験が、p302 の結果と場面ごとに一致することを確かめるまで、原本とバックアップ(`/mnt/project-files/backup/legacy-suite-319/`)を残す。原本の削除は取り消せない操作であり、利用者が決める。AI は削除を提案するところまでにする

**他の案を落とす理由**

- 「決定を固定する場面だけを選ぶ」: 選別の基準が「コメントに決定が書いてあるか」になり、内部調査の表のとおり、ほぼ全件が該当する。選別は手間を減らすだけで、信頼性を上げない
- 「最初から既存の形へ書き直す」: 等価を確かめる手段が無くなる。前回の擁護者(302-310 A 5節 (1))は書き直しを推したが、そのときは原本が流れる状態を前提にしていた。原本がいまのテンプレートで流れない以上、書き直しと期待値の変更が同時に起き、区別できない
- 「テンプレートへ置く」: 上記の理由で落とす

**既存との矛盾**: 無い。A-6 の「fixture は決定の記録ではない」とも両立する(正本は ADR、対応表は ADR を引く側)

## R-2 いま落ちる場面の扱い

**結論**: 移す前に一括で直すことはしない。落ちる場面ごとに、次の 4 分類のどれかを、**決定の引用を添えて**確定する。分類を確定するのは人(このリポジトリでは利用者)である。AI(調査・反映の担当)は分類と引用を起案するところまでにする。分類が確定するまで、元の期待値のまま「落ちることを期待する」印(厳格。予期せず通れば失敗)で入れ、Issue を結ぶ。

| 分類 | 直す側 | 条件 |
| --- | --- | --- |
| A 環境・時計の fixture | fixture(入力・時刻)を直す。**期待値は変えない** | 場面が固定する決定が成り立っていることを、直した後の実行で示す |
| B 決定が変わった | 期待値を変える | 変えた決定(ADR 番号と決定番号)を対応表に書く。元の場面が確かめていた性質のうち、変わらなかった部分を確かめ続ける |
| C 回帰 | 製品のコードを直す | — |
| D 判断が要る | 何も変えない。印と Issue で走らせ続ける | 人が決めるまで |

**各場面への意見**(内部調査の分類への異議を含む)

- scenarios の時計の 1 件(3.1)、replay の日付の 15 件(3.2): **A**。期待値はそのまま。日付の扱いは R-3
- replay の `s4-acc3` の 5 件: **A**(入力が決定 A-4 に反する)。組A が v3・new・tz に施した直しと同じ直しを入力へ施す。A-4 を引用する
- v3 の K65(「取り消せない時間帯」): **内部調査の B に同意しない。D とする**。ADR-0078 は基準を変えていない。期待値を新しい定義の文へ差し替える前に、ADR-0053 決定1 の基準が、エージェントの読む層(`CLAUDE.md` か `.claude/skills/pit/reference/handoff.md`)に届いている必要があるかを人が決める。届けると決めれば C(テンプレートを直す)、D-0 の表だけで足りると決めれば、その判断を記録したうえで、場面の後半を「D-0 に基準がある」へ移す。前半(「不可逆4操作」が無い)はそのまま残す
- scenarios の氏名の確認の 3 件: **D**。擁護者としての見解は「回帰の疑いが強い」である
  - 付記の要求(本人以外の記名)は、同じ変化点でも満たされる。記名する山田は Claude Dupont 本人ではない
  - 2 回に分けても、記名するのは同じ山田である。分けることで独立性・記録の確かさは増えない
  - p302 では受け付けていた。挙動が変わったのは、判定が記録を足す前の構成で行われるという評価順による。#296 の会議体がこの経路を議論した記録は無い
  - 反対の見方(先に確認の記録が履歴に載ってから任命するほうが、監査で順序を追いやすい)もありうる。だから AI が決めず、新しい Issue で人が決める。決まるまで、元の期待値(「反映」)で印を付けて流す。**期待値を「拒否」へ反転させて通すことは、禁止事項3 と同じ形であり、採らない**
- new のカバレッジ(90 → 80 → 85): **B**。ADR-0088(下限は由来と基準値を持ち、未達の代償措置の終了を同じ差分で決める)を引く。場面の主題(下限を下げるには AI維持管理者の記名が要る)は変わらず確かめる
- matrix の 3 行: B。ただし matrix は期待値を持たず、向きが `appoint` から `loosen` へ変わっても合否が ok のままだった。**期待値を持たない場面は、何も固定していない**。移すときに、向きと下限を期待値として持たせる
- stages の 20 件: (a) G-2・G-4 の前提条件(#291 の突合)は B だが、**直すのは fixture**(写した仕様の `[NEEDS CLARIFICATION]` を埋める)。場面の主題は段階の遷移であり、仕様の中身ではない。(b) `iterate` がテストを実行する(ADR-0079)も、fixture 側で失敗するテストを用意し、反復の上限での保留(禁止事項3 を支える仕組み)を確かめ続ける。期待値を「ロックがありません」へ合わせる直しは採らない
- t288 の 6 件・s5-init-pr の 1 件: B(ADR-0079「承認は承認した差分に対して数える」)。直すのは模擬の PR(`commit.oid` を持たせる)。期待値は変えない
- t288 の 3 件・t288b・verify-n の N6: 原因が分解されていない。**分解するまで D**。「決定の変更の可能性が高い」という推測で B にしない

**他の案を落とす理由**

- 「移す前に全部を直す」: 直しの単位が大きくなり、どの直しがどの決定に基づくかを、レビューで追えない。外部調査 B5 の更新の盲目化の形である
- 「落ちる場面を移さない(skip)」: 落ち続けていることを確かめなくなる。外部調査 D2 のとおり、skip と xfail は役割が違う。予期せず通ったことも分からない

**既存との矛盾**: 無い。分類の確定を人に置くのは、5.5 の判断の確定と、第3章 3.5.3(起案したセッションは判定の草案を作らない)に揃う

## R-3 時計

**結論**: 時計は**試験の側で**止める。テンプレート(製品のコード・強制層)に時刻を差し替える入口は**足さない**。

**理由と方法**

- スイートの場面は `generate-profile.mjs` などを**子プロセス**で起動する。Node の `mock.timers` は試験のプロセスの中でしか効かず、子プロセスの時計を止められない(仕組みからの推論。実行では確かめていない)。そのため、外部調査 C2 の手段だけでは足りない
- 子プロセスへ届かせる方法として、`--import` で読み込む前処理のモジュールが `Date` を固定時刻へ差し替え、`NODE_OPTIONS` で子プロセスへ継がせる形を推す。スイートは既に `mockgh-prs.mjs` を `--import` で読み込み、`execFileSync` を差し替えている(内部調査 0.1)。同じ型の仕組みである。**子プロセスへの継承と、テンプレートが `Date` 以外の時刻源(`process.hrtime` 等)を日付に使っていないことは、確かめていない**。採るなら、移植の第1段で確かめる
- 場面ごとに固定時刻を与える。`TODAY` を読み込み時に 1 回だけ計算する誤り(内部調査 4.1。sweep の 68 件)は、固定時刻で消える
- 直書きの日付(`2026-10-01`、`2026-12-01`、`next_review: 2027-03-31`、`reviewBy: 2026-12-31`)は、固定時刻からの相対で書く。replay の入力の日付も同じ
- `stages.mjs` の `HH:60`(内部調査 4.1)は試験の誤りであり、直す
- 時限への手当て: v3 の `2026-12-01` は**約 5 週間後**に新しい失敗を生む(推定。内部調査)。移植がそれまでに終わらない場合も、この 1 件は先に固定時刻か相対へ直す
- 時刻帯(`tz.mjs`)は、時刻を固定したうえで `TZ` を変えて流す。時刻帯の差の確認は保つ

**入口を足す案を落とす理由**

- K65(最後の記録より前の発効日を受け付けない)と `check-d0.mjs` の `next_review` の期限は、どちらも統制である。製品のコードに「時刻を差し替える環境変数」を置けば、採用者の手元で発効日を遡らせる経路が、正規の機能として配られる。これは強制層の縮小・統制の弱化に当たり(CLAUDE.md の受信箱の表、`state:needs-platform`)、試験の都合で正当化できない
- 外部調査 C1(Fowler)の「時計を包む」は、製品の内部に差し替え可能な時計を持つ設計の推奨であり、外から設定できる入口までは求めていない。製品のコードの設計を変えるなら、別の Issue で、入口を公開しない形(モジュール内の注入)を議論する

**時計を止めることの限界**: 固定時刻は、実時間でしか起きない不具合(日付の境をまたぐ実行での、記録と入力の日付のずれ)を隠す。sweep の 68 件は試験の誤りだったが、製品が同じ形の誤りを持てば、固定時刻の試験は検出しない。日付の境をまたぐ場面を 1 つ、固定時刻を進めて(境の前後で)明示的に作る

**既存との矛盾**: 無い

## R-4 期待値を変えるときの手続

**結論**: 決定を固定する場面の期待値を変える変更には、次を求める。

1. 期待値を変える場面ごとに、変えた理由の決定(ADR 番号と決定番号)を対応表へ書く。**引用できる決定が無い期待値の変更はしない**(R-2 の D へ回す)
2. 規則と期待値を同じ差分で変えることは**妨げない**。むしろ求める(決定 A-6「規則データ・本文・回帰の fixture を同時に直す」を維持する)。ただし、コミットの本文か突合の記録に、期待値を変えた場面の一覧を、規則の変更とは分けて書く
3. 期待値の変更は、人(利用者)がその一覧を見て確かめる。反映を起案したセッションは、自分の期待値の変更を確認済みとしない(第3章 3.5.3)
4. 機械の検査は、**各場面が対応表の決定の欄を持つこと**(構造)と、「落ちることを期待する」印に Issue があることだけを確かめる。期待値の差分を検出して失敗させることはしない

**禁止事項3 との関係**

- 期待値の変更は、決定が変わったことに合わせるなら「仕様の変更」であり、禁止事項3 の「解消」ではない。両者を分けるのは、引用された決定の有無だけである。引用の無い期待値の変更は、禁止事項3 と同じ形とみなす
- 4 の「期待値の差分で失敗させない」は、5.8.5 の直後の段落(検証を弱める変更の検出を G-5 の合否に使ってはならない)に揃える。この段落は採用者の G-5 への規定だが、本標準の作り手のリポジトリが逆の運用をすると、規定の理由(正当な変更まで止まり、除外が常態化する)を自ら否定することになる

**#302〜#310 の複製の中での直しの位置づけ**

- 中身は正当だった(A-4・C-3 の決定に基づき、`fix-suite.py` に手順が残る)。しかし手続としては**不適合**として記録する。理由は 3 つ: 構成管理の外で直した、元のスイートを古いまま残した、同じ決定の帰結である replay の入力を直し漏らした(内部調査 3.2 追記)。最後の点は、記録の無い直しが網羅を保証しないことの実例である
- この事例を「担当が複製で直してよい」前例にしない

**他の案を落とす理由**

- 「期待値の変更を禁止し、常に新しい場面を足す」: 決定が変わった場面を古い期待値のまま残すと、落ちる場面が常態になり、印の意味が薄れる
- 「期待値の変更を機械で検出して失敗させる」: 上記 5.8.5 との整合で落とす
- 「スナップショットの自動更新」: 外部調査 B2〜B5 がそろって退ける

**既存との矛盾**: 無い。5.8.4(期待値を人が承認した受入基準から取る)の、本リポジトリでの読み替え(受入基準に当たるのが ADR の決定)である

## R-5 「採らない」と決めた文と、廃した言い回し

**結論**

- 反映の作業(突合)の手順に、「ADR の『課さない』『採らない』の各項目について、`template/` と `src/content/docs/` に、採らなかった義務が書かれていないかを確かめ、結果を突合の記録に残す」を足す。機械の検査にはしない(文の意味の一致は部分一致で拾えない)。拾える特徴的な句があれば、従来どおり登録簿へ足す
- 登録簿の由来の欄は**既にある**(`by`)。新しい欄は足さない。議題の前提を訂正する
- `research/` は登録簿の検査範囲に**入れない**。調査・会議体の記録は、廃した言い回しを正当に含む(ADR の本文を除外しているのと同じ理由)。過去の記録を書き換えさせる検査は、記録の保全に反する
- `zenn/` を含めるかは #320 で決める。ここで決めると二重の決定になる。#320 が決めるまで、`zenn/` は「見ていない」と登録簿の文書に明記する
- 部分一致の誤検出は、既存の `retired-ok: 理由` で扱う。新しい仕組みは足さない

**擁護者として足す論点**: 登録簿は「残ってはならない語」を見る。v3 の K65 の場面が示したのは、逆に「**消えてはならない語**」(決定が残すと定めた基準)が消える危険である。これは登録簿の役ではなく、決定を固定する試験の役である。R-1 で移す場面のうち、文書の存在を確かめる場面を、この役として明示的に残す

**他の案を落とす理由**: 句ごとの由来の欄の新設(既にある)。`research/` の走査(上記)

**既存との矛盾**: 無い(ADR-0077 の「置き場が無い・空なら失敗」はそのまま)

## R-6 CI と実行時間・知識ベースへの依存

**結論**

- スイートの本体(sweep を除く。約 5〜6 分)は、親の `npm run check` に入れ、`ci.yml` で PR と main への push のたびに流す。公開(`deploy`)と配布(`publish`)は、従来どおりその通過の後に限る
- sweep(8〜11 分)は、テンプレートのサブモジュールの参照を進める変更と、`config.mjs`・`generate-profile.mjs` を変えるテンプレートの版を取り込む変更で必ず流す。加えて定期(週 1 回)に流す
- テンプレートの `gate-g5.yml` には入れない(R-1)
- `ci.yml` のジョブに `timeout-minutes` を置く。値は実測から決め、根拠水準を開示する

**理由**

- #311〜#318 の決定変更で新しく落ちた場面が、どれも気付かれなかったのは、変更のたびに流していなかったからである(内部調査 2.4。組A・組C の後に誰も流していない)。定期だけにすると、落ちた原因を変更へ結べなくなる
- 実行時間の長さは採否の理由にしない(コアポリシー)
- sweep は p302 で失敗 0、adapt の 68 件は時計だった。毎回の価値は他より低いが、回答の全組合せを見るのは sweep だけなので、構成の生成に触れる変更では省かない

**他の案を落とす理由**: 定期実行だけ(上記)。テンプレートの CI(知識ベースを作れない)

**既存との矛盾**: 無い。`scripts/check-ci-wiring.mjs` が、新しい検査が `check` から結線されていることを確かめる対象に入れる

## R-7 標準の側の規定

**結論**: 2 点だけを規定し、残りは**課さないと明記**する。新しい ADR で決める。

1. 規定する: 検証に数えるテストは、期待値・入力データ・試験の補助(偽の外部コマンド等)を含めて版管理下に置く。版管理の外にあるテストの結果を、検証に数えない
   - 根拠: 外部調査 A5(CMMI CM、NASA SWE-081、IEC 61508-3 6.2.3)と G(Fowler)。本標準は既に、生成に用いた指示・権限設定・ツールの一覧を版管理下に置かせている(第5章 5.8.6 要求2、安全の検証の表の 2、第3章のツールの一覧)。テストだけが明示されていない
   - 文の案(第5章 5.8.4 の末尾。本文): 「検証に数えるテストは、期待値・入力データ・試験の補助を含めて、版管理下に置かなければなりません。版管理の外で実行したテストの結果を、検証に数えません。」
2. 規定済みであることを明示する: 期待値の由来(5.8.4。人が承認した受入基準)と、テスト側の変更による失敗の解消の禁止(5.8.5 の禁止事項3)。期待値の更新の手続を新設する必要は無い。新設すると、5.8.4 と二重の正本になる
3. 課さない(明記する): 「落ちることを期待する」印の機構、隔離の件数・期限の上限、期待値の変更の機械による遮断
   - 理由: 印と隔離は、外部調査 D・C4 のとおりツールの実務であり、規格の要求は見つからなかった。期限を機械が落とす公式の仕組みも見つからなかった(外部調査 D の小括)。機械による遮断は 5.8.5 の直後の段落が退けている
   - 文の案(箇条書き。附属書か第5章の注記): 「既知の失敗の印、隔離の件数・期限の上限は課さない。印を付けた試験は、検証を弱める変更として独立レビューの確認事項に含める(5.8.5)」

**理由(擁護者として)**: 本件の発端は、本標準の作り手のリポジトリの運用の欠陥であり、採用者の側の欠陥の実証ではない。採用者への新しい義務は、外部の規範が一致して支える 1 だけに絞る。2・3 は、既存の条項で足りることと、課さないことを読み手が区別できるようにするために書く

**落とす案**: 第7章・附属書に「決定を固定する試験」の型を新設する案。採用者の決定(ADR)と試験の対応表を義務にする根拠は、外部調査 F3(修士論文 1 件)に限られ、規格の要求ではない。義務にするなら根拠水準マークが要り、実証の無い義務は信頼性を上げない。手引きとして例示するにとどめる

**既存との矛盾**: 1 は附属書H H.1 の「決定論的な検査を検証に数える条件」に条件を 1 つ足すことになる。H.1 と保証の開示の項目へ波及するため、同じ ADR で附属書H を突合する。附属書H の既存の条件(期待値が人の承認した受入基準に由来すること)とは矛盾しない
