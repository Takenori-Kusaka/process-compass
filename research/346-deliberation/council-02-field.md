# 会議体 #346 意見書 02: 現場(field)

- 立場: 個人・小さなチームで、GitHub の public/Free のリポジトリから配備・配布を運用する開発者
- 作成: 2026-10-27。読んだもの: issues-context.md、council-00-agenda.md、survey-346-1-internal.md、survey-346-2-external.md、gate-criteria.md G-8(L1190〜1197)、ci-gates.md「デプロイゲート」(L880〜925)、`.github/workflows/ci.yml` のジョブ publish(L123〜)、project-management.md L127
- 前提: 所有者の指示により、鍵(deploy key・秘密情報に置く長期のトークン)を設定する案は採らない。この前提は本リポジトリの運営への制約であり、**条項の採否の理由には使わない**(本リポジトリに合わせて規格を曲げない)
- 根拠の記号: 〔内〕= 内部調査、〔外〕= 外部調査、〔確〕= 自分でファイルを読んで確かめた、〔未〕= 調査に無く、自分でも一次資料で確かめていない(一般に知られた挙動として扱う)

## 0. 現場から見た問題の核

1. 小さなチームが gh-pages や配布用のブランチへ書く最も普通の形は、`GITHUB_TOKEN` にジョブの `permissions: contents: write` を付ける形です。今の G-8 の文のままでは、この形は全て「資格情報を秘密情報に置いていない」になります。しかも未達の扱いは「使えない場合」に限られ、public/Free で Environment の秘密情報を「使えるのに使わない」場合の扱いがありません〔内 1.1〕。結果は、規定を読んだ採用者が (a) 鍵を足す、(b) 黙って守らない、(c) 「使えない」と言い張って未達にする、のどれかです。(b)(c) は形骸化です
2. 一方、(a) の鍵を足しても、それだけでは何も守られません。配布先の参照へ書き込みの権限を持つ全員が直接 push できる限り(経路 B〔内 3.3〕)、鍵を Environment に置いても「誰が配布先を書けるか」は変わりません。守りが生じるのは、配布先の参照の更新をルールセットで鍵だけに限ったときです(#293 J-6 の裁定 b+d〔内 2.2〕)。鍵の管理(失効期限の無い deploy key の更新・漏えい時の無効化・リポジトリごとの登録)は、1人で回す現場では放置されやすく、放置された長期の鍵は短命のトークンより悪い状態です〔外 2.6: 短命 > 長期は指針の一致〕
3. 逆に、`GITHUB_TOKEN` の書き込みは参照に結び付かず、Environment もトークンを限りません〔外 1.2・1.4〕。ブランチにワークフローを置ける主体は、`permissions` を書くだけで書き込みに届きます。**この経路が問題になるのは、その主体が直接には持たない能力に届くときだけ**です。現場で実際に起きるのは次の場合です
   - 配備先がリポジトリの外(パッケージの公開、OIDC で入るクラウド、リリースの発行で利用者へ届く配布)
   - ブランチへ push できる主体の資格情報が、リポジトリ全体の書き込みより狭い場合(AI エージェントの資格情報が特定のブランチの接頭辞へ限られている、ワークフローのファイルを書く権限を外してある等)。ブランチにワークフローを置ければ、その狭さはトークンの側で外れます
   - 秘密情報(リポジトリの秘密情報)が同じジョブから読める場合

## R-1 条項は、ジョブの権限で発行される短命のトークンをどう扱うか

### 結論: 条件つきで認める。条件は「新しい能力を与えない」ことの3要件。「短命」は条件にしない

ジョブの権限で発行されるトークンで配備・配布することを、次の全てを満たす場合に限って認めます。満たさない場合は、資格情報を参照に限った実行環境の秘密情報に置くか、未達として記録します。

1. トークンで届く先が、ワークフローを置いたリポジトリの参照(ブランチ・タグ)の更新だけである。パッケージ・リリース・Pages・外部の配備先への発行、`id-token: write` による外部の資格情報の取得を含まない
2. そのリポジトリのブランチへ push できる全ての主体(人・AI エージェント・自動化)が、配布先の参照へ自分の資格情報で直接書ける。言い換えると、ブランチ上のワークフローは、起動した主体が既に持つ能力を超えさせない
3. 同じジョブから、配備・配布のための秘密情報を読めない

認めた場合も、**配布先を守ったことにはなりません**。配布先を書ける者の範囲は「ブランチへ push できる全員」であり、それを保証の開示に残存リスクとして書きます(R-2 の文の案)。

### 理由

- 条項の目的は、ブランチの書き換えで、起動者が持たない能力(配備・秘密情報・保護された参照の更新)に届かせないことです(ci-gates.md L899「書き込みの権限を持つ者は、自分のブランチへ置いたワークフローから、リポジトリの秘密情報とトークンの書き込みの権限に届きます」〔確〕)。要件 1〜3 を満たすとき、ブランチ上のワークフローは新しい能力を与えません。このとき「統制」(誰が配布先を書けるか)の実体は、リポジトリの共同作業者の一覧とルールセットであり、どちらもワークフローのファイルの外にあります。G-8 の禁止文「ブランチで書き換えられる場所の中**だけ**に置いてはならない」と矛盾しません
- 要件はどのプランでも判定できます。Free の非公開のリポジトリ(Environment の秘密情報と参照の限定が無い〔確 ci-gates.md 表〕)でも、要件 1〜3 は設定ではなく構成で決まります。プランで分岐しない規定は、現場で読み違えが起きにくい
- 要件 2 を「全ての主体」で書くのは、AI エージェントの資格情報を狭めている現場ほど、この経路で狭さが外れるためです。人の開発者だけを見て「全員 write だから同じ」とすると、エージェントの統制(第5章 5.8.6、第3章 3.5 の「認証情報(トークン)」の分離〔内 1.4〕)を、トークンの側から崩します

### 他の案を落とす理由

- **無条件で認める**: 要件 1〜3 を外すと、OIDC で外部へ入る配備、リリースの発行、狭い資格情報のエージェントによる昇格を素通りさせます。外部の指針は短命(OWASP CICD-SEC-6)と未レビューのコードに資格情報を渡さないこと(SEC-4・SEC-1・SEC-5)を別の要求として立てます〔外 2.1・2.6〕。短命は後者の代わりになりません
- **認めない(秘密情報の置き場だけを正とする)**: 現場で最も普通の形の全てを、鍵の追加か未達の記録へ追い込みます。鍵の追加は、ルールセットで更新を鍵だけに限らなければ守りを増やしません(0 節 2)。未達の記録は「直す道が鍵しかない」ため恒久化し、毎回の保証の開示に同じ行が並びます。信頼性の判断軸から見て、守りが増えないのに負担と記録の雑音だけが増える規定は採れません
- **「短命」を条件にする**: `GITHUB_TOKEN` は常に短命です〔外 1.1〕。条件にしても何も選別しません。逆に「短命なら良い」という誤読(短命で参照への結び付けの代わりにする)を生みます〔外 2.6: その根拠は見つからない〕。短命の利点は、要件を満たした後の付随の利点として注記に留めます

### 文の案(第4章 G-8「配備の統制と資格情報の置き場」へ追加。本文はですます調)

> ジョブの権限で発行されるトークン(GitHub の `GITHUB_TOKEN` など)は、起動元のブランチのワークフローの定義で権限が決まります。参照に限った実行環境の秘密情報には置けません。**このトークンで配備・配布してよいのは、次の全てを満たす場合に限ります**。満たさない場合は、資格情報を前項のとおり実行環境の秘密情報に置くか、保証の開示に未達として記録します。
>
> - トークンで届く先が、同じリポジトリの参照の更新だけであること(パッケージ・リリース・外部の配備先への発行と、外部の資格情報への交換を含まない)
> - ブランチへ push できる全ての主体(人・AI エージェント・自動化)が、配布先の参照へ自分の資格情報で直接書けること
> - 同じジョブから、配備・配布のための秘密情報を読めないこと
>
> 満たす場合も、配布先を書ける者は、ブランチへ push できる全ての主体です。**これを保証の開示に残存リスクとして書きます**。トークンが短命であることは、この条件の代わりになりません。委任の取り込み([第5章 5.5.4])は既定ブランチの保護を越える操作であり、この扱いの対象にしません。

### 既存の ADR・条項との矛盾

- G-8 の禁止文: 矛盾しない(統制の実体はファイルの外)。置き場の文「資格情報は…秘密情報に置きます」には例外の文が要るため、上の文で範囲を書く。採用済み ADR の本文は変えない
- 第5章 5.5.4(委任): 対象外と明記する。委任のマージのトークンは既定ブランチの保護を越えるため、要件 2 を満たし得ない〔確 G-8 L1192 の「委任…も同じです」〕
- 第5章 5.8.6・第3章 3.5: 要件 2 が AI エージェントの資格情報の狭さを守る方向で、整合する
- ADR-0028: 満たさない場合の未達の記録は同じ枠組み。矛盾なし
- ADR-0077 決定6 の開示「満たしません」: 新しい条項の下では本リポジトリが要件を満たす可能性がある(R-3)。ADR-0077 は書き換えず、新 ADR が開示の部分を置き換える

## R-2 認める場合、何が止めるか。語の定義

### 結論

1. ブランチ上のワークフローからの書き込みを止める手段を、GitHub の標準機能では持てない(public・個人所有・Free)。止めるのではなく、**昇格が起きない状態(R-1 の要件 2)を主体側で保つ**ことを統制とする
2. 主体側の統制として現場で使えるのは次の3つ。条項の本文には要件だけを書き、手段は ci-gates.md の対応表へ置く
   - AI エージェント・自動化に渡す資格情報から、ワークフローのファイルを書く権限を外す(GitHub の fine-grained のトークンの Workflows の権限、GitHub App の `workflows` の権限。外せば `.github/workflows/**` を変えるコミットを push できない)〔未: 一般に知られた GitHub の挙動。一次資料での確認が要る〕。外せないなら、その主体の資格情報を配布先へ直接書ける広さで扱う(要件 2 の判定)
   - リポジトリの Workflow permissions を read に置く。効くのは `permissions` を書かないワークフローだけ〔外 1.2〕。対応表に「上限ではない」と明記する
   - 配布先の参照に、削除と強制 push の禁止をルールセットで置く。早送りの更新は止めない〔内 2.1〕
3. 落とす手段と、その理由を対応表に明記する(課さないと決めたことの明記)
   - Environment の配備の参照の限定: ジョブを main 以外で走らせないことだけを止め、トークンを限らない〔外 1.4〕。配備の記録を残す用途に留める
   - `.github/workflows` の CODEOWNERS と必須レビュー: マージの関門で、ブランチ上の実行を止めない〔外 2.4〕。ソロでは自己承認しか無い
   - Restrict file paths: Enterprise Cloud の internal/private に限る〔外 1.5〕
   - ルールセットの Restrict updates: `GITHUB_TOKEN` をバイパスへ入れる公式の手段が無く、配布も止まる〔外 1.5・1.6〕
   - ワークフロー実行の保護(2026-09 GA): 起動する主体・イベントを限るが参照もトークンの権限も限らない〔外 1.7〕。個人所有の public で使えるか、新しいファイル名に及ぶかは未確認。要件の手段に数えず、対応表に「検討の余地。参照では限らない」と書く
   - 配備を別のリポジトリへ分ける: 別のリポジトリへ書くには結局資格情報が要る〔外 3〕。採用者の選択肢として例示に留め、要求しない
4. 語の定義は **G-8 の節の中**に置く。「資格情報」「秘密情報」「実行環境」はこの節と第5章 5.8.6 でしか規範に使われていない〔内 1.4〕。現場の読み手は G-8 を開いた場所で読み切りたい。1.4 の用語集へは G-8 を指す行だけを足す
5. IMPL-0237 の降ろし先 `deploy-workflow` の説明を、本文の範囲(既定ブランチ、またはリリースのタグ)へ合わせる〔内 1.1: 食い違い〕。加えて、本文に入れる R-1 の要件に新しい実装マークを付ける(降ろし先は R-4 のテンプレートの検査。`state=undelivered` から始める)

### 理由

- 外部調査の結論は「`GITHUB_TOKEN` の書き込みを参照で限る手段は確認できなかった」です〔外 5.2〕。止められない手段を「止める」と書けば、採用者は設定したことで守ったと誤認します。現場で一番危ないのは、効かない設定に安心することです(Environment `dist-standard` を作れば守れたと読む誤読は、ADR-0077 自身が否定している〔内 2.1〕)
- 主体側の統制(資格情報からワークフローの権限を外す)は、Free・public でも設定でき、AI エージェントを使う小さなチームの実際の昇格経路を直接止めます

### 文の案

G-8 の節の冒頭(本文):

> この節で、**資格情報**は、配備先・配布先へ書き込むための認証の手段をいいます。長期の鍵、秘密情報に置くトークン、ジョブの権限で発行されるトークン、外部の資格情報と交換するトークンを含みます。**秘密情報**は、ワークフローの定義の外に保管され、実行時に渡される値をいいます。**実行環境**は、参照ごとに秘密情報と実行を限れる配備の環境(GitHub の Environment など)をいいます。

ci-gates.md の対応表へ追加する行(体言止め):

| 本節の語 | GitHub の機能 | 注意 |
| --- | --- | --- |
| ジョブの権限で発行されるトークン | `GITHUB_TOKEN` と `permissions` | 参照に結び付かない。ブランチのワークフローで `permissions` を書けば書き込みを得る。Environment はこのトークンを限らない |
| トークンの既定の権限 | Workflow permissions | 既定であり上限ではない。`permissions` を書かないワークフローにだけ効く |
| 主体の資格情報の範囲 | fine-grained のトークン・GitHub App の Workflows の権限 | 外せば、その主体はワークフローのファイルを push できない。外せない主体は、配布先へ直接書ける主体として扱う |
| 起動の主体の限定 | ワークフロー実行の保護 | 起動する主体とイベントを限る。参照とトークンの権限は限らない。G-8 の要件の手段に数えない |

### 既存の ADR・条項との矛盾

- ADR-0071 決定3(判定の証跡は判定記録に限る): 対応表の設定の事実は判定の証跡にしない。矛盾なし
- ci-gates.md L899「ファイルの外の設定(実行環境の配備の参照の限定)だけが、この経路を止めます」: トークンについては誤り(限定はトークンを止めない)。「秘密情報への経路を止めます。トークンの書き込みの権限は止めません」へ直す必要がある。これは本文(ADR ではない)の訂正
- 「配布用のブランチの保護を独立の要求事項にしない」(ci-gates.md L921〜924): 維持する。削除・強制 push の禁止は対応表の手段であって要求事項ではない

## R-3 本リポジトリの配布

### 結論

1. 鍵は使わない(前提)。R-1 の条件つきの扱いを本リポジトリに当てはめ、**要件を満たすかを実設定で確かめてから**適合と書く。確かめるまでは未達として開示を続ける
2. 最優先は、#293 以降の変更をリモートの main へ入れ、旧 `publish-standard.yml` を消すこと。リモートでは今も、最上位 `contents: write`・Environment なし・強制 push・`workflow_dispatch` の旧ワークフローが配っており〔内 3.4〕、新旧どちらの条項にも、ADR-0077 の運営の形にも合っていません。条項の議論より先に、記録と実態の乖離を閉じる
3. 所有者が行う設定の一覧(入れる順。各項目に設定した日付と確かめた結果を Issue #346 に記録する)
   1. 作業ブランチを main へ取り込み、`publish-standard.yml` が main から消えたことを確かめる(取り込みは所有者の操作。取り消せない操作として扱う)
   2. Actions の Workflow permissions を read に置き、「GitHub Actions に PR の作成・承認を許す」を外す(画面で確かめる。API はこの環境で読めなかった〔内 3.4〕)
   3. Environment `dist-standard` と `github-pages` を、配布の最初の実行より前に作り、配備のブランチを `main` に限る(トークンは限らない。ジョブ publish を main 以外で走らせない用途と、配備の記録の用途)
   4. `dist/standard` にルールセットを置き、削除と強制 push を禁じる。Restrict updates は置かない
   5. 書き込みの権限を持つ主体の棚卸し: 共同作業者の一覧と、AI エージェント(クラウドのセッション、GitHub App)に渡している資格情報の範囲。この環境の `gh` のトークンは admin を持つ〔内 冒頭〕ため、エージェントは既に配布先へ直接書ける。要件 2 は満たすが、それはエージェントが広い権限を持つことの裏返しである(残存リスクとして開示)
4. EV-0137 の差し替え条件は、`GITHUB_TOKEN` の方式では意味を失っている。「既定ブランチ以外から起動した配布が拒まれた記録」は、Environment を参照するジョブ publish を拒むだけで、`environment:` を消したブランチのワークフローは拒まれません〔外 1.4〕。拒まれた記録を「規定が効いた」証拠として残すと誤った安心を作ります。EV-0137 の対象の文は新しい条項に合わせて書き直し、差し替え条件を変えるなら新しい EV 番号を起こす。本リポジトリで残す記録は次の2件とする
   - (a) main 以外から dispatch したジョブ publish が Environment で拒まれること(Environment の限定の確認)
   - (b) `environment:` を持たない試験のワークフローを作業ブランチに置き、使い捨ての参照(例: `probe/346`)へ push できてしまうこと(残存リスクの実在の確認)。**`dist/standard` そのものへは試さない**(配布の受け手を壊さないため)。試験の後に参照とブランチを消す(消すのは所有者)
5. 本リポジトリは「本標準に従う開発の案件ではない」〔内 2.3〕が、EV-0137 の検証の場として使っています。検証の場に使う以上、所有者の設定の記録は案件と同じ水準で残す

### 理由

- 本リポジトリの配布物の受け手は、準拠テンプレートの `template:kb` の複製とサイトです。受け手は配布物の版(`VERSION.md`)を信じて取り込むため、記録と実態の乖離(旧ワークフローの強制 push)は、条項の文言より実害に近い
- 条件つきの扱いを採っても、本リポジトリは要件 2 を「設定を読んで」判定する必要があります。現状は Environment と Actions の設定が読めていない〔内 5〕ため、適合とは書けません。読めない設定を適合と書くのは、テンプレートが env-check で禁じている形(AI が確認済みにしない)と同じ誤りです

### 他の案を落とす理由

- **鍵で条項に合わせる**: 前提により採らない。加えて、R-1 の 0 節 2 のとおり、ルールセットで更新を鍵に限らなければ守りは増えない
- **適用外として開示を続けるだけ**: 新しい条項の下で要件を満たし得るのに、未達の記録を固定すると、採用者に「この形は満たせない」と誤って伝えます。逆に、確かめずに適合へ切り替えるのも採らない(結論 1)
- **旧ワークフローを残したまま条項を先に直す**: 記録と実態の乖離が続き、EV の材料も取れない

### 文の案(新 ADR の決定。体言止め)

- 本リポジトリの配布は、G-8 のジョブの権限で発行されるトークンの扱いの要件で判定する。要件 2 は、書き込みの権限を持つ主体の棚卸しの記録で判定する
- 設定の記録(Issue #346)が揃うまでは、保証の開示に未達として残す
- `dist/standard` を書ける者は、リポジトリへ push できる全ての主体である。これを残存リスクとして開示する

### 既存の ADR・条項との矛盾

- ADR-0077 決定6(「満たしません」「#293 で別に扱う」): 書き換えない。新 ADR で「#346 で扱い、決定6 の開示を置き換える」と書く
- project-management.md「管理者の設定」手順3(main 以外から publish が走らないことを確かめた結果を #293 に記録): 記録の先を #346 へ移し、(a)(b) の2件に改める(本文の訂正)
- EV-0137: 本文の EV の文の書き直しと、新しい EV 番号の起票(識別子は再利用しない)

## R-4 採用者とテンプレート

### 結論

1. 標準(ci-gates.md): R-2 の対応表の行を足し、「`GITHUB_TOKEN` で配布用のブランチへ書く」形の判定の手順(要件 1〜3 を確かめる順)を例として書く
2. テンプレート: **デプロイのワークフローは同梱しない**。配備先は採用者ごとに違い、雛形は「そのまま使って要件を満たしたつもりになる」形骸化を生むため
3. テンプレートのワークフローの最上位の書き込みの権限(`pull-requests: write`・`statuses: write`・`issues: write`)を、それを使うジョブへ下ろす。テンプレート自身の検査に「最上位で書き込みを与えない」を足し、違反で失敗させる(本リポジトリの check-ci-wiring 条件5 と同じ規則)
4. `adoption-trial.mjs env-check` に、Actions の Workflow permissions(`GET /repos/{o}/{r}/actions/permissions/workflow`)と Environments の一覧・配備の参照の規則(`GET /repos/{o}/{r}/environments`)の読み取りを足す。読めない(403)ときは「未確認」と出し、通過にしない。AI エージェントの資格情報の範囲は API では読めないため、採用者が記入する欄(誰が・どの資格情報で・Workflows の権限の有無)にする
5. G-8 の要件 1〜3 の記入欄を、保証の開示(層1 の受容の対象)へ足す。記入するのは人

### 理由

- 最上位の書き込みは、その権限を要らないジョブにも渡ります。`delegation.yml` は `pull_request_target` を契機に持ち〔内 4〕、最上位の `pull-requests: write` は判定のジョブにも渡る。外部から来る PR の文脈で書き込みの権限を持つジョブを減らすことは、外部の指針(OWASP CICD-SEC-5「必要な分だけ」、GitHub Secure use「ジョブ単位で必要な分だけ上げる」、Scorecard Token-Permissions)と一致します〔外 2.1・2.4・2.5〕
- env-check は今、ブランチ保護とルールセットだけを読みます〔内 4〕。条件つきの扱いを入れるなら、採用者が要件を確かめる道具が要る。現場では「画面を見て確かめる」は続きません。読めるものは機械で読み、読めないものは欄にして空欄を `/pit` に出す、が続く形です
- Workflow permissions の API は管理者の権限を要する〔未: 一般に知られた GitHub の API の要件〕。読めないことを「設定が無い」と扱わない(template-repository.md L114 の注意と同じ〔内 1.4〕)

### 他の案を落とす理由

- **テンプレートに `GITHUB_TOKEN` の配備の雛形を入れる**: 要件 2 は採用者の主体の構成で決まり、雛形では満たせない。雛形の存在が適合の証拠のように読まれる
- **最上位の権限を残し、注記だけにする**: 注記は読まれず、同じ構造(ブランチ上のワークフローから書き込みに届く)が残る
- **env-check の結果を G-8 の判定の証跡にする**: ADR-0071 決定3 に反する。env-check は保証の開示の材料に留める

### 文の案(テンプレートの README・`/artifact` の補助ファイル。体言止め)

- 配備・配布にジョブの権限のトークンを使うときは、第4章 G-8 の3つの要件を保証の開示へ記入する。記入は人
- AI エージェント・自動化に渡す資格情報は、ワークフローのファイルを書く権限を外す。外せない場合は、その主体を配布先へ直接書ける主体として数える
- `env-check` が「未確認」を出した設定は、確かめるまで未確認として残す。AI が確認済みにしない

### 既存の ADR・条項との矛盾

- ADR-0040(テンプレートの様式は必須欄の存在だけを検査): 保証の開示へ欄を足すなら `template-fields.yaml` に登録する。矛盾なし
- テンプレートの CLAUDE.md の禁止事項6(閾値・除外設定を機能変更と同じ PR で変えない): ワークフローの権限の変更は単独の PR で行う。矛盾なし
- IMPL-0236(委任のマージは Environment の秘密情報): 変えない。R-1 の扱いの対象外

## R-5 記録

### 結論

1. 新 ADR(番号は採番時に決める)を起こし、ADR-0077 決定6 の「#293 で別に扱う」を受けて、開示の部分を置き換える。ADR-0077 の本文は書き換えない
2. 新 ADR の「経緯」に、方式の変更(コミット b185611)が調査・会議体・突合を経ずに入った事実を書く。理由は「所有者の指示による制約」と明記し、熟議の結論と区別する
3. 所有者の指示は、要旨(「鍵を設定しない。GitHub Actions のジョブの権限で行う。配布先の更新の制限は緩める」)を「所有者の指示(2026-10-23)」として公開の記録に書く。原文の引用を公開するかは所有者が決める。「保守者の決定」とだけ書く今の形は、熟議の結論か制約かを読み手が区別できません
4. `research/293-deliberation/implementation.md` は書き換えず、末尾に日付つきの追記を置き、deploy key 方式から変わったことと、この会議体の記録への参照を書く

### 理由

- 「書かれていない」と「課さないと決めた」を区別する、が本プロジェクトの方針です。同じく「熟議で採った」と「制約で採った」の区別も、採用者が自分の案件へ当てはめるときに要ります。制約で採った形を、採用者は「標準の推奨」と読みかねません
- 現場の目では、手順を経ずに入った変更の記録が残っていないことが、後から一番困ります(なぜこの形かを誰も説明できない)。事実だけを短く残せば足ります

### 他の案を落とす理由

- **ADR-0077 を改訂する**: 採用済み ADR の本文は書き換えない規約に反する
- **記録を Issue のコメントだけに置く**: Issue は検索で辿りにくく、ADR から引けない
- **所有者の発言の原文を、所有者の判断なしに公開の記録へ載せる**: 公開の記録へ何を出すかは所有者が決めることで、会議体が決めない

### 既存の ADR・条項との矛盾

- ADR-0077: 置き換えの関係を新 ADR に書く。本文は変えない。矛盾なし
- CLAUDE.md(コアポリシー: 取り込みの前に議論する): b185611 がこれを経ていない事実の記録は、ポリシーに沿う
