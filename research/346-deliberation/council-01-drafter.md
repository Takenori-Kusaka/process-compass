## R-1 条項は、ジョブの権限で発行される短命のトークンをどう扱うか

### 結論

**短命であることを条件に認める案と、目的を「起動者が持たない能力への到達」に読み直す案は、どちらも採らない**。条項の判断の軸を「短命か長期か」ではなく「**資格情報が、配備を許す参照に結び付いて得られるか**」に置き直し、次の3点を起案します。

1. 置き場の規定を、秘密情報の1形態から、**参照に結び付いた資格情報の2形態**に広げる。(a) 配備を許す参照に限った配備の環境の秘密情報、(b) 発行の際に、発行者または受け手が実行の参照・配備の環境を検証する短命の資格情報(OIDC の `sub` を検証する受け手が典型。GitHub Pages の deploy-pages が先例)
2. **ワークフローのファイルの権限の宣言だけで発行されるトークン(GITHUB_TOKEN の `permissions`)は、(a)(b) のどちらにも当たらない**ことを明記する。配備先への書き込みにこれを用いる構成は、規定を満たさない
3. 満たさない場合の扱い(未達の記録)を、「手段を使えない場合」から「**手段を使わないと決めた場合**」にも広げ、未達の理由の区分と開示の中身を定める。開示の中身に「開いたままの経路を持つ主体」と「その主体が配備先へ直接書き込めるか」を入れる

### 理由

- 条項の禁止(第1文)の対象は「統制と資格情報を、起動元のブランチで書き換えられる場所の中だけに置く」ことです。GITHUB_TOKEN の書き込みの権限は、ワークフローのファイルの `permissions` から生じ、起動元のブランチのファイルが使われます [外 1.2・1.3]。Workflow permissions は出発点で、上限とする記述はありません [外 1.2 の推論]。Environment は GITHUB_TOKEN の権限を限りません [外 1.4]。したがってこのトークンは、**禁止の文がそのまま当たる「ファイルの中だけに置いた資格情報」**です。条項を変えずに読んでも満たしません [確: G-8 本文]
- 指針は「短命」(OWASP CICD-SEC-6、CISA/NSA)と「未レビューのコード・設定を走らせる文脈へ資格情報を渡さない」(CICD-SEC-4・SEC-1・SEC-5、GitHub Secure use)を別々の要求として立てます。短命で後者を代える根拠は見つかっていません [外 2.1・2.6]。短命は漏えい後の悪用の期間を縮めますが、「誰が発行させられるか」を変えません。SLSA v1.2 の Trusted Robot の定義(codebase を一者で左右できない)にも当たりません [外 2.2]
- 一方、今の第2文は「秘密情報に置く」に限るため、**参照に結び付いた短命の資格情報(OIDC + 受け手の検証)を満たす形として読めません**。指針が最も推す形(短命かつ参照に束縛)を規定が排除しているのは、規定の側の欠陥です [外 1.8・2.4]。本リポジトリの deploy ジョブ(Pages、`id-token: write`、Environment `github-pages`)はこの形で、現行の文では判定できません [確: ci.yml の構成は内 3.1]
- 「起動者が持たない能力への到達」への読み直しを採らない理由: (1) G-8 の統制の対象は「配備を許す参照以外から配備先へ届くこと」で、到達の主体が誰かではありません。起動者が自分の権限で配備先へ直接書き込めるなら、それは**配備先の保護が欠けている**状態であり、トークンが新しい能力を足さないことは充足の理由になりません。(2) 本標準では AI エージェントのセッションが作業ブランチへ push する書き込みの主体です。読み直すと、AI の書き込みの権限の範囲がそのまま配備の範囲になり、「取り消せない操作は人へ戻す」(第5章 5.5.1 (c))の歯止めを配備の層で失います [確: テンプレート CLAUDE.md]。(3) GitHub では、配備先の参照をルールセットで保護すると、その保護はトークンにも同じく掛かり、GITHUB_TOKEN をバイパスに入れる公式の手段がありません [外 1.5・1.6]。つまり同じリポジトリの参照への配備では、「人には保護され、トークンには保護されない」形は作れず、「人にもトークンにも保護されない」か「配備も止まる」の二択になります。読み直しの条件を満たす構成は、常に配備先の保護が無い構成です
- ただし読み直しの論点が指す事実(トークンが起動者の権限を超えない構成がある)は、**開示の中身として価値があります**。未達の開示に「開いた経路を持つ主体の集合が、配備先へ直接書き込める主体の集合と同じか」を書かせれば、読み手が残存リスクを評価できます。充足の条件ではなく、開示の項目へ置きます
- 「使わないと決めた」場合を未達へ入れる理由: 今の文は「使えない場合」だけを未達とし、使えるのに使わない場合が書かれていません [内 1.1・6.2]。書かれていない状態は、読み手には「省略」と「課さないと決めた」の区別がつきません(ADR-0028 の趣旨に反する)。不適合を隠さず未達として記録させる方が、信頼性の軸に合います。ただし理由の区分を分け、決めた者を記名させ、AI の名義を禁じます(第5章 5.5 の「緩める向きの変更を AI が決めない」と整合)

### 落とす案

| 案 | 落とす理由 |
| --- | --- |
| 短命なら認める | 指針は短命と参照への束縛を別要求とする。誰が発行させられるかを変えない [外 2.6] |
| 同じリポジトリへの書き込みで、起動者の権限を超えない場合は認める | 充足の条件を満たす構成が「配備先が保護されていない構成」と一致する(上記)。条項が守る対象(配備を許す参照以外からの配備)を守らないまま適合を主張させる |
| 条項を変えず、GITHUB_TOKEN に触れない | 採用者の大半が使う形(GITHUB_TOKEN の `contents: write`、`packages: write`)が、満たすのか未達かを本文から決められない状態が続く [内 1.4] |
| OIDC の形を加えない | 指針が最も推す形を規定が排除する。Pages の配備が判定できない |

### 文の案(第4章 G-8「配備の統制と資格情報の置き場」の置き換え)

> **配備・配布の統制と資格情報を、起動元のブランチで書き換えられる場所(ワークフローの定義のファイルなど)の中だけに置いてはなりません**。その場所の中の確認は、起動元のブランチで書き換えれば外れるためです。配備の資格情報は、次のどちらかの形で得ます。
>
> - 配備を許す参照(既定ブランチ、またはリリースのタグ)に限った配備の環境の秘密情報
> - 発行の際に、発行者または受け手が、実行の参照または配備の環境を検証して発行する短命の資格情報(受け手がその検証を行う場合に限る)
>
> **ワークフローのファイルの権限の宣言だけで発行されるトークンは、短命であっても、どちらの形にも当たりません**。発行の可否が起動元のブランチのファイルで決まるためです。このトークンで配備先へ書き込む構成は、この規定を満たしません。参照する配備の環境は、参照する前に作り、保護を設定します。委任の取り込み([第5章 5.5.4])に用いる資格情報も同じです。
>
> 次の場合は、この規定を満たせません。**満たしたものとして扱わず、保証の開示に未達として記録します**([ADR-0028])。
>
> - 契約の条件などにより、配備の環境の秘密情報・配備の参照の限定・参照を検証する受け手を使えない場合(区分: 手段なし)
> - 使えるが、組織が使わないと決めた場合(区分: 不採用。決めた者を記名する。AI の名義を書かない)
>
> 未達の記録には、次を書きます。
>
> - 開いたままの経路(起動元のブランチの書き換えで配備先へ届く経路)
> - その経路を持つ主体(書き込みの権限を持つ人・AI エージェント・自動化の主体)と、その主体が配備先へ直接書き込めるかどうか
> - 経路を狭める措置と、その措置が止めないもの

- 「短命の資格情報を優先する」は要求事項にせず、ci-gates.md の理由の節へ置く(長期の鍵の禁止は、所有者の指示の対象であって標準の規範ではない。標準は長期の鍵を Environment に置く形も (a) として認め続ける)
- 根拠水準: 新しい EV を付ける(EV 番号は採番時。現時点の最大は EV-0183 [確])。対象=OIDC の形を充足に含めること、GITHUB_TOKEN を不充足と明記すること、不採用の区分。根拠 E1(間接。GitHub 一次文書と OWASP・SLSA)。差し替え条件=GITHUB_TOKEN の `permissions` に参照の束縛が入る GitHub の変更(2026 ロードマップには無い [外 1.7])、または OIDC の受け手が参照の検証を省いていた事例

### 既存との突合

- ADR-0077 決定6 の「標準:」の段落(置き場は秘密情報)を広げるため、**一部置き換え**に当たる(R-5)。ADR-0028(未達と省略)とは整合し、むしろ「不採用」の区分で省略との混同を減らす
- 第5章 5.5.4・IMPL-0236(委任のマージの Environment の秘密情報)は (a) に当たり、変更なし

## R-2 何が止めるか。語の定義

### 結論

1. **GitHub の標準機能に、GITHUB_TOKEN の書き込みを参照で限る手段は無い**と ci-gates.md に明記する。Workflow permissions・ルールセット・CODEOWNERS・ワークフロー実行の保護・Environment は、**未達の経路を狭める措置**として対応表に並べ、充足の手段に数えない
2. 語の定義を第1章 1.4 に3語足す: 「配備の資格情報」「配備の環境」「参照に結び付いた資格情報」。一般語の「資格情報」は定義しない(G-5 基準7・3.5・5.8.6 が別の範囲で使っており、一般の定義はそれらの範囲を動かす)
3. IMPL-0237 と `impl-targets.yaml` の `deploy-workflow` の説明を、本文の範囲(既定ブランチ、またはリリースのタグ)と2形態に合わせる

### 理由

- 止める候補の各々の限界は外部調査で一次文書から確かめられています [外 3 の表]。Workflow permissions は既定値で、`permissions` の明示で上がる(上限とする記述は無い。**推論であり実機で未確認**)。ルールセットの更新の制限はトークンも止め、配備も止める。`Restrict file paths` は Enterprise Cloud の internal/private に限る。CODEOWNERS はマージの関門で、ブランチ上の実行を止めない。ワークフロー実行の保護は主体・イベントを限り、参照を限らない [外 1.5〜1.7・2.4]
- 「止める手段がある」と書けば、採用者は狭める措置を充足と誤読します。手段が無いことを明記し、狭める措置を未達の開示の項目(R-1 の第3項)へ結び付けるのが、表の目的に合います
- 別のリポジトリへ配備を分ける案は、配布先のリポジトリへ書く資格情報が結局要るか、配布先が取りに行く設計が要ります [外 3]。後者(取りに行く側が参照を検証する)は (b) の変形で、充足し得ます。対応表の「充足の形」に入れます
- 1.4 に置く理由: G-8 は第4章、対応表はフェーズ5、IMPL の説明はデータで、3か所が同じ語を使います。節の中で局所に定義すると、ci-gates.md・impl-targets.yaml が定義を引けません

### 文の案

第1章 1.4 用語の定義(追加):

| 用語 | 定義 |
| --- | --- |
| 配備の資格情報 | 配備・配布の先へ書き込む権限を、配備の処理に与えるもの。鍵・トークン・ワークフローの権限の宣言で発行されるトークンを含む |
| 配備の環境 | 配備の処理が参照し、参照できる起動元の参照・承認・秘密情報を、ワークフローの定義の外で設定する単位(GitHub の Environment など)。AI エージェントの実行環境(第5章 5.8)とは別の語である |
| 参照に結び付いた資格情報 | 配備を許す参照からの実行にだけ得られる配備の資格情報。参照を限った配備の環境の秘密情報と、発行の際に参照または配備の環境を検証して発行する短命の資格情報の2つ(第4章 G-8) |

ci-gates.md「統制と資格情報の置き場」の理由の段落(L899)の末尾の文の置き換え:

> ファイルの外の設定だけが、この経路を止めます。ただし、**ワークフローの権限の宣言で発行されるトークン(GitHub の `GITHUB_TOKEN`)の書き込みの権限は、ファイルの外のどの設定でも参照に限れません**。このトークンで配備先へ書き込む構成は、第4章 G-8 を満たさず、未達として記録します。長期の鍵より短命の資格情報を優先することは推奨しますが、短命であることは参照への結び付きの代わりになりません。

対応表(追加の行):

| 本節の語 | GitHub の機能 | 注意 |
| --- | --- | --- |
| 参照を検証する短命の資格情報 | OIDC(`id-token: write`)と、`sub` クレームの参照・環境を検証する受け手。GitHub Pages の配備(`actions/deploy-pages`)は受け手が検証する | 受け手が検証しない場合は当たらない。同じリポジトリのブランチへの push には、検証する受け手が無い |
| ジョブの権限で発行されるトークン | `GITHUB_TOKEN` とワークフロー・ジョブの `permissions` | **参照に結び付かない**。Environment を参照するジョブでも、権限は Environment に属さない。`environment:` を消した同じジョブは、規則を通らずに同じ権限を得る |
| 経路を狭める措置(充足の手段ではない) | Workflow permissions を read に / `.github/workflows` の CODEOWNERS / ワークフロー実行の保護(起動する主体・イベントの許可) / 配備先の参照のルールセット(削除・強制 push の禁止) | Workflow permissions は既定値で、`permissions` の明示による引き上げを止めない(推論。実機で未確認)。CODEOWNERS はマージの関門で、ブランチ上の実行を止めない。ワークフロー実行の保護は参照を限らない。ルールセットの更新の制限は、`GITHUB_TOKEN` をバイパスに入れられないため配備も止める。`Restrict file paths` は Enterprise Cloud の internal・private に限る |

- 「2026-10-27 時点の GitHub Docs に基づく。実機では確かめていない」を表の前置きの日付に反映する
- 「Workflow permissions は上限ではない」は推論で、EV を付ける(差し替え条件=組織の restricted 既定で `permissions` の明示が拒まれる記録)

IMPL-0237 の note と `impl-targets.yaml` の `deploy-workflow` の description:

> 配備の資格情報を、参照に結び付いた資格情報(配備を許す参照=既定ブランチ、またはリリースのタグに限った配備の環境の秘密情報、または参照を検証する受け手が発行する短命の資格情報)から得る。ワークフローの権限の宣言で発行されるトークンで配備先へ書き込む場合は、保証の開示へ未達(区分と開いた経路・主体)を記録する。

### プランの制限

- 現行どおり。Free の非公開では Environment の秘密情報・参照の限定が使えず「手段なし」の未達 [確: ci-gates 対応表]。OIDC の受け手の検証は、受け手(クラウド・Pages)の側の機能で、リポジトリのプランに依らない。ただし `github-pages` 環境の参照の限定はプランに依る(起案者は確かめていない [未])

### 既存との突合

- ci-gates.md L921〜924「配布用のブランチの保護を独立の要求事項にしない」は維持。今回の定義は「配備の資格情報」を足すだけで、「配布物」を定義しない
- ADR-0071 決定3(判定の証跡は判定記録に限る)と整合: 狭める措置の設定の事実は判定の証跡にしない

## R-3 本リポジトリの配布

### 結論

1. **条項に合わせず、未達(区分: 不採用)として開示を続ける**。決めた者は保守者(記名)。ADR-0077 決定6 の「#293 で別に扱う」は、新しい ADR(R-5)で「規範の側を R-1 の形に直し、運営の側は不採用の未達として残す」と決着させる
2. 鍵を使わずに充足する唯一の経路(参照を検証する受け手を持つ配布路。例: Pages の成果物として配る、配布の受け手の側が main の実行の証明を検証して取りに行く)は、**受け手(準拠テンプレートの `template:kb` と submodule の利用者)の公開インタフェースを変える**ため、本 Issue では決めず、別の Issue を起票して所有者の判断へ回す
3. リモートの実状は、ADR-0077 が前提とした状態より悪い。所有者が行う設定の一覧を確定し、設定の記録を Issue #346 に残すまで、「開いた経路」の記述をリモートの実状に合わせて書く
4. EV-0137 の差し替え条件を直す。「既定ブランチ以外から起動した配布が拒まれた記録」は Environment を参照するジョブの経路しか試さず、GITHUB_TOKEN の経路の閉塞を示さない

### 理由

- 鍵を置かない前提で、同じリポジトリのブランチへの push を参照に結び付ける手段は無い [外 0.3・1.8]。条項に合わせるには配布路そのものを変えるしかなく、それは submodule で `dist/standard` を固定する採用者の取り直しの経路(履歴から旧版を取れる。ADR-0077 決定6・project-management.md [確])を変えます。人へ戻す (b)「公開インタフェース・データ形式を変える選択」に当たります
- 不採用の未達として開示する方が、適用外とするより信頼性が高い。「本リポジトリは本標準に従う開発の案件ではない」は ADR-0077 が既に書いていますが、適用外と書くと規範を書いた側が規範の検証の場を手放します。EV-0137 の差し替えの材料も本リポジトリの配布に依っています [確: ci-gates L913〜919]
- 本リポジトリの開示の中身(R-1 の第3項)は、主体の集合が「書き込みの権限を持つ者=ソロ期の保守者1名と、保守者の資格で push する AI のセッション」で、どちらも `dist/standard` へ直接書き込めます(ルールセットに更新の制限が無い)[内 3.3・3.4]。トークンは新しい能力を足しませんが、配備先は保護されていません。これをそのまま書きます
- リモートの実状 [内 3.4]: #293 以降の変更はリモートの main に未反映。旧 `publish-standard.yml`(最上位 `contents: write`、Environment なし、強制 push、`workflow_dispatch`)が動いており、ルールセットは空、`main` も `dist/standard` も保護なし。ADR-0077 の「止まらない経路」は新しい ci.yml を前提に書かれ、今動いている形(強制 push で履歴が消える)を書いていません。ここは開示の誤りで、未達の記録の前に直す対象です

### 所有者が行う設定の一覧(起案。順序つき)

1. work/346 までの変更をリモートの main へ入れ、旧 `publish-standard.yml` と `deploy.yml` が消えたことを確かめる(作業ツリーの `.github/workflows/` は ci.yml・evidence-review・graphify-update・link-check の4本 [確])
2. 入れる前に、Environment `dist-standard` を作り、Deployment branches and tags を `main` だけにし、管理者の迂回を許さない(public のため Free でも可 [外 1.4])。`github-pages` も同じく `main` に限る
3. `dist/standard` にルールセット: 削除の禁止・強制 push の禁止。更新の制限は置かない(置けば配布も止まる)
4. Settings → Actions → Workflow permissions を read(restricted)にし、「Allow GitHub Actions to create and approve pull requests」を無効にする(狭める措置。充足ではない)
5. ワークフロー実行の保護で、`push`・`workflow_dispatch` を起動できる主体を限れるかを評価する(個人所有の public で使えるかは未確認 [外 4])。限れる場合でも充足には数えない
6. 設定した日付、各設定の画面または API の応答、`main` 以外から起動したジョブ `publish` が Environment で拒まれた記録を Issue #346 に残す(project-management.md 手順3 の宛先 #293 を #346 へ改める)

### 文の案(ci-gates.md EV-0137 の本文の置き換え。ADR ではないので書き換えてよい)

> 機序は GitHub の一次文書から導けます。この要求事項で迂回が減った効果は、測られていません。本リポジトリの配布(`dist/standard`)は、ワークフローの権限の宣言で発行されるトークンで書き込むため、この規定を満たさず、未達(不採用)として開示しています([ADR-0090])。本リポジトリで残す記録は、Environment `dist-standard` を参照するジョブが既定ブランチ以外から拒まれた記録です。**この記録は、Environment を参照しないワークフローの経路が閉じたことを示しません**。

- 差し替え条件の文(「拒まれなければ本文を直します」)は維持する。拒まれなければ Environment の機序の記述が誤りで、本文を直す必要があるため

### 既存との突合

- ADR-0077 決定6 の運営の段落(GITHUB_TOKEN だけ、鍵を作らない、ルールセットは削除・強制 push)と一致。ADR-0077 の開示(L70)は「規範の側か運営の側かを決めない」としており、新しい ADR が決める
- project-management.md「止まらない経路」に、リモートの実状(旧ワークフローの強制 push)の行と、未達の区分を足す必要がある(本文の編集。ADR ではない)

## R-4 採用者とテンプレート

### 結論

1. 採用者が GITHUB_TOKEN で配備する場合の扱いは、R-1・R-2 の文で決まる(未達、区分と開示の中身)。ci-gates.md の対応表がその指針の所在
2. 準拠テンプレートの `adoption-trial.mjs env-check` に、**Actions の既定の権限(`actions/permissions/workflow` の `default_workflow_permissions` と `can_approve_pull_request_reviews`)と、`delegated-merge` の Environment の配備の参照の限定**を読む項目を足す。読めない場合は「未確認」と出す(ルールセットの `bypass_actors` と同じ扱い。template-repository.md L114 [内 1.4])。新しい IMPL を `state=undelivered` で付け、実装は別 Issue
3. テンプレートの workflows の最上位の書き込みの権限(`pull-requests: write`・`statuses: write`・`issues: write`)を**ジョブ単位へ下ろす**。本リポジトリの check-ci-wiring 条件5 と同じ形の検査をテンプレートにも置く。別 Issue
4. テンプレートにデプロイのワークフローの雛形は**置かない**(IMPL-0237 は undelivered のまま)。配備先が案件ごとに違い、(b) の受け手の検証は配備先に依るため、雛形が誤った充足の印象を与える

### 理由

- `can_approve_pull_request_reviews` が有効だと、`pull-requests: write` を持つブランチ上のワークフローが github-actions の名義で PR を承認できます。その承認が必須レビューの数に入るかは、起案者は確かめていません [未]。入るなら、委任の取り込み(5.5.4)と独立レビューの前提が、ブランチの書き換えで外れます。少なくとも無効を確かめる項目は要ります
- 最上位の書き込み → ジョブ単位: OpenSSF Scorecard の Token-Permissions が推す形 [外 2.5]。GitHub Secure use も同じ [外 2.4]。テンプレートの最上位の `pull-requests: write` は、本件と同じ構造(ブランチ上のワークフローから同じ権限に届く)を持ちます [内 4]。ジョブ単位にしても届く経路は消えませんが、権限を要しないジョブ(判定・集計)にまで書き込みを配らないことで、注入や依存の悪用の被害の範囲を狭めます
- env-check は採用者が実環境で人の名義で実行する確認です(テンプレート CLAUDE.md「AI が確認済みにしない」[確])。読む項目を足しても、AI が充足を宣言する経路は増えません

### 文の案(ci-gates.md の準拠テンプレートの段落、L911 の後ろへ追加)

> 準拠テンプレートは、配備先へ書き込む権限(`contents: write`・`packages: write`・`pages: write` など)をどのワークフローにも付けません。案件がデプロイのワークフローを足すときは、第4章 G-8 の2つの形のどちらかで資格情報を得ます。ワークフローの権限の宣言で発行されるトークンで書き込む場合は、未達として、区分・開いた経路・経路を持つ主体を保証の開示に記録します。導入前の検証(`adoption-trial.mjs env-check`)は、Actions の既定の権限と、Actions による PR の承認の可否を読みます。

### 既存との突合

- IMPL-0236(委任のマージ、Environment の秘密情報)は (a) に当たり維持
- template-fields.yaml(様式の必須欄)・ADR-0040 には触れない
- テンプレートの変更は pit-in-template の規約(`.claude/**` 以外、`.github/workflows` の変更は PR 経由、強制層の縮小ではない)に反しない。最上位→ジョブ単位は権限の縮小であり、統制の弱化ではない

## R-5 記録

### 結論

1. **新しい ADR(仮番号 ADR-0090「ジョブの権限で発行されるトークンと配備の資格情報の置き場」)を起こす**。ADR-0077 のステータスを「一部置き換え(→ ADR-0090 の決定1)」にし、両側が互いを指す状態にする(adr/index.md 規則3・5 [確])
2. 方式の変更(b185611)が会議体・突合を経ていない事実を、ADR-0090 の「コンテキスト」に事実として書く。`research/293-deliberation/implementation.md` は書き換えず、末尾に「この記録の後、b185611 で方式を変えた。審議は #346」の追記の段落だけを足す
3. 公開の記録の所有者の指示は「保守者の決定(2026-10-23)」の表記を維持し、**決定の中身**(鍵を設定しない、ジョブの権限で書き込む、ルールセットの更新の制限を置かない)を ADR-0090 に列挙する。所有者の発言の逐語は research/ にだけ置く

### 理由

- ADR-0077 決定6 の「標準:」の段落は「資格情報は…秘密情報に置きます」を決定の中身として持ちます [確: ADR-0077 L72]。R-1 はこれを2形態へ広げ、未達の区分を足すため、範囲の明確化ではなく決定の一部の変更です。ADR-0077 自身が ADR-0033 との関係で「置き換えではなく明確化」と書き分けた先例があり [確: L44]、今回はその基準で置き換えに当たります。運営の段落(GITHUB_TOKEN だけ)は置き換えません
- 会議体を経ない変更の事実を書かないと、読み手は ADR-0077 決定6 の方式が審議を経たと誤読します。CLAUDE.md のコアポリシー(取り込みの前に議論する)に照らし、逸脱を記録することが是正の一部です
- 所有者の発言の逐語を公開の ADR に入れる必要はありません。判断の根拠として読み手が要るのは決定の中身と、それが鍵を禁ずる運営上の制約であって標準の規範ではないことです

### 文の案(ADR-0090 の決定の骨子)

- 決定1(標準): G-8 の置き場の規定を「参照に結び付いた資格情報」の2形態へ改める。ワークフローの権限の宣言で発行されるトークンは、短命であってもどちらにも当たらない。未達に「不採用」の区分を足し、開示の中身(開いた経路・経路を持つ主体と直接の書き込みの可否・狭める措置と止めないもの)を定める。ADR-0077 決定6 の「標準:」の段落を置き換える
- 決定2(標準): 1.4 に「配備の資格情報」「配備の環境」「参照に結び付いた資格情報」を定義し、G-8 と ci-gates の「実行環境」を「配備の環境」に改める。一般語の「資格情報」は定義しない(課さないと決めた)
- 決定3(標準): ci-gates の対応表に OIDC・ジョブの権限のトークン・狭める措置の行を足し、狭める措置を充足に数えない
- 決定4(運営): 本リポジトリの配布は GITHUB_TOKEN のまま、未達(不採用、決めた者=保守者)として開示する。配布路を変えて充足する案は、受け手のインタフェースを変えるため別 Issue で所有者が判断する。所有者の設定の一覧と記録の宛先(#346)を project-management.md に置く
- 決定5(テンプレート): env-check に Actions の既定の権限と PR の承認の可否を足す。最上位の書き込みの権限をジョブ単位へ下ろす。デプロイの雛形は置かない(課さないと決めた)
- 検討した選択肢: 短命なら認める / 起動者の権限を超えなければ認める / 条項を変えない / 適用外とする / 配布路を Pages へ移す(別 Issue へ) / 1.4 に一般語「資格情報」を定義する — それぞれ R-1〜R-4 の落とす理由を書く
