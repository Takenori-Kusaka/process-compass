## 1. 指摘

### X-1(高)(a) を用いても、配備先が結び付かない資格情報から書ける構成を、G-8 が未達にしていない

- 所在: `phase4-process-design/gate-criteria.md` G-8「配備の統制と資格情報の置き場」、ADR-0090 決定1
- 根拠: G-8 は「配備の資格情報」を (a)(b) で参照に結び付けることを求め、「このトークン(`GITHUB_TOKEN`)で配備先へ書き込む構成は、この規定を満たしません」と書く。しかし配備先が同じリポジトリの中(配布用のブランチ、リリースの資産、パッケージ、Pages のブランチなど)にある場合、配備の処理が (a) の秘密情報(App のトークンなど)で書き込んでいても、書き込みの権限を持つ者は自分のブランチのワークフローで `permissions: contents: write` を宣言し、`GITHUB_TOKEN` で同じ配備先へ書ける。`ci-gates.md` の新しい表も、(a) の行の「止めないもの」に「秘密情報を使わず `GITHUB_TOKEN` で書く経路」と書いている。つまり、表は (a) が経路を閉じないことを認めながら、G-8 の文ではその構成を「満たす」と読める。規定の第1文(統制を起動元のブランチで書き換えられる場所の中だけに置かない)の目的は、この構成で果たされていない。#293 の会議体の裁定 J-6 の b・d(deploy key を Environment の秘密情報に置き、**ルールセットで更新を deploy key だけに限る**)は、配備先の側の限定を対で持っていた。今回の (a)(b) は、その対の片方だけを規範にした
- 直し方の案: G-8 に「配備先が、参照に結び付かない資格情報(ワークフローの権限の宣言から生じるトークンを含む)からも書き込める場合は、(a)(b) を用いていても満たさない」を足す。満たす形の例として「配備先の側で、書き込みを結び付いた資格情報に限る(ルールセットの更新の制限と、配備専用の主体だけのバイパス)」をフェーズ5 の表に置く。配備先がリポジトリの外(クラウド・レジストリ)で、`GITHUB_TOKEN` に届かない場合は該当しないと書く。`ci-gates.md`「配布用のブランチの保護を独立の要求事項にしない」(ADR-0077)とは、独立の要求事項ではなく資格情報の結び付きの条件として書くことで両立させる。本リポジトリの開示(未達)は変わらない

### X-2(中)(b) の「配備の環境を確かめる」は、その配備の環境が参照に限られていなければ参照に結び付かない

- 所在: G-8 の (b)、1.4「参照に結び付いた資格情報」、ADR-0090 決定1
- 根拠: GitHub の OIDC の `sub` は、ジョブが Environment を参照すると `repo:<o>/<r>:environment:<名>` になり、参照(ブランチ)を含まない([SRC-0712])。受け手が `environment:prod` だけを確かめ、Environment `prod` に配備の参照の限定が無ければ、どのブランチのワークフローも `environment: prod` を書いて資格情報を得る。G-8 の「参照する配備の環境は、参照する前に作り、保護を設定します」は、保護の中身(配備を許す参照に限る)を言っていない。`ci-gates.md` の (b) の行の「監査で読む値」に `github-pages` の配備の参照の限定があるだけで、規範としては読めない
- 直し方の案: (b) の括弧に「配備の環境を確かめる場合は、その配備の環境を配備を許す参照に限る」を足す。1.4 の定義も同じ条件を持たせる。`ci-gates.md` の (b) の行の「止めないもの」に「参照の限定の無い配備の環境を確かめる受け手」を書く

### X-3(中)EV-0184 の差し替え条件が、EV-0137 で退けた「拒まれた記録だけ」の形のまま

- 所在: G-8 の EV-0184
- 根拠: 裁定 R-3 と ADR-0090 決定5 は、EV-0137 を「(a) 既定ブランチ以外から拒まれた」と「(b) `environment:` を外した経路が書き込めるか」の対に改め、(a) だけを証拠に数えないとした。EV-0184 の差し替え条件は「既定ブランチ以外の参照からの発行・受理が拒まれた記録」と事例の件数だけで、同じ欠陥を持つ。(b) の形でも、`environment:` を外したジョブが OIDC のトークンを得て受け手に受理されるか(受け手が環境の主張の欠落を拒むか)を確かめなければ、結び付きは示されない。`actions/deploy-pages` の README([SRC-0713])は、受け手が主張を確かめることと、保護された Environment の規則が優先することを述べるが、`environment:` を外した配備を拒むとは明示していない(WebFetch の要約による)
- 直し方の案: EV-0184 の差し替え条件を対にする。(1) 既定ブランチ以外の参照からの発行・受理が拒まれた記録、(2) `environment:` を外した(または別の Environment を参照した)ジョブの発行・受理が拒まれた記録。(1) だけを数えない。本文の「GitHub Pages の配備が … 参照を確かめること [SRC-0713]」は、README が明示する範囲(主張の確認と保護された Environment の優先)に限って書く

### X-4(中)プロジェクト運営の開示が、裁定の退けた論点「トークンは新しい能力を足さない」を書いている

- 所在: `community/project-management.md`「標準の規定との関係」の「経路を持つ主体と直接の書き込み」の箇条
- 根拠: 「トークンは新しい能力を足さないが、配布先は保護されていない」とある。裁定 §0 と ADR-0090 決定1 は、この論点を3つの経路(PR の自己承認、範囲を狭めた資格情報を持つ主体の昇格、名義の消失)で退けた。とくに同じ箇条が主体に挙げる「保守者の資格情報で push する AI のセッション」は、所有者の設定5(管理者の権限と `workflow` の範囲を外す)の後は、まさに「範囲を狭めた資格情報を持つ主体」になり、トークンが能力を足す。開示と ADR が食い違う
- 直し方の案: 「トークンは新しい能力を足さないが、」を削る。代わりに「現時点では、どちらの主体も直接 push できるため、トークンの経路は直接の書き込みより広くない。設定5 の後は、AI のセッションがトークンの経路で自分の資格情報に無い書き込みを得る(ADR-0090 決定1 の2つめの経路)」と書く

### X-5(中)env-check が、タグの配備の参照を、パターンもタグの作成の限定も見ずに確認済みにする

- 所在: `template/scripts/gate/adoption-trial.mjs` の Environment の項目、`template-repository.md`「既定ブランチ(とリリースのタグ)に限られていれば、env-check は確認済みと書く」
- 根拠: 判定は `type === 'branch'` の規則だけを既定ブランチと比べ、`type === 'tag'` の規則は名前を問わず通す。`v*` も `*` も確認済みになる。`ci-gates.md` 自身が「タグからの配備を許す配備の環境は、タグの作成を限らなければ同じ穴を持ちます」と書いており、書き込みの権限を持つ者はどのコミットにもタグを打てる。タグの作成を限るルールセットの有無を読まずに確認済みと出すのは、本文の記述と合わない
- 直し方の案: タグの規則がある Environment は、タグのルールセット(`rules` の `creation` を対象のパターンに掛け、バイパスが空)を読み、無ければ不一致(「タグの作成を限っていない」)とする。読めなければ未確認。少なくとも、確認済みの説明に「タグの作成の限定は読んでいない」と書く。試験に `*` のタグと、タグのルールセットの無い場面を足す

### X-7(中)Environment が無い場合の「対象外」は、委任のトークンをリポジトリの秘密情報に置いた構成を見逃す

- 所在: env-check の Environment の項目、`implementation.md` §2 の逸脱3
- 根拠: 対象外は「Environment が1つも無い」だけで決まる。マージのジョブは `secrets.DELEGATED_MERGE_TOKEN` を読む。Environment `delegated-merge` が無くても、同名のリポジトリの秘密情報があれば、ジョブは参照した時点で保護の無い Environment を自動で作り、リポジトリの秘密情報を読んで動く。リポジトリの秘密情報は任意のブランチのワークフローから読める(`ci-gates.md` の表)。この状態で env-check は対象外を出し、全体の成否を妨げない。逸脱3 は `delegation.allowed` と変数が別であることを理由に不一致の案を退けたが、変数そのもの(`DELEGATED_MERGE_ENABLED`)を読めばその理由は当たらない
- 直し方の案: Environment が空の場合でも、(1) リポジトリの変数 `DELEGATED_MERGE_ENABLED` が `true` なら不一致、(2) リポジトリの秘密情報の名前の一覧に `DELEGATED_MERGE_TOKEN` があれば不一致、読めなければ未確認、とする。どちらも無い場合だけ対象外にする

### X-9(中)主体の資格情報から `workflow` の範囲を外す措置の「止めないもの」に、既存のワークフローが実行するブランチ上のコードが無い

### X-15(低)ADR-0090 の影響の「所有者が設定を済ませるまで、旧いワークフローの強制 push で配られ続ける」の条件が違う

- 根拠: 旧い `publish-standard.yml` が止まる条件は、#293 以降の変更をリモートの `main` へ入れること(所有者の設定の表の2)であり、設定(Environment・ルールセット・Actions の権限)の完了ではない
- 直し方の案: 「#293 以降の変更がリモートの `main` に入るまで」と書く

## 2. 裁定そのものへの指摘

- **D-1(X-1 の源)**: R-1 は「資格情報の形」だけを規範にし、配備先が結び付かない資格情報からも書けるかを問わなかった。#293 の J-6 の b・d は配備先の側の限定を対で持っており、R-1 はその半分を落とした。裁定の判断軸(§0「配備の権限が、許した参照に、ブランチで書き換えられない場所で結び付いていること」)に照らせば、配備先の側の条件が要る
- **D-2(X-2 の源)**: R-1 の (b)「参照または配備の環境を確かめてから」は、配備の環境の参照の限定を条件にしていない。OIDC の `sub` が Environment を参照すると参照を含まないことは、外部調査の範囲で読めた事実である
- **D-3(X-3 の源)**: R-3 は EV-0137 の差し替えを対の確認に改めたが、R-1 の5(EV-0184)には同じ考え方を当てなかった
- **D-4**: R-4 は env-check の Environment の項目を「配備の参照の限定」として決めたが、タグの規則の扱い(タグの作成の限定)と、Environment の外に置かれた委任のトークン(リポジトリの秘密情報)の扱いを決めていない(X-5・X-7)。実装担当は対象外の条件を自分で決めた(逸脱3)
