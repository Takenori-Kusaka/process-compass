## 0. 一次資料の水準での吟味(外部調査への所見)

外部調査の結論の大筋は、引いた一次資料の範囲で支えられています。ただし、規範の根拠として引く前に、次の水準の差を区別します。

| 主張 | 水準 | 所見 |
| --- | --- | --- |
| GITHUB_TOKEN の権限は `permissions` で足し引きされ、Workflow permissions は既定(出発点)である | GitHub Docs の記述 + 推論 [外 1.2] | 「上限ではない」は推論。ただし本リポジトリの publish ジョブの形がそれを前提に書かれており、ADR-0077 も同じ理解に立つ [確]。規範の根拠に使ってよい。組織の restricted が昇格を禁ずるかは未確認のまま残す |
| Environment は GITHUB_TOKEN の権限を限らない | 「限るという記述が無い」+ 機序の推論 [外 1.4] | 不在の記述からの推論。ただし `environment:` を書かないジョブに Environment の規則が及ばないことは、Docs の「a job referencing the environment」の文言から直接導ける。結論は堅い |
| ルールセットのバイパスに GITHUB_TOKEN を入れる公式の手段は無い | Docs の列挙 + GitHub 社員の発言(Community Discussion)[外 1.5・1.6] | Community の発言は一次資料ではない。規範の文には書かず、フェーズ5 の対応表の注意(時点つき)に留める |
| OWASP は「短命」と「未レビューのコードに資格情報を渡さない」を別要求とする | OWASP CICD-SEC-1・4・5・6 の本文 [外 2.1] | 一次資料の記述そのもの。本件の判断の主たる根拠にできる |
| SLSA の Trusted Robot に当たらない | SLSA v1.2 Source の定義 + 推論 [外 2.2] | 定義(「cannot be unilaterally influenced」)への当てはめで、推論として妥当 |
| ISO/IEC 27001 附属書A 5.17・8.4・8.31・8.32 に掛かる | 管理策の名称だけ [外 4.1] | **本文・27002 の手引きは読めていない**。規範の根拠として引かない。参考の対応づけに留める |
| SP 800-204D 5「制御面はステップより高い信頼で動く」 | 本文の記述 [外 4.3] | 本委員は PDF を読み直していない。根拠水準は外部調査に依る |
| SSDF PS.1.1 が configuration-as-code を保護対象のコードとする | 本文の記述 [外 4.2] | 同上。ワークフローのファイルを「保護するコード」と読む根拠として妥当 |

要点: **どの指針も「短命であること」を「参照・レビューへの束縛」の代わりに扱っていない**。逆に、短命であることを禁ずる指針も無く、OWASP CICD-SEC-6・CISA/NSA・GitHub の Secure use は短命を優先します。したがって論点は「短命を認めるか」ではなく、「その短命の資格情報が、配備を許す参照に束縛されているか」です。

## R-1 条項は、ジョブの権限で発行される短命のトークンをどう扱うか

### 結論

**条件つきで認める。条件は「短命」ではなく「参照への束縛」である。** 資格情報の種類(長期・短命、秘密情報に置くもの・実行のたびに発行されるもの)を問わず、書き込み・配備の権限が、配備を許す参照からの実行に限って得られることを要求事項とします。

- ワークフローのファイルの `permissions` だけで書き込みの権限を得る GITHUB_TOKEN は、この条件を満たさない(G-8 の禁止文「起動元のブランチで書き換えられる場所の中だけに置いてはならない」にそのまま当たる)
- OIDC のトークンを、参照・実行環境のクレームを検証する受け手へ渡して短命の資格情報を得る形(GitHub Pages の deploy-pages が先例)は、受け手の検証が起動元のブランチの外にあるため条件を満たす
- 「短命」は要求事項にしない。推奨として置く(後述の文の案)

### 理由

1. **現行の文は手段を指定しすぎて、最良の実務を不適合にしている**。G-8 は「資格情報は…実行環境の秘密情報に置きます」と置き場を指定します [確]。この文に従うと、秘密情報を持たない OIDC の配備(本リポジトリのジョブ `deploy` もこの形 [内 3.1])は文言上満たさず、OWASP CICD-SEC-6・CISA/NSA・GitHub Secure use がそろって優先する短命の資格情報を、規格が劣後させることになります。規格は成果(何が保証されるか)で書き、手段は例示に回すのが SSDF・27001 の書き方と同じです(SSDF の各タスクは成果の文で、実装例を Examples に分けている [外 4.2])
2. **「短命」で「束縛」を代えてはならない**。短命は漏えい後の悪用の期間を縮めるが、誰が発行させられるかを変えない [外 2.6]。OWASP CICD-SEC-4 の脅威の主体は「ソース管理へのアクセスを持ち、ビルド環境へのアクセスを持たない攻撃者」で、Direct PPE はまさにブランチ上の CI 設定の書き換えです。発行のたびに新しいトークンが得られるので、短命は Direct PPE への防御になりません
3. **論点「起動者が自分で直接できることを超えない」は、規範の読み直しとして採らない**。
   - その条件が成り立つのは、配備先の参照が人に対しても保護されていない場合に限られます。そのとき欠けているのは資格情報の置き場ではなく、配備先の統制そのものです。条項の目的を「起動者が持たない能力」に置き換えると、配備先を誰にも保護しない構成ほど適合しやすくなり、規範が逆向きに働きます
   - OWASP CICD-SEC-1 の推奨は「未レビューのコードを push できるアカウントは、配備のパイプラインを起動する権限を持たない」です [外 2.1]。問題は能力の大小ではなく、**ゲート(G-8)を経ない経路で配備に届くこと**です
   - 本標準では、作業ブランチへ push する主体に AI のセッションが含まれます。第5章 5.5.1(c) は本番デプロイ・外部への発行を「取り消せない操作」として人へ戻す対象にしています(準拠テンプレートの CLAUDE.md の表 [確])。ブランチ上のワークフローから配備に届く構成は、AI の push 権限を取り消せない操作の権限へ変換します。「起動者の能力」で測ると、この変換が見えなくなります
   - SLSA v1.2 Source の Trusted Robot は「identity と codebase を一者で左右できない」自動化です [外 2.2]。ブランチで書き換えたワークフローのトークンは当たりません。保護された参照を更新する主体として扱う根拠になりません
4. **ISO/IEC 27001 附属書A との対応(参考。本文未読)**: 8.4(ソースコードへのアクセス。ワークフローのファイルへの書き込みが配備の権限を伴う)、8.31(開発の文脈と本番の文脈の分離)、8.32(変更管理)、5.17(認証情報)の管理策名に掛かります。名称の水準を超えて根拠には使いません

### 他の案を落とす理由

- **認める(無条件)**: OWASP CICD-SEC-4・SEC-1、SLSA Source、SSDF PS.1(configuration-as-code の保護)のいずれとも両立しない。G-8 の禁止文とも直接矛盾する
- **短命を条件に認める**: 指針が別要求として並べるものを1つにまとめる誤り(理由2)
- **認めない(秘密情報への置き場の指定を維持)**: OIDC + 受け手の検証という、束縛と短命を両方満たす唯一の形 [外 2.6] を不適合にする(理由1)。所有者の指示(鍵を置かない)の下では、これを維持すると採用者にも本リポジトリにも「長期の鍵を置くか、不適合か」の二択しか残らない
- **目的を「起動者が持たない能力への到達」と読み直す**: 理由3

### 文の案(第4章 G-8「配備の統制と資格情報の置き場」の第1段落の置き換え)

本文(ですます調):

> **配備・配布の統制と資格情報を、起動元のブランチで書き換えられる場所(ワークフローの定義のファイルなど)の中だけに置いてはなりません**。その場所の中の確認は、起動元のブランチで書き換えれば外れるためです。配備・配布の書き込みの権限は、配備を許す参照(既定ブランチ、またはリリースのタグ)からの実行に限って得られるようにします。限定は、起動元のブランチで書き換えられない場所(実行環境の設定、資格情報を発行する側・受け取る側の検証)に置きます。資格情報が長期のものか、実行のたびに発行される短命のものかは、この限定の代わりになりません。

手段の例示(同じ節の箇条書き。である調・体言止め):

> - 参照を限った実行環境の秘密情報へ置く資格情報
> - 実行の参照・実行環境を検証する受け手へ渡す、短命の識別トークン(OIDC など)と、受け手が発行する短命の資格情報
> - **満たさない形**: 実行の権限の宣言(ワークフローの `permissions` など)だけで得るトークン。実行環境を参照しても、そのトークンの権限は実行環境に限られない
> - 限定を満たす手段の中では、短命の資格情報を優先(推奨。要求事項ではない)

課さないことの明記:

> 資格情報が短命であることは、要求事項にしません。長期の資格情報でも、参照を限った実行環境の秘密情報に置けば限定を満たすためです(準拠テンプレートの委任のマージの経路)。

### 既存との矛盾

- ADR-0077 決定6 の開示「本リポジトリの配布は…満たしません」と整合する(結論は同じで、満たさない理由が明確になる)
- ADR-0077 は「資格情報は…実行環境の秘密情報に置きます」を標準の文として記録している。採用済み ADR の本文は書き換えず、**新 ADR で「置き場の指定」を「参照への束縛の要求」へ改めることを記録する**(ADR-0077 の当該の標準の文の一部を置き換える旨を明記)
- 第3章 3.5.3 の「認証情報(トークン)の分離」[確] と矛盾しない。3.5.3 は席の分離、G-8 は参照への束縛で、対象が違う。ただし語が割れている(R-2)
- EV-0137 の対象の文が変わるため、caution の本文を改め、短命のトークンの扱いには新しい EV を付ける(識別子は再利用しない)

## R-2 何が止めるか。語の定義

### 結論

1. 標準(第4章)には、**止めるものを機能名で書かない**。R-1 の文のとおり「起動元のブランチで書き換えられない場所に置く限定」を要求し、GitHub の機能の対応はフェーズ5 の対応表に置く
2. フェーズ5 `ci-gates.md` の対応表に、**限定にならないもの**を行として明記する: GITHUB_TOKEN とジョブの `permissions`、Workflow permissions(既定)、ワークフローの中の `if:`・`environment:`、CODEOWNERS(マージの関門で、ブランチ上の実行を止めない)、ワークフロー実行の保護(起動の主体・イベントを限るが参照を限らない)。いずれも**緩和**として記載し、限定を満たしたものとして扱わない
3. 限定になるものとして、OIDC + 受け手の検証の行を足す(GitHub Pages の配備が先例)。配備先の参照のルールセット(Restrict updates)は、バイパスの主体が参照に束縛された資格情報である場合に限って限定になる、と注意に書く
4. **語の定義を第1章 1.4 に置く**: 「資格情報」と「配備の実行環境」。3.5.3 の「認証情報」との関係を定義の中で明示する
5. IMPL-0237 の降ろし先の説明(`impl-targets.yaml` の `deploy-workflow`)を、本文に合わせて「既定ブランチ、またはリリースのタグ」へ直す。本文が正本で、食い違いは降ろし先の誤り

### 理由

- 機能名を規範に入れると、GitHub の仕様の変更(2025-12 の `pull_request_target` の変更、2026-09 GA のワークフロー実行の保護、予告されている scoped secrets [外 1.7])のたびに規範が古くなる。規格の本文は技術中立に書き、時点つきの対応をリファレンスへ分けるのが本標準の既存の構成(G-8 → フェーズ5)と同じ
- 「限定にならないもの」を書かないと、採用者は本リポジトリと同じ誤読(Environment を参照すれば資格情報の置き場になる)をする。ADR-0077 自身が「限定は資格情報の置き場にはならない」と書いている [確] のに、標準の対応表には GITHUB_TOKEN の行が無い [確]。規範の利用者が、規範を書いた側と同じ穴に落ちる状態は、信頼性の欠落そのもの
- 語の定義: G-8 は「資格情報」、3.5.3 と 1.10.2 の列挙に無い離脱は「認証情報」を使う [確]。ISO/IEC 27001:2022 附属書A 5.17 は authentication information で、JIS Q 27001 の訳語は「認証情報」と承知している [未。JIS の本文は確かめていない]。2語の関係を定義しないと、3.5.3(席ごとに分ける対象)と G-8(参照に束縛する対象)に GITHUB_TOKEN が含まれるかが読み手ごとに割れる

### 定義の案(第1章 1.4 の表へ追加)

| 用語 | 定義 |
| --- | --- |
| 資格情報 | 配備先・リポジトリ・外部のサービスへの書き込みや配備の権限を行使するために提示する情報。秘密情報として保管する長期の鍵・トークンと、実行のたびに発行される短命のトークン(実行の権限の宣言で発行されるもの、識別トークンとの交換で得るもの)を含む。第3章 3.5.3 の認証情報は、実行主体の文脈が用いる資格情報をいう |
| 配備の実行環境 | 配備のジョブが参照し、参照を許す参照(ブランチ・タグ)・保護規則・秘密情報を、起動元のブランチで書き換えられない場所に設定できる単位(GitHub の Environment など) |

- 「秘密情報」は一般語として定義しない(定義すると第5章 5.8.6 の秘密情報・秘匿情報との整理が要り、本件の範囲を超える)。必要なら別 Issue
- 「認証情報」と「資格情報」を1語へ統一するかは、本件で決めない。3.5.3・1.10.2・ADR-0035 に及ぶため、別 Issue として起票する(決めないことの明記)

### プランの制限(フェーズ5 の対応表の注意へ)

- OIDC はプランに依らず使える [外 1.8]。Environment の秘密情報・参照の限定は Free の非公開で使えない [確 ci-gates.md]。`.github/workflows/**` のパスの制限は Enterprise Cloud の internal・private に限る [外 1.5]
- G-8 第2段落の「使えない場合」の未達は維持する。ただし R-3 のとおり「使えるのに使わない場合」も満たしたものとして扱わないことを足す

### 他の案を落とす理由

- **Workflow permissions を read にすることを要求事項にする**: `permissions` で明示した昇格を止めない [外 1.2]。止めない統制を要求事項にすると、満たしたことが保証の誤認を生む。推奨(緩和)に留める
- **CODEOWNERS + `.github/workflows` の必須レビューを要求事項にする**: マージの関門で、ブランチ上の実行を止めない [外 2.4]。SSDF PS.1.1 のコード所有者のレビューに当たる良い実務だが、G-8 の限定の代わりにならない
- **ワークフロー実行の保護を限定として認める**: 参照・トークンの権限の制限が記述に無い [外 1.7]。AI の主体による起動を止める緩和としては有効でありうるが、個人所有の public での提供範囲と新規ファイルへの及び方が未確認
- **配備を別のリポジトリへ分ける**: OWASP SEC-4 の「別の保護されたブランチ」と同じ向きだが、別リポジトリへ書くには結局資格情報が要る [外 3]。限定の一手段として例示に入れるのは可、独立の要求にはしない

### 既存との矛盾

- ci-gates.md L899 の「ファイルの外の設定(実行環境の配備の参照の限定)だけが、この経路を止めます」[確] は、GITHUB_TOKEN については誤り(Environment は止めない)。ADR-0077 決定6 の記述と食い違っている。**誤りは ci-gates.md の側**で、本件で直す
- 第3章 3.5.3 と語が割れる点は上記(定義で関係を明示し、統一は別 Issue)

## R-3 本リポジトリの配布

### 結論

1. **現時点では、開示を続ける。ただし開示の区分を正す**。本リポジトリは本標準に従う開発の案件ではない [内 2.3] が、規範を書いた側の運営として、開示の文は「手段が無いため未達」ではなく「手段はあるが、保守者の決定により使わない(長期の鍵を置かない)ため満たさない」とする
2. 鍵を使わずに条項へ合わせる経路を、**別 Issue で評価する**。候補は「配布物を GitHub Pages の配備(OIDC + `github-pages` の実行環境)に含める」形。これは ADR-0077 決定4(`dist/standard` を配布物とする)を変えるため、本件の会議体では決めない
3. G-8 の第2段落に「使えるのに使わないと決めた場合」を足す(採用者にも当たる一般の規定)
4. 所有者が行う設定の一覧を、緩和として運営の記録(project-management.md)に置く。**いずれも限定を満たしたものとして扱わない**
5. EV-0137 の差し替え条件を直す(後述)

### 理由

- **開示の区分**: 現行の G-8 の未達は「契約の条件などによって…使えない場合」に限られる [確]。本リポジトリは public で、Environment の秘密情報も参照の限定も使える [内 3.4]。「使えない」と書けば事実に反する。ADR-0028(未達と省略の区別)の趣旨は、読み手が「満たしていない理由」を誤読しないことであり、区分を偽らないことが前提になる
- **最優先はリモートの実状**: リモートの main では旧 `publish-standard.yml`(最上位 `contents: write`、Environment なし、強制 push、`workflow_dispatch`)が動き、ルールセットは空 [内 3.4]。work/346 の形は、条項を満たさないとしても、旧形より OWASP CICD-SEC-5(最小権限)・Scorecard の Token-Permissions の点で明確に良い [外 2.5]。開示の文を整える前に、リモートが開示の記述と違うことを解消しないと、開示自体が事実と食い違う
- **Pages の経路の評価を別にする理由**: deploy-pages の README は Pages の配備 API が OIDC のクレームを検証すると書く [外 1.8] が、`github-pages` の実行環境の参照の限定は読めていない(API が 403)[内 5]。配布物の受け手の取得方法(ブランチを取得する前提か)も、本委員は確かめていない [未]。根拠の揃わない構成変更を本件で決めると、ADR-0077 の決定4 を突合なしに変えることになる
- **artifact attestations(provenance)**: 受け手が「main の ci.yml で作られたか」を検証できる下流側の統制として SLSA Build の provenance と同じ向き [外 2.2 補足]。ただし外部調査は該当文書を読んでおらず、本委員も確かめていない [未]。書き込みそのものは止めないため、限定ではなく緩和。別 Issue の評価に含める

### EV-0137 の差し替え条件の修正

現行の条件「既定ブランチ以外から起動した配布が拒まれた記録を残します。拒まれなければ本文を直します」[確] は、`environment:` を参照するジョブの拒否しか試さない。GITHUB_TOKEN の経路では、拒まれても限定の成立を示さない。次の対の試験に改める:

> 既定ブランチ以外から、(a) 実行環境を参照する配備のジョブを起動して拒まれること、(b) 実行環境を参照せずに書き込みの権限を宣言したワークフローから、配備先へ書き込めるかを、同じ設定の下で確かめた記録を残します。(b) で書き込めた場合、その経路は限定を満たしていません。

(b) は本リポジトリでは「書き込める」と予想され、ADR-0077 の開示の裏付けになる。実施は取り消せない操作(配布先への書き込み)を含むため、試験用のブランチ・試験用の配布先で行い、保守者が実施する。

### 他の案を落とす理由

- **条項の適用外として開示をやめる**: 本リポジトリが案件でないことは事実だが、規範を書いた側の運営が規範と食い違うことの開示は、規格の信頼性に直結する(ADR-0077 自身がそう判断した [確])
- **条項を緩めて本リポジトリを適合させる**: 規範の側を運営に合わせる理由が、外部の指針のどこにも無い(R-1)
- **鍵を置いて合わせる**: 前提により採らない

### 文の案(G-8 第2段落の置き換え)

> 契約の条件などによって限定の手段を使えない場合、または手段を使えるのに使わないと決めた場合は、この規定を満たせません。**満たしたものとして扱わず、保証の開示に未達として記録します**([ADR-0028])。記録には、どちらの場合かと、限定の代わりに置いた緩和を書きます。緩和を、限定を満たしたものとして書きません。

- ADR-0028 と矛盾しない(未達の区分の中に「使えない」「使わない」の理由を併記するだけで、省略へは回さない)

## R-4 採用者とテンプレート

### 結論

1. フェーズ5 の対応表に R-2 の行を足し、採用者が GITHUB_TOKEN で配備する場合は G-8 を満たさないこと、その場合の未達の記録と緩和の書き方を示す
2. テンプレートの `adoption-trial.mjs env-check` が、Environments の参照の限定・保護規則と、Actions の Workflow permissions(既定の権限、PR の作成・承認の許可)を**読んで記録する**。読めない場合は未確認として出す(既存のルールセットの扱い [確 template-repository.md L114] と同じ)。採用者が実環境で実行し、AI が確認済みにしない(テンプレートの規約どおり)
3. テンプレートのワークフローの最上位の書き込みの権限(pull-requests・statuses・issues)をジョブ単位へ下ろす。**ただし標準の要求事項にはしない**(推奨として phase5 に書く)
4. IMPL-0237 は undelivered のまま表示を続ける。テンプレートにデプロイのワークフローの雛形を足すかは、本件で決めない(別 Issue)

### 理由

- 採用者が本リポジトリと同じ形を取ったときの扱いが、標準にもテンプレートにも無い [内 4]。規格として最も信頼性を損なうのは、規範を書いた側が見落とした穴を、採用者が規範の文面どおりに再現すること
- env-check が読む範囲を広げるのは観測の追加で、判定ではない。Environment の参照の限定が設定されていないことは、IMPL-0236(委任のマージ)の前提が崩れていることを意味する [確 G-8 の IMPL-0236 の注]。今は機械が確かめておらず、手作業の確認に依存している
- 最上位の書き込みの縮小は OWASP CICD-SEC-5(各パイプライン・ステップは必要な資格情報だけ)、GitHub Secure use、Scorecard Token-Permissions に沿う [外 2.1・2.4・2.5]。一方、ブランチ上のワークフローが同じ権限を宣言すれば得られる構造は変わらないため、G-8 の限定にはならない。限定にならない統制を要求事項にすると「満たした」の誤読を生む(R-2 と同じ理由)ので推奨に留める

### 他の案を落とす理由

- **テンプレートにデプロイのワークフローを本件で足す**: 降ろし先の形(OIDC の受け手の有無、配備先)が採用者ごとに違い、雛形の根拠が揃っていない。IMPL-0237 の未達表示で開示を続ける方が、根拠の無い雛形より信頼できる
- **最上位の権限の縮小を G-5 の検査(pr-rules)で強制する**: 本リポジトリの check-ci-wiring 条件5 に相当する検査を採用者へ課す根拠(手戻り・事故の実績)が無い。将来の検討として別 Issue に残す

### 文の案(フェーズ5 ci-gates.md「統制と資格情報の置き場」への追記。本文はですます調)

> ジョブの権限で発行されるトークン(GitHub の `GITHUB_TOKEN`)の書き込みの権限は、ワークフローのファイルの `permissions` で宣言します。ファイルは起動元のブランチのものが使われるため、書き込みの権限を持つ者は、自分のブランチへ置いたワークフローで同じ権限を宣言できます。実行環境(Environment)は、そのトークンの権限を限りません。このため、`GITHUB_TOKEN` に配備・配布の書き込みの権限を与える形は、第4章 G-8 の限定を満たしません。この形を採る場合は、未達として記録し、置いた緩和(既定の権限を読み取りに留める、書き込みをジョブ単位に限る、配備先の削除と強制 push を禁じる、起動できる主体を限る)を併記します。

対応表への追加行(案):

| 本節の語 | GitHub の機能 | 注意 |
| --- | --- | --- |
| ジョブの権限で発行されるトークン | `GITHUB_TOKEN` とジョブの `permissions`、Workflow permissions | Workflow permissions は既定で、上限ではない。`permissions` を書けば昇格する。**限定にならない** |
| 参照を検証する受け手 | OIDC(`id-token: write`)と、クレームを検証する配備先 | 受け手が参照・実行環境のクレームを検証する場合に限って限定になる。GitHub Pages の配備が例。同じリポジトリのブランチへの push には受け手が無い |
| 起動の主体の制限 | ワークフロー実行の保護(2026-09 GA) | 起動する主体とイベントを限る。参照とトークンの権限は限らない。緩和 |

## R-5 記録

### 結論

1. **新 ADR を起こす**(番号は起案時に採番)。内容: G-8 の「置き場の指定」を「参照への束縛の要求」へ改めること、短命を要求にしないこと、未達に「使わないと決めた場合」を含めること、本リポジトリの開示の区分。ADR-0077 との関係は「決定6 の『#293 で別に扱う』を引き取り、ADR-0077 が標準の文として記録した『実行環境の秘密情報に置く』を置き換える」と明記する
2. **方式の変更(b185611)が会議体・突合を経ていない事実を、新 ADR の経緯と research/346 の実装の記録に書く**。#293 の `implementation.md` が deploy key 方式のままである事実も併記する。過去のファイルは書き換えず、追記の注で新しい記録を指す
3. **所有者の指示の記録**: 公開の記録には、指示の要旨(長期の鍵を置かない、書き込みはジョブの権限で行う、更新の制限を置かないことに同意)と日付、指示した者の席(保守者)を書く。ADR-0077 が挙げた理由(長期の鍵の管理・更新・漏えい)は、起案側が付した理由であることを区別して書く [内 2.1・2.2 による。所有者の発言そのものに理由の文は無い]
4. 決めないことの明記: 「認証情報」「資格情報」の語の統一、Pages の経路への配布の移行、テンプレートのデプロイの雛形、最上位の権限の検査の強制は、本件で決めない(各々別 Issue)

### 理由

- 本標準のコアポリシーは、条項の新設・改廃の前に調査・議論・突合を行うことを求める [確 CLAUDE.md]。b185611 はその手順を経ずに ADR-0077 の決定(標準の規範との食い違いの開示を含む)を書き換えた。手順の不履行を記録しないと、ADR-0077 決定6 が会議体を経た決定であると読まれる。ISO 9001 7.5・ISO/IEC 27001 7.5(文書化した情報)の趣旨である、決定の根拠の追跡可能性の観点からも、経緯の欠落を開示することが要る [27001 の本文は確かめていない。条項番号の対応は一般に知られた構成として挙げる]
- 指示の要旨と、起案側の付した理由を区別するのは、後の見直し(EV の見直し、鍵を置かない判断の再評価)で、どの前提が誰の判断かを特定できるようにするため。逐語の引用は要らないが、要旨は公開の記録に要る(現行の「保守者の決定」だけでは、何を決めたかが ADR-0077 の文脈からしか読めない)
- 採用済み ADR の本文を書き換えない規則 [確 CLAUDE.md] に従い、置き換えは新 ADR で行う

### 他の案を落とす理由

- **ADR-0077 に追記で済ませる**: 採用済み ADR の本文を変えることになる
- **所有者の発言を逐語で公開の記録へ載せる**: 要旨で決定の内容は特定できる。逐語は research/346 の issues-context.md に既にある [確]。公開の記録へ移す必要は示されていない
- **経緯の不履行を記録しない**: 上記の理由

### 既存との矛盾

- 無し。ADR-0077 の本文は変えず、関係を新 ADR に書く
