# 議長の裁定(#346 ジョブの権限で発行される短命のトークンと、G-8「配備の統制と資格情報の置き場」)

入力: `issues-context.md`、`survey-346-1-internal.md`、`survey-346-2-external.md`、`council-00-agenda.md`、`council-01`〜`05`。新しい ADR は ADR-0090。番号の起点は、#319 の後の次の空き番号とします(実装で確かめる)。**所有者の指示により、鍵を設定する案は採りません(前提)**。

## 0. 全体の方針

- 判断軸は「配備の権限が、許した参照に、ブランチで書き換えられない場所で結び付いていること」です。短命であるかどうかは軸にしません。指針(OWASP CICD-SEC-6 と SEC-1・4・5、SLSA の Trusted Robot、CISA/NSA)は、短命とレビューへの結び付けを別の要求として立てています。短命でレビューへの結び付けを代える根拠は、見つかりませんでした。
- 所有者の指示(鍵を置かない)は、本リポジトリの運用を縛る前提です。しかし、適合の判定を縛るものではありません(擁護者)。本標準の作者の1件の都合で条項を緩めることは、他組織が従う規格の立場と両立しません。
- 議題が置いた論点「トークンは、起動した者が既に持つ能力を超えない」は採りません。理由は品質保証の委員が示した3つの経路です。
  - 「Actions に PR の作成と承認を許す」設定のもとでは、GITHUB_TOKEN が PR を承認できる。書き込み権限を持つ者が、自分のブランチのワークフローで自分の PR を承認させられる。
  - 範囲を狭めた資格情報を持つ者(AI エージェントを含む)も、ワークフローの `permissions` で、自分の資格情報に無い権限をトークンへ与えられる。
  - 書き込みは `github-actions[bot]` の名義になり、責任者が git の履歴から消える。

  さらに、配布先に保護を掛ければトークンも同じく止まり、トークンだけを除外する公式の手段はありません。この読み方で適合になるのは、配布先が誰にも保護されていない構成だけです(起案者・擁護者)。

## R-1 条項は短命のトークンをどう扱うか

**裁定**: 認めません。ただし、G-8 の第2文を、置き場の指定から、満たすべき性質の規定へ改めます(起案者・規格・品質保証・擁護者の4委員。現場の条件つきの許容は、上の3つの経路で成り立たないため採りません)。

1. 配備・配布の資格情報は、次のどちらかの形で、許した参照(既定ブランチ、またはリリースのタグ)に結び付けます。
   - (a) 許した参照に限った配備の環境の秘密情報
   - (b) 発行する側か受け取る側が、参照または配備の環境を確かめてから発行・受理する短命の資格情報(OIDC と、それを検証する受け手。GitHub Pages の配備が先例)
2. ワークフローのファイルの `permissions` だけから権限が生じるトークン(GitHub の GITHUB_TOKEN)は、短命であっても、(a)(b) のどちらにも当たらないと明記します。
3. 「短命の資格情報を用いる」は推奨とし、要求事項にしないと明記します。
4. 未達の範囲を広げます。いまの未達は「手段を使えない場合」だけです。これに「手段はあるが、組織が使わないと決めた場合」を足します。この決定は人が記名で行い、AI の名義にしません。未達の記録には、次の3つを書きます(起案者)。
   - 開いている経路
   - その経路を持つ主体と、その主体が配布先へ直接書けるか
   - 経路を狭める措置と、その措置が止めないもの
5. (b) の形は実証が薄いため、新しい EV(E1)で開示します。EV-0137 は再利用しません。

## R-2 何が止めるか。語の定義

**裁定**:

- `phase5-implementation/ci-gates.md` に、次を書きます。「GitHub には、このトークンの書き込みを参照で限る機能はありません(2026-10 時点の GitHub Docs)」。対応表に行を足し、各行に、何を止めるか・何を止めないか・監査で読む値を書きます(品質保証)。
  - GITHUB_TOKEN(ジョブの権限)
  - Workflow permissions の既定(上限ではなく出発点)
  - `environment:` の参照(消せば外れる)
  - `.github/workflows` の CODEOWNERS(マージの関門であり、ブランチ上の実行は止めない)
  - ワークフロー実行の保護(起動する主体・イベントを限るが、参照とトークンの権限は限らない)
  - 配布先のルールセット
  - Restrict file paths(Enterprise Cloud の internal・private に限る)
  - OIDC と検証する受け手(参照に結び付く)

  (b) 以外の行は、適合の手段に数えず、狭める措置とします。
- `ci-gates.md` 899 行の「ファイルの外の設定だけが、この経路を止めます」は、GITHUB_TOKEN については誤りです。直します(5委員が一致)。
- 語の定義: 1.4 に、次の3つを足します(起案者)。
  - 配備の資格情報
  - 配備の環境
  - 参照に結び付いた資格情報

  一般の語「資格情報」は定義しません。G-5・3.5・5.8.6 が別の範囲で使っているためです。3.5.3 の「認証情報」との関係を注記します。G-8 と `ci-gates.md` の「実行環境」は「配備の環境」へ改めます。5.8.6 と成果物の様式の「実行環境」(AI エージェントの環境)と衝突するためです。語の全体の統一は、後継の Issue の候補にします。
- IMPL-0237 と `impl-targets.yaml` の `deploy-workflow` の説明を、本文の範囲(既定ブランチ、またはリリースのタグ)へ合わせます。
- 主体の側の統制は、狭める措置として、表に書きます。AI のセッションに渡す資格情報から、管理者の権限と `workflow` の範囲を外すことです。ただし「`.github/workflows` を変えるコミットを push するには `workflow` の範囲が要る」ことは、委員の知識による主張で、一次資料で確かめていません。実装で一次資料を確かめ、確かめられなければ EV を付けます。

## R-3 本リポジトリの配布

**裁定**:

- 条項に合わせる変更はしません。未達の開示を続けます。区分は「手段はあるが使わないと決めた」とし、決定者は保守者(所有者)と書きます(起案者・規格・擁護者・品質保証)。いまの開示の「手段が無い」は事実と違います。リポジトリは public で、手段はあるためです(規格)。
- 鍵を使わずに適合する道は、配布の経路を変えることだけです。Pages を使う形や、受け手が出どころを検証する形がこれに当たります。この変更は、テンプレートと submodule の利用者が頼るインタフェースを変えます。所有者が決める事項として、後継の Issue の候補にします。成果物の来歴の証明(artifact attestation)と、`dist/standard` の各コミットを main への push の成功した CI の実行と突き合わせる定期の検査(品質保証)も、同じ Issue で扱います。
- **リモートの実状**: リモートの main では、旧 `publish-standard.yml` がいまも動いています。最上位で `contents: write` を持ち、Environment を使わず、強制 push を行い、`workflow_dispatch` で起動できます。ルールセットは空です。ADR-0077 が開示している状態より悪い状態です。開示を、この実状に合わせて正します。
- **所有者が行う設定**: 順序つきで #346 に示します(起案者の6項目に、品質保証の項目を足す)。各項目には、監査で読む値を添えます。設定するのは所有者です。AI が設定済みとは書きません。
  1. #293 以降の変更をリモートの main へ入れ、旧 `publish-standard.yml` が消えたことを確かめる。
  2. それより前に、Environment `dist-standard` を作り、`main` に限る。管理者の迂回は外す。`github-pages` も同じく限る。
  3. `dist/standard` にルールセットを掛け、削除と強制 push を禁じる。
  4. Workflow permissions の既定を read にする。Actions による PR の作成・承認を無効にする。
  5. AI のセッションに渡す資格情報から、管理者の権限と `workflow` の範囲を外す。
  6. ワークフロー実行の保護で、`push` と `workflow_dispatch` を起動できる主体を限れるかを評価する。
  7. 各設定と、`main` 以外からの起動が拒まれた記録を #346 に残す。
- **EV-0137 の差し替え条件**を、対の確認へ改めます(規格・品質保証)。
  - (a) 配備の環境を使うジョブが、既定ブランチ以外から拒まれること。
  - (b) `environment:` を外して書き込みの権限を宣言したワークフローが、書き込めるかどうか。

  (b) は使い捨ての参照で確かめ、`dist/standard` そのものでは試しません。(a) だけを適合の証拠に数えないことを書きます。

## R-4 採用者とテンプレート

**裁定**:

- 採用者への指針は、R-1 の文と `ci-gates.md` の表に置きます。GITHUB_TOKEN で配備する構成は未達とし、狭める措置を記録します。
- テンプレートにデプロイの雛形は足しません。意図した省略として明記します(IMPL-0237 は undelivered のまま)。
- env-check が、次を読むようにします(現場・品質保証・規格の3委員)。
  - Workflow permissions の既定
  - Actions による PR の承認の可否
  - Environment(`delegated-merge` を含む)の配備の参照の限定

  読めない場合(403 など)は「未確認」と出し、通過にしません。適合の判定には使わず、事実として出します(ADR-0071 決定3。擁護者)。新しい実装マークを付けます。
- テンプレートの最上位の書き込み権限をジョブ単位へ下ろすことと、`delegation.yml` の `pull_request_target`・`workflow_run` の機械の検査は、後継の Issue の候補にします。最小権限の衛生であって、G-8 の資格情報の置き場とは別の論点だからです。

## 却下の一覧(ADR-0090 に理由とともに残す)

| 案 | 理由 |
| --- | --- |
| 短命を理由に GITHUB_TOKEN を認める | 指針は短命とレビューへの結び付けを別の要求とする |
| 「起動者が持たない能力」に条項の目的を読み直し、条件つきで認める | PR の自己承認・権限の昇格・名義の消失の3経路。保護の無い配布先だけが適合になる |
| 条項を置き場の指定のまま保つ | OIDC と検証する受け手(推奨される形)が不適合になる |
| 本リポジトリを「適用外」とする | 採用者が `dist/standard` を submodule で固定する。手段はある |
| 鍵を置く | 所有者の指示(前提) |
| Environment・CODEOWNERS・ワークフロー実行の保護を適合の手段に数える | 経路を止めない |
| 一般の語「資格情報」を 1.4 で定義する | 他の節の範囲と衝突する |
| EV-0137 の「拒まれた記録」だけで差し替える | Environment を外した経路を確かめない |
| テンプレートにデプロイの雛形を足す | 未達を雛形として配ることになる |
