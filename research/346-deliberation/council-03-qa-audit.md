## 0. 攻撃者の側から見た要点

議題の前に、各議題が共通して頼る事実を、攻撃者の側から整理します。

1. **GITHUB_TOKEN の書き込みは、ワークフローのファイルを書ける者なら誰でも得られる**。所有者がリポジトリの設定を変えても止まらない。「Anyone with write access to a repository can modify the permissions granted to the `GITHUB_TOKEN`」[確: GitHub Docs「Managing GitHub Actions settings for a repository」、2026-10-27 閲覧][外 1.2]
2. **トークンが起動者の能力を超える経路がある**。議題 R-1 の論点「起動者が自分の書き込み権限で既にできることを超えない」は、次の3つで崩れる
   - (a) 「Allow GitHub Actions to create and approve pull requests」が有効なら、GITHUB_TOKEN は PR を承認できる。書き込み者は、自分の PR を自分のブランチのワークフローで承認させられる。必須レビューの1件を、人の承認ではないものが満たす[確: 同頁。個人所有のリポジトリの既定は無効、組織では組織の設定を継ぐ]
   - (b) 起動者の資格情報が持たない権限(`packages`・`actions`・`pages`・`deployments`・`id-token` など)を、ワークフローの `permissions` で得られる。権限を絞った GitHub App やトークンで動く AI エージェントでも、ワークフローのファイルを書ければ、そのリポジトリの全権限の書き込みへ広がる[外 1.2 から導出]
   - (c) 書いた主体が `github-actions[bot]` になり、git の履歴から人が消える。監査人は Actions の実行の記録(起動者・head_branch・event)を突き合わせない限り、誰が配布したかを特定できない[内 3.3、project-management.md L113 が既に突き合わせを要すると書く]
3. **ワークフローのファイルを書けるかは、資格情報の側の権限で決まる**。OAuth・classic PAT は `workflow` スコープ、GitHub App・fine-grained PAT は Workflows 権限が無いと、`.github/workflows/` のファイルを作成・更新する push は拒まれる。GITHUB_TOKEN 自身もワークフローのファイルを書き換えられない[未: 本委員の知識。この審議では一次資料を読めていない。外部調査にも無い]。これが正しければ、AI エージェントと乗っ取られた限定のトークンに対しては、プランに依らず使える数少ない予防の統制になる。ただし、所有者が人の PAT や gh のログインのトークン(`workflow` スコープを含むことが多い)を AI のセッションへ渡す運用では効かない
4. **本リポジトリで最大の穴は、GITHUB_TOKEN ではない**。内部調査の時点で、この環境の AI のセッションは保守者の `permissions.admin: true` のトークンで `gh api` を呼べていた[内 冒頭]。管理者のトークンを持つ主体には、ブランチのワークフローを経由する必要がない。直接 `dist/standard` へ push でき、Environment とルールセットも書き換えられる。第5章 5.8.6 要求事項1(認証情報・秘密情報への接触は実行時に拒否する)と突き合わせるべき事実です(本委員が 2026-10-27 に `gh auth status` を実行した時点では、トークンは無効と出た[確])
5. **fork の PR は主な脅威ではない**。public のリポジトリでは、`pull_request` の GITHUB_TOKEN は読み取りに落ち、秘密情報も渡らない[外 1.2]。危ないのは `pull_request_target` と `workflow_run` で、どちらも既定ブランチのファイルが、書き込みのトークンで、fork の生成物や本文を扱う。準拠テンプレートの `delegation.yml` は両方を持つ(R-4)
6. **`dist/standard` には受け手がいる**。採用者は submodule で `dist/standard` の版を固定する(project-management.md L104、standard-editions.md L53)[確]。書き込み者が `dist/standard` へ積んだ中身は、採用者の手元へ流れる。「個人の docs-as-code だから影響は小さい」とは言えません

## R-1 条項は、ジョブの権限で発行される短命のトークンをどう扱うか

### 結論

**「満たしたもの」としては認めない。手段として使うことは禁じない。使った場合は、到達を参照に結び付けていないことを未達として開示させる。** あわせて、条項を手段(秘密情報)ではなく性質(到達の参照への結び付け)で書き直します。これにより、受け手が参照を検証する短命の資格情報(OIDC を受け手が検証する形。GitHub Pages の配備が先例)は、秘密情報が無くても満たす側に入ります。

### 理由

- 条項の第1文の対象は、統制を「起動元のブランチで書き換えられる場所の中**だけ**」に置く形です。ジョブの `permissions` は、その場所そのものです[外 1.2・1.4][内 1.1]。Environment はトークンを限らないので、`environment:` を消したジョブには何も掛かりません[外 1.4]。「短命」は、漏えいした後に悪用できる時間を縮めます。誰が発行させられるかは変えません。OWASP CICD-SEC-6 と SEC-4・SEC-1・SEC-5 も、この2つを別の要求として立てています[外 2.1・2.6]。短命を代わりに数える根拠は見つかりません[外 5.1]
- 「起動者の能力を超えないなら新しい能力ではない」という読み直しは、監査で確かめられません。成り立つかどうかが、ファイルの外の、標準が確かめさせていない設定に依るためです。0 節 2 の (a)〜(c) がその例で、(a) は組織の設定を継ぐので、案件の側からは見えないことさえあります。成り立つと言い切るには、書き込み者の全員について「トークンで届く範囲 ⊆ 本人の資格情報で届く範囲」を示す必要があります。そのための記録の様式は、標準にもテンプレートにもありません
- 配備先が同じリポジトリで、書き込み者が配備先へ直接 push できる場合は、確かにトークンは最も弱い環ではありません。しかし、それは「満たした」ではなく「配備先がそもそも参照で守られていない」状態です。どちらの理由でも「既定ブランチだけが配備に届く」という主張は成り立たないので、開示の値は未達です(ADR-0028)
- 未達の範囲を「使えない場合」に限る今の文は、手段を使えるのに使わないと決めた場合を書いていません[内 1.1・6.2]。読み手が「使えるのに使わない形は禁止なのか、黙っていてよいのか」を判別できません。CLAUDE.md の「書かれていない」と「課さないと決めた」の区別に反します

### 他の案を落とす理由

- **認める(短命なら満たす)**: 外部の指針に反します。SLSA の Trusted Robot は「identity and codebase cannot be unilaterally influenced」を条件にしており、ブランチで書き換えたワークフローのトークンは当たりません[外 2.2]。監査人が「短命なら満たす」を受け入れると、本標準の G-8 の主張は、配備先を書ける全主体の数に比例して弱くなります
- **条件つきで認める(起動者の能力を超えなければ満たす)**: 上の理由で、条件の成立を確かめられません。どうしても採る場合は、条件を「確かめられる設定の値」で列挙させる必要があります。(1) 配備先が同じリポジトリの参照に限られる、(2) Actions の PR 作成・承認が無効、(3) 配備先の参照を書ける主体の一覧、(4) その全員がワークフローのファイルを書ける権限を持つ、の4つです。(4) は「誰でもトークンを作れる」ことの確認であり、統制が成り立っている証拠ではありません。そのため、この案は満たした扱いの根拠になりません
- **禁止する(GITHUB_TOKEN で配備してはならない)**: 採りません。鍵を持たないことには利点があります(漏えいする長期の秘密が無い)。禁止すると、鍵を置けない組織は「規範違反」か「鍵の導入」の二択になり、後者は所有者の前提に反します。開示させる方が信頼性が高いと考えます

### 文の案(G-8「配備の統制と資格情報の置き場」の書き直し。採用済み ADR は書き換えず、新 ADR で決める)

> 配備・配布の資格情報への到達は、配備を許す参照(既定ブランチ、またはリリースのタグ)に結び付けます。結び付けは、起動元のブランチで書き換えられない場所で行います。次のどちらかに当たる場合に、結び付けたものとします。
>
> - 資格情報を、配備を許す参照に限った実行環境の秘密情報に置いている
> - 資格情報を受け取る側が、発行を求めた実行の参照と実行環境を検証し、配備を許す参照からの求めにだけ応じている(OIDC の主張を受け手が検証する形など)
>
> ジョブの権限から発行される短命のトークン(GitHub Actions の `GITHUB_TOKEN` など)の権限を、ワークフローのファイルで与える形は、結び付けたものとして扱いません。有効期間が短いことを、結び付けの代わりにしません。この形で配備・配布する場合、および実行環境の秘密情報や配備の参照の限定を使えない場合は、この規定を満たせません。**満たしたものとして扱わず、保証の開示に未達として記録します**。記録には、配備先へ届く主体(配備先の参照を書ける主体と、ワークフローのファイルを書ける主体)と、残した検出の手段を書きます。

- 既存との矛盾: ADR-0077 の標準の部分(「資格情報は…秘密情報に置きます」)を広げます。手段の列挙に OIDC の受け手の検証を足す変更で、ADR-0077 の本文は書き換えず、新 ADR に置きます。ADR-0028 とは整合します(未達の範囲を広げるだけ)。EV-0137 の対象の文は変わるため、EV を新しく採番し、0137 は再利用しません

## R-2 何が止めるか。語の定義

### 結論

R-1 で満たした扱いにしないため、R-2 の各手段は「満たす手段」ではなく、**未達のまま残す予防と検出の手段**として、ci-gates.md の対応表へ置きます。各行に「何を止めるか/止めないか/監査で何を見れば成立を確かめられるか」を併記します。語は G-8 の節の中で定義し、1.4 へは「資格情報」だけを足します。

### 手段の評価(攻撃者の側から)

| 手段 | 止めるもの | 止めないもの | 監査で確かめる方法 | 根拠 |
| --- | --- | --- | --- | --- |
| Workflow permissions の既定を read | `permissions` を書かないワークフローの書き込み | `permissions` を明示した昇格 | API `actions/permissions/workflow` の `default_workflow_permissions` | [外 1.2][確] |
| Actions の PR 作成・承認を無効 | トークンによる自己承認(0 節 2a) | 配備先への書き込み | 同 API の `can_approve_pull_request_reviews` | [確] |
| 資格情報の Workflows 権限・`workflow` スコープを持たせない | AI エージェントと限定のトークンによるワークフローの設置 | 人の書き込み者、`workflow` スコープ付きのトークンを渡された AI | App の権限は見える。個人の PAT・OAuth のスコープは管理者から見えない | [未] |
| ワークフロー実行の保護(起動する主体・イベントの許可リスト) | 許可していない主体(AI の App、Copilot)の push・dispatch による起動 | 許可した主体、参照の限定 | ルールセットの API(評価モードの記録を含む) | [外 1.7]。個人所有の public で使えるかは未確認 |
| 配備先の参照の削除・強制 push の禁止 | 痕跡の消去 | 早送りの書き込み | ルールセットの API | [内 3.4] 本リポジトリは未設定 |
| 配備先の参照の更新を制限 | 全ての書き込み | バイパス主体 | ルールセットの API | GITHUB_TOKEN をバイパスに入れられず、配布も止まる[外 1.5・1.6] |
| CODEOWNERS とルールセットで `.github/workflows` の変更にレビューを課す | 未レビューのワークフローの既定ブランチへの取り込み | **ブランチ上での実行**(攻撃の本体) | ルールセットの API | [外 2.4] |

- 攻撃者の側から言うと、**予防の効く手段は「主体の側」(Workflows 権限、ワークフロー実行の保護、PR 承認の無効)にしかありません**。参照の側の手段は、GITHUB_TOKEN には効かないか、配布も止めます。外部調査 5.2 の「主体側か下流側」と同じ結論です
- 「`.github/workflows` へのレビュー」は、標準で予防として数えてはなりません。ブランチへの push で実行は始まるためです[外 2.4 推論]。本委員が最も誤読を恐れる行です
- 来歴の証明と事後の突合は、ADR-0052 決定1(配る仕組みではなく、配布物そのものを検査する)と同じ向きです。鍵を置けない前提の下で、監査人が統制を確かめられるのはこの2つだけです

### 語の定義(G-8 の節の中に置く案)

> - 資格情報: 配備先・配布先へ書き込む権限を与えるもの。長期の鍵、秘密情報に置くトークン、ジョブの権限から発行される短命のトークン、OIDC の主張と引き換えに受け手が発行する短命の資格情報を含む
> - 結び付け: 資格情報を得られる実行を、配備を許す参照からのものに限ること。限るのは、起動元のブランチで書き換えられない設定、または受け手の検証である

- 「秘密情報」「実行環境」は今の対応表(ci-gates.md L903〜909)で足りるので、定義しません。「資格情報」は 3.5 の「認証情報(トークン)」と 5.8.6 の「認証情報・秘密情報」でも使われます。G-8 の定義を全章へ広げるかは、別の突合が要ります。本議題では G-8 の節に限ります
- IMPL-0237 の降ろし先の説明(`impl-targets.yaml` の `deploy-workflow`、「既定ブランチに限った」)は、本文の「既定ブランチ、またはリリースのタグ」に合わせて直します[内 1.1]。タグからの配備はタグの作成を限らなければ同じ穴です(ci-gates.md L899)。タグを外した説明のまま降ろすと、監査の確認項目からタグが抜けます

## R-3 本リポジトリの配布

### 結論

1. 当面は**未達として開示を続けます**。「適用外」とはしません。本リポジトリは本標準に従う案件ではありませんが、`dist/standard` は採用者が submodule で取り込む配布物です。受け手から見て、保証が無いことを書くべきです
2. **開示は実状に合わせます**。ADR-0077 決定6 と project-management.md の記述は、リモートでまだ動いていない形を書いています。リモートの main では、旧 `publish-standard.yml`(最上位 `contents: write`、Environment なし、強制 push、`workflow_dispatch`)が動いています。ルールセットは空です[内 3.4]。今の開示は、実状より強い統制を読み手に想像させます。監査では、記録と実状の不一致そのものが指摘の対象になります
3. 鍵を使わずに条項を満たす経路は、**配布の置き場を、受け手が参照を検証する経路へ移すこと**だけです。例: GitHub Pages(`github-pages` 環境を main に限れば、GitHub が OIDC で参照を検証する[外 1.8])の下に配布物を置く。または、`dist/standard` を残したうえで来歴の証明を付け、採用者に検証させる。前者は採用者が submodule で固定する形を変える(公開インタフェースの変更)ため、本会議体では決めず、別の Issue で扱うことを提案します
4. **EV-0137 の差し替え条件の試験は、設計を直します**。今の条件「既定ブランチ以外から起動した配布が拒まれた記録」は、`environment: dist-standard` を書いたジョブを main 以外で走らせて Environment が拒むことしか確かめません。攻撃者は `environment:` を消します。拒まれた記録は「統制が成り立つ」証拠に見えますが、実際は統制が成り立たないことを隠します。試験には、**`environment:` を持たないワークフローを作業ブランチに置き、試験用の参照(例: `dist/test-346`)へ書き込む**変種を含めます。この変種は成功すると予想しています。成功した記録を、未達の開示の根拠として残します

## R-4 採用者とテンプレート

### 結論

1. ci-gates.md の対応表に、GITHUB_TOKEN の行を足します。中身は「ジョブの `permissions` による付与は結び付けにならない(未達)」「Workflow permissions は既定であり上限ではない」「Environment は GITHUB_TOKEN を限らない」です。あわせて、R-2 の手段の表(止めるもの/止めないもの/監査で見る値)を置きます
2. **env-check に、Actions の権限と Environment を読ませます**。読む値は `actions/permissions/workflow`(`default_workflow_permissions`・`can_approve_pull_request_reviews`)と、`environments/<名>`(配備の参照の限定・保護規則)です。読めない(403 など)場合は「未確認」と出し、通過にしません。template-repository.md L114 のルールセットの扱いと同じです[内 1.4]。内部調査が 403 で読めなかった事実は、採用者の環境でも同じことが起きうることを示しています
3. **テンプレートの workflows の最上位の書き込みの権限は、ジョブ単位へ下ろします**。理由は、同じワークフローの中で書き込みを要しないジョブ(第三者のアクションを含む)へ、書き込みのトークンを渡さないためです(OWASP CICD-SEC-5、Scorecard の Token-Permissions[外 2.1・2.5])。これはブランチ上の昇格を止めないので、統制としては数えません。本リポジトリの check-ci-wiring 条件5 に当たる検査をテンプレートにも置くことを提案します
4. **`delegation.yml` は監査の重点に置きます**。`pull_request_target` と `workflow_run` は、fork の PR から、既定ブランチのファイルを書き込みのトークンで動かします。今は既定ブランチを `persist-credentials: false` で checkout しています[内 4]。PR の側の本文・生成物を実行しない、または評価式へ埋め込まないことを、機械の検査で確かめるべきです(OpenSSF Scorecard の Dangerous-Workflow と同じ観点[外 2.5])
5. 採用者が GITHUB_TOKEN で配備する場合の指針は、R-1 の文(未達として開示)をそのまま当てます。テンプレートにデプロイのワークフローの雛形を足すかは、IMPL-0237 の降ろし方として別に決めます。雛形を足す場合は、OIDC の受け手の検証(Pages、クラウドの配備)を既定の形にします

- 既存との矛盾: ADR-0040(テンプレートは第6章の部分集合)とは無関係です。env-check の拡張は、#314 で IMPL-0236 を manual へ下げた理由(実機で確かめていない)を解消する方向で、矛盾しません

## R-5 記録

### 結論

1. 新しい ADR を起こします。ADR-0077 決定6 の運営は置き換えず、その未決の点(「#293 で別に扱う」)を決着させる ADR として、ADR-0077 から参照される関係にします。ADR-0077 の本文は書き換えません
2. **手続きの逸脱を、新 ADR の「経緯」に事実として書きます**。書く内容は、コミット b185611 が deploy key 方式(#293 裁定 J-6 b・d)を、調査・会議体・突合を経ずに GITHUB_TOKEN 方式へ改めたことと、本会議体がそれを事後に評価したことです。監査の立場では、所有者の決定が先にあったこと自体は問題ではありません。決定の後に検証の記録が無いまま、規範と運営の食い違いを「開示した」の一文で閉じていた点が問題です
3. **所有者の指示の記録**: 公開の記録の「保守者の決定、2026-10-23」は、監査には足りています(決定者の役割と日付がある)。原文は issues-context.md にあります。新 ADR からその所在を参照すれば足ります。文言を ADR の本文へ写す必要はありません
4. `research/293-deliberation/implementation.md` は deploy key 方式の記録のままです[内 2.2]。追記の節(「2026-10-23 の変更で GITHUB_TOKEN 方式へ改めた。#346 を参照」)を足します。調査メモなので、採用済み ADR の不変の規則には当たりません
5. 記録と実状の不一致(R-3 結論2)を、新 ADR の「影響」に書きます。ADR-0077 の「影響」は、リモートに入った後の形を書いているためです

## 自分で確かめた主張と、確かめていない主張

- 確かめた: Workflow permissions の既定と昇格、PR 作成・承認の設定とその既定(GitHub Docs の該当頁、2026-10-27)。publish ジョブの形、`graphify-update.yml` の `contents: write`、CODEOWNERS が `*` の1行であること、採用者が submodule で `dist/standard` を固定すること(リポジトリのファイル)
