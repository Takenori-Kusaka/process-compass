# 会議体 #346 意見書 05: 既存決定の擁護者(defender)

- 作成: 2026-10-27。立場: G-8「配備の統制と資格情報の置き場」の現行の条項、EV-0137、ADR-0077(とくに決定6)、ADR-0052 を擁護する。条項を緩める変更が本当に必要か、所有者の運用上の都合で規格を曲げていないかを問う
- 読んだもの: issues-context.md、council-00-agenda.md、survey-346-1-internal.md(以下「内部」)、survey-346-2-external.md(以下「外部」)。本文を直接確かめた箇所: gate-criteria.md G-8 の節(L1190〜1197)、ci-gates.md L895〜924、ADR-0077 決定6・検討した選択肢・影響、ADR-0052 決定1〜4、ADR-0028 冒頭、project-management.md「止まらない経路」「管理者の設定」、`src/data/impl-targets.yaml` の `deploy-workflow`
- 前提: 鍵(deploy key・秘密情報に置く長期のトークン)を設定する案は採らない(所有者の指示)。この前提は「本リポジトリの運営の手段」を縛るものであり、**規格の要求事項を縛るものではない**。以下はこの区別を軸にする

## 0. 立場の要約

1. #346 の発端は、規格の欠陥の報告ではなく、**本リポジトリの運営が規格を満たさなくなった**ことである。ADR-0077 決定6 はそれを自ら開示している。発端が規格の作者自身の1件である変更で、規格を緩めることを最も警戒する
2. 擁護の対象は「規範の目的」と「規範が既に正しく捉えている機序」である。**文言の誤りや説明の誤りは擁護しない**。調べた結果、現行の本文には、擁護すべきでない誤りが2つある(ci-gates.md L899 の「実行環境の配備の参照の限定だけが、この経路を止めます」は GITHUB_TOKEN について誤り。IMPL-0237 の降ろし先の説明がタグを落としている)。これは直す。直す向きは締める側か中立であり、緩める側ではない
3. 結論: 条項は緩めない。GITHUB_TOKEN をワークフローの `permissions` で書き込みへ上げる形は、G-8 の第1文が禁じる「起動元のブランチで書き換えられる場所の中だけに置いた資格情報」そのものであることを本文で明示する。本リポジトリは未達(不適合)として開示を続け、その理由が「プランの制限」ではなく「保守者の選択」であることを隠さない

## R-1 条項は、ジョブの権限で発行される短命のトークンをどう扱うか

### 結論

**認めない**(条件つきの許容も置かない)。ワークフローのファイルの `permissions` から書き込みの権限を得る短命のトークンは、G-8 の第1文の「起動元のブランチで書き換えられる場所の中だけに置いた資格情報」に当たる、と本文で明示する。あわせて、手段を使えるのに使わない場合も未達として記録することを明示する(締める側の明確化)。

ただし1点だけ、目的を保ったまま文言を正す。第2文の「秘密情報に置きます」は手段の指定であり、目的は第1文にある。**配備を許す参照を、ブランチの外にある受け手が検証する短命の資格情報**(OIDC のクレームを配備先が検証する形。GitHub Pages の deploy-pages が先例。外部 1.8)は、第1文の目的を満たす。これを現行の文言は「秘密情報に置いていない」として不適合へ倒す。これは緩和ではなく、目的と手段の取り違えの修正である。

### 理由

1. **機序は既に本文と ADR が捉えている**。ci-gates.md L899 は「書き込みの権限を持つ者は、自分のブランチへ置いたワークフローから、リポジトリの秘密情報とトークンの書き込みの権限に届きます」と書き、ADR-0077 決定6 は「`GITHUB_TOKEN` は Environment に属さないため、限定は資格情報の置き場にはならない」と書く。外部調査(1.2〜1.6)は、Workflow permissions が上限ではなく出発点であること、Environment がトークンの権限を限らないこと、ルールセットのバイパスに GITHUB_TOKEN を入れられないことを一次資料で裏付けた。**規範の前提は調査で崩れていない。崩れたのは本リポジトリの運営だけである**
2. **「短命」は条件にならない**。OWASP CICD-SEC-6(短命を優先)と SEC-4・SEC-1・SEC-5(未レビューのコードに資格情報を渡さない)は別の要求である(外部 2.1・2.6)。短命は漏えい後の悪用の期間を縮めるが、「誰が発行させられるか」を変えない。G-8 が防ぐのは後者である。短命で後者を代替する根拠は外部調査で見つかっていない。SLSA v1.2 の Trusted Robot の定義(「codebase cannot be unilaterally influenced」)にも当たらない(外部 2.2)
3. **議題の論点「起動者が既に持つ能力を超えないなら新しい能力を与えない」への反論**。この論は、配備先が人に対しても保護されていない場合に限って成り立つ。配備先をルールセットの Restrict updates で守れば、ルールセットは GITHUB_TOKEN にも掛かり、トークンでも書けない(外部 1.5・1.6)。つまり「トークンが起動者の能力を超えない」状態とは、**配備先が誰にも守られていない状態**のことである。その状態を「条件を満たすので適合」と書けば、統制の無い配布を適合と呼ぶことになる。目的の読み直し(「起動者が持たない能力への到達を防ぐ」)は、この帰結を招くため採らない
4. **G-8 は資格情報だけでなく「配備・配布の統制」を対象にしている**。第1文の主語は「統制と資格情報」である。本リポジトリでいえば、`npm run check` を通った版だけを配る(ADR-0077 決定4、ADR-0052 決定1)という統制が、ブランチ上のワークフローで外れる。起動者が自分で直接 push できるとしても、それは統制の外の経路が別にあるということであり、ワークフローの中の統制が有効になる理由にはならない
5. **同じリポジトリへの書き込みでも、配布は「外部への発行」である**。`dist/standard` は準拠テンプレートと採用者が取り込む参照である。準拠テンプレートの CLAUDE.md は「外部への発行」を取り消せない操作(c)に挙げる。「自分のリポジトリへの書き込みだから軽い」という読みは、本標準の別の規定と整合しない
6. **条件つき許容は、採用者が監査できない**。「トークンの権限が、起動し得る全主体の権限を超えない」を確かめるには、ワークフローの全ての権限(`contents`・`pull-requests`・`actions`・`packages`・`id-token` など)、OIDC の受け手の信頼条件、ルールセットのバイパス、全ての書き込み主体(AI のセッションを含む)を突き合わせる必要がある。他組織が従う規格の適合の条件として、判定の再現性が低い。特に `id-token: write` は、受け手の信頼条件がリポジトリ単位なら、起動者が持たない外部の権限へ届く(外部 1.8 の推論。受け手次第)

## R-2 何が止めるか。語の定義

### 結論

R-1 で認めないため、「認める場合に何が止めるか」は**ブランチの外に置く手段の一覧として、止めるもの・止めないものを ci-gates.md の対応表へ明記する**形で答える。止めないものを止めないと書くこと(却下の明記)に重点を置く。語の定義は G-8 の節の中に置き(R-1 の文の案)、1.4 には置かない。IMPL-0237 の降ろし先の説明を本文に合わせて直す。

## R-3 本リポジトリの配布

### 結論

**条項に合わせて条項を曲げることはしない。未達として開示を続ける**。「適用外」とは書かない。新しい ADR で ADR-0077 決定6 の「#293 で別に扱う」を「規範の側では解かない。運営の側で、鍵を置かない制約の下では満たせないことを未達として開示し続ける」と決着させる。そのうえで、**現にリモートで動いている旧ワークフローの方が、開示している形より悪い**ことを最優先で正す。

### 理由

1. **規格の作者の運営を、規格の側で適合へ寄せることは、ここで最も避けるべき形である**。発端は本リポジトリの1件で、本リポジトリは「本標準に従う開発の案件ではない」(ADR-0077 L70)。ADR-0077 自身が、配布用のブランチの保護を独立の要求事項にしない理由を「根拠は同じ作者の2件に留まる」と書いた。同じ物差しを、緩める側にも当てる。単一事例・同じ作者で規範を緩めるのは、EV-0137(E1)より弱い根拠で E1 の規範を動かすことになる
2. **所有者の指示は手段を縛るが、適合の判定を縛らない**。「鍵を設定しない」を受け入れることと、「鍵を設定しない形を適合と呼ぶ」ことは別である。前者は運営の決定、後者は規格の改変である。本意見書は前者を前提として受け入れ、後者を拒む
3. **「適用外」と書かない理由**。G-8 の本節には適用範囲の限定が無く、#293 の実装記録は「自動のデプロイ・配布を持つすべての案件に掛かる」として見出しに付けなかった(内部 1.1)。本リポジトリは案件ではないが、適用外という語を使うと、採用者が「配布用のブランチは適用外」と読む先例になる。「案件ではないが、規範を書いた側の運営が規範を満たさない」を未達の語で開示する現行の ADR-0077 の書き方が正しい
4. **リモートの実状が開示と食い違っている**(内部 3.4)。リモートの main では、旧 `publish-standard.yml` が最上位 `contents: write`、Environment なし、**強制 push**、`workflow_dispatch` ありで動き、ルールセットもブランチ保護も無い。ADR-0077 決定6 が開示する形(履歴を積む、publish だけに書き込み、削除・強制 push の禁止)は、まだどこでも動いていない。開示を続けるなら、開示どおりの状態にすることが先である。いまの状態では、強制 push で配布の履歴を消せる
5. **条項に合わせる、鍵を使わない手段の候補は1つある**: 配布物を `dist/standard` の `git push` ではなく、OIDC と Environment で参照を検証する GitHub Pages の配備に載せ、受け手がそこから取得する形(外部 1.8 の先例の応用)。ただしこれは配布の経路(受け手から見た公開のインタフェース)を変える選択であり、準拠テンプレートの取得手順(submodule)に影響する。本会議体で採るとは決めない。**候補として新しい ADR の検討した選択肢に記録し、採否は別 Issue で調査する**(推論。一次資料で手順を確かめていない)

## R-5 記録

### 結論

1. **新しい ADR を起こす**(ADR-0077 の置き換えではなく補足)。内容: (a) G-8 は緩めない、(b) R-1・R-2 の明確化(ジョブのトークンは置き場にならない、OIDC の形、使わないと決めた場合も未達)、(c) 本リポジトリは未達の開示を続け、ADR-0077 決定6 の「#293 で別に扱う」をここで決着させる、(d) 検討した選択肢に「条件つきで認める」「目的の読み直し」「適用外とする」「Pages の配備に載せ替える(別 Issue)」を却下・保留の理由つきで残す
