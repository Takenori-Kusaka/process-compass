## 前提として共有したい現場の事実

1. **標準は月に数十回変わる**(確認: 直近1か月で docs を変えたコミットが 33)。コミット単位を「版」にすると、案件は毎日違う版に従っていることになり、顧客への説明が成り立たない。改訂ごとに全案件が移行作業をするなら、採用は続かない
2. **顧客・監査人が見るのは見出しの1語**である。添付の一覧は読まれない前提で語を選ぶ必要がある。「適合」と書けば、逸脱の併記は読み飛ばされる
3. **逸脱は小さな体制だけの話ではない**(確認: `roles-responsibilities.md:552` の認証情報の分離は人数を条件にしない)。10名の案件でもトークンを分けられない構成はある。2名の体制でも、G-6 の確認者を確かめれば未達は解け、G-7 の逸脱だけが残る(確認: `overview.md:382`、ADR-0029)。つまり「未達も欠落も無いが、逸脱はある」構成は現に生じる

## Q-1 標準の版の付番と改訂時の扱い

### 結論

1. 版は**発行した時点の断面**だけに付ける。`main` の各コミットは版ではない(未発行)。適用の表明・適合の主張には未発行の断面を引かない
2. 付番は **「第N版」(連番)+ 発行日**。意味を変えない修正は **「第N版 訂正M」**
3. 版を上げる変更(規範の変更)と、訂正で済む変更を、**適合の主張に要る作業が変わるか**で分ける。迷ったら規範の変更として扱う
4. 改訂時の既存案件: **旧版のまま続けてよい。新版への適合を主張しない**(FAA AC 20-115C 型)。旧版の主張に期限を設けない。新たな適用の開始は、その時点の最新版による
5. 版ごとに**移行の要否の一覧**(規範の変更ごとに、既存の構成で新たな未達・作業が生じるか、生じるなら手順)を発行物に付ける
6. 標準は、版を**取り下げる**ことができる。取り下げは理由と日付を公表し、取り下げ日より後の範囲について、その版への適合を主張しない
7. 準拠テンプレートは、案件が従う版を `process.config.json` に記録する。版の切替は `/process-change` の新しい種別として `changeLog[]` に残す

### 理由

- 現場が顧客へ言える文は「第3版に適合」であって「コミット f383ee2 に適合」ではない。`qms-document-control.md:90` は、ハッシュが監査の場で版として通用しないと本標準自身が書いている(内部 2節)。自分が採用組織へ課していることを、自分が守っていない状態は、規格の信頼を損なう
- **連番を採るのは、監査人が欠番と前後関係を確かめられるから**である(`qms-document-control.md:90` の「連続性と前後関係」)。日付だけの版名(`2026-11 版`)は、同じ月に2回出したとき・飛ばしたときに前後関係が名前から読めない
- 訂正の層を設けるのは、移行作業を発生させない改訂を先に定義するためである(外部 10.3 OpenAPI「記述方法は変えない」、10.2 SLSA「レベルの意味は変えない」)。訂正で主張がやり直しにならないことが保証されていれば、現場は訂正を無視してよいと判断できる。**無視してよいものが分かること自体が、作業を減らす**
- 期限を設けない理由: 本標準には認証の制度が無い(`overview.md:384`)。外部の 36 か月の移行は認証機関が審査で強制する仕組みで、強制する主体が無い本標準が期限だけ書いても、守られたかを誰も確かめない。代わりに、**主張できる文を版で縛る**(外部 8節・10.6)。旧版の主張は旧版の主張として真であり続け、読み手は版を見て判断できる
- 新たな適用の開始を最新版に限るのは、準拠テンプレートから始めれば自然にそうなり、追加の手間が無いからである。古い版で新しく始める理由は現場にほぼ無い
- 移行の要否の一覧が無いと、各案件が差分を自分で読んで影響を推定することになる。これは案件の数だけ同じ作業を繰り返す、典型的な無駄である。標準の側で一度書けば済む
- 取り下げを置くのは、規範に欠陥(例: 塞いだはずの経路が開いていた)が見つかった版に、期限なしで適合を主張させ続けると、読み手を誤らせるからである。期限を一律に置かない代わりに、問題のある版だけを個別に止める

### 落とす案と理由

| 案 | 落とす理由 |
| --- | --- |
| コミット・実行番号のまま(現状) | 自己の規定(`qms-document-control.md:90`)に反する。月に数十の「版」が生じる |
| 意味つきの版(major.minor.patch) | プロセス標準では「互換」の定義が立たない。要求事項を1つ足すのは major か minor か、で毎回もめる。現場が知りたいのは互換性ではなく「自分に作業が要るか」で、それは移行の要否の一覧が直接答える |
| 日付だけの版名 | 前後関係・欠番が名前から読めない(上記) |
| 規範の変更ごとに即時に版を発行 | 現状の変更頻度では版が週に複数出る。版を出す間隔は標準の運営が決めてよいが、版の発行は `main` への push と切り離す |
| 移行期間(36 か月等)と旧版の失効 | 強制する主体が無い。全案件に定期の移行作業を課し、信頼性は上がらない(主張は版つきで既に区別できる) |
| 進行中の案件に新版を強制 | `improvement-cycle.md:151` が採用組織のプロセス定義について「着手時の版のまま完走」を勧めており、標準自身の改訂だけ逆にする理由が無い |

### 文の案(第1章 1.10 の下に新設。節番号は仮に 1.10.4)

> ### 1.10.4 本標準の版
>
> 本標準は、発行した断面に版を付けます。版は「第N版」と発行日で識別します。意味を変えない修正は「第N版 訂正M」として発行します。発行していない断面を、適用の表明と適合の主張に引きません。
>
> - 適合の主張に要る作業を変える変更は、版を改める。要求事項・禁止事項の追加・削除・強さの変更、適用範囲の変更、ゲートの基準と様式の必須欄の変更、テーラリングの規則データの変更がこれに当たる
> - 前項に当たるかを判断できない変更は、版を改める変更として扱う
> - 訂正は、適用の表明と適合の主張のやり直しを要しない
> - 版を改めるときは、規範の変更ごとに、既存の構成に新たな未達または作業が生じるかと、生じる場合の手順を、発行物に添える
> - 適用の開始は、その時点で発行されている最新の版による
> - 適用の開始の後に版を改めることは、案件が選ぶ。旧い版のまま続けてよい
> - 適用の表明と適合の主張には、案件が従う版を書く。従っていない版への適合を主張しない
> - 本標準は、版を取り下げることがある。取り下げの理由と日付を公表する。取り下げ日より後の範囲について、取り下げた版への適合を主張しない
>
> **旧い版の主張に期限を設けません**。意図的な決定です。本標準には認証の制度が無く、期限を確かめる者がいないためです。版の区別は、主張の文に版を書くことで行います。

`:::caution[暫定 EV-NNNN / 見直し 2027-10]` — 旧い版の主張を期限なしに認めることが、読み手を誤らせないかの実証は無い。差し替え条件: 取り下げの発生件数と、旧版の主張が新版の欠陥修正を知らずに引かれた事例の観測。

### 既存の ADR・条項との突合

- ADR-0077(配布)・ADR-0052: 版は `dist/standard` の配布物に付け(タグと `VERSION.md` の人が読める欄)、受け取り側で検査する。矛盾しない。#331 論点4 はこの実装になる
- `check-template-drift.mjs` が `source.commit` を比較から外す件(内部 7節6): 版の欄は外さずに検査する。規則データが変わったのに版が変わらない状態は検査で落とせる(規則データの変更は定義上、版を改める)
- `template/README.md:471-489`(テンプレート更新の既存案件への影響): 標準側の規定が無いまま運用規律だけがある状態を、上の条項が受ける。矛盾しない。README の該当節は本条を引く形へ寄せる
- ADR-0068 決定1・2: 版の切替は適用の開始を動かさない(Q-5 と合わせて明記)。新版で増えた要求事項は、切替の時点から未達として表示される(決定2 の「同時に適用」と同じ向き。経過措置を設けない)

## Q-2 適用の終了

### 結論

定義する。事象は2つに限る。

1. **案件の終了**(中止・廃止・運用の終了。会議体の「中止」(`roles-responsibilities.md:699`)を含む)
2. **適用の取りやめ**(案件は続くが、本標準の適用をやめる。契約の終了、他の標準への切替など)

終了の後は、現在形の適用の表明(「適用している」)を撤去する。終了より前の範囲を対象とした適合の主張は、その範囲の主張として残る。一時停止・期日による失効・範囲の縮小は設けない。

### 理由

- 現場で現に起きるのは、案件の終了と、顧客との契約が切れて標準の適用をやめる場合の2つである。どちらも「README のバッジと表明をいつ外すか」「過去の主張は嘘になるのか」を決めないと、各案件が独自に判断する
- 過去の範囲の主張を残すのは、適合の主張が範囲(期間・リリース)を持つ文だからである(1.10.2)。終了でそれが偽になるわけではない。撤去を求めると、出荷済みのリリースに付けた文書まで回収する作業が発生する
- 表示の撤去の義務は外部の明文がある(外部 5.2 の取消し後の表示の停止、5.4)
- 終了を**記録の事象**にするのは、記録が無いと「適用している」が惰性で残るからである。テンプレートには終了を記録する種別が無く、構成を未設定へ戻す変更は契約検査が落とす(内部 7節7)。戻す操作で終了を表すのではなく、`changeLog[]` に終了の種別を足す

### 落とす案と理由

| 案 | 落とす理由 |
| --- | --- |
| 定義しない | 惰性の表明が残る。中止の判定値が「記録の保管」を確定させる(`roles-responsibilities.md:699`)のに、表明の扱いが無い |
| 一時停止 | ADR-0068 決定3 が導入の途中の状態を設けない。止めている間の出荷を規定の外に置く状態になり、同じ理由で採れない。止めるなら取りやめ、戻るなら新しい適用の開始 |
| 期日による失効 | 認証の制度が無い(Q-1 と同じ)。主張は既に範囲つき |
| 範囲の縮小 | 適用の単位は案件(1.10)。範囲を縮めたいなら案件を分ける。案件の中に適用外の部分を作る経路は、ADR-0068 が塞いだ「一部適用」と同じになる |
| 終了の後は過去の主張も撤去 | 範囲つきの文を偽にする理由が無い。回収作業だけが増える |

### 文の案(1.10 に新設。仮に 1.10.3)

> ### 1.10.3 適用の終了
>
> 適用の終了は、案件の終了、または案件が続くまま本標準の適用をやめることを、案件の記録に残した時点とします。準拠テンプレートでは、構成の変更の記録への終了の記載がこれに当たります。
>
> - 適用の終了の後に、当該案件について本標準を適用していると表明しない。掲示している適用の表明は、終了の時点で取り下げる
> - 適用の終了より前の範囲を対象とした適合の主張は、その範囲の主張として残る
> - 適用の終了の後の変更は、本標準の要求事項の対象としない
> - 適用の終了の後に再び適用するときは、改めて適用の開始(1.10.1)を置く。終了の前の未達と記録の欠落は、終了の前の範囲に残る
> - 判定が指す記録の保管は、適用の終了によって終わらない(第4章「判定が指す記録の保管」による)
>
> 適用の一時停止、期日による失効、案件の中での適用の範囲の縮小を、本標準は設けません。意図的な決定です。

### 突合

- ADR-0068 決定3(途中の状態を設けない)と同じ向き。新 ADR で「決定の外に置いた」(ADR-0068 `:111`)を受ける
- `gate-criteria.md:76-82` の保管(`IMPL-0243 undelivered`)・#333 と接する。終了で保管を打ち切らない旨だけを書き、期間は組織が定めるまま
- 実装マーク: 終了の種別をテンプレートへ足すまで `state=undelivered` で表示する

## Q-3 逸脱がある場合の適合の主張

### 結論

1. 主張を3つに分ける。**適用の表明** / **逸脱を伴う適合の主張** / **適合の主張**
2. 「逸脱」の語は、**本標準が条項の中で条件つきで認めた不充足(代償措置と記録を伴う)**の1義に限る。1.7.1 の「逸脱を認めない」は「満たさないことを認めない」に改め、語を使わない
3. 逸脱に当たるものは**本標準が条項で列挙したものに限る**(閉じた列挙)。組織・案件が新たな逸脱を作らない。列挙の外の不充足は未達、または例外承認の経路による
4. 必須の記載の正本は **1.10.2**。H.8 は対外の文の形だけを持ち、記載事項は 1.10.2 を引く

### 理由

- 現場から見て「主張できない」は採れない。2名の体制で G-6 の確認者を確かめ、G-7 は ADR-0029 の条件をすべて満たした案件は、本標準が許すことをすべてやっている。それでも「適用の表明」(未達件数つき)しか言えないなら、顧客には「未達があるのでは」と読まれる。正直に逸脱を記録した案件ほど損をする構造になり、逸脱を記録しない方向へ誘導する。これは信頼性を下げる
- 一方で、逸脱つきを素の「適合」と呼ぶのも採れない。顧客は見出しの語しか読まない(前提2)。1.7.1 と ISO/IEC Directives 3.3.3 の要求事項の定義(外部 1.2)に照らしても、満たしていないものがある状態を同じ語で呼べない
- 外部の2系統(12207 の完全適合/修整適合、MISRA の Compliant/Deviations)が独立に「別の語」で同じ結論に達している(外部 13.3 の11)。**語を分けることには先例が2つある**。ただし 12207 の箇条4 の本文は読めていない(外部 2.1)ので、「修整適合」の語は借りない。本標準の「テーラリング」は宣言を伴えば適合を放棄しない(`tailoring-guide.md:16`)ので、修整の語を逸脱に当てると、テーラリングと逸脱が混ざる
- 閉じた列挙にするのは、MISRA の「逸脱できない層を標準が先に決める」(外部 7.2)と同じ理由である。現場の都合で逸脱を作れるなら、顧客との間で毎回「その逸脱は妥当か」の交渉が起きる。標準が列挙しておけば、「標準が認めた逸脱の No.3 に当たる」で説明が終わる。**交渉の作業を消すのは閉じた列挙である**
- 語の2義は、使用が多い側(3.5.2・ADR-0029・`:427`・`:552`・adoption-guide・テンプレートの `deviations[]`)に合わせる。1.7.1 側は表の1升の言い換えで済み、意味は変わらない。ADR-0029 の本文を書き換えずに済む
- 正本を 1.10.2 に置くのは、要求事項が本文にあり、H.8 は「対外の書き方」として 1.10.2 から送られている(`:378`)からである。現状は H.8 の方が記載事項が多く、1.10.2 だけを読んだ現場は版・逸脱・署名を落とした表明を出す(内部 3.2 の1・5)。**チェックリストは1か所に無いと使えない**

### 落とす案と理由

| 案 | 落とす理由 |
| --- | --- |
| 逸脱があれば主張できない(適用の表明まで) | 記録した者ほど不利になり、記録しない方向へ誘導する。人数に依らない逸脱(`:552`)まで主張を封じる |
| 逸脱を併記すれば素の「適合」 | 見出しの語だけが読まれる。1.7.1・Directives 3.3.3 の要求事項の定義と合わない |
| 12207 の「修整適合」の語を借りる | 原文未読。本標準のテーラリングの語と衝突する |
| 組織が逸脱を定義できる(開いた列挙) | 未達を逸脱と言い換える経路になる。交渉の作業が案件ごとに生じる |
| 正本を H.8 に置く | 規定の要求事項が附属書に先にある形になり、本文の 1.10.2 が不完全なまま残る |

### 文の案

1.10.2 の表を次に置き換える(新 ADR で ADR-0068 決定4 の表を拡張する)。

> | 述べること | 述べる条件 | 併記する事項 |
> | --- | --- | --- |
> | 適用の表明(本標準を適用している) | 適用の開始の後で、適用の終了より前である | 従う版、調整、未達のゲートの件数、記録の欠落の件数、逸脱の一覧。無い場合は 0 件と書く |
> | 逸脱を伴う適合の主張(本標準に、逸脱を伴って適合している) | 主張の範囲に、未達のゲートと記録の欠落が無い。逸脱がある | 従う版、主張の範囲、逸脱の一覧(根拠の条項・代償措置・受容した者) |
> | 適合の主張(本標準に適合している) | 主張の範囲に、未達のゲートと記録の欠落と逸脱が無い | 従う版、主張の範囲 |
>
> - 逸脱は、本標準が条項の中で、条件と代償措置を定めて認めた不充足に限る。条項に定めの無い不充足を、逸脱として扱わない
> - 逸脱のある範囲について、「本標準に適合している」と述べない
> - 表明と主張には、記名の自然人が署名する
> - 本項に定める併記の事項のいずれかを欠く表明と主張を、本標準に基づく表明と主張として扱わない
> - 対外の文の形は、附属書H H.8 による。併記の事項は本項による

1.7.1 の表の「要求」の行の意味の升: 「適合を主張するには、これを満たす。満たさないことを認めない(本標準が条項で定めた逸脱を除く)」。
1.4 の用語に「逸脱」を足す: 「本標準が条項の中で、条件と代償措置を定めて認めた、要求事項の不充足。未達とは別に表示する」。
H.8 の2行(`:742-743`)は、記載事項を「第1章 1.10.2 の併記の事項」へ置き換え、逸脱を伴う適合の主張の行を足す。

`:::caution[暫定 EV-NNNN / 見直し 2027-10]` — 「逸脱を伴う適合」の語が顧客・監査人に、素の適合と区別して読まれることの実証は無い。差し替え条件: 対外の文書での読み違えの事例の収集。

### 突合

- ADR-0029「代償措置を独立性の回復として扱いません」: 逸脱を伴う適合は回復を主張しない語であり、矛盾しない。素の適合を認めない点で、むしろ同じ向き
- ADR-0028(未達と省略の区別): 逸脱を未達に数えない区分はテンプレートの `unmet` / `deviations[]` の既存の区分と一致する(確認: `aggregate-evidence.mjs:1715` 以降)
- ADR-0068 決定4: 表を拡張する。本文は書き換えず新 ADR で置き換える
- H.6 項目1・`:497` の「差し戻すのは記載の欠落だけ」: 逸脱は差し戻しの対象ではないまま。主張の語が変わるだけで、開示の扱いと矛盾しない
- 逸脱の列挙が閉じているか: 現在の箇所(3.5.2、`:427`、`:552`、adoption-guide `:317`・`:653`)を一覧にして 1.10.2 から引けるようにする作業が要る(棚卸しは本会議の後の作業)

## Q-4 引用規格の版の書き方

### 結論

1. 1.3 の引用は**すべて発行年付き**とする。国際規格と JIS は両方を発行年付きで併記する
2. 発行年なしの引用は使わない
3. 版を改めるとき(Q-1)に、引用規格の改訂の有無を確かめる**棚卸し**を行い、結果を確認日つきで残す。改訂があっても追随するかは別に決め、追随しないなら「どの版を踏まえたか」を書いたまま残す
4. 1.3 の各行は出典台帳の SRC を引き、検査で台帳の実在を確かめる

### 理由

- 本標準は附属書H H.10 で ISO 9001 の箇条を対応づける(内部 4.1)。部分を引くなら発行年は必須(外部 1.1 の箇条10.5)。現に 1.3 は版なしの ISO 9001 を引きながら H.10 は 2015 年版の目次による。監査人に「どの版か」を聞かれて答えられない状態である
- 発行年なしは「全改訂を取り込む」意味になる(外部 1.1 の箇条10.4)。読んでいない改訂を取り込んだと読める引用は、1.3 の注意「適合性を主張しない」以前に、出典として不正確である
- 棚卸しを版の発行に結び付けるのは、別の周期を作ると忘れるからである。版を出すたびに1回で済む
- 追随しないことを許すのは、共通フレーム2013 の実例(外部 11.3)のとおり、版を書いていれば読み手は判断できるからである。追随は個別の判断(12207 は #341)
- 台帳との接続は、本文から SRC への参照が 0 件(内部 4.2)なのを解く。ただし全本文に強制すると作業が膨らむので、1.3 の行に限る

### 落とす案と理由

| 案 | 落とす理由 |
| --- | --- |
| 現状のまま(一部だけ版つき) | 監査で答えられない |
| 文書全体の引用は版なし可 | 本標準は 1.3 の全規格を部分(箇条・手順)で使っている。全体の引用に当たる行が無い |
| 引用規格の改訂に必ず追随 | 原本を買って読むまで追随できない。読まずに版だけ上げるのは、読了していない条文を引く形になる(H.8 `:763` の禁止と同じ理由) |
| 本文の全引用に SRC を必須 | 範囲が大きく、#313 の対象を超える。1.3 から始める |

### 文の案(1.3 の表の前)

> 引用する規格・ガイドラインは、発行年または版を付けて引きます。引いた版だけが、本標準の前提です。国際規格と、対応する日本産業規格は、両方を発行年付きで併記します。
>
> - 発行年または版を付けない引用をしない
> - 本標準の版を改めるときは、引用する規格の改訂の有無を確かめ、確認日とともに記録する
> - 引用する規格が改訂されても、新しい版を前提とするまでは、引いた版のまま記載する

### 突合

- `qms-document-control.md:141-143`(箇条番号は H.10 の1か所にだけ書く): 矛盾しない。版の表記は 1.3 と H.10 の見出しの2か所に出るが、同じ版を指すことを検査できる
- EV-0096(JIS Z 8301 の原本未確認): 日本語の定型文は原本確認まで暫定。上の文案も EV で開示する
- #341・#336: 個別の更新はそちら。本条は書き方と棚卸しの作業だけ

## Q-5 適用の開始の境(pre-init)

### 結論

**文書(`ci-gates.md:313` の「`changeLog[]` の1件目」)が誤り**。境は「構成が設定済みになった最初のコミット」(実装の `findInitCommit`)とする。あわせて次を定める。

- 設定済みの構成は、初期化の記録(`changeLog[]` の1件目)を同じコミットで持つ。持たない新しいコミットは契約検査で落とす
- 宣言の要求事項(第8章)を欠いた初期化も、適用の開始である。欠けた事項は記録の欠落として表示する
- 再テーラリングと版の切替は、適用の開始を動かさない

### 理由

- ADR-0068 決定1 は「境は履歴の1コミットで決まり、後から動かせません」と書く(確認)。`changeLog[0]` は配列の要素で、切り詰め・差し替えで動く(内部 5.3)。文書の定義は ADR に反し、実装の定義は ADR に合う
- 分かれる4件のうち、実装の定義は「旧い構成で `changeLog` が無い」場合にも境が立つ。文書の定義では境が無くなり、全履歴の扱いが読めなくなる。旧い版の構成を抱えた現場(#315)にとって、境が消えるのは最悪の結果である
- 手で `configured: true` を先に入れた履歴では、実装の定義の方が**境が早い**。境が早いほど要求事項の対象が広く、未達と欠落が多く表示される。**迷う場合は、表示が増える側を採る**のが、未達を隠さない ADR-0028 の向きと合う
- 不完全な宣言を「開始していない」とすると、宣言を欠いたままにすることが義務を先送りする手段になる。欠けた宣言は表示して直させる方が、現場でも作業がはっきりする

### 落とす案と理由

| 案 | 落とす理由 |
| --- | --- |
| 文書に合わせ、実装を `changeLog[0]` に変える | 切り詰めで境が動き、ADR-0068 決定1 に反する。旧い構成で境が消える |
| 両方が揃った最初のコミット | 手で先に設定した履歴で境が遅くなり、対象が狭まる。新規のコミットは契約検査で揃うので、二条件にする利点が無い |
| 宣言の要求事項を満たした時点 | 開始の判定が人の解釈に依り、機械で1コミットに決まらない |

### 文の案

`ci-gates.md:313` と `template-repository.md:33` のカッコ内を「`process.config.json` が設定済みになった最初のコミット」へ改める。1.10.1 に次を足す。

> - 宣言が第8章の要求事項のいずれかを欠く場合も、記録に残した時点を適用の開始とする。欠けた事項は記録の欠落として表示する
> - 2回目以降のテーラリングの宣言と、従う版の切替(1.10.4)は、適用の開始を動かさない

### 突合

- `tailoring-guide.md:18`「いずれかを欠く省略は、本標準に基づく調整として扱いません」: 調整が無効になり、元の要求事項が掛かる、と読めば矛盾しない(開始は起き、調整が効かない)
- IMPL-0119(delivered): 実装は変えない。文書の側を直す
