# #363 会議体(重) 委員: 規格

- 立場: ISO/IEC/IEEE 29119-2、IEC 62304、DO-178C、ISO 9001 8.6、GitHub の必須チェックの仕様、Nx・Bazel・alls-green の実務との整合を重視する
- 読んだもの: `council-00-agenda.md`、`survey-363.md`(5.4・6〜8節)、`survey-363-2-external.md`(以下「外部」)、`council-01-drafter.md`・`council-02-opponent.md`、`gate-criteria.md` 660・681・847 行、ADR-0085 84・88・89 行、ADR-0028 26・41・43 行
- 根拠の水準の注意: 29119-2 は公開プレビューの原文(4.1.1・3.59 まで)。7.2・7.4 は未確認。62304・DO-178C・9001 8.6 は二次資料だけで逐語は未確認(外部 4節・6節)。以下でこれらに依る箇所は「二次資料」と書く

## 0. 規格から読める共通の型(判断の前提)

- 規格は「すべてを試験せよ」とは求めない。29119-2 は試験の範囲と完了基準を戦略で決めて記述し(3.59 Note 1)、適合の範囲を宣言する(4.1.1)ことを求める(外部 SRC-D1)
- 62304 は構成要素の間で要求を変えることを、分離の識別と有効性の記録を前提に許す(5.3.5、二次資料。外部 SRC-D2)。DO-178C は検証で触れなかったコードを必ず分類して処置を決める(二次資料。外部 SRC-D3)。9001 8.6 は計画した検証の完了を出荷の条件とし、例外は権限者の承認と記録で通す(二次資料。外部 SRC-D4)
- 共通項は「試験しない部分を**識別し・理由を決め・記録し・権限者が受け入れる**」。無言の省略を許す規格は見当たらない(外部 5節)。欠陥③は、この4つのどれも満たさない
- 本標準は 9001 よりも強い側を既に選んでいる。G-5 基準1 の値は「例外なし」(gate-criteria.md 660 行)で、検査を外せるのは第8章の調整だけ(681 行)。規格の「権限者の承認による例外」を、本件で基準1 へ持ち込む余地はない(4節で採らない案として記録する)

## R-1 正本の方式

- **推す案**: 本文の要求は「G-5 の必須の検査の集約は、製品のすべてのスタックの基準1・2・3・5 の検査を含む」という**結果の要求**とする。準拠テンプレートでの実現は (c1) 複数のアダプタとする。加えて、製品の目印のスタックと宣言したスタックの集合の突合を、PR ごとの契約検査で行い、宣言の無いスタックがあれば G-5 を失敗にする(反対の委員の推す案 115〜123 行と同じ骨格)
- 理由
  - 本文に機構(アダプタの数)を書かず結果を書くのは、規格の書き方の型に合わせるため。29119-2 は手段ではなく範囲の宣言と完了基準を求める(4.1.1・3.59)。本標準の採用者は準拠テンプレートを使わずに G-5 を組むこともある。機構で書くと、テンプレートの外の採用者に要求が届かない
  - 「全テスト」が全スタックを指すと本文に明記する。現行でも 660・681 行から読めるが、読みが割れる余地が残った(survey 6節)。29119-2 4.1.1 の「宣言」の型に照らせば、範囲は書かれていなければ宣言されていない
  - 実務は (c1) と整合する。Nx・Pants・Bazel は1つの PR で複数スタックの検査を走らせる前提で作られ、「構成あたり1言語」の形を取らない(外部 SRC-B1・B2・B4)。Bazel の既定は全言語で、絞り込みは明示のフラグで行う(SRC-B4。`//...` の逐語は未確認)。「既定は全部、除外は宣言」の型を本件も取る
  - 突合を契約検査に置くのは、GitHub の仕様が「走らなかった」と「通った」を区別しないため。`if:` で飛ばされたジョブは Success を報告し、必須チェックでも合流を止めない(SRC-A1・A2)。プラットフォームの層では塞げず、塞げるのは利用者側のプロセスだけ(外部 5節)。(c1) を入れても、宣言から漏れたスタックは走らないまま緑になる。Nx も「入力の宣言から漏れたものは走らない」限界を持つ(SRC-B1 の示唆)
  - 集約は「走った検査の一覧」を証跡に持つ。alls-green は失敗が skipped に化けることを既知の挙動として扱い、飛ばしてよいジョブを `allowed-skips` で名指しする(SRC-A4)。G-5 の集約が合否だけを持つと、同じ穴が残る
- 他の案を落とす理由
  - (c2) 混在を止める: DO-178C の「除去」に当たるが、本件のスタックは製品のコードで、除去できない。止めても受け皿は `none` の手書きだけで、基準3 が未実施へ押し出される(survey 5.4)。持ち込みの時点しか見ず、開始の後の追加を止めない。ADR-0085 84 行の「止めると持ち込みそのものができなくなる」と同じ害を、多言語を当然とする実務(SRC-B1〜B4)に対して起こす
  - (c3) 単独: 規格の型の「識別・記録」は満たすが「権限者の受け入れ」を欠く(外部 5節)。開示つきで通すことは、681 行の禁止に開示の札を付けるだけになる。GitHub の skipped = success を、本標準の内側で再現する
  - (d) 差分の網羅率: 基準3 の測り方の話で、基準1・2 を受けない。混在の node アダプタでは python の `coverage.json` そのものが生成されない(反対の委員 104 行)。#360(IMPL-0259)の範囲に置く
  - Scorecard・SLSA に依る案: Scorecard の CI-Tests・SAST は言語の網羅を見ず、SLSA の Build track は試験を要求しない(SRC-C1〜C3)。外部の評価で代えることは採らない
- 条件・留保
  - カバレッジはスタックごとに基準値と比べ、合算しない。合算は厚い側が薄い側を薄める(反対の委員 97・121 行。ADR-0079 の薄まりと同じ問題)。62304 の分離の型(構成要素ごとに識別する)とも合う(二次資料)
  - アダプタの外の言語(rust・java など)が製品にあり、採用者が自分の検査を集約へ入れないなら、G-5 は通さない(失敗)。開示つきの通過にしない
  - 複数のアダプタを同時に回した実行は無い(E0。反対の委員 100 行)。未実証。規定に効く値は ADR-0026 のマークで開示する

## R-2 宣言と除外

- **推す案**: 製品のスタックの宣言を求める。製品でない目印(道具・試験の材料・取り込んだ第三者のコード・文書の生成用の依存)は、パス・区分・理由・記名(人の名義。AI の名義を認めない)つきの一覧で検査の外とする。除外の一覧の変更は、製品のコードの変更と同じ PR で行えば止める(閾値・除外設定の分離と同じ扱い)。区分は「製品でない」だけを持ち、**製品のスタックを除外する区分を置かない**
- 理由
  - 宣言は 29119-2 4.1.1 の「範囲の宣言」の型そのもの。宣言は人が書き、検出は突合にだけ使う。ADR-0085 89 行「点検は…設問の回答を検出の結果で埋めない」と矛盾しない
  - 除外の型は alls-green の `allowed-skips`(名指しの例外以外は止める。SRC-A4)と Bazel の明示の絞り込み(SRC-B4)に合う。理由と記名を要するのは、62304 の「文書化されていなければ存在しない」(二次資料)と、9001 8.6 の追跡可能性(二次資料)の型による
  - 製品のスタックの除外を区分に持たせないのは、基準1 が「例外なし」(660 行)で、外せるのは第8章だけ(681 行)だから。除外の一覧が製品のスタックを受けると、宣言による除外の経路で 681 行が崩れる(起案の委員 28 行)
  - 同じ PR の除外の変更を止めるのは、survey 5.6 の D-5(`pyproject.toml` の中の除外の拡大が同時変更の検査に掛からない)と同じ型の穴を、除外の一覧に作らないため
- 他の案を落とす理由
  - 宣言を求めず検出だけで決める案: 目印のファイル名では製品か否かを判別できない(反対の委員 88 行)。ADR-0085 89 行にも反する
  - 理由だけで記名を求めない案: 9001 8.6 の型の「誰が受け入れたか」を欠く(外部 5節)
- 条件・留保
  - 承認者(記名に加えて誰が受け入れるか)は、強制層への組み込みの承認(AI維持管理者。gate-criteria.md「是正の起動」の段落、第3章 3.11.2・3.11.4)にそろえる向き。第3章との突合を議長に委ねる
  - 誤検出の率は測っていない。未実証。誤検出が多ければ、G-5 の原則「実効的な偽陽性が無いこと」に掛かる。EV で開示し、試行の記録で見直す

## R-3 暫定の扱いと既存の採用者

- **推す案**: (c1) が降りるまでは、G-5 の実行時に宣言の外のスタックの目印を検出したら、保証の開示 項目4 と G-5 の集約に「**基準1 未充足**(構成のアダプタの外: スタック名)」と出す。暫定であることを `:::caution[暫定 EV-NNNN / 見直し …]` と IMPL の `state=undelivered` で開示する。基準1 を実際に満たす道として、`none` に全スタックのテストを書く形を、基準3 が未実施になる限界つきで手引きに書く
- 理由
  - 語は「未充足」を採る。「検査していない」は中立の語で、GitHub の skipped が成功に数えられる(SRC-A1・A2)のと同じく、読み手に未検査を許容の状態と読ませる。規格の型では未検査は逸脱であり、逸脱として名指す(9001 8.6、二次資料)
  - 暫定の間に止めないのは、受け皿の無いまま止めると、採用者が基準3 を落とす `none` へ押し出されるだけだから(survey 5.4)。ただし `none` の形は基準1 を満たすので、手引きで道を示す
- 他の案を落とす理由
  - 暫定でも止める案: (c1) が無い間の唯一の受け皿が `none` で、基準3 が #330 の未実施になる。未実施の長期化の歯止めは #330 で未決
  - 暫定を表示だけで期限を持たない案: 降りない状態が恒久化する。見直しの年月を必ず置く
- 条件・留保
  - 暫定の表示は基準1 の充足を装わない表示で、9001 8.6 の「権限者の承認による出荷」に当たらない。暫定の間の通過は、本標準の要求を満たした通過ではないと本文で明記する
  - 旧い構成(1つのアダプタ)は、単一スタックのリポジトリではそのまま有効とする。(c1) の後、混在のまま1つのアダプタで通っている採用者は契約検査で落ちる。形式の版の繰り上げと `migrate`(ADR-0085 決定5)、落ちうる検査と直し方の列挙(同 決定6)を掛ける

## R-4 記録・ADR

- **推す案**: 新しい ADR を起こし、ADR-0085 決定2 の 88 行の理由「黙っては外れない」を、単一スタックの場合に限ると補う。ADR-0085 の本文は書き換えない。新しい ADR の決定は、(1) 基準1・2・3・5 の対象を製品のすべてのスタックと明記、(2) 宣言と除外の一覧の型、(3) 契約検査で宣言の外のスタックを止める、(4) カバレッジはスタックごと、(5) 暫定の表示と語、(6) 採らない案
