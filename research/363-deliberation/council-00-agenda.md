# 会議体の議題(#363 欠陥③: 複数のスタックを持つリポジトリ)— 重

軽の会議体(`council-01-drafter.md`・`council-02-opponent.md`)は、2委員とも (c1) 複数のアダプタを推し、新しい義務と ADR-0085 決定2 の理由の変更に当たるとして重へ上げるべきとした。これを受けて重の会議体を開く。

入力: `survey-363.md`(内部・実行での確認)、`survey-363-2-external.md`(外部)、軽の2委員の意見。

## 前提として確かめた事実(要旨)

- 欠陥③: node と python が混在するリポジトリで node アダプタを選ぶと、わざと落とした python のテストが走らないまま G-5 を通る(実行で確認)。G-5 基準1「全テストが GREEN/例外なし」(gate-criteria.md 660 行)、集約から検査を外すことの禁止(681 行)
- 構成が持てるアダプタは1つだけ。事前点検は言語の目印を告げるだけで、アダプタの前提と突き合わせない
- 外部: GitHub の if: で飛ばされたジョブは Success と報告され、必須チェックでも合流を止めない。paths でワークフロー全体が飛ばされると Pending のまま止まる(公式文書)。Scorecard の CI-Tests・SAST は言語の網羅を見ず、SLSA の Build track は試験を要求しない。塞げるのは利用者側のプロセスだけ
- Nx・Pants・Bazel は1つの PR で複数のスタックの検査を走らせる。選択型の仕組みにも「対象に宣言されなかったものは走らない」穴があり、どの道具も既知の限界として公開している。alls-green の allowed-skips は、飛ばしてよいジョブを名指しで宣言し、それ以外の飛ばしを止める型
- 規格は「すべてを試験せよ」とは求めないが、無言で省いてよいとする規格も見当たらない。29119-2 は試験の範囲と適合の宣言を求める(4.1.1・3.59 原文確認)。62304・DO-178C・9001 8.6 は「識別・理由・記録・権限者の受け入れ」を求めると読める(二次資料)
- 軽の2委員: (c1) を正本にする。製品にある目印のスタックが宣言したスタックの集合に入っているかを PR ごとの契約検査で確かめて止め、誤検出は理由と記名つきの除外で受ける。(c1) が降りるまでは (c3) の表示を暫定にする(語は「未充足」)。(c2) は持ち込みの時点しか見ず誤検出が多い。(d) は基準3 しか受けない

## R-1 正本の方式

- 問い: (c1) 複数のアダプタ、(c2) 混在を止める、(c3) 告げて開示する、(d) 差分の網羅率、その他。どれを本標準の要求とするか

## R-2 宣言と除外

- 問い: リポジトリにあるスタックの宣言を求めるか。製品でないスタック(道具・試験用のスクリプト等)の除外の形(理由・記名・承認者)。誤検出の扱い

## R-3 暫定の扱いと既存の採用者

- 問い: (c1) が降りるまでの間と、旧い構成(1つのアダプタ)の扱い。表示の語(未充足/検査していない)、止めるか開示か

## R-4 記録・ADR

- 問い: ADR-0085 決定2 の理由の改め方、新しい ADR、EV・IMPL、#360(IMPL-0259)との分担、採らない案
