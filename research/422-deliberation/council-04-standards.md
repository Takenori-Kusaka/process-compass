〔未〕の文書について、条番号・文言を引用しません。以下で「規格の作法」と書くものは、上表の【既知・未照合】の範囲の趣旨です。条項の根拠に使うなら、原典との照合を先に要します。

## 総論(規格の立場からの基本線)

1. 規格の作法では、**レビューの範囲・目的・読み方を決めるのは、レビューを計画する側(またはレビュアの側)であり、作成者ではない**。作成者は入力(成果物・関連資料)を出す側に置かれる【既知・未照合】。#422 の「論点を抜き出して人をそこへ絞る」は、範囲の決定を作成側(または作成側の道具)へ移す形になりうる。これは独立の考え方(確認する側が、確認の対象と範囲を作成側から受け取らない)と衝突する
2. 機能安全の規格群で、自動化が人の検証の**代わりに数えられる**経路は、道具の適格性確認(決定論的な振る舞いを示し、資格を得た道具)だけである【既知・未照合】。本標準はこの経路を AI の確認に対して設けないと既に決めている(`overview.md:185`「道具の適格性を示して段に数える経路も設けない」)。#422 の「残りを AI レビューで補う」は、この決定の再審になる
3. 本標準は既に、G-6 の承認が全行の読解を意味しないと定める(`assurance-case.md:465-469` H.5、`review-guide.md:19`)。したがって #422 の論点は「人の確認を絞るか」ではなく、**誰が・何によって範囲を決め、決めた範囲の外の保証を何に置くか**である(内部調査の要点1 と同じ認識)
4. 外部調査で、所有者の前提(Anthropic の運用)は半分しか確かめられていない(`survey-422-2-external.md` 1.5)。確かめられた運用は「論点で絞る」ではなく「リスクの層で絞る + 低リスク層の自動承認 + 標本検査」である。規格は、伝聞の運用ではなく、確かめた事実と本標準の判断軸で書く

## R-1 人の確認の範囲を絞るか、何で絞るか

### 結論

1. **G-6 の承認の範囲を「PR ごとの論点」に絞る規定を設けない**。G-6 の範囲は、現行どおり判定基準1(受入基準の項目ごと。`gate-criteria.md:880`)と附属書C のパス1(差分は基準の範囲内か。`review-guide.md:21-40`)で定まる。その旨を、課さないと決めたこととして明記する
2. **パス1(仕様外の変更の混入の確認)は、差分の全体に掛ける**。重点の提示の有無・内容によって、パス1 の範囲を狭めない。絞ってよいのは、パス2・パス3 の読み込みの深さに限る。この「深さを絞ってよい」根拠は、既存の担保水準 L1 の「実行可能な保証で範囲を限定できる」(`gate-criteria.md:1503`)と規模の確認の「保証の所在」(`gate-criteria.md:1580-1612`)の経路だけとする。新しい根拠を足さない
3. **重点の生成元は、機械的な導出に限る**(3.10.12 `roles-responsibilities.md:1270`、ADR-0023 決定7・8)。生成元の候補は、区分の下限の規則のパス(3.8.1 `roles-responsibilities.md:938`)、影響範囲(索引部)、既存テストの変更の一覧、依存の差分(G-5 基準8)である。これらは **範囲を広げる情報**(ADR-0023 決定3 の索引部)として扱い、範囲の**上限**として扱わない
4. 作成側(人または AI)が書く重点(PR テンプレートの「レビュー観点の指定」)は、**注意を狭める情報**として扱う。パス1 の後に読む。範囲を定める効力を持たない(R-4 で書式を扱う)
5. **AI に重点・論点を抽出させ、それを人の確認の範囲にする形は採らない**
6. 「論点」を本標準の用語にしない。必要な概念は既存の語(3.10.12「重点箇所」、ADR-0023「索引部」「注意喚起部」)で書く
7. リスクの層による濃淡は、既存のリスク区分(変更ごと、ADR-0039 決定4)と委任の条件(5.5.4)で既に実装されている。**新しい層別・自動承認の経路を設けない**(第4章「判定の時点を移す別の経路を新設しない」`gate-criteria.md:1823`)

### 理由

- **範囲を決める主体の問題**。規格の作法では、レビューの範囲と読み方はレビューを計画する側が決め、作成者は入力を出す側に置かれる【既知・未照合: ISO/IEC 20246 の計画の工程、IEEE 1028 のインスペクションで作成者が進行役・記録者を兼ねない構成】。作成者が「ここを見てほしい」と示すこと自体は、規格も禁じない。しかし、それが範囲の**上限**として働けば、作成側が確認の範囲を決めたことになる。これは本標準の独立の定義(`overview.md:113`、確認する側が作成を指示した側と別の自然人)が守ろうとするものを、範囲の側から崩す。独立を人の単位で守っても、範囲を作成側が決めれば、確認は作成側の主張の検証に縮む
- **ADR-0023 決定2 の判定規則にそのまま当たる**。「その記述がレビュアが自分で確認しなくてよいと読める場合、それは結論である」(`adr/0023-review-package-cues-not-conclusions.md:29`)。論点に絞る運用は、論点の外について「確認しなくてよい」と読ませる仕組みそのものである。既存の ADR を置き換えずに採れない
- **パス1 を論点の外にも掛ける理由**。附属書C は、仕様外の「ついで実装」を AI 生成の最頻の混入物として、パス1 の目的に置く(内部調査 1.4)。仕様外の変更は、定義上、作成側が論点として挙げない場所にある。論点に絞れば、パス1 の検出対象が体系的に論点の外へ落ちる。これは絞り方の巧拙ではなく、構造上の帰結である
- **AI による抽出を採らない理由**。Tufano ほか(2024、29 名の対照実験)で、AI の出力を起点にしたレビュアは示された場所へ注意を寄せ、高重大度の指摘は増えなかった(`survey-422-2-external.md` 3.2)。根拠は1件で弱いが、向きは第4章の緩和根拠の表(`gate-criteria.md:1642-1646` 自動化バイアス)と ADR-0023 の 2004 年の実験の引用(`adr/0023-...md:43`)と一致する。既存の判断を覆す新しい実証は無い
- **品質特性の観点**。ISO/IEC 25010 の品質特性のうち、人のレビューが実際に多く見つけるのは保守性に関わる欠陥である(Mäntylä & Lassenius 2009 の 75%。`survey-422-2-external.md` 3.1)。PR ごとの「本質的な論点」は、作成者・AI のどちらが書いても、機能・正しさの側へ寄る(Anthropic の Code Review の既定の観点も正しさ)。論点に絞ると、保守性の副特性(解析性・修正性・試験性など)が論点の外へ落ちやすい。人のレビューの主な産出を、絞り込みの外へ出す形になる
- **リスク層の濃淡は既にある**。本標準は R1〜R3 の区分ごとに統制を変え(テストの生成の分離・変異試験・人確定)、区分の下限を機械の規則で導く(3.8.1)。Anthropic の「リスクで層別」と同じ発想は既に入っている。違うのは「低リスク層の自動承認」であり、本標準でそれに当たるのは 5.5.4 の委任(7条件。根拠は「検出でき、取り消せること」)だけである。2つ目の経路を作ると、条件の緩いほうへ流れる(#172 の棄却理由、`gate-criteria.md:1823`)
- **用語の問題(指針第2部)**。規格の文書は、定義した用語で書き、定義の無い語で要求を書かない。「論点」「本質的」「長期的」は、検証できる定義を与えにくい。「本質的な論点に絞る」という要求は、満たしたかを第三者が判定できない。指針第2部の「検証できない要求を書かない」の考え方【既知・未照合: 条番号は引かない】に反する。本標準の 5.7.4(記述の質を機械で判定しない)とも、判定の方法が無いという点で同じ問題を持つ

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. 作成者(人)が論点を書き、人の承認をその範囲に絞る | 範囲を作成側が決める形になる(独立の考え方と衝突)。ADR-0023 決定2 の「結論」に当たる。パス1 の検出対象が論点の外へ落ちる |
| B. AI が論点を抽出し、人の承認をその範囲に絞る | A の問題に加え、3.10.12 の生成元の限定(自動検査の出力)と ADR-0023 決定7・8(機械的な導出、自由記述で生成させない)に反する。自動化バイアスの向きの実証(Tufano)と、第4章の緩和根拠の表の判断に反する |
| C. 機械の導出した重点を、人の確認の**上限**にする | 機械の導出は網羅を主張できない(区分の下限の規則は網羅を主張しない。`roles-responsibilities.md:946`)。上限にすれば、規則の漏れがそのまま確認の漏れになる。範囲を広げる情報としてだけ使う |
| D. リスク層別の自動承認(Anthropic・Meta の運用)を新設する | 判定の時点を移す経路は 5.5.4 に限る(`gate-criteria.md:1823`)。Meta RADAR の効果は選択バイアスと交絡する観察研究で、単一組織(`survey-422-2-external.md` 2.3)。新設の根拠に足りない。5.5.4 の7条件で足りない具体例が示されれば、5.5.4 の改訂として扱う(別経路にしない) |
| E. 視点別の読み方(perspective-based reading)で観点を割り当て、各レビュアの範囲を絞る | 規格の作法としては正当な読み方である【既知・未照合: ISO/IEC 20246】。しかしそれは、複数のレビュアで視点を分け、全体で覆う前提の技法である。G-6 は多くの構成で1名であり、1名に視点を割り当てれば残りの視点が誰にも覆われない。2名の構成でも、本標準は観点の分担を課さないと決めている(ADR-0067 決定3、`gate-criteria.md:923`)。課す根拠となる測定は今回も見つかっていない |

### 反論されうる点

- 「現に人は全部を読んでおらず、絞らないと形骸化が進む。規定が実態から離れる」。これに対しては、絞ること(深さ)は L1 と /human-verify の順5 で既に認めている、と答える。絞り方の根拠を作成側の申告ではなく実行可能な保証に置く点が、本標準の立場である。ただし、L1 の「実行可能な保証」の中身を機械で確かめられない(`gate-criteria.md:1607`、内部調査 4.2 の穴)ことは弱点として残る。R-4 の測定で補う
- 「作成者の論点の申告は、作成者しか知らない文脈(自信のない判断)を伝える唯一の手段である」。そのとおりであり、欄そのものは残す(R-4)。読む時点と効力を定めるだけで、伝達は妨げない
- 「1.7 の規定の表現形式上、『論点に絞る規定を設けない』は要求事項ではないので書く必要が無い」。書く。コアポリシーの「書かれていないと課さないと決めたの区別」による。課さないことは、1.7.1 の「不必要」または禁止の形で書けば足りる
- 規格の作法に関する本意見の根拠(ISO/IEC 20246・IEEE 1028)は原典未照合である。条項の根拠としては使えない。本意見の結論は、本標準の既存の ADR(0023・0039・0067)と第4章の規定の整合からも同じ結論が出るため、原典未照合でも結論は変わらないと判断する

## R-2 長期的な決定の切り出し

### 結論

1. **採る**。判断記録の対象になりうる変更(第2章 2.6 の「設計上の選択」の例示。`lifecycle.md:155-161`)を、**変更の対象のパスと変更種別から機械で検出し、判断記録の所在の記入を求める**
2. 検出の規則は、新しい規則の体系を作らず、**3.8.1 の区分の下限の規則と同じ置き場・同じ書式・同じ起案と承認の手続**(技術判断者が起案、AI維持管理者が承認、規則のファイルを変える変更の下限は R2。`roles-responsibilities.md:938-943`)に置く。出力の属性だけを分ける(区分の下限 / 判断記録を要する)
3. 検出された変更の判定は、**既存の G-3(技術判断者)の経路に乗せる**。G-6 の独立レビュアに長期的な決定の承認を兼ねさせない。新しい承認の経路(専任の承認者の席)を作らない
4. 機械が確かめるのは、判断記録の所在の記入と、その判断記録に G-3 の判定記録があることまでとする。判断記録の内容の妥当性は G-3 の判定者が見る(5.7.4 の線)
5. 規則は網羅を主張しない(ADR-0041)。規則に当たらない設計上の選択は、現行の PR テンプレートの自己チェックと G-3 の基準2(既存の判断記録との突合)で拾う。その残余を明記する
6. 検出による効果は未測定である。暫定マーク(ADR-0026)を付ける

### 理由

- **現行の穴が具体的である**。PR に埋もれた設計上の選択を G-3 へ引き上げる手段は、PR テンプレートの折りたたみの自己チェックだけで、機械の検査が無い(内部調査 3、`template/.github/PULL_REQUEST_TEMPLATE.md:104-115`)。G-6 基準3 はコア機能に限る(`gate-criteria.md:882`)。自己チェックだけに頼る統制は、本標準が 3.8.1 で「記名だけではこの経路を塞げない」(`roles-responsibilities.md:934`)とした構造と同じ弱点を持つ。区分については既に機械の下限で塞いだのに、判断記録についてだけ自己申告に委ねる理由は無い
- **外部の実例がある**。Kubernetes の API レビューは、型・登録のパスから自動でラベルを付け、専任の承認者の経路に回す(`survey-422-2-external.md` 2.5。長期の運用。ただし規格化された作法ではない)。#422 の「長期的な決定を人に残す」のうち、外部で確かめられた形はこれだけである
- **規則を1つの体系にまとめる理由**。区分の下限の規則の例示(認証・認可、個人データ、**公開インタフェース**、**データの移行**、ビルドと配備の設定)と、2.6 の設計上の選択の例示(依存、**外部インタフェース**、**データ形式**、構成単位の境界)は重なる。別の規則ファイルを作れば、同じパスを2か所で管理する二重管理になる。ADR-0039 決定3(注記と別のマーク体系を設けない)と同じ考え方で、正本を1つにする。手続も同じにすれば、規則を緩める向きの変更の統制(3.13.3 の記名)がそのまま掛かる
- **G-3 へ乗せ、G-6 に兼ねさせない理由**。規格の作法では、設計の決定(アーキテクチャ定義)と検証(レビュー)は別の工程として置かれる【既知・未照合: ISO/IEC/IEEE 12207 のアーキテクチャ定義プロセスと検証プロセスの分離】。本標準も G-3 の判定者を技術判断者とし、G-6 と分けている(`gate-criteria.md:429-447`)。G-6 の独立レビュアに長期的な決定の承認を兼ねさせると、判定基準の異なる2つの判定(G-3 の5基準と G-6 の6基準)が1つの承認に混ざる。どちらの基準で承認したかを記録から区別できなくなる
- **新しい承認の席を作らない理由**。専任の承認者(Kubernetes の API レビュア)に当たる席は、本標準では技術判断者として既にある。席を増やすと、1〜2名の体制で席の兼務の判定(3.5)が増え、未達の扱いが変わる。既存の席で足りる
- **機械の範囲を記入の有無に限る理由**。5.7.4 は記述の質を機械で判定しない。検出の規則が「判断記録を要する」と出しても、その変更が本当に設計上の選択を含むかは人が判定する。規則に当たったが判断記録が不要と判断する場合の扱いは、区分の下限と同じく「下限より高い記載は妨げない」とは逆向きの問題になる。ここは R-5 の ADR で、判断記録が不要と判断した旨の記名(作成を指示した者以外の自然人)を求めるかを決める必要がある。規格の立場としては、**3.8.1 要求事項3 と揃えて、作成を指示した者以外の自然人の記名で「不要」を確定させる**形を推す。指示した者だけの記名で外せると、規則が自己申告に戻るためである

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. PR テンプレートに「長期的な決定」の欄を必須にし、作成者に書かせる | 欄の記入は自己申告であり、書かなければ漏れる。3.8.1 で区分について退けた構造と同じ。機械の検出を先に置き、欄はその補完にとどめる |
| B. AI に PR から長期的な決定を抽出させる | 抽出の網羅を確かめる手段が無い。抽出されなかったことが「長期的な決定を含まない」と読まれる(ADR-0023 決定4 の「指摘の無い箇所を確認済みと読ませる」と同じ構造)。AI の指摘として検出の層に置くことは妨げない(R-3) |
| C. 長期的な決定の承認者として新しい席・経路を作る | 技術判断者の席と G-3 が既にある。席を増やすと兼務の判定が変わり、1〜2名の体制の未達が増える。新しい経路は第4章の「別の経路を新設しない」の趣旨(条件の緩いほうへ流れる)にも掛かる |
| D. 区分の下限の規則とは別の規則ファイルにする | 同じパスの二重管理になる。手続が分かれると、片方だけ緩める変更が統制を外れる |
| E. 検出された変更の G-6 の承認者を2名にする(コア機能と同じ扱い) | 承認者の数は検出率の向上を主張しない(`gate-criteria.md:920`)。長期的な決定に要るのは別の基準(G-3 の5基準)での判定であり、同じ基準の承認の人数ではない |

### 反論されうる点

- 「パスで検出できる長期的な決定は一部で、依存の追加の意味や暗黙の契約の変更は漏れる」。そのとおりで、網羅は主張しない(結論5)。漏れの残余を開示する。検出できる部分を自己申告から機械へ移すだけでも、信頼性は上がる
- 「判断記録の要否の判定まで記名を求めると、PR ごとの負荷が上がる」。負荷は採否の理由にしない。規則が誤検出を多く出すなら、規則の改訂(技術判断者の起案)で直す。誤検出の件数は規則の改訂の入力にする
- 「区分の下限と判断記録の要否は別の性質で、同じ規則ファイルに置くと意味が混ざる」。置き場と書式と手続を共有し、出力の属性を分ける。意味は属性で区別できる。性質が違うことは、規則を2つの体系に分ける理由にならない
- 外部の作法(Kubernetes)は OSS の単一のプロジェクトであり、規格ではない。採る根拠の水準は E2(単一事例)相当で、暫定マークを要する

## R-3 AI レビューの位置づけ

### 結論

1. **AI レビューを、検出の層(H.4)の外に数える余地は無い**。論点の外を AI レビューで「補った」ことを、人の確認の範囲を縮める根拠に数えない。H.4 条件4(`assurance-case.md:322`「通過を理由に人の確認を減らさない」)を維持する
2. 「補う」を規定の語として使わない。AI レビューの働きは「検出の層として置く」と書く。「補う」は、確認の範囲を AI と人で分け合い、合わせて全体を覆ったと読める。H.4 の検出の層の定義(`assurance-case.md:313`「人の確認を減らす理由にもなりません」)と逆の意味を持つ
3. **AI レビューを承認とみなさないことを再確認する**。AI と bot の名義の承認は数えない(`gate-criteria.md:913`、第3章 3.5.4)。AI の確認はどの独立の段にも数えず、道具の適格性で段に数える経路も設けない(`overview.md:185`)。新しい規定は要らず、既存の所在を ADR で引くだけでよい
4. **AI レビューの指示を、レビューの対象の変更から読まない**。これは H.4 条件3(`assurance-case.md:321`)と第5章の要求事項7(IMPL-0333、`human-ai-boundary.md:1075`、`state=undelivered`、#369、見直し 2027-04)で既に要求事項である。#422 では新しい条項を作らず、IMPL-0333 の降ろし方(基底の側の指示でレビューする仕組み)が未達であることを、#422 の運用の前提の欠落として明示する
5. AI レビューの指摘を全部直すことを求めない。採否は人が決め、指摘の内容と採否を残す(H.4 条件5 と同じ)。「指摘が無いこと」を安全の根拠にしない旨は、H.4 の検出の層の定義で既に足りる
6. AI レビューの検出率を前提にした配分(「AI が X% 捕まえるので人は見なくてよい」)を採らない

### 理由

- **規格群で自動化が人の検証の代わりになる経路は、道具の適格性確認だけである**【既知・未照合: DO-330、ISO 26262-8 の道具の信頼度】。その経路は、道具の振る舞いが決定論的で、要件に対して検証でき、版が固定されることを前提にする。AI の推定による判定は、同じ入力で同じ出力を返す保証が無く、担い手の識別が変われば測り直しを要する(H.4 条件1)。本標準が H.4 で「決定論的な検査は検証に数え、AI の推定による判定は検出の層に限る」と分けた線(`assurance-case.md:307-311`)は、規格群の線と同じ位置にある。#422 はこの線を動かす新しい根拠を持っていない
- **検出の層の外に数えるには、実測が要る**。EV-0059 の差し替え条件は「ある条件を欠いても検出率に差が無い場合は、その条件を外す」(`assurance-case.md:365`)。条件4 を外す道は、自組織の欠陥注入の測定で開いている。所有者の提起や外部の運用の伝聞では開かない。外部の AI レビューの検出性能は F1 約 50% で、測定はベンダの関与したものだけである(`survey-422-2-external.md` 2.7)。人の確認を減らす根拠になる水準ではない
- **外部の一次資料も、AI レビューを承認に数えていない**。Anthropic の Code Review は承認も阻止もしない(`survey-422-2-external.md` 1.1)。GitHub Copilot は既定で必須承認に数えない(同 2.4)。社内の自動承認(Anthropic の低リスク層、Meta RADAR)は、AI のレビューを承認に数えたのではなく、リスクの層の判定で人の事前の承認を外し、事後の標本検査を置いた構成である。本標準でこれに当たるのは 5.5.4 の委任で、その根拠は「AI が代わりに読んだこと」ではなく「検出でき、取り消せること」である(`human-ai-boundary.md:422-494`)。外部の構成も、根拠を AI のレビューだけに置いていない点で本標準と同じ向きである(ただし RADAR は LLM レビューを適格性の段の1つに含む。段の1つであって、承認の主体ではない)
- **指示を PR から読まない点は、外部で設計が割れている**。Anthropic の `REVIEW.md` は基底ブランチから読み、GitHub Copilot の指示は head ブランチから読む(`survey-422-2-external.md` 2.4)。本標準は H.4 条件3 で前者を要求している。後者の構成を使う採用者は、条件3 を満たさない。採用者向けにこの差を注記することは、規格として有益である。ただし道具の名は書かず、「指示を変更の側から読む構成は条件3 を満たさない」と書く(1.7「特定の製品名に依存する表現は用いない」`overview.md:282`)

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. 論点の外を AI レビューが見たことを記録し、その範囲の人の確認を省く | H.4 条件4 の否定。AI の範囲の自己申告は確認の範囲の根拠にしてはならない(`assurance-case.md:430-434`)。入力の記録も「確かめたこと」を示さない(同) |
| B. 検出率を測った AI レビューに限り、検出の層の外(判定の一部)に数える | 検出率が高くても、推定による判定は決定論的な検査にならない。判定に数えるには、人の判定か決定論的な検査のどちらかが要る。検出率の測定が整えば、変わるのは H.4 の条件(どの条件を外せるか)であり、種別ではない |
| C. AI レビューの指摘への応答を合否条件にする(重大な指摘が残ればマージを止める) | 第4章「AI による事前審査を合否条件として挿入する手段は採りません」(`gate-criteria.md:1831`)。偽陽性が正当な変更を止め、偽陰性が「通過した」記録として残る。止めたいものは G-5 の決定論的な検査に置く |
| D. #422 のために新しい条項で「AI レビューは承認でない」を書き直す | 同じ事項の規定は1か所に書く(1.7 `overview.md:280`)。所在は H.4・3.5.4・`overview.md:185` にある。ADR で所在を引けば足りる。重複して書くと、改訂のたびに食い違う |

### 反論されうる点

- 「AI の品質が上がり続けており、検出の層に留め続けるのは能力の過小評価である」。能力の評価は、2026-11-04 時点の公開の測定(F1 約 50%、独立の測定なし)による。能力が上がれば、EV-0059 の差し替え条件で自組織の測定から条件を外す道がある。規格は能力の見通しではなく、測定で書く
- 「AI レビューを検出の層に留めるなら、人は全行を読む負荷から逃れられず、形骸化が続く」。本標準は人に全行を読むことを求めていない(H.5)。形骸化への手段は、欠陥注入(5.6.2)と承認権限の一時制限(7.9)である(ADR-0059 決定1)。AI に範囲を渡すことは形骸化への手段にならない。人の注意を AI の示した場所へ固定する向きの実証がある(Tufano)
- 外部の自動承認の運用(Anthropic・Meta)を「AI を承認に数えた例」と読む委員がいるかもしれない。一次資料の記述は「リスクの層の判定で自動承認し、標本を人が見る」であり、AI のレビューが承認の主体であるとは書いていない〔要照合: Anthropic の記事は WebFetch の要約経由〕

## R-4 記録・計測・テンプレート

### 結論

1. **G-6 の判定記録に「確認した範囲 / 確認していない範囲」を課さない**。5.7.2 の「確認していない事項」の構造(`human-ai-boundary.md:830-847`)は、G-8・SG・例外承認の決断の記録のままとし、G-6 へ広げない。課さないと決めた旨を明記する
2. **計測は採る**。絞り込み(重点の提示)の効き目を、承認ごとの申告ではなく、**欠陥注入の配置**と**欠陥の台帳の欄**で測る
   - 欠陥注入(5.6.2)で、重点の提示(索引部・注意喚起部・レビュー観点の指定)を用いる構成では、注入する欠陥の一部を提示された箇所の**外**に置く。提示の内と外の検出率を分けて記録する
   - 欠陥の台帳とポストモーテムに、「見逃した欠陥の所在が、レビューで提示された重点の内か外か」の欄を置く
   - 外の検出率が内より低い状態が続く場合は、ADR-0023 決定10(下がった場合は撤去)を提示の仕組みに当てる
3. **PR テンプレートの「レビュー観点の指定」は任意のまま残し、必須にしない**。そのうえで、欄の扱いを本文(`pr-workflow.md:92-95`、`:116`)と準拠テンプレート(`template/.github/PULL_REQUEST_TEMPLATE.md:98-100`)の両方に書く
   - 書き手は作成側である(人。作成を指示した者を含む)
   - 注意を狭める情報として、パス1 の後に読む(ADR-0023 決定3)
   - 確認の範囲を定めない。**指定の有無にかかわらず、差分の全体がパス1 の対象である**。現行の注記「省略した場合は差分全体が対象です」は、裏返して「指定した場合は指定箇所だけが対象」と読めるため、改める
   - 結論(「ここ以外は問題ない」「ここは確認済み」)を含めない(ADR-0023 決定2)
   - AI に生成させない(`pr-workflow.md:124` 判断を含む欄を自動生成させない)
4. 準拠テンプレートへの降ろし方は、`src/data/template-fields.yaml` の必須欄の対象にしない(任意の欄のため)。注記の文言を実装マーク(`target=pr-template`)で降ろす。check-pr はこの欄の中身を読まない(5.7.4)。欄の記入を必須にしないので、有無も検査しない
5. `/review` 系のスキルを新設しない。レビュー側の入口は `/human-verify` と `/gate G-6` に既にある。重点の扱い(パス1 の後に読む、範囲を定めない)は `/human-verify` の検証の順序へ追記する

### 理由

- **承認ごとの範囲の申告を課さない理由**。#271 で「承認ごとに何を確かめたかの署名様式」を却下している(内部調査 2。先例は承認の事実の署名まで、検出能力を示さない書類が増える)。G-6 の承認の意味は H.5 で既に固定されている(受入基準との一致と挙動の説明。全行の読解は意味しない)。承認ごとに範囲を書かせると、承認の意味が承認ごとに変わる。「受入基準の項目1〜3 は確認、4 は確認していない」と書いた承認は、判定基準1(受入基準の項目ごとに挙動を確認)を満たさない承認であり、範囲の記録ではなく差し戻しの対象である。範囲の記録が意味を持つのは、範囲が判定ごとに変わる判定(G-8・SG・例外承認)であり、範囲が基準で固定された G-6 ではない
- **規格の作法との関係**。IEEE 1028 の技術レビューの出力や ISO 19011 の監査報告は、対象・目的・範囲の記載を求める【既知・未照合】。これは、レビューの単位が会議体・監査の1回で、範囲がその回ごとに計画されるためである。本標準の G-6 は、範囲を判定基準が固定し、記録(判定基準1・2・6)を PR ごとに残す構成で、同じ要請を既に満たしている。範囲を回ごとに計画する様式を、範囲が固定された判定へ持ち込む必要は無い
- **測るのは工程であり、個人の申告ではない**。ADR-0023 決定10 は効果を欠陥注入の検出率で、工程単位で測る。ADR-0059 は形骸化の検知を 5.6.2 と 7.9 に置く。重点の提示が注意を固定するかどうか(Tufano の向き)は、提示の外に注入した欠陥の検出率でしか確かめられない。現行の 5.6.2 には注入の配置の要件が無い(内部調査 4.3 の穴)。この穴を埋めることが、#422 の懸念(承認が形だけになる)に対して最も直接の手段である
- **「レビュー観点の指定」を必須にしない理由**。必須にすると、作成側が毎回、注意を狭める情報を書く。提示が注意を固定する向きの実証(Tufano、MetaMateCR の UI の変更)がある以上、必須化は固定の機会を全 PR へ広げる。中身の質は機械で判定できない(5.7.4)ので、必須化しても形だけの記入が残る(5.7.2 の冒頭が「1行の理由」を退けたのと同じ理由)
- **注記を本文と準拠テンプレートの両方に書く理由**。現状、本文は「とくに見てほしい箇所・自信のない判断」、準拠テンプレートは「省略した場合は差分全体が対象」で、ずれている(内部調査 3)。準拠テンプレートの文言は、範囲を限定する効力を持つと読める。規格の写しが規格より強い限定を持つ状態は、ADR-0040(テンプレートは第6章の部分集合。標準と逆の指示を書かない)の趣旨に反する

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. G-6 の判定記録に「確認していない事項」を必須にし、「なし」を認めない(5.7.2 を G-6 へ広げる) | G-6 の範囲は判定基準で固定されている。確認していない受入基準があれば差し戻しであり、記録で済ませるものではない。#271 の却下と同じ形(検出能力を示さない書類が増える) |
| B. G-6 で人が確認した範囲を任意で書ける欄を置く | 任意でも、書いた範囲が承認の意味を狭めたと読まれる。「範囲を書けば承認の意味を狭められる」経路ができる。承認の意味は H.5 に1つだけ置く |
| C. 「レビュー観点の指定」を必須にし、check-pr で有無を検査する | 上記の理由。固定の機会を全 PR へ広げ、中身は形だけになる |
| D. 論点の外で見つかった欠陥の率を、承認者ごと・レビュアごとに算出する | ADR-0023 決定10 は個人単位の検出率を算出しない。個人の評価に使われると、提示を読まない動機と読んだと書く動機が同時に生じる |
| E. `/review` スキルを新設する | 入口は `/human-verify` と `/gate G-6` にある。入口を増やすと、同じ手順の写しが2か所に生じる(1.7 の1か所の原則) |
| F. PR の規模の上限(行数)を、論点を絞る代わりの規範にする | #422 の範囲の外。規模は ADR-0047・ADR-0058(上限は遮断でない、規模の確認)で扱っている。SmartBear の数値は原典未読・2006 年・人のコードが対象(`survey-422-2-external.md` 3.3) |

### 反論されうる点

- 「G-6 で範囲を記録させないと、人がどこを見たか後から分からない」。後から分かる必要があるのは、工程として見逃しが起きているかであり、個々の承認者が何行読んだかではない。前者は欠陥注入の配置と台帳の欄で分かる。後者を記録させても、記録と実際の確認が食い違うことを確かめる手段が無い(H.4 の自己申告の扱い `assurance-case.md:430-434` と同じ理由)
- 「欠陥注入を提示の外へ置く要件は、注入の設計の負荷を上げる」。負荷は採否の理由にしない。配置の要件が無ければ、提示の仕組みが注意を固定しても検出されない
- 「パス1 を差分の全体に掛けるなら、大きな差分で人の負荷が下がらない」。パス1 が見るのは「差分が基準の範囲内か」で、全行の読解ではない(目安10分、`review-guide.md:21-60`)。大きな差分の負荷は、規模の確認と分割(第4章)で扱う
- Google の手引きは「一部しか見ていないならどこを見たかを書く」とする(`survey-422-2-external.md` 2.1)。これは G-6 に範囲の記録を課す根拠になりうる。しかし Google の手引きは、範囲を書いたうえでほかのレビュアが残りを見る前提であり、承認の意味を1つに固定した規格の判定とは単位が違う。本標準で「一部しか見ていない」承認は、判定基準1 を満たさないため承認にしない

## R-5 記録

### 結論

1. **新しい ADR を起こす**。#422 の結論は、課さないと決めたことを複数含み、ADR-0023・ADR-0056(H.4)・ADR-0059 と #162・#172・#271 の却下の再確認を伴う。あとから同じ提起が来たときに、どこで何を決めたかを1か所で引けるようにする
2. ADR は、**既存の ADR のどれも置き換えない**。ADR-0023 決定2・3・7・8・10、ADR-0056 決定4(H.4 条件4)、ADR-0059 決定1、ADR-0067 決定3 を引いて維持する。採用済み ADR の本文は書き換えない
3. ADR の決定(案)
   - 決定1: G-6 の承認の範囲を PR ごとの論点に絞る規定を設けない。パス1 は差分の全体に掛ける。深さを絞る根拠は L1 と規模の確認の保証の所在に限る(R-1)
   - 決定2: 重点の生成元を機械的な導出に限り、範囲を広げる情報として扱う。作成側の「レビュー観点の指定」は注意を狭める情報として、パス1 の後に読み、範囲を定めない(R-1・R-4)
   - 決定3: 判断記録を要する変更を、区分の下限の規則と同じ置き場・書式・手続の規則で検出し、G-3 の経路に乗せる。網羅を主張しない。規則に当たった変更で判断記録を不要とするときは、作成を指示した者以外の自然人が記名する(R-2)
   - 決定4: AI レビューは検出の層であり、人の確認の範囲を縮める根拠に数えない。「補う」を規定の語に使わない(R-3)
   - 決定5: 欠陥注入の配置(提示の外)と、欠陥の台帳の欄(提示の内/外)で、重点の提示の効き目を工程単位で測る(R-4)
   - 決定6: G-6 に「確認していない事項」を課さない(R-4)
4. ADR の「検討した選択肢」に、採らない案を理由とともに載せる。最低限、次を載せる
   - 作成者または AI が論点を抽出し、人の承認をその範囲に絞る
   - リスク層別の自動承認と標本検査(Anthropic・Meta の運用)を新しい経路として設ける
   - AI レビューの検出率を前提にした人の確認の配分
   - AI レビューを承認、または合否条件に数える
   - 長期的な決定の承認の新しい席・経路
   - G-6 の判定記録への「確認していない事項」の必須化
   - 「レビュー観点の指定」の必須化
   - 視点別の読み方による観点の割り当て
5. コンテキストに、**所有者の前提が一次資料で半分だけ確かめられたこと**を事実として書く(確かめられたのは全 PR の AI レビュー・承認は人・リスク層別。確かめられなかったのは論点で絞ること)。前提が確かめられた場合でも採否は信頼性の判断軸で決めた、と書く
6. 暫定マーク(ADR-0026)を付ける対象
   - 決定3(機械の検出が判断記録の漏れを減らすという前提)。根拠の水準は E2(Kubernetes の単一事例)。差し替え条件は、規則の導入の前後で、G-3 を経ずに取り込まれた設計上の選択(後から判断記録が起こされた件数)の差
   - 決定5(提示の外への注入で注意の固定を検出できるという前提)。根拠の水準は E1〜E2(Tufano の1件と ADR-0023 の引く実験)。差し替え条件は、自組織の提示の内と外の検出率の差
   - 決定1 のうち「論点に絞るとパス1 の検出が落ちる」は、構造上の帰結として書き、実証を主張しない。実証を主張しないことを明記する
7. 本 ADR が依る外部の規格(ISO/IEC 20246、IEEE 1028、DO-330 など)は、原典未照合である。ADR の根拠に規格の条文を引かない。引くなら原典と照合してからとする。照合していない規格は、ADR の本文で「趣旨のみ、原典未照合」と書くか、引かない

### 理由

- **却下は成果である**(コアポリシー)。#422 の結論の多くは「課さない」であり、本文に書かれないものが多い。ADR に残さなければ、「書かれていない」と「課さないと決めた」の区別がつかない。#162・#172 で既に却下した形が #422 で再び提起されたこと自体が、却下の記録の引きやすさが足りないことを示している
- **既存 ADR を置き換えない理由**。本意見の結論は、どの既存の決定も変えない。新しく足すのは、R-2 の検出の規則、R-4 の注記と計測の配置、R-3 の語の扱いである。いずれも既存の決定の範囲を埋めるもので、矛盾しない。突合の結果は次のとおり
  - ADR-0023 決定3 の索引部・注意喚起部の区分に「レビュー観点の指定」を注意喚起部の側として位置づける(矛盾なし)
  - ADR-0039 決定4 のリスク区分の変更ごとの単位を変えない(矛盾なし)
  - ADR-0059 決定1 の検知の担い手(5.6.2・7.9)を変えない。決定5 は 5.6.2 の注入の配置を足すだけ(矛盾なし)
  - ADR-0067 決定3 の観点の分担を課さないを維持する(矛盾なし)
  - ADR-0041(範囲は網羅でない)と、決定3 の網羅を主張しない書き方が一致する
  - ADR-0040(テンプレートの様式)と、R-4 の注記の降ろし方が一致する(任意の欄なので必須欄に登録しない)
- **規格の条文を引かない理由**。1.3(`overview.md:62-70`)は、本標準が引用規格を持たず、引くときは版と読んだ範囲を書くと定める。今回読めていない規格を ADR の根拠に引けば、この規定に反する

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. ADR を起こさず、Issue のコメントに結論を残す | #162・#172 は Issue のコメントに残したため、#422 の提起の時点で引かれにくかった。課さないと決めたことは公開の記録に置く |
| B. ADR-0023 を置き換える新 ADR にする | ADR-0023 の決定はどれも変えない。置き換えると、変えていない決定の所在が新 ADR へ移り、引き先が増える |
| C. 外部の運用(Anthropic)を採らなかった理由を「未確認だから」と書く | 未確認であることは事実として書くが、採否の理由にしない。確かめられていても、R-1 の結論は信頼性の判断で変わらない |

### 反論されうる点

- 「ADR が却下の列挙ばかりになり、決定の記録として読みにくい」。読みにくさは採否の理由にしない。決定と検討した選択肢を分けて書けば、決定は6つに収まる
- 「R-2 の検出の規則は、ADR の決定にする前に、区分の下限の規則の書式に属性を足せるかの実装の確認が要る」。そのとおりで、決定3 は規則の置き場と手続を決め、属性の書式は実装の Issue に回す。実装が降りるまで実装マークを `state=undelivered` で表示し続ける
- 規格委員として、本意見が既存の決定を守る方向に偏っているとの批判はありうる。既存の決定を守る理由は、それが既存だからではなく、#422 の提起にも外部調査にも、既存の決定の根拠(自動化バイアス、独立の考え方、別経路の禁止)を覆す新しい実証が無いからである。R-2 と R-4 の計測は、既存の規定に無い穴を埋める新しい規定であり、守るだけの意見ではない
