# 会議体 #422 委員「現場(field)」の意見

- 日付: 2026-11-04
- 立場: AI エージェントが PR を大量に出す現場のレビュア。承認が形だけになる実態、レビュアの帯域、1〜2名・3〜9名・10名以上の体制で回るかを問う
- 入力: `council-00-agenda.md`、`survey-422-1-internal.md`、`survey-422-2-external.md`、本文(path:line は各論点に記す)
- 所有者の提起(#422)も第三者の意見として扱う。安さ・変更量の少なさは採否の理由にしない

## 前置き: 現場で承認が形だけになる仕組み

所有者の動機(承認・マージを形だけ行っても意味がない)は、現場の実感と一致します。ただし、形骸化の原因の見立てが提起とずれていると考えます。

- 現場で形骸化が起きる直接の原因は、**流入の量**である。エージェントは1人のレビュアに1日十数件の PR を積める。附属書C の目安は1人1日 3〜4 件(`review-guide.md:170`、EV-0086)。差が数倍になった時点で、レビュアは「全体を薄く見て承認する」か「滞留させる」しか選べない。前者が形骸化である
- 「論点に絞る」は、この差を埋めない。**「全体を薄く見て LGTM」が「3行の論点を見て LGTM」に置き換わるだけ**である。絞った範囲の外は、誰も見ていない状態で承認の記録が残る。形骸化の範囲が見えなくなる分、現状より悪い
- 作成側(エージェント)が書いた論点は、現場では**事実上の上限**として働く。附属書C は「省略した場合は差分全体が対象」と書く PR テンプレートの注記(`template/.github/PULL_REQUEST_TEMPLATE.md:98-100`)を持つ。裏返すと「指定すればそこだけ」と読まれる。忙しいレビュアは必ずそう読む
- Tufano ほか(survey-2 §3.2)の「LLM が示した場所に注意が寄る」は、現場の観察と合う。AI の指摘が10件並ぶと、レビュアはその10件の妥当性の判定に時間を使い、指摘の無い箇所を探さなくなる。MetaMateCR(AI の修正案を見せるとレビュー時間が伸びた)も同じ現象である

したがって現場の結論は、「範囲を絞る」ではなく「**流入を絞り、深さの配分だけを変える**」です。以下の各論点はこの見立てに立ちます。

## R-1 人の確認の範囲を絞るか、何で絞るか

### 結論

- **G-6 の確認の「範囲」は絞らない。絞ってよいのは「深さ」だけ**とする。パス1(差分が受入基準の範囲内か。仕様外の変更の混入)は、論点の有無にかかわらず**差分全体**に掛ける
- 深さの配分の材料(どこを深く読むか)は、**機械的な導出**(自動検査の出力、変更パスの一覧と影響範囲、既存テストの変更、依存の差分、リスク区分の下限の規則に当たったパス)に限る。これは既存の 3.10.12(`roles-responsibilities.md:1270`)、ADR-0023 決定7、`/human-verify` の検証の順序(`template/.claude/skills/human-verify/SKILL.md:24-36`)の再確認であり、新しい経路ではない
- 作成者(人)が書く「見てほしい箇所」は、**範囲を広げる方向にだけ効く情報**として扱う。範囲を狭める根拠にしない。AI の担い手が論点を抽出して書くことは認めない
- リスクの層で人の承認を外す(Anthropic・Meta 型の低リスク自動承認)は、本論点では採らない。判定の時点を移す経路は 5.5.4 と第8章の1つだけ(`gate-criteria.md:1823`)であり、低リスクの変更を人の事前確認から外したいなら、その7条件で扱う

### 理由

1. **パス1 は数え上げで回る**。差分の変更パスの一覧を受入基準と突き合わせる作業は、`/human-verify` 順1〜3 で機械が材料を揃えるので、PR が大きくても 10 分の目安(附属書C)に収まる。帯域を食うのは順5(実装コードの逐読)であり、そこは既に「疑義が生じた箇所に限定して」読む(SKILL.md 順5)。つまり**帯域の問題は、範囲ではなく深さで既に解いてある**。範囲まで絞る必要が現場に無い
2. **AI 生成の PR で最も多い混入物は仕様外の「ついで実装」**(`review-guide.md:21-60`)。作成側の論点は、作成側が意図した変更について書かれる。意図していない混入は、定義上、作成側の論点に載らない。論点で範囲を絞ると、パス1 の目的そのものが論点の外へ落ちる
3. 作成側の論点は、3.5.3 の入力の分離(`roles-responsibilities.md:585-596`)で言う作成側の主張であり、ADR-0023 決定2 の「自分で確認しなくてよいと読める記述」= 結論に当たる。現場では、この種の記述は書いた側の意図と無関係に上限として読まれる(前置き)
4. リスク層の自動承認(Meta RADAR)は、効果の報告が選択バイアスと交絡し、人の注意深さを測っていない(survey-2 §2.3)。また、Anthropic の一次資料で確かめられたのも「層別」までで、「論点で絞る」ではない(survey-2 §1.5)。提起の前提は根拠として使えない

### 体制ごとに回るか

| 体制 | 現場の実態 | この結論で回るか |
| --- | --- | --- |
| 1〜2名 | 2名なら相互確認で G-6 が成立(`tailoring-guide.md:195`)。1名・相手も指示に関与した変更は外部の確認者が要り、帯域は外部側にしかない | 回る。外部の確認者の帯域は**リスク区分で件数を配分**してよい(`tailoring-guide.md:236-240`、ADR-0054 決定8)。これは「どの変更に人を当てるか」の配分であり、1件の中の範囲を絞るのではない。定常変更は第8章の事後監査への切替で扱う。範囲を絞る新しい規定は要らない |
| 3〜9名 | 最も破綻しやすい。レビュア 1〜2 名に対し、エージェントを使う開発者が数名いると、流入が帯域の数倍になる | 範囲を絞っても破綻は防げない。効くのは第4章「流入を絞る」の制御2(指名先が無ければ生成を止め、実装計画へ差し戻す。`gate-criteria.md:1808-1812`)。**この制御が実行層に降りていないなら、それが #422 の本当の穴**である(R-4 で扱う) |
| 10名以上 | レビュアの母数はあるが、領域ごとの所有者に依頼が偏る | 範囲は絞らず、指名の割り振り(所有者の領域、R-2 の別経路)で偏りを解く。範囲を絞る必要は小さい |

### 譲れない点

- **パス1 は差分全体に掛ける**。論点・観点の指定・AI の指摘のいずれも、パス1 の範囲を狭めない
- 範囲を狭める根拠を、作成側の申告と AI の出力に置かない
- 人の承認の記録が、人が見ていない範囲まで覆っているように見える状態を作らない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| PR ごとに作成側(人または AI)が「本質的な論点」を書き、人はそこだけを承認する | 論点の外の混入をパス1 が拾えなくなる(理由2)。作成側の主張が上限として読まれる(理由3)。形骸化の範囲が記録上見えなくなる |
| AI の担い手に論点を抽出させ、人に提示する | 3.10.12 の生成元の限定(自動検査の出力)と ADR-0023 決定8 に反する。Tufano の注意の固定をそのまま制度化する |
| 低リスクの変更を人の承認なしで自動承認し、標本を人が見る(リスク層別、Anthropic・Meta 型) | 判定の時点を移す2つ目の経路になる(`gate-criteria.md:1823`、#172 の棄却と同形)。採るなら 5.5.4 の7条件の改訂として別に議論する。本論点の結論にしない |
| 1〜2名の体制に限り範囲を絞ってよいとする | 1〜2名は確認者が最も少なく、絞った外を拾う者が誰もいない。帯域の配分は件数単位で既にある(`tailoring-guide.md:236`)。体制が小さいほど絞りを緩める根拠は無い |

### 反論されうる点

- 「パス1 を全体に掛けても、数千行の差分では結局薄くなる」。これには規模の上限と分割(第4章、ADR-0047・ADR-0058)で応じる。規模の確認を越えた差分の「保証の所在」(`gate-criteria.md:1580-1612`)は、範囲を実行可能な保証で限定する既存の経路(L1)である。ただし L1 の中身を機械で確かめられない(survey-1 §4.2 穴)ことは認める
- 「深さだけの配分なら、深く読まなかった箇所の欠陥は結局見逃す」。その通りで、H.5 は全行を読んだことを主張しない(`assurance-case.md:461-473`)。見逃しの量は欠陥注入で測る(R-4)。範囲を絞る案は、この見逃しを測る手段も持たない点で劣る
- 「現場は既に論点だけ見ている。規定が実態に追いついていない」。実態は形骸化の実態であり、規定を実態へ寄せる理由にならない(コアポリシー: 判断軸は信頼性)

## R-2 長期的な決定の切り出し

### 結論

- **採る**。長期的な決定に当たりうる変更(公開インタフェース、永続データの形式・スキーマ・migration、依存の追加、権限・設定の構造、アーキテクチャの境界を定めるパス)を、**変更の内容から機械的に検出**し、判断記録の有無を確かめ、無ければ G-3 へ引き上げる。新しいゲートは作らず、**既存の G-3(技術判断者)へ乗せる経路**とする
- 検出の規則(パス・型・依存の差分)の正本は、**PR 自身の変更では書き換えられない場所**(既定ブランチの保護された設定)に置く
- 規則に載らない長期的な決定は、PR テンプレートの自己チェック(`PULL_REQUEST_TEMPLATE.md:110`)を残し、加えて**レビュアが「判断記録が要る」を差し戻しの理由に挙げられる**ことを明記する
- AI の担い手の「長期的な決定に当たる」との指摘は、**検出を足す方向にだけ**使う。「当たらない」との出力で検出を外さない

### 理由

1. 長期的な決定は、PR の差分に埋もれると G-6 のレビュアの帯域では拾えない。3〜9名の体制で、1日に十数件を見るレビュアが、各 PR の設計上の選択を判断記録に照らす余裕は無い。**拾える前提に立った規定は、現場では拾われない**
2. 本標準は判断記録と G-3 を既に分けている(第2章 2.6、`gate-criteria.md:429-447`)。欠けているのは、PR から G-3 へ引き上げる**検出**だけで、それが自己チェックに頼っている(survey-1 §4.1 穴)。自己チェックは作成側の申告であり、エージェントは「該当なし」に印を付ける
3. 外部の実例として Kubernetes の API レビュー(パス・型から自動でラベルを付け、専任の承認者の別経路)がある(survey-2 §2.5)。長期運用の実績があり、Anthropic の `REVIEW.md` の「`migrations/` 配下は Important」とも方向が一致する
4. 機械的な検出は、作成側の申告にも AI の推定にも依らない。入力の分離・ADR-0023 決定7(機械的導出に限る)と矛盾しない

### 体制ごとに回るか

| 体制 | 懸念 | 回し方 |
| --- | --- | --- |
| 1〜2名 | 技術判断者と作成の指示者が同じ人になりやすい | G-3 の判定者の兼務の扱いは既存の規定による。本論点は検出を足すだけで、兼務の可否を変えない。検出されたことと判断記録の有無が記録に残ることで、少なくとも後から追える |
| 3〜9名 | 技術判断者が1名で、検出が多いと律速になる | 検出の規則を広く取りすぎると、ラベルが常時付いて無視される(警報の形骸化)。規則は**登録制で、件数と判断記録に至った割合を見て見直す**。見直しは規則の正本の変更として人が行う |
| 10名以上 | 領域ごとに技術判断者が分かれる | 規則と判定者の対応(領域の所有者)を登録して指名を割り振る。CODEOWNERS と同形 |

### 譲れない点

- 検出は**機械の規則**で行い、規則の正本は PR から書き換えられない
- 検出された変更で判断記録が無いものを、G-6 の承認だけで通さない(G-3 へ引き上げる)
- AI の出力で検出を外さない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| PR に「長期的な決定」の欄を設け、作成側に必須で書かせる | 作成側の申告で、エージェントは空欄か「なし」を書く。検出の根拠にならない。欄の存在だけを検査しても(5.7.4)中身は確かめられない |
| AI の担い手に長期的な決定かを判定させ、その結果で経路を分ける | AI の推定による判定は検出の層に限る(H.4、`assurance-case.md:303-368`)。「当たらない」を根拠に外すと、偽陰性が記録として残る |
| 長期的な決定の承認者として新しい席を設ける | G-3 の技術判断者が既にいる。2つ目の承認経路を作ると緩いほうが使われる(`gate-criteria.md:1823` と同じ理由) |
| 長期的な決定を G-6 の判定基準に加え、G-6 のレビュアに見つけさせる | 理由1。G-6 のレビュアの帯域では拾えない。G-6 基準3(コア機能の判断記録の添付)は残す |

### 反論されうる点

- 「規則に載らない長期的な決定(依存の意味、暗黙の契約)は漏れる」。漏れる。規則は網羅を主張しない旨を明記し、レビュアの差し戻しと自己チェックで補う。漏れた決定は事後に判断記録の欠落として欠陥の台帳に載せ、規則の追加の材料にする
- 「検出の誤検出が多いと現場は無視する」。その通りで、規則の見直しの量(件数と判断記録に至った割合)を持たせるのはそのため。量の基準値は実測が無いので、置くなら暫定マーク(ADR-0026)を付ける

## R-3 AI レビューの位置づけ

### 結論

- AI レビューは**検出の層**のままとする(H.4、`assurance-case.md:303-368`)。論点の外を AI レビューで「補う」ことを、人の確認の範囲を縮める根拠に数える余地は**無い**。H.4 条件4「通過を理由に人の確認を減らさない」を維持する
- 本標準の文言として、AI レビューが人の確認を「補う」「代わる」「肩代わりする」と書かない。書けるのは「**人の確認と別の観点で欠陥を探す検出の層**」まで
- AI レビューは承認ではない(必須承認の数に数えない。`gate-criteria.md:913`)ことを再確認する。GitHub Copilot の「設定で必須承認を満たせる」機能(survey-2 §2.4)を使う構成は、本標準に準拠しない構成として明記する
- AI レビューの指示(`REVIEW.md` 相当)は **PR 自身の変更から読まない**。既定ブランチの保護された正本から読む(IMPL-0333 の系として降ろす)
- **AI の指摘の採否は作成側が判断して記録する**。人のレビュアに AI の指摘一件ずつの採否判定を課さない。採否の記録と AI の指摘は、人のレビュアには**パス1 の後**に開く(ADR-0023 決定3・4 と同じ扱い)

### 理由

1. 現場で AI レビューを入れると、レビュアの負荷は**下がらずに移る**。AI の指摘が十数件付いた PR では、レビュアは指摘の妥当性の判定に時間を使う(MetaMateCR のレビュー時間の増加、Beko の「無関係なコメント」への不満。survey-2 §3.2)。AI レビューを「補い」に数えると、この時間が「人の確認」として記録され、指摘の無い箇所は誰も見ていない状態になる
2. AI レビューの検出性能は F1 約 50%(ベンダ関与の測定のみ。survey-2 §2.7)。半分を拾う層を根拠に人の範囲を削れば、削った範囲の見逃しは半分残る。しかも独立した測定が無い。H.4 条件1(検出率の測定)を満たした組織は現場ではまず無い
3. 人のレビューの価値の多くは保守性と理解の共有(Mäntylä & Lassenius 75%、Bacchelli & Bird)で、AI レビューの既定(正しさ)とは重なりが小さい(survey-2 §3.1)。**重ならないので、補い合う関係ではない**。「AI が正しさを見たので人は正しさを見なくてよい」と言える構造でもない(人のパス2 にも正しさは含まれる)
4. 採否の判定を作成側へ寄せるのは、現場の帯域の観点で効く。レビュアの仕事を「AI の指摘を裁く」から「自分で差分を見る」へ戻す。これは事前審査を合否条件にすること(`gate-criteria.md:1829`)とは違い、合否に用いない。作成側の採否は作成側の主張なので、パス1 の後に開く
5. PR から指示を書き換えられると、エージェント自身が自分の PR の AI レビューを緩められる。Anthropic は基底ブランチから読み、GitHub は head から読む(survey-2 §1.1・§2.4)。改ざん耐性の要件として前者を採る

### 体制ごとに回るか

- 1〜2名: AI レビューは代償措置として記録し、G-6 の未達を解かない(`tailoring-guide.md:228`、`:419`)。結論はこれを変えない。1名体制の現場は AI レビューを「誰かが見た」と感じやすいので、未達の表示を消さないことが最も重要
- 3〜9名: 採否を作成側へ寄せることで、レビュア 1〜2 名の時間が AI の指摘の裁定に吸われるのを防ぐ
- 10名以上: AI レビューの指示の正本を領域ごとに分けてよいが、いずれも保護された既定ブランチに置く

### 譲れない点

- AI レビューを人の確認の範囲の縮小、承認、G-6 の未達の解消のいずれにも数えない
- AI の指摘を、人のレビュアの**パス1 より前**に見せることを既定にしない
- AI レビューの指示を PR の変更から読まない

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| H.4 条件4 を外し、AI レビューを通過した範囲は人の確認を省いてよいとする | EV-0059 の差し替え条件(条件を欠いても検出率に差が無いことの観測)が無い。検出性能の独立測定も無い(理由2) |
| AI レビューを PR の必須チェックにし、指摘ゼロを人のレビューの開始条件にする | 第4章「AI による事前審査を合否条件として挿入しない」(`gate-criteria.md:1829`)、#162 の却下と同じ。偽陽性が正当な変更を止め、偽陰性が通過の記録になる |
| AI の指摘一覧を人のレビュアに最初に提示し、確認の起点にする | Tufano の注意の固定(survey-2 §3.2)。ADR-0023 決定4(AI の指摘一覧をパッケージに含めない) |
| AI の指摘をすべて解消することを作成側に求める | Anthropic 自身が「全部直すと過剰設計」と警告(survey-2 §1.1)。採否の判断と理由の記録で足りる |
| 複数の AI(人格・文脈を分けたもの)の合議で人の確認に代える | 合議・多数決は数えてはならない(`assurance-case.md:346-355`)。分離は独立でない(3.5.4) |

### 反論されうる点

- 「作成側に採否を記録させると、エージェントが全部『不採用・理由: 誤検出』と書く」。ありうる。採否の記録は判定の材料ではなく、パス1 の後に人が照合する材料である。不採用の理由が不当なら差し戻しの理由になる。全件不採用の率は検知の材料にできるが、合否の閾値にはしない(ADR-0059 と同じ扱い)
- 「AI の指摘を後で見せると、人と AI が同じ箇所を重複して見る」。重複は許容する。重複を嫌って AI を先に見せると、注意の固定で人の検出が AI の検出の部分集合になる。重複は2層の独立性の対価である

## R-4 記録・計測・テンプレート

### 結論

- **G-6 の判定記録に「確認した範囲 / 確認していない範囲」の自由記述を課さない**。代わりに、`/human-verify` の順1〜4 の機械的な材料(受入基準とテストの対応、外部インタフェースの差分、差分の性質、実行トレース)を**どの版で提示したか**を記録に残す(人が何を読んだかではなく、何が提示されたか)
- **論点の外で見つかった欠陥を測る**。(a) 欠陥の台帳とポストモーテムに「レビューで提示された材料・観点の指定の内か外か」の欄を足す、(b) 欠陥注入(5.6.2)の注入箇所の一部を、観点の指定と AI の指摘の**外**に置く
- PR テンプレートの「レビュー観点の指定」は**任意のまま**とし、注記を直す。(1) 書き手は人(作成を指示した者)、AI の担い手に生成させない、(2) 指定は確認の範囲を狭めない(パス1 は差分全体)、(3) 「ここは問題ない」「ここは見なくてよい」と読める記述を書かない、(4) 人のレビュアはパス1 の後に読む。現行の「省略した場合は差分全体が対象」の一文は削る(裏返しの読みを生むため)
- **第4章「流入を絞る」の制御1・2(同時保有数の上限、指名先が無ければ生成を止める)に実装マークが無く、準拠テンプレートにも実装が見当たらない**(`gate-criteria.md:1796-1812` に IMPL マークなし。`template/scripts` に該当の検査なし。本委員の確認)。#422 の動機(形骸化)に対して最も効く規定が実行層へ届いていないので、`state=undelivered` の実装マークを付けて台帳に出す。降ろし方(check-pr が判定待ちの件数を読むか、/pit が指名先の不在で生成の停止を出すか)は別 Issue で決める

### 理由

1. 現場の体感として、PR ごとの自由記述は量に比例して定型文になる。レビュア1人が1日十件を見るとき、「確認していない範囲」は「特になし」か、同じ文言の貼り付けになる。5.7.2 は「なし」を認めない(`human-ai-boundary.md:830-847`)が、それを G-6 に持ち込むと「受入基準の範囲外は確認していない」といった**何も言っていない定型文**が量産される。#271 で「承認ごとに何を確かめたかの署名様式」を却下した理由(検出能力を示さない書類が増える)と同じである。G-8・SG・例外承認は件数が少ないので自由記述が機能するが、G-6 は件数が桁違いに多い
2. 提示した材料の版の記録は、機械が書くので帯域を食わず、定型文にならない。後から見逃しを調べるとき、「何が提示されていて、何が提示されていなかったか」が分かる。人が何を読んだかは記録で証明できない(H.5)ので、証明できるものだけを残す
3. 論点の外の欠陥の計測は、#422 の運用(論点に絞る)を**採らない判断の根拠を検証可能にする**。もし観点の指定・AI の指摘の外で欠陥がほとんど出ないと測れたなら、そのときに絞りの議論を再開できる。測らなければ、提起は同じ形で繰り返される
4. 観点の指定を必須にすると、エージェントが毎回埋める(書き手を人に限っても、人がエージェントの出力を貼る)。必須の欄は現場で最初に形骸化する欄である。任意のまま、読む時点と効き方を明記するほうが信頼できる
5. 流入の制御は、3〜9名の体制で形骸化を防ぐ唯一の直接の手段である(R-1 の表)。規定があっても実行層に無ければ、現場はエージェントの生成速度に引きずられる

### 体制ごとに回るか

- 1〜2名: 外部の確認者の件数の配分(`tailoring-guide.md:236-240`)の記録で足りる。欠陥の台帳の欄は件数が少なく負荷にならない
- 3〜9名: 流入の制御の実装が最優先。同時保有数の既定値(1人3件、EV-0011、E0)は実測が無いので、較正の材料(判定待ちの件数と滞留時間)を機械で集める
- 10名以上: 欠陥注入の「論点の外」への配置は、母数があるので統計として意味を持つ。小さい体制では件数が少なく、傾向の判断に使えないことを開示する

### 譲れない点

- 観点の指定・AI の指摘が範囲を狭めないことを、PR テンプレートの注記に書く(現行の注記は逆に読める)
- 論点の外の欠陥を測る手段を持つ
- 流入の制御を、降りていない規定として台帳に表示する

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| G-6 の判定記録に「確認した範囲 / していない範囲」の自由記述を必須にする | 理由1。件数が多い G-6 では定型文になり、検出能力を示さない。#271 の却下と同じ |
| 「レビュー観点の指定」を必須欄にし、check-pr で欄の有無を検査する | 理由4。欄の有無しか検査できず(5.7.4)、中身は機械で判定しない。必須化は形骸化を早める |
| 承認までの時間・差分の量の比で形だけの承認を検知し、合否に使う | ADR-0059(承認の比率を検知条件に置かない)、`gate-criteria.md:976`。観測値は注意の喚起にとどめる |
| `/review` スキルを新設し、論点の抽出と人への提示を担わせる | 論点の抽出を AI に担わせる形になる(R-1)。レビュー側の入口は `/human-verify` と `/gate G-6` で足りる。足りないのは注記と流入の制御 |

### 反論されうる点

- 「提示した材料の版だけでは、人が見ていない範囲が記録に出ない」。出ない。人が見た範囲は記録で証明できないというのが H.5 の立場で、記録に出せるように見せる様式は、出せないものを出せるように装う。見ていない範囲の結果は欠陥注入と欠陥の台帳で測る
- 「流入の制御は生産性を落とす」。落とす。帯域を超えた生成は、承認の記録を伴った未確認の変更を増やすだけで、信頼性の観点では生産ではない(`gate-criteria.md:1796-1812` の論理)

## R-5 記録

### 結論

- **新しい ADR を起こす**。題は「人の確認は範囲でなく深さを配分する。長期的な決定は機械で検出して G-3 へ引き上げる」の趣旨。決定の柱は次のとおり
  1. G-6 の確認の範囲を、作成側・AI が示す論点で狭めない。パス1 は差分全体。深さの配分の材料は機械的な導出に限る(R-1)
  2. 長期的な決定を変更の内容から機械的に検出し、判断記録が無ければ G-3 へ引き上げる。規則の正本は PR から書き換えられない場所に置く(R-2)
  3. AI レビューは検出の層のまま。「補う」を人の範囲の縮小の意味で使わない。指示を PR から読まない。指摘の採否は作成側が記録し、人にはパス1 の後に開く(R-3)
  4. 論点の外の欠陥を欠陥の台帳と欠陥注入で測る。G-6 に範囲の自由記述を課さない。流入の制御を実行層へ降ろす(R-4)
- **#422 の動機(形骸化)は認める**。#162・#172 は帯域を動機とした省略を却下した。#422 は動機が違うが、提起された手段(論点に絞る)は #172 で棄却した濃淡と同じ帰結(人が見ない範囲が承認の記録に含まれる)を持つ。ADR には、**動機は受け入れ、手段は採らず、形骸化への手段を流入の制御と欠陥注入に置いた**ことを書く
- 提起の前提(「Anthropic で行われている」)は、一次資料で確かめられた範囲と確かめられなかった範囲を ADR の背景に分けて書く。確かめられた運用(リスク層別の自動承認)は、本 ADR では採らず、採るなら 5.5.4 の改訂として別に扱うことを明記する
- 実証を欠く値(規則の見直しの量、同時保有数の既定値、論点の外の欠陥の比率の判断基準)は暫定マーク(ADR-0026)で開示する

### 理由

1. コアポリシー「却下は成果」。#422 の手段は、言い回しを変えて繰り返し提起される型である(#162・#172 に続く3回目)。「書かれていない」のではなく「課さないと決めた」ことを読み手が区別できなければ、次の提起でまた議論が要る
2. ADR-0023・ADR-0059・H.4 は採用済みで、本文を書き換えない。今回の決定はそれらの**適用の確認と、穴(観点の指定の扱い、長期的な決定の検出、流入の制御の未達)の補修**であり、置き換えではない。新 ADR はそれらを引いて「矛盾しない」ことを突合の結果として書く
3. 現場の観点から最も重要なのは、**形骸化の原因を流入の量と見立てた**ことを記録に残すことである。この見立てが誤っている(流入を絞っても形骸化が減らない)と分かれば、そのときに見直せるよう、差し替え条件として「流入の制御の導入前後の欠陥注入の検出率」を置く

### 譲れない点

- 採らない案を ADR の却下表に、理由つきで残す
- 提起の前提の確認の結果(確かめられた / 確かめられなかった)を ADR の背景に書く
- 形骸化への手段を「範囲を絞る」以外に置いたことと、その差し替え条件を書く

### 採らない案(ADR の却下表に載せる候補)

| 案 | 採らない理由 |
| --- | --- |
| 論点に絞った人の承認(作成側・AI が論点を書く) | R-1 |
| リスク層別の低リスク自動承認+標本検査 | 判定の時点を移す2つ目の経路になる。採るなら 5.5.4 の改訂として別に扱う |
| AI レビューの検出率を前提にした人の範囲の配分 | 独立した検出性能の測定が無い(F1 約 50%、ベンダ関与)。H.4 条件1・4 |

### 反論されうる点

- 「新 ADR は ADR-0023・H.4 の再言で冗長」。再言の部分は引用にとどめ、新しい決定(長期的な決定の検出、観点の指定の注記、論点の外の計測、流入の制御の降ろし)だけを決定に書く
- 「形骸化の原因を流入の量と見立てる根拠は現場の観察と目安(EV-0086)だけで、実証が弱い」。認める。だから見立てを暫定として開示し、差し替え条件を置く。提起の手段(論点に絞る)のほうが、Tufano の対照実験という逆向きの実証を持つ点で、根拠はさらに弱い
