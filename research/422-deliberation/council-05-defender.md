# #422 会議体 意見書 05: 弁護(現行の規定と既存の決定の側)

- 委員: 弁護(defender)
- 日付: 2026-11-04
- 入力: `council-00-agenda.md`、`survey-422-1-internal.md`(内部)、`survey-422-2-external.md`(外部)。本文は path:line で引く
- 立場: 附属書H H.4 の検出の層と条件4、第4章の緩和根拠の表、3.10.12、3.5.3 の入力の分離、ADR-0023、#162・#172・#271 の却下を弁護する。改める必要が本当にあるか、改めると何を壊すかを問う。弁護できない欠陥は欠陥と認める
- 判断軸: 信頼性。変更量の少なさは弁護の理由にしない。所有者の提起も第三者の意見として扱う

## 0. 総論

#422 の動機は「承認とマージが形だけになる」こと、つまり形骸化です。帯域ではありません(内部調査 Q9)。この動機には同意します。ただし、提起の処方「論点に絞り、残りを AI で補う」は、形骸化を止める手段ではなく、**形骸化を制度として承認する手段**になりうる、というのが弁護側の基本の見立てです。理由は3つあります。

1. 外部の唯一の対照実験(Tufano ほか 2024、29 名)は、AI が示した場所に人の注意が寄り、高重大度の指摘は増えないと報告している。「AI が論点を抜き出し、人はそこを見る」は、この失敗様式の制度化である
2. 提起の前提「Anthropic で行われている」は、一次資料で裏付けられた部分が「AI レビューを全 PR に掛け、承認は人」と「リスク層別」だけである(外部調査 §1.5)。「論点で絞る」は確認できない。前提の半分が崩れている
3. 本標準は既に、絞ること自体を禁じていない。H.5(`assurance-case.md:461-473`)と附属書C(`review-guide.md:19`)は全行の読解を主張しない。L1(`gate-criteria.md:1503`)・保証の所在・レビューパッケージ索引部・/human-verify 順5 が、**機械的な導出か実行可能な保証**を根拠に範囲を絞る経路として既にある。欠けているのは「絞る経路」ではない

一方で、弁護できない穴が複数あります(PR テンプレートの「レビュー観点の指定」の扱い、長期的な決定の機械的検出、論点の内外の計測、未達の IMPL)。これらは R-2・R-4 で欠陥として認めます。

## R-1 人の確認の範囲を絞るか、何で絞るか

### 結論

- **G-6 の承認の範囲を「PR ごとの論点」に絞る運用を、新しい規定として入れない**。範囲を絞る正規の経路は既存の3つ(L1 の「実行可能な保証で限定」と規模の確認の保証の所在 `gate-criteria.md:1503`・`:1580-1612`、レビューパッケージの索引部、/human-verify 順5)で足りており、これを維持する
- 論点の生成元を問われるなら、**機械的な導出に限る**(3.10.12 `roles-responsibilities.md:1270`、ADR-0023 決定7)。作成者(人)の申告は「注意を狭める情報」としてパス1 の後に置く(ADR-0023 決定3、`review-guide.md:62-71`)。**AI の抽出は、論点として人へ提示する形でも、範囲を絞る根拠としても採らない**
- **パス1(差分は受入基準の範囲内か)は、論点の外を含む差分全体に必ず掛ける**。絞ってよいのはパス2 の深さと、実装コードの逐読(/human-verify 順5)だけ。これは現行規定の読み方の確認であり、明文化は弁護側も支持する
- リスク層で絞る案(Anthropic・Meta 型)は、本標準では**既に 5.5.4 の委任 + 第8章の事後監査として一本化されている**(`human-ai-boundary.md:422-494`)。Anthropic の自動承認+リスク加重の標本検査は、構造上この経路と同じ形をしている。**2つ目の経路は新設しない**(`gate-criteria.md:1823`、#172)

### 理由

1. **絞る主体が誰かで、信頼性が逆転する**。機械的な導出なら、誤りは「導出の不具合」として検査・改修できる(ADR-0023 決定7・9)。作成者や AI が書いた論点は、誤り(漏れ)を人が検出する手段がない。漏れた箇所は「論点の外」として誰も見ない。外部調査が挙げた立場 A の弱点(「誰が論点を抜き出すか」)は、本標準が ADR-0023 で既に答えを出した問いである
2. **AI による論点の抽出は、3.10.12 の「AI による差分の要約」と同じ働きをする**。要約が「ここを読め」の形を取っても、自動化バイアスの機序(承認シグナルを出す仕組みが人の吟味を減らす。`gate-criteria.md:1644-1646`)は変わらない。Tufano ほか(2024)は、まさに「LLM が示した場所に注意が寄る」を観測した。根拠は対照実験1件で弱いが、**逆向きの実証(AI の抽出で人の高重大度の検出が上がった)は1件もない**。根拠の弱い側に条項を倒すことはできない
3. **パス1 を論点の外へ広げないと、AI 生成で最頻の混入物(仕様外の「ついで実装」。`review-guide.md:21-40`)が構造的に見えなくなる**。「ついで実装」は作成側が論点として挙げない変更そのものである。論点に絞る運用は、検出したい欠陥の類型を定義上除外する
4. **リスク層別は採っているが、根拠の置き場が違う**。5.5.4 は委任の根拠を「AI が代わりに読んだこと」に置かず、「壊れたことを検出でき、取り消せること」に置く(`human-ai-boundary.md:422-494`)。Anthropic の公開資料も、層の判定を「何を自動化するかを意図して決める」とし、AI の通過そのものを承認の根拠にしてはいない(外部調査 §1.2)。Meta RADAR も除外条件(SOX・OSS・追加レビューを要するコード)を先に置く。**外部の実例は、本標準の 5.5.4 の形と矛盾しない**。差は、本標準が R3・CL0 に限り7条件を課す点で、これを緩める根拠(独立した測定)は外部にない(RADAR は選択バイアスと交絡する観察研究)
5. #172 の却下理由「同じ結果を導く手続を2つ持つと、条件の緩いほうだけが使われる」は、#422 の「論点で絞る」にもそのまま当たる。論点で絞った G-6 は、5.5.4 の7条件を満たさない R1・R2 の変更にも使える「事実上の事後化」になる

### 反論されうる点

- 「現行の3経路は重く、実務では誰も L1 を名乗れない。だから人は形だけ承認している」。これは認める。L1 の「実行可能な保証」の中身が機械で確かめられない(`gate-criteria.md:1607`)のは欠陥である。ただし処方は L1 を具体化することであり、AI の抽出を足すことではない(R-4 で扱う)
- 「Google は人のレビューで設計を最初に見る。論点優先は業界の作法だ」。Google の優先順は**読む順序と濃淡**であり、範囲の除外ではない(人が書いたコードは "every line"。外部調査 §2.1)。しかも「一部しか見ていないならどこを見たかを書く」は、範囲の記録を求める作法で、R-4 で一部を受け入れる
- 「人の申告(作成者が自信のない判断を書く)まで禁じるのは過剰」。禁じてはいない。注意喚起部と同じく**パス1 の後**に読む情報として扱う、と言っているだけである。ただしこの扱いが PR テンプレートに書かれていないのは欠陥で、R-4 で認める
- 「Anthropic の SDLC は低リスク層を自動承認している。本標準の 5.5.4 は狭すぎる」。狭いのは意図である。広げる根拠は外部の自社報告だけで、人の注意深さも測っていない。広げるなら EV-0059 型の差し替え条件(条件を欠いても検出率に差が無いこと)の観測が先に要る

## R-2 長期的な決定の切り出し

### 結論

- **欠陥と認める**。PR に埋もれた設計上の選択を G-3 へ引き上げる手段は、PR テンプレートの折りたたみの自己チェック(`template/.github/PULL_REQUEST_TEMPLATE.md:104-115`)しか無い。これは作成側の申告であり、2.6 が可逆性について退けた「判定の前に起案者の申告で済む」形(`lifecycle.md:171-172`、ADR-0071)と同じ弱さを持つ。弁護できない
- 処方は、**新しい承認の経路を作らず、既存の G-3(技術判断者)へ乗せる検出を足す**ことに限る。Kubernetes の API レビューの形(パス・型から機械的に検出し、専任の承認者へ回す)は、本標準では「検出 → 判断記録 → G-3」にそのまま対応する。G-6 の中に「長期的な決定の欄」を作って独立レビュアに判定させる形は採らない(G-3 と G-6 の判定者と基準が二重になる)
- 検出の規則は、既存の**構成に置くパスと変更種別の規則**(3.8.1 のリスク区分の下限の規則、コア指定のパス。`assurance-case.md:648`)と同じ置き場・同じ承認(AI維持管理者)に置く。新しい台帳を作らない。依存の追加は G-5 基準8 の dependency-diff が既に機械で出しているので、それを入力にする
- 検出が当たった変更に課すのは、**判断記録の識別(番号と版)が PR から引けること**の有無の検査まで。中身の妥当性は G-3 の判定者が見る(5.7.4 要求事項1。記述の質を機械で判定しない)
- 要求の強さは **2.6 のステージ表に従う**(S0 は G-3 の判定の対象とした選択、S1 はコア機能、S2 は全件。`lifecycle.md:174-183`)。検出を理由にステージ表より重い要求を課さない。S0 で検出が当たり判断記録が無い場合は、差し戻しでなく注意の喚起に留める
- 検出に当たらなかったことを「長期的な決定を含まない」と読ませない。2.6 の一覧は例示で網羅ではない(ADR-0041)。検出規則も同じく網羅を主張しない一文を持つ(ADR-0023 決定6 と同型)

### 理由

1. 長期的な決定は、取り返しのつかなさ(可逆性)で重みが決まる。2.6 と G-3 はその重みを判定する場を既に持っている。欠けているのは**場へ連れてくる入口**だけで、場そのものではない。場を二つにすると、#172 の「条件の緩いほうだけが使われる」が G-3 にも起きる
2. AI に「この PR は長期的な決定を含むか」を判定させる案は採らない。それは AI の推定による判定であり(H.4)、通過(「含まない」)が人の判定の省略(G-3 に回さない)に直結する。条件4 の否定になる。機械の規則(パス・型・依存の差分)なら、誤りは規則の不具合として改修できる
3. 外部の実例(Kubernetes、CODEOWNERS+ADR)は、いずれも**パスで切り出し、人が承認する**形であり、AI の判定で切り出す実例は外部調査に無い。この点で外部の実務と本標準の原則は一致している
4. ステージ表に従わせるのは、検出を足すことで S0 の軽さ(学習を優先)を壊さないためである。ステージ表を変えるなら別の論点で、#422 の範囲ではない

### 反論されうる点

- 「パスで切り出せない長期的な決定(暗黙の契約、依存の意味の変化)が漏れる」。漏れる。外部調査の立場 C の弱点そのもの。だから自己チェックを**廃止せず併置**し、検出の規則を網羅と読ませない。漏れの量は R-4 の計測(論点の外・検出の外で見つかった欠陥)で測り、規則へ反映する(IMPL-0168 の経路)
- 「検出の規則を書くのは AI維持管理者の負荷になる」。負荷は採否の理由にしない。規則が無い構成では「確かめられない」と表示する、既存の `coreReviewerCount` と同じ扱い(`assurance-case.md:648`)にすればよい
- 「G-3 の技術判断者が律速になる」。Kubernetes でも律速は起きている。帯域は判定を省く理由にならない(`gate-criteria.md:1815-1817`)。手段は第4章の順(流入を絞る → 労力を下げる → 人数を増やす)による

## R-3 AI レビューの位置づけ

### 結論

- **「論点の外を AI レビューで補う」を、検出の層(H.4)の外に数える余地は無い**。H.4 条件4「通過を理由に人の確認を減らさない」(`assurance-case.md:303-368`、ADR-0056 決定4)、第4章の緩和根拠の表で「AI による差分要約・自動レビューコメント」を認めない判断(`gate-criteria.md:1641-1646`)、3.10.12、`gate-criteria.md:1829-1831`(AI の事前審査を合否条件にしない)を、すべて維持する
- 本標準の語として「AI レビューで補う」を使わない。AI レビューは**人の確認と並んで走る検出の層**であり、人の確認の欠けを埋めるものではない。人の範囲の外にある部分は、AI が読んだかどうかに関わらず「人が確認していない範囲」として扱う
- **AI レビューを承認とみなさない**ことを再確認する(G-6 で AI と bot の承認は数えない `gate-criteria.md:913`、構成の `canApprove: false`、附属書C `review-guide.md:127-152`)。外部の既定(Anthropic の Code Review は承認も阻止もしない、GitHub Copilot は既定で必須承認に数えない)とも一致する
- **AI レビューの指示を PR 自身の変更から読まない**ことは、H.4 条件3(指示の書き換えの防止。`assurance-case.md:332`)で既に要求事項である。本文に新しい規定は要らない。ただし**実行層は未達である**(IMPL-0333 undelivered。同じ PR で指示を変えた場合に、基底の側の指示でレビューさせる仕組みが無い)。これは弁護できない欠陥で、#422 の結論とは独立に降ろすべきである。Anthropic の `REVIEW.md` は基底ブランチから読む設計で、条件3 の妥当性を外部が裏付けた。GitHub Copilot のカスタム指示は head ブランチから読むため、そのまま使う構成は条件3 を満たさない。この点は**準拠テンプレートの ai-review.yml と手引きに注記として降ろす**べきで、これは弁護側も支持する(IMPL-0333 の系)
- AI の指摘の採否は人が決め、全部直すことを求めない。「指摘なし」を安全と読まない。いずれも H.4 条件5(指摘の内容と採否)と ADR-0075 の範囲で、既に書かれている

### 理由

1. 条件4 は、AI の検出率が測られていないから置いた条件ではない。**検出率が測れても**、通過を人の確認の縮小に結び付けると、偽陰性が「確認済み」の記録として残り、人の層の検出の機会も消える(`gate-criteria.md:1829-1831` の論理)。外部の測定(F1 約 50%、ベンダ関与のみ)は、この危険が現実の大きさであることを示す。半分を見逃す層を理由に人の範囲を縮めれば、縮めた範囲の欠陥の半分は誰にも見つからない
2. 条件4 を外す正規の手続は EV-0059 の差し替え条件として既に開かれている(条件を欠いても検出率に差が無いことの観測)。#422 はその観測を持っていない。手続の外で条件を外すのは、ADR の決定を新 ADR なしに書き換えるのと同じである
3. 人のレビューの価値の多くは保守性と理解の共有にある(Mäntylä & Lassenius 75%、Bacchelli & Bird)。AI レビューの既定の観点は正しさで、重なりが小さい。**AI が正しさを見たことは、人が保守性と理解の共有を省く理由にならない**。分担を言うなら、人が残すべきものはむしろ「論点」ではなくパス3(挙動要約)である
4. Tufano ほかの結果と MetaMateCR の UI 変更(AI の修正案をレビュアに見せず作者にだけ見せた)は、AI の出力を人の前に置く**位置**が注意を変えることを示す。ADR-0023 決定4(AI の指摘一覧をパッケージに含めない)と附属書C の「パス2 で別の成果物として提示」は、この外部の知見と一致する

### 反論されうる点

- 「AI レビューは既に人より多くのバグを見つけている(Anthropic の自社報告)。それでも人の範囲を縮めないのは非合理」。自社報告で、独立の測定が無い。しかも Anthropic 自身が "A review with no findings doesn't mean your code is error-free" と書く。縮めないことは非合理ではなく、未測定の層に重みを置かないという一貫した扱いである。測れば EV-0059 の経路で見直せる
- 「条件4 があるせいで AI レビューを入れても人の負荷が下がらず、誰も入れない」。負荷を下げるのは AI レビューの役割ではない。帯域の手段は第4章の順に定めてある。AI レビューの価値は、人が見落とす欠陥を別の層で拾う点にある
- 「GitHub Copilot の head ブランチ読みを注記するのは特定製品への言及で、規格に書くべきでない」。本文には書かない。本文は条件3 の一般形のままにし、製品ごとの注意は準拠テンプレートの手引き(実行層)に置く

## R-4 記録・計測・テンプレート

### 結論

- **PR テンプレートの「レビュー観点の指定(任意)」の注記は欠陥と認め、改める**。現行の注記「省略した場合は差分全体が対象です」(`template/.github/PULL_REQUEST_TEMPLATE.md:98-100`)は、裏返すと「指定した場合は指定箇所だけが対象」と読め、ADR-0023 決定2 の定義で**結論**に当たる。本文側の注記(`pr-workflow.md:92-95`「とくに見てほしい箇所・自信のない判断」)ともずれている。改める中身は次の4点で、いずれも既存の規定の写しであり、新しい要求ではない
  - 指定の有無にかかわらず、確認の範囲は差分全体である(パス1 は全体に掛かる)
  - 書き手は人。AI に生成させない(`pr-workflow.md:116`・`:124`)
  - 注意を狭める情報であり、レビュアはパス1 の後に読む(3.5.3、ADR-0023 決定3)
  - 「確認不要」「影響なし」の類を書かない(ADR-0023 決定2)
- **「レビュー観点の指定」を必須にしない**。必須にすると、全 PR で作成側が注意を狭める情報を書くことになり、入力の分離の対象を常設化する。欄の中身は機械で判定できない(5.7.4 要求事項1)ので、必須化は空欄でない文字列を書かせる効果しか持たない。check-pr にこの欄を読ませない現状を維持する
- **G-6 の判定記録に、承認ごとの「確認した範囲 / 確認していない範囲」の様式を課さない**。#271 の却下(検出能力を示さない書類が増える。ADR-0056 却下表)を維持する。範囲の限定は既に作成側が「保証の所在」(`pr-workflow.md:88-90`)で記録しており、R-1 の結論どおりパス1 は全体に掛かるので、承認者が別に書くべき「見ていない範囲」は原則として生じない
  - ただし、**承認者が保証の所在で示された範囲を超えて読まなかった部分がある場合**(例: 生成物を読まなかった)に限り、その旨を承認コメントに書かせることは、#271 の却下と両立する例外の記載として支持する。毎回の署名様式ではなく、例外の記載である。5.7.2 の「確認していない事項」(G-8・SG・例外承認)と同じ考え方
- **論点の外で見つかった欠陥の計測は、新しい量を作らず、既存の 5.6.2 欠陥注入と欠陥の台帳に寄せる**。具体的には (a) 注入箇所の一部を、注意喚起部・レビュー観点の指定・AI の指摘が**触れていない箇所**に置く、(b) 欠陥の台帳とポストモーテムに「提示された箇所の内か外か」の欄を置く。これは ADR-0023 決定10(効果を検出率で検証し、下がれば撤去)の測定を具体化するもので、支持する。個人単位の検出率は算出しない(決定10)
- 準拠テンプレートへの降ろし方は、**新しい規定より先に、未達の IMPL を降ろす**。IMPL-0220(/gate に「要約だけで判定しない」。#359、review=2026-11)、IMPL-0253(確認側へ渡した入力の記録)、IMPL-0155(指摘の内容)、IMPL-0168(見逃した類型の反映経路)、IMPL-0333(指示を基底から読む)。#422 の問題意識(形だけの承認)に直接効くのはこれらである
- **`/review` スキルを新設しない**。レビュー側の入口は /human-verify と /gate G-6 で足り、入口を2つにすると手順が分岐する。/human-verify は「結論・評価・要約を生成しない」設計であり、論点抽出を担わせる改修も採らない

### 理由

1. 欄の注記の欠陥は、**現行の規定に照らして**誤っている(本文は全体を対象とし、テンプレートは指定箇所への限定を示唆する)。直すことは規定の変更ではなく、実行層を本文へ合わせることである。弁護の対象にならない
2. 必須化と署名様式は、形骸化への処方として逆向きに働く。形骸化の機序は「見ずに承認しても記録上は区別が付かない」ことで、書く欄を増やしても、見ずに書けるなら区別は付かない(#271 の論理)。区別を付けるのは、承認者の挙動要約(G-6 基準2)と、欠陥注入による検出の測定(5.6.2)である
3. 計測を足すべき理由は、R-1 で弁護側が「AI の抽出は人の注意を狭める」と主張した根拠が対照実験1件(E1 相当)にとどまるからである。弁護側の主張も測定で反証可能にしておく必要がある。測定の置き場を既存の 5.6.2 にするのは、検出率の分母を一つに保つため(手段ごとの効果は review-burden-measurement で分離する)
4. 未達の IMPL を先に降ろすべき理由は、降りていない規定の上に新しい規定を重ねると、どの規定が効いたのかを測れなくなるからである

### 反論されうる点

- 「例外の記載を認めるのは、#271 の却下を一部覆している」。覆していない。#271 が却下したのは承認ごとの**常設の**署名様式である。例外の記載は、範囲を限定したときだけ生じ、限定の事実が記録に残らない穴を塞ぐ。ただし、この区別が実務で崩れて常設化しないよう、様式の欄にはしない(承認コメントへの記載)
- 「欠陥注入を論点の外に置くと、注入の設計が重くなる」。重さは採否の理由にしない。置かないと、絞り込みの漏れを測る手段が本標準に一つも無い
- 「必須にしない欄は誰も書かず、作成者の自信のない判断が伝わらない」。伝える手段はある(PR 本文の説明、パス1 の後に読む)。必須化の効果(空でない文字列)と副作用(常設の注意の固定)を比べると、副作用が大きい。書かれた割合を見て、伝わっていないことが分かれば別に扱う

## R-5 記録

### 結論

- **新しい ADR を起こす**。#422 で「定めないと決めたこと」が多く、却下は成果として残す必要がある(コアポリシー)。既存の ADR(ADR-0023・ADR-0056・ADR-0059)は書き換えず、新 ADR から引く。**置き換えではなく、既存の決定の再確認と補足**として書く
- 新 ADR に書く決定(弁護側の案)
  1. G-6 の範囲を PR ごとの論点に絞る経路を設けない。範囲を絞る経路は L1・保証の所在・レビューパッケージ索引部・/human-verify 順5 に限る。パス1 は差分全体に掛かる
  2. 論点・重点箇所の生成元は機械的な導出に限る(3.10.12・ADR-0023 決定7 の再確認)。作成者の指定は注意を狭める情報で、パス1 の後に読む
  3. AI レビューは検出の層であり、人の確認を「補う」ものとして数えない。H.4 条件4 を維持する。条件4 を外す経路は EV-0059 の差し替え条件だけ
  4. 長期的な決定は、機械の規則(パス・型・依存の差分)で検出し、既存の G-3 へ乗せる。新しい承認の経路は作らない。要求の強さは 2.6 のステージ表に従う。検出は網羅を主張しない
  5. PR テンプレートの「レビュー観点の指定」の注記を本文に合わせる(R-4 の4点)。必須にしない
  6. 論点の外の検出を、5.6.2 の注入箇所と欠陥の台帳の欄で測る
- 新 ADR の却下表に明記する案
  - AI による論点の抽出を人への提示または範囲の根拠にする案(3.10.12、ADR-0023 決定7・8、H.4 条件4)
  - AI の検出率を前提に人の範囲を配分する案(外部調査 S8。独立の測定が無い。F1 約 50% はベンダ関与)
  - リスク層別の自動承認を、5.5.4 と別の経路として新設する案(#172 と同じ理由。Anthropic・Meta の運用は 5.5.4 の形と矛盾しないことを併記)
  - G-6 に承認ごとの確認範囲の署名様式を課す案(#271 の維持)
  - 「レビュー観点の指定」を必須にする案
  - G-6 の中に長期的な決定の判定欄を置き、独立レビュアに判定させる案(G-3 との二重化)
  - AI に長期的な決定の有無を判定させ、G-3 へ回すかを決めさせる案(H.4 の推定による判定)
  - `/review` スキルの新設
- 提起の前提について、**「Anthropic で行われている」は一次資料で半分だけ確かめられ、「論点で絞る」は確認できなかった**ことを、背景の節に事実として書く。採否は外部の運用の有無ではなく、信頼性の判断軸で決めたことを書く
- 根拠水準のマーク(ADR-0026)を付ける箇所: 決定2・3 のうち、AI の抽出が人の注意を狭めるという判断(Tufano ほか 2024 の1件。E1 相当)。差し替え条件は「AI の抽出した論点を先に見せた場合と見せない場合の、論点の外への注入欠陥の検出率の差。見せた場合が下回らないなら、提示を注意喚起部(パス1 の後)として認める向きで見直す」。決定6 の測定がこの差し替え条件の観測を供給する

### 理由

1. #162・#172・#271 で却下した案と、#422 の処方は同じ形を多く含む。却下を ADR に残さないと、同じ提起が繰り返されるたびに会議体を開き直すことになり、そのたびに条件の緩い側へ寄る危険がある
2. ADR-0023 等を書き換えないのは、採用済み ADR の本文を書き換えない運用(CLAUDE.md)による。新 ADR は、既存の決定を**再確認した**ことと、新しく足した入口(長期的な決定の検出)と測定を記録する
3. 外部の前提の確認状態を書くのは、採用判断者が「Anthropic がやっているのに本標準は採らない」と誤読しないためである。実際には、確認できた Anthropic の運用(AI は承認しない、層で分け人の承認を残す、指示を基底から読む)は本標準の既存の規定と一致している

### 反論されうる点

- 「再確認だけの ADR は不要で、Issue のコメントで足りる」。#162・#172 は Issue のコメントでしか却下を残さず、#422 で同じ論点が再来した。Issue のコメントは採用判断者が読む記録ではない。ADR に残すことの信頼性上の価値は大きい
- 「弁護側の案は、所有者の動機(形骸化)に正面から答えていない」。答えの置き場が違うだけである。形骸化への処方は既に 5.6(判断の深さ)、5.6.2 欠陥注入、5.7.5 提示の周期的な変更、G-6 基準2 の挙動要約にあり、#422 で効くのは**それらの未達の IMPL を降ろすこと**である(R-4)。新 ADR の背景に、この対応関係を書くべきである
- 「EV マークの差し替え条件が、弁護側の結論を覆す余地を作っている」。作るべきである。覆す余地の無い却下は、根拠水準の開示(ADR-0026)と両立しない
