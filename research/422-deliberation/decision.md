# 議長の裁定(#422 人の承認とマージを、PR の本質的なレビューの論点と長期的な決定に絞り、残りを AI レビューで補う運用)

入力: `council-00-agenda.md`、`survey-422-1-internal.md`、`survey-422-2-external.md`、`council-01-drafter.md`〜`council-05-defender.md`。新しい ADR は ADR-0101。

## 0. 前提として確かめた事実

- 所有者の前提「Anthropic で行われている」は、一次資料で半分だけ確かめられた(外部調査 §1)。確かめられたのは、ほぼ全 PR に AI のレビューを掛けること、AI のレビューは承認も阻止もしないこと、コードベースをリスクで層別し、低リスク層を自動承認として人がリスク加重の標本を見ること。確かめられなかったのは「人のレビューを PR ごとの本質的な論点と長期的な決定へ絞る」こと。絞る軸は論点ではなくリスクの層だった。この事実は ADR の背景に書くが、採否の理由にしない(規格・弁護)
- 本標準は、深さの配分を既に認めている(H.5「承認は全行を読んだことを意味しない」、L1、規模の確認の保証の所在、/human-verify の順5)。どれも絞る根拠を機械の導出か実行可能な保証に置く。範囲の上限を作成側や AI が決める形は、ADR-0023 決定2・3・7・8、3.5.3、3.10.12、H.4 条件4 と衝突する
- 準拠テンプレートの PR 様式の注記「省略した場合は差分全体が対象です」は、裏返すと「指定した場合は指定箇所だけが対象」と読める(品質監査・弁護)。本文側の注記(pr-workflow.md)ともずれている。R-1 の結論にかかわらず塞ぐ
- 長期的な決定を PR から G-3 へ引き上げる手段は、PR 様式の折りたたみの自己チェックしか無い(5 委員一致で欠陥と認める)

## R-1 人の確認の範囲を絞るか、何で絞るか

**裁定**: G-6 の承認の範囲を PR ごとの論点に絞る運用は採らない(5 委員一致)。代わりに、G-6 に節「確認の範囲と深さ」を置き、絞ってよいもの(深さ)と絞ってはならないもの(仕様との突合の範囲)を分けて定める(起案・規格・現場・品質監査。弁護は「書かなくても足りる」寄りだったが、注記の欠陥を認めており、区別の不在が提起の原因である点に反対しなかった)。

1. パス1(差分が受入基準の範囲内か)は、差分の全体に掛ける。作成側の指定・AI の指摘・注意喚起部で対象から外さない
2. 逐行に読む箇所を限ってよいのは、根拠が機械の導出(影響範囲、区分の下限の規則、G-5 の出力、既存テストの変更の一覧)か実行可能な保証(L1 の根拠)の場合に限る
3. 作成側の「レビュー観点の指定」と AI のレビューの指摘は、注意を狭める情報として扱い、確認の範囲の上限にしない。パス1 を終えてから読むことを**推奨**する。要求事項にしない(品質監査: 読んだ時点を記録で確かめる手段が無い。EV-0176 で人への読む順序を推奨に下げた経緯と同じ)
4. AI の、確かめた範囲・確かめていない範囲の申告を、人が読む範囲を狭める根拠にしない(H.4 を引く)
5. リスク層別の自動承認(Anthropic・Meta の確かめられた運用)は、本標準では第5章 5.5.4 の7条件と担保水準 L2 が受ける。人の事前の承認を経ずに取り込む2つ目の経路は新設しない(#172 の棄却と同じ理由、5 委員一致)。この対応づけを本文に書く(起案: 書かないと利用者が「本標準は層別を認めない」と読んで独自の経路を作る)
6. 「論点」を本標準の用語にしない(規格)

**採らない案**: 作成側に PR ごとの「人が確かめるべき論点」を必須で書かせる。AI に論点を抽出させて提示する(#162 の3行要約と同形、Tufano のアンカリング)。論点の外を事後の抜き取りに回す(#172 と同形)。5.5.4 と別のリスク層別の自動承認を新設する。何も書かない。

## R-2 長期的な決定の切り出し

**裁定**: 採る(5 委員一致)。第2章 2.6 に「判断記録の要否の規則」を置く。

1. 規則は、区分の下限の規則(3.8.1)と同じくプロセス構成に置き、変更の対象のパスと変更種別から「判断記録を要する変更」を導く。区分の下限とは別の値として書く(規格・起案・弁護)。新しい台帳は作らない
2. 規則は基底ブランチの構成から読む。規則を変える変更の区分の下限は R2 とし、規則と製品のコードを同じ変更で変えない(3.8.1 の要求事項6 と同じ。現場・品質監査)
3. 規則に当たる変更は、判断記録の識別(トレーラ `ADR`)を要する。識別が指す判断記録が実在しない変更も、識別が無いものとして扱う
4. **規則に当たった変更を、申告で外す経路を作らない**(品質監査)。起案・規格の「人の記名による『設計上の選択を含まない』の記載」は採らない。理由: 長期的な決定は取り消しにくく、見逃しの費用は取り消しの困難さそのもの、偽陽性の費用は判断記録 1 件である。外す向きの申告は定型文に最も早く収束する(起案も弱点として認めた)。2.6 が可逆性で判断記録の要否を分けなかった理由(起案者の申告で済む)と同じ形になる。偽陽性は、規則を狭める変更(統制を緩める変更として扱う)で直すか、判断記録に「選択の余地が無かった」と書いて G-3 に掛ける
5. 要求の強さは 2.6 のステージ表に従う(弁護)。S0 では規則に当たって識別が無い変更を失敗させず注意として示し、S1 以降は失敗させる。ステージの分からない構成は失敗させる側に倒す
6. 判断記録の識別を持つ変更は、取り込む前にその判断記録の G-3 の判定記録を要する。G-3 の判定記録への到達は機械では確かめない(G-3 の判定者と G-6 の判定者が確かめる)
7. 依存の追加・更新は、G-5 基準8 と G-6 基準5 に既に経路がある。規則に自動で含めない(品質監査)。依存のマニフェストを規則に書くことは妨げない
8. 規則の網羅は主張しない(ADR-0041)。規則が無い構成、または規則のパスが追跡中のファイルに 1 件も当たらない構成では、未宣言として「長期的な決定を検出できない」と示す(品質監査)。規則の外の選択は、自己チェックと G-6 のパス1、レビュアの差し戻しに残る。自己チェックは廃止しない(弁護)
9. AI の指摘・作成者・レビュアが「長期的な決定に当たる」と**足す**ことは認める。「当たらない」との出力で検出を外さない(現場・品質監査)
10. G-6 基準3(設計意図の記録)を、コア機能に加え、判断記録の要否の規則に当たる変更へ広げる(起案)。G-6 に長期的な決定の妥当性を判定させない(判定は G-3)
11. 新しい承認の席(専任の API 承認者)は作らない(5 委員一致)

**採らない案**: PR に「長期的な決定」の欄を置き作成者が書く形だけにする。AI に長期的な決定を判定させ、その結果で経路を分ける。専任の承認者の席。人の記名による否定の記載で外す。依存の差分を規則へ自動で含める(既存の経路と重なる)。G-6 のレビュアに長期的な決定を見つけさせる。

## R-3 AI レビューの位置づけ

**裁定**: 論点の外を AI のレビューで「補う」ことを、検出の層(H.4)の外に数える余地は無い(5 委員一致)。

- H.4 条件4(通過を理由に人の確認を減らさない)を維持する。「補う」は規定の語にしない。AI の層の検出率で条件4 を外さない
- AI のレビューを承認とみなさないことは、既存の所在(H.4、3.5.4)を引いて確かめるだけにし、条文を書き直さない(規格)
- AI のレビューの指示を PR 自身の変更から読まないことは、H.4 条件3 で既に要求事項である。実行層の IMPL-0333 は降りていない(#369)。これを運用の前提の欠落として ADR に書く。準拠テンプレートの AI レビューの手引きに、head 側の指示を読む道具(GitHub Copilot のカスタム指示)をそのまま使う構成は条件3 を満たさない旨の注記を置く(弁護)
- AI の指摘を読む時点は、R-1 の 3 のとおり推奨に留める

**採らない案**: AI の検出率を前提に人の確認を配分する。AI のレビューの通過を G-6 の範囲の縮小に使う。AI の層を数えるのをやめる観測なしに条件4 を外す。

## R-4 記録・計測・テンプレート

**裁定**:

- G-6 の判定記録に「確認した範囲 / 確認していない範囲」の欄を課さない(5 委員一致。#271 の却下を維持。自己申告で検証できず、変更ごとに発生するため最も早く定型化する。パス1 は全体に掛かるので、承認者が別に書く「見ていない範囲」は原則として生じない)
- 計測は採る(5 委員一致)。第5章 5.6.2 に、レビューに注意を狭める情報(レビュー観点の指定・注意喚起部・AI の指摘)を示す工程では、注入の一部をその外に置き、内と外の検出率を分けて工程単位で記録する旨を置く。運用中の継続の注入の手段は準拠テンプレートに無い(#356)ので、降りていない規定として表示する
- 欠陥の台帳に欄「レビューで示した箇所(内 / 外 / 提示なし)」を置く。G-6 を経た変更が原因の欠陥について、その変更の PR が示した注意を狭める情報が欠陥の箇所を含んでいたかを書く。空欄は「不明」とする
- 「レビュー観点の指定」は任意のまま残す(5 委員一致)。本文と準拠テンプレートの注記を改める。書き手は作成側の人(現行の pr-workflow.md の「自動で埋める欄と、人が書く欄」の表のとおり。起案・規格)、指定の有無にかかわらず差分の全体が対象、結論(「ここ以外は見なくてよい」と読める記述)を含めない、パス1 の後に読む。書き手が人であることは機械で確かめない。書き手が誰であっても、この欄は作成側の主張であり、注意を狭める情報として扱う
- `/review` スキルは新設しない(5 委員一致)。`/human-verify` と `/gate G-6` に、パス1 を差分の全体に掛けること、「限定」の根拠に作成者の指定と AI の指摘を数えないことを書く
- 内部監査で、レビュー観点の指定に範囲を除外する記述が無いかを抜き取りで見る(品質監査。機械では判定しない、5.7.4)

**採らない案**: G-6 に確認した範囲の欄。レビュー観点の指定を必須にする。`/review` の新設。

## R-5 記録

**裁定**: ADR-0101 を 1 本起こす(5 委員一致)。既存の ADR を置き換えない。ADR-0023・0041・0056・0059・0067・0071 を引いて維持する。#162・#172・#271 の却下を維持する。所有者の前提の確認結果を背景に事実として書く。課さないと決めたことを恒久の決定として書く。根拠水準のマーク: R-1 の範囲と深さの区別(E1)、R-2 の規則(E2、Kubernetes の単一事例)。既存の未達(IMPL-0220・0253・0155・0168・0333)は本 ADR で解消したことにしない(品質監査)。

## 残るリスク(送りではない)

- 規則に載らない長期的な決定(暗黙の契約、依存の意味の変化)は漏れる。自己チェック・パス1・差し戻しに残る。漏れは欠陥の台帳と監査の抜き取りで見つけ、規則へ足す
- パス1 の所要時間を測った資料が無い(附属書C の 10 分は EV-0085 の目安)
- 小規模な組織では注入の件数が足りず、内と外の差を読めない。チーム単位の集計の限界として開示する
- 第4章の流入の統制(タスクの分割基準など)に実装マークが無い箇所がある(現場)。本件の範囲の外で、記録にとどめる
