# #422 会議体 委員意見: 品質監査(qa-audit)

- 日付: 2026-11-04
- 立場: 監査人。人の承認が何を確かめたかを記録で検証できるか。範囲を絞ることで、論点の外の欠陥が誰の責任にもならない穴ができないか。自動化バイアスで確認が空洞化しないか
- 入力: `council-00-agenda.md`、`survey-422-1-internal.md`(以下「内部」)、`survey-422-2-external.md`(以下「外部」)、本文と ADR(path:line で引く)
- 所有者の提起(#422)は第三者の意見として扱う。前提「Anthropic で行われている」は、外部 §1.5 のとおり「論点で絞る」部分が一次資料で確かめられていない。本意見はこの前提に依らない

## 監査人としての前置き: 「範囲を絞る」で監査が失うもの

監査が確かめられるのは、記録に残ったものと、記録から機械が導けるものだけです。G-6 の承認について現在の記録から言えることは次の範囲です。

- 承認の事実、承認者と名簿の対応、指示者でないこと、挙動要約の形(`gate-criteria.md:907-913` の4条件と付記)
- 挙動要約の実質(附属書H H.3 観点1。`assurance-case.md:256`。監査人の読解による)
- 署名が意味しないこと(全行を読んだこと、欠陥が無いこと。`assurance-case.md:461-473` H.5)

「論点に絞る」を入れると、承認の意味が「受入基準との一致+挙動の説明」(H.5)から「**提示された論点についての**一致+説明」へ変わります。変わった部分(論点の外)を、次のいずれも引き受けません。

| 主体 | 論点の外の欠陥を引き受けない理由 |
| --- | --- |
| 独立レビュア | 「論点の外は範囲外」と言える |
| AI レビュー | 判定に数えない検出の層であり、人の確認を減らす理由にならない(`assurance-case.md:313`、H.4 条件4 `:322`) |
| 作成者・論点を書いた者 | 作成側の主張であり、確認の主体ではない(3.5.3、ADR-0023 決定2) |
| 出荷判定者(G-7) | 内容の十分性を判定しない(`assurance-case.md:471`) |

つまり、**論点の外は構造上だれの署名にも入らない領域**になります。この穴は、保証の開示にも出ません。開示に出ない未達は、本標準の開示の考え方(未達と省略の区別、ADR-0028)に反します。以下の結論はすべて、この穴を作らないか、作るなら開示と測定で見えるようにするかの観点で出しています。

## R-1 人の確認の範囲を絞るか、何で絞るか

### 結論

1. **G-6 の承認の範囲を、PR ごとの論点で縮める運用は採らない**。論点(重点箇所)は「注意を向ける材料」として提示してよいが、承認の範囲を画定しない。承認の意味は H.5 のまま変えない
2. **パス1(差分が受入基準の範囲内か、仕様外の混入が無いか)は、論点の有無・内容にかかわらず差分全体に掛ける**ことを規範(要求事項)として明記する。現在は附属書C(参考、`review-guide.md:47-50`)の手引きにとどまる。G-6 基準1「受入基準の項目ごとに挙動を確認」(`gate-criteria.md:880`)の確認方法へ「差分の全体が受入基準の範囲に収まることを含む」を足す形を推す
3. 人の逐読の範囲を狭めてよい根拠は、既存の**担保水準 L1(影響範囲の機械的な提示+実行可能な保証)と規模の確認の「保証の所在」**(`gate-criteria.md:1503`、`:1587`)に限る。論点の生成元が作成者でも AI でも、それ自体は狭める根拠にならない
4. リスク層別の自動承認(Anthropic の SDLC、Meta RADAR。外部 §1.2・§2.3)は、既存の L2(`gate-criteria.md:1504`)と 5.5.4 の委任(`human-ai-boundary.md:422-494`)の外に**新しい経路として設けない**(`gate-criteria.md:1821`「別の経路を新設しない」、#172 の棄却)
5. 準拠テンプレートの PR 様式の注記「省略した場合は差分全体が対象です」(`template/.github/PULL_REQUEST_TEMPLATE.md:100`)は、**指定した場合は指定箇所だけが対象と読める**。「指定の有無にかかわらず差分全体が対象」へ直す。これは監査上の穴であり、R-1 の結論にかかわらず塞ぐ

### 理由

- 前置きのとおり、論点で範囲を縮めると、論点の外が署名の外に落ち、しかも開示に出ない。絞ることで生じる未確認の範囲を、誰も記名せず、誰も数えない
- 論点の外に落ちやすいのは、まさにパス1 の対象(仕様外の「ついで実装」、AI 生成で最頻の混入物。`review-guide.md:49`)である。論点は「この PR が何をするか」から書かれるので、**その PR がするはずでないこと**は原理的に論点に入らない。パス1 を論点の外に掛けないと、最頻の混入物の検出を構造的に捨てる
- 生成元が AI の場合: Tufano ほか(外部 §3.2、29 名の対照実験)で、人は LLM が示した場所へ注意を寄せ、高重大度の指摘は増えなかった。「AI が論点を抜き出し、人はそこだけ見る」は、この失敗様式を手続として固定する。3.10.12(`roles-responsibilities.md:1272`)・ADR-0023 決定2・7・8 とも衝突する
- 生成元が作成者の場合: 作成側の主張であり、注意を狭める情報である(3.5.3 `roles-responsibilities.md:585-596`、ADR-0023 決定3)。作成者は自分が気づいていない欠陥を論点に書けない。欠陥は「作成者が自信を持った箇所」にも入る
- 所有者の動機は帯域ではなく形骸化である(議題)。しかし、範囲を絞ることが形骸化を減らすという測定は無い。5.6.1(`human-ai-boundary.md:602-628`)は、人が見る対象で欠陥が稀になるほど形骸化しやすいと述べる。論点が当たっていれば人の見る範囲の欠陥密度は上がるが、外れていれば下がる。どちらに働くかを測る手段が先に要る(R-4)
- 一方で、**人に全行の逐読を要求する案も採らない**(H.5 を変えない)。G-6 が全行の読解を意味しないことは既に確定しており、そのうえで「受入基準との一致」と「差分が受入基準の範囲内」を差分全体に対して問う、というのが監査で崩れにくい最小の約束である。逐読の深さを変えることと、確かめる問いの適用範囲を変えることを分けて扱う

### 監査で確かめられること

- PR 様式の注記が「差分全体が対象」になっていること(機械: 様式の文言の存在)
- 「レビュー観点の指定」欄に、範囲を除外する記述(「〜以外は見なくてよい」「〜は確認不要」)が書かれていないこと。機械では判定しない(5.7.4)。内部監査の抜き取りで見る。ADR-0023 決定2 の判定規則(自分で確認しなくてよいと読める記述は結論)をそのまま監査の判定規則に使える
- 流出欠陥のうち、仕様外の変更(受入基準に対応しない差分)に由来するものの件数(R-4 の欠陥台帳の欄で数える)
- L1 を名乗る宣言の根拠のパスの実在と見直し日(既存。`gate-criteria.md:1607`)。中身は確かめられない限界も既存のまま開示する

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| A. 論点で G-6 の範囲を縮める(所有者の案) | 論点の外が署名の外に落ち、開示に出ない。パス1 の対象が原理的に論点の外に落ちる |
| B. AI が論点を抽出し、人はそこを見る | 3.10.12、ADR-0023 決定2・7・8、Tufano のアンカリング。#162 の「3行要約の自動提示」の却下と同形 |
| C. リスク層別の自動承認・標本検査を新経路として置く | 5.5.4 と L2 の外に2本目の経路を作ると、条件の緩いほうへ流れる(`gate-criteria.md:1821`、#172)。Meta の効果は選択バイアスと交絡し、人の注意深さは測られていない(外部 §2.3) |
| D. 全行の逐読を G-6 に課す | H.5 の確定を覆す根拠が無い。AI 生成量の下で形骸化の原因になる(外部 §4 D の弱点) |

### 反論されうる点

- 「パス1 を差分全体に課すのは、現状の附属書C の手引きを規範へ上げる新たな負荷だ」→ 負荷の大小は採否の理由にしない。加えて、パス1 は逐読ではなく「差分の各部が受入基準のどれに対応するか」の突合であり、レビューパッケージの索引部(受入基準と差分の対応)が機械で労力を下げる
- 「パス1 を差分全体に掛けたことを記録で確かめられないなら、規範にしても監査できない」→ そのとおりで、直接は確かめられない。確かめられるのは、流出した仕様外の欠陥の件数と、欠陥注入で仕様外の変更を差分の各所に注入したときの検出率である(R-4)。規範と測定を組にして置く
- 「Anthropic は層別している。業界の実態に背を向けている」→ 層別は L2 と 5.5.4 で既に受けている。外部の運用が自動承認の検出能力を測っているかは確かめられていない(外部 §1.2 は標本検査の存在まで)

## R-2 長期的な決定の切り出し

### 結論

1. **採る**。長期的な決定(第2章 2.6「判断記録の範囲」の例示。`lifecycle.md:155-161`)に当たる変更を、PR の差分から**機械的に検出**し、検出した変更には判断記録の識別と、その判断記録の G-3 の判定記録への到達を求める。G-6 の承認では代えない
2. 検出の規則は、組織が構成に宣言するパス・種別(公開インタフェースの定義、永続スキーマ・migration、依存の宣言ファイル、構成単位の境界を表す設定)とし、**基底ブランチの構成から読む**(検査の対象となる PR から規則を書き換えられない。H.4 条件3 と同じ理由)
3. 宣言したパスが追跡中のファイルに1件も当たらない場合は、未宣言として扱う(規模の確認の要求事項7 `gate-criteria.md:1592` と同じ塞ぎ方)。未宣言の構成では「長期的な決定を検出できない」と保証の開示に出す
4. 作成者・レビュア・AI が「これは長期的な決定だ」と**足す**ことは認める。**外す**こと(検出された変更を「判断を含まない」と申告して判断記録を省く)は認めない。検出の偽陽性は、判断記録で「選択の余地が無かった」と書いて G-3 に掛ける。申告で外す経路を作らない(`gate-criteria.md:1611` の「作成側の申告で検査を外す経路を作らない」と同じ)
5. 依存の追加は既に G-5 基準8 と G-6 基準5 の経路がある。重ねて新設しない。検出の規則に依存の宣言ファイルを含めるのは、判断記録への到達を見るためだけとする

### 理由

- 監査上、長期的な決定が PR に埋もれる穴は現存する。検出の手段は PR 様式の折りたたみの自己チェック(`template/.github/PULL_REQUEST_TEMPLATE.md:111`)だけで、作成者の申告に依る。G-6 基準3 はコア機能に限られる(`gate-criteria.md:882`)。自己申告の穴は監査で事後に見つけるしかなく、見つけたときには取り返しにくい
- 長期的な決定は「あとから変えにくい」ので、検出の誤りの非対称が大きい。見逃しのコストは取り消しの困難さそのもので、偽陽性のコストは判断記録1件である。だから**外す方向の申告を塞ぎ、足す方向だけを開ける**
- G-6 の承認者に長期的な決定の妥当性を判定させない理由: G-6 の署名の意味は受入基準との一致と挙動の説明であり(H.5)、設計上の選択の妥当性は G-3(技術判断者)の判定である(`gate-criteria.md:431`)。G-6 に混ぜると、G-6 の署名がどちらを確かめたのかを記録から区別できなくなる
- Kubernetes の API レビュー(外部 §2.5)は、パス・型から機械的に検出し別経路の承認者へ回す長期運用の実例である。規格化された作法は無い(外部 §2.6)ので、根拠の水準は E2 相当と見る

### 監査で確かめられること

- 宣言したパスに触れた PR のうち、判断記録の識別と G-3 の判定記録への到達が無いものの件数(機械で数えられる)
- 宣言の網羅性: 監査の抜き取りで、宣言の外にある長期的な決定(暗黙の契約、宣言されていない公開インタフェース)を含んでいた変更を探し、宣言の不足として是正する。**機械が検出しないことを、決定が無いことと読まない**(附属書H の観点4・6 と同じく、検出の仕組みが働いていたかを見る)
- 「足した」申告の件数と、検出の規則へ取り込んだかどうか(宣言の改善の入力)

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| PR に「長期的な決定」の欄を置き、作成者が書く形だけにする(所有者の案1) | 自己申告の穴をそのまま残す。書かなければ検出されない |
| AI に長期的な決定を抽出させ、検出の根拠にする | AI の推定は判定に数えない(H.4)。AI が挙げなかったことを「長期的な決定が無い」と読む記録が残る。AI の指摘を「足す」入力にすることは妨げない |
| 専任の API レビュアの席を新設する(Kubernetes の形) | 判定者は既に G-3 の技術判断者である。席を増やすと G-3 と並ぶ2本目の判定経路になる |
| 検出された変更を申告で外す | 本文の理由のとおり |

### 反論されうる点

- 「G-3 は設計工程のゲートであり、実装の PR で見つかった決定を G-3 に掛けるのは順序が逆だ」→ 逆になっていること自体が所見である。PR の時点で見つかった判断記録の無い決定は、G-3 を経ずに実装された決定であり、戻る先は第4章「確定した版を変える場合」の経路で足りる。新しい経路は要らない
- 「パスの宣言は組織ごとに貧弱になり、形だけになる」→ 宣言の網羅性は機械で確かめられない。監査の抜き取りで不足を見つける以外に手段が無いことを、限界として開示する
- 「偽陽性が多いと判断記録の形骸化を招く」→ 偽陽性の件数は数えられる。数えて宣言を絞るのは組織の改善の判断であり、申告で外すこととは違う

## R-3 AI レビューの位置づけ

### 結論

1. 「論点の外を AI レビューで補う」を、**H.4 の検出の層の外に数える余地は無い**。AI レビューは検出の層であり、通過しても判定は成立せず、人の確認を減らす理由にならない(`assurance-case.md:313`、条件4 `:322`)。本標準の本文では「補う」の語を、人の確認の範囲の縮小の根拠として使わないと明記する
2. AI レビューを承認とみなさないことを再確認する。AI と bot の名義の承認は数えない(`gate-criteria.md:913` の付記)。AI レビューを必須チェック・合否条件に入れない(`gate-criteria.md:1829`)
3. AI レビューの指示(組織のレビュー指示ファイル)は、**検査の対象となる PR の変更から読まない**。基底ブランチの保護下の正本から読む(H.4 条件3。Anthropic の `REVIEW.md` の設計と一致、GitHub Copilot の既定と逆。外部 §1.1・§2.4)。準拠テンプレートの ai-review.yml の差し込み口の注記に置く
4. 「AI レビューの指摘が無い」ことを、確認済みの記録として残さない(H.4 条件5)。指摘が無い箇所を人が見なくてよい理由にしない。Anthropic の製品文書自身が「指摘が無いことは誤りが無いことを意味しない」と書く(外部 §1.1)
5. 保証の開示では、人が逐読しなかった範囲を AI の層が見たと**主張しない**。AI の層の働きは検出率(値または「未測定」)で示すだけとする(H.4 条件1)
6. 人のレビュアに AI の指摘を見る時点(パス1 の後)を**要求事項として課さない**。附属書C の推奨にとどめる

### 理由

- 結論1: 補うという語は、監査で読むと「論点の外は AI が確かめた」という主張に読める。AI の範囲の自己申告を確認の範囲の根拠にしてはならない(`assurance-case.md:430-434`)。AI の層の検出性能は F1 約 50%、ベンダ関与の測定しかない(外部 §2.7)。検出率を前提に人の範囲を削る設計の根拠は無い。EV-0059 の差し替え条件(`assurance-case.md:362-366`)も、条件4 を外す観測ではなく、AI の層を数えるのをやめる観測と、条件の要否の観測を求めている。条件4 を外すに足る自組織の測定は、まだどこにも無い
- 結論3: 指示を PR から読めると、作成側が検査を緩める経路が開く。Anthropic と GitHub で設計が逆である以上、「業界の既定」に委ねず本標準が定める理由がある
- 結論6: Tufano のアンカリングは、AI の指摘を先に見せる順序の害を示す。しかし、レビュアが PR の画面で AI のコメントを見た時点を、記録で確かめる手段が無い。確かめられない順序を要求事項にすると、守られたかを監査できない規範が1本増える。ADR-0067 決定3 が2人目の順序を課さなかった理由と同じである。代わりに R-4 の欠陥注入で「AI が指摘した箇所の外」の人の層の検出率を測り、アンカリングの害が自組織で出ているかを観測する

### 監査で確かめられること

- ブランチ保護・必須チェック・合否条件に AI の推定が入っていないこと(H.4 条件4。機械で設定を見られる。観点22 `assurance-case.md:273`)
- AI レビューの指示の置き場が PR から書き換えられない保護の下にあること(条件3。設定を見られる)
- G-6 の承認・判定記録・保証の開示に「AI レビュー通過」「AI が確認済み」の語が根拠として現れないこと(条件5。抜き取り)
- 判定記録の根拠が AI の要約ではなく原資料の該当箇所であること(3.10.12。抜き取り。IMPL-0220 が降りるまでは、降りていない規定として台帳に出続ける)

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| AI レビューを論点の外の確認として数える | H.4 条件4 の否定。検出率の測定が無い |
| AI レビューを shadow mode から始めて、信頼を得たら承認に数える(Anthropic の SDLC。外部 §1.2) | 「信頼を得た」の判定基準が公開されていない。承認に数える経路は、AI の推定を判定に数えない根拠2(`assurance-case.md:62-78`)と衝突する |
| AI の指摘を人に見せない構成を要求する | 確かめられない。推奨にとどめ、測定で害を観測する |
| AI の指摘の全件に応答を課す | 当事者が過剰設計の害を警告している(外部 §1.1 Best practices)。採否と理由は条件5 の範囲で残す |

### 反論されうる点

- 「AI レビューが人より多く見つけている現場で、人の範囲を減らせないのは非合理だ」→ その主張は自組織の欠陥注入で、人の層と AI の層の検出率を同一条件で測ってから出せる(5.6.2、EV-0059)。測る前に削ることを、本標準は認めない。測定の結果で条件を外す手続は既に EV-0059 にある
- 「順序を課さないなら、アンカリングの害を放置している」→ 放置ではなく測定に回している。課しても守られたかを確かめられない規範は、監査では「満たしていると主張された」記録しか生まない

## R-4 記録・計測・テンプレート

### 結論

1. **G-6 の承認ごとに「確認した範囲 / 確認していない範囲」を書かせる欄は課さない**。#271 で却下した「承認ごとに何を確かめたかの署名様式」と同じ形であり、却下の理由(検出能力を示さない書類が増える)が今回も当てはまる。G-6 の確認していない範囲は、**H.5 の「意味しないこと」として標準の側で一律に開示済み**である(全行・欠陥の不在)。これを課さないと決めたことを明記する
2. 代わりに、**範囲を絞ったことの害を工程の量として測る**。次の2つを置く
   - (a) **欠陥の台帳・ポストモーテムの欄**: 流出した欠陥が、その変更の PR で提示された重点箇所(「レビュー観点の指定」・レビューパッケージの注意喚起部・AI の指摘)の**内か外か**、および受入基準に対応しない差分(仕様外の変更)に由来するか。工程の単位で集計し、個人の検出率を出さない(5.6.2 の用途の限定 `human-ai-boundary.md:636-642` に従う)
   - (b) **欠陥注入の層別**: 5.6.2 の注入の一部を、提示された重点箇所の**外**と、受入基準に対応しない差分(仕様外の混入)として置く。人の層の検出率を「提示の内 / 外」で分けて出す。差が大きければ、提示がアンカリングとして働いている観測になる(ADR-0023 決定10 の「下がれば撤去」の判定材料にもなる)
3. PR 様式の「レビュー観点の指定」は**任意のまま**とする。必須にしない。ただし欄の扱いを本文(pr-workflow)と準拠テンプレートに書く
   - 書き手は人(作成を指示した者、または確認を求める者)。AI に生成させない(`pr-workflow.md:124`)
   - 注意を狭める情報として扱う。人のレビュアはパス1 の後に読むことを勧める(附属書C の入力の分離と同じ推奨)。確認側の AI へは判断の前に渡さない(3.5.3 要求事項1。これは要求事項)
   - 結論を含めない。「ここ以外は見なくてよい」と読める記述を書かない(ADR-0023 決定2)
   - 指定の有無にかかわらず、差分全体が対象である(R-1 結論5)
4. check-pr(pr-rules)はこの欄の中身を読まない。機械で中身を判定しない(5.7.4)。確認側の AI の入力にこの欄を入れていないことは、H.4 条件2 の確認(AI維持管理者)に含める
5. 準拠テンプレートへの降ろし方: PR 様式の注記の修正、ai-review.yml の差し込み口の注記(入力から PR 本文の主張と「レビュー観点の指定」を除く。指示を基底ブランチから読む)、欠陥台帳の様式への欄の追加、導入前の検証の注入の層別。いずれも実装マークを付け、降りるまでは `state=undelivered` で表示し続ける

### 理由

- 結論1: 承認者が自分で書く「確認していない範囲」は、記録で検証できない。AI の範囲の自己申告を根拠にしない理由(`assurance-case.md:430-434`)は、人の自己申告にもそのまま当てはまる。出力の構造を満たしたまま実際の確認と食い違う。しかも G-6 は変更ごとに発生するので、定型文(「論点の外」「なし」)へ最も早く収束する欄になる。5.7.2(`human-ai-boundary.md:845`)は「なし」を認めないと定めるが、それを機械が検出しないことも開示している(IMPL-0171 の note)。G-8・例外承認のように頻度が低く記名者が少ない判断と、G-6 では欄の劣化の速さが違う
- 一方で、監査人として「確認していない範囲がどこにも見えない」ことは受け入れられない。そこで、**個々の承認の申告ではなく、流出と注入という外部の観測で、絞ったことの害を見えるようにする**。外部の観測は、承認者の申告と独立に取れる
- 結論2(a): 現在の欠陥台帳には「AI 起因」の欄はあるが、「提示の内か外か」の欄が無い(内部 §4.3)。この欄が無いと、論点の抜き出しが外れたことを誰も数えられず、#422 の決めること3(歯止め)が実体を持たない
- 結論2(b): 注入箇所の層別が無いと、欠陥注入は「提示が当たった箇所」の検出率を測っているのか、全体を測っているのかが区別できない。アンカリング(Tufano)が自組織で起きているかを確かめる唯一の手段である
- 結論3: 必須にすると、書き手が定型文で埋める欄が1つ増え、中身は機械で確かめられない。任意のままでも、扱い(書き手・読む時点・結論を含めない)が無いことのほうが穴である

### 監査で確かめられること

- 欠陥台帳の「提示の内 / 外」「仕様外の変更に由来」の欄が埋まっているか(空欄の件数は機械で数えられる)。埋めた内容の正しさは、ポストモーテムの抜き取りで見る
- 欠陥注入の記録に、提示の外と仕様外の混入の注入が含まれ、人の層の検出率が層別に出ているか
- PR 様式の注記が改められ、「レビュー観点の指定」に除外の記述が無いか(抜き取り)
- 確認側の AI の入力の記録(H.4「確認側へ渡した入力の記録」。IMPL-0253、#360 で未達)に、PR 本文の主張と観点の指定が入っていないか。IMPL-0253 が降りるまでは、**この確認は実行層で成立していない**と開示し続ける

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| G-6 に「確認した範囲 / 確認していない範囲」の欄を課す | 結論1 のとおり。#271 の却下と同形。自己申告で検証できず、最も早く定型化する |
| 「レビュー観点の指定」を必須にする | 中身を機械で確かめられず、定型文の欄が増える。必須の欄の有無だけを見る検査は、記入した事実しか示さない |
| 論点の外の欠陥件数を、レビュアごとに集計する | 個人の検出率を出さない(5.6.2 の用途の限定)。評価に接続すると検出しやすい対象へ最適化される |
| 承認までの時間・差分の量で形骸化を判定する | ADR-0059 で検知条件に置かないと決めている |
| `/review` スキルを新設して論点の提示を担わせる | レビュー側の入口は /human-verify と /gate G-6 で足りる。新設すると、結論・要約を生成しない規律(/human-verify)の外に入口ができる。必要が出たら別 Issue で起こす |

### 反論されうる点

- 「欠陥台帳の欄は、流出してからしか分からない。歯止めとして遅い」→ 遅いことは認める。早い観測は欠陥注入(b)が担う。両方を置くのはこのためである
- 「提示の内か外かを、ポストモーテムで後から正しく判定できるのか」→ 提示は PR 本文とレビューパッケージに残っているので、記録から判定できる。判定するのは人であり、判定の一貫性の限界は開示する
- 「G-6 に確認していない範囲を書かせない一方で、5.7.2 は G-8 に書かせる。一貫していない」→ 一貫させる軸は「その記録で何が検証できるか」と「劣化の速さ」である。5.7.2 の欄は事業決裁者が残存リスクを受容する判断の記録で、受容の範囲を画定する役割がある。G-6 の範囲は H.5 で一律に定まっており、変更ごとに画定する必要が無い

## R-5 記録

### 結論

1. **新しい ADR を起こす**(番号は採番時に決める)。ADR-0023・ADR-0056・ADR-0059 は書き換えず、新 ADR から引く。置き換えではなく、既存の決定の適用範囲を PR の論点と長期的な決定へ広げた記録とする
2. 新 ADR の決定に置くもの
   - G-6 の承認の範囲を、PR ごとの論点で縮めない。承認の意味は H.5 のまま
   - パス1(差分が受入基準の範囲内か)を差分全体に掛けることを G-6 の確認方法に含める
   - 長期的な決定を基底ブランチの宣言から機械的に検出し、判断記録と G-3 へ到達させる。申告で外す経路を作らない
   - AI レビューは検出の層であり、人の確認の範囲を縮める根拠に数えない。指示を PR から読まない
   - 「レビュー観点の指定」の書き手・読む時点・結論を含めない扱い
   - 欠陥台帳の「提示の内 / 外」の欄と、欠陥注入の層別
3. 新 ADR の「課さないと決めたこと」に置くもの(却下は成果として明記する)
   - 論点で G-6 の範囲を縮める運用(所有者の案)
   - AI による論点の抽出・要約を、範囲の根拠にすること(#162 の却下と同形であることを書く)
   - リスク層別の自動承認と標本検査を、L2 と 5.5.4 の外の新しい経路として置くこと(#172 の却下と同形)
   - AI レビューの検出率を前提にした人の確認の配分
   - G-6 の承認ごとの「確認した範囲 / 確認していない範囲」の欄(#271 の却下と整合)
   - 「レビュー観点の指定」の必須化
   - 人のレビュアに AI の指摘を見る順序を要求事項として課すこと(ADR-0067 決定3 と同じ理由)
   - AI レビューを shadow mode から承認に昇格させる経路
   - PR の規模の上限の見直し(#295・ADR-0058 の範囲であり、本 ADR では扱わない)
4. 背景に、所有者の前提の確認結果を書く。「Anthropic で行われている」は、「ほぼ全 PR に AI レビュー」「承認は人」「リスク層別と標本検査」までが一次資料で確かめられ、「論点で人のレビューを絞る」は確かめられなかった(外部 §1.5)。**前提が確かめられなかったことは、採否の理由にしない**。採否は信頼性(監査で崩れないか)で決めた旨を書く
5. 根拠水準のマーク(ADR-0026)
   - パス1 を差分全体に掛けることの根拠(仕様外の混入が AI 生成で最頻)の水準を確かめ、実証が足りなければ暫定でマークする
   - 欠陥注入の層別で、提示の内外の検出率の差をアンカリングの観測と読む判断は、Tufano の1件(29 名)に依る。E2 として暫定にマークし、差し替え条件を「自組織の注入で、提示の内外の検出率に差が無いこと」とする
   - 長期的な決定の機械検出の有効性は、Kubernetes の1事例に依る。E2 として暫定にマークし、差し替え条件を「宣言の外で見つかった長期的な決定の件数」とする
6. 実装マーク(#222): R-4 結論5 の降ろし先ごとに付ける。IMPL-0220・0253・0155・0168 の既存の未達は、本 ADR で解消したことにしない。未達のまま表示し続ける

### 理由

- 「課さないと決めた」ことを書かないと、次に同じ提起が来たとき、書かれていないのか却下したのかを読み手が区別できない(コアポリシー)。#422 は #162・#172・#271 と同じ形の案を含んでおり、却下の系譜を ADR の上でつなげておかないと、同じ審議を繰り返す
- 既存の ADR を書き換えないのは運用規則による。ただし監査の観点では、決定が分散すると「どの ADR が G-6 の範囲を定めているか」を引けなくなるので、新 ADR から既存の決定番号を明示的に引く

### 監査で確かめられること

- 新 ADR の決定と「課さないと決めたこと」が、本文の条項と1対1で対応しているか(`npm run lint:refs` が番号の実在を見る。中身の対応は人が見る)
- 暫定マークの差し替え条件が観測可能な量で書かれ、その量を R-4 の欄・注入が実際に出しているか

### 採らない案

| 案 | 採らない理由 |
| --- | --- |
| ADR を起こさず、本文の注記だけで済ませる | 却下の系譜(#162・#172・#271)をつなげられない。課さないと決めたことが条項の外に散る |
| ADR-0023 の本文に追記する | 採用済み ADR の本文は書き換えない |
| 外部の運用(Anthropic・Meta)の採用を根拠に書く | 外部の運用は前提の確認にすぎない。採否の根拠は監査で崩れないかに置く |

### 反論されうる点

- 「却下の列挙が長く、ADR が読みにくくなる」→ 読みにくさは採否の理由にしない。列挙は表にして、各行に先例の Issue・ADR を引けば足りる
- 「欠陥台帳の欄と注入の層別は、実際に降りるまで何も測らない」→ そのとおりで、降りるまで `state=undelivered` を出し続ける。降りていないことが見えていれば、監査の穴にはならない
