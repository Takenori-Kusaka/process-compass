## 1. 項目ごとの異議と対案

### 444-4 0510(異議 A。最重要)

- 起案 §2-4 と受付 §3.4 は「template が強制層に使う `ask`」を前提にする。実際は2段である。`template/.claude/settings.json` の `ask` は**初期化の前**の形で、`generate-profile.mjs` の guard 有効の分岐(`guardEnabled` が真)は `standardCategoryAB`(settings.json・guard.json・hooks・process.config.json)と `standardCategoryC`(rulesets・workflows・adapters・scripts/gate・scripts/vendor)を **`permissions.deny` に置く**(l.6829-6836、6904-6911)。標準の本文(IMPL-0199 の note)も「初期化の前は確認つき(ask)、構成の生成の後は拒否(deny)」と書いている。
- W7 の sb3 は、deny の型が sandbox のシェルにも効くと示した。つまり**初期化の後の template は、sandbox を有効にするだけで 0510 の強制層の経路(W7 が試した範囲)が塞がる**。`ask`→`deny` への移行は不要で、「重へ上げる候補」と「`sandbox.filesystem` が効くか未確認」の第一案も不要になる。起案は §2-4 で template の設定を実際に読んでいない(読んだものの欄にも生成器が無い)。
- 対案: 0510 は「sandbox を有効にする設定(0506 と同じ変更)+ 初期化の後の deny が sandbox のシェルにも効くことの対の試験」で降ろす。残る穴は2つで、条文では**書かず、IMPL-0510 の note と EV で開示**する。
  1. 初期化の前(ask の段)はシェルの経路が開いている。これは「初期化の前は 5.8.6 要求事項6 を満たさない」と開示し、ask を deny に変える案は採らない(初期化の前は人が Claude の道具で直す経路を持つ、が理由)。第7章の例外承認で受ける必要もない(初期化の前は適合を主張する段ではない、と note に書けば足りる。要確認)
  2. W7 の sb3 が試した deny は `scripts/gate/**` と `.github/workflows/**` の2つだけ。`.claude/guard.json`・`process.config.json`・`.claude/settings.json`・`adapters/**`・`scripts/vendor/**` は**未実測**(`.claude/hooks/` は既定の保護)。同じ型だから効くはずだが、「確かめた」と書かない。対の試験は生成後の settings の全パスで探りを流す形にする(template の項目)
- 実機の確認に関する注意: W7 は `-p`(ヘッドレス)で行った。`ask` がヘッドレスで拒否になる挙動と、対話の挙動は同じとは限らない。「ask は効かない」の根拠は「ask はシェルの書き込みの拒否を作らない(承認を求める対象は道具の呼び出し)」という仕様の面に置き、W7 の出力の面は補助にする。note には「ヘッドレスで確かめた」と書く。

### 444-1 0207 と 444-1b

- 分割は賛成。ただし**マーク note が長すぎる**(起案 §3-1 の 0207 の note は環境変数名・トレーラ名・updatedInput 不採用・親への引き当て未確認・版を上げるたびの T1 を1行に詰める)。マーク note の役は「何の規定か・誰が確かめるか」(`implementation-marking.md` の note の定義)であり、環境変数名・版の確認の再実施は EV と手引きに既にある。**note から環境変数名と T1 の指示を外す**。二重に書くと、片方だけ更新されて食い違う(CLAUDE.md の「同じ事実を2か所で書かない」と同じ理由)
- 起案は「環境変数名は提供者の文書に載っていない」と事実として書く(§3-1、§4-1)。起案の読んだもののどこにも提供者の文書の確認が無い。受付 §3.2 も「提供者の文書で確かめる調査を1つ行うのが望ましい」と未了のままである。**確かめていない否定を事実として書いている**(観点 4)。実装の段までに、(a) 文書の確認をするか、(b) 「確認した範囲では見つからない」と書き、日付と確認の範囲を添える
- `check=machine` は、対の試験が「足す・足さない・再開で同値」を持つことを条件にする。機械が確かめるのは**フックの振る舞い**であって、**AI のコミットが必ずフックを通ること**ではない(`--no-verify`、`core.hooksPath` の差し替え、隔離の外のコミット。サンドボックスの中の `git commit` は W7 で成功したのでフックは動くが、`--no-verify` は未確認)。note と台帳に「トレーラの付与は確かめる。付与の漏れの検出は 0743 の側」と分けて書く。さもないと machine の表示が「AI のコミットの全件に識別子がある」と読まれる

### 444-6 0743(異議 B)

- 起案の条件は「Co-Authored-By を持つが `Agent-Run:` を持たないコミットを抽出から外す」。問題が2つある。
  1. **fail-open**。Co-Authored-By は CLAUDE.md の規則で AI が書くもの(IMPL-0176 は `check=manual`、IMPL-0177 の note は「トレーラの無いコミットは検出しない」)。AI が Co-Authored-By を書き落とし、かつ hook が付かなかったコミットは、どちらの印も持たず、**人のコミットとして抽出に残る**。版を特定できない AI の出力を監査の入力に用いない、という規定の本旨と逆に落ちる。決定可能な条件でも、母集団の定義が AI の自己申告に依るので「閉じた」とは言えない
  2. **起案自身の分割と矛盾**。0743 は「**版**を特定できない実行の出力」(`tailoring-guide.md:491-497`)。起案は 0207 を「識別子」と「版」に分け、`Agent-Run:` が運ぶのは識別子だけだと言う。0743 が頼るべきは**版のマーク(新番号)**であり、識別子のトレーラの有無ではない。識別子があれば版が分かるとは限らない(下位の担当、利用者の範囲の指示)
- 対案: 0743 の `plan` と依存を、版のマークに付け替える。条件は「版の記録(SessionStart の記録)に結び付く識別子を持たないコミットは、AI のものとして判定できないものとして**除外するのではなく件数を出す**(母集団から消さず、別の欄に分ける)」。AI のコミットと人のコミットを機械で判別できない以上、「外す」は機械の統制でなく、**人の判断を要する**。manual に下げ、確かめる者(監査人。標本抽出のとき)を書き、`Agent-Run:` を持つコミットの版の欠落だけを機械の件数にする。機械にするのは決定可能な範囲(トレーラの有無・版の記録との結び付きの存在)に限る(所有者の方針)

### 444-5 0828(異議 C)

- 起案 §2-5 は「0207 が降りたとき `check=manual` で delivered」。しかし 3.12.5 要求事項5 は「切り替え期間中に生成された変更を**特定できる状態**」であり、その源(切り替えの記録)は IMPL-0826(#447)で未解決。起案自身が「固有の実装は無い」「template には源が無い」と書く。**降りたものが何も無い規定を delivered と表示する**ことになり、#359 の再確認の裁定(機械でない統制を機械と読ませない)と ADR-0084 決定4(降ろす手段が無い規定を scheduled と表示し続けない)の両方に触れる。443-6 の案(iii)と同じ問いなのに、起案の扱いが揃っていない
- 対案(2つ。議長が選ぶ)
  1. 0828 は 0826 に従属させ、**undelivered のまま**にする(`plan` は 0826 と同じ。期間の源が決まるまで)。条件は「0826 が決まるまで delivered にしない」と note に書く。表示の食い違いが最小
  2. 源を採用者の実行基盤にあると認め、**adopter(decision=ADR)**に移す。template が持てるのは識別子とモデルの識別の記録だけで、期間との突き合わせは採用者の基盤の記録が要る。ただし ADR が要り、#447 の裁定と順序を合わせる必要がある
- 「手引きだけで delivered」は採らない。手引きは降ろし先ではない(`impl-targets.yaml` の kind に guidance 相当は無い。要確認)

### 444-3 0506(異議 D)

- 起案は「基盤ごとにマークを分けない(同じ設定を2回数える)」と言い、一方で 0207 は「表示と実態の食い違い」を理由に分ける。**同じ基準を使っていない**。0506 の delivered(presence、単位: キー)は「設定のキーがある」ことしか示さず、効くのは WSL2 の1回(Claude Code 2.1.314、drvfs)だけ。macOS・ネイティブ Linux の採用者が台帳の delivered を見て「隔離される」と読む危険は 0207 と同じ型である。起案の対処は note の注意書きだが、それなら 0207 も note の注意書きで足りたことになる
- 対案: 0506 を「設定の複製(presence、キー。delivered)」と「効く基盤の確認(manual。基盤の欄を持つ。macOS・Linux は undelivered のまま)」に**分ける**(0207 と同じ扱い)。または逆に 0207 を分けず、note で足りるとする。**どちらかに揃える**。判断軸は信頼性であり、番号が増えることは理由にならない。私は分ける側を推す(適合の主張に響くのは効く基盤の方)
- 「依存の取得の宛先の既定は最小に置く」は、値の既定を template に置く話で、実測が無い(npm・pip・Maven など採用者の stack に依る)。stack ごとの宛先は adopter の領分であり、template は空の一覧 + 追加の手引きでよい。値を置くなら EV。ここは「最小」の中身が未定のまま降ろしに入っている
- sandbox が効かない基盤(ネイティブ Windows)に同じ設定を複製しても、警告つきで隔離なしで動く(W4)。**複製した設定が効かないのに、拒否が成立したように見える**。5.8.6 の「この条件を満たさない実行基盤では要求事項1 の拒否は成立しない」と整合させるため、template の初期化は基盤を判定できないので、ここは手引きで「効いた」ことの確かめ(S2。ファイルの実在で確かめる)を採用者に求める形にとどめる。これは機械にできない(基盤の判定は決定可能でない)ので manual と書く

### 444-2 0200(異議 E)

- adopter へ移さない判断は賛成。ただし「記録だけの形を最初に降ろす」と「その記録が EV-0251 の差し替え条件を満たす」は成り立たない。差し替え条件は「この範囲で書き込みを拒否する実装の運用の記録で、**誤った遮断**と範囲の外への書き込みの件数」。記録だけの形では誤った遮断は起きず、起きたはずの数(would-block)が観測できるだけ。**代理指標を、差し替え条件を満たしたと言い換えている**(観点 4)。EV-0251 の差し替え条件の文言を、実装の段で「拒否した実装、または拒否しなかった場合の外への書き込みの件数」へ**改める**か、満たすのは一部と書く
- 記録だけの形は、guard-write の新しい動作モードであり、新しいログ形式と、その検査を要する。起案は「template の機械(パスの照合は決定可能)」とだけ書く。**新しい設定項目を足す**ことは、所有者の第3問(破られたときの損失)に照らすと、モード切替を悪用して拒否を外す抜け道にもなる(`guard.enabled` の一時緩和と同じ種類)。緩和は記名と理由を要する既存の経路(`guard.enabled` の上書き、process.config.json)に乗せ、**新しい緩和の経路を作らない**。対案: 記録だけの形は template に作らず、既存の denied.log に「拒否した」記録を残す現行の動作のまま、`guard.json` に計画外の置き場の**空の既定**を置いて採用者に埋めさせ、誤遮断は denied.log の件数で見る。0200 は undelivered のまま、EV-0251 は E0 のまま。新しいモードを作らない

## 2. 観点ごとの総括

1. **決定可能でない条件を機械にしていないか**: 0743(AI かどうかの判別を Co-Authored-By の有無に頼る)が該当。0207 の machine も付与の漏れの検出まで主張しない形に限る。起案は §2-4 で「シェルのコマンドの解析は決定可能でない」と正しく退けており、その線を 0743 にも引くべき
2. **template が持てるものを「降ろさない」にしていないか**: 起案の逆の誤りの方が大きい。0510 は template が既に持っている(初期化の後の deny)。降ろす作業は小さく、重への昇格も要らない。0828 は template が持てるのは識別子まで、と線を引き直す
3. **細かい定義を増やしすぎていないか**: マーク note への環境変数名・トレーラ名・手順の混入、手引きの足し(S2 の確認方法、S3 の3通り、記録だけで1期間)、EV 2件、新モード。EV と手引きに書いたものは note で繰り返さない。EV は2件のままでよい
4. **確かめていないことを確かめたと書いていないか**: (i) 環境変数名が文書に載っていない、(ii) 記録だけの形が EV-0251 の条件を満たす、(iii) `sandbox.filesystem` を第一案にした(起案自身が未確認と書く点は誠実)、(iv) W7 の deny は2パスのみ。いずれも上記のとおり
5. **既存の ADR・条項との矛盾**: ADR-0084 決定4・#359 再確認(0828 の delivered)。ADR-0126 決定3(0200 を scheduled で保つ)には矛盾しない。決定4「IMPL-0198 を根拠に要求事項6 の全体の適合を述べない」は、0510 を降ろした後も**初期化の前**の穴が残るため維持する。5.8.6 の「確認つきは拒否に数えない」とは矛盾しない(初期化の前は拒否に数えない、と note に書く)

## 3. 起案が弱いと自認した3点への回答

1. 0507 を adopter のまま保つ判断: **正しい**。0507 は WSL2 の効きと別の経路(ネイティブ Windows のシェル・MCP・WebFetch)を持つ。ただし note の日付と版(2.1.326)は agentic-freshness に従って必須。ネイティブ Windows の「隔離は機能ゲートの裏」は単一の版・単一の機械の観測なので、EV の対象にも入れる
2. 0207 の分割で番号が増える: 分割に**賛成**。ただし 0506 も同じ基準で分ける(異議 D)
3. 0510 の `sandbox.filesystem` が未確認: 第一案ごと不要(異議 A)。deny の型で足りる

## 4. 重への昇格の要否

起案が挙げた2つはどちらも**重へ上げない**。0510 は ask→deny の議題が消える。0200 を adopter へ移す案は、起案も私も採らない。割れた点(0828 の扱い、0506 の分割)は新しい義務・ADR の原則の変更・安全に当たらない(表示の整合の問題)ので、議長の裁定で足りる。ただし 0828 を adopter にする場合は ADR を要する。

## 5. 採らない案(記録のため)

- 0510 を `ask`→`deny` で閉じる案: 初期化の後は既に deny。初期化の前の ask は人の経路として残す
- guard-write をシェルへ広げる案: 起案と同じ理由(決定可能でない)で採らない
- 0200 に記録だけのモードを新設する案: 緩和の抜け道を増やす。既存の denied.log の件数で足りる
- 0828 を「手引き + delivered(manual)」にする案: 降りたものが無い
- 0743 を「Co-Authored-By の有無で外す」案: 申告に頼る fail-open
