# #443 軽の審議: 反対委員の意見

読んだもの: council-443-drafter.md、intake.md の #443 の節、`issue=443` の 11 件のマーク(lifecycle.md 2.10.5・2.10.6、human-ai-boundary.md 5.7.4・5.7.5 は全文)、`implementation-marking.md`、`impl-no-adopter.yaml`、`impl-targets.yaml` の flow-observation・gate-skill・gate-record-template、ADR-0094、template の `scripts/gate/next.mjs`(価値責任者の判断の扱い)。実行したのは `template/scripts/gate/test-content-sampling.mjs` の 1 回だけ(30 passed, 0 failed)。

## 0. 総括

起案は 11 件の大半を「adopter か手引き1文」で片付け、重へ上げる事案を自分で避けている。落とす点は次のとおり。

- **0174 の分割は、adopter の意味に当たらない。かつ要求事項の分け方が誤っている**(異議1)
- **0954・0851・0899 の adopter 化は、束 C の2巡目の裁定(降ろし先を分ける案は採らない・flow-observation を置き場とする)を、触れずに覆している**。既存の決定との矛盾(異議3)
- **0374 の「候補」は、決定可能な述語を決めずに逃げている**。ADR-0094 の「完了スループットを、閉じた件数と並べる」との関係も未突合(異議4)
- 0175 の機械の検査の3条件のうち、「別の種で別の並び」は決定可能だが、試験の中身が「慣れが遅れる」の代理になっていないかの開示が要る(異議2)
- 実機の確認は起案自身が「していない」と書いているのに、0174 の `--verify` の試験の有無や 0614 の「決定可能」を確かめた体で書いている箇所がある(異議7)

## 1. 0174: 分割案への異議

1. **要求事項2 は「当事者に抽出を選ばせない」で、機械の側(種を実行者が選べない値から導く、締めの前の抽出の拒否、`--seed` の照合)は template が既に持っている**。マーク全文と `test-content-sampling.mjs`(今回実行: 30 passed)で確かめた。機械で閉じないのは、5.7.4 本文のとおり「選び直しを止める者」の部分で、それは要求事項2 ではなく**要求事項4(確かめる者は判定者以外)**に書かれた人の統制である。したがって起案の分け方「機構=要求事項1・3〜6、要求事項2=新マーク」は、条項の境界と実装の境界が一致しない。機械が持つのは2の機械の半分と3・5・6の一部で、人が持つのは2の残り半分と4である。
2. **`plan=adopter` は意味に当たらない**。`implementation-marking.md` は adopter を「準拠テンプレートは実装しない。採用者が自ら実装する」と定義する。要求事項2 の機械は template が実装済みで、残るのは「判定者以外が確かめる」という運用であり、採用者が実装する機械ではない。起案自身が弱点に挙げた点で、答えは「当たらない」である。さらに adopter にすると、`decision=` の ADR に「採用者に求めること」を書く必要が生じ、既に条文(5.7.4 要求事項4)が求めている運用を ADR で二重に定めることになる。
3. **対案**: 分割せず、IMPL-0174 全体を `state=delivered check=manual` にする。note に「機械が運ぶのは母集団・種・抽出・再現の確認。選び直しを止めるのは判定者以外の確かめる者(要求事項4・EV-0249)で、機械は確かめない。確かめる者: 抽出した記録の判定者以外の人と内部監査」を書く。これは IMPL-0173・IMPL-0172(いずれも `delivered check=manual` で、機械の確かめない旨と確かめる者を note に置く)と同じ型で、既存の語彙で足りる。
4. 起案が退けた理由「#359 の再確認の裁定と食い違う」への再反論: #359 の裁定は「機械の統制を主張しないため降りていない規定として表示する」で、動機は**機械の統制に見えること**の防止である。`check=manual` は定義上「機械は確かめない」を意味し(マークの `check` の区分)、`delivered` でも機械の統制を主張しない。ただし、**これは裁定の動機を `check=manual` が満たすという主張であり、表示を弱める向きの変更である**。「表示を減らす」変更は、コアポリシーが求める根拠水準マークの開示がなければ採れない。対案を採るなら、EV-0249 の差し替え条件に「要求事項4 の確かめが実際に行われた四半期の割合」を観測の源として足し、manual の実態を追う。この点は議長の裁定事項(表示を弱めることの是非)で、割れたとき議長が決める。
5. 3問 (2): 起案は「例外承認で受けない」と言うが、(3) の損失(内部監査が実質の無い記録を見逃す)は安全でも取り消せない操作でもなく、適合の主張の信頼にだけ響く。それなら条文に細かく足すのでなく、現状の note と EV-0249 の開示で足りる、という3問の (3) からも対案が支持される。

## 2. 0175: 条文の寄せ直しへの異議

1. 起案の文案は「周期的に変える。変えるのは提示の層に限る。…`/human-verify` の検証の順序は変えない」と、**条文へ除外と見出しの固定を足している**。所有者の問い (1)「条文は結果と証跡まで」に反して、手順寄りの限定が増えた。除外(検証の順序)と固定(見出し・機械が読む欄)は、template の設計と手引きに降ろす。条文は「提示の層(レビュー本文の雛形と判定記録の草案の確認を求める項目)に限る」までで、`/human-verify` は条文の語彙に登場しない。
2. **「別の種で別の並び」の検査は決定可能だが、「同じ種で同じ並び」「見出しと機械が読む欄が不変」と合わせても、慣れが遅れることの代理にならない**。3条件は構文・値の一致で閉じる範囲にとどめ、これが慣れの抑制を示さないことを EV マークの対象に明記する。起案は「慣れが遅れること」は manual と書くが、manual の確かめる者が誰かを書いていない。note に確かめる者(AI維持管理者または承認設計の評価指標 5.7.6 の担当)を置く。
3. 起案は「周期の長さは実証が無い、template の設定値とし条文に書かない」と書く。この方向は採る。ただし EV の差し替え条件に使う「承認の差し戻し率の推移」は、5.7.6 の評価指標と重複するか否かを突合していない。5.7.6 の指標を引くか、指標を新設しないことを明記せよ。
4. 「提示の版を記録に残す欄を足さない」は採る。ただし、受付の案(5)は「提示した版を記録に残す」を求めていた。起案は PR・Issue の本文が残るので足りると言うが、**版が「どの種で出したか」を後から再現するには、種の導き方(日付から)が決定可能でなければならない**。起案は template の項目に書いているが、「同じ日付なら同じ並び」の日付が判定日か作成日か未定。これは template の定義の欠けとして書き残すこと。

## 3. 0851・0954・0899: adopter 化への異議(最重要)

1. **既存の決定との矛盾**。`impl-targets.yaml` の flow-observation の description に、「2.10.5 の調整の記録と、2.10.6 の見込みの評価・手続の開始・選択の順序の記録の置き場とする(予定。IMPL-0899・0954。束 C の突合 1巡目 C1-22 の裁定で説明を広げ、束 C の2巡目の裁定で追認した。降ろし先を分ける案は採らない)」とある。起案はこの裁定に一度も触れず、0954・0899 を adopter にして降ろし先から外している。覆すなら、どちらが誤りかを明示して決めなければならない(コアポリシーの「突合」)。起案の書き方は、矛盾の存在を見落としている。
2. **adopter は「逃げ」と読まれうる**と起案自身が認める。判断軸は信頼性で、安さを理由にしない。ところが起案が adopter を採る根拠は、「新しい義務を避ける」「重にしない」であり、変更量の少なさと実質同じ構造になっている。
3. **0954 の「事前レビュー期間へ載せる」を adopter にする点**: 第3章 3.10 の仕組みは**標準側にも見つからなかった**(マーク note: 2026-11-15)。「事前レビュー期間へ載せる仕組みが標準に無い」なら、載せる先の定義が標準に無いまま採用者へ委ねることになる。adopter の定義は「規定は課したまま」だが、実装先が定義されていない規定は、採用者が実装できない。ここは **3.10 に載せ先があるか**を本文で突合するのが先である。起案は突合していない。
4. **「調整の記録 = テンプレ4 のゲート名『価値責任者の調整』」の新設は、新しいゲート名という語彙の追加**で、起案は「新しい義務ではない」と言うが、次の理由で言い切れない。
   - `next.mjs` は既に「価値責任者の判断」を `state:needs-po` の遷移の前提の判定記録の名として読む(`next.mjs:512`)。**「価値責任者の判断」と「価値責任者の調整」は紛らわしく、記録の取り違えを生む**。既存の名を使えば `--pickup` が調整の記録を経路の判断と誤読する。新しい名を足せば、`aggregate-evidence.mjs` や `04-gate-record.md` の注記(`必達基準の判定(ステージの途中)` のように名を見分ける仕組み)に影響しうる。この影響を起案は確かめていない。確かめるまで「新しい欄を足さない」「軽のまま」の判断は仮である。
   - 受付の判定基準は「既存の判定記録(テンプレ4)のゲート欄の値で運ぶなら軽」。名の新設が「値」に当たるかは受付の傾きと一致するが、**運ぶ先が flow-observation の記録の置き場(束 C の裁定)と二重になる**。
5. **対案**: 束 C の裁定を維持し、0954・0899 は `plan=scheduled` のまま(target=flow-observation、template の項目)とする。本文では「調整の記録」の定義(テンプレ4 のゲート欄の値)を2.10.5 に1段落置く点だけを採る(定義の欠けの解消。起案と一致)。ただしゲート名は、(a) 既存の「価値責任者の判断」を流用して `--pickup` との取り違えを許すか、(b) 新設して集約と注記を直すか、を template の項目として**実行で確かめるまで本文に確定させない**。確かめられない間は、本文の定義は「調整の記録は第6章テンプレ4 の判定記録で運ぶ。ゲート名の値は template が定める」までにとどめる。
6. **0851(上限)**: 起案は adopter+`check=manual` で、確かめる者は価値責任者。ここは**採る**。理由は、層ごとの個数を数える置き場がなく、機械で閉じない(決定可能な条件にならない)からである。ただし note の「機械の検査にするかは決めていない」を、ADR に「採らない: ラベル運用の義務化。決定可能にするには層の帰属の置き場が要り、採用者への新しい義務になる」と明記して、「決めていない」から「課さないと決めた」へ改めること(却下は成果、書かれていないことと課さないことを区別)。
7. **0899 の順序(範囲を削る → 期日を動かす → 基準を下げる)と SC-M を先に削らない統制**は、適合の主張の信頼に響く。起案は adopter+manual+記録は調整の記録で運ぶとするが、**この順序の違反を発見する人は誰か**(価値責任者本人が破る場合、確かめる者が本人になる)が空白。確かめる者を、価値責任者以外(事業決裁者または B-2、ステージ移行ゲート SG の判定者)に置くこと。置けない構成(1人体制)の扱いは、5.7.4 要求事項4 の「体制の内が1名のときは本人が確かめ、その旨を記録に書く」と同型にせよ。例外承認で受ける形(7.3)は、順序の違反を承認する形になるので採らない。

## 4. 0374: 「候補」への異議

1. 起案は、完了の述語を決めず、template が出すのは「完了の候補」、判断は価値責任者、と分けた。**機械が出す数と標準が使う数(要求事項4・5 の実測スループット、7.7.3 の区分算定)が別物になる**。7.7.3(0377)は0374の集計を入力とするから、0377 は「候補」を入力にした区分を出す。区分は判定者を拘束する(受付の3問 (3)、起案も認める)。入力が候補なら、区分は「人が完了と判断した数」に依らず、判定者を誤って拘束する。起案はこの帰結を「候補と閉じた件数の差を並べる」で受けるが、**差を並べる要求事項5 が既に条文にある**のは、完了でない閉じ方を除くためで、候補と完了の差ではない。意味が違う。
2. **決定可能な述語は作れる**。受付が挙げたとおり、「取り込んだ PR と結び付いた作業単位」は決定可能である。それを述語として採用し、企画書の完了の条件(要求事項4)が**より強い**場合に、その差を人が記入する(完了の判断の記録)形にすれば、「候補」とせずに済む。つまり、候補を数えて人が判断する案は、述語を決める代わりに、全件を人が判断する運用を暗に課す。件数が多いと破綻する(実測スループットの意味が失われる)。
3. **対案**: 述語は「取り込んだ PR と結び付いた作業単位」を template の定義として開示する(`closes` の結び付きと PR の状態は値の一致で決まる)。企画書の完了の条件が、これより強い案件は、完了の判定記録(価値責任者の判断のゲート名)を作業単位に残したものだけを数える、の2段にする。いずれも EV マーク(E0)で開示し、差し替え条件は起案のとおり。
4. これは受付の傾き(取り込んだ PR)と一致し、起案の「候補」は受付の傾きから後退している。起案は G-6 通過の記録を退けた点では妥当(G-6 省略構成で数えられない)。
5. 3問 (1): 条文に足すのは手引きの1文という起案は採る。ただし、その1文は**判定者を拘束する入力の定義**を含むので、手引きでなく 7.7.3 の要求事項側に「入力は 2.10.2 要求事項4 の完了の条件を満たした作業単位」と既にあるか確かめる。あるなら足さない。確かめていない。

## 5. 0377・0614・0615・0283・0500

- **0377**: 変えないは採る。ただし 0374 の述語が変われば前提が変わるので、異議4の決定後に再確認。
- **0614 の分割**:
  - 「日程と SC-M の変動率は決定可能」は**確かめていない**。日程の遅延の見込みは 2.10.6 で価値責任者が評価するもの(自由な判断)で、機械が出すのは材料の集計(2.10.6 末尾の「材料の集計は実行の担い手に任せてよい」)までである。**日程の見込みを機械の算定にすると、見込みの評価主体(価値責任者)を機械が代替する**。ここは `scheduled` でなく「材料の集計」と書き改めるべきで、note も同様。起案は IMPL-0614 を日程と変動率に限って `scheduled` に残すが、「日程の遅延の見込み」の機械の算定の式(何から、どの閾値で)を挙げていない。式がなければ決定可能でない。SC-M の変動率は SG の記名の一覧の差分の比で決定可能だが、7.6 の参考の値との比較と発火は人の判断。
  - 予算の見込みを adopter とする点は、IMPL-0499(ADR-0125 決定4)と同型で採る。ただし `decision=` を ADR-0125 の決定4 の延長として書けないか。新 ADR の決定1つを足すより、ADR-0125 の表への追記が不可なら(採用済み ADR は書き換えない)、新 ADR の決定に「0499 と同じ置き場」と参照する形で足りる。
- **0615(adopter)**: 起案は「7.6 は no-adopter に無い」で足りるとする。しかし 7.6 は**エスカレーション(停止・安全に隣接する経路)**で、`impl-no-adopter` が理由とする「採用者の実装の有無で統制が消える型」に近い。登録簿に無いことは許されることの証明にならない。起案の3問 (3) は「人の起票でも起こせる」と書くが、それは**発火の自動化がなくても経路は残る**という意味で、adopter の根拠として妥当。登録簿の趣旨との関係を ADR に1行で明記すること(「登録簿に載せない理由」)。
- **0283**: 本文を変えないは採る。起案が template の項目に挙げた「着手した時点の定義」は、2.10.4 の語の欠けなので**本文側の定義の欠け**でもある。template の定義として開示するだけだと、標準と template の定義が分離する。本文に「着手した時点」の定義を置かないと決めるなら、その決定(課さない)を ADR に書く。
- **0500**: 宣言行は妥当だが、起案の「破られたときの損失が小さいので細かく書かない」は採る。一方で、**コメントの書き込み権限が無いとき、標準出力に出すだけで件数に数えない**という扱いは、形骸化の兆候が見えない状態を作る。表示する際に「数えられなかった件数」を別に出すこと。実機の確認(トークンの権限・重複)は template の項目で、この束では未確認と明記されている。そのとおり未確認として書くこと。

## 6. 重へ上げるべきか

- 異議3(0954・0899 が束 C の裁定を覆す)は、**既存の決定との矛盾**で、調整の記録の置き場の ADR の原則に関わる。これは起案の想定(★は新しい欄を足す案のみ)と別の経路で、**軽の枠で議長が裁定する**。重にするのは、割れた点が「新しい義務・ADR の原則の変更」に当たる場合。本案の対案(束 C の裁定を維持)なら新しい義務は生じず軽のまま。
- 異議1(0174 の表示を弱める)は、表示と実態の食い違いの向きでは「実態を正す」側。重にはしない。ただし議長が裁定し、採らない案を記録する。

## 7. 実機・実行で確かめていないこと(起案の記述の検証)

- 起案の冒頭は「実行はしていない」と書くが、1.1 は「`--verify` に試験があるなら」と条件つきで済ませている。試験は存在し、30 件通る(今回確認)。ただし起案の「機構を `check=machine` へ上げられるか」は、`machine` の要件(試験の内容の確認・目印の場面と規定の突合、`implementation-marking.md` の EV)を満たすか未確認。`check=machine` にするには `test=` の属性が要る。要求事項2 の半分が manual のマークを machine にはできない。上げない。
- 「日付から導く種で決定可能」(0175)、「日程と変動率は決定可能」(0614)、「ゲート名の追加は集約に影響しない」(954) は、いずれも実行で確かめていない。template を触らないこの束では確かめられないので、**確かめたと書かず、template の項目として「確認前」と書く**こと。
- ADR-0162 の採番は、0160 が欠番のまま(ls で確認)。仮の番号として扱うのは妥当。
