- 作成: 2026-11-17。読んだもの: intake.md §1、council-441-drafter.md、gate-criteria.md 2655-2722 とマーク行(IMPL-0044・0268・0516・0977)、roles-responsibilities.md 3.11.7 と IMPL-0230・0981、ADR-0137(ステータス表・決定4)、ADR-0084 決定4・implementation-marking.md の adopter の節、ADR-0129:93、git-strategy.md:125、ci-gates.md:168、template の next.mjs・autonomy.mjs・check-pr.mjs・aggregate-evidence.mjs(読むだけ。実行はしていない)

## 1. 441-b 短期書き換え率: adopter にするのは結論として賛成。ただし新マークと新 ADR は要らない(重複)

- 異議: 3.11.7 の「短期間で書き換えられた行の比率」は、`IMPL-0230 target=evidence-aggregation plan=adopter decision=ADR-0137` が既にある。note は「準拠テンプレートは算出を実装しない。採用者が、G-1 で定めた定義・観測の窓・最小標本数で、自動の集計の手段を置く。確かめる者: 採用者の AI維持管理者」。起案の新マーク(窓と最小標本数を備える・満たない値を用いない)は、これと同じ内容を別の番号で二重に課す。ADR-0137 の表も「3.11.7 の4指標は採用者の実装」と既に決めている
- 起案が見落とした点: 第4章の定義(14日、AI 生成の行)と 3.11.7 の行(短期間で書き換えられた行の比率)は、定義が別である。ADR-0137 が「第4章の窓は #441 で別に決める」と残したのはこの差。ただしこれは**窓と最小標本数が要求事項3 で全指標に既に課されている**ため、別のマークで課す根拠にならない
- 対案: IMPL-0268 は一発承認率だけに絞り、note の「AI 生成行の短期書き換え率は期間で集計しない」の一文を「採用者の実装(IMPL-0230。窓と最小標本数は要求事項3)」へ**差し替える**。**新しいマークも新しい ADR も作らない**。第4章の定義の行に1文「算出は IMPL-0230 が採用者に委ねる」を足すかは突合で決める。ADR-0137 の「#441 が行の帰属の集計を入れるなら置き換える」条件は、入れないので発生せず、ADR は書かなくてよい(記録は `research/441-...-deliberation/` で足りる)
- 根拠の所在: roles-responsibilities.md の IMPL-0230 行、ADR-0137 ステータス表の IMPL-0268 の行と「決定 4」、ADR-0084 決定4 と implementation-marking.md の adopter の節(理由と求めることは `decision=` の記録に既にある)
- 3問: (1) 結果は要求事項3 が既に書く。(2) 例外承認の話ではない。(3) 破られても合否へ波及しない。細かく書く理由が無く、条文・マーク・ADR を増やす(細かい定義の増加)ほど信頼は増えない
- 起案の弱点への応答も不足: 「採用者が窓の無い値を出しても照らす先が無い」への起案の答えは IMPL-0977(G-1 の記録の席)だが、IMPL-0977 は閾値の記録の欄であり、短期書き換え率の**集計の値**を見る席ではない(note は 5.4.6 の閾値の記録の欄不足の話。確かめた範囲)。席を言い切れないなら「照らす先は無い」と note に書き、根拠水準マークで開示するのが誠実。起案の「IMPL-0977 の席で確かめる」は確かめていない主張

## 2. 441-a 一発承認率: 「template の機械の検査」への異議。決定可能とは確かめられていない

- 異議1(決定可能性): 起案は「分母・分子は PR のレビューの状態から決定できる」と書くが、実際に確かめたのは `lastReviewStates`(aggregate-evidence.mjs:407 付近)が**レビュアごとの最終状態だけを保つ**形に読めること。一発承認は「承認の前に CHANGES_REQUESTED が一度も無い」という履歴の性質で、最終状態からは出ない。履歴が写しに残っているかは起案は見ていない(確認していない)。また「期間内に承認された」の期間の帰属(承認の日か、マージの日か)、dismiss された承認や push で失効した承認を一発に数えるかは、決定可能な条件ではなく定義の選択である。第4章の定義(差し戻しを受けずに承認された変更の件数 ÷ 期間内に承認された変更の件数)は、ここを定めていない
- 異議2(統制の閉じ方): 値の窓と標本数の「存在」(29件で値を出さない)は機械で決定できる。しかし**値そのものの意味**(一発の判定)は、上の定義の選択に依るため、機械が出した値が「正しい」とは言えない。起案は窓と標本数の検査と、値の算出の正しさを区別していない。機械にするのは前者だけにし、後者は根拠水準マークで開示すべき
- 異議3(既存の規定との緊張): gate-criteria.md「一発承認率は、差し戻し率および欠陥の検出工程と対で確認します。単独では判断材料になりません」。template の集約が単独で一発承認率を出すと、規定の「単独で提示しない」に反する出し方になり得る。起案はこの対の義務に触れていない。出すなら差し戻し率(IMPL-0516)と並べる出し方に限るべき
- 異議4(合否の判定に使わない指標を機械化する意味): 起案は「3問の(3)が軽いが安さを理由にしない」と書く。軽いこと自体は採否の理由にならないが、**機械化の便益は信頼の増加でなければならない**。この指標は「指摘を控えれば上がる」と本標準自身が述べ、操作可能である。機械が算出して集約に載せると、権威を帯びる害(起案が441-bの案B を落とした理由と同型)がある。起案は441-b でこの理由を使い、441-a では使わない。理由の適用が非対称
- 対案(2つ。競わせる):
  - 案1 一発承認率も `adopter`: 理由は(i) 履歴の定義の選択が採用者の運用(ラベル・レビューの運用)に依り、機械が決定できない、(ii) 操作可能で合否に使わない、(iii) IMPL-0230 と同じ扱いに揃う。起案は「理由を書けないので不可」と言うが、(i)(ii) は書ける。ADR-0084 決定4 の「理由を書けない」に当たらない。したがって起案の「採らない案」の根拠は誤り
  - 案2 template で窓と最小標本数の検査だけを降ろす: 値の算出は template がせず、採用者の集計が出した値を受ける場所が無いので成立しにくい。弱い
  - 反対委員は案1を推す。ただし議長が template で降ろす裁定をするなら、条件として「差し戻し率と並べて出す」「履歴の定義(失効・dismiss の扱い、期間の帰属)を note と手引きで明示する」「値の意味は根拠水準マークで開示する」を付ける
- 根拠水準: 起案は「新たに足す必要は無い」と書くが、一発承認の定義の選択(期間の帰属・失効の扱い)は新しい未検証の前提であり、template に降ろすなら `:::caution[暫定 EV]` が要る。降ろさないなら要らない

## 3. 441-c トレーラ: 方向は賛成、前提の確認が足りない

- 賛成の根拠: 規範は git-strategy.md:125(末尾の段落)、ci-gates.md:168(「スカッシュのコミットのメッセージになる PR の本文の末尾の段落で見る」)で、`doneTasks`(next.mjs:766-774)だけが本文のどこでも読む。規範に揃えるのは正しい
- 異議1(未確認): 起案は「GitHub の squash は本文の後に自動でトレーラを足すことがあるか」を確かめていない。ci-gates.md の同じ段落は、リポジトリのスカッシュ設定を「PR の題名と本文」にする前提を書く。設定が違うと(例: 既定のコミットメッセージ)、`Spec:` が末尾の段落から外れて `doneTasks` が数え漏れる。autonomy.mjs の `specTrailersOf` は既にこの読み方で、手戻り率の分母に使う。揃えると next.mjs の数え漏れが**手戻り率の母数と同じ**になる利点はあるが、実機(squash の実メッセージ)での確認は無い。#444 の probe の対象外とした起案の判断は、確かめる手段を捨てている。実機の確認は議長が採否を決めてからで、起案は「確かめた」とは書けない
- 異議2(別の規範): 同じ `Spec:` を読む第3の場所として、aggregate-evidence.mjs:1403 は `git log` の `%(trailers:key=Spec)` を使う。これは git 自身のトレーラの解釈(末尾の段落。ただし git は末尾の段落が全部トレーラでなくても一定の条件で読む)で、末尾の段落の規則とは細部が違う。起案は「2通りの実装」と書くが、**実際は3通り**(next.mjs の本文全体、autonomy.mjs・check-pr.mjs の lastParagraph、aggregate の git の trailers)。共有関数にするなら、3つ目の扱いを決めずに「揃える」と言えない
- 異議3(3問): 起案は(3)で「適合の主張(委任の拡張の判定)の信頼に響く」と書く。ここの前半は、next.mjs の `doneTasks` が「次の一手」の表示に使う値であって、委任の拡張の判定の入力ではない(autonomy.mjs の `specTrailersOf` が手戻り率に使う)。つまり `doneTasks` の食い違いは**「次の一手」の誤表示**で、適合の主張の信頼への影響は間接的。起案の重要度の記述は過大。ただし採否は変わらない
- 対案: 移行の注意を「手引きに1行」とするのは、既存の履歴で「未済」に戻るコミットが実在するかを、本標準自身のリポジトリか fixture で数えてから書く(未確認の影響を手引きに書かない)

## 4. IMPL-0268 の分割・表示

- 分割は不要(§1)。note の「期間で集計しない」を直す点だけは賛成。ただし「算出しない」は、一発承認率を template で降ろす裁定なら「未実装」、adopter なら「採用者が実装」と書く。どちらかに決めずに書き換えるとまた食い違う
- 起案の文案のマークの「確かめる者: G-1 の閾値の記録の席(IMPL-0977)」は、§1 のとおり確かめていない席の指名なので削る。implementation-marking.md の書式(確かめる者の欄)に合うかは `npm run lint` を流して確かめる前に書いてはならない(起案は文案としているので誤りではないが、実行では確かめていない)

## 6. 結論(反対委員の対案の一括)

1. 441-b: 新マーク・新 ADR を作らない。IMPL-0268 の note を IMPL-0230 を指す形に直し、一発承認率だけに絞る
2. 441-a: adopter(案1)を推す。割れた場合は、議長が template を採るなら上の3条件を付ける。割れた点は新しい義務でも ADR の原則の変更でも安全でもないので、軽のまま議長が裁定できる
3. 441-c: template の項目として残すのは賛成。ただし3通りの読み方の扱いと、スカッシュ設定の実機の確認を項目に加える
4. 重へ上げる点: なし(起案の「短期書き換え率を指標から外す案」も、この反対委員は主張しない)
