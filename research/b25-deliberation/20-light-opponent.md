# 束 B25 — 軽の会議体 反対委員の意見(2026-11-19)

入力: `research/b24-deliberation/00-intake.md`・`30-ruling-draft.md`。実物は phase4-process-design の本体、template/scripts/gate/ を読んだ。実行はしていない。

## 先頭: 新しい義務・ADR の原則の変更・安全に当たる点

- **0594 は安全に当たる**。案の理由「既存の組(0663・0062・0919)が全経路で満たす」は実物で成り立たない(下の 2)。ただし新しい義務ではなく、案の machine 表示が実態と食い違う問題である。重へ上げる前に、裁定の案を直せば軽のまま閉じられる(後述の対案)。割れた点が安全なので、案が machine を維持するなら重へ上げる条件に当たる

## 1. IMPL-0216(形骸化の指標)

**結論: 条件つきで同意**(分けて降ろす方向は支持する。日数の測り方と母数の扱いを直す)。

反証と指摘:
- 判定の時点を「判定の記録を入れた PR のマージの時刻」で代理する案は、指標を良く見せる向きにずれる。マージは判定の後に遅れうる(判定記録の PR が数日放置される)。遅れた分だけ「公開から判定まで」が長く出て、規定日数を下回る事例が隠れる。短縮の検出は 0830 が公開と判定予定日 T で既に行っている(`pre-review.mjs` 463 行、`timelineOf` 101 行)。`pre-review.mjs` に merged の読みは無く(grep で 0 件)、結び付けは 0214 の未実装の部分に依る。0214 の実装を待つ依存を案は書いていない
- 結べない上程を母数から外し「件数だけ出す」案は、外した件数の比率が高いときに指標が良く見える。結べない比率を同じ行に必ず出し、比率が閾値を超えたら「指標は参考値」と出す、までを条件にする
- 会議体のない工程ゲートへ当てない根拠は条文にある。roles-responsibilities.md 1259 行「工程ゲートでは判定会議を開かないため、非同期コメント期間のみ」、3.7.1(943 行)。よって手引きの側(判定当日の論点)は B-1〜B-4 に限り、工程ゲートに「当たらない」旨を書くのは正しい。ただし 3.10.8 の表(1397〜1403 行)は上程の種別で指標を分けておらず、日数の指標は工程ゲートにも当たる。日数は工程ゲートも母数に含める
- マークを分けること自体は条文の単位と合う。1405 行のマークは既に「降りている3指標/降りていない2指標」を1つに束ね、「一部だけ降りた規定は降りていない側に置く」と書いている。これは機械で閉じる部分と閉じない部分が混ざった表示で、分ける方が表示と実態が合う。ただし分けた新マークは、表の「判定当日に初めて出た論点の比率」の行(1400 行)に付ける。ADR・scope 台帳の単位が3.10.8 の節全体のため、`lint:impl` が節に対して2件のマークを許すかを実行で確かめる

対案:
1. 日数の指標の判定の時点は、判定記録の「判定日」の欄(様式の既存の欄)を第一に読み、無ければマージ時刻で代理して「代理」と出力に印を付ける
2. 結べない上程の比率を同じ行に出す
3. 手引き(G)の指標は「比率」を要求せず、会議体の判定記録に初出の論点を区別して書くところまでにする(集計は人。IMPL-0999 と同じ扱い)

3問: (1) 指標の集計と開示まで。条文の結果は満たす。(2) 該当しない。(3) 形骸化に気づくのが遅れる。安全・取り消せない操作には響かない。細かくは書かない。

## 2. IMPL-0594(リスク区分ごとの最大レベル)

**結論: 案に反対**(ADR-0220 を正とし ruling-a1 §3.3 を採らない点は支持する。「既存の組が全経路で満たすので machine」は反対)。

実物の反証:
- 条文 human-ai-boundary.md 92〜96 行は「R1 は最大 L1、R2 は最大 L2」。L3 を導くのは `autonomy.mjs` の登録した変更種別だけで(3〜5 行・396 行 `level: stops.length ? 'L1' : 'L3'`)、**種別単位**であり変更ごとのリスク区分を読まない。`check-pr.mjs` に autonomy の参照は無い(grep で 0 件)
- 案が頼る IMPL-0663 は条件2(R3 を求める)で、`delegation.mjs` 219〜221 行にある。しかしこれは**委任の経路(自動マージ)だけ**の条件。委任を経ずに、登録した種別の変更が R1 または R2 として PR を出す経路には、L3 の適用(AI 主導の自己修復)を止める検査が無い。さらに IMPL-0663 のマークは `state=delivered check=manual`、note に「実行して確かめていない(所在を読んだ)」(roles-responsibilities.md 1073 行)。machine の組と数えられない
- IMPL-0062 は machine だが(1129 行、test-check-pr.mjs 623・625 行)、区分の記載の下限と確定者の記名を検査するだけで、AI自律レベルを区分に照合しない。さらに adoption-guide.md 159 行は「下限の規則に当たらない R1 相当の変更は R3 と記載されて通りうる」と自ら認めている。R1 の申告が R3 に化ける経路が残る
- R2 は「L2 を支えないため L1 で進む」は厳しい側で問題ない。R1 の側が問題である
- Q1「いいえ」の案件で安全関連部が生じる道: IMPL-0919 の note 自身が「Q1 の答えの正しさは機械で閉じない」「留保を付けた『いいえ』は落ちない」と開示している。案の理由はこの開示と整合するが、0594 の note に machine と書くと、その開示が消える

対案:
- state は `delivered check=manual`(machine にしない)。試験の場面と目印は足す(R1 の PR は条件2 で委任を拒否する。R2 は同じ)が、note に「委任を経ない経路で、登録した種別の変更のリスク区分が R1・R2 のとき、L3 の適用を止める検査は無い。確かめる者: 判定者(区分の確定時)」と開示する
- この残りを降ろすなら、`check-pr` が登録した種別の PR のリスク区分が R1・R2 のとき L3 の適用を協働へ落とす決定可能な検査を足す案が正攻法。これは新しい処理であり、「新しい処理は足さない」という案の前提を外す。範囲外の発見として #446 の open なコメントへ足す(CLAUDE.md の後継の扱い)
- 採らない案(補足): 案のまま machine と表示する(0594 は安全の規定で、表示と実態の食い違いは最も重い欠陥)

3問: (1) 結果は「R1・R2 の変更を L3 で進めない」。現状は委任の経路でだけ満たす。(2) 例外承認で受けない(案と同じ)。(3) 安全関連部が人の確定なしに進む、R1 が L3 で進む。安全に当たるので細かく書く対象。

## 3. IMPL-0840(委任の対象の属性)

**結論: 条件つきで同意**(`introducesPaths` を足さない点は支持。ただし手引きだけでは条文の結果が残らず、machine と表示できる範囲を限る)。

実物の確認:
- `excludePaths` は規則ごと(`config.mjs` 2284 行の検証、2616 行の判定)。実際の働きは「PR の差分に、規則のパスの外か excludePaths に当たるファイルがあれば、その規則での委任を拒む」で、**拒否リスト**として効く。つまり導入に当たるパス(マイグレーション・権限)を excludePaths に書けば、`introducesPaths` と同じ結果(協働へ落ちる)になる。二重の定義の疑いは実物で裏付く
- 意味の違い: `excludePaths` は規則ごと、`introducesPaths` は案件の全体。規則が増えるたびに採用者が全規則へ同じ列を書き写し、1つの規則に書き漏れると**黙って**委任が通る。全体の欄なら漏れない。この点は案に無い。ただし B21 の目的(決定可能な代理)に対しては、欄が多いと細かい定義が増える(CLAUDE.md の線)ため、新しい欄を足さない判断は支持できる
- 条文(tailoring-guide.md 425〜430 行)の結果は「導入するもの: 新たな外部呼び出し・データ構造・権限のいずれも導入しない」。手引きだけでは結果が残らない。(i) 依存の追加の行(決定可能)は (M) で降ろす案が残るので、それは machine と表示してよい。(ii) マイグレーション・権限は採用者が書いた列に当たるものだけ

対案:
- (i) は machine、(ii) は手引き。マークは1つのままなら **`check=machine` にしない**(一部だけ降りた規定は降りていない側へ、という IMPL-0175 の扱いに揃える)。分けるなら (i)=machine・(ii)=manual の2マークにする。0216 と同じ形で揃う
- 手引きに「全ての委任の規則に同じ列を置く。規則を足すときは列を写す」を明記し、`config.mjs` の検査で「導入の疑いのあるパスの典型(migrations/・権限の設定)が paths に含まれる規則に excludePaths が無い」を**注意**に出す(失敗にしない。決定可能)
- note に「所在の外で導入したものは確かめない。規則に書かれていないパスの導入は確かめない(確かめる者: 登録する者と事後の抜き取り)」と開示する

3問: (1) 結果は「導入しない種別を委任の対象にする」。拒否リストと依存の追加の行まで。(2) 該当しない(安全でも取り消せない操作に近い。権限の持ち込みは協働へ落とす向きで狭める)。(3) 権限や依存を持ち込む変更が人の事前確認なしに進む。取り消しにくい。だが失敗側の方向は「通る」ため、書き漏れが静かに効く点は細かく書く。
