## 1. IMPL-0216(2委員は条件つきで一致)

採る:

- マークを2つに分ける(両委員が支持)。機械の側は 0216、判定当日の論点は新しい番号で `target=gate-skill state=delivered check=manual`
- 日数の指標は、**IMPL-0214 の判定の結び付けを実装した後に**置く。判定予定日 T で代用しない(起案)
- 判定の時点は、判定記録の判定日の欄を先に読む。読めないときだけ、判定の記録を基底ブランチへ入れた PR のマージの時刻で代理し、出力に「代理」と出す(反対。マージが遅れると、規定日数を下回る事例が隠れる向きにずれるため)
- 結べない上程は母数から外し、**件数と比率を同じ行に出す**(反対)
- 日数の指標は工程ゲートも母数に含める(3.10.8 の表は上程の種別で分けていない)。判定当日の論点の手引きは会議体(B-1〜B-4)に限り、工程ゲートに当たらない旨を書く(根拠: 3.7.1 と 3.10 の「工程ゲートでは判定会議を開かない」)
- 「規定日数を下回った」の判定は、0830 の短縮の検出と同じ関数を通す(二重の定義を作らない)
- 手引きの側は、決定者が判定記録に当日初めて出た論点を区別して書くところまで。比率の集計は人(プロセス内部監査)。note に「記入は決定者の申告。機械は確かめない」を書く

採らない:

- 結べない上程の比率に閾値を置き「参考値」と出す案(反対の対案の一部): 閾値に実証が無い。比率を出すところまでにし、解釈は人が行う
- 当日の論点を機械が数える案、様式 04 に欄を足す案、1つのマークのまま undelivered を保つ案(案のとおり)

## 2. IMPL-0594(2委員が割れた。議長が裁定する)

割れた点: 起案は「既存の組で満たすので `delivered check=machine`」。反対は「L3 を導く `autonomy.mjs` は変更ごとのリスク区分を読まない。委任の条件2(`delegation.mjs`)は委任の経路にしか効かない。IMPL-0663 は manual。machine の表示は実態と食い違う」。

裁定:

- ADR-0220 を正とし、`ruling-a1.md` §3.3 の safetyRelated の宣言の条件を採らない(両委員が一致)
- **「新しい処理は足さない」という案の前提は外す**。判断軸は信頼性で、条文(R1 は最大 L1、R2 は最大 L2)は安全に響く。単位 D の実装の最初に、次を**実行で確かめる**: 登録した変更種別に当たる変更が、リスク区分 R1 または R2 で、委任を経ない経路を通るとき、L3 の導出が何かの出力・挙動(表示・判定資料・マージの可否)に効くか
  - (ア) 効く場合: 自律レベルを使う箇所で、変更のリスク区分の記載(決定可能な値)が R1・R2 のとき L1 へ落とす検査を足し、ng/ok の試験を付けて `delivered check=machine` にする。R2 は L2 を支えないため L1(厳しい側。ADR-0081 決定6)
  - (イ) L3 の効果が委任(自動マージ)に限られると実行で確かめられた場合: 条件2 の R1 の場面を試験に足し、`delivered check=machine`。note に「L3 の効果は委任の経路だけ。条件2 が R3 を求める」と範囲を書く
  - (ウ) リスク区分が使う箇所で決定可能に読めない場合: `delivered check=manual` にし、note に「委任を経ない経路で、登録した種別の変更の区分が R1・R2 のとき L3 を止める検査は無い。確かめる者: 区分を確定する者」と開示する
- どの場合も note に「安全関連部は IMPL-0919(Q1 の答えの正しさは機械で閉じない)」「区分の正しさは IMPL-0062 の下限と確定の記名。下限に当たらない R1 相当が R3 と記載されて通りうる(adoption-guide の開示)」「IMPL-0663 は manual」を残す。既存の組が全部 machine であるかのように書かない
- 重へは上げない。新しい義務でも ADR の原則の変更でもなく、既にある条文の降ろし方の正確さの問題で、裁定は安全の側(検査を足すか、開示する)へ倒している

採らない: 案のまま、実行で確かめずに machine と表示する案(表示と実態の食い違い)。safetyRelated の宣言の条件。`changeInType` から safetyRelated の型を外す案

## 3. IMPL-0840(2委員は条件つきで一致)

採る:

- `delegation.introducesPaths` は足さない(両委員が支持。既存の `excludePaths` が同じ結果を持ち、二重の定義になる)。束 B21 の裁定のこの部分を変える。理由は、裁定の時点で見えていなかった事実である
- マークを2つに分ける。0840 は「依存の目印のファイルの追加の行」に限って `delivered check=machine`。新しい番号を「マイグレーション・権限の設定の置き場を、委任の規則の `excludePaths` に書く」手引きに付け、`state=delivered check=manual`。note に「置き場に書いた分だけ委任から外れる。書いていない規則・所在の外の導入は確かめない。確かめる者: 登録する者と事後の抜き取り」
- 手引き(process-change の delegation の補助ファイル)に書く: (a) `excludePaths` は規則ごとで、全ての委任の規則に置く。規則を足すときも置く (b) 「委任から外す」であって禁止ではない(人の判定へ戻る) (c) 置き場が変わったら登録を改める

採らない:

- `introducesPaths` の新設(二重の定義)
- 典型のパス(migrations/ など)を paths に含む規則に `excludePaths` が無いとき注意を出す案(反対の対案の一部): 典型のパスの一覧は推測で、採用者の構成ごとに違う。細かい定義が増え、当たらない構成では偽の安心を作る
- 生成する D-0 の表に置き場を出す案(欄の新設)
- 1つのマークのまま machine と表示する案(表示が実態より強い)
