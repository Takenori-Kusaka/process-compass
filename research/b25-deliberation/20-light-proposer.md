## 項目1 IMPL-0216(形骸化の5指標)

**結論: 直して採る**(分ける案は採る。日数の指標に順序の条件を足す)

実物で確かめた事実

- 表の警戒サイン: `roles-responsibilities.md:1395-1403`。日数は「規定日数を下回る事例が続く」、当日の論点は「高い」

- `template/templates/04-gate-record.md` に当日の論点を区別する欄は無い(ADR-0040 により様式の欄は標準の第6章が先)

3問への答え
1. 結果は「月ごとに値が開示され、人が警戒を解釈できる」まで。当日の論点の数え方は手引きで足りる
2. 例外承認では受けない。そもそも義務の緩和ではなく測る手段の問題である
3. 破られると、事前レビューの形骸化に気づくのが遅れる。失うのは採用者の内部監査の材料。安全・取り消せない操作・適合の主張の信頼には直接響かない。細かく書かない案に同意

直す点
- 日数は**判定の時点を 0214 の結び付けで取れた上程だけ**を母数にする。取れない上程は件数だけ出す(案のとおり)。ただし実装の順序は **0214 の結び付けの後**。先に出すなら T(予定日)で代用したくなるが、それは「実際の日数」ではないので**代用しない**。順序を実装の指示に書く
- 「規定日数を下回った上程の件数」は 0830 の短縮の検出と同じ事実を数える。値が割れないよう、同じ関数を通す(二重の定義を作らない)
- 新しい番号のマーク(当日の論点)は `state=delivered check=manual`。ただし**手引きを置いただけで、決定者が書いたかは確かめない**。note に「記入は決定者の自己申告。内部監査が判定記録から抜き取る」と書き、確かめる者を明記する(案のとおり)。根拠水準マークは要らない(新しい値を定めていない)

反対側が突くと思う弱点と答え
- 弱点: 手引き+manual は「降ろし残しを delivered と言い換えた」ものでは。答え: 機械で閉じない統制を manual にして開示するのは所有者の決定(統制の閉じ方を裁定で決める)。undelivered のまま保つと、台帳に降ろし残しとして永久に出て、本当の降ろし残しが埋もれる。開示の水準は note で正直に書く
- 弱点: コメントの時刻で当日の論点を代理できる。答え: 事前の意見への返信や判定当日の追記も数えて誤る。誤った値は安心を作るので採らない

## 項目2 IMPL-0594(リスク区分ごとの最大レベルと安全関連部)

**結論: 案のまま採る**(ruling-a1 §3.3 の条件は採らず ADR-0220 を正とする。試験の場面を1つ足す点に補足)

実物で確かめた事実
- マーク本文: `human-ai-boundary.md:122`(undelivered/manual)。前半は R1 は L1・R2 は L2、後半は安全関連部の R1・L1 固定
- ADR-0220「課さないと決めたこと」(`src/content/docs/adr/0220*.md:27`)が「安全関連部の範囲を構成に持たせること」を採らないと明記。ruling-a1 §3.3 の「safetyRelated の宣言が無ければ止める」は、この範囲を構成に持たせる前提で、衝突する。後の ADR が置き換えたので ADR-0220 が正
- 安全関連部: `autonomy.mjs:97` の `safetyPartStop` が Q1 を読んで案件の全体を止める。`:158`・`:170`・`:269` の3経路が同じ関数を通る。`test-check-delegation.mjs:841-888` が IMPL-0919 の ng/ok で確かめる
- R1・R2 を L3 で進めない: L3 は登録した変更種別だけ(`autonomy.mjs:3-5`。IMPL-0289 は delivered)。登録した種別の委任は `delegation.mjs:220` の条件2 が「R3 でなければ不成立」とする。R2 が L2 を支えない点は `autonomy.mjs:3` が「L1 と L3 の2つだけ」と明記。つまり R2 は L1 で進む(厳しい側)
- 試験: `test-check-delegation.mjs:61-62` が R2 と未記入の場面を持つ。R1 の場面は `:236` の入口の試験(終了コード1)だけで、**条件2 を名指しで確かめていない**。案の「R1 → 条件2」の場面は実際に欠けている

3問への答え
1. 結果は「R1・R2 の変更が L3(委任)で人の確定なしに進まない」「安全関連部が人の確定なしに進まない」。どちらも既存の組で成立している
2. 例外承認では受けない(安全)。採用者が R1 を R3 と記載して通る経路は IMPL-0062 の下限と確定の記名で受ける。残る穴は `adoption-guide.md:159`・`:430` が既に開示している
3. 破られると、安全関連部または R1 の変更が人の確定なしに進む。失うのは利用者と、適合を主張した採用者。ゆえに細かく書く点は案に同意(新しい処理は足さず、組が結果を満たす証拠を試験の目印で固定する)

直す点(補足)
- 目印の付け先を確かめた: IMPL-0663 はマーク上 `check=manual`(`roles-responsibilities.md:1073`)で、試験の目印を持たない。案が言う「既存の組」のうち 0663 は manual である。note に「0663 は manual、機械が確かめるのは条件2 の R3 要求(`delegation.mjs:220`)」と書き、**既存の組が全部 machine であるかのように書かない**
- 新しい state は `delivered check=machine` でよいが、`test=` に載せる試験の場面は「R1 → 条件2」を**必ず足す**。目印を足すだけで場面を足さないと、R1 が確かめられない

反対側が突くと思う弱点と答え

- 弱点: 安全の項目に、新しい処理なしで delivered はやり過ぎでは。答え: 処理は既に delivered(0919)で、本件は試験の場面の欠けを埋めるだけ。R1 の場面を足して初めて delivered と言える。場面が通らなければ state は上げない

## 項目3 IMPL-0840(委任の種別が満たすべき属性)

**結論: 直して採る**(`introducesPaths` は足さない案を採る。ただしマークを分ける)

実物で確かめた事実
- マーク本文: `tailoring-guide.md:436`。「外部呼び出し・データ構造・権限を導入しない」という属性を求める
- 既存の `excludePaths`: `config.mjs:2284` が配列を検査、`:2616` が「規則の paths の外、または excludePaths に当たるファイルを含む変更」を委任の対象外にする。`excludePaths` に置いたパスを変える変更は**委任から外れて人の判定へ戻る**。`introducesPaths` が求める効果と同じで、2つ持つと食い違いうる(B21 は `delegation.introducesPaths` を足す案だった。`ruling-deferred-draft.md:186`・`:191`)
- 手引きの置き場: `template/.claude/skills/process-change/kinds/mode.md:20` が規則の例に `"excludePaths": []` を書いている。委任の手引きを足す場所はここの隣が自然
- 依存の目印のファイル(マニフェスト・ロックファイル)の追加の行は、差分から決められる(決定可能)

3問への答え
1. 結果は「導入するものの属性を持つ変更が、委任で人の確定なしに通らない」。条文は属性で書いており、パスの置き場を指定していない。置き場は採用者の構成による
2. 珍しい構成(マイグレーション・権限の設定の置き場が組織ごとに違う)は新しい欄を足さず、既存の `excludePaths` と 7 章の手続で受ける。ここは方針の 2 問目そのもの
3. 破られると、マイグレーションや権限を変える変更が、委任で人の確定なしに入る。失うのは取り消せない操作(データ構造の変更)を受ける採用者。ここは「細かく書く」側に近いので、機械の部分は削らない

直す点
- 議長案は 0840 を `delivered check=machine` にし、note で所在の外は確かめないと断る。これは 0216 で議長が採った分け方(機械で閉じる部分と閉じない部分を別のマークにする)と**食い違う**。機械が確かめるのは依存の追加の行だけで、属性の全体(外部呼び出し・データ構造・権限)ではない。そのまま delivered machine にすると、表示が実態より強い。**直す**: 0840 は「依存の追加の行」に限った delivered machine。「置き場に書いた分だけ確かめる(`excludePaths`)。所在の外は確かめない」を別の番号で `state=delivered check=manual`(手引き)とし、note に確かめる者(登録する者と事後の抜き取り)を書く。表示と実態が食い違う「高」を作らない
- `excludePaths` へ置くよう**手引きで求める**だけでは、書かない採用者を機械が見つけられない。案は「所在の外は確かめない」と開示する形で、これで足りる。だが**書いていない旨も開示する**: 構成に `excludePaths` が空の規則があっても失敗にしない(決定可能な条件ではない)。生成する D-0 の表に「導入する属性の置き場: 規則ごとの excludePaths」を出す案は採らない(欄の新設に当たる)
- 手引きには、**独立の突合で見るべき2点**を書く: (a) `excludePaths` は「委任から外す」であって「禁止」ではない(人の判定には戻る)、(b) 置き場が変わったら登録を改める(既存の変更種別の追加と同じ手続)

反対側が突くと思う弱点と答え
- 弱点: B21 の裁定を覆すのでは。答え: 覆す理由は、裁定の時点で見えていなかった事実(`excludePaths` が同じ効果を既に持つ)。二重の定義は信頼性を下げる。採らない案を記録する
- 弱点: 手引きだけでは書かない採用者が通る。答え: そのとおり。書かない採用者の穴は、機械が決められない条件(置き場が何かは組織ごと)で、manual+開示が方針。穴は note に書き、事後の抜き取りで拾う。`introducesPaths` を足しても、書かない採用者は同じく通る。新しい欄は穴を狭めない
- 弱点: 依存の目印の検査も組織ごとに違う(ロックファイルの名前)。答え: 名前の一覧はテンプレート側の定数でよく、足りない形式は採用者が追加できる。決定可能な条件にとどめる
