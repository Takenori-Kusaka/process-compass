## 所見

### 高-1 G-5 の上程の短縮を止めない(条文・ADR は G-4・G-5 を禁止。実装・note・試験は G-4 だけ)

- 所在: `template/scripts/gate/pre-review.mjs` の `shorteningForbidden`(`p.target === 'proposal' || gateTokenOf(p) === 'G-4'`)、`template/scripts/gate/test-pre-review.mjs` の `IMPL-0830(a):ok`(G-5 の上程に印が G-5 の行があれば通知しない、を合格の場面として固定)、`roles-responsibilities.md:1306`(IMPL-0830 の note「G-4 と B-1〜B-4 は短縮できず」)、同 1288〜1290 の図(「G-4 か」だけ)
- 事実: 3.10.2 の本文(1280 行)は「7.4 が後回しを禁止したゲート(**G-4・G-5**)と、第7章 B-1〜B-4 の会議体の上程は、短縮してはなりません」。ADR-0223 決定2 も「(G-4・G-5)」。一方、実装では G-5 の上程は G-5 を名指す行があれば「通知しない・合格ともしない」になる。行の有効性(7.4 が G-5 を禁止していること)は IMPL-0608・0609 が manual で、機械は G-5 を名指す行を拒まない(exception-escalation.md:169・199)。よって、条文が禁じた G-5 の短縮を機械が黙って通す。note は「G-4 と B-1〜B-4」と書き、表示が条文より狭い。ずれの起点は B22 の issue コメント項目2(G-4 だけを名指した)と本文の図で、本束はそれをそのまま実装した
- 直す案: `shorteningForbidden` を G-4・G-5 と B-1〜B-4 にする。試験 0830(a) の題材を G-5 から別の工程ゲート(G-3 / G-6)へ移し、0830(b) に G-5 の ng(G-5 を名指す行があっても「短縮できません」)を足す。note・コメント・図を「G-4・G-5」へ揃える(図は本文の編集の指摘として直す)

### 高-2 R1 の上程で必須応答の者を導出できないとき、0214 の検査が黙って「合格」を出す

- 所在: `pre-review.mjs` の `respondedCheck`(`if (!isR1 && req.logins === null)` だけが「確かめていない」に回る。R1 は `req.logins ?? []` で必須応答の者を落とし、指名レビュアだけで照らす)
- 事実(写しで実行): R1・判定資料の所在が PR #77・CODEOWNERS `* @dave`・指名レビュア bob と carol の宣言行あり、で PR の変更ファイルを読めないとき(`prFiles: {}`。API の失敗に当たる) → `status: pass`、行は「宣言行が揃った(判定日 2026-11-27 まで。2 名)」。必須応答の者(dave)を確かめていないことはどこにも出ない。同じ条件で変更ファイルを読めると → `fail`。通知の側((c))は同じ場面で「必須応答の者を導出できない(…)。指名レビュアの分だけ照らす」と注意を出すが、検査の側には無い。ADR-0223 決定6 の「3.10.9 の上程では必須応答の者の全員」が、読み取りの失敗で黙って抜ける
- 直す案: R1 で `p.materialPr` があり `req.logins === null` のときは、指名レビュアの分を照らしたうえで status を `unverified`(指名レビュアに欠けがあれば `fail`)にし、「必須応答の者を導出できない(理由)。指名レビュアの分だけ照らした」の行を出す。試験に ng を足す(上の場面で `pass` にならない)

### 中-1 README の「必須にする手順」をそのとおり行うと、docs/gates に触れない PR がすべてマージできなくなる

- 所在: `template/.github/workflows/pre-review-responded.yml`(`on.pull_request_target.paths: ['docs/gates/**']`)、`template/README.md` の「事前レビュー期間の応答の揃いを必須にする」の手順の行(「Require status checks to pass」に `pre-review-responded` を加える)
- 事実: GitHub の仕様では、パスの絞り込みで実行されなかった workflow の必須チェックは「Pending」のまま残り、その PR はマージできない(GitHub Docs「Troubleshooting required status checks」/ workflow の paths の注記)。README は手順の注意としてこれを書いていない。`respondedCheck` は記録の無い PR を「確かめていない」で 0 終了にする作りで、全 PR で動かす前提と合わない。実物の GitHub では確かめていない(note どおり)
- 直す案: (甲)`paths` を外し、記録の無い PR は「確かめていない(記録を含まない PR)」で 0 終了にする(コードは既にそう返す)/(乙)`paths` を保ち、README に「ルールセットの必須チェックにすると記録を含まない PR が止まる。必須にするなら paths を外す」と書く。推すのは甲(採用者が手順どおりに行って止まらないことを優先する)

### 中-2 結べない記録・確かめていない記録が混ざっても、総合の判定が「合格」になる

- 所在: `pre-review.mjs` の `respondedCheck` の末尾(`['fail', 'pass', 'out', 'unverified'].find(...)`)と `respondedMain` の最終行
- 事実(写しで実行): 結べる記録1件(揃った)と結べない記録1件(対象「F-012」)を含む PR → `status: pass`、最終行は「応答の揃いの検査: 合格: 宣言行が揃った(応答の中身は確かめていない)」。個別の行には「確かめていない」が出るが、総合の判定とチェックの結果(緑)は合格に見える。加えて、`unverified` も終了コード 0 なので GitHub のチェックは成功の表示になり、ログを開かないと「確かめていない」が見えない。裁定(失敗にしない)には沿っているが、「黙って合格に見える出力」に当たる
- 直す案: 優先の順を `fail > unverified > pass > out` にする(終了コードは裁定どおり fail だけ 1)。`unverified` のときは `::warning::` の注記かジョブの要約(`$GITHUB_STEP_SUMMARY`)に「確かめていない」を出し、チェックの画面で見えるようにする。試験に混在の場面を足す

### 低-1 sync-escalation.md の「機械が止める範囲」が、起案者が転記で足した必須応答の者まで含むと読める

- 所在: `template/.claude/skills/gate/reference/sync-escalation.md` の追記の「判定へ進めない強制」の行(「範囲は R1 の上程と、必須応答の者を載せた上程」)

- 直す案: 「範囲は R1 の上程の指名レビュアと、CODEOWNERS から導いた必須応答の者。起案者が判定資料へ足した者は機械は照らさず、決定者が確かめる」と書く

### 低-2 「規定日数を下回った」が 0830 と同じ関数を通すことを、試験が固定していない

### 低-3 印のゲートの範囲の書き方(G-3〜G-5)を読まない

### 低-4 0216 の代理の時刻と「結べず外した」の数え方の表示

- 直す案: (a) 代理の根拠を2種に分けて数える (b) 外した理由ごとの件数を同じ行に出す。どちらも裁定の範囲の中の表示の細かさで、直さないなら note に書く
