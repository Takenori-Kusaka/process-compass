## 2. D-2: record-copy

### 2.1 具体

- `.github/workflows/record-copy.yml` の `concurrency.group`(61〜63 行)を `record-copy-${{ github.event.pull_request.number }}` に
- **グループを分けるだけでは直らない**。別の PR の写しが並行で `records` へ push すると、後の push が non-fast-forward で失敗する(待ちの取り消しが、push の失敗へ形を変えるだけ)。直す箇所は2つ
  1. git 経路(232・240 行の `git push origin "$RECORDS_BRANCH"`): 失敗したら `git pull --rebase origin "$RECORDS_BRANCH"` の後に再 push、最大 5 回。衝突の記録の push(232 行)にも同じ
  2. GraphQL 経路(`expectedHeadOid`。288 行付近): 不一致で失敗したら先頭を読み直して再実行、最大 5 回
- 再実行は安全: 写しは PR ごとの新しいファイルで、既にあれば比べる欄の一致で成功する(223 行)

### 2.2 試験と、閉じ方の開示

- 機械で閉じる(構文): `test-base-judge-workflow.mjs` に、(a) グループが `pull_request.number` を含む (b) push の失敗の後に `pull --rebase` と再試行の上限がある (c) GraphQL の経路に先頭を読み直す再試行がある。違反側は旧いグループ名の定義を渡して NG になること
- **機械で閉じない**: 競合が実際に解消すること。静的な検査は「ループがある」までしか言えない。実機で再現するなら、一時リポで 2 つの PR を 5 秒間隔でマージし、写しが 2 つできることを確かめる。再現しないなら、IMPL-0354 の note と EV に「競合の再試行は、実機で未確認」と開示する。ruling の案(静的な検査だけで閉じる)は、この開示を欠く。足すべき
