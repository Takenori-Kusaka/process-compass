# #373 会議体 現場の委員の意見

- 立場: 1〜2名を含む小さいチームと受託開発の現場。確認の相手がいない体制での手数と詰み、外部の確認者を得る費用と現実性を重視する
- 入力: `council-00-agenda.md`、`survey-373-1-internal.md`(以下「内部」)、`survey-373-2-external.md`(以下「外部」)。行番号は 2026-11-05 の作業ツリーで自分で開いて確かめたもの
- 判断軸は信頼性。変更量の少なさは理由にしない

## 前提として現場から見えること

- **CL0 と CL1 の境は、小さいチームにとって存続の境である**。CL1 以上では 1〜2名の構成そのものを認めない(`phase4-process-design/tailoring-guide.md:961`、初期化で拒否 965、運用中は出荷できない 967)。CL0 は委任の条件1 でもある(同 346)。1〜2名のチームが本標準のもとで出荷を続けられるかは、CL0 と判定できるかだけで決まる。**判定を低く付ける動機が、最も強く働くのはこの境である**
- CL1 の典型例は「決済、与信、人事評価の支援」(`tailoring-guide.md:839`)。受託の小さい案件(EC の決済の組み込み、会員の与信の補助)はこの境に普通に当たる。境の上か下かは、現場では珍しくない判断である
- CL1 と CL2 の境は、3名以上の組織で効く。CL1 と判定すれば、テンプレ9・附属書F・独立した安全性の評価(段2)が外れる(`tailoring-guide.md:854-856`)
- 内部 2.2: 初回の判定には判定者・確認者・根拠の記録の規定が無い。準拠テンプレートの `q-criticality` は記名も根拠も無く構成に入る(内部 5.1)。現場では、初期化のときに AI に聞かれて答えた1行が、そのまま案件の全期間の CL になる
- 段は距離の尺度であり、**能力の尺度ではない**(`phase4-process-design/overview.md:182-187`)。外部の1名(別の法人の知人)は、条件の上では段3・段4 にも当たりうる。一方で、その人が案件の用途を知らなければ、判定を確かめたことにならない。現場で高いのは距離ではなく、用途と規制を知っている人の時間である。この点は R-1 と R-2 の両方に効く

## R-1 CL の判定の確認を求めるか、誰が、どの段で

### 推す案

**案(d) の変形「外す側の区分が求める段」に、全区分で段1 の下限を置き、区分の昇順に単調にする**。あわせて、判定者の記名と、判定の根拠の記録を全区分で求める(案(e) の記録の部分)。

1. 判定者: D-0 表1「体制と運用形態」の決定者(既定は事業決裁者。`phase4-process-design/deliverable-templates.md:209`、区分の変化点の決定者と同じ。`tailoring-guide.md:87`)。受託では**発注側**に置く。企画承認(G-1)とリリース決裁(G-8)は発注側に固定されており(`tailoring-guide.md:648, 655`)、最悪の帰結を決める用途の文脈を持つのは発注側だからである
2. 根拠の記録(全区分で必須): 構成要素ごとに (i) 想定できる最悪の故障の帰結、(ii) 1つ上の区分の判定基準に当たらない理由、(iii) 典型例(`tailoring-guide.md:838-841`)との照合、を書く。帰結は**対策を入れる前**の帰結で書く(外部 2.2 の FDA の型)。対策で下げる場合は、既存の「設計によって区分を下げる」の4要求の経路(`tailoring-guide.md:926-` の節)を通す
3. 確認者と段: 判定者と別の自然人が確かめ、段は判定した区分が外す要求で決める

| 判定した区分 | 外す要求(1つ上の区分) | 確認者の段 |
| --- | --- | --- |
| CL0 | CL1 の要求(3名以上、委任の禁止、G-6・G-7 の緩和の取り消し)。CL1 は段を求めない | 段1(1〜2名の体制では R-2 による) |
| CL1 | CL2 の要求(テンプレ9、附属書F、独立した安全性の評価の段2) | 段2 |
| CL2 | CL3 の要求(評価者の段3、承認者2名、L1 固定) | 段3 |
| CL3 | 外すものが無い | 段3(単調にするため。CL3 の採用者は段3 の評価者を既に持つ) |

4. 附属書F F.2 の安全関連部の切り分け(`phase4-process-design/safety-verification.md:52-60`)は、CL2 以上で独立した安全性の評価の範囲に含める。評価者(段2・段3)は既に置かれているため、新しい担い手を要しない
5. 届かない段は未達として表示する。理由を書いて低い段で代える経路は置かない(ADR-0088 決定2 と同じ)。AI の確認はどの段にも数えない

### 理由

- **循環を断つには、確認の段を判定の結果そのものから導かないこと**が要る(内部 6.3)。本案は「その判定が外す要求」から段を導く。判定を1つ下げると、外れる要求の分だけ確認が強くなる。低く付けるほど確認が軽くなる構造が消える
- 確認の強さを、判定の誤りの帰結に合わせられる。CL1 を CL0 と誤ったとき失うのは段を求めない統制(人数・委任・ゲートの緩和)なので、確認は段1 で釣り合う。CL2 を CL1 と誤ったとき失うのは段2 の評価なので、確認も段2 にする。**守りを外す判定を、外される守りより弱い確認で通さない**、という1つの原則で全区分を説明できる。現場は原則が1つなら覚えられ、例外の表を引かずに済む
- 単調にすれば「上位は下位を包含する」(`tailoring-guide.md:845`)を崩さない。内部 6.1 が案(c) について指摘した包含の崩れは起きない
- **確認は案件ごとに1回(と変化点ごと)であり、変更ごとではない**。G-6 のように PR のたびに外部の人を呼ぶ形とは手数の桁が違う。1枚の根拠の記録を読む作業は、受託の要件定義の打ち合わせ1回の中で終わる量である(現場の見積りであり**未実証**)。費用が小さいところで循環を断てるのに、断たない理由は無い
- 受託では、発注側が判定し受注側が確かめる(または逆)と、別の法人どうしの確認が追加の費用なしで成立する。受注側は、発注側の指揮系統の外にあり、リリースの権限(G-8 は発注側)を持たないので段2 に当たる。資源と指揮系統でも独立しているので段3 にも当たりうる(`overview.md:185-186` の定義から導いた推論。事例での確認は無い)
- 根拠の記録を必須にするのは、確認者の能力の不足を様式で補うためである。段は能力を測らない(前提の5つ目)。「1つ上の区分に当たらない理由」を書く欄があれば、用途を詳しく知らない確認者でも、「決済を含むのに CL0」のような典型の過少申告は読める。FDA は低い区分にも理由を書かせ、ソフトウェアを含まない機器にさえ「理由と結果」を書かせる(外部 2.2、付録 A 例1)。規格で調べたものに、最も低い判定を確認の外に置くものは無かった(外部 7)
- 対策前の帰結で書かせるのは、初回から対策を前提に低く付けると、既存の引き下げの4要求(ADR-0030)を素通りできるからである(内部 2.5「初回から低く判定した場合は根拠の記録が無く、検出の手掛かりが無い」)。対策前で書けば、下げたい者は引き下げの経路を通るしかない。その経路には ADR と受入基準の必須制約が残る

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| (a) 全区分に最上段(段3 以上)を課す(ISO 26262 の HARA の I3 と同型。外部 1) | CL0 の判定で失う守りは段を求めない統制であり、段3 を課すと確認だけが守りより重くなる。小さいチームでは CL0 の判定のたびに外部の確認者が要る。さらに、外部の1名は条件の上で段3 を満たしやすく、能力は保証しない。**距離を最上にしても、現場では「用途を知らない社外の知人の記名」が最も安い満たし方になり、形だけ満たす経路を作る**。信頼性を上げるのは距離の最大化ではなく、根拠の欄と、外す守りに見合う段である。また ISO 26262 の I3 の読みは翻訳草案で、EV-0180 と同じ制約を受ける(内部 1.4) |
| (b) 求めない | 循環が残る(内部 6.3)。小さいチームで最も強い動機(CL0 と CL1 の境)を、何も確かめずに通す。採らない |
| (c) CL0 の判定にだけ確認を求める | CL1 と判定して CL2 の要求を逃れる経路が残る(内部 3.2)。3名以上の組織では、こちらの動機の方が費用の上で強い。包含も崩れる(内部 6.1) |
| 段を判定とは別の属性(物理的な危険源の有無、規制への該当)で決める(外部 7 の案2) | 別の属性も判定者が答えるので、同じ循環が1段ずれるだけである。規制への該当は CL2 の判定基準そのもので(`tailoring-guide.md:840`)、別の尺度にならない |
| 型D「判定が無ければ最上位(CL3)とみなす」(外部 2.1 の IEC 62304) | 未記入のまま 1〜2名で初期化すると CL3 で拒否になり、利用者は根拠の欄を定型文で埋めて先へ進む。結果は「記録を必須にする」と同じで、失敗の形が悪い。**根拠の欠落は、欠落として止める**(R-4)。最上位の既定値は採らない |
| 確認者に資格・能力の要件を課す | 本標準に能力を測る仕組みが無い。ISO 26262 も評価者の資格証を求めない(外部 1.1・6)。根拠の欄で能力の不足を補う形にし、能力の要件は採らない |
| 理由を書けば低い段で代えられる | 小さい体制では全員が理由を書く(#318 の現場の意見と同じ。`research/318-deliberation/council-02-field.md:40`)。採らない |

### 条件・留保

- 段の割り当て(CL1 の判定に段2、CL2 の判定に段3)は「外す要求に合わせる」という本標準の推論であり、**未実証**。EV-0180 と同じく E1 以下で開示する(R-4)
- 受注側を確認者に数えるとき、発注側と受注側が「低い CL の方が安い」という同じ利害を持つ場合がある。段は利害を測らない(利害を見るのは段4 だけ。`overview.md:187`)。この共謀は本案では塞げない。残る穴として明記し、保証の開示に判定者と確認者の所属を出して、受け取る側が読めるようにする
- CL1 の判定に段2 を課すと、3〜9名の内製で全員が代表に直属する組織では、外部の確認者が案件ごとに1回要る。CL1 は未達のまま出荷しない区分なので、確保できなければ出荷が止まる。決済・与信の案件はふつう法務・監査の相手を既に持つので、確保は現実的と見る(現場の経験からの推論であり**未実証**)。既存の CL1 の採用者は、次の G-7 の時点で未達として現れるので、本文の反映のときに予告の期間を置くかを起草で決める(置く場合も、出荷を止める判断は先送りしない)
- 判定の確認は「評価・確認の活動」への段の追加であり、ADR-0088 決定1 の掛け先を広げる。決定2 は掛け先を2つに限る書き方なので、新しい ADR で3つ目を足す(採用済みの本文は書き換えない)

## R-2 1〜2名の体制と、組織の外の確認者

### 推す案

**1〜2名の体制の CL0 の判定は、チームの外の自然人が確かめる。確かめる者がいなければ止めずに未達として開示し続ける。根拠の記録の欠落は止める。**

1. 1〜2名の体制で CL0 と判定するとき、確認者は**名簿上のチームの構成員以外**の自然人とする(2名の体制の相手は確認者に数えない)。担い手の例は、受託の相手方(発注側または受注側)、顧問、別の組織の技術者、外部の評価者。名簿へ外部の確認者として登録する
2. 確認者を確保できない間は、CL の判定の確認を**未達**として表示する。CL0 なので出荷は止めない(ADR-0028 決定1〜3、`tailoring-guide.md:961` の「CL0 で規制業に該当しない案件だけ」が未達のまま運用できる)。表示先は PROCESS-PROFILE.md の冒頭、出荷の証跡、保証の開示。表示は「CL の判定: 判定者のみ。チームの外の確認なし」とし、判定者の名と根拠の記録の所在を添える
3. 根拠の記録(R-1 の2: 最悪の帰結・1つ上に当たらない理由・典型例との照合)の欠落は**止める**。最初のゲート判定(G-1)の前提条件に置く(R-4)
4. 外部の確認者の帯域は、変更ごとの R1 への集中(`tailoring-guide.md:232-247`)より先に、CL の判定の確認へ充てる。案件ごとに1回で、全部の構成の前提になるためである
5. 判定の見直しを D-0 の定期の見直し(四半期・ステージ移行ゲート・U1/Sev1 の事後レビュー。`deliverable-templates.md:501-506`)の項目に入れる。見直すのは「根拠に書いた用途・露出・扱うデータが変わっていないか」の1行で、変わっていれば変化点5 として再判定する。外部の確認者を再び呼ぶのは、区分を変えるか根拠を書き換えたときだけとする

### 理由

- **欠落の性質で扱いを分ける**。根拠を書くのは判定者本人の手で解ける。止めても詰まない。確認者を得るのは他人の手が要る。1名の体制で止めれば、本標準を捨てるか、相手がいる形に偽るかの二択になる。ADR-0030 が「引き下げの可否を個別の審査制にする」を退けた理由は「1〜2名の体制に審査の相手がいない」だった(`adr/0030-criticality-reduction-by-design.md:65`)。本案は同じ現実を認め、止めずに開示する。ただし「記録で検証する形」(同)だけでは循環が残るので、チームの外の目が入っていないことを隠さない
- **2名の体制の相手を数えない**のは、CL0 の判定が外すのが「3名以上」の要求そのものだからである。2名のどちらにとっても、CL0 と判定できるかでチームの存続が決まる(前提の1つ目)。同じ利害を持つ人の確認は、段1 の条件を満たしても、この判定の過少申告を止めない。R-1 の原則「守りを外す判定を、外される守りより弱い確認で通さない」を当てると、3名以上の要求を外す判定は、その3名の要求の外にいる人が確かめる必要がある
- 費用は小さいと見る。読むのは1枚の根拠の記録で、案件ごとに1回と区分の変化のときだけである。受託なら相手方が既にいる。個人開発でも、勉強会・業界団体・取引先の技術者に頼める量である(現場の経験からの推論。**未実証**)。G-6 のように変更ごとに外部を呼ぶのとは手数の桁が違う
- 1〜2名の小さい事業ほど、用途の転換(社内ツールから有償の外部提供へ、決済の組み込み)が速い。CL0 の前提が崩れる典型は、初回の誤りより、転換の後の放置である(内部 2.3「定期の CL 再判定の規定は無い」)。既にある D-0 の定期の見直しに1行足すだけで拾える。新しい会議を作らない

### 他の案を落とす理由

| 案 | 落とす理由 |
| --- | --- |
| 1〜2名の CL0 でも、チームの外の確認が無ければ出荷を止める | 他人の手が要る欠落で止めると詰む。詰んだ体制は、本標準を使わなくなるか、確認者を名目で登録する。名目の登録は、未達の表示よりも信頼性を下げる(未達は少なくとも事実を示す) |
| 2名の体制の相手の確認で足りるとする(R-1 の表の段1 のまま) | 上の理由。同じ利害を持つ相手の確認を数えると、表示の上では「確認あり」になり、受け取る側が過少申告の余地を読めなくなる。ただし相手の確認を**記録すること**は妨げない。数えないだけである |
| 外部の確認者を有償の評価機関に限る | 段は能力を測らず、有償かどうかも測らない。CL0 と CL1 の境の判定に要るのは、用途と規制を知っている人の目で、評価機関の認定ではない。費用が案件の規模を超え、確保できない体制が未達のまま固定される |
| AI による確認を、チームの外の確認として数える | AI の確認はどの段にも数えない(`overview.md:191`、ADR-0088)。AI は判定者の書いた根拠を前提に読むので、用途の取り違えを拾えない。代償措置として記録はしてよいが、未達を解かない(ADR-0028 決定6) |
| 1〜2名の体制では CL を既定で CL1 とし、CL0 を選ぶには外部の確認を要件にする | 確認を得るまで構成が初期化できず、1名の体制は初日に詰む。結果は「止める」案と同じ |
| 確認の有無を表示しない(開示に寄せない) | 1〜2名の CL0 では、外部の目が無いことを知るのは本人だけになる。受託の相手方・利用者が判断できない |

### 条件・留保

- 開示は止める力を持たない。1名の内製の SaaS で、保証の開示を読む利用者がいなければ、未達の表示は誰にも読まれない。**この穴は本案では塞げない**。表示はリリースごとに変わる件数ではなく案件の1行なので、「変わらない表示は読まれなくなる」(`tailoring-guide.md:245`)の問題も残る。見直しの1行(推す案の5)で、少なくとも四半期ごとに判定者本人の目には入れる
- 「チームの外」の判定は名簿で行う。2名の体制で、相手の家族・同じ会社の別の人を確認者に登録する形は止められない。段の判定(#357 の欄)で所属の法人を記録すれば、同じ法人の者を「チームの外」に数えない検査は書ける。#357 へ渡す
- 3名以上でも全員が CL0 の判定に利害を持つ(全員が代表に直属し、CL1 になれば予算が足りない)組織はある。そこへ同じ規定を広げるかは、本件の材料(1〜2名の人数の境)では決められない。3名以上には R-1 の段1 を当て、広げない。広げないことを明記する
- 外部の確認者の帯域の優先順位(推す案の4)は、EV-0054 の配分と並べて読めるよう、同じ節に書く

## R-3 テンプレ9 の要否と確認

### 推す案

**要否は第6章の4条件を正とし、軸E の表と規則データを第6章へ合わせる。テンプレ9 の確認は段1 を全件に求め、CL2 以上では独立した安全性の評価者が読む。製品の危害を下げた記録はテンプレ9 から外し、R-1 の CL の判定の記録へ移す。**

### 理由

- **エージェントの危害は製品の CL に依らない**。CL0 の社内ツールの開発でも、本番の資源へ到達できるエージェントは本番のデータを消せる。危害の大きさを決めるのは、エージェントの権限と到達範囲であり、製品の用途ではない。第6章の4条件はこの性質に合っている。軸E の「CL0・CL1 は不要」は、HARA とテンプレ9 を同じものと読んだ誤りに見える(内部 2.4 X-c と同じ読み)
- 小さいチームほど、1人で本番の資格情報を持ったままエージェントを L2(複数機能の並行実装、`human-ai-boundary.md:62`)で回す。第6章の条件に当たる案件は、CL0 の小さいチームに多いと見る(現場の観察からの推論。**未実証**)。今の規則データはそこでテンプレ9 を一度も出さない(内部 5 の補足)。**最も要る体制に、最も届いていない**
- 質問を4つ足さないのは、利用者が初期化の時点で自分のエージェントの権限を正確に答えられないからである。L2 か否か、本番に届くか否かは、使い始めてから変わる。既定を「必須」にして、外すときに理由を書かせる方が、答えの誤りが安全側に倒れる。軽量版は1ページ(`deliverable-templates.md:1842`)で、記入の手数は小さい
- 承認を段1 に留めるのは、テンプレ9 が区分を外す判定ではないからである。テンプレ9 は危険源と低減策の表で、書いた結果で守りが外れるのは SR の判定だけである。SR2 以上の残留リスクの受容は既に R1 の決定として決裁者が要る(`deliverable-templates.md:1737`)。CL2 以上では評価者が既にいるので、その人に読ませれば段2・段3 の目が追加の費用なしで入る。#318 の起案の委員が R-1 案で「評価者と同じ段以上」をテンプレ9 に掛けた(内部 3.2)のと結果は同じになるが、確認者を新設しない分、小さい組織でも届く
- 1名の体制で独立した承認者の欠落で G-1 を止めると、利用者は自律レベルを L1 と申告して適用条件を外す。これは R-1 と同じ循環で、止めるほど申告が偽られる。止めるのは、本人の手で解ける欠落(表が無い、SR4 が残る)だけにする(R-2 と同じ原則)
- 製品の危害の低減をテンプレ9 に書かせると、エージェントの表に製品の欄を足すか、欄が無いので書かれないかのどちらかになる。現場では後者が起きる。製品の最悪の帰結を書く場所は、CL の判定の記録の1か所に集めた方が、見る人も見る場所も1つで済む
