## 0. 結論の先出し

1. **「未達を残した出荷」を許す規格は、例外なく「誰が許したか」と「何を許したか」の記録を求める。承認者の水準を、リスク・規制で変える仕組みは、規格より FDA・航空の実務の側に見える。** ISO 9001 は水準を変えず、権限者の特定だけを求める[二次]。IEC 62304・FDA・航空は、既知の異常の評価と開示を求め、リスクの高い欠陥は直してから出す側に倒す[二次]
2. **「CL1 以上・規制業の未達は出荷しない」(IMPL-0738)に直接当たる規格の条文は、見つけていない。** 近い先例は、(a) FDA の実務で「高リスクの欠陥は直す、低リスクは次版へ繰り延べ」[二次・会議報告]、(b) 航空の OPR(未解決の問題報告)の管理で、申請時に長い未分類の一覧を出すこと自体を問題視する指針[二次]。止める条件を安全水準で変えること自体は、先例と整合する(考察)
3. **承認の数え方は、実務の規範が「別の人」「最終版に対する承認」の2点に収斂している**(SLSA v1.2 [一次]、GitHub [一次])。GitHub のスタック型 PR は、**各層を「スタックの基底に対する規則」で評価する**と明記しており、IMPL-0498 の前提(base.ref だけでは区別できない)の読みに使える。ただし、承認が rebase の後も残る条件が、公式文書に書いてある
4. **類似度・一致の閾値を判定に使う実務は、閾値を「候補を絞る」ために使い、「合否を決める」ためには使わない傾向がある**(トレーサビリティ復元の研究、近似重複検出)。閾値の値は、対象の集合ごとの較正が前提で、固定値を規範に置く先例は見つけていない
5. 読んだ範囲に無かったもの: ISO/IEC/IEEE 12207・15288・CMMI の本文、IEC 62304 §5.8 の本文、ISO 9001 §8.6・8.7 の本文、ISO 26262-2 の独立性の表。**これらについて「規格はこう定める」と断定できる材料は、今回無い**

## 1. 問い1: 未達の項目を残したまま出荷する判断

### 1.1 ISO 9001 の不適合の管理(8.6・8.7)

- 8.7.2: 次を記録として保持する。a) 不適合の記述、b) とった処置、c) 得た特別採用(concession)、d) 不適合への処置を決める権限者の特定[二次。本文を再掲したページによる](https://centauri-bg.blogspot.com/2016/08/interpretation-of-iso-90012015-cl87.html)(補強: [thecoresolution](https://www.thecoresolution.com/clause-8-7-2-iso-9001-2015-explained))
- 8.6(リリース): 合否基準への適合の証拠と、**リリースを許可した者への追跡可能性**を記録として保持する[二次]([9000store](https://the9000store.com/articles/documented-information-required-by-iso-9001/)、検索結果の要約)。「計画した取決めが完了するまでリリースしない。ただし関係する権限者(および該当すれば顧客)が承認した場合は除く」という趣旨の文があるはずだが、**本文を確かめていない(筆者の記憶。要確認)**
- 特別採用は「正式に権限を与えられた者」が行う[二次]([certbetter](https://certbetter.com/blog/guide-to-iso-9001-clause-87-control-of-nonconforming-outputs))。審査員向けの学習教材は、特別採用の承認者の記録の欠落を 8.7 の不適合指摘で最も多いものとする[二次・学習教材。裏付けは弱い]([open-exam-prep](https://open-exam-prep.com/study-guides/cqi-irca-qms-lead-auditor/clause-8/clause-8-release-nonconforming))
- **リスク・規制の水準で承認の厳しさを変える規定は、読んだ範囲に無い。** 承認者は「権限者」と書かれるだけで、人数・独立性は規定されない(二次)。未解決: 8.7.2 が「是正して解消した不適合」まで記録を要するかは、権威ある答えを見つけていない

### 1.2 IEC 62304 と医療機器ソフトウェアの既知の異常

- 5.8.2 は残存する既知の異常の文書化、5.8.3 はその評価(リスク)と読める。コンサルタントの対応表は 5.8.3 を「B・C のみ」と書き、別のチェックリストは「A・B・C」と書き、**自分たちの資料の間で食い違う**[二次]([openregulatory 対応表](https://openregulatory.com/articles/software-release-iec-62304)、[既知の異常の一覧の雛形](https://openregulatory.com/document_templates/list-of-known-anomalies))。クラス別の適用は本文で確かめる必要がある
- 実務: 既知の異常ごとにリスク分析を行い、リスク表へ記録する。出荷の可否の確認項目に「既知の異常のリスクを評価した」を置く。一覧は「直さないと決めた欠陥と、その理由」の記録である[二次・同上]
- FDA の実務(MedCon 2026 の発言の要約): 異常は品質システムに記録しリスクを評価する。**高リスクなら修正と検証・回帰試験、高リスクでなければ次版へ繰り延べてよい**。未解決の異常の追跡を期待する[二次・会議報告]([RAPS](https://www.raps.org/resource/medcon-fda-industry-experts-discuss-best-practices-for-managing-software-defects-anomalies.html))
- FDA「General Principles of Software Validation」(2002 年 1 月)は、未解決の異常を扱う節と、異常の報告・解決の手順の整備を持つ[二次・目次と要約。本文は未読]([FDA 掲載の PDF](https://www.fda.gov/media/73141/download))。出荷判定に誰が署名するかの文言は確かめていない
- **含意の核**: 医療機器の実務は「未達を持ったまま出す」ことを禁じず、**記録・評価・理由を求め、リスクが高いものだけ止める**。この構造は IMPL-0738 の「CL1 以上は止める」と同型だが、止める条件の根拠(リスクの高低)は個々の欠陥ごと。本標準の案は案件の CL で一括して止めるため、粒度が荒い(考察)

### 1.3 ISO 26262 と航空(DO-178C)

- ISO 26262-2: 確認措置(confirmation review・監査・機能安全アセスメント)の完了が「量産へのリリース」(6.4.13)の判断の前提になる。独立性は ASIL で上がり、資源・管理・**リリース権限**の独立が論じられる[二次]([Synopsys 白書](https://www.synopsys.com/content/dam/synopsys/automotive/white-papers/automotive-iso26262-confirmation-measures.pdf))。**未完了の確認措置を残したリリースの可否と、リリースの署名者は確かめられなかった**
- 航空: DO-178C は、未解決の問題報告(OPR)を SAS(ソフトウェア達成要約)に載せることを許す。FAA の AC 20-189 / EASA の AMC 20-189 は OPR の管理を扱い、**申請時に未分類・未解決の OPR の長い一覧を出すことを問題視する**[二次]([patmos-eng](https://patmos-eng.com/?p=621))。分類(安全・機能など)の枠は古い通達の例[二次・Wikipedia 下書きの紹介]。公式の通達の本文は未読

### 1.4 ISO/IEC/IEEE 12207・15288、CMMI、DORA

- 12207・15288: 検証・妥当性確認が 2017 版の 6.4.9・6.4.11 に置かれることは目次で確認できた[二次]。**独立性の文言と、判定の意思決定プロセス(15288 の決定管理)の文言は確かめられなかった**。さらに、検索結果は 12207 の「2026 年版」の存在を示す記述と矛盾する。2017 版の箇条番号を引く前に最新版を確かめる
- CMMI V2.0: 検証・妥当性確認(VV 3.1「基準を整備して使う」、3.2「結果を分析し伝達する」)とピアレビュー(PR 2.x、3.1)の実践の名称は確認できた[二次]。**例外・既知の欠陥を持った出荷の承認を定める実践は、見つけていない**(公式のモデルビューアは未読)
- DORA: 外部の承認(CAB など)は、変更失敗率の低下と関連しなかったという。重い承認は配信を遅くする傾向。**規制対応の目的(承認の証拠)は認めており、代替としてピアレビューを開発基盤に記録する形と、高リスクの変更を早く検出して追加の審査にかける形を勧める**[一次]([DORA: streamlining change approval](https://dora.dev/capabilities/streamlining-change-approval/))。「全変更を同じに扱うな」という趣旨が明記されている。外部承認の影響を数値で示す記事(2.6 倍など)は二次の引用で、DORA 自身の報告で確かめていない
- **規制業の特例を DORA は述べていない**。DORA の研究責任者の発言として、業種が配信性能の予測因子になることは稀とする二次の引用がある(未確認)

### 1.5 問い1の本標準の案への含意(考察)

- 止める条件を、リスクや安全の水準で変える先例はある(FDA の実務の高リスク/低リスク、DORA の高リスクの変更の追加審査、ISO 26262 の ASIL による独立性の上昇)。**ただし、規格の条文として「安全の水準が X 以上なら未達の出荷を禁じる」と書いたものは、読んだ範囲に無い**。IMPL-0738 を「新しい義務」として扱う重の判断は、外部の先例の有無からも妥当
- 記録の項目(何が未達か、評価したリスク、誰が許したか、期限)は、ISO 9001 8.7.2・IEC 62304 の実務・FDA の実務で一致している。本標準の例外承認の記録(R1)と同じ型である
- 「CL で一括して止める」案は、先例の粒度(欠陥・不適合ごとのリスク評価)より荒い。F4(CL1 以上の未達が止まらない穴)を埋める場合でも、**止める対象を「未達のゲート」とするか「未達のうちリスクが評価されていないもの」とするか**は、外部の先例からは決まらない。所有者・会議体の判断になる

## 2. 問い2: 層が重なるときの承認の数え方と独立性

### 2.1 GitHub のスタック型 PR(IMPL-0498 の前提)

- 公式文書: スタックの各 PR は、**直下のブランチではなく、スタックの基底(trunk)の規則で評価される**。必須のレビュー・必須のステータスチェック・コードスキャンは基底に対して評価される。「スタックの途中の PR も、最下層と同じ水準を求められる」[一次]([GitHub Docs: Stacked pull requests](https://docs.github.com/en/pull-requests/reference/stacked-pull-requests))
- CODEOWNERS も基底から評価される[一次・同上]
- マージ: ある PR は、基底の要件を満たし、**かつ下のすべての PR も要件を満たす**ときに限りマージできる。線形の履歴が前提。バイパス規則を使うと、最下層の PR しかマージできない[一次・同上]
- 承認の維持: 「差分が変わらない rebase は新しいレビュー対象のコミットに数えない」ため、「古い承認を却下する」規則が有効でも**承認は維持される**[一次・同上]。下の層へ変更を push した場合などに線形の履歴を失い、cascading rebase で戻す[一次・同上]
- 公式文書に書かれていない点: 公開(プレビュー/一般提供)の状態。強制 push と retarget の扱い。**検索結果では GitHub の変更履歴(2026-10-06)が一般提供を伝える一方、gh-stack の頁は private preview と書き、食い違う**[二次]([変更履歴](https://github.blog/changelog/2026-10-06-stacked-pull-requests-generally-available))
- 含意(考察): 公式の挙動は、**スタックの標準の機能で作った層では、各層が「基底の規則」で承認を求められる**ため、「中間の層を取り込んだ差分に 1 件の承認」が全層を通ることは、標準の機能では起きにくい。起きるのは、(a) 手動のスタック(base.ref が中間のブランチ)、(b) squash で層をまとめる運用、(c) 保護の無い中間のブランチへのマージ、である。受付の F5(手動・squash は検出、rebase の見逃し)と整合する。**「差分が変わらない rebase は承認が残る」という仕様は、F5 の見逃し(中間の取り込みの後の Y の rebase)を、GitHub 側では「承認の維持」として扱っていることを意味する**。式で見逃しを閉じるか、開示にとどめるかは、会議体の論点

### 2.2 SLSA(Source track、一次)

- v1.2 Level 4「二者のレビュー」: 保護ブランチの変更は、事前に **2 人以上の信頼される人が合意する**。組み合わせは「提出者とレビュー者が別の信頼される人」または「別の 2 人のレビュー者」[一次]([SLSA v1.2 Source requirements](https://slsa.dev/spec/v1.2/source-requirements))
- 「信頼される人」は、変更を提案し承認する権限を組織から与えられた**人間**。信頼されないものは承認できない[一次・同上]
- **最終版に適用する**。レビュー中にさらに変更したら、その変更もレビューする。承認は特定の文脈(リポジトリ・ブランチ)に結びつく。別の文脈へ移した内容は、改めてレビューが要る[一次・同上]。これは IMPL-0498 の趣旨(層ごとの確認)と同型の規範
- 信頼されるロボットは、組織が方針の恒久の例外を与えられる(例: Dependabot)[一次・同上]。v1.1 は「1 人に複数のアカウントを持たせない」を求めていた(二次の検索結果の要約。v1.2 の頁は複数アカウントに触れていない)
- 脅威モデルは「文書は例外」のような例外を作ると悪用されるため、例外を設けないことを勧め、**ロボットが作った変更も 2 人のレビューを要する**とする[二次・検索結果の要約]([SLSA threats](https://slsa.dev/spec/draft/threats))

### 2.3 同一人物の兼任と four-eyes

- GitHub: 「最新のレビュー対象の push を、push した人以外が承認する」設定がある。以前のレビュー者が再承認すれば満たせる[二次・検索結果の要約]([About protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches))。自分で push した版の自己承認を機械で止める手段である
- DORA: 職務分離のためのピアレビューを開発基盤に記録する。規制の規則は「変更は作成者以外が承認する」[一次]([DORA](https://dora.dev/capabilities/streamlining-change-approval/))
- SOC 2 の実務(二次): 開発した者と本番へ出す者を別にする、作成者以外のレビュー者の承認を branch protection と CODEOWNERS で強制する。監査人は期間内の変更を抜き取り、依頼から出荷まで追う。**小規模な組織は、職務分離が現実的でないとき、検知的な統制(通知と記録)で代える例がある。他方、PR を要件としない形で SOC 2 Type II の報告書を得た例もある(監査人・期間は不明)**。いずれも監査法人・ベンダーのブログで、AICPA の基準本文は未読(検索結果の要約)
- PCI DSS 4.0 の 6.5.1(変更の承認)・6.5.3(事前環境と本番の分離): 開発と本番の分離は、アクセス制御で強制する。**作成者と承認者を分けるという文言は見つけていない**[二次]
- OpenSSF Scorecard の Code-Review: 承認があるか、マージした者が作成者と異なる(暗黙のレビュー)コミットを数える。bot の変更は別に扱う。**参加者が 1 人のプロジェクトでは全変更のレビューは現実的でないと、文書自身が認める**[二次・検索結果の要約。公式の checks.md は未読]
- NIST SP 800-53 AC-5: 分離すべき任務を特定し、文書化し、それを支えるアクセス認可を定義する。目的は権限の乱用と共謀なしの悪意の活動の低減[二次]。ISO/IEC 27001 付属書 A 5.3 は**本文を確かめていない**
- 既存の出典(台帳): COSO の生成 AI 補足ガイダンスは、職務分離を「AI の設定を構成する権限」と「出力を承認する権限」に分ける(SRC-0535)。SOX の実務者ブログは、AI を職務分離の二者の一方に数えてよいかを問い、**目的が正確性の二重確認なら AI が担い得る**とする(SRC-0540)。IEC 61508 の機能安全アセスメントの独立性は、人・部門・組織の三段(SRC-0677・0678)

### 2.4 ISO 26262 の独立性

- 独立性は ASIL で上がり、レビュー者・監査人・アセッサのいずれでも段が上がる[二次]。段の対応表(I0〜I3 など)は、**ブログの表が定義を取り違えている疑いがあり、確かめられなかった**。表の値を本標準の根拠に引かない

### 2.5 問い2の本標準の案への含意(考察)

- **承認の数え方の共通項は 3 点**: (1) 承認者は作成者と別の人間、(2) 承認は最終版に対して有効で、後から変えた分には改めて必要、(3) 承認は特定の文脈(ブランチ)に結びつき、別の文脈へ移した内容は改めて要る。IMPL-0498 の「中間の層を取り込んだ差分への 1 件の承認を、層ごとの確認に数えない」は、(3) に当たる。SLSA の規範に近い
- 3 名の同一人物の承認を記録つきで受ける既存の決定(MEMORY の suite fixture)は、「人間であること」「別人であること」を強く求める SLSA・SoD の主流とは緊張関係にある。ただし、GitHub の「push した人以外が承認」や、DORA の「作成者以外が承認」は、**1 人の組織を想定していない**。小規模な組織が検知的な統制で代える例(SOC 2 の実務の二次)、Scorecard の「参加者 1 人では現実的でない」という自認は、**兼任を完全に禁じるのではなく、記録をもって開示する形の先例**になる。本標準は後者を採っている。この線引きは変えない前提で、重の審議では確認のみ
- AI のレビューを承認の数に入れるかは、規格の条文では決まっていない。SLSA は「信頼される人」を人間に限り、ロボットの例外は組織が方針として与える。COSO と SOX 実務者の見解(SRC-0535・0540)は、AI が担い得る任務と、設定権限を分ける点を挙げる。**「AI を承認の数に入れない」本標準の立場は SLSA と整合**する(考察)
- 「層ごとの承認の有無」を式へ入れる設計は、GitHub が標準で各層を基底の規則で評価する以上、**GitHub 側の設定(必須のレビュー)が正しければ、手動のスタックの検出以外に、本標準が重ねて数える必要は薄い**可能性がある(考察。F6 の「ship-evidence の verify は必須でない」ことと併せて検討)

## 3. 問い3: 判断記録と実装の一致の機械の検査、類似度の閾値

### 3.1 既存の規格の位置づけ

- 台帳・調査 TH08: IEC 62304 修正票1 §5.7.4 は、全要求の検証済みの確認・トレーサビリティの記録・合否基準の充足を別項目として課す。ただし**対応の有無の確認と内容の判定を分けて、機械の検査を独立のゲートとする条文は確認できていない**。機械化は、出力の独立検証かツールの認定を条件に認められる(FND-0237、`research/282-survey-2026-09/themes/TH08-spec-traceability-assumptions.md`)。ISO 26262・DO-178C・IEC 62304 本文は未読
- 本問のために新しく見つけた規格の条文は無い。**「判断記録(ADR など)と実装の一致」を機械で検査することを規定した規格は、読んだ範囲に無い**

### 3.2 閾値の実務

- トレーサビリティ復元(情報検索による候補リンクの生成): 再現率 90% で適合率が 5〜30%、研究によっては 40% 未満、10% 未満になる。この分野は「再現率を優先して候補を出し、**分析者が各候補を確認して採否を決める**」形を取る。分析者は出力を最終結果として受け取らない[二次・検索結果の要約]([Hayes らの研究ほか](https://www.cs.wm.edu/semeru/tefse2011/papers/p58-dekhtyar.pdf))。閾値の選び方を直接扱った研究は見つけていない。固定の個数(上位 10 件)で報告する研究もある
- 近似重複の検出(SimHash): 8 十億ページの規模で、64 ビットの指紋・ハミング距離 3 以下が妥当とする報告。**値は対象の集合での検証から出た値であり、一般の規範ではない**。適合率・再現率の数値は今回見つけていない[一次の論文の要旨と二次]([Manku ら 2007](https://www.www2007.cpsc.ucalgary.ca/papers/paper215.pdf))。ライブラリの文書も「閾値は対象による」とする
- 埋め込みの類似度・LLM 判定: 埋め込みのコサイン類似度の閾値は、符号化器ごとに意味が変わり、**ラベル付きデータで較正しないと合否線に使えない**。論理的に矛盾する文を近いと採点しうる。LLM を判定者にする場合は、2 者の判定に第 3 者を加える手法などがある。専門家との一致は完全ではなく、プロンプトの様式や文体の偏りに敏感[二次・実務者のガイドと予稿]([MLflow](https://mlflow.org/articles/semantic-eval-metrics/)、[CLEV](https://arxiv.org/pdf/2503.08542.pdf)、[EACL 2026](https://preview.aclanthology.org/ingest-eacl/2026.eacl-long.182.pdf))
- いずれも「2025〜2026 年の学術的な合意」とまでは言えない。検索結果の要約で、原論文の本文は一部しか読んでいない

### 3.3 問い3の本標準の案への含意(考察)

- 規格・実務に共通するのは、**類似度や一致の指標は「候補の絞り込み」と「人の確認の優先順位づけ」に使い、「合否の最終判定」には人の確認を挟む**形である。IMPL-0990 の案 A(一致の失敗化)は、閾値の根拠の面で先例に乏しく、案 C(機械の列を「しない」、人の列を「判定する」へ改める)は、実務の型と整合する
- 案 B(所見にする)は、実務の「候補を出して人が確認する」型に近い。ただし、IMPL-1022 や b1-decision の経緯が示すように、所見が読まれる保証は規格にも実務にも無い。**読まれる保証をどう作るか(必須のレビューの項目にするか)は、外部の調査から決められない**
- 閾値を使うなら、(1) 対象の集合での較正、(2) 偽陽性・偽陰性の開示、(3) 閾値の変更の記録、が先例の最小限。本標準にはこれを満たす実証が無いため、閾値を置く案は根拠水準マーク(ADR-0026)での開示が前提になる(考察)

## 4. 日本の企業文化(建前と実運用の乖離)

- 本調査で、日本の企業文化に特化した一次情報は見つけていない(検索は米国向けの設定。日本語の出典は引いていない)
- 一般の傾向(二次): 承認の記録が「形式的な押印」に流れる問題は、ISO 9001 の審査員向け教材が「承認者の記録の欠落が最多の指摘」と述べる点に、間接的に現れる。日本固有の根拠ではない
- 追加調査が要る: 稟議の「合議」の数え方(複数の押印が独立の確認に数えられるか)、J-SOX の実施基準での職務分掌の記述
