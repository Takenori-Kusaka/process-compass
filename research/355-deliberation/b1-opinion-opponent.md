# #355 束1 反対委員の意見書(IMPL-0043・IMPL-0132・IMPL-0042)

作成日 2026-11-15。起案委員の案は見ていない。コード・本文は変更していない。判断軸は信頼性。実行で確かめた点には「(実行)」、読んで推した点には「(読解)」を付ける。実証を欠く点はそう書く。

## 0. 受付の裁定への異議

- 横断の方針1(存在・非空を delivered と呼ばない)に異議は無い。ただし `check=presence` は「規則を運ぶ単位の有無まで」と定義されている(implementation-marking.md「検査の手段」)。規定の文が「完備」「欠落 0 件」のとき、`state=delivered check=presence` は規約の語彙の上では書ける。規約の語彙が許すことと、規定の文が求めることは別である。**表示が許されても、規定の文が内容を求めるなら delivered にしない**を、束の裁定に明記することを求める
- 方針4(`review=2026-11` の更新)は、束1 で降ろさず残すマークがあれば、見直しの年月を議長が決める。今月で切れるので、更新を忘れると「期限切れの表示」と「実態」が食い違う。0042 を残す場合は必ず付ける
- 0132 の `issue=289` から `issue=355` への付け替えは編集の指摘として妥当。ただし、付け替えの前提(寄せ先の Issue が担い手として合っているか)は機械で確かめない規約(確かめる者: 付け替える者)。#289 側のコメントに寄せるマークと受け入れ条件の案を足したかを、実装時に確かめること

## 1. 規定ごとの、決定可能な部分と決定できない部分

### 1.1 IMPL-0043(G-7 基準4「完備(監視項目・障害時連絡先・復旧手順)」)

規定の文は「完備」。現行は `docs/handover.md` の有無だけ(aggregate-evidence.mjs L3245・criteria[4] の `partial`)。

| 部分 | 決定可能か |
| --- | --- |
| 3項目に当たる節が在る | 在る。ただし**対応づけが標準と様式で食い違う**(下記) |
| 節の本文が空でない | 構文として決定可能。ただし様式の初期文を非空と数える |
| 3項目の内容が完備(監視の閾値が書かれ、連絡先が実在し、復旧手順が動く) | 決定できない |

偽の合格(実行): `template/templates/05-handover.md` を未記入のまま節ごとに数えた。見出しは「4. 監視」「3. 動かしかた」「5. よくある障害と対処」「6. 外部依存」。**未記入の様式そのものが、「実質の行」を節3 に 4 行、節4 に 2 行、節5 に 2 行持つ**(表の区切り行と見出し行を除いても、節3 の「切り戻し」行の説明文、節5 の最終列の初期値「AI(判断は人)」が残る)。「空でない行が在る」を基準にすれば、**何も書いていない様式が合格する**。「表のデータ行に非空のセルが在る」でも、節3・節5 は同じく合格する。節4 だけが空の表になる。

偽の不合格・対応づけの食い違い(読解):
- 標準テンプレ5(deliverable-templates.md)の見出しは「監視項目」「障害時の連絡先・体制」「復旧手順」。様式は 05-handover.md で番号つきの別の見出しになり、`src/data/template-fields.yaml` が `監視項目→監視`、`復旧手順→切り戻し`(部分一致)、`障害時の連絡先・体制→5. よくある障害と対処` を対応づける。連絡先は、実際には節4 の「誰へ通知するか」と節6 の「連絡先」列にもあり、節5 には連絡先の列が無い。**標準が「障害時連絡先」と呼ぶものの置き場が、様式の中で一意でない**。見出しの語で検査すれば、連絡先を節6 に書いた正当な文書が不合格になり、節5 の「一次分析の担当」だけで合格する
- 「復旧手順」は様式では節3 の「切り戻し」行。節3 全体が空でないことを見ても、復旧(切り戻し)の記載の有無にならない
- 正当な「該当なし」: 外部依存が無いシステムの節6 は空でよい。3項目の検査には含めないが、節の対応づけを誤ると巻き込む

→ **決定可能な部分は「3項目に当たる節が、様式の対応づけどおりに在り、初期文(様式の既定の文)以外の記入が1つ以上ある」までで、これは完備ではない**。

### 1.2 IMPL-0132(G-3「記載の検査」の4検査)

規定の文(gate-criteria.md L615〜619)は、機械が「検査する」と明記する4行。標準自身が内容の妥当は検査しないと切り分けている(L620)。したがって 0043 と違い、**規定の文が機械の検査を求めており、存在・構文の範囲に収まる**。ここは降ろす側に理がある。

| 検査 | 決定可能か |
| --- | --- |
| 欄が空 | 決定可能。ただし「欄」の範囲の定義が要る(事業影響の5項目か、全欄か。基準5 は事業影響欄5項目を指す) |
| 回復に要する時間が単一の値 | 「幅」の構文を定義すれば決定可能。定義が窓口になる |
| 兆候が「なし」 | 完全一致なら決定可能。言い換えを拾えない |
| 前の判断記録と記述が一致 | 「前」の定義(番号順か、同じ決定者か、同じ変更種別か)と「一致」(全文一致か類似度か)が先。標準に定義が無い |

偽の合格・不合格(実行。簡易な正規表現で試した):
- 「回復」: 「2時間(30分〜4時間の見込み)」は幅と判定される(実質は点推定に幅の注を足したもの)。「1時間以内」「約1日」「半日程度」は単一と判定される(上限だけの値を幅と数えるかは標準に無い)。「30分〜2時間」「数分から数十分」は幅
- 「兆候」: 「なし」は落ちるが、「特になし」「該当なし」「N/A」「TBD」「—」「なし(自動で戻せるため)」は通る。完全一致で閉じると言い換えで抜ける。部分一致で閉じると、「更新がなしのまま」のような正当な文を落とす
- 欄が空: 様式を写して初期文(「何を観測すれば誤りだったと分かるか。『なし』と書かないこと」)を残した記録は、非空として通る
- 「前の記録との一致」: 定義が無いまま全文一致にすると、定型の理由を1語変えれば抜ける。類似度の閾値を置けば、**値の根拠が無い**(暫定の値であり、暫定 EV で開示が要る)。そのうえ、複数の ADR が正当に同じ「影響を受ける利用者」を書く(同じ機能に関わる決定)場面で偽の FAIL が出る

既存の判断記録への当て込み(読解・一部実行): このリポジトリの `src/content/docs/adr/` は「回復に要する時間」の欄を持たず(grep で 0024・0040 の言及のみ)、template の `context/decisions/` は README.md だけで実例が無い。**偽の FAIL を出す入力は、template 側の実例が無く試験を作れない**。試験は合成した記録で書くことになり、実際の採用者の記録でどうなるかの実証は無い。

### 1.3 IMPL-0042(G-7 基準3「記録漏れ 0 件」)

規定の文の核は「受容した負債が台帳に載っている」。**記録漏れは、定義上、台帳に無いものである**。台帳を読む機械は、台帳に無いものを見られない。

- 現状の結合: 区分「例外」は「対象」に PR 番号を書く形で既に PR と突合される(aggregate-evidence.mjs L2403〜2477。研究メモ)。区分「負債」「未解決」の「対象」は「—」でよい(03-debt-ledger.md の欄の書き方)。結合キーが無い
- 標準が既に求める欄だけで結合できるか: **できない**。「対象」を負債にも必須にすると、**03-debt-ledger.md の欄の書き方(「負債」「未解決」の行は「—」でよい)を逆転させる**。これは採用者への新しい記入義務であり、標準の様式の変更(template-fields.yaml の対応と ADR-0040 の双方向の検査にも波及する)
- 他の経路: PR のチェック項目(.github/PULL_REQUEST_TEMPLATE.md L155)の有無と、台帳の行数の増加の突合(研究メモの (c))は、「チェックを付けた PR ⇒ 台帳に行が増えた」を見る。だが偽の合格: **無関係な行を1つ足した PR が通る**。偽の不合格: 負債が無い PR にチェックを付けなかった場合は検査対象外なので問題が出ないが、チェックを付けて台帳を直前の PR で先に書いていた場合は落ちる。そもそも、チェックを付けない妥協(記録漏れの本体)を見ない
- 機械に降ろすと何が起きるか(読解): 「検査が緑 = 記録漏れ 0 件」と読まれる。実態は「チェックを付けた PR については台帳の変化が在る」だけである。**チェックを付けなかった漏れが、緑の検査の下に隠れる**。表示と実態が食い違う「高」の類型であり、巡の数に関わらず直す対象になる

## 2. IMPL-0043: 見出し・非空の検査を delivered と呼べるか

呼べない。規定の文は「完備」。表の注は「『記録漏れ 0 件』『欠落 0 件』『完備』は記録の完備を求める要求」と明記している(L1429)。見出しと非空の検査は「3項目の節に初期文以外の記入が在る」までで、完備を確かめていない。#333 の先例(IMPL-0243・0521)は、規定の文が**自然に2つに分かれる**ときにだけマークを分けた。0043 の文は「完備(3項目)」の1文であり、「記載が在る」と「完備である」に分ける切れ目が文に無い。切れ目を作るには標準の文を書き換える必要があり、それは条項の改廃で束1 の範囲を超える。

## 3. 重へ上げるべき点

1. **IMPL-0042**: 「対象」を負債にも必須にする案は、採用者への新しい義務であり、03-debt-ledger.md の欄の書き方を逆転する。重。受付の裁定どおり、束2 へ移す(あるいは採用しない)
2. 0132 の「前の記録との一致」を機械の検査にするなら、「前」と「一致」の定義と閾値は新しい基準の設定であり、実証の無い値になる。軽の範囲を超える場合は、この1検査だけを重へ上げるより、**マークを分けて manual に残す**ほうが適切
3. 0043 を完備まで機械で閉じると標準の文に書く案は、条項の改廃で重
4. 安全に当たる点は、束1 には無い(G-7 基準7 は別の規定)

### 偽の安心の観点からの付記

- 0132 を delivered にする場合でも、`machine` の3要件(違反と適合の対の試験)を満たすこと。合成した記録での試験しか作れない点は、根拠水準マーク(暫定 EV)で開示する。実際の採用者の記録で偽の FAIL が出るかは、実証が無い
- 0043 の所見を足す場合、集約の出力の表現を「完備」「合格」と読める文にしない。「3項目の節に記入が在る」と書く
- 実行で確かめた範囲は、簡易な正規表現と様式の行数の数え上げに限る。check-decisions.mjs への実装は試していない(読むだけの約束のため)
