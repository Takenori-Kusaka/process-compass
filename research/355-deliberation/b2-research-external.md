# #355 束2 外部の調査(0045・0044・0046・0042・0136・0981)

調査日 2026-11-17。担当は外部の調査。内部の調査は別の担当。標準の条項は変えていない。含意は「会議体に渡す問い」の形で書く。
新しい出典は SRC-0780〜0784(仮番号。0757〜0759 は別の作業が仮に使っているため 0780 から振った。push の前に付け直す)。既存の出典は SRC-0437・0467・0466・0525・0527・0751・0755・0756 を使った。

## 0. 結論(先に)

1. **安全の検証記録(0045)**: 規格は、検証を計画し、結果を「合格か、失敗の理由か」を示して文書にし、強く推奨(HR)の技術を採らないときは理由を詳述させる。これは附属書 F.7 の項目と同型で、F.7 は規格より重くない。ただし規格はどれも「記録の置き場の様式」を定めない(IEC 62304 の FAQ は、分類の記録の仕方は製造者が決めるとする)。**項目の存在・非空・理由つき「該当なし」を機械の検査にし、中身の妥当性は人の確認とする分け方が、世の中の実務と整合する**。
2. **類似の検知(0046)**: 実務は「公開コードとの一致を出所とライセンスつきで示す」道具(Copilot の code referencing、SCANOSS、Black Duck 等)で、**合否に使わず、一致を人が判断する**形である。ベンダー自身が止めない(coding agent は Block 非対応)。法の面は未確定(Doe v. GitHub は DMCA 1202(b) の請求を退けたが、契約違反は係属)。日本の文化庁の整理では、学習していれば依拠性は通常推認され、**利用者側に責任が残る**。「検知の実施の記録」を求める根拠はあるが、「検知で止める」根拠は世の中に無い。
3. **SLA の判定(0136)**: 規格(ISO/IEC 20000-1)は SLA の目標を測定可能にし、監視・見直し・報告し、未達のとき処置を取ることを求める。判定の記録の置き場は定めない。レビューの速さは、Google など主要な実務ではチーム単位の指針で、個人の判定には使わない。
4. **個人の指標(0981)**: DORA は指標を**アプリケーション/サービスの単位**で使うものとし、目標にすると Goodhart の法則で操作されるとし、複数の指標を緊張関係で組ませることを求める。SPACE は個人・チーム・システムの3水準の例を出すが、一次の本文は 403 で読めなかった(後述)。**「個人の指標を必ず対で確認する」という規範の直接の先例は見つからなかった**。世の中の実務は「個人の指標を集めない」か「個人へ絞り込まない」側にある。

## 1. 安全の検証記録(IMPL-0045。附属書 F.7)

### 1.1 本標準の現状(照合用)
F.7 は 6 項目(安全関連部の切り分け・適用規格と安全度水準・適用した手法(適用しなかった HR は理由を記載)・故障挿入の結果・AI の利用・独立した評価)をゲート判定記録に添付させる(`safety-verification.md` L274〜289)。G-7 基準7 は「欠落がない」。集約は criteria[7] を `not-checked` とする。

### 1.2 規格の要求
| 規格 | 要求(抜き書き) | 出典 |
| --- | --- | --- |
| IEC 61508-3 7.9 | 検証を計画し文書にする。計画は基準・技術・道具、検証結果の評価、是正を扱う | SRC-0783#c1 |
| IEC 61508-2 7.9.2.6 | 各検証活動の結果を、合格か失敗の理由かを示して文書にする | SRC-0783#c2 |
| IEC 61508-3 附属書 A 凡例 | HR の技術を採らないとき、その理由を詳述する | SRC-0783#c3 |
| ISO 26262-6:2018 9.5 | 作業成果物として「ソフトウェアの検証の仕様」と「検証報告」を要求する。ASIL により手法の推奨度が変わる | SRC-0527(既存。9.5 の語は検索結果の抜粋で確認。カードへの追記は未) |
| DO-178C 11.14 | 検証結果(レビュー記録・構成管理情報つき)を記録し、見つかった不一致は問題報告で追跡する | SRC-0437(差分表) |
| DO-178C 9.3 / 11.20 | 認証当局へ出す最小の記録は PSAC・SCI・SAS。SAS は検証結果の要約を含む | SRC-0437 |
| IEC 62304 5.7.4 | 全ソフトウェア要求が試験または他の検証で確かめられ、追跡できること | SRC-0525 |
| IEC 62304 4.3(Team-NB の FAQ) | 安全クラスの割り当ては必須。**分類の記録の方法は製造者が決める** | SRC-0751 |

読み取り:
- 規格は項目(何を残すか)を定め、**様式(どこへ・どの形で)は定めない**。F.7 を採用者の様式に任せる設計は、規格の流儀に沿う。
- 「HR を採らない理由」は IEC 61508 に先例があり、F.7 の該当行は規格より重くない。
- DO-178C は記録の存在を当局への提出物(PSAC・SCI・SAS)の側で確かめ、内容の妥当性は独立した確認(DER/ASE の査察)で閉じる。**存在の機械確認と内容の人の確認の分担**が、実務の型である。

### 1.3 本標準への含意(問い)
- Q1. 項目の存在・非空・「該当なし」の理由の記載を machine、中身の妥当性(規格の特定の正しさ・故障挿入の網羅)を manual とする分け方は、規格の実務(存在は記録の検査、妥当性は独立した評価)と整合するか。
- Q2. 0045 を `plan=adopter` に改める案は、規格の側では**根拠が無い**(安全の検証記録の欠落の確認を採用者の裁量に委ねる規格は、調べた範囲に無い)。ただし規格はどれも「製造者/組織の検証」を求めるもので、**ゲートの集約が代わりに確かめる**ことは求めていない。したがって「標準の集約が確かめない」ことは規格違反ではないが、「標準が欠落なしを基準にする」以上、表示との食い違いを開示する必要がある。
- Q3. 安全クラス(構成の `q-criticality`)から「安全関連のみ」を決める判定は、IEC 62304 の「分類は必須」と同じ型で、決定可能にしてよい。分類を空欄で通すことは、規格のいう「任意にする」に当たるかを会議体が見る。
- 限界: 規格本文は有償で、公開の版は草案・プレビューに限る。SRC-0783 は改訂案(コメント付き)で、制定版との照合は未。ISO 26262-6 9.5 の項目は、無許諾の転載に由来する検索結果の抜粋を使わず、条の見出しの確認にとどめた。

## 2. 類似の検知と知財(IMPL-0046。基準8、IMPL-0548)

### 2.1 世の中の実務(2026-11 時点)
- **ベンダーの検知**: Copilot の code referencing は、提案を公開コードの索引と照合し、一致があれば出所とライセンスを示す。Block にするか許すかは管理者が選ぶ。Copilot coding agent は **Block 非対応**で、一致はセッションログに強調表示される(SRC-0782。2026-02-18)。GitHub の知財補償は、一致する公開コードをブロックする設定を要件とする(検索結果の要約。一次の条文は未読)。
- **サードパーティの検知**: SCANOSS(スニペットの照合、100M 超のファイルの知識ベース、SPDX/CycloneDX の出力)、Black Duck、FOSSID などが、宣言されない取り込みをスニペットの水準で検出する(ベンダーの紹介。効果の測定は無い。自己申告)。実務の型は「**走査の実施 → 一致の一覧 → 人がライセンスを判断**」である。
- **合否の扱い**: 道具の多くは方針(許可しないライセンス)で止められるが、一致の有無を機械が「侵害」と判定するわけではない。本標準自身が gate-g5.yml で「類似検知は合否条件にしません」と書く(research.md の内部の調査)。

### 2.2 法の状況
- **米国**: Doe v. GitHub(9th Cir. 2026-09-16)は DMCA 1202(b) の請求を退けた。「同一であること」を独立の要件とはしないが、Copilot の出力は複製ではなく学習に基づく新作と理解した。出力が実質的な複製で CMI を欠くなら除去の強い状況証拠になりうる。契約違反の請求は地裁で係属(SRC-0781。二次の解説による。本文は未読)。
- **日本**: 文化庁「AI と著作権に関する考え方」(2024-03-15)は、利用者が既存著作物を知らなくても、生成 AI が学習していれば、類似した生成物について依拠性は**通常推認**され、利用者の侵害になりうるとする。例外として、学習した創作的表現が出力されないことが技術的に担保されている場合(出力段階のフィルタリング等)を挙げ、別の意見として、その場合も過失が否定されるにとどまるという立場を注で併記する(SRC-0780)。

### 2.3 本標準への含意(問い)
- Q4. 「類似の検知の実施」を記録として求める根拠は十分にある(利用者側の責任、検知の実務)。一方、**検知の結果で出荷を止める根拠は世の中に無い**。基準8 の「期限を超過した未処理の指摘」を欠落に数えることは、指摘の処理を台帳へ載せる流れを前提にする。載せる義務を課すのが新しい義務に当たる。
- Q5. 検知の道具の水準を標準が指定するのは無理がある(SCA の商用・OSS、IDE 内蔵の照合、道具を使わない組織)。現状の実装(ライセンス検査の記録の有無)を「類似の検知の実施」と数えることの偽の一致を、開示するか、記録に道具の識別を要求するかが論点。
- Q6. 利用者側に責任が残る以上、`plan=adopter` に倒して統制を消すのは、日本の整理とは整合しにくい。
- 限界: 米国の判決の本文、GitHub の補償の約款、日本の文化庁文書のページ番号は未確認。

## 3. SLA の判定の記録(IMPL-0136)

- **規格**: ISO/IEC 20000-1 の要求は、SLA を文書にして顧客と合意し、測定可能な目標を含め、SLA に対する実績を**監視・見直し・報告**し、未達のとき処置を取る、という形(解説記事による。規格本文は未読)。典型の記録は、サービスレベルの実績報告、レビュー会議の議事録、エスカレーションの記録。判定の記録の様式は組織が定める。
- **SRE の型**: SLI を測り、SLO と照らし、誤差予算で優先を決める。SLO は内部の目標、SLA は契約上の下限で、SLO を SLA より厳しくして余裕を持たせる(ベンダー解説。一次ではない)。
- **レビューの SLA**: Google は応答を1営業日以内の上限とする**指針**で、最適化の対象はチームの速さとする(SRC-0784)。測定の記録には触れない。
- **DORA の「変更のリードタイム」**: 始点はバージョン管理へのコミットで、コミット前の滞留は含まない(SRC-0756#c1)。文書だけの変更の SLA を、これと同じ起点で測るかが論点になる。

含意(問い):
- Q7. 「SLA で判定する」の判定結果の記録は、規格では「実績の報告」と「未達時の処置」に当たる。**観測(分布・超過件数)を出すことは、判定ではなく実績の報告に当たる**。ADR-0137 決定3 の「観測を判定と呼ばない」は、この区別と整合する。
- Q8. SLA の値は組織固有で、値の存在の確認と超過の件数の表示が機械の範囲になる。超過の「是非」は人。

## 4. 個人の指標と対の確認(IMPL-0981。3.11.7)

- **DORA**: 指標は「アプリケーションまたはサービスの水準」で使う。異なるアプリの比較は誤解を生む。目標にすると Goodhart の法則で操作される。「1つの指標ですべてを測る」を避け、**緊張関係のある複数の指標**を使う。チーム間の競争を避ける(DORA 指標ガイド。SRC-0467、SRC-0756 と同じ頁。下の追加案)。
- **Goodhart の法則**: 指標が目標になると良い指標でなくなる。Manheim & Garrabrant は過剰最適化の失敗の型を整理する(SRC-0755#c1)。DORA は AI 利用の指標の操作(トークン消費の水増し)も報告する(SRC-0466)。
- **SPACE(Forsgren ら 2021)**: 生産性は単一の指標では測れず、5 つの次元と、個人・チーム・システムの 3 水準で見る。**少なくとも 3 つの次元を選び、認知の指標(調査)を 1 つ含める**ことを勧める(二次の解説による)。個人の水準の指標例は挙げるが、一次の論文本文(ACM Queue)は 403 で読めず、「個人の評価に使うな」の明文の有無は**確認できていない**。二次の解説は、集計はチーム以上の水準で出すことを勧める、と述べる。
- **Google SRE/eng-practices**: チームの速さを最適化し、個人の速さを最優先しない(SRC-0784#c2)。
- **実務の観察(自己申告・ブログ)**: 個人の指標を評価に使うと、PR の細切れ・レビューの形骸化・負債の放置が起きる、という事例報告がある。標本・測定は無く、単一事例。根拠水準は低い。

含意(問い):
- Q9. 世の中の先例は「個人の指標を、別の指標と対にして確認する」ではなく、「**個人を単位に測らず、チーム/サービスの単位で、緊張関係のある複数の指標を見る**」である。3.11.7 の文を「対」に直すなら、対にする相手を個人の指標から**チーム/リポジトリ単位の保守性の指標**へ置き換えるのが、実務に近い。運用メトリクスの原則(個人の評価に使わない・個人へ絞り込まない)とも矛盾しない。
- Q10. 「個人の指標」の定義が標準に無い。SPACE の「個人の水準」と DORA の「サービスの水準」を参照して定義する案がある。ただし SPACE の一次を読んでいない。

## 5. 記録の置き場(IMPL-0044・0046・0042)の外部の観点

- 規格(61508・26262・DO-178C・62304)は、**項目を定め、様式と置き場を組織に任せる**。標準が様式を固定する義務(テンプレートの置き場)を課すことは、規格の流儀より重いが、禁じられてはいない。標準の独自の判断になるため、根拠水準マークで開示する対象。
- AI 品質指標(0044)の外部の先例: DORA は AI 利用の指標の虚栄化と、AI 導入で配信の安定性が下がる関係を報告する(SRC-0218、SRC-0466)。標準が「合否にしない傾向確認」とする方針は、Goodhart の面からも筋が通る。**記録の置き場を作ること自体の先例は調べた範囲に無い**。
- 受容した負債の台帳(0042): 外部の調査はしていない(内部で足りる見込み)。
