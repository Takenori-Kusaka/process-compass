## 1. 規定ごとの切り分け

### IMPL-0241(版の変更と判定記録の整合)

規定の文が求めるのは3つ。(i) 確定した版から3節が変わった機能に、変更後の版を対象とする G-4 の判定記録があること、(ii) G-3 判断記録の書き換えを G-3 で判定すること、(iii) G-3 記録の無い置き換えを止めること。

- 決定可能: 「最新の G-4 通過の記録が指す版の3節 = 出荷の範囲の先端の3節」の文字列一致。記録の存在
- 決定できない: (a) 記録の「対象」が `F-012 / PR #34` のとき版へ届くか(gh と履歴に依る。squash で消える)。(b) 「意味を変える変更」か。一致は文字列であって意味ではない。(c) 判定が実質か(結果が通過で、判定者・判定日時・D-0 の版が空でも集約は通す。fix-round2 の確認済みの穴)。(ii)(iii) は式が違い、置き換えの関係は ADR/判断記録の参照の構文であって、書き換えが「決定を改める」かは読まないと分からない

実行で確かめた偽の合否(`specSections`、node v22):

| 変更 | 結果 | 合否にしたときの害 |
| --- | --- | --- |
| 行末の空白・CRLF・H2→H3 | 一致(正規化済み) | 妥当 |
| 行内の空白の差(`- A`→`-  A`)、表の整形(`| A |`) | 不一致 | 意味が同じでも偽の FAIL。出荷が止まる |
| 見出し `前提`→`前提条件` | `前提` が **null**(読まれない) | 判定時と現行の両方が「前提条件」なら null = null で**偽の合格**。その節の変更は永久に見えない |
| 節が両側で無い | null = null | 空の一致は合格に数える形になる |

最後の2行が重い。#334 は表示なので害が無いとされたが、合否では節の取り出しの網羅が検査の信頼性を決める。`前提条件` を読まない仕様(#334 の裁定)は、閉じの統制では穴になる。

### IMPL-0023(宣言と実態のずれ)

規定の文(roles-responsibilities.md 3.13.5): 「3組のずれを機械で検出する」「検出したずれは、3.13.3 の起票として扱う」。求めるのは検出と、検出を起票(変化点の手続)に結びつけること。

- 決定可能: 検出の3組(実装済み、`aggregate-evidence.mjs` の `drift`、L4596〜)。D-0 の版の不一致は欠落(合否)
- 決定できない: 「起票として扱った」こと。変化点の手続は決定者の記名を要し、機械は起票を代行できない
- 実装の穴(実行はしていない。コード読み): 人数の検出は `q-team-size` が `size-1-2`/`size-3-9` のときだけ。10名以上の宣言は常に検出されない。担い手の識別は `includes` の部分一致で、短いモデル名の宣言が別の共著者を通す偽の合格がありうる。人の共著者は偽の検出になる(文面に既に書いてある)

## 2. IMPL-0241: 合否にする時点

- PR の時点で合否にしない裁定(#334)は正しい。判定は PR の承認レビューとして後から付き、待つ状態と欠けた状態を区別できない
- 出荷の集約の時点なら、「最新の G-4 通過」が決まる。ただし偽の FAIL の正当な経路が3つある。(1) D-0 の改訂で節の文言が整形だけ変わる。(2) 節の付け替え(見出しの階層・名称変更)で null になる。(3) 差し戻し後の再判定で、記録が複数あり「最新」の選び方が(c)で決まらないと古い版を見る
- 機械の合否は、決定可能な部分だけにする。推す形: 集約は「3節の一致を取れた機能」の件数と「取れなかった機能(対象が版に届かない・節が null・記録なし)」の件数を**値として出す**。合否(記載の欠落)にするのは、**判定記録が全く無い機能**(式の右辺を決められない場合は除く)だけ。節の差は所見として出し、出荷判定者が突合する
- 合否にしないなら表示は `undelivered`(plan=scheduled のまま)か、分けて一部 `delivered`。「一致の所見の表示」は delivered にしてよいが、規定の文が求める「判定記録がある」の統制は閉じていない。note に降りた部分(所見の表示)と残る部分(意味の変更・実質の判定)を書く(方針1、#333 の IMPL-0243/0521 の先例)

## 3. IMPL-0023

検出を既存の警告のまま、レポートの文言に「起票してください」と出す形は既に在る。これを delivered と呼ぶのは**誤り**。

- 規定の「起票として扱う」は、ずれが次の出荷までに変化点の手続を経て処理されたことを求める。文言を出すだけは、見るかどうかが人任せで、現状の `undelivered` と実質が変わらない
- 機械で閉じる決定可能な形が1つある。**前回の出荷で出たずれが、今回も同じ種類・同じ値で残っている**(変更記録に追記が無い)こと。これは新しい合否の条件(c 案)で、採用者への新しい義務(ずれを放置した出荷が失敗する)になる。重へ上げる対象
- 軽の範囲で出来るのは (a) 案: 現状の検出と文言を表示として認め、note を実態で書き直す。ただし state は `undelivered` のまま(降りた部分 = 検出と警告、残る部分 = 起票の確認)にするか、規定の文を「検出と報告」と「起票として扱う」に分けて前者を delivered にする。後者は manual。分ける場合の edit は規定の意味を狭めるので、軽の審議を要する
- 自動の起票(Issue 作成)は採らない。3.13.3 の決定者の記名と別経路になり、`issues: write` の権限も増える

## 4. IMPL-0498

- 数え方を変えない場合に残る穴: 集約は PR ごとに承認を数え、PR の head に中間の層が入ったかを見ない。ADR-0124 決定4 は中間へのマージ自体を禁じるが、検出は IMPL-0248(写しの `base.ref` ≠ 既定、**合否に使わない**)だけ。git merge + push の経路、squash・リベース、基底の付け替え後のマージは拾えない(定型文に既に開示)。したがって 0498 を機械で閉じても、実際に起きる形の大半は検出の外
- 機械で決められる形: 範囲内で `base.ref` が非既定の写し X があり、X の `merge_commit_sha` が、既定へ入った PR Y の `head_sha` の祖先であるとき、Y の承認を層ごとの G-6 に数えず、X に独立した承認が在るかを見る。写しに `head.ref` が無く(`head_sha` のみ。record-copy.yml)、祖先の判定は履歴の取得(浅いクローンでは不能)に依る。これは未確認が多い
- 数え方を変える場合に壊れる既存の決定: (1) 層の合わさりを検出できなかった PR の承認は従来どおり数える(偽の陰性)。検出できた PR の承認を数えない(偽の陽性)ことは、スタックで下の層が既に層ごとに承認済みでも起こりうる。(2) 数えない = 欠落にすると、GitHub 標準のスタック(基底が非既定で、規定が当たらないと明記)が偽の FAIL になる。標準のスタックと手動のスタックを写しから区別できない(`base.ref` だけ)。(3) G-6 の承認の数え方は、template の `test-aggregate-records.mjs` など suite の fixture が過去の決定(兼務の禁止、同一人物の承認の扱い、`notCountedReason` の語彙)を固定している。語彙の新設は fixture と ADR との突合が要る。この突合は未実施(実証を欠く)
- 数え方の変更は、G-6 の統制を機械が変える。**方針により重へ上げる**(議長の受付の裁定どおり)。このセッションでは数え方を変えない
