# TH10 リポジトリ構成と Git/PR/CI

基準日: 2026-09-30(初版 2026-09-24、穴埋め検索の追加分を反映)/ Issue: #282(受け止める Issue: #271 #272 #273)/ 主材料: FND-0136〜FND-0150、FND-0253〜FND-0260

## 結論

- AI・エージェント作成 PR は人のレビュー待ちが長い。LinearB(2026-05 公開、1 社のテレメトリ)で着手待ち p75 が 17.6 時間対 3.4 時間、Faros(2025-07 公開)で PR マージ +98%・レビュー時間 +91%。いずれも相関で、着手後のレビュー所要は AI 支援の方が短い(3.2 時間対 4.2 時間)[FND-0136](E3)。前回の「人の検証帯域が律速」は観察としては維持(律速は解釈)
- PR 本数は指示や AI で膨らみ、待ち行列は実質レビューの迂回で吸収された(1 社: 1 人あたり 21.2→44.3 本、実質レビュー率 約 48%→約 21%)[FND-0137](E2)
- #273 の実測(統合 PR 1 本に 181 本・1,368 ファイル・前回統合から 29 日)は、公開リポジトリの API 値と git 履歴で一致(経過は 28.8 日)[FND-0253](E2)。ただし旧 runbook は経過日数の閾値(3 日で警告・5 日で危険)を既に持ち、その状態で空白が生じた [FND-0254](E2)
- PR 本数そのものと経過時間の予測力を比べた測定は束に無い [FND-0140](E2)。近い測定は AI 以前の OSS で、衝突の発生には変更ファイル数(オッズ比 3.27)が効き、期間の効果は小さい(1.04〜1.09)。衝突の件数はどの指標でも予測できない [FND-0255](E2)
- エージェント作成 PR のマージ再現(2026-04 公開、AIDev 由来の 5 エージェント、未マージの PR が対象)では 27.67% にテキスト衝突。衝突率は小さい PR ほど低いが、46〜185 行で頭打ちになり単調ではない [FND-0256](E2)
- PR の大きさは母集団で割れる。企業テレメトリでは拡大(p75 で AI 支援 400 行超・人手 157 行)[FND-0138](E3)、OSS の AIDev では中央値に有意差なし(90 対 88 行)[FND-0139](E2)
- GitHub 標準のスタック型 PR(2026-07-30 public preview)は全段で main 向けの CI が発火する。代償は CI 使用量の段数倍、線形履歴の必須、Web の rebase による署名喪失 [FND-0141](E1)。#273 の「CI が動かない」は手動スタックの制約
- サードパーティのスタック(Graphite・git-spice)でも CI は動くが実行数が増え、間引くと上段が「必須 CI 未実行」で止まる [FND-0257](E1)。LLVM では Graphite のスタック一括マージで rebase と CI 再実行が約 12 時間続いた [FND-0258](E2)
- エージェントとスタック型 PR の併用事例は割れる。ファインディは人のマージ待ちを解消 [FND-0142](E2)、Rootly は負担増で規則を廃止しリスクラベルとロールバック計画へ置換 [FND-0143](E2)
- モノレポか分割かの統制比較は束に無く、根拠はベンダーのデモと意見に限られる [FND-0144](E0)。分割が人の手番をボトルネックにしたという測定報告も束に無い。Cursor はクラウドエージェントが複数リポジトリにまたがって変更すると説明 [FND-0260](E1)。並行変更の干渉は実 PR 対で 834 実行中 1 件、構成課題で 97% [FND-0145](E2)
- PR 説明文は実体とずれ、読み手の判定も動かす。説明と差分の大きな不一致は 23,247 件中 1.7%、最多は未実装の変更を主張する型 [FND-0146](E2)。説明文は LLM レビューの判定を左右する [FND-0147](E2)
- リリースノート自動化の OSS 4 件は、顧客向け記録の入力を題名・ラベル・コミットメッセージへ分け、検査の免除を決まった文字列やラベルで機械判定する [FND-0259](E1)。4 つの読み手を 1 本文に持たせる設計と行単位判定の先例は束に無い [FND-0148](E1)
- GitHub の「依頼者は自分の PR を承認できない」は一次で確認。2026-09-01 の public preview で Copilot の承認を必須承認に算入する経路が入った(既定は無効)[FND-0150](E1)

## TH10-Q1 モノレポと分割の判断基準、分割による人のボトルネック

**答え**: 2026-09-30 時点で、モノレポと分割を統制して比べた測定は束にありません。分割によって人の手番がボトルネックになったことを測った報告も無く、あるのは意見だけです [FND-0144](E0)。分割が一貫して推奨されているわけでもなく、見解は割れています。否定条件(falsifier)の前半(報告が無い)には該当し、後半(一貫して推奨)には該当しません。穴埋め検索で足されたのは、エージェントが複数リポジトリにまたがって作業できるというベンダー公式文書 1 件 [FND-0260](E1)で、この結論は変わりません。

## TH10-Q2 スタック型 PR のツールと CI 発火条件、エージェント併用

**答え**: GitHub 標準のスタック型 PR が 2026-07-30 に public preview となり、base ブランチの制約による CI の不発は、ネイティブ機能を使う場合には解消しています [FND-0141](E1)。代わりに CI 使用量・線形履歴・署名に別の制約が生じます。エージェントとの併用は、解消を報告する事例 [FND-0142] と負担増を報告する事例 [FND-0143] に割れています。Graphite と git-spice の 2026-09-30 時点の状況は公式文書と変更履歴で確認できました [FND-0257](E1)。サードパーティのスタックでは CI は動きますが実行数が増え、間引くと上段の PR が必須チェック未実行で止まります。スタックの一括マージが CI と衝突した一次事例も 1 件あります [FND-0258](E2)。未回答なのは、ネイティブ機能の挙動の第三者測定と、サードパーティのスタックツールをエージェントと併用した報告です。

**根拠**:

- 2026-07-30 に全リポジトリへ public preview として展開開始。merge queue 対応は段階展開 [SRC-0180#c2]
- スタック内の各 PR は、直接の base ではなくスタックの基底(通常 main)の規則で評価 [SRC-0447#c1]
- main を対象とする pull_request ワークフローは、ワークフローを変えなくても全段で発火 [SRC-0448#c1]
- ワークフローは PR ごとに 1 回走るため、CI 使用量は段数倍。公式は重い処理を最下段と最上段に限る条件式を提示 [SRC-0448#c2]
- 全ブランチ間の完全な線形履歴がマージの必須条件 [SRC-0447#c3]。merge queue はスタックをまとめるため上限を最大 50% 超過可能 [SRC-0447#c2]
- Web の Rebase stack ボタンは committer を書き換えて署名を失わせ、署名付きコミットを要求するブランチ保護を破る [SRC-0449#c2]
- ファインディ(2026-08-05): Sub-issue を AI エージェントが並列実装する仕組みで、自作の同期機構をスタック型 PR に置き換えて削除。レイヤー間の人のマージ待ちが解消 [SRC-0450#c1]。待ち時間を作っていたのは人のレビューとマージのタイミングと総括 [SRC-0450#c2]。並列で実装し、後から依存順に直列化する運用 [SRC-0450#c3]
- Graphite の公式文書(取得 2026-09-30): スタック化で CI 実行が増える理由は、PR 数の増加と裏側の rebase [SRC-0579#c1]。保護ルールを trunk 以外の base にも掛け、上段で CI を走らせない構成では、上段 PR が「必須 CI 未実行」と表示 [SRC-0579#c2]。CI の間引きは障害時に CI を走らせる側へ倒す設計 [SRC-0579#c3]
- Graphite のマージキューはスタックを単位とし、1 本でも失敗するとスタック全体がマージされない [SRC-0580#c1]。並列 CI は投機実行で、flaky なテストがあると後続の CI をやり直す [SRC-0580#c3]。キュー経由でマージした PR は GitHub 上で merged ではなく closed と記録 [SRC-0580#c2]
- git-spice の変更履歴: 下段マージ後の上段 PR の base 付け替え(v0.29.0、2026-05-25)[SRC-0581#c3]、スタックの一括マージ(v0.30.0、2026-06-29、実験扱い)[SRC-0581#c2]、GitHub での CI 二重起動の修正(v0.31.1、2026-07-20)[SRC-0581#c1]
- Sapling の公式文書: 重なり合う PR は GitHub の PR 画面で分かりにくい [SRC-0582#c1]。レビューは専用ビューア(ReviewStack)を推奨 [SRC-0582#c2]

**限定条件・反証**:

- FND-0141 はベンダー公式文書の仕様記述であり、挙動の第三者測定は束に無い。public preview のため変わりうる(reviewBy 2026-12)
- FND-0257 もベンダー・OSS の公式文書と変更履歴(自己申告)で、第三者測定ではない。Graphite と Sapling のページに日付は無い。Graphite の「スタックを使う人が 10 人未満の組織では CI に差が出にくい」[SRC-0579#c4]、「並列 CI でマージが 1.5 倍速い」[SRC-0580#c4] は標本と測定方法の記載が無い。git-spice の最新版 v0.31.2(2026-07-21)は GitHub 標準スタックより前。束のカードにエージェントとの併用の記述は無い
- LLVM(2025-11-03): Graphite でスタックのマージを要求すると rebase と CI の再実行が繰り返されて終わらない問題 [SRC-0583#c1]。約 12 時間続いた例 [SRC-0583#c2]。保守者は、マージキューの導入はマージ前に緑の CI を必須にするのと同じで大きな方針変更になるとして反対 [SRC-0583#c3]。起票者は当面の緩和策に一括マージの無効化を挙げた [SRC-0583#c4] [FND-0258](E2)。否定条件(スタック型 PR が CI と衝突しない)に反する側の事例
- FND-0258 は 1 プロジェクトのフォーラム議論(6 投稿)の自己報告で、件数の集計は無い。エージェント併用の事例ではなく、GitHub 標準スタックの public preview より前の経験。Rootly [FND-0143] とは機序が異なる(CI 資源の浪費とマージの停止)
- Rootly(2026-05-20): エージェントにスタック型 PR を作らせると各 PR が base に未存在のコードを参照し、レビュアの負担が増えた [SRC-0451#c1]。2 年間運用した小 PR・スタックの規則を廃止 [FND-0143](E2)。この経験はネイティブ機能の public preview より前
- ファインディの「待機 2 回→0 回」は記事の例示(4 つの Sub-issue を 3 層に分けた場合)であり、実測の集計ではない [SRC-0450#c1]
- LLVM のフォーラム(2026-08-12): force push がレビュアに与える問題(前回レビューとの差分)は新機能で大きく改善しないという指摘 [SRC-0452#c1](意見)

**Issue との突合(#273)**: #273 は「feature を base にした PR では CI が 1 つも動かない」ことを不採用の理由とし、「CI がどの base でも発火する設定」を前提として明記するよう提案しています。原典では、これは手動スタックの制約であり、ネイティブのスタックは main 向けのワークフローを変更せずに全段で発火します [SRC-0448#c1] [SRC-0447#c1]。Issue 自身も「当時の GitHub の機能と CI の制約」と書いており、観測は当時の事実として整合しますが、提案の前提はネイティブ機能を使う場合には当たりません。サードパーティのスタックでは、CI は動くものの実行数が増え、間引くと必須チェック未実行で止まるという別の形の制約があります [FND-0257]。「スタック型 PR に対応できることが重要」という主張には、支持する事例 [FND-0142] と反する事例 [FND-0143] [FND-0258] の両方があります。

**前回からの変化**: 前回メモ(2026-08-04)にスタック型 PR の節は無く、FND-0141〜FND-0143 は新規です。FND-0257・FND-0258 は 2026-09-30 の追加分です。

## TH10-Q3 PR 本数の閾値と、経過時間・バッチサイズによる統合の健全性

**答え**: #273 の主張のうち「PR 本数は AI で膨らみ、律速は人の手番」は外部の観測と同方向です [FND-0136] [FND-0137]。「バッチの大きさと統合の間隔で見る」方向は DORA の手引きと整合します [FND-0140](E2)。Issue が挙げる実測(統合 PR 181 本・前回統合から 29 日)は、公開リポジトリの API 値と git 履歴からの数え直しで一致しました [FND-0253](E2)。ただし「本数から経過日数へ置き換える」には限定が 2 つ付きます。当の runbook は経過日数の閾値を既に持っており、その状態で 28.8 日の空白が生じていました [FND-0254](E2)。また AI 以前の OSS の査読研究では、衝突の発生に効くのは変更ファイル数で、期間の効果は小さく、衝突の件数はどの指標でも予測できませんでした [FND-0255](E2)。PR 本数そのものを因子にして経過時間と比べた測定、統合後の欠陥や監査の差し戻しを結果に取った測定は、2026-09-30 時点でも束にありません。

**根拠**:
