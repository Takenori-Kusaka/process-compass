# TH08 仕様・要求・前提・トレーサビリティ

基準日: 2026-09-30(初版 2026-09-24、穴埋め検索の知見を追加)/ Issue #282 / 主材料: FND-0106〜FND-0120、FND-0237〜FND-0244(theme TH08)/ 根拠水準 E0〜E3 は findings.yaml の level

## 結論

- 双方向トレーサビリティは DO-178C・FDA ガイダンス・ISO/IEC/IEEE 29148 が明示または定義する規範上の確立事項 [FND-0106](E1)。対象は要求間にとどまらず、コード・テスト・ハザード・リスク分析結果へ及ぶ [FND-0239](E1)
- 全要求の検証済み確認・トレーサビリティの記録・合否基準の充足を別の項目として並べる条文は確認できた(IEC 62304 修正票1 §5.7.4 [SRC-0525#c1]、DO-178C §6 [SRC-0530#c3])。「対応の確認」と「内容の判定」という読み分けは本調査の解釈で、原文に無い。いずれも同じ検証活動の中の列挙で、対応の有無だけを数える検査を独立の手続・ゲートとして定めるものではない。ISO 26262 の該当条項は未読 [FND-0237](E1)。2026-09-24 時点の「読めた範囲に無い」[FND-0107] を限定する
- 航空・原子力の規範が検査の機械化に付ける条件は、出力の独立検証(人手のレビュー)かツール自体の認定 [SRC-0531#c2]。LLM を用いる検査ツールの認定を扱う記述は束に無い [FND-0238](E1)
- 対応の検査が決定論的に成り立つのは、対応が ID で明記されている場合に限られる。推定方式は要求→コードで平均 F1 最良 .322(ICSE 2025、GPT-4o)[SRC-0434#c1]、Spec Kit の analyze も LLM の推論 [FND-0108](E2)
- 仕様接地の効果(+18〜+40pp、誤警報 33%→0%)は原典と一致(単一の統制実験、2026-07 公開、小さな純関数課題)[SRC-0001#c2] [SRC-0001#c5]。ただし効果の大半は列挙の形式ではなく仕様の内容に由来し(素の段落で 30 件中 27 件 [SRC-0001#c4])、前提の検証状態を記録させる効果は未測定 [FND-0109] [FND-0110](E2)
- GSN は現行の第3版でも前提を「立証しない言明」として別要素に置き、検証済みと想定に分ける属性は読めた範囲に無い [FND-0111] [FND-0240](E1)。近い先例は、未確定の値へ TBR と解消条件を添える NASA の点検表(手引き)[FND-0241](E1)。計画分野の ABP が前提を分ける軸は影響と脆弱さで、検証済みか否かではない [FND-0242](E1)
- エージェントの支配的な失敗は、聞かずに誤った信念を形成する側(pass@3 75〜89% → 4〜24%。HiL-Bench、2026-04 公開、GPT-5.3-Codex・GPT-5.4・Gemini 3.1 Pro・Claude Opus 4.6 [SRC-0081#c2])[FND-0112](E2)
- EARS や受入基準が事後に未完成の正当化へ読み替えられる現象の外部報告は束に無い [FND-0113](E1)。一方、要求文の中の逃げ道の句を「実装しない言い訳を与える」として避けさせる指針は存在する(INCOSE R8 [SRC-0575#c1])[FND-0243](E1)。否定形は INCOSE と NASA の点検表が避けさせ、例外は 2 つ [FND-0244](E1)。基準の充足と意図の達成の乖離は測定あり [FND-0114](E2)
- 仕様の正しさを判定するオラクルは利用者以外に無いとされ、ChatGPT 支援は要求の臭いの検出精度を下げた(34 名・学生 [SRC-0320#c1])[FND-0115](E2)
- SDD は Radar で Assess にとどまり、採用率の実測は束に無い [FND-0116](E1)。仕様の肥大は試行報告 3 件(各 n=1、非統制、2025-10〜11 時点の版)が同じ向き [FND-0117](E2)、生産性は非統制の単一事例が相反 [FND-0118](E2)、作成後の整合維持は未解決の領域 [FND-0120](E1)

## TH08-Q2 双方向トレーサビリティと数え上げ検査

**答え**: 双方向の追跡は規範文書に明示されており、対象は要求間だけでなくコード・テスト・ハザード・リスク分析結果へ及びます。2026-09-30 時点で、対応の確認と内容の判定を別の項目として並べる条文を確認できました(IEC 62304 修正票1 §5.7.4、DO-178C §6)。ただし、いずれも同じ検証活動の中の列挙であり、対応の有無だけを数える検査を独立の手続・ゲートとして定めるものではありません。機械化は、出力を人手でレビューするか、ツール自体が認定を経ることを条件に認められています。falsifier(数え上げを要求していない、または区別していない)には該当しない側の結果です。ISO 26262 の該当条項は未読で、DO-178C は二次解説、IEC 62304 は修正票のプレビュー経由のため、確定ではありません。

**根拠**:

- DO-178C は §5.5 で双方向を明確化し、トレースデータを独立したライフサイクル成果物(§11.21)として導入 [SRC-0437#c2] [SRC-0437#c3]。§6.5 はテスト結果・手順・ケースから要求までの追跡を明示 [SRC-0437#c1] [FND-0106]
- FDA の申請文書ガイダンス(2023)は、SRS→SDS とその逆などの追跡分析を、設計が全要求を「正しく完全に」実装していることの客観的証拠の一例に挙示 [SRC-0438#c1] [SRC-0438#c2] [FND-0106] [FND-0107]
- ISO/IEC/IEEE 29148:2018 は要求トレーサビリティを上方(導出元)と下方(割当先)の経路の識別・文書化と定義 [SRC-0439#c1]。要求の検証(well-formed の確認)と妥当性確認(意図どおりか)は別の活動 [SRC-0439#c2] [FND-0107]
- 対応と内容の並置: IEC 62304 修正票1(2015)§5.7.4 は全安全クラス(A・B・C)で、全要求が試験または他の方法で検証済みであること、要求と試験・他の検証の間のトレーサビリティが記録されていること、試験結果が合否基準を満たすことの 3 項目の確認を製造業者に課す [SRC-0525#c1] [SRC-0525#c2]。DO-178C §6(NASA の解説論文 2012 経由)は「コードが全下位要求を正しく満たす」と「全コードが 1 つ以上の下位要求へ追跡できる」を別の検証項目として列挙 [SRC-0530#c3] [FND-0237]
- 確認の担い手とリンクの限界: NASA-STD-8739.8B(2022-09-08)は、双方向トレーサビリティが完了し・記録され・維持されていることの確認を保証側のタスクとする [SRC-0522#c5]。Automotive SPICE 4.0(2023-11-29)は、リンクが存在するだけでは情報どうしの整合を意味しないと注記 [SRC-0554#c4] [FND-0237]
- 対象範囲: DO-178C(同解説経由)はシステム要求と上位要求、上位要求と下位要求、下位要求とソースコード、要求とテストケース、テストケースと手順、手順と結果の各組を挙げ、孤立コード・デッドコードが意図せず作られないことを目的とする [SRC-0530#c1] [SRC-0530#c2]。FDA の一般原則(2002)はリスク分析結果への追跡 [SRC-0524#c4]、NASA-STD-8739.8B はハザードへの追跡が含まれることの確認を要求 [SRC-0522#c5]。IEC 61508-3 第3版の投票用原案(2025-02)は、トレーサビリティの要求を個々のフェーズから外し、ライフサイクル全体の管理活動の表へ移動 [SRC-0528#c1] [FND-0239]
- 機械化の条件: DO-178C は生成するツールと検証するツールの双方に認定を求め [SRC-0530#c4]、使い方と工程への潜在的影響に応じた 5 段階の認定水準を置く(FAA AC 20-115D、2017-07-21)[SRC-0529#c2]。NASA の委託報告書(2017)は、目標をツールで満たすとき、出力を人手でレビューするかツールが認定を経るかのいずれかが要ると整理 [SRC-0531#c1] [SRC-0531#c2]。米 NRC の RG 1.168(2013-07)は、ツールで作られたソフトウェアがツール由来の欠陥を検出できる V&V を受けるなら、ツールへの V&V 作業を不要とする [SRC-0523#c5] [FND-0238] [FND-0226]
- NTT データの公共案件(2026-05-28 公開)は導出元だけを下位成果物に記載し、下位→上位は辿れたが上位→下位が辿りにくく、文書修正時の影響調査に時間を要した [SRC-0255#c1] [FND-0106]
- 自動推定の水準: ICSE 2025 の LiSSA(GPT-4o と RAG)は要求→コードで平均 F1 最良 .322(5 プロジェクト)[SRC-0434#c1]、著者は実務での完全自動化に届かないと結論 [SRC-0434#c2]。回復性能は要求の記述品質に左右される(189 件のユースケース、28 種の欠陥、5 手法)[SRC-0433#c1] [FND-0108]
- 製品の実装: Spec Kit の /speckit.analyze は「タスクが 1 件も無い要求」と「要求に対応しないタスク」の双方向の欠落と Coverage % を出力 [SRC-0435#c2]。対応付けはキーワードや ID 参照からの LLM の推論 [SRC-0435#c1] [FND-0108]

**限定条件・反証**:

- 並置は独立の手続ではない。62304 と DO-178C の列挙は同じ検証活動の中にあり、「a) は網羅の確認、c) は内容の合否」という読み分けは原文に無い解釈(検証役の注記)。方向は 62304 の a) が要求→検証(上位→下位)、DO-178C がコード→要求(下位→上位)[FND-0237]
- 未読の範囲: IEC 62304 は修正票の公開プレビューで本体 2006 年版の該当条は未読。DO-178C・DO-330 は有償本文を未読(小節番号は不明)。ISO 26262-6 のプレビューは §5.2 までで、トレーサビリティを扱う §6 以降と第8部 §6 は未読。29148 は用語定義のみ [FND-0237] [FND-0107]
- 機械化の条件の限定: AC 20-115D は強制でない適合手段の通達 [SRC-0529#c4]。RG 1.168 の免除は立会い・レビュー・試験の V&V タスクに限られ、検出できることを示せない場合は指針がツール開発に適用される。認定は従来の開発・検証ツールが対象で、LLM を用いる検査ツールの認定を扱う記述は束に無い(不在の確認ではない)。あるプロジェクトで認定されたツールが別のプロジェクトで認定済みとは限らない [SRC-0530#c4] [FND-0238] [FND-0226]
- DO-178C の本文は、個々の目標が目的の達成にどう寄与するかの根拠をほとんど示さない [SRC-0534#c1] [FND-0226]
- 対象範囲の限定: DO-178C の組数(6)は列挙を数えた値で原文は数を明言しない。FDA の一般原則は非拘束で該当段落の節番号は未確認。IEC 61508-3 は原案で、2026-09-30 時点の発行有無は未確認 [FND-0239]
- #269 の「網羅性は警告に留める」に対し、62304 は全要求の検証済み確認を shall で課す。ただし機械判定の hard-fail の可否を述べた条文ではない [FND-0237]
- 対応を推定させる方式と、ID を明記して辿る方式は別物。Kiro のタスク一覧は要求番号へ遡る形で生成され [SRC-0228#c6]、要求 ID をコード・テストへタグ付けし本文ハッシュで片側変更を LLM を使わず検出する個人ツールもある(自己申告)[SRC-0286#c2] [FND-0108]
- 対応が揃っていても内容が正しいとは限らない。仕様の正しさのオラクルは利用者以外に無いとする展望論文 [SRC-0432#c1]、Spec の正確性を検証する方法が無いとする cc-sdd 作者の登壇(2025-11)[SRC-0287#c3] [FND-0115]。保留テストとの差は、人の継続的な監督下で作られた C コンパイラでも残存(97.8% 対 83.3%)[SRC-0311#c3] [FND-0114]

**前回からの変化**: 規格側の知見(FND-0106〜0108)は初版(2026-09-24)ですべて新規でした。穴埋め検索(2026-09-30)で、FND-0107 の「読めた範囲に無い」を FND-0237 が限定しました(change: changed。訂正ではなく、読めた範囲が広がったもの)。初版で不足に挙げた「規格が機械化をどこまで認めるか」には FND-0238 が答え、対象範囲の FND-0239 は新規です。254 メモ §5.1 が引いた仕様接地の数値(+38 / +28 / +19 / +36 / +18pt、27/30 対 2/30、誤警報 33%→0%、倍にしても +4pt)は原典と一致しました [FND-0109] [FND-0085]。

## TH08-Q3 前提の検証状態の記録様式

**答え**: 安全ケースの分野では、前提を「立証しない言明」として、証拠で立証された主張や正当化と構造上分けて記録する記法が定着しています。GSN の現行第3版でも構造は同じで、前提を検証済みと想定に分ける属性は、読めた範囲に定義されていません。近い先例は 2 つあります。NASA の点検表は、未確定の値に TBR(要解決)を付け、根拠・解消行動・責任者・期限を添えます(手引き)。計画分野の Assumption-Based Planning(ABP)は、前提ごとに監視する事象・閾値を置きます。falsifier(検証状態を区別する様式が無い)には該当しない側の材料がありますが、前提台帳(assumption register)本体の様式と 29148 の該当節は未読で、部分的な回答です。

**根拠**:

- GSN 共同体標準 第 1 版(2011)は前提を「立証されていない言明」と定義 [SRC-0440#c1]。論証戦略を決める際に置いた重要な前提の記録を求め、正当化とは別の要素として扱う [SRC-0440#c2] [FND-0111]
- GSN 現行第3版(SCSC-141C、2021-05)も前提を「意図的に立証しない言明」と定義し、読めた範囲(第1部 1:2)に検証済みと想定を分ける属性は無い [SRC-0562#c1]。未展開(undeveloped)の標識は goal と strategy に付く別の定義 [SRC-0562#c4]。第3版は疑念の発見と残存する疑念の表示を扱う弁証法拡張(challenges 関係、defeated 状態)を追加 [SRC-0562#c5] [FND-0240]
- NASA システムズエンジニアリングハンドブック附属書 C の点検表(Web 版 2023-07-26 更新)は、未確定の値を最良推定値に TBR を付けて記録し、根拠・解消のための行動・解消の責任者・期限を添えることを挙げる [SRC-0563#c1]。要求に添える根拠中の前提は、ベースライン化の前に確認する対象 [SRC-0563#c2]。不完全な要求をすべて TBD / TBR として捕捉し、その一覧を要求とともに維持しているかも点検項目 [SRC-0563#c3] [FND-0241]
