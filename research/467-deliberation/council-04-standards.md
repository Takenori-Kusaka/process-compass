## 2. 争点への見解

- **P-1 A-22**: 判断の1文だけを残し、手順・結果は実行記録の所在で受ける案に**賛成**。規格の通例(15289 の記録の考え方は記憶による。未確認)は「結果と、結果へ至る証跡の所在」を求め、同じ事実の写しを求めない。ただし G-6 基準6 の「動かして確かめた人がいる」は、人の1文が証跡である。1文は残す
- **P-2 A-37**: 残す。ADR-0070 決定2 が挙動要約を「人が書く欄」と定め、決定10 が形骸化の抑止を既存の手段で足りるとした。件数の削減は本件の範囲外(#466)。この件で要約を減らす提案は採らない
- **P-3 A-29**: 残す。ADR-0058(超過は失敗にせず確認する)が決定済みで、4欄を引く理由は「自己申告」だけである。欄の数は議長が裁いてよいが、廃止は ADR-0058 の置き換えを要する
- **P-4 A-06・A-10**: 残す。S0 の統合は ADR-0028 の `merged-into-gN`(統合は調整として成立)で既に表現される。S1 へ広げるなら、G-2 基準3〜5 を G-4 へ移す条項の再編であり、重の審議が別に要る
- **P-5 C-11**: 残す。様式が規模によらず必須と書く。G-7 を省く構成で検査が作用しない点(§7-8)は、**欄を減らす理由でなく、検査の穴**である。最小の構成で空欄を止める機構が無いなら、ADR-0028 の原則に従い「未検査」と表示する
- **P-6 B-23・B-24**: B-23 は残す(出荷の判断そのもの)。B-24 の「2案以上」を条件つきにするのは、必須欄の条件の変更で、`template-fields.yaml` の `## 比較した選択肢(R1 および例外承認で必須)` の条件欄と標準が両方向で一致している。標準の条件の変更に当たるので、別の審議を要する
- **P-7 A-16**: 行為ごと手引きへ下ろす案に傾く。記録だけを外して行為を義務に残すと、確かめられない義務が増える(ADR-0028 の「表示と実態」)。ただし「AI の提示を見る前に人が方針を立てる」ことは、アンカリングを防ぐ中心の手段なので、本文から消すなら**採らなかったのではなく手引きへ移した**と明記する(コアポリシー: 却下は成果)
- **P-8 A-27b**: 手引き(`/implement`)へ置けば足りる側に賛成。ただし ADR-0028 に従い、最小・非コアの「G-6 が無く提示が無い」ことを開示する
- **P-9 A-12**: 残す。23 欄の削減は、様式を標準の部分集合とする ADR-0040 決定1 の下では、標準側の必須欄を減らす審議になる(template だけでは減らせない)

## 3. 実装へ進むときの手続の見立て

- **置き換えの ADR が要るもの**: Y-8(ADR-0243 決定8 を一部置き換え。IMPL-1036 の範囲を狭める)。G-5 の暦の統合(周期の条項)。Y-6・Y-7 を標準の本文から手引きへ移す場合(ADR は未特定だが、順序の義務を変えるので新 ADR にして、IMPL-0819 の扱いを決定へ書く)。B-24 の条件の変更。M-3 で「未観測」を採る場合は ADR-0018 の置き換えが要る(AC-0 の生成に絞れば不要)
- **ADR を要さず、既存の決定の適用で足りるもの**: M-1・M-2・M-4・M-10(ADR-0070 決定2)。Y-2・Y-3・Y-4(template を標準に揃える修正。ただし Y-4 は「標準と template の食い違いの解消」で、軽の審議)
- **`template-fields.yaml` の必須欄から外すもの**:
  - Y-2(t1 の「承認」。`structure` なので必須欄でなく、登録行の削除のみ。omit は不要)
  - Y-3(t7 の「承認(G-4)」。`same-as-standard` なので、標準の「承認の記録の所在」を残すか、**omit へ理由を書く**。標準と逆の指示を書く形は omit で登録できない)
  - t6 の「承認(G-1)」(C-21 の周辺。`structure`。同様に登録行の削除)
  - PR のチェックリスト(Y-1・Y-5)と AI 関与範囲(Y-4)は、この ymal に PR 様式の登録が見当たらなかった(grep でチェックリストの語は t4 の「チェックリスト突合」だけ)。PR 様式が別の検査で管理されているかは未確認
- **IMPL の扱い**:
  - IMPL-0819(Y-6・Y-7): 義務を手引きへ下ろすなら、マークは消さず `state` を改めるか、降ろし先の本文を新しい決定に合わせて改める。**降りていない規定は消さずに表示し続ける**(CLAUDE.md)に従い、義務をやめるなら「やめた」を決定として残し、マークは削除でなく置き換えの記録を残す
  - IMPL-0042(G-2): 項目7 のチェックをやめると前提が崩れる。同時に改める
  - IMPL-0837(Y-4): undelivered のまま。ADR-0216 が採用者に委ねたので変わらない
  - IMPL-1036(Y-8): 範囲を狭めるなら note へ条件を書く
  - いずれも `npm run impl:write` で台帳を再生成する
- **EV のマーク**: Y-6・Y-7 の根拠水準は triage が未確認(「現時点で最も根拠が厚い」と標準が書くだけ)。マークの有無を確かめ、あれば見直しの根拠として使う。台帳は `npm run evidence:write`
- **template と本体の push は対で行う**(MEMORY の記録)。template を先に push すると並行の束の `test:fields` が落ちる

## 4. 自分の立場から見た最大の危険

**「機械が出す」と「人が書く」の境界が曖昧なまま機械へ移すと、人の記名が機械の写しの記名になり、ADR-0070 決定5(記名者と判定される側が書き換えられない場所)と、ADR-0106(効力を持つ記録の帰属)が崩れる。** M-1・M-4・M-9・B-20 は、機械が値を出すこと自体は決定済みだが、草案の段で埋めた値を判定者が上書きでき、上書きの有無が記録に残らないなら、出所を併記する意味が失われる。移す側の実装は、出所の併記と書き換えの検知までを同じ束で作ること。
