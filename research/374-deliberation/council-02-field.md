## R-1 「簡略」の扱い

### 推す案

**案(b) 適用へ寄せる + 内部調査の (d1)「S1 の緩和の所在を本文に書く」**。CL0 × S1 × 品質「標準」の G-7 の升を「適用」にし、S1 のステージによる緩和がどこにあるか(G-7 の基準2 のトリアージの S1 の行、基準3 の負債台帳の「記録+返却目安」、G-6 のコア機能への限定)を第8章の本文に1段落で書く。「ゲートの状態では緩めない」と明記する。

### 理由

1. **現場で省ける作業は、今の「簡略」の下でも0件である**。準拠テンプレートは `simplified` を `required` と同じに扱う。
   - 集約は `g7.state !== 'omitted'` なら、引き継ぎ文書・負債台帳・判定記録の有無を全部数える(`template/scripts/gate/aggregate-evidence.mjs:2716-2727`)
   - スキル `gates/G-7.md` は `simplified` にも S1 にも触れない。手順は1通りだけ(全文を確認)
   - 成立条件4、`/pit`、様式も区別しない(内部調査 4.3)
   - 適用へ寄せても、小さいチームの出荷の手数は1つも増えない。今の「簡略」は、手数を減らしていないのに、減らしたと宣言している
2. **表示と中身の食い違いが、現場の手戻りを生む**。PROCESS-PROFILE.md と保証の開示の項目2 に「簡略化」と出る(`aggregate-evidence.mjs:3279-3283`)。規則の注記は「出荷判定は簡略化する(記録は残す)」(`rules-business-phase.yaml:49-51`)。この表示を読んだ開発者は「MVP の出荷判定は軽くてよい」と読む。`docs/handover.md` を用意せずに出荷の集約を走らせ、欠落で止まる。止まった理由は「簡略」の語からは読めない。318 の会議体の現場の委員も「現場は『記録だけ残せばよい』と読み、形骸化する」と述べた(`research/318-deliberation/council-02-field.md:107`、内部調査 3.2)。この手戻りの頻度は未実証である。ただし、語と挙動が逆を向く以上、起きる向きははっきりしている
3. **S1 は、実利用者に初めて届く段階である**。トリアージ表の S1 は「限定した実利用者」(`gate-criteria.md:2060`)。S0 の省略の前提2(露出が社内と実験参加者に限られる、`tailoring-guide.md:488`)を外れた最初のステージである。小さいチームほど、最初の顧客の障害で連絡先も復旧手順も無いと、全員の手が止まる。出荷判定を軽く見せる表示は、この段階に要らない
4. **S1 の緩和は、既に基準の中にある**。基準2 は S1 の行を持つ(「コア機能は出荷不可。非コアは既知の不具合として公開すれば可」、`gate-criteria.md:2060`)。基準3 の負債は S1 で「記録+返却目安」(`tailoring-guide.md:473`)。G-6 は S1 でコア機能だけ(`:469`)。現場が実際に軽くなっているのはここである。升の「簡略」を重ねても、何も軽くならない。軽くなっている場所を本文に書けば、現場は「どこが軽いか」を表から読める
5. **先例がある**。旧 G-3 の S0 の簡略を ADR-0063 が適用へ寄せた(内部調査 3.3)。中身の無い簡略を、実際の判定に合わせて「適用」と書き直した例である

### 他の案を落とす理由

- **案(a) 基準ごとに中身を定義する: 採らない**
  - 実質の候補は基準4(運用引き継ぎ)の一部だけである(内部調査 5.1)。基準6 は合否に使わない(`gate-criteria.md:2136`)。基準7 は CL0 で既に適用外。この2つを「省く」と書けば、何も省かない簡略を中身があるように見せる。現場にとっては最も悪い形である。省けたと思って読み進めると、何も省けていない
  - 基準4 の3項目(監視項目・障害時連絡先・復旧手順)は、実利用者がいる段階で最初に要るものである。小さいチームでは、3項目は数行で書ける(未実証)。省いて減る手数は小さく、障害時に失うものは大きい
  - 外部でも、最も軽いクラスでリリースの活動を省く例は見当たらない。IEC 62304 のクラス A でも検証の完了の確認・既知の残存異常の文書化・版の文書化は残る(二次情報、`survey-374-2-external.md` S-02)。ISO 9001 8.6 はどの規模でも受入基準への適合の証拠と許可者の追跡を求める(S-03)
  - 定義しても、テンプレートの集約・スキル・様式へ降りるまで、`undelivered` の期間が生じる。その間、表示と中身の食い違いが続く
- **案(c) 省略へ寄せる: 採らない**
  - S1 の出荷がすべて保証の主張の成立条件4 を満たさなくなる(内部調査 2.3、5.3)。最初の顧客へ出す出荷の保証の開示に、毎回「品質保証の対象外」と出る。小さいチームが顧客に説明できる状態ではない
  - トリアージの S1 の行(コア機能の Sev1 は出荷不可)を確かめる席が消える。G-8 は技術品質を蒸し返さない(`gate-criteria.md:1506`)
  - S0 の省略の前提3(S0 で確認を経なかった変更を S1 以降の出荷で欠落として扱う、`tailoring-guide.md:489`)の受け皿が S2 まで無くなる。S0 の省略そのものの根拠(EV-0101)が崩れる
  - 手数の面でも得は小さい。省略しても、集約は独立した人の確認を経ていない変更の件数を出し続け、G-8 は残る(`tailoring-guide.md:477, 492`)。省けるのは記名1つと突合の時間である。その代わりに保証の主張を失う
- **案(d) 簡略の条件を変更ごとのリスク区分(R)へ寄せる: 本件では採らない**
  - 現場から見ると、本当に手数が減るのは「変更の性質で軽くする」形である。Google の LCE の型(低リスクの類型に短いチェックリスト、S-04)は魅力がある
  - しかし G-7 は出荷ごとの判定であり、R は変更ごとの区分である(ADR-0039)。1つの出荷の範囲に R の違う変更が混ざる。どの R の組み合わせなら出荷判定を軽くするかの規則は、本標準にも外部調査にも無い。いま定義すれば、実証の無い値を出荷判定へ持ち込む
  - 「決めていない事項」として後継の Issue の候補に残す(課さないと決めたのではない)。条件は、低リスクの出荷の類型の定義と、その類型で G-7 のどの基準を短くするかの根拠(Google の型が求める「過去の障害による裏づけ」に相当するもの)
- **組織の選択にする(内部調査 d3): 採らない**。升は規則が定める結果で、組織が選ぶ余地を示さない(`tailoring-guide.md:477`、第1章 1.7.3)。ADR-0065 決定4 が同じ型を退けた
- **暫定マークで決めずに残す(d4): 採らない**。ADR-0088 が CL1 以上から簡略を外した理由「定義の無い語で出荷判定を緩める」(`adr/0088…:192`)が、CL0 に当たり続ける。現場の混乱(理由2)も続く

### 条件と留保

- **実行で確かめる**: CL0・S1・品質「標準」の構成で `gates.g7.state` だけを `simplified` と `required` にした2つを作り、同じ履歴で集約を実行して、項目2 以外の出力が同じことを確かめる(内部調査 6.1)。理由1 の「手数は1つも増えない」は、これが確かめられるまでコードの読みであり未実証である。違いが出たら、その違いを本件の会議体へ戻す
- **既存の CL0・S1 の構成への出方**: 厳しくする向きなので、再導出で即時に適用できる(ADR-0055 決定5)。取り込みの案内には「判定の作業は変わらない。表示が実際の判定に合うだけ」と書く。案内が「出荷判定が厳しくなった」とだけ読めると、現場は何かを足さなければならないと誤解する
- **PoC から MVP へ移るときの一覧**: `generate-profile.mjs:3503-3512` は S0 の構成に「省略・統合・簡略のゲートを復活させる」を出す。案(b) の後も S0 の G-1 の簡略が載るので、一覧の形は変わらない。G-7 は S0 で省略なので、引き続き「復活させる」に載る
- **本件の外だが、現場の本当の負担**: S1 の小さいチームで重いのは、基準の数ではなく、G-7 の記名者の確保である(成立条件4: 作成の指示者でも G-6 の承認者でもない人、`gate-criteria.md:1404`)。簡略の有無と関係なく既に課されている。本件で緩めない。体制の負担の問題として軸A の側で扱う

## R-2 軸B の升の表記と軸C の上書き

### 推す案

**升の中に書く。** 品質「高」以上・規制業で軸C が勝つ升に、CL1 以上と同じ括弧の限定で書き込む。R-1 の案(b) を採ると、S1 の G-7 の升は次になる。

- 「適用(品質『高』以上は軸C で強化。CL1 以上も適用)」の形。語の並びは起案に委ねる

あわせて、表の後の段落(`tailoring-guide.md:477`)に「升は軸B の結果に、軸C・軸E が優先する升の限定を括弧で添えたものです」と、読み方を1文で書く。S0 の前提の箇条(`:494`)にある「品質要求が『高』以上の構成では、軸C の調整が本軸の省略に優先」と同じ事実を、S1 の升からも読めるようにする。

### 理由

1. **表は、小さいチームが最初に読む場所である**。品質「高」(金銭を扱う MVP など)で S1 を始めたチームが表の升「簡略」を読むと、出荷判定を軽く見積もる。エンジンは `strengthen` を出し、軸C の「+限定的な抜き取り確認」(`tailoring-guide.md:545`)が掛かる(内部調査 4.2)。表で読んだ手数と実際の手数が逆を向く。R-1 で升を「適用」にしても、「強化」とは別の状態である。上書きを書かなければ食い違いは残る
2. **限定は升の中に書くのが本標準の規約である**。#226 の適用範囲の書き方は「限定を、規範とは別の段落へ置かない。表の行が限定を持つなら、その行の中に書く」とする(`community/scope-marking.md`、CLAUDE.md の要約)。軸E の上書き(CL1 以上は適用)は既に升の括弧にある(`:469-470`)。軸C の上書きだけを別の箇条(`:494`)に置く理由が無い
3. **S0 の升も同じ問題を持つ**。S0 の G-6・G-7 の「省略」も、品質「高」以上では軸C で適用になる(`:494`)。この事実は箇条にはあるが、升には無い。R-2 の直しは S1 の G-7 だけでなく、軸C が勝つ升の全部に当てる

### 他の案を落とす理由

- **別の段落だけに一般則として書く(升は触らない): 採らない**。上の理由2 の規約に反する。現場は升を拾い読みする。段落の一般則まで読む前提を置かない
- **書かない(PROCESS-PROFILE.md に実際の状態が出るので足りる): 採らない**。PROCESS-PROFILE.md は構成を作った後に読むものである。体制や品質要求を決める前に表を読む採用者(S1 へ移る前の見積もり)には届かない。テンプレートの出力で品質「高」の S1 の G-7 が `required` か強化として出るか、理由に軸C の注記が出るかも、実行では未確認である(内部調査 6.6)
- **軸C の表(`:545`)の側にだけ書く: 採らない**。軸C の表は「出荷判定の厳格さ」を書くが、軸B の升を上書きすることは読めない。上書きは2つの表の関係であり、読み手が最初に当たる軸B の升に書く

### 条件と留保

- **エンジンの試験に、品質「高」・規制業の S1 の G-7 を入れる**。`expectG7` の全升の走査は品質「標準」だけである(`scripts/test-tailoring-engine.mjs:366-367`、内部調査 4.2)。升に書いた上書きが規則の挙動と一致することを、試験で固定する。升だけ直して試験が無いと、次に規則の優先度を変えたとき、表と挙動が再び食い違う
- 軸C が勝つ升を全数で洗い出す作業は、起案の側で行う。現場の委員としては、少なくとも S0 の G-6・G-7 と S1 の G-7 の3升を確認した(`:469-470, :494`)
- 括弧の中が長くなる升がある(S0 の G-6 は既に長い、`:469`)。長さを理由に別段落へ逃がさない。読みにくければ脚注番号ではなく、升の下の行に注記を置く表の形を起案が検討する

## R-3 「簡略」の語の全体の扱い

### 推す案

**語は残し、定義を置く。定義の無い「簡略」を今後置かない旨を書く。** 置き場は第1章 1.7.3 の工程ゲートの状態の語彙(`phase4-process-design/overview.md:358`)。中身は次の3点とする。

1. 「簡略」は「適用」の一種である。判定は行い、判定記録を作る(ADR-0028 の `simplified` =「簡略化して適用する」と同じ)
2. 判定基準を外さない。減らすのは成果物の分量・形、または判定の対象の範囲であり、その限定を升の括弧に書く(例: G-1 の S0「簡略(1枚企画書)」、`tailoring-guide.md:464, 479`)
3. 括弧の限定を持たない「簡略」を升に置かない。判定基準を外す調整は「簡略」と呼ばず、基準ごとの適用範囲として、#226 の書式で基準の行の中に書く

あわせて、ゲートの状態の「簡略」と、様式の簡略化(欄を落とし `omit` へ理由付きで登録する、ADR-0040)が別物であることを1文で書く。

### 理由

1. **現場は語から作業を読む**。「簡略」と書かれれば「何かを省いてよい」と読む。何を省くかが書かれていなければ、各チームが自分で決める。小さいチームほど、省く範囲を広く取る(未実証。318 の現場の委員の見立てと同じ向き)。語の中身を「判定基準は外さない、減らすのは括弧に書いたもの」と決めれば、読み違いの余地が括弧の中に限られる
2. **今の中身のある唯一の例は、この定義に収まる**。G-1 の S0 は「記述の分量を減らす調整であり、前節の宣言を外すものではない。新しい様式を設けない」(`tailoring-guide.md:479`)。定義を置いても、G-1 の S0 の升も本文も変わらない
3. **判定基準を外す道を、別の名前で残せる**。R-1 で案(a) を採らなかったのは、いま外せる基準が実質に無いからである。将来、外部の実証がそろって基準を外すときは、基準ごとの適用範囲として書く(IEC 62304 の型、`survey-374-2-external.md` S-01)。この形なら、どの基準を外したかが判定記録と範囲の台帳(`npm run scope:write`)から読める。「簡略」の一語に包むと読めない
4. **「課さないと決めた」と「書かれていない」の区別**。定義の無い「簡略」は、2026-07-15 の初版から3か月以上、誰も中身を書かずに残った(内部調査 1.4)。「定義の無い簡略を置かない」と書いておけば、同じ形の升が新しく足されるのを、執筆の時点で止められる

### 他の案を落とす理由

- **語を廃止し、G-1 の S0 を「適用(1枚企画書)」と書き換える: 採らない**
  - 第8章の要求事項2 は「簡略化した項目を、理由とともに宣言する」(`tailoring-guide.md:23`)。分量を減らしたことを外へ宣言する語として「簡略」は役に立つ。G-1 の S0 は実際に分量を減らしており、その宣言は保証の開示の項目2 に出るのが正しい
  - 廃止すると、分量の削減が「適用」と同じ表示になる。R-1 で直す食い違い(減らしていないのに減らしたと出る)の逆向き(減らしたのに減らしていないと出る)を作る
- **定義せず、個々の升の括弧だけで運用する: 採らない**。今の S1 の G-7 がまさにその形で、括弧の無い升ができた。語の定義と「括弧の無い簡略を置かない」の規則が無ければ、同じことが繰り返される
- **「簡略」の中身を判定基準の番号で定義する(基準ごとに省く形): 採らない**。R-1 の案(a) を落とした理由と同じ。先例の2つ(G-1 の S0、旧 G-3 の S0)はどちらも基準の番号でなく、成果物の形か対象の範囲で限定した(内部調査 1.3)

### 条件と留保

- **機械で止めるか**: 規則データの `simplify` の注記と、第8章の升に括弧があるかを検査で確かめる案がある。現場としては、検査が無いと「置かない」は守られにくいと考える(未実証)。ただし、どの検査(`lint:provisions` か新しい検査か)に載せるか、括弧の中身の良否をどこまで機械で見るかは、規格と起案の委員に委ねる。載せないなら、その旨と理由を ADR に書く
- `tool/knowledge-base-schema.md:65` の動詞 `simplify` の定義(「簡略化する」の言い換えだけ)も、1.7.3 の定義を引く形に直す。道具の頁の例「PoC の出荷判定の省略と MVP の簡略化を取り消す」(`:68`)と `tool/proposal-logic.md:51` は、R-1 の後に古くなるので書き換える

## R-4 記録・開示・ADR

### 推す案(項目ごと)

1. **保証の開示の項目2 の「簡略化」**: 表示の仕組み(`aggregate-evidence.mjs:3279-3283` の `STATE_TEXT`)は変えない。R-1 の後は、CL0・S1 の再導出した構成で G-7 の行が消える。G-1 の S0 の「簡略化」は引き続き出る。これが正しい表示である(R-3 理由「廃止を採らない」)
