## ステータス

採用(2026-11-15)。[ADR-0084](/process-compass/adr/0084-check-strength-plans-and-resident-rules/) の決定4 のうち、次の1項と、検討した選択肢(R-4)の表の1行を置き換えます。採用済みの ADR の本文は書き換えていません。

- 置き換える項: 「`issue=` が閉じた Issue を名指すことは、機械で検出しない。検査はオフラインで実行し、Issue の状態を知り得ないためである。閉じた Issue を名指さないことは、Issue を閉じる者が確かめる」
- 置き換える行: 「閉じた Issue を名指すマークを機械で検出する」を採らなかった案とした行

ADR-0084 が退けた理由は、検査(`npm run check`)をオフラインで実行し、同じ結果を出すことでした。この原則は保ちます。

## コンテキスト

[#439](https://github.com/Takenori-Kusaka/process-compass/issues/439) は、閉じた #359 を `issue=` に持つ未達の実装マークが残ることを指摘しました。実行で確かめると、該当は 7 件ではなく 14 件(閉じた Issue 4 件: #359・#358・#289・#290)でした。

- 閉じる者が「0 件を確かめてから閉じる」という人の手順だけの統制は、ADR-0084 の後に確かめた 8 件の Issue のうち 4 件で破れた。破れは 2026-10-29 から残り、別件の審議が見つけるまで検出されなかった
- 破れの条件は決定可能である。マークの `issue=` の番号の集合と、閉じた Issue の番号の集合の共通部分が空であればよい
- 退けた理由は条件の決定可能性ではなく、検査の実行環境(オフライン)だった。検査の外に置けば、理由と両立する

## 決定

### 1. 検出する。置き場は検査の外のワークフローと、手元の同じスクリプトとする

- スクリプトは `scripts/check-impl-plan-issues.mjs`(`npm run impl:issues`)。`issue=` の番号の状態を `gh` で問い合わせ、閉じた Issue・実在しない番号・Issue でない番号(PR)を名指すマークを列挙する。コードブロックの中の見本は数えない
- ワークフローは `.github/workflows/impl-plan-issues.yml`。契機は `issues: closed`、docs の変更を伴う main への push、月次、手動。月次と push は、閉じた後に足されたマークと、ワークフローが動かなかった期間の取りこぼしを拾う
- `npm run check` には入れない。木が同じでも、誰かが Issue を閉じると main の検査が落ちる形を採らない
- 所見があれば実行を失敗にする。公開は止めない

### 2. 機械は Issue の状態を変えない

- ワークフローは、所見のある閉じた Issue へ「この Issue を名指すマーク(識別子と所在)」をコメントし、実行を失敗にするだけである。開き直さない・閉じない・編集しない
- 同じ所見(識別子の集合が同じ)のコメントが既にあれば、足さない。月次と push で重ねて動くためである
- 食い違いは、コメントと失敗の表示を受けた人が、`issue=` を open の Issue へ付け替えるか、Issue を開き直すかを決めて解く
- `issues: write` の権限は、コメントするジョブにだけ付ける(`evidence-review.yml` と同じ付け方)

### 3. オフラインの検査で、番号の実在と種別を確かめる

- `npm run lint:impl` は、`issue=` の番号が Issue の一覧の写し(`src/data/issue-index.tsv`)に在り、種別が Issue であることを確かめる。状態(開閉)は見ない。写しは [ADR-0089](/process-compass/adr/0089-regression-suite-under-version-control/) が定める。状態を書かないのは `scripts/issues-snapshot.mjs` の設計であり、そのままである
- 番号の打ち間違いと、PR の番号の名指しを落とす。後継の Issue を名指すときは、写しの更新(`npm run issues:snapshot`)が要る

### 4. 閉じる者の手順は残し、道具を与える

- Issue を閉じる者は、閉じる前に `npm run impl:issues -- --issue <番号>` を実行する。この入力は Issue の状態に依らず、その番号を `issue=` に持つマークを列挙し、1 件以上で終了コード 1 になる(オフライン。`gh` は要らない)。引数なしの `npm run impl:issues` は閉じた Issue を探す確認であり、閉じる前の問いには答えない
- `Closes #N` を書くコミットは、付け替えを同じ push に含める
- 付け替える者は、寄せ先の Issue へ、寄せるマークと受け入れ条件の案をコメントで足す

### 5. 機械で閉じない部分は manual とし、根拠水準マークで開示する

| 残る部分 | 扱い |
| --- | --- |
| 寄せ先の Issue が、その規定の担い手として合っているか | manual(付け替える者)。機械は open であることだけを見る |
| ワークフローが実際の GitHub で発火し、コメントが動くこと | main へ入った後に確かめる。確かめるまで暫定(EV-0260) |
| ワークフローの無効化・権限の変更・GitHub Actions の障害 | 検出しない。月次の契機と、閉じる者の手元の実行(`--issue`)が補う |
| フォークや写しのリポジトリ | 対象外。本リポジトリの Issue だけを見る |

## 検討した選択肢

| 案 | 採らなかった理由 |
| --- | --- |
| A: `npm run check` の中で GitHub へ問い合わせる | オフラインで同じ結果を出す原則を破る。認証の無い環境・レート制限・フォークの PR で結果が変わる。木が同じでも、誰かが Issue を閉じると main の検査が落ちる。採るなら重の審議が要る |
| B: 状態つきの写しを版管理へ置き、`lint:impl` が突き合わせる | 破れは Issue を閉じた直後に起きる。写しが最も古い時点に当たり、通過の表示が実態と食い違う。鮮度を push の前の手順に頼れば、人の手順へ戻る。機械に写しを更新させると、Issue の事象ごとに main へのコミットが生じる |
| D: 人の手順と開示だけを続ける | 8 件のうち 4 件で破れた。開示しても、台帳が閉じた Issue を計画として表示する状態は直らない |
| 機械が閉じた Issue を開き直す | 所有者の決定(2026-11-15)。人が閉じた判断を機械が覆さない。意図して閉じた Issue(重複・取り下げ)でも、機械と争うことになる |
| 台帳の冒頭に件数だけを出す | 台帳の生成はオフラインで、状態を知り得ない(B と同じ問題) |
| `review=` を過ぎたマークで検査を落とす | ADR-0084 が退けた(暦で CI が落ちる)。変えない |

## 影響

- 採用組織への新しい義務は無い。本リポジトリの追跡の道具の変更であり、準拠テンプレートと標準の条項は変えない
- 付け替えの作業そのもの(14 件)は #439 で行った。[#443](https://github.com/Takenori-Kusaka/process-compass/issues/443)・[#444](https://github.com/Takenori-Kusaka/process-compass/issues/444) を起票し、[#326](https://github.com/Takenori-Kusaka/process-compass/issues/326)・[#355](https://github.com/Takenori-Kusaka/process-compass/issues/355)・[#361](https://github.com/Takenori-Kusaka/process-compass/issues/361) へ寄せた
- 検出が「`issue=` を書かない」誘因にならないよう、`plan=scheduled` の `issue=` 必須は保つ。合わない open の Issue へ機械的に寄せる誘因は、機械で閉じない。manual の確かめ(上の決定5)で開示する
