## ステータス

採用(2026-08-05)

## コンテキスト

Issue #126 は、全成果物のトレーサビリティを確保し、テーラリングツールの提案ロジックへ接続することを求めていた。着手時の点検で、次の乖離が判明した。

| 乖離 | 内容 |
| --- | --- |
| 調整軸の不足 | 第8章の調整軸は4つで、**危害の深刻度を扱う軸がない**。Issue が求める SaMD・車載といった入力を受け取れない |
| 語彙の不一致 | 調整軸Bが PoC / MVP / グロース / 安定運用の4区分で、第2章の事業ステージ S0 / S1 / S2 と対応づいていない |
| 調整対象の不足 | 会議体 B-1〜B-4、D-0、テンプレ9、附属書F、移行段階 T-0〜T-4 が調整の対象に含まれていない |

調査により、危害の深刻度でプロセス要求を段階付ける公開された実例(医療機器ソフトウェア、宇宙機、航空、AI 規制、医療機器ソフトウェアの国際的なリスク分類)に共通する構造を確認した。

- 軸はほぼ常に**危害の深刻度**であり、技術的な複雑さやチーム規模ではない
- 段階は3〜5が主流
- **上位は下位を包含する**(上位で別のことをするのではなく、追加で行う)
- 段階の差は**列挙可能な差分**(成果物の有無、要求の件数)で定義されている
- 分類は最も粗い粒度のテーラリングそのものである

あわせて、出力形式について次を確認した。推薦の理由の提示は受容を高めるが、**確信度の数値の提示は受容と信頼のいずれへも影響しない**。また、過剰依存を最も減らす設計に対して利用者は最も低い主観評価を与える。

## 決定

1. **安全重要度を軸Eとして導入し、区分を CL0〜CL3 とする**。既存の記号(S / SG / G / B / D / R / L / E / Sev / Hz / SR / RRS / T / TG / EN)と衝突しない
2. **判定は最悪の場合の帰結で行う**。上位は下位を包含し、構成要素ごとに判定して最も高い区分が全体の区分になる
3. **段階の差を列挙可能な形で定義する**。「より厳格に」という表現を用いず、成果物名とゲート名で示す
4. **上限を段階の延長として表現しない**。CL3 の安全関連部と L2 以上の組み合わせは許容せず、CL4 を作らない。段階を増やすと「厳しくすれば実施してよい」という誤読を招く
5. **軸Eの優先度を 50 とし、限界ケースの代替(40)より優先する**。人員の不足を理由に危害の深刻度に基づく要求が黙って外れる経路を作らない
6. **軸Bを事業ステージ S0 / S1 / S2 に対応づける**。ツール側の4区分は運用上の呼称とし、規定上は S2 を2区分に分けない
7. **テーラリングに宣言を伴わせる**。調整軸に基づくこと、外した項目を理由とともに宣言すること、調整後に目的の達成を示すことの3点を要求事項とする
8. **提案書を7ブロックで構成する**。要約・差分の宣言・各判定の理由・外せない下限・変更の手順・検証の記入欄・改善の順序
9. **総合スコア、適合度の百分率、成熟度のラベルを出力しない**。確信度の提示に効果がなく、ラベルは組織内の評価材料に転用される
10. **摩擦を全項目にかけない**。CL2 以上または R1 に関わる判定へ限定し、利用者自身の検証の記入を求める

## 検討した選択肢

- **既存の軸C(期待品質・規制)で代用する** — 軸の数は増えないが、可用性・監査対応と危害の深刻度は別の性質である。規制業でも人身への危害を伴わない場合があり、逆もある
- **既存の R1〜R3(リスク区分)を流用する** — R は決定の取り消し可能性であり、危害の深刻度とは対象が異なる。同じ記号にすると判定の意味が失われる
- **CL4 を作り、禁止をレベルの最上位として表現する** — 段階としては単純だが、「さらに厳格にすれば実施してよい」という誤読を招く
- **軸Eの優先度を 30(品質と同列)にする** — 実装は単純だが、1〜2名で外部レビュアがいない場合に限界ケースの規則が勝ち、安全の要求が黙って消える
- **総合スコアを出す** — 一覧性は上がるが、確信度の提示が受容と信頼のいずれへも影響しないという実験結果があり、内部の評価材料になる副作用のほうが大きい

## 影響

- 第8章に軸E、事業ステージとの対応表、調整の宣言に関する要求事項、会議体と移行段階の調整を追加した。禁止事項を3件から6件へ増やした
- 知識ベースに `rules-criticality.yaml`(3規則)を追加し、`questions.yaml` に `q-criticality` を追加した。シミュレーターは質問を動的に描画するため、画面側の変更は不要である
- `constraints.yaml` に3件を追加した(安全関連部の自律度の上限、安全成果物の非省略、調整の宣言)。検証スクリプトの件数の表明を更新した
- `src/content.config.ts` の `axis` に `E` を追加した
- 検証シナリオを2件追加した(CL3 と限界ケースの衝突、CL2 の包含と CL0 の無加算)
- 「成果物トレーサビリティと記号の索引」を新設し(`vision/04-traceability.md`)、17系統の記号と混同しやすい対の一覧を置いた
- 「提案書の出力フォーマット設計」を新設した(`tool/proposal-output.md`)
- 出力のブロック4〜7は未実装である。実装は後続の Issue で扱う
- 軸Cと軸Eには入力の重複がある。現在は調整対象を分けることで二重適用を避けているが、**利用者が両方を高く申告した場合の説明は改善の余地がある**
- 調査根拠は `research/phase4-standard/126-tool-integration.md` に記録した
