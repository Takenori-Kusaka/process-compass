## コンテキスト

- [#466](https://github.com/Takenori-Kusaka/process-compass/issues/466): 人がボトルネックになる既定の構成への所有者の懸念。S2 の中くらいの変更(R2)は、作成者が確かめ、別の人が区分を確定し、さらに別の人が中身を読んで承認するまで取り込めなかった
- 所有者の決定(2026-11-27。`owner-answers-04.md`):
  - 問1: (a) この形で進める。中くらいの変更(人手で戻せるもの)は、作った人が確かめ、機械の検査を通れば取り込む。別の人は、出荷を決めるまでに読む。区分の確定も出荷判定までへ移す。同じ機能の続きは、まとめた差分で読んでよい
  - 問2: (a) 取り込みが本番を直接起動する構成は、別の Issue で審議する([#469](https://github.com/Takenori-Kusaka/process-compass/issues/469))。本束には入れない
- 議長の判定(所有者の元の懸念に答えたか): 時点を移すだけでは、半分しか答えていない。答えたのは、作る人と取り込みを、読む人の空きに合わせて待たせないことである。「人の読める量に作る量を合わせる構成」そのものには、答えていない。人が読める量は、出荷の量の上限として残る。所有者の品質の定義は、「いまどこまで確認できているか」を出荷の時点で問う。人が読むべきものは出荷物であり、作る途中の全部ではない。構成は「人の読める量に作る量を合わせる」から、「人の読める量に出す量を合わせる」へ変わる
- 読む件数は減らない。減るのは、取り込みの待ちと、作り直しで捨てた途中の版を読む手間である。「減った」と書くと誇大になる
- 範囲: 本 ADR は S2 の形を決める。S0・S1 の行は ADR-0274、値と事故の警告は ADR-0273、委任の経路と記録の独立性は ADR-0272 である

## 決定

### 1. S2 の中くらいの変更と登録していない R3 は、取り込む前に人が読む範囲の外で承認を待たずに取り込み、出荷判定までに全件を読む

- 範囲の外の S2 の R2 と、登録していない R3 は、独立レビュアの承認を待たずに取り込める
- 独立レビュアの席の人が、その変更を含む出荷判定(G-7)までに、全件を G-6 の基準1〜6 で読み、挙動要約を自分で書く。記録は G-6 の判定記録の様式で残す(承認レビューの本文では残さない。取り込んだ後に付けた承認レビューは、出荷の前の確認に数えない。採らなかった案: 承認レビューにも出荷判定の記録との前後の照合を当てる。取り込んだ後のレビューの数え方は実機で確かめておらず、確かめていない経路を規範にしないため)
- 読まれていない変更は、G-7 基準5 の記録の欠落になる(既存の仕組みが働く)。急ぐときは第7章 7.3 の例外承認(既存。回収の期限と責任者)を経る
- 読む時点の期限の値は置かない(所有者の軸)。出荷の直前に固めないための手当ては、決定6 の表示と、決定4 の累積の差分である
- 範囲の判定は機械が行う。AI の担い手に行わせない
- 差し戻しの是正の経路(取り込み済みの変更を、独立した人の確認の後に直す)が既に本文にある。本決定は、それを正規の経路に格上げする。新しい機構を足すのは、範囲の判定と、記録の独立性と、開示の投影だけである

### 2. 取り込む前に人が読む範囲は、次の和集合とする。新しい区分・定義は足さない

どれも既存の宣言・規則・様式の列・検出の再利用で、人の記入なしに機械が決める。

| # | 当たる変更 | 受ける既存の仕組み |
| --- | --- | --- |
| 1 | 記載か区分の下限が R1 の変更。区分を読めない変更 | 第3章 3.8.1 |
| 2 | コア機能・確約範囲のパス。未宣言なら全変更 | 保護するパスと区分の下限の規則のパス |
| 3 | 判断記録の要否の規則のパス | 第2章 2.6、ADR-0101 決定3 |
| 4 | 統制の設定・AI が指示として読むファイル。プロセスの構成のファイルに触れる変更は、鍵を問わず入れる | 統制の設定の変更の承認 |
| 5 | 仕様・依存の宣言とロックファイル・サブモジュールの宣言 | G-5 基準8 が依存として読むファイル |
| 6 | 基底ブランチにあるテストの削除・アサーションの行の削除 | G-5 の検出 |
| 7 | 実装計画の「依存」が基底ブランチへ取り込まれていないタスクの変更 | 実装計画の「依存」の列。トレーラの無い変更は照らさず、照らしていない旨を出す |
| 9 | 形骸化の検知(差し戻し率 0% の継続)で登録を止めた委任の種類の、規則の範囲 | 既存の委任の規則 |

- 8 は作らない。事故の原因の変更が触れたパスを範囲へ足す定めは、所有者の決定(ADR-0273 決定、問3 (Y))により採らない。事故の後は、警告と開示で受ける
- 範囲の中の変更は、取り込む前に、前掲の条件を満たす承認(作成を指示した者と別の人。挙動要約つき)を求める
- 5〜7 を足す理由: 所有者が事前に人が触るとして挙げた土台・依存・順序のうち、機械が何も見ないものを残さないため。止めず、取り込む前の読みへ回すだけで、作業は止まらない
- 未確認の変更とパスが重なる変更を範囲の中へ倒す案は採らない(採らない案に書く)

### 3. 範囲の外の R2 の区分の確定は、出荷判定までに行えばよい

- 区分の下限は、機械が取り込む前に決める(第3章 3.8.1 要求事項2。既存)。R2 の区分の、作成を指示した者以外の人による確定(要求事項3)は、範囲の外の変更に限り、その変更を含む出荷判定までに行う
- 確定するのは、出荷の前に中身を読む独立レビュアでよい。判定記録の既存の欄「リスク区分を確定した者」へ記名する。新しい欄は足さない
- 出荷の証跡の集約は、範囲の外の R2 の変更に確定の記名が無ければ欠落にする(機械)。R1 の確定は取り込む前のままである(R1 は範囲の中)
- 理由(多数の委員と違う結論なので書く。5 委員のうち 4 委員は取り込む前に残す意見だった):
  1. 取り込む前の確定の防ぎは、すでに迂回できる。R1 を R3 と書けば、要求事項3 は掛からない(要求事項4)。塞ぐのは「R1 を、わざわざ R2 と書いた」場合だけである。区分を低く書く変更を取り込む前に止めているのは、区分の下限の規則である
  2. 出荷の前の確認の後は、R2 と R3 の扱いが同じになる。確定を取り込む前に残すと、R2 と正直に書いた変更だけが 1 件ずつ人を待ち、R3 と書けば待たない。正直な記載を罰し、低く書く誘因を作る
  3. 区分の誤りが出荷の前に見つかれば、R1 の扱いを満たすまで欠落になる(既存の型)。利用者へ届く前に塞がる
  4. 取り込みの時点で他者が関与した、という説明は失う。本番への反映の境界で答える: 作成者が単独で本番へ出せる経路は無い。出荷の前の独立の確認、出荷判定と残存リスクの受容の別人の記名、本番反映の記名がある。予防でなく発見の統制と開示する
- 残る危険: 規則に当たらない R1 相当の変更が R2 と書かれて取り込まれ、その上に変更が積まれる。R1 を R3 と書く既存の残余と同じ型で、規則の網羅を主張しないことと、保証の開示で受ける。区分の下限の規則に、データの移行・ビルドと配備の設定・公開インタフェースのパスを書くことを手引きで強く勧める

### 4. 同じ仕様の連続した変更は、累積の差分で読んでよい(機械で閉じる条件の内側に限る)

- 組は「トレーラ `Spec:` が同じで、すべてが範囲の外にある、取り込み済みの連続した変更」。トレーラの無い変更は組に入らず、1 件ずつ
- 範囲の判定は、組の累積ではなく、取り込む時点で 1 件ずつ行う。1 件でも当たれば、その変更は取り込む前に読まれている。途中で入って消えた副作用(秘匿情報・移行・依存)は、G-5 と範囲が 1 件ずつ受ける
- 累積の差分が構成の規模の基準値(`task.maxChangedLines`・`maxChangedFiles`)を超えた組は、1 件ずつへ戻す。**規模の基準値が未定義なら、この読み方は開かない**(1 件ずつの読みは使える。止めない。緩める向きの経路を、値の無いときに開かないだけ)
- 累積の差分で読んでよいこと(決定)は残す。記録は変更ごとに対応づくように書く(判定記録の「対象」へ変更ごとの番号を並べる)。準拠テンプレートは範囲の書き方を解いて中の変更を対応づける処理を持たない(採らなかった案: 集約に範囲の書き方を解かせる。組の条件の判定と一体で、この束では実装しない)。受入基準の確認(パス1)は累積の差分の全体に掛ける(ADR-0101 決定1)
- 組を AI の推定で決めない(H.4 条件4 と同じ誘導の危険)
- 効かない所: 純増の新しい機能を読む量は減らない。減るのは、作り直しで捨てた途中の版である
- **準拠テンプレートは、組の条件を機械で照らさない**(IMPL-1074。undelivered で表示する)。累積の差分で読んでよいことは決定として残り、準拠テンプレートでは 1 件ずつ読む形で決定を満たせる

### 5. 取り込んだ後に作る G-6 の判定記録は、ADR-0272 決定8 の条件で数える

- 出荷の前の確認の記録は、当該の変更を含む出荷判定の記録より前に、判定者本人が足したものだけを独立した人の確認に数える(ADR-0272 決定8。第4章 G-6 の足し手の条件。実装マーク IMPL-1068)
- 出荷判定の記録の後の追加、前後を履歴から読めない記録、判定者と別の者が足した記録は数えない
- 署名を要しない構成では、足し手を作成者の名義で照らす。他人の名義を使った書き込みは防げず、保証の開示に出す(EV-0388)
- 本 ADR が出荷の前の確認を、取り込んだ後の記録で数える以上、この条件が無ければ表示が偽になりうる。ADR-0272 を先に入れた理由である

### 6. 出荷判定の材料と保証の開示に、毎回投影を出す。値と閾値は置かない

- 出荷の前の確認が済んでいない変更の件数、その最も古い変更の取り込みからの経過日数
- 未確認の変更の後に、同じファイルを触って取り込まれた変更の件数(積み重なり。未確認の変更が差し戻されたときの作り直しの量)
- 例外承認で出した変更の件数と、範囲の外の変更に占める割合
- 出荷の前の確認を済ませた確認者ごとの件数(偏りは人が見る。比率の閾値は置かない)
- 範囲の外の R2 のうち、区分の確定者の記名が無い変更の件数
- 出す所: 出荷の証跡の集約の宣言の表、保証の開示の項目1・3。委任の「事後へ移した変更」とは混ぜない
- ADR-0274 が「在庫の表示」を課さないとした理由(誰も動かない数)は、本形では当たらない。未確認の量は、所有者の品質の定義の「いまどこまで確認できているか」そのもので、出荷判定者が判定に使う数である
- 閾値を置いて止めない(ADR-0059 と同じ理由。確認の期限の値は所有者の軸)

### 7. 取り込みが本番への反映を直接起動する構成では、この形を使わない。この構成への便益は審議中である

- 取り込みが本番を直接起動する構成では、読まれていない変更が利用者へ届くため、この形を使えない。要求事項として本文に書く
- 検査は、配備の環境を指定したジョブを持つ workflow を、構文で検出する。起動の契機が人の手動の起動だけ、または PR の検査だけであるときを除き、起動する側へ倒す(push・workflow_run・release・schedule・読めない契機を含む)。ブランチの絞り込みと条件式は読まない。push などで動く workflow が再利用の workflow を呼ぶジョブを持つときは、呼ばれる側がリポジトリの中にあって読め、配備の環境が無いと確かめられる場合を除き、起動する側へ倒す。申告の欄は足さない(採らなかった案: push と環境の組だけを拾い、残りを開示で受ける。読まれていない変更が利用者へ届く場面が、よくある構成で抜けるため)
- 拾えない形は、配備の環境を指定せずに秘密情報で配備する workflow と、workflows の外の配備(別のリポジトリ・外部の仕組み)である。機械で見えない。採用者の責任とし、保証の開示に「配備の起動を機械で確かめた範囲は workflows に限る」と出す(IMPL-1075。adopter)
- **この構成に、確認の時点を出荷の前へ移す便益を届けるかは、審議中である**([#469](https://github.com/Takenori-Kusaka/process-compass/issues/469))。AI で最も速く作る採用者ほど、取り込み=本番の構成を使うため、所有者の懸念が最も強く当たる層に、本 ADR の便益は届かない。「出荷」を利用者への露出(段階的な公開・機能の切り替えの印)と読み替える定義の拡張は、重の審議が要るので、本 ADR に入れない。結論が出るまで、この構成の確認は取り込む前のままである
- 安全重要度 CL1 以上・規制業・品質「高」は、既存の禁止のまま、この形を使わない

### 8. 出荷の前の確認の変更は、トレーラ `Delegated:` で識別しない

- 集約は、範囲の外の変更を、パスと区分から導く。トレーラ `Delegated:` を流用しない(流用すると、欠落にならず件数の開示で出る)
- 第4章 G-7 基準5 の突合の表は、「G-6 の判定を事後へ移した変更」を、委任に限ると書く。出荷の前の確認の変更は、記録が無ければ欠落の行に入る
- 人の新しいトレーラ・欄を足さない

### 9. 人が触る場所の表(ADR-0274 決定1)の S2 の行の新しい値

0274 は、決定の時点のいまの値(前+記)を書きました。本 ADR の後の値は次のとおりです。凡例の「出荷前」は、取り込んだ後、その変更を含む出荷判定までに、作成を指示した者以外の人が全件を読む形を指します。

| 場面 | 0274 の時点 | 本 ADR の後 |
| --- | --- | --- |
| S2・R1 | 前+記 | 前+記(減らない) |
| S2・R2・取り込む前に人が読む範囲の中 | 前+記 | 前+記(減らない) |
| S2・R2・範囲の外 | 前+記 | 記(出荷判定まで)+出荷前(**減る**。取り込みの待ちが外れる。読む件数は減らない) |
| S2・R3・登録した種類 | 後 | 後(2 版と同じ) |
| S2・R3・登録していない・範囲の外 | 前 | 出荷前(**減る**) |
| S2・R3・登録していない・範囲の中 | 前 | 前 |

- 条件: 安全重要度 CL0・品質が標準(「高」を除く)・規制業を除く・承認者 1 名・取り込みが本番を直接起動しない構成。使えない構成の行は、決定7 のとおり、前+記のまま
- 準拠テンプレートは、委任の規則を登録した構成では、この形を使わない(決定10)。S2 で委任の規則を登録した組織の R2 は、取り込む前のままである
- 「前」の 1 件の重さは変えない。変わるのは、どの行に「前」が掛かるかと、出荷前の読みだけである

### 10. 形骸化の検知で止めた委任の種類の戻し先は、取り込む前とする。準拠テンプレートは、この範囲を求める判定を持たない

- 形骸化の検知(差し戻し率 0% の継続)で登録を止めた委任の種類は、その規則の範囲の変更を、取り込む前に読む範囲へ入れる(範囲の行 9)。協働へ戻した変更が、また出荷の前へ集中するのを防ぐ
- 準拠テンプレートは、停止の出力を PR の検査へ渡す仕組みを持たないため、行 9 を求める判定を実装していない(IMPL-1073。undelivered)
- 緩めない側に倒す: **委任の規則を登録した構成では、準拠テンプレートはこの形を使わない**。R2 は取り込む前のままである
- 採らない案: 行 9 を実装して委任と両立させる。停止の出力を PR の検査へ渡す仕掛けが要り、本束に足さない
- 事故の後の警告の件数の内訳に「出荷の前の確認」を足さない。この形と委任の規則は同時に成り立たず、常に 0 になる

### 11. 準拠テンプレートの既定

- 構成の既存の値だけから使うかを決める。事業ステージ S2(グロース・安定運用の値)・G-6 必須・範囲が全変更・承認数 0・安全重要度 CL0 の記入・品質が標準の記入・承認者 1 名・委任の規則なし。未記入と未知の値は使わない
- 生成の既定は、S2 の組織で承認を取り込む前に人が読む範囲に掛け、ブランチ保護の必須の承認数を 0、必須の検査(`gate-g5-base`)が範囲の中の PR にだけ承認を求める。S1 のコア機能の形(ADR-0274 決定3・4)と同じ仕組みを、範囲の集合へ一般化する。ルールセットは新しく作らず、S1 の `team-core` を使う
- 実機の確認が済むまで、「準拠テンプレートはこう動く」と書かない。実装マークは undelivered で表示する(IMPL-1072)

## 課さないと決めたこと

「書かれていない」と区別します。

| 論点 | 課さないこと | 理由 |
| --- | --- | --- |
| 読む時点の期限 | 出荷の n 日前などの値 | 所有者の軸。値を置かない |
| 確認者ごとの件数 | 閾値を置いて止める | ADR-0059 と同じ。比率の閾値を置かない |
| 取り込みが配備を起動するかの申告 | 申告の欄 | 機械が workflows を構文で見る。外の配備は採用者の責任 |
| 区分の確定を取り込む前に残すこと | 範囲の外の R2 の取り込む前の確定 | 決定3 |
| 累積の差分の組の機械の照合 | 準拠テンプレートでの判定 | 実装マークで undelivered |
| 読んだ中身の質と例外承認の常態化 | 機械で止めること | 機械は記録の有無と形だけを数える。人が見る(IMPL-1077) |
| 事故の後の範囲の戻し | 事故の原因の変更が触れたパスを範囲へ足すこと | ADR-0273。警告と開示で受ける |
| 出荷の点の定義の拡張 | 「出荷」を利用者への露出と読み替えること | 重の審議が要る。#469 |

## 影響

- 実装は準拠テンプレートの次の所にある
  - `scripts/gate/config.mjs` の `approvalByPreRead`: この形を使う構成の判定
  - `scripts/gate/check-pr.mjs`: 範囲の判定(`preReadRangeOf`)・配備の検出・承認の照合・範囲の外の R2 の確定者の扱い
  - `scripts/gate/aggregate-evidence.mjs`: 範囲の外の変更の識別・確定者の記名の欠落・投影
  - `scripts/init/generate-profile.mjs`: S2 の生成の既定(`team-core`・承認数 0)
  - `.claude/skills/gate/gates/G-6.md`・`templates/04-gate-record.md`: 記録の書き方
- 準拠テンプレートの文には、条項(章・節)だけを引き、ADR 番号・Issue 番号を足していない
- 採用者への影響: S2 の範囲の外の変更は、承認を待たずに取り込める。出荷判定の前に、独立レビュアが全件を読む。範囲の中は今のとおり承認を要する。取り込みが本番を直接起動する構成と、委任の規則を登録した構成は、変わらない
- 失うもの: 取り込む前に別の人が読む機会。範囲の外の変更が、読まれる前に既定ブランチへ入り、他の作業の前提になる。失うのは、利用者(出荷までに見つからなかった欠陥)と、出荷判定者(「全件を人が読んだ」と開示する責任)と、作り直しを負う作成者である。読まれていない変更の上に積まれた変更は、差し戻しの連鎖の取り消しを招く。「戻せる」は時間とともに失われる
- 実装していない所(undelivered で表示する)
  - 承認数 0 のルールセットと必須の検査の組み合わせで、範囲の外が実際に取り込め、範囲の中が止まること。マージ済みの PR に後から付けた承認・判定記録が数えられること。ルールセットの適用をホスティングが受け付けること(IMPL-1072。試験用リポジトリは private・無償のプランで、ルールセットとブランチ保護のどちらも使えなかった)
  - 形骸化の検知で止めた委任の種類の範囲(決定10。IMPL-1073)
  - 累積の差分の組の機械の判定(決定4。IMPL-1074)
  - workflows の外の配備の検出(決定7。IMPL-1075。adopter)
  - 読んだ中身の質・例外承認の常態化(IMPL-1077。人が見る)
- 偽って低く書く誘因: 区分を R3 と書けば、取り込む前の確定は掛からない(既存の残余)。出荷の前の確認の後は、R2 と R3 の扱いが同じになり、誘因は増えない
- 本文の側の食い違い: 第3章 3.8.1 要求事項3 の時点と、第4章 G-7 基準5 の突合の表を、本 ADR の決定へ書き換える。第5章 5.5.2・5.7.1・第8章 軸B の表の注も書き換える
- 実機の確認の状態: 実装マーク IMPL-1072 のとおり、承認数 0 のルールセットと必須の検査の組み合わせは、確かめていない。確かめられなければ、S2 の生成の既定を戻す(generate-profile の判定を偽にする 1 コミット)ことで、S2 は取り込む前のままになる。集約と PR の検査は、承認数 0 の構成にだけ効く
- 回帰スイートの注意: 場面が S2 の既定(team・承認 1)を固定している場合は、決定の置き換えに伴う期待の変更になる

:::caution[暫定 EV-0393 / 見直し 2027-05]
**対象**: S2 の中くらいの変更の確認を、取り込む前から出荷判定の前へ移し、「前」を「出荷前」へ減らす判断。読まれていない変更が、出荷判定までの間、既定ブランチへ入ること。
**根拠の水準**: E0(なし)。
**差し替え条件**: S2 の採用組織で、範囲の外の変更に起因する欠陥の件数、出荷の前の確認で差し戻した件数、例外承認で出した件数と割合、出荷判定までの最古の未確認の経過日数の観測。

所有者の決定です。議長と 5 委員は、案に条件つきで賛成し、全員が「読む件数は減らず、時点が移るだけ」と述べました。取り込んだ後・出荷の前に全件を人が読む型は、調べた範囲の公開の実務に見つかっていません(2026-11-27 時点)。区分の確定を出荷判定まで移す点は、5 委員のうち 4 委員が取り込む前に残す意見でした。
:::
