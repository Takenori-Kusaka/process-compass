## コンテキスト

[#380](https://github.com/Takenori-Kusaka/process-compass/issues/380) は、第4章の「判定記録だけのコミットを基底ブランチへ入れる操作に、記名者以外の承認を課さない」が強制層へ降りていない(IMPL-0124)ことを扱う Issue でした。GitHub のルールセットはパス単位の免除を持たず、記録だけの PR にも承認 1 件が残ります。内部・外部の調査(`research/380-deliberation/survey-380-*.md`)と、起案・現場・品質監査・規格・弁護の 5 委員の会議体(`research/380-deliberation/council-*.md`)を経ました。5 委員はいずれも、問題の立て方そのものを退けました。

### 見つかったこと

- 記録の大半は、既に条項を満たしていた。様式と写しは記録用ブランチへ承認なしで入り、出荷の PR がまとめて運ぶ。承認 1 件が残るのは、出荷の PR、例外承認の台帳、停止の解除の記録の 3 つだった
- 台帳と停止の解除は、PR の時点の検査が既定ブランチの先端から読む。入った時点で、判定される側の変更の合否を変える。条項を字義どおり降ろす案(パス単位の免除、bypass actor、記録用ブランチへの移設)は、どれも判定される側が自分の例外・解除を足して自分の変更を通す経路を開く
- 品質監査の委員は、残る承認 1 件も統制として足りていないことを、準拠テンプレートのコードから示した。PR の時点の照合も出荷の集約も、台帳の行の「承認した者」を名前で照合し、PR の作成者でないことしか見ない。3 名以上の体制では、判定される側 X が「承認した者: Y」と書いた台帳の PR を開き、無関係の Z が承認すれば、X の例外が成立する。停止の解除も同じ構造だった
- 出荷の PR について、準拠テンプレートは「開くのは出荷判定者、承認するのも出荷判定者の本人」と書いていた。GitHub では PR の作成者は自分の PR を承認できない。手順として成立していなかった
- 外部: GitHub は、パスごとに承認件数を変える公式の手段を持たない。パス条件でチームの承認を足す機能(2026-02 GA)は、ユーザー所有のリポジトリでは使えない。「一律 0 + 足し戻し」の構成は、公式の記述と検証が無い。bypass はアクター単位でパスを見ない。Azure DevOps・GitLab・Gitea はパス単位の承認規則・免除を持つ

### どちらが誤りか

ADR-0070 決定6 は、事後の照合で足りる記録の性質から導いた「承認を課さない」を、入った時点で効力を持つ記録にも及ぶ文で書きました。残る承認を「取り込みの事務」と呼び、それが担っていた役割を論じませんでした。誤っているのは決定6 の範囲と語です。判定記録についての核(写しを機械で取り、記名者以外の判定を課さない)は正しいと判断しました。ADR-0078 の原理も正しく、現行の実装(既定ブランチの先端から読む)が帰属を確かめない代用だったことが欠けていました。

## 決定

### 1. 基底ブランチへ入る記録を2つに分ける

| 区分 | 該当する記録 |
| --- | --- |
| 判定記録 | 様式(G-1・G-7・G-8・SG、対象が PR でない判定)、承認レビューの写し、保証の開示、出荷の PR が運ぶそれらの複製 |
| 効力を持つ記録 | 例外承認の記録、停止の申し立ての解除の記録、層1、D-0 の決定の記名、前倒しで要る SG の判定記録 |

列挙で閉じ、列挙に無い記録を効力を持つ記録として扱いません。語は第1章 1.4 に「効力を持つ記録」「転記の確認」「帰属の確認」として足します。裁定の段階では既存の「判定の材料」を使う案でしたが、1.4 の「判定の材料」は判定者が読む記録(判断記録・運用引き継ぎ文書)を指し、意味が衝突するため採りませんでした(独立の突合の指摘)。

### 2. 判定記録には記名者以外の者の判定を課さない。残る承認は転記の確認

ホスティングの規則が一律に承認を課す場合、その承認は転記の確認です。承認者は複製が置き場の記録と一致することを機械の検査の結果で確かめ、中身を判定しません。準拠テンプレートでは、出荷の PR の承認がこれに当たります。

### 3. 効力を持つ記録は、効力を持つ前に記名者本人の操作で帰属を裏づける

名前の一致を裏づけに数えません。裏づけは、(A) 対象の PR の上の記名者本人のレビュー、(B) 記録を入れた変更(記録の今の中身を入れた変更)の作成者または承認者が記名者のアカウントであること、のいずれかを機械が確かめられるものに限ります。記名者が作成者の場合は、記名者以外の人の承認(帰属の確認)を経ます。帰属の確認者を置けない体制(名簿に記名者以外の人がいない体制)では、記名者本人のアカウントの操作を受け付け、記名が自己申告であることを記録ごとに開示します。

### 4. 例外承認と停止の解除の受け皿に、対象の PR の上の記名者本人のレビューを加える

宣言行を案件の構成で事前に定めます。書き手は、名簿の人で、AI の名義でなく、PR の作成者と異なる者に限ります。レビューの対象のコミットは、PR の先頭と一致するものに限ります。承認の後の変更で失効します。例外承認では、書き手が記録の承認した者で、作成を指示した者でないものに限ります。停止の解除では、書き手が層1 の項目4 の権限者で、申し立ての後で出したものに限ります。この経路では、記録だけの PR が要りません。

起案の委員は、台帳の行とレビューの欄の一字一致を求めました。採りませんでした。行の中身はレビューの対象のコミットに固定されるため、書き手が見た版です。二重の転記を書き手に課す理由がありません。

### 5. 層1・D-0 は効力を持つ記録に数える

層1 の項目4 は停止の解除の権限者を定め、PR の時点の検査がそれを読みます。直接の push を止める既定ブランチの強制層は維持します。ADR-0057 の採らなかった案の理由「記名の意味と二重になる」は、帰属の確認が中身を承認しないため当たりません。層1・D-0・SG の帰属を機械が確かめる実装は本件で降ろさず、IMPL-0415(#428)で表示します。

### 6. 出荷の PR の承認者を出荷判定者の本人と書かない

出荷の PR は、開いた人以外の人が承認します。承認は転記の確認です。G-7 の判定は G-7 の様式で成立しています。Actions・App・個人のトークンに出荷の PR を開かせる・承認させる形は採りません。承認の件数に数えられるかを確かめておらず、機械の承認を人の確認に見せるためです。

### 7. 採らない手段

- パス単位の承認の免除、bypass actor(exempt を含む)、検査を掛けない別ブランチへの移設によって、効力を持つ記録を承認の要件の外へ出すこと。パス単位の規則を持つホスティングでも、免除してよいのは判定記録に限る
- 承認の件数を一律 0 にし、パス条件のチームの承認で足し戻す構成を既定にすること。合成の規則の公式の記述と実機の検証が無く、失敗したときに開く構成である
- Actions・App の承認を承認の件数に数える形
- 台帳と解除の記録を記録用ブランチへ移し、検査がそこを読む形(a1)。記録用ブランチは書き込みの権限を持つ者とジョブのトークンが追記・変更できる(EV-0185、#379 未決)
- 署名コミットだけで裏づける形(a2)。署名の鍵と名簿のアカウントの結び付きを確かめていない。1〜2 名の体制で鍵の運用を既定にする根拠が無い
- 承認者を CODEOWNERS と `require_code_owner_review` で記名者へ寄せる形。記録の置き場に複数の席が同居し、作成者本人は承認できない
- Issue のコメント・PR 本文を受け皿にする形(第4章が退けている)
- 条項をそのまま維持し、降りていない規定として表示し続けること。降ろすと統制が壊れる規定を、降ろすべき規定として表示することになる
- すべての記録の取り込みに記名者以外の承認を課すこと。ADR-0070 が解消した「中身を見ない承認」を判定記録にも戻す

## 反論されうる点

### IMPL-0124 を delivered にしたのは、言い換えで未達を消したのではないか

消していないことの根拠は3つです。様式と写しは、記録用ブランチの経路で承認なしで入ります。残る承認(出荷の PR)の承認者が見るものを、機械の検査の結果に定めました。新しく課した要求(帰属の裏づけ)は、別の実装マーク(IMPL-0413〜0415)で表示しています。1 名と外部の確認者の体制では、出荷のたびに外部の確認者の転記の確認が要ります。この負担は残ります。

### 認証情報を共有する構成では、レビューの書き手を区別する手段が無い

AI の担い手が記名者の認証情報で動く構成では、レビューを本人が書いたか担い手が書いたかを区別する手段がありません。ホスティングの記録で帰属を示す方式すべての前提の崩れです。準拠テンプレートは、担い手が宣言行のレビューを出さないことを、権限設定と常駐の規則で定めます。作成者本人のレビューは数えません。アカウントの分離を構成の入力にするかは、[#429](https://github.com/Takenori-Kusaka/process-compass/issues/429) で扱います。

### 名簿の照合がログイン名で行われている

第4章「アカウントと人の対応表」は、数値の識別子を求めます。準拠テンプレートの照合の関数は、本件の前からログイン名で照合しており、本件の照合も同じ関数を使います。#429 で扱います。
