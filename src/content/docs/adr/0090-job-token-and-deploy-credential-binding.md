## コンテキスト

[#346](https://github.com/Takenori-Kusaka/process-compass/issues/346) は、第4章 G-8「配備の統制と資格情報の置き場」が、ジョブの権限で発行される短命のトークン(GitHub の `GITHUB_TOKEN`)を想定していないことを問いました。

G-8 は「資格情報は、配備を許す参照に限った実行環境の秘密情報に置きます」と置き場を指定していました。`GITHUB_TOKEN` は秘密情報に置くものではなく、書き込みの権限は、起動元のブランチで書き換えられるワークフローのファイルの `permissions` から生じます。本リポジトリの配布(`dist/standard`)はこの形で書き込みます。ADR-0077 は、本リポジトリの配布がこの規範を満たさないことを開示し、解き方を「#293 で別に扱う」としていました。#293 の記録に、その扱いはありません。

#293 の会議体の裁定 J-6 の b・d は、配布専用の deploy key を Environment の秘密情報に置き、ルールセットで更新を deploy key だけに限る方式でした。本リポジトリの配布は、これをコミット `b185611`(2026-10-23)で `GITHUB_TOKEN` の方式へ改めたものです。**この変更は、調査・会議体・突合を経ていません**。保守者の決定(2026-10-23)を受けて、実装の側で方式を改めました。本 ADR は、その変更を事後に審議した記録でもあります。保守者の決定の中身は次の3つです。

- 鍵(deploy key・秘密情報に置く長期のトークン)を設定しない
- 配布の書き込みは、GitHub Actions のジョブの権限(`permissions`)で行う
- `dist/standard` のルールセットで更新を制限しない(`GITHUB_TOKEN` をバイパスに入れる公式の手段が無いため)

鍵を設定する案は、保守者の決定により審議の対象にしませんでした。ただし、保守者の決定は本リポジトリの運営を縛る前提であり、適合の判定を縛るものではありません。本標準は他組織が従う規格であり、作者の1件の都合で条項を緩めることは、その立場と両立しないためです。

指摘をそのまま条項にせず、調査2本と会議体5名の意見書で扱いました。記録は `research/346-deliberation/`(`decision.md` の R-1〜R-5)にあります。

### 見つかったこと

- GitHub には、`GITHUB_TOKEN` の書き込みを参照(ブランチ・タグ)で限る機能がない(2026-10 時点の GitHub Docs)。権限はリポジトリの既定から始まり、起動元のブランチのワークフローのファイルの `permissions` で足し引きされる。Workflow permissions は既定であり、上限ではない。Environment はこのトークンの権限を限らない。`environment:` を消した同じジョブは、Environment の規則を通らずに同じ権限を得る
- 参照に結び付く仕組みは、Environment の秘密情報と、OIDC の主張を確かめる受け手(GitHub Pages の配備が先例)だけである。同じリポジトリのブランチへの push には、確かめる受け手が無い
- 外部の指針(OWASP CICD-SEC-1・4・5・6、SLSA の Trusted Robot、NSA・CISA)は、短命の資格情報を優先することと、レビューを経ないコードを走らせる文脈へ資格情報を渡さないことを、別の要求として並べる。短命であることで後者を代える根拠は見つからなかった
- 旧い G-8 の文は置き場を秘密情報に限るため、指針が最も推す形(OIDC と確かめる受け手)を満たす形として読めなかった
- **リモートの実状は、ADR-0077 が開示していた状態より悪い**。本リポジトリの #293 以降の変更は、2026-10-27 時点でリモートの `main` に入っていない。リモートの `main` では旧い `publish-standard.yml` が動いている。このワークフローは最上位で `contents: write` を持ち、Environment を使わず、強制 push で配り、`workflow_dispatch` で起動できる。ルールセットは空で、`main` と `dist/standard` は保護されていない

## 決定

### 1. G-8 の資格情報の規定を、置き場の指定から性質の規定へ改める

配備の資格情報は、次のどちらかの形で、配備を許す参照(既定ブランチ、またはリリースのタグ)に結び付けます。

- (a) 配備を許す参照に限った、配備の環境の秘密情報
- (b) 発行する側か受け取る側が、実行の参照、または配備を許す参照に限った配備の環境を確かめてから発行・受理する短命の資格情報(OIDC と、それを確かめる受け手)。配備の環境を確かめる受け手は、その配備の環境が参照に限られている場合に限り当たる。Environment を参照したジョブの OIDC の `sub` には、参照が入らないため

これに加えて、次の (c) を満たすことを求めます。

- (c) ジョブのトークン(またはブランチで書き換えられる場所から得られる資格情報)が配備先に届く場合、配備先は、参照に結び付いた資格情報以外からの書き込みを拒む(例: 配備先の参照のルールセットで更新を限り、迂回を結び付いた資格情報だけに許す)

**(c) を満たさない構成は、(a)(b) を使っていても未達です**。配備先が同じリポジトリの参照なら、(a) の形を使っても、どのブランチのワークフローもジョブのトークンで書き込めるためです。#293 の裁定 J-6 の b・d は、資格情報の置き場と配備先の側の限定を対で持っていました。#346 の裁定(R-1)は前者だけを規範にし、後者を落としていました。突合(`research/346-deliberation/crosscheck.md` の X-1)の指摘を受け、議長が誤りと認めて (c) を足しました(`decision.md` §8)。(c) は配布用のブランチの保護を独立の要求事項にするものではなく、ジョブのトークンが配備先に届く場合の条件です。

**ワークフローのファイルの権限の宣言だけから権限が生じるトークン(`GITHUB_TOKEN`)は、短命であっても、(a)(b) のどちらにも当たらない**と本文に明記します。「短命の資格情報を用いる」は推奨とし、要求事項にしません。(a) の形で長期の鍵を配備の環境の秘密情報に置く構成も、規定を満たします。

議題が置いた論点「トークンは、起動した者が既に持つ能力を超えない」は、採りません。次の3つの経路で崩れるためです。

- 「Actions に PR の作成と承認を許す」設定のもとでは、`GITHUB_TOKEN` が PR を承認できる。書き込みの権限を持つ者が、自分のブランチのワークフローで自分の PR を承認させられる
- 範囲を狭めた資格情報を持つ者(AI エージェントを含む)も、ワークフローの `permissions` で、自分の資格情報に無い権限をトークンへ与えられる
- 書き込みは `github-actions[bot]` の名義になり、責任者が git の履歴から消える

さらに、配布先に保護を掛ければ、このトークンも同じく止まります。トークンだけを除外する公式の手段はありません。この読み方で適合になるのは、配布先が誰にも保護されていない構成だけです。

(b) の形は実証が薄いため、新しい根拠水準マーク EV-0184(E1)で開示します。EV-0137 は再利用しません。EV-0184 の差し替えには、EV-0137 と同じく対の確認を当てます。(b) の受け手が既定ブランチ以外の発行を拒むことと、`environment:` を外したジョブの発行が受理されないことの2つです。拒まれた記録だけを証拠に数えません。

### 2. 未達に「手段はあるが、組織が使わないと決めた場合」を足し、記録の中身を定める

旧い文の未達は、手段を使えない場合だけでした。使えるのに使わない場合が書かれておらず、読み手は省略と区別できませんでした。次の2つを未達とします。

- 手段が無い場合(契約の条件などにより、配備の環境の秘密情報・配備の参照の限定・参照を確かめる受け手・配備先の書き込みの限定のどれも使えない)
- 手段はあるが、組織が使わないと決めた場合。この決定は人が記名で行い、決定者の欄に AI の名義を書かない

未達の記録には、次の3つを書きます。

- 開いている経路
- その経路を持つ主体と、その主体が配備先へ直接書き込めるかどうか
- 経路を狭める措置と、その措置が止めないもの

### 3. 配備の語を 1.4 で定義し、G-8 とフェーズ5 の「実行環境」を「配備の環境」へ改める

第1章 1.4 に「配備の資格情報」「配備の環境」「参照に結び付いた資格情報」を足します。G-8 と `ci-gates.md` の「統制と資格情報の置き場」の「実行環境」は「配備の環境」へ改めます。第5章 5.8.6 と成果物の様式は「実行環境」を AI エージェントの環境の意味に使っており、衝突するためです。5.8.6 などのほかの用法は変えません。

一般の語「資格情報」は定義しません(課さないと決めた)。第4章 G-5 の基準7・第3章 3.5・第5章 5.8.6 が、それぞれ別の範囲で使っているためです。第3章 3.5.3 の「認証情報」との関係は、1.4 の「配備の資格情報」の行に注記します。

### 4. フェーズ5 に、止めるもの・止めないもの・監査で読む値の表を置く

`ci-gates.md` に「GitHub には、このトークンの書き込みを参照で限る機能はありません(2026-10 時点の GitHub Docs)」と書きます。各措置の行に、何を止めるか・何を止めないか・監査で読む値を書きます。行は次のとおりです。

- 参照に限った配備の環境の秘密情報、OIDC と確かめる受け手、配備先の書き込みを結び付いた資格情報に限ること(適合の手段)
- `GITHUB_TOKEN`(ジョブの権限)
- Workflow permissions の既定、Actions による PR の作成・承認
- `environment:` の参照、`.github/workflows` の CODEOWNERS、ワークフロー実行の保護
- 配布先のルールセット、Restrict file paths
- 主体の資格情報から管理者の権限と `workflow` の範囲を外すこと

(a)(b)(c) の3行だけを適合の手段とし、ほかの行は狭める措置とします。旧い文の「ファイルの外の設定だけが、この経路を止めます」は、`GITHUB_TOKEN` については誤りでした。直します。

「`.github/workflows` を変えるコミットの push には `workflow` の範囲が要る」は、一次資料で確かめました(GitHub Docs の OAuth の範囲の表と、個人のアクセストークンの頁。2026-10-27)。同じパスと内容のファイルが同じリポジトリの別のブランチにあれば、範囲が無くてもコミットできるという例外も、同じ表にあります。

### 5. 本リポジトリの配布は変えず、未達(使わないと決めた)としてリモートの実状に合わせて開示する

本リポジトリの配布を、条項に合わせて変えることはしません。未達の区分は「手段はあるが使わないと決めた」とし、決定者は保守者です。旧い開示の「手段が無い」に当たる読み方は事実と違います。リポジトリは公開で、Environment の秘密情報も配備の参照の限定も使えるためです。

鍵を使わずに適合する道は、配布の経路を変えることだけです(Pages を使う形、受け手が出どころを確かめる形)。この変更は、テンプレートと submodule の利用者が頼るインタフェースを変えるため、所有者が決める事項として後継の Issue の候補にします。

開示は、リモートの実状(旧 `publish-standard.yml` が動き、ルールセットが空)に合わせて[プロジェクト運営](/process-compass/community/project-management/)で正します。所有者が行う設定は、順序つきの一覧として同じ頁に置き、設定の記録は #346 に残します。AI のセッションは、設定済みと書きません。

EV-0137 の差し替え条件を、対の確認に改めます。(a) 配備の環境を使うジョブが、既定ブランチ以外から拒まれること。(b) `environment:` を外して書き込みの権限を宣言したワークフローが、書き込めるかどうか。(b) は使い捨ての参照で確かめ、`dist/standard` そのものでは試しません。(a) だけを適合の証拠に数えません。

### 6. 準拠テンプレートにデプロイの雛形を足さず、env-check に狭める措置の事実を読ませる

テンプレートにデプロイのワークフローの雛形は足しません。意図した省略として、IMPL-0237 を降りていない規定のまま、採用者に委ねる(`plan=adopter`)形で残します。配備先が案件ごとに違い、(b) の受け手は配備先に依るため、雛形は未達を配る形になります。

採用者に求めることは次のとおりです。デプロイのワークフローを足すときは、(a)(b) のどちらかの形で資格情報を得て、ジョブのトークンが配備先に届くなら (c) を満たします。`GITHUB_TOKEN` で書く場合は、未達として決定2 の3項目を記録します。

導入前の検証の `env-check` は、Workflow permissions の既定、Actions による PR の承認の可否、Environment(`delegated-merge` を含む)の配備の参照の限定を読みます。配備の参照にタグの規則があれば、タグのルールセットのパターンとタグの作成の限定も読み、限定が無ければ不一致とします。Environment の有無に依らず、リポジトリの秘密情報と変数の名前(値は読まない)を読み、委任のトークン(`DELEGATED_MERGE_TOKEN`)が Environment の外にあれば不一致とします。一覧はページ送りで読みます。読めない場合(403 など)は「未確認」と出し、通過にしません。これらの値は、G-8 の適合の判定には使わず、事実として出します。実装マークは IMPL-0351 とします。

### 7. 記録の扱い

`research/293-deliberation/implementation.md` は書き換えず、日付つきの追記の段落だけを足します。公開の記録には「保守者の決定(2026-10-23)」と、決めた中身を書きます。保守者の指示の原文は `research/` にだけ置きます。原文を公開するかは、所有者が決めます。

### 8. 本件で決めないこと

次は、本 ADR では決めていません。課さないと決めたのではなく、後継の Issue の候補として残しています。

- 配布の経路の変更(Pages・受け手の検証・成果物の来歴の証明・`dist/standard` の各コミットと `main` への push の成功した CI の実行との突き合わせ)
- 「実行環境」「資格情報」「認証情報」の語の全体の統一
- 準拠テンプレートの workflows の最小権限(最上位の書き込みの権限をジョブ単位へ下ろすこと、`delegation.yml` の `pull_request_target`・`workflow_run` の機械の検査)
- 来歴の証明(artifact attestation)

## 検討した選択肢

| 案 | 採らなかった理由 |
| --- | --- |
| 短命を理由に `GITHUB_TOKEN` を認める | 指針は、短命とレビューへの結び付けを別の要求とする。短命は、誰が発行させられるかを変えない |
| 「起動者が持たない能力」に条項の目的を読み直し、条件つきで認める | PR の自己承認・権限の昇格・名義の消失の3つの経路で崩れる。配布先に保護を掛ければトークンも止まるため、この読み方で適合になるのは、保護の無い配布先だけである |
| 条項を置き場の指定のまま保つ | OIDC と確かめる受け手(指針が推す形)が、満たす形として読めない |
| 本リポジトリを「適用外」とする | 採用者が `dist/standard` を submodule で固定して取り込む。手段もある。適用外と書くと、規範を書いた側が規範の検証の場を手放す |
| 鍵を置く | 保守者の決定(前提)により審議の対象にしなかった |
| Environment・CODEOWNERS・ワークフロー実行の保護を適合の手段に数える | どれも、ブランチ上のワークフローからトークンの書き込みに届く経路を止めない |
| 一般の語「資格情報」を 1.4 で定義する | 第4章 G-5 の基準7・第3章 3.5・第5章 5.8.6 が別の範囲で使っており、定義がそれらの範囲を動かす |
| EV-0137 の差し替えを「既定ブランチ以外から拒まれた記録」だけで行う | Environment を外した経路を確かめない。拒まれた記録は、統制が成り立たないことを隠す |
| テンプレートにデプロイの雛形を足す | 未達を雛形として配ることになる |

## 影響

- 第4章 G-8 の節は、(a)(b) の2つの形と配備先の側の条件 (c)、`GITHUB_TOKEN` の除外、短命の推奨、未達の2つの区分と記録の3項目を持つ。EV-0184 を付けた
- 第1章 1.4 に3語が加わる。G-8 と `ci-gates.md` の当該節の「実行環境」は「配備の環境」になる
- `ci-gates.md` に、措置ごとの表(区分・止めるもの・止めないもの・監査で読む値)が加わる。EV-0137 の対象と差し替え条件が改まる
- IMPL-0237 は `plan=adopter`(決定の所在は本 ADR)へ移る。[実装マークの規約](/process-compass/community/implementation-marking/)の「採用者に委ねる理由の置き場」は、ADR-0084 決定4 の表に限らず `decision=` が指す ADR を含むよう改まる。ADR-0084 は採用済みで本文を書き換えられず、新しい `plan=adopter` の理由をその表へ足せないため。降り先 `deploy-workflow` の説明は、本文の範囲(既定ブランチ、またはリリースのタグ)と2つの形に合う
- 準拠テンプレートの `env-check` の項目が6から9へ増える。Environment の項目は、タグの作成の限定と、Environment の外の委任のトークンの名前も読む。旧い記録は、足した3項目が未確認(実行していない)と読まれる。強める向きの変更であり、採用者は env-check を実行し直す。Actions の設定の読み取りは管理の権限を要する
- [プロジェクト運営](/process-compass/community/project-management/)の開示は、リモートの実状と未達の区分に合わせて改まる。所有者の設定の一覧と、記録の宛先(#346)が置かれる。#293 以降の変更がリモートの `main` に入るまで、`dist/standard` は旧いワークフローの強制 push で配られ続ける。本リポジトリの配布は (c) も満たさない。鍵を置かない前提のもとでは、迂回を許す結び付いた資格情報が無いため
- 本リポジトリの公開(ジョブ `deploy`)は (b) の形だが、`main` 以外から拒まれた記録はまだない
