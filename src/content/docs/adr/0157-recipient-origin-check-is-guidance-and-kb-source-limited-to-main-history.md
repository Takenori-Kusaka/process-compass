## ステータス

採用(2026-11-17)。[ADR-0090](/process-compass/adr/0090-job-token-and-deploy-credential-binding/) の決定8 のうち、「受け手の検証」と「来歴の証明(artifact attestation)」の2項目を、候補から決定へ移します(一部置き換え)。決定8 のほかの項目(配布の経路の変更のうち Pages と、`dist/standard` の各コミットと `main` の CI の実行との突き合わせ、語の全体の統一、準拠テンプレートの workflows の最小権限)は候補のまま残します。[ADR-0052](/process-compass/adr/0052-delivery-is-verified-at-the-destination/) の決定2、[ADR-0077](/process-compass/adr/0077-repository-ci-wiring-and-distribution/) の `VERSION.md` が自由に書けることの開示、[ADR-0083](/process-compass/adr/0083-standard-edition-end-of-application-and-deviation/) の第1章 1.10.2 は維持します(置き換えません)。軽の審議の結論です(Issue [#332](https://github.com/Takenori-Kusaka/process-compass/issues/332)、`research/332-deliberation/`)。

決定3 の配る側の検査は、2026-11-18 に実装済み(`scripts/check-gate-criteria.mjs`、試験は `scripts/test-kb-ancestry.mjs`)。以下の本文の「未実装」は採用時点(2026-11-17)の記述です。

## コンテキスト

#332 は、配布物(`dist/standard`、準拠テンプレートの知識ベース)の生成元を、受け取り側に確かめる手段が無いことを問いました。あわせて、PR を経ない1名の体制での検査の段の構成を問いました。

審議の中で、実行して確かめた事実があります。

- 準拠テンプレートは `dist/standard` を submodule で固定する形ではない。保守者が `npm run template:kb` で複製した知識ベース(`scripts/vendor/tailoring-kb.json`)を同梱し、適用の表明が名指すのはその `source.commit` である
- 確かめた時点(2026-11-17)のテンプレートの main が同梱する知識ベースの `source.commit`(59425d2e21db…)は、**標準の main の祖先ではなく、標準のどのブランチからも到達できない**。束ごとの rebase の前に生成したコミットを名乗ったまま、同じ変更が別のコミットとして main に入ったためである。中身は、`source.commit` の行を除いて `dist/standard` の知識ベース(生成元 154c2086…)とバイト一致した。誤っているのは識別だけである
- 既存の検査はこれを通した。`commitProblems` は 40 桁の16進の形式だけを見る。知識ベースの乖離の検査は、[#301](https://github.com/Takenori-Kusaka/process-compass/issues/301) によりコミットを除いて比べる。`editionAt` は到達できないコミットを「発行の時点でない」と読み、失敗にしない

最初に見つかった食い違いは、配る側(標準からテンプレートへの複製)の rebase の手順が生む、表示と実態の食い違いでした。悪意でも強制 push でもありません。この食い違いは直っていません(決定3)。

## 決定

### 1. 受け取り側の生成元の確認を、採用者の義務にしない。手順を手引きに置く

- 第1章 1.10.2 は変えない。確認の実施も、適用の表明への確認の結果の併記も、課さない
- 手順は[本標準の版の発行](/process-compass/community/standard-editions/)の「受け取り側が生成元を確かめる手順」に置く。適用の表明の読み手・監査する者・採用者のだれもが、適用の開始と版の切り替えのときに行える
- 手順は、取り込みの形ごとに2つの条件を確かめる。来歴(名指したコミットが標準の `main` の祖先か、`dist/standard` を固定する形では `D` が `origin/dist/standard` の上にあるか)と、中身(CI の生成物と一致するか)である。正本の URL から取得した clone で行う。どちらも決定可能な条件(存在と一致)である
- 保証しないことを手引きに明記する。本文が正しいこと、確かめた後の `main` の書き換え、保守者の権限で `main` へ書かれた変更は、検出しない
- 手順は、使い捨てのリポジトリの例と2026-11 の配布物の1時点で確かめただけである。根拠水準は EV-0301 で開示する

### 2. artifact attestation を、文書の配布に課さない

- GitHub は個別の文書ファイルを対象にすべきでないとしている(FND-0100)。git のコミットとして取り込む形と型が合わない。署名は、どのパイプラインと ID でビルドしたかを言い、保守者の書いたコードを処理したことも中身の良さも言わない(SRC-0459#c1、SRC-0415#c1。FND-0100、水準 E1)
- 再開の条件は、配布を単一の成果物(tarball・パッケージ)にするときである

### 3. 複製する知識ベースの生成元を、標準の `HEAD` の祖先に限る。ただし降ろすまでの間は未実装とする

- 規定: 標準の `npm run check` が、既定の対象(テンプレートへ複製した知識ベース)の `source.commit` が標準の `HEAD` の祖先であることを求める(`git merge-base --is-ancestor`)。履歴を読めない場合(浅い clone、コミットの対象が無い)は、未確認を通さず失敗とする([#293](https://github.com/Takenori-Kusaka/process-compass/issues/293) 裁定 J-3)。祖先であることは `HEAD` が進んでも保たれるため、コミットを比較から外した #301 と衝突しない
- **未実装(標準のリポジトリの検査をまだ実装していない。ゲートの状態の「未達」ではない。実装マークの対象ではない)**: この検査は、本束(B11)では実装していない。現在のテンプレートの main の知識ベースが祖先でなく、検査を入れると `npm run check` が落ちるためである。準拠テンプレートを触る束が、知識ベースを再生成するときに、検査を同時に入れる。**降ろすまでの間は未実装**であり、上の食い違いはそれまで直らない
- 同じ理由で、手引きの条件1 の祖先の確認は、今の同梱の知識ベースを失敗にする。手引きはこれを隠さず開示する
- 採らない案: テンプレートの契約検査へ入れる(ネットワークに依存し、正本の書き換えで後から落ちる)。採用者のテンプレートに 40 桁の形式と `VERSION.md` との一致の検査を足す(採用者のテンプレートは `VERSION.md` を持たず、形式は配る側で既に見ている)

### 4. 実行の番号の突き合わせと配布の経路は、候補のまま残す

- `dist/standard` の各コミットと `main` の CI の実行との突き合わせ、配布の経路の変更(Pages)は、本件で決めない。番号を自由に書ける場所へ足しても、権限者の偽装は検出できないためである
- `main` と `dist/standard` への、Actions だけが書けるルールセットは範囲外とする

### 5. 1名の体制の段の列を足さず、集約が落ちた後の revert・ロックを課さない

- [Git 戦略](/process-compass/phase5-implementation/git-strategy/)の1名の行を正本とする。[計算資源の戦略](/process-compass/phase5-implementation/compute-strategy/)には、段の構成の差を書く1段落だけを足す。1名の体制の列や節は新設しない(二重になり乖離のもとになるため)
- 集約が落ちた後の revert・既定ブランチのロックを、求めない。公開と配布を集約の通過に結線した体制では、落ちた版は外へ出ない。「望ましい」の推奨も書かない。推奨の語は根拠水準マークを要する実務の主張になり、出典が E0〜E1 で支えられないためである
- 計算資源の戦略の「PR」の語2か所は、変更ごとの検査を指す中立の語に直した(編集の指摘)

## 検討した選択肢

| 案 | 採らなかった理由 |
| --- | --- |
| 1.10.2 に確認の結果(済の日付と条件、または未実施)の併記を求める | 必須の併記事項を足すと、表明の成立条件を変え、採用者への新しい義務になる。「済」は自由に書ける自己申告で、`VERSION.md` が自由に書けるという弱点と同じ型である。表明の読み手は、名指されたコミットについて同じ手順を自分で再現できる。前提の配布物 `docs/` と生成元の本文の一致は、知識ベースだけを持つ準拠テンプレートの採用者に使えない |
| 併記を「してよい」とする任意の条項 | 何も規律せず条文を増やすだけである。添えることは条文が無くても禁じられていない。手引きに書けば足りる |
| 確認の実施の義務化 | 新しい義務である。実証は1時点(EV-0301) |
| 祖先の確認だけを手順とする | 実在のコミットを名乗って中身を差し替えた配布物を通す |
| `docs/` の比較と `source.commit` の一致だけを `D` の条件とする | 知識ベースの判定基準だけを差し替えた配布物を通す(1巡目の独立の突合 T8 で確かめた)。`D` が `origin/dist/standard` の上にあることを足した。`dist/standard` への早送りの書き込みは検出しない |
| 採用者が再生成して知識ベースまで一致を見る | 採用者の環境に生成の一式が要り、node の版などで結果が揺れる。CI の生成物との比較で同じことを決定可能に確かめられる |
| artifact attestation を課す | 決定2 |
| テンプレートの契約検査で祖先・中身まで自動化する | 決定3 |
| 本束で実行の番号の突き合わせを実装する | 検出できるものが手順の2条件と重なる。権限者の偽装は検出しない |
| ADR を立てず手引きの冒頭だけに書く | ADR-0090 決定8 の「課さないと決めたのではない」の文言と食い違ったまま残る |
| ADR-0077 の `VERSION.md` が自由に書けることの開示を置き換える | 開示は配る側の弱点として今も正しい。手順は弱点を消さず、別の確かめ方を足すだけである |
| 計算資源の戦略に1名の体制の列・節を新設する | Git 戦略と二重になり乖離のもとになる |
| Git 戦略の1名の行に「プッシュ前が重くなる」を足す | 段の構成の説明は計算資源の戦略の役目で、1名の行は体制の条件を書く場所である |
| revert の義務、ロックの義務、「望ましい」の推奨 | 決定5 |

## 影響

- 義務は動かない。採用者・準拠テンプレートの採用者に、新しい義務は生じない
- 決定3 の検査は降ろすまで未実装である。重大度が高い食い違い(辿れない `source.commit` の同梱)は残る。再生成と検査の追加は、準拠テンプレートを触る束が同時に行う。それまで、手引きの条件1 は今の同梱の知識ベースで失敗する
- 語: 1.10.2 の「配布物のコミットの識別」と、テンプレートの表示「標準のコミット」(`source.commit`)の語の食い違いは、本件では直さない。どちらも手引きの手順で `main` まで辿れる
- 根拠水準マーク: EV-0301 を足した(手引きの手順。1時点の事実)
- 実装マークは足さない。1.10.2 を変えず、実行主体を制約する規定が増えないためである
