## ステータス

採用(2026-10-23)。一部置き換え(→ ADR-0090 の決定1・2): 決定6 の「標準:」の段落のうち、資格情報の置き場を「配備を許す参照に限った実行環境の秘密情報」に指定する文と、未達を「プランにより手段を使えない場合」に限る文は、[ADR-0090](/process-compass/adr/0090-job-token-and-deploy-credential-binding/)の決定1・2 が置き換えました。資格情報は、参照に限った配備の環境の秘密情報か、参照を確かめる受け手が発行・受理する短命の資格情報のどちらかの形で参照に結び付け、`GITHUB_TOKEN` はどちらにも当たりません。未達には、手段はあるが使わないと決めた場合が加わりました。決定6 の開示の段落の「#293 で別に扱う」は、ADR-0090 の決定5 で決着しました。決定6 の「運営:」の段落は置き換えていません(2026-10-27)。

本 ADR は、採用の時点で採用済みの ADR の決定を置き換えていません。[ADR-0033](/process-compass/adr/0033-no-target-as-recorded-state/) 決定2 の範囲を明確にし、[ADR-0052](/process-compass/adr/0052-delivery-is-verified-at-the-destination/) 決定1 の「配布物」が `dist/standard` を含むことを記録します(後掲「既存の決定との関係」)。両 ADR のステータスの節は変えていません。

## コンテキスト

[#293](https://github.com/Takenori-Kusaka/process-compass/issues/293) は、本リポジトリの運営(CI・公開・配布)の欠陥をまとめた Issue です。#260・#277・#280・#281 の残りを含みます。運営の決定と、標準の条項の変更が混ざっていました。

指摘をそのまま条項にせず、調査2本と会議体5名の意見書で扱いました。記録は `research/293-deliberation/`(`decision.md` の J-1〜J-9)にあります。

### 見つかったこと

- 検査の一覧を書いた箇所が 8 か所あり、すべて `package.json` の `check` と食い違っていた
- サイトの公開(`deploy.yml`)と標準の配布(`publish-standard.yml`)は、CI の検査を待たずに走っていた。公開していたのは、検査とは別に2回目のビルドをした生成物だった
- 準拠テンプレート(`template/`)を読む検査は、テンプレートが無いときの扱いが割れていた。飛ばすもの、「一致」「違反なし」と黙って通すもの、失敗するものが同じ `npm run check` に並んでいた
- 配布の知識ベースの生成元の版が `'unknown'` のときに、検査を通っていた。`dist/standard` は配布物として検査されていなかった
- `dist/standard` は配るたびに孤立したコミットへ強制 push され、過去の配布の多くがどの参照からも辿れなくなっていた。案件が submodule で固定した版を取り直せる保証が無かった
- 配布のワークフローは `contents: write` を持ち、起動元の確認と実行環境を持たなかった。書き込みの権限を持つ者は、自分のブランチへ置いたワークフローから `dist/standard` を書き換えられた
- 準拠テンプレートの委任のマージの経路は、マージのトークンをリポジトリの秘密情報に置く手順だった。手動の起動は選んだブランチの定義で動くため、同じ穴があった

## 決定

### 1. 検査の一覧の正本は `package.json` の `check` だけとする

説明の側(CLAUDE.md・README・CONTRIBUTING・PR テンプレート・プロジェクト運営の頁)は列挙せず、`check` を参照します。`scripts/check-ci-wiring.mjs` を `check` に入れ、`ci.yml` の結線を YAML の構造で確かめます(契機、`npm run check` の手順、サブモジュールの取得、`needs: check`、最上位の権限、配布の実行環境)。

散文の列挙を機械で禁じることは課しません。散文の検出は偽陽性を生み、G-5 の3条件の1つ目を満たさないためです。

### 2. 公開と配布を、CI の検査の通過に繋ぐ

公開と配布を `ci.yml` のジョブにし、`needs: check` と「main への push」の条件で繋ぎます。公開するのは、`check` が作ったビルドそのものです。`workflow_run` は採りません。検査に落ちた版は、サイトと `dist/standard` のどちらへも出ません。代わりに、検査の違反1件でサイトの更新が止まります。完了の定義の「サイトに公開されている」の遅れは、信頼性の代償として受け入れます。

### 3. 検査器の入力の欠如を、「対象なし」と名乗らせない

運営: 検査器の入力(`template/` など)が無いときは、手元でも CI でも検査を失敗させます。空のディレクトリも無いものに数えます。失敗の文言に取得の命令を出します。

標準: 第4章 G-5「検査対象が存在しない場合の扱い」に、入力の欠如は「対象なし」に当たらず、G-5 の判定で失敗に数えることを置きます。**これは ADR-0033 決定2 の置き換えではなく、範囲の明確化です**。決定2 は対象が存在しない基準を扱い、入力が無いために実施できなかった検査を扱っていません。決定2 は「対象なし」の理由の中身を限っていないため、入力の欠如を理由に書けば今の文面で通っていました。この1文はその経路を閉じます。G-5 の基準の数(ADR-0033 決定1)は変えません。

起票の文「検査の対象が存在しないとき、検査を通過として扱いません」は採りません。決定2 と字面で衝突します。誤りは起票の文の側で、起票の事象は「対象が無い」ではなく「入力が無い」でした。

### 4. `dist/standard` を、ADR-0052 決定1 の配布物に含める

ADR-0052 決定1 の「配布物そのものを検査する」は、配布物を限定していません。`dist/standard` は同じ生成器の出力であり、範囲の拡張ではなく実装の欠落でした。配布のジョブで、生成の直後・push の前に、配る知識ベースを `check-gate-criteria.mjs --kb` で検査します。生成元の版(`source.commit`)は 40 桁の16進に限り、配布のジョブでは起動したコミットとの一致を求めます。`'unknown'` を通しません。テンプレート側の知識ベースにも 40 桁の16進を求めます。

### 5. 手元の結果を G-5 の判定の証跡にしない。段の中の順序と、手元の停止は課さない

第4章 G-5「判定基準を実装する検査と集約」に、手元で実行した検査の結果を G-5 の判定の証跡としてはならないことを置きます。段の中の検査の順序は定めません。基底で検査の定義が更新されたことを理由に手元の実行を止めることは、課しません(EV-0138)。

### 6. 配布は履歴を積み、書き込みはジョブ単位の GITHUB_TOKEN の権限で行う

運営:

- 強制 push をやめ、前回の `dist/standard` の上へ配布のコミットを積む。配る中身(本文・知識ベース・`VERSION.md`・`LICENSE`)は変えない。過去の到達できない配布は取り戻さない。配るかどうかは、配布済みの中身との差(`VERSION.md` と知識ベースの生成元の版を除く)で決める。前の配布が失敗しても、次の main への push で取り戻す
- 配布の資格情報は、ジョブ `publish` の `GITHUB_TOKEN` だけとする。`contents: write` は `ci.yml` の中でジョブ `publish` にだけ付け、最上位と他のジョブは読み取りに留める。deploy key・SSH 鍵・秘密情報は作らない(保守者の決定、2026-10-23)。トークンはジョブの終了で失効する。手順の中でトークンを扱わず、`actions/checkout` が設定した認証のまま、同じリポジトリの作業ツリー(`git worktree`)から push する
- ジョブ `publish` は Environment `dist-standard`(配備のブランチを `main` に限る)を参照する。この限定が止めるのは、このジョブを `main` 以外の参照で走らせることだけである。`GITHUB_TOKEN` は Environment に属さないため、限定は資格情報の置き場にはならない
- ジョブの先頭で、起動が main への push であることを確かめる(事故の歯止め。ワークフローのファイルを書き換えれば外れる)
- 全ワークフローの最上位の権限を `contents: read` にし、書き込みはジョブ単位で付ける
- `VERSION.md` に、起動の契機・ref・コミットを書く
- 必須レビュアは置かない。1名の体制の自己承認は独立した確認ではなく、記録として承認と誤読される
- `dist/standard` のルールセットは、削除と強制 push を禁じる。更新の制限(Restrict updates)は置かない。2026-10-23 時点の GitHub Docs で、ルールセットのバイパスに入れられるのはロール・チーム・GitHub App などで、`GITHUB_TOKEN`(GitHub Actions)を挙げていない。更新を制限すると、配布のジョブの push も止まる
- Environment・ルールセットの設定は、管理者(保守者)が行う。止まらない経路(書き込みの権限を持つ者による早送りの push を含む)とともに、[プロジェクト運営](/process-compass/community/project-management/)に書く

**本リポジトリの配布は、下の標準の規範「資格情報を実行環境の秘密情報に置く」を満たしません**。`contents: write` の付与はワークフローのファイルの中にあり、起動元のブランチで書き換えられます。本リポジトリは本標準に従う開発の案件ではありません([プロジェクト運営](/process-compass/community/project-management/))。それでも、規範を書いた側の運営が規範と食い違うことを、ここに開示します。食い違いを規範の側で解くか、運営の側で解くかは、本 ADR では決めません(#293 で別に扱う)。

標準: フェーズ5「CI/CD ゲート構成」のデプロイゲートに、「デプロイ・配布の統制と資格情報を、起動元のブランチで書き換えられるワークフローのファイルの中だけに置いてはなりません」を置きます(EV-0137)。資格情報は、配備を許す参照(既定ブランチ、またはリリースのタグ)に限った実行環境の秘密情報に置きます。本標準はリリースをタグで固定するため、既定ブランチだけには限りません。プランにより実行環境の秘密情報や配備の参照の限定を使えない場合(GitHub Free の非公開のリポジトリなど)は、この規定を満たせないことを、保証の開示に未達として記録します([ADR-0028](/process-compass/adr/0028-unmet-gate-distinct-from-omitted/)。満たしたものとして扱わない)。実行環境の自動作成、プランによる必須レビュアの制限、管理者の迂回を開示します。必須レビュアが使えない場合の G-8 の成立の条件は、本 ADR では定めません(別に検討する)。準拠テンプレートの委任のマージの経路は、同じ規範に合わせてトークンを Environment の秘密情報へ移します。Environment を参照するのは、組織が有効化した場合だけ動くマージのジョブに限ります(有効化していない採用者に、保護の無い Environment を作らせない)。配布用のブランチの保護を独立の要求事項にすることは、課しません。

## 検討した選択肢

| 案 | 採らなかった理由 |
| --- | --- |
| 検査の一覧の文書を置き、`check` と突合する | 一覧が第3の正本になる。ADR-0052 が同じ理由で却下した型 |
| 説明の側の列挙を直すだけにする | 8 か所すべてが同じ形で古くなった実績がある |
| `workflow_run` で CI の完了を待つ | 完了の順に起動し、古い版が新しい版を上書きしうる。起動元の SHA の受け渡しと条件の絞り込みを手で書く分だけ、誤りの入口が増える |
| 公開・配布を独立のまま、検査を待たないことを開示する | 検査に落ちた版を正本として出す経路が残る。開示で害は消えない |
| 入力が無いとき、手元は未実施と出して続け、CI では失敗させる | 手元と CI で「`npm run check` が通った」の意味が割れる。`check-impl.mjs` が既に template 無しで失敗しており、手元の `check` は通らない |
| 配布物を事後に週次で検査する | 配った後にしか見つからない |
| ワークフローのファイルの中の確認だけで配布を守る | 起動元のブランチでファイルを書き換えれば外れる |
| Environment に必須レビュアを置く | 1名の体制の自己承認は独立した確認ではない。プランによっては使えない |
| 配布専用の deploy key を Environment `dist-standard` の秘密情報に置く | 保守者の決定(2026-10-23)で採らない。長期の鍵は、管理・更新・漏えいの対象となる資格情報を1つ増やす。ジョブ単位のトークンはジョブの終了で失効する。代わりに、ルールセットで更新を deploy key だけに限る統制を失う(前掲) |
| `dist/standard` のルールセットで更新を制限し、GitHub Actions だけをバイパスに入れる | 2026-10-23 時点の GitHub Docs は、バイパスに入れられる主体に `GITHUB_TOKEN`(GitHub Actions)を挙げていない。更新を制限すると配布の push も止まる |
| 配布用のブランチの保護を標準の独立の節にする | 「配布物」は本標準の語として定義されていない。根拠は同じ作者の2件で、デプロイゲートの規範が資格情報の置き場で同じ穴を塞ぐ |
| 基底の検査の定義の変化で手元の実行を止める | 製品の先例が無く、根拠は1件。公式の判定が最新の基底に対して行われることで担う |

## 影響

- `npm run check` に、CI の結線の検査(`lint:ci`)とその陽性対照(`test:ci-wiring`)が加わる。`template/` を初期化していないと、`npm run check` は失敗する
- `deploy.yml`・`publish-standard.yml` は `ci.yml` のジョブ `deploy`・`publish` になる。検査が通らない限り、サイトの更新と配布は止まる
- 配布は、管理者の設定を待たずに動く。管理者に残るのは、Environment `dist-standard` の配備のブランチを `main` に限ることと、`dist/standard` のルールセット(削除・強制 push の禁止)である。設定の前に配布のジョブが走ると、保護の無い Environment `dist-standard` が自動で作られ、配布はそのまま成功する(止まる側には倒れない)
- 書き込みの権限を持つ者は、`dist/standard` へ早送りの push ができる。履歴は積み上がるだけで消せず、配布のコミットは `VERSION.md` に ref・コミット・実行の番号を持つ。`VERSION.md` は書き込んだ者が自由に書けるため、実行の番号を Actions の実行の記録と突き合わせて確かめる
- `dist/standard` の履歴は、以後の配布から積み上がる。過去の到達できない配布は戻らない
- 準拠テンプレートの委任のマージを有効化する組織は、Environment `delegated-merge` を作り、トークンをその秘密情報へ置く手順が1つ増える
- 本リポジトリの変更を main へ入れる前に、準拠テンプレート側の変更を template の main へマージし、サブモジュールの指す先を template の main の上のコミットにする必要がある
- 公開・配布・委任のマージの経路は、実際の GitHub 上で実行して確かめていない。構文は actionlint で確かめた
