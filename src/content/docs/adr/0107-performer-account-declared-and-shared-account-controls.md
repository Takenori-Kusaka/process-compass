## コンテキスト

[#429](https://github.com/Takenori-Kusaka/process-compass/issues/429) は、#380 の会議体で議題の外とした H-7 の後継です。調査(`research/429-deliberation/survey-429-*.md`)と、起案・現場・品質監査・規格・弁護の 5 委員の会議体を経ました。

### 見つかったこと

- 本標準の認証情報の規定は、席どうしの分離だけを扱っていた。席の責任者とその席の担い手が1つの認証情報を共有する構成には、禁止・推奨・開示のいずれも無かった。第1章 1.10.2 の「席ごとに認証情報を分けている」は、席の中の共有のまま字面で満たせた
- G-6 の「AI と bot の名義の承認は数えない」は、名義で AI を見分けられる前提に立つ。担い手が人のアカウントで出した承認は、人の承認として数えられた。品質監査の委員は、`gh pr review` を拒否していても `gh api` の `-f` で承認レビューを作れ、それを検査が独立した人の確認として数えることをコードで示した
- 担い手のアカウントを書く欄が、構成・D-0・`/process-init`・保証の開示のどこにも無かった。準拠テンプレートの中でも、手順書の前提が割れていた
- 外部: Copilot cloud agent はコミットの作者を Copilot とし、依頼した人の承認を数えない。Claude Code Action は既定で App として動く。ローカルの Claude Code は利用者の認証情報で動く。NIST SP 800-53 Rev.5 は IA-2 で利用者の一意の識別と代理のプロセスへの結び付けを求め、AC-2(9) で共有アカウントを説明責任の欠けとして扱う。OWASP Agentic Top 10 の ASI03 は「attribution gap」と「Identity Sharing」を挙げる。人の認証情報の共有を禁じる明文の条文は見つからなかった
- Co-Authored-By と署名は、人の名義の操作を人の操作と区別する証拠にならない

## 決定

### 1. 名義を申告させ、能力で判定する

担い手ごとに、名義(ホスティングが担い手の操作を誰の操作として記録するか)を構成で申告します。値は専用・共有・未申告で、未申告は共有として扱います。判定は能力で行います。担い手の実行環境から使える認証情報で、名簿の人のアカウントとして承認・レビュー・記録の push を作れる構成は共有です。実行環境の設定で拒否していても共有のままです。置き場は第3章 3.5.3「人と AI の担い手の名義」です。

### 2. 専用の名義を課さない。共有と未申告を列挙に無い離脱とする

課さないと決めた理由は、明文の規範が無いこと、禁止しても機械で確かめる手段が申告と照合に限られること、崩れる統制を統制ごとに扱えることです。第1章 1.10.2 には、既存の行(担い手どうしの認証情報)と別の行を足します。行を分けないと、2 名の体制が適合の主張の条件を共有のまま字面で満たせるためです。品質監査の委員の「1.10.2 に入れない」は採りませんでした。

### 3. 崩れる統制を統制ごとに扱う

| 統制 | 扱い |
| --- | --- |
| G-6 の承認(名義を共有する人のアカウント) | 条件1〜4 を満たせば数え、件数を保証の開示の項目1 に出す。適合の主張の根拠に数えない |
| G-6 の承認(専用と申告したアカウント) | 語の一致に依らず、数値の識別子で照合して数えない |
| 効力を持つ記録の帰属 | 名義を共有する記名者の操作だけでは数えない。名義を共有していない人の帰属の確認を要する。その人がいない体制では自己申告として受け付け、区別して開示する |
| 作成を指示した者の既定値・PR の作成者の別 | 変えない。作成の側の共有は、ブランチ保護と既定値が安全側に倒す |

G-6 と効力を持つ記録で扱いを分けた理由は、害を止める機会と後退経路の有無です。G-6 の承認は出荷判定の前に集約で読まれ、開示を見た出荷判定者が出荷を止められます。効力を持つ記録は、入った時点でマージを通し、事後の開示では取り消せません(ADR-0106 の決定の核)。

現場の委員は、共有のアカウントの G-6 の承認を数えない案を出しました。採りませんでした。共有の申告そのものが自己申告であり、数えない規定は正直に申告した採用者にしか効きません(品質監査の委員)。数えないと、人が実際に確かめた承認を捨て、2 名の体制で G-6 を差し戻し続けます。担い手が共有のアカウントで承認を作った事象が 1 件でも見つかれば、数えない側へ改めます(EV-0221)。規格・品質監査の委員の「効力を持つ記録も自己申告として数える」も採りませんでした。#380 が塞いだ、担い手が記名者の名義で例外承認のレビューを出してその場で通す経路が、再び開くためです。

### 4. 名義を担い手の識別に含めない

第3章 3.4.2 の識別(モデル・指示資産・権限の組)に名義を含めません。名義は席の判断を再現する力を変えず、含めると名義の変更だけで適合性確認が失効し、失効が実体と離れるためです。「権限の組」は実行環境の設定を指し、ホスティング上の権限は名義の側で扱います。名義の変更は変化点4 に数え、専用から共有への切り替えを緩める向きとします。

### 5. 権限設定と実行時のフックは抑止であり、分離に数えない

共有と未申告の担い手には、承認・レビュー・マージ・記録用ブランチへの push・ブランチ保護の変更・認証情報の読み出しを拒否する設定を置きます。準拠テンプレートでは、権限設定が `gh pr review` と `gh auth token` を拒否し、実行時のフック(`.claude/hooks/guard-bash.mjs`)が書き込みの形の `gh api`・GraphQL の mutation・`curl` による書き込みを拒否します。担い手が書いたプログラムから API を呼ぶ経路は止まりません。この設定を名義の分離として扱いません。`gh api` の全面の拒否は、読み取りの経路を壊すため採りませんでした。

### 6. 降ろす順序

名義の欄・契約検査・G-6 と集約での数え方・`/process-init` の問い・env-check の照合は、[#430](https://github.com/Takenori-Kusaka/process-compass/issues/430) で、名簿の数値の識別子による照合([ADR-0108](/process-compass/adr/0108-roster-matched-by-numeric-account-id/))と同じ単位で降ろします。本文の要求事項は本 ADR の時点で置き、降りていない規定として表示します。

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 共有の構成を禁じる。専用の名義を義務にする | 明文の規範が無く、守られているかを確かめられない禁止になる |
| 専用の名義を推奨と書くだけにする | 推奨は数え方を変えない。G-6 と効力を持つ記録の前提の穴が残る |
| 黙る | 「書かれていない」と「課さないと決めた」を区別できない |
| 1.10.2 の既存の行(席どうしの認証情報)へ読み込む | 主語が違う。2 名の体制の主張の条件を字面で満たせる |
| 1〜2 名の体制の申告を免除する | 共有が最も起きやすい体制で開示が消える |
| 設定で拒否した共有を専用に数える | 担い手が書いたプログラムから API を呼ぶ経路が残る |
| 共有のアカウントの G-6 の承認を数えない | 決定3 |
| 効力を持つ記録を自己申告として数える | 決定3 |
| Co-Authored-By・署名・監査ログの `actor_is_agent` を区別の証拠にする | 人の名義の操作を区別しない。監査ログの印は Copilot に限られ、プランに依る |
| 名義を担い手の識別に含める | 決定4 |
