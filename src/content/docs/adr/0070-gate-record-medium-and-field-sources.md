## コンテキスト

[#321](https://github.com/Takenori-Kusaka/process-compass/issues/321) は、ゲート判定記録の成立手続を問いました。起票者の訴えは「帳票の手間で統制するのではなく、強制層でマージを止めるべき。帳票の記入を AI に任せられないのは非効率」でした。指摘をそのまま条項にせず、調査・会議体・突合の順で扱いました。記録は `research/phase4-standard/` にあります。

- 調査 4 本: `gate-record-00-internal-inventory.md`(本標準の内部の棚卸し)と `gate-record-01-regulatory.md`(規制と規格)。`gate-record-02-github-mechanics.md`(ホスティングの機構)と `gate-record-03-industry-practice.md`(業界の実務)
- 会議体: 5 名の第1巡と 3 名の第2巡(`321-council-00-brief.md`〜`321-council-05-defender-r2.md`)
- 決定の正本: `321-decision.md`

### 起票の記述のうち、事実として成り立たなかった 2 点

起票者の記述のうち、次の 2 点は現物で確かめた結果、成り立ちませんでした。

- 「リベースで対象の SHA が変わるたびに記録を作り直す」。第6章 テンプレ4 の対象は PR 番号で書けるため、リベースは記録の作り直しを要しない
- 「`check-pr.mjs` は基底ブランチの `docs/gates/` しか読まない」。基底ブランチの台帳を読むのは停止の解除と例外承認に限られる。G-6 の承認者数の検査は `docs/gates/` を読まない

一方で、起票者の訴えの半分は正しいと判定しました。氏名・日時・対象を手で書く欄は、誰が判定したかを裏づけません。裏づけるのはホスティングの承認レビューです。

### 現行のテンプレートが、既存の決定と揃っていなかった

準拠テンプレートの `/gate` スキルは、判定 1 件ごとに記録だけの PR を立て、判定者以外の承認者を課していました。この置き方は、次の 3 つの決定と揃っていませんでした。

| 既存の決定 | 内容 | テンプレートとの食い違い |
| --- | --- | --- |
| [ADR-0057](/process-compass/adr/0057-organizational-quality-assurance/) | 層1 の改版に PR を課すと別の承認者が要り、記名の意味と二重になる | 記録の取り込みに別の承認者を課していた |
| [ADR-0058](/process-compass/adr/0058-size-over-is-confirmed-not-blocked/) | PR 2 本・承認 2 回の構成を却下した | 本体 PR と記録 PR の 2 本になっていた |
| [ADR-0067](/process-compass/adr/0067-purpose-of-two-approvers/) | 承認者 2 名の目的は、1 名の承認だけでは変更を取り込めない状態を作ること | 記録だけのコミットは変更の取り込みではない |

第5章 CI/CD は、判定記録だけのコミットを製品の変更の対象外と定めています。テンプレートはこの定めを強制層へ降ろしていませんでした。

### 2 名体制で、中身を見ない承認を制度が生んでいた

2 名体制では、本体 PR の作成を指示した者は、相手の立てた記録 PR の承認者になります。承認者は本体の変更を見ておらず、記録の中身を確かめる材料も持ちません。中身を見ずに承認するしかない構造を、現行の手続が自ら作っていました。起票者の懸念「中身を見ないままマージされる」は、帳票の有無ではなく、記録を基底ブランチへ届ける儀式から生じていました。

### 規格が記録に求めるもの

規制と規格の調査(`gate-record-01`)は、承認の記録に求められる性質を、帰属(誰が)、同時性(いつ)、対象とのリンク、改変不能、保持と取り出し、意味の事前の定義として整理しました。手で書いた帳票は、このうち帰属と同時性と対象とのリンクを自ら示せません。ホスティングの承認レビューは、これらを機械の記録として持ちます。一方で、判定の理由と確認した観点は、どの媒体でも人が書かない限り残りません。規格は媒体を紙か電子かで区別せず、同じ期待を両方に置きます。ただし、システムの記録を記録と認めるには、保持・取り出し・帰属の対応表・意味の定義を組織の側で定めることが要ります。条件が無ければ「ホスティングにある」は記録の証拠になりません。

## 決定

### 1. 判定記録の媒体を限定しない

工程ゲートの判定は、判定記録の作成をもって成立します(ADR-0036 決定1。変えません)。判定記録とは、第4章「判定の成立」の定める欄が埋まった記録であり、第6章 テンプレ4 はその様式の正本です。欄を運ぶ媒体を、本標準は様式のファイルに限定しません。ホスティングのレビューが欄を運び、案件の構成が事前に対応づけ、第5章の保全の条件(決定8)を満たすとき、そのレビューは判定記録です。欄を運ばない操作(Issue のクローズ、PR のマージ、ラベルの遷移、承認の操作そのもの)は、引き続き事務です。

### 2. 機械が出す欄と人が書く欄を分ける

| 機械が出す欄 | 人が書く欄 |
| --- | --- |
| 推定を含まない写し。出所を併記する | 判定者本人が自分の言葉で書く。AI に生成させない |
| 判定者(アカウントの数値の識別子と名簿の席)、判定日時、提出日時、対象(PR 番号・コミットの識別子・レビューの識別子)、結果(宣言行から)、参照した D-0 の版、承認の数、作成を指示した者との別 | 挙動要約、確認した項目、確認していない事項、差し戻し理由(項目番号と再提出の期限)、決断の記録、比較した選択肢の採否の理由、リスク区分の確定者の記名 |

第6章の欄は 1 つも減りません。[ADR-0040](/process-compass/adr/0040-template-forms-as-subset-of-standard/)の omit でも逆の指示でもなく、欄の出所の指定です。先例は、第7章 7.3 の記録者と承認者、D-0 の要求事項、IMPL-0062 にあります。「転記」の語は附属書C の「AI 転記」と衝突するため使わず、「機械が出す欄」「写し」と書きます。

### 3. 人が書く欄の受け皿は 2 つに限る

- 対象が PR として存在する判定(G-6。および G-2・G-3・G-4 で仕様・ADR が PR として存在する場合): 判定者本人のレビューの本文
- それ以外(G-1・G-7・G-8・SG、例外承認、停止の解除、対象が PR でない場合、ホスティングが決定8 の条件を満たさない場合): 判定記録(様式)
- PR 本文は作成側の欄であり、Issue のコメントはコミットに固定されず削除できるため、受け皿にしない

### 4. G-2・G-3・G-4 のレビューの条件

判定者本人のレビューであれば、状態(APPROVED / CHANGES_REQUESTED / COMMENTED)を問いません。判定者が仕様 PR の作成者である構成に限定を置きません。理由は、G-2・G-4 が確定であって独立した確認ではないためです([ADR-0060](/process-compass/adr/0060-drafting-context-and-two-layer-independence/))。ブランチ保護が作成者本人の APPROVED を止めるのは「1 名の確認で取り込めない状態を作る」という別の目的の規則であり(ADR-0067)、確定の記録を巻き込む理由になりません。

- 本文の 1 行目に宣言行を書く(`G-4: 通過` / `G-4: 差し戻し / 基準 N / 期限 YYYY-MM-DD`)。続けて確認した項目を見出し語で書く。宣言行の無い承認は取り込みの事務であり、G-2・G-4 に数えない
- 対象の版はレビューの `commit_id` である。集約が `commit_id == マージ時の head` を検査し、ずれた変更は「確定していない版を取り込んだ」として欠落に数える。人は「機能の ID + PR 番号」を書き、マージ後のコミットの識別子は集約が併記する
- この承認を G-6 の独立した人の確認に数えない。QMS 対応表の G-2・G-4 の行にその旨を書く
- 様式は後退経路である。レビューが既定であり、様式は対象が PR でないときにだけ現れる。「同じ結果を導く手続を 2 つ持つと緩いほうが使われる」には当たらない

### 5. 写しは承認と同じ時期に機械が取り出し、記名者と判定される側が書き換えられない場所へ置く

写しに含める最小の組は、レビューの識別子・状態・`commit_id`・`submitted_at`・アカウントの数値の識別子とログイン名・本文・PR 番号・マージのコミット、および同じ期間の bypass と保護の変更の記録です。取れないプランでは「取れない」と写しに書きます。写しは要約と評価を含まず、附属書G の投影と区別します。ホスティングの監査ログは 180 日で消えるため、写しを出荷判定(G-7)の時点で初めて作ることは認めません。

### 6. 基底ブランチへ入れるのは遅くとも出荷判定(G-7)。入れる操作に記名者以外の承認を課さない

- 判定記録と写しを基底ブランチへ入れるのは、遅くとも G-7 である
- 記録だけのコミットを基底ブランチへ入れる操作に、記名者以外の承認を課さない。ADR-0057、第5章 CI/CD、ADR-0067 の一般化である。帰属の裏づけは記名者本人の操作(署名コミット、または記名者の承認レビュー)とする。裏づけの無い記録は、記名が自己申告であることを保証の開示へ出す。残る記録 PR に他者の承認が付く場合、それは取り込みの事務と明記する
- G-7 の PR に写しを同梱する場合、CI が同じ集約を再実行して一致を検査する。G-7 で判定される側は出荷の範囲の変更の作成者と指示者であり、出荷判定者ではない([ADR-0066](/process-compass/adr/0066-shipping-approver-separation-and-development-line/))。「判定の材料を、判定される側が同じ変更で用意できない形にする」に触れない
- 停止の解除と例外承認の台帳は、現行どおり基底ブランチへ先に入れる

### 7. 既定ブランチの強制層を、写しのために縮小しない

bypass actor を足しません。`exempt` を用いません。「マージごとに Bot が bypass で既定ブランチへ写しを入れる」案を採らない理由は、ホスティングでできないからではなく、強制層の縮小([ADR-0038](/process-compass/adr/0038-detection-handoff-of-control-weakening/))に当たるためです。強制層に置いた項目だけが遮断できたものとして数えられる以上、この構成は「App の名義の変更は人の承認を経ない」と開示してしか成立しません。組織が bypass を伴う構成を選ぶことは禁じません。ただし、`state:needs-platform` の経路で統制の弱化として記録し、本標準の既定にはしません。

決定5〜7 を両立させる置き場の形(既定ブランチの外の記録用ブランチ、CI の成果物)は、準拠テンプレートが決めます。[ADR-0035](/process-compass/adr/0035-separation-by-execution-context/)の、ファイルの形式と配置を標準で規定しないとした型です。第一候補は、`non_fast_forward` と `deletion` だけを置き、`pull_request` と bypass のどちらも置かない記録用ブランチです。規制業と CL2 以上では `required_signatures` を加えます。実機で確かめてから降ろします。

### 8. レビューを記録と認める条件を標準に書く

- 成立の条件(第4章): 欄の充足、書き手が判定者本人、`commit_id` による対象の特定、承認の後の push による失効(G-6)または `commit_id == head` の検査(G-2〜G-4)、承認者ごとの最後の状態、変更要求の本文に満たさない基準の項目番号と期限
- 保全の条件(第5章 QMS 文書管理): アカウントと実在の人の対応表と数値の識別子、レビューの意味(宣言行)の事前の定義、写しの取り出しの時期と保持、組織の文書管理規程の対象に写しを含めること、PR の承認が電子署名の要件を自動的に満たさないこと
- 条件を満たさないホスティングでは様式へ戻る。ツールを変えても成立要件は変わらない(ADR-0036 の却下表の判断を保つ)

### 9. 規制業(軸C)・CL2 以上(軸E)は、変更ごとの G-6 の判定記録と監査対応書式を維持する

文言を「承認レビューは機械が出す欄の出所になる。判断の中身の監査対応書式と変更ごとの記録が無ければ記録にならない」へ改めます。「変更ごとの記録を G-7 で承認レビューから機械生成する」案は、査察で受理された一次事例が無いため採らず、差し替え条件へ送ります。

### 10. 形骸化の抑止は既存の手段で足りる。観測値は合否にしない

挙動要約の形(8 文字以上、承認の語だけでない)、同一の文の検出、変更の規模(ADR-0058)、検出能力の測定、内部監査の抜き取りで足ります。承認までの時間・コメントの有無・差分量は観測値として出し、内部監査のリスクに基づく抽出の条件に加えます。閾値を置けば最短経路が「閾値の直上で承認」になるため、合否にしません([ADR-0059](/process-compass/adr/0059-no-approval-ratio-trigger/))。「機械が見るのは形だけ」の限界(EV-0083)は、レビューの本文に置いた欄にも掛かります。

### 11. QMS 対応表の語を改める

| 箇所 | 改める前 | 改めた後 |
| --- | --- | --- |
| 列名 | 成立の条件 | 承認の記録として扱う条件 |
| G-7 の行 | 判定記録のマージ | 判定記録を基底ブランチへ入れること。入れる操作に記名者以外の承認を課さない |
| G-2・G-4 の行 | (無し) | 判定者本人のレビュー(宣言行つき)。この承認は独立した人の確認(G-6)ではない |
| G-8 の行 | (無し) | 決断の記録はテンプレ4 に残す。承認操作だけでは記録にならない |

第4章と対応表に実質の対立は無く、語の誤りでした。

### 12. 1 名体制で変わる範囲を明記する

1 名体制(`checks-only.json`)では、G-2・G-4 を仕様 PR への本人のレビューで記録でき、機械が出す欄の手入力が消えます。本体 PR の基底の更新による再承認の往復は、本決定では軽くなりません(#296)。ルールセットを使えないプランでは、記録の日時が自己申告であることを保証の開示へ出します。

## 影響

- 第4章「判定の成立」に、媒体の非限定、欄の出所、記名者以外の承認を課さないこと、保持を書いた。ADR-0036 決定1 に無かった根拠水準マーク(EV-0109)を、ここに置いた。採用済み ADR の本文は書き換えないため、ADR-0036 には足していない
- 第4章 G-2 にレビューの条件を足した。G-6 に小節「レビューを判定記録とする条件(適用: G-6。規制業の監査対応書式を除く)」を、見出しに適用範囲を併記して新設した。G-7 基準5 に、基底ブランチへ入れる時点と写しの突合を足した
- 第5章 QMS 文書管理の対応表の語と保全の条件を改めた。Label Mailbox の図から `docs/gates/` を外した(置き場は準拠テンプレートによる)。CI/CD に、写しの取り出しと G-7 の PR 上での再生成の検査を足した
- 第6章 テンプレ4 の冒頭に、機械が出してよい欄の注記を足した。規制業の注記の文言を決定9 のとおり改めた。附属書G に、写しと投影の区別を足した
- 第8章の規制業の注記、附属書I 要件⑦(実環境の識別の鍵に写しのパスとレビューの識別子)、フェーズ6 プロセス内部監査のリスクに基づく抽出の条件を改めた
- 実装マーク IMPL-0124〜IMPL-0129 を足した。対象は、記名者以外の承認を課さないこと、機械が出す欄の写しと出所の併記、写しの取り出し、変更要求の本文の項目番号と期限、記録だけの PR の承認者と記名者の照合、G-2・G-4 のマージ後の識別子の併記である。記名者以外の承認を課さないことの降ろし先は、新規登録した `rulesets` である。GitHub のルールセットはパス単位の免除を持たないため、`state=undelivered` で表示し続ける
- `template-fields.yaml` のテンプレ4 に、「提出日時」と「非同期コメント期間」を機械が出す欄として omit に登録した。既存の欠落を、判断の記録として埋めた
- 準拠テンプレートは、次を改める。`/gate` スキル(レビュー本文の雛形、様式は後退経路、記名者は記録 PR へ push しない手順)。集約と次の一手のスクリプト(写しと記録用ブランチを読む)。出荷の証跡のワークフロー(写しを置き場へ出し、G-7 の PR 上で再生成する)。記録用ブランチのルールセット。CODEOWNERS(誘導層。遮断に数えない)。rulesets の README
- 以前の手順で作った判定記録は、書き換えない。次の判定から新しい手順を使う

## 実機確認

2026-10-23 に pit-in-template の PR #53 で確かめました(確認後にクローズし、ブランチを削除しました)。

| 対象 | 結果 |
| --- | --- |
| PR 作成者本人が COMMENTED レビューを提出できる | できる。`state: COMMENTED`、`commit_id`、`submitted_at`、`user.id` が付く |
| 後続の push の後も COMMENTED レビューが残り、`commit_id` が元のコミットを指し続ける | 残る。head が進んでも状態と `commit_id` は変わらない。`commit_id == head` の検査でずれを検出できる |

## 根拠水準マーク

決定6 と決定2 の理由に置いた判断のうち、本 ADR に属するものは次の 2 つです。第4章・第5章・第6章・第8章・フェーズ6 に置いた判断のマーク(EV-0109〜EV-0114、EV-0117〜EV-0119)は、それぞれの節にあります。

:::caution[暫定 EV-0115 / 見直し 2027-04]
**対象**: 承認の回数を増やさないことが 1 件の承認の重みを保ち、記録 PR の第三者承認の廃止が形骸化の抑止になるという判断(決定6)。
**根拠の水準**: E1(間接)。
**差し替え条件**: 採用組織で、記録 PR の廃止の前後の挙動要約の形の充足率と、内部監査の抜き取りの結果。

根拠は、承認の求めが増えると、人は中身を見ないまま承認する傾向を示すという、隣接する領域の報告です。エージェントの権限プロンプトのうち 93% を中身を見ずに許可したという値はベンダーの自己報告であり、PR の承認への外挿は実証されていません。
:::

:::caution[暫定 EV-0116 / 見直し 2027-04]
**対象**: 「重い手続は記録を消す」という知見を判定記録へ適用し、人が書く欄を判断の中身に絞ること(決定2)。
**根拠の水準**: E1(間接)。
**差し替え条件**: 準拠テンプレートで人が書く欄の数を変えた前後の、記録の件数と欠落の件数。

根拠は、医療のインシデント報告の様式の欄を 16 から 7 へ減らしたところ、報告の件数が 7.7 倍になったという別領域の単一研究(出典台帳の 236b)です。開発プロセスの判定記録での実証はありません。
:::
