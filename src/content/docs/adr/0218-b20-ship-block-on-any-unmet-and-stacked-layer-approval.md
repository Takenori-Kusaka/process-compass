## ステータス

採用(2026-11-18)。束 B20 の重の件のうち、IMPL-0738(未達のまま出荷が止まらない穴)と IMPL-0498(層の合わさりの承認の数え方)の決定です。

[ADR-0136](/process-compass/adr/0136-spec-recheck-by-string-match-and-human-filing-of-drift/) の決定4(層の合わさりの承認の数え方は変えない)を置き換えます。ADR-0136 の本文は書き換えません。[ADR-0028](/process-compass/adr/0028-unmet-gate-distinct-from-omitted/)(未達と省略の区別)・ADR-0055・ADR-0088・ADR-0113 とは矛盾しません。審議の記録は `research/448-deliberation/b20-decision-heavy.md`(2 節・3 節)です。

## コンテキスト

- 第8章の表は、CL1 以上と規制業の案件は未達のまま出荷しないと定める。ところが集約は、人員不足の出荷できない状態(shipBlocked)と、判定の確認の未達でしか止めなかった。手で `unmet: []`・`g3: omitted` と書いた構成は、契約検査の照合(`unmet[]` と `gates` の相互参照だけ)をすり抜ける
- 実行で確かめた。未達を生む処理は2種(G-6 と G-3)で、G-3 は「スタックが未確定、かつ PoC でない」ときだけである。スタックが確定していれば未達は0件で、典型の初期状態で出荷が永久に止まることはない
- 層の合わさりの承認は、条文(IMPL-0250)が「数えない」と定めるのに、集約は PR ごとに数え続けました。ブランチを消す運用では、`refs/pull/N/head` を取得しないと先頭を読めない(使い捨てのリポジトリで確認)

## 決定

1. CL1 以上の案件と規制業の案件は、未達の種類を問わず、集約の記載の欠落に数える。解く道は未達の解消だけとする。CL0 で規制業でない案件は、現行のとおり開示と G-8 の受容で出荷できる
2. 欠落の元は、構成の `unmet[]` と、回答とスタックから導き直した G-3 の未達の和とする(`config.mjs` の `unmetShipBlockers`)。G-3 の条件と記載は `detectUnmet` と共有する1か所に置く。構成の手書きに頼らない
3. 止まるのは出荷判定(集約の exit 1)で、マージは止めない(IMPL-0769 と同じ強さ)。CL1 以上で種類を問わず止めることは、規格の条文に先例が無く、**本標準が足す**。例外承認は未達を解かない(第7章 7.3)
4. 層の合わさり: 基底が既定ブランチ以外の写しで、その層自身に有効な承認が無いもの(X)の `merge_commit_sha` が、既定ブランチへ入った PR(Y)の `head_sha` の祖先なら、Y を確認ありに数えない(理由 `stackedLayer`)
5. 履歴を読めないときは、数えない側へ倒す(理由 `stackedUnconfirmed`)。浅い取得、または Y の先頭を取得できないときである。Y の先頭があり、浅い取得でなく、祖先でないとき(X の版が無い場合を含む)は数える
6. 判定が要るのは承認の無い X があるときだけで、そのとき Y ごとに `git fetch --no-tags origin refs/pull/<Y>/head` を行う。数えなかった結果は、G-7 基準5 の表(`exceptionNeeded`)が既存のとおり扱い、新しい停止は足さない。開示に、承認の無い層の件数・数えなかった件数・未確認の件数・見逃す場面を出す
7. 根拠水準: 0738 は EV-0331、0498 は EV-0332(いずれも E0)。EV-0269(数え方を変えない判断)は対象が消えるので外し、識別子は再利用しない

## 課さないと決めたこと

- 既存の案件への猶予。解消は構成の変更1回で足り、新しい条項になる
- 欠陥ごとのリスク評価を止める条件にすること。評価の定義が標準に無く、機械で閉じない
- 取り込みの後に rebase した変更の検出。patch-id などの近似は決定可能でなく、偽陽性が出る。見逃す場面として開示する
- 拒否の設定(ADR-0124 決定4)。本決定は事後の数え方である

## 検討した選択肢(採らない)

| 案 | 採らなかった理由 |
| --- | --- |
| 未達を人員由来に限る(規格) | 限定の語が条文に無い。判定の確認の未達と独立した安全性の評価の未達が同じ表を引くので、人員由来に限る読みと合わない |
| 条文が名指す未達だけを止める(弁護) | 表は未達を名指して限定していない。G-3 だけを外す根拠が無い |
| R1 の例外承認で解除する(現場) | 例外承認は未達を解かない。7.3 は構成の条件を対象にしない |
| `shipBlocked` に原因の種別を足す(監査) | 前提が事実と違う。`shipBlocked` も集約で止まるので、層を移しても強さは変わらない |
| 層の合わさりを候補の提示にとどめる(現場) | 条文は「数えない」と定める。候補の提示だけでは、機械が規定と逆に数え続ける |
| 読めないときに数える側へ倒す(起案・規格) | 浅い取得で検査を無効にできる。判定が要るのは承認の無い層があるときだけで、数えない側へ倒しても影響は小さい |
| X の承認の有無を条件から外す(弁護) | 層ごとに正当に承認した積み重ねを落とす |
| `base.ref` だけで数えから外す | 標準のスタックと区別できない |

## 影響

- CL1 以上と規制業の採用者は、スタックが未確定で PoC でないと、出荷の証跡の集約が止まる。解消は `/process-change` のスタックの確定1回である
- 手動のスタックを使う採用者は、承認の無い下の層を含む差分への承認が、確認ありに数えられない。例外承認の行が対応づけば、欠落にならない
- 取り込みの後の rebase は見つからず、GitHub の実機での `refs/pull/N/head` の公開と verify ジョブでの再実行は確かめていない。使い捨ての git リポジトリでだけ確かめた
- 確かめていない点: 契約検査(`verify-gate-contract.mjs`)は、手書きの構成を通す。止めるのは集約である(実行で確かめた)
