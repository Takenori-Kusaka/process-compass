## コンテキスト

G-5 の必須の検査 `gate-g5` は、準拠テンプレートでは `pull_request` で動きます。ワークフローの定義も、検査のスクリプト(`scripts/gate/`)も、PR の側から読まれます。同じ PR で集約を書き換える、検査の対象の一覧を空にする、同じ名前のジョブを足すと、その PR の `gate-g5` は通ります。検査を緩める変更が、緩めた検査を通ります。

AI維持管理者の承認(第3章 3.11.2)は、PR の本文の「受け入れた者」の欄の記名で照らしていました。欄は誰でも書け、本人の操作に結び付きません。

「判定のコードを基底から読む」規定は、委任の経路(第5章 5.5.4)と配備(第4章 G-8)にはありました。G-5 にはありませんでした。G-5 は、強制層の中で最も多くの規定が降りている先です。

G-5 の判定のコードは、変更が入った時点から、その変更自身と以後のすべての変更の合否を変えます。ADR-0106 の区分で言えば、事前に効く読み手です。ADR-0109 が事後の検出で足りるとしたのは、判定記録という事後に効く記録の置き場です。本件はその区分の外にあります。

規格は実装を指定しません。検査の定義とロジックの変更を自己承認させない要求は、NIST SP 800-204D(制御面は個々の手順より高い信頼の水準で動く。検査は迂回されうる)、SSDF PS.1.1(設定のコードの保護とコード所有者のレビュー)、SLSA の水準3(技術的な統制の継続の証拠)から導けます。

検討の記録は `research/371-deliberation/` にあります(議題、内部と外部の調査、5 委員の意見、裁定、実機の確認、実装の記録)。

## 決定

### 1. 変更のコードを実行しない判定は、判定のコードと構成を基底ブランチから読む

G-5 の判定のうち、変更のコードを実行せずに行える判定(PR 単位の検査、統制の設定の変更の検出、その承認の照合)は、判定のコードと構成を基底ブランチ(既定ブランチの先端)から読みます。変更の側の差分・本文・ファイルの中身は、データとして読み、実行しません。

**判定のコード**を、判定の定義・判定のスクリプト・それらの読み込み先をまとめた1語とします。定義だけを外へ出す構成は、要求を満たしません。定義が変更の側のスクリプトを実行する限り、スクリプトの書き換えが残るためです。

変更のコードを実行することが目的の判定(テスト・ビルド・静的解析など)は、変更の側で実行します。その結果は信頼しないデータとして扱います(決定3)。

### 2. 基底から読む判定の結果は、check run で出す形に限る

基底から読む判定の結果は、判定の実行そのものの結果(GitHub の check run)で出します。commit status で出す形は採りません。commit status は同じ context の最新の値だけが効き、PR の側のワークフローが後から上書きできたためです(実機の確認 E-4)。

「PR の側から同じ名前・同じ送り手で結果を出せる構成は、外せない形に当たらない」とします。必須の検査の送り手(`integration_id`)の固定は、独立の要求にせず、適合の手段にも数えません。固定が止めるのは、人や外部の資格情報が出す偽の結果だけです。PR の側のワークフローが出す結果は、送り手を GitHub Actions に固定しても区別されませんでした(E-3・E-14)。

手段は指定しません。例は、既定ブランチの定義で起動し、PR のコードを checkout せず、差分と本文をデータとして読む判定(`pull_request_target`)です。`pull_request_target` は唯一の形にしません。送り手の偽装を解かず、PR のコードを取り出して実行すると任意のコードの実行になる誤設定の危険があるためです。

### 3. 統制の設定を変える変更は、本人の承認のレビューを変更の側から外せない形で求める

統制の設定を変える変更は、その変更自身が書き換えた検査に合格しただけでは取り込みません。push した者と別の者、すなわち AI維持管理者が本人のアカウントで出す承認のレビューを、変更の側から外せない形(ホスティングが強制する規則と、決定1 の基底から読む判定)で求めます。

- 照らすのは、人の名簿の数値の識別子である([ADR-0108](/process-compass/adr/0108-roster-matched-by-numeric-account-id/))
- 本文の記名は、承認に数えない
- 向きに依らず掛ける。機械に向きを判定させない
- 照らす場所は2つである。基底から読む判定と、出荷の証跡の集約(G-7)である
- 手段の例は、基底から読む判定の結果を必須の検査にする形、ホスティングが強制するコード所有者の承認、組織のルールセットの必須のワークフローである。例示に留め、適合の手段を1つに決めない

満たせない構成(個人所有・無償のプランで規則を強制できない構成、基底から読む判定を必須にしていない構成)は、未達として開示します。実環境の統制の確認(env-check)に、満たす・満たさない・確かめていないの3値で記録させます。

### 4. 承認の記録を、効力を持つ記録の列挙へ加える

統制の設定の変更の AI維持管理者の承認の記録を、効力を持つ記録の閉じた列挙(第1章 1.4、第4章「判定記録を基底ブランチへ入れる操作」)へ加えます。承認は検査の合否を変えるのに、列挙に書かれていませんでした。記録は承認のレビューそのものであり、帰属は ADR-0106 の (A) と同じ条件で確かめます。

### 5. 1名の体制は自己申告として区別する

1名の体制では、別の者の承認を得られません。作成者が唯一のコード所有者のとき、コード所有者のレビューは何も止めず、作成者本人の承認も拒まれました(E-7 の副次の観測、E-13)。この体制では、席の責任者本人のアカウントの操作を受け付け、承認が自己申告であることを変更ごとに保証の開示へ出します。新しい要求は足しません(ADR-0106 決定3 と同じ扱い)。

席の責任者が変更の作成者である場合(体制が2名以上)は、席の責任者以外の名簿の人の承認(帰属の確認)を要します。本人は自分の変更を承認できないためです。

### 6. 所有する組織の事前の同意の形を定める

所有する組織の事前の同意は、所有する組織が置くホスティングの規則(指名した者の承認のレビューを要する規則)と、指名した者本人のレビューで行う形とします。規則の所在と指名した者はテンプレ8 第9項に記録し、構成へは写しません(ADR-0087 決定3、ADR-0069 決定2)。この形で確かめられない同意は、未達のまま残します。IMPL-0340 は降りていない規定のままです。

### 7. 書き込みの権限を持つ処理は、基底の定義で動かす

マージせずに閉じた PR で、承認レビューの写しのワークフロー(`record-copy.yml`)が PR の側の定義のまま `contents: write` の権限で動きました(E-5)。PR の側の定義で統制が動くという本件の論点そのものであるため、本件で直します。書き込みの権限を持つ処理は既定ブランチの定義で動かし、PR のコードを checkout しません。同じワークフローの誤ったコメント(「マージ後の基底ブランチの定義を読む」)を直しました。

### 8. #369 とは統合せず、条件を渡す

#369(AI レビューの指示を、変更が書き換えられない所から読む。IMPL-0333)とは統合しません。守るもの(指示というデータ)と機構が違うためです。#369 は、本 ADR の基底から読む型の上で実装します。AI レビューは PR の題名・本文・差分をモデルへ渡します。このため、プロンプトの注入によって、変更の側から指示を書き換えられる危険があります。これを #369 への条件として渡します。

## 実機の確認

2026-11-05、所有者の判断(ダイアログで「public の一時リポジトリで行う」)にもとづき、個人所有・public・無償のプランの一時リポジトリで確かめました。確認の後に削除しています。所在は `research/371-deliberation/probe-371.md` です。

| # | 確かめたこと | 結果 |
| --- | --- | --- |
| E-1 | 集約を書き換えた PR で `gate-g5` が通るか | 通った(マージ可能) |
| E-2 | 検査の対象の一覧を空にした PR で、陰性の確認の検査が外れるか | 外れた |
| E-3 | 別のワークフローの同名のジョブで必須の検査を満たせるか。送り手の固定で区別されるか | 満たせた。区別されない |
| E-4 | `pull_request_target` の結果が必須の検査として数えられるか | check run は数えられ、PR の側の同名の成功で上書きされない。commit status は PR の側が後から上書きできた |
| E-5 | `record-copy.yml` がどちらの定義で動くか | 閉じただけの PR は PR の側の定義で動き、条件を消せば `contents: write` で動いた |

| E-11 | fetch と diff だけの判定が PR のコードを実行しないか | PR の `.gitattributes`・`.gitmodules` は実行の経路にならなかった(gitlink は未確認) |
| E-14 | PR の側のワークフローが commit status を出せるか | 出せた。送り手の固定で区別されない |
| E-15 | `pull_request_target` の定義の読み元 | PR の基底に依らず、既定ブランチの定義で動いた |

**確かめていない項目**は次のとおりです。いずれも所有者と別のアカウントを要し、承認の範囲(所有者のアカウントの下の一時リポジトリの作成と削除)の外にあるため行っていません。

- E-7 の本題: コード所有者の判定に、PR の基底の側の CODEOWNERS が使われるか
- E-12: フォークからの PR で、`pull_request_target` が受け取るトークンの権限と秘密情報
- E-13: 専用の名義の AI の担い手が作った PR に、人が承認のレビューを出したとき、ホスティングが承認として数えるか

これらに依る部分の実装マークは、降りていない規定として残しています(IMPL-0460)。準拠テンプレートの `gate-g5-base.yml` と、`pull_request_target` の `closed` を契機とする `record-copy.yml` は、そのままの形では実機で動かしていません。確かめたのは、同じ構造の確認用のワークフローです。

## 採らなかった案

| 案 | 採らなかった理由 |
| --- | --- |
| 開示だけで足りるとする | 緩めた検査を通る経路を塞がない。ADR-0109 自身も、開示は検出と組で採るとした |
| 出荷判定(G-7)の事後の検出だけで足りるとする | 事後の検出は、弱めた検査で通した変更が入った後に効く。事前に効く読み手の区分に合わない。集約そのものも書き換えられる。事後の検出は、決定3 の2つ目の照合の場所として組で採る |
| G-5 の全体を基底の版で走らせる | テスト・静的解析は変更のコードを実行することが目的であり、基底の版では判定の対象を失う。変更のコードを `pull_request_target` で実行すれば任意のコードの実行になる |
| `pull_request_target` を唯一の形にする | 送り手の偽装を解かず、誤設定の危険がある |
| 組織のルールセットの必須のワークフローを必須にする | 個人所有のリポジトリで使えない(E-9)。例示に留める |
| 定義だけを外へ出す | スクリプトの書き換えを防げない |
| 送り手の固定を適合の手段に数える | 偽の status しか止めない(E-3・E-14) |
| 判定だけが持つ資格情報(専用の App の鍵)を要求にする | 1〜2名の体制で鍵の運用を既定にする根拠が無い。個人所有のリポジトリで送り手を固定できるかも確かめていない |
| 本文の記名を承認に数える | 本人の操作に結び付かない(ADR-0106 決定3) |
| 機械に緩める向きを判定させる | 向きの判定は設定の意味の解釈を要し、実効的な偽陽性が生じる。承認は向きに依らず掛ければ要らない |
| 所有する組織と指名した者を構成へ写す | ADR-0087 決定3(正本を1か所にする)と衝突する |
| #369 と統合する | 対象(データ)と機構が違う。独立に降ろせる部分を遅らせる |
| push のパスの制限・マージのキュー・固定した版のスクリプトだけ | 経路を塞がないか、体制・プランへの依存が大きい。push のパスの制限は個人所有・public のリポジトリで使えない(E-10)。マージのキューは変更を含む合成のコミットの定義で動く |

どれも、決めていない事項ではなく、課さないと決めた事項です。

## 所有者の承認待ちの事項

準拠テンプレートの変更(`gate-g5-base.yml` の追加、`record-copy.yml` の契機の変更、`check-pr.mjs` の `CONTROL_FILES` の追加と承認の照合、ルールセットの雛形の必須チェックの追加)は、強制層の変更です。本 ADR 自身の決定3 により、AI維持管理者が本人のアカウントで承認する必要があります。準拠テンプレートの `main` へ入れた時点では、この承認を経ていません。AI維持管理者の席の責任者(所有者)の承認を待つ事項として、ここに記します。承認者の欄と名簿は人が書くため、本 ADR には書きません。

## 影響

- 第4章 G-5: 「判定のコードの読み元」「統制の設定の変更の承認」を新設した。「検査を外す変更の記録」に、受け入れはレビューで成立し、記名を承認に数えないことを足した。効力を持つ記録の表に承認の記録を足した。G-7「保証の開示」の項目1 と記載の欠落の表に足した
- 第1章 1.4: 「判定のコード」の語を足し、効力を持つ記録の列挙に承認の記録を足した
- 第3章 3.11.2: 承認がレビューで成立することを足した
- 第5章 5.5.4・5.5.7: 判定の規則に判定のコードを含むこと、委任の規則の変更が統制の設定の変更として承認のレビューを要することを足した
- 第8章 軸D: 事前の同意の形を足し、IMPL-0340 の注記を改めた
- 附属書H H.6: 項目1 の出所に足した
- 根拠水準: EV-0233(見直し 2027-05)
- 実装マーク: IMPL-0455〜0461。IMPL-0460 は降りていない
- 準拠テンプレート: `gate-g5-base.yml` を足し、ルールセットの雛形4本の必須チェックに `gate-g5-base` を足した。`CONTROL_FILES` に `.github/actions/**` と `.github/gate-node-version` を足した。`record-copy.yml` を `pull_request_target` の `closed` へ移した。env-check に3値の記録を足した。出荷の証跡の集約が承認の無い変更を欠落に数える
- 既存の採用者: 準拠テンプレートの更新を取り込んでも、ルールセットを人が適用し直すまで `gate-g5-base` は必須にならない。その間は env-check が「満たさない」を記録し、保証の開示に未達と出る。採用日(2026-11-05)より前に取り込んだ変更は、承認が無くても欠落に数えない。採用日より後に統制の設定を変える変更は、AI維持管理者の承認のレビューを要する。依存の更新の bot の PR がワークフローを変える場合も対象である
- 準拠テンプレートの `gate-g5.yml` は変えていません。PR の側の `pr-rules` は残り、承認を照らしません(同じ PR で外せるため)
