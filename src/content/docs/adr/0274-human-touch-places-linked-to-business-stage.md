## 決定

### 1. 人が触る場所を、事業ステージ・リスク区分・コア機能の表で書く。「ベースライン」の語をやめる

- 第5章 5.4.2 は、「人がどこで触るかは、事業ステージ・安全重要度・変更のリスク区分で決まる(第8章 軸B の表)」を主語にする
- 次の表を、第8章 軸B の表の後ろへ置き、5.4 から引く。表は既存の定めの索引で、各行に出所の条項を付ける。新しい義務を足さない
- 機械で照らすのは、既にある S×G-6 の升と導出の一致(`check-stage-table.mjs`、IMPL-0447)だけ。R の列の読みは manual と開示する

凡例(重いほうから)

- **前** = 取り込む前に、作成者と別の人が読んで承認する(第4章 G-6)
- **例** = 出荷までに、作成を指示した者以外の人が例外承認を記録する(第7章 7.3)
- **記** = 区分 R1・R2 を、作成を指示した者以外の人が確定して記名する(第4章 G-6 の区分の下限と確定者。G-5 が照らす)
- **後** = 登録した種類の変更を、取り込んだ後に別の人が確かめる(第5章 5.5.4 の条件6。材料が揃うまでと値が無い間は、当月の全件)
- **本** = 作成を指示した本人だけが確かめる。**独立の確認ではない**
- どの行にも掛かる(表に書かない): 本番反映の人の記名(5.4.3 不変条件2・G-8)、認証・認可・個人データ・外部の契約の人の判断(不変条件3)、出荷判定 G-7(S0 は省略)
- 条件: 安全重要度 CL0・標準以上の品質・確認者を置ける体制。承認の人数は全行で 1 名。品質「高」は S0 で G-6 を全変更に適用し、S1 ではコア機能の承認を 2 名にする

| S1・非コア・R3 | 本 | **前** | 本(**減る**) |
| S2・R1 | 前+記 | 前+記 | 前+記(**減らない**) |

- 安全重要度 CL1 以上: すべてのステージで S2 の列(委任は使えない)。変えない
- 表の冒頭に「S2 の R1・R2 は 1 件も減らない」と文で書く。数は本文に書かない(仮定の数で、E0 の値になる)
- 「前」の 1 件の重さは変えない。変わるのは、どの行に「前」が掛かるかだけである

### 2. L1 の監視者の欄を書き換え、独立の確認ではないことを同じ文に併記する

- 5.4.2 の「2026-08-05 時点のベースラインは L1 です」の文と、表の L1 の監視者の欄「人間が全ての変更を確認する」を改める
- L1 の監視者は「作成を指示した人が、エージェントの出力を確かめる」とする。**同じ文の中に**「独立の確認ではない。独立の確認は G-6 による。確認者を置けない体制では G-6 の未達を表示し続ける」と書く。限定を別の段落へ置かない
- 日付つきの能力の記述は、5.3 の前提へ移す
- 自律レベルと担保水準の記号の重なり(L1・L2)は本件に入れない。本件で書き換える文は、裸の「L2」を書かず、「自律レベル L2」「担保水準 L2」と書く。記号の改めは既存の Issue へ寄せる

### 3. 価値確立(S1)では、コア機能に触れる変更だけに取り込む前の承認を求める

- 準拠テンプレートを標準にそろえる。コア機能は、既存の `corePathsOf`(保護するパスと、区分の下限の規則のパスの和)で決まる。新しい宣言を足さない
- 仕組み(1): `gate-g5-base` は、コア機能のパスに当たる PR で、G-6 の承認者の数(1 名。品質「高」は 2 名)を必須にする
- 仕組み(2): S1 のブランチ保護の必須の承認数は 0 にする。必須の検査(`gate-g5`・`gate-g5-base`)は残す
- 仕組み(3): パスが未宣言なら、全 PR で承認を求める。追跡中のファイルに 1 件も当たらない宣言は、未宣言と同じに扱う
- 適用の条件: CL0・標準以上の品質・承認者 1 名。規制業で承認者 2 名の S1 と、安全重要度 CL1 以上は現行のまま(承認 1 名以上を保護で要する)
- 保証の開示(項目2)に、承認数 0 で承認をパスによって掛けていることを書く。承認の後は `gate-g5-base` の最後の実行を再実行する。承認の取り下げでは再実行されないため、出荷の証跡の集約が最後の状態で照らす
- **実機の確認が済むまで、「準拠テンプレートはこう動く」と書かない**。実装マークは undelivered で表示する(決定11)

### 4. 承認数 0 を問題に数える既存の検査には、S1・コア機能に限る構成のルールセットだけ例外を設ける

- 既存の検査(IMPL-0416)は、PR を課すルールセットで承認数 0 を問題に数える(パス条件で足し戻す構成を既定にしない)。S1・コア機能に限る構成は、まさにこの構成を既定にする
- 承認数 0 のルールセットのうち、必須の検査に `gate-g5-base` があるものだけを問題に数えない。標準の側の文(承認数 0 を問題とする定め)に、この構成の扱いを同じ行の中で書く
- 理由: 所有者の決定(価値確立ではコア機能に触れる変更だけに承認)を、必須の承認数ではなく必須の検査で実現する以上、この形になる

### 5. S2 は、いまの値のまま。S2 の組織が S1 と宣言し続ける誘因を開示する

- S2 の R1・R2 の行は本 ADR で変えない。読む件数は減らない
- 偽って低く宣言する誘因は、現行より増える。S2 の規模の組織が S1 と宣言し続けると、コア機能に触れない変更が、取り込む前の独立の確認なしに入る。機械ではステージの宣言の真偽を確かめられないため、止められない(ADR-0065 の却下表で、成立を機械で確かめる手段が無いと決着済み)。開示で受け、根拠水準のマークを付ける

### 6. 「作るのを止める」を「確認の依頼を積み増さない」へ狭める

- 第4章 G-6 の確認者の負荷の制御2 の要求は、「確認者が上限に達している間、新しい判定依頼を積み増さない」だけにする。「生成を止める」の語をやめる
- 作成側が何に回るか(表の「本」「記+本」の行の変更、仕様、テスト、負債の返却)は手引きに置く。要求にすると、R1・R2 を担う者が R3 へ偏る誘因になる
- **取り込みの停止は床として残す**。「前」の行の変更は、確認者が空くまで取り込まない。R1・R2・コア機能に限らず、「前」の行のすべてである。GC の「帯域を理由に判定を省略しない」は変えない
- 押し寄せたときの並べ方(R1・CL1 以上・コア機能を先)は手引きに置く
- 所有者の理由(「アサインしたリソースを空いたまま待たせることは不可能」。0272)との関係: 止めるのは依頼の積み増しで、人と AI の手は止めない。確認の済まない変更を取り込まないことは、手を空けることではない。両立すると判断した。ただし、作る量が確認の量を恒常的に超えると、確認待ちの在庫は増える

### 7. H.4 条件4 は文言を変えず、注記を 1 文足す

- 条件4(AI の推定による判定を検出の層として数える条件)は変えない
- 決定可能な条件(ステージ・リスク区分・パス・構成)で、人の確認の時点や範囲を変えることは、条件4 の対象外である
- AI のレビューの通過を理由に人の確認を減らすことは、条件4 が禁じる。所有者の決定にも入っていない
- この 2 つを分けて、H.4 の既存の注記と同じ型で 1 文を足す。既存の注記は、委任に事前確認が無いのは AI の確認を通過したためではなく 5.5.4 の 7 条件のためだ、と書く
- 理由に書く事実(`external-02-anthropic.md`。取得は 2026-11-27。WebFetch の要約を含む。出典台帳への登録は別の段):
  - Anthropic の公開の実務は 2 つに割れる。AI のレビューは承認せず、阻止もしない。承認は人に残す
  - 一方、Claude Approvals の既定の例は、Code Review の通過を条件に必要な人数を 2 人から 1 人へ下げ、Claude が承認する
  - 同じ文書が、分類器の答えは PR の作成者が書いた文で誘導されうると自ら警告し、重要なパスには分類器を読まない規則で著者以外の人 1 人を求めるよう勧める。既定は観察モードで始まる
  - 軽減の下での見逃しの率・障害率は公開されていない。数値の大半は自己報告で方法が薄い
  - 「取り込みの後に人が見る」公開の実務は、取得した範囲に見つからなかった
- 条件4 の維持は「実証に基づく」判断ではなく、「未実証の軽減を入れない」判断である。根拠水準のマークで開示する

### 8. 本 ADR は、安全重要度・品質の緩和を足さない

- CL1 以上・品質「高」・規制業では、緩めない。品質「高」の S1 は、コア機能の承認を 2 名にする(`rules-quality.yaml` の `coreReviewerCount`)
- 品質「高」・CL1 以上では、取り込み後の確認の形(別の ADR)も使わない

### 9. ADR-0050 との突合の結論

- ADR-0050 決定1 は、軸B が動かすのは「ゲートの有効・省略と、記録の厳格さ」で、強制層に置いた規則そのものを動かさないと決めた
- 本 ADR の連動は、ステージによって G-6 の適用範囲(軸B のゲートの有効・省略)だけを動かす
- 強制層の規則は動かさない。G-6 を適用する変更は承認を要し、記録の無い変更は出荷できない
- S1 の非コアは、軸B の表で G-6 を適用しない範囲として扱う
- 決定3 の「遮断の範囲の誤り — 範囲を絞る」に当たる。決定4 により、遮断の範囲を記述した記録(IMPL-0471 の開示の文)を、同じ変更で更新する

## 課さないと決めたこと

「書かれていない」と区別します。

| 論点 | 課さないこと | 理由 |
| --- | --- | --- |
| S1 の非コア | 独立した人の事前の承認 | 所有者の決定。ADR-0065・0112 が既に決めたこと |
| ステージの宣言の真偽 | 機械の検査 | 成立を機械で確かめる手段が無い(ADR-0065) |
| 作成側の回る先 | 表の升で名指す要求 | 手引きに置く。要求にすると R3 へ偏る誘因になる |
| 在庫 | 判定待ちの件数と最古の滞留日数の表示 | 誰も動かない数を出すと、読まれない証跡が増える(後継の出荷の前の確認では別の理由で表示する) |
| 記号 | 自律レベルと担保水準の記号の変更 | 本件の範囲外。既存の Issue へ寄せる |

  - `scripts/gate/material-attribution.mjs`: 承認数 0 の検査の例外
- 準拠テンプレートの文には、条項(章・節)だけを引き、ADR 番号を足していない
- 採用者への影響: S1 の非コアの変更は、承認を待たずに取り込める。コア機能の PR は、別の人の承認(挙動要約つき)の後の再実行で通る。パス未宣言の構成は全 PR に承認を求める。S2・CL1 以上・規制業は変わらない
- 失うもの: S1 の非コアの変更に、取り込む前の独立の確認が無い。コア機能のパスの宣言が古い・漏れていると、事業の約束を担う機能の変更が、独立の確認なしに入る。失うのは価値責任者と顧客である。歯止めは、未宣言なら全変更・親と HEAD の版の和で判定・名前の変更の元を含む(既存)と、S1 から S2 で全変更へ戻ること
- 実機の確認(未実施。段 F1): ルールセット `team-core` を GitHub が受け付けること、非コアの PR が承認なしでマージできること、コア機能の PR が止まり、別の人の承認の後の再実行で通ること、承認の後の push で承認が失効すること、パス未宣言で全 PR が止まること
- **案D へ退く条件**: 実機で、承認数 0 と必須の検査の組み合わせが、非コアの変更を通し、コア機能の変更を止めることを確かめられなかったとき
  - 準拠テンプレートの 2 コミット(S1 の承認の変更)を戻す
  - 本文は実態を開示する形にする。「標準は S1 の非コアに独立の確認を課していない。準拠テンプレートは全変更に承認を求める(標準より厳しい)」
- 実機の限界: 試験用リポジトリは所有者のアカウント 1 つで動かすので、別の人の承認で通る側は実機で確かめられない(自分の PR は承認できない)。止まる側と非コアが通る側だけを確かめ、通る側は fixture の試験に依ると開示する。委任のマージの経路は、必須承認を回避できる専用のトークンが要るので、実機では確かめない
- 本文の側の食い違い: 「承認数はパスで分けられない」という記述は、本 ADR により偽になる。第8章 軸B の表の S1 の行と、IMPL-0416 の文・IMPL-0471 の開示の文を、本 ADR の決定へ書き換える
- 根拠水準: 以下のマークで開示する

:::caution[暫定 EV-0379 / 見直し 2027-05]
**対象**: 人が触る場所を事業ステージに連動させ、S1 ではコア機能に触れる変更だけに取り込む前の承認を求めても、品質の基準を壊さないという判断。
**根拠の水準**: E0(なし)。
**差し替え条件**: S1 の採用組織で、非コアの変更に起因する欠陥の件数と、コア機能の変更の取り込み前の承認で止まった件数の観測。

所有者の決定です。緩めて安全だという実測はありません。議長と 5 委員は、実測が無いことを理由に L1 の値の維持を推していました。
:::

:::caution[暫定 EV-0380 / 見直し 2027-05]
