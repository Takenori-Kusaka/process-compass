本ページは「AI協調型ソフトウェア開発プロセス標準」(以下、本標準)の総則です。本標準は、生成AIを開発の主たる実装主体として組み込みながら、日本の大企業が備える投資決裁・品質保証・監査の統制と接続できる開発プロセスを規定します。

## 1.0 名称

本標準の通称を **ピットイン方式**(PIT-IN)と定めます([ADR-0027](/process-compass/adr/0027-process-name-pit-in/))。

| 層 | 用途 | 名称 |
| --- | --- | --- |
| 通称 | 口頭・検索・リポジトリ名 | ピットイン方式(PIT-IN) |
| 正式名称 | 稟議・QMS 文書・規格の引用 | AI協調型ソフトウェア開発プロセス標準 |

F1 のピット作業は、18〜20名が2秒以下で完了します。レースは止まりません。決められた場所でだけ人の手を入れます。この構成を本標準のゲートに重ねています。

本標準を一文にまとめると、次の要約になります。

- マシンは人間より速い。それでも、決められた場所では必ず人間が触る

![ピットイン方式の全体像。内側の速い AI 協調ループ(仕様承認・AI 実装・自動検証・独立レビュー)のうち、人が触る 2 か所をピットボックスとして示し、外側に事業判断の節目(企画承認・ステージ移行・リリース決裁)の環を置いた図](../../../assets/figures/pit-in/kv-overview.png)

図は2層からなります。内側のループは時計回りに、仕様承認(人)、AI 実装、自動検証(機械)、独立レビュー(人)の4工程を回ります。人が関わる2工程をピットボックスの形で示しています。外側の環は事業判断の節目で、既存の稟議・決裁制度をそのまま使います([第2章](/process-compass/phase4-process-design/lifecycle/))。

## 1.1 目的

本標準の目的は次のとおりです。

- 生成AIを実装主体とする開発において、成果の品質・責任の所在・意思決定の記録を担保する要求事項を定めること
- 既存の品質マネジメントシステム(QMS)または決裁権限規程を有する組織では、それらを置き換えることなく、その上に AI 協調の運用を接続すること
- 組織・事業フェーズ・規模の違いをテーラリング(第8章)で吸収し、同一の成果定義のもとで運用できる状態を維持すること

ここでいう担保は、製品に欠陥が無いことの約束を意味しません。品質を保証する主体は本標準ではなく、本標準を適用した組織です。組織が主張できる範囲と主張しない範囲は 1.9 に定めます。

## 1.2 適用範囲

| 区分 | 内容 |
| --- | --- |
| 適用対象 | 生成AIエージェントを実装・設計・検証のいずれかに用いるソフトウェア開発およびその保守 |
| 適用組織 | 適用対象の開発または保守を行う組織。1名の体制を含む。品質マネジメントシステムと決裁権限規程のどちらも持たない体制を含む |
| 適用フェーズ | 企画・要件・設計・実装・検証・出荷判定・運用の全ライフサイクル |
| 適用外 | AI を一切用いない開発、および本標準の要求事項を既存規程が上位で禁止する領域 |

適用外の領域が存在する場合は、テーラリング(第8章)の記録として除外理由を残します。

適用組織を、既存の規程を持つ組織に限りません([ADR-0068](/process-compass/adr/0068-start-of-application-and-conformance-claim/) 決定6)。品質マネジメントシステムまたは決裁権限規程を有する組織は、本標準をその上に接続します。どちらも持たない体制は、決定の権限を D-0 体制図に記名で定めます([第8章](/process-compass/phase4-process-design/tailoring-guide/)「会議体と体制図の調整」)。

1名の体制を適用組織に含めることは、その体制が品質保証の主張の成立条件を満たすことを意味しません。成立条件は 1.9 と[第4章 G-7](/process-compass/phase4-process-design/gate-criteria/)によります。本標準を適用していると言える時点と、適合を主張できる範囲は、1.10 によります。

本標準は、開発の方式と開発手法の名によって、適用の対象を限定しません。反復型の手法を用いる開発も、計画駆動の開発も、上表の適用対象に当たれば適用の対象です。

本標準は、既存の開発手法との併用の可否・有効性・要素の対応・置き換えを主張しません。既存の開発手法と本標準を併用した案件の記録を、本標準の策定で確かめていないためです。本標準は、反復の周期、チームの会合の持ち方、事業ステージより短い期間の計画の方法を規定せず、採用組織に委ねます。作業の一覧については、[第2章 2.10](/process-compass/phase4-process-design/lifecycle/)が定める事項(スコープ3層、規模の合意、進捗の観測、棚卸しと調整)に限って規定します。他の手法を用いていることと、その手法の名と組み合わせて名乗ることを、本標準は適用の開始に当たる事象として扱いません。適用の表明と適合の主張の根拠としても扱いません(1.10)。対外の文書での書き方は、[附属書H](/process-compass/phase4-process-design/assurance-case/) H.8 によります。

既存の開発手法を用いる組織が、本標準の定める事項と定めない事項を読み分けるための説明は、[附属書A](/process-compass/phase4-process-design/integrated-process/) A.7 に示します。判断の根拠は [ADR-0080](/process-compass/adr/0080-method-neutrality-and-relation-to-existing-methods/)によります。

## 1.4 用語の定義

本標準で用いる主要な用語を次のとおり定義します。用語は後続の章の改訂に伴って追加します。

| 用語 | 定義 |
| --- | --- |
| AI協調ループ | 仕様承認・AI実装・自動検証・独立レビューを機能単位で反復する開発サイクル |
| マクロライフサイクル | 事業ステージの移行によって区切られる低頻度のプロセス階層 |
| 事業ステージ | 不確実性の低減段階を表す区分。S0 探索・S1 価値確立・S2 スケールの3段階(別称: DR0・DR1・DR2) |
| ステージ移行ゲート | 事業ステージの境界に置く制御点。SG-0・SG-1・SG-2。投資継続と移管の可否を判定する |
| 工程ゲート | 1つの開発サイクル内に置く制御点。G-1〜G-8。判定の対象(本表「判定の対象」)を次工程へ進めてよいかを判定する |
| ゲート | 定められた判定者が、定められた基準との突合により次段階への移行可否を判定する制御点の総称 |
| 判定の対象 | 工程ゲートが、次工程へ進めてよいかを判定するもの。技術設計判断(G-3)では技術上の選択であり、判断記録ではない。ほかの工程ゲートの対象は第6章「成果物と様式の対応」による |
| 判定の材料 | 判定者が、判定基準の確認方法として読む記録。判定の対象と同じものとは限らない。G-3 の判断記録(第6章 テンプレ2)と、G-7 の運用引き継ぎ文書(テンプレ5)は判定の材料である |
| 判定の証跡 | 判定が成立したことを示す記録。工程ゲートでは判定記録(第6章 テンプレ4)に限る。判定の材料を、判定の証跡に数えない(第4章「判定の成立」) |
| 結果責任(A) | 成果の正しさに対する最終責任。成果物ごとに1名のみ割り当てる |
| 実行(R) | 実際の作業。AIエージェントは実行を担えるが、結果責任は担えない |
| 席 | ロールの別称。責務と、判定者となるゲートの組。体制が変わっても変わらない。責任者・担い手と対で述べるときに用いる(第5章 5.5) |
| 責任者 | 席の結果責任(A)を負う記名の自然人。席ごとに1名。体制の変化点でのみ変わる |
| 担い手 | 席の作業を実際に行う実行主体。人、または AI の実行主体の文脈。AI の担い手は、モデルの版・指示資産の版・権限の組で識別する |
| 運用形態 | 担い手が席の判断をどこまで進めるかの区分。人確定・協働・委任の3つ。上限は変更ごとのリスク区分で決まる(第5章 5.5) |
| 独立 | 確認する側が、作成を指示した側と別の自然人であること。人の単位でのみ用いる。構成の条件と、変更ごとの条件の2層で定める。構成の条件は、確認する席の責任者が、確認される側の席の責任者と別の自然人であること。変更ごとの条件は、変更を確認した人が、その変更の作成を指示した者と別の自然人であること。安全関連は組織上の独立を重ねる(第3章 3.5.4) |
| 開発ライン | 同一の案件の、開発者の席と独立レビュアの席。作成を指示する側と、それを独立レビュー(G-6)で確認する側を合わせて指す。出荷判定者の席と事業決裁者の席を含まない。この語を、ほかの意味に用いない。複数の案件にまたがる開発の単位は「開発組織」、案件に関わる人の全体は「案件に関与する者」と書く(第3章 3.5) |
| 第三者レビュー | 本標準を適用する組織と別の組織にあり、案件に利害を持たない者による検証。本標準のゲートには無い。独立レビュー(G-6)、同じ組織の別部門による検証、プロセス内部監査を、第三者レビューと呼ばない。同じ組織の別部門による検証は「組織上独立した検証」と呼ぶ |
| 契約上の確認行為 | 委託の契約が定める、発注側が納入物または実施された業務を確認する行為。検収、業務終了の確認、実施業務の確認が例に当たる。何が当たり、どの効果を持つかは、契約による。本標準のゲートの判定は、契約上の確認行為ではない(第8章 軸D) |
| 分離 | 文脈の分離(作業領域・セッション・認証情報が別)と、入力の分離(作成側の説明文・主張・推論の過程を確認側へ渡さない)の総称。分離だけでは独立は成立しない |
| 体制の変化点 | D-0 体制図、テーラリングの入力、担い手の適合性確認の前提のいずれかを変える変化。5種(第3章 3.13) |
| 設計の有効性 | 統制の設定(閾値・除外設定・必須の検査・ルールセット・フック・権限と、それらを動かす検査装置)の値が、規定どおりであること。設定が在ることの確認で示せる |
| 運用の有効性 | 統制の設定で、止まるべきものが実際に止まること。設定が在ることの確認では示せない。統制の設定を変える変更では、陰性の確認(止まるべき違反を通し、止まった結果)で確かめる(第4章 G-5「統制の設定の陰性の確認」) |
| 検査装置 | 強制層の検査(CI の必須の検査、実行前フックと権限設定による遮断)と、それを動かす構成とスクリプト(検査のスクリプト、スタック別の検査の定義、ワークフロー、検査が読む規則データ)の総称。第3章 3.11.3 の強制層の手段と、その実装を合わせて指す。足す・直す・外すの対象であり、強制層への組み込み(追加・削除・統合)は AI維持管理者が承認し、追加の要否は技術判断者が決める(第3章 3.11.2・3.11.4)。[ADR-0073](/process-compass/adr/0073-corrective-action-by-impact-and-control-effectiveness/) の「検査の装置」と同じもの |
| 保証の開示 | 出荷ごとに、独立性の成立状況・外した項目・未実施の検証・検出能力の測定値を1枚で示す記録。既存の記録からの投影。項目の正本は第4章 G-7「保証の開示」、読み方と定型の文は附属書H H.6 |
| 品質保証 | 顧客・社会のニーズを満たすことを確実にし、確認し、実証するために、組織が行う体系的活動(JSQC-Std 00-001:2023 の 1.3)。本標準が定めるのは、範囲・根拠・証拠を伴う品質保証の主張(assurance)であり、契約上の担保(warranty)と結果の約束(guarantee)を含まない(附属書H H.1) |
| 品質保証の主張 | 本標準を適用した組織が、宣言した保証範囲について、品質の要求事項が満たされるという確信の根拠を、証拠・論証・開示とともに示し、その責任を引き受けること。成立条件は第4章 G-7 による |
| トップマネジメント | 組織を最高位で指揮し管理する人または人々。品質保証の方針と受容の基準に記名し、組織の保証の主張の最終責任を負う |
| 品質保証の方針と受容の基準 | トップマネジメントが記名する、組織に1つの1ページの文書(層1)。保証の相手と範囲の方針、受容しない条件、外枠、受容の権限の段階、上申先の5項目。様式は第6章 テンプレ11 |
| 保証範囲 | 組織が品質を保証する対象(製品・リリース・利用条件・期間)。案件の開始時に G-1 で宣言する(層2)。範囲外の成果物について、組織は品質を保証すると主張しない |
| 外枠 | 受容の基準の前提となる、適用される法令・契約の要求事項・整合規格・技術水準・社会の許容。組織の受容の対象ではない |
| 検出の層 | 欠陥や逸脱を見つけるために置く確認のうち、ゲートの判定に数えないもの。AI の推定による確認が当たる。通過しても判定は成立せず、人の確認を減らす理由にもならない。検出率または「未測定」を開示する(附属書H H.4) |
| コンテキスト基盤 | AI に与える文脈の情報を、恒久層と案件層に分けて保守する仕組み |
| 前提 | 確かめないまま成り立つとみなして置き、崩れると成果物に影響する言明。本標準が置いた前提は、成り立っているかを前提の台帳(第6章 テンプレ10)で観測する。案件の前提は、成り立っているかを判定しない。案件層への登録の有無を G-2 基準3 で確かめ、崩れたときの影響を書く。機能仕様の前提の欄に書かれたものは、すべて確かめていないものとして読む(第4章 G-2「前提の欄(基準3)」)。ゲートの「前提条件」(判定を開始するために整っていなければならない状態。第4章「前提条件と判定基準の区別」)とは別の語である |

| 危険源 | 危害を引き起こす潜在的な根源。Hz-nnn で識別する |

| リスク低減ステップ | 危険源への対処の段階。RRS1 実行不能化・RRS2 検知と承認・RRS3 情報提供。順序を入れ替えない |
| 安全関連ソフトウェア | 安全機能の実現・安全状態への遷移・監視と診断のいずれかを担う部分。無条件にリスク区分 R1 として扱う |
| 安全度水準 | 安全関連系に要求される安全性の水準の総称。具体的な指標は適用規格を特定してから確定する |
| 未検証の入力 | AI が生成した出力の初期状態。決定論的な検証を経て初めて成果物になる |
| 故障挿入試験 | 意図的に異常を発生させ、保護方策の動作を確かめる試験 |

:::note
「逸脱」の語は、本文の一部で事象を指して用いています(委任の範囲の逸脱、意図的な逸脱、基準の逸脱、運用の逸脱など)。これらは上表の「逸脱」の定義の外にあり、適合の主張の名に関わりません。事象を指す用例の改名は、別に扱います(Issue #316)。
:::

## 1.7 記述の原則

本標準の記述は次の原則に従います。

- 本文と規定の附属書は、要求事項・推奨事項・許容事項を記述する。設計思想・検討経緯・比較検討は附属書A へ記載する
- 規定の強さは、文末の形で示す。対応は 1.7.1 による
- 説明は、理由の文と注記に書く。規定と説明の読み分けは 1.7.2 による
- 表の升に入れる語は、1.7.3 の語彙に限る
- 同じ事項の規定は1か所に書く。ほかの箇所は、その所在を引く
- 特定の製品名・組織内の口頭文脈に依存する表現は用いない
- AI の能力に関する記述には、その記述が妥当な時点(YYYY-MM-DD)を併記する

### 1.7.1 規定の表現形式

本標準を適用する者が、適合を主張するために満たす要求事項を、文面から識別できるようにします。要求事項と、推奨事項・許容事項・可能性の記述は、文末の形で区別します。本文と規定の附属書に、次の表の形を使います。

| 種類 | 本文(ですます調) | 箇条書き・表(である調) | 意味 |
| --- | --- | --- | --- |
| 要求 | 〜します/〜とします/〜によります/〜しなければなりません | 〜する/〜とする/〜による/〜しなければならない | 適合の主張には、これを満たす。満たさない要求事項が、本標準が条項で条件と代償措置を定めた逸脱(1.10.2)に限られる範囲は、逸脱を伴う適合の主張になる |
| 禁止 | 〜しません/〜してはなりません | 〜しない/〜してはならない | 要求の否定の形。強さは要求と同じ |
| 推奨 | 〜することを推奨します/〜することが望ましいです | 〜することが望ましい/〜を推奨する | 特に適していると本標準が判断した選択。ほかの選択を排除しない。従わなくても適合する |
| 推奨しない | 〜しないことを推奨します | 〜しないことが望ましい/非推奨 | 適していないと本標準が判断した選択。禁止ではない |
| 許容 | 〜してよいものとします/〜して差し支えありません | 〜してよい/〜してもよい | 本標準がこれを認めている |
| 可能性・能力 | 〜できます/〜場合があります/〜ことがあります | 〜できる/〜場合がある/〜ことがある | 起こりうること、または行う力があること。本標準の許可ではない |
| 外部の制約 | 〜とされています/〜と定められています | 〜とされている/〜と定められている | 法令など、本標準の外が定めること。本標準の要求事項ではない |

- 本文と規定の附属書の地の文で、平叙の動詞文(「〜します」「〜しません」)は、要求事項として読む。「〜しなければなりません」と「〜します」の強さに差は無い
- 文末の「〜できます」を、許容の意味で使わない。許容には、表の許容の形を使う。「〜できます」は、可能性と能力の記述に限る
- 依頼の形(「〜してください」)と「〜すべきです」を、規定の文末に使わない。強さが決まらないためである
- 箇条書きと表の中の体言止めは、見出しの文または列の見出しが示す種類として読む

:::caution[暫定 EV-0096 / 見直し 2027-04]
**対象**: 規定の表現形式の表(1.7.1)の日本語の文末と、JIS Z 8301 の表現形式との対応。および、文末の書き分けが適合の判定のばらつきを減らすという前提。
**根拠の水準**: E1(間接)。
**差し替え条件**: JIS Z 8301 の原本で確かめた表現形式の表との照合の結果。書き直しを終えた章について、別の読み手2名が要求の文を数えて食い違った件数。

種類の立て方(要求・推奨・許容・可能性と能力・外部の制約)と、表に無い形を規定に使わないという決まりは、ISO/IEC 専門業務用指針 第2部(第9版、2021)の箇条7 によります。原典で確かめました。日本語の文末は、本標準が定めた対応です。JIS Z 8301 は第三者の転載でしか読めていないため、同規格の文を引いていません。本標準の文末が同規格の表現形式と一致するとは主張しません。文末の書き分けの効果を測った結果も、見つかっていません。
:::

### 1.7.2 規定と説明の読み分け

次のものは説明です。要求事項として読みません。

- 理由の文。文末が「〜ためです」「〜からです」の文
- 注記(`:::note`)、根拠水準のマーク(`:::caution[暫定 …]`)、図、例
- 定義と事実の記述。名詞または形容詞で結ぶ文(「〜です」)
- 主語が「本標準」である文。「本標準は〜を課しません」「本標準は〜を定めません」は、課さないと決めたことの表明であり、本標準を適用する者への禁止ではない
- 参考の附属書の記述(1.5)

要求事項を、名詞で結ぶ文と注記に書きません。規定として効かせる事項は、1.7.1 の要求または禁止の形で書きます。

平叙の動詞文が説明か要求かを、機械は判定しません。迷う文は要求として読みます。要求の取りこぼしより、説明が要求として読まれるほうが安全なためです。

### 1.7.3 表の升に入れる語

| 升が示すもの | 使う語 | 意味 |
| --- | --- | --- |
| 工程ゲートの状態 | 適用、簡略、統合、省略、未達 | テーラリングの規則が定める結果([ADR-0028](/process-compass/adr/0028-unmet-gate-distinct-from-omitted/))。組織が選ぶ余地を示す語ではない |

### 1.7.4 検査と、その限界

`npm run check` は、本文と規定の附属書について、依頼の形と「〜すべき」の文末、廃した升の語を検出します。参考の附属書については、要求と禁止の文末、実装マークを検出します。廃した言い回しの登録簿に載せた句は、公開ドキュメントと準拠テンプレートの全体から検出します。書式は[規定の表現形式の検査](/process-compass/community/provision-forms/)によります。

「〜できます」が許容か能力かを、機械は判定しません。平叙の動詞文が要求か説明かも、判定しません。この2つは、人が読んで確かめます。

### 1.7.5 組織が書く基準の読み替え

本標準は、組織が書く基準(受入基準、品質保証の方針と受容の基準、テーラリングの宣言)に、その基準が緩める理由へ読み替えられる場合の列挙を求めません。列挙が十分かを記録で判定できず、書かれた禁止は守られにくいためです。読み替えへの歯止めは、本標準の各条項の中に禁止として書きます(例: [第8章](/process-compass/phase4-process-design/tailoring-guide/) 軸B「本軸は、未達の表示を動かしません」、[附属書H](/process-compass/phase4-process-design/assurance-case/) H.11)。条項を起草するときの手順は[規定の表現形式の検査](/process-compass/community/provision-forms/)「起草の規則」によります。

規定の目的に反する結果を文言の充足で得てはならない、という一般的な規定も置きません。判定者に目的への照合を求めると、当該ゲートの判定基準だけで判定する決まり([ADR-0036](/process-compass/adr/0036-gate-closure-by-record/) 決定4)と当たり、判定を記録で再現できなくなるためです。

:::caution[暫定 EV-0128 / 見直し 2027-10]
**対象**: 組織が書く基準に、緩める理由への読み替えの列挙を求めないこと。
**根拠の水準**: E1(間接)。
**差し替え条件**: 附属書H H.11 の表に載らない読み替えが、案件の流出の原因として観測された件数。

基準の書き手に読み替えの列挙を課した規格は、調べた範囲で見つかっていません。書かれた禁止が AI の実行主体に守られにくいことは、独立した複数の測定が示しています。列挙を求めないことの効果は、測られていません。
:::

### 1.7.6 根拠水準のマークの範囲

## 1.9 本標準を適用する組織が主張できること、主張しないこと

**本標準そのものは、品質を保証する主体になりません**。品質を保証すると主張し、その責任を負うのは、本標準を適用した組織です。最終責任はトップマネジメントにあります。本標準は、組織が保証を主張するための要求事項であり、その主張の拠り所です([ADR-0057](/process-compass/adr/0057-organizational-quality-assurance/))。

組織が主張できるのは、次のことです。

> 本標準を適用した組織は、トップマネジメントが記名した品質保証の方針と受容の基準のもとで、宣言した保証範囲について、顧客と社会に対し、品質を保証する。約束する品質を生成より前に人が定め、AI と独立な検証で確かめる仕組みを確立し(確実にする)、出荷ごとに開発ラインの外の記名の自然人が基準の充足と記録の完備を突合し(確認する)、確かめていない範囲と、受容の基準に照らして記名で受け入れた残存リスクを、保証の開示で示す(実証する)。

主張は3つの層で支えます。

| 層 | 内容 | 正本 |
| --- | --- | --- |
| 層1 | トップマネジメントが記名する品質保証の方針と受容の基準。導入時と変化点だけで改める | 第6章 テンプレ11 |
| 層2 | 案件の開始時に、事業決裁者が G-1 で承認する品質の約束と保証範囲 | 第4章 G-1、第6章 テンプレ6 |
| 層3 | 出荷ごとの出荷判定(G-7)と、層1 に照らした残存リスクの受容(G-8) | 第4章 G-7・G-8 |

法令・契約・整合規格・技術水準・社会の許容は、層の外の前提条件(外枠)です。受容の対象ではありません。

主張は、出荷ごとに、保証範囲に入る変更が6つの成立条件を満たす場合に限ります。成立条件と判定は[第4章 G-7](/process-compass/phase4-process-design/gate-criteria/)によります。満たさない範囲は、「品質保証の対象外として出荷した」と顧客へ伝えます。1名体制は、外部の確認者を置かない限り、組織として品質を保証するとは主張できません。

**この保証は、製品に欠陥が無いことの約束ではありません**。組織の保証の主張は、次の事項を含みません。

- 欠陥が無いこと(結果の約束)
- 契約上の担保(仕様への適合や無償の修補の約束)
- 社内の受容が、製造物責任・契約責任・規制上の責任を限定すること
- 機械学習の振る舞いを持つ製品について、その振る舞いの保証(本標準の範囲外)
- 受入基準と試験計画が十分であること
- AI による確認が、独立した人の確認と同等であること
- 人のレビューが全行を読んだこと
- 抜き取られなかった範囲に逸脱が無いこと
- 既存規格への適合(1.3)
- 契約上の責任の帰結

主張の構造、成立条件の読み方、主張を支える条項と証跡の対応、AI による確認の数え方、署名の意味、出荷ごとの保証の開示、対外的に使う表現は、[附属書H](/process-compass/phase4-process-design/assurance-case/)に示します。附属書H は既存の条項からの投影であり、要求事項の正本は各章です。本標準の運用が欠陥の流出を減らしたという測定はありません。主張の成立条件が対外の根拠として足りるかも実証しておらず、根拠の水準は ADR-0057 に開示しています。採用を判断する者の問いへの回答は、[附属書I](/process-compass/phase4-process-design/adoption-guide/)にあります。

## 1.10 適用の開始と適合の主張

本標準を**適用している**ことと、本標準に**適合している**と主張できることを区別します。品質保証の主張(1.9)は、このどちらとも別の主張です。判断の根拠は [ADR-0068](/process-compass/adr/0068-start-of-application-and-conformance-claim/)、[ADR-0083](/process-compass/adr/0083-standard-edition-end-of-application-and-deviation/)、[ADR-0085](/process-compass/adr/0085-adoption-into-existing-repositories/)によります。

適用の単位は案件とします。適用の期間は、適用の開始(1.10.1)から適用の終了(1.10.4)までです。表明と主張は、従う本標準の版(1.10.3)を名指して述べます。

```mermaid
flowchart LR
  B["適用の開始<br/>(宣言の記録)"] --> P["適用の期間<br/>表明: 開始から表明の時点まで数える"]
  P --> E["適用の終了<br/>(終了の記録)"]
  P -.-> C["主張の範囲<br/>開始と終了の間で、1つの版の中"]
```

### 1.10.1 適用の開始

適用の開始は、当該案件のテーラリングの宣言([第8章](/process-compass/phase4-process-design/tailoring-guide/)「調整は宣言を伴う」)を、案件の記録に残した時点とします。準拠テンプレートでは、構成(`process.config.json`)が設定済み(`configured: true`)になった最初のコミットがこれに当たります([準拠テンプレートリポジトリ](/process-compass/phase5-implementation/template-repository/))。

- 適用の開始より前の変更は、本標準の要求事項の対象としない
- 適用の開始の後は、テーラリングで導いた要求事項のすべてを、同時に適用する。満たしていない要求事項は、未達・記録の欠落・逸脱・列挙に無い離脱のいずれかとして表示する(1.10.2)
- 適用の開始の後に、ゲートを順に有効にしていく経過措置を設けない
- 強制の前に、違反に当たる操作を観測するだけの期間を置く場合は、適用の開始より前に置く。適用の開始の後に、強制層を観測だけの設定にしない
- 適用の開始より前の案件について、本標準を適用していると表明しない
- 宣言の記載が欠けていても、適用の開始は動かない。欠けた記載は、記録の欠落として表示する
- 準拠テンプレートでは、適用の開始のコミットに、構成の変更の記録の初期化の記録(`changeLog` の `init`)を同じコミットで書く。無ければ記録の欠落として表示し、適用の開始は動かさない。適用の開始のコミットが検査の範囲(初期化の PR など)にある間は、契約の検査を失敗にする。この記録の欠落は、適用の表明の件数(開始から表明の時点まで)に常に1件として数える
- 再テーラリング(構成の変更)、版の切り替え(1.10.3)、構成の再初期化は、適用の開始を動かさない
- 適用の開始の境は、既定ブランチの主系列(既定ブランチへ順に積まれた変更の列。併合で取り込んだ側の履歴を含まない)の上に置く
- 適用の開始より前の履歴には、履歴の出所(採用者の過去の変更、併合した他のリポジトリの履歴、準拠テンプレートの開発履歴)を問わず、適合を主張しない。出所を識別して、一部の履歴を要求事項の対象に含めたり、対象から除いたりしない。適用の開始の後に併合した履歴も、出所を問わず要求事項の対象とする

#### 既存のリポジトリで適用を始める場合(適用: 既存のコードと履歴を持つリポジトリで適用を始める案件)

既存のリポジトリには、本標準より前からの統制(エージェントへの指示、CI、ブランチ保護、コードオーナーの定め)があります。これらとテンプレートの統制の関係を決めずに始めると、どちらかが**失敗を出さずに外れる**ことがあります(矛盾する指示ファイルの片方が任意に選ばれる。コードオーナーの定めは最初の1か所だけが効き、不正な行は飛ばされる)。次の要求事項は、適用の開始の記録の内容として掛かります。開始より前の準備の活動には掛かりません。

- 適用の開始の記録に、既存の統制の資産の一覧と、資産ごとの扱いを含める。資産は、エージェントの指示ファイル(入れ子のものを含む)、CI のワークフローと必須チェック、ブランチ保護とルールセット、コードオーナーの定め、カバレッジの測定、使う言語と道具の対応(アダプタ)とする。扱いは「取り込む」「置き換える」「残して並存する」「対象外とする」のいずれかとする
- 扱いは、技術判断の席の責任者(人)が記名で確定する。AI の担い手は一覧を起案してよいが、扱いを確定しない
- 機械が検出した資産(準拠テンプレートでは初期化の事前点検の出力)は、一覧に載せる。一覧の網羅を、人の申告だけで示さない
- 統制に効くファイル(エージェントの指示ファイル、コードオーナーの定め、強制層のワークフロー、フックの登録)が、準拠テンプレートの規則を欠いたまま、適用を始めない

判定の対象は、一覧の記録の有無と記名、機械が検出した資産との照合、統制に効くファイルの規則の有無です。一覧が既存の資産を網羅したことそのものは、判定の対象にしません。機械が検出しない資産(リポジトリの外の設定など)の漏れは、実環境の統制の確認([附属書I I.11](/process-compass/phase4-process-design/adoption-guide/) 要件⑦)で補います。

持ち込みの手順は、準拠テンプレートの手引きに置きます([準拠テンプレートリポジトリ](/process-compass/phase5-implementation/template-repository/)「既存のリポジトリへ持ち込む」)。本標準は、次の3つを**採らないと決めました**。

| 採らないこと | 理由 |
| --- | --- |
| 持ち込みの手順の全体を、本標準に置く | 実際の GitHub 上での通しの検証と、python・go の既存のリポジトリでの試行が無い。確かめていない手順に従ったことを、適合の根拠にさせない |
| 資産ごとに順に適用する段階の展開 | 上の「導いた要求事項のすべてを、同時に適用する」と矛盾する。部分的な適用を適合と読ませる |

### 1.10.3 本標準の版

本標準の版は、本標準の保守者が発行したものに限ります。版は「第N版」と発行日で示します。要求事項を変えない改訂は「第N版 修正M」と示します。版の発行・付番・引用の棚卸しの手続は、[本標準の版の発行](/process-compass/community/standard-editions/)によります。

- 適用の表明と2つの主張には、従う本標準の版を書く。発行日を併記する
- 発行していない状態(作業中の版)を、適合の主張と逸脱を伴う適合の主張に名指さない。公開のサイトと配布物の内容が、発行した版と一致するとは限らない
- 適用の表明は、作業中の版を、配布物のコミットの識別とともに名指してよい。適用の表明は件数を併記する事実の記述であり、版の意味の改訂に左右されないためである
- 版の名は、発行の時点のコミットの配布物に限って付く。発行の後に変わった配布物は、作業中の版(第N版の後)として示す
- 従う版は、テーラリングの宣言([第8章](/process-compass/phase4-process-design/tailoring-guide/))と構成に記録する
- 新しい版は、旧い版を置き換える。旧い版に従う案件は、旧い版への主張を期限なく続けてよい
- 追従していない版への適合を主張しない。新しい版への主張は、その版でテーラリングの宣言をやり直した後の範囲に限る
- 版の切り替えに、移行の期間と旧い版の失効を設けない
- 第8章「調整は宣言を伴う」の要求事項4(従う版の宣言)を足す前に書いた宣言と D-0 体制図には、版の記載が無い。版の記載を足すまでは、宣言の記載の欠けとして記録の欠落に数える。準拠テンプレートでは、`/pit` がこの欠けを注記する。版の記載の無い宣言と D-0 を、遡って書き換えない。次に改めるときに版を書く
- 配布物のコミット(機械の識別)は、版と併記する。コミットを版の代わりにしない
- 準拠テンプレートは、自身の検査が実装する本標準の版を宣言する。要求事項の検査を変える準拠テンプレートの更新は、従う版の切り替えと同時に取り込む。従う版を切り替えずに、新しい版の検査だけを取り込まない
- 準拠テンプレートの構成の形式を改めた場合も、移行の期間を設けない。準拠テンプレートの検査は、知らない形式の版の構成を受け付けない。旧い形式の構成の移行は、構成の値(ゲートの状態・席・閾値)を変えない。値を変える必要があれば、記名を伴う構成の変更で行う

版の番号 N を上げる改訂は、要求事項・禁止・適用範囲・判定基準・テーラリングの規則データ・テンプレートの必須欄のいずれかを変える改訂です。どちらに当たるか迷う改訂は、N を上げます。

:::caution[暫定 EV-0158 / 見直し 2027-10]
**対象**: 版の番号 N を上げる改訂と、修正 M に留める改訂の境(要求事項・禁止・適用範囲・判定基準・テーラリングの規則データ・テンプレートの必須欄の変更は N、迷うものは N)。
**根拠の水準**: E0(なし)。
**差し替え条件**: 観測の源は、版の発行の記録(`src/data/edition.yaml` の履歴)と、各版の発行の後に採用者から寄せられた照会です。修正 M として発行した改訂のうち、採用者が要求の変更として読み、宣言のやり直しを求めた件数を数えます。1件でもあれば、その改訂の種類を N の側へ移す向きで見直します。N として発行した改訂のうち、採用者のテーラリングの結果と構成が1つも変わらなかったものが半数を超えれば、N の範囲を狭める向きで見直します。

どの改訂で版の番号を上げるかの境を定めた一次資料は、読めた範囲で見つかっていません。境は、本標準の要求事項の種類から導きました。区分の境が採用者の読み違いを減らすかを測った資料も、見つかっていません(2026-10-24 時点。`research/313-deliberation/`)。
:::

:::caution[暫定 EV-0159 / 見直し 2027-10]
**対象**: 版の切り替えに移行の期間と旧い版の失効を設けず、旧い版への主張を期限なく有効とする定め(1.10.3)。
**根拠の水準**: E0(なし)。
**差し替え条件**: 観測の源は、採用者の構成の版の欄(`standard.edition`)と、版ごとの重大な欠陥の報告です。旧い版に留まる案件の件数と、その版で後から見つかった、安全または品質保証の主張を損なう欠陥の件数を数えます。旧い版の欠陥が判明した後も旧い版に留まり主張を続ける案件が観測されれば、欠陥のある版に限って失効を設ける向きで見直します。観測されなければ、期限を置かない定めを保ちます。

認証の制度(ISO 9001:2015 と ISO/IEC 27001:2022 の移行)は、移行の期間の終わりに旧い版の認証を失効させます。期日で切らず、旧い版のまま続けることを認め、新しい版への適合の宣言だけを禁じる型が、FAA AC 20-115C にあります。本標準には、適合を強制する認証の機関がありません。失効を定めても、確かめる者がいないため、後者の型を採りました。期限を置かないことが、新しい版への追従を遅らせるかを測った資料は、見つかっていません(2026-10-24 時点。`research/313-deliberation/`)。
:::

### 1.10.4 適用の終了

適用の終了は、案件への本標準の適用を終えた記録を残した時点とします。

- 終了の記録には、理由の区分(案件の完了・中止、運用の終了、採用の取り下げのいずれか1つ)、決定した者の記名、終了の日付を書く。準拠テンプレートでは、`/process-change` の終了の種別がこれに当たる
- 終了の記録が無い案件は、適用が続いているものとして扱う
- 適用の終了の後は、現在形の適用の表明をしない。公開の表示(バッジなど)は、期間を示す形へ改めるか外す
- 適用の終了の前の範囲についての主張は、その範囲の記録を保管している間に限り有効とする
- 同じ案件で適用を再開した場合、件数は最初の適用の開始から数える。終了から再開までの空白の期間は、記録の欠落として表示する

**本標準は、適用の一時停止、期日による適用の失効、適用の範囲の縮小を設けません**。意図的な決定です。いずれも、適用の途中を表す状態(1.10.1)と同じく、未達を隠す経路になるためです。適用をやめるときは終了を記録し、再び適用するときは再開として扱います。

:::caution[暫定 EV-0161 / 見直し 2027-10]
**対象**: 適用の終了を1つの事象(終了の記録)で定め、一時停止・期日の失効・範囲の縮小を設けず、同じ案件の再開では件数を最初の開始から数えて空白を記録の欠落とする定め(1.10.4)。
**根拠の水準**: E0(なし)。
**差し替え条件**: 観測の源は、採用者の構成の変更の記録(`changeLog` の end)と、終了の後の公開の表示です。終了の記録の件数と理由の区分の内訳、再開した案件の件数、終了の後に現在形の表明が残った件数を数えます。一時停止に当たる運用(終了と再開を短い間隔で繰り返す)が観測され、空白の記録の欠落が理由で再開をあきらめた案件が出れば、一時停止の状態を設ける向きで見直します。観測されなければ、1つの事象の定めを保ちます。

外部の制度は、認証の終了・縮小・一時停止・取消しを、別々の事象として定めています(ISO/IEC 17065:2012 の箇条7.11 の見出しと、認証機関の運用規程による。本文は二次の資料でしか読めていません)。案件の終結を終了の事由とした一次資料は、見つかっていません。本標準は認証の制度を持たないため、事象を1つに絞りました(2026-10-24 時点。`research/313-deliberation/`)。
:::
