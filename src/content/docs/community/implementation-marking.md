本標準の規定は、案件の実行層へ降りて初めて実行主体へ届きます。降りていない規定は、**案件からは「規定がない」ものとして扱われます**。

実際に、次の事象が続きました。

| 案件からの申し立て | 実際 |
| --- | --- |
| ロールとセッションの対応づけの規定がない | 第3章 3.5.1 にあった |
| 段階的なエスカレーションの規定がない | 第7章 7.6 と D-0 第4節にあった |
| 強制層の変更が事業決裁者へ直行してしまう | `state:needs-platform` という経路があった |

いずれも公開されており、リンクも通っていました。**読まれる場所に無かっただけです**。

本規約は、規定と降ろし先の対応をマークして追跡可能にする書式を定めます。

## 何を追跡するか

対象は「実行主体の挙動を制約する規定」です。全条項を対象にしません。維持できない台帳は、それ自体が降りていない規定になります。

| 対象にする | 対象にしない |
| --- | --- |
| 実行主体が守るべき禁止・権限・経路 | 背景・根拠・比較の記述 |
| 案件の構成へ反映すべき判断 | 組織の制度設計に関する規定 |
| 案件のエージェントが起動時に知る必要のある内容 | 読者の理解のための解説 |
| ゲートの判定者・ロールの席が守るべき手続のうち、様式・スキル・通知へ降ろすもの | 参考の附属書とフェーズ5・6 の頁(手引き)の記述。対応する規範には、本文の所在で付ける |

実行主体には、人の担い手も含みます。[第1章 1.4](/process-compass/phase4-process-design/overview/) は担い手を、人または AI の実行主体と定めます。判定者や人の席を縛る規定も、降ろし先があれば対象です。

参考の附属書と、フェーズ5・6 の頁にはマークを置きません。どちらも規範を持たないためです([第1章 1.8](/process-compass/phase4-process-design/overview/)。[ADR-0086](/process-compass/adr/0086-guide-pages-and-remaining-verbal-forms/))。手引きの記述が本文の規範を実装する手段を示している場合は、本文の所在にマークを付けます。手引きの頁にマークを置くと、規定の表現形式の検査(`npm run lint:provisions`)が失敗にします。

## 書式

規定の直後へ、HTML コメントとして置きます。読者には表示されません。**開示ではなく追跡のためのマーク**であり、[根拠水準のマーク](/process-compass/community/evidence-marking/)とは目的が異なります。

```markdown
<!-- impl IMPL-0001 target=config-roles state=delivered check=machine test=template/scripts/gate/test-roster-rules.mjs note="兼務の禁止を構成へ出力する" -->
<!-- impl IMPL-0002 target=claude-md state=undelivered check=manual plan=scheduled issue=123 review=2027-04 note="...。確かめる者: 計画の Issue(issue= の番号)の担当者(降ろすときに確かめる。それまでは降りていない規定として台帳に出る)" -->
```

見本の Issue の番号(`123`)は架空の番号です。

| 要素 | 規則 |
| --- | --- |
| 識別子 | `IMPL-` + 4桁の連番。**再利用しない**。マークを削除しても番号を空けたままにする |
| `target` | 降ろし先の識別子。`src/data/impl-targets.yaml` に登録されたものだけを使う |
| `state` | `delivered`(降りている)または `undelivered`(降りていない) |
| `check` | 規定の中身を何が確かめるか。`machine`・`presence`・`manual` のいずれか(次節)。**必須**。欠けたマークを検査が落とす |
| `test` | `check=machine` だけに書く。違反と適合の対を持つ試験のファイル(リポジトリの直下からのパス)。**`machine` では必須** |
| `plan` | `state=undelivered` だけに書く。`scheduled`(降ろす予定)または `adopter`(採用者が自ら実装する)。**`undelivered` では必須**(「降りていない規定の扱い」) |
| `issue`・`review` | `plan=scheduled` で必須。降ろす Issue の番号と、見直しの年月(`YYYY-MM`) |
| `decision` | `plan=adopter` で必須。採用者に委ねると決めた記録の所在(ADR など) |
| `note` | 何の規定かを1行で。台帳の見出しになる。空白を含む場合は引用符で囲む。`check=presence` では、規則を運ぶ単位を書く。`check=manual` では、確かめる者を書く(次節) |

- マークはコードの外に置く。囲みのコードブロック・字下げ(4字以上)のコードブロック・行内のバッククォートの中のマークは、台帳に載らず、読者には文字列のまま表示される。検査はこれらのマークを失敗にする(本規約の書式の見本を除く)
- マークは規定ごとに付ける。1つのマークで節の規定がすべて済んだと扱わない

## 検査の手段

「降ろし先がある」ことと、「規定の中身を検査している」ことは、別の事実です。`state` は前者だけを示します。後者は `check` で示します([ADR-0061](/process-compass/adr/0061-check-means-on-implementation-marks/))。

| `check` の値 | 台帳の表示 | 意味 |
| --- | --- | --- |
| `machine` | 機械が確かめる | 機械が規定の中身を検査し、違反を止めるか件数で出す |
| `presence` | 実在だけ確かめる | 機械が確かめるのは、規則を運ぶ単位(欄・キー・行・ファイル)の有無までである |
| `manual` | 人が確かめる | 機械は確かめない。確かめる者と時点を `note` に書く |

- `state` の値は増やさない。`state` と `check` は独立に書く
- `check` を欠くマークを、検査は落とす。[ADR-0061](/process-compass/adr/0061-check-means-on-implementation-marks/) の後に未分類で残っていた 100 件は、[#314](https://github.com/Takenori-Kusaka/process-compass/issues/314) で分類した([ADR-0084](/process-compass/adr/0084-check-strength-plans-and-resident-rules/))
- 迷ったら弱い値を書く。試験が無ければ `machine` にしない。何を読むかを確かめていなければ `manual` にする
- `check=manual` の `note` には、「確かめる者: 」(または「人が確かめるのは」)に続けて、確かめる者と時点を書く。検査は、この語が無い `manual` を落とす。機械の出力はあるが違反と適合の対の試験が無い規定も `manual` であり、その旨を `note` に書く

### `machine` の要件

`check=machine` は、次の3つを満たす規定に限ります。検査(`scripts/check-impl.mjs`)が3つを確かめます。

| # | 要件 | 検査が確かめること |
| --- | --- | --- |
| 1 | 属性 `test` で、試験のファイルを名指す | ファイルが実在する |
| 2 | 試験が、違反の入力で検出する場面と、適合の入力で通る場面の対を持つ | 試験の本文に、目印 `IMPL-NNNN:ng`(違反の入力)と `IMPL-NNNN:ok`(適合の入力)がある。同じ識別子の `:ng` と `:ok` は別の行にある(1つの検査に両方の目印を付けない) |
| 3 | 試験が、必須の集約から実行される | 準拠テンプレートの試験は、集約 `gate-g5` が合否に使うジョブの `run:` から実行される。その手順は、`run:` の行の `\|\| true`、手順の `if:`、手順の `continue-on-error` を持たない(持てば結線の不備として落とす)。本リポジトリの試験は、`package.json` の `check` から `npm run` で辿れる |

- `:ng` の場面は、違反の入力で**検出する**ことを確かめる。検出は、落ちること、または件数・一覧・警告に出ることである。警告や一覧にとどめる規定(承認者の数の警告、既存のテストの変更の一覧など)の `:ng` は、警告や一覧に出ることを確かめる
- 規定が入口(コマンド・スキル)についてのものなら、関数を直接呼ぶ試験では足りない。入口を通す試験を名指す
- **3つの確かめは、試験の中身が規定を正しく確かめていることを示さない**。目印の場面が規定の違反と適合に当たるかは、試験を書いた者と、条項を改めるときの突合で確かめる

### `presence` の単位

`check=presence` は、規則を運ぶ単位の実在の確認に限ります。単位は、欄・キー・行・ファイルのいずれかです。`note` に `単位: 欄` のように書きます。検査は、この語が無い `presence` を落とします。

規則を運ぶ単位より粗い単位の確認は、`manual` です。たとえば、規則の行がある節の見出しだけを確かめる検査や、手順の文を持つファイルの実在だけを確かめる検査が当たります。規則がファイルの中の振る舞い(書き込みを遮断する、手順を順に行う など)にある場合も、ファイルの実在は規則より粗いため `manual` です。ファイルそのものが規則を運ぶ場合(設定のファイルを版管理に置く など)に限り、単位をファイルとします。深さの属性(どこまで確かめたか)は足しません。単位を `presence` の定義で縛り、注記で示せば足ります。属性を増やすと、同じ事実を2か所で書くことになります。

:::caution[暫定 EV-0163 / 見直し 2027-10]
**対象**: 検査の手段を `machine`・`presence`・`manual` の3値で区分し、`machine` に違反と適合の対の試験と集約からの実行を求め、`presence` を規則を運ぶ単位の実在の確認に限ること。
**根拠の水準**: E1(間接)。
**差し替え条件**: 観測の源は、是正の記録(第7章)と、条項を改めるときの突合の記録です。`machine` と記録した規定で、違反が検査を通り抜けた事例が是正の記録に現れたら、`machine` の要件へ試験の内容の確認(目印の場面と規定の突合)を加える向きで見直します。`presence` と記録した規定で、規則が欠けたまま検査を通った事例が現れたら、その単位を `manual` へ移す向きで見直します。どちらも 0 件なら、区分を保ちます。

検証の方法を検査・分析・実演・試験に分け、方法の指定に合否の基準を求める型は、システム工学と航空の規格にあります。規則の試験に陽性と陰性の場面を並べる型は、Semgrep の規則の試験にあります。区分の境界(どこからを `machine` と呼ぶか)が規定の違反の見逃しを減らすことは、測られていません。出典の所在は `research/314-deliberation/survey-314-2-external.md`(F1〜F4、F13、F16)です。
:::

## 降ろし先の登録簿

`src/data/impl-targets.yaml` が降ろし先の正本です。登録されていない `target` を書くと検査が失敗します。降ろし先の欄 `checker` は、降ろし先を検査する準拠テンプレートのスクリプトの名です。マークの属性 `check`(検査の手段)とは別の事実です。

| 種別 | 意味 | 検査の内容 |
| --- | --- | --- |
| `config-key` | 準拠テンプレートが生成する `process.config.json` のキー | サンプル回答から構成を生成し、キーの存在を確かめる |
| `template-file` | 準拠テンプレートに置くファイル | 存在を確かめる |
| `planned` | 準拠テンプレートにまだ無い、置く予定の実装 | 存在を確かめない。`state=undelivered` のマークだけが使える。`delivered` で使うと検査が失敗する |

**降ろし先の実在を機械的に確かめます**。台帳が「降ろしたつもり」の一覧になると、降りていない規定を隠すためです。

`planned` は、まだ無い実装を指すための種別です。これが無いと、降りていない規定のマークも実在するファイルを指すしかなく、規定と関係の無いファイルが降ろし先として台帳に載ります。実装が入ったら `template-file` などへ改め、`state` を改めます。

## 降りていない規定の扱い

`state=undelivered` は削除の対象ではありません。**降りていない事実を表示し続けます**。[未達のゲート](/process-compass/adr/0028-unmet-gate-distinct-from-omitted/)と同じ扱いです。

`state` は2値のまま保ちます。降りていない規定をどう扱うかは、別の属性 `plan` で示します([ADR-0084](/process-compass/adr/0084-check-strength-plans-and-resident-rules/))。

| `plan` の値 | 台帳の表示 | 意味 | 必須の属性 |
| --- | --- | --- | --- |
| `scheduled` | 予定 | 準拠テンプレートへ降ろす予定がある | `issue`(Issue の番号)、`review`(見直しの年月) |
| `adopter` | 採用者が実装する | 準拠テンプレートは実装しない。採用者が自ら実装する。**規定は課したまま**である | `decision`(採用者に委ねると決めた記録の所在) |

- すべての `state=undelivered` に `plan` を書く。`scheduled` の Issue は、領域ごとにまとめて起票してよい
- 「課さない」は `plan` の値にしない。課さないと決めた規定は、条項を改め、棚卸しの区分を「対象にしない」の `not-imposed` へ移す
- 次の節の規定は、`adopter` にできない。登録簿は `src/data/impl-no-adopter.yaml` である。一律で AI に委譲できない領域(第5章 5.8.3・5.4.3)、人へ戻す3つの場合(第5章 5.5.1)、人が確定する判断(第5章 5.5.5)、停止の申し立て(第7章 7.11)、統制の弱化の検出(第3章 3.5.5「統制の弱化を検知したときの引き渡し」)が当たる。採用者の実装の有無で統制が消える型の規定だからである
- `adopter` とした規定ごとの、採用者に委ねる理由と採用者に求めることは、[ADR-0084](/process-compass/adr/0084-check-strength-plans-and-resident-rules/) の決定4 の表に記録する。理由を書けない規定は `scheduled` とする
- 見直しの年月を過ぎた `scheduled` の件数を、台帳の冒頭に出す。**合否にも警戒の条件にも使わない**。期日の日数も課さない
- `issue=` が閉じた Issue を名指すことを、**検査は検出しない**。検査はオフラインで実行し、Issue の状態を知り得ないためである。この検出は採らない。Issue を閉じる者は、その Issue を `issue=` に持つマークが 0 件であることを確かめてから閉じる。[#314](https://github.com/Takenori-Kusaka/process-compass/issues/314) を仮に名指した 60 件は、後継の Issue(#355〜#360)の起票の後に番号を改めた。[#316](https://github.com/Takenori-Kusaka/process-compass/issues/316) も同じ扱いとし、後継の Issue の起票まで `issue=316` を仮に置く。起票した後に `issue=` を後継の番号へ改め、`issue=316` のマークが 0 件になることを #316 の閉じる条件とする
- 台帳の降りていない規定の表は、降ろし先の種別で書き分ける。降ろし先が予定の置き場(`planned`)なら、置き場がまだ無い。降ろし先が実在するなら、置き場はあるが規定の全部または一部がそこに無い。無い部分は `note` に書く

降りていない規定を降ろす順序は、次のとおりです。台帳の表もこの順で並べます(表示の誤りは見つけたその場で直すため、台帳の並びは2段目からです)。

1. 表示の誤り(注記が実態と違うマーク)
2. `adopter` にできない規定
3. G-7・G-8 の判定と R1 の決定に関わる規定
4. その他

2段目と3段目は、マークが置かれた節の鍵を登録簿と照らして決めます。2段目は `src/data/impl-no-adopter.yaml`、3段目は `src/data/impl-decision-sections.yaml` です。どちらも下位の節を含みます。注記の語(G-7・G-8・R1)では判別しません。付随の言及(「R1 は10営業日前」など)を拾い、決定に関わらない規定を前へ出すためです。登録簿の鍵に当たる節が無くなると、検査が落ちます。

:::caution[暫定 EV-0164 / 見直し 2027-10]
**対象**: 降りていない規定を降ろす順序(表示の誤り → 採用者が実装するにできない規定 → G-7・G-8・R1 の決定の規定 → その他)。
**根拠の水準**: E0(なし)。
**差し替え条件**: 観測の源は、台帳の履歴(マークが `undelivered` から `delivered` へ変わった時点。git の履歴で数える)と、案件から「規定が無い」と申し立てられた Issue です。段ごとに、降りるまでの期間と申し立ての件数を数えます。申し立てが4段目(その他)の規定に集中して2段目・3段目より多ければ、順序を申し立ての件数と影響から決める形へ見直します。2段目・3段目の規定の降りるまでの期間が4段目より長ければ、段の順序を守らせる手段を足す向きで見直します(例: 見直しの年月の間隔を段ごとに変える)。どちらでもなければ、4段を保ちます。

未達の統制に順序を付ける外部の型(脆弱性の是正の期日、認証の是正計画)は、統制の種別ではなくリスクの評価で順序を決めます。本標準の4段は、その型を写したものではありません。この順序が、規定の欠けによる手戻りや判断の漏れを減らすことは測られていません。
:::

台帳は降りていない規定を冒頭に置きます。下位の節へ送りません。0件のときも、節と件数の行を出します。

**降りていない規定の件数を、合否にも警戒の条件にも使いません**。件数が少ないことは、規定が降りたことを示しません。マークを付けていない規定は数に入らないためです。逆に、件数が増えたことは、棚卸しで規定が見つかったことを示す場合があります。件数を目標にすると、降りていない規定をマークしないまま残す誘因が生まれます。

:::caution[暫定 EV-0136 / 見直し 2027-10]
**対象**: 降りていない規定の件数を、合否にも警戒の条件にも使わないこと。0件を異常の兆候として扱わないこと。
**根拠の水準**: E0(なし)。
**差し替え条件**: `undelivered` が0件の期間に、案件から「規定が無い」と申し立てられた規定の件数。

0件を異常の兆候として扱う規格は見つかっていません。逆の扱いを支える測定もありません。網羅の側は、未棚卸しの節の件数で示します。
:::

## 運用

- マークを追加・変更したら `npm run impl:write` で台帳(`community/implementation-ledger.md`)を再生成する
- 台帳は自動生成である。**手で編集しない**
- `npm run check` が台帳の鮮度、降ろし先の実在、対象の棚卸しの登録を検査する
- 検査そのものの陽性対照は `npm run test:impl`(`scripts/test-check-impl.mjs`)である。既知の違反を入れて、検査が落ちることを確かめる

## 対象の棚卸し

マークは、付けた規定についてだけ降ろし先を追跡します。付け忘れた規定は台帳に現れません。そこで、対象の頁を節に区切り、**節ごとに、マークの要否を判断したかどうか**を登録します([ADR-0076](/process-compass/adr/0076-inventory-of-implementation-marking-targets/))。

### 母集団と単位

| 項目 | 規則 |
| --- | --- |
| 対象の頁 | 本文の8章と、規定の附属書の各頁。フェーズ5・6 の頁は手引きであり対象にしない(#316 で対象から外し、頁にあったマークは番号を保って本文の条項へ移した) |
| 対象にしない頁 | 参考の附属書、ADR、community の頁 |
| 節 | 見出しと、次の見出しまでの本文。本文の無い見出しは節に数えない。最初の見出しより前の本文は「(冒頭)」の節とする |
| 表の行 | 節の中の番号つきの表の行。番号つきの表は構造で判別する。1列目の見出しが `#` で、本文の行の1列目が番号の表である。2列目の見出しの語(要求事項・手続・記載事項など)では絞らない。行の鍵は、2列目の見出しの語と番号(例: `要求事項6`、`手続3`) |
| 鍵 | 頁の所在 + `#` + 見出しの経路。上位の見出しから ` > ` で連ねる。見出しの適用範囲の注記(`(適用: …)`)は外す |

文末の表現で規範の文を機械で列挙することは、棚卸しの補助に限ります。合否に使いません。文末で作る一覧は閉じず、迷う文を要求として読む規則([第1章 1.7.2](/process-compass/phase4-process-design/overview/))とも合わないためです。

### 区分

登録簿は `src/data/impl-inventory.yaml` です。本文の外に置きます。

| 区分 | 値 | 意味 |
| --- | --- | --- |
| マーク済み | `marked` | 節の、実行主体の挙動を制約する規定のすべてに、マークがあると登録者が判断した。節の中にあるマークを1件以上列挙し、列挙する識別子はすべて節の中に置かれていなければならない。規定の一部を他の節のマークで追う場合は、その節を所在(`location`)に挙げる。番号つきの表の行がある節は、行ごとに `marked` か `none` を書く |
| 判定基準の表 | `kb` | 工程ゲートの判定基準の表。知識ベースへ降りる([ADR-0048](/process-compass/adr/0048-gate-criteria-source-of-truth/)) |
| 対象にしない | `none` | 理由の区分と理由を必須とする。区分は、説明(`explanation`)・制度設計(`org-design`)・所在は他節(`elsewhere`。所在の節の鍵を必須とする)・課さない(`not-imposed`)。節の中にマークが無く、他の節のマークで追う節は、`elsewhere` で登録する |
| 未棚卸し | `pending` | まだ判断していない。基準線にある節だけが使える。番号つきの表の行の区分は求めない |

### 基準線

2026-10-23 の凍結の時点で未棚卸しだった節(857節)を、基準線(`src/data/impl-inventory-baseline.yaml`)にしました。Issue #292 で区分を判断した節は、基準線に含めません。未棚卸しで登録できるのは、基準線にある節だけです。

- **基準線のファイルは編集しない**。検査は、鍵を整列した一覧の要約(SHA-256)を定数で持ち、食い違えば失敗にする。鍵の追加・削除・入れ替えのどれでも食い違う
- 節が消えた基準線の鍵は、残したままにする。検査は無視する
- 新しく足した節と、見出しを改めた節は、鍵が基準線に無い。未棚卸しで登録できず、区分を判断して登録する
- 区分を判断した節を、未棚卸しへ戻さない。検査は、比較の基点(既定ブランチ。CI では PR の基点のブランチ、main への push では直前のコミット)の登録簿を読めるとき、基点で未棚卸し以外だった節が未棚卸しになっていれば失敗にする。読めないときは、比べなかったことを出力する
- 台帳の冒頭に、未棚卸しの節の件数を章ごとに出す

棚卸しの残りは、章ごとの Issue で進めます。

### 検査が失敗にするもの

| # | 失敗の条件 |
| --- | --- |
| 1 | 対象の頁の節に、登録が無い |
| 2 | 登録の鍵に当たる節が無い(見出しを改めた、節が消えた) |
| 3 | 登録に挙げた識別子が台帳に無い |
| 4 | 節の中のマークが、その節の登録に挙がっていない |
| 5 | 「マーク済み」の節の中にマークが無い。列挙した識別子が節の中に無い |
| 6 | 「対象にしない」の節に、マークがある |
| 7 | 区分・理由の区分が閉じた語彙の外にある。理由が空である。所在に当たる節が無い |
| 8 | 番号つきの表の行の区分が欠けている、または節の表に無い行がある(未棚卸しの節を除く) |
| 9 | 基準線に無い節を、未棚卸しで登録している |
| 10 | 基準線のファイルが、凍結の時点の要約と食い違う |
| 11 | 比較の基点で未棚卸し以外だった節を、未棚卸しへ戻している(基点の登録簿を読めるときだけ) |
| 12 | コードの中(囲み・字下げのコードブロック、行内のバッククォート)にマークがある(本規約を除く) |

本標準は、節の本文の指紋(ハッシュ)で登録を無効にする仕組みを課しません。文言の調整のたびに発火し、確認が機械的な更新に変わるためです。節の中身が変わって新しい規定が入った場合は、条項を改めるときの突合で区分を確かめます。これは機械が見ない事項です(次節)。

:::caution[暫定 EV-0135 / 見直し 2027-10]
**対象**: マークの対象を節と番号つきの表の行の単位で棚卸しし、区分を本文の外の登録簿に記録し、未棚卸しの節を凍結した基準線の中に限ること。
**根拠の水準**: E1(間接)。
**差し替え条件**: 棚卸し済みの節で、後から未マークの規範が見つかった件数。

識別子を先に振った閉じた集合へ網羅の検査を掛ける型は、適用宣言書や適合性の試験にあります。節の棚卸しで、付け忘れの規定が減ることは測られていません。区分の判断の一致率も測っていません。出典の所在は `research/292-deliberation/` です。
:::

## 限界

**台帳の件数は、網羅の証明ではありません**。降りていない規定が0件であることも、未棚卸しの節が0件であることも、規定がすべて降りたことを示しません。

機械が確かめることと、確かめないことを分けて示します。

| 機械が確かめること | 機械が確かめないこと |
| --- | --- |
| 対象の頁の節に、区分の登録があること | 節の中の規定が、すべてマークされていること |
| 登録の鍵に当たる節があること | 「マーク済み」「対象にしない」の判断が正しいこと |
| 登録とマークの識別子が台帳にあること | 登録の後に節の中身が変わり、新しい規定が入ったこと |
| 「対象にしない」の節にマークが無いこと | 対象の頁の外(参考の附属書・ADR・community)の規範の文 |
| マークの降ろし先が実在すること(`planned` を除く) | 降ろし先の中身が規定を実現していること(`check` で開示する) |
| 未棚卸しの節が、凍結した基準線の外に無いこと | 比較の基点と比べられない環境(浅い取得・基点に登録簿が無い など)で、区分を判断した節を基準線の中で未棚卸しへ戻すこと |
| 「マーク済み」に列挙した識別子が節の中にあること | 所在(`location`)に挙げた節のマークが、その規定を本当に追っていること |

右の列は、条項を新設・改廃するときの突合で、人が確かめます。**この限界を隠さずに運用します**。

### 逆流を検出できない

本規約が見るのは「規定 → 降ろし先」の一方向だけです。**逆向き、すなわち実行層にしか存在しない規定を検出できません**。

[#223](https://github.com/Takenori-Kusaka/process-compass/issues/223) で、この形の破れが実際に起きました。ゲートを閉じる手続と判定の語彙が標準本文に無く、準拠テンプレートのスキルと様式が事実上の正本になっていました。案件からは「標準に規定がない」と見えます。

| 破れの向き | 見え方 | 検出 |
| --- | --- | --- |
| 規定はあるが降りていない | 案件が規定に気づかない | 本規約のマークで追跡する |
| 実行層にしかない | テンプレートが正本になる | ファイルの単位の逆向きの追跡(下記)と、スキルの文の要求と禁止の文末を持つものの検査(次節)。ファイルの中の規則ごとの逆流は**手段がない** |

ファイルの単位の逆向きの追跡は、次を確かめます([ADR-0084](/process-compass/adr/0084-check-strength-plans-and-resident-rules/))。

- 対象のファイルが、降ろし先の登録簿の `path` か `checker` に現れること。対象は、準拠テンプレートのゲートのスクリプト(`scripts/gate/`・`scripts/init/`)、フック(`.claude/hooks/`)、ワークフロー(`.github/workflows/`)である。エージェントの設定(`.claude/` の直下の `json`)とルールセット(`.github/rulesets/` の `json`)も対象とする。現れないファイルは、除外の一覧(`src/data/impl-untraced.yaml`)に理由の区分と理由を書いて載せる。区分は `library`(他の検査が使う部品)、`infra`(検査の実行の足回り)、`variant`(登録簿の降ろし先の変種・設定)である。`variant` は、同じ規定を運ぶ降ろし先を `of` で名指し、検査が登録簿に実在することを確かめる。どちらにも無いファイルを、検査が落とす
- 試験(`test-*.mjs` のうち、集約から実行されるもの)は対象の外である
- 準拠テンプレートのコード・スキル・様式に書かれた `IMPL-NNNN` が、標準本文のマークに実在すること

次のものは、ファイルの単位の逆向きの追跡の**対象の外**です。規則を運ぶものを含みますが、標準に無い規則を持ち込んでも、この追跡では分かりません。

| 対象の外 | 中身 |
| --- | --- |
| `.github/CODEOWNERS` | 確認者の割り当て |
| `.github/actions/` | ワークフローが使う手順の部品(スタックの準備) |
| `.github/dependabot.yml` | 依存の更新の設定 |
| `.github/ISSUE_TEMPLATE/`・`.github/PULL_REQUEST_TEMPLATE.md` | Issue と PR の様式(PR の本文の欄は G-5 の `pr-rules` が読む) |
| `.github/rulesets/` の `json` 以外(`README.md`) | ルールセットの選び方の説明 |
| `.claude/skills/` | スキルの文(次節の検査が、要求と禁止の文末を持つ文に限って見る) |
| `scripts/vendor/`・`adapters/`・`profiles/`・`templates/` | 知識ベースの複製、スタックごとのアダプタ、構成の型、様式(様式の必須欄は `npm run test:fields`) |
| `.gitignore`・`.ignore` | 版管理と探索から外すファイルの指定 |

ファイルの中の関数や分岐ごとの対応は、追跡しません。機械で閉じた集合を作れず、登録を保守できないためです。登録簿に載ったファイルが、標準に無い規則を持つことは、検出できません。

逆流は、[ADR-0010](/process-compass/adr/0010-data-doc-interface/)が定める正本の向きを崩します。テンプレートは案件が改変できるため、統制の根拠になりません。テンプレートへ規定を足すときは、標準本文の対応箇所を必ず確かめます。

スキルの文については、次節の検査が、要求と禁止の文末を持つ文に限って逆流を検出します。**それ以外の文の逆流を検出する手段は、ありません**。

## 準拠テンプレートのスキルの文

準拠テンプレートのスキルと補助ファイル、`CLAUDE.md` は、本標準の実装です。本標準と食い違う場合は、本標準によります。

スキルの文のうち、要求または禁止の文末を持つものには、次のどちらかを付けます([ADR-0064](/process-compass/adr/0064-skill-provisions-trace-to-standard/))。

| 印 | 書くこと |
| --- | --- |
| `<!-- 根拠: 標準 第5章 5.8.5 -->` | 本標準の所在。複数は「、」で区切る |
| `<!-- テンプレート独自: 理由 -->` | 本標準に対応する規定が無い文。足した理由を書く |

- テンプレート独自の文は、本標準の要求事項を弱めない。本標準と逆の指示を書かない
- 本標準が限定つきで定める事項を、限定を外して書かない
- 所在に書けるのは、本文の節(`第N章 a.b`、`第4章 G-N`、`第N章「節の名前」`)、規定の附属書の節(`附属書B`、`附属書H H.6`)、実装マークの番号(`IMPL-NNNN`)である。参考の附属書は根拠にならない

### 検査の対象

`npm run check` が `scripts/check-skill-provisions.mjs` を実行します(単独では `npm run lint:skills`)。対象は、`template/.claude/skills/` の Markdown と、`template/CLAUDE.md` の構成依存部分(生成区間)の外のうち、次の文です。

| # | 対象 | 印を書く場所 |
| --- | --- | --- |
| 1 | 文末が「〜なければなりません」「〜なければならない」「〜てはなりません」「〜てはならない」「〜ないでください」の行 | その行 |
| 2 | 見出しに「〜てはならない」「禁止事項」を含む節の、箇条書きと表の行 | その行。または、節の見出しの行か、見出しの直後の行 |

検査は、印の有無と、所在の実在を確かめます。

依頼の形(「〜ないでください」)の行は、[#314](https://github.com/Takenori-Kusaka/process-compass/issues/314) で要求・禁止の文末へ書き直しました。検査の対象の文末にも加えています。書き直した後に、同じ形が印なしで戻ることを防ぐためです。

**この検査は、文の所在の追跡です**。AI の担い手がその文に従うことを示しません。振る舞いの評価(同じ指示で複数回試し、従った割合を測ること)は、CI に課しません。非決定的な結果を合否に使うと、偽陽性で落ちる検査になるためです。

:::caution[暫定 EV-0165 / 見直し 2027-10]
**対象**: スキルと `CLAUDE.md` の要求・禁止の文に本標準の所在の印を求める検査を、文の所在の追跡に限り、振る舞いの評価を CI に課さないこと。
**根拠の水準**: E0(なし)。
**差し替え条件**: 観測の源は、振る舞いの評価の記録(同じ指示で複数回試した結果。本リポジトリと採用者が行ったもの、外部の研究)と、振る舞いの評価を CI に入れた案件からの報告です。印のある文の遵守の割合が、印の無い文より高いことが評価の記録に現れたら、印を求める範囲を平叙の否定と太字の否定へ広げる向きで見直します。差が無ければ、印を所在の追跡としてだけ扱い、範囲を広げません。振る舞いの評価を CI に入れた案件から、試行の回数と合格の割合を定めて偽陽性による失敗が生じないという報告が得られたら、振る舞いの評価を CI に課さない選択を見直します。

指示文が読まれ守られる率は低く、効果は研究の間で割れています。文書の走査だけの検査がスキルの効果を示さないことは、外部の調査にもあります。所在の印で遵守が高まるかは、測られていません。振る舞いの評価を CI に入れない選択で信頼性が高まるかも、測られていません。出典の所在は `research/314-deliberation/survey-314-2-external.md`(F20〜F24)です。
:::

### 検査の限界

| 確かめないこと | 補う手段 |
| --- | --- |
| 引いた節の内容と、スキルの文が合っているか | 条項を改めるときに、その節を根拠に持つスキルの行を検索して読む |
| 本標準の要求を、スキルが落としていること | 「規定 → 降ろし先」の向きの実装マーク |
| 平叙の否定(「〜しない」)と太字の否定(「**〜しない**」)で書いた規則 | 手段は無い。件数(太字の否定を含む行と、平叙の否定で終わる行)を検査の出力と[実装の台帳](/process-compass/community/implementation-ledger/)の「スキルの文のうち、検査の範囲の外の否定」に出す。数値は台帳から引き、本頁に書き写さない。スキルの文を改めるときに、人が本標準と突き合わせる。語の整理は [#316](https://github.com/Takenori-Kusaka/process-compass/issues/316) で扱う |
| AI の担い手が、文に従うこと | 手段は無い。振る舞いの評価は CI に課さない(上記) |
| 様式(`template/templates/`)とスクリプトの文 | 様式の必須欄は `npm run test:fields`。スクリプトの文は対象外である |

**検査が通ることは、スキルが本標準と一致していることを意味しません**。
