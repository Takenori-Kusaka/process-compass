仕様・判断記録・プロセス定義をリポジトリ内の Markdown で管理する構成は、変更履歴と承認記録が版管理の機構と一体になる利点があります。一方で、品質マネジメントシステム(以下 QMS)の文書管理要求に対しては、**対応関係を明示しない限り「記録がない」と評価されます**。

本ページは、その対応関係を規定します。

:::caution
**本標準は「ISO 9001 に適合する」とは書きません**。適合の判断は認証機関および自組織の QMS 所管が行います。本ページが規定するのは、文書管理に関する要求へ対応する記録を、どこにどう残すかです。この姿勢は[知財潔白性の扱い](/process-compass/phase4-process-design/gate-criteria/)と同じです。
:::

## 要求と機構の対応

QMS の文書管理が求める事項に対し、本標準がどの機構を当てるかを示します。

| 要求される事項 | 本標準における機構 | 監査で提示するもの |
| --- | --- | --- |
| 識別と記述(表題・日付・作成者・参照番号) | frontmatter の必須項目 | 当該ファイル、および公開ページの見出し部 |
| 様式と媒体 | テンプレート([第6章](/process-compass/phase4-process-design/deliverable-templates/))と CI の様式検査 | 検査の設定と実行記録 |
| 適切性に対するレビューと承認 | ゲート判定([第4章](/process-compass/phase4-process-design/gate-criteria/))と所有者定義に基づく承認 | ゲート判定記録、承認 PR |
| 配付・アクセス・利用可能性 | 公開サイトのビルドと権限設定 | 公開されたページ |
| 変更の管理(版の識別を含む) | 版管理の履歴と、公開ページへ出力した版の識別子 | 履歴、公開ページの版表示 |
| 保持と廃棄 | ステータスによる区分と、履歴の保持 | 廃止した文書とその後継の対応 |

**この表そのものを、監査で最初に提示する資料として保守します**。表がない状態で個別のログだけを示すと、機構と要求の対応づけを監査の場で組み立てる展開になります。

## 承認権限のマッピング

版管理の操作は、それ自体では承認になりません。**どの操作がどの承認へ相当するかを事前に定めた場合だけ、承認として成立します**。

| ゲート | 承認の主体 | 版管理上の操作 | 承認の記録として扱う条件 |
| --- | --- | --- | --- |
| G-2 要件合意 | 価値責任者 | 仕様ファイルの PR への判定者本人のレビュー | 所有者定義で当該者が指定されている。判定者本人のレビューであり、本文の 1 行目に宣言行(`G-2: 通過` / `G-2: 差し戻し / 基準 N / 期限 YYYY-MM-DD`)がある。レビューの状態(承認・変更要求・コメント)を問わない。宣言行の無い承認は取り込みの事務であり、G-2 に数えない。この承認は独立した人の確認(G-6)ではない |
| G-4 機能仕様承認 | 価値責任者または委譲先 | 同上 | 委譲が担当表に記載されている。判定者本人のレビューであり、本文の 1 行目に宣言行(`G-4: 通過` / `G-4: 差し戻し / 基準 N / 期限 YYYY-MM-DD`)がある。レビューの状態を問わない。宣言行の無い承認は取り込みの事務であり、G-4 に数えない。この承認は独立した人の確認(G-6)ではない |
| G-6 独立レビュー | 独立レビュア | PR 承認 | 承認が、独立した人の確認の4条件([第4章 G-6](/process-compass/phase4-process-design/gate-criteria/))を満たす。最後に push した本人の承認はブランチ保護が止める。PR の作成者が AI・bot の場合、作成を指示した者の承認はブランチ保護では止まらず、出荷の証跡の集約が数えずに欠落として出す |
| G-7 出荷判定 | 出荷判定者 | 判定記録を基底ブランチへ入れること。入れる操作に記名者以外の承認を課さない | 開発ラインとの兼務がない([第3章 3.5](/process-compass/phase4-process-design/roles-responsibilities/))。3名未満の体制で兼務する場合は、同章 3.5.2 の4条件を満たし、兼務と代償措置が D-0 体制図に明記されている。この場合は逸脱として表示する |
| G-8 リリース決裁 | 事業決裁者 | 実行環境の承認操作 | 当該者が承認者として登録されている。出荷判定者の席の責任者と同一人物でない(第3章 3.5)。3名未満の体制で同一人物である場合は、逸脱として表示する。決断の記録は[第6章 テンプレ4](/process-compass/phase4-process-design/deliverable-templates/)に残す。承認操作だけでは記録にならない |

- 承認の記録として扱う条件を満たさない操作は、**承認の記録として扱いません**。権限者の指定がない状態での承認操作は、誰でも行える操作と区別できません
- アカウントと実在する人物の対応表は、リポジトリの外側で保守する。この表がない場合、承認者を同定できない(実装は[CI/CD ゲート構成](/process-compass/phase5-implementation/ci-gates/))
- 承認の**対象と意味**を PR の記述へ残す。「マージした」という事実だけでは、何に対する承認かを後から特定できない
- 判定記録を基底ブランチへ入れる操作は事務であり、判定ではない。残る記録 PR に記名者以外の承認が付く場合、その承認は取り込みの事務として扱う

### レビューを判定記録として保全する条件

[第4章「判定の成立」](/process-compass/phase4-process-design/gate-criteria/)は、判定記録の欄を運ぶ媒体を様式のファイルに限定していません。ホスティングのレビューが欄を運ぶとき、そのレビューを判定記録として扱えるのは、上の対応表で事前に対応づけ、かつ次の保全の条件をすべて満たす場合です。成立の条件(第4章)が「判定として成り立つか」を定めるのに対し、保全の条件は「記録として後から読めるか」を定めます。

| 条件 | 内容 |
| --- | --- |
| アカウントと実在の人の対応表 | リポジトリの外側で保守する対応表に、ログイン名だけでなくアカウントの数値の識別子を持つ。退会したアカウントはホスティング上で匿名化され、ログイン名は一定の期間の後に他人が取得できるため、ログイン名だけでは承認者を同定できない |
| レビューの意味の事前の定義 | ゲートの判定に対応するレビューの宣言行(本文の 1 行目)は、案件の構成で判定の前に定める。定めの無いレビューは、承認の操作であって判定記録ではない |
| 写しの取り出しの時期 | レビューの写し(識別子・状態・対象のコミット・提出日時・アカウントの数値の識別子とログイン名・本文・PR 番号・マージのコミット、同じ期間の bypass と保護の変更の記録)は、承認と同じ時期に機械が取り出す。ホスティングの監査ログは 180 日で消えるため、出荷判定(G-7)の時点で初めて作ることは認めない(後掲「提示の準備を監査の直前に行わない」) |
| 写しの保持 | 保管期間の値は、自組織の文書管理規程による(本ページ末尾)。規程の対象に、様式の判定記録だけでなくレビューの写しを含める |
| 電子署名との関係 | PR の承認は、電子記録と電子署名の規制(21 CFR Part 11 の 11.50・11.200 など)が求める署名の構成要素と署名者の認証を、自動的には満たさない。電子署名が要る記録かどうかは、当該領域の所管部門が決める(次項) |

条件を満たさないホスティングでは、判定記録(様式。[第6章 テンプレ4](/process-compass/phase4-process-design/deliverable-templates/))へ戻ります。ツールを変えても、成立要件は変わりません。

:::caution[暫定 EV-0118 / 見直し 2027-04]
**対象**: レビューの写しに含める最小の組と、写しの保持の要求(保管期間の値は定めない)。
**根拠の水準**: E1(間接)。
**差し替え条件**: 監査で提示を求められた記録のうち提示できなかった件数。査察で不足を指摘された項目。

電子記録の規制(21 CFR Part 11 の 11.10(e)・11.50)と ISO 13485 4.2.5 の読みから組んだ項目であり、本標準の採用組織が監査に提示した事例はありません。提示できない記録が 1 件でもあれば、項目を足し、取り出しの周期を短くします。
:::

### 電子署名との関係

署名済みコミットのみを許可する設定は、改ざんへの耐性を高めます。ただし、**規制領域で要求される電子署名の要件を自動的に満たすものではありません**。PR の承認も同じです。医薬・医療機器など、電子記録と電子署名に固有の規制が適用される領域では、要件の充足を当該領域の所管部門と確認してください。本標準はその判断を代替しません。

## 文書のステータス

### 3つの状態を置く

| ステータス | 意味 | AI の参照 |
| --- | --- | --- |
| `draft` | 起案中。承認を経ていない | **参照させない** |
| `approved` | 承認済み。現行の版である | 参照させる |
| `superseded` | 後継の文書へ置き換えられた | 参照させない。後継を参照させる |

`superseded` を置く理由は、承認済みの記録を削除しないためです。判断記録([第6章 テンプレ2](/process-compass/phase4-process-design/deliverable-templates/))は、採用後に本文を書き換えず、新しい記録で置き換えます。

### ステータスの表示に依存させない

AI エージェントが未承認の文書を正式な仕様として参照する事故は、**frontmatter の文字列を読ませることでは防げません**。読解に依存する統制は、読解が失敗した回に破れます。

| 手段 | 信頼性 | 扱い |
| --- | --- | --- |
| ディレクトリを分ける(承認済みのみを参照範囲へ置く) | 高い。参照範囲の指定で機械的に決まる | **既定とする** |
| ブランチを分ける | 高い。ただし運用の負荷が大きい | 規制対象で選択できる |
| frontmatter の値を読ませる | 低い。読解の失敗で破れる | 併用する。単独で用いない |

既定は**ディレクトリによる分離**です。承認をもってファイルを参照範囲へ移動させ、移動の操作を承認 PR に含めます。文脈基盤が収集する範囲の設定は[コンテキスト基盤](/process-compass/phase5-implementation/context-base/)によります。

frontmatter の値は、この分離が正しく行われたかを CI で検査するために用います。**参照の制御ではなく、検査の材料として使います**。

### CI で検査する項目

| # | 検査 | 失敗時の扱い |
| --- | --- | --- |
| 1 | 必須項目(文書番号・版・作成者・承認者・承認日・ステータス)の欠落が 0 件 | マージ不可 |
| 2 | 参照範囲に `draft` または `superseded` のファイルが存在しない | マージ不可 |
| 3 | `superseded` の文書に後継の識別子が記載されている | マージ不可 |
| 4 | `approved` の文書の承認者が、所有者定義で当該文書の権限者である | マージ不可 |

検査4が要点です。**承認者の欄に記入すること自体は、誰にでもできます**。記入された氏名と、実際に承認権限を持つ者の一致を機械で確認しない限り、この欄は自己申告にとどまります。判定記録の記名も同じです。記名者本人の操作(署名コミット、または記名者のレビュー)の裏づけが無い記録は、記名が自己申告であることを保証の開示へ出します(実装は[CI/CD ゲート構成](/process-compass/phase5-implementation/ci-gates/))。

## 版の識別を人が読める形で出す

版管理のハッシュは、監査の場で版の識別子として通用しません。連続性と前後関係を、監査員が確認できないためです。

公開ビルドの時点で、各ページへ次を出力します。

| 出力する項目 | 生成元 |
| --- | --- |
| 文書番号と版 | frontmatter |
| 承認者と承認日 | frontmatter(検査4で所有者定義と照合済み) |
| 最終更新日 | 版管理の履歴 |
| 改訂の履歴(版・日付・変更理由) | 承認 PR の記述から生成する |

**この出力を手で書いてはなりません**。手書きの版表示は実体と乖離し、乖離した表示は監査で「管理されていない」と評価されます。

## 外部監査への提示

### 形式を規程で固定しない

監査で提示する形式(印刷可能な文書、閲覧用のサイト、台帳の一覧)は、監査を受ける相手と時期によって要求が変わります。**本標準は特定の出力形式を義務づけません**。形式を規程へ書き込むと、要求が変わったときに規程の側が破綻します。

規定するのは次の3点です。

- 承認済みの文書の一覧を、文書番号・版・承認者・承認日を含む形で機械的に出力できる
- 個々の文書を、版管理の操作を知らない者が読める形で提示できる
- 提示した内容と、版管理上の実体が一致することを確認する手段がある

### 提示の準備を監査の直前に行わない

出力を自動化していない場合、監査の直前に人手で資料を作ることになります。**この作業で作られた資料は、実体と乖離する可能性が最も高い資料です**。出力は日常のビルドに含め、監査の時点で改めて作らない構成にします。レビューの写しの取り出しも同じです。承認と同じ時期に機械が取り出し、出荷判定の時点で初めて作りません(前掲「レビューを判定記録として保全する条件」)。

## 文書管理以外の要求との対応

文書管理に隣接する要求については、**本標準の既存の規定が実体として対応します**。同じ手続を QMS の語彙で書き直したページは作りません。2か所に持つと、改訂のたびに乖離するためです。

| 要求される事項 | 本標準における規定 |
| --- | --- |
| 内部監査 | [プロセス内部監査](/process-compass/phase6-operation/process-audit/)。実施者の要件、抽出、観点、是正の追跡 |
| 是正処置 | [第4章 G-5「是正の起動」](/process-compass/phase4-process-design/gate-criteria/)(是正を起動する条件と記録の正本。出荷後の Sev1・Sev2 はポストモーテムが記録)、[改善サイクル](/process-compass/phase6-operation/improvement-cycle/)の3区分の仕分けと反映、[インシデント対応](/process-compass/phase6-operation/incident-response/)、[技術負債の返済](/process-compass/phase6-operation/debt-payback/) |
| マネジメントレビュー | [第3章 3.7](/process-compass/phase4-process-design/roles-responsibilities/)の会議体(B-1 IT投資委員会、B-2 ステアリングコミッティ)、および[指標](/process-compass/phase6-operation/metrics/)とゲートの健全性 |
| 設計・開発の管理と、設計・開発の変更 | [第4章](/process-compass/phase4-process-design/gate-criteria/) G-2〜G-4(要件合意・技術設計判断・機能仕様承認の判定記録)、同章「確定した版を変える場合」(確定した受入基準・前提・スコープ外・判断記録を変えたときの判定の受け直し)、判断記録(ADR)、[第3章 3.8.1](/process-compass/phase4-process-design/roles-responsibilities/)(変更ごとのリスク区分と、区分を確定した者の記名) |
| 製品の検証 | 第4章 G-5(機械検査)・G-6(人の確認)、[第5章 5.8](/process-compass/phase4-process-design/human-ai-boundary/)(AI の出力を未検証の入力として扱う)。実施しなかった検証は、出荷ごとの保証の開示に出る |
| リリースの許可と、許可した人の記録 | 第4章 G-7(出荷判定者の記名)・G-8(事業決裁者の記名)。署名の意味は同章「出荷判定者の署名の意味」による |
| 基準を満たさないものの識別と、受け入れの許可 | 第4章の欠陥トリアージ基準と既知の不具合、[第7章 7.3](/process-compass/phase4-process-design/exception-escalation/)の例外承認、未達と逸脱の表示 |
| 変更の管理 | [第3章 3.12.3](/process-compass/phase4-process-design/roles-responsibilities/)(モデルの差し替え)・3.13(体制の変化点)、D-0 体制図の改訂履歴 |
| 識別とトレーサビリティ | 第5章 5.8.2(モデルの版・指示資産の版・検証の記録)、[エージェントの操作の統制](/process-compass/phase5-implementation/agent-trace-control/) |

下の6行は、AI を介した開発成果物をどう担保するかという問いに関わります。主張と証跡の対応、および対応の弱い点は、[附属書H 品質保証の論証](/process-compass/phase4-process-design/assurance-case/)に示します。

- 委任([第5章 5.5.4](/process-compass/phase4-process-design/human-ai-boundary/))を適用した変更のうち、G-6 の判定を事後へ移した変更は、G-6 の承認の記録として扱わない。人の事前確認を経ていない変更として識別し、件数を保証の開示へ載せる。開発者の席だけが委任の変更は、独立レビュアが事前に承認し、その承認を G-6 の記録として扱う
- 組織の外へ渡す保証の開示には、氏名と自由記述を出さない。席の名前と件数で出す([附属書H](/process-compass/phase4-process-design/assurance-case/) H.6「組織の外へ渡すとき」)
- 記録の保管期間の値は、本標準が定めていない。自組織の文書管理規程による。規程の対象に、様式の判定記録と、レビューの写しを含める。判定記録と出荷の証跡が指す記録は、その期間のあいだ到達できなければならない。CI 基盤の既定の保持を、保管とみなさない([第4章「判定が指す記録の保管」](/process-compass/phase4-process-design/gate-criteria/))。GitHub では、成果物の既定の保持は 90 日で、2026-10-01 以降はチェックの履歴も設定の保持期間に従って消える([CI/CD ゲート構成「証跡の保管と CI 基盤の保持期間」](/process-compass/phase5-implementation/ci-gates/))


対応づけは**この表の側で保守します**。個別のページに QMS の条項番号を書き込むと、規格の版が変わったときに全ページの改訂が必要になります。

**箇条の番号は、[附属書H](/process-compass/phase4-process-design/assurance-case/) H.10 の1か所にだけ書きます**。この表には書きません。H.10 の番号と題は、2015 年版の公開されている目次によります。確かめたのは箇条の題までです。ISO 9001 は 2026-09 に改訂版が発行されており(二次情報による)、本標準はその本文を確認していません。読了していない条文を、確かめた対応として示しません。要求事項の本文との対応づけは、自組織の QMS 所管が行います。
