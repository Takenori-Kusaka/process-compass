## 0. 本計画の前提（毎セッション必読）

### 0.1 「実装」の定義
成果物は**コードではなく社会・組織実装パッケージ**である。
規程・ガイドライン・テンプレート・チェックリスト・トレーニング計画・移行ステップを

### 0.2 5つの設計柱（全Issue共通の整合基準）
1. **AI自律レベル動的境界** — 2026年時点で「AIが主導実装・人間はdiffレビューとコンテキスト設計」がL1ベースライン。L2(仕様駆動マルチエージェント)/L3(自己修復)へスライドするロードマップ。
2. **会議体設計とデジタル根回し** — IT投資委員会 / SteerCo / DR会 / リリース判定会の4体制 + 非同期事前レビュー。
3. **Seeded Errors と例外(Bypass)** — 自動化バイアス対策と、特権サインによる期日救済の両立。
4. **三識（知識・見識・胆識）** — 人間を「AIの受動的承認者」にしない評価軸とダッシュボード。
5. **ISO 12100 準拠リスクアセスメント** — D-0成果物として危険源→ソフト故障モード→3ステップ低減→PLr/SIL のトレーサビリティ。

### 0.4 Git 運用（オーナー決定 2026-08-05）
- **main へ直接 push**（PRフローは使わない）。
- コミット単位は Issue 1件 = 1コミット以上。コミットメッセージに `#<issue番号>` を含める。

#### push 手順の注意（graphify pre-push フック）★事故防止

`graphify` の pre-push フックが `graphify-out/` を再生成して**自作のコミットを追加し、自分で push する**。
このため通常の `git push` は、成功時でも末尾に `error: failed to push some refs` を出す（**見かけ上のエラー**）。

```
git push origin main                 # 末尾の error は無視してよい
git fetch origin
git log --oneline -3 origin/main     # ★自分のコミットが載っているか必ず確認
git reset --hard origin/main         # 載っていた場合のみ実行
```

> **YOU MUST**: `git reset --hard` の前に、`git log origin/main` で自分のコミットが
> リモートに載っていることを必ず確認する。リモートが先に進んでいて push が本当に失敗している
> ケースがあり、確認せず reset するとコミットを失う。
> Why: 実際に #98 のコミットを一度失い、`git reflog` → `git cherry-pick <SHA>` で復旧した。

`git pull --rebase` で `graphify-out/` が衝突した場合は、**自分の graphify コミットを
`git rebase --skip` で捨てる**。フックが次回 push 時に再生成するため内容は失われない。

また **`EXECUTION_PLAN.md` は追跡対象ファイル**である。進捗表を更新したら、
`git reset --hard` を実行する前に必ずコミットすること。

### ★Web 検索枠（2026-08-05 判明・重要）

Claude Code の WebSearch には**セッションあたりの呼び出し上限**がある。この環境では **200 回**。
枠は**親セッションと全サブエージェントの合計**で共有され、サブエージェントごとではない。

上限に達すると、検索実行の代わりに次が返る（実測で確認済み）。

```
Web search was not performed: this session has used its web search budget
(200 of 200 WebSearch calls). ... ask the user to raise
CLAUDE_CODE_MAX_WEB_SEARCHES_PER_SESSION.
```

**運用ルール**

- WebFetch（URL 直接取得）は別枠で、上限後も動く。ただしキーワード探索ができないため、
  URL を知らない情報には到達できない
- **1 Wave（調査エージェント 2〜3 本）でおおむね 100〜150 回を消費する**。
  したがって **1 セッションで 2 Wave 以上の調査を回さない**
- 調査エージェントが「検索枠が枯渇した」と報告してきたら、その調査メモは
  **網羅的探索を経ていない**。「未確認」の扱いを厳しくし、次セッションで補完する
- 規格の条項番号など逐語確認が要る Issue（#122・#123 など）は、
  **枠がリセットされた新セッションの先頭で着手する**

### Wave 6（#122・#123）の設計上の注意

**記号の衝突を避けること。これが最大の落とし穴。**

既に 3 つの重大度・リスク体系が本標準に存在する。ISO 12100 系はこれらと**別の軸**であり、
同じ記号を使い回すと現場が混乱する（Wave 1 で DR 記号、Wave 5 で L 記号の衝突を実際に起こしている）。

| 既存体系 | 規定場所 | 対象 |
|---|---|---|
| Sev1 / Sev2 / Sev3 | 第4章 欠陥トリアージ基準 | 欠陥がもたらす技術的影響 |
| R1 / R2 / R3 | 第3章 3.8.1 | 決定の取り消し可能性と影響範囲 |
| L1 / L2 / L3 | 第5章 5.4 | AI自律レベル |
| E1 / E2 / E3 | フェーズ5 ai-environment.md | AI の実行形態 |

→ ISO 12100 の「危害のひどさ」「発生確率」「回避可能性」、および PLr / SIL は
**新しい記号体系として導入し、上表との対応表を必ず作る**こと。

**調査で必ず検証すべき前提**（Wave 5 で Issue 本文の前提が 3 件誤っていた実績がある）

- IEC 62304 は医療機器ソフトウェア規格。**汎用の開発標準ではない**。
  「ISO 12100 / IEC 62304 準拠」と併記することが妥当かを最初に検証する
- ISO 13849（PLr）と IEC 61508（SIL）は**別規格・別体系**。相互の対応表は
  参考情報であって等価ではない。安易に「PLr/SIL」と併記しない
- ISO 12100 は機械安全の規格であり、**AI ソフトウェアのリスクアセスメントへの適用は
  本標準の解釈**になる可能性が高い。適用の妥当性を明記する
- 規格本文は有償で 403 が多い。**条項番号の逐語確認ができない場合、
  「〜に準拠」と書かず「〜の手順を参照した本標準の規定」と書く**

**#121（社会実装・組織移行）と #126（総括）は既存成果物の統合**が主で、
新規の外部調査依存度は低い。検索枠が厳しければ後回しにせず、この 2 件を先にしてもよい。
